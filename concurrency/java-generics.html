Generics

Type parameters, bounds, wildcards and erasure, ending with a generic bounded blocking queue that works for any element type.

Before this:Classes, interfaces and inheritance

Every concurrent container you will use or build is generic: BlockingQueue<E>, Future<V>, ConcurrentHashMap<K, V>, AtomicReference<V>. In a coding round, interviewers expect your own queue, cache or pool to be generic too, and they notice when the types do not line up or when an unchecked cast hides a bug.

In plain words

Think of storage boxes with labels: "cricket balls only". A checker at the warehouse door reads every label and refuses to let a tennis ball into a cricket ball box. That checker is the compiler, and the label is the type argument in List<CricketBall>.

Inside the warehouse, though, the labels are peeled off to save space. Every box looks the same, so a worker inside cannot ask "is this a box of cricket balls?". If someone sneaks a tennis ball past the door through a side entrance, nobody notices until a customer opens the box and finds the wrong ball. Java generics are checked at the door and erased inside. That one fact explains almost every rule in this lesson.

Why this matters for concurrency

  • java.util.concurrent is generic throughout: BlockingQueue<E>, Callable<V>, Future<V>, CompletableFuture<T>, ConcurrentHashMap<K, V>, AtomicReference<V>, ThreadLocal<T>. Reading their signatures, wildcards included, is part of using them correctly.
  • The classic coding problems want generic answers: a bounded blocking queue of T, a cache of K to V, a future of T, an object pool of T. The bounded blocking queue is asked at Rubrik and LinkedIn, Databricks rounds build on the same producer and consumer shape, and the generic version is the natural follow up to the int one.
  • Erasure shapes how containers are built: you cannot create a T[], so real queues such as ArrayBlockingQueue store an Object[] and cast on the way out.
  • A bad cast inside a shared container fails far away, in some other thread, long after the bug. Generics are how you keep that from happening.

What generics buy you

Before Java 5, collections held Object, and you cast on the way out. A wrong element went in silently and blew up somewhere else:

A type parameter is a promise the compiler checks for you: everything that goes into a List<String> is a String, so everything that comes out is one. In a concurrent program, where the producer and the consumer of a queue may be different threads written by different people, that promise is worth even more.

Bounded type parameters

Plain T can be anything, so generic code may only call Object methods on it. A bounded type parameter parameter promises more, so you can call more:

Bounds show up directly in concurrent code. A scheduler's queue of tasks needs elements it can order: PriorityBlockingQueue<E> orders by Comparable or by a Comparator you pass. A type can also have several bounds, such as <T extends Runnable & AutoCloseable> for a task that must also be closed after it runs.

Wildcards

Generic types are invariant: a List<Integer> is not a List<Number>, even though an Integer is a Number. If it were, this would compile and corrupt the list:

Invariance is safe but rigid, so Java adds wildcard types to describe "some type related to T":

WildcardMeansYou canYou cannot
List<? extends Number>A list of some subtype of NumberRead elements as NumberAdd anything except null: you do not know which subtype it holds
List<? super Integer>A list of Integer or some supertype of itAdd Integer valuesRead elements as anything more specific than Object
List<?>A list of some unknown typeRead elements as Object, call size()Add anything except null

The rule of thumb is PECS, producer extends, consumer super: if a parameter produces T values for your method, make it ? extends T; if it consumes T values from your method, make it ? super T.

sum now accepts a List<Integer>, a Set<Double> or a Queue<Long>; fillWithSquares accepts a List<Integer>, a List<Number> or a List<Object>. The concurrency library uses exactly this pattern:

  • BlockingQueue<E>.drainTo(Collection<? super E> c): the queue puts its E elements into c, so c is a consumer.
  • Collection<E>.addAll(Collection<? extends E> c): c produces the elements to add.
  • CompletableFuture<T>.thenApply(Function<? super T, ? extends U> fn): the function consumes a T and produces a U.
  • ExecutorService.invokeAll(Collection<? extends Callable<T>> tasks): the collection produces tasks.

Type erasure: what the JVM actually sees

Generics exist only at compile time. After checking your code, javac erases type arguments: List<String> and List<Integer> both become plain List in the bytecode, a type variable becomes its bound (Object for a plain T), and javac inserts casts where values come out. This is type erasure, and it was chosen so that generic code could run alongside the pre-generics libraries.

Using List without type arguments is a raw type, and putting the wrong type into a generic container this way is heap pollution. Imagine raw.add(42) running on a producer thread and names.get(0) on a consumer thread minutes later: the stack trace points at the innocent consumer. Never use raw types in new code. The consequences of erasure you will meet:

  • No new T() and no new T[n]. The JVM does not know what T is at run time.
  • No instanceof List<String> on an arbitrary object. The type argument is gone at run time, so on an Object only instanceof List<?> (or raw List) compiles. Since Java 16 the compiler does accept it when it can already prove the type argument, for example on a variable of type Collection<String>.
  • No primitives as type arguments. List<int> does not exist, so you get boxing, with its allocation and the traps from objects and references. Specialized classes such as AtomicIntegerArray, LongAdder and IntStream exist for this reason.
  • No overloading on type arguments. void handle(List<String> a) and void handle(List<Integer> b) clash: both erase to handle(List).
  • Static members are shared by every parameterization. There is one Box class, so Box<String> and Box<Integer> share one copy of each static field. A static counter in a generic class is a single shared variable, and needs the same protection as any other.

Generic arrays and the Object[] trick

A ring buffer wants an array of T, and new T[capacity] does not compile. There are three honest options:

  1. Store an Object[] and cast each element on the way out. This is what ArrayBlockingQueue does: it keeps final Object[] items and casts in one small helper. The cast is unchecked but safe, because the only way in is a method that accepts T.
  2. Use a collection instead, such as ArrayDeque<T>, and let it hold the array for you.
  3. Ask the caller for a way to build arrays, as Collection.toArray(IntFunction<T[]>) does: list.toArray(String[]::new).

The tempting shortcut, T[] items = (T[]) new Object[n];, works only while the array never leaves the class. Return it as a T[] to a caller who expects a String[], and the hidden cast fails with ClassCastException in the caller's code. Prefer option 1 and keep the @SuppressWarnings("unchecked") on the smallest possible piece of code.

Build it: a generic BoundedBlockingQueue<T>

Here is the bounded blocking queue from the model problem, made generic and built on a fixed ring buffer. It uses the monitor pattern from producer and consumer: one lock for all the state, a "not full" condition for producers, a "not empty" condition for consumers, and every wait in a loop. Look for the three places generics matter: the Object[] storage, the single unchecked cast, and the ? super T on drainTo.

What each generic decision buys you:

  • Object[] storage with one private, annotated cast. Erasure means the array would be an Object[] at run time anyway; keeping it typed that way stops the array from ever leaking as a fake T[].
  • put(T item) is the only way in, which is what makes the unchecked cast in elementAt safe. Rejecting null keeps "no element" unambiguous, the same choice ArrayBlockingQueue makes.
  • items[head] = null after taking. A queue that keeps references to taken elements keeps them alive for the garbage collector: a slow leak of large objects.
  • drainTo(Collection<? super T>) lets a queue of Order drain into a List<Order>, a List<Record> or a List<Object>.
  • The same class serves Order and String with full type checking, and consumers never cast.

drainTo may partially succeed if the destination throws. The queue updates its count after each completed transfer and signals freed capacity in finally, so its remaining contents stay usable. A destination that adds an item and then throws may retain that item while it also remains queued: this is not a transaction across both containers. The caller must coordinate destination access, and its add method must not call back into this queue or create a lock cycle while the queue's lock is held.

Worked example: reading real signatures

Generic signatures in the JDK look intimidating until you read them as "who produces, who consumes". Four you will meet:

  1. <U> CompletableFuture<U> thenApply(Function<? super T, ? extends U> fn), on a CompletableFuture<T>. The method introduces its own type U, the result type. The function consumes the future's T, so ? super T lets you pass a Function<Object, String>; it produces a U, so ? extends U lets it return a subtype. The result is a future of U.
  2. <T> List<Future<T>> invokeAll(Collection<? extends Callable<T>> tasks). You hand in a collection that produces tasks, perhaps a List<MyTask> where MyTask implements Callable<Integer>, and get back one Future<Integer> per task, in the same order.
  3. V computeIfAbsent(K key, Function<? super K, ? extends V> mappingFunction), on a ConcurrentHashMap<K, V>. The function consumes the key and produces a value; with Map<String, List<Order>>, k -> new ArrayList<>() works because an ArrayList<Order> is a List<Order>.
  4. static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll), in Collections. T must be comparable with itself or with one of its supertypes, which lets a subclass of a comparable class qualify. The odd Object & is an erasure detail: it makes the erased return type Object, matching the signature max had before generics existed.

The method is always the same: find each type parameter, then ask of each wildcard whether that argument hands values to the method or takes values from it.

Common mistakes

  • Raw types such as List or BlockingQueue without type arguments. They switch the checks off and allow heap pollution.
  • List<Object> where you meant List<?> or List<? extends T>. A List<String> cannot be passed as a List<Object>.
  • Exposing (T[]) new Object[n] from a method that returns T[]. The caller's hidden cast fails. Keep an Object[] and cast elements.
  • Suppressing unchecked warnings on a whole class. Put @SuppressWarnings("unchecked") on the one method or variable whose cast you have proven safe, with a comment saying why.
  • Expecting a static field to be per type argument. All parameterizations share one class and one static field.
  • Boxing in hot paths because a generic API forced Integer. Look for a primitive-specialized alternative.

In the interview

Two places. First, quick theory: "What is type erasure?", "Why can't you create a generic array?", "What does ? super T mean?". Second, and more often, in the coding round itself: after you write an int bounded queue or an LRU cache of strings, the follow up is "make it generic", and the interviewer watches how you handle the array and the casts.

Java generics are checked at compile time and erased at run time, so a List<String> and a List<Integer> are the same class. That is why I cannot write new T[n]: I store an Object[] and cast on the way out in one private method, which is safe because put only accepts T. That is exactly how ArrayBlockingQueue does it.
For parameters I use producer extends, consumer super: drainTo takes a Collection<? super T> because the queue puts its elements into it, and addAll takes a Collection<? extends T> because it reads from it.

Follow ups to expect: "Why is List<Integer> not a List<Number>?" (invariance prevents adding a Double through the wider type; arrays allow it and throw ArrayStoreException), "Can a generic class have a static field of type T?" (no: there is one static field for all parameterizations), and "How is this different from C++ templates?" (see below).

Senior depth

  • Java generics versus C++ templates. A C++ template is stamped out as separate code for every type it is used with, with full type information and no boxing. Java compiles one class for all type arguments and erases them, which keeps binaries small and old code compatible, at the cost of boxing, casts and no run-time type arguments.
  • Getting a type at run time. When code really needs the type, pass it explicitly: a Class<T> token (EnumMap takes one), or a factory such as Supplier<T> or IntFunction<T[]>.
  • Generic varargs can pollute the heap. A T... parameter is an array, and an unsafe alias can permit incompatible elements to be written into it. @SafeVarargs promises that the implementation does not perform unsafe operations on that parameter; the compiler does not prove the promise. Retaining the array is not automatically unsafe: Arrays.asList safely retains its backing array.
  • Recursive bounds. class Enum<E extends Enum<E>> and <T extends Comparable<? super T>> look circular but just say "comparable with its own kind". The ? super T lets a subclass inherit compareTo from a comparable parent and still qualify.

Key takeaways

  • Generics move type errors from run time, possibly on another thread, to compile time.
  • Bounds such as <T extends Comparable<? super T>> let generic code call methods on T.
  • Producer extends, consumer super: ? extends T to read T values, ? super T to write them.
  • Erasure means one class for all type arguments: no new T[], no instanceof T, shared statics, boxing for primitives.
  • Generic containers store Object[] and cast in one place, made safe by a typed way in.
  • A generic bounded blocking queue is the bounded queue problem plus three generic decisions: storage, one cast, and ? super T on drainTo.

Write code
Add boolean offer(T item, long timeout, TimeUnit unit) throws InterruptedException to the generic BoundedBlockingQueue<T>: it waits at most the timeout for space, and returns false if the queue is still full.
Model answer

awaitNanos returns an estimate of the time remaining, so each spurious or stolen wakeup uses the remaining condition-wait budget instead of starting a fresh timeout. This is not a strict deadline for the entire call: initial lock acquisition is not timed, and scheduling or lock reacquisition can delay return. The loop re-checks the condition after every wakeup, the lock is released in finally, and InterruptedException propagates so callers can cancel. It is the same shape as ArrayBlockingQueue.offer.

Explain
Explain type erasure to an interviewer and give two consequences you would hit while writing a generic thread-safe container.
Model answer

Java checks generic types at compile time and then erases them: the bytecode has one class for all type arguments, type variables become their bounds, usually Object, and the compiler inserts casts where values come out. It was designed that way so generic code could interoperate with the pre-generics libraries.

Two consequences for a container. First, I cannot create a T[], so a ring buffer stores an Object[] and casts elements in one private method with @SuppressWarnings("unchecked"); the cast is safe only because the single way in is a method that accepts T, which is exactly how ArrayBlockingQueue works. Second, primitives cannot be type arguments, so a Queue<Integer> boxes every element, which costs allocation and garbage collection on a hot path; if that matters I would use a specialized primitive structure. I would also mention that static fields are shared across all parameterizations, so a static counter in a generic class is one shared variable needing synchronization, and that a raw type can sneak a wrong element in, which then fails as a ClassCastException in whichever thread reads it.

Design
You are writing a small task runner with a method that accepts a batch of tasks and returns their results. Choose the parameter and return types, explain each wildcard, and say what the method should do if one task throws.
Model answer

I would mirror invokeAll: <T> List<Future<T>> runAll(Collection<? extends Callable<T>> tasks). The type parameter T is the result type, chosen per call. The collection only produces tasks for me to read, so it is ? extends Callable<T>, which lets a caller pass a List<PriceCheck> where PriceCheck implements Callable<Price>. Returning List<Future<T>> in the same order as the input lets the caller match results to tasks.

A task that throws should not break the batch: each task runs inside its future, so its exception is captured and rethrown, wrapped in ExecutionException, only when the caller calls get() on that future. The method itself should wait until every task has finished, propagate InterruptedException if the waiting thread is interrupted, and cancel the unfinished tasks in that case. If I also offered a callback variant, its parameter would be Consumer<? super T>, because the callback consumes results.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"You have written an integer blocking queue. Make it generic and explain why the array and the cast are safe."
What a strong answer covers
  • Introduce a type parameter with typed insertion and removal methods
  • Erasure prevents creating new T[capacity]; retain a private Object[]
  • Keep the unchecked element cast in one small helper with a documented invariant
  • Only typed insertion may populate occupied slots; raw aliases or exposed storage would break that proof
  • The existing lock, wait predicates and signalling still provide concurrency safety
  • Clear removed slots and never return an Object array disguised as a concrete element array
How a senior would say it
I would parameterize the queue with T, accept T in put and return T from take. The storage stays a private Object array. Java checks type arguments at compile time and erases them, so the generic class cannot create an array with T as its runtime component type. I would put the unchecked element cast in one small private helper and explain its invariant: every occupied slot was written through the typed insertion method, and no caller can access the array. That makes the cast justified as long as callers do not bypass the API with raw types or unchecked casts. I would suppress the warning only at that helper, not across the whole class. Generics do not change the concurrency proof. Head, tail, count and array accesses still use the same lock, waits still recheck their predicates, and successful operations signal the appropriate condition. After removal I clear the slot so the queue does not retain the element unnecessarily. I would never return the Object array pretending it was a String array, because the caller's runtime cast would fail. The result is one queue implementation with checked element types, plus the same explicit synchronization that made the integer version safe.

Likely follow up: What if callers need a correctly typed array of the queued elements?

Out loudabout 75 s
"Your queue holds Orders. Why should drainTo accept a collection of Object, and how would you write the wildcard?"
What a strong answer covers
  • The destination consumes queue elements, so use Collection<? super T>
  • A queue of Order can drain into collections of Order or its supertypes
  • Collection<T> is unnecessarily restrictive because generic types are invariant
  • ? extends T describes a producer and cannot safely accept arbitrary T values
  • Wildcard bounds provide type safety, not locking or atomicity of the transfer
  • Preserve queue invariants if destination insertion throws, and define destination access rules
How a senior would say it
The destination consumes elements from the queue, so I would accept Collection<? super T>. For a queue of Orders, that permits a collection of Order, Record if Order is a record, or Object. Every one of those can hold an Order. A plain collection of T is too restrictive because generic types are invariant: a list of Object is not a list of Order. Using extends would reverse the guarantee. The destination might then be a collection of some narrower subtype, and inserting an arbitrary T would be unsafe. That is producer extends, consumer super, applied from the method's perspective. The wildcard only proves that the types fit. It does not make a transfer atomic across the queue and destination, or protect another thread reading the destination. I would specify how callers coordinate access to that collection. I would also handle an insertion that throws: already removed items must be reflected in the queue's count, and waiting producers must be signalled for the space actually freed. Type correctness and synchronization are separate obligations.

Likely follow up: Could draining into a collection whose add method acquires another lock introduce a deadlock?

Out loudabout 75 s
"A consumer throws ClassCastException while reading a List of String that another thread populated. The code compiled. Where do you look first?"
What a strong answer covers
  • Investigate raw types and unchecked casts at the producer or container boundary
  • Erasure allows a polluted Object-backed collection to store an Integer without checking String
  • The compiler inserts a String cast at typed retrieval, so the symptom appears in the consumer
  • Trace all aliases and writes, remove unchecked entry paths, and keep warning suppression narrow
  • Check publication and collection synchronization separately; generics do not make ArrayList thread-safe
How a senior would say it
I would trace how values entered the list, especially raw aliases and unchecked casts. A declaration saying list of String is a compile-time promise, not a runtime check on every insertion. If a producer treats an ordinary ArrayList as a raw List and adds an Integer, the insertion can compile with a warning and succeed. The list stores Object references after erasure. Later, when the consumer assigns a retrieved element to a String, the compiler's inserted cast fails. The consumer's stack trace identifies where the bad value was discovered, not necessarily where it was introduced. I would follow every alias that can write into that container, remove the raw entry path and fix unchecked warnings instead of suppressing them broadly. If a legacy boundary cannot be typed, I would validate values there before admitting them. I would separately check that the handoff establishes visibility and that concurrent mutations use an appropriate lock or concurrent collection. Even a perfectly typed ArrayList is not safe for unsynchronized sharing. Repairing the type boundary and repairing the threading policy solve different problems.

Likely follow up: Would comparing the runtime classes of a List of String and a List of Integer reveal their element types?
