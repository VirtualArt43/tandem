How Java runs: JVM, bytecode, JIT and GC

From source to running threads: bytecode, class loading, the interpreter and JIT, the JVM's memory areas and garbage collection.

Asked atAppleMicrosoftWalmart

Your Java source becomes bytecode, and HotSpot compiles hot paths to machine code. Its optimizations must obey the Java Memory Model, but a plain shared field can still surprise you, and a garbage collection pause can stall every request in the process.

In plain words

Picture a restaurant chain. The head chef writes recipes in plain English (your source code). A translator turns them into a compact shorthand that every kitchen in the chain can follow (bytecode). In each kitchen a supervisor reads the shorthand aloud, step by step, for the first few orders (the interpreter). Once a dish has been ordered hundreds of times, a cook learns it by heart and starts taking shortcuts (the JIT compiler). A shortcut may reuse an earlier reading of the order board unless the kitchen's communication rules require checking for another cook's update.

All the cooks share one big pantry (the heap), and each has a small notepad at their own station (their stack). A cleaner throws out ingredients that no notepad refers to any more (the garbage collector), and every so often shouts "everybody freeze" to mop the floor (a stop-the-world pause). Most surprises in a busy kitchen come from a shortcut that is safe for one cook and wrong when two cooks share the pantry.

Why this matters for concurrency

  • The JIT must preserve the memory model's guarantees. A plain field with no synchronization may still be read once and never again. That can make a stop flag work in a debugger and hang in production. The demo below can expose this.
  • The heap is shared; stacks are not. A local variable lives in one thread's stack frame and no other thread can ever see it. An object lives on the heap and is shared the moment two threads can reach it. Telling these apart is the first step of every thread-safety review.
  • One line is several instructions. count += 1 compiles to a separate read, add and write, so another thread can slip in between. Bytecode makes the lost update visible.
  • Garbage collection can pause every thread at once. That shows up as latency spikes, timeouts that fire during a pause, and leases that expire while their holder is frozen.
  • Interviewers file this under "Core Java" and "the threading model". The topics a recruiter announced for one Apple hiring manager screen were Core Java, the memory model, the threading model and GC, and a Microsoft senior round went from volatile all the way down to CPU caches and registers.

From source file to running program

Java runs in two steps that can be far apart in time. First javac compiles your .java files into .class files that hold bytecode, a compact instruction set for an imaginary machine. Then the java command starts a JVM, a real operating system process, which loads those classes and runs them.

The bytecode is identical on every platform; only the JVM differs. That is the "write once, run anywhere" idea, and it is why the Java memory model is defined by the language and not by a particular CPU: the JVM has to give you the same guarantees on an x86 laptop and on an ARM server, adding whatever fences each CPU needs.

On an instance field you get the same shape with getfield and putfield. A local int is different: x += 1 on a local compiles to a single iinc, and it would not matter anyway, because no other thread can touch a local variable.

Class loading: lazy, once, and thread-safe

The JVM does not load your whole program at start up. It loads, links and initializes each class the first time the class is actively used: an object of it is created, a static method is called, a static field is assigned, or a static field that is not a compile-time constant is read. (The JVM may load and link a class earlier; the specification fixes only the moment of initialization.) Initialization runs the class's static field initializers and static { } blocks, exactly once. This is class loading and initialization.

The JVM also makes initialization thread-safe. If two threads touch a class for the first time at the same moment, one runs the initializer while the other waits, and both then see the fully initialized static state. Watch it:

Class initialization is one of the few places where the JVM synchronizes for you. The lazy holder idiom for singletons is built on exactly this; you will meet it in static, class initialization and singletons.

The interpreter and the JIT compiler

The JVM starts by interpreting bytecode, one instruction at a time. That is slow, so it counts how often each method is called and how often each loop goes round. Code that gets hot is handed to the JIT compiler, which compiles it to native machine code on background threads while your program keeps running.

HotSpot, the JVM inside OpenJDK, uses tiered compilation. A method called a few hundred times gets a quick compile by C1, with profiling built in. After thousands of calls, or tens of thousands of loop iterations, C2 recompiles it aggressively using that profile. Treat those numbers as orders of magnitude; the exact thresholds are JVM flags. A long-running loop does not even need to return: on-stack replacement swaps the compiled version in while the loop is still going.

C2 is a serious optimizing compiler. These are the optimizations that matter for threaded code:

OptimizationWhat it doesWhat it means for threads
InliningCopies a small method's body into its callerRemoves call boundaries that used to hide a field read from the optimizer

These transformations must preserve both each thread's semantics and the Java Memory Model. That model still constrains racy programs; it does not let the optimizer ignore every other thread. However, a plain field with no ordering between its writer and reader has no guarantee of eventual visibility. Use the appropriate synchronization, such as volatile, a common lock, or the guarantees of java.util.concurrent. Thread start, join, class initialization and final fields also have specified guarantees. The details begin with visibility.

The JVM's memory areas

A running JVM is one operating system process, and its memory is divided into areas with different owners, lifetimes and limits. Interviewers ask for this map by name, and each area runs out in its own way:

Heap: old generationSharedObjects that survived several young collections: caches, sessions, long-lived structures-Xmx caps the whole heap; OutOfMemoryError: Java heap space
MetaspaceSharedClass metadata: each loaded class's structure, method code and constant pool. It replaced the old PermGen in Java 8 and lives in native memory, outside the heapUnbounded by default, capped with -XX:MaxMetaspaceSize; OutOfMemoryError: Metaspace, usually from leaking class loaders

In HotSpot, static fields are stored with their class's Class object on the heap, while class metadata sits in Metaspace; interned strings live on the heap too. Ordinary shared Java objects live on the heap, although threads can also share off-heap data through direct buffers or native code. Every platform thread needs a native stack and operating system resources: a thread per request can exhaust those resources while the heap still has room. That is why "unable to create native thread" calls for checking native memory and thread limits, not just heap usage.

Heap versus stack: what threads share

For threads, two of those areas decide everything:

  • The heap holds every object and every array, no matter which thread created them. There is one heap per JVM, shared by all of its threads. Static fields belong to their class, and every thread can reach them too.
  • Each thread has its own stack: one frame per method call in progress, holding that call's parameters and local variables. A local int lives in the frame itself. A local of an object type holds only a reference; the object it refers to lives on the heap.
Kind of variableWhere it livesCan another thread reach it?

Every platform thread reserves its own stack: by default 1 MB on x86-64 Linux and 2 MB on 64-bit ARM, Apple silicon Macs included. It is reserved address space; pages are committed only as the stack grows. Check yours with java -XX:+PrintFlagsFinal -version (look for ThreadStackSize) and change it with -Xss. Deep recursion that runs out throws StackOverflowError in that thread only. Java 21 virtual threads keep their frames on the heap while they are not running, which is one reason you can have millions of them; see virtual threads and coroutines.

Garbage collection and stop-the-world pauses

You never free memory in Java. The garbage collector finds objects that nothing can reach any more and reuses their space. Reachability starts from the roots: every live thread's stack frames, every static field, and a few JVM internals. An object stays alive as long as some chain of references leads to it from a root. Two consequences for concurrent code:

  • A live thread keeps alive everything it can reach. A worker blocked forever on a queue keeps its whole stack, and every object those frames point to, in memory. Leaked threads are memory leaks. So are unbounded queues that producers fill faster than consumers drain them.
  • Collection needs the world to hold still. To move objects and fix up references safely, collectors stop every application thread at a safepoint for at least part of their work. That is a stop-the-world pause pause, and from inside your program it looks like every thread freezing at the same instant.

The practical picture rests on one observation, the generational hypothesis: most objects die young. So the heap is split into generations. New objects go into Eden. A young collection runs often and is cheap, because it only copies the few young objects that are still alive into a survivor space; an object that survives several young collections is promoted to the old generation, which is collected rarely and at a higher cost. G1, the default collector, divides the whole heap into many equal regions, each serving as Eden, survivor or old space, and collects the regions with the most garbage first, hence its name, garbage first. ZGC goes further and does almost all of its work while your threads keep running. Many OpenJDK builds also ship Shenandoah, another mostly concurrent collector. Whichever you use, a pause is invisible to the code and visible to everything outside it. A 300 ms pause in the middle of a request looks like a slow dependency. A timeout measured across a pause fires even though the work was nearly done. And a process holding a time-limited lease, say a distributed lock that expires after 10 seconds, can pause past the expiry, wake up, and write as if it still held the lock while another node already has it. That is why distributed locks need fencing tokens.

Worked example: shared or confined?

  • size: a primitive local, copied into the lambda when it is created. Confined.
  • sb: a local reference to a new StringBuilder. The calling thread creates it and hands it to exactly one pool thread through submit, which guarantees the pool thread sees everything written before the hand-off, and the caller never touches it again. Confined to one thread at a time: fine.
  • rows: the caller's list. The pool thread reads it later, while the caller might still be changing it. Shared and risky: take a copy (List.copyOf(rows)) before submitting, while the caller guarantees no concurrent mutation or while holding the lock used by all writers. Copying an already-racing list is not a safe snapshot.
  • CACHE: a static HashMap written by up to four pool threads at once. Shared, and HashMap is not thread-safe: use a ConcurrentHashMap.
  • generated: an instance field, reached through the this that the lambda captures. Four pool threads run generated += 1 on it: a lost update. Use an AtomicInteger or a LongAdder.
  • report: a fresh object, but it is published through CACHE and through the Future. It is a record with final fields and immutable components, so once published, sharing it is safe.

Three of the six variables needed a fix, and none of them looked dangerous. The method of finding them was mechanical: for each variable, ask whether it is on a stack or on the heap, and if on the heap, which threads can reach it.

Common mistakes

  • "It works on my machine, so the flag is fine." Short runs, prints and debuggers keep code in the interpreter or change its timing, so the hoisted read never happens. Production runs long enough for C2. Correctness must come from volatile, a lock or an atomic.
  • "Locals are thread-safe, so the object is safe too." The local variable is confined; the object it points to is shared as soon as its reference escapes to another thread, a lambda, a queue or a field.
  • "Adding a print fixed shutdown." Logging can change compilation, timing or incidental synchronization. Use a cancellation protocol whose correctness does not depend on log lines.
  • Calling System.gc() to "free memory now". It is only a request, and on most collectors it triggers a full stop-the-world collection. Never put it in a request path.
  • Using finalize() to release locks, files or connections. It runs at an unpredictable time on a JVM thread, if at all, and has been deprecated for removal since Java 18. Use try-with-resources.
  • Measuring performance on a cold JVM. The first seconds run in the interpreter and C1. Use JMH, the OpenJDK microbenchmark harness, which handles warm-up for you.

In the interview

This comes up as warm-up theory ("what happens when you run a Java program?", "stack versus heap?") and, more sharply, inside a concurrency question: "this loop works in tests but hangs in production, why?" or "which of these variables need synchronization?". The interviewer wants the pipeline, the stack versus heap rule, and the link from the JIT to the memory model.

javac compiles to bytecode; HotSpot interprets it and the JIT compiles hot code to machine code. Optimization must respect the Java Memory Model, but a plain racy stop flag may still be read once and hoisted out of a loop. I use volatile or an atomic for that flag, or a common lock around every access, to establish the required visibility.
Locals and parameters live in the thread's own stack frame, so they are confined. Objects live on the shared heap, so anything two threads can reach needs synchronization, immutability, or confinement by design.

Follow ups to expect: "Why did it work in the debugger?" (interpreter, different timing), "Can the JIT reorder my writes?" (yes, unless a happens-before rule forbids it), "How does GC affect latency?" (stop-the-world pauses hit every thread at once; choose G1 or ZGC and keep allocation rates down), and "What is a safepoint?" (a point where the JVM can pause a thread; stop-the-world work waits for all threads to reach one).

Ask which memory model they mean. "Explain the Java memory model" is ambiguous. Walmart rounds and an Apple hiring manager screen have listed "memory model" as a topic without saying which one (the Apple screen listed it next to GC), and in Java interviews in India the phrase often means the runtime memory areas and garbage collection from this lesson; concurrency interviewers usually mean the JMM, the rules in the language specification for what one thread is guaranteed to see of another's writes. Asking is a senior move, not a weak one:

Two things go by that name. One is the runtime layout: a shared heap with young and old generations, Metaspace for class metadata, and a stack and program counter per thread, with the garbage collector managing the heap. The other is the Java Memory Model in the specification: the happens-before rules, volatile, locks and final fields, which decide what one thread is guaranteed to see of another's writes. Which one would you like me to go into?

The JMM side starts in happens-before and synchronizes-with, after visibility and reordering.

Senior depth

  • Speculation and deoptimization. C2 compiles against the profile: if only one implementation of an interface has been seen, it inlines that one behind a cheap check. When a new class breaks the assumption, the JVM deoptimizes back to the interpreter and recompiles later. Behavior never changes; latency can.
  • Time to safepoint. A stop-the-world pause starts only after every thread reaches a safepoint. Compiled code polls at method returns and loop back edges, and under G1 and ZGC, C2 splits very long counted loops so they poll often enough (loop strip mining). Threads blocked in native code or I/O already count as safe. A long pause in the GC log can be time to safepoint, not collection.
  • Collectors change the compiled code. G1 adds small write barriers to reference stores and ZGC adds load barriers to reference loads (generational ZGC adds store barriers as well), so the same method compiles differently under different collectors.
  • Locks on objects that never escape are free. Escape analysis can remove the locking inside a StringBuffer (whose methods are synchronized, unlike StringBuilder) that stays inside one method. That also means synchronized (new Object()) { ... } protects nothing: no other thread can ever lock the same object.
  • Pauses break time-based reasoning. GC is one source of process pauses; virtual machine migration and swapping are others. Any design that relies on "I checked the lease a moment ago" needs a fencing token checked by the storage, not a hope that pauses are short.

Under the hood

On x86, C2 may compile count += 1 on a field to a load, an add and a store, or to a single add instruction on memory. Neither is atomic across cores: without a lock prefix, two cores can both read the old value. AtomicInteger.incrementAndGet() compiles to lock xadd, and on ARM to an atomic add instruction or a load-exclusive and store-exclusive retry loop. A volatile write on x86 adds a full fence after the store, while on ARM volatile reads and writes use load-acquire and store-release instructions. You can see the generated code with -XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly, which needs the separate hsdis disassembler plugin.

Key takeaways

  • javac produces bytecode; HotSpot interprets it and compiles hot code while respecting the Java Memory Model.
  • One source line can be several instructions: count += 1 is a separate read, add and write.
  • The heap (young and old generations) is shared; each thread has its own stack and program counter; class metadata lives in Metaspace, outside the heap. Locals are confined, heap objects are shared once two threads can reach them.
  • The interpreter can hide a race that the JIT exposes. Only happens-before edges (volatile, locks, atomics) make shared access correct.
  • Class initialization runs once and is thread-safe; it is one place where the JVM synchronizes for you.
  • GC pauses stop every thread at once: expect latency spikes, early timeouts and expired leases.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A worker runs while (!stop) { spins += 1; } where stop is a plain static boolean. main sleeps 300 ms and then sets stop = true. What can happen on HotSpot?
Why. With no happens-before edge between the flag write and read, the memory model permits the worker to keep observing the old value. Hoisting the read is one possible optimization. Interpreted runs often stop, but that is not a correctness guarantee. The compiler never forces volatile, and IllegalMonitorStateException is about calling wait or notify without holding the monitor.
Inside a method, a thread runs int n = 5; List<String> names = new ArrayList<>();. Where do these live?
Why. Primitive locals and the reference itself live in the frame; the object created by new lives on the heap (escape analysis may remove the allocation, but it never changes what the program means). The third option is the dangerous one: the list is confined only while its reference stays inside this thread.
A service starts a new platform thread for every request. Under a traffic spike it crashes with OutOfMemoryError: unable to create native thread, while heap usage is only at 40 percent. What ran out?
Why. Thread stacks are native memory reserved per thread (typically 1 to 2 MB each), and the operating system also limits how many threads a process may have. Neither is part of -Xmx, so the heap can look healthy. Classes and compiled code are shared by all threads. The fix is a bounded pool or virtual threads, not a bigger heap.
javap -c shows getstatic, iconst_1, iadd, putstatic for count += 1 on a static int. What does that tell you?
Why. The read and the write are separate steps, and the JIT does not make them atomic: even a single x86 add on memory is not atomic across cores without a lock prefix. iinc exists only for local variables, and incrementing a local copy would not update the shared field at all.
A service's p99 latency jumps for every request at the same moment, every few minutes. The GC log shows a 300 ms pause at exactly those moments. What is the best explanation?
Why. The correlated GC log makes a stop-the-world collection the best explanation. A deadlock does not normally clear by itself, and background JIT compilation does not explain this matching GC pause. Latency spikes alone would not prove GC: operating system scheduling and other process-wide pauses can also stall work.
A stop-flag loop without volatile hangs. A colleague adds System.out.println(spins) inside the loop and the hang goes away. What is the right conclusion?
Why. A print in the reader alone establishes no ordering with the flag writer. It can change timing or inhibit hoisting, but it does not make the plain field volatile. If the writer also releases the same output monitor after writing the flag, a later reader acquisition can introduce ordering, which is another reason logging can mask the missing protocol. Use volatile or an AtomicBoolean explicitly.
Two threads read Config.SETTINGS for the very first time at the same moment. SETTINGS is a static final map built in a static { } block. What does the JVM guarantee?
Why. Class initialization happens under a per-class initialization lock: one thread runs the initializer while the others wait, and finishing it happens-before any other thread's use of the class. That is why the lazy holder idiom is a safe singleton.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer says: "This worker loop passes every unit test, but in production shutdown() sometimes never stops it. The flag is a plain boolean field." What is going on, and how do you fix it? Answer as you would out loud.
Model answer

The flag is written by one thread and read by another with no synchronization, so there is no happens-before edge between the write and the read, and the JVM need not show the reader the new value. One possible explanation is JIT hoisting: a short test may repeatedly read the field, while a hot compiled loop can reuse a single read. Neither a short test nor an interpreted run establishes correctness.

The fix is to create a happens-before edge: declare the field volatile, or use an AtomicBoolean. For a worker that can block, interruption may be more useful: shutdown() calls worker.interrupt() and the loop checks Thread.currentThread().isInterrupted(). Interruptible waits such as sleep, wait and blocking queue operations throw InterruptedException, which the worker must handle by exiting or propagating appropriately. I would join the worker before declaring shutdown complete, and would not rely on log lines for the cancellation protocol.

Explain
A method is called from many threads at once. For each of these, say where it lives and whether it needs synchronization: a local int; a local StringBuilder that never leaves the method; a static HashMap used as a cache; an int counter field of a singleton service.
Model answer
  • Local int: in the calling thread's stack frame. Every call has its own copy, so no synchronization is needed.
  • Local StringBuilder that never escapes: the reference is in the frame, the object is on the heap, but only this thread can reach it. Confined, so no synchronization is needed (and escape analysis may even remove the allocation).
  • static HashMap cache: on the heap and reachable by every thread through the class. Concurrent writes can lose entries or corrupt the map, so replace it with a ConcurrentHashMap and use atomic methods such as computeIfAbsent.
  • Counter field of a singleton: on the heap inside one object that every thread uses. count += 1 is a read-modify-write, so use an AtomicInteger, a LongAdder, or a lock that every reader and writer takes.

The rule I apply: stack means confined; heap means shared once a second thread can reach it, and shared mutable state needs atomics, locks or immutability.

Design
A service holds a lease-based distributed lock with a 10 second expiry and renews it every 3 seconds. Explain how a garbage collection pause can lead to two nodes both believing they hold the lock, and what you would do about it.
Model answer

Node A holds the lease and is about to write to storage. A long stop-the-world pause freezes every thread in A, including the renewal thread, for longer than the remaining lease time. The lock service sees the lease expire and grants it to node B, which starts writing. A then wakes up, its code still believes "I checked the lease a moment ago", and it writes too. Now two writers interleave, and the protected data can be corrupted.

Shorter pauses (G1 tuning, ZGC, lower allocation rates) make this rarer but cannot rule it out, because process pauses also come from virtual machine migration, swapping or a slow disk. The real fix is fencing: the lock service hands out a token that increases with every grant, every write carries the token, and the storage rejects any write whose token is lower than the highest it has already seen. A's stale write then fails safely. I would also make the protected operations idempotent, so a rejected or retried write cannot double apply.

"Walk me from a Java source file to running machine code. Where do class initialization and concurrency guarantees enter that story?"
What a strong answer covers
  • Javac produces class files containing bytecode, which a JVM loads and verifies
  • Loading and linking can happen early; active use triggers initialization subject to the language rules
  • Class initialization coordinates competing threads and publishes the completed static state
  • HotSpot interprets code and uses profiling to compile hot methods or loops into native code
  • Compiled execution must obey the Java Memory Model as well as each thread's semantics
  • Initialization does not make later mutations of a shared object thread-safe
How a senior would say it
Java source becomes bytecode first, and the JVM then executes it, using native code for hot paths. The compiler writes class files. The JVM loads, verifies and links classes, potentially before they are needed. Initialization is a separate step, triggered by active use such as calling a static method or reading a nonconstant static field. If two threads first use the same class, one performs initialization and the other waits, so successful initialization safely publishes the completed static state. HotSpot initially interprets code and collects execution profiles. Its tiered compilers turn hot methods and loops into machine code; a running loop can switch into compiled code without returning first. Those optimizations must still obey the Java Memory Model. The compiler cannot ignore synchronization, although a plain racy field may have reads reused or moved. For example, a map created during class initialization is safely visible to later users. That does not make future updates to a mutable map safe. I would use an immutable map, a concurrent collection, or a common lock for those updates. Initialization publishes state; it does not permanently protect it.

Out loudabout 90 s
"A plain boolean stop flag works in short tests but sometimes spins forever in production. Someone proposes adding a sleep or a log line. How would you respond?"
What a strong answer covers
  • The unsynchronized write and read form a data race with no guaranteed visibility
  • HotSpot may reuse or hoist the read; short tests and debugger runs do not establish correctness
  • Sleep supplies no synchronization, and logging can change timing or introduce incidental ordering
  • Use a volatile boolean or AtomicBoolean for a simple flag, or the same lock for every access
  • Volatile visibility does not make compound operations such as increment atomic
  • Interruption supports cooperative cancellation of interruptible waits; handle InterruptedException and join the worker
How a senior would say it
I would fix the communication between threads. A plain flag read and written without synchronization has no guarantee that the worker will observe the write. HotSpot may compile the hot loop so that it reads the flag once and reuses that value. That explains one possible production hang, but it is not a prediction that every run must hang. Short tests and debugger runs can produce different timing or compilation decisions. Sleeping does not establish a happens-before edge. Logging can change optimization and timing, and sometimes introduce incidental ordering through a shared output lock, but it is not a reliable cancellation protocol. For a simple stop flag I would use a volatile boolean or an AtomicBoolean. A common lock around every access also works. Volatile gives the visibility needed for this flag; it does not make a read, increment and write into one atomic operation. If the worker can block in a queue operation or sleep, I would consider interruption so it can also leave an interruptible wait. The worker must cooperate, including handling InterruptedException by exiting or propagating it appropriately. Finally I would join the worker before treating shutdown as complete. Tests can exercise cancellation, but the synchronization rule is the correctness argument.

Likely follow up: Would declaring a shared counter volatile make count += 1 safe for two writers?

Out loudabout 75 s
"All requests in one Java process stall at the same time, then recover. How would you check whether garbage collection is involved, and what could that break besides latency?"
What a strong answer covers
  • Correlate request stalls with GC and safepoint logs rather than infer GC from latency alone
  • Separate time reaching a safepoint from time spent doing stop-the-world collection work
  • Inspect allocation rate, retained live data and collector configuration before choosing a mitigation
  • Lower allocation or a concurrent collector may reduce pauses but cannot guarantee their absence
  • A paused lease holder can resume after its lease expires and another holder takes over
  • Fencing tokens let storage reject older writers after a newer token has been accepted
How a senior would say it
I would correlate the stalled request timestamps with GC and safepoint logs before blaming the collector. A stop-the-world collection can pause application work across the process, so synchronized latency spikes are a useful clue, not proof. I would separate time spent getting threads to a safepoint from time spent collecting, then inspect allocation rate, retained live data and the collector configuration. Reducing temporary allocations or choosing a mostly concurrent collector may help, but neither guarantees that the process will never pause. The correctness risk is work that relies on a lease still being valid. Suppose a node owns a ten-second lease and pauses long enough for it to expire. Another node acquires the lease and starts writing. The first node resumes with its old local belief that it is still the owner. Shorter GC pauses only make this less likely. I would use increasing fencing tokens and require storage to reject older tokens after it has accepted a newer one. That protects against a stale writer even when a process pause is longer than expected.
