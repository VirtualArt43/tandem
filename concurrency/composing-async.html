Composing async work: CompletableFuture and continuations

Chain, combine, recover and time out asynchronous work, choose where continuations run, and understand the limits of Java and C++ futures.

Asked atGoogleAppleRubrik
Before this:Futures and promises

Waiting in get() can occupy a worker needed by the very task you are waiting for. Composition describes what happens next without dedicating a thread to that dependency wait. Java provides callback futures; C++20 standard futures do not provide continuations.

In plain words

You put a cake in the oven. You could stand and stare at the oven door for 40 minutes. Or you leave a note on it: "when this is done, frost it, then box it; if it burns, bake a cupcake instead; if it is not out by 6 pm, sell the shop-bought one". Then you go and do other work.

That note is a continuation: the next step, attached in advance, run by whoever is around when the cake comes out. Composing async work is writing good notes instead of standing at ovens.

From waiting to continuing

With plain futures, a consumer usually calls get() to obtain a result; it waits only if the result is not ready. Starting each independent operation only after getting the previous result unnecessarily serializes them. Starting all operations first preserves overlap, but waiting still occupies the caller. If every worker of a fixed pool waits for queued work in that same pool, you get the pool self-deadlock from the failures lesson.

A continuation removes the dependency wait: instead of "wait for the result, then do X", you register "when the result exists, do X". Registration can itself run a ready, non-async continuation inline, so it is not necessarily an immediate return. Java's CompletableFuture is a future you can complete and attach continuations to, with combinators for every common shape:

A real composition, and the C++ version

A page needs a user, then that user's orders (which depend on the user), and a display theme (independent, but the theme service is slow today, so after 100 ms we use a default). An observed stage failure should produce an error page; a failure after a timeout fallback has won is no longer that page's result. Sleeps below simulate service latency; they do not establish ordering. In Java the pipeline is one expression. C++20's std::future has no then, so the C++ side adds a tiny then helper on top of std::async and handles the deadline with wait_until: readable, but each pending step holds a whole thread while it waits.

Typically about 100 ms until printing, rather than the roughly 400 ms of sequential calls: the user and theme calls overlap, and the theme's 300 ms is cut off by the fallback. Note what the timeout does and does not do. Completing a Java future on timeout does not stop the work. The slow theme call keeps running in both programs: Java's completeOnTimeout completes the same future with a fallback, ignoring a later attempt to publish the real result (the demo separately interrupts unfinished work during cleanup), and in C++ the std::async future's destructor waits for it at the end of main. C++ wait_until merely returns a readiness status; it does not complete or cancel the future, which can still yield its real result later. Scheduling delays can stretch both examples; neither is a hard real-time deadline.

The fixed Java executor above has an unbounded queue, which is acceptable only for this tiny, fixed graph. A service needs bounded admission and a rejection policy, even when every dependency is expressed as a continuation.

thenApply versus thenCompose

This is a common composition distinction, and it is the difference between map and flatMap. thenApply takes a function from a value to a value. If your function already returns a future (because the next step is itself async), thenApply wraps it again and you get a future of a future. thenCompose flattens it:

The tempting wrong fix is user.thenApply(u -> fetchOrders(u).join()). It returns the right type, but it blocks a thread inside a continuation, which brings back every problem composition was meant to remove.

Errors flow down the chain

When a stage completes exceptionally, success-only functions attached to that outcome are skipped. Their returned stages also fail, so the failure reaches an error handler: exceptionally (recover with a value), handle (see value or failure, return a new value), or whenComplete (observe and normally preserve the outcome). If the observer throws after success, its returned stage fails; if both source and observer fail, the source failure wins. Independent sibling work continues. Two other details trip people up:

  • Wrapping. Dependent stages often deliver CompletionException, but a handler attached directly to failedFuture, completeExceptionally, cancellation or timeout can receive the original exception. join() reports ordinary failure with unchecked CompletionException; get() uses checked ExecutionException and is interruptible. Direct cancellation throws CancellationException. Inspect conditionally, as the helper above does, rather than assuming every failure has a cause.
  • Swallowing. exceptionally(ex -> null) turns every failure into a successful null, which can surface later as a confusing NullPointerException far from the cause. Recover with a meaningful value, or let it fail.

Which thread runs a continuation?

This is the question that separates people who have used CompletableFuture from people who have debugged it. For the plain (non-async) methods such as thenApply:

  • If the future is already complete when you attach the step, OpenJDK 21 normally runs a success callback inline on the attaching thread.
  • If it is not complete yet, the callback may run on the completing thread or another caller helping completion. Do not assume a fixed thread or an order among sibling callbacks.

The ...Async variants (thenApplyAsync, thenComposeAsync and so on) dispatch eligible steps through an executor: the one you pass, or the default described below. That does not guarantee a different thread: a direct executor such as Runnable::run, or a caller-runs rejection policy, can execute inline. So a heavy step attached with plain thenApply may run on an I/O thread, an HTTP client's callback thread, or, after completeOnTimeout, the internal timer thread, and slow it down for everyone else.

Java

Typical output: completer, then main, then pool-thread, then CompletableFutureDelayScheduler, the single internal thread that fires every orTimeout and completeOnTimeout in the JVM. Anything slow attached with a plain method after a timeout may run on that shared thread. This sample can print main for the last step if the timeout wins before handle is attached; the thread names illustrate OpenJDK 21 behaviour, not a portable scheduling guarantee. The rule of thumb: plain methods for cheap, non-blocking steps; ...Async(fn, yourExecutor) for anything that blocks or takes time.

C++

In C++, callback placement is a library contract, not a rule imposed by the language. One possible design is the future you will build in the last lesson of this module: it can run callbacks inline on a completing or attaching thread. Other libraries require or choose an executor. Read that contract before putting expensive work in a callback.

The common pool caveat

For ordinary CompletableFuture instances, ...Async methods without an executor use ForkJoinPool.commonPool(), the common pool, when its parallelism is at least two; otherwise they create a thread per task. Subclasses may override the default for instance methods. The common pool is JVM-wide: parallel streams and libraries share it. Its default target parallelism is usually available processors minus one, with a minimum of one; configuration and compensation threads mean this is not a fixed thread count. It was built for short CPU-bound tasks. Put blocking HTTP or database calls on it and a handful of slow calls can occupy every thread, stalling unrelated parallel streams and async stages across the application. Always pass your own executor for I/O. You will see the pool's design in fork/join.

Fan out and fan in

allOf returns a CompletableFuture<Void> that completes after every input completes, exceptionally if any failed. It is not fail-fast and does not cancel siblings. Collect results in its success continuation; every input is then ready and successful. An empty allOf succeeds immediately. anyOf returns CompletableFuture<Object> with the winning completion, including failure; simultaneous or already completed inputs need not have a meaningful chronological winner. Empty anyOf never completes. Neither combinator starts the supplied work.

"First success" needs a separate policy (see the checkpoint). Do not rely on applyToEither to ignore a failed input: when one side fails, the CompletionStage contract does not promise that the other side will be awaited for success.

Deadlines, ownership and admission

Timeout methods mutate their receiver. If two consumers share a Java future, shared.orTimeout(...) changes the outcome for both. For a private deadline use shared.copy().orTimeout(...); the producer future stays separate. A cancellation on a dependent stage does not automatically cancel upstream or sibling work. If the operation owns a socket or request handle, arrange cancellation through that handle.

Use one request deadline and pass the remaining budget to each stage; granting every sequential step a fresh 200 ms multiplies the total budget. The vendor example gives each Java call its own 200 ms budget, whereas the C++ loop shares a deadline after submission. Neither bounds submission time, worker cleanup or arbitrary blocking inside callbacks. Reject, limit or batch fan-out before an unbounded graph of tasks exhausts memory.

A published result is not permanent ownership of a mutable object. Completion safely hands off preceding writes, but later concurrent mutations still need synchronization. In C++, capture values or shared ownership when tasks may outlive the stack frame. In either language, a continuation failure still needs an observer; an abandoned failed future does not reliably log itself.

What C++ offers instead

C++20 standard futures have no continuation operation: they offer result retrieval, waiting, timed waits, valid and share. A then was proposed in the Concurrency TS (std::experimental::future::then) but never adopted. What people actually use:

  • A small then helper over std::async, as in the example above. Clear, correct, and costs one blocked thread per pending step. Fine for a handful of steps, wrong for thousands.
  • Continuation passing on a pool: each step, when it finishes, posts the next step to the pool, and the last one fulfils a std::promise. No thread waits for a child future, at the price of callbacks inside callbacks and error handling at every level.
  • A future type with real callbacks, either from a library (folly's Future with thenValue and via(executor), Boost.Thread's future::then) or your own, which is exactly the future you build in Build it yourself: a future.
  • C++20 coroutines with a task library: co_await each step and write the code top to bottom (Virtual threads and coroutines). Senders and receivers are a separate composition model; they are not part of this C++20 target or an API you can assume in this interview environment.

Worked example: replacing blocking gets in a crawler

A crawler worker fetches a page, then fetches every link on it, then indexes the page with the results. The first version runs on a pool of 16 and does fetch(url), then for each link pool.submit(fetch(link)) and get() on each. Under load it freezes: every worker is waiting for link fetches stuck in the same queue.

The composed version never waits for child futures inside the pool. Each fetch returns a CompletableFuture<Page>; the links are fetched with thenCompose, whose function starts one fetch per link and joins them with allOf, and indexing runs with thenApplyAsync(index, cpuPool), on a separate pool sized for CPU work, because indexing is computation, not I/O. No thread waits for child futures, although blocking fetches still occupy I/O workers. The I/O pool and the CPU pool are separate bulkheads, and a transport timeout per fetch limits how long a dead host occupies a worker. A future timeout alone only bounds waiting for the page result. Bound fan-out too, because composition does not provide backpressure. A 2022 Rubrik candidate made the same move in the crawler round, rewriting a thread pool solution with CompletableFuture when asked to improve it.

Common mistakes

  • Calling join() or get() inside a stage. It blocks a pool thread and invites self-deadlock. Use thenCompose or thenCombine.
  • supplyAsync without an executor for blocking I/O. It normally uses the JVM-wide common pool and can starve other users of that pool.
  • thenApply with a function that returns a future, producing a future of a future. Use thenCompose.
  • Assuming a timeout or cancel stops the work. orTimeout and completeOnTimeout complete the future; cancel(true) on a CompletableFuture does not interrupt anything. The underlying call runs on.
  • Using anyOf for "first success". It completes with the first result to finish, including a failure.
  • Swallowing failures with exceptionally(ex -> null), or never attaching any failure handling to a chain whose result nobody joins.
  • C++: a then built on std::async used at scale. One blocked thread per pending step does not survive thousands of requests.

In the interview

Expect it in two forms. As a coding task: "call these three services in parallel, combine the results, add a timeout and a fallback". And as internals: a 2026 Google L5 coding round asked a candidate to design and implement a custom variation of CompletableFuture "under the hood", a 2025 Apple round asked about the internal working of CompletableFuture, and a Rubrik candidate's crawler follow up moved from a thread pool to CompletableFuture. For C++ candidates the honest answer is part of the test: know that C++20 has no then, and show what you would do instead.

I would not block on get() inside the pipeline. I would start the independent calls with supplyAsync on an I/O executor I own, not the common pool, chain dependent steps with thenCompose, join independent ones with thenCombine or allOf, put a completeOnTimeout with a fallback on each remote call, and handle failures once at the end with exceptionally or handle. Plain thenApply may run on a completing or attaching thread, so anything heavy goes in an Async variant with an explicit executor.

Follow ups to expect: "Which thread runs this thenApply?" (completer or caller, as above), "What does orTimeout do to the running call?" (nothing; it only completes the future), "How would you get the first successful result?" (complete a shared future from whenComplete on success and count failures), and "How would you do this in C++?" (a pool plus promises, a future type with callbacks, or coroutines; C++20 has no then).

Under the hood

OpenJDK 21's CompletableFuture implementation holds a volatile Object result and a lock-free stack of dependent actions. Attaching a stage pushes a small "completion" object onto that stack with a compare-and-set and then checks the result again; completing the future sets the result with a compare-and-set (so only the first completion wins) and then pops and fires the dependents. A completion that invokes user code claims that action before running, so whichever thread gets there first runs it, and it runs exactly once, whether it was attached before or after completion. The implementation walks dependent chains iteratively, avoiding one Java stack frame per stage. Recursive user callbacks can still overflow their own stack. You will build a lock-based version of this machinery in the last lesson of the module.

Key takeaways

  • Compose instead of blocking: thenApply (map), thenCompose (flatMap), thenCombine and allOf (join), exceptionally and handle (recover).
  • Failures skip success-only functions; handlers may receive a wrapper or an original exception, so inspect conditionally, and never recover with a meaningless null.
  • Plain stages may run inline; Async variants use an executor whose execution policy you must understand.
  • Pass your own executor for I/O; the common pool is shared and small. Java timeout completion and C++ timed waits do not stop underlying work.
  • C++20 standard futures have no continuations: use a then helper, continuation passing on a pool, a callback-based future, or coroutines backed by a task library. A bare std::future is not directly awaitable.

Why. A map step wraps the returned future again, giving a future of a future. Waiting inside the step returns the right type but blocks a pool thread, which is exactly what composition avoids. Your callback-future API permits non-async continuations to run inline. You attach a slow callback to an already successful future on thread T. Which assumption is safe?
Why. A ready result permits inline execution on the registering thread. There is no required handoff to the producer or a pool, and completed futures can still accept callbacks. Even an Async method can run inline if its executor uses the caller.
Three independent remote calls take 100 ms, 200 ms and 300 ms. Assume enough execution capacity, negligible overhead and no failures. You start all three together, then compose them so a result is produced when all three are done. About how long until the result exists?
Why. All three run at once, so the combined result waits only for the slowest, 300 ms. 600 ms is what you get if you start each call only after the previous one finishes. Waiting for the first of them (a race) would take 100 ms.
A running remote call takes 5 seconds. After 200 ms the caller uses a fallback, without requesting cancellation or setting a transport timeout. What happens to the call?
Why. Java completeOnTimeout completes the same future; its fallback cannot be overwritten by a later ordinary completion. C++ wait_until only reports readiness and leaves the future available for later retrieval. Neither operation interrupts the call or releases its resources. To actually stop it you need cancellation the task honours, or a timeout on the call itself.

Why. This is pool self-deadlock moved into a continuation. Once every pool thread is blocked like this, the tasks they wait for can never run. Composition exists precisely so that nothing waits inside the pool.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
anyOf fails if the first call to finish fails. Write firstSuccessful(calls): submit every call for concurrent execution and complete with the first success to publish its result; fail only if every attempt fails, including submission rejection (with the last recorded error). Handle an empty list. Assume non-null callables and an executor that either accepts a task for eventual execution or throws.
Model answer

Why it is correct: CompletableFuture.complete is already "first wins" (later calls return false), so Java needs only the failure counter, and the counter reaches the total exactly once, after every call has failed. A std::promise throws std::future_error (promise_already_satisfied) if it is set a second time, so C++ guards it with a mutex and a done flag, which also keeps the failure count and the decision in one critical section. The shared state is held by a shared_ptr captured in every task, because tasks may finish after the caller has returned. Rejection counts as a failed attempt rather than abandoning the returned future. C++ here requires a non-void value type; publishing a throwing move counts as a failed attempt. "First" means first successful publication, and simultaneous contenders may win in either order. A production version would also bound admission, give the whole race a deadline, and request cooperative cancellation of losers when safe. Silently discarded or externally removed tasks need an explicit completion path too.

Explain
A teammate attached a heavy JSON parsing step with plain thenApply to a future returned by an HTTP client, and the client's I/O threads became a bottleneck. Explain why, and the fix.
Model answer

A plain thenApply may run inline during completion. In this scenario the HTTP client completes futures on its small set of I/O threads, so the parsing ran on those threads, and while they parsed JSON they could not read responses for any other request. (If the future had already been complete, the step would have run on the attaching thread instead.) The fix is thenApplyAsync(parse, cpuExecutor): hand heavy or blocking steps to an executor sized for that work, and keep plain stages for cheap, non-blocking transformations. The same reasoning applies to steps after orTimeout, which can run on the JVM's single timeout thread, and in C++ to any callback-based future: decide which executor runs each continuation.

Debug
A service calls CompletableFuture.supplyAsync(() -> httpGet(url)) for every outgoing request, with no executor. Under load, an unrelated nightly report that uses parallelStream() becomes very slow, although CPU usage is low. Explain, and fix it.
Model answer

Without an executor, supplyAsync runs on ForkJoinPool.commonPool(), whose default target parallelism is usually available processors minus one and which is shared by the whole JVM (assuming parallelism at least two). The blocking HTTP calls occupy those threads for the full network latency, so the parallel stream, which also uses the common pool, gets almost no threads and crawls while the CPUs sit idle. Fix: give I/O its own bounded executor, sized with Little's law (supplyAsync(() -> httpGet(url), ioExecutor)), keep the common pool for short CPU work, and put a timeout on the HTTP call itself, not only on the future. One more shared thread worth naming: orTimeout and completeOnTimeout fire on a single JVM-wide timer thread, so heavy plain stages attached after a timeout delay every other timeout in the process; attach them with an Async variant.

"A page needs a user, that user's orders, and an independent theme. Walk me through the async pipeline and tell me where each step runs."
What a strong answer covers

  • Use thenCompose for an asynchronous dependent step and thenCombine for independent results
  • Keep dependency waits out of bounded pool workers to avoid starvation deadlock
  • Plain callbacks can run inline; choose explicit executors for expensive or blocking work

How a senior would say it
I would start the user and theme requests together, then start orders only after the user succeeds. In Java, I use thenCompose for orders because that operation already returns a future. A plain map would give me a future containing another future. Once I have orders and theme, I combine their results into the page. If either required result fails, I return an explicit error page or a documented fallback. I avoid calling a pending future's get inside a worker. If every worker waits for a child queued in the same pool, none of those children can start. Composition represents the dependency without that wait. I also choose where the work executes. A plain continuation can run inline on a completing or attaching thread, so I keep it cheap. Parsing belongs on a CPU executor; blocking service calls need an appropriate I/O executor. An Async suffix still follows the supplied executor's policy. Finally, I bound outstanding calls and use one request deadline. Composition alone provides neither backpressure nor cancellation. In C++20, standard futures have no continuation API and are not directly awaitable. I would use a callback or coroutine task library, or post each next step explicitly to the pool. A helper that blocks another thread is only a small-scale demonstration.

Likely follow up: What changes if a service returns a future that is already complete, and your parsing callback takes 200 milliseconds?

"We added a timeout and the page now returns quickly, but our connections are still exhausted. What would you check?"
What a strong answer covers
  • Separate completion of the caller's future from cancellation of the underlying operation
  • Java timeout methods mutate the same future; use copy for an independent consumer deadline
  • C++ wait_until reports readiness without completing or cancelling the future

How a senior would say it
I would first check whether the timeout only changed the result the caller sees. That can make page latency look healthy while the remote operations keep their connections and workers for seconds. In Java, completing a future with a timeout or fallback does not stop its supplier. Cancelling a CompletableFuture does not interrupt that supplier either. Those timeout methods also mutate the receiver. If several consumers share it, I would put a private timeout on a copy when they need separate deadlines. In C++, a timed wait is different again: it reports readiness and leaves the future's eventual result intact. The resource fix is a deadline on the actual HTTP or database operation, plus cancellation that the operation honours. I would bound admitted calls so timed-out work cannot accumulate faster than it finishes, and pass the remaining request budget through successive stages. I would also inspect cleanup. Destroying a future from asynchronous std::async can wait for unfinished work, and pool destruction can join workers. Captured references must remain alive. Finally, expensive inline callbacks after a timeout can occupy the timer thread, so I would move that work onto an appropriate executor.

Likely follow up: How would you race three replicas for the first successful response without failing just because the fastest replica returned an error?
