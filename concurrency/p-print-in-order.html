Print in order

Ordering puzzleswarm-up20 minLeetCode 1114

The smallest ordering puzzle there is, and the one that shows in two minutes whether you know the difference between waiting, spinning and hoping. Every later ordering puzzle (foo bar, zero even odd, FizzBuzz, round robin) is this one with more turns.

The task

One Foo object is shared by three threads. Thread A calls first(), thread B calls second() and thread C calls third(). The threads start in any order and run at any speed. Make the output come out in order, every time:

  • first() prints at once.
  • second() prints only after first() has printed.
  • third() prints only after second() has printed.

Each method receives the printing as a callback: call printFirst.run() (in C++, printFirst()) exactly once. Whatever order the threads start in, the output is firstsecondthird.

Rules:

  • A thread that has to wait must block, not spin: the tests check that waiting threads use no CPU. This is what interviewers expect, and it rules out loops on a flag.
  • No sleep to push one thread behind another. Sleeping changes the odds, not the guarantee.
  • Each Foo object serves one round of three calls, as on LeetCode. The tests create a fresh object for every round.
  • In C++, ThreadSanitizer must stay quiet.

What the tests check

  • With only the second and third threads started, nothing is printed for 200 ms, and both threads are blocked rather than spinning (Java: their thread state is not RUNNABLE; C++: the process uses almost no CPU while they wait). Then first starts and the output is exactly first second third.
  • All 6 start orders, 200 rounds each. Rounds rotate through three start styles: started one after another, started 1 ms apart (so the later methods are already waiting when first runs), and released together from a gate. The output must be exactly first second third in every round.
  • No round hangs: each one must finish within 2 s in Java and 3 s in C++.
  • No exceptions escape your methods, and in C++ ThreadSanitizer reports nothing.

Taught in: Making threads take turns

Open them one at a time. Each one gives away a little more.

second needs to know one fact: has first finished? third needs another: has second finished? Where can a thread go to sleep until another thread makes a fact true?
Two one-shot signals (latches) are enough. In Java, a CountDownLatch of 1 (or a Semaphore with 0 permits) per step. In C++20, a std::latch or std::binary_semaphore per step. Or, in either language, one lock, one condition variable and a stage counter.
With a condition variable: stage starts at 0. first prints, sets stage = 1 and wakes everyone. second waits while (stage < 1), prints, sets stage = 2 and wakes everyone. third waits while (stage < 2). Wake everyone (notifyAll, notify_all), because two different threads can be waiting on the same condition.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why not spin on a volatile boolean in Java, or a std::atomic<bool> in C++?
It would be correct, because the volatile or atomic write and read create a happens-before edge. But the waiting thread burns a whole core, and on a busy machine it can steal the CPU from the very thread it waits for. Spinning is right only when the wait is known to be a few microseconds. A plain boolean or bool is worse than wasteful: in Java the JIT may hoist the read out of the loop and spin forever, and in C++ it is a data race, which is undefined behavior.
Why notifyAll and not notify?
second and third can both be waiting on the same monitor. If first calls notify, the JVM may wake third, which re-checks, sees it is not its turn and goes back to sleep. The only wakeup was spent on the wrong thread, and second sleeps forever: a lost wakeup. notifyAll wakes both, and the one that can proceed does. With one latch or one condition per step, each signal has exactly one kind of waiter, and then signal or notify_one is enough.
What guarantees that third sees everything first and second wrote, for example into a shared output buffer?
Happens-before. Releasing the monitor (or countDown, or a semaphore release) in one thread happens-before the matching acquire, await or acquire in the next thread, so every write made before the signal is visible after the wait. The chain first, then second, then third carries all the writes along.
In C++, can I lock a std::mutex in the constructor, unlock it in first(), and let second() lock it?
No. A mutex is owned by the thread that locked it, and unlocking it from another thread is undefined behavior, even though this famous LeetCode answer often appears to work. Use a std::binary_semaphore (C++20), a std::promise<void> and std::future<void> pair, or a condition variable. A semaphore has no owner, which is exactly what a signal needs.
Make one object serve many rounds: first, second, third, first, second, third, and so on.
Make the stage cyclic: second waits for stage == 1, third for stage == 2, and first now also waits, for stage == 0; third sets stage = 0 at the end. Waiting for an exact value instead of "at least" stops a thread from the next round slipping in. That is the round robin pattern, and it needs first to wait as well.
You ordered the threads by starting T2 only after T1.join() returned. Now do it without join(), using only wait() and notify().
That is the reference solution: one monitor, a stage counter, while (stage < k) wait(); in each later step and notifyAll() after each step. join() only orders threads that one controller starts one after another; it cannot help when all three are already running and call in any order, which is the real problem. An Oracle interviewer asked exactly this in 2022, right after a join() answer. Say why notifyAll and why while before they ask.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Each method waits for the step before it, then announces its own step. The reference keeps a single stage counter under one lock: 0 means nothing has printed, 1 means first has printed, 2 means second has. The invariant is a callback runs only when stage equals the number of callbacks already run, so the output can only be first, second, third.

Why each line is there

  • One lock around stage. The counter is written by one thread and read by others, so it needs a happens-before edge. The lock gives it, and the condition variable needs the lock anyway.
  • Wait in a loop. In Java while (stage < 1) wait();; in C++ the predicate overload of wait, which loops for you. A woken thread re-checks because the wakeup may be for someone else (notifyAll from first wakes third too) or spurious.
  • notifyAll after changing stage. Two different threads may wait on the one condition, and only one of them can proceed. Waking all of them is the only safe choice with a single condition.
  • The callback runs while holding the lock. Simple and correct here. In real code you would avoid calling unknown code under a lock, but the ordering would still hold if you printed after unlocking, because the next step cannot start until stage changes.

Pitfalls

  • if instead of while. third waits, second waits, first calls notifyAll, and third wakes first: with an if it prints before second. The tests catch this in the rounds where both later threads are already waiting.
  • Spinning on a plain flag. In C++ a plain bool written by one thread and read by another is a data race; ThreadSanitizer reports it on every run. In Java the JIT may turn the loop into an infinite one. Even with volatile or std::atomic, spinning wastes a core.
  • notify with one shared condition. It can wake the wrong waiter, and the signal is lost.
  • A mutex used as a signal (C++). Unlocking from a thread that does not own the mutex is undefined behavior, even when the output looks right.
  • sleep to order threads. It passes most runs and fails on a loaded machine, which is the worst kind of bug.

How to say it in the interview

Each method has to wait for the step before it, so I need two one-shot signals. I'll keep a stage counter under one lock: second waits while the stage is below one, third while it is below two, each in a loop, and every step notifies all waiters because two different threads can wait on the same condition. If library helpers are fine, two CountDownLatches of one, or two std::latch objects in C++20, do the same in fewer lines. Either way the release in one thread happens-before the acquire in the next, so the ordering and the visibility both hold.
