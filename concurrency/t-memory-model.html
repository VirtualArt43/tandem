The memory model

Visibility, reordering, happens-before, volatile and std::atomic, memory orders, safe publication, final fields, double-checked locking, caches and false sharing.

1Corevisibility
Why can a thread spin forever on a flag another thread already set?
Model answer

With a plain flag (not volatile in Java, not atomic in C++), nothing obliges the reading thread to read memory again. The JIT or the C++ compiler sees a loop that never writes running, so it may load the flag once and keep it in a register: while (running) {} effectively becomes if (running) for (;;) {}. That transformation is legal, because without synchronization the reader has no guarantee of ever seeing the other thread's write. This is hoisting.

Cache coherence does not force the program to issue another load, and it does not provide language-level synchronization. In C++, conflicting plain accesses without happens-before are a data race and undefined behavior, not just a stale-read problem.

A lock around every read and write of the flag also works. In C++, relaxed ordering suffices for a standalone stop flag; use release and acquire if it publishes data. Neither ordering guarantees a scheduling deadline or bounded termination time.

Likely follow up: "Adding a println inside the loop makes the bug go away. Why?" Printing changes timing and optimization, and may involve locking. Unless the writer and reader share an appropriate synchronization edge, this is not a valid fix.

2Corehappens-before
What is happens-before?
Model answer

happens-before is a partial order on actions in a program. If A happens-before B, B must respect A's effects, although an intervening ordered write can overwrite A's value. It is not about wall clock time: unordered conflicting ordinary accesses form a data race. Java can permit stale reads; C++ gives undefined behavior when at least one conflicting access is non-atomic. Atomic accesses can be unordered by happens-before without a C++ data race.

Java's edges (JLS 17.4.5 and the java.util.concurrent documentation):

  • Program order within one thread.
  • Unlocking a monitor, then any later lock of the same monitor.
  • A volatile write, then every subsequent read of that variable in synchronization order.
  • Thread.start(), then everything in the started thread; everything in a thread, then another thread detecting its termination through join(); a timed-out join is insufficient.
  • Actions before putting an element into a concurrent collection, then its access or removal; task submission to execution; task actions to successful result retrieval with Future.get().
  • And it is transitive.

C++ builds the same thing from "sequenced before" within a thread plus synchronizes-with between threads: a release store and an acquire load that reads it, a mutex unlock and a later lock, thread creation, and join.

I can name the synchronization edge for every cross-thread handoff.

Likely follow up: "Does happens-before mean A actually executes first?" No. The compiler may reorder freely as long as no thread can observe the difference; it only constrains what can be observed.

4SeniorvolatilehardwareMicrosoft
How does Java volatile work on a single core versus a multi-core machine, down to the CPU?
Model answer

volatile is a Java memory-model contract, not a command to flush RAM. A volatile write publishes earlier actions to subsequent volatile reads of that variable in synchronization order. The JIT must preserve that contract, including on a single core: ordinary racy reads may otherwise be reused or hoisted.

Hardware mappings depend on the CPU, JIT and surrounding code. For ordinary cacheable memory on x86, loads already supply acquire ordering and stores release ordering. HotSpot can use an ordinary load for a volatile read and a store with a locked instruction or fence for the stronger store-to-load ordering. On AArch64, acquire loads and release stores such as ldar and stlr are common. These are implementation examples, not Java requirements.

Cache coherence orders accesses to individual locations; it does not replace ordering across locations or make an increment indivisible. On one core, inter-core cache transfers disappear, but the compiler contract still matters, and the JVM may still emit barriers.

Likely follow up: "What does it cost?" There is no portable latency. A cached read can be cheap; a contended write can transfer cache-line ownership and drain buffered stores. Measure on the target JVM and CPU rather than promising a fixed nanosecond cost.

5Corereorderinglitmus
Thread 1 runs x = 1; r1 = y; and thread 2 runs y = 1; r2 = x;, with x and y starting at 0 and no synchronization. Can both r1 and r2 end up 0?
Model answer

For Java plain fields, yes. For C++ plain fields, the program has a data race and undefined behavior; use relaxed atomics to study this outcome in a defined C++ program. This is the store buffering litmus test. Intuition says at least one store must land before the other thread's load. But each core puts its store into its store buffer and lets its following load read memory, which still holds 0, before the store drains. Both loads read 0.

For ordinary write-back memory, x86 permits this store-to-load reordering (a store followed by a load of a different address); ARM allows it and much more; compilers may also reorder the independent store and load.

The fix is sequentially consistent operations: volatile in Java, or std::atomic with the default memory_order_seq_cst in C++.

Acquire and release are not enough here: when both loads read the initial zero, neither reads the other thread's release, so no synchronizes-with edge connects the threads. This is exactly why Dekker's and Peterson's mutual exclusion algorithms need sequentially consistent operations or a full fence.

Likely follow up: "Which reorderings does x86 forbid?" For ordinary cacheable scalar accesses, load-load, load-store and store-store ordering hold; store-load reordering and store forwarding still matter. Special memory types and instructions need separate analysis.

6Seniorcppmemory-order
Explain the C++ memory orders seq_cst, acquire, release and relaxed.
Model answer
  • relaxed: atomicity only. No ordering of other memory, though each atomic variable still has one modification order every thread agrees on. Right for counters and statistics that nobody uses to infer other state.
  • release (on a store): publishes preceding actions to an acquire that reads this store or its release sequence.
  • acquire (on a load): reads after it see everything released by the store it read from. Release plus acquire is the message passing pattern.
  • acq_rel: for read-modify-writes that both consume and publish.
  • seq_cst (the default): loads acquire, stores release, and read-modify-writes do both, plus one total order of all seq_cst operations consistent with the standard's ordering rules. Useful for the store-buffering example.
  • consume exists, but compilers treat it as acquire; avoid it.

Typical lock-free scalar mappings on x86: relaxed/acquire loads and relaxed/release stores use mov; a seq_cst store typically compiles to xchg (a full barrier). On ARM, acquire and release map to ldar and stlr.

I default to seq_cst, use acquire and release for a clear publish and consume pair, and relaxed only for counters.

Likely follow up: "What breaks if the producer uses relaxed?" No synchronizes-with edge protects the plain payload. Reading it races with its write, so the C++ program has undefined behavior, not merely permission to read zero.

7Seniorcpphardware
x86 has a strong memory model. Can you skip atomics and memory orders on x86?
Model answer

No, for three reasons:

  1. The compiler follows the C++ model, not the CPU's. Concurrent conflicting accesses to a plain bool without synchronization form a data race and give undefined behavior on any CPU, and the compiler can hoist, merge or split accesses to it. Writing relaxed where you needed release also lets the compiler reorder, even on x86.
  2. x86 still reorders a store followed by a load. Dekker style code fails without seq_cst or a fence.
  3. Code moves. ARM servers (AWS Graviton) and Apple Silicon Macs have weak memory models where acquire and release really matter. Bugs that never appear on an x86 laptop show up there.

For ordinary lock-free scalar atomics on x86, acquire loads and release stores commonly compile to ordinary moves. Sequentially consistent stores, fences and read-modify-writes can cost more; contention and the atomic type also matter.

I write to the C++ memory model, not to the CPU. x86 hides ordering bugs; ARM reveals them.

Likely follow up: "How do you find such bugs?" ThreadSanitizer for data races, stress tests on ARM hardware, and model checking tools for lock-free code.

8Seniordouble-checked-lockingsingletonMicrosoft
Explain exactly which reordering breaks double-checked locking, and write a correct version in each language.
Model answer

The broken pattern checks instance == null without a lock, then locks, checks again, and assigns instance = new Helper(). That assignment is three steps: allocate, run the constructor (write the fields), store the reference. Nothing stops the store of the reference from becoming visible before the field writes. The lock's release orders things only for threads that later acquire the lock, and the fast path reads instance without locking. So a second thread can see a non-null instance and use an object whose fields still hold defaults. Java needs safe publication; C++ additionally has undefined behavior from the raced plain pointer. A release publication and an acquire read repair the handoff. The C++ owner below must outlive all callers, with worker shutdown before static destruction.

In practice, prefer the simpler forms that do this for you: in Java the holder class idiom or an enum singleton (class initialization is thread-safe); in C++ a function-local static (a function-local static, thread-safe since C++11) or std::call_once.

Likely follow up: "Why read the volatile into a local?" So the fast path performs one volatile read instead of two.

9Seniorsafe-publicationjava
What is safe publication, and what are the ways to do it in Java?
Model answer

Publishing means making an object reachable by another thread. safe publication means the other thread sees not only the reference but the object's fully constructed state. With unsafe publication (a plain field write raced by a plain read), the reader can get the reference and still see default values in the object's non-final fields.

The safe ways:

  1. Initialize it in a static initializer (class initialization is thread-safe).
  2. Store the reference in a volatile field or an AtomicReference.
  3. Store it in a final field of a properly constructed object.
  4. Store it in a field guarded by a lock that both writer and reader take.
  5. Hand it over through a thread-safe collection or executor: ConcurrentHashMap, a BlockingQueue, ExecutorService.submit, Thread.start.

After safe publication, an object that is never modified again (effectively immutable) needs no further synchronization. Later mutations need their own synchronization, such as locks or atomic fields.

C++ equivalents: a release store and acquire load of the pointer (std::atomic<T*>, or std::atomic<std::shared_ptr<T>> in C++20), a mutex, or the edges from thread creation and std::promise.

Likely follow up: "Is a plain field good enough for an immutable object?" Final-field semantics protect correctly constructed immutable state even if the reference is read racily, provided this did not escape. They do not guarantee that a reader ever observes a new reference. Prefer an explicit publication edge.

10Seniorfinal-fieldsjava
What exactly do final fields guarantee across threads?
Model answer

JLS 17.5: when a constructor finishes, the object's final fields are frozen. Any thread that obtains a reference to the object after that, even through a data race, sees the constructed values of the final fields, and also the state of objects reachable through them as of the freeze (for example, the contents of a final array filled in the constructor). Non-final fields get no such guarantee.

The conditions and limits:

  • this must not escape during construction: registering this as a listener, starting a thread in the constructor, or storing this in a static. Otherwise another thread can see the object before the freeze, with default finals. That is this escape.
  • Later mutations are not covered: a final List can still be modified, and those changes need their own synchronization.

A record is only shallowly immutable: its components may refer to mutable objects. Final-field semantics protect initialization when the reference is obtained, not timely visibility of a racy reference update. JVM barriers implementing the freeze are architecture dependent; they do not imply a hardware instruction on every constructor exit.

Likely follow up: "How do you start a thread for an object safely?" Use a static factory method: construct the object fully, then start the thread, so this never escapes the constructor.

11Seniorfalse-sharingperformance
What is false sharing, and how do you detect and fix it?
Model answer

Caches move data in cache lines: commonly 64 bytes on x86 and 128 bytes on many Apple Silicon CPUs; check the target. Coherence works per line: a writer must obtain exclusive ownership, invalidating other cached copies as needed. If two threads write different variables that happen to sit in the same line, such as two counters next to each other in an array, each write steals the line from the other core, and the line ping-pongs although no data is actually shared. That is false sharing. Throughput can drop several times; microbenchmarks often show an order of magnitude.

Detect: scaling gets worse as you add threads, even though threads touch "independent" data. On Linux, perf c2c reports cache lines with heavy cross-core traffic.

Fix: keep hot per-thread data on separate lines, or accumulate in locals and merge at the end.

C++17 offers std::hardware_destructive_interference_size where the standard library provides it. In Java, the JDK uses @jdk.internal.vm.annotation.Contended (for example on LongAdder's cells); application use requires opting into the internal annotation at compilation and using -XX:-RestrictContended at run time. Manual padding is layout dependent, so verify rather than assuming field placement.

Likely follow up: "Should you pad everything?" No: padding wastes memory and cache. Pad only data that different threads write frequently.

12Seniorcache-coherencehardware
Caches are coherent (MESI). Why do we still need memory barriers and atomic instructions?
Model answer

cache coherence guarantees that all cores agree on the order of writes to a single location, and that a write is not lost. MESI names the states a line can be in: Modified, Exclusive, Shared, Invalid (Intel and AMD use variants such as MESIF and MOESI).

Coherence says nothing about:

  • Ordering across different locations. The pipeline sits in front of the cache: stores wait in a store buffer before reaching it, loads can be satisfied early or speculatively, and architectures permit different cross-location observation orders. So core 1 can write data and then a flag, and core 2 can see the flag before the data. Barriers and acquire and release order one thread's accesses relative to each other.
  • Atomicity of read-modify-write. Two cores can both read 5 and both write 6. Atomic instructions (lock xadd and lock cmpxchg on x86, load-linked and store-conditional or LSE atomics on ARM) provide an indivisible successful update. Load-linked/store-conditional detects interference and retries; it need not hold the line exclusively between the two instructions.
  • The compiler, which follows the language memory model; coherent hardware does not prohibit source-level transformations of unsynchronized code.

Likely follow up: "What does a contended atomic cost, then?" Moving the line between cores: on the order of 100 cycles or more per transfer, more across sockets.

13Seniormemory-modelsc-drf
What does "sequential consistency for data-race-free programs" mean, and why should you care?
Model answer

sequential consistency means the execution can be explained as one interleaving of operations that respects each thread's program order. It does not make a sequence of several operations atomic.

Java's JLS guarantees sequentially consistent behavior for correctly synchronized programs: all sequentially consistent executions must be free of data races. Ordinary fields protected by monitors, together with correctly used volatile handoffs, fit this model. Weaker VarHandle modes require their own ordering analysis.

C++ needs an extra qualification: data-race-free alone does not imply sequential consistency. Two threads can use only relaxed atomics in the store-buffering test, have no data race, and both read zero, an outcome impossible under sequential consistency. The usual SC-for-DRF reasoning applies when synchronization uses mutexes and sequentially consistent atomics, with no weaker atomic operations affecting the argument.

This lets you reason using interleavings for ordinary locked code, while keeping explicit proofs for acquire/release or relaxed algorithms. Eliminating data races is necessary; it does not eliminate race conditions such as check-then-act on two separately atomic calls.

Likely follow up: "Does volatile increment become safe?" No. Its individual Java accesses are synchronized, but another increment can interleave between the read and write.

14Corevisibilitylitmus
Thread A runs x = 42; ready = true; and thread B runs if (ready) print(x);. What can B print with a plain ready, and with a volatile (or std::atomic) ready?
Model answer

Plain fields, Java: 42, 0, or nothing.

  • Nothing, if B reads ready before A's write lands, or never sees it.
  • 0, because there is no happens-before edge: the compiler or CPU may reorder A's two writes, or B's two reads (B may load x early, speculatively).

Plain fields, C++: a data race, so undefined behavior; do not enumerate a closed set of legal outputs for that C++ program.

volatile ready (Java) or atomic ready with seq_cst, or release on the store and acquire on the load (C++): 42 or nothing. The write to x happens-before the write to ready; the read of ready that sees true synchronizes with it; so x must be 42.

Note that only ready needs to be volatile; x can stay plain. That works only because x is written before the flag and read after it.

Likely follow up: "What if A writes x after setting ready?" Java may read the old value; C++ has a data race on the plain payload. Publication covers preceding writes, and the example assumes a one-shot flag with no later payload mutation.

15Stretchcppfences
What does std::atomic_thread_fence do, and when would you use it instead of putting the order on the atomic operation itself?
Model answer

A fence orders memory operations around it without being tied to one atomic variable. A release fence followed by a relaxed store, paired with a relaxed load that reads that store followed by an acquire fence, synchronizes exactly like a release store and an acquire load.

When fences are worth it:

  • Many relaxed operations that need one barrier between them, for example checking several relaxed flags and paying for a single acquire fence only if one was set.
  • Specialized lock-free algorithms that need ordering between operations on different variables. Fences alone cannot legalize raced plain payload reads in a C++ seqlock.
  • Correctly placed seq_cst fences can supply Dekker-style ordering; shared flags must still be atomic.
  • std::atomic_signal_fence orders only against a signal handler on the same thread: a compiler barrier.

For inter-thread publication, fences need an atomic communication path; fences around plain accesses alone do not repair a data race. Java has VarHandle.acquireFence, releaseFence and fullFence (Java 9).

Likely follow up: "So should you prefer fences?" No: ordering on the operation is clearer and usually just as fast. Fences are for specific patterns.

16Stretchjavavarhandle
What are VarHandle access modes, and how do they map to C++ memory orders?
Model answer

A VarHandle (Java 9) performs atomic operations with a chosen memory ordering on fields and array elements, replacing most uses of sun.misc.Unsafe. From weakest to strongest:

  • Plain (get, set): like a normal field access; no ordering, and long or double may tear.
  • Opaque (getOpaque, setOpaque): bitwise atomic and coherent for the same variable, but with no cross-variable publication ordering. Roughly analogous to C++ relaxed, without a bounded visibility guarantee.
  • Release and acquire (setRelease, getAcquire): C++ release and acquire.
  • Volatile (getVolatile, setVolatile): the same as a volatile field, roughly C++ seq_cst.

Plus read-modify-writes (compareAndSet, weakCompareAndSetPlain, getAndAdd) and fences.

The JDK's own concurrency classes use these heavily. Application code rarely needs them: the AtomicX classes expose the same modes, for example lazySet, which is setRelease.

Likely follow up: "Why would anyone use lazySet?" It provides release rather than volatile ordering, useful for publication to an acquire reader, such as a single-producer queue index. A cheaper hardware mapping is possible, not guaranteed.
