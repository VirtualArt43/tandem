Taking several locks safely

Why two locks taken in different orders deadlock, and the three reliable fixes: one global order, all-or-nothing acquisition, and lock hierarchies.

Asked atRubrikNvidiaApple
Before this:Mutexes and RAII guardstryLock, timeouts, interruptible locking and fairness

One lock cannot deadlock with itself across threads. The moment an operation needs two locks, a transfer between two accounts, a move between two stripes, you can write code that passes every test and hangs in production. This lesson is the toolkit for never writing it.

In plain words

Two cooks share one knife and one chopping board, and every dish needs both. Cook A picks up the knife and reaches for the board; at the same moment cook B picks up the board and reaches for the knife. Each politely waits for the other to finish. Neither ever will.

The kitchen fixes it with a house rule: always pick up the board first, then the knife. Now whoever gets the board will also get the knife eventually, and the other cook simply waits for the board. Nobody can hold the knife while waiting for the board, so the circle of waiting can never close.

How two locks deadlock

The classic case is a bank transfer that locks the source account, then the destination. Each call is correct alone. Two calls in opposite directions are not:

A deadlock needs four conditions at once: mutual exclusion (a lock has one holder), hold and wait (a thread keeps one lock while waiting for another), no preemption (nobody can take a lock away), and circular wait (a cycle of threads, each waiting for the next). Remove any one and deadlock is impossible. Locks need the first and third, so the practical fixes attack the other two: break circular wait with an order, or break hold and wait with all-or-nothing acquisition. The full taxonomy is in deadlock: the four conditions.

Run the Java version and look at the thread dump the site shows: the JVM finds the cycle itself and prints "Found one Java-level deadlock", naming which thread holds which lock. The bug here is a dynamic lock order: the order depends on the arguments, so no single line of code looks wrong.

Fix 1: one global order

Pick a total order over all the locks, and have every thread acquire them in that order. Then a cycle is impossible: a thread holding a "smaller" lock may wait for a "bigger" one, never the other way round, and a chain of waits can only climb. This is lock ordering, and for accounts the natural order is a unique, immutable id.

Two details carry real weight. The self-transfer check: in C++, ordering from and to when they are the same account would lock one std::mutex twice, which is undefined behavior; in Java it would work (monitors are reentrant), but it is still a case to decide on purpose. And the order key must be unique and stable: if it can change while threads use it, or two locks can share it, the order is no longer total.

When keys can tie

Sometimes there is no natural unique key. Java code sometimes orders by System.identityHashCode(lock), but two different objects can have the same identity hash. The standard trick for that rare tie is a global tie-breaking lock: when the keys are equal, first take one extra lock that only tie cases use, then the two locks in either order. Only one tied transfer can be inside at a time, so tied pairs cannot form a cycle. In C++ you can order by address instead: std::less on pointers gives a total order over all objects, and distinct objects never share an address.

For more than two locks the rule generalizes: collect the locks, sort them by the key, remove duplicates, acquire in that order, release in any order. Release order does not matter for deadlock; only acquisition order does.

Fix 2: take them all at once, or none

Sometimes no order is available: the locks are discovered as you go, or belong to code you do not control. Then break hold and wait instead: try to take every lock, and if any one is busy, release all the ones you got, back off, and retry. No thread ever waits while holding a lock.

C++ has this built in. std::scoped_lock (C++17) with several mutexes, or std::lock (C++11), acquires them all using a deadlock avoidance algorithm, whatever order you list them in. Java has no library equivalent, so you write the loop with tryLock, as in tryLock and backoff.

C++

Before C++17, the same thing takes two steps: std::lock(a.m, b.m); to acquire both, then std::lock_guard<std::mutex> ga(a.m, std::adopt_lock); std::lock_guard<std::mutex> gb(b.m, std::adopt_lock); so that RAII releases them. Or create std::unique_locks with std::defer_lock and pass the locks to std::lock. Interviewers who expect C++11 or C++14 will ask for this form. Under the hood, common implementations lock one mutex, try_lock the rest, and on failure release everything and start again with the mutex that was busy, which is the all-or-nothing loop above.

Two limits to know. All-or-nothing only protects the locks you acquire together: if you already hold lock C before calling std::scoped_lock(a, b), and another thread holds A while waiting for C, you can still deadlock. And retry loops can burn CPU under heavy contention. Without the randomized backoff, two threads can even grab one lock each, both fail, both release and both retry in step, forever: a livelock, where everyone is busy and nobody progresses. That is why ordering is usually the first choice when an order exists.

Fix 3: lock hierarchies

In a large codebase, "always lock the smaller id first" does not scale to dozens of lock types. A lock hierarchy assigns every lock a level, for example the bank's registry lock 100, an account lock 10, a ledger lock 5, and enforces one rule: a thread may only take a lock whose level is lower than every lock it already holds. Any code that respects the levels cannot form a cycle.

The real power comes from checking it at runtime. A wrapper that records the current thread's levels throws the moment a thread asks for a lock out of order, even in a single-threaded test where no deadlock could actually happen. A rare timing-dependent hang becomes an immediate, reproducible error.

Large systems keep hundreds of locks deadlock free this way: the order is part of each lock's documentation, and a checker runs in test builds (the Linux kernel's lockdep validator is a well-known example of runtime lock order checking). The cost is design discipline, and a checked wrapper usually forbids taking two locks of the same level, so peers such as two accounts still need an ordering rule inside their level.

Finding deadlocks when they happen anyway

  • Java: a thread dump (jstack <pid>, jcmd <pid> Thread.print, or the SIGQUIT the site sends) lists every thread with the locks it holds and waits for, and reports cycles as "Found one Java-level deadlock". Programmatically, ThreadMXBean.findDeadlockedThreads() finds cycles among monitors and ownable java.util.concurrent locks such as ReentrantLock (it misses waits on conditions and latches, and locks held in read mode, which have no single owner); a watchdog can call it every few seconds and raise an alert.
  • C++: attach a debugger or capture all thread stacks (gdb with thread apply all bt, lldb with bt all) and look for threads parked in mutex waits, each holding what the next one wants. On Linux, ThreadSanitizer can also report lock-order inversions, a potential deadlock, from a run that did not hang, because it records the order in which each thread took its locks; the Apple toolchain that runs this site's samples does not report them.
Java

Worked example: the deadlock that hides in two classes

Debugging rounds rarely hand you transfer(a, b). They hand you two well-meaning classes. A Taxi has a synchronized setLocation() that, on arrival, calls dispatcher.notifyAvailable(this), which is synchronized on the dispatcher. The Dispatcher has a synchronized getImage() that loops over its taxis and calls each taxi.getLocation(), which is synchronized on the taxi.

  1. Find the lock pairs. setLocation takes taxi, then dispatcher. getImage takes dispatcher, then taxi. Two paths, opposite orders: a deadlock as soon as one taxi arrives while the dispatcher draws its map.
  2. Notice why no line looks wrong. Each method takes only its own lock. The second lock is taken inside a call to another object, which is exactly the "calling foreign code while holding a lock" problem from reentrancy.
  3. Fix with open calls. In setLocation, update the location under the taxi lock, decide whether it arrived, release the lock, then call the dispatcher. In getImage, copy the set of taxis under the dispatcher lock, release it, then ask each taxi for its location. No method holds one object's lock while taking another's.
  4. State the trade-off. The map is now a set of individually consistent snapshots, not one atomic picture, which is fine for a display. If a truly atomic view were needed, you would need one order for all taxi and dispatcher locks.

Common mistakes

  • Ordering by argument position. "Lock from, then to" is an order that depends on the caller. Order by a property of the lock itself.
  • A non-unique or changing order key. Hash codes can tie and mutable fields can change. Use an immutable unique id, add a tie-breaking lock, or in C++ order by address.
  • Forgetting the same-object case. std::scoped_lock(m, m) and ordered lock_guards on one mutex are undefined behavior in C++. Check &from == &to first.
  • Believing release order matters. Releasing in reverse order is tidy (RAII does it) but irrelevant for deadlock. Only the order of acquisition can form a cycle.
  • Using all-or-nothing while already holding another lock. std::lock and tryLock loops protect only the set they acquire together.
  • Calling into another object while holding your lock. Callbacks, listeners and getters on other objects create lock orders you never wrote down. Prefer open calls.

In the interview

"Write a thread-safe transfer between two accounts" is the canonical form; an Nvidia report asked exactly how two locks in a deposit can deadlock and how to fix it, and Apple has asked how deadlocks happen and how to resolve them. At Rubrik it shows up in debugging rounds built on someone else's code (a barber shop simulation whose deadlocks you must fix, a cinema booking service, a banking app), and in the transfer deadlock problem you will practice.

Two threads taking the same two locks in opposite orders can each hold one and wait for the other. I remove circular wait by imposing a global order: I always lock the account with the smaller id first, handle the same-account case explicitly, and use a tie-breaking lock if the order key could ever tie. When there is no natural order, I break hold and wait instead: in C++, std::scoped_lock takes all the mutexes with a deadlock avoidance algorithm; in Java, I try each lock and release everything on failure, with randomized backoff.
In a larger codebase I would assign lock levels and check them in test builds, so an out-of-order acquisition fails immediately instead of hanging once a month, and I would avoid calling other objects while holding a lock.

Follow ups to expect: "What if the ids can be equal?", "Now transfer among N accounts" (sort, deduplicate, lock in order), "How would you detect a deadlock in production?" (thread dumps, findDeadlockedThreads, stack captures), "Is your fix deadlock free if a callback runs under the lock?", and "How does this relate to the dining philosophers?" (five locks in a ring: number the forks and always take the lower one first, take both forks all or nothing, or let at most four sit down at once; see the dining philosophers).

Senior depth

  • Ordering composes, all-or-nothing does not. If every module respects one global order, any combination of modules is deadlock free. All-or-nothing must see every lock of an operation at one call site, which breaks down across layers.
  • Deadlock is not only locks. A thread holding a lock while waiting for a pool thread, a queue slot or a future can deadlock with a thread that needs that lock to produce it. The same four conditions apply to any resource; hold-and-wait across a blocking call is the usual culprit.
  • Timeouts are a last line, not a design. A timed tryLock turns a deadlock into an error that someone must handle, often by retrying into the same deadlock. Prevent the cycle by construction, and keep timeouts for overload protection.
  • When the second lock is discovered under the first. Sometimes you must hold one lock to learn which other lock you need: lock a node to read its parent, lock an order to find its account. You cannot sort up front, so take the second lock with a non-blocking tryLock or try_lock. If that fails, release the first, take both in the global order, and then re-check what you read, because while you held nothing the node may have moved or the account may have closed. If it changed, release and start again.
  • Hand-over-hand locking is ordering too. Walking a linked list or a tree by locking the next node before releasing the current one never deadlocks, because every walker takes locks in the same direction, head to tail or root to leaf. One operation that walks the other way, say a rebalance that climbs from a child to its parent while holding the child, breaks the order and can deadlock with a walker coming down.
  • Databases do it differently. A database lock manager detects cycles in its waits-for graph and aborts one transaction as the victim, then the application retries. That is detection and recovery instead of prevention, and it works because transactions can be rolled back. Threads holding mutexes cannot.

Key takeaways

  • Two locks taken in different orders by different threads can deadlock; argument-dependent order is the usual hidden cause.
  • Fix 1, one global order: lock by a unique, immutable key; handle the same-object case; break ties with a tie lock or, in C++, by address.
  • Fix 2, all or nothing: std::scoped_lock or std::lock in C++, a tryLock loop with randomized backoff in Java. Only protects locks taken together.
  • Fix 3, lock hierarchies: levels plus a runtime check turn rare hangs into immediate errors.
  • Release order does not matter for deadlock. Calling other objects while holding a lock creates orders you never chose.

Quick check

Answer each question, then read why. Your score is saved for your module test.

transfer(from, to) locks from and then to. Thread 1 calls transfer(a, b) and thread 2 calls transfer(b, a), with no other synchronization. What can happen?
Why. If one call takes both locks before the other starts, it finishes. If each thread gets its first lock before the other's second, they wait for each other forever. Neither language detects this at the lock call; a Java thread dump can report it afterwards.
You order lock acquisition by a hash of each account, and two different accounts can have the same hash. What do you need?
Why. With a tie, two threads may lock the pair in opposite orders, which is the original deadlock. A secondary unique key restores a total order; a tie lock lets only one tied operation take its pair at a time, so no cycle can form among tied pairs.
All threads acquire locks A and then B. Some release A first, others release B first. Can the release order cause a deadlock?
Why. A cycle needs threads waiting for locks, and only acquisition waits. Releasing in reverse order is a good habit (and RAII does it automatically), but any release order is safe as long as acquisition follows the global order.
A checked hierarchy gives the bank lock level 100 and an account lock level 10; a thread may only take a lock with a lower level than any it holds. A single-threaded test holds an account lock and then asks for the bank lock. What happens?
Why. The checker compares the requested level with the levels already held and refuses out-of-order acquisitions on the spot. That is the point of a checked hierarchy: an ordering bug shows up in any test that exercises the path, without needing the unlucky interleaving.
A thread already holding lock C calls an all-or-nothing acquisition of A and B (std::scoped_lock(a, b), or a tryLock loop in Java). Another thread holds A and is blocked waiting for C. What can happen?
Why. The first thread holds C and cannot get A, which the second thread holds while it waits for C. In C++ std::scoped_lock simply blocks on A; a Java tryLock loop retries forever instead. Either way neither thread ever makes progress. Deadlock avoidance algorithms only cover the locks passed to one call. Either include C in the same acquisition or follow a global order for all three.
Java onlyA Java watchdog calls ThreadMXBean.findDeadlockedThreads() every few seconds. Which hang will it NOT report?
Why. findDeadlockedThreads looks for cycles of threads waiting to acquire monitors or ownable synchronizers such as ReentrantLock. Threads waiting on a condition, a latch or a queue are not waiting to acquire anything that another thread owns, so a lost wakeup or a starved queue does not appear as a deadlock, even though the program is just as stuck.
C++ onlytransfer(Account& from, Account& to) uses std::scoped_lock lk(from.m, to.m); with std::mutex members. What happens when someone calls transfer(acct, acct)?
Why. The deadlock avoidance algorithm assumes distinct mutexes. Calling lock or try_lock on a std::mutex the calling thread already owns is undefined behavior. Check for the same object before locking.

Model answer

A complete answer, which also refuses an overdraft while it holds both locks:

The points that matter:

  • Order by a unique, immutable id, so every thread agrees on the order regardless of argument order.
  • Return early when from and to are the same account. In C++ this avoids undefined behavior; in Java it avoids pointless reentrant locking and makes the intent explicit.
  • Update both balances while holding both locks, so no thread ever sees money in flight (a reader that sums balances must also take the locks, in the same order).

Explain
Compare the three ways of taking several locks safely, and say when you would pick each.
Model answer

Global ordering breaks circular wait: every thread acquires locks in one total order, such as ascending account id. It costs nothing at runtime, composes across modules, and is my default whenever a natural order exists. Its weakness is discipline: one code path that ignores the order reintroduces the bug, and dynamic orders (by argument) are easy to get wrong.

All or nothing breaks hold and wait: take every lock or none, backing off on failure. std::scoped_lock and std::lock do it in C++; in Java it is a tryLock loop. I pick it when no order is available, for example when locks are discovered at runtime. It only protects locks acquired in the same call, and under contention the retries waste CPU and need randomized backoff to avoid livelock.

Lock hierarchies are ordering at scale: every lock type gets a level and a thread may only acquire downward. With a runtime checker in test builds, an ordering bug fails deterministically on the first test that exercises the path. I would use it in a large system with many lock types. On top of all three, I avoid calling foreign code while holding locks, because callbacks create orders nobody wrote down.

Debug
A service hangs under load. Thread dumps show thread 1 holding the Inventory lock and waiting for the Order lock inside Order.markShipped(), and thread 2 holding the Order lock and waiting for the Inventory lock inside Inventory.reserve(). Neither method mentions the other class's lock directly. What is going on, and how do you fix it?
Model answer

It is a lock order inversion across two objects. One path calls from code that holds the Inventory lock into Order.markShipped(), which takes the Order lock; the other path calls from code holding the Order lock into Inventory.reserve(), which takes the Inventory lock. Each method only locks its own object, so no single line looks wrong, but together they acquire the same two locks in opposite orders, and under load the interleaving finally happens.

The cleanest fix is to stop calling across objects while holding a lock: compute what needs to happen under one lock, release it, then call the other object (open calls). If the two updates must be atomic together, define one global order (say Inventory before Order), make both paths acquire both locks in that order at the outermost level, and document it. Then add a regression check: a lock hierarchy assertion in tests, or at least a stress test that runs both paths concurrently, and keep a deadlock watchdog (findDeadlockedThreads in Java) in production.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Here is a transfer(from, to) that locks from, then to. Walk me through how it can hang, and how you would fix it."
What a strong answer covers
  • The interleaving: thread 1 runs transfer(a, b) and locks a, thread 2 runs transfer(b, a) and locks b, each then waits for the other
  • Name it: circular wait, and the order comes from the arguments, so no single line looks wrong and tests usually pass
  • The fix: lock in one global order by a unique, immutable id, whatever the argument order
  • Handle the same account before locking: locking one std::mutex twice is undefined behavior in C++
  • Ties or no natural key: a tie-breaking lock in Java, address order with std::less in C++
  • The alternative: std::scoped_lock in C++, a tryLock loop with randomized backoff in Java
How a senior would say it
It hangs when two transfers run in opposite directions. Thread one calls transfer from a to b and locks a. At the same moment thread two calls transfer from b to a and locks b. Now thread one wants b, which thread two holds, and thread two wants a, which thread one holds. Neither lets go, so both wait forever. That is circular wait, and the nasty part is that the order comes from the arguments, so no single line looks wrong and the tests usually pass. The fix is to stop letting the caller choose the order. Every account has a unique id that never changes, and I always lock the smaller id first. Then a thread holding a lower lock only ever waits for a higher one, so the circle cannot close. Two details. If from and to are the same account, I return early, because locking one std::mutex twice is undefined behavior in C++. And if the key could ever tie, I add a tie-breaking lock, or in C++ order by address. In C++17 I could also hand both mutexes to std::scoped_lock, which avoids the deadlock for me.

Likely follow up: Now one transfer touches N accounts. What changes?

Out loudabout 80 s
"Sometimes you only learn which second lock you need after you hold the first. How do you take both without risking a deadlock?"
What a strong answer covers
  • You cannot sort the locks up front, so plain ordering does not apply directly
  • Never block on the second lock while holding the first out of order
  • Try the second without waiting; on failure release the first and take both in the global order
  • Re-check after reacquiring: what you read under the first lock may have changed while you held nothing
  • Alternatives: all or nothing with randomized backoff, or one coarser lock if the path is rare
How a senior would say it
The one thing I must not do is block on the second lock while holding the first, because another thread may be taking the same two the other way round. So I try the second lock without waiting, with tryLock in Java or try_lock in C++. If I get it, I am done, because I never waited while holding anything. If I do not, I release the first lock, and since I now know both, I take them in the global order, say by id, where blocking is safe. The step people forget is the re-check. I learned which second lock I needed while holding the first, and then I let go for a moment, so the node may have moved to another parent, or the account may have closed. After reacquiring I validate again, and if it changed, I release and start over. If there is no usable order at all, all or nothing with randomized backoff works too, at the cost of retries. And if this path is rare, one coarser lock over both may simply be better.

Likely follow up: Could that retry loop run forever? What would you do about it?

"A service hangs a few times a month and only a restart fixes it. How do you find out whether it is a lock order deadlock, and how do you stop it coming back?"
What a strong answer covers
  • Capture every thread's stack while it is hung, before the restart: jstack or jcmd Thread.print, or gdb or lldb in C++
  • A deadlock shows threads blocked on locks, each holding what the next wants; a Java dump names the cycle
  • Threads in wait, on a condition or on a queue with no cycle of owners point to a lost wakeup or a starved pool instead
  • Find the two code paths that take the same locks in opposite orders, often a call into another object under a lock
  • Fix with one global order or open calls; guard with checked lock levels in tests, ThreadSanitizer on Linux and a deadlock watchdog
How a senior would say it
First I get evidence while it is hung, before anyone restarts it. In Java I take a thread dump with jstack or jcmd Thread.print. If it is a lock order deadlock, the JVM says so: it reports a Java-level deadlock and names which thread holds which lock. In C++ I attach gdb or lldb and dump every thread's stack, looking for threads stuck in a mutex lock, each holding what the next one wants. If instead the threads are sitting in wait, on a condition or on a queue, and nobody owns what another needs, it is not a deadlock. It is a lost wakeup or a starved pool, and that is a different hunt. Once I see the two locks, I find the two code paths that take them in opposite orders. Often one of them calls into another object while holding its own lock, so the fix is an open call, or one documented global order. To stop it coming back, I check lock levels in test builds, run the tests under ThreadSanitizer on Linux, which reports lock order inversions even when nothing hangs, and in Java I keep a watchdog calling findDeadlockedThreads.

Likely follow up: The dump shows no cycle at all, just every pool thread waiting on a future. What is going on?
