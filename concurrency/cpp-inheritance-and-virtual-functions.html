Inheritance and virtual functions

Read class hierarchies, predict virtual dispatch and destruction, and keep partially constructed objects away from worker threads.

Before this:Classes, constructors, destructors and RAIIunique_ptr, shared_ptr and weak_ptr

A worker often owns a pointer to an interface and calls an implementation it has never seen. Understanding what exists behind that pointer, and when it stops existing, prevents some of the hardest C++ shutdown bugs.

In plain words

A delivery service promises a method called deliver. A bicycle courier and a van courier keep that promise differently. The dispatcher needs the promise, not a separate branch for every vehicle. Inheritance describes the relationship; a virtual function lets the actual courier choose the behavior.

But a van cannot drive while its engine is still being assembled. Construction and destruction have stages. Giving a worker access to an object during those stages is a lifetime problem before it is a locking problem.

Why this matters for concurrency

Thread pools store tasks behind interfaces, caches receive interchangeable loaders, and tests inject fake clocks. Those designs depend on dispatch through references or pointers. A correct mutex does not rescue a sliced object, a missing virtual destructor, or a worker calling a destroyed derived member. The core lessons on safe publication and creating threads build on these language rules.

Start with the base subobject

class FileTask : public Task means a FileTask contains a Task base subobject and publicly satisfies its interface. An accessible, unambiguous derived pointer converts to a base pointer automatically. The conversion borrows the same object; it does not copy it. Public inheritance should model a substitutable relationship: a caller using the base contract must still be correct with the derived object.

public members are part of the caller's API. private members belong to the class's implementation, including when the object has a derived part. protected grants access to derived classes as well. It does not mean thread protected. Prefer private state and protected operations that preserve invariants; an exposed protected counter lets every subclass invent its own synchronization policy.

Classes default to private inheritance if the access word is omitted; structs default to public inheritance. Write public explicitly for an interface relationship. Private inheritance is an implementation technique and usually loses to composition in an interview design.

Base private members remain inaccessible to derived code unless friendship grants access. Only public inheritance permits an ordinary outside caller to make an implicit derived-to-base conversion. Protected access to a nonstatic member also restricts the object expression: a derived member can use its own derived objects, but cannot access that member through an arbitrary Base&.

Static type, dynamic type, and the call that runs

In Task& task = file, the expression task has static type Task, while the complete object has dynamic type FileTask. Calling a virtual function through that reference selects the final overriding implementation for the live object: dynamic dispatch. A nonvirtual function is selected using the static type. The object remains derived whether its reference is const or nonconst.

override asks the compiler to prove that the declaration overrides a base virtual function. A missing const, a different parameter type, or a spelling mistake becomes a compile error. Once virtual, a function stays virtual in descendants even if they omit the word. Write override on overrides anyway. final on a function prevents further overriding; final on a class prevents further derivation. Neither word is a synchronization primitive.

An explicit qualified call such as file.Task::run() deliberately selects the base implementation. Default arguments are also chosen from the static declaration, even when the function body dispatches virtually. Avoid changing defaults across overrides: it creates a surprising combination of base arguments and derived behavior.

Overriding is different from hiding an overload set

A derived declaration with the same name hides base overloads during name lookup, even if its parameters differ. using Base::name; brings the base overloads back into the candidate set; it does not create an override. Name lookup and overload resolution happen before virtual dispatch.

The member's const and reference qualifiers such as & must match for overriding. Return types normally match too, with a limited covariant return exception for class pointers or references: Derived* can replace Base* when the conversion is accessible and unambiguous. Returning std::unique_ptr<Derived> cannot override a function returning std::unique_ptr<Base>; both declarations must return the base smart pointer type. An override may add noexcept but cannot weaken a base noexcept guarantee.

Access checks use the declaration selected at the call site, so a public base virtual can dispatch to a private override. Constructors, static member functions and member function templates cannot be virtual. Declaring virtual void run() = 0; makes an operation pure virtual; a class with a pure final overrider is abstract and cannot be instantiated. See abstract classes and interfaces for complete contracts.

The C++ standard specifies observable behavior, not a vtable layout, pointer count, or fixed byte overhead. Multiple inheritance may need several pointers and address adjustments. A compiler can devirtualize a call when it knows the concrete type, including many calls on final classes. Do not sell virtual dispatch as either free or automatically too expensive: measure the hot path. A storage request often spends far more time in I/O than dispatch.

Construction and destruction are ordered stages

Construction initializes virtual bases first when present, then direct bases in declaration order, then data members in declaration order, then executes the constructor body. The order written in the initializer list cannot reorder those steps. Destruction runs the destructor body, then destroys members in reverse declaration order, then bases in reverse order. Virtual bases are destroyed last by the most derived object's destruction.

A virtual call made from a base constructor on the object being constructed reaches the base's current override. The derived part is not ready. The corresponding rule applies during destruction after the derived part has been torn down. If that stage's final overrider is pure, making the virtual call from the constructor or destructor, including through a helper, is undefined behavior; giving the pure virtual function a body does not make that call safe. These dispatch rules are specified in the C++20 construction and destruction rules.

The trace owns its strings and outlives both destructors. Real production destructors should avoid allocating or throwing while logging; this short program uses a trace only to expose the language sequence.

Virtual destruction is an ownership requirement

For ordinary deletion through a base pointer, the base needs a virtual destructor when the complete object is derived. Otherwise the behavior is undefined, not merely a guaranteed resource leak. std::unique_ptr<Base> with its default deleter still deletes through a base pointer and therefore needs that destructor. Smart ownership does not repair a wrong destruction contract.

The usual interface declaration is virtual ~Base() = default;. A base deliberately not supporting deletion through its interface can instead have a protected nonvirtual destructor, preventing callers from performing that deletion. For the polymorphic owning pointers used in Tandem, prefer the public virtual form. A virtual destructor also makes a class polymorphic, even if it has no other virtual member.

std::shared_ptr<Base> p = std::make_shared<Derived>(); preserves the destruction operation created for Derived, so this particular ownership path works even without a virtual base destructor. Constructing a fresh shared_ptr<Base> from an already erased Base* with its default deletion operation does not recover the derived type. The distinction is how ownership was created, not whether the pointer is smart. Keep a public virtual destructor for an interface intended to support ordinary base-pointer deletion.

A pure virtual destructor, declared virtual ~Base() = 0;, still needs a definition, typically Base::~Base() = default; outside the class, because derived destruction invokes it. Also, a user-declared destructor suppresses implicit move operations; review the special members when a base owns resources. Copy and move semantics covers that separate responsibility.

Object slicing is a copy, not a dispatch bug

With a concrete, copyable base, Base copy = derived; constructs a new base object without a derived portion: object slicing. Passing a base by value and storing derived objects in std::vector<Base> do the same thing. Pass a base reference for borrowing, and store owning smart pointers when a heterogeneous collection must retain derived behavior. If polymorphic copying is required, design an explicit virtual clone operation returning an owning pointer.

Assignment through a base reference is a different trap: it assigns only the base subobject of an existing derived object, potentially breaking its invariants without changing its dynamic type. Polymorphic bases can make copying protected or delete it to prevent accidental public copying and slicing. Abstract bases already reject creating standalone base values.

Worked example: the constructor publishes this

Imagine a base constructor starts a thread capturing this; the worker calls run(), and the derived class supplies run() using a vector member. The worker can begin before that vector is constructed. Its calls can overlap construction and changing dispatch state. The synchronous constructor dispatch rule is not a license for this concurrent access.

Finish construction first, then start the worker through an explicit lifecycle operation or a factory that starts a fully constructed object before returning it. Specify whether start() is single caller only. For a worker making virtual calls on the object, stop and join before that object's destructor begins, so dispatch cannot overlap teardown. In every design, joining must precede destruction of the state the worker accesses; a base destructor is too late for derived members. Never join while holding a mutex the worker must acquire to exit. Cancellation explains the protocol.

Keep the worker's owner outside the task hierarchy

The task is fully constructed before launch, the owner keeps it alive, and successful join() makes the worker's result visible before the assertion. Only the main thread prints. C++20 std::jthread also joins on scope exit if still joinable, before earlier locals are destroyed; in C++17 use std::thread with an RAII joining guard.

This finite task needs no cancellation. A long-running task needs a cooperative stop protocol, including waking any blocking wait; request_stop() does not forcibly interrupt arbitrary code. A jthread member in a base class would still be destroyed too late to protect derived state. Do not call unknown virtual hooks under an internal lock unless their contract explicitly controls blocking and re-entry: an override can acquire another lock or call back into you.

Multiple inheritance and the diamond

A class can derive from several bases, commonly several small interfaces. An inherited name can be ambiguous and need qualification; a base pointer can point into a different part of the complete object. A diamond with ordinary inheritance contains two copies of the repeated base; virtual inheritance shares one virtual base, initialized by the most derived constructor. None of this implies virtual functions by itself. Prefer composition for shared implementation, and use multiple interface inheritance only when the contracts really belong together.

For Left : Root, Right : Root, and Leaf : Left, Right, converting a Leaf* directly to Root* is ambiguous; choosing the Left path selects one of the two subobjects. If both branches instead inherit virtual Root, Leaf has one shared Root. If both branches override the same virtual function of that shared base, Leaf must supply a unique final override; virtual inheritance alone does not resolve competing implementations.

Common mistakes

  • Leaving off override: a parameter or const mismatch can hide the base name instead of overriding. Let the compiler check the intent.
  • Returning a derived object by value as its base from a factory: it slices. Return std::unique_ptr<Base>.
  • Assuming protected state is synchronized: access control and thread safety are different guarantees.
  • Stopping a derived worker in the base destructor: derived members may already be gone. Join before task destruction when the worker dispatches virtually.
  • Declaring a mutex in the base and letting subclasses bypass it: protect invariants through operations, not informal access conventions.

In the interview

Expect a short hierarchy and a request to predict output, then a question about owning it through a base pointer. State the static and dynamic types before naming the function that runs. For a service hierarchy, add the construction and shutdown boundary without being prompted.

I use a base reference to preserve dynamic dispatch and a virtual destructor for default-deleting owning base pointers. I publish the object only after construction, and I stop and join its worker before task destruction begins.

Key takeaways

  • Public inheritance is a contract; virtual functions choose behavior through references and pointers.
  • override checks signatures and final closes extension points.
  • Construction and destruction dispatch within their current class stage.
  • Owning deletion through an ordinary base interface needs virtual destruction.
  • Derived-to-base value copies slice; publication and shutdown must respect the entire object's lifetime.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A base constructor synchronously calls a nonpure virtual name() on this. The derived override exists. Which body runs?
Why. The derived portion is not yet constructed. A normal nonpure virtual call is legal, but its dispatch is limited to the current construction stage.
Base is concrete and publicly copyable, and Derived publicly inherits it. void run(Base b) receives a Derived. What can a virtual call on b see?
Why. Pass by value copies the base portion when Base is concrete and copyable. A reference preserves the original dynamic type, but a value parameter does not. Being polymorphic does not prohibit base copies.
A std::unique_ptr<Base> owns a Derived through its default deleter. Base has a public nonvirtual destructor and no custom deallocation function. What is the deletion contract?
Why. Default deletion uses Base*. A virtual destructor is needed; the smart pointer does not retain a derived destruction operation. Undefined behavior is not a promise to leak only the derived resources.
The base has virtual int size() const. The derived writes int size() override. What happens?
Why. The override specifier catches the mismatch. Without it the new declaration can hide a name without overriding this function. An override cannot remove the base function's const qualification.
What does the C++ standard require about a polymorphic object's vptr?
Why. Vptr and vtable describe common ABIs. Multiple inheritance and optimization make fixed layout claims incorrect.
A worker calls virtual methods on a derived task. When should its owner stop and join it?
Why. Joining before task destruction keeps virtual calls from overlapping teardown. A base destructor is already after derived member destruction. Detach does not extend the task's lifetime or wait for outstanding calls.
What does this complete program print?
Why. b.value() takes the base default 1 but calls the derived body; d.value() takes default 2 and the same body. Nonvirtual b.tag() selects the base function. d.Base::value() explicitly suppresses virtual dispatch and uses the base default. The other answers incorrectly make defaults or nonvirtual calls dynamic, or suppress dispatch just because a reference has base type.

"Walk me through a virtual call in a base constructor and why a worker started there is dangerous."
What a strong answer covers
  • The synchronous call dispatches in the current constructor class
  • Derived state is not ready
  • A worker can overlap construction
  • Start after full initialization and join before task destruction begins
How a senior would say it
The synchronous call uses the override in the base constructor's class. The derived part is not ready, so it cannot be treated as a ready implementation. Starting a worker there introduces a second problem: this escapes while construction is still happening. The worker can race with initialization or touch a member whose lifetime has not begun. I would build the complete object first, then start it through a controlled lifecycle operation. For virtual calls from a worker, I would use an external owner that stops and joins the worker before the task's destructor begins. That keeps dispatch and member access clear of teardown. A sleep is not an ordering guarantee.

Likely follow up: Why is joining only in a base destructor too late?

Out loudabout 60 s
"Why does my vector of base objects keep calling the base implementation?"
What a strong answer covers
  • Insertion copies only the base subobject
  • The resulting dynamic type is Base
  • References preserve behavior without ownership
  • Default-deleting unique owning base pointers need virtual destruction
How a senior would say it
The vector stores actual base values. Inserting a derived object copies its base portion and discards the derived portion, which is slicing. Calling a virtual function then correctly dispatches on a base object. I would use base references for temporary borrowing, or a vector of unique owning base pointers for a heterogeneous collection. The base needs a virtual destructor because those pointers delete through the base type. If the design also needs copies, I would make polymorphic cloning explicit instead of trying to get it from the base copy constructor.
