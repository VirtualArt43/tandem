Collections for coding rounds: comparators, heaps, trees and traps

Turn ordering, top-k, predecessor queries and counting into reliable Java code, without comparator, collection view or boxing surprises.

Before this:The collections you will useLambdas, functional interfaces and method referencesIterators and ConcurrentModificationExceptionequals, hashCode and objects as keys

You can have the right algorithm and still lose a coding round to a comparator that overflows, a tree that drops equal-priority jobs, or a list that refuses an insertion. Learn the exact Java operations that make your algorithm's promise true.

In plain words

A railway clerk can sort the whole day's tickets, keep the next departure on top, find the last departure before noon, or serve passengers in arrival order. Each arrangement answers a different question quickly.

Two passengers with the same departure time are still two passengers. A window into another clerk's register is not your own copy. Decide what stays distinct, what order matters, and who owns the paper before choosing the tool.

Why this matters for concurrency

A scheduler orders deadlines, a crawler queues work, and a metrics worker counts keys. These examples use collections owned by one thread; the collections overview already teaches implementation choices and sharing rules.

A convenient method name does not promise atomicity. Shared HashMap.merge calls need synchronization, and an atomic map insertion does not protect a mutable value. Continue with concurrent hash maps, scheduled executors and the concurrent collections toolkit for those mechanisms.

Write the ordering rule before the comparator

compare(a, b) returns a negative number when a belongs before b, zero for an ordering tie, and a positive number when a belongs after b. Only the sign matters. Swapping arguments must reverse the sign, ordering must be transitive, and tied values must compare with the same sign against every third value.

Complexities below assume constant-time key comparisons and equality checks. Long strings or custom comparison logic can add work to each comparison.

For "team ascending, priority descending, sequence ascending", reverse only the priority comparison. Calling reversed() after the entire chain reverses every key. Method references are explained in lambdas and method references.

Comparable<T>.compareTo(T) defines a type's natural order; a Comparator<T> supplies an external order for a particular use. A record does not automatically implement Comparable. These examples assume non-null comparison keys; for nullable team names, use Comparator.comparing(Job::team, Comparator.nullsLast(Comparator.naturalOrder())). That handles a null team, not a null job, and cannot override a collection's ban on null elements.

The jobs print A 5 1, A 2 0, A 2 2, then B 9 0. Subtraction prints -2147483648, falsely putting the largest integer before negative one; Integer.compare prints 1. Use Integer.compare or Long.compare, never subtraction or a narrowed timestamp difference.

Stable sorting preserves input order among comparator ties. It cannot invent arrival order from an unordered set. Sorting requires element replacement, so fixed-size Arrays.asList works while List.of does not. See the Java 21 contracts for comparators and list sorting.

Heaps: keep the next item, or the best k

A PriorityQueue is a binary heap whose head is least according to its comparator. Natural integer order gives a min heap; Comparator.reverseOrder() gives a max heap. Duplicates survive, but equal priorities have no FIFO guarantee. Add an increasing unique sequence as the final key when arrival order matters.

Worked example: the largest three values seen so far

Keep a min heap of at most three values. Insert each input, then poll once if oversized. The invariant is that the heap contains the largest three values in the processed prefix, or all values when fewer than three have arrived.

This table is not heap iteration order. Repeated polling is ordered and destructive; copy the heap first if you must preserve it.

For n inputs and k at least one, processing costs O(n log(k + 1)); retained storage is O(k). Draining m retained values costs O(m log(m + 1)). A max heap of size k instead keeps the smallest k. Sort when you need every element ordered once.

Changing a queued object's priority does not repair the heap. Remove before changing and reinsert, or enqueue immutable replacements and skip stale versions when polling. There is no decrease-key operation. The PriorityQueue contract also leaves iteration unordered.

Removal by object searches using equals, not the priority comparator, and costs O(n). Lazy replacement avoids that search but retains stale entries until removed: compare each polled version with the authoritative current version and discard mismatches. Bound that extra memory or periodically rebuild; live task count alone no longer bounds heap size. A constructor's initial capacity is not a queue limit, and an insertion that grows the backing array can cost O(n) on that call.

Trees: neighbours, ranges and duplicates

Use TreeMap or TreeSet for neighbours, ordered traversal or ranges. Comparison returning zero means the same tree key: a set rejects the second element, and a map replaces the existing value. Ordering equivalence should match equals for the usual set and map contracts; revisit equality and keys for the distinction from hashing.

One-argument headMap(x) excludes x; tailMap(x) includes x. Navigation follows the comparator, so "first" means numerically largest under reverse order. Basic updates and neighbour queries cost O(log n); traversing r range entries costs O(log n + r). Computing a range view's size may scan it.

The original becomes {20=v2, 30=v3} while the copy stays {10=v1, 20=v2}. Views share storage, including removals; inserting an out-of-range key through one throws IllegalArgumentException. Copying a tree copies references, not its key and value objects.

firstEntry() returns an entry snapshot that does not support setValue; update through the map. Guard a missing floor before unboxing: int t = versions.floorKey(5) would throw. See the TreeMap and TreeSet contracts.

The fixed comparator uses both record components, matching this record's equality. A unique id does not automatically make every comparator consistent with every class's equals. Keep comparison fields immutable while stored; remove an old leaderboard key before inserting its replacement. Locking cannot repair an ordering rule you invalidate yourself.

For duplicate numbers, a TreeMap<Integer, Integer> can store value to positive frequency: bag.merge(value, 1, Integer::sum) adds one. To remove one known-present value, read its count, remove the key if the count is one, otherwise store count minus one. Remove zero-count keys so neighbour queries only find live values. bag.size() counts distinct values, not occurrences; counts need overflow bounds, and the whole update needs one lock if shared.

A tree's ordering does not provide rank in O(log n). headMap(score).size() may scan the range, and Java's TreeMap has no built-in kth-element operation. For frequent rank queries, use a structure that maintains subtree counts or a frequency index over bounded scores.

ArrayDeque: choose the two ends deliberately

For FIFO, insert at the tail and remove at the head. For LIFO, insert and remove at the head. Prefer ArrayDeque to legacy Stack, which extends Vector and synchronizes individual methods without making "check, then pop" atomic.

The interval array contains int[] references, so it accepts a comparator. It prints [[1, 2], [1, 4], [3, 5]]; the matrix prints [[-1, 0, 0], [-1, -1, -1]]. For primitive descending order, sort ascending and reverse by swapping endpoints.

Fill each matrix row: Arrays.fill(dp, -1) selects an object-array overload and throws ArrayStoreException. Filling all outer slots with one int[] instead makes every row reference the same array.

Arrays.asList(intArray) contains one element, the entire array. Varargs do not box each primitive into a separate Integer; loop over the primitives to build that list. List.of prevents list changes, including sorting, but does not freeze elements. See immutability and records, and the Arrays and unmodifiable list contracts.

On List<Integer>, remove(1) removes index one and returns the removed Integer; remove(Integer.valueOf(1)) removes the first value equal to one and returns a boolean. From [1, 2, 1], those calls independently leave [1, 1] and [2, 1]. list.subList(lo, hi) is another backed view, with hi exclusive: clearing it deletes that range from the parent. Structural changes to the parent outside the view invalidate its specified semantics; take an ArrayList copy when you need an independent result.

Binary search: a match is not a boundary

Arrays.binarySearch(a, key) requires a sorted array and returns a matching index, or -(insertionPoint + 1) when absent. Recover an absent insertion point with -(result + 1). With duplicates, a successful search may return any matching index. Collections.binarySearch(list, key, comparator) follows the same convention and requires sorting by that comparator; on a large linked list, navigation can still cost O(n).

These are the array search and list search contracts. Neither method promises the first duplicate.

To find the first value at least a target, keep a half-open search interval [lo, hi): everything before lo is too small, everything from hi onward qualifies. For the first value strictly greater, change < to <=; do not search for target plus one, which can overflow.

Both searches use O(log(n + 1)) time and O(1) extra space. They return n when no element qualifies, so check the result before indexing. The difference upperBound(a, x) - lowerBound(a, x) counts x; a predecessor at most x is at upperBound(a, x) - 1 if that index is non-negative. Searching is logarithmic, but inserting into a sorted ArrayList still shifts elements in O(n).

Counting, grouping and iterating maps

API card: Map convenience methods

OperationMeaning

The counter prints blue=2, green=1, red=3; sorting a copy makes output deterministic. HashMap promises no iteration order. getOrDefault(k, expensive()) evaluates the fallback even for an existing key; computeIfAbsent invokes its factory only when required. Neither a factory nor a merge callback should modify the same map.

For a HashMap owned by one thread with non-null counts, counts.entrySet().removeIf(e -> e.getValue() == 0) removes zeros safely. Calling the map's structural modification methods inside an enhanced for loop can throw ConcurrentModificationException, even on one thread. The full mechanism belongs to iterators and ConcurrentModificationException.

HashMap counting needs confinement or locking when shared. ConcurrentHashMap.merge can make counting atomic per key, but computeIfAbsent(k, x -> new ArrayList<>()).add(v) still exposes an unsynchronized list. Follow the Map contracts and the concrete implementation's guarantees.

Boxed numbers: equality and hot loops

Two Integer references compared with == use identity; use Objects.equals(a, b) for null-safe value equality. Comparing an Integer with primitive 3 unboxes it and throws if null. Caching can hide an identity bug. Types and modern Java covers the conversions and cache boundaries.

Autoboxing makes maps convenient, but updates may create wrappers and incur GC work. Keep a hot accumulator as long, not Long, and use primitive arrays for dense bounded keys. The JIT may eliminate allocations; do not claim every boxing operation allocates or invent a speed ratio. Use long counts when bounds can overflow int; Integer::sum does not detect overflow.

Common mistakes

  • Subtracting comparator keys. Use comparison methods, and test extremes and ties.
  • Reversing the whole comparator chain accidentally. Reverse the intended key.
  • Using a max heap to retain the largest k. Keep the weakest retained candidate at the head, using a min heap.
  • Using priority as tree identity. Distinguish full keys consistently with equality, or map each priority to a bucket.
  • Returning a range view as a snapshot. Copy under the appropriate lock, and decide whether values need copying.
  • Treating fixed-size as immutable. Arrays.asList permits replacement; List.of does not. Neither deep-copies elements.
  • Confusing a search match with the first duplicate. Use explicit lower and upper boundaries, and decode negative library results before indexing.
  • Trusting a missing exception or a map helper. Fail-fast detection is best effort; ordinary maps and nested mutable values need a sharing policy.
  • Boxed identity and boxed hot accumulators. Compare values, handle null, and keep repeated arithmetic primitive.

In the interview

Expect "retain the best k", "find the latest version at or before t", "why did one task vanish?", and "now several workers call this". State the order, duplicate policy, empty result and mutation boundary before typing.

I will keep a min heap of at most k candidates. The root is the weakest retained candidate, so inserting and removing the root when oversized preserves the largest k seen so far. I will specify a tie-breaker when output order matters, and test duplicates, extreme keys, empty input and k equal to zero.

Follow ups: "Change priorities?" Remove and reinsert, or use versioned entries. "Duplicate priorities in a tree?" Distinct full comparison keys or buckets. "Can readers keep this range?" Define snapshot or locking semantics. Invariants and critical sections turns those promises into synchronization boundaries.

Key takeaways

  • Compose comparison keys, reverse only the intended key, and never subtract to compare.
  • A heap exposes one extreme; a tree adds neighbours and ranges, with comparison ties defining duplicate keys.
  • Use ArrayDeque endpoints deliberately; empty polling returns null and never waits.
  • Distinguish fixed-size lists, unmodifiable lists, live views and shallow copies.
  • Give map helpers explicit null, overflow and iteration policies.
  • Choose value equality and primitive arithmetic, then define synchronization separately.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A comparator returns a - b for arbitrary int keys. What happens for a = Integer.MAX_VALUE and b = -1?
Why. Subtraction wraps to Integer.MIN_VALUE. Java does not throw for ordinary integer overflow. Integer.compare(a, b) returns the correct positive sign without subtracting.
You need priority descending and id ascending for non-null tasks with non-null ids in record Task(int priority, String id) {}. Which comparator works?
Why. Reverse priority before appending ascending id. Reversing the finished chain also reverses id. Starting with id makes id the primary key, and leaving the priority comparator unreversed sorts priority ascending.
A min heap retains the largest three values by offering each value and polling once when oversized. After inputs 4, 1, 7, 7, 2, 9, what do three polls return?
Why. The largest three include both sevens, and a min heap returns them ascending. Iteration is unordered; polling still obeys the comparator.
A TreeSet<Task> compares only priority. You add (priority=4, id="a"), then (priority=4, id="b"). The record's equals says they differ. What happens?
Why. The tree uses comparison zero as equivalence, collapsing two unequal records and violating the general equality-based set contract. A heap would retain both, but a sorted set does not.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write best(scores, k) for unique non-null names mapped to non-null integer scores. Return at most k names by descending score, then ascending name. Bound the heap to k candidates, handle k equal to zero, and explain its comparator.
Model answer

Reverse the desired output order for the heap: its head must be the worst retained candidate, including the lexicographically largest name on a score tie. Sort only retained candidates for output.

For n entries and k at least one, heap work costs O(n log(k + 1)); sorting m retained entries costs O(m log(m + 1)). Space is O(k). Unique names resolve ties, so iteration order cannot affect the answer. A shared source map needs a snapshot or synchronization contract.

Debug
A method returns versions.headMap(cutoff, true) from a natural-order TreeMap<Integer, String> as a "snapshot". Its caller clears the result. With no intervening writes, int t = versions.floorKey(cutoff) throws. Explain both symptoms and the correct snapshot boundary when concurrent writers are introduced.
Model answer

Clearing the backed view deletes original entries at or below the cutoff. The floor lookup then returns null, and assignment to int unboxes null, throwing NullPointerException. Keep the result as Integer and handle absence explicitly.

Construct new TreeMap<>(versions.headMap(cutoff, true)) under the same lock every access to versions uses, then release the lock before iterating the copy. Its structure is independent and these String values are immutable. For mutable value types, a shallow copy still shares references: use immutable values or copy them if their state belongs to the snapshot contract. Copying an unsynchronized tree during writes is unsafe.

Explain
A teammate proposes groups.computeIfAbsent(key, k -> new ArrayList<>()).add(value) on a ConcurrentHashMap, saying it fixes missing groups and concurrent appends. What does it fix, and what remains?
Model answer

The map coordinates value creation and publication per key. The following add runs on an ordinary list outside that map operation; callers can obtain the same list and race inside it. Protect each group's reads and writes with the same lock, choose a suitable concurrent value collection, or atomically replace immutable values. If groups can be removed, also define whether appending to an already removed group is allowed; protecting the list alone does not settle that lifecycle race. A plain HashMap would need protection even for lookup and insertion.

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Two equal-priority jobs enter a tree, but one disappears. Walk me through the bug and what you would change before sharing this scheduler across threads."
What a strong answer covers
  • The comparator returns zero for distinct jobs, so the tree treats them as one key
  • TreeSet rejects the second add; TreeMap replaces the existing value
  • Use a comparison key that preserves identity and agrees with the intended equality
  • Keep ordering fields immutable or remove before changing and reinserting
  • A lock protects shared operations but cannot repair an incorrect ordering rule
How a senior would say it
The comparator is treating two different jobs as the same tree key. If it compares only priority, equal priorities return zero. A tree set then rejects the second insertion, and a tree map replaces the value already stored at that key. I would define the identity rule first. If both jobs must survive, I would compare priority and then a distinguishing id, with equality designed consistently. For example, priority four with id a must differ from priority four with id b. I would also keep ordering fields immutable while stored. To change priority, remove the old entry and insert a replacement. Before sharing the scheduler, I would protect its state transitions and reads with the chosen synchronization policy. A lock prevents overlapping operations, but it cannot make a comparator that discards valid jobs correct.

Likely follow up: When would you choose a priority queue instead, and what would happen to equal-priority arrival order?

Out loudabout 60 s
"Several workers need to append values to groups in a map. Why is computeIfAbsent not the whole thread-safety answer?"
What a strong answer covers
  • Atomicity depends on the map implementation; HashMap has no such concurrency guarantee
  • ConcurrentHashMap can coordinate installation of the value for one key
  • The following ArrayList.add is a separate operation on shared mutable state
  • Choose a value-level lock, a concurrent collection, or immutable replacement
  • Include readers and group removal in the same ownership and lifecycle contract
How a senior would say it
It can make group creation safe on a concurrent hash map, but it does not automatically make the group safe. On a plain hash map, even the compute operation needs external protection. With a concurrent hash map, two workers can safely obtain the same installed list, then both call add on that ordinary array list at once. Those appends are outside the map operation and can lose data or damage the list. I would choose a policy for the value: a lock used by every reader and writer, a suitable concurrent collection, or immutable replacement through an atomic map update. I would also ask whether groups can be removed. An append to a list that was just detached from the map can disappear from future lookups even if the list itself is synchronized. The full operation needs a clear lifecycle contract.

Likely follow up: If the operation must update two groups together, is one atomic map operation per key sufficient?
