TTL cache with a cleaner thread

Thread-safe structuresmedium40 minUber machine coding and LLD roundsUber

A cache whose entries expire is what Uber's machine coding rounds keep coming back to: a cache with expiry that must handle concurrent requests, and an expiring counter where the interviewer wanted stale data purged like a production component. It tests three things at once: time, a shared map, and a background thread you must be able to stop.

The task

Build a thread-safe key-value cache where every entry has its own time to live:

  • put(key, value, ttlMs) stores the value; the entry is live while clock() < putTime + ttlMs and expired from then on. Putting an existing key replaces its value and its expiry.
  • get(key) returns the value of a live entry, or none (null, std::nullopt) if the key is missing or expired. Reading an expired entry also removes it (lazy cleanup).
  • size() counts live entries only, even if expired ones have not been removed yet.
  • storedEntries() counts entries physically stored, expired or not, so the tests can see cleanup happen.
  • A cleaner thread, started by the constructor, removes expired entries every cleanupIntervalMs of real time, so keys that are never read again do not stay in memory forever.
  • close() stops the cleaner promptly and returns only after it has stopped. Calling it twice is fine. In C++ the destructor calls close().

Rules:

  • Measure expiry on the injected clock (milliseconds). The cleaner's interval is real time. The tests mostly use a fake clock that moves only when the test moves it, and one small check uses the real clock.
  • The cleaner must be stoppable at once: a close() that has to wait out a 60 second interval fails the tests. In Java, name the cleaner thread ttl-cleaner; the tests look for it.
  • close() only stops the cleaner. get and put keep working afterwards, with lazy cleanup only.

What the tests check

  • Expiry boundaries on a fake clock: an entry with a ttl of 100 put at time 1000 is there at 1099 and gone at 1100; a second put of the same key resets its expiry.
  • size() counts only live entries, without any get calls to clean up first.
  • Reading an expired key removes it: storedEntries() drops.
  • The cleaner removes expired entries that nobody reads, and leaves live ones alone.
  • close() returns within half a second even with a 60 second cleanup interval, and the cleaner is gone afterwards (Java: no live ttl-cleaner thread; C++: the thread was joined). A second close() returns at once; in C++ destroying a cache that was never closed also returns promptly.
  • Concurrency: 8 threads do gets and puts on 64 keys over 40 rounds while the fake clock moves forward between rounds and the cleaner runs every millisecond. A get never returns an expired value or another key's value, and at the end size() agrees with what get sees.
  • The real clock: an entry with a 300 ms ttl is there right after the put and gone 600 ms later.
  • In C++, ThreadSanitizer must stay quiet, which rules out a cleaner that scans the map without the lock.

Taught in: Thread-safe caches: LRU, TTL and single-flight

Open them one at a time. Each one gives away a little more.

Store each value with its expiry time, clock() + ttlMs, in a map guarded by one lock. get compares the expiry with the clock, and removes the entry if it has expired. size() counts the entries that are still live.
The cleaner is a loop: wait for the interval, then remove every expired entry, holding the lock while it touches the map. The question is how it waits. If it sleeps, close() cannot wake it, and you either wait out the interval or leave the thread running.
Wait on a condition with a timeout instead (awaitNanos in Java, wait_for with a predicate in C++), checking a closed flag guarded by the same lock. close() sets the flag, signals the condition, and then joins the thread. Make the second close() harmless, and in C++ make the destructor call close() so the std::thread is never destroyed while joinable.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Add getAverage(): the average of all unexpired values. Confluent asked this, with a heavy focus on strong versus eventual consistency.
Keep a running sum and count of the stored entries, updated on put, overwrite and removal. The catch is that entries expire silently as time passes, with no call to update the sum. Strong consistency: before answering, remove every entry that has expired, under the lock; to find them without scanning, keep a min-heap (or a sorted map) of expiry times, so the purge costs O(k log n) for k expired entries. Eventual consistency: answer from the running sum and let the cleaner correct it on its next sweep, so the average may still include values that expired since then. Say which one you are giving, and why.
Why both lazy expiry and a cleaner thread?
Lazy expiry alone keeps every key that is never read again, so memory grows without bound. A cleaner alone would return expired values between sweeps unless get checks the expiry anyway. Together, get is always correct and the cleaner bounds memory. Redis does the same: it expires keys when they are accessed, and also samples keys with a ttl in the background and deletes the expired ones.
The cleaner scans the whole map while holding the lock. What is wrong with that at scale?
With millions of entries the scan is a long pause during which every get and put waits. Fixes: index entries by expiry time (a min-heap, or time buckets as in a timing wheel) so the cleaner touches only expired entries; sweep in small batches and release the lock between them; or shard the map so each shard is cleaned separately. Redis samples a small number of keys at a time and keeps going only while a large share of them turn out to be expired.
Why must the cleaner wait on a condition instead of sleeping?
close() needs to stop it now, not after the interval. A timed wait on a condition releases the lock and can be cut short by a signal; a sleep cannot (in Java you could interrupt it, but then every interrupt path must be right). After signalling, close() joins the thread so the caller knows the cleaner will never touch the map again. In C++ that join also matters for lifetime: destroying a std::thread that is still joinable calls std::terminate.
Should get extend an entry's lifetime?
That is the choice between expire after write (an absolute deadline, as here) and expire after access (a sliding deadline renewed on every read). Guava and Caffeine offer both. Sessions usually slide; data that must be refreshed from its source on schedule usually does not.
When a hot key expires, a hundred threads miss it at once and all reload it. How do you prevent that?
Load it once: the first thread to miss installs a future for the key, and the others wait on that future (single-flight); see the single-flight cache problem. Two refinements: refresh a hot entry in the background shortly before it expires, and add a little random jitter to ttls so many keys do not expire in the same instant.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

One map from key to (value, expiry time), guarded by one lock, and one background thread. Expiry is checked in two places: on every read (so a get is always correct) and periodically by the cleaner (so memory stays bounded). The invariant is get never returns an entry whose expiry time is at or before the current clock; expired entries may sit in the map for a while, which is why size() counts only live ones and storedEntries() exists to observe cleanup.

Why each line is there

  • Store the expiry time, not the ttl. One comparison with the clock answers "live or not", and an overwrite simply stores a new expiry time.
  • get removes what it finds expired. Lazy cleanup costs nothing extra: the lock is already held and the entry already found.
  • The cleaner holds the lock while it touches the map. A scan without the lock races with every put (in C++ that is undefined behavior, and a rehash can crash the scan), and deleting a key it saw expired can delete a fresh value that was put in between.
  • The cleaner waits on a condition, not a sleep, and checks closed under the lock. close() sets closed, signals, and joins, so it returns promptly and the cleaner never runs again afterwards.
  • Start the thread last. In Java, start the cleaner at the end of the constructor, after every field is set; in C++, declare the std::thread member last so it starts after the mutex and the map are constructed.
  • The clock is injected. Expiry can then be tested exactly at the boundary, with no sleeps, and the production clock can be a monotonic one.

Cost

get and put are O(1) under the lock. size() and each cleaner pass are O(n) here; an expiry-ordered index makes both proportional to the number of expired entries instead. The lock is shared by readers, writers and the cleaner, so a long sweep shows up as latency on every other call.

How to say it in the interview

Each entry stores its value and its expiry time, in a map behind one lock. Get checks the expiry against an injected monotonic clock and removes expired entries it finds, so reads are always correct. A cleaner thread bounds memory: it waits on a condition with the cleanup interval as a timeout, then removes expired entries under the lock. Close sets a closed flag under the lock, signals the condition and joins the thread, so shutdown is immediate and nothing touches the map afterwards. If the map is large, I would index entries by expiry time so the cleaner only touches what has expired.
