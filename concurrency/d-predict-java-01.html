Predict the output, Java set 1

Thirteen Java snippets: say what each prints, whether it can hang, and which monitor each line really takes.

LinkedIn has asked candidates for the output of a multithreaded snippet, Arista showed a Java snippet that turned out to deadlock, and VMware asked about class level versus object level locks. Read each snippet as the JVM would, not as its author hoped. Every program here was compiled and run on Java 21; where the output can vary, the question says "can" and every possible output among the options is marked correct.

13 questions, 20 minutes. Answers and explanations stay hidden until you submit or the clock runs out. Multi answer questions say so; pick every option that is true.

Which statement about the printed value is true?
Why. synchronized void inc() locks this, and the threads use different instances, c1 and c2. They therefore do not exclude each other while updating the one shared static count. Each increment reads, adds and writes, so updates can be lost; the local run printed 199692, while a schedule without lost updates can print 200000. An instance does not get a separate copy of a static field. Use static synchronized, one shared monitor such as Counter.class, or an AtomicInteger. Each invocation acquires only its own instance monitor and waits for no other resource, so these calls do not form a deadlock cycle.

Why. There is no single guaranteed complete output. main done is printed, but the worker is a daemon, so the JVM may terminate without waiting for it. If main finishes while the worker sleeps, only main done appears. Scheduling can instead let the worker finish before main prints; a probe delaying main produced worker done, worker finally, then main done. This runs on one thread. What does it print?
Why. On OpenJDK 21, list.remove(x) selects remove(Object) because x is an Integer, so it removes value 3. The iterator checks for structural modification in next(), while hasNext() compares its cursor with the current size. Removing 3 leaves both at 3; iteration ends without another next(), so the output is [1, 2, 4] and 4 is never visited. The local Java 21 run confirmed it. This exact behaviour is an implementation detail, not permission to modify an ArrayList during enhanced for iteration: fail-fast detection is best effort. Removing 2 instead reaches another next() and throws on this implementation. Use Iterator.remove() or list.removeIf(x -> x == 3).
Thread 1 calls transfer(a, b, 10) while thread 2 calls transfer(b, a, 20). Both accounts start at 100. What can happen? Select every possible outcome. Select all that apply
Why. If one transfer finishes before the other takes its first lock, both complete and a ends at 100 minus 10 plus 20, which is 110, and b at 90. But thread 1 can lock a while thread 2 locks b; then each waits for the other's monitor forever. synchronized has no timeout, and the JVM never breaks a deadlock: a thread dump reports "Found one Java-level deadlock" and that is all. With a 50 ms pause between the two locks the hang happened on every run. The fix is one global lock order (for example by account id), or tryLock with a timeout and back off. Arista asked candidates to find exactly this deadlock.
