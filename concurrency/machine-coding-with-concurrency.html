Machine coding rounds: thread-safe designs end to end

Build runnable concurrent services with explicit invariants, ownership, lifecycle rules and meaningful tests, using three worked designs.

Asked atUberRubrikMicrosoftAmazon
Before this:The monitor object patternLock granularity, contention and lock stripingThread-safe caches: LRU, TTL and single-flight

Machine coding at Uber and LLD with multithreading at Rubrik ask you to build a small, runnable service that stays correct under concurrent calls, often within 60 to 90 minutes in reported formats. Running code and a reason for every synchronization boundary matter together.

In plain words

Imagine setting up a small shop in 90 minutes. You put in the counters (the interfaces), the stock room (the state) and the till (the critical data). Then you decide which doors need a lock. The till and the stock room do. The display shelf of printed price cards does not: nobody changes it. A shop that padlocks every drawer is not safer; the staff spend the day queueing for keys, and two clerks each holding one key the other needs can stand there forever.

That is the craft of these rounds: working code first, a clear owner for every piece of shared state, and a lock exactly where an invariant needs one.

An older Uber India brief, quoted on Blind, put the goal plainly: show you can code a reusable library, it must compile and run, use interfaces and OOP, and the sample problem was a message broker in 90 minutes. An Uber Bangalore interviewer added the most useful warning: candidates "put synchronization everywhere". Microsoft (a message queueing system judged on multithreading and design patterns) and Amazon (a concurrent parking garage) run the same kind of round.

A plan for 90 minutes

  1. Minutes 0 to 10: requirements. The API, the entities, and the concurrency questions: which calls run at the same time, which results must be exact, what may be slightly stale, what blocks and for how long.
  2. Minutes 10 to 20: classes and a thread-safety plan. Sketch interfaces, models and services, then write one line per class saying how it is safe: immutable, confined to one thread, guarded by a named lock, or built on a concurrent collection.
  3. Minutes 20 to 65: the core, end to end. The happy path running first, then edge cases. Keep it compiling at every step.
  4. Minutes 65 to 80: test it. A main or tests that start many threads at once and check invariants. An Uber L4 candidate reported using CountDownLatch tests to exercise concurrent execution.
  5. Minutes 80 to 90: extensions. Scaling, cleanup, failure cases, and what you would change for production.

For Rubrik's 60 minutes, compress steps 1 and 2 to ten minutes in total, and make the demo a short main.

Where the locks go (and where they do not)

  • Find the invariants first. "An offset is never given to two messages", "a spot belongs to at most one vehicle", "the total equals the sum of the live per-key counts". Start with one lock guarding every variable in an invariant. If you split it across locks later, specify how an operation acquires all locks it needs.
  • Immutable objects need no lock. Safely publish value objects and keep their reachable state immutable. Java records and final fields are only shallowly immutable: a final list can still change. C++ value objects likewise need immutable contents and a lifetime that covers every reader.
  • Lock per entity, not per system. One lock per topic, per car, per seat, per key lets unrelated work proceed in parallel. Take one global lock only when an invariant really spans everything, as with the parking lot's free spots.
  • Several entities at once means an order. Booking two cars or moving a seat between users takes both locks in a fixed order, such as by id.
  • Never call out while holding a lock. Subscriber callbacks, listeners, I/O and other services are called after releasing it: the open call rule.
  • Concurrent collections for independent keys. A registry of topics or sessions is a ConcurrentHashMap with computeIfAbsent (a mutex-guarded map in C++). Compound invariants across keys still need a lock.
  • Write the rule down. One comment per class: "Thread-safe: guarded by lock", "Immutable", "Not thread-safe: owned by the dispatcher thread". It is the fastest way to show the interviewer you designed the concurrency rather than sprinkled it.

Design 1: a pub-sub broker

The classic Uber prompt: multiple publishers and subscribers on many topics, publishers decoupled from slow consumer processing, consumers reading in order. An in-memory append-only log is a useful starting point:

  • Each topic is an append-only list of messages with its own lock and a condition "grew". publish appends and returns the message's offset; assigning the offset and appending happen in one critical section, so offsets are dense, unique and in log order.
  • Consumers pull: poll(topic, fromOffset, max, timeout) returns what is available from that offset, or waits on the topic's condition until something arrives or the timeout passes. Each consumer keeps its own offset, so subscriber processing does not run on the publisher. Copying a batch still holds the topic lock briefly and can delay other operations.
  • The broker only maps names to topics. Each topic has its own data lock. The C++ registry still serialises name lookups briefly, and Java topic creation can contend inside the concurrent map.

Demo contract: names and messages are non-null, offsets are non-negative, batch size is positive, and timeouts are from zero to one day. The timeout bounds condition waiting after acquiring the topic lock, not registry lookup, lock acquisition, batch copying or scheduling delays. Empty polls time out without advancing the caller's offset. This compact sample has no retention or shutdown yet, and assumes memory allocation succeeds.

Linearization points: a successful publish takes effect at the append under the topic lock; a successful poll observes a log snapshot while holding that same lock. A timeout observes its predicate still false after the waiting budget expires. No reader can observe a message without its assigned position.

Push instead of pull? A dispatcher reads the log and invokes its subscriber outside the topic lock. Bound its queue and choose a full-queue policy: block, drop, disconnect or spill to storage. You cannot guarantee bounded storage, lossless delivery and publishers that never wait when a consumer can remain slow forever. Calling callbacks after unlocking also needs ordered dispatch: two publishers can otherwise deliver offset 1 before offset 0.

Consumer groups? A shared committed offset alone does not prevent two group members processing the same message. Add exclusive partition ownership or explicit in-flight claims, and only commit the contiguous processed prefix. For example, completing offset 11 before 10 must not advance the committed position past unfinished work. Replaying after a crash requires idempotent processing or a transaction with the effect.

Retention and shutdown? Track a base offset when removing a log prefix so offsets never restart at zero. Define whether a lagging consumer gets an offset-out-of-range error or skips expired data. A close flag under the topic lock rejects publishes, wakes all pollers and lets them drain retained data before reporting closed; join users before destroying the C++ broker. Java interruption must propagate to the caller.

Why signalAll? Every waiter independently checks its requested offset. Waking one whose offset is still in the future can strand another whose data is ready. All waiters recheck the predicate; a notification is not a reserved message. Java propagates cancellation even while acquiring the topic lock; C++ needs an explicit cancellation or close protocol.

Design 2: reservations and the 1-D parking lot

Rubrik asked this one twice in 2026, once framed as a memory allocation problem: a lot of N spots in a line, a car takes one spot, a truck two adjacent spots, park and leave are called concurrently. The invariant spans the whole array ("free spots" and "which vehicle holds which spots"), and a truck needs two neighbours to be free at the same moment, which is a check then act across two spots. One lock around the search and the take makes it trivially correct, and the O(N) search is a reasonable starting point for a small lot; measure before adding stripes.

The contract uses positive vehicle ids because zero denotes a free spot; a repeated live id is rejected, and leaving an absent id returns false. Java returns a defensive array copy, while C++ returns a value. The stress test uses atomic ownership stamps and disjoint ids to detect overlapping owners on exercised schedules. It releases the test stamp before calling leave, so a valid next owner cannot race a late test cleanup. A clean run is evidence, not a proof; also test exhaustion, duplicate ids and mutation of returned collections. The number of successful random parkings varies between runs.

When the lot is huge, stripe it: S stripes of consecutive spots, each with a lock. A car locks one stripe. A truck whose two spots straddle a stripe boundary takes both stripes' locks in ascending stripe order, which rules out deadlock. The vehicle-to-spots map also needs protection after striping: use a separate registry protocol with one global lock order, or shard it by vehicle id. Two calls using the same id must not reserve different stripes. The same reasoning covers reservations in general: a car rental or a meeting room keeps one lock per resource (a car, a room) guarding that resource's bookings, booking checks for overlap and inserts under that lock, and booking two resources at once takes their locks in id order. Seat booking adds holds that expire: see the seat booking problem and design cases.

Design 3: Uber's expiring counter

The L5A prompt: put_element(k), get_element_count(k), get_total_elements(), and every element expires t seconds after it was put. The candidate expected a multithreaded problem and was marked down on production behaviour: the interviewer pushed for purging stale timestamps on read. A compact exact-count design, with explicit limits:

  • Keep every live element in a global queue of (time, key), oldest first, and per key a queue of times, oldest first.
  • Every call first purges: while the oldest global element has expired, pop it and pop the front of its key's queue (the same element, since both are in time order), and drop a key whose queue becomes empty. After a call purges, stored entries correspond to live elements at its sampled time and counts are exact for that instant. When idle, expired entries remain until the next call.
  • Each element is pushed once and popped once, so purging is O(1) amortized per element.
  • One lock guards both structures, because the total and the per-key counts form one invariant. Read a monotonic clock under the lock, so insertion order matches timestamp order. Reading a wall clock under a lock does not prevent it moving backwards.
  • The clock is a parameter: an injectable clock lets the test move time without sleeping.

The injected clock returns non-negative elapsed ticks in the TTL's unit, never moves backwards, and stays within the signed 64-bit range. A production wrapper can measure elapsed time from an origin using System.nanoTime() or std::chrono::steady_clock; the sample rejects a broken clock. This clock is trusted, fast and non-reentrant because it is invoked under the lock. TTL must be positive. These compact multi-container updates assume memory allocation succeeds and do not implement recovery from metadata allocation failure.

Each count is linearizable at its clock sample under the lock: purging removes exactly the elements expired at that instant, and no writer changes either queue during the calculation. Separate calls to count and total are separate snapshots; provide one snapshot method if a caller needs them to agree at one instant.

The last read removes all expired entries and empty keys. Lazy cleanup does not run while idle, and collection backing storage may retain its high-water capacity. For a strict memory bound, add admission limits and periodic cleanup under the same lock, with an explicit shutdown for the cleanup worker. One call after a long idle period can purge O(E) entries and hold the lock for a long time even though work is O(1) amortized per element.

Many puts per second per key? Per-second count buckets reduce entry count, but are exact only if the time contract is quantised to those seconds. Otherwise events at opposite ends of a bucket expire at different instants and boundary counts are approximate. One lock is a bottleneck? Shard by key. An exact global total needs every shard locked in a fixed order and purged against one sampled time. Adding individually locked shard counts gives a weak snapshot; reading mutable shard structures without locks is unsafe.

Testing it in the round

A start gate makes workers eligible to run together, not literally simultaneous. Use it to increase contention, collect worker failures, require completion within a deadline, and check a precise invariant such as "exactly 10 of 50 distinct cars parked in an initially empty lot of 10, with no departures". Stress tests and ThreadSanitizer detect some bugs; neither proves all interleavings correct. Explain the lock invariant and each operation's linearization point as well.

Worked example: a thread-safety plan for a car rental service

Uber's L5A loop asked for a car reservation service in the style of Avis or Hertz. Before coding, write the plan as a table. It takes three minutes and answers half the interviewer's concurrency questions in advance.

ClassStateThread-safety rule
Car, Reservation, IntervalIds, type, timesImmutable records: no lock
CarCalendar (one per car)A sorted map of booked intervalsGuarded by its own lock; book checks overlap and inserts in one critical section
InventoryMap from car id to calendar, list of cars per typeBuild once, then safely publish before readers start; read without locks. Dynamic additions must update both indexes atomically, for example by publishing one new immutable inventory snapshot
ReservationServiceNo state of its ownreserveAnyCar(type, interval) tries each car's calendar in turn, taking one lock at a time, and stops at the first success, so it never holds two locks

Then say what you deliberately did not lock: the immutable records and the startup-only inventory. That is the answer to "where are your locks and why", and it is the opposite of synchronization everywhere.

Common mistakes

  • No running code at the end. A design on paper scores below a smaller design that runs with a demo, in both companies' rounds.
  • Synchronization everywhere. synchronized on every method of every class adds contention, invites lock order deadlocks between objects, and shows no reasoning. Lock per invariant.
  • Calling subscribers or listeners under a lock. A slow or re-entrant callback stalls publishers or deadlocks the broker.
  • Check-then-act across two calls. if (lot.isFree(i)) lot.take(i) is two critical sections with a gap between them; put the check and the take in one method under one lock.
  • No cleanup. Expired entries, finished sessions and empty keys that stay in maps forever are a memory leak that interviewers now probe for explicitly.
  • Sleeping in tests. Thread.sleep(100) to "let the other thread finish" makes tests slow and flaky. Use joins, latches and injectable clocks.
  • Returning internal collections. Handing out the live list from inside a locked object lets callers read it without the lock. Return a copy or an immutable snapshot. An unmodifiable view backed by a mutable collection still changes and is not a snapshot.

In the interview

Open with requirements and the concurrency questions, then the class sketch with one thread-safety line per class, then code. Narrate decisions as you make them; the interviewer is grading the reasoning as much as the result.

Messages, reservations and vehicles are immutable records, so they need no locking. Each topic, car or lot owns its mutable state behind its own lock, and every invariant lives entirely inside one of those objects, so each operation takes exactly one lock, and the rare operation that spans two takes them in id order. I never call out to subscribers or other services while holding a lock. And I will test it with a gate that releases fifty threads to contend against one resource and checks the invariant afterwards.

Follow ups to expect: "how does this scale to millions of topics or keys?" (shard by key, one lock per shard, or one single-threaded owner per partition), "a consumer is slow" (pull model, or a bounded per-subscriber queue that drops or blocks by policy), "what if two of these services run on different machines?" (the locks no longer help; use the database's constraints, conditional updates or a partition owner, see ordering by ownership), and "show me it is correct under concurrency" (the invariant argument plus gated tests).

Senior depth

  • Keyed serialization. Instead of locks, route all work for a key to one worker thread (hash the key over N single-threaded executors). Each key's operations run in the order accepted by its worker queue; keys mapped to different workers can run in parallel. Reads must go through that owner too, or use safely published snapshots. An Uber candidate proposed this "keyed executor" for a thread-safe leaderboard. It trades lock contention for queueing delay on hot keys.
  • Read-mostly state. When reads vastly outnumber writes (a catalogue, a routing table), publish immutable snapshots and rebuild on write. Java can use a volatile reference. In C++, std::atomic_load and std::atomic_store on a std::shared_ptr can publish and retain snapshot lifetime; all accesses to that pointer use the atomic API. Readers avoid an application mutex, but shared-pointer atomic operations need not be lock-free. See copy-on-write and snapshots.
  • Bounded everything. Every queue in a machine coding answer should have a capacity and a policy for when it is full, and every blocking API needs a defined deadline, cancellation or shutdown policy. Saying so unprompted reads as production experience.
  • Retries need idempotency even in one process. A lock prevents conflicting state changes, but a retry can still make a second booking. Store a request id and its result atomically with the booking; across machines, use durable idempotency records and conditional writes; see idempotency and exactly-once effects.

Key takeaways

  • Machine coding and LLD-with-concurrency rounds grade running code, clean structure and correctness under many threads, in that order of visibility.
  • Write a thread-safety rule per class: immutable, confined, guarded by a named lock, or a concurrent collection.
  • One lock per invariant, per entity where possible; fixed order when an operation spans two; never call out while holding one.
  • Production behaviour is part of correctness: purge expired data, drop empty keys, bound queues, time out waits.
  • Combine a lock and lifetime argument with gated tests, distinct ids, deadline checks and injected clocks.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A push-based broker calls every subscriber's onMessage callback inside the topic's lock. What is the risk?
Why. Callbacks are foreign code: their duration and their calls back into the broker are outside your control. Under your lock, a slow subscriber stalls the topic and a re-entrant call can deadlock (or, with a reentrant lock, see half-updated state). Copy what you need under the lock and deliver after releasing it, or give each subscriber its own queue and dispatcher thread.
An initially empty topic has two publishers. A calls publish("A") once and stores its returned offset; B does the same for "B". Main joins both and prints A's offset followed by B's. Which outputs can the locked implementation produce?
Why. The append and its zero-based offset are assigned in one critical section. Whichever publisher acquires the lock first gets 0, and the other gets 1. Starting A first would not guarantee lock acquisition order. Duplicates violate the invariant, and starting at 1 contradicts the empty log's zero-based indexing. The result slots are read only after joining their writers.
A huge parking lot is split into lock stripes of 100 spots each. A truck needs spots 199 and 200, which fall in stripes 1 and 2. How should park lock?
Why. The truck's check-then-take spans two stripes, so it needs both locks. Taking them in ascending stripe order everywhere means no two trucks can each hold one stripe and wait for the other's. Locking only one stripe lets a car in the other stripe take spot 200 at the same moment.
Uber's expiring counter is called by many threads. Assuming a monotonic clock, why does put read the clock while holding the lock rather than before taking it?
Why. Purging from the front assumes the queues are sorted by time. Reading the clock inside the critical section ties the time stamp to the insertion order. With the clock read outside, thread A reads 7, thread B reads 8, B inserts first, and the queue holds 8 then 7, so an expired 7 can sit behind a live 8.
Which belong in a strong machine coding answer with concurrency? Select all that apply.Select all that apply
Why. Stating the rule per class shows designed concurrency, the start gate test exercises contention, and cleanup is the production behaviour Uber has graded on. Blanket synchronization is the reported anti-pattern, and sleeps make tests slow and still flaky; use joins, latches and injectable clocks.
Java onlyWhy is topics.computeIfAbsent(name, t -> new Topic()) suitable for this registry, which never removes topics?
Why. With get then put, two threads can both see "absent", both create a topic, and one overwrites the other, so messages land in a topic nobody reads. putIfAbsent with a pre-built object also works but may create throwaway topics; here computeIfAbsent avoids redundant construction while a successfully installed topic remains mapped. The factory can run again if the mapping is removed, the factory throws, or it returns null. Keep the factory short: other updates can block while it runs, including colliding keys.
C++ onlyThe C++ Broker returns Topic& from get() after releasing the registry mutex. Why is that reference safe to use?
Why. An unordered_map rehash invalidates iterators but not references to its elements, and the heap-allocated Topic behind each unique_ptr never moves at all. The real requirement is the lifetime: topics must not be erased and all users must finish before the broker is destroyed. If topics could be deleted, you would hand out std::shared_ptr instead.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
Uber asks for a meeting room service: init(rooms), book(start, end) returns any free room or none, cancel(bookingId). Many threads call it. Give the thread-safety design, and say what changes at 10,000 concurrent requests.
Model answer

Each room has a calendar, a sorted map from start time to booking, guarded by that room's own lock. Require start < end and use half-open intervals [start, end): the preceding booking must end at or before start, and the next booking must start at or after end. book tries rooms one at a time: lock a room, find the last booking starting strictly before start and the first starting at or after start to check for overlap, insert if free, unlock, return; if not free, move to the next room. It never holds two locks, so it cannot deadlock, and two bookings for different rooms run in parallel. Use a unique booking id that encodes its room, so cancellation locates the room without a second mutable index; under that room's lock, verify and remove the id, making repeated cancellation harmless. If a separate id index is required, publish and remove its entries consistently with the calendar under a documented locking protocol. Bookings and intervals are immutable records.

A failed scan with concurrent cancellation is only a best-effort "none found": availability can move between rooms during the scan, with no instant when all rooms are unavailable. If "none" must mean a linearizable global lack of space, recheck all rooms while holding their locks in id order, or use a global booking coordinator. Per-room exclusion alone guarantees no double booking, not that stronger failure result.

At 10,000 concurrent requests the bottleneck is everyone trying room 1 first and queueing on its lock. I would start the scan at a different room per request (a random or hashed start), or keep a shared index of rooms with free time and accept that it is a hint that the room's own lock re-checks. If a single process is not enough, partition rooms across processes and route by room, and make the room's calendar the only writer for its bookings, so each partition stays single-owner.

Write code
Write a test for the parking lot that releases 50 threads through one start gate, each parking one car with a distinct id, in a lot of 10 spots, and returns how many parked. What must the result be?
Model answer

With 50 distinct positive ids, an initially empty lot of 10 spots, no departures and successful worker completion, exactly 10 must park. More than 10 means a spot was handed out twice (a check-then-act gap); fewer means a lost update or a broken search. Run it many times, and in C++ under ThreadSanitizer, because one passing run proves little. Use a process-level timeout for C++ joins; never detach workers that still reference a local lot. In C++17, replace std::latch with a mutex, condition variable and an open flag checked by a wait predicate.

Explain
The interviewer looks at your code and says: "You have synchronized on every method of every class. Defend it or fix it."
Model answer

I would fix it, and explain the fix in terms of invariants. The value classes (messages, reservations, vehicles) are immutable, so I would make them records or final-field classes and remove their locks entirely. The stateless service class does not need a lock either; it only delegates. The classes that own mutable state keep exactly one lock each, and I would check that every invariant lives inside one such object, so each operation takes one lock.

Then I would look for the two dangers that blanket synchronization hides: a method that holds one object's lock while calling into another synchronized object, which can deadlock when another path calls in the opposite order, and a lock held while calling a listener or doing I/O, which stalls everyone. I would move those calls outside the lock, and where an operation genuinely needs two objects, take both locks in a fixed order. The result has fewer locks, shorter critical sections and a sentence of justification for each remaining lock, which is what the interviewer is really asking for.

Out loudabout 90 s
"You have ninety minutes to build a concurrent reservation service. How do you organise the design and demonstrate that it works?"
What a strong answer covers
  • Define booking, cancellation, interval and failure semantics before choosing locks
  • Assign immutable values and per-resource mutable state clear ownership
  • Make overlap checking and insertion one atomic transition; order multi-resource locks
  • Address retries and the semantics of an unsuccessful scan during cancellations
  • Combine invariant reasoning with gated tests, deadlines and worker-error checks
How a senior would say it
I would get a small end-to-end service running, with one clear concurrency rule for every class. First I would define the API: valid half-open intervals, booking identifiers, cancellation behaviour and what a failed search promises. Messages and reservations would be immutable values, safely published. Each room would own its calendar behind one lock. Booking checks the neighbouring intervals and inserts the reservation in that same critical section, so two callers cannot both reserve an overlapping interval in one room. Cancellation verifies the booking id under the same lock. If an operation spans rooms, I acquire their locks in room-id order and commit all changes together. I would keep callbacks and external work outside those locks. A scan taking one room lock at a time prevents double booking, but with concurrent cancellations a failed scan may miss moving availability. If the contract requires an exact global failure result, I need a coordinated recheck. Retries need a request id stored with the result; a mutex alone does not deduplicate them. Finally I would explain the invariant and linearization points, then test with gated concurrent callers, distinct ids, bounded completion and captured worker exceptions. I would check returned bookings for overlaps and test cancellation and boundary times separately.

Likely follow up: How would you reserve two rooms atomically while unrelated single-room bookings continue?

Out loudabout 90 s
"Design a pub-sub broker where one slow subscriber does not stall everyone. What guarantees can you actually make?"
What a strong answer covers
  • Use a per-topic ordered log with atomic append and offset assignment
  • Separate subscriber processing from publication using pull or ordered dispatch
  • State the bounded-storage, lossless-delivery and nonblocking-publication trade-off
  • Define retention offsets and contiguous commits for consumer groups
  • Describe predicate waits, close wakeups and lifetime requirements
How a senior would say it
I would separate publication from subscriber processing with a per-topic log. A topic lock protects appending a message and assigning its offset as one operation, so offsets are unique, dense and ordered. Each subscriber tracks its own position and pulls a bounded batch. Copying that batch still briefly holds the topic lock, but the subscriber's application code runs outside it. For push delivery, I would use ordered dispatch rather than invoke callbacks directly from competing publishers. I would then clarify the overload contract. With a subscriber that can stop forever, finite storage cannot preserve every message while allowing publishers to run indefinitely without waiting. We must choose blocking, dropping, disconnecting the subscriber or spilling to storage. Retention needs a base offset and a defined response when a consumer asks for data already removed. Consumer groups also need ownership or claims; one shared offset does not stop duplicate processing. Commits advance only over the contiguous completed prefix, so finishing message eleven cannot skip unfinished message ten. Pollers wait in a predicate loop and recheck after notification. Closing marks the topic closed, rejects publication and wakes every waiter to drain or exit. Finally, all users must finish before the broker and its condition variables are destroyed.

Likely follow up: What happens if a consumer finishes a side effect and crashes before committing its offset?

Out loudabout 60 s
"Your expiring counter returns the right counts, but memory stays high after traffic stops. What do you investigate?"
What a strong answer covers
  • Separate logical expiration, lazy removal and retained collection capacity
  • Use monotonic time sampled under the lock and purge empty keys
  • Add bounded admission or scheduled cleanup with shutdown when idle reclamation is required
  • Explain purge latency and the accuracy trade-off of time buckets
How a senior would say it
I would distinguish logical expiry from actual removal and from retained collection capacity. This counter purges on calls, so an idle instance can still contain expired entries until the next operation. Even after removal, a collection may retain its backing storage. I would verify that reads purge expired elements and remove empty keys, using a monotonic clock sampled under the same lock as insertion. If the requirement is reclamation while idle, I would add scheduled cleanup under that lock, with explicit worker shutdown, and bound admission for a strict capacity limit. I would also measure the first call after a long pause: it may remove many entries while holding the lock, despite constant amortized work per element. Time buckets reduce entry count, but are exact only when the contract quantises timestamps; otherwise bucket boundaries introduce approximation. Tests should advance an injected clock through exact expiry boundaries.

Likely follow up: How would you get an exact total after sharding this counter by key?
