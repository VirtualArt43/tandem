FizzBuzz multithreaded

Ordering puzzlesmedium25 minLeetCode 1195

Four threads share one counter, and the owner of the next number changes in an irregular pattern. The middle is easy; the end is where people fail, because a thread with nothing left to print must still notice that the game is over and return.

The task

One FizzBuzz object is shared by four threads. Together they print the numbers from 1 to n, FizzBuzz style, in order:

  • Thread A calls fizz(), which prints fizz for numbers divisible by 3 but not by 5.
  • Thread B calls buzz(), which prints buzz for numbers divisible by 5 but not by 3.
  • Thread C calls fizzbuzz(), which prints fizzbuzz for numbers divisible by 15.
  • Thread D calls number(), which prints every other number itself.

For n = 15 the output is 1, 2, fizz, 4, buzz, fizz, 7, 8, fizz, buzz, 11, fizz, 13, 14, fizzbuzz. All four methods must return once the last number is printed, including a method that had nothing to print at all (for n = 2, fizz(), buzz() and fizzbuzz() print nothing and must still return).

Rules: 1 <= n <= 100. Exactly one thread calls each method once, in any start order. Invoke each supplied callback on that method's calling thread, exactly once for each number it owns. Finish one callback before starting the next, since a callback may take time to print. Callbacks eventually return normally and do not call back into FizzBuzz; callback failures and Java interruption are discussion follow ups, outside the required game.

A waiting thread must block, not spin. No sleep to arrange the order. A method may return after its own final turn, but all four must return after the game finishes. Each object serves one game with its own counter and bound; different objects may run concurrently and must progress independently. In C++, ThreadSanitizer must stay quiet.

What the tests check

  • Delay each role in turn in a game with n = 30. Output must stop exactly before that role's first number: at 2 before fizz, 4 before buzz, 14 before fizzbuzz, and before any output for number. The other three methods still have work and must wait. Starting the missing role must finish the exact sequence.
  • Waiting must block even after printing has begun. Java samples worker states five times; C++ observes process CPU time and context switches during a 200 ms idle window. These checks flag sustained spinning.
  • Hold callbacks at positions 2, 3, 5 and 15 in separate games with n = 16. No subsequent callback may start until the held callback returns. Every callback must run on its method's calling thread, and callback executions must never overlap.
  • Pause a game with n = 31 before its first fizz, then finish a separate game with n = 16. The first game's output must remain 1, 2 until its missing roles start, then finish with its original counter and bound.
  • The exact sequence for n = 1, 2, 3, 5, 14, 15, 16, 31 and 100, with all 24 start orders of the four threads (twice each, once for n = 100), rotating through three start styles: one after another, 1 ms apart, and released through a common gate. These 408 rounds include roles with no output, final fizz at 3, final buzz at 5 and 100, final fizzbuzz at 15, and final plain numbers at 14 and 16.
  • Every method returns, including a role with no turns. Completion waits are bounded at 1 s in Java and 1.5 s in C++; whole-suite watchdogs stop failures after 3.5 s and 6 s respectively.
  • No exceptions, and in C++ no ThreadSanitizer report.

Inputs and launch orders are repeatable; the operating system chooses actual interleavings. Callback gates force the important pauses. Short observation windows and state or CPU samples detect common blocking mistakes but cannot prove the absence of spinning under every possible schedule.

Taught in: Making threads take turns

Open them one at a time. Each one gives away a little more.

Keep one shared counter, current, the next number to deal with. Each thread waits until current is a number it owns, prints, adds one, and wakes the others. What should a thread do when current passes n?
Put the end into the wait condition: wait while current <= n and the number is not yours. After waking, if current > n, return. Otherwise print, add one to current, and wake everyone (notify versus notifyAll), since any of the other three may own the next number.
All four methods can share one private loop that takes an "is this number mine?" test and a print action. In Java, IntPredicate and IntConsumer; in C++, two lambdas. Classify with 15 first: a multiple of 15 belongs to fizzbuzz, not to fizz or buzz.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why must the end test sit inside the wait condition?
When the last number is printed, the other threads are asleep waiting for a number of their own kind. If their condition is only "is current mine?", then n + 1 is not theirs and they sleep forever, and whoever joins them hangs. The thread that printed n wakes everyone, and the condition current > n || mine(current) lets each one wake up, see the game is over and return.
notifyAll can wake three threads when only one owns the next number. Can you target that owner?
Yes. Give each thread its own condition (or semaphore). After printing k, compute who owns k + 1 and signal only that thread; after printing n, signal all four so they can leave, or design the loops so nobody is waiting at the end. At most one waiting role is signalled per advance instead of broadcasting to up to three. Actual wakeups depend on which roles are already waiting.
Each thread can work out its own numbers in advance. Does that help?
A lot. fizz can loop over 3, 6, 9 and so on, skipping multiples of 15, and wait for current == k before each print. Its loop ends by itself after the last number it owns, so there is no end-of-game check and no thread is left waiting. Combined with one semaphore per thread and a hand-off to the owner of k + 1, every wakeup goes to the right thread (see the notes).
Why not check current without the lock, since only one thread changes it at a time?
In the shared-counter solution, unsynchronized reads conflict with writes and create a data race. Java volatile can provide visibility; C++ needs std::atomic, not volatile. Neither alone orders whole callback executions: advancing an atomic counter before a slow callback finishes lets the next thread print too soon. Protect the check, callback and advance together, or use an explicit hand-off after the callback returns.
Why must a wait recheck the ownership predicate?
A wakeup is permission to check, not permission to print. With one shared condition, all three other roles can wake after an advance, but at most one owns the next number. Use while around Java await or wait, or a predicate with C++ wait; also include termination in that predicate.
How would you have caught the hang at the end in your own tests?
Join every thread with a timeout, and use values of n where some thread has nothing to print (1, 2, 4, 14). A test that only compares output misses a solution that prints everything correctly and then leaves a thread blocked forever. This harness checks both exact output and completion of every method.
What if a callback throws or a Java worker is interrupted?
Define a cancellation policy first. One useful extension stores a terminal failure under the same lock, wakes every waiter, and makes the remaining methods exit without printing further numbers. Preserve the original callback failure or propagate InterruptedException to the affected caller, and release the lock in finally or through RAII. Simply leaving one worker strands every later turn it owns. The supplied reference assumes callbacks succeed and workers are not interrupted.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

One counter, current, runs from 1 to n + 1 under one lock. All four threads run the same loop with a different ownership test: wait until the game is over or current is mine; if over, return; else print, advance, wake everyone. The invariant is everything below current has been printed in order, and exactly one thread owns current while current <= n. The value n + 1 is the "game over" state, and because it is part of every wait condition, every thread leaves.

Why each line is there

  • One lock around current and the callback. Several threads read the counter and one at a time writes it. In this reference, the check, the complete callback and the advance share one critical section. A targeted hand-off can enforce the same ordering without holding a lock through the callback.
  • The end in the wait condition. current > n || mine(current) is the whole trick. Without the first half, the threads that own nothing past n sleep forever.
  • signalAll (notify_all). The next number may belong to any of the other three, and all of them wait on the same condition. signal could wake the wrong one and the wakeup would be lost.
  • 15 before 3 and 5. The ownership tests are disjoint: fizz is "divisible by 3 and not by 5", and so on. Overlapping tests let the wrong role claim a multiple of 15, even when locking prevents duplicate prints.

There are O(n) callback invocations and O(1) shared state for four fixed roles. Broadcasting wakes at most three other roles per advance. Time spent inside callbacks or waiting for scheduling is additional; neither version promises a wall-clock completion bound without those assumptions.

Pitfalls

  • Forgetting the end. The classic failure: the output is perfect and then the program never exits, because fizz is still waiting for a multiple of 3 that will never come. The tests join every thread with a timeout.
  • notify with one shared condition. Wakes one of three possible owners, often the wrong one.
  • Overlapping ownership. Testing k % 3 == 0 for fizz without excluding 15 lets fizz and fizzbuzz both claim 15.
  • Reading current outside the lock. A data race, and a check then act between the read and the print.

How to say it in the interview

I'll keep one counter, current, under one lock, and run the same loop in all four threads with a different ownership test. Each waits until current is past n or belongs to it; past n it returns, otherwise it prints, advances and signals all, because any of the other three may own the next number. Putting the end of the game into the wait condition is what lets the threads with nothing left to print exit. If wakeups matter, each thread can loop over its own numbers with its own semaphore, and whoever prints k hands the turn straight to the owner of k plus one.
