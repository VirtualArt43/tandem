Memory and object layout: sizeof, alignment, new and delete

Measure object size, explain padding and virtual dispatch overhead, match allocation with destruction, and connect storage layout to concurrent allocators.

Asked atRubrik
Before this:Object lifetime, the stack and the heapClasses, constructors, destructors and RAII

A struct's fields can add up to six bytes while the struct occupies twelve. Understanding those missing bytes, and the difference between reserving storage and constructing an object, lets you explain memory costs and build the storage underneath a concurrent queue.

In plain words

Imagine a warehouse with numbered floor tiles. A small crate fits anywhere, but a loading machine needs every large crate to start at a tile numbered in multiples of four. Workers leave gaps to obey that rule, and rearranging the crates can save space.

Reserving a patch of floor does not assemble the machine that will stand there. Likewise, dismantling that machine does not return the floor to the warehouse. Storage and the object occupying it are separate things.

Why this matters for concurrency

A queue can reserve a buffer once, then construct and destroy elements inside individual slots. Separately, two threads can update different objects safely yet run slowly because those objects occupy the same cache line. Correct lifetime and efficient placement are different requirements.

This is also preparation for allocator rounds: a 2025 Rubrik candidate report describes alloc(size) and free(index) over a fixed arena, with the interviewer steering toward buddy allocation. The full algorithms belong in memory allocators; here you learn what a valid allocation must provide.

sizeof measures an object, not everything it owns

sizeof(T) and sizeof expression return a compile-time std::size_t count of C++ bytes. A byte is sizeof(char), always 1; its bit count is CHAR_BIT from <climits>, normally 8 on our targets. The operand is not evaluated, so even sizeof(function()) makes no call.

  • An array's size includes every element. A pointer's size measures the pointer alone. A function parameter written int values[] is adjusted to a pointer, so it has lost the array extent.
  • sizeof(std::vector<int>) includes the vector's own bookkeeping, not its allocated elements. Changing the length does not change that sizeof. Container behavior is covered in STL containers and the STL for coding rounds.
  • sizeof(reference) gives the referred-to type's size. It does not expose how a reference is implemented. sizeof(*base_pointer) uses the static type, even if the object is derived.
  • You cannot apply sizeof to void, an incomplete class, a function type or a bit-field in standard C++. Variable-length arrays are a compiler extension, not C++20.

The call count is 0 and the element count is 4 on every conforming implementation. The byte counts are measurements of your compiler and target, not universal constants. sizeof also excludes allocator metadata outside the object.

Alignment, padding and the stride of an array

Alignment restricts the addresses at which an object may begin. alignof(T) reports that requirement in bytes. For a straightforward struct, the compiler inserts padding before members to satisfy their alignment, and often at the end so the next element in an array is aligned too.

For ordinary complete object types, sizeof(T) is a multiple of alignof(T). Array elements are contiguous with a stride of sizeof(T); there is no extra gap between elements beyond the padding already counted inside that size. The exact member offsets and alignment are implementation choices.

Worked example: shrink twelve bytes to eight

The application binary interface (ABI) specifies how compiled code represents and passes objects on a target. Assume char has size and alignment 1, int has size and alignment 4, and the ABI uses the usual minimal padding. Compare char tag; int count; char ready; with int count; char tag; char ready;.

LayoutByte offsetsSize and alignment
Originaltag: 0; gap: 1 to 3; count: 4 to 7; ready: 8; tail gap: 9 to 11Size 12, alignment 4
Reorderedcount: 0 to 3; tag: 4; ready: 5; tail gap: 6 to 7Size 8, alignment 4

The payload is six bytes in both. Reordering saves four bytes per object, or 4,000,000 bytes for a million elements, excluding allocation overhead. Grouping members by decreasing alignment is a useful heuristic, but measure the result.

offsetof(T, member) from <cstddef> gives the member's byte offset. These are standard-layout types, a language category with restricted inheritance and member layout; use offsetof on such types for portable results. It is only conditionally supported for other class types.

Reordering changes the binary interface, aggregate initialization positions and member construction order. Check dependencies before changing declarations. Avoid packing pragmas as a general optimization: they are nonstandard and can produce misaligned members, especially dangerous for atomics.

Padding bytes are not field values. Do not use memcmp as struct equality or dump a struct as a portable file format. Equal fields can coexist with different padding; sizes, byte order and layout can differ across targets. Serialize the named fields deliberately.

Standard layout and byte-copy safety are separate properties. For distinct, complete, live objects of the same trivially copyable type, std::memcpy from <cstring> can copy an initialized source's representation into the destination and preserve its value. Check std::is_trivially_copyable_v<T> from <type_traits>; standard layout alone is insufficient, and copying the bytes of a std::string or smart pointer is not an ownership-preserving copy. Even a trivially copyable struct is not automatically a portable wire format. These are the C++20 object-representation guarantees.

alignas requests a boundary, not synchronization

struct alignas(64) Slot { long count; }; requests at least 64-byte alignment for the type. Its size is rounded to preserve that alignment in arrays. alignas(T) requests T's alignment; if several specifiers appear, their strongest nonzero requirement wins and must not weaken the natural alignment. Unsupported extended alignments are rejected; alignas(0) has no effect.

Applying alignas to a variable changes that object's placement, not the underlying type's alignof. Aligning an array's beginning does not separate its elements: alignas(64) long counts[2] still has adjacent long elements. Align the element type when you need a padded stride.

Here the integer address conversion is a target-level diagnostic; the cast itself is covered in types, casts and initialization. Since C++17, normal new expressions support over-aligned types through alignment-aware allocation; custom allocation functions must honor the requirement too.

Why a smaller struct can be slower

False sharing happens when threads on different cores access independent memory locations in one cache line and at least one thread writes. This can be race-free and still cause repeated coherence traffic, including when one field has a writer and a neighbouring field has only readers, as the Linux kernel's false-sharing guide illustrates. Making two hot per-thread counters adjacent saves bytes but can worsen this traffic; separating them consumes memory and can reduce it.

The sample's 64 is a layout exercise, not a promise about this Mac's cache line. C++17 offers std::hardware_destructive_interference_size in <new> when the library supports it, advertised by __cpp_lib_hardware_interference_size; otherwise use a documented target choice and benchmark. Neither padding nor alignment makes concurrent writes to the same plain counter safe. Continue with CPU caches and false sharing and counters at scale.

Different member names do not always mean different memory locations. In struct Flags { unsigned ready : 1; unsigned done : 1; };, the adjacent nonzero-width bit-fields form one memory location. Two threads writing one field each without synchronization have a data race, not merely false sharing. Separate ordinary scalar members are distinct memory locations; read and write only your own member, keep the containing object alive, and synchronize any access that conflicts. The C++20 memory-location rules make this distinction explicit.

What a virtual function costs in object size

A class with virtual functions is polymorphic. Common ABIs place a hidden vtable pointer in each simple polymorphic object, pointing to shared dispatch metadata. On an ordinary 64-bit pointer ABI that pointer is typically eight bytes; alignment can make the total size increase larger. The standard does not require this representation.

Adding five virtual methods does not add five pointers per object; their entries belong to the shared table. Multiple inheritance can require more than one dispatch pointer, and a derived class may reuse a base's pointer. Static members and ordinary member function bodies do not occupy a slot in every object. Inheritance and virtual functions covers dispatch and deletion through a base pointer.

For a polymorphic base intended to own derived objects, provide a virtual destructor. The default deleter of std::unique_ptr<Base> needs the same safe base-deletion contract as ordinary scalar delete. A virtual destructor still does not permit deleting a derived array through a base pointer.

Typical results on this Mac are plain=4 virtual=16 more-virtual=16. The twelve-byte increase includes an eight-byte pointer and four bytes of padding. Treat this as an ABI observation, not a portable size equation; the Itanium ABI layout rules explain this common implementation family.

Empty base optimization lets an empty base subobject occupy no additional space in suitable layouts. A complete empty object still has nonzero sizeof, usually 1, so array elements have distinct addresses, but WithEmptyBase commonly occupies only its int's four bytes. This helps store stateless policies or deleters; same-type address constraints and inheritance layout rules limit when it works. C++20 [[no_unique_address]] allows similar overlap for eligible members, without guaranteeing that every compiler will eliminate their space.

new and delete combine two jobs

A new-expression, such as new Job("queued"), obtains suitably aligned storage through an allocation function and initializes the object there. delete p runs the destructor and then a deallocation function. Calling operator new directly does only the storage step; it does not run a constructor.

std::malloc and std::free are C storage APIs: they do not call C++ constructors or destructors. C++20 allows malloc to implicitly create objects of implicit-lifetime types, including some class types, when that makes subsequent access valid. That does not run a std::string constructor, and a cast cannot replace one; resource-owning objects still need proper construction. See the C++20 allocation wording.

new (std::nothrow) T returns null for allocation failure; a throwing T constructor still propagates its exception. If initialization in an ordinary new-expression throws, matching deallocation releases the acquired storage; completed array elements are destroyed too. new int leaves an indeterminate value, while new int{} initializes zero; see initialization rules.

The malloc call reserves bytes without running Tracked's constructor. Array allocation can have bookkeeping outside the elements, often an element count for destruction; never guess its location or pass an interior pointer to deallocation. Applying delete or delete[] to a suitably typed null pointer is harmless, as is std::free(nullptr); freeing the same non-null allocation twice is undefined behavior.

These raw operations expose the mechanism for allocator work. In application code, retain the ownership rules from RAII: use std::make_unique<T>, std::make_unique<T[]> or containers so exceptions and early returns cannot skip cleanup. Smart pointers teaches that ownership API.

Placement new: construct in storage you already own

Placement new has the form ::new (address) T(args). The standard non-allocating overload returns that address and construction happens there. You must supply a non-null pointer, sufficient space, correct alignment and storage available for the new lifetime.

The destructor also destroys the std::string member, but the byte array remains until scope exit. Each construction uses its returned pointer, avoiding stale pointers across replacement. std::construct_at is the C++20 library spelling; placement new is the C++17 alternative, and std::destroy_at can replace the explicit destructor call.

In this exact example the two complete, non-const Job objects are transparently replaceable, so first can also refer to the second object after construction finishes. That automatic retargeting does not apply to every replacement, including base subobjects. Prefer the new construction's returned pointer. C++17 std::launder in <new> can obtain a pointer to an already-live replacement under its type and reachable-storage requirements; it neither constructs an object nor fixes a race. See the C++20 replacement rules.

Never apply delete to this buffer. If you used malloc storage instead, destroy the constructed object and then call free on the original allocation; if construction throws, free the storage without destroying the object that never finished construction. A real reusable slot needs an engaged flag and an RAII owner to enforce exactly one destructor call on all paths.

Calling x.~T() on an ordinary local T x is usually a bug: scope exit will try to destroy it again unless you correctly reconstruct it. Placement storage also needs exclusive access during construction, destruction and reuse; an allocator's lock cannot protect a client that continues using a freed object. Follow the lifetime problem into lock-free stacks and memory reclamation.

Advance an arena cursor correctly

An arena must align the actual address, not just round an offset while ignoring the buffer's base alignment. std::align finds space; it neither allocates nor constructs. After success, reserve the object's bytes yourself, because the function subtracts only padding from the remaining capacity.

The fixed buffer has enough room for both slots, and Item construction cannot throw. A generic arena needs a cleanup owner for successfully constructed objects and a rollback policy if a later constructor fails. Check count-times-size and padding arithmetic for overflow when capacities come from input; the std::align contract does not check arithmetic you performed before calling it.

Overload allocation for one class

A class can provide static void* operator new(std::size_t) and static void operator delete(void*) noexcept. The first supplies storage; the new-expression still runs the constructor. The second releases storage; a normal delete-expression has already run the destructor. They are static even if you omit the keyword.

std::make_unique<Ticket> uses a new-expression internally, so the class hooks still run; its owner performs deletion. Both allocations are released, but only the successfully constructed object's destructor runs. The :: selects the global storage functions instead of recursively calling the class hooks. This normally aligned, final class uses single-threaded counters; those counters would need synchronization under concurrent allocations.

Scalar hooks do not intercept array new-expressions: arrays use operator new[] and operator delete[]. Other forms include sized delete (void*, std::size_t, C++14) and aligned overloads (std::align_val_t, C++17). If an unsized and a sized usual class delete are both available, the unsized one is selected. Keep each allocation family paired.

For an over-aligned class, implement alignment-aware hooks or explicitly obtain and release appropriately aligned storage. A size-only class hook can hide the global aligned overload, so blindly forwarding to ::operator new(bytes) can under-align the object. A pool must also handle exhaustion, slot size, alignment, constructor failure and concurrent free-list changes; see the allocator lesson.

Find a leak, then fix ownership

A memory leak is allocated storage that is never released when it should be. Losing the last pointer, skipping manual cleanup on an exception and owning-reference cycles are common causes. An unbounded cache can also retain reachable memory forever; a reachability-based leak detector may report nothing.

  1. Repeat one workload, drain outstanding work and compare live allocation counts or bytes between iterations. Resident memory alone also includes allocator caching and fragmentation.
  2. Use AddressSanitizer for invalid memory access and a supported LeakSanitizer runtime for leaked allocations. Follow the allocation stack to the missing owner, not merely the place memory was used.
  3. Give the allocation an RAII owner and rerun the workload, including its failure paths. Use ThreadSanitizer separately for races; a clean race report is not a leak check.

Common mistakes

  • Adding field sizes and calling that sizeof. Account for internal and tail padding, and label ABI assumptions.
  • Allocating sizeof(pointer) bytes for its target. Use the object's type and check multiplication overflow before allocating arrays of raw bytes.
  • Mixing allocation families. Scalar delete on an array, free on new storage and delete on malloc storage are undefined behavior.
  • Treating an aligned address as a live object. Storage capacity and alignment do not run a class constructor.
  • Destroying a placement object twice. Track whether the slot contains a live object; release its backing storage separately.
  • Using alignment as a race fix. It can help layout and performance, but shared mutable state still needs synchronization.
  • Calling an unsupported leak check a clean result. Confirm detector support, then test a known leak as well as the repaired program.

In the interview

Expect a struct-size calculation, a mismatched deletion to diagnose, or a request to place objects inside a fixed buffer. For the reported Rubrik allocator shape, first clarify whether the API returns offsets or typed objects: an integer offset simulation does not itself construct a C++ object.

I will state the target's size and alignment assumptions, place each member at an allowed offset, then round the total size for the array stride. After that I can reorder independent members, but I will check ABI and construction-order constraints.
My allocator promises nonoverlapping storage with the requested size and alignment. Constructing the object is a separate step. I will pair destruction with the correct storage return, handle construction failure, and synchronize allocator metadata without claiming that makes the user's objects thread-safe.

Follow ups: "What if the constructor throws?", "What if the type requires 128-byte alignment?", "Why did shrinking the struct hurt throughput?", and "Can another thread still hold this slot when you reuse it?" These lead into fixed-buffer queues and free lists and buddy allocation.

Key takeaways

  • sizeof includes the object's padding and excludes allocations it points to. alignof describes valid starting addresses.
  • Reorder independent members to reduce padding; separate hot per-thread fields when false sharing is the measured bottleneck.
  • Virtual dispatch often adds a pointer per simple polymorphic object plus padding, not a pointer per virtual method.
  • New/delete combine storage and lifetime operations. Malloc/free and direct allocation functions do not run constructors or destructors.
  • Placement new and class allocation hooks require explicit alignment, lifetime, cleanup and concurrency contracts.
  • Own allocations with RAII. Validate leak-detector support; ThreadSanitizer does not replace memory-error or leak checks.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Assume char has size/alignment 1, int has size/alignment 4, and ordinary minimal ABI padding. What are the sizes of { char a; int b; char c; } and { int b; char a; char c; }?
Why. The first has three padding bytes before b and three after c. The second has only two tail padding bytes. The tempting 9 and 6 ignores the rounding needed for the next array element's alignment.
What does int n = 4; auto bytes = sizeof(n += 1); std::cout << n; print?
Why. The operand of sizeof is unevaluated, so the increment never happens. The size is stored in bytes, but the printed variable is n.
Widget* p = new Widget[1]; delete p; uses an array with only one element. Is it correct?
Why. Allocation and deallocation forms must match independently of the element count or destructor triviality. One element does not turn an array new-expression into a scalar one.
The resource-owning Job above is constructed using placement new inside alignas(Job) std::byte storage[sizeof(Job)]. What is the correct cleanup before the buffer leaves scope?
Why. Leaving scope releases the byte array's storage and ends any remaining contained object lifetime, but does not automatically call the placement Job's destructor. Explicit destruction first releases its resources; delete and free would misuse the automatic backing storage.
In the Ticket allocation-hook example, storage allocation succeeds and the constructor throws. What happens?
Why. The new-expression handles failed initialization by releasing storage. There is no fully constructed Ticket to destroy; any completed bases and members are cleaned up during unwinding.
Two threads repeatedly write different long array elements. Which claim about alignas(64) long counters[2] is correct?
Why. Array alignment does not change element stride. Use an aligned wrapper type to separate elements, choose the boundary for the target, and measure. Alignment never adds synchronization.
Adding another virtual method to the simple Virtual example usually leaves its object size unchanged. Why?
Why. The common ABI keeps the dispatch entries outside each object. sizeof includes hidden in-object overhead, but neither a vtable representation nor an exact size is mandated by C++.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
Using the worked example's ABI assumptions, lay out struct Record { char kind; double score; int count; char ready; }; when double has size/alignment 8. Reorder it to reduce size, give both sizes and offsets, and name two reasons not to ship the change blindly.
Model answer

Initially kind is at 0, score at 8, count at 16 and ready at 20. Seven initial padding bytes and three tail padding bytes produce size 24 and alignment 8. Reorder to double score; int count; char kind; char ready;: offsets 0, 8, 12 and 13, followed by two tail padding bytes, produce size 16 and alignment 8. That saves eight bytes per element. The change breaks binary layout compatibility and changes aggregate initializer positions; it also changes member construction order, which can break dependencies. I would measure on the target and check all those contracts.

Design
A reusable slot must hold one nontrivial T without an allocation on each insertion. Describe insertion, removal, exception handling and the concurrency contract.
Model answer

Use at least sizeof(T) bytes aligned for T, plus an engaged flag. Under the slot's ownership or synchronization protocol, insertion first verifies the slot is empty, constructs with placement new, and sets engaged only after success. If construction throws, the flag stays false and there is no complete T to destroy. Removal uses the live object, destroys it exactly once, then marks the slot empty. The owner destroys any remaining engaged object before releasing the backing storage. Accessors must not retain a reference across removal; a lock around allocation metadata alone cannot enforce that. Publication and reclamation need a protocol that all clients obey.

Debug
A service's resident memory keeps growing, ThreadSanitizer is quiet, and the Mac aborts when you set ASAN_OPTIONS=detect_leaks=1. What can you conclude, and what do you do next?
Model answer

I cannot conclude that there is a leak or that the service is leak-free. ThreadSanitizer checks races, and this Apple runtime has rejected leak detection rather than completed it. I would repeat a bounded workload, drain it, and compare live allocations using Instruments or a supported LeakSanitizer runtime verified with a known leak. I would inspect exceptional exits and ownership cycles for leaked allocations, and separate those from reachable growth such as an unbounded cache or queued tasks. Resident memory can also remain high because an allocator retains freed storage. The fix needs a workload regression showing the appropriate live counts return to baseline.

Out loudabout 75 s
"This struct has only six bytes of fields. Walk me through why sizeof says twelve, and whether you would reorder it in our concurrent service."
What a strong answer covers
  • State the size and alignment assumptions before calculating an ABI-dependent result
  • Place char, int, char at offsets 0, 4 and 8, then round the complete size to 12
  • Reordering int, char, char gives offsets 0, 4 and 5 and a size of 8
  • Check ABI compatibility, initializer positions and construction dependencies before reordering
  • Different writers can false-share a line; padding does not make shared writes safe
  • Measure layout and workload performance instead of assuming smaller is always faster
How a senior would say it
The extra bytes are alignment padding. Assuming a one-byte char and a four-byte int aligned to four bytes, the first char sits at offset zero. The int cannot start at offset one, so the compiler leaves three bytes and places it at four. The last char lands at eight. Three tail bytes bring the size to twelve, which keeps the next object in an array correctly aligned. If I put the int first, the chars can occupy offsets four and five, and the complete size becomes eight. Before shipping that change, I would check binary compatibility, aggregate initializers and any constructor dependency on declaration order. In a concurrent service I would also ask which threads write these fields. Packing independent hot counters together can increase false sharing, while padding cannot make writes to the same plain counter safe. I would measure the actual offsets and size on our compiler, then benchmark the real workload. Smaller objects help capacity, but their placement can still hurt throughput.

Likely follow up: What changes if I align the array itself to 64 bytes instead of aligning its element type?

Out loudabout 75 s
"We already have a buffer. Why can't I just cast its address to Job* and later delete that pointer? Compare the correct options."
What a strong answer covers
  • A cast does not run a nontrivial Job constructor; storage and object lifetime are separate
  • Require enough storage, correct alignment and exclusive access before placement construction
  • Use placement new and its returned pointer, then explicitly destroy the constructed object exactly once
  • Release backing storage using its original allocation family; an automatic buffer is not deleted
  • Handle constructor failure without destroying an incomplete object; retain RAII ownership of storage
  • Ordinary new/delete combine both stages and smart owners are the default outside allocator internals
How a senior would say it
A cast gives me a different pointer type; it does not construct a nontrivial Job. I first need enough storage, the right alignment and exclusive access to that slot. Then I can use placement new to construct Job there and keep the pointer it returns. When I remove the job, I explicitly run its destructor exactly once. That releases the job's own resources but leaves the slot's storage available for reuse. I must return that storage according to its original owner. For a local byte array there is no manual deallocation. For malloc storage I eventually call free on the original allocation. Ordinary delete is wrong for either placement pointer because it couples destruction with a different deallocation contract. If construction throws, I leave the slot empty and preserve or release its storage through its owner; there is no complete Job to destroy. Ordinary new and delete combine those stages for me. Outside allocator internals I would use an RAII owner, usually a container or unique pointer, to keep failure paths correct.

Likely follow up: What protects a reference another thread obtained just before you destroyed and reused the slot?

"Our process grows after every failed request, but ThreadSanitizer reports nothing. How would you investigate on this Mac?"
What a strong answer covers
  • A quiet ThreadSanitizer run does not check leaks; distinguish live allocations from resident memory
  • Repeat and drain a bounded workload, then compare live allocation counts or bytes
  • The tested Apple Clang runtime rejects detect_leaks; use Instruments or a verified supported runtime

How a senior would say it
I would investigate ownership and retention, because a quiet ThreadSanitizer run says nothing about leaks. First I would repeat one bounded request workload, wait for outstanding work to drain, and compare live allocation counts or bytes. Resident memory alone can grow because of allocator caching or fragmentation. I would then inspect allocation stacks and ask which owner should have released each surviving allocation.
