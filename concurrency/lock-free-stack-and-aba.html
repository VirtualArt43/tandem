A lock-free stack and the ABA problem

Build a Treiber stack with compare-and-swap in both languages, watch ABA corrupt it, and learn why C++ must not free popped nodes early.

Asked atRubrik
Before this:CAS loops and atomic state machinesC++ memory orders: seq_cst, acquire, release and relaxed

The lock-free stack is the "hello world" of lock-free data structures, and a real Rubrik follow up: build a thread-safe stack, then make it lock-free with compare-and-swap. The code is short. What it hides, the ABA problem and safe memory reclamation, is what the interviewer is really testing.

In plain words

A canteen keeps a stack of plates, and a sign on the wall says which plate is on top. To take a plate you note the top plate and the one under it, then update the sign, but only if it still names the plate you noted. If someone beat you to it, you look again.

Now the trap. You note "top is plate A, under it is plate B", and get distracted. Meanwhile someone takes A, someone else takes B, and A is washed and put back on top. The sign says A again, so your check passes and you set the sign to B. But B is in someone's hands. The sign looked unchanged, yet the stack under it had changed completely. That is the ABA problem.

One atomic head

The treiber stack (R. Kent Treiber, IBM, 1986) is a singly linked list whose top is a single atomic pointer, head. Both operations are CAS loops on head:

  • Push: make a new node, point its next at the current head, then CAS head from that current head to the new node. On failure refresh the expected head and retry; weak CAS can fail spuriously even without a change.
  • Pop: read the head; if it is null the stack is empty. Otherwise read head.next, then CAS head from the node you read to its next. If the CAS fails, try again. If it succeeds, the node is yours.

The shared update point is head; the nodes and their links also hold state. With safely published links and safe node lifetimes, the CAS protocol can be lock-free: a paused updater does not own a lock that others need. This classifies the protocol, assuming lock-free atomic primitives; allocation, value operations and reclamation need their own progress analysis.

The stack in both languages

The program checks LIFO order on one thread, then runs 4 pushers and 4 poppers and confirms that every value comes out exactly once.

Why each line is there

  • next is written only before publication. A node's next is set while the node is still private to the pushing thread, and never touched after the CAS publishes it. That is what makes it safe for a popper to read current.next without a lock: nobody is writing it.
  • Read next before the CAS, from the node you compared. The pop reads current.next and then swaps head from current to that value. Reading head.get().next instead would read a different node if the head moved.
  • Memory order (C++). The push's successful CAS is a release, so the node's value and next are visible to whoever acquires it. The pop's load and CAS are acquires, and so is the failure order, because after a failed CAS the loop dereferences the fresh current. With all-default orders (sequentially consistent) the code is equally correct, just possibly slower on ARM. In Java, the AtomicReference operations give you these guarantees automatically.
  • The retired list (C++). A popped node goes onto a second, push-only list and is freed only in the destructor. Why not free it at once is the second half of this lesson. The node gets a separate retired link because another thread may still be reading its next.

The lifetime contract is part of the API. Java rejects null values so that null unambiguously means empty. The C++ template requires non-throwing moves and destruction: a move that threw after unlinking a node could otherwise skip retirement. Destroy the C++ stack only after all users have stopped, as the demo does by joining every thread. These stress checks can reveal bugs; they do not prove all possible interleavings correct.

Why acquire-only pops can expose an older node. Every concurrent head modification here is a read-modify-write operation. In C++20 those operations extend the release sequence headed by an earlier publishing push, so an acquiring read that sees a later head value can still observe that earlier node's initialization. Replacing a head CAS with an unrelated relaxed store would need a new proof.

Where the operation takes effect

A successful push or nonempty pop takes effect at its successful head CAS, its linearization point. An empty pop takes effect at the atomic read that observes null, including the failed C++ CAS that refreshes current to null. A push that happens just afterwards does not invalidate that empty result.

Each attempt does O(1) work, excluding allocation and moving the value, but one caller can retry without a bound. For the progress proof, a strong CAS mismatch means another operation changed the head; it does not promise that every caller finishes. C++ weak CAS can also fail spuriously, so a single weak failure is not evidence of another success. The usual lock-free argument assumes the underlying atomics make progress rather than failing spuriously forever.

ABA: when "the same" is not the same

A compare-and-swap asks "is head still the pointer I read?" The pop needs its saved successor to remain valid if that comparison succeeds. A push and pop above the same unchanged node is harmless; returning to a node whose lifetime or next changed is not. That harmful case is the ABA problem.

You can force that exact interleaving with two latches and watch it happen. This version pushes node objects directly, so a node can be pushed again after it was popped, the way a node pool behaves. The C++ demo keeps all nodes alive and uses C++20 std::latch; in C++17 use a mutex and condition variable with a predicate to coordinate the same steps.

Nothing here is a data race: the latches order every step, and ThreadSanitizer stays quiet. The program is simply wrong. The next pop will hand out B a second time, and if T2 had linked B into some other structure, the stack would now lead into that structure. ABA is a logic bug that every individual atomic operation took part in correctly, which is why it is so hard to find in testing.

Why Java rarely sees it, and when it does

In the Treiber stack from the first program, every push allocates a brand new node. For T1's CAS to be fooled, head would have to hold the very same object A again. The garbage collector never frees, let alone reuses, an object that some thread still references, and T1 holds a reference to A. So a fresh-node Java stack cannot suffer the pointer form of ABA. The garbage collector is a memory reclamation scheme, and it is the reason lock-free code is so much easier on the JVM.

Java code does hit ABA in three situations:

  • You recycle objects, for example a node pool to avoid allocation, as in the demo above.
  • You compare-and-swap values, not fresh objects: an AtomicInteger state that goes IDLE, BUSY, IDLE, or an index into an array of slots. A thread that read IDLE cannot tell that a whole BUSY period happened in between.
  • The meaning of a value changed while the value did not, such as a balance that returned to the same number through two different transactions, when the decision depended on history.

A version stamp distinguishes successive appearances of the same reference, provided it does not wrap while an old observation remains usable. AtomicStampedReference pairs a reference with an int stamp and compares both at once. AtomicMarkableReference instead pairs a reference with a boolean, useful for logical deletion; a reusable bit is not a general ABA counter.

The fragments below require a non-null, unlinked node exclusively owned by the caller of push. Reinsertion is allowed only after a successful pop. C++ callers must keep every node alive until all operations stop. Reused links are volatile in Java and atomic in C++ because stale readers may still read them during reinsertion; tags alone do not make those accesses safe. The fragments assume the stamp cannot wrap during a stale operation.

Replay the bad interleaving with stamps: T1 reads (A, stamp 3). T2's two pops and one push move the stamp to 6. T1's CAS expects (A, 3), finds (A, 6), and fails. Read reference and stamp together with get(stamp); separate getReference() and getStamp() calls can observe different updates.

Java's implementation uses boxed reference-stamp pairs, so updates can allocate, including losing CAS attempts. Its reference comparison is still ==, not equals. The Java stamp repeats after 2^32 increments; the unsigned C++ tag repeats after 2^64. A wider tag makes wrap less likely, but correctness still needs a bound on intervening updates or a reuse protocol. A 16 bit tag wraps after just 65,536 updates.

On usual 64 bit targets, the C++ Head occupies 16 bytes. A lock-free implementation needs suitable wide atomic support; otherwise the library may use an internal lock. Check the actual atomic object's is_lock_free() and the target implementation instead of assuming a particular machine instruction.

In C++, ABA and freeing are related problems

A C++ programmer reading the first program wants to delete the popped node at the end of pop(). Here is why that is wrong. Between T1 reading head (node X) and T1 reading X->next, thread T2 can pop X and free it. T1 then reads freed memory: use-after-free, undefined behavior. Worse, the allocator may hand X's address to the very next push, so head holds "X" again and T1's CAS succeeds: ABA, caused by the free.

So the C++ question is safe memory reclamation: when is it safe to free a node that has been removed, given that other threads may still hold a pointer to it? The options:

A good point to make out loud: safe reclamation prevents premature freeing and allocator-induced ABA when the algorithm follows the protection protocol. It does not stop a caller from explicitly reinserting a live node and changing its links. Tags detect intervening head changes until they wrap, but cannot protect a dereference of freed memory. The TaggedStack therefore requires caller-owned nodes to remain alive. C++20 has no standard hazard-pointer or epoch-reclamation facility; production code should use a proven implementation.

Worked example: the ten-minute follow up

You have written a locked stack and the interviewer says, with ten minutes left: "Make it lock-free." A Rubrik candidate reported exactly this, in the final ten minutes, and did not finish. Here is a plan that fits.

  1. Say the design in one sentence (30 seconds): "A linked list with an atomic head; push and pop are compare-and-swap loops on the head."
  2. Write push (2 minutes): new node, node.next = current, CAS, retry.
  3. Write pop (3 minutes): read head, null check, read next, CAS head from current to next, retry; return the value.
  4. Name the two traps unprompted (2 minutes): "In C++ I must not free the popped node, because another thread may still read its next, and a reused address causes ABA; I would retire nodes and free them with hazard pointers or epochs, or in an interview just defer frees to the destructor. In Java the GC handles it as long as I never recycle nodes."
  5. Offer the trade-off (1 minute): "The head-update protocol is lock-free with suitable atomics; allocation still needs analysis. It is not automatically faster: every operation contends on one head, so under heavy contention a lock can do as well. I would measure."

Point 4 is where the round is won. The code is the easy part; the reasoning is the signal.

Common mistakes

  • Ignoring the pop's CAS result. Returning current.value after failure can return another popper's element, or return an element that a concurrent push left on the stack. Refresh and retry instead.
  • Reading next from a second read of head. head.compareAndSet(current, head.get().next) takes next from a node that may not be current.
  • Freeing the popped node in C++. Use-after-free for a thread still reading it, and ABA through address reuse. Retire it instead.
  • Writing the original stack's plain next after publication. Concurrent readers can race with that write. Recycling needs a different protocol, such as the atomic links and stamped head above, plus a lifetime rule.
  • Recycling nodes "for performance" in Java. It brings back exactly the ABA that the garbage collector was protecting you from.
  • Assuming shared ownership guarantees lock-freedom. Atomically acquiring a std::shared_ptr can simplify lifetime management, but its atomic operations and destruction are not guaranteed lock-free. C++20 specifies std::atomic<std::shared_ptr<T>>; this Mac's libc++ lacks that specialization. C++17 has the free std::atomic_load and std::atomic_compare_exchange_weak overloads for shared pointers, also with no lock-free guarantee.
  • Keeping an exact size(). A separate atomic counter is updated at a different moment from head, so it can be briefly off. Say that size() is approximate, or drop it.

In the interview

Rubrik has asked this in more than one shape: a US onsite in 2024 went from a thread-safe stack on a linked list to "now make it lock-free with CAS" in the last ten minutes, with the candidate asked to explain the primitives, and a US screen in 2025 asked for an atomic stack built from linked list nodes. The flip side comes from a lower-confidence Databricks report: a candidate who could not justify why a lock-free attempt was thread-safe nearly failed, and a plain synchronized version passed. Correctness you can explain beats cleverness you cannot.

The stack is a linked list with an atomic head. Push and pop retry a CAS, and a successful head CAS is where each update takes effect. With lock-free primitives, head mismatches show that other operations are advancing, although weak CAS can also fail spuriously. The danger is ABA: a reused node can compare equal even though its successor changed. Fresh Java nodes avoid that reuse; in C++ I must also keep removed nodes alive while readers may dereference them. I would use proven reclamation or defer freeing until all users stop in a bounded demo.

Follow ups to expect: "Show me an interleaving that breaks it" (draw the A, B, A timeline), "How does a version counter help, and can it wrap?" (every finite tag can wrap, so state the bound you rely on), "Is it faster than a mutex?" (not necessarily; next lesson), "What progress guarantee is it?" (the CAS protocol is lock-free, not wait-free, under the stated primitive assumptions).

Senior depth

The hazard pointer protocol. Load head, publish that pointer in your hazard slot, then reload head; retry if it changed, and only then dereference. Keep protection until your last access and clear it afterwards. The remover must first unlink, retire, then scan with ordering that ensures either it sees your protection or your validation sees the removal. A simple proof uses sequentially consistent head operations, hazard publications and scans throughout; sprinkling one release store or one fence into otherwise relaxed code is not a proof. Use a verified library protocol before weakening any orders.

One hot spot, still. All Treiber operations contend on head. An elimination-backoff stack lets a concurrent push and pop exchange a value in a side array; their overlapping operations can cancel without changing the central stack. Java's ConcurrentLinkedDeque provides concurrent push and pop operations, with pop throwing on empty and poll returning null. ConcurrentLinkedQueue uses a non-blocking algorithm based on Michael and Scott: linking a node is essential, while lagging tail maintenance can be helped by another thread. Do not promise an exact CAS count for Java's implementation.

Pointer tagging in one word. Some implementations pack a tag into pointer bits that their target ABI leaves available. This is not portable C++: address widths, alignment and pointer representations matter. A small tag wraps quickly, and must be removed before dereferencing; packing never replaces a lifetime proof.

Key takeaways

  • A Treiber stack is a linked list with one atomic head; push and pop are compare-and-swap loops on it, and a node's next never changes after publication.
  • ABA: a CAS checks that the value is equal, not that nothing happened; a reused node or address can fool it into corrupting the structure.
  • Java's garbage collector protects fresh node identities; recycling objects or CASing on repeating values can reintroduce ABA. A version stamp distinguishes updates only until wraparound.
  • In C++ retire popped nodes and reclaim with a correct hazard or epoch protocol, or after every user stops. Reclamation prevents allocator reuse bugs, but not arbitrary reinsertion of live nodes.
  • Lock-free is a progress property, not a speed promise: the head is still one hot cache line.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A correct Treiber stack holds A on top of B. Threads T1 and T2 call pop() at the same moment, and no one pushes. What can they return?
Why. Both read head A, but only one CAS from A to B succeeds. The loser's CAS fails, it re-reads head B and pops B. Returning A twice would need two successful CASes from A, which compare-and-swap rules out; returning empty would need the loser to see a null head, which never happens while B is on the stack.
In the ABA problem, why does the stale thread's compare-and-swap succeed?
Why. The head can be atomic and race-free throughout, as the forced demo shows. CAS answers "is it equal now?"; it does not validate the stale successor. No hardware bug or non-atomic head access is required. Comparing a version as well detects the intervening changes provided that version has not wrapped.
Why is the classic ABA problem rare in a Java Treiber stack that allocates a new node on every push?
Why. The thread that is about to CAS holds a reference to the old head, so that object stays alive and no fresh node can have the same identity. The head can return harmlessly to the unchanged old node if pushes above it are undone. Harmful reuse needs recycling or repeating logical values. Reference CAS uses ==, not equals; it supplies no hidden version stamp, and locking would not detect history either.
C++ onlyIn a C++ Treiber stack, pop() has successfully unlinked the node and extracted its value. Why can it still not immediately reclaim the node?
Why. A successful CAS proves the node is no longer reachable from head, not that no thread holds an earlier pointer. Even after extracting the value, immediate freeing is unsafe. The issue is reader lifetime, not a general lack of thread safety in deallocation. Retire and reclaim after protection ends, or at destruction after all users stop.
Java onlyWhen does AtomicStampedReference.compareAndSet(expectedRef, newRef, expectedStamp, newStamp) succeed?
Why. Both parts must match; neither matching alone is sufficient, and reference equality means identity, not equals. Incrementing the stamp on every change detects this ABA until the stamp wraps. Use get(stamp) to read the pair consistently.
What is wrong with this pseudocode, where compareAndSet returns a boolean and leaves current unchanged?
Why. A failed CAS means this thread did not remove current, either because another thread popped it or because a push put something above it. Either way it does not own that node. The CAS does not overwrite the new head, so it does not itself discard the pushed elements, and this straight-line code has no waiting cycle. Loop until removal succeeds or the stack is observed empty.

Why. Hazard pointers and epochs both delay the free until no thread can be using the node; deferring to the destructor is the blunt version that is correct but lets memory grow. A lock around delete does nothing because readers never take that lock, and volatile has nothing to do with lifetime or threads.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a Treiber stack with push(value) and pop() (returning empty or null when empty) in your language. In C++, make sure no popped node is freed while another thread might still read it.
Model answer

What the grader looks for: next read from the node that was compared, the CAS inside a loop, the value returned only after a successful CAS, and in C++ no delete in pop, with a sentence on why (use-after-free and ABA) and on what production code would use instead (hazard pointers or epochs).

Explain
Explain the ABA problem to an interviewer with a concrete interleaving on a lock-free stack, and give two different fixes.
Model answer

Take a stack A, B, C. Thread T1 starts a pop: it reads head A and A's next, B, and is preempted before its CAS. Thread T2 pops A, pops B, and pushes A back, either the same recycled node or a new node that the allocator placed at A's old address. The stack is now A, C. T1 resumes and does CAS(head, A, B). Head equals A, so the CAS succeeds and sets head to B, a node T2 owns. The stack now says B, C: B will be handed out twice, and if B had been freed, the stack points into freed memory.

The root cause is that compare-and-swap checks current equality, not whether the saved successor is still valid. Fix one: compare pointer and version together, incrementing the version on every head change and ensuring it cannot wrap during a stale operation. This does not solve use-after-free or unsafe link mutation. Fix two: forbid live-node reinsertion and delay freeing or reuse until readers are protected by a correct reclamation protocol, or use fresh Java nodes and GC. Both the lifetime rule and the reuse rule matter.

Explain
The interviewer asks: "Is your lock-free stack faster than a stack with a mutex?" Give a senior answer.
Model answer

Not necessarily, and I would not claim it without measuring. Both versions serialize on one hot spot: the lock-free stack on the head's cache line, the locked one on the mutex and the top node. Under heavy contention the lock-free version wastes work on failed CAS attempts and generates a lot of cache line traffic, while a good mutex lets one thread run while the others sleep, so it can match or beat it. Each lock-free push also allocates, and in C++ safe reclamation adds its own costs.

The lock-free protocol avoids dependence on a particular lock holder: other active threads can keep completing operations while one pauses. It does not bound an individual's latency or make allocation, reclamation and callbacks non-blocking. For throughput I would consider elimination or batching. Per-thread stacks with stealing reduce sharing but change the global LIFO contract, so that requires agreement on semantics.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Walk me through an ABA failure on a stack. Would garbage collection or a version stamp fix it?"
What a strong answer covers
  • CAS compares the current value, not its history or the validity of a saved successor
  • T1 saves head A and successor B; T2 pops A, pops B, and reinserts A above C
  • T1's stale CAS succeeds and incorrectly restores B, which T2 already owns
  • Fresh Java nodes and GC prevent harmful identity reuse; explicit live-node recycling can still fail
  • Compare pointer and incremented stamp together, with a wraparound bound
  • A stamp does not protect C++ node lifetime or make concurrent link mutation safe
How a senior would say it
ABA is when the head compares equal again but the successor I saved is no longer valid. Start with A above B above C. My pop reads head A and saves B, then pauses. Another thread pops A, pops B, and puts A back above C. I resume and compare the head with A. That comparison succeeds, so I install B as the new head, even though the other thread already owns B. Every head access can be atomic and the stack is still wrong. For a Java stack that always allocates fresh nodes, garbage collection preserves object identity while I hold a reference, and popped objects are never reinserted. Explicitly recycling live nodes removes that protection. A stamped head is another approach: compare the reference and version together and increment the version on every head change. My old version then fails even when the reference matches. But a finite stamp can wrap, so I need a bound on updates while a stale observation is usable. And in C++, a stamp does not keep the node alive long enough to read its successor. I still need safe reclamation and safe access to any links that reinsertion changes.

Likely follow up: Can the head return to A without causing a bug, and what makes that case harmless?

"You have written the C++ CAS loop. When can you free a popped node, and where does the pop take effect?"
What a strong answer covers
  • Successful head CAS is the nonempty pop's linearization point, not proof that all readers are gone
  • A stale reader may still dereference the unlinked node, so immediate freeing is unsafe
  • A bounded demo can retire nodes and reclaim only after all callers stop
  • Production reclamation protects readers through hazard publication and validation, or an epoch grace period
  • Separate link storage and non-throwing value moves are explicit contracts in this example
  • Allocation and reclamation must be included before claiming end-to-end lock-freedom
How a senior would say it
The pop takes effect at its successful head CAS, but that is too early to free the node. Another thread may already have loaded the old head and be about to read its next pointer. Unlinking proves the node is no longer reachable from the stack, not that no reader holds it. For a bounded interview demo, I put removed nodes on a retired list and reclaim them only after every caller has stopped. That is simple, but memory grows with the total work. For a server I would use a proven reclamation protocol. Hazard pointers publish and validate protection before dereferencing; epochs wait for readers that could have seen the node to leave their protected intervals. I keep a separate retirement link because stale readers still access the stack link. This example also requires non-throwing value moves, so an exception cannot skip retirement after removal. Finally, calling the head protocol lock-free does not classify the whole method. The allocator, value transfer and reclamation path also need progress analysis.
