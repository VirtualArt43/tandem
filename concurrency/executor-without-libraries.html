An executor without libraries: submit, wait for all, shutdown and shutdownNow

Build an executor from primitives, then add shutdown, cancellation, exception handling, bounded admission, idle worker retirement and precise completion semantics.

Asked atRubrikLinkedInMicrosoft
Before this:Build it yourself: a thread pool with futures and shutdownProducer and consumer with a bounded bufferStopping a thread: interruption and cooperative cancellation

"Implement an executor, no library allowed" recurs in Rubrik reports from 2020 onwards. Reports in 2026 add shutdown versus shutdownNow, exceptions inside tasks, interrupts, per-task timeouts and reclaiming idle threads. Build the runnable executor and lifecycle first, then work through timeout and snapshot-wait extensions.

In plain words

Think of a tiffin kitchen with three cooks. Orders go up on a board; a free cook takes the oldest order, cooks it, packs it, and comes back to the board. The manager can ask "tell me when no orders remain unfinished". If one cook burns a dish, that dish is reported as failed, but the cook does not walk out of the kitchen.

At closing time there are two ways to stop. "No new orders, finish the board" is shutdown. "Fire alarm: drop what you are doing if you safely can, and hand me the orders nobody started" is shutdownNow. And when the lunch rush is over, the extra cooks hired for the rush go home after standing idle for a while: that is reclaiming idle threads.

The question, as it is asked

The Rubrik reports show one family with several faces:

  • 2020 to 2022: schedule(task) never blocks; waitUntilComplete() blocks until all scheduled work is done; no thread-safe deque or blocking queue allowed.
  • 2022 and 2025: a single-threaded client calls submitWork(task), which returns at once, and blockUntilComplete(); spread the load over workers.
  • 2026: build a bounded queue (a ring buffer, in one report), then a thread pool on it with submit, execute, shutdown and shutdownNow. Follow ups: an exception thrown inside a task, a per-task timeout, reclaiming idle threads. The interviewer judged shutdown semantics, interrupts and which exceptions are caught, and changed the requirements three times.

The research also records a LinkedIn pool implementation with the API banned and a Microsoft ThreadPoolExecutor implementation question. The answer is the same machine, so build it once, properly.

The state, the invariant, the two conditions

Before any code, say what is shared and what must stay true:

  • a FIFO queue of tasks not yet claimed by a worker;
  • a pending count: tasks accepted and not yet finished or removed, so queued plus claimed/running;
  • a state: running, shutting down, or stopped (the executor lifecycle);
  • the set of workers, and how many of them are idle.

One lock guards all of it, because the invariant ties the pieces together: pending equals queued plus claimed/running, and waiters sleep only while the thing they need is false. Two kinds of thread wait for two different things, so there are two condition variables. Idle workers wait for "there is work, or the pool is ending". Callers of waitUntilComplete wait for "pending is zero".

Three rules follow, and each one is a graded point:

  1. Take the task under the lock, run it outside the lock. Running under the lock serializes the pool and can deadlock callbacks, especially with C++'s nonrecursive mutex.
  2. Do the bookkeeping (pending -= 1, signal at zero) in a finally block or after a catch-all, so a failing task cannot leave the count high and a waiter asleep forever.
  3. Every wait is a loop on the real condition, re-checked after every wakeup.

Version 1: schedule and waitUntilComplete

This is the phone screen answer: a fixed number of workers started up front, an unbounded queue (so schedule never waits for capacity or task completion), and a close that finishes queued work and joins the workers. It is reusable: you can schedule a batch, wait, and schedule another.

This is a blocking synchronization design. Submission may wait for the mutex and allocation; "returns at once" means it does not wait for the task to finish. This version creates threads in the constructor; Version 2 may create one during submission. An unbounded queue trades admission waits for potentially unbounded memory use. waitUntilComplete observes global idleness under the lock, so later submissions may extend the wait or arrive just after it returns.

Only an external owner may call close or wait for the entire pool; a task waiting for its own pending count to disappear deadlocks even when tasks run outside the lock. Serialize close calls in this simple version, and keep the executor and captured task data alive until all workers finish.

Version 1 stops workers through close, not through interrupts. Java's awaitUninterruptibly preserves interrupt status when it returns, so the worker clears that status after the idle wait and before claiming the next task. Otherwise an interrupt received while idle could immediately abort an unrelated task's first interruptible operation.

The mutex also publishes data. Writes before schedule become visible when a worker acquires the same lock to claim the task. A task's result writes precede its completion update under that lock, so a successful completion wait observes those writes. This does not protect concurrent writes by different tasks to the same result: use separate result slots or synchronize those writes too.

Read it against the three rules. The task runs between two locked regions, never inside one. The decrement sits in finally in Java and after a catch-all in C++, which matters more in C++: an exception that escapes a std::thread function calls std::terminate and ends the whole process, while in Java it only kills that worker, silently shrinking the pool. And waitUntilComplete re-checks pending in a loop, so it is immune to spurious wakeups.

The predicate update must use the lock the waiter checks under. In C++, notification may occur after unlocking, provided the condition variable is still alive. Making the counter atomic does not save you, because the danger is not a torn counter, it is a signal that arrives between the waiter's check and its sleep:

That is a lost wakeup. A condition obtained from Java's ReentrantLock requires holding that lock to signal, which closes this exact window, but the same bug comes back if a Java waiter checks the count before taking the lock and then waits unconditionally. The shared rule is to check and update the predicate under one mutex and wait through that mutex. Other Condition implementations may document different signalling rules; C++ notification itself does not publish the predicate.

Version 2: the full lifecycle

The 2026 version of the question wants the lifecycle a real pool has. The shutdown methods below follow Java's ThreadPoolExecutor lifecycle. waitUntilComplete is our additional API, and our growth and rejection policies differ from the library:

CallNew submissionsQueued tasksRunning tasksReturns
shutdown()RejectedStill runFinish normallyWithout waiting for tasks to finish
shutdownNow()RejectedRemoved and handed backInterrupted (Java) or asked to stop (C++); they stop only if they cooperateWithout joining workers, with the tasks still queued

Workers start lazily, up to max; core is a retention floor, not a promise to prestart that many threads. Workers above core retire after an idle wait budget. The queue holds at most capacity waiting tasks, with at most max additional claimed/running tasks. A full queue rejects even if more workers could theoretically be created. This retirement of surplus workers is idle thread reclaim, a reported 2026 follow up.

The output is illustrative: sleeps make the workload and idle retirement visible, but do not enforce the printed thread counts or task split. The C++ stop-token wait needs C++20. For C++17, use a task-owned mutex, condition variable and cancellation flag; publish cancellation under that mutex and notify its waiters.

Pool retirement is not the same instant as native thread exit. Java removes a worker immediately before its final return. C++ parks its handle before that return and later joins it. The timed methods budget condition waiting after lock acquisition; lock contention, scheduling and C++ joins can make total elapsed time longer. Keep the pool alive through every API call and task, use one external termination owner, and never wait for pool-wide completion from one of its tasks.

The lines that carry the grade:

  • The spawn rule in execute. A new worker starts when there are more queued tasks than idle workers and the pool is below max. Comparing with the idle count, not with zero, handles the case where an idle worker was already signalled for an earlier task but has not woken yet.
  • The order of checks in takeTask. Stop first, then the queue, then shutdown, then the idle timeout. Because the queue is checked before the timeout, a task that arrives just as a worker times out is still taken.
  • Retire under the same lock as the decision. The worker removes itself from workers in the critical section where it decides to leave. If it left the set later, execute could count it as present, decide not to start a thread, and strand a task in the queue with no worker.
  • Clear stale interrupts (Java). A task may restore the interrupt flag on its way out. Thread.interrupted() before the next task stops that flag from aborting an innocent task. Java's ThreadPoolExecutor similarly distinguishes normal execution from its STOP state. Here the clear and STOP check hold the same lock as shutdownNow, so a new shutdown interrupt cannot be erased before a claimed task runs.
  • Who joins a thread that leaves on its own (C++)? A thread cannot join itself, and detaching requires a separate lifetime protocol this pool does not have. So a retiring worker moves its own std::thread into retired_, and execute, awaitTermination or the destructor joins it later, outside the lock.
  • shutdownNow cannot kill anything. Java interrupts, and only tasks that block in interruptible calls or check the flag stop early. Standard C++ has no thread interruption API, so the pool exposes a std::stop_token and the task waits on it with std::condition_variable_any. This is cooperative cancellation in both languages.

Claiming a task is removing it under the pool lock. shutdownNow returns tasks still in the queue; a worker may already have claimed a task without calling it yet, so that task receives a stop request but is not returned. The stop request is pool-wide and permanent. In C++, it happens outside the mutex because registered callbacks execute synchronously: a callback that calls poolSize() would otherwise deadlock. Such callbacks must return promptly; shutdownNow is not a constant-time operation.

The C++ retirement map transfers nodes without allocation. Worker startup allocates its bookkeeping before starting the thread, and a startup failure rolls back the submission under the lock. Constructor validation prevents a zero-worker executor from accepting work it cannot execute. Assume task counts and clock arithmetic remain representable, and do not treat recovery from VM or allocator exhaustion as guaranteed.

Exceptions: three places they bite

Inside the task. These examples catch Throwable in Java and ... in C++ around each task. That retains the worker after ordinary task failures, including a Java AssertionError; it is not a guarantee of recovery from a VM failure. With direct execute, Java's ThreadPoolExecutor can instead let a failed worker exit and replace it as required. Completion bookkeeping must run either way, and an error handler must not throw or block indefinitely.

Getting results and errors back. A caller who needs a value or needs to know about the failure gets a future. The task's exception goes into the future. Java get() throws ExecutionException with the failure as its cause, while C++ future::get() rethrows the stored exception:

If the interviewer bans CompletableFuture as well, the hand-built future from build it yourself: a future slots in. The shared_ptr in the C++ version is there because std::packaged_task is move-only and std::function needs a copyable callable.

Tasks that never ran. The Java queue stores lambdas, not their returned futures: cancelling the returned Runnable objects is not an available API. The owner must retain and complete the corresponding futures, or extend each queued task into a descriptor with both run and cancel actions. In C++, the future becomes ready with broken_promise only when the last wrapper owning the unrun packaged task is destroyed; keeping the returned task list alive keeps those futures pending.

The Java wrapper is a result channel, not an interruptible task handle: CompletableFuture.cancel(true) and orTimeout do not stop the work. A queued cancelled wrapper can still call the original task. Use a FutureTask or an explicit task cancellation protocol when you need that stronger contract.

Interrupts, handled on purpose

"Which exceptions do you catch?" is really "do you know where an interrupt can land?" There are four places, and each needs its own answer:

Timeouts: a task that runs too long

Neither language can safely kill a running thread. Java's Thread.stop() throws UnsupportedOperationException in Java 21, and C++ has no safe equivalent. So a per-task timeout is always a request plus a policy for when the request is ignored:

  1. The caller enforces its waiting budget. A timed future wait does not cancel work. After timeout, Java FutureTask.cancel(true) attempts to interrupt its runner if cancellation wins; the CompletableFuture wrapper above does not. C++ futures have no cancellation API: pass a per-task stop token separately. Decide whether the budget includes queue time or starts on execution.
  2. The pool enforces a deadline. A watchdog tracks task identity, worker assignment and deadline. In Java, serialize checking the assignment and delivering the interrupt with the worker's completion and reassignment; otherwise a late interrupt can hit the next task after it cleared its flag. A generation check followed by an unlocked interrupt is still racy. In C++, capture a per-task stop source and request it outside the pool lock; callbacks may execute synchronously.
  3. A task ignores cancellation. The caller may time out while the task continues consuming resources and causing side effects. Keep it counted as running until it actually returns. Do not automatically replace stuck threads without a bound: that defeats the concurrency limit and can exhaust the process. Apply admission limits, alert, and use a process boundary when hard termination is required. Timeout and completion must race to one terminal result; cancellation cannot undo completed I/O.

Worked example: shutdown versus shutdownNow, step by step

Consider an idealized Java schedule with negligible scheduling overhead and tasks that return when interrupted. A pool has 2 workers (core = max = 2). At time 0 you execute five tasks, T1 to T5, each sleeping 100 ms. At 10 ms, T1 and T2 are running and T3, T4, T5 are queued. Now compare the two calls at 10 ms:

Change one detail: T1 is a CPU loop taking about 100 ms that never checks isInterrupted(). Then shutdownNow still returns at once with T3 to T5, but T1 runs its full course and awaitTermination(50) returns false. That is the sentence interviewers want: shutdownNow is a request, and termination depends on the tasks cooperating.

Common mistakes

  • Decrementing pending only on success. One throwing task and waitUntilComplete hangs forever. Decrement in finally.
  • Running the task under the lock. The pool becomes single-threaded, and a task that calls waitUntilComplete deadlocks the whole pool.
  • Waking one worker on shutdown. shutdown changes a state every idle worker must see, so it needs signalAll or notify_all.
  • Letting shutdown drop queued work. Workers that exit on "closed" without checking the queue lose accepted tasks. Exit only when the queue is drained (shutdown) or the pool is stopping (shutdownNow).
  • Swallowing interrupts in the wrong place. An empty catch (InterruptedException e) {} inside a task hides shutdownNow; the task runs to the end and termination is late. In the worker's own wait, by contrast, the interrupt is only a cue to re-check the state.
  • Retiring a worker outside the lock. execute sees the leaving worker, starts no thread, and a task waits in the queue with nobody to run it.
  • Detaching retired threads in C++. A detached worker can still be running when the pool's destructor finishes, and it then touches a destroyed mutex. Park its handle and join it.

In the interview

The phone version asks for schedule and waitUntilComplete; the 2026 version starts from a bounded queue and adds a pool with the full lifecycle. Practise these follow ups: "a task throws", "add shutdown", "now shutdownNow", "what happens to interrupted tasks", "add a per-task timeout", "threads sit idle at night, give them back", "wait only for my tasks while others keep submitting".

One lock guards the queue, the pending count and the pool state, with two conditions: workers wait for work or shutdown, and waitUntilComplete waits for pending to reach zero. Tasks run outside the lock, inside a catch-all, and the pending decrement is in a finally block, so a failing task can neither kill a worker nor hang a waiter. Shutdown rejects new work and lets the queue drain; shutdownNow also hands back the queued tasks and interrupts the running ones, which is a request, so termination depends on tasks honouring interrupts.

If asked about timeouts, say first that no thread can be killed safely, then explain task-specific cancellation, the reassignment race and a bounded policy for uncooperative tasks. If asked about idle threads, describe the timed wait and why the worker must retire inside the lock.

Senior depth: the waiter that never finishes waiting

waitUntilComplete waits for "pending is zero". If other threads keep scheduling, pending may never reach zero, and the waiter starves even though its own tasks finished long ago. One fix is to wait for a snapshot of all accepted tasks, not for later submissions: give every task a sequence number when it is scheduled, keep the numbers of unfinished tasks in a sorted set, and wait until the smallest unfinished number is at least the next number at the moment you started waiting. Assign the sequence and insert it into the set in the same locked acceptance step. Remove it on completion or queued cancellation, and signal all waiters because their targets differ. This is not per-client waiting: explicit task groups or retained futures are needed for that. Keep sequence arithmetic from wrapping.

Two more senior notes. Java's ThreadPoolExecutor packs the run state and the worker count into one atomic int (ctl), so some state/count transitions use compare-and-set; worker-set and lifecycle bookkeeping still use locks, and it adds the states TIDYING and TERMINATED around its terminated() hook; your one-lock version is the honest interview equivalent. And a task that waits on another task in the same bounded pool can deadlock the pool when every worker is waiting; see the pool self-deadlock problem.

Key takeaways

  • One lock guards the queue, a pending count and the state; distinguish global idleness from a snapshot or task-group wait.
  • Run tasks outside the lock, inside a catch-all, with completion bookkeeping on every path: report ordinary task failures and retain worker capacity.
  • shutdown rejects new work and drains the queue; shutdownNow hands back queued tasks and only requests that running ones stop.
  • Interrupts land in four places; in the worker's own wait they mean "re-check the state", and stale ones are cleared between tasks.
  • Idle threads above core retire after a timed wait, and they must leave the worker set inside the same critical section; in C++ someone else joins them.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A worker finishes a task, decrements pending and signals allDone. There is one completion waiter. Which arrangement can lose a wakeup and leave that waiter asleep indefinitely?
Why. Even a protected read is insufficient if the waiter unlocks between checking and committing to a wait. The worker can decrement and signal in that gap; that signal reaches nobody, and the waiter then sleeps on a count that is already zero. Checking and waiting under the same lock, in a loop, closes the gap. signalAll is fine here; it only wakes more waiters.
In MiniPool, core = 2, max = 4, capacity is at least 3, and two workers are idle. Three tasks are submitted before any worker resumes or retires. What does poolSize() return immediately afterwards?
Why. The rule is "start a worker if queued tasks outnumber idle workers and the pool is below max". Task 1: 1 queued, 2 idle, so signal. Task 2: 2 queued, 2 idle, so signal. Task 3: 3 queued, still 2 idle (the signalled workers have not woken), so start a third worker. The third task triggers growth to 3 workers; any worker may claim any queued task. Counts 2 and 4 do not follow this sequence, and 5 exceeds max.
At the locked STOP transition, two workers have claimed T1 and T2, and T3, T4 and T5 are queued. With no concurrent shutdown caller, what does shutdownNow() do?
Why. shutdownNow removes and returns the tasks still queued at the transition, then requests a stop for claimed work without joining it. C++ stop callbacks run synchronously before the requesting call returns. Waiting is the job of awaitTermination. No thread is killed: a task that ignores the interrupt or the stop token runs to completion.
Why must an idle worker remove itself from the worker set inside the same critical section in which it decides to retire?
Why. execute decides whether to start a thread by looking at the worker count. If a worker decides to leave, releases the lock, and only later removes itself, an execute in that gap sees the old count (for example at max), queues the task and starts nothing. The leaving worker then exits and the task is stranded. Making the decision and the removal one critical section removes the gap.
You build submit(task) on top of execute. The task throws. Where should the exception go?
Why. The caller who submitted the work is the one who can act on its failure, and the future is the channel to that caller. completeExceptionally in Java and std::packaged_task in C++ store the exception. Java get() wraps it in ExecutionException; C++ get() rethrows the stored exception. Rethrowing on the worker kills or disturbs the worker for no benefit, and a shared error field reports the failure to the wrong caller.
Java onlyWhy does the Java MiniPool call Thread.interrupted() before handing a worker its next task?
Why. The interrupt flag belongs to the thread, not the task, and workers are reused. A well-behaved task that catches InterruptedException restores the flag before returning, and without a reset the next task's first sleep or take would throw at once. The pool's state, not the flag, says whether to stop. await() can throw on a set flag, but the boundary reset is also needed when a queued task is available without waiting. This static method clears status; it neither sets cancellation nor changes daemon status.
C++ onlyIn the C++ MiniPool, a worker that retires moves its own std::thread into retired_. Why not call join() or detach() on itself?
Why. Joining yourself is reported as a would-deadlock error. Detaching avoids the join, but then nothing guarantees the thread has finished before the pool's mutex and condition variables are destroyed, which is undefined behavior if it touches them. Parking the handle lets execute, awaitTermination or the destructor join it later, outside the lock.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Add waitUntilComplete(timeoutMs) to the executor: after acquiring the lock it waits up to that budget, returning true if it observes zero pending and false otherwise.
Model answer

The Java loop feeds the remaining time back into awaitNanos, so a spurious wakeup does not restart the clock. The C++ predicate overload does the same loop internally and returns the predicate's final value. Conversion in Java saturates rather than overflowing. Lock acquisition and scheduler delays are outside this waiting budget; it is not a strict bound on method duration.

Explain
Explain shutdown versus shutdownNow to an interviewer, covering: new submissions, queued tasks, running tasks, futures of tasks that never ran, and how the caller knows the pool has finished.
Model answer

Both reject submissions once their locked state transition occurs; a racing submission may be accepted first. Neither waits for task completion, though lock contention and C++ stop callbacks can delay return. shutdown is the orderly one: everything already queued still runs, running tasks finish normally, and the workers exit once the queue is drained. shutdownNow is the urgent one: it removes tasks still queued at that transition and returns them to the caller, and it interrupts the workers in Java or requests a stop in C++. That is only a request: a task blocked in an interruptible call or checking its flag or token stops early, a task in a tight CPU loop that never checks keeps running.

The tasks handed back by shutdownNow never ran, so if they were submitted with futures, their futures need a completion policy. Java callers must retain the future or use a task descriptor with a cancel action. In C++, destroying the last owner of an unrun packaged task makes its future ready with broken_promise. To know the pool has finished, the caller calls awaitTermination(timeout), which returns true once shutdown and worker retirement are observed, joining collected handles in C++. A timeout may indicate slow cleanup, scheduling delay or a task ignoring cancellation; it does not diagnose which one.

Debug
Find at least four bugs in this worker loop.
Model answer
  1. if instead of a loop around the wait. After a spurious or stolen wakeup, or after close wakes everyone, the queue can be empty: Java's removeFirst throws NoSuchElementException, and C++'s front() on an empty deque is undefined behavior. Wait in a loop on "queue not empty or closed".
  2. The task runs while holding the lock. Only one task runs at a time, and a task that calls back into the executor (for example waitUntilComplete) deadlocks it. Release the lock before running the task.
  3. No exception safety. If the task throws, Java leaves the lock held forever (no finally around unlock), so every other thread blocks, and pending is never decremented. In C++ the exception escapes the thread function and std::terminate ends the process. Catch everything around the task and do the bookkeeping afterwards.
  4. closed is read without the lock. In C++ that is a data race on closed_; in Java a plain field read may never see the update. Read it under the lock, inside the wait condition.
  5. Shutdown can lose work or hang. The loop exits on closed without draining the queue, and a worker asleep in the wait never wakes unless close signals all. Exit only when closed and the queue is empty, and have close wake every worker.

The fixed loop is the one in Version 1 above. Pool-wide completion waits must still come from outside the pool, because a worker cannot wait for its own unfinished task.

Out loudabout 90 s
"Walk me through shutdown and shutdownNow. Include a submission racing with shutdown and the futures of tasks that never run."
What a strong answer covers
  • Linearize acceptance and shutdown under the same mutex
  • Orderly shutdown rejects later work and drains accepted tasks
  • Immediate shutdown returns still-queued tasks and requests cancellation of claimed work
  • Distinguish Java interrupts from C++ cooperative stop requests
  • Resolve unrun futures explicitly and distinguish future completion from physical task exit
  • Wait for termination separately without promising a strict wall-clock bound
How a senior would say it
Both shutdown modes close admission; the difference is what happens to accepted work. I serialize submission and the state change under one mutex. If submission wins, its task is accepted. If shutdown wins, submission is rejected. Orderly shutdown keeps the queue and lets workers drain it. Immediate shutdown removes and returns tasks still queued, while requesting cancellation of work already claimed. A claimed task may not have entered its body yet, so the returned list is not every task whose body has not started. Java interrupts the worker. C++ needs a cooperative stop token or flag, and I request stop outside the pool mutex because callbacks can run synchronously. Neither mechanism safely kills an uncooperative task. I must also settle futures for removed work. In this Java wrapper the caller retains the futures, or I add task descriptors with a cancel action. In C++, destroying the last owner of an unrun packaged task produces a broken-promise error. A future reporting cancellation does not prove the task stopped. Finally, a separate termination wait observes worker retirement and performs the required joins. Its waiting budget does not eliminate lock contention or scheduling delay, and destruction must wait for all remaining access to the pool to end.

Likely follow up: What if a stop callback calls back into the executor?

"All my tasks finished, but waitUntilComplete is still blocked. What are your leading explanations?"
What a strong answer covers
  • Define global idleness and explain how other submissions extend the wait
  • Check exception-safe completion bookkeeping against queued plus claimed/running
  • Check for a lost wakeup between predicate inspection and waiting
  • Explain a sequence-boundary snapshot and out-of-order completion
  • Distinguish a snapshot from per-client task groups and forbid self-waiting
How a senior would say it
I would first check what completion means. This implementation waits for global idleness, so another client's submissions can keep pending above zero after my own tasks finish. Next I would check the invariant: pending equals queued plus claimed or running work. An exception path that skips the decrement leaves a permanent phantom task. Then I would inspect the wait protocol. Checking pending, unlocking, and later waiting without checking again can miss the final notification even if every individual access is protected. The predicate check and condition wait must form one locked protocol. If the requirement is a snapshot, I would assign sequence numbers at acceptance, capture the next sequence under the lock, and wait until no unfinished number is below that boundary. A total completion count is insufficient because later tasks can finish before earlier ones. Remove numbers on completion or queued cancellation and notify all relevant waiters. For only one client's tasks, I need explicit task groups or futures. Finally, no worker may wait for pool-wide completion that includes itself; its own task cannot finish while it waits.

Likely follow up: Why does waiting for a total of N completions fail when tasks finish out of order?

Out loudabout 75 s
"Add a per-task timeout. Can you just interrupt its worker and start a replacement?"
What a strong answer covers
  • A timeout bounds waiting or requests cancellation; it cannot safely kill a thread
  • Clarify whether the deadline includes queue time
  • Prevent a stale watchdog action from interrupting the next task
  • Distinguish FutureTask cancellation, CompletableFuture completion and per-task C++ stop sources
  • Keep uncooperative tasks counted and bound resources instead of replacing without limit
How a senior would say it
I would separate the deadline from actual task termination. A timeout can end the caller's wait and request cancellation, but it cannot safely kill a thread. First I would decide whether queue time consumes the budget or the clock starts when execution begins. The watchdog must target a particular task assignment. If it checks a worker, pauses, and interrupts after that worker starts another task, it cancels the wrong work. Clearing the interrupt flag between tasks does not close that race. In Java I would serialize assignment validation and interrupt delivery with completion and reassignment. A correctly used FutureTask already coordinates its own cancellation; cancelling the CompletableFuture wrapper here does not interrupt its computation. In C++, I would capture a stop source belonging to that task and request it outside the pool lock. If the task ignores cancellation, I keep counting it as running until it actually returns. Unlimited replacements would defeat the concurrency bound and exhaust resources. I would limit admission, report the stuck work, and use process isolation when hard termination is a requirement. Cancellation also cannot undo side effects already performed.

Likely follow up: How do timeout and successful completion race to publish exactly one result?
