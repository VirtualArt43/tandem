The toolkit: std::atomic and memory orders

Read atomic APIs, write a correct CAS loop, publish data with release and acquire, and know when an invariant still needs a mutex.

Asked atMicrosoftGoogleRubrik
Before this:The toolkit: std::thread, std::jthread and thread_localThe toolkit: mutexes and lock guards

An atomic variable gives indivisible operations on that variable. Choosing which operation you need, and whether it must order other memory accesses, is the part that turns syntax into a correct algorithm.

In plain words

A ticket dispenser can hand out one ticket without two people receiving the same number. It does not automatically update the seating chart and payment ledger as one transaction. Atomics are excellent ticket dispensers; multi-record agreements need a larger protocol.

Why this matters for concurrency

Core lessons use atomic counters, stop flags, publication pointers, and compare-and-swap loops. You must recognize each call without assuming every atomic access makes the whole algorithm safe. Continue with atomics and CAS, CAS loops, and memory ordering for proofs and harder algorithms.

One atomic operation versus several

Initialize explicitly, for example std::atomic<int> count{0};. Prefer named load and store calls while learning, because they show where shared accesses happen. An atomic object cannot be copied into another atomic by its copy constructor; copy the loaded value if you want an independent new atomic value.

Construct the atomic before publishing it to other threads: construction itself is not atomic. The primary std::atomic<T> template requires a trivially copyable type that also satisfies its copy/move construction and assignment requirements; it cannot wrap an arbitrary std::string or container. A supported small struct can hold combined state, but its operations may use an internal lock.

count.store(count.load() + 1) contains a load and a separate store. Two threads can load the same value and overwrite each other's increments, even though neither access is a C++ data race. count.fetch_add(1) performs one indivisible read-modify-write and returns the previous value. Distinguish a race in the larger algorithm from an unsynchronized ordinary-memory data race.

For std::atomic<int>, count++, ++count, and count += 1 each perform one atomic read-modify-write with default ordering. Postfix increment and fetch_add return the old value; prefix increment and += return the new value. count = count + 1 still separates the load from the store. C++ volatile provides neither atomicity nor inter-thread synchronization; a conflicting ordinary access without happens-before can be a data race, which is undefined behaviour.

exchange(true) can claim an action once: the returned old boolean tells you whether someone already claimed it. Claimed does not mean finished. A losing caller cannot safely use results the winner writes after that exchange; use a separate completion protocol or std::call_once for initialization.

A pointer atomic protects the pointer value, not the pointed-to data or its lifetime. Loading a pointer and then dereferencing an object another thread freed is still invalid.

CAS loops and the expected argument

Compare-and-swap is spelled compare_exchange_weak or compare_exchange_strong in C++. Pass a local expected value by reference and the desired replacement by value. Success stores desired, leaves expected unchanged, and returns true. Failure performs no modification of the atomic and updates expected with the observed value; weak CAS may fail spuriously even when the representations match.

Recompute desired after every failure. Do not keep deriving it from a stale original value. Place irreversible side effects after a successful claim, or design compensation: a CAS loop can execute its speculative computation many times. Strong CAS is convenient for a one-shot comparison when a spurious failure would require extra handling; it does not make a multi-step algorithm correct by itself.

Relaxed is sufficient here because remaining is the entire shared admission state; no unrelated payload is published by the claim. Each worker writes a distinct won element, and main reads them after joining. The range is deliberately small, so computing expected - 1 cannot overflow. In real counters, define exhaustion: integer atomic fetch_add has defined wraparound even for signed types, but ordinary signed arithmetic used to compute a CAS replacement can overflow with undefined behaviour.

Memory orders: start with the default, weaken with a proof

C++20 name in stdUse and limitation
memory_order_seq_cstThe default. Adds a single order for sequentially consistent operations, alongside their acquire/release effects.
memory_order_relaxedAtomicity and the atomic object's modification order, without publishing unrelated ordinary memory.
memory_order_releaseFor stores and read-modify-write operations that publish earlier work.
memory_order_acquireFor loads and read-modify-write operations that observe a suitable release and then consume its earlier work.
memory_order_acq_relBoth sides on a read-modify-write operation; not a load-only or store-only order.
memory_order_consumeC++20's dependency-ordering option; prefer acquire in this course rather than relying on fragile dependency reasoning.

A release and acquire must connect through the same atomic communication: the acquire observes the release's value or an appropriate release sequence. In C++20, that sequence can continue through consecutive read-modify-write modifications by any thread, even relaxed ones; an intervening plain atomic store ends it. Merely using release and acquire on unrelated atomics does not connect threads.

A release store of a ready flag can publish preceding ordinary payload writes to a reader that observes it with acquire. A relaxed statistics counter generally needs no such payload relationship. Relaxed does not mean approximate arithmetic: after joining every incrementing thread, a relaxed load still sees the final count, provided there were no resets or overflow.

Loads and atomic waits cannot use release or acq_rel. Stores cannot use acquire, consume, or acq_rel. A CAS has a successful read-modify-write order and a failed-load order; failure cannot use release or acq_rel. Common pairs are seq_cst/seq_cst, acq_rel/acquire, and relaxed/relaxed, depending on the proof. Use defaults until you can explain the specific ordering edge you need.

With one explicit order argument, CAS derives its failure order: acq_rel becomes acquire, release becomes relaxed, and other orders remain the same. With no order argument, both paths use seq_cst. The orders belong to individual calls, so a later load does not inherit an earlier store's ordering.

Sequential consistency is a stronger default, not a global lock on your program. Two sequentially consistent atomic balances still cannot make a transfer between them one indivisible operation. An observer may see the debit before the credit. Protect the cross-field invariant with a mutex, or encode the complete state in one suitable atomic representation with a proven update protocol.

Acquire/release also does not give all atomics one shared order. With x and y initially zero, A can release-store x = 1 then acquire-load y, while B release-stores y = 1 then acquire-loads x: both loads may return zero, because neither observes the other's release. Making all four operations seq_cst forbids that result: no single order respecting both threads' statement order can put each load before the other thread's store. See the C++20 ordering rules.

C++20 atomic wait and notify

The writer changes the value before notifying. If publication happens before the reader enters wait, the differing value lets it return without needing a remembered notification. Internal wakeups may be spurious, but the API returns only after it observes a different value. Notification alone with an unchanged value does not fulfill that condition.

Notification is not the publication edge. The release store and observing acquire operations publish payload.value; changing both sides to relaxed would leave its ordinary read and write without happens-before. A store alone need not wake an already blocked waiter. If several readers wait for the same one-time publication, use notify_all() so none remain blocked.

A value that changes away and back can be missed, the ABA limitation. A generation counter can reveal that changes occurred, subject to wraparound, but does not deliver each event; use a queue when every event must be processed. There is no timed atomic wait in C++20; use a condition variable for timeout contracts. This example never clears the pointer, and the payload outlives both workers; reusable pointer structures need memory reclamation.

For C++17, replace this wait protocol with a mutex, a condition variable, and a ready predicate protected by that mutex. The writer updates the predicate while holding the mutex, then notifies; the reader uses predicate-based wait. An atomic predicate alone does not close the condition variable's check-to-sleep gap. Use joined std::thread workers instead of std::jthread.

atomic_flag and a small spin mutex

std::atomic_flag guarantees lock-free test_and_set, clear, and test; std::atomic<bool> has no universal lock-free guarantee. A spin mutex repeatedly attempts to set the flag, using acquire to obtain ownership and release when clearing. Its lock method still blocks algorithmically while another owner holds it. A lock-free operation does not make this lock a lock-free algorithm, and yielding does not guarantee fairness.

The inner relaxed test reduces repeated read-modify-write traffic while the flag is busy. It does not remove spinning, preemption hazards, starvation, or cache contention. Use std::mutex for ordinary application critical sections unless measurements and scheduling assumptions justify spinning. The core spinlock lesson examines those costs.

For C++17, omit the inner test loop and yield after each failed test_and_set; this increases write traffic. ATOMIC_FLAG_INIT initializes the flag clear in both versions. C++20 also adds wait and notifications to atomic_flag, but a call to wait can block even though the flag's state operations are lock-free.

atomic_ref has a storage and lifetime contract

std::atomic_ref<T> wraps an existing trivially copyable object. Respect required_alignment, which may exceed that object's normal alignment, and keep the object alive longer than every wrapper. While any wrapper exists, all accesses to that object must go through such wrappers, even in one thread. Do not simultaneously reference a whole object and one of its subobjects with separate wrappers. See the C++20 atomic reference requirements.

After the workers' wrappers are destroyed and the workers joined, the sample safely reads existing normally. Wrapping only one writer does not repair ordinary concurrent readers. C++17 has no atomic_ref: use owned atomic storage or protect all accesses to the existing object with one mutex.

Atomic specializations have different supported operations. Atomic pointer arithmetic moves by elements but does not check array bounds or protect object destruction. This Mac's installed libc++ lacks the C++20 std::atomic<std::shared_ptr<T>> specialization; do not infer library support from language mode alone.

Worked example: why two atomic fields are insufficient

Start with available equal to 1 and reserved equal to 0. One operation decrements available, then increments reserved. A snapshot between those operations sees zero in both, violating the invariant that their sum remains one. Sequential consistency permits exactly that interleaving. A single mutex around the transition and snapshot preserves the pair; changing each individual field to atomic only removes individual data races.

Common mistakes

  • Atomic load plus store used as an increment: use one read-modify-write.
  • Ignoring CAS's updated expected argument: retry from the observed state.
  • Choosing relaxed for a ready flag that publishes ordinary data: establish a release/acquire edge.
  • Using an atomic pointer as a reclamation scheme: lifetime remains a separate problem.
  • Calling a spinning lock lock-free because its flag is lock-free: distinguish instruction support from algorithmic progress.

In the interview

Expect a counter to repair, a bounded claim to implement, or a publication flag to justify. Microsoft and Google reports include atomic counters; Rubrik reports include a thread-safe stack followed by a CAS version. Be ready to identify the precise state transition and explain every access to associated ordinary data.

I will first identify the atomic state transition. For a counter that publishes no other data, relaxed can be sufficient. For publication, I need an acquire that observes the release. For an invariant across fields, I begin with a mutex rather than assuming individual atomics compose.

Follow ups: why can weak CAS fail, what changes in expected, which CAS failure orders are valid, and when can a waiter miss a change? For performance, explain that weaker ordering does not remove contention on one hot counter; consider per-thread accumulation when you only need a final sum.

Senior depth

A lock-free implementation guarantees system-wide progress, not a bounded completion time for your thread. A retrying CAS algorithm can starve one caller; wait-free is the stronger per-operation bound on steps. A true is_lock_free() result says nothing about fairness, allocation, or blocking elsewhere in your algorithm.

C++20 CAS compares value representations, not operator==; padding bits that never participate in the value representation are ignored. Distinct floating-point representations such as positive and negative zero can compare equal numerically yet fail CAS. Strong CAS removes spurious comparison failure; it does not detect a pointer changing from A to B and back to A. A version tag can detect such ABA until wraparound, but safe reclamation remains separate.

Key takeaways

  • Atomicity of each operation does not make a sequence atomic.
  • CAS updates expected on failure; weak CAS belongs in a valid retry protocol.
  • Memory ordering governs relationships to other accesses.
  • Atomic waiting needs a changed value and notification, with ABA and timeout limits.
  • Atomic pointers and atomic_ref still require valid storage lifetimes.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Explain why the bounded claim CAS loop never allows more than three successful claims.
Model answer
Every success atomically changes a positive remaining value to one less. With no replenishment, only one contender can succeed for each value. Failed contenders receive a new expected value and retry only while it is positive, so zero is never decremented. The only successful transitions are three to two, two to one, and one to zero; failed attempts do not consume a claim.
Explain
Why is the ordinary payload read safe in the pointer-publication program?
Model answer
The payload write is sequenced before the release pointer store. The reader observes publication with acquire before reading the payload. That establishes the required ordering, and the pointed object remains alive until both threads are joined. The pointer never reverts to null in this one-shot example.
Design
Can you make an existing shared int safe by using atomic_ref only in the writer?
Model answer
No. The storage must meet alignment and lifetime requirements. While any wrapper exists, every access to the referenced object must go through such wrappers, including accesses in the creating thread. Ordinary concurrent readers are not repaired by one atomic writer. Change the whole access protocol or use a mutex.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"How would you explain compare_exchange_weak and its expected argument?"
What a strong answer covers
  • Compare and replace is one atomic operation
  • Failure updates expected
  • Weak can fail spuriously
  • Retry recomputes desired and checks the operation remains valid
How a senior would say it
Compare exchange checks whether the atomic still matches my expected value and, on success, replaces it with the desired value in one step. Expected is passed by reference. On failure it receives the observed value, which gives my next attempt a new starting point. The weak form may fail spuriously, so it is normally used in a loop that tolerates that. I recompute desired after failure and check whether the business condition still permits a change. I also keep irreversible side effects outside the speculative retry, because the loop body can run several times.

Likely follow up: When would you choose the strong form?

Out loudabout 60 s
"Choose memory orders for a statistics counter and a flag publishing ordinary data. Why might your choices differ?"
What a strong answer covers
  • Independent counting needs atomic arithmetic
  • Publication also orders unrelated memory
  • Release must be observed by acquire
  • Lifetime and multi-field invariants remain separate
How a senior would say it
An independent statistics counter needs increments not to overwrite each other, but it may not need to order any other data. Relaxed can provide that atomic arithmetic. A publication flag has a second job: it tells the reader that ordinary payload writes are ready to use. I need a release operation and an acquire that observes that publication to establish the ordering. Merely making the flag atomic is not enough. I would still check payload lifetime and whether the publisher modifies it again. Atomics do not automatically protect a larger multi-field invariant either.

Likely follow up: Does sequential consistency make two balance updates a single transfer?

Out loudabout 60 s
"We call notify_all() but an atomic waiter stays blocked. What do you check?"
What a strong answer covers
  • Check the atomic value changes before notification
  • Wait returns only after observing a value different from its argument
  • Transient changes can be missed through ABA
  • Notification does not supply publication ordering
  • Use a condition variable when a timeout is required
How a senior would say it
I first check the value, because notification is not a stored event. If the atomic still equals the value passed to wait, the call keeps waiting. I change the value before notifying and check whether another thread can change it back, hiding the transition. A generation counter can help detect a change, while a queue is needed to preserve individual events. I also check the release and acquire operations: notification does not publish ordinary payload data by itself. If this operation needs a timeout, I choose a condition variable because C++20 atomic wait has no timed overload.

Likely follow up: How would you wake several readers after one-time publication?
