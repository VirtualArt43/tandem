The STL for coding rounds: algorithms, heaps, hashing and traps

Choose STL operations, write correct comparators and pair hashes, parse input safely, and recognise the traps before adding threads.

Before this:STL containers, complexity and iterator invalidationLambdas, captures and callables

You remember how to put values into a vector. The interview tests whether you can get the right values out: the next deadline, the best three candidates, the last version before a timestamp, or every distinct request, without a hidden correctness bug.

In plain words

Imagine organising application forms. Sometimes you need the whole pile alphabetised. Sometimes you only need the three highest scores, and sometimes you keep accepting forms while always knowing which one to handle next. Sorting every pile every time wastes work; choosing the wrong rule for equal scores can lose somebody's place.

The standard library supplies the tools. Your job is to state what must be true when the operation finishes, then choose the tool that promises it.

Why this matters for concurrency

A scheduler orders deadlines, a cache hashes keys, and a metrics reader selects a top-k snapshot. A lock cannot repair an invalid comparator or a dangling view. Conversely, a correct STL operation does not make a sequence of shared operations atomic.

The container lesson covers storage and general invalidation rules; lambdas and callables covers capture syntax. Here you apply those tools. Programs run as C++20 and also work in C++17. Numeric rules belong to types, casts and initialization, and representation details belong to memory and object layout.

API card: algorithms by the promise you need

Ranges are half open: [first, last) includes first and excludes last. An empty range has first == last; end() is never an element. Costs below describe sequential overloads, with n elements and constant-cost comparisons.

Sorting: define ties before writing the lambda

For sorting, comp(a, b) answers "does a belong before b?" A strict weak ordering requires comp(x, x) to be false, forbids both directions being true, and requires transitivity. Equivalence, defined by neither direction being true, must also be transitive. This is the standard's ordering contract.

Use a.score < b.score, never a.score <= b.score. Returning a.score - b.score is wrong too: C++ wants a Boolean ordering, so both positive and negative differences become true, and subtraction can overflow. Compare fields directly, then a tie breaker. Freeze external scores first; a comparator must not change its answer mid-operation.

For floating-point scores, reject NaNs or explicitly order them as a separate group. Ordinary < on a domain containing NaNs and distinct numbers is not a strict weak ordering: NaN compares equivalent to both 1 and 2, but 1 and 2 are not equivalent. A tie breaker alone does not repair that inconsistent equivalence.

The named comparator prints C A B; the stable sort prints C B A. Stability preserves comparator equivalence, not necessarily operator==. Use it when the input already encodes arrival order; ordinary sort makes no promise about those ties.

Selection: a rank, a sorted prefix, or the whole order

For the kth smallest value with one-based k, select begin() + (k - 1) after checking 1 <= k <= size(). For a prefix of k smallest values, partition at begin() + k and take the k elements before it. Duplicates count separately. Include an identifier in the comparator if tied records need deterministic selection.

For k largest values use std::greater<>. partial_sort already sorts its retained prefix; nth_element followed by prefix sorting takes average O(n + k log k), not worst-case linear selection. Both mutate their input, so copy first if the original order must survive.

Bounds: find a boundary, then handle absence

With ascending numbers, lower bound means first value at least x, upper bound means first value greater than x. Their difference on a vector counts copies of x. To find the last value at most x, take the predecessor of upper bound, but only if it is not begin().

These algorithms need a range partitioned for the query; keeping it sorted with the same comparator is the practical reusable contract. With descending order, lower bound means first value at most x. A mismatched comparator breaks the precondition; it is not a reliable "not found" result.

Use member bounds on a set or map. Generic std::lower_bound(s.begin(), s.end(), x) has logarithmically many comparisons but can require linearly many iterator steps; it cannot navigate the tree's private links. A map's iterators expose pairs, while m.lower_bound(key) searches keys directly. The standard's binary-search requirements distinguish comparison count from traversal cost.

std::prev(end()) needs <iterator> and a nonempty container. For ascending keys it is the maximum; with descending order it is the minimum. Set elements and map keys cannot be assigned through iterators; remove and reinsert to change a key. Comparator-equivalent keys count as the same key even if other fields differ.

std::multiset and std::multimap retain equivalent keys. Their erase(key) removes every match in O(log n + count); to remove one, use find and erase that iterator only if it is not end(). equal_range(key) returns both bounds. Traversing or measuring that range on a tree is linear in the number of matches, unlike subtracting vector iterators.

C++20 contains(key) checks membership without inserting; C++17 uses find(key) != end(). try_emplace skips mapped-object construction on a hit, but m.try_emplace(key, expensive()) still evaluates expensive() before the call. Passing constructor arguments avoids building a mapped object unnecessarily; the function is not a lazy factory or a synchronization primitive.

The expiry loop consumes the iterator returned by erase, applying the invalidation rule. Vector erase also invalidates everything at or after the position, including the old end; reacquire those boundaries. For bulk vector filtering, use erase with remove_if, or C++20 std::erase_if, rather than repeated O(n) shifts.

Brackets deliberately insert an empty string above; integer mapped values start at zero. Use find for non-inserting lookup. Adding locks comes later in check then act and concurrent hash maps; a lookup that inserts cannot run under a readers-only lock.

Linear tools: sums, deduplication and reverse traversal

unique removes only adjacent duplicates. Sort first for global deduplication when reordering is allowed, then erase the unused tail. Values in that tail are valid but unspecified, not necessarily "the duplicates". If original order matters, scan with a separate seen set.

std::accumulate(..., 0) accumulates in int even if you assign the result to long long. Choose 0LL before the arithmetic, and prove the total fits. Signed overflow is undefined behaviour. Inside a custom fold, widen before multiplication too; a wide accumulator cannot repair a product that already overflowed in int.

size_t is unsigned: subtracting one from zero wraps to a huge value, and i >= 0 never ends an unsigned loop. Starting at size() and subtracting only after i > 0 also handles an empty vector. Reverse iterators, rbegin() and rend(), avoid index arithmetic when you only need traversal.

Enumerate permutations without missing the first one

Sort first, process the current arrangement, then advance. A while (next_permutation(...)) loop alone skips the starting arrangement. Equal values do not create duplicate arrangements; an empty range has one empty arrangement in this enumeration. The factorial number of arrangements is the limiting cost.

Heaps: the comparator direction you must explain

Type and headerOperationOne-line semantics
priority_queue in <queue>empty(), size(), top()Inspect in O(1); top returns a const reference and requires nonempty.
priority_queuepush(x), emplace(args...)Add with O(log n) heap comparisons; vector growth may also relocate O(n) elements.
priority_queuepop()Remove the top in O(log n), returning nothing; requires nonempty.
priority_queue<T, vector<T>, Compare>Comparator choiceless<T> by default exposes the maximum; greater<> from <functional> exposes the minimum.

A binary heap exposes one extremum, not sorted iteration. Think "comp(a, b) true means a has lower priority than b" for the adaptor. For earliest deadline first, return a.due > b.due; add a sequence number for FIFO ties. The priority queue specification requires a strict weak ordering here too.

Assign sequence numbers monotonically in the same critical section as insertion with concurrent producers, and define an overflow policy. A heap is not stable without a tie breaker. There is no arbitrary erase or decrease-key API; use lazy stale entries or another structure. A comparator consulting changing external priorities breaks the existing heap ordering even if those reads are atomic.

For lazy cancellation or rescheduling, keep immutable (deadline, id, generation) entries and an authoritative table of live generations. Skip a popped entry if its id is cancelled or its generation is obsolete; coordinate table changes and heap access under the same lock. Rebuild periodically to bound stale storage, or use a set of (deadline, id) plus an id-to-iterator index for direct O(log n) updates. A burst of stale entries can make one lazy pop slow.

Keep empty, copying top, and pop under one lock when shared, then execute the removed task outside it. The queue orders removal; multiple workers can start or finish those tasks in a different order. Waiting and waking for deadlines belongs to scheduled executors; these integers describe order, not clocks.

Use the heap algorithms when you need the storage

In <algorithm>, make_heap builds a heap in O(n) comparisons; n separate insertions can take O(n log n). After appending a value, push_heap restores heap order using the existing heap prefix. On a nonempty heap, pop_heap moves the top to the last position and repairs the prefix, but does not erase anything; copy or move from back(), then call pop_back(). Use the same comparator throughout.

sort_heap consumes heap order to produce sorted order in O(n log n); heap updates require rebuilding the heap afterwards. A heap over your own vector also permits moving a move-only task from the extracted back element. priority_queue::top() returns a const reference, so std::move(top()) cannot normally move a unique_ptr or another type requiring a non-const move source.

Worked example: keep the largest three values from a stream

Use a min heap containing at most k values. Its top is the weakest retained candidate. After inserting, remove the minimum if oversized. For 7, 2, 9, 5, 9 and k = 3, the retained multisets become {7}, {2, 7}, {2, 7, 9}, {5, 7, 9}, {7, 9, 9}.

The invariant: the heap contains the largest min(k, seen) values. The only discard needed is the smallest of the old winners plus the newcomer. For k at least 2 this is O(n log k) time and O(k) storage, plus O(k log k) to drain it; you never store the whole stream.

For a concurrent leaderboard snapshot, copy scores under the protecting lock, release it, then select the owned copy. The result describes that snapshot, not every update made while sorting. Snapshots and concurrent iteration develop that contract.

Hash a pair without changing what equality means

C++20 does not supply a general std::hash<std::pair<int, int>>. Pass a callable as the unordered map's third template argument. Equal keys must have equal hashes; unequal keys may collide, and equality resolves that hash collision. Ordinary pair equality already compares both fields.

Mix both hashes in order. Plain XOR makes (a, b) and (b, a) collide systematically. The mixer below is a practical non-cryptographic example, not protection against adversarial keys. Its unsigned size_t arithmetic may wrap, which is defined.

Brackets are intentional for counting: zero is the desired missing value. For an undirected edge, canonicalise insertion and lookup to (min(a, b), max(a, b)); changing only the hash does not change equality. Custom equality and hashing must agree. Never depend on unordered iteration order or stable hash values across runs.

Set max_load_factor before reserve if changing it. Reservation plans buckets, not constructed elements, and does not eliminate collisions or all future allocations. Rehash invalidates iterators but preserves pointers and references to surviving elements; erasure invalidates those too. Stability across rehash does not permit unsynchronized access during mutation. For adversarial inputs, a tree offers O(log n) comparisons; hashing and comparing long string keys also cost time proportional to the characters inspected.

<string>getline(stream, text, delimiter)Read up to a delimiter, consuming but not storing it; newline is the default.

A string view owns no characters. Copying it copies the address and length; capturing a view by value does not keep its source alive. string::substr makes an owning copy, while string_view::substr makes another view. std::string_view v = owned.substr(0, 3) dangles when the temporary substring dies.

A view's data() need not be null-terminated at its boundary. The source must remain alive and its storage valid; editing live characters changes what the view sees, and a concurrent writer requires synchronization. These are borrowed range semantics, not ownership.

Check find against npos before adding offsets: npos + 1 wraps to zero. substr throws out_of_range when its starting position exceeds the size, but clips an oversized count. remove_prefix(n) and remove_suffix(n) require n no greater than the view's size; they do not perform checked slicing.

The boundary read is safe here because the original string still contains = there; it shows why the slice is not a C string. Queue an owned std::string when the input buffer may be reused. These APIs count bytes, not user-visible characters; reversing bytes is not general Unicode text reversal.

Parsing: accept a whole field or reject it explicitly

stoi("42ms") returns 42 and stops before m. Check pos to reject trailing characters. No conversion throws invalid_argument; a value outside int throws out_of_range. Leading whitespace and a sign are accepted; reject them separately if forbidden by your grammar. Use stoll for long long fields.

Extraction with >> skips leading whitespace and leaves terminating whitespace in the stream, so an immediately following getline can return an empty line. To discard the rest of the current line, ignore through its newline. getline(in >> std::ws, line) instead skips all leading whitespace, including blank lines, which changes the grammar.

Drive the loop with the read operation, never while (!stream.eof()): EOF is discovered by a read. Numeric extraction can accept prefixes too; for strict tokens, read each as a string and validate the whole token. On failure, reject input or clear the error and skip to a defined recovery boundary; clear() resets flags, not the read position or input buffer.

C++17 integer from_chars in <charconv> parses a pointer range without copying a view into a string or throwing on conversion errors. It skips no leading whitespace and accepts a minus sign for signed integers, but no leading plus. Check both the error code and complete consumption, as specified by the C++20 conversion contract.

Common mistakes

  • Sorting with <= or subtraction. Use strict field comparisons and explicit ties.
  • Binary search after nth_element. The partitions are not sorted; sort the searched range first.
  • Generic bounds on tree iterators. Use member bounds for logarithmic traversal.
  • Treating unique as erase. Erase its tail; sort first only when reordering is allowed.
  • A max heap for streaming largest k. Keep a min heap to discard the weakest winner.
  • Lookup through map brackets. Missing keys are inserted; use find when absence should remain absence.
  • Unsigned reverse loops and narrow accumulators. Guard before subtraction and choose 0LL before adding.
  • Incrementing an erased iterator or retaining top() across a pop. Consume the erase successor and copy the heap value before removal.
  • Queuing a copied view of a reused buffer. The view still borrows; queue an owned string.

In the interview

Expect changes such as "the input is a stream", "ties must be FIFO", "support timestamp floor lookup", or "writers continue while you calculate top k". State the invariant, cost and result lifetime before choosing an API.

For a stored batch I would select with nth_element and sort only the winners. For a stream I would keep a size-k min heap. For shared scores I would take an owning snapshot under the lock, compute outside it, and describe the answer as a snapshot.
For a deadline queue the comparator returns true for a later deadline, so the earliest is on top. A sequence number breaks ties. Checking, copying and removing the top form one critical section.

Follow ups: "Can priorities change?" requires removal/reinsertion or stale-entry handling. "Is hashing always constant time?" requires average versus worst-case costs. "Can this result outlive the lock?" requires ownership, not just a const view. Continue into concurrent caches and scheduled executors for full threaded designs.

For "exact current top k", define current as one instant during the call. Copying all score values under their common lock already gives that snapshot, even if the calculation finishes later. To avoid selecting on each query, maintain an ordered (score, id) set alongside the id-to-score map, updating both atomically: O(log n) updates and O(k) traversal of winners under the lock, for constant-cost keys. No returned list can remain continuously current after later writes.

Key takeaways

  • Choose full order, sorted prefix, rank selection or streaming heap according to the required result.
  • Comparators require strict weak ordering; stability and deterministic ties are separate choices.
  • Use vector algorithms and tree member bounds; check boundaries before dereferencing.
  • Hash and equality must agree, brackets may insert, and erase changes iterator validity.
  • Use wide accumulators, guarded unsigned loops, owned strings when data escapes, and complete-field parsing.
  • A correct STL call still needs an ownership and synchronization contract when data is shared.

Quick check

Answer each question, then read why. Your score is saved for your module test.

v is {1, 2, 2, 2, 5}. What are the lower-bound index, upper-bound index and binary_search result for 2?
Why. Lower bound finds the first 2 at index 1; upper bound points past every 2 to index 4. The half-open interval has length 3. The last matching index, 3, is not the upper-bound index.
On a nonempty vector of integers, nth_element(begin, begin + k, end) finishes with 0 < k < size(). Which guarantees hold?Select all that apply
Why. The call selects and partitions, but does not sort either side. Its sequential comparison complexity is linear on average, not a worst-case linear guarantee. Sort the prefix if output must be ordered.
A deadline heap comparator returns a.due < b.due. After pushing deadlines 30, 10 and 20, what is on top?
Why. Less-than produces a max heap. Return a.due > b.due for earliest-first and add a sequence tie breaker for FIFO ties. Applying sorting's "before" intuition directly gives the tempting 10 answer.
A comparator is return a.score <= b.score;. What is the issue when two scores are equal?
Why. A value must not compare before itself. Less-than-or-equal says both equal values precede each other. Stability does not relax this contract; the result is not merely a different tie order.
After std::map<int, int> m; int value = m[7];, what are value and m.size()?
Why. Brackets insert a value-initialized int, which is zero. find leaves the map empty; at throws. Apparently read-only bracket access cannot be protected with only a shared reader lock.
On this Mac, where int is 32 bits, for std::vector<int> v{2000000000, 2000000000}, which sum is correct and safe?
Why. The initial value determines the accumulator type. 0LL makes this sum fit; converting after an overflowing int addition cannot repair undefined behaviour. Narrowing the valid result back to int cannot represent 4000000000.
A producer queues a string_view into its reusable input string. The consumer protects only the queue with a mutex and later prints the view. What is the correct review?
Why. A view copies an address and length, not ownership. The queue mutex does not protect the later lifetime and accesses to the backing buffer. Const access through the view does not make the source immutable.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
You need the largest k scores from n batch values, in descending order. Then the input becomes a stream. Choose algorithms and costs, and handle k = 0 and k greater than n.
Model answer

Clamp k to n, return empty for zero, partition at begin() + k if k is smaller than n, resize to k, then sort descending. This is average O(n + k log k), plus O(n) copying to preserve the original. partial_sort with greater<> directly gives a sorted prefix using O(n log k) comparisons for k at least 2. When k equals n, sort directly.

For a stream keep at most k values in a min heap; after insertion, pop if oversized. For k at least 2 it takes O(n log k) time, O(k) storage, plus O(k log k) to drain. Zero returns empty; fewer than k arrivals return all values. Duplicates remain separate unless distinct scores are required. Copy a shared batch consistently before selection outside its lock.

Write code
A map stores timestamp to version. Describe the code to find the latest version at or before t, returning absence if none exists, then erase timestamps strictly before cutoff. State locking and result-lifetime rules.
Model answer

Compute auto it = versions.upper_bound(t). If it == versions.begin(), no timestamp qualifies, including on an empty map. Otherwise std::prev(it) is the latest qualifying entry; copy its value into an optional<string>. Lookup costs O(log n).

Start expiry at versions.begin(). While the iterator is not end() and its key is less than cutoff, assign it = versions.erase(it). Never increment the erased iterator. Erasing r prefix nodes this way costs O(r) amortized. With writers, protect lookup through copying and the entire expiry traversal using the same mutex. If lookup and expiry must form one atomic operation, hold that lock across both. Return an owned value, not an iterator or view into an erasable entry.

Debug
A parser queues string_view fields from getline's reusable string, converts numbers using stoi(field), and totals them with accumulate(..., 0). Identify defects and repairs.
Model answer

The views borrow a reused buffer; they can observe overwritten bytes, dangle after reallocation, or race with writes. Queue owning strings or retain immutable owned backing storage through consumption.

stoi takes a string, not a string_view; explicit string(field) fixes compilation but still accepts numeric prefixes. Check the consumed position and handle invalid_argument and out_of_range. Finally, 0 selects an int accumulator. Use 0LL and prove the total fits in long long; assigning to a wide destination afterwards is too late.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"You have a batch of scores and need the largest ten. Now writers keep updating the scores. Walk me through your choice and what the answer means."
What a strong answer covers
  • Choose nth_element plus prefix sorting for a stored batch, or partial_sort
  • State average O(n + k log k), with no worst-case linear selection claim
  • Handle empty input, zero k, k greater than n, and ties
  • Copy scores consistently under the protecting lock and compute outside it
  • Describe the result as a snapshot, not as continuously current
  • Choose a bounded min heap when the input becomes a stream
How a senior would say it
I would take an owning snapshot of the scores, select the ten largest values, and sort just those winners. For a stored batch, nth_element followed by sorting the prefix takes average linear selection time plus k log k for the output order. I would not claim worst-case linear selection. partial_sort is another good choice when I directly want a sorted prefix. I clamp k to the number of scores and return empty for zero or empty input. If equal scores need deterministic winners, I compare an identifier after the score. With concurrent writers, I copy the scores while holding the lock that protects them, then release it before selection. Otherwise sorting or selecting would mutate shared data while writers use it. The result describes the copied snapshot; it does not include updates made later. If the input becomes a stream, I switch to a bounded min heap. Its top is the weakest retained score, so after inserting a new score I remove the minimum whenever the heap exceeds k.

Likely follow up: What changes if callers require an exact current top ten while updates continue?

Out loudabout 75 s
"My deadline queue runs the latest task first, and equal deadlines come out unpredictably. How would you debug and fix it before adding worker threads?"
What a strong answer covers
  • Identify the default max heap or a less-than comparator as the reversed-priority cause
  • Return true for a later deadline so the earliest is on top
  • Break ties with a monotonic sequence number and preserve strict weak ordering
  • Keep priority fields stable while entries remain in the heap
  • With threads, assign sequence and insert under one lock; check, copy top and pop together
  • Run outside the lock, recheck deadlines after wakeups, and distinguish removal from execution order
How a senior would say it
I would check the comparator: a default priority queue is a max heap. To expose the earliest deadline, I return true when the first deadline is later than the second. For equal deadlines I compare sequence numbers in the same direction, so the smaller sequence is removed first. I use strict comparisons; a heap does not otherwise promise FIFO ties. I test equal deadlines and a later deadline. Stored ordering fields must stay unchanged; updates need reinsertion or stale entries with validation. With concurrent producers I assign the sequence and insert under the same mutex. Workers check emptiness, copy the top and remove it within one critical section, then execute outside the lock. That guarantees removal order, not execution order across workers. A waiting worker rechecks the head after waking, because a producer may have inserted an earlier deadline.

Likely follow up: How would you support cancelling an arbitrary task without scanning the heap?

Out loudabout 60 s
"A producer queues string views, and the consumer sometimes logs the next request's text. The queue is locked. What do you check?"
What a strong answer covers
  • Identify borrowing from a reused input buffer as the likely cause
  • Explain that copying a view copies address and length, not ownership
  • Distinguish overwritten bytes, dangling storage after reallocation, and a possible data race
  • Explain why the queue lock alone does not protect later backing-buffer reads
  • Queue owning strings or retain immutable backing storage through consumption
How a senior would say it
I would check the lifetime and reuse of the backing input buffer first. A string view borrows characters; copying it into the queue copies an address and length, not the text. If the producer reads the next request into the same string, the consumer may see that new text. If the string reallocates, the old view can dangle. If the producer writes while the consumer reads those bytes, there is also a data race. The queue mutex protects insertion and removal, but it does not automatically protect later accesses to the buffer. My simplest fix is to queue an owning string so each request retains its text. If copying is too expensive, I would retain immutable backing storage until all consumers finish. I would test reuse, growth and delayed consumption, because a small happy-path input can hide this lifetime bug.

Likely follow up: Would capturing the string_view by value in a lambda fix its lifetime?
