Retain best cache

Thread-safe structuresmedium45 minLinkedIn

Keep high-ranked entries without letting a slow miss freeze every hit or make eight callers load the same key eight times.

The task

get(key) returns a cached entry or loads it from the supplied slow source. Capacity is positive and counts completed resident entries. Each immutable entry has a signed rank; higher is better. The source is thread-safe and does not reenter this cache.

  • When inserting a loaded entry into a full cache, evict the resident with the lowest rank. Break equal-rank ties by lowest integer key. Insert the newly loaded entry even if its rank is lower than the evicted resident's; this is an eviction rule, not an admission filter.
  • Concurrent misses for the same key join one in-flight load. Every joined caller receives that load's value or failure, even if the resulting resident is evicted before the caller wakes.
  • Failures are not cached. Existing joiners share the failed attempt; a later caller can retry. A Java waiter can be interrupted without cancelling the shared load.
  • Load outside the cache lock. A slow load cannot block hits on other keys, and loads of different keys can overlap. Published resident size never exceeds capacity.
  • size, cachedKeys and waiters are synchronized diagnostic snapshots. They must not return mutable internal containers. Allocation failure is outside the exercise.

Example: capacity 2 holds ranks 10 and 20. Loading rank 30 evicts rank 10; reading the rank-20 key remains a hit.

What the tests check

  • Lowest-rank eviction and retained-entry hits without another source call.
  • Eight same-key callers join exactly one blocked load.
  • Two different loads overlap while a cached hit completes, measured by an active-source counter.
  • A failed load wakes all eight joiners and a later call retries.
  • Eight seeded callers repeatedly miss and evict without exceeding capacity or returning another key's value.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Give a race for each locked section, as in the LinkedIn report.
Without atomic lookup and flight installation, two misses both load. Without atomic capacity check, eviction and insertion, two completions exceed capacity. Without synchronized result publication, a waiter can miss completion or read a partial flight.
Can eviction be faster than scanning every entry?
Maintain an ordered rank index under the same lock as the key map. Eviction becomes O(log C), but both indexes must change atomically and equal ranks need a deterministic tie rule.
What if ranks change?
This contract uses immutable ranks. Mutable ranks require explicit updates to the eviction index or carefully versioned lazy entries. Calling arbitrary rank callbacks while locked can introduce blocking or reentrancy.
What happens if a waiter is interrupted?
It stops waiting and releases its reference to the flight. It must not erase the flight or cancel a load other callers still need. The loader still publishes its result.
Does capacity also bound in-flight loads?
No. This contract bounds residents only. Add a separate admission limit for distinct loads, with timeouts and backpressure, if source fan-out or flight memory must also be bounded.
How does this differ from LRU or a distributed cache?
Ranking is independent of recency. Across processes, a local single-flight map deduplicates only within one process; global coordination, leases or accepting duplicate loads are separate choices.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The invariant

The resident map has at most C entries. The flight map has at most one loading attempt per key. A flight transitions once from pending to a value or error. Waiters retain that flight object until they observe completion, so eviction cannot erase the result they were promised.

Why the lock is short

A hit returns a value copy under the metadata lock. A miss either joins an existing flight or becomes its loader. Only the loader calls the source, outside the lock. Completion takes the lock again, evicts if needed, inserts, records the flight outcome and notifies. The source must not recursively request its own in-flight key, because it would wait for itself.

The reference scans residents to find the minimum rank, breaking ties by key. That keeps the cross-container invariant focused on residents and flights. An ordered rank index is a useful optimization after correctness. Failed loads skip insertion and eviction entirely, publish the exception to their joiners, and remove the flight so later calls may retry.

The broken interleaving

The broken version checks the resident cache under a lock, then loads outside it without joining an existing flight. A misses and starts loading; B misses before A publishes and starts a second load. Both return correct values and the capacity bound still holds, but eight simultaneous requests can produce eight source calls. The blocked-source burst test catches this even if the source is fast in ordinary runs. A failing burst also exposes the missing shared outcome.

Costs and limits

Java hits are expected O(1), C++ ordered-map hits O(log C). A full-cache insertion scans O(C) residents. Memory is O(C + F), where F is the number of distinct active flights, plus waiting callers. No test can prove absence of every race, but blocked-source gates force the same-key, independent-key and failure schedules instead of hoping they happen.

How to say it in the interview

I will keep resident values separate from loading flights. Misses install or join a flight under one short lock, and the loader runs outside it. Completion atomically evicts the lowest-ranked resident, publishes the value or error to that flight, and wakes its waiters.
