Thread-safe max stack

Thread-safe structuresmedium45 minLinkedInMicrosoft

A max stack has two views of the same nodes: stack order and value order. Concurrency is safe only when both views change together.

The task

Make the LeetCode 716 max stack linearizable. push appends to the top. pop removes the top and top observes it. peekMax observes the largest value. popMax removes the largest value, choosing the one closest to the top when several values tie.

  • Empty observation and removal return empty optionals. All signed int values are valid, including the minimum and maximum values.
  • Target O(log n) or better amortized operations, with O(1) top. Do not scan the whole stack for each maximum removal. Use a stack-order structure plus a value-order index.
  • Every operation protects the invariant spanning both indexes. A thread-safe map by itself does not make a compound node removal atomic.
  • validate() is an O(n) or O(n log n) locked diagnostic: check one-to-one node membership, values, and oldest-to-newest order within equal-value buckets. It is not part of the target operation cost. size() returns a synchronized snapshot. Allocation failure is outside the exercise.

Example: push 5, 1, 5. popMax() returns 5 and leaves 5, 1, so top() is 1. Removing the older 5 would violate the tie rule even though the returned value is the same.

What the tests check

  • The LeetCode sequence, newest-equal-maximum tie breaking, empty results and integer boundaries.
  • Two thousand seeded operations compared with a simple sequential model, including duplicate and negative values.
  • Eight active callers interleave unique pushes with pop and popMax; every value appears exactly once among removals.
  • After stress, the stack is empty and its full node/index invariant holds.
  • Bounded joins and a watchdog report hangs; C++ reference runs must be ThreadSanitizer clean.

Taught in: Invariants, critical sections and finding shared state

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What was the reported LinkedIn follow-up?
The reports ask Max Stack and then how to make it thread-safe. Name the invariant across the list and value index before choosing a mutex; merely replacing one map with a concurrent map does not protect both views.
How is Microsoft's maximum-frequency stack different?
The report concerns frequency, not numerical maximum. Its priority is frequency and then recency, so the secondary index is different. The transferable requirement is that frequency bookkeeping and stack membership change atomically.
Why does popMax remove the newest equal maximum?
That is the LeetCode contract. Store each value's nodes in insertion order and remove from that bucket's tail. Returning the same integer is not enough if the remaining stack order is wrong.
Could readers use a read-write lock?
Top and peekMax can use a shared read lock, but push and both removals mutate the list and index together. Benchmark before adding the complexity; tiny critical sections often favor one mutex.
How would you add a blocking pop with shutdown?
Add a not-empty condition and a closed flag under the same lock. Wait for nonempty or closed, signal after push, and wake everyone on close. Define whether close drains remaining nodes before returning an end result.
What if several callers do top followed by pop?
Those are two separate atomic operations. Another thread can change the stack between them. A caller that needs the removed value should use pop directly, or request an explicit conditional removal operation.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The invariant

Every live stack node appears exactly once in the value index, under its own value. Within each value bucket, nodes follow insertion order. The list tail is the most recently pushed surviving node. The largest bucket's tail is the newest surviving node with the largest value. One mutex protects all of these facts.

The reference representation

Java uses explicit doubly linked nodes and a TreeMap of deques. C++ uses a stable-node std::list and an ordered map of vectors of list iterators. Removing another list node does not invalidate those iterators. Pop updates the bucket for the list tail, while popMax looks up the largest bucket and unlinks its newest node directly. Empty buckets are removed immediately.

All returned results are values, so callers never hold an iterator into mutable storage. The lock covers the whole cross-index update; there is no unlock between removing from the rank index and unlinking from the list. Diagnostic validation checks identities and order, rather than only comparing sizes.

The broken result

The broken implementation chooses the oldest node in the maximum bucket. From [5, 1, 5], popMax still returns 5 but leaves [1, 5], making top return 5 instead of 1. It preserves the internal node invariant and remains race-free. The observable sequence test catches the semantic error that an exact-once stress test alone would miss.

Costs and testing limits

Push, pop and popMax use O(log D) ordered-map work for D distinct values, plus amortized O(1) bucket operations. Top is O(1); maximum lookup is O(log D) in the Java reference and constant-time access to the ordered map's last entry in C++. Storage is O(n). All mutations serialize; the active-worker counter proves concurrent demand rather than claiming simultaneous mutation of one representation.

Unique values in the concurrent test make lost and duplicated removals visible. Duplicate values in the sequential model test the tie policy. Neither replaces the other. A clean sanitizer run covers executed schedules only, so the notes state the locking invariant independently of test results.

How to say it in the interview

I will keep stable nodes in stack order and index those same nodes by value. The maximum bucket stores duplicates oldest to newest, so popMax removes its newest node. One lock spans both index updates, which makes each public operation atomic and keeps iterators internal.
