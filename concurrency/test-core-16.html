Why is "commit the database change, then publish the event to the broker" unsafe?
Why. These two independent commits are not atomic, so a crash between the writes leaves them disagreeing; retrying in the same process does not help if the process is gone. The event cannot overtake the commit here, because it is only published after the commit returns; that is the hazard of the opposite order, publish then commit. A consumer commits its dedup record and database effect in separate transactions. Depending on which it commits first, what can go wrong?
Why. The dedup record and the effect must commit atomically. Record first and a crash makes redelivery skip a missing effect; effect first and a crash lets redelivery repeat it. From: Idempotency, retries and exactly-once effects
Why use lease or session expiry when a remote lock must recover automatically from a crashed holder?
Why. A dead client cannot release its lock, so expiry is one mechanism for automatic recovery; other safe revocation protocols are possible. Expiry does not inherently make acquisition faster. The price is the opposite problem: a holder that is merely paused can outlive its lease while still believing it holds the lock, which is why leases do not remove the need for fencing.
