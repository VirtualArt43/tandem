Locks

2CorelockssemaphoresLinkedIn
Is a binary semaphore the same as a mutex?
Model answer

Both have two states, but the semantics differ in one way that matters: ownership. A mutex has an owner and only the owner may unlock it (std::mutex::unlock from another thread is undefined behavior; ReentrantLock.unlock from a non-owner throws IllegalMonitorStateException). A binary semaphore has permits, not owners: any thread may release.

That difference decides what each is good for:

  • A semaphore can signal: thread A releases when step 1 is done, thread B acquires before step 2. A mutex cannot do that.
  • Ownership enables things a semaphore cannot offer: reentrancy, priority inheritance (the OS can boost the owner only if it knows who the owner is), error checking (PTHREAD_MUTEX_ERRORCHECK catches double locking and foreign unlocks), and thread dumps that name the holder.

The classic bug: using a binary semaphore as a lock and releasing it twice on an error path. Java's Semaphore(1) does not enforce a binary maximum, so it can hold 2 permits and silently admits two threads into the critical section. C++20 std::binary_semaphore guarantees max() is at least 1, not necessarily exactly 1. Exceeding its actual max() violates the release precondition; even if 2 is representable, it breaks your binary protocol.

I use a mutex for mutual exclusion and a semaphore for counting or signaling. A binary semaphore used as a lock gives up ownership checks and priority inheritance.

Likely follow up: "Can a mutex be used for signaling between threads?" No: the thread that unlocks must be the one that locked.

3Corelocksjava
synchronized or ReentrantLock: when do you use which?
Model answer

Both are reentrant mutexes with the same memory semantics: a final unlock publishes prior writes to a subsequent successful acquisition of the same lock. A recursive acquisition does not itself hand ownership to another thread.

synchronized: block structured, released automatically even when an exception is thrown, less code, well optimized by the JVM, visible in thread dumps, and one wait set per monitor (wait and notify).

ReentrantLock adds:

  • tryLock() and tryLock(timeout): back off instead of deadlocking, or shed load.
  • lockInterruptibly(): a lock wait that can be cancelled.
  • Optional fairness (new ReentrantLock(true)).
  • Several Condition objects per lock, for example notFull and notEmpty.
  • Locking that is not block structured, such as hand-over-hand traversal.
  • Introspection: isLocked, getQueueLength.

Its cost is discipline: you must unlock in finally.

Java 21 adds one more reason: a virtual thread that blocks inside synchronized pins its carrier thread. For Java 21, prefer ReentrantLock where such pinning would hold a carrier through a long blocking operation; short in-memory synchronized sections need not be replaced automatically.

synchronized by default; ReentrantLock when I need timeouts, interruptible waits, fairness or several conditions.

Likely follow up: "Why is lock() called before try and not inside it?" If it were inside and threw, the finally would unlock a lock you never acquired and throw IllegalMonitorStateException, hiding the original error.

4Corelockscpp
lock_guard, unique_lock, scoped_lock and shared_lock: what is each for, and why not call lock() and unlock() yourself?
Model answer

All four are RAII guards: they manage lock ownership and release owned locks at scope exit, including during exceptions. Their default locking constructors acquire the lock; defer, try and adopt forms have different acquisition rules.

  • std::lock_guard: the simplest, one mutex, cannot unlock early, cannot move.
  • std::unique_lock: movable, can unlock and relock, supports std::defer_lock, std::try_to_lock and timeouts on a timed mutex. std::condition_variable::wait requires it, because waiting must unlock and relock.
  • std::scoped_lock (C++17): locks one or several mutexes at once, using a deadlock avoiding algorithm for several. A convenient choice for several; lock_guard remains a clear choice for one.
  • std::shared_lock: shared (reader) ownership of a std::shared_mutex.

With manual lock() and unlock(), any exception or early return in between leaves the mutex locked forever, and the next thread to lock it hangs. One more trap: a guard without a name, such as std::lock_guard<std::mutex>{m};, is a temporary that locks and unlocks within that one statement, protecting nothing.

Likely follow up: "Which guard do you use with a condition variable?" std::unique_lock, because wait has to release and reacquire it.

5CorereentrancyAmazon
What is a reentrant lock, and what happens if a thread locks a non-reentrant mutex it already holds?
Model answer

A reentrant lock lets its owner acquire it again; a hold count goes up, and the lock is free only after the same number of unlocks. Java's synchronized and ReentrantLock are reentrant, which is why one synchronized method can call another on the same object.

std::mutex is not. Locking it twice from the same thread is undefined behavior, often a self-deadlock: the thread waits for itself forever. An Amazon online assessment showed exactly this shape: a container's set() held its mutex and called resize(), which locked the same mutex again. std::recursive_mutex exists, but the better fix is structural: public methods lock, private helpers assume the lock is held.

Why recursive locks are a smell: the nested call runs while the outer method may be halfway through an update, so the callee can see a broken invariant, and the lock no longer tells you that.

Likely follow up: "Why did Java make reentrancy the default?" Object orientation: a subclass's synchronized method calls the superclass's synchronized method on the same object, which would deadlock otherwise.

6SeniorjavainternalsMicrosoft
How does synchronized work inside the JVM?
Model answer

A synchronized block compiles to monitorenter and monitorexit, with an exception path that releases the monitor. A synchronized method instead carries ACC_SYNCHRONIZED. An instance method locks this; a static method locks the declaring class's Class object. Those are different locks.

In Java 21 HotSpot, object-header state and runtime locking structures support a fast uncontended path. Exact mechanisms depend on the build, locking mode and JIT optimizations; do not equate the language keyword with exactly one CAS. Contention or wait() can require an inflated ObjectMonitor, with ownership, recursion and wait-set state. The runtime may spin before parking. Biased locking is absent in Java 21.

The JIT can eliminate locks on thread-confined objects and coarsen adjacent locking regions when observable semantics are preserved. Neither optimization weakens the specified happens-before edge from a monitor unlock to a subsequent acquisition.

Likely follow up: "Is synchronized slow?" Measure the workload. Uncontended operations can be inexpensive, while long critical sections, cache-line transfers, parking and scheduling dominate contended paths. Java 21 virtual-thread pinning during blocking inside a synchronized region is another cost. A thread dump reveals ownership and blocked entrants; Flight Recorder helps measure contention.

7Seniorinternalsfutex
How is a mutex built? Explain the fast path and the slow path.
Model answer

Fast path, entirely in user space: an atomic operation such as compare-and-swap changes a lock word from free to held. The uncontended path can avoid system calls; unlock may be a release store or an exchange, depending on the algorithm.

Slow path: if the CAS fails, spin a little in case the owner releases soon; then mark the word as "locked with waiters" (2) and sleep in the kernel. On Linux, futex(addr, FUTEX_WAIT, 2, ...) sleeps only if the word still equals 2, and that check-and-sleep is atomic inside the kernel, which is what prevents a lost wakeup. Unlock sets the word to 0 and, if it was 2, calls futex(addr, FUTEX_WAKE, 1, ...). Java's version is the AbstractQueuedSynchronizer (AbstractQueuedSynchronizer): a volatile int state changed by CAS, a FIFO queue of waiting threads, and LockSupport.park and unpark. ReentrantLock, Semaphore, CountDownLatch and ReentrantReadWriteLock are all built on it.

Likely follow up: "Why the third state?" The third state conservatively records possible waiters so uncontended unlock can skip notification. A two-state implementation can notify on every unlock; its library may still avoid a syscall internally.

8Seniortrylockfairness
When would you use tryLock with a timeout, and what does a fair lock cost?
Model answer

tryLock with a timeout is for three situations:

  • Deadlock avoidance when taking several locks: if the second lock is not available in time, release the first, back off with random jitter, and retry.
  • Bounded latency: a request handler returns an error instead of piling up behind a lock held by a stuck thread.
  • Load shedding: if the resource is that busy, skip optional work.

You must handle the false result, and in Java the timed version also throws InterruptedException. C++ has std::timed_mutex::try_lock_for and std::unique_lock with a duration.

Fairness: a fair ReentrantLock favors the longest-waiting queued thread under contention. It does not guarantee FIFO CPU scheduling or wall-clock arrival order across all calls. An unfair lock lets a newly arriving thread take a free lock ahead of queued waiters (barging). Barging can improve throughput by letting a running thread acquire before a queued thread is scheduled. Honoring the queue can leave a free lock waiting for a scheduled handoff and reduce throughput; the effect is workload-dependent. Unfair locks offer no starvation bound, while fairness can improve waiting-time variation.

Two details worth knowing: the untimed tryLock() barges even on a fair ReentrantLock, and std::mutex makes no fairness promise at all. Timeouts bound the requested wait, not actual return latency under scheduling delays, and repeated retries can livelock.

Likely follow up: "How would you get FIFO order without a fair lock?" A ticket lock, or an explicit queue of waiters, each waiting on its own condition.

9Seniorread-write-locksGoogleRubrik
When does a read-write lock help, and when does it hurt?
Model answer

It helps when reads vastly outnumber writes and read critical sections are long enough that letting readers overlap matters: for example, one thread updating a map of flight prices while many threads read it, a follow up Google has asked.

Writers must take the matching exclusive lock. It hurts when:

  • Critical sections are short: a read-write lock does more bookkeeping, and every reader still writes the shared reader count, so on many cores readers contend on that cache line and it can be slower than a plain mutex.
  • Writes are frequent.
  • The policy starves someone: reader preference starves writers; writer preference stalls readers.
  • A "read" actually mutates, such as an LRU get that moves the entry to the front; that operation needs the write lock, so the read lock buys nothing.

When you implement one (Rubrik has asked for exactly that), the interviewer probes the cases: reader or writer preference, reentrancy, and upgrade. ReentrantReadWriteLock can downgrade from write to read but cannot upgrade: a reader that asks for the write lock waits for all readers, including itself, forever. std::shared_mutex has no atomic upgrade or downgrade API and is not recursive. Release shared ownership, acquire exclusive ownership and revalidate; recursively acquiring it is undefined behavior.

Likely follow up: "What would you use instead for read-mostly data?" An immutable snapshot swapped atomically (copy-on-write), or StampedLock optimistic reads.

10Corelockscpp
What is the difference between std::mutex, std::timed_mutex, std::recursive_mutex and std::shared_mutex?
Model answer
  • std::mutex: exclusive and not recursive; lock, try_lock, unlock. The usual default; performance depends on the implementation and workload. Locking it twice from one thread, or unlocking it from a thread that does not hold it, is undefined behavior.
  • std::timed_mutex: adds try_lock_for and try_lock_until, for waits with a deadline.
  • std::recursive_mutex (and std::recursive_timed_mutex): the owner may lock again and must unlock as many times. Mostly for legacy code.
  • std::shared_mutex (C++17): lock for writers, lock_shared for readers, used through std::unique_lock and std::shared_lock. std::shared_timed_mutex (C++14) adds timeouts.

Shared facts: none promises fairness, the shared mutexes have no atomic upgrade operation, and none is copyable or movable (a mutex's address is its identity, and other threads may be blocked on it), so a class holding one is not copyable by default. Declare the mutex mutable so const member functions can lock it.

Likely follow up: "Which one would you reach for in a cache that is read 100 times per write?" Measure std::shared_mutex against std::mutex; for short lookups the plain mutex often wins.

11Seniormultiple-locksdeadlock
How do you lock several objects safely when you only learn at runtime which ones, and what is hand-over-hand locking?
Model answer

The rule is a global lock order: give every lock a unique, immutable key (an id, or an address in C++) and always acquire in ascending order. Threads that all acquire in the same order can never form a cycle, so circular wait, one of the four deadlock conditions, cannot happen. The general version handles a runtime set, assuming stable unique ids and one lock per account:

Deduplicate first: duplicate C++ nonrecursive mutex acquisition is undefined behavior. Java distinct() deduplicates by equals, so ensure that matches account identity and that distinct accounts do not alias one lock. In C++, std::scoped_lock(a.m, b.m, c.m) uses a deadlock-avoidance algorithm for a fixed set of distinct mutexes; for a runtime collection, sort by stable id or std::less pointer order and hold acquired locks in RAII guards. Multi-object updates still need exception safety; locking alone gives no rollback.

Hand-over-hand locking (lock coupling) is for walking a linked structure with a lock per node: lock node i plus 1 before releasing node i, never holding more than two. Every thread moves in the same direction, so the order is consistent, and operations on different parts of the list proceed in parallel. It needs non-nested unlocking, so in Java it requires ReentrantLock; nested synchronized blocks cannot express it.

Likely follow up: "What if two objects have no natural id?" In Java, order by System.identityHashCode and break ties with one extra global lock; in C++, compare addresses with std::less.

12SeniorgranularitystripingMeta
Coarse or fine-grained locking: how do you decide, and what did ConcurrentHashMap change between Java 7 and Java 8?
Model answer

Coarse: one lock for the whole structure. Easy to prove correct, and cross-structure invariants are easier to maintain, but every operation is serialized. Fine: a lock per part (shard, bucket, node, account). More parallelism, but operations that span parts (size, resize, iteration, moving an item between parts) need several locks in a fixed order or become approximate, and every lock costs memory.

Decide by measurement: start coarse with short critical sections; split only when a profile shows contention on that lock (threads blocked, throughput flat as cores grow). lock striping is the usual split: N locks, each key mapped to hash(key) % N.

ConcurrentHashMap shows the progression. Java 5 to 7: 16 segments by default, each a ReentrantLock guarding its own small table, so up to 16 writers in parallel. Java 8: no segments; inserting into an empty bin is a lock-free CAS, otherwise the writer locks only that bin's first node with synchronized, with special protocols for tree bins and resizing; ordinary retrievals generally do not block. The bin-level description is an implementation sketch, not the whole Java 21 algorithm. In a Meta design round for a single machine memcache, sharding the table into roughly one part per core, "to be able to lock more efficiently", was what the interviewer praised.

Likely follow up: "How many shards?" A small multiple of the core count, a power of two, then measure.

13Seniorlocksdesign
Why should you never call callbacks, listeners or other unknown code while holding a lock?
Model answer

Because you do not know what that code does. It may:

  • take other locks, creating a lock order deadlock with code you have never seen;
  • call back into your object, which self-deadlocks on a non-reentrant lock, or, with a reentrant lock, mutates your state while your invariant is temporarily broken;
  • block on I/O, so every thread waiting for your lock now waits for the network;
  • simply run for a long time.

The fix is an open call: under the lock, copy what you need (a snapshot of the listener list, the event); release the lock; then call out.

The same rule covers less obvious "alien" calls: logging that may block, completing a CompletableFuture (non-async dependent stages may run synchronously on the completing thread), and notifying observers. CopyOnWriteArrayList exists largely to make listener lists follow this rule for free.

I never hold a lock across a call I do not control: snapshot under the lock, act outside it.

Likely follow up: "What do you give up?" A removed listener may receive a pending event, concurrent publishes may be reordered, and listener failures need a policy. Document these semantics; snapshotting alone does not serialize callbacks.

14StretchspinlockskernelNvidia
In kernel or driver code, why must an interrupt handler use a spinlock rather than a mutex?
Model answer

A hard interrupt handler cannot sleep waiting for a mutex. It must use an appropriate non-sleeping synchronization primitive, keep the protected work tiny, and defer anything that may block to a schedulable context. Threaded interrupt handlers are different: they run as schedulable threads and may use sleeping locks where their context allows.

The subtle deadlock is local: process-context code holds lock L, an interrupt on that same CPU takes L, and the handler spins forever because the interrupted owner cannot resume. The process-context path must disable the relevant local interrupts while holding the shared lock and restore their previous state afterward.

On conventional Linux kernels this commonly uses spin_lock_irqsave and spin_unlock_irqrestore. On PREEMPT_RT, ordinary spinlock_t has different semantics; genuine hard-interrupt code requiring a raw spinning lock uses raw_spinlock_t and the appropriate irqsave operations. Do not transfer one kernel configuration's rules blindly to another.

Likely follow up: "Where does heavy work go?" A workqueue or threaded handler can do sleepable work; softirq context is not a general escape hatch for sleeping. In user space, spinning is risky when the owner can be descheduled. Signal handlers likewise cannot safely take a mutex interrupted code might hold.

15Seniorperformancenumbers
Roughly how expensive is taking a lock?
Model answer

Orders of magnitude on a modern x86 server; measure on your own hardware:

  • Uncontended lock and unlock, lock word hot in this core's cache: often tens of nanoseconds; neither the duration nor the instruction sequence is guaranteed.
  • Lock word moving between cores, but nobody waits: often tens to hundreds of nanoseconds, mostly coherence and cache-line transfer costs.
  • Contended with a sleeping waiter: a system call to wake it plus a context switch, a few microseconds to tens of microseconds before the waiter runs.
  • Lock held across I/O: at least the lock hold time, potentially milliseconds or longer.

So "locks are slow" is the wrong lesson: contention is slow. A lock also caps throughput: if every request holds one lock for 10 microseconds, the system can never exceed about 100,000 requests per second through it, no matter how many cores you add. That is Amdahl's law with the critical section as the serial part.

First I shorten the hold time: compute outside the lock, copy in and out. Only then do I split the lock.

Likely follow up: "How do you see contention?" In Java, Flight Recorder's jdk.JavaMonitorEnter and jdk.ThreadPark events, or many BLOCKED threads in a dump. In C++, off CPU profiling with perf, or sampled lock-wait and hold-time instrumentation. A failed try_lock is not an exact contention count because spurious failure is permitted.

16Corelocksvisibility
Does a lock only provide mutual exclusion?
Model answer

No. It also provides visibility and ordering. Releasing exclusive ownership publishes writes to a later successful acquisition of the same lock, so everything the previous holder wrote, inside the critical section and before it in program order, is visible to the next holder.

Two consequences interviewers check:

  • Readers need the lock too. A getter that reads a field without the lock gets no happens-before edge: in Java it may see a stale value, in C++ it is a data race and undefined behavior.
  • It must be the same lock. Two threads that use different locks for the same data get neither exclusion nor visibility between them. A common version of this bug is synchronized on this in one class and on a separate lock object in another class that touches the same field.
A lock is a promise between every thread that touches the data; a thread that skips it is outside the promise.

Likely follow up: "Can I read a field without the lock if all writes happen under it?" Only with another valid protocol: Java volatile, a C++ atomic, safe immutable publication, or reading after all writers have joined. A single atomic read still does not snapshot a multi-field invariant. C++ volatile is insufficient.
