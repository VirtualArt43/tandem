Byte reads and writes over a block device

Concurrent systemshard40 minRubrik system coding (byte level read, write and seek over a block API, then make it concurrent)Rubrik

Rubrik has asked for byte level reads and writes on top of an API that only moves whole blocks (reports from 2022 and 2024), and a 2026 report of a similar byte storage question had the follow up "make it concurrent". The single threaded part is careful arithmetic. The concurrent part hides a lost update inside every partial block write, and a torn read in every operation that spans blocks.

The task

The harness gives you a device that only reads and writes whole blocks of 64 bytes. Build byte level access on top of it:

  • read(offset, length) returns length bytes starting at byte offset; write(offset, data) stores data there. Offsets and lengths need not line up with blocks.
  • A write that covers only part of a block must keep that block's other bytes: read the block once, change the bytes, write it back once (read, modify, write). A write that covers a whole block writes it once without reading it first. A read reads each covered block once. Touch only the blocks in the range; this exercise has no block cache.
  • Let capacity = blockSize() * blockCount(), computed in 64 bits. A valid range has 0 <= offset <= capacity and 0 <= length <= capacity - offset. Reject every other range with IndexOutOfBoundsException in Java or std::out_of_range in C++, before any device I/O. This includes negative lengths, empty ranges outside the device and huge offsets. Validate without overflowing offset + length. Valid empty reads return an empty result; valid empty writes do nothing. Neither makes a device call.
  • Many threads call read and write at once. Each call is atomic: a read that overlaps a concurrent write sees all of that write or none of it, and two writes to different bytes of the same block never lose either update.
  • Calls that touch disjoint sets of blocks must make independent progress, including adjacent blocks and every read/write pairing. A paused device call on block 10 must not hold up a call on block 11. Per block locks or equivalent range locks meet this rule; a global lock or shared stripes do not.
  • The device does not protect itself: two device calls on the same block must not overlap if one of them is a write. Calls on different blocks may overlap.

One ByteStore owns the device for these tests. Its block size is 64, its positive block count is fixed, and valid device calls succeed. Callers keep input buffers unchanged until write returns; the device copies each block synchronously. Device failures and crash recovery are follow ups below.

Worked example: the lost update inside a block

Thread A writes 1 byte at offset 3 and thread B writes 1 byte at offset 40. Both bytes live in block 0. A reads block 0, B reads block 0, A changes byte 3 and writes the block, B changes byte 40 in its own, older copy and writes the block. A's byte is gone, although the two writes never touched the same byte. Even if each device call were atomic, the read, modify, write sequence would not be. The supplied device also requires callers to exclude conflicting calls on the same block. Hold block 0's lock from the read until the write.

What the tests check

  • 10 writes and 8 reads at awkward offsets and lengths, checked against a byte model and the device contents. Cases include partial blocks, whole blocks, long ranges, boundaries and the final byte.
  • Exact block I/O counts: whole block writes skip reads; partial writes preserve other bytes; reads fetch only covered blocks.
  • 19 invalid read/write calls throw the required exception, make no device calls and leave every byte unchanged. Cases include negative lengths, empty ranges outside the device, offsets above 32 bits and additions that would overflow 64 bits.
  • 12 valid empty calls at six offsets, including capacity, return empty or do nothing, with zero I/O.
  • 8 writers update distinct bytes within the same four blocks over eight rounds; every byte keeps its final update and conflicting device calls never overlap.
  • Two writers replace a 150 byte record across three blocks while two readers make 160 checked reads. Returned lengths must be exact and every record must be whole.
  • Controlled schedules pause a multi-block operation inside its middle block. Ordered observations reject a partially visible write and a read assembled from states that never existed together.
  • For all four read/write pairings, a call on block 11 must complete while a device call on adjacent block 10 is paused. Worker exceptions, returned bytes and final device contents are checked.
  • Six threads complete 360 overlapping operations with fixed seeds 50 to 55, with no conflicting device calls or worker exceptions. Timed joins and watchdogs bound failures: 3.5 seconds in Java and 7 seconds in C++. C++ also runs under ThreadSanitizer.

Taught in: Files, offsets, buffers, flush and fsync

Open them one at a time. Each one gives away a little more.

Get the arithmetic right first, single threaded. Reject invalid ranges with subtraction before adding offset and length. Return immediately for a valid empty range. The blocks of a nonempty range are offset / bs to (offset + length - 1) / bs. In block b, which starts at b * bs, the part you touch runs from max(offset, b * bs) to min(offset + length, (b + 1) * bs). If that part is the whole block, a write needs no read.
Give every block its own lock, and hold a block's lock across its read, modify and write. That fixes the lost update.
For atomicity across blocks, lock every block of the range before touching any of them, and release them all at the end. To make that deadlock free, always take the locks in increasing block order: two operations then can never each hold a lock the other is waiting for. Reads take the same locks, so a read never interleaves with a write of the same blocks.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Readers of the same block block each other here. Could they share?
Yes: use a read-write lock per block, taken in shared mode by reads and exclusive mode by writes, still in increasing block order. Reads of hot blocks then run in parallel. The ordering argument for deadlock freedom still holds.
A huge read locks thousands of blocks. Is that a problem?
It holds many locks for a long time, blocking writers of any of those blocks, and costs one lock operation per block. A range lock records locked intervals instead of holding one mutex per block; a Rubrik candidate proposed this for the byte storage version. Lock striping uses a fixed number of locks, acquired in stripe order and deduplicated, but it serializes some disjoint blocks and therefore relaxes this exercise's parallelism requirement. Copy on write or MVCC can reduce reader blocking, but the reader must choose one consistent version across the entire range; independent per block versions alone do not give a snapshot.
What about the seek in the original question?
A per handle position: seek(pos) sets it, read(n) reads at the position and advances it. If several threads share one handle, the position itself is shared state: either lock it together with the I/O, or, better, give each thread its own handle, or offer positional calls like the ones here, the same reason pread exists.
The device can fail in the middle of a multi-block write. What then?
Release the locks and propagate the error; already written blocks may contain new data. Locks provide isolation, not rollback or crash safety. For failure atomicity, use a write ahead log with durable commit records and recovery, or copy on write with new blocks made durable before an atomic metadata switch. Correct persistence ordering and recovery are needed to recover one complete version after a crash.
How would you add a cache of blocks?
Keep recently used blocks in memory, keyed by block number, under the same per block locks, with a dirty flag. Reads hit the cache; writes update it and either write through immediately or write back later on eviction or flush. Write back needs a flush and a clear story for durability, which is exactly the page cache and fsync discussion.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Split each call into per block pieces, and do partial pieces with read, modify, write. For thread safety, give each block a lock and have each call take the locks of all its blocks, in increasing order, before touching any block. Holding a block's lock across its read, modify and write prevents lost updates; holding all of them across the whole call makes each call atomic; the fixed order makes deadlock impossible; and calls on disjoint blocks share no lock, so they run in parallel.

Invariants

  • While a call holds a block's lock, no other call reads or writes that block on the device.
  • Every thread acquires block locks in strictly increasing block number, so the waits-for graph can never contain a cycle.
  • A write changes exactly the bytes in its range; every other byte of every touched block is written back unchanged.

Why each primitive

  • A lock per block, the natural unit: a partial update still replaces a whole device block. Different blocks are independent.
  • Lock ordering instead of try-lock and back off: simple, and it never livelocks.
  • Range checks before any locking or I/O, so a bad call changes nothing. First establish 0 <= offset <= capacity, then compare length with capacity - offset. In Java, signed addition can wrap; in C++, signed overflow is undefined behaviour. Narrowing the offset to 32 bits before validation also accepts invalid addresses.
  • In C++, a vector of std::unique_lock holds the locks, so they are released even if a device call throws.

Pitfalls

  • Locking each block only while working on it: no lost updates, but multi-block reads and writes tear. This is the broken version the tests catch.
  • Reading a block outside its lock and writing it inside: the lost update comes back.
  • Taking locks in different orders in read and write (or from both ends): deadlock under load.
  • One global lock or shared lock stripes: byte values can be correct, but disjoint blocks cannot progress independently. The adjacent block tests reject this.
  • Off by one block at the end of a range: use (offset + length - 1) / bs for the last block, and handle length 0 before computing it.
  • Reading a fully covered block before writing it: correct but twice the I/O.

Cost

A nonempty call touching k blocks takes k locks. A read makes k block reads. A write makes k block writes plus one read for each partially covered block, at most two such reads. The reference keeps one lock per device block, and uses O(k) lock bookkeeping in C++ plus a block buffer and the read result. Java needs no per-call lock list. Calls on disjoint blocks share no block lock.

How to say it in the interview

I map the byte range to blocks, and for the partial blocks at either end I read, patch and write back; whole blocks are written directly. For concurrency each block has a lock. A call locks every block in its range in increasing block order before touching any, and unlocks at the end. That makes each read and write atomic, so no read sees half a write and no partial block update is lost, the fixed order rules out deadlock, and calls on different blocks never contend. If readers dominate I would switch to a read-write lock per block, and for very large ranges to a range lock. Striping would save lock memory but weaken the disjoint progress guarantee.
