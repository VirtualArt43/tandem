Exceptions, noexcept and exception safety

Unwind safely with RAII, preserve invariants on failure, use noexcept accurately, and deliver worker exceptions through futures.

Asked atRubrikDatabricks
Before this:Classes, constructors, destructors and RAIICopy, move and move-only typesLambdas, captures and callables

In threaded code an exception is never just an error. It is a jump out of the middle of whatever the thread was doing, often out of the middle of a critical section, and every other thread inherits whatever state that jump leaves behind.

In plain words

A restaurant kitchen has one key to the spice store. A cook takes the key, trips on the way out and is rushed to hospital. If the key goes to hospital in the cook's pocket, the whole kitchen stops: everyone waits for a key that will never come back. A sensible kitchen ties the key to the store's door on a spring, so it snaps back however the cook leaves. That spring is RAII.

The spring returns the key, but it does not tidy the store. If the cook fell halfway through moving jars from one shelf to another, the next cook finds the shelves half moved. Deciding what state the store must be in when someone leaves suddenly is exception safety. And if a cook in another kitchen fails at a dish you are waiting for, someone has to walk over and tell you; otherwise you stand at the counter forever.

Why this matters for concurrency

  • A throw skips a manual unlock(). If nothing later unlocks the mutex, other threads that need it remain blocked. RAII guards (std::lock_guard, std::unique_lock, std::scoped_lock) unlock during stack unwinding.
  • Unlocking can expose a half-done update. The guard releases the lock but does not roll anything back. Threads that subsequently acquire the same mutex can observe the state your function left. exception safety is how you decide what that state may be.
  • Exceptions do not cross threads on their own. One that escapes a thread's function calls std::terminate and kills the whole process. A worker must catch everything and hand failures to whoever is waiting, through a future or an std::exception_ptr.
  • It is asked. Rubrik interviewers asked what happens when a task throws inside a hand-built thread pool, and graded which exceptions a pool catches; their job-runner questions require the first failure to stop everything. A Databricks L4 candidate wrote the event writer in C++ with std::promise and std::future, the same channel that carries errors.

throw, try and catch

You throw an object, usually one derived from std::exception, and the nearest dynamically enclosing try with a matching catch handles it. Catch by const reference to avoid slicing, and use throw; with no operand to rethrow the current exception. Handlers are tried in source order: derived types before base types, and catch (...) last. Calling throw; with no currently handled exception terminates the process.

std::runtime_error, std::system_errorruntime failures; thread creation and mutex locking can report underlying system failures through std::system_error

Stack unwinding: destructors run on the way out

As control unwinds to a matching handler, fully constructed automatic objects in scopes being exited are destroyed in reverse construction order. If no handler is found, std::terminate is called, and whether the stack was unwound first is implementation defined. Do not rely on cleanup on a termination path.

If a constructor throws, the object's own destructor does not run, but its fully constructed bases and members are destroyed. That is why resources belong in RAII members. An ordinary raw pointer member does not release a resource merely because the containing constructor failed.

The second call prints "release lock" and "release file handle" before "caught": guards in the scopes being exited are released before the handler runs. A std::lock_guard unlocks in exactly that way. If the catch is inside the guard's scope, however, the guard remains alive and still holds the lock.

The three exception safety guarantees

RAII releases the lock during ordinary unwinding, but says nothing about the state you leave behind. Other threads can observe that state once they acquire the same mutex. Each operation should document its guarantee:

GuaranteeIf it throwsExamples
Nothrowno exception escapes; cleanup operations must still meet their contractvalid calls to std::mutex::unlock, condition variable notify_one and notify_all; suitably designed destructors, swaps and moves
Strong (commit or roll back)the state is exactly as before the callstd::vector::push_back when the element can be moved without throwing or can be copied; copy-and-swap assignment
Basicno leaks and every invariant still holds, but the state may have changeda batch operation documented to retain completed items while preserving all container invariants

Below basic there is "no guarantee": you cannot assume the object is usable. Claiming basic safety while leaving an invariant broken is a bug; an API may also document weaker behavior for particular throwing element types. A strong guarantee covers the documented state, not arbitrary external effects such as an email already sent.

The technique that gives you the strong guarantee is to do everything that can throw first, then commit with steps that cannot throw. Compare two orders for a transfer that must keep a journal in step with the balances:

Why std::queue::pop returns void

A value-returning pop can remove an element and then fail while transferring its result, losing that element. Separating front() from pop() lets sequential callers copy successfully before removing. A concurrent queue must combine those steps under one lock; T item = std::move(items_.front()); items_.pop_front(); return item; avoids this failure when T has nonthrowing move construction and destruction. Do not rely on optional copy elision to make a throwing return safe.

noexcept

noexcept promises that no exception escapes a function. It may throw and catch internally, but an exception attempting to leave calls std::terminate instead of reaching an outside handler. Unwinding before that termination is implementation defined. A destructor without an explicit exception specification is normally nonthrowing, but a potentially throwing base or member destructor can make it potentially throwing too.

Even a destructor declared noexcept(false) terminates if an exception escapes it while it is being invoked for stack unwinding. Throwing and catching a second exception entirely inside that destructor is allowed; the problem is letting it escape. Put fallible cleanup in an explicit close() or commit() that can report failure, and keep destructor cleanup nonthrowing.

During vector reallocation, a possibly throwing move could modify old elements before failing. When copying is available, libc++ copies instead of moving to preserve the strong guarantee. If T is move-only and its move can throw, the vector must use that move, and a failure can leave unspecified effects; noexcept is not required for compilation.

If capacity grows through 1, 2, 4 and 8, there are seven relocations; the growth policy and counts are implementation dependent. Each relocation of Task copies its string, which need not allocate for a short string. Mark a move noexcept only when no exception can escape, or default it and let the compiler infer its specification from the members.

The operator noexcept(expression) checks whether an expression is potentially throwing without evaluating it. Generic code can write Box(Box&&) noexcept(std::is_nothrow_move_constructible_v<T>) when its body only move-constructs a T; include <type_traits>. std::move_if_noexcept selects a const reference for copying when moving may throw and copying is available. A nonthrowing declaration alone does not prove rollback or successful completion: it may terminate if the promise is violated.

For the threading library itself: unlock(), notify_one() and notify_all() do not throw. std::thread's constructor and std::mutex::lock() may throw std::system_error when the OS refuses (out of threads, for example), which matters when a pool starts its workers. std::promise::set_value throws std::future_error if the promise was already satisfied.

Exceptions and threads

An exception travels up the call stack of the thread that threw it, and no further. Three rules follow.

Rule 1: an exception that escapes a thread function kills the process

If the function you gave to std::thread lets an exception out, std::terminate is called. It is not delivered to join(), and wrapping the std::thread construction in a try does not catch it. On macOS with libc++ the program dies with:

Diagnostics vary by runtime and version. The default terminate handler aborts the process, including the other threads; a custom terminate handler cannot resume normal execution. Catch task failures inside the worker, or use an adapter such as std::packaged_task that stores them. The error-reporting path must itself be reliable; merely adding catch (...) does not make mutex or allocation failures recoverable.

Rule 2: unwinding past a joinable std::thread also kills the process

A std::thread that is still joinable when destroyed calls std::terminate, even if its function has already finished. An exception makes that easy to trigger: you start a thread, the next line throws, and unwinding destroys the object before you join. C++20's std::jthread requests stop and joins when destroyed while joinable:

"indexer finished" prints before "caught", because the jthread is destroyed, and therefore joined, while the exception unwinds the try block. In C++17, wrap the std::thread in your own small RAII class whose destructor joins, or catch, join and rethrow by hand.

jthread does not catch exceptions from its function and does not forcibly cancel work. A task that ignores its stop request can delay destruction indefinitely. Do not destroy a joining owner on its own worker thread or while holding a lock that worker needs to finish.

Rule 3: to report a failure to another thread, ship it

std::current_exception(), called inside a catch, returns a std::exception_ptr retaining the handled exception or a copy. std::rethrow_exception(p) rethrows the captured exception at the receiving call site; do not rely on exception-object identity. Outside exception handling current_exception() returns null, and passing a null pointer to rethrow_exception is undefined behavior.

Reading error in main needs no lock only because join() comes first: everything the worker did happens-before join() returns. If several workers can fail at once, the shared exception_ptr needs a mutex, as in the worked example below.

Futures package this mechanism. A std::promise supplies a value or an exception to its shared state, and the associated future's get() rethrows a stored exception. std::packaged_task and std::async capture callable failures for you. A deferred std::async call may execute in the thread that waits rather than a new worker.

If a promise with an unsatisfied shared state is destroyed, it makes that state ready with std::future_error(std::future_errc::broken_promise). The waiter then learns that the producer abandoned the result, rather than waiting forever. Prefer explicitly completing accepted work with its actual result or error. set_exception requires a non-null exception pointer and an unsatisfied valid state; it can itself throw std::future_error on misuse.

future.wait() waits for readiness but does not rethrow the stored task failure; get() does and consumes an ordinary future's state, even on that failure. Do not call get() twice. Use std::shared_future when several observers need to read one shared result.

Exceptions inside a worker loop

A pool worker runs other people's code. If one task throws and nothing catches it, the worker's thread function ends with an exception: std::terminate, and the whole service is gone. The rule for every worker loop is:

  • Run tasks outside the queue lock and capture their exceptions with a catch (...) or a packaged task.
  • Deliver the failure to the submitter: store the task as a std::packaged_task so its future receives the exception automatically, or set the exception on the task's promise.
  • Keep the worker alive and take the next task. A dead worker silently shrinks the pool.

This is exactly the follow up a Rubrik interviewer raised on a hand-built pool (an exception thrown inside a task), and the one-line answer is: each worker catches everything around each task, the failure goes into that task's future, and the worker moves on.

Worked example: the first failure stops the job runner

Rubrik's job-runner reports include stopping on the first failure. Define the boundary precisely: here, claiming an index under a mutex admits a job. Recording the first error under that same mutex closes admission. Already admitted jobs may still begin their function bodies or finish; arbitrary running C++ code cannot be forcibly stopped safely. This example handles independent jobs; dependency scheduling is a separate layer.

A separate atomic stop check would have a gap: A reads false, B records failure, then A claims another job. Here the mutex orders both admission and error recording. "First" means first recorded under that mutex, not earliest throw by wall-clock time. A std::stop_token can request that already admitted jobs cooperate in cancellation, but cannot force them to stop.

Every invocation has fresh state, and zero workers is rejected. jthread ownership also joins previously created workers if a later thread construction fails; that startup exception propagates after cleanup, though those workers may have performed work. The example assumes functioning synchronization primitives and jobs that eventually finish. Rethrowing happens only after joins, outside the mutex.

Common mistakes

  • Manual lock() and unlock() around code that can throw. A skipped unlock can strand every waiter. Use a guard.
  • Assuming the guard also restores the state. It only unlocks. Order the work so everything that can throw happens before the commit.
  • Letting a task exception escape its thread function. std::terminate, not a failed join(). Capture it inside the worker or use a packaged task.
  • Throwing while a std::thread is still joinable. Unwinding destroys it and calls std::terminate. Use std::jthread, or join before anything can throw.
  • catch (...) {} in a worker that swallows the error. The worker survives but the caller never learns the task failed. Put the exception in the task's future or record it.
  • Catching by value. catch (std::exception e) copies and slices a derived exception down to the base. Catch by const&, and rethrow with throw;, not throw e;.
  • Abandoning a promise accidentally. The waiter gets broken_promise, losing the original failure context. Complete accepted tasks explicitly, including cancellation, when possible.
  • Marking a function noexcept while allowing an exception to escape. That converts recoverable propagation into std::terminate.

In the interview

Exceptions arrive as follow ups to a concurrency design: "what if the task throws?", "what if doWork() throws while you hold the lock?", "how does the caller of submit find out?", "how does your job runner stop on the first failure?". The interviewer wants to hear that you thought about every path out of a critical section and out of a thread.

Every lock in my code is a guard, so an exception unlocks it during unwinding. That doesn't roll back state, so inside the critical section I do everything that can throw first, and only then commit with steps that can't fail. That way other threads never see a half-applied update.
Nothing may escape a worker thread, because an uncaught exception in a thread calls std::terminate. Each worker catches everything around each task, puts the exception into that task's future through the packaged_task or the promise, and moves on to the next task. The submitter sees the original exception when it calls get().

Follow ups to expect: "What happens if you destroy a joinable std::thread?" (std::terminate; use std::jthread), "Why does vector copy your tasks when it grows?" (the move constructor is not noexcept), and "What if two workers fail at the same time?" (first error wins under a lock, the rest are dropped or logged).

Senior depth

Codebases without exceptions. Some systems compile with -fno-exceptions and return status values. C++23's std::expected<T, E> is one value-or-error representation, unavailable in C++20. Choosing that representation does not by itself make allocations or library operations nonthrowing; the project must define its failure policy. Accepted work still needs a result or error delivered to its waiter.

What a throw costs. Apple clang on this 64-bit target uses table-based exception handling: normal entry to a try does not register a dynamic handler. That does not mean exceptions are free: metadata, code size and optimization effects remain, and an actual throw searches for a handler and performs cleanup. Measure on the target; use exceptions for failures rather than routine control flow in a hot loop.

Scope guards that know why they run. std::uncaught_exceptions() (C++17, <exception>) returns this thread's count of exceptions not yet caught. A scope guard records a baseline at construction and checks for an increase at destruction; testing only for nonzero can mistake an outer unwind for a new failure. Rollback must not throw, and a fallible commit belongs in an explicit operation.

Key takeaways

  • Unwinding destroys fully constructed automatic objects in exited scopes in reverse order. RAII cleanup is not guaranteed on termination paths.
  • A guard unlocks; it does not roll back. Do everything that can throw first, then commit with nothrow steps, so other threads never see half an update.
  • noexcept is a promise enforced by std::terminate; on move constructors it helps vector choose how to relocate elements safely.
  • An exception that escapes a thread function, or unwinding past a joinable std::thread, terminates the process.
  • Carry failures across threads with std::exception_ptr, std::promise::set_exception, or std::packaged_task, and rethrow where someone can handle them.

Why. A plain std::mutex has no idea an exception happened. unlock() was simply skipped, so the mutex stays owned. With std::lock_guard<std::mutex> lock(m); the destructor would unlock it during unwinding.

Why. exception_ptr, promises and packaged tasks transport the failure to a receiving call that rethrows it. Why. A guard unlocks; it never undoes your writes. The fix is ordering: append to the journal first (the only step that can throw), then change the balances with operations that cannot fail. std::bad_alloc is an ordinary exception and can be caught.

Write a single-thread Worker with template <typename F> auto submit(F f) that returns a std::future of f's result. A task that throws must not kill the worker; its exception must come out of the future's get(). The destructor finishes queued tasks and joins.
Model answer

std::packaged_task is move-only and C++20 std::function needs a copyable callable, so a shared_ptr lets a small copyable lambda own it. Each valid packaged task is invoked exactly once: user exceptions go into its future and the loop continues. submit can itself throw before accepting the task, for example on allocation failure.

The owner must finish all submissions before destruction, and destroy the worker from another thread. Tasks must eventually return and must not wait for another task queued behind them on this single worker. As with the other examples, synchronization primitives are assumed to function; this is task-error handling, not recovery from a broken runtime.

Explain
The interviewer asks: "In your blocking queue, what happens if the element's copy throws while push holds the lock?" Answer as you would out loud.
Model answer

The guard releases the lock as control unwinds out of its scope. Single-element insertion at the end of a deque has no effects on the deque if allocation or element construction throws, so the queue remains usable. I notify consumers only after successful insertion; consumers still recheck their predicate because wakeups may be spurious. This guarantee covers queue state, not a caller's argument altered by a throwing move.

For pop I require nonthrowing move construction and destruction, covering extraction, removal and return. Assigning into T& out before removal is not a universal fix: a throwing move assignment can mutate the queued source. A carefully specified copy-out can preserve the queue while leaving out changed, or the queue can transfer an owning handle such as std::unique_ptr<T> with a nonthrowing move.

Debug
This crashes the whole service when one file name is empty. Why, and how do you fix it?
Model answer

If the third name is empty, two threads are already running when the exception is thrown. Unwinding destroys workers, which destroys two joinable std::thread objects, and each destructor calls std::terminate. The throw meant for the caller kills the process instead. There is a second hazard: if process(f) itself throws inside a worker, that also terminates the process.

Fixes: validate every input before starting any thread; use std::vector<std::jthread>, whose destructors join, so an exception waits for the running workers and then propagates; and wrap the body of each worker in try { process(f); } catch (...) { /* store std::current_exception() under a mutex */ }, then rethrow the first stored error after the joins. With jthread, the references to f stay valid too, because the threads are joined before files can go away.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"You used a lock guard around a balance transfer. Are you now exception safe if appending to the journal throws?"
What a strong answer covers
  • RAII releases the mutex during unwinding but does not restore balances
  • Changing balances before a failed journal append breaks the balance-journal invariant
  • Define basic safety versus the strong guarantee for the operation's state
  • Validate IDs, amount and overflow, append safely, then commit with nonthrowing updates
  • All observers use the same mutex; external side effects need their own protocol
How a senior would say it
The lock guard gives me cleanup, but it does not give the transfer an exception guarantee by itself. If I change both balances and then journal allocation fails, the guard unlocks during unwinding. The next reader taking that mutex can see money moved with no journal record. That breaks the invariant even though there is no leaked lock. I would state the guarantee explicitly. Basic safety means no leaks and valid invariants after failure. Strong safety means the operation leaves its documented state unchanged on failure. For this in-memory transfer, I would validate the account IDs, positive amount, available funds and destination overflow first. Then I would append the trivial journal entry, relying on the vector insertion's strong guarantee. Once that succeeds, the checked integer updates cannot throw, so they form the commit. Every reader must take the same mutex to avoid observing the intermediate state. This reasoning covers the in-memory state. If journaling means writing to an external service, I need a transaction or recovery protocol; a lock guard cannot undo an external side effect.

Likely follow up: What happens to an object's resources if its constructor throws before the object is fully constructed?

Out loudabout 90 s
"A task in your pool throws. How does the submitter learn about it, and what changes if the first failure should stop the whole batch?"
What a strong answer covers
  • An exception escaping a thread function terminates; join does not transport it
  • Capture each task failure with packaged_task or a promise and exception_ptr
  • Future get rethrows the failure while the worker can continue; wait only observes readiness
  • For batch failure, serialize work admission and first-error recording under one mutex
  • Already admitted work may run; cancellation is cooperative and first means first recorded
  • Join all workers before reporting failure and use RAII ownership for partial startup
How a senior would say it
I would capture the exception inside the worker and deliver it through that task's future. An exception escaping the thread function terminates the process; joining does not transport it back. A packaged task already captures failures from its callable. With a manual promise, I catch everything and set the current exception on the shared state. The submitter's get then rethrows it, while the worker can take another task. Waiting alone only observes readiness. Stopping a batch is a different policy. I would protect job admission and the first stored exception with one mutex. Under that mutex, a worker either claims the next job or observes failure and exits. The first handler to record an error closes admission. A separate atomic flag checked before claiming work leaves a gap where another job can be admitted after failure. I would explicitly allow already admitted jobs to finish, even if their function bodies have not started yet. Stopping those jobs requires cooperative cancellation, not killing their threads. I then join every worker before rethrowing the recorded failure to the caller. RAII thread ownership also handles an exception while creating later workers. Finally, the reporting path itself must not silently swallow errors or leave accepted futures pending indefinitely.

Likely follow up: If two tasks throw almost simultaneously, which exception is the first one your API promises to report?

Out loudabout 75 s
"Why is vector copying my tasks during growth, and should I fix it by putting noexcept on every move constructor?"
What a strong answer covers
  • Copying preserves old elements when moving could throw and copying is available
  • Noexcept promises no exception escapes; violation terminates instead of propagating
  • Mark or infer noexcept only when member operations support that promise
  • A move-only type with a throwing move still works but can lose the strong guarantee
  • Capacity growth and relocation counts are implementation dependent
  • Destructors must not let a new exception escape during unwinding
How a senior would say it
I would inspect the move constructor's exception specification before changing anything. During growth, vector relocates existing elements. If moving might throw and copying is available, copying preserves the original elements until relocation succeeds. A move that changes several source objects before failing would make rollback much harder. Noexcept promises that no exception escapes the function. It is not a request to suppress errors: violating it calls terminate instead of propagating to the caller. I would mark a move noexcept only after checking every operation it performs, or default the move so its members determine the specification. Generic wrappers can use a conditional noexcept based on the contained type. If the type is move-only, vector can still use a potentially throwing move. The tradeoff is weaker exception guarantees if that move fails. Exact relocation counts depend on the implementation's capacity growth policy. I would also check cleanup: a destructor invoked during unwinding must not let another exception escape. A fallible close operation should report errors explicitly, while destruction provides reliable cleanup rather than a second failure.

Likely follow up: Can a noexcept function legally call code that throws, if it catches the exception internally?
