Concurrent time-based key-value store

Thread-safe structuresmedium35 minLeetCode 981, extended for concurrent and out-of-order writesGoogle

Think of a notebook that keeps every revision of a value. Many people can add revisions while others ask what the value was at an earlier time. You must preserve both the history and a consistent answer during concurrent updates.

The task

Build a time-based key-value store that many threads use at once.

  • set(key, value, timestamp) stores value for key at timestamp. Setting the same key and timestamp again replaces only that version, preserving all other timestamps.
  • get(key, timestamp) returns the value whose timestamp is the largest one less than or equal to timestamp, or the empty string if there is none (a floor lookup).
  • Timestamps can arrive in any order. Support the whole signed 32-bit int range, including its minimum and maximum. Timestamps are caller-supplied version labels, not deadlines or wall-clock readings.
  • Keys and values are strings and may be empty. Java inputs are non-null. An empty value is a stored version: it must hide an older nonempty value until the next version. It is intentionally indistinguishable from a missing value through this API.
  • Keys compare by their text. Each TimeMap instance starts empty and owns independent state. Retain all versions; deletion and retention are follow ups.
  • Every operation must be linearizable: it takes effect at some instant between call and return. A completed write must be visible to a later read, unless a subsequent write supersedes it. Overlapping writes to the same timestamp may take effect in either order; their invocation or return order alone does not select the winner.
  • Aim for reads that do not block each other. The tests enforce correctness and bounded completion, not a particular lock choice or a throughput target.

Example: after set("foo", "bar", 1) and set("foo", "bar2", 4), get("foo", 3) is bar, get("foo", 4) and get("foo", 5) are bar2, and get("foo", 0) is empty. If sets arrive as 30, 10, 20, then get(k, 25) must still return the value set at 20. Replacing the version at 20 must not erase the version at 30.

Where it comes up: a Google candidate reported LeetCode 981 with follow ups on deletion and a multithreaded implementation. This practice version explicitly adds arbitrary arrival order, replacement, and boundary cases.

What the tests check

  • Single-thread floor lookups: exact matches, gaps, queries before the first version, missing keys, shuffled timestamps, and replacement.
  • Both int extremes, negative and zero timestamps, empty keys and values, and preservation of neighbouring versions after an overwrite.
  • Equal key text supplied through separate strings, distinct keys sharing timestamps, and two simultaneously live instances. Java also uses two unequal keys with the same hash code.
  • A writer and an existing reader exchange 64 rounds using rendezvous points. Each read follows a completed overwrite and precedes the next one, so its full value must match exactly, including empty and long values. Earlier and later versions must remain intact.
  • 24 short concurrent histories with three workers inserting, overwriting and reading one key. The harness searches for a sequential order matching every result and final read, while respecting operations that finished before another began. Overlapping calls are allowed either order.
  • Four writers insert shuffled timestamps while four readers query one key. A preloaded version prevents vacuous empty answers; readers check valid timestamp values, no future result and no backwards movement of the newest timestamp. Final floor lookups must all be exact.
  • Eight workers rendezvous before each fresh key, then fill its history. Every version must survive: 300 keys in Java and 60 in C++. Missing-key readers also run alongside writers growing the key table.
  • Timed coordination and joins plus a watchdog bound failures. Worker exceptions fail the test. C++ also runs under ThreadSanitizer. These checks expose bugs; finite executions do not prove all possible schedules correct.

Taught in: Concurrent hash maps

Open them one at a time. Each one gives away a little more.

A list supports binary search only while it stays sorted. Locking an append does not make timestamps arrive in increasing order.
Keep a sorted history per key. In Java, TreeMap.floorEntry(timestamp) finds the floor. In C++, use std::map::upper_bound(timestamp) and step back unless it returned begin(). Do not compute timestamp + 1: the maximum timestamp overflows.
Protect the key table and each history. A single reader-writer lock is sufficient. Another design uses a concurrent key table that atomically creates one history per key, then a reader-writer lock per history. Hold the read lock through both floor selection and copying the value.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Reads are 99 percent of the traffic. Which design would you try?
Measure a single reader-writer lock first, then consider a lock per history so unrelated keys can proceed independently. The shared reader count can still be a contention point. Immutable histories published atomically let each reader search one stable snapshot; writers must coordinate or retry a compare-and-set so two copied histories cannot lose each other's updates. A concurrent sorted collection helps with safe access, but audit the consistency of the complete floor-and-value operation before claiming the same guarantee.
Add delete. What should it mean?
Ask whether it removes all history or records a deletion from a timestamp onwards. A tombstone supports the latter: floor lookups that select it return empty, while earlier queries retain history, and a later set can restore the key. For whole-key removal, coordinate removal with writers using that history. Java references keep an old history alive; C++ needs lock-protected lifetime or shared ownership. Memory safety alone does not settle the ordering of delete and set.
Histories grow forever. How do you bound them?
Declare queries earlier than a retention horizon unsupported. Keep the newest version at or before that horizon as an anchor, plus every later version. Dropping the anchor breaks floor lookups just after the horizon. Define whether late writes before the horizon are rejected or can replace the anchor, and serialize trimming with those writes. Do not silently prune versions under the original contract.
Does the newest timestamp never moving backwards prove correctness?
No. It is a necessary property for this insert-and-replace API, but a reader returning one stale value forever could satisfy it. The coordinated overwrite test checks freshness after completed writes; the small-history checker also tests whether overlapping calls admit a legal sequential explanation. Neither proves correctness for every schedule. Explain your locking invariant and the point each operation takes effect. Reading two keys is not an atomic pair; that requires a snapshot, as in the snapshot store.
One key gets almost all the writes. What now?
Lock striping cannot divide one history's contention. Consider batching through one owner or a suitably validated concurrent ordered structure. If you batch, set must wait until its version is published before returning to preserve this contract; returning while the write is still buffered changes the visibility guarantee. Measure whether lock contention, allocation or history size dominates first.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Store a sorted map per key, from timestamp to value, and answer get with a floor lookup. The invariant is that each key has exactly one protected history, sorted by timestamp regardless of arrival order. Replacement changes one entry, including when the new value is empty.

Why each primitive is there

  • Java key publication. ConcurrentHashMap.computeIfAbsent installs one History per key. A separate check followed by a put can replace another writer's newly created history. Histories remain installed for the life of this store.
  • Java history protection. Each history owns a TreeMap and a ReentrantReadWriteLock. Writers take its write lock; readers keep its read lock through floorEntry and extracting the value. finally releases either lock even on an exception. Reads of one history can share the lock.
  • C++ protection. One std::shared_mutex guards the key table and every history. set takes it exclusively, and get shares it until the returned string has been copied. get uses find, because operator[] would insert a missing key while holding only a shared lock.
  • Safe floor boundaries. upper_bound(t) finds the first timestamp strictly greater than t. Check for begin() before stepping back. Direct comparisons handle both integer extremes without addition or subtraction.

Why not simply a concurrent skip list?

For this contract, selecting the floor timestamp and obtaining its value must agree with one instant. In the Java 21 implementation, findNearEntry selects a node and subsequently reads its value. Consider a lookup at 25 that selects timestamp 10, then a writer inserts timestamp 20 and overwrites timestamp 10 before the lookup reads its value. The new value at 10 is not a legal answer at any instant during that history: before the insert the old value was at 10, and afterwards the floor is 20. The reference uses an explicit history lock to keep selection and value observation together.

Correctness and cost

Under the relevant exclusive lock, a set takes effect when it inserts or replaces the entry. Under a read lock, the history stays unchanged while the floor and value are selected. If Java finds no history in the key table, the empty lookup takes effect at that observation; it may precede a concurrent first set. If it finds an installed but still empty history, the read lock orders it before or after that first insertion.

Ignoring contention and string-processing costs, a history operation costs O(log v) for v versions, plus the key-table lookup, which is expected O(1). Space is O(V + K) for V total versions and K keys, plus stored strings. Java permits unrelated histories to proceed independently after lookup or creation, though key-table updates can still contend internally. C++ uses one simpler global lock; per-key locks are a possible next step. Neither reference promises fairness or starvation freedom under unbounded competing traffic.

How to say it in the interview

I cannot assume concurrent timestamps arrive in order, so I keep a sorted history for each key. Every set replaces exactly one timestamp, and every get selects the floor and copies its value while that history is protected. I also make creation of the history atomic so first writers cannot lose each other. I would start with a reader-writer lock, then split protection by key if measurement shows contention. The correctness argument is the protected history; stress tests and recorded operation histories help find violations.
