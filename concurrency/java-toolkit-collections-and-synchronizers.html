The toolkit: concurrent collections and synchronizers

Choose concurrent collections and coordination primitives by their atomic operations, capacity, ordering, visibility and failure contracts.

Asked atRubrikDatabricks
Before this:The collections you will useIterators and ConcurrentModificationExceptionExceptions, InterruptedException and try-with-resourcesThe toolkit: ReentrantLock, Condition, ReadWriteLock and StampedLock

A thread-safe collection protects its own operations. Your job is to choose operations that protect the application's rule, and a coordination primitive that still works when a participant times out or fails.

In plain words

Picture a restaurant with several cooks. The order board needs safe updates, the serving counter has limited space, and a dish cannot leave until all its parts are ready. Those are three different jobs: storing shared information, handing work over, and waiting for other people.

A safe order board does not stop two cooks both deciding to prepare the last order. A bell does not create another space on the counter. Pick the tool for the promise you need.

Why this matters for concurrency

These are the library types you will read in threaded Java and choose in LLD rounds. A cache needs an atomic per-key update; a worker pipeline needs a queue and an overload policy; a batch needs a completion signal. Each choice has a different failure contract.

Ordinary collections covers interfaces and costs, and iterators covers traversal models. Here you learn the concurrent API contracts. Thread creation, locks, atomics and task execution belong to threads, locks, atomics and executors and futures.

ConcurrentHashMap: choose the atomic operation

A ConcurrentHashMap rejects null keys and values. A get returning null means no mapping was observed. Its weakly consistent iterators and bulk operations do not give a transaction over the whole map; size() is unsuitable for enforcing an admission limit while writers run.

synchronized (map) does not freeze its concurrent operations: they do not acquire that monitor. A larger invariant needs a locking protocol followed by every relevant caller, or a different representation.

computeIfAbsent(k, key -> value)Only when absent, once for that invocation if computation is neededReturns the existing or computed value; a null result installs nothing.
computeIfPresent(k, (key,v) -> next)Only when presentReturns the new value, or null if absent or removed; a null callback result removes the mapping.
compute(k, (key,v) -> next)Once per invocation, with v == null for absenceReturns the new value; null removes a present mapping or leaves an absent key absent.
merge(k, supplied, (oldValue,addedValue) -> next)Only when present; otherwise installs the non-null supplied valueReturns the resulting value; a null callback result removes the mapping.

Keep callbacks short and do not modify the same map from inside them. A callback may hold up other updates, including keys sharing internal coordination. Recursive computation can throw IllegalStateException; slow I/O or waiting for another map updater can stall the system. A thrown callback exception leaves the mapping unchanged, but does not undo side effects or mutations you made to a referenced object. These are the Java 21 computation contracts.

computeIfAbsent is not “once forever”: a null result, an exception or later removal allows a later call to compute again. putIfAbsent(k, load()) may run several loads even though only one value wins. Expensive shared loads need an explicit in-flight result and failure policy; see caches and single-flight.

remove(k, expected) and replace(k, expected, replacement) compare values by equality, not reference identity or a version number. They cannot detect that an equal value was removed and reinserted in between. If that history matters, include a generation in an immutable value and compare that too. ConcurrentHashMap.newKeySet() supports add; a map's ordinary keySet() supports removal but rejects addition because it has no value to associate with a new key.

This prints tea=2000, cake=3. The stock callback assumes the key is present for those two calls, as established by this program; a reusable stock method must also handle absence. For the familiar lost-update interleaving, follow check then act; for implementation and contention, follow concurrent hash maps.

The map protects mappings, not later mutations to the values. map.computeIfAbsent(k, x -> new ArrayList<>()).add(v) still shares an unsafe list. Use immutable replacement inside compute, or a value with its own concurrency contract. LongAdder values suit statistics, as explained in counters at scale, but removal can detach an adder that another thread is about to increment.

Choose the traversal and ordering contract

CopyOnWriteArrayList suits small listener registries with many notifications and few edits. Use addIfAbsent instead of contains followed by add. Indexed reads are O(1); an insertion copies O(n) references. It permits null elements. Iterators capture references, not deep copies; removal does not retract a listener from an ongoing traversal. Iterator remove and list-iterator set and add are unsupported, as the list contract specifies. The mechanism is in copy-on-write and snapshots.

ConcurrentLinkedQueue suits nonblocking FIFO handoff when growth is controlled elsewhere. Call poll directly instead of testing isEmpty first. It rejects null and supplies no waiting consumer or capacity limit: spinning on a null result wastes CPU. Its iterators are weakly consistent, and size() traverses the queue, taking O(n) work and reserving nothing for later operations.

ConcurrentSkipListMap supplies sorted keys, floor and ceiling lookups, and ranges while writers run. Keys follow the comparator, including its definition of equality; see comparators and ordered collections. It rejects null keys and values. A subMap is live, and neither a range scan nor firstEntry() followed by remove() is one atomic operation: use pollFirstEntry() to claim the smallest entry.

Do not transfer callback guarantees between map classes. Skip-list computations can perform redundant or repeated callback work under contention, so keep functions free of external side effects. The skip-list API explicitly gives a weaker callback guarantee than ConcurrentHashMap.

Synchronized wrappers: lock the owner during iteration

A synchronized wrapper works only when every access goes through it. Do not keep using the backing collection. For a list, hold the returned list's monitor for the whole iterator traversal; for a map view such as entrySet(), lock the map wrapper, not the view. Sorted subviews retain the original owner's lock. Iterators, spliterators and stream traversals require this external protection; a parallel stream is a poor fit for such a lock-held traversal. This is the wrapper iteration rule.

Process the copy outside the lock if processing is slow. It is a shallow copy, so mutable values still need protection. The monitor syntax is in synchronized; the larger consistency question is in concurrent iteration.

API card: BlockingQueue operations and implementations

A BlockingQueue joins storage with waiting. All its implementations reject null elements so poll can use null as its failure result. Successful insertion publishes the producer's earlier writes to the thread accessing or removing that element; it does not protect changes made after insertion. The interface contract also specifies no built-in close operation.

Blocking and timed interface methods declare InterruptedException; propagate it or restore the interrupt and end the task. A timeout limits waiting, not subsequent processing time, and is not a precise scheduling deadline. See time and budgets and cancellation.

The no-argument remove() claims the head or throws NoSuchElementException; remove(Object) instead attempts to remove an equal element and returns a boolean. It cannot cancel a job already taken by a consumer. drainTo moves currently available elements, but a failure while adding to the destination can leave a partial transfer; do not use it as an all-or-nothing batch operation.

A bounded queue provides back-pressure only if callers act on full or timed-out insertion. Throwing away offer's boolean silently drops work. Unbounded queues move overload into growing memory use and latency. The queue bounds waiting items, not queued plus running tasks; executor admission belongs to executor anatomy.

The first timed offer must fail because no consumer has started. Later put(9) may wait or may find a free slot, depending on scheduling; correctness does not depend on which. Real consumers need an end-of-stream protocol: for a FIFO queue, stop producers and then enqueue one distinct stop message per consumer, or manage cancellation explicitly. Study shutdown and queue internals in blocking queues and producer and consumer.

Priority is not a delay

A priority queue returns the best available item immediately. A delay queue's take, poll and no-argument remove only remove an expired head; remove(Object) can remove an unexpired element, which is useful for cancellation. Never mutate queued priority or deadline fields in place: the queue does not reorder itself when your object changes.

The constructor's 2 is an initial allocation size, not a bound. The sequence belongs to this single submitter; several submitters would need a safe sequence allocator and a precise definition of tie order. Priority selection does not guarantee task completion order or prevent starvation of lower-priority work.

Delayed requires getDelay and an order consistent with that delay. This queue holds only Ticket objects and uses short, nearby deadlines, so subtraction handles clock wraparound; arbitrary deadlines spanning half the long range would violate that assumption. The test checks order and expiry, not an exact elapsed duration. See the delay queue contract and scheduled executors for scheduling work beyond storing deadlines.

offer("orphan") fails before any receiver exists. put and take later meet regardless of which arrives first. A successful handoff says the item was received; it does not say processing finished.

Count events with a latch, limit holders with a semaphore

A CountDownLatch counts events, not thread identities. One thread may count down more than once; extra calls after zero do nothing. It never resets. Writes before a contributing countDown() become visible after a successful await(), but a timed await returning false does not establish that all results are ready. The latch records completion, not success: record failures separately. See the latch contract and latches.

A Semaphore limits how many permits are outstanding. Acquire first, then enter a try/finally that releases exactly what was acquired. It has no owner and no automatic upper cap at its initial permit count: releasing after a failed acquire creates capacity. new Semaphore(1) is not a reentrant mutex. Fair mode orders acquisition at internal queueing points; untimed tryAcquire() may still barge. See the semaphore contract and semaphores.

acquire(n) takes all requested permits together; repeatedly acquiring one can leave several callers holding partial allocations while each waits for more. Under fair acquisition, a large request at the front can delay smaller requests even when enough permits exist for those smaller requests. A semaphore limits concurrency, not requests per second: faster completion recycles permits faster. For a time-based quota, use a rate limit.

Worked example: four results, only two calls at a time

You need four independent results, but a downstream service allows two calls in flight. A semaphore answers “may I start?” and a latch answers “has every attempt finished?” They cannot substitute for each other.

Each worker owns one array slot; successful latch waiting publishes those writes before the sum, even though joining happens later. Zero is this demo's detectable incomplete-result marker. A real service stores a result or failure for each task, often in a future. Permits return even when work throws; completion is signalled even when acquisition is interrupted.

CyclicBarrier: finish this round before the next

A CyclicBarrier waits for a fixed number of arrivals per generation. await() returns an arrival index, with zero for the last arrival, and the optional barrier action runs on that last thread before the generation releases. Writes before arrival become visible to the action and then to participants after successful waiting. See the barrier contract.

The action reads partial results before either worker can overwrite them for the next round. If workers instead read each other's slots after await, a fast worker could already be writing the next round; use another barrier or separate buffers for that protocol.

A waiter that exits with InterruptedException or TimeoutException breaks the generation; other waiters receive BrokenBarrierException unless they too are interrupted. If the barrier action throws, the last arrival receives that failure and waiting peers receive BrokenBarrierException. But a worker that dies before reaching the barrier does not automatically break it: use timed waits or a coordinator's cancellation policy. reset() breaks current waiters and creates a fresh generation; it cannot repair application state on its own.

Phaser: register work before it can finish

A Phaser separates registration, arrival and waiting. register() adds a party, arrive() contributes once to the current phase without waiting, and arriveAndDeregister() contributes and leaves. Registered parties are counts, not tracked thread identities, so your code must ensure exactly one arrival per participating party per phase.

The coordinator's initial party prevents early advancement while tasks are being registered. Register before launching or submitting each task; if launch or submission fails, undo that registration. This demo also terminates the phaser on start failure; already started workers finish independently and deregister in finally. By default, deregistration that leaves zero parties terminates the phaser; a newly constructed Phaser(0) is still active, but registration cannot revive a terminated instance.

arriveAndAwaitAdvance() and awaitAdvance(p) are not interruptible waits. For cancellation, record the phase returned by arrive() and call awaitAdvanceInterruptibly(p, timeout, unit). A timeout or interrupt does not break the phaser or remove the party; define collective termination or coordinated departure rather than blindly arriving twice. forceTermination() releases waiters but does not stop tasks; negative phase results report termination, not successful work completion. The phaser lifecycle, its onAdvance hook and multi-phase algorithms go deeper in barriers and phasers.

Exchanger: swap ownership with one partner

An Exchanger is a two-way rendezvous: each participant supplies a value and receives its partner's value. It can swap a full buffer for an empty one. Writes made before a successful exchange become visible to the partner after return, but ownership discipline is still yours: stop using the buffer you handed away. With several participants the API does not promise a particular partner.

Timed exchange throws TimeoutException, unlike a queue's timed poll, which returns null. Interruption throws InterruptedException. A failed exchange does not justify transferring buffer ownership in your application; the caller retains its offered buffer. Use timed waits or coordinated interruption if a partner can disappear. See the exchange contract.

The visibility promise and the boundary around it

These tools establish happens-before edges, not just convenient waiting. Queue insertion publishes to an accessing or removing consumer; a map update publishes to a retrieval observing it; a semaphore release publishes to a successful subsequent acquire; latch completion, barrier advancement, phaser advancement and exchange each have their documented edges. Follow happens-before and safe publication for proofs.

None makes later arbitrary mutation safe, makes several keys one transaction, or makes a timeout proof of completion. Encapsulate the invariant and failure policy behind your own class, using LLD design and putting the toolkit together.

Common mistakes

  • Safe calls mistaken for a safe sequence. Use merge, conditional replacement or an explicit shared lock for the entire invariant.
  • Assuming the map guards its values. A shared ArrayList inside a concurrent map still needs its own policy.
  • Using size as permission. Claim through poll, insert through offer, or acquire a permit; observing a count reserves nothing.
  • Calling every concurrent iterator a snapshot. Copy-on-write snapshots freeze references; map and linked-queue traversals are weakly consistent.
  • Confusing initial allocation with a bound. A priority queue's constructor size does not stop growth, and the linked blocking queue's default is effectively unbounded.
  • Releasing in a finally that also covers failed acquisition. Place the release scope after success, or track exactly how many permits were acquired.
  • Counting only successful tasks down. Signal completion in finally, store failure separately, and never read incomplete results after a timed-out wait.
  • Ignoring a missing participant. A barrier, phaser, queue handoff or exchange needs a cancellation and failure policy; waiting is not failure detection.

In the interview

Project research records Databricks questions about ConcurrentHashMap locking. A Rubrik report describes assessment of construct choices, including CyclicBarrier and Semaphore, and exception handling; other Rubrik system-coding reports ban library queues and executors. State the library contract first, then be ready to implement it with conditions and lower-level primitives.

I choose by what must be atomic and what must wait. Per-key state changes belong in a concurrent map operation. Bounded work handoff belongs in a blocking queue. A semaphore limits in-flight holders, a latch counts one batch, a barrier separates repeated rounds, and a phaser handles changing membership.

Expect “what happens if the loader throws?”, “what bounds memory?”, “does removing a listener cancel an ongoing notification?”, and “what if one worker never arrives?” For map internals, distinguish the API from implementation details; current Java does not promise the old fixed-segment design.

Senior depth

Registration needs cleanup even for work that never starts. A queued task cancelled before execution never enters its task body's finally. A coordinator must account for rejected, discarded and cancelled tasks exactly once, coordinating with task startup so cancellation and completion cannot both arrive for the same party. The same issue applies to a latch counted down only inside task bodies; executor shutdown alone does not discharge those counts.

A correct synchronizer can still exhaust a pool. Put three barrier participants on a fixed pool of two threads: the first two can wait forever while the third stays queued. Likewise, a task that holds the last semaphore permit while waiting for a child needing that permit prevents its own completion. Ensure awaited work can run without a resource held by its waiter, or restructure completion into continuations; practise this in the pool starvation bug.

A phaser action has its own failure contract. onAdvance(int phase, int registeredParties) returns true to terminate and runs on the party advancing the phase. If it throws, that caller receives the failure and the phase does not advance; peers are not automatically released as they are by a broken barrier. Keep the hook short and define recovery such as forceTermination() from the caller's failure handler, following the hook contract.

The Java 21 implementation supports at most 65,535 parties per phaser. A tree of child phasers can accommodate larger groups and reduce contention, with each nonempty child counting as one party in its parent.

Key takeaways

  • Choose an atomic operation for the entire per-key change; callback and mutable-value rules matter.
  • Choose copy-on-write for read-heavy snapshots, linked queues for nonblocking FIFO, and skip lists for concurrent sorted navigation.
  • Bound queues explicitly when overload must slow or reject producers, and handle timed failure results.
  • Latch: one batch. Barrier: fixed repeated rounds. Phaser: changing membership. Semaphore: reusable permits. Exchanger: paired swap.
  • Publish results before signalling, clean up after failure, and distinguish completed work from successful work.
  • Synchronized wrappers require their owning monitor during traversal and compound sequences.

Two threads share a ConcurrentHashMap and each run map.putIfAbsent("k", expensiveLoad()) once. The key starts absent, neither thread removes it, and both loads return non-null without modifying the map. Which statement is correct?
Why. Java evaluates arguments before the method call, so both loads execute. putIfAbsent makes the insertion conditional, not argument evaluation: one candidate wins and the losing caller returns that stored value without throwing. computeIfAbsent delays the callback, although long-running loads still need a deliberate cache design.
What does this print?
Why. The null merge result removes the existing mapping. A null compute-if-absent result installs nothing. Null values are forbidden as stored values, but callback null results have defined control semantics.
A CopyOnWriteArrayList contains mutable Listener objects. A thread captures its iterator, then another removes a listener and changes that listener's plain mutable field without other synchronization. What is guaranteed?
Why. The snapshot holds the old array of references, so removal cannot retract its reference or cause ConcurrentModificationException. Copy-on-write does not clone elements or synchronize subsequent accesses to their fields; the iterator guarantees no particular value for that later field read.
Which queue statements are correct? Select all that apply.Select all that apply
Why. The linked constructor specifies capacity. The priority constructor specifies initial allocation, and that queue is unbounded. Future delayed elements are stored but unavailable for polling. A synchronous queue stores no elements between matching operations.
A semaphore starts with two permits. Both are held. A third caller's timed acquire returns false, but its finally still calls release(). After both real holders also release, with no other operations, how many permits are available?
Why. A semaphore tracks a count, not owners, and its initial count is not a maximum. False means no permit was acquired. Only successful acquisitions belong in a scope that later releases.
A healthy CyclicBarrier has several waiting parties, but its last party never arrives. Exactly one waiter uses a timeout; the others use untimed await(). Nobody is interrupted or calls reset(). What happens when the timed wait gives up?
Why. The timed waiter throws TimeoutException and breaks the barrier; the other waiters throw BrokenBarrierException. No party is deregistered, and the barrier stays broken until reset, so later arrivals also fail. await returns an arrival index on success, never a boolean. A phaser's interruptible wait has a different contract: timeout alone neither breaks it nor removes registration.
Workers register with a Phaser before submission. One submission is rejected, and nobody compensates. What is the bug?
Why. A phaser tracks counts, not task scheduling or thread identity. The submitter must undo a registration for work that cannot run. Merely waiting for a phase change does not contribute an arrival.

Write code
Implement addTag(key, tag) and tags(key) for a concurrent map of immutable tag lists. Updates for the same key must not lose tags, reads must return a stable list, and duplicate tags are allowed.
Model answer

compute combines reading the old mapping and replacing it for one key. Published lists are never mutated, and their strings are immutable, so returning the list does not leak writable state. Each append copies O(n) elements; large or write-heavy lists need another value representation. This is not an atomic snapshot across all keys.

Design
Producers submit faster than consumers finish. Choose a queue for at most 100 waiting FIFO jobs, explain timed submission and shutdown, and distinguish that bound from at most 100 unfinished jobs.
Model answer

I would choose ArrayBlockingQueue<Job>(100) or a capacity-100 LinkedBlockingQueue. Timed offer returns false if admission cannot complete within the budget, so the API reports rejection or applies an explicit retry policy. It must not acknowledge work it did not accept. take waits for a job; interruption is cancellation, not an empty job.

The bound covers waiting elements only. With W workers there can also be W running jobs. To bound unfinished jobs to 100, acquire an admission permit before enqueue and release it after processing finishes, or after submission fails. Shutdown first closes admission and resolves producers already submitting, then drains accepted work. With a FIFO poison-message protocol, enqueue one distinct stop message per live consumer after producers stop; handle consumer failure separately and join workers. The queue alone does not provide this lifecycle.

Debug
A batch coordinator's timed latch wait returns false, so it reads partial results. Elsewhere, a worker times out in Phaser.awaitAdvanceInterruptibly and calls arriveAndDeregister, even though it already called arrive for that phase. Diagnose both.
Model answer

A false latch wait means the batch is not known complete; some results may still be written and the full completion visibility guarantee is unavailable. Return timeout, or arrange cancellation and completion before reading unprotected results. Keep success or failure separate from the completion count.

The phaser wait does not arrive, cancel registration or break the phaser. After the worker already arrived, immediately calling arriveAndDeregister can contribute a second arrival to the same phase and consume another party's expected arrival. Use a defined coordinator protocol, such as terminating the whole phaser on failure, cancelling tasks and checking termination results, or arranging deregistration at a correctly tracked later phase. Do not infer a safe arrival from a timeout alone.

"We use a ConcurrentHashMap, yet our cache sometimes loads twice and our lists lose entries. Walk me through what you would inspect."
What a strong answer covers
  • The map protects mappings, not arbitrary call sequences or mutable value contents
  • putIfAbsent evaluates a supplied load before insertion; computeIfAbsent defers computation
  • Null results, exceptions and removal allow later computation; once forever is not guaranteed
  • Callbacks must stay short and must not modify the same map; expensive loads need shared in-flight state
  • Fix mutable lists with immutable replacement inside compute or separately synchronized values
How a senior would say it
I would inspect the exact update operation and the value type. A concurrent map protects its mappings; it does not make all surrounding work atomic. If the code passes a load call into putIfAbsent, every caller can run that load before the map chooses a winner. computeIfAbsent defers computation until needed and coordinates it for the key, but it is not a once-forever promise. A null result, an exception or later removal allows another computation. The callback must not modify that map. I would also avoid slow I/O inside it because it can delay other updates. For an expensive load, I would represent the shared in-flight result explicitly and define retry after failure. For lost list entries, I would look for an ArrayList stored as the value and mutated after the map call returns. That list is still unsafe. One fix is compute that copies the old list, appends and publishes an immutable replacement. Another is a value with its own synchronization. I would choose based on list size and update frequency, then test concurrent callers and loader failure.

Likely follow up: "What if a thread removes the key while another thread still holds its old mutable value?"

"You have a batch of tasks that discovers more tasks as it runs. Only eight remote calls may run at once. Which Java primitives would you choose, and how do failures change the design?"
What a strong answer covers
  • Use a semaphore with eight permits for simultaneous remote calls, not for counting completions
  • Use a phaser for dynamic task membership, with an initial coordinator party
  • Register before submission; compensate exactly once for rejected or never-started tasks; running tasks deregister in finally
  • Acquire successfully before entering the release scope; record failures separately from completion
  • Define cancellation because phaser waiting timeout does not deregister or break the phaser
How a senior would say it
I would separate the concurrency limit from completion tracking. An eight-permit semaphore limits remote calls. Each task acquires before the call and releases in a finally block entered only after acquisition succeeds. For a dynamically growing batch, I would use a phaser rather than a fixed-count latch. The coordinator starts registered so the phase cannot finish during initial submission. Every child is registered before submission, and rejected submission must undo that registration. A parent must register its children before it deregisters itself, so there is no gap where the batch appears complete. Each running task deregisters in finally and records its result or failure separately. Cancellation before startup needs coordinator cleanup that discharges that registration exactly once. Completion does not mean success. I would also define a batch cancellation policy. An interruptible phaser wait that times out neither removes a party nor breaks the phaser. For collective abort, the coordinator can terminate the phaser and request task cancellation, then join or otherwise observe task completion before consuming mutable results. The semaphore still needs cleanup on every successful acquisition, including during that cancellation.

"Choose between a bounded blocking queue, a SynchronousQueue and an Exchanger for handing buffers between threads."
What a strong answer covers
  • A bounded blocking queue stores up to a chosen number of waiting buffers and supports producer backpressure
  • SynchronousQueue stores nothing and requires a matching consumer for each transfer
  • Exchanger pairs participants and returns each other's buffer, supporting full-for-empty swaps
  • Queue timed offer and poll return false or null; timed exchange throws TimeoutException
  • Successful transfer publishes earlier writes but requires ownership discipline and a shutdown policy
How a senior would say it
I would choose based on whether we need buffering or a paired swap. A bounded blocking queue lets producers get ahead by a fixed number of waiting buffers. Timed offer lets the caller reject or retry when that capacity is exhausted. A synchronous queue has no storage: a transfer needs a matching consumer, so it fits direct handoff. It does not wait for the consumer to finish processing. An exchanger is different because both participants supply a buffer and receive the other's. That is useful when a producer trades a full buffer for an empty one to reuse. I would specify timeouts and failure handling: timed queue operations return false or null, while timed exchange throws a timeout exception. A successful transfer publishes earlier writes, but both threads must respect ownership afterwards. None of these choices provides a complete shutdown protocol, so I would define what happens if a partner exits.
