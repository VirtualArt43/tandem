A pair starts at (0, 1). A writer sets low to 1, then high to 2. Each field uses a Java volatile int or a C++ std::atomic<int> with default ordering. A reader reads low, then high and prints the pair. Which statement is correct?
Why. The writer can set low to 1, the reader can read both fields as 1, then the writer can set high to 2. Atomic individual fields prevent data races here, but do not make the pair an atomic snapshot. Consistent old and new pairs are possible too; neither consistency nor seeing only the old pair is guaranteed, and these operations do not throw. Capture one safely published immutable snapshot, or lock the whole pair.

An owner keeps changing a list and returns a read-only view: Collections.unmodifiableList(items) in Java, or const std::vector<int>& in C++. Is that view a safe snapshot for concurrent readers?
Why. Read-only access through one reference does not stop another reference from mutating the object. In Java this can produce inconsistent observations or ConcurrentModificationException, which is not guaranteed; in C++ concurrent vector mutation and traversal can be a data race. Copy under the owner's lock and publish the copy safely. Java's List.copyOf is shallow, so mutable elements also need attention. Speed is unrelated to this correctness issue.

A concurrent buffer, a lock or a dedicated parser thread would add machinery without protecting any actual sharing. Merely declaring a reference local would not suffice if it pointed to shared storage.

A map has individually thread-safe lookup and insert operations. Two threads check that key k is absent, load a value, then insert it. There is no lock covering that sequence. What is true?
Why. Both absence checks can finish before either insertion, so both loaders run and the second insertion can overwrite the first value. The map's own structure remains safe; this sequence need not deadlock. Java's ConcurrentHashMap.computeIfAbsent makes a per-key computation atomic; keep its callback short because other updates may block. A C++ wrapper can provide the equivalent operation under its lock. For slow I/O, publish an in-progress future and load outside the map lock.

A cache uses an individually thread-safe map and atomic size counter. It must keep size equal to the entry count and at most 1,000. For distinct absent keys, each insertion checks size < 1000, increments size, then inserts, using separate operations. What is the problem?
Why. At size 999, both callers can pass the check and then increment to 1,001. Independently, the counter differs from the map between an increment and its insertion. Neither atomic counters nor thread-safe maps combine the operations or supply a capacity policy. Put check, count and insert under one lock, including readers that require a consistent pair, or give them one owner.

C++ onlyA global const Config* current is replaced by a writer while readers do current->limit, with no synchronization or lifetime protocol. What is wrong?
Why. Even an immutable object's pointer is mutable shared state when it is replaced. Hardware-atomic pointer writes on x86 do not repair a C++ data race, and leaking the old object would not fix publication. Synchronize the holder with a mutex or suitable atomic operation. A std::shared_ptr<const Config> snapshot can retain the old object's lifetime, but concurrent access to the same shared-pointer holder still needs synchronization.

Java onlyA Config(int limit) record is fully constructed without escaping and stored in static Config current = new Config(100);. Later a writer replaces this plain, non-volatile field. Readers repeatedly capture the reference and call limit(). What can go wrong?
Why. Proper construction gives this final primitive field initialization safety once a reader obtains the record, but does not ensure that readers discover a later replacement of the plain field. They can retain the old reference. One captured record cannot mix fields from different objects, and no collection iteration is involved. Use volatile or AtomicReference for the changing holder; records with mutable components need additional care.

When is moving from a lock to lock-free code (rung 6) justified?
Why. Performance concerns alone and field count do not establish a benefit. Lock-free algorithms can be correct and useful, so "never" is also wrong. Measure, identify the linearization point, and justify progress and reclamation. A one-word rate limiter is a simpler starting point than a linked structure. A CAS instruction alone does not prove the whole operation lock-free.

A pool reuses the same worker for tasks A then B. A leaves its thread-local context as "alice". B does not set it and prints its value (context.get() in Java). What is printed?
Why. The worker retains the binding, so B prints "alice". A new task does not reset thread state, reading an existing binding throws no exception, and garbage collection does not clear a reachable binding. Use finally or an RAII guard at every request boundary.

A constructor starts a thread that reads a field, and the field is assigned on the line after start() (in C++: the member thread is declared before the vector it reads). What is the problem?
Why. this escapes during construction. In Java the thread may see default values, and final field guarantees do not hold for an escaped this. In C++ members are built in declaration order, so the thread may read a member that is not constructed. Both examples compile, and neither quick construction nor a release build establishes the missing ordering. Construct first, start later.

Four threads each count into their own HashMap (or unordered_map), created by the main thread and handed to them, and the main thread merges the maps after joining all four. Which statement is true?
Why. Ownership moves safely: thread start publishes what the main thread wrote before it, each worker is the only user of its map while it runs, and join publishes the worker's writes back. That is confinement with hand-off. Allocation on main does not force sharing during the work, so neither concurrent maps nor locks around each update are needed.

Why. A block scope thread_local has thread storage duration: one instance per thread, initialized on that thread's first pass and destroyed at thread exit. In a pool whose threads never exit, it lives as long as the program.

From: Single writer, actors and message passing
Owner A, while handling a message, asks owner B for a value and blocks on the future. B, while handling a message, asks A and blocks on its future. What happens?
Why. An owner that blocks cannot process its mailbox, including the request that would unblock the other side. Reply with continuation messages instead of blocking, or establish an acyclic wait graph with independent execution capacity. There is no automatic timeout or mailbox reordering that releases these blocked owners.
From: Single writer, actors and message passing
Senders produce 10,000 messages per second and the owner can process 6,000. These rates persist, nothing drops messages, and the mailbox is unbounded. What happens over time?
Why. With sustained fixed rates, the backlog grows at 10,000 minus 6,000 = 4,000 messages per second. An unbounded queue neither drops nor blocks because of capacity, and it cannot increase the owner's service rate. A bounded mailbox makes senders wait (back-pressure) or get rejected, which surfaces the overload where it can be handled.

A keyed executor has stable routing and FIFO lanes. Two concurrent callers enqueue commands for key K: one sets its value to 1, the other sets it to 2. After both enqueue calls return, a third command for K prints the value. What can it print?
Why. K always maps to one lane. Its print command runs after both writes, so it cannot see the initial value. The two concurrent writes have no predetermined call-start order, so either can be last. This is per-lane enqueue order, not a global order across lanes; different keys can also collide into one lane.

A deposit handler changes the balance and then throws before completing its reply. A wrapper catches the exception and fails that future. Which guarantee follows?
Why. A failed reply reports an error, not a transaction rollback. A catch can let the loop continue, but changed state remains unless code restores it. Neither retry nor owner death follows automatically. If an exception escapes the wrapper, Java ends that thread while C++ calls std::terminate, which normally ends the process.

A developer adds a getBalanceFast() method that reads the actor's private HashMap (or C++ unordered_map) directly from the calling thread, "because reads do not change anything". What is wrong?
Why. A read concurrent with a write is a data race. The owner's writes are only safe because nobody else touches the map. Ask the owner, or have it publish an immutable snapshot for fast reads.

Why. One thread doing 50 ms of blocking work per message completes at most 1000 / 50 = 20 per second. Move slow I/O out of the owner (or batch it, as the event writer does with one flush per batch), and keep the owner for the state changes.

With sustained input above 8,000 items per second, bounded blocking queues and negligible overhead, a three stage pipeline can do 50,000, 8,000 and 20,000 items per second in its three stages. What is the pipeline's throughput, and which queue fills up?
Why. The slowest stage sets the pace. Work arrives at the second stage faster than it can handle, so the queue in front of it is the full one, and with bounded queues the first stage then blocks. The full queue points at the bottleneck.

Why. A queue hands each item to exactly one taker. Send one marker per worker, and have the downstream stage count one marker per upstream worker before it stops.

A producer makes 5,000 items a second, a consumer handles 3,000, and the queue between them is unbounded. Assume constant rates and enough memory for ten minutes. How much backlog accumulates?
Why. The excess is 5,000 minus 3,000 = 2,000 per second; 600 seconds adds 1,200,000 items. There is no automatic dropping or throttling in this model, and the slower consumer cannot catch up while rates stay constant. A bounded queue would make the producer block at the capacity, settling the item flow at 3,000 a second with a bounded queue backlog.

Why. A wait releases only the lock of the monitor you wait on. That is nested monitor lockout. Release your own lock before blocking on another object, or restructure so you never wait while holding it.

A pool's close() sets closed = true under the lock and calls signalAll(), but acquire() waits with while (available == 0) permitFree.await();. No permit is released. What happens to a thread blocked in acquire() when the pool closes?
Why. Signalling only makes waiters re-check their predicate. If the predicate does not include the closed flag, they re-check, see nothing new, and sleep again. Every wait must be while (available == 0 && !closed), followed by a check of closed.

Inside a monitor method, while holding the lock, a class calls listener.onChange(newValue) on listeners registered by other code. Why is this risky?
Why. Code you do not control, run under your lock, inherits your lock. Copy what the callbacks need while holding the lock, release it, and then call them: an open call.
