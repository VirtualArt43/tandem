CPU caches, coherence and false sharing

How CPU caches and coherence work, why two threads writing different variables can slow each other down, and how to fix it.

Asked atMicrosoft
Before this:Visibility: why a thread may never see your writevolatile in Java, std::atomic in C++

Correct code can still be slow for a reason you cannot see in the source. Two threads that never touch each other's variables, with no locks and no data races, can still fight over the hardware, because their variables happen to share a cache line.

In plain words

Two students share one notebook page. One writes only on line 3, the other only on line 30, so they never overwrite each other's work. But only one of them can hold the page at a time, so they keep passing it back and forth across the table, and each spends most of the time waiting for the page instead of writing.

A CPU core works the same way: it can only write to memory in whole cache lines that it holds exclusively. If two cores write different variables in the same line, the line ping-pongs between them. That is false sharing: the program shares nothing, the hardware shares everything. The fix is to give each student their own page.

The memory hierarchy

Main memory is far slower than a CPU core, so each core has small, fast caches, backed by larger, slower ones. The numbers below are orders of magnitude for a modern desktop or server chip; exact values vary by processor.

LevelTypical sizeShared byLatency (order of magnitude)
Registershundreds of bytes to a few KBone coreunder 1 ns
L1 data cachetens of KB (32 to 128 KB)one coreabout 1 ns, a few cycles
L2 cachehundreds of KB to a few MB (Apple's shared L2 is larger)one core, or a cluster of coresa few ns
L3 or system level cachetens of MBmany or all cores on the chipabout 10 to 20 ns
Main memory (DRAM)GBseverythingabout 100 ns

A hundred nanoseconds is hundreds of cycles in which the core could have done useful work. Caches are why most code runs fast, and why access patterns (walking an array in order, keeping hot data small) matter so much for performance.

Cache lines

Caches do not hold individual bytes or variables. They hold fixed-size blocks called cache lines, and every transfer between memory, caches and cores moves whole lines. A line is 64 bytes on most x86 chips; Apple M series chips report 128 bytes (on macOS, sysctl hw.cachelinesize prints 128 on this site's machines). On Linux, getconf LEVEL1_DCACHE_LINESIZE tells you.

So when a thread reads one long, the core actually fetches the 7 or 15 neighboring longs too. That is great for arrays (the next element is already there) and terrible when two threads write neighboring variables. Java gives you no API for the line size, and C++17 offers std::hardware_destructive_interference_size, a compile-time constant that is the compiler's guess. That guess can be off: Apple's clang sets it to 64 on M series chips, whose OS reports 128.

Coherence: how cores agree, in plain words

If every core has its own copy of a line, something must stop them from disagreeing. That is cache coherence, and the classic protocol is called MESI after the four states a line can be in, in each core's cache:

StateMeaningCan this core write it without asking?
ModifiedOnly this cache has it, and it has been changed (memory is out of date)Yes
ExclusiveOnly this cache has it, unchangedYes (it becomes Modified)
SharedOther caches may hold a copy too, all unchangedNo: it must first invalidate the other copies
InvalidThis cache's copy is not usableNo: it must fetch the line first

The one rule that matters: to write a line, a core must hold the only valid copy. It sends an invalidation to every other core holding the line (and fetches the data too if its own copy is Invalid), waits for the others to acknowledge, and only then holds the line in the Modified state. Reads of a line that another core has modified make the owner supply the data, and both copies become Shared. Real chips use richer variants (Intel's MESIF, AMD's MOESI), but the write rule is the same.

Reads alone are cheap: any number of cores can hold a line in Shared and read it at full speed, with no traffic at all. It is writes that force transfers, so read-mostly data shares well, while one writer next to many readers makes every reader miss again after each write.

Coherence is also why the visibility lesson said caches are not the reason a flag goes unseen: the hardware keeps every core's copy of a line consistent. What coherence does not make cheap is moving a line between cores: each transfer costs tens of nanoseconds or more, one to two orders of magnitude slower than an L1 hit.

False sharing, measured

False sharing is exactly that ping-pong: independent variables written by different threads, sitting in one line. It produces no wrong answers and no warnings, only lost speed, and it gets worse with every thread you add. The demo below has two threads each add 1 to a counter millions of times, in three layouts: both on the same counter (real sharing), on neighboring counters 8 bytes apart (false sharing), and on counters in separate lines.

Timings vary with the machine, its load, and the language (the C++ version runs under ThreadSanitizer, which slows every atomic operation, so it does fewer iterations). The shape is what to look at: neighboring counters are about as slow as one shared counter, typically 2 to 5 times slower than counters on separate lines. To the cache, false sharing is sharing.

One Java caveat shows why padding in Java is fiddly. The JVM only aligns objects to 8 bytes, so you cannot choose where an array starts relative to a line boundary. A pair of neighbors lands in two different lines whenever the first slot is the last long of its line, and then that pair shows no slowdown at all. Because allocation is repeatable, this can happen on every run, not once in a while: on this site's machine, slots 0 and 1 of the first round's array straddle a 128 byte boundary every time. That is why the Java demo times two neighbor pairs 4 slots apart and reports the slower one: lines hold 8 or 16 longs, so at most one of the two pairs can straddle. Separating slots by 16 longs (128 bytes) or more is safe wherever the array starts.

Fixing false sharing

There are three fixes, from most local to most fundamental.

  1. Pad or align each hot, independently written variable onto its own line.
  2. Spread array slots out: per-thread slots every 16 longs instead of every long.
  3. Write shared memory less often: accumulate in a local or thread-local variable and publish occasionally, or merge results at the end.
C++

C++ alignment options. alignas(64) is right on most x86 machines; alignas(128) is the safe portable choice, because Apple M series chips report 128 byte lines and Intel's spatial prefetcher tends to pull lines in 128 byte pairs. alignas(std::hardware_destructive_interference_size) (C++17, header <new>) states the intent, but it is a compile-time constant that can disagree with the machine the code runs on, and GCC even warns when it is used in a header, because its value can change with tuning flags and silently change a type's layout. Since C++17, new and std::vector respect over-aligned types, so a std::vector<PaddedCounter> really does put each element on its own boundary.

Java

Java padding options. Spreading slots in an array, as above, is the most reliable trick, because array elements are laid out contiguously. Padding an object with unused long fields is fragile: the JVM decides field order, and newer JVMs group fields by size. The JDK's own fix is the @Contended annotation (jdk.internal.vm.annotation.Contended), which pads a field or class by 128 bytes on each side by default. Outside the JDK it is ignored unless the JVM runs with -XX:-RestrictContended, and since it lives in an internal package, javac must also be told to export that package to your code, so it is rarely worth it in application code. LongAdder uses it internally on its cells, which is one reason it scales. To see real object layouts, use the OpenJDK JOL tool (Java Object Layout).

True sharing: when padding cannot help

If many threads write the same variable, it is not false sharing, it is true sharing, and the line must visit every writer in turn whatever you do with padding. The demo's "same counter" column is exactly that. The only fixes change the design: stripe the variable across cells and combine on read (Java's LongAdder, a sharded counter in C++), let each thread accumulate privately and merge at the end, or batch updates. You will build these in counters at scale. The same applies to locks: a lock word that every thread writes is a hot line, which is one reason striped locks (lock striping) scale better than one global lock.

NUMA, in one paragraph

On a multi-socket server, each CPU socket has its own memory controller and its own DRAM. Reading memory attached to the other socket goes over an interconnect and is noticeably slower, very roughly 1.5 to 2 times local latency, and moving cache lines between sockets is slower than between cores of one chip. That is NUMA (non-uniform memory access). Operating systems usually allocate a page on the node of the thread that first touches it, so a thread that migrates to the other socket, or a buffer initialized by the wrong thread, can quietly lose performance. Tools: numactl and libnuma on Linux to pin threads and memory; for Java, -XX:+UseNUMA lets the Parallel and G1 collectors allocate memory on the node of the allocating thread. It mostly matters for large in-memory systems such as databases and caches on big machines, which is where it comes up in design interviews.

Worked example: a stats array that does not scale

A server keeps per-worker request counts in a plain array so that a reporter thread can sum them: long[] counts = new long[workers] in Java, std::vector<std::atomic<long>> counts(workers) in C++. Each worker increments only its own slot. With 1 worker it handles 2 million requests a second; with 8 workers, throughput barely improves.

  1. Correctness first. In C++ the slots are atomics, so the reporter's reads are race free. In Java, a plain long[] written by one thread and read by another is a data race; switch to AtomicLongArray or LongAdder.
  2. Diagnose. Eight slots of 8 bytes span 64 bytes: one or two 64 byte lines, or one or two 128 byte lines, depending on where the array starts. Either way each line holds several workers' slots, so every increment invalidates that line in the cores of the other workers that share it: false sharing.
  3. Fix. Space the slots 16 longs apart, or use padded per-worker counters as in the code above, or LongAdder, which pads its cells.
  4. Do better. Each worker counts in a local variable and adds to its shared slot every thousand requests, or the reporter asks workers for their totals; the shared line is then written a thousand times less often.
  5. Verify. Measure before and after with a real benchmark harness (JMH for Java, Google Benchmark for C++) and a profiler; on Linux, perf c2c is built to find false sharing by showing contended cache lines.

Common mistakes

  • Per-thread slots in a plain array. "No sharing, so no problem" is true for correctness and false for performance.
  • "Each thread has its own object, so they cannot share a line." Small objects allocated one after another usually sit next to each other: a Java thread allocates from its own buffer in order, so eight AtomicLong objects created in a loop are neighbors, and malloc or new packs small blocks close together too. Separate objects are not separate lines; use LongAdder, array striding, or aligned types.
  • Assuming 64 bytes everywhere. Apple M series chips report 128. Pad to 128 when you do not control the hardware.
  • Padding only one side. A padded counter can still share a line with whatever the allocator places right after it. Align the start of each hot object to a line boundary and make its size a multiple of the line.
  • Padding everything. Padding wastes memory and cache space, which slows down everything else. Pad only hot variables written by different threads.
  • Trusting Java field padding. The JVM may reorder or pack fields; use array striding, LongAdder, or @Contended with the JVM flag.
  • Confusing false sharing with lock contention. Both show up as poor scaling. False sharing happens with no lock at all; a profiler that shows time spent on memory accesses (rather than in lock waits) points to it.
  • Micro-benchmarks without warm-up. Short Java timing loops measure the JIT, not the cache. Use JMH, repeat runs, and report ranges.

In the interview

This is a senior depth topic. It appears as "why does this counter not scale with more threads?", as a follow up to "how does LongAdder work?", and as hardware depth: a 2025 Microsoft senior loop in Hyderabad pushed a candidate on how Java volatile and synchronized work down to CPU caches and registers. It also hides inside design rounds: one Meta candidate designing a single-machine memcache was praised for sharding the table about one shard per core so that locking would contend less, which is the true sharing problem solved at the design level.

If per-thread counters do not scale with cores, I would check for false sharing: independent variables written by different threads that sit in the same cache line, so the line ping-pongs between cores even though no data is shared. Cache lines are 64 bytes on most x86 and 128 on Apple's chips. I would fix it by padding or aligning each hot variable to its own line, or spreading slots apart, and better still by updating shared memory less often. If they all write the same variable, that is true sharing, and only striping, like LongAdder, or per-thread accumulation helps.

Follow ups to expect:

  • "How big is a cache line, and how do you find out?" 64 on most x86, 128 on Apple M series; getconf or /sys on Linux, sysctl on macOS.
  • "What is MESI?" Four states per cached line; a writer must invalidate every other copy first.
  • "Why does LongAdder beat AtomicLong under contention?" Threads hash to different padded cells, so they write different lines; sum() adds the cells.
  • "Why can adding threads make it slower?" More cores fighting over one line means more transfers per useful operation.
  • "How would you detect it in production?" Poor scaling with low lock contention; perf c2c on Linux; then confirm by padding and re-measuring.
  • "Where else does it show up?" The head and tail indices of a ring buffer, written by the consumer and the producer: put them on separate lines, and let each side keep a cached copy of the other's index, rereading the shared one only when the buffer looks full or empty. Also a lock word next to unrelated hot data, and per-thread result slots in one array.
  • "Do readers suffer too?" Many readers of a line nobody writes cost nothing. One writer next to them makes every reader miss again after each write, so keep a hot written field away from read-mostly fields.

Senior depth

Store buffers and invalidation queues. Waiting for every invalidation acknowledgement before each write would stall cores constantly, so CPUs add a store buffer (writes wait there while the line is being claimed) and, on many designs, an invalidation queue (incoming invalidations are acknowledged before they are applied). These two structures are what make perfectly coherent caches look out of order at the instruction level, and fences exist to drain or order them. That is the hardware story behind reordering.

Atomics on hot lines. An uncontended atomic increment on a line already owned by the core costs a few nanoseconds. The same increment on a line that another core just wrote needs a cross-core transfer first, roughly tens of nanoseconds on one chip and more across sockets, so contended atomics are an order of magnitude or two slower than uncontended ones. This is why lock-free code is not automatically fast, and why much of the cost of a contended lock is moving the cache line it lives in.

Constructive interference. C++17 also defines std::hardware_constructive_interference_size: the size within which data you want together should fit, so that one line fetch brings all of it. Grouping fields that are read together (and separating fields written by different threads) is the full layout rule.

Key takeaways

  • Caches move whole lines: 64 bytes on most x86, 128 bytes reported on Apple M series chips.
  • Coherence (MESI) keeps caches consistent; a core must own the only valid copy of a line to write it, so writes to a shared line force transfers between cores.
  • False sharing: threads writing different variables in one line. No wrong answers, just lost speed, often as bad as true sharing.
  • Fix it by aligning or padding hot per-thread data to its own line (prefer 128 when unsure), spreading array slots, or writing shared memory less often.
  • True sharing needs a design change: striping (LongAdder), per-thread accumulation, batching. NUMA adds a cross-socket cost on big servers.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A teammate's benchmark: 8 threads, each increments counts[threadIndex] 100 million times, where counts is an AtomicLongArray of length 8 (Java) or a std::array<std::atomic<long>, 8> (C++). It is barely faster than one thread. Explain why, and rewrite the counter layout so it scales.
Model answer

Every thread writes its own slot, so there is no data race and no logical sharing, but all 8 slots together take only 64 bytes, so they sit in one or two cache lines, each holding several threads' slots. Each increment requires the writing core to own its slot's line exclusively, so each line is passed between the cores that share it on nearly every operation; the threads spend their time waiting for cache line transfers. That is false sharing. The fix is to put each thread's counter on its own line, and to write shared memory less often.

Better still, each thread can count in a local variable inside its loop and call add once at the end (or every few thousand iterations), which removes almost all shared writes. I would confirm with a proper benchmark, JMH or Google Benchmark, comparing the two layouts with 1, 2, 4 and 8 threads.

Explain
An interviewer asks: "Explain cache coherence and false sharing, and tell me how LongAdder (or a sharded counter) avoids the problem that AtomicLong (or one std::atomic) has." Answer as you would out loud.
Model answer

Each core caches memory in fixed-size lines, 64 bytes on most x86 chips and 128 on Apple's. A coherence protocol, MESI or a variant, keeps the copies consistent: each core's copy of a line is Modified, Exclusive, Shared or Invalid, and a core can only write a line when it holds the only valid copy, so it first invalidates everyone else's. That keeps caches correct, but it means a line that several cores write keeps moving between them, and each move costs tens of nanoseconds or more.

False sharing is when threads write different variables that happen to share a line: logically independent, physically contended, so it scales as badly as if they shared one variable. One AtomicLong has the related true sharing problem: every thread writes the same variable, so every increment needs the line. LongAdder keeps a base value plus an array of cells; under contention threads hash to different cells, and the cells are padded with @Contended so they sit on different lines, so increments mostly hit a line the core already owns. sum() adds up the cells, which makes reads slower and only approximately current while writers are active, a good trade for counters that are written far more than they are read. In C++ the same idea is an array of atomics each aligned to 128 bytes, one per thread or per hash bucket, summed on read.

Numbers
Give rough, order of magnitude numbers for: an L1 hit, a main memory access, and a cache line transfer between two cores on one chip. Then estimate the throughput ceiling of a single counter that 16 threads increment, if every increment needs the line to move.
Model answer

Orders of magnitude: an L1 hit is about 1 ns (a few cycles), main memory is about 100 ns, and a cache line transfer between cores on one chip is in the tens of nanoseconds, say 50 ns for estimation; across sockets it is more.

If every increment must first pull the line to the incrementing core, the increments are serialized on that line: at roughly 50 ns per transfer, the whole machine manages about 1 / 50 ns = 20 million increments per second on that one counter, no matter whether 2 or 16 threads are trying. Adding threads does not raise that ceiling; it only adds waiting. By contrast, 16 threads each incrementing their own padded counter in their own L1 cache can each do hundreds of millions of increments per second. That gap, one or two orders of magnitude, is why striped counters like LongAdder exist. These are estimates; I would measure on the real hardware before relying on them.

Out loudabout 90 s
"Here is a symptom: a single producer, single consumer ring buffer is correct, but much slower than expected. The head and tail indices are declared next to each other. What would you look at, and how would you fix it?"
What a strong answer covers

  • Mechanism: a core can only write a line it holds as the only valid copy, so the line bounces between the two cores on almost every operation, tens of nanoseconds each
  • It is not a correctness bug: no data race and no wrong answers, so no test or race detector flags it

  • Go further: each side caches the other's index and rereads it only when the buffer looks full or empty; measure before and after, with perf c2c on Linux
How a senior would say it
My first suspect is false sharing between the two indices. The consumer writes the head and the producer writes the tail, and if they sit next to each other they share one cache line. A core can only write a line when it holds the only valid copy, so every update by one side invalidates the other side's copy, and the line bounces between the two cores on almost every operation. Each bounce costs tens of nanoseconds, against about a nanosecond for a write to a line the core already owns. Nothing is wrong logically. There is no data race and no wrong answer, which is why no test or race detector flags it. The fix is layout. I would put the head and the tail on separate lines, aligned to 128 bytes in C++, and in Java spaced apart or padded, because the JVM decides field order. A further step is for each side to keep a cached copy of the other side's index and reread the shared one only when the buffer looks full or empty, so the lines move far less often. Then I would measure before and after, and on Linux perf c2c shows the contended line directly.

"The hardware keeps caches coherent. So why do we still need volatile in Java or std::atomic in C++?"
What a strong answer covers
  • Coherence keeps each single line consistent: a writer invalidates the other copies, so no core reads a stale copy of a line forever
  • The compiler or JIT may keep a value in a register and never read memory again, and coherence never sees registers
  • Store buffers and invalidation queues delay writes, so writes to different locations can be seen in a different order
  • Coherence is per location; ordering across locations is the memory model's job
  • volatile, atomics and locks restrain the compiler and emit the fences; coherence only decides how much that costs
How a senior would say it
Because coherence solves a smaller problem than the one we have. Coherence means every core agrees on each single cache line: before a core writes a line it invalidates every other copy, so no core keeps reading a stale copy of that line forever. But three things sit outside it. First, the compiler or the JIT may keep a variable in a register and never read memory again, and coherence never sees a register. Second, each core has a store buffer, so its writes reach the cache late, and another core can see two writes to different locations in a different order than they were made. Third, the compiler and the CPU reorder independent operations for speed. Coherence is per location; ordering across locations is the memory model's job. So volatile, atomics and locks do what the hardware alone does not: they stop the compiler from caching or reordering across them, and they emit the fences that order the store buffer. Coherence then makes those guarantees cheap to deliver. Correctness comes from the language rules, and the caches decide the cost.

Out loudabout 90 s
"You have two minutes: design a request counter for a 64 core server. Every request increments it, and a metrics thread reads it once a second."
What a strong answer covers
  • One shared atomic is true sharing: every increment moves its line, so the whole machine is capped at tens of millions of increments a second, as an order of magnitude, however many cores you add
  • Stripe it: per-thread or per-cell counters, each on its own line, summed on read (LongAdder in Java; 128 byte aligned cells with relaxed fetch_add in C++)
  • Read side trade off: the sum is slower and not an atomic snapshot while writers run, which is fine for a metric read once a second
  • Cost: one cache line of memory per cell
  • If still hot: count in a thread-local and publish every N requests; confirm with a benchmark at 1, 8 and 64 threads
How a senior would say it
I would not use one shared atomic. Every increment needs that counter's cache line in the incrementing core, so with 64 cores the line just moves from core to core, and the whole machine is capped at something like tens of millions of increments a second, as an order of magnitude, however many cores I add. Since the counter is written on every request and read once a second, I would stripe it. In Java that is LongAdder, which sends contending threads to different cells, padded onto separate lines, and adds them up in sum(). In C++ I would keep an array of counters, each aligned to 128 bytes so no two share a line, give each thread its own cell, increment it with a relaxed fetch_add, and sum the cells on read. The trade off is a slower read, and the sum is not an exact snapshot while writers are running, which is fine for a metric read once a second. It also costs a cache line of memory per cell. If that is still too hot, each thread can count in a local and add to its cell every thousand requests. Then I would benchmark at 1, 8 and 64 threads to confirm it scales.
