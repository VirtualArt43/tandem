Backup retention service

Thread-safe designshard55 minRubrik

An expired incremental backup can still be the only path to a live restore point. Deleting by timestamp alone can destroy a recovery chain.

The task

Implement a thread-safe forest of backups. A backup has one immutable parent or is a full-backup root. An expired backup must remain while a live descendant needs it. expireBackups(now) removes every eligible backup atomically and returns the exact number removed.

Rules

  • New IDs and timestamps range from zero through the largest signed 64-bit value. A negative new ID or deadline throws IllegalArgumentException in Java or std::invalid_argument in C++, without changing state.
  • Adding an existing ID or a nonexistent parent returns false without changing any metadata, including the existing parent and deadline. A negative parent is nonexistent. Self dependencies fail too. New nodes only point to existing nodes, so successful adds cannot create cycles.
  • A backup is live at the supplied timestamp exactly when expiresAt > now. A deadline equal to now has expired. Keep all ancestors of every live backup, including expired ancestors. A live ancestor does not retain expired descendants. Remove the whole expired remainder, including internal nodes and leaves, in the same expiry operation.
  • Expiry timestamps must be nonnegative and nondecreasing in the order expiry operations take effect. A negative time or a time below the last successful expiry throws IllegalArgumentException or std::invalid_argument, without changing the forest or the last successful time. Equal timestamps are legal, including concurrent calls with the same timestamp. Each call sweeps the current forest, even if the timestamp has not changed.
  • Adds with an already-past deadline are allowed. They remain stored until the next expiry call removes them or retains them for a live descendant. size() counts all stored backups, including expired ancestors and newly added expired backups.
  • findRecoveryChain returns a detached, complete root-to-target list, or empty if the target is absent. IDs need not increase along a chain. The result describes one instant during the call and does not change after later adds or expiry. Java may return an immutable list. If the result is mutable, changing it must not change the service.
  • Deleted IDs may be reused as new independent identities once callers stop using the old identity in API calls. Old detached lists are historical data, not lifetime pins for a restore that starts later. Reuse must not inherit an old parent, deadline or cached chain.
  • Every API is thread safe. Adding a child and deleting its parent must serialize: either the live child commits first and retains the parent, or expiry removes the parent first and the add fails. Duplicate adds have exactly one winner; its parent and deadline stay paired. Concurrent expiry calls cannot split one atomic sweep or count a deletion twice.
  • Recovery readers must overlap. The supplied reading(id) hook is nonthrowing and nonreentrant, and is a no-op in production. Call it exactly once per lookup, including an absent target, with the requested ID before traversal and under read protection. Adds and expiry must wait while the hook holds that protection. Keep the forest stable for the complete traversal.

Worked example

A full backup expires at 5, its child at 20 and grandchild at 30. Expiry at 10 or 20 keeps all three. At 30 there is no live dependent and all three are removable.

What the tests check

  • A live grandchild keeps multiple expired ancestors. Expired siblings and internal branches disappear even below a live root. Exact deadline equality removes the entire eligible remainder.
  • Absent targets, missing and self parents, duplicate rejection without overwriting the original parent or deadline, zero IDs and full-width timestamps.
  • Negative arguments, decreasing expiry times, unchanged state after rejection, and lock release on exception paths. Repeated timestamps sweep newly added expired backups.
  • Detached recovery results survive deletion and ID reuse. Changing a mutable returned list does not alter the service.
  • Gated hooks prove two readers overlap and block both an add and an expiry until they finish. Hook arguments and invocation counts are checked.
  • Eight competing duplicate adds choose one intact winner. Thirty-two child-add versus sole-parent-deletion races accept either legal serial order. Concurrent expiry calls remove the forest exactly once.
  • Eight seeded adders race an expirer while querying chains and size, then a final sweep removes all nodes. Seed 721 fixes launch shuffles, not the scheduler. Worker failures are reported; watchdogs and bounded joins stop stalled solutions. C++ also runs under ThreadSanitizer.

Separate the set of live nodes from the set of nodes that must be retained.
Start at every live node and mark its ancestor path, stopping when you reach an already marked node.
Make marking and deletion one write-locked operation. An add cannot publish a dependency into the gap between them.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What did the Rubrik report ask?
The 2026 CPD report describes add_dependency, recovery-chain lookup and expiry that preserves dependencies, with every API thread safe. The candidate completed the sequential part but ran out of time on synchronization; this exercise makes that concurrency requirement explicit.
How do you protect a long-running restore?
Return a lease or pin that increments retention references for the required chain. Release it when restore ends. A detached list alone does not keep backup data alive after the lookup returns.
Can you avoid scanning the whole forest?
Maintain live-dependent counts or a leaf-expiry heap, but updates to deadlines, ancestry and dependency counts must be atomic together. Compare that complexity with a simple marked snapshot first.
What changes for several parents?
The structure becomes a DAG. Mark every reachable ancestor, reject cycles during dependency changes, and preserve all paths needed by a recovery policy.
Can physical object deletion happen under the metadata lock?
Prefer marking an immutable deletion batch under the lock, then doing slow storage calls outside it with generations or tombstones. Retries must not delete a new object that reused the same logical ID.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

Key idea and invariants

Every stored nonroot node has a stored parent. Under the write lock, expiry marks the transitive ancestor closure of live nodes and deletes its complement. A retained node's entire chain is retained. Adds and expiry share the same write lock, so neither can observe or create half a dependency transition.

Why these primitives

A read-write lock gives recovery traversals a stable forest and permits readers to overlap. The exclusive mode protects insertion, the expiry watermark and the complete mark/delete pass. Validate a decreasing time before updating that watermark, and release locks even when validation throws. Equal timestamps still need a new sweep because an intervening add can introduce an expired node. A global metadata write lock is deliberate here; parallel storage I/O is a separate extension. There is no wall-clock dependency because expiry receives its timestamp.

Pitfalls and broken interleaving

The broken version computes expiry using each node's own deadline. A live child is accepted, then the expirer deletes its old parent. The map remains individually synchronized but the recovery invariant is lost.

Cost and interview explanation

Each marking pass visits each retained node once, plus a scan of all nodes: expected O(N) with Java hashing, O(N log N) with the C++ ordered maps and sets. A chain query costs its height times lookup cost and allocates a detached result of that height. Temporary marking space is O(N). Mark ancestors only: keeping every descendant of a live root leaks expired branches. Say: “I will delete the complement of live ancestry, not every expired timestamp. The metadata lock makes dependency admission and the expiry snapshot one serial order.”
