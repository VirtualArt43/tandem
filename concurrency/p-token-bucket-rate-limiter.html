Token bucket rate limiter

Concurrent systemsmedium30 minRubrik system coding (rate limiter, single threaded, then concurrent)Rubrik

Rate limiters show up in Rubrik system coding rounds as "single threaded first, then make it concurrent, then distributed". The token bucket is the version to know cold: a few lines of arithmetic, a lazy refill instead of a timer thread, and one classic race that lets through more requests than the limit.

The task

Build a per key rate limiter. Each key (a user, an IP address, an API token) has its own bucket:

  • A bucket holds at most burst tokens and is full when its key makes its first request.
  • Tokens flow back in at ratePerSecond, continuously: fractions of a token count and add up.
  • tryAcquire(key) takes one token and returns true if at least one whole token is there; otherwise it returns false and takes nothing. It never blocks.
  • Refill lazily: when a request arrives, work out how many tokens the elapsed time has earned. No background thread.
  • Read time only from the given Ticker, a monotonic nanosecond clock (the tests move it by hand).
  • Many threads call tryAcquire at once, for the same key and for different keys. The limit must hold exactly.

Worked example

Rate 10 per second (one token every 100 ms), burst 5. A new key sends 6 requests at time 0: the first 5 pass and the bucket is empty, so the sixth fails. At 99 ms the bucket holds 0.99 tokens: fail. At 101 ms it holds 1.01: pass, leaving 0.01. After 10 idle seconds it holds 5, not 100, because a bucket never holds more than burst.

What the tests check

  • Burst then steady rate, exactly as in the worked example.
  • Fractions are kept: with burst 1, take the token, wait 60 ms (0.6), try (fail), wait 60 ms more (1.2), try (pass).
  • The refill stops at burst, and a new key starts full.
  • Keys are independent.
  • 8 threads make 8000 attempts on one key with a full bucket of 2000 and time frozen: exactly 2000 pass.
  • 8 threads hit each of 300 brand new keys at the same instant: each key admits exactly burst (3), so a bucket is never created twice.
  • While the threads themselves move the clock forward 800 ms, at most 10 + 800 requests pass.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Thread-safe rate limiters

Open them one at a time. Each one gives away a little more.

A bucket needs two fields: tokens (a double) and last, the time tokens was last brought up to date. On every request: tokens = min(burst, tokens + (now - last) * rate / 1e9), last = now, then take one if tokens >= 1.
Those few lines are a read, modify, write of two fields that must change together. Guard each bucket with its own lock (a synchronized method, or a std::mutex inside the bucket). A concurrent map alone does not make the bucket's arithmetic safe.
Creating the bucket for a new key must be atomic too, or two threads each create a full bucket and the key gets twice its burst. In Java use computeIfAbsent; in C++ create it under the map's mutex and keep a stable pointer (a std::unique_ptr in the map), then lock the bucket itself.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why compute tokens lazily instead of a thread that adds tokens every few milliseconds?
A refill thread costs a thread, wakes up even when nobody calls, has to touch every bucket (a million keys means a million updates per tick), and is only as precise as its period. The lazy formula is exact, costs O(1) per request, and does nothing for idle keys. A 2022 Rubrik report suggests exactly this trade-off came up in the round.
Why a monotonic clock and not the wall clock?
Wall clock time can jump backwards or forwards (NTP corrections, manual changes). A backwards jump makes elapsed time negative; a forwards jump hands out a burst of free tokens. System.nanoTime and std::chrono::steady_clock only move forward, which is what elapsed time needs.
The map of buckets grows forever. What would you do?
A bucket that has been idle for at least burst / rate seconds is full again, so it carries no information: it can be dropped and recreated on the next request without changing any answer. Sweep such buckets periodically, or keep them in an access ordered map with a size cap.
How is a token bucket different from a leaky bucket?
A token bucket allows bursts up to burst and then the long run rate. A leaky bucket, used as a meter, is the same idea seen from the other side; used as a queue, it smooths traffic to a constant output rate by delaying requests instead of rejecting them. Rubrik has asked for a leaky bucket in one report.
How would you make it work across many servers?
Keep the bucket state in a shared store and update it atomically there, for example a Redis script that does the refill and the take in one step, or shard keys so each key's bucket lives on one server. A cheaper approximation gives each of N servers rate / N, which over-limits when traffic is uneven.
Can you avoid floating point?
Yes: store tokens in units of 1 / rate seconds, or keep "the time at which the bucket will next be full" as a single integer (the GCRA formulation). One integer per key also allows a lock-free version with a single compare-and-swap per request.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

A token bucket is two numbers per key and one formula. Because the refill is computed from elapsed time when a request arrives, there is no timer and no background thread: the whole limiter is a map of small monitors. The concurrency work is to make each bucket's update atomic and to make bucket creation atomic.

Invariants

  • 0 &lt;= tokens &lt;= burst for every bucket, always.
  • Tokens admitted for a key over any run are at most burst + rate * elapsed.
  • Each key has exactly one bucket for the life of the limiter.

Why each primitive

  • A lock per bucket: the refill and the take read and write tokens and last together, so they form one critical section. A per key lock means two hot keys never wait for each other.
  • computeIfAbsent, or creation under the map mutex: the check "is there a bucket?" and the act "create one" must be one step.
  • Reading the clock inside the bucket lock: then the lock orders the readings, so now never goes backwards for one bucket. Reading it before taking the lock lets a thread with an older reading move last backwards, and the same time span gets paid out twice.

Pitfalls

  • Unsynchronized bucket fields inside a concurrent map: lost updates, more requests than the limit. This is the broken version the tests catch.
  • get, then put a new bucket if missing: two threads create two full buckets for the same key.
  • Integer division in the refill (tokens += elapsed / interval; last = now): it throws away the fraction every time, so frequent callers starve.
  • Updating last only when a token is added, but adding only whole tokens: same lost fraction problem in another shape.
  • Using the wall clock.

Cost

O(1) per request: one map lookup and a few arithmetic operations under an uncontended lock. Memory is one small bucket per active key.

How to say it in the interview

Each key has a bucket with a token count and the time I last updated it. On a request I add elapsed time times the rate, cap it at the burst, and take a token if there is a whole one, so there is no refill thread and idle keys cost nothing. The update touches two fields together, so each bucket has its own lock, and computeIfAbsent makes bucket creation atomic, so two threads can never create two full buckets for one key. I read a monotonic clock under the bucket lock so elapsed time never goes negative. To scale out I would drop idle buckets, which are full anyway, and keep shared state in a store with an atomic script.
