Why thread pools exist

Threads cost time and memory to create, so a pool reuses a few, caps the load you push downstream, and queues the bursts.

Asked atRubrikLinkedInMicrosoftDatabricks
Before this:What a thread costs, and why more threads can be slowerProducer and consumer with a bounded buffer

Servers, crawlers and job runners often use thread pools to control how much work runs at once. Knowing why pools exist tells you how to size one, what to bound and how it will fail, and those are exactly the follow ups interviewers ask.

In plain words

Picture a busy restaurant kitchen. One way to run it: hire a new cook for every order, let them cook that one dish, and send them home. You would spend more time hiring than cooking, and during the lunch rush you would have 300 cooks fighting over 6 burners.

Real kitchens keep a fixed crew and an order rail. Waiters clip tickets to the rail, and whichever cook is free takes the next ticket. The crew is sized to the burners, the rail soaks up the rush, and when the rail is completely full the host stops seating people for a while. That crew plus rail is a thread pool: reuse a few workers, cap how many work at once, and queue the rest.

One thread per task, and what it costs

A straightforward way to run work concurrently is to start a new thread for every task: every request, every file, every URL. For platform threads, this becomes expensive under heavy load for three reasons; Java virtual threads change the creation cost, as discussed below.

  • Creation is not free. A platform thread is an operating system thread. Creating one means a system call, a stack reservation, kernel bookkeeping and a scheduler entry, and tearing it down costs again. Creation and teardown can cost tens or hundreds of microseconds, as an illustrative order of magnitude rather than a portable benchmark. Runtime, OS, load and instrumentation change the result. For a tiny cache lookup, this overhead can exceed the useful work.
  • Memory grows with the thread count. Platform-thread stacks often reserve hundreds of KiB to several MiB of address space, an order-of-magnitude range that depends on runtime, platform and configuration. Java exposes stack sizing through -Xss; C++20 does not specify a default stack size. Reserved address space is not all resident RAM. Ten thousand live threads still add stacks and kernel bookkeeping; when many are runnable they also add scheduling and context switching overhead.
  • Nothing caps the load you push downstream. This is the one that takes production down. Without a separate connection or concurrency limit, 10,000 request threads can attempt 10,000 simultaneous database queries. That can overload the database even before local thread creation fails.

When the operating system finally refuses, Java throws OutOfMemoryError: unable to create native thread and the C++ std::thread constructor throws std::system_error with the error condition resource_unavailable_try_again. Resource limits can trigger this before RAM is exhausted, so neither thrashing nor a particular error-message string is guaranteed.

The three jobs a pool does

A thread pool reuses worker threads to execute tasks, commonly with a work queue. This lesson studies a fixed-size pool: some other pools grow dynamically, and a cached pool can allow effectively unbounded thread growth. Submission makes a task available to a worker, directly or through the queue; the worker runs it and then takes more queued work. That shape does three separate jobs, and an interviewer will want all three:

  1. Amortize creation. Workers are reused for many tasks, amortizing creation. Submission still pays allocation, queue synchronization and possibly wakeup and scheduling costs.
  2. Bound resources. A fixed worker count bounds worker stacks and simultaneously executing tasks. It caps downstream calls only if each task holds its worker until its call finishes and does not fan out. Queued task memory needs a separate bound.
  3. Decouple arrival from execution. An accepted asynchronous submission returns without waiting for task completion, although queue locking can briefly block it. A bounded queue needs an explicit full-queue policy: reject, wait, or run work on the caller, each with different latency and concurrency consequences. This is the producer-consumer pattern with tasks as the items.

The general idea has a name of its own: an executor is anything that takes a task and decides when and on which thread it runs. A pool is one implementation. An executor may instead run a task inline on the calling thread, so asynchronous return is not guaranteed by the executor abstraction itself.

See the difference

Here are 2,000 tiny tasks, run once with a new thread each and once on a pool of 4 reused threads. Java has a standard pool. C++20 has no standard thread pool, so the C++ side builds a teaching implementation: a queue, a mutex, a condition variable and a few workers. You will grow it into a real pool in the build-it lesson.

The expected sum is 1,999,000 in both cases; the times depend on your machine and can round to zero milliseconds. This is an overhead demonstration, not a benchmark or a promised speedup: JIT warmup, run order, contention on the atomic sum and ThreadSanitizer affect it. Read this simple C++ pool closely: one lock guards the queue, workers wait on a condition variable, and tasks run outside the lock. The destructor sets a flag, wakes everyone, lets the workers drain the queue, and joins them, so no thread outlives the pool.

Scope of the demo. Both queues are unbounded, so the examples limit workers rather than total retained task memory. TinyPool drains accepted tasks and reports task failures, but has no futures or public cancellation API. Stop all producers before destroying it, destroy it from an owning thread outside the pool, and require tasks to finish: joining a hung task also hangs shutdown.

Java shutdown() only initiates shutdown; a timed awaitTermination returns a boolean you must check. Java 21 close() waits for termination; if the closing thread is interrupted, it attempts shutdownNow, keeps waiting and restores the interrupt flag. Tasks still need to cooperate with cancellation. C++20 std::jthread is used for the standalone threads above; in C++17 explicitly join every started std::thread, including on partial creation failure.

A pool is a queueing system

Once you see a pool as tasks arriving, waiting in a queue and being served by N workers, everything you know about queues applies to it directly. That is the most useful sentence in this module.

Three quantities describe it. The arrival rate (tasks per second), the time each task spends being served, and the number of workers. Two facts follow:

  • Little's law: in a stable system, average tasks in the system equals throughput times average total time in it, including queueing. For the service stage alone, completed throughput times average worker occupancy gives average busy workers. At a sustained 400 completions a second and 50 ms of occupancy per task, that is 20 busy workers. Queue wait is additional; 20 workers leaves no headroom for variability. You will use this to size pools in Sizing a pool.
  • Capacity is a hard ceiling. With N workers and fixed mean worker occupancy S seconds, ideal service capacity is N / S tasks a second. Shared CPUs, locks or downstream bottlenecks can lower it or increase S as N grows. If accepted work arrives faster than departures indefinitely, an unbounded queue grows until resources run out; a bounded queue reaches its overflow policy. The only real question is what you do with the overflow, which is the subject of Bounded queues, rejection and the ways pools fail.

What a pool does not do

Pools are often credited with things they cannot do. Be precise about the limits, because interviewers test them:

  • It does not make CPU-bound work faster than your cores allow. A machine with eight available logical CPUs can schedule at most eight software threads simultaneously. Extra runnable workers do not create CPU capacity and usually add scheduling and cache overhead. Physical cores and hardware threads are not interchangeable; measure throughput near the available CPU count.
  • It does not fix a slow dependency. If the database slows down, each task holds its worker longer, capacity drops, and the queue grows. The pool turns a slow downstream into latency, quietly.
  • Worker bounds do not bound the queue. A fixed pool with an unbounded queue caps threads but not memory or waiting time. The next lesson shows that the most common Java factory method does exactly this.
  • It brings failure modes of its own: tasks that wait on other tasks in the same pool, exceptions that vanish, thread-local values that leak from one task to the next. They get their own lesson.

Worked example: a crawler with 10,000 URLs

Assume each fetch occupies one worker for 200 ms, nearly all waiting on the network, with enough bandwidth and connection capacity. Ignore startup and scheduling overhead for this ideal calculation. Compare three designs.

Sequential: 10,000 times 0.2 s is 2,000 s, about 33 minutes.

One thread per URL: up to 10,000 live platform threads and outstanding fetches, absent a connection limit. Stack reservations can reach gigabytes; this is not the same as resident RAM. If all URLs target one host, the burst can overload it; locally you may hit thread, descriptor or memory limits.

A pool of 50: up to 50 fetches are in flight, each taking 0.2 s, so the pool completes 50 / 0.2 = 250 pages a second, and the ideal crawl time is 10,000 / 250 = 40 s. Need it in 10 s? You need 1,000 pages a second, so 1,000 times 0.2 = 200 fetches in flight, so 200 is an ideal occupancy estimate, if the site and network sustain that concurrency at the same latency. Real deadlines need headroom, measurements and per-host limits. Notice the pool size came from arithmetic, not a guess. Databricks interviewers have pushed candidates on exactly this: pool size, dataset size, and where the disk or network becomes the bottleneck.

Common mistakes

  • Creating a pool per request. Executors.newFixedThreadPool(8) inside a request handler pays thread creation on every request (a fixed pool starts a new thread for each submitted task until it has 8), and if it is never shut down those threads leak with every request until the process dies. Create one pool for the application and share it.
  • Never shutting the pool down. With Java's default thread factory, workers are non-daemon threads, so the JVM does not exit while they wait for work. In C++ destroying a joinable std::thread calls std::terminate. Every pool needs an owner who shuts it down.
  • Thinking a bigger pool always means more throughput. It can help when more workers fill otherwise idle execution capacity or hide blocking. Beyond the available CPU capacity, extra pure-compute workers usually add overhead; benchmark rather than treating physical core count as an exact optimum.
  • Letting exceptions escape a C++ worker. An exception that leaves a thread's function calls std::terminate and kills the whole process. Catch inside the task, or wrap tasks so the worker catches.
  • Blocking a pool thread on another task in the same pool. If every worker waits for a task that is stuck in the queue behind them, nothing ever runs again. This is pool self-deadlock, covered in the failures lesson.

In the interview

It arrives in three ways. As theory or an online test question ("why use a thread pool instead of a new thread per task?"; Rubrik's online assessments include multiple choice questions on multithreading and the OS). As the core of a system coding round: Rubrik asks for a task executor with a cap on threads whose schedule() returns immediately, and in 2026 asked candidates to build a thread pool on their own bounded queue; LinkedIn has asked for a ThreadPoolExecutor clone without the API, and Microsoft to explain and implement one. And as a design follow up: Databricks crawler rounds probed thread pool size against dataset size and the disk and network bottlenecks.

A platform thread per task pays creation and stack overhead repeatedly. A fixed pool reuses workers and limits the number of tasks executing on them. I would also bound the queue and define rejection or backpressure, because limiting workers alone does not limit retained work. For synchronous tasks, the worker count also caps simultaneous downstream calls; asynchronous fan-out needs its own dependency limit. I would estimate occupancy from throughput and service time, leave headroom, and measure queue wait and latency under load.

Follow ups to expect: "What happens when tasks arrive faster than the pool finishes them?" (the queue grows without limit unless it is bounded; then you reject or push back on the producer), "How is a pool different from a semaphore?" (a pool owns workers and schedules tasks; a semaphore owns permits, not threads or a queue of tasks. A caller waits when it cannot acquire a permit under the semaphore's admission policy, or can use a non-blocking or timed attempt), and "What changes with virtual threads?" (creation gets cheap, but you still need a limit on concurrency; see Virtual threads and coroutines).

Senior depth

A fixed pool combines worker reuse and a concurrency cap: it amortizes creation and limits simultaneous worker tasks. Java 21 virtual threads make a thread per blocking task practical: do not pool virtual threads just to reuse them. They still need admission control and resource limits. That is why a modern answer to "thread per request with virtual threads?" is "yes, plus a semaphore in front of each scarce dependency".

An event loop multiplexes many non-blocking operations on a few threads; a blocking worker pool dedicates a worker while each task waits. Moving blocking work off an event loop can preserve responsiveness, but its destination queue and dependency concurrency still need limits. You will compare these designs in Server threading models.

Submission is not ownership transfer of mutable data. Java executor submission publishes earlier caller actions to the task, and Future.get publishes its completion back. This C++ queue provides the first direction through its mutex, and joining workers provides the return direction. Neither mechanism protects a captured object that the caller keeps modifying after submission. Prefer immutable inputs or owned copies, and explicitly synchronize any shared mutation.

What to measure. Separate queue wait from execution time. Track active workers, queue depth and oldest queued age, completed throughput, rejection count, and dependency latency. All workers blocked on a slow database suggest an I/O bottleneck; all CPUs busy suggest a compute limit. Increasing the pool in either case without checking the bottleneck can make latency worse. Remove per-request ThreadLocal values in a finally block, or reset C++ thread_local state explicitly, because the worker lives longer than the request.

Key takeaways

  • A platform thread per task pays repeated creation and stack overhead; a thread-per-task design needs a separate downstream limit.
  • A fixed pool reuses workers and caps their task concurrency; bounded queues and admission policies also limit queued work.
  • Ideal capacity is workers divided by worker occupancy time; Little's law estimates average occupancy, not a latency guarantee.
  • A pool does not make CPU-bound work faster than the cores, does not fix a slow dependency, and does not bound queued memory when its queue is unbounded.
  • Every pool needs an owner who shuts it down; C++20 has no standard pool; use a library pool or build one with a mutex, a condition variable and a queue.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A stable pool completes 400 tasks per second and each occupies one worker for 50 ms on average, excluding queue wait. On average, how many workers are busy?
Why. Little's law: busy workers equals arrival rate times time per task, 400 times 0.05 s, which is 20. Fewer than 20 workers cannot sustain this throughput at that occupancy time. Twenty is an average demand, not a safe size with variable arrivals. Neither 8 nor 400 is the product, and 2,000 also uses the wrong unit conversion.
A pool has exactly 2 workers, no caller execution and a FIFO queue through which all tasks pass. You enqueue three tasks in order; task k records its digit atomically in a synchronized output log. Spaces below separate log entries. Which outputs are possible? Select all that apply.Select all that apply
Why. Each worker runs one task at a time. Task 3 leaves the queue only after tasks 1 and 2 have been taken, and with only two workers one of them must have finished (and printed) before either worker is free for task 3. So 3 is never printed first. But a worker can take task 2, print, take task 3 and print before the other worker, which already took task 1, runs its task body, so 2 3 1 is possible.
A request handler creates a fresh fixed pool of 8 workers, submits two subtasks, waits for both results and returns. It never shuts the pool down. With no automatic idle-worker timeout, what is wrong?
Why. The owner must stop and join the pool; a handler returning does not do that. Java's default fixed pool starts two non-daemon workers for these submissions and keeps them waiting. A C++ pool object leaked per request similarly leaves workers alive; a local RAII pool would instead shut down on scope exit. Either request-local construction wastes reuse. Share an application-owned pool or define another explicit lifecycle; request threads can submit to it, and two workers can run the subtasks concurrently.
A fixed pool with no caller execution accepts 1,000 tasks per second and completes 800 per second. Starting empty, what happens after an hour of sustained rates, assuming memory has not run out?
Why. The admitted excess is 200 tasks per second, so 200 times 3,600 gives about 720,000 additional unfinished tasks. Almost all are queued, apart from the fixed number in service. The fixed worker count cannot expand, no rejection is assumed, and the stated sustained load has no dip to drain the backlog. An unbounded queue has no configured capacity limit, but real memory is finite and admission can still fail.
For a fixed pool with queued tasks and no caller execution, each task makes at most one synchronous database call and does not fan out. Which benefit does it NOT provide?
Why. A pool does not create processing capacity beyond the available logical CPUs. It reuses workers and queues bursts. Under the question's synchronous, no-fan-out assumption, at most one database call per busy worker can be outstanding. Without that assumption, a worker cap alone would not imply a database-call cap.
Java onlymain creates Executors.newFixedThreadPool(4), submits tasks, prints the results and returns without calling shutdown(). What happens?
Why. The default thread factory creates non-daemon threads, and core threads in a fixed pool never time out, so they wait forever on the queue and keep the JVM alive. Call shutdown() (or use try-with-resources with close() on Java 19 or later).
C++ onlyYou delete the line for (auto& w : workers_) w.join(); from TinyPool's destructor. What happens when a TinyPool goes out of scope?
Why. Destroying a std::thread that is still joinable calls std::terminate, which aborts the process. A pool must join every worker (or use std::jthread, which joins in its destructor). Detaching instead would let workers touch the destroyed pool's members, which is undefined behavior.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "Why not just start a new thread for every incoming request?" Answer as you would out loud, in under a minute.
Model answer

For platform threads, creation and stacks can cost more than a small request, and a burst can exhaust native thread resources. A fixed pool amortizes creation and limits simultaneous worker tasks. I would bound the queue too: a thread limit alone does not bound retained requests or queueing delay. If each worker makes one synchronous database call, the pool also limits those calls; asynchronous fan-out needs its own semaphore or connection limit. I would estimate average occupancy from throughput and service time, then measure with headroom. Java virtual threads change the creation trade-off, but not the need to limit scarce dependencies.

Numbers
You must crawl 20,000 pages in about one minute. Each fetch takes about 250 ms, almost all of it waiting. How many concurrent fetches do you need, and what could stop you from getting that throughput?
Model answer

Throughput needed: 20,000 / 60 s, about 334 pages a second. Little's law: in flight = 334 times 0.25 s, about 84. So a pool of roughly 85 to 100 threads (some headroom for variance). What could stop it: the target hosts (politeness limits, rate limiting, or simply slowing down under 84 concurrent connections, which raises the 250 ms and so raises the needed concurrency), your network bandwidth, file descriptor limits, and DNS. If fetches slow down to 500 ms, the same pool delivers only half the throughput, so I would measure latency during the crawl rather than trust the first number.

Write code
Replace a thread-per-file design with at most 8 simultaneous calls to process(file). Wait until every submitted file finishes or fails, report each failure, and keep processing the others. Defer caller interruption until the batch is drained; assume tasks eventually finish and submission resources are available.
Model answer

The pool caps processing at 8, and waiting on every future plus executor termination (Java), or draining in the destructor (C++), gives the batch completion guarantee. Java deliberately postpones interruption and restores the flag only after draining; a cancellable batch would need a different contract. C++ copies each filename into its task and catches even non-standard exceptions. Keep the input collection stable while submitting; both examples retain an unbounded number of tasks and Java also retains the futures, so a huge batch needs bounded submission.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Why would you use a thread pool instead of starting a thread for every request? What changes if we use Java virtual threads?"
What a strong answer covers
  • Lead with reuse and a fixed bound on simultaneously executing worker tasks
  • Explain platform-thread creation and stack costs without a universal timing claim
  • Separate worker bounds from queued memory and full-queue policy
  • Qualify downstream limits for synchronous tasks versus asynchronous fan-out
  • Explain virtual-thread-per-task with separate dependency admission control
  • Name an owner responsible for shutdown and completion or cancellation
How a senior would say it
I would use a fixed platform-thread pool to reuse workers and cap how many tasks execute on them. Creating a native thread for every small request adds stack and scheduling costs, and a traffic burst can exhaust thread resources. Reuse amortizes those costs, while a queue lets a short burst wait for capacity. But the worker count does not bound queued memory. I would set a queue capacity and decide whether overload rejects, blocks submission or runs work on the caller. Caller execution changes the concurrency bound, so that choice matters. A pool also limits database calls only when tasks hold their worker until each call completes. If tasks launch asynchronous calls and return, I need a separate limit around the dependency. With Java virtual threads, I would normally use one virtual thread per task instead of pooling them for reuse. They make blocking tasks cheaper to represent, but they do not create database connections or CPU capacity. I would still limit admission and use a semaphore for a scarce downstream resource. Finally, the pool or executor needs an owner. That owner stops new submissions and waits for completion or requests cooperative cancellation; dropping the reference is not a shutdown policy.

Likely follow up: What would happen if every worker submitted another task to the same pool and waited for its result?

Out loudabout 90 s
"We receive 400 tasks a second, and each occupies a worker for 50 milliseconds. Would you choose 20 workers? Explain what you would measure."
What a strong answer covers
  • Compute 400 times 0.05 as 20 workers of average service demand
  • Distinguish worker occupancy from total response time including queue wait
  • Explain why 20 workers gives no spare capacity under the model
  • Check CPU and downstream limits before adding workers
  • Bound the queue and choose overload behaviour
  • Monitor queue age, occupancy, completions, rejections and latency under sustained load
How a senior would say it
Twenty workers is the average occupancy estimate, not yet a safe configuration. Four hundred tasks per second times fifty milliseconds is twenty worker-seconds of service per second. With twenty workers, the ideal capacity is exactly four hundred tasks per second, so there is no spare capacity to drain a burst or absorb a slow task. I would first confirm what the fifty milliseconds measures. For worker sizing it must be time occupying a worker, including blocking within the task, but excluding time waiting in the pool queue. Total response time includes both. Then I would check the bottleneck. If the tasks are CPU bound on eight available logical CPUs, adding twenty workers cannot supply twenty cores of computation. If they mostly wait on a database, more workers may help until database or connection limits dominate, and added concurrency may itself increase service time. I would test a size with headroom, bound the queue and define rejection or backpressure. During sustained load I would track busy workers, completed throughput, queue depth and oldest task age, rejections and downstream latency. Growing queue age with all workers busy means we are not keeping up; a short successful benchmark does not establish stability.

Likely follow up: If each task now takes 100 milliseconds, what happens to capacity with the worker count unchanged?
