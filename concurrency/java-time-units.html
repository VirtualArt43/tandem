Time: nanoTime, Duration and TimeUnit

Measure elapsed time with nanoTime and never the wall clock, express timeouts with Duration and TimeUnit, and turn timeouts into deadlines that survive wakeups.

Asked atConfluent
Before this:Exceptions, InterruptedException and try-with-resources

Every timeout, deadline, rate limiter and delayed scheduler you write in an interview reads a clock. Read the wrong clock, or the right one the wrong way, and the timeout fires early, late, or never.

In plain words

Timing your tea with the kitchen clock works until someone moves the clock forward for daylight saving, or it corrects itself against a radio signal. Then your tea has brewed for minus 55 minutes. A stopwatch cannot be set to a time of day at all; it only counts forward from the moment you pressed it. System.currentTimeMillis() is the kitchen clock. System.nanoTime() is the stopwatch.

Now say you have ten minutes to finish a task and you keep getting interrupted. You do not restart the stopwatch from zero after every interruption. You note the moment you must be done, and after each interruption you check how much time is left. That moment is a deadline, and it is the second idea of this lesson.

Why this matters for concurrency

  • Timed waits are everywhere in concurrent Java: tryLock, poll, offer, await, awaitNanos, Future.get, awaitTermination. Each takes a duration, and inside your own blocking code you must work out how much of it is left.
  • Delayed schedulers, token buckets, TTL caches and leases all compare "now" with a stored time. A wall clock that jumps makes them fire early, late or never; a monotonic clock does not. A collection of reports on Confluent's delayed task runner question lists a monotonic clock among the things the interviewers look for.
  • A wait loop that restarts the full timeout after every wakeup can wait far longer than the timeout, or forever. The fix is a deadline, and the JDK's own blocking queues show exactly how.

Two clocks

The nanoTime documentation is unusually blunt. It says the method can only be used to measure elapsed time and is not related to any notion of wall-clock time; that its values become meaningful only when you subtract two readings from the same JVM; that it gives nanosecond precision but not necessarily nanosecond resolution; and that differences spanning more than about 292 years overflow.

That last point leads to a rule worth memorizing: compare two nanoTime readings by subtracting them, never directly. Write System.nanoTime() - start >= timeoutNanos, not System.nanoTime() >= start + timeoutNanos. The values can wrap past Long.MAX_VALUE, and subtraction still gives the right answer when they do, while a direct comparison does not. The direct comparison claims a deadline that is 292 years away has already passed, because now + Long.MAX_VALUE wrapped around to a negative number (HotSpot's nanoTime is positive on the usual platforms; with a negative origin the bug would show up with other values instead). The subtraction is still right. Both clocks are cheap to read, on the order of tens of nanoseconds on current hardware, so read them per operation without worry, just not in the tightest inner loop.

Duration and Instant

java.time.Duration is an immutable amount of time, so it is safe to share between threads: Duration.ofMillis(250), Duration.ofSeconds(2), d.toMillis(), d.toNanos(), d.plus(other), d.compareTo(other). Two traps:

  • getSeconds() returns the whole seconds and getNano() returns only the nanoseconds inside the last second, not the total. For Duration.ofMillis(1500), getNano() is 500,000,000 while toNanos() is 1,500,000,000.
  • toNanos() throws ArithmeticException when the result does not fit in a long (about 292 years). TimeUnit.NANOSECONDS.convert(duration) saturates at Long.MAX_VALUE instead.

java.time.Instant is a point on the UTC timeline, read from the wall clock: Instant.now(), start.plus(duration), deadline.isBefore(Instant.now()), and Duration.between(a, b) for the gap between two instants. It has the same jump problem as currentTimeMillis, so use it for timestamps, not for timeouts.

Java 19 added Duration overloads to Thread: Thread.sleep(Duration), and t.join(Duration), which returns true if the thread finished in time. Most of java.util.concurrent still takes a long and a TimeUnit.

For tests, use an injectable clock instead of sleeping. Pass a LongSupplier that is System::nanoTime in production and a value you advance by hand in the test (or a java.time.Clock when the code needs wall time). A Snowflake phone screen report lists tests with a mocked clock among the follow ups to a rate limiter question. The worked example below does it.

TimeUnit

java.util.concurrent.TimeUnit is an enum of units, NANOSECONDS up to DAYS, with conversions and a few helpers:

  • TimeUnit.SECONDS.toMillis(3) is 3000, and unit.toNanos(timeout) is how blocking code normalizes whatever the caller passed.
  • TimeUnit.MILLISECONDS.convert(90, TimeUnit.SECONDS) is 90000. Read it as "into milliseconds, convert 90 seconds"; the argument order trips people up. Converting to a coarser unit truncates: TimeUnit.SECONDS.convert(1999, TimeUnit.MILLISECONDS) is 1. Converting to a finer unit that would overflow saturates at Long.MAX_VALUE instead of wrapping.
  • Helpers that read well: TimeUnit.MILLISECONDS.sleep(200), TimeUnit.SECONDS.timedJoin(thread, 5), and unit.timedWait(monitor, timeout), which needs you to hold the monitor, just like wait.

Every timed method in java.util.concurrent takes (long timeout, TimeUnit unit), and each reports a timeout in its own way. Know the column on the right; ignoring it is a common bug.

Sleeping, periodic work and drift

Thread.sleep waits at least roughly the time you asked for, subject to the precision of the system timers and the scheduler, so it can oversleep. It is interruptible, and unlike wait it does not release any lock you hold, so never sleep inside a critical section. And a sleep is never a way to wait for another thread: use join, a latch, a future or a condition.

Periodic work drifts if you write it as "do the task, then sleep 100 ms": the period becomes 100 ms plus the task time plus any oversleep. ScheduledExecutorService gives you the two honest choices. scheduleAtFixedRate aims at fixed start times, so if one run is late the following runs start back to back to catch up, though never concurrently with each other. scheduleWithFixedDelay waits the full delay after each run ends. More in scheduled executors and timers.

A hand-built delayed scheduler, a favorite interview problem, follows directly from this lesson. Store each task's due time as System.nanoTime() + delayNanos. Keep tasks in a priority queue ordered by due time, comparing two due times by subtraction; the JDK's ScheduledThreadPoolExecutor does exactly that, with a sequence number to keep equal times in submission order. The worker waits with awaitNanos(dueAt - now), and when a task with an earlier due time arrives, the submitter signals the worker so it recomputes its wait.

Common mistakes

  • currentTimeMillis for elapsed time or timeouts. A clock adjustment makes the timeout fire early, late or never. Use nanoTime differences.
  • Comparing nanoTime readings directly. now > deadline breaks when values wrap. Write now - deadline > 0.
  • Storing or sending a nanoTime value. It means nothing in another JVM, on another machine, or after a restart. Send wall-clock time, or a duration.
  • Restarting the full timeout after every wakeup. Compute the remaining time from a deadline, or use the value awaitNanos returns.
  • TimeUnit.convert backwards, or forgetting it truncates. SECONDS.convert(1999, MILLISECONDS) is 1, not 2.
  • Duration.getNano() when you meant toNanos(). The first is only the part inside the last second.
  • Doing time arithmetic in int. int nanoseconds overflow after about 2.1 seconds. Keep times in long and convert with TimeUnit.
  • Sleeping to wait for something. Polling with sleep is slow when the event is early and flaky when it is late. Wait on a condition, latch or future.
  • Sleeping while holding a lock. sleep keeps every lock, so everyone else waits for your nap.

In the interview

Time rarely arrives as its own question. It hides inside others: poll(timeout) on your blocking queue, tryAcquire(timeout) on your semaphore, a delayed task scheduler (the most reported LinkedIn concurrency question in our research, and the core of Confluent's delayed task runner), token bucket refill in a rate limiter, and expiry in a TTL cache.

For elapsed time I use System.nanoTime, never currentTimeMillis. It is a monotonic clock, so a clock sync or someone changing the system time cannot make my timeout fire early or never. I only ever subtract two readings.
Inside a wait loop I turn the timeout into a deadline once, and after every wakeup I wait only for what is left. With a Condition, awaitNanos hands me the remainder directly.
To test it without sleeping, I inject the clock: a LongSupplier that is System::nanoTime in production and a counter I advance by hand in the test.

Follow ups to expect. "What happens if the system clock jumps back an hour?" (with wall-clock deadlines everything waits an extra hour; with nanoTime nothing changes). "Fixed rate or fixed delay?" (start to start versus end to start; fixed rate catches up after a slow run). "How do you wake a scheduler's worker when an earlier task arrives?" (signal its condition so it recomputes its awaitNanos). "A periodic task throws once. What happens to the schedule?" (in ScheduledThreadPoolExecutor every later run is suppressed and nothing is printed; catch inside the task, and in your own scheduler decide the policy explicitly).

Senior depth

  • There is no shared monotonic clock across machines. Wall clocks on different machines disagree, by milliseconds on a good day and by much more on a bad one. Distributed leases and TTLs should be measured as durations on each machine's own monotonic clock with a safety margin, and correctness must not depend on clocks agreeing. That is what fencing tokens are for; see distributed locks, leases and fencing tokens.
  • A pause can land between the check and the act. A garbage collection pause or a frozen VM can stop a thread right after it checked "my lease is still valid" and before it writes. Time checks are a check-then-act on the clock itself, and the same fencing fix applies.
  • Precision is not resolution. nanoTime reports nanoseconds, but how often the value actually changes depends on the platform. Never assume two readings a few nanoseconds apart differ.

Key takeaways

  • nanoTime is the stopwatch: monotonic, meaningful only as a difference within one JVM. currentTimeMillis and Instant are the wall clock, which can jump.
  • Compare nanoTime readings by subtracting: now - start >= timeout, never now >= start + timeout.
  • Duration is an immutable amount of time; TimeUnit converts units (truncating toward coarser ones) and is the unit argument of every timed java.util.concurrent method.
  • In a wait loop, convert the timeout to a deadline once and wait only for the remainder; awaitNanos returns it for you.
  • Inject the clock to test time-dependent code without sleeping.

Quick check

Answer each question, then read why. Your score is saved for your module test.

You need to know whether 500 ms have passed since a request started. Which is correct?
Why. Elapsed time needs the monotonic clock, compared by subtraction. The currentTimeMillis and Instant versions use the wall clock, which can jump during the request. The third option uses the right clock but compares directly, which breaks if the values wrap past Long.MAX_VALUE.
What is TimeUnit.MILLISECONDS.convert(90, TimeUnit.SECONDS)?
Why. convert(sourceDuration, sourceUnit) converts from the argument's unit into the receiver's unit: 90 seconds into milliseconds is 90,000. Reading it left to right as "milliseconds to seconds" is the usual mistake.
What is TimeUnit.SECONDS.convert(1999, TimeUnit.MILLISECONDS)?
Why. Conversions to a coarser unit drop the remainder, so 1,999 ms is 1 second. Conversions to a finer unit that overflow saturate at Long.MAX_VALUE rather than throwing. If you need rounding, do it yourself before converting.
A timed poll waits with if (!notEmpty.await(timeoutMs, TimeUnit.MILLISECONDS)) return null; inside while (items.isEmpty()). Other consumers keep stealing items that arrive. How long can a call with a 1 second timeout block?
Why. Each time the consumer is woken and finds the queue empty again, it calls await with the full timeout. Under steady traffic that keeps waking it, it may never time out. Compute a deadline once and wait for the remainder, for example with the value awaitNanos returns.
For Duration d = Duration.ofMillis(1500), what does d.getNano() return?
Why. getNano() is the nanosecond part inside the last whole second; the whole seconds are in getSeconds(), which is 1. The total in nanoseconds is toNanos(), which is 1,500,000,000. Mixing them up silently drops whole seconds from a timeout.
What does condition.awaitNanos(nanos) return?
Why. It returns the remaining budget so a loop can pass it straight into the next call after a spurious or stolen wakeup, and stop when it reaches zero or below. The boolean return belongs to await(time, unit), which is why awaitNanos is the better fit inside a loop.
A service stores System.nanoTime() + ttlNanos as the expiry time of each cache entry in Redis, so that every server in the cluster can check expiry. What is wrong?
Why. Each JVM's nanoTime counts from its own arbitrary origin, so comparing one server's reading with another's is meaningless, and even the same server loses its origin on restart. Shared expiry times need wall-clock time with a margin for skew, or a TTL kept by the store itself.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Add boolean awaitReady(long timeout, TimeUnit unit) to a class that uses synchronized, wait and notifyAll. It returns true as soon as markReady() has been called, or false if the timeout passes first. It must not wait longer than the timeout in total, whatever wakeups happen.
Model answer

The deadline is computed once, so a spurious wakeup or a notifyAll meant for something else only shortens the next wait instead of restarting it. The condition is checked in a while loop under the monitor. InterruptedException is declared, so the caller decides what an interrupt means. notifyAll is right because every waiter waits for the same condition and all of them can proceed once it holds.

Explain
An interviewer asks: "What is the difference between System.nanoTime and System.currentTimeMillis, and when do you use each?" Answer as you would out loud.
Model answer

currentTimeMillis is wall-clock time: milliseconds since the 1970 epoch in UTC. It means something on its own, so it is right for timestamps, logs and expiry times I store or send to another machine. But the system can adjust it at any moment, through clock synchronization or a manual change, so it can jump backward or forward.

nanoTime is a stopwatch: nanoseconds from an arbitrary origin, monotonic in practice, and meaningful only as the difference between two readings in the same JVM. So I use it for anything elapsed: timeouts, deadlines, latency measurements, token bucket refills. I compare readings by subtracting, because the raw values can wrap, and I never persist or send a nanoTime value, because another JVM or a restart has a different origin. For testability I inject the clock as a LongSupplier.

Numbers
A task should run every 100 ms and takes 30 ms. What is the effective period with (a) a loop that runs the task and then sleeps 100 ms, (b) scheduleWithFixedDelay(task, 0, 100, MILLISECONDS), and (c) scheduleAtFixedRate(task, 0, 100, MILLISECONDS)? In (c), what happens if one run takes 250 ms?
Model answer

(a) About 130 ms or a little more, because the sleep starts after the work and sleep can oversleep; over time the schedule drifts. (b) About 130 ms as well: fixed delay measures from the end of one run to the start of the next. (c) 100 ms from start to start, so runs begin at 0, 100, 200 and so on.

If the run at 0 takes 250 ms, the runs due at 100 and 200 are late. Fixed rate never runs the same task concurrently with itself, so the late runs start back to back as soon as the long run ends, at about 250 and 280 ms, then the run due at 300 starts at about 310 ms, and the run due at 400 is on time again. The schedule catches up instead of shifting, which is right for "about ten times a second on average" and wrong for "never closer together than 100 ms"; for the second, use fixed delay.
