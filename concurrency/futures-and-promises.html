Futures and promises

Futures deliver values and failures; promises complete them. Learn waiting, deadlines, cooperative cancellation, batch results and C++ ownership traps.

Asked atDatabricksRubrik
Before this:Why thread pools existPassing data in and getting results out

Starting work on another thread is the easy part. Getting the answer back, with its errors, without waiting forever, is the hard part. Futures and promises are the standard answer in both languages, and many asynchronous APIs expose this pattern.

In plain words

At a busy food court you order, pay, and get a buzzer. The buzzer is a future: a claim on food that does not exist yet. The kitchen keeps the other half of the pair, the promise: when the food is ready, they press the button, or they press a different one to say "sorry, we are out".

You choose how to wait. Stand at the counter until it buzzes (block), glance at it now and then (poll), or decide that if it has not buzzed in 15 minutes you will eat elsewhere (a timeout). If the kitchen closes without pressing anything, C++ can signal a broken promise when the kitchen gives up its handle. Java needs the producer to report failure explicitly.

Two halves of one shared state

A future and a promise are two handles on one small shared object: a slot that is empty, then completed once with a value or an exception (or a cancellation state in Java), plus a way for readers to wait until it is filled.

  • The promise (write side) is held by whoever produces the result: a worker thread, an I/O callback, a pool task.
  • The future (read side) is held by whoever needs the result. get() waits until the slot is filled, then returns the value or throws the stored exception.
  • The slot is filled once. A second attempt is ignored or reported as an error, never an overwrite. (Java's CompletableFuture.obtrudeValue and obtrudeException deliberately override outcomes for error recovery; ordinary completion does not.)

Completion publishes the result. In Java, actions of the asynchronous computation happen-before actions after the corresponding Future.get(). In C++, storing the result synchronizes with a waiting operation successfully detecting that the shared state is ready. This publishes preceding writes, not mutations made afterwards. A timeout or cancellation does not prove that the producer has stopped; separately synchronize access to anything it can still mutate.

Getting a result back

In Java, ExecutorService.submit(Callable) returns a Future<V>. In C++, std::async returns a std::future<T>. Both deliver the task's exception through the future, with one difference worth remembering: Java wraps it in ExecutionException; C++ rethrows the original exception object.

Java

The Java Future API in full: get(), get(timeout, unit), isDone(), cancel(mayInterruptIfRunning) and isCancelled(), plus, since Java 19, state() (RUNNING, SUCCESS, FAILED or CANCELLED), resultNow() and exceptionNow() for inspecting completion without waiting. resultNow() requires success; exceptionNow() requires failure; otherwise they throw IllegalStateException. isDone() also includes failure and cancellation, and RUNNING means incomplete, possibly still queued. get can throw four things, and each means something different: ExecutionException (the task threw; the cause is the real error), CancellationException (someone cancelled it), TimeoutException (your timed get gave up; it does not cancel queued or running work), and InterruptedException (your waiting thread was interrupted; restore the flag or propagate it).

C++

The C++ std::future<T> API includes get(), valid(), share() and waits. get() consumes the state even when it rethrows a stored exception; afterwards valid() is false. Calling get() again has undefined behavior, so do not rely on any particular crash or diagnostic. valid() means a state exists, not that it is ready. wait() returns void; only wait_for(duration) and wait_until(time_point) return std::future_status (ready, timeout or deferred). Waiting for readiness does not rethrow the task's exception; get() does. Machinery errors use std::future_error, for example broken_promise, future_already_retrieved or promise_already_satisfied.

A ready future is not a thread join: a producer can call set_value or complete and then continue working. Reclaim shared resources only after the appropriate join or executor termination, and synchronize any accesses after publication. The std::async asynchronous-thread wait has additional join-like semantics, discussed below.

A task object that carries its own future

Pools need a way to turn "a function" into "a function whose result lands in a future". Java's FutureTask and C++'s std::packaged_task are exactly that: a task wrapper that, when run on a thread, fills its own shared state. They are useful building blocks for result-returning pools. With ordinary run() or invocation, each shared state is completed at most once: Java ignores a second run; C++ throws. packaged_task::reset() creates a new state for reuse, not a second result in the old state. Retrieve each promise or packaged task's future once, then move it to the consumer.

The promise side, by hand

Sometimes there is no task to wrap: the result arrives from a callback, a message, or the end of a batch. Then you hold the write side yourself. C++ has std::promise with set_value and set_exception. Java has no class named promise; CompletableFuture plays both roles, with complete and completeExceptionally as the write side. The next lesson is about the rest of CompletableFuture.

Look at the last part of the C++ program: a promise destroyed without being set stores a broken_promise error, so the reader wakes up with an exception instead of hanging. That is a real safety net. Java has no equivalent: a CompletableFuture that nobody completes stays incomplete forever, and an untimed get() on it waits forever. In Java, every code path of the producer must complete the future, including the error paths, so catch failures at the producer boundary and call completeExceptionally. Completing a future does not decide whether a fatal error should also be rethrown or terminate the worker.

Waiting with a deadline, and cancelling

An untimed get() trusts the producer to finish. A timeout limits the wait, not the work. For a Java FutureTask from ThreadPoolExecutor.submit, successful cancel(true) requests interruption of a running task; the task stops only if it responds. CompletableFuture.cancel(true) does not interrupt its producer at all. C++ futures have no cancellation API: pass a C++20 std::stop_token (std::stop_token) and check it. In C++17, use a shared atomic stop flag and join owned threads explicitly.

When cancellation wins on a FutureTask, isCancelled() and isDone() become true and get() throws CancellationException, even if the task keeps running. cancel(false) can also win after the callable has started; it does not interrupt it, and its eventual result is ignored. If normal completion already won, cancellation fails. These are FutureTask semantics; a general Future implementation may refuse cancellation. Cancellation also does not roll back side effects or necessarily remove the queued wrapper immediately.

Use one deadline for a whole operation. Compute remaining time before each wait, including admission and downstream calls; two consecutive one-second waits can spend two seconds. A timed wait may overrun because of scheduling, and cleanup may wait for threads. A hard response deadline needs a longer-lived owner for unfinished work, safe captured lifetimes, and a separate cleanup policy. See Stopping a thread for the cancellation contract.

Waiting for a batch: invokeAll and invokeAny

Two batch shapes come up constantly: "run all of these and give me every result" and "run all of these and give me whichever succeeds first". Java's ExecutorService has a method for each; C++ has neither, and you should be able to write both.

  • invokeAll(tasks) submits every task and blocks until all of them are done, normally or by failing. It returns the futures in the same order as the input, each already complete, so get() on them never waits. It does not throw a task's exception itself; each failure surfaces when you call get() on that task's future, as an ExecutionException.
  • invokeAll(tasks, timeout, unit) returns when all are done or when the timeout passes, whichever comes first, and cancels every task that has not finished, so those futures report isCancelled() and their get() throws CancellationException.
  • invokeAny(tasks) blocks until one task completes successfully and returns its result directly (not a future). Failures are skipped while others are still running. As soon as it has a winner, or gives up, it cancels unfinished tasks; the standard thread-pool implementation requests interruption. If every task fails it throws ExecutionException carrying one of the failures; with a timeout it throws TimeoutException if nothing succeeded in time.

invokeAll accepts an empty collection and returns an empty list; invokeAny rejects one with IllegalArgumentException. Interruption cancels unfinished batch tasks and propagates InterruptedException. Both block the calling thread, so the self-deadlock rule applies: do not consume all workers waiting on batches queued to the same pool. And when you want results in the order they finish rather than input order, ExecutorCompletionService hands you futures as they complete. The C++ versions below illustrate related result policies, not the full Java executor contract: invokeAll is "submit everything, then wait for each future in order", and invokeAny is a small shared state (a mutex, the winner, a failure count) plus a std::stop_source that asks losers to stop. This C++ helper owns and joins its threads before returning; Java batch cancellation need not wait for a losing callable to exit. The Java example closes its executor afterwards, which does wait for task termination.

Typical output shows mirror B winning, but sleep durations do not guarantee completion order under every schedule. invokeAll returns all results, including the failure. invokeAny chooses the first observed success and requests cancellation of losers. The C++ version then joins them, so an uncooperative loser can delay its return indefinitely. A deadline-aware version must wait against one deadline and arrange both stop requests and ownership of unfinished work; adding timed waits alone does not bound cleanup.

C++

std::async: launch policies and the blocking destructor

std::async takes a launch policy, and the policy changes everything:

  • std::launch::async: run the task as if on a new thread. This does not guarantee immediate scheduling, and std::async is not a bounded thread-pool API.
  • std::launch::deferred: do not run it at all yet. It runs lazily on the first thread to make an untimed wait (get() or wait()), and never runs if nobody does.
  • No policy (the default, async | deferred): the implementation picks. So you cannot assume another thread, you cannot rely on thread_local values, and a loop like while (f.wait_for(10ms) != std::future_status::ready) can spin forever, because a deferred task reports deferred, never ready. Always pass a policy explicitly.

And the rule that bites everyone once: releasing the last reference to an unfinished std::async state launched with std::launch::async waits for its thread. A future that dies at the end of a loop iteration, or a return value you never stored, serializes work by waiting for its background thread at each scope exit. A never-started deferred task is not launched by destruction. C++20 marks std::async [[nodiscard]], so ignoring its result outright can produce a compiler warning; a named short-lived future avoids that particular diagnostic.

Futures from std::promise and std::packaged_task do not block in their destructors; an unfinished asynchronously launched std::async state is the special case. Dropping a promise-backed future does not stop its producer: ensure references captured by the task still outlive it. That is one more reason real code runs tasks on a pool and returns packaged_task futures, as you will in the build-it lesson.

Many readers: std::shared_future

A std::future is move-only and its get() works once, so it has one consuming handle; move that handle when transferring ownership. When several threads need the same result (a loaded configuration, a "start" signal), call share() to get a std::shared_future. It is copyable, get() for a value type returns const T& and can be repeated (T& and void specializations differ), and each thread should hold its own copy. Keep a copy alive while using the returned reference, and do not assume a const reference makes pointed-to data immutable.

Java

Many readers, and fire and forget

A Java Future can be read by any number of threads, any number of times: get() on a finished future just returns the stored result again. Dropping a Java future never waits for anything; the task can keep running, but nobody observes its result or exception unless another reporting path exists (the failures lesson covers that trap). C++ differs on both points, which is worth knowing when you pair with a C++ engineer.

Worked example: an event writer that acknowledges after fsync

A Databricks concurrency round asked for a thread-safe EventWriter whose appendEvent returns only once the data is durable on disk, with high throughput. The candidate's path went from a mutex plus write plus fsync per event (correct but slow: one fsync per event), to one writer thread fed by a queue, to batching, and finally to a per-event promise completed after the batch's fsync; a full C++ implementation was expected. The promise is the piece that lets thousands of callers wait for one shared fsync.

The fragment below is only the batch I/O and completion boundary. A surrounding writer owns a bounded FIFO queue, copies submitted bytes, drains accepted events on close, and on I/O failure stops admission and fails both the current batch and queued requests. It calls this method with fresh, uniquely owned promises. Callbacks must not block the writer waiting for another append.

Why this is the right shape: callers block only on their own future, the single writer keeps events in order, and one fsync is shared by a whole batch, so the synchronization cost is amortized across the batch. The acknowledgement promises only the durability contract of the chosen storage API. Errors reach every affected caller through the same futures. A failed write may have partially reached disk; failure does not mean rollback. New-file directory persistence and device power-loss guarantees need separate treatment. On macOS, fsync alone is not a guarantee that volatile drive caches are flushed; a stronger contract may require F_FULLFSYNC. See files and durability and the durable log writer problem.

Common mistakes

  • Calling get() right after submitting. submit(a).get(); submit(b).get(); runs a and b one after the other. Submit everything first, then wait.
  • Untimed get() on anything remote. If the producer hangs, so do you, and there is no default timeout in either language. Wait with a deadline, then cancel.
  • Swallowing the cause. Catching ExecutionException and logging only its message loses the real error; use getCause(). Catching InterruptedException and carrying on loses the interrupt; restore it.
  • Believing cancel stops the task. Successful FutureTask.cancel(true) requests interruption; CompletableFuture.cancel does not. C++ needs a separate stop request. None forcibly stops arbitrary work.
  • A Java producer with an error path that never completes the future. The reader waits forever. Complete exceptionally in a catch block.
  • C++: std::async without a policy, or a short-lived std::async future that silently serializes the work in its destructor.
  • C++: calling get() twice on a std::future. Use shared_future for several reads.

In the interview

Futures appear inside bigger questions far more often than on their own. A Rubrik system coding round asked for a JavaScript-style Promise in Java (working code first, then optimize); Databricks expected std::promise and std::future in a C++ durable event writer; and a result-returning pool needs the same completion mechanism. The theory questions are predictable: future versus promise, what get throws, how timeouts and cancellation work, and in C++, launch policies and the std::async destructor.

A future is the read side of a single-assignment slot and a promise is the write side; the producer fills it once with a value or an exception, and filling it happens-before get returns, so the reader needs no extra locking. I never call get without a deadline on anything remote, and I treat cancellation as cooperative: FutureTask cancellation may request interruption, CompletableFuture cancellation does not, and C++ needs a separate stop token. In C++ I pass an explicit launch policy to std::async and keep its future alive, because releasing its last asynchronous state can wait for the task.

Follow ups to expect: "What is the difference between invokeAll and invokeAny?" (all results after all finish, versus the first success with the rest cancelled; both block the caller), "What if an unset C++ promise is destroyed?" (get throws std::future_error with broken_promise; an exception escaping a raw thread instead terminates the process), "How would you wait for the first of several futures?" (ExecutorCompletionService gives completed submitted tasks; CompletableFuture.anyOf races the first completion, including failure, and does not cancel losers; C++20 has no standard when_any), and "Two tasks of 300 and 500 ms in parallel, how long until both are done?" (about 500 ms if submitted together, whichever order you call get in).

Key takeaways

  • A future reads and a promise writes one shared slot, filled once with a value or an exception; the fill happens-before get returns.
  • Java wraps a task's exception in ExecutionException; C++ rethrows the original. Destroying an unset C++ promise reports broken_promise; a Java promise that nobody completes can leave readers waiting forever.
  • FutureTask and std::packaged_task turn a function into a runnable that fills its own future; pools are built on them.
  • Wait with one deadline; cancellation is separate from stopping work. Use interruption-aware tasks or stop tokens, with an explicit cleanup owner.
  • C++: always give std::async a launch policy, keep its future alive, and use shared_future for many readers.

The main thread submits a task that prints B and then returns. Main then prints A, calls get() on the task's future, and prints C. Assume each print is one synchronized output operation and the task is not cancelled. Which outputs are possible? Select all that apply.Select all that apply
Why. The task may print before or after main prints A, so both of the first two happen. But get() returns only after the task has finished, and the task prints B before finishing, so C always comes after B. Main prints A before it calls get(), so C can never come first either.
A task throws IllegalArgumentException in Java, or std::invalid_argument in C++. What does get() on its future do?
Why. Java's get always wraps a task failure in a checked ExecutionException, so you read getCause(). C++ stores an exception_ptr and rethrows the very same exception object, so you catch the original type. std::future_error is only for problems with the future machinery itself, such as a broken promise.
A worker fills a result object's fields and then completes a future with it. No thread mutates those fields after completion. Another thread successfully calls get() and reads the fields without any lock. Is that safe?
Why. Both languages guarantee the edge: Java documents that actions in the asynchronous computation happen-before actions after Future.get(), and in C++ setting the promise synchronizes with the return from get(). Immutability is still good design, but it is not what makes this particular handoff safe. Writes made after completing the future are not covered.
Two independent remote calls take 300 ms and 500 ms. Ignore scheduling and submission overhead. You submit both to a pool with free threads, then call get() on the 500 ms one first and on the 300 ms one second. About how long until you have both results?
Why. Under the stated assumptions, both calls run in parallel. Waiting for the 500 ms one covers the 300 ms one too, so the second get() returns immediately. Calling get() does not reschedule independent tasks; submitting the second only after waiting for the first would serialize them. Ignore scheduling and submission overhead for this estimate.
An "any of these" call (Java's invokeAny, or the C++ version in this lesson) gets three tasks: one fails immediately, one succeeds first after 50 ms, and one is still running then. Assume losers promptly honour cancellation. What happens?
Why. "Any" means the first success: failures are skipped while other tasks can still win, and once there is a winner the rest are cancelled (interrupted in Java, asked to stop through a token in C++). The untimed result policy throws if all tasks fail; interruption or submission failure can also abort the call. The C++ helper joins losers before returning. A list of completed futures is what invokeAll returns, after waiting for all of them.
Java onlyA FutureTask submitted to a ThreadPoolExecutor is running a CPU loop with no interrupt checks or interruptible operations. While it runs, cancel(true) succeeds. What is true afterwards?
Why. Successful FutureTask.cancel(true) changes the future state and requests interruption of the runner. A loop that never checks it keeps going. The future, however, moves to the cancelled state right away, so waiters stop waiting. Here cancellation is stated to have succeeded, so normal completion did not win the race. This is not a guarantee for every implementation of Future.
C++ onlyThis loop runs twice: for (int i = 0; i < 2; i += 1) { auto f = std::async(std::launch::async, task100ms); }. How long does it take?
Why. Here std::launch::async was explicit, and each unfinished task's last future waits for its thread on destruction. f is destroyed at the end of each iteration, so iteration two starts only after task one is done. C++20 marks the returned future [[nodiscard]], which encourages a warning when ignored; naming it does not prevent scope-exit waiting.

Checkpoint

Write code
Write sumBoth(a, b): launch two tasks, wait in input order and sum their results, using one overall waiting deadline of 1 second. Propagate observed failures and request cancellation on failure or timeout. In C++, join owned threads safely. Explain why this does not guarantee a hard response deadline or fail-fast detection of the second task's error. Assume the sum fits in int.
Model answer

Submit both before waiting and reuse one monotonic deadline. The Java finally also handles rejection of the second submission; the C++ catch handles launch failure and requests both stops before joining either thread. Waiting in input order can hide B's early failure behind A's timeout; use a completion queue or continuations for fail-fast observation. Cancellation does not roll back side effects. C++ cleanup still waits for cooperative tasks, so it can exceed the deadline, indefinitely if a task ignores stop. For a prompt response, a longer-lived executor must own unfinished tasks and all their captured data; a detached thread referencing stack data is not a safe shortcut.

Explain
Explain to an interviewer what a future and a promise are, who holds which, and what happens if the producer dies or forgets to set the result, in Java and in C++.
Model answer

They are the two ends of one single-assignment shared state. The producer holds the promise and fills the state exactly once, with a value or an exception; the consumer holds the future and waits on it, then gets the value or observes the failure, wrapped in Java and rethrown directly in C++. Filling the state happens-before the consumer's get() returns, so the result is safely published without extra locks. In C++ these are separate types, std::promise and std::future, and a packaged_task bundles a function with its promise. In Java, FutureTask plays the task role and CompletableFuture is both ends at once, with complete and completeExceptionally as the write side.

If the producer never fills it, the languages differ. In C++, destroying an unset std::promise stores a broken_promise error, so the consumer wakes with a std::future_error. In Java, an incomplete CompletableFuture stays incomplete forever, so an untimed get() hangs; every producer path, especially the error path, must complete it, and consumers should wait with timeouts.

Design
Many threads call appendEvent(bytes), which must return only after the bytes are durable on disk. For this estimate, assume a serialized fsync takes 5 ms and other costs are negligible. How do you get far more than 200 appends a second, and what does each caller wait on?
Model answer

With one writer and the stated timing assumptions, one fsync per append caps you at about 200 appends a second. Instead: producers put (bytes, promise) into a bounded queue and wait on the promise's future. A single writer thread takes everything waiting in the queue as one batch, writes it in order, calls fsync once, and then completes every promise in the batch (or fails them all with the I/O error). While one fsync is in progress, new events accumulate for the next batch, so batch size grows with load: at 50 events per batch, the simplified model gives about 10,000 appends a second, before write bandwidth, queueing and scheduling overhead. This is group commit. The bounded queue gives backpressure, a single writer keeps order, and close() stops accepting, drains the queue, does a final fsync and completes the last promises. Each caller waits only on its own future, ideally with a timeout.

"Explain a future and a promise to a teammate. What makes reading the result safe?"
What a strong answer covers

  • Completion delivers a value or failure and publishes preceding writes

How a senior would say it
A future is the read handle for a result, and a promise is the producer's way to complete that result. They refer to one shared state that moves from incomplete to a value or a failure. A waiting consumer can then retrieve the outcome. Completion also publishes the producer's preceding writes, so a consumer that successfully gets a constructed result does not need an extra lock just for that handoff. It does need synchronization for later shared mutations. In Java, CompletableFuture combines the producer and consumer roles, while an executor can return the narrower Future interface. Java callers may get the result repeatedly. In C++, promise and future are separate types, and future.get consumes its state, even when it rethrows a stored exception. For several readers I use shared_future copies and keep the state alive while using a returned reference. There is also a lifecycle difference: destroying an unset C++ promise reports broken_promise. Forgetting to complete a Java CompletableFuture can leave readers waiting forever, so every producer path needs an outcome.

"A request times out after one second. Can you guarantee its background work has stopped?"
What a strong answer covers
  • Timeout ends a wait and does not stop or roll back work
  • Successful FutureTask.cancel(true) requests interruption; CompletableFuture.cancel does not interrupt
  • C++ futures need a separate stop mechanism and tasks must cooperate
  • Use one deadline across admission and multiple waits
  • Joining or async state destruction can delay return; unfinished work needs a longer-lived owner
How a senior would say it
No. A timeout tells me the caller stopped waiting; it does not prove the producer stopped or undo its side effects. With a Java FutureTask, successful cancel with interruption enabled requests an interrupt, but a CPU loop that ignores interruption can continue after its future reports cancelled. CompletableFuture cancellation does not even interrupt the producer. In C++, a future has no cancellation operation, so I pass a stop token and make the task check it or use an operation that supports cancellation. I would propagate one deadline through admission and every wait, instead of spending a fresh second at each step. Cleanup matters too. A jthread joins when destroyed, and releasing the last unfinished asynchronous state from std::async can wait for its thread. Either can delay the response beyond the deadline. If the caller must return promptly, a longer-lived executor must own unfinished work and its captured data. I would bound that outstanding work and monitor cleanup, rather than detach a thread that might reference a dead stack frame.

Out loudabout 60 s
"One replica fails immediately, another succeeds, and a third is slow. Which result should an any operation return?"
What a strong answer covers
  • Clarify first completion versus first successful completion
  • invokeAny skips failures while success remains possible and cancels unfinished tasks
  • CompletableFuture.anyOf can complete exceptionally first and does not cancel losers
  • C++20 has no standard when_any; a helper needs synchronized winner and failure accounting
  • Request stop outside shared-state locks and distinguish selection latency from joining losers
How a senior would say it
I would first clarify whether any means the first completion or the first success. For a replicated read, I usually want the first success. Java's invokeAny ignores an early task failure while another can succeed, returns a successful result, and cancels unfinished tasks. CompletableFuture.anyOf has a different contract: an early failure can complete the combined future exceptionally, and it does not automatically cancel the losers. In C++20 there is no standard when_any, so I need a completion queue or shared state recording the first winner and how many tasks failed. If all fail, I report a failure. I request stop outside the result mutex, because stop callbacks can execute synchronously. Finally, selecting a winner is different from returning it. The helper in this lesson joins its threads before returning, so an uncooperative loser can still delay the caller. That ownership decision must be explicit.

Likely follow up: How would you return the winner promptly while keeping losing tasks and their data alive safely?
