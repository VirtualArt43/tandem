Executors, futures and async

Thread pools and their internals, shutdown, sizing, failure modes, futures and promises, CompletableFuture, scheduled executors, virtual threads and coroutines.

1Corethread-pools
Why use a thread pool instead of creating a thread per task?
Model answer
  1. Cost: creating and destroying a platform thread can cost tens of microseconds or more as an order of magnitude, plus stack resources; measure the platform; for small tasks that overhead dominates.
  2. Bounded resources: a thread pool caps the number of threads, and with a bounded queue it caps pending work too, so a burst cannot create 10,000 threads and topple the process. It gives you one place to apply backpressure and rejection.
  3. Lifecycle in one place: shut down, wait for completion, name threads, handle uncaught exceptions, export metrics.
  4. Policy separate from submission: the caller says what to run; the executor decides how (how many threads, which order, timing, virtual or platform threads).

The downsides: tasks share threads, so one slow or blocking task occupies a worker; thread-local state leaks from one task to the next; and tasks that wait for other tasks in the same bounded pool can deadlock.

Java 21 changes one part of the argument: for blocking, I/O heavy tasks, virtual threads (Executors.newVirtualThreadPerTaskExecutor()) make a thread per task cheap again. Per-task thread overhead becomes much smaller; resource limits still matter, so you still bound concurrency, now with a semaphore instead of the pool size.

Likely follow up: "Should you pool virtual threads?" No: they are cheap to create, so create one per task and limit access to scarce resources with a semaphore.

2Corejavathread-poolsMicrosoftLinkedIn
How does ThreadPoolExecutor decide whether to run a task on a new thread, queue it, or reject it?
Model answer

For a running executor whose thread factory can create workers, execute(task) follows this policy:

  1. If fewer than corePoolSize workers exist, start a new thread with this task, even if other workers are idle.
  2. Otherwise offer the task to the queue; if the queue accepts, a worker will take it later.
  3. Only if the queue is full and fewer than maximumPoolSize threads exist, start an extra thread with this task.
  4. Otherwise hand it to the RejectedExecutionHandler, the rejection policy (abort with an exception by default; caller-runs, discard and discard-oldest also exist).

Threads above the core size die after keepAliveTime idle (core threads too, with allowCoreThreadTimeOut(true)).

The trap is queue before max. With an unbounded LinkedBlockingQueue, which newFixedThreadPool uses, step 2 always succeeds: the queue normally prevents growth beyond core size; shutdown still rejects, and allocation or worker creation can fail; the queue grows until memory runs out. With a SynchronousQueue (newCachedThreadPool), step 2 fails unless a worker is waiting, so threads grow toward Integer.MAX_VALUE.

After enqueueing, the executor rechecks shutdown and ensures a worker exists. CallerRunsPolicy runs inline when saturated but silently discards after shutdown, so returned futures can remain incomplete. Use an explicit rejection contract for result-bearing tasks.

Likely follow up: "In that pool, when is the 9th thread created?" Only after 1,000 tasks are already queued.

3CoreshutdownRubrik
What is the difference between shutdown(), shutdownNow() and awaitTermination()?
Model answer
  • shutdown(): stop accepting new tasks (later submissions are rejected), but run everything already queued and running to completion. Returns immediately; it does not wait.
  • shutdownNow(): stop accepting, remove the queued tasks and return them as a List<Runnable> (they never started), and interrupt every running worker. Running tasks stop only if they respond to interruption. Also returns immediately.
  • awaitTermination(timeout): block until all tasks have finished after a shutdown, or the timeout passes; returns whether it terminated.

The standard two phase idiom, as shown in the ExecutorService Javadoc:

Since Java 19, ExecutorService is AutoCloseable: close() initiates shutdown and waits without a timeout. If interrupted it requests immediate shutdown, continues waiting, and restores interruption before returning. Noncooperative tasks can therefore hang scope exit.

For a pool you build yourself, which Rubrik asks for: shutdown sets a flag, wakes idle workers, and lets them drain the queue and exit when it is empty; shutdownNow sets a stop flag, clears the queue, returns what was in it, and requests worker cancellation. Removed FutureTasks are not automatically cancelled by shutdownNow(); cancel or otherwise resolve their futures explicitly.

Likely follow up: "A task ignores interrupts. What does shutdownNow achieve?" Nothing for that task: awaitTermination times out and the task keeps running, which is why tasks must check for interruption and use timeouts on blocking calls.

4Seniorthread-poolsbuildRubrik
In a pool you build yourself, how should the worker loop handle task exceptions and interrupts?
Model answer

The requirements:

  • Ordinary task failures must not silently shrink the pool: contain them or replace failed workers.
  • The failure must reach the submitter, through the task's future.
  • An interrupt means "stop" only when the pool is stopping; a stray interrupt left behind by a task must not kill the worker either.
  • A future wrapper can catch Throwable to record failure; executor policy must separately decide whether a fatal Error retires the worker or makes the process unhealthy. A Rubrik interviewer probed exactly which exceptions a candidate's pool caught.

In Java, stopping must be volatile. Clearing stale interruption before checking stopping avoids leaking it into the next task or losing shutdown. Poison pills require stopped admission and one pill per worker after accepted work. Dequeue can race with shutdown, so define when a task becomes claimed and cancel unstarted futures. C++ has no interrupts: shutdownNow closes the queue, drains and returns the pending tasks, and sets a stop flag that long tasks check (or a std::stop_token).

Likely follow up: "Should the worker rethrow an Error?" Record it in the task's future first; for something like OutOfMemoryError, treat the process as unhealthy rather than looping on.

5Corejavaexceptions
What is the difference between execute() and submit() on an ExecutorService, especially when the task throws?
Model answer

execute(Runnable) on a normal ThreadPoolExecutor worker is fire and forget. If a plain task throws, the exception escapes the worker's run: the worker thread dies, the thread's uncaught exception handler runs (the default prints the stack trace), and ThreadPoolExecutor replaces it if lifecycle and capacity require it. Other executors, caller-runs policies and wrapped tasks can behave differently. Noisy, but visible.

submit(...) wraps the task in a FutureTask and returns a Future. The FutureTask catches every Throwable and stores it; the worker survives and nothing is printed. The failure appears only when someone calls Future.get(), as an ExecutionException whose cause is the original exception; get() can also be interrupted or report cancellation. If nobody calls get(), the failure is lost.

This is the classic "the background job stopped and nobody noticed" bug. It is worse with scheduleAtFixedRate: one exception silently cancels every later run. Remedies: use execute when you need no result; catch and log inside the task; always consume the future; or override afterExecute in a ThreadPoolExecutor subclass to inspect completed futures.

Likely follow up: "How does C++ compare?" A std::packaged_task behaves like submit: the exception sits in the future until get(). Without that wrapper, an exception escaping a thread terminates the process.

6CoresizingnumbersMetaDatabricks
How do you size a thread pool?
Model answer

Start from the kind of work, then measure.

  • CPU bound: start near the CPU capacity available to the process, accounting for quotas, other pools and SMT; then measure. Extra threads often add switching.
  • Blocking I/O: threads approximately = cores x target utilization x (1 + wait/compute time). At full target utilization, 8 cores and 90 ms waiting per 10 ms computing suggest 80 threads.
  • Little's law: steady-state mean concurrency = throughput x mean latency. 500 requests per second at 200 ms each needs about 100 in flight.

Cap it by the real bottleneck:

  • The downstream: 200 threads sharing a 20 connection database pool just queue at the pool.
  • Bandwidth and disk: a Databricks crawler round probed thread count against dataset size and disk/network limits.
  • Per-host limits: a Meta downloader round asked for a safe thread count. Choose using protocol, server capacity and bandwidth.
  • Memory per in-flight task.

Keep separate pools for different classes of work (CPU versus I/O) so one cannot starve the other, and confirm with a load test: throughput rises, flattens, then falls. Pick the knee.

Likely follow up: "The database slows from 10 ms to 100 ms. What happens to your pool?" By Little's law the same throughput now needs ten times the concurrency; the pool saturates and the queue grows, so you need timeouts, a bounded queue and rejection.

7Seniorthread-poolsfailures
What are the classic ways thread pools fail in production?
Model answer
  1. Unbounded queue: latency and memory grow quietly until an OutOfMemoryError minutes later.
  2. thread starvation deadlock: tasks block waiting for other tasks submitted to the same bounded pool (a parent waits on its children's futures). When every thread is a waiting parent, the children never run. Fix with separate pools or non-blocking composition (thenCompose); fork/join workers can help with suitable acyclic task dependencies, but arbitrary blocking or cyclic waits can still deadlock.
  3. Swallowed exceptions: submit() stores failures in futures nobody reads.
  4. A slow dependency saturates the pool: every worker blocks on a hung call with no timeout, and the whole service stalls. Fix with timeouts and bulkheads.
  5. Thread-local leakage between tasks that share a worker.
  6. The shared common pool: parallel streams and CompletableFuture.supplyAsync without an executor run on ForkJoinPool.commonPool(), with configurable parallelism, commonly available processors minus one. If common-pool parallelism is below two, default async CompletableFuture tasks use new threads instead. Blocking I/O there starves unrelated code.
  7. Forgotten shutdown: non-daemon workers keep the JVM alive.
  8. Too many pools: every library brings its own, and the process ends up with hundreds of threads.
Every pool I create gets a bounded queue, a name, a rejection policy, timeouts on its blocking calls, and metrics on queue depth and active threads.

Likely follow up: "How would you spot starvation deadlock?" A thread dump where every worker of one pool is WAITING in Future.get on tasks belonging to that same pool.

8Corefuturesjavacpp
What are futures and promises, and how do the Java and C++ versions differ?
Model answer

A future is a read handle to a value that will exist later; a promise is the write handle that sets it, a value or an exception, exactly once.

Java:

  • Future<T> (from submit): get() blocks, get(timeout), cancel(mayInterrupt), isDone(). Cancellation requests are cooperative; isDone() also includes failure and cancellation. You cannot complete it yourself and cannot chain on it.
  • CompletableFuture<T> is both future and promise: complete(v), completeExceptionally(e), plus non-blocking composition (thenApply, thenCompose and the rest).

C++:

  • std::promise<T> (set_value, set_exception, get_future once) and std::future<T> (get once, after which it is invalid; wait, wait_for).
  • std::shared_future<T> for several readers; std::packaged_task wraps a callable and fills its future.
  • std::async(std::launch::async, f) runs f on another thread and returns a future. Releasing the last reference to its still-running async shared state can block, so discarding the returned temporary waits at the end of the expression. Default-policy std::async(f) may instead defer execution until a wait or get.
  • C++20 has neither standard future continuations nor built-in future cancellation. Java CompletableFuture.cancel(true) also does not interrupt its computation.

Exceptions: Java's get() wraps the failure in ExecutionException; C++'s get() rethrows the original exception.

Likely follow up: "What if a promise is destroyed without being set?" In C++, get() throws std::future_error with broken_promise. A Java CompletableFuture that is never completed blocks get() forever, so use timeouts.

9SeniorcompletablefutureinternalsGoogleApple
How does CompletableFuture work internally?
Model answer

A CompletableFuture keeps its state in two fields:

  • result: a volatile Object, null while pending; otherwise the value, or a wrapper holding null or an exception.
  • stack: a lock-free treiber stack of Completion objects, the dependent actions waiting for this future.

complete(v) encodes the value, including null, then CASes result from pending to that encoding. Only the first completer wins; later calls return false. Completion callers can help drain and fire dependents (postComplete); this is not exclusively the winning thread's job.

thenApply(fn) creates a new future d and a completion linking source to d. If the source is already normally complete, fn can run in the calling thread; exceptional completion skips this success handler. Otherwise the completion is pushed onto the source's stack with a CAS, and the source is checked again in case it completed in the meantime, which closes the lost completion race.

Threads: non-async stages may run in a completing thread, another completion caller, or the registering caller. The ...Async variants submit to an executor, ForkJoinPool.commonPool() by default, with a new-thread fallback when its parallelism is below two. Exceptions flow down the chain wrapped in CompletionException until a stage handles them.

Google has asked candidates to design a custom CompletableFuture "under the hood". Explain one-time completion, callback registration races and execution policy.

Likely follow up: "Why can thenApply run on a surprising thread?" An I/O callback can run dependent actions inline. Avoid blocking that completion thread.

10SeniorfuturesbuildRubrik
Build a simple future with complete, get and then(callback).
Model answer

State: a done flag, the value, and a list of callbacks, all guarded by one lock. complete sets the value once, wakes blocked get callers, and takes the callback list, then runs the callbacks outside the lock, since they may be slow or call back into this future. then registers the callback if not done, or runs it at once if done. Rubrik has asked for a JavaScript style Promise in Java: working code first, then improvements.

Callback failures are isolated through a nonthrowing reporter so one callback does not skip the rest. Callbacks can run concurrently and are not promised registration order. Reading value after leaving the lock in then is safe: we observed done == true under the lock, and value was written before done under that same lock. In C++, the same design uses a std::mutex, a std::condition_variable and a std::vector<std::function<void(const T&)>>.

Likely follow up: "Add failures." Store a Throwable, add completeExceptionally, make get throw ExecutionException, and give callbacks both the value and the error.

11Seniorcompletablefuturejava
Explain thenApply, thenCompose, thenCombine and allOf, and the handlers exceptionally, handle and whenComplete.
Model answer
  • thenApply(fn): transform the result, like map.
  • thenCompose(fn): fn itself returns a CompletionStage; the result is flattened, like flatMap. Use it when the next step is asynchronous, to avoid a future of a future.
  • thenCombine(other, fn): when both futures complete, combine their results.
  • allOf(...): a CompletableFuture<Void> that completes when all complete; read each result with join(). anyOf(...) completes with whichever finishes first.
  • exceptionally(fn): called only on failure; returns a fallback value.
  • handle((v, ex) -> ...): always called; can transform success and failure alike.
  • whenComplete((v, ex) -> ...): observe either outcome. If the observer throws after success, the returned stage fails; if the source already failed, its failure takes precedence.

Handlers may receive the original exception or a CompletionException, so unwrap only known wrappers. orTimeout exceptionally completes that future; it neither stops the underlying work nor automatically cancels sibling stages.

Likely follow up: "One future passed to allOf fails. What happens?" allOf still waits for all of them, then completes exceptionally; the others keep running unless you cancel them yourself.

12SeniorfuturesdurabilityDatabricks
Many threads call appendEvent(bytes), which must return only once the event is durable on disk. How do you make it fast?
Model answer

A serialized write followed by a successful durability operation can acknowledge one event at a time, provided partial writes and errors are handled. Storage flush latency varies from microseconds to milliseconds as an order of magnitude. With one event per flush, throughput is roughly the reciprocal of that measured latency, not a universal events-per-second limit.

group commit fixes it:

  1. Each producer puts (event, promise) into a queue and waits on its future.
  2. One writer drains a batch bounded by bytes, count or time, writes all bytes while handling short writes and interruptions, flushes once, then completes that batch's promises.

Batches grow automatically with load, so throughput rises with concurrency while latency stays near one fsync plus queueing. Order is queue admission order, respecting non-overlapping appends. Recovery also needs record framing and a policy for incomplete tails. Add backpressure with a bounded queue, and on shutdown close the queue, drain it, fsync a final time, and complete or fail every pending promise. If fsync fails, fail every promise in that batch. This is the path a Databricks L4 report described, implemented in C++ with std::promise and std::future.

Likely follow up: "Is the queue's lock the bottleneck now?" Measure; batching often shifts the bottleneck. Use the target OS and filesystem's documented durability contract, including stronger flushes or directory synchronization where required.

13Seniorscheduled-executorsLinkedInNetflixRubrik
How does a scheduled executor work, and what is the difference between scheduleAtFixedRate and scheduleWithFixedDelay?
Model answer

Use a deadline-ordered priority queue, lock and condition. A worker waits while empty, then examines the earliest task; if it is due, remove it and run it outside the lock; otherwise wait with a timeout until it is due. schedule() inserts a task and signals if the new task is now the earliest, so a sleeping worker recomputes its wait. Forgetting that signal is the classic bug: a task due in 1 second waits behind one due in an hour. Use a monotonic clock (System.nanoTime, steady_clock) and bound scheduled-task admission: Java's delay queue is unbounded.

Java's ScheduledThreadPoolExecutor keeps a heap and uses a leader-follower waiting scheme: one leader waits with a timeout for the head task while the others wait without one, so they do not all wake together.

  • Fixed rate: next start = previous scheduled start + period. Keeps the cadence; if a run is late or slow, the next runs start back to back, but never overlap.
  • Fixed delay: next start = previous end + delay. Guarantees a gap between runs.

A periodic failure suppresses later runs; inspect its ScheduledFuture or log and handle expected failures. Cancelled delayed tasks may be retained until due unless setRemoveOnCancelPolicy(true) is enabled. LinkedIn, Netflix and Rubrik have all asked candidates to implement this executor.

Likely follow up: "Why not give each delayed task its own thread that sleeps and then runs?" With thousands of tasks you get thousands of sleeping threads; one timer queue serves them all.

14Seniorthread-poolsbuildRubrik
How would you add per-task timeouts and reclaim idle threads in a pool you build yourself?
Model answer

Timeouts: a running task cannot be killed safely, so the options are cooperative:

  • The caller waits on the task's future with a timeout and, on expiry, cancels it with interruption; the task must respond to interrupts.
  • A watchdog tracks task identities and deadlines, requesting cancellation only if that same task is still running. A stale timer must not interrupt a worker already running its next task.
  • Pass the remaining deadline into blocking operations such as socket calls and timed locks; interruption support varies by API.

If interruption is ignored, work may continue after its future is cancelled. Unbounded replacement workers defeat the capacity limit; cap replacements, shed load, and isolate noncooperative work in a process when hard termination is required.

Idle reclaim, like keepAliveTime: workers above the core size use poll(keepAlive) instead of take(). On a timeout, check the worker count and decrement it in one atomic step; otherwise several idle workers can all see "above core" and all exit, dropping the pool below its core size.

Rubrik asked exactly these follow ups after a candidate built a bounded queue and a pool on it.

Likely follow up: "How does ThreadPoolExecutor do the count?" It packs the run state and the worker count into one AtomicInteger and decrements with a CAS.

15Seniorjavathread-pools
When do you use invokeAll, invokeAny and an ExecutorCompletionService?
Model answer
  • invokeAll(tasks): submit them all and block until all complete; returns futures in task order. With a timeout, unfinished tasks are cancelled. For "fan out, then wait for everything".
  • invokeAny(tasks): returns the result of one task that completed successfully and cancels the rest; throws ExecutionException only if all fail. For redundant requests, such as asking two replicas and taking the first good answer.
  • ExecutorCompletionService, a completion service: wraps an executor; take() and poll() return futures in completion order, so you process results as they finish instead of waiting on a slow first future.

CompletableFuture.allOf is a similar completion gate. anyOf is not first-success selection and does not cancel losers. invokeAll returns failed futures too: inspect each with get(). Submission rejection and interruption also need cleanup. C++ has none of these in the standard library: keep a vector of futures, or have each task push its result into a shared blocking queue, which is the completion service pattern by hand.

Likely follow up: "How does anyOf differ from invokeAny?" anyOf completes with whichever future finishes first, even if that one failed; invokeAny waits for the first success.

16Seniorvirtual-threadsjava
What are Java 21 virtual threads, when do they help, and what are their pitfalls?
Model answer

virtual threads (JEP 444, final in Java 21) are Thread objects scheduled by the JVM onto a small pool of carrier platform threads, a dedicated ForkJoinPool whose default target parallelism is the available processors. When a virtual thread blocks on a supported operation (socket I/O, sleep, java.util.concurrent locks and queues, join), it unmounts: its stack is saved to the heap and the carrier runs another virtual thread. Millions may be possible for small waiting tasks.

They help with high concurrency, mostly waiting, blocking style code: thread-per-request servers, fanning out to many services. You get the throughput of asynchronous code while writing plain sequential code.

They do not help CPU bound work, which is still limited by cores. They do not accelerate computation.

Pitfalls:

  • pinning: on Java 21, blocking inside synchronized or a native frame pins the carrier, which can starve the scheduler. On Java 21, prefer ReentrantLock around long waits; diagnose with -Djdk.tracePinnedThreads=full or the jdk.VirtualThreadPinned Flight Recorder event.
  • Do not pool them; limit access to scarce resources with a Semaphore, not with a pool size.
  • ThreadLocal-heavy code (per-thread caches) multiplies memory by the number of threads.
  • Some blocking operations, such as many filesystem calls, can capture carriers and trigger bounded scheduler compensation. Pinning does not receive that compensation; do not assume arbitrary native blocking is recognized.

Likely follow up: "Will virtual threads fix a slow database?" No: the connection pool of, say, 20 connections is still the limit; virtual threads just wait for it more cheaply.

17Stretchcppcoroutines
How do C++20 coroutines differ from threads, and where do they fit in concurrency?
Model answer

A coroutine is a function that can suspend (co_await, co_yield) and be resumed later. C++20 coroutines are stackless: locals surviving suspension live in a coroutine frame, often heap allocated. Suspension occurs at coroutine suspension points, including co_await, co_yield and initial/final suspension, not transparently deep inside an ordinary called function.

They provide no threads and no scheduler. When resumed, a coroutine runs on whichever thread calls resume(). Concurrency comes from what you pair them with: an event loop (Boost.Asio's io_context with awaitable operations), a thread pool executor, or another asynchronous runtime. C++20 itself ships only the low level coroutine machinery, not a standard task or I/O runtime.

Suspension need not enter the kernel, but allocation, executor hops and I/O determine cost. Scheduling is cooperative, so a coroutine that computes for a second blocks its thread for that second.

Compared with Java virtual threads: virtual threads can suspend deep call stacks during supported blocking operations; C++ coroutines use explicit suspension points and asynchronous APIs.

Data races still apply: a coroutine resumed on another thread needs the same synchronization as any other cross-thread handoff, and later thread-local lookups can refer to a different thread's instance. Never concurrently resume one coroutine, and keep captured objects and its frame alive until completion.

Likely follow up: "When would you choose coroutines over a thread pool in C++?" For many waiting I/O operations where platform threads would cost too much memory.
