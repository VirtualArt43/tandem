Ranged key-value store

Thread-safe structureshard55 minUberRubrikMicrosoft

A consistent range snapshot must exclude overlapping batches without stopping an unrelated writer on the other side of the key space.

The task

Implement set, get, atomic setAll, and inclusive getRange. This exercise uses a fixed integer key universe 0 to keyCount - 1, with 1 to 1024 keys. Values are signed 64-bit integers and keys start absent. Missing reads return an empty optional; range results contain only present keys.

  • setAll is one atomic update, including when caller iteration order is reversed. A range sees a complete before or after state for overlapping keys, never a half-applied batch. Invalid keys reject the entire batch before any write.
  • Lock only keys touched by the write or covered by the read range. A slow range must permit writes outside it. The returned map is detached from subsequent writes.
  • The constructor's visit(key) hook is harness instrumentation. Invoke it once for each key, including absent keys, during range copying while the complete range remains protected. In production pass a no-op. It may block or throw, but never reenters the store.
  • Inputs are not mutated concurrently by their caller. Memory allocation failure is outside the tested contract. Do not replace consistency with repeated reads until values happen to match.

Example: a batch changes balances 50 and 50 to 40 and 60. A range covering both keys returns either pair. A concurrent write to key 15 must finish while a range over 0 to 1 is paused.

What the tests check

  • Absent keys, scalar reads, detached snapshots and invalid-batch rejection.
  • An explicitly paused range overlaps a completed outside write, measured with an active-reader counter.
  • Snapshots never see half a batch; reversed input construction order does not cause deadlock.
  • Four writers perform random transfers within independently owned account pairs while four readers repeatedly verify the global sum.
  • A throwing visit hook releases every lock; seeded stress, watchdog and bounded joins catch hangs.

Taught in: Lock granularity, contention and lock striping

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How does this match the Uber range-lock follow-up?
The reported follow-up asks to lock only the range during getRange to reduce waiting and deadlock. The bounded integer universe makes per-key locking explicit; an arbitrary ordered key space needs interval locks or another phantom-safe design.
How would you support the Rubrik snapshot API?
Give snapshots stable versions and retain old values while readers reference them, or copy an immutable snapshot. Taking separate per-key snapshots without a common boundary can combine different moments.
What changes for the Microsoft tree snapshot variant?
The topology is shared state too. Concurrent insertions and deletions require a versioned tree, an immutable root, or locking that protects the traversed structure, not just existing node values.
Does get followed by setAll make a transfer atomic?
No. Another writer can change a balance between those calls. Add a transfer operation that holds both write locks through read and update, or use a version check. The harness gives each transfer writer a distinct pair so it tests batch visibility without introducing that separate client bug.
Can stripes replace one lock per key?
They reduce lock memory but introduce false conflicts: unrelated keys can share a stripe. That can violate this exercise when a paused range blocks an outside write. An interval-lock table is a more general follow-up.
Are readers or writers guaranteed fairness?
The standard read-write locks used here do not establish the same starvation guarantee on every platform. Strict fairness requires an explicit admission policy and separate tests.

The invariant

Each key's lock guards its presence and value. A batch holds all its write locks before changing the first value. A range holds all its read locks before copying the first value. Consequently, an overlapping writer cannot leave only part of its batch visible. Locks for absent keys prevent insertion phantoms inside this fixed universe.

Ordering and linearization

Every operation acquires locks in ascending key order. The input map's iteration order never controls lock order. A batch becomes visible while it holds its complete set, and a range can be linearized once its complete read-lock set is acquired. Disjoint sets have independent locks, so a writer outside a paused read proceeds.

Java uses finally to release locks in reverse order. C++ stores RAII lock guards in a vector. Hook exceptions cannot leave a lock behind. Scalar reads take the same per-key lock as writes. The range map contains copied values rather than references into mutable storage.

The broken design

The broken implementation adds a single global lock around ranges and batches. It can preserve values correctly and pass ordinary atomicity stress tests. But a reader over keys 0 and 1 pauses while holding that lock; a writer to 15 cannot finish. The hook test observes this blocked independent operation and then releases the hook so the harness still terminates.

Costs and limits

Lock storage is O(N) for the configured universe. A range of width W takes O(W) locks and up to O(W log W) work to build the ordered result map. Java sorts B batch keys in O(B log B); C++ receives a sorted map. Both then take B locks and do B writes. Broad ranges intentionally block writers inside their bounds; this implementation is unsuitable for an unbounded sparse key space without redesign.

How to say it in the interview

I will lock the entire touched set before reading or changing any values, always in ascending key order. That gives a consistent snapshot and atomic batches without a global data lock. The fixed universe also lets me protect absent keys, so inserts cannot appear midway through a range.
