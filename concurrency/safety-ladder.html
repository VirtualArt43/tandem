The safety ladder

Six ways to make shared state safe, from not sharing it to lock-free code, and how to pick one for each piece of state.

Asked atGoogleUberLinkedIn
Before this:The lost update: read, modify, writeInvariants, critical sections and finding shared stateSafe publication, immutability and final fields

When an interviewer says "now make it thread-safe", first identify the state and the rules it must preserve. Walk down a ladder: can it avoid being shared, can it be immutable, can one thread own it, can a proven structure hold it, and which lock guards any remaining invariant?

In plain words

Think of how an office handles shared things. Everyone has a personal notebook, so nobody fights over notebooks. The leave policy is a printed sheet on the notice board: hundreds read it, nobody writes on it, and a new version replaces the old sheet whole. Petty cash is touched only by the accountant; everyone else hands her a slip. Visitor badges come from a system the building bought, which already handles two receptionists at once. The meeting room has one booking sheet with a pen on a string. And somewhere there is a clever self-organizing system that one engineer built and nobody else understands.

That list runs from safest to riskiest, and the further down you go, the more ways there are to get it wrong. A good engineer uses the highest step that fits each thing, and goes lower only when the higher step truly cannot work.

The six rungs

RungThe ideaJavaC++What can still go wrong
1. Do not shareEach thread has its own copy; combine at the endLocals, per-request objects, per-thread partial resultsThe same; locals and per-thread containers merged after joinA reference escapes to another thread
2. Share immutablyShared, but nobody can change it after it is builtRecords and final fields, swapped whole through a volatile or atomic referenceconst objects behind std::shared_ptr<const T>, swapped wholeHidden mutable parts; unsafe publication
3. One ownerOne thread accesses mutable state; others send it messagesA single thread draining a queueThe same with a mutex-guarded queue and a condition variableThe owner becomes a bottleneck
4. DelegateA proven concurrent structure holds the stateConcurrentHashMap with merge and compute, BlockingQueue, LongAdder, atomicsstd::atomic; there is no standard concurrent map or queue, so use a tested wrapper or vetted libraryCompound actions across two calls or two structures
5. SynchronizeA lock guards each invariantsynchronized, ReentrantLock, read-write locksstd::mutex with RAII guards, std::shared_mutexDeadlock, contention, forgetting the lock on one path
6. Custom lock-free algorithmsGuarantee system-wide progress even if one participant stallsProven compare-and-set algorithmscompare_exchange_weak algorithms with appropriate memory orders and lock-free underlying atomicsABA, memory reclamation, ordering, starvation

Higher rungs can remove whole classes of races. Truly confined state cannot race; safely published immutable state does not change underneath readers; state accessed only by its owner has no concurrent accesses. This is a design preference, not a formal ranking of guarantees: a clear monitor with one lock is often an excellent answer, and a single-owner design can still fail through unsafe messages or an unbounded queue.

How to pick a rung for one piece of state

Do not pick a rung for a class. Pick one for each invariant and all the state it covers, working through these questions in order:

  1. Does it need to be shared at all? Per-request scratch data, buffers, partial results: keep them confined to one thread. Rung 1.
  2. Can each published version stay unchanged? Configuration, routing tables, lookup data: build it, freeze it, and replace it whole when it changes. Rung 2.
  3. Can one thread own access to the mutable state? An append-only log, a writer that batches to disk, state with complex invariants and modest write rates: give it an owner. Rung 3.
  4. Does a proven structure's single operation cover the whole invariant? A counter, a cache of independent entries, a work queue: delegate. Be honest about compound actions: if the invariant spans two calls or two structures, this rung does not fit. Rung 4.
  5. Otherwise, what exactly is the invariant, and which one lock covers it? Rung 5, with the lock guarding everything the invariant mentions and nothing else.
  6. Is that lock measurably the bottleneck, or is nonblocking progress a requirement? Consider rung 6 only with a correctness and progress argument. One atomic word is a useful simple case, not a requirement of all lock-free algorithms.

The boundary matters as much as the state

A local variable is not proof of confinement. A local reference can point to a shared list, and a callback can capture and expose a local buffer. Keep mutable aliases inside the owner, or transfer ownership through a synchronized queue and stop accessing the object on the sending side. In a thread pool, a thread-local value belongs to a worker, not a request; clear request-specific data when the task ends.

One writer is not enough if readers access its mutable state directly. Route reads through the owner too, or publish immutable snapshots. A correctly synchronized queue publishes writes made before enqueueing; it does not make later sender mutations safe. Bound the mailbox, define rejection and shutdown, and say whether an acknowledgement means queued, applied, or durable.

Immutability must extend to reachable mutable data. Java records provide final component fields, but a record containing a list needs a defensive copy and immutable elements. In C++, std::shared_ptr<const T> restricts access through that handle; it does not stop another mutable alias, a mutable member, or a pointer inside T from changing data.

Rung 2 up close: why immutable beats careful

Here is the kind of state that tempts people into locks: a range with a low and a high value that must stay one apart. The writer updates the fields one by one; readers check the invariant.

In Java a reader can see the new low and the old high. These are inconsistent pairs, not torn individual int reads. The output is illustrative: Java may observe no inconsistent pair in a particular run. In C++ the unsynchronized accesses cause a data race and undefined behaviour, so the language does not restrict the result to such pairs; ThreadSanitizer can expose the race even if the count is zero.

You could fix this with one lock around the whole pair update and the whole pair read. Another choice is an immutable object published as one snapshot: each reader captures the reference once and then reads that version. This simplifies the invariant, but allocation, copying and reference counting have costs; it is not automatically faster than a lock.

Two details make it work. The object is fully built before any other thread can see it, and the reference uses safe publication: a volatile field in Java gives the reader a happens-before edge to everything the writer did before the write (see safe publication). In C++ the shared pointer itself is shared state, so it needs protection; the mutex is held only to copy the pointer, never while reading the range. The shared pointer also keeps an old snapshot alive for as long as a reader holds it, which is what makes "replace whole" safe in a language without a garbage collector.

C++

C++20 specifies std::atomic<std::shared_ptr<T>>, but Tandem's installed Apple libc++ does not provide it. The mutex example also works in C++17. The older std::atomic_load and std::atomic_store overloads for shared_ptr are available here and deprecated in C++20; neither those overloads nor the C++20 specialization promise lock-free operations.

Capture one snapshot per logical operation. Reading range separately for lo and hi can mix two valid versions. With multiple writers, immutable snapshots alone do not prevent lost updates: two writers can derive replacements from the same old version and overwrite each other's change. Serialize read-modify-publish with a writer lock, or use a CAS loop that recomputes from the latest snapshot.

Worked example: one class, five rungs

A URL shortener service is a single class used by every request thread. "Make it thread-safe." Instead of a lock on every method, classify each field:

StateHow it is usedRungConcretely

Config: limits and feature flagsRead on every request, changed by an admin a few times a day2. ImmutableAn immutable config object behind a volatile or atomic reference, replaced whole
Audit log written to a file in orderAppended by every request; order matters; disk is slow3. One ownerRequests put entries on a bounded queue; one writer thread owns the file

Nothing here needs rung 6. A request can retain an older config until it finishes; there is no one-version staleness bound. The audit log adds a queue hop, counters and map bins can contend, and the cache lock serializes cache operations. Sharding that cache reduces contention but gives per-shard recency and capacity, rather than one exact global LRU order.

Common mistakes

  • Adding locks without naming the invariant. One shared lock around related methods can be a correct monitor. Separate locks for coupled fields are wrong, and two individually locked calls still do not form an atomic transaction. Explain why each critical section is needed.
  • Immutable in name only. A final field that points to a mutable list, a getter that returns the internal array, a const pointer to non-const data: the reference cannot change, the contents can.
  • Publishing through a plain field. A changing plain reference can remain stale in Java; concurrently replacing and reading an ordinary C++ pointer is a data race. Java can publish through volatile, an atomic reference, a lock or a concurrent collection. C++ needs a suitable atomic or synchronization protocol; C++ volatile does not publish between threads.
  • Two safe calls, one unsafe sequence. containsKey then put on a ConcurrentHashMap is a check-then-act. Use the single atomic call (putIfAbsent, computeIfAbsent, merge).
  • Two safe structures, one invariant. A concurrent map plus an atomic size counter that must agree can disagree between the two updates. One invariant needs one lock, or one owner.
  • Starting at rung 6. Lock-free code without a measured bottleneck and a proof is a liability. Most systems never need it.

In the interview

The "now make it thread-safe" follow up appears after ordinary coding questions at many companies. A 2025 Google L5 report shows the bar: asked to handle a per-user counter map in a multithreaded setting, the candidate listed ConcurrentHashMap, AtomicInteger and synchronized yet got No Hire, and concluded afterwards that the interviewer wanted reasoning about specific races and guarantees, not a list of tools. LinkedIn interviewers have asked candidates to give an example race for each lock they add, and to walk through the interleaving in which two threads both see 99 of 100. An Uber Bangalore interviewer on Blind (2021) complained that candidates "put synchronization everywhere".

Before adding locks, let me classify the state and its invariants. The request buffer stays confined. The config becomes an immutable snapshot published safely. For metrics I can use an adder; an exact quota needs an atomic conditional update. Independent map entries can use a concurrent map operation, or a tested locked wrapper in C++. The LRU order and the map must agree, so those two share one lock. I will explain the race it prevents, then measure where contention remains.

Follow ups to expect: "Which race does this lock prevent?" (name the interleaving). "What if reads dominate?" (a snapshot or a read-write lock). "Where is the contention now?" "Can you remove that lock?" (sharding, an owner thread, or, with evidence, an atomic).

Senior depth

The ownership ideas extend across machines, but the guarantees do not transfer automatically. Partitioning reduces sharing; immutable versions simplify reads; one leader can order a partition's writes. Failover still needs an ownership protocol that prevents stale leaders from writing, such as fencing enforced by the storage layer. Database transactions require the right isolation level. Optimistic transactions and convergent replicated data types are separate concepts, not the distributed meaning of lock-free progress.

Safety and progress are separate. A CAS loop can preserve an invariant while starving one caller. Lock-free means system-wide progress, while wait-free bounds each operation's own steps; neither means no contention or no scheduler delays. In C++, check the atomic type's is_lock_free() and account for allocation, reclamation and callbacks before claiming the whole operation is lock-free. See progress guarantees.

Measure throughput, tail latency and allocations before changing the design. Locks, immutable copying and queue hops all have workload-dependent costs. A short critical section can still wait behind a descheduled holder, so its size is not a wall-clock latency guarantee.

Rung 4 in C++ is thinner than in Java. The C++ standard library has atomics but no concurrent map or queue. "Delegate" in C++ usually means a small class you write once, test under ThreadSanitizer and reuse, or a vetted third-party library, and in an interview it usually means rung 5 behind a clean interface.

Key takeaways

  • The ladder: do not share, share immutably, one owner, delegate, synchronize, lock-free only with evidence.
  • Pick a rung per invariant and all the state it covers, not once for the entire class.
  • Immutable values swapped whole beat careful field by field updates: readers get a snapshot that cannot tear.
  • Concurrent collections protect single calls; invariants across calls or structures need one lock or one owner.
  • In the interview, classify the state first, then name the race each lock prevents.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A pair starts at (0, 1). A writer sets low to 1, then high to 2. Each field uses a Java volatile int or a C++ std::atomic<int> with default ordering. A reader reads low, then high and prints the pair. Which statement is correct?
Why. The writer can set low to 1, the reader can read both fields as 1, then the writer can set high to 2. Atomic individual fields prevent data races here, but do not make the pair an atomic snapshot. Consistent old and new pairs are possible too; neither consistency nor seeing only the old pair is guaranteed, and these operations do not throw. Capture one safely published immutable snapshot, or lock the whole pair.
An owner keeps changing a list and returns a read-only view: Collections.unmodifiableList(items) in Java, or const std::vector<int>& in C++. Is that view a safe snapshot for concurrent readers?
Why. Read-only access through one reference does not stop another reference from mutating the object. In Java this can produce inconsistent observations or ConcurrentModificationException, which is not guaranteed; in C++ concurrent vector mutation and traversal can be a data race. Copy under the owner's lock and publish the copy safely. Java's List.copyOf is shallow, so mutable elements also need attention. Speed is unrelated to this correctness issue.
Which is the simplest rung for a scratch buffer used by one request thread, with no escaping aliases?
Why. The stated absence of escaping aliases makes the buffer confined, so it needs no synchronization. A concurrent buffer, a lock or a dedicated parser thread would add machinery without protecting any actual sharing. Merely declaring a reference local would not suffice if it pointed to shared storage.
A map has individually thread-safe lookup and insert operations. Two threads check that key k is absent, load a value, then insert it. There is no lock covering that sequence. What is true?
Why. Both absence checks can finish before either insertion, so both loaders run and the second insertion can overwrite the first value. The map's own structure remains safe; this sequence need not deadlock. Java's ConcurrentHashMap.computeIfAbsent makes a per-key computation atomic; keep its callback short because other updates may block. A C++ wrapper can provide the equivalent operation under its lock. For slow I/O, publish an in-progress future and load outside the map lock.
A cache uses an individually thread-safe map and atomic size counter. It must keep size equal to the entry count and at most 1,000. For distinct absent keys, each insertion checks size < 1000, increments size, then inserts, using separate operations. What is the problem?
Why. At size 999, both callers can pass the check and then increment to 1,001. Independently, the counter differs from the map between an increment and its insertion. Neither atomic counters nor thread-safe maps combine the operations or supply a capacity policy. Put check, count and insert under one lock, including readers that require a consistent pair, or give them one owner.
C++ onlyA global const Config* current is replaced by a writer while readers do current->limit, with no synchronization or lifetime protocol. What is wrong?
Why. Even an immutable object's pointer is mutable shared state when it is replaced. Hardware-atomic pointer writes on x86 do not repair a C++ data race, and leaking the old object would not fix publication. Synchronize the holder with a mutex or suitable atomic operation. A std::shared_ptr<const Config> snapshot can retain the old object's lifetime, but concurrent access to the same shared-pointer holder still needs synchronization.
Java onlyA Config(int limit) record is fully constructed without escaping and stored in static Config current = new Config(100);. Later a writer replaces this plain, non-volatile field. Readers repeatedly capture the reference and call limit(). What can go wrong?
Why. Proper construction gives this final primitive field initialization safety once a reader obtains the record, but does not ensure that readers discover a later replacement of the plain field. They can retain the old reference. One captured record cannot mix fields from different objects, and no collection iteration is involved. Use volatile or AtomicReference for the changing holder; records with mutable components need additional care.
When is moving from a lock to lock-free code (rung 6) justified?
Why. Performance concerns alone and field count do not establish a benefit. Lock-free algorithms can be correct and useful, so "never" is also wrong. Measure, identify the linearization point, and justify progress and reclamation. A one-word rate limiter is a simpler starting point than a linked structure. A CAS instruction alone does not prove the whole operation lock-free.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
A leaderboard service keeps: a map from player id to score, a sorted top 10 that must always match the scores, a request counter for metrics, a config with the scoring rules, and a per-request JSON builder. Classify each piece onto a rung and justify it, then say where the contention will be.
Model answer

The JSON builder is used inside one request, so it stays local: rung 1, no synchronization. The scoring config is read on every update and changed rarely, so it is an immutable object behind an atomic or volatile reference, replaced whole: rung 2; each request captures one version; decide explicitly whether older in-flight requests may finish under those rules. The request counter is for metrics, so LongAdder in Java or a relaxed atomic in C++ fits rung 4. LongAdder.sum() is not an atomic snapshot during updates and cannot enforce an exact admission limit.

The score map and the top 10 must agree with each other, so the invariant spans two structures. Two options. Rung 5: one lock guards both, and every score update changes the map and adjusts the top 10 under that lock. Or rung 3: a single writer thread owns both and applies updates from a queue, and it publishes an immutable copy of the top 10 after each change. A top-10 reader sees one completed version; an operation requiring scores and top 10 together must use the same snapshot or query the owner. With many concurrent updates the single lock (or the single writer) is the contention point. Sharding by player id and merging shard top tens can reduce contention, but independently sampled shards do not form an exact global snapshot during updates. Preserve the stated consistency requirement with a coordinated snapshot or global ordering, or explicitly relax it. Within one consistent snapshot, every global top-ten player must appear in its shard's top ten, using the same tie-break rule.

Explain
In about ninety seconds, explain the safety ladder to an interviewer and say why you prefer the higher rungs.
Model answer

When I make something thread-safe, I go through the state one piece at a time and use the highest step that fits. First, can it avoid being shared, as locals or per-thread copies? Then, can it be immutable and replaced whole when it changes? Then, can one thread own all the changes while others send it messages? Then, does a proven concurrent structure cover the invariant in one operation, like a concurrent map's merge or an atomic adder? Only then do I use a lock, one per invariant, with the smallest critical section. Lock-free code comes last, only with evidence that its cost is justified and a correctness and progress argument. I prefer the higher steps because they make whole classes of bugs impossible rather than just unlikely: truly confined data cannot race, safely published immutable snapshots stay stable, and owner-confined data has no competing accesses, while every lock I add is something that can deadlock, be forgotten on one path, or become a bottleneck.

Write code
Write a config holder: many threads call get() on every request; an admin calls update(change) that builds a new config from the current one. Concurrent updates must not lose each other's changes. Readers must not wait for the change function to run. Explain whether the implementation also guarantees nonblocking reads.
Model answer

Readers get an immutable snapshot with a volatile-semantics atomic read (Java) or a pointer copy under a short mutex (C++), then inspect it without locks. C++ readers can block on that mutex; even std::atomic<std::shared_ptr<T>> would not guarantee lock freedom. The requirement here is that readers do not acquire the writer lock or wait for the change callback. In Java, updateAndGet applies the change function in a compare-and-set loop, so if two admins update at once, the loser re-applies its change to the winner's result and nothing is lost; the change function must therefore have no side effects, because it may run more than once. In C++ the writers are serialized by their own lock, which keeps the function from running twice, and the new config is built before the short pointer swap. The C++ callback must not call update() recursively because its writer mutex is non-recursive; it may call get(). Both languages require a valid, fully built replacement. A reader may retain an older config for its entire request, so confirm whether that is acceptable, especially for permission revocation. Two atomic reads still would not provide a consistent pair of versions.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"You have a request buffer, a live configuration, some metrics, and an LRU cache. How would you make the service thread-safe?"
What a strong answer covers
  • Classify the invariants before choosing primitives
  • Keep the request buffer confined, including all mutable aliases
  • Publish immutable configuration snapshots safely and capture one per request
  • Use metrics adders only when an exact concurrent snapshot is unnecessary
  • Guard the cache map and recency order with one lock and identify the race
  • Measure remaining contention before changing the design
How a senior would say it
I would choose a policy for each invariant, rather than one policy for the whole service. The request buffer stays with its request thread, and I make sure no callback or shared field exposes it. The configuration becomes an immutable snapshot. I publish replacements safely and capture one version at the start of a request, so related settings agree. If two administrators update it, I serialize their updates or use a retrying compare and set, otherwise one change could overwrite another. For approximate metrics, an adder is suitable. I would not use its live sum for an exact quota. The LRU cache is different: its map and recency list must describe the same entries, so one lock protects both, including lookups that move an entry. Otherwise a lookup can move an entry while eviction removes it. Finally I measure the actual contention. The cache lock, counters, or allocation could dominate. Sharding is an option, but I would state that it changes global LRU into per-shard LRU.

Likely follow up: What changes if every request must use the latest permissions immediately after an admin update completes?

Out loudabout 75 s
"Both fields are atomic, yet readers sometimes see an impossible pair. Why, and what would you change?"
What a strong answer covers
  • Atomic fields do not make a multi-field snapshot atomic
  • Give a concrete interleaving producing an inconsistent pair
  • Choose a lock around the whole invariant or one immutable snapshot
  • Explain safe publication and lifetime in Java and C++
  • Capture the holder once and coordinate read-modify-publish updates
  • Distinguish a short mutex from a nonblocking progress guarantee
How a senior would say it
Atomicity of each field does not give atomicity of the pair. Suppose the pair starts at zero and one. The writer changes the low value to one, the reader reads both fields as one, and only then does the writer change the high value to two. There is no data race on the atomic fields, but the relationship is broken. I can use one lock around both writes and both reads. For read-heavy configuration, I can instead construct an immutable pair and publish one reference to it. The reader captures that reference once. Reading the holder twice could mix versions again. In Java I would use a volatile reference or an atomic reference. In C++ the holder needs synchronization, and shared ownership keeps old snapshots alive. A short mutex around that pointer is correct, but readers can still block. If writers derive a new value from the old one, I also serialize that transformation or retry it with compare and set. Immutability alone does not prevent lost updates.
