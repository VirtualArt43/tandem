Processes and threads: the memory picture

What a process owns, what each thread owns, and why the shared part of memory is where every concurrency bug lives.

Asked atLinkedInMicrosoftRubrikMeta
Before this:Welcome to Tandem

Every concurrency question starts from one picture: which memory is shared and which is private. Get that picture right and you can look at any code and point to the lines where bugs are possible, before you have even worked out what the code does.

In plain words

Think of a joint family living in one house. The kitchen, the fridge and the living room belong to everyone. Each person also has a personal notebook and remembers which step of the recipe they are on. Two people can cook in the same kitchen at the same time, and nothing goes wrong until both reach for the last tomato.

The house is a process. The people in it are its threads. The kitchen is memory that every thread can reach; the notebooks are memory that only one thread can reach. A family in another house has its own kitchen: to share food with them you have to carry it over, which is slower, but it also means nobody next door can ever grab your tomato.

A process: a running program and everything it owns

When you start a program, the operating system creates a process for it. A process owns:

  • an address space: its own range of memory addresses, which the OS maps onto physical memory. By default no other process can read or write it.
  • the program's code, its global and static data, and a heap for objects created while it runs;
  • open files, sockets and other handles, a process id and a current directory;
  • at least one thread. In C++ the first thread runs main. A JVM starts several threads of its own (for garbage collection, the JIT compiler and more) and runs your main on a thread named main.

The OS keeps processes apart on purpose. If one process writes through a bad pointer, it can only damage its own memory. To talk to another process it must use inter-process communication: a pipe, a socket, a shared memory segment that both map, or a file. Isolation is what a process is for.

A thread: one line of execution inside a process

A thread is the thing that actually runs. It is a position in the code plus the values it is working on right now. Each thread has its own:

  • stack: one frame for every method call in progress, holding that call's local variables, its arguments and where to return to;
  • registers, including the program counter (the next instruction to run) and the stack pointer (the top of its stack);
  • a small area of thread-local storage, and its own scheduling state.

Everything else is shared with the other threads of the same process: the code, the globals, the heap and the open files. The operating system schedules threads, not processes. Each core runs one thread at a time (on a CPU with hyperthreading, each hardware thread runs one), so a process with eight threads can keep eight cores busy, and a process with one thread can use only one.

What lives where, in Java and in C++

The picture is the same in both languages. What differs is which syntax puts data in which region.

JavaC++
Shared by all threadsEvery object: anything made with new, arrays, strings, the objects a lambda captures. Static fields.Globals and static variables (function-local statics too). Everything from new, std::make_unique and std::make_shared, and the elements inside containers.
Private to one threadLocal variables and parameters: primitives, and the references themselves.Local variables and parameters (automatic storage), and thread_local variables.
The trapA local reference to an object that another thread can also reach. The reference is private; the object is not.A pointer or reference to a local handed to another thread, or a lambda that captures locals with [&].

The trap row is where most beginners go wrong. In Java, List<String> names = new ArrayList<>(); makes a private variable names that points to a list on the shared heap. The list is safe only while no other thread can reach it. Store it in a field another thread reads, or hand it to another thread, and it is shared from that moment on.

In C++, int count = 0; inside a function is private, until you write std::thread t([&] { count += 1; });. The lambda captures count by reference, so two threads now share one stack variable. Worse, if the thread is detached and the function returns before the thread finishes, the thread writes into a stack frame that no longer exists. (If it is neither detached nor joined, destroying t at the end of the function calls std::terminate.)

See it: one global, two stacks

Two threads run the same function. Each gets a fresh local on its own stack, and both update one shared counter. The C++ version also prints addresses: watch which ones differ.

Each thread's local reaches exactly 1000, because no other thread can see it. The shared counter reaches 2000 only because every increment is atomic; with a plain int you would get the lost update from the races module. In the C++ output, the two &local addresses are far apart (two different stacks, a little over half a megabyte apart on this Mac), while &shared is the same for both threads. In Java you cannot print addresses, but the result is the same: one function, two threads, two separate locals, one shared counter. Notice too that the workers can finish in either order; run it a few times.

Processes versus threads

Both give you concurrency. They trade isolation against the cost of sharing.

fork, exec and wait, and what happens to threads

On Unix systems a new process is born in two steps. Interviewers ask this as theory (a Meta production engineering intern loop asked about fork, exec and wait), and it hides a real threading trap.

  • fork() creates a child process that is a copy of the parent: same code, same data, same open files. It returns twice: 0 in the child, and the child's process id in the parent. The memory is not copied up front; parent and child share pages until one of them writes, and only then is that page copied (copy-on-write, lesson 01-08).
  • exec() (execve and its friends) replaces the program running in the current process with a new one: new code, new data, new heap and stack, same process id. Every other thread in the process is destroyed. Open files stay open unless they were marked close-on-exec.
  • wait() (or waitpid) lets the parent block until a child exits and collect its exit status. Until the parent does, the dead child stays as a zombie (state Z in ps). If the parent exits first, the child becomes an orphan and is adopted by the init process (or a designated subreaper), which reaps it when it exits.

Java has no fork: ProcessBuilder and Runtime.exec start a new program, and the JVM does the fork and exec, or a combined spawn, for you. In C++ you call the POSIX functions yourself, or posix_spawn, which does both steps in one call.

The trap: fork in a multithreaded program. The child gets a copy of the whole address space but only one thread, a copy of the thread that called fork. Every other thread simply does not exist in the child. Any lock those threads held at that instant is copied in the locked state, with no owner left to unlock it, so if the child touches that lock, perhaps inside a logging library or any other code with an internal mutex, it deadlocks forever. (glibc and macOS protect malloc's own locks across fork, but POSIX does not promise that, and most libraries do nothing.) For this reason POSIX allows the child of a multithreaded process to call only async-signal-safe functions until it calls exec. execve is on that list; execlp and execvp, which search PATH, are not, so a threaded program builds its argument array before forking and calls execve in the child. The sample above is single threaded, so its execlp and perror are fine. The rule of thumb: in a threaded program, fork only to exec immediately, or use posix_spawn.

When the main thread ends. Threads have no parent and child relationship for their lifetimes: a thread that started another can finish, and the other keeps running. What ends threads is the process ending. In C++, returning from main calls std::exit, which ends the whole process and every thread in it, and before that, destroying a std::thread that is still joinable calls std::terminate. In Java, when main returns the JVM keeps running as long as any non-daemon thread is alive; when the last one ends, daemon threads are stopped abruptly and the JVM exits. System.exit ends everything at once, after running shutdown hooks. Microsoft has asked exactly this, as "what happens to a child thread when its parent dies?"

Why this picture finds bugs

Every variable in a program falls into one of three groups:

  1. Confined: it lives on one thread's stack and never escapes, or it belongs to an object that only one thread can reach. It needs nothing.
  2. Immutable: other threads can reach it, but it never changes after it was built, like a Java object whose fields are all final and refer only to objects that never change, or a C++ object that is const and fully constructed before any other thread sees it. It needs nothing once it has been published safely (lesson 06-06).
  3. Shared and mutable: two or more threads can reach it and at least one writes it. It needs a lock, an atomic, or a redesign that moves it into one of the first two groups.

Races live only in the third group. That is why the first move with any concurrent code, yours or an interviewer's, is to sort the variables. The smaller the third group, the fewer places a bug can hide.

Worked example: sort every variable

One RequestHandler object is shared by every request thread in a server. Which variables need protection?

VariableGroupWhat it needs

(2) the size limitImmutable: a constantNothing
(3) the server nameImmutable: set once in the constructor, before the handler is sharedNothing (a final or const field)
(4) the handled countShared and mutable: one handler, many threadsAn atomic (AtomicLong or LongAdder, std::atomic<long>)

Two variables out of six need protection. That ratio is typical: most data is safe by construction, and the skill is finding the few variables that are not, quickly and out loud.

Common mistakes

  • "Local variables are always thread-safe." The variable is. The object it points to may be shared. Ask where the object came from and who else holds a reference to it.
  • "Each thread has its own heap." There is one heap per process. Allocators may give each thread its own region to allocate from (Java calls these TLABs), but that is a speed trick: any object can be reached by any thread that gets a reference to it.
  • Thinking static means "one per thread". A static field or a C++ static variable has exactly one copy for the whole process. If threads write it, it is shared and mutable.
  • Capturing locals by reference in a C++ thread. [&] makes the locals shared, and if the thread is detached and the function returns first, the thread uses a dead stack frame. Capture by value, or make sure the thread is joined before the locals go out of scope.
  • "A crash only takes down one thread." In C++ a segfault or an escaping exception ends the process. In Java an uncaught exception ends one thread, but it can leave shared data half updated for every other thread.

In the interview

This comes up as a direct theory question. LinkedIn phone screens in 2025 asked process versus thread, a Microsoft senior loop asked how two processes communicate, and Rubrik candidates report process and memory management concepts inside system coding rounds. It also comes up implicitly every time you are handed concurrent code: the interviewer watches whether you find the shared state before you start fixing things.

A process is the unit of isolation: its own address space and its own file handles. A thread is the unit of execution inside it: its own stack and registers, sharing the heap, the globals and the code with every other thread in the process. So threads communicate cheaply through memory, and that shared memory is exactly where races come from. When I read concurrent code, I first sort every variable into confined, immutable, or shared and mutable, and only the last group needs synchronization.

Follow ups to expect: "Then why not always use processes?" (communication must be copied or explicitly mapped, and creating and switching processes costs more); "When would you choose processes?" (isolation: untrusted code, crash containment, a leaky native library, or a runtime such as CPython, whose global interpreter lock, in its default build, keeps one process from running Python code on several cores at once); "What is thread-local storage?" (a separate copy of a variable for each thread, ThreadLocal in Java and thread_local in C++, which is one way to keep state confined; see confinement and thread-local state).

Senior depth

On Linux, processes and threads are both "tasks" made by one system call, clone (or its newer form, clone3). Its flags decide what the new task shares: with CLONE_VM, CLONE_FS, CLONE_FILES, CLONE_SIGHAND and CLONE_THREAD (plus a few more that pthread_create adds) you get a thread in the same process; without them you get a new process. That is why Linux tools call threads lightweight processes: ps -eLf lists each one with its own LWP id. fork copies the parent's address space lazily (copy-on-write), so pages are duplicated only when one side writes them.

Signals follow the same split. The handlers belong to the process, each thread has its own signal mask, and a signal sent to the process is delivered to any one thread that does not block it. A common pattern is to block signals in every worker and let one dedicated thread wait for them with sigwait.

Switching between two threads of one process keeps the same page tables. Switching to another process changes them; modern CPUs tag TLB entries with an address space id (PCID on x86, ASID on ARM), so the switch no longer throws the whole TLB away, but the incoming process often finds its data pushed out of the caches by the one that ran before. Java maps every platform thread to exactly one OS thread, created when you call start(); virtual threads, in lesson 01-07, break that rule.

Under the hood

"Registers" means the program counter, the stack pointer, the general purpose registers, the flags, the floating point and vector registers, and a register that points at the thread's thread-local storage (fs on x86-64 Linux, TPIDR_EL0 on ARM64 Linux). When the kernel stops a thread to run another, it saves exactly this set and later restores it. That save and restore is the context switch you will meet in lesson 01-04. Each stack ends in a guard page that the program has no permission to read or write, so running off the end of it traps: Java turns that into a StackOverflowError, while C++ simply crashes.

Key takeaways

  • A process owns an address space, files and at least one thread. Processes are isolated and talk through IPC.
  • A thread owns a stack and registers, and shares the code, globals, heap and files with the other threads of its process.
  • Races can only happen in data that is shared and mutable. Sort every variable: confined, immutable, or shared and mutable.
  • A private variable can point to shared data: a local reference in Java, a pointer or a [&] capture in C++.
  • Choose processes for isolation, threads for cheap sharing and parallel work inside one program.
  • fork copies only the calling thread, so a threaded program should fork only to exec at once; when the process ends, every thread ends with it.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "What is the difference between a process and a thread, and when would you pick processes?" Answer as you would out loud, in under a minute.
Model answer

A process is the unit of isolation. It has its own address space, its own open files and at least one thread, and the operating system stops it from touching any other process's memory. A thread is the unit of execution inside a process: it has its own stack and its own registers, and it shares everything else, the heap, the globals, the code and the open files, with the other threads of that process.

That trade-off decides the choice. Threads communicate by reading and writing the same objects, which is fast, and it is also where every race comes from. Processes have to communicate through IPC, which costs copying or explicit shared memory, but a crash or a memory corruption stays inside one process. I pick threads for parallel work and concurrent requests inside one service. I pick processes when I need isolation: running untrusted code, containing crashes or leaks from a native library, giving each tenant a separate failure domain, or working around a runtime such as CPython that, in its default build with the global interpreter lock, cannot run Python code on several cores within one process.

Debug
Many threads call addLine on one shared WordCounter. Sort every variable into confined, immutable, or shared and mutable, then fix the class.
Model answer

Sorting. line is the caller's string, read only here. words (Java), in and word (C++) are locals created per call: confined. SPACES is a compiled Pattern, which is immutable and documented as safe for concurrent use: immutable. counts and linesSeen belong to the one shared object and every call writes them: shared and mutable. Those two need protection; nothing else does.

Fix. The simplest correct fix holds one lock for the whole update, and takes the same lock for every read. The splitting stays outside the lock, because it touches only confined data, which keeps the critical section short.

In Java you could instead use a ConcurrentHashMap with merge and an AtomicInteger, because the two fields have no invariant linking them. One lock is easier to get right first, and it is the version to write before you optimize.

Explain
A worker thread is still running when the main thread finishes. What happens to the worker in Java, and in C++? An interviewer phrases it as "what happens to a child thread when its parent dies?"
Model answer

First, threads have no parent and child relationship for their lifetimes. The thread that started another can end, and the other keeps running; what ends threads is the whole process ending.

Java: when main returns, the JVM does not exit while any non-daemon thread is alive, so a normal worker keeps running and the program ends when the worker finishes. If the worker is a daemon thread, it is stopped abruptly as soon as the last non-daemon thread ends, without running its finally blocks, which is why daemon threads must not own work that has to complete. System.exit ends everything at once, after shutdown hooks.

C++: returning from main calls std::exit, which ends the process and kills every thread in it. Before that, if the std::thread object for the worker is destroyed while still joinable, std::terminate aborts the program. So the correct code joins the worker before main returns (or uses std::jthread, which joins in its destructor). A detached thread is simply killed when the process exits, mid-work. Calling pthread_exit from main would end only the main thread and let the process live until the last thread finishes, but that is rare in C++ code.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"A junior engineer on your team says local variables are always thread-safe. Are they? How would you explain it to them?"
What a strong answer covers
  • The variable itself is private: every call gets its own copy on the stack of the thread that made the call
  • A local is often a reference or pointer, and the object it points to lives on the shared heap
  • The object becomes shared the moment it escapes: stored in a field, handed to another thread, captured by a task
  • In C++ a [&] capture or a pointer to a local shares the stack slot itself, and it dangles if a detached thread outlives the function
  • The real question is who else can reach the object; then keep it confined, make it immutable, or synchronize it
How a senior would say it
Partly. The variable itself is always private. Every call gets its own copy on the stack of the thread that made the call, so an int counter inside a method can never race. But a local is often a reference, and the object it points to lives on the heap, which every thread can reach. A local list is safe only until it escapes. The moment I store it in a field, hand it to an executor, or capture it in a task that runs elsewhere, two threads can touch the same list. C++ has a sharper version. If I start a thread with a lambda that captures by reference, the stack slot itself is shared, and if that thread is detached and the function returns, it writes into a dead frame. So the question I teach is not whether it is local. It is who else can reach this object. If nobody can, it is confined and needs nothing. Otherwise it must be immutable, or guarded by a lock or an atomic.

Likely follow up: Then is an object held in a final field safe to share between threads?

Out loudabout 90 s
"A third party native library you call to resize images segfaults about once a week, and every time it does, your whole service goes down with every request in flight. What would you change?"
What a strong answer covers
  • A segfault in any thread kills the whole process, because all threads share one address space
  • Catching it inside the process does not work: it is a signal in C++, and a native crash takes the whole JVM down in Java
  • The fix is a process boundary: run the library in a pool of separate worker processes
  • The service talks to the workers over IPC, a pipe or a local socket, with shared memory for large images
  • A supervisor restarts dead workers, only the request on that worker fails and can be retried, and every job gets a timeout
  • The cost is memory per worker and a copy or mapping per request, paid for crash containment
How a senior would say it
I would move the library out of the service's process. All threads share one address space, so a segfault in any thread, even deep inside a native call, kills the whole process and every request with it. I cannot catch my way out of it: in C++ it is a signal, not an exception, and in Java a crash in native code takes the whole JVM down. Only a process boundary contains it. So I would run a small pool of worker processes that do nothing but resize images. The service sends each job over a pipe or a local socket, and for large images it puts the bytes in a shared memory segment and sends only a handle. A supervisor restarts any worker that dies, and only the one request that was on it fails, so it can be retried. Every job also gets a timeout, because a native bug can hang as easily as it can crash. The price is extra memory per worker and a copy or a mapping per request, which is small next to resizing an image. It is the same reason browsers put sites in separate processes.

Out loudabout 90 s
"Your multithreaded C++ server forks a child to run a helper tool. Once in a while the child hangs forever before the helper ever starts. What is going on, and how do you fix it?"
What a strong answer covers
  • fork copies the whole address space but only the thread that called it
  • A lock that another thread held at that instant is copied in the locked state, with no owner left to release it
  • If the child calls code that takes that lock before exec, a logging call for example, it blocks forever; that is why it is intermittent
  • POSIX allows only async-signal-safe calls between fork and exec in a threaded program
  • The fix: prepare everything before forking and call execve straight away in the child, or use posix_spawn
How a senior would say it
This is the classic fork in a threaded program bug. fork copies the whole address space, but only the thread that called it. Every other thread simply does not exist in the child. Now suppose a logging thread held the logger's mutex at the instant of the fork. The child gets a copy of that mutex in the locked state, and the thread that would unlock it is gone. If the child logs anything before it calls exec, it waits on that lock forever. It is intermittent because it only happens when the fork lands while some other thread holds a lock. That is why POSIX says the child of a multithreaded process may only call async-signal-safe functions until it execs. So the fix is to do all the work before forking. Build the argument array and the environment first, then in the child call execve at once, with nothing in between except closing or redirecting file descriptors. Better still, use posix_spawn, which does both steps in one call, with only safe code inside the C library in between.
