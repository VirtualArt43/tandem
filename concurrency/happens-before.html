Happens-before and synchronizes-with

The one rule that decides what a thread must see: happens-before edges in Java and C++, data races, and why race-free code is easy to reason about.

Asked atDatabricksApple
Before this:Visibility: why a thread may never see your writeReordering by the compiler and the CPU

The last two lessons showed writes that are never seen and writes seen in the wrong order. Happens-before is the rule that turns that chaos back into something you can reason about: if you can draw a happens-before path from a write to a read, the read is guaranteed to see that write, or a later one. If you cannot, there is no guarantee at all.

In plain words

Think of a hospital shift change. The outgoing nurse writes notes all night, then signs the handover sheet. The incoming nurse reads the handover sheet, then reads the notes. Everything written before the handover is guaranteed to be seen by the next nurse after the handover. A note scribbled after signing the sheet has no such guarantee, and neither does a note read before reading the sheet, even if it was physically written hours earlier.

In code, the handover is a synchronization action: releasing and acquiring a lock, writing and reading a volatile or atomic variable, starting or joining a thread. The notes are your ordinary variables. Happens-before is just the chain of "written before a handover, read after it" links, and the clock on the wall has nothing to do with it.

The definition

happens-before is a relation between actions in a program (reads, writes, locks, unlocks). It is built from three ingredients:

  1. Program order. Inside one thread, each action happens-before every later action of that thread. (C++ calls the single-thread part sequenced-before.)
  2. Synchronizes-with. Certain pairs of actions in different threads are linked: an unlock and a later lock of the same lock, a write to a volatile or atomic variable and a read of that variable that sees the write, starting a thread and the thread's first action. The first action of the pair is a release, the second an acquire. This is the synchronizes-with edge.
  3. Transitivity. If A happens-before B and B happens-before C, then A happens-before C. So chains can cross any number of threads.

The guarantee: if a write happens-before a read of the same variable, and no other write gets in between, the read sees that write. Equally important is what happens-before is not. It is not "happened earlier in time". Two actions can run a second apart on the wall clock and still have no happens-before relation, and then the language promises nothing about what the later one sees.

Timing is not happens-before

The most common wrong mental model is "the write ran first, so the reader sees it". Here the writer even gets a 100 ms head start. The program will almost certainly print 42, and it is still broken, because nothing connects the write to the read.

Look carefully at why there is no edge. Starting a thread does create one, but only for writes made before start() (or before the std::thread constructor). data = 42 comes after it. A sleep is not a synchronization action. So the write and the read are a data race. ThreadSanitizer reports it on every run, and it even adds the note "As if synchronized via sleep", because it knows exactly this mistake. Move data = 42 above the line that starts the thread and the race disappears.

Java's happens-before rules

The Java Language Specification (chapter 17, the Java memory model) lists the edges. Learn them as a table; interviewers ask for it.

RuleWhat happens-before what
Program orderEach action in a thread, before every later action in the same thread
Monitor lockAn unlock of a monitor (end of a synchronized block), before every later lock of the same monitor
Volatile variableA write to a volatile field, before every later read of that field (that sees it or a later write)

TransitivityA before B and B before C gives A before C

The java.util.concurrent documentation adds the edges every library hand-off gives you, under "Memory Consistency Properties":

  • Executors and futures: actions before submit() or execute(), before the task starts. Actions in the task, before another thread returns from Future.get(). A CompletableFuture is a Future, so the same holds for its get().
  • Concurrent collections: actions before putting an object into a ConcurrentHashMap, BlockingQueue, CopyOnWriteArrayList and the rest, before actions after another thread reads or removes it.
  • Synchronizers: actions before a "release" (Lock.unlock, Semaphore.release, CountDownLatch.countDown), before actions after a successful "acquire" (Lock.lock, Semaphore.acquire, Condition.await returning, CountDownLatch.await) on the same object. Barriers and Exchanger give the same for each party.

Notice that wait and notify are not in the table. They add no edge of their own: wait releases the monitor and re-acquires it before it returns, so the edge a waiting thread gets comes from the notifier's unlock to that re-acquire. That is one more reason to change the condition only while holding the lock.

One more guarantee is not an edge but matters just as much: final fields. A thread that sees a reference to a properly constructed object sees its final fields initialized, even without an edge. That is the subject of safe publication.

C++: sequenced-before, synchronizes-with, happens-before

C++ builds the same relation with more precise names, because it also has to describe its weaker atomic orders:

  • Sequenced-before is the single-thread order: in a = 1; b = 2; the first full expression is sequenced before the second. (Within one expression the rules are subtler: in i++ + i++ the two increments are unsequenced, which is undefined behavior even in one thread.)
  • Synchronizes-with links threads: a release operation on an atomic M synchronizes with an acquire operation on M that reads the value it wrote. A seq_cst store and load count as release and acquire.
  • Inter-thread happens-before is a chain that crosses threads: A synchronizes with B, or A is sequenced before X and X inter-thread happens before B, and so on. In short, any path made of sequenced-before steps and at least one synchronizes-with step.
  • Happens-before is sequenced-before or inter-thread happens-before.

A condition variable has no edge of its own: its waits and notifies are ordered through the mutex they use. And notice what is missing from the table: std::this_thread::sleep_for, std::this_thread::yield, volatile, and a relaxed atomic load. None of them synchronize with anything on their own. (A relaxed operation can take part in synchronization when it is paired with a fence; that is in memory orders.)

Data races, and why race-free programs are simple

Both languages define a data race the same way: two accesses to the same memory location, from different threads, at least one of them a write, that are not ordered by happens-before. In Java the accesses are to a plain (non-volatile) field. In C++ at least one of them is non-atomic; atomic accesses never race with each other, whatever their memory order.

The payoff is the most useful theorem in concurrency, often called DRF-SC: if a program has no data races, it behaves as if it were sequentially consistent, that is, as if the threads' operations were simply interleaved, each thread in program order. All the store buffers, hoisting and reordering from the last two lessons become invisible. You can reason with interleavings again.

  • Java (JLS 17.4.5): a correctly synchronized program, one whose sequentially consistent executions have no data races, has only sequentially consistent executions. A program with races still has defined behavior, just weak: a racy read returns some value written to that variable, possibly a stale one (for a non-volatile long or double, possibly a torn mix of two writes), and the memory model's causality rules forbid values appearing out of thin air.
  • C++: a program with a data race has undefined behavior, full stop. A race-free program that uses only mutexes and seq_cst atomics is sequentially consistent. Using acquire, release or relaxed orders keeps the program race free but gives up part of the sequential consistency, deliberately, which is why those orders get their own lesson.

So the working method is: never race, and you never have to think about the hardware. Every shared read must be connected to the write it needs by a chain of edges.

A method for proving code correct

  1. List the shared variables: fields, statics, and objects reachable from them. Locals are not shared, unless their address escapes or, in C++, a lambda run on another thread captures them by reference.
  2. For each read of shared state, ask which write it must see.
  3. Find a chain from that write to that read: program order to a release, a synchronizes-with edge, program order from the acquire. Name each link out loud.
  4. If any shared read has no chain from a conflicting write, you have found a data race. Fix the code; do not argue about whether the hardware will "probably" make it visible.

Worked example: why the bounded buffer publishes the items

A producer builds an object and puts it into the buffer from the producer and consumer lesson; a consumer takes it and reads its fields. The object's fields are plain and not final. Why does the consumer see them filled in?

  1. The producer writes the fields, then calls put. Program order: field writes happen-before the producer's unlock at the end of put.
  2. The consumer's take locks the same lock after that unlock (it found the item, so it ran after put released the lock). Monitor lock rule: the producer's unlock happens-before the consumer's lock.
  3. The consumer reads the fields after take returns. Program order: its lock happens-before its field reads.
  4. Transitivity: the field writes happen-before the field reads. No race, and the consumer sees the fields.

The same argument covers every BlockingQueue in Java (the documented collection edge) and every mutex-guarded queue in C++. It also shows the rule that keeps it safe: the producer must not touch the object after putting it. A field write after put has no edge to the consumer and is a race.

Common mistakes

  • Treating happens-before as time. "It ran a second ago" is not an edge. Only synchronization actions create edges.
  • Edges on different objects. Unlocking lock A and then locking lock B connects nothing. A volatile write to x and a volatile read of y connect nothing.
  • Wrong order around the edge. The writer must write the data before the release (the unlock, the volatile write); the reader must read the data after the acquire. Data written after the release, or read before the acquire, is unprotected.
  • A timed join that timed out. t.join(1000) that returns because time ran out while t is still running gives no edge. Check isAlive() before trusting anything t wrote.
  • Sleep, yield, or volatile in C++. None of these synchronize. They may make a race rarer; they never remove it.
  • Trusting a debug print. System.out.println takes a lock inside the stream, so a print in both threads can add an accidental edge (and changes the timing too). The bug seems fixed, then comes back when the print is removed. Find the missing edge instead.
  • Touching an object after handing it off. Once it is in the queue, in the map or submitted to the executor, the producer must treat it as read-only, or guard every later access.

In the interview

Happens-before is the vocabulary interviewers expect for any visibility or ordering question. A Databricks-tagged commenter on Blind told a staff candidate to expect the Java memory model, happens-before and volatile in the concurrency round, and a recruiter listed the memory model among the topics of an Apple hiring manager phone screen in 2026. The question might be "what does volatile guarantee?", "why is this thread-safe?", or "what can this print?"; the answer always goes through edges.

I do not reason about caches or reordering directly; I reason with happens-before. A read is guaranteed to see a write only if there is a chain of happens-before edges from the write to the read: program order inside each thread, plus synchronization edges between threads, like unlock to lock on the same lock, a volatile write to a read that sees it, thread start and join, or a hand-off through an executor or a concurrent collection. If two conflicting accesses have no such chain, that is a data race, and I fix the code. If there are no data races, the program behaves sequentially consistently, so ordinary interleaving reasoning is valid.

Follow ups to expect:

  • "List the happens-before rules." Program order, monitor lock, volatile, thread start, thread termination and join, interruption, transitivity, plus the java.util.concurrent hand-offs.
  • "Is Thread.sleep a synchronization point?" No; the JLS says so explicitly.
  • "Do wait and notify create happens-before?" Not by themselves. The edge comes from the monitor: the notifier's unlock, then the waiter's re-acquire inside wait. In C++ the same holds for a condition variable and its mutex.
  • "If I put an object into a ConcurrentHashMap, does another thread that gets it see the object's fields?" Yes, the fields written before the put; that is a documented edge.
  • "What is a data race, and what happens in Java versus C++?" Defined but weak behavior in Java; undefined behavior in C++.
  • "Does happens-before mean the first action ran earlier?" No. It is a guarantee about visibility and ordering, not a timestamp; the JIT may even run the two actions in the other order if no thread can tell.

Senior depth

The machinery behind the Java rules. All synchronization actions (volatile reads and writes, locks and unlocks, thread start and join) form a single total order, the synchronization order, consistent with each thread's program order. Synchronizes-with edges are defined over it ("a volatile write synchronizes with every subsequent read in the synchronization order"). That total order is why Java volatile accesses behave like C++ seq_cst. Happens-before consistency alone would allow a racy program to read values that appear out of thin air (a value justified only by itself in a cycle), so the JMM adds causality requirements to forbid that.

Release sequences. In C++, an acquire load that reads a value written by a read-modify-write that came after the release still synchronizes with the release: RMWs extend the release sequence. That is why a reference count decremented by many threads with fetch_sub works. C++20 narrowed release sequences to RMWs only; plain stores by the releasing thread no longer extend them.

Strongly happens-before. The C++20 revision of the memory model (paper P0668) defines two more relations, "simply happens before" and "strongly happens before", to fix a subtle hole in how seq_cst operations interact with weaker ones. You will not be asked to define them, but knowing that the C++ model was repaired as late as C++20 is a good reason to stick to mutexes, seq_cst, and textbook acquire and release patterns.

ThreadSanitizer is a happens-before detector. It keeps a vector clock per thread and per synchronization object, joins clocks at every acquire, and reports a race when two conflicting accesses are not ordered by those clocks. That is the definition from this lesson, implemented. It is also why it reports races that "cannot happen" because of a sleep.

Key takeaways

  • Happens-before is built from program order, synchronizes-with edges between threads, and transitivity.
  • If a write happens-before a read, the read sees it or a later write. Time order is irrelevant; sleeps and yields create no edges.
  • Edges come from locks, volatile or atomic variables, thread start and join, and library hand-offs such as executors, futures and concurrent collections.
  • A data race is two conflicting accesses with no happens-before order. Java gives racy reads weak but defined values; in C++ a race is undefined behavior.
  • Data race free programs are sequentially consistent, so eliminating races is how you get back to simple reasoning.

ready is volatile (Java) or a seq_cst std::atomic<bool> (C++); data is plain. Thread A runs data = 42; ready = true;. Thread B runs if (ready) print(data);. What can B print?
Why. If B reads ready as true, A's volatile or atomic write synchronizes with that read, and data = 42 comes before the write in A's program order, so it happens-before B's read of data. If B reads ready before A writes it, B prints nothing. 0 would need a missing edge.
Now data is volatile (or atomic) and ready is plain. A runs data = 42; ready = true;. B runs if (ready) print(data);. What can B print?
Why. The edge must run through the flag, because the flag is what B checks first. With a plain ready, B's read of it has no edge from A's write, so B can see ready == true and still read the old data (and in C++ the race on ready is undefined behavior).
A worker thread writes a result into a plain field. Which of these guarantee that main then sees the result? Select all that apply.Select all that apply
Why. Join, a blocking queue hand-off and a release-acquire flag all create happens-before edges from the worker's write to main's read. A sleep creates none, and locks only connect an unlock and a lock of the same lock.
A worker writes result = 7 and then keeps running for a long time. main waits for it with a timeout (t.join(100) in Java, future.wait_for(100ms) in C++), the wait returns because the time ran out, and main reads result. What is guaranteed?
Why. The edge goes from the worker's actions to a thread that detects it has finished: join() returning because the thread ended, isAlive() returning false, or a future becoming ready. A timeout detects nothing, so the read races with the write and may see 0 or 7 (in C++ it is undefined behavior).
Thread A writes x = 1 (a plain variable), then releases lock L. After that, thread B acquires L and writes a volatile (or seq_cst atomic) v = true. Thread C reads v, and if it is true, prints x. What can C print?
Why. Transitivity: A's write is before A's unlock; the unlock synchronizes with B's later lock of L; B's lock is before B's write of v; that write synchronizes with C's read that sees true. So x = 1 happens-before C's read of x, and C does not need lock L itself. If B had taken L before A, there would be no edge from A, and 0 would be possible.
Which of these is a data race?
Why. A data race needs conflicting accesses (at least one write) to a plain location that are not ordered by happens-before. Concurrent reads do not conflict, atomic accesses never form a data race (though the logic can still be a race condition), and the same lock orders the writes.
Java onlyWhich statement is guaranteed by the java.util.concurrent memory consistency rules?
Why. Actions before submission happen-before the task begins, and the task's actions happen-before get() returns in another thread. Writes made after submit() are unordered with the task. isDone() is not one of the documented edges (an implementation may happen to publish through it, but the contract does not promise it), so use get() (or join() on a CompletableFuture) before reading results.
C++ onlyIn C++, which pair creates a synchronizes-with edge from thread A to thread B?
Why. Synchronizes-with needs a release on the writing side and an acquire on the reading side, on the same atomic, with the load reading the stored value (seq_cst counts as both). A relaxed operation on either side breaks the pair, and C++ volatile is not synchronization at all.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "Define happens-before and a data race, and tell me why I should care about the difference between a racy and a race-free program." Answer as you would out loud, for your language.
Model answer

Happens-before is a partial order on a program's actions that decides visibility. It is built from program order within each thread, synchronizes-with edges between threads, and transitivity. Synchronizes-with edges come from synchronization: an unlock and a later lock of the same lock, a volatile or release write and a read that sees it, starting a thread and its first action, a thread's last action and a successful join, and the library hand-offs such as executors, futures and concurrent collections. If a write happens-before a read of the same variable, the read sees that write or a later one. It is not about time; a sleep creates no edge.

A data race is two accesses to the same location from different threads, at least one a write, with no happens-before order between them; in C++, at least one of them is non-atomic. Why it matters: a data race free program is sequentially consistent, so I can reason about it as an interleaving of the threads' operations. A racy program loses that. In Java a racy read returns some value written to that variable, possibly stale, but nothing more exotic. In C++ a data race is undefined behavior, so the compiler can make the program do anything. So my rule is simple: for every shared read I can name the edge chain from the write it needs, or I add synchronization.

Debug
This program computes statistics in a background thread and prints them. It "always works" in testing. Find the problem and fix it in your language without adding a sleep.
Model answer

The worker's writes and main's reads have no happens-before relation: the only thing between them is a sleep, which is not a synchronization action. It is a data race. In Java, main may print stale values (0 and 0.0) or even a mix; total is a non-volatile long, which the specification even allows to be torn. In C++ it is undefined behavior, ThreadSanitizer reports it, and the detached thread may still be running when main reads. "Always works in testing" only means the race is rare.

The fix is to replace the sleep with an edge. The simplest is to join the worker, which also removes the arbitrary 500 ms wait:

A cleaner design returns the result instead of sharing statics: a Future from an executor or a CompletableFuture in Java, std::async with future.get() in C++. The hand-off then carries both the value and the edge.

Pseudo code
A producer creates an Order object with plain (non-final) fields, sets them, and puts it into a ConcurrentHashMap (or a mutex-guarded std::unordered_map) under key 7. Later a consumer gets key 7 and reads the fields. Write out the happens-before chain that guarantees the consumer sees the field values, and say what would break it.
Model answer
  1. Producer: the field writes are in program order before the put (C++: before the unlock at the end of the guarded insert).
  2. The put is a release: in Java the documented collection edge says actions before placing an object in a concurrent collection happen-before actions after another thread retrieves it; in C++ the producer's unlock synchronizes with the consumer's later lock of the same mutex.
  3. Consumer: the get (C++: the lock and the lookup) is in program order before the reads of the fields.
  4. Transitivity: field writes happen-before field reads, so the consumer sees them.

What breaks it: the producer modifying the object after the put (those writes have no edge to the consumer); the consumer reading the map without the lock in C++, or through a plain HashMap in Java; or the consumer caching the reference and reading fields that the producer changes later. The rule is: hand it off, then treat it as read-only, or make the object immutable.

"Thread A writes a config object and then releases a lock. Thread B takes the same lock and then sets a volatile flag. Thread C never touches the lock: it waits until it sees the flag set, then reads the config. Is C guaranteed to see A's config? Walk me through it."
What a strong answer covers
  • Yes, as long as B took the lock after A released it
  • In A, the config write comes before the unlock in program order
  • A's unlock synchronizes with B's later lock of the same lock, and B's lock comes before its flag write
  • B's flag write synchronizes with C's read that sees it, and C reads the config after that
  • Transitivity joins the links into one chain, so C needs no lock of its own
  • What breaks the chain: B locking first, a plain flag, a relaxed flag in C++, or A changing the config after its unlock
How a senior would say it
Yes, as long as B took the lock after A released it, and I can show it by naming each link. In thread A, the config write comes before the unlock in program order. A's unlock synchronizes with B's later lock of the same lock. In thread B, the lock comes before the flag write. The flag is volatile in Java, or an atomic with a release or sequentially consistent store in C++, so that write synchronizes with C's read when C sees the flag set. And in thread C, the config read comes after the flag read. Happens-before is transitive, so A's config write happens before C's read, and C sees it, even though C never took the lock. The chain is fragile in specific ways. If B took the lock before A, there is no edge from A at all. If the flag is a plain field, or a relaxed atomic in C++, the middle link is gone and it is a data race. And writes A makes after its unlock are not covered. So I say each link out loud, and if I cannot name one, I add synchronization instead of arguing about timing.

"A teammate reads a result from a background thread after sleeping for 500 milliseconds. The test has passed a thousand times in a row, and they say half a second is plenty. What do you tell them?"
What a strong answer covers
  • Time order is not happens-before: a sleep has no synchronization semantics, so there is no edge from the write to the read
  • So it is a data race: Java may return a stale value (or a torn long), and in C++ it is undefined behavior
  • A thousand passes only shows the race is rare; ThreadSanitizer reports it on every run, even when the output is right
  • Fix: replace the sleep with a real edge, such as a join, a future, a queue or a latch
  • Best design: return the result through a future, so the hand-off carries the value and the edge together
How a senior would say it
I would tell them the sleep is not what makes it work. Happens-before is not about time. A sleep has no synchronization semantics, and the Java specification says so explicitly, so there is no edge from the worker's write to the reader's read. That makes it a data race. In Java the reader may see a stale value, or even half of a 64 bit long. In C++ it is undefined behavior, so the compiler may assume no other thread changes the variable. A thousand passes only tells me the race is rare on this machine today. ThreadSanitizer would report it on every run, even when the printed value is right, because it checks for the edge, not the outcome. The fix is to replace the sleep with a real edge. If the reader needs the worker to be finished, join it. Better still, have the worker return its result through a future, so get hands over the value and the happens-before edge together, and nobody has to guess how long is long enough.

Out loudabout 90 s
"In Java a program with a data race still has defined behavior. In C++ it is undefined. Why did the two languages choose differently, and does it change how you write code?"
What a strong answer covers
  • Java bounds the damage: a racy read returns some value written to that variable (or a torn long or double), never a value out of thin air
  • The reason: Java promises memory safety and type safety even for buggy or untrusted code
  • C++ makes a race undefined so the optimizer can treat plain variables as if no other thread could see them
  • Both give the same reward for race-free code: it behaves sequentially consistently (in C++, with locks and seq_cst atomics)
  • In practice the discipline is the same, no data races; in C++ a race can break code far from the variable, so run ThreadSanitizer
How a senior would say it
The discipline is the same in both: write race-free code. The difference is how much a mistake can hurt. Java promises that even a racy program has defined behavior. A racy read returns some value that was written to that variable, maybe a stale one, or for a non volatile long or double a torn mix of two writes, but never a value out of thin air. Java needs that because it promises memory safety and type safety even to buggy or untrusted code; a thread must never conjure up a reference to an object nobody gave it. C++ chose freedom for the optimizer. A data race is undefined behavior, so the compiler may treat plain variables as if no other thread can see them, keep them in registers, and merge or reorder accesses. Both languages then give the same reward for race-free code: it behaves sequentially consistently, as long as the C++ code sticks to locks and sequentially consistent atomics. So in Java a race is a bug with bounded damage. In C++ a race can break code far away from the variable, which is why I run the tests under ThreadSanitizer.
