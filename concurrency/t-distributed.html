Two users try to book the last seat at the same moment. How do you guarantee that only one succeeds?
Model answer

It is check-then-act across processes. A lock inside one application server stops working the moment you run two servers, so make the database the arbiter, with one atomic statement:

One row affected means you got the seat; zero means someone else did. The database applies the check and the write together under its row lock. Equivalent tools: a unique constraint on (event_id, seat_id) in a bookings table, so the second insert fails; a short SELECT ... FOR UPDATE inside a transaction; or an optimistic version check.

Real flows add think time, because the user pays after choosing. Use a hold with an expiry: the same conditional update sets status = 'HELD' and hold_expires_at, a later conditional update confirms only if the hold is still yours and unexpired, and an expired hold counts as available. Never keep a row lock open through checkout. Hot events add a virtual waiting room in front, and the payment step needs an idempotency key so a retry cannot charge twice.

Likely follow up: "Could you do the hold in Redis?" Yes: SET seat:42 <user> NX PX 600000 makes a ten-minute hold. The final confirmation should still be a conditional write in the database, which stays the source of truth.

2CoreoptimisticpessimisticMetaRipplingMicrosoft
Optimistic versus pessimistic concurrency control: how does each work, and when does each win?
Model answer

Pessimistic: lock before you read what you will change (SELECT ... FOR UPDATE, a mutex), so others wait. It wins when conflicts are common, when a retry is expensive (long transactions, external side effects), or when you must not do the work twice. It costs blocking, possible deadlocks (so order the locks and use timeouts) and lower concurrency, and it is a disaster if a lock is held across user think time.

Optimistic: read the data with its version, compute, then write with WHERE version = :v. If no row matched, someone else changed it, so re-read and retry or report a conflict. HTTP does the same with ETags and If-Match, and memory does it with compare-and-swap. It wins when conflicts are rare, operations are short and reads dominate, and it works across user think time because nothing is held. Under heavy contention it degrades into wasted work and retry storms, and long transactions can starve.

A practical third option for counters and inventory is the guarded atomic update: UPDATE rooms SET booked = booked + 1 WHERE id = ? AND booked < capacity. There is no read-modify-write in the application, so no lost update and no retry loop. The database serializes the writers on the row.

Likely follow up: "Your optimistic update keeps failing under a flash sale." Contention is high, so switch to the guarded update, a queue that serializes requests per item, or split the inventory across several rows.

3Seniorisolationlost-updatedatabases
Which isolation levels prevent a lost update, and do PostgreSQL and MySQL agree?
Model answer

A lost update in a database: two transactions read stock 10, both compute 9, both write 9. One sale vanished.

  • Read committed (PostgreSQL's default) allows it.
  • PostgreSQL repeatable read is snapshot isolation with first-updater-wins: the second transaction to update the row fails with a serialization error, and the application must retry. Prevented.
  • MySQL InnoDB repeatable read (MySQL's default) does not prevent it for a plain read then write. The SELECT reads from the snapshot, but the UPDATE acts on the latest committed row, and there is no conflict check.
  • Serializable prevents it in both.

So do not rely on the isolation level. The fixes that work everywhere: do the arithmetic in the database (UPDATE stock SET qty = qty - 1 WHERE sku = ? AND qty > 0), lock the row while reading it (SELECT ... FOR UPDATE), or add a version column and make the write conditional on it.

These behaviors are documented in the PostgreSQL and MySQL manuals, and the Hermitage test suite demonstrates them for each database. They are worth quoting precisely, because interviewers who know databases will test the difference.

Likely follow up: "Why would PostgreSQL's repeatable read make your code more complex?" Because serialization failures become a normal outcome: every transaction needs a retry loop with a limit.

4Seniorwrite-skewisolationbookingRippling
What is write skew? Give an example and the fixes.
Model answer

write skew: two transactions read overlapping data, each checks a condition, and each writes a different row. Each transaction alone preserves the invariant; together they break it.

  • Doctors on call: the invariant is that at least one doctor is on call. Alice and Bob both see "two on call" and each takes themselves off. Zero remain.
  • Hotel booking: each transaction checks that the room is free on every night of its stay, then inserts its own booking row. Two overlapping bookings are inserted, and the room is double booked.

Snapshot isolation does not prevent it, because the two transactions write different rows, so there is no write-write conflict to detect. That includes PostgreSQL's and MySQL's repeatable read.

Fixes:

  • Serializable isolation. PostgreSQL's serializable snapshot isolation detects the dangerous pattern and aborts one transaction, which must retry.
  • Lock what you read: SELECT ... FOR UPDATE on each night's inventory row, always in date order so two bookings cannot deadlock.
  • Materialize the conflict: keep one inventory row per room type per night, and have every booking decrement those rows with a guarded update. Overlapping bookings now touch the same rows, which turns write skew into an ordinary write-write conflict.
  • A constraint: a PostgreSQL exclusion constraint on the date range per room, or a unique constraint.

Likely follow up: "Which would you ship for a hotel system?" Per-night inventory rows with guarded decrements in one transaction: simple, fast and correct at any isolation level, and they also handle room types with many identical rooms.

  • Dirty read: you see another transaction's uncommitted write.
  • Non-repeatable read: you read a row twice and get different values.
  • Phantom: you rerun a range query and new rows appear.

Real databases differ from the table. PostgreSQL treats read uncommitted as read committed, and its repeatable read is snapshot isolation, so phantoms do not appear to your reads. MySQL InnoDB's repeatable read uses a snapshot for plain reads, and next-key locks for locking reads. Read committed is the default in PostgreSQL, Oracle and SQL Server; repeatable read is MySQL's default.

The table also omits two anomalies interviewers care about most, lost update and write skew. Snapshot isolation is not an ANSI level at all: it prevents the three read anomalies but allows write skew. Only serializable rules out every anomaly, at the cost of retries or blocking.

Likely follow up: "Which level would you run a booking service at?" Read committed, with the critical write made safe explicitly (a guarded update, a row lock or a constraint), or serializable with a retry loop if many invariants span rows.

6CoreidempotencyretriesStripeRipplingCoinbaseSalesforce
Design idempotency keys end to end for a payment API.
Model answer

The client generates a unique idempotency key per logical operation (a UUID) and sends it with the first attempt and every retry. The server enforces "at most one effect per key":

  1. Insert a row (key, request_hash, status = IN_PROGRESS) under a unique constraint, ideally in the same transaction as the effect.
  2. If the insert succeeds, do the work, store the response, set COMPLETED, and return the response.
  3. If the key already exists and is COMPLETED with the same request hash, return the stored response: no second charge.
  4. If it exists with a different request hash, the client reused a key for a different request: reject it.
  5. If it is IN_PROGRESS, a duplicate is running concurrently: answer "conflict, retry later", or wait for it.

Keep keys for a retention window longer than any client's retry horizon, such as a day. Pass a derived key to downstream systems such as the payment processor, so their effects are idempotent too.

The subtle case is a crash between steps 1 and 2, which leaves the key IN_PROGRESS forever. Give the marker an expiring lease so a retry can take over, or, when the effect is a row in your own database, commit it in the same transaction as the key record.

Likely follow up: "Why not let the server generate the key?" The server cannot tell a retry from a new request; only the client knows that two attempts are the same logical operation.

7Seniorexactly-oncedeliverydeduplicationMetaLinkedIn
Can you get exactly-once delivery? What do systems mean when they claim exactly-once?
Model answer

Over an unreliable network, delivery is either at-most-once (send once and maybe lose it) or at-least-once (retry until acknowledged and maybe duplicate). When an acknowledgement is lost, the sender cannot know whether the message or the acknowledgement was lost. So exactly-once delivery is impossible in general.

What systems achieve is exactly-once effect: at-least-once delivery plus processing that ignores duplicates. Either the effect is naturally idempotent (set a value rather than add to it), or the consumer records each message id atomically with the effect and skips ids it has seen.

Kafka's exactly-once semantics combine an idempotent producer (a producer id plus per-partition sequence numbers, so the broker drops duplicate appends) with transactions that atomically write output records and commit consumer offsets. That covers read-process-write inside Kafka. Side effects outside Kafka, such as a database write or an email, still need their own idempotency.

Choose per use case: live comments can be at-most-once, notifications can be deduplicated by event id in a cache with a TTL, and payments need exactly-once effect.

Likely follow up: "Where do you keep the processed ids, and for how long?" In the same store and the same transaction as the effect, for longer than the maximum redelivery window. A separate dedup store reintroduces the dual-write problem.

How do you build a distributed lock with Redis, and what can go wrong?
Model answer

For a Redis distributed lock, acquire with SET lock:resource <random token> NX PX 30000: set only if absent, expiring automatically after 30 seconds so a crashed holder cannot block forever. Release only if the value is still your token, atomically, with a short Lua script:

A plain DEL could delete someone else's lock after yours had expired.

What can still go wrong:

  • The holder pauses past its expiry: a GC pause, a page fault storm, a slow network. Another client acquires the lock, then the first wakes up and writes as if it still held it. Two writers, and no lock service alone can prevent this.
  • Failover: Redis replicates asynchronously, so a primary can grant the lock and crash before replicating it, and the promoted replica grants it again.
  • Redlock (a majority of independent Redis nodes) addresses failover but still assumes bounded pauses and clock drift, which is the core of Martin Kleppmann's critique.

The senior distinction: if the lock is only for efficiency (avoid doing the same work twice), a Redis lock is fine. If it protects correctness, the resource must check a fencing token, and the lock should come from a consensus-backed store such as etcd or ZooKeeper.

Likely follow up: "What is a fencing token?" A number that increases with every grant; the resource rejects writes that carry an older number than one it has already seen.

9Seniorfencing-tokenleases
What is a fencing token, and why does it fix the paused lock holder?
Model answer

The lock service attaches a monotonically increasing number to every grant: a ZooKeeper zxid or znode version, an etcd revision, a database sequence. The client sends that fencing token with every write to the protected resource, and the resource remembers the highest token it has accepted and rejects anything lower.

The check needs the resource's cooperation: a conditional write such as UPDATE ... SET ..., last_token = :t WHERE id = :id AND last_token <= :t (equal is allowed, so the current holder can write more than once), or any compare-and-set the store offers. That is the real lesson: safety lives in the resource, not in the lock. The lock only makes conflicts rare; the token makes them harmless.

The same idea appears under other names: Raft terms, the epochs of a Kafka controller, and generation numbers of consumer groups. Each one lets the rest of the system ignore a leader or owner that does not yet know it was replaced.

Likely follow up: "The resource is a third-party API that cannot check tokens." Then you cannot get mutual exclusion safely through it. Make the operation idempotent, or route every call through a single owner you control that can check the tokens.

10Seniorleasesleader-election
How do leases and leader election work, and what assumptions do they rely on?
Model answer

A lease is a lock with an expiry. The holder renews it with heartbeats before it expires; if it cannot renew, it must stop acting as the holder before the lease ends from the server's point of view. To be safe, the holder measures from the moment it sent the request, uses a monotonic clock, and subtracts a margin for clock drift. Leases assume bounded drift rates and bounded pauses; a pause longer than the margin breaks them, which is why fencing tokens still matter.

Leader election on a consensus store:

  • etcd: candidates create a key attached to their own lease; the earliest creation revision wins, and the key disappears when the leader's lease expires.
  • ZooKeeper: candidates create ephemeral sequential znodes. The lowest sequence number leads, and each candidate watches only its predecessor, so a leader's death wakes one node instead of all of them.

Split brain, where an old leader has not yet noticed it was replaced, is handled with terms or epochs: every leader action carries its term, and followers or resources reject lower terms. Raft builds exactly this into its protocol.

Likely follow up: "Why watch only the predecessor?" If every candidate watched the leader's node, its deletion would wake them all at once, a herd, and all of them would race to re-check. Watching the predecessor wakes exactly one.

11Seniorredisatomicityrate-limiterSalesforceAmazon
Rate limiting in Redis: why is INCR followed by EXPIRE risky, and what does a Lua script fix?
Model answer

A fixed window limiter often does INCR user:42:minute, and if the result is 1, EXPIRE user:42:minute 60. INCR itself is atomic, so concurrent increments are fine. The risk is the gap between the two commands: if the client crashes or loses its connection after INCR and before EXPIRE, the key never expires and that user stays limited forever as the count keeps growing.

Fixes:

  • A Lua script that increments, sets the TTL when the count is 1, and compares with the limit, atomically on the server in one round trip. This is the standard answer.
  • MULTI, INCR, EXPIRE key 60 NX, EXEC. The NX option (Redis 7) sets the TTL only if the key has none; a plain EXPIRE on every request would keep pushing the expiry out, so an active user's window would never reset.

Pre-creating the key with SET key 0 EX 60 NX and then calling INCR is not safe: if the key expires between the two calls, INCR creates a key with no TTL.

A sliding window log (a sorted set) needs "drop entries older than the window, count, add only if under the limit" as one step. MULTI cannot branch on the count, so use a script. Split into separate commands, two gateways can both count 99 and both add: the single-process check-then-act race, now across machines.

Scripts are atomic because Redis runs commands on one thread, so keep them short; a long script blocks every client. In Redis Cluster, every key a script touches must hash to the same slot.

Likely follow up: "Redis is down. Fail open or fail closed?" Protecting a fragile backend: fail closed, or fall back to a local in-process limiter. On a revenue path: fail open with local limits as a backstop.

12Seniorownershippartitioningordering
How do you get ordering without distributed locks by using ownership?
Model answer

Assign every key to exactly one owner at a time (a partition to a consumer, a shard to its leader) and send all writes for that key through the owner. Order per key comes from the structure, and no distributed lock is needed. With Kafka, records with the same key go to the same partition, each partition has one consumer per group, and that consumer sees the partition in order. Inside the owner, the single-writer pattern means no locks either.

The hazards live at the edges:

  • Rebalancing moves ownership while the old owner may still be processing. Fence it with a generation or epoch number that writes must carry, and commit offsets only after processing.
  • Hot partitions: one key's ordered stream cannot be spread over more workers.
  • There is no order across partitions; anything that needs global order needs a single partition or a merge by timestamp.
  • A poison message blocks its partition: retrying in place keeps order but stalls everything behind it, and moving it to a retry topic unblocks the partition but gives up its order.

Likely follow up: "How do you scale a hot key?" If ordering allows, split it into sub-keys (by sub-entity, or by appending a bucket number) and merge on read; otherwise batch the hot key's updates in its owner.

13Senioroutboxdual-write
Why can you not write to the database and publish an event atomically, and how does the transactional outbox fix it?
Model answer

This is the dual-write problem. Commit first and then publish: a crash in between leaves the database changed with no event. Publish first and then commit: consumers act on a change that may roll back. Most message brokers cannot join your database transaction, so there is no atomic "both".

The outbox pattern: in the same database transaction as the business change, insert the event into an outbox table. Now the change and the event commit or roll back together. A separate relay reads the outbox, by polling or by change data capture on the database log (Debezium is a common tool), publishes each event and marks it sent.

The relay can crash after publishing and before marking, so delivery is at-least-once, and consumers must be idempotent, deduplicating by event id. On the consumer side, the mirror image is an inbox table: record the processed event id in the same transaction as the consumer's effect.

Ordering per aggregate follows the outbox sequence, as long as one relay publishes the events for a given aggregate in order.

Likely follow up: "Polling or change data capture?" Polling is simple but adds database load and latency proportional to the poll interval. Change data capture is near-instant and cheap for the database, but it is more infrastructure to run.

14Seniorsagatwo-phase-commit
Saga or two-phase commit for a transaction that spans several services?
Model answer

Two-phase commit: a coordinator asks every participant to prepare (take locks and promise to commit), then tells them all to commit or abort. It is atomic across participants. The cost: participants hold locks until the second phase arrives, and if the coordinator dies after prepare, they sit "in doubt" holding locks until it recovers. It also adds a round trip, every participant must support the protocol, and availability is the product of all participants'.

Saga: a sequence of local transactions, each with a compensating action. If step 3 fails, run the compensations for steps 2 and 1 in reverse. There are no global locks, but the system is only eventually consistent, and intermediate states are visible to others. Guard those states with explicit statuses such as PENDING (a semantic lock), and make every step and every compensation idempotent, because each will be retried. Orchestration keeps the saga in a central, durable state machine; choreography lets services react to each other's events.

Rule of thumb: two-phase commit inside one database cluster or tightly coupled systems; sagas across independently owned services. A booking saga: reserve the seat, charge the card, confirm; if the charge fails, release the seat.

Likely follow up: "What if a compensation fails?" Retry it with backoff until it succeeds, since compensations must be retryable and idempotent, and route repeated failures to an alert and a manual repair queue.

15Seniorjob-schedulerleasesSalesforce
Many workers pull jobs from a shared table. How do they claim jobs so that two workers never run the same one?
Model answer

Claim with a conditional update that takes a lease:

One row affected means the job is yours. The status check matters: without it, a finished job whose lease has lapsed would be claimed again. For a queue-shaped table, SELECT ... LIMIT 10 FOR UPDATE SKIP LOCKED inside a transaction lets many workers grab different rows without waiting on each other (PostgreSQL, and MySQL 8). The worker heartbeats to extend the lease; if it dies, the lease expires and another worker claims the job.

The catch: a paused worker can wake up after its lease was taken over, so for a while two workers run the same job. "Never twice" therefore really means at-least-once execution with at most one effective completion:

  • Make the job idempotent.
  • Fence the completion: UPDATE jobs SET status = 'DONE' WHERE id = :id AND owner = :me AND attempt = :attempt, which fails for the stale worker.
  • Pass the attempt number as a fencing token to anything else the job writes.

Likely follow up: "How long should the lease be?" Long enough to cover normal heartbeat jitter several times over, and short enough that recovery after a crash is acceptable. Tens of seconds with heartbeats every few seconds is a common choice.

16Stretchhot-rowflash-saleinventoryFlipkartAmazon
A flash sale hammers a single inventory row. How do you avoid overselling without melting the database?
Model answer

The correctness baseline is the guarded decrement, UPDATE stock SET qty = qty - 1 WHERE sku = ? AND qty > 0, checking rows affected. It never oversells, but every buyer serializes on one row lock, connections pile up waiting, and the pool runs dry.

Ways to scale it:

  • An admission gate: an atomic Redis decrement (or a Lua check-and-decrement) in front, so only winners reach the database. Reconcile the two counts afterwards, and give units back to Redis when an order fails later.
  • Split the inventory into N bucket rows and decrement a random bucket that still has stock. That gives N-way parallelism; the last few units need a scan across buckets.
  • A queue per SKU with a single consumer: requests are accepted at once, processed in order, and answered asynchronously. No contention, at the cost of an async user experience.
  • Reservations with an expiry, so abandoned carts return stock (no underselling), released by a sweeper or treated as expired when read.
  • Per-user purchase limits and a virtual waiting room to smooth the spike.

In MySQL, keep sku a primary or unique key so the update locks one record and no gaps, and when one order touches several SKUs, lock them in sorted order.

Likely follow up: "Redis says the user won, but the database insert failed." Compensate: increment the Redis counter back, and let a reconciliation job correct any drift between the gate and the database.
