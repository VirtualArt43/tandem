Putting it together: a thread safe class from scratch

Build a bounded queue with timed admission and graceful shutdown, connect two workers, and audit the class for safety and progress.

Asked atRubrikLinkedIn
Before this:The toolkit: ReentrantLock, Condition, ReadWriteLock and StampedLockThe toolkit: Thread, Runnable, Callable and virtual threadsThe toolkit: concurrent collections and synchronizersTime: nanoTime, Duration and TimeUnitEncapsulation, composition and SOLID

A threaded class earns its name by keeping a promise across every method, including timeout, interruption and shutdown. Build a bounded work queue, then use two workers to show what that promise does and does not guarantee.

In plain words

A small repair shop has two mechanics and a shelf with room for three waiting jobs. When the shelf is full, a customer can wait briefly or leave. At closing time the owner stops accepting jobs, wakes anyone waiting, and lets the mechanics finish the jobs already accepted.

The closed sign and the shelf must follow one shared rule. Checking the sign, walking away, then putting a job on the shelf leaves a gap in which the owner can close the shop. A separate lock on each action does not close that gap.

Why this matters for concurrency

You already have the parts: locks and conditions, threads and tasks, and timeout budgets. Here you make their contracts agree. The same review applies to a connection pool, cache, reservation service or background logger.

For LLD, apply encapsulation and composition: the queue owns admission and storage, workers own execution, and the caller owns shutdown and joining. Rubrik reports include a bounded queue followed by a pool built on it; LinkedIn reports include producers, consumers and draining shutdown. The important skill is explaining the ownership and lifecycle of each piece.

Start with the contract

Our custom CloseableQueue<E> accepts non-null elements in first in, first out order. Capacity is a positive number of waiting elements, excluding jobs workers have already removed. Timed admission provides back-pressure: a caller cannot grow the waiting list without a bound.

OperationContract
new CloseableQueue<E>(capacity)Reject nonpositive capacity with IllegalArgumentException.
offer(item, timeout, unit)Return true only after inserting; return false when the lock or space wait exhausts its budget. Throw IllegalStateException if closure is observed under the lock.
take()Wait for an element while open; remove the oldest element if present. Return null only when closed and empty.
close()Reject future admission, preserve existing elements and wake all waiters. Repeated calls are harmless. Return without waiting for jobs to finish.

offer rejects a null element or unit with NullPointerException, and a negative timeout with IllegalArgumentException. Zero means attempt without waiting. Both admission and removal propagate InterruptedException if their lock acquisition or condition wait detects interruption; that throwing call has not inserted or removed an element.

A timeout limits requested waiting, not wall-clock completion. Scheduling pauses and reacquiring the lock after a condition wait can delay return beyond the budget. After acquiring the lock, available space may win even if the budget has just expired; if still full, no further condition wait is requested.

If lock acquisition times out, offer returns false without inspecting closure. This avoids promising a shutdown diagnosis without owning the lock. close() also needs the lock and can wait to acquire it; it does not wait for task completion.

Write the invariant before the fields

The invariant is: 0 <= items.size() <= capacity; insertion and removal preserve FIFO; once closed, no insertion succeeds. One private lock guards both the deque and closed, including every read. No caller receives the deque, its iterator or the lock.

There are two conditions, attached to that same lock. A producer waits while full and open; a consumer waits while empty and open. Closure changes both predicates, so it must wake both sets of waiters. Read invariants and critical sections for the general method.

First make the admission race visible

This deliberately broken miniature has no unsynchronized field access. Its flaw is the gap between checking and inserting, the check then act pattern applied to shutdown. The latches force that gap open; they are test controls, not a proposed fix.

A separate atomic or volatile closed flag has the same composition problem. Keep the closed check and actual insertion in one critical section. The atomics toolkit explains why visibility alone cannot supply that atomicity.

The complete component, then two workers

Read the queue first, then worker, then main. This capstone is longer than an API example because it includes the full lifecycle and executable assertions. It uses only Java 21 standard library APIs.

For syntax refreshers use classes and interfaces, generics, lambdas and exceptions and cleanup. For an extensible service boundary, use LLD design; do not add inheritance just to reuse queue storage.

We ignore the value returned by awaitNanos because we recompute from the original start after every wakeup. That charges time spent acquiring the lock as well as waiting for space. Never restart the full budget. Timeout arithmetic assumes elapsed intervals shorter than Long.MAX_VALUE nanoseconds, as explained in the time lesson.

One insertion makes one consumer eligible; one removal makes one producer eligible, so ordinary updates use signal. Closure changes what every waiter must do, so it uses signalAll twice. The zero-time tryLock overload here is still interruptible; an interrupt racing with a completed insertion may instead leave a successful return and a set interrupt flag. An interrupt is not a rollback.

A signal neither hands over the lock nor reserves an element. The waiter must reacquire the lock and recheck in a loop because another caller may take the item or space first; spurious wakeups are also permitted. Checking the predicate under the lock and atomically releasing it when waiting prevents a notification from slipping into an unprotected check-to-wait gap. Signals are not stored for future waiters: the queue state is what remembers available work.

Worked example: closure beats a waiting producer

A capacity one queue contains job A. Producer P wants to submit B; consumer C has not yet taken A. The owner O closes admission.

If P inserted before O set closed, B would be accepted and drained. The insertion is the successful offer's linearization point; closing takes effect at closed = true. Returning true after close() returns is possible when the calls overlapped and insertion happened first. Returning true does not mean the job has finished.

What the worker demo proves, and what it leaves to the pool

Constructing the queue before Thread.start() safely publishes it to both workers. Producer writes before an offer's unlock become visible after a consumer acquires that lock: this is a happens-before relationship. The queue transfers references; it does not make mutable payloads safe to change after submission. Prefer immutable jobs or exclusive ownership, and study safe publication for the full argument.

With two workers and capacity two, at most four accepted jobs are queued or executing at once. Blocked submitters may still hold additional jobs in their own stacks, so capacity does not bound total application memory. FIFO describes removal order; workers can start or finish jobs in a different order.

The demo counts task RuntimeExceptions and keeps processing. It does not retry, return futures, replace workers after Error, or forcibly stop hung jobs. Draining assumes workers remain available and tasks eventually return. A worker exits when take() detects interruption; a running task can ignore or clear interruption, so interrupting a worker does not guarantee it stops.

Graceful shutdown has two steps: close admission, then join workers outside the queue lock. Empty storage is not evidence that running jobs have finished. Here joinAll finishes joining every worker even if the owner is interrupted, then restores the owner's interrupt flag. It defers cancellation during cleanup and has no time bound, which is suitable only when waiting for these terminating demo tasks is acceptable.

Restoring the flag inside the retry loop would make the next blocking join() throw again. Restore it after cleanup instead; an InterruptedException from submission still propagates after the finally block. For futures and bounded termination waiting, continue to building a thread pool and cooperative cancellation; for application code start with library executors.

The checklist for any threaded class

  1. Contract: define results, rejection, timeout, interruption and lifecycle transitions before fields.
  2. Ownership: list shared mutable state, its protecting lock and any escaping references; include payloads and callbacks.
  3. Invariant: put every check and update needed to preserve it under the same protection, including reads.
  4. Atomic effect: identify where each successful operation takes effect and how overlapping calls are ordered.
  5. Waiting: state each predicate, loop after wakeups and list every state change that must signal it.
  6. Cancellation: charge one timeout budget, specify what remains unchanged on failure, and release locks on every exit.
  7. Lifetime: publish fully constructed objects; close admission, wake waiters, and wait for workers without holding their lock.
  8. Progress and cost: keep callbacks outside locks; admit that unfair locking can starve a caller. Deque operations are amortized O(1), storage O(capacity), and blocking delay is separate.
  9. Evidence: test capacity one, empty/full waits, closure on both wait sets, interruption, timeout, FIFO and exact item identities under many producers and consumers.

A useful shutdown regression starts several consumers, verifies they reached the condition wait, closes an empty queue, then bounds every join. Repeat with a full queue and waiting producers; all must reject while the original element survives. Use latches or test-only instrumentation for scheduling, capture worker failures, and use a watchdog for hangs. A start latch alone does not prove a thread reached await.

The samples check a forced bad schedule and a small correct run; they are not an exhaustive concurrency test suite. Testing concurrent code develops stronger harnesses; linearizability explains how to check histories. Also work through producer and consumer and spurious and stolen wakeups.

Common mistakes

  • A separate open check: closure can slip between checking and inserting. Combine them under the queue lock.
  • Stopping on closed before inspecting items: this discards accepted work. Stop consumers only when closed and empty.
  • Waking only consumers on close: full-queue producers can remain asleep until timeout. Signal both conditions to all waiters.
  • Calling task.run() or join() under the lock: tasks can block, call back or require the same queue; waiting workers cannot finish. Release first.
  • Returning false for interruption: this erases cancellation. Propagate it from queue methods; restore it at the worker boundary.
  • Equating FIFO with completion order: two workers can finish in either order. Ordered results require another protocol.

In the interview

Expect "implement a bounded work queue", then "add timeouts", "shut it down", and "build workers on top". Clarify draining versus discarding, whether producers may race with shutdown, and what successful submission means before coding.

I will guard admission state and storage with one private lock. An offer checks closure and inserts atomically. Close wakes both producer and consumer waiters; consumers drain accepted work before seeing end of stream. Workers execute after releasing the queue lock, and the owner joins them after closing admission.

For "why not synchronized?", it can implement the same state rules; the monitor toolkit covers that version. This implementation chooses interruptible timed acquisition and two targeted wait sets. For "why not a library queue?", use one when allowed, but still define the lifecycle around it. Review timeouts and fairness before promising latency or starvation freedom.

Senior depth

Immediate shutdown needs a different contract. Close admission and remove pending items under the queue lock, wake both wait sets, then request cooperative cancellation of workers outside it. A task already removed by a worker is absent from the queue even if run() has not begun. Returning every task that has not started therefore needs extra coordination between shutdown and the worker's transition to running; draining the deque alone cannot meet that promise.

Poison pills need producer coordination. If each worker exits after taking one sentinel, stop all producers first and enqueue one sentinel per worker, after the real jobs. The sentinel must be distinguishable from every valid job, and insertion may block when the queue is full. This queue reserves null for closed and empty, so null cannot be an enqueued sentinel.

Callbacks outside locks can still exhaust a pool. If both workers submit child jobs to their own full queue and wait for space, neither worker is available to drain it. A timed offer can break that stall by failing; replacing timed offers with indefinite waits can deadlock. Waiting for child results can also deadlock even when admission succeeds, so choose an explicit policy such as rejecting worker submissions, executing suitable children inline, or composing asynchronously.

Key takeaways

  • State the contract and invariant before choosing synchronization.
  • One lock makes checking closure and admitting work one atomic decision.
  • Conditions are prompts to recheck; closure must wake both wait sets.
  • One elapsed-time budget covers lock acquisition and repeated space waits.
  • Closing admission, draining storage and finishing execution are different events.
  • Keep task execution outside queue locks; thread safety does not transfer automatically to payloads.

Quick check

Answer each question, then read why. Your score is saved for your module test.

An offer inserts just before another thread executes closed = true. Its caller is paused before returning. What can happen?
Why. Insertion orders this overlapping offer before closure. The caller can pause after unlocking but before its response, so close can return first. Close neither removes the item nor retroactively rejects it, and the JVM does not wait for every caller to return. An offer begun after close has returned cannot insert.
After closing a queue containing 10 then 20, with no other consumers or interruption, what is printed if you print the results of three consecutive take() calls?
Why. Close prevents insertion but preserves FIFO contents, so 10 precedes 20 and neither removal throws because of closure. null means closed and empty; returning it immediately would break draining.
An offer has a 100 ms budget. Lock acquisition consumed 60 ms and the queue is still full. Approximately how much waiting budget remains?
Why. Subtract the 60 ms spent acquiring the lock from the original 100 ms, leaving about 40 ms. Passing 100 ms again would extend the budget; 60 ms is time spent, not time remaining, and contention does not itself force failure. Scheduling and lock reacquisition after a condition wait can still postpone actual return.
Several producers wait on a full queue when close() sets the flag and signals only notEmpty. What is the bug?
Why. Each condition has its own wait set, so signalling notEmpty does not signal notFull. Close holds the required lock, so the changed signal alone does not cause IllegalMonitorStateException. Making the flag atomic would not wake sleeping producers. Timed producers can eventually escape on timeout, but shutdown should notify them promptly.
What does the queue guarantee when offer throws InterruptedException from its condition wait?
Why. Insertion is after the interruptible waiting steps, and finally unlocks. Throwing InterruptedException clears the thread's interrupt status; the caller must propagate it or restore the flag when handling it. Interruption cancels this waiting call; it neither discards accepted work nor changes the queue lifecycle.
With capacity 3 and two workers, which claims hold for the demo's design? Select all that apply.Select all that apply
Why. The bound is three queued plus two executing. Blocked producers may retain additional jobs. Closing admission does not wait for worker termination, and parallel execution does not preserve completion order.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
List the queue's shared mutable state, wait predicates and atomic effects. Why is a final deque plus a volatile closed flag insufficient by itself?
Model answer

The mutable deque contents and closed flag share one private lock. A producer waits while full and open; a consumer waits while empty and open. Successful offer takes effect at insertion, successful take at removal, and first close at the flag write. Terminal take observes closed and empty under the lock.

Final fixes the deque reference, not its mutable contents. Volatile makes flag accesses visible but cannot combine the open check and insertion into one operation. The same lock must cover both, and all deque reads and writes.

Debug
A shutdown implementation sets closed, signals both conditions, then joins workers while holding the queue lock. Explain a deadlocking schedule and the repair.
Model answer

A worker is waiting in take. Shutdown takes the lock, sets closed and signals it, but keeps the lock while joining. The worker must reacquire that lock before returning from await and observing closure. The owner waits for the worker; the worker waits for the owner. Move joins after the finally block releases the lock. Do not make a worker join itself; lifecycle waiting belongs to an external owner.

Write code
Add int size() for diagnostics. Explain whether if (queue.size() < limit) queue.offer(...) reserves space.
Model answer

It returns a consistent snapshot during the call, but reserves nothing. Another producer may insert immediately after unlock. Use offer itself to test and perform admission atomically; treat size as diagnostics, not permission.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"You have a bounded queue and two workers. Walk me through a clean shutdown while producers are still submitting."
What a strong answer covers
  • Close means reject new admission and drain accepted jobs
  • One lock guards the closed check and insertion; overlapping calls are ordered by their effects
  • Close sets the flag and signals all producer and consumer waiters
  • Consumers return queued elements after closure and terminate only when closed and empty
  • Workers execute outside the lock; the owner joins after closing and releasing the lock
  • Draining requires available workers and terminating tasks; interruption is a separate cancellation policy
How a senior would say it
I would close admission first, drain accepted jobs, and then wait for the workers. The queue's closed flag and contents share one private lock. An offer checks the flag and inserts while holding that lock, so there is no gap where shutdown can slip in. If insertion happens first, the job is accepted. If closure happens first, the offer is rejected. An accepted offer can return after close because those calls overlapped. Close sets the flag and signals all waiters on both conditions. Producers waiting for space need to wake and reject; consumers waiting for work need to wake and observe the terminal state. Consumers keep removing existing jobs after closure. They return end of stream only when the queue is both closed and empty. Each worker runs its task after releasing the queue lock. The owner then joins the workers outside that lock, because a waking worker must reacquire it before exiting. An empty queue alone is insufficient: a worker may still be executing its last job. This is graceful shutdown, assuming workers remain available and tasks eventually finish. Interrupting workers is a different cancellation policy. For bounded shutdown latency, I would add a termination timeout and define what happens to unfinished jobs.

Likely follow up: What changes if shutdown must return immediately and give the caller every job that has not started?

Out loudabout 60 s
"All the fields are private and every method takes a lock. Is the class thread safe now? What would you review next?"
What a strong answer covers
  • Private fields and individual locking are insufficient for a compound invariant
  • Check that admission and lifecycle state use one lock across check and update
  • Review waiting predicates, loop rechecks and shutdown notifications
  • Review timeout budgets, interruption and exception cleanup
  • Check escaped references, callback placement and a concrete adversarial test
How a senior would say it
No, I still need to check the class's contract across methods. Two individually locked calls can leave a race between checking that the queue is open and inserting a job. I would identify the invariant and ensure the same lock protects the whole decision, including lifecycle state and reads. Next I would write each waiting predicate and identify every change that can make a waiter proceed. Waits need loops, and closing this queue must wake both producers and consumers. I would check that timeouts share one budget and that interruption leaves no partial insertion and releases the lock. Then I would inspect references and callbacks: no internal collection should escape, and task execution belongs outside the lock. Finally, I would force a producer to wait on a full queue, close it, and verify rejection while the original job remains drainable.

Likely follow up: How would you test that a blocked consumer is woken by close without using sleep to arrange the schedule?
