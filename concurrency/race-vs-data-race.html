Race conditions versus data races

The precise difference between a data race and a race condition, an example of each without the other, and what each language promises a racy program.

Asked atGoogleLinkedIn
Before this:Creating, starting and joining threadsPassing data in and getting results out

People say "race" for two different bugs. A data race is about memory accesses; a race condition is about the logic of your program. Knowing which one you have tells you which fix works, and whether a tool like ThreadSanitizer can find it at all.

In plain words

A data race is two people writing on the same square of a whiteboard at the same moment. The marks blur together; you may not get either person's number, and you cannot even say what is written there.

A race condition is two people who each look at the shared office calendar, see Friday free, and each book Friday. Every look and every write was clean and orderly, one person at a time. The bug is that each decision was based on a view that was already stale by the time they acted.

Two precise definitions

A data race is a fact about memory accesses. Two threads access the same memory location, at least one access is a write, and neither access happens-before the other. In C++, at least one conflicting access must also be non-atomic: operations on a std::atomic do not race with each other, even with relaxed ordering that does not publish other data. Java's volatile fields and the ordinary operations of its atomic classes provide synchronization for their accesses. C++ volatile does not.

A race condition is a fact about correctness. The program's result depends on the timing or interleaving of threads, and some interleavings give a wrong answer. It is a bug in the logic, not in any single memory access.

The two overlap a lot, which is why people blur them, but removing data races does not remove every race condition. Java also permits carefully justified data races that do not change the correct result; C++ does not:

No race conditionA correct program: a counter updated with an atomic increment, results read after joinJava's carefully designed String.hashCode() cache, discussed below: stale cache reads only cause recomputation. There is no safe C++ data race

Here every access to the balance is protected by the same lock. There is not a single unprotected read or write, so there is no data race, and ThreadSanitizer stays silent. Two cash machines still take out 200 from an account holding 100.

The sleep widens the window and makes the bad outcome easier to observe; it cannot guarantee a particular schedule. A run that ends at 0 still contains the same logical bug. What went wrong is visible only at the level of the whole operation:

This shape is called check then act, and it gets its own lesson. The fix is not "more synchronization on each access" but making the check and the act one atomic step: a single tryWithdraw(amount) method that checks and subtracts under one lock.

A data race that prints the right answer

Now consider a broken program that often produces the right output. A worker writes a result; main waits "long enough" and reads it. It may print 42 repeatedly. It is still a data race: sleep creates no happens-before edge, so Java need not expose the worker's write and C++ has undefined behavior. A lucky run is not an example of a program without a race condition.

ThreadSanitizer can flag the C++ version even when the output is right, and may note that the threads look "as if synchronized via sleep". It tracks happens-before, not wall clock time. Moving the read after worker.join() removes the race completely, because join is a real synchronization point.

What each language promises a racy program

This is where Java and C++ differ most, and interviewers like the contrast.

C++: a data race is undefined behavior. Not "you may read a stale value": the whole program has no defined meaning. The compiler is allowed to assume no data race ever happens, and optimizes on that basis. It may keep a variable in a register so a loop never sees another thread's write, read a variable twice and get two different values where your code read it once, or tear a value in half. "It printed the right answer" proves nothing, and there is no such thing as a benign data race on a plain variable in C++. Use std::atomic (with memory_order_relaxed if you really need no ordering) whenever threads share a variable without a lock.

Java: racy programs are legal, but the guarantees are weak. Java keeps memory safety and type safety even with races, so you will not crash in the way C++ can. What you can see:

  • Stale values, possibly forever: the JIT may hoist a read out of a loop.
  • Writes in a surprising order: another thread may see a later write before an earlier one, or a reference to an object before the object's fields are initialized (except final fields of a properly constructed object).
  • Torn long and double values: a non-volatile 64-bit write may be split into two 32-bit halves, so a reader can see half of one write and half of another, a torn read. volatile long, volatile double and references are never torn.
  • No values out of thin air: every value a read returns was actually written by some thread at some point, or is the default (for a torn long or double, each 32-bit half was).

Both languages then make the same central promise, the Data race free (DRF-SC) guarantee: if your program has no data races, it behaves as if the threads' steps were simply interleaved in some order (in C++, as long as your atomics use the default sequentially consistent ordering). That is the deal: you remove the data races, and in return you may reason about interleavings, which is all the reasoning in this module does. Race conditions are what remain to reason about.

Which tool finds which bug

Data raceRace condition
What it isUnordered conflicting accesses to one memory locationA result that depends on the interleaving
Who can find itThreadSanitizer in C++ (whenever the racing accesses actually run during the test); in Java, stress tests and tools such as jcstressYour reasoning about invariants, code review, and stress tests that check the result (exact totals, no duplicates)

The practical consequence: a clean ThreadSanitizer run means no data race was detected in that run. Uninstrumented code and suppressions can limit detection. It says nothing about race conditions built from properly synchronized steps, and nothing about code paths the test never exercised.

Common mistakes

  • "ThreadSanitizer is clean, so the code is correct." TSan finds data races in the interleavings that ran. Race conditions between properly locked steps are invisible to it.
  • "It printed the right answer a thousand times." A data race can be right on every test run and still be undefined behavior in C++, or a stale read waiting to happen in Java.
  • "I used thread-safe classes everywhere, so there are no races." Thread-safe calls in sequence are not a thread-safe sequence.
  • "It is a benign race: only one thread writes." One writer and one reader without synchronization is still a data race. In C++ make it a relaxed atomic at minimum.
  • "volatile fixes races." Java's volatile removes the data race on that one variable; it does nothing for compound operations. C++'s volatile does neither.
  • Using the words loosely in the interview. Calling a check-then-act bug a "data race" tells a careful interviewer you are not sure what either term means.

In the interview

It is asked directly ("what is the difference between a race condition and a data race?"), and indirectly whenever you defend a design: LinkedIn interviewers have asked candidates to name the specific race each lock prevents, and a Google L5 candidate who listed ConcurrentHashMap, AtomicInteger and synchronized for a per-user counter map still got a no hire, concluding afterwards that precise reasoning about races and guarantees was expected, not a list of tools.

A data race involves conflicting memory accesses that are not ordered by happens-before; in C++, at least one must be non-atomic. In C++ it is undefined behavior; Java retains memory safety but may expose stale or torn values. A race condition is a logic bug where some interleaving violates the contract. Two synchronized calls in a row can have a race condition with no data race. A lucky output does not establish correctness. ThreadSanitizer looks for data races; invariant reasoning and tests that check outcomes also address logical races.

Follow ups to expect: "Give an example of each without the other." "Can a program with no data races still be wrong?" (yes, and here is one). "What does Java guarantee for a racy program?" (no out of thin air values, but stale, reordered and torn 64-bit values). "Why does C++ make data races undefined behavior?" (so compilers and CPUs can optimize single-threaded code freely; the price is that you must mark every shared access).

Senior depth

Why C++ chose undefined behavior. Almost every useful compiler optimization (keeping values in registers, reordering independent loads and stores, merging reads) would be illegal if any plain variable might change underneath at any moment. C++ lets the compiler assume no data races, and asks you to say "this one is shared" with std::atomic. Java chose to give racy programs some meaning, mainly for security: untrusted code must not be able to break memory safety with a race.

The famous Java "benign" race. String.hashCode() caches the hash in a plain field without synchronization. It is safe only because the hash is an int (never torn), every thread computes the same value, and a thread that sees the default 0 simply recomputes it. It is a deliberate, documented exception inside the JDK, not a pattern for application code. The C++ equivalent must be a relaxed atomic.

What counts as one memory location. In both languages, distinct variables, array elements and fields are distinct locations, so threads writing different ones never race; Java even forbids word tearing for adjacent bytes. One C++ exception: a run of adjacent bit-fields is a single memory location, so two threads writing different bit-fields of the same struct without a lock is a data race.

Key takeaways

  • Data race: unordered conflicting accesses to one memory location. Race condition: a result that depends on the interleaving.
  • Locked check-then-act can have a race condition without a data race. A lucky racy read proves nothing; Java's carefully designed hash cache is a separate example of a benign data race.
  • C++: any data race is undefined behavior. Java: racy programs are legal but may see stale, reordered or torn 64-bit values.
  • Data-race-free Java programs, and data-race-free C++ programs using default sequentially consistent atomics, let you reason in interleavings. Logical races still need checking.
  • ThreadSanitizer finds data races that occur during the run; race conditions need invariants, review and result-checking stress tests.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Which of these has a race condition but no data race?
Why. Every access in the first option is locked, so there is no data race, yet two threads can both pass the check and overdraw the account. count += 1 on a plain int has both a data race and a race condition. The last two are correct: different array elements are different memory locations, and join orders the write before the read.
Your C++ stress test passes a thousand times in a row, and ThreadSanitizer reports nothing. What can you conclude?
Why. ThreadSanitizer is a dynamic data race detector, not a correctness proof. A check-then-act built from locked calls has no data race to report, untested paths remain untested, and incomplete instrumentation or suppressions can hide races. Some Linux builds also detect lock order inversions; Apple clang on this Mac does not.
x starts at 0. Two threads each run x.set(x.get() + 1) 1,000 times on a shared AtomicInteger (in C++, x.store(x.load() + 1) on a std::atomic<int> with default ordering). After joining both threads, which final values are possible?
Why. There is no data race, but the read and the write are two separate atomic steps, so the lost update interleavings from the previous module all still exist, including the one that ends at 2 (one thread reads 0 and stalls while the other does 999 increments, and so on). 0 and 1 are impossible because each thread's last write is at least one more than a value it read. Use incrementAndGet() or fetch_add(1) to make the whole read-modify-write one step.
Which statement about a program with no data races is true?
Why. This is the data-race-free guarantee, the central promise of both memory models. It does not remove race conditions (the locked overdraft is data race free), it usually requires locks or atomics to achieve, and different interleavings can still legally give different outputs.
A plain boolean done (not volatile, not atomic) is set to true once by one thread, while another thread spins in while (!done) {}. How should you classify this?
Why. A write and a read of the same plain variable with nothing ordering them is a data race, no matter how few writers there are. Atomic-sized writes prevent tearing, not staleness: nothing forces the reader to look at memory again. Declare it volatile or AtomicBoolean in Java, or std::atomic<bool> in C++.
Java onlyA Java long field (not volatile) is written by one thread and read by another with no lock. Apart from seeing an old value, what else can the reader see?
Why. The Java language specification allows non-volatile long and double writes to be split into two halves; volatile ones, and references, are always atomic. Many 64-bit JVMs do not tear in practice, but the language does not promise it. Out of thin air values are exactly what the Java memory model rules out.
C++ onlyTwo threads write different members of the same struct with no synchronization: one runs s.a = 1; and the other s.b = 2;, where a and b are ordinary int members. Is this a data race?
Why. A data race needs the same memory location, and each non-bit-field member is its own location. Sharing a cache line can make this slow (false sharing), but it is not a race. The exception is adjacent bit-fields, which the standard treats as one memory location.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Explain the difference between a race condition and a data race to an interviewer, with one example of each that is not also the other.
Model answer

A data race is a memory-level property: conflicting accesses from different threads are not ordered by happens-before; in C++, at least one must be non-atomic. It is undefined behavior in C++. Java preserves memory and type safety, but a racy reader may see stale data or torn non-volatile long and double values.

A race condition is a logic-level property: some interleaving violates the contract. A bank account whose balance() and withdraw() each take the same lock has no data race, yet two callers can both check 100 before either withdraws 100. The account ends negative. For the other direction, Java's String.hashCode() deliberately races on cached results: the underlying content is immutable, all computations agree, and a stale cache read only causes recomputation. That requires a proof for every allowed outcome, not a lucky test result. C++ has no safe equivalent using a plain racy cache field. Fix ordinary data races with appropriate ordering or atomic accesses, and fix compound logical races by making the whole decision and update atomic.

Debug
A reviewer says "this counter is fine, it uses an atomic". Is it? Classify the bug and fix it.
Model answer

It is not fine. There is no data race, because every access goes through the atomic, but there is a race condition: the read and the write are two separate atomic steps, so two threads can read the same current and the second set overwrites the first. That is a lost update, so the total ends up too low. ThreadSanitizer would not flag the C++ equivalent, total.store(total.load() + amount), because there is no data race to find.

The fix is to make the read-modify-write a single atomic operation: total.addAndGet(amount) (or getAndAdd) in Java, and total.fetch_add(amount) in C++. If the new value had to be computed by a more complex function, use updateAndGet or a compare-and-swap loop that retries when another thread got there first; under high contention in Java, LongAdder spreads the updates out.

Explain
A teammate says: "This data race is benign. Only one thread writes the ready flag, and it only ever writes true." Respond for Java and for C++.
Model answer

In C++ there are no benign data races: an unsynchronized write and read of the same plain variable is undefined behavior, so the compiler may, for example, read the flag once before the loop and never again, and the waiting thread spins forever. The fix costs almost nothing: make it a std::atomic<bool>. If ordering with other data matters, the default ordering or a release store with an acquire load is right; if truly nothing else depends on it, memory_order_relaxed still removes the undefined behavior.

In Java the program is legal, but the guarantee is weak: without volatile there is no promise the reader ever sees true, because the JIT may hoist the read out of the loop. And if the flag is meant to say "the data is ready", there is no promise the reader sees the data that was written before the flag either. Declaring it volatile fixes both, because a volatile write happens-before every later volatile read of it. "Only one writer" removes write conflicts, not the need to order the write with the read.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Every account method takes the same lock, but two withdrawals still overdraw the account. Is that a data race or a race condition? Walk me through it."
What a strong answer covers
  • It is a race condition without a data race if every balance access uses the same lock
  • Data races concern unordered conflicting accesses; C++ also requires a non-atomic access
  • Two callers each read 100 before either withdraws 100, leaving a balance of minus 100
  • Expose tryWithdraw with check and subtraction inside one critical section
  • ThreadSanitizer cannot diagnose this logical violation; tests must assert the invariant
How a senior would say it
It is a race condition without a data race, assuming every access to the balance really uses the same lock. A data race concerns conflicting accesses to the same memory location that are not ordered by happens-before. C++ also requires at least one of those accesses to be non-atomic. The lock orders the accesses here, so that problem is absent. The contract can still fail because the decision spans two separate calls. Start with a balance of one hundred. Caller A locks, reads one hundred and unlocks. Caller B does the same. Both have decided they can withdraw one hundred. A now locks and subtracts, leaving zero. B then locks and subtracts, leaving minus one hundred. Every memory access was protected, but the decision became stale. I would expose one operation, tryWithdraw, that checks the amount and balance and performs the subtraction while holding the same lock throughout. Readers would follow the same locking policy. ThreadSanitizer should not report a data race in the original example because there is none to report. I would test the actual invariant: with one hundred available and two competing withdrawals of one hundred, at most one succeeds and the balance never becomes negative. The lock must cover the operation the caller needs.

Likely follow up: Could a compare-and-set loop implement the same operation, and when would you prefer the lock?

Out loudabout 75 s
"Our counter uses atomic loads and stores, but totals are low and ThreadSanitizer is quiet. What would you look for?"
What a strong answer covers
  • Look for a load followed by a separate store of the incremented value
  • Two threads can both load 5 and store 6, losing one increment without a data race
  • Use one atomic read-modify-write operation, not stronger ordering on separate accesses
  • Use a lock if the count must move consistently with other state
  • Assert exact totals after joining; a clean detector run does not prove logical correctness
How a senior would say it
I would look for an increment written as a load followed by a separate store. Atomic access prevents a data race on the counter, but it does not combine those two operations into one. If two threads both load five, both calculate six, and both store six, the final count is six when it should be seven. That is a lost update and a race condition, even with the strongest default ordering. ThreadSanitizer can stay quiet because each access is valid. I would replace the sequence with one atomic read-modify-write: an atomic increment in Java, or fetch-add in C++. If recording the hit also updates another field that must agree with the count, I would protect the complete operation and its readers with one lock instead. For validation, I would start several workers, have each add a known number of hits, join them all, and check the exact total. I would retain the sanitizer run for other data races. Passing that run alone does not establish that the counter meets its contract.

Likely follow up: If the update is a more complicated function than addition, how would you make it atomic?

Out loudabout 75 s
"A worker writes 42 into a plain field. Main sleeps, reads 42, then joins. It has passed a thousand times. Would you approve it?"
What a strong answer covers
  • Reject it: sleeping and repeated success do not order the worker's write before the read
  • The later join does not retroactively protect the earlier read
  • C++ has undefined behavior; Java may read 0 or 42 for a zero-initialized int in this example
  • Move the read after successful join to order completion and visibility
  • Atomic access can remove the data race without guaranteeing the worker has finished
How a senior would say it
No. The read happens before the join, so the code has no synchronization that orders the worker's write before that read. Sleeping changes timing, and a thousand successful runs do not add a happens-before relationship. Joining afterwards does not retroactively make the earlier access safe. In C++, the conflicting plain accesses form a data race, so I cannot give a bounded list of valid outputs: the behavior is undefined. In Java, for this zero-initialized int with only the worker writing forty-two, main can read zero or forty-two; seeing forty-two repeatedly does not establish visibility. The simplest fix is to join successfully and then read. Worker completion is then ordered before main continues, so the result is available without making this field atomic. I would choose a future if I wanted to express result delivery and failure together. Merely making the field atomic removes the data race on that field, but an early load can still read the initial value. I need both safe access and the completion guarantee required by the operation.

Likely follow up: What must you check before reading if you use a Java join with a timeout?
