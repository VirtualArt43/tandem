Synchronizers: semaphores, latches, barriers and phasers

Semaphores, CountDownLatch, CyclicBarrier, Phaser and friends: how each works, how to choose, how to build them, and how they fail.

One question picks the tool: are threads waiting for events, for each other, or for capacity? Details that matter: a latch counts events, not threads, so one thread may count down several times; Java's CyclicBarrier counts arrivals by parties and breaks the generation if an active wait is interrupted or times out; a semaphore has no owner, so any thread may release.

C++20 has the same trio: std::latch, std::barrier, std::counting_semaphore.

A Rubrik booking report explicitly discusses the choice of CyclicBarrier and Semaphore.

Seat booking requires atomic ownership of specific seats, usually under a lock or transaction. A semaphore can cap capacity, but cannot prevent two bookings of the same seat. A barrier is for coordinating phases.

Likely follow up: "Can you reset a CountDownLatch?" No. Create a new one, or use a CyclicBarrier or Phaser.

2Coresemaphores
What is a counting semaphore? Show how you would use one to cap concurrency.
Model answer

A semaphore is a counter of permits with two atomic operations (Dijkstra's P and V): acquire takes a permit, blocking while there are none; release returns a permit and wakes a waiter. It has no owner and the count can exceed one, so it models "at most N at a time". Always release exactly once per successful acquire, in a finally block or a destructor.

Fairness: Java's Semaphore(n, true) orders blocking acquisitions at internal queueing points; call arrival time is not strict FIFO and untimed tryAcquire() may barge. The default allows barging. C++ does not specify fairness.

Likely follow up: "Semaphore of 10, or a fixed pool of 10 threads?" A fixed pool bounds worker threads; queueing, rejection or caller-runs determine what happens to submitters; a semaphore bounds how many already running callers may enter at once, costs no extra threads and works with virtual threads.

3CoresemaphoresorderingNvidia
How do you make threads take turns with semaphores, for example N threads printing 1 to N in order, forever? Could you do it with one semaphore?
Model answer

A semaphore that starts at 0 is a "go" signal that is remembered: a release before the other thread waits is not lost, unlike notify. Give each thread its own semaphore. Thread i waits on its own, prints, then releases the next thread's. Only thread 0's semaphore starts with a permit.

With one semaphore you cannot say whose turn it is: a permit is anonymous. You would need a shared turn variable, and threads that are not next would take the permit, see it is not their turn, give it back and retry, which is a form of busy waiting. The clean single primitive answer is a mutex, one condition variable and a turn counter: each thread waits while turn != me, prints, advances turn, and calls notifyAll.

Likely follow up: "What goes wrong at the end?" If one thread stops early, the next one waits forever; require positive N and equal round counts, or publish cancellation and wake every waiter. Java interruption must propagate or trigger that shared cancellation; otherwise one departing thread strands the ring.

4Corelatchesbuild
Implement a CountDownLatch yourself.
Model answer

State: a count, guarded by a lock. countDown decrements it if positive, and when it reaches zero wakes all waiters, since they all wait for the same one-time event. await waits while the count is above zero. Once zero, it stays zero, so a later await returns at once: that memory is exactly what a bare condition variable lacks. The lock also gives the happens-before edge from the work before countDown to the code after await.

Likely follow up: "Why notifyAll here when a semaphore can use notify?" A latch opening releases every waiter at once; a semaphore release enables only one acquirer.

5SeniorlatchesexecutorsRubrik
submit(task) returns immediately and waitUntilComplete() must block until every submitted task has finished. Why is CountDownLatch a poor fit, and what do you use instead?
Model answer

A latch needs its count up front and works once. Here tasks keep arriving, possibly even while someone is waiting, and the call may be repeated. Use a pending counter guarded by a mutex, plus a condition:

  • submit increments pending before enqueueing; otherwise a fast worker could finish and drive the count to zero before it went up, waking waiters too early.
  • The worker decrements after the task, in finally, so failed tasks count too, and notifies all waiters at zero.
  • waitUntilComplete waits while pending > 0.

Submission uses nonblocking admission and rolls back rejection; blocking put would violate "returns immediately". The wait returns when it observes zero under the mutex, including children counted before their parents finish. It excludes submissions after that observation; a fixed batch needs a separate generation or submission fence. Java's Phaser (register per task, arriveAndDeregister on completion) also fits, but Rubrik often bans the library and has asked this exact API several times.

Likely follow up: "What if a task submits more tasks?" Children are counted correctly, but a task must not call this wait on its own executor: it would wait for its own completion. Endless new work can prevent zero.

6Seniorsemaphorespitfalls
What happens if a thread releases a semaphore it never acquired, or releases it twice?
Model answer

Java: Semaphore has no ownership, so release() normally adds a permit, although exceeding Integer.MAX_VALUE throws an Error; the count can grow past its starting value. A double release on an error path silently turns Semaphore(1) into a lock that admits two threads, or a limit of 10 into 11, then 12. Over-release within that representable range is not detected as an ownership error.

C++20: std::counting_semaphore::release beyond max() violates a precondition, giving undefined behavior. The template argument is a minimum supported maximum, not a runtime cap equal to the initial permit count.

Practices that prevent it:

  • Acquire, then try and finally with exactly one release.
  • Track it: set a local acquired flag right after acquire and release only if it is set; or return an RAII guard object from acquire.
  • Never release in both a catch and a finally.

A release by a different thread is legitimate in a signaling or resource-handoff protocol: ownership is an application rule, not a semaphore rule.

Likely follow up: "How would you notice the opposite bug, a leaked permit?" availablePermits() drifting toward zero under steady load, tryAcquire timeouts rising, or a debug wrapper that records which threads hold permits.

7Seniorbarriersjavacpp
What happens to a CyclicBarrier when one party is interrupted or times out, and how does C++ std::barrier differ?
Model answer

The Java barrier breaks: it becomes a broken barrier. The interrupted or timed out thread gets InterruptedException or TimeoutException; every other thread waiting in that round, and any that arrive later, get BrokenBarrierException; isBroken() returns true. The same happens if the barrier action throws. The reasoning is all or nothing: without it, the others would wait forever for a party that has left.

Recovery is your job: reset() breaks any current waiters and starts a new generation, but every party must agree on what happens next, so it is usually simpler to abandon the computation or create a new barrier.

C++20 std::barrier has no broken state, no timeouts and no interruption. A participant leaving before its arrival can call arrive_and_drop(), contributing its current arrival and reducing future participation. Do not drop twice in one phase or use a zero-participant barrier again. There is no automatic recovery from a missing arrival. Its completion function must not throw (the standard requires it to be invocable without exceptions).

Likely follow up: "Which do you prefer for a fragile workload?" Java's breaking barrier fails loudly; in C++ I would add my own timeout around the work, or use a latch per phase with a timed wait built from a mutex and condition variable.

8SeniorbarriersparallelRubrik
When is a barrier the right tool? Walk through a level-by-level parallel BFS.
Model answer

Use a barrier when work runs in phases and phase k plus 1 needs all of phase k finished: simulation ticks, iterative solvers, level-synchronous graph search. Rubrik has reported a hard graph question solved with threads doing BFS level by level, synchronized with a barrier.

The BFS:

  1. The frontier for the current level is split among T threads.
  2. Each thread expands its share. Marking a node visited must be an atomic check-and-set (a concurrent set's add, or a compare-and-swap on a per-node flag), so two threads never both claim a node. New nodes go into the next frontier.
  3. All threads hit the barrier. The barrier action, run once by the last arrival, swaps the next frontier in, increments the depth and sets done if the new frontier is empty.
  4. Everyone continues with the next level, or stops.

The barrier action's writes happen-before every thread's return from await, so plain fields work here. Costs: each level waits for its slowest thread (load imbalance), and for small frontiers the synchronization costs more than the work, so process small levels on one thread.

Likely follow up: "How else could you do it?" A shared work queue with level tags and a counter of outstanding nodes, or fork/join per level.

9Seniorjavaphaser
What does a Phaser add over CyclicBarrier and CountDownLatch?
Model answer

Dynamic membership and many phases in one object:

  • register() and bulkRegister(n) add parties while active; arriveAndDeregister() removes one.
  • arrive() signals without waiting (latch style); arriveAndAwaitAdvance() signals and waits (barrier style); awaitAdvance(phase) waits without being a party.
  • The phase number advances each time all registered parties arrive.
  • Override onAdvance(phase, registeredParties) to decide termination, for example after N phases or when no parties remain.
  • Phasers can be tiered into a tree to reduce contention when there are many parties; one phaser supports at most 65,535 parties.

The classic use is "wait until all spawned work is done" when the amount of work is unknown up front:

Requires a pool whose execute throws only before acceptance, such as ThreadPoolExecutor with AbortPolicy; avoid inline execution that propagates task failures. awaitAdvance and arriveAndAwaitAdvance are not interruptible waits; timed awaitAdvanceInterruptibly does not automatically break the phaser. Coordinate failure explicitly, for example with forceTermination(), and record task exceptions separately.

Likely follow up: "What is the phaser's equivalent in C++?" There is none in the standard; build it from a mutex and condition variable, or use std::barrier with arrive_and_drop when only leaving is dynamic.

10Corecppsynchronizers
Which synchronizers does the C++ standard library give you, and what do you do in C++17?
Model answer
  • <latch>: std::latch(n) with count_down(k), wait(), arrive_and_wait() and try_wait(). Single use.
  • <barrier>: std::barrier(n, completion) with arrive_and_wait() and arrive_and_drop(). Reusable; the completion function runs once per phase on one of the threads and must not throw.
  • <semaphore>: std::counting_semaphore<Max> and std::binary_semaphore with acquire, try_acquire, try_acquire_for, try_acquire_until and release(n).

Implementations usually build them on atomic wait and notify (futexes on Linux). Missing compared with Java: no Phaser, no broken barrier state, no fairness guarantee, no bulk acquire on semaphores. try_acquire and try_wait may fail spuriously, so false is not proof of unavailable capacity or an unopened latch.

C++17: write each one from a std::mutex and a std::condition_variable (10 to 20 lines each, and interviewers like seeing it), or use Boost. POSIX provides pthread_barrier_t and sem_t on supporting systems; macOS lacks pthread barriers and working unnamed sem_init semaphores. Mutex and condition-variable fallbacks are more portable.

Likely follow up: "Which would you use as a start gate so all threads begin together?" A std::latch(1) that the coordinator counts down once.

11Seniorsemaphoresfairnessjava
What does a fair Semaphore change, and why can acquire(5) wait forever on an unfair one?
Model answer

A non-fair semaphore (the default) lets an arriving thread take permits ahead of threads already queued: higher throughput. A fair one (new Semaphore(n, true)) hands permits to waiters in FIFO order. Even on a fair semaphore, the untimed tryAcquire() barges if permits are available; that is documented behavior.

Bulk acquires, as in a weighted semaphore, expose the difference. A thread calling acquire(5) on an unfair semaphore can starve: whenever a permit comes back, single-permit callers grab it first, and five are never free at once. On a fair semaphore the opposite happens: the head waiter needing five blocks everyone queued behind it, even small requests that could proceed, so permits sit idle (head-of-line blocking).

Choose fairness when starvation is unacceptable, typically for weighted budgets such as "at most 512 MB of request buffers in flight" with acquire(bytes). The default often wins on throughput, but equal-size requests can also starve; choose using the fairness requirement.

C++ std::counting_semaphore::acquire takes one permit at a time and fairness is unspecified, so a weighted, fair budget is built from a mutex, a condition variable and a FIFO queue of waiters.

Likely follow up: "What if a request is bigger than the whole budget?" It can never succeed, so reject it up front.

12Seniorsemaphoresmaps
Limit each user to at most 3 concurrent requests. How do you build per-key limits without leaking memory?
Model answer

The obvious version, map.computeIfAbsent(user, k -> new Semaphore(3)), never removes entries, so the map grows with every user ever seen. Removing a semaphore safely is the hard part: if you remove it when all permits are back, a thread that fetched the old semaphore a moment earlier can acquire on it while another thread creates a fresh one, and the user gets 6 slots.

A clean answer keeps a count per key and updates it atomically with compute, deleting the entry when it returns to zero; the per-key compute operations serialize admission and removal. Call exit exactly once after each successful entry, including exceptional exits.

Alternatives: a fixed array of N semaphores indexed by hash(user) % N (bounded memory, but colliding users share a limit, which is stricter than required), or lifecycle-managed entries that cannot expire while borrowed or awaited. Ordinary TTL eviction can recreate the same duplicate-limit bug. In C++, the same logic is an unordered_map<std::string, int> under a mutex (or sharded), erasing at zero.

Likely follow up: "Callers must wait instead of being rejected. Now what?" Keep the counts under one mutex with a condition variable: waiters for a user wait while that user's count is 3, and exit notifies all.

13Stretchjavarendezvous
What are Exchanger and SynchronousQueue, and when would you use them?
Model answer

A synchronous queue and an exchanger are both rendezvous points: two threads meet.

  • SynchronousQueue has no capacity at all: put blocks until a taker arrives and take blocks until a putter arrives, so it is a direct handoff. offer without waiting succeeds only if a taker is already waiting. Executors.newCachedThreadPool uses it: a submitted task goes straight to an idle worker, and if none is waiting, the offer fails and the pool creates a new thread.
  • Exchanger<V> lets two threads swap objects: exchange(x) blocks until the partner arrives and returns the partner's object. The textbook use is double buffering: a producer fills buffer A while a consumer drains buffer B, then they swap.

LinkedTransferQueue.transfer gives the same "wait until someone takes it" handoff on an ordinary unbounded queue.

C++ has neither in the standard library; both can be built with a mutex and condition variable, but cancellation and partner matching need an explicit state machine, or come from a channel library.

Likely follow up: "Why can newCachedThreadPool create thousands of threads?" A SynchronousQueue never holds tasks and the maximum pool size is Integer.MAX_VALUE, so under a burst of slow tasks every submission creates a new thread.

14Corelatchespitfalls
What happens if a CountDownLatch never reaches zero, and how do you prevent it?
Model answer

An untimed await() can block indefinitely unless interrupted; timed awaits return false on expiry. A thread dump shows threads WAITING in CountDownLatch.await. The usual causes:

  • A worker threw before calling countDown(), because countDown() was not in a finally block.
  • The count was set higher than the number of workers actually started: a pool rejected a submission, or a branch skipped the work.
  • A worker is itself stuck.

Preallocate the batch count before submission, then count down rejected or cancelled-before-start tasks exactly once; a worker's finally cannot cover work that never ran. Carry failures back: a latch only says "done", not "succeeded". Futures (invokeAll, CompletableFuture.allOf) carry exceptions as well.

C++20 std::latch has no timed wait (only try_wait), so if you need a timeout, use your own latch built on a condition variable with wait_for.

Likely follow up: "The latch reached zero but the results are wrong. Why?" A worker failed and still counted down; record failures separately and check them after await.

15Seniormemory-modelsynchronizers
What memory visibility do latches, barriers and semaphores guarantee?
Model answer

They are not just timing tools; each one creates happens-before edges, documented under "Memory consistency effects" in the Java API docs:

  • CountDownLatch: actions before countDown() happen-before actions after a successful return from await() in another thread.
  • CyclicBarrier: actions before await() happen-before the barrier action, which happens-before actions after await() returns in the other threads.
  • Semaphore: actions before release() happen-before actions after a successful acquire() in another thread.
  • C++20 gives the matching guarantees: latch countdowns publish to waits observing zero; barrier arrivals publish through phase completion to released waiters; semaphore release synchronizes with an acquisition observing its effect.

So workers can write results into plain arrays, signal, and the coordinator reads them without any other synchronization, as long as each worker writes its own slot:

The edge covers preceding writes, not later mutations. Initial semaphore permits do not publish a producer's later writes, and failed timed waits do not establish successful-acquisition edges.

Likely follow up: "Could a third thread read partial safely?" Only if it also passes through some edge after the latch opened, for example by awaiting the same latch.
