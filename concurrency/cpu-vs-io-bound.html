CPU bound versus I/O bound work

Is the work computing or waiting? The answer decides how many threads help, which threading model fits, and what to measure first.

Asked atDatabricksMeta
Before this:Concurrency versus parallelism

Before you choose a thread count, a pool size or an async framework, ask one question: is this work bound by the CPU, or by waiting? Interviewers ask it outright ("how do you know threads will help here?"), and the answer decides most of the design.

In plain words

A tailor's shop has four sewing machines. Stitching is limited by the machines: four tailors stitch four shirts at once, but a fifth tailor just waits for a free machine. That is CPU bound work, and the machines are your cores.

Now the shop orders cloth from suppliers, and each order takes days to arrive. While an order waits, the tailor can take measurements for other customers. The more orders that are waiting on suppliers, the more customers the shop can have in progress, and none of them needs a sewing machine while it waits. That is I/O bound work: more people in progress helps, until the suppliers themselves cannot keep up.

Two kinds of time

CPU bound work spends its time executing instructions: parsing, serializing, hashing, compressing, encrypting, sorting, resizing images, planning a query. It needs a core every moment it runs, so it can go only as fast as the cores you give it.

I/O bound work spends its time waiting: for a database to answer, a remote service to reply, a disk to read, an fsync to finish. While a thread waits it is blocked and uses no CPU at all, so other threads can use the core. Most request paths in real services are I/O bound: a typical API call might spend a few milliseconds computing and tens or hundreds of milliseconds waiting on its dependencies (orders of magnitude, not a benchmark).

The distinction matters because threads help the two kinds of work in completely different ways. For CPU bound work, threads are a way to use more cores, and once every core is busy, more threads only add overhead. For I/O bound work, threads are a way to have more waits in flight at once, and the limit comes from whatever you are waiting on.

Measure, do not guess: CPU time versus wall time

You classify work by comparing two clocks. Wall time is how long it took by the clock on the wall. CPU time is how long a core was actually executing it. If CPU time is close to wall time, the thread was computing. If CPU time is close to zero, it was waiting.

The ratio is the number to remember. Pure computing gives a ratio near 1. Pure waiting gives a ratio near 0. Real work is mixed: here the task computes for a third of its time and waits for two thirds. Call the waiting time W and the computing time C; the mixed task has W/C = 300 / 150 = 2, and that number tells you how many threads it can use, as you will see below.

In production you read the same signal from other tools: the time command (real time against user plus sys time), per-thread CPU in top, a profiler, or a thread dump where waiting threads sit in socket reads and lock waits while computing threads sit in your own code.

One trap when you read the ratio: a thread that is ready to run but waiting for a free core also collects wall time without CPU time. On an overloaded machine, CPU bound work therefore looks like waiting. Check the load average against the core count before you call it I/O.

See it: more threads help waiting, not computing

This program makes four tasks per core of each kind. CPU tasks do a fixed amount of arithmetic; I/O tasks wait 20 ms, standing in for a network call. Each kind runs twice: on as many threads as cores, then on four times as many.

Four times the threads made the CPU tasks no faster: 16 cores were already busy, so the extra threads only took turns on them. The same change made the I/O tasks about four times faster, because a waiting thread does not need a core: 64 threads keep 64 waits in flight at once. If you run it while the machine is busy with something else, the CPU numbers move around, but the pattern stays. For computing, the cores are the limit; for waiting, the number of waits in flight is the limit.

How many threads keep the cores busy?

Drag the sliders. Set the I/O wait to 0 and raise the thread count past the cores: useful CPU tops out at 100 percent and then slowly falls, because each extra thread only lengthens the queue for a core and adds switching. Then set the wait to 90 percent: you need about ten threads per core before the cores are busy, because each thread computes only a tenth of the time.

Loading the scheduler simulator

That intuition has a formula, from Brian Goetz's Java Concurrency in Practice:

Take 16 cores, a target of 80 percent CPU, and requests that wait 90 ms and compute 10 ms (W/C = 9): 16 × 0.8 × 10 = 128 threads. For pure computing W/C is 0 and the formula gives about one thread per core, as the demo showed. Goetz suggests cores plus one for a compute pool, so that a spare thread is ready when another stalls on a page fault.

The formula only tells you how many threads keep the CPU busy. It says nothing about what you are waiting on. If those requests wait on a database that allows 40 connections, the 128 threads simply queue for the 40 connections, and the extra 88 add memory and nothing else. The real limit is the smaller of what the CPU needs and what the dependency can take. You will size pools properly in sizing a pool, with Little's law (lesson 15-03) as the cross-check.

Mixed work: split it into stages

Real requests mix both kinds: parse the request (CPU), call two services (I/O), render a response (CPU). Running all of it on one pool sized for one kind is wrong for the other. The robust pattern is to give each kind its own home:

  • CPU heavy stages run on a pool sized to about the number of cores.
  • Waiting stages run on many threads, on virtual threads, or as non-blocking I/O on an event loop.
  • Every dependency gets its own limit (a connection pool or a semaphore), so one slow dependency cannot hold every thread.

The sin to avoid in every model: never block inside something sized for computing. A blocking call on an event loop freezes every connection on that loop. Blocking I/O inside Java's parallel streams starves the common ForkJoinPool. A slow remote call inside a pool sized to the cores leaves the cores idle while the queue grows. Lesson 15-01 turns this into the threading models used by real servers.

Other things work can be bound by

  • Lock bound. Threads wait on each other, not on I/O. CPU is low, threads are BLOCKED or WAITING on the same lock, and adding threads makes it worse because the critical section is serial. The fix is a smaller critical section or a split lock (lesson 04-06).
  • Memory bound. The CPU shows busy, but the cores are stalled waiting for data from RAM. More threads can saturate memory bandwidth and stop scaling well before the core count.
  • Downstream bound. Your service waits on a dependency that is already at capacity. More concurrency from you raises its latency for everyone. The fix is a limit and backpressure, not more threads.

High CPU does not prove the work is CPU bound in the useful sense: spinning loops, garbage collection and cache misses all show up as busy CPU. Look at what the threads are executing, not just at the percentage.

The class belongs to the work on this machine, not to the code. A file read served from the operating system's page cache is a memory copy that costs CPU, not a wait for the disk, so the same job can be I/O bound on a cold run and CPU bound on a warm one. A fast NVMe disk can likewise turn a decompression job from waiting into computing. Measure on realistic data and hardware.

Worked example: "how do you know threads will help?"

Databricks has asked this exact follow up after a single-threaded web crawler: a 2023 L5 candidate was asked how they knew multithreading would help before writing the multithreaded version, and a 2023 SDE-2 candidate was asked about thread pool size, dataset size and disk and network bottlenecks. Here is the reasoning an interviewer wants to hear.

  1. Classify the stages. Fetching a page is I/O: tens to hundreds of milliseconds of network wait (order of magnitude). Parsing links out of the page is CPU: typically a few milliseconds. So fetching dominates, and its CPU/wall ratio is tiny.
  2. Estimate W/C. Say 200 ms of waiting and 4 ms of parsing per page: W/C = 50. On 8 cores the formula allows 8 × (1 + 50), roughly 400 threads before the CPU becomes the limit. So the CPU is not the bottleneck; something else will be.
  3. Find the real limit. Politeness: crawling one host with 400 parallel requests gets you blocked, so cap requests per host. Network bandwidth and the remote servers' rate limits. File descriptors and memory for open connections. The shared visited set, which becomes a contended lock if every thread hits it for every link.
  4. Pick and verify. Start with a pool of, say, 32 to 64 fetchers, a per-host limit, and a concurrent visited set. Measure pages per second and CPU use as you raise the pool; stop where throughput stops rising or a limit is hit.

The answer that scores is not a number. It is the reasoning: the work is mostly waiting, so threads help; the limit comes from the network and the remote hosts, not the cores; and I would measure. You will build this crawler in the web crawler lesson.

Common mistakes

  • Sizing an I/O pool to the core count. Eight threads on eight cores, each waiting 90 percent of the time, leave the CPU mostly idle while requests queue.
  • Sizing a CPU pool in the hundreds. Computing threads beyond the cores take turns, pay context switches and evict each other's cache lines. Throughput stays flat and latency rises.
  • Blocking where only computing belongs. A database call on an event loop thread, in a parallel stream, or in a pool sized for CPU work stalls everything else that shares it.
  • Trusting the formula over the dependency. The thread count that keeps the CPU busy can be far more than the database or the remote API can serve. The smaller limit wins.
  • "CPU is at 100 percent, so we are CPU bound." Check whether that CPU is useful work. Spin loops, garbage collection and memory stalls look the same on a dashboard.
  • "async makes slow computation faster." Async helps you wait without holding a thread. A 50 ms computation still needs 50 ms of a core.

In the interview

The question arrives as a follow up: "How do you know multithreading will help here?" (Databricks, after a crawler), "Thread pool size versus dataset size?" (Databricks), or "How many threads would you want, what is a safe number?" (Meta, for a file downloader in a design round). It also hides inside every pool sizing and server design question.

First I would classify the critical path. If it is CPU bound, threads only help up to the number of cores, so I would size the pool to about the core count and look for algorithmic wins. If it is I/O bound, threads help because the waits overlap, roughly cores times one plus the wait to compute ratio, but my real limit comes from what the dependency can take, so I would cap concurrency at that, with a connection pool or a semaphore, and verify with measurements: CPU time against wall time, and throughput as I raise the limit.

Follow ups to expect: "What if the work is mixed?" (split the stages and give each its own pool and limit); "What happens if you add more threads anyway?" (for CPU work, switching and cache misses; for I/O work, more pressure on a saturated dependency and longer queues there); "How would you measure it?" (CPU time against wall time per request, thread states in a dump, a profiler that can see waiting time).

Senior depth

A normal CPU profiler samples threads that are running on a core, so it only sees on-CPU time. For an I/O bound request that takes 800 ms with 20 ms of CPU, a CPU profile shows you the 20 ms beautifully and says nothing about the 780 ms of waiting. To see where the time goes you need wall clock profiling (async-profiler has a wall clock mode for Java) or off-CPU analysis (tracing where threads block, as Brendan Gregg describes it for Linux). Saying "the CPU profile cannot explain this latency because the request is mostly off CPU" is a strong senior signal in a debugging discussion.

Cheap threads change one part of this lesson and not the other. Java virtual threads and goroutines make it cheap to have thousands of waits in flight, so the "how many threads for I/O" question mostly disappears. The "what can the dependency take" question does not: you still bound concurrency explicitly, as lesson 01-07 shows. One Java 21 caveat: a virtual thread that blocks inside a synchronized block pins its carrier thread, so blocking I/O under synchronized quietly brings back a small, core sized pool. JDK 24 removed that pinning, but on Java 21 prefer a ReentrantLock around blocking calls.

Key takeaways

  • CPU bound work computes; I/O bound work waits. Classify by measuring CPU time against wall time.
  • For CPU bound work, threads beyond the core count add overhead and no throughput.
  • For I/O bound work, threads help because waits overlap: about cores × (1 + W/C) threads keep the CPU busy.
  • The dependency you wait on usually sets the real limit; cap concurrency at what it can take.
  • Split mixed work into stages, and never block inside a pool or loop sized for computing.

Why. User plus sys is the CPU time used by all threads together: half a second over ten seconds of wall time. The cores were idle most of the time, so the job was waiting. A CPU bound job on several cores shows user time close to, or above, real time.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
Each request computes for 5 ms and waits 45 ms on a database. The server has 8 cores, and you want CPU at about 75 percent. (1) How many threads does the sizing formula suggest? (2) The database connection pool has 40 connections. What throughput can the system reach, what is the bottleneck, and how many worker threads would you actually run?
Model answer

(1) W/C = 45 / 5 = 9. Threads = 8 × 0.75 × (1 + 9) = 60.

(2) Each connection is busy for 45 ms per request, so one connection serves about 1000 / 45, roughly 22 requests a second, and 40 connections serve about 890 requests a second. The CPU, at 5 ms per request on 8 cores at 75 percent, could do 8 × 0.75 × 1000 / 5 = 1,200 requests a second. So the database connections are the bottleneck, at about 890 requests a second.

Little's law gives the worker count, assuming a request holds its connection only during the 45 ms query: about 890 requests a second, each holding a worker for 50 ms, keeps about 890 × 0.05, roughly 45 workers busy, 40 of them inside the database and about 5 computing. So 60 workers would leave about 15 waiting for a connection at full load. I would run about 45 workers, or keep 60 but give the wait for a connection a timeout, and watch the pool's wait time. To go faster, the lever is the database side (more connections if the database can take them, or shorter queries), not more threads.

Explain
You wrote a single-threaded web crawler. The interviewer asks: "How do you know multithreading will make it faster, and how many threads would you use?" Answer as you would out loud.
Model answer

I would start by classifying the work. Each page is a network fetch followed by parsing. The fetch is I/O: the thread spends tens to hundreds of milliseconds waiting for the remote server and almost no CPU. Parsing is CPU, but only a few milliseconds per page. So the crawler is I/O bound, and threads will help, because many fetches can be waiting at the same time while the CPU stays mostly idle. I would confirm it by measuring: CPU time per page against wall time per page, which I expect to be a small ratio.

For the number, the formula cores × (1 + W/C) with something like 200 ms of waiting and 4 ms of parsing allows hundreds of threads before the CPU is the limit, so the CPU will not be my bottleneck. The real limits are elsewhere: politeness and rate limits per host, network bandwidth, open connections, and contention on the shared visited set. So I would start with a pool of 32 to 64 fetchers, a per-host concurrency limit, and a concurrent visited set, then raise the pool while watching pages per second and stop when throughput flattens or a host starts throttling.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

"Here is a symptom: p99 latency went from 50 milliseconds to 800, CPU is at 5 percent, and the team wants to double the thread pool. What do you check first?"
What a strong answer covers
  • Low CPU with high latency means the threads are waiting, not computing, so cores are not the limit
  • Take a few thread dumps and see where threads wait: one dependency's socket read, a connection pool, or a lock
  • Check that dependency's latency and saturation; it is probably the real bottleneck

How a senior would say it
I would not double the pool yet. CPU at 5 percent with latency up sixteen times tells me the threads are waiting, not computing, so the cores are not the limit. First I would take three or four thread dumps a few seconds apart and look at where the threads sit. If most of them are in a socket read to the same downstream, or waiting to borrow a database connection, or blocked on one lock, that is my bottleneck. Then I would check that dependency's own numbers: its latency, its errors, its connection count. If it is saturated, doubling our threads only sends it more concurrent work, so its queue grows and everyone gets slower. I would not trust a CPU profile here either. It only samples threads that are on a core, so it shows the small slice of parsing and misses most of the 800 milliseconds. The fix is usually the opposite of more threads: cap concurrency to that dependency at what it can serve, with a semaphore or the connection pool, put a timeout on every call, and shed the excess, so one slow dependency cannot hold every thread.

Likely follow up: The dumps show threads waiting to borrow from our own connection pool, and the database looks idle. What now?

How a senior would say it
I would size them differently because they spend their time differently. Thumbnails are CPU bound: decoding, resizing and encoding an image keeps a core busy the whole time. The aggregator is I/O bound: each request computes for a few milliseconds and waits much longer on the three APIs. With 8 cores and requests that wait twenty times longer than they compute, that is roughly 170 threads to keep the CPU busy. But that number only describes my CPU. Each downstream has its own limit, so I would put a semaphore or a connection pool per dependency, sized to what it can serve, so one slow API cannot hold every thread. "How would you tell whether a piece of work is CPU bound or I/O bound, without guessing?"
What a strong answer covers
  • Compare CPU time with wall time for the same work
  • A ratio near 1 means computing; near 0 means waiting, and the ratio says how much
  • Tools: time (real against user plus sys), per thread CPU in top, ThreadMXBean or the thread CPU clock in C++
  • Thread dumps show what the waiting threads wait for: socket reads, pool borrows, locks
  • Two traps: waiting for a core on an overloaded machine looks like I/O, and spinning or GC looks like computing
How a senior would say it
I measure two clocks and compare them. Wall time is how long the work took. CPU time is how long a core was actually executing it. If the two are close, the work is computing, so it is CPU bound. If CPU time is a small fraction of wall time, it spent most of its life waiting, so it is I/O bound, and the ratio tells me how much. For a whole program I run time and compare real with user plus sys. Per thread, I read ThreadMXBean in Java or the thread CPU clock in C++, or look at per thread CPU in top. A few thread dumps then tell me what the waiting threads wait for: a socket read, a connection pool, a lock. There are two traps. On an overloaded machine, a thread waiting for a free core also looks like waiting, so I check the load against the core count. And busy CPU is not always useful work: spinning, garbage collection and cache misses all look busy.

Likely follow up: The work turns out to be mostly waiting. Would switching to async I/O make it faster than threads?
