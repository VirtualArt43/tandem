Room booking

Thread-safe designsmedium45 minUberFlipkartPhonePe

Two users can both see an empty calendar. Checking the interval and claiming it must be one operation for that room.

The task

Complete the existing per-room scheduler and its other language. There are N rooms numbered from zero. book(start, end) scans them in increasing order and returns a booking in a room where the interval fits, or none. bookRoom targets a particular room. cancel releases a booking by its unique opaque ID.

Rules

  • Intervals are half open: [0, 10) and [10, 20) do not overlap. Require start &lt; end, positive room count and a valid room index. Timestamps are supplied values, not wall-clock reads. IDs do not wrap during the exercise.
  • Overlap checking and insertion are atomic under that room's lock. Use predecessor and successor intervals in its ordered calendar. Different rooms must progress concurrently; do not guard the whole scheduler with one mutex.
  • Cancel returns true exactly once for an existing ID, false for an unknown or already cancelled ID. Its successful return means the interval is free.
  • The supplied audit log is thread safe, nonthrowing and nonreentrant. Each change is logged exactly once, in change order within that room, before the method returns. A slow log for one room must not block another room. Keep this existing API.
  • The ascending scan has no atomic snapshot across all rooms. With concurrent cancels, none means each visited room conflicted when examined. With no cancels, every failed booking must still have a conflict in every room in the final calendar.

Worked example

Book [0, 10) and [10, 20) in room zero. A request for [5, 15) uses room one. Cancelling the first booking makes [0, 10) available again in room zero.

What the tests check

  • Half-open boundaries, first-fit selection, rejection when every room conflicts and cancellation freeing an interval.
  • Two slow audit callbacks overlap on separate rooms, measured by an active counter.
  • Eight seeded callers submit random intervals; the audit ledger detects overlap and duplicate IDs, and checks every rejected interval against final bookings without cancels.
  • Eight concurrent cancellations have one winner. Timed joins and watchdogs bound deadlocks.

Taught in: Design cases: seats, flash sales, schedulers and counters

Open them one at a time. Each one gives away a little more.

For an ordered calendar, only the predecessor at start and the next booking can conflict.
The lock must cover both the overlap decision and insertion. A read lock followed later by a write lock leaves a gap.
Keep cancellation lookup separate from room mutation. Never hold an index lock while waiting for a room if booking takes them in the reverse order.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What did Uber ask beyond the basic room allocator?
The 2024 report adds cancellation and a multithreading follow-up. Another 2024 scheduler report includes audit logs, which explains the retained log API here.
What happens with 10,000 concurrent requests?
The 2025 Uber report asks about that bottleneck. Ascending scans concentrate work on low-numbered rooms and sorting indexes still need atomic updates. Consider availability indexes or partitioned candidate selection, then state the weaker first-fit guarantee.
How do you book several rooms all or nothing?
Sort and deduplicate the room IDs, acquire their locks in increasing order, validate every interval, then insert all or none. Emit audit records with a transaction ID; partial audit failure needs a durable protocol beyond the nonthrowing exercise log.
Can the log be asynchronous?
Enqueue an ordered per-room event while holding the room lock, then flush outside it. Specify durability, backpressure and close semantics; returning before a durable log changes the API guarantee.
How does this work across servers?
In-process locks do not coordinate different instances. Use transactional storage or versioned conditional writes on the room calendar, plus idempotency keys for request retries.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

Key idea and invariants

Each room calendar contains nonoverlapping intervals. Its lock protects the predecessor/successor check and insertion as one operation. An ID points to one booking; cancellation claims that identity once before removing its calendar interval. The completed Java design is retained; C++ encodes the room in opaque IDs and keeps cancellation lookup under that room's lock.

Why these primitives

One mutex or monitor per room keeps unrelated calendars independent. Java uses a concurrent ID index and an atomic ID counter; C++ uses a per-room ID index and an atomic ticket counter. Neither requires holding a global scheduling lock. The log executes under its room lock to preserve the specified log order, with an explicit nonreentrant, nonthrowing contract.

Pitfalls and broken interleaving

The broken implementation releases protection after checking availability, then acquires exclusive access to insert without checking again. Both callers can approve the same interval. Individually synchronized map accesses do not protect the cross-step decision.

Cost and interview explanation

Checking and inserting in one room is O(log B) for B bookings; a full scan is O(N log B). Say: “I will make each room's availability check and insertion indivisible. The scan does not promise a global snapshot during cancellation, and I will define audit ordering before moving logging outside a lock.”
