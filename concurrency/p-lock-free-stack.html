A lock-free stack

Build a primitivesenior45 minRubrik system coding follow upRubrik

A Rubrik thread-safe stack round ended with a follow up to make the stack lock-free with CAS, and the candidate in that report could not finish it in time. This is that follow up done properly: the Treiber stack, plus the two traps that sink most attempts, ABA and freeing a node that another thread is still reading.

The task

Build a stack that many threads can push to and pop from at the same time, without any lock. The only shared variable is an atomic pointer to the top node, and the only way to change it is compare-and-swap.

  • push(value) puts a value on top.
  • pop() removes and returns the top value, or returns none when the stack is empty: null in Java, std::nullopt in C++.

Rules:

  • No locks of any kind: no synchronized, no ReentrantLock, no std::mutex and friends, and no library concurrent collections. Java: AtomicReference. C++: std::atomic with compare_exchange_weak or compare_exchange_strong.
  • Each push allocates a new node; nodes are never reused for another value.
  • C++: never free a popped node while the stack is alive. Keep popped nodes on a retired list and free them, together with any nodes still on the stack, in the destructor. The notes explain why this is the honest answer in an interview, and what production code does instead.

What the tests check

  • LIFO order from one thread, and pop on an empty stack returns none, also after the stack has been emptied and refilled.
  • A stress run with 4 pushers and 4 poppers on one stack: every value comes out exactly once, nothing lost and nothing duplicated.
  • Push then pop: 4 threads each push a value and then pop, many times over, on a stack that is almost always nearly empty. Because every thread pushes before it pops, a correct stack is never empty at that pop. The test checks that pop never returns none and that every value comes out exactly once.
  • C++: once the stack is destroyed, every value object it held has been destroyed too, popped or not.
  • C++: ThreadSanitizer stays quiet, which it will not if a node is freed while another thread can still read it.

Taught in: A lock-free stack and the ABA problem

Open them one at a time. Each one gives away a little more.

Keep one atomic reference to the top node. Every change has the same shape: read the head, build what the new head should be, and compare-and-swap it in. If the CAS fails, another thread changed the head first, so read it again and retry.
push: create the node once, then loop: set node.next to the current head and CAS the head from that value to the node. pop: loop: read the head; if it is null the stack is empty; otherwise CAS the head from that node to node.next, and on success return the node's value.
C++ only. In pop you read old->next before your CAS, while another thread may pop old at the same moment. If that thread freed old, your read touches freed memory; if the allocator then reuses the address for a new node, your CAS can succeed against the wrong node (ABA). So do not free: push each popped node onto a second lock-free list with its own link field (another thread may still read next), and free both lists in the destructor.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What is the ABA problem, exactly?
Thread 1 reads head A and A's next, B, then stalls. Thread 2 pops A, pops B, frees A, and pushes a new node that happens to get A's old address. The head is "A" again, with a different next. Thread 1 wakes up, its CAS compares only the pointer value, sees A, and succeeds, installing B, which has been freed. The CAS checked "same pointer", not "nothing changed".
How do real systems free nodes safely?
With safe memory reclamation. Hazard pointers: each thread publishes the pointer it is about to dereference, and a retired node is freed only when no hazard pointer names it (C++26 adds std::hazard_pointer). Epoch based reclamation: threads announce the epoch they entered in, and a node retired in epoch e is freed once every thread has moved past e. Others are RCU and split reference counts. Java gets this for free: the garbage collector never frees a node that any thread can still reach, so an address cannot be reused while you hold it.
Does a version counter fix ABA?
It fixes the comparison. Pack a counter next to the pointer and CAS both together (a double-width CAS, or spare bits in a 64-bit word); every change bumps the counter, so a recycled address no longer matches. It does not fix use-after-free: a slow thread still reads old->next from memory that may already be gone. Java offers AtomicStampedReference for the same idea.
Is this stack lock-free or wait-free?
Lock-free: a CAS fails only because another thread's CAS succeeded, so the system as a whole always makes progress. A particular thread can, in theory, retry forever, so it is not wait-free. Under heavy contention every thread hammers one cache line; elimination backoff, where a pusher and a popper meet in a side array and cancel out, is the known way to scale it.
Why release on push and acquire on pop?
The pusher writes the node's value and next pointer, then publishes the node with its CAS. A release CAS makes those writes visible to any thread whose acquire load or CAS later reads that head. Without it a popper could see the new pointer but stale node contents. In Java, AtomicReference.compareAndSet has volatile semantics, which already gives this ordering.
When would you not use a lock-free stack?
Most of the time. A mutex around a vector is simpler, has no reclamation problem, and is often as fast at low contention. Lock-free code pays off when threads must never block (signal handlers, real-time paths, a holder that might be descheduled) or under extreme contention with a careful design. Say that you would measure first, and be ready to justify every line of the lock-free version.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

This is the Treiber stack. The whole state is one atomic pointer to the top node, and every operation is a read, compute, compare-and-swap, retry loop. The CAS succeeds only if the head is still exactly what you read, so a successful CAS means nobody changed the stack in between, and a failed one means someone did, so you read again.

  • Push. Allocate the node once. Loop: point node.next at the current head, then CAS the head from that value to the node. The node is private until the CAS succeeds, so writing its fields needs no protection.
  • Pop. Loop: read the head; if null, return none. Otherwise CAS the head from that node to its next. The thread whose CAS succeeds owns the node and is the only one that reads its value.

Why C++ must not free popped nodes here

Between reading old and its CAS, a popper dereferences old to read old->next. Another popper can pop old in that window. Freeing it then causes two separate disasters:

  • Use-after-free. The slow popper reads old->next from freed memory. ThreadSanitizer reports this as a race between the free and the read.
  • ABA. If the allocator hands the same address to a new node, the slow popper's CAS sees the "same" head and succeeds, installing a stale next pointer.

Keeping popped nodes on a retired list and freeing everything in the destructor removes both problems, at the cost of memory that grows with the number of pops. That is the honest interview answer; production code replaces the retired list with hazard pointers or epochs, which free a node once no thread can be holding it. The retired list needs its own link field, because a slow popper may still read next of a node that has just been retired.

Java does not have this problem. A node stays alive as long as any thread holds a reference to it, so its address cannot be reused while a slow popper is looking at it, and ABA on node references cannot happen when every push allocates a fresh node.

Memory ordering

Push uses a release CAS: the node's value and next pointer are written before it, so any thread that later reads the new head with acquire sees them. Pop loads the head with acquire, and its CAS uses acquire too (on success and on failure), so the old->next it reads and the value it moves out are the ones the pusher wrote. Java's compareAndSet and get are volatile operations, which give the same guarantees.

Cost

Each operation is O(1) when uncontended. Under contention, failed CASes are retried, and all threads fight over one cache line, so throughput can drop below a simple lock. The structure is lock-free (some thread always finishes) but not wait-free (one thread can be unlucky indefinitely).

How to say it in the interview

The stack is one atomic head pointer. Push builds the node privately, then loops: point next at the head and CAS the head to the node. Pop loops: read the head, return empty if null, otherwise CAS the head to head next; whoever wins the CAS owns the node. In C++ the hard part is memory: a slow popper may still read a node another thread has popped, so I never free popped nodes while the stack is alive. I keep them on a retired list and free them in the destructor. In production I would use hazard pointers or epoch based reclamation, and that same discipline also prevents ABA.
