Fair connection pool

Concurrent systemsmedium35 minClassic resource pool design

A connection pool must track which objects are borrowed as well as how much capacity is free. This exercise combines timed borrowing, first come, first served handoff, cancellation and release validation without ever losing or duplicating a connection.

The task

Build a thread-safe pool over a fixed list of N distinct, nonnull connection objects. N may be zero. Copy the list's membership; in C++ the caller keeps the connections alive until all pool operations have finished. Connection IDs are labels and need not be unique: membership and ownership use object identity (pointer identity in C++), never id(), equals or hashCode.

  • borrow(timeout) returns a free connection at once if nobody is ahead of it. Otherwise it waits up to timeout milliseconds (0 means do not wait) and returns null (nullptr in C++) if no connection is assigned. Inputs are nonnegative, including Long.MAX_VALUE in Java and INT_MAX in C++; converting the timeout must not overflow.
  • A connection is never held by two borrowers at once, so never more than N are out.
  • First come, first served: when a connection is released, the oldest registered waiter gets it. Registration order is established under the pool lock, not by thread creation time. A borrow that arrives while others are waiting must not take a connection ahead of them, even with a timeout of 0.
  • A borrower that times out leaves the queue without disturbing the order of the remaining waiters. Assignment and cancellation are atomic alternatives under the pool lock: if assignment wins the race with the deadline, the borrower may return that connection. Otherwise it returns nothing and cannot consume a later release.
  • In Java, a preinterrupted caller throws InterruptedException even if a connection is idle. Interruption during a wait propagates and removes the waiter. When interruption races assignment, success or interruption is allowed, but a connection assigned to a cancelled waiter must be passed on or made idle, never lost.
  • release(c) throws (IllegalStateException in Java, std::logic_error in C++) if c is not currently borrowed from this pool: an idle connection, a double release, a foreign connection, or null (nullptr). Rejection leaves all pool state unchanged. If two threads release the same loan with no intervening reassignment, exactly one succeeds.
  • available() returns an atomic snapshot of the number of idle connections. A connection reserved for a waiter is not idle.
  • waiting() returns an atomic snapshot of registered borrowers not yet assigned a connection. Timed out and interrupted borrowers are removed before their calls finish. This diagnostic lets the tests establish queue order without guessing how long a thread takes to start.

The timeout bounds the wait for a connection after entering the pool's critical section; scheduling and lock reacquisition can delay the actual return. The raw-reference API cannot distinguish an old loan from a later loan of the same object. Callers must not release stale references after reassignment; generation-tagged leases are a follow up below. Closing the pool, health checks and reclaiming loans are follow ups, not part of this API.

Worked example: barging

A pool of 1. Thread W has waited 2 seconds for the connection. The holder releases it and signals W. Before W is scheduled and takes the lock, thread B calls borrow(0), sees an idle connection and takes it. W wakes, finds nothing, and waits again: it was overtaken by a thread that arrived two seconds later. Under steady load this can happen to W again and again, which is starvation. The fix is a direct handoff: release gives the connection to W itself, so it never becomes idle for B to grab.

What the tests check

  • Full inventory can be borrowed, exhausted with borrow(0), released and borrowed again. Changing the input list after construction does not change pool membership. Every returned object is one of the original objects, even when all IDs and Java equality values match.
  • Releasing an idle, foreign, equal-valued, already released or null connection throws the specified exception without corrupting later operations.
  • An empty pool stays empty; a positive timeout waits for its budget, while a zero timeout returns promptly. The largest supported timeout still waits and wakes correctly.
  • A release promptly wakes a registered waiter. Four waiters registered in order receive the connection in that order while a zero timeout borrower tries to barge.
  • Timeouts remove the head, middle and tail of a three-waiter queue. The two survivors retain their order and the full inventory is recovered.
  • Java additionally tests interruption at each queue position, preinterrupted borrowing, and 24 races between interruption and handoff. Either permitted race outcome must conserve the connection and let the next waiter progress.
  • Two threads release the same loan in 100 rounds without an intervening reborrow: exactly one succeeds per round.
  • 12 workers make 1,200 attempts on four connections with short timeouts and seeds 7 to 18. A concurrent observer checks both counts; no connection is shared, capacity is bounded, and the exact original inventory is reusable afterwards.
  • Worker exceptions fail the run. Timed joins and a global watchdog bound failures; C++ also runs under ThreadSanitizer. Stress and the interruption race sample schedules rather than proving every possible interleaving.

Taught in: Semaphores: permits as a resource limit

Open them one at a time. Each one gives away a little more.

Keep the state in one monitor: a list of idle connections, a set of borrowed connections (by identity), and a queue of waiting borrowers. release checks that the connection is in the borrowed set before doing anything else; that one check catches double and foreign releases, even when two threads race.
For fairness, do not let a woken waiter compete for the connection. Give each waiter its own small record (a slot for the connection and its own condition). release takes the oldest waiter from the queue, puts the connection in its slot and signals only that waiter. borrow takes an idle connection directly only when no one is waiting.
A waiter loops until its slot is filled or the deadline passes. When it gives up, it removes its record from the queue while still holding the lock, so release can never hand it a connection afterwards. In Java, if it is interrupted after a connection was handed to it, pass that connection on instead of dropping it. In C++, notify the waiter's condition variable while holding the mutex, because the waiter may destroy it as soon as it can return.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Could you build it with a semaphore?
Yes: a semaphore with N permits plus a thread-safe queue of idle connections. Borrow acquires a permit (with a timeout) and then takes a connection; release returns the connection and then a permit. In Java use new Semaphore(n, true) for fairness, and note that tryAcquire() with no arguments barges even on a fair semaphore, while tryAcquire(0, unit) respects the queue. You still need the identity-based borrowed set, because a Java semaphore accepts an extra release. Exact waiting() and available() snapshots also require coordinated bookkeeping for queued requests and reserved connections; a semaphore's approximate queue-length diagnostic is not enough.
What does fairness cost?
Throughput. A handoff means the connection waits idle until the chosen thread is scheduled, whereas a barging thread that is already running could have used it at once. That is why ReentrantLock and Semaphore are unfair by default. Choose based on the contract and measured latency. This exercise requires FIFO; production pools make different throughput and latency trade offs.
A connection may be broken when it comes back. What would you add?
Validation: check the connection on release (or before handing it out, or periodically for idle ones), close a broken one and create a replacement, keeping the count of N. Do the check outside the pool lock, since it may do network I/O.
A caller forgets to release. How would you detect and reclaim leaked connections?
Record the borrow time, a loan generation and optionally the borrower's stack trace. A timeout is evidence of a possible leak, not proof that the caller stopped using the connection: never hand the same live connection to a second borrower merely because its lease expired. Cancel or fence the old loan, retire or close its physical connection, and create a replacement within the capacity budget. A lease wrapper containing the pool, connection and generation lets a stale close be rejected. Java try-with-resources and a C++ RAII guard make ordinary release exception safe.
How would explicit connection states and shutdown change the design?
Track idle, leased, validating, retiring and closed states under the pool lock; waiting belongs to requests. Reserve capacity before creating or replacing a connection, and do network work outside the lock. On shutdown reject new borrows, wake every waiter with a defined closed result, close idle connections, and retire outstanding loans when returned. Keep borrow deadlines separate from maximum loan age. Closing a connection does not necessarily stop already submitted database work, so cancellation or fencing must match the downstream protocol.
How is a pool size like this chosen?
By the downstream limit, not by thread count: the database can serve only so many concurrent queries well. Little's law gives a starting point: connections needed is roughly request rate times time each connection is held. A bounded pool also acts as a bulkhead, so one slow dependency cannot absorb every thread.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

The pool is one monitor holding three collections: idle connections, borrowed connections, and waiting borrowers in arrival order. The key decision is direct handoff: a released connection goes straight into the oldest waiter's slot and is marked borrowed in the same critical section, so it is never idle while someone waits. That gives strict first come, first served and makes the timeout race harmless.

Invariants

  • Every connection is in exactly one place: idle, or borrowed (possibly sitting in a waiter's slot, about to be returned to it).
  • If any borrower is waiting, the idle list is empty.
  • A waiter in the queue has an empty slot; a waiter that leaves the queue on timeout has an empty slot, so nothing is lost.

Why each primitive

  • One lock, because a release must atomically check the borrowed set, pick a waiter and move the connection.
  • A condition per waiter, so release wakes exactly the chosen borrower instead of waking everyone to fight.
  • An identity set of borrowed connections, so validation does not depend on how the caller implemented equals or hashCode.
  • awaitNanos or wait_until with a predicate, so spurious wakeups and the deadline are both handled.

Pitfalls

  • Trusting release: a double release silently grows the idle list and can hand one connection to two borrowers. The broken version retains the FIFO monitor but deliberately skips validation; the tests reject it.
  • signal plus "the woken thread takes from the idle list": a running thread barges in between.
  • A waiter that times out or is interrupted without leaving the queue: the next release hands the connection to nobody. Removing the wrong queue entry can instead strand a live waiter.
  • Notifying a waiter's stack allocated condition variable after unlocking (C++): the waiter may already have returned.
  • Doing slow work (validation, reconnecting) while holding the pool lock.

Cost

borrow and release take expected amortized O(1) work under the lock, excluding waiting, allocation and hash-table growth. Removing a timed out or interrupted waiter is O(waiters) with these queues. Both diagnostic counts are O(1). Space is O(N + waiters).

How to say it in the interview

It is a monitor with idle connections, a borrowed set and a FIFO queue of waiters. Borrow takes an idle connection only if nobody is waiting; otherwise it enqueues a waiter record and waits on that record's own condition with a deadline. Release first checks the borrowed set, which rejects double and foreign releases, then hands the connection directly to the oldest waiter or puts it back. Direct handoff means no thread can barge in, and a waiter that times out removes itself under the lock, so no connection is ever handed to someone who left. A fair semaphore plus a borrowed set is the shorter alternative.
