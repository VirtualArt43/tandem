Ongoing requests tracker

Thread-safe structuresmedium40 minUberGoogleRubrik

A counter is not enough when responses can be duplicated or arrive before requests. Track request identity and active-client membership as one transition.

The task

Requests are identified by the pair (request, client). Any long request and any int client is valid, including negative and extreme values, and the same request number under two clients is two identities. The first request for an unseen pair makes it active. A response completes it, even if no request has arrived yet. Further requests and responses for a completed pair are ignored. Duplicate active requests do not increment again. IDs are not reused during this tracker's lifetime.

  • Each operation is linearizable, including when a request and its response, or two copies of either, arrive on different threads at the same moment. Counts never become negative and equal the number of active identities for that client.
  • Remove a client from the active-count map exactly when its count reaches zero. Keep completed request tombstones separately, because otherwise a late request or response cannot be deduplicated.
  • getOngoingRequests returns zero for an absent client. hasActiveClient is a synchronized diagnostic that distinguishes an absent entry from a retained zero entry.
  • Every processRequest and processResponse call invokes the nonthrowing, nonreentrant test hook entered(client) exactly once, while it holds the protection for that update: another update of the same identity must wait until the hook returns. The two reads do not call it. Production passes a no-op. Independent clients should not require one global update lock.

Example: response 42 for client 7 arrives first. The count remains zero; a later request 42 for client 7 also leaves it zero. Request 42 for client 8 is a different identity.

What the tests check

  • Duplicate requests and responses, a duplicated response before its request, replay after completion, zero for an absent client.
  • Identity is the whole pair: request 42 on clients 7, 8, 23 (which shares a stripe with 7 when there are 16 stripes) and -9, requests that differ only above bit 32, negative and extreme ids.
  • The hook runs exactly once per update, and a request for the same identity waits while a response is blocked inside its hook.
  • Gated updates to independent clients overlap.
  • Eight-thread storms produce exact counts and no negative observations.
  • Zero-count clients disappear without losing a concurrent new increment.
  • Same identity races: up to a few thousand rounds release two requests and two responses for one fresh identity at the same instant while readers poll. A count above one, below zero, or not zero once a response has returned fails, so does a client left active after the round. This is what catches a transition split into two atomic steps.
  • Java only: a reader polls a client whose count never changes while another thread grows the same stripe, which catches unsynchronized reads of a plain HashMap. In C++, ThreadSanitizer reports them.
  • Spin barriers, time limits on every wait, a watchdog and bounded joins turn a hang into a failure.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why was ConcurrentHashMap.compute alone insufficient in the Uber report?
The report says the candidate used compute and was rejected; it does not prove a particular missing fix. A count-only solution cannot distinguish duplicate or reordered events. Another common gap: one compute on the request map and a second compute or merge on the count map are each atomic, but not together. A response can complete the identity and find no count to decrement before the request's increment lands, leaving a completed request counted forever. Explain the request-state invariant as well as the map operation, and do the count change inside the same critical section, or inside the identity's compute.
Can completed tombstones be deleted?
Only with a documented bound on replay and lateness, an epoch, or an external durable deduplication source. Exact lifetime-long deduplication requires retaining enough identity information.
Can request IDs be reused?
Add a generation or session to the identity. Reusing the same pair without a generation is indistinguishable from a duplicate.
How do you read a consistent total across clients?
Acquire stripe locks in a fixed order or maintain a separately coordinated snapshot. Summing independently read counts is not necessarily a single-instant total.
What about requests that never receive responses?
Add an explicit expiry or cancellation event with the same terminal transition. Use an injected monotonic clock and define whether late responses are ignored after expiry.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The invariant

Each stripe protects request states and client counts together. An absent identity is unknown, true means active, and false is a completed tombstone. A client count equals the number of true states for that client. A zero count has no active-client entry.

Transitions and locking

The first request inserts an active state and increments once. A response changes active to completed and decrements once; an unknown response simply creates a tombstone. The entire transition is one critical section. Erasing a zero count while still holding that lock prevents a new increment from being erased by an older cleanup.

Two separately atomic steps are not one transition. If the request marks its identity active in one compute and increments the count in a second step, a response that arrives in between sees the active identity, decrements a count that is not there yet, and the late increment then counts a completed request forever. The same-identity race test releases a request and a response together thousands of times to catch exactly that.

Clients map to fixed stripes. This avoids a race in creating and deleting per-client locks. Different stripes progress independently; collisions deliberately serialize. Reads take the same stripe lock, and the hook is instrumentation rather than caller work.

The broken interleaving

The broken version deletes completed request records. A request becomes active, a response removes it and its zero-count client, and a replayed request now looks new. It resurrects an already completed identity. An early response is also forgotten, so its later request incorrectly increments. Both schedules are tested without timing dependence.

Cost and limits

Java hash operations are expected O(1); the C++ ordered maps use O(log R) within a stripe. Space is O(R + C) for remembered identities and active clients. Counts do not grow with duplicates, but tombstones do grow with distinct completed identities. That is a consequence of the exact replay contract, not an accidental cache leak.

How to say it in the interview

I will make request state terminal once a response arrives. Under one client stripe I update that state, its count and zero-entry cleanup together. Completed IDs remain deduplicated even after the active client entry is removed, so replay cannot resurrect work or make counts negative.
