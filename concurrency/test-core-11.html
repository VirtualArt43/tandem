For unique immutable account ids used by every locking path, which Coffman condition does "lock the smaller id first" break?
Why. Threads still hold one lock while waiting for another, and locks are still exclusive and cannot be taken away. What changes is that every thread climbs the same order, so nobody can wait for a lower lock while holding a higher one, and a cycle cannot form.

Thread 1 runs transfer(a, b) and thread 2 runs transfer(b, a), each locking from and then to, with no ordering. What can happen to print(total) after both threads join? Assume distinct accounts, valid amounts, no other locks or transfers, and ordinary scheduling progress.
Why. If one thread takes both locks before the other takes its first, everything completes correctly. If each grabs its first lock before the other's second attempt, they wait for each other forever. The locks keep the totals correct; the risk is liveness, not wrong numbers. Neither the JVM nor the OS breaks a lock deadlock for you; jstack only reports it.

A fixed pool has 2 workers and an unbounded queue. Both workers are already running parent tasks. Each parent submits a child to that same pool and calls untimed get() on it. No interruption or cancellation occurs. What happens?
Why. Both parents occupy the fixed pool's two worker slots, and untimed get() has no automatic timeout. The unbounded queue accepts their children without creating additional worker slots. Both workers wait for subtasks that only a worker could run. No lock is involved, but the circular wait is there: worker waits for queued task, queued task waits for a worker. Fix it with async composition, a separate pool for subtasks, or structured fork/join tasks with acyclic dependencies.

Five dining philosophers acquire their left then right fork, release both after eating, and release an admission permit last. A semaphore with 4 permits must be acquired before any fork. Which Coffman condition does it break?
Why. A philosopher still holds one fork while waiting for the second, so hold and wait remains. But a cycle around the table needs all five philosophers each holding one fork, and at most four can be trying, so the cycle can never close. Saying it breaks hold and wait is a common slip.
From: Deadlock: the four conditions and how to break each
Two threads use the "take the first lock, try the second, on failure release and retry" scheme, and they retry immediately with no delay. What can go wrong?
Why. For these distinct locks, with no outside locks or blocking work in the critical section, no thread waits for another lock while keeping a partial set, so this acquisition protocol cannot deadlock. But two threads that keep colliding at the same moment can repeat forever: a livelock. Random backoff reduces repeated collisions but gives no deterministic fairness guarantee. A successful tryLock synchronizes with the prior release of that lock, just like a blocking acquisition; it does not introduce a data race.

C++ onlyThread 1 runs std::scoped_lock lk(a.m, b.m); and thread 2 runs std::scoped_lock lk(b.m, a.m);, repeatedly. Can they deadlock with each other if a.m and b.m are distinct std::mutex objects, neither is already owned by the caller, and no other locks or blocking calls are involved?

Java onlyTo order locks on objects without ids, a teammate locks the object with the smaller System.identityHashCode first. What is the remaining hole?
Why. Identity hash codes are stable for an object's lifetime but are not unique. On a tie, two threads could lock the pair in opposite orders. Acquire a single shared tie lock first whenever the hashes are equal, or give objects unique stable ordering ids. Identity hashes are stable, nesting monitors is legal, and the issue is uniqueness, not thread safety.

Two resource types. Available = (1, 1). P0 holds (1, 0) with maximum (2, 2); P1 holds (0, 1) with maximum (1, 2); P2 holds (1, 1) with maximum (2, 1). The state is safe (sequence P1, P2, P0). P0 now asks for (1, 0). What does the Banker's algorithm do?
Why. The request is within P0's need (1, 2) and within Available. Pretend to grant: Available (0, 1), P0's need becomes (0, 2). Then P0 needs 2 of B but only 1 is free, P1 needs (1, 1) and P2 needs (1, 0), and both need an A that is not there. No remaining maximum need fits, so no safe sequence exists: deny and wait. Availability alone is insufficient; the request is within the maximum, and allocation size is not the admission rule.
From: Deadlock avoidance and detection
A resource allocation graph has a cycle. When can you conclude that the system is deadlocked?
Why. With single-instance resources, a cycle and a deadlock are the same thing. With several instances, a thread outside the cycle may hold an instance it will release, breaking the wait; then the cycle is necessary but not sufficient. Two threads are enough for a cycle; graph structure and resource counts, not a minimum of three threads, determine the result.
From: Deadlock avoidance and detection
The Banker's algorithm says the system is in an unsafe state. What does that mean?
Why. Safe means a completion order is guaranteed to exist. Unsafe means that guarantee is gone: if every thread did ask for its maximum, some could be stuck forever. Threads often finish without asking for their maximum, so an unsafe state can resolve on its own. No exceeded claim or zero-availability condition is implied: unsafety is a failed completion-order proof.
From: Deadlock avoidance and detection
Why does PostgreSQL wait for deadlock_timeout (1 second by default) before checking a waiting transaction for a deadlock?
Why. A real deadlock never resolves on its own, but nearly all lock waits are ordinary short waits behind a running transaction. Checking every wait immediately would waste work on those; delaying the check saves work. A cycle can be detected immediately in principle; waiting does not allow the OS or a member of an unbroken cycle to resolve it automatically.
From: Deadlock avoidance and detection
Under wound-wait, an older transaction T1 requests a lock held by a younger transaction T2. What happens?
Why. Wound-wait lets older transactions take what they need from younger ones; a younger requester waits for an older holder. Waits therefore only go from younger to older, so no cycle can form. Wait-die permits the older requester to wait; wound-wait instead selects the younger holder. Neither aborts both, and restarts retain the original timestamp.
From: Deadlock avoidance and detection
A database recovers from a deadlock by rolling back a victim. Why can't a Java or C++ program automatically do the same to an arbitrary deadlocked thread?
Why. A thread blocked on a monitor or a std::mutex does not respond to interruption, and forcibly stopping it would leave the objects it was changing half updated. The JVM does know which monitors a thread holds; that is how jstack finds the cycle. It cannot automatically undo arbitrary changes. Interruptible locking with application cleanup can enable cooperative recovery, but plain monitor entry is not interruptible. CPU usage is not the obstacle.

A service is stuck: throughput is zero, CPU is at 100 percent on four cores, and thread dumps show the same threads RUNNABLE inside retry loops in every dump. What is the most likely diagnosis?
Why. Repeated retries with no completions make livelock the strongest hypothesis. A blocking deadlock or lost wakeup usually leaves participants asleep, and starvation of one caller allows others to finish. CPU alone is not proof: inspect dependencies to exclude a spinlock deadlock or an impossible predicate.
From: Livelock, starvation and fairness
Two threads use "lock one, try the other, release the held lock on failure and retry". They retry after exactly 10 ms every time, and under load they keep colliding. What fixes it best?
Why. A fixed delay can preserve lockstep, whether it is 10 ms or 1 ms. Immediate retries can do the same. Randomness breaks the symmetry, and the growing bound handles heavier contention; blocking acquisition in a global lock order removes this retry cycle. Fair locks do not help, because each thread fails on the lock the other already holds.

A read-write lock admits new readers whenever no writer holds the lock. Readers arrive constantly and their read sections overlap. What happens to a writer?
Why. Reader preference with overlapping readers means the read count never drops to zero, so the writer starves. The fix is writer preference (once a writer waits, new readers queue behind it) or alternating batches. Nothing in a plain read-write lock times out on the writer's behalf.

In the scheduler demo, one priority-5 request arrives and one task runs each tick. The priority-0 report arrived at tick 0. With key arrival - 20 * priority, smaller first, and earlier arrival breaking ties, what does the aging run print?
Why. The report's key is 0. Requests arriving at ticks 0 through 99 have negative keys and run first. At tick 100 the new request also has key 0, but the report wins the arrival tie. Tick 0 ignores the priority bonus, tick 101 ignores the tie-breaker, and indefinite postponement describes the strict-priority run. This exact tick depends on the demo's one-task-per-tick workload; aging does not promise it for arbitrary backlogs.
From: Livelock, starvation and fairness
What does it mean that an algorithm is lock-free but not wait-free?
Why. Lock-free promises system-wide completion, not a per-caller step bound. Wait-free adds that bound on each operation's own steps, not elapsed time. CAS is compatible with either property; a failed weak CAS can even be spurious, so failure alone does not prove another operation completed. The progress guarantees exclude a system-wide deadlock under their execution assumptions.

Java onlyA ReentrantLock is constructed with new ReentrantLock(true). A thread calls tryLock() with no timeout while other threads are queued. What happens if the lock happens to be free at that instant?
Why. The documentation is explicit: the untimed tryLock() does not honor the fairness setting. tryLock(0, TimeUnit.SECONDS) does honor it. The timed form also detects interruption, so the caller must handle or propagate InterruptedException. The untimed form neither queues nor throws merely because waiters exist.

C++ onlyWhat does the C++ standard promise about the order in which threads blocked on a std::mutex acquire it?
Why. The standard specifies mutual exclusion and synchronization, not fairness. FIFO, highest-priority-first and newest-first are all outside its contract. Explicit tickets can order admission after ticket assignment, but the scheduler and the internal mutex still need progress assumptions.
From: Livelock, starvation and fairness
Threads H (high), M (medium) and L (low) share one CPU with a strict priority scheduler. L holds lock X. H blocks on X. X has no inheritance or ceiling protocol. M becomes ready; M never uses X. What happens?
Why. H is blocked, so it cannot run. Of the ready threads, M outranks L, so M runs, and L never gets to release X. H is effectively demoted below M: an unbounded priority inversion. It is not a deadlock cycle: M is runnable and has no dependency on H or L. M need not finish; an endless stream of medium work can delay L indefinitely. Merely holding X does not change L's scheduling priority.
From: Priority inversion and lock convoys
A low priority thread owns one mutex and a higher priority thread blocks on it. What does priority inheritance do?
Why. The problem is that the holder runs at a low priority, so the boost goes to the holder. For this single-lock case it loses the donation when the dependency ends. With several locks it may retain another donation, so its effective priority must be recomputed. Raising the blocked waiter alone does not schedule the owner; inheritance neither lowers unrelated threads nor promises FIFO acquisition.

In a toy convoy model, each acquisition serially costs 1 microsecond of useful work plus 9 microseconds of handoff delay. Ignore all other costs. What is the maximum acquisition rate?
Why. One complete cycle costs 10 microseconds, so the model permits 1,000,000 / 10 = 100,000 acquisitions per second. The first option ignores handoff delay; the third ignores useful work. Four contenders cannot multiply the capacity of one serialized lock. These are supplied model inputs, not measured OS timings.

Four threads hammer one lock with tiny critical sections. Switching it from barging to fair makes throughput collapse. Profiling shows short holds and long wake-to-run delays for queued waiters. What best explains it?
Why. The profile supports a convoy dominated by handoff delay. Barging can let a runnable caller acquire sooner, at the cost of bypassing queued callers. The evidence does not implicate per-waiter memory, disabling the JIT or a deadlock, and fairness does not require sleeping on every acquisition.

Which change best reduces a lock convoy on a hot queue whose consumer takes one item per lock acquisition?
Why. Fewer, shorter acquisitions mean fewer hand-overs and less time with the lock in transit. Processing the batch outside the lock keeps holds short. Fairness can add handoff delay, more consumers can add contention, and priority changes do not address the excessive acquisition count.

On one CPU with strict priorities, L has set an atomic flag to hold a spinlock. H preempts L, executes while (!flag.compareAndSet(false, true)) {} in Java or while (flag.test_and_set()) {} in C++, then prints acquired. Only L can clear the flag, and there are no priority boosts. What can H print?

These atomic operations are race-free but supply no scheduler-visible ownership or priority donation. Visibility does not clear a flag, and atomics alone provide neither fairness nor completion.

Why. For platform threads the scheduling effect depends on the OS and JVM; for virtual threads setPriority is ignored. 100 consumers wait in predicate loops on an empty queue, protected by one mutex. A producer adds one item, broadcasts, and releases the mutex. No more items arrive and all threads eventually run. What happens?
Why. Notify-all moves every waiter back into contention for the lock. They are serialized by the lock, so nothing breaks, but 99 consumers find no item. From: Thundering herd and cache stampede
An empty bounded queue's close() sets closed = true under its mutex and calls notify-one. Twelve consumers wait while empty and not closed. With no further notifications, timeouts, interrupts or spurious wakeups, what goes wrong?
Why. Closing changes the state in a way that lets every waiter proceed (they must all see "closed" and exit), so it must wake all of them. Wake-one is only right when one change satisfies exactly one waiter. The flag is shared state, not a private message to one thread; notification makes waiters eligible to observe it. Broadcast is appropriate; changing the flag alone does not resume all twelve waiters.

200 servers each have a correct in-process single-flight in front of the database. A hot key expires, and 10,000 misses for it arrive before any load completes, spread evenly over the servers; each server has its own cached copy. Roughly how many database queries for that key follow?
Why. Single-flight merges concurrent misses within one process, so each server sends one query. The 50 requests per server are followers of that server's single load, not 50 fleet-wide loads. One fleet-wide query in the healthy case needs coordination outside the process, such as a lease with failure handling; serving stale alone does not elect an owner.

After every deploy, the database is hammered about ten minutes later, although no single key is especially hot. Every cache entry has a 600 second TTL and the cache is warmed at startup. What is the most direct fix?
Why. Thousands of different keys written at startup expire in the same second. Single-flight cannot spread distinct-key reloads, and a longer TTL only moves the cliff. Independent TTL jitter spreads expected reload demand across time; it does not bound every peak. Changing condition-variable notification cannot change cache expiry scheduling.

A server restarts and 50,000 clients reconnect within the same second, knocking it over again. What is the best client-side change?
Why. A fixed delay just moves the whole herd five seconds later. Randomness spreads clients out, and the growing bound keeps load low while the server is still struggling. Immediate retries amplify overload; disabling recovery entirely sacrifices availability. Pair jitter with deadlines, a retry budget and server side admission control.

What does "serve stale while revalidating" trade, compared with blocking every request until a fresh value is loaded?
Why. Serving stale avoids waiting for the source, but freshness is a real cost and is acceptable only when the contract permits it. Duplicate suppression limits reloads separately; stale serving alone does not elect a refresher. Requests stop completing. CPU is near zero. Two thread dumps ten seconds apart show the same two threads, each holding one lock and waiting for the lock the other holds. What is it, and what was the right first tool?
Why. Idle CPU plus threads waiting in the same frames across dumps means waiting, not spinning, and a lock cycle in the dump is a deadlock by definition. A thread dump is a useful first tool here. Why. The profile locates active spinning, not blocked locks or GC. Java permits reuse of a plain field read; C++ gives no valid execution guarantees for this data race. Memory grows slowly for hours and the process dies at peak traffic. The work queue was created without a practical capacity limit, and retained queued jobs dominate the heap. In Java this could be a default LinkedBlockingQueue. What is the fix?
Why. Producers outpace consumers and nothing pushes back, so the backlog lives in memory until it runs out. More memory only delays the crash, and a non-blocking unbounded queue has the same problem. An atomic counter starts at 0. Each of two threads reads it into its own local variable, then stores that local value plus 1. A test gate ensures both reads finish before either store. You take two thread dumps ten seconds apart. Thread A is in the same frame, waiting on the same lock, in both. Thread B is in a different frame each time. What do you conclude?
Why. A could have remained blocked or returned to the same lock between samples. B could be doing useful work or cycling through a livelock. Repeated observation shows a consumer asleep on its not-empty condition while the queue contains 500 items. There is no lock owner, shutdown, competing consumer or further notification. Which bug should you investigate first?
Why. Useful work is stranded with no signal path to resume the consumer. Check predicate reads and writes under the same mutex, atomic release-and-wait, and notifications to the correct waiters. Signalling before a waiter arrives is harmless when the protected predicate is checked correctly: notifications are not stored, but state is.
