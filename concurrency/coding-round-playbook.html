How to run a concurrency coding round

Run a concurrency coding round: clarify the contract, protect invariants, explain interleavings, test failure paths, and handle follow ups.

Asked atRubrikDatabricksLinkedInUberNetflixConfluentRipplingFlipkart
Before this:The monitor object patternTesting concurrent codeDebugging rounds: the bug in someone else's threaded code

Knowing the primitives is only part of a concurrency round. A checklist helps you catch missing requirements, test shutdown, compile early and explain your reasoning while you code.

In plain words

Airline pilots with thousands of hours still read a checklist before take-off, aloud, every time. Not because they forget how to fly, but because pressure makes experts skip the boring step that matters. A concurrency round is the same: an hour, a stranger watching, code that must run. The steps below are your checklist.

The steps also make your thinking visible. Make the reasoning behind your code audible. Saying "the shared state is the queue and the closed flag, the invariant is size never exceeds capacity" scores points before you type a line.

What the round looks like

These are reported examples, not guarantees about your next loop. Team, level and interviewer change the format; confirm the constraints at the start.

The method

Step 1. Clarify the API and the semantics (minutes 0 to 5)

Concurrency prompts often leave important behaviour unspecified. Your clarifications reveal whether you understand the contract. Ask them as a quick list, propose a default for each, and move on:

Before I code: should put block when full, or should I also offer a timed version? On shutdown, do queued tasks finish or get dropped, and should blocked callers wake up? And may I use locks and conditions but not the library queues?

Step 2. Name the shared state and the invariants (minutes 5 to 10)

Write them as comments at the top of the class before any method. Three lines do it: what is shared, which lock guards it, and the invariant that must hold whenever the lock is free. Then list the conditions threads wait for; each becomes a condition variable or a predicate.

Step 3. Choose primitives for a reason

Shape of the problemPrimitive
One variable, simple updateAn atomic (AtomicLong, std::atomic); LongAdder for hot statistics, never an exact admission limit
An invariant across several fieldsOne mutex for all of them
Wait until some state holdsA monitor: lock plus condition variables, waits in a loop

Rendezvous every roundA barrier
Many long reads, rare writesA read-write lock, only if reads really dominate and do not mutate

Say the reason out loud: "one lock, because size and the deque must agree" beats "I'll use a lock" every time. The least clever tool that makes the invariant atomic is the right tool.

Step 4. Write it from the monitor template

Many blocking structures in these rounds fit a monitor, and the template is fixed: one lock guards the state; each method takes the lock, waits in a loop until it can proceed without breaking the invariant, changes the state, signals the waiters the change may release, and unlocks on every path. A closed flag is part of the state from the start, when the contract includes a lifecycle. Here is the template applied to a small permit pool, together with the test you should be able to write in five minutes (step 6):

State the timeout scope. Here the timeout budgets condition waiting after the mutex is acquired; lock acquisition and reacquisition can take longer. For a whole-call budget, use one monotonic deadline, timed lock acquisition, and the remaining budget for each wait; scheduling still prevents a hard return-time guarantee. C++ durations here must be small enough that adding them to steady_clock::now() is representable.

acquire linearizes at the decrement; close linearizes at the flag write under the same lock. An acquire that took its permit before close can return afterwards. Clients must pair each successful acquire with one release: the over-release check catches a full counter, not every duplicate release while other permits are outstanding.

The close check is a smoke test: its sleep makes waiting likely but does not prove the waiter reached the condition wait. A deterministic notification test needs a test hook just before waiting, under the pool lock, so close can acquire that lock only after the waiter releases it. The stress run checks observed safety and some progress, not every possible schedule. In C++17 replace the latch with a mutex, condition and start flag, and replace the stop-aware watchdog with a joined thread waiting on a done flag.

The template's rules, each of which a grader checks: one lock per invariant; waits in a while loop or with a predicate; state change first, then the signal, chosen for who can now proceed (signal when one change frees one waiter, signalAll when it can free many or when waiters wait for different things); unlock in finally or by RAII; no callbacks, I/O or sleeps while holding the lock; the closed flag inside the same lock.

Step 5. Walk the interleavings out loud

When the code is written, do not say "done". Pick up each method and ask six questions, out loud, pointing at lines:

  1. Atomicity: is each compound update protected by one lock hold or one correctly justified atomic operation?
  2. Waiting: is every wait in a loop on the real condition? What if two threads wake for one item?
  3. Waking: does every state change that can end someone's wait signal them? Does the predicate check share the mutex with its update, preventing a lost wakeup? An early signal is fine when the persistent predicate is already true.
  4. Locks: is any lock held while calling out, blocking on something else, or taking a second lock in a different order than elsewhere?
  5. Failure: if this line throws, is the lock released and the invariant still true?
  6. Shutdown: after close, does every blocked thread wake, and are new submissions rejected, while consumers may still drain and holders may release?

Narrating a dangerous interleaving makes your correctness argument concrete. LinkedIn interviewers have asked candidates to give an example race for each lock they add; have the answer before the question.

Step 6. Test it: single thread, then stress, then edges

First a single-threaded sanity check (FIFO order, sizes). Then a stress test with the shape above: a start gate to increase overlap, many threads and iterations, the invariant measured from inside (maximum holders, items exactly once, totals exact), and bounded joins in Java or a process watchdog in C++, so lack of progress becomes a failure. Then the edges: capacity 1, a zero timeout, close while threads are blocked, an interrupt while blocked, a task that throws. In C++, build with ThreadSanitizer when the environment allows: a race is a failure even when the totals come out right.

Step 7. Handle the follow ups

Follow upThe change
"Add a timeout"A deadline computed once, awaitNanos fed its own result, or wait_until; return false or empty
"Make it fair" or "no starvation"A FIFO queue of waiters or tickets; for groups, alternate or cap batches
"Add shutdown"A closed flag under the lock, signalAll or notify_all, reject new work, drain or return queued work; Java shutdownNow attempts interruption; C++ needs a stop protocol that wakes its waits
"What if a task throws?"Catch around the task, record it in the future, keep the worker alive
"It is too slow under contention"Measure contention, then shorten critical sections, stripe independent state or batch. Head/tail locks require a new proof for the shared count, links and wakeups.
"Many readers"A read-write lock if reads dominate and do not mutate; copy-on-write snapshots if writes are rare
"Now across machines"The database or a single owner as arbiter, leases with fencing, idempotency (module 16)

A correct simple version at minute 30 beats a clever one at minute 55. If you are stuck, say what you are weighing; interviewers give hints to people who think aloud. If the interviewer changes the requirements (one Rubrik candidate saw them change three times), restate the new contract in one sentence before editing code.

Code that compiles and runs

  • Compile early, compile often. Get an empty class and a main compiling in the first minutes, then grow it. One Rubrik new grad fixed the deadlock in a debugging round and still lost the round because the fix did not compile.
  • Know your boilerplate cold. Imports (java.util.concurrent.locks.*, java.util.concurrent.atomic.*), C++ headers (<mutex>, <condition_variable>, <thread>, <atomic>, <chrono>), and a test main. A Rippling C++ candidate reported losing time to boilerplate. The Java and C++ cheat sheets collect the main names.
  • Prefer boring code. No clever generics, no lock-free unless asked. Name threads; print the thread name in your debug output.
  • Handle the checked parts. Java: InterruptedException restored or propagated, unlock in finally. C++: join every thread, name every guard, wait with a predicate.
  • Leave a driver. Indian machine coding rounds (Flipkart, PhonePe, Uber) ask for a driver or test that demonstrates concurrent requests. Your stress test is that driver.

When the library is banned

Rubrik reports repeatedly ban ExecutorService, BlockingQueue and concurrent queues; one 2026 report said threading primitives only. A LinkedIn loop allowed only plain threads with wait and notify. LeetCode's own bounded blocking queue problem says a built-in queue would not be accepted. So:

  • Ask exactly what is allowed: "May I use ReentrantLock and Condition, or only synchronized? std::mutex and std::condition_variable? Atomics?" Do not infer permission for another high-level collection from a narrow ban.
  • Name what you are replacing, so the interviewer sees you know the library: "this is the ArrayBlockingQueue contract".
  • Have the hand-built set ready: bounded blocking queue, thread pool with futures and shutdown, latch or "wait for all", semaphore, read-write lock, delayed scheduler. Each has a lock-based implementation and a practice problem here.

Debugging rounds

Rubrik reports include separate debugging rounds (50 to 60 minutes) on someone else's multithreaded program: reports mention a 180-line barber shop simulation, a cinema booking service, a banking application and a C++ producer and consumer. The procedure (debugging rounds has the full version):

  1. Read before touching (5 to 10 minutes): list the threads, the shared state, every lock and which state it guards.
  2. Run it, more than once. A hang means take a thread dump (jstack, or thread apply all bt in gdb) and look for a cycle of threads each waiting for a lock another holds. Wrong output means look for unguarded shared state and check-then-act.
  3. Sweep the usual suspects: if around a wait, notify with mixed waiters, locks taken in different orders, a lock held while calling out, a missing finally, a shutdown that never wakes waiters, an uncaught task exception that kills a worker or a swallowed failure that hides lost work.
  4. Fix minimally, one bug at a time, compiling after each, and explain each fix with the interleaving it prevents.

Worked example: a Rubrik-style hour, minute by minute

The prompt: "Build a bounded queue, then a thread pool on it with submit, shutdown and shutdownNow. No library executors or queues."

  • 0 to 5: clarify: blocking submit when full, or reject? Futures from submit? Does shutdown let queued tasks finish? Does immediate shutdown return unstarted tasks and request cancellation of running ones? What happens when a task throws?
  • 5 to 10: write the comment block: queue state guarded by one lock, conditions not full and not empty, a closed flag; pool state: workers, a state of running, shutdown or stopped.
  • 10 to 25: the queue from the monitor template, with close() from the start; compile; a single-threaded check.
  • 25 to 40: workers that loop on take, catch task exceptions, exit when the queue is closed and empty; submit that rejects after shutdown; immediate shutdown that drains the queue, requests cancellation, wakes workers and returns drained tasks. Compile and run a stress test.
  • 40 to 50: walk the interleavings: submit racing shutdown, a worker blocked in take during shutdown, a cancellation request while a worker is inside a task.
  • 50 to 60: follow ups: per-task timeouts, reclaiming idle threads, futures with exceptions. State the contract change and its new failure paths before implementing it; cancellation and worker retirement need more than a mechanical edit.

Common mistakes

  • Coding before clarifying. Ten minutes into the wrong shutdown semantics is hard to recover.
  • Synchronizing everything. An Uber interviewer complained that candidates "put synchronization everywhere". Lock what the invariant needs, and say why.
  • Listing tools instead of reasoning. A Google L5 candidate who named ConcurrentHashMap, AtomicInteger and synchronized still got No Hire and concluded that precise reasoning about races and guarantees was expected.
  • No shutdown path. Blocked threads that never wake make even a correct steady-state algorithm unusable.
  • Saying "done" without running it. Run a stress test, then walk the interleavings.
  • Silence. Thinking quietly for minutes wastes the interviewer's chance to help.

In the interview

What graders reportedly focus on: shutdown semantics, interrupt handling and exactly which exceptions a pool catches (a Rubrik 2026 screen), the choice of constructs such as CyclicBarrier versus Semaphore and exception handling (a Rubrik G5 round), picking the right critical sections and where to create threads (a Rubrik crawler round), and naming the race each lock prevents (LinkedIn). The sentences that carry the round:

Let me pin down the contract first: blocking or timed, what shutdown does to queued work and blocked callers, and how task failures surface. Then I will name the shared state and the invariant before I write anything.
The shared state is the deque and the closed flag, guarded by one lock, and the invariant is that size never exceeds capacity. Producers wait for not full or closed, consumers for not empty or closed, both in loops.
Before I call it done, let me walk the dangerous interleavings: two consumers waking for one item, close while a producer is blocked, and a task that throws inside a worker.

Senior depth

Separate safety from progress. Identify each operation's linearization point and explain why the invariant survives every exit, including exceptions. Then ask who can unblock every waiter and under what scheduling assumptions. An ordinary mutex plus notify_one does not prove starvation freedom; ticket ordering also needs cancellation rules so an abandoned ticket cannot block the queue.

For a pool, accepting a submission and observing shutdown must be ordered by the same synchronization protocol. Remove a task under the lock, run user code outside it, and settle its future exactly once with a value, failure or cancellation. State your policy for tasks removed by immediate shutdown; merely dropping their queue entries can leave callers waiting forever. Destroy the C++ queue, mutex and conditions only after every user and worker has stopped and joined.

Give complexity as work while holding the lock plus waiting: deque operations may be constant-time or amortized constant-time, but blocked calls have no constant wall-clock bound. Use targeted schedules as well as stress: force a producer to wait on a full queue, race shutdown against submission, and confirm every accepted task completes or gets an explicit cancellation outcome.

Key takeaways

  • Clarify blocking, timeouts, fairness, bounds, shutdown, exceptions, cancellation and library rules before coding; propose defaults.
  • Write the shared state, its lock, the invariant and the wait conditions as comments first.
  • Build from the monitor template, with a closed flag from the start.
  • Walk the six questions out loud, then run a stress test with a start gate and bounded process lifetime.
  • Compile early and often, keep boilerplate in muscle memory, and finish a correct simple version before the clever one.

Quick check

Answer each question, then read why. Your score is saved for your module test.

The prompt is "implement a thread pool". What should you do in the first two minutes?
Why. The behaviors a library would hide are exactly what these rounds grade, and they change the design. Proposing defaults keeps it quick. Theory without a contract delays the code without earning credit.
A capacity-one permit pool is exhausted. One acquirer waits using if (available == 0) changed.await();. Another thread releases one permit, then a new acquirer takes it before the signalled waiter reacquires the lock. Each acquirer subtracts one and prints available while holding the lock. Neither releases a permit. If both calls finish, what do they print, in order?
Why. The release changes 0 to 1. The new acquirer subtracts one and prints 0. The waiter resumes after await without rechecking, subtracts again and prints -1. Locking orders the decrements but does not repair the missing predicate check; await does not know that predicate. With while, the waiter would wait again. Spurious wakeups are an additional reason to loop.
Why does the stress test release all its threads through a start gate (a latch at 1) instead of starting them one by one?
Why. Threads started one by one often finish their first iterations before the next even starts, so the test runs nearly sequentially and proves little. A gate increases the opportunity for overlap, but some threads may reach it after it opens. It does not make the test deterministic; that is why you also measure invariants and repeat runs.
The interviewer says: "No ExecutorService, no BlockingQueue." What is usually still allowed, and what should you do about it?
Why. Bans target the high-level pieces so that you build them from primitives. Concurrent queues are often in the ban too. Ask exactly which primitives you may use, because one reported loop allowed only wait and notify.
Minute 40 of 60: your queue compiles and the single-threaded check passes. What next?
Why. Correctness under concurrency is the point of the round, and the stress run plus the narrated interleavings is where you show it. Lock-free rewrites burn the remaining time on risk nobody asked for.
In a debugging round the given program hangs. What is the most useful first step?
Why. A hang is a state you can inspect: stacks show blocked operations, and Java dumps may identify lock owners and cycles. Combine this with the predicates and producer lifecycle to distinguish a lock cycle from a lost wakeup or an absent producer; a stack alone does not prove which signal was missed. Sleeps hide timing bugs, and a global lock rewrite fails the "minimal fix" expectation.
Spot the bug in this shutdown, written in a monitor whose consumers wait on notEmpty with while (items.isEmpty() && !closed) notEmpty.await();.
Why. Setting the flag under the lock is right and makes it visible; but a waiter only re-checks when woken. close must call notEmpty.signalAll() (and wake producers too) so every waiter sees closed. volatile is unnecessary when the flag is read and written under the lock.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Pseudo code
The prompt: "Build a blocking queue that supports shutdown." List the clarifying questions you would ask, and the default you would propose for each.
Model answer
  • Bounded? Yes, capacity in the constructor.
  • What does put do when full, and take when empty? Block; also offer a timed offer and poll that return false or empty.
  • After shutdown, what do producers get? An immediate failure (false or an exception), including producers already blocked, which must wake.
  • After shutdown, what do consumers get? The remaining items first (drain), then a "closed" result instead of blocking.
  • Is there a shutdownNow? Optionally: clear the queue and return the items.
  • Fairness among waiters? No FIFO or starvation guarantee by default; add explicit admission ordering if required.
  • Interruption? Blocking calls throw InterruptedException in Java; in C++ close is the cancellation path.
  • How many producers and consumers? Many of each.
  • Allowed tools? A lock and condition variables, no library queues.
  • Does it have to run? Yes; I will write a stress test with a start gate.
Debug
Find every bug in this hand-built pool and say how to fix each.
Model answer
  1. if around wait. A spurious wakeup, or another worker taking the task first, leaves task null and task.run() throws. Use while (queue.isEmpty() && !closed) wait();.
  2. Workers never exit. The loop ignores closed. After the wait, if the queue is empty and closed is true, return.
  3. shutdown writes closed without the lock and wakes nobody. Workers blocked in wait sleep forever, and the write may not even be visible. Set it inside synchronized (this) and call notifyAll().
  4. A throwing task kills its worker. Wrap task.run() in try/catch, record or log the failure, and keep looping.
  5. InterruptedException is not handled. wait throws it; catch it, restore the interrupt flag and exit the loop (this is how a shutdownNow would stop workers).
  6. The queue is unbounded (a design choice to state): submit never pushes back under overload. Bound it and block or reject when full.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"You have an hour to build a bounded worker pool. Walk me through your first five minutes."
What a strong answer covers

How a senior would say it
I would agree on the contract before writing the worker loop. I would ask whether submission blocks or rejects when the queue is full, whether shutdown drains accepted work, and what immediate shutdown does to queued and running tasks. I would also ask how callers receive task failures and whether cancellation must interrupt a blocked operation. I would propose defaults so that this discussion stays short. Next I would confirm the allowed libraries and whether the code must compile and run. Then I would write down the shared state: the queue, its capacity and the lifecycle state, guarded by one lock. The queue must stay within capacity, and every accepted task must eventually receive a completion, failure or cancellation outcome under our progress assumptions. Workers wait for work or shutdown; blocked submitters wait for space or shutdown. I would start with a monitor because those predicates and transitions fit one lock. Finally, I would reserve time to test capacity one, task failure and submission racing shutdown, and to explain the dangerous interleavings aloud.

Likely follow up: Where exactly does a submission racing shutdown become accepted or rejected?

Out loudabout 75 s
"Your stress test passes, but production sometimes hangs during shutdown. What do you check?"
What a strong answer covers
  • A passing stress run does not prove progress for all schedules
  • Capture thread stacks and map waiters to predicates and enabling operations
  • Check the closed flag and notifications under the same locking protocol
  • Check joins or callbacks under locks, pool self-dependency and cancellation cooperation
  • Force the shutdown interleaving and bound the entire test process
How a senior would say it
I would capture the hung threads before changing the code. A passing stress run only covers the schedules that happened; it does not prove shutdown can always finish. For each blocked thread, I would identify its predicate and the operation that could make that predicate true. A consumer waiting on an empty queue must also check the closed flag, and close must wake every waiter whose outcome changes. I would verify that checking and changing this state use the same lock. Next I would look for shutdown joining workers while holding a lock those workers need, callbacks running inside critical sections, or tasks waiting for subtasks in the same exhausted pool. I would also check whether cancellation reaches running work and whether that work cooperates. To reproduce the bug, I would use a test hook to place a worker just before its condition wait and then invoke shutdown. The test would assert worker termination and task outcomes, with a watchdog for the entire process. Sleeping to make the schedule likely is useful evidence, but it is not a deterministic reproduction.
