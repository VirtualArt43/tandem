Files, offsets, buffers, flush and fsync

Shared offsets, positional I/O, buffering, durable replacement, sync failures, group commit and range locking for concurrent file access.

Asked atRubrikDatabricks
Before this:CPU bound versus I/O bound workMutexes and RAII guards

Rubrik's System Coding rounds copy files with pread and pwrite and read and write bytes at offsets; Databricks' System Programming round is officially about files, buffering, caching and storage, and the most recurring concurrency task in our research turns on fsync. This lesson is the systems knowledge both of them assume.

In plain words

Think of sending a letter from a big housing society. You write it at your desk: that is your program's buffer. You drop it in the society's outgoing dak box: that is the operating system's cache. The postman empties the box on his own schedule, unless you request a delivery receipt and wait for it. Even the post office keeps letters on a sorting table for a while before they go into the locked room: that is the drive's own cache. A durability receipt must cover that last step too.

If the building loses power, every letter still on a desk or in the dak box is gone. "I wrote it" and "it is safe" are different moments, and a system that promises durability may only say "done" after the letter is in the locked room.

Descriptors, offsets and the shared-offset trap

Opening a file gives your process a file descriptor: a small integer that names a kernel object, and that kernel object holds the file's current offset. This is the open file description: descriptors made with dup share it, whereas independent open calls have independent offsets. A plain read or write uses the offset and moves it forward by the bytes actually transferred. When two threads share a descriptor, they share that offset, and "seek, then write" becomes a check then act across two system calls:

A lock shared by every user around seek and write works, but serializes unrelated ranges. Prefer Positional I/O: pread(fd, buf, n, offset) and pwrite(fd, buf, n, offset) in C++ (POSIX), and FileChannel.read(buf, position) and write(buf, position) in Java. They take the offset as an argument and neither use nor move the shared one, so each call is self-contained. Java's FileChannel documentation says channels are safe for concurrent threads and that operations taking an explicit position may proceed concurrently. Threads writing disjoint ranges of a regular file need no application lock when they own separate buffers and nobody truncates or replaces the file. The provider may still serialize operations, especially file growth.

Short transfers are legal. Loop until all bytes are transferred, advancing both buffer and offset by the actual count. With a nonempty read request, POSIX read and pread return zero at EOF; Java FileChannel.read returns -1 at EOF and may return zero without EOF. The demos treat zero progress as an error for their blocking regular files, rather than spinning indefinitely; POSIX EINTR before progress is retried.

O_APPEND atomically chooses the end position for each POSIX write on supporting local file systems. It neither makes a multi-call record atomic nor makes it durable; network file systems can have weaker append behaviour. Do not mix positional writes with append mode: Java leaves that combination unspecified, and Linux pwrite on an O_APPEND descriptor appends despite the supplied offset.

Where your bytes wait: four layers

Between your write call and stable storage there are up to four places a byte can sit. Knowing which call moves it across which boundary is the whole topic:

LayerLives inSurvives your process crashing?Survives a power cut?What moves it onward
1. Your buffer (BufferedOutputStream, an std::ofstream's buffer, your own batch)Your process's memoryNoNoflush(), or the buffer filling up
2. The page cacheKernel memoryYesNofsync, or background writeback on a configurable schedule
3. The drive's volatile write cacheRAM inside the deviceYesNo, unless the drive has power-loss protectionThe cache flush that fsync requests on Linux; on macOS, F_FULLFSYNC
4. Stable mediaFlash cells or plattersYesYes

Now the precise meaning of the calls people mix up:

  • flush on a buffered file stream pushes buffered bytes to its underlying file. Ordinary buffered file I/O reaches the page cache; it does not promise power-loss survival. Check errors, including C++ stream state. The base OutputStream.flush() does nothing, so the concrete stream matters, and another reader may need to discard its own buffered data before seeing the update.
  • fsync requests file data and metadata persistence and waits for completion. Linux's fsync also requests a device-cache flush. macOS documents that its fsync does not, and offers fcntl(fd, F_FULLFSYNC) for the full flush.
  • fdatasync (POSIX, available on Linux) syncs the data and only the metadata needed to read it back, such as a changed file size, without being required to persist unrelated timestamps. It can be cheaper. macOS does not declare it.
  • Java: FileChannel.force(true) requests content and metadata persistence; force(false) requests content persistence. These resemble fsync and fdatasync, but the exact mapping and whether false saves work depend on the OS. The API guarantee is for local storage, not arbitrary remote providers. FileDescriptor.sync() also exists, and opening with StandardOpenOption.SYNC or DSYNC makes every write synchronous.
  • C++: iostreams have no fsync at all. For durable writes in C++, use POSIX open, write and fsync directly, or fflush a FILE* and then fsync(fileno(f)). These are OS APIs, not part of ISO C++20. C++20 also has no standard way to get an ofstream's native descriptor.

Choose the durability contract explicitly

The C++ helper uses F_FULLFSYNC on macOS and fsync on Linux; it propagates an unsupported operation or storage error instead of falling back to a weaker guarantee. OpenJDK 21's macOS implementation requests F_FULLFSYNC for both values of the force metadata argument; false therefore does not buy a cheaper data-only sync there. That is an implementation fact, not a portable Java mapping, so confirm the provider and storage stack for a strict power-loss contract. A successful call assumes the device honours flush requests; it cannot protect against hardware destruction or dishonest firmware.

The runnable programs demonstrate ordering and successful sync calls, not a power-cut experiment. Their timings are illustrative, and the C++ binary records use native byte order while Java's ByteBuffer defaults to big endian; these demos verify their own format rather than interchange files. std::jthread needs C++20; with C++17, use std::thread and an RAII join guard.

What durable means, exactly

Thread visibility is separate from crash durability. A mutex, Java volatile, or a C++ release/acquire pair can publish memory to another thread; none makes a file survive power loss. Conversely, fsync is not a mutex and does not make concurrent access to a shared application buffer safe. Syncing two files also does not make their updates one crash-atomic transaction; that requires a recovery protocol such as a write-ahead log.

A write is durable when it survives the failures in your contract, here a process crash, system crash or power cut on local storage. That requires a successful sync with the platform's required strength and a durable path to the file. Three consequences interviewers probe:

  1. Acknowledge only after the sync. If a synchronous append(event) returns success, or an asynchronous append completes its receipt successfully, before the sync that covers the event, the system has promised something it cannot keep. This is the heart of Databricks' event writer question.
  2. New files need their directory synced too. fsync on a file does not guarantee that the directory entry naming it is on disk. After creating or renaming a file, sync its parent directory using the platform's supported protocol. If new ancestor directories were created too, persist their entries as well.
  3. Replacing a file safely takes four steps: write the new content to a temporary file in the same directory, sync it, rename it over the old name (rename within one file system is atomic), then sync the directory. With an already durable old file and directory, and a file system supporting this crash-consistency protocol, recovery sees a complete version. Atomic rename alone specifies visibility to live readers, not portable crash recovery; after the final directory sync succeeds, the new version is the durable one.

Failure after rename is an uncertain outcome. If the rename succeeds but the directory sync fails, the new version is already visible, although its crash durability is unconfirmed. Throwing does not roll the rename back; a retry or recovery procedure must inspect and reconcile the version.

Atomic replacement publishes a new file object: existing open descriptors still refer to the old one. If permissions, ownership or other attributes must be preserved, set them on the temporary file before its sync; the demo publishes a new file with restrictive temporary-file permissions.

The next demo assumes one replacement at a time and an existing parent directory on the local Mac/Linux provider. Java does not portably guarantee directory forcing or replacement of an existing target with ATOMIC_MOVE; unsupported cases must fail, not fall back to copy-and-delete. The C++ version syncs the target's actual parent, including for nested paths.

A storage error is not a retry instruction. PostgreSQL documents that on some systems a failed sync can discard dirty pages, letting a later sync succeed without saving the lost bytes; its default is to panic on such failures. Fail pending writes and treat the file as suspect after an I/O error. Retrying POSIX EINTR is different: it handles interruption, not evidence that failed storage has recovered.

What fsync costs, and why batching wins

An fsync waits for a device, so it costs far more than a write into the page cache. Rough orders of magnitude, which vary a lot by device and are worth measuring yourself:

StorageOne fsync, roughly
Spinning diskseveral milliseconds
Consumer SSD, no power-loss protectionfrom about 0.1 ms to a few milliseconds
Data centre SSD with power-loss protectiontens of microseconds
Network block volume in the cloudaround a millisecond or more

The consequence is a hard ceiling. A writer that syncs after every event can acknowledge at most about one event per fsync time: with a 1 ms fsync, about 1,000 durable events per second, however small the events are. The escape is group commit: write many events, sync once, and acknowledge all of them. Ignoring per-event overhead, 100 events per sync gives an upper bound near 100,000 per second; real throughput also includes copying, writing and scheduling.

The curve flattens because per-event work starts to dominate once the sync is shared widely. The price of batching is latency: an event may wait for the batch it joins plus the sync in flight. The neat trick is natural batching: no timer at all. While one sync is in flight, new events pile up, and the next write and sync take whatever has piled up. Under light load batches are small and latency is low; under heavy load batches grow by themselves. You will build exactly this in the durable log writer.

Concurrency patterns for file access

SituationPatternWhy
Many producers append to one logOne writer thread owns the file; producers hand it events through a queueOrder comes free from the queue, and the writer can batch and sync once per batch
Threads read or write disjoint regions (a parallel copy, fixed-size records)Positional I/O, no lockNo shared offset, no shared bytes, so nothing to protect
Ranges may overlap (a byte store with write(offset, data))Range locks: one lock per block, taken in ascending block orderCalls on disjoint blocks can proceed together; byte ranges within one block still conflict; ascending order rules out lock cycles
Writes smaller than a block on a block deviceLock the block, read it, modify the bytes, write it backWithout the lock, two writers to different bytes of one block can erase each other's change, a lost update on disk
Coordinating separate processesOS file locks (fcntl record locks, FileChannel.lock)Traditional POSIX record locks and Java file locks coordinate processes, not threads within one process

That last row catches people. Java's FileLock is documented as held on behalf of the whole JVM and unsuitable for controlling access between threads of the same JVM; a second overlapping lock from the same JVM throws OverlappingFileLockException. POSIX fcntl record locks also belong to the process, and closing any descriptor for the file releases all of that process's locks on it. Between threads, use your own locks.

These fragments assume validated nonnegative ranges within a fixed store, no overflow in offset + length, and an initialized lock array large enough for every block. Java callers release with unlockRange in a finally block; C++ callers retain the returned guards until all I/O finishes. Empty ranges acquire nothing.

With a huge store you cannot afford a lock per block, so you stripe: block b uses lock b % S. Then sort and deduplicate the stripe numbers before locking, because consecutive blocks wrap around the stripes, and locking in block order would take stripes out of order and could deadlock. With std::mutex, deduplication also matters because locking the same mutex twice is undefined behavior.

Worked example: is it durable yet?

A Java service handles append(event) like this: it writes the event to a BufferedOutputStream, calls flush(), and returns "OK". Walk an event through and ask, at each point, whether a power cut loses it.

  1. After write into the BufferedOutputStream: the bytes may still be in process memory, unless this write filled or bypassed the buffer. Neither a process-crash nor a power-loss guarantee follows from the call alone.
  2. After flush(): the bytes are in the page cache. A process crash no longer loses them, and other processes can read them. A power cut can still lose them, and the service has already said "OK". That is the bug.
  3. Fix: write through a FileChannel and call force(false) before acknowledging. Now each acknowledgement costs one sync, so throughput falls to roughly one event per fsync time.
  4. Fix the throughput: let one writer thread take every waiting event, write them together, force once, and then acknowledge all of them. With a 1 ms sync and 100 events per batch, up to 100,000 events per second before per-event costs, under this illustrative steady load.

The numbers behind step 4: per batch, about 1 ms of sync plus 100 events times 2 microseconds of copying, so 1.2 ms for 100 events, about 83,000 events per second. An accepted event in this drain-all model typically waits for the current batch plus its own. Two batch times is not a universal bound: queueing before admission, disk stalls, scheduling delays and batch caps can add more.

Common mistakes

  • Treating flush as durable. flush() reaches the page cache, not the disk. Acknowledge after fsync or force.
  • Sharing a descriptor's offset between threads. seek then write from two threads puts data in the wrong place. Use positional I/O.
  • Ignoring short reads and writes. One read call may return fewer bytes than asked. Loop until the buffer is full, and handle end of file.
  • Forgetting the directory. A newly created or renamed file can vanish after a crash even though the file itself was synced.
  • Using file locks between threads. FileLock and fcntl locks are per process. They do not protect one thread from another.
  • Retrying a failed fsync and carrying on. The data may already be gone. Fail the pending writes.
  • Syncing inside the producers' lock. Every producer then waits for the disk one at a time. Sync from a single writer, outside the queue's lock.

In the interview

At Databricks this knowledge is examined through the event writer: candidates were asked about the cost of fsync, why batching helps, and what durability guarantee appendEvent can give. At Rubrik it shows up as code: copy a file with open, pread, pwrite and close; byte-level read, write and seek over a block API; and a byte store with write(offset, data) and read(offset, len) that must then become concurrent, where a candidate proposed range locks so non-overlapping calls do not block each other.

An ordinary file write can return with bytes only in process memory or the page cache; durability needs a successful sync of the required strength, so I acknowledge an event only after the sync that covers it. If a measured sync takes one millisecond, syncing per event caps us near a thousand events a second, so I use group commit: one writer thread drains everything that queued up during the last sync, writes it with a short-write loop, syncs once, and then completes all of those events.

Follow ups: "what if fsync fails?" (fail every pending event and stop accepting; do not retry and pretend), "what about a crash in the middle of a write?" (records need a length and a checksum so recovery can find and drop a torn tail), and "how do readers see new data?" (through the page cache, as soon as it is written, even before it is synced).

Senior depth

  • fdatasync and file growth. Appending changes the file size, and the size is metadata that fdatasync must sync. Preallocation can reduce allocation work. To avoid size changes, extend and sync the logical file first, then write within it using explicit offsets; O_APPEND would instead write after that size. Space reservation with FALLOC_FL_KEEP_SIZE alone does not stop later file growth, and other metadata work can remain.
  • Bypassing the page cache. O_DIRECT on Linux (with aligned buffers and offsets) or F_NOCACHE on macOS skips the page cache, so the database manages its own cache and memory. It does not by itself make writes durable; you still sync.
  • Torn writes. A crash can leave a record half written. Use bounded lengths and checksums to detect an incomplete tail before appending again. Corruption inside an acknowledged prefix needs repair or fail-stop handling; do not silently truncate acknowledged data.
  • Memory-mapped files. For a shared writable file mapping, use msync(..., MS_SYNC) on POSIX or MappedByteBuffer.force() in Java to request persistence. A private mapping does not update the file. Mapping visibility still needs synchronization, and platform/device-cache caveats still apply; FileChannel.force is not guaranteed to persist mapped-buffer changes.
  • Group commit everywhere. Databases batch their log flushes the same way, and Linux journaling file systems can satisfy several concurrent fsync callers with one journal commit. The pattern you build by hand is the one the whole storage stack uses.

API references: Java 21 FileChannel, Files.move, Linux sync semantics, Apple sync semantics, PostgreSQL sync-error handling, and OpenJDK 21 macOS forcing.

Key takeaways

  • Threads sharing a descriptor share its offset; positional I/O (pread, pwrite, FileChannel with a position) removes it, and disjoint ranges then need no lock.
  • Loop on every read and write: short transfers and interrupted calls are normal.
  • flush reaches the kernel's page cache; only fsync or force makes data durable, and new or renamed files need their directory synced too.
  • One fsync per event caps throughput at roughly one event per sync time; group commit shares each sync across a batch.
  • Use range locks for overlapping access; OS file locks are for processes, not threads.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A service uses an ordinary buffered stream over a local file, with no synchronous-open option. It writes an event, successfully flushes the stream and replies "saved", without syncing. The machine then loses power. What can happen?
Why. For this buffered file stream, flush sends buffered bytes to the kernel. The bytes may reach storage later, so loss is possible rather than certain. A power cut can lose them even if the process never crashed first. A successful durability sync of the required platform strength, plus durable directory publication where needed, must precede the receipt. Append mode controls placement, not persistence; the base OutputStream.flush() alone has no such flushing guarantee.
Two threads share one file descriptor. Each runs lseek(fd, myOffset, SEEK_SET) and then write(fd, myRecord, 64). What can happen?
Why. Per-call offset handling does not make the pair atomic: the other thread can move the shared offset between your seek and your write. The kernel neither rejects that second seek merely because another thread is writing nor groups each thread's calls into a transaction. pwrite(fd, buf, 64, myOffset), or FileChannel.write(buf, position) in Java, takes the offset as an argument and leaves the shared one alone, so disjoint ranges need no application lock.
A log writer thread calls fsync after every single event, and one fsync takes about 1 ms on this disk. Ignoring per-event work, what is its approximate throughput ceiling?
Why. Each acknowledgement waits for its own sync, so the writer completes at most one event per millisecond, about 1,000 a second, whether the event is 10 bytes or 1,000. Ignoring copying and writing costs, sharing each sync across 100 events lifts the ceiling near 100,000 a second, which is the whole case for group commit.
Four threads must write fixed-size records into disjoint regions of one open file. Each thread owns its buffer, append mode is off and nobody truncates the file. Which approach needs no application lock?
Why. Positional writes neither use nor move the shared position, and the regions do not overlap, so there is nothing to protect. Setting the position and then writing is the shared-offset race again. Separate buffered wrappers do not by themselves reserve the intended file ranges and may share or conflict over offsets. Append mode puts every record at the end, not at its own offset.
A shared regular file starts with offset zero. Thread A completes pwrite(fd, "A", 1, 8) or Java ch.write(bufferOfA, 8). After A joins, B prints the descriptor/channel position. No other I/O occurs, and append mode is off. What prints?
Why. The explicit offset determines where A writes, but positional I/O leaves the shared position unchanged at zero. One byte was transferred and the file may grow to nine bytes, but neither the byte count nor file size becomes the shared position. A plain write after seeking to eight would leave position nine.
You must replace config.txt so that after a crash you find either the complete old version or the complete new one. Assume an already durable old file and a supporting local file system. Which steps belong in the procedure? Select all that apply.Select all that apply
Why. Writing and syncing a temporary file makes the new bytes durable without touching the old file; rename within one file system atomically swaps which content the name points to; syncing the directory makes the rename itself durable. Deleting first opens a window with no file at all, and overwriting in place can leave a mix of old and new bytes after a crash.
Java onlyWhich Java call requests content persistence without requiring all metadata to be forced, although the OS may do more?
Why. force(false) requests content persistence; force(true) explicitly requires metadata too. The exact syscall mapping is OS-dependent. Buffered file-stream flushing does not request durability, and garbage collection has no persistence contract.
C++ onlyYou wrote a file with std::ofstream and called flush(). How do you make the data durable?
Why. Successful flush() and close() push buffered file bytes towards the kernel but promise no stable-storage sync. Repeating flush or yielding the thread adds no durability guarantee. C++20 has no standard fsync or stream native-handle API, so design durable file access around an OS descriptor or a library that exposes one.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
A Databricks interviewer asks: "What can appendEvent promise when it returns? Explain flush, fsync and fdatasync on the way."
Model answer

A successful ordinary OS file write transfers the returned number of bytes into the kernel's page cache; at that point the data survives my process crashing, and other readers can see it, but a power cut or kernel crash can lose it. flush only moves bytes from my own buffer into the page cache, so it is no stronger. fsync makes the kernel write the file's dirty data and metadata to the device and, on Linux, ask the device to flush its write cache, and it returns only when that is done; fdatasync does the same for the data and only the metadata needed to read it back, such as the file size, so it is often cheaper. In Java the analogous content-plus-metadata and content requests are FileChannel.force(true) and force(false), with platform-dependent implementations.

So appendEvent can promise durability only if it returns, or completes its future, after the fsync that covers its event has succeeded. If the sync fails, every event it covered must fail too, and I would stop accepting writes rather than retry the sync, because the kernel may have dropped the data. If measured sync latency is around a millisecond, I would batch: one writer thread syncs once for everything that queued during the previous sync and then completes all those events, which keeps the guarantee and raises throughput by the batch size.

Numbers
On a disk where one fsync takes 2 ms, copying an event into the batch costs 5 microseconds. (a) With one fsync per event, what is the most events per second you can acknowledge? (b) With batches of 200 events, what is the throughput? Assuming an already admitted event joins the very next full batch and no scheduling or device stalls, how long can it wait? (c) You need 50,000 events per second: what is the smallest batch size that works?
Model answer

(a) Each event costs 2 ms plus 0.005 ms, about 2 ms, so about 500 events per second.

(b) A batch of 200 costs 2 ms plus 200 times 0.005 ms, which is 3 ms, so 200 events per 3 ms, about 66,700 events per second. An event that arrives just after a batch started waits for that batch (up to 3 ms) and then for its own (3 ms), so about 6 ms in the worst case.

(c) A batch of b events takes 2 + 0.005b milliseconds, and we need b divided by that to be at least 50 events per millisecond: b is at least 50 times (2 + 0.005b), so b is at least 100 + 0.25b, so 0.75b is at least 100, so b is at least about 134 events per batch. This is a capacity calculation, not a guaranteed batch size or latency. Under smooth arrivals the corresponding natural-batching equilibrium is about 133.3 events; burstiness and scheduling change the actual batches, so leave headroom.

Design
Rubrik follow up: you built a byte store with write(offset, data) and read(offset, len) over a file. "Make it concurrent, so calls that do not overlap never block each other." Describe your design and any limits of block locking.
Model answer

For strict byte-range independence I need a range-lock manager: under a short metadata mutex, wait while an active interval overlaps mine and either interval is a write, register my interval, then release the mutex for positional I/O. Remove the interval and wake waiters on completion. Even disjoint calls briefly contend for metadata, but they do not wait through each other's I/O. Block locks are simpler but weaken that requirement: disjoint byte ranges in one block conflict, and stripes add further false conflicts.

For that simpler contract I divide the store into fixed blocks, say 4 KB, and keep one lock per block, or for a very large store a fixed array of S stripe locks where block b uses stripe b mod S. Every call computes the blocks its range touches and locks them in ascending order (for stripes: the sorted, deduplicated stripe numbers), does its work with positional reads and writes, and unlocks. Without striping, two calls that touch no common block take disjoint locks and can run in parallel; overlapping calls serialize on the shared blocks; ascending order means no cycle of waits, so no deadlock.

If the underlying device only reads and writes whole blocks, a write that covers part of a block must read the block, change the bytes and write it back, and that read-modify-write must happen under the block's lock, or two writers to different bytes of the same block erase each other's changes. If reads dominate, each block can have a read-write lock so overlapping readers share it. I would say the trade-off out loud: a lock per block costs memory for big stores, which is why striping exists, at the price of occasional false conflicts between unrelated blocks that share a stripe.

"Our service flushes the file and says saved, but records disappear after a power cut. Walk me through the fix."
What a strong answer covers
  • A buffered-stream flush is not a durability acknowledgement
  • Trace process buffer, kernel page cache, device cache and stable storage
  • Use a successful platform-appropriate sync before acknowledging; flush alone is insufficient
  • Persist the parent directory when creating or replacing the file
  • Treat storage errors as uncertain outcomes and stop accepting writes
  • Share each sync across a batch without weakening acknowledgement order
How a senior would say it
I would move the saved response after a successful durability sync. Flushing a buffered file stream usually moves bytes from the process into the operating system's page cache. That can survive the process dying, but not the machine losing power. The drive may have another volatile cache, so the operation must cover that boundary too. On Linux I use fsync; on macOS the C++ path requests a full device flush. In Java I use FileChannel.force and check the local provider's guarantees. For a newly created file I also persist the parent directory, because durable contents are useless if the filename disappears. If the sync reports a storage error, I fail the pending requests and stop using that log. I cannot assume the bytes are absent, or that another sync will repair them. Once correctness is established, I batch. If a measured sync takes one millisecond, syncing every event caps one writer near a thousand events per second before other costs. Sharing that sync across a hundred events raises capacity, but every receipt still waits for the successful sync covering its own bytes. I would test acknowledgement timing with a fake disk that pauses inside sync; successful readback alone does not test power-loss durability.

Out loudabout 60 s
"Two threads seek to different offsets, then write, and records land in the wrong places. What would you change?"
What a strong answer covers
  • Seek and write are separate operations on a shared open-file offset
  • Give a concrete interleaving that redirects one write
  • Use positional I/O and advance by actual transfer counts
  • Keep buffers private and coordinate overlapping ranges or truncation
  • Block and stripe locks can serialize even disjoint byte ranges
How a senior would say it
I would use positional I/O so each write carries its destination offset. With a shared descriptor, A can seek to offset four thousand, B can seek to eight thousand, and then A writes at B's position. Each call can be correct while the pair is wrong. A shared lock around both calls fixes that, but serializes unrelated work. Positional writes avoid the shared offset: pwrite in C++, or FileChannel.write with a position in Java. I loop on short writes and advance by the actual count, with a separate buffer per thread. Disjoint ranges then need no application lock, assuming nobody truncates the file. Overlapping updates still need coordination, especially a block device's read, modify, write sequence. Block locks are simple but can conflict for disjoint bytes in one block; stripe locks add more false conflicts. Positional I/O fixes placement, not durability.
