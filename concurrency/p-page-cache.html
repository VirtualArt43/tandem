Page cache with write-back

Thread-safe structureshard50 minRubrik system coding round, the "logical memory unit"Rubrik

Rubrik asked for a "logical memory unit": pages of entries served from memory, loaded from slower physical memory on a miss, with queries for the most recent entries, and then "make it thread-safe". Adding a size limit makes it a real cache, and the hard part is the moment a dirty page is on its way back to the store while another thread wants it again.

The task

A page is an append-only list of entries (64 bit numbers here). Every page lives in a slow PageStore (the physical tier) that the harness gives you. Build a PageCache (the logical tier) that holds at most capacity pages in memory:

  • append(pageId, entry) adds the entry at the end of the page. If the page is not in memory, load it from the store first.
  • latest(pageId, k) returns the k most recent entries of the page, newest first (fewer if the page is shorter). A page the store has never seen is empty.
  • residentPages() returns how many pages are in memory right now, counting pages that are still loading.

When a page must come in and the cache is full, evict the least recently used page that is fully loaded. A page that was appended to since it was loaded is dirty: write it back with store before it leaves memory. A clean page is simply dropped.

Rules:

  • Never call load or store while holding a lock that other pages need. A slow page must not stall reads and appends of other pages.
  • Each page is loaded at most once at a time: when eight threads miss the same page together, one loads it and the others wait for that load (single-flight).
  • While a dirty page is being written back, nobody may append to it (the append would miss the store) and nobody may load it again (the load would read the old copy). Those callers wait until the write-back finishes.
  • If load throws, the caller that ran it gets the exception and nothing is cached. Callers that were waiting for that load either try the load again or get the same exception; either way a later call loads the page afresh.
  • store never throws in this problem.

Worked example

With capacity 2: append(1, 12) loads page 1 (the store had [11]), so page 1 is now [11, 12] and dirty. latest(2, 5) loads page 2. latest(1, 1) returns [12] and makes page 1 the most recently used. latest(3, 5) needs a slot: page 2 is the least recently used and clean, so it is dropped without a write. latest(2, 5) needs a slot again: now page 1 is the least recently used, and dirty, so store(1, [11, 12]) runs before it goes. A later latest(1, 5) loads it back and returns [12, 11].

What the tests check

  • From one thread: appends, latest newest first, short pages, pages preloaded in the store, a new page, and one load per page.
  • Eviction picks the least recently used page; a clean page is dropped without a write; a dirty page is written back with exactly its entries.
  • A burst: 8 threads miss the same page at once and it is loaded exactly once, with every caller getting the same answer.
  • Four cold pages load in parallel (at least 2 loads in flight together), and a hit plus an append on loaded pages take under 200 ms while another page spends 600 ms loading.
  • An append that arrives while its page is being written back (the store holds the write for 300 ms) is not lost: afterwards latest(1, 10) is [13, 12, 11], and the page was never loaded while its write-back ran.
  • A load that throws reaches its caller as an exception, a caller waiting on it does not hang, and a later call loads the page again.
  • Stress: 8 threads, 10 pages, room for 3, random appends and reads. Every latest(k) answer is consistent (only this page, each writer's entries newest first with no gaps), each thread reads its own appends, residentPages() never exceeds 3, no page is loaded twice at once, and at the end every page holds exactly every entry appended to it, in order.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Thread-safe caches: LRU, TTL and single-flight

Open them one at a time. Each one gives away a little more.

Start with the single threaded design: a map from page id to an in-memory page (a list of entries, a dirty flag, a last used stamp) and a capacity. Then ask what a page can be doing while the lock is released for slow I/O. It can be loading, it can be ready, or it can be on its way back to the store.
Give each page in the map a state: LOADING, READY or WRITING_BACK. Inserting a LOADING entry is the claim: whoever inserts it loads the page, and everyone else who finds the entry waits. Use one lock for the map and one condition that you signal whenever a page changes state.
The trap is eviction. If you remove the page from the map and then write it back without the lock, a miss on that page in between loads the old copy from the store. Keep the evicted page in the map, marked WRITING_BACK, until store returns; only then remove it and signal. Count it as gone for capacity purposes as soon as you start, so another page can take its slot.
Write the main loop as "look at the map, then act": READY means use it; LOADING or WRITING_BACK means wait and look again; absent and full means evict one READY page (which may release the lock) and look again; absent with room means claim and load. Every time you come back from waiting or from I/O, start the loop from the top.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why not a read-write lock so that many latest calls run together?
Because latest is a write: it moves the page to the most recently used position, and it may load or evict. This is the classic trap with every LRU structure. If you want concurrent readers, make the recency update cheap and racy (an atomic timestamp per page, approximate LRU) or shard the cache so each shard has its own lock and its own LRU.
One lock guards every page. How would you scale it?
Stripe by page id: N shards, each with its own lock, map and capacity of C / N, so pages in different shards never contend. The cost is an approximate global LRU, which caches in practice accept. The slow I/O already runs without the lock, so the remaining lock holds are short.
The process crashes. What is lost, and how do you fix it?
Every dirty page that was not written back. Either write each append through to a write-ahead log and fsync it before append returns (then the cache can be lost and rebuilt), or accept the loss window and flush dirty pages periodically. Add flush() and close() that write every dirty page back, using the same WRITING_BACK state so appends wait.
Pages grow forever, but queries only want the latest k. What changes?
Keep only the newest K entries of each page in memory (a ring buffer per page) and append the rest to the store as a log, so a page's memory is bounded. If queries can ask for any k, split pages into fixed size segments and load only the segments a query needs.
A load hangs forever. What happens to the callers waiting for it?
They hang too, because they wait for the LOADING state to end. Give the load a timeout (most storage clients have one) and treat a timeout like a failure: drop the claim, signal, and throw. Waiters can also wait with a deadline (awaitNanos, wait_until) so no caller blocks past its own budget.
Rubrik's follow up is only "make it thread-safe". What is the smallest correct answer?
One lock around everything, including the load and the write-back. It is correct and easy to explain, and it is the right first step to say out loud. Then say why it is not enough (a slow load blocks every other page) and move the I/O out of the lock with the per-page states above.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

This is the monitor pattern with a small state machine per page. One lock guards the map, the resident count and every page's state; one condition is signalled whenever any page changes state. The slow load and store run with the lock released, and the page's state tells everyone else what that page is doing while the lock is free: LOADING (someone is loading it, wait), READY (use it), WRITING_BACK (it is leaving, wait, then load it fresh).

Invariants

  • At most one entry per page id is in the map, so at most one thread loads or writes back a given page at a time.
  • resident counts LOADING and READY pages and never exceeds capacity. A WRITING_BACK page does not count: its slot is already promised to someone else.
  • Appends and reads only touch READY pages, and only while holding the lock, so no eviction can start in the middle of one.
  • The store's copy of a page is current whenever the page is absent from the map: it is removed only after its write-back has finished.

Why each primitive

  • One ReentrantLock or std::mutex for the map, the LRU stamps and the count, because eviction reads all of them together.
  • One condition, signalled to all. Waiters wait for different things (a load to finish, a write-back to finish, a slot to free up), and every state change can matter to any of them. In C++ the wait uses a version counter as its predicate, so a wakeup with no change goes back to sleep.
  • Explicit unlock and relock around I/O. This is the one place where you release the lock in the middle of an operation. Every pass of the loop afterwards looks at the map again, because anything may have changed.
  • A per-page state instead of per-page locks. Nobody ever holds two locks, so there is no lock order to get wrong.

Other pitfalls

  • Calling load with the lock held: correct, but every page waits for every load. The parallel test catches it.
  • Checking the map, releasing the lock to load, then inserting: two threads that miss together both load, and the second insert overwrites appends made to the first copy.
  • Evicting a LOADING page: its loader would publish a page that is no longer counted.
  • Forgetting to remove the LOADING claim when load throws: every later caller for that page waits forever.
  • Waiting with if instead of a loop: after a wakeup the page may be in a different state, or gone.

Cost

A hit is O(1) plus O(k) to copy the answer. A miss with a full cache scans the resident pages to find the least recently used one, O(C); for large C use a linked list in recency order (Java's LinkedHashMap with access order) to make it O(1). The lock is held only for in-memory work.

How to say it in the interview

I keep a map from page id to a page with a state: loading, ready or writing back, under one lock with a condition. Inserting a loading entry is the claim, so each page is loaded once; others wait on the condition. The slow load and the write-back run without the lock. When I evict a dirty page I keep it in the map as writing back until the store returns, because if I removed it first, a concurrent append would reload the old copy and one version would overwrite the other. A page being written back no longer counts against capacity, so the next page can start loading right away.
