Double-checked locking and lazy initialization

Why classic double-checked locking is broken, the correct versions in Java and C++, the simpler idioms that replace it, and when lazy initialization is worth it.

Asked atMicrosoft
Before this:Safe publication, immutability and final fieldsvolatile in Java, std::atomic in C++

"Write a thread-safe singleton" is one of the most common warm-up questions in concurrency interviews, and its most famous answer, double-checked locking, was broken for years in both Java and C++. Knowing why it broke, and the one-line fixes, is a quick way to show you understand the memory model rather than reciting patterns.

In plain words

The office coffee machine has to be switched on once each morning. The first person in switches it on; everyone after that just pours. Without any coordination, two early arrivals both flip the switch (two machines' worth of work, or a broken machine), or someone sees the light on and pours while it is still heating (a half-ready result).

Double-checked locking is the obvious fix: glance at the light without queueing; if it is off, join the queue for the switch, look again once it is your turn, and only then switch it on. The glance is the "first check", the second look is the "second check". The catch, as you will see, is that the glance must be a real look at the machine, not a peek at a reflection that can show the light on before the water is hot.

The problem: lazy initialization

Lazy initialization means building an object the first time it is needed, usually because it is expensive and might never be used. Across threads, "if it does not exist yet, create it" is a check then act on shared state, so the naive version has two bugs at once:

The simplest correct fix is to make the whole method synchronized (or lock a mutex inside it). It is correct, and an uncontended lock costs only tens of nanoseconds, an order of magnitude estimate. But every call pays it forever, long after the object exists, and under heavy contention every caller queues on one lock. That cost is what tempted people to "optimize" with double-checked locking.

The broken version

Check without the lock; only if the object is missing, take the lock, check again, and create it:

The second check fixes bug 1: only one thread creates the object. Bug 2 is still there. The first check reads the shared field without any synchronization, so it is the unsafe publication from the safe publication lesson in disguise. The writer's "allocate, construct, store the reference" can become visible to other threads as "allocate, store the reference, construct": the compiler or CPU may move the store of the reference ahead of the constructor's writes. A thread doing the first check then sees a non-null reference, skips the lock entirely, and uses an object whose fields are still empty.

This was not a theoretical worry. Around 2000, a group of Java experts including Bill Pugh, Doug Lea and Joshua Bloch published "The 'Double-Checked Locking is Broken' Declaration" explaining that no amount of cleverness made it work under the original Java memory model. The fix arrived with the new memory model (JSR-133) in Java 5, which gave volatile the acquire and release meaning it has today. C++ had no memory model at all until C++11, and Scott Meyers and Andrei Alexandrescu's 2004 article on the "perils of double-checked locking" made the same point for C++.

The fixes: volatile in Java, acquire and release in C++

The whole repair is to make the first check a synchronized read: a volatile field in Java, a std::atomic loaded with acquire and stored with release in C++. Now the store that publishes the reference happens after the constructor's writes (release), and a thread that sees a non-null reference also sees those writes (acquire). This program races eight threads into the first call and counts constructions.

Details an interviewer may probe:

  • Why the local variable c (or p)? On the fast path, the field is read once instead of twice (once to check, once to return). With a volatile field, that saves a synchronized read on every call. It is the form Effective Java recommends for lazily initialized instance fields.
  • Why can the second check be relaxed in C++? It runs under the mutex, and the only store happens under the same mutex, so the lock already orders it. The first check must be acquire because it runs without the lock.
  • Why publish last? The store of the reference must come after construction is complete. instance = new Service(); instance.init(); publishes before init() runs, and volatile cannot save that.
  • What does the fast path cost? On x86 a volatile or acquire load is an ordinary load, so after initialization the check is nearly free; on ARM it is a load-acquire instruction.
  • Is the static mutex itself safe from initialization order problems (C++)? Yes. std::mutex has a constexpr default constructor and the atomic pointer starts from a constant, so both are constant initialized before any code runs, and the first caller can never find them unbuilt.

Let the language do it: the holder class and the function-local static

Both languages already contain a correct, lazy, thread-safe one-time initialization, built into the runtime. For a singleton, use it and skip double-checked locking entirely.

  • Java: the holder class idiom. The JVM initializes a class the first time it is actively used, and the Java Language Specification (12.4.2) requires that initialization to happen exactly once, under a lock, with every later user seeing the result. Put the instance in a static field of a private nested class: Holder is initialized only when instance() first touches it. After that, there is no lock and no volatile read at all.
  • C++: the function-local static. Since C++11, the standard requires that if several threads reach the declaration of a local static at once, exactly one initializes it and the others wait. Compilers implement this with a hidden guard flag checked by an acquire load, which is double-checked locking done correctly inside the compiler.

The other idioms: an enum in Java, std::call_once in C++

Java's enum singleton. Effective Java calls a single-element enum often the best way to implement a singleton: the JVM guarantees exactly one instance, it is thread-safe through class initialization, and unlike a class with a private constructor it cannot be duplicated by serialization or reflection. It is created when the enum class is initialized, which happens on its first use.

C++'s std::call_once. When the lazily built thing is a member of an object rather than a global, a function-local static does not fit, because there would be one per program, not one per object. std::once_flag plus std::call_once runs a function exactly once per flag; concurrent callers wait until it finishes, and if it throws, the flag stays unset and the next caller tries again.

Do you even need lazy initialization?

Often not. A static final field initialized eagerly (Java) or a global constructed at startup (C++) is simpler and already thread-safe, and it moves the cost to startup instead of to the first unlucky request. Prefer lazy initialization when the object is expensive and may never be used, or when its dependencies are not ready at startup.

  • Latency. Lazy init makes the first request pay. Services often warm such objects up eagerly at startup for exactly that reason.
  • C++ static initialization order. Globals in different source files are initialized in an unspecified order, so one global's constructor can use another that is not built yet (the "static initialization order fiasco"). A function-local static fixes it, because the object is built on first use.
  • Testability. A singleton is hidden global state: tests cannot replace it and tests can leak state into each other. In most designs, creating one instance at startup and passing it to whoever needs it (dependency injection) beats a global accessor. Saying so in an interview is a senior signal.

Worked example: picking the idiom

  1. A process-wide registry of codecs, needed by almost every request. Not worth lazy init: an eager static final field in Java or a global (or function-local static) in C++. If it is lazy, use the holder class or a function-local static, never hand-written double-checked locking.
  2. A machine learning model that takes 3 seconds to load and is used by one rare endpoint. Lazy: holder class or function-local static. Consider loading it at startup in the background so the first request does not wait 3 seconds.
  3. A per-connection field computed by a network call the first time it is asked for. One per object, so not a static. Java: a volatile field with double-checked locking (the demo above). C++: std::call_once with a per-object std::once_flag.
  4. A connection pool whose creation can fail and must be retried. In C++, std::call_once passes the exception to its caller and leaves the flag unset, so the next call tries again (a function-local static behaves the same way). In Java, avoid the holder class here: if a static initializer throws, the first caller gets ExceptionInInitializerError and every later caller gets NoClassDefFoundError; the class can never be initialized again. Use double-checked locking with a volatile field, which simply tries again on the next call.

Common mistakes

  • Double-checked locking without volatile (Java) or without atomics (C++). The unlocked first read races with the publishing write and can return a half-built object.
  • Publishing before initialization finishes. instance = new Service(); instance.configure(); lets other threads use an unconfigured instance through the fast path. Build completely in a local, then publish.
  • Relaxed ordering on the publishing store or the first check in C++. The store must be release (or seq_cst) and the unlocked load must be acquire (or seq_cst).
  • Locking on different objects. The second check must run under the same lock that every creator uses.
  • Hand-writing what the language provides. For singletons, the holder class or enum (Java) and the function-local static (C++) are correct by construction and faster to write and review.
  • Recursive initialization. If a static's initializer calls the function that owns it, C++ says the behavior is undefined (it may deadlock or throw), and in Java the same thread sees the class half initialized. Keep initializers simple.
  • Ignoring failure. A Java holder class whose initializer throws can never be retried; plan for it.

In the interview

It arrives as "implement a thread-safe singleton" (a Microsoft L62 loop in Hyderabad paired it with printing 1 to 100 from three threads), as "make this lazy getter thread-safe", or in code review of a classic broken double-checked lock. One 2024 Google L5 report from Bengaluru describes fixing a C++ concurrency problem "using mutexes and double locking approach" without further detail: if you use that phrase, be ready to explain exactly why your version is correct.

For a singleton I would let the runtime do it: in Java the holder class idiom, where the JVM initializes the nested class exactly once on first use, or an enum; in C++ a function-local static, which has been thread-safe since C++11. If I need double-checked locking, for a lazily initialized instance field, the field must be volatile in Java, or an atomic loaded with acquire and stored with release in C++. Without that, the unlocked first check can see the reference before the constructor's writes and return a half-built object.

Follow ups to expect:

  • "Why exactly is the version without volatile broken?" The reference store can become visible before the constructor's writes, and the first check skips the lock, so no happens-before edge reaches the reader.
  • "Why does the holder idiom work, and why is it lazy?" Class initialization is synchronized by the JVM and happens on first use of Holder.
  • "Is a C++ function-local static thread-safe?" Yes, since C++11. Before that the standard promised nothing (GCC already guarded them; Microsoft's compiler only from Visual Studio 2015), and GCC and clang still accept -fno-threadsafe-statics, which turns the guard off.
  • "If every field of the object is final, do you still need volatile?" Java's final field rule (JLS 17.5) means a thread that sees the reference sees the final fields as the constructor set them, so the half-built object goes away for those fields. You must still read the field once into a local, and any non-final state is unprotected, so say it would work and that you would still write volatile.
  • "What if the constructor throws?" call_once retries; a C++ function-local static also retries on the next call; a Java holder class is broken for good.
  • "Why does Bloch recommend an enum?" One instance guaranteed by the JVM, including against serialization and reflection attacks.
  • "Should this be a singleton at all?" Consider passing one instance explicitly; singletons complicate testing.

Senior depth

The racy single-check idiom. If the lazily computed value is a primitive (not long or double) or an immutable object with all final fields, and computing it twice is harmless, Java code can skip the lock entirely: read the plain field once into a local, and if it is 0 or null, compute, store it and return the local. Two threads may both compute it, and that is acceptable. String.hashCode() caches its hash this way. The local matters: with two plain reads of the field, the Java memory model allows the second to return the old 0 or null even after the first saw the new value. It is a data race, deliberately, and it depends on final field semantics and on ints not tearing. In C++ the same code is undefined behavior: use a relaxed atomic for a plain number, but a pointer to an object still needs a release store and an acquire load, because C++ has no final field rule.

Class initialization deadlocks. While one thread runs a class's static initializer, the JVM makes every other thread that needs that class wait. If class A's initializer touches class B while another thread is initializing B, which touches A, the two threads deadlock with no lock visible in your code. Keep static initializers free of cross-class work and of thread starts.

How C++ implements function-local statics. GCC and clang emit a guard variable and a fast path that does an acquire load of it. Only if the object is not built do they call into the runtime: __cxa_guard_acquire takes a lock and checks again, the compiled code runs the constructor, and __cxa_guard_release marks the guard done and wakes any waiters (or __cxa_guard_abort resets it if the constructor throws). That is double-checked locking, written once by compiler engineers and exercised by every C++ program that uses a local static, which is the best argument for using it.

Key takeaways

  • Naive lazy init is a check-then-act race plus an unsafe publication.
  • Classic double-checked locking fixes the double construction but not the publication: the unlocked first check can see a half-built object.
  • The fix: a volatile field in Java; an atomic with acquire on the first check and release on the publishing store in C++. Publish only a fully built object.
  • For singletons, prefer the runtime's own lazy init: the holder class or enum in Java, the function-local static in C++. For per-object lazy fields, std::call_once or volatile double-checked locking.
  • Ask whether lazy init is needed at all: eager init is simpler, and singletons hurt testability.

Answer each question, then read why. Your score is saved for your module test.

In classic double-checked locking without volatile (Java) or atomics (C++), what can a second thread observe?
Why. The second check under the lock already prevents double construction. The remaining bug is the unlocked first check: it can see the reference before the constructor's writes become visible, skip the lock, and use a half-built object.
Which single change makes the classic Java double-checked locking version correct? (The C++ counterpart of the right answer is an atomic pointer loaded with acquire and stored with release.)
Why. A volatile write publishes everything written before it, and the volatile read on the fast path receives it: the same release and acquire pair as the C++ atomic. The field cannot be final because it is assigned lazily, and more checks do not add a happens-before edge.
Inside the locked section of a correct, volatile-based double-checked lock, the code runs instance = new Service(); instance.configure();. What is wrong?
Why. Publication happens at the volatile (or release) store, and the fast path never takes the lock. Anything done to the object after the store is invisible to that guarantee. Build and configure in a local variable, then publish.
Why is the Java holder class idiom (or the C++ function-local static) both lazy and thread-safe without any explicit lock?
Why. JLS 12.4.2 makes class initialization a synchronized, once-only step that happens on first active use, and C++11 requires the same for function-local statics. Both are lazy because the work happens on first use, not at program start.
Which situation needs a per-object lazy initialization tool (double-checked locking on a volatile field in Java, std::call_once in C++) rather than the holder class or a function-local static?
Why. Holder classes and function-local statics give one instance per program. A per-object lazy field needs per-object state: a volatile field with double-checked locking in Java, or std::call_once with a per-object std::once_flag in C++. The other options are better served by eager or runtime-managed initialization.
Java onlyA holder class's static initializer throws an exception the first time it runs. What happens on later calls to instance()?
Why. A class whose initialization failed is in an erroneous state for the life of the class loader; the JVM never retries it. If initialization can fail transiently, use double-checked locking on a volatile field, which simply tries again on the next call.
C++ onlyThe function passed to std::call_once throws an exception. What happens on the next call with the same std::once_flag?
Why. An exceptional execution propagates the exception to its caller and leaves the flag unset, so another call (from that thread or another waiting one) runs the function again. That makes call_once a good fit for initialization that can fail transiently.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a thread-safe, lazily created Pricing singleton in your language two ways: once with the idiom you would actually use, and once with double-checked locking done correctly.
Model answer

Version 1 relies on the runtime's own once-only initialization and costs nothing after the first call. Version 2 needs the volatile field (Java) or the acquire load and release store (C++) so that a thread taking the lock-free fast path is guaranteed to see a fully constructed object; the second check under the lock prevents double construction, and the object is published only after it is fully built.

Explain
An interviewer shows you double-checked locking without volatile and says: "The second check is under the lock, so this is safe." Explain, step by step, why it is not, and what fixes it.
Model answer

The second check prevents two threads from both constructing, but it does nothing for threads that never reach the lock. The first check reads the shared field without synchronization. Meanwhile the creating thread does three things: allocate memory, run the constructor, and store the reference. Nothing orders the store of the reference after the constructor's writes as seen by other threads: the compiler or CPU may make the reference visible first, and the reading thread may also read the fields early. So a second thread can see a non-null reference at the first check, skip the lock, and use an object whose fields still hold default values.

The lock does not help that thread, because a lock creates a happens-before edge only between an unlock and a later lock of the same lock, and the fast-path thread never locks. The fix is to make the first check a synchronized read: declare the field volatile in Java, so the publishing write is a release and the read is an acquire, or use a std::atomic in C++ with a release store and an acquire load. Even better for a singleton is the holder class idiom or a function-local static, which let the runtime do the once-only initialization correctly.

Design
A service has a Translator that loads a 2 GB model and is used by one endpoint that gets a few requests an hour. A teammate proposes a lazy singleton. What do you recommend, and why?
Model answer

Lazy creation makes sense here because the object is expensive and rarely used, but I would think about three things before writing a singleton. Latency: a lazy load makes the first request after every deploy wait for a 2 GB load, so I would start loading it in the background at startup (or on the first request, while returning a "not ready" response quickly) rather than blocking a user. Failure: a load can fail transiently, so the initialization must be retryable; in Java that rules out the holder class idiom, because a failed static initializer leaves the class permanently unusable, so I would use a volatile field with double-checked locking or a future that can be replaced on failure; in C++ std::call_once or a function-local static both retry after an exception. Memory: 2 GB for a rarely used feature might justify unloading it after an idle period, which a singleton makes awkward.

Finally, rather than a global accessor, I would create one Translator holder at startup and inject it into the endpoint's handler. The lazy loading can live inside that holder, tests can substitute a fake translator, and nothing else in the code base can reach for global state.

"What exactly does volatile buy you in double-checked locking, and what does it cost on the fast path?"
What a strong answer covers
  • A volatile write is a release: the constructor's writes become visible no later than the reference
  • A volatile read is an acquire: a thread that sees the non-null reference also sees those writes, the edge the unlocked check was missing
  • The second check needs no extra ordering because the lock orders it, which is why the C++ version can load it relaxed
  • Cost: an ordinary load on x86, a load-acquire on ARM; read the field once into a local so each call pays one volatile read
  • What it cannot fix: publishing before setup finishes, so build in a local and publish last
How a senior would say it
It buys a happens-before edge on the path that never takes the lock. A volatile write acts as a release, so everything the constructor wrote is visible before the reference is. A volatile read acts as an acquire, so a thread that sees the non-null reference also sees those writes. That is exactly the edge the unlocked first check was missing. The second check, inside the lock, does not need it, because the lock already orders it against the write made under that same lock. That is why the C++ version can load it relaxed. The cost is small. On x86 an acquire load is an ordinary load, and on ARM it is a load-acquire instruction, so after initialization the fast path is nearly free. I also read the field once into a local, so each call pays for one volatile read, not two. What volatile cannot fix is publishing too early. If you assign the field and then call a configure method, other threads can use the half-configured object, so build everything in a local and publish last.

Likely follow up: Would it still be correct if you removed the second check, the one inside the lock?
