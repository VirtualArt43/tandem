Liveness: deadlock, livelock and starvation

Deadlock, livelock, starvation, convoys and herds: how each one arises, how you spot it in a running system and how you fix it.

1CoredeadlockNvidiaApple
What is a deadlock, and what are the four conditions for one?
Model answer

A deadlock is a set of threads in which every thread is blocked waiting for something that only another thread in the set can give it, so none of them ever moves again. The textbook case: thread A holds lock 1 and waits for lock 2, while thread B holds lock 2 and waits for lock 1.

The four Coffman conditions must all hold at the same time:

  1. Mutual exclusion: a resource can be held by only one thread at a time.
  2. Hold and wait: a thread keeps what it holds while it waits for more.
  3. No preemption: nobody can take a resource away from its holder.
  4. Circular wait: the wait-for graph has a cycle.

Because all four are necessary, breaking any one of them prevents deadlock. Circular wait is broken by a global lock ordering. Hold and wait is broken by acquiring everything at once (std::scoped_lock never blocks while holding part of the set). No preemption is broken by giving locks up: tryLock with a timeout that releases everything and retries (textbooks file this here; many engineers call it breaking hold and wait), or a database aborting a victim transaction. Mutual exclusion is broken by not sharing: immutable data, a single owner thread, or a lock-free structure.

Likely follow up: "Which condition do you break in your own designs?" Circular wait, with a documented lock order, because it costs nothing at run time and is easy to check in review. Mention tryLock with a timeout as the fallback when no fixed order exists.

2Coredeadlocklock-orderingNvidia
Write a money transfer between two accounts that cannot deadlock.
Model answer

The naive version locks from and then to. When transfer(a, b) and transfer(b, a) run together, each thread takes its first lock and waits forever for the other. The fix is one global order: always lock the account with the smaller id first, whatever the direction of the transfer.

In C++ std::scoped_lock (C++17) or std::lock (C++11, then std::lock_guard with std::adopt_lock) locks several mutexes without deadlock regardless of order. Java has nothing like it for intrinsic locks, so you order by a unique, immutable key. If there is no natural key, System.identityHashCode can collide, so add a tie-breaker lock that is taken first when the two hashes are equal.

Likely follow up: "What if one operation touches N accounts?" Sort the accounts by id, drop duplicates (locking one mutex twice self deadlocks), and lock them in that order: in Java with a ReentrantLock per account taken in a loop and released in finally, in C++ with a std::vector of std::unique_lock, since std::scoped_lock needs the count at compile time.

3CoredeadlocklivelockstarvationRubrik
Explain deadlock, livelock and starvation, and how you would tell them apart in production.
Model answer

Deadlock: threads are blocked forever waiting for each other. Two cars meet head on at a one lane bridge and neither reverses. The stuck threads use no CPU (unless they spin on a spinlock).

Livelock: threads are running and keep reacting to each other, but no useful work completes. Two people in a corridor both step aside the same way, again and again. A code version is two threads that tryLock the second lock, fail, release the first and retry in lockstep. CPU is busy and throughput is zero.

Starvation: the system as a whole makes progress, but one thread or one class of requests never gets its turn. A writer waits on a read-write lock while new readers keep arriving; a low priority thread never runs under strict priority scheduling; a barging lock keeps going to whoever is already running.

In production: deadlock shows threads BLOCKED or WAITING with identical stacks in two dumps taken seconds apart, and a cycle of owners. Livelock shows high CPU, no completed requests, and stacks that change between dumps but always sit inside the same retry loop. Starvation shows normal average throughput with one request type stuck in the far tail of latency or timing out.

Likely follow up: "How do you fix each?" Lock ordering for deadlock, randomized backoff or ordering for livelock, and fairness for starvation: a FIFO queue, a fair lock, aging, or writer preference.

4SeniordeadlockdebuggingRubrik
Your service has stopped making progress. How do you confirm it is a deadlock and find the cycle?
Model answer

First take two or three thread dumps a few seconds apart. Identical stacks in BLOCKED or WAITING mean stuck; changing stacks mean slow work or a livelock.

In Java, jstack <pid> or jcmd <pid> Thread.print. The JVM looks for cycles among monitors and ownable synchronizers such as ReentrantLock, and prints "Found one Java-level deadlock" with each thread, the lock it waits for and who holds it. In code, ThreadMXBean.findDeadlockedThreads() does the same check, which is handy in a watchdog or a test.

In C++, attach gdb -p <pid> and run thread apply all bt. Stuck threads show a futex wait (__lll_lock_wait on glibc) called from pthread_mutex_lock. With glibc, the mutex's __data.__owner field holds the thread id of the owner, so you can walk owner, then what that owner waits for, until the cycle closes.

If there is no owner cycle, it is not a lock deadlock. Look for threads parked in Condition.await, a condition variable wait, a latch or a future: that is a lost wakeup, a missing countDown, a future nobody completes, or a pool whose threads all wait on tasks queued behind them. The JVM's detector cannot see those, because they have no owner.

Likely follow up: "How do you stop it recurring?" Document a lock order and check it in debug builds, add tryLock timeouts that log the holder, and never call unknown code while holding a lock.

5Seniordeadlockexecutors
What is a thread-starvation deadlock in a thread pool? Give an example.
Model answer

In a thread-starvation deadlock, every thread in a bounded pool is blocked waiting for a result that can only come from a task still sitting in that pool's queue. The queued task never gets a thread, so nobody finishes. No lock is involved at all, which is why it surprises people.

With N threads it needs N outer tasks at once, so it passes every test and hangs under load. The same thing happens in a hand-built C++ pool when a task calls pool.submit(...).get(), and in a DAG job runner where a parent task blocks waiting for its children.

Fixes, best first: do not block inside a pool task on work in the same pool; compose asynchronously instead (thenCompose, or a continuation that runs when the child finishes); give dependent stages separate pools; in a ForkJoinPool, use fork and join, which run or steal queued subtasks instead of just parking. Making the pool larger than the deepest dependency chain works but is fragile.

Likely follow up: "Would an unbounded pool fix it?" It removes the deadlock but trades it for unbounded threads under load. Removing the blocking dependency is the real fix.

6Corelivelockbackoff
Show how a livelock happens with tryLock, and how you fix it.
Model answer

Two threads need locks A and B and take them in opposite orders. To avoid deadlock, each uses tryLock for its second lock and backs off on failure. If they run in step, they repeat the same dance forever.

Fixes: add random jitter to the backoff (exponential backoff with jitter) so the threads fall out of step, which is exactly how Ethernet resolves collisions. Better still, remove the conflict: take the locks in one global order, and the retry loop disappears. A practical hybrid is to retry with tryLock a bounded number of times, then fall back to a blocking acquisition in the global order.

Livelock is not only about locks. Two services that retry each other's failed requests at fixed intervals, or optimistic transactions that keep aborting each other, livelock the same way, and the same cure applies: jitter and fewer conflicts.

Likely follow up: "Is a CAS retry loop a livelock risk?" Not in the same way: a failed CAS means another thread's CAS succeeded, so the system as a whole progresses (lock-free), although one unlucky thread can starve.

7SeniorstarvationfairnessRubrik
How can a thread starve even though nothing is deadlocked, and what are your options to prevent it?
Model answer

starvation has a few usual causes. A barging lock hands itself to a thread that is already running, so a parked waiter keeps losing. A reader-preferring read-write lock never lets a writer in while readers overlap. Strict priority scheduling never runs the low priority thread. And a monitor whose admission rule favours the group already inside: in a "one team at a time, at most 10 players" playground, the current team keeps admitting teammates and other teams wait forever.

The options, from strongest to cheapest:

  • FIFO order: a ticket counter or an explicit queue of waiters, or a fair lock (new ReentrantLock(true), a ticket lock in C++). Nobody waits behind more than the threads that arrived before them.
  • Bounded turns: after K admissions of one group, stop admitting that group while another group is waiting. This keeps most of the batching throughput and bounds waiting.
  • Aging: waiting time raises a waiter's priority until it wins.
  • Writer preference on read-write locks: a waiting writer blocks new readers.

Fairness costs throughput, because strict handoff forces a context switch on every release. Pick the weakest guarantee that meets the requirement: usually bounded waiting rather than strict FIFO.

Likely follow up: "Write the admission rule." For the playground: admit when inside < 10 and (inside == 0 or same team), and not when another team waits and this team has already had K admissions in its turn.

8Seniorread-write-lockstarvationRubrik
Can writers starve on a read-write lock? What do ReentrantReadWriteLock and std::shared_mutex actually do?
Model answer

Yes. With reader preference, if read sections keep overlapping, the reader count never reaches zero and the writer waits forever.

Java: the ReentrantReadWriteLock Javadoc promises nothing about order in the default non-fair mode and warns that continuous contention can postpone readers or writers indefinitely. The implementation adds a heuristic: a new reader blocks if the thread at the head of the wait queue is a writer, which makes writer starvation unlikely in practice. Fair mode (new ReentrantReadWriteLock(true)) grants roughly in arrival order.

C++: the standard leaves the policy of std::shared_mutex unspecified, so it differs by platform. On Linux, libstdc++ wraps the glibc pthread_rwlock_t, whose default kind prefers readers, so a steady read load can starve writers. libc++ (Clang on macOS) uses its own two-gate design in which a waiting writer stops new readers, which is writer preference. Never rely on either in portable code.

If you build your own (a common Rubrik ask), make the policy explicit:

  • readers wait while writerActive || waitingWriters > 0;
  • writers wait while writerActive || activeReaders > 0.

That is writer preference. It fixes writer starvation and can now starve readers under a steady write load.

Likely follow up: "Now readers starve. Fix that too." Use phases: when a writer releases, admit every reader that was already waiting before letting the next writer in. Each side waits at most one phase of the other.

9Seniorlock-convoyperformance
What is a lock convoy, and why can adding threads make throughput fall?
Model answer

A lock convoy forms around a hot lock. When the holder releases, a waiting thread is woken, but it needs the scheduler to put it on a CPU, which takes a context switch. Meanwhile the releasing thread comes straight back for the lock and has to queue. The threads move in a procession, and throughput drops to about one lock acquisition per context switch, far below what the critical section itself allows.

Fair, handoff-style locks make it worse, because the lock is reserved for a thread that is not running yet. Barging locks soften it: a running thread may take the lock ahead of the woken one. Adaptive locks that spin briefly before parking also help, because a short spin often catches the release without a context switch.

Symptoms: a high context switch rate (vmstat or pidstat -w), CPU that is neither idle nor saturated, and throughput that falls as you add threads. Adding threads hurts because the serial part does not shrink while the handoff overhead grows with the number of waiters.

Fixes: shorten the critical section and move work outside it, split the lock (striping, per-key locks), accumulate per thread and merge (LongAdder), batch several operations per acquisition, or replace the lock with a single owner thread fed by a queue.

Likely follow up: "How would you measure lock contention?" Java Flight Recorder's monitor and park events or async-profiler's lock mode in Java; perf with off-CPU or futex tracing in C++.

10Seniorthundering-herdcaches
What is a thundering herd, both for threads and for caches, and how do you prevent it?
Model answer

For threads: notifyAll or notify_all wakes every waiter when only one of them can proceed. All of them fight for the lock, one wins, and the rest go back to sleep, which wastes a context switch each. Fix it with one condition per predicate (notFull, notEmpty) and signal or notify_one when every waiter is equivalent and one unit of work arrived. A semaphore does this naturally.

For caches, the herd is a cache stampede: a hot key expires and thousands of requests miss at once and all hit the database. Fixes:

  • Single-flight: the first miss loads the value and the others wait on its future.
  • Stale-while-revalidate: serve the old value while one thread refreshes it.
  • Jittered TTLs, so keys written together do not expire together.
  • Early refresh before expiry, or a short lease on the key in a shared cache so one instance refreshes.

The same shape appears after an outage, when every client retries at the same moment; exponential backoff with jitter spreads them out.

Likely follow up: "Implement single-flight." In Java, ConcurrentHashMap<K, CompletableFuture<V>>: putIfAbsent a new future, and only the thread whose insert won runs the load, outside the map; remove the entry when the load fails. In C++, a map from key to std::shared_future<V> under a mutex, where only the inserting thread runs the load.

11Seniordeadlock
Can you deadlock with only one lock, or with no locks at all?
Model answer

Yes to both, because deadlock is a cycle in any wait-for graph, not only a cycle of locks.

With one lock:

  • Self deadlock: a thread locks a non-recursive std::mutex it already holds (undefined behavior, in practice a hang). Java's intrinsic locks and ReentrantLock are reentrant, but a Semaphore(1) used as a lock hangs the same way.
  • A thread holds lock L and joins another thread that needs L.

With no locks:

  • Two threads join each other.
  • Bounded queues in a cycle: stage A blocks putting into a full queue that B reads, while B blocks putting into a full queue that A reads.
  • A pool whose threads wait on tasks queued behind them.
  • Java class initialization: thread 1 initializes class A, whose static initializer touches B, while thread 2 initializes B, which touches A. Each waits for the other's initialization to finish.
  • A parent process blocks writing to a child's full stdin pipe, while the child blocks writing to its full stdout pipe, which the parent plans to read only after it finishes writing.

Likely follow up: "How do you avoid the queue cycle?" Avoid cyclic pipelines. If one is unavoidable, make one edge non-blocking (drop, spill or reject), or cap total work in flight with one shared credit pool so the queues can never all fill.

12Coredeadlockcode-reviewRubrik
In a code review or a debugging round, what patterns make you suspect a deadlock?
Model answer
  • Nested locks taken in different orders in different methods: A then B in one, B then A in another.
  • Calling unknown code while holding a lock: listeners, callbacks, overridable methods, equals and hashCode of user keys, logging frameworks with their own locks. Prefer open calls: copy what you need, release, then call.
  • Blocking while holding a lock: I/O, future.get(), join, put on a bounded queue, sleep.
  • Waiting on one monitor while holding another. wait releases only the inner monitor, so a thread that must take the outer one to signal never can (a nested monitor lockout).
  • lock() outside try with unlock() not in finally (Java), or manual unlock() in C++. One exception leaves the lock held forever, which looks exactly like a deadlock.
  • Synchronizing on objects other code can reach: string literals, boxed integers, this of a public class, a collection you returned to callers.
  • A pool task that waits for another task of the same pool.

In a timed debugging round, write down every lock and the order each code path takes them, pick one global order, and reorder the minimum number of acquisitions. If contention does not matter, merging two locks into one is a legitimate and very safe fix.

Likely follow up: "After your fix, how do you show it works?" Run it with many threads and iterations under a timeout, take a thread dump if it stalls, and in C++ run ThreadSanitizer, which on Linux also reports lock order inversions (Apple clang's build does not).

13Seniordeadlockdining-philosophersApple
Solve the dining philosophers. Which solutions are deadlock free, and which are also starvation free?
Model answer

Five philosophers sit at a round table with one fork between each pair, and each needs both neighbouring forks to eat. If everyone picks up the left fork first, all five hold one fork and wait for the right one: circular wait.

  • Resource ordering: number the forks and always pick up the lower numbered one first, so one philosopher reaches right first and the cycle cannot form. Deadlock free and the easiest to prove. Starvation free only if the fork locks are fair.
  • Limit the table: a semaphore with 4 permits (N minus 1). With at most four seated, at least one can get both forks. Deadlock free.
  • Take both forks at once: one monitor with a state per philosopher; a philosopher eats only when neither neighbour is eating. Deadlock free, but a philosopher whose two neighbours take turns can starve, so add a FIFO or aging rule.
  • tryLock both forks with random backoff: deadlock free, with a probabilistic livelock risk.
  • Chandy and Misra's clean and dirty forks, built for distributed philosophers: deadlock and starvation free.

In C++, std::scoped_lock lk(left, right) is deadlock free without any ordering, but it promises nothing about starvation.

Likely follow up: "Which one would you code in 20 minutes?" Ordering: few lines, an obvious proof, and you can explain the semaphore variant out loud as the alternative.

14Stretchdeadlockdatabases
Prevention, avoidance or detection: which approach do real systems use for deadlock?
Model answer

Prevention designs one Coffman condition away. Most application and kernel code does this with lock ordering. The Linux kernel's lockdep validator learns the order in which lock classes are taken at run time and warns on the first inversion, even when the deadlock never actually happened.

Avoidance checks every request at run time and grants it only if the system stays in a safe state, as in the banker's algorithm. It needs each process's maximum claim in advance, so it is rare outside textbooks and some resource managers.

Detection and recovery lets deadlocks happen, finds cycles in a wait-for graph and breaks them by aborting a victim. Databases do this. InnoDB detects deadlocks as they form and rolls back one transaction; PostgreSQL waits deadlock_timeout (1 second by default) and then runs its check. The application sees a deadlock error and retries the transaction.

Timeouts are the crude form of detection: lock wait timeouts, tryLock with a deadline, RPC deadlines. They turn a silent hang into a visible error.

Likely follow up: "Why can a database abort a victim but your program cannot?" A transaction can be rolled back cleanly. A thread's partial side effects cannot, and Java removed the tool anyway: Thread.stop is deprecated and since JDK 20 throws UnsupportedOperationException. So application code prevents with ordering and keeps timeouts as a safety net.

15Seniorlost-wakeupcondition-variable
What is the difference between a lost wakeup and a deadlock, and how do you rule out lost wakeups in your code?
Model answer

In a deadlock, threads wait for each other in a cycle. In a lost wakeup, a thread waits for a condition that is already true, because the notification happened before it started waiting and nobody will notify again. The state says "go"; the thread sleeps anyway.

The usual causes:

  • Waiting without checking the condition first, or with if instead of while.
  • Changing the shared state without holding the mutex the waiter uses. In C++, where notify_one needs no lock, the change and the notify can both land between the waiter's check and its sleep, even if the variable is atomic. (Java requires the lock to notify or signal.)
  • notify on a monitor shared by waiters with different conditions: the single signal goes to the wrong kind of waiter and is swallowed.
  • A CountDownLatch or future that some code path forgets to count down or complete, typically an exception path.

The rules that rule it out: change the state while holding the lock, always wait in a loop on the predicate (while (!ready) cond.await(); or cv.wait(lock, pred)), use separate conditions per predicate or notifyAll, and complete futures and latches in finally.

In a thread dump, a lost wakeup shows threads parked in await with no owner cycle, while a debugger shows the predicate is already true.

Likely follow up: "Why is cv.wait(lock, pred) enough in C++?" It rechecks the predicate under the mutex before every sleep and after every wakeup, which handles both lost and spurious wakeups.
