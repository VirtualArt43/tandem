Barriers and phasers

Coordinate repeated phases with barriers, handle failures explicitly, and manage changing membership with Java Phaser and C++20 arrive_and_drop.

Asked atRubrik
Before this:Latches: wait until N things happen

Some parallel algorithms move in lockstep: every thread must finish step k before any thread starts step k+1. A barrier is the meeting point between steps. Rubrik has asked for a graph search done level by level with threads synchronized by a barrier, and has questioned candidates on choosing CyclicBarrier over Semaphore.

In plain words

A trekking group walks at different speeds, but the guide has one rule: at every checkpoint, wait until the whole group has arrived. When the last person turns up, the guide counts heads, announces the next stage, and everyone sets off together. The same rule applies at every checkpoint, all the way up the mountain.

And if one trekker turns back injured, the guide must tell everyone waiting at the checkpoint, or they would wait forever. Everyone waits for everyone, the routine repeats every stage, and a failure must release the rest: that is the coordination a barrier provides, together with an explicit failure policy.

What a barrier is

A barrier starts with an expected number of arrivals per phase, N. In the basic pattern, each of N parties arrives once. Each party calls await (Java) or arrive_and_wait (C++) when it finishes its part of the current phase. The first N minus 1 callers block; the Nth releases them all, and the barrier resets itself for the next phase. Two things make it more than a latch:

  • It is reusable. The same barrier object serves phase 1, phase 2, phase 3 and so on.
  • It can run an action once per phase: after the last party arrives and before any party is released. That is the natural place to merge the phase's results and prepare the next phase, because the workers have finished accessing this phase's shared data. With split arrival and waiting, they may still be doing unrelated work.

And it carries memory effects: work before arrival happens-before the action, and the action happens-before work following a successful wait for that phase. Workers can write separate plain-data slots, then read the completed results. This does not protect concurrent writes within a phase, or stop a fast worker overwriting a slot while a slow worker still reads it; use another barrier before reuse or separate buffers.

Java

java.util.concurrent.CyclicBarrier. new CyclicBarrier(parties) or new CyclicBarrier(parties, barrierAction). await() blocks until all parties arrive and returns the arrival index: getParties() - 1 for the first to arrive, down to 0 for the last. The barrier action runs in the last thread to arrive, before the others are released. There is also await(timeout, unit), getNumberWaiting(), isBroken() and reset().

Breakage. Interruption detected inside await, a waiting timeout, or an exception from the barrier action breaks the current generation. Other waiters get BrokenBarrierException; the interrupted caller gets InterruptedException, the caller whose wait expires gets TimeoutException, and the action's caller receives its original exception. Later calls fail until reset(). Reset releases current waiters exceptionally but immediately creates a fresh, unbroken generation, so it is not a persistent cancellation signal.

A worker throwing or exiting before calling await does not automatically break the barrier. Even an interrupt flag only matters once the thread reaches an interruptible operation. Detect such failures with a coordinated cancellation protocol or timed waits.

C++

C++20 std::barrier<CompletionFunction>, in <barrier>. std::barrier sync(n, completion); where the completion function must be nothrow-invocable with no arguments, normally a noexcept lambda. A potentially throwing callable does not meet the type requirement; throwing out of a noexcept body terminates the process. Calls:

  • arrive_and_wait(): arrive and block until the phase completes.
  • arrive() returns an arrival_token; wait(std::move(token)) blocks later. Splitting the two lets a thread do unrelated work while the others catch up. Include <utility> for std::move. The token must belong to this barrier's current or immediately preceding phase.
  • arrive_and_drop(): arrive for this phase and also lower the expected count for every later phase. This is how a party leaves for good, instead of its normal arrival. It does not wait, and a party that already arrived must not also drop for that phase.

The completion step runs on a participating thread before phase waiters return. With the defect-corrected C++20 contract, whether completion runs when nobody calls wait is implementation-defined; do not rely on a final all-drop phase to run a callback. There is no broken state, no timeout and no interruption: if a party never arrives, everyone else waits forever. Before C++20, build a reusable barrier yourself (the next lesson but one does), or use Boost; macOS does not supply POSIX pthread_barrier_t.

Phased algorithms: BFS level by level

Breadth-first search explores a graph in rings: first the start node, then everything 1 step away, then everything 2 steps away. Each ring (level) depends on the whole previous ring, so a parallel BFS is naturally phased:

  1. All workers share the current level, the frontier. Each takes every k-th node and looks at its neighbours.
  2. A neighbour not yet visited is claimed with a compare-and-swap on its distance, so exactly one worker adds it to the next level.
  3. Each worker adds its claimed nodes to the shared next level under a short lock, then waits at the barrier.
  4. The barrier's action, running once while every worker is stopped, makes the next level the new frontier and checks whether the search is done.

The program runs this on a 60 by 60 grid from one corner. On a grid the true distance of a cell is its row plus its column, which makes the result easy to check.

Why each piece is there:

  • The barrier is what makes it a BFS. Without it, a fast worker could start expanding level 6 while a slow one is still on level 5, and nodes would be claimed with the wrong distance.
  • The CAS on dist resolves the race when two frontier nodes share a neighbour: both workers try, one wins, and the node is added to the next level once.
  • The lock around next is needed because several workers append to one list in the same phase. Each worker collects into its own mine first, so the lock is taken once per level, not once per node.
  • The action swaps in the next level while every worker is parked, so nobody reads frontier while it changes, and sets done before anyone is released to read it.
C++

Why the completion function takes the lock

By the standard, every arrival happens before the completion step, so the lock inside start_next_level is not needed for correctness. It is there for ThreadSanitizer. In libc++, the arrival half of std::barrier lives in the compiled library, which is not built with the sanitizer, so the tool cannot see that ordering and reports a race on next and frontier that cannot happen. Taking the same mutex makes the ordering visible to it, with one additional mutex acquisition per phase; its performance cost depends on the workload. The general lesson is worth keeping: sanitizers can report false positives when synchronization happens inside code they cannot see, so when a report contradicts a documented guarantee, check where the synchronization is implemented before you "fix" it.

The grid includes distances 0 through 118, so processing every frontier takes 119 phases. This demonstration assumes all workers start and phase work succeeds; it does not implement recovery from allocation failure or partial thread startup. A production coordinator must handle those failures with the protocol below.

When a party fails

A barrier makes every party depend on every other. That is its power and its danger: one thread that dies, hangs or leaves its loop without arriving holds up the whole group.

So every barrier-based design needs an answer to "what if a party fails?":

  • Java: treat BrokenBarrierException as "the computation is over", stop cleanly, and report the original failure. Use a timed await if a hung party is possible. Do not catch the exception and loop back to await: the barrier stays broken until reset(), and resetting while others are mid-phase mixes rounds.
  • C++: catch worker exceptions inside the thread function, record failure, and call arrive_and_drop() instead of that phase's arrival. An uncaught exception escaping the thread function calls std::terminate. A phase-aware RAII guard can handle a missing arrival, but must not drop twice or drop after the party already arrived. Publish failure before dropping; stop the group at a phase boundary.

Parties that come and go: Phaser and arrive_and_drop

A CyclicBarrier has a fixed party count. Real workloads are messier: workers finish at different times, or new tasks join mid-way. Java's phaser handles both; C++ covers the "leave" half with arrive_and_drop().

The C++ coordinator waits once per phase so even the final phase has a waiter and its completion callback is required to run. Java's last output line additionally reports terminated: true.

Java

The Phaser API. Parties register() (or bulkRegister(n)) and leave with arriveAndDeregister(). arriveAndAwaitAdvance() arrives and waits, but is not interruptible; arrive() arrives without waiting; awaitAdvance(phase) waits for a given phase to end without being a party. Phases are numbered from 0 and wrap to 0 after Integer.MAX_VALUE. Override onAdvance(phase, registeredParties) to run code at each phase boundary; returning true terminates the phaser, after which waits return immediately with a negative phase. The default returns true when no parties remain registered. A single phaser supports up to 65,535 parties; beyond that, phasers can be arranged in a tree (tiering), which also reduces contention.

Cancellation differs from CyclicBarrier. awaitAdvance also keeps waiting through interruption. For interruptible or timed waiting, record int phase = phaser.arrive() and call awaitAdvanceInterruptibly(phase) or awaitAdvanceInterruptibly(phase, timeout, unit). Those exceptions do not break the phaser or undo the arrival. A whole-job cancellation can record the error and call forceTermination(), which releases waiters; they must check termination and stop. Do not blindly deregister after an arrival, since that could count twice in the same phase. Keep onAdvance nonthrowing: an exception there prevents phase advancement.

Registration is counted, not tied to a thread identity. Register a task before making it runnable, arrive exactly once per phase, and balance registration with deregistration. For Rubrik's recurring "schedule tasks, then wait until every scheduled task is done", this fragment supports batches with one coordinator: finish all calls to schedule before waitUntilComplete, and submit the next batch only after that wait returns.

If submissions race with the wait, a registration can join either side of a phase boundary, so this is not a snapshot of "all tasks submitted before the call". Supporting concurrent submission needs an explicit batch or admission boundary. Task errors need a separate result or failure channel.

If interviewers ban java.util.concurrent, you build the same thing from a counter and a condition variable, as in the latches lesson.

Barrier, latch or semaphore?

Rubrik interviewers have asked candidates to justify choosing CyclicBarrier versus Semaphore. The question is really "what are you waiting for?":

You needUse
A fixed group of threads to all reach a point, repeatedly, before any continuesBarrier
One or more threads to wait until N events have happened, onceLatch
At most N threads inside some section at a timeSemaphore
A group whose membership changesPhaser in Java; arrive_and_drop only removes parties in C++, so adding parties needs a different protocol

Worked example: H2O with a barrier and semaphores

LeetCode 1117, Building H2O: hydrogen and oxygen threads arrive in any order, and they must leave in groups of exactly two hydrogens and one oxygen. It is a good test of the table above, because this solution combines two different kinds of waiting:

  • "At most two hydrogens and one oxygen may be forming the current molecule" is a limit on how many are inside: semaphores with 2 and 1 permits.
  • "The three must leave together" is mutual waiting of a fixed group: a barrier of 3.

A hydrogen thread takes a hydrogen permit, waits at the barrier, does its "release" callback, and gives the permit back; oxygen is the mirror image with the oxygen permit. This puzzle assumes enough atoms, no cancellation, and callbacks that return normally. Production cancellation needs whole-group abort and error reporting; merely dropping an atom would violate the molecule ratio.

Why groups cannot mix: a thread from the next molecule can only get a permit after a thread from this molecule has returned one, and threads return permits only after their own release callback. So the next molecule cannot pass the barrier until all three of this molecule have been released. Writing the oxygen side and testing it is the practice problem.

Common mistakes

  • A party count that does not match the threads. With N+1 threads, one extra thread spills into the next phase and mixes rounds; with N minus 1, the barrier never trips.
  • Barrier tasks in a pool that is too small. Four tasks that each wait at a 4-party barrier, submitted to a pool of 3 threads, deadlock: three block in await and the fourth never gets a thread.
  • Slow or throwing barrier actions. No phase waiter returns until the action finishes, so keep it short. In Java a throwing action breaks the barrier; in C++ a throwing completion terminates the program, which is why it must be noexcept.
  • Ignoring BrokenBarrierException. Calling await again throws immediately until a coordinated reset; a retry loop can spin instead of making progress.
  • Leaving the loop without arriving (C++). An early return or a caught exception followed by return without arrive_and_drop() strands the others. An uncaught exception terminates the process.
  • Using a barrier for a one-shot fan-in, or a latch for repeated phases. Pick the tool that matches "what am I waiting for?".

In the interview

Rubrik has asked a hard graph problem solved with threads doing BFS level by level, synchronized with a barrier, and in a 2025 booking-system round judged the candidate's choice of constructs such as CyclicBarrier and Semaphore, along with exception handling. Expect "why a barrier and not a latch?", "what happens if one worker throws?" and "how many threads, and from what pool?".

The levels of a BFS depend on each other, so I would run the workers in phases with a barrier: each worker expands its share of the current frontier, claims unvisited neighbours with a compare-and-swap on their distance so each node is added once, merges its claims into the next frontier under a short lock, and waits at the barrier. The barrier action swaps in the next frontier while everyone is parked and sets a done flag when it is empty. A barrier, not a latch, because it is reused every level. If a worker fails outside Java's await, I explicitly cancel its peers; the barrier does not detect arbitrary task failures. In C++ I catch the error, publish a shared failure flag, and replace the missing arrival with arrive_and_drop.

Follow ups to expect: "What is the cost of a barrier per level?" (every level waits for the slowest worker, so uneven frontiers waste time; it pays off when levels are wide), "Could you avoid the barrier?" (an asynchronous shortest-path algorithm can repeatedly relax distances, but first-claim-wins is then insufficient; shorter discoveries must be propagated and termination detected), and "How would you build a reusable barrier yourself?" (a generation counter; the next lesson but one).

Senior depth

Bulk-synchronous parallel. "Compute locally, exchange, barrier, repeat" is the BSP pattern. Across machines, the same phase structure needs failure detection and coordinated recovery: a local barrier alone cannot detect a remote crash.

Split-phase waiting. C++'s arrive() followed later by wait(std::move(token)), and Java's arrive() with awaitAdvance(phase), let a thread announce "my part of this phase is done" and keep doing work that does not depend on the others before it blocks. That hides some waiting, but shared phase data must remain untouched until the matching wait completes. If unrelated work fails after arrival, record failure and finish that phase with the existing token; coordinate stopping or dropping in a later phase instead of counting a second arrival. Once all parties have dropped, the expected count is zero; destroy the C++ barrier after its users finish instead of trying to reuse it.

Barrier cost at scale. A simple barrier is one shared counter, a hot spot when hundreds of threads arrive together. Tree-shaped barriers (and tiered phasers) combine arrivals in small groups first, and libc++ implements std::barrier with a tree internally for the same reason.

Key takeaways

  • A barrier makes a fixed group of threads wait for each other at the end of every phase, and it is reusable.
  • The barrier action (Java) or completion function (C++) runs before phase waiters return: the place to merge results when parties have stopped accessing phase data.
  • Java's CyclicBarrier breaks on failed barrier waits or action failure, not arbitrary worker failure. C++ needs explicit cancellation and balanced arrivals or drops.
  • Phaser handles parties that join and leave; in C++, arrive_and_drop handles leaving.
  • Barrier for repeated mutual waiting, latch for one-shot events, semaphore for "at most N inside".

Quick check

Answer each question, then read why. Your score is saved for your module test.

A barrier is created for 3 parties. Six threads each call await() (or arrive_and_wait()) exactly once. What happens?
Why. A barrier is cyclic: when the third party arrives, the phase completes and the barrier resets. The next three arrivals make up the following phase. Mixing groups like this is usually a bug in real code, but it does not hang or throw.
Four tasks, each of which waits at a 4-party barrier, are submitted to a fixed thread pool with 3 threads. What happens?
Why. All blocking parties must be able to reach the barrier; they need enough execution slots, not simultaneous CPU execution. Blocking pool threads on something that requires a task still waiting in the queue is the classic pool self-deadlock. Size the pool to at least the number of parties, or do not run barrier parties as pool tasks.
Java onlyFour threads use a CyclicBarrier(4). Three are waiting in await() when the fourth calls await() with its interrupt flag already set. There is no concurrent reset. What happens to the three?
Why. The fourth caller detects interruption inside await, throws InterruptedException and breaks this generation. The other three get BrokenBarrierException, not an interrupt flag. It neither trips successfully with three arrivals nor waits for a replacement. If the fourth never called await, its interrupt flag alone would not release them; reset instead starts a fresh generation.
C++ onlyFour threads share a std::barrier sync(4). One thread catches an exception from its work and returns normally from its thread function without arriving or dropping. What happens to the other three?
Why. C++ barriers count arrivals only; they neither adjust membership nor manufacture a completion on thread exit. An uncaught exception escaping the thread function would terminate the process instead. A party that leaves must say so with arrive_and_drop(), ideally from an RAII guard on the error path, and the group usually also needs a shared "failed" flag so the remaining parties stop at the next phase.
All parties call await() or arrive_and_wait() once per phase, with no failures. When does the barrier action (Java) or completion function (C++) run?
Why. It runs once per phase on a participating thread (the last arrival in Java), before waits return. It is neither per-party nor a background callback, and reuse runs it again. That is why it can safely merge per-phase results and set up the next phase.
Which situation calls for a barrier rather than a latch?
Why. Only the simulation needs the same group to wait for each other repeatedly, which is exactly what a reusable barrier does. The other three are one-shot waits for events, which is a latch (or futures).
A plain integer x starts at 0 before the threads start. A writes x = 1 and waits at a barrier. B successfully waits for that same phase and then reads x. There are no other writes to x. What can B see?
Why. Barriers carry memory effects: everything a party did before arriving happens-before what every party does after being released from that phase. This is what lets BFS workers read the frontier the barrier action built without extra locks.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Three threads each print "thread i: step k" for k = 1, 2, 3. No thread may print step k+1 until all three have printed step k. Use a barrier.
Model answer

Within one step the three lines can appear in any order, but all three step 1 lines come before any step 2 line, because no thread can pass the barrier until all have arrived. One barrier object serves all three steps. The C++ mutex only keeps lines from interleaving character by character; the barrier provides the ordering.

Explain
For each scenario, choose CyclicBarrier, CountDownLatch or Semaphore (or the C++ equivalents) and say why: (a) at most 5 threads may call a licensing server at once; (b) the main thread waits until 3 caches have loaded before opening the HTTP port; (c) 6 threads run 100 rounds of a simulation and must stay in step.
Model answer
  • (a) Semaphore with 5 permits. It is a limit on how many are inside at once, not a wait for an event. I would use a timed acquire so callers fail fast if the server is slow.
  • (b) Latch with a count of 3. It is a one-shot wait for three events by a thread that is not one of the loaders; the loader threads may keep running afterwards. In Java I would also use a timed await so a hung loader shows up as a startup failure.
  • (c) Barrier with 6 parties. The same group waits for each other again and again, and the barrier action can do per-round work such as swapping buffers while everyone is stopped.

The rule behind the choices: a semaphore counts how many are inside, a latch counts events once, and a barrier makes a fixed group wait for each other repeatedly.

Design
You run a simulation on 8 threads with a barrier per time step. Any thread can hit an error. Describe how you make sure the other threads stop cleanly instead of hanging, in your language.
Model answer

In Java I create and publish the worker list before starting any worker. I record the first error in an AtomicReference<Throwable> and interrupt every peer when work or the barrier action fails. Workers stop on InterruptedException or BrokenBarrierException, restoring interrupt status when caught. A peer already waiting breaks the barrier; a peer still computing eventually calls await with its flag set or observes cancellation and exits. Work must cooperate with interruption, and the coordinator joins every started worker before reporting the recorded error. A timed await can detect a missing arrival, but cannot forcibly stop hung work or a stuck barrier action. I do not use reset as cancellation: a late peer could enter the new generation and wait forever.

In C++ I catch failures inside each worker, publish an atomic failure flag, and replace that worker's missing arrival with arrive_and_drop(). The completion function observes failure and publishes a common stop decision before releasing the phase. Survivors see that decision after their waits and all leave together; no later phase will be used, so they need not drop again. A guard must track whether this phase's arrival already happened. A genuinely hung worker cannot cooperate or drop, so bounded waiting needs a custom barrier with a broken state and a timed condition wait, plus a way to stop the work itself.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Walk me through why you would use a barrier for parallel BFS. What exactly does it protect?"
What a strong answer covers
  • A reusable barrier separates frontier levels so no worker expands the next level early
  • CAS claims each unvisited node once; separate slots or a mutex protect concurrent appends
  • The phase action installs the next frontier before waiters resume
  • Arrival and successful waiting publish phase data but do not serialize work within a phase
  • Workers wait for the slowest participant and need enough execution slots to reach the barrier
How a senior would say it
I would use a reusable barrier because each BFS level depends on finishing the previous frontier. Each worker expands its assigned nodes and claims an unvisited neighbour with compare and swap, so shared neighbours enter the next frontier only once. Workers collect results locally, then append under a short mutex. At the barrier, the phase action installs the next frontier and checks whether it is empty. The arrival and successful wait publish that data before workers read it, so the frontier itself does not need atomic elements. But the barrier does not make concurrent appends safe inside the phase; that is still the mutex's job. A latch would need replacing every round, and a semaphore alone only limits admission. The costs are waiting for the slowest worker and requiring enough execution slots for every participant to reach the barrier.

Likely follow up: What happens if three pool threads run four tasks that all wait at the same barrier?

Out loudabout 75 s
"One simulation worker throws before reaching the barrier, and the other workers hang. How would you fix the failure protocol?"
What a strong answer covers
  • An error outside a Java barrier wait does not break it; an uncaught C++ worker exception terminates the process
  • Record the original failure and cancel peers; Java wait interruption or timeout can break the generation
  • Reset is not cancellation because it immediately starts an unbroken generation
  • In C++, catch the error and publish failure before replacing the missing arrival with one drop
  • Use a common phase-boundary stop decision, join workers, and distinguish failure from unresponsive work
How a senior would say it
I would make failure an explicit part of the protocol. A Java barrier does not notice an exception thrown during ordinary work, so the surviving workers can wait forever. In C++, an exception escaping the thread function terminates the process; a caught exception followed by return can strand the peers. I would record the original error first. In Java I would interrupt the published worker set and have workers exit on interruption or a broken barrier. A timed wait can also detect a missing arrival. I would not use reset as cancellation, because a late arrival could enter its fresh generation and hang again. In C++ I would catch the error, publish failure, and call arrive and drop instead of that phase's normal arrival. The completion publishes one stop decision for the survivors. I would never arrive and then drop again for the same phase. Finally, I would join every worker before destroying shared state. A hung worker is a separate problem: a timeout detects missing progress, but stopping its work still requires cooperation.

Out loudabout 60 s
"Our worker set grows and shrinks between rounds. Would you choose a Phaser or a barrier, and how would you cancel a wait?"
What a strong answer covers
  • Java Phaser supports registration and deregistration; C++ std::barrier supports dropping but not adding parties
  • Register before task launch and arrive exactly once for each registered participation in a phase
  • Phaser arrival and ordinary waiting are not interruptible; use awaitAdvanceInterruptibly with the arrival phase
  • Timeout and interruption leave Phaser state intact, so cancellation needs an explicit policy
  • Whole-job cancellation can record failure, force termination, and make workers stop on termination
How a senior would say it
In Java I would choose a Phaser because it supports both registration and deregistration. In C++, the standard barrier can shrink through arrive and drop, but it cannot add participants, so growth needs another protocol. I would register each task before launching it and make its arrivals match its registration. For cancellation, Phaser differs from CyclicBarrier: ordinary arrival and waiting are not interruptible. I can arrive, save the phase number, then use awaitAdvanceInterruptibly with that phase and optionally a timeout. Interruption or timeout does not break the phaser, and the arrival still counts. I must not blindly deregister again in the same phase. If one failure should abort the whole computation, I would record the cause, force termination, and have workers stop when they observe termination. Dynamic membership helps coordination, but it does not define the application's cancellation or task-submission boundary.
