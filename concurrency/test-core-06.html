On a modern multi-core machine, what is the most common reason a plain stop flag loop never ends?
Why. Hardware caches are coherent: a write invalidates other cores' copies. The loop never ends because the optimizer hoisted the read into a register, which is legal when nothing synchronizes. The write itself reaches memory just fine.

Why. A context switch saves and restores the worker's registers, including the hoisted copy of the flag. Hoisting is a compiler decision, so the bug exists on one core exactly as on many. This is the core of the "volatile on a single core" interview question.

Why. A lock creates visibility only between a release and a later acquire of the same lock. The reader never acquires it, so its read is unsynchronized and can be hoisted. Make the getter take the same lock, or make the field volatile.

From: Visibility: why a thread may never see your write

From: Reordering by the compiler and the CPU
On x86 hardware, with no compiler reordering, which reordering can another core observe?
Why. x86 keeps stores in order and loads in order, but its store buffer lets a later load finish while an earlier store is still pending. That is exactly the store buffering test, so x86 is not sequentially consistent.
From: Reordering by the compiler and the CPU
Which change guarantees that the store buffering test never ends with both reads returning 0?
Why. Sequentially consistent accesses on both sides are never reordered with each other, so one thread's read must come after the other's write in a single global order. With only x volatile, each thread still has one plain access, and a volatile access holds a plain one back in one direction only: A's plain load of y can move ahead of its volatile store, and B's plain store to y can move after its volatile load. x86 allows exactly this outcome. Swapping the lines makes both reads of 0 the common case, not impossible.
From: Reordering by the compiler and the CPU
A thread runs a = 1; b = 2; and then, in the same thread, reads b and then a. Can it see b == 2 and a == 0?
Why. Reordering is allowed only where the thread itself cannot detect it (the as-if rule). The store buffer forwards a thread's own pending writes to its own loads. Other threads are the ones who may see a different order.
From: Reordering by the compiler and the CPU
A program runs on a machine with one CPU core. Can another thread observe two independent plain writes in the opposite order to the source code?
Why. Compiler reordering does not care about the number of cores. If the writes are emitted in swapped order and the scheduler switches threads between them, the other thread sees the second write without the first.

Why. The plain write of data comes before the volatile write in A, and the volatile read comes before the plain read in B. If B sees ready == true, the volatile write happens-before that read, so B also sees data == 42. If B reads ready before it is set, it prints nothing.
From: Reordering by the compiler and the CPU
C++ onlyIn the C++ store buffering demo, x and y are std::atomic<int> used with memory_order_relaxed, and both reads return 0. Which statement is true?
Why. Atomic accesses never form a data race, whatever their memory order, so ThreadSanitizer stays quiet and the behavior is defined. Relaxed only gives atomicity and a single order of writes per variable; it does not order the store to x with the load of y, so both reads returning 0 is permitted.
From: Reordering by the compiler and the CPU

From: Happens-before and synchronizes-with

Why. The edge must run through the flag, because the flag is what B checks first. With a plain ready, B's read of it has no edge from A's write, so B can see ready == true and still read the old data (and in C++ the race on ready is undefined behavior).

Why. Join, a blocking queue hand-off and a release-acquire flag all create happens-before edges from the worker's write to main's read. A sleep creates none, and locks only connect an unlock and a lock of the same lock.
From: Happens-before and synchronizes-with
A worker writes result = 7 and then keeps running for a long time. main waits for it with a timeout (t.join(100) in Java, future.wait_for(100ms) in C++), the wait returns because the time ran out, and main reads result. What is guaranteed?
Why. The edge goes from the worker's actions to a thread that detects it has finished: join() returning because the thread ended, isAlive() returning false, or a future becoming ready. A timeout detects nothing, so the read races with the write and may see 0 or 7 (in C++ it is undefined behavior).
From: Happens-before and synchronizes-with
Thread A writes x = 1 (a plain variable), then releases lock L. After that, thread B acquires L and writes a volatile (or seq_cst atomic) v = true. Thread C reads v, and if it is true, prints x. What can C print?
Why. Transitivity: A's write is before A's unlock; the unlock synchronizes with B's later lock of L; B's lock is before B's write of v; that write synchronizes with C's read that sees true. So x = 1 happens-before C's read of x, and C does not need lock L itself. If B had taken L before A, there would be no edge from A, and 0 would be possible.
From: Happens-before and synchronizes-with
Which of these is a data race?
Why. A data race needs conflicting accesses (at least one write) to a plain location that are not ordered by happens-before. Concurrent reads do not conflict, atomic accesses never form a data race (though the logic can still be a race condition), and the same lock orders the writes.
From: Happens-before and synchronizes-with
Java onlyWhich statement is guaranteed by the java.util.concurrent memory consistency rules?
Why. Actions before submission happen-before the task begins, and the task's actions happen-before get() returns in another thread. Writes made after submit() are unordered with the task. isDone() is not one of the documented edges (an implementation may happen to publish through it, but the contract does not promise it), so use get() (or join() on a CompletableFuture) before reading results.
From: Happens-before and synchronizes-with
C++ onlyIn C++, which pair creates a synchronizes-with edge from thread A to thread B?
Why. Synchronizes-with needs a release on the writing side and an acquire on the reading side, on the same atomic, with the load reading the stored value (seq_cst counts as both). A relaxed operation on either side breaks the pair, and C++ volatile is not synchronization at all.
From: Happens-before and synchronizes-with
Two threads each run count += 1 100,000 times on a counter declared volatile int (Java or C++). What is true?
Why. Volatile (in Java) makes each read and write visible but does not make the read-add-write sequence indivisible, so two threads can read the same value. In C++ volatile is not synchronization at all, so the unsynchronized accesses are a data race. It does compile in both: C++20 deprecates += on a volatile, but deprecated is not removed. Use incrementAndGet or fetch_add.
From: volatile in Java, std::atomic in C++
A shared counter is an AtomicInteger (Java) or std::atomic<int> (C++), and two threads each run a.set(a.get() + 1) (Java) or a.store(a.load() + 1) (C++) many times. What happens?
Why. Atomicity covers one operation at a time. Between the atomic read and the atomic write, another thread can do its own read, so one increment overwrites the other. There is no data race (all accesses are atomic), only a race condition. incrementAndGet() or fetch_add(1) is one operation.
From: volatile in Java, std::atomic in C++
A compare-and-set (compareAndSet or compare_exchange_weak) in an update loop returns false. What should the code do?
Why. A failed CAS means the value changed since you read it (or, for a weak CAS, that it failed spuriously), which is normal under contention. Recompute from the fresh value and retry. A plain write would throw away the other thread's update, and a sleep adds latency without guaranteeing anything.

Why. Loads and stores are right when each write does not depend on the old value: a flag, or a reference to an object that never changes after publication. The counter and the lazy initialization are read-then-write sequences, so two threads can interleave inside them; they need an atomic read-modify-write, a CAS, or a lock.
From: volatile in Java, std::atomic in C++
A running maximum is updated with if (x > max.get()) max.set(x); where max is atomic. What can go wrong?
Why. It is a check-then-act on shared state. Thread A checks 50 > 40 and pauses; thread B stores 90; thread A stores 50, and 90 is lost. A compare-and-set loop (or accumulateAndGet(x, Math::max)) only stores if the value is still the one you compared against.

minLatency and maxLatency are two separate atomic variables, each updated correctly with CAS loops. A reporting thread computes maxLatency - minLatency. What can it see?
Why. Each atomic is consistent on its own, but the reader's two loads are separate, and updates can land between them. An invariant that spans two variables needs a lock, or one immutable pair published through a single atomic reference.

Why. volatile applies to the field, which holds a reference. slots[3] = 7 reads the volatile reference and then does a plain element write. For per-element volatile semantics use AtomicIntegerArray (or a VarHandle for arrays).

C++ onlyWhat is C++ volatile actually for?
Why. Volatile accesses must be performed as written, which is what device registers need. It gives no atomicity, no fences and no happens-before between threads, so a race on a volatile variable is still undefined behavior. Use std::atomic for threads.
From: volatile in Java, std::atomic in C++

From: C++ memory orders: seq_cst, acquire, release and relaxed
In the store buffering test, A runs x.store(1, release); r1 = y.load(acquire); and B runs y.store(1, release); r2 = x.load(acquire); (Java: setRelease and getAcquire). Can r1 == 0 and r2 == 0?
Why. Release only holds back earlier operations and acquire only holds back later ones, so neither stops a load from passing an earlier store. On x86 both compile to plain moves and the store buffer produces exactly this outcome. seq_cst on all four operations, or a seq_cst fence between each store and load, forbids it.
From: C++ memory orders: seq_cst, acquire, release and relaxed
What does a relaxed atomic operation still guarantee? Select all that apply.Select all that apply
Why. Relaxed keeps atomicity, race freedom and per-variable coherence (a single modification order). It gives no ordering of other memory, and on its own it never synchronizes with anything, so it cannot publish data. (A release fence placed before a relaxed store can carry an edge, but then the fence does the synchronizing, not the relaxed operation.)
From: C++ memory orders: seq_cst, acquire, release and relaxed
Eight threads increment a statistics counter in a hot loop, and the main thread reads the total only after joining all of them. Which order is enough for the increments (C++), or which tool fits best (Java)?
Why. Exactness comes from the atomic read-modify-write, not from ordering; the join gives main a happens-before edge to every increment. A plain non-atomic variable would lose increments while the threads run. Java has no relaxed add, so LongAdder (which also removes contention) is the idiomatic choice.
From: C++ memory orders: seq_cst, acquire, release and relaxed
Why is memory_order_consume discouraged?
Why. Consume orders only reads that depend on the loaded value, which ARM and POWER give for free. But optimizers routinely break or replace dependencies, so no mainstream compiler implements consume as specified; they promote it to acquire, and C++17 discouraged its use.
From: C++ memory orders: seq_cst, acquire, release and relaxed
Java onlyWhich Java operation corresponds to a C++ release store?
Why. setRelease (and lazySet, which is documented with the same memory effects) keeps earlier accesses before the store without the full fence a volatile write needs. A volatile write is stronger: it behaves like a seq_cst store. A plain write has no ordering at all.
From: C++ memory orders: seq_cst, acquire, release and relaxed

A constructor starts a background thread that calls one of the object's methods, and only after that assigns the remaining fields. What is the risk?
Why. Starting a thread is a happens-before edge only for writes made before the start. Fields assigned afterwards race with the thread. In Java the final field guarantee also requires that this does not escape the constructor, so it does not protect them either. Construct fully, then start.
From: Safe publication, immutability and final fields
A Java class has only final fields, or a C++ class only const members, but one of them refers to a list (a Java List, or in C++ a std::shared_ptr<std::vector<int>> that is itself const) that callers can still modify through a getter. Is the object immutable?

Why. JLS 12.4.2 makes class initialization a synchronized, once-only step that happens on first active use, and C++11 requires the same for function-local statics. Both are lazy because the work happens on first use, not at program start.

Why. A class whose initialization failed is in an erroneous state for the life of the class loader; the JVM never retries it. If initialization can fail transiently, use double-checked locking on a volatile field, which simply tries again on the next call.

From: Double-checked locking and lazy initialization

Why. A core may only write a line it holds as the single valid copy. It sends invalidations, waits for them to be acknowledged, and moves the line to Modified. That transfer of ownership is the cost false sharing pays on every write.

How large is a cache line on the machines you are most likely to meet?
Why. Caches transfer fixed-size lines, typically 64 bytes on x86. Apple's M series reports 128 bytes, which is why 128 byte alignment is the safe portable choice. 32 byte lines belong to much older processors, and 4 KB is a typical page size, a different concept.

Why. An L1 hit takes a few cycles, about a nanosecond; a DRAM access takes on the order of 100 ns. That gap is why cache-friendly layouts and avoiding cross-core line transfers matter so much.
