Bounded blocking queue

Thread-safe structuresmedium30 minLeetCode 1188RubrikLinkedIn

A bounded queue tests whether you can make threads wait for a condition without losing a wakeup. It is a common building block for worker pools and producer-consumer pipelines, reported in Rubrik and LinkedIn interviews.

The task

Build a thread-safe queue with a fixed capacity:

  • enqueue(element) adds an element at the back. If the queue is full, the calling thread blocks until there is space.
  • dequeue() removes and returns the element at the front. If the queue is empty, the calling thread blocks until there is an element.
  • size() returns an exact snapshot of the element count at some instant during that call.

Many producer threads and many consumer threads use the queue at the same time. Each operation must behave as one atomic action. Elements come out in insertion order. Enqueues that overlap may be ordered either way; sequential enqueues by one producer must keep their order. Waiting threads need not be served in arrival order.

The supplied capacity is always positive, including 1. Accept every int value, including zero, negative values and both integer limits. Duplicates are separate elements. Each queue instance has its own contents and capacity; invalid constructor arguments are outside this task.

Java

If a thread is interrupted while waiting for space or an element, propagate InterruptedException without adding or removing an element. Release any held lock, leave the queue usable, and let other waiting threads continue when their condition becomes true.

Rules, as in the real interview: no library blocking queues. In Java use a lock with conditions, or synchronized with wait and notifyAll. In C++ use std::mutex and std::condition_variable. Rubrik interviewers in particular often ban java.util.concurrent queues and executors for this problem, so practise without them.

For example, a capacity 2 queue can hold two copies of -1. An enqueue(42) must wait until a consumer removes the first -1; the remaining dequeue results are then -1 followed by 42.

What the tests check

  • Repeated fill and drain cycles at capacities 1, 2 and 7: FIFO values, duplicates, signed integer limits, and exact size() after each operation. Separate instances must not share state.
  • Six producers wait on a full capacity 1 queue. Each removal makes room for exactly one successful enqueue, and every submitted element is eventually received.
  • Six consumers wait on an empty capacity 1 queue. Each insertion permits exactly one successful dequeue, with no fabricated or duplicated values.
  • In Java, interrupt a blocked producer and a blocked consumer. Each must propagate InterruptedException, leave the contents unchanged, and allow another waiter and later operations to complete.
  • Seeded start orders with 4 producers and 4 consumers at capacities 1 and 4: 800 items per run, every item exactly once, FIFO within each consumer's observations, size snapshots within bounds, and an empty queue at the end.
  • Four producers and one consumer at capacity 7: the consumer observes each producer's complete sequence, so FIFO checks cannot miss a reversal split across different consumers.
  • Bounded waits and a whole-suite watchdog report stalled operations, including calls made by the harness thread. C++ also runs under ThreadSanitizer to detect data races.

The start order and inputs are repeatable; the operating system still chooses thread interleavings. Short observation windows check that calls remain blocked, and completion deadlines bound failures. These checks exercise safety and progress but cannot prove correctness for every possible schedule. Timeouts, batch insertion and shutdown below are discussion follow ups, not additional methods required by this harness.

Taught in: Producer and consumer with a bounded buffer

Open them one at a time. Each one gives away a little more.

You need one lock that protects the whole queue, and a way for a thread to sleep until the state it needs appears. That is a condition variable. How many different conditions do threads wait for?
Two conditions: producers wait for "not full", consumers wait for "not empty". After adding, wake a consumer; after removing, wake a producer.
Always wait in a loop: while (queue is full) wait;. A woken thread must re-check, because another thread may have taken the space first, and wakeups can be spurious. In C++, pass the condition as a predicate to wait.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why while and not if around the wait?
Two reasons. Spurious wakeups are allowed by every threading API, so a thread can wake with nothing changed. And with several consumers, a woken consumer may find the element already taken by another consumer that got the lock first. A wakeup means "check again", never "go ahead".
Can you use one condition variable instead of two?
Yes, but then producers and consumers wait on the same condition, so you must use notifyAll (notify_all): a notify could wake a producer when only a consumer can make progress, and the signal is lost. Two conditions let you use signal (notify_one) safely and wake only threads that can proceed.
Add offer(element, timeout) and poll(timeout) that give up after a timeout.
Wait with a deadline: awaitNanos in Java (it returns the remaining time; loop until the condition holds or the time runs out), or wait_until with a predicate in C++, which returns false on timeout. Return false or an empty optional on timeout. This is how real services shed load instead of blocking forever.
How would you shut the queue down once producers stop, while consumers drain accepted work?
Add a closed flag under the same lock. close() sets it and wakes both producers and consumers (signalAll, notify_all). Enqueue waits while full and not closed, then rejects if closed. Dequeue waits while empty and not closed; it keeps returning queued elements after close and reports closed only when empty. Make close idempotent, and join the workers before destroying the queue. A poison pill per consumer is another approach when producers have already stopped; choose a representation that cannot collide with a valid item.
Add an atomic multiput that appends a batch.
First define whether the batch is all or nothing. For atomic insertion, reject a batch larger than capacity; otherwise wait until enough slots exist and append the entire batch under the lock. No other producer may interleave items within it. Wake enough consumers for the new items. If producers wait for different batch sizes, wake all waiting producers after removals and let them recheck: waking just one whose batch does not fit can strand another whose batch does fit.
Build a thread pool on top, with submission, shutdown and task exceptions.
Workers dequeue tasks in a loop. Return a future for submissions that need a result, capture task exceptions in that future, and keep workers alive for later tasks. Coordinate rejection and shutdown with admission so no accepted task disappears. Graceful shutdown drains accepted work; immediate shutdown cancels queued tasks and requests cooperative cancellation of running tasks. Practise the full lifecycle in the thread pool problem.
Build it on a fixed array instead of a deque.
Use a ring buffer: an array of size capacity, a head index, a tail index and a count. Enqueue writes at tail and advances tail = (tail + 1) % capacity; dequeue reads at head and advances head the same way. No allocation after construction, which is why high performance queues do it.
What would change with exactly one producer and one consumer?
You could build a lock-free single producer, single consumer ring buffer: the producer only writes tail and the consumer only writes head, so each index has a single writer, published with release stores and read with acquire loads. Blocking when full or empty still needs some wait mechanism, or a spin with backoff.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

This is the monitor pattern: one lock guards all the state (the items), and threads wait on conditions tied to that lock. The invariant is simple: 0 <= size <= capacity, and items come out in the order they went in. Every method takes the lock, waits in a loop until it can make progress without breaking the invariant, changes the state, and signals the threads that may now be able to proceed.

Why each line is there

  • One lock for everything. The deque and its size form one invariant, so one lock guards both, including in size().
  • Two conditions. Producers wait on "not full", consumers on "not empty", so a signal selects the right kind of waiter. The chosen thread still rechecks the predicate when it regains the lock.
  • Wait in a loop. await (and wait) release the lock while sleeping and take it back before returning; by then the state may have changed again.
  • Change the state before signalling. Java Condition.signal requires ownership of its lock, and notifyAll requires ownership of the object's monitor. In C++, notification may happen while holding the mutex or after unlocking, provided the condition variable stays alive. In either language, the waiter must reacquire the lock before checking the state.
  • Propagate interruption in Java. lockInterruptibly lets a thread cancel while acquiring the lock; await lets it cancel while waiting for an item or a slot. Mutation happens only after the wait succeeds, and finally releases the lock even when await throws. A monitor implementation can propagate InterruptedException from wait, although acquiring a Java monitor itself is not interruptible.

Cost and trade-offs

Deque updates take amortized O(1) time and storage is O(capacity); size() takes O(1) time once it owns the lock. Lock acquisition and condition waiting add potentially unbounded delay. Under heavy load all producers and consumers contend for one lock; Java's LinkedBlockingQueue uses separate put and take locks so a producer and a consumer can work concurrently. Item FIFO does not imply fair admission of waiting threads.

How to say it in the interview

I will use the monitor pattern: one mutex guarding the deque, and two condition variables, not full and not empty. Enqueue waits in a loop while the queue is full, adds, and signals not empty; dequeue is the mirror image. The loop handles spurious and stolen wakeups. Because each condition only has one kind of waiter, signalling one thread is safe. If you want, I can add timeouts and a close method next.
