The toolkit: async, future, promise and packaged_task

Separate execution from result delivery, choose async launch policies, propagate exceptions, and understand shared states and future lifetime traps.

Asked atRubrikGoogleMicrosoft
Before this:The toolkit: std::thread, std::jthread and thread_localExceptions, noexcept and exception safetyCopy, move and move-only types

A thread describes execution. A future describes a result that may become available through a dedicated thread, a worker pool, or deferred work.

In plain words

A collection receipt lets you return for a parcel later. The receipt does not tell you whether one courier, a warehouse worker, or you yourself will do the remaining work. A promise is the delivery end, a future is the collection end, and their shared state stores either the parcel or the explanation of failure.

Why this matters for concurrency

Pool submissions return results without exposing worker threads. Exceptions must cross thread boundaries deliberately. Waiting for a result can also deadlock when the caller holds a resource the task needs. Learn these APIs here, then study futures and promises, asynchronous composition, and building a thread pool.

Start with the shared state

A shared state is the library-managed connection between the producer and consumer. It contains readiness plus either a result or an exception. A future is a move-only handle to that state. valid() is true even while the task is running; a default constructed or moved-from future has no state.

For an ordinary std::future<T>, get() waits, obtains the stored result, and invalidates the handle, including when it rethrows a stored exception. Do not call get() twice. Use valid() only for association checks; use timed waits for readiness checks. Calling get() or a waiting function on an invalid future is undefined behaviour in C++20; do not rely on a particular library always throwing a helpful error.

Readiness publishes preceding work. Successfully detecting readiness establishes the library's synchronization with the provider's result publication. A timed wait returning timeout or deferred, and a call to valid(), provide no such publication guarantee. See the C++20 shared-state rules.

That synchronization does not authorize concurrent mutation of the same external object after readiness. A future carrying a pointer also does not automatically own the pointee. Prefer a value result or an explicit owning pointer when that expresses the real lifetime.

std::future<T>::get() moves an ordinary value out, so T can be move-only, such as std::unique_ptr<int>. std::future<T&>::get() returns T& without extending the referred object's lifetime; std::future<void>::get() returns nothing but still waits and propagates failure. These are distinct result retrieval contracts.

std::async: choose the launch policy explicitly

With std::launch::async, the callable runs as if in a new thread of execution. With std::launch::deferred, execution is postponed until the first nontimed wait, such as get() or wait(), on the state. The waiting thread executes it. While work is still deferred, a timed wait reports deferred without starting it. If nobody performs a nontimed wait, the deferred callable never runs.

The overload without an explicit policy permits std::launch::async | std::launch::deferred, so it can choose deferred execution. Specify std::launch::async when the contract requires a separate execution thread, although simultaneous progress still depends on scheduling. An inability to start that thread throws std::system_error with std::errc::resource_unavailable_try_again; allocation can throw std::bad_alloc. std::async is not a bounded worker pool.

In C++20, std::async copies or moves decayed versions of the callable and arguments in the submitting thread. Failures while making those copies escape the call itself; exceptions from running the callable are stored for get(). Use std::ref(x) from <functional> to pass an argument by reference deliberately. Neither it nor a lambda's reference capture extends x's lifetime: keep x alive through completion, or transfer ownership with a value or move capture.

The async destructor trap

A future obtained with std::launch::async has special shared-state lifetime behavior: releasing the last reference to that state can wait for the asynchronous execution to complete. Consequently, discarding each temporary future in a loop can serialize work you intended to overlap. Keep the futures, then call wait() or get() after launching the intended set.

Do not generalize this into “all future destructors join.” A future obtained from a promise or std::packaged_task does not gain ownership of an arbitrary producer thread. Conversely, shared future copies can extend the async state lifetime, moving the final wait to another owner's destruction. The precise special case is described by the C++20 async shared-state rules.

A blocking destructor is especially dangerous while holding a mutex the async task needs. The same applies to get() and wait(). Establish the lifetime boundary outside such locks, including move assignment that releases an existing async state. Discarding an async future also discards ordinary result inspection: destruction waits when required but does not rethrow the task's stored exception for you.

std::promise: explicitly deliver a value or exception

A promise is the provider endpoint. Obtain its future before transferring the promise to a producer, so you retain the consumer handle. Move the promise, because it is not copyable. A successful set_value() or set_exception() fulfills the state once; another fulfillment throws std::future_error with std::future_errc::promise_already_satisfied.

get_future() is permitted once per shared state; repeating it throws std::future_error with std::future_errc::future_already_retrieved. Fulfillment may precede that first retrieval. Calling get_future(), set_value(), or set_exception() on a moved-from promise throws std::future_error with std::future_errc::no_state; this differs from an invalid future's get(), which has undefined behaviour.

Use std::promise<void> for a completion event without a value and call its set_value() with no argument. For a failure, catch inside the worker and use std::current_exception() to capture the active exception. Pass a non-null std::exception_ptr to set_exception(); the consumer's get() rethrows it on the consumer thread. A plain thread does not perform this transport automatically.

These result APIs date from C++11. The samples use C++20 std::jthread for automatic joining during unwinding; in C++17 use std::thread with an RAII joining guard, as in the threads toolkit.

The outer caller cannot catch a worker's escaping exception with a try around join(); an exception escaping the thread function calls std::terminate(). In this program the worker catches before escaping, and the shared state transports the exception. Setting an already fulfilled or moved-from promise is a separate programming error, not a task failure to silently retry.

Destroying an unfulfilled provider abandons its state. If a consumer remains, it becomes ready with std::future_errc::broken_promise rather than waiting forever for a result that can no longer arrive. That is different from the task explicitly throwing std::runtime_error. It often signals a dropped task, a missing fulfillment branch, or shutdown discarding queued work.

A ready result is not necessarily an exited producer

A promise's set_value() can wake the consumer while the producer keeps running. It publishes work before fulfillment, not later cleanup. set_value_at_thread_exit() and set_exception_at_thread_exit() instead store the outcome now and make it ready at thread exit, after thread-local destruction; see the promise contract. Do not use these to signal per-task completion on a long-lived pool worker.

std::packaged_task: the callable plus its result channel

A packaged task combines the callable with the promise-like result storage. Obtain its future, move the task into an execution mechanism, and invoke it there. Invocation stores a normal return or catches and stores the callable's exception. Construction alone starts no thread. This separation is why std::packaged_task is a useful building block for a pool.

For ordinary T, std::shared_future<T>::get() returns const T& into the shared state. Copies keep that state alive; do not retain a reference after the owning handles are gone. std::shared_future<T&>::get() returns T&, and the void specialization returns nothing. Repeated get() calls also rethrow a stored exception repeatedly, without invalidating the handle.

Give each consumer its own std::shared_future copy. The shared state synchronizes readiness; it does not make concurrent assignment or destruction of the same handle safe. Access through the returned result must also be safe: a shared future of a mutable pointer does not protect its pointee. Sharing a future of std::unique_ptr<T> allows observation through a const reference, not multiple transfers of unique ownership.

std::packaged_task is move-only, so std::function<void()> cannot directly hold a C++20 lambda that owns one by move. Options include a queue whose element is std::packaged_task<void()>, a custom move-only task wrapper, or a copyable lambda holding a shared pointer to a task with carefully defined single invocation.

Each task state is fulfilled once. A second invocation throws std::future_error with std::future_errc::promise_already_satisfied, even though valid() remains true. reset() retains the callable but creates a fresh result state: obtain a new future before reusing it. Existing futures retain the old outcome; resetting an unfulfilled task abandons the old state with broken_promise. See the task member contracts.

Waiting, cancellation, and pool starvation

C++20 std::future has no cancel() method and no built-in then() continuation member. A timeout from wait_for() stops waiting, not the underlying work. Supply a stop token or another explicit cancellation protocol to the task if cancellation is part of the contract. A timeout is also not proof that the task has not started, and readiness may change immediately after that observation.

A timed wait does not bound the enclosing function's latency. Scheduling can delay the wait's return, and returning from a timeout branch can destroy the last async future and wait for the task anyway. Handle ready, timeout, and deferred separately; polling until ready will never start deferred work. For repeated waits use one std::chrono::steady_clock deadline instead of restarting the full timeout each time.

A pool worker that waits on a child task submitted to the same fully occupied pool can prevent that child from ever running. This is a capacity dependency even without a mutex. Avoid blocking nested waits, reserve execution capacity deliberately, or choose a scheduler designed for that composition. The pool failure lesson explores these cases.

Worked example: submit in a small pool

Suppose your two-worker pool accepts tasks A, B and C. Create a std::packaged_task and obtain its future for each submission. Under the queue mutex, either accept the task or reject it according to shutdown and capacity rules. A worker removes a task while locked, then leaves the lock scope before invoking it.

A returns 42 and B throws: their futures become ready with 42 and the captured exception respectively. If shutdown destroys queued C before invocation, C's future becomes ready with broken_promise; if shutdown only returns C to an owner who retains it, C remains pending. Choose that policy explicitly. None of these outcomes require exposing a worker thread to the caller, and B's callable exception does not kill its worker.

Common mistakes

  • Using valid() as a ready check: it reports state association.
  • Calling get() twice on std::future: use std::shared_future for repeated observation.
  • Assuming wait() rethrows task exceptions: get() performs result retrieval.
  • Discarding async futures and accidentally waiting at each semicolon: keep the handles until all intended launches have occurred.
  • Expecting a timed wait to cancel work or a promise future to join its producer: manage cancellation and thread lifetime separately.
  • Returning work that captures a local by reference: give the task ownership, or keep the local alive until completion.

In the interview

Expect “make pool submissions return results,” “why do these async calls run serially?” or “the wait timed out, so why has the request not returned?” Explain the execution policy, state ownership, and publication boundary before proposing a fix.

I separate who executes the task from how its result travels. A packaged task can run on any worker and fulfill a future with a value or exception. I state the launch policy, avoid waiting under locks, and define rejection and cancellation outside the future API.

Be ready to trace a dropped queued task, return a move-only result, distinguish readiness from thread exit, and explain why a pool full of waiting parents cannot run their children.

Key takeaways

  • A future observes a result; a thread supplies execution.
  • get() consumes an ordinary future, while std::shared_future supports repeated reads.
  • Launch policy and last-state destruction can change when and where work completes.
  • A promise transports explicitly stored failures; a packaged task captures callable failures automatically.
  • Readiness publishes preceding work; timeout, cancellation, and thread exit are separate events.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A valid future is not ready yet. Is that contradictory?
Why. Association and readiness are different. Timed waits inspect readiness; valid() does not, so get() can still block. Futures from async launches and packaged tasks can also be valid before they are ready.
A future's deferred callable has not started. What does wait_for(std::chrono::milliseconds(0)) do?
Why. A timed wait neither starts a background thread nor executes the deferred callable. Deferred execution starts on a nontimed wait such as wait() or get(), in the thread performing that wait. After the callable has completed, later waits report readiness instead.
A task exception was stored in a future. Which call retrieves and rethrows it?
Why. wait() waits for readiness but does not extract the result. get() performs retrieval and rethrows a stored exception. valid() only checks whether the handle refers to a shared state; an exception is still a ready outcome.
Which destructor can wait for task execution as a special shared-state rule?
Why. The std::launch::async case has special execution lifetime rules. A promise-produced or packaged-task-produced future does not automatically own or join an arbitrary producer thread, so “every destructor” is wrong. Unstarted deferred work is not executed merely because its future is destroyed, but that does not make “no destructor can wait” true.
An unfulfilled promise is destroyed while its future survives. What is the result?
Why. Abandonment stores std::future_error with std::future_errc::broken_promise and makes the state ready. get() throws that error; no default result is fabricated and the missing producer does not leave the future waiting forever.
Why is std::packaged_task useful in a pool?
Why. The pool supplies execution and queueing; constructing a packaged task creates no workers. std::packaged_task captures the outcome and is move-only, so neither it nor a lambda owning it becomes copyable just because the callable is packaged.
Assuming thread creation succeeds, what does this program print?
Why. The write to payload precedes publication, which synchronizes with successful waiting. The read therefore observes 42 without a data race even before the worker is joined. wait() does not consume the handle, so valid() is true, printed as 1. A read after only valid() or a timed-out wait would lack this publication guarantee.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
Two discarded std::launch::async calls appear to run serially. What is the likely reason?
Model answer
Each temporary future can be the last owner of its unfinished async state. Its destruction at the end of the statement waits before the next statement launches more work. Keep both futures until the intended launches have occurred, then retrieve results. This permits overlap; scheduling does not guarantee simultaneous execution.
Design
How would a pool return exceptions to callers without killing its workers, including tasks dropped during shutdown?
Model answer
Wrap tasks in std::packaged_task or catch inside a worker and fulfill a promise with std::current_exception(). Execute user work outside the queue mutex. Return the associated future so get() rethrows on the caller. Reject before returning a future, or return a future fulfilled with a defined rejection exception. Destroying queued, uninvoked packaged tasks makes their futures ready with broken_promise; merely retaining those tasks elsewhere leaves the futures pending. If the API promises a distinct cancellation exception, provide that result explicitly rather than treating abandonment as cancellation.
Debug
A function times out in wait_for() and immediately returns, but the caller still waits for the task to finish. Why?
Model answer
The timeout only ended that wait; the task can already be running. Returning can destroy the last future for a std::launch::async state, which waits for completion. Keep execution and captures alive under a longer-lived owner, or request cooperative cancellation and wait for acknowledgement if that fits the deadline contract. Neither a future timeout nor a stop request forces an uncooperative task to finish. Even the timed wait itself can return late because of scheduling.

How a senior would say it
A thread is an execution resource. A promise is the provider side of a shared result state, and a future is the consumer side that waits and retrieves a value or exception. A packaged task combines a callable with that result channel: invoking it stores either the return value or the thrown exception. It does not start a thread by itself. That makes it useful in a pool, where the queue and workers decide when to execute it. I can return the future to the submitter while keeping thread ownership inside the pool.

Likely follow up: What happens if a queued provider is destroyed without ever running?

Out loudabout 60 s
"Why can destroying a future unexpectedly block, and why is that dangerous under a lock?"
What a strong answer covers
  • std::launch::async states have a last-reference completion rule
  • Temporary future destruction can serialize launches
  • Promise futures do not universally join producers
  • Waiting under a needed mutex creates a cycle
How a senior would say it
The special case is a shared state created with std::launch::async. Releasing its last reference can wait for the associated execution to finish. That can happen at the end of a statement when a temporary future is discarded, so apparently parallel launches may become serial. It is also dangerous while holding a mutex: if the worker needs that mutex before returning, destruction waits for a worker that is waiting for the caller. I keep the result handles deliberately and place completion waits outside such locks. I would not generalize the behavior to every promise-produced future.

Likely follow up: Does destroying that future rethrow a stored task exception?
