Seat booking with expiring holds

Thread-safe designshard40 minTicketmaster and BookMyShow style roundsMetaRubrik

Meta's Ticketmaster design rounds and Rubrik's BookMyShow style system coding round both come down to this class. Two users must never get the same seat, and a hold must lapse on time, even while the holder's payment is still in flight.

The task

A show has seats seats, numbered 0 to seats - 1. A user first holds a seat for a limited time while they pay, then confirms it. Thousands of users click at once, so every method is called from many threads.

  • hold(seat, user, ttlMs) succeeds if the seat is not booked and has no live hold by another user. The hold lasts ttlMs from now. If the same user holds the seat again, the hold is renewed: it now lasts ttlMs from the renewal.
  • confirm(seat, user) succeeds if this user has a live hold on the seat. The seat is then booked by this user for good. Confirming a seat this user already booked returns true again, because payment callbacks get retried; for anyone else it returns false.
  • release(seat, user) drops this user's live hold and returns true. It returns false if the user has no live hold on the seat, including when the seat is booked.
  • bookedBy(seat) returns the user who booked the seat, or nothing.

Time comes from a clock you are given, in milliseconds, and it never goes backwards. A hold granted at time t with ttlMs = d is live while clock() < t + d and has expired from t + d on. Never read the system clock yourself: the tests move time by hand.

Rules. No background threads are needed: an expired hold can simply be treated as free whenever a call looks at the seat. Users are non-empty strings. Seat numbers are always in range.

Example. The clock reads 1000. Alice holds seat 7 for 100 ms, so her hold is live until 1100. At 1099 Bob's hold(7, "bob", 100) returns false. At 1100 Alice's hold has expired: Bob's hold now succeeds, Alice's confirm(7, "alice") returns false (her payment must be refunded), and Bob's confirm returns true.

What the tests check

  • One thread: hold, a second user refused, confirm, a retried confirm, release and hold again, holding a booked seat refused.
  • Expiry with a fake clock, at exact boundaries: live at expiry minus 1 ms, expired at expiry; confirm and release after expiry fail; a renewed hold lasts from the renewal.
  • 8 users hold the same free seat at the same instant, then all try to confirm (200 rounds in Java, 80 in C++): exactly one hold and one confirm succeed, both by the same user.
  • Confirm racing expiry (300 rounds in Java, 120 in C++): Alice confirms at the instant her hold expires while Bob tries to take the seat. Never both; if Bob got the hold, his confirm must succeed; bookedBy must agree with whoever confirmed.
  • A stress run over many shows: 8 users hammer 8 seats with random holds, confirms and releases while the clock moves forward. The harness records every successful confirm, so a seat confirmed for two different users fails the test, and bookedBy must match the record at the end.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Design cases: seats, flash sales, schedulers and counters

Open them one at a time. Each one gives away a little more.

Model one seat before you think about threads. What states can it be in? Free, held by a user until some time, booked by a user. An expired hold behaves exactly like free, so you do not need a thread to clean it up: compare the clock with the expiry whenever you look.
Every method is a check-then-act on one seat: "free or expired, so take it", "my live hold, so book it". The check, the act and the clock reading must all happen under the same lock. A ConcurrentHashMap read with get and written with put makes each call safe and the decision between them unsafe.
No method touches two seats, so one lock per seat is enough and lets different seats proceed in parallel: a small Seat object used as a monitor in Java, or a struct holding a std::mutex in C++. Inside the lock, read now once, treat the hold as live only if now < expiresAt, and decide.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

A family wants four seats together, all or nothing. How do you hold several seats at once?
Lock the four seats in increasing seat number, check all four, then take all or none, and unlock. The fixed order is what stops two families wanting overlapping seats from deadlocking (lock ordering). In a database it is one transaction whose conditional update must change exactly four rows, else roll back; in Redis, a Lua script that checks and sets all four keys in one step.
Payment takes three minutes and the hold is two. What happens, and what should happen?
The confirm fails, by design: after expiry the seat may already belong to someone else, so confirming would double book it. The payment flow must handle the loser: void or refund the charge, keyed by an idempotent payment id so a retried callback cannot refund twice. Better still, renew the hold when payment starts, or authorise first and capture only after the confirm succeeds. Never keep a database lock open across a payment.
The service now runs on many servers. Where do the holds live?
In one shared store that can do a conditional write. Redis: SET seat:42 alice NX PX 120000 takes a free seat with an expiry in one atomic command. SQL: UPDATE seats SET holder = ?, expires_at = ? WHERE id = ? AND status = 'OPEN' AND (holder IS NULL OR expires_at <= now()), then check that one row changed; confirm is another conditional update on holder = ? AND expires_at > now(). Use the store's clock, never each server's. This is where Meta's Ticketmaster interviews push hardest.
Why not a background thread that deletes expired holds?
Correctness would then depend on the sweeper's timing: a hold that expired a second ago but has not been swept would still block the next user, unless every check also compares times. Once every check compares times, the sweeper only reclaims memory. Lazy expiry is exact and simpler; add a sweeper or a delay queue only if dead holds pile up.
Why pass a clock in at all?
Because expiry logic cannot be tested with real time: tests would sleep, run slowly, and flake at the boundaries. An injectable clock lets a test step to exactly expiry minus 1 and expiry. In production pass a monotonic clock (System.nanoTime() / 1_000_000, std::chrono::steady_clock), never wall time, which can jump backwards.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Each seat is a tiny state machine: open (no holder, or a hold whose time has passed), held by one user until expiresAt, or booked by one user forever. The invariant the tests attack is: a seat is booked by at most one user, ever, and at any instant at most one user has a live hold. Every method reads one seat's state, decides, and changes it, so every method is a check then act, and each one runs entirely inside that seat's lock.

With the lock, Alice's read and write are one step: either she books the seat before Bob looks (Bob is refused), or Bob takes it first (Alice's confirm sees Bob's hold and fails). The harness checks exactly that, hundreds of times.

Why each line is there

  • A lock per seat, not one for the whole show: no method touches two seats, so finer lock granularity costs nothing in correctness and lets a sold out front row not slow down the back row. If a method ever needs two seats (the family follow up), take their locks in seat order.
  • Lazy expiry. "Expired" is computed, never stored, so there is no window where a hold is stale but still blocking, and no sweeper thread to start, stop and test.
  • now < expiresAt for live, >= for expired. Pick one boundary and use it everywhere; the tests check both sides of it.
  • Idempotent confirm. Payment providers retry callbacks. Returning true to the winner's retry, and false to everyone else, makes a retry harmless.
  • release refuses an expired hold. After expiry the seat may already be someone else's, and releasing it would drop their hold.

Cost and trade-offs

Every call is O(1) under one seat's lock, and the lock is never held for anything slow. A booked seat keeps its user forever, and an expired hold costs one object per seat at most, so memory is O(seats). The design scales across cores with the number of distinct seats being clicked; a single hot seat serializes, which is exactly the point.

How to say it in the interview

Each seat is a small state machine: open, held until a time, or booked. Every operation is a check-then-act on one seat, so each runs under that seat's lock, and I read the clock inside the lock because expiry is part of the state I decide on. Expiry is lazy: a hold whose time has passed is treated as open, so there is no sweeper to get wrong. Confirm is idempotent for the winner because payment callbacks retry. Across servers I would move the same conditional writes into the database or Redis and use the store's clock.
