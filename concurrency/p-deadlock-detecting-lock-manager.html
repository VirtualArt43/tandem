Deadlock-detecting lock manager

Build a primitivehard55 minMicrosoft

Detecting a cycle is easy on a frozen graph. Keep that graph correct while real threads acquire, wait, release and recover.

The task

Manage named exclusive resources identified by integers. An acquisition either succeeds, waits in arrival order, or is rejected because adding its wait would create a cycle. In Java reject with DeadlockException; in C++ return false. No timeout or arbitrary retry may replace cycle detection.

  • A resource has one owner. Reacquiring one you own, releasing another thread's resource, and releasing an unowned or unknown resource throw IllegalStateException in Java or std::logic_error in C++. These errors leave ownership and queues unchanged. A successful release permits a later acquisition of the same identifier.
  • Arrival order is the order blocked requests join that resource's queue. Ownership must pass to its oldest waiter without barging.
  • A rejected acquisition leaves all the caller's existing resources owned and removes the rejected request from the queue and wait graph. The caller must release its existing resources to let the other threads progress. Rejection must not leave a phantom owner when those resources are reused.
  • A thread has at most one outstanding blocked acquisition. Dependencies must reflect current ownership and FIFO admission, including after ownership changes. Graph updates and detection are atomic relative to acquisitions and releases. A valid implementation may use immediate FIFO predecessors or an equivalent graph that follows each requested resource's current owner.
  • An interrupted Java waiter throws InterruptedException, removes its pending request and keeps resources it acquired earlier. If interruption races with a grant, either acquisition succeeds and the caller must release it, or interruption wins and the manager must pass on any ownership granted to the cancelled request. An exceptional return must leave neither that queue entry nor ownership of the requested resource behind.
  • waitingCount(id) is a thread-safe, read-only snapshot of that resource's queued requests. It excludes the owner and returns zero for an unknown identifier. All integer identifiers are valid, including negative values. Resource identifiers persist for the manager's lifetime; reclamation and resource exhaustion are outside this exercise.

Example: A owns 1 and waits for 2; B owns 2 and asks for 1. Reject B's new request. B still owns 2 and must release it so A can continue.

What the tests check

  • Coordinated cycles of two, three and eight threads each produce exactly one victim. Every affected resource is then acquired again to catch abandoned owners and rejected requests left in queues.
  • A queued thread becomes the owner while another thread still waits behind it. A subsequent request must detect the cycle using the new owner, retain the victim's earlier ownership and recover.
  • Five waiters acquire in recorded arrival order. A new acquisition after release must join behind them.
  • Releasing one resource wakes its eligible waiter while another resource remains owned. Unrelated wakeups must not let the other waiter enter.
  • Eight threads acquire resources in ascending order without false cycle reports or overlapping owners.
  • Independent resources are owned concurrently, measured with an active counter.
  • Reentrancy, foreign-owner release, double release and unknown-resource release fail with the required exceptions. Extreme integer identifiers and reuse after errors work.
  • Java cancellation removes the first, middle or last of three waiters before the owner releases. The cancelled thread retains its earlier resource while a new request traverses its graph entry; surviving waiters keep FIFO order.
  • Sixteen Java interrupt versus handoff races accept either valid outcome, then reacquire the affected resources to catch leaks. Worker exceptions fail the run. Watchdogs and bounded joins prevent hangs; C++ runs under ThreadSanitizer.

Taught in: Deadlock avoidance and detection

Open them one at a time. Each one gives away a little more.

Write down who each blocked thread must wait for. A FIFO waiter may first depend on another waiter.
Use one metadata mutex for owners, queues and wait edges. Add the proposed edge and search before sleeping.
Reject and remove only the new request when a cycle appears. Release should transfer ownership directly to the oldest waiter.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How does this relate to the Microsoft cycle-detection question?
The reported question reduces threads and resources to graph cycle detection. This exercise adds live ownership updates, FIFO queues and recovery, so the graph must stay consistent while callers block.
Is a cycle sufficient with multiple instances per resource?
Not in general. This exercise has one exclusive instance per identifier. Multiple interchangeable instances need counts and a different safety or detection algorithm; do not apply this graph rule unchanged.
Who should be the victim?
Rejecting the newly arriving request is deterministic and avoids revoking a running owner. A production system could choose by rollback cost, but would need a safe cancellation protocol.
Could lock ordering solve this instead?
Yes, requiring a global order prevents cycles. The point here is to allow arbitrary acquisition order and detect the unsafe request. A timeout alone neither proves nor identifies a cycle.
How would you debug a real hang?
Capture thread stacks plus the owner and waiter graph, and look for a cycle or an owner that never releases. Apple ThreadSanitizer does not provide the Linux lock-order-inversion detector; explicit graph assertions and bounded waits remain useful.

The invariant

One monitor owns the resource table and the wait relation. A thread in a queue has exactly one waiting entry and no ownership of that requested resource. The first waiter depends on the owner; later waiters depend on their immediate predecessor. Those edges include the ordering imposed by FIFO admission.

Under the one-outstanding-wait rule, each FIFO predecessor is itself waiting in that same queue, so following predecessors eventually reaches the current owner. For cycle detection, you can also connect every waiter directly to that current owner: expanding or compressing these queue paths preserves whether a cycle exists. This equivalence does not excuse caching the owner seen at enqueue time. After a handoff, that thread may no longer block anyone.

The algorithm and its linearization points

Uncontended acquire installs an owner under the monitor. A contended acquire appends a waiter, records its resource, and follows dependencies. If the traversal repeats a thread, remove the new request and report a deadlock. Otherwise sleep with a predicate. Release transfers ownership before notifying, so a newcomer cannot steal the resource while its oldest waiter is waking.

The same mutex makes cycle testing and graph mutation indivisible. Waiting releases it, so unrelated resource owners can execute their protected work concurrently. In Java an interrupt can race with ownership transfer. Cleanup must handle both cases: remove a queued entry, or hand off ownership again if the waiter already became owner.

For example, O owns X, A queues for X, and B owns Y and queues behind A for X. O releases X to A. If A now asks for Y, reject A: A waits for B, and B waits for the new owner A. A cached edge from B to O would miss this cycle. After the rejection, A still owns X and must release it so B can finish.

The broken interleaving

The broken implementation checks only whether its immediate dependency waits directly back on it. A holds 0 and waits for 1, B holds 1 and waits for 2, and C holds 2 and waits for 0. No pair is a two-thread cycle. All three wait forever, so the three-thread test fails its bounded join.

Costs and pitfalls

The reference favors readable containers. Dependency lookup scans a resource queue, so detecting a chain of T waiting threads with maximum queue length Q costs O(TQ), plus map and set lookup costs. Direct predecessor links and hash tables can reduce traversal overhead. Metadata uses O(R + T) space for resources and blocked threads. Detection is not recovery: rejecting one request only helps if the victim releases the resources it already owns.

How to say it in the interview

I will serialize the owner table and wait graph, not the protected work. Before blocking I add the dependency and check for a cycle. If it closes one I reject only that acquisition. Release hands ownership to the oldest waiter, and the victim releases its earlier resources so the remaining threads can progress.
