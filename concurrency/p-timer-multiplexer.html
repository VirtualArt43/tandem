Many timers on one hardware timer

Executors and asynchard50 minGoogle onsite 2019 and phone screen 2025 (many timers over one single-shot timer)Google

Google has asked this one at least twice: the device has exactly one timer that can hold one deadline, and you must build as many timers as callers want on top of it, safely, from any thread. It looks like a heap question until you notice the interrupt runs on its own thread, races with every schedule and cancel, and can arrive when nothing is due.

The task

The harness gives you a HardwareTimer with two calls. now() reads a monotonic clock in milliseconds. arm(deadline) sets the timer's single pending deadline and replaces whatever was pending. When the clock reaches that deadline, the timer clears it and calls your onInterrupt() on its own interrupt thread. A deadline that has already passed fires at once. Interrupts can also arrive late or spuriously, when nothing is due.

Build TimerMultiplexer on top of it:

  • schedule(callback, delayMs) may be called from any thread. It returns a unique id, and the callback runs once, on one of workers worker threads, no earlier than now() + delayMs.
  • cancel(id) stops a timer that has not been handed to a worker yet and returns true; it returns false if the timer already fired, was cancelled before, or never existed.
  • onInterrupt() is called by the hardware on the interrupt thread. It must return quickly and must never run a callback itself: hand due callbacks to the workers.
  • shutdown() drops every pending timer, lets callbacks already handed to a worker finish, stops the workers and returns. schedule afterwards returns -1.

Rules, as in the interview: build the mechanism yourself. No scheduled executors, no Timer or TimerTask, no DelayQueue, no std::async. In Java a plain fixed pool for the workers is acceptable, but a few threads of your own are just as short. In C++ use std::thread, std::mutex and std::condition_variable.

Worked example

The clock reads 1000. You schedule A in 500 ms, so the hardware is armed for 1500. Then B is scheduled in 100 ms: B is now the earliest, so you re-arm for 1100. Then C in 300 ms: the alarm stays at 1100, because arming for 1300 would make B late. At 1100 the interrupt arrives, you hand B to a worker and arm for 1300. If B is cancelled before 1100 instead, you re-arm for 1300 straight away (or ignore the useless interrupt at 1100 and re-arm then).

What the tests check

The harness's timer runs on a manual clock: time moves only when a test advances it, so every deadline is checked to the millisecond.

  • A timer fires exactly at its deadline, and not one millisecond before; the hardware is armed for the right deadline after each schedule.
  • A timer scheduled later but due earlier re-arms the hardware, and a later one never pushes the alarm back.
  • Cancelling the head leaves the hardware armed for the next timer, and the cancelled callback never runs.
  • A stale interrupt (nothing due) runs nothing and leaves the alarm set for the head; one on an empty multiplexer is harmless.
  • cancel is true once, false the second time, false after the timer fired, false for an unknown id.
  • Two slow callbacks due together overlap on two workers, none runs on the interrupt thread, and onInterrupt returns quickly.
  • A callback that throws does not kill its worker; a callback can schedule the next timer without deadlocking.
  • Stress: 8 threads schedule 1,000 timers and cancel some of them at random while the clock is stopped; then the clock moves in random steps. Every live timer fires exactly once, cancelled ones never, none early, and with one worker they run in due order.
  • Stress: 8 threads schedule and cancel while another thread keeps advancing the clock; every live timer fires exactly once and never early.
  • shutdown returns, later schedule calls return -1, and dropped timers never run. In C++, ThreadSanitizer must stay quiet.

Taught in: Scheduled executors and timers

Open them one at a time. Each one gives away a little more.

Keep every pending timer in one structure ordered by due time (a min-heap, or an ordered set so you can delete from the middle), with a map from id to timer for cancel. One mutex guards all of it. The hardware should always be armed for the earliest pending timer.
Remember the deadline you last armed. In schedule, re-arm only when the new timer is earlier than that. In cancel, re-arm only when you removed the head. In onInterrupt, read now(), move every timer with due <= now to a ready queue for the workers, then arm for the new head.
Never trust an interrupt to mean "the head is due". Check due times every time: a stale interrupt must move nothing. And never run callbacks in onInterrupt or while holding your mutex: workers wait on a condition variable for the ready queue, take one callback, release the mutex, run it, and catch whatever it throws.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What if the interrupt handler is a real interrupt service routine that may not block on a mutex?
Then onInterrupt cannot take a lock that a thread may hold while preempted. The usual design keeps the handler tiny: it sets a flag or posts to a lock-free single producer queue (or a semaphore that is safe to post from an interrupt), and a dispatcher thread does the heap work under a normal lock. On a single core embedded system you may instead disable interrupts around the short critical sections in schedule and cancel. Say which world you are in before you pick.
The 2021 Google version had millions of scheduled jobs. Does a heap still work?
A heap is O(log n) per insert and per expiry, which is fine for a few million timers but heavy for very many short timeouts that are mostly cancelled (network retransmission timers). A hierarchical timing wheel gives O(1) insert and cancel: buckets per tick at several resolutions, with timers cascading to finer wheels as they get close. Linux and Kafka use timing wheels for exactly this reason. You still arm the hardware for the next non-empty slot.
Add periodic timers. Fixed rate or fixed delay?
Fixed rate computes the next due time from the previous scheduled time (due += period), so the timer does not drift but can bunch up after a slow callback. Fixed delay schedules the next run period after the callback finishes, so it never overlaps itself but drifts. Re-insert from the worker after the run, under the same mutex, and keep the same id so cancel still works.
Can cancel stop a callback that is already running?
No, and it should not pretend to: once a worker has the callback, cancel returns false because it cannot take the run back. If callers need to stop running work, pass a cancellation token that the callback checks, which is cooperative cancellation. The important guarantee is the race-free one: exactly one of "cancel returned true" and "the callback ran" happens, because both decisions are made under the same mutex.
Why a monotonic clock and not wall-clock time?
Wall-clock time can jump backwards or forwards (NTP corrections, manual changes), which would fire timers early or hold them for hours. Due times must be computed on a clock that only moves forward: System.nanoTime in Java, std::chrono::steady_clock in C++.
The Google 2022 variant passed register_callback(fn, arg, delay) in C. What changes?
Only the shape: the callback becomes a function pointer plus a void* argument stored in the timer entry, and the worker calls fn(arg). The concurrency design is identical: one lock around the heap, re-arm on a new earliest timer, check due times in the interrupt, run callbacks elsewhere.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The key idea

The hardware timer is a single slot, so the multiplexer's whole job is to keep one promise: whenever a timer is pending, the hardware is armed at or before the earliest due time, or an interrupt is already on its way and will re-arm. Every method either keeps that promise or restores it before releasing the lock. The interrupt is treated as a hint ("look at the heap now"), never as proof that the head is due.

Invariants

  • A timer is in exactly one place: the pending set (ordered by due time, with the id map), the ready queue, or gone. cancel succeeds only while it is pending, and onInterrupt moves it out of pending under the same lock, so "cancel returned true" and "the callback ran" can never both happen.
  • armedFor is the last deadline handed to the hardware. schedule arms only when the new due time is earlier, so a later timer never pushes the alarm back.
  • onInterrupt resets armedFor, hands over only timers with due <= now(), and re-arms for the new head. A stale interrupt therefore moves nothing and simply re-arms.
  • Callbacks run only on workers and never under the lock, so a slow callback cannot delay the interrupt, and a callback may call schedule or cancel.

Why each primitive

  • One mutex around the heap, the id map, the ready queue and armedFor: they form one invariant, and every operation is short.
  • A min-heap or ordered set keyed by (due, id): O(log n) insert and expiry, and the id breaks ties so equal deadlines fire in scheduling order. Java's PriorityQueue.remove(e) is O(n), which is fine here; the C++ reference uses std::set so cancel is O(log n). Lazy deletion (mark cancelled, skip when popped) is the other common answer.
  • A condition variable for the ready queue: workers sleep until there is work or shutdown, and wait in a loop (predicate) because wakeups can be spurious or stolen.
  • Re-arming with past deadlines is safe: if the head became due while you were working, arm fires at once and the next interrupt handles it.

Pitfalls

  • Running callbacks inside onInterrupt: they serialize on the interrupt thread, one slow callback delays every other timer, and in a real system it blocks interrupt handling. This is the broken version the tests catch.
  • Arming on every schedule: the last scheduled timer wins and earlier ones fire late.
  • Popping the head without checking its due time: a stale or early interrupt fires it early.
  • Calling a callback while holding the mutex: a callback that calls schedule deadlocks with std::mutex, and everything else stalls behind it.
  • Forgetting to re-arm after an interrupt: the one-shot alarm is spent, so the next timer never fires.
  • Letting an exception from a callback escape the worker loop: the worker dies and the pool quietly shrinks.

Cost

schedule, cancel and each expiry are O(log n) under one lock; the lock is never held during a callback. With many threads scheduling at a very high rate the single lock becomes the bottleneck, which is where sharded wheels or per core timer structures come in.

How to say it in the interview

I keep pending timers in a min-heap by due time with an id map for cancel, all under one mutex, and I keep one invariant: the hardware is armed for the earliest timer. Schedule re-arms only if the new timer is earlier, cancel re-arms only if it removed the head. The interrupt handler treats the interrupt as a hint: it reads the clock, moves every timer that is actually due to a ready queue, and re-arms for the new head, so a stale interrupt does nothing. Callbacks never run on the interrupt thread or under the lock; a small worker pool takes them from the ready queue, so slow callbacks overlap and can even schedule new timers.
