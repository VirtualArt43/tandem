Atomics and lock-free programming

Atomic variables, compare-and-swap and CAS loops, counters under contention, spinlocks, the lock-free stack, ABA, and progress guarantees.

1CorecasRubrikDatabricks
What is compare-and-swap, and how does it work in hardware?
Model answer

compare-and-swap takes an address, an expected value and a new value, and atomically: if the current value equals the expected one, it writes the new value and reports success; otherwise it changes nothing and reports failure. In C++ a failed CAS also writes the current value back into expected. CAS builds lock-free algorithms and locks. Java AtomicReference compares reference identity, not equals.

In hardware:

  • x86: lock cmpxchg. The core holds the cache line exclusively for the duration, so no other core can change it in between.
  • ARM: originally load-linked and store-conditional (ldxr and stxr): the conditional store can fail if a conflicting write or another event clears its reservation. Mere reads need not make it fail; implementations may retry internally for a strong CAS. ARMv8.1 added a single CAS instruction (the LSE atomics).

CAS is optimistic: losers retry or give up. Its progress depends on the atomic implementation; a generic C++ atomic may use a hidden lock. That is why it suits short updates of one variable.

Likely follow up: "How would you build an increment from CAS?" Read, add one, CAS, and retry on failure: a CAS loop.

2Corecas-loop
Write a CAS loop that atomically updates a value with any function, for example "add, but never above a cap".
Model answer

The pattern: read the current value, compute the new value from it, CAS from current to new; if the CAS fails, someone else changed the value, so read again and retry. The function must be pure, with no side effects, because it may run several times for one successful update. Java packages this loop as updateAndGet and accumulateAndGet.

The examples accept nonnegative deltas and avoid arithmetic overflow; a current value above the cap is clamped. The update loop is lock-free if its atomic primitive is lock-free and retries make system-wide progress. It is not wait-free: one thread can repeatedly lose. A weak CAS may also fail spuriously, so failure does not always prove another update.

Likely follow up: "Why must the function be free of side effects?" It can run several times per successful update, so a log line or an external call inside it would happen several times.

3Corecppcas
What is the difference between compare_exchange_weak and compare_exchange_strong?
Model answer

strong fails only when the current value differs from expected. weak may also fail spuriously, even when the values are equal. The standard allows that so machines with load-linked and store-conditional (ARM, POWER) can implement it as a single attempt with no hidden retry loop.

Both update expected on failure. C++20 compares value representations, not operator==: NaNs and signed zero can therefore behave differently from numeric equality.

  • Use weak inside a retry loop: a spurious failure only costs one more iteration, and weak can be cheaper on load-linked machines. On x86 the two compile to the same instruction.
  • Use strong for a single attempt whose result you act on, such as "try to become the leader once": a spurious failure would wrongly tell you that someone else won.

You can also give separate memory orders for success and failure, for example acq_rel on success and acquire on failure. The failure order cannot be release or acq_rel, because a failed CAS does not store.

Java's compareAndSet is the strong form; the weakCompareAndSet family (weakCompareAndSetPlain, weakCompareAndSetVolatile and others) is the weak one.

Likely follow up: "What bug does the updated expected cause?" Reusing expected for a second attempt without resetting it: after a failure it no longer holds the value you meant.

4Seniorlock-freestackRubrik
Implement a lock-free stack with CAS. What is safe in Java that is not safe in C++?
Model answer

The treiber stack: one atomic pointer to the top node. push builds a node pointing at the current top and CASes the top to it, retrying on failure. pop reads the top and CASes it to top.next. The linearization point of each operation is its successful CAS. Rubrik has asked for a thread-safe stack and then this lock-free version in the last minutes of the round.

Java is safe because of garbage collection: a node cannot be freed or reused while any thread still holds a reference to it, so reading cur.next() is always safe and a node's address cannot come back as a different node. With raw pointers in C++, pop reads cur->next while another thread may already have popped and deleted cur (use after free), and a freed address can be reused by a new push (ABA). Raw pointer versions need hazard pointers or epoch based reclamation. The C++ version uses the C++17-compatible atomic shared_ptr free functions, also available in C++20, because this Mac library lacks the C++20 specialization. It keeps nodes alive but makes no lock-free claim. Allocation and value operations also affect progress; if extraction throws after a successful pop, the node is already removed. Java rejects null values so null unambiguously means empty.

Likely follow up: "Where is the linearization point of pop on an empty stack?" The read of top that returned null.

5Senioraba
What is the ABA problem, and how do you prevent it?
Model answer

CAS checks only that the value equals expected, not that it never changed. In a lock-free stack:

That is the ABA problem. Fixes:

  • Version tags: pair the pointer with a counter that every update increments, and CAS both together. Java has AtomicStampedReference; in C++, a 16 byte CAS (cmpxchg16b on x86-64) or a counter packed into unused pointer bits.
  • Safe memory reclamation: never free or reuse a node while another thread may hold it, using hazard pointers, epoch-based reclamation, RCU or reference counting. In C++20 these require a library or a separate implementation; version tags alone do not make dereferencing freed nodes safe.
  • Garbage collection: GC prevents address-reuse ABA while a reference is live, but not explicit removal and reinsertion of the same mutable node. That requires a no-reinsertion rule or versioning. ABA on plain values remains possible: an int that goes 5, 6, 5 fools a CAS if your logic assumed "unchanged means nothing happened".

Likely follow up: "What does AtomicStampedReference cost?" Changing the reference or stamp can allocate a new pair object, increasing allocation and GC pressure. Finite stamps wrap, so bound reuse during an outstanding operation.

6Seniorprogress
Define blocking, obstruction-free, lock-free and wait-free.
Model answer

These are progress guarantees: what happens to everyone else when some threads are delayed (preempted, page faulting, or dead).

  • Blocking: one delayed thread can stop all others, because it holds a lock they need. Every mutex based design.
  • obstruction-free: any thread that runs alone, with the others paused, finishes in a bounded number of steps. Under contention, threads may keep undoing each other (livelock).
  • lock-free: if threads keep taking steps, operations continue completing system-wide. An individual thread can starve. No promise is made about wall-clock deadlines or progress when no thread is scheduled.
  • wait-free: every thread finishes in a bounded number of its own steps, whatever the others do. The strongest guarantee, and often slower in the common case. Do not infer a portable wait-free guarantee from one hardware instruction; C++ specifies whether an atomic is lock-free, not a per-thread completion bound.

The misconception to avoid: "lock-free" is a property, not "the code has no lock objects". A spinlock built from atomics is still blocking: if its holder is preempted, everyone spins. And lock-free is not faster by definition; its value is resilience to delays, which can matter in systems code. Hard real-time deadlines need stronger bounds, and signal handlers also require every operation, including allocation and reclamation, to be signal-safe.

Likely follow up: "Is ConcurrentHashMap lock-free?" Its reads are non-blocking, but updates lock a bin, so as a whole it is not. ConcurrentLinkedQueue is lock-free.

7Corejavacounters
AtomicLong or LongAdder: which do you use for a counter, and why?
Model answer

AtomicLong is one variable. Every increment is an atomic instruction on one cache line; with many cores incrementing at once, the line bounces between them and throughput collapses. In return, each read observes a linearizable value, which can become stale immediately and it supports compareAndSet, so it works for sequence numbers and CAS-based decisions. Handle overflow before relying on IDs being unique.

LongAdder (Java 8) keeps a base value plus an array of padded cells. Under contention, threads hash to different cells, so increments rarely collide; sum() adds the base and all cells. The costs: more memory, sum() is linear in the number of cells and is not an atomic snapshot (increments that happen during the sum may or may not be counted), and there is no compare-and-set.

  • Hot statistics written often and read rarely (hits, bytes, errors): LongAdder.
  • Ids, low contention, or when you must read the exact value to decide something: AtomicLong.

C++ has no LongAdder; build a striped counter: an array of cache line padded std::atomic<long> slots, each thread incrementing its own slot with relaxed ordering, and a read that sums them.

Likely follow up: "Can a rate limiter use LongAdder for its check?" No: the check needs an atomic read and decide, which LongAdder cannot give. Use a CAS loop on an AtomicLong, or a lock.

8Seniorcascontention
Under heavy contention, why can a CAS loop be slower than a lock?
Model answer

Every CAS attempt needs the cache line exclusively. With N cores retrying, each successful CAS invalidates the line in the other N minus 1 caches, whose CAS then fails and retries: potentially many wasted attempts and ownership transfers per success; the count depends on scheduling and hardware. A parking mutex can perform better by suspending waiters instead of having every thread retry; spin-based queued locks have different tradeoffs. Any expensive computation inside the CAS loop is also thrown away on every failure.

Mitigations:

  • For a plain increment, use fetch_add (getAndIncrement), not a CAS loop: on x86 it is one lock xadd, which always succeeds.
  • Exponential backoff after a failed CAS.
  • Stop sharing one location: striping, LongAdder, per-thread accumulation merged later.

Illustrative orders of magnitude are nanoseconds to tens of nanoseconds for an uncontended scalar CAS and tens to hundreds for cache-line transfers. CPU, topology and contention can shift these substantially; benchmark the target.

Lock-free trades blocking for retries. Under heavy write contention the real fix is to stop writing to one location.

Likely follow up: "So where do CAS loops shine?" Low to moderate contention, short updates, and readers that must never block.

9Seniorspinlock
Implement a spinlock. What is test-and-test-and-set, and why does it matter?
Model answer

Plain test-and-set loops on exchange(true) until it returns false. Every exchange is a write, so every spinning core keeps grabbing the cache line exclusively, flooding the interconnect and even slowing down the holder's release. test-and-test-and-set spins on an atomic load instead (each core reads its own shared copy, with no traffic) until the lock looks free, and only then tries the exchange.

Acquire on lock and release on unlock give the critical section the same visibility a mutex gives. Real spinlocks add a pause hint (Thread.onSpinWait(), _mm_pause) and backoff. Limitations: no fairness (a ticket lock fixes that), no owner tracking, and wasted CPU whenever the holder is preempted.

Likely follow up: "Would you use this in application code?" Only for tiny critical sections on dedicated cores; otherwise a mutex. Some implementations spin before parking, but this is not a portable guarantee. Use Java try and finally, or C++ std::lock_guard<SpinLock>, so exceptions release it.

10Seniorspinningblocking
When does spinning beat blocking?
Model answer

When both of these hold:

  • The expected wait is shorter than sleeping and waking, which can cost microseconds as an order of magnitude. A tens-to-hundreds-of-nanoseconds critical section may qualify, depending on contention and the scheduler.
  • The holder is actually running on another core, so there are no more runnable threads than cores, and the holder is not preempted. Many kernel spinlocks disable local preemption for this reason; kernel configuration and lock type matter.

For a user-space mutex on one runnable CPU, spinning usually wastes the time the holder needs to release it. Specialized interrupt-driven protocols are a different case.

That is why real locks use adaptive spinning: glibc's adaptive mutex type and HotSpot's monitors spin briefly before parking, and HotSpot adjusts how long based on whether spinning recently succeeded. Low latency systems (trading, packet processing) go to the other extreme on purpose: they pin threads to dedicated cores and busy poll, trading whole cores for microseconds of latency.

Likely follow up: "What goes wrong with spinning inside a virtual machine?" Lock holder preemption: the hypervisor deschedules the virtual CPU that holds the lock, and every spinner burns its entire slice. Paravirtualized spinlocks exist to address this.

11Corecppatomics
Is std::atomic<T> always lock-free?
Model answer

No. The primary std::atomic<T> template requires a trivially copyable, copy/move constructible and assignable, unqualified T, but when the hardware cannot update a T atomically (large structs, and sometimes 16 byte types without the right compiler flags), the library falls back to a hidden lock, often one from a table of locks indexed by address.

  • a.is_lock_free() checks at run time; std::atomic<T>::is_always_lock_free (C++17) checks at compile time.
  • Integers and pointers up to 8 bytes are lock-free on mainstream 64 bit platforms. std::atomic_flag is the only type guaranteed lock-free everywhere.
  • std::atomic<std::shared_ptr<T>> (C++20) is typically not lock-free.
  • std::atomic<double> gained fetch_add in C++20.
  • std::atomic_ref<T> (C++20) applies atomic operations to an ordinary object, which must be suitably aligned, while all accesses during the lifetime of any referencing atomic_ref use an atomic_ref; the object must outlive those references.

Why it matters: an algorithm called lock-free but built on a non-lock-free atomic is really blocking, and atomics that use locks are not safe to use from a signal handler.

Likely follow up: "And Java's AtomicLong?" Common JVMs use native atomic operations, but Java does not expose a portable is_lock_free query. Do not claim a formal wait-free bound for its methods.

12Seniorlock-freequeue
How does a lock-free queue (Michael and Scott) work, at a high level?
Model answer

A singly linked list with a dummy node, plus atomic head and tail pointers.

Enqueue: create a node, then loop: read tail and tail.next. If next is null, CAS tail.next from null to the new node; that CAS is the linearization point. Then try to CAS tail forward to the new node; it is fine if that second CAS fails. If next was not null, tail is lagging behind, so help: CAS tail forward to next, then retry.

Dequeue: read head, tail and head.next. If head == tail and next is null, the queue is empty. If head == tail but next is not null, help advance tail first. Revalidate that head is unchanged before acting on the snapshot. Otherwise read the value from next and CAS head to next; the old dummy becomes garbage and next becomes the new dummy.

The helping step is what makes it lock-free: a thread stalled between its two CASes cannot block anyone, because any other thread can finish its work for it.

Java's ConcurrentLinkedQueue is based on this algorithm, with optimizations. In C++ the hard part is not the CASes but memory reclamation of dequeued nodes (hazard pointers or epochs).

In an interview I explain the two CASes and the helping trick, and unless asked otherwise I implement a locked queue or a bounded single producer, single consumer ring buffer instead.

Likely follow up: "Is its size() cheap?" No: ConcurrentLinkedQueue.size() walks the list and is only approximate under concurrent updates.

13Senioratomicsdesign
How do you atomically update two related variables without a lock?
Model answer
  1. Pack them into one word: two 32 bit values in one AtomicLong or std::atomic<std::uint64_t>, and CAS the whole word. ReentrantReadWriteLock does this with its state: the high 16 bits count read holds and the low 16 bits count write holds.
  2. Swap an immutable holder: an AtomicReference to an immutable object containing both values, replaced with compareAndSet. One allocation per update; in C++ it needs memory reclamation or std::atomic<std::shared_ptr>.
  3. Double width CAS: a 16 byte compare-and-swap (cmpxchg16b on x86-64); std::atomic of a 16 byte struct may be lock-free with the right compiler flags, so check is_lock_free().
  4. Use a lock: often just as fast, and always simpler.

What does not work: two separate atomics updated one after the other. A reader can see the new first value with the old second one.

Likely follow up: "Why carry a version at all?" It detects changes between the snapshot and CAS, until the version wraps. This API checks a value at call time; callers needing an earlier version must pass the expected packed word, not just the value.

14Coreatomicsraces
Spot the bug: an AtomicInteger counts open connections, and the code does if (open.get() < MAX) open.incrementAndGet();. What happens under load?
Model answer

It is check-then-act on an atomic: each call is atomic, the pair is not. Many threads can read MAX - 1 at the same moment, all pass the check, and all increment, so the count overshoots MAX by up to the number of racing threads minus one. An atomic variable makes one operation atomic, never a sequence of them.

Fix it with a CAS loop that increments only while below the limit, or use the primitive that already does exactly this, a Semaphore(MAX) with tryAcquire() and a release() when the connection closes. In C++, a compare_exchange loop or std::counting_semaphore::try_acquire.

The same trap in other clothes: if (map.get(k) == null) map.put(k, v) on a ConcurrentHashMap, and x.set(x.get() + 1) on an AtomicInteger.

Likely follow up: "And the release side?" Decrement in a finally block when the connection closes, so a failure never leaks a slot.

15Stretchjavaatomics
Why does the JDK use VarHandle or AtomicIntegerFieldUpdater on plain fields instead of AtomicInteger fields in some classes?
Model answer

Memory and indirection. An AtomicInteger field is a separate object: often around 16 bytes total for the object with compressed headers, plus a 4 or 8 byte reference, depending on JVM layout and alignment, and every access chases a pointer. For classes with millions of instances, such as queue nodes, futures or buffers, that can double the memory and hurt cache locality.

A atomic field updater performs CAS on an embedded volatile field. A VarHandle can also target a plain field; its access mode supplies the ordering. The JDK's own concurrency classes do this: ConcurrentLinkedQueue nodes and FutureTask use VarHandles in OpenJDK 21. Do not generalize to every class: that version's AbstractQueuedSynchronizer still uses internal Unsafe operations.

The downsides: reflective setup, the field must be volatile for the updater classes, and the code is clumsier and easier to get wrong.

In application code I use the AtomicX classes unless a profile shows millions of instances; then I switch to a VarHandle on a field.

Likely follow up: "Is there a C++ equivalent problem?" No: a std::atomic<int> member is stored inline, with no extra object. std::atomic_ref (C++20) covers the opposite need, atomic operations on a plain field.

16Seniorlock-freejudgment
When would you not use a lock-free algorithm, even if one exists?
Model answer

Most of the time. The reasons:

  • Correctness is hard to argue: ABA, memory reclamation, memory orders. Interviewers will ask you to justify why it is thread-safe, and a reviewer has to verify it later.
  • It is often not faster: under low contention an uncontended lock costs about as much as a CAS, and under high contention CAS retries burn cache traffic.
  • Invariants across several variables need locks or very complex designs.
  • Waiting still needs blocking: a consumer waiting for an item must sleep somewhere, so lock-free queues still need a blocking layer.

When lock-free is the right call:

  • A single variable: counters, flags, state machines with CAS transitions. That is routine.
  • Proven library structures: ConcurrentLinkedQueue, the read path of ConcurrentHashMap.
  • Contexts forbidding blocking, provided the whole path meets the stricter constraints. Lock-free alone is neither a hard real-time bound nor permission to allocate inside a signal handler.
  • Measured lock contention, where a lock-free design has been validated with stress tests and model checking.
I start with a lock, measure, use library lock-free structures before writing my own, and write my own only with a proof I can explain.

Likely follow up: "Then why learn CAS at all?" Because it underpins many locks and concurrent structures, alongside primitives such as exchange and fetch-add; debugging them requires that model.
