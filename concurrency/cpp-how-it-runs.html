How C++ becomes a running program

Preprocess, compile, link, run: headers and the one definition rule, undefined behavior, and the flags that catch data races.

C++ never runs your source code. It runs what the compiler and linker built from it, after an optimizer that assumes you never break the language rules. Learn that pipeline and you will read a data race the way the compiler does: not as a slightly wrong number, but as a program with no meaning at all.

In plain words

Picture a big restaurant preparing a banquet. A clerk photocopies the shared recipe pages into each cook's folder. Each cook then works alone at their own station, from their own folder, never seeing the other stations. At the end the head chef assembles the banquet, matching every "use the sauce from station 3" with the actual sauce, and complains loudly if a dish is missing or was made twice.

That is C++: the preprocessor pastes headers into each source file, the compiler turns each file into machine code on its own, and the linker joins the pieces. The cooks are fast because they take every shortcut the rules allow, assuming the rules were followed. If you broke one, say two stations stirring the same pot at once, nobody promises what reaches the table. That promise-free zone is called undefined behavior.

Why this matters for concurrency

  • A data race is undefined behavior. The optimizer compiles each function as if no other thread can change a plain variable behind its back, so it may read a flag once and never again. You will watch that happen below.
  • Headers are pasted into every file that includes them. A mutex declared static in a header gives every source file its own private mutex, and the data it was meant to protect is not protected at all.
  • Threads and race detection are build settings: -pthread to build threaded code portably, -fsanitize=thread to find races. Every C++ sample on this site is compiled with ThreadSanitizer.
  • Rubrik's debugging round hands you threaded C++ and expects it compiling and running at the end; one 2025 new grad found the deadlock and then lost the round on a compile error. Toolchain fluency is part of the grade.

The four stages

When you type one build command, four things happen in order. Knowing which stage produced an error tells you where to look.

StageInputOutputTypical failure

CompileOne translation unitAn object file (main.o): machine code plus a table of names it defines and names it needsSyntax and type errors, template errors, warnings
LinkAll object files plus libraries (the C++ standard library, the thread library)An executable"undefined reference" (a name nobody defined), "duplicate symbol" (defined twice)

A translation unit is one .cpp file after preprocessing. The compiler handles each one alone: while compiling main.cpp it knows nothing about worker.cpp except what the included headers declared. With a modern standard library, #include <iostream> by itself preprocesses to tens of thousands of lines (an order of magnitude; run -E and count), which is why headers are worth understanding and not just copying.

Declarations, definitions and headers

A declaration says a name exists and what its type is. A definition creates the thing: the function body, the storage for the variable. A header holds declarations (and a few kinds of definitions that are allowed to repeat, below); a .cpp file holds the definitions. Here is the usual split for a small thread-safe class.

#pragma once (or a classic #ifndef COUNTER_H include guard) stops one translation unit from pasting the same header twice. It does nothing across translation units: every .cpp that includes counter.h gets its own pasted copy. That fact drives the next rule.

The one definition rule

The one definition rule says every function and variable your program uses must be defined exactly once in the whole program. Some entities may have definitions in several translation units: class definitions, templates, inline functions and inline variables. The definitions must satisfy the ODR requirements, including identical tokens and consistent name lookup; identical text alone is not enough. Internal-linkage entities in different translation units are separate entities.

There are two ways to break it. The lucky way: define an ordinary function or global variable in a header, include it from two files, and the linker stops with a duplicate symbol error. The unlucky way: two translation units see different definitions of the same class or inline function (built with different macros, say). No diagnostic is required, and the program has undefined behavior.

inline means "may be defined in many files"

inline sounds like an optimization request, but its real meaning today is about the one definition rule: an inline function or variable with external linkage may be defined in every translation unit that uses it, and valid definitions denote one entity with one address. Whether the optimizer actually pastes the body into callers is a separate decision it makes on its own.

  • Member functions defined inside the class body are implicitly inline. That is why header-only classes work.
  • constexpr functions, and static constexpr data members since C++17, are implicitly inline.
  • Templates have the same multiple-definition permission, which is why templates live in headers.
  • A static local variable inside an inline function with external linkage is still a single object for the whole program, not one per file.
  • C++17 inline variables let a header define one shared global: inline std::atomic<int> live_sessions{0};.

Undefined behavior

Undefined behavior means the standard places no requirements at all on what the program does. Not "you get some value", but anything: a wrong answer, a crash, an infinite loop, or the right answer until a compiler upgrade. Common sources: signed integer overflow, reading past the end of an array, using an object after it was destroyed, dereferencing a null pointer, reading an uninitialized variable, and data races.

The reason is the as-if rule. The compiler may transform your code in any way that keeps the observable behavior of a correct program, and it is allowed to assume your program is correct. Every optimization is a deduction from "this code has no undefined behavior", so when the assumption is false, the deductions are false too.

For threads the rule is blunt. If two threads access the same memory location, at least one of them writes, at least one access is not atomic, and neither access happens-before the other, that is a data race, and the behavior of the entire program is undefined. Not just the racing variable: the entire program.

Common mistakes

  • Defining an ordinary function or global in a header. Two files include it and the link fails with a duplicate symbol. Mark it inline, or move the definition into a .cpp.
  • static or unnamed-namespace mutexes and counters in headers. One copy per file, silently. Use an inline variable, or keep the state private to one .cpp.
  • Testing only at -O0. The flag loop above "works" there. Run the tests optimized and under ThreadSanitizer.
  • Ignoring warnings. With clang, -Wall flags std::unique_lock<std::mutex>(m);, which declares a new variable named m and locks nothing, and std::thread t(Worker());, which declares a function instead of starting a thread. Both are real interview slips.
  • Adding -fsanitize=thread to the compile step only. The link fails with missing sanitizer symbols. The flag goes on both.
  • Reasoning from hardware. "An aligned int write is atomic on x86, so the race is harmless." The compiler is not bound by x86; the race is undefined behavior before any CPU sees it.
  • Using volatile for a shared flag. In C++, volatile is for memory-mapped hardware, not threads. Use std::atomic.
  • Debugging a race with print statements. std::cout takes internal locks that add synchronization and can hide the very race you are chasing.

In the interview

Nobody asks "explain the linker". The pipeline shows up inside other questions: "is this thread-safe?", "what can this print?", "what happens if we compile with optimizations?". Microsoft has asked candidates to predict the output of a multithreaded C++ program and then find its issues (a 2024 report), and the honest answer to "what does a racy program print" starts with undefined behavior. Senior depth

Threads entered the language in C++11. Before that, the standard had no threads; POSIX rules and compiler goodwill filled the gap. Hans Boehm's 2005 paper "Threads Cannot Be Implemented as a Library" showed why that was unsound: a compiler could legally invent a write to a variable another thread was using. The C++11 memory model fixed it, and part of the fix is that a compiler may no longer introduce a data race that was not in your source.

"Memory location" is precise. Each scalar object is its own memory location, so two threads writing s.a and s.b of struct S { char a; char b; } do not race, even though they share a word and a cache line (they may still slow each other down through false sharing). The exception is bit-fields: adjacent non-zero-width bit-fields form one memory location, so two threads writing neighbouring bit-fields do race.

Link-time optimization (-flto) lets the optimizer inline across translation units, so a race that was hidden behind a function call in another file can start misbehaving after a build change. Undefined behavior is a property of the program, not of how it happens to be compiled today.

Under the hood

When you start the program, the loader maps the executable and its shared libraries (the C++ runtime, the C library), runs the constructors of global objects, then calls main. Creating a std::thread on Linux and macOS calls pthread_create, which asks the kernel for a new schedulable thread with its own stack. The full mapping is in how std::thread maps to the OS.

Key takeaways

  • Preprocess, compile each translation unit alone, link, run. Headers are pasted into every file that includes them.
  • The one definition rule: one definition per program, except classes, templates and inline functions and variables, which may repeat identically.
  • static at namespace scope in a header means one copy per file. A mutex declared that way protects nothing across files.
  • A data race is undefined behavior for the whole program. The optimizer may hoist, merge or remove accesses on the assumption that no race exists.
  • Build tests with -g -Wall -Wextra -pthread plus -fsanitize=thread (and separately ASan and UBSan), and run them optimized.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Thread A runs data = 42; ready = true; and thread B runs while (!ready) {} std::cout << data;. Both variables are plain globals (bool ready, int data), there is no other synchronization, and the program is built with -O2. What can happen?
Why. Both variables are raced on, so the program has no defined meaning. Concretely, the compiler may load ready once and spin forever, and the writes or reads may be reordered so B prints 0. "Always terminates" assumes undefined behavior is somehow bounded; it is not. The source order of A's writes guarantees nothing to B without a happens-before edge.
log.h contains static std::mutex log_mutex;. Both a.cpp and b.cpp include it, and both lock log_mutex before appending to one global std::string log_buffer defined in log.cpp. What is true?
Why. static at namespace scope gives internal linkage: each translation unit gets its own private log_mutex, so there is no link error and no mutual exclusion. Use inline std::mutex (C++17), or extern in the header with one definition in a .cpp, or hide the mutex inside log.cpp behind a function.
A header defines void log_line(const std::string& s) { /* body */ }, not inline and not a template. Two .cpp files include it. In a normal Clang build, what diagnostic would you expect?
Why. Each translation unit contains an external definition of log_line, which breaks the one definition rule, and a normal linker reports duplicate symbols. The C++ standard does not require a diagnostic for every cross-translation-unit ODR violation. Marking the function inline makes identical definitions legal, and then the linker does keep one. "Each file calls its own copy" is what static would do.
For a function with external linkage defined in a header, what does inline allow, assuming the definitions meet all ODR requirements?
Why. inline is an exemption from the one definition rule. Whether calls are actually inlined is the optimizer's separate decision. It says nothing about thread safety, and a static local in an inline function with external linkage is one object for the whole program.
Which statements about the sanitizers are true? Select all that apply.Select all that apply
Why. The sanitizer runtime is linked in, so the flag is needed at both steps. TSan checks the accesses that actually ran (it flags races even when the timing was lucky, but only on executed paths). TSan cannot be combined with ASan, so keep separate test builds. -Wall is compile-time warnings and does not detect races.
Two threads write, without any lock, to different members of one object: struct S { char a; char b; } s; Thread 1 writes s.a and thread 2 writes s.b. Is this a data race?
Why. Since C++11 every scalar object is its own memory location, and the compiler must not invent writes to neighbouring locations. Sharing a cache line can cost performance (false sharing) but not correctness. The exception is adjacent bit-fields, which form one memory location.
A colleague's flag loop on a plain bool "works" at -O0 and hangs at -O2. Which is the best explanation?
Why. The data race is the defect regardless of optimization level. Reusing a register value instead of reloading is one permitted consequence, not something the symptom alone proves. Cache coherence does not repair a C++ data race; use atomic accesses or synchronization and inspect the generated code if you need to explain this particular build.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer says: "This stop flag is a plain bool. It works on my machine, so the race is harmless." Answer them as you would out loud.
Model answer

It is not harmless, and "works on my machine" is the trap. Two threads access the flag, one writes, nothing orders them, and the variable is not atomic, so it is a data race, which in C++ is undefined behavior for the whole program. The compiler is allowed to assume no other thread changes a plain bool during the loop, so with optimizations it can load the flag once and spin forever; clang does exactly that to a simple spin loop at -O2. It may also reorder the flag with the data it is supposed to publish, so even when the loop exits, the data may not be visible yet. The fix is std::atomic<bool> (sequentially consistent by default, which also publishes earlier writes), or protecting the flag and the data with one mutex. Then I would exercise it with a ThreadSanitizer build and review the ordering argument. A clean sanitizer run is evidence for the paths exercised, not a proof of race freedom.

Debug
ThreadSanitizer reports a data race on a global counter. Both reported accesses show "(mutexes: write M0)" and "(mutexes: write M1)", and the code at both lines takes a std::lock_guard on something called stats_mutex. What is the most likely bug, and how do you fix it?
Model answer

Both accesses were locked, but with different mutexes, so the two locks never excluded each other. With a name like stats_mutex used in two files, the likely cause is a header that declares it static (or inside an unnamed namespace), which gives each translation unit its own private mutex. It links fine because the names are private. Fixes, from best: keep the mutex and the counter in one .cpp and expose functions like count_request(); or declare extern std::mutex stats_mutex; in the header and define it once; or in C++17 make it inline std::mutex stats_mutex;. After the fix, rerun under ThreadSanitizer and check the count is exact.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"My threaded program compiles each source file, but the final build says a counter method is undefined. Walk me through the build and where you would look."
What a strong answer covers
  • Successful per-file compilation followed by an undefined symbol points to linking, not a runtime threading failure
  • Preprocessing expands headers into translation units; compilation produces object files with definitions and unresolved references
  • A declaration permits compilation, but the linker still needs the matching definition
  • Check the definition, signature, namespace and whether its object file or library is linked
  • Include guards act within one translation unit; they neither supply missing definitions nor prevent cross-file duplication
  • Compile and link sanitizer builds with the sanitizer flag before exercising threaded paths
How a senior would say it
I would investigate the link step. Compiling a call proves that the compiler saw a suitable declaration; it does not prove that the program contains the method's definition. First, preprocessing expands each source file's includes and macros into a translation unit. The compiler turns each translation unit into an object file, recording both the symbols it defines and the symbols it still needs. The linker then combines those objects and libraries and resolves the references. For the missing counter method, I would check that its body exists, that its parameter types, const qualification and namespace match the declaration, and that the object file containing it is actually in the link command. An include guard cannot fix that. It prevents repeated inclusion within one translation unit, not missing definitions or duplicate definitions across different files. Once the program links, I would exercise the threaded paths in a sanitizer build. The ThreadSanitizer flag belongs on both compilation and linking so the instrumentation and runtime are present. A successful build gets me to runtime testing; it does not establish thread safety.

Likely follow up: What changes if the missing method belongs to a template whose definition is hidden in a source file?

Out loudabout 75 s
"A worker polls a plain boolean stop flag. It seems fine in debug builds and hangs when optimized. Would you blame the compiler or add volatile?"
What a strong answer covers
  • The unordered read and write of a plain flag form a data race and cause undefined behavior in C++
  • Optimization may reuse a loaded value or transform the loop; the symptom alone does not prove a specific transformation
  • C++ volatile supplies neither inter-thread synchronization nor atomicity
  • Use an atomic flag or one shared mutex; publishing associated data also needs an appropriate happens-before edge
  • Use ThreadSanitizer and optimized tests as evidence, not a proof that all races are absent
How a senior would say it
I would fix the data race first. The worker reads an ordinary boolean while another thread writes it, and there is no synchronization ordering those accesses. In C++, that makes the program's behavior undefined, including in the debug build that seemed to work. The optimizer may load the flag once and reuse the value, or transform the loop another way. The hang is consistent with that, but I would inspect the generated code before claiming a particular transformation happened. Adding volatile is not a thread-safety fix in C++; it supplies neither atomicity nor the ordering needed between these threads. I would use an atomic boolean, starting with its default sequentially consistent operations, or protect the state with one mutex. If the flag also publishes a result, I must ensure the reader observes the publishing store before reading that result, and that no later unsynchronized writes race with it. Finally, I would run ThreadSanitizer and optimized tests. They can expose failures on exercised paths, but a clean run is supporting evidence, not a proof covering every execution.

Likely follow up: If the flag only requests stopping and publishes no other data, could relaxed atomic operations be enough?

Out loudabout 75 s
"ThreadSanitizer says two counter updates race, but both lines hold a mutex named stats_mutex. The report names different mutex addresses. How would you explain that?"
What a strong answer covers
  • Matching source names do not imply the same mutex object; different addresses explain missing exclusion
  • A namespace-scope static mutex in a header has internal linkage and creates a separate object in each translation unit
  • One extern counter can therefore be updated concurrently while each thread holds its own mutex
  • Encapsulate the counter and mutex in one source file, or use an extern declaration and one definition
  • C++17 inline variables provide one shared object with external linkage; inline is not a request for guaranteed call substitution
  • Rerun the concurrent count check and ThreadSanitizer, and inspect all access paths
How a senior would say it
The two updates are holding different mutex objects. The same spelling in source code does not guarantee the same object in the running program. I would inspect the header for a namespace-scope static mutex or an unnamed namespace. That gives the mutex internal linkage, so each translation unit gets its own instance. If the counter is declared extern and defined once, both threads still reach one counter while holding different locks. Each lock works locally, but neither excludes the other update. My preferred repair is to put the counter and its mutex together in one source file and expose operations that always use that mutex. Alternatively, the header can declare the mutex extern and one source file can define it. In C++17, an inline variable with external linkage is another way to provide one shared object from a header. Here inline concerns definitions and identity; it does not promise that calls are substituted by the optimizer. I would then check every counter access, rerun the exact-total test concurrently, and run ThreadSanitizer again to look for remaining conflicting accesses.

Likely follow up: Why would adding an include guard to that header leave the original race unchanged?
