Fix the broken shutdown

Bug huntshard40 minRubrik

Rubrik interviewers grade exactly the parts a library would hide: what shutdown promises, who wakes the sleeping workers, and which exceptions a worker survives. Here the hand-built pool already exists, and it is broken in more than one way.

The incident

The ingest service runs every record through an in-house WorkerPool: a fixed set of threads taking tasks from one shared queue. Each deploy calls shutdown() and then exits. The documented contract:

  • submit(task) queues the task and returns true, or returns false once shutdown has started.
  • shutdown() stops taking new work, lets the workers finish every task already accepted, and returns once every worker thread has exited.

What the team has seen this month:

  • Deploys of quiet instances hang. shutdown() never returns, and the orchestrator kills the process when its grace period runs out.
  • On busy instances shutdown returns quickly, but the daily ingest count comes up short. Records whose submit returned true were never processed.
  • Last Tuesday one malformed record made a task throw. Within minutes that instance stopped processing anything, and its queue grew until a restart. The Java build had logged one stack trace per worker; the C++ build crashed outright.

Your job: find every bug and fix each with the smallest correct change. Keep the public API exactly as it is. As in the interview, no library thread pools or blocking queues.

What the tests check

  • 30 tasks on 3 workers all run.
  • shutdown() on a pool whose workers are all idle returns within 1 s.
  • With both workers busy in long tasks and 20 more queued, shutdown() waits for the running tasks, and all 20 queued tasks run before it returns.
  • After shutdown, submit returns false and the task never runs.
  • Four submitter threads race a shutdown: every task whose submit returned true has run by the time shutdown() returns.
  • Two tasks that throw do not stop the pool: the 10 tasks queued behind them run, and no worker dies. In C++ an exception that escapes a thread ends the process; the harness reports that as a failed test.
  • Every wait is timed, so a hang is a failed test, not a stuck run. In C++, ThreadSanitizer must stay quiet.

Taught in: An executor without libraries: submit, wait for all, shutdown and shutdownNow

Open them one at a time. Each one gives away a little more.

Walk one worker through three moments: shutdown arrives while it sleeps on an empty queue; shutdown arrives while it is busy and the queue still holds work; the task it runs throws. Where is the worker at each moment, and what wakes it or ends it?
A sleeping worker wakes only when someone signals the condition it sleeps on, and goes back to sleep if its wait condition still holds. Does shutdown() signal anything? Does the wait condition mention shutdown at all? And exactly when should a worker be allowed to leave its loop?
Changing the shutdown state and signalling must happen under the same lock the worker holds while it checks and goes to sleep, or the signal can fall into the gap between them. For the third symptom: what happens to a thread when code it runs throws and nothing catches it, in Java and in C++?

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Add shutdownNow(): stop at once and return the tasks that never started.
Add a second state, stopping, that makes workers exit without draining. Under the lock: set it, move every queued task into a list and clear the queue, then signal all. Outside the lock, interrupt the workers in Java so a task blocked in sleep or wait can stop, and join them. Removing the tasks under the same lock that workers take them with guarantees no task is both returned and run. C++ has no interruption, so running tasks stop only if they check a cancellation flag or a std::stop_token.
A task ends by restoring its interrupt flag with Thread.currentThread().interrupt(). What happens to the worker?
The flag stays set on the worker thread. The next time the queue is empty, await() throws InterruptedException at once, this worker treats that as "exit", and the pool silently loses a thread. Enough such tasks and the pool stops. ThreadPoolExecutor clears the interrupt status before each task unless the pool is stopping; do the same with Thread.interrupted() after each task, and keep interrupts for shutdownNow().
Why catch RuntimeException and not Throwable?
A Runnable can only throw unchecked exceptions: a RuntimeException or an Error. An Error such as OutOfMemoryError means the process may be in a bad state; ThreadPoolExecutor lets that worker die, reports the error and starts a replacement. Swallowing Throwable and carrying on hides fatal problems. In every case, never drop the exception silently: log it, count it, or deliver it through the task's future.
Add awaitTermination(timeout).
Split "start shutting down" from "wait". shutdown() only changes the state under the lock and signals all. Each worker, as it exits, decrements a live worker count under the lock and signals a "terminated" condition when it reaches zero. awaitTermination waits on that condition with a deadline (awaitNanos, or wait_until with a predicate) and returns false on timeout. In C++ join has no timeout, so the counter is what makes a timed wait possible; join the threads once it reaches zero.
The flag is volatile (atomic in C++). Is setting it and then calling signalAll or notify_all enough, without the lock?
In C++, no: a worker may have checked the predicate (not shut down) and be about to block when the store and the notify_all happen, so the wakeup is lost and the worker sleeps forever. The store must happen under the mutex. In Java signalAll must be called while holding the lock, which happens to close the gap, but write the state under the lock anyway: one rule, "change what waiters test only under their lock", is easier to defend than a special case.
How does the JDK's ThreadPoolExecutor handle the same three problems?
Its run state (RUNNING, SHUTDOWN, STOP, TIDYING, TERMINATED) lives in the high bits of one atomic int, ctl. shutdown() sets SHUTDOWN and interrupts idle workers so that they wake from the queue. A worker's getTask() returns null, ending the worker, only when the state is at least SHUTDOWN and the queue is empty, or at least STOP. A task's exception ends that worker, but the pool records it and starts a replacement worker, so capacity is not lost.

The three bugs

Each symptom in the incident is one bug, and each lives in the worker loop or in shutdown(). The tests catch them in this order.

Bug 1: idle workers never hear about shutdown

An idle worker sleeps on notEmpty inside while (queue.isEmpty()). shutdown() sets the flag and joins, but signals nothing, and even a woken worker would find the queue still empty and sleep again, because its wait condition never mentions shutdown. The only place that reads the flag is the top of the outer loop, between tasks, and a sleeping worker is not between tasks. This is a lost wakeup by omission: the state that a waiter needs changed, and no one told it.

Bug 2: busy workers leave with work still queued

while (!shutdown) ends the loop as soon as the flag is set, whatever is still in the queue. A busy worker finishes its current task, sees the flag, and exits. Once all workers have done that, join() returns and shutdown() reports success, while tasks that submit accepted sit in the queue forever. That is the short ingest count.

Bug 3: one exception kills a worker

task.run() (task() in C++) is not protected. In Java the exception ends the worker thread; the default handler prints a stack trace and the pool has one thread fewer, for good. When every worker has met a bad record, nothing runs at all, and shutdown() even "works", because joining a dead thread returns at once. In C++ an exception that escapes a thread's function calls std::terminate, and the whole process dies.

The fix

Why the flag must change under the lock

Making the flag atomic (C++) or volatile (Java) only makes the write visible. It does not stop the write from landing between a worker's check and its sleep. The mutex is what makes "check the condition, then sleep" one step from everyone else's point of view, so the state the waiters test must change under it.

The invariant that makes it correct

A worker exits only when the pool is shut down and the queue is empty, and both are checked under the one lock that submit also uses. submit checks the flag under that lock, so every accepted task is in the queue before the flag can change; workers drain the queue before they can exit; and shutdown() returns only after every worker has exited. So every accepted task has run by the time shutdown() returns. This is graceful shutdown, and it is what ThreadPoolExecutor does with its run states.

How to say it in the interview

There are three bugs. Idle workers sleep on "not empty" and nothing tells them about shutdown, so I set the flag under the queue lock, signal all, and make them wait for "work or shutdown". Busy workers check the flag before the queue, so they drop accepted tasks; a worker must leave only when the pool is shut down and the queue is empty. And a task's exception kills its worker in Java and the process in C++, so I catch around the task and keep the worker alive. The invariant is: every task that submit accepted runs before shutdown returns, because submit, the workers and shutdown all decide under one lock.
