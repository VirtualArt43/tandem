Signaling: condition variables, wait and notify

Busy waiting, condition variables and monitors, spurious and lost wakeups, notify versus notifyAll, Mesa versus Hoare, and waiting with timeouts.

Level

1Corecondition-variables
What is a condition variable, and why does it always come with a mutex?
Model answer

A condition variable lets a thread sleep until some condition over shared state becomes true, and lets another thread wake it after making the condition true. The condition itself ("the queue is not empty") lives in shared variables guarded by a mutex. The condition variable has internal waiting state, but stores no application predicate or notification credit.

The mutex is needed because checking the condition and going to sleep must be one atomic step. Otherwise: the consumer checks and sees an empty queue; the producer adds an item and notifies, but nobody is waiting yet; the consumer goes to sleep and never wakes. wait(lock) atomically releases the mutex and enqueues the thread, and reacquires the mutex before it returns. The notifier changes the state under the same mutex, then notifies.

Likely follow up: "In C++, can the producer set an atomic flag without the mutex and then notify?" Not with this protocol: the consumer can see false just before the notification and then sleep. Changing the state under the mutex closes that gap. Other carefully proved protocols exist; for a single atomic value, C++20 atomic waiting is often simpler.

2Corespurious-wakeupApple
Why must you call wait() inside a while loop and not an if?
Model answer

Because waking up does not mean the condition is true. Three ways it happens:

  • spurious wakeups: POSIX, Java and C++ all allow wait to return without any notify.
  • stolen wakeups: with Mesa semantics the notified thread must reacquire the lock before it runs, and in that gap another thread (a consumer that just arrived) can take the item. By the time the waiter runs, the queue is empty again.
  • Shared wait sets: with notifyAll, or one condition used for several predicates, a producer can be woken by a notification meant for consumers and find the buffer still full.

With if, the thread proceeds on a false condition: poll() returns null, front() on an empty std::queue is undefined behavior, or the buffer overflows its capacity. With while, it simply checks again and goes back to sleep. The C++ predicate overload, cv.wait(lk, pred), is literally while (!pred()) cv.wait(lk);.

A wakeup is a hint to check again, never a guarantee.

Likely follow up: "Why do implementations allow spurious wakeups at all?" The contract gives implementations room to handle internal races and wakeups efficiently. You need the loop even without spurious wakeups, because another consumer can steal the condition before you reacquire the lock.

3Corebusy-waitingApple
Why use wait() or a condition variable instead of looping until a flag changes?
Model answer

A busy waiting loop has four problems:

  • It burns a whole core doing nothing, which you pay for in power and, in the cloud, in money.
  • It steals CPU from the thread that would set the flag; on a single core or an oversubscribed machine that delays the very event it waits for until the spinner is preempted.
  • With a plain (non-volatile, non-atomic) flag, the compiler may hoist the read and the loop never ends.
  • Polling with sleep (while (!done) sleep(10)) trades CPU for latency: roughly one polling interval of added detection latency, potentially longer with scheduling delays. It still needs Java volatile, a C++ atomic or another synchronization protocol.

A parked waiter consumes no execution time while asleep. Notification makes it eligible to resume; scheduling and mutex reacquisition can delay it.

Spinning is right only when the expected wait is shorter than the cost of sleeping and waking (often microseconds as an order of magnitude), the thread you wait for is running on another core, and there are spare cores: spinlocks around tiny critical sections, or the brief spin a mutex does before it sleeps. Inside such loops, use Thread.onSpinWait() in Java or a pause instruction in C++.

Likely follow up: "What does onSpinWait actually do?" It is an optional performance hint; HotSpot commonly emits x86 PAUSE, which can reduce power and resource contention. It supplies no memory ordering or scheduling guarantee. C++20 has no portable equivalent CPU-pause instruction.

4Corejavanotify
notify() or notifyAll(): when is notify() safe?
Model answer

notify() wakes one arbitrary thread in the monitor's wait set; notifyAll() wakes all of them, and they then compete for the monitor and re-check their conditions. A sufficient rule for notify() safety is that both hold:

  1. Uniform waiters: every waiter waits for the same condition, so any one of them can use the notification (for example, only consumers wait, and any consumer can take any item).
  2. Enough notifications: each newly available unit of work gets a notification, or a proved handoff protocol wakes the next waiter. A state change enabling everyone, such as shutdown, usually needs broadcast.

A bounded buffer built on one monitor breaks rule 1: producers and consumers sleep in the same wait set. A consumer's notify() meant for a producer can wake another consumer instead, which finds an empty buffer and sleeps again; the notification is used up and, in the worst interleaving, every thread ends up waiting. This can hang without a lock cycle.

Two safe options: notifyAll() with every wait in a while loop, or separate conditions (notFull, notEmpty from one ReentrantLock), where signal() is safe because each condition's waiters are uniform. Broadcast can add unnecessary wakeups and lock contention.

I default to notifyAll; I use notify or signal only with uniform waiters, usually through separate conditions.

Likely follow up: "Can notifyAll ever break correctness?" It does not change the predicate or grant ownership. A correctly guarded loop remains safe, but broadcast does not fix missing state, broken cancellation or a wrong predicate.

5Corelost-wakeup
What is a lost wakeup, and how do you make sure it cannot happen?
Model answer

A notification sent when nobody is waiting is not remembered: condition variables have no memory, unlike a semaphore's permits. If the waiter decides to sleep based on state it checked without the lock, or the notifier changes the state without the lock, the notification can fall into the gap and the waiter sleeps forever. That is a lost wakeup.

The rules that make it impossible:

  1. The condition lives in shared variables, not in the notification.
  2. The waiter checks the condition and waits while holding the mutex that guards it.
  3. The notifier changes that state while holding the same mutex, then notifies.
  4. Every wait is in a loop.

Then a notify that comes before the wait is harmless: the waiter sees ready == true and never sleeps.

Likely follow up: "What if the event happens exactly once?" Use something with memory: a latch, a promise, or a semaphore starting at 0.

6Corejavamonitor
Why must wait() and notify() be called while holding the object's monitor?
Model answer

Java enforces it: calling either without holding that object's monitor throws IllegalMonitorStateException. The reason is the same race as the lost wakeup:

  • wait() must release the monitor as part of going to sleep, atomically with the check you just did under it. It can only release what you hold.
  • The standard monitor pattern changes the state and notifies under the monitor, so a waiter cannot be between "checked the condition" and "went to sleep" when the notification fires.

It must be the same object: inside synchronized (lock), calling wait() (meaning this.wait()) throws unless you also hold this. Write lock.wait().

And wait() releases only that one monitor. Any other monitors the thread holds stay held while it sleeps, which is how nested monitor lockout happens.

The same holds elsewhere: ReentrantLock conditions require ownership for await() and signal(); the generic Condition interface allows implementations with other documented rules, and std::condition_variable::wait requires a std::unique_lock that the calling thread has locked (otherwise the behavior is undefined).

Likely follow up: "Does notify() release the monitor?" No. The waiter cannot return from wait() until it reacquires the monitor after the notifier fully releases it, including every recursive hold.

7Seniormesahoare
What is the difference between Mesa and Hoare monitor semantics, and which do Java and C++ use?
Model answer

hoare semantics (Hoare, 1974): signal hands the monitor directly to the selected waiter; if the signaler established its predicate, the waiter resumes with it still true; the signaler waits until it gets the monitor back. A waiter could use if instead of while. The price is extra context switches and a harder implementation.

mesa semantics (from the Mesa language at Xerox PARC, described by Lampson and Redell in 1980): signal only moves the waiter to the ready queue. The signaler keeps running, and when the waiter eventually gets the lock, the state may have changed, so it must re-check: while, always.

Java, POSIX threads, C++ std::condition_variable, .NET and Python all use Mesa semantics. Consequences:

  • Every wait goes in a loop.
  • notifyAll and broadcast are natural and safe, as are timed waits.
  • The signaler may notify before it has finished updating the state, as long as it still holds the lock; no other thread can enter the protected monitor code until it releases.

Likely follow up: "Why did Mesa win?" It is simpler, needs fewer forced context switches, and tolerates broadcasts, timeouts and spurious wakeups, all of which Hoare semantics make awkward.

8Seniorcppcondition-variables
In C++, should you call notify_one() while holding the mutex or after releasing it?
Model answer

Both work with the usual protocol: change the predicate under the mutex and ensure the mutex and condition variable stay alive through every operation.

  • After unlocking: the woken thread does not immediately block on a mutex that is still held ("hurry up and wait"), so it is often slightly faster. Some implementations avoid that cost anyway by moving the waiter straight to the mutex's queue.
  • While holding it: simpler to reason about, and useful when the lifetime protocol otherwise permits destruction immediately after the waiter returns, for example when the waiting thread owns the object and deletes it after wait returns. Notifying after unlock could then touch a destroyed condition variable. Join participants or use explicit ownership; notification alone is not a complete lifetime protocol.

With the ordinary wait-loop protocol, changing the state outside the mutex and then notifying is insufficient: the waiter can check, see false, and sleep just after your notification.

Likely follow up: "When is notify_all required?" When a single wakeup cannot guarantee progress, such as heterogeneous predicates or a state change enabling several waiters (closing a queue, opening a latch).

9Coresemaphorescondition-variables
For signaling between threads, when do you use a condition variable and when a semaphore?
Model answer

A semaphore has memory: a release before the matching acquire is remembered as a permit. It counts identical events or resources and needs no extra lock from the caller. Its basic acquire condition is sufficient permits; Java can also acquire several permits at once.

A condition variable has no memory and must be paired with a mutex and a predicate. In exchange it can express any predicate over shared state (closed || size < capacity, "same team and fewer than 10 inside"), and you update state under the same lock. A shutdown predicate must let blocked callers wake and report closure.

So: counting identical things, use a semaphore. An arbitrary condition over several variables, use a mutex and a condition variable. A one-time event, use a latch or a promise. 10Seniorcondition-variablesjava
Why use two conditions (notFull and notEmpty) instead of one?
Model answer

With a single wait set, a notification may wake the wrong kind of thread, so you are forced into notifyAll, which wakes every waiter: many awakened threads may contend and return to sleep; the exact scheduling cost depends on the implementation. With two conditions, producers wait only on notFull and consumers only on notEmpty; a take signals exactly one producer and a put exactly one consumer. signal() becomes safe because the waiters on each condition are uniform.

synchronized cannot do this: a monitor has exactly one wait set. You need ReentrantLock.newCondition(), twice, on the same lock. That is precisely how ArrayBlockingQueue is written.

In C++ the same design is one std::mutex with two std::condition_variables, and notify_one on the matching one.

Likely follow up: "How does LinkedBlockingQueue go further?" It uses two locks, one for the head and one for the tail, plus an atomic count, so a producer and a consumer can work at the same time.

11Seniorinterruptionjava
A thread waiting in wait() is notified and interrupted at almost the same moment. Can the notification be lost?
Model answer

Not solely because of interruption. JLS 17.2.4 says a thread both notified and interrupted may either return normally from wait (with its interrupt still pending) or throw InterruptedException; and if it throws, the notification must not be consumed solely by an interrupted waiter while another eligible waiter remains. If every waiter is interrupted, all may throw. Condition.await has the same contract in its Javadoc: an implementation that favors the interrupt must redirect the signal to another waiting thread, if there is one.

This matters with notify() and signal(), which select one existing waiter when there is one: a lost wakeup could leave an item queued beside a sleeping consumer.

Your code still has a part to play:

  • Re-check the predicate in a loop after every wakeup.
  • If the thread leaves because of the interrupt, make sure it has not already consumed state it will not process, such as removing an item and then throwing before handling it.
  • Restore or propagate the interrupt rather than swallowing it.

C++ has no Java-style thread interruption, but the analogous edge is a timed wait that expires at the moment it is notified. The predicate overloads of wait_for and wait_until return the predicate's value, so a true final predicate allows progress even if the deadline has passed. The wait itself does not remove the item or guarantee a hard return deadline.

Likely follow up: "Does any of this matter with notifyAll?" Much less, because every waiter wakes and re-checks.

12Seniormonitordeadlock
What is nested monitor lockout?
Model answer

A thread calls wait() on an inner monitor while still holding an outer lock. wait() releases only the monitor it is called on, so the outer lock stays held while the thread sleeps. The thread that would make the condition true needs that outer lock first, so it blocks, and the sleeper is never woken: a nested monitor lockout.

In C++ the same thing happens when a thread holds mutex A and calls cv.wait(lock_on_B): only B is released.

Why it is nasty: there need not be a cycle consisting solely of lock ownership. One thread is waiting for a condition, the other is blocked on a lock, so lock cycle detectors (such as the "Found one Java-level deadlock" section of a thread dump) report nothing. The dump shows the producer WAITING on the buffer while it still "locked" the pipeline, and consumers BLOCKED on the pipeline.

Fixes: never wait while holding another lock; let one lock guard the state and all of its conditions; or release the outer lock before calling into a component that may block (an open call).

Likely follow up: "How would you design Pipeline correctly?" Drop synchronized from it entirely and let the thread-safe buffer do all the waiting.

13Stretchcppcondition-variables
What are std::condition_variable_any and C++20 std::atomic::wait, and when would you use them?
Model answer

std::condition_variable requires std::unique_lock<std::mutex>. condition_variable_any accepts other types satisfying the locking requirements, such as std::shared_lock. C++20 adds predicate waits with std::stop_token; they return the final predicate value, which may still be true when stop is requested. Extra internal synchronization is implementation-dependent.

C++20 atomic::wait(old) waits until a load observes a value different from old. The library handles comparison and waiter registration without your own mutex. It may use futexes or other internal primitives; no particular kernel mapping is guaranteed. Spurious internal wakeups do not by themselves make it return.

The store changes state; notification wakes blocked waiters. Prior payload writes become visible when the acquire wait observes the release store. A notification without a value change does not make wait(false) return, and a store without notification may leave an already blocked waiter asleep.

Likely follow up: "Can it miss a change?" Yes: an A to B to A transition may go unobserved, the ABA problem. Use a generation counter when transitions matter, with an explicit wraparound policy. Java has no direct atomic-value wait API; use a higher-level synchronizer or a carefully designed LockSupport protocol.

14Stretchjavalock-support
How do LockSupport.park() and unpark() work, and why is an early unpark not lost?
Model answer

Each thread has one binary permit. unpark(t) makes t's permit available; permits do not accumulate beyond one. park() consumes the permit and returns immediately if it is available; otherwise it blocks until unpark, an interrupt, or a spurious return.

So an unpark that arrives before the park is remembered, unlike notify. But only one: two early unpark calls provide only one permit; a second park may block, though interruption or a spurious return can still release it. And because park may return spuriously, you always loop on a real condition.

No lock is involved, which is why park and unpark are the foundation of AbstractQueuedSynchronizer (and so of ReentrantLock, Semaphore, CountDownLatch, FutureTask) and are adapted for virtual threads. Passing a blocker object, as in park(this), makes thread dumps show "parking to wait for" that object.

Likely follow up: "What happens on interrupt?" park returns without throwing and without clearing the interrupt flag, so the loop must handle it or repeatedly returning park() calls become a busy loop. Safely register the waiter, avoid intervening parks that consume its permit, and do not rely on unpark of an unstarted thread.

15Seniortimeouts
How do you wait on a condition with a timeout correctly?
Model answer

Compute a deadline once and loop against it. Define whether the budget includes initial lock acquisition; these fragments budget the condition wait after acquiring the lock. Because a wait can end early (spurious or stolen wakeups), waiting the full timeout again on each iteration can stretch the total wait far beyond what was asked. Use a monotonic clock (System.nanoTime, std::chrono::steady_clock); wall clock time can jump with NTP adjustments.

awaitNanos also returns an estimate of the remaining time; recomputing elapsed time accounts for work between waits. Initial lock acquisition needs its own timed API if it belongs in the budget. The C++ predicate overload of wait_until loops internally and returns the predicate's final value. Decide by the condition, not by "did it time out": the condition may have become true at the deadline.

Likely follow up: "And with plain wait(ms)?" Recompute remaining time and use wait(millis, nanos) without rounding a positive sub-millisecond remainder down to wait(0), which waits indefinitely. Reacquiring the monitor can exceed the deadline.
