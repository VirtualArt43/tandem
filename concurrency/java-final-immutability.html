final, immutability and records

What final does and does not freeze, how to build truly immutable classes and records, and why immutable objects are thread-safe for free.

Before this:Classes, interfaces and inheritance

An object that never changes cannot be raced on. Immutability is the cheapest thread safety there is: no locks, no atomics, no contention. Java's final keyword and records take you most of the way, provided you know exactly what they freeze and what they leave open.

In plain words

Compare a printed railway timetable with a whiteboard in the station office. Any number of people can read the printed timetable at once, forever, without asking anyone or waiting their turn. The whiteboard needs a rule about who writes when, and readers may catch it half erased.

final is like laminating one line of the timetable. The line can never change. But if that line says "see the whiteboard in room 4 for platforms", the whiteboard can still change, so the timetable is not really fixed. To make the whole timetable trustworthy, every line has to be laminated and no line may point to a whiteboard. That is the difference between a final field and an immutable object.

Why this matters for concurrency

  • Immutable objects need no synchronization to read. Share them across any number of threads, cache them, use them as map keys and pass them through queues as messages.
  • final fields carry a special memory model guarantee: once the constructor finishes, every thread that sees the object sees its final fields correctly, even if the object was handed over through a data race. Non-final fields get no such promise.
  • Many concurrent designs are "build a new immutable object, then swap one reference": configuration reloads, copy-on-write lists, snapshots, and atomic updates with AtomicReference.
  • Lambdas may capture only effectively final locals, which is Java's way of stopping you from sharing a stack variable between threads.
  • Interview staples: "How do you make a class immutable?", "Is a final List immutable?", "Why are immutable objects thread-safe?", "unmodifiableList versus List.copyOf?".

What final means, in four places

Local variable or parameterfinal int limit = 10;Assigned at most once; definitely assigned before it is read

Classfinal class MoneyNobody can extend it

For a field, the compiler enforces "definitely assigned exactly once": forget it in one constructor, or assign it in a method, and the code does not compile. That compile-time check is the first half of the value of final. The second half, the cross-thread guarantee, comes later in this lesson.

final freezes the reference, not the object

A final field or variable of an object type always points to the same object. The object itself can change freely:

So private final List<String> items = new ArrayList<>(); in a shared class is still shared mutable state. final stops anyone from swapping the list; it does nothing about two threads calling add on it at once. final is about the variable; immutability is about the object.

Effectively final

A local variable or parameter that is never reassigned after it is initialized is effectively final, even without the keyword. Lambdas, anonymous classes and local classes may capture only such variables:

The reason is threads. A lambda copies the values it captures into the lambda object, because the lambda may run later, on another thread, after the method that created it has returned and its stack frame is gone. If count could keep changing, the copy and the variable would disagree, and "fixing" that by sharing the stack variable would let two threads race on a local. Java forbids both. You will see the full rules in lambdas and functional interfaces.

Immutable objects are thread-safe for free

An immutable object has state that cannot change after its constructor finishes. Concurrent reads of properly initialized, unchanging state need no locking. String, Integer, BigDecimal, LocalDate and Instant are immutable. List.of(...) fixes the list's contents, but its elements must also be immutable if you want the whole object graph to be unchanging.

The recipe for your own classes:

  1. Do not allow subclasses: make the class final (or give it only private constructors and static factories), so nobody can add mutable state or override behavior.
  2. Make every field private final.
  3. Provide no method that changes state. "Changing" returns a new object instead.
  4. Copy mutable inputs and never hand out mutable internals: store List.copyOf(items), return immutable views or copies.
  5. Do not let this escape the constructor.

Any number of threads can call id(), items() and withItem() on a shared Order at once, with no lock: none of them writes to it. The cost is allocation: each change builds a new object, which is usually cheap next to the locks and bugs it saves.

The final field guarantee, a preview

Here is the property that makes final special in the memory model. Suppose thread A builds an object and stores the reference in a plain shared field, and thread B reads that field with no synchronization. That is a racy publication. For ordinary fields, the compiler or the CPU may let B see the reference before the constructor's writes, so B can read the fields as 0 or null. For final fields, the final field semantics promise that once the constructor has finished, any thread that sees the reference sees the correct values of the final fields, and of whatever they referred to at the end of the constructor.

Three limits to remember. The guarantee holds only if this did not escape during construction. It covers what the final fields pointed to as of the end of the constructor, not later changes to those objects. And it says nothing about whether B sees the reference at all: B may still read null for a long time. To make the reference itself visible you still need safe publication through a volatile field, a lock, a concurrent collection or a thread start. The full story is in safe publication, immutability and final fields.

Records

A record (Java 16) is a class for plain data. One line declares the components, and Java generates private final fields, a canonical constructor, accessor methods named after the components, and equals, hashCode and toString based on all components. Records are implicitly final and cannot declare extra instance fields, so most of the immutability recipe comes for free.

Most, not all. A record's fields are final references, so a record is only shallowly immutable: a List component can still be changed by whoever else holds that list. Fix it with a compact constructor, which runs before the fields are assigned and may replace the parameters:

Records with immutable components make excellent messages between threads, map keys (their equals and hashCode are generated from the components, as the next lesson explains) and snapshot values. One caution: an array component is compared by identity in the generated equals, so two records holding equal arrays are not equal. Prefer List components.

Unmodifiable is not immutable

Collections.unmodifiableList(list) does not copy anything. It returns an unmodifiable view, a wrapper that throws on writes but reads straight through to list. Whoever still holds list can change it, and the view shows the change:

Worse for threads: if one thread reads through the view while another writes base, that is a data race on an ArrayList. A view is safe to share only if nobody writes the original after it is published.

What you holdCan you change it?Can it change under you?Safe to share between threads?
new ArrayList<>(...)YesYesNo

The table describes list structure, not the thread safety of the elements. List.of and List.copyOf reject null elements, and List.copyOf may reuse a suitable unmodifiable list, which is safe because its structure cannot change. Given an unmodifiable view of mutable backing storage, it must isolate the result from later structural changes. An unmodifiable list is only as immutable as its elements: List.of(new StringBuilder()) still holds a mutable object.

Defensive copies

A defensive copy is a copy you make so that nobody else holds a reference to your internal state. Make one when you receive a mutable object and when you hand one out. The order matters: copy first, then validate the copy. If you validate the caller's object and then copy it, another thread holding that object can change it between your check and your copy, which is a check then act race across threads.

Better still, use immutable types and the problem disappears: Instant and Duration instead of Date and long[], List.copyOf instead of a raw ArrayList. Immutable inputs need no defensive copy at all.

Changing immutable state: replace, do not mutate

Real programs do change: configuration reloads, statistics grow, caches update. The immutable way is to build a new object and swap one reference. Readers simply read the current reference and get a complete, consistent object; they never see half an update.

For a single writer, a volatile reference to an immutable object is enough. With several writers, each change is a read-modify-write of the reference, so use AtomicReference.updateAndGet, which retries until it swaps in a new object built from the latest one:

Every reader of stats.get() sees a pair of counts that existed together at some instant, which two separate AtomicLongs cannot promise. Under contention updateAndGet may call withHit more than once before its compare-and-set succeeds; that is harmless precisely because withHit has no side effects. This replace-the-whole-thing style is the heart of copy-on-write and immutable snapshots. (For a pure counter, a LongAdder would be faster; the point here is the pattern.)

Worked example: make this class immutable

A routing service shares Route objects between request threads and a background updater:

Every rule is broken somewhere:

  • setName mutates a shared object, so readers can see the change at any point, or never.
  • The constructor stores the caller's list, and getStops() returns it: both sides hold an alias to the same mutable list.
  • Date is mutable: getUpdated().setTime(0) changes the route from outside.
  • No field is final and the class is not final, so there is no final field guarantee and subclasses can add state.

The updater now builds a new Route and publishes it, for example through a ConcurrentHashMap<String, Route> or a volatile field; request threads read whichever Route they get and can use it for as long as they like. No lock is needed to read the immutable Route itself, and no reader sees a partly updated Route. The publication mechanism may use synchronization internally.

Common mistakes

  • "The field is final, so it is immutable." A final reference to an ArrayList is still a shared mutable list.
  • "I wrapped it in unmodifiableList, so it is a snapshot." A view shows later changes to the original, and racing with them is a data race.
  • Forgetting the compact constructor in a record with a collection component. The record is then only as immutable as the caller's list.
  • Validating before copying. Another thread can change the original between the check and the copy. Copy first.
  • Returning internal arrays or Date objects from getters. Return copies, or switch to an unmodifiable list of immutable elements and immutable time values such as Instant.
  • Leaking this from the constructor of an "immutable" class. The final field guarantee no longer applies, and other threads can see default values.
  • Assuming immutability makes the reference visible. The object's state is safe, but another thread may still not see the new reference without safe publication.

In the interview

"How do you make a class immutable?" is a standard Java screen question, and immutability is the strongest move in many concurrency designs: a configuration that reloads, a snapshot for readers, messages between stages of a pipeline. Name the rules, then name the memory model benefit.

Final class, private final fields, no setters, defensive copies in and out, and no this escape from the constructor. Then the object can be shared across threads with no locking, and because the fields are final, the memory model guarantees other threads see them fully initialized once the constructor finishes. I still publish the reference safely, through a volatile field, a concurrent collection or a queue.
Collections.unmodifiableList is a read-only view: the owner can still change the list underneath. For a real snapshot I use List.copyOf, which gives an independent unmodifiable copy.

Follow ups to expect: "Is a record immutable?" (shallowly; copy mutable components in a compact constructor), "What if one field must change?" (return a new object, and swap references with AtomicReference.updateAndGet if several threads update), "What exactly does final guarantee across threads?" (correct values of final fields after the constructor, if this did not escape), and "Why is String immutable?" (so one string can be shared freely between threads and through the string pool, its hash code can be cached, and a value checked for security, such as a file path, cannot change after the check).

Senior depth

  • String caches its hash in a non-final field. hashCode() computes the hash on first use and stores it in a plain int with no synchronization. Two threads may both compute it and both write it, which is a deliberate, harmless data race: every thread computes the same value, and an int write cannot tear. This "racy single-check" idiom works only for values that are cheap to recompute, never torn, and identical every time.
  • Reflection can break final. Where access rules permit it, Field.set after enabling access can change some ordinary final instance fields after construction, and threads may not see the change. Enabling access alone does not mutate a field, and record component fields cannot be changed this way. Treat finals as frozen.
  • Iteration order of Set.of and Map.of is unspecified and in practice changes from run to run. Never let a concurrent algorithm, a test, or a lock ordering depend on it.
  • Immutability shifts cost to allocation. Replacing a large object on every small change can be expensive. Persistent data structures share most of their structure between versions; in the JDK, CopyOnWriteArrayList is the simple version that pays a full copy per write, which is right only when reads vastly outnumber writes.

Under the hood

HotSpot implements the final field guarantee with a store barrier at the end of any constructor that wrote a final field: the constructor's stores must become visible before any later store, such as the one that publishes the reference. On x86, stores are never reordered with other stores, so the barrier costs no instruction at all. On ARM it is a real barrier instruction. Readers need nothing extra on the CPUs Java runs on today, because a load through a reference cannot run ahead of the load of the reference itself.

Key takeaways

  • final freezes a variable's reference, not the object it points to.
  • Immutable objects have no writes after construction, so they are thread-safe without locks.
  • The recipe: final class, private final fields, no mutators, defensive copies, no this escape.
  • Final fields are seen correctly by every thread once the constructor finishes; the reference itself still needs safe publication.
  • Records are shallowly immutable: copy mutable components in a compact constructor.
  • Collections.unmodifiableList is a view; List.copyOf is a snapshot.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Explain to an interviewer why immutable objects are thread-safe, and the one thing you still have to get right when sharing one between threads.
Model answer

Every data race needs a write to shared state that some other access can conflict with. Once immutable state is properly initialized, any number of threads can read it without locking. That is why String, Integer and unmodifiable lists of immutable values are useful for messages between threads and snapshots for readers. An unmodifiable list alone does not make its elements immutable.

What I still have to get right is publication: the other thread must see the reference. If I store it in a plain field with no synchronization, the reader may see null, or an old object, indefinitely. If the class has only final fields and does not leak this, the memory model at least guarantees that whoever sees the reference sees fully initialized fields; but to make the hand-off itself visible I publish through a volatile field or AtomicReference, a lock, a concurrent collection, a BlockingQueue, or before starting the thread. Then the only concurrency question left is who swaps the reference.

Write code
Make this class immutable and safe to share between threads: public class Booking { private String guest; private List<String> rooms; private Date checkIn; public Booking(String guest, List<String> rooms, Date checkIn) { this.guest = guest; this.rooms = rooms; this.checkIn = checkIn; } public List<String> getRooms() { return rooms; } public Date getCheckIn() { return checkIn; } public void addRoom(String r) { rooms.add(r); } }
Model answer

The record makes the class final with private final fields and no setters. The compact constructor copies the caller's list, so no alias survives, and rooms() returns an unmodifiable list. Date is mutable, so it is replaced by Instant. addRoom becomes withRoom, which builds a new object; code that shares bookings swaps references, for example with map.put on a ConcurrentHashMap or AtomicReference.updateAndGet.

Design
A service reloads its feature-flag configuration from a file every 30 seconds, and 200 request threads read several flags on every request. Design the in-memory side so that reads take no lock and no request ever sees half of a reload.
Model answer

I would make the configuration an immutable object, for example a record holding a Map.copyOf of the flags plus a version number. The holder keeps one volatile reference to the current config (or an AtomicReference). The reloader thread reads and parses the file into a brand new config object off to the side, validates it, and only then publishes it with a single write to the volatile field. If parsing fails, it keeps the old config and logs.

Request threads call current() once at the start of the request and keep the result in a local variable, so all flags they read come from one consistent version, even if a reload happens mid-request. Reads are a single volatile read with no lock and no contention; the volatile write and read give the happens-before edge, and the final fields of the immutable config guarantee its contents are complete. Old configs are simply garbage collected when no request holds them. If there were several writers that each change part of the config, I would use AtomicReference.updateAndGet with a side-effect-free function that builds the next version from the current one.

Out loudabout 75 s
"We pass a record containing a list of strings between worker threads. A teammate says its final fields make it immutable. Would you approve that?"
What a strong answer covers
  • A record's final component field fixes the reference, not the list's contents
  • The caller or an accessor can expose the same mutable list to other threads
  • Use List.copyOf in the compact constructor to retain an unmodifiable snapshot
  • Copying the list does not copy its elements; strings are immutable but mutable elements need their own policy
  • Build the snapshot from stable input and publish the completed record safely
How a senior would say it
I would approve it only after checking the list's ownership. A record makes its component fields final, but that freezes the references, not the objects they refer to. If the constructor stores an ArrayList supplied by the caller, the caller can still add an element, and the generated accessor exposes that same list. Passing the record through a queue does not freeze it. For a list of strings, I would use List.copyOf in the compact constructor. That gives the record an unmodifiable snapshot of the membership, and strings themselves are immutable. Wrapping the original with an unmodifiable view would not be enough, because changes through the original list still show through. Copying the list also does not copy its elements: if they were mutable jobs, I would need immutable job values or defensive copies of those too. The input must be stable while I copy it. Finally, I would publish the completed record through a queue, a volatile reference or another safe handoff. Immutability protects the snapshot; publication delivers it.

Likely follow up: How would your design change if the record held a byte array instead of strings?

Out loudabout 90 s
"One background thread reloads configuration while two hundred request threads read several flags per request. Design this so readers never see half a reload."
What a strong answer covers
  • Build and validate a complete immutable configuration before publishing it
  • Use one volatile reference for the current configuration with a single reloader
  • Each request captures that reference once and reads every flag from that snapshot
  • Keep the old snapshot if validation fails; existing requests can finish using it
  • For multiple writers deriving updates from current state, use a lock or an atomic reference update with a side-effect-free function
  • State the allocation cost and the fact that volatile does not make a read-modify-write atomic
How a senior would say it
I would publish whole immutable snapshots through one volatile reference. The reloader parses the file into a new configuration, copies any mutable collections and validates the complete result before assigning that reference. A bad reload leaves the old configuration in service. Each request reads the current reference once into a local variable and uses that object for every flag lookup. That last detail matters: reading the shared reference again for each flag could combine values from different versions. A request already holding the old object can finish with it while later requests use the new one. No request needs to lock the configuration, because neither version changes after construction. The volatile handoff makes the new snapshot and its initialized state visible. With one reloader, a simple replacement is enough. If several writers derive changes from the current configuration, plain read, build and write can lose an update. I would then serialize updates with a lock or use an atomic reference update whose function has no side effects, because it may be retried. The cost is allocating new snapshots and temporarily retaining old ones. I would choose this when reads dominate and the configuration is small enough that copying remains reasonable.

Likely follow up: Why can a request still observe mixed versions if the shared reference is volatile but it reads that reference twice?

Out loudabout 75 s
"If final fields are visible across threads, why do you still publish immutable objects through volatile fields or queues? Explain the difference."
What a strong answer covers
  • Final-field semantics protect initialization of properly constructed objects, not delivery of the shared reference
  • Construction must finish without exposing this to the reader early
  • A reader that obtains the properly constructed object sees its initialized final fields
  • A plain shared reference can remain null or stale; volatile or another handoff supplies publication ordering
  • The guarantee does not synchronize later mutations of objects reached through final references
How a senior would say it
Final fields protect initialization; they do not deliver a new reference to another thread. If I construct an object without letting it escape and assign its final limit field to ten, a reader that obtains that properly constructed object gets ten for that field. This special guarantee can hold even when the reference was published through a plain field. But that reader is not guaranteed to discover the reference at all. It may keep seeing null or an older object. I still use a volatile reference, a queue or another synchronization mechanism to establish the handoff. Construction also matters: if I register a callback from the constructor and it runs before the limit is assigned, final does not prevent that callback from observing the default value. Finally, a final reference to a list does not make later list changes visible or safe. The initialization guarantee covers the state reached through that reference at construction, not arbitrary future mutations. I separate the two questions: is this snapshot fully built, and how does another thread receive it?

Likely follow up: Does replacing a volatile immutable snapshot with a modified copy remain safe when two writers do it concurrently?
