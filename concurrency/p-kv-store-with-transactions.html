Key value store with nested transactions, then many threads

Thread-safe designshard50 minRippling coding rounds, 2023 to 2025Rippling

One of Rippling's most reused coding questions, reported from 2023 to 2025. The nested transactions are graded on running code; the follow up that separates senior candidates is "now two threads update the same key". In one 2024 report the interviewer had the candidate reproduce exactly that race, then fix it.

The task

Part 1: one thread

  • set(key, value), get(key) and remove(key) work on string keys and integer values. get of a missing key returns nothing (null in Java, std::nullopt in C++). The method is remove because delete is a C++ keyword.
  • begin() opens a transaction. Transactions nest: calling begin() inside one opens a child.
  • Inside a transaction, set and remove are buffered. This thread's own get sees them at once; nobody else sees them.
  • commit() closes the innermost transaction. If it has a parent, its changes merge into the parent and stay private. If it is the outermost, all its changes become visible to everyone at once. It returns false when no transaction is open.
  • rollback() throws away the innermost transaction's changes and returns true, or returns false when none is open.

Part 2: many threads

  • Every thread has its own transactions. Another thread's open transaction is invisible to you, and you cannot commit or roll it back: your commit() only sees your own.
  • Outside a transaction, each set and remove is applied at once, like a one-key commit.
  • The conflict policy is optimistic, first committer wins. An outermost commit() fails, returns false and discards the whole transaction if any key this transaction read or wrote was changed by another commit after this transaction first touched that key. The caller retries. No call ever blocks waiting for another thread's transaction.

In the interview you pick a policy and say which. This problem picks for you, because the other common answer, last committer wins, silently loses exactly the update Rippling's follow up is about. The follow ups below compare the options.

Example on two threads. c starts at 0. Thread A: begin(), reads 0, set("c", 1). Thread B: begin(), reads 0, set("c", 1). A commits: true, and everyone sees 1. B commits: false, because c changed after B read it, so B's transaction is gone. B retries, reads 1, writes 2, commits: true. No increment was lost.

What the tests check

  • Plain set, get and remove; commit and rollback with nothing open return false.
  • The nested sequence above, a remove inside a transaction then rolled back and then committed, and an inner commit that disappears when its parent rolls back.
  • Isolation, driven step by step on two threads: uncommitted writes are invisible to the other thread and to the main thread, each thread reads its own writes, and the second committer of a key it shares fails.
  • A lost update caught at commit, and the retry that succeeds.
  • A transaction belongs to its thread: another thread's commit and rollback return false and leave it alone.
  • Stress: 8 threads increment one key in transactions with retry; the final count must be exact.
  • Stress: 6 threads move money between 4 accounts in transactions while 2 auditors sum all 4 inside read-only transactions. Every audit that commits must see the exact total, no balance may go negative, and the final total is unchanged.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Machine coding rounds: thread-safe designs end to end

Open them one at a time. Each one gives away a little more.

Get one thread right first. Keep a stack of layers, each a map. A write goes into the top layer; a read looks through the layers from the top down, then falls back to the committed store. A remove needs a marker in the layer (a tombstone), because "deleted in this transaction" is different from "not mentioned in this transaction". Commit of a child merges its layer into the parent's.
Each thread needs its own stack. In Java, make it a thread-local storage field (ThreadLocal.withInitial). In C++, thread_local cannot be a non-static member, so keep a map from std::this_thread::get_id() to that thread's transaction, guarded by the store's mutex.
For conflicts, give every key a version number that goes up on each committed change. The first time a transaction reads or writes a key, remember the version it saw. At the outermost commit, under the store lock, check that every remembered version is still current; if so, apply all the writes and bump their versions inside that same lock, and if not, discard everything and return false.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why not last committer wins? It is simpler.
It is simpler, and acceptable if you say it out loud: commit just applies the buffered writes under the lock. But any read-modify-write inside a transaction then loses updates: two threads read 0 and both write 1, which is the lost update Rippling asked about. It also cannot keep invariants that span keys, like a total across accounts. Use it only when transactions are blind writes.
Could you use locks instead, so commits never fail?
Yes: lock each key the first time a transaction touches it and hold every lock until commit or rollback (two-phase locking, the pessimistic choice). Commits always succeed, but transactions now block each other, and two transactions that touch the same two keys in opposite orders deadlock. Since keys are discovered as the code runs, you cannot pre-sort them, so you need lock timeouts or a wait-for graph. Optimistic wins when conflicts are rare; locking wins when they are frequent and retries are expensive.
Under heavy writes, read-only transactions keep failing. How would you fix that?
Give each transaction a snapshot. Keep several versions of each key (MVCC) and let a transaction read the newest version committed before it began; a read-only transaction then never conflicts and never blocks a writer. Postgres works this way. The cost is keeping old versions and cleaning them up once no open transaction can see them.
Is your store serializable?
Yes. Commit validates every key the transaction read, under the same lock that applies the writes, so each committed transaction's reads were still current at its commit point, and the result equals running the transactions one at a time in commit order. If you validated only the keys written (snapshot isolation), write skew would be possible: two transactions each read keys x and y and each write a different one.
The store is used from a thread pool. What breaks?
Thread-local transactions outlive the task. A task that throws before committing leaves its transaction open, and the next task on that thread silently runs inside it. Real client libraries avoid this with explicit handles (Txn t = store.begin(); t.set(...); t.commit();), with try-with-resources or RAII rolling back anything not committed. Say this if the interviewer asks how you would productionise it.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Three ideas stack up. Layers give nesting: each begin pushes a map, reads search from the top, a remove writes a tombstone, and a child's commit merges into its parent. Per-thread state gives isolation: buffered writes live only in the calling thread's stack, so nobody else can see them. Versions plus validation give safe concurrency: a transaction remembers the version of every key it touched, and the outermost commit, under the store lock, applies its writes only if all of those versions are unchanged. That is optimistic concurrency control with first committer wins.

The rest of the design

  • Version numbers are never reused. They come from one global commit counter, and a removed key keeps its entry. If each key counted from zero again after a remove, a later write could bring back the same version number with a different value, and a transaction that read the old value would pass validation.
  • The version is recorded on first touch, read or write, under the lock, together with the value read, so the two always belong to the same committed state.
  • Validation and apply happen under one lock acquisition. Check, unlock, then apply would reopen the same race one level up.
  • A failed commit discards the whole transaction, so a retry starts clean with begin(). A nested rollback keeps the versions its keys recorded; that can only cause an extra conflict, never a missed one.
  • Java keeps the stack in a ThreadLocal and touches the shared maps only inside synchronized (lock). C++ keys a map by std::this_thread::get_id() and does everything under one std::mutex, which is simpler and still correct.

Why the auditors prove commits are atomic

An auditor reads the four accounts inside a transaction and commits. If that commit succeeds, none of the four versions changed between the auditor's reads and its commit, so all four values belong to one committed state, and since every transfer keeps the total, the sum must be exact. A store that applied a commit key by key, or that let one thread see another's uncommitted writes, shows up as an auditor that committed with the wrong total.

Cost and trade-offs

A read or write is O(depth) in the layers plus one short lock acquisition the first time a key is touched. A commit is O(keys touched) under the store lock. All of that is in memory, so the global lock is held for microseconds; to go further, stripe the store by key and lock the stripes a commit touches in a fixed order. Under heavy contention on one key, optimistic retries waste work; that is the moment to argue for per-key locking.

How to say it in the interview

For nesting I keep a stack of layers per transaction, with tombstones for deletes, and a child commit merges into its parent. For threads, each thread has its own stack, so uncommitted writes are private. For conflicts I use optimistic concurrency: every key carries a version, a transaction remembers the version of each key it touches, and the outermost commit, under one lock, applies its writes only if none of those versions moved; otherwise it returns false and the caller retries. That makes read-modify-write safe, which last committer wins is not, and it is serializable because I validate reads as well as writes.
