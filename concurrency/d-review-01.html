Code review set 1: locks, flags and lifecycles

Ten code reviews in your language: find every real problem in a class that claims to be thread safe.

Amazon's online assessment has shown a mutex guarded, C style C++ container that claims thread safe indexed access and asked candidates to pick every problem (deadlock, leak, corruption); Microsoft has asked candidates to find the issues in a snippet "assuming that there is multithreading involved", and Rubrik runs whole debugging rounds on broken concurrent code. Each question here is one class of 20 to 60 lines in your language. Several options are usually right and some wrong options are things that look wrong but are fine, so judge every option on its own. Every snippet compiles; the key failures (self deadlock, the reentrant ConcurrentModificationException, the busy loop) were reproduced by running them.

10 questions, 25 minutes. Answers and explanations stay hidden until you submit or the clock runs out. Multi answer questions say so; pick every option that is true.

C++ onlyThe author says this is "a thread safe growable int array". Which statements are true? Select all that apply. Select all that apply
Why. std::mutex is not recursive, so set() calling resize() while holding m_ violates the locking precondition; a self deadlock is a common manifestation. The early return -1 in get() leaks ownership. Another thread cannot acquire that mutex while the owner never unlocks it; the owner attempting to lock it again instead violates the same non recursive precondition. resize() also overwrites data_ without freeing the old allocation, and no destructor frees the last one. For valid indices, successful allocations and arithmetic without overflow, the intended invariant is size_ <= cap_, so the copy length itself is not an extra bounds bug. Both public operations use the same mutex. Use std::vector<int>, RAII guards and a resize helper that assumes the lock is already held; also validate indices and allocation limits.

Java onlystart() and stop() are called from a controller thread. Which statements are true? Select all that apply. Select all that apply
Why. The plain running flag has no happens before edge from stop() to the worker, so continued reads of true are allowed. A volatile boolean is enough for this single stop flag; it cannot tear, and compare and set is unnecessary. An interrupt alone is not a reliable stop request here: sleep clears the status when it throws, the catch ignores it, and the loop never checks interrupt status. Restore the flag and exit on interruption, or use an interrupt-aware loop with a matching catch policy. A second start() overwrites the stored reference to the first thread, so this object loses its handle for joining it. Finally, stop() does not join either worker, so returning from it does not establish that pinging has ended.
C++ onlystart() and stop() are called from a controller thread. Which statements are true? Select all that apply. Select all that apply
Why. A plain bool shared between threads with a writer is a data race, and a data race is undefined behaviour, whatever the loop contains; in C++ volatile does not create synchronization, and "a function call forces a reload" is an observation about one compiler, not a guarantee. Use std::atomic<bool>. stop() never joins, so the defaulted destructor destroys a joinable std::thread and the program terminates; assigning a new thread over a joinable one terminates too. The clean C++20 version is a std::jthread member whose lambda takes a std::stop_token and waits on a std::condition_variable_any with that token, so a stop request ends the sleep at once and the destructor joins.

Why. open() writes the volatile flag, then calls notifyAll() without owning lock, so it throws IllegalMonitorStateException and sends no notification. Parked waiters may remain blocked; a spurious wakeup can still let one see the now true flag and return. Put the flag update and notification inside synchronized (lock). The timed overload returns true even after timing out with the gate closed; it needs a predicate loop, a deadline and a result reflecting open. Java onlyAbout 200 request threads call onEvent; four writers drain the queue. Which statements are true? Select all that apply. Select all that apply
Why. Four writers taking about 20 ms per insert can drain roughly 200 events per second, assuming independent inserts. The default LinkedBlockingQueue capacity is Integer.MAX_VALUE, so it is practically huge, not infinite. Sustained excess input builds backlog and latency and may exhaust memory before reaching that capacity. If the queue does reach capacity, offer() returns false; onEvent() ignores the result and therefore loses that event without reporting it. Configure a useful capacity and choose blocking, a timeout or explicit rejection, then handle the outcome. The queue itself supports concurrent producers. shutdownNow() interrupts workers, but this loop catches and ignores the interrupt, so it does not implement cancellation. On InterruptedException, restore the flag and return instead of calling take() again.
C++ onlyAbout 200 request threads call on_event; four writers drain the queue. Which statements are true? Select all that apply. Select all that apply
Why. There is no configured queue capacity or overload policy, so producers that get the mutex ahead of the writers can build a large backlog. Mutex contention does slow producers, but it is not a deliberate capacity limit. lk stays held through db_insert, so only one writer inserts at a time and producers cannot enqueue during that insert. Release the lock after popping and before calling the database. Once stopping_ is true, writers return even if items remain queued, so destruction abandons those items. A draining shutdown should return only when stopping and empty, and must reject new producers or ensure they have stopped before destruction. The predicate update is protected by the mutex before notification, and the destructor releases that mutex before joining, so neither of the proposed notification or join deadlocks follows from this code.
Java onlyA pool of Fetcher workers is stopped with the shutdown code below. Which statements are true? Select all that apply. Select all that apply
Why. shutdownNow() interrupts the workers but cannot force them to exit. BlockingQueue.take() is interruptible: it throws InterruptedException and clears the status, after which (1) immediately waits again. The backoff sleep also clears the status when it throws, and (2) merely logs and continues retrying. Restoring the flag while keeping continue is another bug: the next take() throws immediately, producing a busy loop. A probe repeated that immediate failure ten times. Restore the flag and return to implement cancellation. If ordinary non daemon pool workers stay in this loop, the termination wait can return false on timeout and those workers keep the JVM alive. This rule is specific to interruptible calls; not every blocking operation in java.util.concurrent throws on interruption.

Why. A fixed pool creates workers as tasks arrive, up to eight here. If f.get() throws before shutdown(), the created workers are left alive; they may still be rendering and then wait idle, keeping the JVM alive. The leak is up to eight workers per failed call, not necessarily eight for a report with fewer parts. Other submitted tasks are not cancelled automatically. C++ onlybuild is called once per report request. Which statements are true? Select all that apply. Select all that apply
Why. The loop attempts one thread creation per part with no configured concurrency limit. Some workers may finish before later ones start, and resource exhaustion may prevent all creations. If creation throws after earlier threads were added, unwinding destroys joinable std::thread objects and calls std::terminate; a finished thread remains joinable until joined. If render() itself throws out of a worker, that also terminates the process, as the probe confirmed. Use a bounded executor for a concurrency limit and catch worker failures into futures or std::exception_ptr. If using direct threads, std::jthread gives joining during unwinding but does not transport exceptions or cap concurrency. Each worker writes a different element of a vector that is not resized, so those writes do not race. On the normal path, joins complete before the referenced vectors go out of scope.

C++ onlyMany request threads call Pricing::get().price(sku). Which statements are true? Select all that apply. Select all that apply
Why. The first read of plain instance_ is outside the mutex while construction writes it under that mutex, so it is a data race and the whole program has undefined behaviour. It is not limited to seeing partially initialized fields. Release stores and acquire loads on an atomic pointer fix publication when the locked second check is retained; a function local static is simpler and has synchronized initialization.
