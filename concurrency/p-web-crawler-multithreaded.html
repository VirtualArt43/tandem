Multithreaded web crawler

Concurrent systemshard60 minLeetCode 1242, extended with a depth limit, several start URLs, a per host limit and failing fetchesDatabricksRubrik

Databricks asks it as "crawl from a start page, now limit the depth, now make it fast with threads". Rubrik asks it with thread pools and blocking queues banned. Arcesium added politeness: at most 5 fetches on one host at a time. All of them grade the same things: where your critical sections are, how the workers know the crawl is over, and whether your answer stays correct and busy once fetches finish in random order.

The task

Write a crawler that starts from one or more start URLs and returns every page on their hosts that is at most maxDepth links away. Fetching a page is slow (it is a network call), so you fetch many pages at once with up to threads threads, but never more than maxPerHost at once on any one host.

  • HtmlParser.getUrls(url) fetches one page and returns the URLs it links to. It is given to you, it takes tens of milliseconds, and it is safe to call from many threads at once. It can fail: in Java it throws a RuntimeException, in C++ an exception derived from std::exception.
  • The host of http://news.example.com/a/b is news.example.com: the text between http:// and the next /. The allowed hosts are the hosts of the start URLs. Only follow links whose host equals one of them exactly.
  • The depth of a start URL is 0. The depth of any other URL is the fewest links you must follow from the nearest start URL to reach it. Return every URL on an allowed host with depth at most maxDepth; maxDepth of -1 means no limit.
  • Crawling a page means calling getUrls on it. Every URL you return must be fetched exactly once, and you must not fetch anything you do not return. Pages at depth maxDepth are fetched, but their links are not followed. A start URL listed twice is still crawled once.
  • If getUrls throws, the page still counts as crawled: return it, treat it as a page with no links, and carry on. The crawl must still finish.
  • The order of the returned list does not matter. One crawler may run several crawls, one after another.

Rules, as in the real interview: no library thread pools, executors, futures or blocking queues. Start your own threads and coordinate them with a lock and condition variables (ReentrantLock and Condition, or synchronized with wait and notifyAll, in Java; std::mutex and std::condition_variable in C++).

  • Never run more than threads fetches at the same time, and never more than maxPerHost on one host.
  • Keep the threads busy: when pages are waiting and both limits allow another fetch, start it. In particular, a thread must not sit blocked behind a full host while a page on another host could be fetched, and a thread whose page is done must not wait for the other pages of its batch before taking the next one.
  • Never spin or poll while waiting. Idle threads sleep on a condition until something they need changes, and so does the thread that waits for the crawl to end.
  • Stop every thread you start: in Java join them before crawl returns, in C++ at the latest when the crawler is destroyed.

Worked example

Say http://docs.example.com/start links to a and b on the same host, a links to x, b links to c, c links to x, and x links to y. With maxDepth 3 the answer is start, a, b, c, x and y: x is at depth 2 through a, so y is at depth 3. If a is slow and b and c are fast, a crawler running ahead may reach x first through b and c, at what looks like depth 3, and wrongly stop there. The tests check exactly this, and the same trap with two start URLs: a page three fast links from one start but one slow link from the other has depth 1.

What the tests check

  • A full crawl of a 63 page site with cycles, self links, repeated links and links to other hosts: the exact URL set, every page fetched exactly once, and no page on another host fetched, including hosts like news.example.com.evil.org and sports.news.example.com that share letters with the real host.
  • Depth limits of 0 and 2: the exact set, each page fetched once.
  • The trap from the worked example: a depth limit must use the shortest path, even when a longer path is discovered first.
  • Two start URLs on two hosts, one of them listed twice, with a depth limit of 3: depth counts from the nearest start URL, the repeated start is fetched once, and links to a third host are skipped.
  • Real parallelism: with 24 pages ready and 6 threads, exactly 6 fetches must run together within 1 s, never more.
  • The per host limit: 8 threads and a limit of 5 on one host must run exactly 5 fetches at once, never 6.
  • The per host limit across hosts: 8 threads, a limit of 5, and a level that lists 20 pages of one host before 4 of another. Within 1 s, 8 fetches must run together (5 on the first host, 3 on the second), never more than 5 on a host. A thread that takes the next page and then blocks until its host has room fails this.
  • Threads stay busy around slow pages: one level of 14 pages, 4 threads, a slow page first and last and 12 quick pages between. Each slow page lasts until all 12 quick pages are fetched, so the other threads must fetch them meanwhile. Starting a page whenever a thread is free finishes in about 150 ms; waiting for a whole batch of 4 before starting the next, or giving each thread a fixed share of the level, leaves a slow page waiting 1 s and fails.
  • 1200 pages on four hosts that link to each other, fetched with no delay by 16 threads with a limit of 3 per host: the exact set, each page once, never more than 3 on a host.
  • A chain of 400 fast pages, one per level: the hand over between levels must never lose the links of the page that finished last, and must be prompt: the whole chain in under 1 s, which a thread that checks every few milliseconds whether the level is over cannot do.
  • With one thread the crawl is still correct and never overlaps two fetches.
  • One crawler runs three crawls in a row: the same crawl twice, then a crawl of another host whose pages link back to the first one. All three are exact: nothing from an earlier crawl (the URLs seen, the allowed hosts) leaks into a later one.
  • Many short crawls: 40 crawls of one instant page with 16 threads each, so the crawl is over while most workers are still starting. Each returns the one page, fetched once. In Java the thread that fetched it must have ended when crawl returns; in C++ a stop flag read outside the lock shows up here as a ThreadSanitizer report.
  • No threads are left behind: in Java none of the threads the crawl started is alive at the moment crawl returns (telling them to stop without joining them fails); in C++ none is alive 1 s after the crawler is destroyed.
  • No busy waiting: a chain of 3 pages of 150 ms (7 of 8 threads idle), then 3 pages of 120 ms on a host with a limit of 1. The crawl must use under 60 percent of one core, and the idle threads must sleep instead of polling. Java counts how often the crawl's threads go to sleep: at most 300 times in all and 40 in any one thread, which includes the thread that waits for the crawl to end. C++ counts context switches while the slow pages are fetched (at most 400), and in a separate crawl of one second where both threads are always fetching, so that only the thread waiting for the end is idle (at most 90). Waiting on a condition passes easily, and so does a timed wait of 50 ms used as a safety net; a loop that sleeps or waits for only a few milliseconds at a time fails, even in a single thread.
  • A failing fetch: two pages throw, with two different exception types (in Java an IllegalStateException and an UncheckedIOException, in C++ a std::runtime_error and a plain std::exception), on a crawler with 2 threads and a limit of 2 per host. The crawl must return within 3 s, return both pages, and never fetch the pages that only they link to. A failure that ends its worker, keeps its host slot or skips the count leaves nothing to fetch the rest, so the crawl hangs and fails (in C++ an exception that escapes a worker ends the program).
  • In C++, ThreadSanitizer must stay quiet.

Taught in: The multithreaded web crawler

Open them one at a time. Each one gives away a little more.

Split the work in two. Fetching is slow and can happen in parallel without any lock. Deciding what to fetch next (is this URL new? is it on an allowed host? how deep is it? does its host have room?) is fast and touches shared state. Keep the slow part outside the lock and the shared decisions in one place.
The depth trap breaks the classic "free running" crawler, where each worker pushes new URLs as soon as it finds them. Crawl one level at a time instead: hand a whole level to the workers, wait until every page in it is fetched, then build the next level from the new links. That is breadth first search, and breadth first search from all start URLs at once sees every URL first at its shortest depth.
One lock and two conditions are enough. Workers wait on "there is a page I may fetch, or we are stopping". The coordinating thread hands out a level, sets unfinished to its size, and waits on "unfinished is zero". Each worker takes a URL under the lock, fetches it without the lock, then takes the lock again to add the links it found and decrement unfinished, signalling at zero. At the end, set a stopping flag, wake everyone, and join the workers.
For the per host limit, keep a count of running fetches per host under the same lock. A worker looking for work takes the first waiting URL whose host is below the limit and skips full hosts; it never waits on one particular host. Free the host's slot and decrement unfinished on every path, including when getUrls throws: put the fetch in a try and do the bookkeeping after it.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why crawl level by level? What does it cost, and what is the alternative?
Level by level gives exact shortest depths for free, but each level waits for its slowest page, so one slow page idles every other thread (the straggler problem). The free running alternative keeps every thread busy: keep a map from URL to the best depth seen so far, cache each page's links once fetched, and when a URL turns up at a smaller depth than recorded, lower its depth and re-expand its cached links without fetching it again. Without a depth limit, the free running crawler is simply better.
How do you know multithreading will help here at all?
The work is I/O bound: a thread spends almost all of a fetch waiting on the network, not using the CPU. With 50 ms per page, one thread manages about 20 pages a second; 20 threads manage about 400, until the bottleneck moves to bandwidth, the remote server, or parsing. If the work were CPU bound, more threads than cores would not help.
Without a depth limit, how does a free running crawler know it is finished?
Keep a counter of URLs that are queued or being fetched. Increment it when you enqueue a URL; decrement it after a worker has fetched a page and enqueued that page's new links. Because the children are counted before the parent is uncounted, the counter only reaches zero when there is truly nothing left; then wake every waiter so the workers exit. Checking "queue empty" alone is wrong: the queue is briefly empty while a worker is still fetching a page that will add more.
Why not a semaphore per host?
A semaphore per host is the textbook politeness tool, but the natural way to use it, take the next URL and then acquire its host's semaphore, parks the thread on a full host while pages on other hosts wait. That is head of line blocking, and with many hosts it can leave most threads idle. Either use tryAcquire and pick a different URL when it fails, or keep the per host counts under the crawler's own lock and only take a URL whose host has room, as the reference does. Arcesium asked for at most 100 threads overall and 5 per host.
How many threads would you use?
For I/O bound work, roughly cores times (1 + wait time / compute time), which for a crawler is large. In practice the limit is politeness: a site may allow only a few concurrent requests, which is the per host limit here. Real crawlers add a rate limit per host (requests per second, not just concurrent requests) and retries with backoff.
What if getUrls hangs instead of throwing?
Throwing is handled by doing the bookkeeping on every path: a worker that dies, or skips the decrement, leaves unfinished above zero or a host slot taken forever, and the crawl hangs. A hang inside getUrls is worse, because the thread never comes back: give every fetch a timeout (an HTTP client timeout, or a deadline the fetch checks), count a timed out page as a dead end, and if you cannot interrupt the call, at least stop waiting for it and replace the stuck thread.
What if the fetch is asynchronous: fetchAsync(url, callback) returns at once and calls the callback later on one of the library's threads?
Then you need no worker threads at all. Under one lock, keep a count of outstanding requests, the per host counts and the queue of waiting URLs. To start a fetch, take a slot and call fetchAsync. In the callback, take the lock, record the links, free the slot, decrement the count, start whatever fetches the limits now allow, and signal the waiting caller when the count reaches zero. Three traps: never block inside a callback (it runs on the library's I/O thread and stalls every other request), never call fetchAsync while holding your lock if the library might run the callback on the same thread before returning (a non reentrant lock then deadlocks), and make failures arrive as a callback too, so the count still reaches zero. Google has asked this kind of follow up: switch to an async API that calls back on another thread.
How would this scale to billions of pages on many machines?
Partition the URL space by host hash so each host is owned by one machine: deduplication and politeness then stay local. The frontier becomes a persistent queue per partition, the visited set a disk backed store (often with a Bloom filter in front), and links to other partitions are sent to their owners.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Separate fetching from deciding. Fetching is slow, independent and parallel; it needs no lock. Deciding which URLs are new, how deep they are and whether their host has room is fast and shared; it belongs to one place. The reference solution keeps the visited set inside the calling thread, which acts as a coordinator, and runs a small fixed set of workers that only fetch. The crawl goes level by level, starting from every start URL at once: the coordinator hands a level to the workers, sleeps until the level is done, and builds the next level from the links they found.

Invariants

  • A URL enters seen once, at the moment it is placed in a level, so it is fetched exactly once. Start URLs go through seen too, so a repeated start is crawled once.
  • Levels are built in breadth first order from all start URLs together, so the level a URL is first placed in is its distance from the nearest start. The depth limit is therefore exact.
  • unfinished equals the number of URLs in the current level that are not fetched yet. It reaches zero exactly once per level, and only then does the coordinator move on.
  • running[host] equals the number of fetches in flight on that host, and never exceeds maxPerHost: a worker increments it when it takes a URL and decrements it after the fetch, on every path.

Why each primitive

  • One lock guards the waiting URLs, the per host counts, the list of found links and unfinished. It is held for microseconds; getUrls is always called outside it, which is what makes the fetches overlap.
  • Two conditions, because two different kinds of thread wait for two different things: workers for "a page I may fetch, or stop", the coordinator for "level done". Each wait is in a loop (the C++ predicate form is the loop).
  • signalAll for new work, since a whole level arrives at once and many workers can use it; a single signal for "level done", since only the coordinator waits on it.
  • No signal when a host slot frees up. The worker that freed it goes straight back to look for work under the lock, so it uses the slot itself if any waiting URL can. Every worker is interchangeable, so if it finds nothing, no sleeping worker could either. Signalling anyway would also be correct, just noisier.
  • Skip, never wait on, a full host. Taking the first URL whose host has room keeps the threads busy on other hosts; this is what the "across hosts" test checks.
  • A try around getUrls, bookkeeping after it. A failed page is a dead end, but its slot and its count must still be released, or the crawl hangs.
  • A stopping flag and join end the workers cleanly. In C++ this sits in a destructor, so the threads are joined even if the crawl throws.
  • The visited set needs no lock because only the coordinator touches it. That is confinement, the cheapest kind of thread safety.

Cost

Each page is fetched once and each link is examined once: O(pages + links) work, with wall time close to the sum over levels of (pages in the level / threads) times the fetch latency, or (pages on the busiest host / maxPerHost) when the per host limit binds. Taking a URL scans the waiting list for a host with room, which is cheap with a handful of hosts; with thousands, keep one queue per host plus a queue of hosts that have room. The price of level by level is the straggler effect described in the follow ups.

Pitfalls

  • Marking a URL visited after fetching it instead of when queueing it: two workers find it at once and both fetch it.
  • if (!seen.contains(u)) seen.add(u) on a concurrent set: a check then act race. Use the boolean that add (or insert(...).second) returns, which is one atomic step.
  • Calling getUrls while holding the lock: correct, but every fetch is serialized and the threads are useless.
  • Ending when the queue is empty: a worker may still be fetching a page that adds more.
  • Decrementing unfinished and signalling in one critical section, then adding the links in a second one: the coordinator can wake in between and build the next level without them. The long chain test catches it.
  • Checking the host with startsWith: news.example.com.evil.org passes.
  • A free running crawler with a depth tag: correct without a limit, wrong with one (the worked example). Crawling the start URLs one after another with a shared visited set falls into the same trap.
  • Taking a URL and then blocking until its host has room: head of line blocking, threads idle while other hosts wait.
  • Fetching a level in batches of threads pages and joining each batch before the next, or giving each thread a fixed share of the level: one slow page idles every thread whose page is already done. Hand out pages one at a time, to whichever thread is free.
  • Freeing the host slot only when the fetch succeeds: two failures on a host with a limit of 2 block that host forever.
  • Catching one exception type, or letting the exception end the worker after a finally did the bookkeeping: each failure costs a thread, and once failures outnumber threads nothing is left to crawl. In C++ an exception that leaves a thread's function ends the whole program.
  • Waiting with a loop around sleep, yield or a very short timed wait: it works, but it burns CPU or adds latency. Wait on a condition. This includes the thread that waits for the crawl to end: while (pending > 0) sleep(10) is the classic version.
  • Keeping the allowed hosts or the visited set in a field and never resetting it: the second crawl of the same crawler returns nothing, or wanders onto the first crawl's site.
  • Never stopping the workers: in Java daemon threads hide the leak until the process has thousands of parked threads. Setting the stop flag without joining is not enough either: the workers may still be running when crawl returns.
  • In C++, reading the stop flag outside the lock (a plain bool checked at the top of the worker loop): a data race with the write in the destructor, which ThreadSanitizer reports.

How to say it in the interview

Fetching is slow and independent, so it runs on a fixed set of worker threads with no lock held. Deciding what is new is fast, so I keep the visited set in one coordinating thread and need no lock for it. I crawl level by level from all start URLs at once: hand a level to the workers, wait on a condition until the unfinished count hits zero, then build the next level from the links they found. Breadth first order means every URL is first seen at its shortest depth, so the depth limit stays exact even though fetches finish in any order. For politeness I keep a running count per host under the same lock, and a worker takes the first waiting URL whose host has room, so a full host never blocks a thread. Every fetch is wrapped so a failure still frees its slot and its count. Without a depth limit I would switch to a free running pool with a pending counter, which avoids waiting for the slowest page in each level.
