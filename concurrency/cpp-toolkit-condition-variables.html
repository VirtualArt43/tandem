The toolkit: condition variables

Wait on protected predicates, interpret timed results, choose notifications, and build a bounded queue that wakes and drains on close.

Asked atRubrikLinkedIn
Before this:The toolkit: mutexes and lock guardsstd::chrono: durations, clocks and deadlines

A condition variable lets a thread block until it can recheck shared state. The protected state remembers readiness; notifications do not.

In plain words

A cook waiting for an order checks the order board, then sleeps until somebody rings a bell. The bell is not the order. If another cook took the order first, the awakened cook must check the board again. If the order was posted before the cook arrived, checking the board avoids sleeping unnecessarily.

Why this matters for concurrency

Bounded queues, pools, limiters, and shutdown protocols all wait for state. The difficult interview bugs are often a wrong predicate or a missing wakeup, not a complicated algorithm. Learn the call signatures here, then go deeper with condition variables, predicate loops, and lost wakeups and notification choice.

std::condition_variable requires an owning std::unique_lock<std::mutex> passed by reference, with the mutex locked by the calling thread. Concurrent waits on the same condition variable must use the same underlying mutex; violating these preconditions is undefined behaviour. A std::lock_guard cannot temporarily give up ownership, and a std::shared_lock is the wrong type.

std::condition_variable_any accepts a lock meeting the BasicLockable requirements: it supplies lock() and unlock() with the required ownership semantics. For example, it can wait with a std::shared_lock<std::shared_mutex>, provided writers take exclusive ownership and readers do not mutate under shared ownership. Both condition variable types are noncopyable and nonmovable; the stop-token overloads require C++20.

The wait protocol, one step at a time

  1. Acquire the mutex protecting the predicate.
  2. Check whether the state permits progress.
  3. If not, atomically release the mutex and enter the wait.
  4. After waking, reacquire that mutex before examining state.
  5. Recheck the predicate, then perform the state transition while still locked.

The atomic release-and-wait closes the gap between checking and sleeping, provided the notifier changes state under the same mutex. An atomic flag updated outside that mutex can still cause a lost wakeup.

A predicate tests whether this caller may proceed or must exit. The notifier's mutex release and the waiter's later acquisition establish happens-before for protected data. Notification alone does not publish arbitrary unsynchronised payload data.

Inside a member function, [this] captures the object's pointer, not a copy of its fields or an extension of its lifetime. The predicate runs while the mutex is held and should be a cheap state check, without I/O or callbacks into unknown code. A spurious wakeup is possible, and even after a genuine notification another consumer can reacquire first and take the item. Both cases need the same predicate loop.

Build a bounded queue in four decisions

First, define state: a deque, positive fixed capacity, closed flag, one mutex, and two conditions. The invariant is that the size never exceeds capacity and no insertion occurs after the closed flag is set. Keeping both conditions on one mutex lets every transition see a consistent queue and closed state.

Second, define predicates: a producer can wake when closed or when space exists; a consumer can wake when closed or an item exists. Waking because of close does not imply success. A producer rejects once closed. A consumer drains buffered items, then returns no value once closed and empty.

Third, name transitions: successful push may enable a consumer; successful pop may enable a producer. Close changes both predicates permanently, so it wakes all producers and consumers. The close method is idempotent, and the implementation does not promise FIFO ordering among waiting threads.

Fourth, define ownership: the queue must outlive all calls. Closing wakes callers; it does not join external threads or make destruction concurrent with their calls safe.

std::optional<int> distinguishes an item, including zero, from end of stream. while (auto value = queue.pop()) constructs and tests an optional on each iteration; *value reads its contained int. Each consumer writes its own sum, and main combines after joins. Operations run outside assert so defining NDEBUG cannot remove the work.

The queue is deliberately specialised to int. If deque allocation throws, insertion has no effect; the catch passes the unused slot to another producer before propagating the exception, and scope exit releases the mutex. Without that notification, the only awakened producer could fail while others remain asleep despite free capacity. A general element type also needs explicit guarantees for throwing moves or copies during removal.

Insertion, removal and setting closed_ are the successful operations' linearization points, all under the mutex. A push that inserted before close may return success after close returns; the overlapping push logically happened first. Item FIFO guarantees neither waiter fairness nor processing completion order.

The class itself works in C++17. The demonstration uses C++20 std::jthread; for C++17 replace it with std::thread and retain the explicit joins on both normal and exception paths. Even a std::jthread destructor cannot rescue an ordinary condition-variable wait: its stop request does not change this queue's predicate. Close before joining, and join before destroying the queue.

Notify one or all, under the lock or after it?

For one newly available item and equivalent consumer predicates, notify_one() is sufficient. For shutdown, notify_all() reaches every waiter whose exit predicate changed. If one condition variable serves different predicates, waking one arbitrary waiter can wake the wrong role and leave a capable waiter asleep. Separate condition variables or notify_all() let eligible waiters compete.

Notify for each successful single-item push, not only when the queue changes from empty to nonempty: two pushes can enable two sleeping consumers. A batch must wake enough consumers, use notify_all(), or arrange for awakened consumers to pass notifications onward. Broadcasting for every item is correct but can create a thundering herd of waiters contending and going back to sleep.

It is legal to notify while holding the mutex. The waiter still must acquire it before returning from wait, so waking under the lock may cause immediate contention. Updating under the lock and notifying after unlocking is a common choice, as above. Correctness comes from protected state and the waiting protocol, not from the notify call itself. Ensure the condition variable remains alive until notification and all waits finish; an unlocked notification is not permission for concurrent destruction.

Timed waits: status versus predicate truth

A nonpredicate timed wait returns std::cv_status; untimed wait() returns void. std::cv_status::no_timeout does not prove useful work exists, because the wake can be spurious or the state can be unsuitable. A predicate timed wait returns bool: true means the predicate passed while locked, and false means it was false at the final timeout check. It can return true after the deadline, including when state changed during mutex reacquisition.

For a total waiting budget, compute one std::chrono::steady_clock deadline and pass it to wait_until, or use the standard predicate wait_for overload. Do not implement a loop that gives every spurious wake a fresh full duration. Wall clocks can jump; steady_clock measures elapsed time without those calendar adjustments.

A deadline does not bound the return time. Scheduling and mutex reacquisition can delay return, and the mutex acquisition before the call is outside a wait_for budget. If the contract rejects work after a deadline even when ready, check the clock under the mutex before committing and define that check as the admission decision. Neither that check nor a timed wait makes the operation hard real-time.

Stop-aware waiting with std::condition_variable_any

The token-aware overload handles a stop request even if it arrives just before the worker actually waits; the latch marks arrival, not proof that the worker is already blocked. It returns the predicate result, not simply the inverse of stop_requested(). If work is ready and stop is requested, the result can be true. Your service decides whether cancellation or available work takes priority before committing the operation.

Ordinary std::condition_variable has no corresponding stop-token overload in C++20. In C++17, use a mutex-protected stopping flag in every wait predicate, set it under that mutex, call notify_all() for every affected condition, and explicitly join your std::thread workers. A stop request is cooperative: even the token-aware overload must reacquire the lock before returning.

Worked example: closing a full queue

A producer is waiting because capacity is exhausted. Close acquires the mutex and sets closed. Its notification wakes the producer, which reacquires the same mutex and sees that the wait predicate is now true because of closed. It then rejects the push. Consumers continue taking old items, freeing storage but never reopening admission. A producer predicate that mentions only capacity would miss this shutdown path.

Common mistakes

  • Using an if around a raw wait: use a predicate overload that loops.
  • Notifying without changing durable state: an early notification is not remembered.
  • Checking queue emptiness outside its mutex: the check itself races or becomes stale.
  • Returning success whenever wait_for wakes: inspect the protected predicate.
  • Closing without notifying both roles: producers can remain asleep on a full queue.
  • Holding an unrelated lock across a wait: only the supplied lock is released, so a notifier that needs the other lock can deadlock.

In the interview

Expect a bounded queue to implement or debug, then follow ups about multiple waiters, timed admission and draining shutdown. Be ready to explain why an atomic flag still permits a missed notification, why one condition with notify_one() can stall, and why closing is different from joining.

I will write the state and the two predicates before the wait calls. Every predicate read and state transition uses one mutex. Push wakes a consumer, pop wakes a producer, and close wakes everyone. Timeout and cancellation are outcomes of the operation, not just wakeup reasons.

Key takeaways

  • State remembers readiness; a notification does not.
  • Wait atomically releases the mutex, then reacquires before returning.
  • Predicate loops handle both spurious and stolen wakeups.
  • Use one deadline for a total timeout and understand each overload's return type.
  • Shutdown changes predicates and wakes every affected role.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A raw wait_for returns std::cv_status::no_timeout. What can you conclude?
Why. A spurious wake is possible without any notification. Even after a notification, another consumer may take the item before this waiter reacquires the mutex, so no item is reserved. Status is not a readiness contract.
Why does std::condition_variable need std::unique_lock<std::mutex> rather than std::lock_guard<std::mutex>?
Why. std::unique_lock exposes the unlock and relock operations needed by the wait. Both lock wrappers are noncopyable; std::lock_guard also works with ordinary std::mutex, but cannot release and regain ownership.
A producer waiting on the lesson's full queue wakes after close() sets the flag. What should it do?
Why. The wake predicate includes closed_ to let blocked producers exit even while full. Waiting for capacity could strand them, and a wake grants neither a slot nor permission to insert after close.
A predicate wait_until uses an already expired deadline, but its predicate is already true. What does it return?
Why. The predicate overload checks the condition first, so an expired deadline does not force false when it is already true. It returns bool; the nonpredicate timed overload returns std::cv_status.
Why can notify_one() be a poor choice for one condition shared by distinct waiter roles?
Why. Selection is not based on your predicates and has no FIFO guarantee. notify_one() unblocks one current waiter, not all roles; separate conditions or notify_all() let eligible waiters compete.
A token-aware std::condition_variable_any wait returns true even though stop was requested. Is that possible?
Why. Readiness and cancellation can coexist without any data race. The overload reports predicate truth, so cancellation does not force false; the operation must define which outcome wins before committing work.
Assume thread creation succeeds. What can this buggy program do?
Why. The atomic flag prevents a data race, and C++ permits notification without holding the mutex. But the producer can store and notify between the predicate's false check and the waiter's atomic unlock-and-wait. No further notification is guaranteed, and spurious wakes are permitted, not required, so termination is not guaranteed. Updating ready under the same mutex closes that gap.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Pseudo code
Write the producer and consumer predicates for a bounded queue that drains on close.
Model answer
Producer waits for closed or size below capacity, then rejects if closed. Consumer waits for closed or nonempty, then returns no value only when empty. Otherwise it removes an item. Close sets closed under the mutex and notifies both conditions.
Debug
A timeout occasionally lasts far longer than requested after many notifications. What code pattern would you inspect?
Model answer
Look for a hand-written loop that calls wait_for with the full original duration after every wake. Compute one steady-clock deadline and reuse wait_until, or use the predicate wait_for overload that manages the total waiting interval. Even correct deadline handling cannot bound scheduling or mutex reacquisition; inspect long critical sections too.
Explain
Explain why updating state under the mutex and notifying after unlock does not lose a necessary wakeup.
Model answer
A waiter checks the predicate while holding that mutex and releases it atomically with entering the wait. If the state was updated first, the waiter sees it during its check and does not need the notification. If it checked false first, the notifier cannot update until the atomic release-and-wait step. Object lifetime must still cover both operations.

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Walk me through the predicate wait in a bounded queue."
What a strong answer covers
  • Lock the predicate state
  • Predicate checks closed or availability
  • Wait atomically releases and later reacquires
  • Recheck and commit while locked
How a senior would say it
I acquire the queue mutex and check whether the queue is closed or an item is available. If neither is true, the wait atomically releases that mutex and blocks. When it wakes, it reacquires the mutex and checks again. That loop handles a spurious wake and another consumer taking the item first. Once the predicate is true, I still distinguish shutdown from useful work. An empty closed queue ends the stream; a nonempty one returns an item while preserving the same lock around the removal. The notification itself never reserves an item for me.

Likely follow up: Why does close need to wake blocked producers too?

"Compare the return values of timed waits and stop-aware waits."
What a strong answer covers
  • Raw timed waits return std::cv_status
  • Predicate timed waits return predicate truth
  • Timeout budget uses one deadline
  • Timed stop-aware false needs context and an outcome priority rule
How a senior would say it
A raw timed wait returns a timeout status, which is not proof about my application state. A predicate timed wait returns whether the predicate passed at its final protected check, even if that happens after the deadline. That is usually the useful API for a queue. I use one monotonic deadline so repeated wakeups do not reset the budget. The stop-aware condition_variable_any overload also reports predicate truth, so readiness can be true even when cancellation was requested. With its timed overload, false can mean timeout or stop. Both may be observable together, so the service defines which outcome wins.

Likely follow up: Can a timed wait return after the deadline because of scheduling?

Out loudabout 60 s
"The flag is atomic and already true, but a worker is stuck waiting. ThreadSanitizer is silent. What do you check?"
What a strong answer covers
  • Atomic state alone does not make a condition-variable protocol correct
  • Walk through false check, producer store and notify, then wait
  • A notification is not stored for a future waiter
  • Update predicate state under the same mutex and retain the predicate wait
  • ThreadSanitizer does not prove absence of lost wakeups
How a senior would say it
I would check whether the producer takes the waiter's mutex when it changes the flag. An atomic flag prevents a data race, but it does not close the gap before sleeping. The worker can check false, then the producer stores true and notifies before the worker actually starts waiting. That notification is not saved for a future wait, so the worker may sleep indefinitely. I would update the predicate state under the same mutex and keep the predicate overload. Notification can follow unlocking as long as the object stays alive. ThreadSanitizer can stay silent because this is a progress bug in a program without a data race.

Likely follow up: Would changing notify_one() to notify_all() close that gap?
