Mutexes and RAII guards

What a lock really guarantees, synchronized and ReentrantLock in Java, std::mutex with lock_guard, unique_lock and scoped_lock in C++.

Asked atRubrikMicrosoft
Before this:Invariants, critical sections and finding shared state

The mutex is the tool you will use more than any other. Learn exactly what it guarantees (mutual exclusion and visibility at its boundaries), exactly how to hold it so it is always released, and the handful of lock types you will write in every round.

In plain words

A petrol station has one washroom and one key on a big wooden block. Whoever holds the key goes in; everyone else waits outside the door. That is mutual exclusion. The key must come back even if you trip on the way out, which is why it is chained to a block nobody can walk off with: in code, that block is RAII.

There is a second, quieter guarantee. Whatever the last person left inside is exactly what the next person finds. Handing over the key hands over the state of the room. For threads, that is visibility: everything written before the unlock is seen after the next lock.

What a lock guarantees, and what it does not

A mutex gives you two guarantees:

  1. Mutual exclusion. At most one thread at a time holds it, so at most one thread at a time runs any of the code guarded by it.
  2. Visibility and ordering at the boundaries. An unlock happens-before every later lock of the same mutex. Everything a thread wrote before releasing the lock is visible to the next thread that acquires it, in order.

And it promises nothing else. It does not decide which waiting thread goes next (most locks are not fair by default). It does not protect data that some code reads or writes without taking it. And it does not know which data it guards: that is purely a convention you keep, which is why writing down what guards what matters.

Java: synchronized and intrinsic locks

Every Java object carries an intrinsic lock, also called its monitor lock. synchronized takes it:

  • A synchronized instance method locks this.
  • A static synchronized method locks the Class object, a different lock from any instance's.
  • A synchronized (obj) { ... } block locks whatever object you name: prefer a private lock object that no outside code can reach.

Intrinsic locks are reentrant (the holder can take them again, see reentrancy) and are released however the block exits, return or exception. They also carry the wait and notify methods of the same object, which you will use in condition variables.

C++: std::mutex and a guard

std::mutex has lock(), unlock() and try_lock(), but you almost never call them yourself. You create a guard object whose constructor locks and whose destructor unlocks, so the mutex is released on every path: that is RAII. The everyday guard is std::lock_guard. A std::mutex cannot be copied or moved, so a class containing one is not copyable by default, and it must be declared mutable if const member functions need to lock it.

Java: ReentrantLock, the explicit lock

java.util.concurrent.locks.ReentrantLock does what synchronized does, with the same memory guarantees, plus abilities synchronized lacks: tryLock() and tryLock(timeout, unit), lockInterruptibly(), an optional fair ordering, and several Condition objects per lock. The price is that you must release it yourself, always in this exact shape:

Use synchronized by default: it is shorter and cannot be left locked. Reach for ReentrantLock when you need a timeout, interruptible waiting, fairness, or more than one condition. Those features are covered in tryLock, timeouts and fairness. One Java 21 detail: a virtual thread that blocks inside synchronized is pinned to its carrier thread; JDK 24 removed most of that limitation, but on Java 21 hot paths for virtual threads prefer ReentrantLock.

C++: the three guards

std::unique_lock costs a little more (it stores an owns flag) and is the flexible one; std::scoped_lock is the one to reach for when a single operation needs two mutexes, such as a transfer between two accounts. Taking several locks safely, in both languages, is the subject of taking several locks.

Why not lock and unlock by hand

Here is the code RAII exists to prevent. Every early return and every exception between the lock and the unlock leaves the mutex locked forever, and every thread that needs it hangs. With ReentrantLock you must write the finally; in C++, use a guard and you cannot forget.

C++

Two C++ guard typos compile and silently protect nothing. std::lock_guard<std::mutex>{m_}; creates a temporary that unlocks at the end of that same statement. std::unique_lock<std::mutex>(m_); declares a new local variable named m_ that locks nothing. Clang warns about the second (-Wvexing-parse), but compilers usually say nothing about the first; clang-tidy's bugprone-unused-raii check flags it. Always name the guard: std::lock_guard<std::mutex> guard(m_);.

A std::mutex is not recursive: locking it again from the thread that already holds it is undefined behavior, in practice a self-deadlock. Destroying a mutex that is still locked, or letting a thread end while it owns one, are undefined behavior too.

Reads need the lock too

It is tempting to lock only writes: "a read cannot break anything". But a lock gives visibility only to threads that take it. An unlocked size() or getter can see a stale value, or the middle of an update that breaks an invariant, and in C++ it is a data race with the writers, which is undefined behavior. Every access to guarded state, reads included, takes the same lock. If a reader needs no lock, the field should be an atomic, or immutable.

Worked example: a thread-safe stack

Rubrik has asked for a thread-safe stack both in a screen and in an onsite system coding round, with a lock-free version as the follow up (you will build that in the lock-free stack). The design choice that matters is the interface. std::stack and java.util.Stack style APIs separate "look" from "remove": if (!s.empty()) { v = s.top(); s.pop(); }. With a lock inside each method, two threads can both see one element, both read the same top, and then both pop, one of them from an empty stack. That is check-then-act again. So the stack offers one operation that checks and removes together, returning "nothing" when empty.

The test checks a real invariant: every value pushed is either popped exactly once or still on the stack, so the sums must match exactly, however the threads interleave. Notice the C++ try_pop moves the element out before removing it, all under the lock, and returns it by value: returning a reference to the top would let the caller use it after the lock is released. The blocking version, where pop waits for an element, needs a condition variable; that is the thread-safe stack problem.

Common mistakes

  • Two different locks for the same data. One method locks this, another a private object, or a static synchronized method and an instance method share a static field: none of them exclude each other.
  • Locking writes but not reads. Stale or half-updated reads, and a data race in C++.
  • lock() and unlock() without finally or a guard. The first early return or exception leaves the lock held forever.
  • lock() inside the try with unlock() in finally. If lock() (or lockInterruptibly()) fails, finally unlocks a lock you do not hold and throws IllegalMonitorStateException, hiding the original problem.
  • An unnamed C++ guard. It is a temporary that unlocks immediately. Always give the guard a name.
  • Returning a reference or pointer to guarded data. The caller uses it after the lock is gone. Return copies.
  • Synchronizing on a field that gets reassigned, or on a shared constant such as a string literal or a boxed Integer. Threads end up locking different objects, or unrelated code locks yours. Lock a private final object.

In the interview

The mutex is the default answer to "make this thread-safe", so the questions are about precision. Classic ones: "synchronized versus ReentrantLock?", "lock_guard versus unique_lock versus scoped_lock?", "what does synchronized guarantee besides mutual exclusion?" and "is this getter thread-safe?". Microsoft C++ candidates have been asked to build a producer and consumer with std::mutex, std::unique_lock and std::condition_variable; Rubrik has asked for a thread-safe stack as runnable code.

A lock gives two things: only one thread at a time in the critical section, and visibility: everything written before an unlock is seen by the next thread that locks. So every access to the guarded state, reads included, goes through the same lock. In Java I use synchronized on a private lock object by default and ReentrantLock with try and finally when I need tryLock, timeouts or several conditions. In C++ I never call lock and unlock myself: std::scoped_lock or std::lock_guard for a plain section, std::unique_lock when I need to unlock early or wait on a condition variable.

Follow ups to expect: "What happens if an exception is thrown inside synchronized?" (released). "Inside a ReentrantLock section?" (released only by your finally). "Why must size() lock?" (visibility, and a data race in C++). "How would you make this stack lock free?" (a CAS on the head pointer, then the ABA problem).

Under the hood

An uncontended lock can often be acquired and released entirely in user space. Acquisition commonly uses an atomic read-modify-write; release need not use compare-and-swap.

Under contention, an implementation may spin briefly and then park the thread, using a futex on Linux, for example. Instructions, latency and spinning policy depend on the runtime, platform and workload. HotSpot can inflate synchronized locking to a monitor with a wait queue when needed. The details are in how locks are built.

Key takeaways

  • A lock gives mutual exclusion and visibility: an unlock happens-before the next lock of the same lock. Nothing more: no fairness, no protection for unlocked accesses.
  • Java: synchronized on a private lock by default; ReentrantLock with lock() before try and unlock() in finally when you need its extra features.
  • C++: never call lock() and unlock() yourself. std::lock_guard or std::scoped_lock for plain sections, std::unique_lock for flexibility and condition variables, std::scoped_lock for several mutexes.
  • Every access to guarded state, reads included, takes the same lock; return copies, never references to guarded data.
  • Design interfaces so that check and act happen in one call, such as a tryPop that returns an optional.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a thread-safe BankAccount with deposit(amount), withdraw(amount) that returns false and changes nothing if the balance is too low, and balance(). Use a lock in your language and explain why withdraw is the method that needs the most care.
Model answer

withdraw is a check-then-act: "is there enough?" followed by "subtract". If the check and the subtraction were separately locked, two withdrawals could both pass the check and overdraw the account, so both happen inside one critical section. Positive-amount validation touches no shared state, so it runs before locking. The deposit's overflow check depends on the balance and stays under the lock; an overflowing deposit throws without changing it. balance() takes the lock so it sees the latest value, and in C++ so that it is not a data race. The lock is a private object (Java) or a private member (C++), so no outside code can take it.

Explain
Your interviewer asks you to choose a lock type for a cache's get and put, and then for a method that moves money between two accounts that each have their own lock. Explain your choices in your language.
Model answer

Java: for the cache I would use synchronized on a private final lock object, since get and put are short critical sections and synchronized cannot be left locked. If I needed to give up after a timeout, wait interruptibly, use fairness, or have several conditions, I would switch to a ReentrantLock with lock() before try and unlock() in finally. For the transfer, Java has no statement that takes two locks at once, so I would take both locks in a fixed global order, for example by account id with a tie breaker, so that two opposite transfers cannot deadlock.

C++: for the cache, std::scoped_lock or std::lock_guard on a mutable std::mutex member, since the sections are plain; if I needed to unlock early, or to wait on a condition variable, std::unique_lock. For the transfer, handle a transfer to the same account first, then use std::scoped_lock lock(from.m, to.m); for two distinct mutexes. It locks both with a deadlock avoidance algorithm whatever order the arguments come in. In both languages, every read of the guarded data takes the same lock, and nothing slow happens while holding it.

Debug
Under load, some threads calling this hang forever. Find the bug and fix it.
Model answer

The early return false leaves the mutex locked: the first request for an unknown or short product leaves m_ held, and every later call to anything that locks m_ hangs. It shows up "under load" only because that is when such a request first arrives. Any exception between lock() and unlock() would do the same.

The fix is to never lock and unlock by hand: replace the two calls with std::lock_guard<std::mutex> guard(m_); (or std::scoped_lock guard(m_);) at the top of the function. The guard's destructor unlocks on every path, the early return and exceptions included. The Java version of this bug is lock.lock() with unlock() not in a finally; the fix is lock(); try { ... } finally { unlock(); }, or simply a synchronized block.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"A teammate locks every write but leaves the getters unlocked. Walk me through what the lock guarantees and why that design is still wrong."
What a strong answer covers
  • A mutex provides mutual exclusion and visibility only through a shared locking protocol
  • An unlock orders earlier writes before accesses after a later successful acquisition of the same lock
  • An unlocked reader can observe an inconsistent pair of fields; in C++ a conflicting ordinary access is a data race and undefined behavior
  • All accesses to guarded state use the same lock, including copying a snapshot
  • Locking does not promise fairness or make a sequence of separately locked calls atomic
How a senior would say it
The getters need the same lock as the writers. A mutex gives mutual exclusion and a visibility guarantee, but only when threads follow the same locking protocol. One thread's unlock orders its earlier writes before another thread's accesses after acquiring that same mutex. Taking an unrelated lock does not create that connection. Suppose a writer changes a lower bound and an upper bound together. An unlocked getter can read one old field and one new field, even though the writer holds a lock throughout. In C++, those conflicting ordinary accesses are a data race, so the program has undefined behavior. I would lock the getters too, and copy both fields while holding the lock when callers need a consistent snapshot. An independently atomic field is a different design, and I would document it explicitly. I would also avoid promising more than the mutex provides. Ordinary locking does not guarantee which waiter goes next, and two separately locked calls still leave a gap. If a caller must check and update together, the class needs one operation covering both.

Likely follow up: If a getter takes the lock but returns a reference to the guarded collection, is the caller protected?

Out loudabout 75 s
"How would you choose the locking API for a simple cache, a blocking queue, and a transfer between two accounts?"
What a strong answer covers
  • A simple cache uses a private lock with scope-based release in C++, or synchronized in Java
  • Condition waiting needs unique_lock with std::condition_variable; Java can use a monitor or ReentrantLock with conditions
  • Java ReentrantLock needs unlock in finally after successful acquisition
  • Transfers handle the same-account case first and acquire distinct locks in a global order or with C++17 scoped_lock
  • Releasing locks automatically does not by itself prevent deadlock or roll back partial updates
How a senior would say it
I would choose the simplest API that supports the operation, with release guaranteed on ordinary returns and exceptions. For a cache with short critical sections, that means a private monitor with synchronized in Java, or a named guard around a mutex in C++. A blocking queue adds a wait for a state change. Java can wait on the same monitor, or use a ReentrantLock with separate conditions. In C++, a standard condition variable needs a unique lock because waiting releases the mutex and reacquires it before returning. With an explicit Java lock, I acquire before the try block and unlock in finally. For a transfer, I first handle the case where both accounts are the same. For distinct accounts, Java takes both locks in one global order, such as unique immutable account identifiers. In C++17 and later, scoped lock can acquire both mutexes with deadlock avoidance. These choices manage lock ownership, but they do not make the business operation exception safe automatically. I still validate before committing changes and preserve the invariant if something fails.

Likely follow up: Could recursive locks replace the global ordering rule for a transfer?

Out loudabout 60 s
"An inventory service hangs after an out-of-stock request. The reservation method calls lock, checks stock, and unlocks at the bottom. What do you inspect?"
What a strong answer covers
  • Inspect the early return and exception paths for an acquired lock that is never released
  • An out-of-stock return before unlock leaves other threads blocked on that mutex
  • Use a named C++ guard or Java synchronized; explicit Java locking releases in finally
  • An unnamed C++ guard is destroyed at its statement and does not protect later accesses
  • Exercise the failing reservation path, then another reservation, with a bounded completion check
How a senior would say it
I would inspect the out-of-stock return first. If the method acquired the lock and returned before reaching unlock, it leaked ownership. Other threads then wait for a release that never happens. That matches a service that works until one particular request arrives. Exceptions between acquisition and release create the same failure. In C++, I would replace manual locking with a named guard whose scope covers the check and the update. The name matters: an unnamed temporary guard is destroyed at the end of its own statement. In Java, I would use synchronized, or put unlock in finally after successful explicit acquisition. Then I would test an out-of-stock reservation followed by a valid one from another thread, with a deadline on completion. I would also exercise an exception path. A successful reservation alone never reaches the branch that caused this hang.

Likely follow up: The lock now releases on exceptions, but an exception occurs halfway through a multi-field update. Is the state necessarily valid?
