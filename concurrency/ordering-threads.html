Making threads take turns

Solve ordering puzzles with turn state, monitors and semaphores, then handle termination, failures and targeted wakeups.

Asked atMicrosoftNvidia
Before this:Condition variables and monitorsSpurious and stolen wakeups: always wait in a loopSemaphores: permits as a resource limit

Ordering puzzles look like toys, but they test the one skill every concurrency round needs: making a thread wait until another thread has done something, without missing the signal and without burning a core while it waits.

In plain words

Picture a wedding kitchen with three cooks: one plates the starter, one the main course, one the dessert. They get ready at random times, and the dessert cook is often ready first. Dessert must still not go out before the main course. On the wall is a small board that says whose turn it is. A cook who is ready looks at the board; if it is not their turn, they sit by the pass and wait until someone calls out. A cook who finishes writes the next name on the board and calls out.

That board is the whole trick. Every ordering puzzle is a shared "whose turn" value, a way to sleep until it is your turn, and a way to wake the others when the turn changes. The puzzles only differ in the rule that decides who is next.

One pattern behind every ordering puzzle

A thread that must run "after" another needs two things: a fact it can check (has step 1 happened?) and a way to sleep until that fact becomes true. There are three toolkits for this, and interviewers expect you to know all three.

ToolkitHow the turn is passedBest for
A mutex, a condition variable and a turn variableChange the turn under the lock and wake the waiters; each waiter re-checks the turn in a loopAny number of threads and any rule for who is next
Semaphores used as batonsEach thread waits on its own semaphore; a thread that finishes releases the next thread's semaphoreA fixed chain or ring of steps
One-shot latches or futuresA step counts down a latch or completes a promise that the next step waits on"B after A" that happens exactly once

One property separates semaphores from condition variables, and it decides many of these puzzles: a semaphore remembers a release that happened before anyone waited, and a condition variable does not. If thread A calls release() before thread B calls acquire(), the permit is stored and B goes straight through. If A calls notify before B calls wait, the notification is gone, which is why the condition variable toolkit always pairs the signal with a turn variable that B checks before it sleeps.

There is a fourth way that works and that you should mention only to reject: spin on an atomic variable until it holds your number. For these single-writer turn flags it can be correct with Java volatile or C++ std::atomic using its default ordering, but a running waiter consumes CPU doing no useful work, and on a machine with fewer cores than threads the spinners can delay the very thread they wait for. That is busy waiting; its own lesson covers when spinning is right.

State the contract first. These demos use one worker per role, nonnegative bounds well below integer overflow, callbacks that finish without throwing or re-entering the coordinator, and no cancellation. Round robin also requires N >= 1 and worker ids from 0 to N - 1; leave room for the final counter increment. Completion assumes every worker eventually runs. The failure and shutdown extension appears below.

The handoff orders memory as well as output. Java semaphore releases establish happens-before with successful subsequent acquires; C++ semaphore release/acquire also publishes preceding writes. In a monitor, unlocking and the next successful lock acquisition provide that ordering; the notification alone is not the publication mechanism. Thus a later stage may safely read data written before the earlier stage hands over.

Print in order (LeetCode 1114)

One object Foo has three methods, first(), second() and third(). Three threads call them, one each, in any order. The output must always be "firstsecondthird".

The naive attempt and why it fails

The first idea is a pair of boolean flags and a loop that waits for them:

Two things are wrong. The flags are shared with no synchronization, so there is no happens-before edge from the write to the loop: the compiler may load firstDone once, keep it in a register and loop forever. In C++ it is a data race, which is undefined behavior. And even with visibility fixed (volatile in Java, std::atomic<bool> in C++), the waiting threads spin at full speed for as long as they wait.

Three correct versions

The cleanest fix is two semaphores that start with zero permits. second() cannot pass until first() has released, and third() cannot pass until second() has released. Because a semaphore stores a release, it does not matter which thread starts first. The demo requests thread starts in reverse order; the scheduler still chooses when each worker actually runs.

std::binary_semaphore and std::latch are C++20. In C++17, use the monitor version below, or a std::promise<void> and std::future<void> pair per step.

Two more versions are worth having ready. Latches fit because each method runs exactly once per object; a monitor can also handle repeating steps if you add an appropriate reset or generation rule. The stage counter shown here is one-shot.

FooBar (LeetCode 1115)

One thread calls foo(), which prints "foo" n times; another calls bar(), which prints "bar" n times. The output must be "foobar" repeated n times.

The tempting wrong answer wraps each print in the same lock. A lock gives one-thread-at-a-time, which feels like order, but it is not:

Add the missing state, a fooTurn flag, and wait for it in a loop. With exactly one worker per role, notify() would also work here: at a notification the only possible other waiter is the worker for the opposite turn; notifyAll() is the habit that stays correct when the puzzle grows.

The semaphore version is a ping pong of two batons. The invariant that makes it correct: there is one logical baton, either stored as an available permit or held by the worker between acquire and release, so at most one thread may print.

ZeroEvenOdd (LeetCode 1116)

Three threads share one object. One calls zero(), one odd(), one even(), and together they must print "0102030405..." up to n: a zero before every number, odd numbers from the odd thread, even numbers from the even thread.

The rule for who is next is a chain with a fork in it: after every zero comes the odd or the even thread, depending on the number; after every number comes zero. Three semaphores express it directly, and each thread's loop bounds tell it how many turns it gets, so every thread ends on its own.

Worked example: tracing ZeroEvenOdd for n = 3

Write the permits as (zero, odd, even). They start at (1, 0, 0).

StepWho runsWhat it doesPermits after
1zero (i = 1)takes the zero permit, prints 0, 1 is odd so it releases odd(0, 1, 0)
2odd (i = 1)takes the odd permit, prints 1, releases zero(1, 0, 0)
3zero (i = 2)prints 0, 2 is even so it releases even(0, 0, 1)
4even (i = 2)prints 2, releases zero; its loop ends because 4 > 3(1, 0, 0)
5zero (i = 3)prints 0, releases odd; its loop ends(0, 1, 0)
6odd (i = 3)prints 3, releases zero; its loop ends because 5 > 3(1, 0, 0)

Output: 010203. The last column shows the state after each handoff, before the next acquire. At those boundaries the permits add up to one. During a callback all three counts are zero: the running worker holds the logical baton. Available permits plus held batons always total one. The left over zero permit at the end is harmless; nobody waits for it.

FizzBuzz with four threads (LeetCode 1195)

Four threads count from 1 to n together. fizz() prints for multiples of 3 that are not multiples of 5, buzz() for multiples of 5 that are not multiples of 3, fizzbuzz() for multiples of 15, and number() prints every other number. The output must be the usual FizzBuzz sequence in order.

Here "who is next" depends on the number itself, so a semaphore chain gets awkward. The monitor is natural: one shared counter, and each thread waits for a predicate that says "the current number is mine". The predicate must also say "or the run is over", otherwise three of the four threads wait forever after the last number.

Two details are easy to miss. The thread prints while it still holds the lock and only then moves current on; if it advanced first and printed after unlocking, the next thread could print ahead of it. And notifyAll is required here: four threads wait on one condition for four different predicates, so a single notify may wake a thread whose turn it is not, which goes back to sleep while the right thread sleeps on. That is a wrong-waiter notification: the enabled worker receives no wakeup, so the program can hang. The state is correct, but the wakeup policy is not.

Round robin with N threads

N threads print 1 to M in turn: thread k (counting from 0) prints the numbers i with (i - 1) mod N = k. This is the shape Microsoft asked as "print 1 to 100 with 3 threads", and Nvidia as "1 to N with N threads".

The FizzBuzz monitor solves it with the predicate (current - 1) % N == k. It works, but if all other workers are waiting, one step can wake N - 1 threads although only one has the next turn. That is a small thundering herd on every number. The fix is one condition per thread, so each step wakes exactly the next thread.

No wakeup can be lost here even though signal is targeted: a thread always checks the predicate under the lock before it waits, so if its turn arrived before it got there, it simply does not wait. The broadcast at the end matters too: when the run is over, threads waiting for a number that will never come must be woken to see it.

Nvidia's follow up was "now do it with one semaphore". If the one shared semaphore is the only waiting primitive, it cannot select a particular role. Using it as a mutex around a turn counter gives acquire, check, release and retry whenever the wrong worker wins. That version can waste CPU and offers no per-role progress guarantee; fairness of the semaphore does not establish the required numeric order. Clarify whether additional conditions or atomics are allowed before claiming a general impossibility. With N semaphores you get the ring of batons from FooBar: thread k waits on its own semaphore and releases the next one (the checkpoint below has the code).

The traffic light (LeetCode 1279)

An intersection joins road A (directions 1 and 2) and road B (directions 3 and 4). One light is green for one road at a time, and road A starts green. Each car calls carArrived(carId, roadId, direction, turnGreen, crossCar): if its road is red, it must call turnGreen() and then crossCar(). Both roads may never be green, and no car may cross on red.

The core is a check then act: "is my road green? if not, turn it green; then cross" must happen as one step, otherwise a car from road B can flip the light between a road A car's check and its crossing. One lock around all of it is the accepted answer:

The follow up writes itself: "this lets only one car cross at a time; let cars on the green road cross together." Now you count the cars crossing, a car from the other road waits until the count is zero before it flips the light, and to stop the red road from starving you close the current batch when the other road starts waiting, drain it, and explicitly hand the phase to that road. Admit a finite batch before handing back if both roads have waiters; simply blocking both roads whenever the other has a waiter would deadlock. That is group mutual exclusion, the same problem as the unisex bathroom.

Failure, cancellation and reuse are part of the protocol

A callback that throws before handing over strands later workers. Restoring a Java interrupt flag is appropriate at a thread boundary, but it does not tell the other workers to stop. The demos assume those events do not occur; a reusable service needs a shared terminal state, not just a catch block in one thread.

For a monitor, add stopped and a failure value under the same lock. Wait for stopped || done || myTurn, check the terminal state before doing work, and on interruption or callback failure record the first failure and broadcast to every condition. Propagate the Java exception after publishing failure, or restore interruption at the outer worker boundary; in C++ catch inside the worker, record a std::exception_ptr, and join before rethrowing on the owner thread.

A stop request does not automatically wake std::condition_variable::wait or a semaphore acquire. See cooperative cancellation.

With semaphores, do not blindly release a success baton in finally: that lets dependent work run after a failed prerequisite. Either define explicit failure tokens and a safe wakeup protocol, or use a monitor for cancellation. Extra releases can exceed a C++ semaphore's maximum count. A timeout similarly needs one deadline and a terminal transition that wakes peers; silently abandoning a turn hangs the rest.

Callbacks run while the coordinator owns the turn, and monitor examples also hold its lock. Require short callbacks that do not re-enter or wait for another role. For slow work, reserve the turn, work outside the lock, then publish completion before making the next turn available.

The one-shot Foo objects are not reusable across overlapping runs; use fresh objects or an explicit generation number. Latches cannot be reset, and leftover permits are not a generation protocol.

Common mistakes

  • Ordering with sleep. "Sleep 100 ms before printing second" works on an idle laptop and fails under load, and it creates no happens-before edge. Sleep is never synchronization.
  • Treating a lock as a turn. A lock prevents overlap; it says nothing about who goes next. Turns need state.
  • if instead of while around the wait. A thread can wake spuriously, or be woken for someone else's turn. Re-check every time; in C++ pass the predicate to wait.
  • notify with several kinds of waiter on one condition. It can wake the wrong thread, which waits again, and the program hangs. Use notifyAll, or one condition (or semaphore) per kind of waiter.
  • A wait with no way out. Open-ended monitor loops need "or the run is over", and the last worker must broadcast. Fixed per-role semaphore loops can instead stop after exactly their assigned number of turns.
  • Moving the turn before the output is done. Print, then advance. If you advance and unlock first, the next thread can print ahead of you.
  • Wrong semaphore start values. Two permits in a ring lets two threads print at once; zero everywhere deadlocks at once. Start with exactly one permit; during execution count both stored permits and the baton held by a worker.

In the interview

These puzzles arrive as warm ups, phone screens and online assessment questions, more often in India loops and system software roles than in Google or Meta loops. Reported examples: Microsoft asked "print 1 to 100 using 3 threads" (the candidate managed only two) and odd and even printing with two threads; Nvidia asked "print 1 to N with N threads" with N semaphores and then with one, and odd and even in C with a mutex and condition variables. LeetCode's crowd reported company tags list Print in Order for Google and Microsoft and FizzBuzz Multithreaded for Nvidia.

What the interviewer watches: that you reach for a turn variable and a condition (or semaphores) rather than sleep or a spin; that every thread exits; and that you can say why you chose notifyAll.

Every one of these is a turn variable plus a way to sleep until it is my turn. I will keep a counter for whose turn it is under one lock; each thread waits in a loop for its own predicate, which also checks whether the run is over, prints, advances the counter and signals. Different threads wait for different predicates on one condition, so I use notifyAll, or one condition per thread when N is large, so that each step wakes exactly one thread.

Follow ups to expect: "Now N threads." "Without busy waiting." "Why notifyAll and not notify?" "Only semaphores? Only one semaphore?" "Make it run forever and stop cleanly on shutdown" (a stop flag in the predicate, set under the lock, then a broadcast). "How would you test it?" (hundreds of rounds, random start order, exact output, a timeout that fails instead of hanging, and ThreadSanitizer for C++).

Senior depth

Coordination adds cost without parallel useful work. Ordered FizzBuzz serializes the callbacks, while adding locks, wakeups and scheduling overhead. A handoff may cause a context switch if a worker blocks, but not every handoff must do so, especially across cores; printing cost also depends on buffering and the output device. Expect no computational speedup for this tiny workload, and measure before quoting a latency.

Count the wakeups. Ignoring spurious wakes, with one condition and notifyAll the potential wakeup work is O(N times M) for M numbers and N workers. Targeted conditions or semaphores reduce it to O(M + N), including final shutdown. These describe notification-driven work, not exact wake counts: late arrivals and workers already waiting for the mutex reduce it, while spurious wakes add unrelated work. The idea of handing the right to run directly to the one thread that should run next is often called passing the baton.

Turn order comes from the predicate. During an active run exactly one role is eligible, so FIFO locks are unnecessary for output order. Progress still assumes that the eligible worker is eventually scheduled, acquires the lock and finishes its callback. An unfair scheduler can stall the entire sequence; a turn predicate cannot force a thread to run.

Key takeaways

  • Every ordering puzzle is turn state, a wait for my turn, the work, then advancing the turn and waking the others.
  • A lock gives one at a time, not order. Order needs a turn variable or batons.
  • Semaphores remember releases; condition variables do not, so pair them with state and always wait in a loop.
  • With several kinds of waiter on one condition, use notifyAll, or give each thread its own condition or semaphore to wake exactly one.
  • Every worker needs a termination plan: a terminal predicate or a fixed number of turns. Complete the work before passing the turn.

Quick check

Answer each question, then read why. Your score is saved for your module test.

FooBar is built with one shared lock around each print and no other state, and n = 2. Which output is possible?
Why. A lock prevents two prints from overlapping, but the foo thread can release it and take it straight back before bar is scheduled. Alternation needs state that says whose turn it is, plus a wait for that state. There is no lock cycle here, and starting bar first does not force its whole schedule or make its output unique.
Thread B calls release() on a semaphore that has 0 permits. Afterwards, thread A calls acquire(), with no interruption and no other acquirer. What happens to A?
Why. A semaphore is a counter, so a release stores a permit for a later acquire. That memory is exactly what a condition variable lacks: a notify sent before anyone waits is simply lost, which is why condition variables are always paired with a state check. Releasing from zero is legal, and fairness makes no difference when there is only one acquirer.
Three threads print 1 to 9 round robin. All state checks and notifications hold the same monitor. They wait on one condition with while (!myTurn) wait();, and the printing thread calls notify() (not notifyAll()) after advancing the counter. What can happen?
Why. The loop protects against acting on a wrong wakeup, but it cannot create the missing one. With two kinds of waiter on one condition, a single notify can be spent on a thread that cannot proceed. Use notifyAll or one condition per thread. The locked predicate check prevents duplicate prints; holding the monitor satisfies the API ownership requirement, so IllegalMonitorStateException is not the issue.

Why. When current passes n, the predicate is false for every thread that does not happen to own n + 1, so they wait forever and join never returns. The wait condition must be current <= n && !mine.test(current). Before completion, the locked predicates preserve uniqueness and order, and the role for 1 can start, so the other options do not describe this bug.
For ZeroEvenOdd with three semaphores, which starting permits are correct for (zero, odd, even)?
Why. Zero must go first and nobody else may go until it has. (1, 1, 0) lets the odd thread print 1 before the first 0; (0, 0, 0) deadlocks immediately. (1, 1, 1) also allows numbers before zero. Initially exactly one permit enables zero; during a callback the worker holds the baton and the available counts total zero.
A monitor version of FooBar is changed so that foo() sets fooTurn = false, calls notifyAll(), leaves the synchronized block, and only then calls printFoo.run(). What can go wrong?
Why. Once the turn has moved and the lock is free, bar may print immediately, while foo has not printed yet. The notification still wakes waiters, and nothing here requires a deadlock, but the output order is no longer guaranteed. Do the work while you still hold the turn, then advance it.
N threads print 1 to M round robin, with large N and M much larger than N. Assume the other N - 1 workers are waiting at each handoff, and ignore spurious wakes and final shutdown. How does the wakeup work scale for one condition with notifyAll, compared with targeted conditions?
Why. Under the stated assumption, broadcast wakes N - 1 workers per step and targeted signalling wakes one, giving O(N times M) versus O(M). Actual runs need not park every worker at every handoff; these counts are a contention model, not a scheduler guarantee. The reversed option assigns the broadcast cost to the wrong design, and O(N) ignores the M handoffs.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write the round robin printer with N semaphores: N threads print 1 to M in order, thread k prints the numbers i with (i - 1) mod N = k. No busy waiting, and every thread must exit.
Model answer

Why it is correct: there is one logical baton across the available permits and the worker holding it, so at most one thread may print, and it is always the owner of the next number. Each thread's loop visits exactly its own numbers, so every thread ends by itself; the final release lands on a thread that has nothing left to print, which is harmless. Each release enables only the next role, with no thundering herd. If M = 0 nobody acquires; if M < N, unused roles have empty loops; if N = 1, the worker releases its own semaphore after each print.

Explain
Your interviewer asks two things about your FizzBuzz monitor: "why notifyAll and not notify?" and "is the four thread version faster than a single loop?" Answer both as you would out loud.
Model answer

notifyAll, because four threads wait on one condition for four different predicates. Suppose all three word workers are waiting while the number worker prints 2. The next value is 3, but a single notify might wake buzz instead of fizz. Buzz re-checks and sleeps again; the number worker also waits because 3 is not its turn. Fizz remains asleep, so the program can hang without printing 3. notifyAll wakes all of them, the right one proceeds and the rest go back to sleep. If the cost of those extra wakeups mattered, I would give each thread its own condition and signal exactly the owner of the next number.

I would not expect a speedup. Callbacks remain sequential, and coordination adds locking and potentially blocking, waking and context switches. Not every number switches workers: the number worker can print 1 and 2 consecutively. The output device and buffering may dominate the measured time, so I would benchmark instead of promising a fixed slowdown. This puzzle tests coordination.

Debug
A candidate's FooBar uses two semaphores, but both start with one permit: fooMayRun = 1 and barMayRun = 1. Give an interleaving that prints the wrong output for n = 2, and fix it.
Model answer

Both threads can pass their first acquire at once, because each semaphore already holds a permit. An interleaving: both workers acquire their initial permits before either releases anything; bar prints "bar" before foo prints "foo"; the output starts "barfoo". The two prints can also run at the same time, so the output can even interleave inside a word if the print is not atomic.

The fix is to start barMayRun at 0, so there is one initial permit: foo first, then each thread passes the baton to the other. A quick way to check any baton design is to add up the starting permits: the answer must be one. Other schedules with the broken C++ binary-semaphore version can also release beyond max(), violating its precondition; a semaphore is not a saturating flag.

How a senior would say it
The lock prevents overlapping prints, but it does not enforce turns. Foo can print, unlock, then acquire the lock again before bar runs. I would use two semaphores for this fixed alternation: foo starts with one permit and bar starts with zero. Each worker acquires its own permit, completes its print, then releases the other worker's semaphore. That also handles bar starting first, because it waits until foo has completed. The invariant is one logical baton. It is either an available permit or held by the worker between acquire and release; the stored counts do not always sum to one. Each worker loops exactly n times, so both terminate. A monitor with a turn flag and predicate waits is equally valid. Both designs assume callbacks finish successfully and workers keep running; cancellation needs a separate protocol to wake peers and stop the sequence.

Likely follow up: What happens if foo's callback throws after acquiring its permit?

"My four-thread FizzBuzz prints 1 and 2, then hangs. Every wait uses a loop. What would you inspect?"
What a strong answer covers
  • A predicate loop ensures safety but cannot guarantee the right waiter is notified
  • After number prints 2, a single notify may wake buzz while fizz remains asleep
  • Use broadcast on the shared condition or a separate condition for each role
  • Keep state checks, output and counter advancement under the same lock
  • Include completion in every wait predicate and broadcast after the final value
  • Test exact output and bounded completion, including empty and small runs
How a senior would say it
I would first inspect the notification policy. A loop prevents a worker from printing on the wrong turn, but it cannot wake the worker whose turn it actually is. Suppose fizz, buzz and fizzbuzz are waiting while number prints 2. The counter becomes 3. A single notification might wake buzz, which finds that 3 is not its turn and waits again. Number must also wait, while fizz remains asleep. The state is valid, but nobody can advance it. I would broadcast after changing the counter, or use separate conditions and signal the role that owns the next value. I would also check that all predicate checks and counter updates use the same lock, and that output completes before ownership passes. For termination, every wait must accept either its turn or the end of the run, with a final broadcast. I would test the exact sequence and require every worker to finish before a deadline, including zero items, one item and a final fizzbuzz. Those checks separate ordering bugs from shutdown bugs.

Likely follow up: Can targeted signalling lose a wakeup if the next worker has not started waiting yet?

Out loudabout 90 s
"Make this ordered printer safe to shut down when a worker is interrupted or its callback fails. How would you design that?"
What a strong answer covers
  • Choose shared terminal state and a first-failure value protected by the monitor
  • Wait predicates include stopped or completed as well as the role's turn
  • Publish failure and wake every waiter before propagating the worker's failure
  • Do not release a success baton after failed work or assume a stop request wakes a wait
  • Define callback completion and cancellation boundaries without advancing output early
  • Join every worker before destroying state, and test failures at handoff boundaries
How a senior would say it
I would use a monitor with an explicit terminal state and a stored first failure. Every worker waits for its turn, normal completion, or shutdown, and checks the terminal state before invoking its callback. If a callback throws, I record the failure under the lock, mark the run stopped and wake every waiting role. Interruption follows the same state transition. In Java I then propagate the interruption or restore the flag at the outer worker boundary. In C++ I catch inside the worker and let the owner report the saved exception after joining. Merely setting a stop flag does not wake a condition variable or semaphore. I would not release the next success baton in a finally block, because that would let dependent work proceed after its prerequisite failed. I would also define what cancellation means for a callback already running: normally it may finish, but no later turn starts once shutdown is published. A callback must not re-enter the coordinator or wait for another role. If callbacks need to run outside the lock, I reserve the turn until completion and publish the next turn only afterwards. Finally, I join every worker before destroying the coordinator and test failure before a handoff, during a callback and while peers are waiting.

Likely follow up: How would you preserve these guarantees if callbacks perform slow I/O outside the monitor?
