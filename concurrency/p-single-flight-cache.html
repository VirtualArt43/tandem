Single-flight cache

Thread-safe structureshard45 minRubrik

When a hot key goes missing, a thousand requests miss at once and a thousand identical loads hit the database. A single-flight cache makes them share one load. The happy path is ten lines; the interview is about failures, invalidation and never holding a lock while the load runs.

The task

Build a cache in which concurrent misses on the same key share one load. This is called single-flight, and it is the standard cure for a cache stampede.

  • get(key, loader) returns the cached value for key. On a miss there are two cases. If a load for that key is already in flight, wait for it and return its result. Otherwise this caller becomes the loader: it calls loader(key) on its own thread, with no lock held, caches the value on success, and hands the outcome to every caller that waited.
  • A failed load is not cached. Every caller that was waiting for that load gets the failure, and the next get starts a new load.
  • invalidate(key) forgets the key immediately, and never waits for a load. A load that is already in flight still answers the callers already waiting on it, but its result must not be cached (the data may have changed under it), and the next get starts a fresh load.
  • Loads of different keys run at the same time, and a hit on a cached key never waits behind a load of another key.

Failures. In Java the loader throws a RuntimeException, and get must throw an exception that is either that exception or has it as its cause, so a CompletionException wrapping it is fine. In C++ the loader's exception must come out of get in every waiting thread with its type intact, so catch (const std::runtime_error&) still works. Library tools are allowed here: ConcurrentHashMap, CompletableFuture, std::promise and std::shared_future are all fair game. The loader never returns null.

Where it comes up: a Rubrik senior system coding round (reported through a question bank, so treat the details as approximate) asked for a cache refresh where, on a miss or expiry, only one thread per instance refreshes a key and every other thread waits and reuses the new value. The same idea is the golang.org/x/sync/singleflight package in Go.

What the tests check

  • From one thread: values are cached per key, invalidate makes the next get load again, and a failure is thrown and not cached.
  • A burst: 8 threads miss the same key at once. The loader runs once and all 8 get the same value.
  • A failing burst: 8 threads wait on a load that fails. All 8 see the failure, the loader ran once, and the next get loads afresh.
  • Loads of 4 different keys overlap in time, and 50 hits on a cached key complete while another key's load is stuck.
  • invalidate during a load: it returns at once, the next get starts its own load instead of waiting, the old caller still gets the old result, and the old result does not end up in the cache even though it finishes last.
  • Stress: 8 threads do random gets and invalidates on 20 keys. Every value belongs to its key, and no key is loaded more often than once plus the number of times it was invalidated.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Thread-safe caches: LRU, TTL and single-flight

Open them one at a time. Each one gives away a little more.

Besides "absent" and "cached", the cache must remember a third state per key: "someone is loading this right now". Which object lets other threads wait for a value that does not exist yet?
A future. Store one future per key. The first caller to find the key absent inserts a new, unfinished future in one atomic step (putIfAbsent, or under a mutex), releases any lock, runs the loader, and completes the future. Everyone else just waits on the future. In C++, a std::promise with a std::shared_future gives you exactly this, exceptions included.
On failure, remove the entry first, then complete the future with the exception, and remove only your own entry (remove(key, mine) in Java, a load id in C++): an invalidate plus a newer load may already have replaced it. invalidate itself only removes the entry. Because the entry is the future, a load that finishes later completes a future that is no longer in the map, so its stale result cannot sneak back in.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why not just call ConcurrentHashMap.computeIfAbsent(key, loader)?
It is single-flight only while loads succeed. The loader runs while holding the lock on that key's bin, so other keys in the bin wait, and so does remove: your invalidate stalls behind a slow load. When the loader throws, the callers blocked on the bin are let in one by one and each runs the loader again, so a stampede turns into a queue of sequential loads against a backend that is already failing. The documentation also asks for short mapping functions that do not touch the map. Storing futures moves the load out of every lock. The tests in this problem catch the one-line version.
Add a time to live.
Store the expiry time with the entry and treat an expired entry as absent. The first caller that sees it expired replaces it atomically (replace(key, old, fresh) in Java, or compare the load id under the mutex) and loads, so expiry is single-flight too. Others either wait for the new value, or keep returning the stale one while a single refresh runs, which keeps latency flat (serve stale, also called stale-while-revalidate). Add random jitter to TTLs so keys loaded together do not all expire together. This is the per-instance half of the Rubrik two-tier refresh.
What happens if a loader hangs?
Every caller waiting for it hangs too. Bound the wait: orTimeout or get(timeout, unit) in Java, wait_for on the std::shared_future in C++. Then decide what a timeout means: fail only that waiter, or fail the whole flight and remove the entry so the next caller retries. A timeout should also cancel the backend call if the client library allows it, or the hung loads pile up.
Many servers share one remote cache. How do you get one load per key across all of them?
In-process single flight gives at most one load per key per server. Across servers, the first server to miss takes a short lease on the key in the shared store (for example a set-if-absent with an expiry and a unique token), refreshes the value, and releases it; the others wait and re-read, or serve stale. The lease must expire so a crashed holder cannot block the key forever, and if a late write could overwrite a newer value, use a fencing token. That is the cross-instance half of the Rubrik question.
The cache grows without bound. What changes when you add LRU eviction?
Eviction removes an entry exactly as invalidate does, so the same reasoning holds: callers already waiting hold the future and still get their answer, and the finished load cannot re-insert itself. Usually only completed entries are eviction candidates, so an in-flight load does not count against the budget for long. Combine this with the thread-safe LRU cache.
Does every waiter get the same exception object, and is that a problem?
With CompletableFuture each waiter gets its own CompletionException wrapping the same cause; with std::shared_future the same exception object is rethrown in every thread. Both are fine as long as nobody mutates the shared exception (for example by adding suppressed exceptions to it from several threads). If callers need their own stack traces, wrap the cause in a new exception per caller.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Make the cache entry a future, the pattern Java Concurrency in Practice calls the Memoizer. A key is in one of three states: absent, in flight (an unfinished future) or cached (a finished future). The invariant: for each key the map holds at most one entry, and an entry is either a successful finished future or the unfinished future of the one load in flight. Since a miss can only become a load by inserting the future atomically, at most one load per key can be in flight.

Why each line is there

  • putIfAbsent(key, mine), or the insert under the mutex. This is the election. Exactly one caller wins and loads; everyone who loses gets the winner's future back.
  • The loader runs outside every lock. Holding a lock during a load would make hits and loads of other keys wait behind the slowest backend call. Only the map operations are inside the lock, and they take microseconds.
  • Remove, then complete exceptionally. If you completed first, a new caller could find the failed future in the map and receive a stale failure. Removing first means later callers start a fresh load, while the callers already holding the future still see this failure.
  • Remove only your own entry. Between your miss and your failure, someone may have called invalidate and a newer load may have inserted its own future. remove(key, mine) (or comparing the load id) leaves that newer entry alone.
  • invalidate removes the future, not just a value. The timeline below shows why the entry must be the future itself.

Cost and trade-offs

A hit is one map lookup and a read of a completed future. A miss adds one atomic insert and one future. Memory is one future per key, which is why real caches bound the size with eviction. With ConcurrentHashMap the reads take no lock at all; the C++ version uses one mutex for the map, held only for lookups and inserts, and could be striped exactly like the striped hash map if that mutex ever became hot.

How to say it in the interview

The cache entry will be a future, not a value. On a miss, a caller atomically inserts an unfinished future with putIfAbsent; whoever wins runs the loader with no lock held and completes the future, and everyone else just waits on it, so there is one load per key no matter how many threads miss. A failure is never cached: the loader removes its own entry, then completes the future exceptionally so the current waiters all see the same failure and the next caller retries. Invalidate just removes the entry, and because the entry is the future, a slow load that finishes later cannot write a stale value back.
