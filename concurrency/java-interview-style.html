Writing Java in an interview

A template for thread-safe classes, lock and condition idioms, interrupt handling, the compile errors that cost rounds, and how to talk while coding.

Asked atRubrikLinkedIn
Before this:Exceptions, InterruptedException and try-with-resourcesTime: nanoTime, Duration and TimeUnit

In a concurrency round the code has to compile, run, and survive the interviewer's follow ups, all in about 45 minutes. Fluency in a handful of idioms is what buys you the time to think about the actual race.

In plain words

Before a busy service, a good cook sets out their mise en place: every ingredient chopped and waiting in the same bowl, in the same spot, every day. During the rush their hands move without thinking, and their attention stays on the orders. The class template, the lock idiom and the wait loop in this lesson are your mise en place: typed the same way every time, so your head stays free for the interleavings.

Why this matters for concurrency

  • Rubrik usually expects code that runs in CoderPad, and one candidate fixed the deadlock in a debugging round but lost the round to a compile error. Libraries such as ExecutorService and BlockingQueue are often banned there, so you write the locks and conditions yourself.
  • LinkedIn's concurrency round expects working code, and one 2024 loop allowed only plain threads with wait and notify, plus a graceful shutdown.
  • Clean code is not enough on its own. An Uber interviewer complained that candidates "put synchronization everywhere", LinkedIn interviewers asked candidates to name the race each lock prevents, and a Google L5 candidate who named all the right tools still got a No Hire and concluded that precise reasoning about the races was what counted. You have to narrate.

The template for a thread-safe component

Almost every concurrency coding question is a small class that several threads share: a queue, a pool, a cache, a limiter, a scheduler. Start every one of them from the same skeleton:

Eight habits are baked into it. Make them reflexes:

  1. A one-line policy comment at the top saying what guards what. It tells the interviewer you have a policy, and it keeps you honest.
  2. private final for the lock, the conditions and the collections, and a "guarded by lock" comment on every mutable field. (The @GuardedBy annotation you may have seen comes from outside the JDK; a comment works everywhere.) A private lock also means no outside code can lock your object by accident.
  3. lock() just before try, unlock() in finally, in every method that touches the state, readers included.
  4. Every wait in a while loop, re-checking the condition after each wakeup.
  5. Conditions named after the state a waiter needs: notEmpty.await() reads as "wait until not empty", and notEmpty.signal() as "it is no longer empty".
  6. Signal after the state change, while holding the lock.
  7. Blocking methods declare throws InterruptedException, and nothing swallows it.
  8. A way to stop: close() sets a flag under the lock and wakes every waiter, and the waits check the flag.

One platform detail: a Java file may contain only one public top-level class, named like the file. In CoderPad or a similar pad, leave your own classes package-private (no public) next to the platform's main class.

Say the choice and the reason in one sentence: "I'll use a ReentrantLock because I need two conditions, not full and not empty; with synchronized there is one wait set, so I would have to notifyAll on every change." If only wait and notify are allowed, the same queue looks like this:

The rule for signal versus signalAll: signal (or notify) is safe only when every thread waiting on that condition waits for the same thing, and one state change lets exactly one of them proceed. Otherwise use signalAll. With synchronized, producers and consumers share one wait set, so notifyAll is the default, which is the subject of lost wakeups and notifyAll.

The idioms, typed the same way every time

InterruptedException in interview code

  • Methods of your component that block (put, take, acquire, await): declare throws InterruptedException. The caller decides.
  • Worker lambdas, which are Runnables and cannot throw it: catch it, restore the flag with Thread.currentThread().interrupt(), and exit the loop.
  • main and test drivers: write public static void main(String[] args) throws Exception and skip the ceremony.
  • Tasks that should return or throw: make them Callables. pool.submit(() -> queue.take()) compiles, because the lambda becomes a Callable, which may throw.

Never add an empty catch (InterruptedException e) {} just to make the compiler quiet. Interviewers notice, and it breaks shutdown; the exceptions lesson shows exactly how.

How to talk while you code

Interviewers grade the reasoning they can hear. A script that works:

  1. Pin down the semantics (one or two minutes): blocking or not, capacity, timeouts, what shutdown means (drain the queue or drop it), fairness, and whether java.util.concurrent is allowed.
  2. State the invariant and the policy out loud: "the deque and the closed flag are guarded by one lock; the size never exceeds the capacity".
  3. Name the waits: "producers wait for not full, consumers wait for not empty".
  4. Write from the template, narrating decisions, not syntax: "lockInterruptibly, so a blocked producer can be cancelled", not "now I open a brace".
  5. Walk one risky interleaving, such as two consumers and one item, and show why the while loop handles it.
  6. Test it: a quick single-thread check, then a stress run with several threads, an invariant check at the end, and joins with timeouts so a deadlock shows up as a failure instead of a hang.
  7. Offer the follow ups before you are asked: timeouts, shutdown, fairness, and performance (two locks as in LinkedBlockingQueue, or striping).

When you are stuck, say so productively: "let me get a correct single-lock version first, then optimize." Name the race each lock prevents ("this lock stops two consumers from removing the same item"), and leave confined or immutable data unlocked on purpose, saying why.

Worked example: a complete answer, runnable

The task: "Three workers process tasks from a shared queue. A task may throw. When the producer is done, everything submitted must still run, and then the workers must exit." This is the template above plus a driver that tests it the way you would in the round.

What to say while writing it: the queue's policy (one lock, one condition, a closed flag), why close uses signalAll (every worker must wake and see it), why take returns null only when closed and empty (so the workers drain the queue before exiting), why the worker catches Throwable around each task and restores the interrupt flag, and why the test checks timed joins and uses daemon workers only as a test failure guard. Successful completion still requires every worker to finish and the task totals to match. That covers correctness, shutdown, failure handling and testing in about 90 lines.

Common mistakes

  • Clever lock-free code you cannot justify. One Databricks report (low confidence) describes a lock-free attempt that nearly sank a candidate while a plain synchronized version passed. Correct first, then fast.
  • Locking everything. Locks on immutable or thread-confined data add contention and suggest you have not found the real shared state.
  • No shutdown path. Workers that can never exit, and a test that hangs at the end.
  • Thread.sleep in the test driver to "wait for the threads". Use join with a timeout, a latch or futures.
  • Starting a thread inside a constructor. The thread can see the object before the constructor finishes: this escape.
  • Calling unknown code while holding your lock: listeners, callbacks, user tasks. It invites deadlocks and long holds. Copy what you need under the lock and call outside it.
  • if instead of while around a wait, and signal where waiters wait for different things. The first can let a thread proceed on a false predicate; the second can strand a thread that could proceed.
  • Slow I/O inside a critical section. Every other thread waits for the network.

In the interview

Rounds are graded on correctness under concurrency first (no races, no deadlocks, no lost wakeups), then clarity, then how you handle the follow ups. Rubrik reports name shutdown semantics, interrupts and exception handling as graded points; LinkedIn interviewers asked for the race behind each lock; and a Google report suggests that reasoning about guarantees mattered more than naming tools.

Before I code: put never blocks here, take blocks while the queue is empty, and close wakes everyone so the workers can drain and exit. One ReentrantLock guards the deque and the closed flag, with a notEmpty condition. Every wait is in a while loop, and the blocking method throws InterruptedException so callers can cancel it.
This lock is there so that two consumers can never both see the last item and both remove it. The counter outside it is an AtomicInteger because it is a single variable that no invariant ties to the queue.
To test it, I'll run several producers and consumers, check that every item arrives exactly once, and join with a timeout, so a deadlock or a lost wakeup shows up as a failure instead of a hang.

Follow ups to expect on the task queue. "Why signal in put but signalAll in close?" (every waiter waits for the same thing and one item lets exactly one taker through, but close must release all of them). "Make put block when the queue is full." (add a capacity and a notFull condition; put waits on it in a loop and take signals it). "Add poll(timeout)." (an awaitNanos loop that waits only for the remaining budget). "Why not synchronized?" (with one condition it would also be correct; I chose ReentrantLock for lockInterruptibly and so that notFull is one line away). "What if a task never returns?" (that worker is lost; per-task timeouts need futures and cancellation, and the task itself must respond to interrupts).

Senior depth

The checklist a strong interviewer runs over your code, which you can run first:

  • Is every piece of shared mutable state identified, and is each guarded by exactly one lock, with one lock per invariant?
  • Is any lock held across I/O, a sleep, or a call into unknown code?
  • Is every wait in a loop, on a condition named for the state it needs, with the right choice of signal or signalAll?
  • What is the interrupt policy, and does shutdown wake every waiter and say whether queued work is drained or dropped?
  • Are queues bounded, and what happens when one is full (block, time out, reject)?
  • Do the tests stress the code with many threads, check invariants, and fail instead of hanging?

Then state the contention profile ("every producer and consumer serializes on one lock") and offer the next step only after correctness is settled: two locks for head and tail, striping by key, or a lock-free structure if the interviewer wants to go there.

Key takeaways

  • Start every shared class from the template: policy comment, private final lock and conditions, guarded fields, lock and try and finally, while-loop waits, InterruptedException declared, a close path.
  • Choose synchronized for simple exclusion and ReentrantLock for several conditions, timeouts, interruptible acquisition or fairness, and say why in one sentence.
  • Know the javac messages for checked exceptions in lambdas, effectively final captures and missing returns, and the run-time traps: wait on a Condition, unlock without the lock, run instead of start.
  • Narrate decisions and name the race each lock prevents; test with stress, invariants and join timeouts.

Quick check

Answer each question, then read why. Your score is saved for your module test.

This compiles. What happens when the queue is empty?
Why. A Condition is an object, so it inherits wait, notify and notifyAll from Object, and the code compiles. Those methods require holding the object's monitor through synchronized, which this thread does not, so they throw. The Condition methods are await, signal and signalAll.
Where should lock.lock() go?
Why. If acquiring fails (for example lockInterruptibly() throwing InterruptedException), a finally that unlocks would release a lock this thread does not hold, throwing IllegalMonitorStateException and hiding the real exception. Placing lock() just before try means the finally runs only once the lock is really held.
A test creates Thread t = new Thread(task, "worker") and calls t.run(). What happens?
Why. run() is an ordinary method call. Only start() creates the new thread, which then calls run(). The mistake is silent: the output looks right, and the test exercises no concurrency at all.
javac reports "local variables referenced from a lambda expression must be final or effectively final" for for (int i = 0; i < n; i += 1) pool.submit(() -> work(i));. What is the cleanest fix?
Why. The lambda captures a copy of the value, so Java requires the variable never to change after capture, and the loop counter changes. A fresh local per iteration is effectively final and gives each task its own value. A static field would compile but share one changing variable among all tasks, a real bug.
You are building a bounded buffer where producers wait while it is full and consumers wait while it is empty. Which choice fits best, and why?
Why. Two conditions separate the waiter groups; then signal on notEmpty selects a consumer, never a producer. A single condition with signalAll would also be correct. With synchronized there is one wait set, so notify can wake the wrong kind of thread and lose the signal; notifyAll would be correct there, but it wakes everyone.
Producers and consumers wait on the same single Condition, changed. After adding an item, a producer calls changed.signal(). What can go wrong?
Why. signal does not select by the predicate a thread needs. A ReentrantLock condition signals in FIFO order, so even its oldest waiter can be the wrong kind. If waiters on one condition wait for different things, the woken thread may re-check, find it cannot proceed, and wait again, and the signal is spent. Use signalAll, or give each kind of waiter its own condition.
int take() { try { return queue.take(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } } does not compile. Why, and what is the best fix?
Why. Every path of a method that returns int must return or throw, and the catch path does neither. For a blocking method of your own component, declaring throws InterruptedException is cleanest, because the caller decides. If you must catch, restore the flag and then throw an exception or return a value the caller treats as "stopped".

Write code

Model answer

Why it is right: one lock guards the single invariant, 0 <= count <= max. Two conditions mean each kind of waiter has its own queue, so signal is safe: every waiter on aboveZero waits for the same thing, and one increment lets exactly one decrement through. Both waits are while loops, so spurious and stolen wakeups are harmless. Design
The interviewer says: "Implement a thread-safe job queue that worker threads pull from, with shutdown." Say, as you would out loud, what you clarify and state in the first three minutes, before writing code.
Model answer

Clarify: is the queue bounded, and if so, should submit block, time out or reject when it is full? Does shutdown mean finish everything already queued, or stop as soon as possible and return the unstarted jobs, like shutdown versus shutdownNow? What happens to submit after shutdown, an exception or a rejected result? Do callers need a result or failure per job, so a future? May I use java.util.concurrent, or should I build it from locks?

Then state the plan: "One ReentrantLock guards the deque, the size and the shutdown state. Workers wait on a notEmpty condition, and if it is bounded, submitters wait on notFull. Every wait is a while loop. Shutdown sets a flag under the lock and calls signalAll on both conditions, so every blocked thread wakes and sees it; take returns a sentinel once the queue is shut down and drained, so workers exit cleanly. For shutdownNow I also interrupt the workers, and their loop treats an interrupt while waiting as the stop signal. A failing job is caught around the job, as Throwable, and reported through its future, so it never kills a worker. I'll test with several submitters and workers, check that every job runs exactly once, and join with timeouts."

Debug
Find every problem in this snippet (assume the imports are present): the compile errors first, then the bugs that would survive compilation.
Model answer

Compile errors. One: the lambda uses the loop counter i, which changes every iteration, so javac says "local variables referenced from a lambda expression must be final or effectively final"; copy it first with final int id = i; and name the thread with it. Two: hasJob.await() throws InterruptedException, which a Runnable lambda cannot throw ("unreported exception InterruptedException; must be caught or declared to be thrown").

Bugs that survive compilation once those are fixed. Three: t.run() instead of t.start(): the first worker's endless loop runs on the calling thread, start never returns, and no other worker is ever created. Four: lock() and unlock() are not in try and finally, so any exception, including the InterruptedException from await, leaves the lock held forever. Five: there is no shutdown path; the while (true) loop can never end, and the interrupt handler must restore the flag and leave the loop. Six: nothing ever adds a job; a submit method must take the lock, add the job and call hasJob.signal(). Seven: job.run() is rightly outside the lock, but an exception from a job escapes and kills the worker, so it needs a catch (Throwable t) around it. And the threads have no names, which will hurt the first time you read a thread dump of this pool.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 105 s
"Design a bounded Java job queue with graceful shutdown. Before you type, talk me through the contract, the synchronization and how you would test it."
What a strong answer covers
  • Clarify allowed libraries, full-queue behaviour, shutdown semantics and job failure reporting
  • State one lock for the deque and closed flag, with size between zero and capacity
  • Choose two conditions, acquire interruptibly before try, wait in while loops and unlock in finally
  • After mutations signal the opposite waiter group; close wakes both groups, rejects producers and lets consumers drain
  • Run jobs outside the queue lock and handle task failures separately from worker cancellation
  • Test capacity-one contention, exact item identities, shutdown races and interruption with bounded test termination
How a senior would say it
I would start with one lock guarding the queue and its closed flag. Before coding, I would confirm whether library queues are allowed, whether a full queue blocks or rejects, whether shutdown drains accepted work, and how job failures are reported. Assuming we build it ourselves with blocking submission and graceful drain, the invariant is that the size stays between zero and capacity. I would use a private ReentrantLock with conditions named not empty and not full. Blocking methods acquire interruptibly before entering the try block and always unlock in finally. Producers wait while full and open; consumers wait while empty and open. Both waits use while loops because waking does not reserve a slot or an item. An insertion signals a consumer, and a removal signals a producer. Close sets the flag under the same lock and wakes both groups. A producer checks closed again after waiting and rejects if necessary. Consumers keep taking queued jobs, then receive an end marker only when closed and empty. That also resolves a submit racing with close at the shared lock. Workers run jobs outside the queue lock, report task failures, and treat interruption as a separate cancellation decision. I would test capacity one, several producers and consumers, exact job identities, a failing task, interruption, and close racing with submission. Tests need timed joins plus a failure path that terminates the test process; a timeout alone does not stop stuck workers.

Likely follow up: How would immediate shutdown differ, especially for a job already running or one just removed from the queue?

Out loudabout 75 s
"Why did you choose ReentrantLock for this bounded buffer? Could you write a correct version with synchronized, and what would you lose?"
What a strong answer covers
  • Both choices provide mutual exclusion and visibility when all guarded accesses follow the same locking policy
  • ReentrantLock supports separate notFull and notEmpty conditions for targeted signalling
  • A synchronized version uses one wait set with while-loop waits and notifyAll for mixed waiters
  • Explicit locking supports timed or interruptible acquisition; Object.wait is interruptible but monitor acquisition is not
  • Fair mode favours the longest-waiting acquirer, costs throughput and does not guarantee scheduling or cover untimed tryLock
How a senior would say it
Both can implement a correct buffer. I chose ReentrantLock because producers and consumers wait for different predicates, so two conditions make targeted signalling straightforward. One lock still protects the whole invariant, and readers follow the same policy as writers. With synchronized methods, I would keep the same guarded state and while-loop checks, but use the object's single wait set. After a change, I would use notify all so waking a producer when only a consumer can proceed cannot strand the queue. The tradeoff is extra wakeups and competition to reacquire the monitor. Explicit locking also gives me interruptible acquisition and timed acquisition. Object wait itself is interruptible, but a thread waiting to enter a synchronized block cannot cancel that acquisition through interruption. If fairness is required, a fair lock favours the longest-waiting acquirer, usually at a throughput cost. It does not control thread scheduling, and untimed try lock can still barge. I would choose based on those requirements and explain the policy, rather than assume one keyword or class is universally faster.

Likely follow up: If several producers submit batches of different sizes, is signalling one producer on notFull still sufficient?

Out loudabout 90 s
"A worker lambda captures a changing loop index and calls await. After some quick compile fixes, starting the workers never returns. How would you review this code out loud?"
What a strong answer covers
  • Copy the loop index into a final or effectively final local for each worker
  • A Runnable cannot propagate InterruptedException; restore the flag and exit at the worker boundary
  • Check for run instead of start, which executes the endless worker loop on the caller
  • Acquire before try, release in finally, and recheck the predicate after await reacquires the lock
  • Run jobs outside the lock, report task failures and provide a close protocol that wakes waiters
  • Verify worker identities, completion and interruption with timed joins and a bounded test failure path
How a senior would say it
I would separate the compile errors from the lifecycle bugs. First, a changing loop index cannot be captured by the lambda. I would copy it into a final local inside each iteration and use that value to identify the worker. Second, await throws a checked interruption exception, but a Runnable cannot declare it. At the worker boundary I would catch it, restore the interrupt flag and exit, rather than continue an endless loop. For the symptom that starting never returns, I would check whether the code calls run instead of start. Run executes on the caller, so the first worker can trap the caller before any other worker is created. Next I would inspect lock ownership. Acquisition belongs before try, unlocking belongs in finally, and the wait belongs in a while loop. Await releases the lock and reacquires it before returning or throwing an interruption exception. After removing a job, I would release the lock before running it and report any task failure. I would also require a close path that wakes idle workers and defines whether queued work drains. Finally, I would verify actual worker identities, job completion and interruption. Timed joins detect stalls, but the test also needs daemon workers or a bounded process exit on failure.

Likely follow up: Why can catching an interruption, restoring the flag and then continuing the same await loop turn into a busy loop?
