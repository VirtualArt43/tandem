What a thread costs, and why more threads can be slower

Stacks, creation time and scheduler load: what each thread really costs, and the four reasons adding threads can make a program slower.

Asked atMetaDatabricksRubrik
Before this:Thread states and what blocking really does

Threads look free in code: one line starts one. They are not. Each costs memory, creation time and scheduler work, and past a certain point every extra thread makes the program slower. Interviewers probe this with "how many threads would you use?" and "why did adding threads make it worse?"

In plain words

A restaurant hires more cooks for the dinner rush. Each new cook needs a locker and a uniform (memory), takes time to hire and train (creation), and needs the head chef's attention (scheduling). That is the fixed cost of each cook.

Then the kitchen gets crowded. With four stoves, the fifth cook mostly waits for a stove. Cooks bump into each other and keep putting down and picking up each other's utensils. They queue for the one tandoor. And the vegetable supplier can deliver only so fast. Past a point, every new cook makes dinner slower, not faster.

When a limit is hit, thread creation fails. Java throws an OutOfMemoryError whose message says it was unable to create a native thread, even when the heap has plenty of room. In C++ the std::thread constructor throws std::system_error. Both usually mean the design creates threads without a bound, not that the machine is too small.

Reserved is not the same as used

Stacks are reserved in virtual memory. Reserving a megabyte of addresses costs almost nothing; the operating system backs a page with physical memory only when the thread first touches it. A thread with shallow calls touches a small part of its stack, so 10,000 Java threads reserve about 10 GB of address space but use far less real memory. On a 64-bit machine, reserving 10 GB of addresses is usually allowed.

So the memory cost of threads is real but smaller than the headline number. What does not shrink: the kernel stacks and structures, the pages each stack really uses, the per-thread buffers your own code allocates, and the work the garbage collector and the scheduler do per thread. And some systems do count reservations: Linux with strict overcommit (vm.overcommit_memory=2) refuses reservations that exceed its commit limit.

Measure it here

Where the time goes: on Linux, creating a thread means a stack and guard page (mapped with mmap, or reused from glibc's cache of recently freed stacks), a clone system call that makes a new kernel task sharing the process's memory, and setting up its thread-local storage; the JVM then adds its own per-thread structures. Joining means waiting for the kernel to report that the thread has exited. This program starts and joins 2,000 threads that do nothing at all, one after another, and reports the average cost of each.

The output above is Java on this Mac; C++ printed about 25 µs here under ThreadSanitizer, which the Run button uses, and about 15 µs in a normal optimized build. So an empty thread costs tens of microseconds, as an order of magnitude. If each task is a 5 µs cache lookup, creating a thread per task spends several times longer on the thread than on the work. Handing the task to a thread that already exists costs one wake-up, a few microseconds (lesson 01-04), which is a big part of why thread pools exist.

Choosing a stack size

Usually you leave the default alone. You change it in two situations: many threads that only make shallow calls (a smaller stack saves address space), or one thread that recurses very deeply, such as a recursive descent parser (a larger stack avoids an overflow). Java sets it for every thread with -Xss, or per thread when you create it. Standard C++ gives std::thread no option at all, so you use POSIX threads directly.

The Java version catches StackOverflowError to show how deep each stack let the recursion go; the depths change from run to run as the JIT compiler shrinks the frames. C++ cannot recover from a stack overflow (the program simply crashes), so the C++ version prints the default size for new threads, 512 KB on this Mac and commonly 8 MB on Linux, and then runs a recursion that needs about 5 MB safely on a 16 MB stack. On the default 512 KB stack the same recursion would crash. One caution: the Java documentation allows the JVM to treat the requested size as a hint, and on some platforms to ignore it.

Four reasons more threads can be slower

Being able to name all four, with the mechanism for each, is a strong senior signal.

  1. Context switch overhead. Once runnable threads outnumber cores, the scheduler time slices them, and every context switch costs about a microsecond of kernel work. This is oversubscription, and it shows as rising involuntary switches with flat throughput.
  2. Cache and TLB pollution. Every thread that runs on a core drags its own data into the caches and pushes the previous thread's out. With a few threads per core, each one finds its data still warm. With dozens, each runs cold after every switch, and memory stalls eat the time you hoped to gain. A switch between threads of one process does not flush the TLB, but their different working sets still compete for its few entries.
  3. Lock contention. More threads hitting the same lock means longer queues at it. Each handoff of a contended lock is a sleep and a wake-up, so the lock spends more of its time being passed around than being used: a lock convoy. The critical section is serial no matter how many threads wait for it, so contention caps the speedup and then makes it worse.
  4. Downstream amplification. Every thread that calls a database or a service adds load to it. Past its capacity, its latency rises for everyone, so your threads block longer, so it looks as if you need even more threads, which pushes it harder still. This is how a thread pool becomes a weapon against your own database.

Two more costs ride along: memory (stacks, per-thread buffers, ThreadLocal caches multiplied by the thread count) and, in Java, more garbage collection work, because every collection has to scan every thread's stack for references.

The first three grow with the thread count, and the coordination costs among them (threads waiting on each other at a lock, shared cache lines bouncing between cores) can grow faster than linearly, because they scale with the number of pairs of threads that interact. The Universal Scalability Law models exactly this: it extends Amdahl's law with a cost for every pair of threads that must coordinate. Amdahl alone says throughput flattens; add coordination and it falls.

Both curves assume 5 percent of the work is serialized; the lower one also charges a small cost for every pair of threads that has to coordinate. The coefficients are made up to show the shape, not measured. In real systems you find your own peak by measuring throughput as you add threads, and you stop where it flattens: the right thread count is a measurement, not a guess.

How you see these costs on a live system

On Linux, ps -o nlwp= -p PID or the Threads: line of /proc/PID/status gives the thread count; in Java, jcmd PID Thread.print lists every platform thread. Each thread's own /proc/PID/task/TID/status counts voluntary_ctxt_switches (the thread blocked, on a lock or I/O) and nonvoluntary_ctxt_switches (the scheduler preempted it); pidstat -wt -p PID 1 shows both rates for every thread each second, and the cs column of vmstat 1 shows the system wide rate. Rising involuntary switches with flat throughput means oversubscription; rising voluntary switches means threads are blocking, often at a hot lock.

So how many threads?

  • CPU bound work: about the number of cores. More only adds the costs above. In Java, Runtime.getRuntime().availableProcessors() counts logical CPUs and respects a container's CPU limit; in C++, std::thread::hardware_concurrency() is only a hint, may return 0, and does not know about a container's CPU quota, so read the limit from configuration when it matters.
  • I/O bound work: cores × (1 + W/C) to keep the CPU busy (lesson 01-03), capped by what the dependency can take.
  • Reuse threads with a pool, so you pay creation once, and so the pool size doubles as a limit on concurrency.
  • Tens of thousands of mostly idle connections: do not give each its own kernel thread. Use an event loop, or virtual threads in Java 21 (next lesson).

As an order of magnitude: a well behaved service runs somewhere between a few hundred and a few thousand kernel threads. Tens of thousands are possible with tuning; hundreds of thousands are rarely practical.

Worked example: two ways to get it wrong

Thread per connection at 50,000 connections. A chat gateway keeps 50,000 websocket connections open, each with its own Java platform thread that blocks reading its socket. On x86-64 Linux that reserves about 50 GB of stack address space (50,000 × 1 MB) and keeps about 800 MB of kernel stacks resident (50,000 × 16 KB). Creating the threads costs about 1.5 seconds of CPU (50,000 × 30 µs), every garbage collection walks 50,000 stacks, and the process is at or past default limits such as vm.max_map_count. Yet 99 percent of the connections are idle at any moment. The fix is not a bigger machine: an event loop, or a virtual thread per connection, holds an idle connection in kilobytes.

The pool that got slower. An image resizing service runs on 16 cores with a pool of 16 threads. Under load someone raises the pool to 256. Throughput drops and p99 latency doubles. Why: the work is CPU bound, so 240 extra threads only time slice the same 16 cores (reason 1); each switch evicts the image data another thread was working on (reason 2); and 256 large image buffers in flight instead of 16 multiply the memory held and the garbage collector's work. Back to about 16 threads, plus a bounded queue in front, and the service recovers.

Common mistakes

  • Creating a thread per task in a loop. Tens of microseconds per thread, and no limit. Use a pool, or virtual threads for blocking tasks.
  • "A bigger pool fixes high latency." If the work is CPU bound, or the bottleneck is a lock or a dependency, a bigger pool makes latency worse.
  • Shrinking -Xss to fit more threads. It moves the failure from "cannot create thread" to StackOverflowError in some deep call path. Fix the thread count instead.
  • Unbounded thread creation. In Java, Executors.newCachedThreadPool() has no upper limit and starts a new thread whenever none is idle; under a burst of slow tasks it can create thousands.
  • Reading reserved memory as used memory. 10,000 threads do not consume 10 GB of RAM. They do consume kernel memory, scheduler time and GC work, which is what you should count.

In the interview

It appears as a sizing question inside other problems. A Meta design round on a file downloader asked how many threads the candidate would want and what a safe number is. A Databricks crawler round asked about thread pool size against dataset size, and disk and network bottlenecks; another asked how the candidate knew multithreading would help at all. A Rubrik screen asked how a delayed task runner would handle a large number of threads, and insisted that any executor be built by hand.

Threads are a way to use capacity, not to create it. Each one costs a stack reservation, kernel memory, tens of microseconds to create, and scheduler and cache pressure. Once the bottleneck is saturated, whether that is the CPU, a lock or a downstream service, every extra thread only adds switching, cache misses and queueing. So for CPU work I size to the cores, for I/O work I size to what the dependency can serve, I reuse threads through a bounded pool, and I measure throughput as I change the size rather than guess.

Follow ups to expect: "Why not a thread per request?" (creation cost, no bound, memory and switching at scale); "Name the reasons more threads can be slower" (switching, cache pollution, lock contention, downstream amplification); "What happens at 100,000 connections?" (a kernel thread each is impractical; use an event loop or virtual threads); "How do you know more threads will help?" (find the bottleneck first: if the cores are already busy or a lock is hot, they will not; if threads mostly wait on I/O and the dependency has headroom, they may; then measure throughput as you add them).

Senior depth

Some per-thread costs hide in libraries. glibc's malloc gives threads separate memory arenas to reduce lock contention, allowing up to eight times the number of cores on 64-bit systems; with many threads, a Java or C++ process can show much higher resident memory than its heap suggests. Capping arenas with the MALLOC_ARENA_MAX environment variable is a known fix for such services. Likewise, every ThreadLocal cache, every per-thread buffer and every per-thread connection is multiplied by the thread count, which matters a lot once threads become cheap.

In Java, the garbage collector must find every reference on every thread's stack, so its work grows with the number of threads and the depth of their stacks. G1, the default collector, does that scanning inside its stop-the-world pauses; ZGC does most of it concurrently, but the work still has to be done. A service with thousands of deep, idle platform threads pays for them on every collection, not just at creation.

Key takeaways

  • A thread costs a stack reservation (512 KB to 8 MB by platform), kernel memory, tens of microseconds to create, and scheduler work.
  • Reserved stack is not used memory; count kernel memory, touched pages, per-thread buffers and GC work instead.
  • More threads can be slower: context switches, cache pollution, lock contention and downstream amplification.
  • CPU work wants about one thread per core; I/O work wants what the dependency can serve; both want reuse and a bound.
  • The right thread count is found by measuring throughput as you change it.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A Java service on x86-64 Linux runs 10,000 platform threads with the default stack size. How much stack address space do they reserve?
Why. The default -Xss there is 1 MB, so 10,000 threads reserve about 10 GB of addresses. The operating system backs pages only when they are touched, so resident memory is much lower. The real per-thread costs are kernel memory, touched pages, scheduling and GC scanning.
Roughly how long does it take to create, start and join a platform thread that does nothing, on a modern machine?
Why. Creating a thread involves system calls, allocating and mapping a stack, and kernel and runtime bookkeeping: on the Mac Tandem runs on, about 15 to 35 µs. That is cheap once, and expensive per task when the tasks are small, which is why pools reuse threads.
Which of these is NOT one of the reasons that adding threads can make a program slower?
Why. The heap is shared by all threads of a process and is not divided among them, and objects are not copied between threads. The other three are real mechanisms, and together with downstream amplification they make up the four reasons.
A service's throughput rises as you go from 1 to 24 worker threads, then falls steadily as you add more. Which explanation fits best?
Why. Amdahl's law only explains a curve that flattens. A curve that falls needs a cost that grows with the number of threads, which is what the Universal Scalability Law's coordination term models. In practice: hot locks, shared cache lines bouncing between cores, and oversubscription.
A chat server keeps 50,000 websocket connections open, mostly idle, with one kernel thread per connection blocked on a read. What is the main problem?
Why. Each idle connection pins a whole kernel thread: a stack reservation, a resident kernel stack, scheduler state, GC scanning in Java, and creation cost. The connections themselves are cheap. An event loop or a virtual thread per connection holds the same idle connection in kilobytes.
Java onlyA Java service submits 20,000 slow, blocking tasks in a burst to Executors.newCachedThreadPool(). What happens?
Why. A cached thread pool has a core size of 0, a maximum of Integer.MAX_VALUE, and a SynchronousQueue that holds nothing, so every task that finds no idle worker gets a new thread. Under a burst of slow tasks that means thousands of threads and, eventually, an OutOfMemoryError saying a native thread could not be created. Bound it, or use virtual threads with a semaphore.
C++ onlyThe operating system refuses to create another thread, because a limit has been reached. What does std::thread t(work); do?
Why. The standard says the constructor throws std::system_error if the thread cannot be started, and names resource_unavailable_try_again as a typical condition. Code that creates threads in a loop must expect this, which is one more argument for a bounded pool.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
A team plans thread per connection for a Java service on x86-64 Linux that must hold 20,000 concurrent connections. Estimate the stack address space, the kernel stack memory and the total creation time, say what else will hurt, and propose an alternative.
Model answer
  • Stack address space: 20,000 × 1 MB, about 20 GB reserved. Resident memory is much less, but it grows with how deep each thread's calls go.
  • Kernel stacks: 20,000 × 16 KB, about 320 MB, always resident.
  • Creation: 20,000 × about 30 µs, about 0.6 seconds of CPU. Acceptable once, but painful if connections churn quickly.

What else hurts: thread count limits (ulimit -u, pids.max in a container) sit uncomfortably close; every garbage collection must scan 20,000 stacks; per-thread buffers multiply (a 64 KB read buffer per connection is another 1.3 GB); and when traffic bursts and thousands of threads become runnable at once, the scheduler thrashes.

Alternative: most connections are idle most of the time, so they should not each hold a kernel thread. Use non-blocking I/O with an event loop (Netty style) and a small, bounded worker pool for real work, or, on Java 21, a virtual thread per connection, which keeps the simple blocking code while an idle connection costs kilobytes. Either way, keep an explicit limit on how many requests do expensive work at once.

Explain
An engineer doubled a CPU bound worker pool from 32 to 64 threads on a 32 core machine, and throughput fell by 10 percent. Explain why, with at least three mechanisms, and say what you would do.
Model answer

The work was CPU bound, and 32 threads were already enough to keep all 32 cores busy, so the extra 32 threads added no computing capacity. They added costs instead:

  • Oversubscription: 64 runnable threads on 32 cores means constant time slicing and involuntary context switches, each a microsecond or so of kernel work.
  • Cache pollution: each switch brings in another thread's working set, so threads keep running with cold caches and stall on memory.
  • Contention: if the workers share anything, a queue, a counter, a lock, twice as many threads fight over it, and a contended lock handoff costs sleeps and wake-ups.
  • Memory: twice as many in-flight tasks means more live buffers and more work for the garbage collector.

What I would do: go back to about 32 threads (one per core, perhaps one or two fewer to leave room for the garbage collector and the OS), and confirm with measurements: throughput against pool size, the involuntary context switch rate, and CPU utilization. If throughput is still short, the levers are the work itself (profiling, better algorithms, less shared state) or more machines, not more threads.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"We raised a worker pool from 32 to 256 threads and throughput fell. Which of the reasons more threads can be slower is it, and how would you tell them apart?"
What a strong answer covers
  • Each reason leaves a different fingerprint, so measure instead of guessing
  • Cores pegged and involuntary context switches up: oversubscription and cache pollution
  • Cores not full, voluntary switches up, dumps parked at one lock or queue: contention
  • A dependency's latency rising with your concurrency: downstream amplification
  • Fix: go back to the measured peak, bound the queue, and fix the real bottleneck
How a senior would say it
I would not guess, because each reason leaves a different fingerprint. First I look at CPU and context switches. If the cores are pegged and involuntary switches jumped, the work is CPU bound and I am oversubscribed: 256 runnable threads take turns on the same cores, and every switch evicts the last thread's data from the caches. If the cores are not full but voluntary switches jumped, threads are blocking. A few thread dumps show whether most of them are parked at the same lock or the same queue. That is contention, and the critical section is serial no matter how many threads wait for it. Then I check the dependencies. If the database's latency rose in step with our concurrency, we pushed it past capacity, and our extra threads just wait longer. Whichever it is, the fix has the same shape. I measure throughput and p99 at a few pool sizes, go back to the size where throughput peaked, put a bounded queue in front, and fix the real bottleneck: the hot lock, the algorithm, or the limit on the dependency. More threads only help when cores sit idle and the dependency has headroom.

Likely follow up: Throughput stayed flat from 32 to 64 threads, but p99 latency doubled. Why?

Out loudabout 75 s
"What does a thread actually cost? Give me the numbers you would put on a whiteboard."
What a strong answer covers
  • A stack reservation: 1 MB for Java on x86-64 Linux, often 8 MB for pthreads, 512 KB on macOS; address space, not RAM
  • Always resident: a kernel stack of about 16 KB plus scheduler state
  • Creating, starting and joining one: tens of microseconds
  • Running costs: about a microsecond per switch plus cold caches, and in Java GC scans every stack
  • Limits in the thousands to tens of thousands per process, then OutOfMemoryError or std::system_error
How a senior would say it
A thread is cheap to write and expensive in large numbers. Memory first. Each thread reserves a stack: 1 MB by default for Java on x86-64 Linux, often 8 MB for pthreads on Linux, 512 KB for secondary threads on macOS. That is address space, not RAM, because only the pages a thread touches become resident. What is always resident is the kernel's side: about 16 KB of kernel stack plus scheduler structures. Then time. Creating, starting and joining a thread costs tens of microseconds, because it takes system calls and a fresh stack. Running costs come on top: a context switch is about a microsecond of kernel work plus cold caches afterwards, and in Java every garbage collection scans every thread's stack. Finally, limits. A process runs out somewhere in the thousands to tens of thousands, and then Java throws an out of memory error about native threads and C++ throws std::system_error. So a few hundred threads are free in practice, and a hundred thousand are not.

Likely follow up: So do 10,000 Java threads use 10 GB of RAM?

Out loudabout 80 s
"Why not just start a new thread for every request? It is simpler than a pool."
What a strong answer covers
  • Creation costs tens of microseconds, which can be more than the work in a small request
  • No bound: a burst or a slow dependency piles up thousands of threads
  • The pile up costs memory, switching and GC, then creation fails with OutOfMemoryError or std::system_error
  • A pool pays creation once, and its size plus a bounded queue is the concurrency limit and the overload policy
  • Java 21 virtual threads remove the creation cost, not the need for a limit
How a senior would say it
Because simple stops being cheap at scale, and nothing bounds it. Creating a thread costs tens of microseconds, so if the request itself is a few microseconds of work, most of the time goes on the thread, not the request. Worse, a thread per request has no limit. Under a burst, or when a dependency slows down and requests pile up, the service creates thousands of threads. Memory, switching and garbage collection costs grow with them, and eventually creation fails: Java throws an out of memory error saying it could not create a native thread, and C++ throws std::system_error. A pool fixes both problems. It pays for creation once and hands each task to a waiting thread for the cost of a wake-up. And its size is a concurrency limit: with a bounded queue in front, I decide what happens under overload instead of the operating system deciding for me. On Java 21, virtual threads remove the creation cost, so a thread per request is fine there, but I still put an explicit limit, such as a semaphore, around anything scarce.
