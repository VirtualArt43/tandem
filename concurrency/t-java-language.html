Java language questions interviewers ask

Forty spoken questions on Java 21: object contracts, types, exceptions, collections, memory, modern language features and API design.

1Corejavaequalityreferences
When do you use ==, equals, and Objects.equals?
Model answer

For primitives, == compares values after the applicable numeric conversions. For two object references, it compares identity: whether both refer to the same object, or both are null. equals is an instance method whose meaning belongs to the class. The implementation inherited from Object compares identity, while String and many value types override it to compare contents.

I use Objects.equals(a, b) when either reference might be null. It returns true for identical references, handles nulls, and otherwise calls a.equals(b); it does not repair broken equality. Arrays inherit identity equality, so I use Arrays.equals for element comparisons and Arrays.deepEquals for nested object arrays. For enum constants, == is appropriate because each constant has a unique identity within its enum class.

Likely follow up: "Does Integer == int compare identities?" No. The wrapper is unboxed, so it compares numeric values and throws NullPointerException if the wrapper is null.

2Corejavaequalshashcode
State the equals and hashCode contracts, then implement a value key.
Model answer

equals must be reflexive, symmetric, transitive and consistent while equality-relevant state stays unchanged. A non-null object must compare unequal to null. Equal objects must have equal hash codes; equal hash codes do not imply equal objects. A hash code must remain consistent during an execution while equality-relevant state is unchanged, but need not be stable across executions.

I override both methods and use the same logical identity fields. Here the class is final, the identifier cannot change, and the equality signature really overrides equals(Object). Overloading equals(Key) alone would leave collections using identity equality.

Likely follow up: "Is returning a constant hash code correct?" It satisfies the contract but creates collisions and can severely degrade hash collection performance.

3Seniorjavaequalityinheritance
Why does adding a field in a subclass make value equality difficult?
Model answer

Suppose Point compares coordinates and accepts every Point subtype, while ColoredPoint also compares colour. A plain point may consider a coloured point equal, but the coloured point rejects the plain point. That violates symmetry. Making the coloured point ignore colour only when compared with plain points can instead break transitivity: a plain point can connect two differently coloured points.

I decide the equality boundary when designing the hierarchy. A final value class or a record avoids subclass ambiguity. Exact runtime-class comparison can preserve symmetry, but deliberately makes a base instance unequal to a subclass instance with identical base fields. If colour is independent information, composition is often a clearer design. There is no universal choice between instanceof and getClass; the domain contract decides.

Likely follow up: "Does a matching hashCode fix asymmetric equality?" No. Hashing relies on a valid equivalence relation; it cannot create one.

4Seniorjavahashmapmutable-keys
A key is still visible while iterating a map, but get cannot find it. What happened?
Model answer

I first check whether a field used by the key's equality or hash code changed after insertion. A hash map stores the entry according to its insertion-time hash; it does not relocate entries when arbitrary key objects change. A later lookup can use a different hash and fail even with the same reference. More generally, changing equality-relevant state while an object is a key violates the map's usage contract.

I prefer immutable keys or extract an immutable identifier. If mutation is unavoidable, remove the entry before changing the key, then reinsert it under exclusive ownership. Trying to remove it after mutation may already fail. In this example a mutable list is itself the key, so changing its elements changes its hash.

Likely follow up: "Would ConcurrentHashMap fix this?" No. Thread-safe map operations do not freeze keys or repair their contracts.

5Corejavastringstring-pool
Why is String immutable, and how does the string pool affect equality?
Model answer

A string's character sequence cannot change after construction. Methods such as replace return a result rather than modifying the receiver. Immutability makes strings safe to share as values, supports stable map keys and permits cached hashes. A variable referring to a string can still be reassigned.

String literals and string-valued constant expressions are interned, meaning equal contents share a canonical string reference. new String creates a distinct object; intern() returns the canonical representative. Non-constant concatenation creates a new string object rather than automatically interning it. I still compare string contents with equals, because identity observations from literal-heavy tests are not a general application contract. Interned strings are heap objects, not a promise of immortal storage in a separate non-heap region.

Likely follow up: "Does final StringBuilder become immutable?" No. The reference is fixed, but the builder's contents can change.

6Seniorjavastringunicode
What string assumptions cause correctness or performance bugs?
Model answer

String.length() counts UTF-16 code units, and charAt returns one code unit. A supplementary Unicode code point uses two units. Even code points are not always user-perceived characters because combining marks and multi-code-point sequences exist. I choose code-unit, code-point or grapheme handling from the problem's definition, rather than treating every char as a complete character.

For repeated concatenation in a loop, I use a local StringBuilder. Repeatedly rebuilding an ever-growing immutable prefix can copy a quadratic amount of data. A single + expression is usually clear and can be efficiently implemented by the compiler and runtime; I do not claim every + creates a particular number of temporary objects. StringBuilder is mutable and not thread-safe, while StringBuffer synchronizes individual operations.

Likely follow up: "Does StringBuffer make a check followed by append atomic?" No. An invariant spanning multiple calls still needs one synchronization boundary.

7Corejavafinalpublication
What does final mean for variables, methods and classes?
Model answer

A final variable can be assigned only once under Java's definite-assignment rules. A final reference cannot be redirected, but the referenced object can remain mutable. A final method cannot be overridden or hidden, and a final class cannot be subclassed. None of these declarations makes an arbitrary operation atomic.

Final fields also have special initialization guarantees in the Java memory model. If an object is properly constructed, with no escape of this during construction, a thread that obtains its reference gets guarantees about the final fields' initialized values, including relevant state reached through them at construction. This does not make later mutations safe or guarantee visibility of every unrelated non-final field. I still use a clear publication mechanism, such as class initialization, a volatile reference or a lock.

Likely follow up: "Is every static final field a compile-time constant?" No. Only final primitive or string variables initialized with constant expressions are constant variables.

8Corejavafinallyfinalization
Distinguish final, finally and finalize. Does finally always run?
Model answer

final restricts assignment, overriding or inheritance. finally is a block associated with a try statement, executed as control leaves the try or its catch blocks, including through a return or exception. It is not guaranteed after process termination or a JVM crash, and it is not reached while the try block never finishes.

finalize() is a legacy cleanup method, deprecated for removal in Java 21. Its execution is unpredictable and may never happen. I do not use it to release resources. I use AutoCloseable and try-with-resources for deterministic ownership; a cleaner can at most be a fallback, without timely-execution guarantees. The Java 21 finalization documentation describes those limitations.

Likely follow up: "What if finally returns or throws?" Its abrupt completion replaces the pending return or exception, potentially hiding the original failure. I avoid returning from finally.

9Corejavanested-classesretention
When would you choose a static nested class instead of an inner class?
Model answer

A static nested class is associated with the enclosing type and needs no enclosing object. A non-static member inner class has an enclosing instance and can access that instance's members directly. Both can access private members subject to their enclosing context; being static does not mean losing all access to private data.

I use a static nested class for a helper, node or builder that does not need an outer instance. An inner class is useful when that relationship is part of its semantics, but retaining the inner object can also retain outer state. That matters when a listener or task outlives a request or UI component. Local and anonymous classes can additionally capture local variables, which must be final or effectively final.

Likely follow up: "Can an inner class declare static members?" Yes in Java 21. The older blanket restriction is obsolete; enclosing-instance semantics still distinguish it from a static nested class.

10Corejavainterfacesabstract-classes
How do you choose between an interface and an abstract class?
Model answer

I use an interface to express a capability or contract that unrelated classes can implement. A class can implement multiple interfaces but extend only one class. An abstract class is useful for a closely related family that shares instance state, constructor-enforced invariants or protected implementation hooks.

Modern interfaces can contain abstract, default, static and private methods. Their fields are public static final, and they do not have per-instance fields or constructors. Default methods permit shared behaviour and API evolution, but do not provide multiple inheritance of instance state. If unrelated interfaces supply conflicting defaults, the implementing class must resolve the conflict; a concrete inherited class method takes precedence. I prefer composition when the shared implementation does not represent a genuine subtype relationship.

Likely follow up: "Can an abstract class have no abstract methods?" Yes. Declaring it abstract can simply prevent direct instantiation while retaining shared implementation and constructors.

11Corejavaoverloadingoverriding
Explain overloading versus overriding, including what happens through a base reference.
Model answer

Overloading provides the same method name with different parameter lists. The compiler chooses the applicable signature from compile-time types; changing only the return type is insufficient. Overriding replaces an inherited instance-method implementation, and runtime dispatch chooses the implementation for the receiver's actual class.

An override cannot reduce accessibility or broaden checked exceptions, but may return a covariant reference type. Static methods are hidden rather than dynamically overridden; private methods are not inherited, and constructors are not overridden. I use @Override so a mistaken parameter type becomes a compile error.

Likely follow up: "How is choose(null) resolved?" String is more specific than Object, so that overload wins. With unrelated reference-type overloads and no most-specific choice, the call is ambiguous.

12Corejavapass-by-valuereferences
Is Java pass-by-reference? Why can a method mutate my list but not replace it?
Model answer

Java is always pass-by-value. A primitive argument copies the primitive value. An object argument copies a reference value, so caller and callee initially refer to the same object. Mutating that object is observable through either reference, but assigning the parameter changes only the callee's local copy.

In this method, clearing the list changes the caller's object. Assigning a new list to the parameter does not change the caller's variable, so the caller still sees its original, now empty list. The same rule explains why a method cannot swap two caller variables merely by exchanging its parameters. If replacement is needed, return the new value or deliberately use an owning mutable holder.

Likely follow up: "Would making the parameter final prevent clear?" No. It prevents parameter reassignment, not mutation of the referenced list.

13Seniorjavaconstructorsinitialization
Why is calling an overridable method from a constructor dangerous?
Model answer

Instance fields first receive default values. In Java 21, superclass construction runs before the subclass's instance field initializers, instance initializer blocks and remaining constructor body. Overridden instance methods still dispatch dynamically during construction, so a superclass constructor can enter subclass code before the subclass's invariants exist.

Here constructing Derived prints zero even though the field initializer says seven. The superclass calls the override before that initializer executes. I keep construction local: validate inputs, initialize state and avoid overridable callbacks or publishing this. A factory can perform registration after construction if the lifecycle genuinely needs it.

Likely follow up: "Would final fields make constructor callbacks safe?" No. A blank final field read by the callback can still have its default value before assignment. Publication guarantees do not complete construction.

14Seniorjavaclass-initializationstatic
When does class initialization happen, and why does the holder singleton work?
Model answer

Loading a class is different from initializing it. Active uses, such as creating an instance, invoking a static method or accessing a non-constant static field declared by the class, trigger initialization. Reading an inlined constant variable does not.

A triggering access to an inherited static member initializes its declaring class, not necessarily the qualifying subclass. The class's constant variables initialize before required superclass and default-method interface initialization. Remaining static field initializers and blocks then run in textual order.

A nested holder initializes on first active use; JVM coordination safely publishes its completed static instance, but does not protect later mutation. Recursive initialization on the initializing thread can observe default values; circular dependencies across threads can deadlock. I avoid callbacks and dependency cycles in initializers. Different defining class loaders can have separate singleton instances.

Likely follow up: "What if initialization fails?" The class is marked erroneous; later initialization attempts fail with NoClassDefFoundError. A non-Error cause is initially wrapped in ExceptionInInitializerError. See the initialization procedure.

15Seniorjavaaccess-controlprotected
What does protected allow, and why can a subclass fail to access a protected field?
Model answer

public makes a member broadly accessible subject to its containing type and module boundaries. Package access, written without an access modifier, allows access within the package. private confines access to the enclosing top-level declaration and its nested types. protected allows same-package access and additional access from subclasses outside the package.

The subtlety is the receiver of an instance member accessed from a subclass in another package. From that subclass, a qualifying reference must have the subclass's type or a subtype, not just the superclass type. A subclass cannot use inheritance as permission to inspect arbitrary superclass instances. I usually keep representation private and expose narrow operations instead of protected mutable fields, because those fields couple every subclass to implementation invariants.

Likely follow up: "Does public bypass the module system?" No. Another module must have the required readability and exported-package access; public alone is insufficient.

16Corejavaexceptionsapi-design
What distinguishes checked from unchecked exceptions, and how do you choose?
Model answer

Unchecked exceptions are RuntimeException, Error and their subclasses. Other throwable exception types are checked: code must catch them or declare them when the compiler determines they can escape. Both categories occur at runtime; checked does not mean the failure happens at compile time.

I use a checked exception when the API deliberately requires callers to acknowledge a recoverable outcome, and an unchecked exception for violated preconditions or failures better handled at a higher boundary. That is a design choice, not a guarantee that every checked failure is recoverable or every unchecked failure is a programmer bug. I preserve the cause when translating an exception and catch only where I can recover, add useful context or enforce a boundary.

Likely follow up: "What about InterruptedException?" Propagate it when possible. If the interface cannot throw it, restore the interrupt flag and stop or hand control to a cancellation-aware boundary; do not silently continue.

17Seniorjavaexceptionsresources
How does try-with-resources behave when both the body and cleanup throw?
Model answer

Try-with-resources manages AutoCloseable resources. Resources initialize left to right and successfully initialized resources close in reverse order. If a later initializer fails, earlier resources still close. A null resource is skipped. An already declared resource can be used if its variable is final or effectively final.

If the body throws and close also throws, the body's exception remains primary and close failures are normally attached as suppressed exceptions, accessible through getSuppressed(). If the body succeeds, the first closing failure becomes primary and subsequent closing failures are suppressed. This preserves information that naive cleanup in a finally block can overwrite. I make resource ownership explicit and use the construct for files, connections and other bounded resources, not just heap memory.

Likely follow up: "Is a suppressed exception the same as a cause?" No. A cause explains why another exception arose; a suppressed exception records an additional failure during handling or cleanup.

18Seniorjavagenericserasure
What survives type erasure, and what restrictions does erasure explain?
Model answer

Generics let the compiler check type relationships before execution. Erasure maps a type variable to its leftmost bound, or Object when unbounded, and removes parameterization from runtime class identity. The compiler inserts casts and sometimes bridge methods to preserve overriding. Changing only the type argument does not create a distinct runtime class: new ArrayList<String>() and new ArrayList<Integer>() have the same runtime class.

I cannot create new T() without another construction mechanism, test an arbitrary Object with instanceof List<String>, or overload methods solely on List<String> versus List<Integer> because their erased signatures clash. Generic declaration metadata can remain in class files and be inspected reflectively; erasure does not mean every trace of generics disappears. Raw types and unchecked casts can introduce heap pollution that fails later at an inserted cast. The erasure rules define the exact mapping.

Likely follow up: "Is instanceof List<?> legal?" Yes. It tests a reifiable list type without claiming to know its element type.

19Seniorjavagenericswildcards
Explain PECS with an API that copies elements between lists.
Model answer

Generic types are invariant: List<Integer> is not a subtype of List<Number>, because a writable number list could accept a Double. Wildcards describe the flexibility an operation actually needs. Producer extends, consumer super: a source that produces values assignable to T can be ? extends T, and a destination accepting T can be ? super T.

From ? extends Number, I can read a Number but cannot add an arbitrary non-null number: the element type might be Integer. A capture helper can reinsert an element of that same captured type. Into ? super Integer, I can add an integer but can only assume reads are Object. A wildcard is not immutability; removal or clearing may still be permitted by the concrete list. If the same element type connects several parameters or a return value, a named type parameter expresses that relationship.

Likely follow up: "Why not return wildcard types everywhere?" They push capture constraints onto callers. I expose them only when that flexibility is useful.

20Seniorjavaarraysgenerics
Why can String[] become Object[], while List<String> cannot become List<Object>?
Model answer

Arrays are covariant and retain their component type at runtime. A String[] can be referenced as Object[], but storing a non-string through that reference throws ArrayStoreException. Generic collections are invariant, so the corresponding unsafe assignment is rejected at compile time.

This mismatch explains why creating an array with a non-reifiable component type, such as new List<String>[10], is illegal. Runtime array-store checks cannot verify the erased element argument. An array of unbounded-wildcard lists is different because that component type is reifiable. I generally prefer a list of lists when the structure needs parameterized elements, and avoid unchecked generic-array casts.

Likely follow up: "Does @SafeVarargs make unsafe code safe?" No. It asserts that the implementation safely handles its non-reifiable varargs array; the author must justify that assertion.

21Corejavaboxingnull
Which autoboxing traps do you watch for in interview code?
Model answer

Boxing converts primitives to wrappers; unboxing does the reverse and throws NullPointerException for null. Two wrapper references compared with == use identity, so cached values can hide bugs. Integer.valueOf guarantees caching from -128 to 127; larger values may also be cached. I compare wrapper values with equals or deliberately unbox when null is excluded. Different wrapper classes, such as Integer and Long, do not become equal merely because their numbers match.

Overload resolution is another trap: List<Integer>.remove(1) removes index one, while remove(Integer.valueOf(1)) removes a matching value. Boxing in a hot loop can also add allocation and indirection; primitive arrays or primitive streams can help when measured. Updating a wrapper creates or obtains a replacement value and is not an atomic shared counter operation.

Likely follow up: "Can I rely on caching outside small wrapper values?" No. Cache extensions are implementation choices; use value comparison.

22Corejavaarithmeticoverflow
Why can assigning an arithmetic result to long still overflow?
Model answer

The operand types determine the arithmetic before assignment. Multiplying two int values performs int arithmetic, so assigning the result to a long only widens an already overflowed value. I widen an operand first. Java integer overflow wraps; it is not undefined behaviour and does not automatically throw. Math.addExact and Math.multiplyExact are useful when overflow must be rejected.

Integer division truncates toward zero and throws for a zero divisor. Dividing the minimum integer by -1 overflows silently; floating-point division can produce infinities or NaN. Decimal fractions such as one tenth are usually not exactly representable in double; for exact decimal calculations I choose an appropriate scaled integer or BigDecimal and specify rounding. Constructing BigDecimal from a decimal string avoids importing a binary approximation.

Likely follow up: "Why not compare integers by subtraction in a comparator?" The subtraction can overflow and reverse ordering. Use Integer.compare or Long.compare.

23Seniorjavajvmmemory-areas
Walk me through the JVM memory areas without saying that every local lives on the stack.
Model answer

The JVM defines shared heap storage for objects and arrays, and a shared method area containing per-class structures such as runtime constant pools and method information. Each thread has a program counter and a JVM stack of frames, with local-variable slots and an operand stack. Native method stacks may also exist. A local reference and the object it references are different things.

These are logical areas in the JVM specification, not a mandatory physical layout. HotSpot stores much class metadata in native-memory metaspace and compiled machine code in a code cache. Direct buffers and thread stacks can consume memory outside the Java heap. The JIT can keep values in registers or eliminate an allocation through escape analysis and scalar replacement, so source-level rules do not prove physical placement.

Likely follow up: "Does a healthy heap rule out process memory exhaustion?" No. Metaspace, native allocations, direct buffers or excessive threads can exhaust other limits.

24Corejavagarbage-collectionreachability
How does garbage collection decide what to reclaim, and does it handle cycles?
Model answer

A tracing collector starts from roots, such as live thread references, static state of live classes and native handles, and follows references to identify reachable objects. Unreachable objects can be reclaimed, including cycles that have no reachable path from a root. Scope exit alone does not determine an object's lifetime, and becoming unreachable does not imply immediate collection.

Collectors use combinations of marking, copying, sweeping and compaction, with different pause and throughput trade-offs. Many exploit the observation that most objects die young, but I would not claim every collector has identical generations or that a concurrent collector has no pauses. GC reclaims managed memory; it does not replace deterministic closing of files or sockets. System.gc() is a request, not a deadline or a proof of cleanup.

Likely follow up: "How would you investigate GC latency?" Correlate GC logs or JFR events with request latency, allocation rate, retained live data and pause causes before changing collector settings.

25Seniorjavamemory-leaksdiagnostics
How can Java leak memory if it has a garbage collector?
Model answer

A logical memory leak happens when objects remain reachable after the application no longer needs them. GC cannot infer that business meaning. Common causes are unbounded caches or queues, forgotten listeners, static collections, class-loader retention and request data left in thread-local values on long-lived workers.

I compare the retained live set over time under comparable load and inspect a heap dump for dominant retainers and paths to GC roots. Allocation rate alone does not prove a leak: a program can allocate rapidly and reclaim everything. I fix ownership or retention, for example by bounding a cache, unregistering a listener or removing thread-local state in a finally block. More heap may delay the failure without correcting it.

Likely follow up: "Would a WeakHashMap always solve a cache leak?" No. A strongly held value that refers back to its key can keep that key reachable, and weak keys do not provide a predictable cache eviction policy.

26Seniorjavahashmapcomplexity
Explain HashMap lookup, collisions and resizing in Java 21.
Model answer

In OpenJDK 21, HashMap mixes a key's hash and selects a bucket in a power-of-two table. It then checks stored hashes and identity or equality to find the key. Collisions initially share a linked bin. Large bins can become red-black trees. For put, adding to eight existing entries requests treeification; below capacity 64 it resizes instead. Those are implementation details, not portable API promises.

The default load factor is 0.75. Growth beyond the size threshold normally doubles capacity and redistributes entries. With well-distributed hashes, basic operations are expected constant time and insertion is amortized constant time; a resize itself costs linear work. Tree bins mitigate collisions, but pathological equal hashes without useful comparable ordering can still require linear searches. The map allows a null key and null values and promises no iteration order. The API contract and OpenJDK 21 source distinguish guarantees from implementation choices.

Likely follow up: "How do you distinguish missing from mapped-to-null?" Use containsKey; get returning null alone is ambiguous.

27SeniorjavahashmapconcurrencyDatabricks
Is a shared HashMap safe if only one thread writes? What would you choose instead?
Model answer

One writer does not make unsynchronized readers safe. Readers and the writer still access shared mutable state without a visibility or consistency protocol. A fully built map that is safely published and never modified can support concurrent reads, but that is a different lifecycle.

For independent concurrent key operations I would usually choose ConcurrentHashMap. It rejects null keys and values and provides atomic operations such as putIfAbsent, compute and merge. Replacing a map with it does not make a sequence of calls atomic: a get followed by a put can still lose an update. A synchronized wrapper is another option, but iteration and compound operations require holding the wrapper's lock. For an invariant across several keys, I define a wider locking or transactional protocol explicitly.

Likely follow up: "Does ConcurrentHashMap make values thread-safe?" No. A stored mutable list still needs its own ownership or synchronization rules. See the Java concurrency questions for the implementation follow ups.

28Corejavaarraylistlinkedlist
Compare ArrayList and LinkedList. Is insertion faster in a linked list?
Model answer

ArrayList stores references in a resizable array. Indexed access is constant time, appending is amortized constant time, and inserting or removing near the front shifts a linear number of references. It usually has good locality and little per-element structural overhead.

LinkedList uses doubly linked nodes. Indexed access takes linear traversal, while insertion or removal at a position already held by a list iterator is constant time. Finding that position can still be linear, so saying linked-list insertion is always faster hides the search and allocation costs. It also adds node objects and pointer chasing. I default to ArrayList for lists, and often choose ArrayDeque for a stack or queue. A linked list fits a specific access pattern, not a universal optimization.

Likely follow up: "What happens if you loop with get(i) over a linked list?" Repeated traversal can make the loop quadratic. Use an iterator for linear traversal.

29Seniorjavacollectionsimmutability
Compare Arrays.asList, List.of, unmodifiableList and List.copyOf.
Model answer

Arrays.asList gives a fixed-size view backed by the supplied reference array: element replacement works, size changes do not, and changes are shared with the array. Arrays.asList(new int[]{1, 2}) contains one array, not two integers. List.of is unmodifiable and rejects null elements. Collections.unmodifiableList wraps another list, so changes through the backing list remain visible.

List.copyOf gives an unmodifiable list that does not reflect later source additions, removals or element replacements, and rejects null elements. It may reuse a suitable existing unmodifiable list, so I do not rely on a new identity. All these operations are shallow: mutable elements can still change. Taking a copy also requires a valid reading protocol if another thread mutates the source.

Likely follow up: "Is subList a copy?" No. It is a backed view; structural modification of the backing list outside that view makes the view's semantics undefined.

30Corejavaiteratorsfail-fast
What does a fail-fast iterator guarantee, and can it detect every race?
Model answer

A fail-fast iterator checks for certain unexpected structural modifications, commonly through a modification counter, and may throw ConcurrentModificationException. It is a best-effort bug detector, not synchronization and not a guarantee that every concurrent modification will be noticed. The exception can also happen in one thread if that thread modifies the collection directly while iterating.

When supported, the iterator's own remove keeps its traversal state consistent; calling the collection's removal method instead is a different operation. A copy-on-write iterator traverses a snapshot of references, while a concurrent-map iterator is weakly consistent and can reflect some concurrent changes. I choose the collection and iteration semantics intentionally, rather than catching the exception and pretending a partial traversal is a consistent result.

Likely follow up: "Does replacing an ArrayList element count as a structural change?" Ordinary set does not change size or structure, but that does not make unsynchronized concurrent element access safe.

31Seniorjavacomparablecomparator
When do you implement Comparable, and when do you pass a Comparator?
Model answer

Comparable defines a type's natural order through compareTo. A Comparator supplies an external order, letting the same type be sorted by different criteria without changing its class. Comparison returns a negative value, zero or a positive value, and must obey sign symmetry, transitivity and consistent treatment of elements that compare as zero.

Sorted sets and maps use comparison returning zero to identify equivalent keys. I keep ordering consistent with equals when using them as ordinary sets or maps. BigDecimal is a familiar exception: numeric comparison can return zero for differently scaled values whose equals returns false. A comparator based only on priority can therefore collapse distinct jobs in a TreeSet; I add a stable tie-breaker when identity requires it.

Likely follow up: "Can an ordering field change inside a TreeSet?" Not safely. Remove the element before changing it, then reinsert it, or use immutable keys.

32Seniorjavapriorityqueuecollections
Why is iterating a PriorityQueue not the same as repeatedly polling it?
Model answer

A priority queue maintains a heap, which guarantees that its head is a least element under the chosen ordering. It does not keep every stored element in globally sorted traversal order. Iteration and toArray therefore have no sorted-order guarantee; repeated poll returns elements in priority order while consuming an otherwise unmodified queue. For non-destructive sorted output, I copy and sort or poll a copied queue.

In Java's PriorityQueue, peek is constant time, insertion is amortized logarithmic, head removal is logarithmic, and searching for or removing an arbitrary object is linear. Equal-priority elements have no FIFO guarantee, so I add a sequence number if stable tie ordering matters. Mutating an element's priority does not repair the heap. I remove it before changing priority, then reinsert it, use immutable replacement entries with lazy invalidation, or choose a structure with decrease-key support.

Likely follow up: "Is PriorityBlockingQueue bounded backpressure?" No. It provides blocking retrieval but is logically unbounded; capacity control needs a separate policy.

33Corejavarecordsimmutability
What does a record generate, and is every record immutable?
Model answer

A record declares a data carrier whose components determine its state description. It is implicitly final, extends Record, and gets private final component fields, accessors, a canonical constructor and component-based equals, hashCode and toString unless explicitly supplied where allowed. It can implement interfaces and define methods, but cannot declare extra instance fields.

Records provide shallow immutability. A final list component still points to a mutable list unless I copy or otherwise control it. A compact constructor is a concise place to validate and normalize components before implicit field assignment. Here the list structure is protected and strings are immutable. The record contract describes the generated behaviour.

Likely follow up: "Does a record containing an array get deep equality?" No. The generated reference-component equality uses the array's identity equality unless you deliberately customize the contract.

34Seniorjavasealedpattern-matching
What problem do sealed types solve, and how do they help a Java 21 switch?
Model answer

A sealed class or interface restricts its direct subtypes to a known permitted set. Each permitted branch must continue the policy by being final, sealed or non-sealed, explicitly or implicitly where the language allows. Permitted subtypes must be in the same named module, or the same package when in the unnamed module.

This expresses a closed set of alternatives, such as success and failure, more precisely than an unrestricted hierarchy. Java 21 pattern matching for switch can use that set for exhaustiveness checking. A non-sealed branch deliberately reopens extension within that branch. Sealing controls inheritance, not object mutability, and adding a variant requires reviewing consumers. See the permitted-subclass rules.

Likely follow up: "Does exhaustive mean null is covered?" No. This switch throws for null; add case null or reject null at the boundary if needed.

35Seniorjavaimmutabilitydefensive-copy
Design an immutable class that owns a byte array. Why is a final field insufficient?
Model answer

Immutability means externally observable value state cannot change after construction. I prevent uncontrolled subclass behaviour, establish invariants during construction, avoid escape of this, and keep owned mutable representation inaccessible. A final array field only fixes the reference; callers can still change array elements if they retain or receive that array.

I therefore copy mutable inputs and copy mutable outputs, or expose an interface that cannot modify the owned state. The class below uses defensive copies on both boundaries. For nested mutable objects, one shallow copy is not enough; the ownership design must cover the whole reachable representation. Copying an input that another thread is concurrently mutating also needs a consistent read protocol.

Likely follow up: "Could you return a read-only buffer instead?" Possibly, but it is a view. It preserves immutability only if nobody can mutate its backing storage through another alias.

36Stretchjavaserializationcompatibility
What should a senior engineer know about Java object serialization?
Model answer

Java serialization encodes Serializable object graphs, preserving shared references and ordinary object cycles. Default serialized state includes non-static, non-transient fields of serializable classes, and every traversed object must be serializable unless custom handling replaces it. serialVersionUID participates in version compatibility checks; declaring one does not make every schema change compatible.

Deserialization is a construction boundary. For ordinary serializable classes, their constructors are bypassed and the first non-serializable superclass's accessible no-argument constructor runs. Externalizable instead runs the class's public no-argument constructor. Records use their canonical constructor, and cycles through their components back to the record are not preserved, as the serialization specification explains. I validate invariants and avoid deserializing untrusted native object streams because reconstruction can invoke dangerous behaviour. Filters constrain accepted classes and graph size but do not prove arbitrary input safe. For a new external protocol, I prefer an explicit schema and versioning policy.

Likely follow up: "Does transient mean secret?" No. It only omits a field from default serialization; custom serialization, logs or other references can still expose the data.

37Seniorjavareflectionmodules
When is reflection useful, and what are its limits in Java 21?
Model answer

Reflection lets code inspect classes, fields, methods, constructors and runtime-visible annotations, then access or invoke members dynamically. Frameworks use it for binding, dependency injection and adaptation when concrete types are not known at compile time. The costs include weaker compile-time checking, more complex failure paths and potentially reduced optimization opportunities; I measure performance rather than quote a universal slowdown.

getDeclaredMethods inspects methods declared by that class, including non-public ones, while getMethods returns public methods including inherited ones. Access still matters. Strong module encapsulation can block deep access; setAccessible(true) is not an unrestricted bypass, and trySetAccessible() reports whether suppression succeeds under the access rules. I use ordinary interfaces when the contract is known and isolate reflection at framework boundaries.

Likely follow up: "How does Method.invoke report an exception thrown by the target?" It wraps it in InvocationTargetException; inspect the cause to distinguish application failure from reflection failure.

38Corejavalambdascapture
What does a lambda capture, and how is it different from an anonymous class?
Model answer

A lambda supplies an implementation for a target functional interface: an interface that is not sealed and has one abstract method after method-combining rules. Default, static and private methods add no abstract obligations; declarations matching public Object methods do not count. The annotation @FunctionalInterface asks the compiler to enforce the intent.

Captured locals are final or effectively final; their values are captured, including reference values that can point to mutable objects. That restriction does not make the object thread-safe. Within a lambda, this refers to the enclosing instance; an anonymous class has its own this. I do not rely on lambda object identity or a particular allocation strategy. A bound method reference evaluates its receiver immediately but invokes the referenced method later when called.

Likely follow up: "Why can a lambda mutate a field but not reassign a captured local?" Fields belong to objects, while captured local bindings are fixed. Shared field mutation still needs synchronization.

39Seniorjavastreamsparallelism
What makes a stream pipeline safe, and why is parallel() not a free speedup?
Model answer

A stream describes a computation over a source, not a storage container. Intermediate operations are lazy; a terminal operation drives traversal, potentially short-circuiting it. A stream is generally consumed once. Behavioural parameters should be non-interfering and usually stateless, so I avoid mutating the source or shared external state during traversal.

A parallel reduction needs an associative operation, a valid identity and compatible accumulation and combination. Floating-point addition is not mathematically associative under rounding, so regrouping can change results. Parallel execution also adds splitting, scheduling and merging overhead, and ordering constraints or blocking work can erase its benefit. I choose parallelism from workload measurements. I do not use peek for essential effects because implementations can omit work that does not affect the result.

Likely follow up: "Is Stream.toList() mutable?" No. It returns an unmodifiable list. Collectors.toList() does not promise a particular mutability or implementation.

40Corejavaoptionalapi-design
When does Optional improve an API, and what are its common traps?
Model answer

Optional<T> makes a potentially absent return value explicit and supports composing the present case through map, flatMap and filtering. I return an empty optional for legitimate absence and an exception for a distinct failure when the API requires that distinction. An optional variable itself should not be null. of rejects null; ofNullable converts null to empty.

orElse evaluates its fallback expression eagerly, even when a value is present. orElseGet invokes its supplier only when empty, which matters for expensive work or side effects. I avoid unchecked get() and use operations that express the intended fallback or failure. Optional is primarily a return-type tool, not a reason to wrap every field, parameter or collection element, and it provides no synchronization.

Likely follow up: "Why flatMap?" If the mapping function already returns an optional, it avoids nesting Optional<Optional<T>>.
