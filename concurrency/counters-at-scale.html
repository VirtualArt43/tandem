Counters at scale: contention, LongAdder and striping

Why atomic counters stop scaling, how striping reduces contention, and which guarantees you trade for faster updates.

Asked atGoogleLinkedInUber
Before this:Atomic variables and compare-and-swapCPU caches, coherence and false sharing

A single atomic counter is correct, and on a busy many-core server it can quietly become one of the hottest spots in the process. Knowing why, and what to use instead, is one of the most reliable senior signals in a "now many threads call this" follow up.

In plain words

A cricket stadium wants to count everyone who enters. If all 40,000 fans must pass one turnstile with one counter, the queue at that turnstile is the bottleneck, however many gates the stadium has. So every gate gets its own turnstile and its own counter. Entry is fast because nobody shares a counter.

The price shows up when someone asks "how many have entered?". Now an official has to walk round and add up every gate's counter, and during that walk fans keep coming in. Her reading mixes observations from different moments instead of freezing every gate together. Fast to add, slower and fuzzier to read: that is the trade.

Why one atomic counter stops scaling

On typical cache-coherent CPUs, an atomic increment needs write ownership of the counter's cache line. One core can retain that ownership across many increments. With threads on several cores updating the same counter, cache coherence repeatedly transfers ownership, serializing updates to that location. Not every increment transfers the line, but frequent handoffs can dominate the cost of adding one.

Two details make it worse than you might expect:

  • Adding cores can add traffic without throughput. Once ownership handoffs dominate, extra writers may make throughput fall. The ceiling depends on the CPU, topology and access pattern; there is no universal increments-per-second limit.
  • It is not only your counter. Independent counters on the same line also compete for ownership. This is false sharing, and it can erase the benefit of splitting the counter.

A hardware fetch-and-add, such as x86 lock xadd or AArch64 ldadd where the LSE extension is available, does not expose CAS failures to its caller. Other targets may implement it with a retry loop. Either way, fewer software retries do not remove contention for the shared location.

Coordinate worker starts, vary writer count and scrape frequency, and report throughput and latency distributions on the target hardware. Keep sanitizer runs for correctness.

How LongAdder works

Java's LongAdder is the stadium with many turnstiles. OpenJDK 21's Striped64 implementation allocates extra cells lazily; these are implementation details, not promises made by the public API:

  1. A base field, and no cells at first. Without a cell table, an update first tries CAS on base. A successful update needs no cell allocation; the object still has more bookkeeping than an AtomicLong.
  2. Failure enters a retry path. That path can initialize a two-slot table. A failed CAS usually signals contention, but this implementation uses weak CAS, which may fail spuriously. Another thread may initialize the table first, or this thread may retry base.
  3. Each thread picks a cell by its own hash. Every Thread carries a per-thread hash code (the "probe" that ThreadLocalRandom maintains). The cell index is that hash masked by the table size, so different threads usually land on different cells.
  4. Collisions move threads and grow the table. Repeated failures lead to rehashing and table doubling. Growth stops once the length reaches the CPU-count threshold, with power-of-two sizes and an initial size of two. This is a memory-versus-collision heuristic, not proof that extra stripes could never help.
  5. Cells are padded. The JDK's internal @Contended annotation asks HotSpot to separate cells and reduce false sharing. The exact layout depends on the JVM and its configuration.
  6. A tiny spinlock guards only the table. Creating a cell or doubling the table takes a one-bit spinlock (cellsBusy). A thread that finds it busy does not wait; it tries another cell or base instead.

sum() reads base and the cells separately: it is not an atomic snapshot. It is accurate without concurrent updates, but racing updates need not all appear. Use reset() at a quiescent point. sumThenReset() also needs coordination if you require an exact interval boundary; in OpenJDK 21 it exchanges each component with zero separately, not the entire counter at once.

LongAccumulator takes a side-effect-free function and an identity. For predictable results regardless of grouping and update order, use an associative, commutative function, for example new LongAccumulator(Long::max, Long.MIN_VALUE). DoubleAdder and DoubleAccumulator provide similar tools for doubles, but floating-point addition is not exactly associative, so rounding can depend on update order.

The same trick sits inside ConcurrentHashMap: its size is a base count plus an array of counter cells, which is why size() under heavy writes is an estimate, and why mappingCount() exists for maps bigger than an int.

Striped counters in C++

C++ has no LongAdder, so you build a striped counter yourself. Three decisions matter: how many cells, how a thread picks its cell, and how to stop cells sharing cache lines.

  • Padding. alignas(128) makes successive C++ array elements at least 128 bytes apart, avoiding shared lines when the target uses 64 or 128 byte lines. That is a target assumption, not a portable cache-line size. C++17 specifies std::hardware_destructive_interference_size in <new>, but library support varies; check __cpp_lib_hardware_interference_size and use a measured fallback when unavailable. Java array layout and spacing are also JVM dependent.
  • Picking a cell. The C++ thread_local assignment gives the first N participating threads distinct slots and avoids assigning or hashing on every call. The assignment is shared across instances of this class. More threads, or thread churn, can map active writers to the same slot; the atomic still makes that safe. The Java mask can collide even without filling all slots.
  • Number of cells. Start near the active writer count, then measure. More stripes reduce some collisions but use memory and increase scan cost; a scrape itself also brings cell lines into the reader's cache.

Relaxed atomics for pure counters

The C++ counter uses std::memory_order_relaxed. A relaxed atomic increment is still a full atomic read-modify-write: no increment is ever lost, and all threads agree on the order of changes to that one counter. What it drops is ordering with respect to other memory. For a pure statistic that nothing else depends on, that is exactly right, and the final read after join() is exact because join itself provides the ordering.

Be precise about what relaxed buys. On x86, relaxed and sequentially consistent increments commonly use the same locked instruction; on AArch64 with LSE they may use ldadd and ldaddal respectively. Exact instructions depend on the compiler and whether the return value is used. Relaxed ordering does not remove contention, and a live relaxed load has no wall-clock freshness guarantee. These examples assume counts and intermediate sums fit in long; Java arithmetic wraps on overflow, while the C++ plain total += value would have undefined behaviour on signed overflow.

Do not share at all

The fastest counter is one no other thread touches. When the work is split into chunks, count into a local variable and publish once per thread:

The C++ starts_with call needs C++20; in C++17 use line.compare(0, 5, "ERROR") == 0. The input chunks must remain immutable while these methods read them.

For long-running threads, batch local increments and publish every B events, including a final flush on worker exit. With P workers and at most B unpublished events per worker, at most P times B events are locally buffered, including a worker paused just before its flush. This bounds buffering, not every reader's visibility lag. A periodic timer alone gives no hard time bound if the worker can be descheduled; reading another thread's plain local count without synchronization is not a safe shortcut.

In a model where each cell read observes a value during the scan, positive-only updates without overflow or reset put the sum between the totals at the scan's start and end. That is not a portable freshness promise for the C++ relaxed implementation. Neither API promises a numerical error bound for arbitrary live traffic. After writers finish and the reader joins them, the total is exact.

Even positive additions can produce a value that never existed. Start with cells (0, 0): the reader reads the first zero, writer A adds 2 to cell 0, writer B then adds 3 to cell 1, and the reader reads the second cell as 3. It returns 3, although the actual totals were 0, 2 and 5. Mixed positive and negative updates can be worse. Strengthening each cell's ordering cannot turn several separate reads into one linearizable snapshot.

If the caller needs its own update's result, such as a ticket number, use a single atomic RMW or protect the operation with a lock. A hard limit needs a CAS loop that checks and reserves together, or a lock or semaphore; get() followed by increment() is still a race. Choose striping for statistics whose readers accept a non-snapshot total, not for admission control.

Worked example: a counter per user, many threads

A service counts requests per user id, with 64 request threads, millions of users and a few very hot ones. This is the shape of the "counter per userId under many threads" question a Google L5 candidate reported in 2025.

Why it is correct. Creating a counter is a check-then-act, so it must be atomic per key: computeIfAbsent in Java, the exclusive lock plus try_emplace (which does nothing if another thread inserted first) in C++. In C++, shared locking permits concurrent lookups and atomic increments while excluding structural changes; rehash also preserves element addresses. The map still needs synchronization even when references to its elements remain stable.

Where it scales. Existing Java keys use a lookup followed by an adder update; collisions can still cause retries. The C++ version is a simple baseline: one shared mutex protects map access, and each hot key still has one atomic. A shared mutex's reader bookkeeping can itself contend. Measure before replacing hot counters with stripes and partitioning the map into separately locked shards.

What to say about cost. A contended LongAdder grows to about one padded cell per CPU, so millions of adders on a 64-core box can cost real memory. If only a few keys are hot, a plain AtomicLong per key plus a LongAdder for known hot keys is a reasonable refinement. Saying that trade-off out loud is the senior part.

Lifetime is part of correctness. These examples never remove or replace counters. If Java removes a key after get() but before increment(), the update can land on a detached adder and disappear from future reports. Coordinate deletion, replacement and updates per key; swapping a reference alone does not drain old writers. Bound key cardinality in a real service, and define whether eviction is allowed to discard history.

Common mistakes

  • Using a striped counter when the caller needs its own result. LongAdder.increment() returns nothing. An id generator or a "stop at 100" limit needs incrementAndGet or a CAS loop on one atomic.
  • Calling sum() on the hot path. It walks the table, including empty slots. Frequent reads can erase striping's benefit; measure the update/read mix or use a cached total when stale statistics are acceptable.
  • Cells without padding. Adjacent eight-byte counters can share a 64 or 128 byte line, so independent writers still contend. Separate frequently written cells according to the target's layout.
  • Hashing the thread id on every increment. It costs time and can map two busy threads to one cell. Assign the slot once per thread.
  • reset() while writers run. It can erase concurrent increments. sumThenReset() has no single boundary across all cells, and a reference swap leaves old writers in flight. Prefer cumulative totals with reader-side deltas for metrics; exact reporting periods need coordinated handoff or quiescence.
  • Believing relaxed ordering fixes contention. It removes ordering constraints, not ownership handoffs.

In the interview

Counters arrive as follow ups: "now many threads call hit()". A 2025 Google L5 report had exactly this, a counter per user id under many threads; the candidate listed ConcurrentHashMap, AtomicInteger and synchronized, was marked No Hire, and concluded that the interviewer wanted reasoning about races and guarantees, not a list of tools. LinkedIn has asked a staff candidate to count events by type in the last N minutes under high-throughput concurrent writes, and an Uber L4 report asked how to make all three methods of a per-key counter safe under many threads. In a Meta single-machine cache design round, the interviewer praised sharding the hash table about one shard per core, which is the same idea applied to a map.

One atomic is correct, but its shared cache line can become the bottleneck. For write-heavy metrics I would try LongAdder in Java, or padded atomic stripes in C++, and compare them under the real write and scrape load. Stripes can collide, so the cells still need atomic updates. A live sum is not a snapshot; after writers finish and join, it is exact. For ticket numbers I would keep a single atomic RMW, and for a hard limit I would make checking and reserving one CAS operation or use a lock.

Follow ups to expect: "Why allocate cells lazily?" (avoid cell memory for cold counters), "Why pad?" (false sharing), "Can we reset every minute?" (not for exact periods without coordination), "How would you count across 100 servers?" (aggregate local counters, then define how restarts and duplicate reports are handled).

Senior depth

The same pattern, everywhere. A hot database row that every request updates is the distributed version of a hot cache line, and the fix is the same: split it into N rows, add to a random one, sum on read. The Linux kernel's per-CPU counters do the same inside the kernel, with batching to bound the error. Recognizing "this is striping again" across levels is a strong signal.

Contention is not only counters. Reference counts (std::shared_ptr copies across threads) and shared gauges can also become hot locations. Reduce unnecessary ownership copies or confine ownership, but do not replace a lifetime reference count with an approximate metric: deciding when to destroy an object needs a correct reclamation protocol.

Approximation needs a contract. For dashboards, specify scrape frequency, buffering and restart behaviour. A hard rate limiter must not admit two callers who both saw 99 of 100. Across servers, cumulative per-server totals with identities and epochs help avoid counting a retried report twice; global exact limits require coordination or preallocated quotas. Striping alone does not solve those semantics.

Key takeaways

  • A shared atomic counter can bottleneck on cache-line ownership; adding writers can make throughput fall.
  • OpenJDK's LongAdder starts with a base field and allocates padded cells lazily on its retry path; sum() is not a snapshot.
  • In C++, build a striped counter from cache-line aligned atomics with a thread_local slot, or count locally and publish once.
  • Relaxed atomics are right for pure counters, but they trim ordering costs, not contention.
  • If the caller needs the result of its own update, use one atomic; if only a later reader needs the total, stripe it.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Assume no overflow. Which task needs the result of an atomic read-modify-write rather than a racing striped sum?
Why. An atomic RMW assigns each id at a distinct update position; overlapping calls can still return to their callers in a different order. A lock could also serialize allocation, but a striped sum cannot identify a caller's own increment. The other options are statistics that can accept periodic aggregation; none requires a unique result per update.
A safely published LongAdder (or atomic striped counter) starts at 0. Thread A performs 1,000 increments; thread B calls sum() once with no ordering between the threads. There are no resets or other updates. Across possible schedules, what can B see?
Why. Every value from 0 to 1,000 is possible by scheduling the read before, between or after increments. Without resets or overflow, there are no negative values and no contributions beyond those 1,000 increments. The API does not fix the result to the number completed when the call began; joining A first would instead force the final result of 1,000.
Why can 16 threads incrementing one atomic counter take longer in total than 1 thread doing all the increments alone?
Why. For a hardware lock-free counter on a cache-coherent CPU, contention for write ownership explains the slowdown without any OS lock or JIT conversion to a monitor. Atomic increments do not disable interrupts on every core. The exact handoff frequency depends on scheduling and topology, and C++ does not promise that every atomic type is lock-free.
A developer stripes a counter as std::atomic<long> cells[16] in C++ (or new AtomicLongArray(16) in Java), one cell per thread, and finds it barely faster than a single atomic. Why?
Why. Several adjacent counters may share a cache line, depending on their size and starting alignment. Independent atomic elements remain atomic, but their writers compete for the line. Nothing in the declaration sums on each increment, and choosing four cells cannot by itself fix false sharing. Use target-appropriate spacing, or Java's padded LongAdder cells.
C++ onlyA pure statistics counter uses fetch_add(1, std::memory_order_relaxed), and the total is read after all threads are joined. What is true?
Why. Assuming no overflow, relaxed RMWs lose no increments, and joining all writers orders their updates before the final read. Relaxed operations are atomic and do not create a data race. They still contend for one location; on x86 changing the memory order often does not change the locked instruction.
Java onlyIn OpenJDK 21, what does a brand new LongAdder first attempt on increment(), before any retry path?
Why. The initial fast path tries to update base. It does not first take the table lock, allocate cells for all CPUs or create a per-thread counter. A weak CAS can fail spuriously as well as from contention, so failure enters the retry path rather than proving that another writer intervened.
In a simplified model, every increment requires one serialized ownership handoff costing 50 to 100 ns, and all other costs are ignored. What aggregate rate does that model predict?
Why. One second divided by 100 ns is 10 million; divided by 50 ns it is 20 million. This is an illustrative model, not a measured universal ceiling. The serialized resource is shared, so multiplying by the number of cores is wrong; eliminating software CAS retries does not remove handoff cost.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
A service on a 48-core machine handles 2 million requests a second, and every request increments one shared AtomicLong (or std::atomic<long>) for metrics. A profile shows a large share of CPU time inside that single increment. Explain what is happening with rough numbers, and fix it.
Model answer

The shared atomic is a candidate bottleneck because its cache line repeatedly changes write owner. If, illustratively, each increment required one serialized 100 ns handoff, 2 million increments would require 0.2 seconds of handoff service per second, and that model's ceiling would be 10 million per second. Those assumptions do not establish actual utilization, CPU time or latency: measure the target's contention, bursts and surrounding work before claiming a ceiling.

For metrics with occasional scrapes, compare LongAdder in Java and padded atomic stripes or local batching in C++. A stripe is not necessarily private to one thread. Readers scan cells and accept a non-snapshot live total; joins give an exact final total. Measure again with the real reader frequency, because scanning also costs time and cache traffic.

Write code
Write a RequestStats class with record(endpoint), called by many request threads, and total(endpoint), called occasionally by a reporting thread. Choose your primitives for a write-heavy load and justify them in two sentences.
Model answer

Justification: atomic per-key creation prevents duplicate counter objects, and each counter safely accepts concurrent updates; the C++ version also locks the map and uses relaxed atomics only for statistics. Java's adder spreads hot-key writes, while the C++ version is a baseline to profile before substituting striped counters or sharding the map's shared mutex.

Explain
An interviewer asks: "Why not always use LongAdder instead of AtomicLong?" Give a complete answer.
Model answer

Because they answer different questions. AtomicLong gives every caller the exact result of its own update, incrementAndGet returns the new value, and supports compare-and-set, so it is the tool for id generators, limits ("only the first 100 get in") and any decision based on the current value. LongAdder.increment() returns nothing, and sum() is not an atomic snapshot while others are adding, so it cannot make those decisions.

LongAdder is usually preferable for highly contended metrics with occasional reads. Its costs are extra memory, with a cell table that can grow to a power of two around the CPU count, and slower reads that scan that table. It supplies neither CAS nor an exact concurrent reset boundary. So I would start with AtomicLong for low contention or coordination, use a CAS loop for conditional limits, and measure LongAdder for write-heavy statistics.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Our request counter is atomic, but throughput falls when we add workers. What would you investigate, and what would you change?"
What a strong answer covers
  • Separate correct atomic updates from scalable throughput and check for cache-line contention
  • Confirm the required read semantics and measure representative writer and reader loads
  • Use LongAdder in Java or padded atomic stripes in C++, with possible stripe collisions
  • Explain scan cost, extra memory, non-snapshot live reads and exact totals after joining writers
  • Keep atomic reservation or locking for unique ids and hard limits; measure again after the change
How a senior would say it
I would investigate contention on the counter's cache line, then choose a replacement based on what readers need. Atomic increments prevent lost updates, but they do not make one shared location scale across cores. Repeated transfers of write ownership can cost much more than adding one. First I would check the profile, the number of runnable writers, and how often readers scrape the value. I would compare representative loads rather than trust one timing on an idle laptop. If this is a metric read occasionally, I would try LongAdder in Java or padded atomic stripes in C++. Writers spread their updates across cells, which reduces competition for one location. Stripes can still collide, so their updates remain atomic. The costs are extra memory and a scan on every read. A live sum is not a snapshot, while the final total after joining all writers is exact, assuming no overflow. If we only need a final total, local counting followed by one merge per worker is another option. For unique ids or a hard admission limit, I would retain an atomic reservation or a lock. Finally I would measure throughput and tail latency again, including the actual scrape load, to confirm the change helps.

Likely follow up: Would switching the C++ increment to relaxed ordering remove the bottleneck?

Out loudabout 90 s
"We need exact counts for each reporting minute. Can we just call sumThenReset(), or swap in a new striped counter?"
What a strong answer covers
  • Neither separate cell resets nor a reference swap establishes an exact interval boundary by itself
  • Explain a writer retaining the old counter across the swap
  • Define whether the boundary follows event time or the recording operation, then coordinate writers
  • Use cumulative totals and reader-side deltas when approximate reporting periods are acceptable
  • Bound locally buffered events separately from visibility or scheduling delay
How a senior would say it
Neither operation alone gives an exact reporting boundary. I would first define whether an event belongs to a minute by its timestamp or by when recording it takes effect. Those are different contracts, especially when a worker pauses across the boundary. sumThenReset() handles components separately, so it does not divide all concurrent updates at one instant. Swapping the current counter reference has another race. A worker can obtain the old counter, pause, and increment it after the reporting thread swaps and reads it. That update can disappear from reports even though the increment itself was thread-safe. For an exact operation boundary, I would coordinate recording and rollover with one lock, or use a proven epoch handoff that waits for old writers to finish before reading the retired counter. Timestamp-based reporting also needs a policy for late events. The coordination cost is part of the requirement. For ordinary metrics, I would prefer cumulative counters and subtract successive scrapes, accepting fuzzy intervals. If each of P workers buffers at most B events, at most P times B events are locally unpublished. That does not bound every reader's visibility lag. A timer alone also cannot guarantee a deadline when the scheduler can pause its worker.

Likely follow up: How would key eviction race with a thread that has already looked up that key's adder?
