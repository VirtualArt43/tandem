Parallel level BFS

Executors and asynchard60 minRubrikGoogle

A fast worker must not turn a breadth-first traversal into a race between path lengths. Coordinate whole levels while keeping work inside a level parallel.

The task

Implement ParallelBfs.distances for an immutable directed, unweighted adjacency list. Use p worker threads, a CAS to claim newly discovered vertices, private next-frontier buffers and a reusable barrier between levels. Return each shortest distance from source, with -1 for unreachable vertices.

Rules

  • p is positive. Validate endpoints and source before launching workers. An empty graph with source zero returns an empty result. Duplicate edges, self loops and cycles are valid.
  • Claim a vertex before adding it to a next-frontier buffer. Exactly one worker may schedule that vertex, and it is visited exactly once. Source distance is zero. A worker processing level d + 1 must wait until all processing at level d finishes.
  • Use exactly p workers for a nonempty graph, even when some have no frontier entries. All workers participate in every barrier phase until the frontier is empty. The caller joins them before returning.
  • The thread safe probe is called once just before scanning each reached vertex's edges, with its vertex and level. It may block or throw an exception. A failure ends the traversal after the current phase, joins workers and propagates an exception; it must not strand peers at the barrier. Java caller interruption is restored and reported after workers finish.
  • The graph and probe remain alive and unchanged until return. Thread creation and allocation succeed at the bounded exercise sizes. No worker cancellation or scheduling fairness is promised.

Worked example

For edges 0 -> 1, 0 -> 2, 1 -> 3 and 2 -> 3, the distances are [0, 1, 1, 2]. Vertex 3 is claimed once, and its callback starts only after both level-one callbacks finish.

What the tests check

  • Distances match a sequential BFS on deterministic graphs and eight shuffled random graph traversals.
  • A diamond, repeated edges, a self loop and a cycle schedule each reachable vertex only once; disconnected vertices stay unvisited.
  • A broad level holds four callbacks simultaneously. A counter proves four active workers and the next level remains untouched until release.
  • Empty input, invalid worker count and a callback exception finish without leaving barrier participants blocked. Bounded joins and a watchdog catch deadlock.

Taught in: Barriers and phasers

Open them one at a time. Each one gives away a little more.

A successful -1 to level + 1 CAS is permission to enqueue, not just a distance assignment.
A worker with no frontier entries still arrives at the barrier. Otherwise the number of participants changes mid-round.
Separate “all buffers are complete” from “the merged frontier is published.” Use two rendezvous phases, or a barrier completion action with the same ordering.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What did the Rubrik report specifically describe?
The 2022 report describes threaded BFS level by level with a barrier. It lists no follow-ups. The failure handling and performance extensions here are additional practice.
How does this relate to the Google shared-distance-grid report?
Concurrent discovery needs an atomic claim. The level boundary makes the first claim shortest for unit edges. Without that boundary, atomicity alone does not prove a shortest distance.
Can one barrier replace the two waits?
Yes, if the merge is its completion action and is guaranteed to finish before any participant returns. A wait followed by an ordinary leader-only merge does not provide that guarantee.
What if one vertex has millions of outgoing edges?
Static vertex partitioning is imbalanced. Split large adjacency ranges into level-local tasks or steal work, then detect completion of all tasks before advancing.
Can this handle weighted edges?
Not by keeping the same first-claim rule. Weighted shortest paths need relaxation and a suitable ordering or convergence argument, such as a parallel priority or bucket scheme.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

Key idea and invariants

The current frontier contains exactly one distance level and is immutable while workers scan it. CAS gives each undiscovered vertex one owner. Only that owner appends it to its private buffer. At the first barrier every buffer is complete; worker zero merges and clears them; the second barrier publishes that new frontier and level before any worker reuses a buffer.

Why these primitives

An atomic distance makes discovery indivisible. Per-worker vectors avoid a lock for every edge. The reusable barrier publishes ordinary frontier and buffer memory on each phase. The C++ barrier uses a mutex, condition variable and generation predicate to handle reuse and spurious wakeups. Joining makes final results and captured failures visible to the caller.

Pitfalls and broken interleaving

The broken answer keeps only the first rendezvous. Worker B returns from that wait and starts reading the old frontier while worker A is merging the next frontier. Java can revisit old nodes or reach inconsistent barrier phases; C++ also accesses a vector concurrently with its mutation. A barrier before a leader's work does not publish the work that happens afterward. Throwing directly out of a worker before its barrier would similarly strand its peers, so failures are recorded and everyone completes the phase.

How to say it in the interview

“CAS decides who owns a vertex; the barrier decides which distances may be discovered now. I need both. I will first prove that each frontier is one complete level, then show how each buffer is published and reused.” Total edge and vertex work is O(V + E), with O(p) coordination per reached level. A narrow or skewed frontier limits parallel speedup.
