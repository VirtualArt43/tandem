A fixed-size worker pool accepts every task into an unbounded FIFO queue. Its sustained arrival rate exceeds its processing rate. What follows if this continues?
Why. More work arrives than the fixed workers remove, so pending work accumulates. This queue supplies no finite capacity threshold that would block or reject submissions, and the stated pool cannot add workers. The time to exhaust memory depends on spare memory, task sizes and the excess arrival rate; one hour is not a universal threshold.
From: Blocking queues
A timed take is written as: lock; while (queue is empty) { wait on the condition for up to 100 ms; }; then take. Several producers often call notify-all for unrelated reasons. What is the bug?
Why. A timed operation must fix its deadline once and wait only for the time that remains (wait_until(deadline), or the value awaitNanos returns), and must return "nothing" when the deadline passes. As written, the loop never exits on timeout, and each wakeup grants another full 100 ms. Timed waits do release the lock while waiting.
From: Blocking queues
Why can the two-lock linked queue let one producer and one consumer modify the queue at the same instant, while a single-mutex bounded queue cannot?
Why. ArrayBlockingQueue has one lock for both ends, so a put and a take serialize. LinkedBlockingQueue keeps a dummy head node so producers only touch the tail and consumers only touch the head; the atomic count tells each side whether the other has made the queue non-empty or non-full, and its increment and read carry the happens-before. It is still a locking, FIFO queue.

A producer writes payload.value = 42, successfully enqueues the payload, and never mutates it again. A consumer takes it and prints value. With Java's BlockingQueue or our C++ monitor queue, what is guaranteed?
Why. The successful hand-off carries a happens-before edge, so the consumer sees 42 without making the field atomic or volatile. This is not unique to ArrayBlockingQueue. A later unsynchronized producer mutation would need separate coordination; enqueueing does not publish future writes.

A delay queue holds one item due at 10:00:05, and the only taker is sleeping until then. A producer adds an item due at 10:00:01. Which notification policy is sufficient and avoids wakes for insertions that leave the head unchanged?
Why. The taker computed its sleep from the old head. Unless put signals when it installs a new earliest item, that item is served four seconds late. Waking everyone on every put would be correct but wasteful; the precise rule is "signal when the head changes".

Two threads each repeat "get key k's count, add one, put the result" 1,000 times. The count starts at 0; each get and put is atomic, as in a concurrent or striped map, but the pair is not. What can the final value be?
Why. Each call is atomic, but the pair is not. To reach 2, A first reads 0 and pauses; B completes 999 increments; A writes its stale 1; B reads that 1 for its final increment and pauses; A finishes its remaining increments; B finally writes 2. Sequential execution yields 2,000, and intermediate schedules yield intermediate values. There is no collection exception or nested-lock deadlock here. merge(k, 1, Integer::sum) makes each increment atomic.

Why does the lesson's striped map use a separate ordinary hash table inside each stripe, rather than several locks around one shared ordinary table?
Why. The lock boundary must match the state being modified. Independent tables isolate bucket and size changes. Reservation can avoid rehashing but does not remove all shared mutation within one ordinary table. Lookups still take stripe locks, and reading stripe sizes at different moments still produces an estimate.

A cache runs a two-second database loader while holding the bin or stripe lock used for updates. Which consequence and fix are correct?
Why. The lock covers the bin or stripe, not just the key. Reentrancy does not let other threads acquire a held lock, and more stripes cannot separate two updates to the same key. Installing a future first can share one in-flight load while keeping I/O outside map synchronization; define failure and retry handling too.

Two threads atomically get or create the same absent key, using Java's ConcurrentHashMap.computeIfAbsent or a C++ implementation that checks, loads and inserts under one stripe lock. The loader returns a non-null value normally, and nobody removes or replaces it. How many times does the loader run?

Neither overwriting nor a null result is permitted by the stated assumptions. Without them, a null result, exception or removal could allow another load. A separate get followed by load and put would also allow duplicate work.
From: Concurrent hash maps
A striped map with 16 stripes implements size() by locking each stripe in turn and adding its size. Meanwhile another thread removes key A (stripe 2) and then inserts key B (stripe 9). The map had 100 entries before and after. What can size() return?
Why. Each stripe is read under its own lock, so there is no data race, but the stripes are read at different moments. If stripe 2 is counted before A leaves and stripe 9 after B arrives, the sum is 101, a size the map never had at any single instant. Locking all stripes in a fixed order would give an exact snapshot at the cost of stopping every writer.

Why. With nulls allowed, null from get would be ambiguous, and containsKey is a second call that can see a different map. Banning null values makes absence unambiguous. From: Copy-on-write and immutable snapshots
Why must the function passed to AtomicReference.updateAndGet(f) (or the retryable work in a CAS loop) avoid externally visible side effects?
Why. updateAndGet reads the current value, calls f, and tries to CAS the result in; if another thread changed the reference first, it repeats with the new value. A weak CAS may also fail spuriously; implementations can reuse a computed result if the observed reference is unchanged. The API promises neither one invocation nor one invocation per CAS attempt. Sending a message inside f can therefore duplicate it; atomic publication does not roll back that effect.
From: Copy-on-write and immutable snapshots
For copying the whole structure on every update, which workload is the worst fit?
Why. Every write copies the whole structure. At 50,000 writes a second on a million entries, the copying and garbage would swamp everything. Copy-on-write shines when reads vastly outnumber writes and the data is modest in size.

For copy-and-replace RCU, snapshot MVCC and an immutable config, which description captures the shared versioning idea without assuming identical APIs?
Why. All three separate making changes visible from reclaiming older data. They do not require a global mutex, condition variable, garbage collector or per-element lock ordering. RCU alone does not promise a whole-store snapshot, and MVCC does not eliminate every source of blocking.

An LRU cache uses a read-write lock: get takes the read lock and put takes the write lock. What goes wrong under load?
Why. An LRU hit updates recency, which writes shared links. A read lock admits multiple such writers rather than excluding them, even if a particular run happens to look correct. Writer starvation is a separate possible problem, not the only one. Use exclusive protection for each list, including inside a shard, or a correctly synchronized buffered policy.

Why. The first caller installs a future and runs the load; the other 499 find the future and wait on it. Everyone gets the result when the one load finishes. Without single-flight the database would see 500 identical queries at once: a cache stampede.

Why should a TTL cache compute expiry with System.nanoTime() or steady_clock rather than wall clock time?
Why. Expiry is about elapsed time, and only a monotonic clock is guaranteed never to go backwards. Their origins are arbitrary: Java nanoTime values are meaningful only as differences within one JVM. They do not promise better precision, synchronized machine clocks or immunity from overflow; the deadline calculation must respect the clock's range.

Why. Completing the future exceptionally releases every waiter with the same error, and removing the entry lets the next caller try again. A register starts at 0. A calls write(1), which takes a long time. While it is in progress, B calls read() and gets 1. After B returns, C calls read() and gets 0. Then A's write returns. Is this history linearizable?
Why. Each read alone could see 0 or 1, but together they are a new then old inversion: B's result places the write before B's response, and C's read starts later, so its point comes after the write's. The history is sequentially consistent (order C, A, B), which is exactly why sequential consistency is weaker.

On an empty FIFO queue, A's enq(1) returns, then B calls enq(2) and it returns, then C calls deq() and gets 2. Linearizable?
Why. Real-time order fixes enq(1) before enq(2), so the only legal first dequeue is 1. If the two enqueues had overlapped, either order would be allowed and returning 2 would be fine.
From: Linearizability: what correct means
What is the linearization point of a successful push in a lock-free (Treiber) stack?
Why. The successful CAS publishes the new top and is inside the push interval. Another push or pop can immediately change the top again, so it is wrong to promise that every later pop sees that node. Allocation and the initial read are preparation; returning happens after the effect and cannot generally be its point because another pop may already have consumed it. Failed CAS attempts do not publish the attempted node.

What does sequential consistency give up compared with linearizability?
Why. Both require one total order of operations that is legal for the object and respects each thread's own order. Only linearizability also requires that an operation which finished before another began is ordered first.

How does serializability differ from linearizability?
Why. Serializability says transactions behave as if run one at a time in some order, which may not match the order they actually committed in. Linearizability is about single operations on one object and does respect real time. Strict serializability combines the two.

Queues A and B are both linearizable. A initially contains an item, B is unbounded, and a mover thread does x = A.poll(); B.offer(x);. Is "move one item from A to B" atomic for other threads?
Why. Locality says a history of single operations on linearizable objects is linearizable. The move is two operations, so other threads can observe the state in between.
