Invariants, critical sections and finding shared state

A method for any concurrent code: classify the state, write down the invariants, then draw critical sections around them, plus a 30 second scan.

Asked atRubrikLinkedInApple
Before this:The lost update: read, modify, writeCheck then act: two safe calls, one unsafe sequence

Before you can decide what to lock, you need to know what is shared and what must stay true. This lesson is the method: classify the state, write down the invariants, then draw the critical sections around them. Interviewers grade "did you pick the right critical sections?" directly.

In plain words

A shop keeps a stock register and a cash box. One rule must hold whenever anyone looks: opening cash plus today's sales equals the cash in the box. During a sale the rule is briefly false: the shopkeeper has written the sale in the register but not yet put the money in the box.

That moment is fine, as long as nobody counts the cash or makes a decision during it. The critical section is exactly that: the stretch in which the rule is temporarily broken, plus any moment in which someone relies on the rule being true. Close the door during those stretches, and only those.

Step 1: classify every piece of state

Go through every field, static variable and captured object the code touches, and put each into one of these buckets. Shared mutable state needs a synchronization policy; thread-safe objects provide one internally, and immutable objects still need safe publication.

KindExamplesNeeds synchronization?
Stack confinedLocal variables; objects created in a method that never leave itNo: only the running thread can reach them
Thread confinedThread-local storage; state owned by one thread, such as an event loop or a single writerNo, as long as the confinement really holds
ImmutableString; Java records or classes whose entire reachable state is immutable; C++ objects whose reachable state is never mutated after constructionNo, once safely published. Java final references and C++ const views alone do not make referenced state immutable
Thread-safe objectsConcurrentHashMap, AtomicLong, a BlockingQueue, std::atomic<int>Each call is safe; sequences of calls still need care
Shared mutableFields of an object several threads use and change; static counters and cachesYes: a lock, an atomic, or a redesign

Two refinements. A local variable that holds a reference to a shared object is confined, but the object it points to is not. And an object becomes shared the moment its reference escapes: stored in a field, passed to another thread, captured by a lambda that runs elsewhere, or returned from a getter. Confinement and immutability are the cheapest forms of safety, which is why the safety ladder puts them first.

Step 2: write the invariants down

An invariant is a fact about shared state that must hold whenever no thread is in the middle of changing it. Some involve one variable (0 <= size <= capacity), but the ones that cause real bugs span several fields:

  • A bank: the sum of all balances equals the total deposited.
  • A ring buffer: head, tail and count agree with each other.
  • A cache: the hash map and the recency list contain the same keys.
  • A range: lower <= upper.
  • An account: balance equals the sum of the history entries.

Multi-field invariants are where atomics stop being enough. Each field below is an atomic, every individual operation is indivisible, and the range still ends up upside down:

The rule that falls out: a lock protects an invariant, not a variable. Every field that appears in an invariant is guarded by the same lock, and that lock is held for every read and write of those fields.

Step 3: draw the critical sections

A critical section must contain three things, and should contain nothing else:

  1. Every span in which an invariant is temporarily broken, from the first write that breaks it to the last write that restores it.
  2. Every read that relies on the invariant, so that no reader can observe the broken middle.
  3. The check of every check-then-act on that state, together with its act.

Split a critical section in two and you get the bug below: every access holds the lock, there is no data race and ThreadSanitizer is silent, yet the auditor regularly sees a wrong total, because the invariant is broken between two locked blocks.

The first number changes from run to run and may be 0 if the auditor misses the gap; the second is always 0. An oversized critical section costs throughput, and blocking calls or callbacks inside it can introduce deadlock. The usual shape is prepare outside, commit inside: compute what you can from local data with no lock held, then lock, re-check that the state you based your work on has not changed, and apply the change.

The invariant must also survive exceptional exits. A lock guard or finally releases the lock; it does not undo a partial update. Prepare potentially failing work before mutation where possible, or roll back changes before exposing the state again.

Write down what guards what

A locking scheme that lives only in one person's head breaks at the next code change. Next to every shared field, write which lock guards it and which invariant it belongs to: a guarded by comment at minimum. Tools can then check it. In Java, the @GuardedBy annotation is checked by static analyzers such as Error Prone. In C++, Clang's thread safety analysis (-Wthread-safety) checks GUARDED_BY annotations at compile time, given a mutex type annotated for it, such as Abseil's absl::Mutex.

Never let this escape from a constructor

An object is safe to share only after its constructor has finished. If the constructor itself hands this to another thread, by starting a thread that uses the object, registering it as a listener, or storing it in a static, the other thread can see the object half built: fields still at their default values, and in Java even final fields lose their special guarantee. This is the this escape bug.

Since JDK 21, javac -Xlint:this-escape warns about some of these leaks in public classes. The C++ version hides in the class layout: member initialization order is declaration order, regardless of the order in the constructor's initializer list.

The 30 second scan

Put the method together into a checklist you can run on any snippet, in a code review, a debugging round, or on code you just wrote in an interview:

  1. What is shared? Fields, statics, captured and passed objects. Ignore true locals.
  2. Is it mutable after publication? Immutable and safely published means done.
  3. What are the invariants? Which fields must change together?
  4. Any compound operations? Read-modify-write, check-then-act, iterate-then-modify: each whole span must be atomic.
  5. One lock per invariant, everywhere? The same lock for every read and write of those fields, including getters, size() and toString().
  6. Every hand-off ordered? Data passed between threads must ride a lock, an atomic or volatile, a start or join, a queue or a future.
  7. Anything slow or foreign under a lock? I/O, sleeps, waiting on other threads, callbacks into unknown code.
  8. Lifetimes and escapes? this leaking from a constructor, a getter returning internal mutable state, a C++ thread outliving its data.

Worked example: the state of a multithreaded web crawler

Rubrik's crawler question was judged on "picking the right critical sections and the right places to create threads", and Databricks asks the same crawler with a "now make it multithreaded" follow up. Before writing any code, classify the state:

StateKindInvariant it takes part inProtection
Start URL, host name, depth limitImmutable after startNoneNone: set before the threads start
visited setShared mutableEvery URL is fetched at most onceAn atomic add-if-absent: Set.add on ConcurrentHashMap.newKeySet() returns true only for the first adder; in C++, insert under one mutex, using its returned flag
The frontier of URLs to fetchShared mutableEvery URL that won the visited race is fetched exactly onceA thread-safe queue, or a pool you submit tasks to
Pending work countShared mutableThe crawl is done exactly when nothing is queued or runningIncrement before handing a URL off, decrement after processing it; finished when it reaches 0
Result listShared mutableContains each crawled URL onceA concurrent queue, or per-thread lists merged at the end
The page being parsedStack confinedNoneNone

Now the critical sections are obvious and small. "Check visited, then add" is one atomic step: the check-then-act from the last lesson. Fetching and parsing, the slow parts, hold no lock at all. And the pending counter's order matters: if a worker decremented its own count before incrementing for the links it found, the count could touch 0 while work remains, and the crawler would stop early. Saying that out loud is exactly what "picking the right critical sections" means.

Common mistakes

  • One lock (or one atomic) per field when an invariant spans fields. Each field stays consistent, the relationship between them does not.
  • Splitting a critical section. Lock, read; unlock; compute; lock, write: someone else can change the state in the gap. Re-check after relocking, or keep it one section.
  • Unlocked reads. A getter, size() or toString() that skips the lock sees broken middles, and in C++ it is a data race.
  • Returning internal mutable state. A getter that returns the guarded list hands callers a way around the lock. Return a copy taken under the lock, or an immutable snapshot.
  • Starting threads or registering listeners in a constructor. Use a factory or a separate start(); in C++, declare thread members last.
  • Locking everything just in case. Over-locking hides which state matters and invites contention and deadlock. Lock what an invariant needs; confine or freeze the rest.

In the interview

This is the "make it thread-safe" step of almost every LLD and coding question: the LRU cache, the crawler, the parking lot, the booking system. Apple interviewers have asked which parts of an elevator design are critical sections; LinkedIn interviewers have asked candidates to give, for each lock they add, an example of the race it prevents. Rubrik's crawler was graded on the choice of critical sections.

First I'll classify the state: what is immutable, what is confined to one thread, and what is shared and mutable. For the shared part I'll write down the invariants, which fields must change together, and guard each invariant with one lock, held for every read and write of those fields. Then I'll keep the critical sections to the spans where an invariant is broken or relied on, and keep I/O outside them.

Follow ups to expect: "Why not make every method synchronized?" (it does not fix sequences, and it serializes work that touches no shared state). "Why not one atomic per field?" (multi-field invariants). "What race does this lock prevent?" (name the interleaving). "Is it safe to start the worker in the constructor?" (no: this escape).

Senior depth

Invariants decide lock granularity. Independent invariants can have independent locks, which is the whole basis of lock striping: each bucket of a hash map is its own little invariant. Conversely, if one operation must keep two structures consistent, they need one lock or a careful ordering of two. Choosing granularity is choosing which invariants you are willing to check together.

Preconditions are invariants about the future. "take() needs a non-empty queue" is a precondition that may be false now and true later. Instead of failing, a concurrent method can wait for it, which is exactly what condition variables are for; see condition variables.

Read-mostly state. When an invariant spans a large structure that is read far more than written, consider replacing it wholesale: build a new immutable version and publish it with one atomic reference swap. Readers never lock and always see a consistent version; see copy-on-write and snapshots.

Key takeaways

  • Classify state first: stack confined, thread confined and immutable state need no locks; only shared mutable state does.
  • Write down invariants, especially the ones that span several fields; a lock protects an invariant, not a variable.
  • A critical section covers every span where an invariant is broken, every read that relies on it, and every check-then-act on it, and nothing slow besides.
  • Document which lock guards which field; never let this escape a constructor, and declare C++ thread members last.
  • Run the 30 second scan on any concurrent code: shared, mutable, invariants, compound operations, same lock, hand-offs, slow work, escapes.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A service object is shared by many request threads. Which of these need synchronization (or a thread-safe type)? Select all that apply.Select all that apply
Why. Only shared mutable state needs protection: the map field and the static counter are reached and changed by many threads. Locals and objects that never escape their method are confined to one thread, and an immutable, safely published field can be read by everyone without locks.
A range keeps lower and upper in two AtomicIntegers (or std::atomic<int>), starting at (0, 10). setLower(v) checks v <= upper and then sets lower; setUpper(v) checks v >= lower and then sets upper. Thread A calls setLower(5) while thread B calls setUpper(4). What final state is possible?
Why. Each individual read and write is atomic, so there is no data race, but the invariant lower <= upper involves both fields, and each method checks one field and writes the other with a gap in between. One lock guarding both fields, held across each check and write, is the fix.
transfer does: lock; a -= x; unlock; lock; b += x; unlock. An auditor thread takes the same lock and computes a + b. What can the auditor see?
Why. Locking every access prevents data races, not broken invariants. Between the two critical sections the invariant is false and the lock is free, so the auditor can take it and see the middle state. The whole transfer must be one critical section.
A class guards its orders list with a lock, and getOrders() takes the lock and returns the list object itself. What is wrong?
Why. A lock protects data only while every access goes through it. Returning the internal list lets the data escape the lock: callers iterate it while another thread adds to it, or modify it directly. Copy under the lock (List.copyOf(orders), or return a std::vector by value).
A constructor starts a thread that reads a field before the constructor has initialized it for that worker, with no further synchronization. What can happen in Java and C++?
Why. Thread start publishes work done before the start, not assignments that happen afterwards. Java default-initializes fields, so the worker can observe null or 0; final does not rescue this premature access. C++ does not generally default-initialize scalars to zero, and racing accesses or using members before construction can be undefined behavior. Finish initializing everything the worker uses before starting it, and preserve those objects until it stops.
Java onlyList<String> list = Collections.synchronizedList(new ArrayList<>()); One thread iterates the list with a for-each loop while others call add. What does correct code need?
Why. A synchronized wrapper locks each call, not a sequence of calls, and iteration is a long sequence of hasNext and next calls. Its documentation requires callers to hold the list's own lock while iterating (streams too). That is client-side locking, and forgetting it gives ConcurrentModificationException at best.
C++ onlyA class declares its members in this order: std::jthread worker_ (whose function uses m_ and jobs_), then std::mutex m_, then std::deque<Job> jobs_. What is wrong?
Why. The jthread member starts its thread as soon as it is constructed, before the members declared after it exist. Declaring it last fixes both ends: it starts after everything it needs, and since members are destroyed in reverse order, it is stopped and joined before them.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
An Inventory class has Map<String, Integer> stock (units per product), int totalUnits (the sum of all stock), List<String> auditLog (one line per change), a String warehouseName set in the constructor, and a long lastRestockMillis that a dashboard reads. Many threads call restock(product, n), sell(product, n) (fails if there is not enough stock) and report(). List the shared state, the invariants and the critical sections.
Model answer

Classification: warehouseName is immutable, so it needs nothing once the object is safely published. stock, totalUnits and auditLog are shared and mutable. lastRestockMillis is shared and mutable, but on its own.

Invariants: totalUnits equals the sum of the values in stock; no product's stock is ever negative; every change to stock has exactly one line in auditLog, in the order the changes happened. All three involve stock, so stock, totalUnits and auditLog share one lock.

Critical sections: restock locks, updates the product's stock, totalUnits and the log together, then unlocks. sell is a check-then-act, so the check "enough stock" and the decrement, the total and the log line all happen under the same lock. report reads the map, the total and perhaps the log under the same lock, copying what it needs, then formats the report outside the lock. Formatting log lines can also happen before taking the lock. lastRestockMillis is not part of the invariants, so it can be volatile (Java) or a std::atomic<long long> (C++), written inside restock and read by the dashboard without the lock. If it had to agree exactly with the stock the dashboard shows, it would join the lock.

Debug
Users report a rare NullPointerException in pollForever right after startup. Explain why and fix it.
Model answer

The constructor lets this escape: it starts a thread that uses the object before the constructor has assigned endpoints. If the new thread runs first, which is rare but possible, it reads endpoints while it is still null. Even the final field guarantee does not help, because it only applies to threads that get the reference after the constructor finishes.

Fix: finish construction, then start the thread. Make the constructor private, assign endpoints and create (but do not start) the thread there, and add a static factory such as start(endpoints) that calls the constructor and then t.start(). Starting the thread after construction also publishes the fully built object to it, because thread start is a happens-before edge. In C++ the same bug appears as a std::thread or std::jthread member declared before the members its function uses; declare it last.

Explain
An interviewer hands you 40 lines of unfamiliar threaded code and asks "is this thread-safe?". Describe how you would answer in the first minute.
Model answer

I would run a fixed scan out loud. First, what is shared: fields, statics and objects passed to or captured by other threads, ignoring true locals. Second, which of those are mutable after publication; immutable, safely published state I can set aside. Third, what are the invariants: which fields must change together, such as a map and its size, or two balances and a total.

Then I check the code against them: is every read-modify-write and check-then-act a single atomic step; is each invariant guarded by one lock that every read and write uses, including getters and size(); is every hand-off between threads ordered by a lock, an atomic or volatile, a start or join, a queue or a future; is anything slow or foreign, like I/O or a callback, done while holding a lock; and does anything escape, such as this from a constructor, internal state from a getter, or in C++ a thread that outlives its data. For each problem I find, I name the interleaving that breaks it, which is the part interviewers listen for.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Here is an inventory service with a stock map, a total and an audit list. Many threads restock, sell and report. How do you decide what to lock?"
What a strong answer covers
  • Classify shared mutable state separately from confined and safely published immutable state
  • State the invariants: nonnegative stock, total equals stock sum, one audit entry per successful change
  • Guard the related fields and the entire stock check and update with one lock
  • Read a consistent report snapshot under that same lock and format outside it
  • Keep mutable internals private and preserve invariants on exceptional exits
How a senior would say it
I would start with the rules the service must preserve, then choose the lock boundary. The stock map, total and audit list are shared mutable state. A warehouse name that never changes can be read without locking once the service is safely published, and a request's local parsing variables need no shared lock. The main invariants are that stock never goes negative, the total equals the sum of stock, and each successful change has exactly one audit entry. Those rules connect the three mutable structures, so I would initially guard them with one private lock. Selling checks availability and updates the map, total and audit list in one critical section. Restocking updates the same state under that lock. Reporting must acquire it too, copy a consistent snapshot, then release it before formatting or sending the response. Three separately safe containers would still allow a report to observe a partial update. I would avoid returning the mutable map or list, because that lets callers bypass the policy. I would also check exception paths: releasing a lock does not undo half a sale. Potentially failing preparation belongs before mutation where possible, with rollback if necessary. I would split locks only after identifying independent invariants and measuring contention.

Likely follow up: Can the dashboard read the latest restock timestamp atomically without taking this lock?

Out loudabout 75 s
"Both transfer writes take the same lock, and the auditor takes it too. Yet the total sometimes drops. Explain the missing critical section."
What a strong answer covers
  • Separate locked debit and credit leave the conservation invariant broken while the lock is free
  • From balances 500 and 500, an audit between a debit of 10 and its credit sees 990
  • The whole transfer and each consistent audit must hold the common lock throughout
  • Two atomic fields or separately locked getters do not provide a consistent snapshot
  • Validate totals during transfers; a correct final total alone misses the bug
How a senior would say it
The missing critical section is the whole transfer. Locking the debit and credit separately protects each access, but releases the lock while the conservation rule is false. Suppose both accounts start at five hundred. The mover locks, subtracts ten from the first account, and unlocks. Before it credits the second account, the auditor acquires the same lock and reads a total of nine hundred and ninety. No data race occurred; the auditor observed a state the locking policy allowed it to see. I would hold the common lock from the balance check through both updates. The auditor must also hold it across both reads, so it sees either the state before the transfer or the state after it. Two atomic balances would not make their updates one transaction, and two separately locked getters would not make a snapshot. I would copy the balances under the lock and format the report afterwards. To test the fix, I would assert the total while transfers are running. Checking only after joining the workers can miss this bug completely.

Likely follow up: If each account has its own lock, how must transfers and audits acquire locks to preserve consistency without deadlock?

Out loudabout 75 s
"A worker occasionally sees missing configuration just after startup. The constructor starts it, then initializes the fields. How would you review the object's lifecycle?"
What a strong answer covers
  • The constructor exposes this before the worker's required state is ready
  • Java can expose default field values, and final does not fix premature access
  • Finish Java construction before start; thread start publishes preceding initialization
  • In C++, construct dependent members before the thread and join before destroying them
  • Declaring std::jthread last helps member ordering but does not make later constructor work or shutdown automatically safe
How a senior would say it
I would treat this as premature publication. The constructor has exposed the object to a worker before the worker's required state is ready. In Java, the worker can read a default null value before the constructor assigns the configuration, even if that field is final. I would finish construction first, then start the worker from a factory or a separate lifecycle method. Thread start publishes the initialization performed before it. In C++, I would check member declaration order as well as the constructor body. Members are constructed in declaration order, so a thread member must not start using a mutex or queue declared after it. Declaring the thread last helps: a std::jthread is then stopped and joined before earlier members are destroyed. But that is sufficient only if the worker uses already initialized state, later constructor code does not race with it, and the worker responds to stopping. With an ordinary thread I must arrange the join explicitly. I would review startup and teardown together, ensuring the worker never runs outside the lifetime of its dependencies.

Likely follow up: What if the worker is blocked on a condition variable when shutdown requests a stop?
