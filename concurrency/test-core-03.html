Your C++ stress test passes a thousand times in a row, and ThreadSanitizer reports nothing. What can you conclude?
Why. ThreadSanitizer is a dynamic data race detector, not a correctness proof. A check-then-act built from locked calls has no data race to report, untested paths remain untested, and incomplete instrumentation or suppressions can hide races. Which statement about a program with no data races is true?
Why. This is the data-race-free guarantee, the central promise of both memory models. It does not remove race conditions (the locked overdraft is data race free), it usually requires locks or atomics to achieve, and different interleavings can still legally give different outputs.

A plain boolean done (not volatile, not atomic) is set to true once by one thread, while another thread spins in while (!done) {}. How should you classify this?
Why. A write and a read of the same plain variable with nothing ordering them is a data race, no matter how few writers there are. Atomic-sized writes prevent tearing, not staleness: nothing forces the reader to look at memory again. Declare it volatile or AtomicBoolean in Java, or std::atomic<bool> in C++.

Java onlyA Java long field (not volatile) is written by one thread and read by another with no lock. Apart from seeing an old value, what else can the reader see?
Why. The Java language specification allows non-volatile long and double writes to be split into two halves; volatile ones, and references, are always atomic. Many 64-bit JVMs do not tear in practice, but the language does not promise it. Out of thin air values are exactly what the Java memory model rules out.

C++ onlyTwo threads write different members of the same struct with no synchronization: one runs s.a = 1; and the other s.b = 2;, where a and b are ordinary int members. Is this a data race?
Why. A data race needs the same memory location, and each non-bit-field member is its own location. Sharing a cache line can make this slow (false sharing), but it is not a race. The exception is adjacent bit-fields, which the standard treats as one memory location.

Two threads share int x = 0. Each runs x += 1 exactly 5 times, with no synchronization. What is the smallest final value of x that is possible?
Why. Thread A reads 0 and stalls. B does 4 full increments (x is 4). A writes 1. B reads 1 for its last increment and stalls. A does its remaining 4 increments (x is 5). B writes 2. Each thread's final write is at least 1 plus the value it read, so 1 is impossible, but 2 is reachable. Most people guess 5.

Java onlyA Java field is declared volatile int count; and two threads each call count++ 1,000 times. What happens?
Why. volatile guarantees visibility and ordering for that field, so readers see the latest write. It does not stop two threads from reading the same value before either writes. Use AtomicInteger or a lock.

C++ onlyIn C++, two threads run count += 1 on a plain int with no synchronization. What does the C++ standard say?
Why. Two conflicting accesses without a happens-before relation are a data race, which is undefined behavior: the compiler may assume it never happens and transform the code in ways that go well beyond "a wrong count". Hardware atomicity of single aligned writes does not make read, add, write atomic, and volatile is not a synchronization tool in C++.

Several processes may run "create report.lock only if it does not exist yet". What is the right way to do it?

Why. Each individual read and write is atomic, so there is no data race, but the invariant lower <= upper involves both fields, and each method checks one field and writes the other with a gap in between. One lock guarding both fields, held across each check and write, is the fix.

transfer does: lock; a -= x; unlock; lock; b += x; unlock. An auditor thread takes the same lock and computes a + b. What can the auditor see?
Why. Locking every access prevents data races, not broken invariants. Between the two critical sections the invariant is false and the lock is free, so the auditor can take it and see the middle state. The whole transfer must be one critical section.

A class guards its orders list with a lock, and getOrders() takes the lock and returns the list object itself. What is wrong?
Why. A lock protects data only while every access goes through it. Returning the internal list lets the data escape the lock: callers iterate it while another thread adds to it, or modify it directly. Copy under the lock (List.copyOf(orders), or return a std::vector by value).

A constructor starts a thread that reads a field before the constructor has initialized it for that worker, with no further synchronization. What can happen in Java and C++?
Why. Thread start publishes work done before the start, not assignments that happen afterwards. Java default-initializes fields, so the worker can observe null or 0; final does not rescue this premature access. C++ does not generally default-initialize scalars to zero, and racing accesses or using members before construction can be undefined behavior. Finish initializing everything the worker uses before starting it, and preserve those objects until it stops.

C++ onlyA class declares its members in this order: std::jthread worker_ (whose function uses m_ and jobs_), then std::mutex m_, then std::deque<Job> jobs_. What is wrong?
Why. The jthread member starts its thread as soon as it is constructed, before the members declared after it exist. Declaring it last fixes both ends: it starts after everything it needs, and since members are destroyed in reverse order, it is stopped and joined before them.
