x is an atomic integer holding 0. Thread A runs print(x.compareAndSet(0, 1)) (in C++, compare_exchange_strong with expected = 0) and thread B runs the same line at the same time. What can the two threads print?
Why. The first CAS to reach x finds 0 and writes 1; the second finds 1, which no longer matches, and fails. Two successes would mean both read 0 and both wrote, which is exactly what CAS forbids. Two failures are impossible with the strong version because nothing else changes x.

Two threads each run x.set(x.get() + 1) in Java (or x.store(x.load() + 1) in C++) 1,000 times on a shared atomic x that starts at 0. What is true?
Why. Each load and each store is atomic, so there is no data race. But read, add and write are still three steps with a gap, so two threads can read the same value and one increment overwrites the other. Atomic pieces do not make an atomic whole: use incrementAndGet or fetch_add.

From: CAS loops and atomic state machines
Why must the function you pass to updateAndGet, or the code inside a CAS loop, be free of side effects?
Why. Each failed attempt recomputes from the fresh value, so a side effect (sending a message, adding to a list) happens once per attempt. Do side effects after the loop, once the swap has succeeded. No lock is involved at any point.

From: CAS loops and atomic state machines
Sixteen threads run a CAS loop on the same variable under heavy contention. Which statement is true?
Why. A strong CAS fails only because another thread changed the value, which means that thread succeeded. (A weak CAS can also fail spuriously, which costs one more pass but does not change the picture.) So the system as a whole progresses (lock-free), but nothing bounds how often one thread loses (not wait-free). A bound like "within 16 attempts" would be a wait-free guarantee, and this loop has none: the other threads can keep winning, operation after operation. Nobody blocks and nobody holds anything, so deadlock is impossible.

Assume no overflow. Which task needs the result of an atomic read-modify-write rather than a racing striped sum?
Why. An atomic RMW assigns each id at a distinct update position; overlapping calls can still return to their callers in a different order. A lock could also serialize allocation, but a striped sum cannot identify a caller's own increment. A safely published LongAdder (or atomic striped counter) starts at 0. Thread A performs 1,000 increments; thread B calls sum() once with no ordering between the threads. There are no resets or other updates. Across possible schedules, what can B see?

Why can 16 threads incrementing one atomic counter take longer in total than 1 thread doing all the increments alone?
Why. For a hardware lock-free counter on a cache-coherent CPU, contention for write ownership explains the slowdown without any OS lock or JIT conversion to a monitor. Atomic increments do not disable interrupts on every core. The exact handoff frequency depends on scheduling and topology, and C++ does not promise that every atomic type is lock-free.

A developer stripes a counter as std::atomic<long> cells[16] in C++ (or new AtomicLongArray(16) in Java), one cell per thread, and finds it barely faster than a single atomic. Why?
Why. Several adjacent counters may share a cache line, depending on their size and starting alignment. Independent atomic elements remain atomic, but their writers compete for the line. Nothing in the declaration sums on each increment, and choosing four cells cannot by itself fix false sharing. Use target-appropriate spacing, or Java's padded LongAdder cells.

C++ onlyA pure statistics counter uses fetch_add(1, std::memory_order_relaxed), and the total is read after all threads are joined. What is true?

In the runnable example, four workers each increment the plain counter 50,000 times under the same correctly implemented spinlock. The main thread joins all workers before printing. Assuming the workers finish, what count must it print?
Why. Mutual exclusion prevents lost updates, release/acquire orders accesses between owners, and joins order the final read. Thus 4 times 50,000 is 200,000 in both languages. On a single core with strict priority scheduling, low priority thread L holds a spinlock. High priority thread H becomes runnable, preempts L and spins on the same lock. What happens?
Why. Under the stated strict scheduler, runnable H always wins over L, so L cannot reach unlock. The user-space flag does not register an owner or request priority inheritance. From: Spinlocks, backoff and when spinning beats blocking
Why does a good spinlock add randomness (jitter) to its exponential backoff?
Why. Identical delays can synchronize retry bursts; random delays spread them out and may reduce collisions. This is not necessarily livelock, because one contender can still succeed on every handoff. Jitter does not impose admission order, prevent preemption or preserve the loop against compiler removal; atomic accesses supply the required semantics.

A correct Treiber stack holds A on top of B. Threads T1 and T2 call pop() at the same moment, and no one pushes. What can they return?
Why. Both read head A, but only one CAS from A to B succeeds. The loser's CAS fails, it re-reads head B and pops B. Returning A twice would need two successful CASes from A, which compare-and-swap rules out; returning empty would need the loser to see a null head, which never happens while B is on the stack.

From: A lock-free stack and the ABA problem
Why is the classic ABA problem rare in a Java Treiber stack that allocates a new node on every push?
Why. The thread that is about to CAS holds a reference to the old head, so that object stays alive and no fresh node can have the same identity. The head can return harmlessly to the unchanged old node if pushes above it are undone. Harmful reuse needs recycling or repeating logical values. Reference CAS uses ==, not equals; it supplies no hidden version stamp, and locking would not detect history either.

From: Blocking, lock-free and wait-free
A lock is written as while (!flag.compareAndSet(false, true)) { } with flag.set(false) to release. The code has no lock() call anywhere. What progress guarantee does code protected by it have?
Why. If the thread that set the flag is stalled, every other thread spins until it releases: that is the definition of blocking. What matters is whether threads can be made to wait for a particular other thread, not which instruction implements the wait.
From: Blocking, lock-free and wait-free
What does wait-free promise that lock-free does not?
Why. Lock-free guarantees system-wide progress: some thread always finishes. Wait-free guarantees per-thread progress. They need not be faster or avoid CAS: either is compatible with wait-freedom. The defining property is bounded per-caller work, assuming that caller continues taking steps.
From: Blocking, lock-free and wait-free
A benchmark with 32 threads hammering one stack shows a mutex-protected stack beating a Treiber stack. What is the most plausible explanation?
Why. Lock-free removes waiting on a specific thread; it does not remove contention. Under heavy contention failed attempts and cache line traffic can cost more than orderly handoffs through a mutex. That can happen on multicore systems without any correctness bug. A performance result alone is neither evidence of ABA nor a proof that the benchmark is sound.

A counter starts at 0. T reads 0 and pauses. U atomically increments to 1 and returns. T resumes, tries a strong CAS from 0 to 1, then retries using the refreshed value. No other update runs. What is the final value, and what does this show?
Why. U already changed the counter to 1, so T's expected 0 cannot match. T retries from 1 and writes 2 without U taking another step. This demonstrates progress despite a paused updater, not a bound on retries under arbitrary interference. CAS never blindly overwrites a mismatching value.
From: Blocking, lock-free and wait-free
C++ onlyBig meets the requirements for std::atomic<Big>. You only know that std::atomic<Big>::is_always_lock_free is false. What follows?
Why. False means not always lock-free, which includes implementations that are sometimes lock-free as well as those that never are. It does not itself prove an internal lock on this run.
