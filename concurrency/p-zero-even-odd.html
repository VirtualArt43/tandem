Print zero even odd

Ordering puzzlesmedium25 minLeetCode 1116

Three threads, and the next one to run depends on a number, not on a fixed rotation. This is where "wake one waiter" stops being safe with a shared condition, and where you learn to model a puzzle as a small state machine.

The task

One ZeroEvenOdd object is shared by three threads. Thread A calls zero(), thread B calls even() and thread C calls odd(). Together they must print the sequence 0 1 0 2 0 3 ... 0 n: a zero before every number from 1 to n. For n = 5 the output is 0102030405.

  • zero() prints only 0, exactly n times.
  • even() prints only the even numbers 2, 4, 6 and so on up to n.
  • odd() prints only the odd numbers 1, 3, 5 and so on up to n.

Each method prints by calling printNumber.accept(x) in Java, or printNumber(x) in C++.

Rules: the threads start in any order. A waiting thread must block, not spin. No sleep to arrange the order. Each method prints only its own kind of number (zero() must not print 1 on behalf of odd()). Each object serves one run; the tests create a fresh one per round. In C++, ThreadSanitizer must stay quiet.

What the tests check

  • With only the even and odd threads started, nothing is printed for 200 ms and both are blocked, not spinning. Then zero starts and the output for n = 4 is exactly 0 1 0 2 0 3 0 4.
  • The exact sequence for n = 1, 2, 3, 5, 10, 25 and 50, with all 6 start orders of the three threads, repeated (20 rounds per order for small n, fewer for large n), rotating through three start styles: one after another, 1 ms apart, and released together.
  • Every number is printed by the right method: zero() only zeros, even() only even numbers, odd() only odd numbers.
  • No round hangs, no exceptions, and in C++ no ThreadSanitizer report.

Taught in: Making threads take turns

Open them one at a time. Each one gives away a little more.

Write down the state that decides who prints next. Two facts are enough: is a zero due, and if not, which number comes next? Each thread waits until that state says it is its turn.
Keep zeroTurn (true at the start) and next (starts at 1) under one lock. zero waits for zeroTurn, prints 0 and sets it false. odd printing k waits for !zeroTurn && next == k, prints k, adds one to next and sets zeroTurn back to true. even is the same with even k.
Who should be woken after each step? With one shared condition, wake all (notify versus notifyAll: notifyAll, notify_all): waking one may wake the wrong thread. Better, give each thread its own condition on the same lock and signal exactly the one that owns the new state: after a zero, odd if next is odd, else even; after a number, zero.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why does notify() (or notify_one()) with one shared condition deadlock here?
Three kinds of waiter share one condition. Say zero has just printed and next is 3, so only odd can proceed. notify wakes one waiter of the JVM's choosing; if it picks even, even re-checks, sees it is not its turn and waits again. The single wakeup is spent (a lost wakeup), odd never hears about it, and zero is waiting for odd: everyone sleeps forever. Use notifyAll, or give each kind of waiter its own condition.
notifyAll or one condition per thread: what is the real difference?
Both are correct. notifyAll wakes every waiter on every step, so with k threads each step costs k wakeups and k minus 1 of them go straight back to sleep: a small thundering herd. One condition per thread wakes exactly the thread that can run. With three threads the difference is small; with fifty (the round robin printer) it dominates.
Solve it with semaphores instead.
Three semaphores: zeroSem with one permit, oddSem and evenSem with none. zero does, for i from 1 to n: acquire zeroSem, print 0, release oddSem if i is odd else evenSem. odd loops over 1, 3, 5: acquire oddSem, print, release zeroSem; even the same over 2, 4, 6. The zero thread decides who goes next, and releases are never lost.
Why do the three loops have different lengths, and what breaks if they do not match?
zero runs n times, odd ceil(n / 2) times and even floor(n / 2) times. If even looped n / 2 rounded up, then for odd n it would wait for a number that never comes and never return; if a thread loops too few times, the thread it should wake waits forever. Ordering puzzles fail at the ends more often than in the middle, so test n = 1 and an odd and an even n.
Can odd and even print in parallel to go faster?
No. The output is one strict sequence, so the work is completely serial: the threads only take turns, and every step is a handoff with a context switch. The puzzle tests coordination, not speed. Say so if asked: with real work, you would let the threads compute in parallel and only order the output, for example with per-slot results or a sequencer.

The idea

Model the puzzle as a state machine with two fields under one lock: zeroTurn (is a zero due?) and next (the next non-zero number). zero moves the state from "zero due" to "next due"; odd or even prints next, adds one, and moves it back to "zero due". The invariant is in every state exactly one thread is allowed to print, and the printed sequence is always a prefix of 0 1 0 2 ... 0 n.

Why each line is there

  • One lock for both fields. They change together and are read together, so they form one invariant.
  • One condition per thread. zero only ever waits on its own condition (zeroCond in Java, zeroCv_ in C++), and the same goes for odd and even. Each condition has exactly one waiter, so signal (notify_one) is safe, and each step wakes precisely the thread that can run.
  • odd and even wait for next == k, not just "my parity". Each knows the exact number it will print next, which makes the wait condition impossible to misread.
  • Wait in a loop. Spurious wakeups exist, and a loop costs nothing.
  • Loop counts. zero runs n times, odd over 1, 3, 5 up to n, even over 2, 4, 6 up to n, so every thread returns after its last number.

Pitfalls

  • notify or notify_one on a condition shared by different kinds of waiter. The wrong thread wakes, the signal is lost, and the program hangs. The tests catch it within a few rounds.
  • Loop bounds. An even loop that runs one time too many waits forever for odd n.
  • if instead of while. With notifyAll, a thread woken for another thread's turn would print out of turn.
  • Letting zero print everything. The output looks right but breaks the rules; the tests check which method printed each number.

How to say it in the interview

The order is a little state machine: either a zero is due, or the number next is due, and next decides whether odd or even owns it. I keep zeroTurn and next under one lock and give each thread its own condition. Zero waits for zeroTurn, prints, flips it and signals odd or even depending on next; odd and even wait until the state names their exact number, print, advance next and signal zero. Each condition has a single waiter, so signalling one thread is safe and nobody wakes for nothing. A single shared condition would need notifyAll, because notify can wake the wrong thread and lose the signal.
