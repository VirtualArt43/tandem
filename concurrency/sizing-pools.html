Sizing a pool

Size blocking workers from CPU demand and occupancy, cross check with Little's law, enforce dependency limits, and test tail latency.

Asked atDatabricksMetaNetflix
Before this:Inside an executor: the queue-before-max trapCPU bound versus I/O bound work

"How many threads?" comes up in design rounds, in coding follow ups and in production incidents. There is a formula to start from, a law to cross check it, a cap that overrides both, and a measurement that has the last word. A senior answer uses all four.

In plain words

Think of a bakery. A loaf needs 5 minutes of a baker's hands (mixing, shaping) and then 95 minutes in an oven, where nobody touches it. One baker can therefore keep about 20 loaves going at once, and 8 bakers can keep about 160 going. That is the formula: hands-on time and waiting time decide how many jobs each worker can juggle.

But if the bakery has only 100 oven slots, at most 100 loaves can bake at once. More dough can wait, but cannot create oven capacity. The scarcest resource sets the real limit, not the formula. In a blocking service the bakers are cores, each loaf in progress occupies a worker, and the oven slots are database connections.

First question: what does a task spend its time on?

Start with CPU time C, when a task uses a processor, and off-CPU time W while it holds a worker, such as waiting for a network call. Exclude time in the executor queue before it gets a worker. A task that is nearly all C is CPU bound; one dominated by I/O waits is I/O bound. Waiting for a contended lock instead suggests a serialization bottleneck, not spare capacity that more threads can necessarily use.

CPU-bound work: about one thread per core

For independent tasks on N available logical processors, about N workers is a starting point. More runnable threads do not create CPU capacity; they consume stack memory and can add context switches and cache disruption. N plus one is another heuristic when occasional blocking leaves a processor idle, not a universal optimum. Memory bandwidth, locks and unequal core speeds can make the best pool smaller.

  • Java: Runtime.getRuntime().availableProcessors() reports processors available to the JVM. HotSpot 21 on supported Linux containers accounts for detected CPU constraints with container support enabled. A two-CPU quota normally yields 2 if affinity permits at least two and no override is set. -XX:ActiveProcessorCount can override the reported count, and fractional quotas need separate capacity accounting.
  • C++: std::thread::hardware_concurrency() is only a hint and may return 0, so have a configured fallback. C++20 gives no guarantee of container quota awareness or of an upper bound. Inspect deployment limits separately.
  • With simultaneous multithreading (hyperthreads), the count is logical cores. For pure arithmetic, the physical core count is sometimes the better number. Measure.

I/O-bound work: cores times (1 + W / C)

Now let tasks wait. While a task waits, its core is free, so another thread can use it. The question is how many threads keep every core busy.

Derive it rather than memorize it. One thread runs a task that computes for C and then waits for W, over and over. That thread keeps a core busy only C / (C + W) of the time. To fill one core completely you need (C + W) / C threads, which is 1 + W / C. For N cores:

threads = N × (1 + W / C)

If you want the CPUs at a target utilization U below 100 percent (to leave headroom), multiply by U: N × U × (1 + W / C). Example: 8 cores, 5 ms of compute and 95 ms waiting on a database per request. W / C is 19, so 8 × 20 = 160 threads keep the CPUs busy. With 50 ms of compute and 50 ms of waiting, it is only 8 × 2 = 16.

This estimates worker occupancy for independent, blocking tasks with overlapping waits, enough offered work and no other bottleneck. Use the CPU budget allocated to this workload, not the entire machine for every pool. C must be positive; when computation is negligible, size from traffic and downstream limits rather than an enormous W / C ratio.

Measure wall duration from task start to finish and CPU time on that same worker. Their difference includes scheduling delays, CPU throttling and runtime pauses as well as I/O, so profile the cause before treating it as useful overlap. Java's counter below measures platform threads; the C++ counter uses POSIX, not portable C++20. This synthetic example demonstrates the clocks, not a production sizing benchmark.

Output varies with host load, timer resolution and compiler optimization. Sleeping can exceed 36 ms, and printing a checksum does not stop an optimizer simplifying the arithmetic. For real sizing, warm up representative work, measure several load levels without sanitizers, and investigate large wall-minus-CPU gaps rather than automatically increasing concurrency.

Cross check with Little's law

The CPU formula asks how many workers could use your CPU budget. Little's law cross checks traffic: L = lambda × T, using long-run averages over the same stable system boundary. Use the admitted rate, equal to departures in equilibrium, not rejected traffic. No particular arrival distribution is required, but this is not a formula for p99 latency.

At 2,000 completed requests a second and 100 ms holding a worker, average worker occupancy is 200, so start above 200 for headroom if other resources allow it. If 100 ms instead includes waiting in the executor queue, 200 is queued plus executing requests, not busy workers. For the queue alone, average queue length is throughput times average queue wait.

Loading the littles law simulator

With 8 available cores and 5 ms of CPU per request, the ideal CPU ceiling is 8 / 0.005 = 1,600 requests a second, so 2,000 is impossible under those assumptions. The smallest resource ceiling bounds capacity: cores / C, workers / (C + W), and downstream concurrency / time holding that resource. These are optimistic ceilings, not guaranteed throughput. If each request makes k dependency calls, divide that dependency's call capacity by k; measure changing service times under load.

The cap that overrides both: the downstream

Suppose the formula says 160 workers, but the database handles 100 concurrent queries well and degrades beyond that. With one query per task and no separate limit, 160 workers can send 160 queries. Internal queueing raises latency; if arrivals now exceed completions, backlog grows. This unstable overload is not a new steady state to which you can blindly apply Little's law.

Worker count and database concurrency are different limits. Enforce the dependency budget with a semaphore or connection pool around that phase, then size workers for their whole task. For tasks spending almost all their time in one dependency, the counts may be close; they need not be equal. Bound and time out permit waiting too, or the queue merely moves into blocked workers.

  • A thread pool larger than the connection pool. With 200 workers and a configured limit of 10 connections, up to 190 workers can wait for a connection if every task needs one immediately. Those waiters use memory without increasing database throughput.
  • Several pools sharing one dependency. Five services with 100 threads each can send 500 concurrent queries to one database, even though each team "only" configured 100.

The simulator assumes fixed service times and one database call per request. Initially, 64 workers cap throughput at 640 requests a second, below 800 arrivals. With 96 workers the model can sustain 800. At 300 ms database wait, 96 workers cap throughput at about 315; raising the pool to 104 reaches the database ceiling of about 333. Raising it to 400 cannot exceed that ceiling.

Measure, then load test

Ramp offered load and pool size separately, watching throughput, p99 latency, CPU throttling, queue depth and age, rejection rate and dependency latency. Drive arrivals independently of completions so a stalled client does not hide overload. Pick the smallest pool meeting the target rate and latency with headroom; compare it with the throughput plateau, and test bursts and dependency slowdowns.

A smaller pool is not automatically safer: with an unbounded queue it can hide overload just as effectively. Pair worker limits with queue capacity, deadlines and rejection. As a rough budget, a service draining 1,000 tasks a second with 50 ms available for queueing can afford about 50 queued tasks; this fluid estimate is not a p99 guarantee. Also bound retained bytes, and skip expired work before it makes a downstream call.

Worked example: sizing an API service

8 cores. Each request does 4 ms of CPU, then waits 40 ms on a database and 5 ms on a cache. The target is 1,500 requests a second. The database is healthy up to 60 concurrent queries.

  1. Core formula: W / C = 45 / 4 = 11.25, so 8 × 12.25 = 98 threads keep the CPUs busy.
  2. CPU ceiling: 8 / 0.004 = 2,000 requests a second. 1,500 consumes 75 percent of this ideal budget, before other process work.
  3. Little's law: 1,500 × 0.049 s = about 74 requests in flight. A pool of around 96 gives headroom and agrees with step 1.
  4. The downstream: database calls in flight = 1,500 × 0.040 = 60. That is exactly the database's limit, with no headroom. Any blip in database latency pushes it over, W grows, and the spiral starts.

Answer: about 96 workers is a candidate to test, with a 60-permit database limit, bounded queue and short permit deadline. It does not make 1,500 a safe target: the database has no headroom there. Improve database capacity or reduce calls, or provisionally admit about 1,200 requests a second. At that reduced rate the mean worker occupancy is 58.8 and database occupancy is 48, so retest whether a smaller pool meets the latency target.

Common mistakes

  • Using only the CPU rule for blocking I/O. Measure W and C; the general formula reduces to about N workers when W is zero.
  • Ignoring the downstream. Additional workers can move waiting into connection acquisition or the database; enforce a separate dependency budget.
  • Sizing from averages only. Test tails and correlated slowdowns. Do not substitute p99 for the mean in Little's law; absorb bounded bursts or reject them according to deadlines.
  • Counting one pool at a time. Five pools of 200 is 1,000 threads, plus GC and JIT threads, on the same cores.
  • One pool for mixed work. CPU-heavy tasks and blocking calls can exhaust each other's workers. Separate pools provide a bulkhead, but size them within a shared CPU and memory budget.
  • Trusting hardware_concurrency() in a container. Quota awareness is not guaranteed. Read deployment constraints and make the size configurable.

In the interview

It comes as "how many threads would you use?", often as a follow up once you put a pool in your design. A Meta client-side design round asked about a file downloader, "how many threads would you want, what's a safe number"; Databricks crawler rounds asked about thread pool size against dataset size and the disk and network bottlenecks; and Netflix concurrency round discussions include how many threads to run. A number with no reasoning is a weak answer. Show the method:

First I classify the work and the CPU budget available to this pool. For CPU work I start near one worker per available processor. For blocking work I measure compute and wait time, then cross check worker occupancy with admitted throughput times time holding a worker. I calculate a ceiling for each resource and enforce the downstream limit separately. Finally I test the smallest pool that meets the target rate and tail latency with headroom, using bounded queues and explicit rejection.

Follow ups: "Where does 1 + W / C come from?" (derive the worker's busy fraction), "What if worker occupancy time doubles?" (at the same stable throughput, mean occupancy doubles; with fixed workers the ideal worker-limited capacity halves), and "Does this change with virtual threads?" (OS-thread cost changes, resource limits remain).

Senior depth

Adaptive concurrency limits adjust admission using feedback such as latency, estimated queueing and timeouts; Netflix's concurrency-limits library provides examples. Separate workload pools isolate occupied workers, while per-dependency permits limit calls. Both still need a shared CPU and memory budget. See bulkheads, timeouts and retries and queueing math for design rounds.

Also be ready for the fact that throughput can fall, not just flatten, past the knee. Contention for locks and caches grows with the number of active threads; models such as the Universal Scalability Law describe that retrograde region. In practice, this is why "more threads" is a dangerous default fix for a latency problem.

With Java 21 virtual threads or C++ asynchronous I/O and coroutines, many suspended operations can share a small set of OS threads. The blocking-worker formula no longer sizes that scheduler: use CPU demand for runnable work and Little's law for logical operations in flight. Virtual threads still consume memory, and Java 21 blocking inside synchronized can pin a carrier. Coroutines do not automatically make blocking calls asynchronous.

More workers also cannot reliably repair parents that submit children to the same saturated pool and then wait for them. Use continuations, a dependency-aware scheduler or explicit separation of blocking stages; see pool self-deadlock. Separate pools isolate worker occupancy, but still share CPU, memory and any common dependencies.

Key takeaways

  • Split a task into compute C and wait W, by measuring wall time and thread CPU time.
  • CPU bound: about the number of cores. I/O bound: cores × (1 + W / C), because one thread keeps a core busy only C / (C + W) of the time.
  • Little's law uses means over a stable, consistent boundary; the smallest CPU, worker or downstream ceiling bounds throughput.
  • Enforce dependency concurrency separately with a semaphore or connection pool; more workers cannot create downstream capacity.
  • Load test for throughput and tail latency; use bounded queues, deadlines and admission control to make overload visible.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A service has independent CPU tasks, no I/O, and 16 available logical processors dedicated to this workload. Before measuring memory or lock bottlenecks, what pool size do you start from?
Why. About 16 matches the available logical processors for independent CPU work. Four would leave execution capacity unused under these assumptions, while 64 or one worker per request creates no extra processors and can add overhead. This is a starting point; shared memory bandwidth or occasional blocking can change the measured optimum.
A machine has 4 cores. Each task computes for 10 ms and then waits 90 ms for a remote call. What does the formula cores × (1 + W / C) suggest?
Why. W / C = 90 / 10 = 9, so 4 × (1 + 9) = 40. Each worker uses CPU for 10 percent of its occupied time. Four ignores waiting, nine is only the ratio W / C, and 360 multiplies milliseconds by cores without cancelling the time unit.
In steady state an endpoint completes 500 requests a second. Each occupies one worker for 200 ms on average, excluding the executor queue. How many workers are occupied on average?
Why. 500 per second × 0.2 seconds = 100 occupied workers. The other options do not preserve those units and arithmetic. A pool below 100 cannot sustain this rate if worker occupancy stays 200 ms; either admission must fall or the backlog grows. Exactly 100 leaves no headroom for variability, and occupied workers can be blocked rather than using CPU.
The formula says 160 threads, but the database behind the service degrades sharply beyond 50 concurrent queries. What should you do?
Why. Enforce the 50-query budget separately and bound or reject excess demand. Using 160 workers without that guard can exceed the healthy concurrency, retries amplify load, and 1,000 workers cannot remove waiting at the database. The worker formula does not override a dependency's capacity.
A task spends 90 ms in the executor queue, then 10 ms on a worker: 5 ms computing and 5 ms waiting for I/O. An engineer uses C = 5 ms and W = 95 ms to suggest 20 × N workers. What is the correction?
Why. The executor queue delay occurs before a worker owns the task. Only the 10 ms worker interval belongs in C + W, and 5 ms of it is compute, leaving W = 5 ms. Calling all elapsed time compute is wrong, and using all 10 ms as W counts compute twice. Feeding congestion-induced queue delay into the formula can cause runaway oversizing.
Java onlyHotSpot 21 on Linux detects a supported container's two-CPU quota. Container support is enabled, CPU affinity allows at least two processors, and no processor-count override is set. What does Runtime.getRuntime().availableProcessors() report?
Why. With those explicit conditions it reports 2. It does not report all 64 host processors or throw merely because it is in a container. Affinity, failed container detection, disabled support or -XX:ActiveProcessorCount can change the answer; this is not a universal Java guarantee for every JVM and platform.
C++ onlystd::thread::hardware_concurrency() returns 0 on some platform. What does that mean, and what should your pool do?
Why. Zero means the hint is unavailable, not that the machine cannot execute work. Use a positive configured or conservative default size. Caller execution is a separate policy decision, and unlimited workers do not follow from missing information. The C++20 API does not guarantee awareness of container quotas.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
A service on 6 cores spends 3 ms of CPU per request and then waits 57 ms on a downstream that stays healthy up to 120 concurrent calls. The target is 1,800 requests a second. Size the pool and name the bottleneck.
Model answer

Assuming those six cores are available to this workload, W / C = 57 / 3 = 19, so 6 × 20 = 120 workers is the full-CPU starting point. CPU ceiling: 6 / 0.003 = 2,000 requests a second; the target consumes 90 percent, leaving little headroom for variability. Mean worker occupancy is 1,800 × 0.060 = 108. Downstream occupancy is 1,800 × 0.057 = 102.6 calls, or 85.5 percent of its limit. Its ideal ceiling is 120 / 0.057, about 2,105 requests a second, above the CPU ceiling. With 120 workers the worker ceiling also equals 2,000.

So: a pool of about 120, a semaphore of 120 around the downstream as a guard, and a bounded queue. The bottleneck is the CPU: at 90 percent there is little headroom for bursts, so I would either add cores (or instances), reduce the CPU per request, or plan for about 1,600 requests a second per machine. Then confirm with a load test.

Explain
Derive, out loud, why an I/O-bound pool should have about cores × (1 + W / C) threads.
Model answer

One worker repeatedly computes for C and waits for W. It consumes a processor for a fraction C / (C + W) of its occupied time. Its wait leaves execution capacity available to other tasks. To use one processor fully, I need about (C + W) / C workers, or 1 + W / C. Multiply by the CPU budget for this workload and a target utilization if I want headroom. This assumes positive C, enough independent work and waits that can overlap. Exclude executor queue time and do not treat CPU throttling or lock serialization as a reason to add threads. Downstream concurrency remains a separate limit.

Design
One service does two kinds of work: CPU-heavy thumbnail rendering (about 30 ms of CPU, no waiting) and metadata lookups (2 ms CPU, 48 ms waiting on a database that tolerates 40 concurrent queries). It runs on 8 cores. One pool or two? Size them.
Model answer

Two pools isolate worker occupancy: slow lookups should not occupy all rendering workers, and render bursts should not fill the lookup queue. But they share eight cores, so I must allocate a common CPU budget. Without target arrival rates, these are initial candidates to load test, not a unique final answer.

  • Render pool: start with 6 workers, budgeting roughly six cores for rendering. The ideal ceiling is 6 / 0.030 = 200 renders a second, with sustainable load below that for headroom.
  • Lookup pool: budget about two cores, giving 2 × (1 + 48 / 2) = 50 workers by the full-CPU formula. The database ceiling is 40 / 0.048, about 833 lookups a second, using about 1.67 cores. Start by testing 40 workers and a separate 40-query permit limit. Worker capacity is then at most 40 / 0.050 = 800 lookups a second, so target below that rather than promise 833.

Both queues need bounds and deadlines. These are accounting budgets, not CPU reservations: ordinary pools do not pin or reserve cores, and runtime work also needs CPU. If lookup tails suffer during rendering, reduce rendering admission or apply actual resource isolation. Bulkheads isolate workers, not all shared resources.

"How do you decide how many threads a blocking service needs? Derive your starting point rather than quoting a magic number."
What a strong answer covers
  • Start with this workload's available CPU budget and independent CPU work near one worker per processor
  • Derive the worker CPU fraction C / (C + W) and N × U × (1 + W / C)
  • Exclude executor queue delay and distinguish I/O waiting from throttling or lock contention
  • Use admitted throughput times worker occupancy time for mean occupied workers
  • Check dependency ceilings and load test bounded admission against tail latency
How a senior would say it
I start with the CPU budget available to this workload and the resources each request holds. Independent CPU work starts near one worker per available processor. For blocking work, suppose a worker computes for C and waits for W. It uses CPU for the fraction C divided by C plus W. Filling one processor therefore takes about one plus W over C workers. I multiply by the available CPU budget and my target utilization. I measure those times while a task owns a worker, excluding the executor queue. I also check why it is off CPU: a contended lock or CPU throttling is not spare capacity that more workers can fix. Then I cross check with admitted throughput times mean worker occupancy time. That gives occupied workers, whereas end-to-end latency includes queued requests too. Finally I calculate dependency limits, bound waiting and test the candidate size. The result is a starting point, not a promise about tail latency, and I choose the smallest pool that meets the target with headroom.

Likely follow up: What changes if the requests use virtual threads or asynchronous I/O?

"You have eight cores, four milliseconds of CPU per request, forty milliseconds in the database and five in a cache. We need fifteen hundred requests a second, but the database supports sixty concurrent queries. What would you propose?"
What a strong answer covers
  • Compute the ideal CPU ceiling of 2,000 requests per second and 75 percent CPU demand at the target
  • Compute 73.5 mean occupied workers and a full-CPU starting point of 98 workers
  • Compute 60 database queries in flight at the target and identify zero dependency headroom
  • Propose a measured worker candidate, separate database limit, bounded waiting and deadlines
  • Improve capacity or provisionally reduce admitted rate; recalculate occupancy and load test
How a senior would say it
I would not promise fifteen hundred requests a second safely with that database budget. The CPU ceiling is eight divided by four milliseconds, or two thousand requests a second. So the requested traffic uses seventy-five percent of the ideal CPU budget. Each request holds a worker for forty-nine milliseconds, giving seventy-three and a half occupied workers on average. The full-CPU formula suggests ninety-eight, so around ninety-six is a reasonable candidate to test. The limiting calculation is the database: fifteen hundred times forty milliseconds is sixty concurrent queries, exactly the healthy limit, with no room for variability. I would enforce that sixty-query budget separately, bound the executor queue and permit waiting, and carry a deadline through the request. More workers cannot create database headroom. We need fewer database calls or more database capacity, or a lower admitted rate. At twelve hundred requests a second, mean database occupancy is forty-eight and mean worker occupancy is fifty-eight point eight. That may allow a smaller worker pool, which I would retest. I would measure tail latency during bursts and slowdowns, including cache behaviour, and include other process CPU work before calling this a production size.

Likely follow up: What happens to your database budget when five service instances share the same database?
