Scheduled executors and timers

Schedule delayed and periodic work with correct cancellation, monotonic deadlines, timed waits and explicit overload policies.

Asked atLinkedInNetflixConfluentRubrikGoogle
Before this:Build it yourself: a thread pool with futures and shutdownCondition variables and monitors

"Run this in 5 seconds; run that every minute." A delayed task scheduler is reported in concurrency interviews at LinkedIn, Netflix, Confluent and Rubrik, and it tests one waiting skill a plain queue does not: sleeping until the right moment, and waking earlier when something more urgent arrives.

In plain words

A receptionist keeps a stack of appointment cards sorted by time. She looks at the earliest card, sets a kitchen timer for it, and reads a book. When the timer rings she calls that appointment, then sets the timer for the next card. If someone walks in with an appointment earlier than the one her timer is set for, they must tap her on the shoulder, or she will happily read until the old timer rings and that person will be seen late.

Two kinds of repeating appointments exist. "Every hour on the hour", like a bus timetable, is fixed rate. "An hour after the last dose", like medicine, is fixed delay.

What a scheduler promises

A scheduled executor runs a task after a delay, or repeatedly. Java names the three operations as follows; the same timing rules apply to a C++ implementation:

  • schedule(task, delay, unit): run once, no earlier than delay from now. Returns a ScheduledFuture, which you can cancel.
  • scheduleAtFixedRate(task, initialDelay, period, unit): run at initialDelay, initialDelay + period, initialDelay + 2 × period, and so on, measured from the plan, not from when runs happen to finish.
  • scheduleWithFixedDelay(task, initialDelay, delay, unit): run, wait delay after that run ends, run again.

The deadline makes a task eligible, not guaranteed to start immediately. Java's scheduled executor never starts it before that deadline, and successive executions of one periodic registration never overlap. Different registrations of the same callback can overlap.

Cancellation races with starting. A successful cancellation before execution suppresses the task. In Java, cancel(false) lets an already running body finish, while cancel(true) requests interruption; neither undoes effects nor guarantees that the body has stopped when cancellation returns. The custom scheduler below instead commits to a run when it removes the due job under its lock.

Java

The JDK version: ScheduledThreadPoolExecutor

Executors.newScheduledThreadPool(n) builds a ScheduledThreadPoolExecutor: a core pool of n workers sharing an unbounded delay queue ordered by due time. This demo shows a one-shot task, the difference between rate and delay, and the sharpest edge in the API.

The first two lines are one-shot completed and periodic failure observed after 3 runs; the observed counts vary with scheduling. An uncaught failure suppresses later executions of that periodic registration. The future records the failure; the executor does not log it automatically. A successful periodic future never completes normally, so get() waits until failure or cancellation. Catch expected recoverable failures inside the body if the job should continue, and report failures rather than hiding them.

Use ScheduledThreadPoolExecutor directly for its policies. setRemoveOnCancelPolicy(true) removes cancelled queued tasks promptly; the default retains them until their delay elapses. maximumPoolSize does not expand this unbounded-queue executor beyond its core pool, so increasing it does not fix late jobs. Successive runs of one periodic registration have a happens-before relationship, even if different workers execute them; unrelated readers still need synchronization.

After shutdown(), new submissions are rejected, queued one-shot delays run by default, and periodic schedules stop. setExecuteExistingDelayedTasksAfterShutdownPolicy(false) drops those delayed jobs; setContinueExistingPeriodicTasksAfterShutdownPolicy(true) keeps periodic jobs active, which can prevent termination. shutdownNow() attempts interruption and returns queued work; it cannot forcibly stop an uncooperative callback.

The older java.util.Timer uses one thread, and an uncaught task exception terminates that timer thread, preventing all its later tasks. Its wall-clock-based scheduling is sensitive to clock adjustments. Prefer ScheduledThreadPoolExecutor for this use case; OpenJDK measures its relative deadlines with System.nanoTime().

C++

What C++ gives you

The C++20 standard library has no scheduled executor or timer callback service. Libraries do: Boost.Asio's steady_timer with async_wait runs a handler on an io_context when the timer expires, and most event loops have an equivalent. In interviews you build one, from std::priority_queue (or a vector with std::push_heap), std::mutex and std::condition_variable::wait_until, using std::chrono::steady_clock. That is the rest of this lesson.

Building one: a heap, a lock and a timed wait

The design has one data structure and one waiting rule:

  • A min-heap of jobs ordered by due time, with a sequence number to break ties, so two jobs due at the same instant run in the order they were scheduled.
  • One worker thread loops: if the heap is empty, wait until something is scheduled; if the head is not due yet, wait until its due time, but on a condition that schedule signals; if the head is due, pop it, release the lock, run it.
  • schedule signals only when the new job becomes the head. Anything later than the current head cannot change what the worker is waiting for.

Every wait is a loop that re-checks, so it does not matter why the worker woke up: its timer expired, a new earlier job arrived, a shutdown began, or nothing at all (a spurious wakeup). Java waits with awaitNanos(remaining); C++ with wait_until(lock, due, predicate). Both use a monotonic clock (System.nanoTime(), std::chrono::steady_clock), never the wall clock, which can jump.

Cancellation is lazy: cancel(id) removes the id from a set of live jobs, and the worker drops a heap entry whose id is no longer live when it reaches the top. Removing from the middle of a heap is O(n) in Java's PriorityQueue and has no direct API in std::priority_queue, so marking and skipping is a simple choice. An indexed heap can remove a known entry in O(log n); the JDK also supports eager removal. Periodic jobs are re-inserted after each run with due + period (fixed rate), only if they are still live.

This teaching implementation uses one worker, cancels pending work at shutdown, and continues periodic work after a recoverable callback exception. It assumes successful allocation, no id or sequence wrap, and deadlines and retained overdue jobs separated by less than half the clock's numeric range. Use bounded delays in practice: Java subtraction handles nanoTime() wrap only within that range, while C++ deadline arithmetic must stay representable.

The output is illustrative: a busy host can delay submissions as well as execution, so cancellation success, ordering between relative deadlines and tick counts can vary. The latch waits for both one-shot jobs, and shutdown joins the worker; neither relies on a sleep to establish completion. The C++ demo uses C++20 std::latch and contains; in C++17 use a promise/future for completion and find(id) != end() for set membership.

Walk through the details an interviewer will poke at:

  • Tasks run outside the lock. Holding it would block every schedule and cancel for as long as a task runs, and a task that schedules a follow-up would deadlock on a non-recursive C++ mutex.
  • Removing a due job commits that run. A one-shot then leaves the live set, so cancellation returns false even if the callback has not yet begun. Cancelling a claimed periodic job returns true and prevents re-arming, but cannot prevent the claimed run. This is deliberately narrower than Java future cancellation, which may succeed during execution.
  • Fixed rate re-arms from the planned time (due + period), not from now. If a run is late, the next one may already be due and can run straight after, so the timetable catches up. Fixed delay would use now + delay after the run instead; the required changes are in the checkpoint.
  • Recoverable exceptions are logged and periodic jobs continue. Java catches RuntimeException, not fatal Error; the C++ callback boundary catches all thrown exceptions. This is a teaching policy, unlike the JDK periodic future, which suppresses later runs on failure. A production service also needs worker-failure monitoring.
  • Shutdown drops pending jobs and lets a claimed one finish, then joins the worker. The owner must also ensure other callers have stopped before destroying the C++ object. Never shut down or destroy the scheduler from inside one of its own tasks: the worker would be joining itself.
  • Bounded arithmetic. Java compares nanoTime values by subtraction, within the documented half-range assumption. C++ time points compare directly, but adding an unrepresentable delay is still an overflow bug. Zero or negative one-shot delays mean immediate eligibility; periodic intervals must be positive.

More workers: the leader and the followers

One worker thread means a slow task delays every task due after it. Two common fixes, as preparation for the reported multi-worker scheduler follow up ("now make it run tasks on 4 threads"):

  • Split timing from execution. The scheduler thread only decides when; when a job is due it hands it to a worker pool (the pool from the previous build-it lesson). Re-arm both kinds from a completion callback: fixed rate uses the previous planned due time plus period; fixed delay uses completion time plus delay. Keep at most one queued or running execution per periodic registration.
  • Several workers share the heap. Naively, every idle worker does a timed wait for the same head and they all wake at once. The JDK's DelayQueue and the scheduled executor's internal queue use the leader-follower pattern instead: exactly one thread, the leader, waits with a timeout for the head; the others wait without a timeout. A new earlier head invalidates the current leader designation and signals a waiter to time the new head. An outgoing leader wakes a successor when needed. Briefly, an old timed wait can coexist with the replacement; the design avoids giving every worker a timer for each head.

Millions of timers: timer wheels

A binary heap costs O(log n) heap work per insert and per expiry, with amortized allocation costs for a vector-backed heap. That may become expensive for a server with millions of frequently reset idle timeouts, especially when most are cancelled before firing. Measure churn and latency before replacing the heap. The classic answer is a timer wheel (Varghese and Lauck, "Hashed and Hierarchical Timing Wheels", 1987):

  • A circular array of N buckets, each a list of timers, and a cursor that advances one bucket per tick (say every 10 ms).
  • Inserting a timer due in d ticks puts it in bucket (cursor + d) mod N, for an integer d >= 1, with floor((d - 1) / N) earlier visits to skip. Thus a deadline exactly one rotation away fires on the next visit to that bucket, rather than waiting an extra rotation. Insertion is O(1).
  • Cancelling is O(1) too, by unlinking its node from the bucket's doubly linked list.
  • Each tick processes one bucket: timers whose rotation count is zero fire, the others count down.
  • The trade-off is precision: a timer fires on a tick boundary, so rounding a deadline up to a 10 ms tick adds less than one tick of quantization delay. Worker congestion or long pauses can add arbitrarily more lateness; never round down and fire early. Hierarchical wheels (like a clock's second, minute and hour hands) cover long delays with few buckets, moving timers down to finer wheels as they approach.

Netty's HashedWheelTimer is a library example. Bucket processing still costs O(k) for k entries visited; a simple rotation counter can revisit long-lived timers, and many expiries in one bucket cause a burst. In an interview, one paragraph like this is enough: say when a heap stops being good enough, and what the wheel trades away.

Worked example: the LinkedIn delayed scheduler, follow up by follow up

LinkedIn reports repeatedly describe implementing delayed scheduling like ScheduledExecutorService, sometimes with working code required. Treat those reports as examples, not a probability of being asked. Build the answer in stages:

  1. One thread, a heap, a condition. State the invariant: the worker sleeps until the head is due or the head changes.
  2. "A task scheduled later but due earlier runs late." The signal-on-new-head rule. Explain the lost wakeup it prevents.
  3. "Add cancellation." Lazy deletion with a live set; say why removing from a heap's middle is avoided.
  4. "Add periodic tasks." Re-insert after the run; state fixed rate versus fixed delay, and what happens when a run takes longer than its period.
  5. "Run tasks in parallel." Dispatch to a pool, or leader-follower workers.
  6. "Shut it down." Stop flag under the lock, signal, join; decide what happens to pending and periodic tasks (the JDK runs pending delayed tasks after shutdown by default but drops periodic ones).
  7. "What if the system clock changes?" Nothing, because you used a monotonic clock.

The same core appears as Confluent's "delayed task runner" (wake for an earlier deadline, many workers, shutdown, monotonic clock, no spinning), Netflix's "implement a scheduled thread pool executor", Rubrik's non-blocking "run this Runnable after waitTime", and a Google phone screen built around one hardware timer with callbacks registered from any thread.

Common mistakes

  • Not signalling when a new job becomes the head. The worker sleeps through the earlier deadline.
  • Polling instead of waiting: sleep(10) in a loop that checks the head. It causes unnecessary wakeups and adds polling delay, potentially more than 10 ms with scheduling overhead, and interviewers ask for "block without spinning" explicitly.
  • Using the wall clock (System.currentTimeMillis, std::chrono::system_clock) for delays. A clock adjustment runs jobs early or hours late.
  • Running tasks while holding the lock. A slow task blocks every caller of schedule and cancel.
  • wait with a fixed timeout instead of the head's due time, or a single if instead of a loop, so a spurious or early wakeup runs a job before it is due.
  • A thread per delayed task that sleeps and then runs. Ten thousand pending timers become ten thousand sleeping threads.
  • Forgetting that a periodic JDK task dies on its first exception. Catch inside the body.

In the interview

Reports: LinkedIn's concurrency round (several delayed scheduler reports), Netflix (implement a scheduled thread pool executor, sometimes as the phone screen), Confluent (a scheduler or "delayed task runner" that had to run), Rubrik (a non-blocking API that runs a Runnable after a delay; implement ScheduledExecutorService), Uber and Microsoft (job schedulers in machine coding), and Google (a delayed task scheduler over one hardware timer). Interviewers grade the waiting: no spinning, no missed earlier deadline, correct shutdown.

I keep jobs in a min-heap by due time with a sequence number for ties, guarded by one lock. A worker waits on a condition until the head is due, using a timed wait on a monotonic clock, and schedule signals only when the new job becomes the head, so an earlier job always wakes it. Due jobs are popped and run outside the lock. Cancellation marks the job and the worker skips it, periodic jobs are re-inserted at due plus period for fixed rate or now plus delay for fixed delay, and to run tasks in parallel I hand due jobs to a pool or use leader-follower workers.

Follow ups: "Fixed rate with a task slower than its period?" (runs start late, back to back, never overlapping), "Why not Timer?" (one thread, dies on an exception, wall clock), "How would you handle a million timers?" (a hashed timing wheel), and "What happens to pending tasks at shutdown?" (your choice; state it; the JDK's defaults are above).

Senior depth

Catch-up bursts. Fixed rate re-arms from the plan, so after a long pause (a garbage collection pause or a stuck task) several runs are overdue at once and execute back to back. Decide whether missed intervals should be replayed, skipped or coalesced. Replaying samples cannot recover observations that were never taken; heartbeats often need skipped ticks rather than catch-up bursts. Some schedulers let you choose; if yours does not, compute the next due time as the first planned time after now.

Time is not just a clock. For testability, inject the clock: a scheduler that takes a clock interface can be tested deterministically by advancing fake time, but inject the waiting mechanism too, or advancing a fake clock will leave a real timed wait asleep. Test earlier-head insertion, cancellation around claim, exceptions and shutdown using explicit gates. Monotonic does not specify whether a clock advances during machine suspend; calendar jobs also need a wall-clock, timezone and daylight-saving policy.

Bound the backlog. Separate eligibility lag from worker-queue delay and callback duration. An unbounded timer heap or dispatcher queue can exhaust memory. Bound admission, define rejection and missed-tick policies, and avoid caller-runs rejection on the timing thread because it makes that thread execute slow callbacks.

One hardware timer, many logical timers. Keep the same heap and arm the hardware timer for its head. Insertion of an earlier head or cancellation of the head must re-arm it under a consistent synchronization protocol. Treat an interrupt as a prompt to inspect current state: verify the deadline and generation, ignore stale interrupts, move all due jobs to a worker queue and arm the next deadline. Never run arbitrary user callbacks on the interrupt thread. The timer multiplexer problem drills this variant.

Scheduling across machines is a different problem: two instances of a cron-like service must not both run the nightly job, which needs a lease or a lock with fencing (distributed locks), not a better heap.

Key takeaways

  • A scheduler is a min-heap by due time, one lock, and a worker doing a timed wait on a monotonic clock until the head is due.
  • schedule must signal when the new job becomes the head, or an earlier job runs late; every wait is a loop that re-checks.
  • Fixed rate re-arms from the plan (catch-up, never overlapping); fixed delay re-arms from the end of the run.
  • Cancel lazily; run tasks outside the lock; in the JDK, an exception silently ends a periodic task.
  • Scale out with a dispatcher plus pool or leader-follower workers; for millions of timers, a timing wheel trades precision for O(1) insertion and cancellation with node handles.

Quick check

Answer each question, then read why. Your score is saved for your module test.

One periodic registration uses Java fixed-rate semantics with a period of 100 ms, but each run takes 150 ms. What happens?
Why. Runs of one periodic task never overlap. Each next run is already overdue when the previous one finishes, so it is immediately eligible, although workers or the OS can delay it further. A positive period is legal even when work takes longer, and fixed rate does not skip missed runs; it keeps trying to catch up with the plan, which here it never can.
The worker is waiting for the head job, due in 10 s. Another thread schedules a job due in 1 s; the schedule method pushes it onto the heap but does not signal the condition. Assume no spurious wakeup, interrupt, other signal or worker, and negligible dispatch overhead. When does the new job run?
Why. The heap is correct, but the worker is asleep with a timer set for the old head and nothing wakes it. When it finally wakes and re-checks, it runs the new job about 9 s late. Signalling when the new job becomes the head is the fix.
A scheduler waits until an absolute wall-clock deadline, rechecking that clock before dispatch. A clock correction steps the system clock back by one hour. What happens to a job that was due in 5 minutes?
Why. A wall clock deadline is an absolute time; when the clock jumps back, the remaining wait grows by the jump. A jump forward would make jobs run early. Elapsed-time clocks (System.nanoTime(), steady_clock) are unaffected by this wall-clock step. NTP need not step time; the question explicitly assumes a backward step. The deadline is neither cancelled nor immediately reached.
A fixed-rate scheduler stores previousDue = 100 and period = 100, in milliseconds. The callback finishes at 130. Its re-arm code prints next = finishTime + period, so it prints 230. What is wrong?
Why. Fixed rate advances the previous planned deadline: 100 + 100 = 200. Adding the interval to completion instead gives fixed delay: 130 + 100 = 230. No run is overdue here, so restarting at 130 is early. The timing policy never requires overlapping executions of one registration.
A server keeps an idle timeout for each of a million connections and resets it on every packet. Why might a hashed timing wheel beat a binary heap here?
Why. Resetting a timeout is a cancel plus an insert, done constantly. The wheel makes both O(1) by hashing the due tick to a bucket and unlinking from a list. It fires on tick boundaries, so it is less precise, which is fine for idle timeouts.
Java onlyA task scheduled with scheduleAtFixedRate throws a RuntimeException on its third run. What happens next?
Why. The JDK documents that an exception in any execution suppresses all later executions; get() on the returned future throws ExecutionException with the cause. Other tasks are unaffected. (It is java.util.Timer whose thread dies and takes every task with it.) Catch inside periodic bodies.
C++ onlyThe C++ scheduler's destructor sets the stop flag and calls worker_.join(). A scheduled task drops the last owner of the scheduler, so the destructor runs on the worker thread itself. What happens?
Why. Joining yourself is reported as resource_deadlock_would_occur. Destructors are noexcept by default, so the exception calls std::terminate. Never destroy a thread owner or call a shutdown method that joins the calling worker from inside that worker. A nonblocking stop request is different.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Add scheduleWithFixedDelay(task, initialDelay, delay) to the scheduler. Which lines change, and why is it different from fixed rate?
Model answer

Store which kind a periodic job is, and re-arm from the end of the run instead of from the plan. Add the flag to Job, thread it through the add parameter and initial job construction, and pass false from existing one-shot and fixed-rate methods. Reject nonpositive periodic delays. Capture completion time immediately after the callback, before reacquiring the scheduler lock, and pass that timestamp to re-arming. The heap, cancellation and waiting rules stay the same.

Fixed rate keeps a timetable, so a run that overruns the next planned deadline makes its successor immediately eligible; fixed delay guarantees a gap between runs, so it drifts later and never bursts. Choose fixed delay for polling and heartbeats where bursts are harmful, fixed rate for sampling where the timetable matters.

Design
The interviewer says: "Now tasks can be slow. Run them on 4 threads, but keep scheduling precise." Describe two designs and their trade-offs.
Model answer

Dispatcher plus pool. Keep the single scheduler thread exactly as is, but instead of running a due job it submits it to a fixed pool of 4. Slow callbacks no longer directly block deadline processing, but worker saturation can still delay actual starts. Re-arm from a completion callback for both policies, using the previous planned due time plus period for fixed rate and the captured completion time plus delay for fixed delay. This preserves non-overlap without silently skipping fixed-rate executions. Cancellation must cover the handoff: keep a per-job state and recheck it before committing the callback. Cost: one extra thread and a handoff. If the pool's queue fills, decide whether to reject, drop, or delay.

Leader-follower workers. Four threads share the heap. Only the leader does a timed wait for the head; the others wait untimed. When the leader takes a due job, it signals one follower to become the new leader and then runs the job itself. This avoids the extra handoff and the stampede of four timed waiters, and is how the JDK's delay queues work. Cost: more subtle code (who is leader must be tracked under the lock, and a newly scheduled earlier job must reset the leader and signal). In an interview I would build the dispatcher first because it reuses two pieces I already trust.

Explain
Why should schedule signal the worker only when the new job becomes the earliest? What goes wrong if it never signals, and what does it cost if it always signals?
Model answer

The worker is sleeping until the current head's due time. Only a job due earlier than that head can change what the worker should do, and that is exactly the case where the new job becomes the head. If schedule never signals, an earlier job waits until the old head's timer expires, so it runs late: a lost wakeup, which is the bug interviewers are looking for. If schedule signals every time, it is still correct, because the worker re-checks the head in a loop, but it can cause unnecessary wakeups and lock handoffs when a worker is waiting. A signal to one waiter is not itself a thundering herd; signalling all workers would add that risk. Signalling exactly when the head changes is both correct and cheap.

How a senior would say it
I would use a min-heap of monotonic deadlines, guarded by one lock, with a sequence number to break ties. One worker waits until the head is due. If another thread inserts an earlier job, it signals the condition so the worker recomputes its wait. Every wakeup goes through the predicate loop, including a timeout or a spurious wakeup. When a job is due, I remove it under the lock and run its callback outside the lock. That removal commits the run. Cancellation before the claim prevents execution; cancellation after it cannot undo the claim. For a periodic job it can still prevent future runs. I would document that boundary rather than promise cancellation always wins. For example, if I am waiting ten seconds and a job arrives due in one second, inserting into the heap alone is insufficient. The signal changes the wait. If callbacks are slow, I would hand them to a bounded worker pool. Completion re-arms periodic work, so one registration cannot overlap itself. Shutdown rejects new work, drops pending jobs under our chosen policy, wakes the worker and joins it from an owning thread. I would measure deadline lateness separately from worker-queue delay, and bound admission so overload cannot grow memory indefinitely.

Likely follow up: How would cancellation change if a job has left the timer heap but is still queued in the worker pool?

Out loudabout 75 s
"Our cleanup job stopped running, and our heartbeat sometimes runs in bursts. How would you investigate both?"
What a strong answer covers
  • Check the periodic future for failure because one uncaught exception suppresses later runs
  • Observe and report recoverable failures, rather than silently swallowing every failure
  • Explain fixed rate from the planned deadline and fixed delay from completion
  • Use a 150 ms task with a 100 ms period to explain overdue runs without overlap
  • Choose fixed delay or an explicit skip policy for heartbeats and inspect worker saturation
How a senior would say it
I would first inspect the cleanup job's scheduled future. In Java, an uncaught failure ends that periodic registration, while other tasks keep running. The future becomes done, and getting it exposes the cause. I would report the failure and catch recoverable exceptions inside the callback only if continuing is the intended policy. The heartbeat bursts suggest fixed-rate catch-up. Fixed rate advances the previous planned deadline by one period. If a run takes a hundred and fifty milliseconds but the period is a hundred, the next run is already overdue when the first finishes. It becomes eligible immediately, but the same registration never overlaps itself. Fixed delay instead waits a full interval after completion. That gives breathing room, although the schedule drifts relative to the original timetable. For heartbeats I would usually choose fixed delay, or explicitly skip missed fixed-rate ticks. Replaying old heartbeats does not repair a missed observation. Finally, I would check callback duration, pool saturation and process pauses: neither scheduling mode guarantees that an eligible job starts on time.

Likely follow up: Does cancelling the future with interruption enabled guarantee that the running callback has stopped?
