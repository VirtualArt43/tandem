Node task rebalancer

Concurrent systemshard65 minRubrik

A task can be queued on one node, running on one node, or finished. Rebalancing must never make it disappear or give it two owners.

The task

Implement an in-process scheduler with N nodes, a FIFO queue per node and one dedicated worker per queue. addTask(node, task) enqueues promptly. rebalance() transfers queued work from the busiest node to the least busy while workers keep executing. This is the local concurrency exercise from the scheduler reports; network transport and node failure are follow-ups.

Rules

  • N is positive and node IDs are in [0, N). A worker removes the front task and runs it outside queue locks. Each accepted task runs exactly once, including tasks moved between queues.
  • A rebalance considers queued tasks only, never callbacks already running. Move a suffix from a busiest queue to the back of a least busy queue, preserving that suffix's order. Repeat until queue sizes differ by at most one at the rebalance's atomic snapshot. Ties choose the lowest node ID.
  • Tasks that remain on the same node retain FIFO order. Migration changes global execution order; no ordering between different nodes is promised. Queue counts are the load metric, even if task costs differ.
  • Normal enqueue and dequeue use the relevant node's lock. A rebalance may lock all queues in node-ID order for an atomic transfer and snapshot. It must never hold a queue lock during a callback or a thread join.
  • close() atomically stops admission, wakes idle workers, drains accepted tasks and joins workers. Concurrent and repeated closes return after the same drain. Add and rebalance after closure throw. A task exception increments failedTasks() and does not stop its worker. queueSizes() is a coherent diagnostic snapshot.
  • Callbacks may enqueue but must not call close() or destroy the scheduler from a worker. Callbacks finish eventually. Thread creation and allocation succeed at the exercise sizes. There is no timeout or strict lock-fairness guarantee.

Worked example

With running callbacks held and queue sizes [8, 0], rebalance moves the last four queued tasks to node 1, leaving [4, 4]. The first four tasks stay on node 0 in their original order.

What the tests check

  • Three blocked callbacks run simultaneously on distinct node workers, measured by an active counter.
  • With all workers held, balancing conserves exactly sixteen queued tasks and leaves sizes differing by at most one.
  • Close waits for the held callbacks; every task executes exactly once and the subsequence that stays on each node preserves order.
  • Four shuffled producers and four rebalancers shift hotspots between nodes. All tasks drain, exceptions do not kill workers, concurrent close is idempotent and later admission fails. Timed joins and a watchdog bound lock cycles.

Taught in: Taking several locks safely

Open them one at a time. Each one gives away a little more.

Define whether running work can move. Here only queued tasks can transfer; a popped task already belongs to its worker.
Every operation acquiring several queue locks must use the same node-ID order, independent of which queue is the source.
Move a suffix as an ordered batch while both queues are protected. Close needs the same admission boundary, then must release locks before joining.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What did the Rubrik reports require?
The 2024 CPD report asks for real code with specific-node enqueue, per-node FIFO and rebalanceLoad. The 2025 report names add, run and rebalance operations; locking during rebalance was raised by a commenter, not attributed to the interviewer.
Why not acquire the busiest queue and then the least busy queue?
Two concurrent calls can choose opposite directions and wait on one another. Sort lock acquisition by stable node ID; source and destination roles do not define lock order.
How would you shorten the all-queue critical section?
Sample sizes, lock the chosen pair in ID order, revalidate and transfer. Iterate to converge, but weaken the one-call globally balanced snapshot guarantee unless you add a versioned coordination protocol.
What if task costs differ greatly?
Track estimated remaining cost or measured execution time instead of queue length. Estimates can be wrong; migrate only queued tasks and use a threshold to avoid oscillation.
What changes across machines?
A mutex cannot make a cross-node transfer atomic. Persist task identity and ownership, use acknowledgments and fencing, and make execution idempotent. Exactly once in this in-memory exercise does not imply exactly-once effects after distributed failures.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

Key idea and invariants

Queue membership is ownership. A callback leaves its queue exactly once and is then owned by that node's worker until completion. A transfer removes and appends a suffix inside one locked operation, so nobody can observe half a move. Node-ID lock order prevents cycles even when the busiest and least busy roles reverse.

Why these primitives

Each queue has a mutex and condition variable: workers wait on “closed or nonempty,” while add and transfer wake the destination. All-queue locking gives a coherent load snapshot and atomic close admission. An independent close lock makes joining idempotent. A failure counter records callback exceptions without retaining a queue lock. Callbacks on different nodes continue in parallel during queue bookkeeping.

Pitfalls and broken interleaving

The broken implementation copies a tail batch into the destination but leaves it in the source. Source worker A later pops task X; destination worker B also pops X. Both queues were individually locked, yet the ownership invariant was lost. The quiet conservation test catches duplication before execution, and the stress ledger catches duplicate effects. Moving front tasks would also disrupt the intended suffix policy. Joining while holding queue locks would prevent the workers from draining.

How to say it in the interview

“I will state the migration ordering guarantee first. Each queued task has exactly one owner, and every multi-queue operation uses increasing node IDs. The workers execute callbacks after unlocking, so a slow task cannot freeze admission or another node.” The simple reference favors an atomic, easy-to-prove rebalance over maximum queue-operation throughput; discuss pairwise revalidation only after that invariant is clear.
