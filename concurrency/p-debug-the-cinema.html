Debug the cinema

Bug huntssenior50 minRubrik debugging round reportsRubrik

Rubrik interview reports describe a debugging round on code like this: someone else's threaded service, several bugs, about fifty minutes, and it must compile and run when you hand it back. One candidate with 8.5 years of experience was given a cinema booking service. This practice service has three planted bugs of three different kinds; it is not a reproduction of the reported interview code.

The round

Candidates describe the format the same way: you get existing multithreaded code, you explain what it does, you find the concurrency bugs, and you return a version that compiles and runs. One new grad found the main deadlock and still lost the round because the fix did not compile. So practise the method as much as the answers: read for structure, list the shared state and the locks, check every access, then fix with small, safe edits and run it again.

The incident

The multiplex's booking service keeps one lock per show, so independent operations on unrelated shows do not share a show lock. Three complaints reached the team in one week:

  • Two customers, one seat. At Friday's premiere two customers arrived for seat 41 of the same show, both holding confirmations. The audit log has two BOOK lines for that seat, microseconds apart. The show's free seat count was also one lower than the number of empty seats.
  • A frozen pair of shows. During Saturday's promotion many customers moved their bookings between the 6 pm and the 9 pm shows. The service stopped answering every request for those two shows; requests for other shows kept working. A restart cleared it.
  • A waitlist that does not move. On Sunday a customer waiting for one seat stayed on the waitlist all evening although a seat in that show was free for most of it. Support says it seems to happen on shows where families, waiting for several seats together, are also on the waitlist.

The C++ ThreadSanitizer job has been red on this file since it was written. Nobody has read the reports.

Your job: find every concurrency bug and fix each with the smallest correct change. Keep the public API exactly as it is, and keep one lock per show: a single cinema-wide lock would hide two of the bugs and would not survive the design review.

The contract

  • Show and seat indices are zero based and valid. The constructor dimensions are positive, count is between 1 and the show's capacity, timeouts are nonnegative, and customer names are nonempty (also non-null in Java). Invalid input and allocation failure handling are outside this exercise.
  • book succeeds only for a free seat. cancel succeeds only for the named customer, compared by string value. Cancelling an empty seat or cancelling twice returns false without changing any state.
  • exchange moves a booking to a different show, all or nothing. A wrong owner, occupied destination, or identical source and destination show returns false and leaves both shows unchanged. Reject a same-show move even when its destination seat is free.
  • waitForSeats atomically reserves exactly count seats, choosing the lowest numbered free seats and returning their indices in increasing order. It never reserves a partial group while waiting. A timeout returns an empty array or vector and leaves the seats and free count unchanged.
  • A zero timeout is an immediate attempt: succeed if enough seats are already free, otherwise return empty. Once the show lock is acquired, the condition wait uses one monotonic time budget; wakeups must not restart it. Lock acquisition and scheduling can delay return. Recheck availability under the lock before deciding whether to time out.
  • Both cancellation and exchange must wake eligible waiters on the show they free. In Java, interruption before entry or while waiting propagates InterruptedException without reserving seats; the show remains usable. If interruption races with a completed reservation, the completed operation need not be undone. C++ has no interruption API here.
  • holder and freeSeats are synchronized observations. Each call is atomic on its own; two separate calls are not a snapshot. Keep the seat array and free count consistent under one lock per show, including group reservations. Waiting releases that lock.
  • No FIFO admission or starvation guarantee is required. An eligible single customer may pass a group whose request cannot yet be satisfied. Keep the per-show locking design; this structural requirement also needs code review.

For example, if seats 0, 2 and 4 of a six-seat show are held, waitForSeats(show, 2, customer, 0) returns [1, 3] and leaves seat 5 free. A subsequent two-seat request with zero timeout returns empty and must not reserve seat 5.

What the tests check

  • Every method from a single thread. Rejected operations preserve every seat and count, repeated cancellation releases nothing, and Java ownership uses string value equality.
  • Fragmented availability, lowest seat selection, groups equal to capacity, immediate attempts with zero timeout, and unsuccessful groups leaving no partial reservation.
  • A waiter wakes after an exchange frees its source seat, before its own timeout. Other shows remain usable while it waits.
  • A 180 ms group wait receives repeated notifications while too few seats are free. It still times out against its original budget, with scheduling tolerance, without taking any seats.
  • Java interruption during a group wait and before entry, followed by a successful reservation using the same show.
  • Four two-seat groups race for seven seats: exactly three get complete, disjoint groups, one times out, and one seat remains free. Concurrent readers overlap bookings and cancellations.
  • Eight threads (six in C++) race to book the same 64 seats (48 in C++), 30 rounds (10 in C++): exactly one winner per seat, the right holder, and an exact free count.
  • Four threads exchange in opposite directions, 160,000 moves (24,000 in C++): no hang, no failed move, everyone ends in their own seat.
  • A two-seat group waits before a single customer. Cancelling one seat must serve the single customer without partially serving the group. Further cancellations serve the group, with exact returned seats, ownership and counts. C++ repeats this with three shows and nine groups.
  • A seeded mixed-operation stress run checks each customer's reservations and every show's final counts. All worker completion is bounded, watchdogs cover blocked main-thread calls, and C++ ThreadSanitizer must stay quiet.

The harness uses state checks for Java waiters and bounded scheduling windows in C++. C++ does not specify which waiter notify_one wakes, so the mixed-size waitlist test uses several groups and shows. Passing a finite run does not prove every interleaving safe; the lock and notification arguments still matter.

Taught in: Debugging rounds: the bug in someone else's threaded code

Open them one at a time. Each one gives away a little more.

Make a table: for each field of a show, which lock guards it, and which methods read or write it. Then check every access in every method against the table. Be suspicious of any comment that explains why a lock is not needed.
Find every method that holds two locks at once. In what order does it take them? Now run two calls of that method at the same time, in your head, with their arguments swapped.
Look at who waits on seatFreed and what each waiter needs. Do all waiters want the same thing? When one seat frees up, which waiter gets woken, and what happens if that waiter cannot use it?
Each fix is a few lines and keeps one lock per show: the check and the claim in one critical section; one global order for any two show locks; and wake every waiter whose condition might now be true.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why not replace the per-show locks with one cinema-wide lock?
It would fix the race and the deadlock at once, and it would serialize the whole multiplex: every booking for any show would wait for every other. Per-show locks partition the state by show. An operation touching two shows needs consistent ordering or another deadlock avoidance mechanism. In the interview, name both options and say why you keep the striping.
Ordering by show id, std::scoped_lock, or tryLock with back-off: which and why?
A global order (lower id first) is the simplest and works in both languages, but needs a total order on the locks. C++17 std::scoped_lock(a, b) uses a deadlock avoidance algorithm, so no order is needed. Java has no multi-lock helper; tryLock with a timeout, releasing everything and retrying, also works but can livelock unless the back-off is randomized. Prefer ordering; mention the others.
signalAll wakes every waiter on each cancel. Is that a thundering herd?
Every waiter of that show wakes, re-checks under the lock, and most go back to sleep. With a handful of waiters per show that is cheap and correct. At scale, use one condition per kind of request, or an explicit waitlist where a release hands seats directly to a request that fits, so exactly the right thread is woken. First-fit admission is not strict FIFO and can starve large requests.
Can a family waiting for two seats starve behind a stream of single customers? How would you make the waitlist fair?
Yes. Each freed seat is taken by whichever single customer re-checks first, so two seats may never be free at the same moment. To be fair, keep the waitlist as a FIFO queue of requests and serve only the head: freed seats are held for the head until it is satisfied, and nobody barges past it. Fairness costs throughput, because seats sit empty while the head waits; Rubrik's follow ups on the bathroom and playground problems probe exactly this trade-off.
What would ThreadSanitizer and a Java thread dump show for these bugs?
ThreadSanitizer can report the data race in book when the conflicting accesses execute. Linux builds with deadlock detection enabled may also report a potential lock order inversion. Apple clang on this Mac does not report lock order inversions; the harness detects an actual deadlock through bounded completion and its watchdog. In Java, jstack prints "Found one Java-level deadlock" with each thread's held and wanted lock inside exchange. A missed useful notification need not produce a sanitizer warning or a deadlock report: a timed waiter can look normal. Predicate reasoning and a test that checks progress before the timeout expose it.
The ticket code and the audit line are built outside the lock. Is that safe?
Yes. They use local values, immutable show ids and an atomic counter, and doing slow work such as logging outside the critical section keeps the lock short. The cost is that audit lines from different threads may appear in a different order from the bookings themselves. If the audit must be in booking order, take a sequence number under the lock and log it with the line.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

How to find them in the round

Read the class once for its structure. Then write down the shared state and its guard: each show's seats, free and seatFreed belong to that show's lock; ticketsIssued is atomic; the shows array is built in the constructor and never changes. Now walk each method with three questions: is every access to show state under that show's lock? Does the method hold two locks, and in what order? Does it wait or signal, and is the signal right for every waiter? Each question finds one bug here.

Bug 1: book checks the seat without the lock (a race on seat state)

book reads seats[seat] before taking the lock ("no need to lock just to say no"), then takes the lock only to write. The lock protects the write, not the decision. This is a check then act race: two customers can both see the seat free, and both are told yes. The second write overwrites the first, so one confirmed customer has no seat, and free drops by two for one seat. In C++ the unlocked read of a std::string that another thread is assigning is also a data race, which ThreadSanitizer reports.

Fix: take the lock first, then check and claim inside it. Build the ticket code after the lock is released.

Bug 2: exchange locks in argument order (a lock order deadlock)

exchange locks the "from" show, then the "to" show. Two exchanges moving bookings in opposite directions take the same two locks in opposite orders: a lock order inversion. Each can hold its first lock and wait for the other's. All four conditions for deadlock hold, and every later request for either show queues behind those two locks, while other shows carry on, exactly as in Saturday's incident.

Fix: lock the two shows in one global order, lower show id first, whatever the direction of the move. Keep the checks and updates the same: they use from and to, and only the locking order changes. In C++, std::scoped_lock both(from.m, to.m) is an equally good fix.

Bug 3: one signal for waiters who want different things (a lost wakeup)

All waiters of a show wait on one condition, seatFreed, but they wait for different things: free at least 1 for a single customer, at least 2 for a pair. cancel and exchange call signal() (notify_one() in C++), which wakes one waiter. If it wakes the pair while only one seat is free, the pair re-checks, goes back to sleep, and the signal is gone. The single customer, who could have used the seat, sleeps on. This is a missed useful wakeup: the notification reaches a waiter whose predicate is false. With timed waits, the single customer can eventually recheck at its deadline; that does not make the delayed notification correct.

For the supplied Java ReentrantLock condition, signal() selects waiters in FIFO order, so a pair established as waiting first receives the notification. The harness observes that blocking state instead of assuming a sleep established it. C++ notify_one selects an unspecified waiter; its test starts several pairs before each single customer, without claiming a portable selection order.

Fix: signalAll() (notify_all()). Every waiter re-checks its own condition under the lock; the single customer takes the seat and the pair waits on. This also covers an exchange that frees a seat.

The fix, side by side

Wait budgets, invariants and cost

The invariant is that free equals the number of unowned seats and stays between zero and capacity. A successful group reservation changes every selected seat and subtracts exactly the group size under the same lock. Timeout or interruption changes nothing. Java carries the remaining duration returned by awaitNanos; C++ uses the predicate form of wait_for, which preserves a single timeout across wakeups.

book, cancel, holder, freeSeats and the state changes in exchange take O(1) seat operations, excluding contention, string copying and audit formatting. A group reservation scans up to the show's capacity, O(capacity), and returns O(count) indices. Storage is O(shows times seats). Broadcasting after a release may wake every waiter on that show; it gives no FIFO or starvation guarantee.

How to say it in the interview

Each show's seats, free count and condition belong to that show's lock, so I checked every access against that. First, book reads the seat outside the lock and claims it inside, a check-then-act race that sells a seat twice; I move the check inside the lock. Second, exchange locks from then to, so two opposite exchanges deadlock; I lock the two shows in show id order. Third, waiters on seatFreed need different numbers of seats, so signal can wake a pair who cannot use a single seat and the single customer can wait until its timeout before checking again; I use signalAll, and each waiter re-checks in its loop. I kept per-show locking so unrelated shows can still make progress independently.
