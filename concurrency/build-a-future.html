Build it yourself: a future you can complete and chain

Build a completable future with one-shot results, timed waiting, safe callback registration, exception propagation and chaining.

Asked atGoogleRubrik
Before this:Futures and promisesComposing async work: CompletableFuture and continuationsCondition variables and monitors

A 2026 Google L5 coding round asked a candidate to design and implement a custom variation of CompletableFuture, "under the hood"; Rubrik has asked for a JavaScript-style Promise in Java. Underneath both is a small monitor with one hard rule: every callback runs exactly once, whether it was added before or after the future completed.

In plain words

Think of a parcel locker with a notification list. The courier puts the parcel in once; if two couriers arrive with parcels for the same locker, only the first one fits. People who come early and find it empty leave their phone number, and the courier calls everyone on the list after putting the parcel in. People who arrive after the parcel is there just take it.

The whole difficulty is the moment of arrival. If you check "empty?" and then walk to the list to write your number, the courier may arrive in between, read the list without your number, and leave: you are never called. Checking and writing must be one step.

The specification

State it before you code; the interviewer will grade against it:

  • complete(v) and completeExceptionally(e) fill the future once. They return true for the call that won and false for every later call.
  • get() blocks until the future is done, then returns the value or throws the stored error (wrapped in ExecutionException in Java). The timed overload, Java get(timeout, unit) or C++ get(duration), stops waiting on timeout. Java throws TimeoutException; our custom C++ version returns an empty std::optional. These are waiting budgets, not hard scheduling deadlines.
  • isDone() reports whether it has been filled.
  • thenApply(fn) returns a new future that completes with fn(value). If this future fails, the new one fails with the same error and fn never runs; if fn throws, the new one fails with that exception.
  • Each registered continuation is dispatched once when the source completes. A successful source invokes fn once; a failed source propagates its error without invoking fn. In this implementation, callbacks registered before completion run on the completer; later callbacks run on the registrar. Callbacks must terminate for later callbacks in the same drain to progress.

The state and its invariant

This future is a monitor: done, value, error, and a callback list protected by one lock. The invariant:

  • done goes from false to true exactly once, under the lock.
  • value and error are written before done becomes true and never again.
  • While not done, a callback is either in the list or has not been registered yet. At completion, the completer takes the whole list in the same critical section that sets done, so after that moment nobody can add to it: every callback is in exactly one place, the list or the registering thread's hands, never both and never neither.

Two wrong designs break that last line, and they are exactly what interviewers look for:

The correct thenApply takes the lock, and if the future is not done, adds the callback and returns; otherwise it releases the lock and runs the callback itself. The correct complete takes the lock, refuses if already done, writes the result, sets done, swaps out the list, signals waiters, releases the lock, and then runs the list. Either thenApply's critical section comes first (the callback lands in the list and the completer runs it) or completion's does (the registrar sees done and runs it). There is no third ordering.

The whole future

Both versions follow the same design. The main program exercises a chain, competing completers, concurrent registration, timeout and error propagation; it is a demonstration, not a proof over all schedules. In C++, copies share one state, like std::shared_future. This teaching version supports copyable object results, excluding references and void, and copyable callbacks; supporting move-only results or void needs a different result API or a specialization.

The C++ state owns each callback, so the callback must not strongly own that same state: otherwise abandoning an incomplete future leaks a reference cycle. We pass the state into callbacks when running them, and hold it alive locally during the drain. Its value is an immutable shared payload constructed before locking, so user-defined construction and copying do not run under the internal mutex. Callers must still synchronize any mutable objects reachable through their results.

Why each line is there

  • if (done) return false: the first completion wins. The value a reader sees can never change, which is the whole contract of a future.
  • notifyAll / notify_all, not one: every thread blocked in get() is waiting for the same event, and all of them can proceed.
  • while (!done) wait(): waits can wake spuriously, so get re-checks in a loop (C++'s predicate overload is the same loop). The timed version recomputes the remaining time from one deadline on each pass, so spurious wakeups never restart the full timeout. Scheduling and lock reacquisition can still delay the return; the C++ duration starts at wait_for, after acquiring the mutex. Java uses elapsed monotonic time against a nonnegative budget, assuming intervals shorter than the signed nanosecond range.
  • Callbacks run outside the lock. A callback is code you did not write. Run under your lock, a slow callback blocks every get, isDone and thenApply on this future, and re-entering a method that locks the same C++ std::mutex is undefined behaviour, commonly a deadlock. This is the "open call" rule: never call unknown code while holding a lock (open call).
  • Reading value and error in the callback without the lock is safe. A callback runs either on the completing thread, after it wrote them (program order), or on a registering thread that saw done under the lock, after the completer's unlock (the unlock happens-before that lock). And neither field changes after done. That is safe publication through a lock, the same guarantee that makes get() safe.
  • Errors skip fn and flow downstream: the derived future fails with the same error, so a chain of thenApply behaves like a chain of calls where an exception propagates to the end.
  • fn throwing fails the derived future, rather than escaping into the completing thread, which in Java might be a pool worker and in C++ might be a thread whose function would then call std::terminate.

Which thread runs a callback?

In our implementation, the winning completer drains callbacks registered before completion in list order. A later registrar runs its callback inline, and can overlap that drain or overtake earlier callbacks. Java's CompletableFuture does not promise FIFO order or execution only by the winning completer: other threads calling completion methods may help. Its non-async stages should therefore be short, with no assumption about thread identity.

A heavy inline callback delays the completer. Completing a future while holding an application lock also runs callbacks under that outer lock, even though this future releases its own lock first. Complete after releasing application locks, and never block in one callback waiting for a sibling that the same drain has yet to run.

The async extension below uses the exception-safe whenComplete primitive from the checkpoint. It handles source failure, submission rejection and function failure. Add java.util.concurrent.Executor to the Java imports. C++20 has no standard executor interface: this example expects an execute(callable) method that either accepts work exactly once or throws on rejection. The referenced executor must outlive source completion and submitted work, and accepted work must eventually run or be explicitly cancelled rather than silently discarded.

An executor may execute inline, so an async API does not by itself promise a different thread. A bounded executor with observable rejection is easier to reason about than one that silently drops work. get(timeout) only ends that caller's wait; it does not stop the task or complete the future.

Under the hood: the lock-free version

OpenJDK 21 implements CompletableFuture completion bookkeeping with CAS rather than a monitor. This does not make blocking get() or arbitrary user callbacks lock-free. It keeps the result in one volatile field and dependents in a Treiber stack (the structure from the lock-free stack lesson):

  • Completing is a compare-and-set of the result field from null to the value (or to a wrapper for an error, or for a null value). Only one CAS can succeed, which is "first completion wins".
  • Registering pushes a completion node with a CAS and then checks the result field again. If the future completed meanwhile, the registrar tries to run the node itself.
  • Action-bearing nodes claim execution with CAS. For example, a thenApply node claims its function so a racing registrar and completer cannot both invoke it. Other node types, such as waiters and relays, use their own checks; not every node follows one identical claiming protocol.
  • Dependent traversal is iterative. Ordinary chains avoid one stack frame per stage, unlike our recursive sample. This cannot prevent stack overflow if user callbacks themselves recursively invoke completion.
  • get() parks the waiting thread with a node of its own on the same stack, which completion unparks, and it cooperates with fork/join pools so a blocked worker can be compensated.

In an interview, build the lock version first, prove exactly-once with the two orderings, and then describe this design. Treat a 45-minute implementation as a practice target for the lock-based design; the CAS version adds a separate proof obligation around registration and reclamation.

Worked example: the follow ups, one by one

  1. "Add thenCompose." Factor registration into one primitive, whenComplete((value, error) -> ...), then build everything on it. thenCompose(fn): when this completes with a value, call fn(value) to get an inner future, and complete the result from the inner future's whenComplete. The checkpoint has it.
  2. "Add allOf." Set a remaining count to the full input size before registering any callback, because registration can run inline. Under one aggregate lock, record an error and subtract one per input; at zero, snapshot the outcome and complete outside that lock. Java's allOf waits for every input, even if one fails; fail-fast aggregation is a different contract. Zero inputs completes successfully immediately. A C++ version here can return a dummy value, since this sample lacks SimpleFuture<void>.
  3. "Add cancellation." It can compete for the same one-shot state using a cancellation exception, but define retrieval semantics too: Java's CompletableFuture.get() throws CancellationException directly for a cancelled source, whereas our unmodified get() wraps every error. Neither approach forcibly stops running work. Use a cooperative cancellation token or interrupt an owned worker, and ensure its I/O responds to cancellation.
  4. "Add orTimeout." Schedule exceptional completion on the scheduler; result and timer race through the same completion method. Unlike a timed get, this changes the shared future. Cancel an unused timer after early completion to release retained state, and avoid running expensive inline callbacks on the timer thread.
  5. "Make it lock-free." The CAS design above.

Common mistakes

  • Checking isDone() and adding the callback in separate critical sections: a lost callback (bug 1).
  • Adding to the list and also running when done: a double run (bug 2).
  • Running callbacks while holding the lock: slow callers everywhere, and deadlock if a callback re-enters with a non-recursive mutex.
  • if instead of while around wait(), or a timed wait that restarts the full timeout after each spurious wakeup.
  • Letting a later complete overwrite the value. Readers may already have seen the first one.
  • Letting fn's exception escape into the completing thread instead of failing the derived future.
  • notify instead of notifyAll: with several threads in get(), only one wakes and the rest wait forever.

In the interview

The question is reported at Google (L5, 2026: a custom variation of CompletableFuture under the hood) and Rubrik (a JavaScript-style Promise in Java: working code first, then optimize), and the same structure appears inside larger problems: a per-event future completed after fsync in Databricks' log writer, single-flight caches where many callers wait on one load. Expect to write it in about 30 minutes and then take two or three follow ups.

The state is done, value, error and a callback list, all under one lock. Complete takes the lock, returns false if already done, writes the result, sets done, swaps out the callback list and notifies all waiters, then runs the callbacks after releasing the lock. ThenApply takes the lock and either appends the callback, if not done, or releases it and runs the callback on the caller's thread. Because both decisions happen under the same lock, each callback is run exactly once: by the completer if it was registered first, by the registrar otherwise. Get waits in a loop on the condition, and with a timeout it tracks one deadline.

Follow ups to expect: "Why not run callbacks under the lock?", "Which thread runs a callback?", "How would you make it lock-free?", "How do you add thenCompose and allOf?", "What happens with a chain of 100,000 stages?" (the simple version recurses once per stage and can overflow the stack; complete iteratively, as CompletableFuture does).

Senior depth

Linearization and cost. The winning completion linearizes when done changes under the lock; a losing call linearizes when it observes done. Registration linearizes at its append or completed-state observation. Completion detaches the list in O(1) under the lock, then spends O(k) plus user callback time draining k callbacks. Storage is O(k) plus the result; waiting, allocation and lock contention add costs outside this bookkeeping bound.

Readiness is not callback termination. isDone() and get() can observe a ready source while its callbacks are still running. A slow or non-terminating callback can stall siblings in this synchronous drain. Stack overflow in a very deep chain is not safely repaired by catching ordinary exceptions; use a worklist or trampoline. Java propagates interruption from wait() without changing the future; C++20's ordinary condition_variable wait has no automatic stop-token support.

Abandonment and authority. This class does not detect a producer that disappears without completing: a retained dependent can remain pending forever. A production promise/future split can make only the producer writable and complete with a broken-promise error on abandonment. In C++, passing state into callbacks avoids an internal ownership cycle, but a user callback that captures its own source strongly can still create one. Define ownership and cancellation instead of assuming reference counting solves every lifecycle.

Key takeaways

  • Our completable future uses a monitor: done, value, error and a callback list under one lock; the first completion wins.
  • Exactly once: decide "add to the list" or "run now" in the same critical section that completion uses to take the list.
  • Run callbacks and user functions outside the lock; a failing function fails the derived future.
  • get waits in a loop with notify-all; the timed version tracks one deadline.
  • OpenJDK 21 uses CAS-based result publication, a Treiber stack, action claiming and iterative traversal; waiting and callbacks can still block.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A candidate writes thenApply like this: if isDone() (which locks and unlocks) is true, run the callback now; otherwise lock, add the callback to the list, unlock. What can go wrong?
Why. Each step is safe, but the decision spans two critical sections, a check-then-act race. Completion can slip into the gap and drain the list before the callback is added. A retained empty list strands it; the Java sample's cleared list would instead cause a null dereference. Neither the double-run path nor deadlock follows just from this sequence. The fix is to check done and add in one critical section.
Two threads call complete(1) and complete(2) on the same new future at the same time. Then get() is called. What is true?
Why. Whichever thread takes the lock first sets the value and done; the other sees done and returns false without writing. Which one wins depends on timing, but there is exactly one winner, and the value never changes afterwards.
A SimpleFuture from this lesson has completed successfully. Thread T calls thenApply(fn) on it. Who runs fn, and when?
Why. The registrar sees done under the lock and invokes the callback after unlocking, before returning. No executor is involved. The completer may still be draining earlier callbacks, but it never receives this new one. A failed source would skip fn, which is why success is specified.
A callback reads the future's value and error fields without taking the lock. Why is that safe here?
Why. Program order covers the completer, and the lock's unlock-then-lock edge covers every registrar that observed done. Since the fields are written once, before done, there is no later write to race with. Callbacks registered after completion run on the registering thread, so the last option is wrong.
100,000 futures are chained with thenApply before the first one is completed. With the simple design in this lesson, what can happen when the first one completes?
Why. Each complete runs its callbacks, and each callback calls complete on the next future: 100,000 nested calls. Production futures avoid this by completing dependents iteratively; CompletableFuture drains its dependents in a loop for exactly this reason.
Java onlyA refactor moves lock.wait() outside synchronized (lock). Execution reaches that wait while the thread does not own the monitor. What happens?
Why. Object.wait, notify and notifyAll require the calling thread to hold that object's monitor; otherwise they throw IllegalMonitorStateException. Holding the monitor is also what makes the check of done and the wait atomic, so a completion cannot slip in between and be missed.
C++ onlyA C++ version runs the callbacks inside finish() while still holding std::lock_guard<std::mutex> lock(s_->m). One callback calls isDone() on the same future. What does C++ specify?
Why. std::mutex is not recursive, so locking it twice from one thread is undefined behavior and typically hangs. Java's synchronized is reentrant and would hide this particular bug, but running alien code under a lock is wrong in both languages. Run callbacks after releasing the lock.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Add whenComplete(callback(value, error)) as the single registration primitive, then build thenCompose(fn) on it, where fn returns another future. Errors from this future, from fn, and from the inner future must all reach the result.
Model answer

Why this shape: every combinator (thenApply, exceptionally, thenCompose, allOf) is "register a callback that completes another future", so the exactly-once logic lives in one place, whenComplete. thenCompose is flatMap: the outer callback produces an inner future, and the result is completed by the inner future's callback, so no thread ever blocks waiting for the inner one. whenComplete returns a dependent future: if its observer throws, that dependent fails without preventing other callbacks from running. An existing source failure takes precedence; this teaching version does not attach suppressed exceptions. thenCompose forwards source, function and inner failures, including a null Java inner future and a throwing C++ result copy. thenApply can now delegate registration to this primitive too.

Explain
Prove to an interviewer that, in your design, a callback registered concurrently with completion runs exactly once.
Model answer

Both operations that touch the callback list and the done flag do so in a critical section on the same lock, so they are ordered: one critical section entirely precedes the other.

  • If thenApply's critical section is first, it sees done == false and appends the callback. Completion's critical section, later, sees the callback in the list, takes the whole list and sets done, and the completer runs the callback after unlocking. The registrar returned without running it. Exactly once.
  • If completion's critical section is first, it sets done and takes the list, which does not contain the callback. thenApply's later critical section sees done == true, so it does not append; it unlocks and runs the callback itself. The completer never saw it. Exactly once.

There is no interleaving in between, because the decision (append or run) and the list hand-off are each made inside a critical section. And completion can only happen once, because it returns false when done is already set, so the list is taken once. The values the callback reads are visible because it runs either on the completer after its writes or after a lock that follows the completer's unlock.

Design
The interviewer asks: "Now make it lock-free." Describe the design and the race you must handle.
Model answer

Keep two atomic fields: the result (null until done; a value, or a wrapper for an error or for a null value) and the head of a stack of pending callback nodes. Completion is a single compare-and-set of the result from null to the outcome: only one thread can win, which gives "first completion wins", and the winner drains pending nodes. To avoid recursive chains, callbacks enqueue newly ready dependents onto a worklist that the current drain processes iteratively; merely looping over the source's list is insufficient. Registration allocates a node and pushes it with a compare-and-set, like a Treiber stack.

The race: a registrar can push its node just after the completer has finished draining the stack, and the completer will never look again. So after pushing, the registrar re-reads the result; if it is now set, it tries to run the node itself. That creates the opposite race, where both the completer (who did see the node) and the registrar try to run it, so each node has its own small atomic state and must be claimed with a compare-and-set before running; the loser skips it. Waiting in get() is a node too: a thread that parks itself, unparked by completion. That is essentially CompletableFuture's design. I would mention that memory reclamation is easy in Java (garbage collection) but in C++ popped nodes need careful ownership, using a reclamation protocol such as hazard pointers. Shared ownership can simplify lifetime, but atomic shared-pointer operations are not guaranteed lock-free and this Mac's libc++ does not provide std::atomic<std::shared_ptr<T>>. For a C++ sketch I would start with sequentially consistent operations on both atomics, then prove the registration/completion handshake before weakening them. Publication must also synchronize payload access; independent relaxed atomics are insufficient.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Design a future that I can complete and attach callbacks to. Prove that a callback cannot be lost or run twice when registration races completion."
What a strong answer covers
  • Use one lock for done, outcome and pending callbacks, with one winning completion
  • Completion publishes the outcome and detaches callbacks in the same critical section
  • Registration either appends while pending or takes responsibility for immediate dispatch
  • Prove the two possible lock orderings and the single owner in each
  • Wake all getters and run callbacks outside the lock with failures propagated downstream
How a senior would say it
I would protect the completion flag, outcome and callback list with one lock. The first completion wins; later attempts return false without changing the outcome. Completion writes the value or error, marks the future done, and detaches the pending list in one critical section. It wakes all waiting getters and runs the detached callbacks after releasing the lock. Registration uses that same lock for one decision: append if pending, otherwise run the callback after unlocking. There are only two relevant orderings. If registration acquires the lock first, its callback enters the list and only the completer owns dispatch. If completion goes first, registration observes done and never appends, so only the registrar owns dispatch. The broken version checks done and appends in separate critical sections, allowing completion to drain between them. I would also make getters wait in a predicate loop and propagate callback exceptions to dependent futures. The guarantee assumes dispatched callbacks terminate; a blocking first callback can still delay later ones. Thread safety does not by itself guarantee progress through arbitrary user code.

Likely follow up: Can a getter return while a callback is still running, and does that violate your contract?

Out loudabout 90 s
"Your async chaining method sometimes returns a future that never finishes. Walk me through the failure paths you would investigate."
What a strong answer covers
  • Trace source outcome, callback registration, executor acceptance and task execution
  • Forward source failure even when the transformation is skipped
  • Convert executor rejection and transformation exceptions into dependent failures
  • Check dropped work, executor lifetime and blocking dependencies that exhaust workers
  • Distinguish a timed get from completion timeout and cooperative cancellation
How a senior would say it
I would trace which event is supposed to complete the returned future, then check every path that can bypass it. First, if the source fails, the dependent must fail too. Implementing async chaining by attaching only a success transformation can skip that propagation and leave the result pending forever. Second, executor submission can reject work. That exception must complete the dependent exceptionally, just like an exception from the transformation itself. Third, an executor that silently discards accepted tasks breaks progress even when my callback code is correct. I need observable rejection and a shutdown policy for queued work. In C++, I would also check that the executor and captured inputs outlive execution; a borrowed pointer from a completion callback must not escape into delayed work. Then I would inspect blocking dependencies: a worker waiting for another task queued to the same exhausted pool can deadlock. A timed getter only stops that caller waiting; it neither completes the shared future nor stops the producer. A completion timeout changes the outcome, while cancellation still needs cooperation from the underlying work. I would test failed sources, rejected submissions and throwing functions, both before and after source completion, and make each test use a bounded wait.

Likely follow up: What should allOf do after one input fails while another is still running?
