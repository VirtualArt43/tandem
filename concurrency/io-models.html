Blocking, non-blocking and multiplexed I/O

Distinguish blocking, non-blocking, readiness and completion I/O, then debug partial transfers, missed progress and busy event loops.

Asked atDatabricks
Before this:Server threading models

Every server threading model stands on an I/O model: the way a thread finds out that bytes have arrived. Know the four answers (block, poll, multiplex, complete) and you can explain why Nginx, Netty and Node scale the way they do, and debug the event loop bugs that bite people who only know the frameworks.

In plain words

You are expecting several parcels. Blocking: you sit by the door until one arrives and can do nothing else. Non-blocking: you open the door every few minutes to check, which leaves you free between checks but wastes effort on empty doorsteps. Multiplexing: you give the building's concierge a list of the parcels you expect, and they ring you when any of them arrives; then you go down and collect it. Completion: the courier carries the parcel into your flat and leaves a note saying "delivered"; you never touch the door.

Assigning one dedicated person to each of 10,000 doors would be expensive. The concierge lets a few people cover many doors; the courier changes who does the collection work.

Blocking I/O

A positive-length blocking read on a stream socket waits when no data is available, until data, EOF, an error or a configured timeout allows it to return. It need not fill your buffer. A blocking write can wait for send-buffer capacity; success means local acceptance of bytes, not that the peer application received or persisted them.

The calling platform thread cannot do other application work while blocked. Dedicating one to every connection is one design, not an API requirement: a server may assign workers only to active requests, and a virtual-thread runtime may park the logical thread while freeing its carrier.

Non-blocking I/O

Mark the descriptor non-blocking (fcntl with O_NONBLOCK in C, channel.configureBlocking(false) in Java) and socket reads and writes return available progress instead of waiting for data or send-buffer space. If no progress is possible they report "nothing yet" (EAGAIN or EWOULDBLOCK in C, a count of 0 from a Java NIO channel). Non-blocking I/O is an operation mode, not inherently a polling strategy. Repeatedly asking 10,000 sockets "anything yet?" can burn a core learning that the answer is usually no. Usually you combine it with readiness notifications. Non-blocking I/O is not the same as a lock-free algorithm or a hard real-time execution bound.

Two practical facts matter from here on. Reads and writes may be partial: a write of 64 KB may accept 9 KB and you must keep the rest and retry later; a read may return half a message, so you buffer until a full one has arrived. And non-blocking descriptors are the raw material for the next model, which is where they become useful.

Readiness multiplexing: one thread, many sockets

I/O multiplexing asks the kernel one question about many descriptors: "which of these are ready?" The thread can sleep until readiness, a timeout or a wakeup, then attempt non-blocking I/O. Readiness is a hint, not a reservation: another reader may consume the data first, and EOF or errors also produce notifications. This wait drives a readiness-based event loop. The four APIs differ in how they scale:

APIWhereHow the interest list worksCost of each wait
selectPOSIX; Windows has a socket-only variantBit masks of descriptors, rebuilt and passed in on every call; POSIX descriptor numbers must fit the fd_set representation (FD_SETSIZE is commonly 1024)Scanning depends on the highest descriptor range supplied, not just the number of active sockets

The difference shows up at scale. With 10,000 mostly idle connections, poll copies and scans 10,000 entries on every wakeup, even if one socket had data (and select cannot even hold that many with the default FD_SETSIZE). epoll and kqueue keep the interest list inside the kernel and hand back only the ready ones, so delivery work mainly follows returned events. Registration, readiness maintenance, batching and handler work still cost time; this is not a blanket O(1) guarantee. That change is why a single thread can now serve tens of thousands of connections.

See it: one thread serving three connections

This deterministic demo uses three pipes, avoiding network setup. Each contains a tiny ASCII byte stream, then its writer closes. One readiness loop reads at most five bytes per stream per turn and checks every byte at EOF, so partial reads and hangup with unread data are exercised. Pipes support readable events like sockets, but do not have TCP connection establishment or half-close semantics.

The demo buffers a finite stream until EOF; a real persistent protocol parses complete messages as bytes arrive and bounds buffered input. C++ uses POSIX APIs available on macOS and Linux, not an ISO C++ socket library. A server also needs: a per-connection buffer for partial messages, a write queue for partial writes, and interest in "writable" only while that write queue is non-empty (see the worked example below).

Java

Java's NIO in a nutshell. A Selector multiplexes SelectableChannels (sockets, server sockets, pipes) that are in non-blocking mode. register returns a SelectionKey holding the interest set (OP_ACCEPT, OP_CONNECT, OP_READ, OP_WRITE) and an optional attachment, usually your per-connection state. select() waits for readiness, wakeup or interruption and may return zero; selectNow() does not; another thread can break a select() with wakeup(). You must remove each key from selectedKeys() after handling it, or it is handled again; since Java 11, select(Consumer<SelectionKey>) dispatches ready keys to an action instead. Do not rely on that overload leaving the selected set empty or invoking an action only once per key. Cancelled keys are removed during selection processing; check validity when handling them. The OpenJDK 21 default provider uses epoll on Linux and kqueue on macOS, and behaves level-triggered: a channel with unread data is reported again on the next select.

Two higher layers sit on top. NIO.2's AsynchronousSocketChannel offers a completion style API (a CompletionHandler or a Future); on Linux the JDK implements it with epoll plus an internal thread pool. Java 21 virtual threads normally park during supported blocking socket I/O, with readiness managed internally; pinning can prevent unmounting.

Level-triggered versus edge-triggered

A readiness API can report a descriptor in two ways. Level-triggered (the default for epoll, and how select, poll and Java's Selector behave): "this socket has unread data", reported on every wait for as long as that stays true. Edge-triggered (EPOLLET): reports readiness changes rather than repeatedly reminding you about an unchanged ready condition. Events may be coalesced; there is no one-event-per-message or per-packet promise. For kqueue socket filters, EV_CLEAR resets reported state after delivery and requires similar drain discipline, but kqueue filter semantics are not identical to epoll.

Edge-triggered mode can reduce repeated notifications, but requires explicit progress tracking. Use non-blocking descriptors and drain to EAGAIN before waiting for another edge. To avoid starving quieter connections, cap work per turn and put an incompletely drained connection on your own ready queue; do not wait for another edge to resume it. EPOLLONESHOT disables a registration after delivery until EPOLL_CTL_MOD rearms it. It helps assign a handler owner, but does not stop other code reading the socket or an early rearm creating overlap.

Completion I/O: submit operations and collect results

Readiness says "try the operation now"; non-blocking mode protects the loop if that hint is stale. Completion I/O goes further: you submit the operation itself ("read up to 4 KB from this socket into this buffer") and later collect its byte count, EOF or error. A successful read places bytes in the supplied buffer, but can still be partial. That is the proactor pattern.

  • Windows IOCP (I/O completion ports): overlapped operations complete onto a port, and a pool of threads takes completions from it; the port limits how many of those threads run at once, usually to the core count.
  • Linux io_uring (since kernel 5.1, 2019): two ring buffers shared between your process and the kernel, a submission queue and a completion queue. You can queue many operations and submit them with one system call, or with none if a kernel thread polls the submission ring. It covers sockets and files and much more, with support depending on kernel version and operation. Submission-ring polling trades fewer system calls for a polling kernel thread; completion does not imply zero copies or zero kernel work.
  • POSIX AIO exists but is limited and rarely used for sockets.

Files are different

Readiness APIs say little about disk files. A regular file is always "ready" to select and poll, and epoll refuses to watch one at all (EPERM), yet a read that misses the page cache can block the thread on storage. So event-loop runtimes push file work onto threads: Node's libuv runs file system calls on its thread pool, and Nginx added thread pools for blocking file reads. True asynchronous disk I/O is one of the main reasons io_uring exists. Remember this when an interviewer says "it is all event-driven, so nothing blocks": blocking file calls and resolver APIs such as getaddrinfo need offloading or an asynchronous alternative. Node's dns.lookup uses workers, while dns.resolve uses asynchronous network queries; "DNS always needs a worker" is too broad.

The connection-count question

Many mostly idle clients favour a design whose cost follows activity. That does not guarantee a connection count: descriptor limits, socket and TLS buffers, application memory, CPU per message and network bandwidth all matter. Benchmark the intended payloads and idle-to-active ratio rather than treating "one loop handles 100,000 clients" as a universal fact.

C++

Boost.Asio in a paragraph. Boost.Asio is a widely used external networking library; ISO C++20 itself has no standard socket API. An io_context is the event loop; you start asynchronous operations such as async_accept, async_read_some and async_write and pass a completion token: a callback, use_future, or, in C++20, use_awaitable so the operation can be co_awaited in a coroutine. Handlers run on whichever threads call io_context::run(); with several threads, a strand serializes handlers submitted through that strand. Confine all access to the connection state to it, including operation initiation and close; it does not make arbitrary accesses safe or guarantee one fixed OS thread. The API is proactor style on every platform: Asio uses IOCP on Windows and builds completions on top of epoll on Linux (and can use io_uring when enabled at build time).

This optional example requires Boost with C++20 coroutine support and a listening socket, so it has no Run button. Its asynchronous waits suspend the coroutine while I/O is pending, allowing one thread to serve many connections. async_read_some may return part of a message; async_write is a composed operation that writes the supplied bytes or reports an error. The local array lives in the coroutine frame across suspension. C++17 code uses callbacks and explicitly owned per-connection buffers instead.

The state a real loop must keep

Input and output are byte streams. TCP does not preserve message boundaries. Keep a parser and a bounded input buffer per connection, using a length prefix or delimiter with a maximum message size. For a positive-length stream read, C++/POSIX returns 0 at EOF and -1 with EAGAIN or EWOULDBLOCK when it would wait; Java NIO returns -1 at EOF and 0 when no bytes are read. Retry POSIX EINTR according to your cancellation policy; other errors need handling.

Writes need a cursor and a budget. Preserve unsent bytes after a partial write. Try writing when output is newly queued; if it would block, enable write interest. Disable that interest when the queue empties. Bound queued bytes per connection and globally; pause upstream reads at a high-water mark and resume below a low-water mark. In edge-triggered mode, explicitly retry when resuming instead of assuming a new edge will arrive.

Connect, accept and close are states. A non-blocking POSIX connect can report EINPROGRESS; writable readiness then requires checking SO_ERROR with getsockopt, not assuming success. Java uses OP_CONNECT and finishConnect(). Drain edge-triggered accept queues with non-blocking accept until would-block, and configure accepted sockets appropriately. A TCP peer can close its sending direction while still reading your response, so EOF need not mean dropping queued output. POSIX socket writes after peer shutdown may raise SIGPIPE; real servers need a platform-appropriate policy such as SO_NOSIGPIPE on macOS.

Completion buffers must outlive the operation. Do not free, resize or reuse a submitted buffer before the API allows it after completion. A timeout or cancellation request may race with completion; wait for the operation's final disposition before reclaiming its storage. Marshal worker results to the loop with a synchronized queue and a wakeup (Selector.wakeup() in Java); ignore late results for closed requests. Generation identifiers prevent a reused descriptor number from being mistaken for an old connection.

Worked example: three event loop bugs and their symptoms

Symptom: 100 percent CPU with almost no traffic. The loop registered every socket for "writable" permanently. A healthy socket's send buffer almost always has room, so a level-triggered wait returns immediately, every time, forever: a busy loop. Fix: register write interest only while you have unsent bytes queued for that socket, and drop it once the queue is empty.

Symptom: some connections stall with data sitting in the kernel buffer. The loop uses edge-triggered epoll but reads only once per notification. Leftover bytes alone do not guarantee another notification. Fix: drain until EAGAIN, or switch to level-triggered.

Symptom (Java): a handler runs again with stale readiness. The loop leaves handled live keys in selectedKeys(), so they may be visited again even without a fresh event. Fix: iterator.remove() after taking each key, or use the action-based selection API. Cancellation separately makes a key invalid immediately; selection processing removes cancelled keys. Check validity and coordinate close on the owner thread.

All three come from forgetting what the readiness API actually promises. Saying that out loud, "level-triggered means the event repeats until I consume it", is what makes the answer senior.

Common mistakes

  • Busy polling non-blocking sockets in a loop without a multiplexing wait: a core burns to learn that nothing happened.
  • Assuming a read returns a whole message or a write sends everything. Both can be partial; buffer and retry.
  • Edge-triggered without draining, or edge-triggered with blocking descriptors (the drain loop then blocks the loop).
  • Permanent write interest in a level-triggered loop: a 100 percent CPU spin.
  • "Event-driven, so nothing blocks." A blocking file or resolver call still blocks the loop; use an asynchronous API or offload it. CPU-heavy crypto also needs an appropriate execution budget.
  • Doing slow work in the handler: the multiplexing is perfect and the loop is still stuck.

In the interview

Databricks lists I/O operations next to multithreading in its official system programming description. Useful practice prompts, not claimed verbatim company questions, are: "How can one Nginx worker hold 10,000 connections?", "What is the difference between select and epoll?", "What does edge-triggered mean, and what goes wrong with it?", "Why does Node still have a thread pool?".

An event loop uses non-blocking sockets plus a readiness API. The thread asks the kernel which of its connections are ready, sleeps until at least one is, then does non-blocking reads and writes only on those. With select or poll, every wait rescans the whole set, so the cost grows with the number of connections; epoll and kqueue keep the interest list in the kernel and return only the ready ones, so the cost grows with activity instead. That is why one thread can hold tens of thousands of mostly idle connections. Regular files are different: select and poll report them ready even when disk access can block, while Linux epoll rejects them. Offload blocking file work or use an appropriate completion API.

Follow ups: "Level versus edge triggered?" (repeats while true, versus readiness changes that can be coalesced; drain until EAGAIN). "What is a proactor?" (submit the operation, get its completion; IOCP, io_uring). "How does a Java virtual thread fit in?" (blocking API, with the JDK parking the virtual thread on an internal poller).

Senior depth

Accept herds. When several processes or threads wait on the same listening socket, one new connection can wake all of them and only one wins: a thundering herd. Linux offers EPOLLEXCLUSIVE (wake one or a few waiters instead of all of them) and SO_REUSEPORT (a separate listening socket per worker, with the kernel spreading connections), which is how Nginx's reuseport option avoids the herd.

Copies cost too. At high bandwidth the bottleneck moves from waiting to copying. sendfile sends a file to a socket without passing the bytes through user space, and io_uring can use pre-registered buffers to reduce repeated memory registration overhead for supported operations. Neither fixed buffers nor completion I/O automatically makes a transfer zero-copy.

Key takeaways

  • Blocking I/O waits in the caller; non-blocking I/O returns would-block instead. Busy polling is a strategy, not a requirement.
  • Readiness multiplexing lets one thread wait on many sockets; epoll and kqueue retain registrations and return ready events, avoiding repeated full interest-list submissions.
  • Level-triggered repeats while data remains; edge-triggered does not guarantee reminders for leftover data. Drain or explicitly schedule more work.
  • Completion I/O (IOCP, io_uring) performs the operation for you and reports when it is done, and works for files.
  • Regular files are always "ready" to select and poll: event-loop runtimes use thread pools or io_uring for disk work.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A server watches 20,000 mostly idle connections. At any moment about 50 have data. What structural advantage does epoll have here?
Why. The important advantage is avoiding a fresh scan and submission of the whole interest list each wait, not a universal performance guarantee. epoll is still a readiness API: you do the reads yourself. A common FD_SETSIZE of 1,024 limits descriptor numbers usable with select, not with poll. Epoll maintains readiness metadata, not a dedicated thread per descriptor.
An edge-triggered epoll loop receives a readable event with 2,000 bytes already buffered. Its one read returns 512 bytes, then it waits again. The peer sends no more data and stays connected. What failure is possible?
Why. Events are not a count of reads or messages. Unread data alone does not require another edge, so stopping early can strand 2,000 minus 512 = 1,488 bytes. The kernel neither discards them nor reports an epoll error because they remain. Drain until would-block, or retain the connection on an application ready queue.
A level-triggered event loop registers every socket for both readable and writable, permanently. Traffic is light, but one core sits at 100 percent. Why?
Why. A healthy connected socket with spare send-buffer capacity is writable, even with no application output queued. Repeated writable notifications explain the spin without a flood of reads or retransmissions. Level-triggered loops can sleep when no watched condition holds; register write interest only while output is queued.
What does a proactor (completion-based) API give you that a readiness API does not?
Why. Readiness says "attempt the operation now"; completion says "your read finished, here is how many bytes". The OS or library performs the submitted operation. Completion APIs can represent disk reads, but still need execution resources and TCP flow control. A completion can be partial; it does not identify application message boundaries.
Why does Node.js, which is built on an event loop, still run a thread pool?
Why. Regular files are always reported "ready", and a read that misses the page cache blocks anyway. libuv can do that work on workers and dispatch completion to the event loop. This pool does not run user JavaScript callbacks or exist primarily for accepting sockets. Availability of epoll is separate from the need to offload file work; dns.resolve is also different from dns.lookup.
Java onlyA Java NIO loop handles each key from selector.selectedKeys() but never calls iterator.remove(). What goes wrong?
Why. Selection adds or updates ready live keys without clearing previously handled live keys. Remove each as you process it. Cancelled keys are a separate case: selection removes them during deregistration. Omitting removal does not itself throw, change blocking mode or duplicate bytes already consumed; it can repeat handler work. The action-based overload avoids manual iteration, but its contract does not promise an empty selected set afterward.
In the runnable pipe demo, each writer queues request 1;request 2; and closes. The read buffer holds only five bytes. After all reads complete, what does the line for connection 0 print?
Why. The loop accumulates positive read counts and keeps selecting until EOF. Level-triggered readiness reports remaining bytes, and writer closure does not discard them. The final data read can be shorter than five bytes; EOF is observed only after the data is drained. No request-boundary assumption is needed.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
"Explain what happens, step by step, from the moment bytes arrive on one of 10,000 sockets to the moment an epoll-based server's handler runs. Then say what changes if you used one thread per connection instead."
Model answer

The network card delivers the packet, the kernel's TCP stack puts the bytes into that socket's receive buffer, and because the socket is registered with the server's epoll instance, the kernel adds it to that instance's ready list and wakes the thread sleeping in epoll_wait. epoll_wait returns a batch of ready events up to the supplied array capacity; if few sockets are active, it need not return all 10,000 registrations. The loop thread looks up each socket's connection state (stored in the event's data field), performs non-blocking reads until it has what it needs (or until EAGAIN if edge-triggered), appends the bytes to that connection's buffer, and if a full request is there, runs the handler. The handler must be short; if it needs the database, it starts a non-blocking call or hands the work to a pool and returns, and the loop goes back to epoll_wait.

With one thread per connection, each of the 10,000 threads is asleep inside its own blocking read. The arrival wakes exactly the thread blocked on that socket; it runs its handler as plain sequential code and blocks again. The work per event is similar, but the cost of the idle connections is not: 10,000 threads means 10,000 stacks and kernel thread objects, and under load the scheduler juggles thousands of runnable threads. The event loop avoids one OS thread per connection and processes batches of events. Socket buffers and other connection state still need a memory budget.

Debug
A teammate's epoll server works in tests but, in production, some clients that send large requests hang until they time out. CPU is low. The registration code sets EPOLLIN | EPOLLET, and the read handler calls read(fd, buf, 4096) once per event. What is wrong, and how do you fix it?
Model answer

The loop is edge-triggered but reads only once per notification. Edge-triggered epoll does not promise repeated notification just because data remains. Tests send small requests that fit in one 4 KB read, so they pass. In production, when more than 4 KB is already buffered before the handler reads, a single read leaves bytes in the kernel buffer; no new data arrives (the client is waiting for a reply), so another notification is not guaranteed, and the connection can stall until the client times out. CPU is low because nothing is spinning; the loop is simply never told to look again.

Fix: in the handler, loop on read until it returns EAGAIN (or EWOULDBLOCK), appending to the connection's buffer, and treat 0 as the peer closing. The sockets must be non-blocking, or the final read would block the whole loop. Alternatively, drop EPOLLET and use level-triggered mode, where leftover data is reported again on the next wait. Retry EINTR, handle other errors, and use an application ready queue if a fairness budget stops draining early. Test data already buffered beyond the read limit with no later arrivals; a single TCP write alone does not guarantee one readiness event.

How a senior would say it
One thread can serve many sockets because it does work only for sockets that can make progress. I would configure them as non-blocking, register their interests and wait for a batch of readiness events. After a notification, I attempt the operation and handle partial data, would-block, EOF or an error. Readiness is not a reservation of bytes or a complete request. With poll, each wait submits the watched array again. Epoll and kqueue retain registrations and return ready events, which avoids repeatedly submitting the whole idle population. There is still kernel bookkeeping and application work, so this is not a promise of constant cost. Completion changes the contract. I submit an operation with a buffer and later receive its result. A successful read has already placed bytes in that buffer, but it may still be partial. The buffer must remain valid until completion. In either design, handlers must be short and buffers bounded. Regular files need special care: readiness does not prevent a cache-missing disk read from blocking, so I would offload that call or use supported asynchronous file operations.

"Our edge-triggered server hangs on large requests. It reads once per event and CPU usage is low. Walk me through the failure and the fix."
What a strong answer covers
  • Unread bytes do not guarantee another edge-triggered notification
  • Give an interleaving with more buffered data than one read consumes
  • Use non-blocking reads until would-block, handling interruption, EOF and errors
  • Apply a fairness budget with an application ready queue if draining stops early
  • Test buffered excess data with no later arrivals rather than relying on TCP write boundaries
How a senior would say it
The likely bug is waiting for another edge while unread data is already available. Edge-triggered readiness does not promise repeated reminders just because bytes remain in the socket buffer. For example, suppose two thousand bytes are buffered when the event arrives. The handler reads five hundred and twelve, then goes back to waiting. The remaining fourteen hundred and eighty-eight bytes can sit there indefinitely if the client waits for a response and sends nothing more. Low CPU fits that symptom: the loop is waiting, not spinning. I would use non-blocking descriptors and keep reading until would-block, while handling interrupted calls, EOF and real errors. A blocking descriptor would make the final read stall the entire loop. I would also protect fairness. If a hot connection exhausts its work budget before it is drained, I would put it on an application ready queue and resume it without requiring another kernel event. Level-triggered mode is a simpler alternative. The regression test should leave more data buffered than one read consumes, with no later arrival. One large TCP write alone does not guarantee that setup.

Out loudabout 60 s
"An asynchronous read times out. Can I immediately recycle its buffer for another request?"
What a strong answer covers
  • A request timeout does not prove the underlying operation stopped using its buffer
  • Keep storage valid until the operation's completion or cancellation contract permits reuse
  • Resolve the timeout-completion race once on the state owner and ignore late delivery
  • Bound outstanding buffers and distinguish local cancellation from remote side effects
How a senior would say it
No. A request timeout does not prove that the underlying read has stopped using the buffer. I have to follow the I/O API's completion and cancellation contract before recycling that storage. I would mark the request timed out on its state owner and request cancellation if the API supports it. The completion path still has to run or otherwise reach a documented final state. If completion wins the race, it may deliver bytes; if timeout wins, I discard that late result for the caller, while still performing cleanup exactly once. Until the operation is finished, I keep the buffer valid and avoid resizing or reusing it for another request. I also bound outstanding operations so timed-out requests cannot leave unlimited buffers retained. Finally, cancellation of local waiting says nothing by itself about whether a remote server already performed a write or another side effect.
