unique_ptr, shared_ptr and weak_ptr

Owning heap objects with unique_ptr and shared_ptr, observing them with weak_ptr, and exactly what shared_ptr makes thread-safe: the count, never the object.

Asked atVMwareAdobe
Before this:Copy, move and move-only types

Smart pointers decide who deletes an object and when. In threaded code that becomes the question of which thread lets go last, and std::shared_ptr answers it safely. It answers nothing else: the object it points to is exactly as unprotected as before.

In plain words

Think of renting a boat on a lake. With a single renter, one person holds the key and returns the boat when they are done. With a group rental, there is a sign-out sheet at the dock: everyone signs on and off, and the boat goes back when the last person signs off. The sheet is tamper-proof, so two people signing at the same moment never corrupt it. But the sheet says nothing about who is steering: two people grabbing the wheel at once still crash the boat.

A third option is the dock's phone number. You can call to ask whether the boat is still out, and if it is, sign yourself onto the sheet before you climb aboard. Those three are std::unique_ptr, std::shared_ptr and std::weak_ptr.

Why this matters for concurrency

  • When the last std::shared_ptr to an object goes away, the object is destroyed on whichever thread happened to let go last. Copying and destroying different shared_ptr objects that share one object is safe from any thread, because the reference count is updated atomically.
  • The pointed-to object gets no protection at all. Two threads making unsynchronized conflicting accesses through their own copies of a shared_ptr have a data race.
  • One shared_ptr variable that a thread reassigns while another thread copies it is also a data race: the classic "reload the config" bug. C++20 adds std::atomic<std::shared_ptr<T>> for it; a mutex works everywhere.
  • A std::weak_ptr observes without keeping the object alive. Its lock() operation can acquire a temporary owner that keeps the object alive during a callback or cache access.
  • Interviewers ask you to build one. A 2021 VMware candidate had to implement their own shared and unique pointer and then answer what happens in a multithreaded environment and how to synchronize it; a 2021 Adobe candidate was grilled on smart pointers alongside mutexes, lambdas and move semantics; and a prep bank lists a thread-safe reference counted pointer for an Nvidia C++ team. The senior section builds one.

Owning raw pointers were the problem

Before C++11, heap objects were created with new and destroyed with delete, and the type T* said nothing about who must delete. Every early return, every exception and every hand-off between threads was a leak or a double delete waiting to happen. Smart pointers move ownership into the type: std::unique_ptr<T> has one owner, std::shared_ptr<T> has shared owners, std::weak_ptr<T> only observes. A plain T* or T& is still right for "I use this object; someone else owns it". This course never writes a naked new or delete.

std::unique_ptr: exactly one owner

A std::unique_ptr owns one object and deletes it in its destructor. It is move-only and has no reference-counting overhead. With the default deleter, common implementations make it the same size as a raw pointer, although the standard does not guarantee that size.

For threads, a unique_ptr makes ownership transfer explicit: move it into the thread and the thread owns the object. If no other thread accesses the object through an existing alias, it is confined and needs no lock, as the move semantics lesson showed.

std::shared_ptr: shared ownership through a control block

A std::shared_ptr lets several owners keep one object alive. Copying a shared_ptr adds an owner, destroying or resetting one removes an owner, and when the last owner goes away the object is destroyed. The bookkeeping lives in a separate control block:

PieceLives inChanged by
Pointer to the objectEach shared_ptrAssignment, reset, swap on that shared_ptr
Pointer to the control blockEach shared_ptrThe same
Strong count (owners)The control blockEvery copy and destruction of a shared_ptr, atomically
Weak count (observers)The control blockEvery copy and destruction of a weak_ptr, atomically
Deleter and allocatorThe control blockSet once, at creation

A shared_ptr is typically two pointers wide; its exact size is implementation-dependent. Common implementations of std::make_shared<T>(args) place the object and the control block in one allocation, which saves an allocation and keeps them close in memory. The price of that combined allocation: the object is destroyed when the strong count reaches zero, but its storage cannot be returned until the weak ownership also ends. For a large object watched by long-lived weak_ptrs, create it from a unique_ptr instead (std::shared_ptr<T> p = std::make_unique<T>(args);), which gives it a separate control block.

What shared_ptr makes thread-safe, and what it does not

The rule has three parts. Learn it word for word, because "is shared_ptr thread-safe?" is one of the most common C++ concurrency questions, and a vague yes or no fails it.

  1. Different shared_ptr objects, even copies that share one object, may be copied, assigned and destroyed from different threads freely. The counts are atomic, and exactly one thread runs the destructor.
  2. One shared_ptr object used by several threads, with at least one of them calling a non-const member (assignment, reset, swap), is a data race.
  3. The pointed-to object is not protected by anything. Its thread safety is whatever its own class provides.
Two threads, no lockSafe?
Each copies its own shared_ptr to one object, or lets its copy goYes: atomic count, exactly one destructor call
Each only reads the object through its own copyYes, if the object's const operations are safe (the const lesson)
One writes the object, the other reads or writes itNo: rule 3
One assigns a shared_ptr variable, the other copies that same variableNo: rule 2
Both call const members (get(), operator->, use_count()) on one variable, nobody writes itYes

Rule 3 in action: each thread has its own copy, so the count is fine, and the int they both increment is not.

The printed count may well be 2000 and use_count is back to 1: the copies were handled perfectly. ThreadSanitizer still reports the race on the int, because nothing orders the two threads' increments.

Rule 2 is the subtler bug. A service keeps its configuration in one global shared_ptr; a reload thread replaces it while request threads copy it:

Copying a shared_ptr is not one atomic step: it reads two pointers, then increments a count. Only the increment is atomic. If the variable is replaced in between, the copy can increment a count in freed memory.

Fix 1: a mutex around the variable

Readers copy the pointer under a lock, then use their copy with no lock at all; the writer builds the new object outside the lock and swaps pointers under it. This works with every compiler and is the version to write in an interview. The worked example below runs it under load.

Fix 2: std::atomic<std::shared_ptr> (C++20)

It makes loads, stores, exchanges and compare-exchanges of the variable atomic, never the pointee. GCC's library (from GCC 12) and Microsoft's ship it; libc++, which Apple clang and this site use, does not yet, so check the feature macro __cpp_lib_atomic_shared_ptr before relying on it. It is usually not lock-free, because it must update two words consistently; is_lock_free() tells you. The older free functions std::atomic_load(&sp) and std::atomic_store(&sp, value) do the same job, compile everywhere, and are deprecated in C++20.

std::weak_ptr: observe without owning

A std::weak_ptr is created from a shared_ptr and does not keep the object alive. To use the object you call lock(), which in one atomic step either gives you a new owning shared_ptr or an empty one if the object is gone. Holding that shared_ptr keeps the object alive for as long as you need it.

expired() returning true is final, but false can be stale an instant later, which makes it a check then act race. Uses: caches that should not keep entries alive, observer lists, back pointers that break cycles, and callbacks that should quietly skip their work if the target died.

Keeping yourself alive in async callbacks

A member function that hands a callback capturing this to another thread, a timer or an executor creates a dangling pointer the moment the object is destroyed before the callback runs. Derive from std::enable_shared_from_this and capture an owner or an observer instead:

shared_from_this() only works when the object is already owned by a shared_ptr, so create it with std::make_shared. Called from the constructor, or on an object that no shared_ptr owns, it throws std::bad_weak_ptr (since C++17).

Cycles leak

Two objects that own each other through shared_ptr form a reference cycle: they keep each other's strong count above zero forever, so neither destructor ever runs. Make one direction a weak_ptr, usually the back edge: child to parent, observer to subject, callback to its owner.

The threaded version of this leak is worse than lost memory. An object that owns a worker thread and also stores a callback capturing shared_from_this() keeps itself alive: its destructor never runs, so its thread is never stopped or joined.

make_shared, make_unique and passing smart pointers

  • Prefer std::make_unique and std::make_shared. No naked new, the type is written once, and make_shared allocates once. Use a constructor only for a custom deleter.
  • Never build two shared_ptrs from one raw pointer. std::shared_ptr<Widget> b(a.get()); creates a second control block, so the object is deleted twice. Copy the shared_ptr instead.
  • Pass by what the function needs. A function that only uses the object takes T& or T*. One that takes ownership takes std::unique_ptr<T> by value. One that keeps a share (a thread, a stored callback) takes std::shared_ptr<T> by value.
  • A thread that may outlive its creator's interest must own a copy. Pass the shared_ptr by value or capture it by value. A const std::shared_ptr<T>& parameter or a [&sp] capture gives the thread no ownership at all.
  • Copies cost atomic operations. As an order of magnitude, an uncontended atomic increment costs a few nanoseconds, while many threads copying the same shared_ptr in a hot loop fight over one control block's cache line and pay far more. Copy at ownership boundaries, pass references inside a thread.

Worked example: a config that reloads under 3 reader threads

Readers call current() thousands of times a second; a reload thread swaps in new versions. Each Config has an invariant across two fields (the endpoint always names the version), so a torn read would be visible.

It prints checked 6000 snapshots, 0 inconsistent; now on db50, with ThreadSanitizer silent. Four decisions make it work:

  • std::shared_ptr<const Config>: a published config is an immutable object, so readers need no lock while they use it.
  • The lock covers only the pointer copy and the pointer swap, a handful of instructions, so readers barely contend.
  • The new config is built before taking the lock, and the old one is released after dropping it.
  • The old config is destroyed by whichever thread lets go last. If a reader still holds version 7 when version 8 is published, that reader's thread runs version 7's destructor when it finishes. Destructors of shared objects must therefore be cheap and must not take locks the readers might hold.

This is the copy-on-write pattern, and the same shape as read-copy-update in operating system kernels. You will meet it again in copy-on-write and snapshots.

Common mistakes

  • "It is in a shared_ptr, so it is thread-safe." Only the count is. Protect the object, or make it immutable.
  • Sharing one shared_ptr variable between threads with a writer and no lock. Use a mutex or an atomic shared_ptr.
  • Two control blocks for one object, from constructing two shared_ptrs out of one raw pointer. Double delete.
  • if (!w.expired()) w.lock()->use(); The object can die between the calls. Use if (auto p = w.lock()).
  • Cycles, including an object holding a callback that captured shared_from_this().
  • shared_from_this() in a constructor, or on an object not owned by a shared_ptr: std::bad_weak_ptr.
  • Passing a shared_ptr into a thread by reference, which gives the thread no ownership.
  • Deciding things from use_count() in threaded code. The value can be stale by the time you read it.
  • shared_ptr everywhere. When ownership is not truly shared, unique_ptr is clearer and costs no atomics.

In the interview

"Is shared_ptr thread-safe?" is the classic, and the follow ups test whether you know the three parts. You may also be asked to write your own reference counted pointer and then make it thread-safe (VMware, 2021), to explain when to use weak_ptr, and to compare make_shared with constructing from new.

The control block is thread-safe: different shared_ptr instances can be copied and destroyed from different threads, the count is atomic, and exactly one thread runs the destructor. The pointed-to object is not protected at all, and a single shared_ptr variable that one thread reassigns while another reads it is a data race. For that I use a mutex around the variable, or std::atomic<std::shared_ptr> in C++20.
For a read-mostly config I publish immutable snapshots: readers copy a shared_ptr<const Config> under a tiny lock and use it lock-free; the writer builds the new one outside the lock and swaps the pointer. The old version dies when its last reader lets go, on that reader's thread.

Follow ups: "Why is the increment relaxed but the decrement not?" (the senior section); "What is the size of a shared_ptr?" (typically two pointers, not a standard guarantee); "Why might make_shared keep memory alive longer?" (object and control block usually share one allocation, freed only when weak references are gone too).

Senior depth: a thread-safe reference counted pointer from scratch

This is the question behind the VMware report: write your own shared pointer, then make it safe when several threads copy and drop it. Here is a compact version with an owning pointer, a weak observer and the upgrade from one to the other. It allocates through std::make_unique and frees by handing the raw block back to a std::unique_ptr, so even the from-scratch version has no naked new or delete.

It prints destroyed 1 time(s); lock() now gives nothing, with ThreadSanitizer silent, although five threads copy, drop and upgrade concurrently and main lets go first. The reasoning behind each line is what the interviewer is really grading:

  • The increment can be relaxed. Whoever copies already owns a reference, so the count cannot reach zero during the copy, and the increment publishes nothing that another thread needs. Only atomicity matters.
  • The decrement needs release, and the final one needs acquire. Release, so that everything this owner did to the object happens before the destruction. Acquire on the decrement that reaches zero, so the destroying thread sees every other owner's writes before running the destructor. Without them, the destructor could run while another core's last writes to the object are still in flight. libstdc++ and libc++ use an acquire-release fetch_sub. Boost's classic form uses a release fetch_sub and then std::atomic_thread_fence(std::memory_order_acquire) only inside the last-owner branch, which saves the acquire on every other decrement. Note that GCC warns that ThreadSanitizer does not support standalone fences, so the acquire-release form is also the easier one to test.
  • Two counts. The object dies when the strong count reaches zero; the control block dies when the weak count does. All owners together hold one weak reference, so the block cannot vanish while any owner or observer still points at it.
  • Upgrading a weak reference is a compare-exchange loop that increments only from a value above zero. A plain fetch_add would "revive" an object whose count already hit zero and whose destructor may be running. If another thread changes the count first, the failed compare-exchange reloads n and the loop checks for zero again.
  • The deleter is captured with the real type when the block is created (here, std::unique_ptr<T> for the exact T passed to make). That is why std::shared_ptr<Base> p = std::make_shared<Derived>(); destroys a Derived correctly even if Base has no virtual destructor. Converting a std::unique_ptr<Derived> to std::unique_ptr<Base> with the default deleter instead causes undefined behavior on deletion through that nonvirtual base; destroying only the base part is not a guaranteed outcome.
  • The instance is still not thread-safe. Two threads may copy the same RcPtr object at once, because copying only reads it. But one thread assigning to an RcPtr variable while another copies it races exactly as with std::shared_ptr: the copier can read the old block pointer and increment a block that the assignment just freed. That gap is what std::atomic<std::shared_ptr<T>> closes.
  • The rest of the follow ups: make_shared puts the object inside the block for one allocation (this sketch uses two to stay short), and reference counting cannot reclaim cycles, which is why weak references exist.

Read-mostly pointer swapping is common enough that C++26 adds standard read-copy-update (<rcu>) and hazard pointers (<hazard_pointer>), which let readers skip even the atomic increment. The memory order details are in memory orders.

Key takeaways

  • unique_ptr: one owner, move-only, no reference counting. shared_ptr: shared owners with an atomic count in a control block. weak_ptr: an observer that must lock() before use.
  • Different shared_ptr objects are safe across threads; one shared_ptr variable with a writer is a data race; the pointee is never protected.
  • Fix a shared shared_ptr variable with a mutex around copy and swap, or C++20's std::atomic<std::shared_ptr<T>> where the library ships it.
  • Use if (auto p = w.lock()), never expired() then lock(). Break cycles with weak back edges, and capture shared_from_this() or weak_from_this() in async callbacks.
  • The last owner runs the destructor on its own thread, so keep shared-object cleanup cheap and avoid taking locks that the releasing thread may already hold.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Two threads each receive their own copy of a std::shared_ptr<int> that points at one int, and each runs *p += 1 a thousand times. What is true?
Why. The atomic count protects the bookkeeping: who owns the object and who deletes it. The int itself has no protection, so two unsynchronized increments race. Use an atomic, a mutex, or give each thread its own counter.
A global std::shared_ptr<Config> cfg; Thread A runs cfg = std::make_shared<Config>(next); while thread B runs auto mine = cfg;, with no lock. What can happen?
Why. Copying a shared_ptr reads two pointers and then increments a count; only the increment is atomic. If A replaces cfg and drops the old object's last reference in between, B touches freed memory. Guard cfg with a mutex or make it std::atomic<std::shared_ptr<Config>>.
Which code correctly uses a std::weak_ptr<Widget> w that other threads may be about to release?
Why. lock() atomically checks and takes ownership in one step, and the resulting shared_ptr keeps the widget alive while you use it. Checking expired() or use_count() first is a check-then-act: the last owner can let go between the check and lock(), which then returns null. weak_ptr has no operator-> at all.
a->next = b; b->next = a; where both next members are std::shared_ptr<Node>, and then the local a and b go out of scope. What happens?
Why. A reference cycle keeps every strong count in it above zero. Make one direction a std::weak_ptr, typically the back edge, and the cycle no longer owns itself.
A reader thread and the writer thread each destroy their copy of the last two shared_ptrs to a large object at about the same moment. What happens?
Why. The atomic decrement guarantees exactly one thread sees the count drop from 1 to 0, and that thread destroys the object. It may be a reader in a latency-sensitive path, so destructors of shared objects should be cheap and should not take locks other users might hold.
struct Base { ~Base(); }; (not virtual) and struct Derived : Base { std::vector<int> data; };. Which line destroys a Derived correctly, including data?
Why. A shared_ptr captures the deleter for the real type when its control block is created, so it calls ~Derived even through a shared_ptr<Base>. unique_ptr<Base> uses default_delete<Base>, which deletes through a Base*: without a virtual destructor that is undefined behavior. Base classes used polymorphically should still have virtual destructors.
What does C++20's std::atomic<std::shared_ptr<T>> make atomic?
Why. It fixes rule 2, a shared shared_ptr variable with a writer, by making operations on the variable atomic. The object it points to is still unprotected. Plain shared_ptr already has an atomic count.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
"Is std::shared_ptr thread-safe?" Answer precisely, as you would in the interview.
Model answer

Partly, and it is worth being exact. First, the control block is thread-safe: different shared_ptr objects, even copies sharing one object, can be copied, assigned and destroyed concurrently from different threads; the strong and weak counts are updated atomically, and exactly one thread, the one that drops the count to zero, runs the destructor. Second, a single shared_ptr object is not: if one thread assigns or resets a shared_ptr variable while another thread reads or copies that same variable, that is a data race, and the reader can end up with a dangling pointer. I fix that with a mutex around the copy and the swap, or with std::atomic<std::shared_ptr<T>> in C++20 where the library provides it. Third, the pointed-to object is not protected at all: if threads write it, it needs its own synchronization, or I make it immutable and share it as shared_ptr<const T>. One more practical point: the last owner runs the destructor on its own thread, so I keep destructors of shared objects cheap.

Write code
Write an EventBus with subscribe(std::shared_ptr<Listener>) and publish(event). Publishing can run concurrently with subscribing, and external owners can release a listener without unsubscribing. Stored subscriptions must not keep listeners alive, but publishing may acquire temporary ownership while calling a live listener.
Model answer

Stored weak references do not keep listeners alive. lock() atomically either gives a temporary owner for the duration of the call or skips a listener that has died, so a listener cannot be destroyed in the middle of on_event. The list is copied under the mutex and callbacks run without it: a slow listener delays that publisher but does not hold up subscriptions, and a callback can subscribe without re-entering a held bus mutex. Concurrent publishers can still call the same listener concurrently, so the listener must protect its mutable state. std::erase_if is C++20; in C++17 use the erase and remove_if idiom. Pruning with expired() is only tidying: a listener that dies right after the check is skipped by lock() later.

Design
You are asked to implement a thread-safe reference counted pointer without the standard smart pointers. Outline the data layout, the increment and decrement with their memory orders, how weak references work, and what you would say about cycles.
Model answer

Layout: the pointer object holds a raw pointer to the managed object and a pointer to a heap control block. The control block holds an atomic strong count, an atomic weak count and a type-erased way to destroy the object (a virtual function or a function pointer captured with the real type, so a base class without a virtual destructor is still destroyed correctly). A factory can place the object inside the control block for a single allocation.

Copying increments the strong count with a relaxed fetch_add, which is enough because the copier already owns a reference. Destroying does fetch_sub(1, acq_rel); the thread that sees the old value 1 destroys the object: release so every owner's writes happen before destruction, acquire so the destroying thread sees them. Then it releases the implicit weak reference the strong owners hold, and whoever drops the weak count to zero frees the control block. A weak pointer copies only the weak count. Its lock() must not resurrect a dead object, so it loops: load the strong count, stop if zero, otherwise compare-exchange count to count plus one. Copy and move assignment must handle self-assignment and release the old reference after taking the new one. Assigning one shared instance from several threads is still a race, as with the standard type.

Cycles: reference counting cannot collect them. I would document that ownership graphs must be acyclic and break back edges with weak pointers, and mention that the standard design behaves the same way, which is why std::weak_ptr exists.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"A teammate says our config is thread-safe because it is in a shared_ptr. How would you review that claim?"
What a strong answer covers
  • Separate control-block safety, access to one pointer variable, and access to the pointee
  • Different owning handles can be copied or destroyed concurrently without corrupting ownership
  • Copying a shared variable while another thread assigns it needs a mutex or atomic shared pointer
  • An immutable config snapshot permits reading outside the pointer lock; mutable fields need their own protection
  • Build outside the lock, copy or swap under it, and release the old owner outside it
  • The final owner triggers destruction on its thread, which can affect latency and locking
How a senior would say it
The reference count is safe, but that does not make the configuration thread-safe. I would review three separate things: the ownership bookkeeping, the pointer variable, and the config itself. Different shared pointers can safely own the same object while different threads copy or destroy their own handles. That protects lifetime. But if a reload thread assigns one global pointer while a reader copies that same variable, those operations race. An atomic reference count does not make copying the handle atomic. I would guard the copy and replacement with one mutex, or use an atomic shared pointer where the C++20 library supports it. Next I would make each published config immutable. A reader takes the mutex, copies an owning handle, unlocks, and uses that snapshot. The writer builds a complete replacement outside the lock and swaps it in under the lock. Existing readers can finish on the old version. I would also release the writer's old handle outside the lock, because releasing it might run a destructor. Whichever thread drops the final owner triggers destruction, so cleanup must fit that thread's latency and locking constraints. This design separates safe publication, stable lifetime, and immutable contents; mutable contents would still need their own synchronization.

Likely follow up: Would checking that use_count() is one let the writer safely modify the config in place?

Out loudabout 75 s
"You are handing work to a background executor. When would you capture a unique_ptr, a shared_ptr, or a weak_ptr?"
What a strong answer covers
  • Move a unique pointer when the task takes sole ownership and existing aliases will not access the object
  • Capture a shared pointer by value when the task must keep the object alive alongside other owners
  • Capture a weak pointer when work should be skipped if the object has died
  • Call weak-pointer lock once, test the result, and retain that owner throughout use
  • An expired check followed by lock can fail between the two calls
  • Ownership does not synchronize mutable state, and stored strong callbacks can create cycles
How a senior would say it
I choose according to the lifetime the work needs. If a job belongs entirely to one task, I move a unique pointer into the closure and stop accessing the job through any old aliases. That gives the task sole ownership without reference counting. If several operations must keep a session alive, I capture a shared pointer by value. The queued task then owns a share even after its caller returns. If the operation is optional, like a delayed refresh that should disappear with its session, I capture a weak pointer. When the task runs, I call its lock function once and check the returned shared pointer. A successful result keeps the session alive for the whole operation. Checking expired first is insufficient: the last owner can disappear before the later lock call. Finally, none of these choices serializes access to the session's fields. Shared mutable state still needs protection. I also check for cycles: a session that stores a callback owning that same session can keep itself alive forever. A weak capture can break that ownership cycle.

Likely follow up: What happens if the session calls shared_from_this() from its constructor?

Out loudabout 90 s
"You are implementing a reference counted pointer. Walk me through weak-pointer promotion while another thread releases the last strong owner."
What a strong answer covers
  • The weak reference retains the control block but does not retain the managed object
  • Promotion uses compare-exchange to increment the strong count only while it is nonzero
  • If promotion wins from one to two, the releasing owner leaves one owner and cannot destroy the object
  • If release wins from one to zero, promotion fails and must never resurrect the object
  • Ordinary copies may increment relaxed; releases need release ordering and final destruction needs acquire ordering
  • Free the control block only after weak ownership ends, and synchronize access to each mutable handle separately
How a senior would say it
Promotion must compete atomically with the final release, and it must never bring a zero strong count back to life. The weak reference keeps the control block allocated, so it can safely inspect the count even after the managed object is destroyed. I would load the strong count and use a compare-exchange loop to increment it only while it is nonzero. Suppose the count is one. If promotion changes one to two first, the original owner's release changes two to one. The promoted handle now keeps the object alive. If release changes one to zero first, destruction can begin. Promotion must fail, observe zero, and return empty. A separate positive check followed by an unconditional increment would leave a gap that could resurrect a destroyed object. For ordinary copies, an existing owner already keeps the object alive, so a relaxed atomic increment is enough. Releases need release ordering, and the final release needs acquire ordering before destruction; an acquire-release decrement is a simple implementation. The control block survives until its weak ownership is also gone. None of this protects concurrent reassignment of the same handle, or concurrent mutation of the pointee. Those remain separate synchronization responsibilities even when every count update is atomic.

Likely follow up: Why can this implementation still leak two objects that own each other?
