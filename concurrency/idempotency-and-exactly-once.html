Idempotency, retries and exactly-once effects

Make retries safe with durable idempotency keys, atomic effects and an outbox, and identify the boundary of exactly-once processing.

Asked atUberRipplingSalesforceLinkedIn
Before this:Optimistic versus pessimistic concurrency controlBulkheads, timeouts, retries and circuit breakers

A timeout does not tell you that a request failed. It tells you that you do not know. Every retry is a bet that the first attempt did not happen, and idempotency is how you make that bet safe to lose.

In plain words

You tap "Pay" in an app. The spinner spins, and then: "Something went wrong, try again". Did the shop charge you? You cannot tell. Tap again and you might pay twice; do not tap and you might not have paid at all.

Now imagine the shop writes your order number on every payment and refuses to charge the same order number twice. Tapping again becomes harmless: if the first payment went through, the shop just shows you the same receipt. That order number is an idempotency key, and the property it buys, doing something twice has the same effect as doing it once, is idempotency.

A timeout means "unknown outcome"

When a call over the network times out, several outcomes are possible, and the caller cannot tell which:

  1. The request never reached the server. Nothing happened.
  2. The server did the work, and the response was lost on the way back.
  3. The server is still doing the work, slowly, and will finish after you gave up.
  4. The server rejected or aborted the work, but its error response was lost. Work spanning several systems may also have partially completed.

A timeout alone cannot resolve this doubt: acknowledgements can be lost too. If you do not retry, you risk losing the operation; if you retry without deduplication, you risk doing it twice. Durable status lookup and reconciliation can resolve the uncertainty after communication recovers; retries need an explicit policy for duplicates.

Delivery guarantees, honestly named

GuaranteeHow you get itWhat can go wrong
at-most-once deliveryDo not retry an uncertain attempt, or suppress repeated executionThe operation may never happen; lower layers must also respect the intended boundary
at-least-once deliveryDurably retain work and retry until acknowledgedDuplicates; eventual completion assumes recovery and continued retries
exactly-once deliveryCannot promise both eventual delivery and no repeated transmission under arbitrary message lossApplication delivery can still be deduplicated inside a defined boundary
Exactly-once effect (effectively once)At-least-once attempts plus durable, atomic deduplication of the effectLimited by retention, recovery and which effects participate in the atomic commit

The last row is the whole lesson in one line. You cannot stop a message arriving twice; you can make the second arrival do nothing.

Idempotent operations

An operation is idempotent if repeating it leaves the same intended state as applying it once. Responses may differ, for example a second deletion may return not found. These examples assume no intervening operation, and for SQL only the shown row effects, without triggers:

  • UPDATE orders SET status = 'SHIPPED' WHERE id = 7 (setting an absolute value)
  • DELETE FROM carts WHERE id = 9
  • HTTP PUT (replace the resource) and DELETE have idempotent intended semantics; POST has no such guarantee, though an application can make it idempotent

Others are not: balance = balance - 10, "append to the log", "send an email", "create an order". A tempting trick is to turn a relative change into an absolute one ("set the balance to 90"). That is idempotent, but if 90 was computed from a stale read it is a lost update. An absolute write based on a read needs a version check and an increment of that version in the same update (WHERE version = 7, SET version = version + 1), which is the optimistic pattern from the previous lesson.

Idempotency keys

For operations that are not naturally idempotent, the client attaches a unique key to the logical operation, and the server remembers which keys it has already processed.

The client's rules. Create the key once per logical operation (one purchase, one transfer), before the first attempt, and send the same key on every retry. A random UUID is the usual choice. If the operation must survive a client crash, store the key with the pending operation so the restarted client retries with the same key. Many payment APIs accept the key in a request header; Stripe's public API, for example, calls it Idempotency-Key; see its idempotent request contract.

The server's rules. Recording "I have seen this key" is itself a check-then-act, so it must be atomic: a unique constraint does it. Scope the key by authenticated client and operation, authorize every retry, and fingerprint the canonical request including amount, currency and recipient. Otherwise a reused key can expose another customer's response or silently refer to different work.

For this database-only path, the key, debit and payment commit together or all roll back. A conflicting insert waits: if the first transaction commits it inserts nothing, and if the first rolls back it can become the owner. At READ COMMITTED, a subsequent statement can read the committed winner; this path does not expose an uncommitted in_progress row. The unique constraint durably arbitrates a key, while the transaction makes its effect atomic. See PostgreSQL's isolation documentation.

Replay the stored terminal response, including its status, rather than recomputing it. Retain keys through the documented retry and replay horizon, including delayed queues and disaster recovery; never evict unresolved work simply because it is old. After deletion, a delayed retry can execute again, so permanent business uniqueness may still be necessary. Status 422 for a mismatched fingerprint and 409 for work still running are possible API choices, not universal idempotency rules.

When the work includes a call outside your database (charging a card through a payment network), you cannot commit it together with the key. Commit the key as in_progress first, call the provider with the same idempotency key passed along, then record the result. A duplicate that finds in_progress answers "still processing" (or waits), and a recovery job finishes or reconciles keys stuck in progress.

Derive the provider key from your scoped operation identity and preserve it across recovery. A timeout must leave the operation unresolved, not free its key. Reconcile against the provider before its deduplication window ends; if that window has expired, blind retry is unsafe. If the provider offers neither deduplication nor a reliable status query, you cannot guarantee both eventual execution and no duplicate charge.

Client and server, in code

The in-memory version of the server keeps a map from key to the future outcome of the first attempt. putIfAbsent decides atomically who owns the key; every duplicate, even one that arrives while the first is still running, waits on the same future and replays its result. This is the single-flight idea from thread-safe caches, applied to side effects.

Its guarantee lasts only for this server object's lifetime: the map is not shared across replicas, durable across crashes or bounded in size. Java's join() waits without an interruptible timeout; production callers need bounded waits that leave the shared operation intact. The fake network is confined to one client thread, and immediate retries keep the demonstration short.

The first line demonstrates a retry helper that creates a fresh key on every attempt. The key must be created outside the retry loop. Failures remain recorded because an exception does not prove that no charge happened; duplicates see the stored failure rather than charging again. Recovery of that failure requires reconciliation in a durable implementation.

C++

std::latch requires C++20; for this one-shot gate in C++17, use a std::promise<void> and a std::shared_future<void>. The sequential demo key is not a production UUID: real clients need keys unique across processes and restarts.

Deduplication with unique constraints

Often the data already contains a natural key that makes duplicates impossible to store: one invoice per (customer_id, billing_period), one like per (post_id, user_id), one shipment per order_id. Put a unique constraint on it and the database rejects the duplicate for you.

The same trick makes a message consumer idempotent. Record each message's id in the same transaction as its effect. The table below requires a unique event_id; if independent consumers share it, scope uniqueness by consumer identity too:

The deduplication insert and effect must commit together. If the effect commits and the dedup record does not, a redelivery applies the effect twice; if the record commits and the effect does not, the effect is lost forever. This pair, at-least-once delivery delivery and an idempotent consumer, is how real systems get exactly-once effects.

If the effect lives outside your database (an email, a push notification), you cannot commit it atomically with the record. A downstream deduplication contract can suppress repeated effects. Without one, choose explicitly between possible loss and possible duplication, or reconcile an uncertain outcome before acting again; the acceptable tradeoff depends on the product.

The dual write, and the transactional outbox

A service that must update its database and publish an event ("order paid") has a dual write problem: separate commits leave a crash window. A distributed transaction requires both systems to participate and brings coordination costs; the outbox uses one local transaction instead.

The transactional outbox fixes it by turning two writes into one. In the same local transaction as the business change, insert the event into an outbox table. A separate relay reads the outbox, publishes each event, and marks it sent. If the relay crashes after publishing and before marking, it publishes again on restart, which is at-least-once, and consumers dedupe by event id.

The relay marks only events with confirmed durable broker acknowledgements as published. Use one active publisher per aggregate, and serialize business changes for that aggregate or assign versions transactionally and publish those versions in order: ORDER BY seq alone does not guarantee business order across concurrent commits or relays. Keying by aggregate_id then preserves the publication order within a broker partition; it cannot repair events already published out of order. See ordering by ownership.

Change data capture, for example Debezium reading committed outbox inserts from the database log, can replace polling. Consumers must still deduplicate retries. An outbox needs monitoring for unsent rows, retry backoff and cleanup only after the required delivery and retention policy is satisfied.

Exactly-once needs a boundary

Repeated transmission is unavoidable when an acknowledgement can be lost and the sender retries. Exactly-once effects are achievable within a scope that controls both progress and output, because it can commit them together. Processing code may execute repeatedly even though only one result becomes visible; ask which observable effect a guarantee covers.

Kafka is the standard example. Its idempotent producer (enable.idempotence=true) tags each batch with a producer id and sequence number, so the broker drops duplicates caused by producer retries. It does not deduplicate arbitrary repeated application sends or unrelated producer sessions. Its transactions go further: a consume-transform-produce loop writes its output records and the input offsets it consumed in one transaction, so after a crash either both happened or neither did, and consumers set to isolation.level=read_committed never see records from aborted transactions.

For each batch, disable consumer auto-commit, begin a transaction, produce output records, send the next input offset for each processed partition with the current consumer group metadata, and commit. Never advance an offset past unfinished work. The producer's transactional.id must identify one logical processor across restarts and differ across active processors.

Error handling is part of the guarantee. After a confirmed abort, seek the consumer back to committed offsets, or restart it, because aborting the producer does not rewind the consumer's local position. Java commit timeouts can leave the commit in progress: retry that commit or stop and recover, rather than blindly aborting and processing the next batch. Fatal errors such as ProducerFencedException require closing the producer. C++ transactional calls return a nullable RdKafka::Error*; check its is_retriable(), txn_requires_abort() and is_fatal() classification, and own it with RAII. See the Java producer contract and C++ producer contract.

Now the boundary. If the transformation also wrote to a database, charged a card or sent an email, that effect is outside Kafka's transaction: an aborted and retried batch would do it twice. Kafka's exactly-once covers Kafka-to-Kafka processing; anything else your consumer touches still needs its own idempotency. The same is true of every system that advertises exactly-once: it holds inside the boundary that the system commits atomically, and nowhere else.

One more detail ties back to the next lesson. initTransactions() establishes a new producer epoch for the transactional.id, and the broker rejects writes from a producer with an older epoch (ProducerFencedException). That is a fencing token, so a paused "zombie" instance of the processor cannot commit after its replacement has started.

Worked example: charging for a ride, end to end

A ride ends and the app must charge the rider exactly once, then send a receipt.

  1. Client to API. The app sends POST /trips/881/charge with Idempotency-Key: trip-881-charge. The key is derived from the trip, so even a reinstalled app retries with the same key.
  2. API. Inserts the key as in_progress (unique constraint), commits, calls the payment provider passing the same key, then in one transaction records the payment, marks the key done with the response, and inserts a TripCharged row into the outbox.
  3. Duplicates. A retry that finds done replays the stored receipt. One that finds in_progress gets "still processing". A sweeper re-checks keys stuck in progress with the provider (which deduplicated on the same key).
  4. Events. The relay publishes TripCharged at least once, keyed by trip id.
  5. Receipt service. Inserts the event id into processed_events in the same transaction as recording "receipt queued", and sends the email afterwards; a rare duplicate email is accepted, a duplicate charge is not.

The payment effect is deduplicated within the provider and database boundaries. The email sender drains a durable queue and may resend after an acknowledgement is lost; this design explicitly permits duplicate emails. It does not promise exactly-once delivery of the entire workflow.

Common mistakes

  • A new key per attempt. The key must be created once per logical operation, outside the retry loop.
  • Check, then insert, for the key. SELECT the key, and if absent do the work and INSERT it: two concurrent duplicates both see "absent". Use the unique constraint.
  • Recording the key in a different transaction from a local database effect. A crash between them either loses the operation or repeats it.
  • Believing a broker's "exactly once" covers your database writes. It covers what the broker commits atomically, not your side effects.
  • Committing the offset before processing. That is at-most-once: a crash after the commit loses the message. Process, then commit.
  • Keys that expire before the client gives up. A retry after expiry is treated as new and executes again.
  • Retrying without backoff or a budget. Idempotency makes retries safe, not free; a retry storm still takes the service down.

In the interview

Research-backed examples include an Uber SE II stock alert design with idempotency key and notification-delivery follow ups, Rippling event rollups with retried batches, Salesforce payment retries, and LinkedIn notification deduplication. These are candidate reports, not guarantees about a future round. Whenever you propose a retry, be ready to explain how the receiver distinguishes a duplicate from a new operation.

A timeout means the outcome is unknown, so retries imply duplicates, so this endpoint must be idempotent. The client creates one idempotency key per payment and reuses it on every retry; the server inserts the key under a unique constraint in the same transaction as the payment, and replays the stored response to any duplicate.
Exactly-once delivery is not something a network can give us. What we can build is an exactly-once effect: at-least-once delivery plus idempotent consumers that record each event id in the same transaction as the change. For the database write plus the event, I would use a transactional outbox instead of a dual write.

Follow ups to expect: "What if two copies arrive at the same time?" (the unique index serializes them; in memory, a future per key), "How long do you keep keys?" (longer than the longest client retry horizon), "What if the work calls an external system?" (in_progress state, pass the key downstream, reconcile), and "Kafka has exactly-once, why do we need this?" (its scope ends at Kafka).

Senior depth

The key store is a concurrency problem in its own right. It is a check-then-act on "have I seen this key?", so it needs an atomic insert, and its entries need a lifecycle: in progress, done, failed in a retryable way, failed permanently. Free a key only when you know no effect occurred. Decide whether validation failures are recorded; replay terminal failures that were recorded, and keep uncertain outcomes for reconciliation.

Do not page an outbox by "sequence greater than the last one I saw". Sequence numbers are handed out when rows are inserted, but transactions commit in a different order, so a row that took sequence 41 can become visible after the relay already moved past 42. Polling for unpublished rows, or reading the database's commit log with change data capture, avoids the gap.

Ordering and dedup interact. A consumer that dedupes by event id but applies events out of order can still end in the wrong state (a "cancelled" processed before "paid"). Preserve order before publication and partition by aggregate id. A version can reject stale full-state snapshots; incremental events instead need gap detection and ordered replay, because dropping an older increment can lose work.

Key takeaways

  • A timeout means unknown outcome; retrying chooses possible duplicates over possible loss.
  • Idempotency keys: one per logical operation, reused on every retry, recorded under a unique constraint in the same transaction as local database effects; external effects need downstream deduplication.
  • At-least-once attempts plus durable atomic deduplication give an exactly-once effect within the retention and recovery contract.
  • The transactional outbox replaces "write the database, then publish" with one local transaction and a relay.
  • Exactly-once describes a scoped observable effect, not code that can only execute once; Kafka transactions commit input progress and output records together.

Why. Setting an absolute value and deleting leave the same state however many times they run. Subtracting 10 twice subtracts 20, and the insert creates a second order with a new generated id. A server handles idempotency like this at READ COMMITTED: SELECT the key; if absent, charge the card and INSERT the key. Two copies of one request arrive at the same time. What can happen?
Why. Both reads can precede both inserts, so both external charges can happen even if a later unique constraint rejects one insert. Claim the key atomically first, then use a stable provider key and reconciliation for the external charge. A database rollback cannot undo a card charge. No database rule merges the charges or forces a permanent deadlock.
A team says: "Our consumer reads payments from Kafka with transactions and exactly-once enabled, so its card charges can never be duplicated." What is wrong with this?
Why. Kafka supports transactions across multiple partitions, committing output records and consumed offsets atomically. An external charge is outside that commit and can repeat when a batch is retried. It still needs a stable provider idempotency key; merely configuring a consumer does not include its external calls in a transaction.
Why is "commit the database change, then publish the event to the broker" unsafe?
Why. These two independent commits are not atomic, so a crash between the writes leaves them disagreeing; retrying in the same process does not help if the process is gone. The event cannot overtake the commit here, because it is only published after the commit returns; that is the hazard of the opposite order, publish then commit. The outbox writes the event in the same local transaction and lets a relay publish it at least once.
A consumer commits its dedup record and database effect in separate transactions. Depending on which it commits first, what can go wrong?
Why. The dedup record and the effect must commit atomically. Record first and a crash makes redelivery skip a missing effect; effect first and a crash lets redelivery repeat it. SERIALIZABLE does not combine two commits. The unique constraint still works, but uniqueness alone cannot repair the missing atomicity.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
Design the idempotency layer for POST /payments in a service that stores payments in Postgres. Cover the client, the server table, concurrent duplicates, expiry and the response to a duplicate.
Model answer

Client. Generate one UUID per logical payment before the first attempt, store it with the pending payment if the client must survive restarts, and send it as an Idempotency-Key header on every retry. Retry only with capped, jittered backoff.

Table. idempotency_keys(client_id, operation, key, request_hash, status, response, created_at), with a composite primary key on (client_id, operation, key). Authorize retries and compare a canonical request fingerprint before replay.

Flow. In one transaction: INSERT ... ON CONFLICT (client_id, operation, key) DO NOTHING. If one row was inserted, this request owns the key: do the payment writes, store the response, set status done, commit. If zero rows, it is a duplicate: read the stored row; if the hash differs, answer 422 (key reused for a different request); if done, replay the stored response; a separately committed in-progress claim in the external-call path can answer 409 or wait briefly. These status codes are our API policy.

Concurrent duplicates. The unique index serializes conflicting inserts: wait for the first transaction, then replay if it committed, or become the owner if it rolled back. At READ COMMITTED, use a fresh statement to read the committed row.

External calls. If the charge goes to a provider, commit the key as in progress first, pass the same key to the provider, then record the result; a sweeper resolves keys stuck in progress by asking the provider.

Expiry. Retain resolved keys beyond the agreed retry and replay horizon, including queues and recovery. Never expire unresolved payments without reconciliation. After deletion a retry looks new, so use a permanent payment identity if duplicates must remain impossible indefinitely.

Explain
An interviewer says: "We use Kafka with exactly-once semantics, so our consumer that charges credit cards is safe." Respond as a senior candidate.
Model answer

Kafka's exactly-once is real but scoped. The idempotent producer removes duplicates caused by producer retries, and transactions let a consume-transform-produce loop commit its output records and its consumed offsets atomically, so within Kafka a record's effect on output topics happens once. A credit card charge is not a Kafka write. If the consumer charges the card and then the transaction aborts, or the consumer crashes before committing, the batch is reprocessed and the card is charged again. So the charge needs its own idempotency: pass an idempotency key derived from the event (the payment id) to the payment provider, and record the charge with that key under a unique constraint. Kafka gives exactly-once inside its boundary; every side effect outside it needs at-least-once plus idempotency.

Write code
Write payWithRetry(key, amount) around send(key, amount), which may time out. The caller creates and persists the key with the pending payment before calling. Make at most 5 attempts with capped, jittered backoff, preserving the key for a later call if all attempts time out.
Model answer

The caller owns the stable key, so it remains available after a timeout or interruption; the backoff is capped and randomized; and after the last attempt the outcome is still unknown, so the caller keeps the key and either retries with it later or checks the payment's status, without starting over with a new key. The transport must impose a per-attempt timeout; an overall deadline bounds total latency. Java propagates interruption, and the C++ transport must be safe if callers share the client.

"The payment timed out, so the client retries. Walk me through how you prevent a second charge, including a server crash."
What a strong answer covers
  • A timeout leaves the outcome unknown, so a retry must retain the logical operation identity
  • Persist one key per payment, scope it by client and operation, and validate the request fingerprint
  • Atomically claim the key and commit database effects with the stored response
  • Concurrent duplicates replay the winner; an aborted database transaction permits another claimant
  • External charges need the same stable provider key and reconciliation of uncertain outcomes
  • Define retention and recovery boundaries; an in-memory map or a new retry key is insufficient
How a senior would say it
I would make the payment idempotent around a durable operation identity. A timeout means I stopped waiting, not that the charge failed. The client creates one key before its first attempt, persists it with the pending payment, and reuses it after retries or restarts. The server scopes that key by authenticated client and operation, and rejects a different request under the same key. For database-only effects, I insert the key under a unique constraint, perform the debit, and store the response in one transaction. A concurrent duplicate waits for that claim to resolve. If it commits, the duplicate replays the response; if it rolls back, another request can claim the key. An external card charge needs another boundary. I first persist the pending operation, send a stable key to a provider that deduplicates, and then record its result. If I crash after the charge, recovery queries or retries that same provider operation. I do not delete the key because of a timeout. Finally, I define the retention horizon across clients, queues and provider recovery. After deduplication expires, a blind retry can charge again, so permanent payment identity or reconciliation may still be necessary. An in-memory future map only demonstrates concurrency within one process.

Likely follow up: What if the payment provider has forgotten the key before your recovery job runs?

Out loudabout 90 s
"We already use Kafka transactions. Why do you still want an outbox and idempotency keys?"
What a strong answer covers
  • Kafka transactions atomically commit Kafka output records and input progress within their boundary
  • Processing may run again even when only one committed output becomes visible
  • Database commits and external charges are outside that Kafka transaction
  • An outbox commits the business change and publication intent locally, then relays with possible duplicates
  • Consumers deduplicate event ids with their database effects; external providers enforce their own keys
  • Ordering and retention are separate requirements, not automatic consequences of deduplication
How a senior would say it
Kafka transactions protect Kafka input progress and Kafka output records; they do not automatically include our database or payment provider. A processor may run a batch again after a crash, while only one committed output is visible to consumers reading committed records. Suppose that processor charges a card and then aborts its Kafka transaction. The charge is still real, and replaying the batch can charge again. That call needs a stable payment key enforced by the provider. For a database update followed by event publication, I use an outbox because two independent commits leave a crash window. The business change and an event row commit together in the database. A relay publishes the event and records acknowledgement. If it crashes after publishing, it can publish again, so the consumer records the event id in the same transaction as its own database effect. If the consumer sends email, that is another external boundary with its own delivery contract. I would also explain ordering separately: partitioning by order id preserves publication order, but does not repair two relays publishing business events backwards. Finally, the guarantee lasts only through the retention and recovery assumptions we actually enforce. The useful claim is one observable effect within a named boundary, not processing code that can never execute twice.

Likely follow up: What happens if the relay publishes event 42 before an earlier transaction containing event 41 commits?

The practice problem drills the in-process claim and waiter mechanism. Its read-only cache loader may be retried after failure; a payment with an uncertain effect must retain its identity and reconcile first.
