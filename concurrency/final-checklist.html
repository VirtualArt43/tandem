The final checklist

Review the essential guarantees, spot concurrency bugs, and check failure, shutdown and tests before calling a solution complete.

Before this:How to run a concurrency coding roundSaying it like a senior

This is the last page before the room. It does not teach anything new. It makes sure that what you already know is loaded, that you can spot the dozen bugs interviewers plant, and that you never say "done" one check too early.

In plain words

Before a long drive you check four things: fuel, tyres, lights, and the route. You know how to drive; the checklist is there because the one thing you skip is the one that strands you. The night before an interview is the same: environment, templates, the must-know list, a story. And at the end of every solution, one more short checklist, run aloud, before the word "done".

The night before

  • Environment. Know the interview tool (CoderPad, HackerRank, a shared IDE). Know how to set Java 21 or a C++ standard there, how to run, and where output appears. If it is your own machine, have a project that compiles a threaded main in one click.
  • Type the templates once from memory, without looking: the monitor with a closed flag, a bounded blocking queue, a worker pool with shutdown, a stress test with a start gate and timed joins (and a watchdog in C++). If one does not come out cleanly, that is tonight's revision.
  • Read three pages: your language's Java or C++ cheat sheet, the phrasing bank, and the entry for this company in company playbooks.
  • Prepare one concurrency war story: the symptom (a hang, wrong totals, latency spikes), how you found it (a thread dump, a sanitizer, a metric), the cause, the fix, and what you changed to detect or prevent a recurrence. Senior loops also probe project depth; one Rubrik senior candidate was rejected by the hiring manager on project depth after good technical feedback.
  • Know the format: is code expected to run? Are libraries banned? Is there a debugging round? Ask the recruiter if you do not know.
  • Sleep. A missed predicate or exception path can break the whole solution, so leave time to rest.

Worked example: close must reach current and future waiters

A stop flag and a notification solve different problems. The flag remembers that close happened; the notification makes existing waiters recheck it. This small Java 21 and C++20 program exercises both: two workers are waiting when close occurs, then a third call arrives after close.

The waiting counter is test instrumentation under the same lock. Once the main thread observes two, both workers have reached their condition wait and released that lock. No sleep guesses when they are ready. The final read of completed follows both joins and the late call, so no worker is still mutating it; the runner imposes a timeout if a regression hangs.

Before you say "done"

Run this aloud on every solution. It takes two minutes and it is where interviewers see seniority.

  1. State: I can name every piece of shared mutable state and the lock or atomic that guards it.
  2. Invariant: it holds every time the lock is released, including on exception paths.
  3. Atomicity: every check-then-act and read-modify-write sits inside one lock hold or one atomic operation.
  4. Waits: every wait is in a loop on the real condition, and timed waits use one monotonic timeout budget rather than restarting it after each wakeup. This rule concerns condition waits, not one-shot latch or future waits.
  5. Wakeups: every state change that can release a waiter signals it; close wakes everyone.
  6. Locks: slow or unknown work stays outside the state lock; if the contract requires otherwise, I can justify it. Multiple locks follow one order or one compatible deadlock-avoidance protocol.
  7. Failure: exceptions unlock, leave state consistent, and reach a caller or a log; workers survive bad tasks.
  8. Cancellation and shutdown: the contract distinguishes drain from cancellation; new submissions are rejected, relevant waiters are woken, and running tasks cooperate with cancellation. Termination is checked separately.
  9. Bounds: work and resource bounds are explicit, with an overload policy; waits do not spin without a measured reason.
  10. Visibility: publication, guarded reads and object lifetime are justified; independent relaxed atomics do not publish unrelated state.
  11. Tests: single-threaded sanity, a stress run with a start gate and exact invariants, timed joins, edge cases (capacity 1, zero timeout, close while blocked), and ThreadSanitizer for C++.
  12. Cost: I can state the complexity, where contention will appear first, and the next step if it does.

Common mistakes

  • Reciting an API instead of its guarantee. An atomic increment cannot make a separate capacity check atomic; say which whole operation must be indivisible.
  • Equating a stop request with termination. Wake waiters, request cooperative cancellation, then join or await termination. A C++ stop token alone does not wake an ordinary condition variable.
  • Claiming tests prove every schedule. Explain the invariant and synchronization first; tests and ThreadSanitizer find counterexamples, not a universal proof.
  • Optimizing before fixing the contract. Striped LRU, weak snapshots and dropping work under overload change observable behavior. Agree on that behavior before changing the implementation.

In the interview

The research behind this course repeatedly shows rounds lost after the main problem was solved: a Rubrik new grad whose deadlock fix did not compile, a Rubrik screen judged on exactly which exceptions the pool caught and on shutdown semantics, LinkedIn interviewers who asked for a concrete race behind every lock, and a Google L5 candidate who received No Hire after a thread-safety follow up and attributed it to insufficient reasoning. These are reported outcomes, not proof of a single rejection cause. The checklist above is how you collect those last points.

Before I call it done, let me run my checklist: the state is the deque and the closed flag under one lock; the invariant holds on every unlock including the exception path; waits are loops; close wakes everyone; nothing slow happens under the lock; and the stress test passed with eight threads behind a start gate.

Senior depth

Separate safety, progress and lifetime. For a draining queue, safety includes never exceeding capacity and never losing accepted items. Progress requires workers to be scheduled and tasks to finish; a mutex does not promise fairness. Lifetime requires every caller to stop using the queue before its mutex, conditions or storage are destroyed.

Pin down races at the boundary. If close wins the lock before a put, that put fails; if insertion wins, draining close must preserve the accepted item. A timeout should consume one monotonic budget, using System.nanoTime() elapsed-time differences in Java or std::chrono::steady_clock in C++. After reacquiring the lock, check the predicate and the agreed timeout rule; a wakeup alone is not success.

Test the claim you make. Use barriers or latches to arrange a vulnerable schedule and check the allowed result. A stress test can miss a race, and ThreadSanitizer does not prove FIFO, linearizability, fairness or deadlock freedom. Java timed joins and an external C++ watchdog bound a failing test; neither repairs the implementation.

Key takeaways

  • The night before: environment, templates typed from memory, three pages, one war story, the format, sleep.
  • Know the must-know table cold; each line is a lesson you can open.
  • Scan any code for the red flags: if around waits, unguarded reads, check-then-act, locks across I/O, missing wakeups, swallowed interrupts.
  • Never say "done" before the twelve checks, said aloud.

Debug
Review this deliberately broken session cache, used by concurrent callers and an evictor. List the red flags and fixes.
Model answer
  1. Unguarded read of the map. get reads the plain map without the lock while other threads write it: a data race (undefined behavior in C++, corruption risk in Java). Read and copy the value under the same lock, or use ConcurrentHashMap in Java. A C++ shared lock is an alternative only if every writer uses the matching exclusive lock on the same shared mutex.
  2. Check-then-act on a miss. Two threads can both miss and both load and put the same key; the later put overwrites. For a cheap load, Java ConcurrentHashMap.computeIfAbsent makes installation atomic. For slow I/O, install a per-key future under a short lock, load outside the lock, and complete or fail all waiters; a lock only around insertion still permits duplicate loads. Decide whether a load started before eviction may repopulate the cache; use a generation check if it must not.
  3. A lost-update counter. hits++ on a volatile int and hits_ += 1 on a plain int lose increments (and the C++ one is a data race). Use AtomicLong or LongAdder, or std::atomic<long> with fetch_add.
  4. Sleeping while holding the lock. C++ sleeps for a minute under its lock on each iteration; Java retains its monitor for the entire loop. Both block inserts. Clear under a short lock, then use an interruptible or signalled timed wait that releases the lock. Simply moving an uninterruptible sleep outside the lock still delays shutdown.
  5. An invisible stop flag. stopped is written without the lock and is not volatile (Java), and stopped_ is a plain bool (C++), so Java may miss the update and C++ has undefined behavior. For prompt shutdown, guard the stop predicate with the wait mutex, use a timed condition wait that releases it, and notify all in stop(). An atomic flag alone does not wake a sleeper or close the condition-variable check-to-wait gap.
  6. Manual lock and unlock in C++. An exception between them leaves the mutex locked forever. Use std::lock_guard or std::scoped_lock.
  7. A detached thread capturing this. If the cache is destroyed, the evictor uses freed memory. Own the thread; signal stop, wake it and join before any captured state is destroyed. A C++20 std::jthread requests stop and joins on destruction, but an ordinary std::condition_variable does not wake automatically for its stop token. C++17 needs an explicit stop flag, wakeup and join.
  8. evictForever holds the cache lock for its whole life. Java keeps the same monitor for every iteration, not just one minute. Its InterruptedException already propagates correctly; the caller must own and join the evictor thread. Restrict the lock to each clear and use a stoppable wait between clears. Prevent accidental multiple evictors, or explicitly support and join every one.
Explain
Run the "before you say done" checklist aloud on a bounded blocking queue built with one lock and two conditions that you have just written, as you would at the end of a round.
Model answer

The shared state is the deque, its size and the closed flag, all guarded by one lock, and the invariant is that size stays between zero and capacity and closed never goes back to false. Every operation that checks and changes the deque does it inside one lock hold, so there is no check-then-act gap. Enqueue and dequeue linearize at their mutations; close linearizes when it sets the flag. Producers wait in a while loop for not full or closed, consumers for not empty or closed; the timed versions compute one deadline and feed the remaining time back in.

After an enqueue I signal not empty, after a dequeue not full, and close sets the flag under the lock and signals all on both conditions. This is a draining close: puts fail after close, queued values remain consumable, and a closed empty queue returns a distinct end-of-stream result.

Nothing slow happens under the lock: no I/O, no callbacks, no sleeps. Java unlocks in finally; C++ uses RAII. I must verify the chosen container and element operations give the required exception guarantee: one method call alone proves nothing. For integer items, remove only after obtaining the value, and signal after a successful mutation. Java interrupts propagate from await; C++ cancellation needs the explicit flag and wakeup protocol.

The queue is bounded by construction. Visibility is covered because every read and write of the state happens under the lock. I would test FIFO and size single-threaded, then four producers and four consumers behind a start gate checking every item arrives exactly once and capacity is respected, with timed joins or a C++ watchdog. FIFO checks must use dequeue order, not the order consumers later log their results. Edge tests cover capacity one, a zero timeout, close before waiting and close while blocked.

Queue-end operations are constant time for a fixed ring, or use the chosen container's documented bound, excluding waiting and allocation costs. Under contention I would measure first. Separate head and tail locks require a new proof for size, close, visibility and notifications; splitting the existing lock mechanically is unsafe.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Your queue passes the producer and consumer test. Walk me through what you check before calling it done."
What a strong answer covers
  • Name the queue and closed flag, their common lock, and the capacity invariant
  • Identify enqueue, dequeue and close linearization points, including a put racing close
  • Explain predicate rechecks and notification of both wait sets on close
  • Distinguish draining from cancellation, and verify exception paths and object lifetime
  • Describe targeted lifecycle tests, bounded duration and the limits of a clean sanitizer run
How a senior would say it
I would check the contract and shutdown paths before calling it done. The deque and closed flag share one lock, and the size must stay between zero and capacity whenever that lock is released. Enqueue and dequeue take effect when they mutate the deque. Close takes effect when it sets the flag. If a put wins that race, draining close preserves its item; if close wins, the put fails. Producers wait for space or closure, and consumers wait for data or closure. Every wakeup rechecks the predicate, and close wakes both groups. A closed queue drains its remaining items, then reports end of stream. I would check that exceptions preserve the invariant and release the lock, and that timed waits use one monotonic budget. Cancellation is a separate contract, not a promise that running code stops immediately. I would test close before waiting, close while producers or consumers are blocked, capacity one, interruption where supported, and repeated close. I would bound the tests so a hang becomes a failure, and run C++ under ThreadSanitizer. Passing tests supports the implementation, but I still owe the invariant and ordering argument. Finally, I would join the workers before destroying their shared state.

Likely follow up: What changes if close must discard queued items instead of draining them?

How a senior would say it
I would first check whether the worker is blocked rather than reading the flag. Making a flag atomic does not wake a condition wait, an I/O call or a future wait. I would inspect the stacks and identify the exact predicate and wait set. For a condition variable, the closer must change the predicate under the same mutex used by the waiter. Otherwise the closer can set the flag and notify after the worker checks it but before the worker starts waiting. That notification is not saved. I would update the predicate under the mutex and wake every affected wait set. The worker then rechecks the predicate after reacquiring the lock. In Java, interruption can end interruptible waits, but it must be handled correctly. In C++, requesting stop does not automatically wake an ordinary condition variable. Finally, I would join outside any lock the worker needs and ensure the object outlives its threads. Tests should force both close-before-wait and close-while-waiting, with a timeout to catch regressions.

Likely follow up: What if the worker is blocked in I/O that does not respond to your cancellation mechanism?
