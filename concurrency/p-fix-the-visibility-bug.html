Fix the visibility bug

Bug huntsmedium25 min

The bug that passes every test on your laptop and hangs a production shutdown. Interviewers use it to see whether you can list every piece of shared state, say which thread writes it and which reads it, and name the exact edge that makes a write visible.

The task

The incident

Your storage nodes run a background scrubber: one thread that walks the stored blocks over and over, recomputing a checksum for each, so that bit rot is noticed early. A dashboard thread calls scrubbed() once a second to draw a progress graph. When a node shuts down, it calls stop().

The on-call notes from the last two weeks:

  • Node shutdown sometimes hangs forever inside stop(). The thread dump shows the scrubber thread still running at full speed on one core, and the shutdown thread waiting for it.
  • It only happens on nodes that have been up for a while. Starting a scrubber and stopping it straight away has never failed, not in tests and not under the debugger.
  • The C++ build's ThreadSanitizer job fails with reports that point into ScrubWorker.
  • Nobody has touched ScrubWorker in a year. The release that started the trouble upgraded the JDK and the C++ compiler, and turned on a higher optimization level.

Your job: find every concurrency bug in ScrubWorker and fix it with the smallest correct change. Keep the public API exactly as it is. The full class is in the editor.

The contract

  • blocks is nonempty. Java receives a non-null array whose elements the caller never changes after construction. All 32-bit bit patterns are valid, including negative Java integers. Each worker owns independent state.
  • The lifecycle is one start() followed by one stop(), with start() returning before stop() is called. The caller safely publishes the worker if another thread calls stop(). Restart, duplicate starts, concurrent stops and stopping before starting are outside this task.
  • The worker repeatedly visits indices 0, 1, ..., blocks.length - 1, then starts again at index 0. It continues until asked to stop, without a fixed pass count or automatic timeout. For each block, start sum at 17 and apply sum = sum * 31 + logicalRightShift(block, k * 4) for k from 0 to 7. Arithmetic wraps modulo 2 to the power 32. Keep the starter's checksum algorithm and visit order.
  • scrubbed() starts at zero and counts completed blocks across all passes. Any dashboard thread may read it while the worker runs. Reads must be safe, must not go backwards and must expose continued progress; do not reset the count at the end of a pass. Tests do not approach integer overflow.
  • stop() requests termination, allows an already selected block to finish, and waits for the worker to exit. A successful return makes the final count and checksum visible to its caller. They never change afterwards. An immediate stop may complete zero blocks, in which case the final count and checksum are both zero.
  • lastChecksum() is read only after successful stop(). For a positive final count n, it is the checksum of block (n - 1) % blocks.length. It is not a live dashboard API. In Java, an interrupted join may propagate InterruptedException; a stop whose caller was not interrupted must return normally. The harness does not interrupt its stop callers.

Rules: no sleeps, no debug prints and no extra threads in your implementation. Preserve the single background worker. A print inside the loop can change the symptoms, but it supplies no synchronization contract for these fields. Atomics, volatile fields in Java, or a correctly shared lock are valid fixes.

Example: with blocks [5, 9], a final count of 3 means the completed blocks were 5, 9, 5, so the final checksum must be the checksum of 5. Stopping that worker must leave a second worker free to keep scrubbing its own blocks.

What the tests check

  • A hot dashboard begins polling before the worker starts, then observes four 100 ms windows of continuous progress without a decreasing count. The reader warm up is 150 ms in Java and 50 ms in C++. These are observation windows, not a guarantee that a particular JIT optimization occurs.
  • Warm shutdown returns normally, publishes the exact count and checksum, and leaves both stable. Helper exceptions are failures, including an unexpected InterruptedException.
  • Four workers use different block lists, including a singleton, high-bit values and non-power-of-two lengths. They start in a fixed mixed order and stop one at a time. Remaining workers must still progress and stopped workers must stay unchanged. New instances start at zero.
  • Java exercises 96 fresh lifetimes and C++ exercises 48, mixing immediate stops with stops after observed work. The stop caller reads the final state immediately and repeatedly, checking cyclic order, logical shifts and the absence of work after stop.
  • Timed helper waits and a global watchdog bound broken implementations. The watchdog fires after 3.2 s in Java or 5.2 s in C++; a stuck candidate prints a failure and exits. These limits are harness budgets, not language memory-model latency guarantees.
  • C++ runs under ThreadSanitizer, which must report no races on exercised accesses. Hot reads and repeated stops make Java visibility bugs easier to observe, but passing tests cannot prove race freedom or correct joining. You must still explain the synchronization for every shared field.

Taught in: Visibility: why a thread may never see your write

Open them one at a time. Each one gives away a little more.

List every field of ScrubWorker. For each one, write down which threads write it, which threads read it, and when. A field used by one thread only, or read only after something that orders it after the writes, is fine. Every other field needs a reason to be safe.
What makes a write in one thread visible to a read in another? A lock released and then acquired, a volatile (atomic) write then read, starting a thread, joining a thread. For each shared field, find which of these connects the writer to the reader. Look hard at the two threads that run while the scrubber is working.
The hang appears only after the loop has run for a while. What happens to a hot loop after many thousands of iterations in Java, or at a higher optimization level in C++? What is the compiler allowed to assume about a variable that nothing inside the loop writes?

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why does lastChecksum need no fix?
It is only read after a successful stop(), and stop() joins the scrubber thread. Everything a thread does happens-before another thread's successful return from join() on it, so every write to lastChecksum is visible to the caller. If someone later shows it on the dashboard while the scrubber runs, it becomes shared live state and needs volatile (an atomic) like scrubbed.
Would a lock work instead of volatile or an atomic?
Yes, if both sides take the same lock: stop() writes the flag under it and the loop reads the flag under it (a synchronized isRunning()). Unlock then lock of the same monitor or mutex is a happens-before edge. It costs a lock on every pass of a hot loop, and it adds nothing here because each field is a single independent variable. Use a lock when state must change together. Release that lock before joining, or the worker may be unable to reacquire it to finish.
Is scrubbed += 1 on a volatile long safe? It is a read, modify, write.
Here, yes, because only the scrubber thread writes it: with one writer no update can be lost, volatile makes each new value visible, and it makes the 64-bit read and write atomic (the Java specification allows a plain long access to be split into two halves). With two writers it would lose updates; then use AtomicLong or LongAdder, or fetch_add in C++.
Which memory order would you use for the C++ atomics?
The default seq_cst is correct and cheap enough here. The counter is a statistic, so fetch_add(1, std::memory_order_relaxed) with a relaxed load is enough: atomicity without ordering. The flag carries no data with it, and join() orders everything afterwards, so even relaxed would work; release on the store and acquire on the load is the habit to show when a flag publishes data written before it. Say you would keep the default unless profiling showed a cost.
How else could you stop the thread?
In Java, thread.interrupt() with while (!Thread.currentThread().isInterrupted()): the interrupt status is safely published, and it also interrupts sleep, wait, join and supported interruptible I/O operations. It does not unblock every I/O API. In C++20, std::jthread hands the function a std::stop_token; request_stop() is thread-safe, stop_requested() safely queries shared stop state, and the destructor requests a stop and joins if the thread is joinable. Cancellation still requires the worker to cooperate.
Why does it work on my laptop, or after I add a print?
Interpreter execution, optimization choices, logging and scheduling can all change whether a race becomes visible. A hot JIT may reuse a plain flag read, but it is not required to do so. Logging may inhibit an optimization without synchronizing with the writer of that flag. Neither an unoptimized C++ build nor a particular JVM run is a correctness guarantee; reason from the memory model.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

Bug 1: the stop flag is a plain field

running is written by the thread that calls stop() and read by the scrubber on every pass, with no lock, no volatile and no atomic. Nothing in the loop writes it, so the optimizer may read it once, before the loop, and test that copy forever. That is hoisting. A JIT may perform this transformation after warm up, and an optimizing C++ compiler may exploit the absence of defined concurrent access. No particular compiler version, optimization level or warm up duration guarantees this exact transformation. In C++ the unsynchronized write and read are a data race, which is undefined behavior, and ThreadSanitizer can detect exercised conflicting accesses.

Bug 2: the dashboard reads a plain counter

scrubbed is written by the scrubber and read by the dashboard while the scrubber runs. That is the same mistake from the reader's side. The dashboard may see stale values, and Java permits a plain long access to be split into two halves, allowing a torn value (JLS 17.7), although this is not normally observed on this 64-bit JVM. In C++ it is a second data race. The compiler may also keep the counter in a register inside the loop and store it rarely, or never.

Java's hot-reader test can expose stale-counter behavior on some runs, but no finite set of successful runs proves the counter safe. A candidate who fixes only the flag has fixed the symptom, not the class. The field-by-field argument is part of the answer.

The fix

In C++, add <atomic> and change the two declarations. The existing expressions running_ = true, while (running_), scrubbed_ += 1 and return scrubbed_ are all atomic operations on a std::atomic. Java volatile accesses and C++ atomic accesses must obey their respective memory models, so the plain-field reasoning that permits a stale cached loop is no longer valid. Java volatile writes synchronize with subsequent reads of that field. Neither language promises a fixed wall-clock response time: shutdown also depends on scheduling and completion of the current block.

Why not more? No lock is needed: the counter has one writer, lifecycle calls order the flag writes, and no compound state transition is required. Making lastChecksum volatile too would be harmless, but saying why it is already safe (the join() edge) is the stronger answer.

Cost and proof

Each block takes constant work, and each accessor is constant time. The reference adds constant synchronization state; the stored input occupies space proportional to its length. Shutdown waits for the current block and thread termination, so it has no fixed elapsed-time guarantee. Java's constructor retains the caller's array; the input-immutability precondition matters.

The visibility rules are specified in JLS chapter 17, including volatile, join, and plain long accesses. The Java 21 Thread API specifies interruption behavior. C++ atomics and progress are governed by the C++ forward progress rules; scheduling deadlines are separate test assumptions.

How to say it in the interview

The flag is a plain field written by the shutdown thread and read in a hot loop, so there is no happens-before edge. After the JIT compiles the loop it can read the flag once and spin forever, which can explain failures that appear only after warm up. I make it volatile, or an atomic in C++. The dashboard counter has the same problem from the reader's side: one writer, so volatile is enough and I do not need a CAS. The last checksum is only read after join, and join is a happens-before edge, so it can stay as it is.
