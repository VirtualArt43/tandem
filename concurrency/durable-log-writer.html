A concurrent, ordered, durable log writer

Build an ordered log with group commit, durable acknowledgements, bounded admission, flush barriers, graceful close and explicit storage failure handling.

Asked atDatabricks
Before this:Files, offsets, buffers, flush and fsyncProducer and consumer with a bounded bufferFutures and promises

This is the question to master for Databricks. Reported at L4, at senior level and in interviewing.io's description of the round: many threads append events to one file, the output must stay in order, an append is acknowledged only once it is durable, and nothing may be lost on shutdown. The interviewer walks you from a slow correct version to a fast correct one.

In plain words

Picture a railway parcel office. Many people hand parcels across the counter, and each gets a token. One clerk loads the parcels into the van in the order they were received. The van leaves when the clerk is ready, carrying everything on the shelf, and only when it has actually left does the clerk stamp every token in that load "dispatched". If the shelf is full, people at the counter wait. At closing time the clerk sends whatever is on the shelf before locking up.

That is the whole design: a counter that only queues, a single clerk who batches, and a stamp that comes after the van has really left. Ordering comes from the queue, speed comes from batching, honesty comes from stamping late, and the full shelf is your back-pressure.

The question, made precise

The reports describe the same component with slightly different surfaces: a thread-safe EventWriter whose appendEvent returns only once the data is durable (L4, written in full C++ with std::promise and std::future); a log(level, msg) that must not block producers for long, batches, flushes in submission order, loses nothing on shutdown and offers flush() and close() (senior, 2026); a log writing system that starts with synchronous writes and scales to multi-threaded ordered writes (senior, 2026). Pin down this contract first:

  • append(event) may be called by many threads. It returns a future that completes successfully with the event's sequence number only after the event is durable, or fails when durability cannot be confirmed. Failure does not prove the event is absent from disk.
  • Events appear in the file in the order their append calls took effect. Two concurrent appends may go in either order; one thread's appends stay in its own order.
  • Throughput far above one event per fsync, which forces batching: group commit.
  • Back-pressure: at most maxQueued events in the shared queue; when full, append blocks (or rejects, if that is the agreed policy). The in-flight batch and buffers retained by blocked callers are additional memory.
  • flush() captures the accepted sequence frontier under the queue lock and waits for that prefix to become durable. close() stops admission, drains accepted work, resolves every future, joins the writer and releases the file; storage failures must also be reported by close.

For the synchronous interview API, the caller waits on append(event).get() before returning success. The asynchronous API returns a receipt immediately after admission, not a durability acknowledgement. Overlapping appends can be ordered either way, including a producer waiting for capacity when flush snapshots its target.

The path the interview takes

The L4 report lays out the walk explicitly. Do it in this order and say why each step exists.

Version 0: one lock, write and fsync per event

On the success path it is ordered by the lock and durable before returning. These fragments assume the file is already durably published and the owner retires the log on any I/O error; the full version below implements that failure policy. But every append holds the lock across a disk sync, so all producers queue behind the disk one at a time, and throughput is at most one event per fsync time, around a thousand a second on a 1 ms sync. Say this version first in the interview; it shows you know what correct means before you optimize.

Version 1: producers enqueue, one writer thread writes

Split the work: append only puts the event on a queue and returns a future; a single writer thread takes events off the queue, writes and syncs. This is producer-consumer, and a single writer gives ordering for free: the queue's order is the file's order, and the moment an event enters the queue under the lock is its place in the log. Producers normally wait only for queue admission; lock contention or a full queue can still block them. But if the writer still syncs per event, durable throughput has not moved.

Version 2: the writer drains everything waiting into one batch

The writer takes all queued events at once, concatenates them, uses a complete-write loop and one sync, and only then completes every receipt in the batch successfully. This is group commit with natural batching: no timer, no fixed batch size. While one sync is in flight, new events pile up, and the next sync covers them all.

Version 3: futures, back-pressure, flush, close and failure

The full component adds the parts interviewers push on next. A bounded queue turns a slow disk into back-pressure. flush waits on a "durable up to" counter. close is drain, sync, complete, join. A failed write or sync fails the whole batch and everything behind it, because after an I/O error the file is suspect. Here it is, with a demo of four producers appending 500 events each.

The demo owns one local file exclusively, accepts single-line events up to 64 KiB including the newline, and requires enough memory for its configured queue and batch. It does not implement restart recovery: an existing file must already have a validated complete prefix, and sequence numbers restart at zero for this instance. Opening also syncs the file and its existing parent directory before admitting events; Java directory forcing requires a supporting local provider, as discussed in file I/O and durability.

The output is illustrative: the number of syncs depends on scheduling. Two thousand events can use about 33 batch syncs, excluding startup publication syncs. With a queue bound of 64 and producers far faster than the disk, the queue fills, producers wait, and many syncs carry about 64 events. Raising the bound permits larger batches; gains stop when per-event work or device bandwidth dominates. The C++ producer demo uses C++20 std::jthread; C++17 needs std::thread plus an RAII join guard.

Walking through the synchronization

"Walk me through the synchronization" is a reported follow up. Answer it in this order:

  • What the lock guards: the queue, the next sequence number, the durable count, the closed flag and the failure. Not the file: after initialization, only the writer performs writes and syncs, and close releases the file only after joining it (it is confined to one thread).
  • The ordering guarantee: an event's sequence number is assigned and the event enqueued in one critical section, so sequence order, queue order and file order are the same. That moment linearizes admission and fixes the event's order. Durable completion is a later boundary, after sync, so enqueueing alone cannot linearize a synchronous durability acknowledgement.
  • When a receipt completes successfully: only after force or syncToDisk succeeded for the batch that contains it, and only outside the lock. That is the durability guarantee.
  • Who waits for what: producers wait on "not full" (back-pressure), the writer on "not empty or closed", flush on "durable has reached my target or the log failed". Each condition has its own condition variable, and every state change that could satisfy one signals it under or right after the lock.
  • Why the slow part is outside the lock: while the writer writes and syncs, producers keep enqueuing the next batch. That overlap is where group commit gets its speed.
  • Why futures complete outside the lock: completing a CompletableFuture may run non-async dependent callbacks on the completing thread, and set_value wakes waiting threads. Running other people's code while holding your lock invites deadlock and stalls producers; it is the open call rule.

The frontier invariant is 0 <= durable <= nextSeq. All sequence numbers below durable form a successfully synced prefix. The writer advances this count only after writing a whole batch and syncing it. flush snapshots nextSeq once under the same lock, so later producers cannot move its target; queue emptiness alone says nothing about the batch already in flight. Flush guarantees persistence of its prefix, not that every receipt callback has finished.

Outside the lock does not mean outside the writer thread. A Java callback that waits for a later receipt can still deadlock the only writer. The demo rejects calls to append, flush or close made directly by writer callbacks, but callers must also avoid waiting for other receipts there. Use async continuations with a separate executor that actually dispatches work. Returning done.copy() prevents caller cancellation or manual completion from changing the writer's internal receipt; cancellation does not remove an accepted event. The returned copy remains caller-mutable, so a caller that manually completes it has no durability evidence. A read-only API can instead expose minimalCompletionStage() and keep the writable future private.

Close, failure and recovery

Close must lose nothing that was accepted: set closed under the lock, wake the writer and any producers blocked by back-pressure (they fail with "closed"), let the writer drain, write, sync and complete what is left, join it, then close the file. Both versions support repeated and concurrent close calls. Java finishes joining even if the closing caller is interrupted and restores that caller's interrupt flag; it never interrupts file I/O to request shutdown. C++ uses std::call_once for joining and descriptor release. Explicit close reports storage failure, while the C++ destructor drains and suppresses exceptions; the object must outlive every concurrent caller.

A failed write or sync fails every event in the batch, everything still queued, and every later append. Blindly retrying a storage error and declaring success is unsafe, because the kernel may already have dropped the data (see the fsync failure story). A failed future means uncertain durability, not guaranteed absence. A crash after sync but before the caller receives success has the same ambiguity: use durable request IDs and deduplication before retrying, as in idempotency and retries.

A timeout stops waiting, not writing. Interrupting Java admission before enqueueing accepts nothing; timing out on a receipt after admission does not retract the event. C++ future.wait_for likewise reports readiness without cancelling the append. A retry needs the same request ID because the original event may still become durable. A timeout on close cannot both return within a deadline and guarantee draining if storage is stuck; state which guarantee the API offers.

A crash can leave the last record half written: a torn write. Real logs frame every record with its length and a checksum, validate lengths against configured limits, verify checksums and sequence continuity, and truncate an incomplete tail before accepting new appends. Sync that repair. Corruption inside an acknowledged prefix requires repair or fail-stop handling, not silently discarding acknowledged records; checksums detect corruption but do not fix it. Mention it even if you do not code it.

Worked example: sizing the writer

Suppose fsync takes 1 ms, 16 producer threads together offer 40,000 events per second, each event is 200 bytes, and the queue bound is 4,096 events.

  • Per-event sync (version 0 or 1): at most about 1,000 events per second. Version 0 blocks at its lock; version 1's queue fills in about 4,096 / (40,000 - 1,000), or 0.105 seconds, under this offered load.
  • Group commit: during each 1 ms sync about 40 events arrive. Say copying and writing costs 2 microseconds per event; then a batch of b events takes 1 + 0.002b ms, and batches grow until they carry everything that arrives meanwhile: b = 40 times (1 + 0.002b), so b is about 43 events (under 9 KB) per 1.09 ms. The writer keeps up with the 40,000 per second offered, the queue stays short, and it could absorb several times more load simply by letting batches grow.
  • Latency: an event waits for the sync in flight when it arrived and then its own, so roughly 1 to 2.5 ms in this smooth-load model, excluding admission delays, scheduling stalls and device-tail latency.
  • The bound: 4,096 events of 200 bytes is 819,200 bytes of queued payload, about 800 KiB. The in-flight batch can hold another full queue, and concatenation adds a copy: up to about 2.34 MiB of payload here, before futures, containers and producer-owned buffers. A count bound alone is not a byte bound without a maximum event size. If the disk stalls for a second, the queue fills in about 0.1 s and producers block: back-pressure doing its job instead of an out-of-memory crash.

Saying these four numbers out loud is the senior version of "it is fast".

Common mistakes

  • Completing the future before the sync. The event is acknowledged while it is still only in the page cache. A fake disk with a gated sync can catch this deterministically, without cutting power.
  • Syncing inside the queue's lock. Producers then wait for the disk, and admission stalls for the whole disk operation, even though batching can still amortize sync cost.
  • Several writer threads. Two writers can finish their writes in either order, so file order no longer matches append order. One writer, or one writer per partition with ordering per partition only.
  • An unbounded queue. A slow disk turns into unbounded memory growth and eventually a crash that loses everything queued. Bound it and pick a policy.
  • Close that drops the queue. A writer that exits on "closed" without draining loses accepted events and leaves their futures hanging forever.
  • Swallowing a sync failure. Log it and carry on, and the next sync "succeeds" for data that was never written.
  • A sleep as the batching timer. a fixed 5 ms sleep before every write adds delay to every batch even when the system is idle. Natural batching needs no timer; if you want a linger, wait on the condition with a deadline so a full batch leaves at once.

In the interview

Expect the conversation to follow the L4 path: "write events to a file from many threads", then "each call must return only when the data is durable", then "that is too slow", then "now make it fast", then follow ups on back-pressure, shutdown and testing. A 2026 senior candidate started with a lock-protected queue drained by one background writer, which is the right first move.

Producers only enqueue: under one lock each event gets the next sequence number and goes on a bounded queue, and the caller gets a future. A single writer thread owns the file. It takes everything queued as one batch, writes all its bytes with a short-write loop and syncs once, outside the lock, and only after the sync returns does it complete the futures of that batch. One writer means file order equals sequence order; one sync per batch means throughput grows with load instead of being capped at one event per fsync; and the bounded queue means a slow disk pushes back on producers instead of eating memory.

Follow ups and short answers: "producers must never block" (reject when full and use a try-lock to reject contention too; never drop silently for a durable log); "how do you test it?" (a fake disk whose sync is slow and counts calls, many producers, then check order, that no future completed before the sync that covered it, far fewer syncs than events, close completing everything, and an injected sync failure); "what about latency at low load?" (natural batching gives one-event batches and minimal delay; a linger trades additional low-load latency for sharing fixed sync and batch costs; measure whether that trade helps).

Senior depth: other shapes of the same idea

  • Leader-based group commit, no writer thread. The first producer to find no sync in progress becomes the leader: it takes the whole queue, writes and syncs, then wakes the followers whose events it covered, who wait on "durable has passed my sequence number". This saves a thread hand-off per event and is the shape databases use for their log flush.
  • Double buffering. Producers append into buffer A while the writer writes buffer B; when the writer finishes, the two swap under the lock. Same idea as the queue, with fewer allocations.
  • Lock-free reservation. Producers reserve space in a shared buffer with an atomic fetch-and-add, copy their bytes, and mark their slot ready; the writer flushes the longest ready prefix. It may reduce lock contention, but release publication of each ready slot and acquire reads by the writer are essential. A bounded ring also needs wraparound generations and safe reuse; a slow producer leaves a hole that holds back everyone after it. Only reach for it if asked.
  • Rotation. The writer alone switches segments at a sequence boundary. Sync the old segment before completing its final receipts, then create and sync the next segment and its directory before acknowledging events stored there. If recovery discovers segments through a manifest, durably replace that manifest before those acknowledgements too. Keep the old segment until the retention or checkpoint protocol permits deletion; sync the directory if the deletion must survive a crash. Renaming alone does not redirect an already open descriptor.
  • Partitioned logs. Global order across all producers is expensive. If the product only needs order per key or per stream, give each partition an independent ordered log and write pipeline, and scale out. This relaxes the guarantee to order within a partition.
  • Bytes, not counts. Bound the queue by bytes when event sizes vary, and cap batch bytes below allocation and API limits, including Java's int-sized ByteBuffer. Reserve admission budget before copying large payloads; blocked producers retain their input buffers outside the queue bound. A batch cap limits how much work one batch adds ahead of later arrivals.

API reference: Java 21 CompletableFuture completion and execution policies. See the preceding lesson for the OS durability contract.

Key takeaways

  • Producers only enqueue under a lock; a single writer thread owns the file, so queue order is file order.
  • The writer drains everything waiting, uses a complete-write loop and one sync, and completes those futures only after the sync: group commit with natural batching.
  • A bounded queue gives back-pressure; flush waits on a durable-up-to counter; close drains, syncs, completes and joins.
  • A failed write or sync fails the batch, the queue and every later append; never retry the sync and pretend.
  • Do the slow sync and the future completions outside the lock.

Quick check

Answer each question, then read why. Your score is saved for your module test.

In version 0, append takes one lock, writes a small event and syncs before returning. Sixteen producers call it, and sync dominates per-event cost. What limits throughput?
Why. The lock serializes the appends and each one waits for its own sync, so the disk's sync latency sets the ceiling, about 1,000 events per second at 1 ms. Adding producers only lengthens the line at the lock. The fix is to take the sync out of the lock and share each sync across many events.
A candidate's writer loop does this for each batch: complete every future in the batch, then write the batch, then call fsync. What is wrong?
Why. The future is the durability acknowledgement, so it may only complete after the sync covering its event has returned successfully. A fake disk that pauses inside sync can catch premature completion directly. This order need not change record order or cause a deadlock; the broken guarantee is durability before acknowledgement.
A has been accepted. The writer removes A from the queue and pauses before sync, leaving the queue empty. Another thread calls flush(); print("flushed"). What must flush wait for before printing?
Why. Recording the target sequence number at the start and waiting until the durable count reaches it gives a precise promise that cannot be starved by producers that keep appending. "Queue empty" is not durability (the batch may still be syncing), and waiting for later appends could keep flush waiting forever under constant load.
Assuming storage succeeds, which sequence is a correct close()?
Why. Every accepted event needs a durable success or an explicit failure. On the success path the writer drains, syncs and resolves its receipts before the file closes. Clearing the queue loses accepted events and leaves their futures pending forever; closing the file first makes the final writes fail.
The bounded queue is full because the disk has slowed down. Which admission policies preserve the bound without silently abandoning accepted receipts? Successful receipts must still follow sync. Select all that apply.Select all that apply
Why. Blocking and rejecting both tell the producer the truth, and the caller can slow down, retry or shed load. Dropping silently breaks the promise that an accepted event will be written. An unbounded queue just moves the problem to memory, and a crash then loses everything in it.
Why does the writer complete the batch's futures after releasing the lock?
Why. A non-async CompletableFuture action may run on the completing writer; set_value wakes C++ waiters. Completion under a lock is legal, but extends the critical section and can create dependency cycles. Releasing the lock helps but does not make blocking callbacks safe: waiting for a later event on the writer can still deadlock. Completion need not be parallel or reordered.
Java onlyA caller attaches non-async thenApply(seq -> slowWork(seq)) to a receipt. Which threading assumption is safe?
Why. The API permits non-async actions to run on a completing thread; attachment to an already completed future can execute inline on the attaching caller. There is no promise of the common pool or a new thread. Use thenApplyAsync with a separate executor for slow work; a direct executor would still run it inline.
C++ onlyIn a buggy C++ variant, a queued std::promise is destroyed without a value or exception, while its caller still owns the future. What does get() report?
Why. A std::promise destroyed without a value or exception abandons its shared state and stores a broken_promise error, so waiters wake with an exception. The log's close() and destructor drain and fulfil every queued promise, so in this design that only happens after a bug.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
The interviewer adds: "Producers must never block, not even for back-pressure." What do you change, and what do you tell them it costs?
Model answer

append stops waiting on "not full". When the queue is at its bound, it returns immediately with a future that is already failed with a "log busy" error (or returns false from a tryAppend), and it counts the rejection so operators can see it. The writer side is unchanged. This removes waiting for queue capacity, but the mutex can still block. For the literal requirement I would use tryLock or std::unique_lock with std::try_to_lock and reject on contention too. Allocation and scheduling still have no hard real-time bound. Some appends fail under overload, so callers must decide what to do: retry later, shed the request, or report the error upstream.

What I would not do: make the queue unbounded, which turns a slow disk into memory growth and a crash that loses everything queued, or silently drop events, which breaks the durability promise. If the product truly needs "never block and never fail", no finite system can guarantee it under sustained overload or indefinite storage failure. A bigger buffer, spill storage or more partitions buys capacity or time, but does not remove that limit; spill I/O can itself block. I would also express the bound in bytes rather than count if events vary in size.

Explain
"Walk me through the synchronization and tell me how you would test this for race conditions."
Model answer

One lock guards the queue, the next sequence number, the durable counter, the closed flag and the failure. append assigns the sequence number and enqueues in the same critical section, so sequence order, queue order and file order are identical. Only the writer thread touches the file, so the file needs no lock. The writer takes the whole queue under the lock, then writes and syncs outside it while producers keep enqueuing, then records the result under the lock and completes the batch's futures outside it. Producers wait on "not full", the writer on "not empty or closed", flush on "durable has reached my target or failed", and each state change signals the condition that may now hold.

To test: inject a fake storage layer with gates, a sync counter and a durable byte frontier. Hold a batch at sync, assert its futures remain incomplete, fill the queue, then trigger close or inject failure and release the gate. Also run many producers with seeded start orders. Check that the file order matches the sequence numbers and each producer's own order; that every future completed only after the synced byte count covered its event (record the synced length when completing); that a controlled backlog is batched into far fewer syncs than events, without demanding batching for isolated low-load calls; that close completes every accepted future and rejects later appends; that a sync failure fails the batch and everything after it; and that producers block when the queue is full. In C++ I would run it all under ThreadSanitizer, and in Java repeat it many times.

Write code
Add a linger to the writer: after it wakes for a non-empty queue, give it a 2 ms linger budget for 64 events (or queue capacity, if smaller). A full queue or close ends the linger; scheduling and lock reacquisition can exceed the budget. Write the lines that go right after the writer's wait for "not empty or closed".
Model answer

Append signals the condition for each event, so the predicate can end the linger early. A timed wait is a budget, not a hard scheduling deadline. In Java, interrupting the file writer is terminal: the restored interrupt causes subsequent interruptible channel I/O to fail and close the channel, which the existing failure path reports to all pending receipts. Never describe interruption here as harmlessly skipping a delay. For a flush that must bypass linger immediately, add a flush-request flag or target to the predicate and signal the writer when it changes. Linger shares fixed costs across more events at the price of additional latency; measure both.

  • Explain admission pressure, batch latency and byte limits
How a senior would say it
I would use one writer thread and group commit, with a bounded queue between producers and the file. Under one lock, append assigns a sequence number and enqueues the event, then returns a future. That defines the order; overlapping callers may be ordered either way. For a synchronous API the caller waits on that future before returning success. The writer takes the queued events as one batch, releases the lock, writes every byte with a short-write loop, and performs one sync. Only after that succeeds does it advance the durable prefix and complete those receipts outside the lock. Producers can fill the next batch while storage is busy, so batching happens naturally under load. The invariant is that every sequence below the durable counter is safely persisted, and that counter never exceeds the accepted frontier. Flush snapshots the accepted frontier once and waits for that prefix, so later producers cannot keep moving its target. If the queue fills, callers block or receive an explicit rejection. I would bound bytes as well as event count and account for the in-flight batch and copied buffer. This improves throughput by sharing sync cost; it does not remove storage latency, overload, or the need to report failures.

Likely follow up: Can a future callback deadlock this design even when you complete futures outside the lock?

Out loudabout 75 s
"The queue is empty, but flush returns too early. Close also sometimes loses the last events. Walk me through the lifecycle."
What a strong answer covers
  • An empty queue can coexist with an unsynced batch in flight
  • Flush snapshots the accepted frontier under the admission lock
  • Close closes admission and wakes both producer and writer waiters
  • Drain, sync, resolve receipts, join and release the file in that order
  • Report storage failure and define interruption and repeated-close behaviour
How a senior would say it
I would base flush on the durable prefix, not queue emptiness. The writer may have removed the last batch and still be waiting for the disk. Flush captures the next sequence number under the queue lock and waits until the durable counter reaches that fixed target, or a storage failure makes success impossible. Close first shuts admission under the same lock, so every racing append is either accepted into the drain or rejected. It wakes the writer and producers waiting for capacity. The writer then drains accepted work, syncs it, resolves every receipt and exits. Only after joining it do I close the file. That order prevents closing a descriptor underneath an active write. A storage failure still resolves the affected receipts exceptionally and is reported by explicit close. Repeated close must be safe, including concurrent calls. In Java I finish cleanup if the closing caller is interrupted, then restore its interrupt flag; I do not interrupt the file writer to request shutdown. I would test these transitions with a gated fake sync and a full queue.

Likely follow up: Does flush returning imply that every callback attached to those receipts has finished?

Out loudabout 75 s
"The sync succeeded, then the process crashed before the client saw its receipt. Can the client safely retry?"
What a strong answer covers
  • A missing or timed-out receipt is uncertain, not proof that the event was absent
  • Separate durable storage from delivery of the acknowledgement
  • Use stable request IDs and durable deduplication for retries
  • Recover framed records with bounded lengths, checksums and sequence validation
  • Distinguish an incomplete unacknowledged tail from corruption in an acknowledged prefix
How a senior would say it
The client can retry only with a protocol that tolerates duplicates, because a missing receipt does not mean the write failed. The event may already be durable while its acknowledgement was lost. Timing out on the receipt also leaves an accepted append running. I would assign a stable request ID before the first attempt and store enough deduplication information durably with the event, so another attempt can find the existing result instead of applying the effect again. A storage error can also leave an uncertain outcome, so a failed future is not permission to assume the file contains nothing. On restart I would validate the log format before accepting writes. Each record needs a bounded length, a checksum and sequence information, so recovery can find the complete prefix and detect a torn tail. An incomplete unacknowledged tail can be truncated and the repair synced. Corruption inside an acknowledged prefix is different: silently truncating it would violate promises already made, so the system must repair from another copy or stop. Group commit establishes persistence before success; stable identities and recovery establish what retries mean after that success becomes uncertain.

Likely follow up: Where must the deduplication record live so a crash cannot separate it from the event's effect?
