Thread states and what blocking really does

Java's six thread states, the OS five-state model, and what a blocked thread really costs: no CPU, but it keeps everything it holds.

Asked atQualcomm
Before this:The scheduler, time slices and context switches

When a service hangs or crawls, the first thing you read is the state of every thread. Knowing exactly what each state means, and what a waiting thread is still holding, turns a mysterious outage into a five minute diagnosis.

In plain words

Think of patients in a hospital. Some are registered but not yet seen. Some are with a doctor, or next in line for one. Some are waiting outside the operating theatre because someone else is inside. Some wait for test results with no idea when they will come, and some have an appointment at a fixed time. Finally, some go home.

A patient waiting for test results takes none of the doctor's time. But they still occupy a bed, and maybe a wheelchair and a nurse's attention. If every bed is taken by people waiting for one slow lab, the hospital is full even though the doctors are idle. Threads work exactly the same way.

Java's six states

Java gives every thread one of six states, returned by Thread.getState() and printed for every thread in a thread dump. They map onto every runtime you will meet, so learn them precisely.

StateWhat it meansHow a thread gets thereHow it leaves

RUNNABLERunning on a core, or ready and waiting in a run queue, or inside native code such as a blocking socket readstart(), or leaving any of the waiting statesBlocking, waiting, or finishing
BLOCKEDWaiting to acquire a monitor (synchronized) that another thread holds, including taking it back after being notified inside wait(), before wait() can returnEntering a busy synchronized block or methodThe monitor comes free and this thread gets it
WAITINGParked with no time limit until another thread does somethingObject.wait(), Thread.join(), LockSupport.park(), and everything built on parking: Lock.lock(), Condition.await(), CountDownLatch.await(), BlockingQueue.take(), Future.get()A notify, an unpark, the joined thread ending, or an interrupt
TIMED_WAITINGThe same, with a time limitThread.sleep(t), wait(t), join(t), LockSupport.parkNanos, and timed calls like tryLock(t), await(t), poll(t)As for WAITING, or the time runs out

Two surprises interviewers love

A thread waiting for a ReentrantLock is WAITING, not BLOCKED. BLOCKED means one thing only: waiting for a monitor, the lock behind synchronized. Every lock in java.util.concurrent waits by parking, so its waiters show WAITING (or TIMED_WAITING for tryLock with a timeout). If you search a dump for BLOCKED threads to find lock contention, you will miss every contended ReentrantLock.

A platform thread blocked in a socket read is RUNNABLE. The JVM only knows that the thread called into native code. The operating system has it asleep waiting for data, but Java reports it as runnable. A dump full of RUNNABLE threads inside socket reads, with low CPU, is a service waiting on the network, not a busy one.

And one more detail that matters for correctness: after a notify, the woken thread is not running yet. It must take the monitor back before wait() can return, so it passes through BLOCKED:

C++ works the same way: std::condition_variable::wait returns only after the thread has re-acquired the mutex. You will build on this in module 05.

The operating system's view: five states

Operating systems textbooks describe a process with five states, and online assessments ask about them directly (a 2026 Qualcomm assessment included process states next to scheduling). Since the kernel schedules threads, not processes, the same five states apply to each thread of a multithreaded process.

StateMeaning
NewBeing created: the OS is setting up its structures, and it is not yet eligible to run.
ReadyAble to run, waiting in a run queue for a core.
RunningExecuting on a core right now. With N cores, at most N threads are running.
Waiting (or blocked)Cannot run until an event happens: I/O completes, a lock is released, a signal arrives, a timer fires.
TerminatedFinished; the OS keeps a little information (such as the exit status) until it is collected.

The transitions are the part examiners test:

  • new to ready: admitted by the OS;
  • ready to running: dispatched by the scheduler;
  • running to ready: preempted, because the time slice ended or a more urgent thread woke up;
  • running to waiting: the thread blocks on I/O or an event;
  • waiting to ready: the event happened, so the thread is woken;
  • running to terminated: the thread exits.

Two transitions do not exist, and they make good trick questions. Waiting never goes straight to running: a woken thread goes back to ready and must be dispatched like everyone else, which is exactly why a notified thread is not guaranteed to run soon. And ready never goes to waiting: only a running thread can block, because blocking is something the thread does by calling into the kernel. Some textbooks add suspended states (ready-suspended, waiting-suspended) for processes swapped out of memory; most interview questions use the five above.

On Linux, ps and top show a state letter, per thread with top -H or ps -eLo pid,tid,stat,comm:

LetterMeaning
RRunning, or runnable and waiting in a run queue. Linux does not tell these apart here either.
SSleeping, interruptible: waiting for an event such as a lock, data, a timer. Most idle threads are here.
DUninterruptible sleep, usually waiting on disk or network file system I/O. Signals, even kill -9, wait until it ends (Linux also has a killable variant of this sleep, shown as D too, that a fatal signal can end).
TStopped by a signal, for example SIGSTOP or Ctrl+Z (a thread stopped under a debugger shows t).
ZZombie: a process that has exited but whose parent has not collected its exit status yet.

The mapping from Java is direct. NEW has no OS thread at all yet: start() is what creates it. RUNNABLE is R, or S when the thread is inside a blocking system call such as a socket read. BLOCKED, WAITING and TIMED_WAITING are all S: asleep on a futex or a timer, off every run queue. TERMINATED means the OS thread is gone.

C++ gives you no state API at all. The std::thread constructor starts the new thread before it returns, so there is no NEW stage, and a default-constructed std::thread represents no thread. joinable() only says whether the object still owns a thread of execution: it stays true after the function has returned, until you call join or detach. To see what C++ threads are doing, use the OS and a debugger: top -H or ps -eLo pid,tid,stat,comm for the states on Linux, and to print every thread's stack, gdb's thread apply all bt on Linux, or sample PID or lldb's bt all on macOS.

What blocking really does

When a thread blocks, on a lock, an empty queue, a socket with no data, a sleep, this is what happens:

  1. The thread asks the kernel (directly, or through the JVM's parking) to wake it when a specific thing happens.
  2. The kernel takes it off the run queue and puts it on the wait queue for that thing. Its state becomes S.
  3. It uses no CPU at all while it waits. The core runs another thread, or idles.
  4. The thing happens: the lock is released, data arrives, a notify comes, the timer fires. The kernel moves the thread back to a run queue.
  5. When a core is free, the scheduler runs it. It returns from the blocking call, usually with cold caches, a few microseconds after the event at best.

No CPU, but not free

A parked thread costs no CPU. That makes it easy to forget what it still holds:

  • its stack and kernel bookkeeping (lesson 01-06 puts numbers on these);
  • every lock it took before it blocked, so every thread that needs those locks waits too;
  • database connections, file handles, sockets, pool slots, semaphore permits and memory buffers it acquired earlier.

This is the root of a whole family of production incidents. A dependency slows down; threads block on it while holding a connection or a lock; other threads wait for those; soon every thread is waiting, the CPU is nearly idle, and the service looks dead. Blocking while holding a scarce resource is how one slow dependency takes down a whole service.

Worked example: 200 threads, 3 percent CPU, nothing moving

An order service has stopped responding. CPU is at 3 percent. You take a thread dump (jcmd PID Thread.print) and group the 200 request threads by state and top frame. A shortened excerpt:

Read it. Ten threads hold the pool's ten connections and are RUNNABLE inside a socket read: they are waiting for the database to answer a query. The other 190 are parked inside borrow, waiting for a connection. Nothing is computing, which is why the CPU is idle, and nothing is deadlocked: the whole service is queued behind one slow query.

Fix it. Find the slow query on the database side (a missing index, a lock held by another transaction). borrow already waits with a timeout (the threads are TIMED_WAITING in parkNanos), but it is clearly too long: make it short, so requests fail fast instead of piling up, and give queries a timeout too. Keep the critical path short: no remote calls while a connection is checked out. And consider a separate pool, a bulkhead, for the endpoint that runs the expensive query, so it cannot starve the others (lesson 15-05).

Reading a thread dump in a minute

Group threads by state and by their top frames from your own code, then look for these patterns:

  • Many BLOCKED threads "waiting to lock" the same monitor: a hot synchronized lock, or a holder that is itself stuck. Find the thread that "locked" that address and see what it is doing.
  • "Found one Java-level deadlock" at the end of the dump: the JVM found a cycle among monitors or java.util.concurrent locks and names the threads.
  • Many WAITING threads parked in the same pool, queue or latch: a starved resource, a slow dependency behind it, or a signal that never comes.
  • Many RUNNABLE threads in the same method of your code: a CPU hot spot or a busy loop.
  • Many RUNNABLE threads in socket reads with low CPU: waiting on the network.

To take one: jstack PID, jcmd PID Thread.print, or kill -3 PID, which makes the JVM print the dump to its own standard output. For C++, attach gdb and run thread apply all bt, or use sample PID on macOS. On Tandem, when a sample hangs, the Run button does this for you. Lesson 14-01 goes deeper.

Common mistakes

  • "BLOCKED means waiting for anything." Only for a synchronized monitor. Waiting for a ReentrantLock, a latch or a queue is WAITING or TIMED_WAITING.
  • "RUNNABLE means it is using a CPU." It may be waiting in a run queue, or asleep inside native I/O.
  • "A waiting thread costs nothing." It costs no CPU. It still holds its stack and every lock, connection and permit it took before waiting.
  • Using getState() for synchronization. The answer is a snapshot that may be stale by the time you act on it. Coordinate with join, latches or conditions; use states only for monitoring and debugging.
  • Calling start() twice in Java. It throws IllegalThreadStateException. A finished thread cannot be restarted; submit the work again to a pool instead.
  • Calling run() instead of start() in Java. The code runs on the caller's thread, no new thread is created, and the Thread object stays NEW. It compiles and often looks fine in a quick test, which is why it survives code review.
  • Reading joinable() as "still running" in C++. It stays true after the thread's function has returned, until join or detach.

In the interview

Thread states come up as theory ("name the Java thread states", "what is the difference between BLOCKED and WAITING?") and, more usefully, inside debugging. Rubrik's debugging round, where you are handed someone else's multithreaded program that deadlocks or misbehaves, rewards exactly the skill of reading where every thread is stuck and why.

Java has six states: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING and TERMINATED. BLOCKED is specifically waiting for a synchronized monitor; anything that parks, like a ReentrantLock, a condition or a queue, shows as WAITING or TIMED_WAITING. RUNNABLE includes threads inside native I/O, so it does not mean busy. A blocked thread uses no CPU, but it keeps every resource it holds, which is why a service can be completely stuck at three percent CPU. When something hangs, I take a thread dump, group threads by state and top frame, and look for what they are all waiting on.

Follow ups to expect: "Does a blocked thread consume CPU?" (no, but it holds memory and resources); "What state is a thread in right after it is notified?" (it must reacquire the lock first, so BLOCKED in Java until it gets it); "Your service is slow but CPU is low: what do you check?" (a thread dump: what are the threads waiting for); "What is the difference between sleep and wait?" (sleep keeps every lock the thread holds and needs none; wait must be called while holding that object's monitor, or it throws IllegalMonitorStateException, releases only that one monitor while it waits, and must take it back before it returns. Both show TIMED_WAITING or WAITING, and both end early with InterruptedException if the thread is interrupted).

Senior depth

Not every wait can be cancelled. A Java thread BLOCKED on a monitor ignores interrupt() until it gets the monitor, while lockInterruptibly() on a ReentrantLock can be interrupted, which is one reason to prefer explicit locks where cancellation matters (lesson 04-03). At the OS level, a Linux thread in state D cannot be killed until its I/O completes (unless the kernel used the killable variant of that wait), which is how a hung network file system can leave unkillable processes behind. Linux also counts D threads in the load average, so a high load average with idle CPUs often points at stuck I/O rather than busy threads.

Virtual threads use the same six states, but a parked virtual thread holds no carrier thread at all (unless it is pinned, for example by blocking inside synchronized on JDK 21), and classic jstack output does not list virtual threads. One state reads differently: a virtual thread waiting in a socket read is parked by the JDK rather than asleep in native code, so it shows WAITING, not RUNNABLE. To see them, use the JDK 21 command jcmd PID Thread.dump_to_file -format=json FILE, which writes every thread, virtual ones included.

Key takeaways

  • Java's states: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED. BLOCKED is only for synchronized monitors.
  • RUNNABLE means running, ready, or inside native I/O; it does not mean busy.
  • A notified thread must reacquire its lock before its wait returns, so the condition may have changed again.
  • A blocked thread uses no CPU but keeps its stack and every lock, connection and permit it holds.
  • The OS five-state model: new, ready, running, waiting, terminated. Waiting goes back to ready, never straight to running.
  • When a service hangs, take a thread dump and group threads by state and top frame.

Quick check

Answer each question, then read why. Your score is saved for your module test.

1,000 threads are blocked on a condition variable, waiting for work that has not arrived. What do they cost?
Why. A blocked thread is off every run queue, so it uses no CPU until it is woken. That is the difference from spinning, which would cost a core per thread. But "no CPU" is not "nothing": memory for stacks and kernel structures stays allocated, and any locks or connections the threads hold stay held.
Thread W is waiting on a condition variable (or a Java monitor's wait()). Thread N notifies it while still holding the lock. What happens to W right away?
Why. Waiting releases the lock, and returning from the wait requires taking it back. While N holds it, W is woken but stuck (in Java its state is BLOCKED). When N releases the lock, W competes for it with any other thread, so by the time W runs, the condition it waited for may no longer hold: always re-check it in a loop.
In the five-state model, a thread is waiting for disk I/O and the I/O completes. Which state does it move to next?
Why. Waiting goes only to ready. The woken thread joins a run queue and competes for a core like any other; it runs when the scheduler dispatches it, which may be at once or after other threads' time slices. Java shows the same idea: RUNNABLE covers both ready and running, and a woken thread is not guaranteed to run soon.
A service has nearly stopped. CPU is at 3 percent, and a thread dump shows 190 of 200 request threads parked inside the connection pool's borrow method. What is the most likely problem?
Why. Low CPU means nothing is computing; 190 threads waiting for a connection means the connections are all checked out. Look at the threads that hold them: if they sit in socket reads to the database, a slow query or a database side lock is the cause. It is not a deadlock: as soon as the queries finish, everything moves again.
A thread took a database connection and then a lock, and is now blocked waiting for a slow HTTP response. While it waits, what does it still hold? Select all that apply.Select all that apply
Why. Blocking gives up the core and nothing else. The connection and the lock stay held for the whole wait, so every thread that needs them waits too. That is the classic chain behind outages: one slow call, made while holding scarce resources, stalls threads that never touch the slow dependency.
Java onlyThread T calls lock() on a ReentrantLock that another thread holds. What does T.getState() return while T waits?
Why. ReentrantLock waits by parking (LockSupport.park), and a parked thread is WAITING. BLOCKED is reserved for threads waiting to enter a synchronized monitor. With tryLock(timeout), the state would be TIMED_WAITING.
Java onlyWhat does this print?
Why. Before start(), a thread is NEW. join() returns only after the thread has finished, so the second print always shows TERMINATED. This one is deterministic, unlike most thread output.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A banking service hangs completely. Here is part of its thread dump. What is wrong, why did it happen, and how do you fix it?
Model answer

What is wrong. It is a deadlock between two transfer threads. transfer-7 holds account b2 and waits for a1; transfer-12 holds a1 and waits for b2. Neither can proceed, and the JVM has confirmed the cycle in its "Found one Java-level deadlock" report. The other 31 threads are collateral damage: they are BLOCKED on the same two accounts and will wait forever behind the deadlocked pair.

Why. Line 21 of Bank.transfer locks the source account and then the destination, in argument order. One thread transferred from b2 to a1 while another transferred from a1 to b2, so they took the same two locks in opposite orders. Each got its first lock, and then each waited for the other's.

Fix. Make every thread take the two locks in one global order, for example lower account id first, whatever the direction of the transfer. Then a cycle is impossible. An alternative is tryLock with a timeout on ReentrantLock, backing off and retrying when the second lock is not available. To restore service right now, the process has to be restarted, because a monitor deadlock cannot be broken from outside. The full treatment is in the deadlock lesson and the transfer deadlock problem.

Explain
Explain to an interviewer what happens to a thread from the moment it calls lock() on a mutex that another thread holds until it owns the mutex, and what that costs compared with an uncontended lock.
Model answer
  1. The thread tries to take the lock with an atomic compare-and-swap in user space. It fails, because the lock word says "held".
  2. Many implementations spin briefly, retrying for a short while, in case the holder is about to release it.
  3. If the lock is still held, the thread registers itself as a waiter and asks the kernel to put it to sleep: a futex wait on Linux. In Java a ReentrantLock waiter parks and shows WAITING; a synchronized waiter shows BLOCKED. It is off the run queue and uses no CPU.
  4. The holder unlocks. Seeing that there are waiters, it asks the kernel to wake one: another system call.
  5. The woken thread becomes runnable and waits for a core. When it runs, it tries the compare-and-swap again. It may lose to a thread that arrived just then and grabbed the lock (barging), in which case it waits again. Otherwise it now owns the lock and returns from lock().

Cost: an uncontended lock and unlock is a few nanoseconds of atomic instructions in user space. A contended acquisition adds system calls, two context switches and cold caches: microseconds, hundreds to thousands of times more. That is why contention, not locking itself, is what makes locks slow, and why the cure is shorter critical sections and less sharing.

  • Low CPU with no progress means the threads are waiting, not computing: a deadlock, a starved resource or a slow dependency
  • Take two or three thread dumps a few seconds apart (jstack or jcmd PID Thread.print; gdb's thread apply all bt for C++)
  • Check for the JVM's deadlock report, then group threads by state and by the top frame in your own code
  • Follow the chain: threads parked in a pool lead to the threads holding its resources, and to what those are waiting on
  • Fix the cause and limit the blast radius: short timeouts, a separate pool for the slow path, no slow calls while holding a connection or lock
How a senior would say it
Low CPU with no progress tells me the threads are waiting, not computing, so the question is what they are waiting for. I take a thread dump with jstack or jcmd, and a second one a few seconds later, so I can tell stuck threads from slow ones. First I look for the deadlock report at the end: if the JVM found a cycle, it names the threads and the locks, and the fix is a consistent lock order. If there is no cycle, I group the threads by state and by the top frame in our own code. Usually one big group is parked in the same place, say 190 threads in the connection pool's borrow. Then I look at who holds the scarce thing. If the ten threads holding connections are RUNNABLE in socket reads to the database, the real cause is a slow query, and everything else is queued behind it. A restart only buys time. The fix is the query itself, plus short timeouts on borrowing and on queries so requests fail fast, and a separate pool for the expensive endpoint, so that one slow dependency cannot take the whole service down. In C++ the method is the same, with thread apply all bt in gdb.

Likely follow up: The deadlock report is empty and both dumps look the same. How do you tell a deadlock from a dependency that is just very slow?

Out loudabout 80 s
"A thread is inside wait() and another thread calls notify(). Walk me through the states the waiting thread passes through until its code runs again, and what that means for how you write the wait."
What a strong answer covers
  • While inside wait() it is WAITING: parked, using no CPU, and it has released the monitor
  • After notify() it becomes BLOCKED, because it must take the monitor back and the notifier still holds it
  • It competes for the monitor once the notifier leaves, so another thread can get in first and change the condition
  • Then it is RUNNABLE, which in OS terms means ready: it still has to be dispatched onto a core
  • So the condition is rechecked in a while loop; C++ condition_variable::wait behaves the same way
How a senior would say it
It goes through three states, and the middle one is the one people forget. While it sits in wait(), it is WAITING: parked, using no CPU, and it has released the monitor so that others can change the state. When another thread calls notify(), the waiter does not run. It becomes BLOCKED, because wait() cannot return until it owns the monitor again, and the notifier is still inside its synchronized block. When the notifier leaves, the waiter competes for the monitor with any other thread that wants it, and a newcomer can get in first and take whatever the waiter was waiting for. Once it wins the monitor it is RUNNABLE, which in operating system terms means ready, not running: it still has to be dispatched onto a core. So by the time my code after wait() runs, the condition may be false again. That is why I always wait in a while loop that rechecks the condition. C++ is the same: condition_variable::wait returns only after the mutex is taken back, and I use the overload with a predicate.
