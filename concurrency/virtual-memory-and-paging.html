Virtual memory and paging

Pages and frames, page tables and the TLB, page faults, replacement, thrashing, copy-on-write and mmap, and why all of it matters for threads.

Asked atLinkedInRubrik
Before this:Processes and threads: the memory pictureWhat a thread costs, and why more threads can be slower

Every address your program uses is an illusion that the CPU and the kernel translate on every memory access. That machinery explains why processes cannot see each other's memory, why a thread stack is cheap to reserve, why fork is fast, and why a healthy machine can suddenly slow to a crawl when memory runs short. LinkedIn infrastructure phone screens ask about it directly, and Rubrik candidates report rounds that turn into memory management discussions.

In plain words

Picture a library with a huge store room and a small reading hall with forty desks. You think of your books by shelf number, 1 to 10,000, as if every shelf were yours. In reality only forty shelves' worth of books can be on desks at once. A catalogue says which of your shelf numbers is on which desk right now; the receptionist remembers the last few lookups so you rarely wait for the catalogue.

Ask for a shelf that is not on a desk and a librarian fetches it from the store room, maybe carrying another one back to make space. That trip is slow, but it is rare if you mostly reread the same few shelves. If you keep asking for more shelves than there are desks, the librarians spend all day fetching and returning books and nobody reads anything. Your shelf numbers are virtual addresses, the desks are physical memory, the catalogue is a page table, the receptionist is the TLB, the fetch is a page fault, and the all-day fetching is thrashing.

Virtual addresses and physical memory

Each process has its own address space of virtual addresses. The program reads and writes those addresses; a hardware unit in the CPU, the memory management unit (MMU), translates each one to a physical address in RAM, using tables the kernel maintains for that process. This one level of indirection buys a lot:

  • Isolation. A process can only reach physical memory that its own tables map, so it cannot read or corrupt another process.
  • Laziness. Address ranges can be reserved without any memory behind them; memory is attached only when touched. This is virtual memory at work in every thread stack (lesson 01-06).
  • Sharing. Two processes can map the same physical memory: shared libraries, shared memory segments, a parent and child after fork.
  • More than fits. The total of all address spaces can exceed RAM, with rarely used pages kept on disk (swap) or re-read from their files.

Pages and frames

Translation works in fixed-size blocks. Virtual memory is divided into pages and physical memory into frames of the same size: 4 KB on x86-64 Linux and most systems, 16 KB on Apple Silicon Macs. An address splits into two parts: the page number, which is translated, and the offset within the page, which is copied unchanged.

That arithmetic is a classic exam question: the offset needs log2 of the page size in bits, and the page number gets whatever is left.

Page tables and the TLB

A page table maps each page number to a frame number plus a few bits: present (is it in RAM?), writable, user accessible, accessed (used recently?) and dirty (written since it was loaded?). One flat table for a 64-bit address space would be enormous (with 48-bit addresses and 4 KB pages, 2^36 entries of 8 bytes, 512 GB per process), so real page tables are trees: x86-64 with 48-bit addresses and 4 KB pages uses four levels, each indexed by 9 bits of the address (newer CPUs can add a fifth level for 57-bit addresses). A tree saves space because a region that maps nothing needs no lower-level tables at all, and real address spaces are mostly empty. Translating one address the slow way, a page walk, means up to four extra memory reads.

Doing that on every load and store would be ruinous, so every core caches recent translations in the TLB (translation lookaside buffer), a small cache of tens to a few thousand entries. Programs touch the same pages again and again, so almost every access hits the TLB and costs nothing extra; a miss costs a page walk. Two consequences you will meet again:

  • Switching processes disturbs the TLB. The new process has different translations. CPUs tag entries with an address space id (PCID on x86, ASID on ARM) to avoid flushing everything, but the new process still starts with few useful entries. Switching between threads of one process keeps the same translations: one reason a thread switch is cheaper (lesson 01-04).
  • Large pages extend the TLB's reach. One 2 MB page (x86-64) covers what 512 small pages would need 512 entries for. Databases and JVMs with large heaps use huge pages for this reason.

Page faults and demand paging

When the MMU finds no valid translation for an access, the CPU stops the instruction and enters the kernel: a page fault. The kernel decides what kind it is:

KindWhen it happensCost (order of magnitude)
Minor (soft)The data needs no disk read: the first touch of freshly allocated memory (the kernel hands out a zero-filled frame), a file page already in the page cache, or a copy-on-write copyAround a microsecond (a few hundred nanoseconds to a few microseconds)
Major (hard)The page must be read from storage: it was swapped out, or it is part of a file that is not in the page cacheTens of microseconds on a fast SSD to milliseconds on a spinning disk
InvalidThe address is not mapped at all, or the access breaks the page's permissionsThe process gets a segmentation fault (SIGSEGV)

After a minor or major fault, the kernel fills in the page table and the instruction runs again as if nothing happened. The program never sees the fault, only the delay. A major fault puts the faulting thread to sleep while the disk works, and the scheduler runs something else.

Demand paging means nothing is loaded until it is touched: not the pages of the executable, not the heap, not a thread's stack. Allocating a gigabyte with malloc or mmap costs almost nothing; the first touch of each page pays a minor fault. First touches of malloc memory show up as minor.

Page replacement

When memory is full and a fault needs a frame, the kernel must evict a page. Clean pages can simply be dropped (their file still has the data); dirty pages must be written back first. Which page to evict is the page replacement policy:

  • FIFO: evict the page that has been in memory longest. Simple, and blind to use: a page used every millisecond goes out as readily as one never touched again.
  • LRU (least recently used): evict the page unused for the longest time. A good bet when the recent past predicts the near future, but exact LRU needs a timestamp per access, which hardware does not provide.
  • OPT (Belady's optimal): evict the page that will be used furthest in the future. Impossible in practice, since it needs to know the future; used as the yardstick for the others.
  • Clock (second chance): pages sit in a circle with the hardware's accessed bit. A hand sweeps the circle: a page with the bit set gets the bit cleared and a second chance; the first page found with the bit clear is evicted. It approximates LRU cheaply, and real kernels use refinements of this idea.

At reference 3 (the tenth), FIFO evicts 1, the oldest arrival, while LRU evicts 5, which has not been used since the seventh reference. On this string OPT needs only 7 faults and Clock needs 9. Notice that LRU lost to FIFO here: this string loops over more pages than there are frames, which is LRU's worst case. LRU is a good heuristic, not a law.

Belady's anomaly. Run FIFO on the same string with 4 frames and it takes 10 faults, one more than with 3: more memory, more faults. This can happen with FIFO because the set of pages it keeps with 4 frames is not always a superset of the set it keeps with 3. LRU and OPT are stack algorithms, whose resident set with more frames always contains the one with fewer, so they never show the anomaly; on this string they drop to 8 and 6 faults with 4 frames.

Thrashing

Every running program has a working set: the pages it touches in a short window of time. While the working sets of everything running fit in RAM, faults are rare. When they no longer fit, each fault evicts a page that someone needs again a moment later, so faults cause more faults. The machine spends its time moving pages between RAM and disk, CPU use falls, and everything slows by orders of magnitude: thrashing. Early batch systems made it worse by admitting more jobs when they saw the CPU idle.

The signs are a high major fault rate, heavy swap traffic, CPU waiting on I/O, and a latency cliff rather than a slope. The cures reduce demand or add memory: run fewer things at once, shrink working sets, add RAM. For services it connects straight to concurrency: every request in flight brings its own working set, so admitting too many concurrent requests, or running too many threads each with its own buffers, can push a healthy box into thrashing. Bounding concurrency protects memory as well as the CPU. A JVM whose heap no longer fits in RAM is the classic disaster: a full garbage collection walks every live object wherever it sits in the heap, so it faults swapped pages back in one by one and the pause stretches from milliseconds to seconds.

Copy-on-write after fork

fork would be slow if it copied the whole address space. Instead the kernel gives the child a copy of the page tables, marks every private writable page read-only in both processes, and shares the frames. (Pages mapped as shared, such as a MAP_SHARED region, stay shared and writable in both.) When either process writes to such a page, the write faults, the kernel copies that one page, and the writer gets its private copy. This is copy-on-write: a child that calls exec right away (lesson 01-01) copies almost nothing.

Redis uses this to save snapshots without stopping: it forks, the child writes a consistent picture of memory to disk, and the parent keeps serving writes. The cost is visible in production: memory use grows with the number of pages the parent modifies during the snapshot, and Redis's documentation advises disabling transparent huge pages, because copy-on-write then copies large pages instead of small ones.

mmap: files as memory

mmap maps a file into the address space as a memory-mapped file. Reading the mapped memory triggers page faults that bring file pages in through the page cache; writes change the page cache, and the kernel writes them back later. With a shared mapping, other processes mapping the same file see the changes, which makes it an IPC mechanism too. Java exposes it as FileChannel.map, returning a MappedByteBuffer; C++ uses POSIX mmap, msync and munmap. Databases and search engines use it to treat large files as arrays without copying them through read buffers.

Two cautions. Durability: a write into a mapping is not on disk until it is flushed, with force() on the buffer in Java or msync in C++. And hidden blocking: touching a mapped page that is not resident blocks the thread on disk I/O with no blocking call anywhere in the code. You cannot put a timeout on it, it does not show up as I/O in a profiler that tracks system calls, and in Java it blocks a virtual thread's carrier, because the JVM never sees it happen. A third, rarer one: if another process truncates the file, touching a mapped page past the new end raises SIGBUS, which kills a C++ process unless it is handled, and surfaces in Java as an InternalError.

Why this matters for threads

  • One address space, one set of page tables. That is what makes sharing memory between threads possible at all, and why a pointer or reference means the same thing in every thread of a process.
  • TLB shootdowns. When one thread unmaps memory or changes its protection, other cores may still cache the old translation for other threads of the process. The kernel interrupts those cores to flush it before the change completes. The cost grows with the number of cores running the process, which is why allocators and garbage collectors that frequently return memory to the OS can slow down heavily threaded programs.
  • Thread stacks are demand-paged reservations. Each stack reserves its full size of addresses with a guard page at the end, but only the pages a thread touches use RAM, which is why thousands of threads reserve far more memory than they use (lesson 01-06).
  • Faults and mapping changes share per-process kernel state. On Linux, page faults and mmap or munmap calls in one process coordinate through a per-process lock (mmap_lock), so many threads that fault while others map and unmap can contend; recent kernels have added finer-grained locking to reduce this.
  • NUMA first touch. On multi-socket Linux machines, a page is usually placed in the memory of the socket whose thread first touches it. A thread that initializes a big array and hands it to workers on the other socket makes every one of their accesses remote (NUMA).

Common mistakes

  • "Virtual memory means swap." Virtual memory is the translation from virtual to physical addresses. Swap is one thing it makes possible; most systems use virtual memory constantly even with swap turned off.
  • "Allocating 1 GB uses 1 GB of RAM." Only touched pages use RAM. The exception is memory your code initializes up front, such as std::vector<char>(n), which writes a zero to every element and so touches every page. (A large calloc usually does not, because fresh pages from the kernel are already zero.) This is also why tools show a process's virtual size (VSZ) far above its resident size (RSS): a JVM with 2,000 threads reserves gigabytes of stack it never touches.
  • "A page fault means a bug." Minor faults happen on every first touch of memory and are normal. Invalid accesses are the bugs, and they end in a segmentation fault.
  • "LRU always beats FIFO" and "more frames always means fewer faults". The worked example breaks both: LRU loses on a looping string, and FIFO shows Belady's anomaly.
  • "fork copies the parent's memory." It copies page tables and shares the pages copy-on-write. What is copied is only what gets written afterwards.
  • "Writes to a mapped file are durable." Not until force() or msync returns.

In the interview

LinkedIn infrastructure phone screens have asked about virtual memory, paging and page faults alongside process versus thread, and a 2025 LinkedIn phone screen listed paging next to deadlocks and mutexes. Rubrik loops include memory management discussions, and a Rubrik L4 candidate recommended studying the OS chapters on memory management and process synchronization. Expect "what is virtual memory?", "what happens on a page fault?", "what is the TLB for?", "what is thrashing?", fault counting on a reference string, and the address arithmetic.

Each process gets its own virtual address space, divided into pages that the MMU maps to physical frames through per-process page tables, with the TLB caching recent translations so most accesses cost nothing extra. Memory is attached on demand: the first touch of a page causes a minor fault, and a page that has to come from disk causes a major fault, which blocks the thread for microseconds to milliseconds. When the working sets of everything running exceed RAM, the system thrashes, so for a service I bound concurrency to keep the in-flight working set in memory. For threads the key facts are that they share one address space, so mapping changes need TLB shootdowns across cores, and that their stacks are lazily backed reservations.

Follow ups to expect: "Minor versus major fault?"; "Why is a thread switch cheaper than a process switch?" (same page tables, so the TLB stays useful); "How does fork stay fast?" (copy-on-write); "What does mmap give you, and what can go wrong?" (zero-copy file access; hidden blocking and durability); "Count the faults for FIFO and LRU with three frames on this string".

Senior depth

Linux normally overcommits: it lets processes reserve more memory than RAM plus swap, betting that not all of it will be touched. When the bet fails, the out-of-memory killer picks a process and kills it, often the largest, which is a common way for a busy Java service to vanish without an exception. Latency sensitive systems often avoid swap entirely, lock critical memory in RAM (mlock), and pre-touch their heap at startup (the JVM's -XX:+AlwaysPreTouch) so that page faults happen before traffic arrives, not during it.

Huge pages trade TLB reach against flexibility: explicit huge pages must be reserved up front, while transparent huge pages are assembled by the kernel in the background, which can add latency and, as Redis notes, makes copy-on-write copy much larger units.

That is the general page size trade off, a classic follow up. Larger pages mean smaller page tables, more TLB reach and fewer faults for the same data. Smaller pages waste less memory inside half-used pages (internal fragmentation), move less data per fault and per copy-on-write, and let protection and sharing be set at a finer grain.

Key takeaways

  • Each process has its own virtual address space; the MMU maps pages to frames through per-process page tables, and the TLB caches the translations.
  • Memory is attached on first touch: minor faults are cheap and normal, major faults wait for the disk.
  • Replacement: FIFO, LRU, OPT and Clock. Count faults by drawing the frames after each reference; FIFO can show Belady's anomaly.
  • Thrashing happens when working sets exceed RAM; bounding concurrency bounds the working set.
  • fork shares pages copy-on-write; mmap turns file access into page faults, with hidden blocking and explicit flushing.
  • Threads share one address space: TLB shootdowns on mapping changes, lazily backed stacks, NUMA first touch.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A machine uses 32-bit virtual addresses and 4 KB pages. How many bits form the page offset, and how many pages can one address space hold?
Why. 4 KB is 2^12 bytes, so 12 bits address a byte within a page. The remaining 32 - 12 = 20 bits are the page number, giving 2^20 pages of 4 KB, which is the full 4 GB. The tempting slip is to give the page number the same 12 bits as the offset.
FIFO page replacement with 3 frames, all empty at the start. How many page faults does the reference string 1 2 3 1 4 1 2 cause?
Why. 1, 2, 3 fault (3). The second 1 hits. 4 faults and evicts 1, the oldest arrival (4). 1 faults and evicts 2 (5). 2 faults and evicts 3 (6). LRU would take only 5 faults here, because it keeps the recently used 1 when 4 arrives.
A program touches a page of freshly allocated anonymous memory for the first time. What happens?
Why. Allocation only reserved addresses. The first touch faults, and the kernel satisfies it from memory alone by handing over a zeroed frame, so it is minor. Major faults need storage: a swapped out page, or a file page missing from the page cache.
Which statement about Belady's anomaly is true?
Why. On 1 2 3 4 1 2 5 1 2 3 4 5, FIFO takes 9 faults with 3 frames and 10 with 4. LRU and OPT are stack algorithms: their resident set with more frames always contains the set with fewer, so more frames can never cause more faults.
A process with a 2 GB heap calls fork. The child changes one variable on one page and then exits. Roughly how much memory was copied for the heap?
Why. fork copies the page tables and shares every frame read-only. The child's single write faults, and the kernel copies just that page (a whole 2 MB page if transparent huge pages back the heap). The page tables themselves are copied, though, so forking a process with a huge address space is not free. "2 GB" is the tempting answer if you picture fork as a memory copy.
Thread A unmaps a region of memory while threads B and C of the same process are running on other cores. What does the kernel have to do?
Why. All threads share one set of page tables, but each core keeps its own TLB. Cores that may hold the old translations get an inter-processor interrupt to flush them, otherwise B or C could still reach memory that no longer belongs to the process. The more cores run the process, the more each shootdown costs.
Java onlyYour Java code writes records into a MappedByteBuffer that maps a file. When are the writes guaranteed to be on the storage device?
Why. A put changes the page cache through the mapping; the kernel writes dirty pages back on its own schedule. force() asks for the mapped content to be written to the device and returns after it is, which is the durability point you need for a log or an index.
C++ onlyRight after std::vector<char> v(1 << 30); versus auto p = std::make_unique_for_overwrite<char[]>(1 << 30); (C++20), how does resident memory compare?
Why. std::vector<char>(n) value-initializes every element to zero, which writes to every page. make_unique_for_overwrite default-initializes, which for char means no writes at all, so demand paging attaches frames only when the program touches them.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Walk an interviewer through what happens, step by step, when a thread reads an address whose page is currently swapped out to disk. What do the other threads of the process do meanwhile?
Model answer
  1. The load misses in the TLB, so the MMU walks the page table and finds the entry marked not present.
  2. The CPU raises a page fault, switching to kernel mode in the context of the faulting thread.
  3. The kernel checks that the address belongs to a valid mapping of the process (if not, the process gets a segmentation fault). It finds that the page lives in swap.
  4. It needs a free frame. If none is free, it runs page replacement: picks a victim, approximately least recently used, and if the victim is dirty, schedules it to be written out first.
  5. It starts the read from the swap device and puts the faulting thread to sleep: this is a major fault, costing tens of microseconds to milliseconds. The scheduler runs other threads meanwhile.
  6. When the read completes, the kernel fills the page table entry with the new frame, marks it present, and makes the thread runnable.
  7. When the thread is scheduled again, the faulting instruction runs again, this time successfully, and the TLB caches the translation.

The other threads of the process keep running. They share the address space, but the fault blocks only the thread that touched the page, unless they touch pages that are also out, or contend for the process's memory management lock while mapping or faulting.

Numbers
Memory access takes 100 ns and a TLB lookup 10 ns; the page table has one level, so a TLB miss costs one extra memory access. (1) With a 90 percent TLB hit ratio, what is the effective access time? (2) Now suppose 1 access in 100,000 causes a major page fault that takes 10 ms to service. What does the effective access time become?
Model answer

(1) A hit costs 10 + 100 = 110 ns. A miss costs 10 + 100 + 100 = 210 ns. Effective access time = 0.9 × 110 + 0.1 × 210 = 99 + 21 = 120 ns.

(2) Each access now also carries an expected fault cost of (1 / 100,000) × 10 ms = 10,000,000 ns / 100,000 = 100 ns. The effective access time becomes about 120 + 100 = 220 ns, close to double.

The lesson: even one major fault in a hundred thousand accesses nearly halves memory speed, because in these numbers a disk access is a hundred thousand times slower than a memory access (10 ms against 100 ns; a fast SSD narrows the gap to roughly a thousand times, which still hurts). That is why latency sensitive services avoid swap and why thrashing is a cliff, not a slope.

Numbers
Three frames, all empty. Run FIFO and LRU on the reference string 7 0 1 2 0 3 0 4 2 3 0 3 2, writing the frames after each reference, and count the faults.

Say it out loud

"A Java service on a 16 GB box is fine with 200 requests in flight. Someone raises the limit to 800, and p99 latency jumps from 30 ms to several seconds while CPU use drops. What do you suspect, and what do you check?"
What a strong answer covers
  • Name it: the in-flight working set no longer fits in RAM, so the box is thrashing, a cliff rather than a slope
  • Why CPU drops: threads sit blocked on major faults, waiting for the disk instead of running
  • Evidence: major fault rate and swap traffic (the si and so columns in vmstat), resident size against RAM, I/O wait
  • The JVM twist: a full garbage collection walks every live object, faulting swapped pages back in, so pauses explode
  • Fix: bound concurrency to what fits, shrink per request memory or the heap, keep swap away from a latency sensitive box, then measure again
How a senior would say it
My first suspect is thrashing. Every request in flight brings its own working set: buffers, objects, a stack. At 200 it all fit in RAM. At 800 it does not, so the kernel keeps evicting pages that someone needs again a moment later. Memory reads turn into major faults, and each one blocks the thread on the disk for tens of microseconds to milliseconds. That is why CPU use falls while latency climbs: the threads are waiting, not running. It is a cliff, not a slope. To confirm, I would check the major fault rate and swap traffic, for example the si and so columns in vmstat, the resident size of the process against physical memory, and I/O wait. A JVM makes it worse, because a full garbage collection walks every live object and faults swapped pages back in one by one, so pauses go from milliseconds to seconds. The fix is to bound concurrency to what fits in memory, or make each request use less, size the heap so it stays resident, and keep swap off a latency sensitive box. Then I measure again.

Likely follow up: How would you pick the concurrency limit instead of guessing it?

Out loudabout 90 s
"A teammate wants to serve lookups from a 50 GB read-only index by memory mapping the file instead of calling read. What do you tell them?"
What a strong answer covers
  • What mmap gives: the file becomes an array, pages arrive on demand through the page cache, no copy into user buffers, and the cache is shared across processes
  • The catch: touching a page that is not resident blocks the thread on disk inside an ordinary memory access, with no timeout and no system call to see
  • Who suffers: a cold start can stall every worker at once, and in Java a fault blocks a virtual thread's carrier
  • Mitigations: warm or pre-fault the hot set, watch the major fault rate; a truncated file gives a bus error
  • Verdict tied to the hot set: mmap when it fits in RAM, explicit reads with an own cache and timeouts when it does not
How a senior would say it
It can be a good choice, with one big catch. Mapping the file turns it into an array. Lookups become plain memory reads, pages arrive on demand through the page cache, nothing is copied into my own buffers, and every process that maps the file shares the same cached pages. Search engines and databases do exactly this. The catch is that a page fault is invisible blocking. If a lookup touches a page that is not in memory, the thread stops for a disk read inside what looks like an array access. There is no timeout, nothing shows up as a system call, and in Java it blocks a virtual thread's carrier as well. After a restart, with a cold cache, every worker can stall on faults at once. So my question is whether the hot part of the index fits in RAM. If it does, mmap is great: I would warm the hot pages at startup and watch the major fault rate. If it does not, I would use explicit reads with my own cache and timeouts, so the slow path is visible and bounded.

Likely follow up: Now the index is written through the mapping too. When is a write durable?

Out loudabout 75 s
"How can fork return almost instantly for a process with a 20 GB heap? And when does that stop being free?"
What a strong answer covers
  • fork copies the page tables, not the memory: parent and child point at the same frames
  • Private writable pages become read-only in both; the first write to one faults and the kernel copies only that page
  • A child that calls exec right away copies almost nothing
  • It stops being free when the parent keeps writing during the child's life: memory grows with every page written, as in a Redis snapshot
  • Huge pages make each copy 2 MB instead of 4 KB, and copying the page tables of a huge process still takes real time
How a senior would say it
Because fork does not copy the memory. It copies the page tables, so the child points at the same physical frames as the parent. The kernel marks every private writable page read-only in both processes. The first time either one writes to such a page, the write faults, the kernel copies that one page, and the writer gets its own copy. That is copy-on-write, and a child that calls exec straight away copies almost nothing. It stops being free when the parent keeps writing while the child lives. Redis is the classic case: it forks to write a snapshot, and every page the parent changes meanwhile gets copied, so memory can grow toward double under heavy writes. Huge pages make it worse, because each copy is 2 megabytes instead of 4 kilobytes, which is why Redis says to turn transparent huge pages off. And copying the page tables of a huge process still costs real time.

Likely follow up: If the child only wants to run another program, what would you use instead of a plain fork?
