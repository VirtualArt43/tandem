Read-write lock, writer preferring

Build a primitivemedium35 minThe classic readers-writers monitor, with writer preference and a timed write lockRubrik

Rubrik has asked candidates to implement a reader-writer lock "handling various cases" and given no further specifics. The cases are the whole question: who goes first, what a waiting writer does to new readers, and what happens when a writer gives up.

The task

Build a read-write lock. Any number of readers may hold it together; a writer holds it alone. This version uses writer preference: once a writer is waiting, new readers wait too, so a stream of readers cannot keep a writer out forever.

  • lockRead() blocks while a writer holds the lock or is waiting for it. Readers already inside are not affected.
  • unlockRead() releases one read hold.
  • lockWrite() blocks until nobody holds the lock (no readers, no writer), then takes it alone.
  • tryLockWrite(timeout) does the same but gives up after timeout and returns false. While it waits it counts as a waiting writer and holds new readers back; when it gives up, it must stop holding them back.
  • unlockWrite() releases the write lock.
  • Upgrades are refused. A lock upgrade and downgrade from read to write deadlocks this design: a thread that still holds the read lock and calls lockWrite() or tryLockWrite() would wait for its own read hold forever. Detect it and throw at once: IllegalStateException in Java, std::logic_error in C++. (For tryLockWrite, returning false at once is also accepted.) The lock must stay fully usable afterwards.

Rules.

  • Build it from one lock and condition variables (one or two, your choice).
  • No library read-write locks or anything that hides one: not ReentrantReadWriteLock, StampedLock, AbstractQueuedSynchronizer or Semaphore in Java; not std::shared_mutex, std::shared_timed_mutex, POSIX rwlocks or std::counting_semaphore in C++. The runner rejects code that names them.
  • To refuse upgrades you must know which threads hold the read lock: a ThreadLocal hold count in Java, or a map from std::thread::id to a count, guarded by your mutex, in C++.
  • The lock is not reentrant (a reader must not call lockRead() again before unlockRead()), and calls are always balanced: you do not need to detect a thread that unlocks what it does not hold.
  • Java only: the lock methods are interruptible. A writer interrupted while waiting throws InterruptedException, and, like a writer that times out, must stop holding readers back.

What the tests check

  • Three readers hold the lock at the same time.
  • A writer waits for the reader inside, then runs alone: a reader and another writer both wait for it.
  • Writer preference: with a reader inside and a writer waiting, a newly arriving reader waits, and the writer gets in before it.
  • A thread holding the read lock calls lockWrite(): it must throw within a second, never deadlock; tryLockWrite(2 s) from the same thread must throw or return false within half a second. Meanwhile another reader can still get in (no phantom waiting writer was left behind), and after the read hold is released a writer gets in.
  • tryLockWrite(200 ms) gives up after about 200 ms; tryLockWrite(5 s) returns true soon after the lock frees.
  • A writer that gives up, by timing out (and in Java by being interrupted), lets the reader it was holding back in at once, while the first reader is still inside.
  • Four readers keep the lock busy with overlapping holds; a writer that arrives still gets in after a small number of reader admissions (the test allows 60), not after the stream ends.
  • A stress run: 5 readers and 3 writers in random start order, writers mixing lockWrite and short tryLockWrite calls. Never a writer together with anyone else, a counter that only writers change ends exact, nothing deadlocks. In C++, ThreadSanitizer must stay quiet (that counter is a plain int, so a broken exclusion shows up as a data race).

Taught in: Build it yourself: read-write lock and reusable barrier

Open them one at a time. Each one gives away a little more.

The whole state fits in three fields under one lock: the number of readers inside, whether a writer is inside, and the number of writers waiting. Write down, for a reader and for a writer, the condition under which each may enter.
A reader may enter when no writer is inside and none is waiting. A writer announces itself (waitingWriters += 1) before it starts waiting, and may enter when nobody is inside. Now decide who must be woken when the last reader leaves, and when a writer leaves.
A writer can stop waiting in three ways: it gets the lock, it times out, or (Java) it is interrupted. Every way must undo the announcement, and the two failure ways must wake the readers it was holding back. A finally block in Java, or one exit path in C++, makes that hard to forget.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

A thread that holds the read lock calls lockRead() again. What happens?
With writer preference it can deadlock: if a writer arrived in between, the second lockRead waits behind the writer, and the writer waits for the first read hold, which this same thread will never release. Since you already track read holds per thread for the upgrade check, the fix is small: let a thread that already holds a read lock re-enter regardless of waiting writers. Java's library lock does exactly that with a per thread hold count.
Dropbox (2021) asked for read_acquire, read_release, write_acquire and write_release built with semaphores. How?
The classic construction: a binary semaphore roomEmpty that writers hold while writing, and a "lightswitch" for readers, a counter under a mutex where the first reader in takes roomEmpty and the last reader out releases it. That alone prefers readers. For writer preference or no starvation, add a turnstile semaphore: a writer takes it and keeps it while waiting for roomEmpty, and every reader passes through it (take, release) before the lightswitch, so readers queue behind a waiting writer. Note that roomEmpty is released by a different thread than the one that took it, which is legal for a semaphore and illegal for a mutex.
Microsoft (2019): only synchronized, wait() and notify(), no library locks and no atomics. What changes?
The design is the same, but there is one wait set per monitor, so readers and writers wait on the same object. That forces notifyAll() wherever you would have signalled one condition: a notify() might wake a reader when only a writer can proceed, and that wakeup is lost. Keep every state change inside synchronized methods, wait in while loops, and handle InterruptedException from wait() by undoing waitingWriters before rethrowing.
Writer preference can starve readers. How?
If writers keep arriving, there is always a writer waiting, so new readers never get in. The fixes are a fair lock that serves arrivals in order and lets consecutive readers share (the fair read-write lock problem), or alternating phases: when a writer leaves, admit every reader that was waiting before the next writer.
When is a read-write lock slower than a plain mutex, and what does std::shared_mutex promise?
When the critical sections are short: every reader still writes the shared reader count, so its cache line bounces between cores, and the bookkeeping costs more than the parallelism saves. Read-write locks pay off for longer reads in read-mostly workloads; for tiny reads look at striping, copy-on-write snapshots or optimistic reads (StampedLock, seqlocks). As for std::shared_mutex, the standard leaves the reader versus writer policy to the implementation, so if you need a guarantee you verify your platform or build the lock, as here.
Rubrik's phone screen: a client wrapper where init is exclusive, requests run concurrently once init has succeeded, close waits for in-flight requests, and close happens once. How?
It is a read-write lock in disguise: init and close take the write lock, each request takes the read lock. Add a state field (new, ready, closed) read and written under the lock, so a request after close fails fast instead of running, and a second close returns at once. Commenters on that report solved it with a read-write lock or shared_mutex.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

This is a monitor with three fields: readers (inside), writing (a writer inside) and waitingWriters. The invariant: if a writer is inside, nobody else is; and while any writer is waiting, no new reader enters. The second half is the writer preference, and it is what keeps a busy stream of readers from starving writers.

Why each line is there

  • Two conditions, canRead and canWrite. Readers and writers wait for different things. With separate conditions, the last reader out can signal exactly one writer, and a leaving writer can either signal the next writer or broadcast to all readers. One condition with a broadcast everywhere is also correct, just noisier.
  • The writer announces itself before waiting. waitingWriters += 1 happens under the lock before the first wait, so from that moment no new reader slips in.
  • The last reader out signals one writer. Any waiting writer can proceed and only one may, so one signal is enough.
  • A leaving writer prefers the next writer. If writers are waiting, signal one of them; otherwise broadcast to the readers, because all of them can enter together.
  • Giving up is a state change. A writer that times out or is interrupted decrements waitingWriters, and if it was the last waiting writer and nobody is writing, it broadcasts to the readers. Forgetting this leaves readers asleep behind a writer that no longer exists, until some unrelated unlock happens to wake them.
  • The timed wait checks the lock before the clock. If the lock frees at the last moment, take it.
  • Refuse upgrades before touching any state. A read holder that waited for readers == 0 would wait for itself. The check runs before waitingWriters += 1, so a refused upgrade leaves no phantom waiting writer that would lock out every new reader. The safe pattern for callers is to release the read lock, take the write lock, and re-check what they read; downgrading (write, then read, then release the write) is always safe.

Cost and trade-offs

Every operation is O(1) under one internal lock; the broadcast to readers is O(waiting readers). Writer preference gives writers bounded waiting (they wait only for the readers already inside) at the price of possible reader starvation under a steady stream of writers. Lock-free reader counts and per-core reader slots exist in production locks, but this monitor is what an interview expects and what you can defend line by line.

How to say it in the interview

The state is the number of readers inside, a writing flag, and the number of waiting writers, all under one mutex with two condition variables, plus a per thread read hold count so I can refuse a read to write upgrade instead of deadlocking. A reader waits while a writer is inside or waiting; that waiting part is the writer preference, so readers cannot starve writers. A writer counts itself as waiting, waits until nobody is inside, then takes the lock. The last reader out signals one writer; a leaving writer signals the next writer if there is one, otherwise wakes all readers. And any writer that stops waiting without the lock, on a timeout or an interrupt, undoes its count and wakes the readers it was holding back. The trade-off is that writers can now starve readers; if that matters I would switch to arrival order.
