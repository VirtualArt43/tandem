Build it yourself: semaphore and latch

Build a semaphore and latch from locks and conditions, prove their invariants and publication, and handle timeouts, overflow, cancellation and fairness.

Asked atRubrikMicrosoft
Before this:Condition variables and monitorsSpurious and stolen wakeups: always wait in a loopSemaphores: permits as a resource limitLatches: wait until N things happen

Rubrik interviewers often ban java.util.concurrent, and a Microsoft round asked a candidate to implement a working semaphore. Building a semaphore and a latch from a lock and a condition variable takes a few lines each, and every one of those lines is a chance to show that you understand waiting correctly.

In plain words

You already know the parking lot with the "spaces free" board. Now you are the attendant. You keep the number in a notebook, and only one person may write in the notebook at a time. Drivers who find the number at zero sit on a bench. When a car leaves, you add one to the number and tap one driver on the shoulder; that driver walks up, looks at the notebook again (someone may have slipped in first), and either takes the space or sits back down.

The notebook is the state, the one-writer rule is the lock, the bench is the condition variable, and "look again before taking it" is the wait loop. Those four things are enough to build the synchronizers here.

The recipe

Both classes follow the monitor pattern, and you will reuse the same recipe in the next lesson and in every "build a primitive" problem:

  1. Name the state and its invariant. For a semaphore: permits, never negative. For a latch: count, never negative and never rising.
  2. Guard all of the state with one lock. Every read and every write, including the ones in "harmless" getters.
  3. One condition variable per thing threads wait for. "A permit is free", "the count reached zero".
  4. For each operation: lock, wait in a loop if needed, change state if needed, notify eligible waiters, unlock.

The loop in step 4 is not optional. A waiting thread can wake up because of a spurious wakeup, or because it was signalled but another thread took the permit before it got the lock back, a stolen wakeup. Waking up means "look again", never "go ahead".

A counting semaphore

State: permits. Invariant: permits >= 0, and it equals the initial count plus releases minus successful acquires. acquire waits while permits == 0, then takes one. release adds one and wakes one waiter. A timed tryAcquire uses one deadline for its condition waits.

This version rejects negative initial counts, has no ownership or fairness guarantee, and allows releases by threads that never acquired. It is a general counting semaphore, not a bounded resource pool: releases can raise it above its initial count, but must not overflow its integer representation.

These classes use ordinary mutexes, so lock acquisition and reacquisition can outlast the deadline; scheduling can delay return too. The budget begins before locking, so time spent acquiring the lock is not followed by another full timeout. For bounded initial lock acquisition, use Java's timed tryLock, or C++'s std::timed_mutex with std::condition_variable_any, sharing the same deadline. Even then, this is not a hard real-time return guarantee. The C++ examples assume durations whose conversion and deadline addition fit the clock's representation.

The demo sleep only makes overlapping holders easier to observe; it is not synchronization. A run may observe a maximum of 1 or 2. These monitor classes also work in C++17; replace the demo's C++20 std::jthread with std::thread and explicitly join each thread. Real permit users need finally in Java or an RAII permit guard in C++ if work can throw.

Java

Clarify a library ban. The code above builds the synchronizer but still uses ReentrantLock and Condition. If all of java.util.concurrent is forbidden, use synchronized methods, wait in the same predicate loop, and notify or notifyAll on that monitor. Monitor entry is not interruptible, although wait is; the fixed-latch checkpoint shows that version.

A countdown latch

State: count. Invariant: count >= 0, it only goes down, and once it is 0 it stays 0. countDown lowers it and, when it reaches zero, wakes every waiter. await waits while count > 0.

The two lines that differ from the semaphore

  • signalAll / notify_all, not one. Reaching zero lets every waiter proceed. Waking one would leave the others asleep forever, because the count never changes again and nobody else will signal. Compare the semaphore, where one release enables exactly one acquirer. The rule from notify versus notifyAll: wake one only when every waiter waits for the same thing and one change lets exactly one of them proceed.
  • Notify while holding the lock (C++). Notifying after unlocking is legal if the condition variable stays alive. If a waiter owns the latch and may destroy it after returning, however, it could observe zero before a delayed notification touches the object. Keeping the notification under the lock closes that gap. It does not establish ownership for all users: keep the latch alive until every waiter and countdown caller has finished, normally by joining them. Java keeps the object alive while a method uses it, but Condition.signalAll still requires its associated lock.

Why the result data is visible

The mutex publishes the data, not the notification. Each loader writes its own array element before locking and counting down. Its unlock synchronizes with a later lock of the same mutex. The chain through all countdowns and the waiter's final acquisition makes all three writes happen-before the read after a successful wait, so each printed sum is 60. A false timed wait does not establish that all results are ready, and the latch does not protect later writes to those elements.

The semaphore's successful acquire linearizes at its decrement under the lock; release linearizes at its increment. A latch countdown linearizes at its decrement, and a successful wait observes zero while locked. A timeout makes its final failed predicate check while locked. If release and expiry race, whichever state the locked check observes determines the result. getCount is only a snapshot, not permission for a later action.

Both primitives have constant-size state and O(1) state changes. Waiting time is unbounded without cancellation or a usable deadline. Latch opening wakes W waiters, so its notification and rescheduling costs can grow with W. A latch opens once; resetting its count would need generations and rules for waiters, which leads to a reusable barrier.

Timeouts done right

A timed wait has one classic bug: waiting for the full timeout again after every wakeup.

Fix the deadline once, before the loop, and measure it on a monotonic clock (System.nanoTime in Java, steady_clock in C++), never the wall clock, which can jump when the system time is corrected. At expiry, check the predicate while still holding the lock: it may have become true near the deadline. The predicate overload does that final check for C++. A nonpositive timeout still tests the predicate once; it does not consume a permit if the predicate is false.

Worked example: a semaphore with acquire(n) and release(n)

An interviewer extends the problem: "Now support taking and returning several permits at once." The predicate and notification policy change, and the API must validate positive requests and prevent overflow.

  • acquire(n) waits while permits < n, then subtracts n.
  • In this simple shared-condition design, release(n) adds n and must now signal all. With a single signal, the release might wake a thread that wants 5 permits when only 2 are free; it re-checks and sleeps again, while a thread wanting 1 permit stays asleep even though it could proceed. Waiters now wait for different things, so the "wake one" rule no longer holds.

Then the follow up: starvation. With signalAll, small requests keep slipping in ahead of a large one, which may never see enough permits at once. The fix is FIFO: give each waiter a ticket number and let only the oldest ticket take permits, holding later requests back even when they could fit. That can cause head-of-line blocking: one permit remains idle behind a request for five. If a ticket holder times out or is interrupted, remove it and wake eligible successors or the abandoned ticket blocks the queue forever. Saying "signalAll for correctness, then FIFO if starvation matters" is the senior answer.

Common mistakes

  • if instead of while. A stolen or spurious wakeup takes a permit that is not there, as the timeline shows.
  • Checking the state outside the lock. if (count > 0) { lock; wait; } lets the last countDown and its signal happen between your check and your wait: a lost wakeup, and you sleep forever. Check and wait under the same lock. In C++ the unlocked read is also a data race.
  • signal in the latch. Only one of several waiters wakes when the count reaches zero.
  • Signalling one waiter when waiters want different things, as with acquire(n). Use signalAll.
  • Restarting the full timeout after every wakeup. The caller can wait many times longer than asked. Use a deadline.
  • Swallowing InterruptedException. Propagate it, or restore the flag with Thread.currentThread().interrupt().
  • Notifying after unlock in a C++ latch that lives on the waiter's stack. The waiter may already have destroyed it.
  • Calling user code while holding the lock, for example a callback in countDown. It can block forever or try to take the same lock.

In the interview

"Implement a semaphore" (Microsoft asked it in a 2022 round) and "wait for all tasks without the library" (Rubrik's recurring waitUntilComplete) are the two common shapes; Rubrik's library bans mean you should be able to write both on a whiteboard in a few minutes. Graders check the loop, the right notify, the lock around every access, interruption in Java, and that you can state the invariant.

I will build it as a monitor: one lock guards the permit count, and one condition variable, "a permit is available". Acquire takes the lock, waits in a loop while the count is zero (the loop handles spurious and stolen wakeups), then decrements. Release increments and signals one waiter, which is enough because one permit lets exactly one waiter proceed. The invariant is that the count is never negative and equals the initial count plus releases minus acquires. For the timed version I wait against a deadline on a monotonic clock. A latch is the same skeleton, except reaching zero must signal all waiters, because all of them can proceed.

Follow ups to expect: "Why while?" (draw the stolen permit), "Why signal and not signalAll?" (and when the answer flips), "Make it fair", "Add acquire(n)", and "Can you do it with atomics only?" (see below).

Senior depth

How the real ones are built. Java 21's Semaphore and CountDownLatch use AbstractQueuedSynchronizer, AbstractQueuedSynchronizer: atomic state and a wait queue, with shared acquisition for these primitives. Their uncontended paths can avoid parking, but the operations are still blocking when permits or events are unavailable. A FIFO wait queue alone does not make admission fair. libc++ also uses atomic state and waiting machinery for its C++20 primitives; the OS mechanism is platform-dependent, not necessarily a Linux futex. Performance relative to a monitor needs measurement on the workload.

Fairness needs admission control. A fair semaphore prevents new arrivals from overtaking queued waiters. One design directly reserves a permit for the queue head; another lets an acquiring thread proceed only when it is the head and enough permits exist. Direct handoff is not mandatory. Define the FIFO ordering point and handle timeout and cancellation removal. Neither fairness nor notification guarantees that the OS schedules a particular waiter promptly.

Semaphores from binary semaphores. A mutex semaphore plus a binary waiting gate needs a baton or acknowledgement protocol. Two releases cannot simply signal the binary gate twice: the gate cannot store two outstanding wakeups, and a C++ binary semaphore must not be treated as an unbounded counter. The protocol must preserve each owed wakeup, including releases that happen before a waiter blocks. That is why the textbook negative-count algorithm cannot be copied blindly onto a binary gate.

Key takeaways

  • Recipe: state with an invariant, one lock around all of it, predicates checked in loops, and notifications when state enables waiting operations.
  • Semaphore: wait while no permits, take one; release adds one and signals one waiter, because one permit enables exactly one.
  • Latch: count down under the lock; reaching zero must signal all, because every waiter can proceed.
  • Timed waits use one monotonic budget and a final locked predicate check; mutex and scheduler delays can still postpone return.
  • Switch to signal all whenever waiters wait for different things, as with acquire(n); add FIFO tickets if starvation matters.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A hand-built semaphore's acquire is written as lock; if (permits == 0) wait; permits -= 1; unlock. What can go wrong?
Why. Waking up does not mean the permit is still there: another thread may have taken it before the woken thread got the lock back, and spurious wakeups happen with no signal at all. Only a loop that re-checks permits == 0 after every wakeup is safe. Waiting releases the lock, signalling under the lock does not reserve the permit, and the same interleaving can occur on one core.
A hand-built latch calls signal() (or notify_one()) when the count reaches zero. Three threads are waiting. What happens?
Why. Every waiter is waiting for the same, permanent condition, and all of them can proceed, so all must be woken. After zero, extra countdown calls do nothing and there are no later signals for the sleepers. The count does not itself wake a condition waiter, and having several waiters is legal.
All acquires request one permit. Why can a semaphore's release() wake just one waiter, while a latch reaching zero must wake all of them?
Why. Signal one is safe only when all waiters wait for the same thing and one change lets exactly one of them go. That holds for a semaphore with single-permit acquires; it does not hold for a latch, nor for a semaphore with acquire(n).
A timed acquire with a 100 ms timeout waits like this:If the thread is woken early three times (spuriously, or by a permit another thread then takes), how long can the caller wait in total?
Why. Each pass waits a full timeout, so three early wakeups can stretch a 100 ms timeout towards 400 ms. Compute a deadline once and wait only for the time remaining, as awaitNanos (which returns the remaining time) and wait_until do.
Java onlyIn the Java semaphore, why must available.signal() be called while holding lock?
Why. A ReentrantLock condition requires ownership when signalling, just as Object.notify requires monitor ownership. Signalling neither releases the lock nor prevents spurious wakeups; the predicate protocol prevents lost wakeups. C++ allows notifying after unlocking, which is sometimes an optimization and sometimes, as with a latch that the waiter may destroy, a bug.
C++ onlyA C++ latch lives on the waiting thread's stack. Several producers can count down concurrently. What is wrong with this count_down?
Why. Two bugs. The unlocked read of count_ races with other count_down calls. And once the count is zero, a waiter woken spuriously (or already about to check) can return and destroy the latch while this thread is still about to call notify_all on it. Decide and notify while holding the lock.
A hand-built semaphore has 0 permits and 3 threads waiting in acquire. Each waiter prints acquired after acquiring. Two other threads each call release() once. Assume the waiters are eventually scheduled, none cancels, nobody else acquires, and there are no more releases. How many acquired lines are eventually printed?
Why. Each release adds one permit and wakes one waiter, so exactly two acquires succeed and the third waiter keeps waiting. If a thread wakes spuriously, the loop makes it re-check and sleep again when no permit is left; it cannot create a permit, and a permit cannot be lost, because every change to the count happens under the lock.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Extend the counting semaphore with acquire(int n) and release(int n). Write the changed methods and explain what changes in the signalling, and why.
Model answer

These methods replace the single-permit methods above; keep their fields and imports or includes, including <limits> and <stdexcept> in C++. The wait condition becomes permits < n. Validate n > 0 and check overflow before addition so failure leaves state unchanged. In this shared-condition design the signalling must become signal-all, because waiters now wait for different things: a single signal might wake a thread that needs 5 permits when 2 are free, while a thread that needs 1 stays asleep with permits available. Waking everyone lets each re-check its own condition. The cost is a burst of wakeups, and a fairness problem: large requests can starve behind a stream of small ones. If that matters, I would serve waiters in FIFO order with tickets, accepting lower throughput.

Debug
This latch sometimes hangs and sometimes lets a waiter through early. Find every bug and fix it. (A C++ version written the same way, with notify_one and an unlocked check, has the same bugs, plus a data race on the count.)
Model answer

Five bugs:

  • The check is outside the lock. await reads count without synchronization, so it may see a stale value, and between the check and the wait the last countDown can run and notify before this thread waits: a lost wakeup, and the waiter hangs forever.
  • if instead of while. A spurious wakeup returns from wait with the count still above zero, so the waiter goes through early.
  • notify instead of notifyAll. With several waiters only one wakes at zero; the others hang.
  • The count can go negative with extra countDown calls, violating the latch invariant and eventually risking integer overflow. Ignore calls at zero.
  • The constructor accepts a negative count. Java's count > 0 check then allows an immediate return, while a C++ zero predicate could wait forever. Reject negative counts.

The monitor version propagates interruption from wait and checks a pre-existing interrupt even if the latch is already open. Entering synchronized itself is not interruptible; use the earlier ReentrantLock version when lock acquisition must be interruptible too.

Explain
An interviewer asks: "Why does the wait have to be in a while loop? Give me a concrete interleaving, not just 'spurious wakeups'."
Model answer

Take a semaphore with zero permits. Thread T1 calls acquire, sees zero and waits, releasing the lock. A releaser adds a permit, so permits is 1, and signals T1. Before T1 gets the lock back, a third thread T3 calls acquire, takes the lock first, sees 1 and takes the permit, so permits is 0 again. Now T1 reacquires the lock and returns from wait. If the code used if, T1 would decrement anyway: permits becomes minus 1 and two threads hold one permit. With while, T1 re-checks, sees zero and goes back to sleep, and the next release will wake it.

That is a stolen wakeup, and it happens with ordinary locks that allow barging, even without spurious wakeups. Spurious wakeups are the second reason: Java's condition waits and C++ condition-variable waits permit returns without a corresponding notification. Both mean a wakeup is a hint to re-check the condition under the lock, never permission to proceed.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Build me a counting semaphore from a mutex and a condition variable. Explain why each part is necessary."
What a strong answer covers
  • One mutex protects a nonnegative count equal to initial permits plus releases minus successful acquires
  • Acquire checks and waits in a loop, then decrements under the same lock
  • A concrete barging interleaving explains why notification does not reserve a permit
  • Release checks overflow, increments, and wakes one waiter for single-permit requests
  • Interruption before acquisition leaves the count unchanged; callers release only acquired permits
  • Multi-permit requests need broader notification or explicit waiter selection, with separate fairness policy
How a senior would say it
I would use one mutex to protect the permit count and one condition for permit availability. The count stays nonnegative and equals the initial permits plus releases minus successful acquires. Acquire locks, waits while the count is zero, and decrements before unlocking. Waiting releases the mutex and reacquires it before checking again. That loop matters even without spurious wakeups. Suppose a release wakes Alice, but Bob acquires the mutex first and takes the permit. Alice must check again or she will subtract from zero. Release checks for integer overflow, adds one permit, and signals one waiter, because each acquire needs one permit. In Java I would propagate interruption before changing the count, and callers return permits in a finally block only after acquisition succeeded. C++ callers use a scope guard. The semaphore itself has no owner. If requests can take several permits, waking just one unsuitable waiter can strand usable permits. I would broadcast or explicitly select eligible waiters, then add a queue if fairness matters. Waking a thread alone does not reserve its permit.

Likely follow up: How would a timeout remove a queued request without blocking every later ticket?

Out loudabout 60 s
"My 100 millisecond acquire sometimes takes several hundred milliseconds. What do you check before calling it a bug?"
What a strong answer covers
  • Check whether each wakeup restarts the full duration instead of using one budget
  • Use monotonic elapsed time or a fixed steady-clock deadline
  • Check the predicate while holding the lock at expiry and leave state unchanged on failure
  • Account for initial lock acquisition, lock reacquisition, and scheduler delay
  • A timeout is a waiting policy, not a hard real-time return guarantee
How a senior would say it
First I would check whether the implementation restarts a fresh hundred milliseconds after every wakeup. Three late wakeups can stretch that budget towards four hundred milliseconds. I would calculate one deadline on a monotonic clock, or subtract elapsed monotonic time from one original budget. Every wait uses only what remains. At expiry I check the predicate while holding the lock; a permit arriving near the deadline may make acquisition succeed, while failure leaves the count unchanged. Then I would inspect lock contention and scheduling. Our simple monitor can wait past its deadline while acquiring or reacquiring the mutex, and a ready thread may still be delayed by the scheduler. Timed initial locking can bound that part of the attempt, but it does not create a hard return deadline. So I would distinguish an incorrectly renewed budget from legitimate lock or scheduling delay.

Likely follow up: What should a zero timeout do when a permit is already available?

Out loudabout 60 s
"Why does opening a latch wake everyone, and why can its waiters safely read the results?"
What a strong answer covers
  • Zero is a permanent latch predicate that enables every waiter, so opening broadcasts
  • Countdowns and predicate checks share one mutex; notifications alone do not publish data
  • Writes before countdown reach successful waiters through the mutex synchronization chain
  • A failed timed wait does not promise completed results, and later writes need separate coordination
  • Keep C++ synchronization objects alive until every caller has finished
How a senior would say it
A latch reaching zero enables every waiter permanently, so the transition must wake everyone. Waking one can leave the others asleep forever because there may be no later notification. Visibility comes from synchronization, not from the wakeup itself. In our monitor, each worker writes its result before counting down under the common mutex. Unlock and later lock operations form a chain through the countdowns to the waiter's final locked check of zero. That makes those earlier writes visible after a successful wait, so three workers writing ten, twenty and thirty give each waiter a sum of sixty. A timed wait returning false does not promise complete results, and writes after countdown need separate coordination. For C++ I would also keep the latch alive until all callers finish. Notifying under the mutex closes one destruction race, but it does not replace ownership and joining.

Likely follow up: Could you reset the count to reuse this latch safely while old waiters are still waking?
