Keyed concurrency limiter

Build a primitivemedium40 minMicrosoftUber

One hot customer must not reserve the whole server while waiting for its own limit. Admit work against the global and per-key limits together.

The task

Limit in-flight calls to G overall and K for each string key. acquire waits for both limits to permit entry, then reserves both counters atomically. release returns one successful admission for that key; it may run on a different thread.

Keys compare by string value, including the empty string. Each successful call owns exactly one admission until released. Limiter instances are independent.

  • G and K must be positive; neither must be smaller than the other. Timeout is 0 to 86,400,000 milliseconds, inclusive. Invalid limits or timeouts throw IllegalArgumentException in Java or std::invalid_argument in C++. Failed calls leave both counts unchanged.
  • Zero timeout means one immediate attempt, even when the clock has a large value. A full limit returns false; a successful call reserves exactly one global and one key slot. Releasing a key with no outstanding admission throws IllegalStateException in Java or std::logic_error in C++, without changing any counts.
  • Java acquisition propagates InterruptedException, clears the interrupt flag and holds no permits when interrupted while waiting or when called with the flag already set. Pre-interruption wins even with free capacity and zero timeout. Keys and the supplied clock are non-null.
  • After a caller starts waiting, expiry at its deadline wins over a simultaneous newly available slot. Rechecking a condition never restarts the timeout.
  • The supplied clock is monotonic, thread-safe, nonthrowing and does not call back into the limiter. Values and differences fit in signed 64 bits. Production uses a monotonic clock; tests inject an atomic clock and wake sleepers through clockChanged() or a release notification after advancing it.
  • A saturated key must not consume a global permit while waiting. An eligible cold key can enter even if hot-key callers arrived earlier. Strict FIFO between all callers is deliberately not promised.
  • Run caller work outside the limiter lock. Pair successful acquisition with release in Java finally or a C++ RAII permit. Diagnostics expose counts, not permission to bypass admission.
  • inFlight() returns an exact snapshot of admitted calls. waitingCount() counts registered acquisition waiters; each successful, expired or interrupted waiter removes itself before returning or throwing. clockChanged() wakes all registered waiters to recheck the supplied clock and their predicates without changing capacity. These methods are thread-safe.

Example: with G = 2 and K = 1, one hot-key call and one cold-key call may overlap. Ten additional hot-key waiters must leave that cold-key slot available.

What the tests check

  • Independent limiter instances, both relative orderings of G and K, multiple admissions for one key, equal string keys, empty keys and immediate attempts at full capacity.
  • Invalid limits and timeout extremes throw the specified exceptions. Invalid and duplicate releases preserve capacity, other keys and subsequent reuse.
  • Non-expiring clock changes force predicate rechecks without restarting the budget. A released slot admits just before the deadline but loses to expiry at or after it, for both global and per-key waits.
  • Four hot-key waiters hold no global slots, a cold key bypasses them, and one clock change expires every waiter. A short timeout leaves a longer waiter able to acquire on release.
  • Release from a different thread, large clock values, exact waiter cleanup and capacity reuse after task exceptions. Java uses finally; C++ exercises RAII during stack unwinding.
  • Java pre-interruption and interruption while waiting propagate the exception, retain no permit and leave another waiter able to proceed.
  • Four admitted calls really overlap. Eight seeded callers check global and per-key limits under contention, with every worker exception observed.
  • Bounded joins and process watchdogs turn deadlocks or lost notifications into failures. Deadline tests use clock changes and waiter registration, not sleeps to order operations.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How does this become the reported Uber task throttler?
Queue tasks and launch one when both limits allow it. Completion and error callbacks both return the slot. Keep user callbacks outside the admission lock; a callback failure must not strand capacity.
How do retries and backoff from the Microsoft domain-limiter report fit?
Release the in-flight slot after each failed attempt, then wait for backoff outside the limiter. Reacquire for the next attempt and enforce a retry budget. A sleeping retry should not occupy execution capacity.
What changes across application servers?
A process-local count cannot enforce a global bound. The Microsoft report discusses a distributed semaphore. A coordinator needs atomic admission, lease expiry and a failure policy; a local mutex cannot solve that.
Can we add strict fairness?
Use per-key queues and choose among eligible heads. A single FIFO queue can cause head-of-line blocking when the oldest key is saturated but other keys can proceed.
How do cancellation and timeout differ from task failure?
A waiting caller owns nothing and simply leaves. An admitted caller must release once even if its task is cancelled or throws. An ownership token can make that distinction explicit.

The invariant and boundary

Under the monitor, total equals the sum of per-key counts, is at most G, and each key count is at most K. Checking the combined predicate and incrementing both counters is one linearization point. Release decrements both under the same lock and removes zero-count keys.

Waiting and time

The shared condition wakes callers whose predicates differ, so release broadcasts. Every caller checks both its own key and the global count. The reference records the clock at the start of waiting and subtracts elapsed time from the original budget. Injecting the clock makes the exact boundary test deterministic.

Real timed waits are a wakeup mechanism; the supplied monotonic clock decides expiry. An unchanged injected clock does not expire just because wall-clock time passes. Compute elapsed time rather than adding the budget to a clock value that may be near the largest signed integer.

The broken interleaving

One hot-key call occupies one of two global slots. The broken implementation reserves the second global slot before waiting for the same hot key's per-key slot. A cold-key caller now fails despite having no conflicting key. When the hot waiter times out, its partial reservation also leaks. The cold-key and accounting tests catch this partial reservation without relying on random scheduling.

Cost and pitfalls

Java map accounting is expected O(1); the reference C++ ordered map uses O(log A) for A active keys. Space is O(A) plus waiting threads.

Broadcast can wake many ineligible callers, so per-key conditions or eligible-waiter scheduling are useful follow-ups. The reference does not promise starvation freedom under an adversarial scheduler. Tests check eligible cold-key progress, not a particular waiter order.

The limiter cannot repair a caller that forgets release. In the harness the task failure occurs inside a cleanup scope, proving correct use of the API. Production code should wrap admissions in a permit object or task runner to make that pairing hard to forget.

How to say it in the interview

I will reserve the global and key capacity together under one lock. A waiter holds neither. It waits against one deadline, and release wakes callers to check their own predicates. That lets an eligible cold key proceed while a hot key is saturated.
