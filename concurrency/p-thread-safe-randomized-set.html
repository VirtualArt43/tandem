Thread-safe randomized set

Thread-safe structuresmedium40 minUberMicrosoftConfluent

A concurrent map alone cannot protect the array positions used by random sampling. Keep the whole representation consistent through every swap and removal.

The task

Make the LeetCode 380 data structure safe for concurrent callers. insert returns true only when a new integer is added; remove returns true only when a present integer is removed. getRandom returns each present value with equal probability, or an empty optional when the set is empty. Support all signed integer values.

  • The three operations must be linearizable. A random result must be a member at some instant during that call. A later removal does not retroactively invalidate a completed sample.
  • Use an array and a value-to-index map with expected amortized O(1) insert and remove and O(1) sampling. Do not copy or scan the set to sample. Hash collisions and resizing explain the expected amortized qualification.
  • The seeded pseudorandom generator is shared mutable state too; synchronize it or give each caller independent state. Exact output sequences need not match across languages.
  • validate() is a locked O(n) diagnostic that checks equal sizes and that every array slot maps back to its own index. size() is a synchronized snapshot. Allocation failure is outside the tested contract.

Example: insert 10, 20 and 30, then remove 10. If you move 30 into the hole, the map must change 30's index to zero before another call can observe the structure.

What the tests check

  • Empty behavior, duplicate insert, missing remove and swap-with-last index repair.
  • A removed value cannot reappear in a quiescent set; random samples never use an invalid index.
  • A seeded loose uniformity check over four stable values.
  • Eight active callers repeatedly insert, sample and remove, followed by the full array/map invariant check.
  • Twenty short concurrent histories are checked against a sequential set model respecting real-time call order.

Taught in: Invariants, critical sections and finding shared state

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How would you add DeleteRandom from the Uber report?
Choose an index and remove that exact entry under the same lock, using the same swap-and-repair helper. Calling getRandom and then remove separately permits another thread to remove or replace the chosen membership between them.
How would you limit getRandom to at most K callers, as in the Microsoft report?
Add an admission semaphore outside the representation lock and release it on every exit. Do not wait for a permit while holding the set lock. With a coarse mutex the implementation already serializes its short sampling critical section, so clarify what work the K limit is intended to cover.
What changes for a queue with getRandom, as in the Confluent report?
A queue additionally preserves FIFO order. Swap-with-last breaks that order, so use stable node identities and a separate sampling index or another representation that maintains both invariants atomically.
Can getRandom use a read lock?
Yes if its random-generator state is separately safe, and it holds the read lock through both bounds calculation and array access. Merely making the map concurrent still leaves the array unprotected.
How do you test that no removed value is returned?
Do not check contains after a concurrent getRandom returns: a valid value may already have been removed. Use quiescent phases or record call intervals and verify a legal sequential history, as this harness does.
Can you sample uniformly across shards?
Choose a shard in proportion to its size, then sample within it. Uniformly choosing shards biases values in small shards. Getting a consistent size-weighted choice under updates is a new synchronization problem.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The invariant and atomic operation

The array contains each present value once, and the map takes each value to its exact array index. One mutex protects both structures and the pseudorandom state. This prevents another caller from seeing the temporary hole or an outdated moved index. Sampling chooses an index and reads that slot while holding the same lock.

Why removal is constant time

Lookup finds the removed slot. Copy the last value there, repair its map index, pop the final array slot and erase the removed value. This sequence also works when the removed value was already last: its temporary updated index is erased before unlocking. Negative values are ordinary keys; an optional represents emptiness without stealing an integer sentinel.

The broken update

The broken version moves the last value but forgets to repair its index. From [10, 20, 30], removing 10 leaves [30, 20] while the map still points 30 to slot 2. A later removal can access beyond the array. The harness checks the representation immediately and stops safely after reporting that failure.

What the tests can establish

The long stress test checks representation integrity and exact insert/remove outcomes for independently owned values. The small-history checker adds a stronger semantic test: it enumerates sequential orders consistent with call intervals and accepts a sample only if it belongs to the model set at that point. This avoids the common incorrect test that checks membership after return.

All mutations serialize briefly; eight live test callers demonstrate contention, not simultaneous execution inside the critical section. Expected amortized work is O(1) per operation, space is O(n), and validation is O(n). The seeded frequency bound is intentionally loose and is a regression check, not a mathematical proof of uniformity.

How to say it in the interview

The invariant spans the array and the index map, so I will lock the complete operation. Removal swaps the last value into the hole and repairs its index under that lock. Random sampling holds the lock from size selection through the array read, and its generator state is protected too.
