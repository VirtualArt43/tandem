Virtual threads and coroutines

Java 21 virtual threads and C++20 coroutines make waiting cheaper, while CPU, memory and downstream limits still need explicit control.

Before this:Kernel threads, green threads and M:N schedulingSizing a pool

Thread pools exist because threads are expensive. Java 21's virtual threads and C++20's coroutines attack that cost from two directions. "What changes with virtual threads?" is a useful senior follow up, and the strong answer is mostly about what does not change.

In plain words

A platform thread is a full-time employee with their own desk. When they wait for a phone call, they sit at the desk doing nothing, and the office can only fit so many desks. A virtual thread is hot-desking: hundreds of workers share a few desks. Whoever is waiting for a call puts their papers in a folder and gets up; when the call comes, they sit at whichever desk is free and carry on exactly where they stopped.

A coroutine is a recipe card with a bookmark. You can stop at step 4, put the card on the shelf, and later anyone can pick it up and continue from the bookmark. The card is cheap; what you need is someone who decides which card to pick up next, a scheduler, and in C++ you bring that yourself.

What makes a thread expensive, and what cheap threads change

A platform thread maps one to one onto an operating system thread, with a stack reservation and kernel scheduling costs. Stack reservations are often of the order of megabytes, depending on the runtime and configuration; reserved address space is not the same as resident memory. There is no universal limit of a few thousand threads, but large populations of mostly idle OS threads can be expensive. Virtual threads and coroutines let many waiting tasks share fewer OS threads, as in kernel threads, green threads and M:N scheduling.

Java 21: virtual threads

A virtual thread is a java.lang.Thread that the JVM, not the operating system, schedules. Java 21 uses a dedicated FIFO-mode ForkJoinPool of platform carrier threads, separate from the common pool. Its target parallelism defaults to the number of processors available to the JVM, which need not equal the physical core count:

  • Mounting: to run, a virtual thread is mounted on a carrier, whose stack its frames use.
  • Unmounting: when it blocks in a JDK operation that supports it (socket reads and writes, Thread.sleep, BlockingQueue.take, ReentrantLock.lock, LockSupport.park), its stack frames are copied to the heap and the carrier is free to run another virtual thread.
  • Resuming: when the I/O completes or the lock is released, the virtual thread is scheduled again, on any carrier.

The code stays plain blocking code: for example, socket.getInputStream().read() can wait without occupying a carrier. Virtual threads are much cheaper than platform threads, but their stacks, task objects and request data still consume memory. The API supports one virtual thread per task: Thread.ofVirtual().start(r), Thread.startVirtualThread(r), and Executors.newVirtualThreadPerTaskExecutor(), whose close() waits for termination. Keep the executor in scope or join explicitly: virtual threads are daemon threads and do not keep the JVM alive.

C++20: coroutines

A C++20 coroutine is a function that can suspend and resume. Using co_await, co_yield or co_return in a function body makes it a coroutine, subject to language restrictions such as no coroutine constructors. Its frame preserves parameters and local state needed across suspension. The frame is typically allocated dynamically, though allocation can be elided; a suspended coroutine does not need to occupy an OS thread. C++20 supplies only the machinery:

  • The promise type, normally the return type's nested promise_type and formally selected by std::coroutine_traits, controls initial suspension, final suspension, return values and exceptions.
  • co_await x obtains an awaiter, possibly through the promise's await_transform and an operator co_await. It calls await_ready() first. If false, it suspends and calls await_suspend(handle): a void result leaves it suspended, false resumes it immediately, and a coroutine handle transfers execution to that coroutine. await_resume() supplies the result or throws. An await need not suspend or change threads.
  • <coroutine> provides std::coroutine_handle, std::suspend_always and std::suspend_never. There is no task type, no scheduler and no async I/O in the C++20 standard library. C++23 adds std::generator, a synchronous generator. For async work you use a library (Boost.Asio's awaitable and co_spawn, cppcoro, folly's coro::Task, the std::execution reference implementation) or write a small scheduler yourself, as below.

Both programs below start 10,000 tasks that each wait 100 ms to simulate I/O latency. With a 1 MB stack reservation, 10,000 platform threads would reserve roughly 10 GB of address space, not necessarily RAM. A pool of 100 processes 100 batches, an idealized ten seconds. Overlapping all the waits instead takes roughly one wait plus task creation, scheduling and timer overhead; measure it rather than promising a fixed speedup.

Task starts eagerly and destroys its frame on completion because final_suspend() returns std::suspend_never. The loop owns pending timer handles, pops each before resuming it, and destroys any still pending at shutdown. It must never resume or destroy a completed handle again.

This timer-only loop is confined to one thread, so the ordinary done counter is safe. It has no concurrent submission, result propagation or cooperative cancellation, and an uncaught coroutine exception deliberately terminates the process. Real libraries integrate sockets and timers and define ownership and cancellation; adding worker threads also requires synchronized queues and protection against concurrent resumption of the same coroutine. C++17 has no standard coroutine syntax: use callbacks and an event loop or a bounded worker pool.

Stackful and stackless

A virtual thread is stackful: a supported blocking operation deep in an ordinary call stack can suspend the whole virtual thread. A C++20 coroutine is stackless: its suspension points belong to its own body, including co_await, co_yield and initial or final suspension. A plain helper cannot suspend its caller's stack. Helpers may still return awaitables or do synchronous work without being coroutines; what must propagate through the asynchronous call chain is an awaitable result. This is often called function coloring. Go's goroutines are stackful, with small growable stacks.

Pinning, and its C++ cousin

A virtual thread cannot always unmount. In Java 21, it is pinned to its carrier when it blocks while inside a synchronized block or method, or inside a native call. A pinned virtual thread blocks its carrier, so the JVM has one fewer carrier for everyone else; if all carriers are pinned, no other virtual thread runs. JDK 24 removed the synchronized case (JEP 491), so on 24 and later only native frames and a few rare cases still pin. On Java 21 the advice is: do not block inside synchronized; use ReentrantLock around blocking I/O, and find pinning with the JFR event jdk.VirtualThreadPinned or the -Djdk.tracePinnedThreads=full system property.

Not every carrier-blocking operation is classified as pinning. In Java 21, many filesystem operations and Object.wait() can also retain a carrier; the scheduler compensates for supported cases by temporarily adding carriers, up to its configured maximum. It does not compensate for pinning by increasing parallelism. Diagnose the blocking operation rather than assuming every wait unmounts. JFR pinning events have a duration threshold, so absence of an event alone does not prove absence of pinning.

C++ has the same trap in a different shape: a coroutine that makes a blocking call blocks its scheduler thread, and with it every coroutine scheduled there, which on an event loop means every connection it serves. std::this_thread::sleep_for instead of co_await loop.sleep, or a blocking socket read inside an event loop coroutine, freezes the whole loop.

The Java blocks are alternative implementations, inside a method that propagates IOException and InterruptedException; migrate every access to the same lock consistently. ReentrantLock avoids this pinning case but still serializes the protected operation. Ideally take a snapshot under the lock, perform I/O outside it, then validate before publishing the result.

Do not pool them; limit with semaphores

With cheap threads, the thread itself is no longer the scarce resource, so never put virtual threads in a fixed pool to "limit" them: a pool of 100 virtual threads brings back the queue, the sizing problem and the self-deadlocks, and gains nothing. Create one per task. But the things a pool used to protect are still scarce: the database still takes 50 concurrent queries, the downstream still has a rate limit, memory is still finite. Those limits move from the pool size to explicit limiters, usually a semaphore per dependency (Semaphores).

Here the sleeps simulate query latency, not synchronization, and the reported peak can be below ten on a particular run. A virtual thread waiting in acquire() usually releases its carrier, but still retains request memory: parked threads form a queue that needs an admission bound and deadlines. In C++, this semaphore blocks a platform thread. Coroutine libraries need asynchronous semaphores whose waits suspend instead of blocking the scheduler.

Structured concurrency

Thread-per-task makes it easy to lose track of work: a handler forks two subtasks, one fails, and the other keeps running after the handler returns. Structured concurrency ties subtask lifetimes to a scope, with a policy for joining and cancelling siblings. Java 21's java.util.concurrent.StructuredTaskScope is a preview API, requiring preview support at compilation and execution. This example uses its Java 21 API; later versions may differ. C++20 has no standard equivalent, so check your library's joining and cancellation guarantees.

Java

ShutdownOnFailure requests cancellation by interrupting unfinished subtasks; it cannot force arbitrary work to stop. join() can return after shutdown while a sibling is still unwinding, and close() waits for that sibling to terminate. A task that ignores interruption can therefore delay scope exit indefinitely. Bound downstream calls with timeouts as well as requesting cancellation.

Worked example: moving a service to virtual threads

A Java service handles requests on a 200 thread pool and calls three downstreams: a database (healthy up to 60 concurrent queries), a pricing service (rate limited) and an image resizer on the same machine (CPU heavy). At peak it queues, and raising the pool past 200 made the database slower.

  1. Requests: switch to newVirtualThreadPerTaskExecutor() (or the server framework's virtual thread mode), one virtual thread per request. Keep an admission limit at the front door, so overload is rejected rather than parked forever.
  2. Database: a semaphore of 60 around queries (and a connection pool of 60), with a timed tryAcquire so callers fail fast instead of piling up.
  3. Pricing: a token bucket matching its requests-per-second limit, plus a separate concurrency cap if needed. A semaphore alone does not enforce a rate.
  4. Resizing: keep a fixed platform thread pool sized to the cores, because virtual threads do nothing for computation.
  5. Audit: on Java 21, replace synchronized around blocking calls with ReentrantLock and check JFR for pinning events; look for large per-thread ThreadLocal caches.

The result: explicit admission, database concurrency, pricing rate and CPU limits. The old request pool imposed only a coarse concurrency cap; it never guaranteed the pricing service's rate limit.

Common mistakes

  • Pooling virtual threads to limit concurrency. Limit resources with semaphores and bound admission; create one virtual thread per admitted task.
  • Expecting speedups for CPU-bound work. A million tasks cannot increase the machine's CPU capacity; hardware threads and workload characteristics determine how many instructions actually progress.
  • Unbounded fan-out. Cheap threads make it trivially easy to send 50,000 concurrent queries to a database that takes 50.
  • Blocking inside synchronized on Java 21 (pinning), or blocking inside a C++ coroutine (stalls its scheduler).
  • C++: reference parameters in a coroutine. The frame stores the reference, not the object. Pass a temporary std::string to a const std::string& parameter, suspend, and on resume the reference dangles. Take parameters by value in coroutines that suspend.
  • C++: assuming the standard library gives you a task type or a scheduler. C++20 gives you the machinery only.

In the interview

Prepare for follow ups after building or sizing a pool: "would virtual threads change this?", "do we still need a thread pool?", "how is this different from Go?", or "how would coroutines help here?". The research includes a 2026 Apple report with Java 21 virtual-thread questions and a candidate using them in a parallel-sum answer. Be ready to defend when they help.

Virtual threads make waiting cheaper: supported blocking operations can unmount them from their carriers, so I can use a thread per request and plain blocking code for I/O-bound work. The database still has the same capacity, so I put a concurrency limit around it and admission control at the edge. Substantial CPU work goes to a bounded executor sized from available CPU capacity. On Java 21 I would watch for blocking inside synchronized, a pinning case removed in JDK 24. In C++ I would use coroutines with a library scheduler. Awaitable results must propagate along the asynchronous call chain; ordinary helpers can still return awaitables.

Follow ups: "What is a carrier thread?", "What is pinning and how do you detect it?", "Why not pool them?", "Stackful versus stackless?", and "Are virtual threads preemptive?" (Java 21 does not time slice virtual threads; a long computation can keep its carrier, though the OS still schedules that carrier).

Senior depth

The concurrency limit moves; it never disappears. With 200 workers, at most 200 handlers execute at once, but a submission queue can still grow without a bound. With unlimited virtual threads and no semaphore, the same slowdown produces 50,000 parked virtual threads, each holding request memory, and the database drowns under 50,000 queries. Cheap threads make overload easier to create, so admission control and per-dependency limits matter more, not less.

Fairness. Java 21 has no virtual-thread time slicing; the OS can preempt a carrier without freeing it to run a different virtual thread. A coroutine that never reaches a suspending await similarly monopolizes its event loop. Even co_await may complete synchronously, so a tight loop of ready awaits need not yield. Isolate substantial CPU work on a bounded executor.

Ownership across suspension. Do not hold a thread-owned std::mutex lock across co_await: resuming on another thread cannot legally unlock it, and on one loop another coroutine may block the only thread trying to acquire it. Keep borrowed objects and coroutine-lambda closures alive until completion, or pass owned values as parameters. A library's cancellation request must unregister pending I/O safely before destroying its frame.

Go comparison. Goroutines are also stackful and support asynchronous preemption since Go 1.14. Bounded worker pools or semaphore channels still protect downstream resources; a lightweight task model does not remove overload.

Key takeaways

  • Virtual threads can unmount during supported blocking operations, making waiting cheaper without eliminating memory costs.
  • C++20 coroutines are stackless functions that suspend at co_await; the standard gives the machinery, not a task type or scheduler.
  • Pinning (blocking in synchronized on Java 21, fixed in JDK 24) and blocking calls inside coroutines both stall the shared runtime threads.
  • Do not pool virtual threads; limit scarce resources with semaphores and admission control.
  • Cheap threads change thread count and code style, not CPU limits, downstream limits, or the rules for races and deadlocks.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Requests run one per virtual thread or coroutine task. Which mechanism directly enforces at most 100 simultaneous database queries, independently of request scheduling?
Why. The scarce resource is the database, so limit exactly that, with a semaphore (an asynchronous one for coroutines). Carrier and scheduler threads can multiplex many in-flight queries, so their count does not bound query concurrency. A rate limiter bounds arrivals per unit time, not simultaneous outstanding queries.
Eight platform workers already saturate eight available CPU execution slots with independent computations. You replace them with a million virtual threads or coroutine tasks. What can you conclude without benchmarking?
Why. With the available CPU capacity already saturated, multiplying tasks cannot multiply execution capacity. Virtual threads and coroutines can execute CPU work, but scheduling and allocation may add overhead. Exact relative performance is workload dependent, so neither a fixed speedup nor a fixed slowdown follows.
Which of these can suspend from inside an ordinary (non-async) function that it calls, deep in its call stack?
Why. Virtual threads and goroutines are stackful: supported blocking operations can suspend them deep in ordinary calls. A C++20 coroutine is stackless: its suspension points preserve its own frame, not an ordinary helper's arbitrary call stack. A helper can return an awaitable, but the caller must await it at its own suspension point.
Many coroutines share one event loop thread. One of them calls a blocking function that sleeps for 2 seconds instead of awaiting an asynchronous sleep. What happens?
Why. A coroutine only gives up execution at a suspending coroutine operation; a normal blocking sleep is not one. A blocking call holds the scheduler thread, and nothing else scheduled on it can run. It is the C++ cousin of a pinned virtual thread, and the reason async code must use async versions of sleeps, I/O and locks.
A shared int count starts at zero. Ten thousand virtual threads, or C++ coroutines running on several threads, each do count += 1. After joining all work, is printing 10,000 guaranteed?
Why. Virtual threads are real threads to the memory model and run in parallel on several carriers. Coroutines on a multi-threaded scheduler run in parallel too (only a single-threaded loop serializes them). Joining waits for termination but does not make the increments atomic. Java volatile does not fix the compound update; C++ volatile is not thread synchronization. Use an atomic or a lock.
Java onlyOn Java 21, a virtual thread reads from a socket while inside a synchronized block. What happens while it waits for data?
Why. In Java 21 to 23, a virtual thread cannot unmount while it holds a monitor, so blocking I/O inside synchronized blocks the carrier. JEP 491 in JDK 24 removed this case. On 21, use ReentrantLock around blocking calls, and detect pinning with the jdk.VirtualThreadPinned JFR event.
C++ onlyTask log(const std::string& msg) first does co_await loop.sleep(10ms) and then prints msg. It is called as log("started " + name);. Assume it suspends and resumes after the calling statement finishes. What is wrong?
Why. Coroutine parameters are copied into the frame by their declared type, so a reference parameter stores a reference. The temporary dies at the end of the full expression, while the coroutine is still suspended. Take parameters by value in coroutines that suspend.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "Now that we have virtual threads, do we still need thread pools?" Answer as a senior engineer.
Model answer

For I/O-bound work, mostly not as thread caches: a virtual thread per task is cheap, and supported blocking operations can unmount it instead of holding an OS thread, so I would use newVirtualThreadPerTaskExecutor rather than size a 200-thread pool. But a pool did two jobs, caching threads and limiting concurrency, and virtual threads only remove the first. The limits move to explicit tools: a semaphore or connection pool per downstream, rate limiters, and admission control at the edge, because otherwise a slowdown turns into tens of thousands of parked requests hammering the database. For substantial CPU work I would use a bounded executor sized from available CPU capacity, because virtual threads add no computing capacity and Java 21 does not time slice them. On Java 21 I would also check for pinning, blocking inside synchronized, which JDK 24 fixed.

Write code
Limit concurrent calls to a downstream to 20 in a thread-per-task design, and shed load: a caller that cannot get a permit during a 50 ms wait reports overload rather than waiting indefinitely.
Model answer

Why: the semaphore limits the dependency, not the threads, so it works the same with virtual threads, platform threads or any other caller. The timed acquire bounds the requested permit wait, though scheduling may delay the return and the downstream call needs its own timeout. In C++, try_acquire_for may also fail spuriously; treating that as overload is acceptable here. Admission control still bounds the number of simultaneous waiters, and releasing in finally (or a destructor) guarantees a failing call cannot leak a permit. With C++ coroutines on an event loop, the same design needs an asynchronous semaphore so waiting suspends instead of blocking the loop.

Design
Compare a Java service on virtual threads with a C++ service on coroutines (an event loop library) for 50,000 mostly idle WebSocket connections that occasionally do a database lookup. Where does each one keep the state of an idle connection, and what must each be careful about?
Model answer

Java: one virtual thread per connection, blocked in a socket read. Idle state is the virtual thread's stack frames, copied to the heap while unmounted, plus the connection's buffers; whether 50,000 fit must be measured from live stack depth, request objects, buffers, heap limits and file-descriptor limits. Care points: no pinning (on Java 21, no blocking inside synchronized), a semaphore around database lookups, bounded per-connection buffers, and no large ThreadLocal caches.

C++: one coroutine per connection, suspended on the library's asynchronous socket-read awaitable. Idle state includes coroutine frames, library operation state and buffers; its size depends on the application, and a few event loop threads serve everyone. Care points: awaitable results must propagate through the asynchronous call chain, nothing may block an event loop thread (database calls must be asynchronous or moved to a separate thread pool), parameters must not be references to temporaries, and if the loop runs on several threads, shared state needs locks or a strand (serialized execution) per connection.

Both avoid dedicating an OS thread to every idle connection; both still need explicit limits on the database and on memory per connection.

How a senior would say it
I would first restore explicit limits around the database and request admission. Virtual threads make waiting cheaper; they do not let the database execute more queries. The old worker pool may have accidentally limited concurrent calls. Removing it can turn a burst into thousands of outstanding queries and parked requests, each retaining memory. I would measure safe database concurrency, then enforce that with a semaphore or connection pool. Permit acquisition needs a deadline, queries need their own timeout, and permits must be released even after failure. Admission control should bound the total waiting population and reject excess work early. If the dependency also has a requests-per-second limit, I need a rate limiter as well; a semaphore alone does not provide it. Next I would check Java 21 pinning around blocking calls using JFR, and move substantial computation to a bounded CPU executor. I would keep one virtual thread per admitted request, then load-test throughput, tail latency and memory. Increasing carrier count alone cannot repair an overloaded database.

"Compare a Java virtual thread with a C++20 coroutine. What would you review before putting either into a server?"
What a strong answer covers
  • Virtual threads preserve an ordinary call stack and can unmount on supported blocking calls
  • C++20 coroutines preserve a frame and suspend at their own suspension points
  • The C++ library must supply scheduling, I/O and ownership; awaits may complete inline
  • Blocking calls, pinning and long computation can occupy shared runtime threads
  • Review lifetime across suspension, lock ownership, cancellation and resource limits
How a senior would say it
A virtual thread lets me keep ordinary blocking code; a C++ coroutine needs an asynchronous protocol supplied by a library. In Java, a supported socket read can suspend a virtual thread deep inside ordinary helper calls. Its stack is preserved and its carrier can run another task. Java 21 has exceptions, including monitor pinning and some operations that retain a carrier. A C++20 coroutine instead preserves its own frame. It suspends at its own explicit or implicit suspension points, not inside an arbitrary ordinary helper. Helpers can still return awaitables without themselves being coroutines. The standard supplies coroutine machinery, but no general task type, scheduler or asynchronous socket API. An await can also complete immediately, so its presence does not prove that execution yielded. In review, I would look for blocking calls on event loops, lengthy CPU work, and locks held across suspension. I would check who owns the frame and every referenced object, who may resume it, and how cancellation removes pending work before destruction. Passing a temporary through a reference parameter is a classic dangling-reference bug. Finally, both designs need bounded admission, dependency limits and synchronization for shared mutable state. Cheap suspended tasks do not make memory or downstream capacity unlimited.

Likely follow up: Why is holding a std::mutex guard across co_await unsafe even when the coroutine body looks sequential?
