1Corememory-modelcpp
Explain the C++ memory model in about a minute.
Model answer

Since C++11 the standard defines threads and a memory model. Memory is made of memory locations: each scalar object, or a run of adjacent bit-fields. Two accesses conflict if they touch the same location and at least one writes. A data race is two conflicting accesses from different threads, at least one not atomic, with neither happening before the other, and a data race is undefined behavior.

The ordering relations:

  • Sequenced-before: program order within one thread.
  • synchronizes-with: a release operation (an atomic store with release or stronger, or a mutex unlock) synchronizes with an acquire operation that reads that value (an atomic load with acquire or stronger, or the next lock of that mutex). Creating a std::thread synchronizes with the start of its function, and the thread's completion synchronizes with the return from join.
  • Happens-before: built from the two above, and transitive.

Atomics default to memory_order_seq_cst. The headline guarantee is SC for DRF: a program with no data races that uses only seq_cst atomics behaves as if every thread's operations were interleaved in a single order. Weaker orders trade that simplicity for speed.

Likely follow up: "Two threads write two different bit-fields of the same struct. Is that a race?" Yes, if they are adjacent bit-fields in the same memory location. Separate them with a non-bit-field member or a zero-width bit-field, or protect them with one lock.

2Coredata-raceundefined-behaviorcpp
Why is a data race undefined behavior in C++, and what can actually happen?
Model answer

The compiler optimizes each thread as if no other thread touches non-atomic variables between synchronization points. A race breaks that assumption, so the standard declines to say what happens. In practice:

  • Hoisting: in while (!done) {} on a plain bool, the load can be hoisted out of the loop, giving an infinite loop.
  • Tearing: a 64-bit value on a 32-bit target, or any struct, can be read half old and half new.
  • Invented or merged stores: the compiler may write a variable speculatively, combine two writes, or write adjacent fields with one wider store.
  • Re-reads: a value checked once (a bounds check) may be loaded again for its use, and the second load can see a different value.
  • Reordering: writes can become visible to another thread in a different order.

There are no benign data races in C++. If you truly need no ordering, use std::atomic with memory_order_relaxed. It usually compiles to the same instructions, but it is defined, and ThreadSanitizer stops reporting it.

Likely follow up: "How is that different from Java?" A racy Java program is not undefined: it can see stale or reordered values (and a torn non-volatile long or double, which the JLS allows), but it cannot crash the JVM or see values out of thin air.

3Seniormemory-ordercpp
Explain the memory orders: seq_cst, acquire, release, acq_rel and relaxed.
Model answer
  • relaxed: the operation is atomic, and each variable has a single modification order, but nothing else is ordered. Use it for counters and statistics.
  • release (on stores): every write this thread made before the store becomes visible to a thread whose acquire load reads the stored value.
  • acquire (on loads): later reads and writes cannot move before it. A matching release and acquire pair creates synchronizes-with.
  • acq_rel: both, for read-modify-write operations such as fetch_add, exchange and compare-exchange.
  • seq_cst: acquire and release, plus one total order over all seq_cst operations that every thread agrees on. It is the default.
  • consume: meant for dependency ordering; compilers treat it as acquire, and it is best avoided.

On x86, acquire loads and release stores are plain moves, because the hardware already gives those orderings; only a seq_cst store costs extra (an xchg, or a move plus mfence). On ARM the orders map to different instructions and the differences are real, so code that "works on x86" with too-weak orders can fail on ARM.

Likely follow up: "Which order would you write by default?" seq_cst. Weaken it only with a measured reason and a written argument for why the weaker order is enough.

4Seniormemory-orderrelaxedreference-countingcpp
When is memory_order_relaxed enough? Use reference counting as the example.
Model answer

Relaxed is enough when the atomic's own value is all that is communicated, and no other memory depends on seeing it in order: statistics counters, a unique id from fetch_add, a hint flag.

Reference counting, as inside std::shared_ptr, shows both sides:

  • Increments can be relaxed. A thread can only increment if it already holds a reference, so the object is alive, and an increment publishes nothing.
  • Decrements cannot. Each owner's earlier uses of the object must happen-before the final destroy. So every decrement is a release, and the thread that drops the count to zero does an acquire before destroying, to see every other owner's last use.

Using memory_order_acq_rel on every decrement is also correct and simpler. The fence version only pays for the acquire once, on the final decrement.

Likely follow up: "What breaks if the decrement is relaxed?" Thread A writes to the object and drops its reference; thread B drops the last reference and destroys the object. Without release and acquire there is no happens-before between A's last use and B's destroy: A's reads and writes of the object may effectively happen after its decrement, so B frees memory that A is still touching. That is a data race and a use after free.

5Seniorstore-bufferingseq-cstcpp
Show a case where acquire and release are not enough and you need seq_cst.
Model answer

The store-buffering pattern, the core of Dekker's and Peterson's algorithms:

Release orders a store after earlier operations, and acquire orders a load before later ones, but nothing stops a store from moving after a later load. Each thread's store can sit in its core's store buffer while its load runs, so both threads read 0. This happens on real x86 hardware.

With seq_cst on all four operations, every thread agrees on one total order of them. Whichever store comes first in that order is seen by the other thread's load, so (0, 0) is impossible. A std::atomic_thread_fence(std::memory_order_seq_cst) between the store and the load in each thread has the same effect.

The pattern appears wherever two sides each set "I am here" and then check the other: hand-written mutual exclusion, hazard pointers (publish the hazard, then re-read the shared pointer), and sleep protocols where a waiter sets "I am sleeping" and then rechecks for work while a waker sets work and then checks for sleepers.

Likely follow up: "What does seq_cst cost on x86?" Loads are free; each seq_cst store becomes an xchg or a store plus mfence, which costs tens of cycles (order of magnitude) because it drains the store buffer.

6CorevolatilecppNvidia
What does volatile mean in C++, and why is it not a tool for threads?
Model answer

volatile tells the compiler that every access is an observable side effect. Each read and write must actually happen, in program order relative to other volatile accesses, and may not be cached in a register or removed. It exists for memory-mapped hardware registers, for variables shared with a signal handler (volatile std::sig_atomic_t), and for locals that must survive longjmp.

It is not for threads:

  • No atomicity: v += 1 on a volatile int is still a read-modify-write, and a wide type can tear.
  • No ordering with respect to ordinary, non-volatile accesses.
  • No hardware fences, so the CPU can still reorder.
  • A conflicting concurrent access to a volatile non-atomic object is still a data race, and so undefined behavior.

Use std::atomic instead. One vendor exception: MSVC on x86 and x64 defaults to /volatile:ms, which gives volatile accesses acquire and release semantics as an extension; on ARM it defaults to /volatile:iso. Portable code must not rely on it.

Java's volatile is a different thing with the same name: there it is a real synchronization tool, much closer to a seq_cst std::atomic for that one variable.

Likely follow up: "Does volatile at least stop the compiler from hoisting a loop read?" Yes, but it still gives no ordering with the data the flag is meant to publish, and the race is still undefined behavior. An atomic gives you both properties, defined.

7Corestd-threadlifecyclecpp
What are the rules for destroying a std::thread?
Model answer

A std::thread is joinable while it represents a thread of execution that has not been joined or detached, even one that has already finished. Destroying or move-assigning over a joinable std::thread calls std::terminate. Before it dies you must join() (wait for it) or detach() (let it run on its own).

The trap is exceptions: if anything between creation and join throws, the destructor runs on a joinable thread and the process terminates.

More rules: a moved-from thread is not joinable; joining a thread that is not joinable throws std::system_error; arguments are copied into the new thread, so references need std::ref and lifetime care. Detaching is risky: the thread may outlive the locals or this it uses, and at program exit, static objects can be destroyed while detached threads still use them. Before C++20, write a small guard class that joins in its destructor.

Likely follow up: "Why did the committee choose terminate rather than an implicit join or detach?" An implicit join can hang during exception unwinding, and an implicit detach leaves a thread with dangling references. Both are worse than a loud failure, and std::jthread later made joining the explicit default.

8Seniorjthreadstop-tokencpp
How do std::jthread and std::stop_token work?
Model answer

A std::jthread, std::jthread (C++20), is a thread plus a stop source plus a joining destructor. If the callable takes a std::stop_token as its first parameter, the jthread passes its own token in. request_stop() flips the shared stop state (returning true for the first request), and the thread polls stop_requested().

A blocked thread cannot poll, so two tools wake it:

  • std::stop_callback registers a function that runs when stop is requested: on the requesting thread, or immediately on the registering thread if stop was already requested. Use it to close a socket or notify a condition variable.
  • std::condition_variable_any has wait overloads that take a stop token and return when stop is requested, still checking the predicate.

The destructor calls request_stop() and then join(), so a forgotten join no longer terminates the program, and a cooperative worker exits promptly.

Likely follow up: "Why condition_variable_any and not condition_variable?" Only condition_variable_any has the stop-token overloads. With plain condition_variable, put a stopping flag in the predicate and notify_all after setting it.

9Seniorstd-asyncfuturescpp
What are the pitfalls of std::async?
Model answer
  1. The default policy is std::launch::async | std::launch::deferred, so the implementation may defer: the task then runs lazily inside get() or wait(), on the caller's thread, and nothing runs concurrently. On a deferred future, wait_for keeps returning future_status::deferred, so a loop waiting for ready never ends. Pass std::launch::async when you want concurrency.
  2. The future from std::async blocks in its destructor until the task finishes (when the task really launched asynchronously and this is the last future sharing its state). Ignore the return value and the temporary future is destroyed at the end of the statement, so the "asynchronous" call is synchronous. C++20 marks std::async [[nodiscard]], so compilers now warn about exactly this line.
  3. No pool is promised. libstdc++ and libc++ start a new thread for every launch-async call, so thousands of tiny tasks mean thousands of threads; MSVC runs them on a Windows thread pool.
  4. Exceptions are stored and rethrown by get(), which may be called only once; after it, valid() is false. Use std::shared_future when several threads need the result.
  5. Arguments are copied, as with std::thread; references need std::ref and lifetime care.

Only futures that come from std::async block in their destructor. Futures from std::promise or std::packaged_task do not, which is one reason to build on those for anything serious.

Likely follow up: "What would you use instead for many small tasks?" A fixed thread pool whose submit wraps each task in a std::packaged_task and returns its future.

10Corecondition-variablecpp
What are the rules for using std::condition_variable correctly?
Model answer
  • Wait with a std::unique_lock<std::mutex> on the mutex that guards the predicate's state. std::condition_variable works only with that exact lock type; std::condition_variable_any accepts any lockable.
  • Always wait with a predicate (or in a while loop), because wakeups can be spurious or stolen.
  • Change the predicate's state while holding the mutex, even if the variable is atomic, or you can lose a wakeup.
  • notify_one and notify_all may be called with or without the mutex held. Notifying after unlocking avoids waking a thread straight into a locked mutex; the state change itself must still happen under the lock.
  • Use notify_one only when every waiter waits for the same predicate and any one of them can make progress; otherwise notify_all, or separate condition variables per predicate.
  • For timeouts, wait_until with a std::chrono::steady_clock deadline, or wait_for. With a predicate they return the predicate's final value.
  • Do not destroy a condition variable while threads still wait on it.

Likely follow up: "What does cv.wait(lk, pred) expand to?" while (!pred()) cv.wait(lk);, where each inner wait atomically releases the mutex, blocks, and reacquires the mutex before returning.

11Seniorlost-wakeupcondition-variablecpp
Why must you change the predicate under the mutex even when the variable is a std::atomic?
Model answer

Because the waiter's check and its sleep are only atomic with respect to threads that take the same mutex. A signaler that skips the mutex can slip between them:

With the mutex, the signaler cannot change ready while the waiter holds m, and the waiter holds m from its check until wait releases it atomically as it goes to sleep. The store therefore lands either before the check, so the waiter sees true, or after the waiter is asleep, so the notify wakes it. Even an empty lock and unlock of the mutex between the store and the notify closes the window.

The atomic is not wrong, merely insufficient: it makes the flag itself race-free, but the protocol needs the check and the sleep to be atomic as a pair, and only the mutex provides that.

Likely follow up: "Notify inside or outside the lock?" Both are correct once the state change is under the lock; outside avoids a wasted wakeup. Notify inside if the waiter might destroy the condition variable right after waking, for example when the condition variable lives in an object the waiter frees.

12Seniorshared-ptratomicscpp
Is std::shared_ptr thread-safe? What does std::atomic<std::shared_ptr<T>> add?
Model answer

There are three levels to keep apart:

  1. The control block's reference count is updated atomically, so different shared_ptr objects that share one pointee can be copied, assigned and destroyed concurrently from different threads. That is safe.
  2. One shared_ptr object (one variable), read by one thread while another assigns or resets it, is a data race and undefined behavior. Copying from a shared global while another thread replaces it is the classic bug.
  3. The pointee is not protected at all. Concurrent mutation of the T needs its own synchronization.

std::atomic<std::shared_ptr<T>> (C++20) makes the variable itself atomic: load returns a safe copy while store, exchange and compare-exchange replace it. It is typically not lock-free (implementations use an internal lock or spin bit), so check is_lock_free() if it matters. Before C++20, the free functions std::atomic_load and std::atomic_store overloaded for shared_ptr did the same job; they are deprecated in C++20. Library support lags: Apple's libc++ does not provide std::atomic<std::shared_ptr> at the time of writing, so on a Mac the snippet above does not compile, and you use the free functions or a mutex around the pointer.

The classic use is a read-mostly snapshot: readers load and keep their version alive through the reference count, and writers build a new object and store it.

Likely follow up: "Does that solve memory reclamation for a lock-free structure?" Yes, the reference count does, but since the atomic is usually not lock-free, the structure is not truly lock-free either.

14Coremutex-typesraiicpp
Which mutex and lock types does C++ provide, and when do you use each?
Model answer

Mutexes:

  • std::mutex: not recursive. Locking it again from the owning thread, or unlocking it from another thread, is undefined behavior.
  • std::recursive_mutex: the owner may lock again. Legal, but it usually hides a design problem.
  • std::timed_mutex and std::recursive_timed_mutex: add try_lock_for and try_lock_until.
  • std::shared_mutex (C++17) and std::shared_timed_mutex (C++14): exclusive and shared modes.

RAII locks:

  • std::lock_guard: the simplest scope lock.
  • std::scoped_lock (C++17): one or several mutexes at once, with deadlock avoidance. The default choice.
  • std::unique_lock: movable, can defer, try, adopt, unlock early and relock. Required by std::condition_variable.
  • std::shared_lock: shared ownership of a shared_mutex.

Use scoped_lock or lock_guard by default, unique_lock for condition variables and flexible locking, and shared_mutex only for read-heavy data where reads really overlap; for short critical sections its bookkeeping often costs more than it saves.

A classic trap: always give the guard a name. std::lock_guard<std::mutex>{m}; creates a temporary that unlocks at the end of the statement, and std::unique_lock<std::mutex>(m); declares a new, empty lock called m that protects nothing. Both compile; clang at least warns about each, so read your warnings.

Likely follow up: "How do you lock two mutexes before C++17?" std::lock(a, b); followed by std::lock_guard<std::mutex> la(a, std::adopt_lock); and the same for b.

15Stretchcompare-exchangeabalock-freecppRubrik
compare_exchange_weak versus compare_exchange_strong, and what are ABA and the memory reclamation problem?
Model answer

compare_exchange_strong(expected, desired) fails only if the current value differs from expected, and on failure it writes the current value back into expected. The weak form may also fail spuriously when the values are equal, because on load-linked and store-conditional hardware a context switch or cache event can break the reservation. Inside a retry loop that does not matter, and weak can be cheaper; for a one-shot check use strong.

Pop is where trouble starts. ABA: thread 1 reads head A and its next B; thread 2 pops A, pops B, frees B, and pushes A back at the same address; thread 1's CAS from A to B succeeds, and the head now points at freed memory. The deeper issue is memory reclamation: a popped node cannot be freed while another thread may still be reading it. The fixes:

  • Tagged pointers: a version counter next to the pointer, updated with a double-width CAS.
  • Hazard pointers: each thread publishes the pointers it is reading, and a node is freed only when no hazard points at it.
  • Epoch-based reclamation or RCU: free a node only after every thread has passed a quiescent point.
  • Reference counting, for example through std::atomic<std::shared_ptr>, which is usually not lock-free.

In Java the garbage collector solves reclamation, so ABA cannot happen with freshly allocated nodes, only with recycled objects or plain values.

Likely follow up: "Why release on a successful push?" So a thread that pops the node and reads its value sees the value written before the push.

16Corecpp20latchbarriersemaphore
What did C++20 add for synchronization, and what do you use in C++17?
Model answer

C++20 added:

  • std::latch: a one-shot countdown (count_down, wait, arrive_and_wait).
  • std::barrier: reusable phases, with an optional completion function run by the last thread to arrive.
  • std::counting_semaphore and std::binary_semaphore: acquire, release, try_acquire_for.
  • std::atomic::wait, notify_one and notify_all: block until an atomic's value changes, which is futex-style waiting without a mutex.
  • std::jthread and std::stop_token, std::atomic_ref (atomic operations on a plain object), and std::atomic<std::shared_ptr>.

In C++17, build them from a mutex and a condition variable: a latch is a counter and a condition, a semaphore is a permit count and a condition, and a reusable barrier needs a generation number. C++17 itself already offers std::shared_mutex and std::scoped_lock. Interviewers often ask for exactly these hand-built versions, so know them even if you have C++20.

Likely follow up: "Why must the barrier's completion function be noexcept?" The standard requires it: it runs inside the last arriving thread with every other thread blocked, and there is no sensible way to propagate an exception to all of them.
