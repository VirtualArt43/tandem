Putting it together: a thread safe class from scratch

Build a bounded task queue and worker pool with deadline-based admission, transported task exceptions, draining shutdown, and a repeatable concurrency review checklist.

Asked atRubrikLinkedInMicrosoft
Before this:The toolkit: condition variablesThe toolkit: async, future, promise and packaged_taskThe toolkit: semaphores, latches, barriers and stop tokensObject oriented design for LLD and machine coding rounds

Now combine ownership, locks, conditions, futures, and shutdown into one component you can explain line by line. The goal is a small contract with a proof, not a collection of individually familiar APIs.

In plain words

A workshop has a limited waiting shelf and several workers. A caller can wait briefly for shelf space, but closing the workshop stops new admissions. Workers finish everything already accepted, report success or failure through receipts, and leave before the workshop owner removes the shelf.

Why this matters for concurrency

Reported Rubrik rounds extend a bounded queue into a thread pool and probe shutdown and task failures; LinkedIn reports also include implementing an executor. That extension introduces lifecycle requirements that a queue alone does not solve. The deeper lessons are producer consumer, executor anatomy, building a pool, and pool failure modes.

Step 1: make the contract concrete

  • The queue has positive fixed capacity. Its capacity counts queued tasks, not tasks already executing.
  • Submission uses one std::chrono::steady_clock deadline for waiting for space. The predicate takes priority: available space can succeed even after the deadline, including at the final recheck after a timed wait.
  • Closing rejects new submissions, wakes all blocked callers, and preserves already accepted tasks for draining.
  • Each accepted task is removed once and invoked once during normal operation. Its future reports its normal completion or its exception; this is not a crash-recovery guarantee.
  • The owner constructs the pool, calls start() once before publishing it safely to submitters, and eventually calls shutdown(). Shutdown may overlap submissions, but lifecycle calls are not concurrent with one another and never come from a worker.
  • Before destruction begins, the owner prevents new external calls and waits for existing submitters to return. Joining pool workers alone does not join those callers.
  • Every task must eventually return. Cancellation of running user code, FIFO waiter fairness, and nested blocking task dependencies are outside this small contract.

Stating limits is part of correctness. A timeout cannot promise a hard return deadline under arbitrary scheduling or mutex contention, and admission does not impose an execution deadline. Draining shutdown cannot finish if user code waits forever. A task submitting a child and then waiting for it can exhaust the same pool's workers; std::jthread does not prevent that dependency deadlock.

The lock lives in WorkQueue because it owns the queue invariant. Pool composes a queue and owned workers; it does not inherit from a synchronization primitive. The successful push under the queue lock is the acceptance point. If close wins that lock first, submission is rejected. The same order decides close versus a newly awakened producer.

The pool always creates a fresh task from a callable invocable with no arguments, discards any returned value, and exposes std::future<void>. Allocation and callable-construction exceptions can also propagate before acceptance.

Step 3: derive every wait and wakeup

A producer waits for closed or size below capacity. After waking it checks closed first, so shutdown has priority over admitting new work. A consumer waits for closed or nonempty. It checks emptiness after waking; closed plus nonempty still permits draining. Push notifies one consumer, pop notifies one producer, and close notifies all of both kinds.

Each condition variable wait releases the mutex while blocking and reacquires it before checking the predicate again. Spurious wakeups and another producer taking the slot are harmless because the predicate is rechecked. Reusing one absolute deadline avoids restarting a full relative timeout after each wakeup.

The deque provides FIFO removal, but scheduling and different task durations mean execution and completion order are not guaranteed to be FIFO. The task is moved out while locked, but invoked after pop() has released the lock. Otherwise one slow task would serialize every worker and prevent producers from using the queue. A std::packaged_task captures task exceptions in its shared result state, so an ordinary user exception does not escape the worker entry function.

The queue unlock followed by a worker's lock publishes the task and earlier producer writes. Making the task's result ready synchronizes with a successful wait for that result, and worker completion synchronizes with its join returning. These happens-before edges explain visibility; notification alone is not the publication mechanism. Capturing a reference still does not protect simultaneous access to its target.

Step 4: write the complete program

This program uses C++20 for std::jthread and std::latch. The queue itself needs C++17 for std::optional and lock type deduction. The assertions are checks, so compile the demo with assertions enabled.

Read the syntax as ownership decisions

using gives short names to a monotonic clock, its absolute time point, and a move-only task. enum class makes admission outcomes distinct from arbitrary integers. The two exception structs inherit std::runtime_error so callers can catch specific admission failures or a general standard exception. They are different from an exception stored by an accepted task.

The constructor is explicit to prevent an integer from silently becoming a queue or pool. Its initializer list initializes capacity before the body validates it. The const capacity never changes; the mutable mutex permits the const snapshot getter to lock. std::unique_lock is used where a wait releases and reacquires, while std::lock_guard handles the fixed close and getter scopes.

Moving transfers the packaged task's callable and result state into the queue and later into a worker. std::optional distinguishes a drained queue from a valid task; (*task)() dereferences it and invokes the task. The worker captures this, so the pool's members must remain alive until it exits. The explicit destructor joins before member destruction, and reverse declaration order destroys workers before the queue.

Pool is neither copyable nor movable: the deleted copy operations and declared destructor suppress implicit moves. Moving an active pool would require redesigning its ownership because workers already hold its original address. Move-only tasks do not imply a movable pool.

The submission member is a template because callers can supply different callable types, including move-only lambdas. F&& is a forwarding reference here, and std::forward<F> preserves the caller's lvalue or rvalue category when constructing the task. Returning the local future transfers its move-only ownership. No std::function wrapper is required, so the code avoids imposing copyability on task captures.

Step 5: account for failure and lifetime edges

Thread creation happens in start() after the object is fully constructed, preventing constructor publication of this. If creation fails partway through, the catch closes the queue, wakes the workers already started, joins them, and rethrows. After a partially failed start, the queue stays closed and the instance is not restartable. A failure in reserve() happens before the started flag changes or any worker is created, so that earlier failure can be retried.

The owner safely publishes the started pool, for example by creating producer threads after start() returns or handing it to existing threads through a mutex-protected channel. Merely finishing earlier in wall-clock time does not establish synchronization. started_ is written before that publication and never changes during submissions, so concurrent reads need no atomic. The worker vector is accessed only by serialized owner lifecycle calls.

Task construction or queue allocation can fail before acceptance. The packaged task's move is nonthrowing, so moving an accepted task out does not introduce a throwing element-copy gap. A rejected task may already have consumed a move-only capture supplied by the caller; admission rejection does not roll back that ownership transfer. State this when choosing a value-taking submission interface.

If a producer wakes for the only free slot but deque insertion throws, no item was accepted and the slot remains free. Another producer may still be asleep despite being able to proceed. The catch runs after the lock guard unwinds and notifies another producer before rethrowing; without that handoff it might wait until its deadline. Exception safety includes progress as well as preserving the queue invariant.

The queue does not invoke a user task under its lock. pop() moves the task into an initially empty local and removes the moved-from element; callable cleanup occurs outside the queue lock. Normal task failure becomes a future exception. Apart from partial startup, internal mutex or thread system failures are not recovered here; an exception escaping the implicitly nonthrowing destructor terminates the process.

Calling shutdown() from a worker may attempt a self-join or create a join cycle, so the contract forbids it. Shutdown joins workers, not external submitters: after closing, the owner must also stop and join those callers before destroying the pool. Borrowed task data must survive every access; here a ready future confirms invocation finished, not that its capture destructors have run. Owning captures or a lifetime extending past shutdown avoid that distinction.

std::jthread destruction requests stop and then joins if joinable, but a stop request alone does not wake an ordinary std::condition_variable wait. These workers intentionally use queue close and empty as their exit condition and are explicitly joined. Cancellation must distinguish dropping queued tasks, asking running tasks to stop, and reporting abandoned results. Read cancellation before changing those semantics.

Worked example: close racing with a waiting submitter

The queue is full, so the submitter waits with its std::unique_lock temporarily released. Shutdown sets closed under that mutex, then notifies space. If close wins before the submitter's final deadline check, the submitter reacquires, sees closed, and rejects. If the timeout decision wins first, it returns timeout instead. Workers drain previously accepted tasks, and shutdown joins them outside the lock.

The checklist for any threaded class

  1. Shared state: list every field, capture, pointer target, and external dependency that can be accessed concurrently.
  2. The lock: name which mutex or atomic protocol protects each access, including const getters and destructor paths.
  3. The invariant: state valid relationships and the point where each operation commits.
  4. Every wait: write its protected predicate, the transitions that enable it, and every timeout or stop outcome.
  5. How it stops: decide admission, draining, running work, notifications, join ownership, and object lifetime.
  6. Exceptions: identify fallible work before commit, task failures after acceptance, and cleanup on partial startup.
  7. Tests: prove blocking and overlap using gates, test deadline boundaries, force shutdown paths, and stress distinct task identities.

The runnable test fills the queue while both workers are deliberately held, so admission timeout is deterministic. Its active counter proves two jobs overlap. It checks a task exception without losing another task, a move-only capture, rejection after close, repeated shutdown, and exactly-once execution for 120 tasks submitted by three producers. These checks exercise the contract; elapsed speed alone would not prove concurrency.

Run under ThreadSanitizer, then reason beyond it

Run with an external timeout so a missing wakeup becomes a failed test instead of hanging your session. Extend testing to empty shutdown, close while consumers wait, and close while producers wait; gate those paths rather than relying on random scheduling. Inject allocation and worker-creation failures to test exception cleanup. The sample does not force these failure paths; its finite stress run cannot prove all schedules correct.

ThreadSanitizer detects executed data races, not all logical races or missing notifications. A clean run does not prove fairness, linearizability, or deadlock freedom. On this Mac, Apple ThreadSanitizer does not report lock-order inversions; use bounded tests and stack inspection for hangs. Print after joining, as this libc++ can produce a sanitizer report when multiple threads write std::cout concurrently.

Common mistakes

  • Invoking tasks while the queue lock is held: move the task out first so other workers and reentrant queue calls can proceed.
  • Destroying state before workers or submitters finish: close, join owned workers and external callers, then destroy.
  • Closing only the consumer predicate: include closed in both predicates and notify both waiter roles.
  • Dropping accepted work during draining shutdown: retain it until workers invoke it, or explicitly choose cancellation semantics.
  • Assuming future exceptions or std::jthread destruction define the service lifecycle: specify admission, failure transport and termination separately.

In the interview

The acceptance point is insertion under the queue lock. Close uses the same lock, rejects later submissions, and wakes both waiter roles. Workers remove under the lock but execute outside it. Packaged tasks transport failures, and the owner joins only after closing, with no queue lock held.

Expect to build the queue first, extend it into a pool, then defend exceptions, deadlines and shutdown. State the invariant and the lifecycle before writing the worker loop.

Senior depth: the next requirements

Bounded work is not bounded memory. With capacity C and W workers, at most C + W accepted tasks are queued or executing. However, each waiting submitter already owns a task, and captures can be large. Deque end operations are constant time excluding allocation and contention; admission waits, task runtime and shutdown have no fixed latency bound. To bound total memory, also limit submitters or reject promptly, and consider a preallocated ring buffer.

Nested work needs a policy. With one worker, a parent can enqueue a child successfully and then deadlock on its future because no worker is free to run it. An admission deadline does not help after acceptance. Avoid same-pool blocking dependencies, use continuations, or deliberately implement helping or caller execution; those alternatives change ordering and reentrancy. Blocking on a per-key permit inside every worker can similarly starve unrelated keys, so schedule eligible keys before occupying workers.

Result timeouts are not cancellation. future.wait_for(timeout) returning timeout only stops that wait. The accepted job still runs, and destroying this packaged-task future does not cancel it or join the job. For immediate shutdown, remove queued tasks under the lock and destroy them outside it: an uninvoked packaged task makes its future ready with std::future_error carrying std::future_errc::broken_promise. Running jobs need an explicit cooperative stop protocol, and priority scheduling needs a starvation policy.

Return values can use the same queue. For a no-argument callable returning R, create a std::packaged_task<R()>, obtain its std::future<R>, and move the task into a mutable lambda that calls it. Submit that lambda through the existing void-task path and return the typed future only after successful admission. This preserves move-only captures; C++20 std::function<void()> would require a copyable target. The inner task owns result and exception transport.

C++17 fallback: replace every std::jthread, including the demo's producer threads, with std::thread and retain every explicit join, including the partial-start catch. Replace each latch with a mutex-protected countdown and a predicate condition wait; notify all at zero. Explicitly initialize every atomic array element with store(0) before starting workers. The queue, futures and draining protocol otherwise stay the same.

Key takeaways

  • A component needs one coherent contract across admission, work, results, and shutdown.
  • Queue state stays under its mutex; user work stays outside it.
  • One absolute deadline controls waiting, while task completion has its own lifetime.
  • Construct fully, start deliberately, close visibly, and join before destruction.
  • Use deterministic gates and identity checks alongside sanitizer runs.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Where does this pool commit acceptance of a task?
Why. The queue insertion and closed check share one protected transition. Constructing a future alone does not mean the pool accepted its work: admission can still time out. Worker invocation is later; accepted tasks waiting in the queue must also drain.
Why must a worker invoke its std::packaged_task after pop() releases the queue lock?
Why. The queue mutex protects queue transitions, not arbitrary task bodies. Running tasks while holding it serializes execution and can introduce reentry cycles. A packaged task has no knowledge of the queue mutex, and notification makes a waiter eligible to run; it does not transfer lock ownership.
The queue stays full when close notifies a waiting producer. Which predicate lets its predicate wait return after it reacquires the mutex?
Why. Closed is a durable exit condition independent of capacity. The producer checks closed first and rejects. Both other predicates remain false on a closed full queue, so notification alone cannot make their predicate wait return successfully.
An accepted task throws std::runtime_error. What happens in this design?
Why. std::packaged_task captures callable exceptions in its shared state; future.get() rethrows them. They do not escape this valid, single-invocation task wrapper. Joining a thread waits for completion and does not retrieve future exceptions, so shutdown does not rethrow them.
Why is started_ an ordinary bool in this particular contract?
Why. Safe publication orders the write before submitters' reads, and there are no later writes. These flag accesses are outside the queue mutex, so that mutex is not their protection. Wall-clock order alone is not a happens-before edge; concurrent start would need a different lifecycle protocol.
The active counter reaches two while both jobs wait behind a test gate. What does that prove?
Why. Overlapping active invocations prove useful concurrency. They do not establish physical CPU simultaneity, fairness, or every future schedule.
With the WorkQueue and aliases above, what does this single-threaded fragment print?
Why. The empty queue satisfies the predicate immediately, even with a past deadline, so the first task is accepted. The second sees full and open, so its final predicate check is false and it times out. Close makes the third predicate true; the closed check then rejects it. Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
Add a wait-until-idle operation. What state and predicate would it need?
Model answer
Track an outstanding count under the queue mutex: increment in the same critical section as successful insertion, leave it unchanged when a worker dequeues, and decrement under that mutex after invocation. Otherwise a worker could finish before its submission is counted. Idle means outstanding is zero, not merely an empty queue. Notify an idle condition at zero and wait with that predicate. Packaged tasks capture user exceptions, so decrement after invocation still runs; use scope cleanup if invoking raw callables. This is an instantaneous idle observation: another submission can arrive after the lock is released. Close admission first for a permanent drain, or track a batch separately to wait only for earlier submissions.
Debug
The pool hangs during destruction after a worker creation failure. What cleanup path should you inspect?
Model answer
Partially created workers may already be blocked in pop. The startup failure path must close the queue and notify before joining them. Joining a worker waiting on an unclosed empty queue cannot complete, and destructor member ordering alone does not supply the missing wakeup.
Design
What changes for immediate shutdown instead of draining?
Model answer
Define queued and running tasks separately. Under the queue mutex, close admission and transfer queued tasks to a local container. Notify both waiter roles, then destroy those tasks outside the lock, so capture destructors cannot reenter a locked queue. Uninvoked packaged tasks produce broken-promise errors in their futures; a dedicated cancellation result requires a different wrapper. Pass running tasks a cooperative stop mechanism, request stop and join owned threads. Arbitrary running C++ code cannot be forcibly stopped safely, so even immediate shutdown cannot promise an immediate return.

"Walk me through the acceptance and shutdown race in your pool."
What a strong answer covers
  • Acceptance and closed state use one mutex
  • Earlier accepted work drains
  • Later admissions reject and both waiter roles wake
  • Owner joins outside the lock and waits for external callers before destruction
How a senior would say it
A submission becomes accepted only when its task is inserted under the queue mutex. Close sets the closed flag under that same mutex, so those operations have a definite order. If insertion wins, shutdown must drain that task. If close wins, admission rejects even if space becomes available. A submitter that already decided timeout is also unaccepted. Close wakes producers and consumers. Workers drain remaining tasks and exit when closed and empty. The owner joins outside the queue lock, and separately waits for external submitters before destruction. Running jobs still have to return for shutdown to finish.

Likely follow up: How would wait-until-idle differ from observing an empty queue?

"What would you test before claiming this class is thread safe?"
What a strong answer covers
  • State invariants and exactly-once identities
  • Forced blocking and overlapping task counters
  • Timeout, exceptions, close and partial startup
  • Sanitizer plus bounded deadlock tests
How a senior would say it
I would check the queue capacity invariant and track task identities to detect duplicates or losses. I would use gates to force a full queue and blocked workers, then prove actual overlap with an active-call counter. I would test timeout, task exceptions, rejection after close, draining, and both kinds of waiter waking during shutdown. I would also review partial thread creation failure and borrowed capture lifetimes. Then I would run ThreadSanitizer with an external timeout and varied schedules. A clean sanitizer run is useful evidence, but it does not prove logical ordering or rule out every deadlock.
