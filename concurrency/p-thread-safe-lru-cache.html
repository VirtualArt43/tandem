Thread-safe LRU cache

Thread-safe structuresmedium35 minLeetCode 146, then make it thread-safeMicrosoftRubrik

"Implement an LRU cache, now make it thread-safe" is one of the most common concurrency follow ups there is: Rubrik, Microsoft (including an Azure Storage round in C++), Apple and LinkedIn candidates report it. The trap that sinks people is simple to state: in an LRU cache, every read is also a write.

The task

Build a cache of int keys and int values with a fixed capacity and least-recently-used eviction, safe for many threads at once:

  • get(key) returns the value, or -1 when the key is not in the cache. A hit makes the key the most recently used.
  • put(key, value) inserts the key or updates its value, and makes it the most recently used. If the cache is then over capacity, it evicts the least recently used key.
  • size() returns the number of keys in the cache.

Values are never negative. get and put must be O(1).

Rules: no LinkedHashMap in Java (it is an LRU cache already); build the hash map plus doubly linked list yourself. In C++, std::unordered_map with std::list and splice is fine. Make it correct first: the tests do not reward a clever locking scheme, only a correct one.

What the tests check

  • Eviction order from one thread, including that a get hit and a put update both refresh recency, and that a miss does not.
  • Capacity 1, and 20,000 random gets and puts from one thread checked step by step against a model.
  • No lost inserts: 4 threads insert 1,000 distinct keys each into a cache that holds them all; every key must be there with its value.
  • A stress run with 8 threads mixing gets and puts on 64 keys with capacity 16: size() never goes above 16, and every get returns -1 or a value that was put for that same key (no torn or mixed-up entries).
  • After the stress run, the cache still evicts exactly: 16 fresh keys put from one thread are all present and every old key is gone.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Thread-safe caches: LRU, TTL and single-flight

Open them one at a time. Each one gives away a little more.

The single-threaded LRU first: a hash map from key to node, and a doubly linked list of nodes from most to least recently used. A hit moves the node to the front; an insert adds at the front; eviction removes from the back. Sentinel head and tail nodes remove the edge cases.
Which methods change the list? put, obviously. And get: a hit moves a node to the front. So every method changes shared state, and the map and the list must change together.
So a read-write lock buys nothing: get would need the write lock anyway, and running two hits under a shared read lock lets them re-link neighbouring nodes at the same time and corrupt the list. Use one lock for the map and the list together, in every method including size().

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why not a read-write lock, so gets can run in parallel?
Because a hit moves its node to the front of the list, get writes shared state, just like put. Under a read lock two hits re-link nodes at the same time and corrupt the list; with the write lock there is no parallelism left. A Rubrik interviewer pushed on exactly this (both get and put modify the structure, so what is the right implementation?), and a Microsoft candidate on Blind summed it up as "whatever way I made it thread safe, there were always holes". One lock is the correct answer; the follow ups below are how you scale it.
Make it an LFU cache: evict the least frequently used key, breaking ties by recency.
Keep a map from key to node, a map from frequency to a doubly linked list of nodes with that frequency, and the current minimum frequency. A hit moves the node from list f to list f + 1 (and bumps the minimum if list f became empty); eviction removes the oldest node of the minimum-frequency list. Everything stays O(1), and since a hit again changes shared state, it still needs one lock. A Google candidate (2019) was asked for a thread-safe LFU where "just using synchronized" was not enough, and Confluent rounds have asked for thread-safe LFU too.
Add a TTL per entry (Microsoft asked for LRU with TTL, then concurrency, in 2026).
Store an expiry time in each node. get treats an expired node as a miss and removes it (lazy expiry); put sets the expiry. To stop expired but unread entries from holding capacity, either evict expired nodes first when full, or run a cleaner that scans under the lock in small batches. Read time from an injectable monotonic clock so it can be tested. The TTL cache problem drills the expiry part.
One lock serializes every core. How would you scale it?
Shard it: N independent LRU caches, each with its own lock, and route each key by hash. Contention drops roughly N times, but recency is now per shard, so eviction is only approximately LRU globally: a shard may evict its oldest key while another shard holds an even older one. In a 2024 Meta design round for a single-machine memcache, the interviewer praised sharding the table into about one part per core for exactly this reason. Real caches go further: Caffeine records hits in a buffer and replays them under the lock in batches, and Redis evicts by sampling a few keys and dropping the oldest, which is approximate LRU with no list at all.
Two threads miss the same key at once and both load it from the database. How do you stop that?
Single-flight: the first thread to miss puts a placeholder (a future) into the map, and later threads that miss the same key wait on that future instead of loading. The load happens outside the cache lock so other keys are not blocked, and a failed load removes the placeholder so the next caller retries. The single-flight cache problem builds exactly this.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

An LRU cache pairs two structures. A hash map gives O(1) lookup from key to node; a doubly linked list keeps nodes in recency order, most recent at the front. A hit unlinks the node and re-inserts it at the front; an insert adds at the front; when the cache is over capacity, the node at the back is unlinked and its key removed from the map. The invariant is the map and the list hold exactly the same keys, at most capacity of them, and the list is in recency order. Because every operation, get included, changes the list, one lock guards the map and the list together.

Why each line is there

  • Sentinel head and tail. Insert after head, evict before tail: no null checks for empty or one-element lists.
  • One lock for map and list. They form one invariant. Locking them separately lets a thread see a key in the map whose node is half unlinked.
  • get takes the same exclusive lock as put. This is the point of the problem:
  • size() locks too. In C++ an unlocked read of the map's size while another thread inserts is a data race.
  • C++: splice moves a list node to the front in O(1) without reallocating it, so the iterator stored in the map stays valid.

Cost

get and put are O(1) under one lock; memory is one map entry and one list node per key. Throughput is limited by that lock, which is why the follow ups talk about sharding, buffered recency updates and sampled eviction.

How to say it in the interview

I use a hash map from key to node plus a doubly linked list in recency order, with sentinels. Get moves the node to the front, put inserts or updates at the front and evicts from the back when over capacity, all O(1). For thread safety the key observation is that get is a write, because it reorders the list, so a read-write lock does not help: I guard the map and the list with one mutex in every method. If that lock becomes the bottleneck, I would shard by key hash and accept approximate global LRU, or buffer the recency updates.
