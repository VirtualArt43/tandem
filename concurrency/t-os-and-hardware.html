Process versus thread: what does each own, what do they share, and what does each cost?
Model answer

A process is the operating system's container for a running program: its own virtual address space (code, globals, heap, mapped files), open file descriptors, credentials and signal handlers. A thread is a schedulable flow of execution inside a process. Each thread has its own stack, registers (program counter, stack pointer), thread-local storage, signal mask and scheduling state; it shares the address space, heap, globals and open files with the other threads of its process. On Linux both are "tasks" created by clone, with different flags deciding what is shared.

Costs: creating a process (fork with copy-on-write page tables) and switching between processes (a change of address space, with TLB effects) cost more than the same operations for threads.

The trade-off is isolation against sharing. One thread that crashes (a segfault) kills the whole process; separate processes isolate faults and memory, which is why browsers put tabs in separate processes. Threads share memory directly, which is fast but needs synchronization; processes must use IPC such as pipes, sockets or shared memory.

Likely follow up: "What happens to threads when a multithreaded process calls fork?" Only the calling thread exists in the child. Any mutex another thread held at that moment stays locked forever in the child, including locks inside malloc, so the child should call only async-signal-safe functions until it calls exec.

What happens during a context switch, and what does it cost?
Model answer

A context switch is triggered by a timer interrupt (the time slice ran out), by a blocking system call (I/O, a futex wait), or by a higher-priority task waking up. The kernel saves the running thread's registers (general purpose registers, program counter, stack pointer, flags, and floating point and vector state), the scheduler picks the next task, and the kernel restores that task's registers and kernel stack. If the next thread belongs to another process, the kernel also switches the address space by loading a new page-table root (CR3 on x86), which can throw away TLB entries unless they are tagged with an address-space id (PCID or ASID).

The direct cost is on the order of a microsecond to a few microseconds. The indirect cost is often larger: the incoming thread starts with cold caches and TLB entries, and the outgoing thread finds its data evicted when it returns. Mitigations for speculative-execution attacks made kernel entry and exit more expensive too. A switch between threads of the same process skips the address space change, so it is cheaper.

Measure it with the cs column of vmstat, pidstat -w per thread, or perf sched. Thousands of threads on a few cores turn CPU time into switching overhead.

Likely follow up: "Voluntary or involuntary switches: which tells you what?" Many involuntary switches (preemptions) mean the CPU is oversubscribed. Many voluntary switches (the thread blocked) point to lock contention or I/O waits.

3Corekernel-modesystem-calls
What are user mode and kernel mode, and why is a system call expensive?
Model answer

The CPU runs at privilege levels, and the kernel runs in kernel mode. User mode (ring 3 on x86) cannot run privileged instructions, touch hardware directly, or access memory it was not given. Kernel mode (ring 0) can. A system call is a controlled way across: the program puts the call number and arguments into registers and executes syscall (on x86-64); the CPU switches to kernel mode at a fixed entry point; the kernel checks the arguments, does the work, and returns with sysret. Interrupts and exceptions such as page faults also enter kernel mode.

The cost is the mode switch, saving and restoring state, mitigations for speculative-execution attacks (separate kernel page tables add TLB costs), and cache pollution. A trivial call costs roughly 100 ns to a microsecond (order of magnitude), and far more if it blocks.

That cost shapes a lot of design:

  • Buffered I/O batches many small writes into one write.
  • A futex-based mutex makes no system call at all when uncontended.
  • The vDSO maps calls such as clock_gettime into user space, so reading the time needs no kernel entry.
  • io_uring submits and completes many I/O operations through shared rings, with few system calls.

Likely follow up: "So when does locking a mutex enter the kernel?" Only when it has to sleep (it is contended) or wake a sleeper on unlock. The uncontended path is a single atomic instruction in user space.

4Seniorfutexmutex-internals
What is a futex, and how is a mutex built on one?
Model answer

A futex ("fast userspace mutex") is the Linux primitive under almost every lock. The lock's state is an ordinary integer in user memory, and the kernel offers two operations on its address. FUTEX_WAIT(addr, expected) sleeps only if the value at addr still equals expected, checked atomically inside the kernel, which rules out the lost wakeup between "I saw it locked" and "I went to sleep". FUTEX_WAKE(addr, n) wakes up to n sleepers. The uncontended path never enters the kernel.

Ulrich Drepper's classic mutex uses three states: 0 unlocked, 1 locked, 2 locked with possible waiters. C++20's atomic::wait and notify_one express it directly; libstdc++ implements them with a futex on Linux for 32-bit atomics.

State 2 exists so that unlock can skip the wake system call when nobody can be sleeping; a waiter pessimistically sets 2 before it sleeps. Real implementations add a short spin before sleeping, priority-inheritance futexes, and robust futexes for owners that die. Java's LockSupport.park also ends in a futex wait on Linux.

Likely follow up: "Why does the waiter set 2 with exchange rather than a CAS?" It must both claim the lock if it happens to be free (old value 0) and record that waiters may exist (new value 2), in one atomic step.

5CoremutexsemaphorespinlockLinkedInNvidiaRubrik
Mutex versus semaphore versus spinlock. And is a binary semaphore the same as a mutex?
Model answer
  • Mutex: a lock with an owner. Only the thread that locked it may unlock it, and waiters sleep. Ownership enables error checking, recursion, priority inheritance (the kernel knows whom to boost) and robust recovery when an owner dies.
  • Semaphore: a permit counter with no owner. wait (P, acquire) takes a permit or blocks at zero; post (V, release) adds one and wakes a waiter. Any thread may post. It counts resources (at most N connections) and signals between threads (one thread posts, another waits, for example an interrupt handler waking a task).
  • Spinlock: a lock whose waiters busy-wait instead of sleeping. Right only for very short critical sections whose holder is running on another core, and in kernel contexts that are not allowed to sleep.

A binary semaphore also admits one holder at a time, but it is not a mutex: it has no owner, so any thread can release it. That makes it a fine signal and a poor lock: a bug can release someone else's critical section, there is no priority inheritance, and self-deadlock or double release goes undetected. Use a mutex for mutual exclusion and a semaphore for counting and signaling.

Likely follow up: "Can an interrupt handler use a semaphore?" It may post one, and real-time kernels provide special from-interrupt variants for that. It must never wait on one, because an interrupt handler cannot sleep.

6Seniorspinlockadaptive-lockingNvidia
When is a spinlock better than a sleeping mutex, and how do you write a good one?
Model answer

Spinning wins when the expected wait is shorter than sleeping and waking, which costs two context switches, a few microseconds. That means very short critical sections, a holder that is running on another core and never sleeps while holding, and no more threads than cores.

It loses badly on a single core, where spinning only burns the time slice the holder needs (uniprocessor kernels reduce a spinlock to disabling preemption); when the holder is preempted, so every waiter spins a whole time slice, a real problem inside virtual machines; and with long critical sections or many waiters.

Kernels need spinlocks because interrupt context cannot sleep. Code that shares data with an interrupt handler takes the lock with interrupts disabled (spin_lock_irqsave in Linux), and must never sleep while holding a spinlock.

Spinning on a read keeps the cache line shared, while spinning on exchange would bounce it between cores on every attempt. Add exponential backoff under heavy contention, or use a queue lock such as MCS, where each waiter spins on its own line. In Java the pause hint is Thread.onSpinWait().

Likely follow up: "What do real mutexes do?" They use adaptive spinning: spin briefly, then park. HotSpot monitors and glibc's adaptive mutex type both work this way.

7Seniorpriority-inversionreal-time
What is priority inversion, and how is it solved?
Model answer

priority inversion: a high-priority task H waits for a lock held by a low-priority task L. A medium-priority task M, which does not need the lock, preempts L, so L cannot run to release the lock, and H in effect waits for M. With enough medium-priority work, the inversion is unbounded.

The famous case is Mars Pathfinder in 1997. A high-priority bus management task blocked on a mutex held by a low-priority meteorological task while medium-priority tasks ran. A watchdog saw the bus task miss its deadline and reset the spacecraft repeatedly. The fix, uploaded from Earth, was to turn on priority inheritance for that mutex in VxWorks.

Solutions:

  • Priority inheritance: while L holds a lock that H wants, L runs at H's priority, so M cannot preempt it.
  • Priority ceiling: each lock has a ceiling, the highest priority of any task that uses it, and the holder runs at that ceiling. It also prevents some deadlocks.
  • Keep critical sections short, avoid sharing locks across priority levels, or communicate through lock-free queues.

On Linux, pthread_mutexattr_setprotocol with PTHREAD_PRIO_INHERIT or PTHREAD_PRIO_PROTECT selects these; the inheritance protocol is backed by priority-inheritance futexes, so the kernel does the boosting. Inheritance needs an owner to boost, which is one more reason semaphores make poor locks.

Likely follow up: "Does this matter for ordinary server code?" Less so: the normal Linux scheduler gives every runnable thread some CPU time, so inversion shows up as extra latency rather than an unbounded stall. With real-time SCHED_FIFO threads it is a genuine hazard.

8Seniordeadlockbankers-algorithm
Explain the Banker's algorithm with an example. Why is it rarely used?
Model answer

The banker's algorithm avoids deadlock. Each process declares its maximum claim up front, and the system grants a request only if the resulting state is safe: there is some order in which every process can get its remaining need, finish, and release what it holds. The safety check: set Work to Available; repeatedly find an unfinished process whose Need fits in Work, pretend it finishes, and add its Allocation to Work. If every process finishes, the state is safe.

One resource type with 12 units, so 3 are available. Safe sequence: P1 (needs 2, fits in 3; afterwards 5 are free), then P0 (needs 5, fits; then 10), then P2 (needs 7, fits; then 12). The state is safe.

Now P2 asks for 1 more. Tentatively 2 are available and P2 needs 6. P1 can finish (2 fits, then 4 are free), but then P0 needs 5 and P2 needs 6, and neither fits in 4. The state would be unsafe, so the request waits, even though no deadlock exists yet. The check costs O(m × n²) for m resource types and n processes.

It is rare in practice because nobody knows maximum claims in advance, the sets of processes and resources keep changing, and it refuses requests that would probably have been fine. Real systems prevent deadlock with lock ordering, or detect and recover from it, as databases do.

Likely follow up: "Unsafe means deadlocked?" No. Unsafe means a deadlock is possible if every process asks for its maximum; safe means the system can still run every process to completion in some order, so as long as it keeps granting only requests that leave a safe state, deadlock cannot occur.

9Corecache-coherencemesiMicrosoft
What is cache coherence, and how does the MESI protocol work?
Model answer

Every core has private caches. Without coordination, two cores could hold different values for the same address. cache coherence guarantees that all cores agree on the order of writes to each single location. The unit is the cache line, typically 64 bytes on x86.

The MESI protocol gives each cached line one of four states:

  • Modified: only this cache holds it, and it is dirty.
  • Exclusive: only this cache holds it, and it is clean.
  • Shared: several caches hold it, all clean.
  • Invalid: not usable.

A read miss fetches the line; if another cache holds it Modified, that cache supplies the data and both copies become Shared. To write, a core must own the line exclusively: from Shared it broadcasts an invalidation (an upgrade), from Invalid it issues a read-for-ownership that fetches the line and invalidates the other copies; either way the other copies become Invalid and its copy becomes Modified. From Exclusive it moves to Modified silently, which is why the Exclusive state exists. Variants add states: MOESI adds Owned, MESIF adds Forward.

The concurrency consequence: when several cores keep writing the same line (a lock word, an atomic counter, or neighbouring fields), the line ping-pongs between them and each write pays a cross-core transfer. That is the hardware cost behind contention and false sharing.

Likely follow up: "If caches are coherent, why do we need atomics and fences?" Coherence orders writes to one location. Store buffers, invalidation queues and the compiler can still reorder accesses to different locations, and the memory model (fences, acquire and release) governs that.

10Corefalse-sharingcache-line
What is false sharing, how do you detect it, and how do you fix it?
Model answer

false sharing happens when threads write different variables that sit in the same cache line. Coherence works per line, so each write invalidates the other cores' copies, and the line ping-pongs although no data is actually shared. Throughput often drops several times, and adding threads makes it worse.

Detect it: per-thread counters or flags that do not scale despite having no locks are the classic sign. perf c2c on Linux reports lines with heavy cross-core modified hits and the offsets being touched; Intel VTune's memory access analysis shows the same.

Other fixes: C++17's std::hardware_destructive_interference_size instead of a hard-coded 64 (compilers may warn that its value is not stable across builds); Java's internal @Contended annotation (jdk.internal.vm.annotation.Contended), which LongAdder uses and which application code can use only after exporting that package to it at compile time and running with -XX:-RestrictContended; and keeping per-thread data in per-thread objects merged at the end. Line sizes vary: 64 bytes on x86, while macOS reports 128 bytes on Apple M-series chips (sysctl hw.cachelinesize), so pad 128 there; Apple clang's libc++ still sets the interference constant to 64 on those chips. Intel's adjacent-line prefetcher makes some code pad to 128 even on x86.

Likely follow up: "Is padding always worth it?" No: it multiplies memory use and can hurt cache hit rates. Pad only fields that different threads write frequently.

11Seniormemory-orderinghardwarex86arm
Why does lock-free code that works on x86 sometimes fail on ARM?
Model answer

x86 implements TSO, total store order. Each core's stores become visible in program order, loads are not reordered with other loads, and the only reordering software can observe is a store followed by a load from a different address, because the store waits in the store buffer. ARM and POWER are weakly ordered: loads and stores to different addresses may become visible in almost any order unless acquire or release instructions or fences say otherwise.

So code with missing ordering, such as a plain flag that publishes data or relaxed atomics where acquire and release were needed, can work on x86 because the hardware happens to provide the order (and the compiler happened not to reorder), then fail on ARM: Apple Silicon laptops, AWS Graviton servers, phones.

The instruction mapping shows why: on x86 an acquire load and a release store are plain mov instructions, while on ARMv8 they are ldar and stlr, and fences are dmb. So testing only on x86 gives false confidence. ThreadSanitizer finds data races whatever the hardware, and stress tests on ARM machines catch much of the rest.

Likely follow up: "Which reordering does x86 allow, and how do you prevent it?" Store then load to a different address. A full fence (mfence) or any locked instruction between them prevents it, which is what a seq_cst store compiles to.

12Corememory-allocationfree-listfragmentationRubrikNvidia
How does a basic memory allocator work? Explain free lists and fragmentation.
Model answer

malloc manages heap memory obtained from the OS (brk or mmap). Each block has a header holding its size and an allocated bit, and free finds the header just before the pointer it is given. Free blocks are chained into a free list, with the links stored inside the free blocks themselves, so the list costs no extra memory.

Placement policies:

  • First fit: take the first block big enough. Fast, but it fragments the front of the list.
  • Next fit: like first fit, but continue from where the last search stopped.
  • Best fit: take the smallest block that fits. Less waste per allocation, a slower search, and it leaves tiny unusable slivers.

A larger block is split and the remainder goes back on the list. On free, coalesce the block with free neighbours; boundary tags (a footer that repeats the size) let you find the previous block in O(1).

Fragmentation comes in two kinds. Internal: an allocated block bigger than requested, because of alignment or size classes. External: enough free memory in total, but no single contiguous block large enough. Real allocators keep segregated free lists per size class, which makes small allocations O(1), and send large requests straight to mmap. One lock around the whole heap is simple but contended, which the next question addresses.

Likely follow up: "Implement alloc(size) and free(index) over a fixed region." Use a free list or bitmap over fixed units with first fit and coalescing, or, if sizes may be rounded to powers of two, a buddy allocator.

13Seniorbuddy-allocatormemory-allocationRubrik
How does a buddy allocator work?
Model answer

A buddy allocator manages a region of 2^K units. Every block has a power-of-two size, and there is a free list per order (order k holds free blocks of 2^k units).

  • alloc(n): round n up to 2^k. Take a block from free list k. If that list is empty, take a block from the smallest larger non-empty order and split it repeatedly: each split makes two halves, called buddies; put one half on the next lower list and keep splitting the other until it is 2^k.
  • free(offset, k): find the buddy's offset with offset XOR 2^k (offsets measured from the start of the region). If the buddy is free and of the same order, remove it from its list, merge the two into one block of order k plus 1 starting at the lower offset, and repeat one level up. Otherwise put the block on list k.

Both operations are O(log N). Track each block's state and order in a bitmap or a small array. Merging is cheap because a block's only possible partner is computed, never searched for, which keeps external fragmentation low. The price is internal fragmentation of up to about 50 percent: a request for 2^k plus 1 units takes 2^(k plus 1). The Linux kernel's page allocator is a buddy allocator, with blocks up to order 10 by default (4 MB with 4 KB pages).

Likely follow up: "Make it thread-safe." One lock around the allocator is the honest first answer. Then reduce contention with per-CPU or per-thread caches of small blocks in front of it, which is what Linux does for single pages.

14Seniorallocatorsscalability
How do production allocators scale across many threads?
Model answer

A single heap lock serializes every malloc and free, so scalable allocators avoid shared state on the common path.

  • glibc malloc uses multiple arenas, each with its own lock (on 64-bit systems the default limit is 8 per core), assigns threads to arenas, and since glibc 2.26 adds a small per-thread cache (tcache) that needs no locking.
  • tcmalloc keeps per-thread or, in newer versions, per-CPU caches of objects by size class, refilled in batches from central free lists, over a page heap.
  • jemalloc spreads threads over several arenas, adds thread caches, and allocates small objects from slabs by size class.

The common ideas are size classes, thread-local caching and batch transfers between the local caches and central structures, with memory returned to the OS lazily.

The pitfalls: memory blowup when one thread allocates and another frees (the freed memory lands in the wrong cache, which is common in producer-consumer code); false sharing if small objects from different threads share a cache line (most allocators separate them by thread or arena); and fragmentation across arenas.

For an interview allocator, describe one lock per size class or per arena, plus a capped thread-local cache of free blocks.

Likely follow up: "Your service's memory grows although nothing leaks." Suspect allocator caching and fragmentation across arenas: limit the arena count, or try another allocator, and compare resident memory over time.

15CoreschedulingpoliciesRubrik
Compare the classic CPU scheduling policies, and say what Linux actually does.
Model answer
  • First come, first served: no preemption. Short jobs wait behind long ones, the convoy effect.
  • Shortest job first, or its preemptive form shortest remaining time first: minimal average waiting time when burst lengths are known, but long jobs can starve, and lengths must be predicted, typically by an exponential average of past bursts.
  • Round robin: a fixed quantum per turn. Fair, with good response time; too small a quantum wastes time switching, too large degenerates into first come, first served.
  • Priority: low priorities can starve, so add aging.
  • Multilevel feedback queue: several queues with different quanta. A job that uses its whole quantum moves down, interactive jobs stay high, and a periodic boost prevents starvation. It approximates shortest job first without knowing lengths.

Linux: from 2.6.23 the Completely Fair Scheduler kept a weighted virtual runtime per task (weighted by its nice value) and always ran the task with the smallest, using a red-black tree. Since Linux 6.6, EEVDF (earliest eligible virtual deadline first) replaced CFS's core algorithm and adds latency awareness. Real-time classes SCHED_FIFO and SCHED_RR use strict priorities above normal tasks, and SCHED_DEADLINE schedules by deadlines.

The metrics to name when comparing: throughput, turnaround time, waiting time, response time and fairness.

Likely follow up: "Which policy fits an admission problem like the shared bathroom?" FIFO with a batch limit per group: bounded waiting for everyone, while each turn still batches compatible people.

16Seniorvirtual-memorypagingtlbLinkedIn
What are paging, the TLB and page faults, and why do they matter for multithreaded programs?
Model answer

Each process sees a private virtual address space divided into pages (4 KB typically; x86 also offers 2 MB and 1 GB huge pages). Page tables map virtual pages to physical frames, the MMU translates every access, and the TLB caches recent translations.

A page fault is an access to a page that is not currently mapped. A minor fault (first touch of fresh memory, copy-on-write, a shared library page already in memory) is handled in microseconds. A major fault must read from disk (swapped out, or a file-backed page not in cache) and takes milliseconds.

Why threads care:

  • All threads share one address space. When any thread changes a mapping (munmap, mprotect, an allocator returning memory to the OS), the kernel must invalidate the stale TLB entries on every core running that process's threads, a TLB shootdown done with inter-processor interrupts. It is expensive in large multithreaded processes.
  • A major fault while holding a lock stalls every thread waiting for that lock.
  • On NUMA machines, a page is usually placed on the memory node of the thread that touches it first, so which thread initializes data decides where it lives.
  • Huge pages cut TLB misses for large heaps.

Likely follow up: "How can an allocator hurt a threaded program through paging?" One that eagerly returns memory with munmap or madvise triggers shootdowns and later minor faults on reuse, so many allocators hold freed memory for a while.

17SeniorinterruptsisrNvidia
What may an interrupt handler not do, and how do kernels split interrupt work?
Model answer

An interrupt service routine runs asynchronously, preempting whatever was running, often with its interrupt line or all interrupts masked, and outside any context that is allowed to sleep. So it must not:

  • Sleep or block: no mutex, no semaphore wait, no allocation that may block, no copying to user memory that may fault.
  • Take long: it delays other interrupts and adds latency for everyone.
  • Take a lock that the interrupted code may already hold on the same CPU. The handler would spin forever on a lock that can only be released when it returns. That is why process-context code that shares data with the handler takes the lock with interrupts disabled (spin_lock_irqsave).

Kernels therefore split the work. The top half, the real handler, acknowledges the device, grabs what is urgent and schedules the rest. The bottom half (in Linux: softirqs, tasklets, workqueues, threaded handlers) does the heavy processing later with interrupts enabled, and workqueues may sleep. The user-space analogue is a signal handler: it may call only async-signal-safe functions, so it sets a flag and lets the main loop do the work.

Likely follow up: "Why is volatile common in embedded interrupt code?" On a single-core microcontroller, volatile keeps the compiler from caching a variable shared between the handler and the main loop, and interrupts are disabled around multi-byte updates. On multicore systems you need real atomics.

18CoreipcprocessesMicrosoft
How can two processes communicate, and how do you synchronize them?
Model answer
  • Pipes (parent and child, a one-way byte stream) and FIFOs, which are named pipes.
  • Unix domain sockets: two-way, and they can pass file descriptors. TCP sockets work across machines.
  • Message queues, such as POSIX mq_open.
  • Shared memory (shm_open plus mmap, or mmap of a file): the fastest, with no copying, but you must synchronize it yourself.
  • Signals, for asynchronous notification with almost no payload.
  • Files with advisory locks (flock, fcntl locks).

Synchronizing shared memory: place a mutex and a condition variable in the shared region and initialize them with the PTHREAD_PROCESS_SHARED attribute; or use POSIX named semaphores (sem_open); or build a lock-free ring buffer with atomics and wake the reader with a futex or an eventfd. Make it a robust mutex, so that if a process dies while holding it, the next locker gets EOWNERDEAD, repairs the shared state and calls pthread_mutex_consistent, instead of everyone waiting forever.

Choose sockets for generality and isolation, and shared memory with a ring buffer for high throughput and low latency between processes on one machine. In Java, the options are sockets, files and FileChannel.map for shared memory, with FileLock or atomic operations through a VarHandle on the mapped buffer for coordination, since Java has no process-shared mutex.

Likely follow up: "What happens if a process dies holding an ordinary shared-memory mutex?" Every other process that tries to lock it blocks forever. That is exactly the failure robust mutexes exist for.
