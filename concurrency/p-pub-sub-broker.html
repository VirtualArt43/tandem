In-memory pub-sub broker with offsets

Concurrent systemshard45 minUber machine coding (multi-threaded pub-sub, a Kafka-like system with concurrency support)Uber

Uber's machine coding rounds in India keep asking for a multi-threaded pub-sub or "a system like Kafka with concurrency support", as runnable code. The heart of it is small: an append only log per topic, offsets handed out under a lock, and consumers that wait for new data with a timeout without missing a wakeup or waking too early.

The task

Build a broker that keeps every topic as an ordered log, the way Kafka does, so consumers read by offset instead of having messages pushed at them:

  • publish(topic, message) appends the message to the topic (creating the topic on first use) and returns its offset. A topic's offsets are 0, 1, 2 and so on, dense and unique, even with many publishers at once.
  • poll(topic, fromOffset, max, timeout) returns the messages at offsets fromOffset, fromOffset + 1, ..., at most max of them. If there is no message at fromOffset yet, it waits until one arrives or the timeout passes, and then returns an empty list. A timeout of 0 means "do not wait".
  • Each consumer tracks its own offset, so any number of consumers can read the same topic, each at its own pace.
  • Topics are independent: work on one must not block another.

Worked example: a consumer loop

A consumer starts at offset 0 and repeats batch = poll("orders", offset, 64, 200), then offset += batch.size(). If the topic holds 10 messages, the first poll returns offsets 0 to 9 at once and the next one waits. When a publisher appends offset 10, the waiting poll wakes and returns it. If nothing arrives for 200 ms, it returns an empty list and the loop polls again. Several consumers can run this loop on the same topic, and each sees every message in the same order.

What the tests check

  • Offsets and order from one thread, max, and a poll past the end with no waiting.
  • Topics are independent: each has its own offsets starting at 0.
  • A poll on an empty topic times out after about its timeout.
  • A waiting poll wakes promptly when a message is published.
  • Every consumer waiting on a topic wakes for a new message, not just one of them.
  • A poll waiting for offset 5 is woken by offsets 0, 1 and 2 arriving, keeps waiting, and still returns empty at its original deadline (not early, and not with its timeout restarted).
  • 8 publishers, 4000 messages: offsets are exactly 0 to 3999, increasing within each publisher, and each offset holds the message it was returned for.
  • 4 consumers polling while 4 publishers write: every consumer sees exactly the final log, in order.
  • In C++, ThreadSanitizer must stay quiet.

Open them one at a time. Each one gives away a little more.

One topic is one monitor: a lock, a condition variable and a list. publish appends under the lock, takes the new size minus one as the offset, and wakes the waiters. Because the append and the offset come from the same critical section, offsets cannot repeat or skip.
poll waits while log.size() &lt;= fromOffset, in a loop. Several consumers may wait for different offsets, so after an append wake all of them (signalAll, notify_all): each one re-checks its own condition.
Keep the deadline fixed across wakeups. In Java, awaitNanos returns the time left; loop until the condition holds or the time left reaches zero. In C++, compute a deadline once and use wait_until with a predicate, which returns false on timeout.
Look up or create the topic atomically (computeIfAbsent, or a map mutex in C++ with std::unique_ptr values so the topic's address stays fixed). Return a copy of the slice, not a view of the live list.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How would you add consumer groups, where each message goes to only one consumer of a group?
Kafka's answer is partitions: split a topic into P partition logs, give each partition to exactly one consumer in the group, and store a committed offset per (group, partition). Within a partition order is kept; across partitions it is not. Rebalancing reassigns partitions when consumers join or leave.
Memory grows forever. What would you do?
Retention: drop the oldest messages by age or size and remember the offset of the first message still kept. A poll below that offset either fails or skips forward to it. Real brokers store the log in segment files on disk and delete whole old segments.
What if you must push messages to subscribers with callbacks instead of letting them poll?
Give each subscriber its own bounded queue and its own delivery thread, so a slow subscriber blocks only itself (the "without one blocking another" requirement Uber candidates have reported). When a subscriber's queue is full, decide: block the publisher, drop, or disconnect the slow subscriber.
Why not signal or notify_one?
The waiters are not interchangeable: they may wait for different offsets, on behalf of different consumers. Waking one leaves the others asleep although their data is there, until their timeout. With one condition per topic, wake everyone and let each re-check. Waking many is cheap compared with a consumer that stalls for a whole timeout.
Readers copy under the lock, which blocks publishers. Can you do better?
For an append only log, readers only need the current size: publish could append to a structure that never moves old entries (chunks of fixed arrays) and then publish the new size with a release store; readers read the size with an acquire load and copy without the lock. Waiting still needs the condition. It is a good optimization to mention after the simple version works.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

A topic is an append only list guarded by its own monitor. The offset is just the index in the list, assigned in the same critical section as the append, which is what makes offsets dense, unique and ordered. Consumers are passive: they read by offset and wait on the topic's condition when they are caught up.

Invariants

  • For every topic, the message at index i was returned offset i by exactly one publish.
  • Entries are never changed or removed, so a poll that returns offsets a to b returns the same messages whenever it runs.
  • A poll returns empty only if, at its deadline, there was still no message at fromOffset.

Why each primitive

  • A lock per topic, so publishers on different topics never contend.
  • A condition per topic with signalAll, because waiters wait for different offsets.
  • awaitNanos or wait_until with a fixed deadline, so spurious or irrelevant wakeups neither return early nor stretch the timeout.
  • computeIfAbsent (or a map mutex) for topics, so two first publishers cannot create two logs for one name.

Pitfalls

  • signal or notify_one: the broken version the tests catch, where two of three waiting consumers sleep until their timeout.
  • if instead of while around the wait: a wakeup for offset 0 makes a consumer waiting for offset 5 return early or index past the end.
  • Restarting the full timeout after each wakeup: a busy topic can then keep a poll waiting forever.
  • Returning subList (a live view) in Java: the caller then reads the list while publishers modify it.
  • An AtomicLong for offsets with the list updated separately: the offset and the position in the list can disagree.

Cost

publish is O(1) amortized under the topic lock. poll copies up to max messages under the lock. Topics scale independently.

How to say it in the interview

Each topic is an append only log with its own lock and condition. Publish appends and takes the index as the offset in one critical section, so offsets are dense and unique with any number of publishers, then wakes all waiters on that topic. Poll waits in a loop while its offset does not exist yet, with a fixed deadline, and returns a copy of up to max messages. Consumers own their offsets, so many can read the same topic independently, and different topics never share a lock. Next I would add retention, partitions for consumer groups, and per subscriber queues if we need push delivery.
