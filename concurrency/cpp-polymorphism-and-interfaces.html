Polymorphism, abstract classes and operator overloading

Express C++ interfaces with virtual functions or concepts, choose a callable abstraction, and give value types predictable operators.

Before this:Inheritance and virtual functionsTemplates, auto and type deductionLambdas, captures and callables

A good C++ interface lets you change the implementation without changing the caller's reasoning. The language offers runtime interfaces, compile time constraints, and ordinary callable objects; knowing which one you need keeps a low level design answer small and testable.

In plain words

A wall socket standardizes how appliances connect. You can buy a desk with one particular lamp built into it, or leave a socket for whichever lamp you choose later. Both arrangements have rules about what fits; the difference is when you choose and how easily you can swap the lamp.

Why this matters for concurrency

A scheduler needs a clock, a cache needs a loader, and a worker needs a task. Their interfaces hide behavior, but they do not hide lifetime or sharing requirements. A callback can own a mutable counter; an interface can expose an unsafe reference. Read class invariants and executor anatomy after learning the syntax here.

An abstract class is the usual C++ interface

C++ has no interface keyword. The usual owning interface is a class with pure virtual functions, written virtual int read() const = 0;, and a public virtual destructor. The = 0 marks a pure virtual function; it does not provide a default return value. A class is abstract when at least one final overrider is pure virtual: you can name pointers and references to it, but cannot instantiate it.

The final overrider is the implementation virtual dispatch selects in that class. A concrete class must supply or inherit a nonpure override for every pure virtual operation. A pure virtual function can have an out-of-class body, called explicitly with a qualified name such as Reader::read(), while the declaring class remains abstract.

An interface can contain data and implemented methods, but a small contract is easier to substitute and test. Make behavior methods public; keep implementation state in the concrete class. override catches signature errors, including a missing const; an override must also respect a base function's noexcept promise. A pure virtual destructor is legal and still needs a definition when derived objects are destroyed, because derived destruction invokes it.

The qualified call uses the base body without virtual dispatch. FixedReader supplies read() and its implicit destructor overrides the base destructor, so it is concrete. For an ordinary interface, the simpler destructor is virtual ~Reader() = default;. A virtual call to a pure function during base construction or destruction is undefined behavior even if that pure function has a body; see construction and virtual dispatch.

Pass Reader& or const Reader& to borrow. Use std::unique_ptr<Reader> to transfer ownership and std::shared_ptr<Reader> only when multiple owners are actually required. None of these choices promises that concurrent calls to read() are safe. Even a const function can modify mutable fields or external objects. Document the concurrency contract separately.

With the default deleter, std::unique_ptr<Reader> deletes through Reader*, so a derived object requires a virtual base destructor. A deliberately nonowning base can instead use a protected nonvirtual destructor to prevent deletion through the interface. Keep abstract interfaces behind pointers or references; copying a concrete base by value slices away the derived part.

Runtime and compile time polymorphism

Templates do not require inheritance. A type satisfying the required expressions can participate. A concept checks declared syntactic and type requirements; it cannot generally prove that an implementation is thread safe, never blocks, or obeys a business invariant. State those semantic requirements in prose. In C++17 you can use an unconstrained template, sometimes with static_assert; concepts make intent clearer in C++20.

requires(const T& object) introduces an imagined object used only to check expressions. The braces around object.read() and the trailing std::same_as<int> require an int result, rejecting short and int& even though they could supply an integer value. template<Readable R> is shorthand for a template parameter constrained by that concept. This check does not execute the function or generally validate its body; adding noexcept to the compound requirement could check its declared nonthrowing property.

The runtime interface and the template can coexist: twice(view) deduces R as Reader and still makes a virtual call. A known concrete type may allow inlining, but templates do not guarantee it; compilers can also devirtualize calls when they know the target. Templates can increase instantiation work and code size, while runtime interfaces let callers share one static interface type.

dynamic_cast: checked navigation, not a dispatch strategy

For the downcasts above, the source base is polymorphic, meaning it has a virtual member. dynamic_cast<Derived*>(base_pointer) returns null on a type mismatch; the reference form throws std::bad_cast. A null source pointer remains null. Ordinary safe upcasts do not need a dynamic cast. These checked runtime casts use runtime type information, which must be enabled in the build.

Use a cast when the caller legitimately asks whether an optional concrete capability is present. A long chain of casts followed by different behavior usually belongs in virtual functions, a visitor, or a closed std::variant. A static_cast downcast skips the runtime check; using a wrong downcast is not a faster safe alternative. A successful cast also says nothing about whether another thread may destroy or mutate the object.

The source must refer to a valid object; a dangling pointer is not a type mismatch that the cast safely detects. With suitable public, unambiguous inheritance, dynamic_cast can also cross from one interface to another implemented by the same object, adjusting the pointer as needed. It cannot remove const.

Operators are named functions with familiar spelling

Operator overloading lets a user-defined type participate in expressions such as a == b, a < b, out << a, callable(x), and buffer[i]. You cannot invent an operator, change precedence, or make an overloaded logical operator preserve built-in short circuit semantics. Keep the meaning recognizable. A queue should expose push() rather than hiding a blocking operation behind a surprising arithmetic operator.

A spaceship operator defaulted in the class can supply rewritten relational expressions, and implicitly declares equality when the class declares no member or friend named operator==. A manually written spaceship does not by itself provide equality. The result category matters: integral members support strong ordering, while floating point can give partial ordering because NaN is unordered.

If NaNs are possible, ordinary floating comparison does not give an ordered container the strict weak ordering it needs; restrict the domain or choose an appropriate ordering policy. For example, neither 1.0 nor NaN compares less than the other, and the same holds for NaN and 2.0, yet 1.0 < 2.0: the induced equivalence is not transitive. A defaulted comparison examines all participating members; putting a mutex in the object does not give that mutex a meaningful comparison.

For an ordered container, two keys are equivalent when neither compares less than the other, which need not match operator==. For a hash container, equal keys must have equal hashes, but unequal keys may collide. Keep keys and comparison behavior stable while stored; a comparator reading concurrently changing external state can break ordering even when its reads are individually synchronized.

The output is 1:9 2:0 42. Comparison is lexicographic: tenant decides before sequence. The extra parentheses around an assert containing a braced initializer keep its comma from confusing the assert macro. at() makes our indexing throw on a bad index; an ordinary built-in array subscript would not perform that check.

In C++17, write operator== and operator< explicitly; with <tuple>, comparing std::tie(tenant, sequence) against std::tie(other.tenant, other.sequence) gives the same field order. Operators are still functions: nonmember binary operators allow implicit conversions on either operand, and a nonmember stream operator lets the stream remain the left operand. Overloading cannot change precedence or the number of operands.

Assignment and concurrent value semantics

Construction creates a new object; assignment modifies an existing one. Prefer the rule of zero: let value members implement copying and moving. A class containing a mutex is not copyable or movable by default. That is often correct for a service whose address and synchronization identity should remain stable. Explicitly delete copying if the API should make that intention clear.

Slots follows the rule of zero: its implicit copy assignment copies the array. Declaring copy assignment yourself, even as = default, suppresses implicit move operations; decide the complete copy and move policy when customizing it. = delete is useful for an identity-bearing service whose state should not be copied.

If you truly need assignment between synchronized objects, define what is copied and lock both source and destination consistently. Handle self assignment before acquiring a nonrecursive mutex twice, then use std::scoped_lock for both mutexes; a source mutex locked through const T& normally needs to be mutable. Do not copy the mutex itself, and define what state remains if copying the protected data throws.

Returning T& from assignment permits chaining. Returning a reference into synchronized storage from operator[] is different: if the method releases its lock on return, protection ends before the caller uses the reference. A thread safe container commonly offers copied values or operations performed under its lock instead. See concurrent iteration for the related iterator problem.

std::function or a virtual interface?

A function object supplies operator() and may store state; a lambda is a compiler-generated version of that idea. Templates can keep its exact type; std::function<R(Args...)> uses type erasure to hide the concrete callable behind one copyable wrapper. It owns its stored target, which may be a function pointer, lambda, or function object satisfying its requirements. It may allocate, and an empty wrapper throws std::bad_function_call when invoked.

In C++20 the stored target of std::function must be copy constructible, even if you move it into the wrapper. A lambda owning a unique pointer is therefore not directly suitable. For a queued task producing a future, the move-only std::packaged_task can fit: it stores a result or exception in shared state and runs once per state, with reset() needed before reuse. C++23's std::move_only_function is outside this C++20 toolkit.

Choose a virtual interface when several named operations share one lifecycle contract, such as read(), flush(), and close(). Choose a callback for one operation, such as a clock function or a completion action. A const std::function can still call a target that changes state, so concurrent invocation requires a safe target. Copying the wrapper can copy captured values while still sharing objects referenced by its captures.

Owning the callable does not necessarily own its dependencies. A reference capture or std::ref borrows an object; a captured std::shared_ptr extends that object's lifetime without serializing its methods. Concurrent replacement or destruction of a wrapper must also be coordinated with its callers. Neither const nor a successful type check supplies that coordination.

Worked example: a cache loader boundary

A cache needing only load(key) can accept a callable. A loader with open, load, health, and close operations may deserve an interface. In either case, state whether loads run concurrently, whether the cache owns the loader, and whether callbacks may call the cache again.

Suppose two callers miss key K and the contract allows only one in-flight load per key. Store a shared completion object, such as a shared future, under the cache lock before releasing it. The first caller owns the load; later callers copy that completion handle and wait outside the lock.

For this successful trace, assume no eviction or invalidation. If loading throws, complete the shared state with the failure and remove the pending entry under the lock according to your retry policy, so waiters cannot hang. A loader recursively requesting the same pending key would wait for itself; prohibit recursive loading or detect such dependency cycles. Practise the full eviction and loading rules in retain-best cache.

Common mistakes

  • Thinking = 0 provides a default return value: it makes a function pure virtual.
  • Using a concept as proof of thread safety: it checks expressions, not interleavings.
  • Assuming a handwritten spaceship creates equality: define equality explicitly when needed.
  • Returning an unlocked mutable reference from a synchronized container: the caller can bypass its invariant.
  • Capturing a short lived object by reference in a stored callback: the wrapper does not extend its lifetime.

In the interview

Expect a dependency choice, a failed override, or a request to predict callback or comparison behavior. Explain what must vary and when the choice is made, then state ownership, mutation, and failure behavior. Prepare for follow ups: can a pure function have a body, can a template still dispatch virtually, and what does copying the callback actually copy?

I use a virtual interface for a runtime service with several related operations, a callback for one injected action, and a constrained template when the concrete type can remain a compile time choice. Each option still needs an explicit lifetime and concurrency contract.

Key takeaways

  • A pure final overrider makes a class abstract even when the pure function has a body.
  • Templates and concepts check types at compile time; their bodies can still make virtual calls.
  • Operators should preserve familiar value semantics and container ordering contracts.
  • std::function owns its target; captured dependencies may still be borrowed or shared unsafely.
  • A thread safe API must keep protection and lifetime valid for the caller's entire access.

Why. The equals-zero syntax marks a pure virtual function, not a return value. An out-of-class body leaves that declaration pure. A class whose final overrider remains pure is abstract; a concrete descendant needs a nonpure override, possibly inherited from an intermediate base.
A valid dynamic_cast downcast from a live polymorphic base fails its runtime type check. What happens for pointer and reference results?
Why. A failed pointer check has a null result; a reference cannot represent that result, so its check throws std::bad_cast. Failure of a valid runtime check is defined behavior. A dangling source would violate the question's live-object premise.
What can the Readable concept in the sample establish?
Why. The requirement checks that the call expression is valid and yields int, not merely something convertible to it. It neither executes the body nor proves the absence of I/O or data races. Those semantic contracts need separate reasoning.
With the defaulted Key spaceship, what is Key{1, 99} < Key{2, 0}?
Why. The comparison is lexicographic in declaration order: 1 < 2 decides the result before the sequence fields matter. C++20 can rewrite this relational expression using the defaulted spaceship, so a handwritten operator< is unnecessary.
A C++20 lambda captures a std::unique_ptr by move. Can std::function store that lambda directly?
Why. The lambda is move only because its captured unique pointer cannot be copied. mutable changes the call operator, not copyability. Moving into std::function does not waive the wrapper's requirement that its stored target be copy constructible.

Why. The reference escapes the synchronization boundary; locking the lookup does not protect a later read or write. A const getter does not stop other threads mutating or erasing the element. Return a snapshot or provide an operation with a clearly bounded protected access period.

Design
Choose an abstraction for a configurable clock and for a storage connection with read(), flush() and close().
Model answer
A single clock operation can be a callback or a small Clock interface; an interface is helpful when fake and real clocks have named shared semantics. The storage connection naturally fits a virtual interface with several related operations. Document ownership, concurrent call permissions, and failures in either design, including whether close() may overlap a read. For owning base pointers with default deletion, give the interface a public virtual destructor.
Explain
Why does a defaulted spaceship work for Key but fail for an otherwise similar class containing a mutex?
Model answer
The defaulted comparison compares participating bases and members. Integers have comparisons; a mutex has no comparison operations, so the generated operation is deleted when it cannot compare that member. Take a deliberately chosen value snapshot under the appropriate lock, then compare snapshots outside the lock. Simply skipping the mutex while reading live mutable fields would still risk a data race.
Debug
An interface call succeeds during a test but crashes later in a worker. The implementation was captured by reference in std::function. What is missing?
Model answer
The callback borrows the implementation. Ensure it outlives every invocation, or capture a suitable owning pointer and define shutdown. Also check concurrent access to the implementation: extending its lifetime does not serialize its methods.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Would you inject a dependency with a template, std::function, or a virtual interface?"
What a strong answer covers
  • Identify when the implementation is selected
  • Templates preserve concrete types and support compile time constraints
  • Callbacks fit one operation
  • Interfaces fit related operations and require ownership contracts
How a senior would say it
I start with when the choice is made and how many operations belong together. A template is useful when the concrete type is known at compilation and I want generic code without a runtime base class. A concept makes its expression requirements explicit. A callback is a compact choice for one operation, such as a clock reading. A virtual interface fits a service with several related operations and implementations chosen at runtime. I would then state who owns the dependency and whether calls can overlap. None of these mechanisms automatically makes the implementation thread safe.

Likely follow up: Can a concept prove that a callback never races?

Out loudabout 60 s
"Explain why overloading brackets can make a thread safe container unsafe."
What a strong answer covers
  • A reference can escape the locked method
  • Unlock ends protection before the caller uses it
  • Const does not repair shared mutation elsewhere
  • Return a copy or expose a controlled operation
How a senior would say it
A bracket operator often returns a reference. If my implementation locks, finds an element, unlocks, and returns that reference, the caller now touches the element without the container lock. Another thread could modify or erase it. Even a const reference can race with a writer and can become invalid after erasure. I would return a value snapshot when practical, or expose a narrow operation that keeps the required protection for the whole action. I would also avoid running arbitrary user code under an internal lock unless that is an explicit, carefully constrained contract.

Likely follow up: What lifetime problem remains if the returned reference is const?

Out loudabout 60 s
"Two workers call the same const std::function, and a race detector flags its captured counter. What do you check?"
What a strong answer covers
  • A const wrapper can invoke a mutable target
  • Overlapping writes to the same plain counter need synchronization
  • Copying a value capture can separate state but changes the counter's meaning
  • Reference and shared pointer captures can keep state shared across copies
  • Ownership and shutdown must keep the target and dependencies alive
How a senior would say it
I would inspect what the lambda captures and whether the workers invoke the same stored target. A const function wrapper can still invoke a mutable lambda. If both calls increment the same plain integer without synchronization, that is a data race. Copying a lambda that owns an integer gives separate counters, which may change the intended result. Copying one that holds a reference or shared pointer still reaches the same underlying counter. For a shared total, I would use an atomic counter or a mutex, depending on whether other state belongs to the invariant. I would also ensure shutdown waits for calls to finish before destroying the wrapper or its borrowed dependencies.

Likely follow up: Would replacing a reference capture with a shared pointer fix the data race?
