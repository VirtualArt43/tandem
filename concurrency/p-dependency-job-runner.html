Dependency-aware job runner

Executors and asynchard60 minRubrikUber

The most frequently reported Rubrik system coding question: run a graph of jobs on a few threads, start each one as soon as its dependencies have succeeded, and stop cleanly on the first failure. Rubrik hides the graph behind an API, which turns a topological sort into a real concurrency problem.

The task

You get the graph only through a JobSource. You do not know the edges; you can only ask which jobs are ready.

  • allJobs() returns every job id (without dependencies).
  • nextJobs(finished) returns every job that has not finished and whose dependencies have all finished. It can return a job that is already queued or running, so never start a job twice. Treat it as someone else's API: it may be slow, so do not call it while holding your lock.
  • run(job) does the job's work and may throw.

Write JobRunner(threads) and execute(source):

  • Every job runs exactly once, only after all its dependencies have finished successfully.
  • A job starts as soon as its own dependencies are done, not when a whole "level" is done, and up to threads jobs run at the same time.
  • On the first failure, no new job starts, not even one that was already ready. execute waits until the jobs that are still running have finished, then throws (JobFailedException in Java, JobFailed in C++) naming the failed job and carrying its exception.
  • If some jobs can never become ready (a cycle, or a dependency on a job that does not exist), run everything that can run, then throw (IllegalStateException in Java, std::logic_error in C++).
  • execute returns only when nothing is running, and every thread it started has ended. The same runner can run another graph afterwards.

Rules, as in the interview: no library executors, thread pools, concurrent queues or latches; build the workers and the ready queue from threads, one lock and a condition variable. Rubrik candidates report exactly this: "no built-in Java concurrency at all", "ExecutorService not allowed".

Where it comes up: six Rubrik reports from 2024 and 2025, and older ones back to 2021 (a pipeline manager over a DAG whose execute() must end on full success or on the first failure with nothing left running; a job runner over getDependentTasks where the first exception must stop everything; get_next_jobs(finished_jobs) with every available job run concurrently; overnight I/O tasks behind an API that returns what can run now), and an Uber round that asked for a multithreaded job scheduler with prerequisites and maximum parallelism.

What the tests check

  • A diamond, a chain and a loose job: every job runs once, after all its dependencies.
  • 8 independent jobs on 3 threads: exactly 3 run at once, never more.
  • A 300 ms job and a 10 ms job with a child: the child starts before the slow job ends.
  • One thread, and the second job to start fails: exactly 2 jobs ever start, and the exception names the failing job and carries its cause.
  • A job fails while a 300 ms job runs: jobs that become ready afterwards never start, and execute returns only after the 300 ms job has ended.
  • A cycle and a missing dependency: the jobs that can run do, then execute throws the cycle error.
  • A random graph of 150 jobs (120 in C++) on 6 threads: every edge respected, each job once, never more than 6 at once (the seed is printed).
  • Threads that ran jobs have ended when execute returns, the runner can run two more graphs, and an empty graph returns at once. In C++, ThreadSanitizer must stay quiet.

Taught in: A parallel job runner that respects dependencies

Open them one at a time. Each one gives away a little more.

Start N worker threads that share a ready queue under one lock. Fill the queue with nextJobs of the empty set. A worker takes a job, runs it outside the lock, marks it finished, and asks the source what has become ready. What stops the same job from being queued twice?
Keep a seen set: a job enters the queue only the first time any worker learns about it. Call nextJobs outside the lock with a copy of the finished set; whichever dependency finishes last sees all of them in its copy, so no ready job is missed.
When is the run over? Not when the queue is empty: a worker that just finished a job may be about to queue its successors. Count a worker as busy from the moment it takes a job until its successors are queued. The run is over when the queue is empty and nobody is busy; a worker that sees that wakes the others and exits.
Failure: record the first one under the lock and wake everyone. Workers must check for a failure before taking a job, and stop queuing successors. execute joins all the workers, so it returns only after the running jobs end, then throws. After a clean finish, any job in allJobs() that never finished could never become ready: throw the cycle error.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Jobs fail transiently. Retry each job up to 3 times with backoff before failing the run.
Keep an attempt count per job. Retrying in place (sleep, then run again on the same worker) is simple but holds a thread while it sleeps. Better: on failure, if attempts remain, put the job back with a not-before time and let workers skip jobs that are not due yet, which turns the ready queue into a small scheduled executor. Only the last attempt's failure counts as the first failure of the run. Retries are only safe if jobs are idempotent, so ask.
Instead of stopping everything, keep running whatever does not depend on the failed job.
Record the failure but do not set the stop flag. With nextJobs, a failed job never enters the finished set, so its dependents never become ready and are skipped automatically, transitively. At the end, report the failed jobs and, from allJobs(), the ones that never ran because of them. If you need to tell "skipped because of a failure" apart from "part of a cycle", you need the edges, so ask for a dependencies API.
Some jobs are recurring: the whole pipeline runs every night, or a job reruns every hour.
Keep all per-run state (ready queue, seen, finished, busy, failure) in one execution object, as the reference solution does, so a run is independent of the runner and two runs never share state. A scheduler starts a new execution each period; decide whether a run may start while the previous one is still going (usually not: fixed delay semantics, or skip the run and alert). A single recurring job inside a graph is better modelled as a fresh job id per occurrence.
One report says the first exception must stop everything immediately. How do you stop jobs that are already running?
You cannot kill a thread safely. In Java, interrupt the workers that are running jobs and require jobs to respond to interruption (blocking calls throw InterruptedException; loops check the flag). In C++, pass a std::stop_token to each job and request stop on failure. Either way execute still waits for the jobs to return, because "nothing left running" is the guarantee callers rely on.
The API is getDependentTasks(done): it only tells you who depends on a finished job. What changes?
Knowing the dependents is not enough to know when they are ready: a dependent with three parents must wait for all three. You need each job's number of unfinished dependencies (its in-degree), from another API call or a first pass over the graph. Then the runner keeps an in-degree counter per job, decrements it under the lock when a parent finishes, and queues the job when it reaches zero. That is Kahn's algorithm run concurrently.
Can you detect a cycle before running anything?
Only if you can see the edges. With them, run Kahn's algorithm on a copy: repeatedly remove jobs with no remaining dependencies; if fewer jobs are removed than exist, the rest contains a cycle. A depth-first search with three colours also works. With only nextJobs, the earliest you can know is when the runner stalls: nothing queued, nobody busy, and some jobs unfinished.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

A worker pool over a ready queue, plus termination detection. Under one lock the runner keeps the ready queue, a seen set, the finished set, a busy count and the first failure. The invariants: a job is queued at most once, and the run is over exactly when the queue is empty and no worker is busy, where a worker is busy from taking a job until the jobs that its completion made ready are queued.

Why each line is there

  • seen. nextJobs keeps returning jobs that are queued or running until they finish, so deduplication must happen in the runner, under the lock.
  • nextJobs outside the lock, on a copy. It is foreign code and may be slow; holding the lock across it would stall every other worker. The copy is safe because the last dependency of any job to finish takes its copy after all the others were added, so it sees the job as ready.
  • The wait condition. A worker sleeps while there is no failure, nothing queued, and someone is busy. It wakes to take a job, or to exit on a failure or at the end. Every change of state signals all, because both "take a job" and "exit" waiters may be waiting.
  • The first failure wins, and nothing starts after it. Workers check the failure before taking a job and stop queuing successors, so even jobs that were already ready never start.
  • execute joins its workers. That is what "nothing is left running" means in code, and why no thread outlives the call. All per-run state lives in an object made by execute, so the runner can be reused.
  • Cycles at the end. With only nextJobs, a cycle shows up as a stall: the run ends cleanly but allJobs() contains jobs that never finished.

Cost and trade-offs

Each job costs one nextJobs call and one copy of the finished set, so a graph of n jobs costs O(n squared) set copying in the worst case. That is fine for thousands of jobs; for millions, use an in-degree counter per job and an API that returns a job's dependents. Running level by level is simpler and also correct, but every level waits for its slowest job; the third test shows the idle time it costs.

How to say it in the interview

I will start N workers sharing a ready queue under one lock, seeded with nextJobs of the empty set. A worker takes a job, runs it outside the lock, adds it to finished, then calls nextJobs outside the lock on a copy and queues anything it has not seen before, so nothing runs twice. A worker counts as busy until those successors are queued, so the run ends exactly when the queue is empty and nobody is busy. The first failure is recorded under the lock and wakes everyone; no new job starts after it, and execute joins the workers, so it returns only when nothing is running, then throws with the failed job. If the run ends with jobs that never finished, there was a cycle or a missing dependency. Next I would add retries with backoff, and skipping only the dependents of a failed job.
