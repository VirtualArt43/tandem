What is the Java memory model, and what are the happens-before rules?
Model answer

The memory model (JLS chapter 17) defines which values a read is allowed to see. Without synchronization, the JIT may keep values in registers and reorder instructions, and the CPU may reorder memory operations, so a read can see a stale or out-of-order value. The model's central relation is happens-before: if action A happens-before action B, then A's effects are visible to B.

  • Program order: within one thread, each action happens-before the later ones.
  • Monitor: unlocking a monitor happens-before every later lock of the same monitor.
  • Volatile: a write to a volatile field happens-before every later read of that field.
  • Thread start: t.start() happens-before everything t does.
  • Termination: everything t does happens-before another thread returns from t.join().
  • Interrupt: t.interrupt() happens-before t detects the interrupt.
  • Transitivity: chains combine.

java.util.concurrent adds documented edges: putting into a concurrent collection happens-before taking out; submitting a task happens-before it runs; a task's actions happen-before Future.get returns; countDown and release happen-before the matching await and acquire. Final fields have their own freeze rule.

The payoff is the DRF guarantee: a program with no data races (every conflicting pair of accesses ordered by happens-before) behaves as if sequentially consistent. Unlike C++, a racy Java program is not undefined; it just gets very weak guarantees.

Likely follow up: "Is happens-before the same as 'happened earlier in time'?" No. It is an ordering of visibility. A write can occur earlier in real time and still be invisible to a later read if no happens-before edge connects them.

2CorevolatilejavaMicrosoft
What exactly does volatile guarantee in Java, how is it implemented, and is it needed on a single-core machine?
Model answer

Guarantees: visibility (a read sees the most recent write in the synchronization order), ordering (writes before a volatile write cannot move after it, and reads after a volatile read cannot move before it; volatile accesses are also sequentially consistent among themselves), and atomic reads and writes of long and double, which may otherwise tear. It does not make compound actions atomic: count++ on a volatile still loses updates, and there is no mutual exclusion.

Implementation in HotSpot: on x86, volatile loads are ordinary loads, because x86 never reorders loads with other loads. Volatile stores are followed by a StoreLoad barrier, typically a lock-prefixed instruction, because the store buffer is the one reordering x86 allows. On ARM64 the JIT uses ldar for volatile loads and stlr for volatile stores. Just as important, the JIT may not cache a volatile in a register or hoist its read out of a loop.

On a single core, threads take turns on one CPU, and a thread always sees its own core's store buffer, so hardware reordering between threads is not visible. The compiler is still the problem: without volatile, the JIT may hoist while (!stop) into a register and loop forever, on one core or forty. So yes, it is still needed.

Likely follow up: "volatile or AtomicInteger?" volatile gives visibility and ordering for single reads and writes. An atomic adds read-modify-write operations such as incrementAndGet and compareAndSet.

3SeniorsynchronizedmonitorsinternalsjavaMicrosoft
How does synchronized work inside HotSpot?
Model answer

Every object has a header whose mark word can describe a lock.

  • Uncontended: the JVM acquires the lock with a single CAS on the mark word, a thin or lightweight lock. No operating system involvement and no ObjectMonitor.
  • Contended, or when wait and notify are used: the lock inflates into a heavyweight ObjectMonitor that records the owner, a recursion count for reentrancy, an entry list of threads waiting to enter, and a wait set of threads in wait().
  • A contending thread first spins adaptively for a short time, because the holder often releases within microseconds. Only then does it park, which on Linux ends in a futex wait in the kernel.

Biased locking, an optimization for objects only ever locked by one thread, was disabled by default in JDK 15 (JEP 374) and later removed. The JIT adds lock elision (escape analysis proves the object never leaves the thread, so the lock disappears) and lock coarsening (merging adjacent blocks on the same object).

Entering has acquire semantics and exiting has release semantics, hence "unlock happens-before the next lock". wait releases the monitor completely, whatever the recursion count, and reacquires it before returning. At the hardware level the CAS is a lock cmpxchg on x86, which needs the cache line exclusively, so under contention that line bounces between cores.

Likely follow up: "What makes a contended monitor slow?" Inflation, parking and unparking through system calls, context switches, and cache-line transfers of the lock word.

4Corereentrantlocksynchronizedjava
synchronized or ReentrantLock: what does each give you, and which do you choose?
Model answer

Both give mutual exclusion, reentrancy and the same memory semantics.

ReentrantLock adds tryLock (immediate or with a timeout), lockInterruptibly, optional fairness, several Condition objects per lock (such as notFull and notEmpty), introspection (isHeldByCurrentThread, getQueueLength), and locking that is not block-structured, such as hand-over-hand traversal of a list.

synchronized adds automatic release on every exit path, including exceptions, so there is no forgotten unlock. The code is shorter, and the JIT can elide or coarsen it.

Virtual threads add one more point. In JDK 21 to 23, a virtual thread that blocks inside synchronized (or while waiting to enter it) pins its carrier thread, while one blocked on a ReentrantLock unmounts. JDK 24 (JEP 491) removed most of that pinning; native frames still pin.

5SenioraqsinternalsjavaConfluent
What is AbstractQueuedSynchronizer, and how is ReentrantLock built on it?
Model answer

AbstractQueuedSynchronizer is the framework under ReentrantLock, Semaphore, CountDownLatch, ReentrantReadWriteLock and the workers of ThreadPoolExecutor. It provides three things: one volatile int state whose meaning the subclass defines, compare-and-set on that state, and a FIFO queue of parked threads, a variant of the CLH queue.

A subclass implements tryAcquire and tryRelease (or the shared-mode versions), and AQS does the rest. acquire first calls tryAcquire, one CAS on the fast path. On failure it CASes a node onto the queue's tail and loops: first in line tries again, everyone else parks. release calls tryRelease and unparks the successor.

  • ReentrantLock: the state is the hold count, plus an owner thread. Free means state 0, so acquire is CAS 0 to 1 and record the owner; if the owner reacquires, the count goes up. The non-fair version barges with a CAS even when others are queued; the fair version first checks hasQueuedPredecessors().
  • Semaphore: the state is the number of permits.
  • CountDownLatch: the state is the count, and await succeeds in shared mode only when it reaches zero.
  • ReentrantReadWriteLock: one int split in two, the high 16 bits counting read holds and the low 16 bits write holds.

Conditions (ConditionObject) keep their own queue: await fully releases the lock and parks, and signal moves the node onto the main queue to reacquire. All of this gets its memory semantics from the volatile state and the CAS operations.

Likely follow up: "Why park and unpark instead of wait and notify?" park uses a per-thread permit, so an unpark that arrives before the park is not lost, and no monitor is needed.

6SeniorconcurrenthashmapinternalsjavaDatabricks
How does ConcurrentHashMap work since Java 8?
Model answer

A ConcurrentHashMap is an array of bins; each bin is a linked list or, when large, a red-black tree.

  • Reads take no lock. get does a volatile read of the table slot and walks nodes whose value and next fields are volatile, so it always sees fully published nodes.
  • Writes to an empty bin CAS the new node straight into the slot. Writes to a non-empty bin take synchronized on the bin's first node and update within that bin, so writers contend only when they hit the same bin.
  • A bin that grows past 8 nodes becomes a red-black tree when the table has at least 64 bins (otherwise the table grows instead), and turns back into a list when a resize leaves it with 6 or fewer.
  • Resizing is cooperative: moved bins hold a ForwardingNode; writers that meet one help transfer, and readers follow it to the new table.
  • The size lives in a base count plus striped counter cells, like LongAdder, so size() under concurrent updates is an estimate.

compute, computeIfAbsent and merge are atomic per key because the function runs under the bin lock, so keep those functions short and never modify the map inside them (it can deadlock or throw "Recursive update"). Iterators are weakly consistent and never throw ConcurrentModificationException. Nulls are banned so that a null from get can only mean "absent". Java 7 used 16 segments by default, each a ReentrantLock over its own table.

Likely follow up: "Is if (!map.containsKey(k)) map.put(k, v) safe on it?" No. Each call is atomic, but the pair is check-then-act; use putIfAbsent or computeIfAbsent.

7CorehashmapracesjavaDatabricks
Why is a plain HashMap unsafe with concurrent writers? What actually breaks?
Model answer

A put is a read-modify-write on a bucket chain and on size. Two threads inserting into the same empty bucket both read null, and each writes its own node: one entry vanishes. Concurrent size increments lose counts, and two threads that trigger a resize at once can lose or duplicate entries.

Before Java 8, resizing reversed each chain, and two concurrent resizes could link a chain into a cycle; a later get on that bucket then looped forever at 100 percent CPU, a well-known production failure. Java 8 preserves chain order, so that particular cycle is gone, but entries are still lost, and tree bins can be corrupted, which shows up as odd exceptions from inside HashMap.

Even one writer with concurrent readers is broken. Readers have no happens-before edge with the writer, so they can see a node before its fields are set, read a stale table after a resize, or miss keys that are present.

Fixes:

  • ConcurrentHashMap, almost always.
  • Collections.synchronizedMap, which puts one lock around every call. Compound sequences still need synchronized (map) { ... }, and so does iteration.
  • Confinement or immutability: build the map in one thread, then publish it safely and never change it.

Likely follow up: "Is synchronizedMap(m).putIfAbsent atomic?" Yes: since Java 8 the wrapper overrides the default methods (putIfAbsent, computeIfAbsent, merge) and runs them under its lock. A separate get followed by put is still a race.

8Seniorvirtual-threadspinningjava
How do virtual threads work, when do they help, and what is pinning?
Model answer

Virtual threads are final in JDK 21 (JEP 444). A virtual thread is a java.lang.Thread scheduled by the JVM, not the operating system. It runs mounted on a carrier, a platform thread from a dedicated ForkJoinPool whose parallelism defaults to the number of cores. When it blocks on network I/O, a java.util.concurrent lock, sleep or a blocking queue, the JDK unmounts it, saving its stack frames to the heap, and the carrier runs another virtual thread until the operation completes. (File I/O and, in JDK 21, Object.wait() hold the carrier instead; the scheduler compensates by temporarily adding a carrier.) So blocking code scales to hundreds of thousands of I/O-bound tasks.

Pinning: a virtual thread cannot unmount while it is inside a native method or foreign call, or, in JDK 21 to 23, inside a synchronized block or method. If it blocks there, its carrier blocks too. Enough pinned threads exhaust the carriers, and throughput collapses or everything stalls. JDK 24 (JEP 491) lets virtual threads unmount inside synchronized, which removes the main cause. You can detect pinning with the JFR event jdk.VirtualThreadPinned, and on JDK 21 to 23 with the jdk.tracePinnedThreads system property.

Guidance:

  • Do not pool them: create one per task.
  • Limit access to scarce resources with a semaphore, since there is no pool size to cap them.
  • Avoid caching heavy objects in thread-locals.
  • On JDK 21 to 23, prefer ReentrantLock around blocking calls.
  • Expect nothing for CPU-bound work.

Likely follow up: "Does a virtual thread make synchronized code thread-safe in a new way?" No. The memory model and the races are unchanged; only the cost of blocking changed.

9SeniorcompletablefuturethreadsjavaGoogleApple
Which thread runs a CompletableFuture callback?
Model answer

It depends on the stage type and on timing.

  • Non-async stages (thenApply, thenAccept, thenCompose, whenComplete): if the future is already complete when you register, your own thread runs the callback right there, inside thenApply. Otherwise the thread that completes the future runs it as part of completing it, along with every other waiting callback.
  • Async stages (thenApplyAsync and friends): the executor you pass, or by default ForkJoinPool.commonPool(). If the common pool's parallelism is below two, a new thread is created per task instead. supplyAsync and runAsync without an executor also use the common pool.

Consequences: a slow non-async callback hijacks whichever thread completes the future, which might be an I/O thread or a pool worker. Blocking work in the common pool starves parallel streams and every default async stage in the JVM, so pass your own executor for I/O.

Exceptions travel down the chain wrapped in CompletionException; join() throws it unchecked, while get() throws the checked ExecutionException. cancel(true) does not interrupt a running computation: the flag is ignored, and the future simply completes with a CancellationException.

Likely follow up: "How would you implement this yourself?" Keep the result and a list of callbacks; whoever completes the future runs the callbacks, and whoever registers on a completed future runs its callback immediately.

10Seniorfuturebuild-itjavaGoogleRubrik
Build a minimal CompletableFuture-like future: complete once, get, and thenApply.
Model answer

The state is a result or an error, a done flag, and the callbacks waiting for completion, all guarded by one lock. Three rules make it correct: the first completion wins, callbacks run outside the lock, and registering against a future that is already complete runs the callback immediately.

Why the step may read value without the lock: either it runs on the completing thread after that thread wrote the fields, or it runs after the caller saw done inside synchronized, which created the happens-before edge. Running callbacks outside the lock avoids deadlock with user code and keeps get callers from waiting behind slow callbacks. The registration race (register and complete at the same moment) is closed because both check done under the same lock.

Likely follow up: "Make it lock free." Keep a volatile result field that a CAS sets once from null (first completion wins), and a Treiber stack of pending callbacks pushed with CAS. The completer sets the result, then pops and runs every callback. A registering thread pushes its callback, then rechecks the result, and if it is now set, helps run whatever is still on the stack, so no callback is stranded. That is how the real CompletableFuture works: its fields are result and stack.

11Seniorthreadlocalleaksjava
How do ThreadLocal values leak, and how do you prevent it?
Model answer

Each Thread owns a ThreadLocalMap. Entries are keyed by the ThreadLocal through a weak reference, but the value is held strongly for as long as the thread lives.

Leak one, in thread pools: pool threads never die, so a value outlives its task. Buffers accumulate, and worse, stale context such as a user identity or tenant id leaks into the next task on that thread, a correctness and security bug.

Leak two, in application servers: a value whose class came from a web application's class loader pins that loader through the server's pool thread. After a redeploy, the old application stays in memory until Metaspace runs out. Stale entries are cleaned only opportunistically, during later get or set calls.

Prevention:

  • try { tl.set(x); ... } finally { tl.remove(); } around every task.
  • Wrap tasks in a decorator that clears context, or pass context explicitly as a parameter.
  • Declare thread-locals static final, not per instance.
  • With virtual threads, do not use thread-locals as a cache of expensive objects: there is one copy per virtual thread and no reuse.
  • Java 21 offers ScopedValue as a preview API (it became final in JDK 25): an immutable binding for the duration of a call, which cannot leak past it.

Likely follow up: "What does InheritableThreadLocal do with a pool?" It copies values when a thread is created, so pool threads inherit whatever their creator had at that moment, which is usually wrong for every later task.

12Seniorfinalsafe-publicationjava
What do final fields guarantee across threads?
Model answer

When a constructor finishes, the object's final fields are frozen. Any thread that obtains a reference to the object after that, even through a data race with no synchronization at all, is guaranteed to see the final fields as the constructor set them, together with everything reachable through them as of the freeze, such as the contents of an array or map filled in the constructor. Non-final fields carry no such guarantee: a racy reader may see their default values.

The conditions: this must not escape during construction (starting a thread in the constructor, registering a listener, storing this in a static field), or another thread may see the object before the freeze. Writes made to the referenced objects after construction are not covered.

This rule is why String and well-built immutable classes are safe to share even through races. The cost is a store-store barrier at the end of such constructors, which is free on x86 and a real instruction on ARM.

Likely follow up: "Can reflection or deserialization break it?" Changing a final field after construction (through reflection or Unsafe) is outside the guarantee, so other threads may not see the change.

13Coresafe-publicationjava
List the ways to publish an object safely in Java.
Model answer

safe publication means the reference and the object's contents become visible to the other thread together. The standard ways:

  1. Initialize it in a static initializer: static final Config C = new Config();. Class initialization runs under a JVM lock.
  2. Store the reference in a volatile field or an AtomicReference.
  3. Store it in a final field of a properly constructed object.
  4. Store it in a field that is guarded by a lock that readers also take.
  5. Put it into a thread-safe collection: a concurrent map, a blocking queue, CopyOnWriteArrayList, a synchronized wrapper.
  6. Hand it over through the concurrency utilities: Thread.start, ExecutorService.submit, completing a future, a latch.

Then what each kind of object needs:

  • Immutable objects (all fields final, no this escape) are safe even when published unsafely.
  • Effectively immutable objects, never changed after publication although their fields are not final, need safe publication and nothing more.
  • Mutable objects need safe publication and synchronization on every later access.

The classic unsafe publication is a plain field written by one thread and read by another, as in double-checked locking without volatile: the reader can see the reference before the object's fields.

Likely follow up: "Give an example of an effectively immutable object." A configuration object built once, put into a ConcurrentHashMap, and only ever read afterwards.

14SeniorcasatomicslongadderjavaDatabricksRubrik
How does compare-and-swap work in Java, and when do you choose LongAdder over AtomicLong?
Model answer

compareAndSet(expected, update) atomically checks whether the current value equals expected and, if so, writes update and returns true; otherwise it changes nothing and returns false. On x86 it is one lock cmpxchg, which holds the cache line exclusively; on ARM64 it is a load-linked and store-conditional loop or, with ARMv8.1, a single CAS instruction. Java exposes it through the atomic classes and VarHandle, with volatile semantics; the weakCompareAndSet variants may fail spuriously, so use them in loops.

A CAS loop is lock free: a failed CAS means another thread succeeded. Under heavy contention, though, threads keep retrying while the line bounces between cores. AtomicLong.incrementAndGet compiles to one hardware fetch-and-add where the CPU has one (lock xadd on x86, ldadd on ARMv8.1), so no retries, but every core still serializes on that line.

LongAdder spreads the load: a base value plus an array of cells, each padded against false sharing. A thread whose CAS on the base fails is assigned a cell and adds there instead. sum() adds the base and every cell, so it is not an atomic snapshot while writers are active.

Choose LongAdder for hot counters that are written far more than read (metrics, statistics). Choose AtomicLong when you need the exact current value or conditional updates: sequence numbers, compareAndSet logic, limits.

Likely follow up: "What is the ABA problem?" CAS compares values, not history: a value can change from A to B and back to A between your read and your CAS. AtomicStampedReference pairs the value with a version stamp to catch it.

15Seniorinterruptcancellationjava
What happens when you interrupt a Java thread, depending on what it is doing?
Model answer

interrupt() always sets the thread's interrupt flag. What happens next depends on where the thread is:

  • In sleep, wait, join, BlockingQueue.take, Condition.await, lockInterruptibly or Future.get: it throws InterruptedException and clears the flag.
  • Waiting to enter synchronized, or in ReentrantLock.lock(): nothing. It keeps waiting, and the flag is still set when it finally gets the lock.
  • Doing I/O on an interruptible NIO channel (FileChannel, SocketChannel): the channel is closed and the thread gets ClosedByInterruptException. The channel is now closed for every thread that shares it.
  • Blocked in Selector.select(): it returns immediately, with the flag still set.
  • Reading a classic java.io socket stream on a platform thread: not interruptible. Close the socket to unblock it. On a virtual thread (JDK 21) it is interruptible: the socket is closed and the read throws SocketException.
  • In LockSupport.park(): it returns, with the flag still set.
  • Running ordinary code: nothing, until the code checks Thread.interrupted() (which clears the flag) or isInterrupted() (which does not).

So cancellable code uses interruptible blocking calls, checks the flag in long loops, and never swallows InterruptedException: it either rethrows it or restores the flag with Thread.currentThread().interrupt().

Likely follow up: "Why is interrupting a thread that uses a shared FileChannel dangerous?" The interrupt closes the channel for every other thread too. Code that cancels with interrupts should not share NIO channels, or must be ready to reopen them.
