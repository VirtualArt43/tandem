Passing data in and getting results out

How arguments reach a thread in Java and C++, the dangling reference bug, and the safe ways to bring results and failures back.

Asked atDatabricksRubrik
Before this:Creating, starting and joining threads

A thread is useless until it has its input and you have its output. Most "why is my result zero" bugs in Java, and a large share of the crashes in threaded C++, live in these two hand-offs.

In plain words

You send a courier with a delivery. You can hand them a photocopy of the address (a copy), or say "the address is on the note on my desk" (a reference). The photocopy is theirs to keep. The note only works if it is still on your desk, unchanged, when they look at it. If you tidied your desk in the meantime, they go to the wrong house.

Getting the answer back works like a claim ticket at a tailor. You leave with a numbered ticket, and later you redeem it: if the suit is ready you get it, if not you wait, and if the tailor ruined it you hear about that too. That ticket is a future.

Data in: what Java copies and what it shares

A Java lambda or anonymous class can use a local variable from the enclosing method only if that variable is effectively final: assigned once and never changed. The lambda then captures a copy of its value. For a primitive that copy is the number itself. For an object, the copy is the reference, so the thread and the caller point at the same object.

You can capture effectively final locals or pass values to the constructor of a Runnable class. Both copy the value, so an object reference still points to the same object unless you explicitly copy its contents. Shared access needs immutability, synchronization, or a hand-off: after publication, only the receiving thread touches the object until it hands ownership back.

Data in: what C++ copies, references and moves

std::thread (and std::jthread) copies every argument into storage that belongs to the new thread, then calls your function with those copies passed as rvalues. Copying is the default even when your function takes a reference. Three consequences follow:

  • To share, say so. A function taking std::vector<int>& does not compile if you pass the vector directly, because a copied rvalue cannot bind to a non-const reference. Wrap it in std::ref(v); then you are responsible for keeping v alive and for synchronizing access.
  • Move only arguments must be moved. A std::unique_ptr or a std::promise cannot be copied, so pass std::move(p): ownership goes to the thread.
  • Member functions copy the object unless you pass a pointer. std::thread t(&Worker::run, w, 5) runs run on a copy of w; the original never changes. Pass &w or std::ref(w).

Lambdas follow their capture list: [x] or [=] copies at the moment the lambda is created, [&x] or [&] refers to the original, and an init capture such as [p = std::move(p)] moves an object in.

In both versions results is shared, and it is safe only because of a discipline you cannot see in the types: exactly one thread writes it, and the main thread reads it only after joining that thread. The moment two threads write it, you need a lock or a thread-safe structure.

The loop variable trap

The most common slip is starting one thread per loop iteration and using the loop counter inside it. Java refuses to compile it. C++ compiles it and gives you a race.

In the buggy C++ loop, each thread reads i while the main thread increments it, which is a data race. A thread may see 4 and index past the end, and after the loop the reference points at a variable that no longer exists. Capture by value anything that changes after the thread starts. Java's effectively final rule exists for exactly this reason: a captured local is a copy, so letting it change afterwards would be meaningless.

Data that changes or disappears under the thread

The general form of the trap: you give a thread access to something, and then the something changes or dies before the thread is done with it. In C++ that is a dangling reference, which is undefined behavior. In Java the garbage collector keeps objects alive, so the Java version is quieter: a shared mutable object that the caller keeps changing.

The C++ rule of thumb: a thread must never outlive the data it refers to. If the thread is always joined before the data goes out of scope, references are fine, which is why the parallel sum in the previous lesson could pass the array by reference. If you cannot guarantee that, copy the data in, move ownership in, or share it through a std::shared_ptr so the last user frees it.

Results out, way 1: shared slots plus join

The simplest way back: give each thread its own place to write, and read those places only after joining. You saw it in the parallel sum, with one array slot per thread.

It is fast and needs no extra types. In this design, each result is tied to its writer's whole lifetime. A timeout needs a timed join in Java or a separate completion signal in C++, which has no standard timed join. A failed Java worker may leave a default value with no failure recorded in the slot; an exception escaping a raw C++ worker terminates the process. Slots need an explicit failure channel if the work can throw.

Results out, way 2: futures

A future is the claim ticket from the plain words box: a handle to a value that will exist later. get() waits until the value is ready and returns it. If the task failed, get() throws the failure in the thread that asked (Java wraps it in an ExecutionException; C++ rethrows the original exception). You will study futures in depth in futures and promises; here is what you need now.

  • Java: a Callable<V> is a task that returns a value and may throw. Wrap it in a FutureTask<V>, which is both a Runnable (so a plain Thread can run it) and a Future<V> (so you can get() the result). An executor's submit does the same wrapping for you.
  • C++: a std::promise<T> is the sending end and its std::future<T> the receiving end. The thread calls set_value (or set_exception), the caller calls get(). std::async(std::launch::async, f, args...) is a thread plus a promise in one call, and std::packaged_task wraps a callable so its result goes into a future.
C++

Two std::async facts interviewers like. First, pass std::launch::async when you require concurrent execution: the default policy may choose deferred execution, which runs lazily in the thread that first calls get() or a non-timed wait. Second, releasing the last reference to an unfinished task launched with std::launch::async waits for that task. So std::async(std::launch::async, task); with the result thrown away is not fire and forget: the temporary future is destroyed at the semicolon and waits right there, which turns a loop of such calls into sequential code. A deferred task is not run merely because its future is destroyed.

Why the hand-offs are safe: start and join are edges

Nothing above uses a lock, yet none of it is a data race. The reason is that thread start and thread end are synchronization points. These are two of the happens-before edges you will meet properly in happens-before and synchronizes-with:

Start and join alone do not order main's later writes with the worker's reads, or main's early reads with the worker's writes. Conflicting accesses in those gaps need another synchronization mechanism. A future publishes the writes covered by its completion, but a promise may be fulfilled before its worker finishes cleanup; getting the result is not necessarily joining the thread. A plain boolean "done" flag that main polls gives no publication guarantee, which is the visibility bug in its purest form.

Worked example: collect the results of 10 parallel fetches

Ten threads each fetch one web page. You need all ten pages back, in the order of the URLs. Four designs, from worst to best:

DesignVerdict
Every thread appends to one shared ArrayList or std::vectorBroken. Concurrent appends race with each other: items are lost, or the list's size and storage disagree. Joining before reading does not help, because the appends raced among themselves.
Every thread appends to a synchronized list or a concurrent queueCorrect but unordered: pages arrive in completion order, so you must sort them again, and all writers contend on one lock or one queue.
A pre-sized array, one slot per thread, read after joining allCorrect and in order on success, but needs separate failure reporting. An uncaught C++ exception terminates the process. Timeouts also need explicit handling.
One future per fetch, get() in URL orderCorrect, in order, and stored failures come back through get(). Java has timed get; C++ uses wait_for or wait_until before get. Prefer this when outcomes and deadlines matter.

In an interview, say why you rejected the first design out loud: "a shared list would need a lock, and even then I would lose the order, so I keep one future per task." That one sentence shows you saw both the race and the requirement.

Common mistakes

  • Capturing the loop counter by reference in C++. Capture i by value. Java turns this into a compile error for you.
  • A detached thread (or a thread stored somewhere long lived) that refers to locals. When the function returns, the thread is left with a dangling reference. Join before the data dies, or copy or move the data in.
  • Forgetting std::ref, or using it carelessly. Without it the thread works on a copy, or the code does not compile. With it you have shared mutable state, with all the duties that brings.
  • Reading the result before joining or before get(). A Thread.sleep or sleep_for "long enough" does not make the read safe; it is timing, not synchronization.
  • Collecting results in a plain ArrayList or std::vector from many threads. Use per-thread slots or futures.
  • Calling std::async without std::launch::async, or ignoring its future. You may get deferred, single threaded execution, or a loop that waits on every iteration.
  • A get() with no timeout on a request path. If the task hangs, so does the caller. Java's get(timeout, unit) and C++'s wait_for exist for this.

In the interview

This shows up inside bigger problems: "run these tasks in parallel and return their results in order", "make the crawler multithreaded and return all URLs", or, at Databricks, an event writer where every append must return a handle that completes only when the event is durable. One reported L4 solution used a std::promise and std::future per event for exactly that. A Rubrik candidate was asked to implement a JavaScript style promise in Java, so know what a future does underneath.

Each task gets its own copy of its input, so nothing is shared on the way in. On the way out I keep one future per task and call get in input order, which preserves the order and brings back failures as exceptions. Start and join (or get) are happens-before edges, so the results are visible without locks.

Follow ups to expect: "How do you return a value from a std::thread?" (a promise and future, std::packaged_task, std::async, or a slot read after join). "How do you pass a reference to a thread in C++?" (std::ref, and own the lifetime). "Why must Java captures be effectively final?" (the lambda captures a copy of the value, so a later change could never be seen anyway). "What happens if one task throws?" (its get rethrows; see exceptions in threads).

Senior depth

Ownership is the real design question. For every piece of data a thread touches, a senior can say who owns it and for how long: copied in (the thread owns a private copy), moved in (ownership transferred, the caller has nothing left), borrowed by reference (the caller guarantees it outlives the thread, usually by joining), or shared (both own it, so it needs a lock, an atomic or immutability). std::shared_ptr makes shared lifetime safe, not shared mutation, and every copy of it costs an atomic reference count update.

Copies are a concurrency tool. A private snapshot avoids sharing, provided taking the snapshot is itself synchronized with any other writer. Copying a pointer or Java reference does not copy the pointed-to data. Java records and C++ const also do not make reachable mutable objects deeply immutable. Use values such as Java String or genuinely independent snapshots to avoid locks, a theme that returns in the safety ladder.

Start and join are not the only edges. Handing data through a thread-safe queue, completing a future, or releasing a lock that the reader then takes all publish data safely too. What never publishes anything is time: a sleep, a busy loop on a plain variable, or "it is surely done by now".

Key takeaways

  • Java lambdas capture copies of effectively final locals; objects are always shared by reference.
  • std::thread copies its arguments: use std::ref to share, std::move for move only types, and a pointer for member functions.
  • A C++ thread must never outlive the data it refers to; capture changing values (like loop counters) by value.
  • Bring results back through per-thread slots read after join, or better through futures, which also carry failures.
  • Start and join (or get) are happens-before edges; a sleep or a plain flag is not.

Main writes config = 5 to a plain int, then starts a worker that reads config, then main writes config = 6 with no synchronization. What is guaranteed about the value the worker reads?
Why. In Java, start publishes the write of 5 and excludes the earlier initial value, but the unordered write of 6 can also be observed. In C++, the unsynchronized conflicting accesses are a data race, so it is wrong to restrict the result to 5 or 6. Write everything before starting the thread, or hand over later changes through synchronization.
A worker stores its answer in a shared plain int named result and exits. Main starts the worker and reads result right away, without joining. What can main read?
Why. No synchronization orders the result write before main's read. Java can read the initial value or the worker's answer even if the worker appears to have finished. C++ gives no output guarantee because this is a data race. Reading a plain field does not wait for its writer.
Eight threads each compute one number. Which ways of collecting the eight numbers in main are correct? Select all that apply.Select all that apply
Why. Separate slots plus join, and futures, both give a happens-before edge from each writer to main. Concurrent appends race with one another, and the join afterwards cannot repair a list that was corrupted while the threads ran. Plain flags give no visibility guarantee: main may spin forever, or see a flag before the result it guards (and in C++ it is a data race).
A task run through Java FutureTask, or C++ std::async or std::packaged_task, throws instead of returning a value. The caller later calls get() on the task's future. What happens?
Why. Carrying failures back is a main reason to prefer futures over shared slots. The future stores either the value or the exception, and get() delivers whichever it holds. Only a raw thread with nobody catching inside it loses the failure (or, in C++, terminates the process).
A function starts a worker that reads the function's local array (by reference in C++, through a captured reference in Java), and the function joins the worker before returning. Nobody writes the array while the worker runs. Is this safe?
Why. The rule is about lifetime and races, not about where data lives. Other threads can read a stack array perfectly well, as long as it stays alive until they are done (the join guarantees that) and nobody writes it concurrently. The over-cautious answer is a common misconception; the real bug is a thread that outlives the data, as with detach.

Why. std::thread stores decayed copies of its arguments and passes them as rvalues, so a non-const lvalue reference parameter cannot bind. The compiler stops you, which is a good thing: std::ref makes the sharing explicit, and with it you take on the lifetime and synchronization duties.

Why. A lambda may only use locals that are effectively final, because it captures a copy of the value. Declaring final int id = i; inside the loop creates a new variable per iteration, which the lambda can capture. Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write fetchAll(urls) (Java) or fetch_all(urls) (C++). It fetches every URL on its own thread by calling a given fetch(url), and returns the pages in the same order as the URLs. If any fetch throws, fetchAll must throw too. Do not use a shared collection that several threads write.
Model answer

Each task gets its URL by value, and its page or its failure comes back through its own future, so no collection is ever written by two threads. Calling get in input order keeps the order even though fetches finish in any order. One difference worth saying out loud: when a get throws in the Java version, the other fetch threads keep running unattended, so a production version would cancel them (next lesson). In the C++ version, the remaining std::async futures are destroyed during unwinding and each destructor waits for its task, so no thread is left behind.

Debug
Find every bug, and fix it:
Model answer

The lambda captures everything by reference, including the loop counter i. Each thread reads i while the main thread keeps incrementing it, which is a data race. A thread may therefore process the wrong chunk, the same chunk twice, or chunks[4], which is out of bounds. And once the loop ends, i no longer exists, so a thread that has not read it yet holds a dangling reference.

Capture i by value and only chunks by reference: [&chunks, i] { process(chunks[i]); }. Also use a vector of std::jthread in C++20, or joining guards in C++17, so an exception while creating a later worker does not destroy earlier joinable threads. Keep chunks alive until all joins complete and prevent conflicting concurrent writes. In Java the changing local capture does not compile; use final int id = i; inside the loop.

Explain
An interviewer asks: "Your worker writes its result into a plain field. Why is it fine for main to read that field after join() without a lock, but not after Thread.sleep(1000)?" Answer as you would out loud.
Model answer

Because join is a synchronization point and sleep is not. When a thread terminates and another thread's join on it returns, the language guarantees a happens-before edge: every write the worker made is visible to the joining thread. So the read after join is ordered after the write, and there is no data race.

A sleep only changes timing. It makes it likely that the worker has finished, but it creates no ordering between the worker's write and main's read. In Java the read may legally see a stale value; in C++ it is a data race, which is undefined behavior even if it prints the right number every time I test it. If I need the result, I join, or I use a future, whose get gives the same guarantee.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Every worker is supposed to process a different chunk, but some process the same one. How would you investigate the captured input?"
What a strong answer covers
  • A C++ reference capture of the loop counter shares a variable that the creator keeps modifying
  • The accesses race, and the captured reference also dangles once the loop counter's lifetime ends
  • Capture the index by value; borrow the chunks only while their lifetime and access discipline are guaranteed
  • Java rejects a changing local capture, but an effectively final reference can still point to mutable shared data
  • Choose a private snapshot, ownership transfer or synchronized sharing deliberately
How a senior would say it
I would check whether all workers captured the same changing input instead of a value for their own iteration. In C++, capturing the loop counter by reference lets workers read it while the creator increments it. That is a data race, so the behaviour is undefined, not just a predictable final index. Once the loop ends, that reference also dangles. I would capture the index by value, while borrowing the chunk collection only if it stays alive and nobody changes it incompatibly until all workers finish. Java rejects a lambda that captures a changing loop counter, so I create a fresh local index for each iteration. But effectively final does not mean the object is immutable. If every lambda captures one reusable string builder, they still share its changing contents. I would create a separate immutable string before launching each task. Copies cost memory and copying time, so large inputs may justify borrowing or sharing. That choice needs an explicit lifetime and synchronization rule; merely copying a pointer or Java reference does not create a private snapshot.

Likely follow up: Would replacing the C++ reference with a std::shared_ptr fix both the lifetime problem and the race?

Out loudabout 90 s
"Fetch ten pages concurrently and return them in URL order. Would you use a shared list, result slots, or futures? Talk me through the choice."
What a strong answer covers
  • Choose one future per URL and launch all tasks before collecting any result
  • Collect futures in input order; completion order does not dictate result order
  • Plain concurrent appends are unsafe, while locked appends still need explicit ordering
  • Separate pre-sized slots plus joins are safe but need a separate failure channel
  • Futures transport failures; Java wraps task failures and C++ rethrows stored exceptions
  • Use an overall deadline and define cancellation and cleanup for remaining tasks
How a senior would say it
I would keep one future per URL, launch all ten tasks, and collect the futures in URL order. The downloads can finish in any order; the position of each future determines the output position. Waiting for the first page does not prevent the other nine from running, provided I launched them first. Plain concurrent appends to one list or vector are unsafe. Adding a lock makes appends safe, but records completion order unless I also store an index. Separate slots in a pre-sized array are another correct design: each worker owns one slot, and I read it after joining that worker. That is simple for computations that cannot fail, but a default value is not a useful failure report. Futures carry either a result or a failure. Java exposes a task failure through an execution exception with the original cause; C++ rethrows the stored exception. For a request, I would use one overall deadline rather than spending a fresh timeout on every future. On failure or timeout, I would request cancellation of unnecessary work and arrange cleanup. Input order can delay noticing a later failure, so if immediate failure detection is required, I would add a separate completion or failure signal while preserving the output indices.

Likely follow up: Why can throwing away each temporary std::async future accidentally serialize the downloads?

Out loudabout 60 s
"Your worker writes a plain result field. Why do you trust the read after a join, but not after sleeping for a second?"
What a strong answer covers
  • A successful join of the terminated worker establishes ordering and visibility for its writes
  • A sole worker writes the slot; the caller reads only after joining, so no atomic is needed
  • Sleep changes timing but creates no happens-before edge
  • An unsynchronized early read can see stale data in Java and is undefined behaviour in C++
  • A future publishes work before its completion, but may become ready before the thread itself ends
How a senior would say it
I trust the join because it establishes synchronization, not because enough time has passed. If one worker writes the result and I read it only after successfully joining that worker, its write happens before my read. A plain field is sufficient for that ownership pattern. Sleeping for a second creates no such edge. The worker might still be running, and elapsed time does not publish its writes. Java can return stale data; the conflicting unsynchronized accesses in C++ are a data race and give undefined behaviour. A future is another way to publish the result: getting its value makes the writes covered by that completion visible. But a promise can be fulfilled before the worker finishes other cleanup. So receiving the value does not always mean the thread has ended. I still need a lifetime plan for anything the worker uses afterwards.

Likely follow up: If two workers increment the same plain field and I join both, does joining repair their lost updates?
