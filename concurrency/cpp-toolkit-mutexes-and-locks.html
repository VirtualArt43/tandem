The toolkit: mutexes and lock guards

Choose the right C++ lock owner, protect const getters, acquire several mutexes safely, and understand timed, recursive and shared locking.

Asked atMicrosoftBloomberg
Before this:The toolkit: std::thread, std::jthread and thread_localClasses, constructors, destructors and RAIIconst correctness and mutable

A mutex is the shared exclusion mechanism. A lock guard is the local object that makes releasing that mutex unavoidable on normal scope exits and exception unwinding.

In plain words

A meeting room has one key. The mutex is the room's key system; the guard is the person responsible for returning the key before leaving. Copying that responsibility would create two people trying to return one key, which is why guards are not copyable.

Why this matters for concurrency

Most interview data structures become correct by protecting the right complete operation with one mutex. The common failures are a guard ending too early, inconsistent lock order, or a getter escaping protection. This lesson teaches the types; mutex basics, locking rules, and multiple locks teach their proofs.

API card

All runnable examples use C++20. The locking APIs below are available in C++17; std::scoped_lock, std::shared_mutex, and class template argument deduction arrived in C++17. std::shared_lock arrived in C++14; the other listed facilities date from C++11.

Type in its headerMain operations and semantics
std::mutex, <mutex>lock, try_lock, unlock acquire, attempt, and release exclusive ownership; normally invoke them through an owner.
std::lock_guard<M>, <mutex>Constructor acquires; destructor releases; the adopt-lock constructor assumes ownership already exists.
std::unique_lock<M>, <mutex>lock, try_lock, unlock, owns_lock, mutex, release; a movable owner supporting deferred acquisition, and timed acquisition when M supports it.
std::scoped_lock<M...>, <mutex>Owns zero, one, or several mutexes; several are acquired with deadlock avoidance. Releases all owned mutexes at destruction.
std::lock(a, b, ...), <mutex>Acquires at least two lockable objects without deadlocking among those acquisitions; releases acquisitions from this call if locking throws.
std::timed_mutex, <mutex>Adds try_lock_for and try_lock_until, returning whether ownership was acquired.
std::recursive_mutex, <mutex>Allows repeated exclusive acquisition by its owning thread, with a matching release for each acquisition.
std::shared_mutex, <shared_mutex>Exclusive lock or shared lock_shared; shared ownership allows several readers, excluding writers.
std::shared_lock<M>, <shared_mutex>Movable shared owner with lock, try_lock, unlock, and owns_lock; calls the mutex's shared ownership operations.
std::once_flag, std::call_once, <mutex>Run at most one successful initialization for a flag; a throwing attempt leaves it available for retry.

What owning a mutex proves

A std::mutex admits one owner at a time. Its unlock() synchronizes with a subsequent successful acquisition of that same mutex, establishing happens-before from earlier protected writes to later protected reads. A failed try_lock() grants neither ownership nor this synchronization edge; using two different mutexes for one shared variable does not protect it.

Unordered conflicting accesses to ordinary state, with at least one write, are a data race, which is undefined behaviour in C++. A mutex does not automatically attach protection to nearby fields: every caller must follow your protocol. Neither ordinary nor shared standard mutexes promise FIFO service or freedom from starvation.

Only the owning thread may unlock a standard mutex. Keep the mutex and its protected object alive until all users have finished, including blocked callers; join workers before destroying their state. Reacquiring a nonrecursive mutex already owned by this thread violates its precondition, so do not rely on a guaranteed deadlock or exception.

The default is a named std::lock_guard

Declare one mutex beside the state it protects. Every conflicting read and write must follow the same protocol. std::lock_guard guard(mutex_); uses C++17 class template argument deduction; the longer spelling is std::lock_guard<std::mutex> guard(mutex_);. The local name gives the guard a scope. It unlocks at the closing brace, a return, or exception unwinding.

A bare std::lock_guard<std::mutex>{mutex_}; is a temporary destroyed at the semicolon. It protects no following statement. Manual mutex_.lock() followed later by unlock() can skip the unlock on an early return or exception. Use a scope to control lifetime; use std::unique_lock only when you need more control. A guard releases resources but does not undo partially committed state.

mutable allows the const getter to acquire the mutex without permitting ordinary writes to value_. The caller receives an int snapshot, not a reference that escapes the lock. The counter itself cannot be copied or moved by default because its mutex cannot. Returning a synchronized value and moving a synchronization owner are different operations.

This is RAII: resource ownership follows object lifetime. Checks precede the update, including the signed overflow check, so either exception leaves the value unchanged. For a C++17 version of this counter, replace std::jthread with std::thread and retain the explicit joins; robust code must also join already started threads if starting a later one throws.

std::unique_lock: ownership that can change within a scope

ConstructionMeaning
std::unique_lock lock(m)Lock now and own on success.
std::unique_lock lock(m, std::defer_lock)Associate with m without acquiring it.
std::unique_lock lock(m, std::try_to_lock)Attempt once; inspect owns_lock() before touching protected data.
std::unique_lock lock(m, std::adopt_lock)Adopt a lock already held by the current thread; no acquisition occurs.
std::unique_lock<std::timed_mutex> lock(m, duration)Attempt timed acquisition; inspect ownership. A time point instead of a duration uses an absolute deadline.

Calling unlock() on the std::unique_lock releases ownership while preserving its association with the mutex, so it can lock again later. Moving transfers that association and ownership into another std::unique_lock, leaving the source empty. This supports helpers returning locks and condition-variable waits that temporarily unlock and relock.

release() detaches the wrapper without changing the underlying mutex's lock state and returns its pointer. On an owning wrapper it leaves the mutex locked; on an empty wrapper it returns nullptr. Confusing it with unlock() can leak a locked mutex. An adopted lock must already be held by this thread, with no other wrapper still responsible for the same acquisition.

A default-constructed std::unique_lock<std::mutex> has no associated mutex; a deferred lock does. mutex() reports that association, whereas owns_lock() reports this wrapper's ownership. Calling unlock() on a nonowning wrapper throws std::system_error, as does calling lock() on an already owning wrapper. Moving a wrapper does not transfer the underlying mutex's thread ownership: acquire and release must still happen on the same thread.

Several locks: acquire the set as a set

For two distinct account mutexes, std::scoped_lock both(a, b); is the shortest safe owner. It uses a deadlock-avoidance acquisition algorithm. std::lock can instead acquire deferred std::unique_lock owners, useful if each owner needs separate control afterward. Neither approach fixes deadlocks involving other locks already held, callbacks, or joining workers. Do not pass the same nonrecursive mutex twice; handle a self-transfer before acquiring the set.

A try operation can fail spuriously, so the sample allows either count. The adoption example is specifically teaching how to wrap locks obtained by std::lock; ordinary code should prefer std::scoped_lock. Its two guard constructors do not acquire again. Calling lock a second time on an owned nonrecursive mutex is not a recursion strategy.

Timed acquisition and scheduling limits

std::timed_mutex adds relative and absolute timed attempts. Use a std::unique_lock to own success. Failure means no ownership; timed attempts can fail even if the mutex became available, so failure proves neither continuous contention nor deadlock. A zero or negative relative duration attempts acquisition without blocking.

Timeouts can overshoot due to scheduling; they are not hard return-time guarantees. Prefer one std::chrono::steady_clock deadline for a total operation budget, especially across retries. Repeatedly giving each retry a fresh full duration can exceed the caller's intended budget. Blocking mutex acquisition has no stop-token overload: requesting stop on a std::jthread does not interrupt its lock().

The holder cannot release before the attempt finishes because it waits on a separate latch. This proves the timeout branch without guessing how long a worker takes to start. The later ordinary lock proves eventual acquisition once ownership is released.

std::latch and std::jthread require C++20. In C++17, use joined std::thread objects and predicate waits on a separate mutex and condition variable for these handshakes. See the condition-variable toolkit.

Shared readers and recursive ownership

A shared mutex permits either several shared owners or one exclusive owner. Use std::shared_lock guard(mutex_) in read-only operations and std::unique_lock guard(mutex_) in writes. A read operation that updates a cache, a hit count, or a lazy field is not read-only unless those changes have their own safe protocol.

std::shared_mutex is nonrecursive in both modes. Its shared operations are lock_shared(), try_lock_shared(), and unlock_shared(); std::shared_lock calls these for you. For timed shared or exclusive acquisition, choose std::shared_timed_mutex from <shared_mutex>; a timed std::shared_lock constructor uses try_lock_shared_for or try_lock_shared_until. std::recursive_timed_mutex from <mutex> combines recursive exclusive ownership with timed attempts.

There is no atomic upgrade operation on std::shared_mutex. Release the shared lock, acquire exclusive ownership, and recheck the condition because another writer could have changed it. Do not try to acquire exclusive ownership while already holding shared ownership. The standard does not promise reader or writer fairness, and shared-lock bookkeeping can cost more than a plain mutex for short operations. Measure before assuming a read-heavy workload benefits.

A recursive mutex lets the owning thread acquire repeatedly. Every successful acquisition needs a matching release, conveniently provided by nested guards. Recursion depth has an unspecified limit; at that limit, lock() throws std::system_error and try_lock() fails. It does not let other threads enter, fix lock ordering, or make reentrant callbacks see consistent state.

Prefer private helpers that require the caller's existing lock. Recursive locking can conceal accidental calls into partially updated state. Read reentrancy and reader writer locks for their deeper contracts.

std::call_once: one successful initialization

An active call executes the initializer; a passive call returns after successful initialization without executing it. Active attempts are ordered and synchronize with the next active attempt, so accesses to attempts_ are safe. A throwing attempt propagates its exception without completing the flag; the successful active call synchronizes with returning passive callers. Failed attempts do not roll back side effects, so keep retries safe.

The flag is not copyable and has no reset operation. This example additionally guards reads and writes so value() is safe even if called before initialization, when it returns zero. For immutable state read only after std::call_once returns successfully on the same flag, that extra data mutex is unnecessary. A function-local static is often simpler for one lazily constructed object; its initialization is thread-safe since C++11 and retries after an exception, but later mutation still needs protection.

Worked example: a transfer between two accounts

The invariant is nonnegative balances with a conserved total. Treat a self-transfer as a successful no-op after rejecting negative amounts; otherwise acquire both distinct mutexes with std::scoped_lock. Check funds and overflow before either mutation. Integer updates then cannot throw, and the single guard releases both locks on every return.

The public fields keep this demonstration small; a production account hides them behind synchronized operations. Final reads here occur after both joins. During concurrent transfers, a total-balance snapshot must acquire both mutexes too: two separately locked getters can combine balances from different instants.

Two individually safe setters cannot make a transfer atomic. Nor does RAII roll back a debit if a later allocation or logging call throws. Stage throwing work before committing, or design an explicit rollback; keep arbitrary callbacks outside the locked operation.

Compile errors that are trying to help you

A const mutex cannot be locked, so mark a getter's mutex mutable. Neither std::lock_guard nor std::scoped_lock can be copied, moved, or explicitly unlocked; use std::unique_lock when moving or explicit unlocking is needed. A class containing a mutex has deleted implicit copying and moving.

std::condition_variable::wait expects a std::unique_lock<std::mutex>&, not a std::lock_guard, because it must temporarily release ownership. A plain mutex has no try_lock_for; select std::timed_mutex. Include the declaring headers explicitly instead of depending on incidental transitive includes.

Common mistakes

  • Unnamed temporary guards: name the owner so its lifetime covers the operation.
  • Reading after a failed try: check owns_lock() first.
  • Adopting a lock not owned by this thread: adopt means assume, not acquire.
  • Holding a lock during arbitrary callbacks or join: dependencies can form a cycle.
  • Assuming a reader writer lock upgrades or guarantees fairness: neither is promised.

In the interview

Expect a thread-safe class, a broken transfer, or a comparison of lock owners. Explain which invariant the mutex protects, why reads follow the same protocol, and why your guard lives across the whole operation.

I start with a named std::lock_guard for one complete invariant. I use std::unique_lock when ownership must change during the scope, std::scoped_lock for a set of mutexes, and std::shared_lock only for truly read-only operations. I state timeout and fairness behavior separately.

Follow ups: what if the arguments alias, an update throws, a getter returns a reference, or a shared reader needs to write? Answer with the self-operation check, exception-safe commit, a value snapshot, and release then exclusive acquisition with rechecking.

Key takeaways

  • The mutex is shared; the RAII owner has a local, deliberate lifetime.
  • Unique locks can move and temporarily unlock; lock guards cannot.
  • Acquire several mutexes with a common order or a set-acquisition algorithm.
  • Timed and shared locking change semantics, not the need for an invariant.
  • std::call_once permits retries after exceptions and publishes one successful initialization.

Quick check

Answer each question, then read why. Your score is saved for your module test.

What does a temporary std::lock_guard<std::mutex>{m}; protect?
Why. It acquires and immediately releases at the end of the statement. A named guard is needed to protect later statements.
A std::unique_lock was built with std::defer_lock. The thread does not otherwise own the mutex. What may you do before acquiring it?
Why. std::defer_lock stores the association without acquiring. You may later call lock() or pass the wrapper to std::lock; association alone permits no protected access. unlock() on this nonowning wrapper throws std::system_error and does not detach it.
For an owning std::unique_lock, how does release() differ from unlock()?
Why. release() returns the mutex pointer, clears the association and leaves the mutex held. unlock() unlocks it and clears ownership while preserving association. Neither operation keeps the wrapper owning, so they are not aliases.
A transfer receives the same account twice, using a std::mutex member. Is std::scoped_lock both(account.m, account.m); the solution?
Why. The acquisition algorithm neither deduplicates mutexes nor makes them recursive. Reacquiring the same nonrecursive mutex violates its ownership requirements. Handle aliasing before attempting the set.
The only call so far to std::call_once on a flag threw from its initializer. What can the next call do?
Why. A throwing attempt does not complete initialization, so the next call can attempt it again. std::once_flag cannot be assigned a fresh flag. Passive calls may skip the callable only after a successful initializer, not because a previous attempt threw.
A shared reader discovers missing data and wants to insert it. What is the standard std::shared_mutex approach?
Why. There is no atomic upgrade API on std::shared_mutex. Acquiring exclusive ownership while still owning it shared violates the precondition. Mutating under shared ownership lets other readers race with the write. Rechecking after exclusive acquisition covers changes made during the gap.
Which outputs are permitted by C++20? Assume thread creation and locking succeed. Select all that apply. Select all that apply
Why. The reader can acquire first and read 0, or acquire after the writer unlocks and read 42 through the happens-before edge. Starting the writer first does not guarantee that it acquires first. Both accesses to value use the same mutex, and joining the reader makes its assignment visible to main, so there is no data race and -1 is impossible.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A const size() member cannot construct a std::lock_guard from its mutex. Explain the error and repair.
Model answer
The const member treats ordinary members as const through this, but locking mutates mutex state. Declare the mutex mutable, retain logical constness of the stored data, and lock reads and writes using that same mutex.
Write code
Write a C++17 helper that acquires two distinct mutexes without an acquisition deadlock and returns separate owners. State its preconditions.
Model answer

The mutexes must be distinct, alive for all uses, and not already owned by the calling thread. The returned owners must release them on that same thread. Moving leaves the locals empty, so their destructors do not unlock; a failed acquisition releases what this call acquired. Prefer std::scoped_lock when the caller needs only one scope for both mutexes.

Design
When might a plain mutex outperform std::shared_mutex for many readers?
Model answer
When protected operations are very short, shared ownership bookkeeping and cache contention can cost more than serialization. The proportion of reads alone is insufficient; measure contention and critical-section duration, and do not assume writer fairness.

"Explain std::lock_guard, std::unique_lock, and std::scoped_lock without listing every method."
What a strong answer covers
  • All provide scoped ownership
  • Lock guard is the simple one-lock choice
  • Unique lock supports changing and moving ownership
  • Scoped lock acquires several distinct mutexes safely
How a senior would say it
All three make releasing locks follow object lifetime. Lock guard is my default for one mutex held for a whole scope. Unique lock is useful when ownership must change within that scope, especially for condition variable waits, timed attempts, or explicitly unlocking before a callback. Scoped lock is the convenient choice for taking several distinct mutexes together using deadlock avoidance. I would still handle a self-operation before giving it duplicate mutexes, and I would not assume it fixes dependencies involving other locks or joining threads.

Likely follow up: Why can a condition variable not use a std::lock_guard?

Out loudabout 60 s
"A developer says a shared lock lets this getter update its cache. How would you review that?"
What a strong answer covers
  • Shared owners can overlap
  • A hidden write is still a write
  • Use exclusive ownership or another proven protocol
  • Upgrade requires releasing and rechecking
How a senior would say it
A shared lock allows several threads into the method simultaneously. Calling it a getter does not make a cache update read-only. If those callers write the same cache state, they still need exclusive access or a separate proven synchronization protocol. I would either use an exclusive lock for that operation or read under a shared lock, release it, acquire exclusive ownership, and recheck before filling the cache. Standard std::shared_mutex does not provide an atomic upgrade. I would also measure whether shared locking helps for such a short operation.

Likely follow up: Could an atomic hit counter coexist with a shared lock on the data?
