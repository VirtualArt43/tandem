Unique ID generator

Thread-safe structuresmedium45 minAmazonRubrik

An incrementing counter is easy until time stops, rolls back, or several callers exhaust the same millisecond together.

The task

Generate nonnegative 64-bit IDs with 41 timestamp bits, 10 node bits and 12 sequence bits: (milliseconds << 22) | (node << 12) | sequence. Milliseconds are relative to an application epoch. Node IDs are 0 to 1023; timestamp values are 0 to 2^41 - 1.

  • The first allocation in a millisecond uses sequence zero. Later allocations increase it through 4095. Once exhausted, release the generator lock and wait for a later millisecond, then retry.
  • A backwards clock reading is rejected with IllegalStateException or std::logic_error, without changing state. Retry is safe once time catches up. Do not silently reset the sequence on rollback.
  • IDs strictly increase in allocation order within one generator. Concurrent method return order can differ from allocation order. Distinct generators require distinct node IDs; restart safety is a follow-up.
  • The supplied clock is thread-safe, does not reenter the generator, and its wait sleeps until a later time. Java waiting is interruptible and consumes no ID when interrupted. Production uses epoch-relative time and a bounded sleeping wait; tests supply explicit clocks.

Example: after sequence 4095 at time 100, the next caller must wait. At time 101 it may allocate sequence zero, which is larger than every ID at time 100.

What the tests check

  • Exact timestamp/node/sequence layout and monotonically increasing allocations.
  • Sequence exhaustion blocks until an injected clock advances; rollback rejects without changing sequence.
  • Eight threads generate 50,000 IDs each, all 400,000 distinct and increasing within each caller. A counter measures overlapping calls, and Java also checks interruption while waiting on exhaustion.
  • Different nodes produce different IDs for the same time and sequence; watchdogs bound stalled clocks.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How do the Amazon and Rubrik reports extend this?
Amazon reportedly raised throughput to billions of requests per second; Rubrik asked a distributed unique-key service. This layout has a fixed per-node millisecond capacity, so scale requires more nodes, larger sequence space, or allocated ID blocks rather than claiming unlimited throughput.
How would you make the packed state use CAS?
Pack timestamp and sequence into one atomic word, derive the next candidate from an observed state, and CAS it. Recompute after failure. Waiting on overflow stays outside the CAS loop; atomic does not imply wait-free.
What happens after restart?
The same node must not reuse an old timestamp/sequence region. Persist a high-water mark, use a new epoch or generation, or wait beyond the last durable timestamp before serving.
Why not clamp a backwards clock?
Clamping is another valid contract, but it consumes the remaining sequence space at logical time and may block longer. This exercise chooses explicit rejection so rollback is observable and cannot create duplicates.
Can you promise IDs increase in return order?
Not across concurrent callers: a thread can be paused after allocating a smaller ID. Linearizable allocation order and each caller's sequential order are the useful guarantees.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The state invariant

Under one mutex, last time never decreases and sequence is the largest allocated sequence at that time. No other caller can observe and modify these fields separately. The signed top bit remains zero because the timestamp occupies only 41 bits before the 22-bit shift.

Waiting without monopolizing the generator

At sequence exhaustion, copy last time and release the mutex before calling the clock's wait. Another caller may then observe a later time and allocate. The woken caller must reread both time and sequence; it cannot assume it owns the first slot. Backwards readings and invalid ranges are rejected before mutation.

The broken interleaving

The broken version wraps sequence 4095 back to zero in the same millisecond. The next ID duplicates the first ID from that millisecond. The overflow test deliberately holds time fixed for 4096 allocations and verifies the next call is still blocked, then advances time. High-volume uniqueness checks alone might miss overflow when the real clock advances quickly.

Cost and limits

Normal allocation takes O(1) work with one short serialized state update. Capacity is 4096 IDs per millisecond per node in this layout. That is a layout bound, not a measured throughput claim. Time-based uniqueness across machines also requires a collision-free node allocation policy. The 400,000-ID test uses synthetic time so it checks concurrency without depending on the machine's wall clock speed.

How to say it in the interview

I will protect timestamp and sequence as one allocation state. Sequence overflow waits outside the lock for a later millisecond; clock rollback fails without changing state. The bit layout gives uniqueness only if node IDs are unique and restart does not reuse an old allocation region.
