Exceptions and failures inside threads

Where an exception goes when it escapes a thread, how futures carry failures home, and why releasing a lock does not repair broken state.

Asked atRubrik
Before this:Creating, starting and joining threadsPassing data in and getting results out

An exception never crosses from one thread to another by itself. In Java it ends one thread quietly, or hides inside a future nobody reads; in C++ it ends the whole process. "What happens when a task throws?" is the first follow up after almost every thread pool question.

In plain words

A courier has an accident on the way to a delivery. Nobody at the office finds out unless someone carries the news back. If you gave the courier a claim ticket, you learn about it when you try to redeem the ticket. If you did not, you simply wait, or never notice.

The C++ office has a harsher rule: an accident that nobody on the spot handles closes the whole company. So every C++ courier carries a phone and reports the accident themselves.

Where does an escaped exception go?

Exception handling searches for a handler in the thread that threw, never in the thread that launched it. If an exception escapes the thread's entry function, the languages behave differently. In C++, do not rely on stack unwinding before std::terminate when no handler is found.

JavaC++
Exception escapes the thread's functionThe thread's uncaught exception handler runs, then the thread endsstd::terminate is called: the whole process aborts
Default behaviorPrints Exception in thread "name" and the stack trace to standard errorUsually abort(), with no stack unwinding guarantee
The rest of the programKeeps running, often unawareGone
What join doesDoes not rethrow the worker's failure; the caller's wait can still be interruptedDoes not transport the failure; std::terminate ends the process even if the caller is already in join

Both behaviors are dangerous in their own way. Java's is quiet: a worker dies, its work is lost, and unless you look at standard error nobody knows. C++'s is loud but total: one bad input in one task takes down a server. In both languages the cure is the same: catch at the thread boundary and carry the failure to someone who can act on it.

In Java, set a handler per thread with setUncaughtExceptionHandler, or a fallback with the static Thread.setDefaultUncaughtExceptionHandler; a thread factory for a pool is the natural place. A handler can log, alert or explicitly publish a failure through a shared channel. It cannot resume the failed thread, and installing one does not make join() rethrow.

In C++, a std::exception_ptr is a handle to the exception object that can be stored, passed to another thread and rethrown there with std::rethrow_exception. std::current_exception() captures whatever is being handled inside a catch, including types you do not know about, which is why the worker catches ....

Futures carry failures home, if someone asks

The cleaner way to bring a failure back is the same object that brings a result back. A future holds either the value or the exception, and get() delivers whichever it holds:

  • Java: ExecutorService.submit and FutureTask catch everything the task throws and store it. get() throws an ExecutionException whose getCause() is the original.
  • C++: std::async and std::packaged_task store the exception automatically. With a raw std::promise, the thread calls set_exception(std::current_exception()). get() rethrows the original exception, not a wrapper. If a promise is destroyed without ever being fulfilled, get() throws std::future_error with the broken_promise code.

The catch: a stored failure is only seen if someone calls get(). A task submitted and never checked fails in total silence, in both languages.

Java

submit versus execute is a classic question about an ordinary ThreadPoolExecutor. With submit, the pool wraps the task in a FutureTask, which stores the exception; calling get() reports it. With execute on a plain Runnable, an uncaught task exception escapes the worker, reaches its handler and ends that worker; the pool replaces it if needed. ThreadPoolExecutor.afterExecute(r, t) can log failures, but for submitted tasks t is null because the future caught the exception. Inspect the future. This distinction is not universal: even execute can receive an already wrapped FutureTask, and scheduled executors wrap tasks too.

Two more silent killers: a periodic task scheduled with scheduleAtFixedRate that throws once is never run again, and a CompletableFuture stage that throws completes its future exceptionally, where it waits for a join() (which throws CompletionException), a get(), or an exceptionally or handle stage.

Locks and exceptions

If a thread throws while holding a lock, two separate questions arise: is the lock released, and is the data it protects still correct?

The lock. synchronized releases the monitor however the block exits, exceptions included. A ReentrantLock is released only by your unlock() call, so it must sit in a finally. In C++, a std::lock_guard or std::unique_lock releases the mutex in its destructor, which runs during stack unwinding: that is RAII doing its job. A hand written m.lock() followed by m.unlock() skips the unlock when anything in between throws. The mutex then stays locked forever, and the standard says a thread that ends while owning a std::mutex is undefined behavior.

The data. Releasing the lock is necessary, and it is not enough. If the exception struck halfway through an update, the lock is now free and the half-done state is visible to every thread that takes it next. An invariant that the lock was protecting is broken, and nothing will tell you.

This is the strong exception guarantee applied to shared state: either the whole update happens, or none of it does. The usual technique is "prepare, then commit": everything that can throw (allocation, validation, I/O) happens before the first write to shared state. The alternative is to catch, roll back, and rethrow.

A group of tasks: the first failure stops the rest

Real systems run tasks in groups: a request that fans out to four services, a job runner over a graph of jobs. A common requirement is "if any task fails, stop the others and report the first failure". A reported Rubrik job runner question asked for exactly this: the first exception must stop everything. The design has four parts:

  1. A first failure slot that only the first failure can fill: AtomicReference.compareAndSet(null, e) in Java, an std::exception_ptr set under a mutex in C++.
  2. A cancellation signal to every task: interrupts in Java, one shared std::stop_source in C++ (see the cancellation lesson).
  3. Join everything, including the failed and cancelled tasks. No thread is left behind.
  4. Rethrow the stored failure on the caller's thread.

Worked example: four tasks, one fails, everyone stops

Four tasks each do 50 steps of work. Task 2 fails at step 3. The others notice the cancellation at their next check and exit early, and main reports the first failure only after every thread has finished.

Why compareAndSet and not a plain check then set? Two tasks can fail together; both could pass an unsynchronized empty check. "First" means the failure that wins the recording operation. Reading the Java workers list is safe because it is complete before any thread starts and never changes afterwards. Each task also checks the published failure, because interrupting an unstarted thread is not a portable cancellation guarantee.

The Java demo assumes launches succeed and main is not interrupted during its joins; the checkpoint below shows cleanup for those exit paths. Java 21 also previews StructuredTaskScope (JEP 453), whose ShutdownOnFailure policy packages group cancellation and joining. Preview APIs need explicit enablement at compile and run time, so be ready to explain the protocol without them.

Common mistakes

  • Submitting tasks and never calling get(). Every failure is stored and dropped. Check every future, or attach a completion callback, or log inside the task.
  • Letting an exception escape a C++ thread function. std::terminate, no unwinding guarantee, no second chance. Catch at the thread boundary, or use std::async or std::packaged_task, which catch for you.
  • A worker loop with no try and catch around each task. One bad task kills the worker: in Java the pool quietly loses a thread (unless it replaces it), in C++ the process ends.
  • lock() and unlock() with no finally or guard. The first exception leaves the lock held forever, and every thread that needs it hangs.
  • Believing "the lock was released, so we are fine". The data may be half updated. Prepare first, then commit with operations that cannot fail, or roll back.
  • Catching Throwable or ... and carrying on as if nothing happened. Catch to report and to keep the worker alive, not to hide the failure. Java Errors such as OutOfMemoryError mean the process may be in trouble; log them loudly.
  • Storing the "first failure" with a plain check then set. Two simultaneous failures race. Use compareAndSet, or check and set under one lock.

In the interview

After you build a thread pool or a task runner, expect: "what happens if a task throws?". Rubrik reports list it as a follow up to a hand-built pool, judged exception handling in a booking problem, and asked for a job runner where the first exception must stop everything immediately. The grader wants to hear three things: the worker survives, the failure reaches the caller, and shared state stays consistent.

Each worker runs every task inside a try and catch, so one bad task cannot kill the worker. The failure is stored in that task's future, so whoever calls get gets it rethrown on their own thread. For a group of tasks I keep the first failure with a compare-and-set, cancel the others, join everything, then rethrow. And under locks I prepare everything that can throw before I touch shared state, so an exception can never leave it half updated.

Follow ups to expect: "submit versus execute?" (stored in the future versus printed by the handler). "What happens in C++ if a thread function throws?" (std::terminate). "How do you move an exception between threads in C++?" (std::exception_ptr, set_exception, or std::async). "Does synchronized release the lock on an exception? Does ReentrantLock?" (yes; only in your finally). "Your periodic task stopped running. Why?" (scheduleAtFixedRate suppresses later runs after an exception).

Senior depth

Failure is a result, not an accident. Treat "task failed" as one of the outcomes a task can produce, carried through the same channel as success: a future, a completion callback, a result type. Designs that print exceptions and move on are designs where nobody owns failure.

Choose a group policy on purpose. "Fail fast, cancel the rest" suits work that is useless if any part fails (a request fan-out). "Collect all failures" suits batch jobs, where you want the full list. "Best effort" suits optional enrichments with a timeout. Say which one you chose and why.

Thread creation itself can fail. Java throws OutOfMemoryError: unable to create native thread when the OS refuses, and the std::thread constructor throws std::system_error. A pool should create its threads up front, or handle the failure where it creates them; with a vector of std::jthread, the threads already created are joined during unwinding.

Key takeaways

  • Exceptions are handled within their own thread. Java runs the uncaught exception handler if one escapes; C++ calls std::terminate without a stack unwinding guarantee.
  • Catch at the thread boundary and carry the failure home: futures, std::exception_ptr, set_exception.
  • A stored failure is seen only when someone calls get(); unchecked futures fail silently.
  • synchronized and RAII guards release locks on exceptions; ReentrantLock needs finally. Either way, the protected data may be half updated.
  • Prepare everything that can throw before you change shared state, then commit with operations that cannot fail.
  • For groups: first failure via compare-and-set, cancel the rest, join all, rethrow.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A worker thread throws an exception, and nothing inside the thread catches it. What happens?
Why. A worker's exception is not thrown on its creator's stack. Java's thread join does not rethrow it, though the caller can be interrupted. An exception escaping a C++ thread function calls std::terminate, with no guarantee of stack unwinding first. Capture and publish the failure explicitly if another thread must handle it.
Code takes a lock by hand (rlock.lock() on a ReentrantLock, or m.lock() on a std::mutex), then a call throws before the matching unlock, with no finally and no guard. What happens next?
Why. Only synchronized and RAII guards release on unwinding. A manually taken ReentrantLock or std::mutex is released only by an explicit unlock, which the exception skipped. The result is a hang that looks like a deadlock, which is why the rule is lock(); try { ... } finally { unlock(); } in Java and a guard object in C++.
Inside synchronized (or under a std::lock_guard), a method subtracts amount from from.balance, then a logging call throws before it adds amount to to.balance. The lock is released correctly. What is the state now?
Why. Locks give exclusion and visibility, not transactions. The write to from.balance happened and stays. Prevent it by doing everything that can fail before the first write to shared state, or by catching, rolling back and rethrowing.
In your hand-built thread pool, the worker loop calls each task with no try and catch around it. A task throws. What happens in each language?
Why. In Java the exception escapes run, the uncaught exception handler prints it and the worker ends; after a few such tasks a hand-built pool may have no workers left and queued tasks never run. In C++ the exception escapes the thread function, which calls std::terminate. Wrap each task call in a try and catch that records the failure, so the worker survives in both languages.
Four tasks run in parallel. The requirement: "if any task fails, stop the others and report the first failure to the caller". Which design meets it?
Why. Exceptions do not cancel other threads, and printing does not inform the caller. Exiting the process kills unrelated work and skips cleanup. The correct design needs all four parts: record the first failure atomically, request cancellation, join everything, rethrow.
Java onlyFor an ordinary Java ThreadPoolExecutor with default hooks that remains running, which statement about a plain task that throws is true?
Why. submit wraps the task in a FutureTask, which catches everything and stores it, so nothing is printed. execute runs the Runnable directly on the worker, so an exception escapes the worker thread, the handler prints it, and the pool starts a new worker. Neither retries.
C++ onlyWhat happens?
Why. The exception escapes the worker's entry function, which calls std::terminate; stack unwinding is not guaranteed. join does not rethrow worker exceptions, though invalid joins can throw their own errors. Catch in the worker and store a std::exception_ptr, or use std::async or std::packaged_task and call get().

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write runAll(tasks) (Java, a List<Runnable>) or run_all(tasks) (C++, a vector of std::function<void()>). It runs each task on its own thread, waits for all of them whether they fail or not, and if any failed, rethrows the first failure on the caller's thread.
Model answer

The catch records task failures before the worker returns. Choosing only one failure needs Java compare-and-set or a mutex-protected C++ check and store. Every started thread is joined before the method exits, including after a launch failure. Java cleanup defers interruption until the joins finish; a recorded task failure takes priority, with interrupt status preserved, otherwise interruption is propagated. Java Errors are rethrown on the caller, not silently treated as successful work. Cancellation is the natural next step; these joins can wait indefinitely for a task that never finishes.

Explain
A teammate's service uses a thread pool, and "some requests just never finish, with nothing in the logs". Explain how task failures can be silent in Java and in C++, and what you would add so they never are.
Model answer

In Java, the usual cause is submit without get: the pool's FutureTask catches the exception and stores it, so nothing is logged, and if the request was waiting on a different signal it waits forever. scheduleAtFixedRate tasks also stop running after their first exception, silently. With execute, the exception is printed only to standard error and the worker is replaced, which is easy to miss. In C++, a stored exception in a std::future or a std::promise is equally silent until someone calls get, and if a worker dies without fulfilling its promise, waiters see broken_promise only when they ask.

What I would add: every task wrapped so failures are logged with the task's identity and counted in a metric; every future either awaited with a timeout or given a completion callback that reports failure; a default uncaught exception handler (Java) and a catch at the top of every thread function (C++) that report rather than swallow; and, for the request path, a timeout so a lost result becomes a visible error instead of a hang.

Debug
Under load, every thread that calls add eventually hangs. Find the bug and fix it.
Model answer

When validate throws for a bad item, unlock() is skipped, so the lock stays held by the thread that threw, and every later caller blocks in lock() forever. It shows up "under load" only because that is when the first bad item arrives.

Release in a finally, with lock() before the try: lock.lock(); try { items.add(validate(item)); count += 1; } finally { lock.unlock(); }. Move validation outside the lock only if it does not depend on mutable shared state. Also inspect items.add: allocation or user code can still throw, and correctness requires that a failed append leave the collection unchanged or be rolled back before release. Once append succeeds, the count update must not fail. In C++ use a std::lock_guard or std::scoped_lock, and check the container operation's exception guarantee separately.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Some background jobs fail with nothing in the logs. I put a catch around join, but it never catches them. Where should I look?"
What a strong answer covers
  • Worker exceptions do not propagate through a thread join to the creator
  • Raw Java threads invoke an uncaught exception handler; an exception escaping a C++ thread calls std::terminate
  • Futures can store failures silently: Java submit, C++ async and packaged_task
  • Observe every task outcome; Java get() wraps task failure, while C++ rethrows the stored exception
  • For ordinary tasks on a Java ThreadPoolExecutor, distinguish execute from submit and inspect futures in hooks
  • Assign failure reporting to an owner; waiting or checking completion alone does not report success
How a senior would say it
I would look at how the task was launched and who observes its result. A thread join does not transport the worker's exception, so putting a catch around it cannot catch that failure. For a raw Java thread, an uncaught exception reaches its handler and the thread ends. In C++, an exception escaping the thread function calls terminate, so silence while the process continues points me toward a stored or swallowed failure instead. Futures are the common hiding place. Java submit and C++ async or packaged tasks store exceptions in their result state. Waiting until a task is done does not mean it succeeded. Somebody must retrieve or otherwise inspect the outcome. Java get throws an execution exception with the task's failure as its cause; C++ get rethrows the stored exception. On a Java thread pool executor, an ordinary runnable passed to execute can fail through the worker's uncaught exception handler. Submit wraps it in a future, so a logging hook must inspect that future rather than assume a missing throwable means success. I would give every task a failure owner, record its identity and failure, and ensure request waiters receive a failed outcome. Logging alone is insufficient if the caller is still waiting for a success signal that will never arrive.

Likely follow up: Why can a scheduled task disappear after one exception even though the scheduler's worker thread is still alive?

Out loudabout 90 s
"Four parallel tasks belong to one request. If one fails, cancel the others and return the first failure. Walk me through the races and cleanup."
What a strong answer covers
  • Define first failure as the first successfully recorded failure, not an assumed wall-clock ordering
  • Record it once using Java compare-and-set or a mutex-protected C++ exception pointer
  • Publish group cancellation and ensure tasks starting after the failure also observe it
  • Request cancellation outside locks that stop callbacks could acquire; make tasks and waits cooperate
  • Join all started workers before releasing borrowed state, including on launch or caller-interruption paths
  • Rethrow after cleanup without replacing the original failure with cancellation noise; latency is cooperative
How a senior would say it
I would record one failure, request cancellation of the group, wait for every started worker, and then rethrow the recorded failure on the caller's thread. I define first as the failure that wins the recording operation, because two threads can fail concurrently without an observable global order. In Java I would use compare and set on an initially empty failure reference. In C++ I would protect an exception pointer with a mutex. The winner publishes a group stop request. Tasks must check that shared state even if they start after the failure; interrupting a thread before it starts is not a portable substitute for that check. I would request cancellation outside any mutex that a stop callback might acquire. Each running task must cooperate at safe points and in blocking waits. Cleanup joins every thread before borrowed data disappears, including when launching a later thread fails or the caller is interrupted while joining. Cancellation exceptions from sibling tasks must not overwrite the original failure. Only after cleanup do I rethrow it. This gives prompt cancellation signalling, not a hard bound on return time: an uncooperative task can delay joining. If the response has a strict deadline, a longer lived supervisor must own the remaining cleanup and report the stuck task.

Likely follow up: If you collect futures in input order, how do you notice task four failing while task one is still blocked?

Out loudabout 75 s
"The lock guard released the mutex after an exception, but our balances are wrong. Why did exception-safe locking not protect the transfer?"
What a strong answer covers
  • Automatic unlocking protects lock lifetime, not the transaction's invariant
  • A debit followed by a throwing operation can leave the credit unapplied and expose partial state
  • Validate and prepare potentially throwing work before modifying shared state
  • Commit with operations known not to throw, or use a rollback path that restores the invariant reliably
  • The strong exception guarantee is all or nothing for the protected state; external effects need their own protocol
How a senior would say it
Releasing the mutex only lets other threads proceed; it does not roll back changes. If I debit one account, call an audit function that throws, and never credit the other account, the next thread acquires the lock and sees money missing. A Java synchronized block or C++ lock guard handles lock ownership correctly, but cannot repair that invariant. I would validate the transfer and prepare anything that can fail before making the first balance change. Then I would commit using operations whose failure behaviour I have actually checked. For example, allocating an audit entry belongs in preparation; simply moving allocation under a lock does not make it safe. If a later step can still throw, I need a rollback path that reliably restores the earlier state, or a different transaction design. This is the strong exception guarantee for the protected state: either the entire change happens or the original state remains. It does not automatically undo an external payment or durable log write. Those effects need an explicit commit and recovery protocol as well.

Likely follow up: Would moving validation outside the lock be safe if validation reads the current account balance?
