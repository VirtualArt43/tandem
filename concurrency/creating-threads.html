Creating, starting and joining threads

How a thread is created, started and waited for in Java and C++, and the C++ rule that ends your program if you forget.

Asked atRubrikLinkedIn
Before this:Processes and threads: the memory pictureThread states and what blocking really does

Every concurrent program begins with a thread being started and ends with someone waiting for it. Get the start and the end right, and the rest of an executor, crawler or job runner round has something solid to stand on.

In plain words

A head chef (the main thread) writes a recipe card and hands it to a new cook. Writing the card is not cooking. In Java nothing happens until the chef says "go"; in C++ handing over the card and saying "go" are the same moment.

Before the restaurant closes, the chef must wait for every cook to finish, or formally let a cook leave whenever they like. C++ is strict about this: if the chef walks out while a cook is still at the stove and nobody has accounted for them, the whole restaurant is shut down on the spot.

A thread is a task plus its own stack

A thread runs one piece of code, its task, from start to finish on its own call stack, while sharing the heap with every other thread in the process (the picture from processes and threads). Keep two things apart in your head: the thread object in your program, which is just a handle, and the operating system thread that actually runs.

Create, start, join

Here is the whole life cycle in both languages. Watch where the thread actually begins to run.

In Java, new Thread(...) only builds an object in the NEW state. start() asks the JVM to create the OS thread, which then calls your Runnable and ends in TERMINATED. In C++, the std::thread constructor copies the callable and its arguments into the new thread and starts it at once, so the object is joinable from the moment construction returns.

join() blocks the caller until the task has returned. It also does something less visible and just as important: a join is a synchronization point. Everything the thread wrote before it finished is guaranteed to be visible to the thread that joined it. That is a happens-before edge, which you will study properly in the memory model module, and it is why reading a worker's results after join() needs no lock.

Why the C++ sample does not print from main while the worker runs

The standard promises that two threads writing to std::cout at once is not a data race, but it does not keep a line together: each << is a separate call, so pieces of two lines can interleave into garbage. Some standard library builds also trip ThreadSanitizer on those internals. In these samples only one thread prints at a time, or printing happens under a lock. Java's System.out.println locks internally, so lines never mix, although their order is still up to the scheduler.

start versus run: the classic trap

A Java Thread has two methods that look alike. start() creates a new thread which then calls run(). Calling run() yourself is an ordinary method call: the task runs on your thread and no concurrency happens at all. The C++ version of the same slip is calling the function directly instead of handing it to std::thread.

Two more Java rules that show up in multiple choice rounds: a thread can be started only once (a second start() throws IllegalThreadStateException, even after the first run has finished), and a finished thread cannot be restarted. To run the work again, create a new thread or, better, submit it to a pool.

The ways to hand a thread its task

Prefer passing a Runnable to subclassing Thread: the task stays separate from the mechanism that runs it, so the same task can later go to an executor unchanged. In C++, whatever the callable returns is thrown away; getting results back is the subject of the next lesson.

C++

One C++ parsing trap: std::thread t(Task()); with a function object type Task declares a function named t, not a thread (the "most vexing parse"). Write std::thread t{Task()}; or std::thread t((Task())); instead. A lambda never has this problem.

Join on every path

In C++, a std::thread object that still owns a running (or finished but not joined) thread is joinable. If a joinable std::thread is destroyed, its destructor calls std::terminate, and your process dies. An object stops being joinable after join(), after detach(), after it is moved from, or if it was default constructed and never given a thread.

The dangerous moment is between creating the thread and joining it. An early return, or an exception from anything in between, skips the join(), and the destructor then ends the program. Java has no such rule, but the same missing join still hurts there: nobody knows when the work finished, nobody may safely read its results, and its failure goes unnoticed.

std::jthread is the RAII answer: a std::jthread joins in its destructor, so there is no path on which you forget. It also requests a stop before joining, which matters for threads that loop forever; you will use that in the cancellation lesson. If the thread never checks for a stop request, the destructor simply waits until it finishes.

The Java helper deliberately finishes cleanup before restoring the caller's interrupt status. A single join() in finally can itself throw InterruptedException, leaving the worker running and replacing an earlier exception. This helper guarantees ownership through completion, but does not bound the wait: an uncooperative worker can still prevent return.

C++

Before C++20, interviewers expect the same idea written by hand: a small guard whose destructor joins.

Two related rules: std::thread is move only, and move assigning into a std::thread that is still joinable also calls std::terminate. A thread joining itself is detected: join() throws std::system_error with resource_deadlock_would_occur. In Java, Thread.currentThread().join() simply waits forever.

detach: letting a thread go

detach() cuts the link between a C++ thread object and the running thread. The thread carries on by itself, the object is no longer joinable, and nobody can ever join that thread again. A detached thread has two serious risks:

  • It may still be using local variables of a function that has already returned. That dangling reference bug is covered in the next lesson.
  • When main returns, the process exits and detached threads are stopped wherever they happen to be. Objects on their stacks are never destroyed, and static objects may be destroyed underneath them while they still run.

Use detach only for a thread that owns all of its data and is safe to cut off at any instruction, and even then prefer joining. Java has no detach: any Thread can be joined at any time. The nearest Java idea is a daemon thread, which the JVM does not wait for at exit; see daemon threads.

Waiting with a timeout

Sometimes you may wait only so long. Java 19 added join(Duration), which returns true if the thread ended in time (the older join(millis) returns nothing, so you check isAlive() afterwards). C++ std::thread has no timed join, so the usual pattern is to have the thread signal through a future, or a condition variable, and wait on that with a timeout.

The sleeps only make the timing visible. The real lesson is the second half: when the timeout expires, the thread is still running. Neither language lets you kill it safely. You can ask it to stop and wait again, or keep the handle and join later, which is exactly what the cancellation lesson builds.

How many threads, and what to call them

Runtime.getRuntime().availableProcessors() and std::thread::hardware_concurrency() report the number of logical processors (hardware threads) available, so 16 on a laptop with 8 cores and two hardware threads per core. Java's value also respects container CPU limits. The C++ value is only a hint and may be 0 when it cannot be determined, so always have a fallback.

For CPU bound work, about one thread per logical processor is the usual starting point; more just take turns on the same cores. I/O bound work can use many more, because most of them are waiting. Both rules are developed in CPU bound versus I/O bound work and sizing a pool.

Name your threads. A thread dump with ingest-worker-3 in it is readable at three in the morning; one with Thread-17 is not. Java takes the name in the constructor or setName, and gives each thread an id through threadId() (Java 19+, replacing the deprecated getId()). Standard C++ has get_id() and std::this_thread::get_id(), which you can compare, hash and print, but no portable way to set a name: you call pthread_setname_np through native_handle(), and its signature differs between Linux and macOS.

Worked example: split a sum across the cores

Add up the numbers 0 to 9,999,999 with up to 4 threads. The design decisions are the point, not the arithmetic:

  1. Partition the input into one contiguous chunk per thread, so no two threads ever touch the same element.
  2. Give each thread its own result slot. Each thread sums into a local variable and writes its slot once at the end, so there is no shared counter to fight over.
  3. Start all, then join all. Joining inside the creation loop would run the chunks one after another.
  4. Combine after joining. The join is what makes each slot safe to read without a lock.

Why sum into a local first? If every thread added straight into its array slot inside the loop, neighbouring slots would sit on the same cache line and the cores would fight over it. That is false sharing, a pure speed problem covered in caches and false sharing. Writing once at the end avoids it.

Common mistakes

  • Calling run() instead of start(). The program works, single threaded, and the bug hides until someone measures it.
  • Start then join inside the same loop. Each join waits for that thread before the next one is created, so the "parallel" code runs one task at a time. Start all, then join all.
  • A path that skips the join in C++. An early return or an exception destroys a joinable std::thread and calls std::terminate. Use std::jthread or a guard.
  • Detaching to make the terminate go away. It silences the crash and creates a thread that can outlive the data it uses. Join instead.
  • One new thread per task in a loop of 100,000 tasks. Each thread costs a stack and a system call to create; you run out of memory or time. Reuse a fixed set of workers, which is what a thread pool is.
  • Assuming start order is run order. Starting A before B says nothing about which runs first, or whether they overlap at all.
  • Reading a worker's result without joining. Without the join there is no guarantee the result is written, or that you see it if it is.

In the interview

You will rarely be asked "create a thread" on its own. It is the first five minutes of a bigger problem: an executor, a web crawler or a dependency job runner built without library executors, which Rubrik interviewers frequently require, and a thread pool clone in some LinkedIn concurrency rounds. Online assessments also use "what does this print" questions on start and run. What gets graded is whether you create a fixed set of named workers, start them all before waiting, and join every one at shutdown.

I'll create N worker threads up front, named so they are readable in a thread dump, start them all, and keep the handles so that shutdown can join every one. I won't create a thread per task: each one costs a stack and tens of microseconds to create, so for many small tasks I reuse workers.
In C++ I'll hold them as std::jthread, so they are joined even if something throws. A plain std::thread destroyed while joinable calls std::terminate.

Follow ups to expect: "What is the difference between start and run?" "What happens if main returns while workers are still running?" (Java: the JVM waits for non-daemon threads. C++: a joinable std::thread being destroyed terminates the program, and detached threads are cut off at exit.) "How do you wait for a thread with a timeout in C++?" (a future or condition variable with wait_for, because join has no timeout). "How many threads would you start?" (logical processors for CPU work, more for I/O, and why).

Senior depth

What a platform thread costs. Creating and destroying one is a system call round trip, on the order of tens of microseconds. Each reserves stack address space: HotSpot defaults to 1 MB to 2 MB depending on the platform (set with -Xss), and Linux pthreads commonly get 8 MB from ulimit -s. Only the pages actually touched use physical memory, but thousands of threads still mean real memory, scheduler work and context switches, which is the case for pools and, in Java 21, for virtual threads.

Oversubscription. Starting more CPU bound threads than logical processors, oversubscription, does not add throughput. It adds context switches and cache misses, and with locks it adds the chance that a thread holding a lock is descheduled while others wait for it.

Structured ownership. The habit to show is that every thread has an owner responsible for joining it, and that the owner does not return while its threads run. std::jthread, Java cleanup that completes its joins despite interruption, and an executor whose termination is awaited are three spellings of that one rule.

Under the hood

On Linux and macOS, HotSpot platform threads and common C++ standard libraries use pthread_create to create native threads. C++ joining typically uses pthread_join; Java 21's platform-thread join instead waits in a loop on the thread object's monitor until termination triggers notification. A Java platform thread maps to a kernel thread; virtual threads use a different scheduling mechanism. You will see the C++ side in detail in how std::thread maps to the OS.

Key takeaways

  • Java creates the OS thread at start(); C++ creates it in the std::thread constructor. run() is a plain method call.
  • join waits for the thread to finish and makes everything it wrote visible to you.
  • In C++, destroying a joinable std::thread calls std::terminate: join on every path, preferably with std::jthread.
  • Start all threads, then join all; never start and join one at a time.
  • There is no safe kill and no timed join in C++; timeouts need a future or a condition variable.
  • Use the logical processor count as a starting point for CPU bound work, and name your threads.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Main starts thread A, then thread B. Each prints its own letter once (printing is properly synchronized). Main then joins A, joins B, and prints done. Which outputs are possible? Select all that apply.Select all that apply
Why. Starting A first does not make A run first: the scheduler may run B before A. But done is printed only after both joins have returned, and a join returns only after that thread has finished, so both letters always come before done.
A teammate wrote this to download 8 files in parallel, expecting an 8 times speed up: What actually happens?
Why. The join sits inside the creation loop, so main blocks on download 1 before it creates download 2. The fix is two loops: create and start all 8, then join all 8. Joining in a loop is not a deadlock; it only waits.
A worker thread sets result = 42 on a plain field (no lock, no volatile, no atomic) and returns. Main calls join on it and then reads result with no lock. What does main see?
Why. Thread termination followed by a successful join is a synchronization edge in both Java and C++: the worker's writes are visible after join returns, so there is no data race. The tempting answer, "the read is not synchronized", misses that join itself is the synchronization.
You may wait at most 2 seconds for a worker, then you must carry on. Which approach is correct?
Why. Plain join waits forever, and neither language kills a thread for you. A timed wait tells you whether it finished; if not, the thread is still running and you still own it. detach does not stop anything: it only gives up your ability to join.
On a laptop with 8 physical cores and two hardware threads per core, what do availableProcessors() (Java) and std::thread::hardware_concurrency() (C++) typically return?
Why. Both report logical processors, so 16 here. Java's value also respects container CPU limits, and hardware_concurrency() is only a hint that may return 0 when unknown, so C++ code needs a fallback. Neither counts the threads your program has started.

Why. run() is an ordinary method call, so the lambda runs on the calling thread, which is main. Only start() creates a new thread that would print worker.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write parallelSum(int[] data, int k) in Java or parallel_sum(const std::vector<int>& data, int k) in C++. Split the array into k chunks, sum each chunk on its own thread, and return the total. Every thread you start must be joined before the function returns.
Model answer

The points an interviewer checks: the chunks do not overlap and the last one is clamped to the array length; each thread writes only its own slot, so there is no shared counter; all threads are started before any is joined; and the partial results are read only after the joins, which is what makes them visible without a lock. Passing data by reference is safe because every thread is joined before data can go away, and nobody writes to it.

Explain
In C++, what happens if an exception is thrown after a std::thread is created but before join() is called? Give two ways to prevent it, and say what the equivalent risk is in Java.
Model answer

The exception unwinds the stack, which destroys the std::thread object while it is still joinable, and the destructor calls std::terminate, so the whole process dies instead of the exception being handled. Fix one: use std::jthread in C++20, whose destructor requests a stop and then joins, so unwinding joins the thread. Fix two, for C++17: wrap the thread in a small RAII guard whose destructor joins if the thread is joinable, or catch the exception, join, and rethrow. Detaching is not a fix, because the thread may then outlive the data it uses.

Java will not terminate, but the same missing join still hurts: the method leaves while the worker runs, nobody can safely read its results, and its failure goes unnoticed. The fix is cleanup in a finally block that completes the join even if interrupted, restoring the interrupt status afterwards, or an executor that is shut down and awaited. A single interruptible join in finally does not guarantee completion.

Debug
This is meant to fetch 4 pages in parallel, but it takes as long as fetching them one by one. Find the bug and fix it.
Model answer

The join is inside the loop, so each fetch finishes before the next thread is created: the work is sequential. Start all the threads in one loop and join them in a second loop.

That fix exposes a second bug: once the threads really overlap, several of them call add on the same ArrayList at once, which is not thread-safe and can lose entries or corrupt the list. Give each thread its own slot in an array of size 4 (or use futures, next lesson), then build the list after all the joins. In C++ the same shape needs both fixes too: concurrent push_back on one std::vector is a data race.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"I gave each download its own thread, but eight downloads still run one after another. Walk me through what you would check."
What a strong answer covers
  • Check whether each worker is joined inside the creation loop, which serializes the downloads
  • In Java, calling run() directly also executes on the caller; start() schedules a new thread
  • In C++, construction starts the thread; there is no separate start() call
  • Start all workers before joining any, retain their handles, and collect results safely
  • Concurrency permits overlap but does not guarantee an eightfold speedup or a particular run order
How a senior would say it
I would first check whether the creation loop immediately joins each worker. That makes download one finish before download two even starts. In Java I would also check for a direct call to run(): that is an ordinary call on the current thread. start() schedules a new thread. In C++, constructing the thread starts it, so there is no separate start call to forget. I would keep the handles, start all eight downloads, then join them in a second loop. Each worker would write its own result slot, which I would read after its join. That avoids turning the scheduling fix into a shared collection bug. This allows overlap, but does not promise eight times the speed: bandwidth, server limits and scheduling still matter. Starting the first worker first does not guarantee that its download starts or finishes first.

Likely follow up: If every worker appends to the same list, what new bug does moving the joins expose?

Out loudabout 75 s
"Our C++ program terminates on an early return even though the worker already finished. Why, and how would you make thread ownership safe in both languages?"
What a strong answer covers
  • A finished std::thread remains joinable until joined, detached or moved from
  • Destroying a joinable std::thread calls std::terminate, including on an early return or exception
  • Use C++20 std::jthread, or a C++17 joining guard; automatic joining may still block
  • Keep borrowed data alive until the join; detaching does not solve ownership
  • Java does not terminate on losing a handle, but cleanup must account for interrupted joins
How a senior would say it
The worker finishing does not clear ownership of the thread. In C++, a finished thread is still joinable until somebody joins it, detaches it, or moves ownership elsewhere. Destroying that joinable handle calls std::terminate, even if the work finished long ago. I would use a C++20 std::jthread, whose destructor requests a stop and joins, or a joining guard in C++17. For example, if processing throws after launch, the guard still waits during unwinding. The data the worker borrows must outlive that wait, so I declare it before the thread owner. Detaching would remove the join obligation but could leave the worker using destroyed data. Automatic joining can still block forever if the task never finishes or responds to cancellation. Java has no terminating destructor, but losing the handle can still abandon work. I would arrange cleanup on every exit path and handle interruption of the cleanup join explicitly. If ownership requires waiting until completion, I finish joining and restore the interrupt status afterwards. The key is that somebody remains responsible for every worker until it ends.

Likely follow up: What if creating worker three fails after workers one and two have already started?

Out loudabout 75 s
"This request can wait only two seconds for a worker. How do you enforce the timeout, and who owns the worker afterwards?"
What a strong answer covers
  • A timeout bounds the caller's wait; it does not stop the worker
  • Java offers timed joins; C++ needs a timed future or condition variable wait
  • After timeout, request cooperative cancellation and retain ownership for later joining
  • Keep the worker's input and output storage alive until it finishes
  • Moving cleanup to another owner may be needed because a local std::jthread destructor still joins
How a senior would say it
I would bound the wait and separately define what happens to work that is still running. A timeout does not kill the worker. In Java I can use a timed join and check whether it terminated. Standard C++ has no timed thread join, so I would wait on a completion future or condition variable with a deadline. If the deadline expires, I request cooperative cancellation and keep the handle so somebody can join later. The task must support cancellation, including its blocking operations, and its input and result storage must stay alive meanwhile. For example, I cannot return while a C++ worker still writes into a local result variable. There is also a subtle ownership trap: putting the worker in a local std::jthread does not bound the whole function, because its destructor joins before return. If the response must return promptly, a longer lived owner, such as a service executor, must own the task and its data through cleanup. I would report timeout to the caller without pretending that the underlying work has already stopped.

Likely follow up: Does a completion future becoming ready prove that the worker has stopped accessing all of its captured data?
