Deadlock avoidance and detection

Trace safe states, detect wait-for cycles, interpret thread dumps, and choose recovery policies without confusing timeouts with proof of deadlock.

Asked atRubrikNvidia
Before this:Deadlock: the four conditions and how to break each

The last lesson prevented deadlock by design. This one covers the other options: avoid it at run time by refusing dangerous requests, or let it happen, find it and break it. Operating systems courses and online assessments test the theory, the Banker's algorithm above all; production systems rely on detection, timeouts and thread dumps.

In plain words

A bank manager has a limited amount of cash and lends it to builders, each of whom declared up front the most they could ever need. Before handing over money, she asks one question: "if I lend this, is there still some order in which every builder can get the rest of what they declared, finish, and repay?" If yes, she lends. If no, the builder waits, even if the cash is sitting in the safe. That is avoidance.

Detection is different: a hall monitor walks around now and then, draws an arrow from each person who is waiting to the person they are waiting for, and if the arrows form a loop, sends one person home so the others can move. Avoidance needs to know the future; detection only needs to look at the present.

Four ways to handle deadlock

StrategyIdeaWhere it is used
PreventionDesign so one Coffman condition can never hold: lock ordering, all-at-once acquisitionApplication code: the default (previous lesson)
AvoidanceBefore granting each request, check that the system stays in a state from which everyone can still finishThe Banker's algorithm: resource allocators with known maximum demands; textbook and assessment problems
Detection and recoveryLet deadlocks form, find the cycle, abort a victimDatabases
Ignore itProvide no automatic application deadlock recovery; diagnose and restart as needed (often called the "ostrich algorithm")General purpose operating systems, for the locks applications take

Resource allocation graphs

A resource allocation graph has a node for each thread and a node for each resource type, with one dot per instance. A request edge goes from a thread to a resource it is waiting for; an assignment edge goes from a resource instance to the thread holding it. Assume reusable resources, outstanding requests that must be satisfied, and no timeout, cancellation or external reclamation. Then:

  • If every resource has one instance, a cycle in the graph means deadlock, and no cycle means no deadlock.
  • If resources have several instances, a cycle is necessary for deadlock but not sufficient.

An online assessment will typically draw one of these and ask "is the system deadlocked?" Check the instance counts before you answer.

Avoidance: the Banker's algorithm

Dijkstra's banker's algorithm keeps the system in a safe state: a state from which there is at least one order (a safe sequence) in which every thread can get its declared maximum, finish and release everything. It needs four tables for n threads and m resource types:

  • Available[m]: free instances of each type right now.
  • Max[n][m]: the most each thread will ever hold, declared in advance.
  • Allocation[n][m]: what each thread holds now.
  • Need = Max - Allocation: what each thread may still ask for.

The safety check. Start with Work = Available and no thread finished. Repeatedly find an unfinished thread whose Need fits in Work component by component; pretend it runs to completion and releases everything (Work += Allocation[i]), and mark it finished. Add its original allocation, not its maximum: the extra need is borrowed from Work and then returned, so the net increase is just what it already held. If every thread finishes, the state is safe and the order you found is a safe sequence.

The request check, when thread i asks for Request:

  1. If Request exceeds Need[i], it is an error: the thread is asking for more than it declared.
  2. If Request exceeds Available, the thread must wait: there is simply not enough free.
  3. Otherwise pretend to grant it (Available -= Request, Allocation[i] += Request, Need[i] -= Request) and run the safety check. If the result is safe, grant it; if not, undo the pretend grant and make the thread wait.

The simple safety check costs O(m × n2) time and O(m + n) scratch space; the tables use O(m × n) space. Completion assumes that a thread given its needs eventually finishes and returns its resources. The algorithm guarantees a feasible completion order, not fair admission of every waiting request.

Worked example: the Banker's algorithm, step by step

Four threads, three resource types A, B and C with 7, 5 and 6 instances in total.

ThreadAllocation (A B C)Max (A B C)Need (A B C)
P02 0 15 2 23 2 1
P11 2 02 3 21 1 2
P22 1 24 2 32 1 1
P30 1 13 1 43 0 3

Allocations add up to 5 4 4, so Available is 2 1 2.

1. Is the current state safe? Scan the threads in order, repeatedly, starting from Work = 2 1 2:

  • P0 needs 3 2 1: A needs 3, only 2 in Work. Skip.
  • P1 needs 1 1 2: fits. Work becomes 2 1 2 + 1 2 0 = 3 3 2.
  • P2 needs 2 1 1: fits. Work becomes 3 3 2 + 2 1 2 = 5 4 4.
  • P3 needs 3 0 3: fits. Work becomes 5 4 4 + 0 1 1 = 5 5 5.
  • Second pass: P0 needs 3 2 1: fits now. Work becomes 7 5 6, which equals the totals, a good sanity check.

Safe, with safe sequence P1, P2, P3, P0.

2. P3 asks for 2 0 2. It is within P3's need (3 0 3) and within Available (2 1 2), so pretend to grant it: Available becomes 0 1 0, and P3's need drops to 1 0 1. Safety check from Work = 0 1 0: P0 needs A, P1 needs A, P2 needs A, P3 needs A. Nobody fits. Unsafe, so the request is denied and P3 waits, even though the resources were sitting there. This is the step people get wrong: available is not the same as safe.

3. P1 asks for 1 0 2 (the denied grant was rolled back, so we start from the original state). Within need (1 1 2) and Available (2 1 2). Pretend: Available becomes 1 1 0 and P1's need becomes 0 1 0. From Work = 1 1 0: P1 fits (Work 3 3 2), then P2 (5 4 4), then P3 (5 5 5), then P0 (7 5 6). Safe, so it is granted.

4. Two quick ones, after step 3, with Available at 1 1 0. P0 asks for 3 0 0: within its need, but only 1 A is free, so it simply waits; no safety check is needed. P2 asks for 3 0 0: its need for A is only 2, so this is an error, not a wait.

This is a single-threaded simulation with valid, nonnegative initial tables and totals that fit in int. In a real allocator, request, safety checks and the release path must share one lock; a waiter releases that lock while waiting and rechecks after notification. The code derives Need from the other tables, so it needs no separate update or rollback for Need. And notice what unsafe means: not that a deadlock has happened, only that one can no longer be ruled out if every thread asks for its full maximum. That conservatism and the need to know every maximum in advance explain why it is uncommon in general purpose application allocators. This example fixes the participant set; a dynamic allocator can admit new participants only after validating their maximum claims and preserving safety.

Detection: find the cycle

Detection collapses the resource graph into a wait-for graph: an edge from T1 to T2 means T1 waits for something T2 holds. With single-instance resources (an exclusive lock is one), a deadlock is exactly a cycle in this graph. Finding one is a depth-first search that marks the threads on the current path; reaching a thread that is already on the path closes a cycle.

The graph must be a consistent snapshot: synchronize its ownership and wait records, or revalidate a reported cycle before acting. The example returns one cycle, possibly rotated depending on traversal order. T4 is blocked behind the cycle but is not a cycle member; aborting T4 would not release any lock needed by T1, T2 or T3.

With V threads and E edges, Java's hash-map implementation takes expected O(V + E) time; C++'s ordered maps take O((V + E) log V). Auxiliary state and recursion use O(V) space. Dense integer ids with arrays give O(V + E) worst-case traversal time. For very deep graphs use an explicit DFS stack; use strongly connected components to identify all cyclic groups, rather than stopping at one cycle.

For multiple-instance resources, start Work at Available and use current outstanding requests instead of maximum remaining needs. Repeatedly let a process whose request fits finish and add its allocation to Work. Processes holding no resources can initially be marked finished because they cannot contribute to resource deadlock; remaining unfinished holders form the set that cannot complete under this check. This detects a current allocation problem, whereas Banker's asks about possible future maximum demands.

Choose when to run detection: on each wait (quick discovery, more work), periodically, or only after a wait lasts a while, as PostgreSQL does. Recovering one cycle may leave other cycles, so detect again after victim cleanup.

Detecting at the moment of waiting, like a database lock manager

For exclusive resources with one owner, unique transaction ids and one sequential caller per transaction, each transaction has at most one outgoing wait. The check is then simpler: before blocking, follow the chain "who holds the lock I want, what is that holder waiting for, who holds that" and see whether it leads back to you. If it does, waiting would close a cycle, so the requester becomes the victim, rolls back and releases everything. Serialize the check, wait registration and ownership changes under one manager lock so two requests cannot both miss the new edge. This prevents cycles in the managed resource graph, not in arbitrary callbacks or external systems.

Which transaction becomes the victim depends on which one asked second, but there is always exactly one: the requests are serialized by the manager's lock, so the first request sees no cycle and waits, and the second sees the chain lead back to itself. Under the stated one-caller, exclusive-lock assumptions, a new owner is running rather than waiting, and each new wait is checked under the same mutex. Reacquiring a resource already owned by that transaction is idempotent, not reference counted; releaseAll relinquishes all its resources. The demo changes no database rows: its rollback message models victim selection and lock release, not an implemented undo log.

The C++ sample uses C++20 std::latch and std::erase_if. For C++17, use the mutex, counter and predicate-wait latch described in deadlock, and erase matching map entries in an iterator loop, assigning the iterator returned by erase. A production lock manager also needs deadlines, bounded queues and failure cleanup; shared locks and lock upgrades require a graph with multiple blockers.

Detecting deadlocks in a running program

For locks inside one process, the tool is the thread dump. In Java 21, jstack -l PID or jcmd PID Thread.print -l prints platform-thread stacks and lock details; kill -3 PID requests a dump to the process output. The JVM detects cycles of object monitors and ownable synchronizers such as ReentrantLock, not every java.util.concurrent dependency. Here is a dump of a frozen transfer program like the one in the last lesson, trimmed:

How to read it: each thread's state is BLOCKED (on object monitor); its stack shows the lock it holds (- locked <...d78>) and the one it wants (- waiting to lock <...d90>); match the addresses across threads and the cycle is plain, and the summary at the end spells it out. With ReentrantLock the threads show as WAITING (parking) with - parking to wait for <...> (a java.util.concurrent.locks.ReentrantLock$NonfairSync), and the summary says waiting for ownable synchronizer ..., which is held by "worker-2". Name your threads: a cycle between transfer-1 and transfer-2 explains itself; one between pool-3-thread-7 and pool-3-thread-2 does not.

Java

The same check is available through ThreadMXBean.findDeadlockedThreads() for platform threads; findMonitorDeadlockedThreads() covers monitors only. These calls are for diagnostics and can be expensive, so measure the overhead before polling frequently. A null result means no supported cycle was found, not that the program is live.

Java 21's ThreadMXBean does not detect cycles involving virtual threads. Pool starvation, futures, condition predicates, semaphores and remote calls also need application dependency analysis. For virtual-thread stacks use jcmd PID Thread.dump_to_file -format=json /tmp/threads.json; in Java 21 that dump omits lock ownership details and does not supply automatic deadlock detection. For a stalled pool, combine stacks with active worker counts, queue depth and the tasks needed to complete each future.

C++

Standard C++ has no built-in deadlock detector. Dump every stack with thread apply all bt in gdb or bt all in lldb; on macOS use sample PID, and on Linux eu-stack -p PID is another option. Look for mutex waits, which may appear as __psynch_mutexwait on macOS or futex waits on Linux. Caller frames locate acquisition sites, but portable std::mutex exposes no owner query, so a stack alone may not identify every owner.

Debug wrappers that record owners and attempted acquisitions can make the dependency graph explicit. Some Linux ThreadSanitizer runtimes support potential lock order inversion detection; this Mac's Apple clang runtime does not. Such checks only cover observed operations, and a clean run proves neither absence of deadlocks nor correct handling of futures and queues.

Timeouts: bound waits, then recover

A timeout is suspicion, not proof: the dependency may just be slow. Use Java tryLock(long, TimeUnit) or Future.get(long, TimeUnit), C++ std::timed_mutex::try_lock_for or std::future::wait_for, and RPC deadlines where failure is recoverable. C++ future::get() has no timed overload; test wait_for for std::future_status::ready before calling it, and handle deferred separately.

Use one overall deadline, measured with System.nanoTime() or std::chrono::steady_clock, so nested waits and retries consume one budget. A timeout does not release already held locks, roll back partial updates or cancel the task behind a future. Cleanup must do that explicitly, using finally or RAII, cooperative cancellation and a bounded retry policy. A future from std::async(std::launch::async, ...) can still block in its destructor, so timing out wait_for does not necessarily bound the enclosing scope.

Across services, propagated deadlines and cancellation are common ways to limit a stall; distributed deadlock detection also exists, so deadlines are not the only possible strategy. Choose deadlines from the request budget and measured latency distribution, and back off with jitter after releasing resources. OS scheduling can delay a timed call's return, so these are not hard real-time guarantees.

How databases detect deadlocks and choose a victim

Databases are the main users of detection, because they can do what a program cannot: roll a transaction back. Two transactions that lock rows in opposite orders deadlock exactly like two threads:

  • PostgreSQL lets a lock wait run for deadlock_timeout (1 second by default) before it checks for a cycle, because the check is relatively expensive and most lock waits end sooner. If it finds one, it aborts a transaction with ERROR: deadlock detected (SQLSTATE 40P01), and its documentation says plainly that which transaction is aborted is difficult to predict and should not be relied upon.
  • MySQL InnoDB enables deadlock detection by default and rolls back a victim, preferring small transactions, where size is the number of rows inserted, updated or deleted (error 1213). On very high concurrency the detection itself can become a bottleneck, so some systems turn it off and rely on innodb_lock_wait_timeout (50 seconds by default) instead.
  • SQL Server runs a lock monitor that searches for cycles every 5 seconds by default, more often once it has found some, and chooses the victim by DEADLOCK_PRIORITY and then by which transaction is cheapest to roll back (error 1205).

Victim policy is engine-specific: work to undo, priority and fairness can influence it, but no universal rule picks the cheapest or youngest transaction. InnoDB lock wait timeouts normally roll back only the waiting statement, whereas detected deadlocks roll back the transaction; application recovery must explicitly end any remaining transaction before retrying. Two classic timestamp schemes go further and prevent cycles outright, by letting waits go in only one direction of age:

SchemeOlder transaction asks for a lock a younger one holdsYounger transaction asks for a lock an older one holds
Wait-dieThe older one waitsThe younger one dies: it aborts and restarts later with its original timestamp
Wound-waitThe older one wounds the younger: the holder abortsThe younger one waits

Both schemes keep the original timestamp on restart, with a unique tie-breaker if timestamps tie. Under fair scheduling, finite transaction work and eventual completion of older transactions, this prevents repeated restarts from making a transaction permanently young. A wounded holder must finish rollback before a conflicting grant is usable. The rule for application code is to design retries explicitly. Catch the deadlock error, roll back, back off with jitter, and run the whole transaction again; and touch rows in a consistent order (for example by primary key) to reduce deadlocks. Re-run the whole transaction from fresh reads, with bounded retries; emails, payments and other external effects need idempotency or an outbox so retry does not duplicate them.

Why a program cannot recover the way a database does

A database can abort a victim because it tracks transactional changes and has a rollback protocol. An ordinary thread has no automatic undo log, and killing it is unsafe: Java deprecated Thread.stop long ago because it released monitors with objects half updated, and in Java 21 it always throws UnsupportedOperationException; standard C++ has no forced thread-termination API. So inside a process, detection is for diagnosis: dump the threads, alert, restart the process, and fix the lock order. Recovery belongs in the design: interruptible or timed waits, cleanup and rollback on paths that can safely fail. Cooperative cancellation can then recover some stalls; it cannot rescue an arbitrary monitor or mutex cycle.

Common mistakes

  • Treating unsafe as deadlocked. An unsafe state only means the algorithm can no longer guarantee that everyone finishes.
  • Granting because the resources are available. Step 2 of the worked example: available but unsafe means wait.
  • Skipping the "request exceeds need" check, or forgetting to undo the pretend grant when the result is unsafe.
  • Declaring deadlock from a cycle in a multi-instance graph. Check whether some thread outside the cycle can still free an instance.
  • Not retrying transactions on deadlock errors, or retrying immediately without backoff.
  • Lock timeouts shorter than normal waits. They fire under ordinary load and the retries add more load.
  • Diagnosing from one thread dump. Take two or three, a few seconds apart: unchanged stacks are a clue, not proof. An idle worker or a busy loop can appear in the same frame repeatedly. Confirm ownership and dependency edges; an explicit lock cycle in one consistent dump is already strong evidence.

In the interview

Rubrik reports describe assessments with about ten MCQs on multithreading and operating systems. One report describes resource allocation policies before a bathroom scheduling problem; that is not evidence of a specific Banker's question. Nvidia system software interviews ask about deadlock conditions and avoidance. Practise a Banker's table, a resource allocation graph, and then "how would you detect it in production?"

There are three ways to deal with deadlock. Prevention removes a Coffman condition by design, and in application code I use it: lock ordering. Avoidance, like the Banker's algorithm, checks each request against a safe state, but it needs every thread's maximum in advance and is too conservative for general use. Detection lets deadlocks happen and breaks them: a database builds the wait-for graph, finds a cycle and rolls back a victim according to its policy. Inside a process I cannot roll back a thread, so detection there means dependency diagnosis from dumps; timeouts support recovery only with explicit cleanup.

Follow ups: "trace the Banker's algorithm on this table", "is this graph deadlocked?", "what does jstack show for a deadlock?", "how does PostgreSQL or MySQL pick the victim?", "explain wait-die and wound-wait", and "what should application code do when it gets a deadlock error?"

Key takeaways

  • Prevention (by design), avoidance (Banker's, safe states), detection and recovery (wait-for graph cycles), or ignore and restart.
  • Single-instance resources: a cycle is a deadlock. Several instances: a cycle is only a warning.
  • Banker's: request within need, then within available, then pretend and run the safety check; available is not the same as safe, and unsafe is not the same as deadlocked.
  • Detection is a cycle search in the wait-for graph, run on each wait, periodically, or after a wait has lasted a while.
  • Java 21 detects supported platform-thread lock cycles; C++ needs stack inspection and owner information. Neither approach automatically detects every application dependency. Timeouts need cleanup and cancellation.
  • Databases abort a victim and expect the application to retry the whole transaction; an ordinary thread has no automatic rollback, so design cooperative recovery or diagnose and restart.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Two resource types. Available = (1, 1). P0 holds (1, 0) with maximum (2, 2); P1 holds (0, 1) with maximum (1, 2); P2 holds (1, 1) with maximum (2, 1). The state is safe (sequence P1, P2, P0). P0 now asks for (1, 0). What does the Banker's algorithm do?
Why. The request is within P0's need (1, 2) and within Available. Pretend to grant: Available (0, 1), P0's need becomes (0, 2). Then P0 needs 2 of B but only 1 is free, P1 needs (1, 1) and P2 needs (1, 0), and both need an A that is not there. No remaining maximum need fits, so no safe sequence exists: deny and wait. Availability alone is insufficient; the request is within the maximum, and allocation size is not the admission rule.
A resource allocation graph has a cycle. When can you conclude that the system is deadlocked?
Why. With single-instance resources, a cycle and a deadlock are the same thing. With several instances, a thread outside the cycle may hold an instance it will release, breaking the wait; then the cycle is necessary but not sufficient. Two threads are enough for a cycle; graph structure and resource counts, not a minimum of three threads, determine the result.
The Banker's algorithm says the system is in an unsafe state. What does that mean?
Why. Safe means a completion order is guaranteed to exist. Unsafe means that guarantee is gone: if every thread did ask for its maximum, some could be stuck forever. Threads often finish without asking for their maximum, so an unsafe state can resolve on its own. No exceeded claim or zero-availability condition is implied: unsafety is a failed completion-order proof.
Why does PostgreSQL wait for deadlock_timeout (1 second by default) before checking a waiting transaction for a deadlock?
Why. A real deadlock never resolves on its own, but nearly all lock waits are ordinary short waits behind a running transaction. Checking every wait immediately would waste work on those; delaying the check saves work. A cycle can be detected immediately in principle; waiting does not allow the OS or a member of an unbroken cycle to resolve it automatically.
Under wound-wait, an older transaction T1 requests a lock held by a younger transaction T2. What happens?
Why. Wound-wait lets older transactions take what they need from younger ones; a younger requester waits for an older holder. Waits therefore only go from younger to older, so no cycle can form. Wait-die permits the older requester to wait; wound-wait instead selects the younger holder. Neither aborts both, and restarts retain the original timestamp.
A database recovers from a deadlock by rolling back a victim. Why can't a Java or C++ program automatically do the same to an arbitrary deadlocked thread?
Why. A thread blocked on a monitor or a std::mutex does not respond to interruption, and forcibly stopping it would leave the objects it was changing half updated. The JVM does know which monitors a thread holds; that is how jstack finds the cycle. It cannot automatically undo arbitrary changes. Interruptible locking with application cleanup can enable cooperative recovery, but plain monitor entry is not interruptible. CPU usage is not the obstacle.
Java onlyTwo Java 21 platform threads deadlock while using untimed lock() on two ReentrantLocks. What does jstack -l PID show once both are parked?
Why. ReentrantLock parks waiting threads, so they show as WAITING (parking), not BLOCKED. The JVM's deadlock search covers these "ownable synchronizers" as well as monitors, so the report still appears, phrased as "waiting for ownable synchronizer ..., which is held by ...".

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
Two resource types, A and B, with 6 and 4 instances. P0 holds (1, 1) with maximum (3, 2); P1 holds (2, 0) with maximum (3, 3); P2 holds (1, 1) with maximum (4, 2). (a) Is the state safe? (b) P1 asks for (0, 2): grant or wait? (c) Starting again from the original state, P0 asks for (1, 1): grant or wait? Show your work.
Model answer

Available is (6, 4) minus the allocations (4, 2), which is (2, 2). Needs are P0 (2, 1), P1 (1, 3) and P2 (3, 1).

(a) From Work = (2, 2): P0's need (2, 1) fits, so Work becomes (3, 3); P1's need (1, 3) fits, Work (5, 3); P2's need (3, 1) fits, Work (6, 4), equal to the totals. Safe, with sequence P0, P1, P2.

(b) (0, 2) is within P1's need (1, 3) and within Available (2, 2). Pretend to grant: Available (2, 0), P1's need (1, 1). From Work = (2, 0): P0 needs 1 of B, P1 needs 1 of B, P2 needs 1 of B, and there is no B. Unsafe, so P1 waits and the pretend grant is undone.

(c) (1, 1) is within P0's need (2, 1) and within Available (2, 2). Pretend: Available (1, 1), P0 holds (2, 2) and needs (1, 0). From Work = (1, 1): P0 fits, Work becomes (3, 3); P1's need (1, 3) fits, Work (5, 3); P2's need (3, 1) fits, Work (6, 4). Safe, so the request is granted.

Debug
Two services write to PostgreSQL. Service A moves money from account 7 to account 9 in one transaction (update row 7, then row 9); service B moves money from 9 to 7 (update row 9, then row 7). Under load, both see ERROR: deadlock detected a few times an hour, and those requests fail. Explain what is happening and what you would change.
Model answer

Each transaction takes a row lock when it updates a row and holds it until commit. When A has updated row 7 and B has updated row 9, A's update of row 9 waits for B and B's update of row 7 waits for A: a cycle, exactly the two-thread transfer deadlock, one level down. PostgreSQL notices after its deadlock timeout and aborts one of them with SQLSTATE 40P01, and the service turns that into a failed request. Two changes. First, make deadlocks rare: have every transaction touch rows in one consistent order, for example by locking the account rows it needs in ascending id order at the start (SELECT id FROM accounts WHERE id IN (7, 9) ORDER BY id FOR UPDATE), which breaks circular wait just like lock ordering in code. Second, make the remaining ones harmless: treat 40P01 (and serialization failures) as retryable, roll back, wait a short random backoff, and re-run the whole transaction a bounded number of times before failing. I would also keep transactions short, with no network calls inside them, because the longer locks are held the more likely a cycle becomes.

Explain
An interviewer asks: "Prevention, avoidance or detection: which would you use in application code, in a database, and in an operating system, and why?"
Model answer

In application code, prevention: I control the code, so I impose a lock order, take multiple locks with a deadlock-safe protocol, and never hold a lock across calls I do not control. That costs almost nothing at run time and needs no knowledge of the future. Avoidance like the Banker's algorithm does not fit, because threads cannot declare their maximum needs up front and the check is conservative and runs on every request. In a database, detection and recovery: transactions lock rows in an order chosen by user queries, so one global application lock order is not always enforceable; the engine tracks transactional changes, builds a wait-for graph, finds a cycle, rolls back a selected victim and let the application retry. In a general purpose operating system, mostly neither for user locks: the kernel prevents deadlock in its own code with strict lock ordering, but it does not run avoidance or detection for the mutexes applications take; it leaves those to the applications. Avoidance mainly appears in systems with fixed, known workloads, and in exams. Timeouts are a recovery policy, not evidence that a cycle exists.

"The resources are available, but your Banker rejects the request. Walk me through why that can be correct."
What a strong answer covers
  • Availability is an immediate capacity check; safety requires a completion order for all declared maxima
  • Check request against remaining need, then available resources
  • Tentatively update available, allocation and derived need under one allocator lock
  • Trace Work and explain why simulated completion adds Allocation, not Max
  • Grant only if every participant can finish; otherwise restore state and wait
  • Distinguish unsafe from already deadlocked and state the known-maxima limitation
How a senior would say it
Availability is necessary, but it is not enough. Banker grants a request only if the resulting state still has an order in which every participant could obtain its declared maximum and finish. I first check that the request stays within the caller's remaining need, then within the currently available resources. I tentatively grant it and run the safety check under the allocator's lock. Work starts at the new available vector. Whenever an unfinished participant's remaining need fits, I pretend it finishes and add its current allocation back to Work. I add allocation, not maximum, because the extra resources it temporarily borrows are returned too. If everyone can finish, I commit the grant. If nobody else fits before all participants finish, I restore the tables and make the requester wait. For example, handing out the last A may leave every participant needing another A, even though the request itself fitted. That is unsafe, not necessarily already deadlocked: some participants might finish below their maximum. The tradeoff is that Banker needs credible maximum claims in advance and can delay requests conservatively.

Out loudabout 90 s
"Production has stopped completing requests, but the Java deadlock detector returns null. Does that rule out deadlock? What is your next move?"
What a strong answer covers
  • A null result excludes only supported detected cycles, not every liveness failure
  • State Java 21 platform-thread, monitor and ownable-synchronizer limits
  • Collect stacks plus lock owners, pool saturation, queue depth and future dependencies
  • Build a consistent dependency graph and distinguish a cycle from ordinary waiting
  • Explain C++ owner-instrumentation limits and the role of repeated observations
  • Use deadlines with cleanup; do not forcibly terminate an arbitrary lock holder
How a senior would say it
No. A null result means that detector found no cycle it supports. In Java 21, ThreadMXBean detects platform-thread cycles involving monitors and ownable synchronizers. It does not detect cycles involving virtual threads, or infer which queued task will complete a future. I would capture platform-thread stacks with lock details, and use the virtual-thread dump facility when relevant. I would also collect active worker counts, queue depth and the tasks responsible for completing blocked requests. Then I would connect each wait to the owner or producer that can satisfy it. Eight parents waiting for children queued behind them can be a deadlock even with no mutex cycle. For a lock cycle, I need consistent ownership and wait edges; a thread parked in one stack frame alone proves little. Repeated captures help distinguish ordinary waits from persistent dependencies, but do not replace that graph. In C++, stack traces locate waits, while owner instrumentation may be needed because standard mutexes expose no owner query. For recovery I would use existing cooperative cancellation and cleanup paths if they are safe. A deadline only ends a wait; it does not roll back changes or release other locks automatically. Without a safe recovery path, I would capture evidence, restart and fix the dependency.

Out loudabout 75 s
"PostgreSQL aborts one of our money transfers as a deadlock victim. How would you stop that becoming a failed or duplicated payment?"
What a strong answer covers
  • Describe opposite row-lock acquisition and PostgreSQL selecting a victim
  • Acquire account rows in a stable order and keep transactions short
  • Roll back and retry the entire transaction with fresh reads and a bounded deadline
  • Keep external side effects idempotent or behind an outbox
  • Distinguish a deadlock error from a generic timeout and avoid relying on victim choice
How a senior would say it
I would combine consistent row-lock ordering with a bounded retry policy for the entire transaction. Two transfers can lock their source rows first, then each wait for the other's destination row. PostgreSQL detects the cycle and aborts a victim; I would not depend on which transaction loses. I would lock both account rows in ascending immutable id order before validating balances and applying the transfer. I would keep that transaction short and avoid remote calls while holding the locks. If a deadlock error still occurs, I would roll back and retry from fresh reads, with jitter, a retry limit and one overall deadline. Retrying only the failed statement is not enough because the transaction was aborted. Database rollback also does not undo an email or an external payment already sent. Those effects need an idempotency key or a transactional outbox so another attempt cannot duplicate them. Finally, I would classify errors carefully: a deadlock error establishes a detected cycle, whereas a generic timeout could mean ordinary overload. The retry budget must prevent recovery traffic from making that overload worse.
