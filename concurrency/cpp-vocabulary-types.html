optional, pair, tuple, string_view and friends

Design explicit results with optional, unpack pairs and tuples, manage view lifetimes, and represent commands with variant.

Before this:Templates, auto and type deductionObject lifetime, the stack and the heap

A concurrent API keeps having to say "maybe": the queue may be empty, the wait may time out, the key may be missing, the queue may be closed. C++ has small vocabulary types for exactly this; combine them with synchronization so callers can check and act in one operation.

In plain words

Think of a parcel locker at a railway station. You open your locker and it either holds one parcel or it is empty; there is no third state, and you find out by opening it once. std::optional is that locker, an optional value. A pair or a tuple is a tiffin carrier with two or three stacked boxes that travel together.

A string view is a window onto someone else's notice board. Looking through it is free, but if the owner takes the board down, your window shows a blank wall, or worse, someone else's board. A view never owns what it shows.

Why this matters for concurrency

  • "Maybe" must be one call. if (!q.empty()) x = q.pop(); is two calls, and another thread can take the last item in between. std::optional<T> tryPop() checks and takes inside one critical section, and the empty optional says "nothing there" without a magic value like -1.
  • Timeouts and shutdown need a "no value" result. You can design popFor(timeout) to return an empty optional on timeout, and blocking pop() to return empty once the queue is closed and drained.
  • Structured bindings unpack compound results. auto [it, inserted] = cache.try_emplace(key); reports both the entry and whether insertion happened. You must supply the lock; neither the binding nor a standard map synchronizes itself.
  • Views across threads need a lifetime contract. A queued string_view or span can outlive its backing storage. Pass owning types unless you can prove that the storage stays alive and accesses are synchronized.

std::optional: a value or nothing

std::optional<T> (C++17, header <optional>) holds either one T or nothing. The optional stores its T inline, but that T, such as a long std::string, can allocate its own storage. Its exact size is implementation dependent: budget for the payload, an engagement indicator and alignment padding, and measure with sizeof if layout matters.

The concurrency use is the tryPop shape: one locked call that either takes an element or reports that there was none.

The type constraints make both moves, from the queue and into the returned optional, nonthrowing; removing the old element cannot throw either. Without them, a failed move can change the front element or lose an item after removal. This example preloads every task: an empty tryPop() means "empty now", not "no producer will ever add work". C++20's std::jthread also joins during unwinding if starting a later worker fails; in C++17 use an RAII joining wrapper.

This is why a concurrent queue needs a combined check-and-take operation. A locked empty() can still be useful as a snapshot, but its answer is not a reservation. Merge the check and the act into one locked operation, and report "nothing" through the return type.

std::optional<bool> tests presence, not truth

std::optional<bool> ready = false; if (ready) ... takes the branch, because if (ready) asks "is there a value?", and there is one: false. Write ready.value_or(false), or ready && *ready. The same trap applies to std::optional<int> holding 0. A related limit: std::optional<T&> is not allowed in C++20 or C++23, so use a plain pointer (null for "nothing") when you mean "maybe a reference".

value_or(makeDefault()) evaluates makeDefault() even when the optional is engaged, and returns a value, not a reference. Constructing the fallback, converting it, or copying or moving T can throw. For a lazy fallback use opt ? *opt : makeDefault(); C++23's and_then, transform and or_else are not C++20 APIs.

Moving an optional does not disengage the source: it still contains a moved-from T until you call reset(). emplace replaces any old value; if construction throws, the optional is empty. Sharing an optional does not make it atomic, and a pointer or std::optional<std::reference_wrapper<T>> still borrows the referenced object's lifetime.

pair, tuple and structured bindings

std::pair<A, B> (header <utility>) holds two values (.first, .second); std::tuple (header <tuple>) holds any number, read with std::get<0>(t). Every element of a std::map<K, V> is a std::pair<const K, V>. Its ordinary single-element insert, emplace and try_emplace overloads return std::pair<iterator, bool>; hinted overloads return an iterator, and range insertion returns nothing.

Structured bindings (C++17) name the parts directly. auto [a, b] = obj; copies an ordinary pair or tuple lvalue into a hidden object; an rvalue can move or initialize it directly. auto& [a, b] = obj; binds to the original object, and for (const auto& [key, value] : map) avoids copying each entry. They also work with arrays and suitable structs with public data members. Copying a tuple of references or views still leaves aliases to the original data.

try_emplace is the one to remember for concurrent code. Under your lock it does "insert if absent" with a single lookup, and the returned bool tells you whether you created the entry, which is exactly what a registry, a per-key lock table or a single-flight cache needs. It also does not move from its arguments when the key already exists, unlike insert and emplace, which may consume your value even when they insert nothing.

Argument expressions are still evaluated before the call: cache.try_emplace(key, expensiveLoad()) runs expensiveLoad() even on a hit. For lazy construction, pass constructor arguments; for a slow single-flight load, coordinate an in-progress result explicitly. Use a named struct instead of a large tuple when field names communicate the contract better.

Ordering by several fields with std::tie

Schedulers order tasks by deadline, and break ties by arrival order so equal deadlines run first in, first out. std::tie builds a tuple of references, and tuples compare lexicographically, which gives you the whole comparison in one line:

That defaulted operator would be deleted, so it cannot replace the hand-written ordering by due and seq. A real scheduler must also assign seq under synchronization and define what happens before it overflows.

Structured bindings and lambdas

Capturing a structured binding in a lambda, as in auto [host, port] = endpoint(); std::thread t([host, port] { connect(host, port); });, is standard only from C++20. In C++17 mode clang accepts it with the warning "captured structured bindings are a C++20 extension", and older compilers reject it. If you must stay in C++17, copy into plain variables first, or use an init capture: [h = host, p = port].

std::string_view: a window, not a copy

A std::string_view (C++17, header <string_view>) describes characters with a pointer and a length. It is a useful parameter for synchronous text reading without copying. It never owns the characters or extends their lifetime. Two examples show the danger:

Both compile and leave a dangling reference to characters whose lifetime has ended; reading those characters is undefined behavior. Across threads this can hide because the view is created in one thread and used in another, later.

A view is not necessarily null-terminated. view.substr(pos, count) returns another view, and view.data() may point into the middle of a buffer. Pass its length to length-aware APIs, or make an owning std::string and use c_str() when a C API needs a terminator. In contrast, std::string::substr returns a new string, so std::string_view v = text.substr(0, 3); dangles at the semicolon.

The async logger bug

A logger with a background writer thread is an interview design reported at Databricks in the form of an ordered, durable event writer. A small logger can take std::string_view so callers can pass text cheaply. The bug is to store that borrowed view without an ownership contract:

The fix is a rule: copy into an owning type at the thread boundary. The parameter can stay a view; the queue must hold std::string.

Two details worth saying in an interview. The writer thread is the last member, because members are constructed in declaration order and the thread immediately uses the earlier members. The destructor sets done_ under the lock, notifies, and joins; the writer returns only when the queue is closed and empty.

The owner must stop and join all callers of log() before destroying the logger, and destruction must not happen on its writer thread. This teaching example assumes the output sink and synchronization operations succeed; draining to std::cout is not a durability guarantee. A production writer also needs error delivery and backpressure, as in exceptions and the durable log writer.

std::span: the same idea for arrays

std::span<T> (C++20, header <span>) is a span, a view of a contiguous run of elements such as part of a vector. Views shine in parallel code that splits read-only data into chunks: each thread gets a span over its own slice, nothing is copied, and the input data is only read.

The vector must outlive every span and keep the viewed elements alive at stable addresses. This sample fixes its size until all joins, and 1,000 divides evenly into four chunks; general partitioning must handle a remainder. span<const T> prevents writes through that view, not through other aliases. A C++17 fallback is a pointer plus a length or an iterator pair, with the same lifetime rules; C++20 span indexing requires an in-range index and has no checked at().

std::variant: one of several types

A variant, std::variant<A, B, C> (C++17, header <variant>), normally holds one value of one listed type and remembers which. You test with std::holds_alternative<A>(v), read with std::get<A>(v) (throws std::bad_variant_access on a different active type), or use std::get_if<A>(&v) (a pointer, or null), and dispatch with std::visit. Type-based access requires the type to occur exactly once; otherwise use an index.

A default-constructed variant constructs its first alternative, which must be default-constructible. Put std::monostate first if you need an explicit empty state. A throwing type change can instead leave it valueless_by_exception(); index() then returns std::variant_npos and std::visit throws std::bad_variant_access. This exceptional state is different from deliberately holding monostate.

Command queues can use alternatives such as "append", "flush" and "stop"; a future can represent pending, a value or an exception. A visitor must compile for every alternative and, with the deduced-return overload, return the same type and value category for every case. The final assertion depends on the visitor's template parameter, so C++20 accepts it in a discarded branch. Adding another alternative makes compilation fail until you supply its behavior, rather than silently treating an unknown command as stop.

std::any (C++17, header <any>) can be empty or hold a copy-constructible type; value-form std::any_cast throws std::bad_any_cast on a mismatch, while pointer-form casting returns null. Prefer a variant for a known closed set of alternatives. std::expected<T, E> (C++23, not C++20) represents a value or an error; it does not prevent operations on T or E from throwing. std::function and std::reference_wrapper appear in lambdas and callables and templates.

Worked example: choosing the pop API for a concurrent queue

The interviewer asks for a thread-safe queue that many consumers share. Before writing code, decide the shape of "take an element", because the signature decides whether callers can race.

SignatureVerdict
bool empty(); T& front(); void pop();Broken across threads: the check and the take are separate calls, and front() hands out a reference into guarded storage.
T pop() that blocks until an element arrivesReturns a value on success; needs a separate error channel, such as an exception, for timeout or closure.
bool tryPop(T& out)Correct, and the classic C++11 shape. The caller must build a T first, and an out-parameter reads worse.
std::optional<T> tryPop()The modern default: check and take in one call, and "nothing" lives in the type.
std::optional<T> popFor(std::chrono::milliseconds timeout)Waits for a value until a deadline, then reports absence. Scheduling and lock reacquisition can delay its return beyond that deadline. See the chrono lesson.
std::optional<T> pop() that blocks, and returns empty once the queue is closed and drainedWhat you want as soon as the queue can be shut down: consumers leave their loop cleanly instead of hanging or needing a poison pill.

A strong answer picks a contract before picking a type. An optional distinguishes a value from absence, but cannot distinguish timeout, empty and closed by itself. If callers need the reason, return a named result with a status, or a std::variant<T, TimedOut, Closed> when its alternatives are distinct. The implementation still supplies atomicity, and allocation or lock failures can still throw.

Common mistakes

  • *opt without checking. Dereferencing an empty optional is undefined behavior, not an exception. Check first, or use value() (throws) or value_or().
  • if (flag) on a std::optional<bool>. It tests presence, not truth.
  • Keeping a view without its owner. A queued view needs stable backing storage until the consumer finishes. Copy into std::string or std::vector, or retain an immutable owner explicitly.
  • Viewing data that another thread changes. Reallocation invalidates a view; unsynchronized reads and writes to the same characters are a data race even without reallocation.
  • auto& [a, b] = shared; under a lock, used after unlocking. The names refer into the shared object. Copy owning values under the lock; copying a view or reference wrapper is not a deep snapshot.
  • An empty() method on a concurrent queue that callers use for decisions. The answer may be stale before the caller acts on it. Offer tryPop instead; keep size() and empty() for metrics and tests.

In the interview

These types show up as API design questions inside a bigger problem: "your pop blocks forever; how does a caller poll?", "how do consumers find out the queue was shut down?", "what does get return for a missing key?", "why does std::stack::pop return void?".

I'll make every "maybe" explicit in the type. tryPop returns std::optional<T>, so checking and taking happen in one locked call and there is no empty() for a caller to race on. The blocking pop returns an empty optional once the queue is closed and drained, which gives consumers a clean exit without a poison pill.
The logger takes std::string_view so callers don't pay for a copy they don't need, but it copies into a std::string before the message crosses to the writer thread, because a view doesn't keep the caller's string alive.

Follow ups to expect: "Why not return -1 for empty?" (it collides with real values), "Does optional allocate its payload separately?" (no, though T can allocate), and "Why does std::stack::pop return void?" (separating access from removal avoids a throwing value transfer after removal). Our combined queue operation requires nonthrowing moves and destruction to avoid losing a value on its return path.

Key takeaways

  • std::optional<T> is the return type of "maybe": tryPop, popFor, a pop on a closed queue, a cache lookup.
  • Concurrent APIs merge check and act into one call; empty() followed by pop() is a race even when each call locks.
  • try_emplace plus a structured binding is insert-if-absent with one lookup, and it never steals your argument when the key exists.
  • string_view and span never own or extend lifetimes. Across threads, copy into owning types or prove storage lifetime, stability and access ordering.
  • std::variant is a typed "one of": command queues and future states.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a thread-safe queue with push(T), std::optional<T> tryPop(), a blocking std::optional<T> pop(), and close(). After close(), push returns false, and pop() returns the remaining elements and then an empty optional, without ever blocking forever.
Model answer

The wait predicate includes closed_, so close() with notify_all wakes every blocked consumer. A consumer loop becomes while (auto item = q.pop()) { handle(*item); }, which drains what was queued and then exits. The type constraints cover both moves on the removal path. Close and join all callers before destroying the queue; close() itself does not wait for them. A by-value push argument is constructed before the function can reject a closed queue.

Debug
A metrics pipeline sends events to a worker thread. Under load the worker sometimes prints corrupted names. Find the bug.
Model answer

Event::name is a std::string_view into the caller's string. The temporary ("latency." + endpoint) dies at the end of the full expression containing the call, normally the semicolon. If the worker reads the characters afterwards, it accesses objects whose lifetime has ended: undefined behavior, even if a test appears to work. A synchronized queue safely transfers the view but does not keep the backing string alive.

Fix: make the event own its data, std::string name;, so record copies it before returning. Alternatively retain an immutable shared owner with a clear lifetime contract. Passing a view between threads is valid only when its backing storage remains alive and stable and conflicting accesses are synchronized.

Explain
Explain to an interviewer why a concurrent queue should not offer empty(), front() and pop() the way std::queue does, and what you offer instead.
Model answer

With a concurrent queue, empty() can become stale before the caller acts: another consumer can take the last element before front(). Returning a reference also lets guarded storage escape the lock. I offer one locked check-and-take operation, std::optional<T> tryPop(), plus a blocking pop() and, if needed, a timed operation. Each method documents what absence means; if timeout and closure need different handling, I return an explicit status. A locked size() or empty() can be exact at an instant during its call, but it is a snapshot, not a reservation for a later operation.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Design the return types for a queue that supports polling, timeouts and shutdown. Why would you use optional, and where is it not enough?"
What a strong answer covers
  • Use one locked check-and-take operation; optional alone provides no synchronization
  • Explain the two-consumer race between empty and front
  • Define empty results separately for polling, timeout and closed-and-drained blocking pop
  • Use an explicit status or variant when timeout and closure must be distinguished
  • Require nonthrowing moves and destruction for the illustrated value-returning pop
  • Close under the mutex, wake all consumers, and join users before destruction
How a senior would say it
I would return an optional from a single check-and-take operation, with the whole decision protected by the queue's mutex. The optional describes the result; it does not supply synchronization. If two consumers separately check that a queue is nonempty, one can remove the last item before the other calls front. Returning a reference also lets guarded storage escape the lock. For polling, an empty optional means no item was available at that operation. For blocking pop, I would keep draining accepted items after close and return empty only when closed and drained. A timed operation needs a documented meaning for absence. If the caller must distinguish timeout from closure, optional has too few states, so I would return a named status result or a variant with distinct alternatives. I would also constrain this implementation's element type to nonthrowing moves and destruction. Otherwise, extraction or return can fail after changing or removing the queued item. Finally, close changes the predicate under the same mutex and wakes every waiting consumer. The owner joins all users before destroying the queue. That gives callers an explicit result and a lifecycle they can reason about, while unexpected allocation or system failures can still propagate separately.

Likely follow up: What would you change if the payload has a move constructor that can throw?

Out loudabout 75 s
"Our asynchronous logger sometimes prints corrupted request names. It queues string_view values. What would you check, and how would you fix it?"
What a strong answer covers
  • A string_view borrows characters and does not extend their lifetime
  • A temporary concatenated string dies at the end of the caller's full expression
  • Queue synchronization does not preserve the backing storage
  • Copy into string before returning, or retain an immutable owner with a lifetime contract
  • Check storage invalidation and conflicting writes independently of lifetime
  • Views are safe for joined readers over stable immutable data; data is not necessarily null-terminated
How a senior would say it
I would first check whether the logger owns the characters it queues. A string view only borrows a pointer and length. If a caller passes a concatenated temporary string, that string dies at the end of the statement. A background writer reading later has a dangling view, even when the queue itself is perfectly synchronized. My default fix is to keep the view parameter for convenient synchronous access, then copy it into an owning string before log returns. For larger immutable buffers, retaining a shared owner can avoid copying, but the message must carry that ownership contract through consumption. I would check mutation separately. Keeping an object alive does not prevent reallocation from invalidating the view, or another thread writing characters while the worker reads them. Views can safely cross threads when storage stays stable and accesses are ordered, as with read-only spans whose owner joins all readers before destruction. Finally, a string view need not end with a null character, so the output path must respect its length rather than treat data as an arbitrary C string.

Likely follow up: Would copying a tuple containing string_view fields under a mutex give the worker an independent snapshot?

Out loudabout 60 s
"A worker accepts append, flush and stop commands. Would you use any or variant, and what could go wrong during dispatch?"
What a strong answer covers
  • Choose variant for the closed set of command types, with owning payloads
  • Visit requires a valid handler for every alternative and consistent deduced return types
  • Type-based access requires a unique type; get throws on the wrong active alternative
  • Distinguish an intentional monostate from valueless_by_exception after a throwing type change
  • Variant supplies neither queue synchronization nor a shutdown policy
How a senior would say it
I would use a variant because the supported command types form a known, closed set. Append would own its string, while flush and stop could be small marker types. Any would defer type checking to casts and would not express which commands the worker accepts. I would dispatch with visit and make every alternative compile. With the deduced-return overload, every branch must return the same type and value category. If I inspect manually, get throws for the wrong active alternative, whereas get-if returns null. Type-based access also requires that type to appear exactly once. A variant normally holds one alternative, but a throwing type change can leave it valueless, making visit throw. An intentional monostate is a separate, ordinary alternative. Finally, variant only represents the message: I still need a synchronized queue and a contract for whether stop drains or discards pending work.

Likely follow up: How would you ensure adding a fourth command fails compilation until its behavior is implemented?
