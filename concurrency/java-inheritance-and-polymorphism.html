Inheritance, overriding and polymorphism

Predict constructor order and method selection, enforce override contracts, resolve interface defaults, and avoid dispatch into half-built objects.

Before this:Classes, interfaces and inheritancefinal, immutability and recordsExceptions, InterruptedException and try-with-resources

A variable can say Runnable while the object supplies a completely different implementation. To review a worker or defend an LLD design, you must know exactly which method runs, what the compiler promises callers, and whether the object is ready when that method starts.

In plain words

A delivery desk accepts a parcel through a standard booking form. The form determines what you can request; the courier who receives it determines how the delivery happens. Changing the label on the form does not turn one courier into another.

Now imagine asking the courier to deliver while their van is still being assembled. The request reaches the right person, but the equipment is not ready. Java can make exactly that mistake while constructing an object.

Why this matters for concurrency

Workers invoke tasks through interfaces, so the concrete override decides what code executes. Constructor callbacks can reach subclass state before initialization, and an override can change the locking behaviour of a method even when its signature is legal.

Classes and interfaces already establishes private state, locks, and task interfaces. Here you sharpen the language rules behind those designs. Keep composition and SOLID and LLD design patterns for choosing the architecture.

extends creates one object, with a constructor chain

class ExportTask extends Task makes ExportTask a subtype of Task. Every class except Object has one direct superclass, ultimately reaching Object, and may implement several interfaces. A superclass reference to a subclass object is still a reference to that same complete object, not a copied parent portion.

Constructors are neither inherited nor overridden. In Java 21, an explicit super(...) or this(...) must be the first statement of a constructor. super(...) selects a constructor of the direct superclass; this(...) delegates to another constructor in the same class. That delegation must eventually reach a superclass constructor, without a cycle.

If neither is written, the compiler inserts super(), except in Object. Compilation fails if that no-argument superclass constructor is unavailable or inaccessible. The compiler supplies a default constructor only when you declare no constructors at all.

Allocation first gives all instance fields their default values. For each class, its instance field initializers and initializer blocks run in source order after its direct superclass constructor returns, followed by the rest of its constructor body. Delegating with this(...) does not run those initializers twice. Static initialization is a separate mechanism covered in class initialization.

Two decisions: choose the signature, then choose the body

Overloading gives one name different parameter lists. The compiler chooses an applicable signature using the receiver's declared type and the argument expressions' compile-time types. Runtime argument classes do not trigger another overload search.

Overriding supplies a subclass implementation of an inherited instance method. For an ordinary overridable instance call, dynamic dispatch then selects the implementation using the receiver object's runtime class. This is subtype polymorphism: one interface or superclass reference can invoke different implementations.

A cast does not force a parent implementation. Nor does an ordinary call made inside a parent method: its receiver is still this, so an overridden helper can run. For a deliberate parent call inside a subclass, use super.method().

Overloads cannot differ only in return type, access, or throws. Adding accept(String) does not override accept(Object), even though String extends Object. concrete.accept(null) chooses String over Object, while view.accept(null) still selects Object; unrelated String and Integer overloads would be ambiguous for null. Primitive widening, boxing and casts are drilled in types and Java pitfalls.

The override contract the compiler checks

Use @Override on every intended override, including interface implementations. It asks the compiler to check your intention; it does not enable dispatch. A misspelt name or changed parameter type then becomes an error instead of a silently unused overload.

Through view, the expression still has type Number and the caller must handle or declare IOException. The compiler does not rewrite that contract because today's object is a CachedLoader. Runnable.run() declares no checked exceptions, so its implementation cannot add throws InterruptedException; use the handling rules from exceptions and interruption.

A private parent method is not inherited and cannot be overridden. A package-private method is not inherited by a direct subclass in another package, so a matching declaration in that direct subclass does not override it. There is a transitive exception: an intermediate subclass in the original package can override it with public or protected access, and a later subclass in another package can override that accessible method. Follow the inheritance chain, not just the packages of its endpoints.

Generic substitution matters: implementing Consumer<String> with accept(String) overrides Consumer<T>.accept(T) after substituting String for T. The compiler may generate a synthetic bridge method, an adapter that preserves dispatch after type erasure; it is not an extra source-level overload you should write. See generics and erasure for the underlying type rules.

An override does not inherit synchronization

synchronized belongs to the executed method body. Calling an unsynchronized override through a superclass reference does not acquire the lock promised by the superclass implementation. This single-thread probe uses Thread.holdsLock(this) to check whether the calling thread owns this object's monitor.

super.execute() acquires the monitor on the same object, then releases that acquisition on return. Here the caller held no lock beforehand, so the surrounding override code is unprotected. If all three steps must be atomic, synchronize the override on the same monitor; the nested parent call is reentrant. A final synchronized entry method can preserve this boundary, but any overridable hooks inside it still need a locking contract.

Static methods hide; fields and private methods do not dispatch

A subclass static method with the matching signature hides the inherited static method. Selection uses the compile-time type or the named class, not the receiver's runtime class. Write Base.kind() or Child.kind() in real code; calling static methods through variables obscures this rule.

The two name fields are separate storage locations in one object. reveal() calls the private Base.secret(), not the independent method in Child. super.route() deliberately invokes the parent implementation on the same object; any ordinary overridable calls inside that parent implementation can still dispatch to the child.

@Override on a hiding static method is an error. Switching an inherited instance method to static, or a static method to instance, is also illegal for a matching signature. Interface static methods are not inherited: call them through the declaring interface.

final closes a specific extension point

A final class cannot be extended. A final instance method cannot be overridden, but can still be overloaded with a different parameter list. A final static method cannot be hidden. An abstract method cannot be final: it requires an implementation while final forbids replacing it.

Final does not make the whole call tree fixed. execute() is fixed, but work() is still an extension point. If you hold a lock while invoking such a hook, subclass code runs under that lock and may block or acquire another lock. Follow the locking rules and the monitor object pattern for that proof.

A final class can still have mutable, racy state. A final method supplies no memory visibility guarantee. Keep those uses separate from final fields and immutability; restricted hierarchies using sealed belong to modern Java.

Default methods and the diamond rule

A default method is an instance method with an implementation in an interface. When several paths offer the same signature, do not guess from the order of the implements list. Apply these rules:

  1. Class implementation wins. A compatible public concrete method declared in the class or inherited from its superclass takes precedence over an interface default.
  2. More specific interface wins. A subinterface's override takes precedence over its ancestor's default.
  3. Unrelated defaults require a decision. The implementing class must override the method explicitly. It may choose one default, combine them, or provide its own behaviour.

The last case is a harmless diamond: both paths inherit the same declaration from Named. Two unrelated implementations are different. Fast.super.label() explicitly chooses an inherited default through a direct superinterface; you cannot jump around a more specific override by naming a distant ancestor.

An inherited abstract superclass declaration is not satisfied automatically by an interface default; a concrete subclass must implement it. A subinterface can also redeclare an ancestor's default as abstract, requiring a later implementation. An unrelated interface's abstract declaration does not silently accept another interface's default either: resolve that conflict explicitly.

A default cannot override a public Object method such as equals, hashCode or toString. Interfaces may still declare those signatures abstractly.

These rules choose a body, not a synchronization policy. The earlier default-method atomicity example shows why several safe calls inside a default are not one atomic operation. The practical consequences return in check then act and concurrent maps.

Worked example: the constructor reaches a half-built subclass

A parent constructor calls describe() to log the new service. Predict the first line before running this. There are no threads, races, or scheduling assumptions in the demonstration.

  1. Allocation sets name to null and retries to 0.
  2. The implicit super() enters Service(), which calls describe().
  3. Dynamic dispatch selects NamedService.describe() immediately.
  4. Only after Service() returns does retries = 3 run, then the subclass constructor assigns name.

The final field does not rescue this early read. Calling name.length() instead would throw NullPointerException during construction. Marking the override final also changes nothing: it already is the selected subclass implementation.

This is related to this escape, but the distinction matters: the example needs no publication to another thread. It gives subclass code access to an incomplete object. That override could then register this or start a worker, causing actual escape. Neither a lock nor volatile can make a future initializer execute earlier.

Construction finishes before start(), whose happens-before guarantee makes the earlier writes visible to the worker. join() waits for its completion. The lifecycle details live in the thread toolkit and creating and joining threads; publication through other mechanisms is covered in safe publication and happens-before.

A constructor may use private, static or final helpers when they only depend on state already initialized and do not leak the object. Making just the first helper final is insufficient if it calls another overridable method. Trace the whole call path.

Common mistakes

  • Choosing overloads from runtime arguments. Choose from compile-time types first, then dispatch the selected instance signature.
  • Narrowing a parameter to override. That creates an overload; use @Override to catch the mistake.
  • Casting to force the parent body. A cast changes the reference view. A subclass uses super.method() for an explicit parent call.
  • Assuming narrower throws changes every caller. Calls through the parent type still obey the parent's checked exception contract.
  • Assuming an override inherits locking. Preserve the synchronization contract explicitly; calling a synchronized parent method protects only that call unless the caller already holds the monitor.
  • Treating static methods or fields as polymorphic. Both use compile-time selection; prefer class-qualified static calls and avoid hidden fields.
  • Resolving a default conflict by reordering interfaces. Write an explicit override.
  • Logging through an override during construction. Even toString() can dispatch into subclass fields; defer it until construction finishes.

In the interview

For an output puzzle, annotate the receiver type, argument types, selected signature, and runtime body in that order. For a constructor puzzle, write down defaults before following the constructor chain. For an LLD review, separate a legal override from one that preserves behaviour and locking.

I resolve overloads at compile time, then dispatch the selected instance method on the runtime receiver. Static methods hide, fields do not dispatch, and a cast does not change the object's class.
I avoid overridable calls during construction because Java can enter subclass code before its fields are initialized. I finish construction first, then publish or start the task through an explicit lifecycle step.

Expect follow ups on covariant returns, narrowed checked exceptions, super calls that invoke another override, and an abstract superclass competing with a default. Review override and hiding restrictions in JLS 8.4.8, interface conflicts in JLS 9.4.1, constructor dispatch in JLS 12.5, and call selection in JLS 15.12.

Key takeaways

  • All instance fields begin with defaults; superclass construction precedes subclass initializers and constructor bodies.
  • Overloads use compile-time types. Overridden instance bodies use the runtime receiver.
  • An override preserves parameters, cannot reduce access or widen checked exceptions, and may narrow a reference return type.
  • Static methods hide, fields do not dispatch, and final closes only the extension point it marks.
  • Class implementations and more specific interfaces take precedence; unrelated defaults need an explicit override.
  • Never depend on subclass initialization from a superclass constructor callback.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Parent declares only Parent(int n). Child extends Parent declares no constructors. What happens when compiling new Child()?
Why. The default child constructor invokes the parent's no-argument constructor. Java does not invent a default argument for Parent(int). Declare a child constructor that calls super(n).
Using Sink and TaggedSink above, Sink s = new TaggedSink(); Object x = "a"; is followed by s.accept(x). Which body runs?
Why. The selected signature is accept(Object) from the declared types, then the receiver selects its override. The runtime class of the argument does not cause overload resolution to run again.
A parent declares protected Number read() throws java.io.IOException. Which declarations can independently override it? Assume each has a valid body and select all that apply.Select all that apply
Why. A reference return can narrow, access can widen, and checked exceptions can narrow or disappear. Private access reduces visibility, Exception broadens the checked contract, and primitive int is not a covariant reference return.
Base and Child extends Base each declare static kind() and instance field name. Child also overrides route(). For Base b = new Child(), which selection is correct?
Why. Only the overridden instance method dispatches on the runtime object. Static hiding and field selection use the compile-time view. Write the static call as Base.kind() to make this visible.
Two unrelated interfaces each declare default String label(). A class implements both and has no superclass implementation or explicit override. What happens?
Why. Neither default is more specific. Java requires an explicit decision; textual order and class loading do not resolve it. Two paths to the same inherited declaration would be a different, harmless diamond.
A parent constructor invokes value(). The subclass overrides it to return its field int size = 8. The override is final. What does the parent see?
Why. Dispatch is active during Java construction. The override reads the default field value before the initializer runs. Final prevents another subclass from replacing the override; it does not change construction order.
A superclass has public final String execute() which calls protected abstract work(). A subclass implements work(). Which claim is correct?
Why. Final closes one override point, not all calls reachable from it. The hook still runs subclass code, with whatever locks the caller holds. Final itself provides no synchronization.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
CachedLoader.load() returns Integer and declares FileNotFoundException. Why can a caller using Loader still not assign view.load() directly to an Integer, or handle only FileNotFoundException?
Model answer

The call is checked against Loader.load(), whose declared result is Number and whose checked exception is IOException. Dispatch chooses the body, not a new compile-time contract for the caller. A future Loader implementation could return a different Number or throw another IOException. Use the concrete type only when the caller actually requires that stronger contract; otherwise keep the parent result type and handle or propagate its declared exception.

Write code
An abstract superclass Base declares public abstract String label(). Interface Named offers a default returning "named". Write a concrete Service extends Base implements Named that deliberately uses that default. Explain why omitting the override fails.
Model answer

It prints named. The inherited abstract class method prevents the default from automatically satisfying the obligation. A concrete class must implement it, with public access; that body may explicitly delegate through its direct superinterface.

Debug
A parent constructor calls final announce(), and announce() invokes overridable description(). An override reads a subclass final field and registers this in a listener registry. A teammate proposes making announce() synchronized. Diagnose both risks and repair the lifecycle.
Model answer

Final fixes announce() but leaves its call to description() polymorphic. The override runs before subclass initialization, so the final field may still have its default value. Registration additionally publishes an incomplete object, potentially letting another thread call it before construction finishes. A synchronized method cannot force later constructor assignments to have already happened.

Remove that call path from the constructor. Construct fully, then invoke the description or register from a factory or explicit lifecycle method. Registration must itself use a safe publication mechanism when readers are on other threads. Keep construction helpers non-overridable and limited to initialized state; inspect their callees too.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"A worker holds a superclass reference, but the object is a subclass. Walk me through how Java decides which method runs when there are overloads too."
What a strong answer covers
  • Choose the signature at compile time using the receiver and argument types
  • Dispatch the selected overridable instance signature using the runtime receiver
  • Give an Object-typed argument holding a String as an example
  • Distinguish static hiding and field selection from instance dispatch
  • Explain that a cast changes the view while super explicitly chooses a parent body
How a senior would say it
Java makes two decisions. First the compiler chooses a signature from the receiver's declared type and the argument types. Then, for an overridable instance method, the runtime object chooses the implementation of that signature. Suppose the parent exposes accept taking Object, and the child overrides it while also overloading accept for String. Through a parent reference, passing a string still selects accept taking Object, and the child implementation of that signature runs. An Object variable holding a string also remains Object for overload selection. Static methods and fields are different: they use the compile-time view, so I qualify static calls with the class name. Casting the receiver to its parent does not turn off instance dispatch. Inside a subclass, an explicit super call selects the parent body. I trace those decisions separately before discussing what the worker does.

Likely follow up: What if that parent body itself calls an overridden helper?

Out loudabout 75 s
"Our service sometimes fails during construction. The parent logs a description by calling an overridden method. Why is that dangerous, and would final or synchronized fix it?"
What a strong answer covers
  • Identify dispatch into an incompletely initialized subclass as the immediate defect
  • Trace allocation defaults, superclass constructor, subclass initializers, and subclass constructor body
  • Explain why final fields and a final override do not repair an early read
  • Separate the single-thread construction bug from possible this escape to another thread
  • Move callbacks and publication after construction and choose a valid publication mechanism
How a senior would say it
The immediate problem is calling subclass code before the subclass is initialized. Java still dispatches to the override while the parent constructor is running. Allocation has given every field its default value, so a subclass name may still be null. The subclass field initializers run only after the parent constructor returns, followed by the subclass constructor body. A final field does not make a future assignment happen early, and making the override final only prevents further overriding. Synchronization does not repair that ordering either. This can fail with just one thread, for example when the override dereferences the name. It becomes a publication problem as well if the override registers this or starts a worker. I would remove the callback from construction, finish creating the object, and then log or register it through a factory or explicit lifecycle method. For another thread, I also need safe publication, such as starting it after construction. Private or final construction helpers are acceptable only when their entire call path avoids uninitialized state and escape.

Likely follow up: If a final constructor helper calls another overridable method, have you fixed the problem?

Out loudabout 60 s
"A subclass adds bookkeeping before and after calling a synchronized parent method. The override has no synchronized modifier. Is the whole operation protected, and how would you fix it?"
What a strong answer covers
  • Synchronization is not inherited by the overriding method
  • The explicit parent call locks the same receiver only for its execution
  • Without an enclosing lock, the before and after steps can interleave with other calls
  • Synchronizing the override on the same monitor protects the whole sequence and allows reentrant parent calls
  • A final synchronized entry method preserves the boundary but hooks still need a locking contract
How a senior would say it
No. A legal override can drop synchronization. If the caller holds no lock, the bookkeeping starts unprotected. The call to the parent acquires this object's monitor, and returning from that call releases it, leaving the final bookkeeping unprotected too. If those three steps form one invariant, I would synchronize the override on the same object and ensure every other access to that state uses that monitor. Java monitors are reentrant, so calling the synchronized parent while already holding the monitor is allowed. Alternatively, a final synchronized entry method can preserve the boundary for subclasses. I would still review any hooks it calls, because subclass code runs while that lock is held and could block or acquire another lock.

Likely follow up: If the override locks a separate private lock, which accesses to the parent state still need review?
