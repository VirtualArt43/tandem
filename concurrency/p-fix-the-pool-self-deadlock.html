Fix the pool self-deadlock

Bug huntshard35 min

A deadlock with no lock in sight. It tests whether you see a thread pool as a finite resource, and whether you know that a task which waits for other tasks in the same bounded pool can wait forever.

The incident

The reports service builds reports in the background. buildReport(id) puts one task on the service's fixed thread pool. That task fans out four section renders onto the same pool, so that the sections render in parallel, then waits for all four and joins them with |. Each render reads from storage, and the storage team allows no more than threads concurrent readers from this service.

What the on-call engineer wrote down:

  • A single report on a quiet service always works, in every test.
  • During the Monday morning burst the service stops. No report completes, CPU usage drops to zero, and the queue keeps growing. Every pool thread in the thread dump has the same stack: waiting inside assemble.
  • The JVM's deadlock detector reports nothing. There is no lock cycle in the dump.
  • Last month someone doubled the pool size. It froze again, at a bigger burst.
  • A restart clears it until the next burst. Shutdown during the freeze hangs too.

Your job: find the bug and fix it with the smallest correct change. Keep the public API exactly as it is, keep the sections rendering in parallel, and keep the storage limit: never more than threads section renders at once.

In C++ the starter also contains the team's FixedThreadPool. It is used all over the codebase and it is correct as written; the bug is in how ReportService uses it.

What the tests check

  • One report on a pool of 4 threads has the right content.
  • A burst of 8 reports on a pool of 2 threads finishes within 1 s. At the peak exactly 2 sections render at once: never more than the pool size, and not one at a time.
  • 3 reports on a pool of 1 thread finish, with never more than 1 render at once.
  • A section that throws fails its own report, with the storage error as the cause, and does not affect another report.
  • Java: close() returns after every requested report has finished, and leaves no pool thread alive. C++: destroying a service of one thread with three reports still queued finishes all three before the destructor returns.
  • Every wait is timed, so a frozen service shows up as a failed test, never as a hung run. In C++, ThreadSanitizer must stay quiet.

Taught in: Bounded queues, rejection and the ways pools fail

Open them one at a time. Each one gives away a little more.

Picture the thread dump from the incident. Every pool thread is inside assemble, waiting. What exactly is each one waiting for, and where is that work at that moment?
Count threads. With a pool of N threads and N report tasks running, how many threads are left to run sections? A task that blocks on other tasks in the same bounded pool needs a free thread that may never come, and a bigger pool only moves the cliff.
Either the tasks that wait and the tasks they wait for must not share threads, or nothing may block a pool thread while it waits. Whichever you choose, keep the storage limit, and think about the order in which things must stop in close() (or in the destructor).

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why not make the pool bigger, or use an unbounded (cached) pool?
A bigger fixed pool only moves the cliff: N concurrent reports still freeze a pool of N threads. An unbounded pool cannot freeze this way, but it creates a thread per waiting task under a burst, breaks the storage limit of threads concurrent readers, and turns a traffic spike into thousands of threads and an overloaded storage tier. The bound is the point; the fix is to stop the bound from being consumed by waiters.
How would you write it in Java so that no thread blocks at all?
Compose instead of waiting: CompletableFuture.supplyAsync(() -> render(id, s), pool) for each section, then CompletableFuture.allOf(parts).thenApply(v -> join the results). No thread waits; whichever section finishes last runs the join. One pool is then enough, the storage limit holds, and a failure surfaces as a CompletionException with the storage error as its cause. buildReport can still return it as a Future<String>.
Why does fork/join recursion not deadlock a ForkJoinPool the same way?
When a ForkJoinTask calls join() on a subtask, its thread does not simply block: it runs pending tasks itself, its own or stolen from other workers, until the subtask is done. That is work stealing with helping. It only applies to fork/join tasks; a plain blocking call such as Future.get() or I/O inside a ForkJoinPool can still starve it unless you wrap it in ForkJoinPool.managedBlock.
How do you recognise this in production?
Every worker of one pool is parked in Future.get() (or std::future::get), the pool's queue is non-empty and growing, active threads equal the maximum, completed task counts are flat and CPU is idle. The JVM's deadlock detector stays silent because it finds cycles of lock owners, and a starved pool has no owner. Queue depth and active count on a dashboard catch it early.
Are two pools always enough?
For one level of fan out, yes. If section tasks also fanned out and waited, you would need a pool per level, or no blocking at all. The general rule: a task may block only on work running in a pool that can never be waiting on it, so the "waits for" relation between pools must have no cycle.
What about rendering the sections inline in the report task?
It also fixes the deadlock and keeps the storage limit, because only pool threads render and nothing waits. It gives up parallelism inside one report: a lone report takes four render times instead of one. Under a burst the pool is busy anyway, so throughput is similar; for latency of a single report, two pools or composition are better.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The bug: a thread starvation deadlock

assemble runs on a pool thread and blocks in part.get() until its sections finish. The sections are queued on the same fixed pool. When every pool thread is running an assemble, no thread is left to run any section, so every assemble waits forever. Java Concurrency in Practice calls this a thread starvation deadlock. Nothing holds a lock; the scarce resource is the pool's threads, and each one is held by a task that waits for work queued behind it.

It never shows with one report on a quiet service, because free threads are left to run the sections. That is why it passed every test and failed on the busiest morning of the week. The same freeze explains the hung shutdown: close() waits for tasks that can never finish.

The fix: tasks that wait must not hold the threads they wait for

Give the two kinds of task their own pools. Report tasks wait; section tasks never wait on any pool. The section pool therefore always drains, and every waiting report task is eventually released. Only the section pool renders, so at most threads renders run at once and the storage limit holds. This is a bulkhead: one kind of work cannot starve the other.

The trap inside the fix: stopping order

Shutting the pools down in the wrong order brings the bug back in a new place. In Java, if sectionPool shuts down first, a report task that has not started yet gets a RejectedExecutionException when it submits its sections, and requested reports fail. In C++, if sectionPool_ is declared after reportPool_, it is destroyed first: its workers drain the queue and exit, and a report task that starts later submits its sections to a pool that no longer exists. That is undefined behavior; in practice it shows up as a hang, a crash, or reports failing with a broken promise. The rule is the same in both languages: stop the users of a pool before the pool. The close test (the destroy test in C++, on a pool of one thread so that later reports start while the service is being destroyed) catches both mistakes.

How to say it in the interview

Every pool thread is running a report task that blocks on its sections, and the sections are queued on the same bounded pool, so under a burst no thread is left to run them. That is a thread starvation deadlock: no lock cycle, so the deadlock detector is silent, but the pool's threads are the resource. The rule is that a task may only block on work in a pool that can never be waiting on it. I would split report tasks and section tasks into separate pools, keep the section pool at the storage limit, and shut the report pool down first. In Java I would rather compose with CompletableFuture so that nothing blocks at all.
