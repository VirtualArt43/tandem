Lost wakeups, notify versus notifyAll, Mesa versus Hoare

The two hangs where every thread waits and no lock is stuck: a notification that came too early, and one that woke the wrong thread.

Asked atRubrikLinkedIn
Before this:Condition variables and monitorsSpurious and stolen wakeups: always wait in a loop

Some concurrency bugs crash; these just stop. Every thread sits in wait, no lock is held in a cycle, the deadlock detector finds nothing, and the program never moves again. Both causes come down to one fact: a notification is not stored anywhere.

In plain words

A courier rings your doorbell while you are in the shower, waits a moment, and leaves. When you come out, you sit by the door waiting for the bell, and you will wait all day: the ring already happened. The fix is not to listen harder; it is to check the doorstep before you sit down, and to have the courier leave the parcel on the doorstep, not just ring.

Now a building where the parcel courier and the food delivery share one bell. Ring once, and whoever comes down may be the person expecting food, who sees no food, shrugs and goes back upstairs. The person expecting the parcel never heard a thing. Either ring for everyone, or give each kind of delivery its own bell.

Lost wakeup, cause 1: the state changed outside the lock

A condition variable has no memory. If a thread notifies and nobody is waiting yet, the notification does nothing and is gone. That is harmless when waiters check the state before waiting, under the lock, because then a change that happened earlier is seen as state. It becomes a lost wakeup when the check and the wait are not protected against the change:

The window between "decide to wait" and "wait" is tiny, so this bug may run for weeks before it bites. Here it is with the window widened by a sleep, so it bites every time. The two sides show two common forms: in Java the flag is checked outside the lock; in C++ the check is inside the lock and correct, but the setter changes the flag without taking the mutex. A volatile or atomic flag does not help in either case.

The fix is the rule from condition variables, applied without exception: check the state and wait under the lock, and change the state under the same lock. Then the setter cannot run between the waiter's check and its wait, because the waiter holds the lock across both, and wait releases it only as part of going to sleep. The same 100 ms window is now harmless: the setter simply waits for the lock.

C++

The C++ trap deserves its own sentence, because it looks so reasonable: even if the shared variable is a std::atomic, it must be modified while holding the mutex that the waiter uses, or the modification and the notification can both fall into the gap between the waiter's predicate check and its sleep. The atomic makes the flag itself race free; only the mutex closes the window.

Lost wakeup, cause 2: the signal came before the wait

The other form has no state at all. A thread starts a worker and then waits "for the worker's notification", while the worker, being fast, notifies before the waiter has started waiting. Nothing records that the event happened, so the waiter sleeps forever. The fix is the same principle: never wait for a notification, always wait for a state. Add a done flag, set it under the lock before notifying, and wait in a loop on !done. A late waiter then sees done and does not wait at all.

This is the real difference between a condition variable and a semaphore. A semaphore remembers: a release with nobody waiting becomes a permit that the next acquire takes. A condition variable forgets: a notify with nobody waiting is gone. That is why condition variables always come with state, and why a one-shot event is often simplest as a latch.

notify versus notifyAll

notify (signal, notify_one) wakes one waiting thread, chosen by the system with no ordering promise. notifyAll (signalAll, notify_all) wakes them all; they then take the lock one at a time and each re-checks its own condition. With waits in loops, notifyAll is always correct, and a single notify is safe only when two things are both true:

  1. Uniform waiters: every thread waiting on that condition variable is waiting for the same predicate and will do the same thing when it wakes.
  2. One in, one out: each notification enables at most one waiter to proceed.

Break the first rule and a notification can land on a thread that cannot use it. The classic case is a buffer where producers ("wait while full") and consumers ("wait while empty") share one wait set, which is what a single Java monitor or a single C++ condition variable gives you:

Every individual step is correct, the waits even use while, and the program is still stuck. This is a lost wakeup in its multi-thread form: the notification was delivered, to the wrong kind of thread. It happens within milliseconds:

Look at the thread dump the site shows for the Java version: four threads in WAITING on the same monitor, and no "Java-level deadlock" reported, because no thread is waiting to acquire a lock someone else holds. Recognizing "everyone is in wait, nobody holds anything" as a missed or misdirected notification is a debugging-round skill.

Two fixes, both standard:

  • notifyAll (notify_all). Every waiter wakes and re-checks; the right kind proceeds. Simple and always correct with while loops. The cost is a thundering herd: with many waiters, each change wakes them all, most go straight back to sleep, and the context switches add up.
  • Separate condition variables, one per predicate: producers wait on "not full", consumers on "not empty". Now each condition has uniform waiters and one change frees one waiter, so a single signal or notify_one is both safe and cheap. In Java this needs ReentrantLock and two Condition objects, since an intrinsic monitor has only one wait set. This is the design in the bounded blocking queue solution.

Mesa versus Hoare: why every wait is a loop

The behavior in this module, a woken thread that must win the lock again and re-check, is a design choice with a history. In the monitors Tony Hoare described in his 1974 paper, a signal handed the monitor directly to the woken thread. When Butler Lampson and David Redell built monitors into the Mesa language at Xerox PARC (published 1980), they chose the opposite.

Hoare: signal and waitMesa: signal and continue
After a signalThe woken thread runs at once, holding the monitor; the signaler waits until it leaves the monitor or waits againThe signaler keeps the monitor and carries on; the woken thread competes for it later
Is the condition true when the woken thread runs?GuaranteedNot guaranteed: it may have changed again
How to waitif is enoughAlways a loop
CostExtra context switches on every signal, and a forced hand offCheap: the signaler is already running
Broadcast, timeouts, spurious wakeupsAwkward to fit inNatural: they are just more reasons to re-check
Who uses itTextbooks and some teaching systemsJava, C++, POSIX threads and practically every production library

Mesa semantics turn a notification into a hint: "the state may now be what you want, go and look". That is cheaper and more robust, at the price of the loop. When an interviewer asks "why while?", "because these are Mesa semantics" is the one-line senior answer, followed by the concrete cases the loop covers: stolen wakeups, which Mesa semantics make possible, and spurious wakeups, which the Java, POSIX and C++ specifications explicitly allow.

Notify while holding the lock, or just after?

In Java there is no choice: notify, notifyAll, signal and signalAll all require holding the lock. Since waiters cannot return from wait until the lock is released, it does not even matter whether you notify before or after changing the state, as long as both happen inside the same critical section.

C++ lets you choose, because notify_one and notify_all do not need the mutex. The state change itself must always be made while holding the mutex; only the notify can move.

C++
  • Notifying under the lock is always correct. The woken thread may wake only to block on the mutex the notifier still holds (sometimes called "hurry up and wait"), although some implementations move the waiter straight to the mutex's queue to avoid the extra switch.
  • Notifying after unlocking can save that switch, and is common in performance-sensitive code. It has one trap: between the unlock and the notify, the waiter can wake (spuriously, or for another reason), see the condition already true, return, and destroy the object that owns the condition variable. The notify then touches a destroyed object, which is undefined behavior. If the waiter may destroy the condition variable as soon as it sees the condition, notify while holding the mutex. POSIX also says that holding the mutex is required if you need predictable scheduling.
  • Never change the state outside the mutex, atomic or not, as the first demo showed.

Worked example: the two bugs in a classic broken buffer

A debugging round hands you a bounded buffer with one monitor: put does if (full) wait(); add; notify(); and take does if (empty) wait(); remove; notify();. It works with one producer and one consumer, and fails with more. Name both bugs, with an interleaving for each, before you touch the code:

  1. if instead of while: two consumers wait, one item arrives, both get woken over time (by a notify each, or by a spurious wakeup), and the second removes from an empty buffer. Fix: while. That was the previous lesson.
  2. notify with mixed waiters: producers and consumers share the monitor's single wait set, so a consumer's notify can wake another consumer, and the run in the timeline above leaves all four threads waiting. Fix: notifyAll, or move to ReentrantLock with separate notFull and notEmpty conditions and keep a single signal.

Then say which fix you would ship: separate conditions with signal for a buffer with many waiters, notifyAll when waiters are few and simplicity wins. This pair of bugs is exactly the fix the lost wakeup problem.

Common mistakes

  • Checking the condition outside the lock, then locking and waiting. The change and its notification can fall in between.
  • Changing the state without the waiter's lock, especially an atomic flag in C++. Atomic is not enough; the mutex closes the window.
  • Waiting for a notification instead of a state. A notify that comes first is lost. Always wait in a loop on a predicate.
  • Single notify with mixed waiters. Producers and consumers, or readers and writers, sharing one wait set need notifyAll or separate conditions.
  • notify for a broadcast event. Shutdown, "the gate is open" and "the latch reached zero" concern every waiter; use notifyAll.
  • Notifying after unlocking when the waiter can destroy the condition variable (C++). Notify under the mutex in that case.
  • Expecting the deadlock detector to find it. Lost wakeups leave threads in WAITING, not in a lock cycle. Read the waits, not just the locks.

In the interview

These are the follow ups that separate a working bounded queue from a correct one. Rubrik's debugging round has handed candidates C++ producer-consumer code with a critical section bug to find; LinkedIn has run a bounded blocking queue round that allowed only wait and notify; and "notify or notifyAll?" follows almost every monitor you write on a whiteboard.

A condition variable has no memory, so a notify with nobody waiting is lost. That is harmless as long as waiters check the state under the lock before waiting and the state is only changed under the same lock; then an early change is seen as state. A single notify is only safe when all waiters wait for the same condition and one change lets exactly one of them proceed. With producers and consumers on one monitor, notify can wake the wrong kind and the system stalls with everyone waiting, so I use notifyAll there, or better, separate conditions with signal.
All of this follows from Mesa semantics: notify is a hint, the signaler keeps the lock, and the woken thread must re-acquire it and re-check. Hoare semantics would hand the lock over directly and make if sufficient, but no mainstream library works that way.

Follow ups to expect: "Show an interleaving where notify hangs" (the four-thread timeline), "Is notifyAll always safe?" (with while, yes; it only costs wake-ups), "Why not just make the flag volatile?" (visibility is not the problem; the window is), and in C++, "should notify be inside the lock?"

Senior depth

  • Interrupts do not lose notifications in Java. The language specification guarantees that if a thread in the wait set is notified, either some waiter returns normally or all of them exit with InterruptedException; and Condition.await implementations that favor the interrupt must pass the signal on to another waiter. You can rely on it, but you still must re-check state, since the waiter that consumed the signal may not be the one you expected.
  • Counting notifications is a design smell. If correctness depends on "N notifies wake N threads", it will break under spurious and stolen wakeups. Put the count in the state (permits, items, a generation number) and let every waiter check it.
  • Generation counters fix reusable barriers. When a condition becomes true and then false again quickly (a barrier that resets, a flag toggled back), a slow waiter may wake to find it false and wait again, missing its round. Waiting for "generation changed" instead of "flag is true" makes each round's release permanent for that round's waiters; you will use it in the reusable barrier.
  • The platform closes its own window the same way. wait must release the mutex and join the wait set as one step, and POSIX requires it: a signal sent by a thread that took the mutex after the waiter released it must behave as if the waiter were already asleep. On Linux this rests on the futex contract: the kernel puts a thread to sleep only if a memory word still holds the value the caller expects, checking and sleeping as one step. C++20 std::atomic<T>::wait(old) exposes that contract directly, so a store followed by notify_one cannot be missed by a waiter that saw old (though a value that changes and changes back can be, which is again why generation counters exist). Java's LockSupport.unpark leaves one permit that a later park consumes at once. These primitives remember a little; a bare condition variable remembers nothing, so the state has to do it.
  • Herds versus precision. notifyAll costs O(waiters) wake-ups per change. With dozens of waiters on a hot structure, separate conditions (or one condition per waiting thread, as in a FIFO lock) turn that into O(1). Measure before optimizing; with three waiters it does not matter.

Key takeaways

  • Notifications are not stored. A notify with no waiter is lost, so waiters must check state, under the lock, before waiting, and the state must change under the same lock. In C++ that holds even for atomic variables.
  • Never wait for a notification; wait in a loop for a state. A semaphore remembers releases; a condition variable does not.
  • A single notify is safe only with uniform waiters and one-in, one-out. Otherwise use notifyAll, or separate condition variables with a single signal.
  • Mesa semantics (signal and continue) make notify a hint, which is why every wait is a loop. Hoare semantics would hand off the lock directly.
  • In C++, notify under the mutex is always correct; notifying after unlocking is an optimization that is unsafe if the waiter may destroy the condition variable.

Quick check

Answer each question, then read why. Your score is saved for your module test.

The waiter runs if (!ready) { lock; wait; unlock }. The setter runs ready = true; lock; notifyAll; unlock. What can happen?
Why. The check happens outside the lock, so the setter's change and notification can both land between the check and the wait; the notify finds nobody waiting and is lost. Checking and waiting in a loop under the lock, with the setter changing the flag under the same lock, closes the window.
Nobody is waiting. Thread A calls notify on a condition variable; thread B calls release on a semaphore. Later, thread C waits on the condition variable and thread D acquires the semaphore. What happens?
Why. A condition variable has no memory, which is why it must always be paired with state that the waiter checks. A semaphore's count is its memory. Waiting on a condition variable for a notification that already happened is the lost wakeup.
Producers wait "while full" and consumers wait "while empty" on one Java monitor (or one std::condition_variable), and both use a single notify (notify_one). The waits are in while loops. What can happen with two producers and two consumers on a one-slot buffer?
Why. The loops make each wakeup safe, but a single notify that lands on a thread that cannot proceed is wasted, and the thread that could proceed is never woken. Use notifyAll, or separate conditions so each signal reaches the right kind of waiter. The lock still prevents two writers in the slot.
When is a single notify (signal, notify_one) instead of notifyAll safe?
Why. These are the uniform waiters and one-in, one-out conditions. The while loop protects against wakeups with a false condition, but it cannot create a notification for the thread that was never woken. The number of waiters can change at any moment, so "fewer than two" is not a rule you can rely on.
Under Mesa semantics, which is true when a notified thread returns from wait?
Why. With signal and continue, the signaler keeps running and the woken thread re-acquires the lock later; others may run in between. Guaranteed truth and a waiting signaler describe Hoare semantics, which mainstream libraries do not use. In both models wait returns with the lock held.
Java onlyInside one synchronized (lock) block, a Java setter calls lock.notifyAll() and then sets ready = true. Is the order a bug?
Why. A woken thread must re-acquire the monitor before wait returns, which happens only after the setter exits the synchronized block. Both actions are therefore visible together. Setting the state first reads more naturally, and that is the convention, but inside one critical section the order does not change behavior.
C++ onlystd::atomic<bool> ready is checked by a waiter inside cv.wait(lock, [&] { return ready.load(); }). The setter runs ready = true; cv.notify_one(); without locking the mutex. What is wrong?
Why. Atomicity prevents the data race but not the lost wakeup. The waiter holds the mutex between its check and the moment wait blocks; a setter that takes the same mutex to change the flag cannot fall into that gap. Notifying after unlocking is fine; changing the state without the mutex is not.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A bounded buffer uses one monitor: put does if (count == capacity) wait(); add; notify(); and take does if (count == 0) wait(); remove; notify();. With 3 producers and 3 consumers it sometimes throws and sometimes hangs. Explain both failures with interleavings, and fix it.
Model answer

The exception comes from if. Consumer C1 waits on an empty buffer. A producer adds one item and its notify wakes C1, but C1 must still re-acquire the monitor, and before it does, consumer C3 arrives at take, finds the item and removes it. C1 then returns from wait and, because if does not re-check, removes from an empty buffer and throws. A second route needs no third consumer: C1 takes the item and its own notify wakes C2, another waiting consumer, which also returns from wait without re-checking. A spurious wakeup does the same.

The hang comes from the single notify with mixed waiters: producers waiting on "full" and consumers waiting on "empty" share the monitor's one wait set, so a notify can reach a thread of the wrong kind. It shows most clearly once if has been fixed to while, which is why fixing only the if is not enough. With capacity 1: consumers C1 and C2 find the buffer empty and wait; P1 adds an item and its notify wakes C1; P1 and P2 then find the buffer full and wait; C1 takes the item and its notify wakes C2 instead of a producer; C1 loops, finds the buffer empty and waits; C2 re-checks, finds it empty and waits. Every thread now waits and no notification is coming. With the original if, the same misdirected notify makes C2 remove from an empty buffer instead, which is the exception; and a worker killed by that exception can leave the remaining threads waiting forever, a second route to the hang.

Fix: replace if with while in both methods, and either use notifyAll (simple, correct, wakes everyone) or switch to ReentrantLock with two conditions, notFull for producers and notEmpty for consumers, and signal the right one after each change: put signals notEmpty, take signals notFull. With separate conditions each wait set has uniform waiters and each change frees one waiter, so signal is safe and avoids the thundering herd.

Explain
Explain the difference between Mesa and Hoare monitor semantics, and why every mainstream library chose Mesa.
Model answer

Under Hoare semantics, from Hoare's 1974 monitors paper, a signal immediately transfers the monitor to the woken thread, which runs right away with the condition guaranteed true; the signaler is suspended until the woken thread leaves the monitor or waits again. Waiting can therefore use if. Under Mesa semantics, from Lampson and Redell's work on the Mesa language at Xerox PARC, the signaler keeps the monitor and continues; the woken thread is merely made runnable and must re-acquire the monitor later, by which time other threads may have changed the state. A signal is a hint, and every wait must be a loop.

Libraries chose Mesa because it is cheaper and more robust. A Hoare signal forces an immediate hand off, costing extra context switches on every signal and constraining the scheduler, while under Mesa the already running signaler simply continues. Mesa also accommodates broadcast (notifyAll), timed waits and spurious wakeups naturally, since each is just another reason to re-check, and it tolerates extra notifications from anywhere in the program. Java, POSIX threads and C++ all have Mesa semantics, which is the root reason for while around every wait.

Write code
Write a one-shot Completion with complete() and await(), where the waiting thread may destroy the Completion object as soon as await() returns. In C++, where must the notify go, and why? What is different in Java?
Model answer

In C++ the notify must happen while holding the mutex. If complete() set done_, unlocked, and only then notified, the waiter could wake in between (spuriously, or because it was just arriving), see done_ true, return, and destroy the Completion, so the notify would run on a destroyed condition variable: undefined behavior. Under the mutex, the waiter cannot get past its wait until the notifier has released the mutex, which happens after the notify. In Java the question does not arise in the same way: you must hold the monitor to notify, and the garbage collector does not free the object while complete() still references it. In both languages the waiter waits for the done state in a loop, so a complete() that happens before await() is never missed.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Walk me through how a thread can sleep forever on a condition variable when the flag it is waiting for is already true. Would making the flag atomic fix it?"
What a strong answer covers
  • A condition variable has no memory: a notify with no thread waiting is simply lost
  • The interleaving: the waiter checks the flag and sees false, the setter sets it and notifies, and only then does the waiter go to sleep
  • An atomic or volatile flag fixes visibility, not the gap between the check and the sleep
  • The fix: check the flag in a loop and wait under the mutex, and change the flag under the same mutex
  • Why that works: wait releases the mutex and starts sleeping as one step, so the setter cannot land in the gap
  • In C++ the notify call may move after the unlock, but the store to the flag may not
How a senior would say it
Because a condition variable has no memory. A notify with nobody waiting is simply dropped. Picture the waiter checking ready and seeing false. Before it actually calls wait, the setter sets ready to true and notifies. Nobody is asleep yet, so that notify does nothing. Then the waiter goes to sleep, waiting for a change that has already happened, and nothing will ever wake it. Making the flag atomic does not help. That fixes visibility, but the bug is the gap between the check and the sleep, and the setter can still land in it. The fix is one rule. The waiter checks the flag in a loop while holding the mutex, and the setter changes the flag while holding the same mutex. Now the setter cannot run in the gap, because wait releases the mutex and goes to sleep as one step. And if the setter got there first, the waiter just sees true and never waits. In C++ the notify call itself can sit after the unlock, but the store must be under the mutex, even for a std::atomic.

Likely follow up: Is it safe in C++ to call notify_one after releasing the mutex?

Out loudabout 90 s
"Here is a symptom: a service stops making progress. The thread dump shows every worker in WAITING, the CPU is idle, and the deadlock detector reports nothing. What do you suspect, and how do you track it down?"
What a strong answer covers
  • No lock cycle: the threads are waiting on a condition, not blocked acquiring a lock, so suspect a missed or misdirected notification
  • Check every wait: the condition is checked in a loop, under the lock, before waiting
  • Check every state change: it is made under the same lock the waiters use, atomic or not
  • Check every single notify: do different kinds of waiters, such as producers and consumers, share one condition
  • The fix: wait for state, never for a notification, and use notifyAll or one condition per predicate
  • Confirm it with a stress test that joins with a timeout, and a dump showing which condition each thread waits on
How a senior would say it
I would suspect a missed or misdirected notification, not a deadlock. A deadlock detector looks for threads blocked acquiring locks in a cycle. Here nobody is acquiring anything. Every thread is sitting in wait, so the bug is in the signaling, not the locking. I would go through three checks. First, every wait. Is the condition checked in a while loop, under the lock, before waiting? A check outside the lock lets the notify arrive early and be lost. Second, every state change. Is it made under the same lock the waiters use? In C++ that applies even to an atomic flag. Third, every single notify. Do different kinds of waiters share one condition? The classic case is producers and consumers on one monitor. A consumer's notify wakes another consumer, which re-checks and waits again, and soon everyone is waiting with nobody left to notify. The fix is to wait for state, never for a notification, and to use notifyAll or one condition per predicate. To confirm it, I would reproduce it under a stress test with join timeouts and read which condition each thread is waiting on.

Likely follow up: Why did it run fine for weeks before it hung?

Out loudabout 75 s
"notify or notifyAll: which do you reach for, and when is a single notify actually safe?"
What a strong answer covers
  • notifyAll is always correct when every wait is a loop; its cost is extra wakeups
  • A single notify needs uniform waiters: one predicate, and the same action on waking
  • It also needs one in, one out: each change lets at most one waiter proceed
  • Producers and consumers on one monitor break the first rule, and a single notify can stall everyone
  • Best of both: one condition per predicate, so a single signal is safe and cheap
  • Events that concern every waiter, such as shutdown, always get notifyAll
How a senior would say it
My default is notifyAll, because with waits in loops it is always correct. Its only cost is waking threads that go straight back to sleep. A single notify is safe only when two things hold. Every waiter on that condition waits for the same thing and does the same thing when it wakes. And each change lets at most one of them proceed. Producers and consumers sharing one monitor break the first rule. A consumer's notify can land on another consumer, which re-checks and sleeps again, and the producer that could have moved never hears it. So when I want the cheap single wakeup, I split the waiting into two conditions, not full for producers and not empty for consumers. Each condition then has one kind of waiter, and signal is safe and cheap. That is how ArrayBlockingQueue is built. The one exception is an event that concerns everyone, like shutdown, which always gets signalAll.
