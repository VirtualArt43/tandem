Concurrency versus parallelism

Concurrency is many tasks in progress at once; parallelism is many running at the same instant. The difference decides both speed and bugs.

Asked atGoogleApple
Before this:Processes and threads: the memory picture

People use the two words as if they meant the same thing; interviewers do not. Concurrency is about how a program is structured, parallelism is about how it executes, and mixing them up leads to threads that speed nothing up and to races "that cannot happen on one core".

In plain words

One cook is making dal, rice and sabzi on a three burner stove. The cook puts the dal on to boil, washes the rice while it boils, stirs the dal, chops vegetables while the rice cooks. All three dishes are in progress at once, with one pair of hands: that is concurrency. Now imagine three cooks, each making one dish at the same moment: that is parallelism.

Notice what each one buys you. A single cook gains a lot by not standing idle while the dal boils, because waiting can overlap with other work. But if every dish needs fifteen minutes of chopping, one cook cannot chop faster by juggling; you need more cooks and more knives.

Two definitions

Concurrency means several tasks are in progress during overlapping periods of time. They may take turns on one core, switching back and forth, or they may run at the same time on several cores. Concurrency is a property of the program's structure: it has several independent lines of work.

Parallelism means several computations are executing at the same instant, on different hardware: different cores, or different vector lanes inside one core. Parallelism is a property of the execution, and it needs real hardware underneath.

Rob Pike put it neatly in his 2012 talk "Concurrency is not Parallelism": concurrency is about dealing with many things at once, parallelism is about doing many things at once. Concurrency is the shape of the problem; parallelism is one way of running it.

One coreMany cores
One taskSequentialSequential: the other cores sit idle
Many tasksConcurrent, not parallel: the tasks take turnsConcurrent and parallel: tasks really run at the same time

Taking turns on one core

With two threads and one core, the operating system's scheduler runs one thread for a short time slice, then stops it and runs the other. Both threads are in progress the whole time; only one is executing at any instant.

Give the same program two cores and the two threads can run at the same time, one per core. Nothing in the code changed. Whether it runs in parallel is decided by the hardware and the scheduler, not by the program. That is why you design for concurrency, and you get parallelism when the machine allows it.

See both in code

The first half of this program uses one thread to handle four tasks that each wait a different time, the way an event loop does: sleep until the earliest deadline, finish that task, move to the next. The second half runs four pure computations, first on one thread, then on four threads at once.

Read the two halves side by side. In the first, one thread finished 360 ms of waiting in about 120 ms, with no parallelism at all, because the waits overlapped. In the second, one thread needed about four times as long as four threads, because computing cannot overlap with other computing on one core; only more cores help. Your exact numbers will differ, but the shape will not. This is the single most useful fact in this module: concurrency alone speeds up waiting; only parallelism speeds up computing. The next lesson turns it into a design rule.

One nuance keeps that rule honest. On one core, time slicing can still make computing feel faster to people: a short task gets its turn instead of waiting behind a long one, which is how a UI stays responsive while a big calculation runs. What does not shrink is the total work, or the time to finish all of it.

Concurrency without parallelism, and the reverse

SituationConcurrent?Parallel?
Node.js serving 10,000 connections on its one JavaScript threadYes: thousands of requests in progressNo, for the JavaScript itself
Redis executing commands on its single command threadYes: many clients served in turnNo: one command runs at a time
CPython threads running Python code under the global interpreter lockYesNo: one thread runs Python bytecode at a time
A Java or C++ server with 16 busy threads on 16 coresYesYes
One thread adding two arrays with SIMD instructions, 8 numbers per instructionNo: one line of workYes: data parallelism inside one core

The last row surprises people: parallelism does not even need threads. Vector (SIMD) instructions, and the CPU's own instruction level parallelism (pipelining, and issuing several independent instructions in the same cycle), run work in parallel within a single instruction stream. A GPU takes the vector idea to thousands of lanes. In interviews, when someone says "parallel" they usually mean threads on several cores, but naming SIMD as parallelism without concurrency is a crisp senior detail.

How much faster can parallel get? Amdahl's law

Parallelism only speeds up the part of the work that can be split. If a fraction p of the running time can be spread over n cores and the rest is serial, the best speedup is 1 / ((1 - p) + p / n). This is Amdahl's law. The serial part sets a hard ceiling: with p = 0.95, no number of cores gets you past 20 times faster.

The dot marks 16 cores: a job that is 95 percent parallel runs only about 9 times faster on 16 cores, not 16. The serial part is not just "code that runs before the threads start". Every critical section protected by one lock is serial, because only one thread can be inside it. A program that spends 10 percent of its time inside one global lock can never run more than 10 times faster, whatever the hardware. You will meet this again in lock granularity and performance and contention.

Races do not need parallelism

A common belief is that race conditions need two cores, "so on a single core machine they cannot happen". They can. The scheduler can stop a thread between any two instructions, including between the read and the write of count += 1:

Preemption alone is enough to interleave two threads at the worst possible moment. What a single core does remove is the hardware reordering that another core could observe, such as a write still sitting in one core's store buffer, because both threads run on a core that always sees its own writes in order. The compiler can still reorder code and keep values in registers, and in C++ a data race is undefined behavior however many cores you have. Correctness never depends on how many cores you have; code that is only correct on one core is broken.

Worked example: will threads make this faster?

Resize 10,000 photos on an 8 core machine. Pure computation, every photo independent. Parallelism helps almost linearly: with 8 threads, close to 8 times faster. More than 8 threads adds nothing, because there are only 8 cores to run them.

A request handler calls three downstream services one after another, 100 ms each. The handler spends 300 ms waiting and almost nothing computing, so more cores change nothing. If the three calls do not depend on each other, issuing them concurrently brings the request to about 100 ms, the slowest call instead of the sum, even on a single core, because the waits overlap. This is concurrency, not parallelism. If call two needs call one's answer, the chain cannot overlap at all; only a cache or a combined API shortens it.

Sixteen threads all update one map under one lock, and the update is most of the work. The critical section is serial, so p is close to zero. Sixteen threads run about as fast as one, and often slower, because they now also fight over the lock. The fix is to split the lock or the data (lesson 04-06), not to add threads.

Common mistakes

  • Using "concurrent" and "parallel" as synonyms. Say which one you mean. "These requests are handled concurrently" and "this batch is processed in parallel on 8 cores" are different claims.
  • "More threads always means faster." Only if the work can be split, the serial part is small, and there are idle cores (for computing) or idle waiting time (for I/O).
  • "Races cannot happen on one core." Preemption interleaves threads on one core. Single core machines lose updates too.
  • "async and await make code parallel." In JavaScript, and in an event loop generally, they make code concurrent on one thread. CPU heavy work inside them still blocks everything.
  • Using a Java parallel stream for blocking I/O. Parallel streams run on the common ForkJoinPool, sized to the number of cores minus one. Blocking calls inside them starve every other parallel stream in the JVM, and every CompletableFuture async step that runs on the default executor.

In the interview

You may get the definition question directly, but more often it hides in a follow up: "Can you make this faster with threads?" In a Google L5 round in 2024 the interviewer pointed out that the processing could be parallelized, and the candidate felt that needing the hint cost a Strong Hire. Apple interviewers have asked candidates to optimize a topological sort for multi-core execution, and to parallelize summing an iterator across two threads. The interviewer wants to hear whether the work can be split, what stays serial, and what the speedup is bounded by.

Concurrency is about structure: several tasks in progress at once, which can interleave even on one core. Parallelism is about execution: several things running at the same instant on different cores. Concurrency alone helps when tasks wait, because the waits overlap. Only parallelism helps when tasks compute, and then Amdahl's law caps the gain: anything serial, including every critical section under one lock, limits the speedup no matter how many cores I add.

Follow ups to expect: "Can you have one without the other?" (an event loop is concurrent but not parallel; SIMD is parallel without concurrency); "Can a race happen on a single core?" (yes, through preemption); "Your job got 3 times faster on 32 cores; why not 32?" (the serial fraction, lock contention, uneven chunks, memory bandwidth, and the cost of starting and joining the work).

Senior depth

Amdahl assumes a fixed problem size. Gustafson's law looks at the other common case: when you get more cores, you usually take on a bigger problem, and the parallel part grows while the serial part stays the same, so scaled speedup keeps improving. Both are true; they answer different questions.

Also be careful with what counts as a core. availableProcessors() and hardware_concurrency() count logical CPUs. On many x86 chips two hardware threads share one physical core (SMT, or Hyper-Threading), so 16 logical CPUs may be 8 physical cores, and two compute heavy threads on one core get far less than twice the throughput. Apple Silicon has no SMT but mixes performance and efficiency cores: the Mac Tandem runs on reports 16 logical CPUs, a mix of fast performance cores and slower efficiency cores, so equal chunks of work do not finish at equal times. Hand out work in small pieces from a shared queue rather than one big slice per thread.

Containers add one more twist. Java's availableProcessors() follows the container's CPU limit (since JDK 10), but C++'s hardware_concurrency() does not look at a CPU quota such as a Kubernetes CPU limit, so on a big host it can report far more CPUs than the container may use. C++ services usually take their thread counts from configuration for that reason.

Key takeaways

  • Concurrency: many tasks in progress at once. Parallelism: many running at the same instant on different hardware.
  • Concurrency alone speeds up waiting. Only parallelism speeds up computing.
  • Amdahl's law: the serial part, including every critical section under one lock, caps the speedup.
  • Races need concurrency, not parallelism: preemption on one core is enough to lose an update.
  • Design for concurrency; you get parallelism when the hardware and the work allow it.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A machine has exactly one CPU core and runs two threads that both have work to do. Which description is right?
Why. Both threads are in progress at once, so the program is concurrent. Only one can execute at any instant on one core, so nothing runs in parallel. A single core can hold any number of threads; the scheduler switches between them.
Two threads run count += 1 on a shared counter, on a machine with exactly one core. Can an increment be lost?
Why. Preemption can stop thread A after it has read the value into a register and before it writes it back. Thread B then does a full increment, and A writes its stale result over it. No second core is needed for that interleaving.
A job is 90 percent parallelizable. Using Amdahl's law, what is the best speedup on 8 cores?
Why. 1 / (0.1 + 0.9 / 8) = 1 / 0.2125, which is about 4.7. The tempting answer, 7.2, multiplies 8 by 0.9, but the serial 10 percent does not shrink at all, so it takes almost half of the remaining time. With unlimited cores the ceiling is 1 / 0.1 = 10.
Node.js serves 10,000 open connections from a single JavaScript thread. Which statement fits?
Why. Thousands of requests are in progress at once, so it is concurrent. The JavaScript runs on one thread, so the handlers never execute at the same instant. It works because most of each request's time is spent waiting, and the waits overlap.
Which of these is parallelism without concurrency?
Why. A single SIMD instruction is one line of work, so there is no concurrency, yet it performs 8 additions at the same instant in hardware. The event loop is concurrency without parallelism, turn taking is concurrency on one core, and the pool is both.
Four tasks each sleep 100 ms (standing in for a network call). They run on four threads on a machine with one core. Roughly how long until all four finish?
Why. A sleeping or waiting thread does not need the core, so all four waits overlap even on one core. The core is needed only for the tiny amount of computing before and after each wait. That is why concurrency helps I/O bound work regardless of the core count.
Java onlyA Java service calls a slow REST API for each item in a list using items.parallelStream().map(this::callApi). What goes wrong under load?
Why. Parallel streams are meant for CPU work and share one pool whose parallelism defaults to the core count minus one. Blocking I/O inside them holds those few threads while they wait. For many concurrent calls use an executor sized for I/O, or virtual threads, with a limit that protects the API.
C++ onlystd::thread::hardware_concurrency() returns 0 on some platform. What should your code assume?
Why. The standard allows the function to return 0 when the count is not well defined or cannot be computed. It is a hint, not a guarantee, so production code clamps it, for example std::max(1u, hardware_concurrency()), or reads the number from configuration.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Explain the difference between concurrency and parallelism to an interviewer. Give one example of concurrency without parallelism, one of parallelism without concurrency, and say why the difference matters when you decide to add threads.
Model answer

Concurrency is about structure: several tasks in progress during overlapping time, which can take turns on a single core. Parallelism is about execution: several computations happening at the same instant on different hardware.

An event loop such as Node.js or Redis is concurrency without parallelism: thousands of requests are in progress on one thread, interleaved while each waits for I/O. One thread executing a SIMD instruction that adds eight numbers at once is parallelism without concurrency: a single line of work, but several operations at the same instant.

The difference decides whether threads help. If the work mostly waits, on networks, disks or databases, concurrency alone helps, because the waits overlap; even one core gets a big win. If the work computes, only parallelism helps, so threads beyond the number of cores add switching and nothing else, and Amdahl's law caps the gain by whatever stays serial, including every critical section behind one lock. So before adding threads I ask whether the work is waiting or computing, and how much of it is serial.

Numbers
A nightly job is 80 percent parallelizable. What speedup does Amdahl's law allow on 4, 16 and 64 cores, and with unlimited cores? Your manager wants to buy a 64 core machine instead of a 16 core one. What do you say?
Model answer

Speedup is 1 / (0.2 + 0.8 / n).

  • 4 cores: 1 / (0.2 + 0.2) = 2.5 times.
  • 16 cores: 1 / (0.2 + 0.05) = 4 times.
  • 64 cores: 1 / (0.2 + 0.0125), about 4.7 times.
  • Unlimited cores: 1 / 0.2 = 5 times.

Going from 16 to 64 cores buys about 4.7 instead of 4: under 20 percent more speed for four times the cores. The serial 20 percent dominates. I would first measure where the serial time goes (a single threaded reading phase, a global lock, a final merge) and shrink it. Halving the serial part to 10 percent lifts the ceiling to 10 times and makes 16 cores give about 6.4 times, which beats buying the bigger machine.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 70 s
"A teammate says: this service runs in a container with one CPU, so we can drop the locks. What do you tell them?"
What a strong answer covers
  • Keep the locks: races need concurrency, not parallelism
  • Preemption can stop a thread between the read and the write of count += 1
  • A concrete interleaving: A reads 5 and is preempted, B writes 6, A writes 6, one update is lost
  • The compiler can still cache and reorder, and in C++ a data race is undefined behavior on any core count
  • Correctness must never depend on the core count, which is a deployment setting that will change
How a senior would say it
I would keep the locks. A race needs two threads that interleave, not two cores. On one CPU the scheduler can still stop a thread between any two instructions. Say thread A reads a counter of 5 into a register, and its time slice ends. Thread B reads 5, adds one and writes 6. A resumes with its stale 5 and also writes 6. One update is gone, and no second core was involved. A single core does remove some hardware reordering, but the compiler can still keep values in registers and reorder code, and in C++ an unsynchronized conflicting access is a data race, which is undefined behavior whatever the hardware. There is also a practical point. The CPU limit is a deployment setting, and someone will raise it next quarter. Code that is only correct on one core breaks quietly when they do. So correctness has to come from synchronization, never from the core count.

Likely follow up: Then what does a single core actually change for concurrent code?

Out loudabout 95 s
"A batch job runs about 3 times faster on 32 cores than on 1. Walk me through why it is not 32 times, and what you would check."
What a strong answer covers
  • Amdahl's law: the serial fraction caps the speedup, 1 / ((1 - p) + p / n)
  • Put a number on it: 3 times on 32 cores means only about 70 percent of the run is parallel, so more cores give little more
  • Serial parts to look for: a single threaded read or merge, and every critical section under one shared lock
  • Limits Amdahl does not model: uneven chunks, logical versus physical cores, memory bandwidth, start and join overhead
  • Measure per phase and profile lock contention, then shrink the serial part instead of buying cores
How a senior would say it
Because the part that cannot run in parallel sets a ceiling. Amdahl's law says the speedup is one over the serial fraction plus the parallel fraction divided by the cores. If I work backwards, 3 times on 32 cores means only about 70 percent of the run is parallel. The other 30 percent runs on one core no matter what, so even unlimited cores would give little more than 3. So my first question is where the serial time goes. The usual culprits are a single threaded phase, like reading the input or merging the results at the end, and any critical section under one shared lock, because only one thread can be inside it at a time. Then I would look at what Amdahl does not model. Uneven chunks, so a few threads finish late while the rest sit idle. Logical versus physical cores, since 32 logical CPUs may be 16 physical cores with hyper-threading. Memory bandwidth, if the threads mostly stream data. And the fixed cost of starting threads and joining results. I would measure before changing anything: time each phase, and profile for lock contention. The fix is almost always to shrink the serial part, by splitting the lock or merging in parallel, rather than to buy more cores, because halving the serial part doubles the ceiling.

Likely follow up: If the dataset grows with the machine, does Amdahl's law still describe what you will see?

Out loudabout 75 s
"A request handler calls three downstream services one after another, about 100 milliseconds each. Would a machine with more cores make it faster? What would?"
What a strong answer covers
  • No: the handler is waiting, not computing, so extra cores sit idle
  • If the calls are independent, issue them concurrently, so latency is the slowest call, about 100 ms, not the sum
  • That is concurrency, not parallelism: it works even on one core, because a waiting call needs no core
  • If a call needs the previous answer, the chain cannot overlap: cache it, batch it, or ask for a combined API
  • More cores matter only when CPU is the bottleneck: high CPU and flat throughput under load
How a senior would say it
No. That request spends about 300 milliseconds waiting and almost nothing computing, so more cores would just sit idle. What helps is overlapping the waits. If the three calls do not depend on each other, I would start all three at once, with futures or virtual threads in Java, or std::async in C++, and wait for all of them. Then the latency is the slowest call, about 100 milliseconds, instead of the sum. That is concurrency, not parallelism, and it works even on a single core, because a waiting call does not need a core. If call two needs call one's answer, overlapping is impossible, so I would look at caching, or a batched or combined endpoint, to shorten the chain. I would also put a timeout on each call, so one slow service cannot hold the whole request. More cores only matter when the machine is CPU bound under load, which shows up as high CPU and flat throughput, not as slow single requests.

Likely follow up: Now one of the three services gets slow. What happens to your handler, and how do you protect it?
