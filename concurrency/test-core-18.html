Why does the stress test release all its threads through a start gate (a latch at 1) instead of starting them one by one?
Why. Threads started one by one often finish their first iterations before the next even starts, so the test runs nearly sequentially and proves little. A gate increases the opportunity for overlap, but some threads may reach it after it opens. It does not make the test deterministic; that is why you also measure invariants and repeat runs.

Inside a loop, left = cond.awaitNanos(left); returns -120000. What does that mean, and what should the loop do?
Why. awaitNanos returns an estimate of the time left, and a value at or below zero means the deadline passed. Interruption is reported by an exception, not a return value, and the lock is held again on return. Restarting the original timeout after each wakeup could extend the wait indefinitely.

An ordinary ThreadPoolExecutor with no custom hooks accepts a task through submit. The task throws without logging, and nobody inspects its future. What happens?
Why. submit wraps the task so that its outcome, including an exception, is captured in the Future; get() would throw ExecutionException. The submitting thread does not receive that task failure, the worker survives, and the pool does not shut down. A plain throwing Runnable passed to ThreadPoolExecutor.execute follows the uncaught-exception path instead.

A thread holds only the read lock of a ReentrantReadWriteLock, has no write hold, and calls writeLock().lock(). What happens?
Why. Upgrading is not supported: the writer waits for every read hold to be released, and this thread's own hold never will be. The reverse, taking the read lock while holding the write lock and then releasing the write lock, is the supported downgrade.

A function creates std::thread t(work); and returns without calling join() or detach(). What happens?
Why. Destroying a std::thread that is still joinable terminates the program, even if the thread's function has finished, because the thread object still owns that thread until it is joined, detached or moved from. std::jthread (C++20) joins in its destructor instead.

Why. Success stores 4 in the atomic and leaves expected unchanged at 3. Weak CAS may fail spuriously even when values match; failure loads the observed 3 into expected and leaves the atomic at 3. Why. POSIX allows spurious wakeups, and with several consumers a woken thread can lose the item to another that took the mutex first. while (count == 0) re-checks every time; an if does not. "Can't we just use Kafka's exactly-once and skip idempotency in the consumer that sends emails?" Which reply is accurate?
Why. Kafka transactions are real but scoped: they commit Kafka outputs and consumed offsets atomically. Side effects outside Kafka are not part of the commit. An exact LRU cache updates its shared recency list on every hit. Someone proposes a read-write lock "because gets dominate". Which response identifies the limitation?
Why. Hits in this implementation mutate shared order and cannot safely run under a shared read lock. Misses need not change recency, so the benefit depends on workload.
