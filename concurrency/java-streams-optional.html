Streams and Optional

Stream pipelines, why lambdas must not mutate shared state, the parallel stream common pool trap, and Optional for absent results.

Before this:Lambdas, functional interfaces and method referencesThe collections you will use

Streams make data processing short and readable, and .parallel() makes it look like a free way to use every core. It is not free: a lambda with a side effect becomes a race, and every parallel stream in the JVM shares one small pool of threads.

In plain words

Picture an assembly line. Items ride past a few stations: one throws out damaged items (filter), one paints each item (map), and at the end a packer puts them in boxes (collect). Each station only looks at the item in front of it, which is why the line is easy to reason about.

Now open three more identical lines to go faster. That still works, as long as no station scribbles on a shared whiteboard; with four lines writing on one board at once, the board becomes garbage. And there is a catch: the extra lines are staffed from one pool of workers shared by the whole factory. If one line's workers stand around waiting for a delivery truck, every other line in the factory slows down.

Why this matters for concurrency

  • parallel() runs your lambdas on several threads at once. A lambda that writes to a shared ArrayList, HashMap or counter is then a data race, with no Thread anywhere in the code.
  • All parallel streams, and CompletableFuture async methods called without an executor, share ForkJoinPool.commonPool(), which has one thread fewer than the machine has cores. Blocking I/O there starves everything else that uses it.
  • Streams are the tidy way to collect results from futures, but laziness can quietly turn a parallel fan-out into a serial loop. And Optional belongs in your own concurrent APIs, such as a tryTake() that may find nothing.

A stream pipeline

A stream is not a collection; it holds no data. It describes a computation over a source, in three parts:

  • A source: list.stream(), Arrays.stream(array), IntStream.range(0, n), map.entrySet().stream().
  • Intermediate operations, which are lazy and each return a new stream: filter, map, flatMap, distinct, sorted, limit, peek.
  • One terminal operation, which actually runs the pipeline: collect, toList(), reduce, count, sum, forEach, findFirst, anyMatch, min, max.

Four facts about pipelines matter later in this lesson:

  • Lazy, and one element at a time. Nothing runs until the terminal operation, and then each element travels through the whole chain before the next one starts, rather than stage by stage. The exception is a stateful operation such as sorted, which must see every element before it passes any on. Hold on to this; it explains the lazy join trap below.
  • One shot. A stream can be consumed once. A second terminal operation throws IllegalStateException: stream has already been operated upon or closed.
  • toList() is unmodifiable. Adding to its result throws UnsupportedOperationException. Collectors.toMap throws IllegalStateException on a duplicate key unless you pass a merge function.
  • reduce(identity, op) has two rules. The identity must really be neutral for the operation (0 for a sum, 1 for a product), and the operation must be associative. A sequential stream forgives a wrong identity; a parallel one does not.

Side effects: the rule that parallel streams enforce

The stream documentation asks for lambdas that do not modify the source and are stateless, and it strongly discourages side effects. In a sequential stream, breaking that is merely ugly. In a parallel stream, a side effect on shared state is a race. Here are two ways to break a parallel stream, and the fixes:

The ArrayList version loses elements on most runs, sometimes throws ArrayIndexOutOfBoundsException, and can even leave null entries where two threads raced during a resize. toList() is correct in parallel because the stream builds a separate piece per chunk and joins the pieces in order; nothing is shared. The bad reduce adds the seed once per chunk, so its parallel answer depends on how the stream was split: 50 here when it splits into four pieces. Put the 10 outside the reduction.

Java's effectively final rule stops you from writing count += 1 on a local inside a lambda. People work around it with int[] count = {0} (a race in parallel) or an AtomicInteger (correct, but every thread fights over one variable, and the order is still undefined). Both miss the point: express the result as the output of the pipeline, with count(), sum(), reduce or collect.

Two smaller surprises. On a parallel stream forEach runs in no particular order; forEachOrdered keeps the source order, at a cost. And side effects may not run at all: since Java 9, count() may skip the pipeline entirely when the size is known from the source, so List.of("A", "B", "C").stream().peek(System.out::println).count() returns 3 and prints nothing.

Parallel streams and the common pool

A parallel stream, from parallelStream() or .parallel() on any stream, splits the source into chunks and runs them as fork/join tasks on the common pool, ForkJoinPool.commonPool(). The calling thread joins in and does part of the work itself. The common pool's parallelism is the number of available processors minus one (at least one), and you can change it with the system property java.util.concurrent.ForkJoinPool.common.parallelism.

The output names main and ForkJoinPool.commonPool-worker-N: the caller plus the shared pool. That pool is shared by every parallel stream in the JVM, and by CompletableFuture.supplyAsync, thenApplyAsync and the other async methods whenever you do not pass an executor (on a machine where the common pool's parallelism is below 2, those methods start a new thread per task instead).

Parallel streams tend to help whenThey tend to hurt when
Each element needs real CPU workThe work is I/O or any blocking call
There are many elements (thousands and up, as an order of magnitude)The input is small, so splitting costs more than it saves
The source splits cheaply: arrays, ArrayList, IntStream.rangeThe source splits badly: LinkedList, Stream.iterate, I/O sources
Lambdas are stateless and the reduction is associativeLambdas touch shared mutable state
Order does not matterThe pipeline uses limit, findFirst or forEachOrdered on an ordered source
The code runs in a batch job that owns the machineThe code runs inside request threads, which then all compete for the same few pool threads

The worst case is blocking I/O inside a parallel stream. Each call holds a common pool thread hostage while it waits, so every other parallel stream and every default CompletableFuture in the process queues up behind your network calls. For I/O fan-out, use an executor sized for I/O, or Java 21 virtual threads, with an explicit concurrency limit. You will sometimes see the trick of running a parallel stream inside your own ForkJoinPool with pool.submit(() -> list.parallelStream()...).get(). It works because tasks forked from a pool's worker stay in that pool, but that is an implementation behavior, not a documented promise.

Optional

Optional<T> holds either a value or nothing. It was designed as a return type for "there may be no result", which is why findFirst(), max() and reduce(op) without an identity return one. The useful methods:

  • Transform: map, flatMap, filter.
  • Get out: orElse(value), orElseGet(() -> compute()), orElseThrow() (Java 10), or(() -> otherOptional) (Java 9).
  • Act: ifPresent(action), ifPresentOrElse(action, emptyAction) (Java 9). Test: isPresent(), isEmpty() (Java 11).
  • Create: Optional.of(value) (throws on null), Optional.ofNullable(maybeNull), Optional.empty().

The common trap: orElse(expensive()) always runs expensive(), even when the value is present, because Java evaluates arguments before the call. Use orElseGet(() -> expensive()). Also, get() on an empty Optional throws NoSuchElementException; orElseThrow() does the same but says so in the code. Do not use Optional for fields, parameters or collection elements, and never return null from a method declared to return Optional.

Two connections to concurrent code make Optional worth knowing well:

  • Read shared state once. if (cache.get(k) != null) return cache.get(k); reads a shared map twice, and another thread can remove the key in between, so the method returns null after checking that it would not. return Optional.ofNullable(cache.get(k)); reads once and makes "read, then decide" the natural shape.
  • Absent must mean absent. ConcurrentHashMap forbids null keys and values. Doug Lea, its designer, explained why: in a plain map you can tell "no entry" from "entry whose value is null" by calling containsKey, but in a concurrent map the map can change between the two calls, so get returning null must mean "absent" with no ambiguity. The same reasoning makes Optional a good return type for your own tryTake() or poll(): empty means "nothing there right now".

The senior question to ask first: is the input big enough, and the work CPU-heavy enough, to beat the cost of splitting and merging? For a few thousand short lines, the sequential stream is probably faster. Measure, and say that you would measure.

Common mistakes

  • Collecting through a side effect. forEach(list::add) into a shared list or map. Use toList(), collect, or reduce.
  • "Fixing" a lambda counter with an int[] or an AtomicInteger. The first is a race, the second a contention point. Use count() or sum().
  • A reduce seed that is not an identity. It is added once per chunk in parallel. Add constants outside the reduction.
  • Blocking calls in a parallel stream. They hold common pool threads that the whole JVM shares. Use an executor or virtual threads for I/O.
  • Parallelizing small inputs. Splitting and merging cost more than they save.
  • Expecting forEach to keep order in parallel. Use forEachOrdered, or better, collect.
  • Joining futures in the same pipeline that creates them. The fan-out becomes a loop. Two pipelines.
  • orElse(expensive()), and get() without a check. Use orElseGet and orElseThrow.
  • Reading a shared map twice. if (m.get(k) != null) return m.get(k); can return null. Read once into a local or an Optional.

In the interview

Streams are rarely the question in a concurrency round, but they show up in the code you write, and two follow ups are common: "can you parallelize this?" and "what is wrong with this lambda?"

I would only use a parallel stream for CPU-bound work on a large source that splits easily, with no shared mutable state. It runs on the common fork/join pool, which has cores minus one threads for the whole JVM, so for I/O I would use my own executor, or virtual threads with an explicit limit, instead.
Inside a stream, the result comes out of the pipeline through collect or reduce, never through a side effect into a shared collection. Then the parallel version is exactly as correct as the sequential one.

Follow ups to expect. "Which pool do parallel streams use, and how big is it?" (ForkJoinPool.commonPool(), available processors minus one by default, plus the calling thread, shared by the whole JVM). "How would you call 100 services in parallel and keep the results in order?" (submit all to an executor as CompletableFutures, then join them in order). "Why does ConcurrentHashMap reject null?" (so one get returning null always means absent; a follow-up containsKey would race with writers). "What does Optional give you over returning null?" (the signature tells the caller the result may be missing and forces them to handle it, and it composes with map and orElseGet; it costs an allocation, so keep it to return values, not fields or hot inner loops).

Senior depth

  • How parallel collect stays safe. A collector has a supplier, an accumulator and a combiner. In parallel, each chunk gets its own container from the supplier, fills it alone, and the combiner merges containers pairwise. That is thread confinement, not locking, which is why collect(Collectors.toList()) needs no synchronization. The concurrent collectors (groupingByConcurrent, toConcurrentMap) instead share one concurrent map and give up encounter order.
  • Splitting quality decides speed-up. A source reports characteristics such as SIZED and SUBSIZED through its Spliterator. An array or ArrayList splits into equal halves cheaply; a LinkedList has to walk to split, and Stream.iterate hardly splits at all. Calling unordered() can make distinct() and limit() much cheaper in parallel.
  • Parallel streams are a CPU tool; virtual threads are a waiting tool. In Java 21, a blocking fan-out of a thousand calls is a virtual thread per call plus a Semaphore for the limit, not a parallel stream.

Key takeaways

  • A pipeline is a source, lazy intermediate operations and one terminal operation; elements flow through it one at a time.
  • Lambdas must not mutate shared state. In a parallel stream a side effect is a race; produce results with collect, reduce or toList().
  • Parallel streams run on the common ForkJoinPool (cores minus one threads, shared by the whole JVM): use them for big CPU-bound work, never for blocking I/O.
  • Start all futures in one pipeline and join them in another, or the fan-out becomes a loop.
  • Optional is a return type for "maybe no result"; prefer orElseGet and orElseThrow, and read shared state once.

Quick check

Answer each question, then read why. Your score is saved for your module test.

List<Integer> out = new ArrayList<>(); IntStream.range(0, 100_000).parallel().forEach(out::add); Which outcomes are possible? Select all that apply.Select all that apply
Why. ArrayList.add is a read-modify-write of the size and the backing array. Concurrent calls overwrite each other's slots (lost elements), race during a resize (an exception, or slots that end up null), and nothing guarantees the count. Use toList() or collect, which give each chunk its own container.
What does Stream.of(1, 2, 3, 4).parallel().reduce(10, Integer::sum) return?
Why. Each chunk starts its own reduction from the identity, and the partial results are combined. With a true identity (0) that changes nothing; with 10 it adds 10 per chunk. The sequential result is 20, the parallel one varies with the split. Keep the seed neutral and add constants outside.
On Java 21, what does List.of("A", "B", "C").stream().peek(System.out::println).count() print?
Why. Since Java 9, count() may compute the answer directly from a sized source and skip the intermediate operations, so peek never runs. It is a reminder that side effects in a pipeline are not even guaranteed to happen. Add a filter, and the size is no longer known, so peek runs again.
On a machine with 8 available processors, what is the default parallelism of ForkJoinPool.commonPool(), which parallel streams use?
Why. The default is the number of available processors minus one (at least one), because the thread that starts a parallel stream also does part of the work. The pool is shared by the whole JVM, which is why one blocking stream can starve the others; the size can be changed with a system property.
String user = cache.lookup(id).orElse(loadFromDatabase(id)); What happens when lookup finds the user?
Why. Java evaluates method arguments before the call, so the database query runs every time. orElseGet(() -> loadFromDatabase(id)) takes a supplier and only calls it when the Optional is empty.
Why does ConcurrentHashMap refuse null keys and values?
Why. In a plain map you can tell a missing key from a key mapped to null with a second call, containsKey. In a concurrent map another thread can change the map between the two calls, so the answer would be meaningless. Banning null makes a single get unambiguous, the same idea behind returning Optional from your own concurrent methods.
Four ids are processed with ids.stream().map(id -> CompletableFuture.supplyAsync(() -> fetch(id), pool)).map(CompletableFuture::join).toList(). Each fetch takes 100 ms and pool has 4 threads. About how long does it take?
Why. Streams are lazy and push one element through the whole pipeline at a time, so the second supplyAsync is called only after the first join returns. Collect the futures with toList() first, then join them in a second pipeline, and the four calls overlap. There is no deadlock here, because join runs on the calling thread, not on a pool thread.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
A teammate wants to call 1,000 URLs with urls.parallelStream().map(this::fetch).toList(). Would you approve it? If not, what would you write instead, keeping the results in input order and at most 50 calls in flight?
Model answer

No. fetch is blocking I/O, and a parallel stream runs on the common fork/join pool: cores minus one threads, shared by every parallel stream and default CompletableFuture in the JVM. The calls would hold those threads while waiting on the network, so we would get only a handful of calls in flight, and everything else in the process that uses the common pool would stall behind them.

Instead, an executor meant for waiting, and an explicit limit. In Java 21:

The futures are created in one pipeline and joined in a second, so the calls overlap; joining in list order keeps the results in input order. Virtual threads make waiting cheap and the semaphore protects the remote side. On Java 17 I would use a fixed pool of 50 platform threads instead, which gives the limit by itself. I would also add a timeout per call and decide whether one failure should fail the whole batch.

Write code
Make this correct when the stream is parallel, without any lock: List<String> longWords = new ArrayList<>(); words.parallelStream().filter(w -> w.length() > 3).forEach(longWords::add); Then, in the same style, count the words by their first letter.
Model answer

The original shares one ArrayList between the threads of the common pool, so elements are lost or the list is corrupted. In the fix the result is the output of the pipeline: each chunk fills its own container and the stream merges them, so there is no shared mutable state and no lock. For the counts, groupingBy merges per-chunk maps; groupingByConcurrent would insert into one ConcurrentHashMap instead, which is often faster when the order of entries does not matter.

Debug
A cache method reads if (cache.get(key) != null) { return cache.get(key); } return load(key); on a ConcurrentHashMap that another thread evicts from. Callers occasionally get null. Explain, and fix it two ways.
Model answer

It reads the shared map twice. Between the check and the second get, the evictor can remove the key, so the method checks that the value is there and then returns null anyway: a check-then-act across two calls that are each thread-safe on their own.

Fix one: read once into a local. String v = cache.get(key); return v != null ? v : load(key); or, with Optional, return Optional.ofNullable(cache.get(key)).orElseGet(() -> load(key));. Fix two, if a missing value should also be stored: return cache.computeIfAbsent(key, this::load);, which makes the check and the insert one atomic step per key, so concurrent misses on the same key run the loader once. (The loader then runs while that key's bin is locked, so it must be short and must not touch the map itself.)
