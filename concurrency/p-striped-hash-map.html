Striped hash map

Thread-safe structureshard45 minMetaGoogle

One lock around a map is correct and slow: every thread queues for it. Splitting the map into stripes is the first scaling idea every interviewer expects, and computeIfAbsent and size() are exactly where most striped maps quietly break.

The task

Build a thread-safe hash map that uses lock striping. The map is split into a fixed number of stripes. Each key belongs to exactly one stripe, chosen from its hash, and each stripe has its own lock and its own table. Threads working on keys in different stripes must never wait for each other.

  • get(key) returns the value, or nothing when the key is absent.
  • put(key, value) stores the value and returns the previous one, if any.
  • remove(key) removes the key and returns the removed value, if any.
  • computeIfAbsent(key, loader) returns the value for the key. When the key is absent it calls loader once, stores the result and returns it. When many threads call it for the same absent key at the same time, the loader runs once and every caller gets the same value. If the loader throws, nothing is stored and the exception reaches the caller.
  • size() returns the number of keys. It must be exact whenever no writer is running; while writers run, any value between the smallest and largest possible size is fine.

This is how callers use computeIfAbsent: one shared counter per key, created on first use. If two threads could each create a counter for the same word, one counter would be dropped along with every increment made on it.

Rules: library concurrent maps are banned (in Java, ConcurrentHashMap and its relatives), because they are what you are building. A plain HashMap or std::unordered_map inside each stripe is fine, and so is letting that table grow. The number of stripes is fixed at construction. In Java, keys and values are never null.

Where it comes up: a Meta design round praised sharding a cache's hash table into about one part per core so it could lock efficiently, a Google round asked for a per-user counter map under many threads, and Netflix platform loops include writing a concurrent hash map.

What the tests check

  • From one thread: put, get, remove, size and computeIfAbsent behave like a normal map, including keys whose hash code is negative.
  • No lost updates: 8 threads increment 64 shared counters created through computeIfAbsent, and every increment is counted.
  • Exact size: 8 threads put and remove distinct keys; the final size() is exact and a concurrent reader never sees an impossible size.
  • Once per key: 8 threads call computeIfAbsent on the same 300 keys at the same moment with a slow loader; each loader runs once and all threads get the same object.
  • Real striping: loads of keys in different stripes overlap in time, and a slow load in one stripe does not stop put and get on keys in other stripes.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Lock granularity, contention and lock striping

Open them one at a time. Each one gives away a little more.

Start from the version you know is correct: one map and one lock. Now make N of them. What decides which of the N a key uses, and why must that choice never change while the map is alive?
The stripe is hash(key) mod N. Every operation on a key takes only that stripe's lock and only touches that stripe's table. In Java, hashCode() can be negative and % keeps the sign, so use Math.floorMod or clear the sign bit, or a negative key will index outside your array.
computeIfAbsent must look up, call the loader and insert inside one critical section on the key's stripe; if you unlock between the check and the insert, two threads both see the key missing. For size(), do not keep one shared counter updated under different stripe locks: two writers in different stripes hold different locks, so their updates race. Sum the stripe sizes instead.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Your stripes grow separately. Build one table that resizes while readers and writers keep running, and explain how ConcurrentHashMap does it.
The blunt way: take every stripe lock in index order, build a table twice the size, rehash, swap, release. It is correct but stops the world. Java 7's ConcurrentHashMap avoided that by resizing each segment under its own lock, which is your design. Java 8 resizes one big table incrementally: it allocates the new table, and any thread that writes during the resize helps move bins, each bin under that bin's lock, leaving a forwarding node in the old slot. A reader that meets a forwarding node simply looks in the new table, so reads never block, and empty bins are claimed with a CAS. Arcesium asked candidates in 2026 to design a ConcurrentHashMap from a HashMap with bucket-level locks, then followed up on read-write locking; resizing is where that design gets hard.
Reads are 95 percent of the traffic. What would you change?
Give each stripe a read-write lock (ReentrantReadWriteLock, or std::shared_mutex with std::shared_lock for reads) so readers of the same stripe share it. Say the cost too: a read-write lock is more expensive to acquire than a plain mutex, so it only wins when readers are many and the critical section is not tiny. The step after that is lock-free reads: immutable entries published through volatile or atomic fields, which is what ConcurrentHashMap does. Measure before choosing.
How many stripes would you pick?
Enough that two busy threads rarely land on the same stripe: a few times the number of threads that use the map at once, often a power of two so you can mask instead of dividing. More stripes cost memory and make whole-map operations such as size, clear and iteration slower. And striping never helps a single hot key: every thread that wants it still meets on one lock.
Make size() an exact snapshot even while writers run.
Lock every stripe in index order, sum, then unlock. Because every multi-stripe operation takes the stripes in the same order, it cannot deadlock, but it stops all writers for a moment. The cheap alternative is a per-stripe counter summed without locks, which is exact only when the map is quiet. One global atomic counter is exact, but every writer now hits the same cache line, which brings back the contention that striping removed.
What happens if a loader calls computeIfAbsent on the same map?
If the inner key lands in the same stripe, C++ locks a std::mutex the thread already holds: undefined behavior, in practice a self-deadlock. Java's locks are reentrant, so the inner call goes through and modifies the stripe in the middle of the outer call, which is fragile. ConcurrentHashMap documents that the function must not modify the map and throws IllegalStateException when it detects such a recursive update. State the rule in your API: loaders are short and never touch the map.
A slow loader holds its stripe lock, so every key in that stripe waits. Can you avoid that?
Yes, with a per-key placeholder. Under the stripe lock, insert a future for the key and unlock; run the loader outside any lock; then complete the future. Other callers for that key wait on the future, not on the stripe, and other keys in the stripe are free. Failures must remove the placeholder so a later call can retry. That is the single-flight cache.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Split the key space into N disjoint parts by hash. Part i has its own lock and its own ordinary hash table. The invariant: a key only ever lives in stripe hash(key) mod N, and that stripe's lock guards every read and write of it. Two operations on different stripes touch no shared memory, so they run in parallel. Two operations on the same stripe take turns, which is all the safety a single key needs.

Why each line is there

  • A fixed number of stripes. If the stripe array could grow, a key's stripe, and so its lock, would change under concurrent callers. Each stripe's own table may grow freely, because it grows under its own lock.
  • Math.floorMod (or masking). -17 % 16 is -1 in Java. A negative index throws on the first negative hash code. In C++, std::hash returns an unsigned size_t, so this trap does not exist there.
  • computeIfAbsent in one critical section. Look up, call the loader and insert while holding the key's stripe lock. Only that stripe waits for the loader; every other stripe stays free. If the loader throws, nothing was inserted, and synchronized or the lock_guard releases the lock as the exception leaves.
  • size() sums the stripes. Each stripe's size is read under its own lock. The tempting shortcut is one size field updated by every writer, but writers in different stripes hold different locks, so nothing orders their updates:
  • In C++, the stripe vector is sized once. std::mutex can be neither copied nor moved, so std::vector<Stripe>(n) constructs the stripes in place and must never be resized.

Cost and trade-offs

Each operation is O(1) on average and holds one lock. With N stripes and keys spread evenly, two random operations collide on a stripe with probability about 1/N, so contention falls as N grows, until a hot key puts everyone back on one lock. Whole-map operations (size, iteration, clear) now touch N locks. On real hardware, neighbouring stripe locks can share a cache line and slow each other down (false sharing); padding each stripe to 64 bytes (alignas(64) in C++) is a refinement worth mentioning, not something to lead with.

How to say it in the interview

One lock serializes every operation, so I will stripe it: N independent tables, each with its own lock, and a key always maps to stripe hash mod N, with floorMod so negative hashes stay in range. Every operation locks only its key's stripe, so threads on different stripes never meet. computeIfAbsent does the check, the load and the insert inside that one stripe lock, so the loader runs once per key and only that stripe waits. size sums the stripes, because a single shared counter updated under different locks would lose updates. If reads dominate I would move each stripe to a read-write lock, and if loaders are slow I would switch to per-key futures so the stripe lock is never held during a load.
