Types, casts, conversions and initialization

Read conversions precisely, choose the right cast and initializer, and distinguish compile-time constants from shared state across objects and source files.

Before this:Classes, constructors, destructors and RAIIconst correctness and mutable

A queue can have perfect locking and still accept a negative capacity as a huge positive number. Types, conversions and initialization decide what your program actually means before the first thread starts.

In plain words

Imagine ordering storage boxes. "Three boxes" and "one box labelled three" sound similar, but the deliveries are different. Changing the label on a box also does not change what is inside it.

C++ makes both distinctions: punctuation can select a different constructor, and a cast can change how you view an object without changing the object. You must know which promise each spelling makes.

Why this matters for concurrency

Queue capacities cross signed and unsigned boundaries, state machines use enums, and counters can overflow while holding a lock. A static member is shared by instances; a namespace static in a header can create a different mutex in every source file. Neither constexpr nor inline supplies synchronization.

Classes and RAII covers construction order and ownership; const correctness covers read-only interfaces. Here you learn the conversion and declaration rules those designs rely on.

Implicit conversions and explicit boundaries

An implicit conversion happens without a cast, including at initialization, function calls and returns. double d = 3; preserves the value; int n = 3.9; discards the fractional part. Successful compilation does not prove value preservation.

A constructor without explicit can provide an implicit conversion into a class. An explicit constructor requires deliberate construction: Capacity c(3) or Capacity c{3} works, while Capacity c = 3, Capacity c = {3} and passing bare 3 to a Capacity parameter do not. This also applies to constructors with defaulted parameters, not just declarations with exactly one parameter.

This prints capacities 3, 4, 5, then ratio 1.5. Casting after division, static_cast<double>(3 / 2), produces 1.0: integer division already discarded the fraction. Floating-to-integer conversion truncates toward zero; an unrepresentable truncated result, including conversion from NaN or infinity, is undefined behaviour.

explicit controls conversions into the class, not conversions of constructor arguments: Capacity c(3.9) still converts the argument to int; Capacity c{3.9} rejects narrowing. A conversion function such as explicit operator bool() const controls the other direction. It works in if (handle) and with static_cast<bool>(handle), but not in bool b = handle. General deduction rules continue in templates and auto.

An implicit conversion sequence normally includes at most one user-defined conversion. If B can be constructed from A and C from B, passing an A where a C is expected does not automatically chain both constructors.

The four casts: state the operation you intend

CastRight useWhat it does not prove
static_cast<T>(x)Numeric conversion, enum to integer, known class relationship, or restoring an original object pointer from void*No runtime range or dynamic-type check; cannot remove const
dynamic_cast<T*>(p) or dynamic_cast<T&>(x)Checked downcast or cross-cast through a polymorphic hierarchyNo lifetime or thread-safety guarantee; pointer failure returns null, reference failure throws std::bad_cast
const_cast<T*>(p) or const_cast<T&>(x)Change const or volatile qualification at a narrow interface boundaryDoes not make an originally const object writable or provide synchronization
reinterpret_cast<T*>(p)Low-level pointer representation work, such as viewing object bytesDoes not create a T, check alignment or permit access through an unrelated object type

A C-style cast such as (T)x hides the operation and can combine reinterpretation with removing const. Prefer a named cast so a reviewer can inspect the claim. The alternatives are specified in the C++20 cast rules.

static_cast versus dynamic_cast

An upcast from Derived* to an accessible, unambiguous Base* normally needs no cast. A static_cast<Derived*>(base) downcast requires the non-null pointer to identify the appropriate base subobject of a Derived; a wrong downcast is undefined behaviour. Downcasting through a virtual base this way is rejected.

When the runtime type is uncertain, use dynamic_cast and handle failure. Runtime downcasts and cross-casts require a polymorphic source type, meaning it has a virtual function. This example uses a virtual destructor; inheritance and virtual functions explains dispatch and destruction.

A cross-cast moves from one base interface to another within the same complete object, with the runtime checking the public, unambiguous relationship. These checked operations depend on runtime type information, usually called RTTI; builds that disable RTTI cannot use them.

This prints read 64, not a read, then reference cast failed. A null source pointer also produces null; a dangling pointer is not a safe failure case. The runtime cast rules assume a suitable live object. Prefer a virtual operation over repeated type tests when the operation belongs on the interface.

const_cast and reinterpret_cast: narrow permissions

const_cast changes the access path, not the object's original mutability. Writing through it can be valid when the original object is non-const; writing a const object's ordinary data is undefined behaviour. A localized cast can bridge a legacy API taking char* but documented never to write; fixing the API is preferable.

reinterpret_cast can expose a representation through char, unsigned char or std::byte. It does not let you read an int as a float just because their sizes match. C++20 std::bit_cast<To>(from), from <bit>, creates a value from the representation: both types must be trivially copyable and have equal size, and the resulting representation must describe a valid destination value. These are representation-copy constraints, not numeric conversion rules.

In C++17, copy with std::memcpy from <cstring> into a separate existing destination object of the same size, with both types trivially copyable and the copied representation valid for the destination. Do not treat padding or indeterminate bits as data. Neither operation parses a wire format or fixes byte order; memory and object layout explains alignment and storage.

This prints quota 4 and same byte true. No cast coordinates threads. In particular, casting int* to std::atomic<int>* does not turn an integer into an atomic object; use a real atomic and study volatile and atomic.

Arithmetic happens in the operands' types

Integer promotions convert small integer operands before arithmetic: bool becomes int; ordinary character and short integer types promote to int when it represents their entire range, otherwise to unsigned int. Two small unsigned operands can therefore do signed arithmetic. Storing a result in a wider variable does not widen the calculation.

After promotion, integer operands get a common type. With the same signedness, higher rank wins. With mixed signedness, unsigned wins if its rank is at least the signed rank; otherwise the signed type wins if it represents every unsigned value, and failing that both convert to its unsigned counterpart. Unsigned does not always win.

The last comparison is false: -1 becomes the largest unsigned int. The multiplication is safe because 1LL makes it long long before multiplying. On a machine with 32-bit int, long long total = 50000 * 50000; has signed overflow before assignment.

Ordinary signed overflow is undefined behaviour, not guaranteed wraparound. Unsigned arithmetic wraps modulo 2N for N value bits, but a wrapped capacity is still a bug. To add nonnegative int values safely, check b > std::numeric_limits<int>::max() - a before evaluating a + b. A mutex does not change arithmetic rules.

The C++20 integer conversion rules define out-of-range conversions to integer types other than bool by congruence modulo 2N, distinct from signed arithmetic overflow. Conversion to bool instead maps zero to false and every nonzero integer to true. Before C++20, out-of-range conversion to a signed integer was implementation-defined; neither rule validates user input.

Atomic integer fetch_add has its own defined signed arithmetic semantics, covered in atomics and CAS; a plain overflowing expression passed to it is still wrong. A wider atomic destination cannot repair arithmetic that overflowed while computing its argument.

size_t: validate before converting

std::size_t, from <cstddef>, is the unsigned type of sizeof; standard container sizes commonly use it. It is not necessarily unsigned int. On usual 64-bit targets, a negative int compared with a vector's size converts to a huge unsigned value.

  • v.size() - 1 wraps on an empty vector. An unsigned reverse index testing i >= 0 never terminates by that condition.
  • Use for (std::size_t i = v.size(); i > 0; ) { i -= 1; use(v[i]); }, checking before subtraction. Reverse iterators also avoid the issue.
  • C++20 std::ssize(v) from <iterator> returns a signed size, useful for signed index arithmetic when the size fits that result type. In C++17 use reverse iterators or a checked conversion.
  • C++20 std::cmp_less(a, b) compares standard signed and unsigned integers without the negative-to-unsigned surprise; std::in_range<T>(x) checks representability. Both are in <utility>. Comparing safely does not make concurrent v.size() and mutation safe.

Worked example: a capacity check that comes too late

Configuration supplies int requested = -1. Converting it to std::size_t and checking whether the result is positive accepts a huge count. Instead, validate the original value, then convert once, and enforce an application limit.

This prints rejected -1, rejected 0, accepted 1, accepted 3, accepted 1024, rejected 1025, then true. The valid endpoints and their invalid neighbours are exercised. For this small limit in C++17, checking requested <= 0 || requested > 1024 before the cast suffices. Returning a container size as int needs the reverse proof: an established INT_MAX capacity bound or a representability check.

For count * element_size bytes, unsigned wrap is another boundary: when element_size is nonzero, reject count > max_size / element_size before multiplying. Indexing drills continue in the STL for coding rounds; queue indices return in queues inside a fixed buffer.

Braces and parentheses choose different constructors

DeclarationMeaning
int x; as an automatic localDefault-initialized scalar: no initial value; ordinary reading is undefined behaviour in C++20
static int x; inside a function, or namespace-scope int x;Static storage duration: zero-initialized, so starts at zero
int x{}; or int x = 0;Starts at zero
T x(args);Direct initialization; considers explicit constructors
T x{args};Direct list initialization; rejects narrowing and gives initializer-list constructors priority
T x = expression;Copy initialization; excludes explicit converting constructors; does not imply an actual extra copy
T x = {args};Copy list initialization; rejects narrowing and is ill-formed if overload resolution selects an explicit constructor
T x();A function declaration, not a default-constructed object

List initialization rejects narrowing, such as int n{3.0} even though the value is integral. For integer-to-integer narrowing, a constant expression that fits is allowed: unsigned char c{42} works. A nonconstant int initializer is rejected when its type's range does not fit, even if its current value is 42.

For nonempty lists and non-aggregate classes, a viable std::initializer_list constructor is preferred. If that selected constructor needs narrowing, compilation fails rather than falling back to another constructor. Empty braces use an available default constructor. These are list-initialization rules, not interchangeable punctuation.

auto a{3} deduces int; auto b = {3} deduces std::initializer_list<int>. auto c{1, 2} is invalid; auto d = {1, 2} is a list; auto e = {1, 2.0} fails because the element types differ. The list is a view of const elements, not a resizable vector; do not return a list backed by a local braced initializer.

Use parentheses when you mean a container's count or count-and-value constructor. Prefer braces for scalars and deliberate values. int n{static_cast<int>(3.9)} compiles because the cast already discarded the fraction. Braces cannot recover information an earlier expression lost.

For a simple aggregate struct Job { int id; bool done; };, Job job{7}; initializes members in order and makes the omitted done false. Job job{}; makes both zero-like. Do not generalize that to every class: T{} can call a user-provided constructor that leaves scalar members uninitialized. The declaration T object(); is the simplest form of the most vexing parse; use T object{}; to request an object.

For struct A { int n; A() = default; };, automatic A a; leaves n indeterminate, whereas A a{}; value-initializes and first zeroes it. Changing the constructor to A() {} makes it user-provided, so even automatic A a{}; leaves n indeterminate. A default member initializer, int n{};, supplies zero in both cases; see the initialization rules.

enum class: states are not integers

An unscoped enum puts enumerator names in the enclosing scope and permits conversion to integers. enum class keeps names scoped, requires explicit integer conversion, and prevents accidental mixing of unrelated enums. Its default underlying type is int; declare a fixed type when an interface needs one.

This prints legacy 1, closed true, then state code 2. Casting 99u to this fixed-underlying-type enum would not check whether 99 names a state. enum class also does not supply flag operators or atomic updates. Use a lock or std::atomic<State> for shared mutable state; CAS loops and state machines handles legal transitions.

The fixed underlying type matters: static_cast<State>(99u) is a defined conversion to an unnamed value, but static_cast<Legacy>(99) is undefined behaviour because 99 lies outside that enum's range. An enum without a fixed underlying type has a range derived from its enumerators, which need not equal the implementation's storage-type range. Validate before casting; the enum conversion rules distinguish these cases.

constexpr and consteval: when must a value be known?

A const variable cannot be reassigned but can be initialized from runtime input. A constexpr variable must have a constant-expression initializer and is const. A constexpr function can run during constant evaluation or at runtime; the keyword does not force every call to happen during compilation.

C++20 consteval declares an immediate function. An ordinary call must produce a constant expression; calls inside another immediate function can defer that obligation until the enclosing invocation. static_assert checks a constant condition during compilation. constexpr and consteval functions are implicitly inline.

With no arguments this prints fixed 6, runtime 6. In C++17 use a constexpr function and require evaluation at each relevant call site with a constexpr variable or static_assert; there is no consteval declaration. C++20 constinit instead requires static initialization for a static or thread-storage variable and permits later mutation. It implies neither constness nor synchronization. The distinctions follow the constexpr declaration rules.

Namespaces, static, inline and extern: which object is shared?

A namespace groups names, as in tandem::workers; using namespace changes name lookup, not ownership. Avoid broad using-directives in headers because they affect every includer. An anonymous namespace gives its names internal linkage, keeping helpers local to one translation unit.

Spelling in ordinary source and headersMeaningConcurrency consequence
Namespace static int n;Internal linkage; a separate object in each translation unit defining itHeader-level static std::mutex m; can give callers different locks
Function-local static T value = make();Persistent object; dynamic initialization occurs on first passage and concurrent callers waitInitialization is safe since C++11; later access is not automatically protected
extern int n;Declaration referring to an externally linked object defined elsewhereOne shared object, still needing synchronization
inline int n = 0; (C++17)Matching header definitions denote one externally linked objectUseful for a single shared header-defined mutex or counter

extern int n = 3; is a definition because it has an initializer. For an ordinary non-inline variable, put extern int n; in the header and int n = 3; in one source file. Linkage is separate from how long storage exists.

This prints first 3, second 3: the local static remembers its initial value. Configuration changes only on the main thread here; concurrent access would need synchronization. A function-local static retries initialization after an exception; recursively re-entering its own initialization is undefined behaviour.

Static storage does not mean every constructor runs during compilation. Static initialization is constant initialization when applicable, otherwise zero initialization; dynamic initialization can follow. Ordinary namespace objects in separate source files have no general dependency order you can rely on. Use construction on first use for a runtime dependency, or constinit when static initialization is possible; object lifetime covers startup and shutdown dependencies.

The inline rules make a local static inside one external-linkage inline function a single shared object across translation units. An anonymous namespace instead makes a separate function and local static per translation unit. Do not put a program-wide lock there. See how C++ becomes a running program for linker mechanics, and double-checked locking and lazy initialization for safe lazy construction.

Static class members and friend: access is not synchronization

A static data member belongs to the class, not each instance. A static member function has no this, so it needs an explicit object to access instance data. Before C++17, an ordinary static data member typically needs an out-of-class definition; C++17 inline static permits the definition inside the class. A static constexpr data member is implicitly inline since C++17.

For example, declare static int total_; inside the class and define int Counter::total_ = 0; in one source file. The definition does not repeat static. The same rule applies to a static mutex: a declaration alone is not storage for an object you use.

A friend function or class can access private and protected members of the granting class. A friend function is not thereby a member; friendship is neither reciprocal, inherited nor transitive. Friendship grants access, not permission to ignore invariants or locks.

This prints 1000 1000 2000. Separate instance mutexes would not protect the shared total_. One mutex protects the combined update; splitting locks or using atomics belongs in invariants and critical sections and lock granularity.

The deleted copy operations also prevent implicit move operations here. Because the mutex is static, it would not itself stop the compiler generating memberwise copies of local_; those accesses would bypass the lock and could race with add(). This example rejects copying and moving; copy and move semantics explains how to choose those operations deliberately.

Common mistakes

  • Casting to silence a warning. Prove the value range, actual object type and lifetime first.
  • Widening the destination only. Widen an operand before multiplication; an overflowing int expression is already broken.
  • Unsigned reverse indexing. Test before subtracting or use reverse iterators. Zero minus one is a huge unsigned number.
  • Replacing all parentheses with braces. std::vector<int>{3} stores one value, not three elements.
  • Trusting an enum cast to validate input. Check the allowed values before conversion.
  • Calling static state thread-safe. Initialization guards construction only. inline, static and friend do not guard later operations.

In the interview

Expect code reading: "Why did a negative capacity pass?", "What changes if I replace parentheses with braces?", or "Both methods lock; why is the global total still racy?" Name the expression type and the shared object before proposing a fix.

I validate the signed input before converting it. I use parentheses for a vector's element count, and I keep that count bounded so any narrower API result is representable.
A static member is shared by all instances, so per-instance locks do not protect it. I need one shared lock for that invariant, or an atomic operation when the invariant really is only one counter.

Follow ups: checked versus unchecked downcasts, why constexpr functions can execute at runtime, and why a header static mutex differs from an inline mutex. Answer with a rule and a tiny counterexample.

Key takeaways

  • Use explicit construction for semantic types and named casts with a stated range or object-type argument.
  • Arithmetic uses promoted operand types. Signed overflow is undefined; unsigned wrap is defined but can break invariants.
  • Validate sizes before casting. Braces reject narrowing but can select an initializer-list constructor.
  • enum class separates domains; constexpr permits constant evaluation and consteval requires it at ordinary calls.
  • Linkage decides whether source files share an entity. Static class members are shared across instances; their synchronization must be shared too.
  • Compile-time checks, access control and thread safety are separate properties.

Quick check

Answer each question, then read why. Your score is saved for your module test.

With std::vector<int> a{3}; std::vector<int> b(3); auto x{3}; auto y = {3};, which statement is correct?
Why. The vector's initializer-list constructor makes a contain just 3, while the count constructor makes b contain three value-initialized integers, all zero. Direct-list auto with one element is valid and deduces int; copy-list auto deduces std::initializer_list<int>. Neither swapping the vectors' meanings nor giving both auto variables the same type is correct.
On a target with 32-bit int and 64-bit long long, what does long long n = 50000 * 50000; guarantee?
Why. Both operands are int, so the multiplication happens in int. Use 1LL * 50000 * 50000. A wide destination cannot repair overflow, and compilers need not reject every overflowing runtime expression.
For int a = -1; unsigned int b = 1;, what does std::cout << std::boolalpha << (a < b); print?
Why. The types have equal rank, so the common type is unsigned int. Converting -1 to that type yields its largest value, which is not less than 1. The conversion is defined, and no thread schedule is involved. std::cmp_less(a, b) in C++20 would instead preserve the mathematical comparison and return true.
A live Base& actually refers to Other, which is not a Derived. Base has a virtual destructor and both derived classes publicly inherit it. What happens with dynamic_cast<Derived&>(base)?
Why. Runtime reference-cast failure throws because references have no null failure value. A pointer cast would return null. Replacing it with static_cast removes the runtime check and would make this wrong downcast undefined.
Which declarations are valid C++20? Assume struct Count { explicit Count(int) {} };. Select all that apply.Select all that apply
Why. Direct-list construction considers explicit constructors. Copy initialization and copy-list initialization cannot use this explicit constructor. Floating-to-integer list initialization narrows even for 3.0; the integer constant 42 is representable as unsigned char.
Given constexpr int twice(int x) { return 2 * x; } and consteval int fixed(int x) { return 2 * x; }, a small positive int n is read from input. Which is valid?
Why. A constexpr function can execute at runtime, and const does not require a constant-expression initializer. A constexpr variable requires one, and an ordinary consteval invocation requires constant evaluation.
An ordinary header declares extern int total; and defines static std::mutex m;. Two source files each lock their own m before incrementing the one separately defined total. Is the total protected?
Why. Namespace static gives internal linkage. Both threads can hold their respective locks while writing the same total. extern declares the shared total; it does not copy it. A common lock must protect common state.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A queue constructor takes int requested, initializes std::size_t capacity_ = requested, and constructs std::vector<int> slots_{requested}. Its body rejects only capacity_ == 0. Explain the independent bugs and repair the boundary.
Model answer

A negative requested value becomes a huge unsigned capacity, so checking only zero misses it. The vector braces create one element containing requested, not requested slots. Validate the original signed input for positivity, representability and an application maximum before allocation.

Declare capacity_ before slots_, then use capacity_(checked_capacity(requested)), slots_(capacity_) in the constructor initializer list, with the checked function from the worked example. Returning the size as int also needs a representability proof. These requirements precede synchronization.

Explain
You receive a base pointer to a task, a const view of configuration and a pointer to packet bytes. When would each cast be justified, and which safety questions remain?
Model answer

For an uncertain live polymorphic task, use dynamic_cast and handle null, or put the behaviour on its virtual interface. A static downcast needs a proven dynamic type and permitted inheritance relationship. A numeric static_cast needs a range argument and may lose precision.

const_cast changes qualification; writing requires a suitably mutable original object and synchronization. reinterpret_cast does not turn packet bytes into a constructed, aligned target object. Parse fields or use a representation-copy mechanism with its constraints. Prove lifetime and synchronization independently of every cast.

Design
A header defines inline Registry& registry() { static Registry r; return r; }. Registry has a mutable map. What is shared across translation units, what do concurrent first callers receive, and what must the methods still do?
Model answer

With external linkage and matching definitions, this is one inline function with one local static Registry across translation units. One caller performs dynamic initialization and concurrent callers wait. A thrown initialization is retried on a later call. An anonymous namespace around the function instead gives each translation unit its own function and Registry.

After initialization, conflicting map access still needs synchronization. Use a member mutex, RAII guards and a clear invariant, or an immutable design. Thread-safe construction does not make the returned object thread-safe.

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

"The queue has locks everywhere, but passing minus one as its capacity gets past validation. Walk me through what you check."
What a strong answer covers
  • Check the signed input before any unsigned conversion or allocation
  • Explain that conversion to size_t turns minus one into a huge positive value
  • Check range and application maximum, then convert once
  • Distinguish vector count construction with parentheses from initializer-list construction with braces
  • Separate arithmetic and initialization correctness from locking
How a senior would say it
I check the type boundary first. Locks cannot repair a capacity that was converted incorrectly. If the constructor receives a signed integer and stores it in size_t, minus one becomes a huge unsigned value. A later test that the capacity is positive accepts it. I validate the original input for positivity, representability and our application limit before converting or allocating. Then I convert once and use that validated value consistently. I also inspect the vector initializer. Parentheses with three create three elements; braces with three create one element containing three. That can leave the capacity field disagreeing with the storage even for valid input. Finally, I test negative, zero, maximum and just-too-large capacities. Once those sequential invariants hold, I examine the locking around queue operations. The conversion rule and the synchronization rule need separate proofs.

Likely follow up: What changes if the API must return the queue size as an int?

"You see a static cast from a task base pointer to a concrete task. Would you keep it, replace it, or redesign the interface?"
What a strong answer covers
  • Keep a static downcast only with a proven dynamic type and valid inheritance relationship
  • Use dynamic_cast for an uncertain live polymorphic object and handle pointer or reference failure
  • Prefer virtual dispatch when the operation belongs on the interface
  • Explain why reinterpret_cast and const_cast do not solve a dynamic-type mismatch

How a senior would say it
I would keep it only if the surrounding design proves the concrete type and the inheritance relationship permits that downcast. A static cast does no runtime type check, so the wrong object makes the downcast undefined. If the type is uncertain, I use dynamic cast through a polymorphic base and handle failure. A pointer cast returns null; a reference cast throws bad cast. If every task supports the operation, I would instead put it on the virtual interface and avoid type tests at each caller. Reinterpret cast does not repair a wrong dynamic type, and const cast only changes qualification. I also check who owns the task and whether another thread can destroy or mutate it. Even a successful checked cast does not keep the object alive or synchronize access. Those are separate responsibilities of the task handoff.

Likely follow up: Why might a static downcast be rejected even when you know the concrete type?

Out loudabout 60 s
"Two source files both lock a mutex from the same header, yet updates still race. What declaration would you look for?"
What a strong answer covers
  • Look for namespace static or an anonymous namespace creating one mutex per translation unit
  • Explain why identical spelling does not imply the same lock
  • Use an extern declaration with one definition, or an external-linkage inline variable since C++17
  • Distinguish class static shared state from instance state and match the lock to it
  • Explain that safe local-static initialization does not protect subsequent mutation
How a senior would say it
I look for a namespace static mutex or a mutex in an anonymous namespace in the header. Each translation unit then gets its own object. Both threads can hold their locks simultaneously, so identical spelling does not establish mutual exclusion around shared data. I would declare the mutex extern in the header and define it in one source file, or use an external-linkage inline variable in C++17 or later. I then check that every conflicting access uses that same mutex. The related class bug is a static counter protected by separate instance mutexes. The counter is shared across instances, so its protection must be shared too. Finally, if the object comes from a function-local static, only initialization is automatically coordinated. Later map changes or counter updates still need synchronization. I verify the lock's identity as well as its presence.
