The toolkit: volatile and the atomic classes

Choose visibility, conditional atomic updates, striped counters or stamped references, and know exactly which operations each Java API makes indivisible.

Asked atGoogleMicrosoft
Before this:final, immutability and recordsLambdas, functional interfaces and method referencesThe toolkit: Thread, Runnable, Callable and virtual threads

A flag that everyone can see, a counter that never loses an increment, and a reservation that only one caller wins need different guarantees. Java gives you compact tools for each, provided you identify exactly what must happen as one operation.

In plain words

A station displays whether a ticket counter is open. Making that sign visible to everyone does not stop two clerks from selling the last ticket. For that, you need a machine that checks the remaining stock and changes it in one indivisible action.

A visitor tally has a different job: several doors can keep separate counts and add them for a report. That is efficient, but the report is a poor way to decide who gets the last seat. Pick the tool from the promise you must keep.

Why this matters for concurrency

You will use volatile for publication, AtomicBoolean for one winner, numeric atomics for exact transitions, and AtomicReference for state replacement. Metrics and reusable nodes need additional choices. In an LLD round, keep these objects private and expose operations such as tryReserve, so callers cannot split your invariant across separate calls.

The recipes for immutable objects and lambdas are already in immutability and records and functional interfaces. Here the question is what happens when several callers use those objects at once.

What volatile guarantees

A Java volatile field gives visibility and ordering: a write to it happens-before subsequent reads of that same field in the synchronization order. Earlier writes by the publisher therefore become visible to a reader after that reader observes the publication. This is a memory model contract, not a claim that every access travels to RAM.

Individual volatile reads and writes are atomic; compound operations are not. This includes individual long and double accesses, whose plain versions the language permits to tear. But count += 1 still reads, computes and writes separately: two callers can both read 5 and both write 6. The Java memory model defines the ordering; the lost update drills the interleavings.

volatile applies to instance or static fields, not local variables, and a field cannot be both final and volatile. A volatile reference publishes a reference and preceding initialization; it does not synchronize later mutations of the referenced object. For example, volatile int[] slots does not make slots[0] += 1 atomic.

A single CPU core does not remove these requirements. Threads can be preempted between the read and write of an increment, and the JIT can reuse an unsynchronized value rather than reread it. Core count changes the hardware execution, not the Java memory model contract.

The reader must see 42: the payload write precedes the volatile write, and the payload read follows the volatile read that sees true. The final join() lets main inspect the reader's result; it does not supply the publisher-to-reader edge. This is a one-time handoff with no later payload writes, not a reusable mailbox.

Spinning here makes the handoff visible in a tiny program. onSpinWait() is only a processor hint, and neither it nor a flag wakes a thread blocked in a queue or I/O. Use the cancellation tools in the threads toolkit and blocking coordination in the monitor toolkit; the full proof is in happens-before and safe publication.

API card: single values

An atomic variable packages a value with operations on that value. The following classes live in java.util.concurrent.atomic. Keep the holder private final: its reference stays fixed while its contained value changes. An extra volatile on that holder field is unnecessary when the containing object is safely published.

AtomicBoolean has no arithmetic or functional update methods. AtomicReference<Integer> has no increment method and compares boxed objects by identity; use AtomicInteger for a number. These are mutable holders, not value objects: compare get() results when you mean value equality. The atomic package API describes the type boundaries.

Old value versus new value

compareAndExchange returns a witness value: the value observed at its atomic comparison. A witness equal to the expectation means success; otherwise the method returns the conflicting value without replacing it. Above, the first exchange returns 30 and installs 40; the second returns 40 and leaves it unchanged. For references, compare witness and expectation with ==.

getAndIncrement() is useful when the current sequence number belongs to this caller; incrementAndGet() returns the new count. Each call has one linearization point, an instant at which it takes effect, although another thread may change the value before this caller uses its result. Atomic arithmetic still overflows like ordinary integer arithmetic, so a sequence generator needs a wraparound policy. See the AtomicLong API.

Update functions must be side-effect-free. A functional update can retry its computation after interference. updateAndGet(x -> { chargeCard(); return x + 1; }) can charge more than once; mutating a list inside an AtomicReference callback can corrupt shared state before any successful update. Compute a candidate from the input and return it; do external work outside the retry, with a separate failure policy. Numeric functions use IntUnaryOperator or LongUnaryOperator; reference functions use UnaryOperator<T>, and the two-argument forms use the corresponding binary operator. See AtomicInteger's update contract.

AtomicBoolean: select one winner

Compare-and-set (CAS) checks and replaces in one atomic operation. Strong compareAndSet does not fail spuriously: false means the expected value did not match at the comparison. A separate get() followed by set() leaves a gap in which another caller can win too.

Default strong CAS reads with volatile semantics and, on success, writes with volatile semantics. It can therefore publish preceding state as well as perform a conditional change. The deeper mechanism is in atomic variables and CAS.

The successful CAS claims the action; it does not announce that later work finished. If the winner starts initialization after setting the flag, a loser cannot use claimed.get() == true as proof of completion. For a result that others await, including initialization failure, use a future. The AtomicBoolean API protects the flag, not the whole lifecycle.

AtomicReference: compare identities, replace state

compareAndSet on a reference uses ==, not equals. Read the actual expected object from the holder; do not reconstruct an equal object. A successful replacement publishes the new object's preceding initialization, but does not make a mutable object returned by get() thread-safe.

For multiple related fields, put them in one immutable state object and replace its reference; readers take one get() and use that snapshot. The existing snapshot example implements this with updateAndGet. Here the new rule is the identity comparison contract; separate atomic fields cannot make a pair of changes indivisible.

Conditional updates need a retry

Worked example: sell only available stock

Stock starts at 100. if (remaining.get() > 0) remaining.decrementAndGet() is unsafe: two buyers can both observe 1. Instead, validate a snapshot and replace it only if it is still current. If CAS fails, read and validate again.

The rejection takes effect at the read that found insufficient stock. No arithmetic can make stock negative because quantity is positive and no greater than that snapshot. sold is a test tally checked after all joins; it is not an atomically updated inventory ledger.

If stock must change with a mutable order list, use one lock or replace one immutable aggregate. If callers must wait, use locks and conditions or a suitable synchronizer. With continuously changing state, a CAS loop can retry without a bound and gives no individual fairness promise; deepen the reasoning in CAS loops and progress guarantees.

API card: counters for statistics

TypeMain methodsOne-line semantics
LongAdderincrement(), decrement(), add(delta)Accumulate a sum across internal cells; updates return no sequence number.
LongAddersum()Combine the cells, without promising one atomic snapshot during updates.
LongAdderreset(), sumThenReset()Clear to zero, optionally returning the sum; coordinate with writers for an exact interval.

LongAccumulatorget(), reset(), getThenReset()Read the aggregate or restore the identity, with the same concurrent snapshot caveats.

LongAdder can reduce update contention by distributing writes across cells, at a memory and aggregation cost. sum() is exact when no updates overlap, as after joining all writers; during updates it need not represent one instant. It is appropriate for telemetry, not ticket numbers, a strict capacity check, or a completion signal. reset() and sumThenReset() are not exact window boundaries with concurrent writers. See the LongAdder contract and counters at scale.

LongAccumulator generalizes that approach. Use a side-effect-free, associative and commutative function with a proper identity: sum with 0, maximum with Long.MIN_VALUE, minimum with Long.MAX_VALUE. Subtraction is unsuitable because grouping and order change the result. For a maximum of negative inputs, identity 0 silently produces the wrong answer. See the LongAccumulator contract.

API card: a reference with a version

The ABA problem is a stale expectation that appears current again: a reference changes from A to B to the same A. Ordinary CAS accepts A without discovering that history. Java's garbage collector keeps a referenced object alive, but your algorithm can still remove and reinsert that same object.

TypeMain methodsOne-line semantics
AtomicStampedReference<T>new AtomicStampedReference<>(ref, stamp)Store a reference and integer stamp as one atomic pair.
AtomicStampedReference<T>get(int[] holder)Return the reference and put its matching stamp in holder[0].
AtomicStampedReference<T>getReference(), getStamp()Read either component; two separate calls do not make a pair snapshot.
AtomicStampedReference<T>compareAndSet(oldRef, newRef, oldStamp, newStamp)Replace both only when reference identity and stamp both match.
AtomicStampedReference<T>set(ref, stamp)Unconditionally replace the pair; no automatic stamp increment.

With AtomicStampedReference, every relevant transition must advance the stamp under your protocol. A stale (A, 0) then fails against (A, 2). Stamps can wrap or be reused, so they are not an unlimited history guarantee. Keep the stamp holder local to the reading thread. See the stamped reference API.

This sequential replay checks the API decisions at each point in a possible thread interleaving. A version matters only if intervening changes invalidate the planned operation; ordinary counters do not automatically need stamps. The structural failure and full stack algorithm belong in the lock-free stack and ABA lesson.

Atomic arrays protect individual slots, not a whole traversal or a transfer between indices. A plain AtomicInteger[] instead stores references to separately allocated holders; each must be initialized, and replacing an array slot needs its own synchronization. Atomic array storage does not eliminate contention between nearby elements; see false sharing and the array API.

The three arrays are independent. While visitors run, you may see a visit count before its bytes or claimant update; the assertions compare them only after both joins. The first claimant is the first successful reference CAS, which need not be the caller that incremented visits first.

VarHandle and weaker access modes

VarHandle, in java.lang.invoke since Java 9, accesses fields or array elements without an atomic wrapper per value. Use MethodHandles.Lookup.findVarHandle for an instance field, findStaticVarHandle for a static field, or MethodHandles.arrayElementVarHandle for an array. The selected mode controls ordering even when the field is declared volatile. Unsupported operations, such as updating a final field, throw UnsupportedOperationException.

VarHandle modesOrdering contract
get, setPlain access, with no publication ordering; plain long and double accesses may tear.
getOpaque, setOpaqueAtomic access with coherence for this variable, but no publication of other fields.
getAcquire, setReleaseA read observing the release orders the writer's preceding accesses before the reader's subsequent accesses.
getVolatile, setVolatileAcquire/release guarantees plus a total order among volatile accesses.

The four scalar atomic classes also offer these weaker modes, naming plain access getPlain() and setPlain(value). Their lazySet(value) is a release write: it can publish prior initialization to a matching acquire or volatile read, but promises no fixed propagation delay. Use ordinary get, set and strong CAS unless you can prove the weaker protocol. See the VarHandle specification and the core memory model connection.

Spurious failure and memory ordering are separate choices. Scalar atomics have weakCompareAndSetPlain, weakCompareAndSetAcquire, weakCompareAndSetRelease and weakCompareAndSetVolatile; all may fail even when the expected value matches. Their old weakCompareAndSet is deprecated because it has plain semantics. In contrast, VarHandle.weakCompareAndSet has volatile semantics. A weak CAS failure therefore cannot by itself prove that another thread changed the value; retry and revalidate.

Common mistakes

  • Calling set(get() + 1) an atomic increment. Use incrementAndGet(); separate safe methods do not create a safe sequence.
  • Retrying CAS with an unchanged expectation forever. Reload and revalidate after a failure; the previous state may never return.
  • Doing I/O or mutating shared objects in an update function. Retried computation must be harmless, and failed CAS does not roll back side effects.
  • Using a claimed flag as a completed flag. Publish completion after the work, or use a future that represents its result or failure.
  • Replacing a strict limit with LongAdder. A statistical aggregate cannot combine the admission check and reservation.
  • Declaring every field atomic and calling the class thread-safe. Write down the invariant, including related fields, arrays and external effects; protect the whole transition.
  • Expecting synchronized (counter) to exclude atomic operations. A caller of counter.incrementAndGet() does not acquire that monitor. A compound operation protected by a lock requires every conflicting operation to follow the same locking protocol.

In the interview

A reported Google L5 Java round in the research used concurrent per-user counters; a Microsoft senior round probed volatile behaviour across core counts. The useful answer explains the guarantee before naming the class. The class design walkthrough applies that approach end to end.

I use volatile for publication or an independently assigned flag. I use a strong atomic operation when a read and update must happen together. For a conditional reservation I retry CAS and recheck the condition; for several mutable structures I prefer one lock. LongAdder is for statistics whose read need not be an atomic snapshot.

Expect follow ups about overflow, retry side effects, reference identity, failure after claiming work, and ABA. Explain how you would test each boundary; never offer a benchmark result you have not measured.

Senior depth

AtomicMarkableReference pairs a reference with a boolean, often meaning logically deleted. Its get(boolean[] holder) reads both components together, and compareAndSet(oldRef, newRef, oldMark, newMark) compares both. Unlike a version counter, a mark has only two values: resetting it while reusing the same reference can admit ABA again. See the markable reference API.

Older libraries may use atomic field updaters: AtomicIntegerFieldUpdater, AtomicLongFieldUpdater or AtomicReferenceFieldUpdater. These update a selected volatile instance field without a holder per object, checking field type and accessibility during setup. Keep competing updates on the same updater: its contract does not promise atomicity against arbitrary direct field writes. For new low-level code, consider VarHandle; for an interview, prefer the simpler holder unless allocation matters. See the field updater contract.

Key takeaways

  • volatile orders publication and makes individual accesses atomic, but does not make compound updates indivisible.
  • Read the return-value contract: getAnd... returns the old value; ...AndGet returns the new value.
  • CAS checks and changes together; retries need fresh validation and side-effect-free computation.
  • AtomicReference compares identity and protects the reference; immutable state gives readers a consistent aggregate.
  • LongAdder and LongAccumulator scale statistical updates by giving up an atomic aggregate snapshot during writes.
  • Stamped references detect version changes under a disciplined protocol; atomic arrays protect one index at a time.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Initially int data = 0 and volatile boolean ready = false. One writer runs data = 42; ready = true; once. A reader runs if (ready) System.out.println(data);. There are no other writes. What can it print?
Why. Seeing true supplies the happens-before edge for the preceding data write. Seeing false skips printing. A volatile read does not wait for a future write, but once this publication is observed, 0 is forbidden.
With no other threads, AtomicInteger n = new AtomicInteger(4); int a = n.getAndIncrement(); int b = n.incrementAndGet(); int c = n.accumulateAndGet(3, (x, y) -> x * y);. What are a, b, c?
Why. The first call returns 4 and stores 5. The second stores and returns 6. Accumulation computes the function with current value 6 and supplied value 3, stores 18 and returns it.
A developer increments an audit counter inside value.updateAndGet(x -> { audits.incrementAndGet(); return x + 1; }). All holders are atomic. What is wrong?
Why. The method accepts a lambda, but atomicity applies to installing the new value. The function may run again after interference; its effects on another object are not rolled back. No shared lock protects both counters, and independent atomics do not make the callback transactional.
AtomicReference<String> r = new AtomicReference<>(new String("A")); is untouched by other threads. What does r.compareAndSet(new String("A"), "B") return?
Why. Reference CAS uses ==, and the two new String expressions create different objects. Strong CAS has no spurious failure; immutability permits sharing but does not change identity comparison.
Two threads call if (!started.get()) { started.set(true); launch(); } on one initially false AtomicBoolean. Which statement is correct?
Why. Both callers may read false before either writes true, so both may launch. If one finishes setting the flag before the other reads it, only one launches, so two launches are not inevitable. Making the holder reference volatile does not combine its separate method calls. CAS closes the gap, but a successful claim still does not tell other callers that launch() has completed.
Which statements about striped statistics are correct? Select all that apply.Select all that apply
Why. A quiescent sum is exact, and the smallest long is the identity for maximum. Concurrent collection and resetting are not one global boundary. Subtraction is neither associative nor commutative, so distributing and regrouping it changes the result.
One thread executes array.set(0, 10); array.set(1, 20); on an AtomicIntegerArray. Can another thread observe 10 at index 0 and the old value at index 1?
Why. A reader can run between the two stores. Neither constructor choice nor volatile semantics locks all indices or creates a transaction across elements. Use an immutable whole-state replacement or a lock for that invariant.

Checkpoint

Debug
A service writes if (permits.get() > 0) { permits.decrementAndGet(); return true; } return false;. Give a failing interleaving and a corrected Java method. Assume a private AtomicInteger permits starts nonnegative and no other code writes it.
Model answer

With one permit left, A reads 1 and B reads 1. Both decrement, producing 0 and then negative 1, and both return true. The condition must be part of the same atomic transition as the decrement:

The invariant is nonnegative permits. A successful CAS reserves one; a failed CAS rereads and rechecks. This API rejects immediately when empty; it is not a blocking semaphore.

Explain
A stamped reference holds (A, 8). You read it, another thread changes it to (B, 9) and then (A, 10), and you attempt a replacement using your old snapshot. What must you read together, and why does the replacement fail?
Model answer

Use a thread-local int[1] and get(holder) to read reference A and stamp 8 from the same pair. Separate getReference() and getStamp() calls could observe different updates. compareAndSet(A, next, 8, 9) fails against (A, 10) because both identity and stamp must match. Ordinary reference CAS could accept A despite the intervening changes. Every relevant update must advance the version, and wraparound or deliberately restoring stamp 8 can reintroduce the problem.

Design
Choose primitives for three requirements: a cumulative request metric under contention, unique in-process sequence numbers, and a lower/upper bound pair that must always satisfy lower <= upper. Explain the read contract of each.
Model answer

For a metric, use LongAdder if a concurrent read may be a non-atomic aggregate; it is exact after updates stop. Use AtomicLong.getAndIncrement() for sequence numbers, returning a distinct old value per call until wraparound, with a defined exhaustion policy. It is not a distributed or persistent ID generator.

For bounds, use one immutable Bounds object in AtomicReference, validate a candidate against the observed state, and CAS the whole replacement with retry. Readers call get() once and inspect both components of that object. Two independent atomics permit a mixed pair that never existed. A shared lock around both reads and writes is also correct and may be simpler if the state is larger or mutable.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Why would a volatile stop flag work, but a volatile request counter still lose updates?"
What a strong answer covers
  • A stop flag needs visibility of an independent assignment; an increment needs an indivisible read-modify-write
  • A volatile write happens-before subsequent reads of that same field, ordering preceding writes too
  • Two increments can both read 5 and both write 6 despite individually atomic accesses
  • Choose an atomic increment for an exact counter, or LongAdder for a statistical aggregate
  • A flag does not wake blocked work and does not replace interruption or blocking coordination
How a senior would say it
A volatile flag can publish a stop request, but it cannot make a counter increment indivisible. An assignment and an increment need different guarantees. A volatile write happens-before subsequent reads of that field, which also orders the writer's preceding changes. So a worker that checks the flag can observe the request without an explicit lock. An increment still reads, adds one, and writes. Two threads can both read five and both write six, losing one request even though each access is atomic. For an exact counter I would use an atomic increment. For a heavily updated metric, LongAdder may be suitable if its aggregate read contract is acceptable. Finally, a stop flag only helps a worker that checks it. It does not wake a blocked queue operation, so cancellation may also need interruption or an explicit shutdown protocol.

Likely follow up: What changes if the flag is set before initialization starts, and readers treat it as ready?

Out loudabout 75 s
"Walk me through a Java reservation that uses CAS, and tell me where you would put the payment call."
What a strong answer covers
  • Read available stock, reject insufficient stock, compute the candidate, then compareAndSet
  • A successful CAS is the reservation's linearization point
  • After failure, reload and revalidate; two buyers for one unit cannot both succeed
  • Keep payment out of the retry computation because retries may repeat side effects
  • Handle failure after reservation with an explicit lifecycle; CAS alone does not give payment exactly once
  • Prefer a lock or one immutable aggregate when the invariant spans additional state
How a senior would say it
I would reserve with a CAS loop and keep payment outside the retried computation. First I read the available stock, reject an invalid quantity or insufficient stock, and compute the reduced value. I compare and set from the exact value I read to that candidate. Success is the instant the reservation takes effect. On failure, I read again and repeat the check. With one unit left, two buyers may both read one, but only one can change one to zero. The loser rereads zero and rejects. I would not call payment inside an update function or retry loop, because a retry could charge again. After a successful reservation, payment needs its own explicit lifecycle: record the reservation, attempt an idempotent payment, and define confirmation or release on failure. A process crash between those steps needs recovery; the atomic integer cannot solve that. If the reservation also changes a mutable order list, I would protect both with one lock or replace one immutable aggregate. The primitive must cover the business invariant, not just the number.

Likely follow up: If the reservation state returns to the same object while payment is pending, how would you reject a stale completion?

Out loudabout 60 s
"My CAS succeeds even though another thread removed and reinserted the same node. What is happening, and does Java's garbage collector fix it?"
What a strong answer covers
  • Name ABA: A changes to B and back to the same A, so ordinary identity CAS accepts it
  • GC prevents reclaiming a referenced object but not reuse of that same live node by the algorithm
  • Read reference and stamp together with AtomicStampedReference.get(holder)
  • Advance the stamp on each relevant transition and compare both identity and stamp
  • Stamp reuse or wraparound can defeat the protection; a version is a protocol, not automatic history
How a senior would say it
That is ABA: the reference changed from A to B and back to the same A, so an ordinary CAS cannot detect the intervening changes. Java's garbage collector keeps an object alive while it is still referenced, but your algorithm can remove and reinsert that same live node. If that history invalidates the pending operation, I would attach a version. AtomicStampedReference stores the reference and an integer stamp together. I read both using get with a local stamp holder, then compare and set both expected components. If another thread changes A at stamp zero to B at one and A at two, my old expectation fails. Every relevant writer must advance the stamp; the class does not do it automatically. I would also address stamp reuse and wraparound, because seeing the same reference and stamp again defeats the check.

Likely follow up: Why is calling getReference() and then getStamp() insufficient for taking the initial snapshot?
