OA set 3: wakeups, callbacks and orderings

Lost wakeups, exceptions inside tasks, interrupts, callback deadlocks, store buffering and pool starvation, plus queueing and LRU numbers.

Set 3 is where OA questions start to need a careful trace: which thread is waiting when the notify fires, which lock a callback takes, and which results a memory model allows. Work each one through before you pick.

12 questions, 15 minutes. Answers and explanations stay hidden until you submit or the clock runs out. Multi answer questions say so; pick every option that is true.

Java onlyWhat does this program print?
Why. Main calls notify() while holding the correct monitor, but no thread is waiting yet, so that notification has no effect. The later bare wait() may remain blocked forever, and join() then prevents both prints. Java also permits a spurious wakeup: if wait() returns that way, the worker prints woke, terminates, and main prints done. Thus neither a hang nor those two lines is guaranteed. The fix is remembered state: set signaled = true under lock before notifying, and wait with while (!signaled) lock.wait(); under the same lock. join() waits for termination, not merely for a thread to enter a waiting state.
C++ onlyWhat does this program print?
Why. The early notify_one() has no waiting thread to wake and stores no notification for a later waiter. The bare cv.wait(lk) can therefore stay blocked forever, leaving main blocked in join(). It may also return spuriously, in which case the worker prints woke and main later prints done. Calling notify_one() without holding m is legal. To remember that work is ready, set a bool signaled under m and use cv.wait(lk, [] { return signaled; });; the predicate handles both an early notification and a spurious return from the underlying wait.
Java onlyWhat appears on the console?
Why. submit wraps the task in a FutureTask, which catches the exception and stores it in the future. Nothing is printed when the task fails; get() later throws ExecutionException with the original exception as its cause (a real run printed exactly these two lines). If nobody calls get(), the failure is silently lost, a common production bug. execute behaves differently: the exception reaches the worker thread's uncaught exception handler, which prints a stack trace, and the pool replaces the dead worker.
C++ onlyWhat appears on the console?
Why. std::async catches whatever the task throws and stores it in the future's shared state, just like a returned value; get() rethrows the same exception, so the std::runtime_error handler runs (a real run printed exactly these two lines). The terminate trap belongs to a plain std::thread: an exception escaping its function calls std::terminate. std::promise::set_exception and std::packaged_task use the same mechanism as std::async.
x and y start at 0. Thread 1 runs x = 1; r1 = y; and thread 2 runs y = 1; r2 = x;. Both variables are Java volatile fields, or C++ std::atomic<int> used with the default memory order. Which results are possible?Select all that apply
Why. Java volatile accesses and the C++ default seq_cst atomic accesses fit into a total order consistent with these threads' program order. For both reads to return 0, that order would require write x before read y before write y before read x before write x, a cycle. The other outcomes have witnesses: finishing thread 1 first gives (0, 1), finishing thread 2 first gives (1, 0), and doing both writes before either read gives (1, 1). Java plain fields can allow (0, 0); C++ plain shared ints instead create data races and undefined behavior. C++ release stores and acquire loads also allow (0, 0) when both loads read the initial values, because neither then synchronizes with the other thread's store.
Java onlyThe cache is registered with the bus (bus.register(cache)). Which statements are true? Select all that apply
Why. publish holds the bus lock and then needs the cache lock (inside onEvent); refresh holds the cache lock and then needs the bus lock. Two threads can each hold one and wait for the other, and a real run with short pauses inside the methods stayed deadlocked. A single thread is fine because it already owns the cache monitor when onEvent asks for it again. Reentrancy only helps the thread that already holds a lock, never a second thread. The cure is open calls: never call unknown code (listeners, callbacks) while holding a lock.
C++ onlyThe cache is subscribed to the bus (bus.subscribe(&cache)). Which statements are true? Select all that apply
Why. Two threads can form a lock cycle: publish holds the bus mutex and requests the cache mutex, while refresh holds the cache mutex and requests the bus mutex. Even one refresh call is invalid: its callback into on_event tries to acquire the same non-recursive cache mutex again. That is undefined behavior; self-deadlock is a common symptom, not a guaranteed outcome. The proposed open calls remove both nested acquisitions: copy the listener list under the bus lock and update the version under the cache lock, then release those locks before making callbacks. Merely replacing each one-mutex guard with std::scoped_lock leaves the same nesting and recursive acquisition.

Why. No single output is guaranteed by these sleeps. If interruption makes sleep throw, the exception clears the interrupt flag; the catch prints interrupted and the loop can continue. If the worker remains alive after the timed join, main prints true. Two semaphores start at a = 1 and b = 1. Thread 1 runs three times: acquire a, print A, release b. Thread 2 runs three times: acquire b, print B, release a. Which outputs are possible?Select all that apply
Why. Thread 1's k-th A needs its k-th permit from a; a starts with 1, so for k greater than 1 thread 2 must already have released a k minus 1 times, which means k minus 1 Bs were printed. The same holds the other way round. So neither letter can get two ahead, and after every 2 prints there is exactly one of each: the output is three blocks, each AB or BA, giving 8 possible outputs (a search of every interleaving found exactly those 8). AABBAB starts with two As and BBAABA with two Bs, so both are impossible. With a = 1 and b = 0 the only output is ABABAB, which is the usual ping pong.
A fixed pool of 2 threads (Java newFixedThreadPool(2), or a C++ pool with 2 workers and one shared queue) receives two tasks at once. Each task submits a small subtask to the same pool and then blocks waiting for that subtask's result. What happens?
Why. This is thread starvation deadlock. Both workers are busy running the outer tasks, the two subtasks are queued behind them, and each outer task waits for a subtask that can only run on a free worker. A real Java run hung until it was killed. A plain thread pool does not run queued tasks on a blocked worker; in a ForkJoinPool, ForkJoinTask.join lets the waiting worker run other tasks, which is why fork/join code avoids this. Fixes: never block on tasks of the same bounded pool, use separate pools per stage, or compose asynchronously instead of waiting.
Java onlyThread T2 runs while (!ready) {} and then System.out.println(data);, where data starts at 0 and ready at false. Which writer versions guarantee that T2 eventually prints 42?Select all that apply
Why. Assuming the writer runs and the reader continues to be scheduled, the correct publication order is data = 42 followed by a volatile write of ready = true. The volatile read of ready that observes true establishes a happens-before edge from the earlier data write to T2's later read, so 42 is published whether only ready or both fields are volatile. Writing data after the flag instead allows T2 to print 0. Making only data volatile leaves T2 spinning on a plain flag, so it may never reach the data read. Making neither field volatile supplies no synchronization. Sleeping creates no happens-before edge. Volatile publication guarantees visibility and ordering, not a wall-clock deadline or scheduler fairness.
C++ onlyOne thread runs writer() and another runs reader(). What is true?
Why. Relaxed atomics are atomic but promise nothing about other memory, so the write of data and the read of data are not ordered: a data race. Both the compiler and weakly ordered CPUs such as ARM may move the store of data after the flag. A release store paired with an acquire load that reads the stored value makes everything before the store visible after the load, which is exactly message passing, so seq_cst is not needed. "It works on x86" only describes one CPU, and even there the compiler may reorder.
A single worker serves a queue. Jobs arrive at random at 100 per second, and service times are random with a mean of 8 ms (an M/M/1 queue). On average, how long does a job spend in the system (waiting plus service), and how many jobs are in the system?
Why. Utilization rho = arrival rate x service time = 100 x 0.008 = 0.8. For M/M/1, time in system W = S / (1 minus rho) = 8 / 0.2 = 40 ms. Little's law gives the number in the system: L = arrival rate x W = 100 x 0.040 = 4. The waiting time alone is rho / (1 minus rho) x S = 4 x 8 = 32 ms, with 3.2 jobs in the queue on average, which is the trap answer. At 80 percent busy a job already spends five times its service time in the system.
A process has 3 page frames, all empty at the start. It references pages in this order: 2 3 1 4 3 2 3 2 5 4 2 5. How many page faults happen under LRU replacement?
Why. Trace (frames listed least recently used first): 2 fault [2]; 3 fault [2 3]; 1 fault [2 3 1]; 4 fault, evict 2 [3 1 4]; 3 hit [1 4 3]; 2 fault, evict 1 [4 3 2]; 3 hit [4 2 3]; 2 hit [4 3 2]; 5 fault, evict 4 [3 2 5]; 4 fault, evict 3 [2 5 4]; 2 hit [5 4 2]; 5 hit [4 2 5]. That is 7 faults. FIFO on the same string gives 9 (it evicts 3 just before 3 is used again), and the optimal policy gives 5, so 9 and 5 are what you get with the wrong policy.
A bounded buffer of capacity 1 has one producer and two consumers. All three use a single condition (Java: one monitor with wait and notify; C++: one condition_variable with notify_one), and every wait sits in a while loop that re-checks the buffer. What can go wrong?
Why. Trace it: C1 and C2 find the buffer empty and wait. P puts an item and notifies, waking C1; P tries to put again, finds it full, and waits. C1 takes the item and notifies, but the single condition lets that notify wake C2 instead of P. C1 loops, finds the buffer empty and waits; C2 wakes, finds it empty and waits. Now all three are waiting. The while loops prevent wrong data but not this lost progress. Use notifyAll or notify_all, or better, two conditions (not full and not empty), so a notify always reaches the right kind of thread.
Five philosophers sit at a round table with one fork between each pair; each needs both neighbouring forks to eat. Which strategies prevent deadlock?Select all that apply
Why. Lower number first is a global lock order, so a cycle cannot form (one philosopher ends up reaching right first). With only 4 seated, at least one of them can always get both forks. The waiter grants both forks at once, so nobody holds one fork while waiting for the other. Left then right lets all five take their left fork and wait forever. Retrying tryLock while keeping the left fork is the same hold and wait, only busy: all five can spin forever.
