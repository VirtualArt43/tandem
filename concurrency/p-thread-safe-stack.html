Thread-safe stack

Thread-safe structureswarm-up20 minRubrik onsite system codingRubrik

Rubrik has opened onsite system coding rounds with exactly this: a thread-safe stack on a linked list with O(1) push and pop, written as code that runs. It is the smallest complete exercise in mutual exclusion plus waiting, and the warm-up before the lock-free version.

The task

Build a stack that many threads use at once:

  • push(item) puts an item on top.
  • pop() removes and returns the top item. If the stack is empty, the caller blocks until an item arrives.
  • tryPop() removes and returns the top item, or returns none at once when the stack is empty (null in Java, std::nullopt in C++). It never blocks.
  • size() returns the number of items right now.

Rules: build it on linked nodes, as the Rubrik question asks (Java: a private Node class; C++: nodes owned by std::unique_ptr), so push and pop are O(1). Use one lock and a condition for the waiting; no library concurrent stacks, deques or blocking queues.

What the tests check

  • LIFO order, size() and tryPop() from one thread; tryPop() on an empty stack returns none at once.
  • pop() blocks on an empty stack and wakes up when another thread pushes.
  • Three threads blocked in pop(): one push wakes exactly one of them while the other two keep waiting, and two more pushes wake the other two.
  • A stress run with 4 pushers and 4 poppers (two use pop, two use tryPop): every item comes out exactly once and the stack ends empty.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Mutexes and RAII guards

Open them one at a time. Each one gives away a little more.

One lock guards everything that changes together: the top pointer and the size. Every method takes it, including size() and tryPop().
pop() waits for a condition, "not empty". Wait in a loop (while (top == null) wait();, or wait with a predicate in C++), because a woken thread may find that another popper took the item first. push signals one waiting popper after adding.
tryPop() must decide "empty or not" and take the item in one critical section. A quick check outside the lock followed by a pop inside it is a check-then-act: the item can vanish in between, and in C++ the unlocked read is a data race.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

std::stack has separate top() and pop(). Why does this stack return the value from pop?
Two calls are a check-then-act: between your top() and your pop(), another thread can pop, so you remove an item you never saw. A concurrent stack must hand back the item in the same critical section that removes it. std::stack split them for exception safety: if copying the returned value throws after the item was removed, it is lost. Concurrent versions return by value with a non-throwing move, return a std::shared_ptr<T>, or take an output parameter such as bool tryPop(T& out).
Why is waking one popper enough here?
Only poppers ever wait, and each push adds exactly one item, which can satisfy exactly one popper. So notify (notify_one) after each push never wakes the wrong kind of thread. notifyAll is also correct, but wakes poppers that find nothing and sleep again. Add a capacity limit, so pushers wait too, and you need two conditions or notifyAll.
Add pop(timeout).
Compute a deadline, then wait in a loop for the time that is left: awaitNanos or a timed wait in Java, wait_until or wait_for with a predicate in C++. If the stack is still empty at the deadline, return none. Never restart the full timeout after a wakeup.
How would you stop the threads blocked in pop when the program shuts down?
Add a closed flag under the same lock. close() sets it and wakes everyone (notifyAll, notify_all). pop waits while empty and not closed; if it wakes closed and empty, it returns none or throws. Pushes after close are rejected.
Now make it lock-free.
That is the Treiber stack in the lock-free stack problem: an atomic top pointer changed only by compare-and-swap. The blocking pop goes away (lock-free code does not block), and in C++ freeing popped nodes becomes the hard part.
Would a read-write lock make size() faster?
Not in a useful way. size() holds the lock for one read, and push and pop are writes that dominate. If size() is called very often, keep the count in an atomic that push and pop update under the lock, and let size() read it without locking: the value is a recent snapshot, which is all a size can ever be once the lock is released.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

This is the monitor pattern on a linked list. One lock guards the top pointer and the size, which together form the invariant size equals the number of nodes reachable from top. push links a new node on top and wakes one waiting popper. pop waits in a loop until the stack is not empty, then unlinks the top node. tryPop does the same check without waiting.

Why each line is there

  • Every method takes the lock, even size(): in C++ an unlocked read of a field another thread writes is a data race, and in Java it may be stale.
  • Wait in a loop. A popper woken by a push can lose the item to another popper that got the lock first, and wakeups can be spurious, so it re-checks "not empty" every time.
  • Decide and act in one critical section. The classic slip is building tryPop from two safe calls:
  • C++ allocates outside the lock. push creates the node with std::make_unique before taking the mutex, so the critical section is a few pointer moves.
  • C++ frees the list iteratively. A chain of std::unique_ptr nodes would destroy itself recursively and can overflow the call stack for a long stack, so the destructor unlinks one node at a time.

Cost

Push and pop are O(1) under one lock. All threads serialize on that lock, which is fine for a warm-up and for most real use. Under heavy contention the lock-free version, or a stack per thread with work stealing, scales better.

How to say it in the interview

I will keep a singly linked list with a top pointer and a size, guarded by one mutex. Push links a node on top and signals one waiting popper; one is enough because only poppers wait and one item satisfies one popper. Pop waits in a loop on a not empty condition, then unlinks the top node and returns its value in the same critical section. tryPop does the same check without waiting. Everything is O(1). If you want, the next step is the lock-free version with compare-and-swap on the top pointer.
