Thundering herd and cache stampede

Why simultaneous wakeups, cache misses and retries overwhelm a service, and how coordination, jitter and bounded load protect it.

Asked atRubrik
Before this:Lost wakeups, notify versus notifyAll, Mesa versus HoareThread-safe caches: LRU, TTL and single-flight

Some concurrency failures are not wrong answers but stampedes: one event releases a thousand waiters, and they all hit the same thing in the same millisecond. The pattern repeats at every scale, from a condition variable inside one process to a fleet of clients reconnecting to a server that just restarted.

In plain words

A shop announces a sale starting at 10:00 sharp, and 500 people wait outside. At 10:00 the door opens and everyone rushes the single billing counter at once; the crush is so bad that the counter serves fewer people per minute than on a quiet day. Or a hostel where every alarm rings at 6:00 and everyone queues for the one geyser.

The fixes are the ones any shopkeeper knows: let people in a few at a time, hand out time slots spread across the morning, or send one person to fetch for the whole group. Simultaneous arrivals can overwhelm a service that could handle the same people spread over time. If sustained demand also exceeds capacity, spreading arrivals alone is not enough.

What a herd is

A thundering herd happens when one event wakes or releases many waiters at once, but only one of them (or a few) can actually make use of it. Others compete for scarce capacity or repeat the same work; the overhead can outweigh the useful work. It wears several costumes:

HerdThe triggerWho stampedesThe usual fix
Wake-up herdOne item added, notifyAll calledEvery thread waiting on the conditionWake one when only one can proceed; separate conditions
Accept herdA listening socket becomes readableMultiple workers monitoring that socket, depending on the OS and registrationOn Linux: exclusive wakeups or separate SO_REUSEPORT listeners
Cache stampedeA hot key expiresEvery request that misses it, across the fleetSingle-flight, early refresh, serve stale, TTL jitter
Reconnect or retry stormA server restarts or blipsEvery clientBackoff with jitter, admission control, retry budgets
Timer herdThe clock reaches :00Every cron job, cache entry or lease written at the same momentRandom splay

In one process: the notify-all herd

When a producer adds one item and calls notifyAll (notify_all), all waiting consumers become eligible to resume. After the producer releases the lock, they reacquire it one at a time: one takes the item, and the rest wait again if no further item has arrived. This creates unnecessary predicate checks and contention, but a notification is not a context-switch counter: scheduling, parking and lock handoff are implementation details.

Consider N consumers that each take one item and exit. If every broadcast finishes waking the remaining consumers before the next insertion, total resumptions are N + (N - 1) + ... + 1 = N(N + 1)/2, of which N(N - 1)/2 find no item. That is a quadratic schedule, not a guarantee for every execution; consumers can instead receive later items before they return to waiting.

The output is illustrative, not an asserted count or benchmark. A woken consumer may acquire the lock after another item arrives, so this program need not realise the quadratic schedule; spurious wakeups can add checks in either version. Java counts empty returns from await; C++ counts predicate calls minus each consumer's initial and successful checks. The rule from lost wakeups and notify versus notifyAll still holds, and correctness comes first:

  • Wake one for one unit of work when any selected waiter can use it. Separate notFull and notEmpty conditions make this easy for single-item queue operations. Every waiter still rechecks its predicate under the lock. Producers waiting for different batch sizes are not interchangeable, even on notFull: waking only a large batch can strand a smaller batch that fits.
  • Wake all for a shared state change such as closing a queue or opening a gate. With mixed predicates, broadcasting avoids selecting only an ineligible waiter. For a batch, notify enough eligible consumers, broadcast, or use a proven handoff protocol; one notification alone need not drain it.

Between processes: the accept herd

When several workers monitor one listening socket, one readiness event can notify multiple event loops even though only a few connections are available. On Linux, EPOLLEXCLUSIVE (since 4.5) reduces this herd when separate epoll instances watch the same descriptor. Its documented guarantee is one or more exclusive instances receiving an event, not exactly one; non-exclusive registrations still receive notifications.

Linux SO_REUSEPORT (since 3.9) offers another design: each worker binds its own listening socket to the same address and port, and the kernel distributes connections among them. nginx also supports an accept_mutex to make workers accept in turn; its default changed to off in 1.11.3. These are Linux and server-specific mechanisms, not portable Java or C++ APIs. A readiness notification does not reserve a connection, so a nonblocking accept() must still handle EAGAIN if another worker drains the queue.

Across a fleet: the cache stampede

A popular cache entry expires. Every request that arrives before it is reloaded misses, and every miss queries the database for the same row. That is a cache stampede. It is dangerous because it feeds itself: the extra queries make the database slower, so the reload takes longer, so more requests miss, time out and retry.

Facebook's 2013 memcache paper (NSDI, "Scaling Memcache at Facebook") describes herds after cache invalidations and mitigates them with leases: on a miss, the cache hands one client a token that entitles it to refill the key, and tells other clients that a refill is in progress so they should wait briefly and retry, with tokens issued at a limited rate per key. The paper credits leases with a large drop in peak database load. Four fixes, usually combined:

  1. Single-flight. Concurrent misses for the same key share one load, as built in thread-safe caches. In-process single-flight reduces a stampede to one load per server; across 200 servers, that is still 200 loads, which is why fleets add a shared lease or lock in the cache tier to coordinate refresh ownership across the fleet. Lease expiry and failures still need explicit handling.
  2. Early refresh. Refresh hot keys before they expire, from a background task (refresh-ahead), to reduce the chance of an expiry cliff. A neat variant is probabilistic early expiration (Vattani, Chierichetti and Lowenstein, "Optimal Probabilistic Cache Stampede Prevention", VLDB 2015): each reader independently decides to recompute early with a probability that rises as expiry approaches, to spread refresh decisions. This is probabilistic, so it cannot guarantee exactly one refresh or no misses; combine it with duplicate suppression when that guarantee matters.
  3. Serve stale while revalidating. Keep the expired value. The first request to notice the expiry refreshes it; every other request is answered immediately with the stale value. RFC 5861 describes the HTTP stale-while-revalidate directive with a bounded stale window. Caffeine's refreshAfterWrite makes an entry eligible for asynchronous refresh when queried; it does not schedule an unconditional refresh at that instant, and expiry can be configured separately.
  4. TTL jitter. Entries written at the same moment (after a deploy, a cold start, a bulk load) all expire at the same moment. Add a random spread to every TTL, for example plus or minus 10 percent, so expiries spread out. Single-flight can still merge duplicate requests per key, but it cannot spread reloads of different keys.

This example holds one already-populated key, uses a positive, representable TTL, and has no invalidation or cold-miss path. The 100 ms sleep simulates database latency, not synchronization; the stale-reader count depends on scheduling. Java publishes the immutable entry through volatile; C++ protects the shared pointer with a short mutex. Neither holds that mutex across the loader. The C++20 std::latch only coordinates the demo start; in C++17 use a mutex, a boolean and a predicate condition-variable wait.

Recheck freshness after winning the refresh flag. Otherwise a delayed caller can use an obsolete snapshot to start a second load after the first finishes. Java's finally and the C++ scope guard clear ownership even if the loader throws; only the refreshing caller receives that failure here. Requests already holding a stale snapshot may still return it, which this example permits.

The refreshing request pays the reload latency itself. A bounded background executor can keep refresh latency off the request path; handle submission rejection by clearing ownership, and bound refresh time and retry rate. Set a maximum stale age: once it is exceeded, wait with a deadline or fail according to the data's freshness contract. A cold miss has no stale value to serve, so it needs single-flight with bounded waiting or rejection.

Reconnect storms and retry storms

A server restarts, or a network blip drops every connection. Fifty thousand clients notice within the same second and reconnect immediately. Each reconnection costs the server a TLS handshake, an authentication call and a session load, so the burst is far heavier than normal traffic, the server falls over again, and the cycle repeats. Requests retried on timeout behave the same way: the retries add load exactly when the system is slowest. That is a retry storm, and a system can stay stuck in it even after the original trigger is gone. The fixes:

  • Clients back off with jitter. Exponential backoff with full jitter on every reconnect and retry, plus a random initial delay, so clients that failed together do not return together (see livelock and starvation for the code).
  • Retry budgets. Google's SRE book recommends limiting retries per request (a few attempts) and per client, for example allowing retries only while they are under about 10 percent of that client's requests. Retry at one chosen layer: three nested layers making three attempts each, including the original attempt, can produce 27 backend calls. Retry only transient failures, within the caller's deadline, and use idempotency for operations that may already have taken effect.
  • The server protects itself. Admission control and rate limits on new connections, shedding load early with a cheap "try again later" rather than doing expensive work it cannot finish (see backpressure and load shedding).
  • Restart gently. Drain connections before a restart, roll restarts across machines, and reconnect clients to different instances.

Timer herds

Thousands of cron jobs scheduled at "0 * * * *", every service flushing metrics at the top of the minute, certificates or leases renewed on the same schedule, cache entries all written at deploy time: anything aligned to the clock arrives together. The fix is a random splay: run each job at a random offset within its window, add jitter to TTLs, and randomise renewal times while retaining enough margin for renewal latency and retries before a lease expires. Splay reduces synchronisation; it does not add capacity or guarantee that bursts disappear.

Worked example: one hot key, three designs

A product page key is read 50,000 times a second across 100 servers; the unloaded database query takes 50 ms; the TTL is 60 seconds. Assume evenly distributed requests and a simultaneous expiry on all servers. These are illustrative load estimates, not measured results.

  1. No protection. When the key expires, every request in the first 50 ms misses: about 50,000 × 0.05 = 2,500 queries issued during that window. If this exceeds database capacity, queuing lengthens the window and more requests miss. The burst can recur at each expiry.
  2. Single-flight on each server. Each of the 100 servers sends one query and makes its other requests wait for it: about 100 queries per expiry; requests that arrive during a load wait for its remaining duration. Much better, not perfect.
  3. Serve stale, plus one refresher for the fleet. Expired values keep being served; the first server to notice takes a lease and schedules a background refresh; others serve the old value until the new one appears. In the healthy case, one query completes before lease expiry, and requests do not wait for that query. Add early refresh so the key is usually rebuilt before it even expires, and jitter so this key does not expire in lockstep with ten thousand others.

This is close to a Rubrik senior question reported in a question bank: one refresher per instance and one across all instances, with everyone else reusing the new value. Saying the numbers out loud (2,500 queries, then 100, then 1) is what makes the answer land.

Common mistakes

  • notifyAll by habit when one item satisfies one waiter. Correct, but it turns every hand-over into a herd. Use separate conditions and wake one.
  • notify one where several waiters must learn something. A close() that wakes one consumer leaves the others asleep forever. Wake all when many can proceed.
  • Single-flight only inside one process, then surprise that 300 servers still send 300 queries.
  • Identical TTLs for data written together. Add jitter.
  • Retrying immediately, or at every layer, or without a budget.
  • Serving stale data with no upper bound. Decide how stale is acceptable, and fail or degrade beyond it.
  • Refreshing synchronously on a hot path without considering a bounded background executor and its rejection and shutdown rules.

In the interview

It shows up in three places: as a code review point on notifyAll in a producer-consumer solution, as "a hot key expires and the database falls over: what happened and what do you do?" in a design or system coding round, and as the reconnect storm in reliability discussions. A Rubrik senior system coding question (from a question bank) is built on it: refresh a cached key with one thread per instance and one across all instances.

That is a cache stampede: a hot key expired and every concurrent miss went to the database for the same row. I would put single-flight in each server so concurrent misses share one load, coordinate refresh ownership with a lease in the cache tier, reject obsolete publication after lease expiry, and serve stale within an agreed age limit while refresh runs, refresh hot keys a little before they expire, and add jitter to TTLs so keys written together do not expire together. On the client side, retries get exponential backoff with jitter and a budget.

Follow ups: "single-flight works per process; what about 200 servers?", "what if the refresh keeps failing?" (keep serving stale up to a limit, back off the refresh, alert), "when is notify-all required?", "why does jitter help?", and "what is the difference between a thundering herd and a retry storm?" (a burst of competing work versus a feedback loop of retries; one can trigger the other).

Senior depth

A lease is not an exactly-once execution guarantee. A holder can pause past expiry while its source query continues; a successor can start another query. Recheck the shared cache after acquiring the lease, release it only if its owner token still matches, and reject obsolete publication atomically at the cache using a generation or fencing token. Merely attaching a version to a value does not enforce anything. See distributed locks and fencing.

Invalidation needs the same discipline: a refresh that began before a write must not repopulate an invalidated key with old data. Compare the captured generation when publishing. If strict freshness is required, serving stale is unsuitable. Measure source loads per key, refresh failures, stale age, wait time and outstanding refreshes; use a global concurrency limit as well as per-key suppression so many distinct misses cannot overwhelm the source.

Key takeaways

  • A herd is one event releasing many waiters at once when only one or a few can use it.
  • In process: wake one when one waiter can proceed and all wait for the same thing; wake all when many can proceed or waiters wait for different things.
  • Cache stampede fixes: single-flight per process plus a lease across the fleet, early refresh, serve stale while revalidating, and TTL jitter.
  • Reconnect and retry storms: backoff with jitter, retry budgets, one retrying layer, and server side admission control.
  • Spread flexible schedules with random splay; respect deadlines and lease-renewal margins.

Quick check

Answer each question, then read why. Your score is saved for your module test.

100 consumers wait in predicate loops on an empty queue, protected by one mutex. A producer adds one item, broadcasts, and releases the mutex. No more items arrive and all threads eventually run. What happens?
Why. Notify-all moves every waiter back into contention for the lock. They are serialized by the lock, so nothing breaks, but 99 consumers find no item. This does not imply exactly 99 OS context switches. Waking one is enough when every waiter waits for the same condition and one item lets exactly one proceed. The mutex prevents duplicate removal, and contention alone is not a deadlock cycle.
An empty bounded queue's close() sets closed = true under its mutex and calls notify-one. Twelve consumers wait while empty and not closed. With no further notifications, timeouts, interrupts or spurious wakeups, what goes wrong?
Why. Closing changes the state in a way that lets every waiter proceed (they must all see "closed" and exit), so it must wake all of them. Wake-one is only right when one change satisfies exactly one waiter. The flag is shared state, not a private message to one thread; notification makes waiters eligible to observe it. Broadcast is appropriate; changing the flag alone does not resume all twelve waiters.
200 servers each have a correct in-process single-flight in front of the database. A hot key expires, and 10,000 misses for it arrive before any load completes, spread evenly over the servers; each server has its own cached copy. Roughly how many database queries for that key follow?
Why. Single-flight merges concurrent misses within one process, so each server sends one query. The 50 requests per server are followers of that server's single load, not 50 fleet-wide loads. One fleet-wide query in the healthy case needs coordination outside the process, such as a lease with failure handling; serving stale alone does not elect an owner.
After every deploy, the database is hammered about ten minutes later, although no single key is especially hot. Every cache entry has a 600 second TTL and the cache is warmed at startup. What is the most direct fix?
Why. Thousands of different keys written at startup expire in the same second. Single-flight cannot spread distinct-key reloads, and a longer TTL only moves the cliff. Independent TTL jitter spreads expected reload demand across time; it does not bound every peak. Changing condition-variable notification cannot change cache expiry scheduling.
A server restarts and 50,000 clients reconnect within the same second, knocking it over again. What is the best client-side change?
Why. A fixed delay just moves the whole herd five seconds later. Randomness spreads clients out, and the growing bound keeps load low while the server is still struggling. Immediate retries amplify overload; disabling recovery entirely sacrifices availability. Pair jitter with deadlines, a retry budget and server side admission control.
What does "serve stale while revalidating" trade, compared with blocking every request until a fresh value is loaded?
Why. Serving stale avoids waiting for the source, but freshness is a real cost and is acceptable only when the contract permits it. Duplicate suppression limits reloads separately; stale serving alone does not elect a refresher. A stale-age bound must be implemented, and retaining the old value may cost memory, but that is not the main tradeoff here.
A reads an expired snapshot and pauses before its CAS. B claims the refresh flag, loads v2, publishes it and clears the flag. A then wins the CAS while v2 is still fresh. In the sample above, what does A return, and how many loader calls occur across A and B?
Why. A rereads the entry after gaining ownership and sees fresh v2, so it skips the loader and releases the flag on return. Returning the original snapshot would yield v1; omitting the recheck would allow a second load. The flag has been cleared, so B's earlier ownership does not prevent A's CAS from succeeding.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
A cache writes 10,000 keys at the same instant, all with a TTL of 600 seconds. For this estimate, assume one reload per key begins immediately at expiry. (a) Without jitter, how many keys expire in the peak second? (b) With each TTL drawn uniformly between 540 and 660 seconds, roughly how many per second? (c) The database can absorb about 200 extra reloads a second. Is jitter enough, and would single-flight help?
Model answer

(a) All 10,000 expire in the same second, 600 seconds after startup, so 10,000 reloads arrive at once.

(b) With independent continuous uniform TTLs, the expected expiries per one-second bucket inside the 120 second window are 10,000 / 120, roughly 83. Actual bucket counts vary; 83 is not a peak bound.

(c) Jitter makes the expected rate fit comfortably below 200, but it is not a capacity guarantee: random clustering, other traffic and variable query cost still matter. Bound refresh concurrency and observe the peaks. Without jitter, 10,000 is 50 times the one-second budget. In a lazy cache, expiry makes a key eligible for reload only when read, so real request timing also matters. Single-flight cannot spread these distinct-key reloads, though it still merges duplicate misses for each key. Single-flight matters for the hot keys, which TTL jitter alone does not protect: a shared key read 50,000 times a second can still stampede when it expires. Use both.

Design
A Rubrik style system coding question: many instances of a service each keep a local cache in front of a shared cache, which sits in front of a slow source. When a key is missing or expired, only one thread per instance may refresh the local copy, and only one thread across all instances may refresh the shared entry; everyone else must wait for or reuse the new value. Describe your design and its failure handling.
Model answer

Inside each instance I would use single-flight per key: a map from key to future, filled with an atomic put-if-absent, so the first thread to miss becomes the local refresher and every other thread waits on its future; the future is completed outside any lock, failures are delivered to all waiters, and the entry is removed afterwards.

The local refresher then reads the shared cache. If the shared entry is fresh, it uses it. If not, it tries to take a short lease on that key in the shared cache, an atomic "set if absent with an expiry" of a few seconds. The instance that wins rereads the shared entry in case another refresher just completed; if still expired, it reads the source and conditionally publishes under its lease generation. It releases the lease only if the owner token still matches; instances that lose wait with a deadline and jittered backoff until a fresh shared value appears, then complete their local futures. They may serve stale only if the question's freshness contract is explicitly relaxed.

Failure handling: if the lease holder dies, the lease expires and another instance takes over; if it stalls past expiry, queries may overlap, but an atomic publication check enforced by the cache rejects the obsolete generation; if the source keeps failing, all waiters receive failure by their deadlines and later refresh attempts back off. Under an allowed stale-serving policy, stale age also has a hard limit. Cleanup removes only the matching in-flight future so it cannot erase a newer generation. To keep refreshes rare in the first place, I would refresh hot keys a little before expiry and add jitter to TTLs.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"You replaced every broadcast with wake-one to fix a thundering herd. Walk me through when that change is safe and when it can hang the service."
What a strong answer covers
  • Wake-one is suitable for one item when any selected consumer can use it
  • The waiter must reacquire the mutex and recheck its predicate
  • Mixed predicates can select an ineligible waiter and strand useful work
  • Shutdown and gates require notifying all affected waiters; batches need enough notifications or handoff
  • Wakeup counts depend on the schedule and are not exact context-switch counts
  • Correctness comes before measuring and reducing contention
How a senior would say it
I would not make that replacement everywhere. Wake-one is appropriate when a state change supplies one unit of work and any selected waiter can use it. For a queue with separate not-empty and not-full conditions, adding one item can signal one consumer. That consumer still reacquires the mutex and checks the predicate, because notification does not reserve the item and wakeups can be spurious. If producers and consumers share a wait set, a notification can select a producer even though only a consumer can proceed. Useful work can then remain stranded. I would separate the conditions or broadcast. Closing a queue is different again: every waiting consumer must learn that it can exit once the queue is drained, and blocked producers must learn that new work is rejected. A batch also needs enough notifications, a broadcast, or an explicit handoff protocol. The performance issue is unnecessary competition. With one item and a hundred waiting consumers, ninety-nine may find no work, but that is not an exact count of operating-system context switches. I would first prove that every state transition wakes enough eligible waiters, then measure predicate failures, contention and throughput before optimising. A shutdown hang is a much worse result than an occasional unnecessary wakeup.

Likely follow up: What changes if producers wait for batches of different sizes?

Out loudabout 120 s
"A hot cache key expires across two hundred servers and the database falls over. Design the fix, including what happens if the refresher dies."
What a strong answer covers
  • Identify duplicate misses and the positive feedback from a slower source
  • Use per-key single-flight locally and coordinate refresh ownership across the fleet
  • Recheck freshness after winning ownership and keep source I/O outside shared locks
  • Serve stale only within a freshness contract; bound cold-miss waiting and background work
  • Lease expiry permits takeover but can overlap loads; enforce publication generations and owner-checked release
  • Combine failure backoff, TTL jitter and global load bounds, then measure results
How a senior would say it
I would suppress duplicate loads, bound refresh work, and decide how stale the response is allowed to be. This is a cache stampede: many requests miss together and query the same row. Extra queries slow the database, which extends the miss window and attracts still more work. Within each server, I would keep one in-flight future per key so concurrent callers share the load and its failure. Across two hundred servers, that still permits two hundred queries, so I would coordinate refresh ownership in the shared cache with a lease. After winning ownership, I would reread the entry because another refresher may already have completed. The source call runs outside shared locks. If the product permits bounded staleness, requests can reuse the old value while a bounded executor refreshes it. A cold miss has no old value, so callers wait with a deadline or receive a controlled failure. If the refresher dies, lease expiry allows takeover. But expiry does not stop a paused holder's query: two loads can overlap. The cache must atomically reject publication from an obsolete generation, and release must check the owner's token so an old holder cannot delete a successor's lease. Failures complete local futures, cleanup removes only the matching flight, and retries back off with jitter. TTL jitter spreads different keys; it does not replace single-flight for one hot key. I would also cap total source concurrency because thousands of distinct misses can still overwhelm it. Finally, I would measure source loads per key, stale age, refresh failures and waiter latency, then test expiry, cancellation, failure and a holder resuming after its lease has expired.

Likely follow up: How would your design change if every response must reflect the latest committed write?
