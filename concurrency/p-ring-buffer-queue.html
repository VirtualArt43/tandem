Ring buffer blocking queue

Thread-safe structuresmedium35 minRubrik systems coding screenRubrik

Rubrik's systems coding screen has asked for a FIFO queue on a fixed-size int buffer with no dynamic allocation, then for many threads to use it, and a Google L4 onsite asked how several threads should share a circular buffer. The ring buffer is how serious queues store their items: one array, two indexes, and no allocation once it is built.

The task

Build a bounded blocking queue of ints whose items live in one array of exactly capacity slots, allocated in the constructor:

  • put(item) adds an item at the back. If the queue is full, the caller blocks until there is space.
  • take() removes and returns the item at the front. If the queue is empty, the caller blocks until there is an item.
  • size() returns the number of items right now.

Keep a head index (the oldest item), a tail index (the slot for the next item) and a count. Both indexes move forward by one and wrap around to 0 at the end of the array. Many producers and consumers use the queue at once, and items come out in the order they went in.

Rules:

  • No allocation after construction. The array is created once, in the constructor, and items are stored as plain ints: no boxing, no growing collections, no nodes. This is the requirement the interview adds to make you write the index arithmetic yourself.
  • No library queues or deques. Use a lock with conditions (Java: ReentrantLock with two Conditions, or synchronized with wait and notifyAll; C++: std::mutex with std::condition_variable).
  • put and take are O(1).

What the tests check

  • FIFO order and size() from one thread, filling the queue exactly to its capacity.
  • Wraparound: 20,000 random puts and takes from one thread on a queue of capacity 5, checked step by step against a simple model, so head and tail wrap thousands of times.
  • put blocks on a full queue and wakes when a consumer takes; take blocks on an empty queue and wakes when a producer puts.
  • Capacity 1 with two producers and two consumers: 4,000 items pass through a single slot, each exactly once and in order per producer. This is the smallest shape in which waking the wrong kind of thread deadlocks.
  • A stress run with 4 producers and 4 consumers on capacity 3: every item arrives exactly once, items from each producer stay in order, the size never exceeds the capacity, and nothing deadlocks.
  • No allocation after construction: 50,000 put and take pairs from one thread allocate almost nothing. Java measures the bytes the thread allocates; C++ counts calls to operator new.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Queues inside a fixed buffer

Open them one at a time. Each one gives away a little more.

Picture the array as a circle. head points at the oldest item and tail at the slot where the next item goes; each moves forward by one and wraps to 0 at the end. Now ask: when head == tail, is the queue full or empty?
It can be either, so keep a count: full is count == capacity, empty is count == 0. (The other classic fix wastes a slot: allocate capacity + 1 slots and call the queue full when the next tail would equal head. With exactly capacity slots that version holds one item too few.)
The blocking part is the bounded blocking queue: one lock guards the array, the indexes and the count; producers wait on "not full", consumers on "not empty"; always wait in a while loop; after each change, signal the other side. Write tail = (tail + 1) % capacity and head = (head + 1) % capacity.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why keep count? What else could tell full from empty?
With only head and tail, head == tail means both "empty" and "full". The options: keep a count; waste one slot so full is "the next tail equals head"; or use two ever-increasing counters, putIndex and takeIndex, where size is their difference and the slot is the counter modulo capacity. The counter version is what lock-free queues use, because each counter has a single writer. Use 64-bit counters so they never overflow in practice.
Make it lock-free for exactly one producer and one consumer.
The producer owns tail and the consumer owns head, so each index has a single writer and no CAS is needed. The producer writes the item, then publishes the new tail with a release store; the consumer reads tail with an acquire load, reads the item, then publishes the new head with a release store, which the producer reads with acquire to see free space. Put the two indexes on separate cache lines to avoid false sharing. Blocking when full or empty needs a wait mechanism or a spin with backoff.
And with many producers and no lock?
Producers must claim slots atomically (CAS or fetch-add on the tail counter), and a consumer must not read a slot that has been claimed but not yet written. So each slot needs its own sequence number that says whose turn it is, as in Dmitry Vyukov's bounded MPMC queue or the LMAX Disruptor's sequences. It is much harder to get right; a lock is usually fast enough.
Why do high-performance ring buffers use a power-of-two capacity?
Then index % capacity becomes index & (capacity - 1), a single AND instead of a division, and ever-increasing counters map onto slots without any special wrap logic. Modulo with any other capacity is correct, just slower.
Some ring buffers overwrite the oldest item instead of blocking. When is that right?
For data where the newest matters most and losing old entries is acceptable: recent log lines, metrics, a flight recorder. A full put then advances head as well as tail, and you count the dropped items so the loss is visible. Never for a work queue, where every item must be processed.
How would you add timeouts and shutdown?
Exactly as in the bounded blocking queue: wait with a deadline (awaitNanos in a loop, or wait_until with a predicate) and return false or an empty result on timeout; add a closed flag under the same lock, have close() wake everyone, and make blocked take calls return once the queue is closed and empty.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

A ring buffer is an array used as a circle. head is where the next item will be taken from, tail is where the next item will be put, and count says how many items are in between. The invariant is 0 <= count <= capacity, and the items, oldest first, are at head, head + 1, and so on, count of them, all modulo capacity. One lock guards all three fields and the array, because they change together.

Here is a queue of capacity 3. Notice that head == tail both at the start (empty) and after the fourth put (full): that is why count is there.

StepArrayheadtailcount
start[ _, _, _ ]000 (empty)
put 1[ 1, _, _ ]011
put 2[ 1, 2, _ ]022
take gives 1[ _, 2, _ ]121
put 3[ _, 2, 3 ]10 (wrapped)2
put 4[ 4, 2, 3 ]113 (full)
take gives 2[ 4, _, 3 ]212

Why each line is there

  • The array is allocated once. A plain int[] (or a std::vector<int> sized in the constructor) stores the items with no per-item allocation, which is the whole point of the exercise and why real queues work this way: no garbage, no allocator calls, and predictable cache behaviour.
  • Two conditions, waits in loops. Producers wait for "not full", consumers for "not empty", so each signal reaches a thread that can use it, and the loop handles spurious and stolen wakeups.
  • Signal after the change, under the lock. The woken thread re-checks the state once it gets the lock and sees the new count.
  • size() takes the lock too. count is shared state; an unlocked read is a data race in C++ and may be stale in Java.

Cost

put and take are O(1) under one lock, with no allocation, so the queue never produces garbage or calls the allocator. All producers and consumers serialize on that one lock; the lock-free single-producer single-consumer ring in the follow ups removes it when the shape allows.

How to say it in the interview

I will store the items in a fixed int array allocated in the constructor, with a head index, a tail index and a count; both indexes advance modulo the capacity. The count tells full from empty when head equals tail. For threads I wrap it in the monitor pattern: one lock, a not full and a not empty condition, waits in while loops, and a signal to the other side after each put or take. Every operation is O(1) and nothing allocates after construction. If there were exactly one producer and one consumer, I could drop the lock and publish the two indexes with release and acquire.
