CyclicBarrier from scratch

Build a primitivemedium30 minjava.util.concurrent.CyclicBarrier and C++20 std::barrier, rebuilt as a monitor

A one-shot gate is easy. A gate that resets itself for the next round, while the last round's threads are still waking up, is where the obvious answer breaks, and the fix (a generation number) is the idea interviewers are listening for.

The task

Build a reusable barrier for a fixed number of threads, called parties. Each party calls await() when it reaches the end of a phase of work. Nobody gets past until all parties of that round have arrived and its action has finished. Everyone then becomes eligible to return; the scheduler decides when each thread actually resumes. The same fixed group can immediately use the barrier again, with at most one outstanding await() per party.

  • await() blocks until parties threads have called it in the current round. It returns the thread's arrival index, as Java's library does: parties - 1 for the first thread to arrive, then parties - 2, down to 0 for the last. Arrival order is the order calls register under the lock, not the order threads are started.
  • An optional barrier action runs exactly once per round, in the thread that arrives last, before any waiting thread is released. (Use it to merge per-thread results before the next phase starts.)
  • getNumberWaiting() returns a synchronized snapshot of the number waiting in the current round; it is zero initially and after a completed round with no new arrivals. getParties() always returns the constructor's party count.
  • Writes made before a party calls await() must be visible to the action and to every party after its await() returns in that round. Writes made by the action must also be visible after return. The barrier provides the synchronization; callers do not need atomic payload fields.
  • Fewer than 1 party is a caller bug: throw IllegalArgumentException (Java) or std::invalid_argument (C++).

Rules.

  • Build it from one lock and one condition variable.
  • No library help: not the library barrier, Phaser, the library latch, Semaphore or AbstractQueuedSynchronizer in Java; not C++20's barrier or latch, std::counting_semaphore or POSIX barriers in C++. The runner also rejects the standalone identifiers barrier and latch in code; barrierAction is fine. Comments and strings are ignored.
  • The optional action may be absent or null. A supplied action must finish normally, must not call back into the barrier and must not wait for a party to return from this round. Throwing actions are a design follow up, not part of this API contract.
  • The tests never interrupt a waiting thread, but decide what yours does and be ready to defend it (see the follow ups).

What the tests check

  • Both constructor forms reject zero and negative party counts, including the smallest integer. Initial waiting counts are zero, and positive party counts are preserved.
  • One party completes eight rounds with no action, an explicit null action and a supplied action. Each return is 0; the supplied action runs exactly once per round.
  • Four parties arrive in a controlled order for three rounds. Waiting counts advance through 1, 2 and 3, nobody passes while the fourth is withheld, and the exact indices are 3, 2, 1 and 0 in arrival order. Every waiter wakes, counts reset and the number of parties stays fixed.
  • The last arrival runs the action exactly once. A test gate holds that action open while checking that nobody has returned; the gate then opens and all four calls must finish.
  • With no action and with an explicit null action, four workers reuse the barrier for 120 rounds each. Each worker writes ordinary shared data before arrival and checks every worker's data after return, without another test lock or atomic publishing those writes.
  • Seeded stress with an action covers 4 parties for 2,000 Java rounds or 300 C++ rounds, then 7 parties for 500 Java rounds or 150 C++ rounds. Every round checks complete arrivals, distinct indices covering the full range, one action and the correct action thread. Fixed seeds are printed for reproduction.
  • Worker deadlines and a watchdog turn blocked candidates into failures. C++ also runs under ThreadSanitizer. Spurious wakeups are not injected, so a correct predicate loop also needs reasoning. Interrupts and throwing actions remain design follow ups.

Taught in: Build it yourself: read-write lock and reusable barrier

Open them one at a time. Each one gives away a little more.

A counter of arrivals is the natural start, but it is not enough to wait on. Picture the moment right after the last thread resets the counter to zero: a fast thread can come straight back for the next round and bump it before a slow waiter has re-checked. What does the slow waiter see?
Keep a generation counter. On arrival, a thread notes the current generation and waits until the generation changes, not until some count is reached. The last thread to arrive runs the action, resets the count to zero, adds one to the generation and wakes everybody.
The arrival index is parties - 1 - waiting at the moment the thread arrives, computed under the lock. When the barrier trips, broadcast (signalAll, notify_all): every waiter of the round may leave, and a single signal would strand the rest.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why does "wait while the count is not zero" fail when the barrier is reused?
After the last thread resets the count and broadcasts, the woken waiters still have to get the lock back. A fast thread can return first, start the next round and make the count 1. A slow waiter now re-checks, sees a non-zero count and goes back to sleep in the wrong round, while the new round waits for it: a deadlock, or with other conditions a thread counted twice. A generation number fixes it because each waiter compares against its own round, and that round never comes back.
A waiting thread is interrupted, or times out. What should happen to the others?
A missing arrival can strand a round forever. If an already counted arrival simply leaves, the remaining calls may finish that round while later rounds lose a required participant. Java's library therefore breaks the barrier: the caller that triggers the break gets InterruptedException or TimeoutException, peers get BrokenBarrierException, later calls fail, and reset() starts over. The reference here takes a simpler line: a thread already interrupted when it calls await() throws InterruptedException before it is counted, clearing that flag. After that entry check, the reference waits uninterruptibly and preserves a later interrupt for the caller. This policy is deliberately simpler than the library contract. C++20's barrier has no cancellation at all; arrive_and_drop() lets a thread leave the group for good.
What if the barrier action throws?
This exercise requires actions to finish normally; the reference does not recover from an action exception. To support throwing actions, record failure in the current generation and wake every waiter. Java's library propagates the action exception to the last arrival and reports a broken barrier to peers and later callers. Advancing unconditionally and reporting success to the other parties is a different, weaker contract because the phase result may be incomplete. A reusable failure design must keep the failed generation's outcome available even if a reset starts a new one.
Can you build a reusable barrier from semaphores instead?
Yes, with the two-phase turnstile from The Little Book of Semaphores: a counter under a mutex and two turnstile semaphores. The last thread of phase one opens the first turnstile for everyone and closes the second; phase two does the mirror image. The second phase exists only to stop a fast thread lapping the slow ones, which is the job the generation number does here in one line.
CyclicBarrier, CountDownLatch or Phaser?
A latch is one shot, and the threads that count down are not the ones that wait. A barrier is a fixed group whose members wait for each other, round after round, with an optional action between rounds. A Phaser lets parties register and deregister while it runs, numbers the phases, and lets a thread arrive without waiting. C++20 has std::latch and std::barrier (with a completion function and arrive_and_drop).
Where would you use one in real code?
Phased parallel work where step k+1 needs every result of step k: a breadth first search done one level at a time by several threads (a Rubrik round was solved this way), iterative simulations, parallel numeric sweeps. In tests it can hold N threads at a common starting gate, though it cannot make them run at the same physical instant. The research reports Rubrik discussing barrier choices and a barrier-based BFS; it does not report an implement-from-scratch barrier question.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

State: the number of threads waiting in this round, and a generation number that goes up by one every time the barrier trips. The invariant: a thread may leave only when the generation is different from the one it arrived in. Waiting on the generation, not on the count, is what makes the barrier safe to reuse: a round, once ended, is ended for good, whatever the count does next.

Why each line is there

  • Compute the index on arrival, under the lock. parties - 1 - waiting is the number of threads still to come, which is exactly the library's arrival index. When it is 0, this thread is the last one.
  • The last thread runs the action first. It still holds the lock and nobody has been released, so the action sees every thread's work from this round and nobody starts the next phase early.
  • Reset, advance, broadcast, in that order, under the lock. The reset makes the barrier ready for the next round; the new generation is what releases the waiters; the broadcast wakes all of them. Woken threads still need the lock, so they see all three changes together.
  • The lock also publishes data. Arrivals release the lock when waiting, the last arrival acquires it before the action, and returning waiters acquire it again. These synchronization edges publish pre-arrival work and action results to the next phase.
  • Each waiter loops on its own generation. Spurious wakeups and fast threads from the next round cannot fool it, because the fixed group cannot complete another round while one party is still waiting in the previous one.
  • Java interrupts. The reference checks the interrupt before arriving and then waits with awaitUninterruptibly, so a round never loses a party halfway; the flag is kept for the caller.

Cost and trade-offs

Excluding callback work and time spent blocked, each arrival does O(1) bookkeeping and a completed round wakes O(parties) threads. The shared bookkeeping uses O(1) space. Every notified waiter eventually competes for the same lock, which is fine for a handful of parties and is why large scale barriers use trees or per-thread flags instead. Running the action under the lock is deliberate: it is what guarantees "before anyone leaves"; the price is that the action must be short and must not call back into the barrier.

The C++ generation uses an unsigned integer so increment has defined wraparound. With one outstanding call per party, the group cannot complete another round while a party is still waiting in the old one, so no waiter can be lapped through the counter's range.

How to say it in the interview

I keep two fields under one lock: how many are waiting in this round, and a generation number. A thread computes its arrival index, and if it is the last one it runs the action, resets the count, bumps the generation and broadcasts. Every other thread remembers the generation it arrived in and waits in a loop until the generation changes. Waiting on the generation instead of the count is what makes it reusable: a fast thread that starts the next round cannot fool a slow waiter from the previous one.
