static, class initialization and singletons

What static really shares, why the JVM's class initialization is thread-safe, the holder and enum singletons, and why static mutable state is a smell.

Asked atMicrosoft
Before this:final, immutability and records

A static field is one variable shared by every thread in the JVM, which makes it the easiest shared state to create by accident. The machinery that initializes static fields is also what gives Java its cleanest thread-safe singleton.

In plain words

Every student in a school has a notebook, and there is one notice board in the corridor. Whatever is on the notice board, every student sees, and if two students write on it at the same moment you get scribbles. Instance fields are the notebooks. A static field is the notice board.

The board is put up once, by the caretaker, before anyone reads it. While she pins it up she locks the corridor door, so nobody reads a half-pinned notice, and anyone who arrives waits at the door until she is done. That is class initialization, and it is the reason the simplest singleton in Java is already thread-safe.

Why this matters for concurrency

  • Every static mutable field is shared by all threads, so it needs the same protection as any other shared state. Static "utility" objects that secretly keep state, such as SimpleDateFormat, break under load.
  • static synchronized methods lock the Class object, not an instance. Mix them with instance synchronized methods on the same data and you have two locks guarding one variable, which means no lock at all.
  • Class initialization runs exactly once under a JVM lock and publishes its results safely. The holder idiom and the enum singleton stand on that guarantee. "Write a thread-safe singleton" is a real interview question (a Microsoft loop asked it), and its follow ups go straight into the memory model.

What static means

A static field belongs to the class, not to any object: there is one copy, however many objects exist (strictly, one per class loader, which in an ordinary program means one). An instance field has one copy per object. A static method has no this, so it can use static fields directly and instance fields only through an object reference.

If two threads open connections at the same moment, opened loses updates exactly like the counter in the lost update, even though each thread builds its own Connection. The constructor touches the notice board. The fix is the same as there: static final AtomicInteger OPENED = new AtomicInteger(); and OPENED.incrementAndGet().

Two threads calling add on two different Stats objects lock two different objects, so both run total += x at once and updates are lost. And read() takes a third lock that neither of them uses. Static state needs a static lock: a private static final Object LOCK = new Object(); used by every method that touches total, or simply an AtomicLong.

One more static detail you will use soon. A non-static inner class carries a hidden reference to the outer object that created it; a static nested class does not. The holder idiom below relies on a static nested class, and so should most helper classes and tasks you define inside another class.

Class initialization: when it happens

Before a class can be used, the JVM loads it, links it and initializes it; together these steps are called class loading and initialization. Initialization runs the static field initializers and the static { } blocks, in the order they appear in the source, exactly once. javac collects them into a hidden method named <clinit>.

Initialization is lazy: it happens at the first active use of the class, not when the program starts. The Java Language Specification (section 12.4.1) lists the triggers: creating an instance with new, calling a static method, assigning a static field, reading a static field that is not a constant, and initializing a subclass, which initializes its superclass first. Some reflective calls trigger it too.

One exception surprises people: reading a static final field that is a compile-time constant, such as static final int MAX = 3 or a String literal, does not initialize the class, because javac copies the value into the code that reads it.

Read the output in order. Config is initialized at step 3, when a non-constant field is read, not at step 2. Registry is initialized at step 4 by the static method call, but Holder is a separate class, so the constructor runs only at step 5, on the first getInstance(), and never again.

Why class initialization is thread-safe

The JLS (section 12.4.2) gives every class an initialization lock and spells out a procedure that the JVM follows:

  1. The first thread that needs the class marks it "being initialized by me" and runs the static initializers.
  2. Any other thread that needs the class in the meantime sees that another thread is initializing it, and waits.
  3. When the initializer finishes, the class is marked initialized and the waiting threads wake up.
  4. From then on every thread sees an initialized class, together with every value the initializer wrote.

The consequence is the whole point of this lesson: static initializers run once, and their writes are safely published to every thread that uses the class, with no volatile and no lock in your code. Once a class is initialized, the JVM stops paying for the check, so after the first use the guarantee is essentially free.

Two sharp edges of class initialization

It can deadlock. If the static initializer of Prices needs Rates, and the static initializer of Rates needs Prices, and two threads start on the two classes at the same moment, each waits for the other's initialization forever. Run it, then read the thread dump the site shows you.

In the dump both threads show the state RUNNABLE, with a line like "waiting on the Class initialization monitor for Main$Rates", and the JVM's deadlock detector reports nothing, because no ordinary lock is involved. That makes this one hard to spot in production. Keep static initializers small, with no cycles between classes, no blocking, and no threads started from inside them.

It can fail for good. If a static initializer throws, the first use of the class gets ExceptionInInitializerError and the class is marked as failed. Every later use, from any thread, gets NoClassDefFoundError: Could not initialize class ... for as long as the program runs. Java 21 attaches the original failure as the cause, so read the "Caused by" line instead of hunting for a missing jar.

Singletons, from broken to right

A singleton is a class with exactly one instance that everyone shares. There are six common ways to write one in Java: one is simply broken, and one is correct only when every detail is right.

1. Eager, in a static final field. Thread-safe through class initialization, and already lazy in the way that usually matters: the class is initialized on the first call to getInstance() or the first other use of the class.

2. Lazy with a null check. Broken. This is check then act on a static field: two threads can both see null and build two objects. And without a happens-before edge, a third thread may see the reference before it sees the fields the constructor wrote.

3. Lazy with a synchronized method. Correct, and fine when it is rarely called, but every call takes the lock forever after.

4. Double-checked locking. Correct only with volatile. Without it, the write of the reference can become visible to another thread before the writes made inside the constructor, so that thread can skip the lock and use a half-built object. The core lesson double-checked locking walks through that reordering.

5. The holder idiom. Lazy, thread-safe, and with no lock or volatile anywhere. The instance lives in a private static nested class, which the JVM initializes only when getInstance() first touches it, exactly once, under the class initialization lock.

6. The enum singleton. Joshua Bloch's Effective Java recommends a single-element enum as often the best way to write a singleton. The JVM guarantees exactly one instance, and it stays one even through serialization and reflection, which can break the other patterns. Its limit: an enum cannot extend another class, though it can implement interfaces.

Notice the comment in the enum. A thread-safe singleton is not a thread-safe object. The pattern only guarantees one instance, safely published. Its mutable fields still need atomics, locks or immutability, like any other shared object.

Static mutable state: the concurrency smell

A mutable static field is a global variable with a nicer name. Every thread in the process shares it, nothing in a method's signature warns you that the method touches it, tests leak state into each other through it, and it lives as long as the class, usually the whole run. When you see one in code under review, ask who else writes it.

A typical run reports many wrong dates and some exceptions from the shared SimpleDateFormat (the counts change on every run), and zero from DateTimeFormatter. Every thread parses its own input; they only share the formatter object, and that is enough.

Common mistakes

  • Double-checked locking without volatile. Another thread can see a non-null reference to an object whose fields it cannot see yet.
  • Guarding static state with instance locks. synchronized instance methods lock different objects; static synchronized locks the class. Use one static lock, or an atomic.
  • "It's static final, so it's safe." final freezes the reference. A static final HashMap is still a shared mutable map.
  • Heavy work in static initializers. Blocking calls, network or file I/O, cross-class cycles and starting threads there can deadlock, and a failure turns into NoClassDefFoundError for the rest of the run.
  • "It's a singleton, so it's thread-safe." The pattern makes one instance. Its fields are as unsafe as anyone else's.
  • Lazy initialization with if (x == null) x = new X(); on a static field. Use the holder idiom, or the eager field.
  • Sharing SimpleDateFormat, DecimalFormat or a StringBuilder through a static field. They are not thread-safe. Prefer the immutable java.time formatters.

In the interview

"Write a thread-safe singleton" still comes up; a Microsoft report lists it next to a classic thread printing puzzle. The interviewer is not checking whether you remember a pattern. They want to hear why it is safe, and the follow ups test exactly that.

I would use the holder idiom: a private static nested class holds the instance. The JVM initializes that class on the first call to getInstance, exactly once, under its class initialization lock, and the language guarantees that every thread then sees the fully built object. There is no volatile and no lock on the fast path. If serialization or reflection matter, I would use a single-element enum instead.
If you want explicit double-checked locking, the field must be volatile. Without it, another thread can see a non-null reference before it sees the writes the constructor made, skip the lock, and use a half-built object.

Follow ups to expect. "Why is volatile needed in double-checked locking?" (above). "Is the eager version lazy?" (yes, at the granularity of the class). "How can a singleton end up with two instances?" (two class loaders, deserialization, reflection calling the private constructor; the enum resists the last two, while a serializable class-based singleton needs a readResolve() method that returns the existing instance). "Why do people call singletons an anti-pattern?" (hidden global mutable state, hard to test; prefer creating one instance and passing it in).

Senior depth

  • One instance per class loader, not per JVM. Application servers and plugin systems load the same class through several loaders, and each gets its own static fields, so each gets its own "singleton".
  • Why the holder idiom costs nothing after the first call. In HotSpot (an implementation detail, not a language rule), the JIT treats static final fields of an already initialized class as constants, so Holder.INSTANCE compiles down to the object itself.
  • The same guarantee in C++. A function-local static is initialized once, thread-safely, on first use since C++11. The holder idiom is the Java spelling of the same idea, which is a neat point when the interviewer knows both languages.
  • Class initialization is also safe publication for static final fields. An immutable map built in a static initializer can be read by any number of threads without locks, which is the cheapest read-mostly configuration there is.

Key takeaways

  • A static field is one variable shared by every thread; treat every mutable one as shared state that needs protection.
  • static synchronized locks the Class object; instance synchronized locks this. They do not exclude each other.
  • Class initialization runs once, lazily, under a JVM lock, and safely publishes what it writes. Constants do not trigger it.
  • For a singleton use the eager field, the holder idiom or an enum. Double-checked locking needs volatile; the plain null check is broken.
  • A singleton's own mutable state still needs synchronization, and static mutable state is better replaced by an instance you pass in.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A class has synchronized void add(long x) { total += x; } and static synchronized long read() { return total; }, where total is a static field. Do these two methods exclude each other?
Why. An instance synchronized method locks this; a static synchronized method locks ClassName.class. Different locks never exclude each other, and two calls to add on two different objects do not exclude each other either. Guard static state with one static lock, or use an atomic.
What does this print?
Why. Classes are initialized lazily, on first active use, not at program start. LIMIT is a compile-time constant that javac copies into main, so reading it does not initialize Settings. MODE is computed by a method call, so it is not a constant, and reading it triggers initialization just before the value is printed.
Double-checked locking is written without volatile on the instance field. What can go wrong?
Why. The fast path reads instance without the lock, so there is no happens-before edge between the creating thread's writes and the reader. The reference write may become visible before the constructor's writes, and the reader skips the lock and uses a half-built object. volatile on the field supplies the missing edge.
Which singleton is lazy, thread-safe, and needs neither a lock nor a volatile read on each call after creation?
Why. The nested class is initialized on the first getInstance(), once, under the JVM's class initialization lock, and its result is safely published by the language rules. Double-checked locking also works but pays a volatile read per call; the synchronized method pays a lock per call; the plain null check is broken.
private static final List<String> NAMES = new ArrayList<>(); and several request threads call NAMES.add(name). Is this safe?
Why. final guarantees the field always points to the same list and that the list is safely published at class initialization. Every later add is an unsynchronized write to a shared ArrayList: lost elements, or a corrupted size and array. Use a thread-safe list, or confine the list to one thread.
A class's static initializer throws on first use. Later, other threads use the same class. What do they get?
Why. A class whose initialization failed is marked as erroneous, and the JVM never retries. Only the first use sees ExceptionInInitializerError; every later use, from any thread, gets NoClassDefFoundError for the life of the class loader. Recent JDKs attach the original failure as the cause.
Two threads start at the same moment. Thread 1 first touches class A, whose static initializer reads a static field of B. Thread 2 first touches B, whose static initializer reads a static field of A. What can happen?
Why. Each thread holds the right to initialize one class and waits for the other class's initialization to finish: a deadlock on class initialization. Single-threaded, a cycle completes, because the initializing thread may see its own class half initialized. Across two threads it hangs, and since no monitor is involved the deadlock detector stays quiet.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a lazily created, thread-safe singleton AppConfig twice: once with the holder idiom and once with double-checked locking. For each, say in one sentence why it is safe.
Model answer

Holder: the JVM initializes Holder once, on the first getInstance(), under its class initialization lock, and the language guarantees every thread then sees the finished object. Double-checked locking: the lock makes creation happen once, and the volatile write and read create the happens-before edge that stops a fast-path reader from seeing a half-built object.

Explain
The interviewer asks: "Your holder idiom has no volatile and no lock. Why is it thread-safe?" Answer as you would out loud.
Model answer

Because the JVM does the locking for me. A class is initialized lazily, on its first active use, and the Java Language Specification defines that procedure with a per-class initialization lock: exactly one thread runs the static initializer, any other thread that needs the class waits until it finishes, and after that every thread sees the class as initialized along with every value the initializer wrote. That is a happens-before edge from the initializer to every user of the class.

So when the first getInstance() touches Holder.INSTANCE, the Holder class is initialized once and the instance is safely published. Later calls find the class already initialized, and the JVM stops checking, so the fast path is just a field read; HotSpot even treats the static final field as a constant once the class is initialized. The trade-offs: it is lazy at the granularity of the holder class, and if the constructor throws, the class is marked failed and every later call gets NoClassDefFoundError.

Debug
A service formats and parses dates through private static final SimpleDateFormat FMT. Under load, some log lines show impossible dates, and once in a while a NumberFormatException appears from inside the date parsing. Explain and fix.
Model answer

SimpleDateFormat is not thread-safe: it keeps intermediate parsing and formatting state in its own fields, including a shared Calendar. Making the field static final shares one instance with every request thread, so concurrent calls overwrite each other's intermediate state. That produces wrong dates, and sometimes inconsistent internal state that makes the number parsing inside it throw. The final only fixes the reference, not the object's state.

Fix: replace it with java.time: a static final DateTimeFormatter (for example DateTimeFormatter.ofPattern("yyyy-MM-dd")) with LocalDate.parse and format. DateTimeFormatter is immutable and safe to share. If the legacy type must stay, give each thread its own instance with ThreadLocal.withInitial(...), or create one per call; a lock around it would work but serializes every request on date formatting.
