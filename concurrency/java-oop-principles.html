Encapsulation, composition and SOLID

Design Java objects that preserve their invariants, own their mutable state, expose useful contracts and accept testable dependencies.

Before this:Classes, interfaces and inheritancefinal, immutability and records

A class can have private fields and still let callers break every important rule. Good object design makes invalid changes difficult to express, and gives you a small boundary within which to prove thread safety.

In plain words

A cloakroom has ten numbered hooks. Customers ask the attendant to accept or return a coat; they do not reach behind the counter and edit the register. The attendant checks for a free hook and records the coat as one action.

Now imagine two attendants. A private register still needs a shared procedure so they cannot both allocate the last hook. Controlling access and coordinating access solve different parts of the same problem.

Why this matters for concurrency

Locks protect rules about state. Encapsulation limits which code can change that state, composition keeps the synchronization boundary under your control, and immutable results let callers work after the lock is released.

In an LLD round, explain the contract before selecting a collection or lock. This lesson builds on class and interface syntax and immutability and defensive copying. For overriding and dispatch, use inheritance and polymorphism; for pattern implementations, continue to design patterns for LLD.

Encapsulation means preserving a rule

A class invariant is a condition established by construction and preserved by every externally observable operation. For a bounded inbox: capacity > 0, 0 <= size <= capacity, no null messages, and FIFO removal. A method may change several fields internally, but must restore the invariant before releasing its lock or allowing outside code to observe the object, including on exceptional exits.

Private fields are a mechanism, not the finished design. Public setters for capacity and size still let callers create impossible states. Prefer offer(message), which checks capacity and either adds the message or returns false without changing anything.

Design questionBounded inbox answer
What must always hold?The queue contains at most capacity non-null strings
Who owns mutable state?The inbox alone creates and retains its deque
What is one operation?Check capacity and insert together, not size() followed by add()
What does failure do?Invalid input throws before mutation; a full inbox returns false unchanged
What can callers retain?Immutable strings and independent, unmodifiable snapshots

Follow the invariant across all fields and accesses, rather than adding a separate lock per getter. The proof technique is in invariants and critical sections.

Composition: own a delegate and expose a smaller contract

Composition means an object contains collaborators; delegation means it forwards work to them. Our inbox uses an ArrayDeque for storage, but exposes only inbox operations. Extending ArrayDeque would inherit mutation methods that do not know about our capacity rule or lock.

The interface's contract says offer, poll and snapshot each behave atomically for concurrent calls. offer appends a non-null message or returns false unchanged when full; a null argument throws NullPointerException. poll removes the oldest message or returns null when empty, and snapshot returns a non-null, unmodifiable list in FIFO order that later inbox changes cannot alter. These operations do not wait for space or messages, but may wait to acquire the lock.

The output is accepted=1, snapshot=1, remaining=0; which sender wins is unspecified. Each worker writes a different array element, and the main thread reads them after join. The APIs are covered in the thread toolkit and the synchronized toolkit.

The wrapper owns the only path to its delegate. Retaining an arbitrary mutable deque passed into the constructor would let its original owner bypass our lock. Two wrappers with different locks around the same deque would also be unsafe. Create the delegate internally, copy stable input, or enforce a documented ownership transfer.

The wrapper is final to keep this implementation's proof local; callers can still supply another Inbox implementation. Reads and writes take the same lock, including copying the snapshot. Copying after unlocking could race with a writer. Immutable strings make the returned snapshot safe to inspect without our lock.

Choose inheritance when the base is designed for extension and the subtype preserves its full contract. A custom Clock, used below, is one such extension point. Extending a collection merely to reuse storage also inherits its entire API and couples you to how its methods call one another; composition avoids that obligation.

Worked example: the last free slot

Suppose an initially empty inbox exposes separate size() and add() methods, each using the same lock, but add() inserts without checking capacity. Both callers can correctly observe zero and then add. The resulting size is two even though the intended capacity is one.

The fix is an API decision as well as a locking decision: expose the entire state transition. A snapshot is for observation; it never reserves future capacity. Continue to check then act for the general race, and linearizability for the precise meaning of an atomic operation.

Wrapping several calls in synchronized (inbox) does not exclude callers using the inbox's private lock: these are different monitors. If clients need another compound action, add an operation that preserves its whole invariant inside the inbox.

Defensive copies protect ownership, not just syntax

A defensive copy prevents an alias held by a caller from changing your representation. Apply the earlier copying rules at an invariant boundary: take an owned representation, validate it, then retain it. Here, an accepted batch must be nonempty and contain unique, nonblank job IDs.

There is no need to copy String elements. If the batch held mutable Job objects, copying the list alone would preserve aliases to those jobs; convert them to immutable values or copy the relevant mutable state too. The Java 21 List.copyOf contract promises an unmodifiable list independent of later source collection changes, not deep immutability of its elements.

A defensive copy is not a concurrent snapshot protocol. The caller must keep the source stable while this constructor copies it, or provide suitable snapshot semantics. Validating the copy avoids retaining unchecked state, but cannot make concurrent reads of an ordinary mutable source coherent.

An immutable value removes future mutations from the reasoning. Retain a batch for retries or pass it to a worker without worrying that the producer will clear it. Publishing the reference still needs an appropriate handoff, and replacing shared values still needs writer coordination. See safe publication and immutable snapshots.

SOLID: five questions to ask about a design

SOLID is a set of design principles, not a requirement to create five interfaces. Use each principle to justify a boundary that solves an actual change or correctness problem.

PrincipleQuestion to askSmall Java example
Single responsibilityWhich independent reason would make this class change?QuoteService calculates a fee; a separate formatter decides how to display it
Open/closedCan a supported variation be added without rewriting stable orchestration?Add another FeePolicy instead of another provider branch in quote
Liskov substitutionDoes every implementation preserve what callers are entitled to rely on?Every JobReader returns a non-null, unmodifiable snapshot
Interface segregationDoes this client depend only on capabilities it needs?A report takes JobReader, not a repository requiring delete and repair operations
Dependency inversionDoes high-level policy depend on a suitable abstraction rather than a chosen external mechanism?QuoteService accepts FeePolicy; application setup chooses the implementation

Single responsibility, open/closed and dependency inversion

A class can have several methods and one responsibility. Conversely, one large method can mix pricing, database writes and formatting, which change for different reasons. Keep state that must change atomically together; single responsibility does not mean splitting one invariant across unrelated objects.

Application setup is allowed to name concrete classes: something must choose them. Open/closed protects the intended extension point; it does not mean existing code can never change. For two stable cases, a simple branch may be clearer than a hierarchy.

A final dependency reference does not make the dependency thread-safe. These fee policies are stateless, so concurrent calls do not share mutable working state. A replacement that caches results or counts calls must be thread-safe or confined to one thread; separate service locks cannot protect one policy shared between them. If QuoteService is promised safe for concurrent use, document that requirement on supplied policies.

Liskov substitution and interface segregation

Matching method signatures is only the start. A substitute must accept the inputs its contract accepts, preserve promised results and invariants, and honour documented failure behaviour. It must not strengthen preconditions or weaken postconditions. If a contract promises atomic operations for concurrent callers, a replacement cannot silently require callers to add a lock.

The next interface promises an unmodifiable snapshot with immutable elements and no nulls. It permits readers to represent different data sources. A fixed reader and a mutable store can both satisfy it. This small example is confined to one thread; the interface makes no concurrency promise.

Returning null for an empty reader, or exposing a mutable live list, would violate this contract. Implementing a mandatory write operation by always throwing UnsupportedOperationException would also violate a promise to support that operation. This is not a blanket rule against that exception: JDK interfaces such as List explicitly allow optional operations. Read the actual contract.

Separating capabilities avoids forcing a read-only implementation to pretend it can write. It makes the report's needs visible, though an interface reference is not a security boundary against a caller who can downcast. Program to the smallest useful contract, not the smallest number of methods at any cost.

Constructor injection: make time a supplied dependency

Constructor injection means supplying a collaborator when you construct its consumer. Required dependencies become explicit and can be kept in final fields; tests can supply controlled alternatives. No framework, annotations or global service registry are needed.

Dependency inversion is the design principle; injection is a wiring technique. Injecting a concrete database client is still injection, even if the consumer remains coupled to that client. Programming to abstractions does not require an interface keyword everywhere: java.time.Clock is an abstract class.

Clock API cardSemantics
Clock.systemUTC()System time with UTC as its zone
Clock.fixed(instant, zone)Always returns the supplied instant
Clock.offset(base, duration)Returns the base clock's instant plus an offset; does not advance a fixed base
clock.instant() or Instant.now(clock)Reads an Instant from the supplied clock
clock.millis()Reads epoch milliseconds, not elapsed time
clock.getZone(), clock.withZone(zone)Reads the zone or returns a clock using another zone; changing zones does not shift the instant

The Java 21 Clock contract requires every implementation to be thread-safe, including mutable test clocks. A fake can keep its current instant in an AtomicReference<Instant>; an advance based on the previous instant needs an atomic update or a lock, not separate get and set calls. Thread safety alone does not make the fake advance monotonically.

Production wiring can pass Clock.systemUTC() to the same constructor. The test prints expired before/at/after: false/true/true. Keeping the dependency fixed does not freeze time: a system clock continues to move. The result is a decision at one sampled instant, not a reservation that remains valid forever.

Tandem's seat booking and TTL cache harnesses use a LongSupplier for controlled milliseconds. This is the same injectable clock design idea with a different time contract: relative expiry can use a monotonic ticker with an arbitrary origin. A system clock::millis supplies wall-clock milliseconds, so it cannot satisfy a promise that time never goes backwards merely because the units match.

Injectability does not make a clock monotonic. For elapsed budgets and refill intervals, use a monotonic ticker based on System.nanoTime, as covered in Java time and deadlines. If expiry governs a mutable transition, the time check and transition still need coordination; see concurrent caches and testing concurrent code.

Common mistakes

  • Private fields plus unrestricted setters. Expose valid state transitions and document failure behaviour.
  • Leaking the delegate. A getter, iterator or live view can escape the synchronization boundary. Return a suitable snapshot.
  • Assuming composition automatically provides thread safety. Every access must follow the same policy, including aliases retained by the delegate's original owner.
  • Treating an unmodifiable collection as deeply immutable. Audit its elements, and keep the source stable while copying.
  • Calling arbitrary injected code while holding a lock. It may block or call back into your object. Design the boundary deliberately; see the rules of locking.
  • Replacing a dependency with an incompatible fake. A fake must obey the contract, including concurrency and failure semantics relevant to the test.
  • Turning SOLID into class counting. Add a boundary for a concrete responsibility or variation, not one interface for every field.

In the interview

Expect prompts such as "make this class thread-safe", "why composition here?", or "test expiry without waiting". Start with state ownership and the invariant, show the operation that preserves it, then explain how dependencies and observations cross that boundary.

I would expose offer as the atomic operation, own the deque privately, and protect its capacity check and insertion with one lock. Callers receive immutable snapshots. I can change storage without exposing a different mutation path.
I use SOLID to keep contracts honest and changes local. I inject time so tests control the boundary exactly, but I still choose the right time source and synchronize any state transition that depends on it.

Likely follow ups: "What if the delegate was passed in?", "What if snapshot elements are mutable?", "Can an implementation throw for an operation it does not support?", and "Does a fixed clock make the whole service thread-safe?" Answer each from the contract, not from the acronym.

Key takeaways

  • Encapsulation protects invariants through valid operations, not just private field declarations.
  • Composition gives you control over the API; exclusive ownership makes its synchronization policy enforceable.
  • Copies and immutable values prevent later alias mutations; copying a changing source still requires a protocol.
  • SOLID guides responsibility, extension, substitution, client capabilities and dependency direction.
  • Constructor injection makes collaborators explicit; Clock enables exact tests but is not a monotonic ticker.

Quick check

Answer each question, then read why. Your score is saved for your module test.

An initially empty inbox is intended to hold at most one message. Its size() and add() use the same lock, but add() inserts without checking capacity. Two callers each execute if (size() == 0) add(message). What is possible?
Why. Both checks can observe zero before either insertion, so the size can become two. The common lock prevents data races on the deque, but not this race between complete method calls. The inbox must own the whole check and insertion in one operation; making capacity volatile does not join the calls.
What does this print when using the lesson's JobBatch?
Why. The batch retained an unmodifiable snapshot and its string elements are immutable. The original draft is still mutable, so changing it succeeds without changing the batch.
Which changes invalidate the bounded inbox's thread-safety argument? Select all that apply.Select all that apply
Why. The first two create access paths outside the common lock; the last races the copy with writers. Creating and retaining the delegate inside the wrapper preserves ownership.
JobReader.snapshot() promises a non-null, unmodifiable snapshot. A replacement returns null when there are no jobs. Which principle most directly identifies the defect?
Why. A caller entitled to iterate a non-null result breaks under this replacement. Substitution is about behaviour, not merely matching a method signature. Handling an empty result is part of the same responsibility, open/closed allows new implementations, and interface segregation sets no minimum method count.
A reporting class accepts JobReader, while an updater accepts JobWriter. What benefit does interface segregation provide?
Why. The contracts describe client needs without making readers implement unsupported writes. They neither supply locking nor require separate storage, and they are not a security sandbox.
A service accepts a Clock but its expiry method calls Instant.now() with no argument. Why do fixed-clock tests still depend on real time?
Why. Use Instant.now(clock) or clock.instant(). Clock.fixed never advances, and Clock is an abstract class that can still be injected. Passing a collaborator helps only when the consumer actually uses it; volatile does not change which clock gets read.
A developer passes Clock.systemUTC() into a token refill algorithm that assumes time never moves backwards. What remains wrong?
Why. UTC is a zone choice, not an elapsed-time guarantee. A system wall clock may be adjusted. Inject a monotonic ticker for elapsed refill calculations, and reserve absolute instants for contracts that need them.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A class synchronizes snapshot() but returns Collections.unmodifiableList(internalJobs), where internalJobs is an ordinary ArrayList containing no nulls. Other methods append jobs under the same lock. Is the returned value safe for a caller to iterate after snapshot() returns? Repair the design, including the case of mutable job elements.
Model answer

No. The view reads the original list after the lock is released, so iteration can race with later writes. Copy while holding the same lock. With immutable elements, List.copyOf(internalJobs) is enough. With mutable elements, construct immutable job summaries while their fields are stable, or take suitable element copies under the policy that guards those fields. Copying references does not protect their contents. The caller can then retain the result without participating in internal locking.

Design
A thread-safe inbox is implemented by subclassing a mutable collection and overriding only add. Explain a composition-based replacement and its trade-off.
Model answer

Inherited methods can mutate state without the capacity check or locking. Define an inbox contract with atomic offer, poll and snapshots, backed by a privately owned deque. Every access takes one private lock; no live iterator, view or delegate escapes. Reject invalid capacity and messages before mutation. Copy and validate stable initial contents instead of retaining a caller-owned mutable collection. Composition requires forwarding methods and is not a drop-in replacement for the full collection API; that smaller API is intentional. The monitor object pattern generalizes this design when waiting is needed.

Explain
Distinguish dependency inversion from constructor injection using an expiry service. State three exact boundary tests and one remaining concurrency obligation.
Model answer

Dependency inversion keeps expiry policy dependent on a time abstraction rather than hard-coded system time. Constructor injection supplies it explicitly: take a Clock, validate it and store it in a final field. With inclusive expiry, fixed clocks one nanosecond before, exactly at and one nanosecond after the deadline must return false, true and true. All time reads must use the injected clock. If expiry decides whether a hold can be confirmed, the check and confirmation must participate in the same synchronization protocol. A fake clock makes time deterministic, not that transition atomic.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"All the fields in this class are private. Why are you still worried about encapsulation and thread safety?"
What a strong answer covers
  • Private access alone does not preserve a class invariant or coordinate threads
  • An alias returned by a getter can bypass the class's locking policy
  • Separate size and unchecked add calls can both be locked but exceed capacity together
  • Expose offer as one check and update under the same private lock used by readers
  • Return an independent snapshot with immutable elements and keep the delegate owned
How a senior would say it
Private fields are a useful starting point, but I need to know which rules the public operations preserve and whether any aliases escape. A getter that returns the internal list lets a caller mutate it without taking our lock. Even if no reference escapes, separate size and unchecked add methods can each be synchronized and still allow two threads to fill the last slot. Both can observe space before either adds. I would expose offer as the operation: it checks capacity and inserts while holding one private lock, or returns false without changing state. Reads of the deque take that same lock. For inspection I would copy the contents while locked and return an unmodifiable snapshot whose elements are immutable. The caller can then use that result independently. I would also check construction: if we retain a deque supplied by somebody else, that owner may still bypass our wrapper. The proof needs ownership and valid state transitions as well as access modifiers.

Likely follow up: Would an unmodifiable view of the internal list be enough?

Out loudabout 75 s
"Why would you choose composition here, and how does that relate to SOLID?"
What a strong answer covers
  • Composition keeps the inbox API and synchronization boundary under its owner's control
  • Inheritance would expose mutation paths that may bypass the inbox invariant
  • Liskov substitution requires preserving behaviour, including promised thread safety
  • Small reader and writer capabilities illustrate interface segregation
  • Abstractions support needed variations without requiring an interface for every class
How a senior would say it
I would choose composition because an inbox needs a small set of operations, while inheriting a collection exposes many ways to mutate its contents. Owning a private deque lets me enforce capacity and locking at one boundary. That connects to substitution: any implementation of my inbox interface must keep its behavioural promises, including atomic admission for concurrent callers. Matching signatures is not enough. Interface segregation asks a related question from the client's side. A reporting client may need only snapshots, so it should not depend on deletion or repair methods. Dependency inversion lets the client rely on that capability while application setup chooses the implementation. I would introduce those boundaries where they clarify real requirements. I would not create a large hierarchy just to claim SOLID compliance. The trade-off is writing some forwarding code in exchange for a contract I can explain and enforce.

Likely follow up: When would inheritance be a reasonable choice instead?

Out loudabout 75 s
"Our expiry tests sleep and occasionally fail. How would you redesign the time dependency?"
What a strong answer covers
  • Inject a Clock through the constructor and use it for every time read
  • Define the inclusive expiry boundary explicitly
  • Test just before, at and after expiry with fixed clocks and no sleeps
  • Distinguish an absolute wall-clock deadline from a monotonic elapsed budget
  • Keep any expiry check and dependent mutation correctly coordinated
How a senior would say it
I would pass a clock into the constructor and make every time read use it. Production can supply a system clock; tests can supply fixed instants. First I would define the boundary: an item is expired when now is equal to or after its deadline. Then I can test one nanosecond before, exactly at and one nanosecond after the deadline without sleeping. The expected answers are false, true and true. I would also check what kind of time the requirement means. An absolute calendar deadline can use an instant from a clock. An elapsed timeout or token refill budget needs a monotonic ticker instead. Injecting time makes the tests controllable; it does not provide that monotonic guarantee. Finally, if checking expiry authorizes a state change, I still need to coordinate the check and mutation so another thread cannot invalidate the decision in between.

Likely follow up: What must be true of a mutable fake clock shared by several test threads?
