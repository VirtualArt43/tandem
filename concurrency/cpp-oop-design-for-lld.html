Object oriented design for LLD and machine coding rounds

Turn requirements into class invariants, injected dependencies, small design patterns, and thread safe operations with explicit ownership and shutdown.

Asked atMicrosoftRubrik
Before this:Polymorphism, abstract classes and operator overloadingconst correctness and mutable

A machine coding answer is a small working system, not a diagram with the most patterns. Start with the state that must remain true, then choose the objects and operations that make it hard to violate.

In plain words

A booking desk does not hand customers its cash drawer and ledger. It offers operations such as reserve and cancel, each of which keeps the books consistent. A class does the same job: it owns the records and controls the changes that are allowed.

Why this matters for concurrency

Two individually sensible methods can become wrong when callers compose them. A public balance getter followed by a public setter cannot enforce a concurrent withdrawal. The lock belongs with the invariant, and the API must expose the whole operation. The core lesson on check then act explains the interleaving; this lesson builds the C++ boundary that prevents it.

Encapsulation means preserving an invariant

An invariant is a statement that every observable valid state satisfies: stock is nonnegative, a booking has one state, or queued work never exceeds capacity. Private fields help, but a public setter that accepts any value still breaks encapsulation. Write operations named after valid transitions, validate before mutation, and return a meaningful outcome when the operation cannot proceed.

Decide the exception guarantee too. A lock guard releases a mutex if an operation throws; it does not roll back a partially modified ledger. The basic guarantee preserves invariants and leaks no resources; the strong guarantee also leaves observable state unchanged on failure. Compute fallible work before committing, or prepare replacement state and commit with a swap that cannot throw.

Preparation based on shared state must stay under its lock, or you must revalidate after reacquiring it. If a transaction spans several fields, protect their relationship with one synchronization boundary. Atomic fields do not automatically create an atomic transaction.

Composition before inheritance

A reservation service has a clock and a storage dependency; it is not a clock or a database. Store those dependencies as members or references. Public inheritance is for substitutable contracts, not merely sharing lines of code. Composition makes replacement, testing, and ownership visible without exposing protected state to arbitrary subclasses.

A borrowed reference requires the dependency to outlive the service and every operation using it. A std::unique_ptr transfers ownership when moved. Separate std::shared_ptr handles can safely share ownership bookkeeping, but that does not protect the object's mutable state or concurrent mutation of one shared handle. Declare those choices before adding threads.

Keep polymorphic objects behind references or owning pointers: copying a derived object into a concrete base value slices off the derived part. Deleting a derived object through an ordinary std::unique_ptr<Base> requires a public virtual base destructor. A class containing std::mutex is normally neither copyable nor movable; keep its address stable, or design explicit snapshot and ownership-transfer operations instead of trying to copy its lock.

SOLID as five practical design checks

Single responsibility: separate changes that have different reasons to happen. Formatting a report and reserving stock should not require editing the same class. Do not interpret this as one class per method.

Open for extension, closed for modification: isolate the part likely to vary. A shipping calculator accepts a pricing strategy instead of growing a switch every time a new pricing policy arrives. A closed enum is still a good choice when the cases are fixed and exhaustive checking is valuable.

Liskov substitution: a derived implementation must keep the base contract. If Readable::read() promises a nonmutating operation, a subclass must not silently consume the only copy of the data. A subclass cannot strengthen required preconditions or weaken promised outcomes. This is a behavioral rule that override cannot prove.

Interface segregation: clients should depend on the operations they need. A read-only index should not implement a fake throwing write() just because a giant repository interface requires it.

Dependency inversion: business policy depends on a contract, not a hardcoded system clock or socket constructor. Constructor injection makes that dependency explicit. A fake then controls tests without sleeps. This does not require a dependency injection framework.

A clock and a state machine you can test

The reservation accepts a deadline in milliseconds from its injected clock's epoch. confirm() succeeds only once, if its clock read is before the deadline; confirmation is then permanent. Expiry is lazy: confirm() and refresh() expire a held reservation when their clock read reaches the deadline. state() returns the stored state, so it can still report held after the deadline until a transition checks time.

The clock contract is nondecreasing ticks, safe concurrent reads, and no exceptions. std::chrono::steady_clock has an unspecified epoch, not a Unix timestamp; construct deadlines from the same clock and check for overflow when adding a duration. Signed deadlines are valid, including past ones. The fake starts at zero and advance_to() takes the maximum of its current value and the supplied value.

The fake uses an atomic because tests may advance it during reads. A failed compare_exchange_weak updates old with the observed value; the loop retries while an advance is still needed. The service reads time while locked, so clock implementations must be short and must not call back into the reservation or wait on its work. This trusted dependency is a narrow exception to keeping arbitrary user code outside internal locks.

enum class scopes its enumerators and prevents accidental integer conversions. mutable permits the const getter to lock the mutex without making the logical reservation state mutable. lock_guard owns the acquisition until its scope ends; the mutex lesson explains that syntax in detail. The private _locked helper states its precondition in its name and does not acquire the same nonrecursive mutex again.

The runnable examples use C++20 std::jthread. With C++17, use std::thread and an RAII joiner that joins every started thread on both normal and exceptional exits. A plain join loop alone misses exceptions during thread creation. See the thread toolkit for that ownership pattern.

Observer: snapshot membership, then invoke outside the lock

An observer registry connects publishers to listeners. Its mutex protects membership, not arbitrary listener code. Snapshot shared handles while locked, release the lock, then invoke callbacks. Copying std::function targets instead can run user-defined copy constructors under the lock and gives each publication a separate copy of mutable value-captured state.

Construct each callable before locking and retain it with std::shared_ptr<const Listener>. The const wrapper prevents replacement of the callable, but does not make the callable's captured data immutable or thread safe. The snapshot preserves listener identity and lifetime while callbacks can reenter registration without taking an already held registry lock.

The first publication excludes the new listener. The first counter receives 1 + 3 + 200, while the added listener receives 3 + 200. Concurrent publications can call the same listener simultaneously; their shared counters are atomic. The final failure check runs after joining publishers, so its plain tail counter is confined to the main thread.

Each publication calls its snapshot in registration order, but different publications can interleave and there is no global event order. A slow listener delays later listeners in that publication, though it does not hold the registration mutex. Snapshot storage costs O(n) time and space for n listeners, excluding callback work; allocation can throw before any delivery. Callback exceptions are instead counted and delivery continues.

A production unsubscribe API must decide whether removal prevents only future snapshots or also waits for in-flight callbacks; the latter needs per-listener activity tracking. Avoid a callback waiting for itself to finish, and release the last ownership handle outside the registry lock because destroying a callable can run user code too. Snapshot ownership keeps the callable alive, not objects captured by reference: those objects and the registry must outlive all active operations. A callback owning its publisher can form a cycle; capture a std::weak_ptr and lock it when needed if that ownership relationship would otherwise leak.

Factory, singleton, and builder without ceremony

A factory centralizes construction and returns a finished object behind its contract. For example, with <memory> included, std::unique_ptr<Clock> make_clock() can return std::make_unique<SteadyClock>(). A configuration-based factory selects implementations without spreading construction switches across callers. Validate configuration before publishing the object or starting its workers.

Since C++11, initialization of a function local static is synchronized: concurrent entrants wait for its initialization to finish. If initialization throws, a later call retries. That protects initialization, not future mutations of a mutable singleton. Recursive reentry during its own initialization is undefined behavior, and static destruction order can complicate shutdown. Prefer injected dependencies in tests; a singleton adds process-wide lifetime and hidden coupling.

A builder collects optional settings and validates once at build(). The fluent setters return a reference to the same builder. PoolConfig is an ordinary mutable value; make the built object const or give each worker a private copy, and validate again if later mutation is allowed. Do not share the mutable builder across threads; two required parameters usually need only a constructor.

Give lifecycle its own contract

For an object owning workers, define running, closing and closed states. Stop admission and choose whether to drain or cancel accepted work, wake blocked workers, then join them before destroying their dependencies. Do not join while holding a mutex those workers need to exit, and define concurrent repeated close() calls explicitly.

A destructor cannot safely race with callers still using the object. The owner must end those calls before destruction, and constructors must not publish this or start callbacks against partially initialized state. C++ destroys members in reverse declaration order; place workers after the state they access, but still perform the required stop and wake protocol. std::jthread requests stop and joins; it cannot force an uncooperative function to return.

Worked example: lay out the machine coding answer

  1. Clarify operations, invalid inputs, capacities, ownership, time boundaries, and shutdown.
  2. For one reservation, write two invariants: confirmed and expired are terminal, and at most one confirmation succeeds.
  3. Expose confirm(), refresh() and a stored-state snapshot; keep the transition helper private.
  4. Inject a borrowed clock whose lifetime covers all operations. Protect the check and transition with the reservation's mutex.
  5. Walk through the timeline: A reads 99, B waits, time reaches 100, A confirms, and B fails. Swapping A and B changes the winner, not the invariant.
  6. Test before, at, and after the deadline, repeated calls, and contending confirmations. For observers, add reentrant registration and a throwing listener.

For a real stock service, a reservation's private lock is insufficient: competing reservations must share the synchronization that protects the stock. A process-local mutex also cannot coordinate another server; a database constraint or transaction must protect persistent stock. Rubrik's reported pool shutdown and task exception follow-ups and Microsoft's reported singleton questions make lifecycle details practical preparation.

Common mistakes

  • One mutex per field when an invariant spans fields: guard the relationship.
  • Calling arbitrary callbacks while locked: use a snapshot and define delivery semantics.
  • Assuming const getters need no synchronization: const describes the interface, not concurrent writers.
  • Using singleton initialization as proof that all singleton methods are safe: mutable operations still need a protocol.
  • Adding interfaces for every noun: introduce abstractions where behavior actually varies.

In the interview

I will first define the invariant and the transition that preserves it. The class owns its mutex, dependencies have explicit lifetimes, and user callbacks run after unlocking. I can test deadline boundaries with a fake clock and explain exactly what shutdown waits for.

For follow-ups, discuss observer unsubscription, strong exception guarantees, and whether separate objects can progress concurrently. Continue with mutex syntax and the complete worker component.

Key takeaways

  • Encapsulation protects valid transitions, not just private fields.
  • Compose dependencies and use inheritance for substitutable contracts.
  • Inject time and external behavior so tests control difficult cases.
  • Snapshot observer membership under the lock and invoke after releasing it.
  • Keep the mutex beside the state; a const getter may need a mutable mutex.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
Specify an observer unsubscribe operation when publish() uses a membership snapshot.
Model answer
A simple contract removes a registration token from future snapshots but allows already captured deliveries. For a stronger guarantee, give each registration an active flag and in-flight count protected together: publishers check active and increment before invoking, then decrement on every exit. Unsubscribe marks inactive, removes membership, and waits outside the registry lock for the count to reach zero. A captured publisher that has not entered skips an inactive listener. Blocking unsubscribe from a callback can deadlock on itself or another callback, so provide nonblocking removal there and a separate wait from an external owner. Release the final listener handle outside registry locks.
Debug
A const getter races with a setter even though callers use only the public API. What is wrong?
Model answer
Const prevents ordinary mutation through that method; it does not stop other threads from modifying the object. Guard reads and writes with the same mutex, marking the mutex mutable for the getter. Return a value snapshot rather than a reference that escapes protection.
Design
When would you reject a builder or a singleton in a machine coding answer?
Model answer
Reject a builder when a short constructor already expresses the required configuration clearly. Reject a singleton when ownership should be scoped, tests need independent instances, or shutdown must be controlled. Inject the dependency and use a factory if construction varies.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Walk me through how you would structure a thread safe reservation in C++."
What a strong answer covers
  • Clarify deadline and state semantics
  • Write the invariant and transitions
  • Put the lock with the complete state
  • Inject time with an explicit lifetime and test boundaries
How a senior would say it
I start with the state transitions. A held reservation can become confirmed or expired, and both outcomes are terminal. One mutex protects the check and transition, so only one confirmation succeeds. I inject a clock by reference and require it to outlive the reservation and all callers. A clock read before the deadline permits confirmation, even if the call returns later; equality expires the hold. Expiry happens when a transition checks time, while the const getter only reports stored state. I test before, at, and after the deadline, then repeated and contending confirmations. A full inventory service also needs synchronization shared by every reservation competing for that stock.

Likely follow up: How would you prove that two confirmations cannot both succeed?

Out loudabout 60 s
"Why do you snapshot listener handles before calling them, and what does that choice cost?"
What a strong answer covers
  • Snapshot shared listener handles while protecting membership
  • Run callbacks after releasing the lock
  • Allow reentry and avoid lock-held latency
  • Define snapshot delivery and concurrent callback behavior
  • Explain O(n) snapshot cost and captured-object lifetimes
How a senior would say it
I snapshot shared handles under the registry mutex, then unlock before invoking listeners. Copying handles preserves listener identity and avoids copying user callables under that lock. A callback can register another listener, and slow delivery does not block registration. The snapshot costs linear time and space. With simple removal, already captured deliveries can still run. Concurrent publishers may invoke the same callable together, so its state needs its own synchronization; a const function wrapper does not make that state immutable. The handles keep callables alive, but objects captured by reference still need valid lifetimes. I count callback failures and continue to remaining listeners.

Likely follow up: How would unsubscribe wait until every earlier delivery has finished?

Out loudabout 60 s
"A class owns a worker and its destructor sometimes hangs. What would you check?"
What a strong answer covers
  • Check that shutdown rejects new work and wakes blocked workers
  • Check that joining holds no lock the worker needs
  • Check cooperative stop handling and dependency destruction order
  • Require callers to finish before destruction begins
How a senior would say it
I first check the shutdown protocol. It should reject new work, decide whether accepted work drains, and wake any worker waiting for input. Then I check whether the destructor joins while holding a lock the worker needs to finish. That creates a deadlock. A jthread requests stop and joins, but the task must cooperate and blocking waits need a wakeup path. The worker must finish before its mutex, queue, or borrowed dependencies are destroyed. I also require the owner to finish external calls before destroying the object. Concurrent close calls need a separate contract; a destructor is not a safe race against ongoing calls.

Likely follow up: What happens if a callback tries to close and join its own worker?
