C++ memory orders: seq_cst, acquire, release and relaxed

The C++ memory orders you will actually use, what each one buys, how Java expresses the same ideas, and how interviewers test them.

Before this:Happens-before and synchronizes-withvolatile in Java, std::atomic in C++

Every std::atomic operation takes an optional memory order. The default is the safest and usually fast enough; the weaker ones exist for hot paths and for building synchronizers. Interviewers use them to separate candidates who memorized the words "acquire" and "release" from candidates who can say exactly what each one buys, and what it does not.

In plain words

Think of an office mailroom. Release is sealing an envelope with everything you prepared inside and dropping it in the outgoing tray. Acquire is the recipient taking that envelope from the tray and only then reading its contents: whatever you put in before sealing, they will find. Relaxed is a tally clicker at the door: every click is counted exactly, but the clicker says nothing about anything else in the building. Sequentially consistent is a single announcement board that everyone reads in the same order.

Java has the same ideas under different names (volatile, and VarHandle modes). If you code in Java, read this lesson for the vocabulary and the mapping: the words acquire, release and sequential consistency are how memory model questions are discussed in any language.

Six orders, and the three you will use

A memory order tells the compiler and CPU how other memory operations may be reordered around an atomic operation. C++ has six:

OrderUsed onWhat it adds beyond atomicity
memory_order_relaxedany operationNothing: no ordering of other memory, no synchronization
memory_order_consumeloadsOrdering only for data that depends on the loaded value. Discouraged; compilers treat it as acquire
memory_order_acquireloads, read-modify-writesLater reads and writes stay after it; pairs with a release
memory_order_releasestores, read-modify-writesEarlier reads and writes stay before it; pairs with an acquire
memory_order_acq_relread-modify-writesBoth of the above, for an operation that reads and writes
memory_order_seq_cstany operation (the default)Acquire and release, plus one total order of all seq_cst operations that every thread agrees on

In practice: seq_cst by default, acquire and release for hand-offs, relaxed for counters. Passing an order that does not fit the operation, such as store(v, std::memory_order_acquire), is undefined behavior; clang warns about it.

seq_cst: the default

A sequentially consistent operation is an acquire (if it reads) and a release (if it writes), and on top of that all seq_cst operations in the program fall into a single total order consistent with each thread's program order. That extra total order is what forbids the store buffering outcome from reordering: with seq_cst on all four operations, at least one thread must see the other's write. It is also what makes a race free program that uses only seq_cst atomics and mutexes sequentially consistent, so plain interleaving reasoning works.

What does it cost? Less than its reputation. On x86, every load is an ordinary mov whatever the order; only a seq_cst store costs extra (compilers emit xchg, or mov followed by mfence; either way the core waits for its store buffer to drain). On ARM, seq_cst loads and stores are ldar and stlr. The weaker orders also give the compiler more freedom, which matters in tight loops. The rule senior engineers follow: keep the default unless you can name the edge you need and you have measured a reason.

Acquire and release: message passing done right

Acquire and release are one-way barriers that work in pairs:

  • A release store: no read or write that comes before it in program order may be moved after it. Everything you wrote before it is "sealed in the envelope".
  • An acquire load: no read or write that comes after it may be moved before it. You open the envelope before reading what is inside.
  • When an acquire load reads the value written by a release store (on the same atomic), the release synchronizes with the acquire, and everything before the release happens-before everything after the acquire.

In Java you would normally just make ready volatile, which is stronger (it behaves like seq_cst); the only extra cost is on the store, a full fence on x86, which matters only on a hot path. The VarHandle version shows the exact equivalent. Note what happens if either side is weakened: a relaxed store or a relaxed load breaks the pair, and the reader can see ready == true with an old payload.

You have used this pair all along without naming it: locking a mutex is an acquire operation and unlocking it is a release, which is why everything written inside one critical section is visible in the next one. A hand-written spinlock spells it out: exchange(true, std::memory_order_acquire) to take the lock, store(false, std::memory_order_release) to give it back.

What acquire and release do not give you

Because the barriers are one-way, a release store followed by an acquire load to a different variable may still be reordered: the store's barrier only holds back earlier operations, and the load's barrier only holds back later ones. So the store buffering test is not fixed by acquire and release:

On x86 this really happens, because release stores and acquire loads compile to plain mov instructions and the store buffer does the rest. The ARM architecture allows it too (an stlr followed by an ldapr to another address may be reordered), although the Apple chips this site runs on did not show it in our tests; that proves nothing about the language rules. Whenever correctness depends on "I wrote mine, now let me check yours", as in Dekker or Peterson style mutual exclusion, you need seq_cst (or a seq_cst fence between the store and the load).

The second thing acquire and release do not give you is one order that every thread agrees on. Let thread A store x = 1 and thread B store y = 1 with release, while two readers load both variables with acquire, in opposite orders. C++ allows reader 1 to see x == 1, y == 0 while reader 2 sees y == 1, x == 0: they disagree about which write came first. This test is called IRIW (independent reads of independent writes; see reordering). x86 and ARMv8 hardware never show it, IBM POWER can, and seq_cst on all six operations forbids it everywhere.

relaxed: atomic, and nothing else

A relaxed operation still guarantees three things: it is indivisible (no torn values, no lost increments for read-modify-writes), it is never a data race, and all threads agree on a single order of writes to that one variable (once a thread has seen a value, it never later sees an older one). It does not order any other memory, and on its own it never synchronizes with anything (only a fence next to it can make it carry an edge, as you will see below).

That is exactly right for:

  • Counters and statistics that are read after a join (the join provides the ordering) or that only need to be approximately current, like a metrics gauge.
  • Unique ids: next_id.fetch_add(1, std::memory_order_relaxed) gives every caller a distinct number; nothing else has to be ordered.
  • Your own index in a single-writer structure, such as the producer reading its own tail in the ring buffer below.
  • Reference count increments: gaining a reference publishes nothing.

Java has no relaxed add: every AtomicLong add has volatile semantics, and the weakest VarHandle adds are getAndAddAcquire and getAndAddRelease. (The one plain-mode read-modify-write is weakCompareAndSetPlain, a CAS that may fail spuriously.) For a hot counter the Java answer is LongAdder, which removes the contention instead of the ordering. The closest Java mode to relaxed is VarHandle opaque access (getOpaque, setOpaque).

acq_rel: for operations that read and write

A read-modify-write such as fetch_sub, exchange or a compare-exchange both reads and writes. memory_order_acq_rel makes its read an acquire and its write a release. The textbook case is a reference count:

Why each half matters: every owner may have written to the shared object before letting go, and the last owner is about to destroy it. The release on each decrement and the acquire on the final one connect all of those writes to the destruction, through the chain of read-modify-writes on the same counter. (Library implementations often use a release decrement plus an acquire fence only when the count hits zero, which is the same idea, slightly cheaper.)

Compare-exchange takes two orders: one for success and one for failure. head.compare_exchange_weak(expected, node, std::memory_order_release, std::memory_order_relaxed) publishes a new node only when the CAS succeeds; a failed attempt just reloads expected. The failure order applies to that reload, so it may not be release or acq_rel. If you pass only one order, the failure order is derived from it: acq_rel becomes acquire and release becomes relaxed. You will use exactly this in the lock-free stack.

consume, and why it is discouraged

memory_order_consume was meant to be a cheaper acquire for pointer publishing: order only the reads that depend on the loaded pointer (like p->field), which ARM and POWER hardware already orders for free. The trouble is that compilers optimize away dependencies all the time (replacing p->field with a value they can prove, for example), and no compiler found a practical way to track them. Every major compiler simply treats consume as acquire, and C++17 formally discouraged its use. If you see it in an interview, say that, and use acquire.

Fences

A memory fence, std::atomic_thread_fence(order) in C++, is ordering without an atomic operation attached. A release fence followed by a relaxed store behaves like a release store; a relaxed load followed by an acquire fence behaves like an acquire load. The useful trick: poll with cheap relaxed loads, and pay for one acquire fence only after the loop exits.

A seq_cst fence between the store and the load in each thread also fixes store buffering, even with relaxed operations. std::atomic_signal_fence orders only against a signal handler on the same thread, so it constrains the compiler and emits no CPU instruction. In application code fences are rare; you meet them inside libraries, lock implementations and lock-free queues.

Worked example: a single producer, single consumer ring buffer

With exactly one producer thread and one consumer thread, a bounded queue needs no lock. The producer is the only writer of tail and the consumer the only writer of head, so each index has a single writer. Every slot is a little message passing problem: the producer fills it and then publishes it by advancing tail; the consumer reads it and then hands it back by advancing head.

Each order, and why it is the weakest correct one:

  1. Producer reads its own tail: relaxed. Only this thread writes it, so it always sees its own last value.
  2. Producer reads head: acquire. Pairs with the consumer's release on head, so the consumer's read of a slot happens-before the producer overwrites that slot.
  3. Producer writes the slot, then stores tail with release. The slot write cannot move below the release, so the slot is full before it is published.
  4. Consumer reads tail: acquire. Pairs with that release: the consumer sees the slot's contents.
  5. Consumer reads the slot, then stores head with release. The read cannot move below it, so the slot is not handed back while still being read.

Try breaking it. In the C++ version, change the acquire on tail_ in try_pop to relaxed and run: ThreadSanitizer reports a data race on the slot. Compiled normally with optimization, the broken ring will usually still print the right answer: in our tests on an Apple M4 it never failed in dozens of runs. That is luck, not correctness. ARM allows the CPU to perform the slot load before the load of tail when nothing orders the two loads, and then the consumer reads a slot the producer has not filled yet; a different chip, compiler or load can expose it. (A quiet sanitizer is evidence, not proof: ThreadSanitizer only reports races between accesses it actually saw in that run, within its limited history, so run a racy test many times before you trust silence.)

Common mistakes

  • A relaxed "ready" flag. Relaxed orders nothing else, so the reader can see the flag and stale data. A flag that publishes data needs release on the store and acquire on the load.
  • Weakening only one side. Release with a relaxed load, or a relaxed store with an acquire load, does not synchronize. The pair must match on the same atomic variable.
  • Expecting acquire and release to fix store buffering. They do not order a store before a later load. Use seq_cst, or a seq_cst fence.
  • Invalid orders. store with acquire or acq_rel, load with release or acq_rel: undefined behavior. Clang warns; treat the warning as an error.
  • "Relaxed is faster on x86." For loads it is identical; for stores only seq_cst costs extra. The real gain from weaker orders is often compiler freedom, so measure before and after.
  • Using consume. It is treated as acquire everywhere and discouraged by the standard.
  • Weakening orders in code that is not on a measured hot path. The cost is subtle bugs that tests rarely catch; the benefit is often nothing.

In the interview

In application-level interviews, memory orders come up as follow ups to lock-free code: a compare-and-swap stack after a locked stack (Rubrik has asked for exactly that progression), or a single producer, single consumer ring buffer after the bounded blocking queue. Systems and C++ heavy roles may ask about them directly. The questions that come up:

  • "What do acquire and release mean? Give an example." Message passing: the data, the release store of the flag, the acquire load, the guaranteed read.
  • "Why is seq_cst the default? When would you relax it?" Safety and simple reasoning; relax only on measured hot paths with a named edge: counters, single-writer indices, reference count increments.
  • "Which orders does this SPSC ring buffer need?" The five lines of the worked example above.
  • "Does acquire and release prevent the store buffering outcome?" No; explain why, and how seq_cst does.
  • "What does relaxed still guarantee?" Atomicity, no data race, and a single order of writes to that variable.
  • "Why is consume discouraged?" Compilers cannot preserve dependencies, so they promote it to acquire.
  • Java versions: "What is lazySet for?" A release store: cheaper than a volatile write when no later load needs to be ordered after it, which is why queues use it to publish slots.
I default to sequential consistency because it is easy to reason about and on x86 it only costs on stores. When I weaken it, I name the edge: here the producer publishes the slot with a release store on tail, and the consumer reads tail with an acquire load, so the slot write happens-before the slot read. Indices that only one thread writes can be read relaxed by that thread. I would not use relaxed for anything that publishes data, and acquire and release would not be enough if each thread had to see the other's write, as in Peterson's lock; that needs seq_cst.

Senior depth

What each order compiles to. These are what clang emits for a std::atomic<long> on the two architectures you will meet (checked on this site's toolchain):

Operationx86-64ARMv8 (Apple M series)
load relaxed, acquire, seq_cstmov, mov, movldr, ldapr, ldar
store relaxed, release, seq_cstmov, mov, xchgstr, stlr, stlr
fetch_add relaxed, acq_rel or seq_cstlock xadd for all (lock add or lock inc when the result is unused)ldadd, ldaddal, ldaddal
fence acquire, release, seq_cstno instruction, no instruction, mfencedmb ishld, dmb ish, dmb ish

Two things stand out. On x86 the only difference between release and seq_cst is the store, which is why the store buffering outcome is the one place x86 programs see weak ordering. On ARM, acquire uses ldapr while seq_cst uses ldar: ldar is guaranteed not to be reordered with an earlier stlr, which is exactly the store-then-load ordering that seq_cst adds.

Out of thin air. Relaxed atomics in theory allow a value to justify itself in a cycle (each thread reads the other's write of a value that only exists because it was read). No real hardware or compiler produces it, and the standard says implementations should not, but it is why formal reasoning about relaxed code is hard. Keep relaxed to counters and single-writer patterns where the question never arises.

The cost that matters. The instruction differences are a few nanoseconds; a contended cache line costs far more, an order of magnitude or two. Choosing a weaker order rarely rescues a design that has many threads writing one variable; changing the design (per-thread counters, batching) does. See caches and false sharing.

Key takeaways

  • Use seq_cst by default; it is the only order that gives one global order of atomic operations.
  • Release store plus acquire load of the value it wrote creates a happens-before edge: the tool for publishing data. Both sides must use them.
  • Acquire and release do not fix store buffering; seq_cst (or a seq_cst fence) does.
  • Relaxed is atomic and race free but orders nothing else: right for counters, ids and a thread's own index.
  • acq_rel is for read-modify-writes that both receive and publish, like the last reference count decrement. Avoid consume.
  • Java volatile is like seq_cst; setRelease and getAcquire are release and acquire; Java has no relaxed add, so hot counters use LongAdder.

Quick check

Answer each question, then read why. Your score is saved for your module test.

The writer runs data = 42; ready.store(true, release); (Java: READY.setRelease(this, true)). The reader runs if (ready.load(acquire)) print(data); (Java: getAcquire). data is a plain variable. What can the reader print?
Why. If the acquire load reads true, it read the value written by the release store, so the release synchronizes with it and data = 42 happens-before the read of data. If it reads false, nothing is printed. 0 would require the pair to be broken.
Same program, but the reader loads ready with relaxed ordering (Java: getOpaque); the writer still uses release. What can the reader print?
Why. Synchronizes-with needs a release on the writer and an acquire on the reader. With a relaxed load, the reader's read of data may be performed before its read of ready, so it can see the flag and old data. In C++ the unordered access to data is also a data race.
In the store buffering test, A runs x.store(1, release); r1 = y.load(acquire); and B runs y.store(1, release); r2 = x.load(acquire); (Java: setRelease and getAcquire). Can r1 == 0 and r2 == 0?
Why. Release only holds back earlier operations and acquire only holds back later ones, so neither stops a load from passing an earlier store. On x86 both compile to plain moves and the store buffer produces exactly this outcome. seq_cst on all four operations, or a seq_cst fence between each store and load, forbids it.
What does a relaxed atomic operation still guarantee? Select all that apply.Select all that apply
Why. Relaxed keeps atomicity, race freedom and per-variable coherence (a single modification order). It gives no ordering of other memory, and on its own it never synchronizes with anything, so it cannot publish data. (A release fence placed before a relaxed store can carry an edge, but then the fence does the synchronizing, not the relaxed operation.)
Eight threads increment a statistics counter in a hot loop, and the main thread reads the total only after joining all of them. Which order is enough for the increments (C++), or which tool fits best (Java)?
Why. Exactness comes from the atomic read-modify-write, not from ordering; the join gives main a happens-before edge to every increment. A plain non-atomic variable would lose increments while the threads run. Java has no relaxed add, so LongAdder (which also removes contention) is the idiomatic choice.
Why is memory_order_consume discouraged?
Why. Consume orders only reads that depend on the loaded value, which ARM and POWER give for free. But optimizers routinely break or replace dependencies, so no mainstream compiler implements consume as specified; they promote it to acquire, and C++17 discouraged its use.
Java onlyWhich Java operation corresponds to a C++ release store?
Why. setRelease (and lazySet, which is documented with the same memory effects) keeps earlier accesses before the store without the full fence a volatile write needs. A volatile write is stronger: it behaves like a seq_cst store. A plain write has no ordering at all.
C++ onlyA reader polls while (!ready.load(std::memory_order_relaxed)) {} and then reads plain data. The writer did data = 42; ready.store(true, std::memory_order_release);. Where must the reader add a fence so it is guaranteed to see 42?
Why. A relaxed load that reads the released value, followed by an acquire fence, synchronizes with the release store. The fence must come after the load that saw true and before the reads it protects. A fence before the loop orders nothing useful, and without any acquire the pair is broken.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
You are given a single producer, single consumer ring buffer with indices head (written only by the consumer) and tail (written only by the producer). Write push and pop with the weakest correct memory orders in your language, and justify each one in a sentence.
Model answer

Justification: each thread reads its own index relaxed because it is the only writer. The producer's release on tail pairs with the consumer's acquire on tail, so the slot write happens-before the slot read. The consumer's release on head pairs with the producer's acquire on head, so the slot read happens-before the producer reuses the slot. Anything weaker breaks one of those two edges; anything stronger is correct but unnecessary. In C++ the two indices are aligned apart so the producer and consumer do not fight over one cache line: 64 bytes is the line size on x86, but Apple M chips use 128 byte lines, so a portable version uses alignas(128).

Explain
An interviewer asks: "Why does std::atomic default to seq_cst? Give me two cases where you would weaken it and one where you must not." Answer as you would out loud.
Model answer

seq_cst is the default because it is the only order under which a race free program behaves as a simple interleaving: every seq_cst operation is part of one global order that all threads agree on, so I can reason about the code like single-threaded steps taken in turns. Its cost is modest: on x86 only seq_cst stores cost extra, an xchg instead of a mov, and on ARM it is ldar and stlr.

I would weaken it in two common places. A statistics counter that is read after joining the workers can use relaxed fetch_add: atomicity keeps it exact and the join provides the ordering. And a single producer, single consumer queue can use release on the index store that publishes a slot and acquire on the load that consumes it, with relaxed reads of each thread's own index. I must not weaken it when each thread has to see the other's write, the store buffering shape, as in Dekker's or Peterson's lock or "set my flag, then check yours": release and acquire allow both threads to read the old value, so that needs seq_cst on all four operations or a seq_cst fence between the store and the load. And I would only weaken anything after measuring, because the bugs are rare and hardware dependent.

Explain
Explain acquire and release to an interviewer with a concrete example, and then say precisely what they do not guarantee.
Model answer

Release and acquire are a pair of one-way barriers used to hand data from one thread to another. The writer prepares data with ordinary writes and then stores a flag with release: no earlier read or write may be moved after that store. The reader loads the flag with acquire: no later read or write may be moved before that load. If the acquire load reads the value the release store wrote, the store synchronizes with the load, so everything the writer did before the store happens-before everything the reader does after the load. For example, the writer fills a config object and stores ready = true with release; a reader that loads ready == true with acquire is guaranteed to see the filled object. In Java that is a volatile flag, or setRelease and getAcquire.

What they do not guarantee: they do not order a release store with a later acquire load in the same thread, so in the store buffering test both threads can still read 0; they give no single global order of operations, so two readers can disagree about the order of two independent writes on some hardware; and they only work as a pair on the same variable, with the reader actually reading the released value. A relaxed load on the reader's side, or a release on a different variable, gives no edge.

"Walk me through the C++ memory orders you actually use. What does each one buy you, and how do you decide which one to put on an atomic?"
What a strong answer covers
  • seq_cst is the default: acquire and release, plus one total order of seq_cst operations that every thread agrees on
  • A release store and an acquire load that reads its value form a happens-before edge: the tool for publishing data
  • Relaxed keeps the operation atomic and keeps one order of writes to that variable, but orders nothing else: counters, ids, a thread's own index
  • acq_rel is for read-modify-writes that both receive and publish, such as the last reference count decrement
  • Acquire and release do not stop a store from passing a later load, so "set my flag, then check yours" needs seq_cst
  • Weaken the default only on a measured hot path, naming the exact edge you need
How a senior would say it
I use four of the six, and I start from the default. seq_cst gives acquire and release, plus one total order of all seq_cst operations that every thread agrees on, so I can reason about the code as a simple interleaving. When one thread hands data to another, a pair is enough: the writer fills the data and stores a flag with release, and the reader loads the flag with acquire. If the load sees the stored value, everything before the store happens before everything after the load. Relaxed keeps the operation atomic and keeps one order of writes to that one variable, but it orders nothing else, so it fits a counter read after a join, a unique id, or a thread reading its own index. acq_rel is for a read-modify-write that both receives and publishes, like the final reference count decrement. The trap is that acquire and release do not stop a store from passing a later load, so anything shaped like "I set my flag, then I check yours" needs seq_cst. And I weaken the default only on a measured hot path, where I can name the edge.

"Here is a symptom: a lock-free queue passes every test on our x86 laptops, but on the ARM build servers a consumer very occasionally reads an old value from a slot. The producer writes the slot and then stores the tail index with memory_order_relaxed. What is going on, and how do you fix it?"
What a strong answer covers
  • The relaxed tail store publishes nothing: there is no edge from the slot write to the consumer's slot read
  • ARM may reorder accesses to different addresses, and so may the compiler; x86 keeps stores in order and loads in order, which hid the bug
  • In C++ it is a data race on the slot, so the code was broken on every platform, tests or not
  • Fix: release on the producer's tail store, acquire on the consumer's tail load
  • The head index needs the same pair in the other direction, so a slot is not reused while it is still being read
  • Prove it with ThreadSanitizer and a stress run on ARM, not a green x86 run
How a senior would say it
The tail index is the flag that publishes the slot, and a relaxed store publishes nothing. Relaxed keeps the index itself atomic, but it does not keep the slot write before it, so on ARM the consumer can see the new tail and still read the old slot. ARM may reorder accesses to different addresses when nothing orders them, and the compiler may too. On x86 the hardware keeps stores in order with each other and loads in order with each other, so the bug hid there, but it was always a bug: in C++ it is a data race on the slot, which is undefined behaviour. The fix is a matched pair. The producer stores tail with release after filling the slot, and the consumer loads tail with acquire before reading it. The same reasoning runs the other way: the consumer stores head with release after reading the slot, and the producer loads head with acquire before reusing it. Then I would prove it with ThreadSanitizer, which sees the missing edge on any machine, and a long stress run on the ARM servers.

Out loudabout 75 s
"Why can a reference count increment be relaxed, while the decrement needs acquire and release?"
What a strong answer covers
  • Gaining a reference publishes nothing: the caller already holds one, so only exactness matters, and relaxed keeps the count exact
  • Each owner may have written to the object; the release half of its decrement keeps those writes before the decrement
  • The owner that takes the count to zero needs the acquire half to see every other owner's writes before it destroys the object
  • The decrements are read-modify-writes on one variable, so they form a chain that carries each release to the final acquire
  • Libraries often use a release decrement plus an acquire fence only on the path that reaches zero
How a senior would say it
Because the increment publishes nothing and the decrement publishes everything. To increment, I must already hold a reference, so the object is already safely visible to me. All that matters is that the count stays exact, and relaxed atomicity gives me that. The decrement is different. Every owner may have written to the object before letting go, and the last owner is about to destroy it. The release half of each decrement keeps that owner's writes before its decrement. The acquire half of the final decrement, the one that sees the count reach zero, makes all of those writes visible before the destructor runs. It works across many owners because the decrements are read-modify-writes on one variable, so they form a chain that carries each release forward to the final acquire. Libraries often save a little by using a release decrement and an acquire fence only on the path that hits zero. Without the acquire, the destructor could run before another owner's last writes are visible to it.
