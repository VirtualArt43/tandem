The monitor object pattern

One template class, in Java and C++, that every thread-safe class you build can start from, and a recipe for adapting it.

Asked atRubrikLinkedIn
Before this:Condition variables and monitorsSpurious and stolen wakeups: always wait in a loopLost wakeups, notify versus notifyAll, Mesa versus Hoare

Almost every "build a thread-safe X" question has the same skeleton. Learn it once, write it from memory in two minutes, and spend the interview on the parts that are specific to the problem.

In plain words

A railway reservation office has one window and one clerk. The ledger of seats is behind the glass, and only the clerk at the window touches it. You queue, reach the window, and ask for what you need. If it is possible, you get it at once. If it is not, the clerk sends you to a bench: one bench for people waiting for cancellations, another for people waiting for a new train to open. When something changes, the clerk calls out to the bench whose people might now be served. Those people come back to the window and check again, because someone else may have got there first.

One window, a ledger nobody else touches, benches for each kind of waiting, and "come back and check again". That is the whole monitor pattern, and many thread-safe classes you build in an interview fit it.

The pattern, part by part

A monitor object packages shared state with the only code allowed to touch it. A caller runs the method itself while holding the object's lock; the object does not need a dedicated clerk thread. In practice it has five parts:

  1. One private lock. Every operation that accesses guarded mutable state takes it. Private means outside code cannot take it too.
  2. Guarded state. The fields the lock protects, each marked "guarded by" in a comment, read and written only while holding the lock.
  3. An invariant. A statement about the state that is true whenever the lock is free, such as "0 <= size <= capacity". Methods may break it briefly while holding the lock, and must restore it before releasing, including before a condition wait, on exceptions, and before any reentrant call that can observe the state.
  4. Conditions. One condition variable for each distinct thing threads wait for ("not full", "not empty", "a permit is free").
  5. Methods with one shape: lock; wait in a loop while the method cannot proceed; change the state; signal the conditions whose waiters might now proceed; unlock on every path.

The template, filled in once

Here is the shape as real code, filled in as a fixed-capacity pool of permits with two common interview follow ups: a timeout and a way to close. The comments mark the five parts.

The contract is explicit: negative capacity is rejected; zero capacity is allowed but cannot grant a permit. Each successful acquire must have exactly one release, including after close. Closing is idempotent and rejects new acquisitions, even if permits remain. The capacity check catches a release when all permits are free; identifying every double release while other permits are held requires tracking individual leases.

These timed methods budget the condition wait after acquiring the lock. Lock acquisition and reacquisition can add delay, so they are not deadlines for the whole call. For an end-to-end budget, compute one monotonic deadline before locking, use timed lock acquisition, and pass only the remaining time to each condition wait. In C++, that needs a timed mutex with condition_variable_any; even then scheduling can delay return past the deadline.

Read the method bodies again and notice how little is specific to permits: the predicate (available == 0 && !closed), the change (available -= 1), and which condition to signal. Everything else is the template. Three details are worth saying out loud in an interview:

  • The timeout loop recomputes the time left. awaitNanos returns the remaining time, and wait_for with a predicate handles it for you; a loop that restarts the full timeout after every wakeup can wait forever.
  • signal is safe in release, and signalAll is needed in close. Every waiter on permitFree waits for the same thing and one permit lets exactly one of them proceed, so waking one is enough; closing changes the answer for all of them.
  • The closed flag is part of every wait. A waiter that only checks for a permit would sleep through the close.
Java

Condition objects created by ReentrantLock require you to hold that lock when you call signal or signalAll (and notify or notifyAll with synchronized); calling them without it throws IllegalMonitorStateException. The same is true of await and wait.

C++

C++ lets you call notify_one and notify_all after releasing the mutex, as release and close do above. It is correct as long as the state changed under the lock and waiters check their predicate under the lock, and it can save a woken thread from waking up only to block on the mutex you still hold. Notifying while holding the lock is also correct. In either case the mutex and condition variable must remain alive until every caller, including the notifying thread, has finished.

The recipe: adapting the template to any problem

When the interviewer says "build a thread-safe X", go through these steps out loud, in order. They turn the template into the specific class with very little invention:

  1. State and invariant. Write the fields and the sentence that must always hold. For a bounded queue: the items, and "0 <= size <= capacity, and items leave in the order they arrived".
  2. Operations and their preconditions. For each method: under what condition may it proceed, and must it wait otherwise? put needs space; take needs an item; size does not wait on a condition, though acquiring the lock can block.
  3. Conditions. One condition per distinct precondition. If many kinds of waiter share one condition, you will have to wake them all.
  4. Signals. For each operation, after its state change, which preconditions might now be true? Signal those conditions: one waiter if exactly one can proceed and all of them wait for the same thing, all waiters otherwise.
  5. Extras. A closed flag inside every wait condition, timeouts, interruption, and what each method does after close.
  6. Tests. Force full, empty, close and timeout cases with coordination, then stress with many threads. Read state through a locked snapshot or after joining, and use a watchdog to catch hangs. Random timing alone cannot prove correctness.

Worked example: Rubrik's "wait until every task is done"

Rubrik reports include versions of this task: submit(task) returns at once and runs the task on a worker; waitUntilComplete() waits for submitted work; library executors are often banned. Here we implement the simpler contract of waiting until the pool is idle. For a fixed batch, finish submitting that batch before calling awaitAll() and do not submit the next batch until it returns.

  1. State and invariant: pending, the number of tasks submitted and not yet finished; it is never negative. A counter like this is often called a wait group.
  2. Operations: taskSubmitted() and taskFinished() do not wait on conditions, though both can block acquiring the lock; awaitAll() may proceed only when pending == 0.
  3. Conditions: one, allDone.
  4. Signals: taskFinished may make pending == 0 true, and every waiter is waiting for exactly that, so it wakes all of them.
  5. Extras: count a task before handing it to a worker, never after, or awaitAll can return while it sits in the queue; and finish it in finally, so a task that throws still counts as done.

The worker pool around it is the same template again: a bounded task queue with notFull and notEmpty, and workers that take tasks and call taskFinished on both success and failure, using Java finally or a C++ scope guard. If submission is rejected after incrementing the count, roll that increment back exactly once. Record task errors separately so waiting for completion does not hide failures. A counter waits for a moment of global idleness, not a snapshot of tasks present when the wait began: later submissions can extend the wait. For snapshot semantics, capture a submission sequence number and wait for the completed prefix to reach it, or use a separate tracker per batch. Merely counting completed tasks is wrong when later tasks finish first. The full executor exercise is in the practice bank.

The built-in monitors: Java's synchronized, and C++'s other condition variables

Java

Every Java object is a monitor: synchronized takes its lock, and wait, notify and notifyAll are its single condition. LinkedIn has asked for a bounded blocking queue using only these (no java.util.concurrent locks at all), so practise the same template in that form. With only one condition per object, producers and consumers wait on the same condition, which is why notifyAll becomes the default.

Notice the private lock object. An instance synchronized method locks this (a static one locks the class object), and any outside code can write synchronized (pool) { ... } and hold your lock as long as it likes. A private lock object prevents that.

C++

std::condition_variable works only with std::unique_lock<std::mutex>. To wait with another lock type, such as a std::shared_mutex or your own lock class, use std::condition_variable_any. C++20 also gives condition_variable_any a wait(lock, stop_token, predicate) overload that returns when a stop is requested, which pairs naturally with std::jthread for shutdown. Ordinary C++ waits have no Java-style interruption: the predicate overload returns when the predicate holds after a notification or spurious wakeup. A stop-aware wait can also return on a stop request; its Boolean result says whether the predicate holds. Stop alone does not mean a permit was acquired. In C++17, use the closed flag and notify_all shown above.

Common mistakes

  • A lock that outsiders can take. synchronized methods lock this, which any caller can also lock. Use a private lock.
  • if instead of while around the wait. Wakeups can be spurious, and another thread may have taken what you were woken for. Always re-check; in C++, pass the predicate.
  • Signalling one waiter when waiters differ. With producers and consumers on one condition, signal can wake a thread that cannot proceed, and the wakeup is lost. Use separate conditions, or signalAll.
  • A path that forgets to signal. close, a timeout that changes state, an error path, a release in finally: every change that can unblock someone must signal.
  • Reading guarded state without the lock. A size() that skips the lock can read stale values in Java and has a data race in C++ when it conflicts with an unsynchronized write.
  • Calling unknown code while holding the lock. A callback, a listener or I/O under the lock can block for a long time or try to call back in and deadlock. Copy what you need, release, then call it: an open call.
  • Waiting on another monitor while holding this one. take() on a queue releases the queue's lock while it waits, not yours, so everything that needs your lock is stuck. That is nested monitor lockout; release your lock before blocking on anything else.

In the interview

Rubrik's system coding rounds frequently ban library queues, executors and concurrent collections, so candidates build the bounded queue, the thread pool and the "wait for all tasks" latch from locks and conditions; reports of this run from 2022 to 2026. LinkedIn's concurrency round has asked for a bounded blocking queue with only wait and notify. A Microsoft candidate was asked to implement a working semaphore. Every one of those is this template.

I will use the monitor pattern. One private lock guards the state, which is the items and a closed flag, and the invariant is that size stays between zero and capacity. There are two conditions, not full and not empty. Each method takes the lock, waits in a loop until it can proceed or the queue is closed, changes the state, and signals the condition its change may have satisfied, then releases the lock on every path, with finally in Java or an RAII guard in C++. Because each condition has only one kind of waiter, signalling one thread is safe; close signals everyone.

Follow ups to expect: "Why while and not if?" "Why two conditions?" "Add a timeout." "Add close, and say what blocked callers see." "Could this deadlock?" (also check missing signals, impossible predicates, recursive locking of a nonrecursive mutex, and thread pool starvation). "How would you test it?"

Senior depth

Why the loop is mandatory: Mesa semantics. In Hoare's original monitors, a signal handed the lock directly to the woken thread, so the condition was guaranteed true when it ran. Java and C++ use mesa semantics instead: the signaller keeps running, and the woken thread competes for the lock later, by which time the state may have changed again. Signal means "check again", never "go ahead".

Signal one, signal all, and the herd. signalAll avoids selecting the wrong waiter when predicates, state protection and lifecycle are already correct but can wake hundreds of threads that immediately sleep again. Separate conditions per kind of waiter let you wake exactly the right ones. The general rule: signal one only when every waiter on that condition waits for the same predicate and the change lets exactly one of them proceed.

Visibility and atomicity. Unlocking and a subsequent lock acquisition on the same lock publish guarded writes to the next owner. A successful permit acquisition linearizes at the decrement; close linearizes at the flag update. If acquire wins that race it may succeed just before close; close does not revoke already acquired permits. Two public methods are still two operations: a caller's size() followed by take() needs a combined method if the check and removal must be atomic.

Reentrancy, callbacks and lifetime. Java's locks here are reentrant; std::mutex is not. A C++ public method must not call another locking method on the same object while holding its mutex; use a private helper whose precondition is that the caller holds the lock. Java reentrancy avoids that self-deadlock but can expose a temporarily broken invariant to a callback. For an open call, copy an immutable snapshot first; if the callback's result will change state, reacquire and revalidate. Safely publish the object, do not leak guarded mutable references, and in C++ stop and join all users before destruction: close() wakes users but does not join them.

Fairness is separate. A correct monitor does not guarantee FIFO admission or starvation freedom. A fresh caller can take a permit before an awakened waiter; use an explicit waiter queue or tickets if admission order is a requirement, and remove cancelled waiters without blocking the queue.

When to leave the template. A single monitor serializes everything it guards. When profiling shows its lock is the bottleneck, the next steps are to split the state into independent parts with their own monitors (striping), to give the state a single owner thread, or, for one hot word, an atomic. The monitor remains the correct starting point; the others are optimizations you justify with numbers.

Key takeaways

  • A monitor is a private lock, guarded state, an invariant, one condition per kind of waiting, and methods that lock, wait in a loop, change, signal and unlock.
  • Adapt it with the recipe: state and invariant, preconditions, conditions, who to wake after each change, then close, timeouts and tests.
  • Signal one only when all waiters on that condition want the same thing and one can proceed; otherwise signal all.
  • Put the closed flag in every wait, recompute timeouts in the loop, and never call out or block on another monitor while holding the lock.
  • Rubrik's banned library rounds, LinkedIn's wait and notify queue and "implement a semaphore" are all this one template.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Spot the bug in this take() of a bounded queue with several consumers:
Why. Being woken only means "check again". Another consumer can steal the item before the waiter reacquires the lock. Java removal throws; accessing an empty C++ deque is undefined behaviour. Use a Java loop or C++ predicate wait. One producer signal is sufficient after removing one item when producers have their own condition.
A correctly locked bounded queue uses predicate loops but one condition for producers and consumers, and wakes just one waiter after each state change. What can happen?
Why. With different kinds of waiter on one condition, a single signal can be spent on a thread that cannot proceed. Use two conditions (then signal one is safe) or signalAll.
A monitor exposes its lock to callers. An outside caller acquires it and sleeps for about ten seconds without releasing it. What happens to other calls needing that lock?
Why. For example, Java instance synchronized methods lock this, so outside code can interfere through synchronized (queue). Sleep does not release that monitor or a C++ mutex. Contention neither interrupts the sleeper nor throws a monitor-ownership exception. Use a private lock.
Method drain() holds monitor A's lock and calls queue.take() on a blocking queue B, which is empty. The producers that would fill B first need A's lock. What happens?
Why. A wait releases only the lock of the monitor you wait on. That is nested monitor lockout. Release your own lock before blocking on another object, or restructure so you never wait while holding it.
A pool's close() sets closed = true under the lock and calls signalAll(), but acquire() waits with while (available == 0) permitFree.await();. No permit is released. What happens to a thread blocked in acquire() when the pool closes?
Why. Signalling only makes waiters re-check their predicate. If the predicate does not include the closed flag, they re-check, see nothing new, and sleep again. Every wait must be while (available == 0 && !closed), followed by a check of closed.
Inside a monitor method, while holding the lock, a class calls listener.onChange(newValue) on listeners registered by other code. Why is this risky?
Why. Code you do not control, run under your lock, inherits your lock. Copy what the callbacks need while holding the lock, release it, and then call them: an open call.

Why. ReentrantLock conditions throw IllegalMonitorStateException when signalled without ownership. Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a countdown latch from the template (the timeout budgets the condition wait after locking): countDown(), await(), await(timeout) that returns whether the count reached zero, and getCount(). Extra countDowns after zero must be harmless.
Model answer

It is the template with one condition: the state is the count, the invariant is that it never goes below zero, await waits in a loop until it is zero, and countDown wakes everyone when it reaches zero, because every waiter wants exactly that. The timed version keeps the remaining time across wakeups, and getCount takes the lock like every other read. Once the count is zero it stays zero, so the latch is one-shot by design.

Design
Apply the recipe to a parking garage with N spots: parkCar() blocks until 1 spot is free, parkTruck() blocks until 2 spots are free (any 2), leave(spots) frees spots, and close() turns everyone away. Give the state, invariant, conditions and signals, and name one fairness problem.
Model answer

State: free (spots available) and closed. Invariant: 0 <= free <= N whenever the lock is free. Preconditions: a car needs free &gt;= 1, a truck needs free &gt;= 2; both also proceed (to fail) when closed. Conditions: I would use one condition per kind of waiter, carCanPark and truckCanPark, so I can wake the right ones. Signals: leave(k) raises free by 1 or 2; afterwards a waiting truck may fit and some cars may fit, so I signal truckCanPark if free &gt;= 2 and signal carCanPark once per freed spot (or signalAll on both, which is simpler and still correct). close() sets the flag and signals all on both conditions; every wait loop checks closed.

Fairness problem: trucks can starve. Cars need only one spot, so with a steady stream of cars, whenever one spot frees a car takes it and the count never reaches two. The fix is the same as in the bathroom lesson: once a truck is waiting, hold back new cars until the truck parks (a waiting trucks counter in the car's predicate), or serve arrivals in ticket order. Each can cost throughput, which I would say out loud. If a waiting truck times out or is interrupted, remove it from the waiting count or ticket queue and wake any cars its departure makes eligible. Validate releases or track occupied leases so leave cannot raise free space above N.

Debug
Assume max is positive and construction finishes before sharing. This deliberately broken bounded counter has three concurrency bugs. Find them, say what each one can cause, and fix them.
Model answer

Bug 1: increment waits with if instead of a loop. After a spurious wakeup, or when two incrementers are woken together, a thread goes ahead with the counter already at the maximum and breaks the invariant. Fix: while (value == max) lock.wait(); in Java, cv_.wait(lock, [this] { return value_ < max_; }); in C++.

Bug 2: a single notify with two kinds of waiter on one condition. An increment can wake another waiting incrementer instead of a waiting decrementer (or the reverse); the woken thread re-checks and sleeps again, and the thread that could proceed sleeps on, so the program can hang. Fix: notifyAll() and notify_all() in both methods, or two conditions, not full and not empty, each method signalling the opposite one.

Bug 3: get() reads guarded state without the lock. In Java it may keep returning a stale value; in C++ it is a data race, which is undefined behavior. Fix: read it while holding the lock (synchronized (lock) in Java; a std::lock_guard in C++, with the mutex declared mutable so a const method can lock it).

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 80 s
"Explain the monitor object pattern, and show me why a signalled thread must check the condition again."
What a strong answer covers
  • Bundle private guarded state, one lock, invariants and conditions
  • Acquire the lock before checking the predicate or changing state
  • Wait atomically releases the associated lock and reacquires it before returning
  • Walk through another caller stealing the resource before the waiter reacquires
  • Use a loop or predicate wait and restore invariants before every release
  • Choose one notification for one eligible waiter and broadcast for close
How a senior would say it
A monitor object puts shared state and the operations that protect it behind one private lock. I start with the invariant, then define the predicates that let each operation proceed. For a bounded queue, the invariant is that size stays between zero and capacity, and the predicates are space available and item available. A method acquires the lock before checking its predicate. If it cannot proceed, waiting atomically releases that lock and sleeps. Before returning, the wait reacquires the lock, but that does not mean the predicate is still true. For example, a producer adds one item and signals a waiting consumer. Before that consumer reacquires the lock, a new consumer gets the lock and takes the item. The original consumer must see the empty queue and wait again. Spurious wakeups are another reason to recheck. So I use a loop in Java or a predicate wait in C++. I restore the invariant before waiting or unlocking. After one insertion I can wake one consumer on a dedicated condition. Close changes the answer for every blocked caller, so it broadcasts and every wait checks the closed flag.

Likely follow up: What goes wrong if producers and consumers share one condition and you wake only one thread?

Out loudabout 90 s
"Your permit pool supports close and a timeout. What exactly do those operations guarantee, and how would you test the races?"
What a strong answer covers
  • Close rejects acquisitions and wakes all waiters without revoking existing permits
  • The lock orders an acquire racing with close; release remains valid afterwards
  • Use one monotonic budget and distinguish condition-wait time from whole-call time
  • Check accounting, invalid capacity and over-release
  • Test exhausted capacity, multiple close waiters, timeout and concurrent acquire versus close
  • Separate notification from joining and destruction; state fairness and cancellation limits
How a senior would say it
I would define close to reject new acquisitions and wake every blocked caller, while allowing existing holders to release their permits. Close is idempotent. An acquisition racing with close succeeds only if its decrement wins under the lock; closing does not revoke a permit already acquired. The timeout contract needs equal precision. In this template it budgets the condition wait after locking. It does not bound initial lock acquisition, reacquisition or scheduling delay. If the caller needs a whole-call budget, I compute one monotonic deadline before locking, use timed lock acquisition, and pass only the remaining budget to waits. I never restart the full duration after a wakeup. I would test an exhausted pool with several waiters, then close it and verify every caller finishes with the documented outcome. I would also test timeout without a release, release racing with timeout, repeated close, and acquisitions racing with close. Coordinated starts and bounded joins make those tests useful; sleeps alone do not establish an interleaving. Accounting must stay between zero and capacity. I reject negative capacity and obvious over-release, while documenting that full double-release detection needs lease identities. Finally, close only changes state and wakes threads. The owner must join users before destroying a C++ monitor, and fairness requires a separate admission policy.

Likely follow up: How would a FIFO waiter queue handle a timed-out caller at its head?
