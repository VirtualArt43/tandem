ThreadSanitizer and other race detectors

What ThreadSanitizer catches, how to read its reports, why a clean run proves less than you think, and what Java uses instead.

Before this:Race conditions versus data racesHappens-before and synchronizes-with

A data race can sit in a C++ program for years, printing the right answer, until a new compiler or a busier machine turns it into a crash. ThreadSanitizer can expose a data race even when the output looks right, provided the relevant accesses execute and the tool observes them.

In plain words

Think of a cricket match with a third umpire who reviews what happened on the field. The final score can look reasonable even when the players broke a rule along the way. ThreadSanitizer plays a similar role for a program: it watches workers reading and changing shared information, and flags unsafe combinations even when the final answer looks right.

The catch: the replay only covers the match that was played. If a run out never happened in this match, the footage cannot show it, however many cameras you add.

Turning it on

TSan is built into clang and gcc. Compile and link with one extra flag, keep debug info so reports have file and line numbers, and use light optimization so the program is not painfully slow:

Tandem builds every C++ program this way, which is why the Run button can flag races. The cost is real: the clang documentation gives a typical slowdown of 5 to 15 times and a memory overhead of 5 to 10 times. TSan cannot be combined with AddressSanitizer in the same build, and your code and rebuildable dependencies should be instrumented. Uninstrumented code creates blind spots: intercepted library calls may still be visible, but arbitrary loads, stores and inline synchronization may not be.

What it catches, and what it does not

ReportedNot reported
Data races: two accesses to the same memory from different threads, at least one a write, not ordered by happens-before, not both atomicRace conditions that are not data races: a check-then-act built from atomics, a lost update split across two locked calls
Thread leaks on supporting runtimes: a terminated joinable pthread that was neither joined nor detached, typically reported at process exitLost wakeups, livelock, starvation: logic bugs with no unsynchronized access
On supporting Linux runtimes, with deadlock detection enabled: lock order inversions ("potential deadlock"), even in runs that did not hang; some mutex misuse is also detectedDeadlocks through condition variables, latches or futures, and anything in code paths this run did not execute

The main check is memory access ordering; auxiliary checks vary by runtime. None proves program logic correct. TSan knows nothing about your invariants. An atomic counter that oversells tickets through a check-then-act has data-race-free accesses, so TSan is silent; an invariant assertion, a recorded-history check or reasoning about the interleaving is needed (next lesson).

A thread leak here refers to the pthread lifecycle; destroying a joinable std::thread calls std::terminate() instead. Do not expect a leak warning to replace RAII and joins. On Linux, check the runtime's support for TSAN_OPTIONS="detect_deadlocks=1" before relying on its lock-order diagnostics.

A practical note for this site: the TSan that ships with Apple's clang does not report lock order inversions (a limitation confirmed in this site's runner environment). On macOS, a C++ deadlock shows up as a hang and a stack dump, not a TSan warning.

How it works

The compiler instruments ordinary shared-memory accesses and atomic operations that remain after optimization; the runtime also intercepts supported synchronization such as pthread mutex operations, thread creation and join. Private or eliminated accesses need not be instrumented, and unsupported synchronization can be missed. Together these observations let it track happens-before.

  • Each thread carries a vector clock: one counter per thread, recording how much of every other thread's history it is ordered after. Synchronization merges clocks: an unlock publishes the unlocker's clock, the next lock of that mutex absorbs it.
  • For every 8 bytes of application memory, TSan keeps a few shadow cells recording recent accesses: which thread, at what point in its clock, read or write, which bytes.
  • On each access it compares against the shadow cells. If another thread touched the same bytes, one of the two accesses is a write, the two accesses are not both atomic, and that thread's access is not covered by our clock, nothing ordered them: that is a data race, reported with both stacks.

Notice what is not required: the two accesses do not have to collide in time. TSan can report a race even if the accesses were milliseconds apart, when they are unordered and the relevant access history is still available. That is what makes it so much stronger than "run it a thousand times and hope".

Read a report

Read it in five steps:

  1. The kind: data race.
  2. The access that tripped it: a 1-byte write by thread T2 in producer() at line 10, ready = true.
  3. The earlier conflicting access: "Previous read" by T1 in consumer() at line 15, the flag check. "Previous" means earlier in this run, not "the guilty one". The race is the pair; the fix may go on either side, or both.
  4. The memory: Location is global 'ready'. For heap memory it says "heap block of size N" and shows where it was allocated; that tells you which object two threads share.
  5. The threads: where T1 and T2 were created. In a real service that is often a pool's constructor, which tells you which pool's tasks collide.

A payload report has the same shape: a read in consumer() and a previous write in producer(). If the consumer never reads the payload, that access pair is not exercised. Fix the flag to order the payload write before its read:

This is a one-shot handoff: the producer writes the payload once and never modifies it after publishing. The acquire read must observe the release store, or Java's volatile read must observe true, before the consumer uses the message. Reusing the flag while overwriting the payload needs an acknowledgement or a queue; the flag alone does not protect later mutations. The short spin keeps the example small; use a blocking primitive for long waits. Joining both threads in main does not order the producer's accesses before the consumer's earlier accesses.

C++

TSan models atomic memory orders, which makes it a good check on a weak ordering. Change both calls to std::memory_order_relaxed and TSan stops reporting ready (atomic accesses never form a data race) but can still report payload, because a relaxed store and a relaxed load create no happens-before edge. That report is TSan telling you the memory order is too weak.

Why a clean run proves less than you think

A clean TSan run means: the configured detector reported no races in that execution. It does not prove that every executed access pair was ordered: instrumentation gaps, suppressions and finite history can hide a race even in that run.

Only executed code is checked. An error handler, a shutdown path or a rare branch that your test never reached has not been checked at all. That is why you run TSan on stress tests that drive many paths, not on a single-threaded unit test.

Only this schedule's happens-before edges count. Synchronization that has nothing to do with your data can still order it by accident:

History is bounded. TSan remembers only the last few accesses per 8 bytes and a limited event history per thread. A race between accesses far apart can be missed, or reported with "failed to restore the stack" for the earlier access.

It cannot see synchronization it does not model. Hand-written assembly, libraries built without TSan, and fence-based synchronization using std::atomic_thread_fence (not fully modeled by the TSan toolchain used here) can cause both false reports and missed ones. Treat each report as a bug until you can demonstrate the missing ordering or a tool limitation. A suppressions file (TSAN_OPTIONS="suppressions=tsan.supp" with lines such as race:ThirdPartyCache) hides matching diagnostics; it does not make unsafe code correct. Before suppressing, reduce the case, audit both access paths and document the exact limitation and scope.

Worked example: a cache that locks only on writes

A price cache takes its mutex in put but not in get. An illustrative TSan report (with the huge std::__hash_table template names shortened) looks like this:

Here even PriceCache::get is missing because -O1 inlined it; the reader's thread entry (main::$_1, the reader lambda) and find point you there. Inspect callers and source; rebuilding at -O0 may make frames easier to read but also changes the execution.
  • (mutexes: write M0) appears on the writer only. One side held a mutex and the other held none: the classic "locked the writes, forgot the reads".
  • The writer was rehashing. A concurrent find during a rehash can follow a pointer into a bucket array that is being replaced. This is not a stale read; it can crash.

Fix: take the same mutex in get (or a std::shared_mutex, shared for readers and exclusive for writers, if measurement justifies it). Every access to guarded state takes the lock, reads included.

Static checks: tell the compiler which lock guards what

A dynamic tool observes executions; static analysis checks annotated code without running it, including paths tests may not exercise. It is still an approximation, not exhaustive verification. Both languages let you annotate "this field is guarded by that lock" and have a tool reject code that touches the field without holding the lock.

The Java annotation is an external dependency, not part of Java 21: add Error Prone's error_prone_annotations and configure its compiler plugin. Plain javac with only the annotation dependency accepts the code without enforcing the lock contract. The examples deliberately leave peek() unguarded to demonstrate the diagnostic.

The C++ comment shows the actual clang warning text. With libstdc++ (gcc's library) std::mutex is not annotated, so codebases use an annotated mutex type such as Abseil's absl::Mutex with ABSL_GUARDED_BY. In Java, Error Prone's GuardedBy check understands synchronized blocks and Lock objects locked in the same method; SpotBugs has a similar "inconsistent synchronization" detector. Static checks have false negatives too (for example, a reference to guarded state escaping the lock), and these annotations add no locking at run time. Configure the checker on every build; use -Werror=thread-safety when C++ warnings should fail CI.

The other detectors

  • Go's race detector (go test -race) uses ThreadSanitizer technology. The executed-path limitation also applies, but its runtime integration, reports and supported features differ from C++.
  • Valgrind's Helgrind and DRD on Linux need no recompilation, use dynamic binary instrumentation, usually with substantial slowdown, and also report misuse of the pthreads API; Helgrind reports lock order problems as well.
  • Java has no built-in TSan for ordinary JVM bytecode. Its toolbox is jcstress (the OpenJDK harness that repeatedly runs small actor tests and classifies observed outcomes), stress tests with invariants, and static checks like the @GuardedBy one above. Continue with testing concurrent code.

Common mistakes

  • "TSan was clean, so the code is correct." Clean means no reports under that configuration, workload and execution. It does not certify all access pairs, paths or invariants.
  • Running TSan only on single-threaded unit tests. A single-threaded execution cannot exercise a cross-thread data race. Add concurrent callers and lifecycle paths to the tests.
  • Ignoring a report because the output was right. The demo can print the right answer while shared accesses remain unordered. In C++ a data race is undefined behavior; the next compiler may break it.
  • "Fixing" a report with volatile or a sleep. TSan still reports races on volatile (it is not synchronization in C++), and a sleep only changes the schedule.
  • Suppressing instead of fixing. Use a narrow suppression only after explaining the report and documenting an accepted limitation or unresolved defect. Suppressing it is not a repair.
  • Mixing instrumented and uninstrumented code and trusting the result, or trying to build with both -fsanitize=thread and -fsanitize=address.

In the interview

The topic arrives as a follow up after you write thread-safe code: "how would you test this for race conditions?" (asked, for example, after a Databricks log writer question) or "how do you know there are no data races?". In C++ debugging rounds, saying you would build with -fsanitize=thread and run the reproducer is often the fastest route to the bug.

For C++ I would run the stress tests under ThreadSanitizer, which can report unordered conflicting accesses, with both stacks, even when the run printed the right answer. I would not treat a clean run as proof: it only covers the paths and schedules that executed, and it cannot see logic races like a check-then-act built from atomics, so I also assert invariants in the stress test. For ordinary Java bytecode I would use different tools: jcstress for the low level pieces, invariant checking stress tests for the class, and GuardedBy annotations checked by Error Prone on every build.

Follow ups: "TSan passed; are we safe?" (no, explain coverage, tool limits and invariant checks). "Why does TSan report a race when the threads never ran at the same time?" (it checks ordering, not timing). "What can it not find?" (logic races, lost wakeups, unexecuted paths).

Senior depth

Happens-before versus lockset. Older detectors such as Eraser checked a lockset discipline: every access to a variable must hold some common lock. That looks for inconsistent locking in executed code, but it can also flag correct code that synchronizes another way (a handoff through a queue, a thread join), so it reports false positives. Modern TSan primarily detects races through happens-before tracking, reducing those false positives while retaining execution and instrumentation limits. Its first version, built on Valgrind, combined the two.

In CI. Run the stress suite under TSan nightly with halt_on_error=1, keep the build fully instrumented, and treat a new report as a release blocker. Pair it with an ASan build of the same tests (they cannot share a build) and with static annotations in code review.

Key takeaways

  • TSan can detect conflicting accesses in different threads, not both atomic and unordered by happens-before, even when separated in time.
  • Read a report as a pair: the access that tripped it, the previous access, the memory location, and where each thread was created.
  • A clean run means no report, not proof of correct ordering. Logic races made entirely from atomic operations need invariant checks.
  • It costs roughly 5 to 15 times in speed; keep every component instrumented.
  • For Java bytecode, use jcstress, invariant stress tests and GuardedBy static checks.

Quick check

Answer each question, then read why. Your score is saved for your module test.

An atomic counter starts at 9. Each of two threads checks whether it is below 10, then increments if so. Java uses separate get() and incrementAndGet() calls; C++ uses separate load() and fetch_add(1) calls. After joining both threads, which final-value and diagnostic pairs are possible in C++ under TSan? Select all that apply.Select all that apply
Why. If one thread increments before the other checks, the result is 10. If both check at 9, both increment and the result is 11. At least one sees 9 and increments, so 9 is impossible. All accesses to the counter are atomic, so neither outcome creates a data race on it. The bound violation is a logic race; use one locked check and increment, or a compare-and-set loop that retries the check.
A report says "Write of size 4 at X by thread T1" and then "Previous read of size 4 at X by main thread". What does "Previous" tell you?
Why. TSan detects the race when the second access happens and reports the first one from its shadow memory. Neither side is singled out as guilty: two unordered conflicting accesses are the race. Whether a mutex was held shows up separately, as "(mutexes: ...)".
Your test passes cleanly under TSan 100 times in a row. Which statement is true?
Why. TSan is a dynamic tool. It cannot check code that did not execute, and an unrelated lock taken in a lucky order can create a happens-before edge that hides a race in that run. Instrumentation gaps, suppressions and finite history can also hide an executed race. "Clean" is evidence, not proof; it does not establish either general race freedom or deadlock freedom.
Two threads perform instrumented writes to a shared plain int, 50 ms apart, without a happens-before edge. Assume TSan retains the earlier access and no suppression applies. What does it report?
Why. "At the same time" is not the definition of a data race. Without a happens-before edge the compiler and CPU may reorder or cache the accesses, and timing gaps are not guaranteed on another machine. TSan compares vector clocks, so it catches the pair as long as it still remembers the first access.
In a TSan report, the writer's stack is marked "(mutexes: write M0)" and the reader's stack has no mutex listed. What is the most likely bug?
Why. Using the same mutex around every access is the usual protection rule. An unlock and a later lock can also order accesses outside the critical sections, but the report says no observed ordering covers this pair. "Locking the writes and forgetting the reads" is one of the most common races in real code, and the mutex annotation on only one side is the giveaway.
C++ onlyWhich change makes TSan stop reporting the ready and payload races in the flag example, and is also correct?
Why. The acquire load that observes the release store creates the required happens-before edge, which orders the payload write before the payload read as well. volatile gives no inter-thread ordering in C++ and TSan still reports it; a sleep only changes timing; an atomic string is not even possible with std::atomic and would not order the flag.
Java onlyYou want to check whether two actors running x = 1; r1 = y; and y = 1; r2 = x; on plain fields initially zero can ever end with r1 == 0 and r2 == 0. Which Java tool is built for this?
Why. jcstress is OpenJDK's harness for exactly these small concurrency tests: it runs the actors concurrently in many configurations and reports how often each result appeared. javac has no sanitizer, and dumps or JFR do not observe memory-model outcomes. With fields initially zero, 0, 0 is allowed; it need not appear on every run. Store buffering is one mechanism: each thread can read before the other thread's write becomes visible. Neither a stack dump nor a JFR lock event enumerates these outcome pairs.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A TSan report shows "Write of size 8 by thread T3" in Stats::record() (stats.cpp:31, total_ += ms;) under "(mutexes: write M5)", and "Previous read of size 8 by thread T1" in Stats::average() (stats.cpp:40, return total_ / count_;) with no mutex. Location: "heap block of size 48 allocated by main thread at main.cpp:12". The program's output looks fine. What is the bug, why does the output look fine, and how do you fix it?
Model answer

The bug: Stats guards its fields with a mutex in record() but reads them without the mutex in average(). The report shows the writer held M5 and the reader held nothing, so nothing orders the read after the write. The allocation stack and address help identify the shared object; check them against the allocation in main rather than assuming the block size alone identifies Stats.

Why the output looks fine: the race does not have to produce a wrong number on this machine and this run. This execution may happen to read the expected values, but neither alignment nor an apparently untorn load makes a racy C++ access defined. But there is a second problem: total_ and count_ are read separately, so average() can combine a new total with an old count, which is a wrong answer even without tearing. And in C++ the data race is undefined behavior, so the compiler is allowed to transform the code in ways that break it later.

Fix: take the same mutex in average() (a std::lock_guard on the same std::mutex), so the read of both fields happens under the lock and sees a consistent pair. Handle the zero-count case under the lock too. If profiling justifies it, a std::shared_mutex lets readers share; if only the total matters, an atomic would do, but here two fields form one invariant, so one lock covering both is the right tool.

Explain
"Our C++ service passed ThreadSanitizer in CI, and a week later a race crashed it in production. How is that possible, and what would you change?" Answer as you would to the interviewer.
Model answer

ThreadSanitizer is a dynamic tool, so a clean run only says that it reported no races for those executions under that configuration. Several things could let a race through. First, coverage: the racy path may never have run in CI, for example an error path, a shutdown path or a rarely used endpoint. Second, incidental synchronization: an unrelated lock, such as a logging mutex, can create a happens-before edge in the test's schedule that hides the race; production timing removes that edge. Third, what TSan sees: a component built without instrumentation, or synchronization TSan does not model, such as fence-based publication. Finite history and suppressions can also hide executed races.

And if the production bug was a logic race, like a check-then-act built from atomics, TSan could never have caught it, because there was no data race.

What I would change: run TSan on stress tests that drive many threads through every path, including shutdown and error handling, with more threads than cores and noise injected at suspicious points; instrument our code and rebuildable dependencies, and audit unavoidable uninstrumented libraries; add invariant assertions so logic races fail the test; add checked guard annotations to detect unguarded accesses within the analyzer's supported patterns; and turn the production crash into a regression test that reproduces it.

"Our C++ stress tests passed under ThreadSanitizer a hundred times. Why would you still hesitate to call the class thread-safe?"
What a strong answer covers
  • State that no report is evidence rather than proof of thread safety
  • Explain executed-path coverage and incidental synchronization such as a logging mutex
  • Name instrumentation gaps, finite history and suppressions as additional limits
  • Give an atomic check-then-increment interleaving that violates a bound without a data race
  • Combine TSan with invariant checks, progress deadlines and a targeted regression test
  • Distinguish Java tools such as jcstress and checked guard annotations
How a senior would say it
I would treat those clean runs as useful evidence, not a proof that the class is thread-safe. ThreadSanitizer reports conflicting memory accesses it can observe and recognize as unordered. It does not verify the class contract. First, our tests might never reach the failing shutdown or error path. Second, a logging mutex can accidentally order accesses in the test schedule, hiding an ordering bug that appears in production. Third, missing instrumentation, finite access history or suppressions can hide an executed race. There is also a different category that TSan cannot diagnose as a data race. Suppose an atomic counter starts at nine and two threads each check that it is below ten before incrementing. Both can read nine, then each increments, giving eleven. Every memory operation is atomic, but the capacity invariant is broken. I would keep TSan in the test suite, inspect both access stacks for every report, and add assertions for the class invariants. I would exercise cancellation, shutdown and resource exhaustion, with deadlines to catch hangs. A discovered production failure becomes a targeted regression test. For Java, I use jcstress for small memory-model outcomes and invariant stress tests plus checked guard annotations for the larger class.

Likely follow up: Can adding logging actually make a race disappear from TSan's report, and why?

Out loudabout 75 s
"I made the ready flag atomic, but TSan still reports a race on the payload. Explain the fix and its limits."
What a strong answer covers
  • Distinguish atomicity of the flag from publication of the payload
  • Write the payload before a release store and require an acquire load that observes it
  • Explain that relaxed accesses do not provide the required publication edge
  • State the one-shot and lifetime assumptions, including no later payload mutation
  • Map publication to Java volatile and use blocking primitives for long waits
How a senior would say it
The flag being atomic prevents a data race on the flag; it does not automatically publish the payload with every memory order. I would inspect the orders on the store and load. In C++, the producer writes the payload and then stores true with release ordering. The consumer loads with acquire ordering and only reads the payload after that load observes the release store. That establishes the happens-before path from the payload write to its read. If both flag operations are relaxed, there is no such publication edge, even if the output looks correct. In Java, a volatile flag gives the publication ordering for the analogous handoff. This assumes a one-shot message: the producer does not modify the payload again after publication, and the object stays alive until the consumer finishes. Resetting the flag and overwriting the message needs another protocol, such as an acknowledgement or a queue. I would rerun the reproducer under TSan and assert the message contents. For a potentially long wait I would use a blocking primitive rather than spend a core polling.

Likely follow up: Why does joining the producer in main not repair an earlier unsynchronized payload read in the consumer?
