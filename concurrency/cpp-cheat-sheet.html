C++ concurrency cheat sheet, with pthreads

C++ concurrency APIs, their Java counterparts, lifetime and memory-order traps, and pthreads equivalents for C-only rounds.

Asked atNvidiaDatabricksMicrosoftRubrikBloomberg
Before this:Mutexes and RAII guardsCondition variables and monitorsC++ memory orders: seq_cst, acquire, release and relaxed

C++ gives you fewer ready-made tools than Java and more ways to hold them wrong. This page is a reference to the core kit: the standard library from C++11 to C++20, the traps that compile but break, and the POSIX threads version for the rounds that allow only C.

In plain words

A carpenter's apron holds a few tools, each in the same pocket every day, so the hand finds it without looking. This page is your apron: the standard tools by job, the version of C++ each needs, and a column with the Java name, so you can read Shubhi's code and she can read yours.

The last third is for a narrower but real case: some systems software rounds are reported to be C only, and then the tool is pthreads. Same ideas, older names, and a few pieces that macOS simply does not have.

A thread owner does not transport exceptions. An exception escaping the callable of either std::thread or std::jthread calls std::terminate(); catch it in the worker and pass an std::exception_ptr or satisfy a promise. Moving transfers thread ownership: move-assigning over a joinable std::thread also terminates, while std::jthread first requests stop and joins its old thread. detach() does not extend the lifetime of captured references.

Always name the guard

std::scoped_lock{m}; and std::lock_guard<std::mutex>{m}; create a temporary that unlocks at the semicolon, so the next line runs unprotected (a compiler warning is not guaranteed). std::unique_lock<std::mutex>(m); inside a method with a member mutex m is worse: it declares a new empty lock named m that shadows the mutex and locks nothing (clang warns about a vexing parse). Write std::scoped_lock lock(m); every time.

A data race (conflicting accesses to the same memory location in different threads, at least one non-atomic, with neither happening before the other) is undefined behavior. volatile is not a synchronization tool in C++. Different std::shared_ptr instances sharing a control block can be changed concurrently; modifying the same instance needs synchronization. Neither case makes the pointed-to object thread-safe. See memory orders.

Time: measure elapsed time and deadlines with std::chrono::steady_clock (monotonic), wall time with system_clock. using namespace std::chrono_literals; lets you write 50ms.

Ordering is not lifetime. A release store and an acquire load publish preceding writes only when the acquire observes that release or its release sequence. They do not keep a pointed-to object alive or order later mutations. Loads and atomic waits cannot use release or acq_rel; stores cannot use consume, acquire or acq_rel. CAS failure is a load, so its failure order cannot be release or acq_rel. When a CAS must both consume published state and publish preceding writes, acq_rel on success and acquire on failure is a common choice.

Idioms to type from memory

The tables use Java counterparts for orientation; the pairs below show the same contracts in both languages. The later pthreads snippets deliberately use C syntax. Standard-library names require their own headers: thread, mutex, shared_mutex, condition_variable, atomic, future, semaphore, latch, barrier, stop_token, chrono and new for the interference constants.

The channel rejects zero capacity. A closed channel drains existing items, then returns empty; this compact API deliberately uses the same empty result for timeout and closed-and-drained. A production API can return separate statuses. C++ requires nonthrowing moves that do not call back into the channel. Close wakes callers but does not join them: the owner must stop and join all users before destroying the channel.

The deadline bounds condition waiting, not total method latency. Both versions can spend longer acquiring or reacquiring the mutex. They return an available item when the final locked check finds one, even if the deadline has just passed. If the contract forbids admission after expiry, check the clock again under the lock before removing an item; scheduling still prevents a guaranteed return time.

These transfer fragments isolate locking: assume nonnegative amounts, sufficient funds and representable arithmetic. In a financial API validate those conditions while holding both locks, and use these locks for every balance access. Java account ids must be unique to establish a total order.

The worker counts work under one lock; producers must use the same lock and notify after adding work. This fragment only decrements a counter: a real worker removes a task under the lock, then releases the lock before running it. Java interruption is propagated to the caller, which must handle it or restore the flag. The C++ stop check gives stop priority at that check; an already started unit can still finish.

A stop request does not interrupt arbitrary I/O, and referenced state must outlive the worker. Stop callbacks can run synchronously: a successful request_stop() invokes registered callbacks on the requesting thread, and registering after a stop request invokes the callback before its constructor returns. Keep callbacks short and nonthrowing, and do not request stop while holding a mutex that a callback needs.

In C++17, join this worker before result.get(), or use a joining RAII wrapper, so a rethrown exception never destroys a joinable std::thread. In a pool, a std::packaged_task stores either the result or the exception automatically; enqueue and dequeue it under the queue mutex, move it into a local, release the mutex, and only then run it.

POSIX threads: the C-only round

Research for this course found reports of India systems software rounds at Nvidia that were C only, alongside small C thread programs (odd and even printing, 1 to N in order). Most pthreads operations return 0 or an error number directly, without setting errno. Exceptions include pthread_self (thread id), pthread_equal (nonzero means equal), pthread_getspecific (pointer), and the successful serial-thread return from pthread_barrier_wait. Most sem_* operations return -1 and set errno on failure; sem_open instead returns SEM_FAILED. Compile and link with -pthread.

The C snippets below fail fast on unexpected pthread errors, including partial thread creation; a reusable library would return errors and unwind initialized resources. Assume no pthread_cancel: condition waits are cancellation points, and cancellation-safe C needs cleanup handlers to release a reacquired mutex. Semaphore counts and timeouts must be nonnegative and representable, releases must not overflow the count, and barrier parties must be positive. Destroy synchronization objects only after all callers have finished.

The deadline uses CLOCK_REALTIME because that is what pthread_cond_timedwait expects by default, so a wall clock step can stretch or shrink the wait. Mutex acquisition and reacquisition, and scheduling, can also delay the return beyond the deadline; this is not a hard elapsed-time bound. On Linux, set the condition's clock to CLOCK_MONOTONIC and compute the deadline from that clock instead.

The generation counter is what makes it reusable: a thread released from round k waits for "the generation changed", not for "waiting is zero", so a fast thread that re-enters for round k+1 cannot be confused with a straggler from round k.

Tools

  • ThreadSanitizer: compile with -fsanitize=thread -g; it reports observed data races with access stacks. Lock order inversion detection is available on Linux; Apple clang on this Mac does not report those potential deadlocks. AddressSanitizer (-fsanitize=address) catches use after free, which threads make common. See ThreadSanitizer.
  • A hung process: in gdb, thread apply all bt; in lldb, bt all. Look for two threads each waiting in a lock call held by the other.
  • On supported platforms, commonly Linux, Valgrind's Helgrind and DRD inspect executed accesses without recompiling, with substantial overhead; do not assume they run on this Mac.

Worked example: close races with a blocked sender

A capacity-one channel holds item A. A second sender cannot insert B, so it waits on not-full, releasing the mutex. Closing must reject B but preserve A for a receiver; waking only receivers would leave the sender asleep forever.

If the sender inserted B before close acquired the mutex, it would be accepted and later drained. Name that decision point. For a timed receive, compute the deadline once; each wakeup consumes the same budget. Neither a deadline nor a notification guarantees prompt scheduling.

Common mistakes

  • Joining only after get(). A future can rethrow before the join. Use a joining owner, or join first in this one-worker example.
  • Assuming a wakeup is permission. Condition waits re-check a predicate under the lock. Atomic wait instead hides internal spurious wakeups, but can miss a value that changes away and back.
  • Stopping while holding the worker's mutex. A joining destructor can deadlock if the worker needs that mutex to exit. Release it before joining and keep referenced state alive.
  • Resetting a timeout after every wakeup. Reuse one deadline. Cancellation must be part of the wait protocol, not just a flag nobody checks while blocked.
  • Confusing lock-free with fast or wait-free. Measure contention, and separately prove progress and object lifetime before removing a lock.

In the interview

The C++ reports reward fluency with the basics. A Databricks L4 candidate had to write the durable event writer in full C++ with a mutex, condition variables and std::promise and std::future; a Microsoft L61 candidate answered a multi-producer, multi-consumer question with std::unique_lock, std::mutex and std::condition_variable, then got thread_local questions; Rubrik's debugging round has handed over C++ producer-consumer code; Bloomberg rounds ask mutex versus semaphore and RAII; a Google L4 candidate needed the interviewer's help with C++ thread syntax. Type the monitor from memory, and say which standard each tool needs.

I will use the predicate form of wait, which loops for me, and a steady_clock deadline with wait_until for the timed version, so spurious wakeups do not restart the budget and wall-clock changes do not change my elapsed-time target. Reacquiring the mutex can still delay return.
std::counting_semaphore is C++20; if this compiler is C++17 or it is off limits, I will build it from a mutex, a condition variable and a count, which is also what I would do in C with pthreads.

Key takeaways

  • RAII guards always, and always named: std::scoped_lock lock(m);. Join every std::thread, or use std::jthread.
  • cv.wait(lock, pred) and wait_until(lock, deadline, pred) with steady_clock; change state under the mutex before notifying.
  • A data race is undefined behavior; volatile is not synchronization; start with seq_cst and relax only with a reason.
  • C++20 adds semaphores, latches, barriers, jthread and stop tokens; know the C++17 builds of each.
  • pthreads: most status-returning functions return error numbers directly, waits sit in while loops, and macOS lacks barriers, timed mutex locks, spinlocks and unnamed semaphores.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A function creates std::thread t(work); and returns without calling join() or detach(). What happens?
Why. Destroying a std::thread that is still joinable terminates the program, even if the thread's function has finished, because the thread object still owns that thread until it is joined, detached or moved from. std::jthread (C++20) joins in its destructor instead.
Assuming thread creation succeeds, what does this line do: std::async(std::launch::async, flushToDisk);, written as a statement on its own?
Why. Here the temporary is the last reference to an async-launched state, so its destruction waits for completion. Explicit launch::async rules out deferral; discarding the future is legal, though it can produce a warning. A promise-backed future does not have this blocking guarantee. The call is effectively synchronous, but a task exception remains in the discarded state rather than reaching the caller: retain the future and call get() to observe failure.
Inside a method, a developer writes std::unique_lock<std::mutex>(m); intending to lock the member mutex m. What actually happens?
Why. The parentheses are parsed as a declaration: a variable named m of type unique_lock, default constructed, owning no mutex. Clang warns about the vexing parse but compiles it. Name the guard: std::unique_lock<std::mutex> lock(m);.
In C++20, std::atomic<int> counter{3}; int expected = 3; is followed by bool ok = counter.compare_exchange_weak(expected, expected + 1);. With no other writers, which triples ok, expected, counter.load() are permitted by the standard? Select all that apply; print booleans as 0 or 1.Select all that apply
Why. Success stores 4 in the atomic and leaves expected unchanged at 3. Weak CAS may fail spuriously even when values match; failure loads the observed 3 into expected and leaves the atomic at 3. Neither path stores the desired 4 in expected. With competing writers, a failed CAS supplies an observed value that may immediately become stale; a loop recomputes its desired value and retries without needing an extra load.
Spot the wait bug in this pthreads consumer fragment. Assume the pthread calls succeed; the surrounding function unlocks mu after removing the item.
Why. POSIX allows spurious wakeups, and with several consumers a woken thread can lose the item to another that took the mutex first. while (count == 0) re-checks every time; an if does not. Holding the mutex while calling pthread_cond_wait is required: the call atomically releases it and begins waiting, then reacquires it before returning. Signalling before waiting neither stores a permit nor fixes the missing predicate check.
A C program for a round calls sem_init(&s, 0, 3) and runs on a Mac. What happens?
Why. macOS declares sem_init (deprecated) but does not implement it, so the failure shows up only at run time, and code that ignores the return value then uses an invalid semaphore. Named semaphores via sem_open work, and the mutex plus condition variable build works everywhere.
pthread_mutex_lock(&m) returns EDEADLK for a valid error-checking mutex. Where is that error reported?
Why. pthread_mutex_lock reports this error in its return value, not errno or thread-local storage. Status-returning pthread calls generally use this convention, but identity and data accessors differ. Most semaphore operations return -1 on failure and set errno; sem_open returns SEM_FAILED.

Explain
Map a Java ReentrantLock with two Conditions and a Semaphore onto C++20 and onto pthreads, assuming the Java lock is never acquired recursively, and name one behavior that differs.
Model answer

ReentrantLock maps to std::mutex held through std::unique_lock, and to pthread_mutex_t. Each Condition maps to a std::condition_variable and to a pthread_cond_t, all used with that one mutex. await is cv.wait(lock, pred) or pthread_cond_wait in a while loop; awaitNanos is wait_until with a steady_clock deadline or pthread_cond_timedwait with an absolute time; signal and signalAll are notify_one and notify_all, or pthread_cond_signal and pthread_cond_broadcast. The Semaphore maps to std::counting_semaphore in C++20 and to sem_t in POSIX, or to a mutex, condition variable and count where those are unavailable (C++17, or macOS for unnamed POSIX semaphores).

Differences worth naming: ReentrantLock is reentrant and std::mutex is not (relocking it is undefined behavior; a PTHREAD_MUTEX_RECURSIVE mutex is the pthreads equivalent); Java's lockInterruptibly has no direct C++ equivalent, where cancellation is cooperative through std::stop_token; and pthread_cond_timedwait uses a wall clock deadline by default while awaitNanos measures elapsed time.

Out loudabout 90 s
"This worker hangs when its owner is destroyed. Walk me through what you would check in the C++ shutdown path."
What a strong answer covers
  • A joinable jthread requests stop and joins, but stop is cooperative and destruction can block
  • Check whether the owner holds a mutex the worker needs before joining
  • Check ordinary condition waits and blocking I/O for a cancellation path
  • A stop-aware condition_variable_any wait returns the predicate value, so explicitly choose stop versus pending work
  • Stop admission, wake waiters, join users, then destroy shared state; define drain or discard
  • Test idle shutdown and pending work under a process timeout, and run ThreadSanitizer
How a senior would say it
I would first check what the worker is waiting for and whether shutdown can release that wait. A joining thread owner gives me lifetime management, not guaranteed termination. A joinable std::jthread requests stop and then joins, but the worker must cooperate. If the destructor holds the queue mutex while joining, and the worker needs that mutex to exit, I have created a deadlock. I would release the mutex before joining. Next I would inspect the wait. An ordinary condition variable does not wake merely because a stop token changed. I need a closed flag in the protected predicate and notifications, or a stop-aware condition variable wait. That stop-aware wait returns the predicate value, so pending work can make it return true even after stop. I must explicitly choose whether cancellation wins or accepted work drains. A token also cannot interrupt arbitrary blocking I/O; that needs its own cancellation or timeout mechanism. Finally, the queue, mutex and captured references must stay alive until all users have finished. My sequence is stop admission, publish shutdown, wake waiters, join, then destroy state. I would test both an idle worker and pending work, bound the test process runtime, and use ThreadSanitizer for observed data races.

Likely follow up: What changes if shutdown must drain every accepted task, including one that throws?

Out loudabout 60 s
"Can I replace this condition-variable wait with C++20 atomic wait? What changes?"
What a strong answer covers
  • Atomic wait fits a condition expressed by one atomic value, while a mutex predicate can cover several fields
  • wait(old) returns only after observing a different value and hides internal spurious wakeups
  • A transient change away and back can be missed, so use a generation counter when appropriate
  • Store the new state before notifying, and use release/acquire if publishing other data
  • Atomic wait has no standard timed or stop-token overload in C++20; lifetime still needs a protocol
How a senior would say it
I can use atomic wait if one atomic value expresses the condition I need to observe. For a queue whose size and closed flag form one invariant, a mutex and condition variable are usually clearer. Atomic wait takes an old value and returns only after observing a different one. It hides internal spurious wakeups, unlike a raw condition wait. But if a value changes away and back before I observe it, I can miss that transition. A generation counter can represent progress more reliably, provided I address wraparound. The producer stores the new state before notifying. If that state publishes other data, I also need the appropriate release and acquire ordering; notification alone is not the publication mechanism. C++20 atomic wait has no timed or stop-token overload. I would keep the condition-variable design if those requirements matter, and preserve the atomic object's lifetime until every user finishes.

Likely follow up: Does seeing the published pointer also guarantee that the pointed-to object remains alive?

Out loudabout 90 s
"You only have C and pthreads on this Mac. Build me a semaphore that can time out, and explain the traps."
What a strong answer covers
  • Use a nonnegative permit count, mutex and condition variable; macOS sem_init fails with ENOSYS
  • Acquire loops while the count is zero, then decrements under the mutex; release increments and signals
  • Compute one absolute deadline with the condition variable's clock, and re-check the count even on timeout
  • CLOCK_REALTIME can jump, and mutex reacquisition can delay return past the deadline
  • Handle pthread return codes directly, unlike semaphore errno conventions; define cancellation and overflow policy
  • Join all users before destroying the semaphore and test permit bounds, wakeups and timeout races
How a senior would say it
I would implement the semaphore with a permit count, a mutex and a condition variable. On this Mac, unnamed POSIX semaphores are unavailable: sem_init reports failure with ENOSYS. Named semaphores are another option, but the monitor implementation also lets me explain timed acquisition. Acquire takes the mutex, waits in a loop while the count is zero, then decrements before unlocking. Release increments under the same mutex and signals a waiter. The count remembers permits; the signal itself does not. For timeout, I compute one absolute deadline before entering the wait loop, using the condition variable's configured clock. The default is realtime, so a clock adjustment can change elapsed waiting time. I do not restart the deadline after a wakeup. Even when timed wait reports timeout, I inspect the count under the mutex once more, because a release may have raced with that timeout. Reacquiring the mutex can also delay return, so I would not promise an exact wall-clock bound. I handle pthread errors from return values directly and define valid counts, overflow and cancellation policy. Finally, all users must finish before destruction. I would test the maximum number inside, blocked acquisition followed by release, empty timeout, and a release racing with expiry.

Likely follow up: How would you provide a monotonic timeout on Linux, and what is different on macOS?
