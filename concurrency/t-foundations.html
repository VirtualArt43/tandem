Foundations: processes, threads and scheduling

Processes versus threads, concurrency versus parallelism, CPU versus I/O bound work, scheduling, context switches and the real cost of a thread.

1CoreprocessesthreadsLinkedIn
What is the difference between a process and a thread?
Model answer

A process is a running program with its own address space: its own virtual memory, open file descriptors and security identity. A thread is one path of execution inside a process: it has its own stack, registers and program counter, and it is scheduled by the OS or a language runtime. All threads of one process share the heap, the globals, the code and the open files.

That sharing is the whole trade off. Threads often cost less than separate processes, and they communicate by simply reading and writing the same memory, which is exactly why they need synchronization: every shared mutable object is a potential race condition. Separate address spaces contain ordinary private-memory corruption, although shared memory and external state remain shared failure paths. Processes communicate through IPC such as pipes, sockets or shared mappings. Switching address spaces can add TLB and cache costs; hardware address-space tags can preserve TLB entries.

Java platform and virtual threads live inside the JVM process; virtual threads share carrier OS threads. On mainstream C++ implementations std::thread uses an OS thread. POSIX fork(), not an ISO C++ API, creates a process.

Likely follow up: "So when would you choose processes?" When isolation matters more than sharing: a browser renderer per site, a PostgreSQL backend process per connection, or running untrusted plugins.

2CoreprocessesipcMicrosoft
How do two processes communicate, and why is that harder than two threads communicating?
Model answer

Threads already share an address space, but communication still needs synchronization and can incur cache-coherence costs. Processes normally have separate address spaces, so you choose an explicit IPC mechanism:

  • Pipes and FIFOs: byte streams; anonymous pipes commonly connect related processes, while named FIFOs can connect unrelated ones.
  • Sockets: Unix domain sockets locally, TCP across machines; both support bidirectional communication.
  • Shared memory: mappings created with shm_open and mmap, or shared file mappings, avoid copying each message through the kernel after setup.
  • Message queues, signals and files: different persistence, framing and notification tradeoffs.

Shared memory still needs a protocol: use a supported process-shared primitive such as a POSIX mutex configured with PTHREAD_PROCESS_SHARED. ISO C++ does not by itself guarantee that arbitrary std::atomic implementations work across processes. Use offsets rather than ordinary pointers because mapping addresses can differ.

Socket and pipe traffic commonly involves system calls and copies; shared-memory exchanges need neither per message. Neither mechanism is universally fastest. You also need framing, ownership and crash recovery: a process can die while holding a resource or halfway through a message.

Likely follow up: "Which would you choose?" Start with sockets or pipes for a clear protocol; use shared memory when measurements justify the additional synchronization and recovery work.

3Coreconcepts
What is the difference between concurrency and parallelism?
Model answer

Concurrency is about structure: several tasks are in progress during the same period, and their steps interleave. Parallelism is about execution: steps execute simultaneously using multiple hardware execution resources. Concurrency describes overlapping task lifetimes; parallelism describes simultaneous execution.

One hardware thread can run a highly concurrent program by time slicing, without executing two software threads simultaneously. A vectorized loop is parallel without being concurrent in the threads sense. Most servers are both.

Why the distinction matters in an interview:

  • Races do not need parallelism. Preemption can switch threads between any two instructions on one core, so a single core machine still loses updates.
  • Concurrency buys responsiveness and lets you overlap waiting (I/O). Parallelism buys throughput on CPU work and is capped by the number of cores.

Likely follow up: "Would a single core machine need locks?" Yes, for the same reasons: preemption and compiler reordering.

4Corecpu-boundio-boundDatabricks
What is the difference between CPU bound and I/O bound work, and how do you know that adding threads will help?
Model answer

CPU bound work spends its time computing. Beyond the available hardware parallelism, more runnable threads often just take turns, and the speedup is capped by the core count and by the serial part of the work. I/O bound work spends its time waiting for disk, network or a database. While a thread waits, the scheduler can run another thread on that CPU, so concurrent requests can overlap their waits.

To know which you have, measure wall time against CPU time per task. A crawler fetch that takes 200 ms of wall time and 2 ms of CPU is 99 percent waiting, so many concurrent fetches will overlap that latency. A rough sizing rule is threads = available CPUs x target utilization x (1 + wait time / compute time), for independent blocking tasks with stable measured times. It is a starting estimate, not a capacity guarantee.

Then the bottleneck moves somewhere else, and a senior answer names it: network bandwidth, the remote host's rate limit or politeness rules, the database connection pool, or disk throughput. Past that point, more threads only add queueing.

The work is I/O bound: each worker sits waiting on fetch, so parallel fetches overlap the latency, until bandwidth or the remote rate limit becomes the bottleneck.

Likely follow up: "How many threads, then?" Start from the formula, cap it by the downstream limit, and confirm with a load test.

5CoreschedulerosRubrik
How does the OS scheduler decide which thread runs next?
Model answer

The scheduler chooses among runnable OS threads allowed on a CPU. A sleeping thread is not eligible to execute until its event occurs. Scheduling decisions consider the policy, priority, CPU affinity, fairness and locality; they occur when a thread blocks, exhausts its allocation, or a wakeup makes another thread preferable.

Linux commonly uses per-CPU scheduling structures with load balancing. Its normal scheduling class began moving from CFS to EEVDF in kernel 6.6. EEVDF chooses the earliest virtual deadline among eligible tasks owed CPU time. Real-time classes such as SCHED_FIFO and SCHED_RR outrank normal work, subject to configuration and throttling. This is Linux policy, not a Java or C++ guarantee.

Do not assume a fixed millisecond time slice, FIFO wakeup order or immediate execution after notification. Affinity limits where a thread may run; it does not reserve a CPU. A fair lock orders lock acquisition, not all CPU scheduling.

Likely follow up: "What does blocking cost?" A parked thread consumes no execution time while asleep, but parking, waking, scheduling and cache disruption cost work. It also retains resources. Java virtual threads add a runtime scheduler above the OS scheduler.

6Corememoryprocesses
Sketch the memory layout of a process. Which parts do its threads share, and which are private to each thread?
Model answer

A useful process sketch has code and read-only data, initialized globals, zero-initialized storage, dynamic allocations, mapped files and libraries, and thread stacks. On typical Linux systems the traditional heap grows upward and stacks downward, but ASLR, allocator mappings and architecture make this a sketch, not a guaranteed address order. Virtual pages need not all have resident physical frames.

Threads share the address space, heap, globals, mappings and process resources such as file descriptors. Each OS thread has its own register state, stack, thread-local storage and, on POSIX, signal mask. A thread's stack is logically private, not memory-protected from other threads: sharing a pointer to a local makes both lifetime and synchronization your responsibility.

In Java, local references belong to an invocation, but the objects they reference may be shared. The JVM can optimize away allocations or keep objects confined; declaring a reference local does not make its object private.

Likely follow up: "What happens on stack overflow?" Guard pages are a common implementation technique. Java normally throws StackOverflowError; exhausting a native C++ stack often faults, such as with SIGSEGV on Linux, but ISO C++ specifies no portable recovery behavior. Stack sizes and guard arrangements depend on the runtime and platform.

7Corecontext-switchnumbersLinkedIn
What is a context switch, and what does it cost?
Model answer

A context switch saves one thread's CPU state (registers, program counter, stack pointer, floating point and vector state) and restores another's. It happens on preemption, when a thread blocks, or when it yields. Between two threads of the same process the address space stays; between processes the active address-space mappings change too; tagged TLB entries need not all be flushed.

Costs, as orders of magnitude on modern hardware:

  • Direct cost: about 1 to a few microseconds, including entering the kernel and running the scheduler.
  • Indirect cost: often larger. The incoming thread finds cold caches and TLB entries, which can slow it for often tens of microseconds or more, depending on the platform and load.
  • For comparison: an uncontended mutex lock is tens of nanoseconds, and a simple system call that does not switch can take hundreds of nanoseconds. These illustrative orders of magnitude vary with hardware, mitigations and load.

Frequent wakeups and oversubscription add scheduling overhead. Brief spinning can beat blocking when the owner is running and the expected wait is shorter than parking and waking.

Each put that wakes a sleeping consumer costs a wakeup and probably a context switch, so I dequeue a bounded batch under the lock, release it, and process that batch outside the lock.

Likely follow up: "How would you see it?" On Linux, /proc/<pid>/task/<tid>/status shows per-thread voluntary_ctxt_switches (blocking) and nonvoluntary_ctxt_switches (preempted); perf and vmstat show system wide rates.

8Corethread-statesjava
What states can a thread be in, and what does blocking really do?
Model answer

The OS view: running on a core, ready (runnable, waiting for a core), or blocked (waiting for an event, using no CPU, not in the run queue). When the event arrives, the thread moves back to ready and may still wait for a core.

Java's Thread.State:

  • NEW: created, not started. TERMINATED: finished.
  • RUNNABLE: running or ready. It also covers threads blocked inside native I/O such as a socket read, so RUNNABLE in a thread dump does not mean burning CPU.
  • BLOCKED: waiting to enter a synchronized monitor. Only synchronized produces this state.
  • WAITING: wait(), join(), LockSupport.park() with no timeout. A thread waiting for a ReentrantLock shows here, as parked, not as BLOCKED.
  • TIMED_WAITING: sleep, wait(ms), parkNanos.

Blocked platform threads retain stacks and OS resources. An unmounted Java virtual thread retains heap-backed stack state without a dedicated blocked OS thread. BLOCKED also covers monitor reacquisition after Object.wait().

Likely follow up: "A thread dump shows 200 threads BLOCKED on the same monitor. What does it tell you?" A hot lock: find the one thread that holds it (the dump says "locked") and see why it holds it so long, often I/O inside the critical section.

9Seniorcostnumbers
What does a thread cost, and what happens if a server creates one thread per request at 10,000 concurrent requests?
Model answer

Costs, as orders of magnitude on 64 bit Linux:

  • Stack: A HotSpot platform-thread stack is often around 1 MiB, configurable with -Xss; defaults vary by platform. Linux glibc commonly derives its default from the startup stack limit, often 8 MiB. That is virtual address space; resident memory depends on touched pages, guard mappings and runtime metadata.
  • Creation and teardown: often tens of microseconds or more, depending on the platform and load.
  • Scheduling: every runnable thread competes for cores.

At 10,000 threads, even 100 KiB of resident stack per thread is roughly 1 GiB, before request data and runtime overhead. The real problems: if many are runnable at once, context switches and cache thrash dominate; user, system, address-space and container limits (ulimit -u, kernel.threads-max, vm.max_map_count, a cgroup pids limit) can make creation fail, which Java reports as OutOfMemoryError: unable to create native thread; and there is no backpressure, so the server accepts work it cannot finish and every request gets slower. The bottleneck usually moves downstream: 10,000 threads sharing a 50 connection database pool just queue there.

Better designs: a bounded pool with a bounded queue that rejects (HTTP 503) when full, asynchronous I/O, or Java 21 virtual threads for blocking style code, with bounded admission and a semaphore or connection pool limiting downstream concurrency.

Likely follow up: "What is the bottleneck?" Name it concretely: the connection pool, the database's own CPU, or memory per in flight request.

10Seniorperformancescalability
Why can adding threads make a program slower?
Model answer
  • Lock contention: threads queue on a shared lock, so the serial part grows and waiters pile up in convoys.
  • Context switching: once runnable threads exceed cores, time goes into switching and refilling caches.
  • Cache effects: working sets evict each other, and writes to shared data bounce cache lines between cores (true sharing and false sharing).
  • Memory bandwidth: streaming workloads saturate it with a few cores.
  • Coordination overhead: splitting, merging and synchronizing can cost more than small tasks themselves.
  • Downstream overload: a database given more concurrent queries makes each one slower and can thrash.

And amdahl's law caps the speedup by the serial fraction whatever you do. The usual curve: throughput rises, flattens, then falls.

I find the knee of the throughput curve with a load test, then look at why it bends: CPU saturation, lock contention or a downstream limit.

Likely follow up: "How would you tell which one it is?" CPU utilization and context switch rates first; then lock profiling (Java Flight Recorder's jdk.JavaMonitorEnter and jdk.ThreadPark events, async profiler's lock mode; off CPU profiling with perf in C++).

11Corethreadsjavacpp
What are kernel threads, user (green) threads and M:N scheduling? Which does Java use, and which does C++ use?
Model answer
  • 1:1 (kernel threads): each language thread is an OS thread scheduled by the kernel. A blocking system call blocks only that thread, and threads run in parallel on many cores.
  • N:1 (green threads): a runtime schedules many threads on one OS thread. Switches are cheap, but an unadapted blocking system call stalls them all and there is no parallelism. Very early JVMs worked this way.
  • M:N: many user level threads multiplexed over a pool of kernel threads. The runtime adapts blocking operations where possible; an unadapted operation can still block a carrier. Go goroutines, Erlang processes and Java virtual threads work this way.

Java: platform threads are 1:1. Virtual threads (final in Java 21) are M:N: they are mounted on carrier threads from a ForkJoinPool, and when an unpinned thread blocks on supported socket I/O, sleep or a java.util.concurrent lock, it can unmount so the carrier runs another.

C++: std::thread is normally 1:1 (pthreads on Linux and macOS), although ISO C++ does not mandate that mapping. C++20 coroutines are functions that can suspend; they are not threads, and you bring your own scheduler, such as an event loop or a thread pool.

Likely follow up: "Why does M:N work now when it was abandoned before?" Modern runtimes integrate many blocking APIs with their schedulers; they need not make every native operation yield. Code that blocks inside native calls (or, in Java 21, inside synchronized) still pins the carrier.

12Senioramdahlnumbers
A job is 95 percent parallelizable. What is the best speedup on 8 cores, and on unlimited cores?
Model answer

Amdahl's law: S(n) = 1 / ((1 - p) + p / n), where p is the parallel fraction.

  • 8 cores: 1 / (0.05 + 0.95 / 8) = 1 / 0.16875, about 5.9x, not 8x.
  • Unlimited cores: 1 / 0.05 = 20x. No number of cores beats it for this fixed workload and fixed serial fraction, ignoring overhead.

The serial fraction is measured in the original single-worker workload. Serialized lock work, startup and merging may contribute; extra lock contention, coordination and load imbalance are additional overheads that can make scaling worse. That is why shrinking critical sections often helps more than adding cores.

The same law applies to throughput under a lock: if every request must hold one lock for 10 microseconds, the whole system can never exceed 100,000 requests per second, however many threads you add.

Gustafson's law is the optimistic counterpart: if the problem grows with the machine (more data, not the same data faster), the scaled speedup is (1 - p) + p * n. Here p is measured in the scaled parallel run, not Amdahl's original single-worker run, so substituting 0.95 describes a different workload assumption.

Likely follow up: "What would you do to get closer to 8x?" Find the serial part with a profiler, shorten or split it, and balance the work so no core idles at the end.

13Coreprocessesthreadsdesign
Processes are safer than threads. Why not use processes everywhere?
Model answer

Because isolation has a price. Processes do not share a heap, so large in memory state (a cache, an index, a model) must be duplicated, placed in explicit shared memory, or fetched over IPC. Communication through sockets commonly costs system calls and copies; shared-memory IPC can avoid per-message copies. Creation is heavier than a thread, and each process carries its own runtime (a separate JVM heap and garbage collector, for example).

What processes buy: fault isolation (private-memory corruption can be contained within one worker, though shared state still needs recovery), separate memory accounting, independent restarts, and independent resource limits.

Real systems pick per need: PostgreSQL uses a process per connection plus a shared memory buffer pool; Chrome isolates sites in separate renderer processes; nginx runs a few worker processes, each an event loop; most JVM and C++ services use threads in one process because they share caches and connection pools.

The choice is about failure domains and how much state must be shared, not just speed.

Likely follow up: "How would processes share a counter?" A shared mapping with supported process-shared synchronization, or one owner process that others message.

14Seniorhardwarejavacpp
How many threads can truly run in parallel on a machine, and how do you ask from code?
Model answer

The upper bound on simultaneously executing software threads is the number of available logical CPUs, subject to affinity and CPU quotas. SMT can expose several hardware threads per physical core, but they share execution resources. It does not multiply compute throughput by the SMT width; the benefit can be positive, negligible or negative depending on the workload.

Java promises an integer count available to the JVM, at least one. HotSpot on supported Linux configurations accounts for container settings, but fractional quotas and overrides mean this is not a throughput guarantee. C++ promises only a hint, possibly zero; it need not respect affinity or container quotas. Neither API tells you the best pool size.

Likely follow up: "Should CPU work use every logical CPU?" Start with a bounded pool, then benchmark physical-core and logical-CPU counts using the actual workload and container limits. Memory bandwidth, cache sharing and other tenants can lower the optimum.

15Stretchprocessescppos
What happens to the other threads when a multithreaded process calls fork()?
Model answer

The child inherits the address space, with private mappings generally copied on write and shared mappings still shared, but only one thread: the one that called fork(). The other threads simply do not exist in the child, yet their memory state is copied as it was at that instant.

The danger: any mutex another thread held at that moment (the allocator's internal lock, a logging lock, your own) is copied in the locked state, and no thread in the child will ever unlock it. Calling a library routine that needs such state can deadlock; do not rely on libraries repairing every inherited lock. That is why POSIX says that after fork() in a multithreaded program, the child may only call async signal safe functions until it calls exec.

Practical rules:

  • Fork, then exec immediately, or use posix_spawn.
  • If you need forked workers (prefork servers), fork them before starting any threads.
  • pthread_atfork handlers exist but are very hard to get right for every lock in every library.

Java's ProcessBuilder delegates child creation to the JDK's platform implementation; Java application code does not run inside a forked copy of the parent JVM.

Likely follow up: "Why is only one thread copied?" That is the POSIX contract: the child resumes at the calling thread's return from fork; it does not resume every thread or repair their protocols.

16Seniorracesos
On a single core machine, can two threads still race?
Model answer

Yes. Three reasons:

  • Preemption: a timer interrupt can switch threads between the load and the store of count += 1. The compiler typically emits separate load, add and store instructions, and you cannot rely on it emitting one indivisible instruction.
  • Compiler reordering and hoisting happen regardless of core count: a flag read hoisted out of a loop never sees another thread's update, even on one core.
  • Language rules: in C++ an unsynchronized conflicting access is a data race and undefined behavior on any hardware; in Java the memory model gives no visibility guarantee without a happens-before edge.

One physical core may still have SMT hardware threads. Even on one hardware thread, testing fewer simultaneous executions does not establish a language-level happens-before relationship or prove correctness.

The rules do not depend on the core count: all shared mutable state still needs synchronization.

Likely follow up: "Then is volatile enough on one core?" Java volatile can publish a flag, but it does not make count += 1 atomic. C++ volatile provides neither inter-thread synchronization nor atomicity; use std::atomic or a mutex on any core count.
