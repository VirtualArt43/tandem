Classic synchronization problems

Producer-consumer, readers-writers, the bathroom, H2O, the barber, ordering puzzles and hand-built semaphores and barriers: the shapes and the follow ups.

1Coreproducer-consumercondition-variableLinkedInBloombergRubrik
Implement a bounded blocking buffer without library queues, and explain every choice.
Model answer

The state is a fixed ring buffer plus head, tail and count, all guarded by one lock. There are two conditions, one per predicate: producers wait on "not full", consumers on "not empty", so a signal always reaches a thread that can use it. Every wait sits in a while loop, because a wakeup is only a hint: it can be spurious, or another thread can take the slot first.

signal (not signalAll) is safe here because each condition has only one kind of waiter and each operation frees exactly one slot or item. The Java version propagates InterruptedException so callers can cancel a blocked put or take.

Likely follow up: "Add offer with a timeout." Replace the loop with while (count == slots.length) { if (nanos <= 0) return false; nanos = notFull.awaitNanos(nanos); }; in C++ use wait_until with a steady_clock deadline and the same predicate.

2Coreproducer-consumernotifyLinkedIn
With synchronized, wait and notify, why does a bounded buffer need notifyAll? Show the interleaving that hangs.
Model answer

An intrinsic lock has one wait set, so producers and consumers sleep together and notify may wake the wrong kind of thread. Take capacity 1, two producers and two consumers:

The one signal that mattered went to a consumer who could not use it, and was effectively lost. notifyAll wakes everyone, so whoever can proceed will, at the cost of a small thundering herd.

The better fix is a ReentrantLock with two Condition objects, notFull and notEmpty, so each signal goes to a thread that can use it and signal becomes safe. In C++ every std::condition_variable is already separate, so you naturally write two.

Likely follow up: "When is plain notify safe?" When all waiters wait for the same predicate, and each notify enables exactly one of them to proceed: a semaphore's release is the classic case.

3Seniorproducer-consumershutdownLinkedIn
How do you shut down a producer-consumer system cleanly, without losing items or leaving threads blocked?
Model answer

Decide the contract first: graceful (stop accepting, deliver everything already queued) or immediate (stop now, return what was not processed).

The flag approach puts a closed boolean inside the buffer, guarded by its lock:

Every wait predicate must include closed, or a thread sleeps through the shutdown. signalAll is right here, because every waiter must react.

The poison pill approach puts one special item per consumer after the producers stop. It works with any queue, but you must know the consumer count, the producers must be finished first, and it breaks with priority queues, where the pill does not come out last.

Then the owner joins every consumer with a timeout. In C++ the same design uses a bool closed_ checked in both wait predicates and notify_all in close, or std::jthread with a std::stop_token and std::condition_variable_any.

Likely follow up: "And immediate shutdown?" Set the flag, drain the buffer into a list you return, and interrupt or stop the consumers. That is exactly what shutdownNow does in an executor.

4Coreread-write-lockreaders-writersRubrikMicrosoft
Implement a read-write lock yourself. Which policy did you pick, and why?
Model answer

The state is the number of active readers, whether a writer is active, and the number of waiting writers. I pick writer preference, because with reader preference a steady stream of readers starves writers forever. Here new readers wait whenever a writer is active or waiting. The price is the mirror image: a steady stream of writers can now starve readers.

The C++ method names match std::shared_mutex, so std::shared_lock and std::unique_lock work with it. The Java finally matters: an interrupted writer must stop blocking readers.

Likely follow up: "Is it reentrant? Can a reader upgrade?" Neither. A reader that calls lockWrite waits for readers == 0, which includes itself, so it hangs forever. Even a nested read deadlocks: a reader that calls lockRead again while a writer waits blocks behind that writer, and the writer waits for this reader. Supporting reentrancy needs a per-thread hold count, which is where ReentrantReadWriteLock spends most of its complexity.

5Seniorreaders-writerslinked-listRubrik
Searchers, inserters and deleters share a singly linked list. Searchers run with anything except deleters, inserters exclude each other, and a deleter excludes everyone. Design it.
Model answer

This is the searcher-inserter-deleter problem from The Little Book of Semaphores. Map the roles onto a read-write lock plus one extra mutex:

  • A searcher takes the read lock.
  • An inserter takes the insert mutex, then the read lock. It shares the read side with searchers but is serialized against other inserters.
  • A deleter takes the write lock, which waits for every searcher and the inserter to leave.

There is no cycle: deleters never touch the insert mutex, and inserters always take it before the read lock. Use a fair or writer-preferring read-write lock, or deleters starve under a steady search load.

The trap seniors are expected to catch: a searcher and the inserter run at the same time under shared locks, so the shared lock gives no ordering between them. The inserter must build the new node completely and then link it with a publishing write. In Java the next field is volatile; in C++ it is std::atomic<Node*>, stored with memory_order_release and loaded with memory_order_acquire. Otherwise a searcher can see the link before the node's value. Appending at the tail is a single pointer write, so searchers see either the old list or the new one.

Downey's original uses semaphores and "lightswitches" (the first searcher in locks out deleters, the last one out lets them in): equivalent, but harder to get right live.

Likely follow up: "What races do hand-rolled semaphore versions have?" Typically a deleter that can start while a search is still in progress, or an inserter whose new node is not safely published to concurrent searchers.

6SeniormonitorfairnessbathroomRubrik
One bathroom holds at most three people, and two parties may never be inside together. People queue, each stays for a known time, and the most eligible waiting person enters whenever there is room. Design the synchronization.
Model answer

This is a monitor: one lock, one condition, and state that every decision reads.

  • State: inside (0 to 3), currentParty (null when empty), and a FIFO list of waiting people with their arrival order.
  • Invariant: inside <= 3, and everyone inside belongs to currentParty.
  • Enter: add yourself to the waiting list, then while (!canEnter(me)) changed.await();, then remove yourself, increment inside, set the party and signalAll, because the next compatible person may also fit now.
  • Use the bathroom for f(name) outside the lock.
  • Leave: lock, decrement inside, clear the party at zero, signalAll.

The whole question is the admission rule inside canEnter. Strict FIFO: only the head of the queue may enter, and only if compatible. Nobody starves, but a party switch empties the bathroom while compatible people wait. "First compatible in the queue" uses the space better but can starve the other party forever. A middle ground worth proposing: admit the first compatible waiter, but once the head of the queue belongs to the other party, stop admitting the current party so the room drains and the turn passes.

Handle interruption: a waiter that is interrupted must remove itself from the queue and signalAll, or it blocks everyone behind it.

Likely follow up: "Why signalAll rather than signal?" Waiters have different predicates (different parties, different queue positions). A single signal can go to someone who still cannot enter while a person who could enter sleeps.

7CoreschedulingfairnessRubrik
Before coding an admission problem, the interviewer asks you to compare resource allocation policies. What do you say?
Model answer
  • FIFO: serve in arrival order. Simple and starvation free. It suffers head of line blocking: an incompatible head makes compatible requests behind it wait, which lowers utilization.
  • Priority: serve the most important first. Good for latency classes, but low priority requests can starve, so add aging, where waiting raises priority.
  • Shortest job first: serve the shortest expected duration first. It minimizes average waiting time when durations are known, as with f(name) in the bathroom problem, but long jobs can starve.
  • Round robin or turn taking: groups alternate, possibly with a batch quota per turn. Fair across groups, and each turn still batches compatible work.
  • First fit, or most eligible first: admit the first request that fits now. Highest utilization, and it can starve requests that never fit.

Then tie it to the problem: "I will admit compatible people in arrival order, but cap each party's turn at K entries while the other party waits. That gives bounded waiting, which is the property I can prove, and I lose a little throughput at party switches." Naming the trade-off of throughput against fairness is what the question is really checking.

The same vocabulary covers CPU scheduling (FCFS, SJF, round robin, multilevel feedback queues), so the answer doubles for an OS question.

Likely follow up: "Implement your policy." Keep the waiting list in arrival order and put the policy in one canEnter method, so switching policies is a one function change. That is also good design for the grader.

8Coresemaphorebarrierh2oLinkedIn
Solve Building H2O: hydrogen and oxygen threads must leave in groups of two H and one O.
Model answer

Use two semaphores to admit exactly two hydrogens and one oxygen into the current molecule, and a barrier of three so that group bonds together before anyone leaves. A thread returns its permit only after it has released, so the next molecule cannot form until the current one is complete.

Why it is correct: between acquire and release there are at most two H and one O, and the barrier needs three parties, so it trips only on exactly 2H plus 1O. The next group needs both H permits and the O permit back, and each is returned only after that atom has printed.

Likely follow up: "No C++20?" Replace the semaphores with a mutex, counters and a condition variable, and build the barrier with a generation count.

9CoreorderingsemaphoreMicrosoftNvidia
Two threads print odd and even numbers alternately up to N. How do you make them take turns, and what goes wrong at the end?
Model answer

Pass a turn back and forth. Each thread waits for its own turn, prints, and hands the turn to the other. Two semaphores make the handoff explicit: odd starts with one permit, even with zero.

The end is where these puzzles break. Each loop must know its own last number, or a thread waits for a turn that never comes. With the general version (K threads and a shared turn variable on one condition), the wait predicate must include "finished", and the last printer must notifyAll, or the other threads sleep forever. Always ask yourself who wakes the threads after the last item.

Likely follow up: "Now K threads print 1 to N round robin." One lock, one condition and a shared next = 1. Thread id (0 to K minus 1) loops: wait while (next <= n && next % k != id); if next > n, exit; otherwise print, increment next and notifyAll. The next <= n in the wait is what lets every thread out at the end. A condition per thread, or K semaphores, lets you wake only the next one.

10SeniorsemaphorebarberRubrik
Explain the sleeping barber problem, the race in the naive version, and how a debugging round could break it at shutdown.
Model answer

A barber sleeps when nobody is waiting. A customer wakes the barber if the barber is asleep, sits in a free chair if the barber is busy, and leaves if every chair is taken. The naive version races: a customer sees the barber busy and walks to the waiting room, while the barber finishes, sees an empty waiting room and goes to sleep. The customer then sits and waits forever. The check and the sleep are not atomic, which is a lost wakeup.

The counting semaphore customers remembers wakeups that arrive while the barber is busy, so none are lost.

At shutdown the usual bugs are: the barber blocked forever in wait(customers) after closing time (no flag and no wakeup), customers still in chairs who are neither served nor told to leave, and threads joined while they still wait on a semaphore. Fix it with a closing flag checked under the mutex, an extra signal(customers) so the barber wakes and sees it, an explicit decision for queued customers, and joins with timeouts.

Likely follow up: "Several barbers?" The same code works with N barber threads. The done signal must reach the right customer, so give each customer its own semaphore or future.

11Coresemaphorecondition-variableMicrosoft
Implement a counting semaphore using only a mutex and a condition variable.
Model answer

A semaphore is a counter of permits with "wait while zero". The monitor version is short, and it is the shape behind every "build a primitive" question.

notify is safe here because all waiters share one predicate and each release enables exactly one acquire. Java also guarantees that a notify is not lost to an interrupt: if the chosen waiter throws InterruptedException instead of returning, another waiter is woken.

Points to state out loud: there is no owner, so any thread may release, which is what makes it a signaling tool and not a lock. It is not fair, because a barging thread can take a permit ahead of a waiter. And release beyond the initial count is allowed here, as in Java's Semaphore. std::counting_semaphore allows it too, but its count must never exceed max(); for std::binary_semaphore that is 1, so a double release is undefined behavior.

Likely follow up: "Add tryAcquire(timeout)." Java: compute a deadline from System.nanoTime(), loop on wait(remainingMillis) while recomputing what remains, and return false once nothing remains, never calling wait(0), which means wait forever. C++: cv_.wait_until(lk, deadline, pred) returns false on timeout.

12SeniorbarriergenerationRubrik
Build a reusable barrier. Why is a simple counter not enough?
Model answer

A one-shot barrier is a counter and a condition: the last thread to arrive wakes everyone. To reuse it, the counter must reset, and that creates a race. A fast thread leaves round 1, arrives for round 2 and increments the count, while a slow thread from round 1 has not yet woken. If the slow thread's predicate was count == parties or count == 0, it may see round 2's value and sleep forever. The fix is a generation number: each waiter waits for the generation to change, not for a count value.

This is what level-synchronous parallel BFS needs: every worker finishes level k before anyone starts level k plus 1.

Likely follow up: "What if a waiter is interrupted?" Its arrival was counted, so the round can never complete. CyclicBarrier handles this by breaking the barrier: the interrupted thread gets InterruptedException, every other waiter (and any later arrival) gets BrokenBarrierException, and someone must reset it. In your own barrier, either do the same with a broken flag in the predicate, or make the wait uninterruptible.

13CorelatchbarriersemaphoreRubrik
CountDownLatch, CyclicBarrier, Semaphore: when do you choose each? (std::latch, std::barrier and std::counting_semaphore in C++20.)
Model answer
  • Latch: one-shot "wait until N events have happened". Usually the threads that count down are not the ones that wait, and countDown never blocks. Use it for "start when all workers are ready", "main waits until N tasks finish", or a start gate in tests. It cannot be reset.
  • Barrier: N peer threads wait for each other, repeatedly. Everyone both arrives and waits. Use it for phases, such as simulation steps or level-by-level BFS. CyclicBarrier can run an action when each phase completes, and so can std::barrier with a completion function.
  • Semaphore: a count of permits, a resource limit. Use it for "at most K at once" (connection slots, concurrent downloads, the "only 3 threads at once" question) or as a signal with no owner. It is not a mutual exclusion lock, and nobody owns a permit.
  • Phaser (Java): a reusable barrier whose parties can register and leave dynamically.

The mistakes interviewers probe: using a barrier where workers should not wait for each other (they then stall on the slowest), using a latch for a repeating phase (it cannot be reset), and using a Semaphore(1) as a lock. That last one has no owner check and no reentrancy, so a bug that releases twice silently admits two threads.

Likely follow up: "Seat booking: would you use a barrier?" No. Concurrent bookings do not wait for each other; you need per-seat atomicity (a lock per seat or a compare-and-set), plus a semaphore only if total concurrency must be capped.

14Seniorread-write-lockupgradejavacpp
Can a thread upgrade a read lock to a write lock? What do ReentrantReadWriteLock, StampedLock and std::shared_mutex allow?
Model answer

Not in general, because two readers that both try to upgrade deadlock: each waits for the other to drop its read lock. So most locks refuse to upgrade.

  • ReentrantReadWriteLock: no upgrade. A thread holding the read lock that calls writeLock().lock() waits for the reader count to reach zero, which includes itself, so it hangs. Downgrade is allowed: take the write lock, take the read lock, release the write lock.
  • StampedLock: tryConvertToWriteLock(stamp) succeeds only if the conversion is possible right now, for example when you are the only reader. On failure it returns zero and you fall back to releasing and taking the write lock.
  • std::shared_mutex: no upgrade operation. Boost's upgrade_mutex offers an upgradeable shared mode that only one thread can hold at a time, which is what makes its upgrade deadlock free.

15Seniorread-write-locklifecycleRubrik
Wrap a client whose init must run alone, whose requests may run concurrently once init succeeded, and whose close must wait for in-flight requests and run only once.
Model answer

This is readers-writers in disguise. Requests are readers; init and close are writers. Add an explicit state machine so every call knows what is legal.

The state check happens while holding the read lock, so close cannot slip in between the check and the call. The fair mode stops a steady request stream from starving close. In C++ the same shape uses std::shared_mutex, with std::shared_lock in request and std::unique_lock in init and close.

Likely follow up: "Requests should wait for init instead of failing." Add a one-shot gate that init opens when it finishes, success or failure (a CountDownLatch(1) or a CompletableFuture), and have request wait on it before taking the read lock. Waiting must happen outside the read lock, or init can never take the write lock; the read lock cannot hold a condition anyway (readLock().newCondition() throws UnsupportedOperationException).
