equals, hashCode and objects as keys

The equals and hashCode contracts, how hash maps use them, and why a key that changes after insertion breaks any map, ConcurrentHashMap included.

Asked atDatabricksLinkedInApple
Before this:final, immutability and records

Every cache, deduplication set, lock table and per-user counter in a concurrent program is a hash map keyed by your objects. If equals and hashCode are wrong, no amount of locking will make that map correct, and a ConcurrentHashMap will lose your entries just as politely as a HashMap.

In plain words

Picture a large post office with numbered pigeonholes. To file a letter, the clerk works out a pigeonhole number from the address (that is hashCode), then, inside that pigeonhole, compares full addresses one by one (that is equals). The system works only if the same address always gives the same pigeonhole number, and if two letters that count as "the same address" always land in the same pigeonhole.

Now suppose someone rewrites the address on a letter after it was filed. When they come to collect it, the clerk computes the pigeonhole for the new address, looks there, and finds nothing. The letter is still in the building, in the old pigeonhole, and nobody will ever find it again. A key that changes after it is filed is lost, however careful the clerks are about taking turns.

Why this matters for concurrency

  • Concurrent code is full of maps keyed by your objects: caches, single-flight tables, per-key locks, rate limiters, deduplication sets. All of them rely on equals and hashCode.
  • A thread-safe map protects its own structure, not your keys. If a key's fields change after insertion, or another thread changes them, ConcurrentHashMap loses the entry exactly like HashMap does.
  • hashCode decides which lock you contend on. ConcurrentHashMap locks one bin at a time, and lock striping picks a stripe from the hash, so a bad hash function turns a concurrent map into a single hot lock.
  • Databricks has spent most of a concurrency round on how ConcurrentHashMap locking works and why HashMap is not thread-safe. LinkedIn has asked for a thread-safe hash map in a phone screen, and Apple for a thread-safe concurrent hash map. Every one of those answers starts with how keys find their bucket.

Identity versus equality

a == b on references asks "are these the same object?". a.equals(b) asks "do these mean the same thing?". The version every class inherits from Object is identity: equals is ==, and hashCode is the identity hash code, a number fixed for the object's lifetime and unrelated to its contents. In HotSpot it is generated the first time it is needed and stored in the object header, which is why it is not a memory address and does not change when the garbage collector moves the object.

Value-like classes override both: String, the boxed types, List implementations, records. Two different String objects with the same characters are equals and have the same hashCode. That is what lets map.get("asha") find an entry that was stored with a different String object.

The equals contract

equals must behave like a sensible "same value" test. The rules, with what breaks when you ignore them:

RuleMeaningA typical way to break it
Reflexivex.equals(x) is trueRarely broken by accident
Symmetricx.equals(y) exactly when y.equals(x)A case-insensitive wrapper that says it equals a plain String, while String disagrees
Transitiveif x equals y and y equals z, then x equals zA subclass that adds a field and compares it only sometimes
ConsistentRepeated calls give the same answer while the objects do not changeComparing something time-dependent, or a field another thread is changing
Not equal to nullx.equals(null) is false, and never throwsCalling a method on the argument without checking it

Collections assume these rules. Break symmetry and list.contains(x) can disagree with set.contains(x); break consistency and a lookup that worked a moment ago fails now.

The hashCode contract

  1. Equal objects must have equal hash codes. This is the rule people break, by overriding equals and forgetting hashCode.
  2. Calling hashCode repeatedly on an object gives the same number, as long as nothing used by equals changes.
  3. Unequal objects may share a hash code. That is a hash collision: legal, but each one costs time, and in a concurrent map, contention.

Together with the equals rules this is the equals and hashCode contract. The short version: override both or neither, compute both from the same fields, and never change those fields while the object is a key.

How a hash map uses them

Here is what HashMap does on get(key) and put(key, value):

  1. Call key.hashCode() and mix the high bits into the low bits: h ^ (h >>> 16).
  2. Pick a bucket: (n - 1) & hash, where n, the number of buckets, is always a power of two (16 by default, doubling whenever the map is 75 percent full).
  3. Walk the entries in that bucket. For each, compare the stored hash first, then ==, then equals.
  4. If a bucket grows past 8 entries and the table has at least 64 buckets, turn that bucket into a balanced tree. For colliding hashes, compatible Comparable keys whose ordering distinguishes unequal keys allow O(log n) lookup in the bin. If comparisons cannot distinguish keys, lookup can still approach O(n). Below 64 buckets the map grows its table instead.

Note step 3: the hash is stored with the entry when it is inserted. A key whose hash changes later no longer matches its own entry.

A ConcurrentHashMap finds keys in exactly the same way, and adds concurrency on top:

OperationWhat ConcurrentHashMap does
getTakes no lock at all. The table and the entries' values are read with volatile semantics, so a reader sees completed writes.
put into an empty binInstalls the new entry with a single compare-and-swap, no lock.
put into a non-empty binLocks just that bin (synchronized on its first entry), so writers to different bins run in parallel.
ResizeMoves bins to a table twice the size; updating threads can help transfer bins, while readers follow forwarding entries.
computeIfAbsent, compute, mergeOffer atomic updates for one key. Callbacks that execute run under bin coordination, sometimes using a reservation node; an absent-key merge can install its value by CAS without calling the function.

It also clears the sign bit of every spread hash, because negative hash values are reserved for special entries: a forwarding marker during a resize, the root of a tree bin, and a placeholder used while computeIfAbsent runs. The consequence for you: your hashCode decides which bin, and therefore which lock, every operation on that key uses.

Writing equals and hashCode

For a value class, compare exactly the fields that define the value, and hash the same fields:

Objects.hash(a, b, c) is convenient but allocates an array and boxes primitives on every call, which matters on a hot path. Simpler still, a record generates both methods from its components, correctly and consistently. Making the class final sidesteps the symmetry problems that appear when subclasses add fields.

Forget hashCode, lose your entries

Override equals alone and two equal keys almost always get different identity hash codes. They usually land in different buckets, and even when they share one, the stored hashes differ, so equals is never called:

In a concurrent program this looks like a cache that never hits, a deduplication set that lets duplicates through, or a computeIfAbsent single-flight table that loads the same key over and over.

Mutable keys: the object moves, the map does not

The opposite mistake: equals and hashCode are correct, but they read fields that change. Change one after insertion, and the entry stays filed under the old hash. This is a mutable key, and it breaks every hash map, concurrent or not:

Both lookups miss. get(key) hashes "ravi" and searches the wrong bucket, or the right bucket with the wrong stored hash. get(new Cart("asha")) reaches the right bucket, but equals now compares "asha" with "ravi". With the key left in this state, ordinary lookup cannot find the entry, although iteration still exposes it and it still retains memory. Restoring the old equality state could make it reachable again, but mutating live keys is not a safe repair strategy.

With threads it gets worse, because the key does not even have to be changed by the code that uses the map:

The rules for keys follow directly:

  • Use immutable keys: String, Integer, Long, UUID, enums, and records whose components are immutable.
  • If a key must be built from mutable data, copy the relevant values into an immutable key (a record) at insertion time.
  • If what you really mean is "this particular object", use IdentityHashMap (single-threaded), or give the object an immutable id and key on that.

Hash quality matters more under concurrency

In a single-threaded HashMap, a poor hash function costs time. In a concurrent structure it also costs parallelism:

  • Collisions are contention. If every key hashes to the same value, every write to a ConcurrentHashMap takes the same bin lock, and it degrades to one lock around a tree. Tree bins work best when keys are Comparable; otherwise lookups among colliding keys can approach linear time.
  • hashCode runs on every operation. A key that hashes a 10,000-element list on every get puts that cost on every thread. String caches its hash after the first call; your key class can precompute its hash in the constructor if fields are final.
  • Lock striping uses the hash too. A striped map picks locks[stripe(key)], and the obvious formula has a trap:

"polygenelubricants".hashCode() is exactly Integer.MIN_VALUE, whose absolute value does not fit in an int, so Math.abs returns it unchanged and the index is -8: an ArrayIndexOutOfBoundsException. This is one of the possible 32-bit hash values, not a promise about how often real keys produce it. Use Math.floorMod(h, n), or (h & 0x7fffffff) % n, or a positive power-of-two stripe count with h & (n - 1) as HashMap does. You will build a striped map in the striped hash map problem and meet the idea in lock granularity and striping.

Sorted maps identify keys by ordering

TreeMap, TreeSet, ConcurrentSkipListMap and ConcurrentSkipListSet use ordering to locate keys and determine key duplicates: two keys are "the same" when compareTo (or your Comparator) returns 0. Other operations, such as a collection's own hashCode, can still invoke element hash codes. If ordering disagrees with equals, hash-based and sorted collections disagree with each other. The classic example is in the JDK itself:

When you write a Comparator for a sorted concurrent map, a priority queue or a scheduler, make it consistent with equals, typically by breaking ties on a unique field such as an id or a sequence number. Otherwise two different tasks that compare equal silently collapse into one entry in a sorted map or set, and in a PriorityQueue (which keeps both) they come out in an unspecified order, not first in, first out.

Worked example: a key for a per-user, per-endpoint rate limiter

A rate limiter keeps one counter per (user, endpoint) pair in a ConcurrentHashMap, updated by every request thread. What should the key be?

  • The request object itself? It is mutable, has identity equality, and is different for every request. Every request would get its own counter, so nothing is limited.
  • A string user + ":" + endpoint? It works, but it allocates a new string per request, and if user names may contain ":" two different pairs can produce the same string ("a:b" with "c", and "a" with "b:c"). That is not a hash collision, it is an equals collision: two keys that should differ are equal.
  • A record RateKey(String user, String endpoint). Immutable, correct equals and hashCode from both components, no ambiguity.

Each thread creates 10,000 new RateKey objects, yet there are exactly four entries, because equal records hash and compare equal. computeIfAbsent is atomic in ConcurrentHashMap, so two threads that miss on the same key at the same moment still create only one LongAdder. Immutable key, atomic map operation, contention-friendly counter: that is the standard shape.

Common mistakes

  • Overriding equals without hashCode. Equal keys land in different buckets; lookups miss and duplicates pile up.
  • Hashing fields that change. Mutating a key after insertion strands its entry, in every kind of hash map. Keys must be immutable, at least in the fields equals and hashCode use.
  • Using arrays as keys. Arrays use identity equals, so new int[] {1, 2} never finds an entry stored with another array of the same contents. Records with array components have the same problem. Use a List or a record of immutable values.
  • Math.abs(hashCode()) % n for a stripe or shard index. It is negative for Integer.MIN_VALUE. Use Math.floorMod.
  • An expensive hashCode on a hot concurrent path. Every get and put calls it. Precompute it for immutable keys.
  • A Comparator that returns 0 for different items in a TreeMap or ConcurrentSkipListMap (one of them disappears) or a PriorityQueue (equal items come out in no particular order). Break ties on a unique field.

In the interview

This comes up three ways: as a Java screen question ("what is the contract between equals and hashCode?"), inside a concurrent map question ("how does ConcurrentHashMap find and lock a key?"), and as a bug in a design ("what if two threads share this key object?").

Equal objects must have equal hash codes, and neither may change while the object is a key. The map files an entry under its hash at insertion; if the key changes later, lookups go to the wrong bucket and the entry is stranded. That breaks ConcurrentHashMap too: its locks protect the map's structure, not my key objects. So I use immutable keys, usually records.
ConcurrentHashMap spreads the hash, picks a bin, reads without locking, inserts into an empty bin with a CAS, and otherwise locks only that bin. So the key's hash decides which lock a write contends on, and a bad hash turns it into one hot lock.

Follow ups to expect: "What if two unequal keys have the same hash?" (allowed; they share a bin and are told apart by equals), "Why does HashMap treeify?" (bounded cost with bad hashes or deliberate collision attacks), "How would you pick a lock stripe?" (Math.floorMod, or a power-of-two mask), and "Why does ConcurrentHashMap reject null?" (from the previous lesson: null must mean absent).

Senior depth

  • Why ConcurrentHashMap reads are lock-free. Writers fully build an entry before publishing it with a volatile write or a CAS into the table, and values are volatile, so a reader that finds an entry sees it complete. A reader may see the map slightly before or after a concurrent write, which is why size() and iteration are only weakly consistent; mappingCount() returns a long estimate.
  • Java 7 versus Java 8. Before Java 8, ConcurrentHashMap was split into a fixed number of segments (16 by default), each a lock. Since Java 8 it locks individual bins and uses CAS for empty ones, so the useful parallelism grows with the table. Interviewers still ask about "segments", and naming the change is a good senior signal.
  • Treeification is a defense with limits. Java 8 introduced red-black tree bins when collisions and table size cross the thresholds above. They use hash and, where compatible, compareTo to guide searches. This helps against colliding string keys, but does not guarantee logarithmic lookup for arbitrary key classes: equal hashes with no useful comparison can still require searching both subtrees.
  • Single-flight relies on key equality. computeIfAbsent(key, k -> loadOnce(k)) deduplicates concurrent loads only if all callers build equal keys. A key with identity equality silently turns single-flight into "load per caller". Note that the loader runs under the bin lock, so it must be quick and must not update the same map (the documentation forbids it, and it can throw IllegalStateException: Recursive update or deadlock); slow loads belong in a future stored in the map, not in the function itself.

Key takeaways

  • == is identity; equals is value. Value classes must override both equals and hashCode, from the same fields.
  • Equal objects must have equal hash codes; unequal objects may collide.
  • A hash map files entries under the hash at insertion: a key that changes later is lost, in HashMap and ConcurrentHashMap alike.
  • Use immutable keys, ideally records with immutable components.
  • In concurrent structures the hash picks the lock: collisions are contention, and Math.abs(h) % n can go negative.
  • Sorted maps use compareTo; keep comparators consistent with equals.

Key overrides equals to compare an id string but does not override hashCode. After set.add(new Key("a")) on a HashSet, is set.contains(new Key("a")) guaranteed to return true?
Why. Hash collections compare stored hashes before checking equality. Without an override, two logically equal keys may have different identity hashes, so the lookup usually misses. Identity hashes can collide, so success is possible by accident; it is not guaranteed. Nothing checks the broken contract at run time.
A ConcurrentHashMap<Cart, Integer> holds cart -> 3, put there with owner set to "asha", and Cart hashes its owner field. A thread then sets cart.owner = "ravi" and, on the next line, calls map.get(cart). What does that call return?
Why. ConcurrentHashMap keeps a reference to the key and the hash computed at insertion; it does not snapshot the key's fields or guard mutations to them. These owner strings produce different spread hashes, so the lookup no longer matches the entry, which still counts in size(). Equality and hash fields must stay stable while a key is stored.
Which of these does the equals and hashCode contract allow? Select all that apply.Select all that apply
Why. Collisions are allowed; they only cost performance. The hash must stay the same only while the fields used by equals stay the same, which is exactly why changing those fields while the object is a key strands it. Equal objects with different hashes and equals(null) being true both break the contract.
A striped lock table picks locks[Math.abs(key.hashCode()) % locks.length] with 10 locks. What can go wrong?
Why. The absolute value of Integer.MIN_VALUE does not fit in an int, so Math.abs returns it unchanged; with 10 stripes the remainder is -8. Use Math.floorMod(h, n) or mask off the sign bit. Sharing a lock between keys is fine, just extra contention, and the stripe is stable as long as the key is immutable.
What are the sizes of hashed and sorted?
Why. BigDecimal.equals compares value and scale, so 1.0 and 1.00 are different for a HashSet. TreeSet uses compareTo for duplicate detection, which compares only the numeric value and returns 0, so the second element counts as a duplicate.
What does this print?
Why. Arrays inherit equals and hashCode from Object, so two arrays with the same contents are different keys. Use List.of(1, 2) or a record of the values as the key. A record with an array component has the same problem, because records compare reference components with their own equals.
In Java 21, what does ConcurrentHashMap.put do when the key's bin is empty?
Why. An empty bin needs only one atomic step, so a CAS on the table slot is enough. Non-empty bins are locked individually by synchronizing on their first entry. Segments are how the Java 7 version worked, and threads that meet a resize help move bins rather than simply waiting.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
State the equals and hashCode contract, and explain what goes wrong in a ConcurrentHashMap if you break each half of it.
Model answer

equals must be reflexive, symmetric, transitive, consistent, and false for null. hashCode must return equal values for equal objects, and must not change while the fields used by equals do not change; unequal objects may share a hash. Override both from the same fields, or neither.

If equal objects get different hashes, typically because I overrode equals and forgot hashCode, the map files them in different bins and never compares them: get with an equal key misses, putIfAbsent and computeIfAbsent create duplicates, and a single-flight cache loads the same key again and again. If the hash changes after insertion because a key field was mutated, the entry is stranded under its old hash: lookups miss, size() still counts it, and it leaks. ConcurrentHashMap gives no protection in either case, because its bin locks and CASes protect the map's structure, not the fields inside my key objects. So keys should be immutable, and records are the easiest way to get correct, consistent equals and hashCode.

Debug
A search service caches results in a ConcurrentHashMap<Query, Result>. Query has fields text and page, with correct equals and hashCode over both. To fetch the next page, the request handler does query.page += 1 and calls the cache again with the same object. Over a day the cache's hit rate collapses and memory grows. Explain, and fix it.
Model answer

The handler mutates a key that is already in the map. The entry for page 1 was filed under the hash of (text, 1); after page += 1, the same object hashes as (text, 2). If the spread hash changes, lookup with that object misses. A fresh Query(text, 1) also fails because the stored key now says page 2. Stranded entries keep retaining memory until removed or the map is discarded, so memory grows and the hit rate falls. If several threads share the same Query object, they can also change it during a lookup.

Fix: make Query immutable, ideally record Query(String text, int page) {}, and create a new key for the next page with new Query(q.text(), q.page() + 1). Then every key's hash is fixed for its life, equal queries from any thread find the same entry, and nothing is stranded. If the cache must be bounded anyway, add eviction, but that treats the symptom; the bug is the mutable key.

Write code
Write a key class for a ConcurrentHashMap that counts events per (tenant id, user id, event type), where the type is an enum. Then write the line that atomically increments the count for one event.
Model answer

The record is immutable, so its hash can never change while it is a key, and its generated equals and hashCode use all three components consistently. A long, a String and an enum are all immutable themselves. computeIfAbsent is atomic in ConcurrentHashMap, so concurrent first events for the same key create exactly one LongAdder, and LongAdder keeps hot counters from contending on one memory location.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Our ConcurrentHashMap cache keeps growing, but looking up a key we inserted returns null. The request handler increments the page number inside the key. Walk me through your diagnosis."
What a strong answer covers
  • Mutating equality or hash fields while a key is stored can strand its entry
  • The map retains the insertion hash and a reference to the original key object
  • A changed hash makes lookup miss; a fresh key for the old page also fails equality against the mutated key
  • ConcurrentHashMap protects its structure, not mutations inside keys
  • Use an immutable key and a new instance for the next page; rebuild or clear affected cache entries safely
  • Keep equality state stable and test equivalent independent keys, not only the original instance
How a senior would say it
I would suspect a mutable key before changing the map's locking. The entry stores the hash computed at insertion and a reference to the key object. It does not save a copy of the key's page number. Suppose we insert a query for page one and then change that same object to page two. If its hash changes, a lookup uses the new hash, while the entry still has the old one. The stored hash check rejects it, even if both hashes happen to choose the same bucket. A fresh key for page one also misses because the stored object now compares as page two. The entry still counts toward size and retains its value. ConcurrentHashMap cannot prevent this: its synchronization protects the map's structure, not arbitrary writes inside keys. I would make the key an immutable record of the query text and page, and create a new key for each page. That prevents new damage; an already affected cache may need a controlled rebuild or invalidation. I would test lookups with separately constructed equal keys and verify that callers cannot change equality fields after insertion. Eviction can limit memory, but it does not fix the key contract.

Likely follow up: Would making the page field volatile or synchronizing its setter repair the existing map entry?

Out loudabout 75 s
"Explain why overriding equals without hashCode breaks a deduplication set, but returning the same hash for every key can still be correct."
What a strong answer covers
  • Equal objects must have equal hashes; unequal objects may share a hash
  • Hash collections select candidates using hashes before comparing equality
  • Inherited identity hashes can differ for two logically equal objects, causing missed matches
  • A constant hash satisfies the equality implication but forces collisions
  • Collisions hurt lookup cost and can concentrate concurrent writers on one bin lock
  • Use stable immutable equality fields and a well-distributed hash derived from them
How a senior would say it
The contract goes in one direction: equal objects must have equal hashes, but equal hashes do not prove equality. A hash collection first uses the hash to find candidates and then uses equality to distinguish them. If I override equals to compare a user identifier but inherit Object's identity hash, two separate objects for the same user can have different hashes. The lookup can reject the stored entry before equals is called, so deduplication fails. An accidental identity-hash collision might hide the mistake in one case, but it cannot make the implementation correct. A constant hash has the opposite problem. It obeys the contract because every equal pair certainly shares a hash. Distinct keys can still be distinguished by equals, but they all collide. That increases lookup work and, in a concurrent hash map, concentrates writes on the same bin lock. I would use immutable fields that represent the logical identity, implement equals consistently, and derive a reasonably distributed hash from those fields. A record with immutable components is usually a straightforward way to do that.

Likely follow up: Does converting a collision bin to a tree guarantee logarithmic lookup for every possible key class?

Out loudabout 75 s
"Design a key and lock-stripe selection for a per-tenant, per-endpoint counter. What would you reject in a code review?"
What a strong answer covers
  • Use an immutable composite key whose equality includes tenant and endpoint
  • Avoid ambiguous string concatenation and mutable request objects as keys
  • Map a stable hash to a positive stripe count with Math.floorMod or a valid power-of-two mask
  • Math.abs(Integer.MIN_VALUE) stays negative and can produce an invalid index
  • All operations on the same logical key must use the same stripe; stripe collisions cost concurrency, not correctness
  • A stripe does not make writes to one shared ordinary HashMap safe under different locks
How a senior would say it
I would use an immutable record containing the tenant identifier and endpoint. Both fields define equality, so two independent requests for that pair select the same counter and the same stripe. I would reject using the mutable request object, and I would avoid joining strings with a separator unless the encoding is unambiguous. For a fixed positive number of stripes, I would select the index with Math.floorMod of the key's hash and the stripe count. Taking the absolute value is a trap: the absolute value of the minimum integer is still negative, so the remainder can be a negative array index. Every read and update that belongs to this locking policy must use the same stripe rule. Two different keys sharing a stripe is safe; it only reduces parallelism. I would also inspect the storage behind the locks. Different stripes do not make concurrent structural writes to one ordinary HashMap safe. I would use a separate map per stripe, or a concurrent map with the extra locks protecting a clearly defined compound operation.

Likely follow up: How would you acquire locks for an operation involving two keys that might map to the same stripe?
