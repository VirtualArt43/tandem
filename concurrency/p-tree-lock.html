Hierarchical tree lock

Thread-safe structureshard55 minMicrosoftAdobe

Logical locks on a tree must exclude ancestors and descendants without making unrelated branches wait for one global mutex.

The task

The immutable N-ary tree is given by parent indices: node zero has parent -1 and every other node has a parent with a smaller index. Users are nonnegative integers. A logical node lock is owned by a user until explicitly unlocked; it is separate from the internal mutexes that protect operations.

  • lock succeeds only if the target, every ancestor and every descendant are unlocked. Otherwise return false.
  • unlock succeeds only for the target's current user. Lock ownership is by user ID, not the calling OS thread.
  • upgrade succeeds only when the target and its ancestors are unlocked, at least one descendant is locked, and every locked descendant belongs to the requesting user. It atomically clears those descendant locks and locks the target. Failure changes nothing.
  • Use fine-grained locking. Operations in disjoint subtrees must be able to overlap. The nonreentrant, nonthrowing entered(node) hook runs while that node's operation is protected; production passes a no-op.
  • snapshot returns a coherent owner array with -1 for unlocked nodes. It is a diagnostic allowed to exclude all mutations briefly.

Example: user 1 owns both children of node 1. Upgrading node 1 replaces both locks with one parent lock. If any locked descendant belongs to user 2, the upgrade must fail without clearing it.

What the tests check

  • Ancestor/descendant exclusion, owner validation and atomic successful upgrade.
  • Upgrade with a foreign descendant fails without changing any owner.
  • Gated sibling-subtree operations overlap under shared ancestor gates.
  • Eight seeded callers lock, upgrade, snapshot and unlock without an invariant violation or deadlock.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How does this map to the Adobe and Microsoft reports?
Adobe asks tree lock/unlock with parent pointers; Microsoft asks locking strings in a trie and then making it multithreaded. Trie prefixes form the same ancestor relationship. Explain both logical ownership and physical synchronization.
Why can sibling operations share ancestor locks?
They only inspect ancestor ownership and cannot change it. A write to that ancestor takes its exclusive gate, which waits for all such readers. Siblings take different exclusive target gates.
Is this a full database intention-lock manager?
No. It uses shared ancestor gates as an intent-like exclusion protocol. Database IS, IX and SIX modes have a richer compatibility matrix and transaction-lifetime semantics.
Can you avoid scanning descendants?
Maintain locked-descendant metadata, but updating every ancestor adds shared hotspots and a larger atomicity problem. Versioned indexes or more elaborate intention locking trade complexity for speed.
What changes if the tree can be reparented?
The path itself becomes shared mutable state. You need structural locks or immutable versions so an operation cannot validate one ancestor path and commit under another.
Can upgrade drop locks and reacquire the ancestor?
No. Another user can enter the gap. Keep the target gate exclusive through validation, descendant clearing and target assignment.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The protection rule

Every operation acquires shared gates on its ancestors, followed by the target's exclusive gate. To mutate any descendant of a node, an operation must hold that node's shared gate. Therefore an exclusive target gate makes its entire subtree stable while validation and upgrade run.

Ancestor owner fields are read while their shared gates are held. Descendant owner fields are safe to scan under the target's exclusive gate because every descendant writer needs a conflicting shared gate there. All paths acquire root to leaf, so two operations cannot form an opposite-order cycle. Independent siblings share their common ancestors and mutate different target metadata.

Atomic upgrade

Collect the target's descendants, verify ownership for all locked nodes, and require at least one. Only after every check succeeds clear descendant owners and set the target owner. The gate remains exclusive for the complete transition; readers cannot observe the half-cleared state. Snapshot takes the root gate exclusively and copies the owners.

The broken transition

The broken implementation checks that descendants are locked but does not check their users. User 1 owns one branch and user 2 owns another. User 1 upgrades the root and silently deletes user 2's lock. There is no data race, but the ownership contract is violated. The foreign-owner test compares the entire snapshot before and after failure.

Costs and limits

An operation acquires O(H) gates for height H and scans O(S) descendants for lock or upgrade on a subtree of size S. Space is O(N) for tree metadata and gates, plus temporary path and traversal storage. Unlock needs only its path. The locks do not promise starvation freedom on every platform; fair admission would be a separate requirement.

How to say it in the interview

I will read-lock the ancestor path and write-lock the target. That makes the target subtree stable without serializing siblings. Upgrade first validates every locked descendant's owner, then clears them and assigns the target while still holding the exclusive gate.
