A Node.js handler calls a synchronous function that takes 80 ms to parse a large JSON body. What happens to the other 5,000 open connections served by that same JavaScript isolate during those 80 ms?
Why. JavaScript callbacks within this isolate share its event loop thread. Other isolates and the kernel may still make progress. CPU-heavy or blocking work on it stalls every connection. libuv's pool handles certain I/O operations, not your JavaScript; CPU work has to be moved explicitly, for example to worker_threads.

A Netty handler and all other users of its connection state run only on that channel's assigned event loop. Why is no lock needed?
Why. All accesses are serialized by one owner, so this is thread confinement, not a global Netty lock or automatic volatile semantics. Handlers can be stateful. If a worker or a shared handler accesses the same state concurrently, the premise fails and you need an explicit ownership or synchronization plan.

A service must hold 200,000 mostly idle WebSocket connections on one machine. Which model fits worst?
Why. A platform thread per connection requires 200,000 stacks and OS thread records. Sleeping threads do not burn CPU, but the memory and thread limits make this the weakest fit. Event loops, virtual threads and goroutines can wait without one OS thread each; all still require connection-memory and descriptor budgets.

What is the difference between a reactor and a proactor?
Why. Readiness (epoll, kqueue, a Java Selector) versus completion (Windows IOCP, io_uring). A successful read completion includes a byte count for data placed in your buffer; it can also report EOF or an error. Neither pattern dictates threads versus processes or reads versus writes, and they describe different notification contracts.
From: Server threading models
A team moves a thread-per-request service to Java 21 virtual threads and removes its 200-thread pool limit. Under a burst, the service fails anyway. What is the most likely cause?
Why. The old pool was also an accidental concurrency limit. Virtual threads make waiting cheap, but the downstream is no bigger. Use per-dependency limits and bound total admitted work. Virtual threads support network I/O and are not capped at the core count; their benefit depends on the workload, not universal speed.

A single FIFO event loop has tasks A and B already queued before it starts. A submits work to a worker and returns without waiting. B prints B. The worker posts a callback C to the same loop that prints C. Assuming all tasks complete successfully, what can print?
Why. B is already queued before A submits the worker. Even if the worker immediately posts C, C goes behind B. Posting is non-blocking, so there is no deadlock. This orders callbacks in this setup; two independently offloaded requests can still complete in either order.

A server watches 20,000 mostly idle connections. At any moment about 50 have data. What structural advantage does epoll have here?
Why. The important advantage is avoiding a fresh scan and submission of the whole interest list each wait, not a universal performance guarantee. epoll is still a readiness API: you do the reads yourself. A common FD_SETSIZE of 1,024 limits descriptor numbers usable with select, not with poll. Epoll maintains readiness metadata, not a dedicated thread per descriptor.
From: Blocking, non-blocking and multiplexed I/O
An edge-triggered epoll loop receives a readable event with 2,000 bytes already buffered. Its one read returns 512 bytes, then it waits again. The peer sends no more data and stays connected. What failure is possible?
Why. Events are not a count of reads or messages. Unread data alone does not require another edge, so stopping early can strand 2,000 minus 512 = 1,488 bytes. The kernel neither discards them nor reports an epoll error because they remain. Drain until would-block, or retain the connection on an application ready queue.

A level-triggered event loop registers every socket for both readable and writable, permanently. Traffic is light, but one core sits at 100 percent. Why?
Why. A healthy connected socket with spare send-buffer capacity is writable, even with no application output queued. Repeated writable notifications explain the spin without a flood of reads or retransmissions. Level-triggered loops can sleep when no watched condition holds; register write interest only while output is queued.

What does a proactor (completion-based) API give you that a readiness API does not?
Why. Readiness says "attempt the operation now"; completion says "your read finished, here is how many bytes". The OS or library performs the submitted operation. Completion APIs can represent disk reads, but still need execution resources and TCP flow control. A completion can be partial; it does not identify application message boundaries.

Why does Node.js, which is built on an event loop, still run a thread pool?
Why. Regular files are always reported "ready", and a read that misses the page cache blocks anyway. libuv can do that work on workers and dispatch completion to the event loop. This pool does not run user JavaScript callbacks or exist primarily for accepting sockets. Availability of epoll is separate from the need to offload file work; dns.resolve is also different from dns.lookup.

Java onlyA Java NIO loop handles each key from selector.selectedKeys() but never calls iterator.remove(). What goes wrong?
Why. Selection adds or updates ready live keys without clearing previously handled live keys. Remove each as you process it. Cancelled keys are a separate case: selection removes them during deregistration. Omitting removal does not itself throw, change blocking mode or duplicate bytes already consumed; it can repeat handler work. The action-based overload avoids manual iteration, but its contract does not promise an empty selected set afterward.

A stable service admits 3,000 requests per second and each takes 80 ms on average from arrival to response. How many requests are in the service at any moment, on average?
Why. Little's law: L = λ × W = 3,000 × 0.08 = 240. The 37.5 option divides 3,000 by 80 instead of multiplying by seconds; 2,400 and 24,000 use incorrect unit conversion. L is an average occupancy, not a maximum.

Each request fans out to 50 shards in parallel and waits for all of them. Each shard is slow on 1 percent of calls, independently. Ignoring orchestration overhead and calling the user request slow if any shard is slow, roughly what fraction are slow?
Why. 1 - 0.99^50 is about 0.395. The request is as slow as its slowest call, so small per-call tails multiply. Adding 50 individual 1 percent probabilities gives only a 50 percent upper bound because slow events can overlap. One percent ignores fan-out; 99 percent is one shard's success probability, not the chance of any slow shard. At fan-out 100 the slow-request probability would be about 63 percent.

Across two stable windows, admitted throughput is 2,000 requests per second and mean in-flight count rises from 200 to 1,000. CPU remains mostly idle. What does Little's law establish?
Why. W = L / λ: 200 / 2,000 = 100 ms before, 1,000 / 2,000 = 500 ms after. Idle CPU suggests waiting, which could be a lock, queue or dependency. The law alone proves neither a cause nor a memory leak. Stable windows support the calculation; applying it to a transient jump without accounting for unfinished requests would be unjustified.

A FIFO work queue holds 3,000 items and workers continue draining it at 1,500 items per second, with no overtaking or cancellation. Roughly how long will an item that joins now wait before a worker picks it up?
Why. Waiting time is the queue length divided by the drain rate: 3,000 / 1,500 = 2 s. This is a FIFO backlog estimate with a constant drain rate. Little's law instead relates long-run average queue length and waiting time. Requests arrive at 1,200 per second and the service can finish 1,000 per second. The FIFO queue starts empty and rates stay constant. Ignoring rejection and abandonment, how long will a request that arrives after 60 seconds of this wait?
Why. The backlog grows by 1,200 - 1,000 = 200 per second, so after 60 s about 12,000 requests are waiting. Drained at 1,000 per second, the newest waits about 12 s. A sustained rate gap makes waiting grow without limit; no buffer fixes it.

A client is over its per-minute quota. A different server is simply overloaded for everyone. Which status codes fit?

From: Backpressure, bounded queues and load shedding
A slow reader stops calling read on its socket, while the writer on another machine keeps writing. Assuming a live TCP connection with no socket timeout, errors or signals, and plain blocking sockets, what eventually happens to the writer?
Why. TCP flow control: the receiver advertises how much buffer space it has; at zero ordinary data transmission pauses, its send buffer fills, and blocking write waits for space. POSIX non-blocking writes instead report EAGAIN or EWOULDBLOCK if they cannot transfer any bytes. Partial writes are also possible; a full buffer does not itself reset the connection or silently drop accepted data. That is backpressure with no application code.

A Kafka consumer group has a backlog of 90,000 records, treating lag as record count with no offset gaps. Producers add 3,000 messages per second and the group consumes 3,600 per second. How long until the lag is gone?

Ten instances each allow up to 40 concurrent queries to a database that handles 400 well. Autoscaling adds 10 more instances during a traffic spike. What is the risk?
Why. Per-instance limits add up. The dependency feels the per-instance limit times the instance count, so scaling the fleet raises the load it can receive. Size per-instance limits from the dependency's capacity and fleet size, or coordinate admission to maintain the aggregate budget. Adaptation alone does not guarantee a hard fleet-wide bound.
