Parallel file copy with pread and pwrite

Concurrent systemshard40 minRubrik system coding and code design rounds (copy with pread and pwrite, then in parallel)Rubrik

Rubrik asks you to implement cp with only open, pread, pwrite and close, then to make it parallel. It looks like plumbing, but it tests whether you know why positional I/O makes threads safe on one file, that a read can return fewer bytes than you asked for, and how a failure in one thread reaches the caller.

The task

Copy one open file into another using several threads:

  • Split the source into chunks of chunkSize bytes (the last one may be shorter) and copy them with at most threads threads in all: start them once per copy and let each one copy many chunks, rather than one thread per chunk.
  • Use only positional I/O: src.read(buffer, position) and dst.write(buffer, position) on a FileChannel in Java, pread and pwrite in C++. These read or write at an offset you pass in and never move a shared file position.
  • Keep the I/O parallel: several reads, and several writes, must be able to run at the same time. Positional I/O on different chunks needs no lock.
  • A positional read or write may transfer fewer bytes than asked. Keep going until the whole chunk is done. In C++, a call that returns -1 with errno set to EINTR was interrupted by a signal before it moved any data: call it again, it is not an I/O error.
  • Keep memory bounded: about one chunk buffer per thread, never the whole file, which may be far larger than memory.
  • The destination may already hold older, longer data. When copy returns, the destination must be exactly the source: same length, same bytes.
  • If any read or write fails, copy throws (an IOException in Java, any exception such as std::system_error in C++), but only after every thread it started has finished: no read or write of this copy may still be running, or start, once copy has thrown. After a failure, start no new chunks. Never let an exception escape a std::thread.
  • In Java, if the thread that called copy is interrupted, stop starting new chunks, wait for your threads, then throw InterruptedException.
  • Do not close the channels or descriptors: the caller owns them.
  • One ParallelCopier may be used for many copies, one after another, including after a copy that failed.

Rules, as in the real interview: no library thread pools; start your own threads. The files live in the current working folder. In Java the channels you get only allow the positional read and write, plus size, truncate and force; anything that moves a file position throws. In C++ the harness sits in front of pread and pwrite to count and slow them, so use those two calls.

Worked example: why not read and write?

Plain read(fd, buf, n) uses the file offset stored in the open file description, which every thread sharing that descriptor shares. Thread A seeks to 0, thread B seeks to 4096, thread A reads: it now reads at 4096. You could put a lock around every seek and read pair, but then the threads take turns and you lose the parallelism. pread(fd, buf, n, offset) carries its own offset, so the kernel never consults the shared one, and four threads can read four chunks of one descriptor at the same time.

What the tests check

  • Byte identical copies for sizes 0, 1, one less than a chunk, exactly a chunk, one more, five chunks, five chunks and 3 bytes, and 300001 bytes, each copied over an older, longer destination, all by one copier one after another.
  • A copy into a brand new, empty destination. After every copy, both channels (descriptors in C++) must still be open.
  • Short transfers: every read and write moves at most 997 bytes, and the copy must still be exact.
  • In C++, every third pread or pwrite fails with EINTR before moving any data, and the copy must still be exact.
  • Parallelism: with 4 threads and every call slowed to 3 ms, at least 2 reads must run at once and at least 2 writes must run at once, never more than 4 calls, done by between 2 and 4 threads in all (in C++ a new thread counts as new even if it reuses an old thread id).
  • Memory: copying 1 MiB with 4 threads and 4096 byte chunks, no buffer passed to a read or write may be backed by more than 64 KiB in Java, and no single new during the copy may ask for more than 64 KiB in C++.
  • A read that fails in chunk 4 of 128 makes copy throw. No read or write may still be running, or start, after copy throws (in Java every worker thread must also have ended), and fewer than 64 reads may start after the failure.
  • A write that fails in the first chunk, while the other threads are still busy, makes copy throw the same way, and so does a copy where every read fails, with all 4 threads failing at the same moment.
  • In Java, interrupting the thread that called copy makes it throw InterruptedException (an InterruptedIOException or ClosedByInterruptException is accepted too), with no read or write still running and fewer than 64 reads started after the interrupt.
  • The copier that saw those three failures then makes an exact copy.
  • In C++, ThreadSanitizer must stay quiet. With several threads failing at once it catches, for example, an error code or a std::optional that they all write without a lock.

Taught in: Parallel copies, chunked reads and caches over slow storage

Open them one at a time. Each one gives away a little more.

Start with the single threaded version: find the size, set the destination's length, then for each chunk read it fully into a buffer and write it fully at the same offset. "Fully" means a loop: keep calling until the chunk is done, because one call may move fewer bytes than you asked for.
To parallelize, give the threads a shared atomic chunk counter. Each thread repeatedly claims the next chunk number with one atomic increment, copies that chunk, and stops when the number passes the last chunk. No lock is needed: positional I/O touches no shared file position, and different chunks touch different bytes.
Truncate the destination to the source size first (truncate in Java, ftruncate in C++), so a longer old file loses its tail. For errors, let each thread catch its own exception, record the first one in a shared place guarded by a lock or a compare and set, and set a stop flag the others check before each new chunk; the caller joins every thread and then throws what was recorded. In Java, if the caller's join is interrupted, set the same flag, join again, then rethrow. Keep the counter, the flag and the error slot local to copy, so the next copy starts clean.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How many threads should a copy use?
It depends on what is slow. A single local SSD can serve several requests at once, so a few threads help; a spinning disk or a USB stick may get slower with many, because the head seeks back and forth. Across a network the latency per request is high and many requests in flight help a lot. Measure, and make the thread count and the chunk size parameters.
Copying from a slow floppy to a fast SSD: what changes?
The reads are the bottleneck, and parallel reads may not help a device that serves one request at a time. Read in large sequential chunks, and decouple reading from writing with a bounded queue of buffers that you build yourself (Rubrik has forbidden thread pool classes here): one reader keeps the slow device busy all the time, and a writer merges what it takes, in file order, into a few large writes to the SSD. Rubrik candidates have been asked exactly this follow up.
How would you retry a failed chunk instead of failing the whole copy?
Retry only errors that can pass (a timeout or EIO on a network file system; EINTR is simply called again), a bounded number of times with backoff, and only that chunk. Rewriting a chunk is safe because a positional write of the same bytes at the same offset is idempotent. Keep a state per chunk (pending, done, failed) so the copy can also resume after a crash, and fail the copy once a chunk runs out of retries. Rubrik has asked a version where file parts go out in parallel and failed parts are retried.
Would you fsync the destination?
If the copy must survive a crash, yes: call force(true) or fsync once at the end (not per chunk), and to make a new file's name durable too, fsync the directory. Copy to a temporary name and rename it into place, so a crash never leaves a half written file under the real name.
What happens if you interrupt a thread that is blocked in a Java FileChannel read?
FileChannel is an interruptible channel: interrupting a thread during I/O on it closes the channel for everyone and the other threads get ClosedChannelException. That is why the reference stops workers with a shared flag between chunks rather than with interrupt().
How would you copy a 1 TB file to another machine, like scp?
Chunk the file, send chunks over several connections in parallel, checksum each chunk, write each at its offset on the receiver with pwrite, and keep a record of which chunks are done so a broken transfer resumes instead of restarting. Rubrik asks this as a design round.
Is there something faster than reading into a buffer and writing it back?
Yes: let the kernel copy without going through user space, with copy_file_range or sendfile on Linux, transferTo in Java, or copy on write clones on file systems that support them. Interviewers usually forbid these to see the threading, but naming them shows you know the platform.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Positional I/O turns one file into many independent byte ranges. Each worker claims a chunk number from an atomic counter, reads that range fully with pread (or read(buffer, position)), and writes it fully at the same offset. Nothing is shared between workers except the counter, the stop flag and the slot for the first error, so there is no lock on the I/O path.

Invariants

  • Every chunk number from 0 to chunks minus 1 is claimed by exactly one thread, because getAndIncrement (fetch_add) hands out each value once.
  • Once a failure is recorded (or, in Java, the caller is interrupted), no thread starts copying a new chunk.
  • A chunk is written only after it has been read completely, and at the same offset it came from.
  • The destination's length is set before any chunk is written, so the final length is right even if the old file was longer.
  • copy returns or throws only after every worker has been joined.

Why each primitive

  • An atomic counter instead of a fixed split: fast threads take more chunks, so one slow chunk does not hold up a whole fixed share.
  • A buffer per thread, allocated once and reused: no sharing, no allocation per chunk.
  • A first error slot and a stop flag: the first failure is the one worth reporting, and the others stop claiming new chunks.
  • Join, then throw: the caller must not see copy finish while threads still write into its file. The Java reference does the same when its own join is interrupted: it sets the stop flag, joins again, then rethrows.
  • Locals, not fields: the counter, the flag and the error slot live inside copy, so one copier can run many copies, even after one failed.

Pitfalls

  • lseek plus read from several threads on one descriptor: the shared offset is a race, and you copy the wrong bytes.
  • Ignoring short counts: a single pread per chunk usually works on a local file and then breaks on a network or FUSE file system, or when a signal interrupts a large transfer part way. This is the broken version the tests catch.
  • In C++, treating EINTR as an I/O error, or ignoring a -1 from pwrite so a failed write passes silently.
  • A lock around the writes "so they do not collide": different chunks never overlap, and the lock turns the copy back into one writer at a time.
  • Reading the whole file into one big buffer, then writing it out in parallel: fine for a test file, fatal for 1 TB.
  • No stop flag: one chunk fails, and the other threads go on copying the rest of a huge file before copy can report it.
  • In Java, a plain for (Thread t : workers) t.join(); under throws InterruptedException: an interrupt makes copy throw while the workers keep writing into the caller's file.
  • An unguarded std::exception_ptr that two failing threads assign is a data race. ThreadSanitizer on this Mac cannot see it, because the assignment runs inside the compiled libc++, so the tests catch an unguarded error code or std::optional but not this one: guard it with a mutex anyway.
  • Not truncating: copying a short file over a long one leaves the old tail behind.
  • An exception escaping a std::thread calls std::terminate and kills the process.
  • Returning on the first error without joining the other threads.
  • One thread per chunk: a 10 GB file with 1 MB chunks would start ten thousand threads.

How to say it in the interview

pread and pwrite take the offset as an argument, so they never touch the shared file position; that is what makes several threads on one descriptor safe without a lock. I set the destination length first, then a fixed number of workers claim chunk numbers from an atomic counter and copy each chunk with a read loop and a write loop, because either call can return a short count. The first error is recorded, the others stop at the next chunk, and the caller joins everyone before rethrowing. The right thread count depends on the device, so it is a parameter, and for a slow source I would separate one sequential reader from the writers with a bounded queue.
