Testing concurrent code

Find concurrency bugs with start gates, invariants, controlled schedules, timeouts and histories, and understand what a passing test cannot prove.

Asked atDatabricks
Before this:ThreadSanitizer and other race detectorsLatches: wait until N things happen

A concurrency bug that rarely appears locally can become routine at production volume. Testing concurrent code means making dangerous schedules easier to reach, detecting their effects, and gathering evidence for a fix alongside a correctness argument.

In plain words

Imagine certifying a lift for a busy office tower. You do not test it by riding alone at noon. You pack it full, have everyone press buttons at the same moment the doors start closing, do it a hundred times in a row, and after every ride you check the rules still hold: the weight limit was never exceeded, the doors never opened between floors.

A concurrent test is the same: crowd the code, start everyone at once, repeat, and check the rules after every round. Running it politely once proves nothing.

Why ordinary tests miss these bugs

A single-threaded unit test never exercises competing accesses. Even a threaded test can miss the bug: short workers may finish before later workers start, and logging changes both timing and synchronization. A bug that disappears when you observe it is a Heisenbug.

Assume independent trials with a fixed failure probability of 1 in 10,000. Then 100 trials find it with probability 1 - (1 - 1/10,000)^100, about 1 percent; about 30,000 trials give 95 percent. Real schedules are correlated, so these are illustrative probabilities, not a reliability guarantee. Aim to raise the chance per trial of reaching the dangerous schedule and strengthen the checks that detect it.

The anatomy of a stress test

A stress test for a thread-safe class has five parts:

  1. A range of thread counts. Try two threads, roughly one per available CPU, and more runnable threads than CPUs. Oversubscription increases scheduling pressure but does not guarantee any particular interleaving.
  2. A start gate. Thread creation can outlast a short operation. Let every worker announce readiness, then open one latch: nobody starts the tested operation before release. This encourages overlap; it does not promise simultaneous execution.
  3. Short fresh trials and longer steady-state runs. Exercise empty structures, resize, reuse and sustained contention. Seed each worker's random inputs and record them. A seed reproduces those inputs, not the operating system's schedule.
  4. Invariants and histories. Check conservation and exactly-once delivery after joining. Check transient capacity bounds at mutation points under the protecting lock; a final size alone can miss a temporary overflow. Record operation calls and results when order matters.
  5. A deadline and cleanup. Bound startup and completion, collect worker failures, and capture stacks on a timeout. A timed join does not stop a worker. Use cooperative cancellation, or isolate the test in a process that the runner can terminate.

See it catch a bug that ThreadSanitizer cannot

A ticket booth must never sell more than 5 seats. The broken version checks and then acts, with two atomic steps. The test runs 300 trials of 8 threads hitting a fresh booth, each released through a start gate, and checks the invariant after each trial. It runs three ways: the broken booth, the broken booth with noise injection (a yield placed between the check and the act), and the fixed booth with the same noise.

The broken booth can report zero failures with or without noise: a passing stress test is not proof. A yield is a scheduling hint and may be ignored; it does not guarantee a larger failure count. All accesses are atomic, so ThreadSanitizer has no data race to report even if the booth oversells. The fixed booth's successful CAS is its linearization point: only a value below 5 can advance, and a failed CAS retries against the current value.

This compact demo relies on Tandem's process timeout for hangs; the checkpoint below adds explicit deadline handling. std::latch and std::jthread require C++20. In C++17 use a mutex and predicate-based condition variable for the gate, and join every std::thread before reading results or destroying captured state.

Noise injection and other ways to shake the schedule

  • Yields and short random sleeps at suspicious points: between a check and its act, between a read and its write-back, just before a signal, just after an unlock. Put them behind a test-only hook (a function that does nothing in production builds), never in shipped code.
  • Vary CPU availability. On Linux, taskset -c 0 ./tests restricts the test and its new threads to logical CPU 0, if that CPU is allowed. Interleavings then involve preemption or voluntary blocking instead of simultaneous execution. Also run across multiple cores to exercise cache coherence.
  • Run long enough for the JIT (Java). Some bugs appear only after a method is compiled, for example a read hoisted out of a loop. A test that finishes in 5 ms may only ever run interpreted code.
  • Vary the machine and build. ARM permits some memory orderings that x86 does not, so missing acquire/release synchronization can hide on one machine. Test optimized builds as well as sanitizer builds; neither hardware choice makes a C++ data race valid.

Force one bad schedule, then explain the fix

For a deterministic regression of the booth, initialize sold to 4 and put a test-only rendezvous after each of two callers has read 4, before either increments. Release both: the broken method must return two successes and end at 6. Java can use a CountDownLatch(2) reached by both callers; C++20 can use std::latch(2) with arrive_and_wait(). Bound the test externally. For a CAS fix, rendezvous only on each caller's first attempt; a retry must not wait for a caller that already finished. Assert one success and a final value of 5.

Instrumentation changes the execution. A rendezvous inside a locked critical section can deadlock the test because the second participant cannot enter. A latch can also add a happens-before edge that accidentally repairs an unsafe-publication bug. Use hooks to target logical interleavings, and use small memory-model tests without extra ordering when visibility is the property under test.

Testing that something blocks, and that it wakes up

Blocking behavior needs its own tests: an empty queue must not invent an item, and a waiting consumer must complete after an item arrives. Not returning for 100 ms is evidence, not proof of blocking: the worker might not have run. Announce entry, observe a bounded window or a diagnostic thread state, then supply the missing condition and require completion with a generous deadline. State snapshots can be missed, so a state-observation timeout alone does not establish a queue defect.

These fragments require JUnit Jupiter or GoogleTest; the C++ include uses the queue problem's reference class. The observation window is deliberately a test of non-completion, not a sleep used to order operations. For a known implementation, Java getState() and a stack trace can corroborate where the worker waits; they are diagnostic snapshots, not synchronization.

Notice where the assertions are: in the test thread. An uncaught assertion in a raw worker is not automatically reported as a JUnit test failure: the AssertionError kills only that worker, gets printed, and the test goes green. Collect results or failures from workers (an AtomicReference<Throwable>, a future whose get() you call) and assert in the test thread. GoogleTest records failures from other threads where pthreads is available, but an ASSERT_ there returns only from the worker's function, so the test thread carries on.

jcstress: let a harness search the interleavings

For small pieces (a flag, a publication, a lock-free step), Java has jcstress, OpenJDK's concurrency stress harness. You describe two or more actors and the possible outcomes; it can run the actors concurrently millions of times in many configurations and reports how often each outcome appeared.

Each @Outcome is marked ACCEPTABLE, ACCEPTABLE_INTERESTING (allowed, but worth showing) or FORBIDDEN (the test fails if it is ever seen). The report is a table of outcomes with their counts. Projects usually start from jcstress's Maven archetype and run the built jar, java -jar target/jcstress.jar.

The annotation grades outcomes against the test author's specification, not an automatic memory-model verdict. Here 1 is interesting because we are demonstrating a legal Java lost update; in a regression test for a counter promising two increments, mark 1 forbidden. Observing an outcome shows it occurred; not observing it does not prove impossibility. Use a named package, as above, in the jcstress project.

C++ has no standard equivalent. ThreadSanitizer complements invariant tests; for small algorithms, Relacy can explore schedules using its instrumented types and model of atomic operations. Any exhaustive claim is limited to that model and the configured bounds, not arbitrary C++ programs or every possible input.

Deterministic simulation

The most powerful approach turns the scheduler itself into a test input. Deterministic simulation runs the whole system (threads, network, disk, clock) inside one controlled process where every scheduling choice and every injected fault comes from a seeded random generator. If all relevant nondeterminism is controlled, the same seed, simulator version and inputs replay the schedule. A seeded random generator around ordinary OS threads is not sufficient.

FoundationDB uses deterministic cluster simulation to test faults and schedules. At smaller scale the same idea shows up as an injectable clock and an injectable executor in your classes, so a test can drive time and task order by hand. On the JVM, JetBrains' Lincheck checks a concurrent data structure against a sequential specification, either by stress or by systematically exploring interleavings.

Triage a flaky test

A flaky test is evidence to investigate: the cause can be the product, the test or the environment. Do not silently retry away the failure. Instead:

  1. Reproduce at volume. Run just that test thousands of times in a loop (JUnit's @RepeatedTest(1000), or GTEST_REPEAT=1000 for a GoogleTest binary), on a busy machine, with the seed printed.
  2. Turn up the pressure. More threads, noise at the suspicious points, ThreadSanitizer for C++, one pinned core.
  3. Suspect the test, too. Sleeps used to order steps ("sleep 100 ms so the other thread starts"), timing assertions that are too tight, static state shared between tests, assertions inside worker threads, and order dependence between tests cause many flaky failures.
  4. Capture state at failure. On timeout, print every thread's stack; on an invariant failure, print the seed and the operation history.
  5. Explain the fix, then preserve a regression. Identify the invariant and ordering that prevent the bad outcome. Force the failing schedule where feasible, then rerun stress across configurations. Even 30,000 passes provide evidence, not proof.

Worked example: what a bounded blocking queue test must check

Use the bounded blocking queue as a concrete test plan. In one scenario, 4 producers and 4 consumers share a queue of capacity 4. Each producer enqueues items that encode its id and a sequence number (producer 2's 17th item is the pair (2, 17)). Each consumer owns its result list. With bounded completion and safe collection of results, check:

  • Exactly once: every (producer, sequence) pair appears once across all consumers. Nothing lost, nothing duplicated.
  • Order: within each consumer's list, items from any one producer have increasing sequence numbers. Each consumer sees a subsequence of the removal order, so an inversion is a bug. But a reversal split across consumers can escape this check: add a single-consumer run and small history checks. Completion timestamps alone do not order overlapping dequeues.
  • Capacity: sample the synchronized size() and reject values outside 0 to 4. Sampling can miss a transient overflow. To check every mutation, assert the bound or record a peak while holding the queue's own lock, immediately after each size change.
  • Liveness: every thread finished before the deadline. A missed signal shows up as a timeout, and the harness prints a failure instead of hanging.
  • In C++, inspect ThreadSanitizer reports as well: it can detect data races along exercised paths that result checks miss. Silence is not a proof of race freedom.

Before stress, add focused tests: that enqueue on a full queue really blocks and wakes when a consumer makes room, and the mirror image for dequeue. Also test capacity 1, multiple waiters with only one new item or slot, Java interruption, and shutdown if the API supports it. Validate the harness with a deliberately broken implementation so you know it detects failures.

Common mistakes

  • Sleeping to create an order. "Sleep 100 ms so the consumer is waiting" is a guess that fails on a loaded machine. Use explicit phase signals, bounded observations and completion deadlines.
  • Asserting in worker threads (Java). The failure is printed and the test passes. Bring results back to the test thread.
  • No start gate. Short workers may finish before later workers start, reducing overlap.
  • No timeout. One deadlock and the CI job hangs for hours instead of failing in seconds with stacks.
  • Checking invariants with racy reads while threads are still running. Check after everyone joins, or read under the same lock the code uses.
  • Retrying a flaky test until it passes. That can conceal a product defect or a broken test that still needs repair.

In the interview

After you write a thread-safe class, expect "how would you test it?" and a Databricks log-writer report explicitly lists testing for race conditions as a follow up. A 2021 Uber machine coding report describes the candidate exercising the design with CountDownLatch based unit tests. In a running environment (Rubrik, Uber machine coding), writing a small stress harness in the last ten minutes is a strong signal.

I would write a stress test: several thread counts, including oversubscription, with a latch that encourages overlap, hammering a fresh instance for many short trials. After each trial I check the invariants, here that every item comes out exactly once, in per-producer order, and sampled sizes stay within capacity. Internal checks under the lock catch transient overflows. I bound the whole test and capture stacks on timeout; Java timed joins need cleanup, while C++ needs a watchdog or process timeout. I would add noise at the check-then-act points to make rare interleavings common, run it under ThreadSanitizer in C++ or add a jcstress test for the tricky publication in Java, and I would not trust one green run.

Follow ups: "How do you test that take() blocks?" (announce entry, observe non-completion, then supply an item and bound completion). "The test failed once in CI; what now?" (reproduce at volume, do not retry, then look at the seed and stacks). "Why does your test pass without noise?" (the bad schedule may not have occurred; noise changes its chances).

Senior depth

Design for testability. Inject the clock, the executor and the random source. A cache with an injectable clock can test expiry without waiting for real time to pass; a scheduler with an injectable executor can run tasks in an order the test chooses. Patterns that confine mutation (a single writer, message passing, immutable snapshots) shrink the number of interleavings a test must cover, which is an argument for them in design reviews.

Check histories, not just end states. For a concurrent map or queue, record each operation's call and return time and its result, then check that some sequential order consistent with those times explains every result. That is a linearizability check. If A returns before B is called, A must come first; overlapping operations may go either way. For example, with no intervening removal, after put(k, 1) returns a later get(k) returning absent is invalid even if a final read returns 1.

Keep histories small because the search can grow combinatorially, and record them without introducing a global lock around the tested operations. Lincheck automates small JVM scenarios, but bounded schedule exploration does not cover every weak-memory behaviour or input.

Key takeaways

  • Vary thread counts, coordinate starts, test fresh and reused objects, collect worker failures, and bound the whole test.
  • Raise the chance per run: noise at suspicious points, preemption on one core, long enough runs for the JIT.
  • Invariants catch logic races that ThreadSanitizer cannot see; TSan catches data races the invariants miss. Use both.
  • Non-completion is evidence, not proof of blocking; propagate worker failures to the test thread.
  • Investigate flaky tests and keep regression coverage. Neither a passing stress run nor a clean sanitizer run proves correctness.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Assume independent runs, each with a fixed race probability of 1 in 10,000. You run the test 100 times. Roughly how likely are you to see it at least once?
Why. 1 - (1 - 1/10,000)^100 is about 0.01. You would need about 30,000 runs to see it 95 percent of the time, which is why good tests raise the chance per run (start gates, noise, more threads) instead of only adding runs. 63 percent is the answer for 10,000 runs.
Why do stress tests park every thread on a latch and release them together?
Why. A start gate prevents the tested operations from beginning before release and encourages overlap. It neither chooses a deterministic schedule nor changes TSan's rules. The latch publishes actions before its release to awaiters; it does not order the workers' later operations with each other.
A test runs 1,000 random transfers between 10 bank accounts on 16 threads. Which check after all threads join can expose a lost update that changes the total money?
Why. Conservation catches lost debits or credits that change the total. It does not catch every bug: compensating errors can preserve the sum, so also check individual balances and histories. Return values and exceptions look perfectly normal when an update is lost, and timing says nothing about correctness.
In the broken booth example, sold starts at 4 and the limit is 5. Exactly two workers each call the broken booking method once. After both join, which final counts can be printed? Select all that apply.Select all that apply
Why. If one worker increments before the other checks, only one booking succeeds and the count is 5. If both read 4 before either increments, both succeed and the count is 6. At least one caller sees room, so 4 is impossible; each caller increments at most once, so 7 is impossible. This is a logic race in both languages despite every counter access being atomic. A yield between the read and increment may expose 6, but does not guarantee it.
Java onlyA plain JUnit test, with no extension collecting uncaught exceptions, starts a worker thread that runs assertEquals(5, counter.get()), then joins it. The counter holds 4. What happens?
Why. Starting and joining a raw thread does not propagate its exception to the JUnit test method. An error in another thread goes to that thread's uncaught exception handler, which prints it. Bring results or failures back (a future, an AtomicReference<Throwable>) and assert in the test thread.
A concurrent test fails about once in 300 CI runs. What is the best first step?
Why. An intermittent failure can reveal a product bug, an invalid test assumption or environmental pressure. Preserve diagnostics and reproduce it; retries alone do not distinguish those causes. First make it fail reliably, then read the seed, the history and the stacks. Raising timeouts helps only when the failure really is a too-tight timing assertion, which you learn by reproducing it.
C++ onlyA C++ stress test of the broken ticket booth (atomic sold, check then fetch_add) runs under ThreadSanitizer. What do you expect?
Why. Every access to sold is atomic, so there is no data race for TSan to report. The bug is a check-then-act across two atomic operations, a logic race. That is why stress tests assert invariants even in a TSan build.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
You built a fixed-window RateLimiter.tryAcquire(): each aligned one-second window admits the first 100 calls and rejects the rest, with no carryover. Describe the test you would write to convince an interviewer it is correct under concurrency.
Model answer

I would make the clock injectable first, so the test controls time instead of sleeping: the limiter reads a now() function that the test advances by hand.

Then a stress test. Start 16 threads and park them on a latch; make at least 100 calls in total. Release them together; each calls tryAcquire() in a tight loop and counts how many times it got true, while the clock stays frozen inside one second. After joining with a timeout, the invariant is that the total admitted across all threads is exactly 100: not 101 (an over-admission race) and not fewer (lost permits). Repeat for many short trials with a fresh limiter each time. Then advance the clock by one second and check that exactly 100 more are admitted, and test the boundary just before and at the next window. This is a fixed-window contract: 100 calls just before a boundary and 100 just after are allowed. A rolling-window limiter or token bucket needs a different oracle.

To make races likely, I would put a test-only yield hook between the limiter's check and its update. In C++ I would run the whole suite under ThreadSanitizer as well, because the invariant catches logic races and TSan catches data races. Finally I would run the test thousands of times in CI before trusting it, and print the seed and the admitted count on any failure.

Write code
Write a complete stress test for a thread-safe counter with hit() and total(): a start gate, several workers, a fresh counter per trial, an exact-total invariant, and a timeout so a hang fails instead of blocking forever.
Model answer

Java bounds startup and joins with one deadline per trial, forwards worker failures, interrupts on exit and uses daemon workers so a stuck worker cannot keep this test process alive. Daemon status is not cleanup for a shared test JVM: isolate non-cooperative implementations in a child process. C++ has no standard timed join, so its watchdog terminates the test process after four seconds; a supervising runner can capture stacks before termination. Successful runs join every thread. Replace the counter with a plain shared long and the Java test may expose lost updates; in C++ that change creates undefined behaviour and should be tested under ThreadSanitizer.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"You have written a bounded blocking queue. Walk me through how you would test it under concurrency."
What a strong answer covers
  • Separate safety properties from progress and define the queue's contract
  • Use unique items, varied producer and consumer counts, and a start gate
  • Check exactly-once delivery and FIFO without mistaking completion order for removal order
  • Distinguish sampled capacity checks from checking every mutation under the lock
  • Bound startup and completion, propagate worker failures, and clean up or isolate stuck workers
  • Combine targeted schedules, stress and race detection with a correctness argument
How a senior would say it
I would test both what the queue returns and whether waiting operations can make progress. First I would check sequential FIFO behaviour and capacities one and two. Then I would start several producers and consumers behind a gate, giving every item a producer identifier and sequence number. The gate encourages overlap; it does not choose the schedule. After the workers finish, I would check that every submitted item appears exactly once. Each consumer must observe each producer's sequence in order. I would also use a single-consumer run and small operation histories, because overlapping consumers can finish in a different order from removal. For capacity, synchronized size samples provide useful evidence, but an assertion at each size change under the queue lock catches temporary overflow that sampling misses. I would separately test an empty consumer, a full producer, multiple waiters and Java interruption. Startup and completion need deadlines. Worker exceptions must reach the test thread, and a timeout needs diagnostics plus cancellation or process isolation. Finally I would force suspicious schedules with test hooks, vary the stress configuration and run C++ under ThreadSanitizer. I would explain why the locking invariant is correct as well. Passing tests support that argument; they do not replace it.

Likely follow up: How could your test instrumentation accidentally hide an unsafe-publication bug?

Out loudabout 75 s
"This atomic ticket counter passed thirty thousand stress runs. Would you sign off its check-then-increment logic?"
What a strong answer covers
  • Passing stress runs do not make a compound check and increment atomic
  • Give the last-seat schedule where two callers read four and both increment
  • Force the schedule with a bounded test-only rendezvous and assert results
  • Fix with a CAS retry loop or one lock across check and update
  • Explain why yield, a random seed and a silent sanitizer do not establish correctness
How a senior would say it
No. I would inspect the atomicity of the operation before signing it off. Suppose five tickets are available and four have been sold. Two callers can each read four, both decide there is room, and both increment. Every access is atomic, but the final count is six. ThreadSanitizer has no data race to report. For a regression test I would place a test-only rendezvous after both initial reads, then release both callers and check the successful bookings as well as the count. I would bound the test so a bad hook cannot hang the suite. The fix is one lock across check and update, or a compare-and-set loop that changes four to five only if four is still current. A failed compare-and-set must retry and check the limit again. I would then run the targeted test and broader stress. Yield is only a scheduling hint. A seed repeats generated inputs, not an uncontrolled operating-system schedule. Thirty thousand passes therefore add evidence, but the invariant and the atomic decision are what justify the fix.

Likely follow up: Where would you put the test hook so that CAS retries do not deadlock the test?
