Thread pool from scratch

Executors and asynchard60 minRubrikLinkedIn

Candidates rarely fail this Rubrik screen on the happy path. They fail on the questions that follow: what happens to queued work on shutdown, which exceptions the worker catches, how a task times out, and when idle threads go away. Every one of those is a test here.

The task

Build a thread pool with the sizing rules of Java's standard pool: a core size, a maximum size, a bounded queue and a keep-alive time.

When a task arrives andthe pool
fewer than core threads existstarts a new thread to run it
core or more exist and the queue has roomqueues it
the queue is full and fewer than max threads existstarts a new thread to run it
the queue is full and max threads exist, or the pool is shut downrejects it
  • Idle threads are reclaimed. While there are more than core threads, a thread that waits keepAlive without getting a task exits. The pool never shrinks below core this way.
  • Two submission paths, two failure paths. execute(task) is fire and forget: if the task throws, the throwable goes to the onError handler given to the constructor, and the worker carries on. submit(task) returns a future: the result or the exception is delivered through the future (get throws ExecutionException in Java and rethrows the task's exception in C++), and onError is not called.
  • Per-task timeout. submit(task, timeout) limits how long the task may run, counted from when it starts. When the limit passes, the future fails at once (Java: it is cancelled, get throws CancellationException; C++: get throws TaskTimeout) and the task is asked to stop (Java: its thread is interrupted; C++: its std::stop_token is set). The worker takes the next task as soon as the timed-out one returns.
  • Lifecycle. shutdown() refuses new tasks, lets queued and running tasks finish, then lets the threads exit. shutdownNow() refuses new tasks, removes and returns the queued tasks without running them, and asks running tasks to stop (Java: interrupt; C++: the pool's stopToken()). Neither waits. awaitTermination(timeout) waits until the pool is shut down and every worker has exited, and returns false on timeout. isShutdown, isTerminated and workerCount report the state.
  • No thread leaks. Every thread the pool starts, including any helper thread you use for timeouts, must end once the pool terminates. In C++ the destructor shuts down, waits and joins everything.

Rules, as in the interview: no library executors or queues; build the queue, the workers and the lifecycle from threads, one lock and condition variables. For the futures you may use FutureTask in Java, and std::packaged_task, std::promise and std::stop_source in C++: the pool is the point, not the future (that is the future from scratch problem). C++ has no thread interruption, so cancellation there is cooperative, through stop tokens.

Where it comes up: Rubrik screens in 2026 asked for a bounded queue and then a pool on it with submit, execute, shutdown and shutdownNow, judged on shutdown semantics, interrupts and which exceptions are caught ("InterruptedException plus Exception was not enough"), and another Rubrik round followed up with exceptions inside tasks, per-task timeouts and reclaiming idle threads. LinkedIn asked a candidate in 2024 to implement one of Java's standard pool types without using the API.

What the tests check

  • submit delivers values and exceptions through the future, does not call onError, and a single worker survives a failing task.
  • execute failures reach onError, including an AssertionError in Java and a thrown int in C++, and the worker carries on.
  • Growth: with core 1, max 3 and a queue of 2, task 1 gets the core thread, tasks 2 and 3 queue, tasks 4 and 5 get new threads, task 6 is rejected, and all 5 finish.
  • Reclaim: with keepAlive 200 ms, the two extra threads exit once idle and the pool still runs tasks on its core thread.
  • Timeout: a task limited to 150 ms fails after 150 ms or a little more (never before), is interrupted or told to stop, and the single worker runs the next task. A timed task that finishes in time returns normally.
  • shutdown runs the queued tasks, refuses new ones, terminates, and the threads end. Shutting down an idle pool also terminates.
  • awaitTermination(150) returns false after about 150 ms while a task still runs, and true once it ends.
  • shutdownNow returns the 3 queued tasks unrun, stops the running one, terminates and refuses new work.
  • Stress: 4 threads submit, retrying on rejection; every future returns its own value and never more than max tasks run at once.
  • No leaks: in Java no thread the pools started is alive after termination; in C++ the destructor joins every thread. ThreadSanitizer must stay quiet.

Taught in: Build it yourself: a thread pool with futures and shutdown

Open them one at a time. Each one gives away a little more.

Write down the state first: a queue of jobs, the set (or count) of live workers, and a shutdown flag, all under one lock, with a condition for idle workers and one for awaitTermination. Every decision in the growth table is one if chain inside execute, under that lock.
A worker loops: run a job, then ask for the next one. "Give me the next job" is where all the hard decisions live: take from the queue if it is not empty; exit if shut down and the queue is empty; if there are more workers than core, wait at most keepAlive and exit if nothing came. Make the exit decision and remove the worker from the live set in the same critical section, or two idle threads can both retire and leave the pool below core.
Failures: around the task, catch Throwable in Java and ... in C++. For submit, wrap the task so the wrapper stores the outcome in the future (FutureTask, or std::packaged_task held by a shared_ptr so it fits in a std::function); for execute, the catch hands the throwable to onError. Clear the interrupt flag after every task so it cannot leak into the next.
Timeouts: one extra thread keeps a priority queue of deadlines and sleeps until the earliest one (awaitNanos, wait_until). A worker registers the deadline when it starts a timed task. At the deadline, Java calls cancel(true) on the FutureTask (it interrupts only while that task is running), and C++ sets a TaskTimeout into a promise guarded by an atomic flag and requests stop. That thread exits when the pool terminates.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Implement newFixedThreadPool, newCachedThreadPool and newSingleThreadExecutor with your pool.
Fixed: core and max both n, an unbounded queue, keep-alive irrelevant. Single: the same with n of 1, and it must replace a worker that dies, so tasks still run one at a time in order. Cached: core 0, an effectively unbounded max, keep-alive 60 seconds, and a queue of capacity zero that hands each task directly to an idle thread. With the rules above, a zero-capacity queue would start a new thread even when one is idle, so a cached pool needs one more piece of state: a count of idle workers, and a hand-off that gives the task to one of them before growing. Saying exactly where the standard pool's rules and the cached pool's behaviour differ is the point of this follow up.
A pool with core 1, max 50 and an unbounded queue runs everything on one thread. Why?
Because the pool only grows past core when the queue is full, and an unbounded queue is never full. This is the queue-before-max trap: max has no effect. Fix it with a bounded queue, with core equal to max, or with a pool that prefers starting threads to queuing. See inside an executor.
Which exceptions does your worker catch, and why is catching Exception not enough?
An Error such as AssertionError or StackOverflowError is not an Exception, so a worker that catches only Exception dies when a task throws one, and with every worker dead the pool silently stops. Catch Throwable around the task. InterruptedException seen in the worker's own waiting means "check the shutdown state", not "die". Inside tasks, never swallow an interrupt: restore it with Thread.currentThread().interrupt() or let it propagate. In C++, any exception escaping a thread's function calls std::terminate, so catch (...) is mandatory.
The futures of tasks returned by shutdownNow never complete. Is that a problem?
In Java, yes: a caller blocked in get() on one of them waits forever, exactly like the standard pool. Either cancel them before returning (cancel(false) on each FutureTask) or document that the caller owns them now. In C++ it fixes itself: when the returned functions are destroyed, the std::packaged_task inside is destroyed, and its future's get() throws std::future_error with broken_promise instead of hanging.
A task times out but ignores the interrupt.
Its future is failed, but the worker is still stuck inside the task, so the pool has quietly lost a thread until the task returns. Interruption is a request, not a kill: blocking socket reads in Java ignore it (close the socket to unblock them), and C++ has only cooperative stop tokens. Mitigations: make tasks check for cancellation, give blocking calls their own timeouts, or have the pool start a replacement thread when a timed-out task is still running, accepting that the stuck one may finish later.
What should happen when the pool is full?
That is the rejection policy. Throwing (what you built) pushes the decision to the caller. Caller-runs executes the task on the submitting thread, which slows producers down and gives natural backpressure. Discard drops the new task, and discard-oldest drops the head of the queue; both lose work silently and need metrics. Name the policy and why it fits the workload.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

One lock guards the queue, the set of live workers and the shutdown flag. execute applies the growth table under that lock. Each worker runs a job, then asks next() for another, and next() is the only place a worker decides to exit. The invariant: every accepted task either runs exactly once or is returned by shutdownNow, and the live-worker count always equals the number of threads that have not yet decided to exit.

Why each line is there

  • The growth if chain under the lock. "Fewer than core", "queue has room" and "fewer than max" read state that other submitters and exiting workers change, so the check and the action must be one critical section.
  • next() decides and deregisters together. Otherwise two idle threads above core can both see "one too many" and both exit. It takes from the queue before looking at the shutdown flag, so shutdown drains the queue; checking the flag first is exactly the bug that drops queued work.
  • signalAll (notify_all) in shutdown. Idle core workers sleep without a timeout. Nothing else will ever wake them, as the timeline below shows.
  • Catch everything around the task, and clear the interrupt afterwards. An escaped throwable kills a Java worker and ends a C++ process. A leftover interrupt would make the next task's first blocking call fail.
  • FutureTask.cancel(true) for timeouts. It interrupts the thread only while that task is still running and makes run() wait for the interrupt to land, so the interrupt cannot leak into the next task. In C++ an atomic settled flag decides whether the task or the timeout fills the promise, because a promise can be set only once.
  • A deadline thread that ends with the pool. It waits on the same lock and exits when the pool is shut down with no workers left, so awaitTermination can promise that no pool thread is alive. In C++ the thread vector and the watcher are joined in the destructor; finished workers are reaped as new ones start.

Cost and trade-offs

Every hand-off takes the one lock. That is fine for most workloads; at very high task rates the lock itself becomes the bottleneck, and pools move to per-worker queues and work stealing. Starting a thread costs on the order of tens of microseconds plus its stack memory, which is why the pool keeps core threads and reuses them. The timeout thread costs one extra thread per pool; a shared timer could serve many pools.

How to say it in the interview

The pool has one lock over a bounded queue, the live workers and a shutdown flag. Execute follows the standard rules: below core start a thread, else queue, else grow to max, else reject. Each worker runs a task and asks next() for the next one; next() takes from the queue first, exits when shut down and drained, and above core waits only keepAlive before retiring, deciding and deregistering under the lock. Execute failures go to an error handler, submit failures into the future, and I catch Throwable so even an Error cannot kill a worker. Shutdown sets the flag and signals all idle workers; shutdownNow also drains the queue, returns it and interrupts the running tasks. Per-task timeouts use one deadline thread that cancels the future and interrupts only that task.
