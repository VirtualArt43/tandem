The multithreaded web crawler

Atomic URL claims, parallel fetches, reliable completion accounting, exact depth limits and failure handling in a multithreaded crawler.

Asked atDatabricksRubrik
Before this:CPU bound versus I/O bound workWhy thread pools existConcurrent hash mapsCheck then act: two safe calls, one unsafe sequence

Databricks and Rubrik interview reports repeatedly describe the crawler with a "now make it multithreaded" follow up. Three central requirements are: every URL is claimed exactly once, fetches really run in parallel, and the program knows when it is finished without polling.

In plain words

You run a research desk with six assistants. You hand out a starting book; every book cites other books, and each assistant writes the citations on slips and drops them in a tray. A register at the front desk lists every book ever handed out, so nobody reads the same book twice: before a slip goes in the tray, the clerk checks the register and writes the title in it, in one motion.

The hard question is when to send everyone home. An empty tray does not mean the job is done: an assistant may be halfway through a book and about to drop five new slips. The job is done when the tray is empty and nobody is reading. Counting the books that are out, in the tray or in someone's hands, is how you know.

The problem (LeetCode 1242)

You get a start URL and an HtmlParser whose getUrls(url) returns the links on a page. The call is slow, like a real network fetch. Return every URL reachable from the start URL that has the same host name as the start URL, crawling each URL once, using several threads. The host of http://news.example.com/a/b is news.example.com; links to any other host are ignored.

Several reports start with the single threaded version. It is a breadth-first search with a queue and a visited set, and you should be able to write it in two minutes:

The small hostOf helper below assumes the exercise's restricted URL form: an absolute http:// URL, a lowercase hostname, and an optional slash-prefixed path, with no ports, credentials, queries or fragments. Outside that contract it extracts the authority incorrectly: use a URL parser, resolve relative links, normalise hostname case, and define URL identity before deduplication. Same hostname is not the same rule as same origin, which also checks scheme and port.

Notice two details you will keep. A URL is marked visited when it is discovered, not when it is fetched, so it can never enter the queue twice. And the host check compares the parsed host for equality; checking whether the URL string contains the host would accept http://other.org/?from=news.example.com.

Why threads help, and how many

Each getUrls call spends almost all its time waiting on the network. That is I/O bound work: as an illustrative workload, suppose one thread spends 100 ms waiting for every 1 ms of parsing, so you can overlap many fetches on few cores. Databricks interviewers have asked exactly this ("how do you know multithreading will help here?"), and the answer is that the work is waiting, not computing. The rough sizing rule from sizing a pool is threads about equal to cores times (1 + wait time / compute time). With 8 cores and a 100 to 1 ratio that suggests hundreds of threads, so the real limit is something else: how many concurrent requests one host tolerates (politeness), your bandwidth, and memory for the frontier.

Three things that break when you add threads

1. Claiming a URL must be one atomic step

The tempting change is a concurrent set and a check before adding:

if (!visited.contains(u)) { visited.add(u); submit(u); }

Each call is thread-safe, but the pair is a check then act: two workers can both see the URL as new, both add it, and both fetch it. The fix is an operation that checks and marks in one step and tells you whether you won: visited.add(u) returns true for exactly one caller on a ConcurrentHashMap.newKeySet(); visited.insert(u).second does the same on a set guarded by a mutex in C++.

2. "The queue is empty" does not mean "done"

This is the bug that sinks most first attempts, because it hides in the gap between taking a URL and adding its children:

The opposite mistake is a main thread that polls: while (!queue.isEmpty() || active > 0) sleep(10). It burns wakeups, adds up to roughly one polling interval before checking again, plus scheduling delay, and still has to read two values that can change between the reads. Interviewers want termination detection without busy waiting.

3. Count the work, in the right order

Keep one number, pending: URLs discovered and not yet finished, whether they wait in the queue or are being fetched. Start it at 1 for the start URL. When a worker finishes a page, it adds the page's new children to the queue and to pending first, and only then subtracts 1 for the page itself. Because children are counted before their parent is marked finished, pending can only reach zero when there is truly nothing left. A worker waits while the queue is empty and pending is above zero; when pending hits zero, the last worker wakes everyone and they all exit.

Put those three ideas in one monitor and you have a complete crawler with no library executor, which matters at Rubrik, where interviewers have banned ExecutorService and blocking queues for this very problem. The fetch happens outside the lock, so up to six workers can fetch pages at once when the frontier has enough independent work:

The sample handles a finite graph, a thread-safe parser returning non-null lists, and URL strings meeting the contract above. Call crawl once with a positive worker count, keep the parser alive until it returns, and assume thread creation and allocations succeed. Failed fetches are terminal attempts with no children: the result is the set of discovered URLs, including failed attempts, rather than proof that every page was downloaded. This compact version finishes normally before propagating caller interruption; active cancellation is discussed below.

The C++ version uses C++20 std::jthread. For C++17, use std::thread and an exception-safe guard that joins every successfully started worker. Normal completion still explicitly joins before reading the result.

The fake web requests a 2 ms sleep per fetch. Its nominal serial sleep budget is 120 ms for 60 pages; real elapsed time includes scheduling, startup and sanitizer overhead, and the shown 37 ms is only illustrative. Neither the exact time nor a particular speedup is guaranteed. A page that throws is still counted as finished, which matters: if a failure skips the pending -= 1, the count never reaches zero and the crawl never ends.

Worked example: watching the count

Start URL A links to B and C; B links to C and D; C and D link to nothing new. Two workers.

StepWhat happensQueuepending
0StartA1
1Worker 1 takes A and fetches it(empty)1
2Worker 2 sees an empty queue but pending is 1, so it waits(empty)1
3Worker 1 adds B and C (+2), then finishes A (minus 1)B, C2
4Workers take B and C(empty)2
5C finishes with nothing new(empty)1
6B finds C (already visited, ignored) and D (+1), then finishesD1
7D is taken and finishes with nothing new(empty)0

At step 2 the queue was empty while A was in flight, and the count kept worker 2 from quitting. The invariant at every observable monitor boundary is pending = queued + active. Removing an item transfers it from queued to active without changing pending; completing it adds its newly claimed children and removes one active item.

With a separate atomic counter or completion latch, finishing A before registering B and C can publish zero too early. In this monitor, swapping those updates is safe if both remain in the same uninterrupted critical section and zero is tested only after both. Even signalling inside that section does not let a waiter inspect the state before reacquiring the lock. Children-first is a useful discipline because it also works when completion is published immediately by an atomic decrement.

With expected constant-time hashing, bookkeeping takes O(V + E) time for V discovered pages and E examined links, excluding network latency and string-processing costs. The queue and visited set take O(V) space, plus worker stacks and fetched link buffers. Parallel speedup also depends on graph width: a chain of links exposes only one fetch at a time.

With a pool instead of your own workers

When libraries are allowed, the same three ideas move into different tools: tasks on a thread pool, a concurrent set for claiming URLs, and a separate in-flight counter that wakes the caller when it reaches zero.

The counter is worth having as a small, one-shot class. Start with one caller registration; register seed tasks before submission, then release the caller registration with finished() and call awaitZero(). Only a registered, unfinished task may register children, and zero is terminal.

Every successful registration must be balanced exactly once, including rejected submissions. The counter alone does not make a result container thread-safe: use a concurrent container or a lock.

Java

Java also has a ready made tool for "wait until a changing number of tasks are done": a phaser. Register a party before submitting each task, and arrive and deregister when the task ends; the caller arrives once and waits for the phase to advance. Mind one limit: a Phaser supports at most 65,535 registered parties at a time, so a crawl with a huge frontier of submitted tasks can hit it. The counter above avoids that specific party limit, but its integer count can still overflow. Bound outstanding work below the count's maximum, or use checked wider counters. Tiered phasers are another option.

This alternative reports the first runtime failure after draining instead of returning a partial result silently. Its wait is uninterruptible; fetch timeouts remain essential. Call it once. Fatal VM errors and resource exhaustion need a broader abort policy.

One trap with pools: do not make a task wait for the futures of its child tasks. With a fixed pool, every worker can end up blocked waiting for children that sit in the queue with no free worker to run them. That is pool self deadlock; counting in-flight work avoids it because no task ever waits for another.

C++

C++20 has no standard thread pool, so in an interview the monitor version above is the idiomatic answer. If you already built a pool (see build a thread pool), pair it with the InFlight counter: call started() before each submit and finished() at the end of each task, after it has submitted its children. On rejection, undo the registration and record the failure; never report a rejected URL as successfully crawled. Never make a task block on its children's futures inside a fixed pool: every worker can end up waiting for work that has no free worker to run it.

Depth limits, and why a free-running crawl gets them subtly wrong

Databricks' follow up is "limit the crawl to depth K" (the start URL is depth 0). The easy change is to queue (url, depth) pairs and not follow links from pages at depth K. With free-running workers that is subtly wrong. Suppose S -> A -> X reaches X at depth 2, while S -> B -> C -> X reaches it at depth 3, and K is 3. If fetching A is slow, the longer branch can claim X at the depth limit first. It will not expand X. When A finally returns, plain visited-set deduplication discards the shorter route, so a child Y of X at shortest depth 3 is missed. The visited set says "seen", not "seen at its shortest depth".

Two fixes. Keep the best depth per URL and re-queue a URL when it is found again at a smaller depth. Or crawl level by level: fetch every URL of level d in parallel, wait for the whole level, and only then build level d + 1. Level by level gives exact breadth-first semantics and lets one coordinator thread own the visited set, so it needs no lock at all; the price is that each level waits for its slowest fetch.

Here K is nonnegative, the result contains pages at shortest distance at most K, and pages at depth K are returned without fetching their links. If the requirement also downloads boundary-page contents, fetch that final level but discard its outgoing links. The Java caller owns a live executor and calls this coordinator outside its worker pool; fetch failures propagate after the level. C++20 uses std::jthread to join workers even during unwinding; the C++17 fallback is std::thread with explicit joins and an exception-safe joining guard.

Failures, cancellation and bounded memory

Define completion separately from success. A failed page still retires its work registration. If retries are allowed, retain that registration until a terminal result or count the retry before retiring the attempt, cap retries and use backoff. An asynchronous fetch callback follows the same rule: keep the page active until the callback has registered its children, then retire it exactly once on either success or failure.

A wait timeout does not stop the fetch. Give the HTTP operation its own deadline and a cancellation mechanism. For active cancellation, set a stop flag under the monitor lock, reject new work, remove queued work while adjusting pending, wake every waiter, and ask running fetches to stop. Active workers retire their own registrations; join them before returning or destroying shared state. Java interruption is cooperative, and C++20 stop requests do not forcibly interrupt blocking I/O.

A fixed worker count does not bound the frontier. A wide page can produce millions of URLs. If every worker blocks trying to put children into a full bounded queue, no worker remains to consume it. Use a coordinator that can drain results, spill the frontier to persistent storage, or explicitly reject work under a crawl budget. Claiming a URL and accepting its work must be coordinated: on rejection, roll back the claim or return an explicit failed/incomplete crawl. Bound retries and result buffers too.

Common mistakes

  • contains then add on the visited set. Two workers both see a URL as new and both fetch it. Use the single call that checks, marks and reports.
  • Stopping when the queue is empty. The queue is empty whenever every URL is in a worker's hands. Count in-flight work.
  • Finishing a page before counting its children. Publishing zero before registering children can complete the crawl early; a transient zero hidden inside one locked transaction is not observable.
  • A failure that skips the bookkeeping. If getUrls throws and the decrement is not on every path (finally, or a catch that falls through), the crawl hangs.
  • Holding the lock during the fetch. It is correct and completely serial. Take a URL under the lock, fetch outside it, update under it again.
  • A thread per URL. Ten thousand links means ten thousand threads. Bound the parallelism with a fixed number of workers (or, with Java 21 virtual threads, a semaphore).
  • Tasks that wait for their children's futures in a fixed pool. The pool can deadlock with every worker waiting. Count work instead of waiting on it.

In the interview

Databricks asks it as a coding or design round with a "now multithread it" follow up: a 2023 SDE-2 loop in India crawled from seed words with a depth limit K and then multithreading, with questions on thread pool size, dataset size and disk and network bottlenecks; a 2023 L5 loop gave single threaded fetch and parse helpers and a maximum depth, and asked how you know threads will help before asking for the multithreaded version; an earlier SDE3 loop asked a crawl to depth h. Rubrik has asked it at least four times from 2022 to 2025: LeetCode 1242 itself (one candidate moved from a thread pool to CompletableFuture), a 2024 screen judged on data structure choice where a later reply says BlockingQueue and ExecutorService were banned, and a 2025 round over about 1,000 nested pages judged on picking the right critical sections and the right places to create threads. LeetCode's crowd reported tags list Web Crawler Multithreaded for Meta, Apple and Snowflake as well.

The work is I/O bound, so threads help by overlapping the waits. I will keep a frontier queue, a visited set and a count of pending pages under one lock. A worker takes a URL under the lock, fetches it outside the lock, then under the lock claims each new same host link with one add that returns whether it was new, queues it, increments pending, and only then decrements pending for its own page. Workers wait on a condition while the queue is empty and pending is positive; when pending reaches zero the last one wakes everyone and they all exit, so there is no polling.

Follow ups to expect: "Add a depth limit." "How many threads?" "What if getUrls throws or hangs?" (count it as finished on every path; put a timeout on the fetch). "How would you be polite to the host?" (a per host limit on concurrent requests or a rate limiter). "Scale it to a billion pages across machines."

Senior depth

Across machines, partition by host. A distributed crawler assigns each host to one machine by hashing the host name. That machine owns the host's frontier, its visited set and its politeness limits, so deduplication and rate limiting stay local and need no cross-machine locks in normal operation. Ownership changes need coordinated handoff, and a crash between claiming and durably queuing a URL must not lose that work. URLs discovered for other hosts are sent to their owners. It is the single owner idea from single writer and actors at cluster scale.

The visited set outgrows memory. At scale it can become a persistent store fronted by a Bloom filter. A negative says definitely absent; a positive means possibly present and should be checked in the exact store if completeness matters. Only using the filter alone to suppress work loses pages to false positives; that is an explicit approximation, not an inevitable property of a Bloom-fronted store.

Threads are not the only way to overlap waits. With an asynchronous HTTP client, a few threads can keep thousands of fetches in flight; with Java 21 virtual threads, a thread per fetch is cheap, and a semaphore bounds how many run at once. The bookkeeping (claim once, count in-flight work, stop at zero) does not change.

Key takeaways

  • Threads help because fetches wait on the network; size by the waiting, then cap by politeness and bandwidth.
  • Claim each URL with one atomic check-and-mark: add on a concurrent set, or insert(...).second under a mutex.
  • Termination is "nothing queued and nothing in flight": count pending work, add children before finishing the parent, and wake everyone at zero.
  • Fetch outside the lock, and make every failure path finish its page.
  • Exact depth limits need level by level crawling, or re-queuing when a shorter path appears.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Workers share a ConcurrentHashMap.newKeySet() and run if (!visited.contains(u)) { visited.add(u); submit(u); }. What can go wrong?
Why. Each call is atomic, but the pair is a check-then-act. Use the result of the add itself: if (visited.add(u)) submit(u); makes exactly one worker the owner of u. The concurrent set does not lose entries or deadlock in this sequence; the duplicate submission is an application-level race.
Under the correct monitor lock, the main thread waits with while (!queue.isEmpty()) wait(); and returns the visited set once the queue is empty. What is the bug?
Why. An empty queue says nothing about work in flight. Termination needs a count of pages that are queued or being fetched, and that count reaches zero only when both are empty. This loop can return, possibly too soon; it does not itself enqueue duplicate URLs.
A pool task finishes page P. Decrementing its atomic pending counter immediately opens a completion latch if it reaches zero. Which order is safe?
Why. Register children before finishing P so a published zero is terminal. If P is the last registered task, decrementing first permanently opens the latch before its children exist; the waiter does not acquire the task's lock. In the monitor sample, both updates can be reordered within one critical section if completion is tested only afterward. An atomic decrement without child registration does not repair this protocol.
getUrls throws for one broken page, and the worker's code decrements pending only after a successful fetch. What happens?
Why. Every registered page must retire on every terminal path. Catch the failure or use finally and still decrement. The leaked positive count prevents normal zero-based completion, does not enqueue a retry and does not itself create an early zero. If no workers survive, joining them may instead expose a failed partial crawl; worker failure must not be mistaken for successful completion.
An otherwise correct crawler holds its single state lock across getUrls(url) and the frontier update. Assume the fetch returns, does not re-enter the crawler, and has no lock dependencies. What is true?
Why. The slow part is the fetch, and it happens while holding the only lock, so every other worker waits. Take the URL under the lock, fetch without the lock, and take the lock again only to record the results. The given assumptions rule out the proposed deadlock, the set remains protected, and holding a lock does not change host filtering.
Free-running workers crawl with a depth limit K, storing (url, depth) and not following links beyond depth K. Compared with a sequential breadth-first crawl, what can happen?
Why. Concurrency changes which path claims a page first. If the long path wins, the page carries too large a depth and its links are cut off early. Crawl level by level, or keep the best depth and re-queue a page found at a smaller depth. The depth guard still excludes over-limit paths, and on a finite graph with terminating fetches this bug does not itself prevent termination.
Under the restricted URL contract used by the samples, which same-host check is correct for start URL http://news.example.com/?
Why. contains accepts http://evil.org/?u=news.example.com, endsWith rejects normal path URLs and can accept unrelated hostnames ending in that suffix; startsWith also accepts http://news.evil.org/. Extract the host and compare it exactly; in real code, use a URL parser.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
A crawl must fetch 10,000 pages. Each fetch waits about 100 ms on the network and then parses for about 1 ms of CPU. The machine has 8 cores. Estimate the time with 1 thread and with 50 threads, and name what really bounds it. Treat all numbers as orders of magnitude.
Model answer

One thread: 10,000 times 101 ms is about 1,010 seconds, roughly 17 minutes. With 50 threads overlapping the waits: about 1,010 seconds divided by 50, roughly 20 seconds. This ideal estimate assumes enough independent pages are ready, no throttling and no retries; a chain cannot realise the 50-way overlap. The CPU lower bound is smaller: 10,000 times 1 ms is 10 seconds of CPU in total, about 1.25 seconds spread over 8 cores.

The sizing formula, threads about equal to cores times (1 + wait / compute), gives 8 times 101, about 800 threads, which tells you the work is almost pure waiting. Further limits include: how many concurrent requests the host allows before it slows down or blocks you, network bandwidth (10,000 pages of, say, 100 KB each is about 1 GB to download), and memory for the frontier and visited set. In the interview I would start with an agreed per-host concurrency and request-rate budget, measure throughput and latency, and increase concurrency only within that budget.

Write code
Add a depth limit K to the free-running monitor crawler so that its result matches a sequential breadth-first crawl to depth K. Show only what changes.
Model answer

Seed bestDepth[startUrl] = 0, enqueue (startUrl, 0) and set pending = 1 before starting workers. Reject negative K, retain the original host filter before calling onLinks, and call it with an empty list on a terminal fetch failure. Notify all waiters after this locked update, and return the map's keys after joining. The frontier now carries the depth, and the visited set becomes a map from URL to the smallest depth seen so far. A page found again along a shorter path is queued again with the better depth, so its links get the full budget; links of a page at depth K are not followed. The cost is that a page may occasionally be fetched twice (once per depth improvement, potentially many times), which you should say out loud. If refetching is not acceptable, crawl level by level instead: fetch level d in parallel, wait for all of it, then build level d + 1, which gives exact breadth-first depths with each expanded page fetched once. These comparisons assume a stable graph; if links change between fetches, repeated attempts need not reproduce a single snapshot.

Design
A Databricks interviewer asks: "How do you know multithreading will help here, and how would you scale this crawler to a billion pages on many machines?"
Model answer

Multithreading helps when threads spend their time waiting rather than computing. Here each fetch is about 100 ms of network wait for about 1 ms of parsing, so one core could keep many fetches in flight; I would confirm by measuring CPU use during a single threaded crawl (it would be nearly idle) and then watch throughput rise as I add threads until it flattens, which tells me I have hit the real bottleneck: the host's tolerance, bandwidth or memory.

For a billion pages I would partition by host: hash each host name to one machine, which owns that host's frontier, visited set and politeness limit, so deduplication and rate limiting stay local. Links to other hosts are forwarded to their owners in batches. Each machine runs the same local design: a bounded pool of fetchers (or async I/O), the in-flight count for termination of a batch, and a persistent frontier so a crash loses little. The visited set moves to a disk backed store with a Bloom filter in front. Global termination must account for messages in transit as well as local queues and fetches. All machines observing an empty local queue is insufficient; use a distributed termination protocol or a protocol tracking unacknowledged durable work. More often there is no global end at all: a production crawler runs continuously and re-crawls pages on a schedule.

Out loudabout 90 s
"Your crawler's queue is empty, but one fetch is still running. How do you know when the whole crawl is actually finished?"
What a strong answer covers
  • Completion requires no queued or active work, expressed as pending equals queued plus active
  • Claim and enqueue each same-host URL once under the state lock
  • Taking work does not decrement pending; fetch outside the lock
  • Register children before retiring their parent and publish terminal zero to all waiters
  • Failures and rejected submissions must retire exactly one registration
  • A transient zero hidden inside one locked update is not visible to other monitor users
How a senior would say it
An empty queue is not enough. The active fetch may discover more work, so I track pending as queued pages plus active pages. I seed it with one for the start URL. Under one lock, a worker takes a URL from the frontier without changing pending. It releases the lock for the slow fetch, then reacquires it to claim new same-host links, queue them and count them before retiring the parent. Claiming and checking must be one operation, otherwise two workers can fetch the same URL. An idle worker waits while the queue is empty and pending is positive. The last completion makes pending zero and wakes everyone, so workers can exit and the caller can join them. Every terminal failure also retires its page; retries must retain or replace that registration. With an executor, I register before submission and undo the registration if submission is rejected. Otherwise the counter can leak forever. One nuance matters: a transient zero inside a single locked update is harmless if nobody tests completion until the update ends. But an atomic decrement that opens a completion latch publishes zero immediately, so children must already be registered. The invariant and its publication point are the proof.

Likely follow up: How would you bound the frontier without deadlocking workers that also produce new URLs?

Out loudabout 90 s
"You added a depth limit, but your parallel crawler misses pages that sequential BFS finds. What went wrong, and which fix would you choose?"
What a strong answer covers
  • Concurrent completion order does not preserve shortest-path discovery order
  • Give a path of length two and another of length three to X with limit three
  • First claiming X at depth three suppresses expansion and loses a child reachable at depth three
  • Level barriers restore exact BFS depths with coordinator-owned deduplication
  • Alternatively requeue on improved depth, accepting repeated expansion or caching fetched links
  • Define whether boundary pages are returned only or also fetched
How a senior would say it
The visited set records first discovery, but first discovery is not necessarily the shortest path when fetches finish out of order. Suppose the start reaches X through A in two hops, and through B and C in three hops. The limit is three. If A is slow, the longer route claims X first at depth three, so X is not expanded. When A finally returns, the visited set suppresses that shorter route. A child Y of X is therefore missed even though its shortest distance is three. I would choose level-by-level crawling when exact depths and one fetch per expanded page matter. Fetch one level in parallel, wait for it, then let one coordinator deduplicate and build the next level. That also removes concurrent access to the visited set. The cost is a barrier at every level, so one slow page holds up the next level. Alternatively, keep the best known depth and requeue a page whenever that depth improves. This preserves overlap but may repeat fetches or require caching links. I would define the boundary too: our example returns pages at the limit without fetching their outgoing links. If downloading their contents is required, fetch that final level but do not expand it.
