Building, debugging and sanitizers

Compile and link threaded programs, drive lldb through a hung process, and read AddressSanitizer, ThreadSanitizer and UndefinedBehaviorSanitizer reports.

Asked atRubrikMicrosoft
Before this:How C++ becomes a running program

Concurrency bugs hide from print statements and from passing tests. The engineers who find them quickly rely on three things: a build that turns on every check, a debugger that shows every thread's stack, and sanitizers that expose races and lifetime errors even when the output looks correct.

In plain words

Think of a hospital. A debugger is the X-ray room: it freezes the patient and shows you every bone at once, which is exactly what you need when a program is stuck and you must see what every thread is doing. A sanitizer is a blood test that runs all the time the patient is awake, and can flag hidden problems even when the patient looks healthy; no single test detects everything.

That last part is the point. A racy program that prints the right answer is a patient with no symptoms and bad blood. You cannot see the bug by looking at the output, so you need instruments.

Why this matters for concurrency

  • Data races are invisible and undefined. ThreadSanitizer finds them with both stacks: who wrote, who read, and where each thread was created.
  • Deadlocks and lost wakeups show up as a hang. The fastest diagnosis is a thread dump: attach a debugger and print every thread's stack.
  • Lifetime bugs travel between threads. Access through a view, reference or captured pointer after its target dies is a lifetime error, such as a heap use after free or stack use after scope. AddressSanitizer reports it with the freeing thread and the reading thread.
  • Tandem runs all of your C++ under ThreadSanitizer. Every runnable C++ sample and C++ problem attempt uses -fsanitize=thread, so you need to read its reports fluently.
  • It is asked. Rubrik runs a debugging round: you get someone else's multithreaded program, in one report C++ producer and consumer code, and must return code that compiles and runs. One new grad fixed the deadlock and then lost the round on a compile error. Microsoft has asked candidates to predict the output of multithreaded C++ and then find its issues.

From source to a threaded binary

A C++ program is compiled file by file into object files, then linked into one binary. For a single file you can do both in one command. These are the commands to know, with clang; GCC (g++) takes the same flags.

Use -pthread for these Unix clang and GCC commands. On a Mac it changes little, because threads live in the system library. On Linux with a glibc older than 2.34, forgetting it gave link errors such as an undefined reference to pthread_create; newer glibc folded the thread library into libc, so the error disappeared, but the flag is still the portable, correct choice. In CMake the equivalent is find_package(Threads REQUIRED) and target_link_libraries(app PRIVATE Threads::Threads).

Warnings are free bug reports

Compile with -Wall -Wextra and read every warning in threaded code. These are clang diagnostics with this libc++ configuration. The first two expose broken locking; the third asks you to review ownership and synchronization, because capturing this can be intentional and safe:

A compiler error points to source that cannot form an object file, such as a missing declaration. An undefined-symbol linker error means the declaration compiled but no matching definition was linked: check source files, exact signatures, and required libraries. A multiple-definition error often means a non-inline definition lives in a header included by several translation units. Keep declarations in headers and one definition in a source file, or use appropriate inline definitions.

Compile every translation unit you control with the selected sanitizer, then link with clang++ and the same sanitizer flag so its runtime is added. Keep separate object directories for ASan and TSan builds; reusing stale objects can silently remove coverage. -g works with optimization, but optimized locals may be unavailable and stepping may jump between lines. For performance measurements, use a separate optimized binary without sanitizers.

lldb in ten commands

lldb is the debugger that ships with Xcode and clang; gdb is its counterpart on Linux. Build with -g (and -O0 if you want to step line by line), then start the program under the debugger with lldb ./app, or attach to one that is already running and stuck with lldb -p PID.

When any thread hits a breakpoint, lldb stops the whole process, so every thread freezes wherever it is, and thread list marks the ones that hit it with stop reason = breakpoint. With a breakpoint on hits += 1 in a two-thread program, the main thread may be starting another thread or waiting inside join, and one worker has reached the line; the other worker may be at the same line or somewhere else in its loop. By default, a variable watchpoint stops when its value changes, helping answer "who changes this?". Use watchpoint set variable -w write hits to watch writes even when the value stays the same; hardware watchpoint slots are limited.

Diagnosing a hang: get every stack

This program forces a circular wait. A C++20 latch makes each thread hold its first mutex before either tries its second; the bug is the opposing lock order. Sleeps would only make that schedule likely. Press Run: it hangs, and after a few seconds Tandem shows each thread's stack, captured with macOS's sample tool.

An illustrative bt all excerpt has this shape. Addresses, line numbers and library frames depend on the binary; match the mutex addresses to the variables in your own run. In C++17, a mutex-protected arrival count and a condition variable can replace the latch.

Read it from your own frames outward. The main thread is in join(), which is normal. Threads 2 and 3 are both inside std::mutex::lock(), parked in the kernel (__psynch_mutexwait), each at the line of its second lock. The __m= arguments are the addresses of the mutexes they want, and p &accountA and p &accountB tell you which is which: thread 2 waits for accountB (ending in c040) and thread 3 waits for accountA (ending in c000). Each already holds the other one, taken at its first lock: a deadlock from inconsistent lock ordering. The fix is one global order, or std::scoped_lock lock(accountA, accountB);, which acquires both without deadlocking. Remove the demonstration latch when applying either fix: leaving a rendezvous inside the new lock scope would introduce another deadlock.

On Linux the same session is gdb -p PID and thread apply all bt. Without a debugger, macOS has sample PID and Linux has eu-stack or pstack on many systems.

ThreadSanitizer: data races even with correct output

ThreadSanitizer instruments memory accesses in compiled code and observes supported synchronization through instrumentation and runtime interceptors, including mutexes, atomics, thread creation and join. It tracks, for each piece of memory, which threads touched it recently, and whether a happens-before edge orders those accesses. Conflicting accesses from different threads, at least one non-atomic, with no happens-before ordering form a data race, and it reports them even when they did not overlap in time during this run. That is why it catches races that ordinary tests miss.

Read every report in the same five steps:

  1. The kind. "data race" here. Others you will see: "heap-use-after-free" (a thread touched freed memory), "unlock of an unlocked mutex", "destroy of a locked mutex", and "thread leak" (a completed joinable thread was neither joined nor detached).
  2. The two accesses. Which operation (read or write, and how many bytes), which thread, and the stack of each. Your own frames are the ones with your file names: worker() race.cpp:8 twice.
  3. The location. "global 'hits'" names the variable. For heap memory it says which thread allocated the block and where; for a stack variable, whose stack.
  4. Where the threads came from. The creation stacks connect the two accesses to your design: T1 and T2 are the two workers started in main at lines 13 and 14.
  5. The missing edge. Ask: what should have ordered these two accesses? Here the workers have no synchronization ordering their conflicting accesses. Both joins order completion before the main thread reads hits, but do not order the workers against each other. Use a common mutex, or an atomic read-modify-write such as std::atomic<int>::fetch_add for this single counter.

Notice the last line: the program printed 2000, the correct answer. The race is still there, and the report says so. That is the habit to build: correct output alone does not establish race freedom. A clean ThreadSanitizer stress run adds evidence, but still cannot prove that no race occurred or exists.

What ThreadSanitizer does not find

  • Race conditions that are not data races. A check then act made of two separately locked calls is perfectly synchronized at each step and still wrong. ThreadSanitizer is silent; only reasoning and tests catch it.
  • Code that did not run. It is a dynamic tool: a racy path your test never executes is never reported. Run stress tests, many iterations, several times.
  • Deadlocks, on this Mac. Some Linux runtimes can report a "lock-order-inversion (potential deadlock)" when their experimental detector observes a lock-order cycle, even if the run did not hang. On the Mac that runs Tandem that detector is off (TSAN_OPTIONS=help=1 lists detect_deadlocks as false) and switching it on did not produce reports, so here a lock order bug shows up as a hang and a stack dump instead.
  • Uninstrumented code. Memory accesses and custom synchronization inside libraries compiled without -fsanitize=thread may be invisible, hiding races or producing false reports. Intercepted library operations can still be visible; instrumentation is not all or nothing.

The price, from the clang documentation: a typical slowdown of 5 to 15 times and 5 to 10 times more memory. That is why Tandem's harnesses keep their stress runs short.

AddressSanitizer: memory errors with exact stacks

AddressSanitizer (-fsanitize=address) uses shadow memory to track addressability, adds poisoned red zones around many objects, and quarantines freed heap memory. It checks instrumented accesses and intercepts supported library operations; it does not detect every lifetime or bounds error. It reports use after free, heap, stack and global buffer overflows, use of a local after its scope ended, and double free. Linux enables leak detection by default; macOS can enable it with ASAN_OPTIONS=detect_leaks=1 when the installed runtime supports it. The typical slowdown is about 2 times. It cannot be combined with ThreadSanitizer in one build.

Without suitable container annotations, ASan may miss a logical out-of-bounds access that remains inside allocated storage. It does not diagnose ordinary uninitialized-value use; MemorySanitizer is designed for that.

The report answers three questions at once: who read (thread T1, inside the thread function), who freed (the main thread, where message died), and who allocated (construction of message). In threaded code that pattern, freed by one thread and used by another, means a lifetime bug: a view, reference, pointer or [&] capture that outlived its object. The fix is ownership: copy or move the data into the thread ([message]), or join before the object dies. For this latch-controlled demonstration, joining before releasing destroyed would itself deadlock; remove that test gate when changing the lifetime arrangement.

UndefinedBehaviorSanitizer

UBSan (-fsanitize=undefined) checks for many kinds of undefined behavior at run time: signed integer overflow, shifts out of range, null pointer use, misaligned access, invalid enum and bool values, and more. It is cheap, and by default it reports and keeps going (-fno-sanitize-recover=all makes it stop at the first report). It combines with either AddressSanitizer or ThreadSanitizer.

In concurrent code UBSan mostly catches the arithmetic around the threads: an int counter of bytes or requests that overflows under load, or a sequence number that wraps. Choose a wide enough counter and an explicit overflow policy. A 64-bit signed counter can still overflow; unsigned wrap is defined but may break your invariant, and ordinary unsigned overflow is not part of -fsanitize=undefined. UBSan does not detect data races.

A practical setup is two test builds in CI, -fsanitize=address,undefined and -fsanitize=thread,undefined, with stress tests run under both, and a normal optimized build for release. -fsanitize=thread,address fails at once with "invalid argument '-fsanitize=address' not allowed with '-fsanitize=thread'".

How Tandem runs your C++

Every Run button and every automated check on this site compiles your code with Apple clang as clang++ -std=c++20 -O1 -g -fsanitize=thread -fno-omit-frame-pointer -pthread -Wall, inside a sandbox with no network. ThreadSanitizer is told to keep running after a report, so multiple reports can be collected in one run, subject to detection and deduplication limits, and its reports appear next to your output. A program that runs longer than the time limit is stopped and every thread's stack is shown, which is how the deadlock demos in these lessons display.

So when a problem says "ThreadSanitizer must stay quiet", it means the tool reported no data race in the executed, instrumented paths. Suppressions, missing instrumentation and detector limitations can still hide problems. Combine that with tests that check the exact results, and run them more than once.

Common mistakes

  • Debugging a hang with print statements. Prints change the timing and often make the bug vanish. Attach a debugger and read every stack.
  • Running ThreadSanitizer once and calling it done. It reports only what executed. Use stress loops and run them several times.
  • Reading a clean report as "thread-safe". Check-then-act races and logic errors pass ThreadSanitizer. So do deadlocks on this Mac.
  • Combining -fsanitize=thread with address. It does not build. Make two builds.
  • Forgetting -g. Reports and backtraces lose file names and line numbers.
  • Testing only -O0 builds. Some races (a loop on a plain flag, for example) only misbehave once the optimizer keeps values in registers. Test optimized builds too.
  • Ignoring warnings. An unnamed lock_guard locks only until the semicolon; the vexing parse creates an empty lock. Name the guard and check its lifetime; warning availability depends on the library.

In the interview

Debugging rounds hand you broken code and a clock. Interviewers watch your method: do you reproduce, gather evidence, form a hypothesis from the evidence, and verify the fix, or do you change things until the symptom moves? At Rubrik the code must also compile and run at the end, so make small, deliberate edits and rebuild often.

First I'd make it fail reliably, with a stress loop if needed. For a hang, I attach a debugger and dump every thread's stack: two threads each waiting on a mutex the other holds is a lock order deadlock, and a condition-variable wait with no remaining notifier leads me to inspect the predicate, shutdown state and notification paths. For wrong results, I run the stress test under ThreadSanitizer, which gives me both conflicting accesses with their stacks, so a data race is usually quick to fix.
A clean ThreadSanitizer run tells me no data race was reported in the instrumented paths that ran. It doesn't prove the logic is right, so I still check invariants and exact results in the test.

Follow ups to expect: "How would you find this without a debugger?" (sample on macOS, eu-stack or pstack on Linux, or a watchdog that dumps state on timeout), "Why didn't your tests catch it?" (the bad interleaving is rare; stress and sanitizers make it likely and visible), and "What does ThreadSanitizer cost?" (roughly 5 to 15 times slower, so it runs in CI, not in production).

Senior depth

Catch lock discipline at compile time. Clang's thread safety analysis checks annotations such as guarded_by against the locks you hold. With libc++, build with -Wthread-safety -D_LIBCPP_ENABLE_THREAD_SAFETY_ANNOTATIONS, and a member declared int balance_ __attribute__((guarded_by(m_))); read without the lock produces "reading variable 'balance_' requires holding mutex 'm_'". It turns the "guarded by" comments in this course into checked facts.

Tune ThreadSanitizer. TSAN_OPTIONS controls it at run time: halt_on_error=1 stops at the first report, history_size adjusts retained access history with version-dependent semantics, and a suppressions file silences known issues in third-party code. Check the installed runtime with TSAN_OPTIONS=help=1 ./app_tsan; review suppressions because they can hide real bugs. Do not assume option ranges match a different runtime release.

When the bug is rare. On Linux, rr records an execution and replays it deterministically, so a once-in-a-thousand hang can be debugged backward. Core dumps (ulimit -c unlimited) let you inspect a crashed process after the fact with all its threads.

Key takeaways

  • Build threaded code with -std=c++20 -g -Wall -Wextra -pthread, and keep separate ThreadSanitizer and AddressSanitizer test builds, each with UBSan.
  • For a hang, attach and print every thread's stack (bt all in lldb, thread apply all bt in gdb): mutex waits in a cycle mean deadlock, a lone condition-variable wait calls for checking its state predicate and all progress paths.
  • ThreadSanitizer reports data races with both stacks even when the output looks right; read kind, accesses, location, thread origins, then find the missing happens-before edge.
  • AddressSanitizer's "freed by thread A, used by thread B" is a lifetime bug: fix ownership or join earlier.
  • A clean sanitizer run covers only what executed, and ThreadSanitizer never sees check-then-act logic races.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Which pair of sanitizers cannot be enabled in the same build?
Why. ThreadSanitizer and AddressSanitizer both take over memory allocation and shadow memory in incompatible ways, and clang rejects the combination. UBSan combines with either, so the usual setup is two test builds: address plus undefined, and thread plus undefined.
A stress test runs cleanly under ThreadSanitizer, with no reports. What does that establish?
Why. ThreadSanitizer is dynamic: it checks what ran. It never flags a check-then-act made of separately locked steps, because each access is synchronized, and on this Mac it does not report lock order problems. A clean run is evidence, not proof: missing instrumentation, suppressions and detector limitations can hide actual races even on exercised paths. It establishes neither race freedom nor progress nor correct compound operations.
A ThreadSanitizer report says "Write of size 8 ... by thread T3: #0 Cache::put cache.cpp:41" and "Previous read of size 8 ... by thread T2: #0 Cache::size cache.cpp:57", with "Location is heap block of size 64". Both accesses name the same address, put holds the cache mutex, and size does not. Which fix preserves concurrent use and follows that locking discipline?
Why. The report shows a write in put and an unsynchronized read in size of the same 8 bytes. The missing happens-before edge is the lock: if both take the same mutex, unlock in one thread synchronizes with lock in the other. const does not synchronize anything, joining T2 before starting T3 would order the accesses, but violates the required concurrent-use contract, and volatile is not a threading tool in C++.
A program hangs. Which lldb command shows the call stack of every thread at once?
Why. bt all (equivalent to thread backtrace all) prints every thread's stack, which is the thread dump you need for a hang. bt shows only the selected thread, thread list shows one line per thread, and frame variable shows locals of the selected frame. In gdb the equivalent is thread apply all bt.
bt all on a hung program shows thread 2 in std::mutex::lock() called from transfer() at line 30, and thread 3 in std::mutex::lock() called from transfer() at line 30 too. Code and mutex addresses confirm that thread 2 holds A while waiting for B, and thread 3 holds B while waiting for A. What is the diagnosis?
Why. The established A-to-B and B-to-A ownership dependencies form a circular wait, here from transfer(a, b) and transfer(b, a) locking their arguments in order. Two blocked stacks alone would not establish that cycle. A lost wakeup involves waiting for a condition; livelock involves ongoing activity without progress, and these mutex operations are not themselves a data race. Fix with a global lock order or std::scoped_lock over both mutexes.
AddressSanitizer reports a heap-use-after-free: READ by thread T2 inside a lambda, "freed by thread T0" in a destructor called from main. What is the most likely cause in threaded code?
Why. Freed by one thread and read by another is a lifetime bug: something non-owning crossed the thread boundary. Fix the ownership (capture by value, move the data in, use a shared_ptr when lifetimes really are shared) or make sure the thread is joined before the object dies. A counter race or allocation failure does not explain a recorded access to freed storage, and a live owning string capture would keep its own storage valid. Copying a view by value would not provide that ownership.
Two threads each call deposit(1) on the same account, whose plain int balance_ starts at zero. Main joins both, then prints the balance under the mutex. With no other synchronization, what output is guaranteed?
Why. The unnamed guard locks and then unlocks at the semicolon, before the increment. The two conflicting increments are not ordered by those earlier lock scopes or by main's later joins. This is undefined behaviour, so even the apparently plausible range of 1 or 2 is not a guarantee. Each call acquires the mutex only once, so no self-deadlock is implied. This libc++ warns about the discarded guard; the fix is std::lock_guard<std::mutex> lock(m_);, whose lifetime includes the update.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
You get this report from a C++ service's test run. Explain the bug and the fix.
Model answer

The report identifies a one-byte non-atomic access, consistent with a plain bool; I would confirm the declaration because size alone does not prove the type. The main thread writes it in stop() while the worker thread reads it in its loop in run(), and nothing orders the two accesses, so it is a data race, which is undefined behavior. In practice the compiler may keep the flag in a register and the worker may never see the write, so the worker might never stop.

Fix: make it std::atomic<bool> stopRequested{false}; and use store(true) and load(); the default sequentially consistent ordering also makes the main thread's earlier writes visible to the worker once it sees the flag. If the worker sleeps on a condition variable between iterations, instead keep the flag as a plain bool guarded by the same mutex and notify after setting it, or use std::jthread with a std::stop_token and a cancellation-aware wait. An ordinary condition_variable::wait does not wake just because stop was requested. Then rerun the test under ThreadSanitizer to show the report is gone.

Explain
The interviewer says: "This service hangs about once every 50 runs. Walk me through how you would find the cause."
Model answer

First I make it fail more often: run it in a loop, add load, and if needed shrink sleeps or timeouts so the bad interleaving gets more chances. I make sure the build has -g so stacks have line numbers. When it hangs, I do not kill it. I attach a debugger, lldb -p PID and bt all (or gdb -p PID and thread apply all bt), and read every thread's stack. That snapshot narrows the bug class; I confirm it against ownership, predicates and the code. Two or more threads blocked inside mutex::lock, each holding a lock another wants, is a deadlock, and the frames give me the two code paths and their lock order. A thread parked in a condition variable wait while the threads that should notify it are gone or idle suggests a lost wakeup, missing notify or incomplete shutdown protocol, so I check that every state change happens under the mutex, every wait has a predicate, and every transition that can satisfy a waiting predicate notifies the relevant waiters. If nothing is blocked but the program is spinning, it is a livelock or a busy loop. After the fix, I rerun the stress loop many more times than the original failure rate, including under ThreadSanitizer, before calling it fixed.

Write code
Write the commands to build main.cpp and queue.cpp into two test binaries: one with ThreadSanitizer and one with AddressSanitizer, both also with UndefinedBehaviorSanitizer, with good stack traces and warnings on.
Model answer

The sanitizer flag must reach both the compile and the link step; with one command that does both, it does. -O1 keeps the run fast while leaving stacks readable, -g gives file and line numbers, and -fno-omit-frame-pointer improves stack unwinding; inlining and tail calls can still remove frames. ThreadSanitizer and AddressSanitizer need separate builds because they cannot be combined.

How a senior would say it
I would preserve the hung process and collect every thread's stack before changing the code. With debug symbols available, I attach LLDB and run bt all. I start from my application frames and identify what each thread needs in order to progress. If two threads are blocked acquiring mutexes, I map the addresses to objects and check who owns each lock. Two blocked threads alone do not prove deadlock; a cycle of ownership dependencies does. If a consumer is parked on a condition variable, I inspect its protected predicate, the producer's state transitions, notification paths and shutdown state. A finished producer and a true predicate can expose a missed-notification bug. Next I make a small reproducer using explicit synchronization to control the relevant ordering, instead of assuming a sleep forces it. I fix the lock order or waiting protocol, then rerun that reproducer and a stress test under ThreadSanitizer. I also check exact results and completion, because a clean race report says nothing about whether the service makes progress.

Likely follow up: What would you check if every sampled thread is running rather than blocked?

Out loudabout 60 s
"The counter prints the right answer, but ThreadSanitizer reports a race. Which evidence do you trust, and how do you fix it?"
What a strong answer covers
  • Correct output does not make a C++ data race defined
  • Read both conflicting accesses, the address and thread creation stacks
  • Determine which synchronization edge is missing; joining both does not order the workers
  • Use atomic read-modify-write for a counter or a shared mutex for a compound invariant
  • A clean rerun adds evidence but cannot prove correctness or race freedom
How a senior would say it
I take the race report seriously. Correct output does not make a C++ data race safe; the program has undefined behaviour even when this execution appears successful. I read both access stacks, check that they name the same storage, and identify the missing happens-before edge. Joining both workers lets main safely observe their completion, but does not order their earlier writes against each other. For a single hit counter I would use an atomic read-modify-write, such as fetch_add. If the update must preserve an invariant across fields, I would put that whole operation under one shared mutex. Then I rerun the reproducer and check the expected count as well as the reports. A clean run adds evidence, but missing instrumentation, suppressions and untested paths can hide bugs. Separately locked check-then-act operations can also be logically wrong without a data race.

Likely follow up: Would an atomic load followed by an atomic store implement the same counter increment correctly?

Out loudabout 60 s
"How would you set up sanitizer builds for a C++ service, and investigate memory freed by main but read by a worker?"
What a strong answer covers
  • Build separate TSan plus UBSan and ASan plus UBSan binaries
  • Instrument each controlled translation unit and pass sanitizer flags at link time
  • Keep debug symbols and useful stack unwinding, with separate object directories
  • Use the ASan read, free and allocation stacks to reconstruct lifetime
  • Fix ownership or join before destruction, then test without relying on a timing delay
How a senior would say it
I would keep two test builds: ThreadSanitizer with UBSan, and AddressSanitizer with UBSan. ThreadSanitizer and AddressSanitizer cannot share one binary. I compile each translation unit I control with the chosen instrumentation, debug symbols and frame pointers, then link through the C++ compiler driver with the same sanitizer flags. Separate object directories prevent stale objects from silently losing coverage. For a use-after-free report, I read the access stack, the freeing stack and the original allocation stack. If a worker captured a string view while main owned the string, capturing that view by value copied only the pointer and length. It did not extend the string's lifetime. I would move or copy the owning string into the task, or join before destroying it. Finally I rerun a controlled lifetime test under ASan. Adding a sleep changes timing and cannot repair ownership.
