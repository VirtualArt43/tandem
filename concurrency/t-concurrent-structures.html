Why is HashMap not thread-safe, and how does ConcurrentHashMap work since Java 8?
Model answer

HashMap under concurrent writes: updates can lose entries or corrupt structure; a concurrent reader can see inconsistent state. Java 7 resize races could even form cycles. Safely publish read-only maps and synchronize conflicting access when mutations are possible.

ConcurrentHashMap since Java 8, describing OpenJDK details, not a fixed API layout:

  • A single table of bins, read with volatile semantics.
  • Put into an empty bin: a CAS, no lock.
  • Put into a non-empty bin: synchronized on that bin's first node, then update or append. Long bins can treeify: the threshold constant is 8 and minimum table capacity is 64.
  • get does not wait for the bin monitor: a volatile read of the bin head, then a walk over nodes whose value and next fields are volatile.
  • Size: a base count plus striped counter cells, the same idea as LongAdder.
  • Resize: several threads help move bins; a moved bin holds a forwarding node that sends readers to the new table.
  • Atomic compound operations: putIfAbsent, compute, computeIfAbsent, merge, atomic per key; empty-bin operations may use CAS or a reservation node, while other updates use bin synchronization.

Java 7 used segments, defaulting to concurrency level 16. Databricks and Atlassian reports support this topic.

Likely follow up: "Is get guaranteed to see the latest put?" Retrieval reflects the most recent completed update before it begins, or an overlapping update. A non-null retrieval also establishes happens-before from the update it observes; iteration and size are only weakly consistent.

2Coreconcurrenthashmapjava
Why does ConcurrentHashMap not allow null keys or values?
Model answer

Ambiguity. In a HashMap, get(k) returning null can mean "absent" or "mapped to null", and single-threaded code tells them apart with containsKey(k). In a concurrent map, another thread can add or remove k between those two calls, so the answer cannot be trusted. On top of that, the atomic methods use null to mean "absent": putIfAbsent returns null when it inserted, and a computeIfAbsent function that returns null means "do not insert".

Forbidding nulls keeps every method's result unambiguous; Doug Lea, the class's author, has given this reason publicly. ConcurrentSkipListMap has the same rule, and the legacy Hashtable never allowed nulls either.

When you need to cache "known to be missing" (negative caching), store a sentinel object or an Optional instead of null.

Likely follow up: "What does computeIfAbsent return if the function returns null?" It records no mapping and returns null.

3Seniorconcurrenthashmapjava
What does computeIfAbsent guarantee on a ConcurrentHashMap, and what can go wrong?
Model answer

Guarantees: check-and-insert is atomic per key; the mapping function is invoked once by a given invocation when absent. A successful non-null mapping is shared while present; null, an exception, removal or expiry allows later recomputation. That makes it the standard tool for per-key initialization: counters, per-key locks, caches.

Pitfalls:

  • The function can run while a bin is reserved or locked. A slow function (I/O, a remote call) blocks every caller of that key, other keys that share the bin, and can hold up resizing. Keep it short, or store a future as the value and do the slow work outside.
  • The function must not modify the same map. A recursive computeIfAbsent on the same map could loop forever in Java 8; since Java 9 it throws IllegalStateException ("Recursive update") when detected.
  • If the function throws, nothing is inserted and the exception propagates to the caller.
  • On a plain HashMap, computeIfAbsent is not atomic at all.
  • Do not infer that every present-key lookup avoids synchronization; implementation fast paths vary. The API promise is per-key atomicity, not a global once-ever factory call.

Likely follow up: "The load fails. What then?" Complete all waiters exceptionally and remove only that exact future, as above. Silent-discard executors would strand waiters. CallerRunsPolicy can run loading inline, which is why submission also stays outside the map callback.

4Coreconcurrent-collectionsjava
What do size(), isEmpty() and other whole-map reads mean on a ConcurrentHashMap while other threads write?
Model answer

They are estimates. size() adds up striped counters without stopping writers, so exactness is guaranteed when updates have quiesced; prefer mappingCount(), which returns a long. isEmpty() can be stale the moment it returns. Summing all values, or any aggregate over the map, gives a result that may never have existed at a single instant, because writes interleave with the traversal.

So never make a correctness decision on these: if (map.size() < LIMIT) map.put(k, v) is check-then-act and overshoots under load. Keep a separate counter that is updated atomically with the decision (an AtomicInteger with a CAS loop, or a semaphore), or take one lock over the whole structure.

Other collections behave similarly or worse: ConcurrentLinkedQueue.size() walks the whole list and is approximate; CopyOnWriteArrayList.size() is exact for the snapshot it reads. For a consistent view of everything, you need a lock over all writers, a copy-on-write snapshot, or an immutable versioned structure.

Whole-map reads on a concurrent map are for monitoring, not for decisions.

Likely follow up: "How do you enforce a maximum size, then?" Reserve capacity before insertion; return it on duplicate insertion or failure, and release exactly once on successful removal. Every mutation must follow that lifecycle; a separate approximate counter is insufficient.

5Corecppmaps
C++ has no concurrent hash map in the standard library. How do you build a thread-safe map, and which API traps must you avoid?
Model answer

Options, simplest first: an std::unordered_map plus one std::mutex; a std::shared_mutex if reads dominate and never mutate; shards, each with its own mutex and map, chosen by hash; or a library map such as Intel TBB's concurrent_hash_map or folly's ConcurrentHashMap. (Abseil's fast maps are not thread-safe.)

The traps are in the API, not the locking:

  • Do not return unguarded references, pointers or iterators into the map. Once the lock is released, erase can dangle them and concurrent mutation can race. Rehash invalidates iterators, but does not invalidate references or pointers to surviving unordered_map elements. Return copies, such as std::optional<V>, or provide a scoped accessor or a short callback under the lock, with no escaped references.
  • operator[] inserts: a "read" that writes.
  • No check-then-act across calls: offer atomic operations (insert_if_absent, update(key, fn)) instead of contains followed by insert.
  • Locked callbacks must not reenter the map, retain references, block or acquire locks in a conflicting order. If a callback throws after mutation, the lock releases but changes are not rolled back.
  • Whole-map operations (size, clear, snapshot) must lock every shard in a fixed order.

Likely follow up: "Why not std::shared_mutex everywhere?" It costs more than a plain mutex, so for short critical sections a plain mutex often wins; measure.

7Coresynchronized-collectionsjava
Why is Collections.synchronizedMap (or Hashtable) usually worse than ConcurrentHashMap, and when is it still the right choice?
Model answer

A synchronized wrapper wraps every method in one mutex: all readers and writers serialize, and even two get calls contend. Compound actions still need the caller to lock the wrapper, and iteration requires holding that lock for the whole loop or you risk ConcurrentModificationException. Hashtable is the legacy version of the same idea.

ConcurrentHashMap has lock-free reads, per-bin locking for writes, atomic compound methods, and iteration that needs no lock and never throws ConcurrentModificationException.

The synchronized wrapper still wins when:

  • You need an atomic operation over several keys, or a consistent snapshot. You can hold the wrapper's lock across many calls; ConcurrentHashMap offers no multi-key atomicity.
  • You need semantics no concurrent map has, such as a LinkedHashMap in access order for a small LRU.
  • You need null keys or values. A wrapper around HashMap permits them; Hashtable does not.
  • Contention is low and simplicity matters more.

Likely follow up: "Why lock on stock and not on a separate lock object?" Because the wrapper's methods synchronize on the wrapper itself; any other lock would not exclude them.

8Seniorpriority-queues
How do you make a priority queue thread-safe, and why is a concurrent heap hard?
Model answer

The standard answers:

  • Java: PriorityBlockingQueue, a binary heap under one ReentrantLock; take blocks while empty, put never waits for capacity but may wait for the internal lock, and its iterator is not in priority order. DelayQueue adds time.
  • A skip list as a priority queue: ConcurrentSkipListSet with pollFirst() uses a concurrent skip list with expected O(log n) basic operations; the API does not promise every operation is lock-free; elements must be unique, so key them by (priority, sequence number).
  • C++: std::priority_queue with a mutex and a condition variable, or TBB's concurrent_priority_queue.

The C++ example requires copyable values and nonthrowing heap comparisons/moves; add closure and timed waits for production. It is a max-heap with std::less, unlike Java's min-priority default.

Why a concurrent heap is hard: every removeMin touches the root, and insertion or removal may sift along O(log n) nodes, so fine-grained locking is intricate and the root is a permanent hotspot. Under high contention, systems relax strict ordering instead: several heaps where inserts go to a random one and removals take the better of two random tops (the MultiQueue idea), or per-thread queues with stealing. Use approximate priority only if the scheduler contract permits it. Never mutate a queued element's priority.

Likely follow up: "Equal priorities must come out in FIFO order. How?" A heap does not preserve insertion order; add a sequence number as the tie breaker.

9SeniorpoolsdesignSalesforceLinkedIn
Design a thread-safe connection pool: borrow with a timeout, return, and close.
Model answer

Guard an idle deque, a closed flag and total with one mutex and condition. The invariant is total = idle + borrowed + reserved-for-creation, bounded by the maximum. Salesforce and LinkedIn reports include this pool design.

Borrow: compute one monotonic deadline, then under the lock reject closure, reuse an idle connection, or reserve a creation slot. If full, wait in a predicate loop using the remaining budget. Create and validate outside the lock, with the remaining deadline passed into network operations. On failure, roll back the reservation and notify a waiter.

After creation, reacquire the lock and recheck closure and expiry before handing out the connection. If either won the race, decrement total, notify, and close the new connection outside the lock. Otherwise the handoff under the lock is the borrow's linearization point; later closure may coexist with that already borrowed lease.

Return: an idempotent lease guard prevents duplicate returns. Under the lock, put a healthy connection back, or decrement total if closed or broken; signal capacity. Perform physical close outside the lock. Close: mark closed, detach idle connections, adjust the count and wake all waiters, then close detached resources outside the lock. Borrowed connections close on return.

Likely follow up: "Can a semaphore replace the condition?" It can bound borrowers, but does not itself solve duplicate return, cancellation, connection creation, or close races.

10Corecopy-on-writejava
When is CopyOnWriteArrayList the right choice, and what does it cost?
Model answer

Readers read the current array through one volatile reference, with no lock. Writers take a lock, copy the whole array, modify the copy, and publish it by swapping the reference. So reads never block, and every iterator walks a fixed snapshot: it never throws ConcurrentModificationException because of concurrent writes and never sees later structural changes (copy-on-write).

Costs: most content-changing writes copy O(n) references and allocate an array; writes are serialized; readers can be slightly stale (they see the snapshot from when they started); and iterator.remove() is unsupported.

Right for small, read-mostly collections that change rarely: listener and observer lists (iterated on every event, modified on subscribe), configuration lists, routing tables. Wrong for frequent writes or large lists: adding to a 100,000 element list copies 100,000 references each time.

Snapshots copy references, not mutable element state; a removed listener may still receive an event from an existing snapshot.

The same idea elsewhere: an immutable configuration object behind an AtomicReference that is replaced wholesale; in C++, a std::shared_ptr<const T> swapped under a short lock (or std::atomic<std::shared_ptr<const T>> in C++20); RCU in the Linux kernel.

Likely follow up: "Two writers update the snapshot at once. Is anything lost?" Not with CopyOnWriteArrayList, whose writers share a lock. With a hand-rolled AtomicReference, a plain set loses one update; use updateAndGet or a CAS loop.

11CoreiterationcmeApple
What happens when one thread iterates a collection while another modifies it?
Model answer

It depends on the collection:

  • HashMap, ArrayList and other non-thread-safe Java collections: a fail-fast iterator may throw ConcurrentModificationException, on a best effort basis only. It is a bug detector, not a guarantee: with a data race you can also get silently wrong results.
  • Synchronized wrappers: the same, unless you hold the wrapper's lock for the entire iteration.
  • Concurrent collections: a weakly consistent iterator (ConcurrentHashMap, ConcurrentLinkedQueue, ConcurrentSkipListMap) or a snapshot iterator (CopyOnWriteArrayList): safe against concurrent structural updates and not fail-fast. Weak iterators may reflect changes; snapshot iterators never reflect later structural changes. An iterator itself need not support sharing between threads.
  • C++ containers: conflicting element accesses or unsynchronized structural mutation can cause undefined behavior. Concurrent access to distinct existing elements can be allowed, with no structural mutation; vector<bool> is a notable exception; and iterator invalidation (a std::vector reallocating, an std::unordered_map rehashing) bites even in single-threaded code.

For a consistent traversal, lock throughout, copy under the lock, or use an immutable snapshot.

Apple asked about concurrent BST iterators, then writers. Safely published readers alone are fine; writers require a shared locking protocol or persistent tree snapshots.

Likely follow up: "Does Collections.synchronizedList make iteration safe?" No; its documentation requires you to synchronize on the list manually while iterating.

12Seniorlinearizabilitycorrectness
What is linearizability?
Model answer

linearizability (Herlihy and Wing, 1990) is the standard correctness condition for concurrent objects: every operation appears to take effect instantaneously at some point, its linearization point, between its call and its return, and the resulting order respects real time: if operation A returned before operation B was called, A comes first.

It lets clients treat a concurrent object as if it were sequential. Compare:

  • Sequential consistency (in the memory model sense) only requires some interleaving consistent with each thread's program order; it ignores real time across threads.
  • Serializability (databases) is about transactions of many operations and also ignores real time; strict serializability adds it back.

Examples of linearization points: inside the critical section for a lock-based queue; the successful CAS for a lock-free stack; the bin update for ConcurrentHashMap.put. ConcurrentHashMap's per-key operations are linearizable; its size() and iteration are not, they are weakly consistent.

When asked "is your structure correct?", I name the linearization point of each operation and argue that the state changes exactly there.

Likely follow up: "Is a cache that sometimes returns a slightly stale value linearizable?" It violates linearizability if it returns an older value after a completed update with no overlapping update explaining it. Concurrent reads may legitimately see the old value. Staleness alone does not prove eventual consistency; convergence needs its own guarantee.

13Seniorring-bufferlock-freeRubrik
Build a queue inside a fixed buffer with no allocation. How do you make it safe for one producer and one consumer without locks, and what changes with many?
Model answer

A ring buffer: an array of N slots and two unsigned logical counters that wrap modulo their integer range, head (next to read) and tail (next to write). The slot index is counter % N, or counter & (N - 1) when N is a power of two. Empty when head == tail; full when tail - head == N.

One producer, one consumer: only the producer writes tail and only the consumer writes head, so no CAS is needed. The producer fills the slot, then publishes tail with a release store; the consumer reads tail with an acquire load, reads the slot, then frees it by publishing head with a release store. The producer also acquires head before reusing a slot. Unsigned subtraction handles wrap with bounded distance; use a positive power-of-two capacity. Here 128-byte alignment is a target-tuned padding choice. Use a nonblocking, nonallocating value type such as int.

Many producers or consumers race for the same slot: need a capacity-safe reservation protocol and per-slot sequence numbers for publication and reuse. Naively advancing a counter exposes unfilled slots. Some bounded MPMC algorithms can stall behind a delayed producer and are not formally lock-free. Or simply use a mutex with two condition variables. Rubrik asked for fixed-buffer FIFO, multithreaded access, then two queues sharing storage.

Likely follow up: "Two queues in one buffer with minimal waste?" Carve the buffer into fixed-size blocks on a shared free list, and let each queue be a linked list of blocks.

14Seniorskip-listjava
When would you use ConcurrentSkipListMap, and how does it work?
Model answer

Use it when you need a sorted concurrent map: range queries (subMap, headMap, tailMap), floorKey and ceilingKey, ordered iteration, or data keyed by time or score (schedulers, order books, leaderboards).

OpenJDK 21 uses CAS-based skip-list algorithms; the public API promises concurrent safety and expected complexity, not universal lock-free progress. The structure is a sorted linked list with sparse index levels. Random promotion gives expected O(log n) basic operations. CAS links nodes; deletion logically removes the value before marker-assisted unlinking.

Skip-list updates are local; tree rebalancing needs more coordination.

Trade-offs against ConcurrentHashMap: expected O(log n) rather than expected O(1), with more pointer chasing. OpenJDK 21 full-map size() uses a LongAdder, not a full traversal; range-view sizes can traverse. Counts and range iterations are not atomic snapshots. ConcurrentSkipListSet is the set version. C++ has no standard equivalent: use a std::map with a std::shared_mutex, or a library.

Likely follow up: "How would you build a thread-safe leaderboard with it?" Key by (score, player id), with a second map for current scores. Remove/insert across the two maps is not atomic: accept documented gaps, or coordinate all updates and snapshot readers with one lock or immutable version. Per-player writer locks alone cannot hide gaps from range readers.

15Coreconcurrent-collectionschoosing
Pick a structure for each: a listener list, a work queue between threads, a per-key counter map, a sorted index, and a configuration shared by all threads.
Model answer
  • Listener list: CopyOnWriteArrayList. Iterated on every event and rarely changed; snapshot iteration lets listeners unsubscribe during a notification.
  • Work queue: a bounded blocking queue (ArrayBlockingQueue, or LinkedBlockingQueue with an explicit capacity). Workers block on take, and producers feel backpressure on put. In C++, a deque with a mutex and two condition variables.
  • Per-key counters: ConcurrentHashMap<K, LongAdder> with computeIfAbsent(k, x -> new LongAdder()).increment(). For metrics only: sum() is not an atomic snapshot, and removal needs a lifecycle protocol. In C++, use sharded counters with protected entry lifetimes.
  • Sorted index: ConcurrentSkipListMap. In C++, std::map with a std::shared_mutex.
  • Shared configuration: an immutable object in a volatile field or an AtomicReference, replaced wholesale on reload. In C++, copy a std::shared_ptr<const Config> under a short mutex, or use atomic shared-pointer operations consistently.

The rule behind the picks: choose by access pattern (the read to write ratio, whether consumers must wait, whether order matters, whether you need snapshots), and say which consistency you are getting (weakly consistent iteration, approximate size, stale snapshots).

I avoid Hashtable, Vector and the synchronized wrappers in new code unless I need multi-key atomicity: one lock for everything, and iteration still needs external locking.

Likely follow up: "And a cache?" Not a raw ConcurrentHashMap, which never evicts: a real cache library such as Caffeine in Java, or a sharded LRU in C++.

16Seniorconcurrenthashmapbugs
Your ConcurrentHashMap<String, List<String>> still loses data under load. Why?
Model answer

The map is thread-safe; the values are not. Typical code is map.computeIfAbsent(k, x -> new ArrayList<>()).add(v). computeIfAbsent safely returns one shared ArrayList per key, but add on that list runs outside any lock, from many threads: lost adds, ArrayIndexOutOfBoundsException while the list grows, a corrupt size. map.get(k).add(v) has the same race, and map.put(k, newList) can replace a list that another thread is still adding to.

Fixes:

  1. Mutate inside compute, which serializes remapping for that key: map.compute(k, (key, list) -> { if (list == null) list = new ArrayList<>(); list.add(v); return list; }). But readers that later get(k) and iterate the list still race with writers.
  2. Thread-safe values: computeIfAbsent(k, x -> new CopyOnWriteArrayList<>()) or use a map whose value type is ConcurrentLinkedQueue<String>, since it is not a List.
  3. Immutable values replaced atomically, so readers always see a complete list:
A concurrent map makes the map's structure safe; anything I hang off it needs its own safety story.

Likely follow up: "What does the immutable version cost?" An O(n) copy per add, fine for short lists; for long ones, consider concurrent values. Even then, adding to an old value after its mapping is removed does not update the new mapping: coordinate removal with value mutation when that matters.
