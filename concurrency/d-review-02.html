Code review set 2: pools, caches and shutdown

Ten more code reviews: rate limiters, pools, caches, one shot events and watchdogs, each with several real bugs.

The second review set uses the kinds of classes interviewers hand over in debugging rounds and low level design follow ups: a rate limiter, a connection pool, an LRU cache, a metrics flusher, a ledger, a one shot result, a per user limit, a thumbnail pool, feature flags and a watchdog. Read each one as a reviewer who must sign off on it. Several options are usually right, and some wrong options describe things that look suspicious but are actually fine. Every snippet compiles, and the central failures (a lock left held, a self deadlock, a timeout that does not time out) were reproduced by running them.

10 questions, 25 minutes. Answers and explanations stay hidden until you submit or the clock runs out. Multi answer questions say so; pick every option that is true.

Why. An access-ordered LinkedHashMap.get() can move the entry in the linked list, so two calls under a shared read lock can mutate that list concurrently. Acquire the write lock from the start, or use a plain lock: neither get nor put then has a shared read-only path. Why. The POST runs under m_, so callers of inc() wait for it. Move a batch out under the lock and perform the POST after unlocking, with a policy for failed batches. Shutdown has two delays: the destructor may first wait for an in-flight POST to release m_, and join() may then wait for the flusher's next sleep to end. Why. isSet() reads a plain flag without synchronization, so a polling thread has no visibility guarantee. Why. newFixedThreadPool(8) uses eight workers and an unbounded work queue; queued closures retain their images, so sustained overload grows memory and latency. Use a bounded queue and a deliberate rejection or backpressure policy. A cached pool also reuses idle workers; it does not necessarily create one thread per submission. The shown close() calls shutdown(), which rejects new work but lets accepted tasks finish without waiting for them. Use awaitTermination, checking its result, or the Java 21 executor's own waiting close(). The interruption option is a hypothetical change to shutdownNow(): if its interrupt makes the sleep throw, the empty catch skips resize and returns the original image as a normal result. sleep is interruptible, and shutdownNow() alone does not mark that running future cancelled. C++ onlysubmit is called for every upload; the service is destroyed on shutdown. Which statements are true? Select all that apply. Select all that apply
Why. The task deque has no admission bound, so sustained overload retains arbitrarily many images until resources run out. close() wakes workers, but the destructor never joins them: destroying a joinable std::thread calls std::terminate even if its function has already returned. Join all workers in the destructor body while their shared state is still alive. Workers test closed_ before taking a queued task, so shutdown abandons pending tasks; a draining design exits only when closed and empty and rejects new submissions after close.
