Why is fsync expensive, and what do write and flush on their own guarantee?
Model answer

Data passes through three layers of buffering on its way to disk:

  1. Your process's buffer (BufferedOutputStream, std::ofstream, FILE*). flush() only moves this buffer into the kernel with a write system call.
  2. The kernel page cache. When write returns, the data is in kernel memory: it survives a crash of your process and other processes can read it, but a power cut or kernel crash loses it.
  3. The device, which often has its own volatile write cache.

The fsync call pushes the file's dirty pages and metadata to the device and asks it to flush its cache, returning only when the data is on stable storage (if the device honors flushes). fdatasync skips metadata not needed to read the data back, so it is a little cheaper. A new file also needs an fsync of its directory.

The cost is real device I/O. As orders of magnitude: tens of microseconds to a few milliseconds on SSDs, 5 to 10 ms or more on spinning disks, against a few microseconds for a write into the page cache. One fsync per event caps a writer at roughly 1,000 events per second at 1 ms each.

APIs: Java FileChannel.force(true), or force(false) for data only. C++ has no standard fsync, so call POSIX ::fsync(fd). On macOS, fsync does not flush the drive's cache; fcntl(fd, F_FULLFSYNC) does.

Likely follow up: "Is O_DIRECT durable?" No. It bypasses the page cache, but the data can still sit in the device's cache; durability still needs O_DSYNC or fsync.

2Coreevent-writergroup-commitfuturesDatabricks
Many threads call appendEvent(bytes), which must return only once the event is durable on disk. Walk through your design.
Model answer

The path interviewers expect, step by step:

  1. One mutex: lock, write, fsync, unlock. Correct and ordered, but every caller pays a full fsync one after another, so throughput is about one event per fsync.
  2. A single writer thread that owns the file, fed by a queue. Producers no longer fight over the file, but nothing improves while each event still gets its own fsync.
  3. Group commit: the writer takes everything queued, writes it all, and calls fsync once for the whole batch.
  4. A future per event: appendEvent enqueues the bytes with a promise and waits on it; the writer completes every promise in the batch after the fsync returns, or fails them all if the write or fsync failed.

Then bound the queue for back-pressure and add flush and close. Under load, batches grow by themselves, so throughput rises with load while the per-event latency stays at about one or two fsyncs. The catch here only fails the current batch; the next question explains why a real writer must also stop using the file after a failed fsync.

Likely follow up: "Why one writer thread instead of a lock around the file?" It turns contention into batching: concurrent producers become one bigger write and one fsync, which a plain "lock, write, fsync, unlock" cannot do. You can batch under a lock too (leader and follower group commit, where whoever holds the lock fsyncs for everyone queued behind it, as databases do), but the single writer is simpler to get right and keeps the file single-threaded.

3SeniordurabilityfsyncrecoveryDatabricks
What exactly can appendEvent promise about durability, and what do you do when fsync fails?
Model answer

Once its future completes, the event's bytes were written and an fsync covering them returned success. The event survives a process crash, a kernel crash and a power cut, as long as the device honors cache flushes. Ordering comes for free: events land in queue order, and because a later fsync covers every earlier write to that file, an acknowledged event implies every event before it is durable too.

Before acknowledgement there is no promise. After a crash the event may be absent, present, or partially written. So frame every record with a length and a checksum (CRC32C is common), and on recovery scan forward and truncate at the first invalid record. Every acknowledged event lies before that point.

Fsync failure is the trap. You cannot simply retry: on Linux, after a writeback error the kernel may already have marked the pages clean and reports the error once, so a second fsync can succeed although the data never reached the disk. PostgreSQL hit this in 2018 and changed to stop and recover from its write-ahead log instead. So: fail every future in the batch and every later one on that file, stop writing to it, then crash and recover or rewrite the unacknowledged events into a new file. Never acknowledge an event whose fsync failed.

Likely follow up: "And with replication?" Durability becomes a quorum question: acknowledge after a majority of replicas have it on disk, or, with weaker guarantees and lower latency, in memory on N machines.

4Seniorbatchinglatencygroup-commitDatabricks
How big should the writer's batches be, and do you need a timer to flush them?
Model answer

Usually no timer. Use natural batching: whenever the writer is free, it takes everything that is pending. While one fsync runs, new events pile up, and they become the next batch.

  • Light load: batches of one event, and latency is one write plus one fsync.
  • Heavy load: batches grow automatically until the device's bandwidth is the limit.

Throughput is roughly batch size divided by (write time plus fsync time). An event's latency is at most about two fsyncs: it may wait for the fsync already running, then for its own.

A timer that waits to fill a batch (a linger time) adds its full delay to every event when the system is quiet. It is worth it only when bigger writes are much cheaper per byte on the device, and then only as a small cap, never as the only trigger.

Do add upper bounds: a maximum number of events or bytes per batch, which caps the duration of a single write and the memory held. Double buffering is the usual structure: producers fill buffer k plus 1 while the writer writes and fsyncs buffer k, then the two swap.

Likely follow up: "Two files must stay consistent, such as data and an index." Order the fsyncs (data first, then the index that points into it), or put both into one log, which gives a single ordering point.

5CoreflushcloselifecycleDatabricks
Define flush() and close() for the log writer. What must each guarantee, especially when they race with producers?
Model answer

flush() blocks until every event submitted before the call is durable. Implement it by enqueueing a marker with its own future, or by recording the sequence number of the last accepted event and waiting until the writer's durable sequence reaches it. Events submitted after flush started may or may not be included.

close() does four things in order:

  1. Flip the state to closed under the queue lock, so new appendEvent calls fail fast with an exception.
  2. Wake the writer, which drains everything already accepted, writes it, fsyncs, and completes the futures.
  3. Join the writer thread, with a timeout.
  4. Close the file.

The directory fsync belongs at creation, not at close: a new file's directory entry is durable only after its directory is fsynced, so do that once, right after creating the file and before acknowledging any event in it.

The race that matters: appendEvent against close. Because the closed check and the enqueue happen under the same lock as the state flip, every event is either accepted, and therefore drained before the writer exits, or rejected with an error. There is no event that is accepted and then silently dropped.

Likely follow up: "A second thread calls close while the first is still draining." As written it returns at once; if callers rely on "closed means durable", make it wait on the same termination signal as the first caller.

6CoreshutdownexecutorRubrik
What is the difference between shutdown and shutdownNow, and how do you implement both in a pool you built yourself?
Model answer

shutdown(): stop accepting new tasks, let every queued task run, and return at once; awaitTermination(timeout) waits for the workers to finish. shutdownNow(): stop accepting, remove the queued tasks and return them as a list of work that never started, and interrupt the running workers. That is best effort: a task that ignores interrupts keeps running.

In your own pool, keep a state under the pool lock: RUNNING, then SHUTDOWN or STOP, then TERMINATED. The worker's "get next task" method encodes the semantics:

shutdown() sets SHUTDOWN and calls signalAll, so idle workers wake, see an empty queue, and exit. submit rejects when the state is not RUNNING. The last worker to exit sets TERMINATED and signals whoever waits in awaitTermination. Here queue is your own ring buffer or list when library queues are banned.

In C++ there is no interrupt: shutdown_now sets the state, clears the queue, calls notify_all, and requests stop on each task's std::stop_source (or each std::jthread); tasks must check their token.

Likely follow up: "What happens to a submit that races with shutdown?" The state check and the enqueue happen under the same lock, so the task is either queued, and will run, or rejected; never queued after the workers have left.

7Seniorexceptionsexecutorworker-loopRubrik
Which exceptions must the worker loop of a hand-built pool catch, and what do you do with each?
Model answer

Catching InterruptedException plus Exception is not enough. One Rubrik candidate was marked down for exactly that.

  • Anything the task throws, checked or not: record it in that task's future so the submitter sees it on get, and keep the worker alive. A pool that loses a worker per failed task slowly dies.
  • Errors such as OutOfMemoryError or StackOverflowError: catch (Exception e) misses them, the worker dies silently, and the task's future never completes, so its caller hangs forever. Catch Throwable and complete the future exceptionally. Then either keep serving, or rethrow serious VM errors and start a replacement worker. ThreadPoolExecutor shows both halves: for submit, its FutureTask catches Throwable into the future; for execute, the exception kills the worker and the pool starts a replacement.
  • InterruptedException while waiting for a task: re-check the pool state; exit on STOP, otherwise keep serving.
  • An interrupt left over by a task: clear it with Thread.interrupted() before the next task, unless the pool is stopping, so one task's cancellation does not leak into the next.

In C++, wrap each task in try { ... } catch (...) { promise.set_exception(std::current_exception()); }, because an exception escaping the worker's thread function calls std::terminate and kills the process.

Likely follow up: "How does the submitter of a Runnable (not a Callable) learn about failures?" Through the same future, completed with null on success, or through an uncaught-exception hook that you log.

8CoreinterruptioncancellationjavacppRubrik
How should a worker handle InterruptedException and cancellation, in Java and in C++?
Model answer

In Java, interruption is a request, not a kill. interrupt() sets a flag; blocking methods (sleep, wait, join, take, await, lockInterruptibly) throw InterruptedException and clear the flag; CPU loops must poll isInterrupted(). The rule: never swallow it. Either propagate it, or restore the flag with Thread.currentThread().interrupt() and exit, so the code that owns the thread can see it. Some blocking is not interruptible at all: entering synchronized, lock(), and a classic java.io socket read on a platform thread. For the socket, close it to unblock the reader; for locks, use lockInterruptibly or tryLock with a timeout.

C++ threads have no interruption. Cancellation is cooperative through std::stop_token, which std::jthread passes to its function, and C++20's std::condition_variable_any can wait on a stop token, so a stop request wakes a blocked worker.

That C++ wait returns the predicate's value, so after a stop request it keeps returning tasks until the queue is empty: graceful by default.

Likely follow up: "A task catches InterruptedException and just logs it. What breaks?" shutdownNow and Future.cancel(true) silently fail for that task, and the pool never terminates while it runs.

9Corecrawlerio-boundparallelismDatabricks
Why does multithreading speed up a web crawler, and how do you know it will before you write it?
Model answer

A crawler is I/O bound. Each page spends most of its time waiting on DNS, connection and TLS setup, and the server's response, which is tens to hundreds of milliseconds, and very little time parsing, around a millisecond (orders of magnitude). A single thread leaves the CPU idle for nearly all of every fetch. Several threads overlap those waits: while one waits, others fetch.

How you know: measure the single-threaded version. If wall time is far above CPU time (time shows 100 seconds real against 3 seconds user plus system), the wait-to-compute ratio is high, and up to roughly (1 + wait/compute) threads per core can be useful.

When threads will not help:

  • Parsing or processing is CPU bound: then more threads than cores only adds switching.
  • The network link is already saturated.
  • Most URLs are on one host that limits you; politeness caps concurrency per host.
  • A shared frontier or visited set under one lock becomes the bottleneck.
  • Writing pages to one disk becomes the bottleneck.

Amdahl's law bounds the gain by the serial part, such as the coordination around the shared structures.

Likely follow up: "Threads or asynchronous I/O?" For tens of concurrent fetches, a thread pool is simplest. For thousands, use an event loop or Java virtual threads, which keep blocking code but drop the per-thread cost.

10Seniorcrawlerpool-sizingDatabricks
How do you choose the crawler's thread pool size, and how does it relate to the size of the dataset?
Model answer

The pool size comes from the workload's timing and from external limits, not from the number of pages. Little's law: a target of 50 pages per second at 200 ms per fetch needs about 10 fetches in flight. Goetz's formula gives the same idea from the CPU side: cores × (1 + wait/compute).

The dataset matters in two other ways:

  • It bounds useful parallelism. If the frontier at the current depth holds 20 URLs, 200 threads leave 180 idle. A shallow, wide site parallelizes well; a deep, narrow chain does not.
  • It sizes the shared state. A visited set of a million URLs at roughly 100 bytes each is about 100 MB (order of magnitude). Far beyond that you need a disk-backed set or a Bloom filter, which accepts rare false positives (some pages skipped).

External limits usually cap the pool first: per-host politeness (for example, at most two concurrent requests per host), total bandwidth (pages per second × average page size), sockets and file descriptors, memory per thread, and disk write throughput if you store pages. A dedicated writer thread with batching fixes the disk side.

In practice: make the size configurable, start somewhere like 16 to 64 threads (illustrative), measure throughput against thread count, and stop where the curve flattens.

Likely follow up: "Every URL is on one host." Then the per-host limit is the real cap, and threads beyond it just wait. Spend the effort on politeness and retries instead.

11Seniorcrawlerterminationvisited-setRubrikDatabricks
In a multithreaded crawler, how do you know when the crawl is finished?
Model answer

"The queue is empty" is not enough: a worker may be parsing a page and about to add fifty new URLs. Count outstanding work instead. Increment a pending counter when a URL is accepted, before it is queued; decrement it after the page is fully processed, which is after its children were accepted and counted. When the counter reaches zero, nothing is queued and nobody is working, so the crawl is done.

The visited check must be one atomic step: visited.add returns false if the URL was already present, and insert(...).second does the same in C++. A separate contains then add lets two threads crawl the same page.

Likely follow up: "Why decrement in finally?" A failed fetch must still count as finished; otherwise one exception leaves the counter above zero and main waits forever.

12Seniorbackpressurelog-writerDatabricks
The log writer's queue is full. Which back-pressure policy do you choose, and why?
Model answer

The options: block the producer until there is room (with or without a timeout); reject, so the caller decides; drop (oldest, newest, or by level); write synchronously in the calling thread; spill to a secondary buffer on disk.

Choose the back-pressure policy by the contract:

  • If appendEvent returns only once the event is durable, the caller is already waiting for the disk, so blocking on a full queue is honest: it passes the disk's real speed back to the producers.
  • If the requirement is that log must not block producers for long, use a bounded wait (offer with a timeout) and then reject with an error the caller can see. Never acknowledge an event and then drop it.
  • For best-effort application logs, shed the least valuable first: drop DEBUG and INFO, keep ERROR, and write a summary such as "dropped 1,234 events" into the log so the loss itself is visible.

Bound the queue in bytes rather than event count, since event sizes vary. Export queue depth, time spent blocked and the number dropped or rejected.

Likely follow up: "Can blocking producers deadlock?" Yes: if the writer thread itself logs through the same writer, it blocks on its own full queue, so the writer must never call appendEvent. Also, producers that block while holding their own locks can stall unrelated threads.

13Coretestinglog-writerracesDatabricks
How would you test the log writer for race conditions?
Model answer

Put the file behind a small interface so a fake can inject delays and failures and record every write and fsync. Then:

  1. Stress: N producers write M events each, every event tagged with (producer id, sequence number), all started behind a latch. Afterwards, read the output: every event exactly once, sequence numbers increasing per producer, and the right total.
  2. Durability order: with the fake, assert that no future completed before an fsync covering its bytes had returned.
  3. flush: while producers keep appending, call flush; on return, every event accepted before the call must already be covered by an fsync.
  4. close races: close while producers are mid-flight. Every event is either rejected with an exception or present in the file; none is acknowledged and missing; no thread is left blocked (join with a timeout).
  5. Faults: make fsync fail once, and assert that every future in that batch failed and nothing later was acknowledged.

Run the suite many times, run the C++ build under ThreadSanitizer, put a timeout on every wait, and use hooks to force nasty interleavings, such as pausing the writer between its write and its fsync while close runs.

Likely follow up: "How do you test crash recovery?" Cut the file at random byte offsets (or kill the process mid-run), run recovery, and check that it keeps a valid prefix containing every acknowledged event.

14Seniorfile-iopreadparallel-copyRubrik
Copy a large file with pread and pwrite using several threads. Why positional I/O, how do you split the work, and when does it not help?
Model answer

pread and pwrite take an explicit offset and neither use nor move the file's shared offset, so many threads can share one descriptor without a lock. That is positional I/O. lseek followed by read would race on the shared offset. In Java, FileChannel.read(buffer, position) and write(buffer, position) are the positional equivalents and are safe to call concurrently.

Split the file into fixed chunks (1 to 8 MB, as an illustrative size) and hand out chunk indices through an atomic counter. For each chunk, loop on pread until the chunk is full or EOF, because short reads are legal, then loop on pwrite until every byte is written. At the end, check every thread's result and fsync the destination; on any error, fail the copy and remove the partial file. Better still, copy to a temporary name, fsync it, rename it into place and fsync the directory, so nobody ever sees a half-written copy under the real name.

When it does not help:

  • One spinning disk: parallel reads at different offsets cause seeks, and one sequential stream with large buffers is faster.
  • A slow sequential source, as in Rubrik's floppy-to-SSD follow up: the source is the bottleneck, so read it sequentially in large chunks and turn many small writes into a few large ones.

It helps on SSDs and NVMe drives (deeper queues), on network storage (it hides latency), and between machines, as in chunked parallel transfer.

Likely follow up: "Resume after a crash?" Record completed chunks in a small manifest, with a checksum per chunk, and redo only the missing ones.

15Seniorexecutortimeoutsidle-threadsRubrik
Your hand-built pool now needs per-task timeouts and must reclaim idle threads. How?
Model answer

Per-task timeout. You cannot safely kill a thread, so a timeout has two halves. The caller side: future.get(timeout) throws TimeoutException to whoever waits. The cancellation side: on timeout, call future.cancel(true), which for a FutureTask-style future interrupts the worker running that task (a CompletableFuture ignores the flag), or request_stop on the task's std::stop_source in C++. A watchdog thread with a priority queue of deadlines can do this for every task. A task that ignores cancellation keeps its worker busy, so count and log it, and optionally start a replacement worker so the pool keeps its capacity.

Idle reclaim. Workers above the core size wait for work with a timeout. If the timeout expires with no work, the worker removes itself, and the decrement must happen under the same lock as the check, so the pool never drops below its core size or leaves a just-queued task without a worker.

On the submit side, if no worker is idle and workerCount is below the maximum, start a new worker. This is the keepAliveTime model of ThreadPoolExecutor; allowCoreThreadTimeOut(true) applies it to core threads too. In C++ the timed wait is cv.wait_for with a predicate.

Likely follow up: "Why not let the timed wait loop at zero?" awaitNanos(0) returns immediately, so a non-retiring worker would spin; that is why core workers switch to an untimed wait.

16Seniordagjob-runnerfailureRubrik
Run jobs with dependencies in parallel, and on the first failure stop with nothing left running. What are the tricky parts?
Model answer

The state, under one lock: each job's count of unfinished parents, each job's children, a running count, a completed count, and the first failure. Submit every job with no parents. When a job succeeds, decrement each child's count and submit children that reach zero. When a job fails, record the first exception, stop submitting, and cancel the running jobs, which is best effort.

The tricky parts:

  • "Nothing left running" means wait. execute() must not return on the first failure; it waits until the running count reaches zero, or jobs keep running after it returned.
  • A success that lands just after a failure must not schedule children, so check the failed flag under the same lock as the scheduling.
  • Termination is a condition: all jobs completed, or failed and running equals zero. Signal a condition or latch exactly then.
  • Never block a worker waiting for its children; that is a thread-starvation deadlock in the pool.
  • Check for cycles up front, or a cyclic graph never finishes.
  • With an API like getDependentTasks(completed), call it under the lock after each completion and skip jobs already scheduled.

When executors are banned, this coordinator sits on top of your own pool.

Likely follow up: "Do it with CompletableFuture." Each job's future is allOf its parents' futures, then thenRunAsync the job. Dependents fail automatically, but you must still cancel independent branches and wait for running jobs before reporting.

17Stretchfixed-bufferqueuesallocationRubrik
Implement a FIFO queue inside a fixed buffer with no allocation, then two queues sharing one buffer with minimal waste.
Model answer

One queue is a ring buffer: an array of N slots with head, tail and count. put writes at tail and advances it modulo N; take reads at head. Everything is O(1) with no allocation. For threads, add one lock and two conditions, or, with exactly one producer and one consumer, make head and tail atomics that each side alone writes, using release stores and acquire loads.

Two queues cannot simply grow from opposite ends like two stacks, because a FIFO's contents travel around the buffer as they are consumed. A fixed split (N/2 each) wastes space whenever one queue is busier.

The flexible answer: cut the buffer into fixed-size blocks (say 64 slots each) with a free list of blocks. Each queue is a linked list of blocks, the next-block index kept in a header slot, so there is still no allocation. Enqueue fills the tail block and takes a fresh block when it is full; dequeue drains the head block and returns it to the free list when empty. Everything stays O(1), and waste per queue is at most about two partly used blocks.

Concurrency: one lock per queue plus a lock for the free list, always taken after the queue's lock, or one global lock if contention is low.

Likely follow up: "The buffer is 1 GB." The same design works; choose a larger block size so the free list and headers stay small, and keep the head and tail indices as 64-bit offsets.
