Executor with wait for all

Executors and asyncmedium35 minRubrikUber

Rubrik has asked this in phone screens for years: schedule() never blocks, and waitUntilComplete() blocks until everything scheduled so far is done. It is a worker pool and a latch you build yourself from one lock and two conditions, and the classic bug is waiting for an empty queue instead of for finished work.

The task

Build a task runner with a fixed number of worker threads.

  • schedule(task) queues the task and returns at once. It never waits for a task to run.
  • waitUntilComplete() blocks until every task scheduled so far has finished, including tasks that running tasks schedule. It can be called again and again on the same runner, and by several threads at once.
  • Tasks run on exactly the N workers created in the constructor: at most N at once, and no new thread per task.
  • A task that throws counts as finished and must not kill its worker. In Java that includes an Error, not just an Exception.
  • shutdown() lets every scheduled task finish, then stops the workers and returns once they have exited. After it, schedule throws IllegalStateException in Java and returns false in C++. In C++ the destructor calls shutdown().

Rules, as in the interview: no library executors, thread pools, blocking or concurrent queues, latches or phasers. Use threads, one lock and condition variables (ReentrantLock with Condition, or synchronized with wait and notifyAll; in C++ std::mutex and std::condition_variable). Rubrik candidates report exactly this ban, including "no built-in thread-safe Deque or BlockingQueue". The same shape was asked as submitWork and blockUntilComplete, and in an Uber phone screen.

What the tests check

  • waitUntilComplete returns at once when nothing was scheduled, and otherwise only after all 40 tasks of a batch have finished.
  • With 4 workers, at most 4 tasks ever run at once and 4 really do run together, on at most 4 different threads.
  • A tree of 31 tasks where each task schedules two children: the wait covers all of them.
  • One runner, three batches, three threads waiting at once each time: all of them wake, none early.
  • 6 tasks throw exceptions and 2 throw something worse (AssertionError in Java, a plain int in C++). The wait still returns, the other tasks run, and both workers are still alive.
  • 8 threads call schedule at the same time: every task runs exactly once.
  • shutdown runs every scheduled task, the worker threads really end, and a later schedule is refused.
  • In C++, ThreadSanitizer must stay quiet, and an exception escaping a worker is reported instead of crashing the run.

Taught in: An executor without libraries: submit, wait for all, shutdown and shutdownNow

Open them one at a time. Each one gives away a little more.

What piece of state answers "is everything done"? It is not the queue: a task leaves the queue when it starts, not when it finishes.
Keep pending: tasks scheduled and not yet finished. Add one in schedule, under the lock, before any worker can see the task. Subtract one after the task finishes, whatever happened inside it. When it reaches zero, wake every waiter.
Use two conditions on one lock: workers wait for "the queue is not empty, or we are shutting down"; waitUntilComplete waits for "pending is zero". Run the task outside the lock. shutdown sets a flag and wakes all workers; a worker exits only when the flag is set and the queue is empty, then shutdown joins them.
Exceptions: in Java catch Throwable, because an Error is not an Exception. In C++ catch ...: an exception that escapes a std::thread calls std::terminate and ends the whole process. Put the pending bookkeeping after the catch, or in a finally, never inside the try.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

New tasks keep arriving while a thread is waiting. What exactly does your wait wait for?
With one counter it returns at the first instant pending is zero, so tasks scheduled during the wait are included only if they arrive before that instant, and a steady stream could keep the waiter blocked forever. If the caller wants "everything scheduled before my call", use batches: schedule adds to the current batch, waitUntilComplete closes the current batch, starts a new one, and waits for the closed batch's own counter to reach zero. Say which semantics you chose; interviewers let you change the signatures for this.
The caller needs to know which tasks failed.
Record failures instead of swallowing them: keep the first exception (or all of them) under the lock and throw it from waitUntilComplete, the way invokeAll futures or Go's errgroup.Wait report errors, or accept an error callback at construction. Whatever you choose, the worker still survives and the task still counts as finished.
Return each task's result.
Make schedule return a future that the worker completes, with the value or the exception. In C++ wrap the callable in a std::packaged_task held by a shared_ptr so it fits in a std::function queue; in Java either write a small future class or wrap the task in a FutureTask. That is the next problem, the thread pool from scratch.
Scheduling is faster than running and memory keeps growing.
Bound the queue. Then schedule must either block when the queue is full (backpressure, but it breaks "never blocks"), reject the task, or run it on the caller's thread (caller runs, which slows the producer down naturally). Each is a rejection policy the interviewer wants you to name and choose for a reason.
How many workers?
For CPU-bound tasks, about the number of cores; more only adds context switches. For I/O-bound tasks, use Little's law: the number of busy threads equals throughput times the time each task holds a thread, so tasks that wait 90 percent of the time need roughly ten times the cores. The Rubrik variant with overnight I/O and network tasks is the second case. See sizing a pool.
Add a way to cancel everything that has not started.
Under the lock, take everything out of the queue, subtract its size from pending, and wake the waiters if it reaches zero. Running tasks cannot be stopped from outside safely; in Java you interrupt the workers and tasks must respond to the interrupt, in C++ tasks poll a std::stop_token. That is shutdownNow in the thread pool problem.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

A worker pool over one queue, plus a counter that plays the role of a latch you can reuse. The invariant: pending equals the number of tasks that have been scheduled and have not finished, whether they are queued or running. Everything follows from keeping that exact: schedule raises it before any worker can take the task, a worker lowers it only after the task is over, and the wait is "while pending is above zero, wait".

Why each line is there

  • pending += 1 inside schedule, under the lock. If a running task schedules a child, the child is counted before the parent finishes, so pending never touches zero in between and the wait covers the whole tree.
  • Two conditions. Workers wait on hasWork, waiters on idle. A new task wakes one worker with signal; finishing the last task wakes every waiter with signalAll, because several threads may be waiting.
  • The task runs outside the lock. Otherwise the workers would take turns and you would have one worker, not N.
  • Catch everything around the task, and decrement after the catch. An uncaught exception kills a Java worker silently and ends a C++ process. The bookkeeping must run on every path, which is why it sits in a finally (Java) or after the catch (...) (C++).
  • awaitUninterruptibly and clearing the interrupt flag. This runner has no cancellation, so a stray interrupt left behind by one task must neither kill the worker nor leak into the next task.
  • Shutdown drains, then joins. Workers exit only when the queue is empty and the flag is set, so queued work finishes. signalAll is essential: idle workers are asleep and would never see the flag otherwise. In C++ the std::vector<std::thread> is the last member, so the threads start after everything they use exists, and every thread is joined, because destroying a joinable std::thread calls std::terminate.

Cost and trade-offs

schedule and each task hand-off are O(1) under one lock. With very short tasks and many workers that lock becomes the bottleneck; real pools reduce it with per-worker queues and work stealing. The queue here is unbounded, which is what makes schedule non-blocking, and also what lets memory grow if producers outrun the workers.

How to say it in the interview

I will start N workers that loop over one queue guarded by a mutex, with two condition variables: workers wait for work or shutdown, and waitUntilComplete waits for a pending count to reach zero. Pending counts tasks scheduled but not finished, so I increment it in schedule before any worker can run the task and decrement it after the task returns, in a finally, so a throwing task still counts as done; I catch Throwable so even an Error cannot kill a worker. The task itself runs outside the lock. Shutdown sets a flag and signals all workers; they drain the queue and exit, and I join them. If you want per-batch waits or error reporting, I would add a batch object or record the first exception and throw it from the wait.
