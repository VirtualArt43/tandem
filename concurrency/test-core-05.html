A thread spins in while (!done) {} for one second before another thread sets done. Roughly how much CPU time does the waiting thread use?
Why. An empty loop still runs instructions as fast as the core allows, so a one-second wait costs a core-second of CPU. The demo measured about 200 ms of CPU for a 200 ms spin. An empty body does not make it free; it just makes it pointless work.

A consumer polls with while (queue.isEmpty()) sleep(100 ms). An item arrives just after a check. How late can the consumer notice it?
Why. Nothing wakes a sleeping poller early, so an item that arrives right after a check waits a full interval: about 100 ms worst case, 50 ms on average. Shorter intervals cut the latency but burn more CPU on empty checks.

On a machine with a single core, thread W spin-waits for a flag that thread P will set. What does the spinning achieve?
Why. With one core, the waiter and the thread it waits for cannot run at the same time. The spin delays P by up to a whole time slice. A pause hint saves power but does not hand the core over. Blocking would let P run immediately.

What does a thread's call to wait on a condition variable do with the lock it holds?
Why. Releasing is what lets another thread change the state; doing it atomically with going to sleep is what prevents a signal from slipping in between; re-acquiring is what lets the code after wait safely re-check and use the state.

Thread W runs: lock; while (!ready) wait; print "A"; unlock. Thread S runs: lock; ready = true; notifyAll; print "B"; unlock. W is already waiting when S starts. What is printed?
Why. A woken waiter must re-acquire the lock before wait returns, and S still holds it while printing "B". This is signal and continue: the signaller keeps running. W was already waiting, so the notification is not lost.

Producers wait for "not full" and consumers for "not empty", on the same lock. What do two separate condition variables (Java Condition objects, or two std::condition_variables) give you over a single wait set?
Why. With one wait set, a notification may wake a thread that cannot use it, forcing notifyAll or risking a stall. Separate conditions let a consumer signal "not full" for producers only. The lock is still shared, and loops are still required.

Thread W holds lock L1, then takes lock L2, and waits on a condition variable tied to L2. The thread that would make W's condition true must take L1 first. What happens?
Why. wait releases the lock tied to its condition and nothing else. Holding another lock while waiting creates a nested monitor lockout. Design so a waiting thread holds only the one lock its condition belongs to.

A timed wait is written as: loop while the condition is false, calling wait(lock, 100 ms) each time. Under a stream of spurious or unrelated wakeups, what can go wrong?
Why. A deadline must be fixed once and every re-wait must use only the time left. In Java carry the value returned by awaitNanos; in C++ use wait_until with a deadline, or wait_for with a predicate, which computes the deadline once internally.

Java onlyA Java thread calls queue.notifyAll() without being inside synchronized (queue). What happens?
Why. wait, notify and notifyAll all require the caller to own the object's monitor, and the check happens at run time. The JDK 21 message is "current thread is not owner". Condition methods on a ReentrantLock have the same rule.

From: Spurious and stolen wakeups: always wait in a loop
Two consumers wait on an empty queue. A producer adds one item and calls notifyAll. Both consumers use if around their wait. What happens?
Why. notifyAll wakes both. They re-acquire the lock one after the other; the first empties the queue, and the second, having used if, never looks again. With while, the second would see the empty queue and wait again. They cannot take the same item, because each removal happens under the lock.

A consumer must stop waiting when an item arrives or when the queue is closed. Which wait is right?
Why. The loop condition must include every reason to stop waiting. Checking closed outside the loop means a thread woken by close() sees an empty queue and waits again forever. The waiter runs if (!ready) { lock; wait; unlock }. The setter runs ready = true; lock; notifyAll; unlock. What can happen?
Why. The check happens outside the lock, so the setter's change and notification can both land between the check and the wait; the notify finds nobody waiting and is lost. Checking and waiting in a loop under the lock, with the setter changing the flag under the same lock, closes the window.
From: Lost wakeups, notify versus notifyAll, Mesa versus Hoare
Nobody is waiting. Thread A calls notify on a condition variable; thread B calls release on a semaphore. Later, thread C waits on the condition variable and thread D acquires the semaphore. What happens?
Why. A condition variable has no memory, which is why it must always be paired with state that the waiter checks. A semaphore's count is its memory. Waiting on a condition variable for a notification that already happened is the lost wakeup.
From: Lost wakeups, notify versus notifyAll, Mesa versus Hoare
Producers wait "while full" and consumers wait "while empty" on one Java monitor (or one std::condition_variable), and both use a single notify (notify_one). The waits are in while loops. What can happen with two producers and two consumers on a one-slot buffer?
Why. The loops make each wakeup safe, but a single notify that lands on a thread that cannot proceed is wasted, and the thread that could proceed is never woken. Use notifyAll, or separate conditions so each signal reaches the right kind of waiter. The lock still prevents two writers in the slot.

When is a single notify (signal, notify_one) instead of notifyAll safe?
Why. These are the uniform waiters and one-in, one-out conditions. The while loop protects against wakeups with a false condition, but it cannot create a notification for the thread that was never woken. The number of waiters can change at any moment, so "fewer than two" is not a rule you can rely on.

Under Mesa semantics, which is true when a notified thread returns from wait?
Why. With signal and continue, the signaler keeps running and the woken thread re-acquires the lock later; others may run in between. Guaranteed truth and a waiting signaler describe Hoare semantics, which mainstream libraries do not use. In both models wait returns with the lock held.

Java onlyInside one synchronized (lock) block, a Java setter calls lock.notifyAll() and then sets ready = true. Is the order a bug?
Why. A woken thread must re-acquire the monitor before wait returns, which happens only after the setter exits the synchronized block. Both actions are therefore visible together. Setting the state first reads more naturally, and that is the convention, but inside one critical section the order does not change behavior.

A bounded buffer uses one condition (one Java monitor, or one std::condition_variable) for producers and consumers, waits in a while loop, but wakes waiters with notify() (or notify_one()). With 2 producers and 2 consumers, what can happen?
Why. The loop makes the woken thread re-check safely, so nothing is corrupted, but it cannot recover a wakeup that went to a thread that cannot use it. A consumer that wakes a consumer, while producers sleep, leaves everyone waiting. The fix is notifyAll or two conditions.

A consumer's take() is written as if (items.isEmpty()) wait(); return items.removeFirst(); with notifyAll() after every put. There are two consumers. What can go wrong?
Why. notifyAll wakes both. The first to reacquire the lock takes the only item; the second returns from wait and, with if, does not re-check, so removeFirst throws NoSuchElementException (in C++, popping an empty deque is undefined behavior). A while loop sends it back to sleep.

Three producers and four consumers share a library blocking queue, and you shut down with poison pills. Which plan is correct?
Why. One pill stops one consumer, so you need one per consumer. They must go in after every real item, which means after every producer is done; FIFO then guarantees the real work is taken first. A producer putting its own pill can stop a consumer while other producers are still adding work.

In the demo's buffer, every producer has finished and close() is called while 5 items are still queued. One consumer then calls take() in a loop. What does it get?
Why. A consumer waits only while the buffer is empty and open, and reports "nothing left" only when it is empty and closed. Closing stops new puts; it does not throw away queued work. Checking closed before checking for items would lose the 5 items.

A web service's request threads put metrics events into a bounded buffer (losing a few is acceptable). The consumer is down and the buffer is full. Which behavior is best for the request threads?
Why. Request threads must not hang on a non-essential side task, so blocking forever is wrong. An unbounded queue just converts the outage into memory growth, and spinning burns CPU. A bounded wait plus a counted drop keeps the service responsive and makes the loss visible.

Why should a consumer process an item after take() returns, rather than inside the locked region of take()?
Why. The lock protects only the buffer's state. Work done while holding it serializes all consumers and stops producers too, so the pattern loses its parallelism. Remove the item, release the lock, then process it.
