Why. ReentrantLock counts holds per owner. Two lock() calls make the count 2, and one unlock() brings it to 1, so main still owns the lock. The other thread's tryLock() therefore returns false, and main's getHoldCount() is 1 (a real run printed false 1). The lock is freed only when the count reaches 0, which is why every lock() needs its own unlock() in a finally. tryLock() may jump ahead of queued waiters, but never past a thread that holds the lock.
C++ onlyWhat happens?
Why. The standard says a thread must not lock a std::mutex it already owns; doing so is undefined behavior. Most implementations simply block (a run on macOS hung until it was killed), and some may throw std::system_error. The compiler cannot see it. Fix it by splitting the code into a public function that locks and a private helper that assumes the lock is held, or, less cleanly, by using std::recursive_mutex. Java's synchronized and ReentrantLock are reentrant, which is why this surprises Java programmers.
Java onlyOne producer and two consumers share this buffer. What is the bug?
Why. wait() releases the monitor, and a woken thread must win the monitor again before it continues. Between the notify and that moment, the other consumer can take the only item. Java also allows spurious wakeups. Both cases leave the queue empty when remove() runs. Always re-check the condition in a loop: while (q.isEmpty()) wait();. Switching to notify does not fix it (spurious wakeups and barging remain), notifying after the add is the correct order, and wait does release the monitor.
C++ onlyOne producer and two consumers share this buffer. What is the bug?
Why. wait releases m while sleeping and takes it back before returning, so by the time a consumer runs again the other consumer may already have emptied the queue; spurious wakeups are also allowed. Use the predicate overload, which loops for you: cv.wait(lk, [&] { return !q.empty(); });. Notifying after unlocking is fine and often faster here, because the state change was made under the lock, and notify_one alone would not fix the missing re-check.
Java onlyWhat can go wrong with this lazy singleton, and what is the minimal fix?
Why. The second null check under Registry.class prevents duplicate construction, but the fast path reads instance without that monitor. There is no happens-before edge publishing the constructor's writes to that reader, so it may see a non-null instance with table still null. Declaring instance volatile orders construction before a reader that observes the published reference. The holder class idiom or synchronizing all of get() also works. C++ onlyWhat is wrong with this lazy singleton, and what is the idiomatic fix?
Why. The write of instance is locked, but the first read is not, so the accesses form a data race and the behavior is undefined. Replace the entire body of the pointer-returning get() with static Registry r; return &r;. Since C++11, initialization of that local static is synchronized and occurs once after a successful construction. Returning r instead would not compile: the function returns Registry*, not Registry. std::call_once is another option; atomic double-checked locking needs acquire loads, a release store and the locked second check. volatile and a recursive mutex do not repair the unlocked read.
Java onlyWhich statements about CountDownLatch and CyclicBarrier are true?Select all that apply
Why. A latch is a one shot gate: its count only goes down, and at zero it stays open forever. countDown() just decrements (it does nothing at zero), and any thread may call it any number of times, for example once per finished item. A barrier is reusable, which is the "cyclic" in its name. Its optional barrier action runs in the last thread to arrive, before any party is released, so it can safely merge results from the round.
C++ onlyWhich statements about C++20 std::latch and std::barrier are true?Select all that apply
Why. std::latch has one countdown and no reset. count_down(n) does not wait for zero; the same thread can call it repeatedly, but each update must be nonnegative and no larger than the remaining count. Calling the default count_down() after zero violates that precondition and has undefined behavior, unlike Java's harmless extra countDown(). wait() waits for zero, while arrive_and_wait() both decrements and waits. A barrier starts its next phase automatically after completion; its completion function runs after the expected arrivals and before waiting threads are released. There is no reset() member.
Java onlyEach task runs for 10 seconds, and the 7 tasks are submitted back to back. What happens?
Why. ThreadPoolExecutor grows in this order: below the core size it starts a new thread; at the core size it queues; only when the queue is full does it add threads up to the maximum; when that is full too, the rejection policy runs (by default, throw). A real run showed exactly this, and tasks 5 and 6 even started before queued tasks 3 and 4. With an unbounded queue, as in newFixedThreadPool, the queue never fills, so the maximum size is never used.
C++ onlyslow sleeps for 1 second. Roughly how long does main take?
Why. The explicit std::launch::async policy starts each task asynchronously, but its returned future is a temporary destroyed at the end of that statement. Here that future releases the last reference to the shared state and waits for its unfinished task, so the three one-second calls execute one after another: about 3 seconds plus overhead. Discarding the result may produce a [[nodiscard]] warning; it is not inherently a compilation error. Keep the futures in a std::vector<std::future<void>> and wait after submitting all three to allow overlap. The blocking rule here is specific to shared states created by std::async; ordinary promise-backed futures do not have it.
A request handler spends 10 ms computing and then 90 ms blocked on a database call. The machine has 8 cores and the database is not the bottleneck. Using the usual estimate threads = cores x (1 + wait / compute), how many threads keep the CPUs busy, and what throughput can the service reach?
Why. wait / compute = 90 / 10 = 9, so threads = 8 x (1 + 9) = 80. Each request needs 10 ms of CPU, so 8 cores can finish at most 8 / 0.010 = 800 requests per second. Little's law agrees: 80 requests in flight / 0.1 s each = 800 per second. 72 is 8 x 9 (the "1 +" for the compute time was dropped), and 8000 forgets that each request takes 100 ms. With only 8 threads, each core would sit idle 90 percent of the time, giving 80 requests per second.
Counting every process, how many lines of x does this print?
Why. In round i = 0, one process forks into 2, and both print: 2 lines. In round i = 1, each of those 2 forks, giving 4 processes, and all 4 print: 4 lines. Total 2 + 4 = 6 (a real run printed 6). std::endl flushes, so no buffered text is copied into the children. Without the flush (for example printf("x\n") with output going to a pipe or file, which is fully buffered), each child inherits the unprinted line in its buffer and a real run printed 8. The general rule for "fork in a loop of n, then print once after the loop" is 2 to the power n lines.
Which statements about resource allocation graphs are true?Select all that apply
Why. With single instances, every request edge on a cycle waits for exactly one holder, who is itself waiting on the cycle, so nobody can ever proceed. With several instances, a process outside the cycle may hold an instance, finish and release it, which breaks the cycle; so a cycle only says deadlock is possible. No cycle always means no deadlock. The Banker's algorithm exists precisely to handle several instances per resource type, using vectors of available, allocated and still needed units.
Java onlyTwo threads each run this line 100,000 times on a shared ConcurrentHashMap<String, Integer> hits. Which replacements make the final count always 200000? Select all that apply
Why. Starting with k absent or mapped to 0, merge, compute, and one shared lock around the entire update each produce 200000 after both threads finish. The first two operations atomically update that key. With separate getOrDefault and put calls, both threads can read the same old count and then overwrite each other's increment, even though each call is thread-safe. A synchronized map still protects only one call at a time unless the caller locks around both. A volatile map reference does not combine those calls. The external-lock answer requires every update to use the same hits monitor.
C++ onlyTwo threads each run hits.set("k", hits.get("k") + 1); 100,000 times. What is true?
Why. Every access to the map happens under the mutex, so ThreadSanitizer reports nothing: there is no data race. There is still a race condition: both threads can get the same value before either sets, so an increment is lost. Real runs printed 120972, 164855 and 200000. The fix is an operation that does the whole update under one lock, such as void increment(const std::string& k) { std::lock_guard<std::mutex> g(m); map[k] += 1; }.
Main fills a config object and stores it in a plain field (not volatile, not atomic, no lock), then starts a new thread that reads the field. No thread writes the field afterwards. Is the new thread guaranteed to see the fully built config?
Why. Both memory models give thread start a happens-before edge: in Java, a call to start() happens-before any action in the started thread; in C++, the completion of the std::thread constructor synchronizes with the start of the new thread's function. So writes made before the start are visible, with no data race. The guarantee does not cover writes main makes after the start; those need their own synchronization. Sleeping creates no happens-before edge at all.
Two threads each need locks A and B. Thread 1 locks A, then calls tryLock on B; thread 2 locks B, then calls tryLock on A. On failure each releases what it holds and retries the same steps at once, with no delay. What is the risk?
Why. tryLock returns false instead of blocking, so this cannot deadlock, but two threads moving in lockstep can collide on every attempt. They burn CPU and never finish: a livelock. In practice timing noise often breaks the symmetry, but nothing guarantees it. Add a random back off before retrying, or better, make both threads take A before B so the conflict never arises.
A thread holds the read lock of a ReentrantReadWriteLock (Java), or a std::shared_lock on a std::shared_mutex (C++), and now asks for the write lock without releasing the read lock. No other thread is using the lock. What happens?
Why. Java's ReentrantReadWriteLock does not support upgrading: the write acquisition waits for all read holds, including the caller's own, so the call cannot finish. C++ has a different contract: attempting any recursive ownership of a std::shared_mutex, including shared then exclusive, is undefined behavior. A hang is one possible symptom, not a guaranteed C++ result or exception. Release the read lock, acquire the write lock, and re-check the protected state because another writer may have changed it in between. Java permits downgrading by taking the read lock while holding the write lock; C++ std::shared_mutex does not permit that recursive ownership either.
