OA set 5: memory orders, lock-free and hidden deadlocks

The hardest set: independent reads of independent writes, a lapping barrier, false sharing, default executors, deadlock detection, pool shutdown bugs, static initialization deadlocks and Peterson's lock.

Set 5 is harder than any online assessment you are likely to meet. Each question rests on one precise rule (a total order, a permit that goes to the wrong thread, an initialization lock), and the tempting answer is what most experienced engineers would say first.

12 questions, 15 minutes. Answers and explanations stay hidden until you submit or the clock runs out. Multi answer questions say so; pick every option that is true.

Java onlyx and y are volatile int fields starting at 0. Four threads run at once. Can the run end with r1 = 1, r2 = 0, r3 = 1 and r4 = 0?
Why. That result means thread 3 saw x = 1 before y = 1, while thread 4 saw y = 1 before x = 1. In Java's single synchronization order over volatile accesses, thread 3's reads put the write of x before the write of y, and thread 4's reads put the write of y before the write of x: a contradiction, so the outcome is forbidden. This pattern is called IRIW (independent reads of independent writes). With plain fields it is allowed. Some hardware, such as IBM POWER, really produces this outcome, which is why the language rule, not your laptop, decides.
C++ onlyx and y are std::atomic<int> starting at 0. Thread 1 stores 1 to x; thread 2 stores 1 to y; thread 3 loads x then y into r1 and r2; thread 4 loads y then x into r3 and r4. Which choice of memory orders guarantees that r1 = 1, r2 = 0, r3 = 1, r4 = 0 never happens (the two readers never disagree about which write came first)?
Why. Only seq_cst operations take part in the single total order S that every thread agrees on, which rules out the two readers seeing the writes in opposite orders (this pattern is called IRIW). Release and acquire only order things relative to the matching release; they say nothing about the order of two unrelated writes as seen by different readers, so the outcome is allowed. The relaxed option is the subtle trap: every thread does agree on the order of writes to x alone and to y alone, but there is no order between x and y. Some hardware, such as IBM POWER, really produces this outcome even with acquire loads, so a passing test on x86 proves nothing.
A reusable barrier for N threads is built from semaphores and called once per round in a loop. What can go wrong?
Why. Take N = 2. T1 arrives and waits on the turnstile. T2 arrives last, releases 2 permits, takes one, runs its loop body, comes back, increments count to 1, and takes the second permit before T1 has woken. T2 has now passed barrier 2 while T1 is still waiting at barrier 1, and if the threads stop after a fixed number of rounds, T1 can be left waiting forever. A search of every interleaving for 2 threads and 3 rounds found both outcomes. The fix is a two phase barrier with two turnstiles (the classic from The Little Book of Semaphores), or simply CyclicBarrier or std::barrier.
Eight threads each increment their own slot of a shared long[8] (Java) or std::array<std::int64_t, 8> (C++) many millions of times. No slot is touched by two threads, and no locks are used. On a CPU with 64 byte cache lines it runs slower with 8 threads than with 1. What is the cause and the fix?
Why. Cache coherence works on whole lines. Different slots can share a line even though no two threads access the same slot, so this is false sharing rather than a data race. A 64 byte array may span two lines if its start is not aligned to a line boundary; several slots still share each line. Cores must obtain write ownership of a shared line, which can make concurrent updates expensive. Padding or alignment separates the slots: with 8 byte elements and 64 byte lines, placing slot i at array index i * 8 gives a 64 byte stride. Match the spacing to the target CPU rather than assuming all CPUs use 64 bytes. Java LongAdder is an alternative when you need one aggregate counter, not a replacement for eight separately addressable counters.
Java onlyIn OpenJDK 21, availableProcessors() returns 8 and the common pool uses its default configuration. A service submits CompletableFuture.supplyAsync(() -> callRemote()) 100 times without an executor. Each call blocks for 1 second using unmanaged blocking. Assume no other common-pool work, no compensating workers, and negligible submission overhead. Roughly how long until all futures complete?
Why. With the stated defaults, supplyAsync uses ForkJoinPool.commonPool(), whose target parallelism here is 8 minus 1 = 7. Seven workers running 100 one-second calls need ceil(100 / 7) = 15 waves, about 15 seconds. Eight workers would give 13 waves, but that is not the default common-pool parallelism here. This is a sizing estimate under the question's assumptions, not a general timing guarantee: configuration, other work and managed blocking can change it. Blocking remote calls should use an appropriate executor, such as an explicitly supplied Java 21 virtual-thread executor, with a separate bound on downstream concurrency.
C++ onlyWhat does the C++ standard guarantee about auto f = std::async(work); written with no launch policy?
Why. The default policy is std::launch::async | std::launch::deferred, and the library chooses. A deferred task never runs concurrently; it runs inside get() or wait(), and timed waits report deferred without running it. Code that polls with wait_for until ready will loop forever in that case. Pass std::launch::async when you need concurrency, or check for deferred first. The standard does not mention thread pools for std::async.

Why. The detection algorithm assumes any process whose request fits can finish and release everything it holds. Work = (0, 1, 1): only P4's request (0, 0, 1) fits, so Work becomes (0, 1, 1) + (1, 0, 1) = (1, 1, 2). Now P0's request (1, 0, 0) fits: Work = (1, 2, 4). Then P3's (1, 1, 0) fits: Work = (1, 4, 5). P1 needs 2 units of A and P2 needs 2, but only 1 is free. A has 3 units in total, P1 and P2 hold one each, and each waits for more: they are deadlocked. "Only P4 can run now" confuses "blocked at this moment" with "deadlocked".

Java onlyA shared LongAdder starts at zero. Four threads each call adder.increment() 1,000 times, with no resets or other updates, and main calls adder.sum(). Which statements are true?Select all that apply
Why. LongAdder keeps a base value plus a set of cells; contended threads update different cells, which avoids every thread hammering one cache line, and sum() adds them up. No increment is ever lost, so after the joins the total is exact (a real run printed 4000). During updates, the documentation says the sum is not an atomic snapshot, so use it for statistics, not for decisions like "exactly N then act". sumThenReset() is the resetting variant.
C++ onlyFour threads each run count.fetch_add(1, std::memory_order_relaxed) 1,000 times on a shared std::atomic<int> count{0}. Which statements are true?Select all that apply
Why. Every read-modify-write on one atomic, relaxed or not, is atomic and reads the latest value in that variable's modification order, so no increment is lost; join then makes the final value visible (real runs printed 4000). Relaxed only drops ordering with respect to other variables. That is why the last option is wrong: a concurrent reader that sees 4000 through relaxed operations gets no happens-before edge to the workers' other writes, so reading their data is a race. Use release increments and an acquire load for that.

The 100 ms sleeps make that schedule plausible but do not force it. The JVM releases the class initialization lock while executing the initializer; the cycle is in waiting for initialization completion, not two Java monitor blocks held around the entire initializers. If one thread initializes both classes, its recursive request for the class it is already initializing does not wait: that class's still-unassigned field has the default value 0. C++ onlyWhat happens when this runs?
Why. Since C++11 a function-local static is initialized exactly once, and a second thread that reaches it during initialization blocks until it finishes. That guarantee is a hidden lock, so two statics whose initializers call each other from two threads deadlock (a real run hung until it was killed). On one thread it is worse: re-entering a static's own initialization is undefined behavior, and libc++abi aborted with "detected recursive initialization". Break the cycle; do not call code that might need your own static from inside its initializer.
Peterson's lock for two threads (me is 0 or 1, and other is 1 - me): Which versions guarantee mutual exclusion on a modern multicore CPU?Select all that apply
Why. Among these versions, separate Java volatile fields and C++ sequentially consistent atomics provide the ordering needed by Peterson's algorithm. Both flags and turn participate in one order consistent with each thread's program order, which rules out both threads passing the entry test together. Release stores and acquire loads alone allow each thread to read the other's flag as false: neither load then observes the other's release, so no cross-thread synchronization is established. A successful stress run cannot rule out that allowed execution. Plain variables provide no portable mutual-exclusion guarantee, and conflicting non-atomic accesses in C++ are a data race. Declaring the Java array reference volatile does not make its elements volatile; use separate volatile fields or an appropriate atomic array.
A server uses a pool of 50 threads. A filter stores the current user in a thread-local (Java ThreadLocal<User>, or an owning C++ thread_local value) for requests it handles and never clears it. Some later requests can bypass the filter. What can go wrong?
Why. Thread-local state belongs to a thread, not to one request, and a pool reuses threads. If a later request skips initialization and reads the same thread-local, it can inherit the earlier request's identity. Java references and owning C++ values can also retain user objects until replacement, cleanup or thread exit. Simultaneous requests on different threads have different thread-local values. Establish request context at entry and clean it up at exit, including exceptions: use try/finally with Java remove(), or a C++ RAII scope guard that clears or restores the context. For nested contexts, restore the previous value when leaving the inner scope.
For a fixed workload, 5 percent of its one-core execution time must run serially and the remaining 95 percent divides perfectly across the cores. Using Amdahl's model and ignoring overhead, what is the best speedup on 16 cores, and the limit with any number of cores?
Why. Amdahl's law gives speedup 1 / (s + (1 - s) / p) for serial fraction s and p cores. Here 1 / (0.05 + 0.95 / 16) = 1 / 0.109375, about 9.14. As the number of cores grows, the parallel part tends to zero and the limit is 1 / 0.05 = 20. The tempting 15.2 is 0.95 * 16, which omits the serial time. These are ideal speedups for the fixed workload described; synchronization and scheduling overhead can reduce them. A service's throughput across overlapping requests needs a separate model.

Why. The qualified counter loop in the first option is lock-free: after a thread reads the counter, a strong-CAS mismatch means another update intervened, so some operation progressed. It need not be wait-free because one thread can lose indefinitely. CAS by itself is not a progress proof: atomics may use internal locks, loop bodies may block, and a CAS-based spinlock still depends on its owner releasing the lock. Weak CAS can fail spuriously without another update; on failure, C++ compare-exchange updates expected with the observed value. Such a failure alone does not prove progress. Java compareAndSet returns a boolean, while compareAndExchange returns the witness value. A paused thread does not inherently block a correctly designed lock-free loop.
