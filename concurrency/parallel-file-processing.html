Parallel copies, chunked reads and caches over slow storage

Copy independent file chunks safely, bound ordered output, and coalesce concurrent cache misses while handling failures and storage limits.

Asked atRubrikDatabricks
Before this:Files, offsets, buffers, flush and fsyncAn executor without libraries: submit, wait for all, shutdown and shutdownNow

Rubrik interview reports describe parallel copies with pread and pwrite; a Databricks report describes range reads over slow storage with shared chunk fetches. Both are the same skill: cut the data into chunks, let threads work on chunks independently, and be precise about what is shared.

In plain words

Moving a library to a new building with one person carrying books in order is slow. Give four helpers numbered shelf ranges instead: because each helper knows exactly which shelf in the new building their books go on, they never get in each other's way, and nobody needs to coordinate except to hand out the next range. That is a parallel chunked copy with positional writes.

Now picture a reading room in front of a slow archive. When a reader asks for a box that is not in the room, a clerk fetches it once. If three readers ask for the same box while the clerk is still on the way, they do not send three clerks; they wait for the one already going. If the clerk comes back empty-handed, the room does not pretend the box is missing forever; the next request tries again. That is a chunk cache with single-flight fetches.

The questions

  • Rubrik, 2024 and 2025: implement a file copy with pread and pwrite; the 2025 report explicitly adds parallel workers.
  • Rubrik, 2026 screen: implement a cp-like operation using supplied open, close and offset-based read/write operations (the report uses names such as fopen and read(fileId, offset), not real POSIX signatures); follow up: optimize copying from a floppy disk to an SSD, with no ExecutorService or pool classes. The candidate proposed parallel chunked reads merged into a few large writes.
  • Rubrik senior design rounds: an SCP-like copy of a 1 TB file between two machines, with chunking, multithreading and bandwidth.
  • Databricks, 2026: a CachedFile over a StorageClient with getFileSize and fetch(uri, offset, length, buffer): serve reads of arbitrary ranges, make repeated reads cheap, minimize network calls. The candidate used fixed-size chunks, fetched in parallel by a thread pool, each chunk fetched once, and discussed duplicate fetches across threads and failures.

A parallel chunked copy

Start single-threaded in the interview: loop over the file in chunks, pread a chunk into a buffer, pwrite it to the same offset in the destination, handle short reads and the shorter last chunk, sync the destination once at the end. Then make it parallel, which with Positional I/O is a small change:

  • Chunks are claimed, not pre-assigned. A shared atomic counter hands out the next chunk number. A fast thread simply takes more chunks, so nobody sits idle while one thread finishes a slow quarter of the file.
  • No application lock for data transfer. Each chunk owns a disjoint destination range and each worker owns its buffer. Positional calls leave the shared file position unchanged. Chunk assignment and failure reporting still need synchronization; the operating system and Java implementation may use internal locks.
  • Failure stops the others. The first error is recorded in an atomic reference or flag; workers check it before claiming the next chunk. Report the error after joining everyone.
  • One sync at the end. If only the completed file needs a durability acknowledgement, per-chunk syncs add unnecessary work. Check the final sync result; resumable transfers with intermediate durable acknowledgements have a different contract.

The copy below assumes a stable regular source file and paths that are not concurrently replaced. It rejects a source/destination alias before truncating, validates worker and chunk counts, and joins all started workers before closing their handles. It overwrites the destination directly, so failure may leave a partial file; atomic replacement needs a temporary file. A zero-progress transfer is reported as an error here rather than retried forever. Stopping new claims does not cancel an active storage call; cleanup waits for those calls to return.

How big a chunk, and how many threads

There is no single right number, but there is a right way to reason, and interviewers want the reasoning:

ChoiceToo smallToo largeTypical starting point (order of magnitude)
Chunk size, local diskSystem call and bookkeeping overhead dominateFew chunks, poor balance at the end, much memory per thread64 KiB to a few MiB as an initial experiment; page and device block sizes vary
Chunk size, remote storageEach request pays a round trip of millisecondsA failed chunk wastes a lot of transfer; long tail at the endSeveral MB per request
Threads (I/O in flight)The device sits idle between requestsMemory is threads times chunk size; a spinning disk thrashes between positionsA handful for local SSDs, which serve parallel requests well; one sequential stream for a spinning disk

Two principles carry most answers. First, find the bottleneck before adding threads: extra workers help when they hide latency or overlap independent stages; they cannot raise a saturated device's bandwidth. Second, memory in flight is threads times chunk size, so the thread count is also a memory budget: 8 threads with 4 MB chunks hold 32 MB of buffers.

Rubrik's floppy-to-SSD follow up tests the first principle. A floppy, like a spinning disk, has one head: parallel reads at different offsets make it seek back and forth, so they do not help and can hurt. What helps is overlapping the two devices: one reader streams large sequential chunks from the slow source into a small bounded queue of buffers, and one writer drains them to the SSD in large writes. For a large file on independent devices, the ideal time approaches that of the slower stage, plus pipeline startup, drain and sync costs. Parallel chunked reads pay off when the source itself serves concurrent requests, as NVMe drives and remote object stores do.

When the output must stay in order

Positional writes make order irrelevant for a file copy: every chunk lands at its own offset, whatever finishes first. But often the output is a stream: compressing chunks in parallel and sending them over a socket, or checksumming in parallel and appending results to a log. Then chunks finish out of order and must be emitted in order. The tool is a reorder buffer: finished results wait in a map keyed by chunk number, and one emitter writes them strictly in sequence. A window stops fast workers from racing ahead without bound: a worker may not start chunk c until c is less than the next chunk to emit plus the window, which caps the results held in memory.

The demo retains emitted strings only to check their order, so total demo memory grows with output length. The window bounds in-progress and waiting results, not a returned list or arbitrarily large individual results. A production emitter writes to a sink with back-pressure; enforce a byte budget too when result sizes vary. Simply bounding a queue of completed results can deadlock: later chunks fill it, the emitter waits for the earliest chunk, and that chunk cannot publish into the full queue. Bound admission by sequence number so the earliest chunk always has room to finish.

Why the window itself does not create a circular wait, assuming callbacks finish and threads get scheduled: chunks are claimed in increasing order, so the worker holding the next chunk to emit has a number below nextToEmit + window and is never held back by the window. It finishes, the emitter advances, and the window slides. Any positive window permits progress; twice the worker count is only a starting point for tuning, not a guarantee against a slow earliest chunk. Worker failures are recorded and wake the emitter and window waiters. The caller joins every worker before reporting failure; callbacks must terminate, since notification cannot interrupt arbitrary blocking I/O. Call run from only one caller at a time. Sleeps in the demo merely simulate unequal work durations; the maximum held count varies between runs.

A cache over slow storage: each chunk fetched once

Databricks' CachedFile turns the problem around: reads are many and repeated, storage is remote and slow. Split the file into fixed-size chunks and cache whole chunks. A read(offset, length) maps to a range of chunk numbers, and the read is served from those chunks. The concurrency requirement is the interesting part: when eight readers miss on the same chunk at the same moment, the storage should see one fetch, not eight. That is single-flight, and the trick is to cache the future, not the bytes:

  1. Find or claim, under the lock. For each chunk in the range: if the map has a future for it (loaded or loading), take it; if not, put a new incomplete future in the map and remember that this reader must fetch it.
  2. Fetch what you claimed, outside the lock. Complete each claimed future with the bytes. On failure, remove the entry from the map (so a later read retries) and complete the future exceptionally (so everyone already waiting hears about it).
  3. Then wait and copy. Wait on every future in the range and copy the requested slice of each chunk.

The order of steps 2 and 3 matters. A reader fetches everything it claimed before it waits for anything. In a variant that claims chunks individually, waiting first can form a cycle: A waits on B's chunk while B waits on A's. Here all claims for one read are made in one critical section; completing owned fetches before waiting also makes ownership and failure cleanup explicit.

The storage callback must be thread-safe, return exactly one complete chunk (shorter only at EOF), and transfer ownership of bytes that it will never mutate again. The file is immutable for this cache instance. A backend that returns short transfers must assemble the entire chunk before returning; the cache rejects an incomplete result. These teaching snippets handle fetch failures but assume bookkeeping allocations succeed.

Each reader first requests the same range: offset 100 and length 3 times 4096 spans four chunks, numbered 0 through 3. Starts can be staggered; successful chunks remain cached, so those four chunks are fetched once each. Random generators differ between languages, so their total distinct-chunk counts can differ. What the demo leaves out, and what the interviewer will ask next:

  • Parallel fetches for one read. Here a reader fetches its claimed chunks one after another. A read spanning ten cold chunks should hand them to a small fetch pool (the pool from the executor lesson) and wait for all, with a cap on fetches in flight so one huge read cannot swamp the storage. Waiting reader tasks must not occupy all threads of that same pool, or no fetch can run. A rejected submission must fail and remove its claimed future too.
  • Eviction. The cache grows forever. Bound it by bytes with LRU over completed chunks, and never evict a chunk that is still loading, because removing its map entry permits a second fetch for the same chunk; existing waiters still hold the old future.
  • Prefetch. Sequential readers benefit from fetching the next chunk or two before they are asked for.
  • Retries. A failed fetch is not cached, so the next read retries it; add a bounded retry with backoff inside the fetch if the storage is flaky.

Contracts that prevent quiet corruption

A size read is not a snapshot: if the source changes during the copy, different chunks can reflect different versions even when no read fails. Require immutability, hold an appropriate external lock, or copy a snapshot. Reject aliases, including hard links, before truncation. Do not open the destination in append mode: it conflicts with positional writes, and on Linux O_APPEND can make pwrite append despite the supplied offset.

Java positional FileChannel operations are thread-safe, but actual parallel execution is implementation-dependent, and operations that can change file size serialize. truncate(size) does not extend a smaller Java file. C++ here calls POSIX APIs available on macOS and Linux, not ISO C++ file APIs. Java force(true) requests the channel's documented storage guarantee; it is not a portable promise of the macOS full-drive-cache flush. The C++ sample requests F_FULLFSYNC on macOS and reports failure rather than silently downgrading to fsync.

For a mutable remote file, include an immutable version or generation in the cache key and use conditional/versioned reads. Never combine chunks from different versions. Separate timeout of one waiter from cancellation of the shared fetch: one impatient reader must not fail every other reader. Failed fetches are retryable, so “once” means one active fetch for a resident generation, not once forever. Give the storage operation a deadline and fail every claimed future even when a request is cancelled.

Worked example: is parallelism worth it for this copy?

Use decimal units and ideal sustained rates for this estimate: copy 10 GB from an independent source delivering 200 MB/s to a destination writing 500 MB/s. Ignore startup, drain, shared-bus contention and final sync latency.

  • One thread alternates reading and writing each chunk: 10 GB / 200 MB/s is 50 s, plus 10 GB / 500 MB/s is 20 s: 70 s.
  • A reader thread and a writer thread with a small queue of buffers between them: the two devices work at the same time, so the copy takes as long as the slower one: about 50 s. A pool of four reusable 4 MB buffers costs 16 MB including buffers currently owned by the reader and writer; a queue capacity of four alone permits two additional active buffers, or 24 MB.
  • 8 parallel chunk readers: only helps if the source serves parallel requests. If it is a spinning disk or a floppy, the head seeks between chunks and throughput can drop below 200 MB/s. If it is an NVMe drive delivering, say, 1.5 GB/s to 8 readers, the destination becomes the bottleneck and the copy takes about 20 s, holding 8 times the chunk size in memory.

Saying "it depends on which device is the bottleneck, and here is how each case plays out" is the answer the floppy question is fishing for.

Common mistakes

  • A shared file position. Threads that seek and read on one descriptor or channel scramble each other's chunks. Use positional calls.
  • Static thirds or quarters. Splitting the file into one big range per thread leaves fast threads idle while the slowest finishes. Claim small chunks from a counter.
  • Ignoring short reads and the last chunk. A single pread may return less than asked, and the last chunk is usually shorter. Loop, and size the last chunk from the file size.
  • A thread per chunk. With decimal units, a 1 TB file in 4 MB chunks would start 250,000 threads. Use a fixed number of workers.
  • Caching the bytes instead of the future. If the map only holds finished chunks, every reader that misses before the first fetch finishes starts its own fetch, which is exactly the stampede the cache was meant to stop.
  • Caching failures. If a failed future stays in the map, that chunk fails forever, even after the storage recovers.
  • Fetching under the lock. Every reader then waits behind one network call. Claim under the lock, fetch outside it.

In the interview

For the copy, write the sequential version with pread and pwrite first, handling short transfers and the last chunk, then say: "The chunks are independent and positional calls share no offset, so I will let N workers claim chunk numbers from an atomic counter. No lock is needed." For the cache, say the single-flight idea before writing it.

I cache whole chunks, and the map holds a future per chunk rather than the bytes. A reader claims missing chunks under the lock by inserting incomplete futures, fetches what it claimed outside the lock, and only then waits for every chunk it needs. So concurrent misses on one chunk produce one fetch, a failed fetch is removed so it can be retried while current waiters see the error, and reads of different chunks proceed in parallel.

Follow ups: "how many threads?" (find the bottleneck device; memory is threads times chunk size), "the source is a floppy" (sequential reader overlapped with a writer, large chunks, no parallel reads), "the cache is full" (LRU by bytes, never evict in-flight chunks), "what if the storage is slow only sometimes?" (timeouts and a bounded number of fetches in flight).

Senior depth: copying a 1 TB file between machines

Rubrik's senior design rounds stretch the same ideas across a network. Split the file into chunks of several MB, send them on a handful of parallel connections, write each at its offset on the receiver into a temporary file, keep a checksum per chunk and an end-to-end hash, record which chunks are durably confirmed so a broken transfer resumes instead of restarting, throttle with a token bucket so the copy does not starve other traffic, then sync the temporary file, rename within the same filesystem, and persist the directory change using the platform's supported durability procedure. Inside one machine, mention APIs that may use an optimized copy path without application-managed buffers: Java's FileChannel.transferTo and transferFrom, and on Linux copy_file_range and sendfile. Knowing when not to write the loop yourself is a senior signal too.

Key takeaways

  • Positional reads and writes plus chunk numbers claimed from an atomic counter give a parallel copy without an application lock around data transfer.
  • Loop on short transfers, size the last chunk from the file size, and sync once at the end.
  • Extra workers can hide latency or overlap devices; they do not raise a saturated bandwidth limit. Budget every worker buffer.
  • For ordered output, bound the number and bytes of outstanding results, and make every failure wake both workers and the emitter.
  • A chunk cache stores futures: claim under the lock, fetch outside, fetch before you wait, and never cache a failure.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Four threads copy a file chunk by chunk with pread and pwrite (or FileChannel.read and write with a position) on shared descriptors, and each thread owns its buffer. Why is no application lock needed around each data transfer?
Why. A lock protects shared mutable state. Here each chunk has its own source range, destination range and buffer, and positional calls take the offset as an argument. Chunk claiming and failure recording still require synchronization. A separate seek followed by read or write on a shared position needs a lock around the compound operation; positional I/O avoids that race. Java may serialize size-changing writes internally.
A fresh cache has 4-byte chunks and a 12-byte immutable file. One thread calls read(3, 6) and then read(4, 4). All fetches succeed and nothing is evicted. If it prints the total fetch count, what does it print?
Why. The first read covers byte offsets 3 through 8 inclusive, touching chunks 0, 1 and 2, so it fetches three chunks. The second covers offsets 4 through 7, entirely within already cached chunk 1, and adds no fetch. Dividing the length alone by the chunk size misses the unaligned boundaries; counting a fetch per read ignores the number of chunks.
The source is a floppy disk (one head, slow, sequential is best) and the destination an SSD. Which design best preserves sequential source access while overlapping the two devices?
Why. A single-head device serves one position at a time, so parallel reads make it seek and can slow it down. The win is overlapping the slow reads with the writes, which makes the copy take about as long as the slower device instead of the sum of both. Per-chunk syncs and tiny chunks only add overhead.
In the chunk cache, why does the map hold a future per chunk instead of the chunk's bytes?
Why. If only finished bytes were cached, every reader that missed during the first fetch would see "absent" and fetch again: a stampede on exactly the hot chunk. Inserting the incomplete future under the lock marks the chunk as "loading", and everyone who arrives later waits on that one future.
A chunk fetch fails with a timeout. What should the cache do?
Why. Caching the failure makes the chunk fail forever, even after the storage recovers. Silently returning empty bytes corrupts reads. Removing the entry and failing the current waiters reports the error to the readers who needed the chunk now, and lets the next read try again; a bounded retry with backoff inside the fetch is a fine addition.
The ordered pipeline lets 4 workers process chunks while one emitter writes results in chunk order, with a window of 8. Which statements are true? Select all that apply.Select all that apply
Why. The reorder buffer releases a result only when every earlier one has been emitted, and the window stops workers from starting chunks too far ahead, which bounds the number of outstanding chunks, not arbitrary result sizes or the output list. Chunks are claimed in increasing order, so the next chunk to emit always lies inside the window and its worker can finish. The slow work runs outside the lock; only the hand-off is locked.
Java onlyWhich Java channel API exposes a transfer that may use an optimized operating-system copy path without application-managed buffers?
Why. transferTo and transferFrom may use the operating system's direct copy paths, which avoid copying through user space. Loop on short transfers and handle zero progress. Only the receiver of the method call has an explicit position: transferTo advances a file target's position, and transferFrom advances a file source's position. Shared channels therefore cannot be parallelized as though both ends were positional. MappedByteBuffer.force flushes mapped changes; it does not copy a file.
C++ onlyOn Linux, which system call copies a byte range from one file descriptor to another inside the kernel, with offsets you choose?
Why. copy_file_range(fd_in, &off_in, fd_out, &off_out, len, 0) asks the kernel to copy without moving the data through your buffers, and some file systems can even share the blocks. It can copy fewer bytes than asked, so it is called in a loop, and per-chunk calls with explicit offsets parallelize like pread and pwrite.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
You must copy a 200 GB file. The source gives 400 MB/s to one sequential stream and 1.2 GB/s to 8 concurrent readers; the destination writes 600 MB/s. Chunks are 8 MB. Using decimal units and ideal sustained rates on independent devices, estimate the copy time for (a) one thread reading then writing each chunk, (b) a reader and a writer thread overlapped, (c) 8 parallel chunk workers. How much buffer memory does (c) hold?
Model answer

(a) Each chunk is read at 400 MB/s and then written at 600 MB/s, one after the other: 200 GB / 400 MB/s is 500 s, plus 200 GB / 600 MB/s is about 333 s, so about 833 s, roughly 14 minutes.

(b) Overlapped, the copy runs at the slower device's speed: 400 MB/s for reading, so about 500 s, roughly 8.5 minutes.

(c) Eight workers can read 1.2 GB/s, but the destination accepts only 600 MB/s, so the destination is the bottleneck: 200 GB / 600 MB/s is about 333 s, roughly 5.5 minutes. Buffers: 8 workers times 8 MB is 64 MB. The measurements for one and eight readers do not establish the throughput at four. Benchmark intermediate counts; do not assume linear scaling.

Design
Extend your CachedFile design: "A single read often spans ten cold chunks and takes ten round trips in a row. The cache also grows without limit. Fix both."
Model answer

For latency: after claiming the missing chunks under the lock, the reader hands each claimed fetch to a fixed-size fetch pool instead of fetching them one by one, then waits on all the futures. The pool size, or a semaphore around fetches, caps the requests in flight so one big read cannot flood the storage, and a separate admission policy is needed if fairness between large and small reads matters. The invariant stays the same: a chunk's future is completed by whoever claimed it, success or failure, so nobody waits forever.

For memory: bound the cache by bytes. Keep completed chunks in an LRU list under the same lock, update recency on every hit, and evict the least recently used completed chunk when the total exceeds the budget. Keep in-flight entries discoverable so new readers cannot start duplicate fetches; if everything is loading, reserve bytes before admitting fetches and back-pressure new requests. Bound active requests and pinned chunks too: evicting an entry does not free bytes still referenced by a reader. For a large read, process a bounded chunk window instead of pinning the whole range. If reads are mostly sequential, prefetch the next chunk when a reader touches the last part of a chunk. And I would keep the storage call outside every lock, with a timeout, so a slow storage node cannot freeze the cache.

Design
Rubrik: "Copy from a slow sequential device to an SSD, without ExecutorService or pool classes." Describe the threads, the shared state and how it ends.
Model answer

Two threads and a bounded queue I build myself: a lock, two conditions and a fixed array of reusable buffer descriptors, backed by a preallocated pool of four reusable buffers. The reader thread reads the source sequentially in large chunks (several MB), each into a free buffer, and puts (offset, buffer, length) into the queue; when the queue is full it waits, which is the back-pressure that stops it reading too far ahead and caps memory at four buffers across the pool, queue, reader and writer together. Queue capacity by itself would not count the two buffers actively being read and written. The writer thread takes from the queue and writes each buffer at its offset (or sequentially, since order is preserved), and returns the buffer to a free list so no new memory is allocated per chunk.

Ending: when the reader reaches end of file it closes the queue; the writer drains what is left, sees "closed and empty", syncs the destination once and exits; the caller joins both threads. If either thread fails, it records the first error and aborts both the ready queue and free-buffer pool, waking all waiters so the other stops too, and the caller reports the error after joining. This overlaps reading and writing, so the copy takes about as long as the slow source alone, and it does no parallel reads that would make the slow device seek.

  • Measure the bottleneck and budget worker buffers before increasing parallelism
How a senior would say it
I can remove the application lock around data transfer when each worker owns its destination range and buffer, and both reads and writes are positional. First I require a stable source and reject a destination that aliases it, because truncation could destroy the input. I hand out chunk numbers from an atomic counter so faster workers can take more work. Each worker loops over short transfers, handles the smaller final chunk, and treats unexpected end of file or persistent lack of progress as failure. The first failure stops new claims. I join every started worker before closing handles or reporting the error, then sync only on success. Direct overwriting can leave a partial destination; atomic replacement needs a temporary file and a durable rename procedure. Finally I measure storage throughput and budget worker buffers. More threads cannot increase a saturated device's bandwidth.

Out loudabout 60 s
"Eight readers miss on the same remote chunk. How do you avoid eight fetches, including when the first fetch fails?"
What a strong answer covers
  • Insert one incomplete future per versioned chunk under a lock
  • Other readers reuse the same future; the owner fetches outside the lock
  • Publish complete immutable bytes on success
  • Remove the failed generation and complete existing waiters exceptionally
  • Resolve every owned future before waiting on unrelated work
  • Bound fetch admission and retained bytes; one waiter timeout does not cancel a shared fetch
How a senior would say it
I store an incomplete future in the cache before starting the fetch. Under a short lock, the first reader claims the chunk by inserting that future. Later readers find it and wait on the same result. The owner fetches outside the lock, validates the full chunk length, and completes the future with bytes that will not be modified again. On failure, it removes that failed generation and completes its future exceptionally. Existing waiters see the error, while a later request can retry. Every chunk a request claims must eventually complete, even if that request is cancelled. I resolve owned fetches before waiting on someone else's work. For production I also bound fetch concurrency and retained bytes, including chunks pinned by readers. A timeout for one waiter does not cancel everybody's shared fetch, and a mutable file needs its version in the cache key.

Out loudabout 60 s
"Chunk zero is slow while later chunks finish quickly. How do you preserve stream order without running out of memory?"
What a strong answer covers
  • One emitter consumes results by sequence number
  • Admission window bounds how far work may start ahead of the next emission
  • Bound bytes as well as result count and apply sink back-pressure
  • The next needed chunk is inside every positive window
  • Failure wakes emitter and workers; shutdown joins them
  • A retained output list and a stalled callback remain separate limits
How a senior would say it
I use one emitter and a bounded window of admitted chunk numbers. Workers can finish in any order, but they put results in a map keyed by sequence number. The emitter waits for exactly its next number and advances the window as output progresses. If chunk zero is slow, later work eventually stops at the window boundary instead of filling memory forever. I also bound bytes, because eight very large results can still exceed the budget, and the output sink must apply back-pressure. The window itself does not block the next required chunk, so it creates no circular wait when callbacks finish and threads get scheduled. That is not a promise against a hung storage call. Failures set shared stop state and wake both sides, and cleanup joins workers. A demo that collects all emitted output in a list still uses memory proportional to that output.
