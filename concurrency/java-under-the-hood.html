Under the hood: object headers, monitors and the JIT

How HotSpot implements monitors, how the JIT changes locking costs, and why plain shared flags can fail even on one core.

Asked atMicrosoft
Before this:How Java runs: JVM, bytecode, JIT and GCjavac, java, jshell, jstack and jcmd

Most of the time you can treat synchronized and volatile as black boxes. Interviewers sometimes open the box: one Microsoft loop asked how they work internally, down to caches and registers. This lesson gives you an accurate picture, and keeps a clear line between what the Java specification promises and what HotSpot happens to do.

In plain words

Every object carries a small label on its lid. Most of the time the label says which class the object belongs to, plus a little housekeeping. When one thread locks the object and nobody else is around, it scribbles its name on the label in one quick stroke and rubs it out when done. When threads contend, or the owner needs to wait for a condition, the JVM can set up a proper waiting room, with a queue, and point the label at it.

Meanwhile the JIT compiler is a brilliant, literal-minded assistant who rewrites your instructions to do less work. Unless you say that another thread is watching a variable, it may decide to read it once and never look again. That assistant, more than the hardware, is why visibility bugs are real.

Why this matters for concurrency

  • It gives you the cost model. An initial uncontended thin-lock acquisition typically uses a CAS; contention is what costs, through queues, parking and context switches. So the advice is "shrink and split critical sections", never "avoid synchronized".
  • It makes the memory model concrete. A stop flag without volatile can leave a worker spinning forever on HotSpot; the demonstration below tries to expose that allowed outcome.
  • It prepares you for the deep follow ups: "how does synchronized work inside?", "what was biased locking?", "does volatile matter on one core?", "what is a safepoint?". A senior answer starts from the specification, then goes one level down and labels that level as an implementation detail.

The contract and the implementation

Keep two columns apart in your head. The left one is what every correct JVM must provide; the right one is how HotSpot, the JVM inside OpenJDK and most Java distributions, provides it on 64-bit machines. The right column has changed between releases, so say "in HotSpot" when you use it.

The object header

Every object on the HotSpot heap starts with an object header. On 64-bit HotSpot in Java 21 with default header settings it has two parts:

  • The mark word, 8 bytes: the identity hash code once something asks for it (31 bits), the age the garbage collector uses (4 bits), and two lock bits that say how the object is locked right now.
  • The class pointer, 4 bytes with compressed class pointers (the default), which says what class the object is.

Arrays add a 4-byte length. Objects are aligned to 8 bytes, so a plain new Object() takes 16 bytes: 12 of header and 4 of padding. You can see this with the tool from the previous lesson: on a test program holding a million new Object() instances, jcmd <pid> GC.class_histogram reported 1,000,083 instances of java.lang.Object using 16,001,328 bytes. (JDK 24 added compact object headers as an experimental option that shrinks this; Java 21 does not have them.)

On the normal path, monitorexit releases the lock and jumps to return. That is why a synchronized block cannot leak a lock on an exception, while a forgotten unlock() can.

The synchronized method has no monitor bytecodes at all, just the ACC_SYNCHRONIZED flag. The JVM acquires the monitor of this (or of the Class object, for a static method) when the method is called, and releases it however the method exits. monitorenter on a monitor the thread already owns just counts up, which is what makes monitors reentrant.

Thin locks, inflated locks, and what contention costs

Here is what HotSpot does in Java 21's default mode, step by step. The core idea is the thin and inflated lock split:

  1. Uncontended entry. The thread copies the object's mark word into a lock record in its own stack frame, then uses one compare-and-swap to replace the mark word with a pointer to that record (lock bits 00). Exit swaps the original back with another CAS. No queue, no operating system call.
  2. Re-entry. If the mark word already points into this thread's own stack, the thread already owns the lock. It pushes an empty lock record and carries on.
  3. Contention. If another thread owns the lock, the JVM inflates it. It allocates an ObjectMonitor, a structure inside the JVM with an owner, a recursion count, a queue of threads waiting to enter and a wait set, and points the mark word at it (lock bits 10).
  4. Waiting to enter. A contending thread first spins for a short while, hoping the owner leaves soon; HotSpot adapts how long it spins to how often spinning has paid off recently. If the owner does not leave, the thread parks: the operating system takes it off the CPU until the owner's exit wakes it. A thread dump shows this thread as BLOCKED (on object monitor).
  5. wait and notify. They need a wait set, so wait() inflates a thin lock. (Asking for the identity hash code of a thin-locked object can inflate it too, because the original mark word is stored elsewhere.) Calling wait or notify without owning the monitor throws IllegalMonitorStateException.
  6. Deflation. Monitors that are no longer in use are deflated in the background; in a Java 21 thread dump you can see the Monitor Deflation Thread that does it.

What does a lock cost, then? Order of magnitude only, because it depends on the machine: an uncontended lock and unlock is a couple of atomic instructions, tens of nanoseconds; a contended acquisition that has to park and wake a thread costs microseconds, plus a context switch for each side. The cost of a lock is contention, not the keyword. That is the answer to "is synchronized slow?"

Two version notes. Java 21 also ships an experimental alternative to stack locking that tracks thin locks in a small per-thread lock stack, and later JDKs made it the default; the idea, one CAS on the mark word when uncontended, is unchanged. And in Java 21, a virtual thread that blocks while holding a monitor is pinned to its carrier thread, because the monitor is tied to the platform thread underneath; JDK 24 removed that limitation (JEP 491). On Java 21, prefer ReentrantLock around blocking calls made from virtual threads.

Biased locking, and why it is gone

Biased locking was a HotSpot optimization for objects that only one thread ever locks. The first thread to lock such an object wrote its own thread id into the mark word, "biasing" the object toward itself; later locks and unlocks by that thread needed no atomic instruction at all, just a check of the id.

The price came when a second thread wanted the lock. The bias had to be revoked, which meant stopping the owning thread at a safepoint, a costly and complicated operation. The win mattered mostly for code that locked uncontended objects constantly, such as the old Vector, Hashtable and StringBuffer, while modern code uses unsynchronized collections in single-threaded code and java.util.concurrent elsewhere. So JEP 374 disabled and deprecated biased locking in JDK 15, the code was removed afterwards, and on Java 21 the old -XX:+UseBiasedLocking flag is not even recognized: the JVM refuses to start. If an older article mentions it, the up-to-date answer is: it existed, here is what it did, and on Java 21 an initial uncontended thin-lock acquisition normally uses CAS, unless the JIT eliminates it; reentrant entry has its own fast path.

The JIT: why visibility bugs are real

The Java memory model only guarantees that a thread sees another thread's write through a happens-before edge. Without one, the JIT compiler may compile as if no other thread touches a plain field, and it uses that freedom:

  • Hoisting: a plain field read inside a loop that never writes it can be read once, before the loop. while (!stop) { ... } becomes if (!stop) { while (true) { ... } }.
  • Register allocation: a value can live in a register for a long time instead of being reloaded from memory.
  • Reordering: independent loads and stores can move, including the stores made by a constructor relative to the store that publishes the new object.
  • Lock elision and coarsening: escape analysis can remove a lock on an object that never leaves one thread, and adjacent synchronized blocks on the same lock can be merged. These are correct, because no other thread can tell the difference. The optimizer must preserve the observable behaviours allowed by the memory model; synchronization is not an absolute barrier to every code transformation.

What volatile turns into

For the JIT, a volatile field must be re-read on every access and may not be reordered with the surrounding accesses in the ways the memory model forbids. For the CPU, HotSpot emits the ordering instructions the architecture needs. On x86, loads are already kept in order, so a volatile load is an ordinary load, and a volatile store is followed by a locked instruction that acts as a full fence (HotSpot uses lock addl on the stack, which is cheaper than mfence). On ARM64, HotSpot uses load-acquire and store-release instructions (ldar and stlr). These are implementation details; the contract is the happens-before rule.

This answers the famous follow up, "does volatile matter on a single core?" Yes. A single core does not create a happens-before edge. The JIT's hoisting and register allocation apply whatever the core count, so a plain flag can still loop forever even when the hardware executes one thread at a time. On many cores, the caches are kept coherent by the hardware (cache coherence protocols such as MESI), so "volatile flushes the cache to main memory" is the wrong picture. What volatile really does is forbid the compiler optimizations and add the ordering, fences included, that make a write reliably visible.

Safepoints and pauses

A safepoint is a point at which a thread's state, including where all its object references are, is fully known to the JVM. Some VM operations need every Java thread stopped at one: certain garbage collection phases, deoptimizing compiled code, redefining classes, and taking a thread dump. Revoking a biased lock used to be one of them.

  • How threads get there: compiled code checks a poll at method returns and on loop back edges. The VM arms the poll, and each thread stops at its next check. A thread that is running native code or is blocked already counts as safe. Since JDK 10, thread-local handshakes also let the VM stop one thread at a time for some operations.
  • Time to safepoint: one thread in a long loop with no poll delays every other thread, because the pause cannot begin until everyone has stopped. The C2 compiler once removed polls from counted loops for speed; it now keeps one every thousand or so iterations ("loop strip mining"), so this is much rarer than it used to be.
  • Why it matters to concurrent code: a stop-the-world pause pause freezes every Java thread at once, including a lock holder, so every thread waiting for that lock waits for the pause too, and the elapsed time on every clock jumps. A lease checked just before a long pause may have expired by the time the thread acts on it, which is why distributed locks need fencing tokens.

In Java 21, G1 is the default collector on a server-class machine and aims to keep pauses under a target set by -XX:MaxGCPauseMillis (200 ms by default). ZGC, which gained a generational mode in Java 21, is designed for pauses well under a millisecond.

Worked example: what may a reader see?

One thread builds a configuration object and publishes it through a plain static field; request threads read it.

What can happen. Without a happens-before edge, the stores inside the constructor and the store to current may become visible to the reader in a different order: the reader can see the new reference and still see default field values. The memory model allows it; the JIT may reorder independent stores, and ARM processors can make it visible even when the compiled code is in program order. x86 happens to keep stores in order, which is how this bug can pass every test on an x86 machine and then appear on an ARM server.

Three fixes, each with a reason.

  • Declare the field static volatile Config current;. The volatile write happens-before the volatile read that sees it, so the reader sees a fully built object.
  • Make port and host final. The specification guarantees that a thread that sees a reference to an object after its constructor finished also sees the values of its final fields, as long as this did not escape during construction. (In HotSpot, such constructors end with a store-store barrier, free on x86 and a real instruction on ARM.)
  • Use an AtomicReference<Config>, which gives the same guarantees as volatile plus compare-and-set for safe updates.

The best answer combines the second and the first: an immutable Config with final fields, published through a volatile field or AtomicReference, so every reader sees either the old complete object or the new complete object.

Common mistakes

  • "synchronized is slow." Uncontended locking is cheap; contention is slow. Shrink and split critical sections instead of dodging the keyword.
  • "volatile flushes the cache to main memory." Caches are coherent. volatile restricts the compiler and adds ordering, which is what makes the write visible.
  • "It works on my machine." x86 hides some reorderings that ARM shows, and the interpreter hides hoisting that C2 performs. Correctness comes from happens-before edges, not from a passing run.
  • Quoting biased locking as current behavior. It was disabled in JDK 15 and removed afterwards.
  • Locking on a fresh or local object. synchronized (new Object()) excludes nobody, and escape analysis may delete it entirely.
  • Locking on an Integer, a String literal or another shared value object. Unrelated code can end up holding the same lock. javac warns about value-based classes: "attempt to synchronize on an instance of a value-based class".
  • Calling wait or notify without holding the monitor. It throws IllegalMonitorStateException, because the wait set lives in the monitor you do not own.

In the interview

A 2025 Microsoft senior loop in this site's research asked how volatile behaves on a single core versus several cores, and how synchronized works internally, "down to CPU cache and register levels". Confluent insiders, too, advise knowing the internals of the common concurrency utilities. Start from the contract, then go one level down, and say which level you are on.

A synchronized block compiles to monitorenter and monitorexit, with an exception handler that releases the monitor. A synchronized method instead carries a flag. In HotSpot's default Java 21 stack locking mode, an initial uncontended thin-lock acquisition uses CAS to point the object's mark word at a stack lock record. Contention or wait can inflate the lock into an ObjectMonitor with entry and wait queues. Contenders may spin briefly, then park. Biased locking once let repeated acquisitions by one thread skip that CAS, but it was disabled in JDK 15 and has since been removed.
volatile is about the compiler as much as the hardware. Without it the JIT may keep a field in a register or hoist the read out of a loop, so even on a single core a plain stop flag can spin forever. On many cores the caches are coherent; volatile adds the ordering, which on x86 means a fence after the store.

Follow ups to expect. "What is lock inflation, and what triggers it?" (contention, wait). "What is a safepoint, and why do pauses matter for a lock holder?" (a point where the JVM can stop a thread; a stop-the-world pause freezes the holder with its locks, so every waiter waits for the pause too). "Why was biased locking removed?" (revoking a bias needed a safepoint, the code was complex, and modern code rarely locks uncontended objects in hot paths). "Is synchronized fair?" (no: a newly arriving thread can barge ahead of one that was just woken; a fair ReentrantLock favours the longest-waiting acquirer, but does not guarantee scheduling fairness, and untimed tryLock() can barge). "What does the memory model guarantee for final fields?" (visible to any thread that sees the constructed object, if this did not escape).

Senior depth

  • Why lock microbenchmarks lie. Escape analysis can elide a lock on a non-escaping object, and coarsening can merge many small critical sections into one, so a loop of synchronized calls on a local object measures nothing. Use JMH, and lock objects that really are shared.
  • Seeing it for yourself. -XX:+PrintCompilation shows what the JIT compiles and when; printing the generated assembly needs the diagnostic PrintAssembly option plus the separately built hsdis disassembler. The OpenJDK JOL tool (Java Object Layout) prints real object layouts, headers included.
  • Spinning politely. Thread.onSpinWait() (Java 9) tells the CPU a thread is in a spin loop; HotSpot turns it into the PAUSE instruction on x86. It does not create a happens-before edge: the flag you spin on still has to be volatile or atomic.
  • Interpreter versus compiled code. A program can behave differently before and after the JIT compiles a hot loop, which is why a visibility bug can appear only after a minute of load. A memory model guarantee covers every mode; an observation covers only the run you watched.

Key takeaways

  • A synchronized block is monitorenter, monitorexit and an exception handler that always exits; a synchronized method is a flag.
  • In HotSpot, the mark word in every object header holds the lock state: an initial thin-lock acquisition typically uses CAS, and contention or wait can inflate the lock into an ObjectMonitor with entry and wait queues.
  • Biased locking was disabled in JDK 15 and removed; Java 21 still has thin-lock fast paths, reentrancy and JIT lock elimination.
  • Without a happens-before edge, the JIT may hoist, cache and reorder reads of plain fields, so a plain stop flag can spin forever, even on one core.
  • Safepoint pauses freeze every Java thread, lock holders included, which stretches lock waits and breaks time-based assumptions such as leases.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Explain, step by step, what happens inside HotSpot when two threads try to enter synchronized (obj) at the same time on Java 21. Mark which parts are guaranteed by the specification and which are implementation details.
Model answer

Guaranteed by the specification: only one thread at a time owns obj's monitor, the other waits, and when the owner exits, its unlock happens-before the next thread's lock, so the next owner sees everything the first one wrote. Monitors are reentrant, and wait and notify need ownership.

HotSpot details. Each object's header has a mark word with lock bits. The first thread finds the object unlocked, copies the mark word into a lock record in its stack frame and uses one CAS to make the mark word point at that record: a thin lock. The second thread's CAS fails because the object is thin-locked by someone else, so it inflates the lock: the JVM allocates an ObjectMonitor with an owner, a recursion count, an entry queue and a wait set, and points the mark word at it. The second thread spins briefly, adaptively, in case the owner leaves soon; then it parks and shows as BLOCKED in a thread dump. When the owner exits, it releases the monitor and wakes a waiter, which then competes for ownership again; a thread that arrives at that moment may barge in first, because HotSpot monitors make no fairness promise (and neither does the specification). Later an idle monitor can be deflated in the background. Biased locking, which once let a single thread skip even the first CAS, is gone as of Java 21.

Explain
A teammate says: "volatile flushes the CPU cache to main memory, so with volatile, count++ from two threads is safe." Correct both halves of the sentence.
Model answer

First half: caches on mainstream CPUs are kept coherent by the hardware, so a write does not hide in one core's cache forever. What volatile really does is constrain the compiler, which may no longer keep the field in a register, hoist reads out of loops or reorder the access in forbidden ways, and add ordering at the CPU level, for example a fence after each volatile store on x86. The result is the happens-before rule: a volatile write is visible to any later volatile read of that field.

Second half: visibility is not atomicity. count++ is still read, add and write. Two threads can both read 7, both write 8, and one increment is lost, with every access perfectly visible. The fix is an atomic read-modify-write, such as AtomicInteger.incrementAndGet() or LongAdder, or a lock around the whole increment.

Debug
A health check thread loops while (!shutdown) { check(); } on a plain boolean field that another thread sets during shutdown. In testing the service stops cleanly; in production, on an ARM server under load, shutdown hangs. Explain the difference and fix it.
Model answer

There is no happens-before edge between the write of shutdown and the reads in the loop, so the program never had a guarantee. In short tests the loop may still be running in the interpreter, which re-reads the field on every iteration, so it happens to stop. Under sustained load the loop gets hot, the JIT (C2) compiles it, and if it can prove that check() does not write the field (after inlining, for example), it may hoist the read and spin forever. The ARM server and the load are what made the latent bug visible; the code was wrong on every machine.

Fix: declare shutdown volatile (or use an AtomicBoolean), so every iteration reads it and the setter's write is visible. Better still, use interruption or an executor's shutdownNow() if the thread also blocks, so a blocked health check can be woken too. Then add a test that runs the loop long enough to be compiled before signalling it.

"Walk me through two threads entering synchronized on the same object in Java 21. Which parts are Java guarantees, and which are HotSpot details?"
What a strong answer covers
  • Java guarantees mutual exclusion, reentrancy and an unlock-to-later-lock happens-before edge on the same monitor
  • A synchronized block uses monitor bytecodes and exception cleanup; a synchronized method uses a flag
  • HotSpot's default Java 21 stack locking uses the mark word, a stack lock record and CAS for an initial thin-lock acquisition
  • Contention can inflate the lock into an ObjectMonitor; a contender may spin, then park
  • Unlocking makes a waiter eligible to compete again, without a fairness guarantee
  • Biased locking is gone in Java 21; elision and coarsening mean source-level locks do not imply a fixed cost
How a senior would say it
Java guarantees that only one thread owns this object's monitor at a time. The owner can enter it again, and its unlock happens-before a later acquisition of the same monitor. That last rule gives the next owner visibility of earlier writes. For a synchronized block, javac emits monitor entry and exit bytecodes, including cleanup when the body throws. A synchronized method instead carries a flag that tells the JVM to manage the monitor. Now for HotSpot details: in Java 21's default stack locking mode, the first thread saves the object's mark word in a stack lock record and uses compare and swap to point the header at that record. If a second thread contends, HotSpot can inflate the lock into an ObjectMonitor with ownership and waiting information. The contender may spin briefly, then park if necessary. Suppose the first thread updates a balance and leaves. A waiting thread becomes eligible to compete for the monitor, but a new arrival might acquire it first. Java promises no fairness here. Biased locking is gone in Java 21. Still, I would not assign every source-level lock a fixed instruction cost: the JIT can eliminate locks on confined objects or combine adjacent acquisitions. I would measure actual contention before choosing another primitive.

Likely follow up: What changes if the owner calls wait, and does notify hand the monitor straight to a waiting thread?

Out loudabout 90 s
"Our shutdown flag works in short tests but a worker spins forever under load. It even happens on one core. What would you check and fix?"
What a strong answer covers
  • Check for a plain shared flag with no happens-before edge between the writer and reader
  • Explain that JIT hoisting or register reuse can stop repeated reads even on one core
  • Treat interpreter-versus-JIT behaviour as diagnostic evidence, not a correctness guarantee
  • Use a volatile flag for independent stop state; its ordering also publishes writes preceding the signal
  • Distinguish visibility from compound atomicity, with both threads reading 7 and writing 8
  • For a blocking worker, use cooperative interruption or an explicit wakeup protocol as well
How a senior would say it
I would first check whether the stop flag is a plain field shared without synchronization. If it is, the worker has no guarantee of seeing the shutdown write, even on one core. Once the loop gets hot, the JIT may reuse a value in a register or hoist the read outside the loop. The operating system can schedule both threads perfectly and the worker can still keep testing the old value. Running with the interpreter can help diagnose that difference, but a successful run does not make the plain field correct. For an independent stop signal, I would make the flag volatile. A reader that observes the signal also sees writes that happened before the writer published it. This constrains compiler transformations and supplies the hardware ordering needed by the architecture; it does not require flushing every cache to RAM. Visibility also does not make a compound update atomic. Two threads can both read seven from a volatile counter and both write eight. That needs an atomic increment or a lock. Finally, a visible flag cannot wake a worker stuck in a blocking call. I would use interruption where supported, or a wakeup protocol, and ensure the worker responds by exiting. Then I would test shutdown after warmup and while the worker is blocked.

Likely follow up: Would Thread.sleep, Thread.yield or Thread.onSpinWait make the plain flag safe?

  • Measure genuinely shared locks with warmup, representative contention and useful work using JMH
  • Inspect long critical sections and blocking calls before changing the primitive
  • Correlate long waits with safepoint or GC pauses, which do not release an owner's monitor
How a senior would say it
I would check whether the benchmark measured a lock acquisition at all. If the object never escapes the thread, escape analysis may let the JIT eliminate its synchronization. Repeated acquisitions can also be coarsened into one larger critical section. Near-zero time in that setup tells me little about a shared production lock. I would use JMH with warmup, a genuinely shared lock, representative thread counts and work whose result is consumed. I would measure both throughput and the distribution of waiting times. Next I would inspect what the owner does while holding the lock. For example, one network call inside the critical section can make every contender wait, regardless of which lock class I choose. I would move that work outside the lock where the invariant allows it. I would also correlate the long waits with GC and safepoint logs. A stop-the-world pause freezes the owner without releasing its monitor, so waiters inherit that delay. The next change should address the measured cause: the benchmark, the critical section, contention or pauses.
