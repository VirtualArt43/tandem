Build it yourself: a thread pool with futures and shutdown

Build a bounded worker pool with futures, rejection, cooperative stopping and graceful draining, then reason about shutdown races and ownership.

Asked atRubrikLinkedInMicrosoft
Before this:Producer and consumer with a bounded bufferInside an executor: the queue-before-max trapFutures and promisesStopping a thread: interruption and cooperative cancellation

This is the Rubrik question: build a bounded queue, put worker threads on it, return futures, and get shutdown right, with no library executors or queues. Writing the happy path takes ten minutes. The grade is in the lifecycle: what happens to queued work, running work, interrupts and exceptions when someone says stop.

In plain words

A print shop has a fixed crew, an order tray with 4 slots, and hands every customer a receipt they can later swap for their prints. When the tray is full, new customers are turned away at the counter.

At closing time (shutdown) the shop stops taking orders but prints everything already in the tray, then the crew goes home. When the fire alarm rings (shutdownNow) the shop stops taking orders, hands the unprinted orders back to the manager, taps every printer operator on the shoulder, and leaves as soon as they put down what they are holding. The manager waits at the door with a watch (awaitTermination): "everyone out within 2 minutes?"

The contract

Pin the semantics down before writing code; in the interview, say them out loud first. The shutdown policy follows ExecutorService, with a bounded, fail-fast queue chosen for this implementation. Our termination counter records logical worker retirement; physical thread exit is confirmed by joining.

CallNew tasksQueued tasksRunning tasksReturns
submit(task)Accepted while running and the queue has room; otherwise rejectedA future for the task's result or exception
shutdown()Rejected from now onStill runFinish normallyImmediately; it does not wait
shutdownNow()Rejected from now onUnclaimed tasks removed; the pool never runs themAsked to stop (interrupt in Java, a stop token in C++)Tasks not yet claimed by a worker
awaitTermination(t)True once shut down and all workers have retired from the loop; false if time ran out first

The pool's lifecycle has three states, moving only forward: RUNNING, then SHUTDOWN (drain and exit) or straight to STOP (exit now), and it is terminated when, after either, the last worker has retired. SHUTDOWN can also advance to STOP. Java's ThreadPoolExecutor adds TIDYING and TERMINATED for its hooks; you do not need them.

The design: one lock, two conditions, a counter

Everything the workers and callers coordinate on lives under one lock, so there is a single invariant to reason about:

  • The queue: a deque of tasks, never longer than the capacity.
  • The state: RUNNING, SHUTDOWN or STOP.
  • live: how many workers have not retired from the task loop.
  • Condition notEmpty: idle workers wait here for "there is a task, or the state changed".
  • Condition terminated: awaitTermination waits here for "live reached zero".

The key rule: a worker decides to exit, and counts itself out, inside the same critical section in which it saw that there is no more work for it. That ensures a zero count means nobody will execute another task. It does not promise that tasks cooperate with cancellation or that operating-system thread teardown is finished. Submitting wraps the work in a FutureTask (Java) or a std::packaged_task (C++), so results and exceptions land in the caller's future without any extra code in the workers.

The whole pool

Here it is complete, with a main that demonstrates the central paths: a result, a failure, rejection when full, shutdownNow with running and queued work, and a graceful shutdown. The two versions print the same lines. Read it once top to bottom, then read the walkthrough.

Walkthrough: submit and rejection

submit wraps the task so its outcome lands in a future, then hands it to execute, which checks two things under the lock: the state (anything but RUNNING rejects) and the capacity (a full queue rejects). Rejecting with an exception is the fail-fast choice from the rejection lesson; if the interviewer prefers backpressure, add a notFull condition and wait on it with a timeout instead. The insertion is the acceptance point: submit and shutdown racing for the lock are ordered there. The mutex unlock and the worker's later lock also publish task inputs; completion of the future publishes results to get(). Then it signals one idle worker: signal, not signalAll, because one task needs one worker, and every waiter on notEmpty is the same kind of thread.

Two implementation details. std::function requires a copyable callable and std::packaged_task is move-only, so the task lives in a shared_ptr that the queued lambda copies. And the check, the push and the decision to reject all happen under one lock, so a task can never slip in after shutdown has changed the state.

Walkthrough: the worker loop

A worker waits while the pool is RUNNING and the queue is empty. When it wakes, the state decides:

  • STOP: exit immediately, even if tasks remain (shutdownNow already took them out).
  • SHUTDOWN and the queue is empty: exit. This is "drain, then go home".
  • Otherwise: take the head of the queue, release the lock, run the task.

Retiring means counting itself out (live -= 1) under the same lock and signalling terminated if it was the last one. Because the decision and the count happen in one critical section, there is no moment when awaitTermination could see zero workers while one is still about to run a task.

Tasks run outside the lock. Holding the pool's lock during a task would serialize the whole pool and block submit and shutdown for as long as any task runs.

Task failures have an explicit policy. FutureTask and packaged_task capture user exceptions in futures; raw tasks from execute can throw, so this teaching pool catches Throwable in Java and ... in C++ and reports the failure. An uncaught C++ thread exception terminates the process. Java's ThreadPoolExecutor instead lets a raw-task failure end that worker and replaces it when needed. Catching a fatal JVM error is not a guarantee that the process can safely continue; a production policy must distinguish ordinary task failures from process health failures.

And one Java-only subtlety that interviewers who know ThreadPoolExecutor will probe: stale interrupts. A well behaved task that catches InterruptedException restores the interrupt flag before returning. The worker then picks up the next task with the flag still set, and an interruptible operation such as sleep or Condition.await can fail immediately. Ordinary mutex acquisition and non-interruptible I/O need not throw. So the worker clears the flag before each task, unless the pool is stopping, in which case the interrupt was meant for this very task:

C++ has no interrupts, so it has no stale ones: a std::stop_source, once stopped, stays stopped, and only tasks that check the token see it.

Walkthrough: shutdown, shutdownNow, awaitTermination

shutdown changes the state and wakes every idle worker with signalAll (each must see the new state, not just one). shutdownNow sets STOP, moves the queued tasks into a list for the caller, wakes the idle workers, and asks running tasks to stop: Java uses interruption on every worker thread; C++ requests stop on a stop source whose token tasks can read through stopToken(). Either way it is a request. A task that neither responds to an interruptible wait nor checks for stopping keeps running until it finishes, and awaitTermination will honestly report false until then.

What about the futures of the tasks shutdownNow returned? The pool will not run them; the caller must decide whether to retry them elsewhere or discard them. In Java, a caller blocked in get() on one of them waits forever unless someone cancels it, so whoever receives the list should do if (r instanceof Future<?> f) f.cancel(false); for each. In C++, discarded tasks release their waiters only when the returned functions are destroyed: the last shared_ptr to each packaged_task goes with them, the task's destructor stores broken_promise, and every waiter wakes up with an exception.

awaitTermination waits on terminated until the pool is shut down and live is zero. In Java, awaitNanos returns the time remaining, so the loop handles spurious wakeups without stretching the deadline; in C++, wait_for with a predicate does the same loop for you. This observes logical retirement, not physical thread exit: a worker still returns from its function after counting out, and C++ thread-local destructors may run afterwards. Java's owner can call joinWorkers() to confirm physical exit; C++'s destructor joins. Standard C++20 has no timed std::thread::join. The condition budget also excludes time acquiring the mutex, so this method is not a strict wall-clock bound.

Ownership and cleanup

A pool can keep threads alive indefinitely if a task never returns, or if its owner forgets to shut it down. Check each way a worker can be waiting: idle on notEmpty (woken by signalAll in both shutdowns), or inside a task (interrupted or asked to stop by shutdownNow, which only helps if the task cooperates). In C++, the destructor makes the guarantee structural: it calls shutdown() and joins every thread, so a pool cannot be destroyed with a worker still running, and an exception thrown out of the enclosing scope still joins everything during unwinding. Do not destroy a pool from one of its own workers: joining yourself fails or deadlocks. Task captures and other callers must remain valid until workers finish, and no external caller may race pool destruction. The constructors also clean up workers already started if creating a later thread fails; automatic destruction alone does not handle a partially constructed C++ pool. In Java, worker threads are non-daemon, so a pool that is never shut down keeps the JVM alive, the visible symptom of a leaked pool. (A daemon pool would hide the leak and kill tasks mid-run at exit; prefer non-daemon threads plus an explicit shutdown.)

Worked example: the interviewer changes the requirements three times

A 2026 Rubrik screening report describes exactly this: a ring buffer queue first, then a pool on top of it with submit, execute, shutdown and shutdownNow, with the requirements changing three times, and grading on shutdown semantics, interrupts and which exceptions are caught. Another 2026 Rubrik round followed the pool with: what if a task throws, per-task timeouts, and reclaiming idle threads. With the design above, each change has an identifiable place:

  1. "Submit should wait for room instead of failing." Add a notFull condition: execute waits on it (with awaitNanos for a timeout), and a worker signals it after taking a task. Shutdown must signalAll it too, so waiting submitters wake and get rejected.
  2. "Each task gets a timeout." The caller waits on the future with a deadline and cancels on timeout, as in the code below. Do not try to kill threads: neither language can do that safely.
  3. "Reclaim idle threads." Workers above a core count wait with a timeout and retire if nothing arrived, counting themselves out under the lock, so two idle workers cannot both decide to leave the last one. The code is below.
  4. "Add waitUntilComplete()." Keep an unfinished counter under the same lock: increment on submit, decrement after each task (in finally), subtract the tasks shutdownNow removes, and signal an allDone condition at zero. The checkpoint has it in full.

Retirement is only half of a growing pool: submission must create replacement workers when needed, and creation must reserve the live count under the same lock. Do not decrement twice in a final cleanup path. This fragment assumes at least one core worker; allowing zero core workers needs a separate restart-on-submit rule.

Testing it

Interviewers at Rubrik expect code that runs, so test it the way the thread pool problem's harness does:

  • A result and an exception both come back through futures, and the pool still works after a failing task.
  • At most N tasks run at once; gated tasks demonstrate N-way overlap. Count maximum concurrency with an atomic and check that nothing is lost or run twice under several submitting threads.
  • A full queue rejects; a shut down pool rejects.
  • shutdown runs every queued task; shutdownNow returns the queued ones and stops a running task that honours interrupts or the stop token.
  • awaitTermination returns false before the work is done and true after; logical termination means no further task runs. Check physical exit after Java joinWorkers() or C++ destruction; a live-count signal alone does not prove isAlive() is false.
  • No test may hang: join with timeouts in Java and run a watchdog thread in C++.

Common mistakes

  • Workers blocked in take() never see a shutdown flag. Setting a boolean wakes nobody. Signal every idle worker (or interrupt them, or enqueue one poison pill per worker).
  • Shutdown that drops queued tasks (exiting as soon as the flag is set) or shutdownNow that waits for them. Know which one drains.
  • Catching only Exception in the worker, so an Error kills it and the pool silently shrinks; or catching InterruptedException and carrying on, without rechecking STOP, so shutdown is not observed. Idle workers may consume an interrupt if they immediately recheck the lifecycle predicate.
  • Running tasks while holding the pool's lock. One slow task blocks every submit and every other worker.
  • Counting workers out in a separate step from the decision to exit, so awaitTermination can return while a worker is still about to run a task.
  • A C++ destructor that does not join, which calls std::terminate, or one that detaches, which lets workers touch a destroyed pool.
  • Forgetting the futures of tasks shutdownNow removed. In Java, their callers wait forever unless you cancel them.

In the interview

The research contains repeated Rubrik reports of this task: build a bounded blocking queue (sometimes a ring buffer), then a thread pool task executor on it, with submit, execute, shutdown and shutdownNow, usually with library executors and queues banned. LinkedIn has asked for a ThreadPoolExecutor clone without the API, and Microsoft to explain and implement one. Start by stating the contract table out loud, then write the queue, then the worker loop, then the lifecycle.

One lock guards the queue, the state and the count of live workers. Workers wait on a not-empty condition while the pool is running and the queue is empty; shutdown sets the state and signals all, so idle workers drain the queue and exit; shutdownNow sets STOP, takes the queued tasks out and interrupts the workers. A worker counts itself out under the same lock in which it decides to exit, so awaitTermination just waits for that count to reach zero. Tasks run outside the lock and are wrapped in a future, so results and exceptions reach the caller, and the worker catches everything else so an ordinary task failure does not silently remove capacity.

Follow ups to expect: "What exactly does your worker catch, and why?", "What happens to a task that ignores the interrupt?" (it runs to completion; awaitTermination returns false until it does), "Why signalAll in shutdown but signal in submit?", "How would you add per-task timeouts, idle thread reclaim, or a blocking submit?" (above), and "What does a daemon worker change?" (the JVM may exit mid-task, and leaks become invisible).

Senior depth

Graceful shutdown in a real service has more phases than a pool: stop accepting new requests at the load balancer, call shutdown(), awaitTermination for the drain budget, then shutdownNow(), and awaitTermination again briefly, logging anything still running. That is the idiom in the ExecutorService documentation, and stating the two-phase version unprompted is a strong signal.

Interruption is a protocol, not a kill switch. shutdownNow only works for tasks that block in interruptible calls or check the flag, and a task that swallows InterruptedException defeats it. In C++ the same holds for stop tokens. If tasks can be stuck in non-interruptible I/O, the real fix is a timeout on the I/O itself, or closing the socket from outside.

Claiming is not entering user code. Dequeue under the lock transfers ownership to a worker. If STOP wins the lock first, the task is returned; if dequeue wins, the worker may invoke it after shutdownNow() returns, with an interrupt or stopped token available. That is why an exact promise that no user instruction starts after STOP needs a stronger claim/cancel protocol. A FIFO queue also does not guarantee start or completion order with multiple workers.

Blocking submit can self-deadlock too. If every worker submits a child to a full queue and waits for room, nobody remains to drain it. Avoid waiting inside the same bounded pool for admission or completion. Waiting for pool termination from one of its workers is another self-wait. Submission and dequeue are amortized O(1) excluding contention; storage is O(queue capacity plus worker count), with captured payload memory additional.

The core pool uses C++17 features; stop tokens and the demonstration latch require C++20. A C++17 version can expose a shared atomic stop flag and use a mutex with a condition variable for the start gate. Stop callbacks run synchronously during request_stop, so request stop outside the pool lock, keep callbacks short, and do not describe shutdownNow as a hard latency guarantee.

Why not one lock per concern? LinkedBlockingQueue uses separate locks for head and tail so producers and consumers do not contend, and ThreadPoolExecutor keeps its state in an atomic. Both are optimizations with subtle invariants; in an interview, one lock with obviously correct invariants beats a clever design you cannot finish.

Key takeaways

  • State the contract first: shutdown drains, shutdownNow removes queued work and asks running work to stop, awaitTermination waits for logical worker retirement.
  • One lock guards queue, state and live count; idle workers wait on not-empty; shutdown wakes all of them.
  • A worker counts itself out under the lock where it decides to exit; tasks run outside the lock; ordinary task failures have an explicit policy.
  • Futures come from FutureTask or packaged_task; cancel removed Java tasks or destroy removed C++ task wrappers to release their future waiters.
  • Follow ups need explicit contracts: blocking submit, per-task timeouts, idle reclaim, and quiescence versus snapshot completion.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A pool's already idle workers run while (!shutdownFlag) { task = queue.take(); task.run(); }, where take() blocks while the queue is empty. shutdown() sets the flag, then the main thread waits for all workers to exit. The queue is empty. What happens?
Why. A worker blocked in take() is not looking at the flag; nothing wakes it, because no task will ever arrive. Shutdown must wake every idle worker: signal all on the queue's condition with the state checked under the same lock, interrupt them, or enqueue one poison pill per worker.
The queue holds 3 tasks and 2 workers are busy when shutdown() is called. Assume all tasks finish normally. What happens next?
Why. shutdown closes the door and nothing else: no interrupts, no dropped tasks, and it returns without waiting for tasks. Waiting is awaitTermination's job. Dropping queued work and interrupting is shutdownNow.
A pool has 1 worker, running task X, which ignores interrupts and stop requests and prints "X done" when it finishes. Tasks A and B, which print "A" and "B", remain queued until shutdownNow() removes them. Assume X eventually finishes and the caller never reruns the returned tasks. What will be printed?
Why. shutdownNow removes A and B from the queue and returns them to the caller, so they never run. X cannot be stopped because it ignores the request, so it finishes and prints. The worker then sees the STOP state and exits.
Why does the worker loop catch every exception (Throwable in Java, ... in C++) around the task?
Why. Futures do store exceptions for submitted tasks, but raw tasks from execute can throw out of run. In Java an uncaught throwable ends the worker thread; in C++ it ends the whole process. Catching and reporting ordinary task failures preserves capacity here. It does not promise recovery from fatal JVM errors or failures in the pool's own infrastructure.
After shutdown(), awaitTermination(1, SECONDS) returns false. What does that mean?
Why. False only means "not terminated yet"; the last task could even be done while its worker has not yet counted out. Nothing was dropped, and the pool keeps draining in the background. The usual idiom is to wait for a drain budget, then call shutdownNow() and wait briefly again.
Java onlyA task catches InterruptedException, restores the interrupt flag, and returns. Assume a queued task is available and the worker claims it without touching the flag. Its next task immediately calls Thread.sleep(1). What happens, assuming no intervening code clears the flag?
Why. The interrupt flag belongs to the thread, and pool threads run many tasks. So the worker clears the flag before each task, unless the pool is stopping, in which case it re-sets it so shutdownNow still reaches the task. ThreadPoolExecutor also distinguishes stale interrupts from a STOP request.
C++ onlyWhy does submit put the std::packaged_task in a shared_ptr instead of storing it directly in the std::deque<std::function<void()>>?
Why. A lambda that owns a move-only packaged_task is itself move-only, which std::function rejects. Capturing a shared_ptr makes the lambda copyable. (C++23's std::move_only_function removes the need.) A bonus: if the queued function is dropped unrun, the last shared_ptr destroys the task, which stores broken_promise for any waiter.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Add a quiescence barrier waitUntilComplete() to the pool: wait until no accepted task remains queued or running. Call it from outside the pool. Assume producers stop submitting each batch before waiting; it must be reusable and must not hang on tasks removed by shutdownNow. How would a precise snapshot barrier differ?
Model answer

Why it works: the counter counts accepted work, not queued work, so a task that has been taken but is still running keeps waiters waiting. The decrement happens after the task, even when it throws. It reaches zero exactly when nothing accepted is still pending, and it is reusable: the next batch increments it again. Subtracting removed tasks keeps the counter from waiting for work that the pool will not run. The separate pending-future cancellation policy still applies. If producers continue submitting, this is a wait for global quiescence and can wait forever. For a strict snapshot, assign monotonically increasing tickets under the admission lock, capture the highest accepted ticket on entry, and track a contiguous completed prefix plus out-of-order completions. Wait until the prefix reaches that snapshot; a raw completed count is wrong because newer tasks can finish before older ones. Removal counts as a terminal ticket too.

Explain
Explain shutdown versus shutdownNow precisely: new submissions, queued tasks, running tasks, what each returns, and what awaitTermination waits for. Then describe how you would shut a service's pool down in production.
Model answer

Both reject new submissions after their state transition under the admission lock and return without waiting for tasks. A submission overlapping shutdown can win that lock and be accepted first. shutdown() lets queued tasks run and lets running tasks finish; it interrupts nothing. shutdownNow() removes the queued tasks and returns them to the caller (the pool will not run them), and it asks running tasks to stop: in Java by interrupting the worker threads, in C++ by requesting stop on a token the tasks read. A task that ignores the request keeps running. awaitTermination(timeout) waits until the pool is shut down and every worker has logically retired, and returns false if the timeout comes first, which means "not terminated yet", not "failed".

In production: stop sending new work (take the instance out of the load balancer), call shutdown(), wait for a drain budget with awaitTermination, then call shutdownNow(), cancel or fail the futures of the tasks it returned so no caller waits forever, awaitTermination again briefly, and log whatever is still running, since those tasks are not responding to interrupts.

Debug
A candidate's pool uses a BlockingQueue and workers that loop while (running) { queue.take().run(); }. shutdown() sets running = false (a volatile) and then joins the workers. Tests hang in shutdown when the queue is empty, and when they do not hang, tasks queued before shutdown sometimes never run. Explain both bugs and fix them.
Model answer

The hang: idle workers are blocked inside take(); setting a flag does not wake them, and no task will arrive, so join waits forever. The lost tasks: a worker that finishes a task, checks the flag and sees false exits even though tasks are still queued, so shutdown silently drops them, which breaks its contract.

Fix, with the library queue: first close admission atomically with submission, then put one poison pill per worker at the tail of the queue. Workers exit when they take a pill; because the pills are behind the real tasks, every queued task runs first, which is exactly shutdown's semantics; and submit must perform its check and insertion atomically relative to closing admission so nothing can be queued behind the pills. Inserting pills into a bounded queue may block; therefore this direct version changes shutdown into a potentially blocking call. Never hold a lock needed by workers while waiting to insert pills; for the non-waiting shutdown contract use the state-and-condition design here. Fix, with your own queue: put the state under the queue's lock, make workers wait on "queue non-empty or state changed", have shutdown signal all, and exit only when the state is SHUTDOWN and the queue is empty, as in this lesson's pool. Either way, also make submit reject after shutdown, and use joins with timeouts in tests so a bug fails fast instead of hanging. This is the broken shutdown problem.

What a strong answer covers

  • Acceptance and lifecycle transitions share that lock, defining which racing operation wins
  • Workers wait on a predicate, claim a task under the lock and execute outside it
  • FutureTask or packaged_task publishes results and task exceptions
  • Graceful shutdown drains; immediate shutdown removes unclaimed tasks and requests cooperative stopping
  • Removed futures need a terminal outcome; logical retirement differs from joining threads
How a senior would say it
I would use one lock for the queue, lifecycle state and worker count. Submission checks that the pool is running and the queue has room, then inserts under that lock. Shutdown changes state under the same lock. That gives the race a precise answer: a submit that wins admission is accepted; a submit that sees the stopped state is rejected. Workers wait until either work exists or the lifecycle changes. They claim a task under the lock, then release it before running user code. Otherwise one slow task would serialize the pool. Submitted work is wrapped in a FutureTask in Java or a packaged task in C++, so its value or exception reaches its caller. Raw execution needs its own failure policy. Graceful shutdown rejects new work, wakes idle workers and drains accepted tasks. Immediate shutdown removes unclaimed tasks and requests interruption or cooperative stop for work already claimed. A claimed task may enter user code after that request; stopping is not a thread kill. I also settle the removed futures. Here the caller cancels returned Java future tasks or destroys returned C++ wrappers. Workers count themselves out when they retire. Waiting for that count proves no more tasks will run; joining establishes physical thread exit. The owner must keep the pool and task captures alive through cleanup.

Out loudabout 84 s
"Our shutdown sometimes hangs on an empty queue and sometimes loses queued work. The worker loop checks a running flag before taking a task. Talk me through the fix."
What a strong answer covers
  • A flag change does not wake a worker already blocked on an empty queue
  • Exiting solely because the flag is false drops accepted queued work
  • Guard queue and lifecycle together; wait for work or a lifecycle change
  • Graceful shutdown broadcasts and exits only after draining; STOP removes queued work explicitly
  • Use controlled gates and bounded waits to test both races; cancellation still requires task cooperation
How a senior would say it
I would fix the worker's wait predicate and exit predicate together. A visible flag is not enough. A worker already blocked inside an empty queue never gets back to the loop condition unless something wakes it. Conversely, a worker finishing a task can see the flag change and exit while accepted tasks are still waiting. That explains both symptoms. I would protect queue and lifecycle state with the same lock. A worker waits while the pool is running and the queue is empty, rechecking after every wakeup. Graceful shutdown changes state and wakes all idle workers. They keep taking queued work and retire only when the queue is empty. Immediate shutdown is a separate state: it removes unclaimed work and requests cooperative stopping of claimed work. To test this, I would first stop an idle pool and check bounded completion. Then I would hold workers behind a controlled gate, enqueue known tasks, close admission and release the gate. Every accepted task must finish exactly once. A separate immediate-stop test checks removed futures and a cooperative running task. If a task ignores cancellation, termination can still time out; that is a task limitation, not a lost queue wakeup.
