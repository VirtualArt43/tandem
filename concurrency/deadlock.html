Deadlock: the four conditions and how to break each

The four Coffman conditions, safe lock acquisition in both languages, and dependency cycles involving pools, futures and queues.

Asked atRubrikNvidiaAppleLinkedIn
Before this:Taking several locks safelyCondition variables and monitors

A service can stop making progress even when every shared value is protected correctly. For classic resource deadlocks, breaking any one of the four Coffman conditions prevents the cycle.

In plain words

Four cars reach a crossroads at the same moment and each pulls halfway into the junction, waiting for the car on its right to clear. Nobody can move: each car holds a piece of road that another needs, and waits for a piece that another holds. No driver did anything wrong alone; the arrangement is the bug.

Traffic rules fix it by removing one ingredient. A signal imposes an order, so the cars never form a circle. The yellow box rule says do not enter the junction unless you can get all the way through, so nobody holds road while waiting. Remove any one ingredient and gridlock cannot happen.

What a deadlock is

A deadlock is a set of threads in which each waits for a resource or event that only a member of that waiting set can provide, so none can proceed without intervention. The dependency is often a lock, but it can involve any resource a thread waits for: a semaphore permit, a free worker in a pool, a future's result, another thread finishing, a slot in a bounded queue, a database row lock. The defining symptom is a dependency cycle with no way to make progress. Parked waiters use little CPU, but a deadlock involving spinlocks can burn CPU, and unrelated threads may keep running. A long wait alone is not proof of deadlock.

The classic example is two bank transfers in opposite directions. A latch makes both threads hold their first lock before either tries the second, so the cycle is deliberate and repeatable. The examples isolate locking: amounts and balances stay within the integer range, and the stress demos allow overdrafts.

The latch requires C++20. In C++17 use a counter protected by a separate mutex and a condition variable: increment the counter, notify, and wait with the predicate arrivals == 2. That wait releases the coordination mutex while each thread keeps its account lock.

Run the Java version and take a thread dump: the JVM reports the monitor cycle as Found one Java-level deadlock; the next lesson reads that output. A clean ThreadSanitizer run does not prove deadlock freedom. Some Linux runtimes support lock order inversion detection: observing both a then b and b then a can produce a potential-deadlock warning even without a hang. Apple's clang runtime used here does not report those inversions. On this Mac inspect a hang with sample PID or bt all in lldb; mutex owner instrumentation can help connect the stacks.

The four Coffman conditions

The coffman conditions describe classic deadlocks involving reusable resources. All four must hold in the deadlocked set; merely allowing all four in a design does not mean every execution deadlocks.

ConditionWhat it meansIn the transfer bugBreak it by
Mutual exclusionA resource can be held by only one thread at a timeEach account's lock is exclusiveUse a shareable resource, such as an immutable snapshot
Hold and waitA thread keeps what it holds while it waits for moreT1 keeps a while waiting for bTaking everything at once, or letting go before waiting
No preemptionNobody can take a resource away; only its holder releases itNothing can take a from T1A resource manager revokes allocations and safely rolls back a victim
Circular waitA cycle of threads, each waiting for the nextT1 waits for T2, T2 waits for T1One global order for acquiring locks

Breaking any one prevents this resource deadlock. The usual first choice is circular wait, because a global lock order needs no retries. Ordinary mutexes cannot safely be revoked from their owner; giving a mutex back voluntarily is not preemption.

Break circular wait: one global order

If every thread acquires locks in the same global order, a cycle cannot form: to wait in a circle, someone would have to take a lower lock while holding a higher one. This is lock ordering. Order by something unique and immutable, such as an account id.

Two follow ups come up every time. What if there is no unique id? In C++, order by address: std::less<Account*>{}(&from, &to) is a total order on pointers. In Java, System.identityHashCode gives a number but two objects can share one, so on a tie both threads first take one extra global tie-breaking lock, which serializes equal-hash acquisitions. What if from and to are the same account? Java's synchronized is reentrant, so nested locking of one object is harmless, but locking the same std::mutex twice is undefined behavior in C++; check &from == &to first.

Grouped acquisition and releasing before a wait

Reserving every resource together would break hold and wait. A library multi-lock operation gives a related guarantee: deadlock-safe acquisition, without promising that the acquisitions happen atomically.

  • Acquire a set with a deadlock-safe protocol. std::scoped_lock both(from.m, to.m); (C++17) uses std::lock for several mutexes. A common implementation locks one, tries the rest and releases on failure. The standard guarantees deadlock avoidance for that acquisition, not an exact algorithm or atomic acquisition of the entire set. Java has no equivalent multi-lock call; the try and release loop below makes its own protocol explicit.
  • Release before you wait. Copy what you need from the first object, release its lock, and only then lock the second. Revalidate if another thread could invalidate your snapshot; splitting a transfer this way would lose its atomicity. And never hold a lock while doing something that can wait for an unknown time: an RPC, a disk write, a callback into someone else's code (open calls), or future.get(). Each can add a dependency outside your lock-order proof.

Pass distinct mutexes that the current thread does not already own. The group operation cannot prevent a cycle involving an outside lock, a callback or a future. For C++11 or C++14, construct two std::unique_lock<std::mutex> guards with std::defer_lock, then pass those guards to std::lock; their destructors release ownership.

Break hold and wait explicitly: try, give back, retry

Take the first lock, try the second without blocking; if it is unavailable, release the first before backing off and starting over. Here the order follows the arguments, but no thread waits for another lock while keeping a partial set. Call this routine without any outside lock held, and do no blocking work inside the completed critical section.

Without backoff, threads can release, retry and collide repeatedly: a livelock, covered in livelock and starvation. Randomization reduces repeated collisions; it does not guarantee fairness or a bounded completion time. The retry count varies by run, and these demos have no overall deadline.

A timed Java tryLock(long timeout, TimeUnit unit) or C++ try_lock_for(duration) on std::timed_mutex bounds an individual attempt, subject to scheduling delays. It does allow a temporary wait while holding the first lock, so release all held locks on failure. A production loop needs one overall deadline, bounded retries and cancellation, not a fresh full timeout forever.

Break no preemption: revoke only recoverable resources

Preemption requires a recovery protocol. A database resource manager can select a transaction, roll back its changes and reclaim its row locks. An OS can save and restore suitable execution state before reallocating a resource. Neither lets arbitrary application code unlock another thread's mutex safely: a half-updated invariant may be exposed, and unlocking an unowned C++ mutex is undefined behavior.

The retry loop above instead has the owner release voluntarily before it waits again. In Java, interruption only helps if the wait supports it and cleanup releases resources; interrupting a thread blocked entering synchronized does not release its monitors. See detection and recovery for the transaction approach.

Break mutual exclusion: do not need the lock

Immutable snapshots can make a resource shareable without exclusive locking. Replacing one protected update with an atomic can remove that application lock, but atomic does not imply lock-free: C++ atomics can use internal locks, and an atomic spin loop can still wait in a dependency cycle. A truly lock-free algorithm guarantees system-wide progress for its operations, not freedom from every application-level deadlock.

A single owner can serialize transfers without account mutexes, provided it does not block on work that depends on itself. Actors, bounded queues and synchronous replies can still form cycles. Read-write locks also retain exclusive writers; changing lock type alone is not a proof of deadlock freedom.

Worked example: the dining philosophers, four ways

Five philosophers sit around a table with one fork between each pair; each needs both neighbouring forks to eat. If all pick up their left fork at once, every fork is held and every philosopher waits for the right one: a five-thread circular wait. These acquisition protocols prevent that fork cycle:

  • Circular wait, by ordering: number the forks and always pick up the lower number first. Philosopher 4 now reaches for fork 0 before fork 4, so the circle cannot close.
  • Circular wait, by limiting diners: a semaphore with 4 permits lets at most four philosophers try at once. A full cycle needs all five holding a fork, so it can never form. (People often say this breaks hold and wait; it does not. Each diner still holds one fork while waiting for the other.)
  • Hold and wait, by reservation: a waiter grants both forks together or grants neither. A waiting philosopher holds no fork; the waiter must not block on fork acquisition while keeping its own bookkeeping lock.
  • Hold and wait, by retry: pick up the left fork, try the right without blocking; if it is taken, put the left one down before retrying. This is voluntary release, not resource preemption. C++ can instead use std::scoped_lock for deadlock-safe group acquisition.

Mutual exclusion is the one you cannot break here, because a fork really is used by one philosopher at a time. You will implement these in the dining philosophers lesson and problem.

Deadlocks without any locks

Any wait can be part of a cycle. These are the ones that catch experienced engineers, because the code has no synchronized or mutex at the point where it hangs.

The pool that waits for itself

A task running in a bounded thread pool submits a subtask to the same pool and blocks on its result. If every worker is doing that, the subtasks sit in the queue with no free thread to run them, and nothing moves. This is a pool self-deadlock, also called thread starvation deadlock. With one worker it takes a single task:

If all N workers are occupied by parents waiting for queued children, the same cycle forms at any pool size. Small tests can miss that schedule. Prefer asynchronous composition (thenCompose, or a continuation after all children finish), or a separate child pool with no dependency back on the blocked parent pool. Java's ForkJoinTask.join() can help execute work for structured, acyclic fork/join tasks; changing executor type does not cure arbitrary blocking or cyclic dependencies. Practise the pool self-deadlock problem and read rejection and pool failures.

Joining yourself

A thread that waits for its own termination waits for something that can only happen after it stops waiting. An untimed Java self-join waits until interrupted; C++ is required to notice and throw.

Java prints that it gave up after about 200 ms; C++ prints join on myself threw: resource_deadlock_would_occur, because std::thread::join is required to throw std::system_error with that code when a thread joins itself. (This pair has no Run button: ThreadSanitizer's interceptor for pthread_join does not expect a failed self-join and aborts on the later, legitimate join, although the plain build behaves exactly as described.) The same mistake hides in shutdown code: a worker that calls pool.shutdown() followed by awaitTermination(timeout, unit) from inside the pool cannot observe full termination until its own task returns; the wait can only time out or be interrupted.

Other disguises

  • Futures waiting on each other. Task A waits for B's result before producing its own, and B waits for A's. Two futures, no locks, a perfect cycle.
  • Bounded queues in a loop. Stage 1 blocks putting into a full queue to stage 2 while stage 2 blocks putting into a full queue back to stage 1. Break the cycle by consuming before producing, reserving capacity, or making the return path nonblocking with an explicit overflow policy; an unbounded queue trades the capacity wait for memory risk.
  • Waiting on a condition while holding another lock. wait releases only the lock it belongs to, so the thread that would signal you may be stuck on the other lock: a nested monitor lockout.
  • Taking the same lock twice. A non-reentrant lock (a std::mutex, a Semaphore(1)) acquired again by the thread that holds it is a self-deadlock; in C++ it is undefined behavior. A classic interview code review shows a set() that holds the lock and calls a resize() that locks it again.
  • Static initialization. Two classes (or two C++ function-local statics) whose initializers need each other, first used from two threads at once, can deadlock on the runtime's initialization locks.
  • Across services. Service A calls B synchronously, and B calls back into A, while both have small thread pools. Under load every A thread waits for B and every B thread waits for A: a deadlock spread over two machines, addressed with propagated deadlines, nonblocking composition and resource isolation that removes the dependency cycle.

Common mistakes

  • Ordering by something that can tie or change: a hash code, a balance, a name. Use a unique, immutable key, and plan for ties.
  • One code path follows the order and another does not. Ordering only works if every path that takes both locks obeys it, including callbacks and error handling.
  • tryLock without releasing what you hold, or retrying immediately in a tight loop. The first can retain the dependency cycle; the second can livelock. Release on failure and bound retries; random backoff reduces collisions.
  • Holding a lock across a call you do not control: a listener, an RPC, a log write that can block, future.get().
  • Blocking inside pool tasks on the same pool. Fine in tests with idle workers; a hang under real load.
  • C++: locking the same std::mutex twice, for example transfer(a, a). Undefined behavior; check for it.
  • "Fixing" a deadlock with a sleep or a longer timeout. It changes the odds, not the cycle.

In the interview

Deadlocks arrive in three ways. As theory: Nvidia asked a candidate how deadlocks arise with a two-lock deposit and how to fix them, and an Apple hiring manager asked how deadlocks happen and how to resolve them. As a debugging round: Rubrik reports include debugging broken multithreaded code with a deadlock, and expects code that still compiles and runs after your fix. And as a design follow up: "what could deadlock here?"

A deadlock needs four conditions at once: mutual exclusion, hold and wait, no preemption and circular wait, so I only have to break one. Here I break circular wait: every transfer locks the lower account id first, so no lock cycle can form. If I could not order the locks, I would acquire both together with std::scoped_lock, or take one, try the other, and release and retry with random backoff, accepting some retries.
I also look for deadlocks that have no locks in them: a pool task blocking on a future that only the same pool can complete, or a lock held across a call into code I do not control.

Follow ups: "what if two accounts have the same id, or no id?", "does the order of arguments to std::scoped_lock matter?" (no), "is tryLock enough?" (release partial ownership on failure; backoff reduces livelock but does not guarantee fairness), "how would you find a deadlock in production?" (a thread dump; next lesson), "can one lock deadlock?" (yes: a non-reentrant lock taken twice, or a thread waiting on an event whose producer needs that same lock), and "which condition does a semaphore of N minus 1 break for the philosophers?" (circular wait).

Senior depth

Design so you rarely hold two locks. The strongest answer is structural: one lock per invariant, critical sections that never call out, and data owned by one thread where possible. When two locks are unavoidable, document the order and enforce it: a lock hierarchy that checks levels at runtime in debug builds turns a rare production hang into an immediate test failure.

Lock upgrades need their own protocol. Two readers can each retain shared ownership while waiting for exclusive ownership of the same logical resource. A global order between different resources does not fix that cycle. Use a supported upgrade protocol, or release shared ownership, acquire exclusive ownership and revalidate what you read; see read-write locks.

Make deadlocks loud. Name your threads, avoid locks across remote calls and instrument long waits, and alert when a lock wait exceeds a threshold, with a thread dump attached. A deadlock found in a dump at 2 a.m. is a bug fix; one found three days later from user complaints is an incident.

Key takeaways

  • A deadlock is a closed dependency cycle. Low CPU is common for parked waiters, not a requirement.
  • It needs mutual exclusion, hold and wait, no preemption and circular wait. Break any one.
  • Order locks globally or use a deadlock-safe acquisition protocol. Voluntary try, release and retry avoids indefinite hold and wait; it does not preempt a mutex.
  • Deadlocks need no explicit locks: pool tasks waiting on the same pool, a thread joining itself, futures waiting on each other, full bounded queues in a loop.
  • C++: never lock one std::mutex twice; std::scoped_lock makes argument order irrelevant. Java: synchronized is reentrant, and jstack reports supported lock cycles, not pool and future dependencies.

Quick check

Answer each question, then read why. Your score is saved for your module test.

For unique immutable account ids used by every locking path, which Coffman condition does "lock the smaller id first" break?
Why. Threads still hold one lock while waiting for another, and locks are still exclusive and cannot be taken away. What changes is that every thread climbs the same order, so nobody can wait for a lower lock while holding a higher one, and a cycle cannot form.
Thread 1 runs transfer(a, b) and thread 2 runs transfer(b, a), each locking from and then to, with no ordering. What can happen to print(total) after both threads join? Assume distinct accounts, valid amounts, no other locks or transfers, and ordinary scheduling progress.
Why. If one thread takes both locks before the other takes its first, everything completes correctly. If each grabs its first lock before the other's second attempt, they wait for each other forever. The locks keep the totals correct; the risk is liveness, not wrong numbers. Neither the JVM nor the OS breaks a lock deadlock for you; jstack only reports it.
A fixed pool has 2 workers and an unbounded queue. Both workers are already running parent tasks. Each parent submits a child to that same pool and calls untimed get() on it. No interruption or cancellation occurs. What happens?
Why. Both parents occupy the fixed pool's two worker slots, and untimed get() has no automatic timeout. The unbounded queue accepts their children without creating additional worker slots. Both workers wait for subtasks that only a worker could run. No lock is involved, but the circular wait is there: worker waits for queued task, queued task waits for a worker. Fix it with async composition, a separate pool for subtasks, or structured fork/join tasks with acyclic dependencies.
Five dining philosophers acquire their left then right fork, release both after eating, and release an admission permit last. A semaphore with 4 permits must be acquired before any fork. Which Coffman condition does it break?
Why. A philosopher still holds one fork while waiting for the second, so hold and wait remains. But a cycle around the table needs all five philosophers each holding one fork, and at most four can be trying, so the cycle can never close. Saying it breaks hold and wait is a common slip.
Two threads use the "take the first lock, try the second, on failure release and retry" scheme, and they retry immediately with no delay. What can go wrong?
Why. For these distinct locks, with no outside locks or blocking work in the critical section, no thread waits for another lock while keeping a partial set, so this acquisition protocol cannot deadlock. But two threads that keep colliding at the same moment can repeat forever: a livelock. Random backoff reduces repeated collisions but gives no deterministic fairness guarantee. A successful tryLock synchronizes with the prior release of that lock, just like a blocking acquisition; it does not introduce a data race.
C++ onlyThread 1 runs std::scoped_lock lk(a.m, b.m); and thread 2 runs std::scoped_lock lk(b.m, a.m);, repeatedly. Can they deadlock with each other if a.m and b.m are distinct std::mutex objects, neither is already owned by the caller, and no other locks or blocking calls are involved?
Why. With more than one mutex, std::scoped_lock uses std::lock, whose acquisition sequence must avoid deadlock. Try and release is a common implementation, not a mandated algorithm. Argument order does not change that guarantee; external locks and dependencies remain your responsibility. Fair completion time is not guaranteed.
Java onlyTo order locks on objects without ids, a teammate locks the object with the smaller System.identityHashCode first. What is the remaining hole?
Why. Identity hash codes are stable for an object's lifetime but are not unique. On a tie, two threads could lock the pair in opposite orders. Acquire a single shared tie lock first whenever the hashes are equal, or give objects unique stable ordering ids. Identity hashes are stable, nesting monitors is legal, and the issue is uniqueness, not thread safety.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Fix the transfer deadlock in your language. Your transfer(from, to, amount) must never deadlock, must keep money exact under many threads, and must also be safe when from and to are the same account. Assume nonnegative starting balances, unique immutable Java account ids and no external locks held. Reject negative amounts and destination overflow before changing either balance.
Model answer

The Java version breaks circular wait with a global order on a unique, immutable id. The C++ version uses std::scoped_lock for deadlock-safe acquisition of the supplied mutexes, regardless of argument order. Ordering by address with std::less would work as well. Both check the same-account case: harmless in Java because synchronized is reentrant, but essential in C++. Validation of funds and overflow happens before either balance changes, under both locks. Java ids must be unique by construction; a comment alone cannot enforce that contract.

Explain
In about a minute, as you would say it out loud: what are the four conditions for deadlock, and how would you break each one?
Model answer

For reusable resources, all four are necessary. Mutual exclusion means exclusive ownership; shareable immutable snapshots can remove that need. Hold and wait means keeping one resource while waiting for more; reserve the entire set together, or try the next lock without blocking and release partial ownership on failure. No preemption means allocations cannot be reclaimed from their owner; breaking it needs a recovery protocol such as transaction rollback, not an arbitrary mutex unlock. Circular wait means the dependencies form a cycle; one global order on unique immutable lock ids prevents it. That is usually my first choice for application mutexes. Random backoff reduces retry collisions but does not prove starvation freedom, and voluntary release is not preemption.

Debug
A service hangs under peak load but never in tests. A thread dump shows all 8 threads of report-pool in WAITING, each inside FutureTask.get, called from ReportTask.call, and the pool's queue holds 30 SectionTasks. CPU is idle. What is the bug and how do you fix it?
Model answer

This strongly suggests a pool self-deadlock; first confirm that the queued sections are responsible for completing those futures and that no external producer can complete them. Each ReportTask runs on report-pool, submits its SectionTasks to the same pool, and blocks in get() waiting for them. Under peak load, eight reports start at once and occupy all eight workers, so the section tasks they are waiting for sit in the queue with no worker free to run them, and every worker waits forever. In tests fewer reports run at once, so idle workers pick up the sections and nothing hangs. There is no lock in the cycle: workers wait for queued tasks, and queued tasks wait for workers. Fixes, in order of preference: do not block inside the task, compose the section futures asynchronously (for example allOf and then build the report in a continuation); or run sections on a separate pool so parents can never starve children; or restructure the computation as acyclic ForkJoinTasks, whose joins can help execute subtasks. Merely moving arbitrary blocking calls to a ForkJoinPool is insufficient. As a safety net I would add a timeout to any remaining get() with cleanup and cancellation of abandoned children. A timeout ends that wait; it does not cancel the child automatically.

"Two transfers lock the source account and then the destination. Why can this freeze, and how would you fix it?"

  • Map mutual exclusion, hold and wait, no preemption and circular wait to those locks

How a senior would say it
I would put every transfer under one global lock order. The failure is that the first transfer holds account A and wants B, while the second holds B and wants A. Neither can reach the code that releases its first lock. The four conditions are all present: the locks are exclusive, each thread holds one while waiting for another, ownership cannot be forcibly taken away, and the waits form a circle. I would acquire the lower immutable account id first on every path. Every acquisition then moves upward in the same order, so a cycle cannot close. The ids must be unique; a hash needs a tie rule. I would return early for a same-account transfer, especially in C++, where taking the same ordinary mutex twice is undefined behavior. For two distinct C++ mutexes I could also use std::scoped_lock, provided I do not bring an outside lock into the operation. In Java, another option is to try the second lock and release the first on failure. That is voluntary release, not preemption. Random backoff reduces collisions, but does not guarantee fairness or bounded completion. I would keep both locks through balance validation and the update, and avoid callbacks or blocking work inside that critical section.

Likely follow up: What if a callback inside the transfer acquires a third lock?

"All eight workers are waiting in future get, and their queue contains the child jobs they need. No mutex cycle is reported. What do you check and change?"
What a strong answer covers
  • Identify pool self-deadlock only after confirming the queued children complete those futures
  • Trace parent holds worker, parent waits for child, child needs a free worker
  • Explain why low-load tests and a negative monitor detector can miss it
  • Prefer asynchronous composition or an independent child execution resource
  • Limit fork/join to appropriate acyclic tasks and explain timeout cleanup
How a senior would say it
This looks like a pool self-deadlock. I would first confirm that the queued children are the tasks that complete those eight futures, and that nothing outside the pool can complete them. Each parent occupies a worker while waiting for its child. Every child needs a worker, and all workers are occupied by waiting parents. That is the cycle, even though no mutex is involved. A monitor deadlock detector will not reconstruct it, and low-load tests may pass because spare workers run the children. I would have the parents return without blocking and assemble their results in continuations when the children complete. A separate child pool can also work if it has no dependency back on the blocked parent pool. For structured, acyclic CPU tasks, fork/join is another option; moving arbitrary blocking code to a work-stealing pool is not a general fix. I would add an overall deadline and explicitly cancel abandoned work where supported. A timed future wait does not cancel the child by itself, and adding more workers only moves the saturation point.
