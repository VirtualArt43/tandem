Lambdas, captures and callables

What lambdas compile to, captures and their lifetimes in threads, init captures, mutable, std::function, and handing callables to std::thread.

Asked atGoogleAdobe
Before this:Copy, move and move-only types

Almost every thread you start in C++ runs a lambda, and the lambda's capture list is the exact list of what that thread shares with you, and for how long. Read a capture list the way you read a lock: as a statement about sharing and lifetime.

In plain words

You are sending a colleague off to work in another building. You can pack them a lunchbox with copies of everything they need: they can go anywhere, at any time, and nothing at home is affected. Or you can leave a note: "the files are on my desk". The note is lighter, but it only works while the files are still on your desk, and if you are editing them while they read, you will get in each other's way.

A lambda that captures by value packs the lunchbox. One that captures by reference leaves the note. Threads go to another building and come back on their own schedule, which is why the choice matters so much.

Why this matters for concurrency

  • std::thread t([&] { ... }); captures every local it uses by reference: shared state plus a lifetime promise your code must keep until the thread finishes.
  • [=] copies values, but not what pointers and this point to. A by-value lambda can still share, and dangle.
  • Init captures, [v = std::move(v)], can transfer ownership into the thread. Moving an owning value can remove sharing; moving a pointer, view or shared owner does not prove its target is private.
  • Callbacks run later, on some other thread. A 2024 Google phone screen had the candidate re-implement a drive search on top of get_async(path, callback), which runs the callback on a thread it creates, and a 2021 Adobe C++ candidate was grilled on lambda internals.
  • Thread pools store tasks as std::function<void()>, which requires a copyable callable, so a task that owns a std::unique_ptr needs a workaround you should know.

What a lambda is

A lambda expression creates an object, the closure, of a unique unnamed class type that the compiler writes for you. The general form is [captures](parameters) specifiers -> return_type { body }, and most parts are optional. This lambda and the class below it are, for practical purposes, the same thing:

Everything else follows from that picture, and it is what "lambda internals" questions are after:

  • By-value captures are data members, filled in when the lambda is created, not when it is called. Reference captures refer to the original objects; their storage representation is unspecified.
  • The call operator is const unless you write mutable, so by-value captures cannot be changed by default.
  • Every lambda expression has its own type. Store one in auto, pass it to a template, or erase its type with std::function.
  • A lambda with no captures converts to an ordinary function pointer, which is how you pass one to a C API.
  • Parameters can be auto (a generic lambda, C++14), and C++20 allows an explicit template parameter list: []<typename T>(const std::vector<T>& v) { ... }.

Captures: the list of what you share

Every variable capture form says one of two things: "copy this into the closure" or "refer to the original".

CaptureMeaningWhat a thread running it shares with you
[x]Copy x nowThe copy is separate, but pointers, views and shared owners inside it can still reach shared objects
[&x]Refer to xx itself: needs sync if anyone writes, and x must outlive the thread
[=]Copy every local the body usesWhatever those copies point to
[&]Refer to every local the body usesAll of them
[this], or [=, this] in C++20Copy the this pointerThe whole object, through the pointer
[*this] (C++17)Copy the whole objectThe object's copy semantics decide: pointer-like members may still share targets
[v = std::move(v)]Init capture: a new member initialized from an expressionThe closure owns its new member; existing aliases or pointer-like members can still share its target
[&, x] or [=, &total]A default plus exceptionsAs the parts say

Two rules catch people. Globals and statics are never captured; the body uses them directly, so every thread shares them. And in a member function, [=] does not copy members: it captures this, so the body reads the live object. C++20 deprecates that implicit capture of this through [=] (GCC warns by default, clang under -Wdeprecated), so write [=, this] when you mean the pointer and [*this] when you want a copy.

Captures and threads: sharing and lifetime

A reference capture is fine when two things are both true: the referenced object outlives the thread (it is joined in the same scope, for example), and every access to it is synchronized or there are no concurrent writes. When a lambda goes to another thread, capture by value by default and reference only what you have argued about.

Init captures: move ownership into the lambda

An init capture (C++14) creates a closure member from any expression. It is how you move data into a thread instead of sharing it:

Inside the body these members are const, like any by-value capture, so you can read data but not move out of it unless the lambda is mutable. The second line also makes the closure move-only, which matters for std::function below.

mutable: each closure has its own state

mutable removes the const from the call operator, so the body can change its by-value captures. Those changes live in that particular closure object, and copies of the closure are separate objects. std::thread copies the callable it is given, so a thread mutates its own copy:

It prints outer calls = 0, counter() = 3, twin() = 4. The outer variable never changes, the thread's increments vanished with its copy, and the two named closures count independently. mutable makes nothing thread-safe. On a lambda it makes the call operator non-const; on a class data member it instead permits modifying that member through a const object.

Function objects, function pointers and member functions

A lambda is one kind of callable. A function object is any class with an operator(); a function pointer and a pointer to a member function are callables too. std::thread, std::invoke and the rest of the library call all of them the same way, which hides a trap with member functions:

Passing &c shares the object through a pointer; passing c copies the whole object into the thread, exactly like any other argument. Either can be right, but only one of them updates c.

std::function: one type for any callable

std::function <R(Args...)> can hold any copyable callable with a matching signature: a lambda, a function object, a function pointer, a bound member function. It is the usual element type of task queues and callback lists, because every lambda has a different type and a queue needs one.

  • It erases the type, so a call goes through an indirection, and storing a large closure may allocate memory (small ones usually fit in an internal buffer; the size is up to the implementation).
  • Calling an empty std::function throws std::bad_function_call.
  • It requires a copyable target. std::function<void()> f = [p = std::move(ptr)] { ... }; does not compile when ptr is a std::unique_ptr. C++23 adds std::move_only_function; before that, put the move-only part behind a std::shared_ptr.

That last point is exactly the problem of a thread pool's submit, which must return a future. std::packaged_task is move-only, so the classic idiom shares it through a shared_ptr and stores a small copyable lambda in the queue:

std::bind, in a sentence: std::bind(f, args...) makes a callable with some arguments fixed (copied, unless wrapped in std::ref) and placeholders _1, _2 for the rest; prefer a lambda, which is clearer and optimizes better, or C++20 std::bind_front(f, args...) when you only fix the leading arguments.

Handing a callable to std::thread

std::thread t(f, args...) copies or moves f and every argument into the new thread's storage, in the calling thread, before the constructor returns (the decay copy from the values lesson), then calls them in the new thread. Four consequences:

  • Conversions happen late. Arguments are stored as their decayed types and converted to the parameter types only when the new thread calls f. That creates the classic dangling buffer bug below.
  • The return value is thrown away. Use a std::promise, a std::packaged_task or std::async to get a result back.
  • An exception escaping the callable calls std::terminate. Catch inside the thread and pass the error out, as covered in exceptions inside threads.
  • Beware the most vexing parse. std::thread t(Worker()); declares a function named t and starts nothing (clang warns). Write std::thread t{Worker()}; or pass a lambda.

Worked example: searching a drive through get_async

This is the shape of the Google phone screen question. You are given get_async(folder, callback): it lists one folder on a new thread and then calls callback on that thread with the folder's children. It prints /docs/old/plan_v1.txt and /docs/plan.txt, with ThreadSanitizer silent. Walk through the captures the way you would in the interview:

  • folder and callback are moved into the thread's lambda inside get_async, so the caller can return at once and nothing dangles.
  • s is a shared_ptr captured by value. Every pending callback co-owns the search state, so it stays alive however the threads are scheduled.
  • needle is captured by value: a small string, copied, never shared.
  • &drive is the one reference, and it comes with its sentence: main waits for pending to reach zero, so no callback can submit more work before destruction starts. The drive is declared first, destroyed last, and joins the remaining worker threads before its mutex is destroyed.
  • The callbacks run on other threads, so everything they touch in Search is guarded by its mutex, and main waits on a condition variable, not a sleep.
  • Termination is a counter: pending goes up before each request and down after each folder is handled. A child folder's increment always happens before its parent's decrement, so the count cannot reach zero early.

For the complexity follow up: with network latency per listing, the sequential search costs roughly one latency per folder, while this one costs roughly one latency per level of depth, at the price of one thread per folder; a real version would cap concurrency with a pool.

Common mistakes

  • [&] on a lambda that runs on a detached thread or is stored for later. Capture by value, or move ownership in.
  • Capturing a loop variable by reference in threads created in the loop. Capture it by value.
  • Believing [=] copies members. It captures this; use [*this] for a copy, and write [=, this] when you mean the pointer.
  • A task lambda that captures a function parameter by reference, like submit(task) doing queue.push([&] { task(); }). The parameter dies when submit returns.
  • Expecting a mutable lambda's state to change in the original after passing it to std::thread, which copied it.
  • Putting a move-only lambda in a std::function. It does not compile; share the move-only part, or use std::move_only_function in C++23.
  • Passing a char array, or anything needing conversion, to a thread that then detaches. Convert before the thread starts.
  • Letting an exception escape the thread's callable, which terminates the whole program.

In the interview

Lambdas appear in nearly every C++ concurrency answer, so the questions are pointed: "what does [&] capture, and is that safe here?", "what happens to a lambda capturing this when the object is destroyed?", "how do you pass a unique_ptr into a pool task?", "what does the compiler generate for a lambda?". The Google drive question adds the callback twist: your code runs on threads you did not create, so you must say what each callback owns and what it locks.

A lambda is an object of a compiler-generated class: by-value captures are data members holding copies made when the lambda is created, by-reference captures refer to the originals, and the call operator is const unless the lambda is mutable. When a lambda goes to another thread, I capture by value or move ownership in with an init capture, and every reference I do capture comes with a reason it outlives the thread and a lock for every shared write.
std::function needs a copyable target, so for a pool's submit I wrap the packaged_task in a shared_ptr and queue a small lambda that calls it; in C++23 I could use std::move_only_function instead.

Follow ups: "Where does the callback run?" (on the API's thread, so it must be thread-safe and quick, or hand off its work); "What is the cost of std::function?" (an indirect call and possibly an allocation); "Why might [=] in a member function dangle?" (it copied this, not the object).

Senior depth

std::function hides a const loophole. Its call operator is const, but it invokes its target as non-const. Two threads calling one shared std::function can therefore race if its mutable lambda changes captured state without synchronization, even though every call looks like a const read. std::move_only_function in C++23 makes const part of the signature: a std::move_only_function<void() const> only accepts targets callable as const. Const-callability alone still cannot prove thread safety if the target accesses shared mutable objects.

Coroutine lambdas keep their captures in the closure, not in the coroutine frame. If the closure object dies before the coroutine finishes, every capture dangles at the next resume. The C++ Core Guidelines therefore advise against capturing lambdas that are coroutines; pass the data as parameters, which are copied into the frame.

Generic lambdas are templates. [](auto x) { ... } gives the closure a templated call operator, so one closure can be called with different types; every capture rule above applies unchanged.

Key takeaways

  • A lambda has a compiler-generated class type: value captures are members filled in at creation, reference captures borrow the originals, and the C++20 call operator is const unless mutable.
  • By-value captures copy; by-reference captures share and must outlive every thread that runs the lambda. Capture by value by default for threads, and never capture a loop variable by reference.
  • [=] in a member function captures this, not the members; use [*this] or [=, this] explicitly.
  • Init captures move ownership into a closure; a move-only closure cannot go into std::function, so share the move-only part or use C++23 std::move_only_function.
  • std::thread copies or moves the callable and its arguments, converts arguments late, discards return values and terminates on escaping exceptions.

Quick check

Answer each question, then read why. Your score is saved for your module test.

for (int i = 0; i < 4; i += 1) threads.emplace_back([&] { sum += i; }); where sum is a std::atomic<int>, followed by joining all threads. What is true?
Why. All four closures refer to the one variable i, which the main thread keeps incrementing and which stops existing when the loop ends. The atomic sum protects the additions, not the reads of i. Capture i by value: [&sum, i].
What does this print?
Why. Each closure holds its own copy of calls. counter reaches 2, twin is copied at 2 and reaches 3, and the thread runs on its own copy of counter, so counter is still 2 and its next call returns 3. twin() then returns 4, and the outer calls was never touched. (C++17 guarantees left to right evaluation of the << operands.)
Inside a member function, std::thread t([=] { use(count_); }); t.detach(); where count_ is a data member. What does the lambda capture?
Why. Members are reached through this, so [=] captures the pointer, not the member. C++20 deprecates this implicit capture. Copy the member with [count = count_], copy the object with [*this], or keep the object alive with shared_from_this().
Does std::function<void()> f = [p = std::make_unique<int>(1)] { use(*p); }; compile?
Why. std::function must be copyable, so it can only store copyable callables. Share the resource (std::shared_ptr), or in C++23 use std::move_only_function. Init captures of unique_ptr are fine on their own; it is the std::function that objects.
struct Worker { void operator()() const; }; and then std::thread t(Worker()); t.join();. What happens?
Why. This is the most vexing parse: std::thread t(Worker()); reads as a declaration of a function t taking a function that returns Worker. Clang warns on the declaration, and calling .join() on a function fails to compile. Use braces, std::thread t{Worker()};, or a lambda.
Counter c; then std::thread t(&Counter::add, c, 100); t.join(); where add adds its argument to a member. What is c's total afterwards?
Why. Like every argument, the object is copied into the thread's storage, and std::invoke calls add on that copy. Pass &c (or std::ref(c)) to operate on the original, and then make sure c outlives the thread.
void log_line(int level, const std::string& text); In a function, char buffer[64] is filled, then std::thread t(log_line, 3, buffer); t.detach(); and the function returns. What is wrong?
Why. Arguments are stored as their decayed types, so the array becomes a pointer into the caller's stack, and the conversion to std::string happens in the new thread when it calls log_line. Convert first: std::thread t(log_line, 3, std::string(buffer));.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
You have a blocking std::vector<std::string> list_folder(const std::string& path). Implement get_async(path, callback) so callers can return immediately, the callback receives the result, and nothing dangles. Say which thread runs the callback.
Model answer

The path and the callback are moved into the thread's lambda, so the caller's locals can die immediately. The callback runs on the worker thread, not on the caller's thread, so the caller must make it thread-safe (lock whatever it touches) and keep alive anything it captured by reference. The std::jthreads are owned by the lister and joined in its destructor, so no thread outlives the object. A production version would reuse a bounded pool instead of one thread per call, and would decide what happens to callbacks still pending at shutdown.

Debug
A hand-written pool has void submit(std::function<void()> task) { std::lock_guard<std::mutex> g(m_); queue_.push([&] { task(); }); cv_.notify_one(); }. Workers pop and run the queued lambdas. What is wrong, and how do you fix it?
Model answer

The queued lambda captures task, the function parameter, by reference. submit returns right after pushing, so task is destroyed while the lambda that refers to it waits in the queue. When a worker runs it, it calls a destroyed std::function: undefined behavior that may crash, call garbage, or appear to work. It is a lifetime bug, not a locking bug; the lock is fine.

Fix: move the task into the queue instead of wrapping it, queue_.push(std::move(task));, or if a wrapper is needed, capture by move: queue_.push([task = std::move(task)] { task(); });. The rule: anything that outlives the current call must own what it uses.

Explain
An interviewer asks: "What does the compiler generate for [x, &y](int z) { return x + y + z; }, and what does that mean when the lambda runs on another thread?"
Model answer

The compiler generates an unnamed class with a data member holding a copy of x, access to the original y through a reference capture, and a const operator()(int z) that returns x + y + z. The reference capture is typically represented by a pointer, but the standard does not require a data member for it. Evaluating the lambda initializes its captures and produces one closure object. Because it has captures, it does not convert to a function pointer, and its type is unique, so it is stored in auto, a template parameter or a std::function.

On another thread: the copy of x is private to the closure, so it is safe however long the thread runs. The reference to y is shared, so y must outlive the thread (joined in the same scope, or owned elsewhere for longer), and if any thread writes y while this one reads it, that is a data race unless both use a lock or y is atomic. Also, std::thread copies the closure, which copies x again and copies the reference, so the thread still refers to the same y.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"My pool protects its queue with a mutex, but a task sometimes crashes after submit returns. The queued lambda captures the task parameter by reference. What would you check?"
What a strong answer covers
  • The reference capture borrows the parameter and does not extend its lifetime
  • Submit can destroy the parameter before the worker invokes the queued closure
  • The queue mutex protects queue operations, not the lifetime of borrowed task state
  • Move the callable into the queue, or capture it by move in a wrapper
  • Audit pointers, views and references inside the callable for further borrowed lifetimes
  • Run tasks outside the queue lock and join workers before destroying executor state
How a senior would say it
I would first check lifetime. Capturing the task parameter by reference does not keep it alive. The queue can hold a perfectly valid closure whose reference points to a destroyed parameter. For example, submit pushes the wrapper, returns, and destroys its local task. A worker later pops the wrapper and calls through that dangling reference. The result is undefined behavior, even though every queue operation used the mutex correctly. I would move the task directly into the queue. If a wrapper is necessary, I would use an init capture that moves the task into the closure. That gives the queued object ownership of the callable until execution or cancellation destroys it. I would then inspect the callable's own captures. Owning a closure does not make a borrowed pointer or string view inside it safe. Those need an independently valid lifetime or an owning replacement. Finally, workers should remove tasks under the queue lock and invoke them after unlocking, and shutdown must join workers before destroying the state they use. The queue lock solves access ordering; the captures must also solve lifetime.

Likely follow up: What if the moved task owns a unique_ptr, but the queue stores std::function<void()>?

Out loudabout 75 s
"A member function queues a callback with [=]. Does that give the callback a safe snapshot of the object? What would you choose instead?"
What a strong answer covers
  • When the body accesses members, implicit this capture copies the pointer, not the object
  • Destruction can leave the callback dangling; concurrent member mutation can race even while the object lives
  • Capture selected owning values for an independent snapshot, taking synchronization while copying if required
  • Capturing star-this copies the object but leaves pointer-like members sharing their targets
  • Capture a shared owner for required work or a weak observer for work that may be skipped
  • Keeping the object alive still leaves its mutable state needing synchronization
How a senior would say it
No. When the callback uses a member, the default value capture captures the this pointer, not a snapshot of the whole object. If the object dies before execution, accessing the member is undefined behavior. If it survives but another thread changes that member without synchronization, there can still be a data race. For a task that only needs a name and a timeout, I would capture those values explicitly. If they are concurrently mutable, I would take their snapshot under the appropriate lock. Capturing star-this is another option for a copyable object, but it uses the object's copy semantics. Raw pointers, views and shared pointers inside the copy may still refer to shared state. If the callback needs the original object, I would capture a shared owner when completion must keep it alive, or a weak observer when it should skip work after destruction. The weak callback must lock and check the resulting owner before use. Either way, preserving lifetime does not protect mutable fields. I would state both the ownership rule and the synchronization rule before calling the callback safe.

Likely follow up: What ownership cycle could a callback capturing a shared owner create if it is stored inside that same object?

Out loudabout 90 s
"In C++20, design a pool submission that accepts a lambda owning a unique_ptr, returns a future, and queues work in std::function<void()>. Why is a direct conversion rejected?"
What a strong answer covers
  • A unique-pointer capture makes the closure move-only; std::function requires a copyable target
  • Move the callable into a packaged task whose future carries its result or exception
  • Own the packaged task through a shared pointer and queue a lambda capturing that pointer by value
  • Copyable wrappers share one task, so the executor must invoke each accepted task exactly once
  • Execute outside the queue lock and define what happens to accepted work during shutdown
  • C++23 std::move_only_function can remove this copyability workaround if supported by the queue
How a senior would say it
The direct conversion fails because the closure is move-only, while a C++20 std::function requires a copyable target. Moving the lambda into the wrapper does not remove that requirement: the wrapper must support being copied later. I would move the user's callable into a packaged task and obtain its future. Then I would put that packaged task in a shared pointer and queue a small lambda that captures the pointer by value and invokes the task. That wrapper is copyable because copying it copies an owning handle, not the unique pointer inside the original callable. The packaged task carries the return value or a thrown exception to the future. There is still only one logical task, so the pool must invoke each accepted submission exactly once, even if it copied the wrapper internally. A worker pops under the queue mutex and calls the wrapper after unlocking. I would also define shutdown: either drain accepted tasks or abandon them with a documented result, rather than leave futures waiting indefinitely. In C++23, a queue of std::move_only_function can hold move-only wrappers directly and avoid the shared ownership workaround. For C++20, sharing the packaged task is a practical bridge between unique resource ownership and a copyable queue element.

Likely follow up: What does the future observe if its packaged task is destroyed before it is invoked?
