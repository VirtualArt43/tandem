volatile in Java, std::atomic in C++

What Java volatile and C++ std::atomic guarantee, what they do not, the atomic operations you will use, and why C++ volatile is not for threads.

Asked atMicrosoftNvidiaDatabricksRubrik
Before this:Happens-before and synchronizes-withThe lost update: read, modify, write

Java and C++ both have a keyword called volatile, and they mean completely different things. In Java it is a real threading tool. In C++ it is not a threading tool at all; the C++ tool is std::atomic. Mixing the two up is one of the fastest ways to lose an interviewer's trust, and knowing exactly what each one buys is one of the fastest ways to win it.

In plain words

A Java volatile variable is like a whiteboard in the corridor that everyone must read directly, never from a photo on their phone. You always see the latest number. But if two people each read "41", walk back to their desks, and write "42", one of the updates is lost. Seeing the latest value is not the same as updating it safely.

An atomic variable is like the token machine at a bank counter. You press the button and get the next number, and no two customers can ever get the same one, because reading the counter and advancing it happen in one indivisible step. Atomics give you the whiteboard's visibility and the token machine's indivisibility, for one variable at a time.

Java volatile: what it guarantees

A field declared volatile in Java gets four guarantees:

  1. Visibility. A write to a volatile field happens-before every later read of it, so readers always see the latest value. No hoisting, no stale register copy.
  2. Ordering. Reads and writes made before a volatile write cannot be moved after it, and reads and writes made after a volatile read cannot be moved before it. That is what makes the "write data, then set a volatile flag" hand-off safe.
  3. One global order. All volatile accesses in the program fall into a single order that every thread agrees on, which is why volatile fixes the store buffering test from reordering. In C++ terms, volatile behaves like memory_order_seq_cst.
  4. No tearing for long and double. The Java specification (JLS 17.7) allows a plain 64 bit write to be split into two 32 bit halves, so a reader could see half of each value, a torn read. Volatile long and double reads and writes are always atomic. (References are always atomic, volatile or not.)

And one thing it does not give: atomic compound actions. count++, count += 1, "check then set", "read, compute, write back" are several steps, and volatile makes each step visible without making the group indivisible. Volatile is also not mutual exclusion: two threads can be inside the same volatile-using code at once.

volatile does not make count += 1 atomic

This is the single most asked volatile question, so see it fail in both languages. In Java the field is volatile; in C++ the variable is volatile int, which is what people who confuse the two languages write.

Both lose updates, for the reason you know from the lost update: two threads read the same value and both write back one more. The C++ version is worse: ThreadSanitizer reports a data race, because C++ volatile is not synchronization, so the program's behavior is undefined. (C++20 even deprecates += and ++ on volatile variables, which is why the code spells out the read and the write.)

When volatile is the right tool in Java

Volatile is exactly right when every write is independent of the current value, or when only one thread ever writes:

  • Flags: volatile boolean stopRequested, as in visibility.
  • One writer, many readers: a sensor thread publishes volatile double latestTemperature; readers just need the latest value.
  • Publishing an immutable object: build a new Config and assign it to volatile Config current. Readers get a fully built object; see safe publication.
  • Cheap reads with locked writes: readers read a volatile field with no lock; writers update it inside synchronized, so their read-modify-write is atomic. Reads never block.

In C++ the shared variable must still be std::atomic, because get() reads it while a writer may be storing it, and a non-atomic access there would be a data race. For a plain add you would just use fetch_add; the lock earns its place when the update is more complicated than one atomic operation can express.

The atomic toolkit

An atomic variable makes single operations indivisible: the hardware performs the read, the change and the write as one step that no other core can split. Java has AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference and array versions; C++ has the class template std::atomic<T>. The operations line up almost one to one:

Every one of these defaults to the strongest ordering: Java atomics have volatile semantics, and every std::atomic operation defaults to std::memory_order_seq_cst. C++ lets you pass a weaker order as an extra argument; that is the next lesson, memory orders.

compare-and-swap is the operation everything else can be built from: "set it to next, but only if it still holds expected". If another thread changed the value in between, it fails, and you re-read and retry. Three details in the compare-and-set loop are worth saying out loud in an interview:

  • Why a loop. if (x > max.get()) max.set(x); is a check-then-act: between the check and the set, another thread can store a larger value, and you overwrite it with a smaller one. The CAS only succeeds if nothing changed since you read.
  • Who updates expected. C++'s compare_exchange_weak writes the current value into current when it fails, so the loop body can be empty. Java's compareAndSet only returns false, so you re-read yourself (or use accumulateAndGet(x, Math::max), which loops for you).
  • Weak versus strong. compare_exchange_weak may fail even when the value matched (a spurious failure, allowed so that CPUs built on load-linked and store-conditional, such as older ARM cores with their load-exclusive and store-exclusive pair, can implement it cheaply). Inside a retry loop that costs nothing, so prefer weak in loops and strong for a single attempt. Java's compareAndSet is strong; weakCompareAndSetVolatile and friends are the weak versions.

Two atomic steps are not one atomic step

In C++, a = a + 1 on a std::atomic<int> compiles: it is an atomic load followed by an atomic store. Two threads can both load 5 and both store 6, exactly the lost update. a += 1, ++a and a.fetch_add(1) are single atomic operations. The Java version of the same mistake is a.set(a.get() + 1). Atomics protect one operation, never a sequence of them.

Java

VarHandle, in one paragraph

Java 9 added VarHandle: a handle on an ordinary field or array element that offers every atomic operation and lets you choose the ordering per access: plain, opaque, acquire and release (getAcquire, setRelease), or full volatile (getVolatile, setVolatile), plus compareAndSet, getAndAdd and the rest. It is the supported replacement for sun.misc.Unsafe, and many java.util.concurrent classes use it internally (a few core ones, such as AtomicInteger and ConcurrentHashMap, still use the JDK's internal Unsafe). The AtomicXxx classes expose the same modes since Java 9 (setRelease, getAcquire, getPlain). Application code rarely needs it; reach for it when you want atomic operations on a field of an existing class without an extra AtomicLong object per instance.

What can be atomic

In C++, std::atomic<T> accepts any trivially copyable T: integers, pointers, enums, plain structs of any size. Whether the hardware can update a given T in one instruction depends on its size and the CPU. If it cannot, the library silently uses a hidden lock, and the "atomic" is no longer lock-free. You can ask: is_always_lock_free is a compile-time constant, and is_lock_free() answers at run time.

C++

On this site's Apple M chips the 16 byte pair is lock-free and the 32 byte struct is not. On x86-64 the 16 byte answer depends on the compiler and its flags, so never assume; check it, or static_assert(std::atomic<T>::is_always_lock_free) when it matters (it does inside signal handlers and in latency-critical code).

Java's answer to "make a whole struct atomic" is different and often cleaner: make the struct an immutable object and swap references with an AtomicReference. A reference fits in one machine word, so compareAndSet on it is lock-free on every mainstream JVM, and readers get a consistent snapshot of every field at once.

std::atomic_flag and the simplest spinlock

std::atomic_flag is the one atomic type the C++ standard guarantees to be lock-free on every platform. It is a boolean with two operations: test_and_set() (set it and return the old value) and clear(). C++20 adds test(), wait(), notify_one() and notify_all(). Its classic use is a spinlock; the Java equivalent uses AtomicBoolean.compareAndSet.

The counter itself is a plain variable, and it is safe: the successful test_and_set (or compareAndSet) that takes the lock and the clear (or set(false)) that releases it form happens-before edges, just like a mutex. Spinlocks burn CPU while they wait, so they suit only very short critical sections; spinlocks covers when they beat a mutex.

C++ volatile is for hardware, not threads

In C++ (and C), volatile tells the compiler one thing: every access to this object is an observable side effect. It must not remove a volatile read or write, merge two of them, or reorder volatile accesses relative to each other. That is exactly what you need for a memory-mapped device register, where reading has a meaning to the hardware and each read may return something new:

What C++ volatile does not do: it does not make any operation atomic, it emits no CPU fences, it does not order volatile accesses against ordinary ones, and it creates no happens-before edge between threads. Two threads accessing a volatile variable without synchronization is still a data race and still undefined behavior. The legitimate uses are memory-mapped I/O, variables shared with a signal handler (volatile std::sig_atomic_t), local variables that must survive a longjmp, and stopping the optimizer from deleting a benchmark loop.

The confusion has history. Microsoft's compiler, by default on x86 targets, gives volatile acquire and release semantics as an extension (the /volatile:ms option), so code that used volatile flags "worked" on Windows for years, and can break when compiled for ARM, where the default is the standard behavior (/volatile:iso). Systems interviews still ask "what does volatile mean in C?"; an Nvidia system software round in our research lists volatile among its C topics. The answer is hardware registers, not threads.

Worked example: metrics for a request handler

A handler running on 32 threads must track four things. Pick the right tool for each.

  1. Total requests. One variable, updated from its old value by every thread: LongAdder in Java (it spreads contention across cells), fetch_add on a std::atomic<long> in C++, or per-thread counters summed on read when contention becomes visible in profiles.
  2. Slowest request so far. One variable, but the update depends on a comparison: a compare-and-set loop, or accumulateAndGet(latency, Math::max) in Java.
  3. The last error message. A reference written independently of its old value: a volatile String lastError in Java; in C++ a std::string cannot be atomic, so guard it with a mutex (or store an std::atomic<std::shared_ptr<const std::string>> where your library supports it).
  4. Min and max latency, always consistent with each other. Two atomics would let a reader see a new min with an old max. Keep them in one immutable pair behind an AtomicReference with a CAS loop, or under one mutex.

The pattern behind the answers: one variable and one operation, use an atomic; more than one variable or more than one step, use a lock or one atomic reference to an immutable object.

Common mistakes

  • volatile for a counter. Visibility is not atomicity. Use an atomic increment.
  • volatile for threads in C++. It is not synchronization; a race on it is undefined behavior. Use std::atomic.
  • a = a + 1 on a std::atomic, or a.set(a.get() + 1) in Java. Two atomic operations, one lost update. Use fetch_add or incrementAndGet.
  • Check, then set with atomics. if (max.get() < x) max.set(x) can overwrite a larger value. Use a CAS loop.
  • A volatile array in Java. volatile int[] slots makes the reference volatile, not the elements. Use AtomicIntegerArray, AtomicLongArray or AtomicReferenceArray.
  • A non-final atomic field. AtomicLong hits = new AtomicLong() that some code later reassigns makes threads update different counters. Declare atomic fields final.
  • Several atomics for one invariant. Each is consistent on its own; together they are not. One lock, or one atomic reference to an immutable value.
  • compare_exchange_weak outside a loop. It may fail spuriously. Use compare_exchange_strong for a single attempt.

In the interview

Expect this at three depths. The basic one is "does volatile make this counter safe?" The middle one is "how does AtomicInteger.incrementAndGet work?" (a Databricks-tagged commenter on Blind says compare-and-swap questions are now common there, and a Rubrik onsite went from primitives to how CAS works to a CAS-based stack). The deep one is hardware: a 2025 Microsoft senior loop asked how Java volatile behaves on a single core versus multiple cores, down to caches and registers, and a 2026 Nvidia system software round listed volatile among its C questions.

Volatile in Java gives visibility and ordering: every read sees the latest write, and the write acts as a release and the read as an acquire, so I can use it for flags or to publish an immutable object. It does not make compound actions atomic, so for a counter I use an atomic, which does the read-modify-write as one hardware instruction or a compare-and-swap loop. In C++, volatile is only for memory-mapped hardware; for threads I use std::atomic, which defaults to sequentially consistent ordering.

Follow ups to expect:

  • "volatile versus synchronized?" synchronized gives mutual exclusion and visibility (an unlock happens-before the next lock of the same monitor). volatile gives visibility and ordering for one field, never blocks, and makes no compound action atomic.
  • "How is incrementAndGet implemented?" A single atomic add instruction where the CPU has one (x86 lock xadd, ARM ldadd), or a CAS retry loop.
  • "What is the ABA problem?" CAS compares values, not history: if the value goes from A to B and back to A, a stale CAS still succeeds. It is harmless for a counter or a maximum and dangerous for pointers in a lock-free stack; see the lock-free stack and ABA.
  • "What does volatile compile to?" On x86, a volatile read is a plain load and a volatile write is followed by a locked instruction that acts as a full fence. On ARM, load-acquire and store-release instructions.
  • "Does volatile matter on a single core?" Yes: the compiler's hoisting and reordering do not depend on core count.
  • "Is a non-volatile long safe to share?" Not by the specification: a 64 bit write may tear. Make it volatile or use AtomicLong.
  • "What is is_lock_free for?" Knowing whether a std::atomic<T> hides a lock, which matters for signal handlers and latency.

Senior depth

What the instructions look like. On x86, every read-modify-write is a lock-prefixed instruction (lock xadd, lock cmpxchg), and xchg is implicitly locked. HotSpot implements a volatile store as an ordinary store followed by a locked add to the stack, which serves as a full fence; C++ compilers typically use xchg for a seq_cst store. Loads need nothing special on x86. On ARMv8.1 and later (including Apple M chips), clang compiles fetch_add to ldaddal, compare_exchange to casal and exchange to swpal; seq_cst loads and stores become ldar and stlr. Older ARM cores use load-exclusive and store-exclusive retry loops, which is where spurious CAS failure comes from.

Contention is the real cost. An uncontended atomic increment costs roughly a few nanoseconds; the same increment on a cache line that 32 cores are fighting over costs a cross-core transfer every time, an order of magnitude or two more. That is why LongAdder exists and why counters at scale stripes counters across cells.

C++20 additions. std::atomic<T>::wait(old) and notify_one() let a thread sleep until an atomic changes, without a mutex or condition variable (on Linux they are typically built on a futex). std::atomic_ref<T> performs atomic operations on an ordinary object you already have, such as an element of an existing array, for a phase of the program in which every access goes through atomic_ref.

Field updaters. Before VarHandle, Java code that wanted atomic operations on millions of small objects without an AtomicLong per object used AtomicLongFieldUpdater and its siblings on a volatile field. You will still see them in older libraries.

Key takeaways

  • Java volatile gives visibility, ordering, one global order of volatile accesses, and untorn long and double. It never makes count += 1 atomic.
  • Atomics make single operations indivisible: add, exchange, compare-and-set. Two atomic operations in a row are not atomic together.
  • Compare-and-set loops implement any single-variable update; use weak CAS inside loops in C++.
  • Several variables that must stay consistent need a lock, or one atomic reference to an immutable object.
  • C++ volatile is for memory-mapped hardware and signal handlers, not threads. For threads, use std::atomic.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Two threads each run count += 1 100,000 times on a counter declared volatile int (Java or C++). What is true?
Why. Volatile (in Java) makes each read and write visible but does not make the read-add-write sequence indivisible, so two threads can read the same value. In C++ volatile is not synchronization at all, so the unsynchronized accesses are a data race. It does compile in both: C++20 deprecates += on a volatile, but deprecated is not removed. Use incrementAndGet or fetch_add.
A shared counter is an AtomicInteger (Java) or std::atomic<int> (C++), and two threads each run a.set(a.get() + 1) (Java) or a.store(a.load() + 1) (C++) many times. What happens?
Why. Atomicity covers one operation at a time. Between the atomic read and the atomic write, another thread can do its own read, so one increment overwrites the other. There is no data race (all accesses are atomic), only a race condition. incrementAndGet() or fetch_add(1) is one operation.
A compare-and-set (compareAndSet or compare_exchange_weak) in an update loop returns false. What should the code do?
Why. A failed CAS means the value changed since you read it (or, for a weak CAS, that it failed spuriously), which is normal under contention. Recompute from the fresh value and retry. A plain write would throw away the other thread's update, and a sleep adds latency without guaranteeing anything.
Which of these are correct uses of a Java volatile field or a C++ atomic with plain loads and stores, with no lock? Select all that apply.Select all that apply
Why. Loads and stores are right when each write does not depend on the old value: a flag, or a reference to an object that never changes after publication. The counter and the lazy initialization are read-then-write sequences, so two threads can interleave inside them; they need an atomic read-modify-write, a CAS, or a lock.
A running maximum is updated with if (x > max.get()) max.set(x); where max is atomic. What can go wrong?
Why. It is a check-then-act on shared state. Thread A checks 50 > 40 and pauses; thread B stores 90; thread A stores 50, and 90 is lost. A compare-and-set loop (or accumulateAndGet(x, Math::max)) only stores if the value is still the one you compared against.
minLatency and maxLatency are two separate atomic variables, each updated correctly with CAS loops. A reporting thread computes maxLatency - minLatency. What can it see?
Why. Each atomic is consistent on its own, but the reader's two loads are separate, and updates can land between them. An invariant that spans two variables needs a lock, or one immutable pair published through a single atomic reference.
Java onlyA field is declared volatile int[] slots = new int[8];. One thread runs slots[3] = 7; and another thread later reads slots[3]. What does volatile guarantee here?
Why. volatile applies to the field, which holds a reference. slots[3] = 7 reads the volatile reference and then does a plain element write. For per-element volatile semantics use AtomicIntegerArray (or a VarHandle for arrays).
C++ onlyWhat is C++ volatile actually for?
Why. Volatile accesses must be performed as written, which is what device registers need. It gives no atomicity, no fences and no happens-before between threads, so a race on a volatile variable is still undefined behavior. Use std::atomic for threads.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "What exactly does volatile do in Java, what is the C++ equivalent, and what do they compile to? Does any of it matter on a single-core machine?" Answer as you would out loud.
Model answer

In Java, a volatile field gives three things. Visibility: a write happens-before every later read, so the compiler cannot keep the value in a register and readers always see the latest write. Ordering: writes before a volatile write cannot move after it, and reads after a volatile read cannot move before it, so a volatile flag can safely publish data written before it. And a single global order over all volatile accesses, which makes them behave like sequentially consistent atomics; it also makes volatile long and double reads and writes untorn. It does not make compound actions like count++ atomic.

The C++ equivalent is std::atomic with its default memory_order_seq_cst; C++ volatile is not equivalent at all, it only stops the compiler from removing or merging accesses, for hardware registers. On x86 a volatile or seq_cst load is an ordinary load, and the store is either an xchg or a store followed by a locked instruction that acts as a full fence, which waits for the store buffer to drain. On ARM they become load-acquire and store-release instructions, ldar and stlr. On a single core it still matters: the biggest effect is the compiler, which would otherwise hoist or reorder the accesses, and the compiler does not care how many cores there are. The hardware part, store buffers and fences, matters more on multiple cores, but you design against the language model either way.

Write code
Write a lock-free recordLatency(long ms) that keeps the maximum latency ever seen, and a reset() that returns the current maximum and sets it back to 0 in one step. Say why if (ms > max) max = ms is wrong.
Model answer

if (ms > max) max = ms is a check-then-act: between the comparison and the write, another thread can store a bigger value, which this thread then overwrites with a smaller one. With plain variables it is also a data race. The CAS loop only writes if the value is still the one it compared against; otherwise it re-reads and stops as soon as the stored maximum is already at least ms. reset must be one getAndSet or exchange: a separate read and write could lose a latency recorded in between.

Debug
This tracker keeps the smallest and largest latency, each in its own atomic, updated with correct CAS loops. A dashboard sometimes shows a negative range. Explain why and fix it so readers always see a consistent pair.
Model answer

Each atomic is consistent on its own, but the invariant "min and max describe the same set of samples" spans two variables, and width() reads them at different moments. At startup both hold sentinels: if the first sample has already reached max but not yet min, the reader computes something like 50 - Long.MAX_VALUE, a huge negative number (the other order overflows into a huge positive one). Later it can combine a min and a max that never described the same set of samples at any single moment. The fix is to make the pair one value: an immutable snapshot swapped with a single CAS, so a reader always sees a pair that existed at one moment.

In Java the record is immutable and the AtomicReference swap is always lock-free. In C++, std::atomic<Snapshot> works for any trivially copyable struct, but a 24 byte struct is usually not lock-free, so the library uses a hidden lock; that is still correct, and a plain std::mutex around two longs would be just as good and more obvious. What matters is that writers update, and readers read, the pair as one unit.

"How does incrementAndGet on an AtomicInteger, or fetch_add on a std::atomic<int>, actually work, down to the CPU? And what happens when 32 threads hit the same one?"
What a strong answer covers
  • It is one atomic read-modify-write: no other core can act between the read and the write
  • On x86 it is a single lock xadd: the core owns the cache line for the whole instruction, which also acts as a full fence
  • On ARM it is ldadd on ARMv8.1 and later, or a load-exclusive and store-exclusive retry loop on older cores
  • The general form is a compare-and-set loop: read, compute, swap only if unchanged, retry if another thread won
  • Under contention the cache line bounces between cores, so each increment costs a cross-core transfer, an order of magnitude or two slower
  • For a hot counter: LongAdder in Java, sharded or per thread counters in C++, summed on read
How a senior would say it
It is a single atomic read-modify-write, which means no other core can get between the read and the write. On x86 the JIT or the C++ compiler emits one instruction, lock xadd. The lock prefix makes the core hold the cache line exclusively for the whole instruction, and it also acts as a full fence, which is why it gives volatile or sequentially consistent ordering for free. On ARMv8.1 and later, including Apple's chips, it is one ldadd instruction; older ARM cores use a load-exclusive and store-exclusive pair in a retry loop. Conceptually all of these are a compare-and-set loop: read the value, compute the new one, swap only if nobody changed it, otherwise retry. That loop is also how updateAndGet handles any function. Under contention it gets expensive. With 32 threads on one counter, the cache line ping-pongs between cores, and each increment waits for a cross-core transfer, an order of magnitude or two slower than the uncontended few nanoseconds. It stays correct, but throughput collapses. So for a hot counter I would use LongAdder in Java, or sharded per thread counters in C++, and sum them on read.

"Here is a symptom: a C++ service hands work between threads with a volatile bool ready flag. The producer fills a buffer, then sets ready. It ran fine on x86 for years. On new ARM servers, consumers occasionally read garbage from the buffer. What is going on, and how do you fix it?"
What a strong answer covers
  • C++ volatile is not synchronization: no atomicity, no fences, no happens-before, so the program has a data race and undefined behavior
  • It only stops the compiler removing or merging the flag accesses; the plain buffer writes may still move past the flag store
  • x86 hid the bug: it keeps stores in order and loads in order, and Microsoft's compiler even gives volatile acquire and release meaning there by default
  • ARM reorders more: the flag can become visible before the buffer, or the consumer can read the buffer early
  • Fix: std::atomic<bool>, a release store after filling and an acquire load before reading (or the seq_cst default)
  • Confirm with ThreadSanitizer, which flags the old code even on x86
How a senior would say it
The flag was never correct; x86 was hiding the bug. In C++, volatile is not a threading tool. It stops the compiler from removing or merging accesses to the flag itself, but it emits no fences and creates no happens-before edge, so the program has a data race, which is undefined behavior. Worse, the buffer writes are ordinary writes, so even the compiler may move them after the flag store. On x86 it mostly worked because the hardware keeps stores in order and loads in order, and Microsoft's compiler even gives volatile acquire and release meaning on x86 by default. ARM has a weaker memory model. The flag can become visible to another core before the buffer writes, or the consumer can read the buffer before it reads the flag. That is the garbage. The fix is to make the flag a std::atomic<bool>, store it with release after filling the buffer, and load it with acquire before reading, or keep the default sequentially consistent ordering. The release and acquire pair is a happens-before edge, so the buffer is covered on every platform. I would also run the tests under ThreadSanitizer, which flags the old code even on x86.

Out loudabout 80 s
"A junior engineer asks you for a rule of thumb: when is a volatile field enough, when do you need an atomic, and when do you need a lock? What do you tell them?"
What a strong answer covers
  • Ask what the write depends on: if each write is independent of the old value (a flag, a latest reading, a reference to a new immutable object), volatile in Java or an atomic load and store in C++ is enough
  • If the new value depends on the old one (a counter, a running maximum), use one atomic read-modify-write or a compare-and-set loop
  • If the rule spans several variables (a min and a max that must agree), use a lock, or one atomic reference to an immutable object
  • Never volatile for count++: visibility is not atomicity; and in C++ never volatile for threads at all
  • A useful hybrid: volatile reads with writes inside a lock, for read-heavy state with compound updates
How a senior would say it
I would tell them to ask what the write depends on. If every write is independent of the current value, like a stop flag, the latest temperature reading, or a reference to a freshly built immutable config, a volatile field in Java is enough, and in C++ a std::atomic with plain loads and stores. If the new value depends on the old one, like a counter or a running maximum, visibility is not enough, because two threads can read the same value. Then they need one atomic read-modify-write, incrementAndGet or fetch_add, or a compare-and-set loop. And if the rule spans two or more variables, like a min and a max that must agree, no single atomic helps, because a reader can combine values from different moments. Then use a lock, or put the fields in one immutable object and swap it through an AtomicReference. One hybrid is worth knowing: volatile reads with writes inside a lock, for read-heavy state. And in C++ the answer is never volatile; that is for hardware registers.
