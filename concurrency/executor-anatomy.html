Inside an executor: the queue-before-max trap

The six choices in ThreadPoolExecutor, its submission order, and why queue capacity controls growth, overload and rejection.

Asked atLinkedInMicrosoftApple
Before this:Why thread pools exist

ThreadPoolExecutor has six configuration choices, and the most important fact about them surprises almost everyone: once the core size is reached, it tries the queue before adding an extra thread. Get that wrong and your "maximum 200 threads" pool can stay at 8 workers while thousands of tasks wait.

In plain words

A bank branch has 4 permanent tellers, a waiting area with 10 chairs, and a phone number for up to 6 temporary tellers. The manager's rule for each new customer is strict and always in this order: if a permanent desk is unstaffed, open it. Otherwise, if a chair is free, the customer sits and waits. Otherwise, if fewer than 6 temps are in, call one. Otherwise, turn the customer away.

Notice what that rule implies. Temps are called only when every chair is taken. If the waiting area had infinite chairs, the temps would never be called, however long the wait got. That is the queue-before-max trap, and it is exactly how Java's pool behaves.

Executor, ExecutorService and ThreadPoolExecutor

An executor separates submitting a task from deciding how it runs. In Java the idea is a family of interfaces:

  • Executor has one method, execute(Runnable). Callers hand over work; the implementation decides which thread runs it, and when.
  • ExecutorService adds a lifecycle (shutdown, shutdownNow, awaitTermination, and close since Java 19) and results: submit returns a Future, and invokeAll (wait for every task) and invokeAny (take the first success, cancel the rest) run batches; both are covered in Futures and promises.
  • ThreadPoolExecutor backs the fixed and cached pool factories; the single-thread factory wraps one. Other executors can use different scheduling policies.

C++20 has no standard thread pool. std::async does not expose worker or queue limits and is not a configurable pool. C++ teams use library pools or build their own; the same resource decisions apply, but queue-before-max is Java's policy, not a universal rule. If an interviewer requests core and maximum sizes, agree on the submission policy before implementing it.

The six knobs

KnobWhat it meansThe trap
corePoolSizeWorkers normally retained even when idle, created lazilyBelow core, a submission tries to start a worker even if others are idle
maximumPoolSizeCeiling on pool workersOrdinary submissions grow beyond core only when the queue refuses them; caller-run tasks are outside this limit
keepAliveTime and unitHow long an excess idle worker waits before it can retireCore workers do not time out unless allowCoreThreadTimeOut(true) is enabled
workQueueWhere tasks wait between arrival and executionThe critical choice: unbounded, bounded, or no room at all
threadFactoryCreates the worker threadsThe default names them pool-3-thread-7, which tells you nothing in a thread dump
handlerWhat happens at saturation or after shutdownThe default throws RejectedExecutionException; it does not wait for queue space

Constructor bounds are 0 <= corePoolSize <= maximumPoolSize, a strictly positive maximum, and nonnegative keepalive; queue, factory and handler must be non-null. A bounded queue requires positive capacity. Invalid numeric bounds throw IllegalArgumentException.

The submission rule

For a running pool with successful thread creation and no concurrent reconfiguration, ThreadPoolExecutor applies this order. Count all workers, including idle ones, not just active tasks:

  1. Fewer than core threads? Start a new thread with this task as its first task. This happens even if some existing workers are idle.
  2. Otherwise, can the queue take it? Try nonblocking offer, not put. After enqueueing, recheck shutdown and whether any workers remain; a zero-worker pool attempts to start a worker to drain the queue.
  3. Otherwise (the queue is full), fewer than max threads? Start an extra thread with this task.
  4. Otherwise: reject. The rejection policy decides what that means.

Here is a burst of 7 tasks against core 2 and max 4, first with a queue of 2, then with an unbounded queue. Java holds tasks at a latch until every submission is recorded, so the result does not depend on a sleep duration. The C++ program is a single-threaded policy model for this burst, not a concurrent executor; lifecycle checks, synchronization and worker failure handling belong in the real pool.

With a positive core size and an effectively unbounded queue, ordinary load does not trigger growth beyond core: raising max does not fix the backlog. A default LinkedBlockingQueue actually has capacity Integer.MAX_VALUE; memory exhaustion is likely long before that limit. Shutdown can still reject work, and worker creation can fail.

An extra worker receives the newest task directly: task 5 can start while tasks 3 and 4 remain queued. A FIFO queue therefore does not promise FIFO task starts or completions across the whole executor.

The factory methods and their hidden queues

Executors makes pools in one line, and each one hides a decision you might not agree with:

Factory methodWhat it buildsThe hidden risk
newFixedThreadPool(n)core = max = n, unbounded LinkedBlockingQueueNo practical overload rejection before latency or memory becomes a problem
newSingleThreadExecutor()one thread, unbounded LinkedBlockingQueueThe same, with one thread
newCachedThreadPool()core 0, max Integer.MAX_VALUE, SynchronousQueue, 60 s keepaliveNo useful safety cap on threads: a slow dependency can exhaust OS resources
newScheduledThreadPool(n)n core threads, unbounded delay queueThe maximum has no effect; the queue is unbounded
newWorkStealingPool()a ForkJoinPool, target parallelism = available processorsUnmanaged blocking I/O can starve workers; compensation is not guaranteed
newVirtualThreadPerTaskExecutor() (Java 21)a new virtual thread per task, no bounded executor work queueNo admission limit; scheduler queues and downstream limits still exist

Choose factories when their policies fit; construct ThreadPoolExecutor directly when you need explicit bounds. A SynchronousQueue stores no tasks: an offer needs a waiting receiver. Otherwise the executor tries to create a worker up to max, then rejects. This means "handoff or grow or reject", not a guarantee of immediate CPU time.

Name your threads

The first time you read a thread dump of a stuck service, pool-7-thread-3 tells you nothing and payments-db-3 tells you where to look. A thread factory is where you set the name, whether threads are daemons, and an uncaught exception handler.

Idle threads: keepalive, prestarting and core timeouts

Excess idle workers can retire after keepAliveTime, shrinking the pool after a burst. Core workers do not time out by default; allowCoreThreadTimeOut(true) lets an idle pool shrink to zero and requires a strictly positive keepalive. Core workers are created lazily; prestartAllCoreThreads() requests them up front, avoiding thread creation on the first requests, though it does not warm application code.

Those knobs also give you the most useful configuration trick in this lesson. If you want a pool that grows threads first and queues only when it cannot grow, set core equal to max, turn on core timeouts, and bound the queue: new ThreadPoolExecutor(64, 64, 30, SECONDS, new ArrayBlockingQueue<>(500)) plus allowCoreThreadTimeOut(true). Below 64 threads, step 1 creates a thread for every task; idle threads still retire after 30 seconds.

Java

Hooks: beforeExecute, afterExecute, terminated

ThreadPoolExecutor calls beforeExecute(thread, task) and afterExecute(task, throwable) around worker-run tasks, and terminated() when termination completes. Caller-run tasks bypass these hooks. Keep hooks from throwing: a failing beforeExecute prevents the task and its afterExecute hook from running. With submit, the task exception is stored in its Future, so the throwable argument is normally null; inspect the future to observe failure.

C++

Hooks in your own pool

In a hand-built pool the worker loop is the hook: time tasks and clear task-specific thread-local state there. Catch task exceptions before they escape the thread entry point and invoke std::terminate; deliver failures through futures or another explicit error channel.

Shutdown, rejection and publication

shutdown() rejects new work and lets accepted work finish; it returns without waiting. shutdownNow() interrupts workers and returns queued tasks that never started, but cannot force a task to stop and does not automatically cancel their futures. Use awaitTermination(timeout, unit) to wait with a deadline. Java 21's close() waits for termination; interruption triggers an attempt to stop work and restores the caller's interrupt flag before returning. Never wait for your own executor to terminate from one of its tasks.

AbortPolicy reports rejection. CallerRunsPolicy executes on the submitter unless the executor is shut down, when it discards; it can stall an event loop or run a task while the submitter holds locks. DiscardPolicy drops work; DiscardOldestPolicy drops the queue head and retries when running. Silent drops can leave submitted futures incomplete. Choose deliberately, as rejection and pool failures explains.

Submission also publishes data: actions before Java executor submission happen-before task actions, which happen-before retrieval through Future.get(). This does not protect later mutations of shared inputs. A C++ pool must establish its own ordering, usually by locking the queue during enqueue and dequeue; result delivery through a future supplies the completion edge. Capture lifetimes must still outlive the task.

Worked example: "we set max to 200, why do we only ever see 8 threads?"

A service builds its pool as new ThreadPoolExecutor(8, 200, 60, SECONDS, new LinkedBlockingQueue<>()). Under a downstream slowdown, latency climbs to 30 seconds, CPU sits at 10 percent, and the thread dump shows exactly 8 workers.

Diagnosis. The queue accepts the backlog, so growth toward 200 is never triggered. In a stable system, average queue length divided by throughput gives average queue waiting time. During this growing overload, Little's law is not a stationary latency prediction; queue age and backlog growth are the useful incident signals.

Fix, option 1: bound the queue, for example new ArrayBlockingQueue<>(100). With all existing workers occupied, 100 tasks queue before the next submission triggers growth toward 200. When both bounds are full, reject. Queued tasks can still wait while newer tasks start on extra workers.

Fix, option 2: if you really want up to 200 threads before queueing, make core 200, call allowCoreThreadTimeOut(true), and still bound the queue. Either way, decide what rejection should mean for the callers. And ask whether 200 concurrent calls are what the slow downstream can take; often the right answer is fewer threads and a fast rejection.

Common mistakes

  • Setting a maximum with an unbounded queue and expecting ordinary overload to grow the pool beyond core. The queue keeps accepting instead.
  • Using newFixedThreadPool on a request path. Its unbounded queue converts overload into latency and memory growth instead of a clear error.
  • Using newCachedThreadPool in front of anything that can slow down. No thread cap means one thread per stuck task, until the process cannot create more.
  • Expecting an idle core thread to be reused before a new one is created. Below core, every submission creates a thread.
  • Core 0 with an unbounded queue. A sequential burst normally starts one worker to drain it, not max workers. Concurrent submissions racing at zero workers can start more than one, so do not use this as a single-thread guarantee.
  • Default thread names. pool-3-thread-7 in a dump at 3 a.m. Name every pool's threads after the work they do.

In the interview

The direct form is "explain the parameters of ThreadPoolExecutor" or "what happens when a task is submitted?" Research reports include executor APIs in Apple's Java loops, implementing a ThreadPoolExecutor variant at LinkedIn, and explaining and implementing one at Microsoft. For a C++ design, first state the policy your pool will implement. Recite the four steps, then volunteer the trap.

For a running pool, submission first tries to create a worker below core. After core it offers to the queue, then tries to grow up to max if the queue refuses, and otherwise rejects. So a queue that keeps accepting work prevents ordinary overload from growing the pool beyond core. Raising max alone does not fix that backlog. I choose explicit worker and queue bounds, readable names and a rejection policy, and check the shutdown rules separately.

Follow ups to expect: "How would you make it add threads before queueing?" (core equal to max, positive keepalive, core timeouts), "Does a SynchronousQueue guarantee immediate execution?" (no, it avoids stored waiting tasks), and "What happens if shutdown races with submission?" (the state is rechecked; a queued task is rejected only if it can be removed).

Under the hood

In OpenJDK 21, ctl is an AtomicInteger packing lifecycle state and worker count. Each worker also has a non-reentrant lock held while executing, letting shutdown() interrupt idle workers without interrupting active tasks. These are implementation details, not the ExecutorService contract.

getTask() uses workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS) for timed waits and take() otherwise. After a timeout it rechecks state and worker counts before retiring. If a task passed directly to execute throws an unchecked exception, the worker exits and replacement is attempted when the lifecycle permits it; submit normally captures failure in the future instead.

Key takeaways

  • The submission rule: below core, a new thread; else the queue; else an extra thread up to max; else reject.
  • With a positive core size and an accepting unbounded queue, ordinary overload adds waiting tasks rather than workers beyond core.
  • The Executors factories hide unbounded queues (fixed, single, scheduled) or unbounded threads (cached); construct pools explicitly on request paths.
  • For "threads first, then queue", use core equal to max with core timeouts and a bounded queue.
  • Name your threads, choose your rejection policy, and know that C++ has no standard pool: these knobs are what you implement.

Quick check

Answer each question, then read why. Your score is saved for your module test.

In the Java burst example, tasks stay at the latch until all submissions are recorded. With core 2, max 4, queue capacity 2 and successful worker creation, what counts are printed after submission 6, and what does execute do for task 7?
Why. Tasks 1 and 2 create core workers, 3 and 4 fill the queue, and 5 and 6 create extra workers. No task can finish before the latch opens. Task 7 finds both limits reached, so AbortPolicy throws. The queue cannot hold four tasks, max is a real worker bound, and execute uses offer, not a blocking put.
A fresh running pool has core 8, max 200 and an unbounded LinkedBlockingQueue. One caller submits 1,000 tasks before any finish. Assuming successful thread creation and unchanged settings, how many pool workers exist?
Why. Once 8 core threads exist, every further task is accepted by the unbounded queue, and extra threads are created only when the queue refuses a task, which never happens. The maximum of 200 is dead configuration.
A running pool has core size 4 and 2 idle workers. With successful thread creation and no concurrent lifecycle change, what happens when a new task is submitted?
Why. Below core, step 1 always creates a new thread, even when existing workers are idle. Core threads are created lazily, one per submission, until the core size is reached; prestartAllCoreThreads() creates them up front instead.
A service uses Executors.newCachedThreadPool() for blocking payment calls. Latency jumps from 50 ms to 10 s while 300 requests a second keep arriving. Before OS resource limits are reached, what grows?
Why. The SynchronousQueue stores no backlog. If a waiting worker cannot take a task, the pool tries to create one, so it heads toward thousands of workers. Sustaining 300 calls a second at 10 s per call would occupy about 3,000 workers. Idle reuse cannot cover busy calls, and the configured maximum is not a practical safety limit; resource exhaustion may arrive first.
With a positive keepalive and successful worker creation, you want growth up to 64 workers before queueing, at most 500 queued tasks, and shrinkage when idle. Which configuration does that?
Why. Core 64 creates workers before queueing, the queue bounds waiting at 500, and core timeouts permit idle retirement. Core 8 with a bounded queue queues before growing beyond 8. With an unbounded queue, neither core 8 nor core 0 implements growth to 64 before queueing.
Java onlynew ThreadPoolExecutor(0, 10, 60, TimeUnit.SECONDS, new LinkedBlockingQueue<>()) receives 100 one-second tasks from one caller, with submissions completed before any task finishes. No workers fail and creation succeeds. How many workers handle this burst?
Why. The first submission queues, notices zero workers and starts one. Each later submission sees that worker, so the queue continues to grow without starting another. Max 10 is not a target, and the zero-worker check prevents stranding. This sequential burst takes roughly 100 seconds; concurrent submitters racing at zero workers are a different case.
C++ onlyWhich of these is a thread pool provided by the C++20 standard library?
Why. C++20 provides none of these as a pool. std::async does not offer worker-count or queue-capacity controls, hardware_concurrency() returns a concurrency hint, and std::jthread owns a single joining thread. A library or application supplies the pool.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
A teammate set maximumPoolSize to 200 but monitoring shows the pool never goes above 8 threads, while latency climbs under load. Explain what is happening and what you would change.
Model answer

My first hypothesis is an unbounded queue, or a bounded queue that has not filled. I would inspect the actual queue capacity, backlog and age, core setting, lifecycle and worker-creation failures. ThreadPoolExecutor ordinarily grows beyond core only when offer fails. Raising max alone will not drain a queue that keeps accepting work. Average queue length divided by throughput estimates average queue wait only in steady state, not total request latency during growing overload.

If eight workers is the right resource budget, bound the queue and reject excess work. If the downstream and CPU budget support more workers, increase core or use a smaller bounded queue to trigger growth earlier. Core equal to max with a positive keepalive and core timeouts gives growth before queueing while allowing idle retirement. I would choose the actual limit from measurements rather than assume 200 is safe.

Pseudo code
Write, as pseudocode, the decision a ThreadPoolExecutor makes for each submitted task, including what it does if the pool is shut down and the special case when the pool has no threads after queuing.
Model answer
  1. If the pool is shut down: reject.
  2. If worker count < core: attempt to add a worker with this task, rechecking lifecycle and count atomically. Return on success; otherwise reread state and continue.
  3. If still running and queue offer succeeds: reread state. If no longer running and removing this task succeeds, reject it. Otherwise, if the reread count was zero, attempt to add a worker with no first task to drain the queue. Return.
  4. Otherwise attempt to add a worker with this task using max as the count bound, again checking lifecycle. If this fails, invoke the rejection handler.

The shutdown recheck rejects only if removal succeeds: a worker may already have taken the task, so unconditional rejection would incorrectly report work that can run. Direct handoff to a newly added worker also lets a newer task overtake older queued work. These are separate checked transitions, not one atomic operation covering the entire method. This pseudocode omits argument validation and resource exceptions; a factory returning null can also leave queued work without workers.

Design
You are configuring the pool for a request handler: normally 16 threads, up to 64 under a burst, at most 200 requests waiting, reject beyond that, readable thread names. Write the configuration and then say when the extra threads actually appear. Is that what you want?
Model answer

Configuration: new ThreadPoolExecutor(16, 64, 30, TimeUnit.SECONDS, new ArrayBlockingQueue<>(200), Thread.ofPlatform().name("api-", 0).factory(), new ThreadPoolExecutor.AbortPolicy()). In a hand-built C++ pool, the same six values go into its config and the submit rule.

With all tasks held busy, tasks 1 to 16 create workers, the next 200 queue, and task 217 starts worker 17 immediately. There is no mandatory 0.6 s pause before growth. That number is a rough backlog-drain estimate: 200 / (16 / 0.050) = 0.625 s if only 16 workers kept draining 50 ms tasks. Growth changes the drain rate and lets new tasks overtake queued ones. If latency matters, test a smaller queue or core 64 with positive keepalive and core timeouts, but only if CPU and downstream budgets allow it.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Walk me through what happens when I submit work to a pool with core 2, maximum 4 and a queue of 2. Can later work overtake earlier work?"
What a strong answer covers
  • Count all workers, including idle workers; below core a submission tries to add a worker
  • After core, offer to the queue before growing toward max
  • For held tasks, submissions 1 and 2 create workers, 3 and 4 queue, 5 and 6 create workers
  • Submission 7 invokes rejection; the default throws rather than waits
  • New workers receive their triggering task directly, so queued FIFO is not global FIFO
How a senior would say it
Yes, later work can overtake earlier work, because a new worker receives the task that caused its creation. Assume the pool is running, worker creation succeeds, and none of these tasks finishes during the burst. The first two submissions each create a core worker. The next two go into the queue. The fifth submission finds the queue full and creates a third worker, and the sixth creates a fourth. The seventh finds both limits reached, so the default policy throws a rejection exception. It does not wait for a queue slot. Tasks five and six can therefore start while three and four are still queued. FIFO describes removal from that queue, not the order of all task starts or completions. One subtlety is that core counts workers, including idle ones. Below core, a submission still tries to create a worker even if another worker is idle. I would document this policy explicitly in a C++ pool, because C++20 does not provide a standard executor with these rules.

Likely follow up: What changes if I replace the queue with a SynchronousQueue?

Out loudabout 90 s
"Our maximum is 200, but only eight workers exist and latency keeps rising. What do you check, and how do you fix it?"
What a strong answer covers
  • Inspect queue type and capacity, core size, queue age and worker-creation failures
  • Explain queue-before-max: an accepting queue prevents ordinary growth beyond core
  • Choose worker limits from CPU and dependency capacity rather than the configured maximum
  • Bound waiting and choose explicit rejection; core equal to max plus positive keepalive and core timeouts grows before queueing
  • Validate admitted throughput, queue age, tail latency and rejection during bursts and slowdowns
How a senior would say it
My first suspicion is a queue that keeps accepting work, so the maximum never comes into play. I would check the actual queue type and capacity, core size, queue age, and whether worker creation is failing. Java normally offers to the queue after reaching core and only grows beyond core when that offer fails. An effectively unbounded queue can therefore leave eight workers serving a growing backlog. I would then establish the CPU budget and the concurrency the dependency can tolerate. If eight workers is right, I would bound waiting and reject overload. If more workers are safe, I could increase core or reduce queue capacity to trigger growth earlier. Setting core equal to max, with a positive keepalive and core timeouts, gives growth before queueing and retirement when idle. Raising max alone does not help. Queue capacity also needs a latency and memory budget: accepting work that cannot finish before its deadline wastes resources. I would choose a rejection policy explicitly and make rejection visible to callers and monitoring. Finally, I would test bursts and dependency slowdowns, measuring admitted throughput, queue age, tail latency and rejection together. More workers are successful only if useful completions improve within the resource budget.

Likely follow up: If shutdown happens immediately after a task is enqueued, when may the executor reject that task?
