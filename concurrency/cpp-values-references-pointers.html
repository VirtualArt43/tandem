Values, references and pointers

Value semantics, references, pointers, const references and nullptr, and how aliasing turns an ordinary variable into shared state.

Asked atMicrosoft
Before this:How C++ becomes a running program

A data race needs two threads reaching one object. In C++ that only happens through a name that refers to somebody else's object: a global, a reference, a pointer, a captured this. Learn to see those names and you can point at every piece of shared state in a code sample within seconds.

In plain words

Think of an important document. A value is a photocopy: scribble on yours and nobody else's copy changes. A reference is a nickname for the original: whatever you do through the nickname happens to the original. A pointer is a slip of paper with the original's shelf number on it: you can rub it out and write a different shelf, leave it blank, or keep it after the document was shredded, in which case it points at whatever sits on that shelf now.

Two people can work on photocopies all day without ever talking. The moment two people hold nicknames or slips for the same original, and at least one of them writes on it, they have to coordinate. That is all shared state is.

Why this matters for concurrency

  • C++ copies by default. std::vector<int> b = a; copies every element, while Java's List<Integer> b = a; copies a reference to one shared list. In C++, sharing is something you write on purpose: &, *, std::ref, [&], a shared pointer.
  • std::thread stores its arguments by value, copying lvalues and moving eligible rvalues. std::ref(x) explicitly shares x; copied pointers, views and reference captures can also share underlying state.
  • const T& does not protect you from other threads. It only stops you from writing through that name; another thread can still change the object under you.
  • A getter that returns a reference or pointer to data guarded by a mutex leaks the data out of the lock. It is one of the most common findings in concurrent code review.
  • Microsoft has grilled a candidate on pointers alongside synchronization and semaphores (a 2022 report). Expect the basics to be checked quickly and precisely.

Values: every variable is its own object

A non-reference variable of object type T is its own object. Copying an integer, a string or a vector of integers gives an independent value. This is value semantics.

For a class, the copy constructor determines what copying means; default memberwise copying still shares anything reached through pointer or reference members. A copied view or shared pointer also aliases its original data, so a separate object does not always mean independent underlying state.

The price of independence is the copy itself. Copying a vector of a million int values copies about 4 MB when int is four bytes. That is why large objects are passed by reference, or moved, which is the subject of copy, move and move-only types.

References: a second name for an existing object

A reference is an alias. Once bound, everything you do to the reference happens to the object it names.

Three rules: a reference must be bound when it is created, it can never be rebound to another object, and in a valid program it is never null. A const T& can also bind to a temporary, and when a local const T& binds directly to one, the temporary lives as long as the reference: const std::string& s = make_name(); is fine. That extension does not pass through a function that returns a reference, which is a lifetime trap you will meet in the next lesson.

Pointers: an address you can change

A pointer holds the address of an object, or the special value nullptr, which means "no object".

Use nullptr, never NULL or 0. nullptr has its own type, std::nullptr_t, which converts to any pointer type but not to an integer, so with overloads f(int) and f(int*), f(nullptr) calls the pointer version. NULL is implementation defined: with clang f(NULL) is an ambiguous call that does not compile, and where NULL is plain 0 it silently calls f(int).

In modern C++ a raw pointer means "I can see this object", not "I own it". Ownership is expressed with smart pointers, covered in unique_ptr, shared_ptr and weak_ptr.

The standard excludes it from the different-element concurrency guarantee, so such writes can race. Use std::vector<char> or std::vector<std::uint8_t> for per-thread flags.

std::thread copies its arguments

std::thread t(f, x) does not hand x to the new thread. In the calling thread, before the constructor returns, it creates decayed argument objects in storage managed by the thread machinery, copying lvalues and moving eligible rvalues. The new thread invokes the stored callable with those stored arguments.

This decay copy keeps an ordinary integer argument independent, but copying an alias still shares its target: pointers, views and captured references are examples. Two consequences surprise people.

  • If f takes int&, then std::thread t(f, x) does not compile, because the stored copy is passed as a temporary, which cannot bind to int&. The error is long and points deep inside the thread header. Write std::thread t(f, std::ref(x)), and accept that you now own the lifetime and synchronization question.
  • If f takes const int&, it compiles, but the reference names the thread's private copy, not x. Changes to x after the thread starts are not seen, and nothing is shared.

It prints "no" and then "yes". std::ref and std::cref wrap the reference in a small copyable object, std::reference_wrapper, which is what the thread stores. You will use the same idea, written as a lambda capture, in passing data in and getting results out.

Common mistakes

  • "It takes a const reference, so it is thread-safe." const restricts this name, not the object. If another thread writes the object, a const reader still races with it.
  • Returning a reference, pointer or iterator to guarded data. The access happens after the lock is gone. Return a copy or answer the question inside the lock.
  • Passing std::ref to a local and then detaching the thread, or returning. The thread holds a reference to a dead object. Join first, or give the thread its own copy.
  • Believing std::thread t(f, x) shares x because f takes const int&. It binds to the thread's copy.
  • Keeping a pointer to a std::vector element across push_back. Growth reallocates and the pointer dangles; with another thread pushing, it can happen at any moment. See containers and iterator invalidation.
  • Using NULL. It is an integer in disguise. Write nullptr.

In the interview

Pointers and references come up as a warm-up in C++ screens ("difference between a pointer and a reference?"), and then inside concurrency questions: "is passing a const reference to the worker safe?", "why does this std::thread line not compile?", "which variables in this snippet are shared?". Debugging rounds in particular reward the alias hunt from the worked example: name the shared state first, then fix it.

A reference is another name for an existing object: bound at creation, never rebound, never null. A pointer holds an address: it can be null, it can be repointed, and it can outlive its object, which is how pointers dangle. For threads they are the same thing: aliases. Once two threads reach one object through them and one of them writes, I need a lock or an atomic.
std::thread copies its arguments on purpose. If I want the thread to share my variable I write std::ref, and that is my cue to check two things: the variable outlives the thread, and every access is synchronized.

Follow ups: "What does std::ref return?" (a std::reference_wrapper, a copyable object holding a pointer); "How would you return a result from the thread instead?" (a promise and future, or write into a slot the caller reads after join); "Why is returning const std::vector& from a locked getter wrong?" (the lock covers the return, not the reading); "Two threads each write a different element of one vector with no lock: race?" (no for std::vector<int>, because each element is its own memory location; different elements of std::vector<bool> can race because they can share packed storage).

Senior depth

C++20 std::atomic_ref lets you perform atomic operations on an ordinary object through a reference, for data that is plain in a single-threaded phase and shared in a later one. The rule is strict: while any std::atomic_ref to an object exists, every access to that object must go through an atomic_ref. The underlying type must be trivially copyable, the object must meet required_alignment, and it must outlive every referring wrapper.

Aliasing limits the optimizer. Because two pointers of the same type may point at one object, the compiler must reload values after writes through other pointers. That single-thread aliasing assumption is exactly what it does not make about other threads, which is why a race on a plain variable lets it keep stale copies in registers.

References are usually implemented as pointers. A reference member commonly occupies pointer-sized storage, although the language does not require that representation. It causes defaulted copy and move assignment operators to be deleted; a class can still define its own assignment policy. If you need a rebindable reference that can live in a container or be copied into a thread, that is std::reference_wrapper.

Key takeaways

  • Owning value types such as strings and vectors of integers copy independently; copied pointers, views and shared owners can still alias.
  • References and pointers are aliases. Globals, statics, references, pointers, reference captures and this are the only ways two threads reach one object.
  • std::thread stores arguments by value. Reference wrappers, pointers and captured aliases all require lifetime and synchronization checks.
  • const T& limits your access, not anyone else's: it is not a thread safety guarantee.
  • Never let a reference, pointer or iterator to guarded data escape the lock. Return copies or answer inside the lock.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "Pointer versus reference: what is the difference, and what does each mean for thread safety?" Answer as you would out loud.
Model answer

A reference is an alias for an existing object. It has to be bound when it is created, it can never be rebound, and in a valid program it is never null, so it is the natural choice for "this function works on the caller's object". A pointer holds an address: it can be null, it can be repointed, and it can do arithmetic over arrays, so it fits "maybe an object" or "an object I may switch". Both can dangle if the object dies first. In modern code neither one owns anything; ownership belongs to smart pointers.

For thread safety they are the same thing: aliases. A data race needs two threads reaching one object, and in C++ that only happens through globals and statics, references, pointers, reference captures and this. Const on a reference or pointer limits my writes, not anyone else's, so it is not a guarantee. When I see a reference or pointer cross a thread boundary I check two things: the object outlives every thread that can reach it, and every access, reads included, takes the same lock or uses atomics. std::thread stores argument objects by value, but reference wrappers are not the only source of sharing: copied pointers, views and captured aliases can still lead to the original data.

Debug
A Registry class returns const std::map<std::string, int>& from a getter that takes a std::lock_guard. Other threads insert into the map under the same mutex. Describe an interleaving that breaks, then give two fixes.
Model answer

Thread R calls the getter: it locks, binds the return value to the map, and unlocks as the function returns. R then calls find on the map through the reference, with no lock. Meanwhile thread W locks and inserts a key, which rebalances the tree and rewires node pointers. R's find is walking those pointers at the same time: a data race, which is undefined behavior and in practice can follow a half-updated pointer and crash or return garbage. The mutex was held around the return, not around the use.

Fix 1: return a copy, std::map<std::string, int> snapshot() const, made while the lock is held. Simple and correct, at the cost of a copy. Fix 2: do not hand out the data; answer the question inside the lock, for example std::optional<int> lookup(const std::string& key) const that locks, finds and returns a copy of the value.

For read-mostly data with large maps, a third option is publishing immutable snapshots through a std::shared_ptr<const std::map<...>>, with synchronized publication of the snapshot handle. Readers retain their own owning handle while accessing immutable data; copying a shared pointer alone does not synchronize a concurrent replacement of the same handle.

Write code
Write long count_even(const std::vector<int>& v) that uses two threads, each counting even numbers in one half of the vector, with no locks and no atomics. Explain why it is race free.
Model answer

Why it is race free: the vector is shared but only read, and concurrent reads through const access are fine as long as nobody writes it during the call. Each count is a local variable on its own thread's stack. The one shared write, left, is written by one thread and read by the caller only after join, and join makes everything the thread did visible. No lock is needed because no two threads ever write, or read and write, the same object at the same time.

Out loudabout 75 s
"How would you explain values, references and pointers to a junior who is passing data to a worker thread? Does const make the sharing safe?"
What a strong answer covers
  • A value parameter is a separate object, but copied pointers, views and shared owners can still alias underlying data
  • A reference is bound to one object and cannot be reseated; a pointer can be null or reseated
  • Both references and pointers can dangle and do not by themselves establish ownership
  • Const restricts writes through that access path, not writes through other aliases
  • Check lifetime and ordering of conflicting accesses; prefer independent values or read-only sharing when appropriate
How a senior would say it
I would separate three questions: what object the worker reaches, who keeps it alive, and how concurrent accesses are coordinated. A value parameter is a separate object. Copying a vector of integers gives independent elements, but copying a pointer or a shared owner still leads to the same underlying data. A reference is another name for one object: it is bound when initialized and cannot be reseated. A pointer holds an address and can be null or changed to point elsewhere. Both references and pointers can dangle if the object dies, and neither a raw pointer nor a reference establishes ownership by itself. Const does not solve the threading problem. A const reference prevents writes through that name, while another alias can still modify the object. If those ordinary reads and writes are unordered across threads, they race. I would prefer an independent value when copying is reasonable, or read-only sharing when the object's lifetime is guaranteed. If mutation must be shared, I need a synchronization policy covering every conflicting access. Lifetime safety and data-race freedom are separate obligations.

Likely follow up: If two workers each hold a copy of the same shared pointer, which of those obligations does it help with?

Out loudabout 75 s
"A worker takes const int&. I launch it with x equal to 7, then set x to 9. What does it see, and what changes if I pass std::cref(x)?"
What a strong answer covers
  • With an ordinary x argument, std::thread stores a copy made during construction before the caller's later assignment
  • The const reference parameter binds to that stored copy, so the worker reads 7
  • std::cref stores a reference wrapper, so the worker instead reads the original object
  • An unordered assignment to the original then races with the worker read; const and a later join do not repair that race
  • Sharing requires the original to outlive access and conflicting accesses to be synchronized, or mutation delayed until after join
How a senior would say it
With the ordinary argument, the worker reads seven. The thread constructor stores a copy of the integer in the launching thread before the later assignment to nine. The worker's const reference binds to that stored copy, not to the caller's original integer. With std::cref(x), the stored object is instead a reference wrapper, and the worker reaches the original integer. Now the assignment to nine conflicts with the worker's read. Unless something orders those accesses, that is a data race and undefined behavior; I cannot answer that it simply prints seven or nine. Const only prevents mutation through the worker's reference. Joining afterward waits for completion, but it does not order the earlier assignment against a read that happened inside the worker. I would either retain the independent copy, delay changing the original until after joining, or synchronize the read and write using an appropriate shared protocol. I would also ensure the original remains alive until the worker finishes using it. Choosing a wrapper is therefore a sharing decision with both lifetime and synchronization consequences, not just a way to avoid a copy.

Likely follow up: What happens if the worker takes int& and you pass x without a reference wrapper?

Out loudabout 75 s
"This getter locks a mutex and returns a const reference to its vector. Writers use the same mutex. Why can the caller still crash, and what would you return instead?"
What a strong answer covers
  • The guard releases the mutex when the getter returns, before the caller uses the reference
  • A writer can modify or reallocate vector storage while the caller iterates, creating a race and potentially dangling element references
  • Const restricts the caller's writes but does not prevent the writer from changing the vector
  • Return a copy made while locked, or perform a narrow lookup under the lock and return its result by value
  • Large read-mostly data can use immutable snapshots with synchronized publication and retained ownership
How a senior would say it
The lock protects obtaining the reference, not using it afterward. As soon as the getter returns, its guard releases the mutex. The caller may then begin iterating while a writer acquires the mutex and pushes another element. If the vector reallocates, the reader's element references and iterators can point into freed storage. Even without reallocation, unsynchronized access to changing vector state can race. Returning a const reference only prevents the caller from modifying through that reference; it does not prevent the writer from changing the vector. My simplest fix is to return a vector copy constructed while the mutex is held. The caller owns that snapshot and can iterate independently. If it only needs one answer, I would instead perform the lookup under the lock and return a copied result. Both approaches keep the actual shared-data access inside the protected interval. For a very large, mostly read collection, immutable snapshots can reduce copying, but publication must be synchronized and each reader must retain ownership for its whole use. That adds complexity, so I would justify it with the workload.

Likely follow up: If the vector contains shared pointers to mutable objects, does copying the vector also make the pointed-to objects safe to read?
