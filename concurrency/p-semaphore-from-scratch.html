Semaphore from scratch

Build a primitivewarm-up20 minDijkstra's counting semaphore, built as a monitorRubrik

Twenty lines that show whether you really understand a condition variable: a count, a wait, a wake and a timeout. Microsoft interviewers have asked for exactly this (reports from 2019 and 2022), and it is the first brick of every "only N at once" limiter you will build.

The task

Build a counting semaphore: a pool of permits. A thread takes a permit before it uses a limited resource and gives it back afterwards, so at most N threads use the resource at once.

  • acquire() takes one permit. If there are none, the calling thread blocks until a permit is released.
  • tryAcquire(timeout) does the same but waits at most timeout. It returns true if it got a permit and false if the time ran out. A timeout of 0 means "try once, do not wait".
  • release() gives one permit back and wakes a waiting thread, if there is one.
  • availablePermits() returns the number of free permits right now.

Rules.

  • Build it from one lock and one condition variable: ReentrantLock with a Condition, or synchronized with wait and notifyAll, in Java; std::mutex with std::condition_variable in C++.
  • No library semaphores and nothing that hides one: not java.util.concurrent.Semaphore, not AbstractQueuedSynchronizer, not a blocking queue full of tokens, not std::counting_semaphore, std::binary_semaphore or POSIX sem_wait. The runner rejects code that names them, even in a comment, so keep those words out of your file.
  • release() has no upper limit: releasing without a matching acquire adds a permit. Java's library semaphore behaves the same way; std::counting_semaphore instead has a maximum and makes going past it undefined.
  • Java only: acquire and tryAcquire are interruptible. If the thread is interrupted while it waits, throw InterruptedException and take no permit.

What the tests check

  • Counting from one thread: two acquires use up two permits, tryAcquire(0) at zero returns false at once, a release beyond the starting count adds a permit.
  • acquire really blocks at zero permits, and one release wakes it.
  • Five threads block on an empty semaphore; three releases let exactly three of them through, not all five.
  • Three permits let three holders in at the same time, and a fourth thread waits until one of them leaves.
  • tryAcquire(200 ms) at zero returns false after about 200 ms: not early, and not much later. tryAcquire(5 s) returns true soon after a release, without sleeping out its full timeout.
  • Java: an interrupted acquire throws InterruptedException promptly and takes no permit.
  • A stress run: 8 threads in random start order mix acquire and short tryAcquire calls on 3 permits; the number of holders never exceeds 3, nothing deadlocks, and all 3 permits are back at the end. In C++, ThreadSanitizer must stay quiet.

Taught in: Build it yourself: semaphore and latch

Open them one at a time. Each one gives away a little more.

The whole state is one integer: the number of free permits. One lock guards it. What is the one condition a thread waits for?
acquire: take the lock, wait in a loop while the count is 0, then subtract one. release: take the lock, add one, signal one waiter. Ask yourself why one signal (not a broadcast) is enough here.
For tryAcquire, turn the timeout into a deadline once, then loop: while there is no permit, give up if no time is left, otherwise wait for the time that is left. Java's awaitNanos returns the time left; C++ wait_for with a predicate does the whole loop for you. Check for a permit before you check the clock, so a permit that arrives at the last moment is not thrown away.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why is signal (notify_one) enough in release, when the bounded queue's single condition needed a broadcast?
Every waiter here waits for the same thing, "a permit exists", and any one of them can use it. One permit can satisfy exactly one waiter, so waking one is right. The bounded queue with one condition mixes producers and consumers on it, so a single signal can wake the wrong kind of thread. The moment you add acquire(n) (waiters needing different amounts), you are back to needing a broadcast.
Is your semaphore fair? How would you make it first come, first served?
No. When a permit is released, a thread that has just arrived can take the lock and the permit before the woken waiter gets the lock back. This is called barging, and it is why unfair semaphores have higher throughput. To make it FIFO, keep a queue of waiters (or tickets) and hand the permit directly to the head of the queue in release, so a newcomer finds nothing free while anyone is waiting. Java's library offers this as a constructor flag; it costs throughput because every handover now needs a context switch.
Add acquire(int n) that takes n permits at once.
Wait while permits &lt; n, then subtract n. release must now broadcast, because waiters need different amounts and one signal could wake a thread that still cannot proceed. Watch for starvation: a request for 5 can wait forever while requests for 1 keep taking permits as they appear. The fix is again a FIFO queue where the head blocks everyone behind it until its n permits are free.
Build a mutex from your semaphore. What does it still lack?
Start it with one permit: lock is acquire, unlock is release. That gives mutual exclusion, but not a real mutex, because a semaphore has no owner: any thread can call release, even one that never locked, and a second release silently creates a second permit. Record the owner in lock and check it in unlock (throw if the caller is not the owner); add a hold count and you have a reentrant lock. Ownership is also what lets an operating system apply priority inheritance to a mutex.
Now the other direction: a counting semaphore built only from binary semaphores.
Use two binary semaphores and an integer: mutex (starts at 1) guards count, and gate (starts at 1 if count is above 0, else 0) is open exactly when a permit may be free. Acquire: pass the gate, take the mutex, subtract one, and re-open the gate only if permits remain, then release the mutex. Release: take the mutex, add one, and open the gate only when the count goes from 0 to 1, then release the mutex. The gate is never signalled twice, which matters because a binary semaphore cannot hold two signals. Early published attempts at this construction had subtle bugs, which is why interviewers like asking for it.
What can go wrong when a timed waiter gives up?
Picture this: release signals one waiter, and that waiter's timeout expires at the same moment. If its code checks the clock before checking the permit, it returns false and walks away with the signal. The permit stays free while other threads sleep, a lost wakeup. Checking the permit first (as the predicate forms do) fixes it; so does re-signalling on the way out.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

A semaphore is the smallest useful monitor. The state is one integer, permits. One lock guards it, and one condition variable lets threads sleep until it becomes positive. The invariant is: permits is never negative, and every successful acquire is matched by one decrement. Every method takes the lock, waits in a loop until it can act without breaking the invariant, changes the count, and wakes whoever might now proceed.

Why each line is there

  • Wait in a loop, never with if. A woken thread is only told "something changed". Another thread may have taken the permit first, and wakeups can be spurious. The loop re-checks.
  • Signal one waiter in release. One new permit can satisfy one waiter, and all waiters want the same thing, so signal (notify_one) wakes exactly the right number. With synchronized, the monitor has only one wait set, so use notifyAll if anything else ever waits on the same object.
  • A deadline, not a fixed sleep, in tryAcquire. Waits can return early (spurious wakeups, a permit taken by someone else), so the remaining time must be recomputed on every pass. In Java, awaitNanos hands you the remaining time; in C++, wait_for(lock, timeout, predicate) converts the timeout to a deadline on the steady clock and loops internally, returning the predicate's final value.
  • Permit before clock. If a permit arrives exactly as time runs out, take it. Checking the clock first can waste a signal that was meant for you.
  • Interruption in Java. lockInterruptibly and await both throw InterruptedException, and they do it before the decrement, so an interrupted thread never consumes a permit. Do not swallow the exception.

Cost and trade-offs

Every call is O(1) under one lock. Under heavy contention all threads serialize on that lock even though the critical section is tiny; production semaphores avoid it with an atomic count and a CAS fast path, falling back to a wait queue only when a thread must block. The design is unfair (newcomers can barge in ahead of waiters), which maximizes throughput; a FIFO handover gives fairness at the cost of a context switch per permit.

How to say it in the interview

The state is one counter guarded by a mutex, with one condition variable for "a permit is free". Acquire waits in a loop while the count is zero, then decrements; release increments and signals one waiter, because one permit can only help one thread and every waiter wants the same thing. The timed version converts the timeout to a deadline and checks the permit before the clock, so a late signal is not lost. It is not fair: a newcomer can barge in, and if you need FIFO I would hand permits to a queue of waiters instead.
