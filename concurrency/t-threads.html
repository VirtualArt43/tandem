Threads: creating, stopping and failing

Starting and joining threads, getting results out, interruption and cancellation, exceptions inside threads, thread-local storage, daemon threads, sleep and yield.

1Corethreadsjava
What is the difference between calling run() and start() on a Java Thread?
Model answer

start() schedules a Java thread to execute independently and returns without waiting for its task to finish. A platform thread normally has an OS thread; a Java 21 virtual thread uses a carrier. Calling run() directly on the platform Thread below is an ordinary call on the current thread, with no new concurrency. In Java 21, directly calling run() on a virtual thread does nothing.

Two more facts interviewers like: a Thread object is single use, so to run the task again you create a new thread or use an executor; and start() is a synchronization point, because everything the parent did before start() happens-before everything the new thread does.

Likely follow up: "Why is overriding run() in a subclass usually worse than passing a Runnable?" It ties the task to one way of running it; a Runnable can go to a thread, an executor or a test.

2Corethreadscpp
What happens if a std::thread is destroyed while it is still joinable? How do join, detach and std::jthread differ?
Model answer

The destructor of a joinable std::thread calls std::terminate, and the terminate handler runs; the default handler aborts the process. A thread object remains joinable even after its function finishes, until joined, detached or moved from. A default-constructed thread is not joinable.

  • join() waits for the thread to finish, and the thread's completion synchronizes-with the return of join().
  • detach() lets it run on its own. You cannot join it through that std::thread, and it must not touch anything that may be destroyed first: locals of the creator, or globals during program exit.
  • std::jthread (C++20) requests stop and then joins in its destructor, so scope exit cleans up ownership, but can block forever if the worker ignores cancellation or waits on an unwoken resource. Its destructor must not run on its own worker thread.

The trap is exceptions: if code between creating and joining throws, the destructor runs on a joinable thread.

In C++17, write a small guard class whose destructor joins.

Likely follow up: "Is detach() ever right?" Rarely: only when something else guarantees the thread's lifetime. Prefer a pool or a jthread owned by an object.

3Corethreadsresults
How do you get a result back from a thread?
Model answer

Through something that carries both the value and a happens-before edge:

  • Java: submit a Callable to an ExecutorService and call Future.get(); use CompletableFuture.supplyAsync; or have a raw thread write a field that you read after join().
  • C++: std::async returns a std::future; pass a std::promise into the thread; wrap the function in a std::packaged_task; or write a variable that you read after join().

Futures also carry failures: Java wraps the task's exception in an ExecutionException, and C++ rethrows the original exception from get(). A plain thread has no such channel.

Likely follow up: "What if nobody ever calls get()?" Java retains the failure in the future, but nobody observes it unless it is inspected or reported elsewhere. C++ also discards an unobserved exception. Releasing the last reference to a still-running launch::async shared state can wait for completion; arbitrary futures and deferred tasks do not have that rule.

4Corethreadsmemory-model
Besides waiting, why does join() matter for correctness?
Model answer

Because it is a synchronization point. Once termination is confirmed, the thread's actions happen-before the observer continues: in Java by the memory model's thread termination rule, in C++ because the thread's completion synchronizes-with the return of join(). You can then read results without a lock if no other thread is still modifying them. A timed Java join that returns while the target remains alive does not establish completion; check isAlive(). Joining does not repair races between workers.

The mirror rule holds at the start: everything before Thread.start() or the std::thread constructor is visible inside the new thread. What breaks is replacing join() with polling a plain boolean done flag: there is no edge: Java may never observe the flag or may observe stale results; C++ has a data race and undefined behavior.

Likely follow up: "Pool threads never end, so what replaces join()?" Future.get(), a std::promise, a latch or a concurrent queue, each of which provides the same kind of edge.

5CoreinterruptionjavaRubrik
How do you stop a thread in Java?
Model answer

You ask it to stop, and it stops itself. Java has no safe way to kill a thread: Thread.stop() released every monitor mid update and left objects corrupted, so it was deprecated, and since JDK 20 it simply throws UnsupportedOperationException.

The standard mechanism is interruption. t.interrupt() sets the thread's interrupt flag. Blocking methods (sleep, wait, join, BlockingQueue.take, lockInterruptibly, Future.get) respond by throwing InterruptedException; compute loops check the flag between units of work. Executors use the same mechanism: Future.cancel(true) attempts to interrupt a running task, and shutdownNow() makes a best-effort attempt to interrupt workers. Neither guarantees termination.

A volatile boolean stop flag also works for compute loops, but it does not wake a thread blocked in take() or sleep(), which is why interruption (or a carefully designed shutdown message) is preferred.

Likely follow up: "What if the task ignores interrupts or is stuck in a blocking socket read?" Check the flag inside long loops, and close the socket from another thread so the read fails.

6CoreinterruptionjavaRubrik
What should you do when you catch InterruptedException?
Model answer

Never swallow it. An interrupt is a request from whoever owns the thread to stop what it is doing. Throwing InterruptedException clears the interrupt flag, so if you catch it and carry on, the request is gone, and later code waiting for termination can hang forever. shutdownNow() and cancel(true) themselves do not wait for worker termination.

Two correct responses:

  1. Propagate: declare throws InterruptedException. Best for library and helper methods.
  2. Restore and leave: when you cannot throw (inside Runnable.run), call Thread.currentThread().interrupt() and return promptly, so code further up still sees the request.

In a hand-built pool, define whether interrupt means pool shutdown or cancellation of the current task; inspect that policy and shutdown state before deciding whether the worker exits. A broad catch (Exception e) around take() that just continues is the classic bug, because it eats the interrupt along with everything else.

Likely follow up: "Why does throwing clear the flag?" So the handler decides what happens next; otherwise interruptible cleanup calls that check the pending flag could immediately throw again. isInterrupted() observes without clearing; Thread.interrupted() observes and clears the current thread's status.

7Seniorinterruptionjava
What does interrupt() do to a thread that is (a) sleeping, (b) waiting to enter a synchronized block, (c) reading from a classic socket, (d) waiting in lockInterruptibly()?
Model answer

For a live thread, interruption sets an interrupt status and may unblock an interruptible operation. The resulting exception may clear that status; it is not forced termination:

  • (a) sleep, wait, join: normally complete exceptionally with InterruptedException, clearing the flag. Scheduling may delay completion; wait() must reacquire its monitor first, and a racing notification may win.
  • (b) blocked entering synchronized: not interruptible. The thread keeps waiting for the monitor and only notices the flag later. ReentrantLock.lock() behaves the same way.
  • (c) java.io socket read on a platform thread: normally not interruptible for a classic Socket without an associated interruptible channel. Java 21 virtual-thread socket operations are interruptible and close the socket. For the platform-thread case, close the socket from another thread, which makes the read throw SocketException, or set a read timeout. NIO channels that implement InterruptibleChannel are different: an interrupt closes the channel and the blocked call throws ClosedByInterruptException.
  • (d) lockInterruptibly(), tryLock(timeout), Condition.await(): throw InterruptedException.

A pure compute loop notices nothing unless it checks Thread.currentThread().isInterrupted().

If a lock wait must be cancellable, I use lockInterruptibly() or tryLock with a timeout, never synchronized.

Likely follow up: "How do you cancel a task stuck in a blocking read?" Close the resource it is blocked on, and give every blocking call a timeout in the first place.

8Corecancellationcpp
C++ has no interrupt(). How do you cancel a running thread?
Model answer

Cooperatively, as in Java, but you build the signal yourself or use C++20's stop tokens.

  • C++20: std::jthread passes a std::stop_token to its function if the function accepts one. request_stop() (also called by the destructor) sets it, the loop checks stop_requested(), std::condition_variable_any has wait overloads that take the token and wake on a stop request, and std::stop_callback can wake a resource-specific wait. Callbacks may run synchronously in the requesting or registering thread, so keep them short, nonthrowing and free of lock cycles.
  • C++17: a std::atomic<bool> stop flag. If the worker can be waiting on a condition variable, set the flag while holding that condition's mutex, then notify, or the worker can miss the wakeup.

ISO C++ offers no forced thread cancellation. POSIX cancellation is platform-specific; glibc uses forced unwinding that a catch-all handler must rethrow. Prefer cooperative stop tokens.

Likely follow up: "What about a thread blocked in read()?" Use a platform-specific wakeup, such as poll on a socket and a cancellation descriptor, with explicit descriptor ownership. Closing a descriptor in another thread is not a portable way to interrupt read().

9Seniorexceptionscpp
In C++, what happens if an exception escapes a thread's function, and how do you hand it to the thread that waits for the result?
Model answer

If an exception propagates out of the function given to std::thread or std::jthread, std::terminate is called and the whole process terminates; the default handler aborts. Java is gentler: only the thread dies and its uncaught exception handler runs. In C++, an exception escaping a noexcept function also calls std::terminate.

If worker failures should be recoverable, use a top-level catch or a mechanism that carries exceptions across threads:

  • std::exception_ptr: inside catch (...), capture std::current_exception(), store it, and let the waiting thread call std::rethrow_exception.
  • std::promise<T>::set_exception: the matching future::get() rethrows it.
  • std::packaged_task and std::async do this for you.

In a hand-built pool, wrap each task in a std::packaged_task so a failing task neither kills the process nor the worker, and the submitter sees the exception through its future.

Likely follow up: "Should the worker catch everything?" Catch and record everything at the task boundary; do not try to recover inside the worker from errors you do not understand.

10Coredaemonjavacpp
What is a daemon thread, and what is the closest C++ equivalent?
Model answer

In Java, the JVM exits when the only threads left are daemon threads. Daemons are abandoned mid flight: their finally blocks are not guaranteed to finish and buffered writes may be lost. Use them only for background helpers whose work can be dropped, such as cache cleanup or metrics. Call setDaemon(true) before start(); platform threads made with ordinary constructors inherit their creator's daemon status; builders and factories can set it explicitly. The default thread factory of Executors creates non-daemon threads, which is why a forgotten pool keeps the JVM alive after main returns. Virtual threads are always daemon threads.

C++ has no daemon concept. The nearest thing is a detached thread, and it is dangerous: returning from main calls exit, which destroys static objects and flushes streams while detached threads may still be using them. Accessing destroyed objects or racing with cleanup is undefined behavior; detachment alone is not.

In C++ I own every thread and join it before main returns; in Java I make background helpers daemon threads only if losing their work is acceptable.

Likely follow up: "Your Java program does not exit after main returns. Why?" A non-daemon thread is still alive, usually an executor that was never shut down. A thread dump shows which one.

11Corethread-localcppMicrosoft
How does C++ thread_local work: when is each copy created and destroyed, and what can go wrong?
Model answer

thread_local gives each thread its own instance with thread storage duration. A function local thread_local is initialized the first time each thread passes its declaration. Namespace-scope dynamic initialization may occur before the thread function starts or be deferred under the standard's initialization rules; do not assume one universal eager or lazy policy. Each thread's copies are destroyed when that thread exits normally, in reverse order of construction; the main thread's copies are destroyed at exit, before static objects.

What goes wrong:

  • Long-lived pool threads retain their thread_local caches until worker exit, and "per request" context leaks into the next task on that thread unless you reset it per task.
  • Destruction order: a thread_local destructor that touches a static or another thread_local that is already gone is undefined behavior.
  • Access cost: dynamic initialization adds a check per access, more so across shared libraries; trivially constructed types are cheapest.
  • Coroutines resumed on a different thread see that thread's copy.

Likely follow up: "And Java's ThreadLocal?" Same idea as a per-thread map entry; in pools you must call remove() in a finally, or values leak between tasks and keep objects alive.

13Corethreadsjava
Why is passing a Runnable (or using an executor) better than extending Thread, and what does a ThreadFactory give you?
Model answer

Extending Thread mixes the task (what to run) with the mechanism (how it runs). A Runnable or Callable is only the task, so the same code can run on a new thread, on an executor, on the current thread in a unit test, or be retried. Java has single inheritance, so extending Thread also spends your one superclass on something you rarely customize.

A ThreadFactory centralizes how an executor creates threads: the name (essential in thread dumps and logs), the daemon flag, the priority, and the UncaughtExceptionHandler. The default factory names threads pool-N-thread-M; a dump that says order-writer-3 instead saves real debugging time. Java 21 builders make this short:

The C++ standard library has no corresponding ThreadFactory API; you name threads with platform calls such as pthread_setname_np, which debuggers and top can show.

Likely follow up: "Does the factory's uncaught exception handler see task failures?" For a normal ThreadPoolExecutor, an unchecked task failure escaping execute() can reach it. Tasks run with submit() have their exceptions captured in the Future.

14Seniorpriority
Do thread priorities work? Would you use them to fix starvation?
Model answer

Platform-thread priorities are scheduling hints, not correctness guarantees; their OS mapping depends on the JVM and platform. Java 21 virtual threads always have normal priority and ignore changes. std::thread has no priority API; you would call pthread_setschedparam on native_handle(), and real-time policies generally need appropriate privileges or configured limits.

Priorities do not fix starvation caused by lock unfairness, because a high priority thread waiting for a lock still waits for the lock. And they create a new failure, priority inversion: a high priority thread waits for a lock held by a low priority thread, which in turn cannot run because medium priority threads keep the CPU busy. On platforms that support it, a POSIX mutex configured with PTHREAD_PRIO_INHERIT can temporarily raise the holder's priority. Ordinary Java and C++ locks do not promise this behavior.

I fix starvation by design: fair locks or FIFO queues where order matters, bounded batches, and separate pools per class of work, not by tuning priorities.

Likely follow up: "Why can priority inheritance not work with a semaphore?" A semaphore has no owner, so the system does not know whose priority to boost.

15Corethreadscpp
In C++, what can go wrong when you pass arguments to a std::thread?
Model answer

std::thread decay copies its arguments into storage owned by the new thread and then passes them as rvalues. That leads to four traps:

  • References: a function taking T& will not compile unless you pass std::ref(x), and a function taking const T& silently receives a reference to the copy, not to your object.
  • Dangling captures: a lambda that captures locals by reference ([&]) dangles if the creating function returns before the thread finishes, which is easy with detach() or a thread stored elsewhere.
  • Arrays and pointers: a local char buf[64] decays to char*; the copy is just the pointer to your soon to die buffer.
  • Move-only arguments such as std::unique_ptr must be moved in explicitly.

The rule: hand over ownership by value or move, share lifetime through std::shared_ptr, or join within the lifetime of every reference. Shared ownership does not synchronize the pointee. The C++20 jthreads below also join during unwinding if construction of the second worker fails; C++17 needs join guards.

Likely follow up: "Why does Java not have this problem?" Lambdas capture only effectively final locals, and objects live on the garbage collected heap, so nothing dangles; shared mutable objects can still race, though.

16Corethreadslifecycle
What happens if main finishes while other threads are still running?
Model answer

Java: returning from main need not end the JVM. The JVM keeps running until every non-daemon thread has finished; returning from main only ends the main thread. System.exit initiates shutdown: hooks run while other threads may continue, then the JVM halts without guaranteeing their cleanup. A stuck hook can delay shutdown.

C++: two bad outcomes. If a std::thread object is still joinable when its destructor runs (for example a local in main), the program calls std::terminate. If threads were detached, returning from main calls exit, which destroys static objects and flushes streams while those threads may still use them. Accessing destroyed state or racing with cleanup is undefined behavior.

So a clean shutdown is an explicit sequence: tell workers to stop, wake any that are blocked, join them, and only then destroy state they use. A Java join timeout requires checking liveness and an explicit failure policy, not proceeding with unsafe cleanup.

Every thread has an owner, and the owner joins it before it goes away.

Likely follow up: "How do you guarantee that in C++?" Stop and join worker members before destroying their dependencies. Members are destroyed in reverse declaration order, and a jthread destructor can still hang if its worker cannot finish.
