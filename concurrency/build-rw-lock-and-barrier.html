Build it yourself: read-write lock and reusable barrier

Build a writer-preferring read-write lock and a reusable barrier, then reason about fairness, cancellation, generations and visibility.

Asked atRubrikMicrosoft
Before this:Build it yourself: semaphore and latchRead-write locks and StampedLockBarriers and phasers

A read-write lock and a reusable barrier are what interviewers ask you to build when a semaphore is too easy. Each has one idea that separates a working answer from a subtly broken one: who goes first when readers and writers both wait, and the generation counter that stops a fast thread from passing the next barrier too early.

In plain words

A museum gallery lets any number of visitors look at the paintings together, but the restorer needs the room empty. If visitors keep streaming in, there is never a moment when the room is empty, and the restorer waits all day. So the guard adopts a rule: once the restorer is waiting at the door, no new visitors go in; the ones inside finish, the restorer works, then the queue of visitors goes in together.

A walking group meets at every checkpoint before anyone continues. A fast walker may reach the next checkpoint while someone else is still leaving the previous one. Numbering the checkpoints prevents the old all-clear from releasing someone at the next checkpoint. Everyone waits for the all-clear for their own checkpoint.

Part 1: a read-write lock

A read-write lock has two modes: any number of readers together, or one writer alone. You met the library versions in read-write locks; here you build one. The state is three fields, all guarded by one mutex:

  • readers: how many threads hold the read lock now.
  • writer: whether a writer holds the lock now.
  • waitingWriters: how many writers are blocked trying to get in.

Invariant: if writer is true then readers is 0, and at most one writer holds the lock. Every method keeps it true, and every wait loop is a check of it.

Two policies, two kinds of starvation

PolicyA reader may enter whenWho can starve
Reader preferenceNo writer holds the lockWriters: overlapping readers can keep readers above zero forever (writer starvation)
writer preferenceNo writer holds the lock and no writer is waitingReaders, if writers keep arriving
Fair (arrival order)No writer holds the lock, and no writer is ahead of it in the queueNo starvation if holders finish and eligible threads are eventually scheduled

The difference between the first two is literally one condition, waitingWriters > 0, plus the bookkeeping to maintain it. Writer preference is appropriate when new readers must stop delaying a queued update. It prevents starvation caused by a continuous stream of readers, but this implementation does not order writers: a newly arriving writer can beat a signalled one. Writer preference is not FIFO fairness, and it does not guarantee bounded waiting for every individual writer.

Why each line is there

  • Two condition variables. Readers and writers wait for different predicates, so each gets its own condition. Signals target the right kind of waiter, which must still re-check after acquiring the mutex: another thread can get there first. With one condition, use a broadcast on changes that may admit waiters to avoid waking only the wrong kind.
  • The last reader signals one writer. Only when readers reaches zero can a writer proceed, and only one writer can, so one signal is right.
  • Unlocking a writer prefers the next writer, and only when no writer waits does it wake all readers, because every waiting reader can enter together.
  • waitingWriters is counted before waiting, which holds back new readers once the writer registers under the internal mutex.
  • The cancelled writer (Java). A writer interrupted while waiting leaves, but its waitingWriters entry was holding readers back. If it was the last waiting writer and no writer holds the lock, it must wake the readers, or they sleep forever. That finally block is the line most hand-built versions forget, and the same applies to any timed tryLockWrite.
  • The C++ method names. The six untimed members, lock, try_lock, unlock and their shared counterparts, provide the interface expected by std::unique_lock, std::lock_guard and std::shared_lock. The try methods also try the internal mutex, so they never wait for it; they may return false even if the logical lock is free. Readers still respect waiting writers. There are no timed methods, so timed guard constructors are unsupported. The practice problem uses lockRead style names in both languages.

Why the protected data is visible. The internal mutex is released while user code holds the logical read or write lock. The flags enforce exclusion, while each logical unlock acquires and releases the internal mutex after the protected access; the next admitted holder acquires it before accessing the data. That chain publishes earlier writes. Readers must not mutate shared data under a shared lock.

The lock deliberately omits owner tracking, recursion, upgrading and timed acquisition. Only a thread that acquired a mode may release it, exactly once; keep the lock alive until all users finish. The demos use C++20 std::jthread; in C++17 use std::thread and explicitly join every thread before its captured state is destroyed. The printed maximum reader overlap is schedule dependent, not guaranteed to be 4.

Two traps that come with writer preference

Reentrant reads can deadlock. A thread holding the read lock calls a helper that takes the read lock again. If a writer arrived in between, the second lockRead waits behind the writer, and the writer waits for the first read lock to be released, which never happens: a self-deadlock. Java's ReentrantReadWriteLock avoids this by tracking per-thread read holds; a hand-built lock does not, so do not re-enter it.

Upgrades deadlock. "Read, and if needed, write" cannot be done by asking for the write lock while holding the read lock: even one reader waits for its own read hold to disappear, and two upgraders also wait for each other. This lock upgrade and downgrade problem is why ReentrantReadWriteLock allows downgrading (write to read) but not upgrading. Release the read lock, take the write lock, and check the condition again, because things may have changed in the gap.

Part 2: a reusable barrier

A barrier for N parties needs a count of arrivals, a lock and a condition variable. Getting it to work once is easy. Getting it to work round after round is where most first attempts break.

The last thread resets the count and wakes everyone, but by the time the woken threads re-check, the count says 0, so they go back to sleep. The natural patches fail differently. Not resetting the count makes it a one-shot latch. Letting the last thread to leave do the reset opens a worse hole: a fast thread can leave, do the next round's work, and arrive again before a slow thread has left, and the two rounds blur together.

The generation counter

The fix is a generation counter: a number that the barrier increments every time it opens. A thread notes the generation when it arrives and waits until the generation changes, not until a count looks right. The last arrival resets the count and bumps the generation in one step under the lock. A slow thread from round 1 sees "my generation has passed" and leaves, however many threads have already arrived for round 2. A fast thread arriving for round 2 records the new generation, so it waits for round 2's trip and cannot be released by round 1's.

Why each line is there

  • myGeneration is read on arrival, under the lock. It names the round this thread belongs to. Waiting for "the generation changed" is immune to the count being reset and immediately bumped by fast threads from the next round.
  • The last arrival does everything in one step: runs the trip action, resets the count, bumps the generation and signals all, all while holding the lock, so no thread can observe a half-reset barrier.
  • Signal all, not one. Every waiter of the round can proceed.
  • The arrival index is computed before counting this thread, so the first arrival gets parties - 1 and the last gets 0, matching CyclicBarrier. Index 0 can pick one thread for a once-per-round job after returning, but other parties can already continue. Use the trip action when all must see that job complete before leaving.
  • The trip action runs under the lock, as in CyclicBarrier, so every party's work for the round happens-before it and it happens-before everyone's next round. Keep it short: everyone is waiting.
  • Breaking the barrier (Java). An interrupted waiter has already been counted. If it simply left, the round would trip without it, and the next round would wait forever for a party that is gone. It breaks the barrier: the interrupted caller throws InterruptedException, and peers still waiting for that round throw BrokenBarrierException unless they too are interrupted. If the interrupt arrives after its round already opened, it returns normally and keeps the interrupt flag set. An interrupt flag on entry is checked before counting the caller, including the last arrival. A trip action throwing RuntimeException or Error breaks the barrier before propagating the failure. The C++ version, like std::barrier, has no broken state: its trip action must not throw, and parties must not abandon it.

The phase contract matters. Each of a fixed group of parties calls once per round. The action must not re-enter this barrier or wait for a participant that cannot proceed until the action returns. Java's sample stays broken permanently; it has no timeout or reset API. If work fails before a party calls await, the barrier cannot detect that absence: the coordinator must arrange cancellation, or use timed waits and a group failure policy.

The C++ sample has no dropout API. C++20 std::barrier::arrive_and_drop() counts an arrival in the current phase and reduces future participation; call it instead of that phase's arrival, never after already arriving. Its completion function must satisfy a non-throwing invocation requirement. Our C++ generation uses an unsigned type, so wraparound is defined; a full wrap cannot overtake a waiter under the fixed-party contract because that waiter is needed for the next round.

One barrier is not a snapshot of future work. All writes before arrival reach the trip action through the mutex, and the action finishes before any participant resumes. Reading everyone else's slots after returning while fast parties overwrite them for the next round would need a second barrier, double buffering or another protocol. The demo reads the slots inside the action, where no participant can start the next round.

Worked example: Rubrik's ClientWrapper

A Rubrik phone screen asked for a wrapper around Client(init, request, close): init is exclusive and blocks requests and close; requests run concurrently once init has succeeded; close waits for in-flight requests; close happens only once and never concurrently. Commenters solved it with a read-write lock or shared_mutex, and the mapping is direct: requests take the read lock, init and close take the write lock.

Where the policy matters. close() is a writer arriving while requests keep flowing. Java's example chooses fair ReentrantReadWriteLock admission; its default non-fair mode promises no acquisition order and can indefinitely postpone a reader or writer. std::shared_mutex also promises no fairness. Replacing its type with our writer-preferring lock stops newly admitted readers from repeatedly delaying close, although individual writer fairness still needs an ordered queue.

State the wrapper's contract. The underlying client must support concurrent requests, must outlive the C++ wrapper, and must not call back into it while these locks are held. A request that gets the lock before successful initialization is rejected; close before init makes the wrapper terminal. If init throws, a later init retries, so the client must support that; close is attempted at most once even if it throws, because the closed flag is set first.

Holding a read lock through client.request lets close wait for in-flight requests, but a hung request can block close indefinitely. Require request deadlines. An alternative uses a closing flag and an active-request count: reject new requests once closing begins, wait for the count to reach zero, and then close outside the state mutex.

Common mistakes

  • Reader preference by accident. Letting readers in whenever no writer holds the lock starves writers under a steady read load.
  • Waking one reader after a write. All waiting readers can share the lock; waking one leaves the rest asleep until the next write.
  • Forgetting the cancelled writer. A writer that gives up (interrupt or timeout) must remove itself from waitingWriters and, if it was holding readers back, wake them.
  • Re-entering or upgrading. A hand-built lock is not reentrant; a read-to-write upgrade deadlocks. Release, re-acquire, re-check.
  • A barrier that waits on the count. Waiters must wait for the generation to change; a reset count makes them sleep forever, and a shared flag lets fast threads lap slow ones.
  • notify in a barrier. Only one waiter of the round wakes.
  • Silently leaving a barrier. A departing party needs an explicit group failure protocol. Java wait interruption breaks this barrier; C++ dropout needs a different implementation such as std::barrier, not this sample.
  • Unlocking a read lock you do not hold. The reader count becomes wrong, possibly negative, and exclusion can fail. Java library locks detect illegal ownership; do not assume C++ mutexes diagnose misuse.

In the interview

These two are the step up from "build a semaphore". Rubrik has asked for a reader-writer lock from scratch, a phone screen whose standard answer is a read-write lock (the ClientWrapper above), and a level-by-level BFS synchronized with a barrier. A Microsoft candidate made a key-value store thread-safe with a hand-written reader-writer class in a C++ database team's round.

For the read-write lock I keep three fields under one mutex: active readers, whether a writer holds it, and how many writers are waiting. Readers wait while a writer holds it or one is waiting, which is writer preference, so a stream of readers cannot starve updates. The last reader out signals one writer; a writer leaving hands over to the next writer if one waits, otherwise wakes all readers. Two conditions target the right kind of waiter, and each waiter rechecks its predicate. For the barrier, the key is a generation counter: each thread records the generation when it arrives and waits until it changes. The last arrival runs the action, resets the count, bumps the generation and signals all, under the lock. That makes it reusable, and a fast thread from the next round can never release or trap a slow one from this round.

Follow ups to expect: "Make it fair" (serve arrivals in order: FIFO tickets, with consecutive readers admitted together; that is the fair read-write lock problem), "What if a writer times out?" (the cancelled writer must wake the readers it held back), "What does your barrier do if one thread is interrupted?" (break it, like CyclicBarrier), "Why is a read-write lock sometimes slower than a mutex?" (below).

Senior depth

A read-write lock is not free for readers. Every lockRead writes the shared reader count, so readers contend on the internal mutex and that cache line even though their protected read sections can overlap. For short read sections a plain mutex is often as fast, and for read-mostly data an immutable snapshot behind an atomic reference may reduce reader contention at the cost of copying and reclamation. Measure the workload. Some designs offer a different read path: Java's StampedLock offers optimistic reads that write nothing (read, then validate a stamp); failed validation requires a retry or a locked read, and Java optimistic reads must use data that is safe to inspect speculatively.

Fair read-write locks. The usual fair design queues arrivals in order and admits a batch of consecutive readers together, then the next writer alone with no barging past queued writers. Phase-fair designs instead organise admission into reader and writer phases; their precise guarantees depend on the algorithm. FIFO bounds overtaking if holders finish and eligible threads run, but it cannot give a wall-clock deadline under an arbitrary scheduler.

Sense reversal. Spinning barriers in high-performance code use the same idea as the generation counter with a single bit: each thread keeps a local "sense" that flips every round, and waits until the shared sense matches it. The parity of the generation is the sense. The shared sense still needs publication: for example, a release store and acquire loads on a C++ atomic, or a Java volatile field; a plain spin flag is not safe.

Key takeaways

  • Read-write lock state: active readers, a writer flag and waiting writers, all under one mutex, with the invariant "a writer excludes everyone".
  • Writer preference holds new readers back while a writer waits; it prevents starvation caused by incoming readers, but is not FIFO among writers and does not support reentrant reads or upgrades.
  • The last reader signals one writer; a leaving writer prefers the next writer, otherwise wakes all readers; a cancelled writer must release the readers it held back.
  • A reusable barrier waits for a generation counter to change, never for a count to look right; the last arrival resets and bumps it under the lock and signals all.
  • Handle failure: Java breaks the barrier so everyone fails fast; in C++ the trip action must not throw and parties must not silently leave.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A read-write lock admits a reader whenever no writer holds it. Readers arrive constantly, and their read sections overlap. What happens to a writer that calls lockWrite?
Why. That is reader preference, and overlapping readers can keep readers above zero indefinitely: writer starvation. Writer preference fixes it by making new readers wait as soon as a writer is waiting.
With this lesson's non-reentrant writer-preferring lock, thread T holds the read lock and calls a helper that calls lockRead() again. Meanwhile a writer W has called lockWrite() and is waiting. What happens?
Why. A hand-built lock does not know that T already reads, so the writer-preference rule makes T wait behind W, and W can never proceed while T holds a read lock. Java's ReentrantReadWriteLock tracks per-thread read holds to avoid this; with your own lock, do not re-enter.
With at least two fixed parties, all state guarded by one mutex and each party arriving once per round, what goes wrong with this barrier?
Why. The waiters are waiting for "arrived == parties", but the last thread already reset it before they re-check. The loop is right; the condition is wrong. Waiting for a generation number to change is the condition that survives the reset.
Thread A writes x = 7, thread B writes y = 9, then both call this lesson's barrier successfully. A logs y, B logs x using synchronized output, and neither variable is changed again. What values must each observe?
Why. The internal mutex publishes each party's pre-arrival writes before the trip and before peers return, so both see the assigned values. Plain fields are safe here because the barrier orders the conflicting accesses. It does not order the two prints or make writes in a later round safe to overlap these reads; C++ shared output also needs its own synchronization.
Java onlyIn the Java barrier, a waiting thread is interrupted before its round trips. Why does it break the barrier instead of just leaving?
Why. Silently leaving corrupts the party count: the group is now one short for every later round. Breaking the barrier, as CyclicBarrier does, turns a hidden future hang into an immediate, visible failure for everyone.
C++ onlyThe C++ read-write lock implements lock, try_lock, unlock and their shared counterparts with the synchronization semantics shown. What does that give you?
Why. The standard lock guards are templates that only call those member functions. Matching the names lets you write std::shared_lock<ReadWriteLock> r(rw); and never call unlock by hand. The try-lock members also support try-lock guards, but timed constructors require timed methods that are absent. Naming the operations does not choose a policy or add recursion; those are properties of the implementation.
In the writer-preferring lock, a writer calls unlockWrite and finds that no other writer is waiting. What should it do?
Why. Waiting readers are all blocked on the same condition, and every one of them may now enter. Signalling one would leave the rest asleep until the next write. When writers are waiting, writer preference hands over to one writer instead.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a reader-preferring read-write lock, then show exactly which lines change to make it writer-preferring, and say what each policy risks.
Model answer

To make it writer-preferring: add a waitingWriters count; in lockWrite, increment it before the wait loop and decrement it after (in a finally in Java, waking the readers if this writer gave up); change the reader's wait condition to "a writer holds the lock or a writer is waiting"; in unlockRead, signal a writer only if one is waiting; and in unlockWrite, signal the next writer if one is waiting, otherwise all readers. In C++, add the same waiting-writer check to try_lock_shared as to the blocking read path. Reader preference risks writer starvation under a steady read load; writer preference risks reader starvation under a steady write load and makes reentrant reads deadlock.

Debug
A teammate's barrier works for the first round, but in a loop of rounds a fast thread sometimes runs ahead into round k+1 while a slow thread is still finishing round k. Their barrier sets an open flag when the last thread arrives, waiters wait while !open, and the last thread to leave resets open to false. Explain the bug and fix it.
Model answer

The flag cannot tell rounds apart. When round k trips, open becomes true. A fast thread leaves, does round k+1's work and arrives again before the slow thread has left round k, so open is still true and the fast thread passes round k+1's barrier on its own. This reset scheme has no round identity. A sense-reversing barrier is different: its per-party expected bit identifies the phase, so a carefully designed boolean protocol can work.

The fix is a generation counter. Each thread reads the generation when it arrives, under the lock, and waits until the generation differs from the one it read. The last arrival resets the count to zero, increments the generation and signals all, all under the lock. A fast thread arriving for round k+1 reads the new generation, so it waits for round k+1's trip; a slow thread from round k sees its generation has passed and leaves, regardless of how many round k+1 arrivals have happened. No reset by the last leaver is needed at all, which removes the second race too.

Design
Add tryLockWrite(timeout) to the writer-preferring read-write lock. What can go wrong when it times out, and how do you handle it?
Model answer

While the writer waits, it is counted in waitingWriters, and that count is what holds new readers back. If it times out and simply returns false, two things break. First, if it forgets to decrement waitingWriters, readers are blocked forever by a writer that no longer exists. Second, even if it decrements, readers that arrived while it was waiting are asleep on the readers condition, and nobody will signal them until some other writer finishes, which may never happen.

So the timeout path, under the lock, must decrement waitingWriters, and if it is now zero and no writer holds the lock, signal all readers. It must also re-check the condition one last time before giving up, because the lock may have become free just as the time ran out. I would write the wait as a deadline loop (awaitNanos with the remaining time in Java, wait_until with a fixed steady_clock deadline in C++), and put Java cleanup in a finally so interruption takes the same path; C++ needs scope-based or explicit exception cleanup. If another writer remains and the lock is free, wake a writer too, so cancellation cannot strand a handoff. If the timeout covers the entire call, acquiring the internal mutex must use the same deadline: use Java timed tryLock and a suitable C++ timed mutex with condition_variable_any. The untimed internal mutex in the sample cannot promise a total-call deadline.

"Build me a read-write lock. How do you keep a stream of readers from delaying a writer forever, and what does your policy give up?"
What a strong answer covers

  • Guard reader count, active writer flag and waiting writer count with one mutex
  • Block new readers once a writer registers, and wait in predicate loops
  • Explain last-reader signalling and writer handoff or reader broadcast

How a senior would say it
I would use a writer-preferring lock: many readers can hold it together, or one writer can hold it alone. One internal mutex protects the reader count, the active writer flag and the waiting writer count. A reader waits if a writer is active or waiting. A writer registers before waiting for no readers and no active writer. Every wait rechecks its predicate after reacquiring the mutex. For example, if one reader is inside and a writer queues, a second reader waits instead of extending the read phase. The last reader signals a writer. A writer leaving signals another writer if one waits, otherwise it wakes all readers. A cancelled writer must undo its waiting count and wake readers if it was the last writer holding them back. The internal mutex also publishes protected writes through the logical unlock and next acquisition. The trade-off is that readers can starve under continuous writes. Individual writers can also be overtaken because this is not a FIFO queue. For bounded overtaking I would queue arrivals explicitly. I would forbid recursive reads and upgrades: a reader waiting behind a writer can otherwise hold the very read lock that prevents that writer from entering.

Likely follow up: How would a timed writer acquisition avoid leaving readers asleep after it gives up?

  • Explain a fast next-round arrival versus a slow previous-round waiter
  • Explain publication and why an action after returning is not a barrier action
  • Define interruption, action failure and missing-party behaviour
How a senior would say it
I would identify each round with a generation, rather than wait for a count that the last arrival resets. Each party records the current generation and increments the arrival count under one mutex. Unless it is last, it waits until that generation changes. The last arrival runs the action, resets the count, advances the generation and wakes everyone, still under the mutex. Suppose a fast party reaches round two before a slow party has returned from round one. The fast party records the new generation and waits. The slow party sees that its old generation has changed and returns. They cannot confuse the two releases. The mutex also publishes all work before arrival to the action, and the action finishes before anyone resumes. Selecting index zero after returning does not give that last guarantee. For failure, my Java version rejects an interrupt already set on entry. An interrupted waiter or failing action breaks the current barrier and wakes peers with failure. It stays broken. My C++ version requires a non-throwing action and no abandoned parties. A failure before arrival is invisible to either count: the coordinator needs cancellation, timed waits, or an explicit dropout protocol. I would define that policy before shipping it.

Likely follow up: Why might reading everyone else's results after the barrier require a second barrier?
