1Coresafety-ladderdesign
You have shared mutable state. What is your order of preference for making it safe?
Model answer

I climb a ladder and stop at the lowest rung that works, because each rung up is harder to get right and harder to review:

  1. Do not share. Confine the state to one thread: a per-request object, a thread-local, or a single owner thread fed by a queue.
  2. Do not mutate. Use an immutable object, published safely; "changes" build a new object and swap one reference.
  3. Delegate to a proven thread-safe component: ConcurrentHashMap, a blocking queue, LongAdder. C++ has no standard concurrent containers, so this means a small, well-tested class that wraps a mutex.
  4. Use an atomic for a single independent variable: a counter, a flag, a reference swap.
  5. Use a lock when an invariant spans several variables. Start with one lock, then go finer only if contention is measured.
  6. Go lock-free only when profiling demands it and I can argue correctness, including memory reclamation.

Interviewers punish the opposite habit. An Uber interviewer complained that candidates "put synchronization everywhere", and LinkedIn interviewers asked candidates to name the specific race each lock prevents. So for every lock, say which invariant it protects and which interleaving it rules out.

Likely follow up: "Your design has three locks. Justify each." Name the state each one guards, the check-then-act or read-modify-write it makes atomic, and the order in which they may be nested.

2Coreconfinementthread-localjavacpp
What is thread confinement, and what are the pitfalls of thread-local storage?
Model answer

Data that only one thread can reach needs no synchronization at all: that is thread confinement. Local variables, per-request objects that are never shared, and everything owned by an event loop thread are confined. It is the cheapest form of thread safety, enforced only by discipline: once a reference escapes to another thread, the guarantee is gone.

Thread-local storage gives each thread its own copy of a variable: Java ThreadLocal, C++ thread_local. Typical uses are a non-thread-safe helper per thread (a formatter, a random generator, a scratch buffer) and per-thread counters merged at the end.

The pitfalls:

  • Pool threads live forever, so a value set by one task is still there for the next task on that thread. That leaks memory and, worse, leaks context: one user's identity seen by another user's request. Always remove() in finally.
  • InheritableThreadLocal copies values only when a thread is created, so a pooled task sees whatever was set when the pool happened to start that thread, not its submitter's value.
  • With millions of virtual threads, a large value per thread costs real memory.
  • C++ thread_local objects are destroyed when the thread exits, not when a pool task ends, and each access may cost a TLS lookup.

Likely follow up: "How would you pass request context without thread-locals?" Pass it explicitly as a parameter. Java also has ScopedValue (a preview API in Java 21, final in JDK 25), which binds an immutable value for the duration of a call and cannot leak past it.

3Coreimmutabilitysafe-publicationjavacpp
Why is an immutable object thread-safe, and what does it take to build one in Java and in C++?
Model answer

If nothing writes to an object after construction, there is nothing to race on: any number of threads can read it at once. The one remaining requirement is safe publication: other threads must see the fully constructed state, not a half-built one.

In Java: make every field final, make the class final or otherwise non-overridable, add no setters, copy mutable inputs on the way in and mutable outputs on the way out (List.copyOf), and never let this escape from the constructor. The memory model then guarantees that any thread that sees the reference sees the final fields as they were at the end of the constructor, even if the reference was published through a data race. Records give you final fields, but a record holding an ArrayList is not deeply immutable.

In C++: const members, or simply no mutating member functions once the object is shared. C++ has no final-field rule, so the pointer itself must be published with synchronization: before starting the thread (the std::thread constructor synchronizes with the start of the new thread), under a mutex, through an atomic with release and acquire, or as std::shared_ptr<const T> swapped through an atomic. A mutable member, such as a cache, quietly breaks immutability unless it is synchronized.

Likely follow up: "How do you update an immutable configuration?" Build a new object and swap one atomic reference. Readers keep using whichever version they loaded, and the next read sees the new one.

4Seniorsingle-writeractorsmessage-passing
What is the single writer principle, and when would you choose actors or message passing over locks?
Model answer

One thread owns a piece of state, and every other thread sends it messages through a queue instead of touching the state. The owner applies messages one at a time, so the state needs no lock, operations are naturally ordered, and the data stays in one core's cache instead of bouncing between cores. The log writer thread, a Kafka partition consumer, Redis's main loop and the LMAX Disruptor all work this way.

Choose it when the state has complex invariants that many threads touch, when per-key ordering matters, or when a lock on that state is heavily contended.

The costs to name:

  • Every operation pays queueing latency, and one owner gives at most one core's worth of throughput. To scale, shard: route each key to one of N owners.
  • The mailbox must be bounded, or a slow owner turns into unbounded memory. Bounding it gives you back-pressure.
  • Request and reply needs a future per request. Two actors that block waiting for each other's replies deadlock, so replies should be asynchronous.
  • One slow message delays everything behind it.

Likely follow up: "How do other threads read the owner's state?" Either send a query message that completes a future, or have the owner publish an immutable snapshot after each batch of updates, which readers load without blocking.

5Seniorlock-stripingshardinghash-mapMetaNetflix
How do you shard a map across several locks, and which operations get harder?
Model answer

Lock striping: keep N stripes, each with its own lock and its own sub-map, and choose the stripe from the key's hash. Operations on one key take one lock, so up to N threads work in parallel. A small multiple of the core count is a sensible N; contention falls roughly as 1 over N, with diminishing returns.

What gets harder: size is either exact (lock every stripe in index order) or a cheap approximate sum. Iteration becomes per-stripe and weakly consistent. Operations on several keys must lock the stripes in ascending index order, or they can deadlock. And a hot key still lands on one stripe, so striping cannot help it.

In Java you rarely write this, because ConcurrentHashMap already locks per bin. It is still the answer to "design a concurrent hash map", and to a single-machine cache design where one shard per core is the praised move.

Likely follow up: "And for one hot key?" Make its value an atomic or a LongAdder, or split the key into sub-keys merged on read.

6Coremonitorencapsulation
What is the monitor object pattern, and why lock a private object rather than this?
Model answer

A monitor object keeps its state, its lock and its conditions inside one class. Every public method takes the lock for its whole body, so the invariants hold whenever the lock is free and callers never lock anything themselves.

A private lock matters because any code holding a reference to your object can synchronized (yourObject). It joins your lock graph, so it can deadlock with you or simply hold the lock and stall you.

The pattern's traps: calling callbacks while holding the monitor; returning references to internal mutable state; and clients composing two safe calls (if (available(s) > 0) reserve(s, 1)), which is a check-then-act race. Offer the compound operation as one method instead.

Likely follow up: "Two monitors call each other." Then their locks are nested, so you need an order between them, or make one call happen after releasing the lock (an open call).

7Seniorcopy-on-writesnapshotsjavacpp
When does copy-on-write beat a lock, and how do you implement a lock-free read snapshot in both languages?
Model answer

With copy-on-write, readers load the current immutable version with no lock. A writer copies it, modifies the copy, and atomically swaps the reference. It wins when reads vastly outnumber writes and the data is small: configuration, routing tables, listener lists, feature flags. Each write costs a full copy, writers must serialize or retry, and readers may briefly see the previous version.

The Java lambda may run more than once, so it must have no side effects. In C++, the shared_ptr reference count keeps an old table alive for as long as a reader holds it, which solves memory reclamation for free. std::atomic<std::shared_ptr> is C++20 and library support arrived late (libstdc++ has it; Apple's libc++ still does not); the older std::atomic_load and std::atomic_store overloads for shared_ptr do the same job (deprecated in C++20). Strictly, neither is lock-free in mainstream libraries (a tiny internal lock guards the pointer and count update), but a reader never waits for a writer's copy, which is the property that matters here. CopyOnWriteArrayList packages this pattern in Java, and its iterators never throw ConcurrentModificationException.

Likely follow up: "Two writers at once?" Without the writer mutex or the CAS loop, both copy the same old version and one update is lost.

8Seniorpipelinesfan-outbackpressureMicrosoft
Design a processing pipeline with fan-out and fan-in. How do you keep it bounded, ordered and stoppable?
Model answer

Stages are connected by bounded queues, so a slow stage fills its input queue and blocks the stage before it: back-pressure flows upstream automatically. Throughput equals the slowest stage, so give that stage more workers, and keep the queues small. By Little's law, every queued item adds latency.

Fan-out (several workers on one stage) loses order. Two ways to get it back:

  • Tag each item with a sequence number and put a reorder buffer at the fan-in: hold items in a map or heap keyed by sequence number and emit only the next expected one. Bound it with a window, so a producer waits when it is more than W items ahead of the emitter.
  • If only per-key order matters, partition by key so the same worker always handles the same key.

Stopping: each source sends an end-of-stream marker; a stage forwards it only after all of its workers have seen one (a countdown), so nothing is dropped in flight. Errors go downstream as a failure marker, or set a shared cancelled flag that every stage checks, and the coordinator joins every worker.

A logging pipeline is the classic small instance: application threads, a formatter, and one writer thread that owns the file.

Likely follow up: "Where would you batch?" Right before the expensive I/O stage, so one write or one fsync covers many items.

9Seniorbatchinggroup-commitDatabricks
Batching trades latency for throughput. How do you decide when to flush a batch?
Model answer

Batching pays off when each call has a fixed overhead: a system call, an fsync, a network round trip, a database commit. Per-item cost is the item's own work plus the overhead divided by the batch size.

The flush triggers are a size cap (items or bytes), a time cap (linger: the oldest item never waits longer than T), and the one I prefer by default, natural batching: whenever the consumer becomes free, it takes everything that queued up while it was busy. Under light load batches have one item and latency stays minimal; under heavy load they grow by themselves. That is how group commit works in databases.

Combine it with a size cap so one batch cannot grow without bound, and flush on flush() and on shutdown. Avoid a fixed timer as the only trigger, because it adds that delay to every item even when the system is idle.

As an order of magnitude: if an fsync costs about a millisecond and events arrive at 100,000 per second, natural batching settles at roughly 100 events per fsync.

Likely follow up: "What if a producer must know when its own item is durable?" Give each item a future, and complete every future in the batch after the fsync returns.

10Seniorsingle-flightcaches
Implement single-flight: when many threads miss on the same key at once, exactly one of them loads it.
Model answer

For single-flight, store a future per key, not a value. The first thread to insert the future becomes the leader and runs the load outside any lock; everyone else waits on the same future. If the load fails, remove the entry so the next caller retries, and complete the future exceptionally so current waiters see the error.

Do not run the load inside computeIfAbsent: it holds a bin lock in ConcurrentHashMap for the whole load, blocking unrelated keys in the same bin, and the loader may not touch the map.

Likely follow up: "These entries never expire." As written they double as the cache. Add a TTL per entry, or remove the future once the value is copied into a real cache.

11Seniorlazy-initializationdouble-checked-lockingjavacppMicrosoft
Make a lazily initialized singleton thread-safe. Why is double-checked locking broken without volatile?
Model answer

Double-checked locking reads the field without a lock, and only locks if it is null. Without volatile, the write of the reference can become visible to another thread before the writes made inside the constructor. A second thread sees a non-null reference and uses a half-constructed object. The first unlocked read also has no happens-before edge with the writer. Since Java 5, making the field volatile fixes both problems; in C++ the field must be a std::atomic<T*> loaded with acquire and stored with release.

The simplest correct versions avoid the pattern entirely:

Java's class initialization is lazy and runs under a JVM lock exactly once, so the holder idiom is lazy, safe and lock free after the first call. C++11 guarantees the same for a function-local static. std::call_once with a std::once_flag covers the cases where the object is not a static; if the initializer throws, the next caller tries again.

Likely follow up: "When is the C++ static destroyed?" At program exit, in reverse order of construction. A detached thread that still uses it during exit has undefined behavior, which is why some code deliberately leaks such singletons.

12SeniorlrucachesRubrikAppleMicrosoftConfluent
Make an LRU cache thread-safe. Why does a read-write lock not help, and how would you scale it?
Model answer

An LRU get moves the entry to the front of the recency list. Every read is a write, so get and put both need exclusive access, and a read-write lock adds cost without adding parallelism.

The options, simplest first:

  • One mutex around the map and the list. Every operation is O(1) and short, so this is correct and fast enough for moderate thread counts. Keep loads on a miss outside the lock (single-flight).
  • Shard: N independent LRUs chosen by key hash, each with its own lock and capacity divided by N. Eviction becomes approximately LRU, which is almost always acceptable.
  • Relax recency updates: record hits in a buffer and apply them in batches under the lock, as Caffeine does.
  • Replace the list with CLOCK: each entry has an atomic reference bit that get sets without locking, and an evicting hand sweeps and clears bits.

In Java the base version is a LinkedHashMap with access order and removeEldestEntry, behind one lock. In C++ it is a std::list plus an unordered_map from key to list iterator, with splice to move an entry to the front, behind a std::mutex.

Avoid per-node locks on the list: neighbours need lock ordering, deadlock is easy, and it is usually slower than one lock.

Likely follow up: "Add TTL." Store an expiry time per entry, treat expired entries as misses on read, and evict lazily or with a periodic sweep under the same lock.

13Seniorkeyed-executorordering
Process events in order for each key, but in parallel across keys. How?
Model answer

Use a keyed executor: route every key to a fixed lane: lane = hash(key) % N, where each lane is a single-threaded executor or a queue with one worker. The same key always goes to the same lane, so its events run in FIFO order, and per-key state touched only by that lane needs no lock. Kafka gives per-partition ordering in exactly this way.

The costs: a hot key overloads its lane, and you cannot parallelize one key's ordered stream; a slow event delays every key that shares its lane; lane queues must be bounded; and changing N moves keys between lanes, which is only safe once the lanes are drained.

A per-key alternative on a shared pool chains each task after the previous task for the same key:

Without exceptionally, one failed task would make every later task for that key skip silently. Remove finished tails (for example with tails.remove(key, f) once a future completes and is still the tail), or the map grows with every key ever seen.

Likely follow up: "How is this different from a lock per key?" A lock per key gives mutual exclusion but not order: two waiting tasks for one key can run in either order.

14Stretchoptimistic-readseqlockstampedlockjavacpp
What is an optimistic read, and how do StampedLock and seqlocks work?
Model answer

A reader takes no lock. It reads a version number, reads the data, and reads the version again. If the version did not change (and, for a seqlock, is even), the data it read was consistent; otherwise it retries or falls back to a real lock. A writer bumps the version before and after writing, so the version is odd while a write is in progress.

This suits small, read-mostly data such as coordinates, timestamps and statistics. Readers never block writers, but under a heavy write load they keep retrying. The values read before validation may be torn, so copy them into locals and do nothing with them (no following pointers, no indexing arrays) until validation passes. StampedLock is not reentrant and has no conditions.

In C++, a seqlock's plain data reads during a write are a data race and therefore undefined behavior, so a correct C++ seqlock makes the protected fields atomics (relaxed loads and stores are fine). The reader loads the version with acquire and puts an acquire fence before the second version read; the writer puts a release fence after its first version bump and stores the final version with release. The Linux kernel uses seqlocks for timekeeping data.

Likely follow up: "Why not a read-write lock?" A read lock still writes to a shared reader counter, so readers on different cores contend on that cache line. An optimistic read writes nothing.

15Corefork-joinwork-stealingjavacpp
How does fork/join work stealing work, and when is it the wrong tool?
Model answer

In work stealing, each worker has its own double-ended queue. It pushes and pops its own subtasks at one end, last in first out, which keeps its working set hot in cache. An idle worker steals from the opposite end of another worker's deque, taking the oldest and usually biggest task, so steals are rare and worthwhile. A join inside a fork/join task does not simply park: the worker runs or steals other tasks while it waits.

It fits recursive, CPU-bound divide and conquer: sorting, tree and array reductions, parallel streams. The ForkJoinTask Javadoc's rough rule of thumb is that a task should perform more than 100 and fewer than 10,000 basic computational steps; below some threshold, compute sequentially.

It is the wrong tool for:

  • Blocking I/O in the common pool. It has about as many threads as cores, and it also serves parallel streams and the default async CompletableFuture stages for the whole JVM. Use a dedicated pool, or ForkJoinPool.ManagedBlocker so the pool can add a thread.
  • Tiny tasks, where scheduling overhead dominates.
  • Tasks that contend on one lock, which serializes the whole pool anyway.

C++ has no standard fork/join pool. The C++17 parallel algorithms (std::sort(std::execution::par, ...)) run on an implementation-defined backend (libstdc++ uses TBB when it is installed), and oneTBB's task_group is the explicit form.

Likely follow up: "Parallel stream versus a plain loop?" Only for large, CPU-heavy, independent work: measure, because splitting and merging costs real time.
