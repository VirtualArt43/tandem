The collections you will use

List, Set, Map, Queue and Deque implementations, their costs, LinkedHashMap as an LRU cache, and which collections are safe to share between threads.

Asked atDatabricksAtlassianAppleMicrosoftRubrik
Before this:Genericsequals, hashCode and objects as keys

Interview concurrency code is mostly a collection plus a lock. Pick the right collection and the lock stays simple and short; pick the wrong one and you either do O(n) work while holding the lock, or you share a structure that quietly corrupts itself.

In plain words

Think of a restaurant's storage. A numbered shelf where you fetch item 7 directly (a list). A guest list at the door where each name appears once (a set). A coat check that hands back your coat for your token (a map). A ticket line served in order of arrival (a queue), a stack of plates you can take from the top or the bottom (a deque), a hospital triage line where the most urgent goes first (a priority queue), and an alphabetical filing cabinet where you can ask for "the last folder before M" (a sorted map).

Each is fast at some jobs and slow at others, and none of them comes with a lock on its door. If two cooks grab the same shelf at the same moment, things fall off. Choosing the container is choosing your costs; sharing it between threads is a separate decision you must make on purpose.

Why this matters for concurrency

  • None of the everyday java.util collections is thread-safe: ArrayList, LinkedList, HashMap, HashSet, LinkedHashMap, TreeMap, ArrayDeque, PriorityQueue. Concurrent writes lose elements and can corrupt the structure itself.
  • Classic problems are a collection under a lock: a bounded queue is an ArrayDeque, an LRU cache is a LinkedHashMap, a scheduler or delay queue is a PriorityQueue, a time-based key-value store is a TreeMap per key.
  • Costs multiply under a lock. An O(n) operation inside a critical section makes every other thread wait for it.
  • Interviewers ask about the boundary. Databricks has spent most of a round on why HashMap is not thread-safe and how ConcurrentHashMap locks; Atlassian asked why ConcurrentHashMap instead of HashMap; Rubrik, Microsoft and Apple have asked for an LRU cache and then "make it thread-safe".

The map of the territory

The collection interfaces form two families. Collection covers groups of elements: List (ordered, by index), Set (no duplicates) and Queue (elements waiting to be processed), with Deque (a double-ended queue) extending Queue. Map stands apart, mapping keys to values, with SortedMap and NavigableMap for ordered keys.

Java 21 added sequenced collections: a List, a Deque, a LinkedHashSet or a sorted set now has getFirst(), getLast(), addFirst(), addLast(), removeFirst(), removeLast() and reversed(), and a LinkedHashMap or TreeMap has firstEntry(), lastEntry() and pollFirstEntry(). Optional mutations can still throw UnsupportedOperationException: sorted sets reject addFirst and addLast because their comparator decides position. The accessors read well in interview code: list.getLast() instead of list.get(list.size() - 1).

Lists

ArrayList is a growable array. get(i) is O(1), appending is O(1) amortized (the array grows by about half when full, copying everything once in a while), and inserting or removing anywhere except the end shifts every later element: O(n). It is compact and cache friendly, and it is the right list almost always.

LinkedList is a doubly linked list: O(1) at both ends, but O(n) to reach the middle, one object per element, and poor cache locality. It implements Deque too, but ArrayDeque is faster at that job. In practice you will rarely choose it.

TreeMap earns its place with navigation. "The latest version at or before time t" is versions.floorEntry(t), which is the whole of the time-based key-value store problem once you add a lock. Maps also have useful default methods: getOrDefault, putIfAbsent, computeIfAbsent, compute and merge. On a HashMap they are conveniences; on a ConcurrentHashMap they are atomic, which is the point of using them there.

ArrayDeque is a resizable circular array with O(1) amortized operations at both ends, so it is your default queue (offerLast and pollFirst) and your default stack (push and pop). It rejects null, because poll uses null to mean empty. The JDK documentation itself says it is likely faster than Stack as a stack and faster than LinkedList as a queue. Stack is a legacy class that extends Vector and synchronizes every call; do not use it.

PriorityQueue is a binary heap: offer and poll cost O(log n), peek O(1), and remove(Object) and contains O(n). Two things surprise people: iteration and toString show the heap's internal order, not sorted order, and elements with equal priority come out in no particular order unless you break ties yourself:

The unique sequence number breaks ties, so equal-priority jobs are polled in admission order. It does not make this comparator consistent with equals for every possible Job: two jobs with the same priority and sequence but different names compare as zero while the records are unequal. A PriorityQueue allows that; a sorted set or map would treat such keys as equivalent. Schedulers, delay queues and timers in the coming modules are all this pattern plus a lock and a condition.

In single-threaded code an O(n) step is a performance detail. Under a lock it is a contention problem: every other thread waits for the slowest thing you do inside the critical section. A bounded queue built on ArrayList.remove(0) is O(n) per take while holding the lock; on ArrayDeque.pollFirst() it is O(1).

LinkedHashMap: an LRU cache in a dozen lines

An LRU cache evicts the least recently used entry when it is full. LinkedHashMap can do the bookkeeping for you. Its constructor LinkedHashMap(initialCapacity, loadFactor, accessOrder) with accessOrder true switches it to access order: every get or put moves the entry to the end of its internal list, so the first entry is always the least recently used. Override the hook removeEldestEntry, which put calls after inserting, and return true when the map is over capacity:

The class wraps the map instead of extending it (composition, from classes and interfaces), so callers see only get, put and size, all under one lock. The anonymous subclass exists only because removeEldestEntry is a protected hook. Now the part interviewers probe: why does get need the exclusive lock?

Because in access order a get is a write: the JDK documentation calls a get on an access-ordered LinkedHashMap a structural modification. Two threads calling get at once both relink nodes in the same list:

That is why the common first answer, a ReentrantReadWriteLock with get under the read lock, is wrong for an LRU cache, and why "just use a ConcurrentHashMap" is wrong too: the map and the recency order form one invariant, and ConcurrentHashMap protects only the map. One lock around both is correct. If that one lock becomes a bottleneck, split the cache into stripes by key hash, each a small LRU with its own lock (approximate global order), or use a library such as Caffeine, which records accesses in buffers and applies them to the eviction policy in batches. You will build and stress one in the thread-safe LRU cache problem and study the trade-offs in thread-safe caches.

None of these is thread-safe

Every class in this lesson so far assumes one thread at a time. What happens when two threads write to an ArrayList at once is not just a lost element:

Lost elements, null holes where an element should be, an exception thrown from inside add, and sometimes a size larger than the backing array, so that reading the list afterwards throws. HashMap fails the same way: concurrent puts lose entries and can corrupt buckets, and in Java 7 and earlier a concurrent resize could even link a bucket into a cycle, so a later get looped forever. Reads are not safe either: a reader racing a writer can see a half-updated structure, and an iterator that notices a concurrent change throws ConcurrentModificationException, on a best-effort basis only (see iterators and ConcurrentModificationException).

Three ways to share a collection safely

1. Do not share it. Give each thread its own collection and combine at the end: per-thread word counts merged after join, or tasks that return lists through futures. Confinement needs no lock at all.

2. Guard it with your own lock. This is most interview code: a private collection, a private lock, and every access, reads included, under that lock. When the invariant spans several fields (a map and its size counter, a list and a total), this is usually the simplest correct option. Atomically replacing one immutable object containing all the state is another design, with copying and retry costs.

3. Use a collection built for concurrency. Either a synchronized wrapper, which puts every method behind one lock, or a java.util.concurrent class designed for it.

The wrappers, Collections.synchronizedList, synchronizedMap and synchronizedSet, make each single call safe. Sequences of calls are not, and iteration is not: the documentation requires you to hold the wrapper's own lock while iterating. That is client-side locking:

Vector, Hashtable and Stack are the pre-Java 2 versions of the same idea, with the same compound-action problem; avoid them in new code. Here are the concurrent classes to reach for instead, previewed; module 10 covers them properly:

Worked example: pick the collection for the problem

For each classic problem, the data structure decides most of the solution. Here is the choice and the reason:

  • Bounded blocking queue: an ArrayDeque (or a fixed ring buffer) under one lock with two conditions. O(1) at both ends keeps the critical section tiny.
  • LRU cache: a LinkedHashMap in access order with removeEldestEntry, under one exclusive lock, because every get writes.
  • Scheduler or delay queue: a PriorityQueue ordered by due time, then by a sequence number, under a lock, with a condition the worker waits on until the head is due.
  • Hit counter for the last 300 seconds: two arrays of 300 slots, a timestamp and a count per second, indexed by second % 300, under one lock: O(1) per hit and O(300) per query, with fixed memory. An ArrayDeque of timestamps also works, but its memory grows with traffic.
  • Time-based key-value store: a HashMap from key to a TreeMap from timestamp to value, and floorEntry for lookups:
  • Web crawler, "visit each URL once": a concurrent set, because add is an atomic check-then-act that tells exactly one thread it won:

The pattern behind every choice: pick the structure whose cheap operations are exactly the ones your critical section needs, then put one lock around it, or pick a concurrent structure whose atomic operation is exactly your check-then-act.

Common mistakes

  • Sharing a plain ArrayList or HashMap between threads "because only one thread writes". Readers racing a writer can still see a broken structure; guard reads too, or publish immutable snapshots.
  • ArrayList.remove(0) as a queue, especially under a lock. Use ArrayDeque.
  • Relying on PriorityQueue iteration order, or on the order of equal priorities. Poll to get sorted order, and break ties with a sequence number.
  • A read lock around get on an access-ordered LinkedHashMap. In access order, get is a write.
  • Compound actions on a synchronized wrapper without holding the wrapper's lock, and iterating it without the lock.
  • Vector, Hashtable or Stack in new code. Same compound-action problem, plus every call pays for a lock.
  • Assuming every collection accepts null. ArrayDeque, concurrent queues and ConcurrentHashMap reject it because null means "empty" or "absent". Check the specific contract: CopyOnWriteArrayList does allow null.

In the interview

Collections come up in every round: the structure you choose is part of the answer, and the follow up is almost always "now many threads call it". Interviewers expect you to name the cost of each operation and to know where the thread-safety boundary is.

HashMap is not thread-safe: two concurrent puts can lose an entry or corrupt a bucket during a resize. Collections.synchronizedMap puts one lock around every call, so single calls are safe, but check-then-act and iteration still need the caller to lock the wrapper. ConcurrentHashMap reads without locking, writes by locking one bin or with a CAS into an empty bin, and gives me atomic compute and merge, so it is what I use for shared maps.
For an LRU cache I use a LinkedHashMap in access order with removeEldestEntry, wrapped behind one lock. Every get moves an entry, so it is a write: a read-write lock does not help, and ConcurrentHashMap alone cannot keep the recency order consistent with the map.

Follow ups to expect: "What is the complexity of each operation?" (have the table above in your head), "Why ArrayDeque and not Stack or LinkedList?", "How would you scale the LRU lock?" (stripes by key hash, or a buffered design like Caffeine), and "What does weakly consistent iteration mean?" (it can run during updates without ConcurrentModificationException; it visits entries that remain present throughout traversal, but may or may not reflect later changes, including removals, so the result need not match any single moment of the map).

Senior depth

  • Size under concurrency is a snapshot at best. ConcurrentHashMap.size() may be stale the moment it returns; use mappingCount() for a long estimate, and never base a decision such as "full, so reject" on it without a lock or an atomic counter that you control.
  • Copy-on-write is a read-mostly tool. Changes to CopyOnWriteArrayList generally copy the entire backing array, so it suits listener lists and configuration, not a queue of work. Its iterators retain the array present at creation, but do not freeze mutable elements referenced by that array.
  • Bound every queue between threads. An unbounded LinkedBlockingQueue or ConcurrentLinkedQueue turns a slow consumer into a slow-motion out-of-memory crash. Bounded queues push back on producers instead.
  • Memory layout matters for contention. Linked structures allocate a node per element and scatter them across the heap; array-based ones are compact. Under a lock, fewer cache misses mean shorter critical sections.

Key takeaways

  • Defaults: ArrayList for lists, ArrayDeque for queues and stacks, HashMap for maps, TreeMap when you need order or floor and ceiling, PriorityQueue for "next due".
  • Know each operation's cost; under a lock, every O(n) step becomes everyone's wait.
  • LinkedHashMap in access order with removeEldestEntry is an LRU cache; its get is a write, so it needs an exclusive lock.
  • None of the everyday java.util collections is thread-safe; concurrent writes can corrupt them, not just lose data.
  • Share safely by confinement, by your own lock, or with a concurrent class; synchronized wrappers still need the caller's lock for sequences and iteration.

Why. After the three puts the order is a, b, c. get("a") moves a to the end: b, c, a. put("d") appends d, the map has 4 entries, and removeEldestEntry evicts the eldest, b. In insertion order (no access order), a would have been evicted instead, giving [b, c, d].
A teammate protects an LRU cache built on LinkedHashMap(16, 0.75f, true) with a ReentrantReadWriteLock: get under the read lock, put under the write lock. What is wrong?
Why. The JDK documentation states that in an access-ordered LinkedHashMap a get is a structural modification. A read lock lets many gets run at once, so they relink nodes concurrently. Use one exclusive lock. (Upgrading a ReentrantReadWriteLock from read to write is not even supported: it deadlocks.)

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Implement a thread-safe LRU cache with V get(K key) and void put(K key, V value) and a fixed capacity, using LinkedHashMap. Then say in two sentences why you chose that lock.
Model answer

One exclusive lock, because in access order a successful get can move an entry, so reads can be writes, and the hash table and the recency list form a single invariant that must change together. Using a read lock for get allows concurrent reordering, and a ConcurrentHashMap alone does not protect a separate recency list; if the single lock becomes hot, I would stripe the cache by key hash or move to a buffered design like Caffeine.

Explain
Databricks style: why is HashMap not thread-safe, and how do Hashtable, Collections.synchronizedMap and ConcurrentHashMap differ?
Model answer

HashMap has no synchronization at all. A put reads the bucket, links a node and updates the size, and sometimes resizes the whole table; two threads doing that at once can overwrite each other's nodes, lose entries, leave the size wrong, or, during a resize, corrupt buckets (in Java 7 and earlier a concurrent resize could even create a cycle that made a later get spin forever). Without a happens-before edge, a reader may also see a half-built structure or stale values.

Hashtable and Collections.synchronizedMap both put one lock around every method. Each call is safe, but everything is serialized on that one lock, and compound actions such as check-then-put, or iterating, still need the caller to hold the same lock. ConcurrentHashMap is designed for concurrency: reads take no lock; a write into an empty bin is a single CAS; other writes lock only the one bin they touch, so writers to different bins run in parallel; and a resize is done cooperatively by the threads that run into it. It offers atomic compound operations, putIfAbsent, computeIfAbsent, compute and merge, which are what make check-then-act and read-modify-write safe on a shared map. It rejects null keys and values so that a null from get always means absent, and its iterators are weakly consistent: they never throw ConcurrentModificationException but may or may not show concurrent updates.

Design
Design the data structures for a thread-safe hit counter: hit(timestampSeconds) and getHits(timestampSeconds) returning the hits in the last 300 seconds, with many threads calling hit. Assume nonnegative timestamps that are nondecreasing in the order operations execute under the lock. Give the complexity of each operation and say where you would lock.
Model answer

I would use two arrays of 300 slots: times[i], the second that slot currently represents, and counts[i], the hits in that second, with i = timestamp % 300, guarded by one lock. hit(t): under the lock, if times[i] != t the slot holds an older second, so reset it to t and count 1; otherwise add 1. That is O(1). getHits(t): under the lock, sum counts[i] for every slot with 0 <= t - times[i] && t - times[i] < 300. That is O(300), a constant, and memory is fixed no matter how high the traffic. The timestamp assumption matters: a delayed older hit must not overwrite a newer second in the same slot. A service can assign monotonic elapsed-time timestamps inside the lock; accepting arbitrary event timestamps needs a separate lateness policy.

The lock is held for a few instructions per hit, so it scales well for moderate traffic. If hit becomes a hot spot, I could stripe: give each slot its own lock, or keep one AtomicLong per slot that packs the second and the count into a single 64-bit value, so that a compare-and-set loop can reset an old second and count the hit in one atomic step (two separate atomics for time and count could not), accepting that getHits then reads a slightly moving snapshot. The alternative, an ArrayDeque of timestamps under a lock with expired entries polled from the front, is simpler but its memory and getHits cost grow with the number of hits in the window.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Our LRU cache uses an access-ordered LinkedHashMap. Reads take a read lock and writes take a write lock, but the cache still breaks. What would you change?"
What a strong answer covers
  • An access-order get can relink an entry, so it needs exclusive protection
  • Two shared-lock readers can concurrently change the same recency links
  • Use one exclusive lock for get, put, eviction and other access to the private map
  • Trace capacity three: a, b, c; get a; insert d; evict b
  • ConcurrentHashMap alone cannot coordinate the map and a separate recency list
  • Striping can reduce contention but gives up exact global LRU order
How a senior would say it
I would put gets under the same exclusive lock as puts, because an access-order get can change the recency list. Calling it a read does not make its implementation read-only. Two threads holding the shared read lock can both unlink and append entries, changing the same links concurrently. I would keep the map private and guard lookup, insertion, eviction, and any inspection of its state with one exclusive lock. At capacity three, inserting a, b, and c gives that recency order. Getting a changes it to b, c, a. Inserting d then evicts b, leaving c, a, d. That entire bookkeeping needs to remain consistent with the stored entries. Replacing the hash table with ConcurrentHashMap would protect its own operations, but would not coordinate a separate recency list or the capacity rule. The simple lock is my starting point because the operations are short and easy to reason about. If measurement shows contention, I could partition the cache into independent stripes, while explicitly accepting that eviction would no longer follow one exact global LRU order.

Likely follow up: How would you return the keys for inspection without exposing a mutable view of the cache?

Out loudabout 65 s
"A synchronized list still contains duplicate user IDs. The code checks contains and then calls add. Show me how that happens and choose a fix."
What a strong answer covers
  • The wrapper synchronizes individual calls, not the entire check and add sequence
  • Both threads can complete contains and observe absence before either adds
  • Lock the wrapper across both calls if retaining the list
  • Use a concurrent set and its add result when uniqueness is the actual requirement
  • Iteration of the synchronized list also requires its wrapper lock for the entire traversal
How a senior would say it
The list is safe at the method level, but the decision spans two methods. Thread A checks contains and sees the ID is absent, then releases the wrapper's lock. Thread B performs the same check and also sees absence. Both then add the ID, so we have a valid list containing a duplicate. If we keep the list, I would synchronize on the wrapper around both calls. That is the same lock its methods use, and the monitor is reentrant. If the requirement is simply unique membership, I would choose the set returned by ConcurrentHashMap.newKeySet instead. Its add operation tells exactly one caller that it inserted a previously absent ID. That also avoids a linear search through a list. I would separately review iteration: a synchronized list still requires its wrapper lock for the whole traversal. Safe individual calls do not automatically make a larger operation atomic.

Likely follow up: What if the caller that wins the set insertion then fails to submit the corresponding work?

Out loudabout 80 s
"Choose the collection for a bounded FIFO work queue. Why not remove from the front of an ArrayList, and what changes if jobs have priorities?"
What a strong answer covers
  • Choose a bounded BlockingQueue for normal use or ArrayDeque under a lock when implementing it
  • ArrayList.remove(0) shifts remaining entries in O(n) while holding the queue lock
  • ArrayDeque supports efficient end operations but its initial capacity is not a hard bound
  • Check capacity and mutate under one lock, waiting in predicate loops when implementing blocking
  • Use PriorityQueue for priority order; poll is ordered but iteration is not
  • Break priority ties explicitly and retain an admission limit for backpressure
How a senior would say it
For production use I would start with a bounded blocking queue, such as ArrayBlockingQueue. If the interview asks me to build one, I would use an ArrayDeque under a lock. Removing index zero from an array list shifts the remaining entries, so each dequeue takes linear work while other threads wait. A deque removes from the front in constant time and appends in amortized constant time. Its constructor capacity is only an initial allocation, though; it does not enforce a bound. I must check the limit and insert under the same lock, with producers waiting while full and consumers waiting while empty. Both waits recheck their predicates after waking. If jobs have priorities, I would replace the deque with a PriorityQueue. Offering and polling then cost logarithmic time. Polling chooses the next priority; iterating the heap does not give sorted order. I would include a sequence number if equal priorities must preserve admission order. Priority ordering also does not impose a capacity limit, so I would keep explicit backpressure rather than allowing slow consumers to grow memory without bound.

Likely follow up: How would a newly submitted earlier deadline wake a scheduler that is waiting for the current head?
