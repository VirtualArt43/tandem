Ordering by ownership: partitions and single writers

Route each key to one serial owner for ordered updates, then handle hot keys, bounded queues, retries and safe ownership changes.

Asked atUberMetaFlipkartSwiggy
Before this:Single writer, actors and message passingIdempotency, retries and exactly-once effectsDistributed locks, leases and fencing tokens

The cheapest lock is the one nobody takes. Give every piece of state exactly one serial owner and send its reads and changes through that owner: state access is serialized in queue order. This is how Kafka, sharded databases and actor systems scale writes, and it is the in-process single writer, scaled to a cluster.

In plain words

A bank branch with four tellers could let any teller serve any customer, and then every teller would need to phone the others before touching an account ("is anyone else updating account 7?"). Or it could assign accounts by number: accounts ending in 0 to 2 go to teller one, 3 to 4 to teller two, and so on. Now two requests for the same account always reach the same teller, who handles them one after another in the order they arrived. No phone calls, no conflicts.

The catch shows up on the day a celebrity opens an account with teller two and half the city queues to deposit money in it. Teller two is swamped while the others are idle. Ownership localizes coordination; it does not remove load.

One writer per key

The pattern has three parts:

  1. Partition the state by key. Every key (an account, an order, a user) belongs to exactly one partition, computed by a function everyone agrees on, typically hash(key) mod N. This is sharding.
  2. Give each partition a single owner: one serial worker or actor, or one primary that internally serializes conflicting writes. A process or primary can have many threads, so naming one owner alone does not remove its internal synchronization.
  3. Route every change for a key to its owner, through a queue the owner drains in order.

What you get inside a serial worker: its state needs no locks when all reads and writes are confined to that worker. Changes for one key are applied in exactly the order they reached the owner's queue. Owners of different partitions run fully in parallel. And the owner can batch: twenty queued updates to one account can become one write. For the confined in-process design, the queue is the shared handoff point, which is a problem you already solved in producer and consumer.

What it costs: one key can never go faster than one owner. An operation that spans keys in two partitions (a transfer between accounts owned by different lanes) needs coordination again, usually by splitting it into steps with idempotent messages. And when the number of owners changes, keys move.

A keyed executor

Inside one process the pattern is a keyed executor: N single-threaded lanes, and a router that sends each task to the lane chosen by its key. The displayed output is from Java. C++ uses a different random generator and distribution, so its deposit total differs; each program asserts that its applied total equals its own generated total and no account event is out of order.

Look at where synchronization still lives: inside each lane's queue (the executor's internal queue in Java, the mutex and condition variable in Lane in C++), and at the end, where Future.get or join makes the lanes' writes visible to the main thread. The maps remain confined; a read must be submitted to the lane or use a safely published immutable snapshot. If the router posted from many threads, per-key order would be the order in which posts reached the lane's queue, which is why systems that need a strict order per key also have one sequencer per key, with consumers checking for gaps and duplicates. The language hash functions here are for one process; cross-language routing needs an agreed hash of canonical key bytes and a versioned routing table.

The demo has a limited lifecycle contract. It uses finite, non-throwing tasks, one submitting router, and queues without capacity limits. In production bound each queue and reject or backpressure before memory grows without limit; never use caller-runs rejection for owned state, because it executes on the wrong thread. Report task failures through futures, keep captured objects alive until draining finishes, and invoke shutdown from an external thread after producers stop. A task must not synchronously wait for another task on its own lane, or it deadlocks.

Kafka partitions and consumer groups

Kafka supplies the partitioned log for this pattern; the application must still serialize processing. A topic is split into partitions; each partition is an append-only log with its own offsets, and Kafka guarantees order only within a partition.

PieceWhat it doesOwnership consequence
Producer partitionerThe default Java producer hashes serialized key bytes when no explicit partition is supplied and keys are not ignoredSame bytes and partition count give the same partition; append order is not a global business sequence
PartitionAn ordered logThe unit of ordering and of parallelism
consumer groupIn a conventional consumer group, assigns each partition to at most one member at a timeOne owner per partition; with more consumers than partitions, the extras sit idle
Committed offsetWhere the group resumes after a failure or a reassignmentThe commit is the next offset to read; already applied records at or beyond it may be replayed

So the number of partitions caps the number of active group members, and keying by account id gives each account a single owner. Records without a key are spread across partitions and lose any ordering between them.

A consumer that processes its records on one thread, in poll order, keeps per-key order. The classic mistake is to hand records to a thread pool for speed:

If one consumer needs parallel processing across independent keys within its assigned partitions, route inside the consumer by key into lanes (the keyed executor above), and disable automatic commits and track the completed prefix per partition. A committed offset N means resume at N, so every delivered record below N must be finished; never advance past a gap. Keep poll, pause/resume and commit calls on the consumer thread because KafkaConsumer is not thread-safe. Bound lane queues, pause overloaded partitions, and keep polling for group membership.

Ownership moves, and the old owner may not know. A crash or failure to poll within max.poll.interval.ms can trigger reassignment. A slow old worker may still finish its batch. Group membership fences stale offset commits (commitSync can throw CommitFailedException), but does not fence an external database write. On revocation, stop dispatching, drain within a bounded time or abandon and fence unfinished work, then commit only the completed prefix. Side effects need idempotency and storage-enforced ownership epochs. These are separate from the offset commit protocol described in the Kafka consumer API.

Producer retries need ordering too. With enable.idempotence=true, acks=all, retries enabled and at most five in-flight requests per connection, one producer preserves order within a partition across retries. This does not deduplicate an application resubmitting a business event or order concurrent producers; see the producer configuration contract.

Actor sharding and single primaries

An actor is state plus a mailbox, executing one turn at a time (see single writer and actors). Cluster sharding routes an entity id to its active owner. Configure and check asynchronous reentrancy: one thread at a time does not imply an entire operation spanning an asynchronous wait is indivisible. Failover also needs storage-enforced versions or ownership epochs; a routing decision alone cannot stop a paused old process from writing.

Single-primary databases use a related pattern at the storage layer: each shard has one primary that accepts writes for its keys, and replicas follow its log. Whether it is a thread, a consumer or a primary, the rule is the same: one writer per key, and every handoff of ownership fenced by a number that only grows.

Hot partitions

Ownership caps one key at one owner's speed. Real traffic is skewed: a viral post, a celebrity account, a flash sale item, a merchant that receives a third of all payments. That key's partition becomes a hot partition: its owner is at 100 percent and its queue grows, while other owners idle. You see it as lag on one partition, not on the topic.

More partitions may isolate neighbours, but cannot increase one key's serial processing capacity: one key always maps to one partition. The fixes change the key or the work:

FixHowWhat you give up
Split the keyWrite to post-123#0 to post-123#7 chosen at random; readers sum the eightOne total order for that key; safe for independent commutative updates such as counts, provided no cross-shard limit must be enforced
Batch at the ownerApply a thousand queued increments as one writeA little latency
Pre-aggregate upstreamEach producer sums locally and sends one delta per secondFreshness, and the deltas need idempotency
Isolate the keyGive the hot key its own partition, owner or clusterOperational special cases
Admit lessA bounded queue, waiting room or admission limit in front of that keySome users wait or are turned away

The in-process twin is lock striping and LongAdder from counters at scale: when one cache line or one lock is hot, split it into several and combine on read.

Re-sharding

With hash(key) mod N, changing N moves almost every key. Going from 4 owners to 5, a key stays put only if h mod 4 equals h mod 5, which for evenly spread hashes happens for 4 of every 20 values: 80 percent of keys move, each with its state and in-flight work.

Two ways to move less:

  • consistent hashing: place owners and keys on a ring; a key belongs to the next owner clockwise. With balanced placement, usually many virtual nodes, adding a fifth owner takes about a fifth of the keys. A ring with one random point per owner can be badly imbalanced.
  • Many fixed slots: hash keys into a large fixed number of slots, and map slots to owners. Redis Cluster uses 16,384 hash slots; moving one slot moves only its keys. Kafka effectively does this too: you choose the partition count up front, and consumers come and go without changing it.

Kafka can increase a topic's partition count but does not support decreasing it in place, and adding them changes the key-to-partition mapping for new records: a key's old records stay in the old partition while its new ones go to a different one, so a consumer can see them out of order across the change. Size partition counts for future growth, or migrate to a new topic with a planned cutover.

Moving ownership safely is a small protocol: the old owner stops accepting work for the moving range, drains accepted work and persists a final checkpoint. The new owner restores that checkpoint and any remaining log, installs a higher epoch that the storage checks atomically with each write, then routing switches. If the old owner is unreachable, fence it first and recover from durable state; do not wait for it to drain. Skip a step and you get two writers for a while, which is the double leader from the previous lesson.

Worked example: payment events in order per account

Ten million accounts, 50,000 payment events a second at peak, events for an account must apply in order, and a handful of merchant accounts receive 30 percent of the traffic.

Ownership. Key every event by account id into a topic with, say, 256 partitions; a balanced consumer group of 64 instances owns 4 partitions each. One serial worker per partition preserves append order. Local state is restored from a durable checkpoint and replayed log on reassignment.

Correctness on handoff. Apply each state change and its source partition/offset or entity sequence atomically in durable storage, checking the current ownership epoch in the same transaction. With ordered processing and no gaps, a stored high-water mark can reject replay; offsets from different partitions are not comparable. Commit the Kafka position only after that durable update. External effects need a durable outbox and an idempotency key.

The hot merchants. 30 percent of 50,000 is 15,000 events a second, and a merchant's events all land in one partition. If the requirement is only an eventual exact total of independent merchant credits, their credits are written to a separate topic keyed by merchant#shard with 16 shards, and a small job sums the shards. Customer accounts keep strict ordering. A spendable merchant balance or a cross-account transfer still needs coordination; summing live shards is not an atomic snapshot.

Common mistakes

  • Adding partitions to fix one hot key. The key still maps to one partition. Split the key or batch.
  • A thread pool inside a consumer. It breaks per-key order and makes offset commits unsafe. Route by key into lanes and commit only finished offsets.
  • Committing offsets before processing. A crash then skips the records: at-most-once by accident.
  • Assuming the old owner stopped. After a rebalance or failover the previous owner may still be finishing work. Make processing idempotent and fence writes.
  • hash mod N with a changing N. Most keys move on every resize. Use consistent hashing or fixed slots.
  • Records without keys where order matters. Unkeyed records are spread over partitions, and their relative order is lost.

In the interview

Ownership is the senior answer to "how do you avoid all these locks?". It was reported in Uber machine coding rounds ("design a system like Kafka with concurrency support" at SDE2; and, in an older 2021 report, a Kafka-like broker at L5a where publishers and subscribers must not block one another), and one Uber SDE2 candidate answered a thread-safe leaderboard follow up with a keyed executor. Flipkart SDE3 machine coding asked for in-memory streaming with partitions, ordering within partitions and thread safety; Swiggy asked an SDE3 how to keep order across Kafka partitions and an SDE4 for a Kafka-like queue that delivers exactly once per customer. In a Meta design round on a single-machine memcache, the interviewer praised sharding the table into roughly one part per core to lock more efficiently: ownership and striping inside one box.

Instead of locking shared state, I would give each key a single owner: partition by account id, route every update for an account to its partition's consumer, and let that consumer apply them in order with no locks. That gives queue order per key, while partitions run in parallel. Business sequence numbers and failures still need an explicit protocol.
The cost is skew: one key can never go faster than one owner. For hot keys whose updates commute, like counters, I would split the key into shards and sum on read; for keys that need strict order, I would batch at the owner or isolate them.

Follow ups to expect: "What happens during a rebalance?" (old owner may still be processing: idempotent consumers, fenced commits), "How many partitions?" (enough for peak parallelism plus growth, since you cannot remove them and adding them reshuffles keys), "What if one consumer is slow?" (its partitions lag; scale by partitions, not by threads inside it, or use key-ordered lanes), and "How do you handle a transfer between two accounts in different partitions?" (split into a debit and a credit step with idempotent messages, or a saga).

Senior depth

Ownership turns a concurrency problem into a queueing problem. Each owner is a single server queue, so its latency follows the utilization curve from queueing math: under the illustrative M/M/1 assumptions (Poisson arrivals, exponential service times), average queue wait is one service time at 50 percent utilization and nine at 90 percent. Other arrival and service distributions change the numbers. Size owners for the hottest partition, not the average.

Cross-key operations are where the design is tested. A transfer touching two owners cannot be one local transaction. Options: co-locate the accounts when feasible; run a saga with an idempotent debit, an idempotent credit and a compensating step; or keep that data in a store that supports multi-key transactions. Choosing the lower account id as a coordinator does not transfer ownership of the other account: its ordinary updates still race unless they use the same protocol. A saga gives eventual completion or compensation, not an atomic view of both balances.

A poison record needs a policy. Retry transient failures with bounded backoff. Quarantine a permanently failing record only if the business rule permits skipping it, persisting that decision before advancing the commit; otherwise pause the key or partition for repair. Silently skipping a debit or an ordering gap corrupts the state machine.

Ordering is per producer, too. A partition orders records in the order they were appended. Two producers writing the same key can still interleave in a surprising order. If order matters per key, have one producer per key (often the service that owns that entity upstream) or carry a sequence number and let the consumer reorder or reject.

Key takeaways

  • One writer per key: partition by key, give each partition one owner, route every change to it. Confined state needs no locks; ordering is the order accepted by its serial queue.
  • Kafka: order only within a partition, one consumer per partition per group, active group members capped by partition count; application lanes may parallelize independent keys.
  • Ownership moves on rebalance or failover, and the old owner may still be working: idempotent processing and fencing.
  • A hot key cannot be fixed by more partitions; split commutative keys, batch, pre-aggregate or isolate.
  • Re-shard with fixed slots or consistent hashing, not hash mod N with a changing N.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A conventional consumer group is stably and evenly assigned one topic with 6 nonempty partitions. All 8 members subscribe to it. How many receive records?
Why. Within a group, each partition is owned by exactly one consumer at a time, so at most 6 consumers can have work. Extra consumers are standbys. To get more parallelism you need more partitions.
A consumer polls a batch, hands each record to an 8-thread pool, and commits the batch's offsets immediately. Which problems does this create? Select the best answer.
Why. Two pool threads can run one key's records in either order, so the ownership that gave per-key order is gone. Committing before processing is at-most-once: after a crash the group resumes past records that never ran. Route by key into single-threaded lanes and commit only offsets whose records are all finished.
One celebrity account alone exceeds a dedicated owner's processing capacity. With the same per-owner capacity, does doubling partitions remove this bottleneck?
Why. The partitioner maps one key to one partition, whatever the count. Splitting commutative updates, batching and pre-aggregation can increase effective capacity. Isolation helps only when neighbouring keys caused the overload, which this question rules out. Adding partitions also remaps other keys, and can temporarily break cross-cutover order; isolation of neighbouring keys does not solve the stated single-key bottleneck.
Uniformly spread nonnegative hashes are assigned with hash(key) mod N to numbered owners. N grows from 4 to 5, preserving existing owner numbers. Roughly what fraction of keys move to a different owner?
Why. A key stays only when h mod 4 equals h mod 5. Looking at h mod 20, that holds for the values 0, 1, 2 and 3: 4 of 20, so 80 percent move. Consistent hashing or fixed slots would move about a fifth.
After a rebalance, partition 3 moves from consumer A to consumer B. A was not dead, only slow, and was half way through a batch. What can happen?
Why. B resumes from the last committed offset, and A may still finish its in-flight records. Kafka rejects A's late offset commit (an old generation), but it cannot undo A's side effects. The consumer must be idempotent.
In the keyed executor, each lane's account map is a plain HashMap or std::unordered_map with no lock. Why is that safe?
Why. The state is confined to one thread. The queue is the only shared object, and handing a task through it gives a happens-before edge from the router to the lane. Java computes results on the lane and returns them through Future.get; C++ reads the maps only after every lane is joined. Both supply the required visibility edge.
Two unrelated producer threads submit tasks for the same key to a single serial lane. One appends A, the other appends B to a lane-owned string, initially empty. After both tasks finish and the lane is joined, what can the string contain?
Why. Both appends run completely on one serial lane, so neither is lost and the string has no concurrent access. The synchronized join permits the final read. There is no ordering edge between the producers, so naming A first does not force it to enqueue first; both complete orders are possible.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
Design processing for payment events that must apply in order per account: 10 million accounts, 50,000 events a second at peak, and a few merchant accounts receive 30 percent of the traffic. Cover ownership, failure and the hot accounts.
Model answer

Ownership. Key events by account id into a topic with enough partitions for peak parallelism and growth (for example 256), consumed by a group of instances that each own several partitions. Each consumer applies its accounts' events in partition order, confining local state to its worker and serializing durable updates at the owning store.

Failure. Rebalances and crashes mean a partition can be reprocessed from the last committed offset, and a slow old owner may finish its batch. So state, its source position and the deduplication decision commit atomically under a storage-checked ownership epoch. Rebuild local state from a durable checkpoint and log. Process without sequence gaps, and commit only the next offset after the completed prefix; external side effects use idempotency keys derived from the event id.

Hot merchants. The hot merchants collectively receive 15,000 events a second; measure whether any one exceeds its owner's capacity. Merchant credits commute (the order of incoming payments does not change the total), so I would route them to a separate topic keyed by merchant plus a shard number (for example 16 shards), and keep an eventually consistent total of incoming credits as the sum of its shards. This is not sufficient to authorize withdrawals against one balance. Customer accounts, whose debits need strict order to enforce balances, stay on the single-owner path. I would watch per-partition lag to catch new hot keys.

Write code
Write a keyed executor: execute(key, task) runs tasks with the same key one at a time, in submission order, while tasks with different keys may run in parallel; shutdown() finishes queued tasks and stops.
Model answer

Keys must keep a stable hash while work is queued. Same key, same lane, and a lane is one thread draining a FIFO queue, so per-key order holds; different lanes run in parallel. The price is head-of-line blocking: a slow task delays every key that shares its lane. More lanes can reduce collisions but each lane here costs a thread. A per-key serial queue scheduled onto a bounded shared pool separates the number of keys from the thread count. As in the demo, C++ tasks here must not throw and shutdown is called by one external thread after producers stop; a production API returns futures carrying task exceptions. Neither language can guarantee a finite drain if a task never finishes. Java interruption is propagated, and a caller must still arrange to await termination.

Numbers
A cache cluster uses hash(key) mod N over 10 nodes holding 500 million keys. You add 1 node. Roughly how many keys move, and how many would move with consistent hashing?
Model answer

With mod N, a key stays only if h mod 10 equals h mod 11. Over h mod 110, that holds for the values 0 to 9: 10 of 110, about 9 percent. So about 91 percent move: roughly 455 million keys, which for a cache means a near-total miss storm. With consistent hashing (or many fixed slots rebalanced evenly), the new node takes about 1/11 of the keys: roughly 45 million, about 9 percent, with balanced placement; the keys that stay on their existing nodes remain warm.

"Why would you route account updates through one owner, and what problems does that leave you with?"
What a strong answer covers

  • Queue order is not a business order across concurrent producers

How a senior would say it
I would use one serial owner per account to make its state transitions easy to reason about. Every read and write goes through that owner's queue, so the account map needs no lock. The queue still needs synchronization, and a result or snapshot needs safe publication. The order I get is queue arrival order. If several producers create business events, I also need a sequence and a rule for gaps and duplicates. The tradeoff is capacity. One hot account can overwhelm its owner even while other owners are idle. I would bound the queue, measure lag and batch work where possible. Independent credits can sometimes be sharded and summed, but I cannot authorize a withdrawal against an inconsistent sum. Adding partitions alone does not make one account execute in parallel. When ownership moves, the new owner restores durable state and the storage rejects writes carrying the old epoch. Retries also need deduplication committed with the state change. Finally, a transfer between different owners still needs a transaction or an explicit saga. Choosing one account as coordinator does not let it bypass the other account's ownership. This trades shared-state locking for an explicit queue, capacity limit and recovery protocol.

Likely follow up: What happens if a task synchronously waits for another task queued on its own owner?

How a senior would say it
The commit skips unfinished work. Offset 43 means restart from 43, so after the crash record 41 will not be delivered again through the normal group resume. I can commit 41 here, because 40 has finished, but I must stop at that gap even though 42 completed. After 41 finishes, the completed prefix can advance through 42 and the next position is 43. I would track completion separately for each partition and route same-key records through serial lanes. If 41 and 42 share a key, allowing 42 to apply first is already an ordering bug. The consumer thread owns polling and commits, and pauses overloaded partitions while bounded worker queues drain. State changes and deduplication metadata must be durable together before advancing the commit, since a crash before committing can replay completed work. On reassignment I stop dispatching old work and either drain it within a deadline or abandon it safely. Kafka rejects stale group commits, but a database must separately fence the old worker's writes. External effects still need an idempotency key.

Likely follow up: How would you recover if a permanently failing record blocks the completed prefix?
