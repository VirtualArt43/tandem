Classes, interfaces and inheritance

Classes, constructors, interfaces with default methods, abstract classes, composition over inheritance, access modifiers and nested classes, as concurrent code uses them.

Before this:Objects, references and the heap

A thread-safe class is a class first. Its fields are private, its constructor finishes before anyone sees it, its lock is something nobody outside can touch, and no subclass or default method can sneak around that lock. This lesson covers exactly the class machinery that concurrent code leans on.

In plain words

Think of a bank branch. The vault (the fields) sits behind the counter, and customers can only use the windows (the public methods). The branch's rules, such as "the ledger always matches the cash in the vault", hold because every change goes through a teller who follows the procedure and locks the vault door while working (the lock).

An interface is the sign above a window, "Deposits here": any branch can put up that sign and serve deposits its own way. Inheritance is opening a new branch by copying an old branch's floor plan and changing a few rooms; if the old plan quietly relied on "always lock the vault door first" and the new room skips it, the rule breaks. Composition is hiring the old branch as a back office behind your own counter, with your own lock on the door. A class can only keep its promises if every path to its state goes through its own counter.

Why this matters for concurrency

  • Encapsulation is what makes locking enforceable. If a field is private and every access goes through methods that take the lock, you can prove the class is safe. A public or protected mutable field makes that proof impossible.
  • An object is not ready until its constructor returns. Starting a thread or registering a listener inside a constructor lets other threads see it half built.
  • Concurrency APIs are interfaces: Runnable, Callable, Executor, Lock, BlockingQueue, Future. You implement them and program against them.
  • Default methods and subclasses do not automatically use your lock. Check the default method's atomicity contract, and remember that an overriding method does not inherit the synchronized modifier.
  • synchronized methods lock this, which outsiders can lock too. A private lock object cannot be reached from outside.
  • Inner classes and anonymous classes change what this means, which changes which object a synchronized (this) block locks.

A class is state plus the methods that guard it

A class bundles fields (state) with methods (behavior). For thread safety, the important idea is the invariant: a fact about the fields that must hold whenever no method is in the middle of running. For a bank account it might be "the balance is never negative". Encapsulation means only the class's own methods touch its fields, so only they can break the invariant, so only they need to take the lock.

Read it the way a reviewer would. Every mutable field is private and has a "guarded by" comment. Every method that touches balance takes the same lock, including the read. The check then act in withdraw happens inside one critical section. The class is final, so no subclass can add an unsynchronized method later. That is what a thread-safe class looks like in an interview.

Constructors: when does an object exist?

When you write new BankAccount("a1", 100), the JVM allocates the object with every field at its default value (0, false, null), then runs the constructor chain: the superclass constructor first (super(...), implicit if you do not write it), then this class's field initializers and initializer blocks in source order, then the rest of the constructor body. this(...) calls another constructor of the same class. Only when new returns is the object complete.

Until then, nobody else should be able to see it. Leaking this from a constructor, called this escape, hands other threads a half-built object:

A method reference like this::onReading captures this, so it leaks the object just as surely as hub.subscribe(this) would. Even moving the leak to the last line of the constructor is not enough in principle: the guarantee that other threads see final fields correctly (the final field semantics, next lesson) only applies once the constructor has finished, and only if this did not escape. javac 21 can flag some of these with -Xlint:this-escape.

The fix is a static factory: construct first, publish second.

The same goes for threads: give the class a start() method, or have the factory start the thread after construction. Also avoid calling overridable methods from a constructor: the subclass version runs before the subclass's own fields are initialized.

Interfaces: the shape of every concurrency API

An interface is a contract: a set of methods any class can promise to provide. Almost all of java.util.concurrent is defined this way, which is why you write BlockingQueue<Job> q = new ArrayBlockingQueue<>(100); and can later swap in LinkedBlockingQueue without touching the code that uses q.

Default methods do not automatically acquire your lock

Since Java 8 an interface can carry method bodies: a default method (and static methods, and since Java 9 private helper methods). A default method cannot directly access the implementing class's private fields or lock. Without an additional synchronization protocol, a default method built from several atomic calls is not atomic as a whole.

The JDK itself is careful about this. Map.computeIfAbsent is a default method that does a get, then a put, and its documentation says it makes no atomicity guarantees and that any implementation offering atomicity must override it. ConcurrentHashMap does override it, and documents that the whole call is atomic. Here is the same trap in code you might write:

With only the default, two threads each asking for 3 of 4 permits can each take 2, both fail, and leave 4 permits consumed and nobody served. The override checks and takes all the permits in one critical section. When you implement a JDK interface in a thread-safe class, check its default methods too: forEach, removeIf, replaceAll and computeIfAbsent have no automatic guarantee of holding your lock across the whole operation. A default method can explicitly synchronize or use atomic primitives, so inspect its implementation and contract.

Abstract classes

An abstract class is a partly written class: it can have fields, constructors and finished methods, plus abstract methods that subclasses must fill in. A class can extend only one class but implement many interfaces.

InterfaceAbstract class
Instance fieldsNo (constants only)Yes
ConstructorsNoYes
How many per classImplement as many as you likeExtend exactly one
Method bodiesDefault, static and private methodsAny
Concurrency examplesRunnable, Lock, Executor, BlockingQueueAbstractQueuedSynchronizer, AbstractExecutorService, RecursiveTask

The best-known abstract class in concurrency is AbstractQueuedSynchronizer, the AbstractQueuedSynchronizer. It implements the hard part of a lock, a queue of waiting threads with parking and waking, once. ReentrantLock, Semaphore and CountDownLatch each contain a small internal subclass of it (named Sync) that only says what "acquire" and "release" mean. That is the template method pattern: the abstract class owns the algorithm, subclasses fill in the steps.

Inheritance can break thread safety

Inheritance shares implementation, and with it the obligations a parent class never wrote down. Three ways it goes wrong:

1. synchronized is not inherited. It is not part of a method's signature, so an override is unsynchronized unless it says so:

Declare the override synchronized too, or call super.increment(), which takes the lock. Note also the protected field: any subclass can touch count without the lock.

2. Locking the wrong object from outside. Suppose you want "add if absent" on a list made thread-safe with Collections.synchronizedList. Each method of that wrapper locks the wrapper itself, so to make two calls atomic you must hold that same lock, which is client-side locking. Locking anything else protects nothing:

3. Extending a class you do not own. Subclassing a thread-safe class to add a method depends on the parent's private locking policy, which can change in the next version. Composition is sturdier: keep the object private, add your own lock, and expose only what you choose.

The same reasoning answers an old interview favorite, "extend Thread or implement Runnable?". Implement Runnable (or Callable): the task stays separate from the thread that runs it, you keep your one superclass, and the same task can run on a thread, an executor or a virtual thread.

Access modifiers: who can touch your state

ModifierVisible toUse it for
privateThe class itself and its nested classesAll mutable state, and every lock object
none (package-private)Classes in the same packageHelpers and implementation classes. Tandem's problem classes are package-private.
protectedThe same package and all subclassesRarely state: subclasses can touch it without your lock
publicEveryoneThe API, and only immutable or thread-safe things

Locks deserve the same care as state. A synchronized method locks this, and this is public: any code holding a reference to your object can write synchronized (yourObject) and hold your lock for as long as it likes, stalling every method you have. A private lock object cannot be reached from outside.

In a real system the "hog" is a library that synchronizes on objects it is handed, or a caller doing client-side locking for its own reasons. A private lock prevents that direct interference. It does not rule out deadlock: your own methods can still create a lock cycle by calling external code while holding it. The measured delay is illustrative and depends on scheduling.

Nested, inner, local and anonymous classes

Innerclass Cursor inside a class, no staticYes, reachable as Outer.thisAn iterator over its outer object

An inner class instance can read and change its enclosing object's fields, private ones included. That makes a task written as an inner class a second path into the outer object's state, so the outer object's lock rules apply inside it. When the inner class uses the outer object, it holds a hidden reference to it and keeps it alive as long as the task lives: a long-scheduled inner-class task can pin a large object in memory. (Since Java 18, javac drops that hidden field when it is unused.) Prefer static nested classes unless you really need the outer object.

The most surprising difference is what this means. Inside an anonymous class, this is the anonymous object. Inside a lambda, this is the enclosing object:

So synchronized (this) inside an anonymous Runnable locks that Runnable, not the enclosing object. Separately created tasks lock different objects, and none excludes methods that lock the enclosing instance. If you need the outer object's lock there, write synchronized (Main.this), or better, use the same private lock object by name in every access path.

Worked example: make this class safe, then hard to break

A teammate wrote a temperature log that a sensor hub calls from its own threads:

Go through it field by field and method by method:

  1. readings is public: any thread can add to or iterate it without the lock. Make it private.
  2. max is protected: subclasses can read or write it without the lock. Make it private.
  3. The constructor leaks this through this::record, so record can run before construction ends. Use a private constructor and a factory.
  4. max() reads without the lock, so it may return a stale value (and because max is a non-volatile double, the language even allows a torn read), and nothing ties it to readings. Lock it.
  5. The class is not final, so a subclass can override record without synchronized. Make it final.
  6. The methods lock this, which the sensor hub or anyone else can also lock. Use a private lock.

None of the fixes needed clever concurrency. They needed ordinary class design applied strictly: private state, one private lock, no leaks, no extension points you did not intend.

Common mistakes

  • Public or protected mutable fields on a class that claims to be thread-safe. Nobody can enforce a lock on a field anyone can touch.
  • Starting a thread or registering a listener in a constructor. Construct first, then publish, with a factory method or a separate start().
  • Calling an overridable method from a constructor. The subclass's version runs before the subclass's fields are set.
  • Assuming a default method runs under your lock. It calls your methods one at a time; override it if it must be atomic.
  • Overriding a synchronized method without synchronized. The keyword is not inherited.
  • Client-side locking on the wrong object. To combine calls on a synchronized wrapper, lock the wrapper itself, or better, use composition with your own lock.
  • synchronized (this) inside an anonymous class, believing it locks the outer object. It locks the anonymous object.

In the interview

These ideas come up as quick theory ("interface versus abstract class?", "Runnable versus extending Thread?") and, more importantly, in how you write every thread-safe class during a coding round. Interviewers read your class top to bottom and notice a public field, a missing lock on a getter or a thread started in a constructor long before they notice clever code.

I keep all mutable state private and guarded by one private final lock, so no outside code can take my lock or touch my fields. The class is final, the constructor does not let this escape, and anything I hand out is a copy or immutable.
I implement Runnable or Callable rather than extending Thread: the task stays separate from how it is run, so it can go to a thread, a pool or a virtual thread unchanged.

Follow ups to expect: "Is synchronized inherited?" (no), "Why not just use synchronized methods?" (they lock this, which is public), "Is Map.computeIfAbsent atomic?" (only where the implementation overrides it and says so, as ConcurrentHashMap does), "What does this refer to inside a lambda?" (the enclosing object), and "Can one thread run a static synchronized method while another runs an instance synchronized method of the same class?" (yes: the static one locks the Class object, the instance one locks this, so they do not exclude each other, and static state touched by both is unprotected).

Senior depth

  • Document the synchronization policy. Write which lock guards which field, and whether the class is thread-safe, immutable or not thread-safe. Annotation libraries provide @GuardedBy, and Error Prone can check it at compile time.
  • Design for inheritance or forbid it. A thread-safe class that allows subclassing must document which lock subclasses have to use, which ties you to that lock forever. Making it final keeps the policy private and changeable. A sealed class or interface (Java 17) is the middle ground: only the subclasses named in its permits clause may extend it, so you can review every one of them.
  • Template methods hold locks around unknown code. If an abstract class calls an abstract method while holding its lock, a subclass can do I/O or take other locks inside your critical section. Call such hooks outside the lock (an open call) where you can.
  • Every Java object has a monitor. That is why any object can be locked, why wait, notify and notifyAll are final methods on Object (you call them on the object whose monitor you hold), and why a private lock object is just new Object().

Key takeaways

  • Thread safety rests on encapsulation: private state, touched only by methods that take the lock.
  • An object is ready only when its constructor returns; never let this escape before that.
  • Default methods and overriding methods do not inherit your locking; override or forbid them.
  • Prefer composition with your own private lock over extending a class you do not control.
  • Use a private final lock object instead of locking this.
  • Inside a lambda this is the enclosing object; inside an anonymous class it is the anonymous object.

Quick check

Answer each question, then read why. Your score is saved for your module test.

What is wrong with this subclass when several threads call increment()?
Why. synchronized is not part of the method signature, so the override runs without the monitor. Make the override synchronized, call super.increment() for the update, make the parent method final, or keep count private so subclasses cannot touch it at all.
What does this print?
Why. In an anonymous class, this is the anonymous object, whose class javac names Main$1. A lambda does not create a new scope for this, so it means the enclosing Main object. That is why synchronized (this) means different things in the two forms.
interface Counter { void increment(); default void add(int n) { for (int i = 0; i < n; i += 1) increment(); } } is implemented by a class whose increment() is synchronized. Is add(1000) atomic?
Why. A default method only knows the interface's methods; it takes no lock of its own. A thousand atomic steps are not one atomic step. If add must be atomic, override it in the class and do the whole addition under the lock.
Why do many thread-safe classes use private final Object lock = new Object(); instead of synchronized methods?
Why. Both forms use the same monitor machinery with the same visibility guarantees and similar cost. The difference is who else can take the lock: this is shared with every holder of a reference, a private field is not.
A constructor calls registry.register(this) and then assigns this.threshold = 10. Another thread is iterating the registry at that moment. What can it see?
Why. Fields hold default values from allocation until the constructor assigns them, and this escaped before the assignment. The other thread can call methods on a half-built object. Register from a factory method after new returns.
A Cache class schedules a cleanup task, written as a non-static inner class that reads the cache's fields, on a scheduler that lives for the whole program. What is one consequence?
Why. An inner class that uses its enclosing object reaches it through a hidden Outer.this reference, which keeps the outer object alive and gives the task access to all its fields, private ones included. That access is shared state, so the cache's locking rules apply inside the task too.
ListHelper has final List<E> list = Collections.synchronizedList(new ArrayList<>()); and a method synchronized boolean putIfAbsent(E x) { if (!list.contains(x)) { list.add(x); return true; } return false; }. Other threads also call list.add directly. Is putIfAbsent atomic?
Why. Mutual exclusion only works between threads that take the same lock. Direct list.add calls take the list's lock, not the helper's. Lock the list itself across both calls, or hide the list behind your own class and lock.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
When would you use an interface and when an abstract class? Give an example of each from java.util.concurrent, and say why the choice matters for thread safety.
Model answer

An interface defines a contract with no state: a class can implement several, and it is the right choice for a capability many unrelated classes provide. Runnable, Callable, Executor, Lock and BlockingQueue are interfaces, so callers program against them and can swap implementations, for example an ArrayBlockingQueue for a LinkedBlockingQueue. An abstract class can hold state and constructors and implement part of an algorithm, and a class can extend only one. AbstractQueuedSynchronizer is the classic case: it implements the wait queue, parking and waking once, and ReentrantLock, Semaphore and CountDownLatch each contain a small subclass that defines what acquire and release mean.

For thread safety, the point is that neither inherits your locking. Default methods in an interface call your methods one at a time, so they are not atomic unless you override them, as ConcurrentHashMap does with computeIfAbsent. And a subclass of an abstract or concrete class can override a synchronized method without the keyword. So I keep thread-safe classes final where I can, or document exactly which lock subclasses must use.

Write code
Rewrite this class so it is thread-safe and hard to break: public class Stats { public long count; public double total; public Stats(Ticker t) { t.onTick(this::add); } public synchronized void add(double v) { count += 1; total += v; } public double mean() { return total / count; } }. Assume Ticker.onTick(DoubleConsumer listener) calls listeners from its own threads.
Model answer

Changes: the fields are private, so nobody can update one without the other; one private lock guards both, because the invariant (total is the sum of the count values added so far) spans both fields; mean() reads both under the same lock, so it never divides a new total by an old count; the constructor no longer leaks this; the class is final, so no subclass can add an unlocked method; and the empty case no longer divides by zero.

Debug
A teammate writes executor.submit(new Runnable() { public void run() { synchronized (this) { sharedList.add(item); } } }); inside an instance method, expecting it to be protected by the same lock as the outer class's synchronized methods. Explain what actually happens and give two fixes.
Model answer

Inside an anonymous class, this refers to the anonymous Runnable instance, not to the outer object. Each submitted task is a different Runnable, so each locks its own private object, and none of them excludes each other or the outer class's synchronized methods, which lock the outer object. Concurrent add calls on sharedList then race, which can lose items or corrupt the list.

Fix 1: lock the outer object explicitly with synchronized (Outer.this) { ... }, matching the synchronized methods. Fix 2, better: give the outer class a private final Object lock, use it in the outer methods and in the task (synchronized (lock)), and write the task as a lambda, where this means the outer object anyway. Or replace sharedList with a thread-safe structure and drop the lock if no invariant spans several fields.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"A subclass overrides a synchronized counter method to add auditing. Is it still thread-safe? How would you design this so the next subclass cannot break it?"
What a strong answer covers
  • An override does not automatically acquire the overridden method's monitor
  • Calling super.increment() locks only the parent call, not the surrounding audit code
  • Keep mutable fields private and protect every access with the same lock
  • Use a final class or final invariant-preserving methods, and prefer composition for added behaviour
  • Keep external auditing outside the critical section where the required ordering permits it
How a senior would say it
Not automatically. An overriding method does not inherit the synchronized modifier. If it directly increments a protected counter, concurrent calls race even though the parent method was safe. Calling super.increment() protects the parent's update, but it does not put the surrounding audit code under that lock. I would first decide whether the audit and increment must be one observable operation. If they must, the class needs an explicit design that preserves that relationship. For a counter I own, I would keep the field private and take one private lock for both updates and reads. I would make the class final, or make the methods that preserve its invariant final if extension is required. To add logging, I would usually wrap the counter through composition instead of exposing its state to subclasses. External auditing can block or acquire another lock, so I would keep it outside the critical section when the ordering requirement allows that. The proof is about every path to the state, not just the modifier on the original method.

Likely follow up: What changes if the audit record and the counter must always be observed together?

Out loudabout 75 s
"An interface's default method acquires three permits by calling a thread-safe one-permit method three times. Walk me through what can go wrong and how you would fix it."
What a strong answer covers
  • Atomic calls do not make the complete default method atomic or all-or-nothing
  • With four available permits, two callers can each acquire two and then both fail
  • Earlier successful acquisitions remain consumed unless the implementation explicitly restores them
  • Override the batch method to validate, check availability and subtract under one lock
  • Document the batch contract; default methods have no automatic synchronization guarantee
How a senior would say it
The batch is not atomic, even if every one-permit call is thread-safe. Suppose four permits are available and two threads each request three. The first thread takes one, the second takes one, and they alternate again. Each now holds two permits. Both next attempts fail, so both batch calls return false even though all four permits have been consumed. No individual call was broken. The missing guarantee was across the whole request. I would override the batch method in the implementation that owns the permit count. It validates the request, takes the same lock as every other access, checks that enough permits exist, and subtracts the entire request only on success. On failure it changes nothing. I would make the single-permit method delegate to that implementation so there is one policy to maintain. Trying to roll back a partial batch adds more concurrency reasoning and still needs a clear contract. The interface should promise all-or-nothing behaviour explicitly; a default method gets no such guarantee merely because it calls safe methods.

Likely follow up: Could a default method itself use a synchronized block, and what lock agreement would that require?

Out loudabout 60 s
"A refactor replaces a lambda with an anonymous Runnable, and list updates start getting lost. Both versions say synchronized on this. What would you inspect?"
What a strong answer covers
  • A lambda uses the enclosing instance as this; an anonymous class uses its own instance
  • Separately created tasks therefore acquire different monitors
  • Those monitors also differ from the outer object's synchronized-method monitor
  • Use Outer.this consistently or one private final lock shared by all access paths
  • Avoid constructor escape when registering or starting these callbacks
How a senior would say it
I would check which object each synchronized block actually locks. A lambda uses the enclosing instance as this. An anonymous Runnable has its own this, so the refactor changes the monitor. If each submission creates a new task, every task locks a different object. Those locks also fail to exclude the outer class's synchronized methods. Two tasks can then update the same list concurrently despite both containing synchronized blocks. One fix is to name Outer.this explicitly, matching the outer methods. My preferred design is one private final lock object, used by every task and every outer method that accesses the list, including readers. I would also check how callbacks are registered: registration belongs after construction, so a worker cannot observe a partly initialized owner. Changing the callback syntax is safe only after we check its lock identity and what it captures.

Likely follow up: What would a long-lived scheduler retaining this task imply for garbage collection of its enclosing object?
