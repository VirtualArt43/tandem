Visibility: why a thread may never see your write

Why a plain flag set by one thread can stay invisible to another forever, what really causes it, and the three ways to fix it.

Asked atMicrosoftAppleDatabricks
Before this:Race conditions versus data racesThe lost update: read, modify, write

One thread sets stop = true. Another thread, looping on while (!stop), never stops. Nothing is wrong with either line of code. What is missing is a rule that says the write must ever be seen, and without that rule, "ever" really can mean never.

In plain words

Every morning you photocopy the office notice board and work from your copy all day. At ten, a colleague pins "meeting canceled" on the real board. You never find out, and you walk into an empty room at three. Your colleague did their part, and so did you. The problem is that nobody agreed on when you have to look at the real board again.

Threads work the same way. Compilers and CPUs are allowed to keep a working copy of a value and keep using it, as long as the thread itself cannot tell the difference. Another thread's write reaches you only at agreed moments: when you take a lock, read a volatile or atomic variable, or join a thread. Between those moments, you may be reading your photocopy.

The stop flag that never stops

Here is the smallest program that shows it. A worker spins until a flag is set; main sets the flag after a moment and then checks whether the worker noticed. Both programs end on their own: Java waits with a timed join, and C++ (which has no timed join) uses a second, atomic flag only to end the demo.

Run it a few times. On the Java side the worker is still spinning half a second after the write, every time, which for a CPU is an eternity: hundreds of millions of loop iterations. On the C++ side you get the same result, and ThreadSanitizer also reports a data race on stop, because writing and reading a plain variable from two threads without synchronization is exactly that. (The std::memory_order_relaxed in the C++ helper flag just means "an atomic read, with no extra ordering"; the memory orders lesson explains it.)

What actually happened: the read was hoisted

The worker's loop does not change stop, and nothing in the loop tells the compiler that another thread might. So the optimizer applies hoisting, one of its oldest tricks: a value that does not change inside a loop is read once, before the loop. For a single thread this is a perfectly legal and valuable optimization. For our flag it means the loop can never end.

C++

C++ can be even more surprising. Remove the helper flag, so the loop body is only spins += 1 (with spins captured by reference and printed after join), and Apple clang at -O2 compiles the worker to an empty function: it never reads stop at all, and the program prints "worker saw stop after 0 spins" although main waited 100 ms before setting the flag. The standard lets a compiler assume that a loop with no side effects (no I/O, no volatile access, no atomic or synchronization operation) eventually ends. If stop were false at the start, this loop could never end, so the compiler concludes stop must already be true and deletes the loop. This is what undefined behavior means in practice: the compiler reasons from the assumption that your program has no data race. (A ThreadSanitizer build, at -O1, keeps one instrumented read of stop and still reports the race; the plain optimized build leaves nothing for any tool to see.)

Caches are not the main villain

The popular explanation is "each core has its own cache, so it keeps reading an old copy". On every mainstream CPU that is not quite right. Caches are kept in agreement by hardware cache coherence: when one core writes a cache line, every other core's copy of that line is invalidated, and the next read fetches the new value. A write does reach the other cores, and fast.

There are really three places a value can hide:

WhereHow longWhat it causes
A register, because the compiler or JIT kept the value there (hoisting)Forever: the code never reads memory againThe infinite loop above. The main visibility bug.
The writer's store buffer, a small queue of pending writes inside each coreTypically nanoseconds: it drains on its ownA short delay, and writes appearing in a different order to other cores. That is the next lesson, reordering.

Two practical consequences. First, this bug happens on a single core too, because the register copy has nothing to do with how many cores you have. Second, you should not reason about hardware at all when writing code: you reason with the language's rules, and let the compiler emit whatever instructions and fences make those rules true on each CPU.

Loading the visibility simulator

The rule: no happens-before edge, no guarantee

visibility is the question "when is one thread's write guaranteed to be seen by another thread's read?" The answer is defined by the language's memory model, not by timing. Both Java and C++ say the same thing in different words: a read is guaranteed to see a write only if the write happens-before the read. Happens-before edges come from synchronization: unlocking and then locking the same lock, writing and then reading the same volatile or atomic variable (in C++, with the default ordering or a release store and an acquire load), starting and joining a thread.

A plain field written by one thread and read by another, with no such edge, gets no guarantee at all. Not "eventually", not "within a second": the reader may see the new value, an old value, or the old value forever. In Java that is a legal but useless outcome. In C++ the program has a data race and its behavior is undefined. You will meet the full list of edges in happens-before; for now, three fixes are enough.

Three ways to fix it

Fix 1: a volatile or atomic flag

In Java, mark the field volatile. In C++, make it a std::atomic<bool>. Every read now really reads the shared value, and a write is guaranteed to become visible to later reads.

Fix 2: read and write under the same lock

A lock gives visibility as well as exclusion: everything a thread wrote before releasing a lock is visible to the next thread that acquires the same lock. The catch is in the words "the same lock" and "read". Locking only the writer does nothing for the reader.

For a lone flag this is heavier than fix 1, but it is the right fix when the flag is part of a larger invariant that is already guarded by a lock.

Fix 3: use the stop signal the platform already has

Stopping a thread is common enough that both platforms ship a properly synchronized signal for it. Java has interruption: t.interrupt() from one thread is guaranteed to be seen by isInterrupted() in t, and it also wakes t from sleep, wait and blocking queue calls. C++20 has std::jthread, which passes a std::stop_token to the thread function and requests a stop (and joins) in its destructor.

Visibility is not atomicity

A volatile or atomic flag fixes visibility, and it is tempting to think it fixes everything. It does not. volatile guarantees each individual read and write is seen; it does not make a read and a later write into one step. Two threads doing count++ on a volatile field still lose updates, as you saw in the lost update.

Where visibility bugs hide in real code

  • Stop and status flags: running, shutdown, paused, polled by a worker loop.
  • Getters that skip the lock: the setter is synchronized (or locks a mutex) but the getter does not, "because reading is harmless".
  • "Initialized" flags: one thread fills in a structure and sets ready = true; another checks ready and reads the structure. This is visibility plus ordering, and it is the subject of the next lesson.
  • Configuration swapped at runtime: a reload thread assigns a new config object to a plain field that request threads read.
  • Java long and double: the JLS (section 17.7) allows a non-volatile 64 bit field to be written in two 32 bit halves, so a reader could see half of one write and half of another (a torn read). 64 bit JVMs do not split these writes in practice, but the specification does not promise it; volatile does. See volatile and atomic.

Worked example: the getter that skips the lock

A connection object has a state that a background thread changes. A request thread waits for it to be ready:

The bug. The write happens under a lock, but the read takes no lock, so there is no happens-before edge from the write to the read. After inlining, isConnected() is a plain field read inside a loop and can be hoisted, so awaitConnected() may spin forever. In C++ it is a data race, full stop.

Two fixes. Make the getter take the same lock (in Java synchronized boolean isConnected(); in C++ a std::lock_guard in is_connected, with the mutex declared mutable). Or, since this is a single flag with no other state attached, make it volatile boolean connected in Java and std::atomic<bool> connected_ in C++, and drop the lock from the writer too. Spinning is still wasteful here; a real version would wait on a condition variable or a latch, which also gives you the visibility for free.

Common mistakes

  • "It works on my machine." Whether the read is hoisted depends on the JIT tier, inlining and the compiler version. The Java demo above loops forever only after the JIT compiles the loop; run it with the interpreter only and it stops at once. A test that passes proves nothing.
  • "A sleep in the loop fixes it." Thread.sleep and Thread.yield have no synchronization meaning. The Java Language Specification (section 17.3) uses exactly this loop as its example and says the compiler may read the field just once. A sleep often hides the bug in practice, which is worse than failing loudly.
  • "A print in the loop fixes it." System.out.println takes a lock internally, which happens to stop the JIT from hoisting the read. It is an accident, not a guarantee, and it disappears when someone removes the debug print.
  • Synchronizing only the writer. A happens-before edge needs both ends: the writer releases a lock and the reader acquires the same lock.
  • volatile in C++. It stops some compiler optimizations on that variable but gives no inter-thread guarantee, and a race on it is still undefined behavior. Use std::atomic<bool>.
  • Using volatile for more than a flag. if (!started) { started = true; init(); } with a volatile started is still a check-then-act race: two threads can both see false. Use compareAndSet, compare_exchange_strong, or a lock.

In the interview

The classic phrasing is "why can a thread spin forever on a flag another thread already set?", or a code review question with a plain boolean running. It also appears as theory: a 2025 Microsoft senior loop asked how Java volatile behaves on a single core versus a multi-core machine, and how synchronized works, down to CPU caches and registers. A Databricks-tagged engineer on Blind told a staff candidate to expect the Java memory model, happens-before and volatile, and a Blind commenter describing Apple's staff level concurrency rounds advised knowing exactly when mutations become visible to other threads.

The flag is a plain field, so there is no happens-before edge between the write and the reader's loop. The JIT is allowed to read it once and keep it in a register, so the loop can run forever, even on a single core. Making it volatile, or an atomic in C++, gives every read a happens-before relation with the write, so the worker is guaranteed to see it. If the flag guarded more state than itself, I would use a lock on both sides instead, and for stopping threads I would normally use interruption or a stop token.

Follow ups to expect:

  • "Is it the CPU cache?" Mostly no: caches are coherent. It is the compiler keeping the value in a register, plus store buffers delaying and reordering writes; and the language rule, not the hardware, is what you design against.
  • "Does it matter on a single core?" Yes. Hoisting is a compiler decision and has nothing to do with the number of cores.
  • "Would volatile make count++ safe?" No: visibility is not atomicity.
  • "Why does adding a print statement make the bug go away?" The print takes a lock and defeats the optimization by accident; nothing guarantees it.
  • "volatile boolean or AtomicBoolean?" For a flag that one thread sets and others only read, volatile is enough. Use AtomicBoolean.compareAndSet (or compare_exchange_strong in C++) when the flip itself must be one step, such as "only the first caller runs shutdown".
  • "Could the C++ stop flag use memory_order_relaxed?" For a pure stop signal, yes: a relaxed load is still a real atomic load on every iteration, and the standard asks implementations to make atomic stores visible to other threads in a finite time. What relaxed gives up is ordering: data written before the store is not guaranteed visible to the thread that sees the flag. Keep the default seq_cst unless you have measured a cost.

Senior depth

Why the language allows it. If every read of every field had to go to memory, compilers could not keep values in registers, hoist loop invariants or eliminate repeated loads, and ordinary single-threaded code would be far slower. So both memory models make a deal: plain accesses are optimized freely, and synchronization actions mark the places where cross-thread visibility is required. Programs that put synchronization in the right places get simple, interleaving-style behavior; that promise is called DRF-SC and it is the heart of the happens-before lesson.

How the JIT decides. HotSpot interprets a method first, then compiles hot code; a long-running loop is compiled while it runs (on-stack replacement). The interpreter reads the field on every iteration, which is why the bug appears only after warm-up and why it "goes away" with -Xint, which turns the JIT off. A volatile read cannot be hoisted, and neither can a plain read that follows a lock acquisition or a volatile read in the same loop.

Java versus C++. In Java a racy read is defined but weak: it returns some value that was written to that field, possibly an old one. In C++ a data race makes the whole program's behavior undefined, which is how clang can delete the loop outright. That difference is why C++ code must use atomics even where "any recent value would do".

Under the hood

A volatile or seq_cst atomic read compiles to an ordinary load on x86 and to a load-acquire instruction (ldar) on 64 bit ARM. What changes most is what the compiler is allowed to do: it must perform the load every time it appears, and it must not move certain other accesses across it. Volatile and seq_cst writes also constrain the store buffer: on x86 the write is done with a locked instruction (xchg), or followed by one or by mfence, which waits for the store buffer to drain, and on 64 bit ARM it becomes a store-release instruction (stlr). That is about ordering, not about whether the write is seen eventually. You will see those instructions in volatile and atomic and memory orders.

Key takeaways

  • Without a happens-before edge, a thread may never see another thread's write, however long it waits.
  • The usual cause is the compiler or JIT reading a value once and keeping it, not stale CPU caches; it happens on one core too.
  • Fix it with a volatile (Java) or atomic (C++) variable, a lock on both the read and the write, or the platform's stop signal: interruption or std::stop_token.
  • Visibility is not atomicity: a volatile count++ still loses updates.
  • Sleeps and prints in the loop hide the bug; they do not fix it. In C++ a racy flag is undefined behavior.

Explain
An interviewer shows you a worker loop on a plain boolean running and asks: "Another thread sets running to false. Why might the loop never stop, and does it matter whether the machine has one core or sixteen?" Answer as you would out loud.
Model answer

The field is plain, so nothing creates a happens-before relation between the write in one thread and the reads in the loop. Without that edge the language gives no visibility guarantee at all. In practice the JIT sees a loop that never changes running and no synchronization inside it, so it is allowed to read the field once, keep it in a register and turn the loop into an infinite one. The write does reach memory; the loop simply never reads memory again.

The number of cores does not matter, because this is a compiler decision, not a cache effect. On a single core the hoisted value is just saved and restored with the thread's registers on every context switch. Caches on modern CPUs are coherent anyway; store buffers can delay a write by nanoseconds and reorder it, but they do not hide it forever. The fix is to declare the field volatile, or use an atomic in C++, so that every read is a real read with a happens-before edge from the write it sees. If the flag is tied to other state, I would guard both under one lock, and for canceling a thread I would prefer interruption or a stop token.

"You need a flag that tells worker threads to stop. Would you use a volatile or atomic, a lock, or the platform's interrupt or stop token? How do you choose?"
What a strong answer covers
  • All three are correct because each creates a happens-before edge; a plain flag creates none
  • A volatile or atomic is the lightest choice for a lone flag that guards no other state
  • A lock when the flag belongs to a larger invariant already guarded by that lock, taken on both the read and the write

How a senior would say it
All three are correct, because each one creates a happens-before edge from the write to the read, which a plain flag does not. So I choose by what else the flag has to do. If it is a lone flag that guards no other state, a volatile boolean in Java or a std::atomic<bool> in C++ is the lightest correct answer: every read is a real read, and nothing blocks. If the flag is part of a bigger invariant that a lock already protects, say a queue and its closed state, I keep it under that lock and take the same lock on both the read and the write. And if the worker can block, in a sleep, a wait or a queue take, a flag is not enough, because the worker will not look at it until it wakes up. Then I use interruption in Java, which wakes those calls, or a std::jthread stop token in C++, which can also wake a condition_variable_any wait. One thing none of them gives is an atomic check then act. For "only the first caller runs shutdown" I use compare and set.

"A junior engineer says the stop flag bug happens because each core caches its own copy of the variable. How would you correct them?"
What a strong answer covers
  • Caches on mainstream CPUs are coherent: a write invalidates the other cores' copies
  • The real culprit is the compiler or JIT keeping the value in a register after hoisting the read
  • Store buffers delay and reorder writes, but only briefly, never forever
  • The proof: it happens on a single core too, where a context switch just saves and restores the hoisted register
  • We design against the language memory model, not the hardware: no happens-before edge, no guarantee
How a senior would say it
I would say the instinct is reasonable but the mechanism is wrong. On mainstream CPUs caches are coherent: when one core writes a line, the other copies are invalidated and the next read fetches the new value. The thing that can hold an old value forever is a register. The compiler or JIT sees a loop that never writes the flag, reads it once, and tests the register from then on. Store buffers do exist, but they delay a write only briefly and can reorder it; they never hide it forever. The easy proof is that the bug happens on a single core, where there is only one cache: the hoisted value is simply saved and restored with the thread's registers. And the bigger point is that we do not code against hardware at all. We code against the memory model, and the rule is simple: no happens-before edge, no guarantee.
