Parallel merge sort

Executors and asyncmedium35 min

Divide and conquer is the easiest algorithm to parallelise and the easiest to get subtly wrong: too many threads, a parent that sits idle in join, a merge that is no longer stable, an exception that dies quietly on a helper thread.

The task

Sort an array (Java) or a vector (C++) in place with a comparator, using several threads.

  • The sort is stable: elements that compare equal keep their original order.
  • At most threads threads may ever take part, the calling thread included. A thread must not sit idle in join while another thread does its share: split the budget so that every thread you start, and the caller, sorts something.
  • Arrays shorter than 2,048 elements are sorted on the calling thread alone (the sequential cutoff): below that size, starting a thread costs more than it saves.
  • If the comparator throws, sort throws that same exception, and only after every thread it started has stopped.

One way to spend a budget of 4 threads, where each call keeps half of its budget and gives the other half to one new thread:

Rules: use plain threads (Thread, std::thread or std::jthread). Library thread pools, fork/join and parallel sorts are banned here, because controlling the parallelism yourself is the point. For the sequential parts you may use the library's stable sort: Arrays.sort on objects in Java, std::stable_sort in C++ (std::sort is not stable).

Where it comes up: multithreaded merge sort is reported at PayPal (2021, focused on the design) and Zomato (2024, with a follow up on how it changes on an 8-core machine and what the complexity becomes), and a Blind commenter said Apple Maps asked it.

What the tests check

  • Correct and stable for 13 sizes from 0 up, including 2,047, 2,048 and 2,049 around the cutoff, with many equal keys, and for already sorted, reversed and all-equal inputs.
  • 2,000 items: only the calling thread ever calls the comparator.
  • A big array with 4 threads: between 2 and 4 threads take part, never more than 4 compare at the same moment, and two of them are sorting at overlapping times (starting a thread and joining it straight away is not parallel).
  • With 3 threads, 2 or 3 take part; with 1 thread, only the caller.
  • A comparator that throws: the exception comes out of sort, and no helper thread is left running (in C++, an exception escaping a helper ends the process, which the test reports).
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Fork/join, work stealing and parallel algorithms

Open them one at a time. Each one gives away a little more.

Write the sequential merge sort first: split, sort both halves, merge through a scratch buffer. Where in that recursion could a second thread help, and what must happen before the merge may read the left half?
Give each call a thread budget. If the range is below the cutoff or the budget is 1, sort it sequentially. Otherwise start one thread on the left half with half the budget, sort the right half on the current thread with the rest, join, then merge. The two halves are disjoint ranges of the array and the buffer, so they need no lock; join is what makes the helper's writes visible to the merge.
Stability lives in one comparison: when the two front elements are equal, take the one from the left run. In Java that is "take right only if cmp.compare(right, left) < 0". Exceptions: catch everything in the helper, store it, join, then rethrow it on the caller (std::exception_ptr in C++). If the caller's own half throws, join the helper before letting the exception go.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How much faster is it on 4 cores, and what limits it?
The leaves split evenly, but the merges near the top are sequential: the last merge alone touches all n elements on one thread. Work is O(n log n) but the critical path is O(n), so the speedup can never exceed about log n, and in practice memory bandwidth caps it sooner. A parallel merge (take the middle element of the longer run, binary search its position in the other run, merge the two pairs of pieces in parallel) shortens the critical path to a polylogarithmic one. Say work and span: that is the vocabulary interviewers listen for.
Why should the parent sort half itself instead of starting two threads and waiting?
A waiting parent is a thread that costs memory and scheduling but does nothing. Starting two threads per split and joining gives about 2P threads for P of useful work; with only the cutoff as a limit it starts a thread per leaf, hundreds for a big array, far more than the cores. Budget splitting uses exactly P threads, all of them working.
How would you write it with Java's fork/join framework?
With Java's fork/join framework: a RecursiveAction whose compute sorts small ranges directly and otherwise calls invokeAll(left, right) and then merges, run with new ForkJoinPool(P).invoke(task). Fork/join uses work stealing: each worker has its own deque, and a worker that would block in join runs other tasks instead. Arrays.parallelSort is built this way on the common pool, whose size defaults to one less than the number of cores, which is why you cannot easily cap it at P.
And with C++ standard parallel algorithms?
C++17 added std::stable_sort(std::execution::par, first, last, cmp). Support depends on the standard library (GCC's needs Intel TBB, and libc++'s support has lagged), and you cannot portably choose the number of threads. In interviews, write the threads yourself, then mention the parallel algorithms as the production choice where they are available.
The data is 100 GB and memory is 8 GB.
External merge sort: read chunks that fit in memory, sort each one (in parallel, as here), write each sorted run to disk, then do a k-way merge of the runs with a min-heap over the head of each run, reading and writing in large sequential blocks. Now disk throughput is the bottleneck, so overlapping reads, the merge and writes in a pipeline matters more than more sorting threads.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Fork-join by hand with a thread budget. A call that may use t threads either sorts sequentially (small range or t is 1) or starts one helper with half the budget on the left half, sorts the right half itself with the other half, joins and merges. The invariants: two threads never touch the same index range at the same time, and a range is read only after the thread that sorted it has been joined. The first means no locks are needed; the second means every read sees the finished writes.

Why each line is there

  • The budget split. threads / 2 for the helper and the rest for the current thread works for odd budgets too (3 becomes 1 and 2), and the total number of threads is exactly the budget.
  • The cutoff. Creating and joining a thread costs on the order of tens of microseconds, and a sequential sort of a few thousand items takes not much longer, so below that size a thread mostly adds overhead. The exact value is a tuning choice; 2,048 is a typical order of magnitude.
  • One scratch buffer allocated once. Disjoint ranges of it are used by different threads, so it can be shared without locks.
  • join in every path. In Java an un-joined helper keeps writing into the array after sort returns; in C++ destroying a joinable std::thread calls std::terminate. So the helper is joined even when the current thread's half throws.
  • The exception hand-off. An exception cannot cross threads by itself. The helper catches it, stores it, and the caller rethrows it after join.
  • Take from the left run on ties. That single choice is what makes the merge, and so the whole sort, stable.

Cost and trade-offs

Work is O(n log n) comparisons plus O(n) extra memory for the buffer. With sequential merges the critical path is O(n), dominated by the top merge, so on P cores the speedup is good for the leaf sorts and fades at the top levels. Thread creation happens only log2 of P levels deep, so its cost is negligible for big arrays.

How to say it in the interview

I will give each recursive call a thread budget. Below a cutoff of about two thousand elements, or with a budget of one, it sorts sequentially with a stable sort. Otherwise it starts one helper with half the budget on the left half, sorts the right half itself with the other half, joins, and merges, taking from the left run on ties so the sort stays stable. The halves are disjoint so there are no locks, and the join is the happens-before edge that makes the helper's writes visible to the merge. Exactly P threads ever exist, all doing work. The top merges are sequential, so the speedup is bounded by about log n; a parallel merge would fix that.
