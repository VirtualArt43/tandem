CAS loops and atomic state machines

The read, compute, compare-and-swap retry loop; weak versus strong CAS; updating with a function; one-winner state machines; and a lock-free maximum.

Asked atRubrikDatabricksLinkedIn
Before this:Atomic variables and compare-and-swap

Fetch-and-add covers counting. Almost everything else you want to do to one shared variable without a lock, such as a maximum, a balance that must not go negative, or a task that may start only once, is a compare-and-swap in a retry loop. It is the most reused pattern in lock-free code, and interviewers expect you to write it from memory.

In plain words

Four friends on a trip share a kitty, and the balance is written in a notebook. Asha wants to pay 120 for tickets. She reads the balance (500), works out 500 minus 120 is 380 on her phone, and walks over to write 380. But the group has a rule: you may only write your new number if the notebook still shows the number you started from.

Meanwhile Ravi paid 50 for snacks, and the notebook now says 450. Asha does not overwrite it with her stale 380. She reads 450, works out 330, checks there is still enough money, and tries again. Read, compute, write only if nothing changed, otherwise start over: that is a CAS loop.

The shape of every CAS loop

A CAS loop has four steps, always in this order:

  1. Read the current value.
  2. Decide and compute the new value from the value you read, and only from it. You may also decide to give up (not enough money, already started).
  3. Compare-and-swap: install the new value only if the variable still holds the value you read.
  4. If the swap failed, someone changed the variable in between. Go back to step 1 with the fresh value.

Here is the kitty, a withdrawal that must never take the balance below zero. A plain fetch-and-add cannot do this, because the decision "is there enough?" depends on the current value.

Notice the one structural difference. In Java you call get() again on every pass. In C++ a failed compare_exchange_weak has already written the current value into current, so the loop needs no extra load.

Why the loop is correct

The decision and the write are separated by a gap, exactly like the lost update. What makes this safe is the swap: it succeeds only if the variable still holds the value the decision was based on. So a decision is never applied to a value other than the one it was made on. If anything changed, the stale decision is thrown away and remade.

The moment the successful CAS happens is the instant the whole operation "takes effect", what the theory calls its linearization point. Everything before it was preparation that could be thrown away. When the loop gives up without writing, as A does above, the point is the last read: the instant it saw 50, too little for 80.

The rules of a good CAS loop

  • Compute only from the value you read. Reading the variable again in the middle (compareAndSet(current, balance.get() - amount)) brings back the race.
  • No side effects inside. The body may run many times. Sending a message, adding to a list or incrementing another counter in there will happen once per attempt, not once per success.
  • Keep it short. The longer the gap between read and swap, the likelier someone else gets in first and your work is wasted.
  • Know when to give up. A CAS loop may also exit without writing (not enough balance, already started). A loop that can decide not to write is also cheaper, because reading a cache line does not take it away from other cores.

Weak versus strong

C++ gives you two compare-and-swaps. compare_exchange_strong fails only if the value really differed. compare_exchange_weak may also fail when the value did match: a spurious failure. That sounds like a defect, so why does it exist?

On processors that build atomics from load-linked and store-conditional, the conditional store can fail for reasons unrelated to your value: another core wrote a different variable on the same cache line, or an interrupt arrived. The weak version makes one attempt and reports that failure to you. The strong version must hide it, so it wraps the attempt in its own inner loop. The weak version jumps to fail when the store-conditional is disturbed; the strong one jumps back to retry. On x86 both compile to the same lock cmpxchg, and on Apple silicon both become one casal, so the difference only shows on some hardware. The rule that follows is simple:

  • Inside a retry loop, use weak. A spurious failure just costs one more pass, which your loop does anyway, and you avoid a loop inside a loop.
  • For a single-shot decision, use strong. If failure means "someone else won" (claim a job, start a task once), a spurious failure would make you wrongly conclude you lost.
Java

Java. compareAndSet is always strong, and it is what you should write. The weak forms exist (weakCompareAndSetVolatile, and weakCompareAndSetPlain, which also drops the ordering guarantees), and the JDK uses them internally. In JDK 21, AtomicInteger.getAndUpdate is a weak CAS in a loop with one neat trick: if the value has not changed, the failure was spurious, so it retries without calling your function again. C++

C++. Both functions also take memory orders: compare_exchange_weak(expected, desired, success_order, failure_order). The failure order applies to the load you get back on failure, so it cannot be release or acq_rel. If you dereference what a failed CAS gave you (a pointer to a node, say), the failure order must be at least acquire. With the defaults, both are seq_cst, which is always correct.

Updating with a function

Because every CAS loop has the same skeleton, both languages let you write just the "compute" step. Java has it built in; in C++ you write the helper once.

Java

The four Java methods: updateAndGet(f) and getAndUpdate(f) apply a function of the current value and return the new or the old value; accumulateAndGet(x, f) and getAndAccumulate(x, f) apply f(current, x). The Javadoc warns that the function may be re-applied when attempts fail under contention, so it must be free of side effects. On AtomicReference, updateAndGet(list -> ...) must build a new object, never mutate the one it was given: other threads may be reading it.

A lock-free maximum

Tracking the largest value seen (worst latency, highest bid, newest version) is the classic CAS loop with an early exit. If your candidate is not bigger than the current maximum, there is nothing to do, and you do not even attempt a write.

Why can a smaller value never overwrite a bigger one? Suppose thread A holds candidate 5 and thread B holds 9. If B swaps first, A's swap (expecting the old value) fails, A re-reads 9, and its loop ends because 5 is not bigger. If A swaps first, B's swap fails, B re-reads 5 and swaps 9 in. Either way the bigger value wins, and the early exit means that once the true maximum is in place, every later call is just a read.

Atomic state machines

A compare-and-swap on a state field gives you transitions with exactly one winner. This is how futures, connections and tasks avoid running cleanup twice or completing twice. List the states, then make every transition a compare-and-swap from the one state it is allowed to start from.

CallTransitionWho can win
start()CAS from NEW to RUNNINGThe first start or cancel to reach NEW
cancel()CAS from NEW to CANCELLEDThe same race: only one of them can leave NEW
finishRUNNING to DONEOnly the thread that won RUNNING, so a plain store is enough

Use the strong compare-and-swap here: a failure is information ("someone else got there first"), not a reason to retry.

Run it a few times. Sometimes start wins, sometimes cancel wins; the two counts always add up to one. In Java, an AtomicReference holding an enum is safe even though compareAndSet compares identity, because each enum constant is a single object.

Worked example: an invariant across two values, without a lock

The previous lesson ended with a broken NumberRange: two atomics for lower and upper, and two setters that could each pass their check and together leave lower above upper. The lock-free fix is to make the pair one value: an immutable object in Java, or a small struct that fits in one atomic word in C++. Then a CAS loop checks and replaces both bounds in one step.

Replay the bad interleaving: setLower(5) and setUpper(4) both read (0, 10) and both pass their checks. One swap succeeds, say the lower one, giving (5, 10). The other swap fails because the pair changed; it re-reads (5, 10), checks 4 against lower 5, and throws. The invariant holds. In Java the compare works because you pass back the exact Range object you read; in C++ compare_exchange compares the bytes of the struct.

Expect the follow up "your Java version allocates a new Range on every update; can you avoid that?" For two ints, yes: pack them into one long in an AtomicLong, lower in the high 32 bits and upper in the low 32 (((long) lower << 32) | (upper & 0xFFFFFFFFL)), and run the same CAS loop on the long. The C++ version already works this way, because its 8 byte struct is one atomic word.

This pattern scales to any small state: pack it into one immutable object, or one 8 byte word (16 bytes where the hardware and compiler give you a double-width CAS), and every transition becomes one CAS. When the state is too big to copy on every update, or several structures must change together, use a lock.

Common mistakes

  • Not refreshing the value in Java. long cur = x.get(); while (!x.compareAndSet(cur, cur + 1)) {} spins forever once anyone else changes x, because cur is never re-read. The same shape is correct in C++, where a failed compare_exchange refreshes cur.
  • Reading again in the middle. x.compareAndSet(cur, x.get() + 1) computes from a second read, which may differ from cur. Compute only from the value you compared against.
  • Side effects in the loop or in the update function. Logging, sending, adding to a collection or bumping another counter inside the loop happens once per attempt. Do them after the loop, once you know you succeeded.
  • A weak CAS outside a loop. if (!started.compare_exchange_weak(expected, true)) return; can return even though nobody started, because of a spurious failure. Single-shot decisions need the strong version.
  • Mutating the object behind an AtomicReference. ref.updateAndGet(list -> { list.add(x); return list; }) changes a shared object in place while others read it, and because the reference never changes, the CAS cannot notice the mutation; if an attempt does fail, the retry adds x a second time. Build a new object.
  • A CAS loop as a lock. while (!flag.compareAndSet(false, true)) {} is not a lock-free algorithm; it is a spinlock, with all the problems of one (the spinlocks lesson, next but one).

In the interview

CAS loops show up whenever an interviewer says "can you do it without a lock?" Rubrik has pushed candidates from a locked stack to a CAS-based one and asked them to explain the primitive. In a 2026 LinkedIn staff onsite, the candidate was asked to walk through the race in a thread-safe rate limiter where two threads both see 99 requests against a limit of 100 and both get in; a compare-and-swap loop on the counter, or a lock around check and increment, closes that race. Expect small tasks: "increment only while below a limit", "keep the maximum", "make sure this runs once".

I read the current value, compute the new one from it, and compare-and-swap. If the swap fails, another thread changed the value after my read, so I recompute from the fresh value and retry. The successful CAS is the point where the operation takes effect, so no update is ever lost and no decision is made on stale data. The loop body may run several times, so it must be free of side effects. It is lock-free: some thread always succeeds, though a single unlucky thread can retry many times.

Follow ups to expect: "What happens under heavy contention?" (many failed attempts and cache line traffic; add backoff, stripe the data, or fall back to a lock), "Weak or strong?" (weak in loops, strong for one-shot decisions), "Is it fair?" (no; a thread can starve), and "What if two fields must change together?" (one immutable pair behind one atomic, as in the worked example, or a lock).

Senior depth

Contention management. Under heavy contention most attempts fail, and every failed attempt still pulls the cache line around. Remedies, in rising order of effort: back off briefly after a failure; restructure so the loop can exit without writing (the early exit in the maximum); split the variable into cells (the next lesson); or use a lock, which lets one thread work while the others sleep. "Lock-free" and "fast" are different claims. It is also why you never write a plain increment as a CAS loop when fetch_add or getAndAdd exists: on chips with a native fetch-and-add (x86, and ARM with LSE) it cannot fail, so each increment pays for one trip of the cache line, while a contended CAS loop also pays for every failed attempt.

CAS loops in the JDK. ConcurrentHashMap uses a compare-and-swap to place the first node into an empty bin and only locks bins that already hold nodes; its size counter is spread over cells like LongAdder. FutureTask keeps its life cycle in an int state field and completes or cancels with compare-and-swap from NEW, the same one-winner idea as the state machine above. (One difference: a FutureTask stays NEW while it runs, and claims the right to run with a separate CAS on its runner field, so cancel can still win while the task is running.) Naming these shows you have read past the API.

Value comparisons can lie. A CAS checks that the value is equal, not that nothing happened. For a counter or a maximum that is fine. For a state that can return to an earlier value (IDLE, BUSY, IDLE), or a pointer to a node that can be freed and reused, "equal" can hide a change. That is the ABA problem, the subject of the lock-free stack lesson; the standard fix is to add a version number that only ever increases.

Key takeaways

  • A CAS loop is read, compute from what you read, compare-and-swap, and retry with the fresh value if the swap failed.
  • The body may run many times: no side effects, no second read, keep it short, and exit early when there is nothing to write.
  • Use compare_exchange_weak inside loops and compare_exchange_strong for single-shot decisions; Java's compareAndSet is always strong.
  • updateAndGet and accumulateAndGet (or a small C++ helper) write the loop for you.
  • A CAS from one specific state gives transitions with exactly one winner; pack multi-field state into one immutable value to keep an invariant without a lock.

Write code
Write a non-blocking permit counter for a resource with max permits: tryAcquire() takes a permit and returns true, or returns false at once if none are left; release() gives one back and must never let the count rise above max. No locks.
Model answer

Both methods are CAS loops with an early exit: the decision ("is there a permit?", "would this exceed max?") is made on the value read, and the swap applies it only if nothing changed. A plain decrementAndGet would be wrong, because it can drive the count below zero before you check. This is a non-blocking semaphore; when callers must wait for a permit instead of failing, you need a real semaphore, which module 8 builds.

Explain
Explain the difference between compare_exchange_weak and compare_exchange_strong to an interviewer, including why the weak one exists and when you would use each. Java learners: explain how this maps to compareAndSet.
Model answer

Both compare the variable with an expected value and swap in the new value if they match. The strong version fails only when the values really differ. The weak version may also fail spuriously, reporting failure even though the value matched.

The weak version exists because of load-linked and store-conditional hardware such as older ARM cores: the conditional store can fail if the cache line was disturbed, for example by a write to a neighbouring variable or by an interrupt. The weak CAS is a single attempt and reports that; the strong one must hide it with an inner retry loop. On x86 both compile to the same lock cmpxchg, so the difference is invisible there.

I use weak inside retry loops, where a spurious failure just means one more pass and I avoid a loop inside a loop. I use strong for single-shot decisions where failure carries meaning, such as "someone else already started this task". In Java, compareAndSet is always strong and is what application code uses; the weak forms like weakCompareAndSetVolatile exist for library code, and the JDK's own getAndUpdate uses one inside a loop.

Design
A connection object has the states CONNECTING, OPEN, CLOSING and CLOSED. close() may be called by many threads at once, and a connect that fails on a background thread may race with it. Cleanup (closing the socket, failing pending requests) must run exactly once. Design it without a lock.
Model answer

I keep the state in one atomic field and make every transition a compare-and-swap from the state it is allowed to leave. close() is a small CAS loop: read the state; if it is CLOSING or CLOSED, return, because someone else owns the cleanup; if it is CONNECTING or OPEN, CAS from exactly that state to CLOSING, and if the CAS fails, re-read and decide again. The loop matters: a version that tries OPEN then CONNECTING once each can see CONNECTING, lose the race to a connect that moves it to OPEN, fail both swaps and return with the connection still open. The failing connect path tries CAS from CONNECTING to CLOSING. Whichever thread wins a transition into CLOSING is the only one that runs cleanup, and when it finishes it stores CLOSED.

The successful connect path does CAS from CONNECTING to OPEN; if that fails, a close won the race, so the connect path must release the socket it just opened instead of publishing it. The one-shot transitions use the strong CAS, since each failure there is a decision, not a retry. If callers of close() must not return until cleanup is complete, I add a latch or a future that the cleanup thread completes, and the losers wait on it. The point to say out loud: one atomic state field and "only the winner of the transition acts" give exactly-once cleanup without a lock.

"Without a lock, how would you implement withdraw(amount) so the balance can never go negative? Talk me through the loop and why it is correct."
What a strong answer covers
  • A plain atomic subtract cannot do it, because the decision depends on the current balance
  • The loop: read, refuse if too small, compute the new balance, compare-and-swap, and retry from the fresh value if the swap fails
  • Correctness: the swap succeeds only if the balance still equals the value the decision was made on, so a stale decision is never applied
  • A concrete race: two withdrawals both read 100, one swap wins, the other fails, re-reads and decides again
  • The body can run many times, so no side effects inside it
  • Progress: lock-free, so some thread always succeeds, but one unlucky thread can retry many times
How a senior would say it
A plain atomic subtract will not do, because whether I may subtract depends on the current balance. So I write a compare-and-swap loop. I read the balance. If it is less than the amount, I return false. Otherwise I compute the new balance and compare-and-swap it in, expecting the value I read. If the swap fails, someone changed the balance after my read, so I go round again with the fresh value. In C++ the failed compare_exchange_weak has already handed me that value; in Java I call get again. Why is it correct? The swap only succeeds if the balance still holds exactly the value my decision was based on, so a decision is never applied to a different balance. Say the balance is 100 and two threads want 80 and 50. Both read 100 and both think there is enough. The 50 swaps first, and the balance is 50. The 80's swap fails, it re-reads 50, sees that is not enough, and returns false. No overdraft, nothing lost. Two rules close it out. The body can run many times, so no side effects inside it. And it is lock-free, not wait-free: some thread always succeeds, but an unlucky one can retry many times.

Likely follow up: Why compare_exchange_weak in this loop, and where would the weak version be a bug?

Out loudabout 80 s
"A service's CPU is pinned at 100 percent but its throughput has dropped, and the profiler shows most of the time inside a compare-and-swap loop on one shared atomic. What is happening, and what do you do?"
What a strong answer covers
  • Heavy contention: most attempts fail, and every attempt, failed or not, pulls the cache line across cores
  • Every failure reruns the body, and a long body (or one that allocates a new object) widens the window for losing
  • Lock-free is a progress guarantee, not a speed guarantee: nobody sleeps, so the losers burn CPU
  • First make the loop cheap: little work between read and swap, and exit without writing when nothing changes; use fetch-and-add if the update is a plain add
  • Then back off after a failure, or stripe the state so threads stop sharing one line
  • If the state cannot be split, a lock may be faster because waiters sleep; measure before and after
How a senior would say it
That is contention on the CAS loop. With many threads on one variable, most attempts fail, and every attempt, failed or not, drags the cache line to its core, so the CPU is busy moving one line around instead of doing work. Each failure also reruns the loop body, and if that body is long or allocates a new object, the window for losing gets wider, so it gets worse exactly when load rises. Lock-free is a progress guarantee, not a speed guarantee. Nobody sleeps, so the losers burn CPU. I would first make the loop cheap: compute as little as possible between the read and the swap, and exit without writing when there is nothing to change. If the update is really just an add, I would use fetch-and-add, which does not fail and retry. Next, a short backoff after each failure, or splitting the state into stripes so threads stop fighting over one line. And if the state cannot be split, a plain lock is often faster here, because waiting threads sleep instead of spinning. Whatever I change, I measure before and after.

"When would you reach for a CAS loop instead of a lock, and when would you go back to the lock?"
What a strong answer covers
  • CAS fits when all the state lives in one variable, or packs into one word or one immutable object
  • And the update is short and pure, so redoing it is cheap
  • What you gain: no blocking, no deadlock, and a stalled thread never holds others up
  • Lock when several variables or structures change together, the state is too big to copy, or the work has I/O or side effects that must happen once
  • Under very heavy contention a lock can win because waiters sleep; start simple and measure
How a senior would say it
I reach for a CAS loop when everything that has to stay consistent lives in one variable, or I can pack it into one word or one immutable object, and the update is short and pure, so redoing it is cheap. Then I get no blocking, no deadlock, and a thread that stalls halfway never holds anyone else up. I go back to a lock when several variables or structures must change together, when the state is too big to copy on every update, or when the critical section does I/O or has side effects that must happen exactly once. Under very heavy contention a lock can even be faster, because the waiters sleep instead of spinning. So I start with the simplest correct design, often a lock, and move to CAS where measurement says it matters.
