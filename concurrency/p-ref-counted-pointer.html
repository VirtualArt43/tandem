Reference-counted ownership

Build a primitivemedium50 minVMware

An atomic count is only the beginning. The last release must destroy once, and a weak observer must never bring a dead object back.

The task

C++ is the ownership exercise. Implement the shared and weak handles yourself, with an atomic strong count and an atomic weak count in a separate control block. lock() must use a compare-and-swap loop that increments strong ownership only while the count is positive. Library shared_ptr, weak_ptr and make_shared are forbidden. unique_ptr may hold the pointee and guard allocation.

  • Copies of distinct handles may be used concurrently. Concurrently modifying the same handle is outside the contract. This exercise protects lifetime, not mutable fields inside T.
  • The last strong owner destroys T exactly once. Weak handles keep only the control block alive. The last weak handle reclaims that block once strong ownership has ended.
  • Empty and moved-from handles are valid. Copy assignment, self assignment, move and reset must preserve counts. T has a nonthrowing destructor. Reference counts fit in signed int.
  • Java starts with one reference. tryRetain() returns false at zero; retain() then throws IllegalStateException. Each successful retain must be matched by release. Releasing at zero throws. The final release calls close() once and propagates its exception while leaving the count zero.
  • count(), useCount() and liveBlocks() are observation hooks, not permission to access a resource. A caller must own a live reference while using the object. Do not use the observed count for check-then-act lifetime decisions.

Example: make two strong owners and one weak observer. Dropping one owner keeps the object alive; dropping the second destroys it. The weak observer now fails to upgrade but still keeps its control block allocated.

What the tests check

  • Eight owners coexist and the last release destroys or closes exactly once.
  • C++ copy, move, self assignment, weak copy and control-block reclamation.
  • Failed upgrades after zero, plus eight contenders racing the last release in a seeded stress phase.
  • Java double release, retain after zero, and a throwing final close.
  • C++ runs under ThreadSanitizer; bounded joins and watchdogs prevent stalled tests.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What was the VMware follow-up?
The report asks for custom shared and unique ownership and then asks how to synchronize in a multithreaded environment. Explain which handle operations share the control block and why pointee access remains a separate synchronization problem.
Why is load followed by fetch_add insufficient for weak lock?
The final owner can decrement one to zero and destroy the object between those operations. The compare-and-swap must both validate positivity and reserve ownership in one atomic step.
Why does the strong group hold an implicit weak reference?
It keeps the control block alive while the last strong owner destroys the object. An external weak release cannot free that block underneath final destruction.
What happens with ownership cycles?
Strong cycles never reach zero. Use weak backreferences or explicit ownership boundaries. Reference counting alone is not a cycle collector.
Can memory ordering be weakened?
The reference uses relaxed increments from already owned handles, acquire on successful weak upgrade, and acquire-release decrements on cleanup. Prove lifetime and publication separately before weakening anything; using sequentially consistent atomics first is reasonable.
Does Java need a weak count too?
The JVM keeps the RefCounted wrapper memory alive while reachable. Its explicit count controls an external resource such as a socket, not Java object reclamation. C++ must solve both lifetimes.

The two invariants

The strong count equals the number of live owning handles. The weak count equals explicit weak handles plus one while the strong group still exists. Zero strong ownership is terminal. No successful operation can change zero to one. In Java the one counter tracks owned claims on a resource; the wrapper's memory itself is garbage collected.

Why each primitive is there

A strong copy increments from an already owned handle, so that handle prevents concurrent destruction while the copy is created. A weak upgrade has no such guarantee. Its CAS loop reserves ownership only if its observed positive count is still current. The returned handle adopts that reserved count instead of incrementing a second time. The final strong decrement destroys the object and then drops the implicit weak reference.

The C++ control block is initially guarded by unique_ptr until allocation succeeds. Its final deletion is explicit because implementing reclamation is the exercise. This is the narrow ownership-layer exception to the usual rule against manual deletion; callers still use RAII handles. All handle copies in the stress test are distinct objects, so the test does not accidentally introduce a race on a handle variable.

The broken interleaving

The broken versions treat an increment at zero as a valid retain. The last owner releases and destroys or closes the resource. A weak observer increments zero to one and reports success. The result is ownership of a dead resource. The deterministic terminal-state test catches this even when the concurrent race is not scheduled unfavorably.

Costs and limits

Copy and release require O(1) counter operations; weak upgrade retries under contention. Atomics on these types are not promised to be lock-free on every platform, and a CAS loop is not a wait-free guarantee. Copies contend on the same control block. Destructors can run on the last releasing thread, so expensive cleanup affects that thread's latency.

The upgrade contract matches the atomic lifetime decision described by the C++ weak observer specification. Java uses the atomic conditional update provided by AtomicInteger.

How to say it in the interview

I need two lifetimes: the resource ends at the last strong release, and the control block ends after the last weak claim. Weak lock uses CAS to reserve a positive strong count. Zero is terminal, so checking zero and incrementing separately is not safe.
