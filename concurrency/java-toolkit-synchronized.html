The toolkit: synchronized, wait and notify

Choose the right monitor, protect shared state, wait for conditions, and build a bounded buffer with synchronized, wait and notifyAll.

Asked atLinkedIn
Before this:Classes, interfaces and inheritanceThe collections you will useExceptions, InterruptedException and try-with-resourcesThe toolkit: Thread, Runnable, Callable and virtual threads

A thread-safe class needs more than a lock around its writes. You must choose which object owns the lock, keep related state consistent, and let a thread wait without preventing another thread from making progress.

In plain words

Imagine a kitchen with one key and a small serving shelf. A cook takes the key before adding a dish; a server takes it before removing one. If the shelf is full, the cook leaves the key and waits on a bench, so a server can make space.

A call from the kitchen means "come and check the shelf". It does not reserve a space or hand over the key. Whoever comes back must get the key and look again.

Why this matters for concurrency

This is the Java spelling of a monitor: an object's intrinsic lock plus its waiting mechanism. You will use it for queues, ordering puzzles and thread-safe LLD classes. The crucial review question is which state is guarded by which object?

The thread toolkit covers starting and joining workers; the exceptions lesson covers the cancellation policy. Here you learn the monitor protocol those workers use. JVM implementation details belong to object headers, monitors and the JIT.

API card: the lock and its waiting methods

synchronized is a language keyword. The waiting methods are final instance methods of Object, inherited by your classes; they are not methods you call on another thread to pause it. In the table, m is the exact object whose monitor you mean.

Construct or methodOne-line contract
synchronized void update()Acquire this before the method body and release it on normal return or exception.
static synchronized void update() in StoreAcquire Store.class, the declaring class's Class object, for the method body.
synchronized (m) { ... }Acquire the object referenced by m for this block; a null reference throws NullPointerException.
m.wait()With ownership of m, release it and wait; reacquire it before returning or throwing InterruptedException.
m.wait(long millis)Add a timeout to the wait; zero means no timeout, and a negative value is invalid.
m.wait(long millis, int nanos)Add 0 to 999999 nanoseconds to nonnegative milliseconds; both zero means no timeout.
m.notify()With ownership of m, select one arbitrary current waiter; keep ownership until you release it.
m.notifyAll()With ownership of m, wake all current waiters; each still has to reacquire it separately.
Thread.holdsLock(m)Report whether the calling thread owns m's monitor; useful for diagnostics, not acquiring a lock.

The Java 21 Object API specifies the wait overloads and exceptions. A timeout ends eligibility to remain asleep; scheduling and monitor reacquisition can delay the actual return. Never treat wait(100) as a guarantee to return within 100 milliseconds.

Choose an object, not a method name

Two instance methods marked synchronized exclude one another when called on the same receiver. Calls on two different instances use different monitors. A static synchronized method and an instance synchronized method also use different monitors, so they can execute together.

A block lets you protect a smaller region or choose a dedicated private final Object lock = new Object(). Keep that object private and its reference stable: callers cannot accidentally take your internal lock, and methods cannot switch to different locks halfway through the object's life. Equal objects are not necessarily the same monitor; monitor identity uses the actual object, not equals.

Avoid string literals and boxed numbers as locks: unrelated code may share the same interned or cached object. Reassigning a boxed counter also changes which object subsequent calls lock. A dedicated Object avoids both traps.

The five ownership results are true, false, true, true, false. Holding demo does not authorize demo.lock.wait(), notify() or notifyAll(): all three require ownership of their own receiver and otherwise throw IllegalMonitorStateException. Inside synchronized (lock), an unqualified wait() means this.wait(), which is usually the wrong object.

Locking an object does not freeze it. Unsynchronized methods and direct field access can still run, so every access to the guarded mutable state must follow the same protocol. Do not use separate per-instance monitors to guard static state shared across all instances.

Reentrancy, automatic release and visibility

Java intrinsic locks are reentrant. A thread that owns a monitor can enter another synchronized method or block using that same monitor. Each entry adds a hold; each exit removes one, and another thread gets ownership only after the final hold is released.

The inner method's exit does not release the outer method's hold. A concurrent get() therefore observes a completed pair, never the halfway value. Removing synchronized from addPair() would leave each increment safe individually but allow a reader between them. See compound operations and reentrancy for deeper reasoning.

Exclusion and visibility are separate guarantees. Only one thread owns a particular monitor at once. An unlock also happens-before every subsequent lock of that same monitor: writes before the unlock become visible to reads after the later acquisition. This covers ordinary guarded fields; they do not also need volatile. The formal rule is in JLS 17.4.5, with the reasoning developed in happens-before.

A normal return or a thrown exception releases the holds acquired by the exited synchronized regions. It does not roll back state: if you update half an invariant and then throw, the next owner can see that broken state. Validate before mutation and keep the invariant intact at every exit.

For LLD, synchronization is an implementation choice, not a promise automatically imposed on overrides. An overriding method can omit synchronized; invoking an inherited synchronized instance method still locks the actual receiver. Keep the locking contract explicit when extending classes, as discussed in inheritance and overriding.

Wait for state, not for a notification

Each object has one wait set for threads that called its wait methods. A waiting condition, also called a predicate, is a statement about protected state, such as "the queue is not empty". Check it while holding the monitor; if it is false, call wait() on that same object inside a while loop.

  1. Release and register together. wait() places the caller in the object's wait set and releases its monitor without letting a notifier slip between the condition check and registration.
  2. Permit someone else to change state. The caller is asleep, while another owner can update the fields and notify waiters.
  3. Reacquire, then recheck. Notification does not hand over ownership. Before continuing, the waiter must acquire the monitor and evaluate its condition again.

wait() releases all of the caller's reentrant holds on this monitor and restores them before continuing. It releases no other monitor. Waiting while holding an unrelated lock can prevent the producer you need from running. Unlike wait(), Thread.sleep() releases no monitors.

This prints received = 43. The reader cannot return while main owns the monitor, even after notifyAll(). If main publishes before the reader starts waiting, the notification itself is not saved, but ready is: the reader sees it and skips the wait. The state remembers the event. The final join() makes the reader's result available to main.

A spurious wakeup may occur without notification. Even an ordinary notification can be followed by a competing thread consuming the item first. Both require the same loop. A timeout is also just a reason to recheck; use a deadline and recalculate the remaining budget after each wakeup, as in time units and deadlines.

If interruption ends the wait, wait() reacquires the monitor before throwing InterruptedException and clears the interrupt status. An already interrupted caller with a valid monitor and arguments throws without releasing that monitor. Propagate the exception from a blocking method; a Runnable can restore the status and return, as above.

If notification races with interruption, wait() may instead return normally with the interrupt still pending, as specified by JLS 17.2.4. It cannot silently clear that interrupt and return normally. Entering synchronized, including reacquiring after a wait, cannot be cancelled by an interrupt; use the explicit lock toolkit for interruptible or timed acquisition.

Worked example: a notified consumer loses the item

Two consumers want one item. Assume C1 used if (items.isEmpty()) lock.wait() and then removed an item without rechecking. This failure needs no spurious wakeup.

The wakeup says "your condition may hold". The wait-in-a-loop lesson develops both spurious and stolen wakeups; condition variables and monitors explains the underlying protocol across languages.

A complete bounded buffer

The invariant is 0 <= items.size() && items.size() <= capacity, with FIFO order preserved. One private monitor guards the deque, the capacity checks and every mutation. Producers wait for space; consumers wait for an item. Both groups share one wait set, so use notifyAll() after each successful mutation.

The class supports multiple producers and consumers; the small driver transfers five items with main acting as consumer. Each successful insertion or removal takes effect inside its locked region. A wakeup cannot overfill the buffer because the caller rechecks before adding. size() is a protected snapshot, not a reservation for your next call.

Deque operations take amortized O(1) time, excluding waiting and notification overhead, with O(capacity) storage. notifyAll() can wake many threads that immediately wait again. The price buys a straightforward correctness argument when several conditions share one wait set.

This buffer has no close operation, fairness promise or timeout. Cancellation follows the wait() rules above; a successful operation can leave an interrupt pending. The finite driver has no cancellation path. For a service, define shutdown explicitly so a departing producer cannot leave consumers waiting forever. Continue with producer and consumer and the monitor object pattern.

Why notify can strand useful work

notify() cannot choose "a consumer" or "a producer". It selects an arbitrary waiter on the receiver. Consider a capacity-one queue, two consumers C1 and C2, and a producer P that will insert two items, with notify() used after every change:

  1. C1 and C2 wait because the queue is empty.
  2. P inserts the first item and notifies C1. Before C1 reacquires, P tries its second insertion, sees the full queue and waits.
  3. C1 removes the item and notifies C2 instead of P, then finishes.
  4. C2 reacquires, finds an empty queue and waits again. P remains asleep although space exists.

No active thread remains to signal P. A spurious wakeup is permitted, but you cannot rely on one to rescue progress. notifyAll() makes P eligible too. See lost wakeups and notification choices for the full proof obligations.

notify() can be appropriate when any chosen waiter can use the change and the number of signals matches the work enabled. For separate not-full and not-empty wait sets, use Condition objects from the lock toolkit. For application code, prefer a library blocking queue from concurrent collections and synchronizers when its contract fits.

Add a timeout without extending it after every wakeup

Add this method inside BoundedBuffer. It returns an available item, or null when it finds the queue empty with no budget left. Zero means check without a condition wait; negative budgets are rejected. Record the start once with System.nanoTime(), then subtract the elapsed time from the original budget on each pass.

Never round a positive remaining budget down to wait(0). That means an indefinite wait. The nanosecond argument preserves a submillisecond remainder, without promising nanosecond scheduling precision. This method checks availability before expiry, so an item found on reacquisition wins even if the budget has elapsed; initial acquisition and reacquisition can both delay return beyond the budget.

Common mistakes

  • Protecting the same state with different objects. A method locks this, another locks lock: neither excludes the other. Write down the single guarding monitor.
  • Locking only setters. Readers need the same visibility protocol; final on the lock reference does not protect the mutable data by itself.
  • Using if around wait. Recheck in a loop, even with one producer and one consumer, because spurious wakeups remain allowed.
  • Moving notifyAll outside synchronized. Java requires ownership for notification too. Change state and notify while holding the correct monitor.
  • Replacing wait with sleep or a polling loop under the lock. The updater cannot acquire that monitor to make your condition true.
  • Restoring interruption and immediately waiting again. The next wait may throw immediately again. Restore and leave, or propagate to a caller that owns the cancellation decision.
  • Calling arbitrary callbacks while locked. Reentrancy does not prevent lock-order deadlocks or callbacks observing half-updated state. Keep external work outside, with invariants restored first.

In the interview

A LinkedIn July 2024 interview report in the research describes a bounded queue using plain threads, wait and notify, with shutdown as a follow up. Prepare to write the code and explain each line: "which object?", "why while?", "why notifyAll?", and "what does a reader see?"

I will guard the entire queue with one private monitor. Producers wait while it is full; consumers wait while it is empty. Each wait releases that monitor and reacquires it before rechecking. I notify all because both kinds of waiter share one wait set. Unlocking and later acquiring the same monitor also publishes the state changes.

If asked to compare primitives, start from the required operation: use volatile and atomics for their specific visibility or atomic-update contracts, and explicit locks when timed acquisition or separate conditions matter. synchronized gives neither FIFO fairness nor protection from deadlock; review the rules of locking before adding a second lock.

Senior depth

In a thread dump, distinguish waiting for state from waiting for ownership. An untimed Object.wait() uses WAITING; a positive timed wait uses TIMED_WAITING. A thread unable to enter a monitor, including after notification while reacquiring it, is BLOCKED. These are Java thread states, not OS scheduling states; use thread dumps to find the owner and its stack.

On Java 21, blocking I/O inside synchronized can pin a virtual thread to its carrier, occupying that underlying platform thread while blocked. Keep critical sections short; consider ReentrantLock for frequently executed sections with long blocking operations. This is a version-specific scalability concern, not a reason to remove synchronization or replace every short block. See the Java 21 virtual-thread guide and virtual threads and coroutines.

Key takeaways

  • Instance methods lock this; static methods lock the declaring Class object; blocks lock the object you provide.
  • The same monitor provides exclusion and visibility. Ordinary reads must follow the guarding protocol too.
  • Intrinsic locks are reentrant and release on exception, but neither undo mutations nor prevent deadlocks.
  • Hold the exact monitor for wait or notification. Wait releases only that monitor and reacquires it before continuing.
  • State remembers progress; notifications do not. Always wait in a loop and use notifyAll() for the buffer's mixed waiters.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A class stores a static int total. Its add() method is instance synchronized, and its static synchronized get() reads total. Two instances receive concurrent adds. Diagnose both faults and give one locking policy that fixes them.
Model answer

The two add calls lock different receivers, so updates to the shared static field can overlap. The getter locks the class object, which neither add call locks, so it also lacks the intended exclusion and visibility relationship. Make both methods static synchronized on the declaring class, or use one private static final Object lock in all reads and writes. Do not create one private lock per instance for this static field.

Design
Add a close protocol to the bounded buffer in words or pseudocode. Existing items must remain readable, puts must fail after close, and every blocked thread must eventually be able to discover closure.
Model answer

Add closed, guarded by the same monitor. close() acquires it, sets closed = true, calls notifyAll(), then releases it. Put waits while full and not closed, then checks closed before inserting and throws an appropriate closed-state exception if set. Take waits while empty and not closed; if empty after the loop, it reports closed, otherwise it removes the oldest item and notifies all as before.

Both wait predicates and every closure check belong under the same lock. Consumers can drain existing items after closure. Notification makes blocked threads eligible; actual completion still depends on scheduling and acquiring the monitor. Interruption remains a separate propagated cancellation outcome.

Explain
Why can a correctly written monitor avoid a missed notification when the producer runs first? Why is replacing the consumer's loop with an unconditional wait wrong?
Model answer

The producer changes protected state before releasing the monitor. If it runs first, a later consumer acquires that monitor, sees the satisfied predicate and never waits. If the consumer checks first, it still owns the monitor until wait registers it and releases ownership, so the producer cannot slip its update and notification into a gap. An unconditional wait ignores already satisfied state; since notifications are not stored, it can wait forever after the only notification has already occurred.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Walk me through what synchronized actually guarantees. Which object am I locking, and can I call another synchronized method from inside it?"
What a strong answer covers
  • Instance methods lock the receiver, static methods lock the declaring Class object, blocks lock their supplied object
  • Exclusion applies only to code acquiring the same monitor
  • An unlock happens-before subsequent acquisition of that same monitor, providing visibility for ordinary guarded fields
  • Reentrancy permits the owner to enter again; other threads wait until all holds are released
  • Normal and exceptional exit release holds but do not roll back mutations
  • Use a stable private lock and protect reads as well as writes
How a senior would say it
Synchronized gives mutual exclusion and visibility through one particular monitor. An instance method locks its receiver. A static method locks the declaring class's Class object. A block locks the object in its parentheses. That identity matters: two instances have different monitors, and a static method does not exclude an instance method merely because both say synchronized. The visibility rule is that an unlock happens before subsequent acquisition of the same monitor. So ordinary fields written before unlocking are visible after that acquisition, provided readers follow the same protocol. I can call another synchronized method on the same receiver because intrinsic locks are reentrant. The thread adds another hold and releases it when the inner method returns. Other threads still cannot enter until the outer hold is released too. Return and exception paths release the relevant holds automatically, but exceptions do not undo mutations. For an encapsulated component, I usually choose a stable private lock and use it for every access to its guarded state, including getters. I also restore invariants before any exit.

Likely follow up: What changes if the inner synchronized method belongs to a different object?

Out loudabout 90 s
"Your bounded queue works with one producer and one consumer. Now I add more of both and it hangs. What do you check in the wait and notify code?"
What a strong answer covers
  • Check one monitor guards every predicate check, mutation, wait and notification
  • Every wait is in a while loop because of spurious wakeups and competing consumers or producers
  • Wait releases the monitor and reacquires it before continuing; notification retains ownership
  • One wait set contains producers and consumers, so notify can choose the wrong kind and strand progress
  • Use notifyAll() after each successful state change and explain its extra contention
  • Check cancellation or closure so departed producers cannot strand consumers
How a senior would say it
I first check the monitor protocol, especially whether a single notification can wake the wrong kind of waiter. Every queue access and condition check must use the same monitor. A producer waits while full and a consumer waits while empty, using while loops. Wait releases that monitor so someone else can change the queue, then reacquires it before returning. A notification does not transfer ownership or reserve an item. Another consumer can take the item before the notified consumer gets back in, which is why an if statement is unsafe. Spurious wakeups also require rechecking. With intrinsic monitors, both kinds of waiter share one wait set. Imagine two consumers asleep on an empty queue. A producer inserts, wakes one consumer, then waits on its next insertion because the queue is full. The consumer removes the item but notifies the other consumer. That consumer finds nothing and waits again, leaving the producer asleep despite available space. I use notifyAll after each successful change so every waiter can recheck. The cost is extra contention; separate conditions can target wakeups more precisely. Finally, I check whether a producer exited or was interrupted. A service needs an explicit closure protocol so consumers do not wait forever after production ends.

Likely follow up: How would you add a timeout without restarting the full timeout after each wakeup?
