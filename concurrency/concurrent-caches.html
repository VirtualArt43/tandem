Thread-safe caches: LRU, TTL and single-flight

Making an LRU cache thread-safe without the classic holes, scaling it, expiring entries, and sharing overlapping loads and failures per key.

Asked atRubrikMicrosoftAppleConfluentUberLinkedIn
Before this:Concurrent hash mapsFutures and promises

"Now make your LRU cache thread-safe" appears in Microsoft, Apple, Confluent and Rubrik reports; LinkedIn reports include thread-safe cache variants too. Two traps recur in the design: a successful LRU lookup updates recency, and a slow load must not hold the cache lock.

In plain words

A small office fridge holds ten items, and a whiteboard next to it lists them from most recently used to least. Whenever someone takes the milk, they move "milk" to the top of the list. So even "just looking" changes the whiteboard, and if two people rewrite it at the same moment, it ends up wrong. One marker pen, passed from hand to hand, fixes that.

When the milk runs out and five people notice at once, you do not want five people walking to the shop. The first one goes; the other four wait for them to come back. One trip per missing item, however many people noticed. That second idea is called single-flight, and it is what stops a cache miss from turning into a stampede on your database.

A cache hit updates recency

An LRU cache is a hash map for lookups plus a doubly linked list in recency order. get finds the entry and moves it to the front of the list; put inserts at the front and, when the cache is over capacity, evicts the entry at the back. With bounded key/value costs, both take expected O(1) work, excluding lock waiting; hash collisions and allocation can cost more.

The trap is in the word "get". Moving a node rewrites several links, so a get mutates shared state exactly like a put. A read-write lock with get under the read lock lets several threads rewire the list at once:

The precise statement is: a recency-updating cache hit needs exclusive access to the list. A miss, size() or an explicit peek can be read-only, but still needs synchronization with writers. The simple design below uses one mutex for every operation.

Why a concurrent map is not enough

The next idea is to make each piece thread-safe: a ConcurrentHashMap for the index and a concurrent deque for the order. Each structure is now safe, but the cache's invariant spans both of them and the capacity: "the list holds exactly the keys in the map, in recency order, and there are at most capacity of them." Two thread-safe parts do not make that whole atomic:

  • Two puts can make stale capacity decisions, then both try to remove the same eldest key, leaving too many entries; separate list and map removals can also diverge.
  • A get moves key K to the front while a put is evicting K: the map and the list now disagree about whether K is cached.
  • Removing a node from the middle of a concurrent deque is O(n) anyway.

This is the lesson from atomicity: one invariant, one lock. The map, the list and the size are one invariant, so one mutex guards all three.

The one-lock LRU

In Java, LinkedHashMap already is a map plus a recency list: construct it with accessOrder = true and override removeEldestEntry. In C++, a std::list holds the entries in recency order and an unordered_map maps each key to its list iterator, so splice can move an entry to the front in O(1).

Three details are graded. get returns a copy made under the lock (in Java the cached objects should be immutable, so handing out the reference is safe). The critical section includes hashing, allocation, value copying and list updates, so keep that work bounded: no backend loading, logging or eviction listeners. And the miss path here is a check-then-act (two threads may both miss and both insert the same value), which is harmless for a pure function but becomes a stampede when the load is a database call. That is the single-flight section below.

The examples allow capacity zero, which retains nothing; Java rejects a negative capacity. Keys must have stable hashing and equality, and values should be immutable or safely copied. Use non-null Java values when null means a miss.

For the C++ templates, assume hash/equality and destructors do not throw, and value assignment preserves a valid object on failure. New-node insertion rolls back the list if index insertion fails. get returns a value, never an iterator or reference that eviction could invalidate. User-defined hash, equality and value operations must not reenter the cache while its lock is held.

The lock gives a sequential order. A hit takes effect at its recency update, a miss at its protected lookup, and put after insertion or replacement and any eviction. Capacity may be exceeded transiently inside that private critical section, but another cache operation cannot observe it. Test eviction order separately from concurrent stress; an intact list alone does not prove correct LRU behavior.

Making it scale

Start with the one-lock implementation and measure its throughput and tail latency. When profiling shows the lock is hot, these are the steps, in order:

  1. Shrink the critical section. Build values before taking the lock; standard map operations still hash and compare keys under it, so keep those functions cheap; run eviction callbacks after releasing it (an open call).
  2. Segment by key. N independent LRU caches, each with its own lock and a share of the total capacity, picked by a stable nonnegative hash modulo N. Distribute any capacity remainder explicitly. Uniform traffic can spread across the locks, but a hot key still serializes on one shard; there is no guaranteed N-fold speedup. The price: eviction is per segment, so a hot segment may evict an entry that a single global LRU would have kept. A Meta candidate designing a single-machine memcache was praised for exactly this: one shard per core so locks rarely collide.
  3. Make recency best effort. First acquire the value safely through a concurrent map or a locked shard and retain its lifetime. Then try a separate policy lock; if it is busy, skip only the recency update. You cannot read the ordinary map or its list node after failing its data lock. Sampling recency updates has the same safety requirement. Redis takes a similar shortcut: it approximates LRU by sampling a few keys and evicting the oldest of the sample.
  4. Buffer policy updates, as Caffeine does. Its concurrent map supports data lookup while buffered access events update eviction policy in batches. Read events can be dropped under contention; write events must be preserved. Maintenance drains the buffers under a policy lock, usually through an executor, with fallback paths under pressure. Its Window TinyLFU policy combines recency with frequency-based admission. This separates data correctness from approximate eviction order; it is not a promise that every operation is nonblocking or that capacity is exact at every instant.

Expiring entries

A time to live cache stores an expiry time with every entry, and get treats an expired entry as a miss. First choose the contract: expire after a successful write or load, or extend the deadline on every access. The examples use expiry after write; reading refreshes LRU recency but not TTL. Two rules make it correct:

  • Use a monotonic clock (System.nanoTime(), std::chrono::steady_clock). Wall clock time jumps when NTP corrects it or someone changes it, which would expire everything at once or nothing for an hour.
  • Expiry is a write. Removing the expired entry happens under the same lock as everything else.

For Java deadline subtraction, use a positive TTL and compare intervals shorter than 263 nanoseconds; do not persist or compare nanoTime values across JVMs. C++ deadline addition must fit the clock's representable range. Expiry means the entry is expired at the protected time check, not that it stays live until the caller finishes using the returned value.

Lazy expiry on read leaves memory held by entries nobody asks for again. Reclaim it in one of three ways: on each write, check a few of the oldest entries and drop the expired ones (a fixed TTL after write needs a separate write-order queue, moved on every replacement; access order is not expiry order); run a cleaner that waits until the earliest expiry, wakes when an earlier deadline is added, removes entries under synchronization and is stopped and joined by close(); or, for many different TTLs, use a timer wheel, which is what Caffeine does for variable expiration. Decide too whether size() counts expired entries that have not been removed yet, and say so.

Sharing one in-progress load per key: single-flight

A popular key expires. Within a millisecond, 500 request threads miss it, and all 500 call the database for the same row. That is a cache stampede, and it can take down a database that normally sees only the cache's misses. The two tempting fixes are both wrong:

  • Load while holding the cache lock. Now every miss, for every key, waits behind one slow database call, and a lock is held across I/O.
  • computeIfAbsent(key, loader) on a ConcurrentHashMap. Its atomic computation is useful for short local work. A slow loader can block competing updates in the same bin, including unrelated colliding keys; the mapping function must not modify this map. Ordinary retrievals generally do not acquire that bin lock.

The right fix is single-flight: put a future in the map before doing the work. The first thread to miss installs a future atomically, releases every lock, runs the load, and completes the future. Other callers that join that flight find the future and wait on it. Once a pure single-flight removes the completed flight, a later caller can load again: this is not a global exactly-once guarantee. The atomic install decides one winner per key, and the load never runs under a lock.

The runnable example is a small memoizing cache: it retains successful futures, so all eight requests share one result even if some threads start late. It removes failed flights for retry. It has no capacity limit, expiry or invalidation yet; a pure single-flight would also remove successful flights after publishing their result elsewhere.

Callers must use stable keys and loaders with the same meaning for a given key, because only the winning loader runs. The C++ example requires copyable values and nonthrowing hash/equality functions. Cached values must be immutable or safely copied; a shared future does not make its result's mutable contents thread-safe.

The design choices, each of which an interviewer may probe:

  • The future goes in before the work starts. Inserting the result after loading would leave the whole load time as a race window.
  • Failure is shared, then forgotten. All waiters get the same exception (join wraps it in a CompletionException; shared_future::get rethrows it), and the entry is removed so a request after cleanup can retry instead of failing forever. Some systems cache not-found results or transient failures briefly (negative caching) to protect a struggling backend; that is a deliberate choice with its own TTL.
  • Remove only your own future. Java's two-argument remove(key, mine) is a compare-and-remove. This minimal cache never replaces a pending entry, so key-only removal would suffice here, as in the C++ version. If invalidation or replacement is added, an old loader must not delete a newer flight; C++ would then need a flight object or generation token to check too.
  • Combine it with the cache. If flights and cached values use separate maps, recheck the value cache after winning a flight: a caller can pause after a miss until an earlier flight has filled the cache and disappeared. Store the value before completing and removing your flight. Keeping completed futures, as in this demo, avoids that gap. Production implementations also need bounded capacity, expiry and a generation check if invalidation can race with filling.

Timeouts belong to callers and to the backend. Java join() has no timeout and is not interruptible; use get(timeout, unit) for a caller deadline and propagate InterruptedException. Do not call orTimeout on the shared future: it completes that same future exceptionally for everyone. Use a dependent copy for a caller-specific stage. C++ waiters can use shared_future::wait_for or wait_until, then get if ready; this does not cancel the loader. The leader executes the loader synchronously here, so a future timeout alone cannot bound its backend call.

A loader that recursively requests its own key waits on its own unfinished future; dependency cycles between keys can deadlock too. Define recursion as unsupported or detect it. Bound active distinct-key loads with admission control, since one flight per key does not protect the backend from a million different keys. Acquire any backend permit outside the map lock, release it on failure, and do not let one waiter's cancellation cancel work other callers still need.

Worked example: Rubrik's two-tier refresh

A Rubrik senior system coding question (from a question bank, so treat the wording as approximate) asks for a local cache on each service instance in front of a shared cache: on a miss or expiry, only one thread per instance may refresh the local copy of a key, and only one thread across all instances may refresh the shared entry; everyone else waits and reuses the new value.

  1. Inside one instance: single-flight per key, exactly as above. Ten threads missing user:42 become one refresh.
  2. Across instances: the in-process map cannot see other machines, so the winner of each local flight tries to take a short lease in the shared cache (for example a "refreshing" marker written only if absent, with an expiry of a few seconds). The instance that gets the lease reloads from the source and writes the shared entry; the others wait with a deadline and retry the shared lookup. Serving stale values would require a different, explicitly agreed contract.
  3. Failure handling: the lease expires on its own if its holder dies, so another instance can take over. A holder that stalls past its lease (a long GC pause) must not overwrite a newer value: make the shared store reject writes from an older version or fencing token, as in distributed locks and fencing. Expiry can let two loaders overlap; fencing protects accepted writes, not exactly-once backend execution.
  4. Say the trade-off: the reported wait-and-reuse contract adds refresh latency. A stale-while-refreshing variant can reduce that latency only with an explicit maximum stale age and failure policy; a hung refresh does not give a finite bound by itself. The thundering herd lesson shows how to refresh early so the window is rarely visible.

Common mistakes

  • A read lock for get. LRU gets move nodes. Use one exclusive lock, or a design (segments, buffered reads) where recency updates are synchronized separately. Sharded exact LRU still locks each shard on hits.
  • Two thread-safe structures and no common lock. A concurrent map plus a concurrent list cannot keep the map, the list and the size consistent.
  • Loading inside the lock, or I/O inside computeIfAbsent. Use single-flight with the load outside every lock.
  • Losing the failure path. If the loader throws and the future is never completed, existing waiters can remain blocked forever, and future callers too if the unfinished entry remains installed. Complete exceptionally and remove the entry in a finally or catch.
  • Wall-clock TTLs. Use a monotonic clock.
  • Mutable cached values. Callers that modify a cached object modify everyone's copy. Cache immutable values or return copies.
  • Callbacks under the lock. An eviction listener that calls back into the cache, or takes another lock, can deadlock. Collect evicted entries and notify after unlocking.

In the interview

A common two-step question is: implement an LRU (sometimes with TTL), then "make it thread-safe", sometimes "then distributed". Confluent has asked it for LRU and LFU, Uber as a cache with expiry under concurrent requests, Microsoft's Azure Storage with TTL, and LinkedIn with a sharp twist: for each lock you add, name the race it prevents.

A cache hit updates recency, so a shared read lock is insufficient. I will guard the map, the list and capacity with one mutex, keeping hashing and value work short. Misses never load under that lock: they go through a single-flight map of futures, so callers joining the same flight share one load and a failure is reported to all of them and not cached. If the lock becomes the bottleneck, I would shard into N independent LRUs and accept approximate global recency; in production Java I would use Caffeine, which buffers policy updates to reduce contention. I would measure tail latency and hit rate, rather than promise a fixed speedup.
The lock prevents three races: two gets rewiring the same list nodes, an eviction removing an entry that a concurrent get is moving, and a second insert pushing the size above capacity before the first one evicts.

Follow ups: "why not a read-write lock?", "how would you scale this to 64 cores?", "the load takes two seconds; what happens to other requests?", "how do you expire entries nobody reads?", "two levels of cache, one refresher across the fleet?" and "what is wrong with computeIfAbsent here?"

Senior depth

The stale set race. A reader misses, loads row R from the database (value 1), and is delayed. A writer updates R to 2 and deletes the cache entry. The delayed reader now writes value 1 into the cache, where it stays until it expires. Invalidation alone cannot prevent this. Fixes: retain a per-key version or generation even after invalidation, and atomically reject an older fill; comparing only with a cached value is insufficient if invalidation removed that value; or hand out a token on a miss that a later invalidation cancels, so the stale write is rejected. Facebook's memcache paper (NSDI 2013) describes such tokens, called leases, for this race and for stampedes.

Admission matters as much as eviction. LRU lets a one-off scan of a million keys flush every hot entry. TinyLFU admission compares estimated frequencies before admitting a newcomer to the main cache. Plain LFU chooses a least-frequently-used victim but need not reject a cold newcomer, so eviction and admission are distinct choices. If an interviewer asks for LFU, the concurrency story is the same: the frequency counters and the eviction structure form one invariant under one lock, or are updated in buffered batches.

Capacity and tests. An entry-count limit does not bound bytes when values vary in size. Track entry weights under the same invariant, reject or bypass an oversized value, and evict until the total fits. Count hits and misses with striped or per-thread counters if exact instantaneous totals are unnecessary. For tests, control time rather than sleeping through TTLs, force overlapping same-key loads with gates, check different-key progress, failure and retry, and pause a fill across invalidation to verify that an old generation cannot repopulate the cache.

Key takeaways

  • A successful recency-updating LRU get mutates shared order. Read-write locks with gets under the read lock are a classic bug.
  • The map, the recency list and the size are one invariant: one lock, kept short. Thread-safe parts do not make a thread-safe cache.
  • Scale with segments, best-effort recency, or Caffeine-style buffered reads, and say what each costs.
  • TTL: expiry time per entry on a monotonic clock, expired entries are misses, and something must eventually reclaim them.
  • Single-flight: install a future atomically before loading, load outside every lock, share failures, remove only your own future.

Quick check

Answer each question, then read why. Your score is saved for your module test.

An LRU cache uses a read-write lock: get takes the read lock and put takes the write lock. What goes wrong under load?
Why. An LRU hit updates recency, which writes shared links. A read lock admits multiple such writers rather than excluding them, even if a particular run happens to look correct. Writer starvation is a separate possible problem, not the only one. Use exclusive protection for each list, including inside a shard, or a correctly synchronized buffered policy.
A correct one-lock LRU has capacity 2. After put(A, 10) then put(B, 20), two threads concurrently call get(A) and put(C, 30). After both join, what can printing get(B) produce? Print MISS if absent; there are no other operations.
Why. If get(A) goes first, A becomes most recent and inserting C evicts B, so the final read misses. If C is inserted first, it evicts A; the subsequent get(A) misses without changing recency, and B remains with value 20. Correct locking permits both serial orders, but never returns another key's value.
Assume 500 callers join the same pending flight before it completes, the successful loader takes 200 ms, and scheduling overhead is negligible. How many loads run, and roughly when are results available?
Why. The first caller installs a future and runs the load; the other 499 find the future and wait on it. Everyone gets the result when the one load finishes. Without single-flight the database would see 500 identical queries at once: a cache stampede.
Why should a TTL cache compute expiry with System.nanoTime() or steady_clock rather than wall clock time?
Why. Expiry is about elapsed time, and only a monotonic clock is guaranteed never to go backwards. Their origins are arbitrary: Java nanoTime values are meaningful only as differences within one JVM. They do not promise better precision, synchronized machine clocks or immunity from overflow; the deadline calculation must respect the clock's range.
In the demonstrated cache, which does not cache failures, the load for K throws while 30 callers wait on that flight. What should happen after completion and cleanup?
Why. Completing the future exceptionally releases every waiter with the same error, and removing the entry lets the next caller try again. Never leave a future uncompleted: waiters would hang forever. Caching the failure is only acceptable briefly and deliberately (negative caching with a short TTL).
Java onlySuppose invalidation replaces a Java cache's old pending future with a new flight before the old loader fails. Why must old-loader cleanup use entries.remove(key, mine)?
Why. remove(key, value) is an atomic compare-and-remove. In this extended design, invalidation can replace the entry before old-loader cleanup. The minimal sample has no replacement API, so this race cannot occur there yet. Deleting someone else's in-flight future means the next caller starts yet another load.
C++ onlyIn the C++ single-flight, why does the map hold std::shared_future<V> rather than std::future<V>?
Why. Each waiter copies the shared_future out of the map under the lock and calls get on its own copy after releasing it. A plain std::future would let only one caller retrieve the value. Both kinds carry exceptions set with set_exception.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Extend a thread-safe LRU cache with a TTL: put(key, value) stores the value with an expiry of now plus a fixed TTL, and get treats an expired entry as a miss and removes it. Write the class in your language.
Model answer

Expiry uses the monotonic clock, removal of an expired entry happens under the same lock as every other change, and the LRU logic is unchanged. This is lazy expiry after write: reads update recency but do not extend the TTL. Entries nobody reads again may remain until capacity eviction, and insertion may evict a live LRU entry while an expired entry elsewhere remains. A cleaner must scan all entries incrementally or maintain a separate expiry structure; it cannot stop at the first live node in recency order. The Java deadline arithmetic assumes comparisons span less than 263 nanoseconds. The generic type restrictions of the earlier LRU apply here too.

Design
Your one-lock LRU now serves 2 million gets a second on a 64-core machine with a 95 percent hit rate, and profiling shows threads queueing on the lock. What do you change, in what order, and what does each change cost?
Model answer

First I would measure lock hold time and remove backend calls, logging and eviction listeners from it. Hashing, allocation and value copying still occur inside these standard containers, so I would measure those too. Next I would try independent shards with a fixed total capacity budget and a stable shard function. That trades exact global LRU for local LRU and can waste capacity under skew; 64 shards do not guarantee 64 times less contention.

If policy updates remain hot, I would separate safe value lookup from approximate recency. A concurrent map or a locked data shard must still protect lookup and value lifetime; failing a policy try_lock permits skipping recency, not reading an unprotected map. Buffered or sampled events can lower contention, but I would measure the hit-rate change and backend load. At the stated workload even a one-percentage-point hit-rate drop adds 20,000 misses per second. In production Java I would evaluate Caffeine's buffered policy and admission rather than promise a universal improvement. In C++ I would keep the same separation and define how delayed events handle already-evicted nodes.

Debug
After a database outage, some requests to a service hang forever, even after the database recovers. The cache uses a hand-written single-flight: existing = entries.putIfAbsent(key, mine); if (existing != null) return existing.join(); V v = loader.apply(key); mine.complete(v); entries.remove(key); return v; Explain and fix it.
Model answer

When the loader throws (as it does during the outage), the method exits through the exception before mine.complete(v) and before entries.remove(key). The future stays in the map, never completed. Every caller that was already waiting on it blocks forever in join, and every later caller for that key finds the same uncompleted future and blocks too, even after the database recovers, because nothing ever removes it. The fix is to make completion and cleanup unconditional: wrap the load in try, catch RuntimeException | Error for this Function loader and call mine.completeExceptionally(e) so waiters are released with the error, and move the removal into a finally block using entries.remove(key, mine) so only our own future is removed. For caller deadlines I would replace join with timed get, propagating interruption, or apply a timeout to a dependent copy. orTimeout mutates the shared future and would fail every waiter, so it is not a caller-local timeout. The synchronous leader also needs a backend deadline or an explicitly managed asynchronous loader; a waiter timeout does not cancel that work.

Say it out loud

Out loudabout 75 s
"Your LRU works with one thread. Make it thread-safe, then tell me what you would change if the lock became hot."
What a strong answer covers
  • A cache hit changes recency, so a shared read lock is insufficient
  • One mutex protects membership, recency and capacity together
  • Return an owned value and keep backend loading outside the lock
  • Shard only after measuring, accepting per-shard eviction and skew
  • Separate safe data lookup from optional policy updates before skipping recency
  • Measure latency and hit rate instead of assuming a shard-count speedup
How a senior would say it
I would start with one mutex protecting the map, recency list and capacity together. A cache hit moves an entry, so it is a write to the list even though the method is called get. A shared read lock would let several threads rewrite those links at once. I return a copied value or immutable owned object, never a list reference that eviction could invalidate. The lock covers lookup and the policy update; backend loading and eviction listeners run outside it. Hashing, allocation and copying still have a cost inside that section. If measurements show contention, I would shard by a stable key hash and split the capacity budget. That gives per-shard LRU, so skew can waste capacity and a hot key remains a bottleneck. If policy updates still dominate, I would separate safe value access from approximate recency events. Skipping a policy update is acceptable; reading an ordinary map after failing its lock is not. I would compare latency, hit rate and backend load before accepting the change, without assuming a speedup equal to the shard count.

Likely follow up: How would your capacity invariant change if entries had very different sizes?

Out loudabout 90 s
"A popular key expires and hundreds of callers miss. Design the load path, including failures, timeouts and invalidation."
What a strong answer covers
  • Atomically install a per-key future before starting the load
  • Run the loader outside map locks and let followers await the same result
  • Publish cached success before flight removal and recheck after winning a separate flight
  • Complete failures and remove only the matching flight so later calls can retry
  • Keep caller deadlines separate from the shared future and bound backend work
  • Reject stale fills with a retained generation and address recursive loads
How a senior would say it
I would atomically install a future for the key before starting the load. The winner loads outside the map lock, and followers await the same future, so unrelated keys can progress. If cached values and flights live in separate maps, the winner rechecks the value cache: another load may have finished between its original miss and winning this flight. It stores a successful value before completing and removing the flight. Alternatively, the cache can retain successful futures, with an explicit eviction policy. On failure I complete the future exceptionally and remove only my flight, releasing existing waiters and allowing a later retry. A caller deadline should stop that caller waiting, not fail the shared result for everyone. In Java I use timed get or a dependent future, not orTimeout on the shared future. The loader needs its own backend deadline because waiting less does not stop the work. For invalidation, I retain a generation and accept a fill only if that generation still matches; deleting the cached value alone loses that protection. I also reject recursive same-key loads, which would wait on their own result, and bound active distinct-key loads so many different misses cannot overwhelm the backend.

Likely follow up: What happens if a loader pauses past a distributed refresh lease and then tries to publish?

Out loudabout 65 s
"Users see expired values and memory keeps growing. What do you check in a TTL cache?"
What a strong answer covers
  • Define expire-after-write versus expire-after-access and the freshness instant
  • Use a monotonic clock and check expiry under synchronization
  • Separate logical expiry from physical reclamation
  • Use expiry ordering or a complete incremental scan rather than assuming LRU order
  • Bound storage and make cleaner shutdown and deadline changes explicit
How a senior would say it
I would first clarify whether TTL starts at write time or extends on every access, and whether freshness is checked at lookup or promised for longer. For the usual lookup contract, I use a monotonic clock and check the deadline while protecting the entry. An expired entry is a miss even if it is still physically stored. That distinction explains the memory symptom: lazy expiry only cleans keys that are requested again. I would add bounded capacity and scheduled or incremental cleanup. For expiry after write, the recency list is not sorted by deadline, because reads move entries without changing their expiry. A cleaner therefore needs a separate expiry order or a scan that eventually covers every entry. I would also check that new earlier deadlines wake the cleaner and that shutdown wakes and joins it. Tests would inject a controllable clock and cover the exact expiry boundary, replacements and unread expired entries.

Likely follow up: Can a value become expired after get checks its deadline but before the caller receives it?
