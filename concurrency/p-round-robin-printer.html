Round robin printer

Ordering puzzlesmedium25 minClassic interview puzzle

N threads print 1 to M in turn. It is the most reported ordering puzzle outside LeetCode: print 1 to 100 with 3 threads (Microsoft), 1 to N with N threads and then with one semaphore (Nvidia), Aa1Bb2Cc3 with three threads (Qualcomm). One clean solution answers all of them, and the follow ups test whether you know why it is clean.

The task

One RoundRobinPrinter is shared by n threads with ids 1 to n. Each thread calls print(id, printNumber) once. Together they must print the numbers 1 to m in order, and thread id prints exactly the numbers k with k % n == id % n: thread 1 prints 1, n + 1, 2n + 1 and so on, and thread n prints n, 2n, 3n. print returns once the thread has printed all of its numbers; a thread with no numbers at all (when m is smaller than n) returns at once.

With n = 3 and m = 7, thread 1 prints 1, 4, 7, thread 2 prints 2, 5, thread 3 prints 3, 6, and the output is 1 2 3 4 5 6 7.

Rules: the threads start in any order. A waiting thread must block, not spin. No sleep to arrange turns. Each object serves one run; the tests create a fresh one per round. In C++, ThreadSanitizer must stay quiet.

What the tests check

  • With 3 threads and thread 1 not started, threads 2 and 3 print nothing for 200 ms and are blocked, not spinning. Then thread 1 starts and the output is exact.
  • The exact sequence for n and m of (1, 5), (2, 10), (3, 10), (3, 100), (4, 3), (5, 1), (7, 50) and (10, 100), with the threads started in a seeded random order, repeated. The cases with m smaller than n check that threads with nothing to print still return.
  • Every number is printed by the thread that owns it.
  • A mixed pattern: the same class with 3 threads and m = 78, where the tests give thread 1 a printer for capital letters, thread 2 one for small letters and thread 3 one for numbers. The output must be Aa1Bb2Cc3 and so on up to Zz26.
  • No round hangs, no exceptions, and in C++ no ThreadSanitizer report.

Taught in: Making threads take turns

Open them one at a time. Each one gives away a little more.

Keep one counter, next, the next number to print, under one lock. Thread id knows its own numbers: id, id + n, id + 2n, up to m. Before each one it waits until next equals it.
Who should be woken after a print? With one shared condition you must wake everyone, and n minus 1 of them go straight back to sleep. Better: give each thread its own condition on the same lock. The owner of next is thread (next - 1) % n + 1, so after printing k you signal exactly the thread that owns k + 1.
The semaphore version is a ring, turn passing in its purest form: n semaphores, the first with one permit and the rest with none. Thread id acquires its own semaphore, prints, and releases the semaphore of the thread after it. Because each thread loops over its own numbers only, everyone returns on their own.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Print Aa1Bb2Cc3 with three threads: one prints capitals, one small letters, one numbers.
It is this problem with n = 3; only what each thread prints changes. Thread 1's k-th turn prints the k-th capital, thread 2's the k-th small letter, thread 3's the number k. The turn logic does not care what is printed, which is the point to make out loud. A Qualcomm senior candidate was asked exactly this in 2022, and the last test here runs it through your class.
You used n semaphores. Now do it with one counting semaphore.
One semaphore cannot say who goes next, so it can only serve as a lock: acquire it, look at a shared next, print and advance if the number is yours, release it, and retry if it was not. That is correct (the semaphore's release and acquire order the reads and writes of next) but it polls: threads keep waking for turns that are not theirs, wasting CPU in proportion to n. Say that plainly, then explain why the ring of n semaphores, or one condition per thread, is the right tool: each one is a targeted wakeup. An Nvidia interviewer asked this after an n-semaphore answer in 2023.
Locks only, no semaphores and no queues. Then the interviewer changes a line and it deadlocks: find the bug.
Locks only means the monitor version: one lock, a next counter, and conditions. Typical injected bugs: signal on a shared condition instead of signalAll (it wakes the wrong thread and the wakeup is lost), an if instead of a while around the wait, next advanced after the signal or outside the lock, or the wrong condition index signalled (off by one). Diagnose from a thread dump: if every thread is WAITING on a condition and none holds a lock, it is a lost wakeup, not a lock order deadlock. Then check that every state change is followed by a signal to the thread that can now run. Chargebee ran its round this way in 2025.
What does notifyAll cost with many threads?
Every print wakes all n threads, and n minus 1 of them re-check, find it is not their turn and sleep again. That is about n context switches per number and n times m for the run: a thundering herd. With one condition per thread, or the semaphore ring, each print wakes exactly one thread. For three threads nobody will notice; for fifty the difference is large.
Print forever, until someone calls stop().
Make the loop while (!stopped) and add stopped to every wait condition, under the same lock. stop() sets the flag and wakes everyone (signal every condition, or release every semaphore), because a thread blocked waiting for its turn cannot see the flag otherwise. Each thread then returns at its next check.
Print the numbers 1 to a million with several threads as fast as possible.
Then do not hand off per number: strict alternation is completely serial, with a context switch per number. Split the range into blocks, let each thread format its block into its own buffer (or into a pre-sized array at known positions), and write the buffers out in order at the end. Ordering is needed only for the final output, not for the work. A PayPal interviewer pushed in this direction in 2022.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

One counter, next, under one lock, and one condition per thread. Thread id loops over its own numbers id, id + n, id + 2n up to m; before each it waits until next equals it, prints, advances next, and signals the condition of the thread that owns the new next. The invariant is everything below next has been printed in order, and only the owner of next may print. Because every thread loops over exactly its own numbers, every thread returns by itself, including threads that own no number at all.

Why each line is there

  • A condition per thread. Each condition has exactly one waiter, so signal (notify_one) is safe and wakes precisely the next printer. One shared condition would need signalAll and would wake n minus 1 threads for nothing on every number.
  • The owner formula. Number k belongs to thread (k - 1) % n + 1, so its condition sits at index (k - 1) % n; after printing k, the next owner's index is k % n.
  • Wait in a loop. Spurious wakeups exist, and a signal that arrives early is harmless only because the waiter re-checks next.
  • A signal past m is harmless. After the last number, the signalled thread has no numbers left and is not waiting, so the signal is simply dropped.

Pitfalls

  • One shared condition with signal (notify_one). It wakes the longest waiter, which may not own the next number; that thread goes back to sleep and the wakeup is lost. Whether it hangs depends on the start order, which is why the tests shuffle it.
  • if instead of while. With notifyAll, every waiter wakes and prints out of turn.
  • Looping on a shared "is it over?" flag instead of on your own numbers. Threads that own nothing past the end then wait forever.
  • Spinning on next. With n threads, n minus 1 cores burn while one prints.

How to say it in the interview

Each thread knows its own numbers, id, id plus n and so on, so its loop ends by itself. The shared state is just next, the number due, under one lock. I give each thread its own condition: a thread waits in a loop until next is its number, prints, advances next and signals only the owner of the new next, so every print wakes exactly one thread. With one shared condition I would need signalAll and pay n wakeups per number. The semaphore version is a ring: each thread acquires its own semaphore and releases its neighbour's. Printing letters and digits, like Aa1Bb2Cc3, changes nothing but the callbacks.
