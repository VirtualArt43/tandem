Searchers, inserters and deleters

Ordering puzzleshard50 minThe search-insert-delete problem from The Little Book of Semaphores, on a real singly linked listRubrik

Rubrik ran this in 2026 as a System Coding round on a shared singly linked list, and a candidate's semaphore answer was rejected; another 2026 report gave the same rules as a data structure question. It is the search-insert-delete problem problem: readers-writers with three roles, and the list itself shows you why each rule exists.

The task

Three kinds of threads share one singly linked list of integers:

  • Searchers only read the list. Any number of them may run at the same time.
  • Inserters append a node at the tail. Only one inserter at a time, but an inserter may run alongside searchers: appending at the tail does not disturb anyone walking the list.
  • Deleters unlink a node from anywhere. A deleter runs alone: no searcher, no inserter, no other deleter.
  • No starvation of deleters: once a deleter is waiting, newly arriving searchers and inserters wait behind it. (Searchers and inserters already inside finish normally.)

You build two layers in one class. The access protocol is six methods, startSearch/endSearch, startInsert/endInsert, startDelete/endDelete, which enforce the rules above. The list is built on top of it: search, insert (append at the tail), remove (unlink the first node with that value) and snapshot, each wrapped in the matching protocol calls.

Rules.

  • Any building blocks are allowed: your own monitor, or (the answer commenters gave on the Rubrik report) a read-write lock plus a mutex for inserters. The tests only see the behaviour.
  • The one place where a writer and readers run at the same time is the tail: an inserter links a new node while searchers may be walking towards it. That link must be published safely (safe publication): a volatile next field in Java, a std::atomic<Node*> with release and acquire in C++. In C++, own the nodes with std::unique_ptr (no raw new or delete).
  • Keep a tail pointer, so insert is O(1); remember to fix it when you remove the last node.
  • Java only: the start methods are interruptible. A deleter interrupted while waiting throws InterruptedException and must stop holding the others back.

What the tests check

  • Protocol: three searchers inside together; an inserter enters while two searchers are inside; a second inserter waits for the first.
  • Protocol: a deleter inside keeps out searchers, inserters and other deleters; a deleter waits for a searcher inside and for an inserter inside.
  • Protocol: with a searcher inside and a deleter waiting, a new searcher and a new inserter both wait; the deleter goes first.
  • Four searchers and an inserter keep the list busy: an arriving deleter gets in after a small number of admissions (the test allows 60). Java: an interrupted waiting deleter lets the searcher it was holding back in at once.
  • List, one thread: duplicates, removing the first match, removing the head and the tail, inserting after the tail was removed, emptying the list and inserting again.
  • List stress, 6 threads in random start order mixing all three operations on their own values: every remove and search answer is right, and the final list holds exactly the values that should survive, each thread's values in insertion order, no duplicates, nothing lost. In C++, ThreadSanitizer must stay quiet, which is what checks the publication of new nodes.

Taught in: Readers and writers, three ways

Open them one at a time. Each one gives away a little more.

Start with the protocol and forget the list. Write down what each role must wait for: a searcher waits while a deleter is inside (or waiting); an inserter also waits while another inserter is inside; a deleter waits until nobody at all is inside. The state is a searcher count, an inserting flag, a deleting flag and a count of waiting deleters.
That is a monitor with one lock and one condition (broadcast on every exit), or a read-write lock where searchers and inserters both take the read side, inserters also take an insert mutex, and deleters take the write side. With the read-write lock route, the "no starvation of deleters" rule is writer preference.
For the list, use a sentinel head node so removing the first real node needs no special case. In insert, build the node completely, then link it with a single publishing write (volatile or a release store), then move the tail. In remove, walk with a prev pointer, unlink, and if you unlinked the tail, move the tail back to prev.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why must a delete exclude the searchers? Why exclude the inserter?
Searchers: in C++ the deleter frees the node a searcher may be standing on, a use after free; even with a garbage collector, a searcher can hold a stale node and you lose any guarantee about what a concurrent search returns. The inserter: if the deleter removes the current tail while the inserter is linking a new node after it, the new node is attached to a node that is no longer in the list, and the insert is silently lost, along with every later insert if the tail pointer now points outside the list.
The Rubrik candidate's answer used a Semaphore and a ReentrantLock and was rejected. What can go wrong with that mix?
The report does not say exactly; commenters pointed at races. A common trap: the Little Book's solution uses "lightswitches" where the first searcher in locks out deleters and the last one out lets them in. The last one out is usually a different thread from the first one in, so that lock must be a semaphore (no owner); a ReentrantLock there throws IllegalMonitorStateException, or, if you avoid that, the bookkeeping counter ends up unprotected. Mixing primitives also makes it easy to forget the deleter starvation rule.
Show the Little Book of Semaphores solution.
Two lightswitches and two mutexes: insertMutex makes inserters exclusive; noSearcher is held while any searcher is inside (taken by the first searcher, released by the last); noInserter likewise for inserters. A deleter takes both noSearcher and noInserter. That is correct about exclusion but lets a stream of searchers starve deleters; the no starvation version adds a turnstile that a deleter holds while waiting and that searchers and inserters must pass through.
Can searchers run without any lock at all?
Yes, if deletion is made safe for concurrent readers: deleters unlink nodes but defer freeing them until no searcher could still hold a reference, using epochs, hazard pointers or read-copy-update. Then searches are wait free, and only writers coordinate. Java's garbage collector gives you the "defer freeing" part for free, which is why ConcurrentLinkedQueue style structures are easier to write in Java than in C++.
Now make it fair to everyone, not just to deleters.
Deleter preference can starve searchers and inserters under a steady stream of deleters. Serve arrivals in order with tickets, as in the fair read-write lock: a searcher at the front enters if no deleter is inside, an inserter if no deleter and no inserter is inside, a deleter if nobody is inside. Each role then waits only for those who arrived before it.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Two layers. The protocol is a monitor with four fields, searchers, inserting, deleting and waitingDeleters, and three rules: a searcher may enter when no deleter is inside or waiting; an inserter when, in addition, no inserter is inside; a deleter when nobody is inside. The list relies on exactly those rules: searchers only read, the single inserter only touches the tail, and a deleter, being alone, may relink and free anything.

Why each line is there

  • waitingDeleters in the searcher and inserter conditions. That is the no starvation rule: a deleter that is waiting stops new arrivals, so it waits only for those already inside.
  • The deleter's finally (or one exit path). A deleter that stops waiting without entering, because it was interrupted, must undo waitingDeleters and wake the others, or searchers stay blocked behind a deleter that no longer exists.
  • Broadcast on every exit. Waiters want different things (a searcher can go when the deleter leaves, a deleter needs the room empty), so one condition with signalAll is simple and correct.
  • A sentinel head. Every real node has a predecessor, so remove has one code path, and the head pointer itself never changes.
  • Publish, then move the tail. The new node's fields are written first; the link from the old tail is the one write searchers can see, so it is volatile or a release store, and a searcher that sees the node sees it complete. The tail pointer is touched only by inserters and deleters, who never overlap, so it needs no atomics.
  • In C++, ownership runs alongside the links. Each node owns the next one through a unique_ptr, while the atomic raw pointer is what searchers follow. remove moves the ownership around the unlinked node and lets it be destroyed; that is safe only because a deleter is alone.

Cost and trade-offs

Search and remove are O(n) walks; insert is O(1) with the tail pointer. The protocol adds O(1) work under one lock per operation, and the broadcast wakes every waiter on each exit. Deleter preference gives deleters bounded waiting but lets a stream of deleters starve the others; a ticket based version is fair to all three roles. For read heavy lists, lock free searches with deferred reclamation are the production answer.

How to say it in the interview

It is readers-writers with three roles. Searchers share with each other; an inserter is exclusive among inserters but compatible with searchers because it only touches the tail; a deleter is exclusive with everyone because it relinks and frees nodes. I keep a searcher count, an inserting flag, a deleting flag and a waiting deleter count in one monitor, and new searchers and inserters wait while a deleter waits, so deleters cannot starve. Equivalently, a read-write lock with writer preference plus an insert mutex. In the list, the new node is published with a volatile or release store because it is the one place a writer and readers overlap, and remove fixes the tail when it unlinks the last node.
