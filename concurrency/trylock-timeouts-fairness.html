tryLock, timeouts, interruptible locking and fairness

How to wait for a lock without waiting forever, how to cancel a wait, and what a fair lock really costs.

Asked atRubrik
Before this:Mutexes and RAII guardsThe rules of locking

A plain lock() waits as long as it takes, and in production "as long as it takes" can mean forever. Senior engineers know the other ways to ask for a lock, when each one is right, and why the polite, fair lock is often the slow one.

In plain words

Picture the single ATM outside a busy bank branch. You can join the line and wait however long it takes. You can glance at it and walk away at once if someone is using it. You can wait up to five minutes and then leave for your meeting. Or you can wait, but leave the moment your phone rings with an emergency. Those are the four ways a thread can ask for a lock.

Then there is the question of who goes next when the machine frees up. A proper queue serves whoever waited longest: fair, but each time the person at the front has to notice and walk up, and the machine sits idle for those seconds. A crowd lets whoever is standing closest step in: faster overall, but an unlucky person at the back may wait a very long time.

Four ways to ask for a lock

A mutex only promises that one thread at a time is inside the critical section. How long a thread is willing to wait for its turn is a separate choice, and both languages let you make it:

Wait, but let another thread cancel the waitlockInterruptibly()no direct equivalent (see below)

The middle two rows are tryLock: the call returns a yes or a no. That return value is the whole point, and it changes the shape of your code. You may unlock only if the attempt succeeded, so the try and finally go inside the if, never around it.

Notice the third line: the thread asked to wait up to a second, but it got the lock after under 200 ms, the moment the holder let go. A timeout is a ceiling, not a delay.

C++

In C++ the timed functions live on std::timed_mutex (and std::recursive_timed_mutex, std::shared_timed_mutex), not on std::mutex. A std::unique_lock constructed with a duration, std::unique_lock<std::timed_mutex> lk(m, 100ms), calls try_lock_for for you; test lk.owns_lock() before touching the shared state. One surprise: the standard allows try_lock() and try_lock_for() to fail spuriously, returning false even when no other thread held the mutex. Treat false as "not now", never as proof that someone else owns it.

Cancelling a wait: interruptible locking

Suppose a request thread is stuck waiting for a lock and the request is cancelled, or the service is shutting down. With lock() the thread cannot be pulled out; it waits until the lock frees up, however long that is. An interruptible acquisition lets another thread cancel the wait.

In Java, lockInterruptibly() and tryLock(timeout, unit) both throw InterruptedException if the thread is interrupted before or while it waits. lock() and synchronized ignore interrupts while waiting: the interrupt flag is set, but the thread keeps waiting. You can even see the difference in a thread dump: a thread queued on a ReentrantLock is parked and shows as WAITING (or TIMED_WAITING for a timed attempt), while a thread queued to enter synchronized shows as BLOCKED.

C++ has no interruptible lock(). If you really need a cancellable wait, wait in short try_lock_for slices and check a std::stop_token between them. Most C++ code avoids the need instead, by keeping critical sections so short that nobody waits long.

The slices have a price: a stop request is noticed up to one slice late, and an idle waiter wakes a hundred times a second. If an interviewer pushes on that, the C++20 answer without polling is to build the lock from a std::mutex, a bool held and a std::condition_variable_any, and wait with cv.wait(lk, stop, [&] { return !held; }). That overload takes a std::stop_token, returns as soon as a stop is requested, and returns the predicate's value, so false means "cancelled, lock not taken".

When lockInterruptibly() throws, the thread does not hold the lock. That is why the call sits before the try whose finally unlocks: if the acquisition fails, there is nothing to release.

Choosing a timeout, and what to do when it expires

A timeout only helps if the failure path is a real plan. The common ones:

  • Fail fast under overload. If a request cannot get the lock within its budget, return "busy" (an HTTP 503, a rejected task) instead of queueing behind a hot lock until every thread in the pool is stuck. The timeout comes from the request's remaining deadline, not from a number someone liked.
  • Do something else useful. If another thread is already refreshing a cache entry, serve the slightly stale value instead of waiting (see the worked example).
  • Back off and retry. Release everything you hold, wait a random moment, and try again. This is how tryLock prevents deadlock, below.

Measure timeouts on a steady clock. System.nanoTime() and std::chrono::steady_clock never jump; the wall clock can jump when NTP corrects it. In C++, try_lock_for is meant to use a steady clock, and try_lock_until waits on whatever clock its time point uses, so pass a steady_clock deadline.

Fairness: barging versus FIFO hand off

When a lock is released and several threads are waiting, who gets it? There are two designs.

  • Barging (unfair, the default almost everywhere). The lock simply becomes free. Whichever thread grabs it first wins, and that is usually a thread that is already running, often the one that just released it, rather than a waiter that is asleep in the queue.
  • FIFO hand off (a fair lock). The lock is handed to the thread that has waited longest. Nobody can cut in, so nobody waits forever.

Java gives you the choice: new ReentrantLock() barges, new ReentrantLock(true) is fair. synchronized makes no fairness promise at all. In C++, the standard says nothing about fairness for std::mutex, and common implementations let threads barge.

Waking a parked thread costs microseconds (a system call, a context switch, cold caches), while a short critical section costs tens of nanoseconds. A fair lock pays that wake-up cost on every single hand off, and during it the lock is owned but unused. Threads end up marching through the lock one context switch at a time, a lock convoy. Measure it:

In this run the fair lock is almost perfectly even and about ninety times slower. The C++ version shows the same shape: the ticket lock gives almost exactly even counts and a far lower total than std::mutex. Your numbers will differ with the machine and the build (ThreadSanitizer slows both); the shape will not.

So why would anyone use a fair lock? Because an unfair lock can, in principle, let one thread wait indefinitely while others keep cutting in: starvation. That matters when a lock is held for a long time relative to how often threads arrive, or when a bounded waiting time is part of the requirement. Rubrik's reported admission problems (a shared bathroom, a team playground) come with fairness follow ups of exactly this kind: admit the most eligible waiting person, and show several ways to make sure no player or team starves. The usual answer is unfair by default, fair only where a waiting bound is a requirement, and even then, look for the real problem, which is usually a lock held too long.

Two fairness traps in Java

tryLock() with no arguments barges even on a fair lock: if the lock is free at that instant, it takes it, ignoring the queue. The Javadoc suggests tryLock(0, TimeUnit.SECONDS) when you want to respect fairness. And a fair lock is fair about the lock, not about the CPU: a thread that keeps getting scheduled can still take a fair lock many times in a row while another thread is not even running.

tryLock with backoff: avoiding deadlock without a lock order

A classic deadlock: thread A locks account 1 and waits for account 2, while thread B locks account 2 and waits for account 1. Each holds one lock and waits for the other forever. One of the four conditions every deadlock needs is "hold and wait". tryLock breaks it: take the first lock, try the second, and if that fails, release the first and start over. A thread never waits while holding a lock, so no cycle of waiting threads can form.

Many textbooks, OSTEP among them, file this same trick under "no preemption" instead, because the thread gives back a lock it already holds, and the deadlock lesson follows that convention. Either label is defensible in an interview as long as you state the mechanism: nobody ever waits while holding a lock.

The randomness is not decoration. Without it, the two threads can fail, release, sleep exactly the same time, wake together, grab their first locks again, and fail again, for as long as their timing stays in step. Nobody is blocked and the CPUs are busy, yet nothing moves: a livelock.

The full recipe is exponential backoff and jitter with jitter and a deadline: double the wait after each failure up to a cap, pick a random time below it, and give up with an error after a total time limit so a caller is never stuck. The same recipe is used for network retries, for the same reason. Lock ordering is usually the simpler fix when you can impose an order; you will compare both in taking several locks safely.

Worked example: one refresher, everyone else serves stale

A price cache must be refreshed from a slow service every minute. When the entry expires, 200 request threads notice at the same moment. With lock() around the refresh, one thread refreshes and 199 queue behind it for the full duration of a slow network call, and the service's latency spikes every minute.

With tryLock() the shape changes. The thread that wins the lock refreshes; every other thread sees false and immediately returns the current, slightly old price. Nobody queues. In Java:

The C++ version is the same with std::unique_lock<std::mutex> lk(refreshMutex, std::try_to_lock) and if (lk.owns_lock()), and the cached value held in a std::atomic<std::shared_ptr<const Price>> (C++20; libc++ on macOS does not ship it yet, so there you copy the pointer under a tiny mutex), so readers load and the refresher stores the pointer without a data race. A plain std::shared_ptr field read by one thread while another assigns it is a data race. Two details make it correct: the re-check after acquiring (the classic check-then-act fix) and that the losers never touch the lock again, so there is no unlock without a matching successful tryLock.

Common mistakes

  • Unlocking after a failed tryLock. Writing lock.tryLock(); try { ... } finally { lock.unlock(); } runs the critical section without the lock when the attempt fails, then calls unlock on a lock you do not hold: IllegalMonitorStateException in Java, undefined behavior in C++. Put the try inside if (lock.tryLock()).
  • Calling lockInterruptibly inside the try. If it throws, the finally unlocks a lock you never got. Acquire first, then open the try.
  • Swallowing the InterruptedException. A timed or interruptible acquisition can throw it. Propagate it or restore the flag with Thread.currentThread().interrupt(); never catch and ignore it.
  • Spinning on tryLock. while (!lock.tryLock()) {} is a busy loop that burns a core. If you must retry, back off with jitter, or just use a timed attempt.
  • Making every lock fair "to be safe". Throughput can collapse by one or two orders of magnitude. Fairness is a requirement you choose deliberately, not a default.
  • Fixed backoff. Equal retry delays keep competing threads in step and invite livelock. Add randomness.
  • In C++, reading false from try_lock as "someone holds it". It may fail spuriously. It only means "not acquired this time".

In the interview

This topic usually arrives as a follow up. You have written a solution with lock() and the interviewer asks "what if the lock is held for a long time?", "how would you avoid deadlock here without changing the lock order?", or, after a starvation question, "would a fair lock fix it, and what would it cost?" In Java interviews, expect "what is the difference between lock, tryLock and lockInterruptibly?" and "why would you use ReentrantLock over synchronized?"

synchronized is fine until I need one of four things: a bounded wait, a cancellable wait, fairness, or more than one condition queue on the same lock (newCondition()). tryLock with a timeout lets a request fail fast instead of queueing forever, and I take the timeout from the request's deadline. lockInterruptibly lets shutdown or cancellation pull a thread out of a lock wait. I keep locks unfair by default, because a fair lock pays a context switch on every hand off and can be orders of magnitude slower; I only choose fairness when a bounded wait is an actual requirement.
To avoid deadlock without a global lock order, I take the first lock, try the second, and if that fails I release everything and retry after a random, exponentially growing backoff with an overall deadline. That breaks hold and wait. The jitter matters: with a fixed delay two threads can retry in lockstep forever, which is a livelock.

Follow ups to expect: "Is synchronized fair?" (no guarantee), "What happens to a thread blocked in synchronized if you interrupt it?" (it keeps waiting; only the flag is set), "How would you build a fair lock in C++?" (a ticket lock), and "What do you do when the timeout fires?" (have a real plan: fail fast, serve stale, or back off).

Senior depth

  • Fairness and throughput are a real trade-off, not a bug. An unfair lock lets the running thread keep the lock and its data in a warm cache; a fair lock moves both to a sleeping thread on every hand off. Under heavy contention the fair lock's throughput is bounded by how fast the OS can wake threads.
  • Starvation usually signals a design problem. If a waiter starves on an unfair lock, the lock is too hot: shrink the critical section or split the lock (see lock granularity and striping) before reaching for fairness.
  • Timeouts compose with deadlines. In a request path, every wait (lock, queue, RPC) should take its limit from the time left in the request, so the sum can never exceed the request's own deadline.
  • Virtual threads add a fifth reason for ReentrantLock on Java 21. A virtual thread that blocks while inside synchronized, or while waiting to enter it, keeps its carrier platform thread (pinning); one waiting for a ReentrantLock parks and frees the carrier for other virtual threads. JDK 24 (JEP 491) removed most of that difference, so say which version you mean. See virtual threads and coroutines.
  • A timed-out waiter leaves the queue. In Java, a thread whose tryLock(timeout) expires (or whose lockInterruptibly() is interrupted) marks its node in the lock's wait queue as cancelled, and cancelled nodes are unlinked, so abandoned waiters do not pile up or receive the lock. You will see that queue in how locks are built.

Key takeaways

  • lock() waits as long as it takes; tryLock() never waits; tryLock(timeout) waits up to a limit; lockInterruptibly() waits until cancelled. Only unlock after a successful attempt.
  • Java's synchronized and plain lock() cannot be interrupted while waiting. C++ has no interruptible lock at all; use short timed slices with a stop token if you must.
  • Unfair (barging) locks are the fast default. Fair locks prevent starvation but pay a wake-up on every hand off and can be many times slower.
  • tryLock plus releasing everything on failure breaks hold and wait, so it prevents deadlock. Add exponential backoff with jitter and a deadline, or you trade deadlock for livelock.
  • Every timeout needs a real plan for when it fires.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
A teammate proposes making every ReentrantLock in the service fair, "so no request ever starves". What do you say?
Model answer

I would push back. A fair lock hands the lock to the longest waiting thread, which means every hand off has to wait for a parked thread to wake up, a context switch measured in microseconds, while the lock sits owned but unused. With short critical sections that can cut throughput by one or two orders of magnitude, and it creates lock convoys under load. Unfair locks let a running thread take the lock immediately, so the lock is never idle.

Starvation on an unfair lock is rare in practice and usually means the lock is too hot or held too long. I would first shrink the critical section, move slow work such as I/O out of it, or split the lock. I would use a fair lock only where a bounded wait is an explicit requirement, and measure the throughput cost there. I would also mention that fairness of the lock is not fairness of the CPU, and that in Java even a fair lock's tryLock() barges.

Write code
Write boolean transfer(Account from, Account to, long amount, long timeoutMs) that takes both account locks or neither, retries with exponential backoff and jitter, and returns false if it cannot finish within the timeout. Use your language's lock type.
Model answer

The key points: never wait for the second lock while holding the first, release everything before sleeping, randomize the sleep so competing threads fall out of step, cap the backoff, and stop at a deadline measured on a monotonic clock. The self-transfer check matters in C++, where locking the same non-recursive mutex twice is undefined behavior.

Explain
Explain, as you would to an interviewer, what happens to a Java thread that is waiting to enter a synchronized block when another thread interrupts it, and how that differs from a thread waiting in lockInterruptibly().
Model answer

A thread waiting to enter synchronized is in the BLOCKED state, and monitor entry is not interruptible: the interrupt sets the thread's interrupt flag, but the thread keeps waiting until it gets the monitor. Only afterwards, if its code checks the flag or calls something like sleep or wait, will it react.

A thread in lockInterruptibly() is parked, in the WAITING state, and the interrupt wakes it: the call throws InterruptedException (clearing the flag) and the thread does not hold the lock. The caller should then either propagate the exception or restore the flag and stop. That is why cancellable request handling and clean shutdown use lockInterruptibly() or tryLock(timeout) rather than synchronized.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 80 s
"Walk me through what happens at the moment a contended lock is released, first on a barging lock and then on a fair one. Why can the fair one be orders of magnitude slower?"
What a strong answer covers
  • Barging: the lock just becomes free, and a running thread, often the one that released it, takes it while the woken waiter is still getting onto a CPU
  • Fair: ownership goes to the longest waiter, which is asleep, so the lock sits owned but idle for the whole wake up
  • The cost: microseconds to wake a thread against nanoseconds of work, paid on every hand off, which forms a lock convoy
  • What fairness buys: no waiter is overtaken forever, so the wait at the lock is bounded
  • The choice: unfair by default, fair only when a bounded wait is a requirement, and shrink or split the hot lock first
How a senior would say it
The difference is who gets the lock in the instant after it is released. On a barging lock, the lock simply becomes free. The waiter at the front is woken, but while it is still getting back onto a CPU, a thread that is already running, often the one that just released it, grabs the lock and does more work. The lock is never idle. On a fair lock, the release hands ownership to the longest waiter, and that thread is asleep. Waking it costs microseconds, while the critical section may take tens of nanoseconds, and for that whole wake up the lock is owned but unused. That happens on every hand off, so threads march through the lock one context switch at a time: a lock convoy. In a quick benchmark with a tiny critical section, the gap is one to two orders of magnitude. What fairness buys is that no waiter is overtaken forever. So I keep locks unfair by default, and choose fairness only when a bounded wait is a real requirement, after shrinking or splitting the hot lock.

Likely follow up: On a fair ReentrantLock, does a plain tryLock() respect the queue?

Out loudabout 75 s
"Two threads move money in opposite directions. Each takes its first account lock, tries the second, and on failure releases and sleeps exactly one millisecond before retrying. Walk me through how this can run forever without ever deadlocking, and how you fix it."
What a strong answer covers
  • It cannot deadlock: no thread ever waits while holding a lock
  • The interleaving: A locks 1, B locks 2, both tries fail, both release, both sleep exactly 1 ms, both wake and collide again
  • Name it: livelock, the threads are busy and not blocked, but no transfer completes
  • Fix: a random sleep (jitter) whose upper bound doubles after each failure, up to a cap, so the threads fall out of step
  • Add an overall deadline that returns an error, or use a fixed lock order when the accounts have one
How a senior would say it
It cannot deadlock, because no thread ever waits while holding a lock. But it can livelock. Thread A locks account 1 and thread B locks account 2 at the same moment. A tries account 2 and fails, B tries account 1 and fails. Both release, both sleep exactly one millisecond, both wake together, and both grab their first lock again. The same collision repeats for as long as their timing stays in step. Nobody is blocked and the CPUs are busy, but no money moves. The fix is to break the symmetry. I make the sleep random, so one thread usually wakes first and takes both locks before the other comes back. I double the upper bound after each failure, up to a cap, so heavy contention backs off harder. And I give the whole transfer a deadline, so the caller gets an error instead of retrying forever. If the accounts have a natural order, like an id, the simpler fix is to always lock the lower id first, with no retry loop at all.

Out loudabout 90 s
"During a traffic spike, every request thread in your service ends up queued on one hot lock and latency explodes. You have two minutes: how would you use timeouts here, and what happens when one fires?"
What a strong answer covers
  • Replace the unbounded wait with a timed attempt, and take the limit from the request's remaining deadline
  • Touch the shared state and unlock only if the attempt succeeded
  • A real plan when it fires: fail fast with a busy error, serve a stale value, or back off with jitter; never spin on the lock
  • Make the wait cancellable too, so a cancelled request or a shutdown can pull the thread out
  • Say the limit: a timeout bounds the waiting but does not cool the lock; shrink or split the critical section, then measure
How a senior would say it
First, I would stop threads from waiting without a limit. Instead of lock(), each request makes a timed attempt, tryLock with a timeout in Java or try_lock_for on a timed mutex in C++, and the timeout comes from the time the request has left, not from a number I like. The code touches the shared state and unlocks only if the attempt succeeded. Then I need a real plan for when it fails. Usually that is failing fast with a busy error that the caller can retry elsewhere. If the lock guards a cache refresh, the loser serves the slightly stale value instead. If it is a background job, it backs off with jitter. I would also make the wait cancellable, so a cancelled request or a shutdown can pull the thread out, which in Java means lockInterruptibly or the timed form. But I would be clear that a timeout only bounds the waiting. It does not make the lock any less hot. The real fix is to find out why the lock is held so long, move slow work such as I/O out of the critical section or split the lock, and then measure again.
