Copy-on-write and immutable snapshots

Publish complete immutable versions, coordinate writers, and keep old snapshots alive safely in Java and C++.

Asked atRubrikGoogle
Before this:Safe publication, immutability and final fieldsAtomic variables and compare-and-swapConcurrent hash maps

Configuration, feature flags, routing tables and listener lists are often read far more than they are written. Copy-on-write lets you read a consistent version without holding a lock throughout the read: never change data that a reader might be looking at.

In plain words

A restaurant changes its prices. It could rub out the old prices on the menu board one by one while customers are reading it, and some customer would read the new price of the starter next to the old price of the main course. Instead, the manager prints a complete new menu in the back room and swaps it into the frame in one motion.

Customers who were already holding the old menu finish reading a complete, consistent menu; it is just a little out of date. Everyone who picks up a menu after the swap gets the new one. Customers do not have to wait while the manager prepares the new menu. Readers never see a half-written menu, because nobody writes on a menu that has been handed out.

The pattern in three moves

  1. The data lives in an immutable object, the snapshot. Once built and published, it never changes.
  2. One reference points to the current snapshot. In Java it is a volatile field or an AtomicReference; in C++ it is a std::shared_ptr<const T> whose publication is protected by atomic operations or a mutex.
  3. Readers load the reference once and use that snapshot for the whole operation. Writers copy the current snapshot, change the copy, and publish it with a single atomic write of the reference. Readers still holding the old snapshot keep using it; it becomes eligible for garbage collection in Java, or its object is destroyed when the last owning shared_ptr releases it in C++.

Why it is correct: the snapshot is never modified after publication, so there is nothing for a reader to race with. The synchronized publication is safe publication: a reader that sees the new reference also sees everything the writer did to build the snapshot. And because all the fields live in one object, a reader always sees a consistent set of fields from one version, which two separate volatile fields alone cannot guarantee. This is the copy-on-write pattern.

Immutability includes everything you can reach

A frozen container is only a shallow guarantee. Map.copyOf prevents structural edits, but does not freeze mutable values; a record containing a mutable list is not deeply immutable. In C++, shared_ptr<const T> prevents mutation through that handle, but another mutable alias, a mutable member, or a pointer inside T can still change the data. Copy or freeze reachable state and stop using mutable aliases before publishing. The examples use primitive fields or immutable strings.

In C++, use the default sequentially consistent atomic operations unless you have proved weaker orders sufficient. A release store paired with an acquire load that sees it also publishes initialization; a relaxed pointer load alone does not. Keep the owning shared_ptr alive throughout the read, rather than retaining only a raw pointer into it. Atomic does not imply lock-free: atomic shared-pointer operations may use internal locks, and the portable demo explicitly uses a short mutex.

The C++ version guards the pointer with a mutex, but look at what the mutex protects: copying one shared_ptr, which is a reference count increment. The reader then checks the snapshot with no lock held. Atomic alternatives are below; benchmark them rather than assuming they are faster. The read count varies by scheduling; zero mixed snapshots is the invariant.

Read the reference once

A reader can break consistency even when publication is correct:

Writers: one at a time, or compare-and-swap

With one writer, a synchronized reference replacement is enough. With several, two writers can copy the same version, each add their own change, and publish one after the other: the second publish silently throws away the first writer's change. That is the lost update, one level up. Two fixes:

  • Serialize the writers with a lock. Hold it across reading the old version, copying and publishing, not just the final swap. Readers do not take this writer lock; the C++ fallback still takes a separate short pointer mutex.
  • A compare-and-swap loop. Load the current snapshot, build the new one, and publish it only if the reference still points to the snapshot you copied; otherwise reload and try again. Java's AtomicReference.updateAndGet(f) provides this retrying update, which means f may run several times, so it must have no side effects.
C++

std::atomic<std::shared_ptr<T>> is C++20. The libc++ installed in Tandem's runner lacks this specialization, so the routing table above is a non-runnable standards example and the runnable demo uses a mutex. Your options are:

  • C++20 std::atomic<std::shared_ptr<const T>> where your library has it, as in the routing table.
  • The C++11 free functions std::atomic_load(&p), std::atomic_store(&p, q) and std::atomic_compare_exchange_strong(&p, &expected, desired) on a plain shared_ptr. These are the C++17 fallback and remain available, though deprecated, in C++20. Every concurrent access to that pointer must use the atomic functions. They need not be lock-free; the local libc++ uses internal locks.
  • A mutex held only to copy or replace the pointer, as in the demo. Portable to C++11; its latency depends on contention and scheduling.

What you may never do is let one thread assign a plain shared_ptr while another copies it. Separate shared_ptr objects can safely share ownership, but concurrent assignment and copying of the same shared_ptr object are not safe, so that is a data race and undefined behavior.

CopyOnWriteArrayList: the library version for lists

Java packages the pattern for lists and sets. In a CopyOnWriteArrayList, state-changing operations such as add serialize writers and normally copy the backing array, then publish the replacement through a volatile field. No-op cases can avoid copying: removing an absent element, or setting a slot to the identical reference, for example. Ordinary get, size and snapshot iteration do not acquire the list's writer lock.

Its iterator is a snapshot iterator: it walks the array that existed when the iterator was created, never throws ConcurrentModificationException and never sees later changes. Iterator remove and list-iterator set or add throw UnsupportedOperationException. These guarantees cover the captured element references, not later mutations inside the elements.

That makes it ideal for listener lists: registered rarely, iterated on every event, and safe to iterate while a listener unregisters itself. It is terrible for anything written often, because successful updates generally copy the whole array and create garbage. CopyOnWriteArraySet and addIfAbsent cover the set case. The C++ standard library has no equivalent class; a safely published std::shared_ptr<const std::vector<T>> snapshot is the same idea.

Java

A removed listener can still receive an event from an iterator created before removal. Concurrent publishers may call the same listener concurrently, so its own state needs protection. This minimal bus propagates a listener exception and stops that publication; choose isolation explicitly if all listeners must be called. Also, size() followed by repeated get(i) is not one snapshot: use an iterator or capture an array.

Snapshots of a whole store

Rubrik once asked for a key-value store with snapshots, and Google asked a candidate to make a snapshot map multithreaded; the snapshot store problem drills it. "Give me an immutable, consistent view while writers keep going" has four classic designs:

Here n is the number of keys and v is the history length for one key. The first three rows assume expected O(1) hash lookups and bounded key/value sizes; lock waiting, allocation and copying large values add costs. The routing fragment uses std::map, so its lookup is O(log n).

The versioned design is in-memory MVCC. A version counter alone is insufficient. Serialize commits so version 12 cannot publish while version 11 is incomplete. Build a batch privately, then install its entries and advance the published version together under a commit lock; readers must also synchronize access to any mutable index or history. A failed batch must roll back, or never become installed.

Register each open snapshot atomically with choosing its version, coordinated with cleanup. If the oldest snapshot is s, keep each key's newest entry at or before s, plus every newer entry; an older value may still be the value visible at s. Keep deletion tombstones until the same rule permits removal. Long-lived snapshots retain history, so bound their lifetime or budget for that memory.

RCU and MVCC: related versioning ideas

RCU (read-copy-update) separates removing an old object from reclaiming its memory. In a Linux copy-and-replace design, readers enter an RCU read-side section and access the published pointer with rcu_dereference; writers initialize a replacement and publish it with rcu_assign_pointer. These APIs provide the required ordering; an ordinary pointer assignment is not a portable substitute. Reclaim the old object after a grace period, using synchronize_rcu or a deferred call_rcu callback, once pre-existing readers have left.

RCU readers avoid taking the updater's mutex, but RCU alone does not provide an immutable whole-store snapshot: an RCU list traversal can observe concurrent changes to different links. MVCC selects versions visible to a database snapshot, whose scope depends on the isolation level. Ordinary snapshot reads can avoid waiting for row writers; locking reads, schema locks and write conflicts can still block. PostgreSQL retains old tuples, while InnoDB can reconstruct old versions from undo records. See database isolation levels.

The shared idea is preserving versions while readers need them, then reclaiming them safely. State the differences too: publication, snapshot scope and progress guarantees are specific to each design.

Worked example: feature flags read on every request

Suppose a service checks feature flags 100,000 times a second; an admin changes a few flags a couple of times a day, sometimes several at once ("enable the new checkout in India and turn off the old banner").

  1. Snapshot: an immutable Flags object holding a map of 2,000 flags and a version number.
  2. Reads: each request loads the current Flags once at the start and uses it for the whole request, so one request never sees half of an admin's change, and every log line can record which flags version served it.
  3. Writes: the admin endpoint takes a writer lock (writes are rare, so retrying full copies is unnecessary), copies the map, applies every change in the batch, and publishes one new snapshot. Copying 2,000 entries twice a day is likely acceptable; check actual value sizes and allocation cost.
  4. Why not a read-write lock? Typical read-write locks update shared reader bookkeeping, which can contend across cores. Java's snapshot reference avoids that reader count. C++ shared ownership still updates a reference count and may take a pointer lock, so measure rather than promising the same read cost.
  5. The trade-off to say out loud: a request that started a millisecond before the publish runs with the old flags. That is what "consistent but possibly stale" means, and the requirements must permit it, especially for security-related flags.

Common mistakes

  • Mutating a published snapshot. Publishing a HashMap and later calling put on it, or using shared_ptr<T> where shared_ptr<const T> would have stopped you. Freeze reachable state too: Map.copyOf, records and const do not by themselves guarantee deep immutability.
  • Reading the reference twice. Two reads can return two different versions. Load once into a local.
  • Several writers without a lock or CAS. Copy, modify, swap from two threads loses one writer's change.
  • Side effects inside updateAndGet or a CAS loop. The function can run several times. Logging or sending a message from inside it happens several times.
  • Copy-on-write for write-heavy data. Whole-copy updates cost O(n) and allocate new storage. There is no universal read/write ratio cutoff: compare data size, update rate, retention and latency against a concurrent map or locks.
  • C++: sharing a plain shared_ptr without synchronization. Assigning it in one thread while copying it in another is a data race, even though the reference count is atomic.
  • Assuming the swap means nobody uses the old version. Readers can hold it for as long as they like. If something must only happen after every reader has moved on (closing the old backend's connections), you need reference counts or an RCU-style grace period, not just the swap.

In the interview

It appears as "make this config reloadable without slowing down reads", as the multithreaded follow up to Snapshot Array or a snapshot map (a pre-2022 Google L5 candidate reported stumbling on exactly this follow up), as a key-value store with snapshots (Rubrik, also older reports), and as "why would you use CopyOnWriteArrayList?"

Reads vastly outnumber writes here, so I would keep the data in an immutable snapshot behind one atomic reference. Readers capture the reference once and do not hold a lock while traversing it; they always see one complete version, possibly a moment old. Writers copy, modify and publish with a single swap, serialized by a lock, or with a CAS loop if there are many of them. Old versions are reclaimed by the GC in Java and by the last owning shared pointer in C++. The portable C++ version briefly locks to acquire that ownership. RCU and MVCC also retain old versions, but have different consistency and reclamation rules.

Follow ups: "what does a reader see during an update?" (a complete old or new version, depending on when it captures the reference); "what if two admins update at once?" (lost update unless serialized or CAS); "what if writes become frequent?" (the copy cost dominates, move to a concurrent map or versioned values); "how do you make a multi-key update atomic?" (one new snapshot, or a complete batch committed under one published version); and for C++, "how do you publish a shared_ptr safely?"

Senior depth

The hidden contention in C++ snapshots. Copying a shared_ptr increments the reference count in the control block, and decrementing it later is another atomic write. If 32 threads copy the same snapshot millions of times a second, they all write to one cache line, which is the very contention the pattern was supposed to remove. Possible optimizations include keeping a thread-local owning snapshot when the freshness contract permits it, or a reclamation scheme that avoids per-read ownership updates. A cached version number needs a coherent publication protocol; a raw pointer plus a counter does not solve lifetime safety.

Reclamation without a garbage collector is a research area with production answers: hazard pointers (a reader announces the pointer it is using, and writers do not free announced pointers) and epoch-based reclamation (readers announce which epoch they are in, and memory from old epochs is freed once every reader has moved on). These need a proven library or protocol in C++20; do not invent a raw-pointer reclamation scheme during an interview. You also meet the problem in the lock-free stack, where freeing a popped node too early is the bug.

Key takeaways

  • Copy-on-write: immutable snapshots, one atomic reference, readers load it once, writers copy, modify and publish with one swap.
  • Readers see one complete version and need no lock during traversal; C++ pointer acquisition may still lock. A retained version can remain stale for its entire lifetime.
  • Several writers need a lock or a CAS loop, and a CAS loop's function must be free of side effects.
  • In C++, publish shared_ptr<const T> with C++20 std::atomic<std::shared_ptr>, the deprecated free functions, or a mutex held only to copy the pointer; never share a plain shared_ptr unsynchronized.
  • CopyOnWriteArrayList is perfect for listener lists and wrong for write-heavy data.
  • RCU and MVCC also preserve older versions, but neither automatically supplies the same snapshot or progress guarantee as this immutable-object design.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A reader does if (config.get().enabled) send(config.get().endpoint); where config is a Java AtomicReference (in C++, the analogous bug uses two atomic pointer loads) to an immutable object that a writer replaces now and then. What can go wrong?
Why. Each load is atomic and returns a complete, immutable snapshot, so nothing is half built. But two loads can return two different snapshots. Load the reference once into a local and read both fields from that local.
An initially empty immutable map is behind a safely published reference. Two threads each copy the current map, add a different key, and atomically publish their copy, without writer serialization or CAS. After both threads join, what can printing the final map's size produce? Select all that apply.Select all that apply
Why. If both copy the empty map, the last publication contains only its own key: 1. If one copies after the other's publication, it preserves that key and adds its own: 2. Every published map has at least one key, so 0 is impossible, and only two distinct keys are ever added, so 3 is impossible. Atomic publication prevents torn maps but does not prevent lost updates.
Why must the function passed to AtomicReference.updateAndGet(f) (or the retryable work in a CAS loop) avoid externally visible side effects?
Why. updateAndGet reads the current value, calls f, and tries to CAS the result in; if another thread changed the reference first, it repeats with the new value. A weak CAS may also fail spuriously; implementations can reuse a computed result if the observed reference is unchanged. The API promises neither one invocation nor one invocation per CAS attempt. Sending a message inside f can therefore duplicate it; atomic publication does not roll back that effect.
For copying the whole structure on every update, which workload is the worst fit?
Why. Every write copies the whole structure. At 50,000 writes a second on a million entries, the copying and garbage would swamp everything. Copy-on-write shines when reads vastly outnumber writes and the data is modest in size.
For copy-and-replace RCU, snapshot MVCC and an immutable config, which description captures the shared versioning idea without assuming identical APIs?
Why. All three separate making changes visible from reclaiming older data. They do not require a global mutex, condition variable, garbage collector or per-element lock ordering. RCU alone does not promise a whole-store snapshot, and MVCC does not eliminate every source of blocking.
Java onlyThread A starts iterating a CopyOnWriteArrayList of 3 elements. While it is on the second element, thread B adds a fourth. What does A see?
Why. The iterator holds the array that was current when it was created. B's add copies the array and publishes a new one, which A's iterator never looks at. That is a snapshot iterator: no exception, no lock, and no later changes.
C++ onlyA global std::shared_ptr<const Config> g; is reassigned by a writer thread (g = std::make_shared<const Config>(...)) while reader threads do auto c = g;. What does the C++ standard say?
Why. The control block's count is updated atomically, but the writer modifies the same g object that readers copy, and nothing orders those accesses. Use C++20 std::atomic<std::shared_ptr<const Config>>, std::atomic_load and std::atomic_store, or guard g with a mutex held only while copying or assigning it.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a FlagStore in your language: isEnabled(name) is called on every request from many threads and must not hold a lock while traversing the snapshot; apply(changes) is called rarely, takes a map of flag name to boolean, and all of its changes must become visible together.
Model answer

Readers take one snapshot. Java readers take no application lock; C++ readers can briefly wait for the pointer mutex, so this is not a nonblocking implementation. The caller must not mutate changes during apply. A batch is applied to a private copy, so no reader can see half of it, and one publish makes all of it visible together. Writers are serialized, so two concurrent apply calls cannot lose each other's changes.

Design
Design snapshot() for an in-memory key-value store that takes thousands of writes a second and where analysts take a snapshot every few seconds and read it for minutes. putAll must be atomic with respect to snapshots. Compare two designs and pick one.
Model answer

Whole-store copying costs O(n) per write; snapshot-time copying costs O(n) per snapshot and holds up mutations during that copy. For a large store with this workload I would choose versioned values, with a history per key and tombstones for deletes. A commit mutex serializes batches: construct the batch first, then install all histories and advance the published version together. In the simplest correct implementation, point reads, snapshot registration and cleanup take that mutex briefly too; they do not hold it throughout an analyst's session. Copying immutable history handles under the lock can further shorten reads.

A snapshot records and registers version s under the same coordination as cleanup. A point read selects the newest entry whose version is at most s. Commits must publish in order, and a failed batch must leave no partial entries that a later version could expose. If the oldest open snapshot is s, retain each key's newest entry at or before s and all newer entries. For example, a value written at version 3 is still needed by snapshot 10 if the next update is at 12. Snapshot release unregisters it. This makes snapshot capture O(1) with constant-time registration, but reads still synchronize on history access and long snapshots retain memory. It does not promise writers never wait; it avoids holding a writer lock for minutes while a snapshot is used.

Explain
An interviewer asks: "With your copy-on-write config, can a reader ever see a half-applied update? What can it see instead?" Answer precisely.
Model answer

No. A writer never modifies a snapshot that has been published: it builds a new object privately and then publishes it with a single atomic write of the reference. A reader loads that reference once, so it holds exactly one version, and that version is immutable, so every field it reads comes from the same complete update. The publication is safe because Java uses volatile publication, or C++ uses suitable atomic ordering or a mutex, so seeing the new reference also guarantees seeing every write that built the object. What a reader can see is a stale version: if it loaded the reference just before the swap, it finishes its work with the previous complete version. If it loads the reference twice, it can mix two versions, which is why the rule is to load once into a local. If the business needs "after this call returns, nobody uses the old version", that is a different guarantee, and it needs reference counting or a grace period, not just the swap.

I would publish one immutable routing snapshot and have each request capture it once. The request uses that same object for every routing decision, so it cannot combine an old host with a new port. How a senior would say it
No. A snapshot can need a value that was written much earlier than its version number. Suppose a key changed at version three and then at version twelve. An open snapshot at version ten must still read the version-three value. Deleting everything below ten would silently lose it. For each key I retain the newest entry at or before the oldest open snapshot, plus every newer entry. Deletes need tombstones so older values do not reappear. Capturing and registering a snapshot must be coordinated with the cleaner; otherwise cleanup can remove its history before registration finishes. I also serialize commit publication so a later batch cannot expose an earlier unfinished batch. The simplest implementation uses a commit mutex for installation, registration and history access, with no lock held during the analyst's whole session. That is correct but does not promise nonblocking operations. Finally, I monitor snapshot age and retained bytes, because one forgotten snapshot can pin a large history. The choice is to budget for that retention or explicitly limit snapshot lifetimes.
