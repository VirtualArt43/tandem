Stopping a thread: interruption and cooperative cancellation

Why no thread can be killed safely, Java's interrupt protocol, C++20 stop tokens, and the shutdown code interviewers grade.

Asked atRubrikLinkedIn
Before this:Creating, starting and joining threadsPassing data in and getting results out

Neither Java nor C++ lets you safely kill a thread. You can only ask it to stop, and write it so that it listens. When you build a thread pool in an interview, this is exactly what gets graded: shutdown semantics, interrupts, and which exceptions you catch.

In plain words

An umpire cannot drag a batter off the field halfway through a run. The umpire signals, the batter completes the run (or turns back), and then walks off. If batters could be teleported away mid-run, the scoreboard would be left half updated: one run counted at one end and not the other.

Stopping a thread works the same way. One thread signals a request; the running code checks for the signal at safe points, between whole pieces of work, tidies up, and exits. That is cooperative cancellation, and it is the only kind that keeps shared data correct.

Why you cannot just kill a thread

Java once had Thread.stop(). It threw an exception into the target at whatever instruction it happened to be running, which released all of its locks on the way out. The objects those locks protected could be left half updated (money debited from one account and never credited to the other), and every other thread would then see the broken state as if it were normal. It was deprecated in Java 1.2, and since Java 20 it simply throws UnsupportedOperationException.

C++ never had a kill for std::thread. POSIX offers pthread_cancel, but with C++ it either skips destructors or, on glibc, unwinds with a special exception, and a catch (...) that does not rethrow it aborts the program. Treat it as off limits. The rule in both languages is the same: a thread stops when its own code decides to stop.

The simplest protocol: a stop flag

The running code checks a shared flag between units of work. The flag must be volatile (or an AtomicBoolean) in Java and a std::atomic<bool> in C++. A plain boolean is not enough: the worker may never see the change, a visibility bug (see the visibility lesson) that also makes it a data race in C++.

A flag has one big weakness: it is only checked when the worker gets back to it. A worker that is asleep, waiting on a queue or waiting on a condition will not notice the flag until that wait ends, which may be never. Java interruption and C++20 stop tokens can also wake waits designed to observe them; they do not wake arbitrary blocking calls.

Java's interrupt protocol

Every Java thread carries an interrupt flag. t.interrupt() sets it; that is all it does to a running thread. What happens next depends on what the target is doing:

The target is...What the interrupt does
In Thread.sleep, Object.wait, Thread.joinWakes it with InterruptedException; the flag is cleared
In BlockingQueue.put or take, Condition.await, Lock.lockInterruptibly, Future.get, CountDownLatch.await, Semaphore.acquireWakes it with InterruptedException; the flag is cleared
Running ordinary codeNothing, until the code checks Thread.currentThread().isInterrupted()
Waiting to enter a synchronized block, or in Lock.lock()Nothing: it keeps waiting, and the flag stays set
Blocked in a classic java.io stream or socket read (on a platform thread)Nothing; close the stream or socket from another thread to unblock it. (Java 21 virtual threads are the exception for java.net.Socket: an interrupt closes the socket and the read throws.)
Blocked on an NIO interruptible channelThe channel is closed and the thread gets ClosedByInterruptException

Two details trip people up. First, the flag is sticky: if the interrupt arrives before the thread reaches sleep or take, that call throws immediately. A request is never lost because nobody was waiting yet, which is the opposite of a notify. Second, there are two ways to read the flag: isInterrupted() only reads it, while the static Thread.interrupted() reads it and clears it.

In the C++ version, std::this_thread::sleep_for cannot be woken early, so the worker "sleeps" by waiting on a std::condition_variable_any with its std::stop_token: the predicate is false because there is nothing to wait for except the timeout or a stop request. That is the C++ spelling of an interruptible sleep.

Catching InterruptedException: propagate or restore, never swallow

Interruption is a request aimed at whoever owns the thread: a pool's worker loop, or the code that created it. Most code is just a task running on a thread it does not own. So when a task catches InterruptedException, it has two correct choices:

  1. Propagate it. Declare throws InterruptedException and let callers decide. This is the default for library and helper methods.
  2. Restore the flag and return promptly, when you cannot throw it (inside Runnable.run, for example): call Thread.currentThread().interrupt() so the code that owns the thread still sees the request.

Swallowing it, an empty catch, erases the request: the flag was cleared when the exception was thrown, so the pool that sent it will never know. Only the code that owns the thread's cancellation policy may consume an interrupt, as the worker above does when it exits.

C++20: stop sources, stop tokens and stop callbacks

C++20 turned the stop flag into a small toolkit for cooperative cancellation:

  • std::stop_source is the sending side: request_stop() makes the request (once; it returns true only for the call that made it).
  • std::stop_token is the receiving side, a cheap copyable view: stop_requested() tells the running code whether to stop. Many tokens can watch one source, so one request can stop a whole group of tasks.
  • std::stop_callback registers a function that runs synchronously in the thread making the stop request, or in the registering thread if stop was already requested. To wake a plain condition variable safely, the callback must coordinate a stop predicate under the waiter's mutex before notifying. Notification alone can be lost. Never request stop while holding a mutex that a callback needs.
  • std::jthread owns a stop source. If its function takes a std::stop_token as the first parameter, the jthread passes one in; its destructor calls request_stop() and then join().
  • std::condition_variable_any has wait, wait_for and wait_until overloads that take a token. They return the predicate's value: false from the untimed wait means stop was requested while the predicate stayed false; from a timed wait it can also mean timeout. A true predicate can win even when stop was requested, so check the stop state explicitly if cancellation should take priority over queued work.
C++

Before C++20, interviewers expect a hand-made version: put the stop flag inside the condition variable's predicate, set it while holding the mutex, then notify_all(). Setting an atomic flag without the mutex is a classic lost wakeup: a waiter can check the predicate (false), then you set the flag and notify, and only then does the waiter go to sleep, forever.

Cancelling a task that runs somewhere else

With executors you do not hold the thread, you hold a future. Java's Future.cancel(mayInterruptIfRunning) attempts cancellation and can fail, for example if the task already completed. For a successfully cancelled FutureTask, a task that has not started will not run, while true requests interruption if it is running. Successful cancellation makes isCancelled() true and get() throw CancellationException; it does not prove the worker has stopped.

std::future has no cancel at all. You pass a stop token into the task and check it there. The same design works in Java with a flag or a token object of your own. A CompletableFuture also needs a separate cancellation mechanism for its underlying work, because its cancel(true) does not interrupt that work.

What to do when the request arrives

A stop request is a reason to finish soon, not a reason to abandon shared data mid-update. Check for it only between whole units of work, never between two writes that must happen together. When you do stop:

  • Leave every invariant intact: finish or roll back the operation in progress.
  • Release what you hold: locks (RAII or finally), files, connections.
  • Decide what happens to unfinished work: return it (as shutdownNow returns unstarted tasks), log it, or hand it to someone else.
  • Exit promptly. The time between the request and the exit is your cancellation latency, set by how often you check and how long your waits can last.

Worked example: shutdownNow for a hand-built pool

Rubrik often bans library executors and then grades your shutdown. A reported 2026 screen judged "shutdown semantics, thread interrupts" and which exceptions were caught. Here is the shape of shutdownNow that survives the follow ups. It does three things, in this order:

  1. Change the state to stopped, under the pool's rules, so new submissions are refused and every worker loop will exit.
  2. Wake every worker: interrupt in Java, request_stop in C++. Idle workers wake up from their wait; workers running a task pass the request to it.
  3. Drain the queue and return the tasks that never started, so the caller can decide what to do with them.

Why the Java loop checks state and not only the interrupt flag: a task might swallow the interrupt. With the state check, the worker still exits as soon as that task returns. And because the flag is sticky, a worker that read the old state and is just about to call take() cannot miss the request: take() throws at once. In C++, a task that should stop early needs the token passed in; the queue wait is already stop-aware. Graceful shutdown (finish the queued work first) and awaitTermination complete the picture in build a thread pool.

Common mistakes

  • Swallowing InterruptedException. An empty catch, or a log line and carry on. Propagate it, or restore the flag and return.
  • catch (Exception e) around a blocking call inside a loop. It catches InterruptedException too, logs it, and loops back into the wait with the flag now cleared. Catch InterruptedException separately and exit.
  • Checking with Thread.interrupted() when you meant isInterrupted(). The static method clears the flag, so the next check, or the owner's, sees nothing.
  • A plain boolean stop flag. The worker may never see it. Use volatile, AtomicBoolean or std::atomic<bool>.
  • Expecting interrupt() to unblock synchronized, lock() or socket reads. It does not. Use lockInterruptibly, timed waits, or close the resource.
  • In C++, waiting on a plain std::condition_variable and expecting request_stop() to wake it. Use std::condition_variable_any with the token, or a flag in the predicate plus notify_all, set under the mutex.
  • Checking for a stop between two writes that belong together. Check between whole operations so you never exit with an invariant broken.

In the interview

This is asked as a follow up the moment you have a worker loop: "how does your pool shut down?", "what does shutdownNow do to a task that is running?", "what if a task ignores interrupts?". Rubrik reports grade shutdown versus shutdownNow and interrupt handling directly, and LinkedIn concurrency rounds have asked for a producer and consumer with graceful shutdown.

Neither Java nor C++ can kill a thread safely, so cancellation is cooperative: I request a stop, and the code checks for it between units of work and when it waits. In Java that is an interrupt, which also wakes blocking calls; in C++20 a stop token with a stop-aware wait. My worker loop checks the pool's state as well as the interrupt, so one task that swallows the interrupt cannot keep the pool alive.

Follow ups to expect: "What is the difference between interrupted() and isInterrupted()?" "What happens if the interrupt arrives before the thread starts waiting?" (it throws as soon as it waits; the flag is sticky). "Which blocking calls ignore interrupts?" (synchronized entry, lock(), classic I/O). "How do you cancel a std::future?" (you cannot; pass a stop token into the task). "What does shutdownNow return?" (the tasks that never started).

Senior depth

Cancellation policy belongs to the thread's owner. A task should behave as a guest: propagate or preserve the interrupt and leave the decision to the code that owns the thread. This is why library code must never swallow InterruptedException, and why a pool clears a leftover interrupt before giving its worker the next task.

Timeouts are not cancellation. When a caller's get(2, SECONDS) times out, the task is still running and still using a thread, a connection and memory. Under load, abandoned work piles up unless the timeout path also cancels it. Saying "on timeout I cancel the future, and the task checks for interruption at each I/O boundary" is a strong senior signal.

The same idea everywhere. Go's context.Context, .NET's CancellationToken and Kotlin coroutine cancellation are all cooperative: a request travels with the work, and the work checks it. C++ stop tokens are the closest relative; Java's interrupt is the same contract, attached to the thread instead of to the task.

Key takeaways

  • No safe kill exists: Thread.stop is gone and C++ never had one. Cancellation is a request the code checks.
  • interrupt() sets a sticky flag and wakes interruptible waits with InterruptedException, clearing the flag; synchronized, lock() and classic I/O ignore it.
  • When you catch InterruptedException, propagate it or restore the flag. Never swallow it.
  • C++20: std::jthread, std::stop_source, std::stop_token, std::stop_callback, and std::condition_variable_any waits that wake on a stop.
  • Check for stops between whole units of work, keep invariants intact, and make pool loops trust their own state, not just the interrupt.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A worker runs while (!stop) { doWork(); }, where stop is a plain boolean field (not volatile, not atomic). Main sets stop = true. What can happen?
Why. Without volatile or an atomic there is no guarantee the worker ever re-reads memory: the compiler may hoist the read out of the loop. That is a visibility bug, and in C++ an unsynchronized write and read of the same variable is a data race, which is undefined behavior. "Eventually visible" is not a promise either language makes for plain fields.
Why do Java and C++ give you no safe way to kill another thread?
Why. The danger is broken invariants: a thread killed between two related writes leaves the data inconsistent. Operating systems can stop threads, but the language cannot make that safe. Thread.stop() throws UnsupportedOperationException since Java 20, and std::thread has no such member.
A stop request (Java interrupt(), or C++ request_stop() with a stop-aware wait) arrives while the worker is still computing, before it reaches its next blocking wait. What happens when it reaches that wait?
Why. Interrupts and stop requests are state, not signals: they stay set until someone handles them, so a late wait still sees them. That is the key difference from notify, which wakes only threads that are already waiting and is lost otherwise.
You cancel a task (Future.cancel(true) in Java, or request_stop() on the token it was given in C++) while it is running a tight CPU loop that never checks for cancellation and never blocks. What happens?
Why. Cancellation is cooperative. In Java the interrupt sets a flag that only interruptible calls and explicit checks react to. In C++ the token's state changes, and nothing happens until the code calls stop_requested(). Long CPU loops should check every so many iterations.
A worker has debited account A and not yet credited account B when it notices a stop request. What should it do?
Why. Cooperative cancellation exists to keep invariants intact. Leaving money debited but not credited is exactly the damage Thread.stop used to do. Holding a lock forever is not a fix: every other thread then blocks on it.
Java onlyWhat does this print?
Why. The static Thread.interrupted() returns the flag and clears it, so the second call sees false, and so does isInterrupted(), which only reads. Using interrupted() as a casual check is a common way to lose a cancellation request.
C++ onlyA std::jthread runs a loop that waits on a plain std::condition_variable for !queue.empty(). Main calls request_stop() while the queue is empty, and then the jthread object is destroyed. What happens?
Why. request_stop() changes the stop state and runs registered callbacks; it does not automatically notify a plain condition variable. Spurious wakeups cannot help because the predicate still rejects the empty queue. Use condition_variable_any::wait(lock, token, pred), or set a stop flag under the waiter's mutex and notify all. A callback using the latter protocol must follow the same locking rule.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a worker that runs jobs from a queue until it is told to stop, and that stops promptly even while it is waiting for a job. A failing job must not kill the worker. Java: a thread, a BlockingQueue and interruption. C++: a std::jthread, your own queue and a stop-aware wait.
Model answer

In Java, take() is interruptible and its InterruptedException escapes the loop. Jobs must preserve interruption; a job that swallows it needs a separate owner-controlled stop flag, as in the pool example. In C++, the token-aware wait wakes an idle worker, and the explicit stop check prevents draining queued jobs after cancellation. Neither version can forcibly stop a running job. Jobs run outside the queue lock. The std::jthread member is declared last, so its dependencies are constructed before it starts and remain alive until it has stopped and joined.

Explain
An interviewer says: "Your shutdownNow interrupts every worker, yet one worker never exits. What could cause that, and how do you make shutdown robust?"
Model answer

Four likely causes. A task swallowed the interrupt, so the flag was cleared and a loop that only watches the flag goes back to waiting. The worker loop has a catch (Exception e) around take() that catches InterruptedException, logs it and loops. The thread is blocked in something interrupts cannot reach: entering a synchronized block, Lock.lock(), or a classic socket or stream read. Or a task is in a CPU loop that never checks.

To make it robust: keep a pool state field (RUNNING, SHUTDOWN, STOP) that every worker loop checks, so the interrupt is a wake-up call and not the only signal. Catch InterruptedException separately from task failures. Inside tasks, propagate or restore interrupts, use lockInterruptibly or timed waits, and close sockets to unblock I/O. Finally, awaitTermination with a timeout, and if it expires, report the stuck worker with a thread dump instead of hanging the caller. In C++ the same points apply with stop tokens: stop-aware waits, a state flag set under the mutex, and tasks that receive and check the token.

Debug
Why does this worker never stop when the pool calls shutdownNow(), and how do you fix it?
Model answer

shutdownNow() interrupts the worker. If it is waiting in take(), take() throws InterruptedException and clears the flag. Because InterruptedException is a subclass of Exception, the catch logs it as a "job failed" warning and the loop calls take() again, now with no flag set, so the worker waits forever. Even the while (true) gives it no way out.

Fix: separate the two failure kinds. Wrap only job.run() in catch (RuntimeException e) so a bad job is logged and the worker continues; let InterruptedException from take() end the loop (catch it outside the loop, restore the flag, and return). Better still, loop on the pool's state so a job that swallows an interrupt cannot keep the worker alive either. The C++ cousin of this bug is a wait that cannot see the stop: a plain std::condition_variable, or an atomic stop flag set without holding the mutex, which loses the wake-up.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"I interrupted a Java worker. It logged an exception and went straight back to waiting on its empty queue. What happened?"
What a strong answer covers
  • The queue wait threw InterruptedException and cleared the interrupt status
  • A broad catch inside the loop treated cancellation as a task failure and resumed waiting
  • Propagate interruption from helpers, or restore the flag and return when propagation is impossible
  • The thread owner may consume the interrupt only as part of its explicit cancellation policy
  • Separate task failures from cancellation and make a pool's stop state survive a task swallowing an interrupt
How a senior would say it
The worker probably swallowed its cancellation request. An interruptible queue wait throws an interrupted exception and clears the thread's interrupt status. If a broad catch logs that exception and continues the loop, the next wait sees neither an item nor an interrupt and can block again. I would separate cancellation from ordinary task failure. A helper that can throw should propagate the interrupted exception. A runnable that cannot propagate it should restore the current thread's interrupt status and return promptly. Restoring and then blindly retrying the same interruptible wait can create a busy loop, so restoration alone is not a policy. The code that owns the worker may consume the interrupt if it deliberately exits or otherwise handles the request. For a pool, I would also keep a separate stop state that each worker checks between tasks. That way a task which accidentally clears the flag cannot send the worker back to idle waiting after the task returns. This still cannot stop a task that never returns. Cancellation requires cooperation inside the task as well as in the worker loop.

Likely follow up: What changes if the worker is waiting to enter a synchronized block instead of waiting in take()?

Out loudabout 75 s
"My C++ jthread destructor hangs even though it requests a stop. The worker is waiting on an empty queue. What would you change?"
What a strong answer covers
  • The destructor requests cancellation and joins; it does not forcibly terminate the worker
  • A plain condition variable wait does not observe the jthread's stop token
  • Use a C++20 condition_variable_any wait with that token and a queue predicate
  • Define whether stop wins over queued work, since the wait can return true when work is available despite cancellation
  • For C++17, protect the stop predicate with the wait mutex and notify all; check running tasks too
How a senior would say it
I would make the queue wait observe the stop request. A jthread destructor requests cancellation and then joins; it does not kill the worker. If the worker is sleeping on a plain condition variable whose predicate only checks for a job, an empty queue can keep that join waiting forever. In C++20 I would use a condition variable any wait with the worker's stop token and the queue predicate. That lets an idle worker wake and return when cancellation is requested. I would also define what happens when cancellation and queued work are both present. The wait returns the predicate's value, so true does not mean there was no stop request. For immediate shutdown, I check the stop state before claiming another job. In C++17 I would put a stopping flag in the predicate, set it under the same mutex, and notify all waiters. That prevents a request from falling between checking the predicate and going to sleep. Finally, a worker already running a job needs cancellation checks inside that job; fixing the queue wait only fixes idle shutdown.

Likely follow up: Can you hold the queue mutex while requesting a stop if a registered stop callback also takes that mutex?

Out loudabout 90 s
"A request times out while its background task is transferring money. Design cancellation so the caller returns promptly without corrupting the accounts."
What a strong answer covers
  • A caller timeout and task cancellation are separate events; neither is proof of worker termination
  • Java cancellation can request interruption; C++ needs an explicit token, and neither stops an uncooperative CPU loop
  • Check cancellation at invariant-preserving boundaries; finish or roll back a partly applied transfer
  • Make blocking operations cancellation-aware and bound work between checks
  • Retain ownership through cleanup and joining, even if the response returns earlier
  • Define the operation's reported outcome because cancellation does not prove its side effects were undone
How a senior would say it
I would treat the timeout as the caller's deadline and cancellation as a separate request to the task. Neither proves the task has stopped. In Java, cancelling an executor future with interruption enabled can ask the running task to stop. In C++, I would pass a stop token explicitly. A tight loop that never checks either signal will continue running. The transfer must observe cancellation only at a safe boundary. If it has debited one account, it must complete the credit or undo the debit before releasing the lock and exiting. I would release resources through structured cleanup and make blocking operations interruptible, stop-aware, or bounded by deadlines. Cancellation latency then depends on the longest unit of work and wait between checks, so I would keep those bounded. If the caller must return before cleanup finishes, a longer lived owner must retain the task, its data and responsibility for joining it. Finally, I would define what the timeout means to the caller. A timeout or cancelled future is not proof that the money never moved. The operation needs a recorded outcome, and retries may need an idempotency key. Promptly returning an error and safely finishing the underlying operation are two different responsibilities, and both need an owner.

Likely follow up: What does Java Future.get() report after successful cancellation if the task ignores interruption and later performs its side effect?
