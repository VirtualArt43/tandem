Print FooBar alternately

Ordering puzzleswarm-up20 minLeetCode 1115

Two threads taking strict turns: the ping-pong at the heart of every handoff. It is also where most people first meet the lost wakeup, because the obvious wait and notify version deadlocks whenever the wrong thread gets there first.

The task

One FooBar object is shared by two threads. Thread A calls foo(), which prints foo n times; thread B calls bar(), which prints bar n times. Make them take turns so the output is foobar repeated n times, whichever thread starts first.

For n = 2 the output is foobarfoobar. Each method receives the printing as a callback: printFoo.run() in Java, printFoo() in C++.

Rules:

  • A thread waiting for its turn must block, not spin. The tests check it.
  • No sleep to arrange the turns.
  • Each object serves one run of the two methods. The tests create a fresh object for every round.
  • In C++, ThreadSanitizer must stay quiet.

What the tests check

  • With only the bar thread started, nothing is printed for 200 ms and the thread is blocked, not spinning (Java: its state is not RUNNABLE; C++: the process uses almost no CPU and makes almost no context switches). Then foo starts and the output is exactly right.
  • Exact output for n = 1, 2, 5, 100 and 1000, with the foo thread started first and with the bar thread started first: 100 rounds for the small values of n, fewer for the large ones, rotating through three start styles (one after another, 1 ms apart, released together from a gate).
  • No round hangs (2 s per round in Java, 3 s in C++, stretched on a busy machine), no exceptions, and in C++ no ThreadSanitizer report.

Taught in: Making threads take turns

Open them one at a time. Each one gives away a little more.

There is exactly one turn, and it moves back and forth. What object can hold "it is your turn" so that a thread can sleep until it gets it, and so that a turn handed over before anyone is waiting is not lost?
Two semaphores: fooTurn starts with one permit, barTurn with zero. foo acquires fooTurn, prints, releases barTurn. bar acquires barTurn, prints, releases fooTurn. A permit released early simply waits in the semaphore, so no handoff is ever lost.
Without semaphores: one lock, one condition and a boolean fooTurn = true. foo waits while (!fooTurn), prints, sets fooTurn = false and notifies; bar is the mirror image. The flag is what makes it safe: a thread that arrives late sees the flag and does not wait at all.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why does wait() and notify() with no flag deadlock?
A notify only wakes threads that are already waiting; it is not remembered. If foo prints and calls notify() before bar has reached wait(), the notify goes nowhere, foo then waits for bar, and bar waits for a notify that already happened. Both sleep forever. The fix is state: wait only while a condition you can check (the turn flag) says you must, and change that state before notifying. A semaphore is exactly such a remembered signal.
Would spinning on a volatile boolean (or std::atomic<bool>) be acceptable?
It is correct, but each waiting thread burns a core for the whole run, and on a loaded machine the spinner steals CPU from the thread it is waiting for, so it can be slower than blocking. Interviewers treat it as a red flag unless you explain that the waits are microseconds long. A plain boolean is wrong outright: the JIT may hoist the read in Java, and in C++ it is a data race.
What does a semaphore give you here that a mutex does not?
A semaphore has no owner: one thread acquires and another releases, which is precisely a handoff. A mutex must be unlocked by the thread that locked it, so "foo locks, bar unlocks" is undefined behavior in C++ and throws IllegalMonitorStateException for a ReentrantLock in Java.
Now there are three threads: foo, bar and baz, in that order.
Generalize the token: either a turn counter 0, 1, 2 with one lock and notifyAll, or three semaphores in a ring where each thread releases the next one's semaphore. The ring wakes exactly the right thread every time, while one shared condition with notifyAll wakes everyone and lets the wrong ones go back to sleep. That is the round robin printer problem.
How many context switches does this cost, and can you reduce them?
Strict alternation needs about one switch per word, about 2n in total, because every print hands the turn to the other thread. You cannot batch without changing the problem. What helps is a short spin before blocking, since the other side often answers within microseconds; Java's locks and the C++20 semaphore in libc++ already spin briefly before parking.
Add stop(), which makes both threads return early.
Add a stopped flag under the same lock. Each wait condition becomes "my turn or stopped", and each thread returns when it sees stopped. stop() sets the flag and wakes both threads (notifyAll, or release both semaphores). Without the wakeup, a thread blocked waiting for its turn would never see the flag.

The idea

There is one turn token and it travels back and forth. The reference uses two binary semaphores as the two places the token can be: fooTurn starts with the token, barTurn empty. The invariant is at any moment at most one permit exists across the two semaphores: whoever holds it prints, then puts it in the other thread's semaphore. So the words alternate, and the first word is always foo.

Why each line is there

  • fooTurn starts at 1, barTurn at 0. That single choice decides who goes first. Starting both at 1 lets bar print first, or print twice in a row.
  • Acquire before printing, release the other side after. The release happens after the print, so the print is visible to the other thread before it can run: a semaphore release happens-before the acquire that takes the permit.
  • A release before anyone waits is kept. If foo releases barTurn before the bar thread even starts, the permit sits there and bar takes it at once. That is the property the plain wait and notify version lacks.
  • The loop count is fixed at n. Each side does exactly n acquires and n releases, so both methods return, and the last release (bar's) simply leaves a permit nobody needs.

With exactly two threads, notify (notify_one) would also be safe here, because the only possible waiter is the other thread. notifyAll costs nothing extra and stays correct if a third thread is ever added.

Pitfalls

  • wait and notify with no state. The lost wakeup above: it works when bar happens to start first and deadlocks when foo does. The tests start foo first on purpose.
  • Both semaphores starting at 1. bar can print first or twice in a row.
  • Releasing your own semaphore instead of the other one. A one-word slip that turns the handoff into each thread racing alone.
  • Spinning on a flag. Correct only with volatile or std::atomic, and still wasteful; a plain flag is a data race.

How to say it in the interview

There is a single turn that alternates, so I'll model it as a token in one of two semaphores: fooTurn starts with one permit and barTurn with none. Foo acquires its permit, prints and releases bar's; bar does the mirror image. A permit released before the other thread arrives is remembered, so there is no lost wakeup, and the release happens-before the acquire, so each print is visible to the other side. Without semaphores I'd use one lock, a fooTurn flag and a condition, always waiting in a loop on the flag.
