Exceptions, InterruptedException and try-with-resources

Checked and unchecked exceptions, finally and try-with-resources, the interrupt protocol, and why exceptions vanish inside threads and executor tasks.

Asked atRubrik
Before this:Lambdas, functional interfaces and method references

In threaded Java, exceptions decide three things that interviewers grade: whether a lock is released when something fails, whether a cancelled thread actually stops, and whether a failed task is ever noticed at all.

In plain words

Think of a restaurant kitchen. A cook who drops a pan must still turn off the gas before walking away. That is finally: the clean-up that happens on every way out, including the messy ones.

When the manager wants to close early, she does not drag cooks away from the stove. She pins a note on the board, and each cook reads it at the next natural pause and wraps up. A cook who reads the note and bins it has made the kitchen impossible to close. That is swallowing an interrupt. And a cook who burns a dish in the back room, with nobody checking, fails silently: the failure happened, but nobody hears about it unless someone comes back and asks. That is an exception inside an executor task that nobody calls get() on.

Why this matters for concurrency

  • Every lock() needs an unlock() in a finally block. One exception between them and the lock stays held forever, and every other thread that needs it waits forever.
  • Common interruptible waits (sleep, join, wait, take, await, Future.get) declare the checked InterruptedException. Other blocking operations may ignore interruption. What you write in that catch block is your code's cancellation policy, and interviewers read it.
  • An exception thrown in another thread never reaches the thread that started it. In a raw thread it kills only that thread; in an executor it sits inside a Future until someone asks. Rubrik interviewers have graded exactly this: which exceptions a hand-built thread pool catches.

Exceptions in five minutes

Everything that can be thrown extends Throwable, and it splits into three families:

FamilyExamplesMust you catch or declare it?What it usually means
Checked: Exception and subclasses, except RuntimeExceptionInterruptedException, IOException, TimeoutException, ExecutionExceptionYes: the compiler rejects code that neither catches it nor declares throwsSomething outside your control happened; the caller should decide
Unchecked: RuntimeException and subclassesNullPointerException, IllegalArgumentException, IllegalStateException, IllegalMonitorStateException, ConcurrentModificationExceptionNoA bug or a broken precondition
Error and subclassesOutOfMemoryError, StackOverflowError, AssertionErrorNoThe JVM or the program is in serious trouble

When something throws, the JVM unwinds the stack one frame at a time until it finds a matching catch, running every finally block on the way. If nothing catches it, the exception ends the thread it was thrown in, and only that thread. For the main thread you see the familiar stack trace, and the program ends once no other non-daemon thread is running.

Three rules hide in that snippet. Pass the original exception as the cause when you wrap, so the stack trace keeps a "Caused by" line. A catch for a subclass must come before a catch for its superclass, or javac rejects the second one ("has already been caught"). And javac rejects a catch for a specific checked exception that the try block cannot throw. Broad catches for Exception or Throwable are allowed because they can also catch unchecked exceptions.

One more rule matters constantly in threaded code: Runnable.run() cannot throw checked exceptions, while Callable.call() can. So new Thread(() -> queue.take()) does not compile ("unreported exception InterruptedException; must be caught or declared to be thrown"), and a task that needs to throw is better written as a Callable.

finally, and why every unlock lives in it

A finally block runs whether the try block finishes normally, returns early or throws. It does not run if the JVM halts (for example through System.exit), or if the thread never leaves the try at all. That makes it the one safe place for releasing a lock:

Why does lock() go before the try and not inside it? If acquiring the lock fails, for example lockInterruptibly() throwing InterruptedException, a finally around it would call unlock() on a lock this thread does not hold. That throws IllegalMonitorStateException, which replaces and hides the exception you actually needed to see. Here is the leak this idiom prevents:

Two finally traps to avoid. A return inside finally silently discards an exception that is in flight. And an exception thrown inside finally replaces the original one. Keep finally blocks tiny: unlock, close, count down, nothing that can fail.

try-with-resources and AutoCloseable

try-with-resources is finally written for you. Any object whose class implements AutoCloseable can be declared in the parentheses, and Java calls its close() on every path out, in reverse order of declaration. It also fixes the second finally trap: if the body throws and close() throws too, the close failure is attached to the body's exception as a suppressed exception instead of replacing it. Java developers use it the way C++ developers use RAII.

Since Java 19, ExecutorService is AutoCloseable too. Its close() stops accepting tasks and waits for the submitted ones to finish; if the waiting thread is interrupted, it calls shutdownNow(), keeps waiting for the running tasks, and restores the interrupt flag before returning. In Java 21 this is the tidiest way to run a batch:

Keep the futures. close() waits for executor termination, but it never reports individual task failures. If close is interrupted, its shutdownNow() can remove queued tasks without completing their futures in a ThreadPoolExecutor. The interrupt check above cancels outstanding futures and propagates the cancellation instead of risking an indefinite get() on work that never ran. A task that ignores interruption can still keep close waiting forever.

What about a lock guard?

You can wrap a ReentrantLock in a small AutoCloseable class and write try (var g = guard.lock()) { ... }, like std::lock_guard in C++. It works, but in an interview write the plain lock(), try, finally unlock(). Every reviewer recognizes it at a glance, and it is one less class to explain.

InterruptedException and the interrupt protocol

Java has no safe way to kill a thread. Instead every thread carries an interrupt status, a flag that other threads can set to ask it to stop:

  • t.interrupt() sets the flag on thread t. It is a request, not a command.
  • The common waits listed here respond to interruption by clearing the flag and throwing InterruptedException. Many check an already-set flag before waiting, so an interrupt between waits can still be observed. Do not assume every call must throw whenever the flag is set: for example, FutureTask.get() can return an already completed result without waiting or consuming the interrupt. Interruptible waits include Thread.sleep, Thread.join, Object.wait, BlockingQueue.put and take, Condition.await, Lock.lockInterruptibly, Future.get, CountDownLatch.await and Semaphore.acquire.
  • If t is running ordinary code, nothing happens until it looks. Thread.currentThread().isInterrupted() reads the flag. The static Thread.interrupted() reads it and clears it, which surprises people.
  • Some waiting ignores interrupts: waiting to enter a synchronized block, lock.lock(), and a classic blocking read on a java.io socket stream in an ordinary platform thread. Interrupting a thread stuck there only sets the flag; the thread notices once it gets past.

When you catch InterruptedException, you have exactly two honest moves, and one forbidden one:

  1. Propagate it. Declare throws InterruptedException and let the caller decide. This is right for the methods of a blocking component: take(), put(), await().
  2. Restore the flag and stop. When you cannot throw, as inside Runnable.run(), call Thread.currentThread().interrupt() to put the flag back, then finish promptly.
  3. Never swallow it. An empty catch, or e.printStackTrace() followed by carrying on, loses the request for good, because throwing the exception already cleared the flag. After that, shutdownNow() cannot stop your thread, and nothing above you can tell that a stop was requested.

When the interrupt arrives during these sleeps, the swallower completes all 5 rounds with its flag cleared, while the polite worker stops, usually after 1 round, with its flag restored. The sleep in main only makes that timing likely; a busy machine can delay main until a worker has finished, so the exact round counts and flag observations are not guaranteed. Exceptions inside threads and executor tasks

Where an exception is thrown decides who, if anyone, ever hears about it:

The termination wait ensures the task has finished before we inspect its future; elapsed sleep time alone would not prove that. Delete the get() call and the program prints nothing about row 42 at all. A Future that nobody inspects is a place where failures go to disappear.

Which exceptions a hand-built pool must catch

In a 2026 Rubrik report, the candidate built a thread pool by hand, and the interviewer judged which exceptions the pool caught; catching InterruptedException plus Exception was not enough. The report does not say what was missing, so here is a complete list you can check your own pool against:

  1. Choose and implement a worker failure policy. For a pool that captures every task failure in a future and keeps serving, catch Throwable around the task, not only Exception. An AssertionError or StackOverflowError otherwise escapes that catch and can end the worker; capacity stays reduced unless the pool replaces it. The JDK's FutureTask catches Throwable. Capturing a failure is not a promise that recovery from every VM error is safe.
  2. Report the failure. Complete the task's future exceptionally, or pass the failure to a handler. Never drop it.
  3. InterruptedException while waiting for work is not a task failure; it is the shutdown signal. Restore the flag and leave the loop.
  4. Do not leak one task's interrupt into the next. If the pool is not shutting down, clear the flag with Thread.interrupted() before taking the next task. ThreadPoolExecutor does this between tasks.

Worked example: review this uploader

A teammate's worker thread takes files from a queue and uploads them. Find the bugs before reading on.

There are four. One: if upload throws, unlock() never runs and the stats lock is held forever. Two: that same unchecked exception is not caught at all, so it escapes run() and kills the worker. Three: the interrupt is swallowed, so a shutdown can never stop this thread; it just goes back to take(). Four: the slow upload runs while holding the lock, so every thread that wants the stats waits for the network.

Say the four fixes in that order in an interview: release in finally, contain per-item failures, honor interrupts, and keep slow work out of the critical section.

Common mistakes

  • lock() inside the try, or no finally at all. Write lock.lock(); try { ... } finally { lock.unlock(); } every time.
  • Swallowing InterruptedException. An empty catch, or a log line and carry on. Propagate it, or restore the flag and stop.
  • Wrapping it without restoring the flag. throw new RuntimeException(e) alone loses the interrupt. If you must wrap, call Thread.currentThread().interrupt() first.
  • Checking with Thread.interrupted() when you meant isInterrupted(). The static method clears the flag as it reads it.
  • Submit and forget. No get(), no callback, no handler: the exception sits in the Future forever.
  • Catching only Exception around tasks in a hand-built pool. An Error kills the worker and shrinks the pool.
  • return or throw inside finally. Both hide the exception that was already on its way out.
  • Logging only the message of an ExecutionException. Log the full exception, including its cause chain, or inspect getCause(); the underlying failure carries the useful stack trace.
  • Wrapping without the cause. new IllegalStateException("failed") throws away the stack trace you need; pass e as the second argument.

In the interview

Exceptions are rarely the question, but they are graded inside every concurrency answer. Interviewers read your catch blocks the way they read your lock scopes. Rubrik reports mention exception handling being judged in a seat booking problem and in a hand-built thread pool, along with what the pool does on interrupt.

I call lock() just before the try and unlock() in finally, so an exception inside the critical section cannot leave the lock held.
In a Runnable I cannot rethrow InterruptedException, so I restore the interrupt flag and return. Anywhere I can, I declare it and let the caller decide.
Each task in my pool runs inside a catch of Throwable: the failure goes into that task's future and the worker keeps serving. An InterruptedException from the queue is the shutdown signal, not a task failure.

Follow ups to expect. "What happens to an exception thrown by a task you submitted?" (it is stored in the Future; get() throws ExecutionException). "How does shutdownNow stop running tasks?" (it interrupts their threads, so only tasks that respond to interrupts actually stop). "What if a task ignores interrupts?" (then nothing can stop it safely; awaitTermination times out, and the fix is in the task). "Why catch Throwable and not Exception?" (so an Error from one task cannot silently kill a worker). "A scheduleAtFixedRate job stopped running and nothing was logged. Why?" (one run threw; the exception went into its ScheduledFuture and every later run was suppressed, so catch inside the task body).

Senior depth

  • CompletableFuture.cancel(true) does not interrupt anything. Its documentation says the flag has no effect because interrupts are not used to control its processing. If a task must be stoppable, run it on an executor whose Future you can cancel, or check a cancellation flag inside the task.
  • Interrupted while waiting in future.get()? Only your wait ends; the task may keep running. If you no longer need the result, future.cancel(true) requests cancellation and, for a running standard executor task, attempts interruption. Success depends on the future implementation, timing and the task's cooperation; it does not force termination.
  • Interruptible locking is a design choice. lock() ignores interrupts; lockInterruptibly() and tryLock(timeout, unit) respond to them. Blocking components that use them can be cancelled while waiting for the lock itself.
  • Stack traces of async failures show the worker's stack, not the submitter's. When you wrap an exception at the point where you call get(), add context (which request, which key), because the original trace cannot tell you who asked for the work.

Key takeaways

  • Checked exceptions must be caught or declared; Runnable cannot throw them, Callable can.
  • lock() goes just before try, and unlock() goes in finally. try-with-resources closes in reverse order and keeps close failures as suppressed exceptions.
  • Interrupting is a request. Blocking calls throw InterruptedException and clear the flag, so propagate it, or restore the flag and stop. Never swallow it.
  • An exception in another thread never reaches the thread that started it. In an executor it waits in the Future until someone calls get().
  • A hand-built pool catches Throwable around each task, reports the failure, and treats an interrupt while waiting as the signal to shut down.

Quick check

Answer each question, then read why. Your score is saved for your module test.

lock is a ReentrantLock. Thread A runs this method with amount larger than balance. What happens when thread B calls withdraw afterwards?
Why. A ReentrantLock is released only by an explicit unlock(), and the throw skipped it. Thread A still owns the lock, so B and every other thread wait forever (only A itself could get back in, because the lock is reentrant). Only synchronized releases automatically on an exception; that is why unlock() belongs in finally.
A worker runs this loop. Main calls worker.interrupt() while the worker is blocked in take(). What happens?
Why. An interruptible call clears the interrupt flag when it throws InterruptedException. The catch only logs, so when the loop condition runs, the flag is false and the worker goes back to take(). Adding Thread.currentThread().interrupt(); in the catch (or moving the try outside the loop) fixes it.
pool.submit(() -> parse(row)) throws an IllegalStateException inside the task, and the caller never calls get() on the returned future. What is printed?
Why. submit wraps the task in a FutureTask, which catches any Throwable and stores it. It surfaces only when someone calls get(), as an ExecutionException whose cause is the original. Printing plus a replaced worker is what execute does on a ThreadPoolExecutor.
What is the difference between Thread.interrupted() and Thread.currentThread().isInterrupted()?
Why. The static Thread.interrupted() returns the flag and resets it to false, so a second call returns false. Use isInterrupted() to check without changing anything, and interrupted() only when you deliberately consume the request, as a pool does between tasks.
The run() method of a plain thread throws a RuntimeException. The main thread had called t.join(). What does main experience?
Why. An uncaught exception ends only the thread it was thrown in. The default handler prints the trace, but join() just reports that the thread finished. To learn about the failure, install an uncaught exception handler, record it inside run(), or use an executor and Future.get().
In try (Resource a = open("a"); Resource b = open("b")) { body(); }, the body throws exception X, and then b.close() throws exception Y. What does the caller catch?
Why. Resources close in reverse order of declaration, and a failure in close() is added to the primary exception with addSuppressed, so e.getSuppressed() returns Y. A hand-written finally that throws would replace X instead, which is the classic bug try-with-resources fixes.
A hand-built pool's worker wraps each task in try { task.run(); } catch (Exception e) { report(e); }, with no outer handler or worker replacement. One task overflows the stack and throws StackOverflowError. What happens?
Why. StackOverflowError is an Error, not an Exception, so it escapes the catch and ends the worker's run(). Unless the pool notices dead workers and replaces them, capacity silently shrinks. Catching Throwable around the task, as FutureTask does, keeps the worker alive and lets you report the failure.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write the loop that each worker thread of a hand-built thread pool runs. Tasks come from a BlockingQueue<Runnable>; a failing task must not kill the worker; shutdownNow interrupts the workers.
Model answer

Why each part. An interrupt while waiting for work is the shutdown signal, so with stopping set I restore the flag and return; it is never treated as a task failure. Catching Throwable keeps the worker alive through an Error and makes sure the failure is reported, the way FutureTask stores it in the future. After each task I clear any interrupt that was aimed at that task (for example a cancel(true)), so it cannot make the next take() throw, and I re-check stopping after clearing so a shutdown that arrived at the same moment is not erased. ThreadPoolExecutor does the same clear and re-check between tasks. The order matters: shutdownNow() writes the volatile stopping before calling interrupt(), and a thread that sees the interrupt is guaranteed to see that write. The loop condition checks stopping before every take() because a badly written task may swallow the shutdown interrupt; without that check the worker would go back to take() and wait forever on an empty queue. ThreadPoolExecutor checks its run state before each wait for the same reason.

If the pool only ever interrupts workers to shut them down, a simpler version is fine in an interview: restore the flag and return from the catch, and keep the while (!stopping) check. The extra lines are what you add when individual tasks can be cancelled with an interrupt.

Debug
A teammate wrote catch (InterruptedException e) { e.printStackTrace(); } inside a Runnable that loops on queue.take(). The service now hangs on shutdown. Explain why, and fix it.
Model answer

Shutdown calls shutdownNow() or interrupt(), which sets the worker's interrupt flag. take() wakes up, clears the flag and throws InterruptedException. The catch prints the trace and the loop calls take() again, which blocks: the only record of the stop request was the flag, and it is gone. So the worker never exits, awaitTermination times out, and the service hangs.

The fix is to restore and leave. Either put the try around the whole loop and call Thread.currentThread().interrupt() in the catch, so the exception ends the loop, or keep the catch inside the loop and return after restoring the flag. If the worker must finish its current item first, it can remember the interrupt and exit after that item, but it must still restore the flag.

Explain
Explain, step by step, what happens when a task submitted to an ExecutorService throws, and how the code that submitted it finds out.
Model answer

submit wraps the task in a FutureTask and returns it as a Future. A worker thread calls the task; the task throws; FutureTask.run catches the Throwable and stores it as the outcome, marking the future done. The worker thread is unaffected and goes back for the next task. Nothing is printed.

The submitter finds out only by asking: future.get() throws ExecutionException, and getCause() returns the original exception. If nobody calls get(), the failure is lost. With execute instead of submit, there is no future: on a ThreadPoolExecutor the exception escapes the task, the worker thread dies after afterExecute, the pool starts a replacement, and the thread's uncaught exception handler prints it. With CompletableFuture, the exception completes the future exceptionally, dependent stages complete exceptionally as well, and join() throws CompletionException unless a stage such as exceptionally or handle recovers.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 80 s
"Shutdown hangs even though we interrupt the worker. Its catch block logs InterruptedException and loops back to queue.take. What is happening, and how would you fix it?"
What a strong answer covers
  • Interruption is a cooperative request, not forced thread termination
  • BlockingQueue.take responds to interruption by throwing and clearing the flag
  • Logging and continuing loses the request and allows the worker to block again
  • Propagate InterruptedException from blocking APIs; in Runnable restore the flag and exit promptly
  • Place the catch outside the loop or return from an inner catch; release resources in finally
  • CPU work must check cancellation, and a real pool should also track shutdown state
How a senior would say it
The worker consumes the shutdown request and then resumes waiting. Interrupting a thread is cooperative; it does not forcibly end execution. When the worker is blocked in take, interruption makes that call throw and clear the interrupt flag. The catch logs the exception but neither restores the flag nor exits, so the next take can block indefinitely. Even a loop condition that checks the flag now sees false. In a blocking library method I would let InterruptedException propagate so the caller owns the cancellation decision. In a Runnable, I would catch it, restore the flag with the current thread's interrupt method, and finish promptly. I can put the catch outside the whole loop or return from a catch inside it. Locks and resources still need cleanup through finally or try-with-resources. Restoring the flag and immediately retrying the same wait would just create repeated exceptions. If processing includes long CPU work, that work also needs cancellation checks. In a real pool I would maintain shutdown state as well, so a task that clears its interrupt cannot accidentally send the worker back to an endless queue wait.

Likely follow up: Why can shutdownNow still fail to stop a task that never waits and never checks interruption?

Out loudabout 80 s
"A submitted task throws, but there is no stack trace and the worker keeps running. Compare that with a raw thread and with ThreadPoolExecutor.execute."
What a strong answer covers
  • Standard executor submission captures task failure in the returned Future
  • Future.get() throws ExecutionException with the original failure as its cause
  • A raw thread's uncaught failure terminates that thread and reaches its handler; join() does not rethrow it
  • A directly executed Runnable that throws can terminate a ThreadPoolExecutor worker
  • Keep and inspect futures or arrange explicit completion reporting
  • ExecutorService.close() waits for termination but does not report individual task failures
How a senior would say it
That is the expected outcome for a task submitted through a standard executor when nobody observes its future. The task wrapper captures the failure, marks the future complete, and lets the worker continue. I would keep that future and call get; it throws ExecutionException, and its cause is the original task failure. With a raw thread, an uncaught exception instead terminates that thread and reaches its uncaught exception handler. Joining the thread only waits for termination; it does not rethrow the failure in the joining thread. With a runnable passed directly to ThreadPoolExecutor.execute, an escaping exception can terminate the worker and reach that handler, and the pool replaces the worker when needed. That distinction depends on what is actually executed: executing a future wrapper still allows the wrapper to capture the failure. My design would make failure observation explicit, through collected futures or a completion reporting path. I would not assume that closing an executor reports task errors. Close manages termination; the individual outcomes still need inspection. Otherwise a batch can finish with missing results and no useful error report.

Likely follow up: What happens to later executions when one run of a scheduled periodic task throws?

Out loudabout 60 s
"The work throws, and closing its resources throws too. Which failure should I see, and how is that different from a finally block that throws?"
What a strong answer covers
  • Try-with-resources preserves the body failure as the primary exception
  • Successfully initialized resources close in reverse declaration order
  • Close failures are attached as suppressed exceptions and inspected with getSuppressed()
  • Without a body failure, the first close failure becomes primary
  • A throwing or returning finally can replace or discard the original failure
  • For explicit locks, acquire before try and release in finally only after successful acquisition
How a senior would say it
With try-with-resources, I should see the work's failure as the primary exception, with close failures attached as suppressed exceptions. Suppose I open resource a, then resource b, and the body fails. Java attempts to close b before a, and still attempts a if closing b throws. I inspect getSuppressed to see cleanup failures without losing the original cause. If the body succeeds, the first close failure becomes primary and later close failures are suppressed onto it. A handwritten finally does not automatically provide that behaviour: throwing from it replaces the exception already in flight, and returning from it can discard that exception entirely. I would therefore use try-with-resources for closeable resources. For an explicit lock, I acquire before entering the try and unlock in finally after successful acquisition. That keeps a failed acquisition from triggering an invalid unlock that hides the real problem.

Likely follow up: If initializing the second resource throws, which resources are closed and which exception remains primary?
