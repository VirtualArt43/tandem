A semaphore starts with 2 permits. Five threads each run acquire(); work(); release();. What is the largest number of threads that can be inside work() at the same moment?
Why. Each thread inside work() holds one permit, and only 2 exist. Fairness changes which waiting thread gets the next permit, not how many permits there are.

A resource limiter accidentally calls release() after a timed acquire returned false. The current count is below the representation limit. What happens?
Why. A semaphore has no owner, so it cannot know who is entitled to release. Java adds a permit unless its integer representation would overflow. C++ requires the count to stay within max(), and violating that is undefined behavior. In a resource limiter this is a bookkeeping bug; a signalling protocol may deliberately release from a thread that never acquired.

Which statement about a binary semaphore and a mutex is true?
Why. A mutex has an owner, while a semaphore does not track who acquired. Both can block callers. A semaphore is not reentrant: a second acquire waits for another release, potentially forever. A wrong-thread mutex unlock is not always diagnosed: it is undefined behavior for std::mutex.

A semaphore starts at 0 and a plain integer x starts at 0. Thread A writes x = 42, then releases once. Thread B successfully acquires once, then prints x. There are no other accesses. What can B print?
Why. The successful handoff orders A's write before B's read, so there is no conflicting unordered access and B sees 42. A release sent before B waits remains available as a permit. Initialising the semaphore to 1 instead would remove this proof: B could pass before A publishes.

A latch starts at 3. Thread A calls countDown() twice, thread B calls it once, and the main thread is blocked in await(). When does the main thread proceed?
Why. A latch counts events, not threads. One thread may report several events; waiters are released when the count reaches zero. Each event still needs exactly one countdown, and C++ forbids exceeding the initial count. Neither a latch nor a barrier identifies threads for you; your protocol must account for the intended events or phase arrivals.

A latch counts one completion per worker. One worker's doWork() throws before its countdown; an outer handler catches the failure and exits that worker without counting down. All others count down once. What happens to the coordinator's untimed wait?

Why do concurrency tests usually release their threads through a start gate latch instead of just starting them one by one?
Why. A thread can finish a microsecond-long operation before the next thread has even started, so a buggy class can pass. Opening a shared gate after all workers check in removes the staggered-start dependency, but the scheduler still chooses when each worker runs. It does not make the test deterministic or fix races; it exposes them.

A barrier is created for 3 parties. Six threads each call await() (or arrive_and_wait()) exactly once. What happens?
Why. A barrier is cyclic: when the third party arrives, the phase completes and the barrier resets. The next three arrivals make up the following phase. Mixing groups like this is usually a bug in real code, but it does not hang or throw.
From: Barriers and phasers
Four tasks, each of which waits at a 4-party barrier, are submitted to a fixed thread pool with 3 threads. What happens?
Why. All blocking parties must be able to reach the barrier; they need enough execution slots, not simultaneous CPU execution. Blocking pool threads on something that requires a task still waiting in the queue is the classic pool self-deadlock. Size the pool to at least the number of parties, or do not run barrier parties as pool tasks.

Java onlyFour threads use a CyclicBarrier(4). Three are waiting in await() when the fourth calls await() with its interrupt flag already set. There is no concurrent reset. What happens to the three?
Why. The fourth caller detects interruption inside await, throws InterruptedException and breaks this generation. The other three get BrokenBarrierException, not an interrupt flag. It neither trips successfully with three arrivals nor waits for a replacement. If the fourth never called await, its interrupt flag alone would not release them; reset instead starts a fresh generation.

C++ onlyFour threads share a std::barrier sync(4). One thread catches an exception from its work and returns normally from its thread function without arriving or dropping. What happens to the other three?
Why. C++ barriers count arrivals only; they neither adjust membership nor manufacture a completion on thread exit. An uncaught exception escaping the thread function would terminate the process instead. A party that leaves must say so with arrive_and_drop(), ideally from an RAII guard on the error path, and the group usually also needs a shared "failed" flag so the remaining parties stop at the next phase.

A plain integer x starts at 0 before the threads start. A writes x = 1 and waits at a barrier. B successfully waits for that same phase and then reads x. There are no other writes to x. What can B see?
Why. Barriers carry memory effects: everything a party did before arriving happens-before what every party does after being released from that phase. This is what lets BFS workers read the frontier the barrier action built without extra locks.
From: Barriers and phasers
A hand-built semaphore's acquire is written as lock; if (permits == 0) wait; permits -= 1; unlock. What can go wrong?
Why. Waking up does not mean the permit is still there: another thread may have taken it before the woken thread got the lock back, and spurious wakeups happen with no signal at all. Only a loop that re-checks permits == 0 after every wakeup is safe. Waiting releases the lock, signalling under the lock does not reserve the permit, and the same interleaving can occur on one core.

A hand-built latch calls signal() (or notify_one()) when the count reaches zero. Three threads are waiting. What happens?
Why. Every waiter is waiting for the same, permanent condition, and all of them can proceed, so all must be woken. After zero, extra countdown calls do nothing and there are no later signals for the sleepers. The count does not itself wake a condition waiter, and having several waiters is legal.

Why. That is reader preference, and overlapping readers can keep readers above zero indefinitely: writer starvation. Writer preference fixes it by making new readers wait as soon as a writer is waiting.

Java onlyIn the Java barrier, a waiting thread is interrupted before its round trips. Why does it break the barrier instead of just leaving?
Why. Silently leaving corrupts the party count: the group is now one short for every later round. Breaking the barrier, as CyclicBarrier does, turns a hidden future hang into an immediate, visible failure for everyone.
