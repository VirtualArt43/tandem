Scheduled executor

Executors and asynchard50 minScheduledExecutorService, rebuiltNetflixLinkedInConfluentRubrikUber

LinkedIn's most reported concurrency question, a Netflix phone screen, a Rubrik senior screen and an Uber machine coding round: rebuild ScheduledExecutorService. The heap is the easy part. The interview is about a sleeping thread that must wake early, periodic tasks that must never overlap, fixed rate versus fixed delay, and what a throwing task does to its worker.

The task

Build a scheduled executor with a fixed number of worker threads. Never start a thread per task.

  • schedule(task, delay) runs the task once, delay from now: never early, and as close to on time as the machine allows.
  • scheduleAtFixedRate(task, initialDelay, period) runs at initialDelay, initialDelay + period, initialDelay + 2 * period, and so on, measured from the start: a late run does not push the later ones back.
  • scheduleWithFixedDelay(task, initialDelay, delay) starts each run delay after the previous run finished.
  • Two runs of the same periodic task never overlap, even when a run takes longer than the period and other workers are idle. A late fixed-rate run is followed by the next one at once.
  • If a run throws, that task stops repeating (and counts as done), and the worker carries on with other tasks. Catch everything: an Error in Java, anything at all in C++.
  • Each schedule call returns a handle. cancel() returns true if it stopped at least one future run: a one-shot task that has not started, or a periodic task that is still active (a run in progress then becomes its last). isCancelled() and isDone() report the state; isDone() is true once a task can never run again.
  • shutdown() drops every pending run, stops periodic tasks, lets a run in progress finish, and returns once the worker threads have exited. Later schedule calls throw (IllegalStateException in Java, std::runtime_error in C++). In C++ the destructor calls shutdown().

Rules, as in the interview: no library schedulers, timers, executors, or blocking or delay queues. Use a priority queue (or an ordered set), one lock and a condition variable with a timed wait: awaitNanos in Java, wait_until on std::chrono::steady_clock in C++. Measure time with a monotonic clock (System.nanoTime, steady_clock), never the wall clock.

Where it comes up: LinkedIn's concurrency round (a delayed scheduler, reported many times from 2021 to 2024), Netflix platform phone screens ("implement a scheduled thread pool executor"), Confluent's task scheduler rounds, a 2021 Rubrik senior screen that asked for schedule, scheduleAtFixedRate and scheduleWithFixedDelay, and Uber, where the same question appears as "Implement ScheduledExecutorService" and in machine coding with recurring jobs.

What the tests check

  • One-shot tasks with delays 150, 50, 100, 25 and 125 ms run in due order, none early, none more than a generous margin late.
  • With one worker asleep until a task due at 600 ms, a task scheduled later but due at 50 ms still runs at about 50 ms.
  • cancel before the run stops it and returns true, a second cancel returns false, and cancel after a run returns false with isDone() true.
  • Fixed rate: about 8 runs in 330 ms at period 40 ms from 30 ms, each at or after its ideal time and without drift; nothing after cancel.
  • Fixed delay: every run starts at least the delay after the previous one ended.
  • A 40 ms task at a 10 ms period on 4 workers never runs twice at once.
  • A fixed-rate task that throws on run 3 runs exactly 3 times, a fixed-delay task that throws on run 2 runs exactly twice, and the single worker still runs a later task.
  • 3 workers run due tasks 3 at a time, on at most 3 threads.
  • shutdown drops a pending task, stops a periodic one, refuses new tasks, and the worker threads end. In C++, ThreadSanitizer must stay quiet.

Taught in: Scheduled executors and timers

Open them one at a time. Each one gives away a little more.

Keep one priority queue of tasks ordered by next run time (break ties with a sequence number). A worker loops: take the lock, look at the head; if it is due, take it; otherwise wait on a condition until the head's time. What must happen when someone schedules a task that is due earlier than the current head?
Signal the condition whenever the new task becomes the head, or a worker sleeping until the old head's time will not notice the earlier one. Always re-check after waking: the head may have changed, or another worker may have taken it.
Periodic tasks: do not put the next run in the queue when you take the current one; put it back only after the run finishes. Fixed rate computes the next time from the previous scheduled time plus the period; fixed delay from the finish time plus the delay. If the run threw, or the task was cancelled while it ran, do not put it back.
Run the task outside the lock and catch everything around it. For cancel, flag the task under the lock and remove it from the queue (or let workers skip flagged tasks); a worker finishing a run checks the flag before re-queuing. For shutdown, set a flag, clear the queue, signalAll, and join the workers.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

All idle workers wait on one condition until the same head time. What is wrong with that, and how does the JDK avoid it?
When the head comes due, every waiting worker wakes, one takes the task and the rest go back to sleep: a small thundering herd on every task. The JDK's delayed work queue uses the leader-follower pattern: one leader thread does the timed wait for the head, every other idle worker waits without a timeout, and the leader signals a follower when it takes the task. Only one thread ever does a timed wait.
You need a million timers, most of which are cancelled before they fire.
A heap costs O(log n) per schedule and cancellation, and cancelled entries left in it waste memory until their time comes (the JDK keeps them by default; setRemoveOnCancelPolicy(true) removes them). For huge numbers of timers use a timing wheel: an array of buckets, one per tick, where a timer goes into bucket (now + delay) mod size and a hand advances one bucket per tick. Schedule and cancel are O(1); hierarchical wheels handle long delays. Kafka and Netty use timing wheels for exactly this.
Why a monotonic clock? What happens when the wall clock jumps?
With System.currentTimeMillis or system_clock, an NTP correction or a manual change moves every deadline: a jump backwards delays every task, and a jump forwards fires them all at once. System.nanoTime and steady_clock only measure elapsed time and never jump. Use wall time only to convert "run at 9 pm" into a delay when the task is scheduled, and re-plan if the clock changes.
How would a caller find out that a periodic task failed?
The JDK stores the exception in the task's future: further runs are suppressed and get() throws ExecutionException. Here you could add a failure() accessor to the handle, an error callback given to the executor, or a log line with the task's name. Silently stopping a periodic job is the worst option, because the job just disappears; at least count failures in a metric.
What should shutdown do with delayed tasks that have not run yet?
It is a policy decision, so say which one you chose. The JDK's scheduled pool by default still runs delayed one-shot tasks after shutdown but cancels periodic ones, and shutdownNow drops everything and interrupts running tasks. This problem drops all pending runs, which is simpler to reason about; a production scheduler often wants "finish what is due, drop the rest".
Google's variant: the system gives you one hardware timer that can hold a single pending alarm. Build many timers on it.
Keep your own priority queue of deadlines. The hardware timer always holds the earliest one. When a new timer is earlier than the current head, reprogram the hardware timer; when the alarm fires, run every due callback (on a pool, so slow callbacks cannot delay the next alarm), pop them, and program the next head. It is the same "wake early for an earlier head" logic, with the hardware timer playing the condition variable.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

One priority queue ordered by due time, one lock, one condition variable, N workers. A worker waits until the head is due, takes it, runs it outside the lock, and for a periodic task puts it back with its next time. The invariant: every task that can still run is in the queue exactly once, or is being run by exactly one worker. That single sentence rules out both lost tasks and overlapping runs.

Why each line is there

  • Signal when the new task becomes the head. The timeline above is the bug the second test catches, and the most common one in this interview.
  • Re-check everything after waking. The wait may have ended because of a signal, a timeout, or spuriously; another worker may have taken the head; shutdown may have started. The loop re-reads the head every time.
  • Re-queue only after the run. Putting the next run in before running the current one keeps the period "exact", but a spare worker can then start run k+1 while run k is still going. Re-queuing afterwards makes overlap impossible; fixed rate still keeps its schedule because the next time is computed from the previous scheduled time, and a late task catches up immediately.
  • Catch everything around the task. A failing task must stop repeating, so the worker records the failure and does not re-queue; the worker itself must survive, so nothing escapes the catch.
  • Sequence numbers. Tasks with the same due time run in the order they were scheduled, and in C++ they make every key in the ordered set unique, so a task can be found and erased exactly.
  • C++ handles share the core. The mutex, the condition variable and the queue live in a shared_ptr held by the executor, every worker and every handle, so cancel on a handle is safe even after the executor has been destroyed.

Cost and trade-offs

Scheduling and cancelling are O(log n), taking a task is O(log n), and no thread ever spins: idle workers sleep until the head's time. All workers share one lock, which is fine for most workloads; for very large numbers of timers, a timing wheel replaces the heap. Timing accuracy is limited by the operating system's wake-up latency, which is why the tests allow generous lateness but no earliness.

How to say it in the interview

I will keep a min-heap of tasks by next run time, guarded by one lock, with N worker threads. A worker waits on a condition until the head is due, using awaitNanos on nanoTime, takes it and runs it outside the lock. When a new task becomes the head I signal, otherwise a worker sleeping for a later task would miss it. Periodic tasks go back into the heap only after their run finishes, so they never overlap: fixed rate adds the period to the previous scheduled time, fixed delay adds the delay to the finish time. A task that throws is not re-queued, and the worker catches Throwable so it survives. Cancel flags the task and removes it from the heap; shutdown sets a flag, clears the heap, signals all and joins the workers. With many idle workers I would switch to a leader thread doing the only timed wait, and for millions of timers to a timing wheel.
