Fix the transfers that freeze

Bug huntsmedium20 minRubrik debugging round styleRubrik

A reported Rubrik debugging round in 2024 used banking code. This exercise uses that setting: read the symptom, find the lock cycle, and fix the transfers without breaking the accounting.

The incident

Practice incident, wallet transfers hang during the evening peak

  • Twice this week, around 21:00, the wallet service stopped completing transfers. CPU dropped to almost zero, request threads piled up, health checks failed, and a restart fixed it.
  • A thread dump taken during the second hang shows dozens of request threads waiting inside Bank.transfer, and the nightly audit thread waiting inside Bank.totalBalance.
  • The evening peak is mostly friends settling dinner bills, so many pairs of users pay each other back and forth within seconds.
  • Whenever the service was up, the books balanced: the total was always right.

The class is in your editor. Every account has its own lock, so that transfers between unrelated accounts run in parallel; keep that design. Transfers come from many request threads; the audit runs on its own thread.

What the class must guarantee. For distinct accounts and a positive amount, transfer returns true and moves exactly that amount if the source has enough funds when the operation takes effect. Otherwise it returns false and changes nothing. Self transfers, zero and negative amounts always return false. A transfer is all or nothing to other operations: no caller may observe its debit without its credit. No balance goes negative, balance reads its account safely, and totalBalance returns a consistent total. Two separate balance calls do not promise a joint snapshot.

Inputs use a positive number of accounts, valid indices and a nonnegative initial balance. The initial total fits in a signed 64 bit integer. Amounts may be any signed 64 bit value, including the minimum and maximum; do not narrow them to int. Conservation and nonnegative balances then keep every legitimate balance and sum in range. Invalid indices and invalid constructor arguments are outside this exercise.

Every finite batch of valid calls must complete without deadlock. Fair admission and a production latency bound are not required. Preserve the supplied per-account locks: a transfer blocked on one account must not stop transfers between unrelated accounts. In Java retain the locks array; in C++ retain locks_ and the BankTestAccess friend declaration. The harness briefly holds these locks to stage contention, without changing balances. This is a test seam for the supplied implementation, not a new public banking API.

Worked example, enough money for only one transfer

Three accounts start at 100. Two callers both request transfer(1, 0, 100). Exactly one returns true; the other returns false. After both return, the balances are 200, 0 and 100, and the total is 300. If both checked funds before taking the locks, they could both accept and overdraw account 1.

What the tests check

  • A sequential model checks every result and balance for both transfer directions, self transfers, exact funds, insufficient funds, zero, negative and extreme signed amounts, and amounts above 32 bits. It includes empty balances and a single-account bank.
  • A balance reader must wait while its account lock is held, then finish after release. A transfer blocked on account 0 must allow a transfer between accounts 2 and 3 to finish.
  • Two contenders wait while their destination is locked, then compete for enough funds for exactly one transfer. Exactly one succeeds, the refused call changes nothing, and the source ends at zero.
  • Opposite transfers each succeed 10,000 times in Java and 4,000 times in C++, finish within the deadline, and leave both balances unchanged.
  • Eight workers make seeded random transfers among five accounts while an auditor samples totals and individual balances. Final balances must match a ledger reconstructed from successful calls, every sampled total must match the initial total, and sampled balances must stay in range. The seed is printed for reproduction.
  • Timed waits and watchdogs turn hangs into failures. Java can report detected lock cycles; C++ runs under ThreadSanitizer for data races. Apple clang's ThreadSanitizer does not report lock-order inversions, so this Mac relies on completion checks for deadlocks.

The Java lock probes observe queued or waiting threads. The C++ probes use bounded observation windows after worker entry because std::mutex has no portable waiter query. Stress explores additional schedules; passing it is evidence, not a proof that every possible interleaving is safe.

Taught in: Deadlock: the four conditions and how to break each

Open them one at a time. Each one gives away a little more.

A service that stops with the CPU near zero is not working, it is waiting. What exactly is each stuck transfer waiting for, and which thread holds it?
Trace transfer(1, 2, ...) and transfer(2, 1, ...) starting at the same moment, one lock acquisition at a time. Write down who holds what after each step.
Any two threads that take the same two locks must take them in the same order. Choose an order every caller can compute without talking to anyone: the lower account number first, whichever direction the money moves. totalBalance already locks every account in index order, so it agrees with that rule.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Once transfers are fixed, why can totalBalance not deadlock with them?
It takes every lock in index order, the same global order transfers now use, and a deadlock needs a cycle, which needs someone to take a higher numbered lock and then wait for a lower one. The price is different: while it sums, it holds every lock, so all transfers stop for that moment. For a bigger bank, discuss a ledger or a coordinated snapshot. A version counter only helps with a complete validation protocol; it does not make unsynchronized C++ reads of ordinary balances safe.
The accounts are objects with no natural number. How do you order them?
Use any total order every thread computes the same way: a unique account id; in C++, the mutex addresses compared with std::less (which gives a total order over pointers); in Java, System.identityHashCode, with an extra tie-breaker lock taken first for the rare case where two hashes are equal. In C++ you can also hand both distinct mutexes to std::scoped_lock, which performs deadlock avoidance for that set. Every other path must still follow a compatible protocol, and object lifetimes must cover all calls.
How does std::scoped_lock(a, b) avoid deadlock with no ordering rule?
It calls std::lock, which the standard only promises uses some deadlock avoidance algorithm. The common implementations lock one mutex, try-lock the others, and if any try fails, release everything and start again, beginning with the one that failed. In that common algorithm a failed try-lock causes the locks acquired by the attempt to be released before it blocks again. This does not cure unrelated locks already held by the caller. Under heavy contention it can retry several times, and Java has no built-in equivalent, which is why ordering is the answer to give in both languages.
Could you fix it with tryLock and a timeout instead?
Use a separate retry design: take the first lock, try the second, and if that fails release only the first, which is the only one you own. Retry without changing money; check funds only after acquiring both. Timeouts bound an individual wait, and backoff reduces repeated collisions, but neither proves starvation freedom. Returning false just because a lock is busy violates this API, where false means an invalid or unfunded transfer. Java has timed tryLock; C++ needs std::timed_mutex for a timed attempt, while std::mutex offers an immediate try_lock. Fixed ordering is simpler here.
How would you prove it was a deadlock from the production thread dump?
In Java, jstack or jcmd PID Thread.print prints "Found one Java-level deadlock" with each thread's held and wanted locks, ReentrantLocks included (jstack -l also lists them per thread under "Locked ownable synchronizers"). In C++, gdb with thread apply all bt shows the threads parked in pthread_mutex_lock; on some Linux implementations debugger-visible mutex fields can help identify ownership, but those fields are not portable. Linux ThreadSanitizer builds can diagnose potential lock-order inversions with deadlock detection enabled; Apple clang's build does not. A timeout alone indicates lack of progress, so inspect the held and requested locks to establish a cycle.
How would an optimistic compare and replace version work?
The Okta Staff 2026 report recommends preparing CAS-style updates. Two independent CAS operations on two balances do not form an atomic transfer: another caller can observe the gap, and rollback can conflict with other updates. One correct alternative stores the entire immutable ledger behind one atomic reference. Read a snapshot, validate funds, copy and update both accounts, then compare and replace the old snapshot with the new one. On failure, retry from a fresh snapshot and recheck funds. Each read uses one published snapshot. This costs O(accounts) copying per attempt and introduces shared publication contention, so it is a follow-up design rather than the required per-account locking fix.
How would you test concurrent transfers, as asked in the reported Google 2022 wire-transfer question?
Start with a sequential model for results, exact funds and refused calls. Gate opposite transfers together, stage two attempts to spend the same last funds, and check a consistent total while transfers run. Reconstruct each final balance from successful calls, since conservation alone would let a no-op implementation pass. Check that disjoint transfers still make progress, use deadlines so a deadlock becomes a failure, and run C++ under ThreadSanitizer. Deliberately test wrong solutions too. Controlled schedules and stress complement the lock-order proof; none of these finite tests proves all executions correct.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The bug

A deadlock from inconsistent lock order. transfer(from, to) locks from first and to second, so the order depends on the direction the money moves. Two opposite transfers between the same pair lock the same two accounts in opposite orders:

All four coffman conditions hold: the locks are exclusive, each thread holds one lock while waiting for another, nobody can take a lock away from a thread, and the waits form a cycle. Removing any one prevents deadlock; the cheapest one to remove here is the cycle.

The fix

Impose one global order on the locks, the lock ordering rule: always lock the lower numbered account first. The amount still moves from from to to; only the order of locking changes.

Why this is enough

  • A cycle needs a backwards step. With every thread taking locks in increasing order, a thread holding lock i only ever waits for a lock above i. Follow the waits around a would-be cycle and the numbers would have to increase forever and also return to the start, which is impossible.
  • totalBalance already obeys the rule, locking 0, 1, 2 and so on, so the audit can never be part of a cycle either.
  • The self transfer guard is essential. With from == to the code would lock the same lock twice: harmless for Java's reentrant lock, but locking a std::mutex the thread already holds is undefined behaviour (in practice a self-deadlock). The existing guard keeps that case out.
  • Money was never the problem. Each transfer changes both balances under both locks, so totals were right whenever the service was up, exactly as the incident says. The tests still check conservation, because a careless fix (releasing a lock between the debit and the credit, say) would break it.

Cost and limits

Once locks are acquired, transfer and balance take O(1) time. totalBalance takes O(accounts) time and holds every lock; the C++ reference also uses O(accounts) temporary RAII lock storage. The bank stores O(accounts) balances and locks. Lock waiting has no fixed latency bound, and these mutexes do not promise starvation freedom.

How to say it in the debugging round

The dump shows threads waiting on locks inside transfer. It locks from and then to, so transfer(1, 2) and transfer(2, 1) take the same two locks in opposite orders, and each can end up holding one and waiting for the other: a lock-ordering deadlock. The fix is a global order: always lock the lower account number first, then do the same debit and credit. totalBalance already locks in index order, so it is consistent. In C++ I could also use std::scoped_lock on both mutexes.
