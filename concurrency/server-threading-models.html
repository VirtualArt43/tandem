Server threading models

Compare server threading models by waiting cost, state ownership, overload behaviour and the limits each design needs.

Asked atMetaUber
Before this:Why thread pools existCPU bound versus I/O bound work

Before a server answers any request, its design has answered another question: which thread runs this request, and what does that thread do while it waits? That choice decides how many connections the server can hold, how it fails under load, and which bugs it is prone to.

In plain words

A restaurant can be staffed three ways. One waiter per table: the waiter stands by the table for the whole meal. Simple and personal, but most waiters are idle most of the time, and you run out of waiters long before you run out of tables. One very fast host walks the floor, notices which table needs something, deals with it in seconds and moves on. One person can serve fifty tables, but if the host stops to cook a dish, the whole floor waits. Hosts plus a kitchen: hosts take orders and carry plates; a fixed team of cooks does the slow work.

Those are a thread assigned to each active request, the event loop, and a hybrid used by many servers. The question that separates them is what it costs you to have a customer waiting.

The cost of a waiting request

An I/O-heavy server spends much of a request's lifetime waiting for clients, databases or other services. In a platform thread per request design, a waiting active request occupies a thread: reserved stack address space, committed stack pages and kernel bookkeeping. Sleeping threads are not runnable and do not continually consume CPU; scheduling cost grows when many become runnable. Stack sizes and practical thread limits depend on the runtime, platform and workload (see what a thread costs).

In an event loop design a waiting request keeps a state object and buffers without reserving a platform thread. A few kilobytes is only an illustrative application-state estimate: socket buffers, TLS state and queued payloads may cost much more. The model you pick is a decision about that cost, and about who saves and resumes a request's state.

Model 1: thread per request

A worker, usually from a pool, runs an active request from start to finish, blocking whenever it waits. Distinguish thread per request from thread per connection: a keep-alive connection may be idle between requests, and an NIO connector can watch it without retaining a worker. HTTP/2 can also carry several concurrent requests on one connection.

  • Strengths. Sequential code and useful request stacks. Local state is confined if it does not escape; a local reference or pointer does not make the referenced object private. Cancellation is cooperative: Java interrupts work only where the API responds, and C++ stop tokens do not automatically interrupt blocking socket calls.
  • Weaknesses. A bounded platform worker pool caps active request concurrency. Blocking long polling or streaming occupies a worker for the wait; asynchronous handlers can release it. A slow dependency can occupy every worker.
  • Where you see it. Traditional servlet request handling and JDBC services. Tomcat's NIO connector separates socket readiness from request workers. PostgreSQL instead uses a process per client connection, another reason connection pooling matters.

Model 2: the event loop (reactor)

A few threads, often one per core, each run a loop: ask the operating system "which of my connections are ready?" (with epoll, kqueue or a Java Selector, see I/O models), then run a short handler for each ready connection and go back to asking. This is the reactor pattern: the loop reacts to readiness. Keep handlers short: use non-blocking operations or offload slow work, then resume through callbacks, promises or coroutine steps. Wrapping a blocking call in a callback does not make it non-blocking.

  • Strengths. Waiting connections do not each need an OS thread. Large connection counts become feasible if memory, descriptor limits and network capacity allow. If all access to a connection's state stays on its loop thread, it needs no locks: the loop confines it.
  • Weaknesses. One blocking call or one slow computation freezes every connection on that loop. A 50 ms JSON parse is 50 ms of silence for thousands of clients. Stacks are fragmented across callbacks, so debugging is harder.
  • Where you see it. Nginx workers and Netty event loops each watch many connections. A Node.js JavaScript isolate has one event loop; libuv's worker pool handles asynchronous file operations, dns.lookup and selected crypto operations. Explicit worker_threads run additional JavaScript isolates. Redis's main command execution illustrates the same danger: a slow KEYS * delays other command processing on that server.

Model 3: the proactor

A reactor reports readiness; you then attempt non-blocking I/O. A proactor reports an operation's completion: you submit a read with a buffer, then receive a byte count, EOF or an error. Windows IOCP and Linux io_uring support completion I/O. Boost.Asio presents completion-style APIs even when its backend uses readiness. The operating system or a library performs the operation; completion does not guarantee a full application message or successful I/O.

Model 4: a common hybrid

Event loops own the sockets; bounded pools own the work. Every blocking or CPU-heavy step has a designated home with a limit, and the I/O layer never blocks:

Tomcat's NIO connector separates acceptor and poller work from servlet workers. A Netty service can offload blocking calls, and Node can send CPU work to worker_threads. The illustrated limits are example budgets, not recommended defaults. Use non-blocking admission on the I/O thread: a full queue must reject or pause intake, not block the loop or run rejected work there. A semaphore that makes shared workers wait can still exhaust that pool; use immediate admission failure or separate dependency executors. See backpressure and bulkheads.

Model 5: cheap threads

Go's goroutines and Java 21's virtual threads let blocking-style network code wait without dedicating an OS thread to each wait. Go's HTTP server creates service goroutines for connections, with additional concurrency for HTTP/2 streams. Java virtual threads normally unmount during supported blocking socket I/O, freeing their carriers for other work. In JDK 21 the scheduler's target parallelism defaults to the available processor count; that is configurable, not a hard bound on every JVM thread.

You keep sequential code and readable stacks. You do not get free capacity: the database still accepts only so many queries, so you still need explicit concurrency limits (see rate versus concurrency limits). CPU-heavy work still needs cores. And in JDK 21 a virtual thread that blocks while holding a synchronized monitor pins its carrier, so a few such calls can stall the whole carrier pool (see virtual threads and coroutines).

See it: one blocking call stalls the loop

Four requests each need a 100 ms database call, and a cheap health check arrives right after them. First the handlers block the single loop thread; then the loop hands the blocking call to a pool of 4 workers and posts the reply back to itself. (The sleep stands in for the database call, purely to make the timing visible.)

Ignoring scheduling and printing overhead, the blocking phase takes about 400 ms before reaching the health check: every connection on a loop shares its fate. Offloading lets the loop reach the health check without waiting for any database call; the four queries can overlap on the workers. Exact timings and completion order vary. Notice also that every reply is printed by the loop thread: per-connection state touched only by the loop needs no lock. In C++, the Executor destructor drains its queue before joining, and workers is destroyed before loop, so replies posted by workers still find a live loop.

These finite demos use unbounded queues to isolate scheduling; they are not production admission controllers. A fixed Java pool bounds workers, not queued tasks. Neither version waits for worker results on the loop. C++20 supplies std::jthread; in C++17 use std::thread and explicitly join every worker after signalling shutdown, including during partial construction failure.

How each model fails under overload

  • Platform thread per request: a slow dependency occupies workers, and requests wait in application or connector queues. The TCP accept backlog concerns new connections, not all requests on existing connections.
  • Event loop: without admission and buffer limits, connections and queued work consume memory; a blocking handler stalls its loop.
  • Hybrid: a full bounded worker queue must reject promptly. An unbounded queue grows latency and memory; a caller-runs rejection policy is dangerous when the caller is an I/O thread.
  • Cheap threads: a burst can overwhelm a downstream or create many threads waiting for its connection pool. Limit admitted work as well as active downstream calls.

Worked example: pick a model for three services

An internal CRUD API, 500 requests per second, each mostly a 50 ms database call. Assuming stable throughput and a mean request lifetime of 50 ms, Little's law gives 500 × 0.05 = 25 requests in flight on average. A platform worker pool of 50 is an illustrative starting point, not a sizing guarantee; validate burst and tail latency under load. Cap database calls at what the database tolerates.

A chat service with 200,000 WebSocket connections, almost all idle at any moment. A platform thread per connection would mean 200,000 OS threads, mostly parked. Use event loops with state confined to each loop, or virtual threads with explicit state ownership. Budget memory and descriptors for that connection count, and bound each outbound buffer so a slow reader cannot eat memory.

A thumbnail service that spends 200 ms of CPU per image. Event loops for the sockets, a CPU pool sized to the core count for resizing, and a bounded queue in front of it that rejects with a 503 when full. Start near the available CPU budget and measure: oversubscription adds contention, and the loop and runtime also need CPU time.

Common mistakes

  • A blocking call on an event loop: JDBC in a Netty handler, fs.readFileSync in Node, a slow Redis command. One call delays every handler on that loop.
  • CPU-heavy work on the loop: big JSON documents, compression, crypto. Same effect as blocking.
  • One shared pool for everything: a slow dependency fills the pool and takes down endpoints that never touch it.
  • Unbounded worker queues: overload turns into memory growth and requests that time out while still queued.
  • "Virtual threads, so no limits needed." The threads are cheap; the database connections are not.
  • A thread per idle connection for WebSockets or long polling at large scale.

In the interview

The research records an Uber meeting-room interview follow up about 10,000 concurrent requests and bottlenecks, and a Meta single-machine memcache design probing locking and memory management. These motivate explaining execution and ownership explicitly; they are not reports of a named threading-model quiz. Tie your model to the workload:

At the API layer I would use event loops for the sockets and a bounded worker pool for the request logic, because the work is I/O heavy with a lot of fan out. The queue in front of the pool is bounded, so overload fails fast with a 503 instead of growing latency; each downstream gets non-blocking admission sized to its tested capacity. CPU-heavy steps use a separate bounded pool within the machine's CPU budget.

Then pre-answer the favourite follow up, "what if the database slows down ten times?":

I reject excess database work before it occupies shared workers, and apply a request deadline to admitted calls. A separate database executor can provide stronger isolation. A semaphore with blocking acquisition in the shared pool would not be enough. If the product allows it, rejected calls use cached or partial results. I track queue delay, dependency occupancy and event-loop lag to check that unrelated endpoints retain capacity.

Other follow ups: "Why not one thread per connection?" (cost per idle connection). "Why not do everything on the event loop?" (one blocking or CPU-heavy step stalls everyone). "Do virtual threads change your answer?" (the code gets simpler; the downstream limits stay).

Senior depth

Confinement for free. A registered Netty channel has an assigned event loop, but handlers can use a separate executor and application code can access state from other threads. Confinement holds only when every access uses the owner. Hand workers immutable input and post results through a thread-safe queue to that owner. Cross-connection state needs confinement or synchronization too.

Thread per core, share nothing. Frameworks such as Seastar (behind ScyllaDB) take the event loop to its limit: one thread pinned to each core, data partitioned so each core owns its share, and explicit messages between cores instead of shared locks. It reduces shared-memory contention at the price of explicit ownership and cross-core messaging.

Several accept loops. On Linux, SO_REUSEPORT lets several threads or processes each own a listening socket on the same port, and the kernel spreads incoming connections across them, avoiding one acceptor as a bottleneck.

Ordering and lifecycle. A worker for request B may finish before A, even when the loop accepted A first. Sequence responses if the protocol requires ordering. On disconnect or timeout, mark the request finished on its owner, cancel work where supported and ignore late results; cancellation is not proof that a database side effect stopped.

Shutdown and diagnosis. Stop admission first, drain or cancel accepted work within a deadline, then stop workers before destroying the loops receiving their completions. Never call a blocking future wait, pool join or semaphore acquisition from the loop. Diagnose stalls with loop lag, handler duration, runnable CPU demand, queue age, rejection counts and downstream occupancy, rather than thread count alone.

Key takeaways

  • Compare the cost of waiting, the owner of mutable state and the admission limit.
  • A bounded platform worker pool limits active requests, not necessarily open connections or queued requests.
  • Event loops scale to huge connection counts, and one blocking or CPU-heavy handler stalls every connection on the loop.
  • A common hybrid is: loops for I/O, bounded pools for work, a limit per dependency, a separate CPU pool.
  • Cheap threads (goroutines, virtual threads) simplify the code but do not remove the need for concurrency limits.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A Node.js handler calls a synchronous function that takes 80 ms to parse a large JSON body. What happens to the other 5,000 open connections served by that same JavaScript isolate during those 80 ms?
Why. JavaScript callbacks within this isolate share its event loop thread. Other isolates and the kernel may still make progress. CPU-heavy or blocking work on it stalls every connection. libuv's pool handles certain I/O operations, not your JavaScript; CPU work has to be moved explicitly, for example to worker_threads.
A Netty handler and all other users of its connection state run only on that channel's assigned event loop. Why is no lock needed?
Why. All accesses are serialized by one owner, so this is thread confinement, not a global Netty lock or automatic volatile semantics. Handlers can be stateful. If a worker or a shared handler accesses the same state concurrently, the premise fails and you need an explicit ownership or synchronization plan.
A service must hold 200,000 mostly idle WebSocket connections on one machine. Which model fits worst?
Why. A platform thread per connection requires 200,000 stacks and OS thread records. Sleeping threads do not burn CPU, but the memory and thread limits make this the weakest fit. Event loops, virtual threads and goroutines can wait without one OS thread each; all still require connection-memory and descriptor budgets.
What is the difference between a reactor and a proactor?
Why. Readiness (epoll, kqueue, a Java Selector) versus completion (Windows IOCP, io_uring). A successful read completion includes a byte count for data placed in your buffer; it can also report EOF or an error. Neither pattern dictates threads versus processes or reads versus writes, and they describe different notification contracts.
A team moves a thread-per-request service to Java 21 virtual threads and removes its 200-thread pool limit. Under a burst, the service fails anyway. What is the most likely cause?
Why. The old pool was also an accidental concurrency limit. Virtual threads make waiting cheap, but the downstream is no bigger. Use per-dependency limits and bound total admitted work. Virtual threads support network I/O and are not capped at the core count; their benefit depends on the workload, not universal speed.
A single FIFO event loop has tasks A and B already queued before it starts. A submits work to a worker and returns without waiting. B prints B. The worker posts a callback C to the same loop that prints C. Assuming all tasks complete successfully, what can print?
Why. B is already queued before A submits the worker. Even if the worker immediately posts C, C goes behind B. Posting is non-blocking, so there is no deadlock. This orders callbacks in this setup; two independently offloaded requests can still complete in either order.
A service completes 500 requests per second with a mean request lifetime of 50 ms in steady state. It uses a shared 50-worker pool. Which statements are justified? Select all that apply.Select all that apply
Why. 500 multiplied by 0.05 seconds is 25 average in-flight requests, not a maximum or a tail-latency guarantee. Waiting workers still occupy the shared pool. A semaphore bounds permit holders, not the population waiting for permits; admission must separately reject or bound those waiters.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
You are designing an API gateway that receives 20,000 requests per second, each fanning out to 3 backend services with typical latencies of 20 to 50 ms. One backend sometimes slows to 2 seconds. Describe the threading model and what happens when that backend slows down.
Model answer

The workload is almost entirely waiting on the network with heavy fan out, so I would use event loops for all client and backend sockets, about one per core, with non-blocking clients for the three backends. Request handling is short and runs on the loops; anything blocking or CPU-heavy (rare in a gateway, say a large payload transformation) goes to a separate bounded pool.

Sizing with Little's law: with stable throughput, a mean request lifetime of 50 ms gives about 1,000 requests in flight. If each of the three backends also averages 50 ms, backend concurrency totals about 3,000; if their means range from 20 to 50 ms, it totals about 1,200 to 3,000. Typical or percentile latency is not automatically the mean required by Little's law.

Each backend gets its own concurrency limit, sized from its normal rate and latency with headroom: for one taking 20,000 calls per second at 50 ms, about 1,000 in flight, so 1,500 is an illustrative budget only if downstream capacity and load tests support it. Without timeouts or shedding, sustaining 20,000 calls per second at a 2 second mean lifetime would require 40,000 calls in flight. The 1,500-call budget prevents that growth. If it fills, further calls fail fast or take a permitted degraded path; with a shorter deadline, timeouts may fire before the limit fills. Every call carries a timeout derived from the request's deadline; choose a budget below 2 seconds if that is the response target, and cancel underlying work where supported. A circuit breaker can stop calling the backend entirely while it is sick. Bound pending requests and retries too, and verify isolation under load: a concurrency limit alone does not guarantee that every other route retains capacity.

Explain
Explain why event loops fit many idle connections better than one platform thread per connection. How is thread per request different, and what complexity does the event loop introduce?
Model answer

The difference is what a waiting connection costs. In a platform thread-per-connection design, an idle connection holds a whole thread: a reserved stack, a kernel thread object and scheduling work when it wakes. Large idle populations may hit memory or OS thread limits before saturating the CPU. A thread-per-request server with readiness-based keep-alive handling avoids dedicating workers to idle connections. An event loop keeps each waiting connection as a small object with its buffers, and one thread asks the operating system which connections are ready, then runs a short handler for each. This removes the per-connection OS thread cost, though socket buffers, TLS, application state and descriptor limits still bound capacity.

What it gives up: handlers must never block or compute for long, because one slow handler stalls every connection on that loop. Logic that waits has to be written as callbacks, promises or coroutines, which spreads one request's story across many small steps and makes stacks less useful for debugging. Real servers combine the two: loops for I/O, bounded pools for blocking or CPU-heavy work. Virtual threads and goroutines get close to both worlds by letting blocking-style code park cheaply.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"You have 100,000 mostly idle client connections and blocking database calls. Which threading model would you choose, and where would you put the limits?"
What a strong answer covers
  • Choose event loops for many idle sockets and a bounded executor for blocking database work
  • Distinguish open connections from active requests and budget buffers and descriptors
  • Use non-blocking admission before offloading; never wait or run rejected work on the loop
  • Keep connection state on its owner and post worker results back safely
  • Bound downstream concurrency and total admitted work, with deadlines and overload behaviour
  • Explain that virtual threads simplify waiting but do not increase downstream capacity
How a senior would say it
I would use event loops for the sockets and a bounded executor for the blocking database calls. Most of those connections are idle, so dedicating an operating-system thread to each would waste memory. I would budget descriptors, socket buffers and application state separately from the number of active requests. A hundred thousand connections does not mean a hundred thousand database queries should be admitted. Before offloading, I would try to acquire admission without blocking the loop. If the database budget or worker queue is full, I would reject promptly or return a permitted degraded response. I would not use a rejection policy that runs the database call on the submitting event loop. Each loop owns its connection state. Workers receive immutable input and post results back through a thread-safe queue, so offloading does not quietly introduce shared mutable state. Requests carry deadlines, and late results are discarded if the connection has already finished. Java virtual threads are another reasonable implementation when the libraries support them. They simplify the waiting code, but I would retain the same admission and database limits. Finally, I would load-test queue age, loop lag, memory and rejection rates before claiming that this design meets the target.

Likely follow up: How would you stop new work and shut down without losing worker completions?

Out loudabout 75 s
"We added a semaphore around database calls, but when the database slows down even our health endpoint hangs. What would you check?"
What a strong answer covers
  • A semaphore limits active calls but can leave every shared worker waiting
  • Inspect worker stacks, queue age and loop lag to distinguish pool exhaustion from loop blocking
  • Move admission before shared worker occupation or isolate the dependency in a bounded executor
  • Propagate deadlines and cancellation without assuming backend work has stopped
  • Validate unrelated endpoint latency and the bounded wait population under injected dependency delay
How a senior would say it
The semaphore may be limiting database concurrency while still exhausting the shared worker pool. If every worker blocks while acquiring a permit, the health endpoint has no worker left, even though it never uses the database. I would inspect worker stacks and queue age, then check event-loop lag to rule out a blocking call on the loop itself. I would move non-blocking admission ahead of occupying shared workers, or isolate database work in its own bounded executor. Excess calls should fail promptly or use an allowed degraded response. The wait population needs a bound as well as the number of active queries. I would propagate the request deadline into the database operation and attempt cancellation when that deadline expires. Cancellation is not proof that remote work stopped, so I would also check the client's actual timeout and cancellation behaviour. To validate the fix, I would inject database delay while measuring health-endpoint latency, queue age, rejection counts and the number of waiting requests. More worker threads alone would postpone the failure rather than contain the slow dependency.

Likely follow up: What changes if the request handlers use Java 21 virtual threads?
