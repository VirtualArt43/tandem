Java concurrency cheat sheet

Java 21 concurrency APIs, their contracts and traps, with C++20 counterparts, runnable examples and interview drills.

Asked atDatabricksRubrikConfluentAppleLinkedIn
Before this:Condition variables and monitorsvolatile in Java, std::atomic in C++Inside an executor: the queue-before-max trap

The night before, and in the last ten minutes before a round, you do not need explanations. You need the exact method name, its return value, and the one trap that sinks people. This page collects the main Java 21 concurrency APIs and their interview traps.

In plain words

A cook does not read the recipe book during dinner service. Before service, every ingredient is chopped and laid out in small bowls, labelled, in reach. This page is your bowls: the APIs laid out by job, each with its one-line rule. Learn the ideas in the lessons; come here to have them in reach.

Where an equivalent exists, the row includes a C++20 counterpart, so the two of you can read each other's code in a mock round, and so that whichever language the interviewer prefers, you can map the idea across.

The C++20 standard library has no thread pool and no scheduled executor: Piyush writes them with a queue, worker threads and wait_until, which is exactly what Rubrik-style rounds ask both of you to do when they ban the library.

Implementations: ArrayBlockingQueue (bounded array, one lock, optional fairness), LinkedBlockingQueue (optionally bounded, default capacity Integer.MAX_VALUE, separate put and take locks), LinkedBlockingDeque, PriorityBlockingQueue (unbounded), DelayQueue (elements become available when their delay expires), SynchronousQueue (no capacity: a hand-off), LinkedTransferQueue (transfer waits for a consumer). In C++20 a mutex and conditions implement a FIFO queue; priority, delay and rendezvous queues need their own state and predicates.

Fork/join and parallel streams

  • ForkJoinPool.commonPool(), RecursiveTask<V> with compute(): split until small, fork() one half, compute the other yourself, then join() the forked half. invokeAll(a, b) does both.
  • Java 21 normally uses the common fork/join pool plus the calling thread for parallel streams; the Stream API does not promise a particular executor. Blocking I/O can starve other users of that pool. Use a dedicated I/O executor; ForkJoinPool.managedBlock is a specialised option for managed blocking.

Happens-before, the list to recite

For ordinary conflicting accesses, name the happens-before chain: program order; unlock then a subsequent successful lock of the same lock; a volatile write then a subsequent read in synchronization order; actions before Thread.start() then actions in the started thread; all actions of a thread then another thread's detection of its termination. A timed join that returns while the thread is alive does not establish that termination edge.

Library hand-offs also publish preceding actions: insertion into a concurrent collection to subsequent access or removal of that element; task submission to its execution; task actions to result retrieval through Future.get(); actions before latch countDown() to actions after the corresponding successful await(); and actions before semaphore release() to actions after successful acquisition in another thread. These edges do not make later unsynchronized mutations safe. See happens-before.

Final-field initialization safety is a separate rule, not a general constructor-to-reader happens-before edge. A properly constructed object can expose its initialized final fields even through a racy publication, but that does not publish all ordinary fields or make the reference reliably visible. Prefer safe publication through a lock, volatile reference, class initialization or a concurrent hand-off.

Idioms to type from memory

The timed queue examples budget condition waiting after lock acquisition. A whole-call budget also needs timed acquisition and one monotonic deadline, using System.nanoTime() or std::chrono::steady_clock; reacquisition and scheduling can still delay return. Zero timeout is an immediate predicate check once the lock is held. Java propagates interruption; these C++ queue fragments have no cancellation or close operation and must outlive every caller.

The next three snippets use Java library executors and queues. C++20 has no standard executor lifecycle or future cancellation; the matching implementations are in the thread pool lesson and async composition. Do not invent a shutdownNow() on std::async.

The worker exits on interruption when tasks cooperate; it logs RuntimeException but deliberately lets serious Error failures escape. The shutdown helper below follows the executor documentation's termination pattern; an application that retains submitted futures must additionally handle the queued tasks returned by shutdownNow().

A future timeout is not an I/O deadline. The fan-out below substitutes a result after two seconds from submission, including queueing. Its stub fetch is immediate; real I/O needs connect and read deadlines. Because executor close() waits, this method can still wait indefinitely if a running fetch ignores its deadline. The fixed pool also has an unbounded queue: bound input or admission in a service.

The hit-counter pattern assumes entries are not removed or replaced while recording: otherwise an increment can land in a detached LongAdder. The two maps are independent, not one transaction; LongAdder.sum() is unsuitable for enforcing an exact limit.

Worked example: a failed task, then a published result

A submitted task fails, and a later task writes an ordinary field. The first future reports the failure; the second future's successful get() publishes its task's write, so the caller can read 42. The field needs no volatile modifier because there is no access racing that write. A timed-out get would not justify the same read.

Only the main thread prints. In C++ the packaged task captures failure and making its shared state ready synchronizes with successful waiting. std::jthread joins at scope exit in C++20; a C++17 version needs an explicitly joined std::thread, with exception-safe cleanup. Neither example claims that every kind of executor automatically survives every failure.

Tools

  • jstack <pid> or jcmd <pid> Thread.print: a thread dump; Java 21 detects some monitor and ownable-synchronizer cycles, not every logical deadlock and not cycles involving virtual threads. kill -3 <pid> prints one to the process's standard output.
  • jcmd <pid> JFR.start: Java Flight Recorder, for lock contention and thread states over time.
  • jcstress: OpenJDK's outcome-based concurrency stress harness. It explores observed behaviours; it is not a general data-race detector or a proof.

Common mistakes

  • Treating a timeout as cancellation. A future may time out while its task still consumes resources. Put deadlines in the I/O operation and define cooperative cancellation.
  • Returning a permit after a failed acquire. Enter the try/finally that releases only after acquisition succeeds, otherwise an interruption can inflate capacity.
  • Using a read lock to upgrade. Release it, acquire the write lock, and recheck the condition; another writer may have changed it in the gap.
  • Assuming shutdown settles every future. Draining a queue is not the same as cancelling its futures. Decide who cancels, resubmits or reports each unstarted task.
  • Equating language counterparts. A Java reentrant monitor differs from std::mutex; a Java semaphore accepts extra releases, while C++ semaphore counts must respect their maximum.

In the interview

API fluency is checked indirectly. A Databricks round reportedly spent most of the hour on how ConcurrentHashMap locks and why HashMap is not thread-safe; a Rubrik interviewer questioned why the candidate chose CyclicBarrier and Semaphore; another Rubrik round focused on exactly which exceptions a pool catches; an Apple manager screen announced Java memory model and threading model topics; Confluent insiders advise knowing how the standard utilities work inside. When a library is banned, you still name the class you are replacing, which shows you know what it would have done.

I would normally use an ArrayBlockingQueue here; since it is off limits, I will build the same thing with a ReentrantLock and two conditions, not full and not empty, and give it the same put, take and timed poll contract.
I am using submit, so a task's exception is captured in its Future; I will call get and unwrap ExecutionException, otherwise the failure would be silent.

Key takeaways

  • Every condition wait rechecks its predicate; every acquired lock is released in finally; interruptions are propagated or restored with an explicit cancellation policy.
  • ConcurrentHashMap.compute and merge make per-key updates atomic; a sequence of calls needs extra coordination, and bulk operations are not whole-map snapshots.
  • Know the four BlockingQueue method families and the queue-before-max rule of ThreadPoolExecutor.
  • submit captures failures in the future; a periodic task failure suppresses its later executions; immediate shutdown only attempts to stop running work.
  • Give blocking work an explicit executor, and remember that timing out a future does not stop its computation.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Inside a loop, left = cond.awaitNanos(left); returns -120000. What does that mean, and what should the loop do?
Why. awaitNanos returns an estimate of the time left, and a value at or below zero means the deadline passed. Interruption is reported by an exception, not a return value, and the lock is held again on return. Restarting the original timeout after each wakeup could extend the wait indefinitely.
Which BlockingQueue method returns false immediately when the queue is full?
Why. offer(e) is the special-value form. add throws IllegalStateException when full, put blocks, and the timed offer waits up to the timeout before returning false.
An ordinary ThreadPoolExecutor with no custom hooks accepts a task through submit. The task throws without logging, and nobody inspects its future. What happens?
Why. submit wraps the task so that its outcome, including an exception, is captured in the Future; get() would throw ExecutionException. The submitting thread does not receive that task failure, the worker survives, and the pool does not shut down. A plain throwing Runnable passed to ThreadPoolExecutor.execute follows the uncaught-exception path instead.
Three threads call await() on a new CyclicBarrier(3). What does the first thread to arrive get back when the barrier trips?
Why. The arrival index counts down: getParties() - 1 for the first to arrive and 0 for the last. The last arriver runs the barrier action, if present. For three parties the only indices are 2, 1 and 0; 3 is not an arrival index.
A thread holds only the read lock of a ReentrantReadWriteLock, has no write hold, and calls writeLock().lock(). What happens?
Why. Upgrading is not supported: the writer waits for every read hold to be released, and this thread's own hold never will be. The reverse, taking the read lock while holding the write lock and then releasing the write lock, is the supported downgrade.
A fresh Java array int[] value = {0}; is shared only with one submitted task. If this code reaches println, what can it print?
Why. The task's actions happen-before actions after its Future.get(). The lambda shares the array, and capturing an effectively final reference does not freeze its elements. The no-other-access premise avoids a later writer racing the print; a timed-out or interrupted get would not permit this reasoning.
A scheduled task registered with scheduleAtFixedRate throws an exception on its fifth run. What happens to the sixth run?
Why. The documentation says a periodic task that throws has its subsequent executions suppressed. The executor remains usable; it neither retries the failed registration nor catches up with a sixth run. Inspect its future or add explicit failure reporting. Catch recoverable failures inside the task only when continuation is the intended policy.

Explain
Explain shutdown() versus shutdownNow(), and what happens to a running task that ignores interruption.
Model answer

shutdown() stops the executor from accepting new tasks but lets every queued and running task finish; it returns at once, so you follow it with awaitTermination to wait. shutdownNow() also stops new tasks, removes the tasks still in the queue and returns them to you as a list, and attempts to stop running tasks, normally by interrupting their threads. Returned queued futures need an explicit cancellation or resubmission policy; removal alone does not complete them. Interruption is only a request: a task blocked in sleep, wait, take or lockInterruptibly gets an InterruptedException, but a task that neither checks nor responds to interruption can keep running, and awaitTermination will time out. So tasks must cooperate: check Thread.currentThread().isInterrupted() in loops, restore the flag when they catch InterruptedException, and close sockets or use timeouts for I/O that cannot be interrupted. The robust sequence is the two-phase pattern: shutdown, wait, then shutdownNow, wait again, and log if it still does not stop.

"I put a two-second timeout on a future. Why is the service still hanging, and what would you change?"
What a strong answer covers
  • Distinguish a timed wait from CompletableFuture timeout completion
  • Neither timeout automatically stops the underlying computation
  • CompletableFuture cancellation does not interrupt its computation; Future cancellation is cooperative
  • Executor close waits for termination and can outlast the future timeout
  • Use I/O deadlines, bounded admission and an explicit resource cleanup policy
How a senior would say it
The timeout limits an observation of the result, not necessarily the work producing it. A timed Future.get stops my wait by throwing a timeout exception. CompletableFuture.orTimeout instead completes that future exceptionally, but the underlying computation may continue. That distinction matters if the task is stuck in network I/O. Cancelling a CompletableFuture does not interrupt its computation, even with true as the argument. A future returned by a thread pool may request interruption, but the task still has to cooperate. I would also inspect resource cleanup. If the code created an executor in try-with-resources, its close waits for termination, so the method can remain stuck after the future has timed out. I would put connect and read deadlines in the actual client call, propagate a shared request deadline, and define how cancellation releases resources. I would bound admission as well, so slow calls cannot create an unlimited backlog. Finally, I would test a task that ignores interruption and verify the service reports the timeout without claiming that the task has stopped.

Likely follow up: What happens to the futures of queued tasks returned by shutdownNow()?

Out loudabout 75 s
"A teammate says final fields and volatile fields both safely publish the whole object. How would you explain the difference?"
What a strong answer covers
  • Final-field initialization safety and volatile publication are distinct guarantees
  • Correct construction protects final values and construction-time reachable state, not every ordinary field
  • A volatile reference hand-off publishes preceding initialization through a happens-before edge
  • Neither final references nor volatile references make later object mutations atomic
  • Choose immutable published snapshots or locking for a multi-field mutable invariant
How a senior would say it
I would separate initialization safety from publication. Final fields have special guarantees when an object is properly constructed and its reference does not escape during construction. Another thread that obtains that object sees the initialized final values, including the relevant construction-time state reached through a final reference. That is not a general happens-before edge for every ordinary field, and it does not promise that a racing reader will obtain the reference at all. Publishing the completed object through a volatile reference gives a different argument: initialization precedes the volatile write, which happens-before the reader's subsequent volatile read. That chain makes the preceding writes visible. Neither technique turns later mutations into a transaction. A final list reference still points to a mutable list, and a volatile reference does not make a balance update plus a history update atomic. For a configuration snapshot I would build an immutable object and publish it through a volatile reference. For a mutable invariant across fields, I would protect the complete operation and its readers with the same lock.

Likely follow up: Would a successful Future.get() let you read a task's ordinary, non-volatile result field?
