Java onlyThree threads run as below. data is a plain int starting at 0; flag1 and flag2 are volatile boolean fields starting false. What does thread 3 print?
Why. Happens-before is transitive. Thread 1's write of data comes before its volatile write of flag1 in program order; that write happens-before thread 2's read that sees it; thread 2's read is before its volatile write of flag2; and that write happens-before thread 3's read that sees it. Chain them and the write of data happens-before thread 3's read, so 7 is guaranteed on every JVM and CPU. Edges compose across threads, which is why a value can be safely handed through several stages of a pipeline.
C++ onlyThree threads run t1, t2 and t3. What does t3 print, and is there a data race?
Why. Each acquire load that reads a release store synchronizes with it, and happens-before is transitive: data = 7 comes before the release of flag1, which synchronizes with t2's acquire, which comes before the release of flag2, which synchronizes with t3's acquire, which comes before the read of data. So the write happens-before the read: no race, always 7. ThreadSanitizer reported nothing on this program. seq_cst is only needed when threads must agree on a single order of several independent variables.

A lock-free stack pops with old = head; next = old.next; CAS(head, old, next), retrying on failure. Thread 1 reads old = node A and next = node B, then is preempted. Thread 2 pops A, pops B and frees it, then pushes A back (the same node, at the same address). Thread 1 resumes and runs its CAS. What happens?
Why. The CAS compares the current head with A; it does not remember that the head changed in between. A is back at the head, so a successful CAS installs the stale saved B and corrupts the stack. This is ABA. A pointer plus a version counter can reject this stale update, but in C++ tagging alone does not keep a node alive while it is read: the algorithm also needs safe reclamation, such as a correctly implemented hazard-pointer or epoch scheme. Java garbage collection prevents B from being freed while a thread still holds its reference, but reusing or reinserting the same node A can still cause logical ABA. GC is not a general substitute for checking the stack algorithm's reuse rules.
Java onlyA writer thread replaces the config and reader threads use it. Which statement is true?
Why. Final field semantics guarantee that any thread that obtains a reference to an object after its constructor finishes sees the final fields, and what they point to, as the constructor left them. So a half built Config is impossible here. But nothing makes the write to the plain current field visible to readers at any particular time: there is no happens-before edge for the reference itself. volatile adds that edge, which is why immutable objects published through a volatile or atomic reference are the standard way to swap configuration.
C++ onlyA writer thread replaces the config and reader threads copy it. Which statement is true?
Why. Different shared_ptr objects that share one control block may be used from different threads, because the count is updated atomically. One shared_ptr object read and written at the same time is a data race like any other: the copy reads the control block pointer and then increments its count, and the assignment can release the old block, possibly freeing it, in between. ThreadSanitizer reported a race on a test of this exact pattern. libstdc++ supports std::atomic<std::shared_ptr<T>>; Apple's libc++ did not compile it in our test, where the older std::atomic_load and std::atomic_store overloads (deprecated in C++20) or a mutex are the portable choice.
Which statements about fair and unfair (barging) locks are true?Select all that apply
Why. An unfair lock may let a running thread acquire ahead of parked waiters, reducing handoff delay and often improving throughput under contention. That is a workload-dependent benefit, not a promise to save one wakeup and context switch on every handoff. A fair ReentrantLock favors the longest-waiting contender for its fairness-respecting acquisition methods, but untimed tryLock() explicitly ignores that policy and may barge. Fair lock ordering does not impose FIFO scheduling or a fixed waiting-time bound, and C++ std::mutex promises no FIFO policy.
A producer puts exactly one poison pill into a shared blocking queue when it has no more work. Three consumer threads loop: take an item; if it is the poison pill, exit; otherwise process it. After the producer finishes and every real item has been processed, how many consumers have exited?
Why. A pill is an ordinary queue element: one take() removes it, so exactly one consumer sees it and exits. The other two block on an empty queue, and a blocking queue knows nothing about the producer's lifetime. Fixes: put one pill per consumer, have the consumer that takes the pill put it back before exiting, or close the queue with a flag plus a wakeup (for example interrupting the consumers, or a queue with an explicit close() that wakes all takers).
Round robin with a time quantum of 2. Processes (arrival time, CPU burst): P1 (0, 5), P2 (1, 3), P3 (3, 1), P4 (5, 2). A new arrival joins the tail of the ready queue; a preempted process goes to the tail after any process that arrived during its slice. What is the average waiting time?
Why. Schedule: P1 runs 0 to 2 (P2 arrived at 1, queue P2 P1). P2 runs 2 to 4 (P3 arrived at 3, queue P1 P3 P2). P1 runs 4 to 6 (P4 arrived at 5, queue P3 P2 P4 P1). P3 runs 6 to 7 and finishes. P2 runs 7 to 8 and finishes. P4 runs 8 to 10 and finishes. P1 runs 10 to 11 and finishes. Waiting time = finish minus arrival minus burst: P1 11 minus 0 minus 5 = 6, P2 8 minus 1 minus 3 = 4, P3 7 minus 3 minus 1 = 3, P4 10 minus 5 minus 2 = 3. Total 16, average 4. 6.75 is the average turnaround time, 3.25 is FCFS, and 5.5 is what you get if you treat all four as arriving at time 0.
Banker's algorithm with resource types A, B and C, currently Available = (3, 1, 0). P0 requests (0, 1, 0). Should the request be granted?
ProcessAllocation (A B C)Max (A B C)
P01 3 23 5 4
P12 1 25 2 2
P21 0 22 3 4
P32 0 14 0 2
Why. Need = Max minus Allocation: P0 (2, 2, 2), P1 (3, 1, 0), P2 (1, 3, 2), P3 (2, 0, 1). The request (0, 1, 0) is within P0's need and within Available, so the algorithm pretends to grant it: Available becomes (3, 0, 0) and P0's need becomes (2, 1, 2). Now P0 needs B and C, P1 needs B, P2 needs B and C, and P3 needs C, and none of that is available, so no process can be guaranteed to finish: unsafe, so the request is refused. Before the request the state is safe (P1 can finish first with exactly (3, 1, 0), then P0, P2 and P3), which is the trap: Banker's checks the state after the grant, and the single unit of B is exactly what P1 needs.

Why. System.identityHashCode is stable for an object's lifetime but not unique. Java onlyawaitReady must give up and return false if ready has not become true within 2 seconds. What is wrong?
Why. wait(long) returns void whether it was notified, timed out or woke spuriously, so the method cannot tell them apart and waits again; a real run was still waiting after 5 seconds. Compute a deadline once and wait only for what remains: long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(2); then in the loop, if the remaining time is not positive return false, else TimeUnit.NANOSECONDS.timedWait(this, remaining). With ReentrantLock, Condition.awaitNanos returns the remaining time for exactly this loop.
C++ onlyawait_ready must give up and return false if ready has not become true within 2 seconds. What is wrong?
Why. Every pass through the loop starts a fresh 2 second wait, so a timeout just leads to another wait; a real run was still waiting after 5 seconds. Use the predicate overload, which computes the deadline once and returns the predicate's final value: return cv.wait_for(lk, std::chrono::seconds(2), [&] { return ready; });. It returns false on timeout (a test returned false after 2004 ms) and also handles spurious wakeups. With an explicit deadline, wait_until does the same.
A hand written read-write lock: readLock waits while a writer is active, then increments readers; writeLock waits while a writer is active or readers > 0, then marks a writer active; each unlock updates the state and notifies all waiters. Readers arrive steadily, so at any moment at least one reader holds the lock. What happens to a writer?
Why. This readers-preference lock admits new readers even while a writer waits. With continuously overlapping readers, readers never becomes 0, so the writer keeps failing its condition after every wakeup and may starve. Readers still finish and new readers still enter, so this is not a total deadlock. Writer preference can block new readers once a writer queues, but it can then starve readers; a fair admission policy must consider both groups. Java's nonfair ReentrantReadWriteLock has implementation heuristics against writer starvation, but its API still permits indefinite postponement; C++ std::shared_mutex also provides no portable starvation-freedom guarantee.
