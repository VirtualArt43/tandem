Iterators and ConcurrentModificationException

How Java iterators work, why changing a collection inside its own loop throws even with one thread, and how concurrent collections iterate instead.

Asked atApple
Before this:The collections you will use

A for-each loop hides an object that remembers where it is in the collection. Change the collection behind its back and Java may throw ConcurrentModificationException, often with no second thread anywhere in sight. In threaded code that exception is the lucky outcome.

In plain words

Picture a teacher taking attendance by running a finger down the class register. If someone tears out a page while she is halfway down, her finger now points at the wrong child, or at nothing. A careful teacher notes the page count when she starts, and before reading each name she checks the count again. If it changed, she stops and says so, rather than marking the wrong child absent.

That careful teacher is a Java iterator. The page count is a modification counter, and "stop and say so" is ConcurrentModificationException. Notice two things. The person who tore out the page may be the teacher herself, so no second thread is needed. And because she only checks at certain moments, some changes slip past her.

Why this matters for concurrency

  • Iterating a shared ArrayList or HashMap while another thread writes to it is a data race. The exception is the lucky outcome; the unlucky ones are skipped elements, nulls and totals that look fine but are wrong.
  • Collections.synchronizedList makes each call safe, but a loop is many calls. You must hold the list's own lock for the whole loop, and interviewers ask why.
  • The concurrent iterators discussed below tolerate structural changes without this exception. They either work on a snapshot or are weakly consistent, and saying exactly what each promises is a common senior follow up.
  • Iteration is a compound action: one hasNext, next pair after another. Everything you know about check then act applies to it.

What an iterator is

An Iterator<E> is a small cursor object with three methods:

  • hasNext(): is there another element?
  • next(): return it and move the cursor forward.
  • remove(): remove the element that the last next() returned. Some collections do not support it and throw UnsupportedOperationException.

Every collection is Iterable, which means it has an iterator() method that hands out a fresh cursor. The for-each loop is only syntax for that cursor:

For arrays, for-each compiles to a plain index loop instead, and arrays never throw this exception. The important detail is where the state lives: the position belongs to the iterator object, not to the collection. Two threads with two iterators over a list that nobody changes do not disturb each other. The trouble always comes from changing the collection while an iterator is in use.

How fail-fast iteration works

ArrayList, LinkedList, HashMap, HashSet, TreeMap and most of java.util hand out fail-fast iterators. The mechanism is a counter:

  1. The collection has an int field called modCount. Every structural modification adds one to it: a change to the size, such as add, remove or clear, or anything else that would confuse an iteration in progress, such as ArrayList.sort.
  2. When you create an iterator, it copies the current value into its own field, expectedModCount.
  3. Every next() and every iterator remove() first compares the two. If they differ, it throws ConcurrentModificationException.

Not every write counts. list.set(i, x) replaces an element without changing the size, and map.put(k, v) for a key that is already present only replaces a value, so neither trips the check. Adding a new key to a HashMap while you iterate it does.

After the removal the list has 2 elements and the cursor is at 2. hasNext() only asks "is the cursor different from the size?", gets false, and the loop ends without ever calling next(), the only place the check runs. The loop silently never visited "c". Removing "c" leaves the cursor at 3 and the size at 2, so hasNext() says true, next() checks the counter, and the exception fires. Notice also that the list is already changed when the exception arrives: the exception reports the problem, it does not undo anything.

Best effort, not a guarantee

The ArrayList documentation says fail-fast behavior works on a best-effort basis and must only be used to detect bugs, never relied on for correctness. Two reasons. The check only runs inside next() and remove(), so a change made just before the loop ends goes unnoticed, as you just saw. And modCount is a plain int, not volatile and not guarded by any lock, so another thread's changes may never become visible to the iterator at all. If you see the exception, you have a bug. If you do not see it, you may still have one.

Removing safely while you iterate

You have four tools, from best to worst:

  1. removeIf (Java 8 and later): list.removeIf(s -> s.startsWith("tmp"));. It is the clearest, and on an ArrayList it is one pass, while calling remove repeatedly shifts the tail every time and can cost O(n squared).
  2. Iterator.remove(): write the loop with an explicit iterator and call it.remove() instead of list.remove(x). It removes the element the last next() returned and updates expectedModCount, so the iterator stays in sync. Call it at most once per next(), and never before the first next(), or you get IllegalStateException.
  3. Remove through a map's views: map.entrySet().removeIf(...), map.values().removeIf(...) and map.keySet().removeIf(...) all remove from the map itself.
  4. Collect, then change: gather what to remove in a separate list and remove after the loop, or iterate over a copy such as new ArrayList<>(list).

The index loop does not throw, because it uses no iterator, but it is still wrong: after remove(i) the next element moves into position i, and i += 1 steps over it. If you must remove by index, walk backwards with for (int i = list.size() - 1; i >= 0; i -= 1).

Without it the reader may not see the change at all, may see the new size before the new element, or may fail with a different exception. Iterating a collection that is not thread-safe while another thread modifies it is a data race, whether or not the exception appears. You have three honest fixes:

How the concurrent collections iterate

The iterators discussed here tolerate concurrent changes without ConcurrentModificationException. This is not a promise about every operation or view: for example, a CopyOnWriteArrayList sublist can throw that exception after the parent list changes. The main iteration strategies come in two flavors.

Snapshot iterators. CopyOnWriteArrayList and CopyOnWriteArraySet generally copy their backing array when contents change. An iterator keeps a reference to the array that existed when it was created, so it is a snapshot iterator: no ConcurrentModificationException and no later structural changes, while its remove() throws UnsupportedOperationException. The snapshot holds references, so it does not freeze mutable elements. This is useful for read-mostly lists such as event listeners, and expensive when writes are frequent, because each append copies the array.

Weakly consistent iterators. ConcurrentHashMap, ConcurrentSkipListMap, ConcurrentLinkedQueue and the blocking queues promise three things: the iterator can run while other operations proceed, it never throws ConcurrentModificationException, and every element present when it was created (and not removed since) is returned exactly once, while changes made after that may or may not show up. It is not a snapshot: a loop that sums the values can produce a total that never existed at any single instant. In the same spirit, size() on a ConcurrentHashMap is only an estimate while writers are active.

Interviewers sometimes call the iterators of the concurrent collections "fail-safe". The precise words are snapshot for copy-on-write, and weakly consistent for the rest, and using them signals that you know the difference. The core lesson Iterating while others write goes deeper.

Step 3, request threads join in. Now requests add and refresh sessions while the cleaner runs. A HashMap is wrong in every line now, not only in the loop, so the field becomes a ConcurrentHashMap. The same removeIf line is now allowed to run while requests write: it never throws, and it does not block writers for the whole sweep. A session added during the sweep may or may not be examined, which is fine for a cleanup job, because the next sweep catches it.

Step 4, the race to close. Between "this session is expired" and "remove it", a request may refresh the session. Make the removal conditional with the two-argument remove, which the ConcurrentMap interface documents as atomic. (Since JDK 9, ConcurrentHashMap's own values().removeIf happens to remove each entry this way internally, but that is an implementation detail; the explicit loop below states the guarantee you rely on.)

This works when a refresh replaces the session with a new immutable object that does not compare equal to the old value. Equality must include the expiry or version, or use object identity. If requests instead mutate the Session object in place, or equality ignores the refreshed state, the condition can still pass and the race is back. Immutable, distinguishable versions plus conditional removal close the gap. That sentence is worth saying out loud in an interview.

Common mistakes

  • Calling the collection's own remove inside a for-each over it. Use removeIf, or an explicit iterator with it.remove().
  • Treating "no exception" as "no bug". Removing the second to last element ends the loop quietly and skips the last one, and changes from other threads may never be noticed.
  • Catching ConcurrentModificationException and retrying or ignoring it. It reports a bug in how the collection is shared or iterated. Fix the iteration.
  • Removing by index in a forward loop. Every removal makes the loop skip the next element. Use removeIf, or loop backwards.
  • list.remove(1) on a List<Integer>. That removes the element at index 1. To remove the value 1, write list.remove(Integer.valueOf(1)).
  • Looping over a synchronized wrapper without synchronized (wrapper). Each call is safe; the loop is not.
  • Using CopyOnWriteArrayList for a list that is written often. Changes generally copy the whole backing array, so frequent updates are expensive.
  • Expecting a ConcurrentHashMap loop to be a consistent snapshot. It is weakly consistent. If you need a consistent view, copy under a lock that every writer also holds, or design for an immutable snapshot.
  • Confusing UnsupportedOperationException with this problem. List.of(...) is immutable and Arrays.asList(...) is fixed-size, so remove on them throws UnsupportedOperationException, with or without a loop.

In the interview

Iterators come up in three ways. As code reading: "what does this print?" with a removal inside a for-each. As a follow up to a thread-safe collection you just built: "how would a caller iterate it while other threads write?" And as a design question, as in an Apple report where many threads each ran an iterator over the same binary search tree, and the interviewer asked about thread safety and what changes once there are writers.

ConcurrentModificationException is a bug detector, not a concurrency control. The modification count is a plain int checked at specific iterator operations, so detection is best effort. If other threads write, I either hold the collection's lock from iterator creation through the whole loop, copy it under the lock and iterate the copy, or switch to a concurrent collection and accept snapshot or weakly consistent iteration.
Many readers with their own iterators over a tree that nobody modifies are safe once the tree is safely published, because the cursor lives in each iterator. With writers, I would pick a read-write lock held for the whole traversal, immutable snapshots, or a concurrent ordered collection with weakly consistent iteration. A version counter alone does not make pointer traversal safe during mutation.

Follow ups to expect: "Is the exception guaranteed?" (no, and say why). "Which iterators tolerate concurrent changes?" (name snapshot iteration on CopyOnWriteArrayList and weakly consistent iteration on ConcurrentHashMap). "Would Collections.synchronizedMap fix this loop?" (only if you lock the map around the loop). "Why did removing the second to last element not throw?" (hasNext() compares the cursor with the size and never checks the counter). "Can two threads share one iterator over a ConcurrentHashMap?" (no: the cursor itself is unsynchronized state, and the ConcurrentHashMap documentation says its iterators are designed to be used by only one thread at a time; give each thread its own iterator, or hand out the work through a thread-safe queue). "What about list.forEach(x -> list.remove(x))?" (on an ArrayList it throws too: forEach compares modCount before each element, stops at the first change, and then throws ConcurrentModificationException, so unlike the for-each loop it does not stay quiet when you remove the second to last element).

Senior depth

The modification count is an optimistic version check: read a version, do the work, check the version again. StampedLock.tryOptimisticRead and optimistic locking in databases are the same idea done properly, with correct memory ordering and a retry instead of an exception.

When you design an iterator for your own thread-safe structure, there are exactly three honest choices:

  • Block writers for the whole traversal. Simple and consistent; writers wait.
  • Give readers a frozen version. Copy-on-write, or a persistent structure that copies only the changed path and publishes a new root through a volatile field. Readers never block; writers pay for the copying.
  • Let readers walk a structure that is safe to read while it changes. Weakly consistent, which needs every node to be safely published.

Name the one you picked and what it costs readers and writers.

Key takeaways

  • A for-each loop is an iterator in disguise, and the position lives in the iterator object.
  • Fail-fast iterators compare modCount with their expectedModCount in next() and throw on a structural change, even in one thread.
  • The check is best effort: no exception does not mean no bug.
  • Remove while iterating with removeIf or Iterator.remove, never with the collection's own remove.
  • With other threads writing: lock the whole loop, iterate a copy, or use a concurrent collection whose iterators are snapshots (CopyOnWriteArrayList) or weakly consistent (ConcurrentHashMap).

Explain
An interviewer shows a for-each loop that calls list.remove(item) and asks why it throws ConcurrentModificationException when the program has only one thread. Answer as you would out loud, and give the fix.
Model answer

The for-each loop is compiled into an iterator. An ArrayList keeps a modification counter, modCount, that goes up on every structural change, and the iterator copies it when it is created and compares the two on every next(). Calling list.remove changes the counter behind the iterator's back, so the following next() sees a mismatch and throws. Threads have nothing to do with it; the name means "the collection was modified while you were iterating it".

The fix is list.removeIf(predicate), or an explicit iterator with it.remove(), which removes through the iterator and updates its expected count. I would add that the check is best effort: removing the second to last element ends the loop quietly and skips the last element, so the absence of the exception does not prove the loop is right.

Design
Many threads each iterate the same binary search tree with their own iterator. Occasionally one thread inserts a key. What can go wrong, and what are your options?
Model answer

Readers alone are fine: each iterator holds its own cursor, and a tree that nobody modifies is safe to read from many threads once it has been safely published. The insert is the problem. Without synchronization a reader can observe a half-finished insertion or rebalancing: a child pointer that is set while the new node's fields are not yet visible, or a rotation that hides a subtree from the traversal. It is a data race, and the results are not bounded to "slightly stale".

Options, with costs. One: a ReentrantReadWriteLock, with each reader holding the read lock from iterator creation through its whole traversal and the inserter taking the write lock; simple and consistent, but a long scan delays writers. Two: copy-on-write with an immutable persistent tree; the writer copies the changed path, publishes the new root through a volatile field or AtomicReference, and each iterator captures one root and sees a consistent snapshot without blocking. A balanced tree needs O(log n) new nodes per insertion; multiple writers must serialize publication or retry with compare-and-set to avoid losing updates. Three: use a ConcurrentSkipListMap if ordered keys with weakly consistent traversal meet the requirement. A version counter alone is insufficient: readers must also be able to traverse safely while links change, before they ever reach the validation step. For a read-heavy tree with small updates I would choose the persistent snapshot.

"This single-threaded for-each loop removes from an ArrayList. Sometimes it throws ConcurrentModificationException and sometimes it quietly skips an item. Explain both outcomes and fix it."
What a strong answer covers
  • For-each over ArrayList uses an iterator with an expected modification count
  • Direct structural removal changes the list's count without updating the iterator
  • A later next() call detects the mismatch even with only one thread
  • Removing b from a, b, c leaves cursor and size at two, so hasNext() ends the loop and skips c
  • Use removeIf or Iterator.remove; neither supplies synchronization for concurrent writers
  • Fail-fast checks are best effort and cannot establish thread safety
How a senior would say it
The loop invalidates its own iterator by removing directly from the list. No second thread is needed. A for-each over an array list uses an iterator, which remembers the modification count it saw at creation. Removing through the list changes that count but does not update the iterator's expected count. A later next call detects the mismatch and throws. The quiet case comes from where the checks happen. In the OpenJDK implementation, consider a list containing a, b, and c. After the iterator returns b, its cursor is two. Removing b makes the list size two. Has-next now says there is nothing left, so next is never called again and c is skipped without an exception. I would use removeIf for a straightforward filter, or an explicit iterator and its remove method when I need more control. Those maintain the iteration correctly in one thread. They do not make an ordinary list safe against concurrent writers. For sharing I still need a locking or snapshot policy. Fail-fast detection is useful evidence of a bug, never proof that a successful run was correct.

Likely follow up: Why can list.set avoid the modification-count check while still being unsafe against another thread's reads?

Out loudabout 85 s
"You need to traverse a shared collection while writers keep working. Compare locking, copy-on-write and ConcurrentHashMap iteration, and tell me what the caller actually sees."
What a strong answer covers
  • Holding the same lock as writers, from iterator creation through the full traversal, excludes their changes
  • Copy under that lock, then process the copy outside it; copying costs O(n)
  • CopyOnWriteArrayList iterators retain the array present at creation and ignore later structural changes
  • That snapshot copies references, so mutable element state needs separate protection
  • ConcurrentHashMap iteration visits entries that remain present throughout traversal; concurrent changes may or may not appear
  • Choose by consistency needs and write frequency; a live aggregate may match no single instant
How a senior would say it
I would choose based on whether the caller needs one coherent view or can tolerate a moving view. Holding the same lock as every writer, from iterator creation through the entire traversal, gives a stable structure but delays writers for the whole scan. Copying under that lock lets me release it before processing, at the cost of a linear copy. For a listener list with rare changes, CopyOnWriteArrayList is another option. Its iterator retains the array present when it was created, so later additions and removals do not change that traversal. The snapshot contains references, though. It does not freeze mutable objects stored in those slots. With ConcurrentHashMap, iteration can proceed during updates without a concurrent modification exception, but it is weakly consistent. Entries that remain present throughout traversal are visited once; later changes may or may not appear. A sum across entries can therefore describe no single moment of the map. I would accept that for approximate monitoring, but use coordinated locking or published immutable snapshots when the result must be coherent. The choice is a consistency contract as well as a performance choice.

Likely follow up: Would copying a ConcurrentHashMap into a HashMap without coordinating writers create a point-in-time snapshot?

Out loudabout 80 s
"A cleanup thread checks that a session is expired, then removes its key from a ConcurrentHashMap. A request sometimes refreshes the session and still loses it. Walk me through the race."
What a strong answer covers
  • A thread-safe map does not make the expiry check and unconditional removal one atomic action
  • The cleaner can read an expired value, then a request replaces it before removal
  • Use remove(key, observedValue) to compare and remove atomically
  • Refresh must replace immutable values and equality must distinguish the refreshed version
  • Mutating the same object or ignoring the expiry version in equals leaves the race open
  • Weakly consistent cleanup may defer concurrent changes; it is not a complete snapshot sweep
How a senior would say it
The race is between the decision and the removal. The cleaner reads an expired session. Before it removes the key, a request installs a refreshed session under that key. An unconditional remove then deletes the fresh value, even though every map call was individually safe. I would retain the value I checked and call the two-argument remove with the key and that observed value. The map atomically removes only if the current value still compares equal to what I observed. That condition needs a careful value design. Refreshes should replace an immutable session, and equality must distinguish the refreshed expiry or version, or use object identity. If a request mutates the same session object in place, the map still contains that object and the conditional removal can succeed after the refresh. A new object whose equality ignores the refresh version has the same problem. Finally, the scan remains weakly consistent. It need not inspect every concurrent change during this pass. That is acceptable for periodic cleanup when later passes can revisit entries, but it is not an exact snapshot of all expired sessions.

Likely follow up: If sessions must remain mutable, how would you coordinate refresh and expiry removal under the same lock or map operation?
