Thread-safe hit counter

Thread-safe structuresmedium30 minLeetCode 362, then many threadsDatabricks

Picture several ticket scanners updating the same attendance counter. Every scan must count once, and old scans must leave the five-minute window at exactly the right second. Apple reports ask which parts need synchronization; Uber reports extend this to per-key expiry counts. Databricks is tagged for the base problem, with a race-condition follow up in an unverified crowd-sourced report.

The task

Count hits over a sliding five-minute window, with many threads calling at once:

  • hit(timestampSec) records one hit at that second.
  • getHits(timestampSec) returns the number of hits in the 300 seconds ending at that second: hits with a timestamp t such that timestampSec - 300 < t <= timestampSec.

Timestamps are nonnegative signed 64-bit whole seconds, including zero and values beyond 32 bits. Let H be the greatest hit timestamp received so far. A new hit may arrive out of order, but its timestamp is never below H - 299; the same bound holds across overlapping calls. Every hit within that bound must be recorded, including a late hit exactly 299 seconds behind. Inputs guarantee that every 300-second window contains at most Integer.MAX_VALUE or INT_MAX hits, so the return type cannot overflow.

Call getHits(q) with q at least as large as every hit timestamp completed before or overlapping that query. Historical queries below that bound are outside the contract. Query times themselves need not be monotone: a query far in the future does not advance H or discard stored hits. For example, after hit(100), getHits(1000) returns zero; after a subsequent hit(101), getHits(101) returns two.

After writers finish, counts must be exact. While writers run, a query must return a total that existed during its call. At a fixed query second with all overlapping hits inside its window, repeated reads cannot decrease. Counter instances are independent. Negative timestamps, hits more than 299 seconds late, and overflowing counts are outside the input contract.

Rules: use bounded storage independent of the hit rate and elapsed time, and avoid allocating an object for every hit. The classic answer is 300 buckets, one per second of the window, each remembering which second it currently counts. The allocation regression test permits under 64 KiB of allocation for 50,000 hits after warmup, allowing small lazy initialization costs.

What the tests check

  • An empty counter, repeated hits at timestamp zero, independent instances, and exact inclusion at age 299 and exclusion at age 300.
  • Repeated hits, idle gaps, three complete ring generations with all 300 seconds visited out of order, and unequal counts checked against an independent timestamp oracle as the window expires.
  • A future query does not erase hits or cause a subsequent valid arrival to be dropped.
  • 8 writers contend on one second over repeated rounds, including bucket resets. Reads during a round stay between its starting and ending totals and never decrease; completed rounds have exact totals.
  • 4 writers concurrently visit different, out-of-order seconds over three full ring generations. A barrier establishes an exact intermediate count, then reads race with the remaining writes. Each read is bounded below by hits completed before it starts and above by hits invoked before it ends. Queries after completion check the counts as each window expires.
  • A fixed epoch second near 1.8 billion under concurrent writers, timestamps crossing both 32-bit limits, and queries up to the largest signed 64-bit value.
  • An allocation regression: 50,000 hits in one second allocate under 64 KiB after warmup. Java measures the calling thread's allocated bytes when supported; C++ measures ordinary operator new allocation on that thread. This catches common per-hit storage designs; it is not a proof of bounded retained memory for every possible allocator or implementation.
  • Worker exceptions and unfinished operations fail the run. Watchdogs bound the suite at 3.7 seconds in Java and 7 seconds in C++; C++ also runs under ThreadSanitizer. Scheduling stress supplements deterministic boundary checks and does not enumerate every interleaving.

Taught in: The lost update: read, modify, write

Open them one at a time. Each one gives away a little more.

Single-threaded first. Use two arrays of 300: times[i] is the second that bucket i currently counts and counts[i] its hits, with i = t % 300. A hit at a second the bucket does not hold yet starts that second over, at count zero. getHits(t) adds up the buckets whose second is within the window.
Now look for the shared state. counts[i] += 1 is a read-modify-write: two threads lose an increment. And "if times[i] is not t, reset the bucket" is a check-then-act: two threads can both decide to reset and erase each other's hits, even if every field is an atomic.
One lock around both hit and getHits makes the compound updates and reads atomic. A CAS on a packed second and count is a follow up with extra timestamp-width and snapshot assumptions; it is not a drop-in replacement for this full-width API.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Now count per key, plus a total across all keys, and purge stale hits when reading. Uber reports describe put_element, get_element_count and get_total_elements. How does synchronization change?
Start with one lock guarding the key map, expiry bookkeeping and total. Purge expired contributions before answering either a key query or a total query, and remove empty keys. Reading only one key must not leave other expired keys in the total, so use a global expiry index or sweep all keys for a total query. Per-key locks improve concurrency, but an atomic total alone does not coordinate expiry, map membership and an exact global snapshot. Define that snapshot protocol before replacing the single lock.
Can you replace the lock with CAS?
With timestamps restricted to unsigned 32 bits and counts fitting the low 32 bits, pack both fields into one 64-bit word. CAS then makes the reset and increment one atomic action. The notes show this restricted variant. It cannot represent the full timestamp range of the task. Also establish the read guarantee and whether 64-bit atomics are lock-free on the target runtime; using an atomic type alone is not a portable lock-free proof.
A million hits per second land on the same counter. What breaks?
Every hit fights for one bucket's cache line, so the CAS version can spend substantial time retrying and moving cache-line ownership between cores. Stripe it: give each bucket several cells (per core, or hashed by thread, the idea behind Java's LongAdder) and sum them when reading. Writes contend less and reads do more work. LongAdder.sum() is not an atomic snapshot, so relaxed telemetry is a different contract from an exact counter; describe the synchronization needed if exact snapshots remain required.
Why not keep a queue of hit timestamps?
A queue stores the supplied timestamp resolution, which is seconds in this API. Its memory and cleanup grow with the hit rate: a million hits a second means a million queue entries to store and later remove. Buckets fix memory at 300 slots and are exact for this whole-second contract. Supporting millisecond inputs would require a finer representation.
What if hits arrive out of order across threads?
Accept every hit within 299 seconds of the greatest hit timestamp. Such hits use distinct bucket indices unless their timestamps are equal, so an earlier timestamp in a different bucket must not be dropped. Two different seconds sharing a slot differ by at least 300; a newer second can replace that slot because the older one is outside every supported query window. Reads do not advance the hit clock. Arbitrarily late arrivals and historical queries require a different retention policy.
How would you count hits across many servers?
Count locally per server in per-second buckets, then aggregate: push per-second totals to a stream and sum them centrally, or increment per-second keys in a shared store such as Redis with an expiry on each key and sum the last 300 keys on read. Exactness across machines costs coordination; most systems accept a few seconds of lag.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Divide the window into 300 one-second buckets used as a ring: second t goes to bucket t % 300. Each bucket stores the second it currently counts and its count. A hit for a second the bucket does not hold yet starts it over at zero; getHits(t) sums the buckets whose second lies in (t - 300, t]. Memory is fixed at 300 buckets whatever the hit rate. The invariant is each bucket's count is exactly the number of hits recorded at the second it holds, and concurrency threatens it in two places.

The two races

  • The lost update. counts[i] += 1 is a read-modify-write; two threads read the same count and one increment vanishes.
  • The reset check then act. Making each field atomic is not enough:

The reference solution

One lock around both methods. hit and getHits each hold it for O(1) and O(300) work respectively, which is plenty for most uses and easy to prove correct. Start there in the interview.

Senior depth: one packed bucket per CAS

This follow up deliberately narrows timestamps to unsigned 32 bits, unlike the runnable task. Pack the second and count into one 64-bit word per bucket, so one successful compare-and-swap checks and updates both. A hit can require several attempts. Keep the task's total-count limit so the count field and int return value do not overflow.

getHits reads individual buckets at different instants. Under this task's query restriction, no overlapping hit is later than the query: a reused slot's previous second is already outside that window, and the total for the fixed window only increases one hit at a time. The scan therefore returns a total between the values at its invocation and response, which existed during the call. This argument does not extend to arbitrary historical queries, racing future timestamps, decrements, or snapshots of the individual buckets. The full-width reference avoids the packing restriction by locking both methods.

Cost

The reference does O(1) work per hit and O(300) per query, excluding lock waiting, with O(300) storage. All callers serialize through one lock. Packed CAS permits independent bucket updates, but retries are unbounded for one unlucky caller; weak CAS may also fail spuriously. Different words can share a cache line, so separate buckets do not eliminate cache contention.

How to say it in the interview

I keep 300 buckets, one per second of the window, each storing the second it counts and its count; a hit for a new second resets its bucket, and getHits sums the buckets inside the window. Memory is constant whatever the rate. Under threads there are two races: the increment is a read-modify-write, and the reset is a check-then-act, so atomic fields alone still lose hits. The simple fix is one lock around both methods. If we narrow the timestamp range, I can pack a bucket into one word and use CAS so the check and reset stay together. I would first state the read guarantee and check whether the target provides lock-free atomics.
