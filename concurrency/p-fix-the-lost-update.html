Fix the metrics that undercount

Bug huntswarm-up15 mindebugging round style

A warm-up in the style of a debugging round: the code compiles, its single-threaded unit tests pass, and production numbers are wrong. Find the cause, then fix it with the smallest change you can defend.

The incident

INC-4127: the metrics page undercounts requests

Last week the request handler pool went from 1 thread to 16. Since then:

  • The dashboard's request total runs 2 to 15 percent below the load balancer's count for the same minute. The gap grows with traffic.
  • The per endpoint counts shown under the total do not add up to it: sometimes a little more, sometimes a little less.
  • One screenshot shows more errors than requests.
  • Nothing in the logs, no exceptions. The unit tests, which call record from one thread, all pass.

The class is in your editor. Every request handler thread calls record once per request. A dashboard thread calls total and snapshot every few seconds.

What the class promises. Every recorded request is counted exactly once in the total, in its endpoint's count, in the errors if it failed, and in the maximum latency. A snapshot's numbers belong together, because the dashboard shows them side by side: the per endpoint counts add up to the total, and errors never exceed the total.

What the tests check

  • One thread: three requests give an exact snapshot.
  • 8 handler threads record 20,000 requests each in Java (2,000 in C++) over 4 endpoints, after one startup request per endpoint: the total, each endpoint's count, the errors and the maximum latency must be exact.
  • While they run, a dashboard thread keeps taking snapshots: every one must add up, show no more errors than requests, and never show a smaller total than the one before.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: The lost update: read, modify, write

Open them one at a time. Each one gives away a little more.

total += 1 is one line of code. How many steps is it for the processor, and what happens when two threads run those steps at the same moment?
Every field here is shared and updated by a read, a change and a write: the total, the errors, the maximum (a compare, then a write), and the map's get followed by put. Atomics would make each counter exact on its own. Would they also make a snapshot add up?
The snapshot promise ties all the fields into one invariant, so they need one lock. Make record, total and snapshot all hold the same lock: synchronized in Java; in C++ one std::mutex, declared mutable so the const readers can lock it, with a std::lock_guard in each method.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why not make each counter an AtomicLong or std::atomic and the map a ConcurrentHashMap?
Each number would then be exact, and the total would match the load balancer. But a snapshot reads the fields one after another while writers keep going, so the total and the per endpoint counts come from different moments and do not add up. Atomics fix a lost update in one variable; they do not keep an invariant that spans several. Say which promise you need before you pick the tool.
With 64 handler threads the single lock shows up in profiles. What would you do?
Stop sharing on the hot path. Give each thread (or each of a few stripes) its own stats object with its own lock, so writers rarely contend, and let snapshot lock and sum the stripes. If the dashboard can live with numbers from slightly different instants, LongAdder in Java or striped atomics in C++ are cheaper still. The decision is consistency of a snapshot against write throughput, and most metrics systems choose throughput.
Would volatile on the fields have fixed it?
No. volatile makes each single read and write visible to other threads, but total += 1 is still a read, an add and a write, and two threads can interleave between them. It is a visibility tool, not an atomicity tool.
How would you keep the maximum with atomics and no lock?
The maximum is a check-then-act: compare, then write. With atomics it needs a compare-and-swap loop: read the current maximum, stop if yours is not larger, otherwise CAS it in and retry on failure. Java wraps that loop as max.accumulateAndGet(latency, Math::max). Standard C++20 has no atomic maximum, so you write the compare_exchange_weak loop yourself.
How would you have caught this before production?
In C++, one run under ThreadSanitizer flags the data race on the first line of record. In Java, a stress test like this harness, comparing exact counts after a few hundred thousand calls from many threads. And in review: every shared mutable field should say which lock guards it, and a field that names no lock is the first place to look.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The bug

Two bugs, one cause: shared state with no lock at all. First, every update is a read-modify-write, so concurrent handlers overwrite each other's increments: a lost update. Second, snapshot reads the fields one by one while handlers are changing them, so a snapshot mixes moments and breaks the dashboard's invariant even when no update is lost.

The fix

One lock for all four fields, held by every method that reads or writes them. Holding it in record makes the four updates one indivisible step, so no increment is lost and no reader sees a half recorded request. Holding it in snapshot makes the copy happen at one instant between two record calls.

Why this is the right size of fix

  • The readers need the lock too. Locking only record would stop lost updates but leave snapshot reading mid-update: still inconsistent in Java, and still a data race (undefined behaviour) in C++.
  • total() needs it as well, even though it reads one field: in Java without the lock it may return a stale value forever, and in C++ the unsynchronized read is a data race.
  • The work under the lock is tiny, a few additions and one map update, so one lock is cheap until profiles say otherwise. Copying the map in snapshot is O(endpoints), which is small and fixed.
  • Atomics would be a partial fix that passes the count test and fails the snapshot test. That is the trap this problem sets.

How to say it in the debugging round

All four fields are shared, written by every handler with read-modify-write, and nothing guards them, so increments are lost. And the dashboard's promise, that a snapshot adds up, ties the fields together, so per-field atomics would not be enough. The smallest correct fix is one lock that record, total and snapshot all hold. If it ever shows up in a profile, I would stripe the stats per thread and sum the stripes in the snapshot.
