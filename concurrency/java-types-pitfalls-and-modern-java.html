Types, pitfalls and modern Java (17 to 21)

Catch boxing, arithmetic and string bugs, then use modern Java syntax to express clear values and closed command protocols.

Before this:Objects, references and the heapfinal, immutability and recordsequals, hashCode and objects as keys

A perfectly locked counter can still overflow, and two equal request IDs can still fail a boxed == comparison. You need the language's value rules before you can trust the concurrent algorithm built on them.

In plain words

Think of a parcel counter. Two parcels can carry the same number without being the same parcel, a small weighing scale can run out of range, and changing the label on your clipboard does not change a label somebody else already holds. Java has all three distinctions: value versus identity, arithmetic range, and replacement versus mutation.

Modern syntax helps you write the labels more clearly. It does not make the weighing scale bigger or make two clerks coordinate their work.

Why this matters for concurrency

Boxed counters hide unboxing and reassignment; overflow can turn a positive capacity negative; a shared StringBuilder is mutable state. Records and sealed commands clarify messages between threads, but message design and synchronization are separate decisions.

This lesson supplies the language rules. Follow lost updates for compound updates, safe publication for handing references to readers, and the volatile and atomics toolkit for the APIs.

Primitives, wrappers and missing values

A primitive variable contains its value; a wrapper variable holds a reference to an immutable object, or null. Boxing converts a primitive to its wrapper; unboxing extracts the primitive. Prefer primitives for required numeric state; use wrappers when an API requires reference types or absence has an explicit meaning.

For two Integer references, == tests identity. Integer.valueOf always caches -128 to 127 and may cache more: 127 boxing examples have guaranteed sharing, but 128 or 1000 must not be assumed to produce distinct objects. Compare values with equals, or Objects.equals when either reference may be null. This is the Integer API's cache guarantee.

When one operand is primitive, boxed == 1000 unboxes and compares numerically, so null throws. Integer.equals requires another Integer: integer 7 and long 7 are not equal wrapper objects. The general contract is in equals and hashCode.

The results are true, true, true, false, true, both null messages, and 127 -> 128. No output depends on caching outside the guaranteed range.

A wrapper destination does not prevent unboxing. With Integer and int branches, useOverride ? missing : 0 has type int, so selecting missing unboxes null before assignment. To preserve absence, use two Integer branches, such as useOverride ? missing : Integer.valueOf(0); to default absence to zero, use missing == null ? 0 : missing. Only the selected branch is evaluated; both branches determine the expression's type. See the numeric conditional rules.

count += 1 unboxes, adds, boxes and assigns a reference; it never mutates the original Integer. That is still a compound update, even with a volatile Integer field. Do not synchronize on wrappers or string literals: identities may be shared, and reassigning a wrapper can change the lock object. Use a stable private lock as taught in the rules of locking.

Choose the arithmetic type before the operation

For ordinary arithmetic, numeric promotion converts byte, short and char to at least int; a long operand makes integer arithmetic use long. The destination does not choose the multiplication's type: long total = a * b still multiplies two int operands as int.

Integer addition, subtraction and multiplication wrap on overflow without throwing. An int holds -2,147,483,648 to 2,147,483,647; a long holds -263 to 263 minus 1. Widen before computing, or use exact arithmetic when exceeding the range must be rejected.

Expression or APISemantics
(long) a * bMultiply in long; unlike (long) (a * b), conversion happens first
Math.addExact(a, b)Add as int or long, according to the overload; throw ArithmeticException on overflow
Math.subtractExact, Math.multiplyExactThe same checked policy for subtraction and multiplication
Math.toIntExact(value)Convert a long to int, throwing if it cannot fit
(int) valueNarrow a long by discarding high bits; no range check

The first line is -2147483648; the second is -1794967296 2500000000 2500000000. Both rejection messages follow. Math.addExact(a + b, c) cannot detect overflow that already happened in a + b; check each operation that needs checking.

Exact arithmetic is range checking, not synchronization. Assigning total = Math.addExact(total, delta) on a shared field still needs an atomic update or a lock. The Math exact methods define arithmetic policy; invariants and critical sections define which updates must happen together.

Division, casts and char arithmetic

Integer division truncates towards zero: -5 / 2 is -2, and -5 % 2 is -1. Casting the result of 5 / 2 to double gives 2.0; converting an operand first gives 2.5. Integer division by zero throws; the overflow corner Integer.MIN_VALUE / -1 returns Integer.MIN_VALUE without throwing.

char participates in arithmetic as a number. 'a' + 1 is integer 98, while (char) ('a' + 1) is 'b'. Subtracting '0' converts an ASCII digit only after you establish that it is between '0' and '9'; it is not a general Unicode digit parser.

Output: 2.0, 2.5, -2 -1, -2147483648, 98 b, 7, -128, then 2 1, one per line. small = small + 1 would not compile without a cast because the expression is int; compound assignment performs implicit narrowing. A cast can make code compile while still losing data.

The musical symbol uses two UTF-16 code units but one Unicode code point. String.length() and charAt count or index code units; use code point APIs when the input contract requires them. Even one code point need not equal one visible character. The promotion rules and division rules explain the numeric results.

double approximates many decimal fractions and may lose precision when converting large long values. For exact decimal money use integer minor units or BigDecimal with an explicit rounding policy. For comparison without overflowing subtraction, see collections for coding rounds.

For arithmetic with floating operands, double takes precedence over float, which takes precedence over integral types. Floating division by zero does not throw: 1.0 / 0.0 is positive infinity and 0.0 / 0.0 is NaN, meaning not a number. Use Double.isFinite when a result must be finite and Double.isNaN to detect NaN; x == Double.NaN is always false.

Output is false true, true false, false true, then 0 2147483647. Double.equals treats NaNs as equal and signed zeros as distinct, unlike primitive ==; this matters for boxed keys. A floating value cast to int or long truncates towards zero, maps NaN to zero, and clamps out-of-range values to the destination's limits. That is not overflow validation; validate finiteness and range before narrowing. See narrowing conversions.

Strings are immutable; builders are working storage

String operations return a result instead of editing the receiver. Ignoring the result of s.concat("!") leaves s unchanged; s += "!" reassigns s. Two threads reassigning a shared string can lose an update even though every string object is immutable.

Use equals for contents. Literal interning can make == appear correct, but equal text read from a request need not share identity. "stop".equals(input) is safe for null input; Objects.equals(left, right) handles null on either side.

Type and methodWhat changes
String.equals, length, charAtRead contents; do not mutate the string
String.substring, replace, concatReturn a string result; the original contents stay fixed
StringBuilder.append, insert, delete, setCharAtMutate the builder; delete(start, end) excludes end
StringBuilder.length, setLength, toStringRead length, resize contents, or obtain an immutable string snapshot

Output is false true, ready ready!, 0,1,2 | next, then false. Repeatedly appending to an immutable string in a loop can copy growing prefixes and take quadratic work; a builder accumulates the result efficiently. A small fixed concatenation such as "id=" + id is fine.

StringBuilder provides no synchronization. Keep it local to one thread, convert to String, then hand the result off safely. StringBuffer synchronizes individual methods, but several calls still do not become one transaction. See the StringBuilder contract and thread confinement.

Everything here runs on Java 21 without preview features. On Java 17, replace the pattern switch and record patterns with the fallback below. Establish the interview's language version before choosing syntax. Oracle's language release table distinguishes final features from previews.

var infers a static type

var asks the compiler to infer a local variable's type from its initializer; it does not mean Object, dynamic typing or final. var count = 0 is int, so inference does not prevent overflow. Use an explicit type when it communicates a contract better.

This prints 2 3000000000 job2. var x = null, an uninitialized var x, and var task = () -> work() do not supply an inferable type. Ordinary fields, method parameters and return types cannot use var; lambda parameter syntax is a separate feature covered in lambdas. See local type inference.

Inference also affects generics: var jobs = new java.util.ArrayList<>() infers ArrayList<Object>, so adding a string does not make later reads return String. Use new java.util.ArrayList<String>() or an explicit List<String> destination to express the element contract. Continue to generics for type bounds.

instanceof patterns bind only after a match

value instanceof String s checks the runtime type and binds s as a String if it matches. Null never matches. The variable is in scope only where control flow proves the match succeeded, including after a guard that returns on failure.

Output is 3, 0 0, then false true. Changing && to || makes the use of s invalid: the right side would run when the match failed. Matching a reference does not freeze mutable fields or synchronize access.

String switch and switch expressions

A string switch compares contents, case sensitively. Arrow cases do not fall through; old colon cases can fall through without break. A switch expression must yield a value or throw on every applicable path; use yield inside a block, and a semicolon after the whole expression.

Output is 1, 3, then missing command. Without the null guard, this switch throws NullPointerException; default does not catch null. Java 21 permits explicit case null. An exhaustive enum switch expression can omit default if it covers all constants. See switch expressions.

Records and sealed interfaces: data and permitted variants

A record supplies component accessors such as delta(), a canonical constructor, and component based equality, hashing and text output. It is implicitly final and can implement interfaces. Revisit records and immutability for defensive copying: final component references do not freeze their referents.

The generated equals requires the same record class and compares reference components using their equality methods. Arrays therefore compare by identity, not contents: two record Batch(int[] ids) {} values holding separate arrays with the same elements are unequal. Copying an array prevents aliasing but does not change its equality policy; see the record equality contract.

A sealed interface uses permits to restrict its direct subtypes. Each permitted subtype must continue or stop extension using sealed, non-sealed or final; records are already final. They must be in the same named module, or the same package in the unnamed module. These sealed type rules describe inheritance, not thread safety.

A permitted interface uses sealed or non-sealed, since interfaces cannot be final. A non-sealed branch allows further unknown subtypes; an exhaustive switch can cover that branch with a type pattern matching it and its descendants. Sealing fixes the direct family, not necessarily every leaf type.

Worked example: a closed command protocol

A worker accepts add, read and stop commands. A string tag plus an optional numeric payload permits nonsensical combinations; separate records make the payload belong to the right variant. This function only describes commands, so it has no shared mutable state.

Output is add 2, reject negative, read, stop, then missing. Add(long delta) is a record pattern that extracts the component; Add add is a type pattern that binds the object. when adds a boolean guard, so the unguarded Add case must still handle other values.

Order specific cases before broader ones. Putting the unguarded Add first makes the guarded case dominated and compilation fails. The non-null variants are exhaustive without default; add a new permitted variant and recompilation forces you to handle it. Null is a separate policy, not a permitted subtype.

Java 21 pattern switches over arbitrary reference types also need exhaustive coverage, often a default for an open hierarchy. A broad type pattern such as case Object o still does not match null. See pattern switch rules.

Exhaustiveness is checked against the types used at compilation. If a sealed library gains a variant but an old dispatcher is not recompiled, receiving that variant can throw MatchException. Recompile dispatchers with hierarchy changes. Record patterns also call accessors; matching is not a lock or an atomic snapshot of mutable payloads.

The output is identical, but the if chain lacks the switch's compile time exhaustiveness check. A sealed family suits a deliberately closed protocol; an open extension point may suit ordinary interfaces and polymorphism. Text blocks are ordinary strings with readable layout

A text block starts with three double quotes, optional horizontal whitespace, then a required line terminator. Java normalizes line endings and removes incidental indentation; the closing delimiter's position affects indentation and the final newline. Text blocks support escapes and do not interpolate variables automatically.

Output is worker=shubhi|retries=3| and ready:5. Use .formatted(...) when you deliberately want formatting. The result is still a String, with the same equality, immutability and publication rules as a one-line literal.

Common mistakes

  • Testing only small boxed numbers. Test outside the guaranteed cache range and use value equality; null is a separate case, including inside conditional expressions.
  • Widening after computing. Cast an operand before arithmetic; use exact methods if overflow is invalid.
  • Expecting a cast to restore precision. It cannot recover a truncated quotient, discarded bits or a rounded floating point value.
  • Sharing a builder because its variable is final. Final fixes the reference; keep mutable construction local or guard it.
  • Calling records or sealed commands thread-safe by syntax alone. Inspect payload mutability, ownership and publication.
  • Using Java 21 patterns on a Java 17 compiler. Know the fallback; a default case also does not handle null unless explicitly combined with case null.

In the interview

Expect output prediction, a counter that fails at large values, or a request model needing clearer variants. State operand types, null policy and range before talking about threads.

I compare boxed values by value, and choose the arithmetic type before evaluating the expression. Range checking and atomicity are separate: an exact addition can still lose an update.
On Java 21 I would use records for these payloads and a sealed interface for the closed family. An exhaustive switch exposes missing variants during compilation. The queue or publication mechanism still supplies the concurrency guarantee.

Follow ups: null unboxing, whether 1000 is guaranteed uncached, what var infers from 0, whether default catches null, and the Java 17 fallback. Continue to OOP principles for ownership and API contracts in larger classes.

Key takeaways

  • Wrappers can be null; identity is not numeric equality, and caching beyond -128 to 127 is allowed.
  • Operands determine arithmetic types. Promote before computing and choose an overflow policy.
  • Integer division truncates; char arithmetic promotes; UTF-16 code units are not always whole characters.
  • Compare strings by contents. Build text locally and publish the finished string safely.
  • var, records and patterns keep static typing; they add no synchronization.
  • Distinguish Java 17 syntax from Java 21 pattern switches, including exhaustiveness, dominance and null handling.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A service declares volatile Integer total = 0; and every worker runs total += 1. A teammate proposes total = Math.addExact(total, 1). What does the change fix, what remains broken, and what tests would you choose?
Model answer

It changes silent int overflow into an exception, provided the field is not null. It does not make the read, addition and assignment atomic, so workers can still overwrite increments. Use an atomic update for an independent counter or one stable lock if other fields share its invariant; apply the range policy inside that update.

Test sequential values around Integer.MAX_VALUE, the documented null policy if null is permitted, and concurrent increments with an exact count after every worker completes. Review the atomicity argument too: a passing stress test does not prove correctness. Long extends the range but fixes neither lost updates nor unlimited growth.

Write code
Given nonnegative int items and positive int workers, give overflow-safe expressions for the average as a double and the ceiling items per worker as a long. Check items = 5, workers = 2, and items = Integer.MAX_VALUE, workers = 2.
Model answer

After rejecting invalid inputs, use double average = (double) items / workers; and long ceiling = ((long) items + workers - 1L) / workers;. The results are 2.5 and 3, then 1073741823.5 and 1073741824. Zero items gives zero for both. The widened numerator cannot overflow long for these int inputs; items + workers - 1 can overflow int. Casting after division truncates the average first, and casting the completed numerator is too late.

Design
Your sealed command family gains Reset, and a record payload gains a mutable array. What must you revisit in the Java 21 dispatcher, Java 17 fallback and handoff between threads?
Model answer

Add Reset to the permitted family and handle it. Recompiling an exhaustive Java 21 switch without default exposes the missing case; the Java 17 if chain needs review and a new test because its fallback still compiles. A stale compiled switch can throw MatchException for the new variant, so rebuild callers with the changed hierarchy.

The array makes the record only shallowly immutable: decide ownership or take defensive copies on input and output. Validate a private snapshot, keep the explicit null policy, and publish through a safe handoff. If commands are keys or compared in tests, define array content equality explicitly or use an immutable value representation. Sealing and matching supply neither mutual exclusion nor atomic execution of the command.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Our boxed request IDs compare equal in small tests and fail later. Walk me through what you would check, especially if threads also update a boxed counter."
What a strong answer covers
  • Distinguish reference identity from value equality and use equals or Objects.equals
  • State the guaranteed Integer cache range and that caching may extend beyond it
  • Explain that primitive comparison unboxes and null unboxing throws
  • Explain that boxed increment replaces a reference through a compound update
  • Separate the equality fix from atomicity and overflow policies
How a senior would say it
I would check for reference equality first. Two Integer references compared with double equals test identity, not their numeric values. Small tests can hide that because Integer caches minus 128 through 127, and an implementation may cache more. I would use equals, or Objects.equals when null is allowed, and test both small and large IDs. Comparing a wrapper with a primitive unboxes it, so that comparison is numeric but throws if the wrapper is null. The counter is a separate issue. Incrementing an Integer reads a reference, unboxes, adds, boxes and writes a reference back. The old object stays immutable, but two threads can still overwrite each other's updates. Volatile does not combine those steps. I would choose an atomic update or a stable lock, then specify whether overflow should wrap, reject the operation, or require a wider representation.

Likely follow up: Would using Math.addExact inside the assignment make the update atomic?

"Choose a Java representation for commands sent to a worker. Why would you use records and a sealed interface, and what changes if our interview compiler is Java 17?"
What a strong answer covers
  • Choose records for payloads and a sealed interface for a closed variant family
  • State that records have final component fields but mutable referents need an ownership policy
  • Explain Java 21 exhaustive pattern switching and specific cases before broader cases
  • Give an explicit null policy and distinguish default from case null
  • Use instanceof patterns on Java 17 and retain a separate safe handoff mechanism
How a senior would say it
I would use one record per command and a sealed interface for the closed family. Each record carries only the payload that its command needs. Final component fields help, but an array or mutable list still needs copying or a clear ownership rule. On Java 21 I can dispatch with an exhaustive pattern switch. If I add a permitted variant and recompile, the missing case becomes a compiler error. I put guarded cases before broader cases and choose a null policy explicitly, because default does not catch null. On Java 17 the records and sealed interface still work; I replace the switch with instanceof patterns and test every variant because the if chain is not checked for exhaustiveness. None of this makes command execution atomic or publishes the command safely. I still use the queue or synchronization mechanism chosen for the worker.

Likely follow up: When would an open interface with polymorphic methods fit better than a sealed family and a switch?

Out loudabout 60 s
"A buffer size goes negative even though we store it in a long and compute it under a lock. How would you debug that?"
What a strong answer covers
  • Check operand types because a long destination does not widen an int operation
  • Show a concrete overflowing product and widen an operand before multiplication
  • Use exact arithmetic and checked narrowing where the contract requires rejection
  • Separate range correctness from the lock's coordination guarantee
  • Test boundary values and reject invalid input independently of overflow checking
How a senior would say it
I would inspect the types of the operands before changing the locking. If two ints are multiplied, Java computes an int result first, even when the destination is long. Fifty thousand times fifty thousand exceeds the int range, so the product wraps and the later conversion preserves the wrong negative value. I would convert one operand to long before multiplying, or use the long overload of multiplyExact when overflow must reject the request. Casting the finished product is too late. If an API ultimately needs an int, I would use toIntExact rather than silently discard bits. The lock coordinates threads; it does not validate arithmetic. I would test zero, the largest valid size, the first overflowing size and negative inputs. Exact arithmetic handles representable range, but rejecting a negative requested capacity is still a separate domain check.
