Reentrant and recursive locks

What it means for a thread to take a lock it already holds, which locks allow it, and why needing it is often a warning sign.

Asked atNetflixGoogleMicrosoft
Before this:Mutexes and RAII guardsThe rules of locking

Sooner or later a method that holds a lock calls another method that wants the same lock. Whether that works, hangs forever, or quietly breaks your invariant depends on one property of the lock, and Java and C++ made opposite default choices.

In plain words

You have booked the only meeting room from 2 to 3. During your meeting, your own assistant tries to book the same room, same slot, for a follow up with you. A sensible booking system checks the name and says "it is already yours", and notes that you now hold two bookings that both need cancelling. A rigid system says "room taken, please wait until it is free", and your assistant waits for the room... to be released by you, who are waiting for your assistant. Nobody else is involved, and still nothing will ever move.

The sensible system is a reentrant lock. The rigid one is a plain lock, and the hang is a self-deadlock.

What reentrancy means

A lock is reentrant (C++ says recursive) if the thread that already holds it can acquire it again without blocking. To make that work, the lock remembers two things besides "locked or not":

  • The owner: which thread holds it. Another thread that asks still has to wait.
  • The hold count: how many times the owner has acquired it without releasing. Each acquisition by the owner adds one, each release subtracts one, and the lock becomes free only when the count is back to zero.

A plain, non-reentrant lock does not need either. It only asks whether it is taken, so a second acquisition by the same thread waits like anyone else, and since the only thread that could release it is the one now waiting, it waits forever. That is a self-deadlock: a deadlock with one thread.

LockReentrant?Same thread locks it twice
Java synchronized (intrinsic lock)YesFine; the JVM counts the entries
Java ReentrantLock, ReentrantReadWriteLockYesFine; getHoldCount() shows the count
Java StampedLock, Semaphore(1)NoHangs forever (for StampedLock: a second write lock always, a second read lock once a writer is waiting)
C++ std::mutex, std::timed_mutex, std::shared_mutexNoUndefined behavior; in practice usually a hang
C++ std::recursive_mutex, std::recursive_timed_mutexYesFine; must unlock as many times as locked

The self-deadlock, in both languages

Here is the hang. In Java we need a lock without an owner to show it, and a Semaphore with one permit is exactly that: it counts permits, not owners, so it cannot tell "the same thread again" from "someone else". In C++, plain std::mutex does it.

The C++ standard is blunt about this case: locking a std::mutex you already own is undefined behavior. A note in the standard says an implementation that detects it may report resource_deadlock_would_occur (as a std::system_error), but you cannot rely on that; on most platforms it simply hangs, as it does here.

Reentrant locks: the same code, working

Why did Java make every intrinsic lock reentrant? Because object-oriented code calls its own methods all the time. A synchronized method calls another synchronized method on the same object; a subclass's synchronized override calls super, which is also synchronized. Without reentrancy, each of those would hang on the first call.

The hold count tells the story: inside addAll, each nested add raises it to 2 and drops it back to 1, and the lock is truly released only when addAll itself unlocks. With RAII guards and finally blocks the lock and unlock calls always pair up, so the count takes care of itself. Write lock() without its unlock() once, though, and the count never returns to zero: the lock stays held after your method returns, and the next thread to ask waits forever.

Java

ReentrantLock exposes the bookkeeping: getHoldCount() (holds by the current thread), isHeldByCurrentThread() (handy in assertions), and isLocked(). synchronized keeps the same count internally; Thread.holdsLock(obj) tells you whether the current thread holds an object's monitor.

C++

std::recursive_mutex keeps the count internally and does not expose it, and the maximum depth is unspecified: past it, lock() throws std::system_error and try_lock() returns false. There is no recursive version of std::shared_mutex.

On Linux and macOS, std::recursive_mutex is a POSIX mutex of type PTHREAD_MUTEX_RECURSIVE underneath. If you work with raw pthreads, the type PTHREAD_MUTEX_ERRORCHECK makes a relock by the owner return EDEADLK instead of hanging, a useful debugging aid that std::mutex does not offer.

Why needing reentrancy is often a design smell

Reentrancy makes the code above work, but look at what it permits. When add takes the lock, it assumes the object is in a consistent state: that is what holding the lock is supposed to guarantee. Under reentrancy, add can be entered while the caller is halfway through its own update, with the invariant temporarily broken, and add cannot tell. Acquiring a reentrant lock no longer proves the state is consistent. It only proves that no other thread is inside.

That is why many C++ teams treat std::recursive_mutex as a code review flag, and why C++ made plain std::mutex the default. The cleaner structure has two layers:

  • Public methods take the lock exactly once, at the boundary.
  • Private helpers assume the lock is already held and never take it. Name them so (addLocked), assert it in Java, and in C++ make them take a reference to the guard, so a caller cannot even call them without holding one. (The compiler cannot check that the guard is on the right mutex; the token makes forgetting the lock a compile error, which is the common mistake.)

The callback that comes back

The nastiest reentrancy bugs involve code you did not write. An event bus holds its lock while it calls the registered listeners, and one listener, reacting to the event, calls back into the bus to subscribe someone else. Follow it through in each language:

Notice the pattern. With a non-reentrant lock the callback hangs. With a reentrant lock it gets in, but in the middle of an operation that assumed nobody would touch the list: exactly the smell from the previous section, now with real damage. A third failure waits if the listener takes some other lock: the bus lock is now held while acquiring that one, a lock order you never chose, and a deadlock with any thread that takes them the other way round.

The fix is the same in both languages, and it has a name: an open call. Never call code you do not control while holding a lock. Copy what you need under the lock, release it, then make the calls.

The snapshot also defines the semantics cleanly: a listener added during a publish starts with the next event. In Java, CopyOnWriteArrayList packages the same idea for listener lists, which are read far more often than they change.

Worked example: reviewing a "thread-safe" container

A code review hands you a container guarded by one plain mutex. set(i, v) locks the mutex and, when i is past the end, calls resize() to grow the storage. resize() is also public, so it locks the same mutex too. Single-threaded tests pass whenever no resize is needed, which is most of them.

  1. Spot the path: set holds the mutex and calls resize, which asks for it again. On a non-reentrant mutex that is a self-deadlock the first time a set needs to grow the storage.
  2. Do not reach for a recursive mutex. It would make the hang go away, but resize would then run in the middle of set, and any future code in resize that assumes a consistent container would be wrong.
  3. Restructure: make a private resizeLocked() that assumes the lock is held, call it from both the public resize() and from set(), and take the mutex exactly once per public call.
  4. Look for its cousins: an early return that skips the unlock (fixed by RAII), and any callback invoked while the mutex is held.

Debugging and code review rounds hide bugs of exactly this shape; recognizing "a locked method calling another locked method" in a few seconds is the skill being tested.

Common mistakes

  • Bringing Java habits to C++. Nested locking of the same std::mutex is undefined behavior. If a locked method calls another locked method on the same object, restructure with private helpers.
  • Using std::recursive_mutex to make a hang go away. It removes the symptom and hides the real question: is the invariant intact when the inner method runs?
  • Unbalanced lock and unlock on a reentrant lock. One extra lock() leaves the lock held after the method returns. Pair every acquisition with RAII or try and finally.
  • Calling listeners, callbacks or overridable methods while holding a lock. It invites self-deadlock, re-entry into half-updated state, and lock order deadlocks. Use open calls.
  • Treating a binary semaphore as a reentrant lock. A Semaphore(1) has no owner: the same thread acquiring twice hangs, and any thread can release it.
  • Thinking a reentrant lock cannot deadlock. Reentrancy only lets a thread back into a lock it already holds. Two threads that take two reentrant locks in opposite orders deadlock exactly as they would with plain locks.
  • Assuming every Java lock is reentrant. StampedLock is not, and ReentrantReadWriteLock cannot upgrade a read lock to a write lock. You will see both in the next lesson.

In the interview

Three shapes come up. A Java theory question: "is synchronized reentrant, and why does it need to be?" A C++ follow up: "what happens if this method, which holds the mutex, calls that one, which also locks it?" And a build-it question: "implement a reentrant lock", which tests whether you know about the owner and the hold count. Code review and debugging rounds hide the same bug in a container or a listener list.

Yes, Java's intrinsic locks and ReentrantLock are reentrant: the lock records its owner and a hold count, the owner can acquire it again, and it is released when the count returns to zero. That is what lets a synchronized method call another synchronized method on the same object. C++ made the opposite default: locking a std::mutex you already own is undefined behavior, usually a hang, and std::recursive_mutex is the opt-in.
I treat needing reentrancy as a warning sign. If a locked method calls another locked method, the inner one can run while the invariant is half updated, so I would rather lock once at the public boundary and call private helpers that assume the lock is held. And I never call listeners or other foreign code while holding a lock: I copy what I need, release, then call.

Follow ups to expect: "How would you implement it?" (owner, count, wait while another thread owns it; see Under the hood), "What does wait() do when the monitor is held twice?" (see Senior depth), and "Is reentrancy per thread or per call chain?" (per thread, which matters for async code).

Senior depth

  • Waiting while holding a lock twice. In Java, wait() releases all holds on that monitor and restores the full count when it returns; Condition.await() on a ReentrantLock does the same. In C++, a std::condition_variable_any waiting with a std::recursive_mutex locked twice releases only one level: the mutex stays owned, the notifier can never get in, and both threads stop. (Plain std::condition_variable will not even accept a recursive mutex.) In both languages, wait only with your lock held once.
  • Reentrancy follows threads, not tasks. Ownership belongs to the thread that called lock(). If async code locks in one stage and unlocks in a continuation that runs on another thread, the unlock fails: IllegalMonitorStateException in Java, undefined behavior in C++. The reverse also bites: two logically separate tasks that run on the same event loop thread both "own" a reentrant lock, so it does not keep them apart. Do not hold thread-owned locks across async boundaries.
  • Reentrancy is not free of cost, but almost. The owner check is one comparison on the fast path. The real cost is the design ambiguity, not the cycles.
  • A reentrant function is a different idea. Interviewers sometimes ask "what is the difference between reentrant and thread-safe?" and mean functions, not locks. A reentrant function can be interrupted part way (by a signal handler, say) and called again before the first call finishes, because it keeps no shared or static state: C's strtok is not reentrant, strtok_r is. A thread-safe function may still use shared state, guarded by a lock. A lock does not make a function reentrant in this sense: if a signal handler interrupts it while it holds a plain mutex and calls it again, the thread deadlocks on itself, and with a recursive mutex the second call gets in and sees half-updated state. That is why locking functions are not async-signal-safe. Say which meaning you are answering.

Under the hood: a reentrant lock in a few lines

An owner, a count, and a way to wait until the count reaches zero. The waiting uses a monitor (Java) or a condition variable (C++), which module 5 covers in depth; here, just read it as "sleep until notified".

This is the core of the reentrant lock problem, which adds a timed tryLock and a stress test. Real implementations keep the same two fields but make the fast path a single atomic compare-and-swap; how locks are built shows that version.

Key takeaways

  • A reentrant lock records its owner and a hold count, so the owner can acquire it again; it is free when the count returns to zero.
  • Java's synchronized, ReentrantLock and ReentrantReadWriteLock are reentrant. C++ std::mutex is not: locking it twice is undefined behavior, usually a hang. std::recursive_mutex opts in.
  • Needing reentrancy often means a method runs while the invariant is half updated. Prefer locking once at the public boundary and calling private helpers that assume the lock.
  • Never call listeners or other foreign code while holding a lock. Copy under the lock, call outside it.
  • Ownership belongs to a thread, not to a task or a call chain.

Quick check

Answer each question, then read why. Your score is saved for your module test.

What does a reentrant lock track that a plain, non-reentrant lock does not need?
Why. Reentrancy needs the owner (to recognize "the same thread again") and the hold count (to know when the last release happens). Waiting time is what a fair lock tracks; that is a separate property. A count of waiters is something any blocking lock may keep, and it says nothing about who holds the lock.
On a reentrant lock, one thread runs lock(); lock(); unlock();, then starts a second thread that calls the no-argument tryLock() once and prints the result. What does the second thread print?
Why. Two acquisitions and one release leave a hold count of 1. The lock is released only at zero, so the other thread's attempt fails. A plain tryLock() never blocks, so the third option cannot happen.
An event bus holds its reentrant lock while calling listeners. One listener reacts by calling bus.subscribe(...). What goes wrong?
Why. A reentrant lock admits the same thread, so the call does not hang; it lands in the middle of publish, whose loop assumed the list would not change (in Java the loop then throws ConcurrentModificationException). With a non-reentrant lock the same code would self-deadlock. The fix for both is an open call: copy the listeners under the lock and call them after releasing it.
Why do many engineers treat "I need a reentrant lock here" as a design smell?
Why. The extra cost of reentrancy is one comparison. The problem is semantic: entering a locked method normally means "the object is consistent", and re-entry breaks that guarantee silently. Java's reentrant locks work fine with conditions, and C++ std::condition_variable_any accepts a std::recursive_mutex (safe only when it is held once). Reentrant locks still exclude other threads.
An async request handler locks a reentrant lock in its first stage, which runs on thread A. Its continuation runs later on thread B and calls unlock(). What happens?
Why. Ownership is per thread. In Java the unlock throws IllegalMonitorStateException; in C++ unlocking a mutex you do not own is undefined behavior. The tempting first option is the async mental model, but a lock knows nothing about requests, only about threads. Thread-owned locks must not be held across async boundaries.
Java onlyA thread holds an object's monitor twice (a synchronized method called from another synchronized method on the same object) and calls wait() on that object. While it waits, can another thread enter a synchronized method of the object?
Why. The Java specification says wait() relinquishes all claims on that object's monitor and restores the synchronization state exactly when the thread resumes. Condition.await() on a ReentrantLock does the same with the hold count. It does not release other monitors the thread holds.
C++ onlyA thread already owns a std::mutex and calls lock() on it again. What does the C++ standard say?
Why. Not owning the mutex is a precondition of std::mutex::lock(). A note in the standard allows an implementation that detects the deadlock to report resource_deadlock_would_occur, but nothing guarantees it, and on common platforms the thread simply hangs. Use std::recursive_mutex only if you truly need re-entry, and prefer restructuring.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "Why are Java's intrinsic locks reentrant, and why did C++ not make std::mutex reentrant?" Answer as you would out loud.
Model answer

Java made every object a monitor and encouraged synchronized methods, and object-oriented code constantly calls its own methods: a synchronized method calls another synchronized method on this, or an override calls super. Without reentrancy each of those would self-deadlock, so the JVM tracks the owning thread and a hold count, lets the owner re-enter, and releases on the last exit.

C++ went the other way: std::mutex is the cheapest correct lock, with no owner bookkeeping required, and re-locking it is undefined behavior. std::recursive_mutex exists for the cases that need it. The C++ view, which I share, is that needing re-entry is usually a design smell: the inner method runs while the outer method may have the invariant half updated, so holding the lock no longer means the state is consistent. I would rather take the lock once at the public boundary and have private helpers that assume it is held, and never call foreign code under a lock.

Write code
This Account class self-deadlocks in C++ and relies on reentrancy in Java: payOut(amount, afterPayment) locks the account, calls the public withdraw(amount), which locks it again, and then runs the afterPayment callback while still holding the lock. Rewrite it so each public method locks exactly once, no reentrancy is needed, and the callback runs with no lock held.
Model answer

Each public method takes the lock once; the shared logic lives in a private helper that requires the lock (an assertion in Java, a guard token in C++), and the callback runs only after the lock is released. A plain std::mutex is now enough in C++, and the Java version would work even with a non-reentrant lock.

Debug
A C++ service hangs about once a day. A stack dump shows a single thread blocked inside Cache::put, called from Cache::evict, called from Cache::put. No other thread is waiting on anything. What is the bug, and how do you fix it without a std::recursive_mutex?
Model answer

It is a self-deadlock. put locks the cache's std::mutex, and when the cache is full it calls evict, which (directly or through a callback such as an eviction listener) calls put again, which tries to lock the same mutex. Re-locking a std::mutex is undefined behavior and in practice the thread waits for itself forever. It is rare because it only happens when an insertion triggers an eviction that re-enters, which explains the once a day.

Fix: split each public method into "lock once at the boundary" and private putLocked and evictLocked helpers that assume the mutex is held and never lock it. If an eviction listener is involved, collect the evicted entries under the lock and invoke the listener after releasing it (an open call), so foreign code can never re-enter while the mutex is held. A recursive mutex would hide the hang but let put run in the middle of evict, with the cache's size and its index possibly out of step.

Out loudabout 90 s
"What does it mean for a lock to be reentrant? Tell me how you would build one on top of a plain mutex."
What a strong answer covers
  • The owner thread can acquire it again without blocking; every other thread still waits
  • It needs two fields a plain lock does not: the owner thread and a hold count
  • lock: if the caller is the owner, add one; otherwise wait until the count is zero, then become owner with count one
  • unlock: only the owner may unlock; subtract one, and at zero clear the owner and wake a waiter
  • Java's synchronized and ReentrantLock are reentrant; C++ std::mutex is not, std::recursive_mutex is
  • Real implementations make the uncontended path a single compare and swap
How a senior would say it
A reentrant lock lets the thread that already holds it take it again without blocking, while every other thread still has to wait. To do that it keeps two things a plain lock does not need: the owner, and a hold count. I would build it from a mutex and a condition variable. In lock, I take the internal mutex. If the caller is already the owner, I add one to the count and return. Otherwise I wait on the condition until the count is zero, then record myself as the owner with a count of one. In unlock, I check that the caller is the owner and throw if not, because unlocking someone else's lock is a bug. I subtract one, and only when the count reaches zero do I clear the owner and wake one waiter. Java's synchronized and ReentrantLock work this way. C++ made the opposite default: std::mutex is not reentrant, and std::recursive_mutex is the opt in. A production lock keeps the same two fields, but makes the uncontended path one compare and swap and only parks threads under contention.

Likely follow up: How would you add a tryLock with a timeout, and does that change whether notify is enough in unlock?

I would not approve it as it stands. The hang was a self-deadlock: a method that holds the lock reached another method that takes the same lock, maybe through a callback. Making the lock reentrant removes the hang but not the cause. Now the inner method runs in the middle of the outer one, possibly while the invariant is half updated, and it cannot tell. Holding the lock used to mean the object is consistent. After this change it only means no other thread is inside. So I would ask for the re-entry path from the stack dump and restructure it. Public methods take the lock exactly once. The shared logic moves into private helpers that assume the lock is held, checked with an assertion in Java or a guard parameter in C++. If the path runs through a listener, that call moves outside the lock: copy what it needs, release, then call. If the fix is urgent, I could accept the reentrant lock as a stop gap, but with a ticket and a test that reproduces the original path.

Likely follow up: The hang happens about once a day in production. How do you find the path that re-enters?

Out loudabout 80 s
"Your event bus holds its lock while it calls the listeners. Walk me through what happens when a listener subscribes a new listener during a publish, first with a reentrant lock and then with a plain one."
What a strong answer covers
  • With a reentrant lock, subscribe gets straight in, because the same thread is asking again
  • It changes the list that publish is iterating: ConcurrentModificationException in Java, invalidated iterators and undefined behavior in C++
  • With a plain lock, subscribe waits for a lock its own thread holds: a self-deadlock
  • A listener that takes another lock adds a lock order nobody chose, so a two thread deadlock is waiting

How a senior would say it
The publish loop holds the bus lock and calls a listener, and that listener calls subscribe on the same thread. With a reentrant lock, subscribe is let straight in, because the owner is asking again. It adds to the very list that publish is iterating, so when control comes back, the loop is walking a list that changed under it. In Java the next step throws ConcurrentModificationException. In C++ the loop's iterators are invalid, which is undefined behavior. With a plain lock the failure is different: subscribe waits for the lock, the only thread that could release it is the one waiting, and the bus hangs forever. And if a listener takes some other lock, the bus lock is now held while acquiring it, an order nobody chose, so a deadlock with another thread is waiting to happen. The fix for all three is an open call. Copy the listener list under the lock, release it, then call the listeners. A listener added during a publish simply starts with the next event.
