Kernel threads, green threads and M:N scheduling

One to one kernel threads, green threads, M:N scheduling, goroutines and Java virtual threads: what cheap threads fix, and what they do not.

Asked atApple
Before this:What a thread costs, and why more threads can be slower

Kernel threads are expensive, so language runtimes have long offered cheaper ones: green threads, goroutines and, since Java 21, virtual threads. Each answers one question differently: who schedules the thread, the kernel or the runtime? That answer decides what becomes cheap, what still blocks, and what still needs a limit.

In plain words

Imagine every passenger in a city hiring their own private driver for the whole day. The driver waits outside every shop, every meeting, every lunch. It works, but it is expensive, and the city runs out of drivers long before it runs out of passengers. That is one kernel thread per task.

Now imagine a taxi company. A dispatcher puts passengers in cabs only while they are actually travelling; when a passenger stops for shopping, the driver takes someone else. A few hundred drivers serve a whole city. That is M:N scheduling. It has one weakness: a passenger who makes the driver wait in the car while they shop holds that cab hostage, and enough of them bring the fleet to a halt.

Who schedules the thread?

ModelWho schedulesParallel?When a thread makes a blocking callExamples
1:1 kernel threadsThe operating systemYesOnly that thread waitsstd::thread and pthreads on Linux, Java platform threads, Windows threads
N:1 green threadsA runtime library, with all threads on one kernel threadNoEvery green thread in the process waits, unless the runtime avoided the callEarly JVMs, in the Java 1.1 era, on some platforms
M:NA runtime, onto a few kernel threads, usually one per coreYesThe runtime parks the user thread and runs another on the same kernel thread, if it can intercept the callGo goroutines, Java virtual threads, Erlang processes

A kernel thread is a thread the OS knows about and schedules itself; that is what every thread in lessons 01-01 to 01-06 has been. A green thread is invisible to the OS: the runtime switches between green threads itself, which is cheap, but they all share one kernel thread, so they never run in parallel and one blocking system call stops them all. That flaw is why early Java moved to native threads, one per Java thread. Every Java thread was an OS thread until Java 21 added virtual threads, and platform threads still are.

M:N scheduling keeps the cheapness and fixes both flaws: many user-level threads run on several kernel threads, so they run in parallel, and when one blocks, the runtime parks it and runs another on the same kernel thread.

Why M:N is attractive

  • Cheap switches. Switching between user-level threads happens in user space: save a few registers, swap a stack pointer. No system call, no kernel scheduler.
  • Tiny stacks that grow. A user-level thread starts with a few kilobytes and grows only if it needs to, instead of reserving a megabyte up front.
  • Blocking becomes cheap. The code calls an ordinary blocking API. Underneath, the runtime turns the wait into non-blocking I/O, parks the user thread and runs another. You write simple sequential code and get the efficiency of an event loop.

The catch is in the phrase "if it can intercept the call". The runtime can only make blocking cheap for the operations it controls. Anything that blocks the kernel thread underneath, out of the runtime's sight, blocks every user thread waiting for that kernel thread.

Goroutines

Go's goroutines are the best known M:N design, and interviewers who know Go may ask about them. The runtime has three parts: G (a goroutine), M (an OS thread, "machine") and P (a logical processor with its own run queue). By default there are as many Ps as cores (GOMAXPROCS). A goroutine starts with a stack of a few kilobytes (2 KB is the minimum) that grows by being copied to a larger one. Network I/O goes through the runtime's poller (epoll on Linux, kqueue on macOS), so a goroutine waiting for a socket parks and frees its M. When a goroutine enters a blocking system call the runtime cannot avoid, the runtime hands that M's P to another M, so the other goroutines keep running. Since Go 1.14 the runtime can also preempt a goroutine that computes for too long.

Java virtual threads

Java 21 added virtual threads (JEP 444). They are java.lang.Thread objects, so existing code that uses threads, locks and blocking calls works unchanged, but the JVM schedules them instead of the OS:

  • You create them with Thread.ofVirtual().start(task), Thread.startVirtualThread(task), or Executors.newVirtualThreadPerTaskExecutor(), which starts a new virtual thread for every task.
  • A virtual thread runs mounted on a carrier thread, an ordinary platform thread. By default the carriers are a ForkJoinPool with one thread per core; the system property jdk.virtualThreadScheduler.parallelism changes that number.
  • When it blocks on a socket, a sleep, a java.util.concurrent lock or a blocking queue, the JDK unmounts it: its stack frames are copied into a small object on the heap, and the carrier is free to run another virtual thread. When it can continue, it is mounted again, perhaps on a different carrier.
  • Virtual threads are always daemon threads, always have normal priority, and have no name unless you give one.
  • They are not time sliced: a virtual thread that computes keeps its carrier until it blocks or finishes.

Read the first line of the Java output: the virtual thread's id, its state, and the carrier it is mounted on right now, ForkJoinPool-1-worker-1. Ten thousand tasks, each blocked for 100 ms, finished in about 134 ms on 16 carriers, because a sleeping virtual thread does not hold its carrier. Try 100,000 or a million: it still works, limited mostly by the cost of creating the threads.

The C++ version does the same with real kernel threads, and at 1,000 threads it is fine too: about 110 to 210 ms here. Kernel threads were never the problem at a thousand. The problem is a hundred thousand: macOS caps a process at 12,288 threads on this Mac (the kern.num_taskthreads setting), and on Linux 100,000 threads would first need raised limits (the default vm.max_map_count alone stops a process near 32,000), then reserve hundreds of gigabytes of stack address space at the default 8 MB, keep 1.6 GB of kernel stacks resident, and need seconds of CPU just to create. Cheap threads move the ceiling from thousands of concurrent waits to millions.

Pinning: when the carrier cannot be freed

A virtual thread can only unmount if the JVM can save its stack and give the carrier back. In Java 21 two things prevent that, and the virtual thread is then pinned: a blocking call made inside a synchronized block or method, and a blocking call made from native code. A pinned virtual thread that blocks also blocks its carrier, and the scheduler does not add carriers to make up for it. Pin enough of them and every carrier is stuck.

On 16 cores this prints about 110 ms for the ReentrantLock version and about 420 ms for the synchronized one. Nobody waits for anybody's lock here; every task has its own. The difference is pinning alone: inside synchronized, each sleeping virtual thread holds one of the 16 carriers, so 64 tasks run in four waves of 16. With ReentrantLock, the sleepers unmount and all 64 sleep at once.

What to do about it on Java 21: use ReentrantLock instead of synchronized around blocking calls on hot paths, and find pinning with -Djdk.tracePinnedThreads=full (prints a stack trace when a pinned virtual thread blocks) or the JFR event jdk.VirtualThreadPinned. Java 24 (JEP 491) lets virtual threads unmount inside synchronized too, so this demo shows no difference there, nor on Java 25, the next long term support release; native frames still pin. Many companies still run Java 21, so pinning is still worth knowing in an interview, and the senior answer names the version: "on 21, synchronized pins; from 24, it does not".

The same failure exists wherever cheap threads run on a few real ones. In C++ coroutine code, a blocking read or a long computation inside a coroutine blocks the executor thread underneath, and every other coroutine scheduled on it waits.

C++: no virtual threads in the standard

std::thread and std::jthread are always one kernel thread each. C++20 added coroutines: functions that can suspend at a co_await and resume later with their local state intact. A coroutine is stackless and costs only a small heap frame, so millions are possible. But the standard gives you only the language mechanism: no scheduler, no thread pool, no asynchronous I/O. You bring a library for those, for example Boost.Asio, which can run C++20 coroutines on its event loop. (Later standards add pieces, C++23's std::generator and C++26's senders and receivers in std::execution, but still no asynchronous I/O.) Stackful user-level threads, closer to goroutines, also exist in libraries such as Boost.Fiber.

Stackless versus stackful is the distinction interviewers probe. A stackless coroutine can suspend only at a co_await in its own body; a plain function it calls cannot suspend on its behalf, so every function on the path to a wait must itself be a coroutine that is awaited, and async spreads up the call chain. A stackful thread, such as a goroutine, a virtual thread or a fiber, has its own stack, so it can block anywhere, however deep the calls go. Stackless frames are smaller and cheaper; stackful threads let ordinary blocking code run unchanged.

So a C++ service that must hold 100,000 mostly idle connections uses an event loop (epoll on Linux, kqueue on macOS, usually through a library), optionally with coroutines so the handlers read like sequential code, plus a small bounded pool for CPU heavy work. Lesson 09-10 builds on this.

See the trade-off

Choose kernel threads, 2,000 threads, and set the I/O wait to 95 percent. Note the stack memory. Now switch to virtual threads: memory falls from gigabytes to megabytes, and useful CPU rises somewhat because user-space switches are cheaper, but it can never go past 100 percent of the cores you set. Cheap threads cut memory and switching cost, not computation.

What cheap threads do not fix

This is the part interviewers care about most, because it separates people who read the announcement from people who have run virtual threads in production.

  1. CPU bound work. A million virtual threads computing still have 16 cores. They add scheduling, not speed, and because virtual threads are not time sliced, long computations can hog carriers. Use a pool sized to the cores for CPU work.
  2. Races. Every race in this course happens exactly the same way on virtual threads. Shared mutable state still needs locks or atomics.
  3. Downstream limits. If a million cheap threads each query a database that can serve 100 connections, the database still serves 100. The limit used to be the pool size; now you must state it explicitly, with a semaphore or a connection pool around each dependency.
  4. Lock contention. A hot lock is serial. A million threads queueing for it is still one at a time.
  5. Pinning and blocking the carrier. synchronized around blocking calls (Java 21), native calls, and long computations all hold carriers.
  6. Memory per task. A ThreadLocal cache of 1 MB is harmless on 200 platform threads and fatal on a million virtual ones.
  7. Do not pool them. Virtual threads are meant to be created per task and thrown away. A "pool of 100 virtual threads" just recreates the platform thread problem; if you want a limit, use a semaphore.

Worked example: 100,000 mostly idle connections

A notification gateway keeps 100,000 long lived connections open. Each receives a message every few minutes and spends about 1 ms of CPU handling it.

  • A kernel thread per connection: rejected. 100,000 kernel threads means roughly 100 GB of stack reservations in Java on x86-64, 1.6 GB of kernel stacks, thread limits, and garbage collection scanning 100,000 stacks, all for connections that are idle almost all the time.
  • Java 21: a virtual thread per connection, with plain blocking reads and writes. Idle connections cost a few kilobytes each. Check that nothing blocks inside synchronized on the hot path, keep ThreadLocal use small, and put a semaphore in front of anything with limited capacity, such as the database the handlers write to.
  • C++: an event loop on a few threads (epoll or kqueue through a library such as Boost.Asio), with coroutines to keep the handler code sequential, and a small pool for any CPU heavy step so it cannot stall the loop.

Either way, the design statement is the same: idle connections must cost kilobytes, not a thread; work that needs a scarce resource must pass a limit.

Common mistakes

  • "Virtual threads make my code faster." They let more tasks wait at once. Each task's own latency is unchanged, and CPU bound work gets no faster.
  • Pooling virtual threads. Creating them is cheap; create one per task. Limit concurrency with a Semaphore, not with a fixed pool of virtual threads.
  • synchronized around blocking I/O on Java 21. It pins the carrier. Use ReentrantLock there, or move the blocking call out of the critical section.
  • Running CPU heavy parallel work on virtual threads. Use a pool sized to the cores (or ForkJoinPool) for computation.
  • "Green threads give parallelism." N:1 green threads all share one kernel thread. Only M:N, or kernel threads, run in parallel.
  • "Cheap threads remove the need for limits." They remove the shortage of threads. Every scarce resource still needs its own bound.

In the interview

Expect "what is the difference between kernel threads and user threads?", "how do virtual threads work?" and, as a follow up to any thread pool design in Java, "would virtual threads change your answer?". An Apple Java loop in 2026 asked how virtual threads are represented and how they differ from regular threads, and candidates now reach for virtual threads in coding rounds too, so be ready to defend the choice.

Kernel threads are scheduled by the OS: each costs a stack reservation, kernel memory and tens of microseconds to create, so a process sensibly runs thousands. Virtual threads, like goroutines, are M:N: the runtime runs them on a few carrier threads and unmounts them when they block, so millions can wait at once. But cheap threads remove the shortage of threads, not the need for limits. With a virtual thread per request I still bound admission at the front door and put a semaphore in front of every dependency, I keep CPU heavy work on a pool sized to the cores, and on Java 21 I avoid blocking inside synchronized, because that pins the carrier.

Follow ups to expect: "What is a carrier thread?"; "What is pinning, and how would you detect it?"; "Should you pool virtual threads?" (no; use a semaphore for limits); "How does Go handle a goroutine stuck in a system call?" (it hands the P to another OS thread); "What does C++ offer instead?" (coroutines plus a library executor, or an event loop); "Why are C++ coroutines not goroutines?" (they are stackless and suspend only at a co_await, so async spreads up the call chain, and the standard ships no scheduler); "If M:N is so good, why is the OS 1:1?" (see Senior depth).

Senior depth

Virtual threads are built on continuations inside the JVM: a virtual thread is a continuation plus a scheduler, and unmounting saves the continuation's frames to the heap. That is also why they keep what made thread per request pleasant: real stack traces, ordinary debuggers, exceptions that propagate normally. For observability, jcmd PID Thread.dump_to_file -format=json FILE writes a dump that includes virtual threads, which the classic dump does not show.

Java 21 also previewed two companions worth naming: structured concurrency (StructuredTaskScope, JEP 453), which treats a group of related subtasks as one unit that succeeds, fails or is cancelled together, and scoped values (JEP 446), an immutable, cheaper alternative to ThreadLocal for passing context down a call tree. Both were previews in Java 21. Scoped values became final in Java 25 (JEP 506); structured concurrency was still a preview in Java 25, so check your version before using it in production code.

A classic follow up: "if M:N is so good, why are OS thread libraries 1:1?" Because they tried it. Solaris shipped an M:N threads library and made 1:1 the default in Solaris 9, and on Linux IBM's M:N NGPT project was dropped in 2003 in favor of the 1:1 NPTL library. Inside the OS library, M:N means two schedulers that cannot see each other: the kernel does not know which user thread matters, a page fault or a blocking call takes a kernel thread away without the user-level scheduler knowing, and signals, priorities and debuggers become hard. Once kernel thread creation and switching got fast enough, 1:1 was simpler and good enough. Language runtimes succeed with M:N because they own the whole stack: they write the I/O library, so they know where blocking happens, and they control stack layout, so stacks can start tiny and grow.

One more contrast: Go can preempt a goroutine that computes too long, while Java 21's virtual threads give up their carrier only when they block. A handful of CPU heavy virtual threads can therefore occupy all the carriers and delay thousands of I/O bound ones. Keep heavy computation on a separate, core-sized pool.

Key takeaways

  • 1:1 kernel threads are scheduled by the OS; N:1 green threads by a runtime on one kernel thread; M:N runtimes put many user threads on a few kernel threads.
  • Java 21 virtual threads run on carrier threads and unmount when they block, so millions can wait at once; goroutines work the same way in Go.
  • Pinning, a blocking call inside synchronized or native code on Java 21, blocks the carrier too.
  • Cheap threads do not fix CPU bound work, races, lock contention or downstream limits. Bound concurrency explicitly with semaphores, and never pool virtual threads.
  • C++ has no virtual threads: use an event loop, coroutines with a library executor, and a bounded pool for CPU work.

Quick check

Answer each question, then read why. Your score is saved for your module test.

On Linux, how does a std::thread, or a Java platform thread, relate to the operating system?
Why. Linux's pthreads library (NPTL) is one to one, and both std::thread and Java platform threads sit on top of it. That is exactly why each one costs a kernel stack, a stack reservation and creation time, and why thousands are fine but millions are not.
In an N:1 green thread system, one green thread makes a blocking read() system call that the runtime cannot intercept. What happens?
Why. The kernel sees only one thread, and it is blocked in read. No other green thread can run until it returns. M:N runtimes avoid this by intercepting blocking calls, and, as Go does, by handing the waiting thread's work to another kernel thread.
One million virtual threads each perform 1 second of pure computation on a 16 core machine. Roughly how long until all of them finish?
Why. A million seconds of CPU work spread over 16 cores takes about 62,500 seconds whatever kind of thread carries it. Virtual threads make waiting cheap; they do nothing for computing. A JVM can hold a million mostly waiting virtual threads, which is why the last option is wrong.
A virtual thread performs a blocking call while it is pinned to its carrier. What is blocked?
Why. Pinned means the JVM cannot unmount the virtual thread, so the carrier sits blocked with it. In Java 21 this happens inside synchronized and native code, and the scheduler does not add carriers to compensate. With all carriers pinned, no other virtual thread can run.
A service gives every request its own virtual thread. How should it keep 100,000 concurrent requests from overwhelming a database that can handle 100 connections?
Why. The limit belongs to the scarce resource, so it goes around that resource. A pool of virtual threads would throttle everything, not just the database work, and is the anti-pattern the JDK documentation warns about. synchronized would allow only one query at a time and, on Java 21, pin carriers while each query waits.
A goroutine enters a blocking system call that the Go runtime cannot avoid. What does the runtime do?
Why. Go's scheduler detaches the P from the blocked M and gives it to another M, creating one if needed. The blocked goroutine keeps its OS thread for the duration of the call, but nobody else waits for it. Java's scheduler does something similar for some blocking operations, such as file I/O, by temporarily adding a carrier.
Java onlyWhat does System.out.println(Thread.currentThread()) print inside a running virtual thread on Java 21?
Why. A virtual thread's toString shows its id, its state and, while mounted, its carrier. Virtual threads have no name by default (getName() returns an empty string), but toString still prints useful information, and the carrier part changes as the thread is unmounted and mounted again.
C++ onlyWhat do C++20 coroutines give you out of the box?
Why. The standard defines co_await, co_yield, co_return and the customization points around them. It ships no executor and no async I/O, so real programs use a library such as Boost.Asio. And a blocking call inside a coroutine still blocks whatever thread is running it.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Explain to an interviewer how a Java virtual thread handles a blocking socket read, and name two situations in which the carrier thread cannot be freed.
Model answer

A virtual thread runs mounted on a carrier, an ordinary platform thread from the JVM's scheduler pool, which by default has one carrier per core. When the virtual thread calls a blocking socket read and no data is available, the JDK does not block the carrier. It registers interest in the socket with the operating system's readiness mechanism, such as epoll or kqueue, saves the virtual thread's stack frames into a heap object, and unmounts it. The carrier immediately runs another virtual thread. When data arrives, the virtual thread is scheduled again, mounted on whichever carrier is free, and the read returns as if it had simply blocked. So the code reads like plain blocking code while the system behaves like an event loop.

The carrier cannot be freed when the virtual thread is pinned. On Java 21 that happens when the blocking call is made inside a synchronized block or method, and when it happens from native code or a foreign function. Some operations, such as many file system calls, also hold the carrier because of OS limitations, but there the JDK compensates by temporarily adding a carrier. And a virtual thread that simply computes for a long time also keeps its carrier, because virtual threads are not time sliced. To find pinning I would use -Djdk.tracePinnedThreads=full or the JFR jdk.VirtualThreadPinned event, and replace synchronized with ReentrantLock around blocking calls on hot paths.

Design
A service must hold 200,000 concurrent long-poll requests. Each waits up to 30 seconds for an event, then uses about 2 ms of CPU to build a response, which includes one database write. Choose a threading model for a Java version and for a C++ version, and say what you must still bound.
Model answer

The workload. 200,000 requests almost entirely waiting, with tiny bursts of CPU. A kernel thread per request is out: hundreds of gigabytes of stack reservations, gigabytes of kernel memory, and thread limits far exceeded.

Java 21. A virtual thread per request. Each waits on a blocking primitive, such as a BlockingQueue or a CompletableFuture that the event source completes, without holding a carrier. Rules: no synchronized around anything that blocks on the hot path (use ReentrantLock), and check that the database driver and connection pool do not wait on the network inside synchronized either, because that pins carriers on Java 21; small or no ThreadLocal caches; and the 2 ms response building is fine on carriers because it is short.

C++. An event loop on a handful of threads (epoll or kqueue through a library such as Boost.Asio) holding the 200,000 connections, with coroutines or callbacks for the wait, and the response building posted to a small worker pool sized to the cores if it ever grows beyond a couple of milliseconds, so the loop never stalls.

What must still be bounded, in both. Admission: a cap on concurrent long-polls per instance (say 250,000), rejecting new ones with a retry hint beyond it. The database: a semaphore or connection pool sized to what the database can take, because when an event wakes 50,000 requests at once they would otherwise hit it together; add jitter or batching to the wake-ups. Memory per request: keep each request's state small, since it is multiplied by 200,000. And timeouts everywhere, so stuck requests release their slots.

Out loudabout 90 s
"What is the difference between a kernel thread, a green thread and a virtual thread? Who schedules each one, and what happens when it blocks?"
What a strong answer covers
  • The real difference is who schedules the thread, which decides what blocking costs
  • Kernel threads (1:1): the OS schedules them, they run in parallel, only the blocker waits, but each costs a stack, kernel memory and tens of microseconds
  • Green threads (N:1): a runtime schedules them on one kernel thread, no parallelism, one blocking call stops them all
  • Virtual threads (M:N): the JVM runs them on carriers, one per core, and unmounts them when they block
  • Only blocking the runtime controls is cheap: on Java 21, synchronized and native code pin the carrier
  • Cheap threads make waiting cheap, not computing faster
How a senior would say it
The difference is who schedules the thread, and that decides what blocking costs. A kernel thread is scheduled by the operating system, one to one. Threads run in parallel, and when one blocks, only that one waits. But each costs a stack reservation, kernel memory and tens of microseconds to create, so a process sensibly runs thousands, not millions. A green thread, in the old N to 1 model, is scheduled by a runtime on top of a single kernel thread. Switching is cheap, but nothing runs in parallel, and one blocking system call stops every green thread in the process. A virtual thread is M to N. The JVM runs many virtual threads on a few carrier threads, one per core, so they do run in parallel. When a virtual thread blocks on a socket, a sleep or a lock, the JVM saves its stack to the heap and gives the carrier to another one. That is why a million can wait at once. The catch is that this works only for blocking the runtime controls: on Java 21, a blocking call inside synchronized or native code pins the carrier. And cheap threads make waiting cheap, not computing faster.

Out loudabout 80 s
"We moved a Java 21 service to virtual threads. Under load, it never has more requests in progress than the machine has cores, CPU is low and the database is idle. What do you suspect?"
What a strong answer covers
  • In-flight work capped near the core count with low CPU means the carriers are held without doing work
  • On Java 21, blocking inside synchronized or native code pins the virtual thread to its carrier
  • The scheduler does not add carriers for pinning, so every carrier ends up stuck
  • Confirm with -Djdk.tracePinnedThreads=full or the JFR jdk.VirtualThreadPinned event, which shows the frame holding the monitor
  • Fix: ReentrantLock or move the blocking call out of the lock, upgrade the library, or move to Java 24 or later
How a senior would say it
A cap at about the core count, with low CPU, tells me something is holding the carriers without using them, and on Java 21 the usual cause is pinning. The scheduler has one carrier per core. A virtual thread that blocks normally unmounts and frees its carrier. But if it blocks inside a synchronized block or method, or inside native code, it is pinned, and the carrier blocks with it. The scheduler does not add carriers to make up for pinning, so once every carrier holds a pinned sleeper, nothing else runs, and the other virtual threads just queue. To confirm, I would run with -Djdk.tracePinnedThreads=full, which prints a stack trace when a pinned thread blocks, or look for the JFR event jdk.VirtualThreadPinned. The stack shows where the monitor is held. Often it is not our code but a library, such as a database driver that waits on the network inside synchronized. The fixes are to replace synchronized with ReentrantLock around the blocking call, move the call outside the lock, upgrade the library, or move to Java 24 or later, where synchronized no longer pins.

Out loudabout 80 s
"C++20 has coroutines. Why are they not the same thing as goroutines or Java virtual threads?"
What a strong answer covers
  • C++20 coroutines are stackless: they suspend only at a co_await in their own body
  • A plain blocking call inside one blocks the executor thread and every coroutine scheduled on it
  • So async spreads: every function on the path to a wait must be a coroutine that is awaited
  • Goroutines and virtual threads are stackful, so ordinary blocking code works at any depth
  • The standard ships no scheduler and no async I/O; you bring a library such as Boost.Asio
  • Trade off: stackless frames are tiny and every suspension point is visible; stackful threads keep existing code unchanged
How a senior would say it
Because C++20 coroutines are stackless, and the standard gives you no runtime. A stackless coroutine keeps its locals in a small heap frame, and it can only suspend at a co_await in its own body. If it calls an ordinary function that blocks, that function cannot suspend on its behalf, so it blocks the thread underneath, and every other coroutine scheduled on that thread waits. To wait deep in a call chain, every function on the path has to be a coroutine that is awaited, so async spreads through the code. Goroutines and virtual threads are stackful: each has its own stack, so ordinary blocking code works at any depth, and the runtime parks it. The second difference is the runtime. Go and the JVM ship a scheduler and non-blocking I/O. C++20 ships only co_await and its hooks, so I bring Boost.Asio or a similar library for the event loop. The upside of stackless is cost: frames are tiny, millions are cheap, and every suspension point is visible in the code. If I want stackful threads in C++, Boost.Fiber offers them.
