Concurrent hash maps

Why a plain hash map breaks under threads, how ConcurrentHashMap works inside, its atomic compute methods, and a striped map in C++.

Asked atDatabricksAppleNetflixLinkedInAtlassianGoogle
Before this:Check then act: two safe calls, one unsafe sequenceLock granularity, contention and lock stripingAtomic variables and compare-and-swap

Every service has a shared map somewhere: a cache, a session table, a per-user counter. "Make this map thread-safe" and "how does ConcurrentHashMap work" are among the most common concurrency questions there are, and one 2025 Databricks candidate reported a round spent almost entirely on them.

In plain words

Think of a post office sorting wall with hundreds of pigeonholes. If one clerk holds the only key to the sorting room, every other clerk queues at the door, even when they want completely different pigeonholes. Giving sections of the wall separate latches lets clerks work on different sections together. Readers also need a reliable way to see complete letters, not half-written ones.

When the wall gets too full, the office builds a larger wall. Some clerks help move sections, while signs direct other clerks to the right wall. That is the picture behind Java's concurrent hash map: divide normal work, publish changes safely, and coordinate the move.

Why a plain hash map breaks

A hash map looks like one structure, but a put is several steps: find the bucket, check whether it is empty, link a new node, bump the size, and maybe grow the table. Every one of those is a check then act or a read-modify-write on shared memory:

  • Lost entries. Two threads put different keys that land in the same empty bucket. Both see "empty", both write their node into the bucket, and one node vanishes.
  • A wrong size. size += 1 from two threads is a lost update.
  • A broken resize. Two threads grow the table at once, each copying into its own new array; entries one of them moved are lost, and a reader in the middle may look in the wrong table and miss a key that is present.

The displayed size is one possible Java outcome, not a prediction. Concurrent structural mutation can lose entries or corrupt HashMap, and sometimes the size happens to look right. In C++, these unsynchronized insertions cause a data race and undefined behavior; reserving capacity does not limit the damage. ThreadSanitizer can diagnose the conflicting accesses, but a clean-looking output proves nothing.

The legendary version: a map that pegs a CPU forever

The Java 7 implementation used head insertion while moving collision chains during resize. Concurrent unsynchronized resizes could form a cycle, causing a lookup that traversed that cycle to spin. Java 8 changed this transfer algorithm, but removing that particular failure mode did not add synchronization: a plain HashMap still needs protection from concurrent structural mutation.

The C++ rule separates structure from values. Concurrent read-only container access is supported; methods such as find and at are treated as const for data-race avoidance even through a non-const container. Threads may modify different existing mapped values concurrently if those value operations are themselves safe. Shared access to the same value still needs coordination, and structural operations such as insertion, erasure and rehash must be synchronized against lookups.

unordered_map::operator[] is excluded from that const-like guarantee. It can insert when the key is absent; do not use it as a portable concurrent lookup API, even when you expect a hit. Prefer find or at. Rehash invalidates iterators but does not itself invalidate references or pointers to surviving elements; erasure and unsynchronized value mutation remain hazards.

The old answer: one lock for everything

The first fix is a single mutex around the whole map: Java's Hashtable or Collections.synchronizedMap(map), or in C++ a class holding a std::mutex and a std::unordered_map. Ordinary map accesses are serialized. It is correct when everyone follows the protocol, with three tradeoffs:

  • Map operations serialize. Two threads touching unrelated keys still wait for each other; work outside the map can remain parallel.
  • Compound actions are still yours. Each call is atomic, but "if absent, put" is two calls. You must hold the map's lock across both (synchronized (map) { ... } for a synchronized map).
  • Iteration is still yours. Hold the synchronized wrapper's monitor for an entire traversal, including traversal of its views. Failure to do so is unsafe; ConcurrentModificationException is only a best-effort diagnostic, not guaranteed detection.

A read-write lock lets readers run together, but its overhead must be measured against the workload. When contention warrants finer locking, use lock striping in C++ or ConcurrentHashMap in Java. A single lock remains a good design for low contention or invariants spanning several keys.

Inside ConcurrentHashMap (Java 8 and later)

ConcurrentHashMap uses an array of bins. In OpenJDK 21, a bin can contain a list, a tree wrapper, a resize forwarding marker, or a temporary reservation for a computation. Nodes have a final hash and key reference and volatile value and next references; acquire/release access to array slots also participates in publication. These are implementation details, distinct from the public per-key atomicity and visibility guarantees.

put into an empty bin: one CAS, no lock

If the bin is empty, put creates the node and installs it with a compare-and-swap on that array slot. If the CAS fails, another thread filled the bin first, so the loop starts again and takes the next path.

put into a non-empty bin: lock only that bin

Otherwise put does synchronized on the bin's first node, then re-checks that the node is still the first one (a removal or a resize may have changed the bin while it waited). Under that lock it walks the list, replacing the value if the key exists or appending a node if not. Threads working in other bins never touch this lock.

get: no waiting for the bin's writer monitor

A get uses safely published bin slots and node fields. It does not acquire the writer's bin monitor, and tree readers can fall back to a list traversal during restructuring. This is not a wait-free guarantee: hashing, equality, comparisons, scheduling and traversal all cost time, and user-defined key methods can block. If a single put overlaps a lookup, it may see the old or new mapping, including null if the key was previously absent. The mapping is atomic; the fields inside a mutable value are not made atomic by the map. See linearizability.

Tree bins

OpenJDK 21 uses a treeification threshold of 8 and a minimum table length of 64. On the ordinary put list path, adding to eight existing nodes triggers conversion; smaller tables resize instead. A resize split with at most 6 nodes becomes a list, while ordinary removal uses a tree-shape test, not an exact six-node cutoff.

Balanced does not mean every lookup is logarithmic. With usable hash or comparable-key ordering, a tree lookup takes O(log n) comparisons. Equal-hash keys without a usable comparison order can require searching both subtrees, and a reader may traverse the list while a writer restructures the tree. Tree bins help collision-heavy workloads but do not remove every O(n) case.

Cooperative resize

Near the usual three-quarter occupancy threshold, or earlier to handle a long bin in a small table, a writer can start growth. It allocates a table twice as large and moves bins in claimed ranges. Each moved bin receives a forwarding node. Then:

  • A reader that meets a forwarding node follows it and searches the new table.
  • A writer that meets a forwarding node can help transfer a range before retrying in the new table; joining the transfer depends on its current state.
  • The bin being moved is locked while it is split into its two new homes (index i and index i + n), so a writer to that bin waits a moment; every other bin stays usable.

The map has no global resize lock that stops every lookup. Writers can share transfer work, but allocation, bin locks and the runtime can still delay operations. Supplying a realistic initial capacity reduces resize work.

size(): striped counters

A single AtomicLong size would make every insert fight over one cache line. Instead, OpenJDK uses a base count and, under contention, striped counter cells, the same idea as LongAdder. Summing these during writes reads different moments and yields an estimate. When quiescent, mappingCount() returns the exact count as a long; size() returns an int and saturates at Integer.MAX_VALUE.

Why null keys and values are banned

In a HashMap, get(k) returning null is ambiguous: absent, or present with a null value? You can ask containsKey(k) to find out. In a concurrent map that second call is useless, because the map may change between the two calls. So ConcurrentHashMap throws NullPointerException for null keys and values, and null from get always means absent.

Under the hood: Java 7 was different

Before Java 8, ConcurrentHashMap was an array of 16 segments by default, each a ReentrantLock guarding its own small hash table: classic lock striping, with at most 16 writers at once. Java 8 replaced segments with the per-bin design above, so the number of independent locks grows with the table. The concurrencyLevel constructor argument survives only as a sizing hint. If an interviewer describes segments, say "that was the Java 7 design" and explain the change.

Atomic per-key updates: the compute family

Individual key operations are atomic, but a sequence of calls is not, and whole-map operations are not transactions. map.put(k, map.get(k) + 1) is the lost update again, and if (!map.containsKey(k)) map.put(k, v) is check-then-act. Use a method that performs the complete per-key transition:

MethodWhat it does atomically
putIfAbsent(k, v)Insert only if absent; return null on insertion or the existing value otherwise
computeIfAbsent(k, f)If absent, compute the value with f and insert it; f runs at most once per call
computeIfPresent(k, f)If present, replace the value with f(k, old) (null removes it)
compute(k, f)Use f(k, oldOrNull); a null result removes an existing mapping or leaves an absent key absent
merge(k, v, f)Insert non-null v if absent; otherwise use f(old, v), with null removing the mapping
replace(k, expected, replacement) and remove(k, v)Conditionally replace or remove one key by value equality; return whether the change succeeded

If computeIfAbsent returns null or its function throws, it installs nothing, so another call can run the function again. Removal also permits a later load. This is not "once forever" or exactly-once external side effects. Other compute methods leave the mapping unchanged if the callback throws, but cannot undo mutations the callback already made to a mutable value or an external system. Conditional replace and remove compare values by equality; use a version if an intervening equal-valued replacement must be detected.

Java

The one rule: short, and never touch the map

When a compute-family callback runs in OpenJDK 21, it runs under bin synchronization. compute and computeIfAbsent use a locked reservation node when the bin is empty; an absent key in a non-empty bin uses that bin's existing monitor. Two consequences:

  • Keep it short. Every other writer to that bin, including writers of other keys that hash there, waits while it runs, and a resize cannot move that bin. A database call inside computeIfAbsent is a lock held across I/O.
  • Never update the same map from inside it. Recursive updates violate the callback contract. Java 21 throws IllegalStateException for detectably recursive updates, but detection is not complete and does not prevent every deadlock across bins. HashMap.computeIfAbsent can throw ConcurrentModificationException for detected structural modification; that check is best effort too.

For a slow load, put a future in the map instead of the value and complete it outside any lock; that is the single-flight pattern in thread-safe caches. The same rule applies to the merge and compute_if_absent of a C++ striped map, whose function runs under the stripe's mutex.

The map protects the mapping, not the value. Concurrent unsynchronized add calls on an ArrayList retrieved from the map race. Use a thread-safe value or replace immutable values inside compute. A retrieval returning an inserted value sees writes made before publication, not arbitrary later mutations. Even a thread-safe value can become detached if another thread removes or replaces its mapping.

Aggregate status such as size() and isEmpty() reflects transient state during updates, and iterators are weakly consistent rather than snapshots. They do not throw ConcurrentModificationException because of concurrent map updates. putAll and clear are not atomic across all keys. Never write if (map.size() < limit) map.put(k, v) and expect the limit to hold; see iterating while others write.

A striped map: the C++ answer, and the Java build-it question

C++20 has no concurrent map in the standard library, and Apple and Netflix interview reports include writing one. A straightforward design uses N independent stripes, each a mutex plus an ordinary hash map, with hash(key) % N choosing the stripe. Different stripes avoid the same map lock, though allocation and hardware can still contend. Each per-key operation holds its stripe's lock.

The C++ get returns a copy while holding the lock, so this version needs copyable values. A copied pointer still shares its pointee; Java's get returns the original value reference. Neither magically protects mutable objects reached through the result. Keys must retain stable hash and equality behaviour, and those functions must themselves be safe when called concurrently. size() locks stripes individually and therefore is an estimate during writes.

The C++ merge is a simpler combine operation: it has no null-means-remove convention. Throwing value assignment can leave a partially changed value, although RAII releases the mutex; it does not claim Java's mapping-level exception guarantee for arbitrary types. Avoid reentrant callbacks into either striped map. If measurement shows false sharing between stripes, pad for the target hardware; alignas(64) alone does not prove that two locks occupy different cache lines on every machine.

Resizing, exact snapshots and two-key operations

Each stripe owns a separate hash table. Rehashing one table happens under its stripe lock and leaves other stripes usable. Putting several locks around one shared unordered_map is not the same design: insertion still changes shared container bookkeeping, even if you reserve capacity first. Keep the stripe count fixed; changing it requires migrating entries under a coordinated protocol.

For an exact snapshot or a transaction over several keys, compute the affected stripe indices, deduplicate them, and lock all of them in a fixed global order. The same-stripe case takes one lock, not the same non-recursive mutex twice. Read and change the entire invariant before releasing any lock. All participants that observe the invariant must use this protocol; ordinary one-key calls cannot provide a two-key snapshot.

synchronized (concurrentMap) does not stop normal ConcurrentHashMap operations: they do not acquire that monitor. Multi-key consistency needs an external protocol followed by every relevant access, or immutable state published as one unit. For capacity limits, reserve a permit atomically before insertion and release it on failed or duplicate insertion and on removal; merely adding a separate count is not enough.

Worked example: a per-user counter, reasoned precisely

A Google L5 candidate in 2025 was asked to make a per-user request counter thread-safe. They named ConcurrentHashMap, AtomicInteger and synchronized, and still got a No Hire; their own conclusion was that the interviewer wanted precise reasoning about races and guarantees, not a list of tools. Here is that reasoning.

  1. The naive code is counts.put(user, counts.getOrDefault(user, 0L) + 1). Two requests for the same user read 41 and both write 42: a lost update, even on a ConcurrentHashMap.
  2. Fix one key at a time: counts.merge(user, 1L, Long::sum). Each increment is atomic for that user. Other users can progress independently when their bins differ; collision frequency depends on hashing, table size and the workload. In C++, use the striped map's merge.
  3. A hot user can make increments contend on one bin monitor. A LongAdder value spreads increment contention across cells. The adder's increment is outside the map, though its lookup can still take a bin monitor when the key is not the first node.
  4. Now the subtle race. A reset job calls counts.remove(user) while a request thread has already fetched the old LongAdder and is about to increment it. The increment lands in an adder that is no longer in the map, and is lost. If resets must be exact, keep immutable Long values and do both increment and reset through merge and compute, which are atomic with each other; if the window is acceptable, say so out loud.
  5. Reading totals while requests flow does not give a single-instant snapshot across users. LongAdder.sum() is not an atomic snapshot even for one user; after all writers finish, it is exact. For approximate monitoring that can be fine. For strict quotas or billing, choose explicit consistency and overflow rules.

Common mistakes

  • get then put, or containsKey then put. Each call is atomic, the pair is not. Use merge, compute or putIfAbsent, or a lock around both in C++.
  • Slow or recursive functions inside computeIfAbsent. They hold a bin lock across I/O or deadlock the map. Load outside the map and use a future.
  • Mutable values changed outside the map's methods. Concurrent map.get(k).add(x) on a plain list is a race. Use thread-safe values or immutable replacement via compute; mutating a list inside compute still races with readers outside it.
  • Decisions based on size(). Enforce limits with a lock or a complete permit reservation protocol, including rollback on failed insertion.
  • C++: returning references or iterators from a locked map. The lock is gone when the caller uses them. Return copies, or take a callback that runs under the lock.
  • C++: using operator[] to read. It can insert and lacks the const-like concurrency guarantee for associative containers. Use find or at for shared lookup.
  • Mutable keys. Changing hash or equality inputs after insertion can make the key unreachable by normal lookup or route access to the wrong stripe.

In the interview

Expect three shapes. Theory: "why is HashMap not thread-safe, and how does ConcurrentHashMap work?" (Databricks; Atlassian asked a candidate why their rate limiter used ConcurrentHashMap instead of HashMap). Build: "write a thread-safe hash map" or "a partitioned concurrent hash map" (Apple, Netflix, a LinkedIn phone screen). Follow up: "now several threads update this map" at the end of a normal problem (Google's per-user counter and time-based key-value store).

A plain HashMap cannot safely coordinate concurrent structural writes. In OpenJDK 21, ConcurrentHashMap publishes into an empty bin with CAS and synchronizes occupied-bin updates. Retrieval avoids the writer monitor and uses safely published array slots and node fields. Writers can help resize, and size sums striped counters, making it an estimate while updates continue. Those mechanisms support per-key operations, not transactions across an entire map.
For compound updates I use merge or compute, which are atomic per key. The function runs under the bin lock, so I keep it short and never touch the map from inside it; for a slow load I put a future in the map instead.

Follow ups: "why no nulls?", "is get blocking?", "how did Java 7 differ?", "what happens when a bin gets very long?", "why is size approximate?", "your striped map's size is wrong while writers run; does it matter?", and "how would you update two keys atomically?"

Senior depth

Hot keys beat clever maps. Striping and per-bin locks spread load across keys, but they do nothing for one key that everyone wants. The fixes are the same as for counters: a per-key LongAdder, per-thread partial results merged later, or moving that key's updates onto one owner thread.

Do not promise a lockless hit path. OpenJDK 21's computeIfAbsent fast path recognizes a matching first node without taking its monitor. A hit deeper in a collision chain or in a tree can still take the bin monitor. A separate get fast path can help a stable get-or-create workload, but does not turn two operations into an atomic sequence or solve removal races.

C++ libraries. If a C++ team needs a production concurrent map, oneTBB's concurrent_hash_map and Folly's ConcurrentHashMap exist; in an interview, write the striped map and mention that you would measure before reaching for either.

Key takeaways

  • Plain maps need coordination around structural mutation. Different keys do not make simultaneous insertion safe; C++ data races are undefined behaviour.
  • OpenJDK 21 uses CAS into empty bins, synchronization for occupied bins, reads without the writer monitor, tree bins, cooperative resize and striped size counters.
  • Single-key operations are atomic; call sequences and bulk operations are not transactions. Choose the appropriate compute or conditional update method.
  • Functions passed to the compute family run under a lock: keep them short and never touch the map from inside. Put futures in the map for slow loads.
  • In C++, build a striped map: N mutexes, N hash maps, return copies, and remember that its size() is an estimate.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Two threads each repeat "get key k's count, add one, put the result" 1,000 times. The count starts at 0; each get and put is atomic, as in a concurrent or striped map, but the pair is not. What can the final value be?
Why. Each call is atomic, but the pair is not. To reach 2, A first reads 0 and pauses; B completes 999 increments; A writes its stale 1; B reads that 1 for its final increment and pauses; A finishes its remaining increments; B finally writes 2. Sequential execution yields 2,000, and intermediate schedules yield intermediate values. There is no collection exception or nested-lock deadlock here. merge(k, 1, Integer::sum) makes each increment atomic.
Why does the lesson's striped map use a separate ordinary hash table inside each stripe, rather than several locks around one shared ordinary table?
Why. The lock boundary must match the state being modified. Independent tables isolate bucket and size changes. Reservation can avoid rehashing but does not remove all shared mutation within one ordinary table. Lookups still take stripe locks, and reading stripe sizes at different moments still produces an estimate.
A cache runs a two-second database loader while holding the bin or stripe lock used for updates. Which consequence and fix are correct?
Why. The lock covers the bin or stripe, not just the key. Reentrancy does not let other threads acquire a held lock, and more stripes cannot separate two updates to the same key. Installing a future first can share one in-flight load while keeping I/O outside map synchronization; define failure and retry handling too.
Two threads atomically get or create the same absent key, using Java's ConcurrentHashMap.computeIfAbsent or a C++ implementation that checks, loads and inserts under one stripe lock. The loader returns a non-null value normally, and nobody removes or replaces it. How many times does the loader run?
Why. One caller observes absence and installs the value while concurrent updates are excluded; the second sees that mapping and skips its loader. Neither overwriting nor a null result is permitted by the stated assumptions. Without them, a null result, exception or removal could allow another load. A separate get followed by load and put would also allow duplicate work.
A striped map with 16 stripes implements size() by locking each stripe in turn and adding its size. Meanwhile another thread removes key A (stripe 2) and then inserts key B (stripe 9). The map had 100 entries before and after. What can size() return?
Why. Each stripe is read under its own lock, so there is no data race, but the stripes are read at different moments. If stripe 2 is counted before A leaves and stripe 9 after B arrives, the sum is 101, a size the map never had at any single instant. Locking all stripes in a fixed order would give an exact snapshot at the cost of stopping every writer.
Java onlyWhy does ConcurrentHashMap reject null values?
Why. With nulls allowed, null from get would be ambiguous, and containsKey is a second call that can see a different map. Banning null values makes absence unambiguous. CAS can compare against null, and generic reference types can hold null; a red-black tree also does not inherently require non-null values.
C++ onlyWhich of these is safe on a shared std::unordered_map with no lock?
Why. Concurrent lookup is supported, assuming the key's hash and equality functions are themselves safe. find and at have the const-like data-race guarantee even on non-const containers; unordered_map::operator[] is explicitly excluded, so expecting all keys to exist is not a portable guarantee. Concurrent insertion changes shared structure, even for different keys.

Explain
"Walk me through an empty-bin put, an occupied-bin put, a get and a resize in OpenJDK 21's ConcurrentHashMap. Why is size approximate?"
Model answer

An empty-bin put publishes a node with CAS; losing the CAS makes it retry. An occupied list bin uses its first node's monitor and validates that the bin is still current before updating it. Tree bins use a wrapper. A get avoids the writer monitor and follows safely published slots and node fields; during tree restructuring it can traverse the list. This does not make arbitrary key methods or a lookup wait-free. During growth, moved bins become forwarding nodes. Readers follow them, while writers can help transfer ranges and retry in the new table. There is no whole-table resize lock stopping all readers. Size sums a base count and striped cells at different moments, so concurrent changes make it an estimate rather than an atomic snapshot. When quiescent it is exact within its return type; size() saturates at Integer.MAX_VALUE, while mappingCount() returns a long.

Write code
Many threads call record(userId), and a reporter calls count(userId). Write a counter with no lost increments, no removals and no overflow in this workload. Explain the remaining hot-user contention and what a concurrent read guarantees.
Model answer

Java's adder spreads hot-key updates across cells; sum() is not an atomic snapshot during updates but is exact once all writers finish. The C++ version locks the stripe for every lookup and then increments one atomic outside the lock. It is correct but does not provide LongAdder's hot-key scalability: both lookup contention and one atomic's cache line remain. For sustained hot users, expose a stable counter handle for callers to cache and use per-thread partial counters, with an explicit aggregation contract.

The C++ atomic is never erased, and all users finish before the counter object is destroyed. That lifetime rule makes the escaped reference safe; merely using a smart pointer would not synchronize the pointee. A relaxed load returns one atomic value without publishing unrelated state; joining all writers before reading gives the final exact count. Allocation occurs before insertion, so an allocation failure cannot leave a null pointer in the map. Reset or removal requires a redesigned protocol shared by lookup, increment and reset.

Debug
A teammate memoizes an expensive recursive function with memo.computeIfAbsent(n, k -> f(k - 1) + f(k - 2)) on a ConcurrentHashMap, where f itself calls memo.computeIfAbsent. On Java 8 the service sometimes hung at 100 percent CPU; after upgrading to Java 21 it throws IllegalStateException: Recursive update. Explain and fix it.
Model answer

The callback recursively updates the same map, violating its contract. An empty-bin computation uses a reserved node; a recursive call reaching that reservation can be detected and rejected. Not every recursive update or cross-bin deadlock is detected, so exception detection is not the design. Compute outside the callback: check get, compute recursively outside map locks, then use putIfAbsent. Return the winning stored value if another thread inserted first. Duplicate computation is acceptable only for a pure operation or one whose external effects are otherwise controlled. Futures can share in-flight work, but a loader must not wait on its own future or form a cycle of dependent futures. For recursive problems, establish an acyclic dependency order or detect cycles.

Out loudabout 90 s
"We changed HashMap to ConcurrentHashMap, but our request counters still lose increments. Explain what is wrong and how you would fix it."
What a strong answer covers
  • Thread-safe individual key operations do not make get followed by put atomic
  • Give an interleaving where two reads of 41 both produce 42
  • Use Java merge or a C++ stripe lock around the complete read-modify-write
  • Distinguish mapping safety from mutable-value safety and counter lifetime
  • Explain LongAdder's contention benefit, approximate concurrent sum and removal race
  • Use a wider synchronization protocol for strict resets or multi-key invariants
How a senior would say it
The map protects each key operation, but it does not combine a get and a later put into one increment. Two request threads can both read forty-one, both calculate forty-two and both store forty-two. One request has disappeared from the count even though the map itself is healthy. For an exact per-user transition, I would use merge with an immutable numeric value in Java. In C++, I would hold that user's stripe lock across the lookup, addition and replacement. I would also define overflow behaviour. Different stripes can still progress independently. The map only protects the mapping. If the value is a mutable list or counter, changes to that object need their own synchronization. For a very hot Java counter, a LongAdder can spread increment contention, but its concurrent sum is not an atomic snapshot. That is a useful monitoring tradeoff, not a strict quota mechanism. Lifetime matters too. If a reset removes the adder after a request fetched it, that request may increment an object no longer in the map. For exact resets, I would order reset and increment through the same per-key protocol. If an invariant spans two users, I need a wider protocol that covers both keys and every reader of that invariant.

Likely follow up: How would you get an exact total across every user while requests are still arriving?

Out loudabout 90 s
"Build me a concurrent hash map in C++. Why is putting a lock around each key not enough?"
What a strong answer covers
  • Use fixed stripes, each owning its mutex and independent unordered_map
  • Hash and equality must stay stable; protect full per-key operations including rehash
  • Several locks around one ordinary shared map do not isolate shared structural state
  • Return copied values or an explicit guarded handle; account for shared pointees
  • Define approximate size versus exact snapshots and ordered distinct-stripe locking
  • Measure skew, hot keys and callback time; keep I/O outside stripe locks
How a senior would say it
I would start with a fixed array of stripes, each owning a mutex and its own unordered map. A stable hash selects the stripe. Get, put, remove and any compound update hold that stripe's lock for their complete operation, including any rehash of that local table. The separate tables matter. Several key locks around one ordinary unordered map do not protect shared bucket management and size changes during insertion. Reserving capacity does not fix that. I also require stable key equality and hashing, with key functions that are safe to call concurrently. My simple get returns a value copied under the lock. A returned iterator or reference would need an explicit lifetime and synchronization contract, and copying a shared pointer still leaves its pointee shared. For size, summing stripes one at a time is only an estimate while writers run. An exact snapshot requires holding every stripe lock together. Two-key operations similarly lock the distinct affected stripes in a global order, taking a shared stripe only once. Readers needing the same invariant must follow that protocol too. Finally, I would measure key distribution and callback time. More stripes help independent keys, not one hot key. Slow database work belongs outside the locks, possibly coordinated through a stored future.

Likely follow up: What would changing the number of stripes require while operations are running?
