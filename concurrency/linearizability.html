Linearizability: what correct means

The correctness condition for concurrent objects: linearization points, how it differs from sequential consistency and serializability, and how to argue and test it.

Before this:Happens-before and synchronizes-withAtomic variables and compare-and-swapBlocking queues

"Is your queue correct?" has no answer until you say what correct means when two calls overlap in time. Linearizability is that definition, and it turns "I put locks everywhere" into an argument an interviewer can actually check.

In plain words

A bank transaction takes time: you queue, hand over your slip, wait, and get your passbook back. But in the passbook, each transaction takes effect at one instant, the moment the clerk stamps it. If your deposit was stamped and handed back before my withdrawal slip was even handed over, my withdrawal must see your money. If we were at two counters at the same time, the bank may stamp us in either order.

That is the whole idea. Every operation takes effect at one instant somewhere between the moment it was asked for and the moment it answered, and the results must make sense in the order of those instants.

Histories: what an outside observer sees

To talk about correctness, look at a concurrent object from outside, as a history: each thread calls an operation (the invocation) and later gets an answer (the response). Two operations overlap if neither returned before the other was called. Otherwise one precedes the other in real time.

The object also has a sequential specification: what it must do when used by one thread at a time. A FIFO queue's dequeue returns the oldest item not yet removed; a register's read returns the last value written. Correctness for the concurrent object is defined in terms of that one-thread behavior.

The definition

A history containing only completed operations is linearizable (Herlihy and Wing, 1990) if you can choose, for every operation, a single point in time between its invocation and its response, called its linearization point, such that the operations, taken in the order of those points, form a legal history of the sequential specification. For a history with pending calls, append responses to any pending calls needed to explain observed effects, then discard the other pending calls and apply the same test. An object is linearizable if every history it can produce satisfies this rule.

Three consequences make it the right definition for data structures:

  • Each operation looks atomic and instantaneous, however long it really took.
  • Real time is respected. If A returned before B was called, A's point comes first, so B must respect A's effect in the sequential specification, together with any intervening operations. A later write can overwrite A's value; real time does not require every later read to return that original value.
  • It composes. If every object in a program is linearizable, the program's history as a whole is linearizable, so you can reason about one object at a time. This property is called locality, and weaker conditions such as sequential consistency do not have it. One caution: locality covers single operations on each object. "Take from queue A, then put in queue B" is two operations, and it is not atomic just because both queues are.

Pending does not mean invisible. A push may publish a node, then stall before returning; a completed pop can already have removed it. Its pending push must be included to explain that pop. Linearizability is a safety property, not a guarantee of completion, fairness or bounded latency; those are separate progress guarantees.

To claim an object is linearizable, you name the point for every operation, including the unhappy paths.

Say "single-key operations on ConcurrentHashMap are linearizable, but aggregate status queries and traversal are not atomic snapshots, and bulk updates are not atomic as a whole." Java's timed queue signature is poll(long timeout, TimeUnit unit), not a one-argument poll(timeout). These points describe specific algorithms: the Treiber proof also requires correct publication, ABA handling where needed, and safe node lifetime in C++.

Linearizability, sequential consistency and serializability

Three names that sound alike and are asked together:

PropertyUnitMust respect real time?Composes?Where you meet it
LinearizabilitySingle operations on one objectYesYesConcurrent data structures, atomics, "strongly consistent" key-value stores
Sequential consistency (Lamport, 1979)All operations of all threadsNo: only each thread's own program orderNoMemory models: correctly synchronized ordinary Java code; C++ requires the memory-order qualification below
SerializabilityTransactions over many objectsNoNot applicableDatabases
Strict serializabilityTransactions over many objectsYesNot applicableTransactional stores that promise serializability plus real time

The register history above shows the difference precisely. It is sequentially consistent: the order "C reads 0, A writes 1, B reads 1" respects each thread's own order (each thread did one operation). It is not linearizable, because C started after B finished. Sequential consistency lets an operation that happened later in real time be ordered earlier; linearizability does not.

Data-race-free C++ is not automatically sequentially consistent. The usual guarantee uses mutexes and std::memory_order_seq_cst atomics to prevent races, without weaker synchronization. Programs using relaxed or acquire/release atomics can be data-race-free and still lack one sequentially consistent interleaving. Language memory ordering and a data structure's abstract operation contract must both be proved.

Serializability is about a different unit. It says a set of transactions behaves as if they ran one at a time in some order, but that order need not match real time, so a read-only transaction may legally see the database as it was before a transaction that had already committed. Strict serializability adds the real-time rule, and is to transactions what linearizability is to single operations.

How to argue that your structure is correct

This is the part interviewers push on: "why is this thread-safe?" Here is the method, applied to a bounded FIFO queue like the one in blocking queues, extended here with a custom close operation:

  1. State the sequential specification. A FIFO queue with positive capacity C: put appends and take removes the oldest item, waiting for space or data. Close rejects new puts and allows existing items to drain; a closed, empty take returns an end marker. Java's BlockingQueue interface itself has no close method.
  2. State the invariant and what guards it. "The deque holds the items in successful insertion order and its size is between 0 and C; every access to it holds the lock."
  3. Name a point for every operation and every path. put: the addLast under the lock. take: the removeFirst under the lock after the wait loop. A timed offer that gives up: its final locked full check after the wait budget expires. close: setting the closed flag; repeated close: observing it already set. A rejected put: observing closed under the lock. size: the read under the lock.
  4. Show each point is inside the operation's interval (it happens between call and return) and that its effect is atomic and visible to every later point. The lock excludes all other access while the change happens, and each unlock happens-before the next lock, so the next operation sees it.
  5. Check the paths with no effect. A spurious wakeup is an internal step, not a separate operation. If an interrupted wait throws before changing queue state, model that completed call as an allowed no-effect cancellation outcome; do not erase it from the history. A failed CAS does not itself perform the attempted update, but retries and helping must preserve the abstract specification.
  6. Say what is not linearizable and why that is acceptable. For example, a lock-free size estimate.

For lock-free code, successful atomic operations often supply the points, but not every algorithm has one fixed source line for each method. A helping thread may perform another call's decisive update, and some proofs choose points using the surrounding history. Also prove memory safety and publication: a CAS on a pointer is not enough if its node was freed or its fields are not visible.

Checking histories in tests

Record each invocation, response, argument and result, then search for an order respecting real time that replays legally on a sequential model. The tiny checker below models an initially empty, unbounded FIFO queue whose dequeue returns empty immediately; it does not model blocking or deadlines. It explores up to factorially many orders without pruning, so keep histories short.

Here start and end are distinct event sequence numbers with start < end, and all calls are completed. A recorder can obtain numbers from an atomic counter immediately before a call and immediately after it returns, storing records privately per thread and merging after joining. This widens measured intervals and perturbs scheduling, so passing tests is evidence, not a proof. Physical timestamps with ties must not invent or silently discard known precedence; pending calls need the completion rule above.

The example assumes well-formed records, unique operation names and non-null enqueue values. It checks four hand-written histories and asserts the verdicts; it does not exercise a real concurrent queue. Production tools support richer models and better search strategies: Knossos (used by Jepsen to test databases) and Porcupine (Go) check recorded histories, and Lincheck (JetBrains, for the JVM) generates concurrent scenarios against your class and checks each one. On the JVM, jcstress (from OpenJDK) takes a related approach: it repeatedly runs small concurrency tests and classifies observed outcomes against the outcomes you declared acceptable. It is an outcome stress harness, not a general history checker. In C++ there is no standard tool; record histories and check them as above, and run everything under ThreadSanitizer to look for executed data races separately. A clean sanitizer run cannot establish linearizability, and a linearizability checker cannot establish C++ memory safety.

Worked example: is this gauge linearizable?

A gauge of open connections uses a striped counter (Java's LongAdder, or in C++ one atomic per thread, summed on read): open() adds 1, close() subtracts 1, and current() adds up the cells.

  1. open() and close() alone are fine: each update lands atomically in some cell, so each has a point.
  2. current() reads the cells one after another. Suppose two cells hold 5 and 5, so the true value is 10. The reader adds cell 1 (5). Thread X closes a connection through cell 1 (now 4; true value 9), and its call returns before thread Y invokes open through cell 2 (now 6; true value 10). The reader adds cell 2 (6) and returns 11. Real time forces close before open, so the only possible totals are 10, 9 and 10. No point explains 11; this history is not linearizable.
  3. A restricted twist: consider a fixed set of linearizable cells, only unit increments, no reset and no overflow. Each summed cell lies between its start and end values, so the sum lies between the total at invocation and response. That total passes through every intervening integer, supplying a point for the read. This argument needs all those assumptions; it is not a general atomic-snapshot guarantee for LongAdder, arbitrary additions or relaxed C++ loads.
  4. Whether it matters is the senior part. For a dashboard, an approximate answer may be acceptable; no fixed error bound follows from the API, and LongAdder's own documentation says sum() is not an atomic snapshot. For "admit at most N connections" it is not fine: use one atomic counter updated with compare-and-swap, or a lock, so each check-and-increment has a single point.

Common mistakes

  • "Every method is synchronized, so it is correct." Correct with respect to what? State the sequential specification and the invariant, then name the points.
  • Forgetting the unhappy paths. Timeouts, empty results, failed CAS attempts and interrupts need an argument too.
  • Treating composition as atomic. Two linearizable objects do not automatically make a compound action atomic.
  • Confusing linearizable with serializable. One is about single operations and real time, the other about transactions and any serial order.
  • Calling a cache "strongly consistent" because the backing store is. A cache that returns a value overwritten before the read began can violate linearizability, whatever sits behind it. A read overlapping a write may legally return the older value.

In the interview

Our research records a 2025 Google L5 counter follow up involving ConcurrentHashMap, AtomicInteger and synchronized; the candidate reported a No Hire and emphasised learning consistency guarantees. That is a candidate's interpretation, not evidence that the interviewer explicitly asked about linearizability. Use precise correctness arguments when you justify a design, rather than merely naming primitives.

My queue is linearizable because each operation has a point inside its call interval while it holds the shared lock, and those points form a legal FIFO history. A call that returns before another begins must have its point first; overlapping calls may return in a different order from their updates. A waiting take takes effect at removal, and a timed-out poll at its final empty check after its budget expires. Size is exact here because it reads under that same lock. Other designs must establish their own size guarantee; using atomics does not settle it.
ConcurrentHashMap's single-key operations are linearizable; size and iteration do not promise atomic snapshots, and putAll and clear are not atomic whole-map updates. An invariant across keys needs an additional protocol.

Follow ups: "what is a linearization point?", "difference from sequential consistency?", "from serializability?", "is your cache linearizable?", "how would you test it?", and in distributed design rounds, "are your reads linearizable?"

Senior depth

Across machines, linearizable reads cost something. In a replicated store, a read served by an arbitrary replica can be stale, so a linearizable read needs a protocol that establishes a sufficiently recent committed state. Raft-style reads can confirm leadership through a quorum, obtain a safe read index and wait until the local state machine has applied through that index. Leases require explicit timing assumptions; contacting a quorum without a correct version-selection and read protocol is not enough.

ZooKeeper documents linearizable writes and potentially stale reads, and explicitly warns that sync followed by a read is not a strict freshness guarantee. etcd key-value reads are linearizable by default; its optional serializable reads may be stale. That product option is not a promise of transaction serializability. Name the read guarantee your design actually uses.

Weaker guarantees are often the right design. Eventual consistency, read-your-writes or monotonic reads can reduce coordination and suit some feeds, metrics and caches. They are distinct contracts, so name the one your application needs. The skill is to choose deliberately and say it out loud: "this counter is not linearizable, and that is fine because it is only displayed."

Key takeaways

  • Linearizable: every operation appears to take effect at one point between its call and its return, and those points form a legal one-thread history that respects real time.
  • Name a linearization point for every operation and path: the change under the lock, the successful CAS, the read that saw empty, the final condition check when the wait budget expires.
  • Linearizability composes across objects, but compound actions across objects are still not atomic.
  • Sequential consistency drops real time; serializability is about transactions and also drops real time; strict serializability adds it back.
  • Test by recording histories and searching for a legal real-time order (Knossos, Porcupine, Lincheck), and know what your structure deliberately does not make linearizable.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A register starts at 0. A calls write(1), which takes a long time. While it is in progress, B calls read() and gets 1. After B returns, C calls read() and gets 0. Then A's write returns. Is this history linearizable?
Why. Each read alone could see 0 or 1, but together they are a new then old inversion: B's result places the write before B's response, and C's read starts later, so its point comes after the write's. The history is sequentially consistent (order C, A, B), which is exactly why sequential consistency is weaker.
On an empty FIFO queue, A's enq(1) returns, then B calls enq(2) and it returns, then C calls deq() and gets 2. Linearizable?
Why. Real-time order fixes enq(1) before enq(2), so the only legal first dequeue is 1. If the two enqueues had overlapped, either order would be allowed and returning 2 would be fine.
What is the linearization point of a successful push in a lock-free (Treiber) stack?
Why. The successful CAS publishes the new top and is inside the push interval. Another push or pop can immediately change the top again, so it is wrong to promise that every later pop sees that node. Allocation and the initial read are preparation; returning happens after the effect and cannot generally be its point because another pop may already have consumed it. Failed CAS attempts do not publish the attempted node.
Java onlyWhich of these ConcurrentHashMap operations does not guarantee a linearizable result while other threads are writing?
Why. The three single-key operations are atomic for that key. size() combines counts that may be observed at different moments, so some concurrent histories cannot be explained by one point, even though other calls happen to return an exact count. Iteration and bulk updates likewise lack a whole-map atomicity guarantee.
What does sequential consistency give up compared with linearizability?
Why. Both require one total order of operations that is legal for the object and respects each thread's own order. Only linearizability also requires that an operation which finished before another began is ordered first.
How does serializability differ from linearizability?
Why. Serializability says transactions behave as if run one at a time in some order, which may not match the order they actually committed in. Linearizability is about single operations on one object and does respect real time. Strict serializability combines the two.
Queues A and B are both linearizable. A initially contains an item, B is unbounded, and a mover thread does x = A.poll(); B.offer(x);. Is "move one item from A to B" atomic for other threads?
Why. Locality says a history of single operations on linearizable objects is linearizable. The move is two operations, so other threads can observe the state in between. Making the move atomic needs one locking protocol covering the compound move and all observers, or a structure with an atomic move operation. A lock used only by the mover does not constrain other threads.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Argue, as you would to an interviewer, that the bounded blocking queue with put, take, a timed offer and close is linearizable. Cover the blocking and timeout paths.
Model answer

The sequential specification is a FIFO queue of capacity C, where put appends, take removes the oldest item, and a custom closed queue rejects new puts, allows queued items to drain and returns an end marker once empty. Java's BlockingQueue does not itself define close.

The invariant is that the deque holds items in successful insertion order with size between 0 and C, and every access to it holds the one lock. Each operation takes effect at a point inside its own call while it holds that lock. Put takes effect at its addLast; a put that had to wait takes effect at that addLast after the wait, not when it began waiting. Take takes effect at its removeFirst after the wait loop.

A timed offer that gives up takes effect at its final full check under the lock after the wait budget is exhausted, which justifies the no-insertion outcome; similarly a take that returns nothing after close takes effect at the check that saw it closed and empty. Close takes effect when it sets the flag; an already-closed call and a rejected put take effect at their locked observations of closed state.

Because the lock excludes every other access during each of these points, each effect is atomic, and because each unlock happens-before the next lock, every later point sees it, so the order of the points is a legal FIFO history and respects real time. Spurious wakeups are internal steps. An interrupted wait that throws before an update is a completed cancellation outcome with no queue effect, as permitted by the specification. Timeout does not prove the queue was continuously full: another producer may take a briefly available slot before the waiter reacquires the lock.

Pseudo code
A stack starts empty. Thread A runs push(1) from time 0 to 2. Thread B runs push(2) from time 1 to 3. Thread C runs pop() from 4 to 5 and gets 1. Thread D runs pop() from 6 to 7 and gets 2. Is the history linearizable? Then answer again if A's push had ended at time 0.9 instead.
Model answer

Yes. The two pushes overlap (A's interval 0 to 2 and B's 1 to 3 intersect), so we may place B's point first, say at 1.2, and A's at 1.8, both inside their intervals. The stack is then [2, 1] with 1 on top, so C's pop at 4.5 returns 1 and D's pop at 6.5 returns 2, matching the history, and every point is inside its interval with real-time order respected.

If A's push ended at 0.9, it finished before B's push began at 1, so A's point must come first: the stack becomes [1, 2] with 2 on top. The first pop must then return 2, but C returned 1. No placement of points fixes that, so the modified history is not linearizable.

Design
Your service puts a cache in front of a strongly consistent database, with entries refreshed every 50 ms. The interviewer asks: "Are reads through your service linearizable? Does it matter?" Answer.
Model answer

No, they are not. A client can write a new value through the database, get a success, and then read through the cache and get the old value even though the write finished before the read started. That violates real-time order. Refreshing every 50 ms alone does not bound staleness to 50 ms: refresh duration, failures and scheduling delays also matter.

Whether it matters depends on the product contract; some display data can tolerate staleness, but a feature flag that disables a dangerous action may not. For anything that guards an invariant, such as a balance check before a withdrawal, a seat's availability before booking, or a permission that was just revoked, the decision must read from the linearizable source and the check and update must be atomic, for example through a conditional database write that rejects stale assumptions. A separate linearizable read followed by an unconditional write still has a check-then-act race.

A middle ground is read-your-writes using a session version or a bypass until the cache has caught up. Plain invalidation alone is insufficient if an older in-flight fill can repopulate stale data; version-aware publication or coordinated invalidation must handle that race.

Out loudabout 75 s
"Two enqueues overlap, and the later caller's item comes out first. Is my queue broken? Walk me through the rule."
What a strong answer covers
  • Overlapping enqueues may linearize in either order; invocation order alone does not define FIFO
  • Each completed operation needs a point inside its call interval and the results must fit the sequential specification
  • A completed enqueue preceding another invocation must be ordered first
  • Sequential consistency preserves thread order but omits cross-thread real-time constraints
  • Linearizability is a safety property and does not guarantee fairness or completion
How a senior would say it
That result can be correct because overlapping enqueues can take effect in either order. FIFO means dequeue returns the oldest item in the legal insertion order, not necessarily the item whose caller arrived first. I would draw each call from invocation to response and look for one point inside each interval. If enqueue one runs from time zero to four and enqueue two runs from one to five, I can place two first and one second. A dequeue starting at six can then return two. But if enqueue one had returned before enqueue two was even called, real time would force one first, so returning two as the first item would be wrong. The chosen order must explain every result in the history together. Sequential consistency also needs a legal order and preserves each thread's own order, but it drops that cross-thread real-time constraint. Finally, this says which results are allowed, not how quickly operations finish. A queue can be linearizable and still have poor fairness or block indefinitely.

Likely follow up: Can a dequeue return an item whose enqueue has not returned yet?

  • Handle pending calls and test progress separately
How a senior would say it
I would give a correctness argument as well as the test results. First I would state the contract: a bounded FIFO queue, with explicit rules for empty, full, cancellation and close. Then I would state the invariant: the deque contains exactly the inserted items not yet removed, in insertion order, with its size within capacity, and every access follows the same locking protocol. Successful put takes effect at insertion and take at removal. A timed-out offer takes effect at the final full check after its wait budget expires. A closed, empty take takes effect at its locked check. Cancellation linearizes at detection without changing queue state; it is a permitted outcome, not a discarded call. Each point lies inside its call interval. The common mutex excludes competing observations during the update and publishes the state to later lock holders, so these points produce a legal FIFO order. For testing, I would record short invocation and response histories and search for a legal ordering against an independent sequential queue. Pending calls need special handling because they may already have taken effect. ThreadSanitizer checks exercised memory races, not the FIFO specification. Finally I would test termination and cancellation separately, because linearizability alone promises neither fairness nor bounded waiting.
