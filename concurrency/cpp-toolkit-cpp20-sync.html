The toolkit: semaphores, latches, barriers and stop tokens

Match permits, one-time completion, repeated phases and cooperative cancellation to the correct C++20 synchronizer, including this Mac's library caveats.

Asked atMicrosoftRubrik
Before this:The toolkit: std::thread, std::jthread and thread_localThe toolkit: condition variablesThe toolkit: std::atomic and memory orders

A semaphore counts permission, a latch counts remaining arrivals once, and a barrier coordinates repeated phases. Choosing the right one gives the implementation a shape that already matches the requirement.

In plain words

A car park has a limited number of entry tokens. A school trip waits until every child has boarded once. A relay training session waits for every runner at the end of every lap. Those are three different waiting rules, so they deserve three different tools.

Why this matters for concurrency

Interviewers ask why you picked a primitive, then change capacity, repetition, or cancellation requirements. The syntax here should let you adapt without guessing at methods. The core lessons on semaphores, latches, and barriers develop the associated invariants and progress arguments.

API card

These types require C++20 library support. Semaphore, latch, and barrier objects are neither copyable nor movable: construct them where they will live, share references, and finish all operations before destruction.

Semaphore: a count, not mutex ownership

A semaphore initialized to two admits at most two holders if every successful acquire is paired with exactly one release. Different threads can acquire and release permits; unlike a mutex, there is no owning-thread rule. That makes semaphores useful for capacity limits and cross-thread handoffs, but it also makes accidental double release a real invariant violation.

A release publishes preceding writes to an acquire that observes the released permission, but a capacity greater than one still lets several holders touch shared data together. Protect any additional shared-data invariant separately. Use a RAII scope owner for resource permits so exceptions return them. For a signal, a producer may release while a consumer acquires.

Neither use promises FIFO admission. The template parameter N is a least supported maximum, not the initial count; provide the initial count to the constructor. Use a binary semaphore with a protocol that keeps its logical permit count between zero and one, rather than relying on an implementation's potentially larger maximum.

A failed try_acquire() may be spurious. A timed attempt can fail despite a permit having been available during its interval, and scheduling can delay its return beyond the timeout. Only success consumes a permit: a failed attempt creates no release obligation.

The first two holders wait on a test latch while still owning permits, so main proves real overlap instead of inferring it from a fast run. That latch is test orchestration, not work performed while a production capacity permit is idle. The active count is decremented before the permit is released, preserving the measurement's meaning. The timed failure uses a zero-count signal with no concurrent release, and the test does not assert an exact elapsed millisecond count.

Latch: one completion boundary

A latch reaches zero once and stays open. There is no reset or count-up operation. Workers may call count_down() and continue, while an owner waits for all arrivals. If every participant should wait at the same start boundary, include the coordinator in the initial count and have all participants call arrive_and_wait().

Writes before the arrivals are made visible through the latch's completion synchronization to waiters returning after it opens. That does not stop a worker from changing those fields again afterward. A latch that marks “started” is not a substitute for a join that marks “finished.” Keep the latch alive until all its users are done.

Never decrement below zero: an extra default count_down() after zero violates a precondition. A task that throws before its required arrival can leave everyone waiting forever; catch task failures and arrange arrival on every relevant path, or use a protocol that can represent failure. Use a fresh latch for a new one-shot event; do not reuse a completed latch to represent another batch.

Barrier: repeated phases and a completion function

A barrier begins each phase with an expected arrival count. When the phase completes, its completion function runs once, then waiters can proceed into the next phase. A completion function must be nonthrowing under the C++20 contract. Use a small noexcept lambda; avoid allocations and arbitrary user callbacks in it. Do not assume a particular named worker always executes completion.

Use auto token = phases.arrive(); to do independent work before phases.wait(std::move(token));, including <utility> for std::move. The token must belong to that barrier's current or immediately preceding phase. Arrival publishes earlier work to completion; it does not order work after arrival before completion. arrive_and_wait() combines arrival and waiting.

arrive_and_drop() contributes the current arrival and reduces future phase participation without waiting for peers. It is not a general cancellation mechanism: forgetting to arrive or drop strands their phase, and dropping after already arriving would count twice. There is no API to add participants; coordinate a new barrier if the count must grow.

Do not call back into the same barrier from its completion function. With the C++20 defect correction P2588R3, completion when nobody calls wait() is implementation-defined; use an actual wait when your protocol depends on completion. Every phase in the example below has waiters.

All slot writes for one phase precede its completion. The completion finishes before workers advance and overwrite slots for the next phase. Totals use separate fixed slots and are read only after joining. If workers read a shared result after a barrier and later work could overwrite that same result before every reader finished, add another phase boundary or immutable per-phase storage.

The short visibility mutex makes ordinary data accesses visible to ThreadSanitizer on this Mac, whose compiled libc++ barrier implementation has a documented false positive. It is not required by the standard's barrier synchronization guarantees. It also does not replace the barrier: the mutex alone could still allow a worker to overwrite the next phase before the previous sum. The code releases visibility before arriving, so completion can acquire it without deadlock. The barrier specification defines the phase ordering.

Stop state: source requests, token observes, callback reacts

A std::stop_source owns access to a shared stop state and can request cancellation. Its copies refer to the same state. A stop token observes it and can be copied cheaply into work. The request is latched permanently: the first successful request_stop() returns true, later requests return false.

A default constructed std::stop_token has no stop state, so stop_possible() is false. A default std::stop_source creates a usable state; std::stop_source(std::nostopstate) does not. For a token, stop_possible() remains true after a request, but becomes false if all associated sources disappear before requesting stop. Keeping a token alive does not keep a worker alive.

A std::jthread supplies its own token as the first argument when its callable accepts that token followed by the supplied arguments; otherwise it calls without the token. get_stop_source() returns another handle to that same state. A separately created source is independent: requesting it does not cancel every std::jthread in the process. For group cancellation, explicitly pass the group's token to workers or connect their cancellation protocols.

Request stop for the whole group before joining any worker. Destroying workers one at a time can deadlock if the first needs a peer to stop before it can finish. If workers observe only an external group's token, their own std::jthread destructor's request will not reach that token; the owner must request the external source first. Explicit join() waits but does not itself request stop.

entered proves that the worker reached the wait setup, not that it is already asleep. std::condition_variable_any::wait(lock, token, predicate) handles a request both before registration and while blocked. It returns the predicate's value with the lock held: true can coincide with a stop request. Here ready stays false, so cancellation makes the result false; ordinary std::condition_variable has no such overload.

Registered callbacks execute synchronously in the thread making the successful stop request, with no specified callback order. Late registration invokes its callback in the constructing thread before the constructor returns. A losing concurrent request_stop() returning false does not guarantee that the winning request's callbacks have finished.

A callback destructor can wait for its own invocation on another thread to finish. Therefore request_stop() and callback destruction belong in your lock-order reasoning. Keep callbacks short and nonthrowing; an escaping callback exception terminates the program. These are the callback lifetime rules.

Do not request stop while holding a lock that a callback needs. A callback that merely notifies an ordinary condition variable also needs a correct durable predicate protocol; a notification alone can be lost before the wait begins. Prefer std::condition_variable_any's stop-aware overload when cancelling a condition wait. A stop request does not interrupt an arbitrary blocking system call.

A successful stop request synchronizes with a token check that observes the request, but it neither protects unrelated ongoing mutations nor proves that the worker exited. Keep captured objects alive through callback execution and join owned workers before destroying their state. Keep required actions outside assert: disabling assertions must not remove the stop request.

In C++17, own and join std::thread objects explicitly and use a stop flag with a condition-variable wakeup protocol. Under one mutex, a semaphore waits for a positive count then subtracts one; a latch waits for a count to reach zero; a reusable barrier waits for its saved generation number to change. The last barrier arrival resets the count, advances the generation, and notifies all. The linked primitive problems drill these implementations.

Worked example: choose the synchronizer

Limit simultaneous downloads with a semaphore. Wait for an initial configuration batch with a latch. Run several iterations of a parallel reduction with a barrier. Stop the service with a shared cancellation protocol, and still join every owned thread.

Now three reduction workers A, B, and C start a phase, but C must leave permanently. C has not arrived yet, so it calls arrive_and_drop() once. The current phase still needs A and B; the next phase needs only two arrivals. C may return before this phase completes, so it cannot consume its final result without additional synchronization.

Common mistakes

  • Using a latch as a reusable barrier: create a new latch or use a barrier.
  • Releasing a semaphore on a failed acquire: only release a resource permit you acquired.
  • Leaving a barrier without satisfying the current arrival: drop before arriving, and never count the same obligation twice.
  • Holding the visibility mutex across arrive_and_wait(): release it first so completion can acquire it.
  • Assuming a stop token forcibly interrupts work or request_stop() cannot run user code: provide a wakeup path and audit callback lock ordering.

In the interview

Expect to implement a permit limiter or a wait-for-all primitive, then explain what changes for repeated phases, worker failure, and shutdown. The research records semaphore implementation at Microsoft and semaphore theory and completion coordination at Rubrik; that does not establish that either asks for these exact C++20 APIs. Be ready to derive the mutex and condition-variable version when library primitives are disallowed.

I pick the primitive from the fact being counted. Permits limit admission, a latch records one batch, and a barrier separates repeated phases. Stop tokens request cooperation; the service still needs a wakeup path and an owner that joins its workers.

Senior depth

C++20 semaphores, latches, and barriers have no stop-token overloads; latches and barriers also lack timed waits. A semaphore waiter can retry timed acquires while checking a token, but polling adds cancellation latency. If acquisition wins a race with cancellation, either use the permit or return it; do not invent extra permits just to wake shutdown waiters.

A failed barrier worker must still satisfy its current arrival obligation, perhaps by dropping before it has arrived. Publish failure separately and decide whether peers can finish the phase safely. For abortable phases or cancellable admission, a mutex and condition variable with an explicit failure or closed predicate is often clearer.

Key takeaways

  • Pair successful permit acquisitions and releases, including exception paths.
  • Latches open once; barriers coordinate reusable phases.
  • Completion and cancellation callbacks have execution and exception contracts.
  • Cancellation is cooperative and does not replace joining.
  • Verify library support and distinguish toolchain limitations from language guarantees.

Quick check

Answer each question, then read why. Your score is saved for your module test.

What does std::counting_semaphore<8> permits(2); initially allow?
Why. The constructor supplies two initial permits. Eight is a least supported maximum, not the initial count, and the two numbers are not added. Without releases, at most two acquisitions can succeed.
A resource limiter's timed acquire returns false. Should its cleanup release a permit?
Why. A failed attempt consumed nothing, including when failure was spurious. Releasing after either kind of failure creates an extra permit. An RAII owner should exist only after successful acquisition.
A latch reaches zero. How do you reuse it for the next batch?
Why. std::latch is one-shot and has no reset() member. A negative decrement violates its precondition; it is not a supported count-up protocol. Use a new object or a barrier when the phase structure fits.
What does a barrier's arrive_and_drop() do?
Why. Dropping reduces both the current remaining count and every future phase's target by one. It does not skip this phase's arrival or cancel the other waiters: peers still need to meet the remaining phase requirements.
A std::stop_callback is constructed with a token that already reports stop. What occurs?
Why. The callback runs in the constructing thread before construction returns. It is not skipped, and it needs no later request: stop is permanently latched, so repeated requests do not create another cancellation event.

Why. Normal return preserves lock ownership and reports the predicate result. Cancellation does not transfer or abandon the lock, and a true predicate can coincide with a stop request. In this untimed overload, a false result means stop was observed and the final predicate evaluation was false.

Why. The workers write distinct array elements, so their writes do not conflict. Both writes precede their latch arrivals, and the latch orders those writes before the read after wait(). Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
Pick primitives for three downloads at a time, one startup batch, and ten repeated computation rounds.
Model answer
Use a semaphore initialized to three for concurrent admission, a latch with the startup task count for one-time completion, and a barrier for each repeated round. Add a separate cancellation and joining protocol rather than treating any one primitive as universal shutdown.
Debug
Why could request_stop() deadlock when called under a service mutex?
Model answer
It can synchronously invoke callbacks, and a callback may need that same mutex or another lock that participates in a cycle. Release the service lock before requesting stop, keep callbacks short, and include callback destruction in lifetime and lock-order reasoning.
Explain
Why does a latch marking that all workers started not prove their result fields are final?
Model answer
Workers can continue and mutate results after count_down(). The latch orders work before arrival, not all future work. Use a completion latch reached after the final writes or join the workers before reading final results.

"Compare a semaphore, latch, and barrier with concrete uses."
What a strong answer covers
  • Semaphore counts permits
  • Latch records one finite arrival batch
  • Barrier separates repeated phases
  • Each needs lifetime and failure-path handling
How a senior would say it
A semaphore counts available permits, so I use it to limit simultaneous downloads or hand a signal from one thread to another. A latch counts arrivals down to zero once, which fits waiting for a startup batch. A barrier coordinates repeated phases, such as several rounds of parallel computation, and can run a completion step between phases. They are not interchangeable shutdown mechanisms. I must still account for a task that throws before its arrival, pair only successful permit acquisitions with releases, and keep each object alive until its users have finished.

Likely follow up: What changes if one worker permanently leaves a barrier?

Out loudabout 60 s
"What surprises can stop callbacks create in otherwise simple cancellation code?"
What a strong answer covers
  • Stop requests run callbacks synchronously
  • Late registration can invoke immediately
  • Destruction can wait for its own callback invocation on another thread
  • Avoid locks needed by callbacks and keep them nonthrowing
How a senior would say it
Requesting stop can execute callbacks synchronously, so it is more than setting a flag. A callback registered after the request can also run immediately during registration. Its destructor may wait for its own callback already running on another thread. Those facts matter for both lock ordering and lifetime. I avoid requesting stop while holding a mutex a callback needs, and I keep callbacks short and nonthrowing. For a condition wait I prefer the standard stop-aware overload, because a notification callback alone does not establish a durable shutdown predicate or close the wait-registration gap.

Likely follow up: Does the stop request interrupt a blocking socket operation?

Out loudabout 60 s
"Your service hangs while destroying its worker threads. They are all std::jthread objects. What do you check?"
What a strong answer covers
  • A joinable jthread destructor requests its own stop state and then joins
  • The worker must observe the same stop state and have a wakeup path
  • Semaphore, latch, and barrier waits are not stop-aware
  • Request cancellation for every dependent worker before joining any
  • Keep shared state alive until joins finish
How a senior would say it
I first check how the workers notice cancellation and leave their waits. A joinable jthread destructor requests its own stop state, then joins. It cannot force the worker to exit. A worker using a separate group's token will not observe that request, and an ordinary semaphore or barrier wait will not wake just because stop was requested. I request the group's source, or every worker's own source, before joining any worker that depends on its peers. Then I check the wakeup and failure protocols for each blocking operation. Shared state must stay alive until all those joins finish.

Likely follow up: How would you make semaphore admission cancellable without creating extra permits?
