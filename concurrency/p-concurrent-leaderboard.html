Concurrent leaderboard

Thread-safe structuresmedium40 minUber

Updating a score, selecting a top list and assigning a rank must agree about both ties and concurrent changes.

The task

addScore adds a signed delta, creating a missing player with initial score zero, so a zero delta still creates the player. top(k) returns up to k player-score pairs, sorted by descending score then ascending player ID. rank(player) is the one-based ordinal position in that same total order, or zero for an unknown player. Ties do not share a rank. Player IDs are any int, negative values and the extremes included.

  • Each call, rank included, observes one consistent state. Separate top and rank calls need only agree when no intervening updates occur. A returned list is detached: later updates and queries never change it.
  • Negative deltas and zero scores are valid, and a player whose score returns to zero stays on the board. Negative k throws IllegalArgumentException (C++: std::invalid_argument). Overflow in either direction throws ArithmeticException (C++: std::overflow_error) without changing the score.
  • Readers must make progress while writers are running. Copy a consistent snapshot briefly, then do expensive sorting outside the update lock.
  • The nonreentrant copied() harness hook runs after a snapshot has been copied and its data lock released, before any sorting or selection. Production uses a no-op. It can block, or throw (the exception may propagate out of the query), without leaving any lock held.

Example: players 1 and 3 both score 10. Player 1 ranks first and player 3 second. Adding 30 to player 2's score of -4 moves player 2 to rank one.

What the tests check

  • From one thread: additive updates, negative scores, ties ordered by ascending player ID, an empty top(0), zero for an unknown player, and rank agreeing with every position of a quiet top.
  • A zero delta creates a player, and a player whose score returns to zero stays on the board.
  • The smallest and largest player IDs and scores order correctly, which a comparator that subtracts gets wrong.
  • A list already returned never changes after later updates and queries.
  • Negative k and overflow in both directions throw the stated exceptions and change nothing.
  • A writer finishes while a reader is paused inside copied(), and after copied() throws, another thread can still update and query.
  • One instant per top: a mover adds 1 to player 0 and then subtracts 1 from player 255 while two readers take full snapshots. Every snapshot must show the two scores summing to 0 or 1, which per stripe copying or a weakly consistent iteration breaks.
  • One instant per rank: while players 0 and 1 gain points in turn, rank(0) must always be 1.
  • Eight threads add to the same new players at once: every player ends at exactly 8, and the rank of the last place player never reads 0 or falls.
  • Eight writers on 16 shared players plus a concurrent reader: exact totals, sorted lists with no duplicate player, and reads that finish while writers run.
  • In C++, ThreadSanitizer must stay quiet.

What were the Uber follow-ups?
The report describes a simple leaderboard, then caching, then thread safety; the candidate proposed a keyed executor. A cached ranking needs invalidation or versions so it cannot silently mix stale scores with fresh ranks.
Can keyed executors replace locks?
They serialize updates for one player, but a consistent global top still needs coordination across keys or a defined eventual-consistency contract.
How would you reduce top query cost?
Maintain an ordered score index or an order-statistics tree. Update player score and index atomically. The reference intentionally favors a simple correct snapshot before optimizing query cost.
Can stripes improve this design?
They improve independent updates, but an exact global snapshot must coordinate stripes in a fixed order or use immutable versioned state. Independently reading stripes does not automatically produce one instant, and the moving pair test here catches a top that copies stripes one at a time.
How do you cache top K?
Publish an immutable list with a version and a stated freshness policy. Exact immediate freshness requires coordinating invalidation or rebuilding with updates; stale cached results are a different API.

The invariant

Each player has one score. An update holds the write lock across reading and replacing it, and checks overflow before assignment. A query copies all player-score pairs while holding the read lock, establishing a consistent snapshot. Sorting immutable copies cannot race with later score changes.

Concurrency and ranking

The comparator orders scores descending and IDs ascending without subtracting values, which avoids comparison overflow. Rank uses the same ordering, so ties cannot disagree between APIs. It also takes its position from one snapshot: reading the player's score under one lock acquisition and counting better players under another can pair an old score with newer rivals, so a player who never falls behind is reported second. The snapshot point is during the copy; the method may return after several later writes and still be linearizable.

A read-write lock permits readers to copy concurrently, though writes briefly exclude copying. Sorting takes place after release. This is progress under ordinary scheduling, not a strict starvation bound for every platform's read-write lock.

The broken interleaving

The broken update reads under a read lock, releases it, then acquires a write lock to store old plus delta. A and B both read 10; A stores 11 and B stores 11. Both individual map accesses are safe, yet one score update disappears. The shared-player stress test checks exact totals rather than just sorted output.

Cost and limits

Java updates are expected O(1); C++ ordered-map updates cost O(log N). Top and rank copy O(N) values and sort in O(N log N), using O(N) temporary space. This simple baseline favors short write blocking rather than optimal rank lookup. An ordered index improves queries at the cost of a larger cross-index invariant.

How to say it in the interview

I will make each score increment atomic under the write lock. Queries copy a consistent snapshot under the read lock and sort after releasing it. Both rank and top use score descending and player ID ascending, so ties have one unambiguous order.
