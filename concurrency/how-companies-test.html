How top companies test concurrency

Company by company: rounds, library bans, debugging rounds, recurring problems, theory and what interviewers judge, from candidate reports dated 2022 to 2026.

Before this:Welcome to Tandem

Concurrency is tested in very different ways from company to company. At Rubrik it is two dedicated rounds where the standard library is often banned; at Google it is usually the last 10 to 15 minutes of a coding round; at Meta it hides inside system design. Knowing which shape you will face decides what you practise.

In plain words

Cricket is one game played in different formats: a five day Test, a one day match, a T20. A batter who has only ever practised for Tests struggles in a T20, where one ball can decide the match. Concurrency interviews have formats too: the long dedicated round where you build everything from scratch, the ten minute follow up where one answer decides the round, the debugging drill on someone else's code, and the design discussion where nobody says "thread" but every question is about two people wanting the same seat.

This lesson is the fixture list: who plays which format, and how to train for each one.

Where this comes from, and how much to trust it

Everything below comes from research compiled in October 2026 from candidate interview reports dated 2022 to 2026: LeetCode Discuss posts read in full, Blind threads, and other first-hand write-ups, plus official material where it exists (Databricks' interview prep guide of April 2025, Uber's interview guide pages). The reports are anonymous and self-selected, levels are as posters described them, questions are paraphrased, and India based loops are over-represented. A single report means "this happened once", not "this always happens". Reddit and Glassdoor were mostly not readable for the research. So treat this as a map, not a promise, and always ask your recruiter for the exact list of rounds and whether code must run.

Company by company

Rubrik

Rounds. Rubrik runs dedicated concurrency rounds called System Coding (also Concurrency, Multithreading, or Code Design at senior level). A loop usually has two, and the first phone screen is often one of them. Rounds are 60 minutes, live, in CoderPad or a similar environment that can run threads, in any language (Java, C++, Python and Go all appear). Senior (G7, SSE) loops add two design rounds that also probe multithreading, such as copying a very large file between machines in parallel chunks. Some loops start with an online assessment: one coding problem and about ten MCQs on multithreading and operating systems, including predicting a snippet's output and spotting an error.

Library bans. Interviewers frequently forbid ExecutorService, BlockingQueue, ConcurrentLinkedQueue and thread-safe deques, so you build the queue, the pool and the "wait for everything" latch from locks and condition variables. Reports from 2022, 2024, 2025 and 2026 say so; a 2026 thread says "threading primitives only". It is not universal: a 2022 SDE2 used a thread pool and then CompletableFuture for a crawler. Code must compile and run in most reports.

The debugging round. Separately from System Coding, many loops include a 50 to 60 minute round on someone else's multithreaded program: a barber shop simulation of about 180 lines, cinema booking code, a banking application, C++ producer-consumer code. You find deadlocks, races and broken shutdown, then leave the program compiling and running. A 2025 new grad fixed the deadlock and lost the round on a compile error. It is reported for CPD and new grad loops, a G5, and a candidate with 8.5 years of experience.

Smaller clusters round it out: rate limiters (three 2022 reports, none since), a delayed task runner (2022), byte reads and writes over a block device API, per-node task queues with rebalancing, and single reports of a buddy allocator, a two-tier cache where only one thread refreshes a key, reconciling two huge maps across regions, a backup retention service, and a JavaScript style Promise built in Java. "System coding" at Rubrik is broader than threads: memory allocation and block I/O count too (module 17).

Theory reported: mutex, lock and semaphore, and OS task scheduling; OS resource allocation policies with pros and cons before coding; how CAS works; process and memory management; why you chose CyclicBarrier or Semaphore; interrupts, which exceptions a pool must catch, shutdown versus shutdownNow; starvation and deadlock.

What is judged: where the critical sections are and where threads are created; shutdown semantics, interruption and exception handling in pools; the choice of constructs; explicit fairness and starvation follow ups; fully working code. In one 2026 screen the interviewer changed the requirements three times. Passing the coding rounds is not the end: in a 2026 loop the hiring manager rejected the candidate on project depth, so prepare one deep systems project story.

Databricks

Rounds. The official prep guide (April 2025) describes a backend panel of four to six one-hour interviews drawn from Coding, Algorithms, System Programming, Architecture, Domain Deep Dive and Cross-Functional, in CoderPad. System Programming covers multithreading, synchronization, I/O and performance: you build components from files, buffers, caches, storage and concurrency, in both single-threaded and multithreaded versions, and design quality is graded. Officially it is pseudocode and language agnostic, but a 2025 L4 report says a full C++ implementation was expected, and a 2026 SDE-II was told the code need not run but should be close. Plan for code that nearly runs. Candidates call it System Programming, the Concurrency round, or an LLD and concurrency deep dive; it is reported at L4, L5, Staff and L7. Blind commenters (likely 2026) say L4 gets the multithreading round instead of system design, and L5 adds system design. Phone screens are almost always DSA.

Recurring problems. The most common is a concurrent, ordered, durable log or event writer: one lock with a write and an fsync per event (too slow), then a single writer thread fed by a queue, then batching so one fsync covers many events (group commit), then a future per event completed after its fsync, then flush, close and back-pressure. Next, a web crawler made multithreaded, often with a depth limit and given fetch and parse helpers. Then parallel chunk fetching behind a cache, where each chunk must be fetched once. One reported round was mostly theory: how ConcurrentHashMap locks and why HashMap breaks, with about four lines of code; a Databricks-tagged commenter said compare-and-swap questions have become common.

Theory reported: ConcurrentHashMap internals, CAS, the cost of fsync and why you batch, how you know threads will help, pool size against dataset size, disk and network bottlenecks, back-pressure policy, how to test for races. A Databricks-tagged commenter advises knowing the Java memory model, happens-before, volatile, conditions and semaphores.

What is judged: correctness before cleverness (one low confidence report describes a lock-free attempt the candidate could not justify, replaced by a plain synchronized version that passed), and design quality. Practise the durable log writer, the crawler, the cached chunk reader and the hit counter.

Google (L5)

Weight: low to moderate, and team dependent. The standard L5 loop has no concurrency round, and only 8 of 128 senior-titled Google reports in the research mention a concurrency term at all. When it appears, it is usually the last 10 to 15 minutes of a coding round, after the data structure problem is solved: one writer and many readers of a flight price map, many threads updating a per-user counter map, readers and writers on a circular buffer, a multithreaded time-based key-value store, an asynchronous API that calls back on another thread, video frames arriving out of order that must be forwarded in timestamp order (solved in C++ with mutexes). A dedicated question at L5 is rare but real: a 2026 report asked for a custom CompletableFuture built "under the hood". Embedded, Android and infrastructure teams ask more.

What is judged: precise reasoning, not a list of tools. A 2025 L5 candidate who mentioned ConcurrentHashMap, AtomicInteger and synchronized still got No Hire, and concluded that races and consistency guarantees had to be reasoned through. A single follow up can sink a solved round. Syntax matters too: a 2024 L4 candidate needed help with C++ thread syntax mid-round. Practise the concurrent time map, the striped hash map, the reorder buffer, the timer multiplexer and a future from scratch.

Uber

India (L5a, SDE 3): high. The "Depth in Specialization (Coding 2)" slot is usually a machine coding or LLD round: runnable, modular code in your own IDE, sometimes in person at the Bengaluru office, with concurrency requirements. Senior reports include an expiry counter (marked down for not purging stale data, which is "production" thinking), a car rental reservation service, multiple producers and consumers across queues (rejected for no running code), folders whose path printing is called concurrently (rejected on that round alone), and a scheduler. The larger SDE2 (L4) pool is a useful guide to the question pool, though the overlap with senior loops is an inference: a multithreaded job scheduler, multithreaded pub-sub or "Kafka with concurrency support", a thread-safe leaderboard, a circuit breaker, cab hailing "with multithreading scenarios", a cache with expiry.

US: moderate. Depth in Specialization can be a plain LeetCode problem (Trapping Rain Water at L5a in New York, 2024), with concurrency as a follow up in another round: how the solution changes in a multithreaded environment, or what happens when 10,000 scheduleMeeting requests arrive at once. Uber's official guide mentions neither concurrency nor machine coding, so ask which version you will get.

What is judged: running code you can demo, separation of concerns, correctness under concurrency, and production thinking. Over-locking counts against you: an Uber interviewer on Blind (2021) complained that candidates "put synchronization everywhere". Practise the pub-sub broker, the TTL cache, the scheduled executor, the leaderboard, the ranged key-value store and the ride dispatcher.

Meta (E5)

Low in coding, moderate in design. Coding rounds are two problems in about 40 minutes, and the research found only one ambiguous "can you implement thread safe" follow up, in 2025. Concurrency lives in system design and product architecture: ticket booking (seat locks, two users and one seat, popular events), auctions and flash-sale style contention, concurrent contests, a cache on a single machine where sharding the table roughly per core "to lock more efficiently" was praised, and, in an E4 client track loop, a file downloader ("how many threads would you want, what is a safe number?"). Infrastructure loops go deep on "concurrency control and race condition resolutions". What is judged: a concrete mitigation for hot contention, the choice between pessimistic locks, optimistic concurrency and queues, and lock granularity on one machine. Practise seat booking and the striped hash map, and study the design cases.

Rippling

Rounds (2023 to 2026). A technical phone screen on HackerRank CodePair with one multi-part problem, a hiring manager round, two or three coding rounds and one system design; some senior loops add a 90 minute machine coding "web API design" round, and from 2025 there is an AI-assisted coding test option. Rippling reuses a small pool of practical, multi-part object-oriented problems: an in-memory key-value store with transactions, delivery cost tracking for drivers, music analytics, an expense rules engine, a spreadsheet, article voting.

Concurrency depends on the interviewer. Some prompts exclude it in writing ("does not need to be thread-safe"). Others add it as a follow up: two threads updating the same key in the key-value store, where the candidate had to reproduce the race and then fix it; "how to handle race conditions" after a currency conversion problem; options for handling races in the API round, which earned a Strong Yes. In system design, a hotel booking interviewer's main questions were about handling multiple bookings. Idempotency keeps recurring across rounds: event rollups with retried batches in design, and in a 2026 phone screen a payout call that must never pay twice when it is called again. No debugging round is reported at Rippling.

What is judged: running code with tests (one report says non-running code is a reject), finishing all parts, extensible object-oriented design, exact money handling (integer cents or BigDecimal, never double), and honesty if you have seen the question before. The research's own advice: mention concurrency, offer it, do it when asked, but do not slow the base solution down. Practise the key-value store with transactions and room booking, and study idempotency.

LinkedIn

Very high on the Systems and Infrastructure track, where a one hour Concurrency round with working code is the clearest signal in the whole study, sometimes as the very first round. The delayed scheduler (the ScheduledExecutorService.schedule shape) dominates: one 2022 candidate estimated it at about 6 in 10 rounds. Others: a bounded blocking queue (one 2024 loop allowed only wait and notify, with no semaphores, mutexes or executors) with graceful shutdown; producer-consumer with shutdown, with questions on the context switches at each step; Building H2O; a ThreadPoolExecutor clone. Phone screens ask process versus thread, mutex versus semaphore, paging, and the output of a multithreaded program. On the apps track and in the AI-enabled coding round, expect to make the code thread-safe and then give an example of the race each lock prevents (a cache that retains the best entries), or to walk through the race where two threads both see 99 of 100 requests (a rate limiter). Two 2025 infrastructure loops had no concurrency round, so ask. LinkedIn engineers on Blind suggest Java; Piyush should confirm C++ is fine early. Practise the scheduled executor, the bounded queue, producer-consumer with shutdown, H2O and the retain-best cache.

What interviewers judge, almost everywhere

  • Correctness first. No races, no deadlocks, no lost wakeups, every invariant held. A fast wrong answer loses to a slow right one.
  • Precise reasoning. Name the shared state, the race and the interleaving that breaks it. LinkedIn interviewers asked for the race each lock prevents; a Google L5 candidate who listed tools without that reasoning got No Hire.
  • The least clever tool that works. A plain lock you can defend beats a lock-free design you cannot.
  • No over-locking. Locks around everything are a negative signal (Uber), and so is a lock you cannot justify (LinkedIn).
  • Lifecycle and failure. Shutdown, interruption, exceptions inside tasks, timeouts (Rubrik's pool rounds grade exactly these).
  • Fairness when asked. Starvation and admission order are explicit follow ups at Rubrik.
  • Running code, quickly. In AI-enabled and multi-part rounds (LinkedIn, Rippling, Atlassian, Apple), speed on the base task decides whether you even reach the concurrency part.

Worked example: from invite to plan

Piyush gets a Rubrik G6 loop: System Coding 1, Algorithms, System Coding 2, Design, Hiring Manager. With two weeks left: rebuild the bounded queue, the thread pool with shutdown and shutdownNow, the wait-for-all executor and the dependency job runner from memory in C++ with no library executors, each under 45 minutes; do two debugging problems against the clock and make sure they compile; rehearse the reader-writer family and the fair bathroom; review parallel file copy for the design round; prepare one deep project story for the hiring manager; run two Bar Raiser mocks in Rubrik style.

Shubhi gets a Databricks L5 onsite with a System Programming round. With two weeks left: build the durable log writer end to end in Java (single writer, batching, futures completed after FileChannel.force, close and back-pressure) and explain each step out loud; do the crawler with a depth limit and the cached chunk reader; revise ConcurrentHashMap internals, CAS, volatile and happens-before as spoken answers; practise explaining out loud how you know threads will help (lesson 01-03); run two mocks with the "concurrency in system design" and "coding" focus.

Notice the difference: the same subject, two very different preparations, both driven by what the reports say each company asks.

Common mistakes

  • Preparing only LeetCode's concurrency puzzles. Databricks asks I/O systems (writers, crawlers, caches), Rubrik asks executors and debugging, Meta asks design contention. The puzzles are a small slice.
  • Relying on ExecutorService or BlockingQueue for Rubrik. Practise building them from locks and conditions until it takes minutes, not an hour.
  • Reading "pseudocode" literally at Databricks. Write code that would nearly compile; at least one L4 had to write full C++.
  • Listing tools instead of reasoning. "I'd use ConcurrentHashMap" is a start, not an answer. Say which race it prevents and what a reader can still observe.
  • Ignoring the debugging round. Reading someone else's threaded code fast is a separate skill; train it on purpose.
  • Not asking the recruiter. Rounds vary by team, track and level. Ask which rounds you will get, which language, and whether code must run.

In the interview

Whatever the format, the first two minutes are the same: pin down the constraints before you design. One Rubrik interviewer changed the requirements three times in a single screen, and some Rippling prompts rule concurrency out in writing, so asking is not stalling; it is the job.

Before I start, can I check a few constraints? How many threads call this, and can callers block, or must calls return immediately? May I use the standard concurrency library, or should I build the queue and the pool from locks and condition variables? Should this compile and run here, or is detailed pseudocode enough? And is there a fairness or ordering requirement I should respect?

Then name the shared state and the invariant, choose the primitive and say why, write it, and walk through the interleaving that would break a naive version. Expect the same follow ups almost everywhere: name the race each lock prevents (LinkedIn), absorb a changed requirement without starting over (Rubrik), add shutdown, timeouts and task failures (Rubrik's pool rounds), and finally "now there are many servers", where a lock inside one process no longer helps and a database conditional update or an atomic Redis script becomes the arbiter (Salesforce and Amazon reports).

Each lock here prevents one specific race. Without this one, two puts could both see room and push the cache past its capacity; without that one, a reader could see the map updated but the list not yet.

The coding round playbook in module 18 turns this into a full routine, and the company playbooks repeat this lesson's essentials for the night before.

Key takeaways

  • These patterns come from candidate reports dated 2022 to 2026; ask your recruiter for your exact rounds.
  • Rubrik: two System Coding rounds, frequent library bans, a separate debugging round, code that must run.
  • Databricks: System Programming on durable writers, crawlers and caches; "pseudocode" that should nearly run.
  • Google and Meta: a decisive follow up after coding (Google) or contention inside system design (Meta); Uber India, Rippling and the Indian machine coding rounds grade running, thread-safe designs.
  • LinkedIn infrastructure: a dedicated Concurrency round, usually a delayed scheduler or a bounded queue.
  • Everywhere: correctness, precise reasoning about races, the least clever tool, lifecycle and failure handling.

Why. The official wording is a floor, not a ceiling. One L4 candidate had to write a full C++ implementation, and a 2026 SDE-II was told the code should be close to working. Near-runnable code satisfies every version of the round.

Why. Meta's coding rounds are speed and correctness on algorithm problems; the research found only one ambiguous thread-safety follow up. Concurrency questions sit in design: two users and one seat, hot auctions, locking granularity in a single machine cache.
What does Rubrik's debugging round test that writing code from scratch does not?
Why. You are handed a program you have never seen (one report: a barber shop simulation of about 180 lines) with planted concurrency bugs, and must fix them in place within the hour. The tempting wrong answer is "describe the fixes": a 2025 new grad found the deadlock but lost the round on a compile error, so the fix must also build and run. Rewriting from scratch throws away the skill being tested, and predicting output without fixing anything is a different format (Microsoft's predict-then-fix, or online assessment MCQs).
A LinkedIn style follow up: "Walk me through the race in this rate limiter." count is an atomic integer (AtomicInteger in Java, std::atomic<int> in C++) and limit is 100. What is the race?
Why. Atomics make each single call indivisible, but nothing stops a second thread from running its get between your get and your increment. That gap is the 99 of 100 race. Fix it by making check and increment one step: a compare-and-set loop that only writes c + 1 if the value is still c and c is below the limit, or a lock around both. Atomics do guarantee visibility, and an atomic integer is lock-free on every mainstream platform, so there is no lock to deadlock on: the other two options are wrong. Interviewers ask this exact walk-through because naming the interleaving is the reasoning they grade.

Design
Your recruiter confirms a Databricks L5 onsite whose panel includes System Programming, and you have two weeks. Write your preparation plan in five or six lines, each with what you will do and why.
Model answer
  1. Durable log writer, end to end, twice. It is the most reported Databricks concurrency problem: single writer thread, batching with one fsync per batch, a future per event completed after its fsync, flush and close, back-pressure when the queue fills. Build it, then explain each step out loud.
  2. Crawler with a depth limit, then multithreaded. The second most reported problem; practise saying why threads help (fetching is I/O bound) and what limits the thread count.
  3. Cached chunk reader. Parallel fetches where each chunk is fetched once, which is single-flight under concurrency.
  4. Spoken theory. ConcurrentHashMap internals, CAS, volatile and happens-before, the cost of fsync, because at least one reported round was mostly theory.
  5. Write near-runnable code every time, because "pseudocode" has meant full code for some candidates.
  6. Two Bar Raiser mocks in Databricks style, one coding focus and one design focus, and fix whatever the scorecards flag.
Explain
At the end of a Google coding round, the interviewer says: "Many threads now call increment(userId) on your per-user counter map, and others call get(userId). What changes?" Answer as you would out loud, including what guarantees your version gives.
Model answer

The shared state is the map and the counts inside it, and there are two races. First, check then act on a missing key: two threads both see no entry for a new user, both put a count of 1, and one increment is lost. Second, the lost update on the count itself: two threads read 5, both write 6.

In Java I would use a ConcurrentHashMap and do the whole update atomically, with counts.merge(userId, 1L, Long::sum), or computeIfAbsent(userId, k -> new LongAdder()).increment() if a few users are very hot. In C++ I would protect the map with a mutex, or shard it into, say, 16 maps each with its own mutex chosen by the hash of the user id, so threads working on different users rarely contend; the increment happens inside the shard's lock, and get takes the same shard lock, because reading an unordered_map while another thread inserts into it is a data race too.

The guarantees: every increment is counted exactly once, and get returns a value that was true at some moment during the call; it may not include increments still in flight. If someone needs a consistent total across all users, that is a different question: summing shard by shard gives a total that may never have existed at any single moment, unless I lock every shard together, in a fixed order. I would test it by running many threads with known numbers of increments and checking the exact final counts, and in C++ under ThreadSanitizer.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 80 s
"Here is the problem: build a job scheduler that many threads submit to. Before you write anything, what do you want to ask me, and why does each answer matter?"
What a strong answer covers
  • Ask before designing, and say what each answer changes in the code
  • Callers: how many threads submit, and may a submit block or must it return at once
  • Toolbox: is the standard concurrency library allowed, or should the queue and pool be built from a lock and condition variables
  • Format: must the code compile and run here, or is detailed pseudocode enough
  • Rules and lifecycle: ordering or fairness, what shutdown does with queued jobs, and what happens when a job throws or hangs
  • Then the plan: a working single threaded core first, then the shared state, the invariant, the primitive and the interleaving that breaks a naive version
How a senior would say it
Before I design anything, I want five answers, because each one changes the code. First, how many threads submit, and may a submit block, or must it return at once? That decides whether I need a queue in front of the workers and what happens when it fills. Second, may I use the standard library, or should I build the queue and the pool myself from a lock and condition variables? Some companies ban the library on purpose. Third, must this compile and run here, or is detailed pseudocode enough? Fourth, is there an ordering or fairness rule, say jobs start in submission order, or no submitter starves? And fifth, lifecycle: what does shutdown do with jobs still queued, and what should happen when a job throws or never returns? Then I would say my plan: a working single threaded core first, then I name the shared state and its invariant, pick the simplest primitive that protects it, and walk through the interleaving that would break a naive version.

Likely follow up: No libraries allowed. What is the first class you write, and what does it guard?

Out loudabout 90 s
"Your LRU cache works. Now many threads call get and put at the same time. Talk me through what changes, before you write any code."
What a strong answer covers
  • Name the shared state, the map and the recency list, and the invariants: they always agree, and the size never exceeds capacity
  • get is a write, because it moves the entry to the front, so a read-write lock buys almost nothing
  • First version: one mutex around every get and put, with short critical sections and no I/O inside
  • Name the races the lock prevents: two puts overfilling the cache, or a get moving a node that a concurrent put is evicting
  • To scale: shard by key hash into smaller caches with their own locks, and say that eviction becomes only approximately least recently used
  • Test it: many threads, check size and map list consistency, and run C++ under ThreadSanitizer
How a senior would say it
First I name the shared state: the hash map and the recency list, and the rules that they always agree and the size never goes past capacity. The trap is that get is not a read. It moves the entry to the front of the list, so it changes shared state, and a read-write lock buys almost nothing. So my first version is one mutex around every get and put, with short critical sections and nothing slow inside. Each acquisition prevents a specific race: two puts both seeing room and both inserting past capacity, or a get moving a node that a concurrent put is evicting, which corrupts the list. If that one lock becomes the bottleneck, I would shard by key hash into, say, sixteen smaller caches, each with its own lock. That scales, but eviction becomes approximately least recently used rather than exact, and I would say that trade off out loud. To test it, I run many threads, check the size never exceeds capacity and the map and list stay consistent, and in C++ I run it under ThreadSanitizer.

Likely follow up: Why not a ConcurrentHashMap for the map and a separate lock for the list?

Out loudabout 90 s
"Two users click 'book' on the last seat at the same moment. How do you make sure exactly one of them gets it?"
What a strong answer covers
  • The check and the reserve must be one atomic step, or both users see the seat as free
  • In one process: a lock per seat or per show around the check and the reserve
  • Across many servers a process lock does not help: the database decides, with a conditional update where the seat is still free, and a check of rows changed
  • A hold with an expiry, confirmed after payment, with no row lock held through payment
  • An idempotency key, so a retried request does not book twice; for a hugely popular event, a queue or waiting room in front
How a senior would say it
Exactly one wins only if checking the seat and reserving it are a single atomic step. Otherwise both requests read "free" and both book. Inside one process, I would keep a lock per show, or per seat, and do "if free, mark it held by this user" inside that lock, so the second caller sees it taken. But a real booking service runs on many servers, and a lock in one process means nothing to the others. So the database is the arbiter: one conditional update that makes this user the holder only where the seat is still free, with no holder or only an expired hold, and I check that exactly one row changed. The loser gets a clear "seat taken". The hold carries an expiry, so an abandoned checkout frees the seat, and after payment a second conditional update confirms it only if the hold still belongs to this user. I never keep a row lock open through payment, because payment can take seconds or fail. Each request also carries an idempotency key, so a retry after a timeout does not book twice. And for a hugely popular event, I would put a queue or a waiting room in front, so the database is not hit by everyone at once.

Likely follow up: The hold expires while the payment is still in flight, and the payment then succeeds. What happens, and what should happen?
