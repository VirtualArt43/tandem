Distributed locks, leases and fencing tokens

Understand expired leases, reject stale writes with fencing tokens, and choose between coordination services and database constraints.

Asked atAmazonBloomberg
Before this:Optimistic versus pessimistic concurrency controlIdempotency, retries and exactly-once effectsMutexes and RAII guards

A local mutex stays locked when its owner pauses. A lease across machines can expire during that pause, letting a replacement start while the old worker still believes it owns the resource. Correctness depends on what the resource accepts when that worker resumes.

In plain words

A hotel room key card stops working at checkout time. That is a lease: access that expires on its own, so a guest who vanishes does not keep the room forever. But suppose a guest oversleeps past checkout and the room is given to someone new. The old guest wakes up, still holding a card, and walks to the door.

Imagine the door tracks a card issue number: once it has seen card 34, it refuses card 33. The door, not the guest, decides. That issue number is a fencing token, and the idea that the protected resource must reject stale holders is the heart of this lesson.

What breaks when the lock lives on another machine

A distributed lock is a lock held in a separate service (Redis, ZooKeeper, etcd, a database row) so that processes on different machines can exclude each other. Remote coordination must handle these failures independently of the protected resource:

  • The holder can die while holding it. A crashed client never releases its remote lock. Recovery needs a lease, session expiry or another safe revocation protocol.
  • The holder can pause without knowing. A stop-the-world garbage collection, a virtual machine being migrated, heavy swapping or a laptop lid closing can freeze a process for seconds. When it resumes, it carries on from the next line of code.
  • Messages can be delayed. A write sent while you held the lock can sit in a network buffer and arrive after you lost it.
  • Clocks disagree. "Expires in 10 seconds" is measured by two machines, whose clocks run at slightly different rates and can be stepped by time synchronization.

A linearizable lock service can grant only one valid lease at a time. It cannot force a paused client to stop executing when that lease expires. One valid owner does not imply one active worker. Local threads can pause or die too, but a normal std::mutex is not automatically reassigned while its owner is paused.

Leases: locks that expire

A lease is a lock with a time limit. The holder must renew it (a heartbeat, for example every third of the lease time) to keep it; if the holder dies, renewals stop, the lease expires, and someone else can take over. Expiry lets a replacement take over after a crashed holder. A paused holder creates the same takeover opportunity without actually stopping the old program.

The obvious patch, "check that my lease is still valid right before writing", does not work. It is a check-then-act with a gap, and the pause can land in the gap: the check passes, the process freezes, and the write happens much later. A holder should stop starting work before its local deadline: time from before sending the acquire request, subtract acquisition latency and a safety margin, and use a monotonic clock with suitable drift and suspend behaviour. This reduces stale requests but cannot retract a write already in flight.

Fencing tokens: let the resource say no

The fix moves the decision to the resource. Each successful ownership grant for that resource gets a strictly increasing token, and the holder includes it with every write. The resource atomically compares the token, records its maximum and applies the effect; it rejects smaller tokens. The token counter and the resource's accepted maximum must survive failover, and every write path must enforce the check.

The latches force the bad interleaving without sleeps. Real pauses can come from garbage collection, scheduling or suspension in either language; this in-memory simulation has no persistent token state and assumes small positive durations and no counter overflow. In C++17, where std::latch does not exist, a std::promise<void> and its future do the same one-shot handoff.

In a database, a single-row conditional write can implement the check: UPDATE reports SET body = $1, fence = $2 WHERE id = 7 AND fence <= $2. Initialize fence to a non-null value and accept only valid positive tokens; zero updated rows means either the row is absent or the predicate rejected it. A read-check-write sequence in separate requests would reintroduce the race.

Fencing orders ownership generations; it does not check time. If token 34 was granted but storage has only seen 32, a delayed write with 33 can still succeed. The replacement should install 34 at the resource before reading state on which its work depends, or use a resource transaction that checks current ownership. Once 34 is installed, 33 cannot overwrite it. If several rows form one invariant, guard their changes together in a transaction; separate per-row checks do not provide that atomicity.

Equal tokens are allowed here so a holder can issue several writes. They do not deduplicate retries or order writes within one holder: use operation ids and, where necessary, per-operation sequence or version checks. Tokens also are not authentication; callers must not be able to invent an arbitrarily high token.

Token allocation must follow the grant order and never reuse an older generation. A ZooKeeper lock node's creation transaction id (czxid) or an etcd lock key's creation revision can supply that order. An ordinary znode data version resets on recreation, and an unrelated database sequence call can be reordered with acquisition, so neither is automatically safe. Restoring an old snapshot or exhausting a counter also requires a coordinated new epoch before writes resume.

If a resource cannot reject stale operations, an external lease cannot provide this protection for it. Idempotency can suppress duplicates of the same operation, but does not prevent an old holder from submitting a different, stale update. Use a conditional downstream API, a durable dispatcher that enforces ownership, or explicitly accept that limitation.

Both details matter. Without expiry or another recovery mechanism, a crashed client can hold the lock forever. Without the compare-and-delete, a client whose lease expired can DEL a lock that now belongs to someone else, a check-then-act bug in the release path. But a single Redis node is a single point of failure, and if it fails over to a replica that had not yet received the SET (replication is asynchronous), the lock silently vanishes and a second client acquires it.

Redlock, proposed by Redis's author, runs the same SET NX PX on N independent Redis masters (typically 5). A client holds the lock if it acquired it on a majority within less time than the lease; its usable time is the lease minus the time spent acquiring minus an allowance for clock drift.

In 2016 Martin Kleppmann published "How to do distributed locking", a critique with two main points. First, Redlock does not produce fencing tokens (the random values do not increase), so it cannot protect a resource from a paused holder, which is the failure that matters. Second, he argues that its timing assumptions fail under sufficiently delayed messages, pauses and clock changes. Salvatore Sanfilippo's reply disputes the need for bounded network delays and pauses in the lock algorithm, while assuming bounded relative clock-rate error and correct validity checks. Neither argument makes a lease cancel a stale external write. You do not need to pick a winner in an interview. Read the critique, response and Redis locking guidance. ZooKeeper and etcd: sessions, ephemeral nodes and leases

ZooKeeper uses Zab for ordered replicated updates, and etcd uses Raft. Under their quorum and durability assumptions, ordinary leader failover preserves committed coordination state; losing a quorum sacrifices progress rather than granting conflicting ownership. This does not make every read linearizable: ZooKeeper reads can be stale, and etcd offers explicitly stale serializable reads as an alternative to its default linearizable reads. Both systems tie locks to client liveness. See the etcd API guarantees.

ZooKeeper clients hold a session, kept alive by heartbeats. An ephemeral node lives only as long as the session that created it: if the client dies or is partitioned away long enough for the session to expire, ZooKeeper deletes the node. A sequential node gets a counter suffix allocated under its parent. The recipe assumes that parent is retained and the finite counter does not wrap; production use must handle namespace recreation and counter exhaustion. Together they make the standard lock recipe:

The predecessor may disappear between listing and watch registration, so the existence check and watch must be one ZooKeeper operation. If creation succeeds but its reply is lost, find your GUID among the children before retrying creation. Watches are one-shot notifications to re-check state. See the ZooKeeper lock recipe.

Watching only your predecessor, instead of the lock holder, means a normal release wakes its successor rather than all waiters: the thundering herd avoided by design. leader election is the same recipe: the lowest node is the leader. In Java, Apache Curator provides InterProcessMutex and LeaderLatch. For the mutex, acquire(long time, TimeUnit unit) returns a boolean and can throw Exception; only a successful acquisition requires a matching release() by the owning thread. See its API contract; in C++ you would use ZooKeeper's C client with the ZOO_EPHEMERAL | ZOO_SEQUENCE flags.

etcd uses leases directly: you grant a lease with a time to live, attach keys to it, and keep it alive; when it expires, its keys are deleted. A modifying transaction advances the store revision; multiple key changes in one transaction share that revision. In the lock queue, the ownership key's creation revision supplies a fencing token. For data stored in etcd, a transaction can compare that key's creation revision while writing the data; a separate check followed by an external write is not atomic.

Consensus fixes lost locks on failover. It does not fix the paused holder: a session expires on the server, and a frozen or partitioned client does not learn about it until it talks to the cluster again. Even with ZooKeeper or etcd, writes to the protected resource need fencing.

Design so that a brief double leader is survivable

Assume stale work can overlap replacement work, without inventing a bound on how long or how often, and make the effects safe:

  • Fence every write the holder makes, with a token or an epoch the resource checks.
  • Make each action idempotent: a nightly invoice run inserts invoices under a unique key (customer_id, period), so a second leader's inserts fail harmlessly.
  • Make writes conditional on the state the leader read (version checks), so decisions based on an older version cannot overwrite a newer version. A version check alone does not prove current lease ownership.
  • Stop early: renew with enough headroom, for example at a third of the lease, and stop starting work before your local deadline. Renewal must atomically check the current ownership token before extending expiry.
  • Keep leader work small and resumable, so the next leader can pick up from durable state instead of trusting the old one's memory.

Prefer no lock at all

Before reaching for a lock service, ask what the lock protects. Usually the answer is "a row" or "a key", and something cheaper already gives you exclusion:

  1. A single owner by construction. Partition the work so that one consumer owns each key (the next lesson, ordering by ownership). Ownership changes still need fencing or idempotent, conditional effects; a hot partition can still contend.
  2. Let the database arbitrate. A conditional update or a unique constraint often enforces the invariant directly. A FOR UPDATE SKIP LOCKED claim holds a row lock only until transaction end: commit an owner, expiry and increasing attempt number, then check that attempt on every later database effect. See optimistic versus pessimistic.
  3. A lease from a consensus store, plus fencing, for coarse coordination such as "one active scheduler".
  4. A Redis lock, only where a duplicate costs efficiency, not correctness.

The best distributed lock is the one your design does not need.

Worked example: one node sends the nightly invoices

Three scheduler nodes run; invoices must go out once a night.

First attempt: each node tries SET lock:invoices <unique-value> NX PX 600000 at midnight; the winner runs the job. Failure: the job takes longer than 10 minutes, the lock expires, a second node starts, and customers get two invoices. Raising the TTL only moves the problem.

Better: make the job safe to run twice. Insert invoices under a unique constraint on (customer_id, period) and enqueue their emails in the same transaction. A dispatcher uses a stable invoice id as the provider's idempotency key. A conditional database claim alone cannot make an email exactly once: marking before sending risks loss on a crash, and marking after sending risks duplicates. If the provider cannot deduplicate, choose and document that tradeoff. Once the effects are safe, the scheduler lock is only an efficiency hint.

Best: skip the lock. A row per night in a job_runs table with a unique run_date; the node whose INSERT succeeds owns tonight's run, records progress per customer, and a replacement atomically claims an expired run by increasing its attempt number. Each subsequent database transaction locks the job row, checks the current attempt, and commits its progress and outbox effects together; a stale runner cannot pass after takeover commits. External effects still need the downstream idempotency just described.

Common mistakes

  • No recovery mechanism. A crashed holder can block everyone indefinitely without expiry, session recovery or safe revocation.
  • Releasing with a plain DEL. After your lease expired, the key may be someone else's lock. Compare and delete atomically.
  • Checking "do I still hold it?" before writing, and calling that safe. A pause between the check and the write defeats it. Fence at the resource.
  • A lease shorter than the work, with no renewal. The lock expires mid-job by design.
  • Measuring the lease with the wall clock. Time synchronization can step it. Use a monotonic clock and a safety margin.
  • Treating ZooKeeper or etcd as a cure. They stop lost locks, not paused holders.
  • Using a distributed lock where a database constraint would do. More moving parts, weaker guarantees.

In the interview

Candidate reports in the research include an Amazon SDE2 locker design with distributed-locking follow ups and a Bloomberg backup-job coordinator with a lock registry and pessimistic versus optimistic locking. Be ready to explain what happens when a worker pauses during a lease, and which system actually rejects its stale write.

An expiring lock can leave two workers acting as owners, because the old holder can pause past its lease without knowing. So I would make it a lease, renew it, stop early, and, for anything where a double holder causes damage, have the lock service hand out a fencing token that the storage checks, rejecting writes with an older token.
Before adding a lock service I would try to design the lock away: give each key a single owner by partitioning, or let the database arbitrate with a conditional update or a unique constraint. I would keep a Redis lock for efficiency only, where a duplicate run wastes work but corrupts nothing.

Follow ups to expect: "What happens if the lock holder has a long GC pause?", "Why not just check the lease before writing?", "Is Redlock safe?", "How does ZooKeeper's lock recipe avoid waking everyone?", and "What if the resource cannot check a token?" (deduplicate repeated operations where possible, but do not claim that this rejects every stale update).

Senior depth

This idea is older than Redis. Google's Chubby lock service paper (Burrows, 2006) describes "sequencers": a holder can ask for an opaque token describing its lock and generation, pass it to the servers it talks to, and those servers check it. That is a fencing token. Chubby also delays re-granting a lock whose holder vanished, to let stale messages drain, the same instinct as a lease safety margin.

Clock discipline helps validity checks, not external write atomicity. Lease intervals can use elapsed time without synchronized clock origins, provided rate error and suspend behaviour fit the safety margin. A monotonic clock avoids backwards wall-clock adjustments but does not prove bounded drift or timely scheduling. A delayed write still needs resource-side fencing; increasing the TTL trades slower recovery for fewer avoidable takeovers.

Fencing generalizes to epochs within a protocol. Raft terms help peers reject stale leaders, and Kafka producer epochs let brokers reject an older producer. Neither automatically fences an external database or email service: that destination needs its own enforced ownership or idempotency contract. A number in a message becomes a fence only when every relevant receiver checks it.

Key takeaways

  • One valid lease can coexist with an old worker still acting; expiry does not cancel remote work.
  • Leases and session expiry enable recovery after a failed holder, at the cost of possible stale work.
  • Fencing tokens let the resource reject a stale holder's writes; the resource must take part.
  • Redis SET NX PX with compare-and-delete is fine for efficiency; for correctness use a consensus store plus fencing.
  • Design so a brief double leader is harmless, and prefer no lock: single ownership or database arbitration.

Why use lease or session expiry when a remote lock must recover automatically from a crashed holder?
Why. A dead client cannot release its lock, so expiry is one mechanism for automatic recovery; other safe revocation protocols are possible. Expiry does not inherently make acquisition faster. The price is the opposite problem: a holder that is merely paused can outlive its lease while still believing it holds the lock, which is why leases do not remove the need for fencing.
A worker calls a correct, thread-safe application helper lease.isValid() immediately before every write to storage. Why is this still unsafe?
Why. It is a check-then-act with a gap, and a garbage collection pause or a scheduling stall can sit in that gap for seconds. A correct client-side check is still separated from the write. The helper need not be racy, and checking it does not renew anything. The resource must atomically enforce ownership or token ordering with the write.

Why. The rule is "reject anything older than the newest token seen". The current holder may write several times with 34, and a newer holder's 35 is accepted and raises the bar. A client acquires a Redis lock with SET lock:x <random> NX PX 30000, works for 40 seconds, then releases it with DEL lock:x. What can go wrong?
Why. Two bugs combine: the work outlived the lease, so another client could take over during the remaining 10 seconds, and the release may delete a lock it no longer owns. Releasing must compare the stored value with your random value and delete only on a match, atomically, which is why a Lua script is used. Renewal reduces unnecessary expiry but cannot bound all pauses; fencing or equivalent conditional effects must still enforce correctness. DEL on an absent key returns zero, and NX does not restrict later deletes.
Which statement fairly summarizes Martin Kleppmann's critique of Redlock?
Why. Redlock tolerates a minority of failed nodes, and Redis keys do expire. The critique is about correctness under pauses and clock problems: without a token that only grows, the resource cannot tell a stale holder from the current one.
In the ZooKeeper lock recipe, each waiting client watches only the node with the next lower sequence number, not the current holder's node. Why?
Why. If every waiter watched the holder, each release would wake all of them to re-read the children, and all but one would go back to waiting. Watching your predecessor forms a queue: a normal release notifies its successor. Watching the holder is allowed but wasteful; this choice does not provide reentrancy or solve counter reuse.
In a fresh demo Storage, call write("old", 33), write("new", 34), then write("late", 33), in that order. What acceptance results and final content do you get?
Why. Storage starts with maximum token 0. It accepts 33, then accepts 34 and raises its maximum, then rejects 33. Granting a newer lease elsewhere does not update this storage automatically: rejection begins when storage observes the newer generation. Requiring tokens to equal the current maximum would incorrectly reject every new holder.

Checkpoint

Design
A nightly job must run on exactly one of three scheduler nodes, and running it twice would email customers twice. Design it.
Model answer

I would separate invoice creation, job ownership and email delivery. A unique (customer_id, period) key prevents duplicate invoices, and the same transaction inserts an email outbox row with a stable operation id. A dispatcher sends that id to a provider that durably deduplicates it through our retry horizon, then records completion. A conditional claim by itself cannot guarantee one email: marking before sending can lose it, and marking afterwards can repeat it. Without provider deduplication, I would state that limitation rather than promise exactly once.

For scheduling, use one job_runs row per date with a lease and increasing attempt. A takeover atomically increments the attempt. Every progress or outbox transaction locks that job row, verifies its attempt still matches, then writes and commits, so takeover and effects serialize. Recover from durable per-customer progress; a paused worker is rejected when it resumes. If coordination moves to etcd or ZooKeeper, the database still needs to enforce its fencing generation.

Debug
Find the bugs in this lock usage and fix them.
Model answer
  1. The value is not unique. Every client writes "1", so a client cannot tell its own lock from another's. Use a random value per acquisition.
  2. The release is a blind delete. After a 20 second build the 5 second lease has expired and another client holds the lock; delete removes their lock. Release with an atomic compare-and-delete (the Lua script) on the random value.
  3. The lease is shorter than the work, with no renewal. Renew with an atomic ownership check, leave safety headroom, and stop starting work if renewal fails. A background thread can pause too, so renewal does not replace fencing.
  4. The write is not fenced. A paused client can still overwrite a newer report. Obtain a token that only grows (atomically ordered with ownership grants and durable across failover), pass it to storage.put, and have storage reject smaller tokens; or make the write conditional on a version.
  5. No failure path. If buildReport throws, waiters must wait for expiry. Release with compare-and-delete in Java finally or a C++ RAII guard whose cleanup does not throw.
Explain
In two minutes: is Redlock safe, and what would you use instead?
Model answer

Redlock acquires a Redis lock on a majority of independent Redis masters within the lease time, which can tolerate a minority of unavailable masters. Kleppmann's critique makes two points: Redlock hands out random values rather than increasing fencing tokens, so the protected resource cannot reject a client that paused past its lease, and Kleppmann argues that timing failures can violate its safety assumptions; Sanfilippo disputes parts of that timing model. I would state the assumptions and still require the resource to reject stale effects. My practical answer: if the lock exists for efficiency, avoiding duplicate work that is harmless, a single Redis SET NX PX lock with compare-and-delete release is enough and Redlock adds little. If it exists for correctness, I would not rely on any lock alone: I would use ZooKeeper or etcd for the lease and pass a fencing token, the lock node's creation zxid or lock key's creation revision, to the resource, which rejects older tokens. And first I would try to avoid the lock entirely, with a single owner per partition or a database conditional write.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"A worker checks its lease before every write, but an old report still overwrites a new one. Walk me through the failure and the fix."
What a strong answer covers
  • A worker can pause after checking its lease, or its write can be delayed in transit
  • Expiry permits a replacement without stopping the old worker
  • Grants carry increasing tokens and storage atomically checks the token with the write
  • After storage accepts 34, it rejects 33; granting 34 elsewhere alone does not update storage
  • Token and accepted-generation state must survive failover and every write path must enforce them
  • Equal-token retries and multiple writes need separate idempotency or operation ordering
How a senior would say it
I would fence writes at storage, because checking a lease in the worker leaves a gap before the effect. Worker A checks its lease and pauses. The lease expires, worker B takes over and writes a new report, and then A resumes and overwrites it. A delayed network request can cause the same failure even without a process pause. I would give each ownership grant an increasing token and include it in every write. Storage checks that token, updates its accepted generation and changes the report atomically. Once it has accepted token 34, it rejects A's token 33. There is an important boundary: merely granting 34 at the lock service does not update storage. If storage has only seen 32, it can still accept 33. B should install its generation before reading the state used to compute its report, or use an ownership check in the resource's transaction. The token allocator and storage's accepted generation must survive failover without going backwards, and every write path must enforce the check. Finally, fencing does not deduplicate two writes with the same token or order a holder's own operations. I would use operation ids or version checks for those requirements, and test both stale writes and delayed duplicate writes.

Likely follow up: Would rejecting equal tokens as well as smaller ones solve duplicate writes?

"Three schedulers send nightly invoices. Would you use Redis, ZooKeeper, or the database to make this safe?"
What a strong answer covers
  • Start with the invariant and use database uniqueness for one invoice per customer and period
  • Commit invoice creation and email publication intent in one transaction
  • A database claim alone cannot make an external email exactly once; downstream deduplication or an explicit tradeoff is required
  • Recover job ownership with an expiry and increasing attempt, checked transactionally with every effect
  • Redis can reduce harmless duplicate work; consensus coordination still needs resource enforcement
  • Describe deterministic crash, takeover and lost-acknowledgement tests
How a senior would say it
I would start with database invariants, since the invoices already live there. A unique customer and billing-period key prevents duplicate invoice records. The transaction that creates the invoice also inserts an email outbox row with a stable operation id. Sending the email is a separate boundary. Marking it sent before calling the provider can lose an email after a crash; marking it afterwards can duplicate an email after a lost reply. I need provider deduplication with that operation id, or an explicit decision to tolerate loss or duplication. For scheduler recovery, I would keep a job row with an expiry and an increasing attempt number. A replacement claims an expired run atomically. Each transaction that records progress or queues emails locks that job row and verifies the current attempt, so a resumed old worker cannot commit new effects after takeover. A Redis lease can reduce duplicate computation once those effects are safe. ZooKeeper or etcd can provide stronger coordination state, but neither automatically fences the database or email provider. I would test a paused worker across takeover, a crash after invoice commit, and a provider success whose acknowledgement is lost. That tells us which guarantees we actually have, rather than assuming that one scheduler means one effect.

Likely follow up: How would you recover a pending email if the provider has no idempotency support?

The practice problems drill expiry and conditional state transitions with an injectable clock. Their in-memory tests do not establish distributed failover guarantees.
