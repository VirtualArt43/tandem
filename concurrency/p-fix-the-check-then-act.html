Fix the cache that loads twice

Bug huntsmedium20 mindebugging round style

The cache in front of a slow service is the most common place to meet this bug in real code, and the fix interviewers expect is one line in Java. Knowing why that line works, and what it costs, is the senior part.

The incident

INC-4188: profile service overloaded at 9:00, and renamed users keep their old names

  • Every morning at 9:00, while the cache is cold, the profile service sees bursts of identical calls: up to 8 calls for the same popular user within 30 ms, from one app server. The profile team asked us to call them at most once per user.
  • Two users report that after renaming themselves, the site kept showing their old name until the next deploy. Both renamed themselves within a second of logging in, while their profile was still being fetched.
  • No errors anywhere. The unit tests, all single-threaded, pass.

The class is in your editor. Request threads call get to show a user's display name. The profile editor calls update after a user renames themselves. The profile service is passed in as a function and takes about 30 ms per call.

What the class must guarantee. The profile service is called at most once per user for the life of the cache, however many threads ask at the same moment; the others wait for that one call and get its answer. After update returns, every get returns the new name (or a newer one); a fetch that was already in flight must never bring the old name back.

What the tests check

  • One thread: a miss calls the service, a hit does not.
  • 8 threads ask for the same cold user at the same instant, for 5 users in turn: each user is fetched exactly once, and all 8 threads get the same name.
  • A rename during a slow fetch: the harness holds a fetch open, renames that user, then lets the fetch finish. Afterwards get must return the new name, and the user was fetched once.
  • A stress run: 8 threads, 40 users, reads mixed with renames. No user is fetched twice, and every user ends with their latest name.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Check then act: two safe calls, one unsafe sequence

Open them one at a time. Each one gives away a little more.

Read get as two steps: "is it there?" and "put it there". Another thread can do two different harmful things between them. What are they?
First, two threads can both see a miss and both call the service. Second, a fetch that started before update can finish after it and put the old name back. Both are the same mistake: the decision "it is missing" is stale by the time the code acts on it.
Make "look up, fetch, insert" one atomic step for each key. Java: ConcurrentHashMap.computeIfAbsent(userId, profileService) runs the function at most once per key and makes other callers for that key wait for it. C++: hold the mutex across the lookup, the fetch and the insert; the follow ups show how to stop that from blocking other users.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Your C++ fix calls a 30 ms service while holding the cache's only lock, so every other user waits. How do you avoid that?
Use single-flight: on a miss, put a placeholder in the map, a std::shared_future<std::string> from a std::promise this thread owns, then unlock and fetch. Threads that find the placeholder wait on the future without holding the lock, so different users fetch in parallel. When the fetch finishes, set the promise. update replaces the entry with a ready value, so a late fetch only completes its own promise and cannot overwrite the rename. The single-flight cache problem drills exactly this.
Does computeIfAbsent have any catch with a slow function?
Yes. While the function runs, ConcurrentHashMap holds a lock on that key's bin, so writes to other keys in the same bin wait too, and the function must never update the same map (recent JDKs throw IllegalStateException: Recursive update in some such cases; older ones could hang). For a 30 ms call it is acceptable and it is the expected interview fix; for slower calls, store a CompletableFuture in the map instead so the map lock is held only for an instant.
What if the profile service throws?
With computeIfAbsent the exception reaches the caller and nothing is cached, so the next get tries again. With futures in the map you must remove the failed future, or every later caller gets the cached failure forever. Caching failures on purpose (negative caching) is a separate decision, and it needs a short time to live.
Would making get and update synchronized be a correct fix?
Yes, it removes both races. But one 30 ms fetch then blocks every request for every user, so the cache turns into a single file queue in front of a slow service. It is the same trade-off as the C++ fix: correct and simple, but say its cost and offer the per-key version.
Why not fix it with putIfAbsent instead of put?
That fixes only the overwrite: a late fetch can no longer replace a newer name. Two threads that both miss still both call the service, so the 9:00 burst stays. You need both properties, one fetch per key and a fetch that never overwrites, and computeIfAbsent gives both.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The bug

get is a check then act: it checks "not cached", then acts on that answer after a slow call, by which time the answer may be wrong. The same window causes both symptoms in the incident.

A ConcurrentHashMap does not prevent either one. Each get and each put is thread-safe; the sequence of the two is not. That is the whole lesson of this problem.

The fix

Why each fix closes both races

  • Java. computeIfAbsent is atomic per key: the mapping function runs at most once, and other callers for that key block until it finishes and then read its result. An update for the same key during the fetch blocks on the same bin lock, so it lands after the fetched value and wins.
  • C++. With the lookup, the fetch and the insert under one mutex, no second thread can see the miss, and update cannot run until the fetch is in the map, so the rename is always the last write.
  • Declare the field as ConcurrentHashMap, not Map. Map.computeIfAbsent is a default method with no atomicity promise; only the ConcurrentHashMap version is atomic. The call dispatches to the right one either way, but the declared type should state the guarantee your code relies on.
  • The cost is different. Java blocks only callers of keys in the same bin; the C++ fix blocks every caller for 30 ms per miss. Correct first, then the single-flight upgrade from the follow ups, which keeps both guarantees and fetches different users in parallel.

How to say it in the debugging round

The get is check-then-act around a slow call: two threads can both see the miss and both fetch, and a fetch that started before a rename can finish after it and overwrite it. Thread-safe map operations do not help, because the race is between two of them. The fix is to make lookup, fetch and insert atomic per key: computeIfAbsent in Java, or the lock held across the fetch in C++, and if the fetch is slow I would switch to a future per key so other users are not blocked.
