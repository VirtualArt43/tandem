Objects, references and the heap

Variables hold references, not objects; Java passes references by value; aliasing creates shared state; and the boxing and Integer cache traps.

Asked atApple
Before this:How Java runs: JVM, bytecode, JIT and GC

Most shared state in a Java program is created by accident: two variables that point at the same object. Before you can find a race, you have to see the sharing, and in Java the sharing always travels as a reference.

In plain words

Think of houses and addresses. new builds a house. A variable does not hold the house; it holds a slip of paper with the house's address. Copying the variable copies the slip, not the house. Give a copy of the slip to a friend, and now two people can walk into the same house and move the same furniture.

If you and your friend both rearrange the living room at the same moment without talking, the result is a mess, even though each of you followed a sensible plan. That is a race, and the slip of paper is how it started. In Java, sharing an object means sharing its address, and every copy of the address is another way in.

Why this matters for concurrency

  • A thread can touch an object only if it has a reference to it. Handing a reference to a thread constructor, a lambda, a queue, an executor or a static field is exactly how objects become shared. Find the references and you have found the shared state.
  • Java passes references by value. A method or a task gets its own copy of the reference: it cannot change your variable, but it can change your object, and so can every other thread holding a copy.
  • A getter that returns an internal object hands out a key to your state. The caller can then read or change it without your lock.
  • Boxed numbers are objects. == compares references, the Integer cache makes that look right for small numbers only, and locking on a boxed value locks an object that may change on every update or be shared across the whole JVM.
  • Interviewers love the "what does this print" versions of these, and "Is Java pass by value?" is a classic Core Java screen question.

Objects live on the heap; variables hold references

Java has two kinds of types. The eight primitive types hold their value directly. Every other type, every class, interface, array, enum and record, is a reference type: a variable of that type holds a reference to an object on the heap, or the special value null.

new Account(100) does two things: it allocates an object on the heap and returns a reference to it. Account a = new Account(100); stores that reference in a. Arrays are objects too, even int[]: int[] counts = new int[8] puts one array object on the heap and one reference in counts.

Fields get default values (0, false, null) when the object is created. Local variables do not: the compiler refuses to let you read one before you assign it. Keep that difference in mind; it comes back when another thread sees a field before its constructor has finished.

Assignment copies the reference: aliasing

When you assign one reference variable to another, both now point to the same object. That is aliasing: one object, two names. Method calls work the same way. Java is always pass by value: the method gets a copy of each argument. For a primitive, that is a copy of the number. For an object, it is a copy of the reference, so the method sees the same object, but its parameter is its own variable.

mutate reached the caller's list through its copy of the reference. reassign pointed its own copy somewhere new, which the caller never sees. bump changed its own copy of a number. This is why a classic swap(a, b) method cannot work in Java, and why the honest answer to "is Java pass by reference?" is: no, Java passes everything by value, and for objects the value is a reference.

Every alias is a door for another thread

Threads follow exactly the same rules. A lambda captures a copy of each local reference it uses; a Thread constructor stores a reference to its Runnable; a queue stores references to its elements. Copies of a reference all lead to one object, so if that object is mutable, you have shared mutable state, even if every variable involved is a local.

tally is a local variable, and the lambda cannot reassign it (captured locals must be effectively final; more in lambdas). None of that protects the object. Thread confinement is a property of objects, not of variables. These are the usual ways a reference reaches another thread:

  • passed to a Thread, a lambda, a Runnable or a Callable;
  • stored in a static field, or in a field of an object that is itself shared;
  • put into a collection or queue that other threads read;
  • returned from a method of a shared object (a getter);
  • leaked as this from a constructor, before the object is finished (this escape).

Returning your insides

A lock protects state only while every access goes through it. A getter that returns an internal mutable object hands the caller a reference they can use later, outside your lock, from any thread.

itemsLeaky() is synchronized, but the lock covers only the moment of returning the reference. Afterwards, a caller iterating the list can race with later calls to add. itemsSnapshot() copies under the lock, so the caller gets an unmodifiable snapshot. This assumes non-null entries, as List.copyOf rejects nulls; its shallow copy is sufficient here because strings are immutable. Mutable elements would need their own copying or synchronization policy. You will meet copies, views and immutability properly in final, immutability and records.

null

null is a reference to no object. Using it as if it were one (calling a method, reading a field, unboxing it) throws NullPointerException. Since Java 15 the message names the exact variable or call that was null, which saves a lot of guessing.

Two places where null meets concurrency:

  • A field written by one thread may still read as null in another. If thread A assigns cache = new Cache() to a plain field and thread B reads cache, B may see null for a while, or forever, unless something creates a happens-before edge. Lazy initialization with if (instance == null) instance = new X(); is both a check then act race and a visibility problem; see double-checked locking.
  • ConcurrentHashMap refuses null keys and values. In a concurrent map, get(k) returning null must mean "absent". If null values were allowed, you would need a second call, containsKey(k), to tell "absent" from "present but null", and another thread could change the map between the two calls. Banning null removes the ambiguity. HashMap allows nulls because a single thread can make both calls safely.

Primitives, wrappers and autoboxing

Collections and generics hold objects, never primitives, so Java converts between them for you. Autoboxing turns an int into an Integer by calling Integer.valueOf; unboxing calls intValue(). The conversions are invisible in the source, and they carry three traps.

Trap 1: == compares references. On two Integer objects, == asks "same object?", not "same number?". To save memory, Integer.valueOf returns cached, shared objects for values from -128 to 127: the integer cache. So == appears to work for small numbers and fails for larger ones.

The cache range is guaranteed for -128 to 127; the upper bound can be raised with -XX:AutoBoxCacheMax, which is one more reason never to rely on ==. Long, Short, Byte and Character cache small values too; Double and Float do not. Compare boxed values with equals, or unbox them first.

Trap 2: unboxing null throws. int hits = map.get("home"); compiles, and throws NullPointerException when the key is missing, because get returned null and Java tried to call intValue() on it. Use getOrDefault, or better in shared code, merge and compute, which handle "absent" for you.

Trap 3: boxing allocates. Long total = 0L; for (...) total += x; creates a new Long on most iterations. In a hot path, especially a counter that many threads hit, that is pure garbage-collector pressure. Prefer primitives, AtomicLong or LongAdder for counters.

Never lock on a boxed value or a string literal

synchronized (x) locks the object that x refers to right now. Boxed values are immutable: count += 1 on an Integer unboxes, adds, obtains a wrapper for the new value and moves the reference. That wrapper may be cached rather than newly allocated, but it is still a different object from the wrapper for the old value. A lock on count therefore changes with the count.

The output is usually well short of 200,000. Since Java 16, javac warns about this (attempt to synchronize on an instance of a value-based class), but it looks only at the declared type of the expression. Two related traps get no warning at all:

  • synchronized ("lock"): string literals are interned, so every class in the JVM that writes the same literal locks the same object, including library code you have never read. String is not a value-based class, so javac stays silent.
  • A cached object reached through a variable declared as Object, for example Object lock = Boolean.TRUE; or a small Integer: the object is shared by everyone in the JVM, and javac does not see a value-based type to warn about.

The fix is always the same: lock on a dedicated object that never changes and that nobody else can reach, private final Object lock = new Object();. For a counter, drop the lock and use an AtomicInteger or a LongAdder.

Reads of long and double can tear

One more reference-level rule from the Java Language Specification. Reads and writes of references, and of every primitive except long and double, are always atomic: you see the whole old value or the whole new one. Plain long and double fields are the exception: the language allows a write to be split into two 32-bit halves, so an unsynchronized reader could see a torn read, half of each. 64-bit JVMs do not split them in practice, but the specification allows it, and volatile long and volatile double are always atomic. In shared code you will want volatile, an AtomicLong or a lock anyway, for visibility and for compound updates.

Worked example: the price book that handed out its insides

A service records prices per item, and a reporting thread sums them. The class looks thread-safe: every method is synchronized.

Trace the references when a writer thread keeps calling record("tea", ...) while the reporter runs for (int p : book.pricesOf("tea")) sum += p;:

  1. The reporter calls pricesOf, takes the lock, receives a reference to the internal ArrayList, and releases the lock.
  2. The reporter now iterates that list with no lock. It is an alias of the book's private state.
  3. The writer takes the lock and calls add on the same ArrayList. The lock excludes other PriceBook methods, but the reporter is not inside one.
  4. The reporter's iterator notices the change and throws ConcurrentModificationException, or, worse, reads the list in the middle of a resize and sees stale or missing elements. It can even see a slot whose element is not visible to it yet, and unboxing that null throws NullPointerException.

The fix is to never let the alias out:

The copy costs O(n) under the lock. If readers far outnumber writers, store an immutable list per item and replace it on every write, so readers can share it without copying. Obtaining and replacing those references still needs synchronization, such as the existing synchronized methods. That is copy-on-write, coming in copy-on-write and immutable snapshots. The rule is: every conflicting access to state guarded by a lock must follow the same locking discipline. Returning an alias is unsafe when it lets callers bypass that discipline.

Common mistakes

  • "It is a local variable, so it is thread-safe." The variable is; the object it points to is shared as soon as another thread gets a copy of the reference.
  • Comparing boxed numbers or strings with ==. It compares identity. Use equals, or compare primitives.
  • Locking on a boxed value, a string literal, or a field that gets reassigned. Each makes threads lock different objects, or the same object as unrelated code. Lock on a private final Object.
  • Returning internal mutable state from a synchronized getter. The lock ends when the method returns; the alias lives on. Return a copy or an immutable object.
  • Unboxing a missing map value. int n = map.get(k) throws when k is absent. Use getOrDefault, merge or compute.
  • Expecting a method to change the caller's variable. It can change the caller's object, never the caller's variable.

In the interview

Expect this as quick code reading in a screen ("what does this print?" with Integer and ==, or a swap method), as "is Java pass by value or by reference?", and inside concurrency questions as "which of these objects are shared?" or "why is synchronized (count) wrong here?".

Java is always pass by value. For an object, the value that gets copied is the reference, so the method sees the same object and can change it, but it cannot make the caller's variable point somewhere else. For threads that means every reference I hand out, to a task, a queue or a field, is another way into that object, so the object is shared state.
Locking on an Integer counter field is broken: the wrapper is immutable, so an increment repoints the field to a different wrapper and the next thread can lock a different object. I would use a private final lock object, or an AtomicInteger for a counter.

Follow ups to expect: "Why does 127 == 127 print true but 128 == 128 false?" (the Integer cache), "Why does ConcurrentHashMap reject null?" (absent versus null would need two calls, and the map can change between them), and "Is a long write atomic?" (not guaranteed unless volatile).

Senior depth

  • Value-based classes. Integer, Long, Optional and the java.time classes are documented as value-based: you are told not to rely on their identity, so ==, synchronized and System.identityHashCode on them are bugs waiting to happen. The javac warning on synchronizing on them comes from this rule.
  • Boxing costs memory and cache misses. On a typical 64-bit JVM with compressed references, an Integer object takes about 16 bytes and the reference to it 4, against 4 bytes for an int (orders of magnitude, not guarantees). A List<Integer> of ten million distinct values costs roughly five times an int[], and every read chases a pointer.
  • Per-element atomics. An AtomicInteger[] is an array of references to separate objects. AtomicIntegerArray keeps the values in one array and gives each element atomic operations, with far less memory and indirection.
  • Escape analysis may remove boxes and locks inside one compiled method, but only when no other thread could tell the difference, so it never changes what your program means. Code must be correct without it.

Key takeaways

  • Variables of object type hold references; objects live on the heap.
  • Java is always pass by value; for objects, the value is the reference.
  • Every copy of a reference, in a lambda, a queue, a field or a return value, is a way for another thread to reach the object.
  • All conflicting accesses to guarded state must use the same locking discipline; an escaped mutable alias can bypass it.
  • Compare boxed values with equals; the Integer cache makes == work only by accident.
  • Never lock on boxed values, string literals or reassigned fields; use a private final Object.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
"Is Java pass by value or pass by reference?" Answer, then explain what your answer means for an object you hand to another thread.
Model answer

Java is always pass by value. For primitives the value is the number. For objects the value is the reference, so the method receives a copy of the reference that points at the same object. That is why a method can change the caller's object, for example list.add(x), but cannot change the caller's variable: assigning a new object to the parameter only repoints the method's copy, which is also why a swap(a, b) method cannot work in Java.

For threads it means that handing an object to a thread, a lambda, a queue or an executor hands out another copy of its reference. Every copy leads to the same object, so if it is mutable, it is now shared state and needs a lock, atomics, immutability, or a clean hand-off where the sender stops touching it. Confinement belongs to objects, not to variables.

Debug
A job tracker uses private Long completed = 0L; and void done() { synchronized (completed) { completed += 1; } }. Under load the count comes out low, and a code reviewer also noticed synchronized ("jobs") elsewhere in the same service. Explain both problems and fix them.
Model answer

completed is a boxed Long, which is immutable. completed += 1 unboxes, adds, obtains a wrapper for the next value and repoints the field, so each thread locks whatever object the field held when it arrived. Two threads can hold two different "locks" at once, read the same value, and lose an update. Small values are also cached and shared JVM-wide, so unrelated code might contend on the same object. javac even warns about synchronizing on a value-based class.

synchronized ("jobs") locks an interned string literal, which every class in the JVM using the same literal shares, including libraries, so it can cause surprise contention or even deadlock with code you have never seen.

Fixes: for the counter, drop the lock and use private final AtomicLong completed = new AtomicLong(); with completed.incrementAndGet(), or a LongAdder if many threads hit it. For anything that needs a real critical section, use private final Object lock = new Object(); and synchronized (lock). A dedicated, private, final lock object can never change and nobody outside the class can lock it.

Numbers
Roughly how much heap do ten million distinct Integer values in an ArrayList<Integer> take, compared with an int[] of the same length? Give orders of magnitude and say why it matters for a concurrent service.
Model answer

An int[] of ten million is about 40 MB: 4 bytes per element. An ArrayList<Integer> holds a backing array of references, about 4 bytes each with compressed references, so about 40 MB (more if the array has spare capacity), plus one Integer object per distinct value, about 16 bytes each, so about 160 MB. In total roughly 200 MB, about five times the primitive array. These are orders of magnitude on a typical 64-bit JVM, not guarantees.

It matters because every allocated object is work for the garbage collector, and more GC work means more and longer pauses that stop every thread at once. Boxing in a hot path, such as a per-request counter in a Map<String, Integer>, multiplies allocation. Prefer primitive arrays, AtomicIntegerArray, LongAdder or primitive-specialized structures on hot paths.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Java passes objects by value, so each worker gets its own copy, right? Explain what actually happens when I pass a list to two tasks."
What a strong answer covers
  • Java passes the reference value, so both tasks can reach the same list object
  • Mutating through the parameter affects that object; reassigning the parameter does not reassign the caller's variable
  • Local and effectively final references do not make their targets confined or immutable
  • Each invocation has private locals, but concurrent list mutations need synchronization
  • Choose a concurrent collection, one shared lock, immutable input or separate task results
  • A shallow list copy separates the list structure but can still share mutable elements
How a senior would say it
Each worker gets a copy of the reference, not a copy of the list. Java always passes values, and for an object argument that value identifies the same object the caller already uses. If a method adds an element through its parameter, the caller sees the changed list. If the method assigns a new list to that parameter, only the method's local variable changes. Passing the reference to two tasks creates the same kind of aliasing. The fact that the original variable is local, final or effectively final does not make the list private or immutable. Each invocation has its own local variables, but both can call add on one shared ArrayList, which needs protection. I would choose a concurrent collection or one common lock if the tasks must share updates. If they only need input, I would safely create an immutable snapshot. Another option is separate task results that the caller merges after completion. I would also inspect the elements: copying a list copies its element references, so two separate lists can still share the same mutable objects.

Likely follow up: What changes if the list is final but contains mutable account objects?

Out loudabout 75 s
"Our counter uses synchronized (pending) where pending is an Integer. Every increment is inside the block. Why can updates still disappear?"
What a strong answer covers
  • Synchronized locks the referenced object, while incrementing an Integer rebinds the field
  • One thread can wait on the old wrapper while another starts using the next wrapper as its lock
  • Different monitors allow both increments to read the same value and lose an update
  • Cached wrappers can also be shared with unrelated code; avoid them and interned strings as locks
  • Use a private final lock with a primitive counter, or an atomic increment for a standalone counter
  • Protect reads too, and retain a common lock when the invariant spans additional fields
How a senior would say it
The monitor changes when the counter changes. Synchronized locks the object referenced at entry. An Integer cannot be modified, so incrementing it unboxes the number, adds one, boxes the result and reassigns the field to another wrapper. Imagine thread A locks the wrapper for zero while thread B waits for that same wrapper. A stores a reference to the wrapper for one and unlocks. B can now enter holding the old wrapper, while A starts its next increment holding the new wrapper. Both can read one and write two, losing an update despite both being inside a synchronized block. Cached wrappers add another problem: unrelated code can hold the same monitor. Interned strings have that sharing risk too. I would use a private final lock object with a primitive counter, and take that same lock for reads and writes. For a standalone counter, an AtomicInteger with incrementAndGet is simpler. If the count must stay consistent with another field, I would keep one lock around the whole invariant. Making the wrapper field volatile would not fix the changing monitor or the compound increment.

Likely follow up: Would using a final Integer as the lock solve the problem of sharing that monitor with unrelated code?

Out loudabout 75 s
"Every method in this price book is synchronized, but its getter returns the internal list. Is the reporting thread safe when it iterates that result?"
What a strong answer covers
  • The getter releases its monitor on return, while the returned alias still reaches the internal mutable list
  • A later writer can modify the list during the caller's unlocked iteration
  • ConcurrentModificationException is only a possible symptom, not a synchronization guarantee
  • Copy the list while holding the same lock used by writers; an unmodifiable view still shares the original
  • List.copyOf is sufficient for immutable Integer elements but not for mutable element state
  • Copying costs linear time under the lock; immutable replacement shifts copying to writers but still needs safe publication
How a senior would say it
No. The getter protects the act of returning the reference, but it releases the lock before the reporting thread iterates. That reference still reaches the book's internal mutable list. A writer can then hold the book's lock and change the list while the reporter reads it without that lock. The reporter might get ConcurrentModificationException, but that exception is not guaranteed and cannot serve as synchronization. I would create the snapshot while holding the same monitor as the writers, then return the copy. Simply returning an unmodifiable view is insufficient because it still reflects the original list's mutations. Here, List.copyOf gives an unmodifiable snapshot, and the Integer elements are themselves immutable, so sharing those element references is fine. If the elements were mutable price records, I would need immutable value objects, deeper copies, or separate synchronization for their state. Copying costs linear time while holding the lock. If reads dominate, I might instead publish immutable lists and copy on writes. The replacement reference still needs safe publication, and concurrent writers still need a coordinated update. The goal is a stable snapshot with an explicit sharing rule.

Likely follow up: How would you safely obtain the snapshot if the caller, rather than the price book, owns and concurrently mutates the input list?
