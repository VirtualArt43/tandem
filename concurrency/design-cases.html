Design cases: seats, flash sales, schedulers and counters

Work through seats, hotel nights, flash sales, schedulers, counters, leaderboards, caches and auctions, including concurrency invariants, retries and recovery.

Asked atMetaAmazonRipplingFlipkartUberRubrikSalesforceSwiggyConfluentLinkedIn
Before this:Optimistic versus pessimistic concurrency controlIdempotency, retries and exactly-once effectsDistributed locks, leases and fencing tokensOrdering by ownership: partitions and single writers

Design rounds rarely say "concurrency". They say "two people tap Book on the same seat", "the sale opens at noon", "run this once a night", "count likes on a post that goes viral". This lesson works the cases that keep coming up, end to end, with the tools from this module.

In plain words

A theatre box office has a paper seat map. When you point at seat A12, the clerk pencils your name in and says "it's yours for ten minutes while you fetch your wallet". If you are back in time, the pencil becomes ink. If not, the pencil mark simply stops counting, and the next person can have the seat. Two clerks must never ink the same seat, so there is one map and one pencil per seat.

Every case below extends that picture: many requests change shared state, and one place decides which transitions are valid. A seat needs a hold, a counter needs an indivisible update, and a leaderboard needs its scores and ordering to agree.

One method for every case

  1. Name the scarce resource and the invariant. "A seat is sold at most once." "Stock never goes below zero." "A job's effect happens once." Say it out loud; everything else serves it.
  2. Find the contention point and its rate. Which row or key do concurrent requests fight over, and how many times a second? Measure skew: even one seat can attract thousands of contenders at release time.
  3. Choose one arbiter. A conditional write or constraint in the database, an atomic operation in a store such as Redis, or a single owner per key. Never "check here, write there".
  4. Cover time and failure. Holds with expiry for human think time, idempotency keys for retries, leases and fencing for workers, reconciliation for anything that crosses systems.
  5. Scale the hot spot. Split it, batch it, queue in front of it, or admit fewer people to it.

Every case has a shared invariant, whether allocation, uniqueness or agreement between structures, and the interviewer wants the race named, reproduced and closed atomically. In the SQL below, :name marks a bound parameter.

Case 1: Seat booking with holds and expiry

Invariant: a seat is sold to at most one person; a hold lasts ten minutes; only the holder can buy, and only while the hold is live. Contention: per seat, with potentially extreme contention for popular seats.

Expiry is lazy. A lapsed hold is free in the condition, so a failed sweeper cannot strand seats. These are transaction templates: the application must branch on affected rows, never commit a partial group, and lock all group confirmations in the same immutable seat order too. Every path touching several rows must follow that order; other resources can still introduce deadlocks, so retry aborted transactions.

Read time after acquiring the seat locks. PostgreSQL's now() is fixed at transaction start, whereas clock_timestamp() reads current wall time; a transaction that waited for a lock must not confirm using its old start time. Define expiry at the locked decision, not at the later response or commit. Use one database clock and account for clock adjustments; no transaction stays open during user think time. See PostgreSQL's time-function semantics.

A hold needs an identity, not just a user. A delayed confirm from the same user's old checkout must not consume their new hold. Use a fresh hold_id for each acquisition and reuse that id only for retries of that acquisition. On a duplicate Hold, return its recorded result without extending expiry; a row read-back counts as current success only when user, hold id, held status and live expiry all match. Retain completed operation results so a retry after a successful confirm returns the same order instead of incorrectly voiding its payment.

The subtle failure is the hold that lapses while the payment is in flight:

The safe order is: authorize the payment (reserve the money), confirm the seat with the conditional update, then capture; if the confirm changes 0 rows and the recorded result shows no prior success, void the authorization. Use operation-specific payment idempotency keys, such as hold id plus authorize or capture, and record the booking result atomically with the ticket and an outbox entry for capture. On an unknown confirmation outcome, look up that result before voiding or retrying. A crash after booking but before capture is recovered by retrying the durable outbox operation. A terminal capture failure requires an explicit cancellation or refund policy; reconcile provider status before releasing a seat whose charge may have succeeded. A bounded checkout extension can reduce expiry races without hiding them.

For a hot release, add a virtual waiting room that admits users at the rate the seat map can absorb, serve the seat map from a cache (it may show a seat as free a second too long, and the conditional update corrects that), and keep the write path per seat. A Redis SET seat:show9:A12 :token NX PX 600000 can be an admission aid. A unique ticket constraint prevents duplicate sales, but alone does not enforce the current holder's rights after Redis expiry or failover: keep authoritative hold identity and confirmation together in the database, or specify a storage-enforced fencing protocol.

In a low level design round, the same state machine lives in memory. A per-key atomic update is enough:

Use a thread-safe, nondecreasing clock measuring milliseconds from a process-local origin, backed by System.nanoTime() or std::chrono::steady_clock, and non-null ids. It must be quick and must not re-enter this object. These fragments implement single acquisitions; API retry-result storage is an additional layer. Injecting time lets you test the expiry boundary and an old hold id after reacquisition without sleeping. The practice problem adds release, group holds and a stress harness.

The date-range variant: hotel nights

Booking a hotel room for three nights is the seat problem across several rows, and it appears repeatedly in Rippling reports. "Check that every night has a room, then insert the booking" is write skew: two bookings can each see a free room on every night and both insert. Keep one inventory row per hotel, room type and night, and reserve all the nights in one transaction:

Pre-create every inventory night under a unique (hotel_id, room_type, night) key and reject empty date ranges; a missing row is not spare capacity. Aggregate room-type capacity assumes rooms are interchangeable: if the guest must keep one physical room for the entire stay, allocate a consistent room id across nights or explicitly support room reassignment. The follow ups are the module in miniature: a duplicate submit (the reservation id under a primary key), a user who leaves checkout (a hold with expiry), and rooms also sold through other channels (one authoritative inventory allocator or disjoint channel quotas for strict no-oversell; reconciliation alone only detects an overbooking afterwards).

Case 2: Flash sale inventory

Invariant: never sell more than the stock (no oversell), and do not strand stock in abandoned carts (no undersell). Contention: extreme, all on one item, all in the first seconds.

The correct single-row answer is the conditional decrement from the optimistic and pessimistic lesson: UPDATE items SET stock = stock - 1 WHERE id = :item AND stock > 0, then check the row count. Its limit is physics: every buyer queues for one row lock. As an order of magnitude, if a purchase transaction holds that lock for about a millisecond, the row tops out near a thousand purchases a second, however many servers you add.

The ways past one row:

  • Split the stock into K rows (or K counters) and let each buyer try a random one, moving on when it is empty. With balanced requests and available stock, each row sees roughly 1/K of the traffic; empty-bucket retries and skew change that.
  • Gate in front: an atomic counter in memory or in Redis (a Lua script that checks and decrements) admits at most the allocated units before refill, rejecting excess work without touching the order database. A gate bounds demand; it does not increase that database row's write capacity. Retries must reuse a reservation token instead of consuming another permit. Orders are then created asynchronously with idempotency keys and reconciled with the database, because the gate and the database cannot commit together.
  • One row per unit, claimed with FOR UPDATE SKIP LOCKED, so buyers grab different units instead of queueing on one counter. Skipping locked rows reduces waiting, but no returned row can mean every available unit is temporarily locked, not permanently sold out; retry or report temporary unavailability.
  • Admit fewer: a waiting room, and a per-user limit enforced by a unique (user_id, sale_id) key.

Here is the split stock in memory. Each bucket is an atomic counter decremented only while positive, so no bucket ever goes below zero, and a buyer reports "sold out" only after seeing every bucket empty, which is final because stock never grows during the sale.

The output is the same on every run, which is the point: whatever the interleaving, exactly 1,000 units sell. The tempting shortcut, if (stock.get() > 0) stock.decrementAndGet();, is a check-then-act that oversells under exactly this load. The C++ buckets are aligned to 64 bytes to reduce false sharing on machines with 64-byte cache lines; this is not a portable hardware guarantee (some machines use larger lines). Java's AtomicIntegerArray packs counters together, which is fine for a demo and worth a sentence in an interview.

The C++ start gate uses C++20 std::latch; a mutex, condition variable and boolean predicate provide the C++17 fallback. Constructor inputs require nonnegative units and a positive shard count. remaining() is exact after the buyers join; during purchases it is not an atomic snapshot. Undersell is the other half. Units reserved for carts that are abandoned must come back: give each reservation an expiry, then atomically transition it from held to released exactly once while restoring stock. Confirmation and expiry must compete on the same reservation state. With explicit counters, lazy expiry must still reclaim the counter; simply ignoring the expired row leaks stock. When stock can increase, scanning buckets individually cannot prove a single instant when all were empty, so report temporary unavailability or coordinate a consistent exhaustion check. "Avoiding both overselling and underselling" was the stated goal in a Flipkart flash sale design report.

Case 3: A distributed scheduler with idempotent effects

Invariant, honestly stated: each completed logical job occurrence has one externally visible effect, provided the downstream operation supports atomic deduplication. Execution itself cannot be exactly once, because a worker can run a job, pause, and lose its lease mid-way (the paused holder). So the design is at-least-once claiming, fenced writes and idempotent effects.

These are short transactions; the explicit row locks make heartbeat and finish expiry checks occur after waiting, as with seats. Initialize attempt to zero, and use a type whose range covers the job's lifetime. Job-table fencing protects only that row: a shared external resource needs its own storage-enforced token, scoped to that resource. The job's side effects carry an idempotency key built from the job id (and its scheduled time for recurring jobs), so if a paused worker and its replacement both run the job, the downstream system applies the effect once. Only a successful fenced finish inserts a recurring job's next occurrence in the same transaction, under a unique key on (job_name, scheduled_for), so two nodes computing "the next run" cannot create it twice. Inside one process the same shape is the delayed scheduler from scheduled executors and the dependency runner from the job runner lesson; across machines, the database supplies the claim queue. Add retry backoff, an attempt limit and an inspectable failed-job state for permanent failures. Without downstream idempotency or a shared transaction, choose between possible duplicate effects and possible lost effects; fencing alone does not deliver exactly-once effects.

Case 4: Counters at scale: likes

A like counter hides two different problems. Uniqueness: one like per user per post, even when the client retries. Counting: a viral post receives likes faster than one row can absorb.

The other common answer buffers likes in memory on each application server and flushes one delta per post per second, turning a thousand row updates into one. It is counters at scale applied to a database:

Atomic drain is only an in-process guarantee. AtomicLong.getAndSet(0) and C++ exchange(0) assign each increment to one drain, assuming counters do not overflow. Java's LongAdder.sumThenReset() does not promise an atomic interval boundary during concurrent updates, so this example uses AtomicLong; see the Java 21 contract. Only one flusher runs, entries are never removed, and their lifetime covers the flush. Removing idle entries requires coordinating with updaters holding old references.

A callback exception restores the drained amount, but a timeout may mean the database already applied it, so retries can double count. A process crash can lose all unflushed memory. Feed the buffer only after a unique like insertion; unlike contributes a negative delta. This is an approximate display counter, repaired from a consistent snapshot of the authoritative likes table. Exact accounting instead commits a durable outbox event with each like, and stores each flush batch id atomically with its delta. A recount must define a snapshot boundary so concurrent events are not both included and reapplied.

At larger scale, one aggregator owns each post's count in a partitioned stream (ordering by ownership). An absolute count keyed by post and time window is retry-safe only if the same finalized value is replayed, or the sink also conditionally checks a version. Otherwise an older retry can overwrite a newer total.

Case 5: Leaderboard

Operations: add to a player's score (or keep their best), read the top K, read one player's rank. Invariant: the ranking always agrees with the scores. In a store, a Redis sorted set supports these individual operations atomically; Redis runs commands one at a time, so each command is a single owner's atomic step:

Each Redis command is atomic, but a sequence of commands is not one snapshot. ZINCRBY also repeats on a client retry, so deduplicate score-event ids when required. Scores use floating-point storage; exact integer scores must stay within its exact-integer range. Redis reverse ranges break score ties by reverse lexicographic member order, whereas the local example below deliberately uses ascending player id. See the sorted-set score and ordering contract.

In a low level design round you build it, and the trap is the two structures: a map from player to score and an ordered set of (score, player). An update must remove the old entry and insert the new one together, or a reader sees the player missing (between the two steps) and two concurrent updates leave duplicate entries and a lost increment. One lock for both structures, read-shared:

These fragments assume representable score sums and successful allocation; a production implementation also needs an exception-safe rollback strategy for updates spanning two allocating containers. Updates take O(log N), top K takes O(K), and ties use player id. Neither TreeSet nor std::set provides logarithmic rank: scanning is O(N); use a tree augmented with subtree sizes for O(log N) rank. A read-write lock can help when reads dominate, but benchmark its overhead and fairness. When score updates pour in, another design is one writer for the entire board (a keyed executor was one Uber candidate's proposal; its key must identify the board, not each player) that applies updates and periodically publishes an immutable snapshot of the top K for readers, the copy-on-write pattern.

Case 6: A cache or key-value store on one machine

"Design memcache on one machine with 32 cores and 256 GB of memory" sounds like a capacity question. It is a locking question. A Meta E6 candidate reported that what the interviewer praised was sharding the hash table into roughly one part per core "to be able to lock more efficiently"; a Meta recruiter note for the single-node design round said it could cover concurrency and multithreading; and an Uber SDE2 candidate who designed a single-node in-memory cache (LRU, TTL, a write ahead log) concluded afterwards that the round should have stayed on locking strategies and read-write contention, not distributed theory.

The senior move is to say the numbers out loud: on typical storage, a durable flush can be orders of magnitude slower than a memory write, although its cost is hardware and workload dependent, so batching turns thousands of small fsync calls into a few large ones, and one lock per core shard lets the cores work in parallel except on the same shard. It exposes parallelism; it does not guarantee full utilization. Measure hot-key skew, allocator contention, memory bandwidth, queueing and I/O. Keep each key's log order consistent with its applied mutation order, and never wait under a shard lock for a log writer that needs that lock; snapshots need a known log boundary.

Case 7: An auction with a contended highest bid

Invariant: the recorded high bid only goes up, a bid is accepted only if it beats the current high bid, and no bid is accepted after the auction closes. Auction bidding appears in an aggregated list of Meta product architecture questions and in a self-reported community database of Meta questions (where one candidate proposed Redlock and the follow up was a celebrity's hot auction), so treat the attribution as a lead rather than a confirmed first-hand report. Contention: every bid on one auction targets one value, and the last seconds of a popular auction are a flash sale in reverse.

In memory the same rule is one compare-and-swap on an immutable record, and the important detail is that closing goes through the same atomic state. A separate closed flag checked before the CAS would be a check-then-act: a bid could pass the check, the auction could close and pick a winner, and the bid could still land.

The C++ version uses a mutex because the state holds a std::string: std::atomic<State> needs a trivially copyable type, and std::atomic<std::shared_ptr<T>> is C++20 but missing from some standard libraries, including the Apple libc++ that builds Tandem's code.

Scaling a hot auction uses the monotonic invariant. For one auction generation with no bid retractions or failover rollback, the true committed high bid only grows, so a stale cached high bid is a safe filter: any bid at or below the cached value is certainly losing and can be rejected at the edge without touching the arbiter, and only bids above it go through. Beyond that, give each auction a single owner (partition bids by auction id) that applies them in order, log every bid for audit and disputes, and decide the close by the arbiter's clock, not the bidders'. If someone proposes a distributed lock around the auction, ask what happens when the lock holder pauses past its lease: the database conditional update takes a row lock internally and atomically checks the auction state, avoiding a separate distributed lock service. For a scheduled deadline, first lock the row and check database time against closes_at; an explicit close call alone does not enforce a wall-clock deadline. Persist bid ids and their original outcomes to make client retries idempotent.

Worked example: sizing the flash sale

5,000 units, and 100,000 people press Buy within the first ten seconds.

One row. At roughly a millisecond of lock time per purchase (an order of magnitude, not a benchmark), one row sells about 1,000 units a second, so the 5,000 units take about five seconds while excess requests risk a large queue. Whether they time out depends on arrival shape, rejection cost and deadlines; this is a capacity estimate, not a measured result.

A gate in front. An atomic counter (in memory per instance with a fixed allocation each, or one Redis key with a check-and-decrement script) admits at most 5,000 distinct reservations before refill; remaining callers get a fast unavailable response. During this first wave, assume no failures or cancellations. A depleted gate can mean temporarily reserved, not permanently sold. The 5,000 admitted requests create orders through a queue with idempotency keys.

The database stays the truth. Stock is split into, say, 20 rows of 250, so the admitted orders decrement in parallel at an idealized upper bound of 20,000 a second if row locks are the only bottleneck. Shared logging, CPU and storage can lower that bound. Unpaid reservations expire after ten minutes; release them once in the database and propagate an idempotent release event to the gate. Allocate disjoint per-instance quotas durably so restarts cannot recreate spent permits. A reconciliation job compares the gate's count with the database's, because they cannot commit together.

Common mistakes

  • Holding a database lock for the user's think time. Use a committed hold with an expiry instead of an open FOR UPDATE.
  • Expiring holds only with a sweeper. If the sweeper stops, seats stay stuck. Treat an expired hold as free in the condition itself.
  • Confirming without checking the hold is still yours and still live. That is how a lapsed hold sells one seat twice.
  • Using app server clocks for expiry. Use one clock, the database's.
  • A Redis gate as the only truth. It cannot commit with the database; keep a database constraint as the final arbiter and reconcile.
  • "Exactly-once job execution". Promise one logical effect only where an atomic idempotency contract supports it; fence stale writes and state the downstream limitation.
  • Counting likes without uniqueness. A retried like counts twice unless the insert is guarded by a primary key.
  • Two structures, two steps, no lock. A leaderboard's map and sorted set must change together.

In the interview

These prompts usually arrive as ordinary product designs, and the concurrency part is where senior candidates are separated. Meta's ticket booking rounds were described as "really deep dives into concurrency control and race condition resolutions", one Meta candidate believed that missing the one specific mitigation the interviewer wanted for a high-contention question was fatal, and a Flipkart candidate's seat locking approach was judged weak. Lead with the invariant and the arbiter, then volunteer the failure cases before you are asked.

The invariant is one ticket per seat. The arbiter is the database: a hold is a conditional update that treats an expired hold as free, and confirmation is a conditional update that checks the hold is mine and still live, with a unique index on tickets as the backstop. I would authorize payment, confirm the seat, then capture, voiding the authorization if the confirm finds the hold lapsed.
For the flash sale, if measurements show one millisecond of serialized lock time, one row has an ideal ceiling near a thousand purchases a second, so I would put an atomic gate in front that admits at most its allocated stock and turns everyone else away fast, split the stock across rows, expire unpaid reservations so we do not undersell, and reconcile the gate with the database.

Follow ups to expect: "What if the hold expires during payment?", "How do you release seats from abandoned checkouts?", "What if the Redis gate and the database disagree?", "Can your scheduler run a job twice?" (yes, so the effects are idempotent and the writes are fenced), "How do you count likes for a celebrity's post?", and "How would the leaderboard work across shards?" (with one shard per player, merge each shard's top K under the same tie order; exact global top K or rank needs a consistent snapshot, and rank needs counts strictly ahead of the player, including ties).

Senior depth

Pick consistency per field, not per system. Seat ownership and stock need strong consistency at one arbiter. The seat map display, like counts and leaderboard pages can be seconds stale. Saying which is which, and why, is the clearest senior signal in these rounds.

Every gate needs a way back. Holds, reservations and admitted-but-unpaid orders are all leases on inventory. Each needs an expiry, a single clock, and a path back to the pool, or the system slowly leaks stock until a sale "sells out" with units still on the shelf.

Cross-system steps need sagas and reconciliation. Payment provider plus seat database, Redis gate plus order database, hotel plus external channels: none can commit together. Design each step to be idempotent and compensable (void, refund, release), and run a reconciler, because some failure will always land between two steps.

Key takeaways

  • Name the shared invariant, pick an arbiter and make the entire state transition atomic.
  • Holds are committed rows with an expiry that counts as free when lapsed; confirm only a live hold you own; keep a unique constraint as the backstop.
  • A hot row caps throughput; split the stock, gate in front, or claim one row per unit with SKIP LOCKED, and expire reservations to avoid underselling.
  • Schedulers retry execution; one logical effect needs downstream idempotency or a shared transaction, alongside lease claims and fenced completion.
  • Counters separate uniqueness (a primary key) from counting (sharded rows, buffered deltas, or one owner per key); leaderboards change both structures under one lock or one writer.
  • On one machine, shard by core with a lock and an LRU per shard, and batch log fsyncs with group commit; in an auction, bids and the close go through one atomic state.

Quick check

Answer each question, then read why. Your score is saved for your module test.

For one auction with no retractions or rollback, edge servers cache only committed high bids, refreshed every second, and reject any incoming bid at or below the cached value without contacting the arbiter. Is that safe?
Why. Staleness only ever makes the cached value lower than the truth, which means the filter rejects only bids that are certainly losing. The decision for every bid that might win still happens atomically at the arbiter. The same reasoning fails for a value that can go down, such as stock that can be returned.
A user's seat hold lapses while their payment is still processing, and another user holds the seat. Which approach avoids holding a database lock across payment and rejects A's expired hold before capture, assuming no previous confirm succeeded?
Why. The confirm checks the exact hold id, user and live expiry. Authorization reserves funds; capture is attempted only after a durable booking. A lost hold requires voiding the authorization. Longer holds cannot eliminate slow calls, and holding a row lock during payment violates the stated requirement. Charging first needs a compensating refund. Capture failures and unknown outcomes still need the durable workflow described above.
A flash sale item's stock is one row, and each purchase transaction holds its row lock for about 2 ms. Roughly how many purchases per second can that row handle, and what helps most?
Why. Purchases on one row are serialized by its lock: 1 / 0.002 s is about 500 a second whatever the number of servers. Optimistic locking does not raise the ceiling, it adds failed retries. Splitting stock across rows can add parallel write capacity. An admission gate reduces overload but leaves the single row's service ceiling unchanged.
In the sharded stock code, tryTake returns false only after it has seen every bucket at zero. Why is it safe to report "sold out" then, even though other threads are still running?
Why. The argument is monotonicity: counts only go down, so once every bucket has been observed empty, no unit can appear later. If returns or expired reservations could add stock back during the sale, the sold-out answer would need a different rule.
A like service runs UPDATE posts SET likes = likes + 1 WHERE id = :post for every like request. Clients retry on timeouts; assume no unlikes. What is the best fix for the double counting?
Why. For repeated likes without an intervening unlike, the duplicate comes from retries, so the fix is uniqueness: the insert either creates the like once or does nothing. Serializable isolation does not know a retry is a duplicate, and Redis INCR repeats on retry just the same.
A scheduler worker paused past its lease; the reaper requeued the job and another worker finished it as attempt 2. The first worker wakes and runs UPDATE jobs SET status = 'done' WHERE id = :id AND attempt = 1 AND status = 'running'. What happens?
Why. The attempt number works as a fencing token: only the current attempt's writes match. The stale worker's side effects, if any, must still be idempotent (keyed by job id), because fencing protects the jobs table, not the outside world.
A leaderboard keeps a ConcurrentHashMap of scores and a ConcurrentSkipListSet of (score, player), and addScore reads the old score, removes its set entry, writes old + delta to the map, then adds the new set entry without an outer lock. Why. Each structure is thread-safe, but the update is several steps across two of them. A reader between remove and add sees the player gone; two updaters can both read the old score, both remove it, and both add a different new entry, leaving duplicates and a lost increment. No application lock cycle is introduced by this sequence; the collections' internal synchronization does not make the compound operation atomic. Design
Design seat booking for a hot movie release: 300 seats per show, a hundred thousand fans at opening time, ten-minute holds, card payments. Cover the invariant, holds, payment, expiry and the traffic spike.
Model answer

Invariant and arbiter. One ticket per seat, enforced in the database: seats(show_id, seat_id, status, held_by, hold_id, hold_expires_at) plus a unique index on tickets(show_id, seat_id) as the backstop.

Holds. A conditional UPDATE that succeeds only if the seat is free or its hold has expired, setting the user, a fresh hold id and an expiry ten minutes after the locked decision; group holds lock the seats in seat order with FOR UPDATE and require every seat to update, else roll back. Read clock_timestamp() after taking the locks; now() is the transaction start time in PostgreSQL. Expired holds are free by definition, so no sweeper is needed for correctness.

Payment. Authorize with a stable operation-specific key; confirm only the matching user, hold id and live expiry after locking. Commit the ticket, retry result and capture outbox together. Resolve unknown confirmation outcomes by order id; void only when no booking succeeded. Retry capture idempotently, with reconciliation and a cancellation policy for terminal failure. Optionally extend the hold when checkout starts.

The spike. A virtual waiting room admits users at the rate the system can serve; the seat map is served from a cache refreshed every second or two (stale views are corrected by the conditional update); writes are per seat, so contention is limited to people fighting over the same seats. Every API is idempotent so client retries are safe, and a reconciler compares payments with tickets.

Numbers
A flash sale offers 20,000 units, and you expect 20,000 purchase attempts a second at peak. One stock row handles about 1,000 conditional decrements a second. How would you split the stock, and what else do you need?
Model answer

One row gives about 1,000 a second, so 20 rows is the ideal capacity lower bound if rows scale independently. I would start with around 40 and measure skew, logging and storage limits to leave headroom, since queueing delay climbs steeply as a single server approaches full utilization. Each row starts with 500 units; a buyer picks a random row and moves on when it is empty, and an empty scan proves permanent exhaustion only when stock never increases. With expiry returns, an unsynchronized scan means temporary unavailability unless a consistent exhaustion protocol is added. I would also put an atomic gate in front, admitting at most the remaining stock so that late attempts are turned away without touching the database, expire unpaid reservations after a few minutes and return them so we do not undersell, enforce a per-user limit with a unique key, and reconcile the gate and the rows afterwards.

Design
Design the like counter for a social app where some posts get a million likes in an hour. Users must not be able to like twice, and the displayed count may lag by a few seconds.
Model answer

Uniqueness. likes(post_id, user_id) with a primary key. Like is INSERT ... ON CONFLICT DO NOTHING; unlike is a DELETE. Only an actual insertion or deletion emits a delta. Also deduplicate request ids: a delayed retry of Like after a later Unlike must not recreate the like, so enforce an operation version if command order matters.

Counting. A million an hour is about 280 a second, more for spikes, all on one post. Commit each unique like or unlike together with a durable outbox event. Aggregators buffer those events and flush a delta per post each second. Use a recoverable batch identity and commit its deduplication record with the counter change before acknowledging the source events. For the hottest posts, use multiple counter rows and sum them on read; fix each batch's target shard across retries.

Reads. Served from a cache with a few seconds of staleness, which the requirement allows.

Correctness over time. A timeout can hide a successful flush, so retries use that same durable batch id. Crashed aggregators replay the source events, and deduplication prevents double counting. Monitor end-to-end lag to keep the few-second freshness target during normal operation; outages may violate it and must be surfaced. A periodic recount from a consistent snapshot is a repair tool, not a substitute for durable deltas. A purely in-memory buffer plus a nightly recount would not meet this freshness requirement after failures.

Out loudabout 90 s
"A customer paid while their seat hold expired. How would your booking flow prevent a double sale and recover the payment?"
What a strong answer covers
  • Database owns the seat invariant and a unique constraint prevents duplicate current tickets
  • Confirm checks the exact hold generation, user and live expiry after acquiring the row lock
  • Authorize first; commit booking, retry result and capture outbox atomically
  • Resolve unknown confirmation outcomes before voiding or repeating work
  • Retry capture with its stable key and reconcile terminal or ambiguous failures
How a senior would say it
I would make the database decide seat ownership and treat payment as a recoverable workflow. Every hold has a unique id, a user and an expiry. To confirm, I lock the seat row and check that exact hold is still live using current database time. Checking only the user is insufficient because an old checkout could consume a later hold belonging to the same user. A unique seat constraint is the final duplicate-ticket backstop. I authorize payment first, then commit the booking, its retry result and a capture request in an outbox together. If the hold has genuinely been lost, I void the authorization. If the database call timed out, I first look up the recorded order result, because the booking may already have committed. After a successful booking, the outbox worker captures with a stable operation-specific key. A crash before capture is then recoverable. A terminal capture failure needs a defined cancellation policy, and an ambiguous provider response needs reconciliation before I release the seat. I never keep the database transaction open across the payment call. This prevents two buyers owning the seat while making every failure between booking and payment visible and repairable.

Likely follow up: How would the transaction change if the customer needs three adjacent seats or none?

"Our flash sale row holds its lock for two milliseconds. Would a Redis gate fix throughput, and how do you return abandoned stock safely?"
What a strong answer covers
  • Two milliseconds of serialized lock time gives an ideal ceiling near 500 purchases per second
  • A gate limits demand but does not increase the row's write capacity
  • Split stock into independent allocations and retain a database no-oversell check
  • Use reservation identities and one atomic transition for expiry versus confirmation
  • Make cross-store release propagation idempotent and avoid claiming final exhaustion from a refillable scan
How a senior would say it
A gate would control overload, but it would not raise the stock row's write capacity. Two milliseconds per serialized purchase gives an ideal ceiling of about five hundred purchases per second, before other bottlenecks. To add capacity I would split the stock into independent allocations, spread requests across them and measure shared database limits. The gate admits at most its allocated inventory using reservation ids, so a retried request does not consume a second permit. The database still enforces no oversell. Each reservation has held, confirmed and released states. Expiry and confirmation compete in one atomic transition, and only the successful release returns the unit. If the gate is separate, I publish a durable release event and apply it idempotently there; reconciliation repairs disagreements. I also distinguish sold from temporarily reserved. With returns, a scan that saw each bucket empty at different times does not prove all were empty together. I can report temporary unavailability, retry, or coordinate a stronger exhaustion check. Capacity estimates and admission controls are useful only with that reservation lifecycle.

Likely follow up: What if a gate instance crashes and restarts with its original quota?

Out loudabout 75 s
"A scheduler worker wakes after its replacement has finished the job. What stops it from doing the work twice?"
What a strong answer covers
  • A lease cannot stop paused code from resuming; duplicate execution is possible
  • Fence job-table writes with occurrence identity, attempt, status and lease validity
  • Use a stable logical-effect idempotency key across attempts
  • Downstream deduplication and effect must be atomic; job-table fencing does not protect external effects
  • Recover retries and schedule recurrence only after a successful fenced completion
How a senior would say it
Nothing about the lease can stop the old code from resuming. I design for duplicate execution and prevent duplicate logical effects at the places that commit them. Each claim increments an attempt number. Heartbeats and completion check the job occurrence, current attempt, running status and live lease, so an old attempt cannot overwrite its replacement's result. That fences the jobs table only. For a payment or message, I send a stable effect key derived from the logical job occurrence, not the attempt number. The receiving system must atomically record that key with the effect and return the original result on retries. If it cannot provide that contract and cannot share a transaction, I cannot promise exactly-once effects. A crash after the effect but before completion then causes a safe retry when deduplication exists. Only a successful fenced finish schedules the next recurring occurrence, under a unique schedule key. I would also add retry backoff, attempt limits and an inspectable failure state, so permanent failures do not loop forever. The guarantee is about committed effects, not how many times the function runs.

Likely follow up: Would a fencing token derived separately for each job protect two jobs writing the same external resource?
