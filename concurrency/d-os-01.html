OS set 1: processes, system calls and CPU scheduling

Process versus thread, user and kernel mode, fork and exec, process states, IPC, thread models, and SRTF, round robin and priority scheduling arithmetic.

Which of these do the threads of one process share?Select all that apply
Why. Threads of a process share one address space, so the code, the heap and globals are shared, and so is the process's table of open files. Each thread has its own stack, registers and program counter, because each runs its own sequence of calls; that private state is exactly what a thread switch saves and restores. A thread can still reach another thread's stack through a pointer, since the memory is shared, which is how a pointer to a local variable leaks to another thread and later dangles.
Which events themselves require a transition from user mode into kernel mode? For the library calls and lock fast paths, assume code and data pages are resident and no unrelated interrupt occurs.Select all that apply
Why. System calls deliberately enter the kernel, page faults transfer control to a kernel exception handler, and hardware interrupts invoke kernel handlers. By contrast, ordinary strlen and memcpy execute user-mode instructions when their pages are resident. Typical uncontended futex-mutex and monitor fast paths also stay in user space, using atomic operations and bookkeeping; their exact instruction count is implementation-dependent. Parking a contended thread or waking a waiter can require kernel help. The page-residency assumption matters because even a library routine can fault on a missing page.
What makes a switch between two processes more expensive than a switch between two threads of the same process?
Why. Both process and thread switches save and restore execution state such as registers and the program counter. Switching between different address spaces adds page-table switching and can reduce TLB and cache reuse. Address-space tags can retain translations, and shared mappings can retain useful cache contents, so neither a full flush nor a fixed extra cost is guaranteed. Threads in one process normally keep the same page tables but can still have different working sets. Kernel scheduling is involved in both kinds of switch; writing the old process's memory to disk is not a normal context-switch step.
Which statements about fork() and exec() on Linux are true?Select all that apply
Why. Linux normally implements fork() with copy-on-write, so it does not immediately copy every private page. The child contains only the calling thread but inherits synchronization-object state. An ordinary process-private mutex held by another thread can therefore be unusable in the child; unlocking the parent's separate copy does not unlock the child's copy. Coordinated pthread_atfork handling can address some inherited-state problems, but after a multithreaded fork the child must still restrict itself to async-signal-safe operations until exec. A successful exec replaces the program image without changing the pid and never returns to the old program. File descriptors remain open unless marked FD_CLOEXEC.
Assume every fork() succeeds and output succeeds. Counting every process, how many lines does this print?
Why. && binds tighter, so this is (fork() && fork()) || fork(), with short circuiting. The parent P forks C1; in P the first fork returns a positive pid (true), so P runs the second fork and creates C2; that returns true in P, so && is true and P skips the third fork. In C1 the first fork returned 0, so && is false without the second fork, and C1 runs the third fork, creating C3. In C2 the second fork returned 0, so && is false and C2 runs the third fork, creating C4. Processes: P, C1, C2, C3, C4, each printing once: 5 (a real run printed 5 lines, and the process tree matched).
In the classic five state process model (new, ready, running, waiting, terminated), which transition does not exist?
Why. When the event a process waits for happens, the process becomes ready; it runs again only when the scheduler picks it. A process that wakes up does not seize the CPU on its own, even if it has high priority: a preemptive scheduler may dispatch it at once, but that is a ready to running transition decided by the scheduler. The other four are the normal arcs of the model.
On Linux, a child process exits, but its parent keeps running and never reaps it. Assume the default SIGCHLD disposition and no SA_NOCLDWAIT. What is the child now, and what happens if the parent later exits too?
Why. With the stated signal settings, exit releases most of the child's resources but keeps its pid and exit status for the parent to collect with wait or a related operation. That retained process-table entry is a zombie; it uses no CPU but still occupies process-table resources. If the parent exits, init or a subreaper adopts the child and can reap it. An orphan is a living process whose parent exited, not a child that has already exited. Explicitly setting SIGCHLD to SIG_IGN, or using SA_NOCLDWAIT, changes Linux's zombie-retention behaviour; those cases are excluded here.
Which statements about inter-process communication (IPC) are true?Select all that apply
Why. A pipe is normally a one-way byte stream. Ordinary pipe, socket and message-queue I/O often copies payloads through kernel buffers, while shared memory lets processes access the same mapped pages directly. This can help bulk transfer, but performance depends on synchronization, access patterns and the implementation. Shared memory does not by itself coordinate concurrent readers and writers. Unix domain sockets support two-way communication and descriptor passing with SCM_RIGHTS. Signals carry limited notification data, not arbitrary messages; queued signals can include a small value. Threads already share an address space and can communicate through it, using locks or atomics where needed, without requiring pipes or sockets.
Which statements about user level and kernel level threads are true?Select all that apply
Why. Many user threads multiplexed onto one kernel thread share one schedulable entity. A system call that blocks that sole kernel thread stops all of them, and they cannot execute on multiple cores simultaneously. A runtime can avoid some such blocking by using non-blocking I/O. On mainstream systems, Java platform threads and std::thread normally map one-to-one to kernel threads. Java 21 virtual threads instead share a pool of carrier threads and can unmount at supported blocking operations. Not every blocking operation unmounts them: Java 21 can pin a carrier, for example while blocking inside synchronized or native code. Kernel threads can be preempted by the scheduler.
Preemptive SJF (shortest remaining time first). Processes (arrival time, burst): P1 (0, 9), P2 (1, 4), P3 (3, 1), P4 (6, 5). What is the average waiting time?
Why. Timeline: P1 runs 0 to 1. At 1, P2 (4) is shorter than P1's remaining 8, so P2 runs 1 to 3. At 3, P3 (1) beats P2's remaining 2, so P3 runs 3 to 4 and finishes. P2 runs 4 to 6 and finishes. At 6, P4 (5) beats P1's remaining 8, so P4 runs 6 to 11. P1 runs 11 to 19. Waiting = finish minus arrival minus burst: P1 19 minus 0 minus 9 = 10, P2 6 minus 1 minus 4 = 1, P3 4 minus 3 minus 1 = 0, P4 11 minus 6 minus 5 = 0. Total 11, average 2.75. 5.75 is non-preemptive SJF (P1 0 to 9, P3 9 to 10, P2 10 to 14, P4 14 to 19), 7.5 is the average turnaround time, and 5.25 forgets to subtract arrival times.
Round robin with a quantum of 3. Processes (arrival time, burst): P1 (0, 7), P2 (1, 4), P3 (2, 2), P4 (4, 5). Arrivals join the tail of the ready queue; a preempted process goes to the tail behind any process that arrived during its slice. What is the average waiting time?
Why. Timeline: P1 0 to 3 (P2 and P3 arrived; queue P2 P3 P1). P2 3 to 6 (P4 arrived at 4; queue P3 P1 P4 P2). P3 6 to 8, finishes. P1 8 to 11 (queue P4 P2 P1). P4 11 to 14 (queue P2 P1 P4). P2 14 to 15, finishes. P1 15 to 16, finishes. P4 16 to 18, finishes. Waiting = finish minus arrival minus burst: P1 16 minus 0 minus 7 = 9, P2 15 minus 1 minus 4 = 10, P3 8 minus 2 minus 2 = 4, P4 18 minus 4 minus 5 = 9. Total 32, average 8. 12.5 is the average turnaround time, 6 is FCFS, and 10 is what you get if you treat everyone as arriving at time 0.
Preemptive priority scheduling, where a lower number means a higher priority. Processes (arrival time, burst, priority): P1 (0, 5, 3), P2 (1, 3, 1), P3 (2, 6, 4), P4 (4, 2, 2). What is the average waiting time?
Why. Timeline: P1 runs 0 to 1. P2 (priority 1) arrives at 1 and preempts it, running 1 to 4. At 4, P2 finishes as P4 (priority 2) arrives; ready are P1 (3), P3 (4) and P4 (2), so P4 runs 4 to 6. P1 runs 6 to 10, then P3 runs 10 to 16. Waiting = finish minus arrival minus burst: P1 10 minus 0 minus 5 = 5, P2 4 minus 1 minus 3 = 0, P3 16 minus 2 minus 6 = 8, P4 6 minus 4 minus 2 = 0. Total 13, average 3.25. 4 is the non-preemptive version, 7.25 is the average turnaround time, and 2 is the average response time (first run minus arrival), which ignores P1's wait after it was preempted. A steady stream of higher priority work would starve P3; aging (raising priority with waiting time) prevents that.
Which statements about CPU scheduling policies are true?Select all that apply
Why. When all jobs arrive together, putting a shorter burst before a longer one reduces their combined waiting time, so SJF minimizes average waiting. A round-robin quantum longer than every burst gives FCFS behaviour. In the stated repeated work-plus-switch intervals, useful work is 4 / (4 + 1) = 80 percent; that bound does not apply to a lone process that continues without a switch. SRTF can starve a long job if shorter jobs keep arriving. Aging prevents starvation under the last option's conditions: the waiting job eventually reaches the highest priority, FIFO ties put newcomers behind it, and the finite bursts ahead eventually finish.
