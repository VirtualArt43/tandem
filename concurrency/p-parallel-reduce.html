Parallel reduce

Executors and asyncmedium55 minAppleMicrosoftGoogleDatabricks

One loop is correct. Make it use several workers without turning the shared input or the final answer into a race.

The task

Implement three synchronous operations on ParallelReduce. Part 1 returns the sum and maximum of an immutable array. Part 2 consumes a slow, non thread safe iterator exactly once and returns the same pair. Part 3 counts words in a file by partitioning its bytes. Build the split, worker partials and join yourself using threads. Do not use ForkJoinPool, parallelStream or std::async.

Rules

  • p must be positive. Each invocation starts at most p worker threads and uses several when there is enough work. The calling thread coordinates. No worker may outlive the method, including on an iterator exception or Java interruption.
  • Each worker owns its result slot. The caller combines slots after joining. Empty inputs have sum zero and no maximum. All intermediate sums fit signed 64 bits; numeric overflow is outside this exercise.
  • The source returns the next value or a terminal empty result. Protect the complete source call, including exhaustion, then process the value outside that lock. After a source exception, stop pulling, join and propagate it.
  • A word is a maximal run of bytes other than ASCII space, tab, newline, carriage return, form feed and vertical tab. A file fits memory and is unchanged during the operation. Loading it once on the calling thread is allowed; scanning the disjoint byte chunks must be parallel. Empty files contain zero words.
  • The supplied probe is a nonthrowing, thread safe test hook: call enter once at worker entry and exit once at exit. Production uses no-op callbacks. Thread creation succeeds for the bounded input sizes in this exercise. There is no fairness or timeout promise.

Worked example

For [-8, -2, -7] and two workers, return sum -17 and maximum -2. The file alphabet soup contains two words even if a chunk begins in the middle of alphabet.

What the tests check

  • Exact sum and maximum for empty, negative and uneven arrays, including more requested workers than elements.
  • For each of the three APIs, four worker entry callbacks overlap; the peak and distinct worker count are exactly four. Eight shuffled callers reduce independent inputs.
  • An instrumented source detects overlapping calls; source failures reach the caller after all workers join.
  • Real temporary files include a long word crossing several chunks, each ASCII separator and empty data. Watchdogs bound stalled joins.

Taught in: Fork/join, work stealing and parallel algorithms

Open them one at a time. Each one gives away a little more.

Choose half open ranges using length * worker / workerCount; give each worker a private sum and optional maximum.
Separate acquiring an iterator element from processing it. The terminal flag belongs under the same lock as the pull.
Assign ownership by the byte where a word starts. A worker may inspect the preceding byte without owning it.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Apple asked for a two-thread sum over an iterator. Where is the speedup limit?
Set p to two. Pulling is serialized, so a slow source limits speedup even if the processing is parallel. Batch pulls amortize lock cost but cannot remove serial source latency.
Microsoft asked for the fastest maximum on eight cores. What changes?
Use up to eight chunks, a private maximum per worker and a final merge. Small arrays need a sequential threshold; large arrays can become memory bandwidth limited.
Does having 64 cores guarantee a 64-fold improvement?
No. The Databricks-tagged report motivates measuring parallel performance, not a fixed speedup claim. Serial input, thread startup, imbalance and memory traffic set the bound.
How would you handle a file larger than memory?
Use positional reads or bounded buffers with explicit chunk ownership and boundary state. Preserve the rule that only the chunk owning a word start counts it; handle arbitrarily long words.
Google reports parallel independent searches. What transfers?
Give each independent search private working state and a result slot, then join. Shared distance updates require a separate atomic claim protocol and cannot be justified by disjoint result slots alone.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

Key idea and invariants

Partition ownership before launching threads. An array element belongs to one half open range, an iterator value is handed out once under one lock, and a word belongs to its starting byte. Only the owning worker writes its partial. Joining publishes every slot before the merge reads it.

Why these primitives

Threads expose the requested split and join. A mutex or monitor protects the inherently serial source. No atomic sum is needed: separate slots remove concurrent writers. The source exhaustion flag stops later calls after end or failure. C++20 uses std::jthread objects to retain cleanup if thread creation throws; a C++17 version needs std::thread plus a scope guard that joins every started worker; Java explicitly joins every worker and restores an interrupted caller's status.

Pitfalls and broken interleaving

Do not initialize a maximum to zero when all values can be negative. Do not hold the iterator lock while computing a partial. The broken file scan treats every chunk's first nonspace byte as a word start. Worker A owns the start of abcdefghijklmno; worker B begins inside it and counts it again. Both partials look locally reasonable, but the merge cannot repair duplicate ownership.

How to say it in the interview

“I will define ownership and the merge before adding threads. My only input lock surrounds the unsafe iterator call. I join before reading any partial, and my file boundary rule counts starting bytes, so a long word is counted once regardless of the split.” Array work is O(n / p) per worker plus an O(p) merge in the balanced ideal; serial file loading and iterator pulls remain on the critical path.
