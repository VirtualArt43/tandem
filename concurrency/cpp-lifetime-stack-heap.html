Object lifetime, the stack and the heap

Automatic, static, thread_local and dynamic storage, when each object dies, and how a thread or callback ends up reading a dead object.

Asked atMicrosoftVMware
Before this:Values, references and pointers

In C++ you decide when every object is born and when it dies, and a thread is just one more piece of code that can outlive what it is reading. Many crashes in threaded C++ are not lock bugs at all. They are lifetime bugs that only show up on the day a thread runs slowly.

In plain words

Think of a hotel. A meeting room is yours for the length of your meeting, and the moment it ends housekeeping clears it, even if you left a colleague a note saying "see you in room 214". The lobby is there from the day the hotel opens until the day it closes, and every guest walks through the same one. Each employee has a personal locker nobody else uses, emptied when they leave. And a rented storage unit stays full until somebody hands back the key.

Those are the four kinds of storage in C++: the meeting room is automatic storage, the lobby is static, the locker is thread-local, the storage unit is dynamic. Most lifetime bugs are a note that still points at a room after the meeting ended.

Why this matters for concurrency

  • Each thread has its own stack, so local variables are private, until you hand out their address with a pointer, std::ref or a [&] capture. From then on the local must outlive every use by the other thread.
  • A detached thread, a callback stored for later, or a task in a pool that captured a reference to a local is a use after free waiting for a slow day.
  • Globals, static members and static locals are one object shared by every thread. C++11 made the initialization of a function-local static thread-safe, which is the standard answer to "write a thread-safe singleton", asked at Microsoft in a 2024 report.
  • thread_local gives every thread its own copy: per-thread counters, buffers and random generators with no locks. A Microsoft C++ candidate got thread_local questions right after a producer-consumer problem (2025 report).
  • Member destruction order decides whether a worker thread is stopped before or after the data it reads is destroyed.

The four storage durations

Every object has a storage duration, which fixes when its storage exists. Learn this table; most lifetime questions are answered by it.

"Stack" and "heap" are the implementation words for automatic and dynamic storage. A thread's stack has a fixed size. As an order of magnitude, the main thread gets 8 MB on Linux and macOS, other threads get 8 MB by default with glibc on Linux, and only 512 KB on macOS. A large local array that is fine in main can overflow a worker thread, and std::thread has no way to change the size: you would create the thread yourself with pthread_create and pthread_attr_setstacksize.

Lifetime: from constructor to destructor

A class object's lifetime normally begins when its initialization finishes and ends when its destructor starts; releasing or reusing its storage can also end its lifetime. Construction and destruction have special rules that let their code work with initialized members. Accessing an object through a dangling reference after destruction is undefined behavior, even if its old storage still exists. The rules for when the destructor runs are exact:

  • Locals are destroyed at the closing brace of their block, in reverse order of declaration, also on return and when an exception passes through.
  • A temporary dies at the end of the full expression that created it, the semicolon, unless a local const T& or T&& binds to it directly, which stretches it to the reference's lifetime.
  • Members are destroyed after the destructor body runs, in reverse order of declaration. Base classes go after the derived part.

It prints a, b, temporary born, temporary died at once, extended born, then at the closing brace extended, b, a die in that order. The reverse order is what makes RAII guards work: a lock guard declared after the data it protects is released before the data is destroyed.

Your stack is yours, until you hand out an address

Each thread runs functions on its own stack. A local variable in a function is visible only to the thread running that call, which is why locals are the safest data in concurrent code: no lock is ever needed for them. The safety ends the moment you pass &local, std::ref(local) or a [&] lambda to another thread. Now a second thread reaches into your stack frame, and your stack frame disappears when your function returns.

Dangling: when a thread outlives what it points to

A dangling reference refers to an object whose lifetime has ended. With threads, the textbook version looks harmless:

The same bug wears other clothes: a timer or thread pool callback that captured this of an object that has since been destroyed, a std::string_view of a temporary handed to a thread, a pointer to a local passed to pthread_create. The fixes, in order of preference:

  1. Give the thread its own data. Move it into the lambda: [data = std::move(data)]. Nothing the thread uses can die early.
  2. Keep the data alive until the thread is done. Join before the scope ends; a std::jthread does it in its destructor, so it cannot be forgotten.
  3. Share ownership with std::shared_ptr when several parties use the data and nobody knows who finishes last.

Notice the one reference that remains, &result. It is safe for a reason you can state: result is declared before the thread object, so it is destroyed after the thread has been joined. Every reference that crosses into a thread needs a sentence like that, and if you cannot say it, copy or move instead.

Static storage: one object for every thread

Globals, static data members and static locals exist once for the whole program, and every thread sees the same object. Every write to one needs synchronization, exactly like a shared heap object.

Their initialization has two phases. Constant initialization happens before anything runs: values the compiler can compute, such as int limit = 64; or any constexpr constructor. Dynamic initialization runs a constructor before main, and the order between different translation units is unspecified. If a global in server.cpp uses a global in logger.cpp during its own construction, the logger may not exist yet: the static initialization order fiasco.

  • C++20 constinit asks the compiler to prove an object is constant-initialized, or fail to compile. std::mutex has a constexpr default constructor, so constinit std::mutex registry_mutex; compiles, and the mutex is usable from any other global's constructor.
  • The other fix is construct on first use: put the object in a function as a static local, next section.
  • Statics are destroyed after main returns, in reverse order. A detached thread that is still running then can use a destroyed global, which is a classic crash at shutdown. Join every thread before main returns.

The thread-safe function-local static

Since C++11, if several threads reach the declaration of a static local at the same time, one of them runs the initializer and the others wait until it has finished. The initializer runs exactly once. This function-local static guarantee (nicknamed "magic statics") gives you the simplest correct lazy singleton:

Four details interviewers like to probe:

  • Only the initialization is protected. If Registry has a non-const method that changes state, calling it from several threads still needs its own mutex.
  • If the initializer throws, the static is not initialized, and the next thread to arrive tries again.
  • If the initializer calls back into the same function, the behavior is undefined (in practice, a deadlock or an exception).
  • For a lazily initialized member that is not static, use std::call_once with a std::once_flag, which gives the same "exactly once, others wait" guarantee:

Hand-rolled lazy initialization with a plain bool flag is the famous broken version; you will take it apart in double-checked locking.

thread_local: one per thread

A variable declared thread-local storage has one instance per thread. Each thread reads and writes its own, so no lock is needed, and it is destroyed when its thread exits. At block scope thread_local implies static: the value persists across calls on that thread.

It prints main thread calls = 0, total = 600: the workers made 100, 200 and 300 calls on their own copies, and main never called handle_request, so its copy is still zero. Good uses: per-thread statistics merged later, scratch buffers, random generators (a std::mt19937 is not safe to share), and anything like errno. Two traps:

  • Thread pools reuse threads. thread_local state survives from one task to the next on the same worker, so a request id or half-filled buffer can leak into an unrelated task. Reset it at the start of each task.
  • A pointer to another thread's thread_local dangles as soon as that thread exits.

Dynamic storage: the heap is shared

Objects created by std::make_unique, std::make_shared or inside containers live until their owner destroys them, and any thread that holds a pointer can reach them. The allocator itself is safe to call from many threads at once: the standard requires that operator new and operator delete can be called concurrently, and modern allocators keep per-thread caches so they rarely contend on a global lock. But a thread-safe allocator says nothing about the objects you allocate. Deleting an object while another thread still uses it is a use after free, and preventing that is exactly the job of shared ownership in the smart pointer lesson.

Worked example: declare the thread last

An Indexer owns a queue, a mutex, a condition variable and a worker thread that drains the queue. The interesting decision is not the locking. It is the order of the member declarations, because members are constructed top to bottom and destroyed bottom to top.

It prints indexed 3 documents every time. Now move std::jthread worker_; to the top of the member list and two separate bugs appear:

  • Construction: the thread starts in the constructor's initializer list, before m_, cv_ and queue_ exist, and run immediately locks a mutex whose lifetime has not begun.
  • Destruction: reverse order means the queue, the condition variable and the mutex are destroyed first, while the worker is still running, and the join happens last, far too late.

The rule to say out loud: a thread member goes last, so it starts after everything it uses exists and is joined before any of it is destroyed. The same applies to anything that runs callbacks into the object, such as a timer.

Common mistakes

  • Capturing locals by reference in a detached thread or a stored callback. Move the data in, or join before the scope ends.
  • Returning a reference or std::string_view to a local or a temporary. std::string_view v = std::string("a") + "b"; dangles at the semicolon.
  • Believing a function-local static makes the object thread-safe. Only its initialization is. Its methods need their own synchronization.
  • Letting detached threads run during shutdown. Globals are destroyed after main returns, under their feet.
  • Declaring a thread member before the members it uses. Declare it last.
  • Assuming thread_local starts fresh for each task in a pool. It lives as long as the worker thread.
  • Big arrays on a worker's stack. 512 KB goes quickly on macOS. Use a std::vector.

In the interview

Lifetime arrives in three forms. "Write a thread-safe singleton" (Microsoft, 2024; VMware walked a 2021 candidate through one line by line) is answered with the function-local static, and the follow ups test whether you know what it does not protect. "What is thread_local, and when would you use it?" came right after a producer-consumer problem in a 2025 Microsoft C++ loop. And in code reading and debugging rounds, the detached thread that captured a local by reference is a favourite planted bug.

Since C++11, initialization of a function-local static is thread-safe: one thread runs the constructor and any others that arrive wait for it, so a static local in instance() is a correct lazy singleton with no explicit locking. That guarantee covers construction only; if the singleton has mutable state, its methods still need a mutex. For a per-object version I would use std::call_once.
Every reference that crosses into a thread needs a lifetime argument. Here the lambda captures data by reference and the thread is detached, so when the function returns the thread reads a destroyed vector. I would move the vector into the lambda, or keep a std::jthread so the scope cannot end before the work does.

Follow ups: "How is the static local made thread-safe without slowing every call?" (a guard flag checked with an acquire load; the lock is only taken during the first initialization); "When are thread_local objects destroyed?" (at thread exit, on that thread); "What happens to a detached thread when main returns?" (the process exits and it is cut off wherever it is, possibly after globals were destroyed).

Senior depth

Shutdown is a lifetime problem. Static objects are destroyed in reverse order of construction after main returns, and thread_local objects of the main thread are destroyed before them. Code that logs from destructors, or detached threads that touch globals, can run into objects that are already gone. Some large codebases deliberately never destroy certain singletons (they allocate them once and leak them on purpose) to make shutdown order irrelevant; others join every thread in an explicit shutdown sequence before returning from main.

std::thread cannot set a stack size or a name. A name needs a platform call such as pthread_setname_np, and a stack size means creating the thread yourself with POSIX attributes, which you will see in how std::thread maps to the OS.

A thread_local with a non-trivial constructor is typically initialized lazily on first use in each thread, and each access may go through a small check or a runtime lookup, especially from a shared library. In a hot loop, copy it to a local first.

Under the hood

For a function-local static, the compiler emits a hidden guard variable next to the object. Every call does a fast acquire load of the guard; if it says "initialized", the call proceeds with no lock. Only on the first calls does it enter a runtime routine (__cxa_guard_acquire and __cxa_guard_release in the common Itanium C++ ABI) that takes a lock, runs the constructor once, and wakes the waiters. thread_local variables live in a per-thread block of memory that the runtime creates for each new thread and finds through a per-thread register or a lookup function.

Key takeaways

  • Four storage durations: automatic (one thread's stack), static (one object for all threads), thread (one per thread), dynamic (shared with whoever holds a pointer).
  • Locals die at the closing brace in reverse order; temporaries die at the semicolon unless bound to a local const reference.
  • A thread or callback that holds a reference to a local is a dangling reference waiting to happen: move the data in, or join before the scope ends.
  • Initialization of a function-local static is thread-safe since C++11; use it for singletons, and std::call_once for per-object lazy setup.
  • Declare a thread member last, so it starts after and is joined before everything it uses.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a thread-safe, lazily created Config::instance() in C++, then state exactly what the language guarantees and what it does not.
Model answer

Guaranteed: the constructor runs exactly once, the first time control reaches the declaration, even if many threads arrive together; the others block until it finishes, and they all see the fully built object. If the constructor throws, a later call retries. Not guaranteed: anything about the object's methods, which is why endpoint and set_endpoint lock their own mutex. Also worth saying: copying is deleted so nobody makes a second instance, recursion into instance() from the constructor is undefined, and the object is destroyed after main returns, so threads must not use it during shutdown.

Debug
A service crashes rarely, only at shutdown. Its metrics thread is started with std::thread(...).detach() and every second writes to a global MetricsRegistry. What is the likely cause, and how do you fix it?
Model answer

When main returns, static objects are destroyed in reverse order of construction, and the detached metrics thread keeps running until the process actually exits. If it wakes up after MetricsRegistry has been destroyed, it writes into a dead object: undefined behavior that usually shows up as a rare crash during exit. It is rare because the thread must wake in the short window between the registry's destruction and process exit.

The fix is to own the thread instead of detaching it: keep a std::jthread (or a std::thread you join) in an object that is shut down before main returns, and have the loop watch a std::stop_token or a stop flag protected for cross-thread use, so the destructor can request a stop and join. Then shutdown order is explicit: stop the metrics thread first, then let the registry die. If you truly cannot join, make the registry immortal (never destroyed), but owning the thread is the clean answer.

Explain
Explain the four storage durations to an interviewer and say which ones can be shared between threads.
Model answer

Automatic storage is locals and parameters: created when execution reaches them, destroyed at the end of the block in reverse order, living on one thread's stack. They are private to that thread unless I hand out their address, and then I am responsible for the local outliving the other thread's use. Static storage is globals, static members and static locals: one object for the whole program, shared by every thread, so every write needs synchronization; globals across files have an unspecified initialization order, and static locals are initialized thread-safely on first use. Thread storage is thread_local: one instance per thread, created no later than first use and destroyed when the thread exits, so it needs no locks but must not be reached from other threads after its owner exits, and it persists across tasks on a pooled thread. Dynamic storage is anything allocated and owned by a smart pointer or a container: it is shared with any thread that holds a pointer, and the hard part is making sure nobody deletes it while another thread still uses it, which is what std::shared_ptr solves.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"A detached worker captures a local vector by reference. It passes every test on your laptop but crashes under load. Walk me through the bug and your fix."
What a strong answer covers
  • The reference capture does not extend the vector's lifetime
  • The caller can return and destroy the vector before the worker finishes, causing undefined behavior
  • Move the vector into the worker when the caller no longer needs it
  • Alternatively join before the vector dies, including on exception paths
  • Shared ownership preserves lifetime but does not synchronize mutations
How a senior would say it
I would fix the ownership first. The lambda holds a reference to the vector, and that reference does not keep the vector alive. Under load, the worker can be delayed until after the caller returns. The vector is destroyed, its buffer is released, and the worker reads a dead object. That is undefined behavior, even if earlier runs happened to finish in time. If the caller no longer needs the data, I would move the vector into the lambda so the worker owns it. If the worker must borrow it, I would join before the vector leaves scope, using a jthread declared after the vector to cover exceptions too. Shared ownership is another option when several tasks need the same data. It keeps the object alive, but concurrent mutations still need synchronization. I would document both who owns the data and when the worker finishes.

Likely follow up: What changes if the captured value is a std::string_view rather than an owning vector?

Out loudabout 75 s
"Your class owns a queue, a mutex and a jthread. Its destructor sometimes hangs, and another version crashes at shutdown. How would you review the lifetime design?"
What a strong answer covers
  • Join the worker before destroying any member it uses
  • Construction follows member declaration order; destruction reverses it
  • Declare the worker last and finish initializing everything it accesses before starting it
  • A jthread requests cooperative stop and joins; blocked waits must be made responsive to stopping
  • Never join while holding a mutex the worker needs to finish
  • The destructor body must also preserve worker-visible state until the join completes
How a senior would say it
I would make the worker finish before any state it uses is destroyed. Members are constructed in declaration order and destroyed in reverse order, regardless of the initializer list. I would declare the queue and synchronization objects before the jthread, with the worker last. That ensures its members exist before the worker starts, and its destructor joins before those members disappear. I would also check that the worker does not depend on setup still happening in the constructor body. For the hang, I would inspect the stop path. A jthread requests a stop and joins; it does not kill the worker. An ordinary condition variable wait does not automatically wake for that request. The worker needs a stop-aware wait or a shutdown predicate and notification. I would release any mutex the worker needs before joining. Finally, the enclosing destructor body runs before member destruction. It must not clear the queue or invalidate other worker state before the worker finishes. Declaration order helps, but the constructor body, destructor body and shutdown protocol must all respect the same lifetime rule.

Likely follow up: How would you implement the same ownership and shutdown guarantees with C++17 std::thread?

Out loudabout 60 s
"Why would you use a function-local static for a lazy registry, and exactly what does its thread-safety guarantee cover?"
What a strong answer covers
  • C++11 guarantees synchronized initialization of a function-local static
  • One caller initializes successfully and concurrent arrivals wait for completion
  • A throwing initializer can be retried; recursive re-entry during initialization is undefined behavior
  • Later mutations still require their own synchronization
  • Join users before static destruction; use call_once for per-object lazy setup
How a senior would say it
I would use a function-local static because C++11 already provides the synchronization for lazy construction. When several callers arrive, one performs initialization and the others wait for it to finish. They then receive the same fully initialized registry. The precise promise is one successful initialization. If construction throws, that call fails and a later attempt can retry. Recursively entering the same declaration while initialization is in progress is undefined behavior, so I would avoid that dependency cycle. This protects construction only. If the registry later updates a map, those updates and its reads still need a mutex or another suitable protocol. I would also join every user before shutdown destroys the registry. For lazy setup that belongs to each connection object, rather than one registry for the whole program, I would use a separate once flag and call_once in each connection.

Likely follow up: Would making the registry thread_local solve the same problem, or change the design?
