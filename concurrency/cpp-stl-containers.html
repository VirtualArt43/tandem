STL containers, complexity and iterator invalidation

Container costs, iterator and reference invalidation, and the precise concurrency guarantees behind a safe queue, cache or registry.

Asked atGoogleDatabricks
Before this:Templates, auto and type deductionCopy, move and move-only types

Almost every shared structure in a threaded C++ program is a standard container behind a lock. To lock it correctly you must know what each operation really does underneath: which ones allocate, which ones move elements, and which ones silently break the iterators and references that another thread may still be holding.

In plain words

Picture a library. A vector is one long shelf with the books packed tight. When the shelf is full, the librarian buys a longer shelf and carries every book across, so a note saying "third book from the left on the old shelf" now points at empty wood. A deque is a row of small shelves: when one fills up, a new small shelf is added at the end and no book ever moves. A list is a chain of books, each on its own hook. An unordered_map is a set of numbered bins; when the bins get crowded, the librarian adds bins and re-sorts the books into them.

Now put two librarians on the same shelf at the same time, one adding books and one counting them. Each does their own job correctly, and the count still comes out wrong, or a book ends up on the floor. Adding and counting need coordination. You supply it when the container does not guarantee those operations can overlap.

Why this matters for concurrency

  • Structural writes need coordination. Two threads calling push_back on one vector is a data race: lost elements, a corrupted size, or a crash. Even size() racing with a push_back is undefined behavior.
  • Iterator invalidation is how references escape a lock and die. A reference into a vector taken under the lock can dangle if another thread later grows it beyond capacity. Other containers have different rules, so distinguish iterator validity from element lifetime.
  • The right container makes the locking simple. A blocking queue sits on a deque, an LRU cache needs a list plus an unordered_map of list iterators, a scheduler needs a heap, and a striped map is an array of small maps.
  • It is asked. A Google L5 candidate in Bengaluru (2024) built a frame reordering service in C++ on an unordered_map and a list, then spent a long discussion on its concurrency problems. A Databricks report (2025) describes a round on Java ConcurrentHashMap locking and why HashMap is not thread-safe. The corresponding C++ design discussion concerns std::unordered_map; the report is not evidence of a C++ API question.

The thread safety contract

For a safely published container whose lifetime covers all workers, start with these two guarantees:

  1. Concurrent reads are safe. Any number of threads may call reading operations at the same time, when no thread changes its structure or the values those operations read. User-provided hashers and comparators must also avoid races in their own shared state. For this rule the standard treats begin, end, rbegin, rend, front, back, data, find, lower_bound, upper_bound, equal_range, at and, except for map and unordered_map, operator[] as reads, even on a non-const container.
  2. Different elements may be written concurrently. Thread 1 may assign results[0] while thread 2 assigns results[1], because they are different objects. The one exception is std::vector<bool>, whose specialization may pack different bits into the same memory location.

These guarantees do not authorize concurrent structural mutation. For a mutable registry, adopt one synchronization policy for container operations, including insert, erase, size and find; map operator[] may insert. This is a design rule, not a claim that every structural change races with every element access: inserting into a node-based container need not touch an already-held reference to an unrelated element. Any such optimization needs a separate proof of validity, lifetime and nonconflicting access.

Watch it fail. Two threads append to one vector with no lock. Reserving capacity removes the normal need to grow for these 2,000 appends, but it does not synchronize the shared size or element construction. Once a data race exists, no particular outcome is guaranteed.

Inside push_back each thread reads the end pointer, writes the element there, and stores the end pointer plus one: a read-modify-write. Two threads can write to the same slot and both advance the pointer to the same place, so an element is lost. Under ThreadSanitizer the run may even print 2000, and the report still names push_back in both threads. A run that printed the right number proved nothing.

The fix is a class that owns the container and its mutex, and takes the lock for every access, reads included:

"But size() is just reading one number"

A vector usually stores three pointers (begin, end, and the end of its capacity), and size() subtracts begin from end. A reader racing with a reallocating writer can load the new begin and the old end and compute nonsense. And even when the hardware would read a single word cleanly, the C++ rule is simpler: a read and a write of the same memory with nothing ordering them is a data race, and a data race is undefined behavior. Lock the reads.

These bounds count container work, assuming constant-cost element operations, comparison and hashing; copying a long string adds its own cost. Lock acquisition and condition waiting can add unbounded delay. For a sorted vector, O(log n) search means binary search; std::find remains linear.

reserve(n) grows vector capacity when needed without constructing elements: size() stays unchanged, so indexing a merely reserved slot is invalid. Use resize(n) or a size constructor for worker-owned slots. shrink_to_fit() is a nonbinding request, and vector::shrink_to_fit invalidates all handles if it reallocates. list::splice across lists requires equal allocators; moving a range between different lists is linear in the range length, unlike the single-node operation.

Two costs matter more under a lock than anywhere else. A vector that reallocates copies or moves every element while every other thread waits, and an unordered_map that rehashes relinks every node while every other thread waits. When you know the size in advance, reserve it up front so the spike happens before the threads start, not in the middle of the hot path.

Adaptors, heaps and move-only elements

std::queue, std::stack and std::priority_queue wrap another container and expose a narrow interface. Two details trip people up. First, pop() returns void; you read front() or top() and then pop, two calls that must happen under one lock. Check nonemptiness under that same lock: accessing or popping an empty adaptor violates its preconditions. Second, with its default comparison std::priority_queue is a max-heap: for "soonest deadline first" you pass std::greater as the comparator.

Because top() returns a const reference, you cannot move a std::unique_ptr out of a priority_queue. When the elements are move-only, keep a plain std::vector and manage the heap yourself with std::push_heap and std::pop_heap: pop_heap moves the top element to the back, where you can move it out and pop_back().

Iterator and reference invalidation

iterator invalidation means an operation makes an existing iterator unusable. An iterator can become invalid even when the element stays at the same address, as a hash-table rehash demonstrates. References and pointers have their own validity rules; neither they nor iterators protect an element's lifetime or synchronize access.

The table concerns the listed operations, not assignment, destruction or every allocator-sensitive move. Node-based insertion preserves existing element addresses, and hash-table rehash preserves references too. A vector reallocation relocates all elements. Deque end insertion preserves element addresses but invalidates all iterators by contract, even on a particular push that does not grow its block index; middle insertion can relocate elements.

For std::string, non-const element access through operator[], at, front, back and data, and iterator accessors, are exceptions to its broad invalidation permission. Do not assume push_back preserves references merely because capacity appears sufficient. These are C++20 library guarantees, not observations about one run.

What invalidation looks like across threads

For these wrappers, keep the lock for the entire use of an iterator or reference unless the API separately guarantees lifetime and synchronization. Another thread can reallocate a vector, erase a node, or mutate the same value immediately after you unlock.

ThreadSanitizer can detect conflicting unsynchronized accesses, and AddressSanitizer can detect a heap use after free when a dangling reference is exercised. Use them in separate builds. Neither helps if the bug never runs during your test, so the rule has to live in the code: never let an iterator, reference or pointer into a guarded container outlive the lock.

Erasing while you iterate

The single-threaded version of the same bug is erasing inside a loop. For a map, after m.erase(it), it is invalid, so the loop's ++it is undefined behavior. Use the iterator that erase returns, or, in C++20, std::erase_if:

Worked example: the containers inside a thread-safe LRU cache

An LRU cache aims for average O(1) lookup, recency updates and eviction, excluding value-copy costs and lock waiting. Hash-table worst cases are linear. No single container does all three, so you combine two: a std::list of entries in recency order, and an std::unordered_map from key to the list iterator of that entry.

The choice works because of the invalidation table. list::splice moves a node to the front without copying it, and every list iterator stays valid, including the ones stored in the map. When the map rehashes, its own iterators break, but the values it stores (list iterators) are untouched. A vector would need linear shifts to move an entry to the front, making affected positions identify different entries.

Three decisions to say out loud. get takes the exclusive lock, because moving a node to the front is a write; a reader-writer lock would let two "readers" splice the same list at once. get returns a copy of the value (std::optional<std::string>), never a reference into the list. And one mutex guards both containers, because the invariant ("each list node has exactly one matching map entry, and each map entry points at that live node") spans both.

Allocation can throw after the list insertion succeeds, so put rolls that node back if the map insertion fails. This preserves the invariant for this concrete int/std::string cache with its standard hash; a generic cache with throwing hashers or values needs its own exception analysis. A failed result copy in get can still change recency, so this is not a blanket strong exception guarantee.

Common mistakes

  • Locking writes but not reads. size(), find and iteration race with a concurrent writer. In these wrappers, every container operation takes the same lock; explicitly designed disjoint-element access is a separate contract.
  • Using map[key] to look something up. operator[] inserts a default value when the key is missing, so it is not a read-only lookup API. Under a shared (reader) lock, missing keys can cause concurrent structural writes. Use find, or at, which throws when the key is missing.
  • Keeping iterators or references after unlocking. Copy out what you need, or hold the lock for as long as you use them.
  • Erasing inside a range-for loop. Erasing the current element invalidates the loop's hidden iterator. Use it = c.erase(it) or std::erase_if.
  • Calling "different elements are safe" on a vector<bool>. Its implementation may pack bits into shared storage. Use std::vector<char> or std::vector<std::uint8_t> for per-thread flags.
  • Expecting pop() to return the element. queue::pop, stack::pop and priority_queue::pop return void; read the element first, under the same lock.
  • Choosing std::list for speed. Its nodes typically require separate allocations, and pointer chasing often has poor cache locality. Pick it for iterator stability and splice, as in the LRU cache, and a vector or deque otherwise.

In the interview

The direct question is "is std::unordered_map thread-safe?", and the precise answer is what separates candidates. The indirect version is a design follow up: "now several threads call put and get", where you must pick a container, a lock, and say what happens to iterators.

The key standard guarantees are: concurrent calls to read-only operations are safe when nobody writes, and different elements can be modified concurrently. For a shared map with structural mutation, I synchronize all container operations, including reads. A rehash invalidates iterators but preserves element references. Erase still destroys elements, and values can still change, so this API returns owning copies under the lock.

Follow ups to expect: "Can two threads insert different keys at the same time?" (no: the bucket array, the size and a possible rehash are shared), "Can each thread write its own element of a vector?" (yes, if the vector is pre-sized, never resized, and not vector<bool>), "How would you make the map scale?" (stripe it into N shards, each with its own mutex and map, chosen by hash; or a std::shared_mutex if reads dominate and no read mutates), "Why list in your LRU?" (splice of one node is O(1) and iterators survive insertion and erasure of other nodes), and, from interviewers who know Java, "what is the C++ ConcurrentHashMap?" (the standard library has none; you write the mutex or the striping yourself, or select a nonstandard concurrent-container library after checking its access and lifetime contract).

Under the hood

vector growth. When a vector is full, it allocates a bigger block (the growth factor is implementation-dependent), moves or copies every element across, then frees the old block. That is why push_back is amortized O(1) and why all references die at once. If the element's move constructor is not noexcept and the element can be copied, the vector copies instead of moving, to keep its strong exception guarantee (if a noncopyable element's move throws, the usual no-effects guarantee can be waived); more on that in exceptions.

deque blocks. A deque is an array of pointers to fixed-size blocks. Pushing at either end fills the end block or adds a new one; existing elements stay in place for end insertion, but the array of block pointers sometimes reallocates. The standard invalidates all deque iterators on every end insertion regardless of whether that happened this time.

Hash buckets. A typical unordered_map, including libc++, uses a bucket array and linked nodes; exact link layouts are implementation details. When the number of elements exceeds bucket_count() * max_load_factor() (the factor starts at 1.0), it allocates a larger bucket array and relinks every node into it. Nodes stay where they are, so references survive; the order of iteration changes, so the standard declares every iterator invalid. Calling reserve(n) before the threads start budgets buckets for n elements at the current maximum load factor. Staying within that budget with an unchanged load factor avoids growth rehashes, but does not synchronize inserts or eliminate node allocations.

Containers of mutexes. A std::mutex cannot be copied or moved, so a std::vector<Shard> whose Shard holds a mutex can be built with a size (std::vector<Shard> shards(16);) but never grown: push_back fails to compile. A std::array<Shard, 16> is the usual choice for a fixed stripe count, and a std::deque<Shard> with emplace_back works too, because end emplacement does not relocate existing deque elements. Middle insertion has different requirements.

Key takeaways

  • Standard containers allow concurrent reads, and concurrent writes to different elements (not vector<bool>). Use a shared synchronization policy for structural mutation and container lookups.
  • operator[] on a map can insert. size() racing with push_back is a data race.
  • Node-based insertion preserves existing elements; vector reallocation relocates all of them; deque end pushes break iterators but not references; a rehash breaks iterators but not references.
  • Never let an iterator, reference or pointer into a guarded container outlive the lock. Return copies.
  • Pick containers for their invalidation rules as much as their big O: a list plus an unordered_map of list iterators is the LRU cache.

std::vector<int> v{1, 2, 3, 4}; has size 4 and capacity 4. You run int& r = v[0]; v.push_back(5);. Is r still usable?
Why. Size equal to capacity means the push must allocate a new block, move every element and free the old one, so every reference, pointer and iterator dies. With spare capacity, r would have stayed valid. No thread is involved in this bug at all.
std::deque<int> d{1, 2, 3}; You run int& r = d.front(); auto it = d.begin(); d.push_back(4);. What is still valid?
Why. Pushing at either end of a deque invalidates all iterators, because the deque's index of blocks may be reallocated, but no element ever moves, so references and pointers stay valid. This is the opposite of what most people guess.

Why. Reserving storage does not synchronize updates to the vector's shared size or element slots. The race makes the whole program's behavior undefined, so even a correct-looking 2000 is luck. A ThreadSanitizer report diagnoses a race even if the printed total is correct. A clean run is not a proof of correctness.
Why does an LRU cache use a std::list for recency plus an std::unordered_map from key to list iterator?
Why. The design depends on stable list iterators: the map holds them for O(1) lookup, and splice relinks a node without invalidating anything. unordered_map iterators do break on a rehash, but the map's values are list iterators, which a rehash does not touch. Neither container supports concurrent structural mutation without coordination.
A read-heavy registry uses std::shared_mutex. Readers run this under a std::shared_lock. What is wrong?
Why. A shared lock lets many readers in at once, which is only safe if they really only read. operator[] is a modifying call: on a missing key it inserts and rebalances the tree, racing with the other "readers". Use find and handle the missing case. Returning a reference would add a second bug.
sessions is a std::map<int, Session>. What is wrong with this loop?
Why. For a map, erase invalidates exactly the erased element's iterators, and it is that iterator. Incrementing it is undefined behavior, which may crash, skip elements or appear to work. erase returns the next valid iterator; C++20's std::erase_if does the whole loop for you.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
The interviewer asks: "Is std::unordered_map thread-safe? Could two threads at least insert different keys at the same time?" Answer precisely, as you would out loud.
Model answer

No. The standard containers only promise that concurrent calls to read-only operations are safe when nobody modifies the container, and that different elements can be modified concurrently. Inserting different keys is not "different elements": both inserts modify the shared bucket array, the element count, possibly the same bucket chain, and either insert may trigger a rehash that relinks every node. Those combinations are not guaranteed safe by the standard; in ordinary implementations they can race. A different key is not a synchronization boundary. To make it safe I put the map behind a mutex and take it for every access, reads included, and I return owning values by copy: rehash invalidates iterators but preserves references, while erase can destroy the referenced element and updates can race with readers. If it becomes a bottleneck, I stripe it: N shards, each a mutex plus its own map, picked by hash of the key, so threads touching different shards do not contend. If reads dominate and never mutate, a std::shared_mutex lets readers run in parallel.

Debug
A cleaner thread and many request threads share this class. Under load it occasionally crashes inside touch. Find the bug and fix it.
Model answer

find returns a pointer into the map, and the request thread uses it after the lock is released. If the cleaner erases that session in between, touch() runs on a destroyed object: a use after free. Even when the session survives, touch() modifies it with no lock while other threads may read or modify the same session, which is a data race. The map's node stability (references survive a rehash) does not help, because erase destroys the node.

Fix: do the work under the lock, and never hand out a pointer into the map.

If sessions must be used outside the lock for a long time, store std::shared_ptr<Session> in the map and return a copy of the shared pointer; the session then stays alive while any thread uses it, and the session's own state needs its own synchronization.

Design
You are building a thread-safe delay queue: schedule(task, delay), a worker that runs each task when it is due, and later cancel(taskId). Which containers do you use, and why?
Model answer

For schedule and run only: a std::priority_queue min-heap under one mutex, with a comparator that orders entries by (due time, sequence number). std::greater works if the entry type defines that ordering. The heap gives O(log n) insert and O(1) access to the earliest task, and the sequence number keeps tasks with equal deadlines in FIFO order.

std::priority_queue has no arbitrary-erasure API, so for cancel there are two standard options. Lazy cancellation: keep the heap, plus an std::unordered_set of canceled ids (or a canceled flag in a shared state object); the worker discards canceled entries when they reach the top. The hash-set update is average O(1), excluding the lock wait, but canceled entries can occupy memory until they reach the top. Define cancellation of unknown or already-running ids, and notify the worker when the earliest entry is canceled. An indexed heap is another option: store each task's heap position and repair the heap after O(log n) arbitrary removal. Eager cancellation: replace the heap with an ordered std::map (or std::set) keyed by (due time, sequence), plus an std::unordered_map from task id to the map iterator. Map iterators survive other inserts and erases, so erasing through a stored map iterator is amortized O(1); finding that iterator in the hash index is average O(1), while scheduling remains O(log n). Erasing by an ordered-map key would instead cost O(log n). Either way, one mutex guards all of the containers, because they must agree with each other, and schedule notifies the worker when the new task is due earlier than the one it is waiting for. Use steady_clock deadlines and recheck the earliest task after wakeups; remove a ready task under the lock and execute it outside the lock.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Two workers update different keys in an unordered map. Is that enough to make it safe?"
What a strong answer covers
  • Different keys alone do not authorize concurrent insertion or other structural changes
  • Insertions share container metadata and can rehash; lookups need the same synchronization policy
  • Distinct existing mapped values can be updated under a stable-structure ownership contract
  • Use one mutex first, copy results under it, and distinguish lifetime from value synchronization
  • Scale with independent map shards; read locks require genuinely nonmutating lookups
How a senior would say it
No. Different keys are not enough if either operation can insert or otherwise change the map's structure. Inserts share metadata, can touch the same bucket, and can trigger a rehash. I would first protect all container operations with one mutex, including lookups and size. There is a narrower guarantee for different existing elements. If we populate the map before starting workers and freeze its structure, each worker can update its own mapped value through a suitable reference or at, provided the values do not share other mutable state. That is a different contract from concurrent insertion. For the general registry API, I would copy an owning result while holding the mutex. Rehash preserves element references, but erase can destroy the object and an update can race with a reader, so address stability alone is insufficient. If measurement shows contention, I would shard into independent maps, each with its own mutex. For a read-heavy workload, shared locks are another option, but lookup must use find or at. Map subscript can insert a missing key and is not a read-only lookup API.

Likely follow up: Why does reserving all the buckets in advance still not make concurrent insertion safe?

Out loudabout 75 s
"We take a reference while holding a mutex, unlock, then sometimes crash when using it. How would you investigate that?"
What a strong answer covers
  • The lock protected obtaining the reference, not its later use
  • Vector reallocation and erasing a referenced node can end the referenced object's lifetime
  • Deque end insertion and unordered-map rehash distinguish invalid iterators from valid references
  • Stable lifetime still does not prevent a race on the referenced value
  • Copy under the lock or extend protection; use sanitizers as evidence rather than proof
How a senior would say it
I would first check whether the reference is used after the lock is released. The lookup may be protected while the actual access is not. With a vector, another thread can append beyond capacity, moving elements to new storage and destroying the old objects. The reference then dangles. With a node-based map, rehash is different: it invalidates iterators but preserves references to elements. Erasing the referenced element still destroys it. A deque gives another useful distinction: insertion at either end preserves references but invalidates all iterators. I would identify the exact container and operation before calling this an invalidation bug. Even if the object stays alive, a concurrent update to the same value can still be a data race. My default fix is to copy the required value while holding the lock, or keep protection through the entire operation. Shared ownership can extend lifetime, but the object's state still needs synchronization. I would exercise the failure under AddressSanitizer for lifetime errors and ThreadSanitizer for races in separate builds. Clean runs would not replace that lifetime and synchronization argument.

Likely follow up: Why is auto snapshot = getterReturningReference() still unsafe if the getter unlocks before returning?

  • Eviction invalidates the victim's handles; shared reads or escaped references are unsafe
How a senior would say it
I would use a list for recency and an unordered map from key to list iterator. That gives average constant-time lookup and single-node promotion, excluding value copies and lock waiting. Splice moves a node to the front without invalidating its iterator, so the index remains valid. Rehashing the index invalidates the map's own iterators, but not the list iterators stored as values. One exclusive mutex protects both containers, and get takes it too because a cache hit changes recency. I return an owning value copied under that lock. The first failure path is allocation: we may successfully create the list node and then fail to insert its map entry. I roll back the new list node before propagating the exception, so the two containers still agree. The second path is eviction: remove the victim from the index and list under the same lock, and never let callers retain references to that node. A reader lock on get would be wrong because two hits could splice concurrently. I would test zero capacity, repeated keys, eviction order and allocation failure.
