Read-write locks and StampedLock

Many readers or one writer: when a read-write lock wins, when it loses to a plain mutex, and what to use for read-mostly data instead.

Asked atRubrikGoogleMicrosoftApple
Before this:Mutexes and RAII guardsReentrant and recursive locks

"Most of our traffic is reads, so let readers share the lock" sounds like a free speedup. Sometimes it is. Often it is slower than a plain mutex, it can starve writers, and it has a deadlock built in for anyone who tries to upgrade. Knowing which case you are in is the senior skill.

In plain words

Think of the departures board at a railway station. Hundreds of passengers can read it at the same time; reading does not disturb anyone. When the station master needs to change a platform number, he waits for a gap, puts up a "please wait" sign, makes the change, and takes the sign down. While he writes, nobody reads, so nobody sees a half-painted number.

That is a read-write lock: many readers together, or one writer alone. The catch is the gap. If passengers keep arriving and overlapping, there may never be a moment with nobody reading, and the station master waits all day.

The rules, and the API

A read-write lock has two modes. The read (shared) lock can be held by any number of threads at once. The write (exclusive) lock can be held by one thread, and only when no reader holds the read lock. Readers exclude writers, writers exclude everyone.

When a read-write lock helps, and when it hurts

The lock only pays off when readers actually overlap for long enough to matter. Compare two workloads:

  • Long reads, rare writes: a search over a large in-memory index, a report that walks a big structure, a routing table consulted while a request is processed for a few microseconds. With a plain mutex, those reads queue behind each other for no reason. With a read-write lock they run in parallel. This is the case read-write locks are for.
  • Short reads: a hash map lookup that takes 50 nanoseconds. Here the read lock itself is the problem. Every read acquisition is an atomic read-modify-write on the lock's shared state, and every release is another. With many cores reading at once, the cache line that holds that state bounces from core to core (tens to a hundred nanoseconds per transfer, as an order of magnitude), so the bookkeeping costs more than the read it protects. A plain mutex can beat it, and the lock-free alternatives below beat both.

Java's ReentrantReadWriteLock adds one more cost: because read locks are reentrant, it must track each reading thread's own hold count, which it does with a thread-local counter. The lock is a heavier object than a mutex, and it shows on hot paths.

Writer starvation

Now the station master's problem. If the lock lets a new reader in whenever other readers already hold it, a writer that is waiting for "no readers" may wait forever under steady read traffic. That is writer starvation.

Implementations differ here, so know yours:

  • Java: a nonfair ReentrantReadWriteLock (the default) makes a new reader wait if the thread at the head of the wait queue is a writer. That heuristic makes writer starvation unlikely, though not impossible. new ReentrantReadWriteLock(true) serves waiters in arrival order, letting consecutive readers in together.
  • C++: the standard says nothing about priority. libc++ (macOS) makes new readers wait once a writer is waiting. On Linux, libstdc++ builds std::shared_mutex on glibc's pthread_rwlock_t, whose default prefers readers: as long as readers keep overlapping, a writer waits.

The opposite policy, strict writer preference, can starve readers when writes are frequent. A lock that starves neither side serves arrivals in order and lets runs of consecutive readers share: that is the fair read-write lock problem.

Upgrading deadlocks, downgrading is fine

A tempting pattern: take the read lock, look at the data, and if it needs changing, "upgrade" to the write lock without letting go. Neither language supports it, and in both it hangs:

Why not make upgrades work? Picture two readers that both decide to upgrade. Each now waits for all other readers to leave, and the other reader is waiting too. Even a lock that "supports" upgrades has to refuse at least one of them. StampedLock.tryConvertToWriteLock never waits: it converts a read stamp only when the caller is the sole reader, and otherwise returns 0. Designs with a separate upgradable mode, such as Boost's upgrade_mutex, let only one thread hold that mode at a time.

The safe version of an upgrade is to release the read lock, take the write lock, and check again, because another writer may have changed things in the gap. This is the standard get-or-load shape for a cache guarded by a read-write lock:

The loader runs under the write lock, which blocks every reader while it runs: fine for a cheap computation, bad for a network call. Production caches load outside the lock and coordinate concurrent loads of the same key, which you will build in thread-safe caches.

Going the other way is safe in Java: a thread holding the write lock may acquire the read lock and then release the write lock, a downgrade, so it keeps reading a state that no writer can change in between. C++ std::shared_mutex has no downgrade operation; releasing the exclusive lock and then taking a shared one leaves a gap where a writer can get in.

StampedLock: reading without locking at all

Java 8 added StampedLock, built around one idea: for a tiny read, do not take any lock. Ask for a stamp (a version number), read the fields into local variables, then ask the lock whether any writer got in since that stamp. If none did, the copies are consistent and you are done, having written nothing to shared memory. If one did, throw the copies away and take a real read lock. That is an optimistic read.

The same idea in C++ is a seqlock: a counter that the writer makes odd before writing and even after. A reader that sees the same even value before and after its read knows no write overlapped it. There is one sharp C++ difference. In Java, reading a field while a writer changes it is allowed (you may get a stale or mixed value, which validate then catches). In C++, that overlapping read is a data race and therefore undefined behavior, even if you discard the value afterwards. So in a C++ seqlock the protected fields must themselves be atomics.

Rules that come with StampedLock: it is not reentrant (a second write lock in the same thread always self-deadlocks, and so can a second read lock once a writer is waiting), it has no condition variables, and code between tryOptimisticRead and validate must only copy fields into locals: no following pointers you just read, no calling methods on the copies, nothing that could loop or throw on inconsistent values. Use it for small groups of fields on very hot read paths, and treat it as an optimization you measure, not a default.

The better tool for read-mostly data: immutable snapshots

For data that is read constantly and changed rarely (configuration, feature flags, a routing table), there is a design that beats every lock: keep the data in an immutable object, and on every change build a new copy and publish it with a single reference swap. Readers just read the current reference: no lock, no shared write, no bookkeeping. Writers pay for a copy, and still serialize with each other. That is copy-on-write.

A reader that grabbed the old snapshot keeps using a consistent old version while a writer publishes a new one, and the old copy is freed when the last reader drops it (by the garbage collector in Java, by the shared_ptr count in C++). In C++20 the pointer itself can be a std::atomic<std::shared_ptr<const Map>>, which removes the small pointer mutex; libstdc++ and MSVC provide it, but libc++ (the default standard library on macOS) does not yet, which is why the version above guards the pointer copy with a mutex held only for the few nanoseconds a pointer copy takes. Before C++20 the same idea was written with the free functions std::atomic_load and std::atomic_store on a std::shared_ptr (deprecated in C++20); interviewers who know C++17 may expect that spelling. Neither form is guaranteed lock-free: libraries typically use a small internal lock. The full treatment is in copy-on-write and snapshots.

Worked example: a client wrapper with init, requests and close

A reported Rubrik phone screen asked for a wrapper around a client with init(), request() and close(). Init is exclusive and blocks everything else; requests may run concurrently once init has succeeded; close must wait for in-flight requests to finish, and must happen once. Commenters on that report reached for a read-write lock, and it fits the rules exactly:

  • request() holds the read lock for the whole call: requests overlap freely.
  • init() and close() take the write lock: they run alone, and close() cannot get it until every in-flight request has released its read lock. The draining comes for free.
  • Two flags, initialized and closed, guarded by the same lock, make init idempotent, make close run once, and reject requests outside the open window.

Two things to say out loud. First, a request holds the read lock while it does I/O, which normally breaks the "no slow work under a lock" rule; here it is deliberate, because the read lock is how close knows a request is in flight, and readers do not block each other. Second, close depends on the lock's policy: on a reader-preferring implementation, constant request traffic could keep close waiting forever. The fix is a closing flag (an atomic set before close asks for the write lock) that new requests check right after acquiring the read lock, so they fail fast and the readers drain.

Common mistakes

  • A read-write lock for tiny reads. For a 50 ns map lookup the read lock's own bookkeeping dominates. Measure; often a plain mutex, a concurrent map or a snapshot is faster.
  • A read lock for a "read" that writes. An LRU cache's get() moves the entry to the front of the recency list, so it modifies shared state and needs exclusive access. Read locks protect only true reads.
  • Upgrading in place. Asking for the write lock while holding the read lock hangs. Release, take the write lock, re-check.
  • Forgetting the re-check after "upgrading". Between releasing the read lock and getting the write lock, another thread may have done the same work. Without the re-check you load or insert twice.
  • Using a value from an optimistic read before validating. Copy into locals, validate, and only then use the copies. In C++, also make the fields atomic.
  • Assuming a policy. Reader or writer preference differs between libraries. If a bounded wait for writers matters, choose a lock that guarantees it, or design around it.

In the interview

Read-write locks come up in three ways. As a design choice after "make it thread-safe": a Google L5 report includes "one thread updates the flight prices, many threads read them", an Apple candidate used ReentrantReadWriteLock to make an LRU cache thread-safe (mind the LRU trap in the quick check), and a Microsoft candidate asked for a key-value store without library APIs wrote a reader-writer lock by hand. As a build-it question: Rubrik has asked candidates to implement a reader-writer lock, and its searcher, inserter and deleter problem is a readers-writers variant. And as theory: "when would a read-write lock be slower than a mutex?"

A read-write lock lets readers overlap, but every read acquisition is still an atomic write to the lock's shared state, so it only wins when read critical sections are long enough for that overlap to matter and writes are rare. For short reads on a hot path, a plain mutex or a concurrent map is often faster, and for read-mostly data I prefer an immutable snapshot that writers replace atomically, so readers take no lock at all.
I would also check the policy: with reader preference a steady stream of readers can starve writers, and nobody can upgrade a read lock to a write lock in place; I release, take the write lock, and re-check.

Follow ups to expect: "Why does upgrading deadlock?" (two upgraders wait for each other; even one waits for itself), "How would you make it fair?" (serve arrivals in order, batch consecutive readers), "Would you use a read lock for LRU get?" (no, it reorders), and "What is StampedLock's optimistic read?" (read without locking, validate the stamp, fall back to a read lock). For the build-it version (Rubrik, Microsoft), know the shape before you start: a mutex, a condition variable, a reader count, a writer-active flag and, for writer preference, a count of waiting writers; readers wait while a writer is active or waiting, a writer waits while anyone is inside. You will write it in build it yourself: read-write lock and reusable barrier.

Senior depth

  • Bookkeeping is the hidden cost. A read-write lock turns every read into a write to one shared cache line. On a many-core machine that line becomes the bottleneck long before the protected data does. Scalable designs avoid shared writes on the read path entirely: snapshots, per-core structures, or optimistic reads.
  • Holding a read lock across slow work blocks writers. A long report holding the read lock delays every writer, and with writer preference, every reader that arrives after that writer too. The read lock is still a lock.
  • Taking the read lock twice is a trap in C++. A function that holds a shared lock and calls a helper that takes it again usually works, until a writer queues between the two acquisitions. On libc++ a waiting writer blocks new shared acquisitions, so the second lock_shared waits for the writer, which waits for the first: a two thread deadlock that no test without writers will show. On Linux, glibc's default reader preference happens to let it through, but the standard makes it undefined behavior everywhere. Java's ReentrantReadWriteLock lets a thread that already holds the read lock back in even when a writer is queued; the per-thread hold count is how it knows, and part of why it costs more than a mutex.
  • ReentrantReadWriteLock limits. It packs the read count and the write count into one 32-bit state, 16 bits each, so each can count up to 65,535 holds; past that it throws an Error. Only the write lock supports newCondition().
  • Snapshots trade memory for reads. Each write copies the structure, so copy-on-write suits small or rarely changed data. For large maps with frequent writes, a concurrent map with per-bin locking is the better fit (lock striping is the next lesson; concurrent hash maps have their own lesson in module 10).

Key takeaways

  • Many readers together, or one writer alone. Java: ReentrantReadWriteLock. C++17: std::shared_mutex with std::shared_lock and std::unique_lock.
  • It wins for long, frequent reads and rare writes. For short reads, the lock's own atomic bookkeeping can make it slower than a mutex.
  • Reader preference can starve writers; policies differ by library. Know yours or design around it.
  • Never upgrade in place: release, take the write lock, re-check. Downgrading (Java) is safe.
  • Optimistic reads (StampedLock, seqlocks) read without locking and validate a version; in C++ the fields must be atomic.
  • For read-mostly data, an immutable snapshot swapped atomically usually beats any lock.

Quick check

Answer each question, then read why. Your score is saved for your module test.

For which workload does a read-write lock most clearly beat a plain mutex?
Why. The win comes from long reads overlapping. With 50 ns reads, each read lock acquisition and release (atomic writes to one shared cache line) costs about as much as the read, so the lock itself becomes the bottleneck. A counter is all writes. "More reads than writes" alone is not enough.
A thread holds the read lock of a read-write lock that does not support upgrades, and asks for the write lock without releasing the read lock. No other thread is involved. What happens?
Why. Both ReentrantReadWriteLock and std::shared_mutex behave this way. Neither reports an error: Java simply queues the write request behind the readers, and in C++ it is formally undefined behavior, which libc++ and glibc both turn into a hang. The safe pattern is to release the read lock, acquire the write lock and re-check the state.
A thread-safe LRU cache uses a read lock in get() and the write lock in put(). What is wrong?
Why. In an LRU cache every hit is a write to the recency list. Two readers moving nodes at the same time corrupt the list. Options: one exclusive lock with short critical sections, sharding by key with an LRU per shard, or approximate recency that is updated without moving nodes on every hit.
You implement "upgrade" as: release the read lock, then acquire the write lock. What must you do next?
Why. Between the release and the acquire, other threads can run, including writers that make the same decision. Without a re-check, two threads both load the missing entry or both apply the same change. It is check-then-act again.
An optimistic read copies x and y into locals, then the version check (validate, or the seqlock counter) says a writer got in. What should the reader do?
Why. A failed validation means the copies may come from different writes, so together they may break the invariant. The data is fine; only this reader's copies are suspect. Retry optimistically a few times, or take the read lock.
Java onlyWhich of these does ReentrantReadWriteLock support?
Why. Downgrading is explicitly allowed and is the way to keep reading a state you just wrote without letting a writer in. Upgrading deadlocks, readLock().newCondition() throws UnsupportedOperationException, and like any reentrant lock, it must be released by the thread that acquired it.
C++ onlyWith a std::shared_mutex rw, which guards should readers and writers use?
Why. std::shared_lock calls lock_shared(), so many readers may hold it at once. std::unique_lock and std::lock_guard call lock(), the exclusive mode. The mutex cannot guess intent: a writer under a shared lock would race with other readers.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
As in a reported Google L5 follow up: one thread updates flight prices, and many threads read prices to answer queries. Design the synchronization, and compare a read-write lock with the alternative you would pick.
Model answer

The access pattern is one writer, many readers, short reads. A read-write lock would work: readers share the read lock, the updater takes the write lock. But each lookup is short, so every read would pay an atomic write to the lock's shared state, which becomes a contended cache line with many reader threads, and a steady read load could delay the writer depending on the lock's policy.

I would use an immutable snapshot instead. The prices live in an immutable map behind a volatile reference (Java) or a shared_ptr to a const map (C++). Readers load the reference once per query and read without any lock, which also gives each query a consistent view even if it looks up several routes. The single writer builds the next version and publishes it with one reference swap; old versions are freed when their last reader is done. If updates are frequent and the map is large, copying the whole map per update gets expensive; then I would batch updates into one new snapshot every few milliseconds, or move to a concurrent map with per-key atomic values if queries do not need a consistent view across keys. I would state which consistency the queries need before choosing.

Explain
A teammate replaces a synchronized block around a HashMap lookup with a ReentrantReadWriteLock read lock "because 95 percent of calls are reads", and latency gets worse under load. Explain why, and what you would do.
Model answer

The critical section is a single hash lookup, tens of nanoseconds. Acquiring and releasing the read lock are each atomic read-modify-write operations on the lock's shared state, plus the lock tracks each reader's hold count through a thread-local. With many cores reading at once, the cache line holding the lock state moves between cores on every acquisition, so the lock's bookkeeping costs more than the lookup it protects, and all readers serialize on that cache line anyway. The read-write lock adds overhead without adding real parallelism.

I would measure, and then pick by workload: a ConcurrentHashMap (lock-free reads, per-bin locking for writes) for a map with regular writes, or an immutable snapshot swapped atomically if writes are rare, so reads take no lock at all. A read-write lock is for long reads, such as scanning a large structure, where letting readers overlap is worth its bookkeeping.

Write code
Write V getOrLoad(K key) for a cache guarded by a read-write lock: hits must run in parallel, misses load the value once, and nothing may deadlock.
Model answer

Take the read lock and return on a hit. On a miss, release the read lock (never upgrade in place), take the write lock, look again because another thread may have loaded it in the gap, and only then load and insert.

Points an interviewer will look for: the read lock is released before asking for the write lock; the re-check under the write lock; the loader running under the write lock blocks all readers, so for slow loaders you would load outside the lock and use a per-key future (single-flight) so concurrent misses for the same key share one load; and in Java, if the loader can return null, use containsKey or a sentinel, since get returning null cannot distinguish "absent" from "loaded null".

How a senior would say it
It depends on how long a read takes, not just on the read ratio. A read-write lock lets readers overlap, but every read acquisition and release is still an atomic write to the lock's shared state. With many cores, that cache line bounces between them on every read. So if the read is a fifty nanosecond map lookup, the bookkeeping costs more than the work, and a plain mutex can actually be faster. The read-write lock wins when reads are long, say a scan of a big in-memory index, and writes are rare, because then letting readers run together really buys parallelism. For short reads with regular writes, I would use a concurrent map. For read-mostly data like configuration, I would use an immutable snapshot: writers build a new copy and swap one reference, and readers take no lock at all. If I do pick a read-write lock, I check its policy, because steady readers can starve writers on some implementations, and I never upgrade in place. Either way, I measure under real contention before and after.

Likely follow up: When would StampedLock's optimistic read beat all of these, and what does it cost you?

Out loudabout 80 s
"Why can't you upgrade a read lock to a write lock? Walk me through what goes wrong, and show me the safe way."
What a strong answer covers
  • One thread: the write lock waits for every reader to leave, including the thread itself, so it waits forever
  • Two threads: both hold the read lock, both ask for the write lock, and each waits for the other's read lock
  • A lock that offers conversion must refuse at least one: tryConvertToWriteLock returns 0 unless the caller is the only reader
  • Safe pattern: release the read lock, take the write lock, and re-check, because another thread may have acted in the gap
  • Downgrading is fine in Java; C++ std::shared_mutex has no downgrade
How a senior would say it
Because the write lock waits until no thread holds the read lock, and that includes you. Even alone, a thread that holds the read lock and asks for the write lock waits for itself forever. With two threads it is a textbook deadlock. A and B both hold the read lock. A asks for the write lock and waits for B's read lock to go. B asks for the write lock and waits for A's. Each holds exactly what the other needs. So any lock that offers conversion has to refuse someone: Java's StampedLock converts only when you are the sole reader, and otherwise returns zero. The safe pattern is to release the read lock, take the write lock, and check the condition again, because another thread may have done the same work in the gap. In a cache, that is the second lookup under the write lock before loading. Going the other way is fine in Java: take the read lock while holding the write lock, then release the write lock.

"Here is a symptom: on a busy server, config updates take minutes to show up. The config sits behind a read-write lock, and a thread dump shows the updater blocked on the write lock while request threads hold the read lock. What do you check, and what do you change?"
What a strong answer covers
  • Name it: writer starvation; the writer needs a moment with zero readers, and overlapping readers never give it one
  • Check the policy: glibc's default under libstdc++'s std::shared_mutex prefers readers; Java's default makes new readers wait once a writer is first in the queue
  • Check how long readers hold the lock: a read lock held across slow work, such as a remote call, makes the writer wait for all of it
  • Quick fixes: a writer-preferring or fair lock, and slow work moved out of the read section
  • Better design for config: an immutable snapshot swapped atomically, so readers never lock and the writer never waits for them
How a senior would say it
This looks like writer starvation. The writer needs a moment with zero readers, and under steady traffic the readers keep overlapping, so that moment never comes. First I would check the lock's policy, because it differs by library. On Linux, libstdc++'s std::shared_mutex sits on glibc's read-write lock, which prefers readers by default, so a stream of readers can hold off a writer indefinitely. Java's default lock makes new readers wait once a writer is first in the queue, so there I would look at the second cause: how long each reader holds the lock. If request threads hold the read lock across slow work, like a remote call, the writer waits for every one of them to finish. The quick fixes are a writer-preferring or fair lock, and moving slow work out of the read section. But for config, the better design is an immutable snapshot. The updater builds a new copy and swaps one reference, readers grab the current reference without any lock, and the next request sees the update at once.
