Ordered parallel map

Executors and asyncmedium30 min

Call a slow service for every item in a list, never more than K calls at once, and hand back the results in the original order. It is the everyday shape of fan-out, and the tempting answers (a thread per item, or batches of K) each fail in a way an interviewer will point at.

The task

Write map(inputs, fn, K): apply fn to every input and return the results in input order.

  • At most K calls to fn run at the same time, and when there is enough work, K really do run at the same time.
  • Use at most K threads in total; the calling thread may be one of them. Do not start a thread per item.
  • A worker that finishes a call starts the next item at once: one slow item must not hold up the others.
  • If a call throws, start no new calls, wait for the calls still running, then throw that exception (Java: that exception or one caused by it; C++: rethrow it).
  • map may be called by several threads at once, so it must not keep state between calls. fn itself is safe to call from several threads.

Rules: library executors, fork/join and parallel streams are banned, because the bounded fan-out is what you are building. Threads, locks, atomics and semaphores are all fine.

Where it comes up: Uber front-end loops asked for a task queue that runs at most K tasks at once (in TypeScript), an Uber phone screen asked for a throttler with a concurrency limit, and the same shape sits inside every crawler, batch job and "call N services" question.

What the tests check

  • 200 inputs (120 in C++) with random delays come back in input order; an empty input and a K larger than the input both work.
  • With K = 4, exactly 4 calls run at once and never more, on at most 4 different threads.
  • Item 0 takes 300 ms and 39 others take 10 ms each, with K = 4: at least 30 of the fast items finish while the slow one runs.
  • Item 5 throws: the exception comes out of map, few calls ever start, and none is still running when map returns.
  • Four threads call map at the same time and each gets its own correct results.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Pipelines, fan-out, fan-in and batching

Order is the easy part: give every input its own result slot, results[i], and have whoever processes item i write slot i. Then the only shared decision is "which item do I take next".
Start K workers (the caller can be one). Each one loops: take the next index from a shared atomic counter (getAndIncrement, fetch_add), stop when it passes the end, call fn, store the result. A worker is never idle while work remains, and each index is taken exactly once.
Failure: on the first exception, record it (a compare-and-set, or under a mutex) and set a stop flag that workers check before taking another index. Join every worker before returning or throwing: the join both guarantees that nothing is still running and makes the result slots visible to the caller.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

The input is a stream of a million items, and results must be emitted in order as soon as possible, with bounded memory.
Use a window. Item i may start only when item i minus K has been emitted, so at most K calls run and at most K results wait in a reorder buffer; the emitter waits for the head of the window, emits it, and that frees one slot. The price is head-of-line blocking: one slow item stalls emission (but not the calls) until it finishes. This is the order-preserving mapAsync of Akka Streams and buffered in Rust's futures crate.
The calls are network requests, so K should be 500. Does the design change?
Five hundred platform threads cost memory and context switches, so with Java 21 the idiomatic answer becomes a virtual thread per item with a Semaphore of K: virtual threads are cheap enough that "a thread per item" is now the right shape, and the semaphore still bounds the calls in flight. In C++, use asynchronous I/O or an event loop instead of threads. Size K with Little's law: calls in flight equal throughput times latency.
On failure, stop the calls that are already running.
Threads cannot be killed safely, so cancellation is cooperative: in Java interrupt the workers and make fn respond to interruption; in C++ pass a std::stop_token into fn and request stop on failure. map must still wait for the calls to return before it throws.
Return partial results instead of failing everything.
Change the result type to carry either a value or an error per item (a small result class, std::expected in C++23, or a pair), never throw from map, and let the caller decide. Add retries with backoff per item if the failures are transient, and only for idempotent calls.
The service allows 100 requests per second, not K at a time. What changes?
That is a rate limit, not a concurrency limit. A semaphore or K workers bound how many calls overlap; a rate limit bounds how many start per second, so each worker takes a token from a token bucket before calling. You often need both: the rate the service accepts and the concurrency your machine can afford. See rate limits versus concurrency limits.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Work claiming with an atomic counter. K workers, one of them the caller, repeatedly claim the next index with fetch_add and write the result into that index's slot. The invariants: every index is claimed by exactly one worker, and every slot is written by exactly one thread. So the results need no lock at all, the order is the input order by construction, and at most K calls run because there are only K workers.

Why each line is there

  • fetch_add on one counter. Claiming is the only shared decision, and an atomic increment makes it with no lock and no chance of two workers taking the same index.
  • A slot per index. Workers never write the same memory, so there is no data race on results, and no sorting afterwards.
  • The caller works too. With K workers including the caller you start only K minus 1 threads, and the caller is not idle while it waits.
  • A stop flag checked before each claim. After the first failure no new call starts; the calls already running finish on their own.
  • Join before returning or throwing. "No call still running" is the contract, and the join is the happens-before edge that makes every slot written by a worker visible to the caller.
  • No static or shared state. All of it lives in the call, so concurrent calls to map cannot interfere.

Cost and trade-offs

Overhead is one atomic increment per item plus starting K minus 1 threads per call. For many short calls, the thread start-up dominates, and a long-lived pool shared by all calls (with per-call counters) is better. For calls that mostly wait on the network, K should be far above the number of cores, which is where virtual threads or asynchronous I/O take over.

How to say it in the interview

I will preallocate one result slot per input, so order is free. Then I start K workers, using the calling thread as one of them, and each loops claiming the next index from an atomic counter, calling fn, and writing that slot. A free worker always grabs the next item, so one slow call never stalls the rest, and there are never more than K calls or K threads. On the first exception I record it and set a stop flag that workers check before claiming, then I join everyone, so nothing is running when I rethrow, and the join also publishes the results. For a stream of inputs I would switch to a window with a reorder buffer of K.
