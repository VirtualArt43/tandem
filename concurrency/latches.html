Latches: wait until N things happen

Coordinate one-shot events and test start gates, publish results safely, handle failures and timeouts, and distinguish idle waits from fixed-batch completion.

Asked atRubrikUber
Before this:Semaphores: permits as a resource limitCreating, starting and joining threads

A huge amount of concurrent code ends with "wait until all of these are done". A latch is the purpose-built tool for that one-shot fan-in, and in tests it provides a start gate that increases the chance of overlapping operations.

In plain words

A school bus is taking 40 students on a trip. The teacher holds a list and ticks a name as each student climbs aboard. The bus leaves only when all 40 are ticked. Once it has left it does not come back for anyone: the list is used once and thrown away.

A race works the same way in reverse. All the runners wait at the line, and one starting pistol releases them together. Count down to zero, then open for good: that is a latch.

What a latch is

A latch holds a count that only goes down:

  • countDown lowers it by one. Events, not thread identities, are counted: one thread may report several events, but every event must be counted exactly once.
  • await blocks until the count reaches zero.
  • Once the count is zero, the latch is open forever: current waiters become eligible to proceed and future waits do not block on the count. It cannot be reset.

Like the other synchronizers, a latch also publishes memory: writes before the count downs that open it happen-before reads after a successful completion wait. Give each worker its own array element and stop writing that element before counting down. A timeout returning false, an interrupted wait, writes after the countdown, or extra Java count downs after zero do not establish this publication guarantee.

Java

java.util.concurrent.CountDownLatch. new CountDownLatch(n) accepts a nonnegative int (zero starts open); countDown() (once the count is zero, extra calls do nothing); await(), which blocks and throws InterruptedException on interruption, clearing interrupt status; await(timeout, unit), which returns true if the count reached zero and false if the time ran out; and getCount(), for logging and monitoring only.

C++

C++20 std::latch, in <latch>. std::latch done(n); requires a count from 0 to std::latch::max(). Its methods are count_down(std::ptrdiff_t update = 1), wait(), try_wait() and arrive_and_wait(std::ptrdiff_t update = 1) (count down, then wait, the usual call for threads that are both counted and waiting). Three differences from Java matter. There is no timed wait. try_wait() is allowed to return false spuriously, with very low probability, even when the count is zero. And counting down below zero is undefined behavior, where Java just ignores the extra call. Before C++20, use a mutex and condition variable (built in build it yourself), or, for a one-event gate, a std::promise<void> with a std::shared_future<void> for the waiters. A latch is neither copyable nor movable; do not destroy it while callers can still access it.

API references: Java 21 CountDownLatch and the C++20 latch specification.

Use one: fan-in

Split work across workers, then wait for all of them. Each worker writes its result into its own slot and counts down; the coordinating thread waits for the latch and then reads every slot.

"Why not just join() the threads?" is the natural question, and when you created the threads yourself and want them finished, join is fine. A latch is for the other cases:

  • You did not create the threads, for example tasks running in a pool, which you cannot join.
  • You wait for events, not for threads to end: "all 3 services have finished starting" while their threads keep running afterwards.
  • Several observers need the same milestone: any number can await one latch. Thread creation ownership is not itself a restriction on joining; C++ callers must not concurrently join the same thread object.
  • You need a timed event wait, which Java supports. Java thread joins also have timed overloads; C++ standard join and std::latch::wait do not.

Use two: a start gate for tests

Starting and scheduling a thread can take longer than the short operation you want to test; the cost depends on the runtime and machine. If a test simply starts 8 threads that each call increment() once, each thread may finish before the next one even starts, and a race-prone class passes. A start gate improves the test: every thread checks in, then waits on a gate with count 1. Once everyone has checked in, the coordinator opens the gate. This makes all operations eligible to run, but does not guarantee simultaneous execution or even that every worker has parked yet.

The ready, go and finished shape is a useful concurrency test pattern; the C++ example uses joins for the finish step. An Uber L4 candidate reported using CountDownLatch unit tests in a machine-coding interview. A gate increases contention, but passing tests does not prove correctness for every schedule: repeat runs, assert invariants and use race detection.

In Java application code, CompletableFuture.allOf(...) or ExecutorService.invokeAll often replace a manually managed latch. allOf completes with Void, so read individual results separately; invokeAll returns futures whose get() exposes task failures. Latches remain the tool for tests, for start-up gates, and for interviews where the libraries above are banned.

Worked example: when a latch does not fit "wait until complete"

A recurring Rubrik question, reported from 2020 to 2025: implement schedule(task), which returns at once, and waitUntilComplete(), which blocks until every task scheduled so far has finished, usually without ExecutorService. A latch looks perfect, and it is not:

  • The count is unknown up front. A latch needs N at construction, but tasks keep arriving.
  • It is one shot. After the first waitUntilComplete() returns, the next batch needs a fresh latch, and swapping latches while tasks are being scheduled is its own race.

First define the contract. For sequential batches, or a wait for the executor to become idle, use a reusable counter: pending goes up before a task is handed off and down when it finishes, and waiters sleep until zero. A lock and condition variable implement that contract:

This minimal counter assumes outstanding work fits in an int. Each successful started() must have exactly one finished(), including rollback if enqueueing fails. The subtle line is the comment on started(): it must run in schedule(), on the caller's thread, before the task is handed to a worker. If the worker incremented when it began running, awaitIdle() could see zero and return while a scheduled task had not started yet. Java's Phaser can play the same role, as the barriers and phasers lesson shows, and the practice problem builds the whole executor.

Idle is not a fixed submission snapshot. With concurrent submissions, the counter may wait for later work too, or never reach zero. If the contract excludes tasks submitted after the wait began, capture a submission sequence number and track completion of that prefix, or wait on a captured set of futures. A total completed count is insufficient when tasks finish out of order.

Common mistakes

  • countDown outside finally. A skipped countdown can strand the waiter. Record failures and count down in finally, or catch exceptions inside the C++ worker and use scope cleanup. An exception escaping a C++ thread entry calls std::terminate; no countdown wrapper replaces the catch. A timeout cannot stop a stuck worker.
  • The wrong count. A latch sized by threads when each thread counts down per task, or the reverse, either opens early or never opens.
  • Trying to reuse a latch. It is one shot. For repeated rounds use a barrier; for idle, a pending counter; for a fixed submission snapshot, track that batch.
  • Counting down too far in C++. Extra count_down calls are undefined behavior with std::latch, unlike Java.
  • Waiting on a latch you are supposed to count down. A worker that awaits before its own countDown can deadlock the whole group. Use arrive_and_wait in C++, or count down first.
  • Making decisions with getCount(). A positive count can change immediately, and zero says nothing about task success. Use a successful wait for the documented publication guarantee instead of polling a diagnostic snapshot.

In the interview

Latches appear in two ways. As a building block: Rubrik's "schedule tasks, then wait until all finish" (where you build the latch-like piece yourself, often with libraries banned), and fan-in steps in crawlers and parallel processing. And as a testing tool: an interviewer asks "how would you show this is thread-safe?", and the strong answer is a start gate plus many threads plus an invariant check, which is what an Uber L4 candidate did with CountDownLatch tests.

A latch is a one-shot counter: each event counts down, waiters block until zero, and then it stays open. I use it for fan-in when I cannot simply join, for example tasks on a pool, with completion accounting even on failure. Java supports a timed wait; C++ needs another timed mechanism or an external test watchdog. In tests I use a start gate: every thread checks in, waits on a latch of one, and I open it once they have all checked in, increasing the chance of overlap without controlling the scheduler. If the number of events is not known in advance or the wait must be reusable, a latch is the wrong tool; I would first define whether the caller wants idle or a fixed batch, then choose a pending counter or tracked batch completion.

Follow ups to expect: "Latch or barrier?" (one-shot events versus reusable mutual waiting), "What if a worker fails?" (record the failure, count down, and define cancellation; catch C++ worker exceptions), "Can you build one?" (a count, a lock, a condition variable and notifyAll; the next lesson but one).

Senior depth

Completion is not success. The sum example performs only arithmetic and writes distinct slots, so its normal worker path does not throw. For fallible work, give each worker a result and error slot, catch failures inside the worker, then count down. After a successful wait, inspect errors before using results. Cancellation before a queued task starts needs its own exactly-once completion accounting, since the task's cleanup never ran.

A timed-out wait does not cancel anything. It also does not publish a complete results array. Workers may still be writing, so either wait for their termination or use a separately synchronized partial-result protocol. The Java sum demo simply reports timeout and leaves its finite workers running; a service needs an explicit cancellation and cleanup policy. In C++, keep the latch and referenced storage alive until workers can no longer access them.

Watch for pool starvation. If two tasks occupy both threads of a fixed pool while awaiting two queued tasks, the queued tasks can never count down. The same trap affects a ready gate with more participants than available pool workers. Coordinate outside that pool, use separate threads for a test gate, or compose asynchronous completions.

Key takeaways

  • A latch counts down to zero once and then stays open; any thread can count down, any number of threads can wait.
  • Write results and record failures before counting down; a successful completion wait publishes those writes.
  • Use it for fan-in when you cannot join, for start-up gates, and as the start gate in concurrency tests.
  • Java has a timed await and ignores extra count downs; C++ std::latch has no timeout and treats going below zero as undefined behavior.
  • For dynamic work, define idle versus a fixed batch before choosing a pending counter or tracked batch completion.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A latch starts at 3. Thread A calls countDown() twice, thread B calls it once, and the main thread is blocked in await(). When does the main thread proceed?
Why. A latch counts events, not threads. One thread may report several events; waiters are released when the count reaches zero. Each event still needs exactly one countdown, and C++ forbids exceeding the initial count. Neither a latch nor a barrier identifies threads for you; your protocol must account for the intended events or phase arrivals.
A latch counts one completion per worker. One worker's doWork() throws before its countdown; an outer handler catches the failure and exits that worker without counting down. All others count down once. What happens to the coordinator's untimed wait?
Why. Nothing connects a thread's death to the latch: the missing countDown simply never happens. Record failures and ensure completion accounting in cleanup. A Java timed wait can report the stall; C++ needs a separate timed mechanism. The stated catch matters: an uncaught C++ worker exception terminates the process instead.
A batch job uses a latch to wait for 10 tasks. The next batch should reuse the same latch. What is true?
Why. Neither CountDownLatch nor std::latch can be reset. For repeated rounds of the same group, a barrier is reusable; for idle between batches, a counter with a condition variable is. A fixed submission snapshot needs tracking that batch.
A latch starts at 2. Worker A writes 20 to results[0] and worker B writes 22 to results[1], each counting down once afterwards. There are no later writes. After a successful completion wait, what can the coordinator print for their sum?
Why. Latches carry memory effects like locks do: actions before countDown happen-before actions after a successful await. Each worker writes only its own slot, so there is no conflict between workers either.
Java onlydone.await(2, TimeUnit.SECONDS) returns false. What does that mean?
Why. A timed await only bounds how long the caller waits. The caller must decide what to do: report which parts are missing, cancel the work, or retry. Latches have no broken state, and completion may race with the timeout, so workers could already have finished by the time the caller examines the return value.
C++ onlyWhat does this code do?
Why. count_down(n) requires a nonnegative n no larger than the current count. The third call violates that precondition: no wraparound, ignored call or exception is guaranteed. Java's CountDownLatch tolerates extra calls; std::latch does not, so make sure each event counts down exactly once.
Why do concurrency tests usually release their threads through a start gate latch instead of just starting them one by one?
Why. A thread can finish a microsecond-long operation before the next thread has even started, so a buggy class can pass. Opening a shared gate after all workers check in removes the staggered-start dependency, but the scheduler still chooses when each worker runs. It does not make the test deterministic or fix races; it exposes them.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a test helper runTogether(n, task, timeout) that releases n dedicated threads through a common gate. Use one timeout budget for readiness and task completion, and report task exceptions. Does the gate promise simultaneous execution?
Model answer

Assume nonnegative n, a nonnegative practical test timeout, and successful worker creation. Run this helper in an isolated test process: arbitrary stuck code cannot be safely stopped inside a long-lived test runner.

The gate makes tasks eligible together, not simultaneous. Both readiness and completion consume one deadline, so each phase cannot restart the timeout. Java returns false for timeout, propagates coordinator interruption, and reports worker failures after completion; its cleanup requests interruption, which a stuck task may ignore. Daemon status permits JVM exit but does not prevent leftover tasks changing test state, so end the isolated process after failure. C++ uses a condition variable for timed readiness and completion, since std::latch has no timed wait; on timeout it ends the process before local state can be destroyed under live workers.

Explain
When would you use a latch rather than join(), and rather than futures? Give a concrete case for each choice.
Model answer

I use join() when I manage the threads and want them finished: for example a main thread that starts four worker threads for a parallel sum and then joins them. I use a latch when what I am waiting for is a set of events rather than the end of threads I own: tasks running in a pool that I cannot join, three services signalling "started" while their threads keep running, or a timed fan-in in Java. Java also offers timed joins; standard C++ joins and latches do not. Latches are also a useful start gate in tests.

I use futures when each piece of work produces a result or can fail, because a future carries the value or the exception back to the waiter, and CompletableFuture.allOf gives the same fan-in with error propagation. A latch carries no results and no errors: workers have to store results somewhere and record failures themselves. So: join for my own threads, a latch for counting events or for gates, futures for results.

Design
A Rubrik-style question: implement schedule(task) (returns immediately; tasks run on N worker threads) and waitUntilComplete() (blocks until all tasks scheduled so far have finished; may be called many times). Why is a CountDownLatch the wrong tool, and what do you use?
Model answer

A latch needs its count at construction and can be used once. Here tasks keep arriving, so the count is unknown, and waitUntilComplete is called repeatedly, so a one-shot gate would need replacing between batches, which races with concurrent schedule calls.

I keep a pending counter guarded by the same lock as the task queue, with a condition variable "idle". schedule increments pending under the lock before enqueuing, which matters: if the worker incremented when it started running, a waiter could see zero while a task was still queued. Each worker catches and records task failures, then decrements pending in cleanup (so a throwing task still counts) and signals all waiters when it reaches zero. waitUntilComplete waits in a loop while pending is above zero. This is reusable idle waiting. Concurrent later submissions can extend the wait indefinitely. For an exact snapshot, capture a submission boundary and track completion of every earlier task, including out-of-order completions. I would clarify that contract before choosing the counter. Interviewers then usually ask about shutdown, so I would add a closed flag, refuse new tasks after shutdown, and wake idle workers to exit.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Four workers write into an ordinary results array. Can I read it safely after waiting on a latch, or do I still need atomics?"
What a strong answer covers
  • A successful completion wait publishes writes made before the counted events
  • The latch starts at four and each worker writes a distinct element before counting down once
  • A latch does not serialize workers or protect writes after the countdown
  • Timeout or interruption does not provide the successful completion guarantee
  • Record failures separately; completion alone does not mean all results are valid
How a senior would say it
Yes, after a successful completion wait I can read those results without making each element atomic, provided the protocol is correct. I initialize the latch to four. Each worker writes its own array element, then counts down exactly once and stops changing that element. Those writes happen before the coordinator continues from the successful wait. The distinct slots matter because the latch does not serialize workers. If two workers update the same ordinary counter, counting down afterwards cannot repair that race. I also cannot read an unfinished slot safely just because a timed wait returned false, or because my wait was interrupted. I would wait for termination or use separate synchronization for partial results. Finally, completion does not mean success. A worker should record any failure before counting down, and the coordinator checks those failures before treating the array as a valid result.

Likely follow up: What happens if a worker counts down first and only then writes its result?

Out loudabout 60 s
"You say your start-gate test proves the class is thread-safe. Walk me through what it actually proves."
What a strong answer covers
  • A passing test is evidence for exercised schedules, not a proof for all schedules
  • Ready checks in each worker; go prevents operations until everyone has checked in
  • Opening go makes workers eligible but does not promise simultaneous execution
  • Check invariants, capture failures and bound readiness and completion waits
  • Avoid a pool smaller than the gate's participant count, which can deadlock before readiness
How a senior would say it
A passing test is evidence, not a proof that the class is thread-safe under every schedule. I use a ready counter so each worker checks in, then a gate that prevents the tested operation from starting until the coordinator opens it. That removes the staggered launch as a reason for operations never meeting. It does not force simultaneous execution; the scheduler can still serialize them. After release I check the invariant, such as exactly one winner or no lost items, capture worker failures, and put readiness and completion under a deadline. I repeat with different inputs and use a race detector where available. I also use dedicated threads for this gate. If eight tasks must check in but only two pool workers exist, the first two can block at the gate while the other six never run. That would test a deadlocked harness instead of the class.

Likely follow up: How would you force a particular check-then-act interleaving without relying on sleeps?

Out loudabout 75 s
"Implement wait until all submitted tasks finish. Why isn't a latch enough, and what contract do you need me to clarify?"
What a strong answer covers
  • A latch has a fixed initial count and opens once, so dynamic reusable submission needs another design
  • Clarify waiting for idle versus the tasks submitted at the start of the wait
  • For idle, increment pending before handoff and decrement exactly once on completion or rejected handoff
  • Guard pending and wait in a predicate loop, notifying all at zero
  • For a snapshot, track a submission boundary and out-of-order completions; a total count is insufficient
How a senior would say it
A latch is useful for a fixed batch, but it does not directly model continuously arriving tasks and repeated waits. I would first clarify whether you want the executor to become idle or want only the tasks submitted before this call to finish. For idle, I keep a pending count under a mutex. Submission increments it before making the task visible to workers, and a failed handoff rolls that increment back. A worker records success or failure and decrements exactly once. Waiters check for zero in a condition-variable loop, and the transition to zero wakes everyone. That design is reusable, but later submissions can extend the wait forever if the executor never becomes idle. For a fixed snapshot, I capture a submission sequence boundary and track completion of every task through that boundary, or capture their futures. A total completion count is not enough: later short tasks could finish while an earlier slow task is still running. The contract determines which state I need to track.

Likely follow up: What happens if a worker calls this wait while its own task is still counted as pending?
