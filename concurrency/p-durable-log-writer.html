Durable log writer with group commit

Concurrent systemssenior50 minDatabricks system programming round (EventWriter, log writer)Databricks

The most reported Databricks concurrency question. Many threads append small events to one file, and each append may only be acknowledged once the event is on disk. The naive answer is correct and hopelessly slow; the good answer is the same trick every database uses: let one fsync carry many events.

The task

Build a thread-safe log writer over a disk that you are given:

  • append(event) queues the event and returns a future at once. The event is written as its bytes followed by a newline. The future completes only after the event is durable, that is, after an fsync that started after the event's bytes were written.
  • Events reach the file in the order their append calls took effect. If one append returns before another starts (in any threads), its event comes first.
  • Back-pressure: at most maxPending events may be appended but not yet durable. append blocks while that many are outstanding, and only then: when events become durable, every blocked append that now fits goes ahead.
  • flush() returns once every event appended before the call is durable and its future is complete. It is a barrier, not a drain: events appended after the call began do not hold it up, so it returns even while other threads keep appending. Several threads may flush at once.
  • close() stops accepting events: later append calls throw, and so do calls blocked by back-pressure, which close wakes at once instead of leaving them until the disk next finishes an fsync. It then makes every accepted event durable, completes their futures, stops any thread you started, and only then returns. Calling it again, even from another thread while the first call is still running, is harmless and returns under the same conditions. In C++ the destructor closes.
  • Complete the futures without holding your lock. In Java a callback attached to a future (thenRun) runs on the thread that completes it, and other threads must still be able to append while it runs.

Disk.write is fast: it only copies into the operating system's cache. Disk.fsync is slow (milliseconds) and makes durable only the bytes written before it started.

Worked example: why batching is the whole game

Say an fsync takes 3 ms. If every append does its own write and fsync under a lock, the log manages about 330 events a second no matter how many threads call it, because the fsyncs run one after another. If instead one thread writes and syncs whatever has piled up while the previous fsync ran, then with 8 busy producers each fsync carries dozens of events, and the same disk acknowledges thousands of events a second. The latency of one event is still about one or two fsyncs; the throughput is what changes.

What the tests check

  • One producer: three events land in order, and the whole file is durable when their futures complete.
  • A future must not complete before an fsync covers its event (the fake disk tracks exactly which bytes are durable).
  • Stress: 8 producers append 250 events each with an fsync of 3 ms. Every event appears exactly once, each producer's events keep their order, no future completes early, and the whole run uses at most 200 fsyncs for 2000 events and finishes well within 3 s.
  • Back-pressure: with maxPending 8, never more than 8 events are appended but not durable.
  • Back-pressure step by step, on a fake disk that holds each fsync until the test releases it: with maxPending 4 and 4 events outstanding, 4 more appends all block; when one event becomes durable exactly one of them goes ahead; when the next fsync makes several events durable, every blocked append that fits goes ahead.
  • close() while two appends are blocked by back-pressure and an fsync is held: both appends throw at once, two threads call close at the same moment, neither call returns before the held fsync finishes, and afterwards every accepted event is durable and nothing rejected reached the file. No future completes while its fsync is held.
  • flush() returns only when every earlier future is complete.
  • flush() as a barrier, with a held fsync: two threads flush at once; neither returns before the events appended before the calls are durable and their futures complete (in Java one of those futures has a slow callback, in C++ one batch holds 400 futures); both return while an event appended after the calls began still waits for its fsync.
  • close() while 4 producers are appending: every accepted event is durable and its future complete when close returns, every producer then gets an exception from append, nothing rejected reaches the file, a second close is harmless, and (in Java) no thread you started is left running.
  • A slow write: the test holds the first write. An append that starts after the first append returned must still reach the file after it (a second writer thread fails this), and no future may complete before an fsync that started after its bytes were written.
  • Two threads taking turns: the file order must match the real time order of the appends.
  • In Java, a callback on a future waits for another thread's append; completing futures while holding your lock fails this.
  • In C++, destroying a writer without calling close still makes every event durable, and ThreadSanitizer must stay quiet throughout.

Taught in: A concurrent, ordered, durable log writer

Open them one at a time. Each one gives away a little more.

Do not let producers touch the disk. They only put the event in a queue (under a lock) and return a future. One background writer thread owns the disk, which makes the file order equal the queue order for free.
The writer loop: wait until the queue is non empty or closed; take everything in the queue; release the lock; write it all with one write and one fsync; complete the futures; take the lock again to record progress and wake blocked producers. While an fsync is running, new events pile up, so the next batch is bigger exactly when load is high. That is group commit, with no timers.
Count two numbers under the lock: appended and finished (futures completed). Back-pressure is while (appended - finished >= maxPending) wait. flush remembers target = appended and waits until finished >= target. close sets closed, wakes the writer and every blocked producer, then joins the writer, which exits only when the queue is empty.
Complete the futures outside the lock: in Java, callbacks attached to a CompletableFuture run on the thread that completes it. In C++, two threads must not join the same std::thread, so guard the join if close can race with itself or with the destructor.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

What durability guarantee can append really give?
Only that the bytes reached stable storage as far as the operating system and the device report. fsync (or FileChannel.force) asks the kernel to flush its cache and the device to flush its write cache; a device that lies about its cache, or a missing fsync on the directory after creating the file, can still lose data. Say what you rely on: "acknowledged means fsync returned after the bytes were written".
What if fsync fails?
Fail the futures of that batch, and stop the log: fail every later append too. After a failed fsync the kernel may already have dropped the dirty pages and cleared the error, so retrying the fsync can report success while the data is gone. PostgreSQL learned this in 2018 and now treats an fsync failure as a crash and recovers from its write ahead log.
The disk is idle most of the time. Would you add a timer, like "flush every 5 ms or every 100 events"?
Not for correctness: the writer thread already syncs as soon as there is work, and batches grow by themselves under load. A small delay ("wait up to 1 ms for more events before syncing") can raise throughput further at the cost of latency, which is a tuning knob, not a requirement. Size caps on one batch keep a single write bounded.
Why a background thread rather than letting a producer act as the leader for its group?
Leader based group commit (the first producer to find no fsync running becomes the writer for everything queued, and the others wait) avoids a dedicated thread and a handoff. It is what many databases do. It is harder to get right: you need a "sync in progress" flag, a way to hand leadership on, and care that the leader's own latency includes other people's events. The background writer is simpler to explain and to shut down.
How would you test this for race conditions?
A fake disk that records exactly which bytes were durable at each moment, so a future that completes early is caught. Many producers with unique event ids, then check exactly once, per producer order, and counts of writes and fsyncs. Run the C++ build under ThreadSanitizer. Then make the timing exact: a fake disk whose fsync waits until the test releases it lets you freeze the system between two fsyncs and assert precisely who is blocked, who went ahead and what is durable. Test shutdown while producers are blocked by back-pressure, which is where most hangs hide.
A user's callback calls flush(). What happens?
In Java, a callback attached before the future completed runs on the writer thread, in the middle of the batch the writer is completing. flush waits until the writer finishes that batch, and the writer is the thread now waiting: a self deadlock. An append from a callback deadlocks the same way when the log is full. Either document that callbacks must not wait on the log, or complete the futures on another executor (for example CompletableFuture.runAsync(() -> f.complete(null), pool)), which costs a thread hop per batch but keeps user code off the writer thread.
Databricks (2026): the API is a fire and forget log(level, msg) with no future, and it must not block producers for long. What changes?
log only enqueues and returns, and the same writer thread batches as before but has no futures to complete, so flush() becomes the only way for a caller to learn that earlier messages are durable, and close() must still drain everything. Keep the critical section tiny: format the message before taking the lock. The real decision is what log does when the queue is full: block (right for audit events), drop and count the drops (acceptable for debug logs, never silently), or fail fast. A failed fsync cannot be reported to a caller that is gone, so record it and surface it from flush, close or a health check.
Databricks (2026): start with a logger that writes synchronously, then make it multithreaded with ordered writes. How do you evolve it?
Step one is the obvious answer: one lock around write and fsync. It is correct and ordered, and it allows one fsync per message. Step two moves the I/O out of the lock: producers enqueue under a short lock and one writer thread drains the queue, so order comes from the queue. Step three takes the whole queue each time, with one write and one fsync per batch. Step four adds the futures or flush for durability, back-pressure and close. Say why each step exists: the lock serializes the I/O, the queue separates accepting from persisting, and batching spreads one fsync over many events. Keep a single writer: two writers would each need to order their writes against the other.
What should back-pressure do instead of blocking?
Options are block (as here), fail fast with an error the caller can retry, block with a timeout, or drop low priority events. A log of audit or transaction events must not drop; a debug log might. Blocking is the safe default because it slows producers to the speed of the disk instead of growing memory without bound.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Separate accepting from persisting. Producers do the cheap part under a lock: put the event in a queue, count it, return a future. A single writer thread does the expensive part with no lock held: write and fsync. Because the writer takes the whole queue each time, every fsync covers everything that arrived during the previous fsync. That is group commit, and it turns "one event per fsync" into "one batch per fsync".

Invariants

  • File order equals queue order, which equals the order in which append took the lock. That order is consistent with real time.
  • A future completes only after the fsync that covered its batch returned.
  • appended - finished is the number of events accepted but not yet acknowledged, and it never exceeds maxPending.
  • After closed is set no event enters the queue, and the writer exits only when the queue is empty, so close (which joins it) returns after every accepted event is settled.

Why each primitive

  • One lock guards the queue, the counters and the flags. It is never held during I/O.
  • Three conditions for three kinds of waiter: producers wait for room, the writer waits for work, flush waits for progress.
  • A future per event (CompletableFuture, or std::promise and std::future) lets the producer choose: wait now, wait later, or attach a callback.
  • join in close is what makes "close returns after everything is durable" true, and it leaves no thread behind.

Pitfalls

  • Write and fsync per event under a lock: correct but about one event per fsync. This is the broken version the tests catch.
  • Completing futures after write but before fsync: fast, and wrong. Written is not durable.
  • Assuming an fsync covers bytes written while it was already running. It need not, so take the batch, then write, then sync.
  • Counting only the queue for back-pressure. The batch being synced still holds memory and is still unacknowledged.
  • if instead of while around the back-pressure wait: when one place frees up, signalAll wakes every blocked producer and they all go ahead.
  • Waking one producer (signal, notify_one) when a batch frees many places: the rest stay blocked although there is room, until some later batch finishes.
  • A flush that waits for finished == appended instead of a target read at the start: under steady load it may never return.
  • Counting events as finished before completing their futures: flush can then return while a future is still incomplete.
  • close that sets a flag and returns: events still in the queue are lost, or acknowledged after close returned.
  • A second close that returns at once because the flag is already set: it returns while the first call is still draining.
  • Forgetting producers blocked by back-pressure during close: they stay blocked until the disk next finishes an fsync, or forever if the disk hangs, unless close wakes them.
  • Completing futures while holding the lock: in Java the callbacks run right there, on the completing thread, with your lock held. Every producer stalls behind a slow callback, and a callback that waits for another thread's append deadlocks.

Cost

Producers do O(1) work under a short lock. The writer does one write and one fsync per batch. Throughput approaches (batch size / fsync time), and the batch grows with load until maxPending caps it. Latency per event is one to two fsyncs.

How to say it in the interview

The naive version holds a lock across write and fsync, so throughput is one event per fsync. I separate accepting from persisting: producers enqueue under a short lock and get a future; one writer thread drains the whole queue, does one write and one fsync for the batch, then completes the futures. While one fsync runs the next batch builds up, so batches grow with load: that is group commit. Ordering comes from the single queue. Back-pressure blocks appends while too many events are unacknowledged. Close stops intake, wakes blocked producers, and joins the writer, which exits only after draining, so nothing accepted is lost. If an fsync fails I fail that batch and the log, because retrying an fsync is not safe.
