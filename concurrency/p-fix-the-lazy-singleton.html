Fix the lazy singleton

Bug huntswarm-up25 minMicrosoftVMwareFlipkart

Incident report: the service factory usually returns the expected configuration, but startup monitoring sometimes observes incomplete values. A failed startup can leave a registry entry behind.

The task

Repair the supplied factory while keeping its API and construction lazy. Sixteen callers share one LazySingleton. They must receive the same fully initialized Service, and the registry must receive that same object exactly once. The starter compiles as supplied; diagnose the startup symptoms before changing its synchronization.

Rules

  • Creating a factory does not call the build hook or register anything. Its first get() starts construction. The singleton is scoped to one shared factory: two live factories have distinct services, hooks and registries. Production may hold one factory globally. No reset operation is allowed while readers exist.
  • Successful construction sets timeout to 250, endpoint to primary, and checksum to 257. ready() checks all three. Objects are immutable after construction.
  • The build hook may block or throw. Serialize construction attempts and call the hook once per attempt. A failed attempt propagates its original exception to the caller executing it, leaves nothing registered and permits another call to retry. Do not retry internally inside that failing get(), cache a failure permanently or impose a retry limit.
  • Preserve the original exception object in Java, including checked exceptions such as InterruptedException. In C++, preserve its dynamic type and payload by rethrowing it. Concurrent callers must be able to make progress after a failure: one can attempt construction again, and after success all remaining callers receive the same completed object. Do not broadcast one attempt's exception to callers that did not execute it.
  • The registry is thread safe, nonthrowing and nonreentrant; it may inspect the object immediately. Never register an incompletely initialized or failed object.
  • The factory, registry and hook outlive all callers. C++ registry pointers are nonowning and must not be used after the factory is destroyed. Every successful get() must safely observe construction, including the fast path.

Expected behavior

Pause the build hook before it sets configuration fields. The registry must still be empty. Release construction: all sixteen callers receive the same ready object and exactly one registration is recorded.

What the tests check

  • Unused factories perform no work. Two live factories retain distinct identities and call their own hooks and registries exactly once.
  • A gated build hook holds construction while sixteen callers reach get(). No registration or completed call is observed before the hook is released. The registry inspects each published object immediately.
  • Sixteen thousand repeated calls return one fully built object. The registered reference or pointer must match the object returned by get(), not just an equally configured object.
  • Three consecutive failures preserve the original exceptions and publish nothing. Each failing call invokes the hook once, and a fourth call succeeds. Java includes a checked exception and an InterruptedException; C++ checks derived exception types and payloads.
  • In three fresh scenarios, a held first attempt fails while fifteen other callers contend. The failing caller receives the exception, the other callers finish after one successful retry, and only that successful object is registered.
  • Bounded joins and whole-suite watchdogs report stalled initialization. C++ runs under ThreadSanitizer. Gates control the build hook; a short scheduling window gives waiting callers time to enter their wait paths.

Passing these tests is evidence, not a proof of safe publication. In Java, removing volatile from double-checked locking can still appear to work on this machine. Explain the happens-before edge for every return path; no finite stress test establishes its existence.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Where does this appear in reports?
Microsoft reports include a thread-safe singleton coding question. VMware reports describe reviewing singleton code line by line after class-level versus object-level locking; Flipkart’s vehicle-rental review asked about singleton thread safety.
What does volatile fix in Java?
A volatile instance reference safely publishes the preceding initialization writes to a reader that observes it. It does not repair an earlier escape through a different reference, so constructor registration must also move after successful construction.
When would you use the holder idiom?
For a process-wide lazy instance without injected per-factory configuration, a nested static holder uses class initialization to serialize and publish construction. Class initialization failure has different retry behavior from the retrying factory contract here.
What are the C++ alternatives?
A function-local static is initialized once safely since C++11 and retries after a throwing initializer. For this instance-scoped factory, std::call_once coordinates successful initialization and publishes its effects to returning calls. Neither excuses leaking an unfinished object.
Does making the constructor fields final solve everything?
Final fields help initialization safety in Java when construction is not improperly escaped, but they do not create a safe general lifecycle or atomic singleton identity protocol. Keep publication and object lifetime explicit.
Who gets an initialization failure when other callers are waiting?
The caller executing the failing hook gets that original exception. The factory remains uninitialized, so another caller can retry. With a manual state machine, clear the initializing state and wake waiters on failure as well as success. Java monitor exit and C++ std::call_once provide the required handoff in the reference solutions.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

Key idea and invariants

The starter uses an unsynchronized fast read of the instance reference and registers this before the configuration is complete. These are separate publication paths. The fix completes construction first, registers only the completed object, then makes it visible through a safe factory publication boundary.

Why these primitives

Java retains double-checked locking with a volatile reference; the inner monitor ensures one creator, while volatile serves readers that do not enter the monitor. C++ uses std::call_once and unique ownership, with every get() passing through call_once before reading the owner. If construction throws, neither path publishes an instance and another call may retry, including a caller already waiting.

No catch block is needed in either reference. Java monitor exit releases the lock even when construction throws. A throwing std::call_once invocation does not mark the flag complete, so another invocation can run the initializer. Both preserve the original failure and retry after any number of failed attempts.

Pitfalls and failing schedule

Synchronizing the registry does not make the object it receives complete. In the starter, its synchronous callback can already observe default fields, even without a scheduling race. The C++ plain-pointer fast path additionally has a data race; Java also lacks the required publication edge. Do not fix this by resetting a published instance during live reads.

How to say it in the interview

“I will trace all reference escapes, not only the factory return. I need one successful construction, safe publication to fast readers, and no registry entry until construction succeeds. In Java that means volatile or an appropriate initialization idiom; in C++ I prefer a local static or std::call_once over handwritten pointer publication.”

Cost and lifetime

After successful initialization, each call performs constant work and the factory owns one service. A first attempt also pays the hook and registry costs; contention can block callers for as long as those operations take. C++ destroys the owned service with the factory, so registry pointers are usable only during that factory's lifetime.
