A system uses 32 bit virtual addresses, 4 KiB pages and 4 byte page table entries. How large is one process's page table if it is a single flat table?
Why. A 4 KiB page needs 12 offset bits, which leaves 32 minus 12 = 20 bits of virtual page number, so the table has 2 to the power 20 (about a million) entries. At 4 bytes each that is 4 MiB per process, even for a tiny program. 1 MiB counts entries but forgets their size, and 4 GiB is the whole address space. This cost is why real systems use multi level page tables (for example 10 + 10 + 12 bits on classic 32 bit x86), which only allocate the inner tables for regions actually in use.
With 4 KiB pages, a process accesses virtual address 0x00403A7C. Its page table maps virtual page 0x403 to physical frame 0x1F2. What is the physical address?
Why. 4 KiB = 2 to the power 12 bytes, so the low 12 bits (3 hex digits) are the offset and stay unchanged: 0xA7C. The rest, 0x00403, is the virtual page number. Replace it with the frame number: 0x1F2 followed by A7C gives 0x1F2A7C. 0x1F23A7C keeps 16 bits of offset, 0x1F2000 drops the offset, and 0x5F5A7C adds the page and frame numbers as if translation were a base plus offset.
The TLB hit ratio is 95 percent, a memory access takes 100 ns, and a TLB lookup takes negligible time. On a TLB miss, the CPU reads a single level page table in memory and then accesses the data. What is the effective memory access time?
Why. A hit costs one memory access for the data: 100 ns. A miss costs one access to read the page table entry and one for the data: 200 ns. Effective time = 0.95 x 100 + 0.05 x 200 = 95 + 10 = 105 ns. 100 ns forgets the page table access, 200 ns walks the table on every access, and 195 ns swaps the two costs. With a four level table a miss costs 5 accesses (ignoring the caches CPUs keep for page walks), which is why TLB reach and huge pages matter so much for large heaps.
Which statements about page faults are true?Select all that apply
Why. A page fault transfers control to the kernel when address translation or access permissions require attention. Valid causes include first access to a demand-zero mapping, copy-on-write and retrieving a swapped-out page. A minor fault needs no storage I/O; a major fault requires it and can be orders of magnitude slower than a memory access. After successful resolution, execution resumes at the faulting instruction. Invalid mappings or unresolvable permissions can instead cause a signal, and other failures such as unavailable backing storage or exhausted memory can also prevent recovery. The MMU detects the fault; the operating system handles it.
3 page frames, all empty at the start. Reference string: 4 3 1 5 4 5 2 1 2 5 4 2. How many page faults under FIFO?
Why. Frames listed oldest first: 4 fault [4]; 3 fault [4 3]; 1 fault [4 3 1]; 5 fault, evict 4 [3 1 5]; 4 fault, evict 3 [1 5 4]; 5 hit; 2 fault, evict 1 [5 4 2]; 1 fault, evict 5 [4 2 1]; 2 hit; 5 fault, evict 4 [2 1 5]; 4 fault, evict 2 [1 5 4]; 2 fault, evict 1 [5 4 2]. Two hits out of 12 references, so 10 faults. On the same string LRU gives 8 and the optimal policy 6, so those answers come from using the wrong policy. Note that a hit does not change the FIFO order.
3 page frames, all empty at the start. Reference string: 1 2 3 2 4 1 3 2 4 5 2 3. How many page faults under LRU?
Why. Frames listed least recently used first: 1 fault [1]; 2 fault [1 2]; 3 fault [1 2 3]; 2 hit [1 3 2]; 4 fault, evict 1 [3 2 4]; 1 fault, evict 3 [2 4 1]; 3 fault, evict 2 [4 1 3]; 2 fault, evict 4 [1 3 2]; 4 fault, evict 1 [3 2 4]; 5 fault, evict 3 [2 4 5]; 2 hit [4 5 2]; 3 fault, evict 4 [5 2 3]. Two hits, so 10 faults. FIFO gets 8 on this string, so LRU is not always better than FIFO: each time LRU evicts the page that is needed right after next. The optimal policy gets 6.
3 page frames, all empty at the start. Reference string: 1 4 3 5 3 2 4 3 4 1 2 4. How many page faults under the optimal policy (evict the page whose next use is furthest in the future)?
Why. 1, 4, 3 fault into empty frames [1 4 3]. 5 faults: next uses are 3 at once, 4 soon after, 1 much later, so evict 1 [4 3 5]. 3 hits. 2 faults: 5 is never used again, so evict 5 [4 3 2]. 4, 3, 4 hit. 1 faults: next uses are 2 next, then 4, and 3 never again, so evict 3 [4 2 1]. 2 and 4 hit. Faults: 1, 4, 3, 5, 2, 1 = 6. LRU gives 8 and FIFO 10 on this string. The optimal policy needs the future, so it is a yardstick for judging real policies, not something an OS can run.
FIFO page replacement runs on the reference string 1 2 3 4 1 2 5 1 2 3 4 5, with all frames empty at the start. Which statements are true?Select all that apply
Why. With 3 frames, the first seven references fault, then 1 and 2 hit, 3 and 4 fault, and 5 hits: 9 faults. With 4 frames, the first four references fault, 1 and 2 hit, and all six remaining references fault: 10 faults. This is Belady's anomaly: more frames can make FIFO worse, although they do not always do so. LRU has the stack property: the pages in its n frames are a subset of those in n + 1, so extra frames cannot add faults. Optimal replacement also cannot become worse: a larger memory can emulate any smaller-memory strategy, so its minimum achievable fault count cannot increase. On this string LRU gives 10 faults with 3 frames and 8 with 4.
Which statements about thrashing are true?Select all that apply
Why. Thrashing occurs when active working sets do not fit in available physical memory, so useful pages are repeatedly evicted and fetched again. Processes spend more time waiting for storage and CPU utilization falls. Admitting more processes can worsen the shortage. Suspending whole processes reduces the active working set; adding memory increases the available frames. Page-fault-frequency control can allocate more frames to a process faulting too often, but if no frames can be spared, the system must reduce the active load. A faster CPU does not remove the paging bottleneck.
Resource R1 has one instance and R2 has two. P1 holds R1 and requests one R2. P2 holds one R2 and requests R1. P3 holds the other R2 and requests nothing. The resource allocation graph has the cycle P1, R2, P2, R1, P1. Is the system deadlocked?
Why. With several instances of a resource, a cycle is necessary for deadlock but not sufficient. Here one instance of R2 is held by P3, which is outside the cycle and not waiting, so it will release it. Order: P3 finishes, P1 gets the freed R2 and finishes, releasing R1 and its R2, and then P2 gets R1. The detection algorithm reaches the same answer mechanically, and the Banker's algorithm is for avoidance, not for this question. With single instance resources only, a cycle would mean deadlock.

Which statements about spinlocks and futex based mutexes are true?Select all that apply
Why. On one core, a waiter that spins while the holder is preempted prevents the holder from running for as long as the waiter keeps the CPU. Spinning is useful only when the expected wait is very short, typically with the holder running on another core. Sleeping or doing blocking I/O while holding the lock defeats that assumption. A typical Linux futex mutex keeps its lock word and uncontended fast path in user space; contended parking and wakeup use kernel support. The exact atomic operations and bookkeeping depend on the implementation. A tight test-and-set loop repeatedly requests write ownership of the cache line. Test-and-test-and-set first polls with reads and attempts the atomic update only when the lock appears free, reducing coherence traffic.
In the textbook semaphore, wait() decrements the value and blocks the caller if the result is negative, and signal() increments it and wakes one blocked process if the result is not positive. A semaphore starts at 4. Ten different processes each call wait() once, and other processes call signal() 3 times, in some interleaving. Afterwards, what is the value and how many of the ten are blocked?
Why. Each textbook operation changes the value by one regardless of the interleaving, so the final value is 4 - 10 + 3 = -3. In this model the magnitude of a negative value counts blocked processes: seven permits were supplied for ten waits, leaving three blocked. The answer -6 forgets the signals. With Java Semaphore starting at 4 and using only ordinary one-permit acquires and releases, blocked acquires do not drive the available-permit count below zero; the analogous settled state has 0 available and 3 blocked. Java nevertheless permits a negative initial permit count, and subclasses can reduce permits below zero. C++ std::counting_semaphore maintains a nonnegative counter. Do not confuse either library's available permits with this textbook signed waiter count.
One CPU, preemptive priorities High above Mid above Low. At t = 0, Low starts and immediately locks mutex X; it needs 4 units of CPU inside the critical section, then unlocks and is done. At t = 1, High arrives, runs 1 unit, then tries to lock X; once it has X it needs 2 more units and is done. At t = 3, Mid arrives and needs 5 units, using no locks. When does High finish without priority inheritance, and with it?
Why. Without inheritance: Low 0 to 1, High 1 to 2 (blocks on X), Low 2 to 3, then Mid arrives and preempts Low: Mid 3 to 8, Low 8 to 10 (finishes the critical section and unlocks), High 10 to 12. High, the most important task, waited on Mid, which does not even use the lock: priority inversion. With inheritance: when High blocks at 2, Low runs at High's priority, so Mid cannot preempt it; Low 2 to 5 unlocks, High 5 to 7 finishes, Mid 7 to 12. 10 and 5 are when High gets the lock, not when it finishes. This is the bug that reset the Mars Pathfinder lander in 1997, fixed by enabling priority inheritance on the mutex.
