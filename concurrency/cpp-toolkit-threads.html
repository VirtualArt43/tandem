The toolkit: std::thread, std::jthread and thread_local

Start and own C++ threads, pass data safely, collect results, request cooperative stopping, and distinguish thread lifetime from task lifetime.

Asked atMicrosoftGoogle
Before this:Classes, constructors, destructors and RAIILambdas, captures and callablesstd::chrono: durations, clocks and deadlines

Starting a thread is one constructor call. Making sure its arguments remain alive, its errors are handled, and its owner waits for it is the actual programming task.

In plain words

You give a colleague a job and a bag of materials. Copies in the bag belong to them; a note pointing to your desk is only useful while the desk still exists. Joining is waiting for the colleague to finish before clearing the desk.

Why this matters for concurrency

Almost every core example starts workers, shares a small amount of state, and joins them before inspecting results. A join is both lifecycle management and synchronization. Learn the syntax here, then study thread creation, argument sharing, and happens before for the reasoning behind it.

API card

std::thread and thread_local are available from C++11. The joining thread type std::jthread and stop tokens require C++20. In this table, t is a std::thread object and jt is a std::jthread object; both types are declared in <thread>.

A function, a lambda, and a member function

The thread constructor takes a callable first. A plain function name is sufficient. A lambda packages code and captures. A member function pointer needs an object argument next, because the function needs a this object. &Calculator::square names the member, while &calculator points to the particular live object.

Stored arguments are decay-copied or moved into the new thread's invocation state. A plain integer becomes an independent value. Passing a pointer copies the pointer, not the object it points to. std::ref(x) explicitly passes a reference wrapper so a callable taking T& receives the original object. std::cref is the const borrowing form. Both wrappers require the original to outlive the invocation.

The callable is also stored by value unless you wrap it in std::ref. A [this] capture copies a pointer, not the object; [=] does not turn member access into an object copy. Arrays decay to pointers: if a worker expects a std::string, pass std::string(buffer) to construct an owned string before launch, rather than relying on a later conversion from a borrowed character buffer.

The first three starts are deliberately joined individually to isolate each argument form. The vector starts several workers before joining any. Different elements of this ordinary int array are distinct memory locations; each worker writes only its own slot. Main reads them after all joins. Do not generalize that reasoning to packed std::vector<bool> elements, or resize shared storage while workers use it.

std::move permits ownership transfer; it does not create a thread or synchronize accesses. The moved unique pointer becomes null, and the closure owns the pointee. Capturing loop index i by value prevents workers from observing the same changing loop variable. The array is borrowed by reference and stays alive until after all joins.

What start and join actually order

Construction with a callable starts the thread; there is no separate start() call. Constructor completion synchronizes with the start of the stored callable, so state initialized before launch is published to it. Worker completion synchronizes with a successful join() return, so the joining thread can read the worker's results. These happens-before edges do not repair a data race that already occurred while both threads were running.

joinable() is not a running-state query

A default constructed thread has no associated execution. Starting one makes it joinable; a move transfers that association to another handle. Successful join or detach removes it. A worker that returned ten seconds ago is still joinable until its owner performs one of those operations.

Destroying a joinable std::thread calls std::terminate. Move assignment into a joinable destination does too, even if the source is empty. Both thread types are movable but not copyable; a move transfers the association and leaves the source nonjoinable.

Self-join and joining a nonjoinable handle report std::system_error, with error conditions std::errc::resource_deadlock_would_occur and std::errc::invalid_argument respectively. Two unsynchronized calls to join() on the same handle are unsafe. Manage each handle from one owner; joining synchronizes with worker completion, not with other operations on that handle.

Neither thread type has a timed join in C++20. A timeout on a separate completion signal does not end the worker or release borrowed objects safely. Thread IDs can also be reused after a thread has terminated and can no longer be joined; they are not permanent request IDs.

C++17: make cleanup survive a failed launch

Creating a thread can throw std::system_error, and storing a callable or its arguments can throw in the launching thread. Reserving vector capacity avoids reallocations but cannot prevent a later thread launch failing. A RAII guard must join already started workers before their handles or borrowed state are destroyed.

The guard is destroyed before the vector; partial outlives both. The example injects a failure before worker three instead of exhausting OS resources. This guard assumes one external owner, valid joins and workers that finish independently; a join failure in its destructor terminates. In C++20 a vector of std::jthread handles gives automatic joining, but RAII cannot make an impossible wait finish.

detach() gives up the join, not the lifetime problem

A detached thread can continue after the launching function returns. It does not extend the lifetime of local references, this, a condition variable, or a mutex it uses. Process exit also need not wait for detached work to finish. Detached work is appropriate only with a deliberate independent lifetime and shutdown arrangement. A service member thread normally should remain owned and joinable.

Joining a worker while holding a mutex it needs to finish creates a deadlock. Arrange shutdown as state change under the lock, notification after the state is visible, then join without the lock. The deadlock lesson shows why the waiting owner is part of the dependency cycle.

std::jthread and cooperative stop

A std::jthread constructor first tries invoking the callable with its std::stop_token before the supplied arguments; if that form is not valid, it invokes without the token. The worker calls stop.stop_requested() to check the latched request. The worker chooses safe cancellation points; cancellation does not interrupt arbitrary instructions, socket calls, sleeps, or ordinary condition variable waits. The stop-aware std::condition_variable_any waits in the condition variable toolkit provide a blocking alternative.

The C++20 latch is a one-time gate: main waits until the worker has entered before requesting stop. It is introduced fully in C++20 synchronizers. The sleeps demonstrate APIs, not synchronization; correctness depends on the latch, token, and join. ticks needs no atomic because main reads it only after completion. The exact number of ticks is intentionally unspecified.

A std::jthread whose callable ignores its token still gets joined at destruction; it simply will not cooperate with the stop request. Explicit join() does not request stop, which matters for a loop waiting on that request. A stop request is permanent for its stop state; use a new state for a new operation rather than trying to reset it.

request_stop() returns true only for the call that first sets the request, not as proof that the worker has exited. Registered std::stop_callback functions execute synchronously during the successful request, so requesting stop can run user code and block. Avoid holding locks that those callbacks need. In C++17, use a std::atomic<bool> stop flag or a shutdown predicate under a mutex, plus notification for blocked workers and guaranteed joins.

For interdependent workers, request stop for every worker before joining any. Destroying a vector of std::jthread objects stops and joins them one at a time; the first join could wait for a peer that has not received stop yet. Move assignment into a joinable std::jthread also stops and joins its previous worker, so assignment itself can block.

For member workers, declare borrowed state before the worker so reverse member destruction joins first. If the owner's destructor body changes that state, explicitly stop and join before those changes; automatic member destruction comes later. Start only after the worker's dependencies are initialized, and do not expose an incompletely constructed object. Destroying the owning std::jthread from its own worker attempts self-join and terminates.

Thread-local storage is not task-local storage

Each thread has a separate counter, so those increments do not share one location. Initialized thread-local objects are destroyed at normal thread exit. In a pool, the same worker executes many tasks, so a thread-local request identifier or buffer survives between tasks unless you reset it. Do not leak one request's identity into another.

A function-local thread_local with dynamic initialization is initialized on first use in each thread, not on every function call. A new thread initializes its own instance; it does not inherit the launching thread's current value. If you hand another thread a pointer to your thread-local object, ordinary sharing and lifetime rules apply again, and that pointer cannot outlive the owning thread.

Scheduling hints and results

hardware_concurrency() is a hint, not a guaranteed number of available cores or the correct pool size. Handle zero, consider quotas and other workloads, and distinguish CPU work from waiting for I/O. yield() cannot force a particular other worker to run. Neither yielding nor sleeping publishes ordinary memory writes. See pool sizing and sleep and thread-local state.

A thread discards the callable's ordinary return value. Use a separate output slot read after join, a promise/future, or a synchronized result queue. An exception escaping the top-level thread function terminates the process; a try around join() does not catch it. Catch inside the worker and store an exception pointer, or use the future toolkit to transport the result or failure.

Worked example: four independent squares

In the first sample, four workers write 1, 4, 9 and 16 into partial[0] through partial[3]. Main joins them all, then computes 1 + 4 + 9 + 16 = 30. Worker three may finish first; joining worker zero first does not prevent the other workers from running.

The proof has three parts: the array exists before launch and survives every worker, each worker alone writes its slot, and main reads only after joins. Replacing the slots with concurrent total += value operations would introduce a data race that later joins cannot repair. For real chunk sums, also share a stable read-only input; the parallel algorithms lesson develops partitioning and load balancing.

Common mistakes

  • Passing a plain variable to a function taking T&: use std::ref when borrowing is intended.
  • Capturing the changing loop index by reference: capture the index by value.
  • Reading a result before join: it needs synchronization or must wait for completion.
  • Using joinable() as evidence of ongoing execution: finished unjoined threads are joinable.
  • Assuming request_stop() kills blocked work: provide a cooperative exit path.
  • Declaring a member worker before the data it borrows: initialize dependencies first, and join before their destruction.

In the interview

Expect to review a worker launch, predict its output, or explain a crash during cleanup. Walk through ownership, synchronization and failure paths. Follow ups include a failed third launch, a detached [this] capture, an ignored stop token, and a timeout while the worker still uses its owner's data.

Each worker owns its input copies or borrows state that outlives it. I collect independent results, join before reading them, and handle exceptions inside the worker. In C++20 I prefer std::jthread for ownership, while still defining how every blocking operation stops.

If asked why the result is visible, name the worker-completion to successful-join synchronization edge. If asked about shutdown, say which predicate or token ends the loop, what wakes a blocked worker, and which objects remain alive until joining finishes.

Key takeaways

  • Thread arguments are stored values unless you explicitly borrow or transfer ownership.
  • Join is both a lifecycle boundary and a visibility guarantee; it does not repair earlier races.
  • A joinable std::thread must be joined, detached, or moved from before its handle is destroyed.
  • std::jthread destruction requests cooperative stop and joins; it cannot force progress.
  • Thread-local data belongs to a worker thread, not automatically to one request.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A std::thread function has returned, and its handle has not been joined, detached or moved from. Is that handle joinable?
Why. joinable() describes association, not whether instructions are still executing. Completion does not discharge ownership, and the callable's return value is ignored, so it cannot change joinability.
Assume thread creation and joining succeed. What does this print?
Why. The constructor stores 6 before main changes x; the worker never accesses x itself. It writes 36 to the borrowed result, and join orders main's read after that write. Scheduling cannot change the stored argument to 99 or leave main reading the old result.
What does std::jthread::join() do for a worker looping until stop_requested()?
Why. The destructor requests stop before joining, but explicit join only waits. It neither sets the request nor injects an exception into the worker. Without a stop request from elsewhere, this loop keeps join waiting.
Two workers write distinct ordinary int array elements, and main reads only after both joins. What synchronization is required for those elements?
Why. Distinct elements are separate locations and join orders main's reads after completion, so element atomics are unnecessary. Sleep supplies no synchronization. Packed std::vector<bool> and concurrent resizing are different cases.
A pool worker has a thread_local request identifier. What must each new task consider?
Why. Each worker has its own instance, but that instance survives successive tasks on the same thread. Function calls do not reset it. Reset or scope request state explicitly, including on exception paths.
std::thread::hardware_concurrency() returns zero. What does that mean?
Why. Zero is a permitted unknown result, not a claim that processors are absent or thread creation is forbidden. Pool sizing must not turn an unavailable hint into an invalid zero-worker configuration.
Workers A and B have independent stop states. A waits for B to exit; B exits only after B's stop token is requested. Main requests stop on A and immediately joins A, planning to stop B afterwards. Which statements are correct? Select all that apply.Select all that apply
Why. A cannot finish before B, and main postpones B's request until A finishes. Independent stop states do not propagate requests. Requesting both stops first removes that cycle, assuming B can finish and A's wait for B is otherwise correct. Yield affects scheduling only and cannot request cancellation.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a worker that owns a moved std::unique_ptr<int> and returns a squared value or an exception to its caller. Reject negative inputs and exercise both paths.
Model answer

The worker alone writes its result and exception slots; main reads after join, so no additional mutex is needed. The inputs keep the square within int; a general arithmetic API would also define overflow handling. For several workers use one failure slot per worker or synchronize a shared slot. A promise/future is another way to transport a value or failure.

Debug
A program terminates during stack unwinding after starting two std::thread workers. What is the likely ownership error?
Model answer
An exception bypassed a join and destroyed a joinable thread handle. Use a guaranteed cleanup path or std::jthread handles, and ensure their workers can finish during cleanup. A later launch failure happens in the launching thread; an exception from the worker's own code must be caught inside that worker.
Design
Why is changing a member worker from std::thread to std::jthread not a complete shutdown design?
Model answer
The stop request is cooperative. A worker blocked on an ordinary condition variable needs a shutdown predicate and notification, or a stop-aware wait. Joining must occur without locks the worker needs and before its referenced members are destroyed. Declare dependencies before the worker, join before the destructor body mutates shared state, and request stop for all interdependent workers before joining any.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Explain thread arguments, std::ref, and std::move as if you were reviewing a new worker."
What a strong answer covers
  • Default argument storage is by value
  • Reference wrappers borrow with lifetime and synchronization obligations
  • Move transfers ownership when the type supports it
  • Join bounds borrowed lifetimes and result reads
How a senior would say it
By default the thread constructor stores values for the callable and arguments. Passing an integer copies it; passing a pointer copies the address, so the pointee can still be shared. I use std::ref when the worker intentionally needs the original object, and then prove that object remains alive and its accesses are safe. I use std::move to let a resource such as a unique pointer transfer ownership into the worker. The move operation performs that transfer; the cast alone does not. Finally I join before destroying borrowed objects or reading ordinary result slots written by the worker.

Likely follow up: Does capturing this by value copy the whole object?

Out loudabout 60 s
"Why can a finished thread still crash the process at scope exit?"
What a strong answer covers
  • Joinable means associated, even after execution finishes
  • Thread destruction terminates if joinable
  • Join or detach discharges association
  • Prefer std::jthread with a real cooperative shutdown path
How a senior would say it
The handle still owns a joining obligation after the function returns. A std::thread remains joinable until it is joined, detached, or moved from. Its destructor calls std::terminate if that association remains, even when the worker has already finished. I normally join, because that gives a clear completion and lifetime boundary. Detaching gives up that boundary and needs a separate lifetime design. In C++20 std::jthread helps with automatic ownership cleanup, but its worker still needs a way to finish. A destructor can block forever joining a worker that waits for an event nobody will produce.

Likely follow up: What happens if you join while holding the worker's mutex?

Out loudabout 90 s
"We replaced every thread in a service with std::jthread, but shutdown still hangs. Walk me through your review."
What a strong answer covers
  • Stop is cooperative; explicit join does not request it
  • Identify the wait or operation preventing worker progress
  • Wake blocked workers and request stop on the whole group before joining
  • Hold no lock required by workers or stop callbacks during shutdown calls
  • Keep borrowed members alive until joining completes
How a senior would say it
I first find what each worker is waiting for. A joining thread owns cleanup, but it cannot force arbitrary work to stop. If the worker waits on an ordinary condition variable, I need a shutdown predicate and notification, or a stop-aware wait. A blocking socket operation needs its own cancellation or deadline design. I request stop for every interdependent worker before joining any of them, because the first worker may need a peer to finish. I also check that the caller holds no lock needed by a worker or a stop callback. Explicit join does not send a stop request, so simply joining a loop that waits for stop will hang. Finally, I check member order and the destructor body: every borrowed object must remain usable until its worker has joined. Automatic cleanup is useful only after that exit path exists.

Likely follow up: Can a timed wait on a future make it safe to destroy the worker's borrowed buffer?
