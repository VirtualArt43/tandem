Fix the job queue that stalls

Bug huntsmedium25 minRubrik debugging round styleRubrik

Rubrik's debugging round has handed candidates a C++ producer consumer program with a bug in its critical section. This problem drills the classic shape of that bug: two separate mistakes in how threads wait, showing up as three different symptoms.

The incident

INC-4219: the indexing pipeline stalls and leaves jobs behind

Last month we went from 1 upload thread and 1 indexing worker to 4 of each, sharing one JobQueue. Since then:

  • Some nights the indexer "finishes" with jobs still sitting in the queue. The worker logs say each worker exited because take reported the queue closed, but the queue is only closed at shutdown, hours later.
  • A memory alarm fired: the queue, created with a capacity of 100, held 103 jobs.
  • Twice the whole pipeline froze with the CPU idle. A thread dump showed uploaders waiting inside put and workers waiting inside take at the same time.
  • The unit tests, with one uploader and one worker, all pass.

The class is in your editor. Upload threads call put; indexing workers loop on take and stop when it says the queue is closed; shutdown calls close.

What the class must guarantee. put waits while the queue is full and open, and returns false once it is closed. take waits while the queue is empty and open, and reports "closed" (null, or an empty optional) only when the queue is closed and empty. Jobs come out in the order they went in, each exactly once. The size never exceeds the capacity. close wakes everyone who is waiting.

What the tests check

  • One thread: first in first out, close, draining after close, and put refused after close.
  • take waits for a put; put waits while full until a take; close wakes a waiting take.
  • A stress run, 3 rounds: 4 uploaders and 4 workers on a queue of capacity 2. Every job arrives exactly once, no worker is told "closed" before close is called, the size never exceeds 2, and nothing freezes.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Lost wakeups, notify versus notifyAll, Mesa versus Hoare

Open them one at a time. Each one gives away a little more.

When a waiting thread wakes up, what does it actually know? Only that something happened while it slept. Is the condition it was waiting for still true? Who else could have run between the wakeup and the moment it got the lock back?
Uploaders and workers wait on the same condition, so they sit in the same wait set. When a worker takes a job and wakes "one" waiting thread, which thread might that be, and can that thread do anything useful?
Two small changes. Wait in a while loop that re-checks the condition after every wakeup (in C++, pass the condition as the predicate to wait). And wake everyone, notifyAll or notify_all, because with one shared condition a single wakeup can go to a thread that cannot use it. The alternative to the second change is two conditions, not full and not empty.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Fix it with two conditions instead of notifyAll.
Use a ReentrantLock with notFull and notEmpty conditions in Java, or two std::condition_variables in C++. Uploaders wait on not full and workers on not empty, so signal (notify_one) is safe: every thread waiting on a condition wants the same thing, so any one of them can use the wakeup. Keep the while loops, and make close wake everyone on both conditions.
notifyAll is correct. Why would anyone avoid it?
It wakes every waiter, and all of them queue for the same lock just to find, mostly, that they must wait again. With 8 threads that is nothing; with hundreds of waiters it is a thundering herd on every put and take. Two conditions wake only threads that can make progress.
Why do spurious wakeups exist at all?
Both the POSIX and Java specifications allow a wait to return with no notify, because preventing it would make the implementation slower: for example, a signal handler interrupting the underlying futex wait, or wakeup races on multiprocessors. Since a while loop is needed anyway for stolen wakeups, spurious wakeups cost nothing extra to handle.
The C++ version did not crash. What would make the same bug crash?
This take checks empty() after waking and returns nothing, which the worker reads as "closed": wrong, but defined behaviour. Code that assumed the queue was non-empty after the wait and called front() and pop_front() on an empty std::deque would have undefined behaviour, which can crash, corrupt the deque, or appear to work. That is why debugging round code often fails in a different way each run.
Could two counting semaphores replace the condition variable?
Yes: a semaphore of free slots and a semaphore of available jobs, plus a mutex around the deque. A semaphore remembers releases as permits, so a wakeup cannot be lost. The awkward part is shutdown: a semaphore has no "closed" state, so you release extra permits or enqueue one poison pill per worker.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The bugs

Two mistakes, both in how threads wait. First, if instead of while. A woken thread continues without re-checking, but between the wakeup and getting the lock back, another thread can take the job (a stolen wakeup), or the wakeup may be spurious. A worker then finds the queue empty and reports "closed"; an uploader finds the queue still full and adds anyway, which is how 103 jobs got into a queue of 100.

Second, notify with one shared condition. Uploaders and workers wait in the same wait set, and notify wakes an arbitrary one. If a worker's notify reaches another worker while an uploader is waiting for room, the uploader is never told. Even with while loops, this lost wakeup can freeze everyone:

The fix

Why both changes are needed

  • The loop alone stops the early exits and the overfilled queue, but the freeze remains: a notify can still go to the wrong side, as the second timeline shows.
  • notifyAll alone makes the freeze impossible, but now every wakeup releases several threads that pass the if together, so early exits and overfilling get more frequent, not less.
  • Together they give the textbook rule: wait in a loop on the condition you need, and when you change the state, wake every thread that might now be able to proceed. With one condition shared by two kinds of waiter, that means everyone.
  • close was already right: it sets the flag under the lock and wakes everyone, and the loops treat closed as a reason to stop waiting.

How to say it in the debugging round

Two bugs in the waiting. The waits use if, so a woken thread does not re-check: another worker can take the job first, and this one returns null as if closed, and an uploader can overfill the queue. And the code uses notify with one condition shared by uploaders and workers, so a worker's notify can wake another worker while an uploader waits for room, and everyone ends up asleep. The fix is while loops around every wait, and notifyAll; or better, two conditions, not full and not empty, so a single signal always reaches a thread that can use it.
