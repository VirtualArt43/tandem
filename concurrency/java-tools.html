javac, java, jshell, jstack and jcmd

Compile and run from the command line, experiment in jshell, and read stack traces and thread dumps taken with jps, jstack and jcmd.

Before this:How Java runs: JVM, bytecode, JIT and GCExceptions, InterruptedException and try-with-resources

When a threaded program hangs, nothing is printed and nothing is thrown. The fastest way to find out why is a thread dump, and taking one is two commands. This lesson is the toolbox: compile and run from a terminal, try an API in seconds, and read what the JVM tells you about its threads.

In plain words

A doctor does not guess what is wrong with a patient who has gone quiet. She checks who is breathing, listens to the chest, and reads the notes written when the trouble started. For a Java process, jps tells you which JVMs are alive. A thread dump is the stethoscope: what every thread is doing at this instant, and which lock it is waiting for. A stack trace is the note written at the moment something went wrong. And jshell is the scratch pad where you check a fact before you rely on it.

Why this matters for concurrency

  • Deadlocks, lost wakeups and exhausted thread pools produce no exception and no log line: the program just stops making progress. A thread dump shows each thread's state and the exact lock it waits for, and HotSpot names lock cycles outright.
  • The thread states in a dump map one to one onto the concepts of this course: BLOCKED is waiting for a synchronized monitor, WAITING is wait, join or a parked ReentrantLock or Condition, TIMED_WAITING is the timed versions and sleep.
  • Failures in worker threads arrive as chained stack traces ("Caused by"), and reading them quickly is a debugging round skill. On Tandem, the Run button takes a thread dump automatically when a program hangs, so you will read plenty.

javac and java

javac compiles source files into bytecode, one .class file per class, including nested ones such as Main$Worker.class. java starts a JVM and runs the main method of the class you name. For a single-file program you can skip the compile step: since Java 11, java Main.java compiles the file in memory and runs it. In Java 21 that source mode takes exactly one file, and the first class declared in it must hold main.

Three flags matter for concurrency work. -ea turns on assert statements, which are off by default, so a test that relies on assert silently passes without it (Tandem runs your code with -ea). -XX:ActiveProcessorCount=N makes the JVM believe it has N cores, which changes availableProcessors() and therefore the size of the common pool; it is a cheap way to test a pool sizing decision. And -Xlog:gc prints a line per garbage collection, which you line up against latency spikes. Some Java 21 concurrency APIs, such as StructuredTaskScope, are preview features and need the preview flag both when compiling and when running.

jshell: check before you rely on it

jshell (Java 9 and later) is a read, evaluate, print loop: type an expression and see its value. It is the fastest way to settle "does TimeUnit.convert go this way?" before you build an answer on it.

jshell imports java.util, java.util.concurrent, java.util.function, java.util.stream, java.io, java.math, java.net, java.nio.file, java.util.regex and java.util.prefs for you. It does not import java.time, java.util.concurrent.locks or java.util.concurrent.atomic, which is why the session above imports Duration. Useful commands: /vars, /methods, /imports, /list, /open file.jsh and /exit; the Tab key completes names and shows method signatures. You can start threads in jshell too, but measure performance somewhere else: a snippet run once has not been compiled by the JIT yet.

Stack traces: reading one fast

Here is a realistic failure: a pool thread parses a price, the parse fails, the task wraps the error, and the main thread finds out through get().

Read it in this order:

  1. The first line gives the outermost exception and its message. When a trace escapes a thread uncaught, the JVM prefixes it with the thread's name, as in Exception in thread "main".
  2. The at lines list calls newest first. The top line is where that exception was created; scan down for the first line in your own code.
  3. Each Caused by: is the exception the one above it wrapped. The last Caused by is the root cause, and usually the thing to fix: here, a letter O typed where a zero belongs.
  4. ... 5 more means the remaining frames are the same as in the exception above, trimmed to save space.
  5. Two threads in one trace. The ExecutionException frames are main's stack, waiting in get(). The Caused by frames are the stack of the price-loader pool thread, where the work actually failed. This is why you wrap with the cause and name your threads.

Finding the process: jps and jcmd

jps -l lists the running JVMs that belong to your user, with their process ids and main classes; jcmd with no arguments prints the same list. The list comes from small performance data files that each JVM publishes, and jcmd <pid> then talks to the chosen JVM through its attach mechanism, so run both as the same user as the target JVM, ideally from the same JDK version. A JVM started with -XX:-UsePerfData publishes no such file and does not show up in jps, though jcmd can still attach to it by process id.

jcmd <pid> help lists everything you can ask a running JVM. The ones worth knowing: Thread.print (a thread dump), Thread.dump_to_file (a thread dump that includes virtual threads), GC.class_histogram (instance counts and bytes per class), GC.heap_info, VM.flags, VM.uptime and JFR.start.

Thread dumps

Any of these prints a thread dump: the stack of every thread in the target JVM.

The JDK documentation marks jstack as experimental and unsupported, and Oracle's troubleshooting guide recommends jcmd for new work; the output is the same. Below is a real dump, trimmed, from two threads that each hold one synchronized lock and want the other's:

How to read each thread's entry:

  • The header line: the thread's name (which is why you name threads), its Java thread number, the operating system thread id in brackets, its CPU time so far, how long it has existed, and a short summary such as "waiting for monitor entry".
  • java.lang.Thread.State: one of the thread states in the table below.
  • The frames, newest first, with lock lines underneath: - locked <address> is a monitor this thread holds, and - waiting to lock <address> is the one it wants. Search the dump for the same address to find the holder.
  • The deadlock section at the very end, when HotSpot finds a cycle. Here each thread holds the lock the other wants: transfer-1 holds ...a8 and wants ...b8, transfer-2 the reverse.
State in the dumpWhat the thread is doingLine to look for
RUNNABLERunning, ready to run, or inside native code, which includes a blocking socket readyour own frames, or a native I/O frame
BLOCKED (on object monitor)Waiting to enter a synchronized block or method, or to re-enter one after wait- waiting to lock <...>
WAITING (on object monitor)In Object.wait() with no timeout, or Thread.join()- waiting on <...>
WAITING (parking)Parked by a java.util.concurrent class: ReentrantLock.lock(), Condition.await(), BlockingQueue.take(), Future.get()- parking to wait for <...> (a ...ReentrantLock$NonfairSync)
TIMED_WAITINGsleep, wait(ms), join(ms), or a timed park such as poll(timeout) or awaitNanosThread.sleep, parkNanos

Two readings trip people up. A thread waiting for a ReentrantLock is WAITING (parking), not BLOCKED, and the frames do not say who owns that lock; the -l option adds a "Locked ownable synchronizers" list under each thread, which does. And RUNNABLE does not mean "using CPU": a thread stuck in a socket read is RUNNABLE inside native code. HotSpot's deadlock section covers cycles through synchronized monitors and through ReentrantLock and ReentrantReadWriteLock, which it reports as "waiting for ownable synchronizer".

JFR in one paragraph

JDK Flight Recorder is an event recorder built into the JVM, designed to stay on in production at low overhead. Start it with the JVM (java -XX:StartFlightRecording=duration=60s,filename=rec.jfr -jar app.jar) or attach it to a running one (jcmd <pid> JFR.start duration=60s filename=rec.jfr). For concurrency it records contended synchronized entry (jdk.JavaMonitorEnter), wait (jdk.JavaMonitorWait), parking in java.util.concurrent locks (jdk.ThreadPark), and virtual threads pinned to their carrier (jdk.VirtualThreadPinned); with the default settings, monitor entries and parks are recorded once they last 20 ms. Java 21 added jfr view to summarize a recording in the terminal: jfr view contention-by-site rec.jfr ranks the places where threads waited for locks, and jfr summary rec.jfr counts the events. JDK Mission Control is the graphical viewer.

Worked example: a service stopped responding

Requests time out, CPU is near zero, and nothing is in the logs. Low CPU says the threads are waiting, not working, so a thread dump is the first move.

  1. Find the process: jps -l gives the pid.
  2. Take two or three dumps, about ten seconds apart: jcmd <pid> Thread.print -l > dump1.txt, and again into dump2.txt. One dump shows a moment; several show what is stuck.
  3. Read the end of the file first. If HotSpot found a cycle, the "Found one Java-level deadlock" section names the threads and locks, as in the dump above, and you are nearly done.
  4. No cycle? Group threads by state and top frame. Forty request threads BLOCKED on the same address point to one holder: search for - locked <that address> and read what the holder is doing. Holding a lock across a slow network call is a classic.
  5. Compare the dumps. The same thread in the same frame in every dump is stuck; changing frames mean slow but moving. All pool workers WAITING (parking) inside take() means the pool is idle and the work never arrived; all of them RUNNABLE in one slow client call means the pool is exhausted by a slow dependency.

For the dump above, the cause is two transfer calls taking the same two locks in opposite orders. The fix is to always lock in one global order, for example by account id, which the deadlock lesson covers in full.

Common mistakes

  • Taking one dump. A single dump cannot tell stuck from slow. Take two or three, seconds apart.
  • Reading RUNNABLE as "busy on the CPU". Blocking socket reads show as RUNNABLE too.
  • Looking for BLOCKED to find ReentrantLock waits. They are WAITING (parking); add -l to see owners.
  • Leaving threads unnamed. pool-3-thread-7 tells you nothing. Name threads, and give pools a ThreadFactory that names them.
  • Attaching as a different user or with a mismatched JDK. The attach fails or hangs; run the tools as the JVM's user, from the same JDK.
  • Trusting assert without -ea. Assertions are off unless enabled, so the check never ran.
  • Reading only the first line of a trace. The root cause is the last Caused by.
  • Timing code in jshell or in a single run. The JIT has not warmed up, so the numbers mean little; use a benchmark harness such as JMH.

In the interview

Tools come up as "how would you debug this?" after a deadlock or a hang, and as the vocabulary you use in a debugging round, where you are handed someone else's threaded code. Even when you cannot run anything, saying which thread is BLOCKED on which lock, and who holds it, is how you explain the bug crisply.

First I would take two or three thread dumps a few seconds apart with jcmd Thread.print -l. HotSpot prints any cycle through monitors or ReentrantLocks at the end as a Java-level deadlock. If there is none, I group threads by state and top frame: a pile of BLOCKED threads on one monitor points me to the holder, and the same frames in every dump mean stuck rather than slow.

Follow ups to expect. "What is the difference between BLOCKED and WAITING?" (monitor entry versus wait, join or parking). "How would you find lock contention, not a deadlock?" (JFR's monitor enter and park events, for example jfr view contention-by-site, or a profiler's lock mode). "Would the deadlock detector catch a hang on a CountDownLatch?" (no: see below).

Senior depth

  • What the deadlock detector cannot see. It follows owners: monitors and the java.util.concurrent locks that record an owning thread. A latch, a semaphore, a future or a condition has no owner, so two threads each waiting for the other to count down a latch hang forever with no deadlock reported. The same goes for a class initialization cycle, where both threads even show as RUNNABLE.
  • Virtual threads. In Java 21, Thread.print lists platform threads; a virtual thread that is not currently mounted on a carrier does not appear. jcmd <pid> Thread.dump_to_file -format=json threads.json (or the plain format) includes them.
  • A dump pauses the JVM briefly. HotSpot collects the stacks at a safepoint, so every Java thread stops for a moment. It is fine to do in production, but not in a tight loop.

Key takeaways

  • javac compiles, java runs; java Main.java runs a single file directly, and -ea is needed for assert.
  • jshell answers API questions in seconds; it does not import java.time or the locks and atomics packages.
  • Read a stack trace from the first line, down to your code, then to the last Caused by, which is the root cause.
  • jcmd <pid> Thread.print -l (or jstack -l) gives a thread dump: states, held locks, wanted locks, and a deadlock report for monitor and ReentrantLock cycles.
  • BLOCKED is monitor entry; ReentrantLock and Condition waits are WAITING (parking); take several dumps to tell stuck from slow.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A thread is waiting inside ReentrantLock.lock() because another thread holds the lock. What state does a thread dump show for it?
Why. java.util.concurrent locks park the waiting thread with LockSupport.park, which shows as WAITING (parking) with a "parking to wait for" line. BLOCKED is only for synchronized monitor entry. Use the -l option to see which thread owns the ReentrantLock.
A thread is blocked reading from a socket with a classic InputStream on a platform thread. What state does the dump show?
Why. The thread is inside a native read call, and the JVM reports threads in native code as RUNNABLE. That is why RUNNABLE does not mean "using CPU", and why a pool exhausted by a slow downstream service can look busy in a dump while the machine is idle.
Which command gives a thread dump that also lists the ReentrantLocks each thread owns?
Why. Thread.print prints every thread's stack, and -l adds the "Locked ownable synchronizers" list, which is where ReentrantLock owners appear. jstack -l <pid> prints the same. jps only lists JVMs, and the histogram counts objects per class.
A stack trace has three sections: ExecutionException, then Caused by: IllegalStateException, then Caused by: NumberFormatException. Which one usually points at the code to fix?
Why. Each Caused by is the exception that the one above it wrapped, so the last one is the original failure, the root cause. The ExecutionException only says that a task failed and that get() reported it; its frames show where the caller was waiting.
A test harness checks results with assert count == expected; and is run with java -cp out Harness. A bug makes count wrong. What happens?
Why. assert statements are compiled in but skipped at run time unless assertions are enabled with -ea (or -enableassertions). A harness that depends on them passes silently. Use explicit checks that print or throw, or always run tests with -ea.
Which of these hangs does HotSpot's "Found one Java-level deadlock" report detect? Select all that apply.Select all that apply
Why. The detector follows ownership: monitors and the ownable synchronizers behind ReentrantLock and ReentrantReadWriteLock. A latch has no owner, so a cycle through latches, semaphores or futures goes unreported, and a class initialization cycle shows two RUNNABLE threads waiting on the class initialization monitor with no report.
You run java Main.java on Java 21 for a file that declares class Helper first and public class Main with the main method second. What happens?
Why. In the Java 11 to 21 source launcher, the class that is run is the first top-level class in the file, and it must declare main. Move Main to the top, or compile with javac and name the class to run. Extra classes are fine as long as the first one is the entry point.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A batch job hangs. Part of its thread dump is below. What is the bug, and how do you fix it?
Model answer

Both workers are BLOCKED in Inventory.reserve at the same line. worker-1 holds bin ...3f8 and wants bin ...1e0; worker-2 holds ...1e0 and wants ...3f8. That is a lock ordering deadlock: reserve locks two Bin objects in the order the order lists them, and two orders listed the same two bins in opposite orders. Neither thread can ever proceed, and the dump would end with a "Found one Java-level deadlock" section naming this cycle.

Fix: make every thread take bin locks in one global order, for example by bin id: lock the bin with the smaller id first, then the other, whatever order the order lists them in. If the bins can be many, sort the ids first. Alternatives: tryLock with a timeout and back off and retry, or one coarser lock over the inventory if contention is low. I would also add a stress test that reserves overlapping pairs in random order, which reproduces the hang quickly.

Explain
Walk an interviewer through how you would investigate a Java service that has stopped responding but uses almost no CPU.
Model answer

Almost no CPU means the threads are waiting, not computing, so I want to see what they wait for. I find the pid with jps -l and take two or three thread dumps about ten seconds apart with jcmd pid Thread.print -l. First I look at the end of the dump: if HotSpot found a cycle through monitors or ReentrantLocks, it prints a Java-level deadlock section with the threads and the locks, and the fix is a lock ordering change.

If there is no cycle, I group the threads by state and top frame. Many threads BLOCKED on the same monitor point to one holder; I search for that lock address and read what the holder is doing, often slow I/O under a lock. Pool workers all inside the same remote call mean the pool is exhausted by a slow dependency. Workers all parked in take() mean the work never reaches the pool, so I look upstream. Comparing dumps tells me whether threads are stuck or just slow. I also keep in mind what the detector cannot see: waits on latches, futures or class initialization never show as a deadlock. After the fix, I add what made this slow to find: named threads, timeouts on remote calls, and metrics for queue depth and active workers.
