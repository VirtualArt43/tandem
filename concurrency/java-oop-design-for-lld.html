Design patterns for LLD and machine coding rounds

Choose patterns by responsibility, build a runnable design, and place locks where the business rules must hold.

Asked atRubrikUberRippling
Before this:Encapsulation, composition and SOLIDstatic, class initialization and singletonsIterators and ConcurrentModificationException

A booking design needs more than a convincing class diagram: two customers must never get the same seat. Patterns help you organise the answer; explicit ownership and atomic operations make it correct when requests overlap.

In plain words

At a cinema, one person chooses the pricing rule, another prepares a booking request, and the clerk marks the seat as taken. The clerk finishes changing the register before announcing the booking. You can replace the pricing rule or add an announcement recipient without changing how the clerk protects the register.

Give each job a clear owner. Then decide which jobs may happen together and which must happen one at a time. A design pattern is a reusable way to divide those jobs, not a promise that concurrent requests will work.

Why this matters for concurrency

Strategies become shared collaborators, commands become queued tasks, and observers become callbacks into unfamiliar code. Each boundary raises a question: who owns the mutable state, and can two threads enter it together?

You have the mechanics in inheritance and polymorphism and the principles in encapsulation, composition and SOLID. Here you apply them. The monitor toolkit and executor toolkit explain the threading APIs used below.

Use only the rows the requirements need. Two required fields usually need a constructor, not a builder hierarchy. One fixed algorithm can stay a method until you have a meaningful alternative.

Strategy and factory: behaviour and construction

A strategy gives interchangeable algorithms one interface; the caller delegates to it. A simple factory centralises construction and returns that interface, so callers need not name implementation classes.

The policies are stateless, so sharing them is safe. A lambda could instead capture mutable state: a functional interface is not a thread-safety annotation. A quota-tracking policy needs protection; this service keeps its injected choice fixed.

For runtime replacement, publish a fully constructed policy through a volatile FeePolicy and read it once per quote; its mutable internals still need protection. Here pricing uses integer cents and positive whole hours; Math.multiplyExact rejects overflow with ArithmeticException. Fractional billing needs an explicit rounding rule.

A static creation function is a simple factory. The classic Factory Method pattern uses an overridable creation method in a creator hierarchy; an Abstract Factory supplies related products, such as matching storage and transaction implementations. Do not introduce those hierarchies just to hide one constructor.

Builder: validate before the object escapes

A builder accumulates inputs, then constructs a complete object. Required inputs belong in its constructor; optional inputs get named methods and defaults. Validate the complete combination at build(), and detach the product from later builder changes.

The builder belongs to one thread. The product contains final primitives, strings and an unmodifiable list of strings. List.copyOf does not deep-copy mutable elements; see final, immutability and records. Construction validates request shape, not seat availability: check availability during reservation.

Do not register this as a listener or start a thread from a constructor. Finish construction, then hand off through a defined mechanism such as task submission. See safe publication.

Singleton: choose a lifetime, then inject

A singleton restricts construction, but does not justify global access. Build the service graph in main and pass collaborators through constructors. Tests can then supply fresh state and predictable policies.

ChoiceGuarantee and limit

The enum and holder implementations and initialization proof are in static, class initialization and singletons; the memory-ordering follow up is double-checked locking. Neither idiom creates one instance across class loaders or processes. A singleton booking service still needs atomic reservation.

State: behaviour changes with the lifecycle

A state object implements behaviour for one lifecycle stage. Unlike a strategy chosen by the caller, the current state changes because of domain events. Enum constants with behaviour suit a small fixed lifecycle.

The enum instances have no per-job mutable fields, so jobs can share them. The context owns the lock and current state: checking and changing state is one operation. A separate check followed by a setter would reopen the race; a volatile state reference would not close it.

This models transitions, not execution. Real jobs need failure and cancellation states too: requesting cancellation does not mean the work stopped. Keep external work outside the transition lock and define which completion or cancellation wins. Continue with atomic state machines and cooperative cancellation.

Observer: commit first, call listeners after unlocking

An observer registers interest in changes. The publisher owns the data; listeners react to immutable events. Here, “notify” means calling a listener method, not Java's Object.notify().

For a small, rarely changed listener list, use CopyOnWriteArrayList. Its iterator fixes recipients for one dispatch; subsequent membership changes affect future snapshots. This follows the Java 21 API contract; the iterator lesson explains the mechanism and copying cost.

API card: the surface these designs use

The change stays committed even if a listener throws. This API reports runtime failures and continues; it does not catch serious Errors. A slow listener still delays its publishing caller because delivery is synchronous. Copy-on-write makes membership safe, not listener code.

The lock protects price and version. Calling listeners under it would let arbitrary code delay updates, acquire locks in the opposite order, or re-enter an incomplete operation. Listeners should use the event's price: current() can already return a newer version. Even one publisher can reorder delivery when a listener recursively calls changePrice: later listeners receive the nested event before the outer one.

Publishers can invoke the same listener concurrently. For commit-ordered delivery, assign the version and append the event to a FIFO under the same state lock; one dispatcher removes events under that lock and invokes listeners after releasing it. Submitting to a single-thread executor after unlocking can still enqueue version 2 first. Use nonblocking admission and define overflow, for example reject the update before changing state when the queue is full.

Independent bounded subscriber queues isolate slow subscribers only if admission does not wait for them. Define overflow and shutdown rules; see single-writer designs and backpressure. In this sample, membership is captured at iterator creation, not atomically with the price assignment: subscription changes do not acquire the price lock.

Removal cannot retract a listener from an existing snapshot. Stronger unsubscribe needs a registration with an active flag and an in-flight count guarded together: dispatch checks and increments, unlocks to invoke, then decrements and signals waiters under the registration lock in finally. Unsubscribe disables admission and waits in a loop for zero, releasing the registration lock while waiting and holding no domain lock. Forbid waiting unsubscribe from callbacks, providing nonwaiting removal instead, to avoid waiting for themselves or mutually dependent callbacks.

Command and lock ownership: tasks ask entities to act

A command packages an action, its arguments and its receiver. Runnable and Callable are convenient Java command shapes. Queuing a command does not make its receiver thread-safe or repeat execution harmless.

The invariant here is “a seat has at most one owner.” The registry supplies one stable Seat object per ID; that entity owns the lock. This example creates seats on first use and never deletes or replaces them. A fixed catalogue would instead reject unknown IDs.

computeIfAbsent establishes the mapping atomically; it does not protect later value mutations. Its factory must not modify the same map and can run again after removal, an exception or a null result, so it is not an exactly-once business action. See the Java 21 method contract and concurrent hash maps.

Both A1 commands reach the same lock; A2 has another. Assignment of owner is the success point. If entries could be replaced while callers retained them, old and new entities could each accept an owner: stable identity is part of the proof.

The command record references a mutable service; records are not deeply immutable. Retries need request IDs and an idempotency contract; undo needs a valid compensating action. Cancelling a future is not rollback. Java 21 try-with-resources calls ExecutorService.close(), which shuts down and waits for termination; get() observes task results or failures.

Worked example: reserve two adjacent seats

tryBook(A1) followed by tryBook(A2) is not all-or-nothing: another request can take A2 after your first success. Releasing A1 afterwards cannot erase a partial result already observed.

  1. Make the service coordinate the whole operation. Resolve stable entities and deduplicate IDs.
  2. Acquire both entity locks in ascending seat ID order, consistently across all operations.
  3. Check both seats, then update both while holding both locks. If either check fails, change neither.
  4. Capture one immutable event and publish after unlocking. Coherent two-seat reads must follow the same locking protocol.

A single show lock is simpler when whole-show invariants dominate. Per-seat locks improve independence but complicate batches. Continue with multiple locks, lock granularity and booking design cases.

Lay out a machine coding answer

  1. Pin down the contract. Define inputs, errors, ordering, retries, concurrency and process boundaries. State the invariant.
  2. Write the operations. Prefer tryBook or confirm over public state setters. Define failure results before choosing patterns.
  3. Assign ownership. Values hold inputs and results; entities own state; services coordinate; repositories resolve identities. Inject policies and listeners.
  4. Build a complete path. Wire objects in main, run the happy path and one rejection, then extend. Nested static classes suit a single-file round.
  5. Demonstrate concurrency. Release contenders together with a latch, collect results and worker failures, bound waits and assert invariants. Test independent entities and callback re-entry.
  6. Explain limits. Cover shutdown, slow callbacks, multi-entity operations and multiple server processes.

The command driver checks one execution, not every interleaving. Practise controlled schedules in testing concurrent code; build the full answer in machine coding with concurrency and the Java integration lesson.

Common mistakes

  • Starting with seven patterns. Start with operations; abstract behaviour that actually varies.
  • Sharing a mutable builder. Confine it and detach the finished product.
  • Per-job data in enum constants. Constants are shared; put entity data in the context.
  • Listeners under the entity lock. Capture, unlock, invoke; document failures and delivery order.
  • A concurrent map makes its values safe. Protect their invariants or atomically replace immutable values.
  • A lock per request. Competing requests must reach the same entity lock.
  • Two protected calls are one transaction. Multi-entity invariants need a common protocol.

In the interview

Research reports include Rubrik booking and parking designs, Uber multithreaded schedulers, and Rippling extensible rule-based OOP. They support practising these responsibilities, not claiming each company demands a particular pattern. Expect “add a pricing rule”, “two requests arrive together” and “the listener calls back into you”.

The reservation operation owns the availability check and update. A concurrent map resolves one stable entity per seat; that entity guards its state. Pricing is an injected strategy. I capture events after committing state and invoke observers after unlocking. Multiple seats need one atomic operation with ordered locks.

A Java lock coordinates threads sharing that object. With several servers, enforce the rule at the shared authority, for example through a transactional conditional database update. See optimistic versus pessimistic concurrency control.

Senior depth

Future.get(timeout, unit) bounds the caller's wait, not the command's lifetime. Even cancel(true) only attempts cancellation and requests interruption of running work. For deadline-aware booking, validate the deadline and domain cancellation state under the same lock as reservation, and define that check as the acceptance decision. A successful commit can still precede a delayed response.

Keep request-ID deduplication, the reservation and its saved result in one atomic protocol; retry with the same ID returns that result. If cancellation wins before acceptance, the worker must reject; if booking wins, report its result rather than promise rollback. For bounded lock acquisition use ReentrantLock.tryLock(timeout, unit) with the remaining budget, then recheck the deadline; entering synchronized has no timeout. See timed locking.

Key takeaways

  • Strategy varies algorithms; factory selects construction; builder validates a complete product.
  • State owns lifecycle behaviour; command packages actions; neither supplies synchronization.
  • Singleton initialization safety does not protect later mutation.
  • Observer delivery needs membership, ordering, failure and removal contracts.
  • Keep locks with stable state owners and protect the entire invariant.
  • Demonstrate runnable behaviour and adversarial checks before adding abstraction.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Standard and member pricing must change independently of reservation logic. Which design fits?
Why. Strategy isolates the varying algorithm; a factory can select it. Subclassing the service couples pricing to unrelated behaviour. Singleton describes instance count, not interchangeable pricing. Listeners react to events; placing pricing there does not supply the quote operation's policy.
A builder stores List<Seat>; construction successfully uses List.copyOf(builder.seats). Seat has mutable fields. What follows?
Why. The copy does not clone elements. Later builder list changes cannot alter product membership, but a shared seat can still change. The copy neither synchronizes the builder nor makes seat setters throw: mutations through the unmodifiable list, including set, are rejected. Use immutable values or explicit ownership for elements.
The sample's dispatch captures a CopyOnWriteArrayList iterator containing A then B. A removes B and returns normally; dispatch continues. What happens?
Why. The snapshot retains B, so dispatch still invokes it. Removal affects future snapshots, neither changing existing recipients nor waiting for their callbacks. Snapshot iteration does not throw ConcurrentModificationException when the list changes.
Two publishers commit versions 1 then 2 under one lock and invoke observers after unlocking. Both snapshots contain the same listener, which prints its event's version once per callback. Both callbacks complete. What version order can it print?
Why. The first publisher can pause after unlocking, letting the second deliver first; it can also deliver first without that pause. Commit ordering does not supply callback ordering. Copy-on-write does not merge notifications, so both versions print.
A ConcurrentHashMap returns the same seat to two threads. Both execute if (seat.owner == null) seat.owner = user;. What is missing?
Why. The map protects mappings, not field accesses in its values. Singleton construction and command packaging do not close the check-and-update gap. A final map reference prevents reassignment, not concurrent mutation of seats.
Two threads call apply(START) on the same fresh Job from the sample, with no other operations. Both calls terminate, either returning or throwing. How many succeed?
Why. The job lock serializes checks and transitions. The first changes NEW to RUNNING, so zero successes is impossible; the second checks RUNNING, where START is illegal. Enum sharing does not bypass that lock. Adding volatile changes neither the legal transitions nor the atomicity already supplied by the lock.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
Design a parking lot with interchangeable allocation rules and booking notifications. Where do locks live, and what changes for a truck taking two adjacent spots?
Model answer

Use immutable vehicle and ticket values, an injected allocation strategy, spot entities, a parking service and listeners. The strategy proposes candidates; the service validates and reserves atomically. Each spot owns its occupancy lock and retains a stable identity. For a truck, lock both spots in ascending ID order, check both and update both before unlocking. All allocation and release operations follow that protocol. Capture one immutable ticket event and invoke listeners afterwards. A single lot lock is a simpler baseline if independent allocations are not required.

Debug
The listener list is thread-safe, but bookings stall and displays sometimes show an older price after a newer one. Explain both symptoms and propose tests.
Model answer

Inspect whether callbacks hold a domain lock or block their synchronous publisher. Moving them outside the lock prevents lock coupling, but still permits slow listeners and reordered delivery. Use latches to pause publisher A after version 1 commits, deliver version 2 from B, then resume A. Have a listener check that the publisher does not hold its domain lock. Use ordered dispatch when every event matters; for a latest-value display, atomically reject versions older than the applied one. Bound waits and collect worker failures.

Design
A singleton factory returns shared mutable builders and queues command records for automatic retry. Which guarantees are missing?
Model answer

Singleton initialization does not protect builders. Give each request a confined builder and return a validated, detached product. The factory must state whether results are shared or fresh. A record freezes references, not the receiver, which needs its own synchronization. Retry requires a stable request ID and atomic deduplication with the effect, otherwise a timed-out command can succeed twice. Cancellation is not rollback. Inject the service so tests control its lifetime and dependencies.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Your listener list is a CopyOnWriteArrayList. Why would you still move notifications outside the lock, and what guarantees do I lose?"
What a strong answer covers
  • Thread-safe membership does not make listener code safe under the domain lock
  • Commit state and capture an immutable event plus recipients, then unlock before callbacks
  • Slow or reentrant listeners can delay operations or introduce lock cycles
  • Outside-lock delivery permits reordered and overlapping callbacks; versions identify commits
  • Unsubscribe affects later snapshots and listener failures need an explicit policy
  • Enqueue events in commit order and use bounded serial dispatch for ordered delivery
How a senior would say it
I would move callbacks outside the domain lock because a thread-safe listener list only protects membership. It does not control what a listener does. I commit the state, capture an immutable event and the recipient snapshot, release the lock, and then invoke callbacks. A listener might perform slow I/O, call back into my service, or acquire another lock. Keeping it inside my lock would extend the critical section and could create a lock cycle. Moving it out allows publishers to deliver out of commit order. Publisher one can commit and pause, allowing publisher two to deliver first. The same listener can also be called concurrently, so its own mutable state needs protection. I include the commit version in the event rather than asking listeners to reread live state. Removal only affects later snapshots, so an already-selected callback may still run. I also define whether one listener failure stops delivery; here I collect runtime failures and continue. If ordered delivery is required, I enqueue events in commit order under the state lock and use one dispatcher that invokes listeners after unlocking. That dispatcher needs bounded capacity, an overload policy and shutdown rules. Copy-on-write alone does not provide those guarantees.

Likely follow up: What would unsubscribe need to guarantee that no callback is running when it returns?

Out loudabout 90 s
"You have a concurrent map, a booking command and a pricing strategy. Walk me through what prevents two users getting the same seat."
What a strong answer covers
  • The invariant is at most one owner per seat; patterns alone do not enforce it
  • The registry resolves one stable entity per seat ID throughout operations
  • The entity lock covers checking availability and assigning the owner as one operation
  • Strategy selects behaviour and command packages an action without adding thread safety
  • Multi-seat operations need the required locks in a fixed order and one atomic update
  • Test contention and independent entities; process-local locks do not coordinate servers
How a senior would say it
The seat's atomic reservation operation prevents double booking. The invariant is that each seat has at most one owner. My concurrent map resolves one stable seat object for each ID, and that seat owns a private lock. Inside the lock I check whether it is free and, if it is, assign the owner before releasing the lock. A competing caller reaches the same object and sees the changed state. I must not remove and recreate that entity while callers still hold references, because then two different locks could protect the same logical seat. The pricing strategy only chooses the pricing algorithm. The command only packages the request for execution. Neither makes that check and update atomic. For a request covering two seats, I would acquire both locks in a fixed ID order, check both seats, and update both before unlocking. Two separate successful-looking method calls are not a transaction. I would test two callers released together and assert exactly one winner, then verify that independent seats can progress without sharing a domain lock. Finally, this proof covers threads in one process. With several servers, the shared database or another authoritative owner must enforce the reservation rule.

Likely follow up: How would you add a deadline and an idempotent retry, and define which result wins when cancellation races with booking?
