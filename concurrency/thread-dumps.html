Reading thread dumps and stacks

Capture Java and C++ thread stacks, interpret states and lock ownership, and distinguish deadlocks from slow dependencies.

Asked atRubrik
Before this:Thread states and what blocking really doesDeadlock: the four conditions and how to break each

When a concurrent program hangs or crawls, the fastest route to the cause is a snapshot of what every thread is doing right now. Reading that snapshot quickly is what a debugging round tests, and it is the skill you will use on your first production incident.

In plain words

Picture a restaurant kitchen at 8 pm that has gone quiet. Orders are piling up, nobody is cooking. You do not interview every cook about their evening. You take one photo: the first chef stands at the fridge holding the only big knife, waiting for the pan; the second chef stands at the stove holding the pan, waiting for the knife. One photo, and the problem is obvious.

Take a second photo ten seconds later. If everyone is in exactly the same spot, you suspect a stall, but you still need to check whether orders are getting completed. That photo of every thread, with what each one holds and what each one waits for, is a thread dump.

What a dump tells you

A thread dump captures thread stacks. The exact fields and which threads appear depend on the tool; a traditional Java dump of platform threads gives you four useful clues:

  1. Its name (which is why you name your threads).
  2. Its state: running, blocked on a lock, waiting for a signal, sleeping.
  3. Its stack: the chain of function calls it is inside, innermost first.
  4. The locks it holds and the one it is waiting for (Java prints these for you; in C++ you work them out from the frames).

Capture evidence before a restart when the incident budget permits. A traditional Java dump can pause application threads, with cost depending on thread count and stack depth; attaching a native debugger stops the C++ process until you resume or detach. There is no fixed safe pause budget. Prefer a bounded capture and avoid destroying the evidence unnecessarily.

Taking a dump

Java

For HotSpot on Java 21, find the process id with jcmd (with no arguments it lists discoverable JVMs) or jps -l, then use any of these:

The -l flag matters. Without it you still get platform-thread stacks and monitor information, but not the per-thread list of owned synchronizers such as ReentrantLock. kill -3 is what you use when the JDK tools are not installed in a container: the dump goes to the process's standard output, so look in its log.

Run attach tools with the target JVM's effective user and group, in the appropriate process namespace. Attach can be disabled. kill -3 assumes HotSpot's SIGQUIT handler is active, so check the target and configuration first. From inside a program, ManagementFactory.getThreadMXBean() gives you dumpAllThreads(true, true) and findDeadlockedThreads(), for platform threads only.

One Java 21 detail: the classic jstack and Thread.print output shows platform threads only. For platform and virtual threads, use jcmd 4242 Thread.dump_to_file -format=json /tmp/threads.json. This format omits lock ownership and object addresses, and is not an atomic snapshot of all threads. With jdk.trackAllThreads=false, some directly created virtual threads can be missing; the default is true.

C++

C++ has no built-in dump. You attach a debugger, which stops the process, and ask it for every thread's backtrace:

Interactively, the commands are thread apply all bt in gdb and thread backtrace all (short form bt all) in lldb. sample is what Tandem's Run button uses for a C++ program that hangs. Build with -g so frames have file and line numbers, and with -fno-omit-frame-pointer to improve unwinding. Optimisation can still inline functions, remove frames and make arguments unavailable. Attach requires OS permission; on macOS, process protection can prevent it.

Name your threads so the debugger shows something better than a number: pthread_setname_np takes the thread and a name of at most 15 bytes on Linux, and only the name (for the calling thread) on macOS.

Reading one thread

Java

Here is a representative Java 21 thread from the deadlock demo. Addresses, ids and source line numbers vary by build:

  • The quoted name, then #28, the JVM's thread number.
  • [27651] and nid=27651: the operating system's id for the thread. The format depends on the JVM and platform; nid may be decimal or hexadecimal (nid=0x6c03). Convert bases before comparing. On Linux it matches the thread ids that top -H shows, which is how you find the thread burning CPU.
  • cpu=0.93ms: CPU time this thread has used so far. Compare it across two dumps: rapid growth with repeated frames identifies a CPU hot path, which could be useful computation or spinning. Check completed-work counters before deciding.
  • The state line, then the stack, innermost frame first, with lock lines under the frame that took or wants the lock.

The lock lines are the heart of a Java dump:

Line under a frameWhat it means
- locked <0x...20> (a java.lang.Object)Normally this thread holds the object monitor. Check for the Object.wait() exception below.
- waiting to lock <0x...30>BLOCKED: it wants a monitor another thread holds. Search the dump for locked <0x...30> to find the holder.
- waiting on <0x...>Inside Object.wait(). It released this object's monitor while waiting. It can still hold other locks and block their users.
- parking to wait for <0x...> (a ...ReentrantLock$NonfairSync)This class identifies a parked ReentrantLock contender. Other blocker classes can identify a condition, queue or future; a parking blocker is not necessarily an owned lock.
Locked ownable synchronizers: then - <0x...> (a ...ReentrantLock$NonfairSync)Owned synchronizers, including ReentrantLock synchronizers. The per-thread list is requested with -l.

One trap: a thread inside wait() shows waiting on <0x10> and then locked <0x10> for the same object. The locked line records that it entered the monitor before calling wait(); while waiting it has released it. It does not own that monitor during the wait, but locks on other objects remain held. After notification it must reacquire the monitor before wait() returns, so it can then be BLOCKED.

C++

Here is an illustrative macOS lldb backtrace for the deadlock demo (template noise trimmed; frame numbers and symbols vary):

Nothing says "deadlock". You read it like this:

  • The frame chain identifies the wait; a kernel wait name alone is insufficient: __psynch_mutexwait is a mutex on macOS (__lll_lock_wait or a futex wait inside pthread_mutex_lock on Linux), __psynch_cvwait is a condition variable, __ulock_wait under std::thread::join is a join.
  • The first frame in your code says where: main.cpp:21, the second lock_guard.
  • The arguments say which mutex: thread 2 waits for 0x...8040 and, from from=0x...8000, already holds 0x...8000. Thread 3 is the mirror image. Each holds what the other wants: a cycle.

On Linux with glibc, debugger inspection of the underlying pthread_mutex_t may expose __data.__owner, an implementation detail useful for ordinary mutexes. The layout depends on the library and mutex kind; C++ provides no portable owner query. On Apple libc++, infer ownership from source, scopes and stacks instead of assuming that glibc field exists.

States, and what they usually mean

Java stateC++ top framesWhat the thread is doing
RUNNABLEyour own code, or a system call such as read or recvRunning, ready to run, or blocked inside native I/O. A platform thread blocked in native socket I/O can show RUNNABLE. Java states describe JVM-level activity, not OS scheduling state; some I/O paths park and show WAITING instead.
BLOCKED (on object monitor)__psynch_mutexwait on macOS, __lll_lock_wait on LinuxJava BLOCKED specifically means acquiring or reacquiring an object monitor; a contended ReentrantLock normally parks instead.
WAITING (on object monitor), WAITING (parking)__psynch_cvwait on macOS, pthread_cond_wait on LinuxAn indefinite wait: wait(), Condition.await(), queue take, future get or join. Native frames depend on the library, so read the callers too.
TIMED_WAITING (sleeping, parking, on object monitor)nanosleep, or a timed condition variable waitThe same, with a timeout.

Two readings save the most time:

  • RUNNABLE does not mean busy. A lock holder in native network I/O can look RUNNABLE.
  • WAITING does not mean stuck. Idle pool workers park in take() on their work queue all day, and 190 of them waiting for work can be normal. During an outage, also inspect whether work reaches that pool.

The deadlock report

For platform-thread monitor and ownable-synchronizer cycles, HotSpot does the cycle hunting. A traditional dump can end like this (representative output):

Read it as a chain: A waits for something held by B, and B waits for something held by A. Then come the two stacks, which show the two code paths that take the same locks in opposite orders. A standard fix for this two-lock cycle is a single global lock order (see deadlock).

The report also covers ReentrantLock and supported ownable synchronizers, even without -l: the line reads waiting for ownable synchronizer 0x..., (a java.util.concurrent.locks.ReentrantLock$NonfairSync), which is held by "worker-2". What it cannot see is a cycle through something without an owner: a CountDownLatch, a Semaphore, a Condition, or a future. If thread A holds a lock and awaits a latch that thread B will count down only after taking that lock, you get a permanent hang and no report. The pool self-deadlock (tasks blocking on futures of tasks queued behind them in the same pool) is the same story.

Standard C++ has no equivalent JVM deadlock report. You build the wait-for graph yourself from the frames, exactly as in the lldb example: for each blocked thread, which mutex it wants and which it holds.

See it: a deadlock you can dump

Two transfers lock the same two accounts in opposite orders. The latch makes the deadlock certain on every run: each thread takes its first lock, waits until the other has its first lock too, then reaches for the second. Press Run: the program hangs, and after a few seconds Tandem shows the Java dump or the C++ thread stacks. Find the cycle yourself before reading the report.

std::latch is C++20. In C++17 you would use a counter with a mutex and condition variable, with a predicate that both threads have arrived. A sleep would only change the odds and is not a replacement for this rendezvous.

Two or three dumps, a few seconds apart

One dump is a photo; it cannot tell stuck from slow. A thread parked on a queue in one dump may have been idle for a microsecond. So take two or three dumps 5 to 10 seconds apart and compare the same thread across them:

Across the dumpsReadingNext move
BLOCKED or WAITING in the same frame every time, cycle reportedDeadlockRead the cycle, fix the lock order.
Many threads BLOCKED on the same lock; its holder RUNNABLE in the same I/O frameLock held across slow I/O: a convoyMove the I/O out of the critical section.
Many threads WAITING in the same pool or future call, nothing movingPool or connection pool exhausted, or a self-deadlockWho holds the resources, and what are they waiting for?
RUNNABLE in the same few frames, cpu= growing fastA hot loop: spinning, a retry storm, livelock, or a structure corrupted by unsynchronized writesProfile it; read the loop's exit condition.
Different frames every timeExecution is moving; useful progress is not yet establishedCheck completed work and queue depth. Retries and livelock can move through many frames.

Repeated stacks are evidence, not proof of a stall. A healthy worker can finish many requests and return to the same frame between samples. Conversely, a retry loop can visit different frames without completing a single request. Correlate stacks with throughput, queue depth, per-thread CPU deltas and dependency latency; object addresses may change across dumps after a moving GC.

Worked example: the site that stopped answering

A checkout service's p99 jumps from 40 ms to 8 s at peak. CPU is low. You take two dumps 10 seconds apart. Both show 200 request-pool threads: 179 monitor waiters, one lock holder and 20 idle workers. The waiters look like this:

You search for locked <0x00000000c3a1b0e8> and find exactly one thread:

Diagnosis. The shown wait chain suggests a slow dependency, not a monitor cycle. Absence of a JVM deadlock report does not exclude other dependency cycles. PriceCache.get calls the pricing service while holding the cache's monitor. The pricing service got slow, so one thread sits in a socket read (shown as RUNNABLE) holding the lock, and every other request queues behind it. The remaining 20 threads are idle pool workers parked in take().

Fix. Avoid slow I/O while holding the shared cache lock. Look up under the lock, fetch outside it, then recheck under the lock before storing: another thread may have filled or invalidated the entry. Define stale-result handling, and use a per-key single-flight load if duplicate fetches are unacceptable. Add a timeout to the pricing call. In C++ the same incident shows 179 threads in a mutex wait under PriceCache::get, and one thread in recv whose frames pass through PriceCache::get after its lock_guard.

Common mistakes

  • Restarting first. The restart fixes the symptom and deletes the only evidence. Dump (and in C++, gcore) before you restart.
  • Trusting one dump. Take two or three, seconds apart, and compare the same threads.
  • Reading RUNNABLE as "using CPU". Native socket reads can show RUNNABLE. Check cpu= growth or a profiler.
  • Panicking at hundreds of WAITING threads. Idle workers wait for work. Look for many threads waiting on the same thing that never moves.
  • Forgetting -l in Java. Without it you cannot see which thread holds a ReentrantLock in the per-thread listing.
  • Unnamed threads. Fifty threads called pool-7-thread-N tell you nothing. Name every pool after its job.
  • Debugging a C++ binary without symbols. Keep -g in release builds (you can strip the symbols into a separate file) so reports can resolve source lines; without matching symbols, names or lines may be missing.

In the interview

It shows up three ways. In a debugging round (Rubrik runs one: you get someone else's multithreaded program, often with a deadlock, and must hand back code that runs) the program hangs when you run it, and grabbing the stacks is the fastest way to the bug. In a behavioural or design round: "a service stopped responding in production; walk me through how you debug it". And as a direct question: "here is a thread dump, what is wrong?"

Before restarting anything I take two or three thread dumps about ten seconds apart. If the JVM reports a Java-level deadlock, the cycle and the lock lines give me the two code paths that lock in opposite orders, and the fix is one global lock order. If there is no cycle, I group threads by their stacks: if most are blocked behind one lock, I find the holder and see what it is doing, usually I/O under a lock. If most request threads are parked on a pool or a future, I investigate resource exhaustion or a dependency cycle, and I check what the holders are waiting for.

Follow ups to expect: "How do you tell a deadlock from a slow dependency?" (a cycle, and nothing moves across dumps, versus everyone waiting on one external call). "The JVM reported no deadlock but nothing moves; how?" (a cycle through a latch, semaphore, condition or future, which have no owner). "How do you do this in C++?" (an all-thread backtrace in gdb or lldb, then build the wait-for graph from frames and arguments).

Senior depth

  • Automated detection. A watchdog thread can call ThreadMXBean.findDeadlockedThreads() every few seconds and use the thread ids it returns to retrieve and log stacks, so supported platform-thread lock cycles can trigger an alert with diagnostic evidence. C++ has no standard equivalent; teams use a progress watchdog (if work is outstanding and a progress deadline expires, capture diagnostics; an approved crash policy may use std::abort(), with core dumps enabled) or debug-build lock wrappers that check a lock hierarchy.
  • Find the hot thread. On Linux, top -H -p 4242 lists threads with their CPU use; match the hottest thread id to nid in the Java dump.
  • A profiler is many dumps. Sampling profilers take stacks hundreds of times a second and aggregate them. When one dump is too little and you need "where do threads spend their time", reach for wall-clock profiling (see performance and contention).
  • Virtual threads. In JDK 21, a virtual thread that blocks inside synchronized pins its carrier thread; -Djdk.tracePinnedThreads=full can trace parking while pinned, but does not diagnose every blocking operation. JFR can record jdk.VirtualThreadPinned events when enabled and above its configured duration threshold. Later JDKs change these pinning rules, so state that this diagnosis targets Java 21.

Key takeaways

  • A dump captures thread stacks; names, states and ownership depend on the tool and thread kind. Preserve it before restarting when feasible.
  • Compare several dumps with CPU and completed-work counters. Repeated or changing frames alone do not prove useful progress or its absence.
  • HotSpot can report platform-thread monitor and ReentrantLock cycles, but not for cycles through latches, semaphores, conditions or futures.
  • RUNNABLE can be a blocked socket read; WAITING can be a healthy idle worker.
  • In C++, build the wait-for graph yourself from an all-thread backtrace: the frames say where, the arguments say which mutex.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Two dumps taken 10 seconds apart both show thread "worker-3" BLOCKED with waiting to lock <0xa0>, and thread "worker-9" RUNNABLE inside a socket read with locked <0xa0>. No deadlock is reported. What is the most likely problem?
Why. The shown chain ends in network I/O; it provides no evidence of a two-thread lock cycle. RUNNABLE can describe native I/O and does not prove CPU use. worker-3 is acquiring a monitor, not waiting in a task queue. Move the slow call outside the shared lock while preserving the cache invariant, and check dependency timeouts.
A thread's stack shows - waiting on <0x10> (a WorkQueue) and, two frames lower, - locked <0x10> (a WorkQueue). Does this thread stop other threads from entering synchronized (queue)?
Why. Object.wait() releases the monitor while the thread sleeps and takes it back before returning. Dumps can still print the locked line for the frame that entered the synchronized block. Notification does not transfer ownership; the waiter must later reacquire it, and fairness does not change the release rule. Any other monitors it holds remain locked.
All threads are platform threads, and each described lock cycle is established with indefinite waits. Which hang will NOT produce a "Found one Java-level deadlock" section in a Java thread dump?
Why. The JVM can only follow "held by" edges for things with an owner: monitors and ownable synchronizers such as ReentrantLock. A latch has no owner, so the cycle through it is invisible. You find it by reading the WAITING threads and asking who is supposed to wake each one.
Three dumps taken 5 seconds apart show thread "indexer" RUNNABLE in the same three frames every time, and its cpu= value grew by about 5,000 ms between each pair of dumps. What is the best reading?
Why. 5,000 ms of CPU in about 5,000 ms of wall time is approximately one fully occupied core, even if the thread migrates. It could be a healthy indexing loop, so neither RUNNABLE nor repeated frames proves progress. Blocking or deadlock does not explain that CPU growth.
During an outage, 190 of a service's 200 pool threads show WAITING (parking) inside LinkedBlockingQueue.take, called from ThreadPoolExecutor.getTask. Requests are timing out. What does that tell you?
Why. getTask parking in take() is the normal idle state of a pool worker. Idle workers during an outage point away from the pool: look at the threads that are not idle, and at whatever feeds the pool.
Java onlyTwo platform threads are deadlocked on default, nonfair ReentrantLocks. You run jstack 4242, without -l. What do you see?
Why. ReentrantLock parks threads, so they are WAITING (parking), not BLOCKED. Held java.util.concurrent locks appear under "Locked ownable synchronizers" only with -l, but the JVM's deadlock detection runs either way and prints the "waiting for ownable synchronizer ... which is held by" chain.
C++ onlyA hung C++ program's all-thread backtrace shows thread 2 in transfer(from=0x8000, to=0x8040) and thread 3 in transfer(from=0x8040, to=0x8000), both with top frame __psynch_mutexwait under the second lock_guard. What is happening?
Why. The second lock_guard is the one that is blocked, so each thread already holds the first mutex (its from). Thread 2 holds 0x8000 and wants 0x8040; thread 3 holds 0x8040 and wants 0x8000. That is a two-node cycle. __psynch_mutexwait is a kernel wait, not a spin.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A dump of a hung Java service shows: "pay-1" BLOCKED, waiting to lock <0xB> (an Account), with locked <0xA> (an Account) in Bank.transfer; "pay-2" BLOCKED, waiting to lock <0xA>, with locked <0xB>, also in Bank.transfer; "audit-1" WAITING (parking) in CountDownLatch.await inside AuditJob.run. Explain what happened to each thread and how you would fix it.
Model answer

pay-1 and pay-2 are deadlocked. Both are in Bank.transfer, and each holds one account's monitor while waiting for the other's: pay-1 holds A and wants B, pay-2 holds B and wants A. That is the classic transfer deadlock: transfer(a, b) and transfer(b, a) running at once, each locking its source account first. The JVM would also print this cycle in its "Found one Java-level deadlock" section.

audit-1 is a possible downstream victim. The stack proves it awaits a latch, but not who must count it down. Inspect the latch producers: if successful transfers release it, the transfer cycle explains its wait. The shown evidence does not put it in the two-monitor cycle.

Fix: lock the two accounts in a global order, for example by account id: take the lower id first, then the higher, regardless of transfer direction. Then a cycle is impossible because every thread acquires locks in the same order. With explicit locks, an alternative is timed tryLock: release every acquired lock before backing off and retrying. This needs a deadline and does not itself guarantee freedom from starvation. For the same account passed twice, handle that case separately, especially with non-recursive C++ mutexes. I would also give AuditJob a timeout on its await so a stuck dependency surfaces as an error instead of a silent hang.

Explain
An interviewer says: "Our Java service stopped answering at 3 am. CPU is near zero. Walk me through exactly what you do." Answer as you would out loud.
Model answer

Low CPU with no answers suggests waiting or lack of runnable work, so I want to see what they are waiting for before anything is restarted. I take two or three thread dumps about ten seconds apart with jcmd PID Thread.print -l, or kill -3 if the JDK tools are not in the container.

First I check the end of the dump for "Found one Java-level deadlock". If it is there, the cycle names the threads and locks, and the two stacks show the code paths that lock in opposite orders; the fix is a global lock order.

If there is no cycle, I group the request threads by stack. If most are BLOCKED on one monitor, I search for the thread that holds it and look at what it is doing, typically a remote call or disk I/O inside a synchronized block. If most request threads are parked on a connection pool or a future, I investigate resource exhaustion or a dependency cycle, and I check what the holders are waiting on and whether calls have timeouts. I compare dumps with completed requests and dependency latency; stack changes alone do not prove progress.

If a restart or failover is the chosen mitigation, I preserve the dumps first, and add what was missing: named thread pools, timeouts on every remote call, and alerts on pool saturation.

Write code
Make thread dumps readable: in Java, create a fixed pool of 8 named platform threads and a watchdog method that logs detected monitor or ownable-synchronizer cycles with complete stacks. In C++, show how a thread names itself on Linux and macOS.
Model answer

Thread.ofPlatform().name(prefix, start).factory() is the Java 21 way to get numbered names without writing a ThreadFactory class. findDeadlockedThreads covers supported monitor and ownable-synchronizer cycles among platform threads; it does not cover virtual threads or dependency cycles through latches, semaphores and futures. This example targets HotSpot 21 with monitor and synchronizer usage monitoring supported; portable agents must check the support methods on ThreadMXBean. Close the returned executor when its owner shuts down. The C++ helper returns a pthread error code; use names short enough for the platform, and use std::thread plus an explicit join in C++17. A progress watchdog must distinguish an idle service from outstanding work that has stalled, and core-file creation depends on OS configuration.

Out loudabout 90 s
"Our service has stopped answering, CPU is low, and the dump reports no deadlock. Walk me through your next steps."
What a strong answer covers
  • Preserve evidence with bounded captures before a restart when feasible
  • Use Thread.print with -l for Java platform threads or an all-thread native backtrace for C++
  • Follow monitor or mutex waiters to the owner and inspect its stack
  • Trace futures, latches and pool capacity because no deadlock report does not exclude those cycles
  • Compare repeated stacks with completed work, CPU and dependency metrics
  • Choose a mitigation and a fix that preserve the application invariant
How a senior would say it
I would capture the wait chains before assuming that no deadlock report means no deadlock. If the incident budget allows it, I take two or three dumps a few seconds apart before a restart. For Java platform threads I use jcmd with Thread.print and the long lock listing. For C++ I collect all thread backtraces and detach the debugger promptly. I group request threads by what they are waiting for. If many wait on one monitor or mutex, I find its owner and inspect its application frames. A holder in a socket read suggests a slow dependency while holding a shared lock. If workers wait on futures, I check where the tasks that complete those futures must run. A full pool waiting for tasks queued to itself can deadlock without a JVM report. Latches and conditions also require tracing the code that should release them. Repeated frames are clues, so I compare completed requests, queue depth and CPU deltas too. Then I choose a mitigation, such as failing over or timing out the dependency. The code fix might move I/O outside the lock, with a recheck before publishing the result. I preserve the evidence and reproduce the dependency chain in a regression test.

Likely follow up: How would your capture strategy change if requests run on Java 21 virtual threads?

Out loudabout 75 s
"One thread holds account A and wants B. Another holds B and wants A. What have you proved, and how would you fix it?"
What a strong answer covers
  • Identify a two-thread wait-for cycle with both locks held during indefinite acquisition
  • Explain the Java monitor report and how C++ source and stacks establish ownership
  • Choose a global order on stable unique account ids and handle the same-account case
  • Explain that timeout retries must release acquired locks and do not guarantee fairness
  • Test concurrent opposite-direction transfers and conservation of money
How a senior would say it
Assuming both acquisitions wait indefinitely and neither thread releases its first lock, this is a deadlock. The first thread cannot release A until it gets B, and the second cannot release B until it gets A. In a Java platform-thread dump, I match the waiting and held monitor identities. In C++, I use the blocked acquisition frames and the enclosing guard scopes to establish the same cycle. I would acquire account locks in one global order, using stable unique account ids, regardless of transfer direction. I handle a transfer to the same account separately. In C++ a scoped lock over two distinct mutexes is another option for this operation. I would not just add a sleep. If I used timed lock attempts, a failed attempt must release everything already acquired before retrying, with a deadline; that still does not promise fairness. Finally I test opposite-direction transfers concurrently, verify that they finish, and check that total money is conserved. Removing the hang is only half the fix if the balance update becomes unsafe.

Likely follow up: If the owner is waiting on a latch rather than another lock, what evidence would establish the cycle?
