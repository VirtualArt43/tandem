Semaphores: permits as a resource limit

Use permits to limit concurrency or signal between threads, with correct cleanup, timeouts, fairness and memory visibility in Java and C++20.

Asked atRubrikLinkedInMicrosoftNvidiaGoogle
Before this:Mutexes and RAII guardsCondition variables and monitors

A semaphore is a counter of permits with a waiting room. It is the right tool for "at most N at a time", the core of the answer to "how do you stop a slow database from taking down your whole service?", and the subject of one of the most common theory questions of all: mutex versus semaphore.

In plain words

A small parking lot has a board at the entrance: "12 spaces free". A car may enter only if the number is above zero, and entering lowers it by one. When any car leaves, the number goes up and a waiting car may enter. The attendant does not care which car leaves; any departure frees a space.

That is a semaphore: a count of free permits, a rule that you wait when it is zero, and no notion of who holds which permit. That last part, "anyone can give a permit back", is what makes it different from a lock.

What a semaphore is

Edsger Dijkstra introduced the semaphore in the 1960s with two operations, named P and V after Dutch words. Today they are called acquire and release (also wait and signal, down and up):

  • acquire: if the count is above zero, lower it by one and continue; otherwise block until it is above zero, then lower it.
  • release: raise the count by one; when a permit becomes available, an acquirer can take it.

Both update the count atomically. A counting semaphore normally starts at a nonnegative count N within the API's supported range. A binary semaphore is used with a count of 0 or 1. Two different jobs use the same machinery:

  • Limiting: start at N, acquire before using a scarce resource, release after. At most N threads are inside at once.
  • Signalling: start at 0, the waiting thread acquires, the signalling thread releases. The waiter passes only after the signal, and a signal sent before anyone waits is remembered as a permit.

Both languages also give the semaphore memory effects: everything a thread did before release happens-before everything another thread does after the acquire that took that permit. So a semaphore can safely hand data from one thread to another.

The APIs

Java

java.util.concurrent.Semaphore. new Semaphore(permits) or new Semaphore(permits, fair). The useful methods:

  • acquire() blocks and is interruptible (throws InterruptedException and clears interrupt status); acquireUninterruptibly() keeps waiting but preserves interrupt status on return; acquire(n) takes n permits atomically, all or nothing.
  • tryAcquire() takes a permit only if one is free right now. tryAcquire(timeout, unit) waits up to the timeout and returns false if none arrived.
  • release() and release(n) add permits. There is no capacity fixed by the initial count and no ownership check: extra releases can raise the count above where it started. The representation is bounded by Integer.MAX_VALUE; OpenJDK 21 throws Error on permit overflow.
  • availablePermits() is a snapshot for monitoring, not a check followed by acquisition. drainPermits() is a mutation: it atomically sets the count to zero and returns the old count, even if negative. Do not use it merely to inspect availability.
  • The initial count may even be negative: new Semaphore(-2) needs three one-permit releases before the first acquire() can succeed.

Fairness. By default the semaphore allows barging: a new caller can take a permit ahead of queued waiters. With fair = true, FIFO ordering applies at internal queueing points, not necessarily to invocation, return or work-completion order. Fair admission prevents repeated overtaking, at a possible throughput cost; it cannot make a stalled holder release. Untimed tryAcquire() ignores fairness; tryAcquire(0, TimeUnit.SECONDS) respects it and checks interruption.

C++

C++20 std::counting_semaphore<LeastMaxValue> and std::binary_semaphore (an alias for std::counting_semaphore<1>), in <semaphore>. The template argument is a lower bound on the implementation's supported maximum: max() may be larger. Keep binary protocols at 0 or 1 regardless of that maximum.

  • std::counting_semaphore<10> s(3); starts with 3 permits; the initial count must be between 0 and s.max().
  • acquire() blocks and has no stop-token overload. A std::jthread stop request does not wake it; use timed attempts with an explicit stop check when cancellation matters.
  • try_acquire() may fail spuriously even when a permit exists. try_acquire_for(duration) and try_acquire_until(time_point) are timed attempts; false means no permit was acquired, and spurious failure is permitted here too. Scheduling can delay a return past its deadline.
  • release(std::ptrdiff_t update = 1) adds nonnegative permits. Raising the count past max() is undefined behavior. An extra release in a binary protocol is always a logic error; it violates the library precondition if the new count exceeds the actual max().
  • No fairness guarantee, no ownership, not copyable or movable.

Before C++20, build one from a mutex and a condition variable (build it yourself does exactly that). There is no C++17 standard semaphore. Keep a semaphore alive until all callers have finished using it.

API references: Java 21 Semaphore and the C++20 semaphore specification.

Job one: a limit on a scarce resource

Suppose a database can handle about 50 concurrent queries before it slows down for everyone, but your service has 400 request threads. A semaphore with 50 permits in front of the database client keeps the database inside its comfort zone. Add a timeout, and requests that cannot get a permit quickly fail fast instead of piling up. This is a thread-level bulkhead.

The program below runs 24 slow calls from 8 threads through a semaphore with 3 permits, measures the most calls in flight at once, then shows a timed acquire giving up.

Two habits are worth copying exactly. Acquire before the try, release in the finally (or in a destructor in C++), so the permit goes back on every path, including exceptions, but is never released when the acquire itself failed. And prefer a timed acquire in front of a dependency: an untimed acquire turns a slow database into 400 blocked request threads, which is the outage you were trying to prevent.

A concurrency limit is not a rate limit

A semaphore with 50 permits allows 50 calls at once. With sustained demand and negligible overhead, fixed 10 ms calls imply an ideal throughput of 50 / 0.01 = 5,000 calls a second; fixed 1 s calls imply 50 a second. A rate limiter constrains admissions over time, without directly bounding outstanding calls. Real services often need both; see rate limits versus concurrency limits.

Job two: signalling between threads

A semaphore that starts at 0 is a gate that one thread opens for another. A condition variable notification is not saved for future waiters; a persistent predicate protected by its mutex prevents a lost wakeup. A semaphore release is remembered directly as a permit. Here two threads take strict turns, with one semaphore per turn.

Notice that out is an ordinary, non-thread-safe string, yet there is no data race. The semaphores give mutual exclusion (only one thread holds a turn) and visibility (each release happens-before the next acquire). The same idea, one semaphore per thread, prints 1 to N with N threads in turn, a question Nvidia has asked, with the follow up "now do it with a single counting semaphore".

Binary semaphore versus mutex

A binary semaphore and a mutex both let one thread through at a time, so the question "what is the difference?" is a favourite. The difference is ownership.

The one-line version for the interview: a mutex is a lock with an owner; a semaphore is a counter with a waiting room. Use a mutex to protect data, and a semaphore to count resources or to signal.

Worked example: a connection pool

A pool of N database connections needs two things: a count of free connections that threads can wait on, and the connections themselves. A semaphore does the first; a small locked collection does the second.

This minimal pool assumes distinct, non-null connections and exactly one return per borrow, to the same pool. Callers return in finally or through an RAII lease; double-return and foreign-connection validation are extensions in the practice problem. In C++, C is a connection handle with nonthrowing moves, such as std::shared_ptr<Connection>.

The invariant: the number of idle connections is at least the number of free permits plus the number of threads that hold a permit but have not yet taken their connection. Acquiring the permit before taking a connection, and returning the connection before releasing the permit, keeps it true at every step, so removeFirst never finds the deque empty. Swap the order in giveBack and a woken borrower can find nothing to take.

Why not just a semaphore, or just a lock? The semaphore alone cannot protect the collection: several borrowers may hold permits simultaneously. A lock and condition variable alone also work. The semaphore packages permit waiting and timeouts, plus optional fair admission in Java; C++ offers no fairness guarantee.

Never wait for a permit while holding the collection lock: a returning borrower needs that lock to make a permit available. Returning the most recently used connection first favours warm connections, but the sample has no idle eviction. Also, its timeout covers permit acquisition only; a strict end-to-end deadline must include the collection lock, connection validation and the query itself.

Common mistakes

  • Acquiring inside the try. try { sem.acquire(); use(); } finally { sem.release(); } releases even when acquire threw InterruptedException, creating a permit out of thin air. Acquire first, then try.
  • Releasing after a failed timed acquire. If tryAcquire(timeout, unit) or try_acquire_for(timeout) returned false, you hold nothing; releasing raises the limit for everyone.
  • Using a semaphore as a mutex without enforcing the protocol. A binary protocol can protect data, but permits carry no ownership checks. An extra release may admit overlapping users or violate the C++ maximum. Prefer a mutex for ordinary critical sections.
  • An untimed acquire in front of a slow dependency. Every caller blocks, threads pile up, and the whole service stalls behind one sick database. Use a timed acquire and fail fast.
  • Confusing a concurrency limit with a rate limit. 50 permits is not 50 requests per second.
  • Acquiring several semaphores in different orders. Two threads that take semaphores A then B and B then A can deadlock exactly like two locks.
  • Assuming counting_semaphore<N> enforces your resource limit N. max() can exceed N. Your acquire and release accounting must preserve the application limit; exceeding the library maximum is undefined behavior.

In the interview

Semaphores come up in theory screens and in coding rounds. LinkedIn phone screens have asked "mutex versus semaphore" and "binary semaphore versus mutex"; a Rubrik concurrency round opened with mutexes, locks and semaphores before the coding; Nvidia asked for 1 to N printed by N threads with N semaphores, then with one counting semaphore; a Microsoft round asked a candidate to implement a working semaphore (see build it yourself); and a Google L4 task-scheduling question involved semaphores.

Rubrik interviewers have also questioned a candidate's choice of CyclicBarrier versus Semaphore, and rejected a semaphore-plus-lock answer to the searcher, inserter, deleter problem; commenters pointed to races and suggested a read-write lock plus an insert mutex. A semaphore count alone does not express those exclusion rules; the surrounding protocol matters.

A semaphore is a count of permits: acquire takes one or waits, release gives one back, and it has no owner, so any thread can release. I use it for two things: to cap concurrency on a scarce resource, like 50 permits in front of a database client with a timed acquire so callers fail fast instead of piling up, and to signal between threads, because a release is remembered even if nobody is waiting yet. A mutex is different: it has an owner, only the owner can unlock, it can be reentrant and support priority inheritance. So I protect data with a mutex and count or signal with a semaphore.

Follow ups to expect: "What happens if a thread releases without acquiring?" (the count goes up; in C++ past max() it is undefined behavior), "Is it fair?" (Java: optional; C++: no promise), "How would you implement one?" (a count, a mutex and a condition variable), and "Rate limit or concurrency limit?"

Senior depth

The bulkhead needs bounded waiting too. One semaphore per downstream dependency caps its in-flight work. Timed admission limits individual waiting time, but a flood can still fill the shared request pool with waiters. Bound queues or reject immediately when necessary, set an I/O deadline for admitted work, and remember that a local semaphore does not enforce a global limit across service replicas.

Async work keeps its permit until real completion. A callback on another thread may release it because there is no ownership restriction. A timeout or cancellation request is not necessarily completion: returning the permit while the downstream operation still runs would undercount in-flight work. Release exactly once when the operation actually ends.

Virtual threads move the limit into semaphores. With Java 21 virtual threads, threads are cheap and should not be pooled; the JDK guidance is to limit concurrency with a construct designed for it, such as a Semaphore. The thread pool size used to be the concurrency limit; now the semaphore is.

Fair mode has a cost and a trap. FIFO admission can trade throughput for predictable queue ordering, and with multi-permit requests it can block the line: a fair acquire(5) at the head of the queue holds up a later acquire(1) even while one permit is free. Non-fair mode has the opposite risk: a big request can starve behind a stream of small ones.

Batch acquisition and cancellation need a protocol. C++ has no acquire(n): taking permits in a loop is not atomic. Two callers needing all three permits can each hold some and wait forever for the rest. For all-or-nothing batches, use a mutex and condition variable. The turn-taking demos assume no worker is cancelled; restoring Java interrupt status alone does not wake its peer. A cancellable version must publish a stop state and wake or interrupt every participant without treating a cancellation wakeup as an ordinary turn.

A semaphore is a universal building block. Allen Downey's free The Little Book of Semaphores solves dozens of synchronization puzzles with nothing else, and the searcher, inserter, deleter problem Rubrik asked comes from it. Knowing the patterns there (turnstiles, mutex plus counter, the lightswitch for readers) helps you recognise interview puzzles quickly.

Key takeaways

  • A semaphore is a permit count with a waiting room: acquire takes or waits, release returns, and there is no owner.
  • Use it to cap concurrency on a scarce resource (with a timed acquire, so callers fail fast) and to signal between threads (releases are remembered).
  • In a resource limiter, release exactly the permits successfully acquired, using finally or a destructor. In a signalling protocol, another thread deliberately releases.
  • A mutex has an owner. A semaphore has none; prefer it for counting resources and signalling.
  • Java offers fair admission and can exceed its initial count; C++20 promises no fairness and forbids exceeding its actual max().

A semaphore starts with 2 permits. Five threads each run acquire(); work(); release();. What is the largest number of threads that can be inside work() at the same moment?
Why. Each thread inside work() holds one permit, and only 2 exist. Fairness changes which waiting thread gets the next permit, not how many permits there are.
A resource limiter accidentally calls release() after a timed acquire returned false. The current count is below the representation limit. What happens?
Why. A semaphore has no owner, so it cannot know who is entitled to release. Java adds a permit unless its integer representation would overflow. C++ requires the count to stay within max(), and violating that is undefined behavior. In a resource limiter this is a bookkeeping bug; a signalling protocol may deliberately release from a thread that never acquired.
Which statement about a binary semaphore and a mutex is true?
Why. A mutex has an owner, while a semaphore does not track who acquired. Both can block callers. A semaphore is not reentrant: a second acquire waits for another release, potentially forever. A wrong-thread mutex unlock is not always diagnosed: it is undefined behavior for std::mutex.
A semaphore starts at 0 and a plain integer x starts at 0. Thread A writes x = 42, then releases once. Thread B successfully acquires once, then prints x. There are no other accesses. What can B print?
Why. The successful handoff orders A's write before B's read, so there is no conflicting unordered access and B sees 42. A release sent before B waits remains available as a permit. Initialising the semaphore to 1 instead would remove this proof: B could pass before A publishes.
A service must allow at most 50 concurrent calls to a fragile database and fail fast when saturated. Which design fits best?
Why. The requirement is a concurrency limit, which is exactly what permits express; the timed acquire gives the fail-fast behaviour. A lock serializes to one call. A token bucket limits the rate, not the number in flight. A checked counter is a check-then-act race.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
"What is the difference between a mutex and a binary semaphore?" Answer as you would on a phone screen, in about a minute.
Model answer

Both can let one thread through at a time, but they are different tools. A mutex is a lock with an owner: the thread that locked it is the only one allowed to unlock it, which enables reentrant implementations and ownership-aware diagnostics. Priority inheritance needs platform and lock support; the standard APIs here do not promise it. It is for mutual exclusion: protecting shared data in a critical section.

A semaphore is a counter of permits with no owner: any thread can release, even one that never acquired. A binary semaphore is just a semaphore whose count is 0 or 1. That makes it a signalling tool, one thread releases to let another proceed, and a release sent before anyone waits is remembered. A binary protocol can protect data, but an extra release can break mutual exclusion or violate the C++ maximum, without a required diagnostic. So: mutex for protecting data, semaphore for counting resources and for signalling.

Write code
Wrap a function fetch(url) so that at most 4 calls run at once. A caller that cannot get a slot within 100 ms must fail fast with an error. Write the wrapper in your language.
Model answer

The points a grader checks: a timed acquire, not an untimed one; the release only on the path where the acquire succeeded; the release guaranteed by finally or a destructor even when fetch throws; and an explicit fairness choice in Java. Fair mode prevents queued callers being repeatedly overtaken; it does not promise an exact completion deadline. In C++ there is no fairness option, which is worth saying.

Write code
Three threads must print the numbers 1 to 9 in order, thread 0 printing 1, 4, 7, thread 1 printing 2, 5, 8 and thread 2 printing 3, 6, 9. Use one semaphore per thread.
Model answer

Each semaphore means "it is thread i's turn"; at most one permit is available across them at any time, with the current turn held by a worker between acquire and release, so the threads print strictly in order and the printing is race-free. The C++ version stores the semaphores behind unique_ptr because semaphores cannot be copied or moved, so they cannot live directly in a growing std::vector. The last thread's final release leaves one permit in thread 0's semaphore, which is harmless because nobody acquires it again.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Why would you choose a semaphore instead of a mutex in front of a database client?"
What a strong answer covers
  • Choose a semaphore to bound concurrent calls, with one permit per active call
  • A mutex serializes access to one caller; a semaphore has no owner
  • Acquire with a timeout and release exactly once after successful acquisition, even on failure
  • The permit wait and the database operation need separate deadlines
  • A concurrency limit differs from a rate limit, and waiting requests also need a bound
How a senior would say it
I would use a semaphore because the requirement is several concurrent calls with a fixed upper limit. A mutex around the query would allow only one caller at a time. With fifty permits, each caller takes one before starting the query and returns it after finishing. The semaphore has no owner, so my wrapper must enforce that accounting. I acquire before entering the cleanup scope, then release in finally or an RAII destructor. A timeout or interruption during acquisition must not create a permit. I would use a short admission timeout and a separate database deadline, since getting a permit does not bound the query duration. Fifty permits means fifty calls in flight, not fifty requests per second. Faster calls allow a higher request rate. Finally, I would bound the waiting requests or reject them immediately under overload. Otherwise a semaphore can protect the database while the service still runs out of request capacity. The limit also applies only to this instance unless we coordinate across replicas.

Likely follow up: How do you retain the permit if the database client completes asynchronously on another thread?

Out loudabout 60 s
"Our three-permit limiter sometimes has four calls in flight. What would you inspect first?"
What a strong answer covers
  • Suspect an unmatched release and audit every exit path
  • Acquiring inside a try with unconditional finally can release after interruption
  • A failed timed acquire must not release; successful work must always release
  • Java does not cap permits at the initial count; C++ max need not equal the template argument
  • Check that all callers share the limiter and hold a permit until the real work finishes
How a senior would say it
I would first look for a release without a matching successful acquisition. A common Java bug puts acquire inside a try block and release in finally. If acquisition is interrupted, finally still runs and invents a permit. The same mistake happens when a timed acquire returns false. I would move acquisition before the cleanup scope and release exactly once on every path after success, including exceptions. Java does not enforce the initial count as a capacity. In C++, the template argument is only a minimum supported maximum, so it is not an application accounting check either. I would then check that all callers share the same limiter. For asynchronous calls, I would check that the permit survives until the operation actually completes. Returning it when the request is merely submitted would let real in-flight work exceed the intended limit.

Likely follow up: What changes if cancellation is requested but the downstream operation keeps running?

Out loudabout 60 s
"A producer writes a result and releases a semaphore before the consumer waits. Is the signal lost, and is the result visible?"
What a strong answer covers
  • A zero-initialized semaphore remembers the release as a permit
  • A successful matching acquire publishes writes before the release
  • An initial spare permit would let the consumer pass before publication
  • One permit releases one successful acquisition; it is not a broadcast
  • Repeated handoffs need a protocol preventing overwrite while the consumer still reads
How a senior would say it
The signal is remembered, and the result is visible after the successful handoff, provided the semaphore started at zero. The producer writes the result and releases one permit. If the consumer has not started waiting, that permit stays available. When the consumer acquires it, the synchronization orders the earlier write before the later read, so the result itself can be an ordinary variable. Starting with a spare permit would break the argument because the consumer could pass before the producer writes. There are two other limits. One permit admits one acquisition, so this is not a broadcast gate for many consumers. Also, publication does not protect a later overwrite. If the producer reuses the same result slot, I need an acknowledgement or another permit before it writes again. For multiple results, a synchronized queue is usually clearer than one shared slot.

Likely follow up: How would you use two semaphores for a single producer and consumer sharing one reusable slot?
