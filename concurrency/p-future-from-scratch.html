A future from scratch

Build a primitivehard45 minGoogle L5 coding round; Rubrik system codingGoogleRubrik

A future is one value that arrives later, threads that wait for it, and callbacks that must run exactly once. A Google L5 candidate was asked to build their own version of CompletableFuture, and a Rubrik candidate a JavaScript-style Promise in Java: both motivate this exercise. The exact API and edge cases below are the practice contract.

The task

Build SimpleFuture, a future that any thread can complete and any thread can wait on. It starts pending and changes state exactly once: to completed with a value, or to completed with an error.

  • complete(value) and completeExceptionally(error) try to complete it. The first call wins and returns true; every later call returns false and changes nothing.
  • get() blocks until the future is done, then returns the value or reports the error. Java throws ExecutionException with the original error object as its cause; C++ rethrows the stored exception, preserving its type and data. Reads never consume the outcome: repeated and concurrent callers receive the same result.
  • get(timeout) gives up when its wait budget expires. Java throws TimeoutException; C++ returns std::nullopt. A zero or negative timeout only inspects the current state: report an already completed value or error, otherwise time out immediately. A timeout affects only that call; the future stays pending, other waiters remain registered, and later completion still succeeds.
  • isDone() says whether the future has completed, either way.
  • thenApply(fn) returns a new future that completes with fn(value) once this one completes with a value. If this one fails, the new one fails with the same error and fn never runs. If fn throws, the new one fails with what it threw, including a Java Error or a C++ exception that does not derive from std::exception. Its source and sibling callbacks remain unaffected.

Rules:

  • On success, each fn runs exactly once. Registration and completion are ordered atomically. A callback registered while pending runs in the winning completing thread before that completion call returns. Registration that observes an already completed future runs the callback in the registering thread before thenApply returns. Either path is valid when registration races with completion. No callback order is required.
  • Callbacks run outside your lock: a slow fn must not stop other threads from calling get or isDone, and an fn may call methods of the same future, including thenApply. A callback that registers another callback must not deadlock, and the new callback still runs exactly once.
  • No library futures, promises or latches. Build it from a lock and a condition: in Java synchronized with wait and notifyAll, or ReentrantLock with a Condition; in C++ std::mutex and std::condition_variable.
  • Values may be Java null, empty strings or null C++ smart pointers. A callback may also return such a value. The error passed to completeExceptionally must be non-null, and fn and Java unit must be non-null.
  • Java: both get overloads propagate InterruptedException when interrupted while waiting. This does not cancel or complete the shared future.
  • In C++, T and callback result types are copyable, non-void value types, and callbacks are copyable. Allocation failures and exceptions from copying or moving payloads are outside this exercise. The future must outlive every call made on it, as with any object. thenApply returns a std::shared_ptr because the new future must stay alive until the callback completes it.

What the tests check

  • Pending and completed isDone, first-writer-wins for values and errors, repeated reads, strings and null values.
  • Untimed get blocks until completion. Every getter wakes after success or failure, including a mixture of timed and untimed getters on the error path.
  • A pending timed read expires after about 150 ms; an in-time completion returns promptly. Zero, negative and repeated positive timeouts leave the future and other waiters untouched. An already completed value or error wins even with no wait budget.
  • Callbacks registered before or after completion and chained callbacks run exactly once with the correct value. Thread identity checks enforce the synchronous execution rule on both paths.
  • Early and late failure propagation skips callbacks, preserves the Java cause object or C++ exception type and payload through descendants, and leaves siblings and the source intact when a callback throws. Tests include a Java Error and a C++ thrown integer.
  • Six completers race values and errors over many rounds. Exactly one wins, and every observer agrees with the winning outcome.
  • Four registrars race with both successful and exceptional completion over many rounds. Every derived future completes; successful callbacks run once and failed sources never invoke them.
  • A slow callback does not block get or isDone. A callback can register another callback on the same future during completion and after completion.
  • Java: both get overloads propagate interruption without cancelling the future or another getter. C++: the suite runs under ThreadSanitizer.

Taught in: Build it yourself: a future you can complete and chain

Open them one at a time. Each one gives away a little more.

Start with the state: a done flag, the value or the error, and a list of callbacks waiting for the result. One lock guards all of it. Which of your methods change that state, and what must happen atomically when the future completes?
complete is a check-then-act: "if still pending, store the outcome and mark done". Do both under the lock and return whether you won. get is the classic monitor wait: loop while not done, and wake every waiter (notifyAll, notify_all) when the future completes, because every one of them can proceed.
In thenApply the danger is the gap between "is it done yet?" and "add my callback to the list". Decide under the same lock the completer uses: either you queue the callback while the future is pending (the completer will run it), or you see it done and run it yourself. The completer takes the whole list out under the lock and runs it after unlocking.
The future returned by thenApply is just another SimpleFuture. The callback you register computes fn(value) inside a try block and completes that new future with the result, or with the error if fn threw or this future failed.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why must callbacks run outside the lock, and which thread runs them?
A callback is code you do not control. If it blocks (I/O, or get on another future) while you hold the lock, every thread calling get or isDone waits behind it. If it takes another lock that some thread holds while waiting for yours, you have a lock order deadlock. In C++, a callback that calls isDone() or thenApply on the same future locks a non-recursive std::mutex its own thread already holds; in Java the lock is reentrant, but an incorrect implementation that appends to a callback list during iteration can cause ConcurrentModificationException. Reentrancy alone does not imply that exception. Pure Storage's callback registration question (2021) probes exactly these deadlock and modification cases. So take the list out under the lock, release it, then run the list. This exercise requires the winning completer or the registering thread to run the callback. The Java 21 API gives non-async dependent actions more latitude: another caller of a completion method may also execute them. Async variants use an executor, which matters when a slow callback would occupy an I/O or pool thread.
JavaScript promises chain with then, and the function may itself return a promise. Add that.
That is thenCompose (flatMap): fn returns a future, and the result must be the inner future's outcome, not a future of a future. Create next and use an outcome observer like the solution's private whenDone, which sees either success or failure. On source success, call fn(value) to get inner, then observe inner to transfer its value or error to next. Source failure or a thrown callback also fails next. Success-only thenApply is insufficient to observe every failure. Rubrik's reported Promise exercise motivates this extension; flattening is an additional practice follow up.
Write allOf(futures): a future that completes when all of them do.
Use an outcome observer that handles success and failure. Guard a remaining count and the first recorded error with one lock. Each input records its error if needed and decrements the count, even on failure. The last observer completes the result outside the lock, with that error or a success marker. Zero inputs complete successfully at once. Completing immediately on the first failure is a different, fail-fast contract. anyOf transfers the first observed outcome, whether a value or an error; with zero inputs it stays pending. Neither design needs a thread that blocks on inputs in turn.
How would you add cancel()?
Cancel is one more completer: complete exceptionally with a cancellation error, and the first-writer-wins rule decides whether the cancel or the real result counts. If the computation is already running, signal it cooperatively (a flag it checks, or an interrupt in Java). Java's Future.get reports cancellation with CancellationException rather than ExecutionException. Success callbacks are skipped and derived futures fail, just as on other exceptional completions.
Can you build it without a lock?
Yes. Keep one atomic reference that holds either the final outcome or a stack of waiting callback nodes. complete uses CAS to swap the stack for the outcome and then runs the nodes it removed; thenApply uses CAS to push its node while the state is still a stack, and runs the callback itself once it sees an outcome. Blocking get still needs a way to sleep, such as LockSupport.park in Java or a futex wait in C++ (std::atomic::wait in C++20).
How is this different from std::promise and std::future?
The standard pair splits the write side from the read side. A second set_value throws std::future_error instead of returning false, future::get may be called only once because it moves the value out (std::shared_future allows many readers), and there is no continuation like thenApply. Java's CompletableFuture merges both sides, allows many completers (the first wins) and many readers.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

A future is a tiny state machine guarded by one lock: pending, then done, exactly once. Everything follows from making that one transition atomic and from deciding, under the same lock, what each caller does. A completer either wins (stores the outcome, wakes the getters, takes the callback list) or loses. A getter either sees done or waits. A callback is either queued while the future is pending or run at once when it is done.

Why each piece is there

  • First writer wins, under the lock. "If pending, store and mark done" is a check then act, so the check and the writes happen in one critical section and the return value says whether this caller won. A fast path that checks done before taking the lock lets two completers both believe they won, and the second overwrites the first.
  • Wake everyone. Every getter can proceed once the future is done, so use notifyAll (notify_all). With notify one getter wakes and the rest sleep forever.
  • The callback decision is made under the lock. The timeline below is the classic bug. With the decision inside the lock there are only two cases: the callback is in the list before the completer takes the list, or the registering thread sees done and runs it. Never both, never neither.
  • Callbacks run after the lock is released. The completer swaps the list out while holding the lock, then runs it. A callback may block, take other locks or call this future again; under your lock that means blocked getters, lock order deadlocks, or (C++) a thread locking a std::mutex it already holds. A callback that registers another callback is the sharpest case: by the time it runs, the future is already done, so its thenApply runs the new callback at once instead of appending to a list that is being iterated.
  • Reading the outcome outside the lock is safe. The value and error are written once, under the lock, before done becomes true, and never change again. The completer wrote them itself; a registering thread saw done under the lock, which orders it after those writes. The solution passes the outcome to each callback as arguments so this is explicit.
  • A deadline, not a fresh duration, in get(timeout). Use a monotonic clock and wait only for the time left on each pass. Clamp nonpositive Java durations before deadline arithmetic, so an extreme negative value cannot overflow into a long wait. The C++ predicate overload of wait_for keeps one deadline internally. Timing out never changes the shared state.

Cost

Ignoring payload and callable copies, state checks and the state transition take O(1) bookkeeping. Callback registration is amortized O(1), since growing the list can take O(k). A winning completion traverses its k queued callbacks in O(k), plus their execution cost, after unlocking. Pending callbacks use O(k) memory; waiting and user callback execution can take arbitrarily long.

Senior depth

The production design is more involved than replacing done with an atomic boolean. Publishing the outcome, linking a callback node and claiming its execution must agree even when several threads help complete work. Blocking readers also need waiter nodes and a parking mechanism, plus cleanup for interruption and timeout. The lock-based version makes these ownership decisions visible before you attempt a CAS-based design.

In C++, this exercise deliberately behaves like a shared result: get copies the stored value and never moves it out. Supporting move-only values would require a different API, such as a shared immutable value or a single consuming reader.

How to say it in the interview

The future is a state machine with one transition, pending to done, guarded by one lock. Complete is a check-then-act under the lock, so the first completer wins and later ones return false. Get waits in a loop on a condition, and completion wakes all waiters. For thenApply, the decision "queue it or run it now" happens under the same lock, so a callback is either in the list the completer drains or runs in my thread, never both and never neither. The completer drains the list under the lock but runs the callbacks after releasing it, because callbacks are foreign code.
