CountDownLatch from scratch

Build a primitivewarm-up20 minjava.util.concurrent.CountDownLatch and C++20 std::latch, rebuilt as a monitor

Start N jobs, then wait until all of them are done. Build the gate that makes this safe, including many waiters, timeouts and visibility of the workers' results.

The task

Build a one-shot countdown latch. It starts with a count. Worker threads call countDown() when they finish something; any number of threads can call either await overload to block until the count reaches zero. Once it is zero it stays zero, and present and future waiters may proceed, subject to Java's interruption rule below.

  • countDown() lowers the count by one. When the count reaches zero, every waiting thread is released. Calls after the count is zero do nothing; the count never goes below zero.
  • await() blocks until the count is zero. If it already is, it returns at once.
  • await(timeout) returns true if it observes zero while holding the lock. It returns false only when its waiting budget has expired and the count is still positive. A notification while the count is positive must not end the wait. Use a monotonic clock and preserve the remaining budget across wakeups; lock acquisition, lock reacquisition and scheduling can delay the actual return.
  • Timeouts are in milliseconds. Zero or negative values poll without waiting: true at zero, false otherwise. Huge positive values, including Long.MAX_VALUE or std::chrono::milliseconds::max(), must not overflow into an immediate timeout.
  • A timeout affects only its caller. It neither changes the count nor releases, cancels or poisons other present or future waiters. Only countDown() lowers the count.
  • getCount() returns a synchronized snapshot. All methods must be safe to call concurrently, including extra countdowns racing at zero. There is no FIFO requirement.
  • Accept every nonnegative int starting count, including zero and the largest int. For a negative count, throw IllegalArgumentException (Java) or std::invalid_argument (C++).
  • Writes before the countdowns that take the initial count to zero must be visible after a successful wait. A timed wait returning false does not certify completion. Do not busy wait.

Rules.

  • Build it from one lock and one condition variable.
  • No library help: not the java.util.concurrent latch, Phaser, CyclicBarrier, Semaphore or AbstractQueuedSynchronizer; not C++20's latch, std::counting_semaphore or std::binary_semaphore. The site rejects banned names used in code, including a variable named latch; comments and strings are ignored.
  • Java only: both await methods are interruptible. An interrupt while blocked throws InterruptedException and clears the interrupt status. A thread already interrupted on entry must throw even when the count is zero or the timeout is nonpositive. Interruption leaves the count and other waiters intact. If interruption races with opening the gate, either successful completion or interruption is acceptable.

What the tests check

  • Exact counting, zero and negative construction, the largest starting count, and harmless extra countdowns. Zero and negative timeouts poll correctly before and after completion.
  • Six mixed timed and untimed waiters stay blocked at counts 3, 2 and 1, then all six complete at zero. A timed implementation that broadcasts on intermediate countdowns must recheck the predicate instead of returning early.
  • await(200 ms) on a closed gate returns false after its budget; a five second timed wait succeeds soon after release. A maximum positive timeout remains blocked until release instead of overflowing.
  • A timeout leaves the count unchanged, other timed and untimed waiters blocked, and later waits usable. Once zero is reached, repeated waits keep succeeding.
  • Java: interruption of either overload throws promptly, clears the status and leaves a neighbouring waiter blocked. Preinterrupted calls throw on both closed and open gates, including zero duration polls.
  • Eight counting threads start together and perform 2,000 countdowns while three waiters and a count reader run. Another eight threads perform 800 calls from a count of one to exercise concurrent extra countdowns.
  • Four waiters read eight workers' ordinary, non-atomic results immediately after waiting, before any worker join can provide an extra publication edge. C++ runs under ThreadSanitizer.
  • 64 short rounds with a fixed seed, 1 to 4 counting threads and 1 to 3 waiters in shuffled start order. Readiness checks, bounded observation windows, timed joins and watchdogs keep broken submissions from hanging. These tests exercise schedules; they do not prove all interleavings or force every possible spurious wakeup.

Taught in: Build it yourself: semaphore and latch

Open them one at a time. Each one gives away a little more.

The state is one integer and one condition: "the count is zero". Who waits for it, and how many of them may proceed when it becomes true?
countDown: lock, return if the count is already 0, subtract one, and if it just became 0 wake everybody (signalAll, notify_all). await: lock, wait in a loop while the count is above 0.
For await(timeout) preserve a total budget with a monotonic clock: awaitNanos in a loop in Java, predicate waits in C++. Avoid overflowing a duration conversion or now + timeout; use saturation or bounded chunks. Check the condition before the clock while holding the lock.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

Why must the last countDown broadcast, when a semaphore's release signals only one?
A semaphore's release creates one permit, which one waiter can use. Reaching zero opens the gate for every waiter at once, and nobody needs to signal again: the count never moves after zero. A single notification can leave the remaining untimed waiters asleep indefinitely and timed waiters asleep until their deadlines. The Java broken version demonstrates this. The C++ broken version instead demonstrates unlocked reads of the count.
Why can a latch not simply be reset to N for reuse?
Waiters from the old round may not have woken and re-checked yet. If you set the count back to N first, they re-check, see a non-zero count and go back to sleep in the wrong round. A reusable gate needs a generation number that waiters compare against instead of the count, which is exactly the cyclic barrier.
How does this relate to Rubrik's reported submit and wait for all exercise?
That is a related executor exercise, not evidence that this exact latch implementation was asked. Its task count is not necessarily known up front, so it can go up on submit and down on completion, with waiters waiting for zero. This monitor is sometimes called a wait group. Waiting for pending work to become zero is not a snapshot of everything submitted before a call if later submissions can join the count. Define which tasks the wait covers, then choose a pending counter or completion tracking accordingly. The executor wait for all problem builds it with workers.
Should one timeout or interrupted waiter break the gate for everybody?
No. This one-shot gate records worker completions independently of its waiters. Remove only the caller from the wait. A barrier can have a different contract because its waiting participants must cooperate to complete a round. Also check Java's interrupt status before the open-gate fast path: cancellation on entry still throws.
A worker throws before it calls countDown. What happens, and how do you prevent it?
The count never reaches zero and every waiter hangs. Count down in a finally block (Java) or in a destructor of a small RAII guard (C++), and give waiters a timeout so a lost worker shows up as an error instead of a hang.
How does Java's library latch avoid a lock on every countDown?
The count is an atomic integer and countDown is a compare-and-swap loop that only decrements while the value is positive. The thread whose CAS takes it to zero wakes the queue of parked waiters. Waiters park only after re-checking the count, so a count that reaches zero while a waiter is about to sleep is not missed. This is AbstractQueuedSynchronizer in shared mode.
join, a latch, or a barrier: when do you use which?
join waits for specific threads to end, which does not work for tasks in a pool. A latch waits for N events from any threads; the threads that count down do not wait, and it is single use. A barrier makes a fixed group of threads wait for each other, and it resets itself for the next round.

The idea

A latch is a monitor over one integer. The invariant: the count only goes down, never below zero, and once it is zero every waiter is free to go. countDown changes the state and wakes the waiters when the condition they wait for becomes true; await waits in a loop for that condition.

Why each line is there

  • Return early when the count is already zero. Clamping under the lock makes extra calls after completion harmless. This does not deduplicate jobs: calling twice for one job while the count is still positive can release the gate before another job finishes.
  • Broadcast only on the transition to zero. Waking waiters at every count down would only make them re-check and sleep again; waking them at zero must reach all of them.
  • Wait in a loop. Spurious wakeups exist, so the loop (or the predicate in C++) re-checks the count.
  • The timed wait returns the condition. Both solutions check the count before the clock while holding the lock. If zero is observed then, the wait succeeds; if the budget is exhausted and the count remains positive, it fails. A later countdown cannot retroactively change that result.
  • Keep timeout arithmetic bounded. Java's TimeUnit.MILLISECONDS.toNanos saturates rather than wrapping. The C++ solution measures total elapsed time with steady_clock and waits in chunks of at most 60 seconds, so even the largest millisecond timeout never becomes an overflowing nanosecond deadline. It checks nonpositive budgets before subtracting elapsed time.
  • Cancellation belongs to the waiter. Java propagates InterruptedException and unlocks in finally. Neither timeout nor interruption changes the counter or breaks the condition for another caller.
  • getCount takes the lock too. An unlocked read of a plain int while another thread writes it is a data race in C++ (undefined behaviour, and ThreadSanitizer reports it) and a visibility bug in Java. A tempting "fast path" in await that checks the count without the lock has the same problem.
  • The lock publishes worker results. Each contributing countdown releases the same lock that later countdowns and successful waiters acquire. Those edges make earlier worker writes visible to the waiters, even if the workers have not terminated.

Cost and trade-offs

State checks and counter updates use O(1) work under one lock; the final broadcast can wake O(waiters) threads. Waiting time, lock contention and repeated wakeups are additional costs. The object stores O(1) state, with O(waiters) waiting resources managed by the runtime.

Java's library latch uses CAS on its count and a queue of parked waiters. CAS avoids taking this monitor lock, but contending updates can still retry, and it does not give an individual caller a bounded completion time. One-shot state simplifies the design; correct locking, predicate checks and publication still need to be established.

How to say it in the interview

The latch is a monitor over one counter. countDown locks, ignores the call if the count is already zero, decrements, and when it reaches zero it does a notifyAll, because every waiter can proceed and nobody will signal again. await waits in a loop while the count is positive; the timed version waits against a deadline and returns whether the count is zero, not whether it timed out. It is one shot on purpose; if you need it reusable, I would add a generation counter, which turns it into a cyclic barrier.
