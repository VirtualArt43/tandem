Which pair of sanitizers cannot be enabled in the same build?
Why. ThreadSanitizer and AddressSanitizer both take over memory allocation and shadow memory in incompatible ways, and clang rejects the combination. UBSan combines with either, so the usual setup is two test builds: address plus undefined, and thread plus undefined.
From: Building, debugging and sanitizers
A stress test runs cleanly under ThreadSanitizer, with no reports. What does that establish?
Why. ThreadSanitizer is dynamic: it checks what ran. It never flags a check-then-act made of separately locked steps, because each access is synchronized, and on this Mac it does not report lock order problems. A clean run is evidence, not proof: missing instrumentation, suppressions and detector limitations can hide actual races even on exercised paths. It establishes neither race freedom nor progress nor correct compound operations.

A ThreadSanitizer report says "Write of size 8 ... by thread T3: #0 Cache::put cache.cpp:41" and "Previous read of size 8 ... by thread T2: #0 Cache::size cache.cpp:57", with "Location is heap block of size 64". Both accesses name the same address, put holds the cache mutex, and size does not. Which fix preserves concurrent use and follows that locking discipline?
Why. The report shows a write in put and an unsynchronized read in size of the same 8 bytes. The missing happens-before edge is the lock: if both take the same mutex, unlock in one thread synchronizes with lock in the other. const does not synchronize anything, joining T2 before starting T3 would order the accesses, but violates the required concurrent-use contract, and volatile is not a threading tool in C++.

A program hangs. Which lldb command shows the call stack of every thread at once?
Why. bt all (equivalent to thread backtrace all) prints every thread's stack, which is the thread dump you need for a hang. bt shows only the selected thread, thread list shows one line per thread, and frame variable shows locals of the selected frame. In gdb the equivalent is thread apply all bt.

bt all on a hung program shows thread 2 in std::mutex::lock() called from transfer() at line 30, and thread 3 in std::mutex::lock() called from transfer() at line 30 too. Code and mutex addresses confirm that thread 2 holds A while waiting for B, and thread 3 holds B while waiting for A. What is the diagnosis?
Why. The established A-to-B and B-to-A ownership dependencies form a circular wait, here from transfer(a, b) and transfer(b, a) locking their arguments in order. Two blocked stacks alone would not establish that cycle. A lost wakeup involves waiting for a condition; livelock involves ongoing activity without progress, and these mutex operations are not themselves a data race. Fix with a global lock order or std::scoped_lock over both mutexes.

AddressSanitizer reports a heap-use-after-free: READ by thread T2 inside a lambda, "freed by thread T0" in a destructor called from main. What is the most likely cause in threaded code?
Why. Freed by one thread and read by another is a lifetime bug: something non-owning crossed the thread boundary. Fix the ownership (capture by value, move the data in, use a shared_ptr when lifetimes really are shared) or make sure the thread is joined before the object dies. A counter race or allocation failure does not explain a recorded access to freed storage, and a live owning string capture would keep its own storage valid. Copying a view by value would not provide that ownership.

Two threads each call deposit(1) on the same account, whose plain int balance_ starts at zero. Main joins both, then prints the balance under the mutex. With no other synchronization, what output is guaranteed?
Why. The unnamed guard locks and then unlocks at the semicolon, before the increment. The two conflicting increments are not ordered by those earlier lock scopes or by main's later joins. This is undefined behaviour, so even the apparently plausible range of 1 or 2 is not a guarantee. Each call acquires the mutex only once, so no self-deadlock is implied. This libc++ warns about the discarded guard; the fix is std::lock_guard<std::mutex> lock(m_);, whose lifetime includes the update.

int rc = pthread_create(&t, NULL, work, NULL); fails. Where is the reason?
Why. pthread_create reports an error number directly, such as EAGAIN when resources are insufficient. Print it with strerror(rc); errno does not report this failure. No worker was created, and the output thread identifier is not valid for a join, so there is no worker return value to inspect.

On macOS, sem_t s; sem_init(&s, 0, 1); compiles with a deprecation warning. What happens at run time?
Why. macOS's sem_init reports "Function not implemented"; it neither crashes as its specified failure path nor creates a named object. Using s after that failure has undefined behaviour. Use a mutex and condition variable semaphore, sem_open, dispatch_semaphore_t, or std::counting_semaphore instead.

A thread signals an initialized condition variable c when it has no waiters. Later another thread calls pthread_cond_wait(&c, &m) while owning the valid mutex m. What does the earlier signal guarantee?
Why. A signal stores no permit. The later wait can block indefinitely without another notification, but spurious wakeups are also allowed. With valid arguments, an earlier signal is not an EINVAL error or a cause for the signalling thread to deadlock. Check shared state under the mutex before waiting; if the predicate already holds, skip the wait.

Which std::condition_variable call corresponds to pthread_cond_broadcast?
Why. On the pthread backend, notify_all maps to pthread_cond_broadcast and notify_one to pthread_cond_signal. wait blocks rather than notifying, while wait_for is a timed wait. All woken threads still reacquire their mutex and recheck the predicate.

What is the essential difference between a mutex and a binary semaphore?
Why. A mutex must be unlocked by its owner. A semaphore can transfer a permit between threads, or implement exclusion if callers obey a protocol; ownership is not enforced. There is no universal speed ranking. POSIX supports process-shared forms of both where the implementation supplies them; this is not a promise that every such form exists on macOS. A POSIX semaphore initialized to 1 also does not prevent erroneous extra posts from increasing its count above 1.
