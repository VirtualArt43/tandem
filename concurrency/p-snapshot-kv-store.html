Key-value store with snapshots

Thread-safe structureshard50 minRubrik

A snapshot is a frozen moment that readers can keep using while writers carry on. The first idea, copying the map, costs a full copy per snapshot. The senior answer keeps versions instead, and the hard part is throwing away exactly the versions that nobody can see any more.

The task

Build an in-memory key-value store with snapshots, safe for many threads at once. This is Rubrik's snapshot API.

  • put(key, value), get(key) and remove(key) work on the current state. (Rubrik calls the last one delete; it is remove here in both languages because delete is a C++ keyword.)
  • putAll(entries) applies several keys as one write: no snapshot may ever see some of its entries without the others.
  • takeSnapshot() freezes the current state and returns a new, unique id.
  • get(key, snapshotId) returns the value the key had when that snapshot was taken, or nothing. It throws for an unknown or deleted snapshot (IllegalArgumentException in Java, std::invalid_argument in C++).
  • deleteSnapshot(snapshotId) releases the snapshot, and throws the same way for an unknown or deleted id.
  • versionCount() returns how many values you store, counting every version of every key but not deletion markers. Whenever no call is running, every stored value must be visible either in the current state or in some live snapshot. So overwriting a key frees its old value unless a live snapshot can still read it, and deleting a snapshot frees whatever only it was holding.

Do not copy the store when a snapshot is taken. Keep versions per key instead: this is MVCC, multi-version concurrency control. No call may wait for anything except a short lock.

Worked example: what versionCount must say

Put 10 keys: 10 values. Take snapshot A, then overwrite every key 5 times: 20, because each key keeps the value A sees and its newest value, and the 4 values in between are visible to nobody. Take snapshot B and overwrite once more: 30. Delete A: 20. Delete B: 10. Remove 5 keys: 5. Take snapshot C, then remove key 5: still 5, because C still reads key 5's last value. Delete C: 4.

Where it comes up: a 2019 Rubrik report gives exactly this snapshot API, a 2021 Rubrik round asked for a key-value store with snapshots again, and an Uber round in 2026 asked for get, set and getRange on a key-value store under concurrency, locking only the range being read.

What the tests check

  • From one thread: reads at two snapshots after puts, removes and a putAll; a key removed and put again; unknown and deleted snapshot ids throw; deleting one snapshot leaves another intact.
  • Exact cleanup: the versionCount sequence in the worked example above, step by step.
  • A snapshot never changes: 4 writers keep putting, removing and calling putAll on the same keys while 3 readers check an old snapshot, and take, read and delete their own snapshots. Snapshot ids are never reused.
  • putAll is atomic: a writer replaces 8 keys with batch after batch; no snapshot ever shows two batches mixed, and a reader's next snapshot is never older than its last.
  • 8 writers put and remove their own keys at the same time: nothing is lost, and the version count is exact.
  • Churn: 4 writers and 2 snapshot takers run together; the version count stays within the bound the live snapshots allow, and drops to exactly one per key once every snapshot is deleted.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Copy-on-write and immutable snapshots

Open them one at a time. Each one gives away a little more.

A snapshot does not need its own copy of the data. What if every write were stamped with an increasing sequence number, and old values were kept beside the new ones instead of being overwritten?
Keep, per key, a list of versions (sequence number, value or deletion marker), oldest first. A snapshot is just the sequence number of the last write before it. get(key, snap) is a binary search for the newest version whose number is at most the snapshot's. putAll stamps all its entries with one number, so a snapshot sees all of them or none.
Cleanup: a version must stay if it is the newest for its key, or if some live snapshot's number falls between this version's number and the next version's. Keep the live snapshot numbers in a sorted multiset (TreeMap of counts in Java, std::map in C++) and ask for the first one at or after the version. Prune a key whenever you write it, and prune every key when a snapshot is deleted. A deletion marker with nothing older kept can go too.
For thread safety one reader-writer lock is enough: reads share it; writes, takeSnapshot and deleteSnapshot take it exclusively. takeSnapshot must be exclusive, or a writer can prune the very version a snapshot that is being registered needs.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

deleteSnapshot scans every key. Make it cheaper.
Only keys that were overwritten while the snapshot was live can hold versions it pinned. When a write supersedes a version that a live snapshot still needs, add the key to that snapshot's pin list; deleteSnapshot then prunes just those keys. The other road is lazy cleanup: prune a key on its next write or read, plus a background sweeper for keys nobody touches. That is the trade database vacuum and compaction make: cheaper foreground calls, more memory held for a while.
Readers still take a lock. Make snapshot reads lock-free.
Make each key's version list immutable: a writer builds a new list and publishes it through a volatile field or an atomic reference, and keep the snapshot table in a concurrent map. A reader looks up the snapshot's number, then reads the published list without any lock. Writers still serialize among themselves, and snapshots still register under the writer lock, so pruning never removes a version that a registered snapshot needs. In C++ you need an atomic shared_ptr for the lists; std::atomic<std::shared_ptr> is C++20 but not yet in every standard library, so a tiny mutex around the pointer swap is the portable version.
Uber's version: get, set and getRange(startKey, endKey), locking only the range.
With one lock, getRange blocks every writer for the whole scan. You can lock ranges (stripes over a sorted key space, always taken in key order so two range readers cannot deadlock), but with versions you do not need to: take the current sequence number and read every key in the range at it, exactly like a snapshot read. Writers carry on and the range result is still consistent.
Add transactions: begin, commit, rollback.
A transaction remembers its start snapshot and buffers its writes. Reads see its own buffer first, then the start snapshot. Commit takes the writer lock and stamps every buffered write with one new sequence number, exactly like putAll; rollback drops the buffer. That gives snapshot isolation. To stop lost updates, check at commit that no key you wrote has a version newer than your start (first committer wins) and abort otherwise. Practise it in the transactional key-value store.
A client takes snapshots and forgets to delete them.
Every version from that moment on is pinned forever, so memory grows without bound. Give snapshots a lease that expires unless renewed, cap the number of live snapshots, or hand out a handle that releases itself: an AutoCloseable used with try-with-resources in Java, a destructor in C++. Expose the age of the oldest live snapshot as a metric, because that is what to alert on.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Never overwrite. Every write takes the next sequence number and appends a version to each key it touches; a snapshot is just the number of the last write before it. Reading at a snapshot means "the newest version whose number is at most the snapshot's". The invariant has two halves: a snapshot's answers never change, because versions at or below its number are never altered; and every stored version is the newest of its key or is seen by a live snapshot. The first half gives correctness, the second bounds memory.

Why each line is there

  • One sequence number per write, shared by all of a putAll. Snapshots compare numbers, so a batch with one number appears all at once.
  • Deletion markers. Removing a key appends a marker (a tombstone) instead of erasing, so a snapshot taken before the removal still finds the old value, and readers of the current state see the key as gone.
  • The sorted multiset of live snapshot numbers. A version with number s, followed by a version with number n, is visible to a snapshot at number t exactly when s <= t < n. One ceilingKey(s) or lower_bound(s) answers "is there such a t". It is a multiset because two snapshots taken with no write between them share a number.
  • Prune on write and on deleteSnapshot. A write can make the previous newest version invisible; deleting a snapshot can make versions it alone was holding invisible. Those are the only two events that create garbage.

Cost and trade-offs

get is a hash lookup plus a binary search over that key's versions. A write is O(v log s) for a key with v versions and s live snapshots, because it prunes that key. takeSnapshot is O(log s) and copies nothing. This simple deleteSnapshot scans every key, which the first follow up improves. Memory is one value per live key plus whatever the live snapshots pin, which is why long-lived snapshots are expensive in every real multi-version system. Compare this with copy-on-write, where the store is one immutable map replaced on every write: snapshots are free but every write copies everything.

How to say it in the interview

I will not copy anything for a snapshot. Every write takes the next sequence number and appends a version, with deletes as markers; a snapshot is just the number of the last write, and a read at a snapshot is a binary search for the newest version at or below it. putAll stamps all its keys with one number, so it is atomic for every snapshot. To bound memory I keep the live snapshot numbers in a sorted multiset: a version survives only if it is the newest or some live snapshot falls between it and the next version, and I prune on every write and when a snapshot is deleted. One reader-writer lock makes it thread-safe; takeSnapshot takes it exclusively so a writer can never prune what a new snapshot needs. Next steps would be lock-free reads with immutable version lists, and pin lists so deleteSnapshot does not scan every key.
