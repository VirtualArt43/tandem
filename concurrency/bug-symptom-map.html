From symptom to cause: the bug map

Classify hangs, wrong results, memory growth and latency spikes, then use evidence to distinguish causes and validate a repair.

Asked atRubrikMicrosoft
Before this:Deadlock: the four conditions and how to break eachLivelock, starvation and fairnessThundering herd and cache stampede

In a debugging round or a production incident you never start from the cause. You start from a symptom: it hangs, it is slow, the numbers are wrong. Senior engineers run the map backwards: symptom, then three suspects, then the one tool that tells them apart.

In plain words

A good doctor does not order every test for every patient. Fever with a rash points one way, fever with a cough another, and the doctor picks the one test that separates the likely causes. Ordering everything wastes time; guessing without a test is how mistakes happen.

Concurrency bugs are the same. CPU usage helps you choose which suspects to investigate first, and the first thing to do is notice which one you have.

Two questions before anything else

Before reading any code, answer two questions: is the CPU busy? and is anything making progress? They split the suspects into four useful groups. Treat this as triage, not proof: inspect the affected threads and completion counters, since unrelated busy work can hide a blocked subsystem and one saturated core can look small in a machine-wide average.

No progressSlow or partial progress
CPU idleThreads are waiting: deadlock, a pool self-deadlock, a lost wakeup, or everyone stuck on one dependency with no timeoutThreads mostly wait: lock contention, a lock convoy, blocking I/O, a pool too small for its dependency
CPU busyThreads spin: livelock, a loop on a flag that never changes, a CAS retry storm, a corrupted structure looping, the GC thrashing near out of memoryThreads work but waste it: too many threads switching, false sharing, spinning locks, retries doing duplicate work

Three more rows worth knowing. A spike after a downstream blip that never recovers, even after the downstream is healthy: a retry storm or a queue full of work nobody will use, so look at retry rates and queue age. Rare garbled values (wrong dates, mixed-up strings): a shared mutable helper such as Java's SimpleDateFormat or a reused buffer. Occasional nulls or zeros right after startup: an object published to other threads before it was fully built, covered in safe publication.

Reading thread dumps properly

  1. Take two or three dumps, about ten seconds apart. Repeated stacks are clues, not proof: a healthy worker can repeatedly sample in its queue wait, while a livelocked thread moves through different frames. Correlate stacks with completion counts, queue age and per-thread CPU.
  2. Group threads by identical stacks. 150 threads all parked in a connection-borrow method suggest unavailable connections. Check active borrowers, leaks, connection creation and dependency latency rather than assuming every holder is merely slow.
  3. For blocked threads, follow the owner. For monitor contention and supported ownable synchronizers, Java dumps provide lock identities and ownership information. Follow that chain; a condition, future or semaphore may have no single owner, so instead identify the task or event that could satisfy it.
  4. Know what the states mean. In Java, BLOCKED means waiting for an intrinsic monitor, including reacquisition after Object.wait. Untimed wait, join and parking commonly show WAITING; timed versions and sleep can show TIMED_WAITING. A contended ReentrantLock usually parks rather than showing BLOCKED. RUNNABLE can include native I/O waits, so it does not prove CPU consumption; I/O implemented through parking, including virtual-thread I/O, can show waiting states instead. In C++ you read the frames: on macOS __psynch_mutexwait is a mutex wait and __psynch_cvwait a condition variable wait; on Linux both may appear as futex waits. Such frames identify a mechanism, not its cause; inspect the callers and relevant resource state.
  5. Name your threads. A cycle between transfer-1 and transfer-2, or 30 payment-worker threads parked in one client, explains itself; pool-7-thread-12 does not.

To find which platform thread is burning CPU on Linux, top -H -p PID shows per-thread CPU; match the decimal OS thread id to the native nid in a HotSpot dump, converting bases when it has a 0x prefix. Do not confuse it with the Java thread id or assume a format based only on JDK age.

No reported Java deadlock does not mean no deadlock. A pool can have all workers waiting for queued children, with no monitor cycle for the detector to report. Draw a wait-for graph including tasks, pool slots and permits, not only locks. Java 21's ThreadMXBean monitors platform threads; for virtual threads use jcmd PID Thread.dump_to_file -format=json threads.json and JFR. A virtual thread has no permanent OS thread id, and Java 21 monitor pinning can tie up carrier threads; inspect jdk.VirtualThreadPinned events when that is a suspect.

Catching a stall from inside the process

You will not always be watching when a service hangs. A cheap safety net is a progress watchdog: every worker records a heartbeat when it finishes a unit of work, and a watchdog thread reports any worker that has had work but no heartbeat for too long. In Java it can even print the stuck thread's state and stack. The start gate ensures workers cannot run before the main thread holds the demonstration lock. The sleeps only simulate work and make timing visible: the main thread holds a lock for 600 ms, standing in for a holder stuck in slow I/O.

This is illustrative output; scheduling changes timestamps, stack lines and whether a short stall is sampled. All three workers have a fixed batch, so an unfinished worker has outstanding work. Java's atomic arrays and C++ atomics make heartbeat access safe; joins keep captured storage alive. C++20 supplies std::latch; a C++17 fallback is a mutex-protected start flag with a predicate condition-variable wait.

A production watchdog must distinguish idle from stuck, reset the reporting marker when progress resumes, and use thresholds appropriate to task duration. This short demo reports at most once per worker. A heartbeat, state and stack are separate observations, so a report is a reason to investigate, not proof of deadlock. Keep the watchdog independent of the pool it observes, rate-limit diagnostic capture, and monitor externally too: a paused JVM or CPU-starved process may not run its own watchdog.

The 30-second scan of someone else's threaded code

Debugging rounds hand you code you have never seen. Before running anything, scan for the classics; most planted bugs are on this list:

  • Shared mutable fields read or written without the lock that guards them elsewhere.
  • if instead of while around a wait; a notify where waiters wait for different things; state changed outside the lock that guards the wait.
  • Two locks taken in different orders on different paths; a lock held across I/O, a callback or future.get().
  • Check-then-act on a shared map or on a balance; get followed by put.
  • Unbounded queues; waits and calls with no timeout.
  • InterruptedException swallowed in a worker loop; a shutdown that never wakes blocked workers; tasks blocking on the same pool.
  • C++: a thread that is never joined, a detached thread using objects that die before it does, a lambda capturing a local by reference that the thread outlives, a container returned by reference from under a lock.

Worked example: a debugging round, one symptom at a time

Imagine a 150 line ticket booking exercise inspired by reported Rubrik debugging rounds; the following bugs are a teaching scenario, not a claimed transcript. The brief: "under load it sometimes hangs, and sometimes sells the same seat twice". Treat these as two separate bugs.

  1. The hang. Run the load test until it hangs and take a thread dump. Two threads are BLOCKED: booking-3 holds the lock of show 12 and waits for show 7; booking-8 holds show 7 and waits for show 12. The code's transfer(from, to) locks its arguments in order. Fix: lock in a global order (by show id) everywhere both locks are taken.
  2. The double sale. A wrong result under load, so audit the writes. book(seat) does if (seat.isFree()) seat.assign(user) with isFree and assign each synchronized: a check-then-act. Fix: one synchronized method that checks and assigns, or a compare-and-set on the seat's owner.
  3. Look for the third bug. Planted bugs often come in threes. The consumer waits with if (queue.isEmpty()) wait();: after a spurious or stolen wakeup it can try to consume from an empty queue. Fix: recheck in a loop. Separately inspect notify(): it can strand useful work if producers and consumers share one wait set; use separate conditions or broadcast. A loop alone does not repair missing notification.
  4. Leave it compiling and running. Rerun the load test and, for C++, ThreadSanitizer. A Rubrik candidate reported fixing the main deadlock in a debugging round and still losing the round because the fixed code no longer compiled.

Common mistakes

  • Reading code before classifying the symptom. CPU idle or busy, progress or none: two questions that halve the search.
  • Diagnosing from one thread dump. Take several, seconds apart.
  • Trusting averages. Starvation and periodic spikes live in percentiles and per-tenant breakdowns.
  • "It went away when I added a log line." Logging changes timing; the race is still there.
  • Restarting without capturing evidence. Take the dump (and a heap dump if memory is involved) before the restart.
  • Fixing the symptom: a bigger pool for a pool deadlock, a longer timeout for a lock cycle, more memory for an unbounded queue.
  • Treating RUNNABLE as "using CPU". A native socket wait can have this state; check frames and measured CPU, not just the label.

In the interview

Rubrik runs dedicated debugging rounds (reported in at least six loops): someone else's multithreaded program, often a deadlock or a producer-consumer bug, and you must return code that compiles and runs. Microsoft has asked candidates to predict the output of multithreaded C++ and then find its issues, and to spot problems in a snippet "assuming there is multithreading involved". Senior interviews may also ask "tell me about a hard production issue".

First I classify: is the CPU busy or idle, and is anything making progress? A hang with an idle CPU means threads are waiting, so I take two or three thread dumps a few seconds apart and look for a lock cycle or for many threads parked in the same frame. A busy CPU with no progress suggests spinning, retries or GC, so I take a CPU profile. Wrong numbers under load suggest a race or another invariant violation, so I audit the shared state and reproduce it with controlled tests, plus ThreadSanitizer for C++. Memory growth suggests retention or backlog, so I chart queues and thread count and inspect allocations.

For the war story, use the shape symptom, wrong theory, evidence, mechanism, fix, prevention: "p99 went from 40 ms to 8 s; CPU was low, so I checked waiting threads rather than assuming CPU saturation; the dumps showed all 200 workers parked in one client; the dependency had slowed down and the pool had no bulkhead; we added a concurrency limit with a timeout and an alert on its rejections."

Senior depth

A clean race detector is not a correctness proof. C++ ThreadSanitizer observes executed memory accesses; it can miss unexecuted schedules, and it will not diagnose a logical check-then-act made entirely of atomic operations. In C++, a plain flag read racing a write is undefined behaviour, not merely an old cached value. In Java, a plain flag can remain unseen; use the required happens-before edge, not sleeps. jcstress explores small Java concurrency outcomes but does not prove an entire service correct.

Turn the suspected mechanism into a regression: use a latch to place two operations at the vulnerable boundary, assert the exact invariant, and use a deadline to detect lack of progress. Include cancellation, failure and shutdown, then stress additional schedules. On this Mac, ThreadSanitizer does not diagnose lock-order inversions; use stacks and a wait-for graph for deadlocks. More logging or one passing load run can merely change the schedule.

Key takeaways

  • Start with two questions: is the CPU busy, and is anything progressing?
  • Hang with idle CPU: thread dumps. CPU pegged without progress: CPU profile. Wrong counts: audit writes, stress test, ThreadSanitizer. Slow growth: metrics over time and a heap dump. One slow tenant: per-tenant breakdowns and lock profiles. Periodic spikes: line timestamps up with GC, cron and expiry.
  • Take several dumps, group stacks, follow lock owners, and remember that Java's RUNNABLE includes blocked I/O.
  • A progress watchdog with per-worker heartbeats catches stalls you are not watching for, and should capture a dump when it fires.
  • In a debugging round, separate the symptoms, scan for the classic bugs, and leave the code compiling and running.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Requests stop completing. CPU is near zero. Two thread dumps ten seconds apart show the same two threads, each holding one lock and waiting for the lock the other holds. What is it, and what was the right first tool?
Why. Idle CPU plus threads waiting in the same frames across dumps means waiting, not spinning, and a lock cycle in the dump is a deadlock by definition. A thread dump is a useful first tool here. HotSpot can report supported monitor and ownable-synchronizer cycles, but a task dependency deadlock may have no such report. Livelock needs active retries; neither heap retention nor starvation explains the demonstrated lock cycle.
Four workers consume roughly four cores of CPU and complete no work. A CPU profile shows all the time in a loop while (!ready) { } inside four worker threads. Each reads a shared plain boolean ready; another thread wrote true with no synchronization. Which diagnosis is correct?
Why. The profile locates active spinning, not blocked locks or GC. Java permits reuse of a plain field read; C++ gives no valid execution guarantees for this data race. Use Java volatile or an atomic, or C++ std::atomic<bool> with suitable ordering; C++ volatile is not synchronization. There is no competing read-modify-write here to lose an update. Visibility repair still leaves a busy loop, so a latch or condition wait is usually preferable.
Memory grows slowly for hours and the process dies at peak traffic. The work queue was created without a practical capacity limit, and retained queued jobs dominate the heap. In Java this could be a default LinkedBlockingQueue. What is the fix?
Why. Producers outpace consumers and nothing pushes back, so the backlog lives in memory until it runs out. More memory only delays the crash, and a non-blocking unbounded queue has the same problem. GC cannot reclaim jobs still reachable from the queue. A bound turns the overload into backpressure or a visible rejection.
An atomic counter starts at 0. Each of two threads reads it into its own local variable, then stores that local value plus 1. A test gate ensures both reads finish before either store. Main joins both threads and prints the counter. Java uses AtomicInteger.get() and set(); C++ uses default std::atomic<int>::load() and store(). What prints?
Why. Both local reads are 0, so each atomic store writes 1 and the joined result is 1. Atomic accesses prevent a C++ data race, but separate reads and stores do not form an atomic increment. Zero is impossible after both stores; two requires atomic read-modify-write operations or locking the whole update. ThreadSanitizer can remain clean despite this logical lost update.
You take two thread dumps ten seconds apart. Thread A is in the same frame, waiting on the same lock, in both. Thread B is in a different frame each time. What do you conclude?
Why. A could have remained blocked or returned to the same lock between samples. B could be doing useful work or cycling through a livelock. Dumps expose waits and execution locations, but completion counters and the wait-for graph establish useful progress. Thus neither "both stuck" nor "B stuck" follows, and saying dumps offer no evidence is also too strong.
Repeated observation shows a consumer asleep on its not-empty condition while the queue contains 500 items. There is no lock owner, shutdown, competing consumer or further notification. Which bug should you investigate first?
Why. Useful work is stranded with no signal path to resume the consumer. Check predicate reads and writes under the same mutex, atomic release-and-wait, and notifications to the correct waiters. Signalling before a waiter arrives is harmless when the protected predicate is checked correctly: notifications are not stored, but state is. An if instead of while separately allows unsafe progress after a spurious or stolen wakeup; a loop cannot manufacture a missing notification. No active spinning, retained-memory evidence or lock cycle supports the other options.
Java onlyA Java 21 platform thread is reported as RUNNABLE, with its stack inside a native socket-read path. Which conclusion is justified?
Why. RUNNABLE is a JVM state, not an OS CPU measurement. Native I/O can wait in that state; other I/O paths park and show waiting states. BLOCKED specifically describes intrinsic monitor contention. Neither CPU use nor a universal socket state follows from this snapshot.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
An API's p99 latency went from 40 ms to 8 seconds during a busy hour. CPU on the service was 15 percent. Three thread dumps show 180 request threads waiting in AuditClient.send to borrow a connection and the other 20 waiting for audit responses while holding all 20 connections; the audit service's own latency rose from 5 ms to 4 seconds at the same time. Explain what happened, the immediate mitigation, and the lasting fix.
Model answer

Low CPU and threads parked in the same frame mean the service was waiting, not working. Every request calls the audit service synchronously, through a pool of only 20 connections. Assuming one call per connection and mean holding time rising from 5 ms to 4 seconds, the approximate saturated throughput ceiling falls from 20 / 0.005 = 4,000 to 20 / 4 = 5 calls a second. Continued arrivals above that rate grow the queue; the dumps, not CPU percentage or Little's law alone, show that request threads are now waiting.

The connection limit bounds audit calls but does not isolate request threads from waiting. Confirm acquisition and call deadlines rather than assuming none exist. Immediately cap waiting and fail fast or shed requests according to the audit contract.

Do not silently drop audit records: if durable recording is required, persist an outbox or durable log before acknowledging success, with bounded backlog and rejection when storage is exhausted. If the product explicitly permits best-effort audit, a bounded asynchronous queue with a documented drop policy may suffice. In either case, drain with an isolated worker budget, bound retries and dependency concurrency, and alert on queue age, rejections and dependency latency.

Explain
"Walk me through how you would debug a service that hangs in production." Answer the way you would out loud.
Model answer

First I check two things: whether the CPU is busy and whether anything is still completing. If the CPU is idle and nothing completes, threads are waiting, so before restarting anything I capture evidence: two or three thread dumps about ten seconds apart, with jstack or jcmd for Java, or sample, lldb or gdb for C++. I group the threads by stack.

A supported lock cycle means a deadlock and I look for the inconsistent lock order. Many threads parked in the same frame point to what they wait on: Future.get inside a pool makes me check whether all worker slots wait on children queued to that same pool. Condition.await with stable work available makes me inspect the predicate and notification protocol. Socket reads and connection borrows make me check dependency latency and deadlines. None of those frames alone proves the cause.

If instead the CPU is busy with no progress, I take a CPU profile to distinguish retries, spinning and GC. After capturing evidence I choose an appropriate mitigation or restart, fix the root cause, and add prevention: timeouts on every external wait, consistent lock ordering, bounded queues, named threads, and a watchdog or alert that captures a dump the next time progress stops.

Design
What would you export from every thread pool and queue in a service so that the next concurrency incident is obvious from the dashboards?
Model answer

For every queue: its depth and the age of its oldest item, because depth alone hides a slow consumer while age shows how long work has been waiting. For every pool: active threads versus pool size, tasks submitted, completed and rejected per second, and task run time as a histogram, so I can see saturation, rejections and slow tasks separately.

For every dependency: in-flight calls, latency percentiles, timeouts and the rejections of any concurrency limit around it. For locks that matter: wait time from a contention profiler such as JFR, sampled in production. Use bounded-cardinality tenant and endpoint breakdowns or sampled traces, because averages hide starvation and an unbounded label per tenant can itself exhaust monitoring resources.

Then alerts on queue age, rejection rate and a stalled-progress watchdog, with rate-limited diagnostic capture where appropriate. A pool self-deadlock can show busy worker slots with zero completions; a slow dependency can show in-flight calls at their limit with growing wait time; starvation can show one tenant's queue age climbing while others complete. These patterns guide investigation, rather than uniquely identifying a cause.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Requests have stopped completing, but CPU is low. Talk me through your first few minutes of debugging."
What a strong answer covers
  • Confirm the affected workload, completion rate and per-thread CPU rather than relying on one aggregate
  • Capture repeated stacks and correlate them with queue age and dependency latency
  • Follow a wait-for graph through locks, futures, permits and worker slots
  • Distinguish a lock cycle, pool self-deadlock, broken notification and slow dependency using evidence
  • Choose contract-preserving mitigation and validate the mechanism with a controlled regression
How a senior would say it
I would capture evidence and find what the requests are waiting for. Low CPU points me towards waits, but it does not identify the cause or rule out a saturated dependency. First I check which endpoints stopped completing, the age of queued work, and whether one thread or core is still busy. Then I take repeated thread dumps and correlate them with those metrics. I group matching stacks and follow the resource each group needs. A monitor cycle establishes a lock deadlock. If all pool workers are waiting on futures whose children are queued to that same pool, that is pool self-deadlock even without a Java deadlock report. A consumer sleeping while work remains available makes me inspect the predicate and notification protocol. Threads waiting for connections make me examine dependency latency and acquisition deadlines. Repeated stack frames alone are not proof: healthy idle workers can stay in a queue wait, and livelocked threads can change frames without completing anything. Once I have evidence, I restore service with a suitable limit, timeout, rollback or restart. I would preserve required work, especially durable records. Then I reproduce the actual mechanism with controlled scheduling, assert the safety or progress invariant, and add bounded diagnostics so the next stall captures useful evidence.

Likely follow up: What would you do differently if CPU were high but completions were still zero?

"Two callers occasionally reserve the same seat, but ThreadSanitizer is clean. Does that clear the code? Explain what you would test."
What a strong answer covers
  • A clean ThreadSanitizer run does not exclude logical races or unexecuted schedules
  • Separately synchronized availability checks and assignments can both succeed logically
  • Walk through both callers observing free before either reserves
  • Protect check and assignment together or use a conditional atomic ownership transition
  • Force the vulnerable interleaving and assert one winner, then exercise failure and cancellation
  • Separate C++ data-race undefined behaviour from a race condition using otherwise safe operations
How a senior would say it
No. A clean ThreadSanitizer run does not prove that the reservation operation is atomic. It checks executed memory accesses for data races; a logical race can consist entirely of individually synchronized operations. Suppose checking availability takes the seat's mutex and releases it, and assigning the owner takes that same mutex separately. Caller A checks and sees free. Before A assigns, caller B also checks and sees free. Both callers then assign and report success. There may be no unsynchronized memory access for the sanitizer to report, but we have violated the invariant that one available seat has only one winner. I would put the check and assignment inside one critical section, or use a compare-and-set that changes the owner only if it is still unassigned. To reproduce the old bug, I would use a test gate between its check and assignment so both callers reach that boundary. The regression for the repaired API races two reservations and asserts exactly one success, a consistent owner, and completion within a deadline. I would also exercise cancellation and any failure after reservation. Finally, I would keep sanitizer coverage for actual memory races: in C++ those are undefined behaviour, whereas this example is a race condition even though its component accesses are protected.

Likely follow up: How would you make reserving two seats all or nothing without deadlocking?
