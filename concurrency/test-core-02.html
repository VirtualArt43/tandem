A worker thread sets result = 42 on a plain field (no lock, no volatile, no atomic) and returns. Main calls join on it and then reads result with no lock. What does main see?
Why. Thread termination followed by a successful join is a synchronization edge in both Java and C++: the worker's writes are visible after join returns, so there is no data race. The tempting answer, "the read is not synchronized", misses that join itself is the synchronization.

Why. The rule is about lifetime and races, not about where data lives. A worker runs while (!stop) { doWork(); }, where stop is a plain boolean field (not volatile, not atomic). Main sets stop = true. What can happen?
Why. Without volatile or an atomic there is no guarantee the worker ever re-reads memory: the compiler may hoist the read out of the loop. Why do Java and C++ give you no safe way to kill another thread?
Why. The danger is broken invariants: a thread killed between two related writes leaves the data inconsistent. Operating systems can stop threads, but the language cannot make that safe. Thread.stop() throws UnsupportedOperationException since Java 20, and std::thread has no such member.

A stop request (Java interrupt(), or C++ request_stop() with a stop-aware wait) arrives while the worker is still computing, before it reaches its next blocking wait. What happens when it reaches that wait?
Why. Interrupts and stop requests are state, not signals: they stay set until someone handles them, so a late wait still sees them. That is the key difference from notify, which wakes only threads that are already waiting and is lost otherwise.

Code takes a lock by hand (rlock.lock() on a ReentrantLock, or m.lock() on a std::mutex), then a call throws before the matching unlock, with no finally and no guard. What happens next?
Why. Only synchronized and RAII guards release on unwinding. A manually taken ReentrantLock or std::mutex is released only by an explicit unlock, which the exception skipped. In your hand-built thread pool, the worker loop calls each task with no try and catch around it. A task throws. What happens in each language?

Why. Exceptions do not cancel other threads, and printing does not inform the caller. Exiting the process kills unrelated work and skips cleanup. The correct design needs all four parts: record the first failure atomically, request cancellation, join everything, rethrow.

A thread-local counter starts at 0 in each thread. Two threads each increment it 1,000 times, with no lock. Afterwards each reads its counter, and a third thread, which never incremented it, reads it too. What do they read?
Why. Each thread has its own copy, so there is nothing to race on and nothing is lost: each copy counts exactly that thread's increments. The third thread's copy was never touched, so it holds the initial value (0 here). That is also why a thread-local cannot be used to count totals across threads without merging the copies.

Java onlymain starts a non-daemon thread that loops forever, then main returns. What happens?
Why. Returning from main does not end the JVM while a non-daemon thread is alive. Platform threads created with new Thread inherit daemon status unless it is changed before starting; virtual threads are always daemon threads. A fixed thread pool uses non-daemon threads by default, so forgetting shutdown() can keep the program alive. Explicit JVM exit can terminate non-daemon threads too.
From: Thread-local storage, daemon threads, sleep, yield and priority
C++ onlymain creates a std::thread that loops forever, calls detach() on it, and returns. What happens?
Why. Returning from main calls std::exit, and the process ends regardless of other threads. std::terminate happens only when a still-joinable std::thread object is destroyed; a detached thread is no longer joinable. Keeping the process alive for a thread is exactly what Java's non-daemon threads do, and C++ has no such concept.
