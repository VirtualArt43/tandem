Reordering by the compiler and the CPU

Why other threads can see your writes in a different order than you wrote them: compiler and CPU reordering, store buffers and two litmus tests.

Before this:Visibility: why a thread may never see your write

Inside one thread, your code always seems to run in the order you wrote it. Other threads get no such promise. They can see your writes in a different order, and that single fact explains the strangest "impossible" outputs in concurrent code.

In plain words

You post two postcards to a friend, one after the other: "the key is under the mat" and then "the door is open, go in". The post office delivers both, but not necessarily in the order you posted them. Your friend may read "go in" first, try the door, and find no key. From inside your own house the order was obvious; from outside, all your friend has is the order of arrivals.

Compilers and CPUs are the post office. They may perform your memory operations in a different order whenever your own thread cannot tell the difference, because that makes code much faster. Another thread can tell the difference, and unless you use synchronization, it is allowed to.

Program order is a promise to one thread

program order is the order of operations in a thread's source code. The language promises that a single thread observes its own operations as if they ran in that order. This is the as-if rule: the compiler may do anything that a single thread cannot detect. Writing a = 1; b = 2; and then reading b and a in the same thread will always show both writes.

That promise says nothing about what other threads see. If the two writes are independent, the compiler may emit them in either order, the CPU may make them visible to other cores in either order, and a reader may perform its own two reads in either order. All of this is reordering, and it happens at three levels:

WhoWhat it doesWhy
The compiler (and the Java JIT)Schedules instructions in a different order, keeps values in registers, merges or removes repeated loads and stores, hoists reads out of loopsFewer memory accesses, better instruction scheduling
The CPU coreExecutes out of order, starts loads early (speculatively), and parks stores in a store buffer while it keeps goingMemory is slow; waiting for each access in turn would leave the core idle most of the time
The memory systemLets a later load complete before an earlier store has reached other coresThe store buffer, again: a store becomes visible to other cores only when it drains

Hardware differs in how much it reorders. On x86, only one kind is visible: a load may complete before an earlier store to a different address is seen by other cores. ARM (including Apple M series chips and AWS Graviton servers) and POWER allow all four kinds: load then load, load then store, store then store, and store then load. The compiler can reorder all four on every CPU. So "x86 is strongly ordered" does not save you.

The store buffer

When a core executes a store, it does not wait for the cache line to be fetched and claimed. It writes the value into its private store buffer and moves on; the buffer drains to the cache a little later. The core's own later loads check the store buffer first, so the thread always sees its own writes. Other cores read from the caches, where the value has not arrived yet. For a short window, the writing core knows a value that nobody else can see, and its next load can run before its earlier store is visible. That is store then load reordering, and it happens even on x86.

Litmus test 1: store buffering

A litmus test is a tiny program that asks whether one particular outcome is allowed. This one is called store buffering. Two shared variables start at 0; each thread writes one and reads the other.

Think about the interleavings. If A runs first, r1 = 0 and r2 = 1. If B runs first, r1 = 1 and r2 = 0. If they overlap, both read 1. In every interleaving at least one thread has written before the other reads, so r1 == 0 and r2 == 0 looks impossible. It is not:

Here is a harness that runs the test many times. Each round, main resets x and y, starts both threads at the same instant, waits for both to finish, and counts the rounds where both reads returned 0. In Java the test variables are plain fields. In C++ they are atomics with std::memory_order_relaxed: atomic, so there is no data race and no undefined behavior, but with no ordering promise between the store to one variable and the load of the other, which is the freedom that matters here.

The count changes with the machine and the run. On the Apple M chips this site runs on, the Java version shows it in most rounds, because both threads start in lockstep and the JIT may also swap the store and the load. The C++ version runs under ThreadSanitizer, whose bookkeeping slows every access and narrows the window, so expect tens to a few hundred. On x86 you will see it too. What matters is that the number is not zero.

Try the fix. Press Edit and make x and y volatile in Java, or delete the std::memory_order_relaxed arguments in C++ so the four operations use the default, sequentially consistent order. Run again: the count drops to 0. Volatile and seq_cst accesses are never reordered with each other, so each thread's read really does wait until its own write is visible, and one of the two threads must see the other's write.

Litmus test 2: message passing

The second classic test is the pattern every program uses: write some data, then set a flag saying the data is ready.

Intuition says B prints 42 or nothing. With plain variables, B may also print 0: it sees the flag and then reads stale data. Three different reorderings each produce it:

  • The compiler or JIT swaps A's two independent stores, so ready is written first.
  • The CPU makes A's stores visible to other cores out of order (allowed on ARM and POWER).
  • B's two loads are reordered: B reads data early, speculatively, and ready later (also allowed on ARM and POWER).

An honest note about testing this one. On x86 the hardware never produces it (x86 keeps stores in order and loads in order), only the compiler can. On ARM and POWER the hardware is allowed to, and research on these memory models has observed it on real chips. A version of the harness above ran it 200,000 times on an Apple M4 chip and never caught it. Yet the same chip does show it under different timing: in the lock-free ring buffer of the memory orders lesson, weakening the consumer's one acquire load let the CPU read a slot before the index that published it, and stale values came out in two runs out of five. Whether you see it depends on timing and hardware; whether it is allowed does not. That makes it rare, hardware dependent and impossible to test away, the worst kind of bug.

The fix is synchronization on the flag: volatile boolean ready in Java, or an atomic ready stored with release and loaded with acquire in C++ (the default seq_cst works too). Then the write of data happens-before the write of ready, which happens-before the read that sees it, which happens-before the read of data. You will see exactly why in happens-before, and the cheapest correct C++ orders in memory orders.

Program order is not the order others observe

Put the two tests together and you get the rule to carry into every code review: without synchronization, no thread may assume anything about the order in which another thread's writes become visible. "I wrote the data before the flag" is a statement about your source code, not about what other threads see. Only a happens-before edge turns your program order into something another thread can rely on.

What creates the edge, and therefore limits reordering:

MechanismEffect on reordering
A lock (unlock, then lock by another thread)Nothing inside the critical section moves out of it; everything before the unlock is visible after the next lock
Java volatile, C++ seq_cst atomicsAccesses before a volatile write stay before it; accesses after a volatile read stay after it; and volatile accesses are never reordered with each other, which is what store buffering needs
C++ release store and acquire loadOne-way barriers: enough for message passing, not enough for store buffering
Fences (std::atomic_thread_fence, VarHandle.fullFence)Low level ordering points, used to build the above; rarely needed in application code

Worked example: the half-built configuration

A service reloads its configuration in a background thread. The code looks careful: it writes every field first and sets the loaded flag last.

What can a request thread print? "not loaded", or the right answer, or a mix: loaded true with region still null and maxConnections still 0. In Java, region + ... with a null region prints "null / 0". In C++, reading a std::string while another thread assigns it is a data race and can crash.

Fix A, minimal. Make loaded volatile (Java) or std::atomic<bool> (C++, default order, or release on the store and acquire on the load). Writes before the volatile or release write become visible to a reader that sees loaded == true. This works only while nobody writes the fields after setting the flag.

Fix B, better. Build a new immutable settings object and publish it through one volatile reference (Java) or one atomic pointer (C++). Readers grab the reference once and read a consistent snapshot, and a second reload can never be seen half applied. In C++ the old object also has to be freed only after no reader still uses it: std::atomic<std::shared_ptr<const Settings>> (C++20) or a shared_ptr copied under a short mutex handles that. That is safe publication, four lessons ahead.

Common mistakes

  • "I set the flag last, so it is safe." Source order is program order, and program order is promised only to your own thread. Make the flag volatile or atomic.
  • "We run on x86, which does not reorder." The compiler reorders on every CPU; x86 itself reorders stores with later loads; and your code will also run on ARM servers and laptops.
  • Synchronizing the data instead of the flag. In message passing, the flag is the hand-off. A volatile data with a plain ready gives no guarantee: B can still see the plain flag early and the data late.
  • Synchronizing only one side. A volatile write of the flag in the writer paired with a plain read of it in the reader, or the reverse, creates no edge. The writer must write the volatile last, and the reader must read it first.
  • Believing a passing test. The message passing test above never failed in 200,000 runs on an Apple M4, while a ring buffer with the same flaw failed on the same chip. Reason with happens-before; use stress tests and ThreadSanitizer as a safety net, not as proof.
  • "Relaxed atomics are enough for a ready flag." In C++, a relaxed flag is atomic but orders nothing else, so the data can still be stale. The flag needs release and acquire, or seq_cst.

In the interview

Reordering is how interviewers make "what can this print?" questions hard. Rubrik's online assessment has about ten multiple choice questions on multithreading and operating systems, which one report says include predicting a snippet's output, and a Microsoft loop asked a candidate to predict the output of multithreaded C++ code before fixing it. The two litmus tests are the patterns behind most such snippets.

Without synchronization, the compiler and the CPU are free to reorder independent memory operations, as long as the thread itself cannot tell. So another thread can see my writes in a different order, or see a later write before an earlier one. Here both threads can read 0, because each store can sit in its core's store buffer while the other thread reads. I would make both variables volatile, or seq_cst atomics in C++, or put the accesses under one lock.

Follow ups to expect:

  • "Can r1 == 0 and r2 == 0 happen on x86?" Yes: store then load is the one reordering x86 hardware allows, and it is exactly this test.
  • "Would release and acquire fix it?" No. A release store followed by an acquire load may still be reordered; this test needs seq_cst (or a full fence between the store and the load). This surprises many candidates.
  • "What if only x is volatile?" Still broken. A volatile access orders plain accesses in one direction only: in A, the plain load of y may move ahead of the volatile store to x, and in B, the plain store to y may move after the volatile load of x. Both threads can still read 0.
  • "Why do CPUs do this at all?" Memory is far slower than the core. Store buffers and out of order execution keep the core busy instead of stalling on every access.
  • "How would you test for this?" In Java, with jcstress, OpenJDK's harness that runs tiny tests like these millions of times and counts each outcome. In C++, ThreadSanitizer finds data races but stays silent about legal reorderings of relaxed atomics, so you reason with the memory model; tools such as CppMem and herd7 enumerate what a model allows. A test that never shows the outcome proves nothing.
  • "Can another thread see a half-constructed object?" Yes, it is message passing again: the object's field writes are the data and the write of the shared reference is the flag. Final fields or a volatile reference fix it; see safe publication and double-checked locking.

Senior depth

Strong and weak hardware models. x86 implements a model known as TSO (total store order): every core's stores enter one global order in program order, and the only visible relaxation is the store buffer. ARM and POWER are weakly ordered: without barriers or dependencies, they may reorder any two accesses to different addresses. Language memory models are deliberately weaker than all of them, so that one program can run correctly everywhere and compilers can optimize.

Dekker and Peterson. The classic software mutual exclusion algorithms, Dekker's and Peterson's, have exactly the store buffering shape: "I set my flag, then I read yours". Written with plain variables they fail on real multi-core hardware, x86 included. They work only with sequentially consistent atomics or a full fence between the store and the load. If an interviewer asks you to implement Peterson's lock, say this.

Independent reads of independent writes. With four threads, two writers and two readers, can the readers disagree on which write happened first? On POWER, yes, with acquire loads. On x86 and on ARMv8, no: both make a store visible to all other cores at the same moment (the term is "other-multi-copy atomic"). C++ seq_cst forbids it everywhere, which is part of why it costs more on POWER. Knowing that the test exists (it is called IRIW) is a senior signal; you do not need the proof.

Dependencies. On ARM and POWER, a load whose address depends on a previous load (reading p->field after loading p) is ordered after it by the hardware for free. This is what C++'s memory_order_consume tried to expose to programmers, and why it was too hard for compilers to implement; see memory orders.

Key takeaways

  • Program order is a promise to your own thread only; other threads may observe your writes in a different order.
  • Compilers, JITs and CPUs all reorder; store buffers make even x86 show store then load reordering.
  • Store buffering: both threads can read 0. Fix with volatile or seq_cst on both variables, or a lock. Release and acquire are not enough.
  • Message passing: the reader can see the flag before the data. Fix with a volatile flag (Java) or a release store and acquire load (C++).
  • A test that never shows the reordering proves nothing; reason with happens-before.

Why. The plain write of data comes before the volatile write in A, and the volatile read comes before the plain read in B. If B sees ready == true, the volatile write happens-before that read, so B also sees data == 42. If B reads ready before it is set, it prints nothing.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Pseudo code
Explain, step by step and in terms of store buffers, how both threads in the store buffering test can read 0. Then say what makes the outcome impossible, and why.
Model answer
  1. Thread A on core 1 executes x = 1. The value goes into core 1's store buffer; the cache line holding x has not been updated yet.
  2. Thread B on core 2 executes y = 1, which goes into core 2's store buffer.
  3. Core 1 executes r1 = y. It finds no pending store to y in its own buffer, so it reads the cache: 0.
  4. Core 2 executes r2 = x. Same story: 0.
  5. Both store buffers drain. Memory ends with x = 1, y = 1, but both reads already returned 0.

Nothing was lost; each store was simply not yet visible to the other core when the other core read. To forbid the outcome, each thread's load must wait until its own earlier store is globally visible. Declaring both variables volatile in Java, or using seq_cst atomics in C++, does that: the compiler emits a full fence or an equivalent instruction sequence between the store and the following load, and all seq_cst operations fall into one total order, so one of the two writes must precede the other thread's read. A lock around both operations would also work. Release and acquire do not, because a release store followed by an acquire load may still be reordered.

Debug
A teammate writes this hand-off and says it is safe "because ready is set last". What can the consumer see, and how do you fix it in your language?
Model answer

There are two problems. Visibility: ready is plain, so the consumer's loop may read it once and spin forever. Ordering: even if the consumer sees ready == true, nothing orders it after the write of results, so in Java it may see results as null and throw a NullPointerException, or see the array before its elements are visible. In C++ both variables are involved in data races, so the behavior is undefined; reading the vector while it is being assigned can crash.

The fix is to make the flag the synchronization point. In Java, declare private volatile boolean ready;: the write of results comes before the volatile write in program order, so it happens-before any read that follows a volatile read that sees true. In C++, make it std::atomic<bool> ready_{false};, store with ready_.store(true, std::memory_order_release) and spin with while (!ready_.load(std::memory_order_acquire)) { } (the default seq_cst also works). Better still, avoid the spin entirely: hand the results over with a latch or a future, or publish an immutable result object through one volatile or atomic reference.

Explain
A colleague says: "Our servers are all x86, and x86 has a strong memory model, so we do not need volatile on our flags." How do you answer?
Model answer

Three reasons that is not safe. First, the compiler and the JIT reorder and cache memory accesses on every CPU; a plain flag can be hoisted out of a loop or a store can be moved before another, and the hardware model never gets a say. Second, x86 is strong but not sequentially consistent: its store buffer lets a later load complete before an earlier store is visible, which breaks any "set my flag, then read yours" logic. Third, code outlives hardware decisions: ARM servers like Graviton and Apple laptops are weakly ordered, and the same code will run there.

The contract we program against is the language memory model, not the CPU. If a write in one thread must be seen, in order, by another thread, there has to be a happens-before edge, from a volatile or atomic, a lock, or a library hand-off. On x86 that costs almost nothing for reads anyway: a volatile read is an ordinary load there.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Two shared variables, x and y, start at zero. Thread A writes x = 1 and then reads y. Thread B writes y = 1 and then reads x. Can both reads return zero? Walk me through it."
What a strong answer covers
  • Yes, both can read 0, even on x86
  • Why it looks impossible: in every interleaving some write comes before the other thread's read
  • The mechanism: each store waits in its core's store buffer while that core's next load reads the other variable from the cache
  • The compiler or JIT may also swap the independent store and load
  • The fix: both volatile in Java or seq_cst on all four operations in C++, or a lock; release and acquire are not enough
How a senior would say it
Yes, both can read zero, and it surprises people because every interleaving seems to rule it out: whichever thread writes first, the other should see it. The catch is that a store is not visible the instant it executes. Each core puts its store into a private store buffer and keeps going, and its next load reads the other variable from the cache, where the other core's store has not arrived yet. So A's write of x sits in its buffer, B's write of y sits in its buffer, A reads y as zero, B reads x as zero, and only then do the buffers drain. This is the one reordering x86 allows, a store followed by a load of a different address, so you see it on Intel too, and ARM allows even more. The compiler or JIT can also simply swap the store and the load, since they touch different variables. To forbid it, both variables must be volatile in Java, or all four operations seq_cst in C++. Then they fall into one total order, and one read must come after the other thread's write. Release and acquire do not fix it, because a release store followed by an acquire load can still be reordered.

Likely follow up: If I asked you to implement Peterson's lock, what would you have to be careful about?

  • Three culprits: the compiler or JIT swaps the stores, the CPU publishes them out of order (ARM, POWER), or the reader's loads are reordered
  • loaded is plain, so no happens-before edge connects the field writes to the reader
  • Minimal fix: a volatile flag in Java, or a release store and acquire load in C++
  • Better fix: build an immutable config and publish it through one volatile or atomic reference
  • Rare and hardware dependent, so a passing test proves nothing
How a senior would say it
I would tell them the order in the source is a promise to their own thread, not to anyone else. Without synchronization the JIT can swap the two stores, an ARM core can make them visible out of order, and the reader's two loads can be reordered too. Any one of those lets a request see the flag before the data. Because loaded is a plain field, no happens-before edge connects the field writes to the reader, so the language allows exactly what they are seeing. The minimal fix is to make loaded volatile in Java, or a release store with an acquire load in C++. Then everything written before the flag is visible to a reader that sees it true. The better fix is to build a new, immutable config object and publish it through one volatile or atomic reference, so a reader always gets a complete snapshot and a second reload is never half seen. And "it is rare" is the point: it depends on timing and hardware, so no test can prove it is gone.

Out loudabout 70 s
"Why do compilers and CPUs reorder memory operations at all, and what does it cost to forbid it?"
What a strong answer covers
  • Memory is far slower than the core; executing every access strictly in order would leave the core idle
  • CPU side: store buffers, out of order execution and early, speculative loads
  • Compiler side: values kept in registers, instructions rescheduled, loads and stores merged or hoisted
  • The deal: the as-if rule hides all of it from the thread itself, and synchronization marks where other threads need order
  • The cost: fences and seq_cst stores make the core wait for its store buffer, so put ordering only at hand-off points
How a senior would say it
Because memory is slow and cores are fast. A load that misses every cache costs on the order of a hundred nanoseconds, which is hundreds of cycles, so a core that waited for every access in turn would sit idle most of the time. So the CPU parks stores in a store buffer, executes out of order and starts loads early, and the compiler keeps values in registers and schedules instructions freely. None of it is visible to the thread itself; that is the as-if rule. The deal both languages make is that plain accesses get every optimization, and synchronization marks the few places where another thread needs to see things in order. Forbidding reordering everywhere would throw much of that speed away, because a full fence or a seq_cst store makes the core wait for its store buffer to drain. So I put ordering only at the hand-off points: a lock, a volatile flag, or a release and acquire pair.
