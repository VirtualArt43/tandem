Optimistic versus pessimistic concurrency control

Choose conditional updates, version checks or row locks, handle conflicts correctly, and claim jobs safely with short transactions.

Asked atMicrosoftBloombergMetaFlipkartSalesforce
Before this:Database isolation levels and anomaliesCAS loops and atomic state machinesThe lost update: read, modify, write

Two clients read the same row, both change it, both write it back. You already know this is a lost update. This lesson gives you the three database-level fixes, the client code that goes with each, and the judgment to pick one in a design round.

In plain words

Think of a shared document at an office. One way to stop two people overwriting each other: whoever wants to edit takes the only copy to their desk, and everyone else waits until it comes back. That is pessimistic: assume a clash will happen and prevent it by making others wait.

The other way is how a wiki works. Everyone edits freely. When you press save, the wiki checks whether anyone else saved since you opened the page. If not, your save goes in. If so, you get an "edit conflict" and redo your change on the new version. That is optimistic: assume a clash is rare, and detect it at the last moment instead of preventing it. The third way is to avoid the question entirely by making the change one indivisible step, like a counter clicker.

The problem, and three shapes of fix

A service that runs SELECT balance, computes, then runs UPDATE ... SET balance = ? has a read-modify-write spread over two network round trips. Two requests in that gap lose an update exactly like two threads doing count += 1, and, as the previous lesson showed, neither Postgres nor MySQL stops it at their default isolation levels.

Every fix makes the read, the decision and the write behave as one step, in one of three ways:

FixHow it worksIn-process twin
Atomic statementThe database reads, checks and writes in one statement, under its own row lockfetch_add, incrementAndGet
Pessimistic lockLock the row when you read it; others wait until you commita mutex around the read-modify-write
Optimistic checkRead a version; write only if the version is unchanged; otherwise retrya compare-and-swap loop

First choice: let one statement do it

For a check and change confined to one row, prefer a conditional statement. At PostgreSQL READ COMMITTED and MySQL InnoDB's default REPEATABLE READ, a competing writer waits and the operation uses the current row. The write lock lasts until transaction end, which coincides with statement completion only for an autocommit statement. A subquery that reads other rows does not make their invariant safe automatically.

At Postgres READ COMMITTED, a waiting updater re-checks the target row's predicate after the competing commit and computes from the updated balance. InnoDB uses current reads for updates, including the transaction's own changes. At Postgres REPEATABLE READ, a conflicting change committed after your snapshot instead causes a serialization failure. None of these choices removes the need to handle deadlocks, timeouts or other failures.

Always check the number of rows changed. The WHERE ... AND balance >= 30 is the check of a check-then-act, and "0 rows" is how the database tells you the check failed. Code that ignores the row count has turned a correct statement back into a silent bug.

Pessimistic: lock it when you read it

When the decision needs application logic, lock the rows it depends on before reading values for that decision. SELECT ... FOR UPDATE holds row locks until commit or rollback, excluding conflicting lockers and writers. Ordinary MVCC snapshot readers can still read old versions. Keep the read and update in the same explicit transaction; two autocommit statements do not protect the gap.

The lock clauses have close analogies to familiar lock methods; SQL errors and transaction scope differ:

SQLBehaviour when the row is lockedIn-process twin
FOR UPDATEWait until it is freelock()
FOR UPDATE NOWAITFail at once (Postgres SQLSTATE 55P03, MySQL 8 error 3572)tryLock(), try_lock()
SET LOCAL lock_timeout = '2s' inside a Postgres transaction; innodb_lock_wait_timeout in MySQLFail when the applicable lock wait exceeds its configured limittryLock(2, TimeUnit.SECONDS), try_lock_for(2s)
FOR UPDATE SKIP LOCKEDSkip locked rows and return the others"take any free item" from a pool
FOR SHAREShared lock: other readers may share it, writers waita read lock

Everything you learned about locks applies, one level up. Hold them briefly: a row lock held across an HTTP call or a user's think time stalls every other request for that row. Take several in one order, for example SELECT ... WHERE id IN (7, 42) ORDER BY id FOR UPDATE, or two transfers in opposite directions deadlock. Databases detect deadlocks and kill one transaction (Postgres SQLSTATE 40P01, MySQL error 1213), so the victim must retry, but a design that deadlocks often is a design that is slow.

Use immutable sort keys and the same order on every path; indexes, triggers and foreign keys can add other locks, so retain deadlock recovery. NOWAIT and SKIP LOCKED concern row locks, not a guarantee that the whole statement cannot wait on a table lock or I/O. After a PostgreSQL statement error, roll back before retrying; an InnoDB lock-wait timeout normally rolls back only the statement, so explicitly roll back the whole operation before restarting it.

The job queue: SKIP LOCKED

A table of jobs and twenty workers is the classic place where waiting is wrong: a worker does not care which job it gets, only that no two workers get the same one. SKIP LOCKED (Postgres 9.5 and later, MySQL 8.0 and later) lets each worker lock one free row and step over rows other workers hold.

The claim commits before processing, so a long job holds neither a transaction nor a connection open. Five minutes is an illustrative lease, not a recommended timeout. A sweeper re-queues expired running jobs and clears their claim tokens; renewals and completion must check the current token and state, and renewals also require an unexpired lease. Each new claim gets a new token, even if the same worker takes the job again.

This is at-least-once processing. A worker can perform an external effect and crash before marking the job done. The token protects the job row, not an external payment or email; use idempotency at that destination or resource-enforced fencing. See leases and fencing and idempotency. For MySQL, use the locking SELECT and UPDATE in one short transaction rather than porting this PostgreSQL self-referencing subquery directly.

SKIP LOCKED gives each worker some free job, roughly in order. It is not a strict FIFO: a job that one worker locked and then released can be overtaken. Use it for work queues, not for anything that needs exact ordering.

Optimistic: check a version when you write

Optimistic concurrency control adds a version number to the row. You read the version along with the data, hold no lock while you think, and make your write conditional on the version being unchanged:

Zero rows means the predicate matched nothing: the version changed or the row disappeared. Re-read, recompute and retry a replayable operation, or show a conflict for a human edit; a missing row needs its own policy. The conditional UPDATE compares and changes the version atomically under the database's row lock. One affected row is not durable success until the transaction commits.

Use a version that changes on every relevant write. A monotonically increasing integer avoids timestamp collisions, provided it never wraps or resets; deleting and recreating an id with version 0 reintroduces ABA. Preserve a generation across recreation or use a fresh identity. All writers, including maintenance scripts and pessimistic paths, must advance the version.

JPA's @Version provides checks for managed versioned entities and reports OptimisticLockException, potentially at flush or commit. Bulk JPQL updates and native SQL do not automatically obey that entity protocol. Optimistic does not mean lock-free: the conditional database write can acquire locks and wait; what you avoid is holding a lock across reading, computation or user think time.

The same idea over HTTP: ETag and If-Match

HTTP has optimistic concurrency built in. The server returns an ETag (a version tag) with the resource; the client sends it back in If-Match on the write; the server applies the write only if the tag still matches, and otherwise answers 412 Precondition Failed.

If-Match uses strong comparison: a weak tag such as W/"v7" is not suitable. The server must atomically validate and apply the update, for example with the database version predicate; checking the header and then doing a blind write recreates the race. A server can require a precondition using 428 Precondition Required when it is missing.

An editor can keep a document open for twenty minutes without keeping a database transaction open. On conflict, fetch the new representation and merge or ask the user; silently replaying an old whole-document replacement on the new version defeats the user's intent. If-None-Match: * expresses create-if-absent. A retry of an already completed request can have special HTTP success handling, but a new edit with a stale tag must not overwrite it.

The client side: a retry loop that re-reads

Here is the whole story in one program. A tiny in-memory "table" stands in for the database: each method is atomic on its own, like one SQL statement. Four clients deposit 1, ten thousand times each. First with blind writes (read, then write the computed value), then with the optimistic loop.

The blind version is data-race-free because each call takes the table lock, but it can lose deposits: safe calls do not make their sequence safe. The printed values are one illustrative run; the blind version can even produce 40000, and conflicts depend on scheduling. The checked version must reach 40000 or report failure. Yielding is only a scheduler hint, not a correctness or fairness mechanism; the version comparison provides correctness.

The rules for a real retry loop: re-read inside the loop (never retry the old UPDATE with the old version), cap the attempts, and back off with jitter between attempts so that clients that collided once do not collide again in lockstep (the backoff and jitter from module 4). When the cap is hit, report a conflict to the caller rather than spinning forever.

Re-read from a fresh transaction when a snapshot could remain stale, especially at REPEATABLE READ. Retry the intent, such as adding 10, after validating it again; do not reuse an obsolete computed balance. Keep external effects out of the loop. A lost connection during commit leaves an unknown outcome, so blindly retrying a deposit can duplicate it; use an idempotency key. These small samples assume amounts and versions fit their integer types.

When each one wins

SituationBest fitWhy
Arithmetic and a predicate on one rowConditional UPDATEOne statement, no application read-compute-write gap; locks and database failures still apply
Edits where conflicts are rare: profiles, documents, configuration, cartsOptimistic version or ETagNo locks during think time; works across HTTP; conflicts cost a retry
Conflicts are likely, transactions are short, and redoing work is expensivePessimistic FOR UPDATEWaiting in line is cheaper than a retry storm
Many workers, any free item will doFOR UPDATE SKIP LOCKEDSkip row-lock contention while choosing work; an empty result need not mean the queue is empty
A rule across several rows (write skew)Lock the rows the rule reads, a constraint, or SERIALIZABLEA version on one row cannot see the other rows
One extremely hot key (a flash sale item, a viral post)None of them alone: split the key, batch, or give it a single ownerEvery option serializes on that one row; see ordering by ownership and the design cases

The rule of thumb is to measure conflict cost against lock-wait cost. Optimistic control suits rare conflicts and long think time; pessimistic control can avoid wasted computation for short, contended transactions. A conditional single-row statement often avoids both application protocols. Under heavy contention, retries can dominate and a slow client can starve; none of these choices removes a single row's capacity limit.

Worked example: a parking lot booking API

A multi-server parking service must never give one spot to two cars. Spots are rows: spots(id, level, status, car_id, version).

Assigning a specific spot the user tapped on the map: UPDATE spots SET status = 'taken', car_id = $1, version = version + 1 WHERE id = $2 AND status = 'free'. Check the row count; zero means no such free spot. Advancing the version also invalidates any outstanding optimistic editor of that row.

Assigning any free spot on a level: SELECT id FROM spots WHERE level = 2 AND status = 'free' LIMIT 1 FOR UPDATE SKIP LOCKED, then an UPDATE in the same short transaction, avoids waiting on another claimant's row lock. An empty result means no unlocked candidate was found, not proof that the level is permanently full. Decide whether to retry briefly or return temporary unavailability.

Editing a monthly pass (name, vehicle number, payment method) in an admin screen that stays open: a version column, sent to the browser as an ETag, with 412 turned into "this pass was changed by someone else, reload".

Common mistakes

  • Ignoring the row count. A conditional UPDATE that matched 0 rows did nothing. Check it every time.
  • Retrying the old write. A retry that re-sends the UPDATE with the version it read before the conflict fails forever. Re-read inside the loop.
  • Unbounded, immediate retries. Under contention they become a retry storm. Cap the attempts and back off with jitter.
  • Holding FOR UPDATE across a slow call. A row lock held while you call a payment service turns one slow dependency into a queue of blocked requests. Decide quickly, or use an optimistic check, or a hold with an expiry.
  • Locking rows in different orders. Opposite-direction transfers can deadlock. Use a common order and retain deadlock recovery.
  • Using a timestamp as the version. Equal timestamps and clock steps break it. Use a growing integer.
  • Using SKIP LOCKED where order matters. It hands out some free row, not the oldest one in strict order.

In the interview

The research records Microsoft's parking-lot concurrency follow up, Bloomberg backup-job coordination across clusters, Flipkart questions on optimistic, pessimistic and distributed locks, and Salesforce parking-lot concurrency first with threads and then with a central database. Meta ticket-booking reports describe deep concurrency and race-condition follow ups. Use those prompts to practise choosing a protocol from the invariant, conflict rate and transaction duration.

For a simple single-row rule I would use one conditional UPDATE and check its result. For a long edit with rare conflicts, I would compare a version and resolve conflicts without holding a lock during think time. The write itself still locks. For short, expensive operations with frequent conflicts, I would consider FOR UPDATE, keep the transaction short and measure lock waits.
For the queue I would claim a row with SKIP LOCKED, commit a lease and a fresh claim token, then process outside the transaction. A sweeper re-queues expired claims. Completion checks the token, and external effects must tolerate a retry because a worker can crash after doing the work.

Follow ups to expect: "What happens under heavy contention?" (retries pile up; bound them and consider a compatible pessimistic path), "How do you reduce deadlocks?" (common lock order, short transactions, victim retries), "How would you do this over HTTP?" (strong ETag and atomic If-Match validation), and "Can version checks prevent write skew?" (independent versions on only the written rows cannot; a shared guard or complete dependency validation changes that).

Senior depth

Fallback needs a shared protocol. A slow optimistic client can exhaust its retry budget. A pessimistic fallback must lock, re-read, recompute and increment the same version as every optimistic writer. A local mutex alone cannot exclude clients using only database version checks, and adding a lock to an arbitrary lock-free algorithm is not automatically safe.

One row's version cannot validate a whole invariant. To prevent write skew, validate every dependency, including predicates, or make all contenders update a shared guard version in the same transaction. That deliberately creates a conflict point. Constraints, complete locking protocols and serializable transactions are other choices.

Service boundaries do not force a separate distributed lock. Prefer an atomic command at the service that owns the data. If a lease coordinates work across services, the protected resource must reject stale holders; a lease by itself cannot stop a paused process from resuming.

Holds are a state machine. Reserve with a short conditional update storing an expiry and unique hold token. Confirm only the matching, still-live hold; release only the matching hold so an old cancellation cannot release a new customer's reservation. Expiry and payment reconciliation are separate from optimistic version checking.

Key takeaways

  • An unprotected read-modify-write across round trips can lose an update; use a conditional statement, a row lock or a version check.
  • Prefer one conditional UPDATE whenever it can express the change, and always check the row count.
  • FOR UPDATE is lock(), NOWAIT is tryLock(), SKIP LOCKED is "any free item"; keep row locks short and ordered.
  • Optimistic means version plus conditional write plus a bounded retry loop that re-reads; ETag and If-Match are the HTTP form.
  • Measure conflicts and lock waits. Optimistic writes still lock; a saturated hot key may need a different design.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A client runs UPDATE accounts SET balance = 130, version = version + 1 WHERE id = 42 AND version = 7 and the database reports 0 rows changed. What does it mean, and what should the client do?
Why. Zero affected rows means no row satisfied both predicates, so this statement changed nothing. A missing row and a version mismatch are both possible. A lock wait produces waiting or an error, not this success result. Changing isolation cannot recover the old computation; re-read and handle the current state rather than retrying version 7.
Spot the bug in this retry loop. Versions increase on every write and are never reused.
Why. The read must be inside the loop. Once a writer advances the version, the old predicate cannot succeed again. Jitter reduces synchronized retries; it cannot repair stale input. Five attempts is a valid policy, not an inherent bug, and holding a lock across the whole operation would be a different, pessimistic protocol.
Two workers hold row locks on the only two queued jobs in Postgres. Before either releases its lock, a third runs SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED. Assume no other lock conflicts or new jobs. What does it get?
Why. Both candidates are skipped, so the result is empty and no job is shared. Plain FOR UPDATE would wait for a conflicting row lock; NOWAIT would error. This does not prove the queue has no work or promise zero latency from table locks or I/O.
Which in-process call is the closest twin of SELECT ... FOR UPDATE NOWAIT?
Why. For a conflicting row lock, NOWAIT fails without waiting, like an untimed try-lock, though SQL reports an error rather than false. Plain lock acquisition waits; timed acquisition permits a wait up to a bound. Condition waiting instead releases an already held lock while waiting for a predicate. These are analogies, not identical APIs.
Several service instances sell a pre-existing inventory row. The whole rule is to decrement by one only when stock is positive. At Postgres READ COMMITTED, which choice enforces it with the fewest database statements per successful purchase?
Why. The conditional UPDATE checks and decrements in one statement. Version checking and FOR UPDATE can also be correct, but both require an application read followed by a write, and version conflicts add retries. An in-process mutex cannot exclude another service instance. The single statement still takes a row lock and can fail; it does not provide unlimited throughput or deduplicate a retried purchase.
A client sends a new, otherwise valid PUT /documents/17 with If-Match: "v7", but the current strong ETag is "v8". This request has not already succeeded. What should the server answer?
Why. A failed If-Match precondition means 412 and no change, so the client can fetch v8 and merge. 428 is for a request that did not send any precondition when the server requires one.
Balance 100, version 7. Client A adds 10 and client B adds 20 using correct version-checking loops. Both operations eventually commit once, and there are no other writers. What is the final state?
Why. The question explicitly assumes both operations commit once: balance becomes 130 and two successful writes advance version 7 to 9. A rejected attempt changes neither value nor version. A bounded retry loop alone does not guarantee eventual success; an exhausted operation must report failure.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write deposit(amount) with optimistic concurrency against a table that offers select() (returning balance and version) and updateIfVersion(newBalance, expectedVersion) (returning 1 or 0). Bound the retries and back off with jitter.
Model answer

The read is inside the loop, attempts are bounded, and jitter spreads retries apart. Here select() returns a current value, and a successful updateIfVersion() represents a committed single-row operation; a real snapshot transaction must be restarted as needed. Amounts and versions must fit their types, and a conflict after eight attempts is reported without another sleep.

Design
Pick optimistic, pessimistic, an atomic statement or SKIP LOCKED for each, and justify in one sentence: (a) a wiki page editor, (b) stock for one flash sale item, (c) an email job table drained by 20 workers, (d) moving money between two accounts.
Model answer
  • (a) Wiki editor: optimistic. A strong ETag with If-Match avoids locks during editing; validate and update atomically, and let the user resolve conflicting edits.
  • (b) Flash sale stock: atomic statement. UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0 decides and decrements in one step; optimistic retries would storm, and if even this row is too hot, split the stock into several rows or put a queue in front.
  • (c) Email jobs: SKIP LOCKED. Claim an unlocked row with a lease and a fresh token, commit, then process. A sweeper re-queues expired claims; completion checks the token, and the email destination needs deduplication if duplicate sends are unacceptable.
  • (d) Transfer: pessimistic, or two conditional statements in one transaction. Lock both existing accounts in id order, check funds, debit and credit, then commit; alternatively use a guarded debit and a credit with both row counts checked. Roll back if either fails and retry deadlock victims. Both sides must commit together.
Explain
"Optimistic locking scales better because it never blocks." Agree or disagree, as you would in a design round.
Model answer

Disagree with "never blocks". Optimistic control avoids holding a lock across the client's read-compute-write interval, but its conditional database write still acquires locks and can wait. It often works well when conflicts are rare or a user edits for minutes. Under contention, failed attempts consume work and round trips, and a slow client can starve. I would bound retries, measure conflicts and lock waits, and consider a short pessimistic transaction, a conditional single-row statement or a different ownership design for a saturated key. None is universally fastest.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"Would you use optimistic or pessimistic locking for this API? Tell me what you need to know before choosing."
What a strong answer covers
  • Start with the invariant and prefer a conditional statement for a simple single-row rule
  • Choose version checking for rare conflicts or long user think time
  • On zero affected rows, handle absence or re-read and recompute with bounded jittered retries

How a senior would say it
I would start with the invariant, then ask about conflict frequency, transaction duration and the cost of redoing work. If the rule is simply to decrement positive stock, one conditional update is my first choice. I check its affected-row count and commit before reporting success. For a document that a user may edit for minutes, I would use a version check or a strong ETag. That avoids holding a lock during think time. If no row matches, I handle deletion or fetch the latest value and resolve the conflict. For a replayable operation, I recompute from that value, with bounded retries and jitter; I do not resend the old computed result. If conflicts are frequent and the transaction is short, locking before reading may be cheaper than repeated failed work. I would take multiple locks in a consistent order and measure waits. Optimistic writes still take database locks, so this is not a lock-free guarantee. Finally, if the rule spans several rows, I need to protect all its dependencies, not just add a version to the row being changed.

Likely follow up: How could a pessimistic fallback safely coexist with existing optimistic writers?

Out loudabout 75 s
"Twenty workers poll one jobs table. How would you stop duplicate claims and recover when a worker crashes?"
What a strong answer covers
  • Claim an unlocked queued row using FOR UPDATE SKIP LOCKED in a short transaction
  • Record running state, an expiry and a fresh token per claim, then commit before processing
  • Renew and finish conditionally on the current token and state; re-queue expired claims
  • Explain why a reusable worker id cannot distinguish successive claims
  • Identify at-least-once external effects and require destination idempotency or fencing
  • State that SKIP LOCKED provides neither strict FIFO nor proof of an empty queue
How a senior would say it
I would claim work in a short database transaction using FOR UPDATE SKIP LOCKED. The transaction selects an unlocked queued job, marks it running, and records an expiry and a fresh claim token. I commit that claim before doing the work, so the worker does not hold database locks during a long task. A sweeper re-queues expired claims, and long-running workers renew only their own still-valid claim. Completion checks the token and running state, so an old attempt cannot complete a newer attempt's job. The token must change on every claim; a worker id alone is unsafe if that worker later claims the same job again. This still gives at-least-once processing. A worker can send an email or charge a payment and crash before recording completion. The external destination therefore needs idempotency, or fencing where the protected resource supports it. Finally, skipping locked rows means we do not get strict FIFO. An empty poll means no unlocked candidate was found at that moment, not that all work is finished. Other locks and I/O can still delay the query.

Likely follow up: What happens if the payment succeeds but the worker loses its lease before marking the job done?
