Debugging and testing concurrent code

Debugging rounds, thread dumps, gdb, ThreadSanitizer, stress and litmus tests, flaky tests, heisenbugs and review checklists.

1Coredebugging-roundmethodRubrik
In a debugging round you are handed about 200 lines of someone else's multithreaded code. How do you find the bugs quickly?
Model answer

I run it first, if the environment allows, to see the symptom: a hang, wrong output or a crash. The symptom tells me what to look for. Then I make four quick maps on paper:

  1. Shared state: every field more than one thread touches, and which lock guards each access. An unguarded access is a candidate data race.
  2. Locks: every acquisition, and the order in which nested ones are taken. Two paths with opposite orders are a deadlock waiting to happen. So is a lock held across a blocking call.
  3. Signaling: every wait, await or condition variable wait. Is it in a while loop on a predicate? Is the predicate changed under the same lock? Does every path, including error and shutdown paths, notify?
  4. Lifecycle: who starts each thread, who joins it, how shutdown wakes blocked threads, and what happens when a thread throws.

Then I look for check-then-act sequences built from separately synchronized calls, which no tool flags.

I fix one bug at a time and keep the program compiling after each change, rerunning between fixes. A Rubrik new grad found the deadlock and still lost the round because the fix did not compile. For each fix, I state the interleaving it prevents, in one sentence.

Likely follow up: "Which bug do you fix first?" The one that explains the observed symptom: a hang points to a lock cycle or a lost wakeup, wrong totals to an unguarded read-modify-write, a crash to a lifecycle or memory bug.

2Corethread-dumpjava
How do you read a Java thread dump?
Model answer

Take a thread dump with jcmd <pid> Thread.print (or jstack -l <pid>, or kill -3, which prints to the process's stdout). Each thread shows its name, state and stack.

  • RUNNABLE: running, or blocked inside native I/O. A thread stuck in a socket read shows as RUNNABLE, which misleads people.
  • BLOCKED: waiting to enter a synchronized block, shown as "waiting to lock" a monitor address.
  • WAITING and TIMED_WAITING: in Object.wait, join, sleep or LockSupport.park. For java.util.concurrent locks and conditions you see "parking to wait for" with the class, such as ReentrantLock$NonfairSync or a ConditionObject.

"locked" lines show monitors a thread holds; with -l, a "Locked ownable synchronizers" section lists the ReentrantLocks it holds. To find who blocks whom, search the dump for the lock address a waiter is waiting on. If the JVM finds a cycle, it prints "Found one Java-level deadlock" at the end.

Take two or three dumps a few seconds apart: frozen stacks mean stuck, moving stacks mean slow. Name your threads, because a stack in "pool-3-thread-7" tells you nothing. Virtual threads do not appear in the classic dump; in JDK 21 use jcmd <pid> Thread.dump_to_file -format=json <file> (plain text works too), which includes them.

Likely follow up: "All workers are WAITING on a ConditionObject, with no cycle. What is it?" A lost wakeup or a missing signal: check whether the predicate is already true, and whether the thread that should signal died with an exception.

3Coregdbdeadlockcpp
How do you debug a hang or a deadlock in a C++ program?
Model answer

Attach with gdb -p <pid>, or take a core with gcore and look at it offline. Then info threads and thread apply all bt.

  • A futex wait (__lll_lock_wait on glibc) called from pthread_mutex_lock: the thread wants a mutex. With glibc, print the mutex and read __data.__owner, the thread id (LWP) of the holder. For a std::mutex in libstdc++ that is m._M_mutex.__data.__owner. Find that LWP in info threads and see what it waits for; follow owners until the cycle closes.
  • Frames in pthread_cond_wait: a condition variable wait. There is no owner to follow, so print the state the predicate reads (queue size, flags) and decide who should have signaled. Often that thread died or exited early.
  • Frames in pthread_join: a thread waits for another that is itself blocked.

Before it ever hangs, ThreadSanitizer on Linux reports "lock-order-inversion (potential deadlock)" when it sees two mutexes taken in opposite orders on different paths (Apple clang's ThreadSanitizer does not report these), and Valgrind's Helgrind does similar checks. On macOS, LLDB's bt all gives the same picture.

Likely follow up: "The owner field points at a thread that no longer exists." A thread exited, or threw, while holding the mutex: a manual unlock was skipped. That is the strongest argument for RAII guards.

4Corethreadsanitizertoolscpp
What is ThreadSanitizer, how does it work, and what does it miss?
Model answer

ThreadSanitizer is a compiler instrumentation (-fsanitize=thread, with -g and some optimization such as -O1) for C, C++ and Go. Every memory access and every synchronization operation is instrumented. It tracks happens-before with vector clocks and keeps shadow memory recording recent accesses to each word. When two accesses to the same location, at least one a write, are not ordered by happens-before, it reports both stacks and where each thread was created. It also reports misuse such as unlocking a mutex from the wrong thread, and, on Linux, lock order inversions (Apple clang's build does not).

Key property: it reports a race that happened in the run even if the output came out right, because it checks ordering, not results. The cost, per its documentation, is typically a 5 to 15 times slowdown and 5 to 10 times more memory.

What it misses:

  • Code paths the run never executed. It is dynamic, so test coverage matters.
  • Race conditions that are not data races: check-then-act where each step is properly locked, or atomicity violations across two atomics.
  • Accesses in libraries that were not built with it.
  • It can give false reports for synchronization it does not model, such as hand-written assembly or standalone std::atomic_thread_fence.

It cannot be combined with AddressSanitizer in one build. Java has no mainstream equivalent, so there you rely on stress tests, jcstress and static checks.

Likely follow up: "TSan is clean. Is the code correct?" No: it is free of data races on the paths exercised. Logic races still need reasoning and targeted tests.

5CoretestingstressDatabricks
How do you test a concurrent class for race conditions?
Model answer

Start from invariants you can check at the end: totals are conserved, nothing is lost or duplicated, per-producer order is preserved, capacity is never exceeded. Then maximize the chance of a bad interleaving: more threads than cores, tight loops, many iterations, and a start gate so every thread begins at the same moment, instead of being staggered by thread start-up time.

Around that core: join with timeouts and dump threads on a timeout, run the C++ build under ThreadSanitizer, repeat the test many times on more than one machine (ARM shows reorderings that x86 hides), and force specific interleavings with test hooks (a latch that pauses thread A between its check and its act while thread B runs). For a log writer, each producer writes sequence-numbered events and the test checks that every event appears exactly once and in per-producer order.

Likely follow up: "How do you test shutdown?" Call close while producers are mid-flight, then assert that every acknowledged item was written and every later call failed cleanly.

6Seniorreproductiontesting
A race shows up once in a thousand runs. How do you make it reproducible?
Model answer
  • Widen the window: in a debug build or behind a test hook, insert a sleep or yield between the suspected check and act. If the failure rate jumps, you have found the window. This is a diagnostic, never a fix.
  • Change the scheduling pressure: run more threads than cores, and add background CPU load so preemptions land in odd places. Pin everything to one core (taskset -c 0) to force interleavings through preemption, or spread threads across many cores to expose memory ordering effects.
  • Loop the single test thousands of times with a recorded random seed.
  • Record and replay: on Linux, rr records a run and replays it exactly, and its chaos mode deliberately perturbs scheduling to make rare races appear.
  • Explore interleavings systematically: jcstress or Lincheck on the JVM, and model checkers such as Relacy for small C++ algorithms.
  • Log with thread names plus a global sequence number taken from an atomic counter, so the order of events can be rebuilt afterwards.

Once you understand the interleaving, turn it into a deterministic regression test: use latches to drive thread A to the check, run thread B to completion, then release A. That test fails every time on the old code and passes on the fix.

Likely follow up: "Why might pinning to one core hide the bug?" With one core there is no real parallelism, so memory reordering between cores and cache effects disappear; only preemption interleavings remain.

7Seniorjcstressmemory-modeljava
What is jcstress, and what question does it answer that a unit test cannot?
Model answer

jcstress is the OpenJDK harness for testing concurrency at the memory model level. You write a tiny test in which two or more @Actor methods run concurrently against shared state and record what they observed into a result object; @Outcome annotations classify each possible result as acceptable, interesting or forbidden. The harness runs it millions of times, under several JIT compilation modes, and reports how often each outcome appeared.

A unit test checks one interleaving's outcome. jcstress answers "can this outcome ever happen?", which is the real question for visibility and reordering. Make ready volatile and the "1, 0" outcome must disappear.

Read the results with care: an outcome that never appeared on x86 may still appear on ARM, so absence proves nothing. The C++ counterparts are litmus tests run through model tools such as herd7 or CppMem, which enumerate every outcome the memory model allows for a small program.

Likely follow up: "Why does 1, 0 appear on ARM and rarely on x86?" x86 keeps stores in order and loads in order, so the compiler is the only source of this reordering there; ARM may reorder both.

8Coretestingsleep
Why can you not fix a race with sleep, and why does "it passed a thousand runs" prove so little?
Model answer

A sleep only shifts probabilities. Scheduling, GC pauses, machine load and a slower CI box all change timing, so the window comes back. More fundamentally, sleep creates no happens-before edge: the Java Language Specification says explicitly that Thread.sleep and Thread.yield have no synchronization semantics, so the compiler may still cache a field in a register across the sleep, and the other thread's write may never become visible.

A thousand passing runs sample a tiny corner of the interleaving space, usually on one machine with one memory model. x86 hides most hardware reorderings that ARM exposes, and your laptop's timing is not production's.

Correctness needs an argument: every shared access is ordered by happens-before (a lock, a volatile or atomic, a thread start or join, a concurrent collection), and every invariant is changed only inside the critical section that protects it. Tests, ThreadSanitizer and stress runs are evidence that the argument holds, not proof.

In tests, replace sleeps with explicit waits for events: a latch, a future, or polling a condition with an overall deadline. A sleep-then-assert test is the classic flaky test.

Likely follow up: "Then where is sleep legitimate?" In backoff and retry delays, in rate pacing, and in demos to make timing visible, never as synchronization.

9Seniorflaky-teststriage
A concurrent test fails with a timeout once in about 500 CI runs. How do you triage it?
Model answer

A flaky test needs evidence before theories, so first make the next failure informative. On timeout, dump all threads (in Java ThreadMXBean.dumpAllThreads; in C++ a watchdog that prints stacks or aborts to leave a core file), and log with thread names, a sequence number and the random seed.

Then classify it:

  • A test bug: sleep-then-assert timing, a timeout too tight for a loaded CI machine, static state shared between tests, a fixed port.
  • A product bug: a lock cycle (the dump shows it), a lost wakeup (threads waiting on a condition whose predicate is already true), or a worker that died silently from an exception, so a latch or pool never completes. The last one is the most common in practice: look for a missing worker thread in the dump.

Reproduce locally by looping that single test under parallel load, and run the C++ build under ThreadSanitizer. Fix the cause, and then add a deterministic test for the interleaving you found.

Do not "fix" it by raising the timeout unless the evidence shows the work was merely slow, and quarantine with a ticket rather than deleting the test: a flaky concurrency test is usually telling the truth about a rare interleaving.

Likely follow up: "How do you make worker failures visible to the test?" Always call get on every future (or join and check a stored std::exception_ptr), so a thrown task fails the test instead of hanging it.

10Seniorheisenbuglogging
Why does adding a print statement make a race disappear, and how do you log without hiding the bug?
Model answer

System.out.println takes the PrintStream's lock. A lock release followed by another thread's acquire is a happens-before edge, so the print adds synchronization and serializes the threads, besides costing microseconds that shift timing. In C++, writes to std::cout are safe from data races when synchronized with stdio, but they also take internal locks and take time. The print fixes the bug by accident: a heisenbug.

Ways to observe without perturbing much:

  • Record events into a preallocated per-thread buffer (no sharing, no locks) with a timestamp, and dump the buffers after the run or on failure.
  • Use a global sequence number from a relaxed atomic increment to order events. Relaxed operations add no happens-before for other memory, though contention on that counter's cache line still shifts timing a little.
  • Run under ThreadSanitizer, which observes ordering without adding synchronization to your program, although its slowdown changes timing.
  • Record and replay with rr, then inspect any moment of the failing run in the debugger.

The general lesson: any observation tool changes timing, so prefer tools that check ordering (TSan) or record cheaply, and reason from the interleaving rather than from whether the symptom appears.

Likely follow up: "Could the print also hide a visibility bug?" Yes. The lock in the print can force the stale value to be reread, so a spin loop on a non-volatile flag may start working only while it prints.

11Seniorperformancecontentionprofiling
Throughput stops scaling when you add threads. How do you find out why?
Model answer

Start with CPU use, because it splits the space in two.

Low CPU, threads not running: they are blocked on locks or I/O. Sample thread dumps and count which lock or stack the blocked threads share. In Java, Flight Recorder's monitor-enter and thread-park events and async-profiler's lock mode show exactly which locks cost the most waiting time. In C++, use off-CPU profiling (perf with scheduler events, or BPF tools such as offcputime) or a mutex profiler such as mutrace.

High CPU, flat throughput: threads are busy doing the wrong thing. Spinning or CAS retry storms, false sharing and cache-line ping-pong (perf c2c shows contended lines and their offending fields), allocation and GC pressure, or context-switch overhead from too many threads (watch the switch rate in vmstat).

Then reason with Amdahl's law: a serial fraction s caps speedup at 1 over s, so 5 percent serial work caps you at 20 times on any number of cores. The Universal Scalability Law adds a coherence cost that makes throughput actually fall past some thread count, which is the classic shape of a contended lock.

Fixes in rough order: shrink critical sections, stop sharing (per-thread work merged at the end), stripe the lock, batch operations per acquisition, and use fewer threads.

Likely follow up: "How do you prove false sharing?" perf c2c reports cache lines with heavy cross-core modified hits and the offsets touched; padding the fields apart and seeing throughput jump confirms it.

12Corecode-reviewchecklistMicrosoft
Spot the concurrency bugs: what is on your checklist when you review threaded code?
Model answer
  • A stop flag or shared field read without synchronization: while (running) on a plain boolean may never see the update. Use volatile or std::atomic<bool>.
  • Compound actions on a concurrent collection: if (!map.containsKey(k)) map.put(k, v). Use putIfAbsent, computeIfAbsent or merge.
  • wait or await under if instead of while, or a condition variable wait without a predicate.
  • notify when waiters wait for different predicates.
  • Locking the wrong object: an instance synchronized method guarding a static field, synchronized (new Object()), a lock field that gets reassigned.
  • Double-checked locking without volatile (or without an atomic in C++).
  • Iterating a Collections.synchronizedList without holding its lock.
  • lock() outside try and unlock() not in finally; in C++, any manual unlock.
  • this escaping a constructor, for example by starting a thread or registering a listener there.
  • A non-thread-safe type shared between threads: HashMap, SimpleDateFormat, or a std::vector that two threads push_back to.
  • Exceptions lost in submit futures that nobody calls get on.
  • thread.run() called instead of start().
  • C++: a std::thread that is never joined, a lambda that captures locals by reference while running beyond their scope, and one shared_ptr object written by one thread while another reads it.

Likely follow up: "Which one have you seen most in production?" Be ready with a real story. The check-then-act on a map is a strong pick, because each call looks safe on its own and the fix (computeIfAbsent or merge) is one line.

13Seniorcode-reviewraiicppAmazon
This C-style container guards everything with one mutex. What is wrong with it?
Model answer
  • Self deadlock: push holds m and calls resize, which locks m again. The default mutex is not recursive, so the thread blocks on itself (formally undefined for the default type).
  • A leaked lock: the early return in get never unlocks, so the next caller of any method blocks forever. It looks like a deadlock but is a resource leak.
  • No check for negative i, so data[i] can read out of bounds; and -1 is indistinguishable from a stored value.
  • No handling of a failed allocation in resize.
  • No destructor, so the array leaks, and the implicit copy duplicates the raw pointer (a double free once someone adds a destructor) and the pthread_mutex_t, which must never be copied.

The fix has two parts: RAII so every return unlocks, and a split between public methods that lock and private helpers that require the lock to be held already.

Likely follow up: "Why not just use a recursive mutex?" It hides the design problem: resize would run with the invariants of push half updated, and the nesting makes it hard to reason about what holds when.

14Seniorwhat-can-this-printmemory-modelLinkedInMicrosoft
How do you answer a "what can this print" question about threads?
Model answer

Work in three steps. Find the shared variables and the synchronization between the threads. If every shared access is ordered by happens-before, enumerate the interleavings of the atomic steps and list the outputs. If there is a data race or relaxed atomics, also allow stale values and reordering: outcomes that no interleaving can explain become possible (in Java they are legal; in C++ a data race is undefined behavior, so anything goes).

Interleavings give (r1, r2) as (0, 1), (1, 0) or (1, 1). With plain fields, or with acquire and release in C++, (0, 0) is also possible, even on x86: each store sits in its core's store buffer while that core's load runs. With Java volatile or C++ seq_cst atomics on both variables, (0, 0) is forbidden.

Another favourite: two threads each run count++ 1000 times on a plain shared int. In Java any final value from 2 to 2000 is possible. The 2 comes from a pathological interleaving in which one thread's stale write erases almost all of the other's progress. In C++ it is a data race, so formally undefined.

For output interleaving: in Java each println call is atomic as a whole, but two separate print calls from different threads can interleave. In C++ each operator<< on std::cout is a separate call, so std::cout << "a" << i << '\n' from two threads can interleave mid line.

Likely follow up: "Make (0, 0) impossible with the least change." Make x and y volatile in Java, or std::atomic with the default seq_cst in C++. Acquire and release alone are not enough for this pattern.

15Stretchstatic-analysisjavacpp
Which static tools catch locking mistakes before the code runs?
Model answer

In C++, Clang's Thread Safety Analysis. You annotate data with the mutex that guards it and functions with the locks they need, then compile with -Wthread-safety; the compiler warns when guarded data is touched without the lock, or a function is called without a lock it requires. Abseil's absl::Mutex comes with the annotations, so you write int balance_ ABSL_GUARDED_BY(mu_); and functions marked ABSL_EXCLUSIVE_LOCKS_REQUIRED(mu_) or ABSL_LOCKS_EXCLUDED(mu_). libc++ can annotate std::mutex too, behind a configuration macro.

In Java, Error Prone's @GuardedBy checker verifies that annotated fields are accessed only while holding the named lock. SpotBugs flags inconsistent synchronization (a field locked on some paths but not others), double-checked locking, wait outside a loop and similar patterns, and IDE inspections catch many of the same.

The limits: they check locking discipline, not logic. A check-then-act across two properly locked methods passes every one of them, and aliasing (two references to one object) confuses them.

Their biggest value is documentation that the compiler enforces: every field states which lock guards it, which is exactly the sentence an interviewer wants to hear for each piece of shared state.

Likely follow up: "Would you add these to an existing codebase?" Yes, incrementally: annotate the most concurrent classes first, turn the warnings into errors for those files, and expand from there.

16Coreexceptionsthreadsjavacpp
A worker thread dies silently and the system stalls. How do exceptions escape threads in Java and C++, and how do you surface them?
Model answer

Java: an uncaught exception ends that thread only. The default handler prints the stack trace to stderr and every other thread carries on, so a pool or pipeline can quietly lose a worker. In an ExecutorService, execute behaves the same way (the pool replaces the worker), but submit captures the exception inside the Future, and nobody sees it unless someone calls get. CompletableFuture stages likewise hold the exception until something joins or handles them.

C++: an exception escaping a std::thread's function calls std::terminate, and the whole process dies. Loud, but abrupt, with no chance to clean up.

Surfacing them:

  • Java: always call get on futures you submit, or attach whenComplete or exceptionally handlers that log; set Thread.setDefaultUncaughtExceptionHandler as a safety net; wrap tasks in a decorator that logs and rethrows.
  • C++: transport the exception to whoever waits. std::packaged_task, std::async and std::promise::set_exception carry it into a std::future, whose get rethrows it. Manually, catch with catch (...), store std::current_exception() in a std::exception_ptr, and rethrow it with std::rethrow_exception in the joining thread.

In your own pool, the worker loop catches everything a task throws, records it in that task's future, and keeps running.

Likely follow up: "What about Errors like OutOfMemoryError in your worker?" Record them in the future too, then let them propagate, because the JVM may be unhealthy. That is what the JDK does: FutureTask (behind submit) stores any Throwable, Errors included, while a task run through execute that throws lets the worker die, and ThreadPoolExecutor replaces it.
