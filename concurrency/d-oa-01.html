Why. A std::thread starts running as soon as it is constructed. t.join() returns only after t has finished, so A always comes before B, which rules out BACDE. Once u exists, main printing D races with u printing C, so both ABCDE and ABDCE are possible. E is printed after u.join(), so C is always before E, which rules out ABDEC. Why. A Thread object can be started exactly once. Calling start() on a thread that is no longer in the NEW state throws IllegalThreadStateException, even after the thread has finished and been joined. The exception propagates out of main, so y never prints. To run the work again, create a new Thread or submit the Runnable to an executor.
C++ onlyWhat happens?
Why. After the first join(), t no longer represents a thread, so t.joinable() is false. Calling join() on a non-joinable std::thread throws std::system_error with the invalid_argument error condition. Nothing catches it, so std::terminate runs (libc++ prints "thread::join failed: Invalid argument"). The compiler cannot see this; check joinable() or use std::jthread, which joins once in its destructor.
Which statements about a mutex and a binary semaphore (a semaphore with one permit) are true?Select all that apply
Why. Ownership is the real difference. A mutex is locked and unlocked by the same thread, which lets the system detect misuse and apply priority inheritance (boosting the owner). A semaphore is a permit counter with no owner: any thread may release, which makes it a signaling tool (one thread releases, another acquires) but also means nothing stops a buggy thread from releasing a lock it never took. They are not interchangeable, and acquire blocks when no permit is available.
A team fixes a deadlock by making every thread acquire account locks in increasing order of account id. Which of the four necessary conditions for deadlock does this break?
Why. A deadlock needs all four: mutual exclusion, hold and wait, no preemption and circular wait. With a global order, a thread holding lock i only ever waits for a lock j greater than i, so a cycle of waiting threads would need ids that increase all the way round and come back to the start, which is impossible. Hold and wait still happens (a thread holds the lower lock while waiting for the higher one), which is why "hold and wait" is the tempting wrong answer.

A fixed pool of 4 threads receives 10 independent tasks at the same moment. Each task sleeps for 1 second and uses no CPU. Roughly how long until all 10 have finished?
Why. Only 4 tasks run at a time and a task cannot be split. The first 4 run from 0 to 1 s, the next 4 from 1 to 2 s, and the last 2 from 2 to 3 s, so the answer is ceil(10 / 4) = 3 waves of 1 second. 2.5 s treats the work as divisible (10 task seconds over 4 threads). 1 second needs 10 threads, and 10 seconds is a single thread. Because the tasks sleep rather than compute, a bigger pool would finish sooner even on few cores.
80 percent of a job's running time parallelizes perfectly and the remaining 20 percent is serial. What is the best possible speedup on 4 cores, and what is the limit with unlimited cores?
Why. Amdahl's law: speedup = 1 / (s + p / n) with serial fraction s = 0.2 and parallel fraction p = 0.8. On 4 cores: 1 / (0.2 + 0.8 / 4) = 1 / (0.2 + 0.2) = 1 / 0.4 = 2.5. As n grows, p / n goes to 0, so the limit is 1 / 0.2 = 5. The 3.2 answer multiplies 0.8 by 4, which forgets that the serial part still takes its full time.
Java onlyWhat can happen when this runs on a typical HotSpot JVM?
Why. A plain field read in a hot loop may be read once and kept in a register: the JIT is allowed to do that because nothing (no volatile, no lock, no atomic) promises the worker will ever see another thread's write. A real run hung until it was killed. Thread.sleep has no synchronization semantics at all. Declare running volatile (or use an AtomicBoolean) so each read sees the latest write.
C++ onlyWhat can happen when this is built with optimizations?
Why. An unsynchronized write and read of the same non-atomic variable is a data race, so the whole program has undefined behavior. The compiler may assume no other thread changes running and hoist the read; a loop with no side effects may also be assumed to terminate. A clang -O2 build of this exact program printed stopped after 0 immediately, before main had even cleared the flag. volatile is not a synchronization tool in C++. Use std::atomic<bool> running{true};.
Java onlyA thread calls awaitReady() while ready is false. What happens?
Why. wait atomically releases the monitor and suspends the thread, so the calling thread must own that monitor: the call belongs inside synchronized (lock) { ... }. Without it, the JVM throws IllegalMonitorStateException ("current thread is not owner") at run time; the compiler does not check. The same rule applies to notify and notifyAll, and the setter of ready must also hold lock so the change and the notify cannot slip between the waiter's check and its wait.
C++ onlyWhat happens when you build this?
Why. wait has to release the mutex while sleeping and take it back before returning, so it needs a lock object that can unlock and relock: std::unique_lock<std::mutex> lk(m);. std::lock_guard has no unlock, and no wait overload accepts it, so clang reports "no matching member function for call to 'wait'". Keep the predicate form; it handles spurious wakeups.
A counting semaphore starts with 2 permits (new Semaphore(2) in Java, std::counting_semaphore<10> s(2) in C++). These steps run in this order, each one finishing or blocking before the next begins: A acquires, B acquires, C acquires, D releases (D never acquired anything), E acquires, A releases. What is the state at the end?
Why. A and B use the two initial permits, so C initially blocks. D may release without acquiring because a semaphore has no owner. That release and A's later release supply exactly two permits for C and E, so once those pending acquires have run, neither is blocked and the count is 0. One possible schedule lets C take D's permit, then E take A's permit. The default Java semaphore and C++ semaphore do not promise FIFO service: E could take D's permit before C runs, leaving A's permit for C instead. A release makes progress possible; it does not guarantee that a particular waiter has already resumed when the releasing call returns.
Thread 1 calls transfer(a, b, 10) while thread 2 calls transfer(b, a, 20). Which changes remove the deadlock? Select all that apply
Why. The deadlock is thread 1 holding a and waiting for b while thread 2 holds b and waits for a. A global order prevents this cycle. One global lock replaces the pair, at the cost of serializing transfers. A timed attempt may still wait while holding the first lock, but on failure it releases that lock, so the circular wait cannot remain permanent. Random backoff reduces repeated collisions; it does not guarantee that every thread eventually succeeds. Making balances volatile or atomic does not change lock acquisition, and sleeping between acquisitions does not prevent the cycle.
Four processes arrive at time 0 in the order P1, P2, P3, P4 with CPU bursts 10, 4, 2 and 6. What is the average waiting time under FCFS, and under non-preemptive SJF?
Why. FCFS runs P1 0 to 10, P2 10 to 14, P3 14 to 16, P4 16 to 22. Waiting times are 0, 10, 14, 16, total 40, average 10. SJF runs the shortest first: P3 0 to 2, P2 2 to 6, P4 6 to 12, P1 12 to 22. Waiting times are P3 0, P2 2, P4 6, P1 12, total 20, average 5. 15.5 and 10.5 are the average turnaround times (finish minus arrival), and 13.3 and 6.7 divide by 3 because the zero wait was dropped. Order matters a lot: one long job first makes everyone wait (the convoy effect).
