Thread-local storage, daemon threads, sleep, yield and priority

Per-thread variables and how they leak in pools, threads that do not keep a program alive, and why sleep, yield and priority never synchronize anything.

Asked atMicrosoft
Before this:Creating, starting and joining threadsStopping a thread: interruption and cooperative cancellation

Five small tools that arrive as follow up questions: give each thread its own copy of something, let a background thread die with the program, pause a thread, and nudge the scheduler. Each one has exactly one trap that interviewers like to probe.

In plain words

Every cook in a kitchen gets their own knife: nobody waits for a knife, and nobody needs to ask whose turn it is. That is thread-local storage. But when one cook's shift ends and the next cook takes over the same station, the old knife is still lying there, unwashed. In a thread pool, the "station" is the thread, and whatever the last task left behind is still there for the next one.

The night watchman leaves when the last staff member goes home; a watchman alone does not keep the building open. That is a daemon thread. And telling a cook "wait two minutes" or "let someone else go first" is a timing request, not a promise that anything in particular will have happened by then.

Thread-local storage: one copy per thread

A thread-local storage variable looks like one variable in your code, but every thread that touches it gets its own separate slot. The slot needs no lock, but a pointer or reference stored there can still point to an object shared with other threads. Keeping the referenced object private too gives you thread confinement.

  • Java: ThreadLocal<T>, usually a static final field. ThreadLocal.withInitial(supplier) gives each thread a starting value on its first get(); set replaces this thread's value; remove deletes it.
  • C++: the thread_local storage class. A namespace scope or static member thread_local variable has one instance per thread; a block scope one is initialized the first time each thread reaches its declaration. Each copy is destroyed when its thread exits.

Typical uses:

  • A non-thread-safe helper, one per thread. A formatter, a parser, a MessageDigest, a std::mt19937 random generator. For random numbers Java already has one: ThreadLocalRandom.current().
  • A reusable scratch buffer, to avoid allocating on every call in a hot path.
  • Per-thread statistics, merged when someone asks for a total. Striped counters such as LongAdder use a close cousin of this idea: a few shared cells, each thread hashed to one, summed on read.
  • Request context that deep code needs without passing it through every call: the current user, a trace id, a database transaction. Logging libraries keep their diagnostic context this way.

The trap: thread pools reuse threads

A thread-local value lives as long as its thread. On a thread that runs one task and dies, that is fine. On a pool thread, which runs thousands of tasks over hours, a value set by one task is still there when the next task runs. If the value is the current user, the next request runs as the wrong person. That is a security bug, not just a correctness bug.

The rule: whoever sets a thread-local on a pool thread clears it on every way out, with remove() in a finally in Java and a scope guard in C++. Two more Java details matter:

  • Memory leaks. Each thread keeps its values in an internal map whose keys are weak references to the ThreadLocal objects but whose values are strong. A large value set on a long-lived pool thread stays reachable until it is removed or overwritten; in application servers this is a well-known way to leak whole class loaders.
  • InheritableThreadLocal copies at thread creation, not at task submission. A pool thread inherits whatever value the thread that created it had, once, and keeps it. Tasks submitted later by other requests do not inherit anything. To carry context into a pool, capture it when you submit and set it (and clear it) inside the task.

Java 21 adds virtual threads, which also support ThreadLocal. With a million virtual threads, a cache stored in a thread-local means a million caches, so per-thread caching stops making sense there; see virtual threads.

Daemon threads and detached threads: who keeps the program alive?

The two languages answer "when does the program end?" in opposite ways, and this is where Java's daemon threads and C++'s detached threads differ.

JavaC++
The program ends whenEvery non-daemon thread has finished (or System.exit is called)main returns or std::exit is called, whatever other threads are doing
A background thread that must not block exitA daemon thread: setDaemon(true) before start()Nothing to declare: no thread ever keeps the process alive
What happens to it at exitAbandoned mid-step: no finally blocks, no cleanupA detached thread is stopped wherever it is: no destructors on its stack, and static objects may be destroyed while it still runs
A thread you forgot aboutA non-daemon thread keeps the JVM running foreverA still-joinable std::thread being destroyed calls std::terminate

Use a daemon (or detached) thread only for work that is safe to cut off at any instruction: refreshing a cache, emitting metrics, housekeeping. Never for work that must complete, such as writing a file, committing a transaction or flushing a log. For those, keep a normal thread, stop it cooperatively and join it.

The daemon flag is inherited: a thread created by a daemon thread is a daemon too, and main is not a daemon. Virtual threads are always daemon threads. And the reverse surprise: the threads of Executors.newFixedThreadPool are non-daemon, so a program that forgets to call shutdown() on its pool never exits.

sleep: a pause, not a synchronization

Thread.sleep(ms) (or sleep(Duration) since Java 19, or TimeUnit.SECONDS.sleep(n)) requests a pause subject to system timer and scheduler accuracy. C++'s std::this_thread::sleep_for waits at least the requested duration; sleep_until waits for a deadline on its chosen clock, so use a steady clock for elapsed time. Scheduling can delay resumption. Java's sleep is interruptible and throws InterruptedException; standard C++ sleep has no cancellation mechanism, which is why the cancellation lesson used a stop-aware wait instead.

Two facts get asked constantly:

  1. Sleep keeps every lock the thread holds. Sleeping inside synchronized or under a lock_guard makes every other thread that needs the lock wait out the whole sleep. Waiting on a condition is different: it releases the lock while waiting and takes it back before returning.
  2. Sleep never fixes a race. "Sleep 100 ms so the other thread is done" makes the bug rarer, not gone, and in C++ the racy access is still undefined behavior. Synchronize with join, a future, a latch or a condition variable.

For periodic work, a loop of sleep(period) drifts, because the work itself takes time. Sleep until a deadline instead: in C++ add the period to a std::chrono::steady_clock time point and call sleep_until; in Java compute the next deadline from System.nanoTime(), or use a scheduled executor.

yield and spin-wait hints

Thread.yield() and std::this_thread::yield() tell the scheduler "I can give up the processor now if someone else wants it". It is a hint: it may do nothing at all, and it guarantees nothing about who runs next. Its honest uses are few, mostly in spin loops that have waited a while and in tests that try to shake out interleavings.

Java 9 added Thread.onSpinWait(), a spin-wait hint for the inside of a busy waiting loop: on x86 it becomes a PAUSE instruction that saves power and helps a sibling hyperthread. It does not sleep and does not yield. Standard C++ has no portable equivalent; code uses _mm_pause() on x86. Both belong to the world of busy waiting and spinlocks.

Priority: a request, rarely honored

Java threads have priorities from MIN_PRIORITY (1) through NORM_PRIORITY (5) to MAX_PRIORITY (10), set with setPriority and inherited from the creating thread. They are hints to the operating system. On Linux, HotSpot ignores them by default, because ordinary (non real time) Linux scheduling has no static priorities; and a virtual thread's priority is always NORM_PRIORITY. Standard C++ has no priority API at all: you reach the platform through native_handle() and calls such as pthread_setschedparam, and real time policies usually need special privileges.

So never use priority for correctness: a high-priority thread is not guaranteed to run first or more often. Priorities also invite priority inversion, where a high-priority thread waits for a lock held by a low-priority one that cannot get the processor.

Worked example: the support ticket "I saw someone else's account page"

A web service authenticates each request, stores the user in a ThreadLocal, and code deep in the request reads it. Requests run on a pool of 200 threads. Once in a while, a user reports seeing another user's data. Walk through it the way you would in a debugging round:

Why it is rare: it needs an unauthenticated request, a code path that consults the user anyway, and a thread that last served a logged-in user. The fix: set and clear in one place, in a try and finally (or a scope guard in C++) wrapped around the whole request, so no exit path can skip the clear. The senior addition: also clear at the start of each request, so one buggy path elsewhere cannot poison the thread, and add a test that runs an anonymous request on a thread right after a logged-in one.

Common mistakes

  • Setting a thread-local on a pool thread and never clearing it. The next task sees stale data, and large values leak memory. Clear in finally or with a scope guard.
  • Expecting tasks submitted to a pool to see the submitter's thread-locals. They run on other threads. Capture the value at submission and pass it in.
  • Using InheritableThreadLocal with pools. The value is copied once when the pool thread is created, then reused for unrelated tasks.
  • Daemon (or detached) threads doing work that must finish. They are cut off mid-write at exit. Stop them cooperatively and join them.
  • Calling setDaemon after start. It throws IllegalThreadStateException.
  • Sleeping while holding a lock, or sleeping to "fix" a race. The first stalls every other thread; the second only hides the bug.
  • Relying on yield or priorities to order threads. Both are hints the platform may ignore. Order threads with synchronization.

In the interview

These come as short theory follow ups and as multiple choice items in online assessments. Microsoft has asked C++ candidates about thread_local right after a producer and consumer question, and "sleep versus wait" is an old favorite in Java screens. They also appear inside designs: "how does your logger know the request id?" or "why does your service not shut down?".

Thread-local storage gives each thread its own copy, so it needs no locking; I use it for non-thread-safe helpers and per-request context. On a pool thread it outlives the task, so I set and clear it in one try and finally, and I never expect it to follow work into another thread: I pass context explicitly when I submit a task.
Sleep pauses the thread and keeps its locks; a condition wait releases the lock while waiting. Neither sleep, yield nor priority is synchronization: they only change timing.

Follow ups to expect: "Daemon versus user thread?" "What happens to a daemon thread's finally block when the JVM exits?" (it does not run). "When is a C++ thread_local initialized and destroyed?" (namespace scope: before its first use in each thread; block scope: when each thread first reaches it; destroyed at thread exit). "Does Thread.yield() guarantee another thread runs?" (no). "Why is my Java program not exiting?" (a non-daemon thread, often an executor that was never shut down).

Senior depth

Thread-local is implicit coupling. It is a global variable per thread: convenient, invisible in signatures, and wrong the moment work hops threads (pools, async callbacks, CompletableFuture stages, coroutines). Mature frameworks propagate context explicitly by wrapping every submitted task. Java's newer ScopedValue (a preview API in Java 21) binds a value for a bounded scope instead, which avoids the leak by construction.

C++ costs and lifetimes. Reading a thread_local is close to a normal global access in the common case, a little more inside a shared library or when it has a dynamic initializer (the compiler adds a first-use check). Its destructor runs when the thread exits, so a thread_local that holds a connection closes it then; on a detached thread cut off at process exit, it never runs.

Shutdown is a design topic. "Which threads must finish, which may be abandoned, and in what order do we stop them?" is a question about data integrity. A good answer separates the threads that own durable work (stopped cooperatively and joined, with a timeout) from best-effort helpers (daemon or detached), and uses shutdown hooks only for short, safe cleanup.

Key takeaways

  • Thread-local storage gives every thread its own slot: ThreadLocal in Java, thread_local in C++. Objects reached through that slot must also stay confined to avoid sharing.
  • Pool threads outlive tasks, so clear thread-locals in finally or with a scope guard; pass context explicitly to submitted tasks.
  • Java exits when the last non-daemon thread ends and abandons daemon threads; C++ exits when main returns and cuts off detached threads.
  • Sleep keeps locks, guarantees no ordering, and never fixes a race; condition waits release the lock.
  • yield, onSpinWait and priorities are hints; never build correctness on them.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A request handler running on a 4-thread pool sets a thread-local currentUser and never clears it. Later, an anonymous request that sets nothing runs on the same pool thread and reads currentUser. What does it see?
Why. A thread-local belongs to the thread, not to the task, and a pool thread runs many tasks. Neither a Java pool nor your C++ worker loop clears it for you. The value is per thread, so it cannot come from another thread's request; it is whatever this thread last stored.
A thread sleeps for 2 seconds while holding a lock (inside synchronized, or under a std::lock_guard). What do other threads that need that lock do meanwhile?
Why. Sleep only pauses the thread; everything it holds stays held. The release-while-waiting behavior belongs to Object.wait, Condition.await and condition_variable::wait, which is exactly why they take the lock as an argument or require you to hold it.
A thread-local counter starts at 0 in each thread. Two threads each increment it 1,000 times, with no lock. Afterwards each reads its counter, and a third thread, which never incremented it, reads it too. What do they read?
Why. Each thread has its own copy, so there is nothing to race on and nothing is lost: each copy counts exactly that thread's increments. The third thread's copy was never touched, so it holds the initial value (0 here). That is also why a thread-local cannot be used to count totals across threads without merging the copies.
You need thread A to finish its step before thread B starts its step. Which of these can you rely on?
Why. Priorities may be ignored (HotSpot on Linux ignores them by default), yield may do nothing, and a sleep only makes the wrong order less likely. Ordering between threads needs a happens-before edge, which only synchronization provides.
Which are good uses of thread-local storage? Select all that apply.Select all that apply
Why. Thread-local storage shines when each thread needs its own private instance. It cannot give a total across threads by itself (each thread sees only its own copy), and it does not travel with work submitted to other threads: pool tasks run on threads that never saw the submitter's values.
Java onlymain starts a non-daemon thread that loops forever, then main returns. What happens?
Why. Returning from main does not end the JVM while a non-daemon thread is alive. Platform threads created with new Thread inherit daemon status unless it is changed before starting; virtual threads are always daemon threads. A fixed thread pool uses non-daemon threads by default, so forgetting shutdown() can keep the program alive. Explicit JVM exit can terminate non-daemon threads too.
C++ onlymain creates a std::thread that loops forever, calls detach() on it, and returns. What happens?
Why. Returning from main calls std::exit, and the process ends regardless of other threads. std::terminate happens only when a still-joinable std::thread object is destroyed; a detached thread is no longer joinable. Keeping the process alive for a thread is exactly what Java's non-daemon threads do, and C++ has no such concept.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Explain "sleep versus wait" to an interviewer, in Java and in C++. Include what happens to locks and how each one ends.
Model answer

Sleep requests a timed pause and has nothing to do with any lock or condition: Thread.sleep in Java, std::this_thread::sleep_for or sleep_until in C++. Java's timing is subject to timer and scheduler accuracy; C++ sleep_for waits at least the requested duration. Sleep keeps every lock the thread holds, so sleeping inside a critical section stalls everyone who needs that lock. Java interruption ends sleep early with InterruptedException; standard C++ sleep has no cancellation mechanism.

Waiting means waiting for a condition: Object.wait (inside synchronized on the same object), Condition.await, or std::condition_variable::wait with a std::unique_lock. It atomically releases the lock while the thread waits, and retakes it before returning, so other threads can change the state being waited for. It ends when another thread notifies, or spuriously, or on timeout or interrupt, which is why you always wait in a loop that re-checks the condition. In short: sleep is about time and keeps locks; wait is about state and releases the lock.

Write code
Many threads call newToken(), which needs a random number, and render(name, score), which builds a short string in a buffer. A shared generator is either contended (Java Random) or not thread-safe at all (C++ std::mt19937). Make both functions safe and fast without any lock.
Model answer

Each thread gets its own generator and buffer the first time it calls the function, so there is no sharing, no lock and no contention. In Java, ThreadLocalRandom.current() must be called on the thread that uses it, never stored in a shared field. Both functions return a fresh copy of the result rather than the buffer itself, so the caller never holds a reference to per-thread storage that the next call will overwrite. These helpers keep no per-task state, so nothing needs clearing between tasks; a request context would.

Debug
A tracing library stores the request id in an InheritableThreadLocal "so that child threads see it". The service submits work to a shared thread pool. Logs written by pool tasks show request ids of requests that finished long ago. Explain why, and fix it.
Model answer

InheritableThreadLocal copies the parent's value into a child thread once, when the child thread is created. Pool threads are created lazily by whichever request happened to trigger their creation, inherit that request's id, and then live for hours running tasks for unrelated requests. Tasks submitted later do not inherit anything, because submitting a task does not create a thread. So every task on that pool thread logs the id of the request that created the thread, unless something overwrites it.

The fix is to propagate context per task, not per thread: when submitting, capture the current request id, and wrap the task so it sets the id before running and removes it in a finally. Most tracing libraries provide such a wrapper for executors. In C++, thread_local is never inherited at all, so the same rule applies from the start: capture the context at submission and pass it to the task explicitly.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"An anonymous request occasionally runs as the previous user on a pool thread. We use thread-local context. What would you check and change?"
What a strong answer covers
  • The context belongs to the worker thread and survives task completion unless cleared
  • A logged-in request leaves its user behind; an anonymous request on that worker reads it
  • Initialize context at request entry and clear on every exit with Java finally or C++ RAII
  • Capture context at task submission; thread-local values do not automatically follow work into a pool
  • Thread-local references do not make their referenced objects private
  • Test sequential requests on one worker, including an exception before cleanup
How a senior would say it
I would first check for context left behind on a reused worker. Thread-local means one slot per thread, not one slot per request. Alice's request sets the user and returns without clearing it. An anonymous request then runs on that same worker, sets nothing, and reads Alice from the old slot. There need not be two requests running at once for this bug to happen. I would put context setup and cleanup at the request boundary. At entry, explicitly install the current user or the anonymous state. At exit, remove the Java thread-local in a finally block, or use a C++ scope guard that clears it even when handling throws. If work moves into another task, capture the context at submission and install it within that task's scope. An inheritable Java thread-local copies at thread creation, so it does not solve propagation into an existing pool. I would also check that the context does not hold a shared mutable object: a private slot does not make its referent private. My regression test would use one worker, run Alice's request and then an anonymous request, and repeat with Alice's handler throwing. The anonymous request must see no previous user, and the cleanup must still run.

Likely follow up: How would the cleanup change if one context scope could be nested inside another?

Out loudabout 75 s
"The worker needs this lock to set ready. My waiting thread holds it and sleeps in a loop. Why does nothing progress, and would yielding help?"
What a strong answer covers
  • Sleeping retains the lock, so the worker cannot acquire it to change the predicate
  • Yield and priority do not release the lock or establish ordering
  • Wait on a condition associated with the lock, releasing it while blocked
  • Reacquire the lock and recheck the predicate in a loop after every wakeup
  • Use Java interruption or a C++ stop-aware wait for cancellation, and join for completion
How a senior would say it
The waiting thread is preventing the state change it is waiting for. Sleep keeps the lock, so the worker cannot acquire that lock and set ready. Yielding would not release it either, and changing priorities would not repair the protocol. I would use a condition wait tied to the same lock that protects ready. In Java, that can be the lock object's wait method inside synchronized; in C++, a condition variable with a unique lock. Waiting releases that lock while blocked and reacquires it before checking the predicate again. The check belongs in a loop because wakeups can be spurious, and another thread can change the state before the waiter resumes. The worker sets ready under that lock and notifies the waiter. I would also define cancellation: Java waits can throw on interruption, while a C++ stop-aware wait needs explicit support. If all I need is to wait for the worker to finish, joining is simpler. The choice is based on the event I need, not a guessed number of milliseconds.

Likely follow up: What if the waiting thread also holds a second lock that the worker needs?

Out loudabout 75 s
"Our background log flusher delays shutdown. Can I make it a Java daemon or detach it in C++?"
What a strong answer covers
  • Required log writes need an explicit completion protocol, not abandonment at process exit
  • Java daemon threads do not keep the JVM alive; C++ detach gives up joining
  • Neither mechanism guarantees cleanup or completion when the process exits
  • Stop admission, drain accepted work, flush, signal completion and join
  • Define timeout failure and keep C++ resources alive until the worker stops
How a senior would say it
I would first decide whether losing accepted log records is allowed. If those records must be preserved, making the thread disposable is the wrong shutdown policy. A Java daemon does not keep the JVM alive after the last non-daemon thread finishes. C++ detach gives up the ability to join through that thread object; it does not make the worker keep the process alive. At process exit, neither mechanism guarantees that the worker finishes its flush or runs its cleanup. I would stop accepting new records, tell the worker to drain what was accepted, flush according to the logger's durability contract, and join after it reports completion. If shutdown has a deadline, exceeding it must produce an explicit failure outcome rather than a false claim that everything was saved. In C++, the queue, stream and other resources must remain alive until the worker has stopped using them. A daemon can be appropriate for disposable metrics, but that is a deliberate loss policy. The real fix is a shutdown protocol that matches the value of the work.

Likely follow up: What does a successful flush need to mean if the caller requires durability after a machine crash?
