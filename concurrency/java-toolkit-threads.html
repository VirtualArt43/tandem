The toolkit: Thread, Runnable, Callable and virtual threads

Create and own Java threads, read their lifecycle APIs, handle cancellation and failures, and choose virtual threads and thread-local state deliberately.

Before this:Classes, interfaces and inheritanceLambdas, functional interfaces and method referencesExceptions, InterruptedException and try-with-resourcesTime: nanoTime, Duration and TimeUnit

You can know Java syntax and still run work on the wrong thread, return before a worker finishes, or lose a request's context. Read every thread API as a contract about who executes, who waits, and who owns the outcome.

In plain words

A job card describes work; a person carries it out. Writing another card does not hire another person, and handing someone a card does not mean they have finished. You must also decide how to ask them to stop, collect their answer, and hear about a failure.

A private locker belongs to the person, not the next job they pick up. Leave yesterday's paperwork inside and today's job may use the wrong customer's details. That is the trap behind thread-local request context.

Why this matters for concurrency

These APIs appear in every worker, test driver and concurrent LLD exercise. Separate the task from its execution and lifetime. A class implementing Runnable describes behaviour; its owner decides whether to call it directly, start a thread, or submit it to an executor.

The lambda lesson teaches captures and task interfaces, and the exception lesson teaches propagation and restoration. Here you practise their thread APIs. Keep broader design rules in composition and SOLID and LLD design.

API card: tasks and platform threads

Thread, Runnable and ThreadLocal are in java.lang; Callable and executor types are in java.util.concurrent. A thread is an execution context. A task object is ordinary Java behaviour, not a running thread.

Create the task, then start its thread

Here are an implementing class, a lambda, and a Thread subclass. The overrides are public because Runnable.run() is public. Prefer the first two for application work: they keep the task reusable and leave the class free to extend a domain base class. See overriding and polymorphism for the OOP rules.

The lines are class task on caller, class task on class-worker, lambda task on lambda-worker, then subclass task on subclass-worker. Direct run() did not start a, so its later start() is legal. After that start, the same Thread can never be restarted, even after termination.

The joins deliberately serialize this demonstration. To overlap independent work, start all workers first and then join them. start() does not promise that the child executes before the caller's next statement. Never start a thread from a constructor that exposes a partly initialized this; see safe publication.

start() also publishes the caller's earlier writes. They happen-before the worker's actions, even for ordinary fields. Construction alone does not provide that handoff, and writes made after start() need their own synchronization if the worker reads them concurrently.

The lifecycle names are NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING and TERMINATED. RUNNABLE does not prove a thread is currently on a CPU. BLOCKED specifically means waiting to acquire a monitor; waiting for a ReentrantLock commonly appears as WAITING or TIMED_WAITING. Do not coordinate by polling getState(); thread states explains these snapshots.

Join is a wait, not a cancellation policy

A join waits in the calling thread. Detecting a started worker's termination makes its writes visible through happens-before. A timed join that returns while the worker is alive gives no completion guarantee. Follow creating and joining threads and happens-before for the full argument.

This example uses CountDownLatch(1) as a test gate: await() waits until countDown() opens it. The worker cannot finish before the timeout, without relying on a lucky sleep. The synchronizer toolkit teaches the latch itself.

The answers are true, false, and 42. Only the final completed join justifies reading the result. Opening the gate in finally prevents an interrupted first wait from stranding the worker.

join(0) waits indefinitely, but join(Duration.ZERO) does not wait. The older overloads return immediately on an unstarted thread; the Duration overload throws IllegalThreadStateException. Joining yourself indefinitely deadlocks. Scheduling can delay return, and repeated waits need a remaining budget; see Java time units.

Do not join while holding an unrelated application lock the worker needs to finish. The caller keeps holding that lock while waiting, so caller and worker can wait for each other forever.

Sleep and the three interrupt methods

Interruption is a request the target must cooperate with. worker.interrupt() targets the worker; Thread.interrupted() targets whoever executes that statement. Even the legal but misleading spelling worker.interrupted() still tests and clears the caller, because the method is static.

sleep and a blocking join throw InterruptedException in the waiting caller and clear its status. Interrupting a thread waiting in worker.join() does not interrupt worker. The exception lesson covers propagation versus restoration; cooperative cancellation covers blocking APIs and shutdown design.

The sleep is an API probe, not coordination: the pending interrupt makes it throw. A normal sleep pauses the caller, may oversleep, releases no held lock, and does not publish writes. Write static calls with Thread, not an instance, to make their target clear.

A CPU loop must inspect its status between bounded pieces of work. Restoring the flag and repeatedly retrying an interruptible wait can create a hot failure loop; restoring and exiting is the usual Runnable boundary. Do not use obsolete stop, suspend or resume as lifecycle control; in Java 21 they throw UnsupportedOperationException.

Waiting to enter synchronized is not interruptible. Interrupting a thread blocked in an InterruptibleChannel operation closes the channel and throws ClosedByInterruptException, but arbitrary blocking calls need not respond. Use a supported timeout or cancellation mechanism, and retain ownership until termination is confirmed; another interrupt cannot force uncooperative code to finish.

Names, priorities and daemon status

A daemon thread does not keep the JVM alive. When all started non-daemon threads terminate, normal shutdown can begin; remaining daemon work has no completion or finally guarantee. Set platform daemon status before start. With new Thread(...), daemon status and priority come from the creator, with priority capped by the thread group's maximum.

metrics-reporter daemon=true precedes reporter completed because the caller waits. Removing the join makes completion uncertain. Daemon status alone is unsuitable for owning a durable log flush.

MIN_PRIORITY, NORM_PRIORITY and MAX_PRIORITY are 1, 5 and 10. Priorities cannot guarantee order, fairness or progress. Names help thread dumps; priorities and yield() cannot repair races. See daemon, sleep and priority mechanics.

Virtual threads change cost, not correctness

A virtual thread is scheduled by the runtime on a carrier platform thread. It has the familiar stack and interrupt API. Thread.currentThread() returns the virtual thread, not its carrier. These APIs are final in Java 21 and need no preview features.

A Thread.Builder is mutable and not thread-safe. Its factory() produces a thread-safe ThreadFactory for concurrent creators; each newThread(task) call still returns an unstarted thread.

Thread.ofVirtual().name("virtual-worker").start(task) combines construction and start. Virtual threads are always daemon threads with fixed priority 5; valid priority changes are ignored and setDaemon(false) is forbidden. Without a supplied name, their name is empty.

Virtual threads help when many tasks wait for supported blocking I/O. They do not add cores, make shared objects safe, or accelerate a single calculation. Prefer bounded CPU parallelism for compute-heavy work; see CPU versus I/O work.

Callable on a virtual thread per task

Neither Callable.call() nor Runnable.run() chooses another thread. There is no Thread(Callable) constructor. This program calls a task directly and through an executor; its result identifies the execution policy. Interface syntax and checked exceptions stay in the task-interface lesson.

Without an executor, wrap a callable in FutureTask<V>, which implements both Runnable and Future<V>. Pass the wrapper to a Thread, start it, and use the wrapper's get() for its result or ExecutionException; the owner still manages the thread's lifetime.

Run as an ordinary Java program, this prints false, true, then 42. Both tasks are submitted before either result is awaited. The tasks do not print, so unnamed executor threads do not obscure the output.

The executor creates new virtual threads rather than reusing a fixed set. Closing waits, but supplies neither a deadline nor automatic failure reporting. An uncooperative task can delay closure indefinitely. Future results and cancellation belong in the executor and future toolkit and futures and promises.

If interrupted while waiting, close() requests shutdown as with shutdownNow(), continues waiting for active tasks, and restores the caller's interrupt status before returning. It does not throw InterruptedException, so interrupting the owner does not guarantee a prompt exit from try-with-resources.

Cheap threads do not make dependencies unlimited. Limit database or remote-call concurrency with permits and bound admitted work; do not pool virtual threads merely to reuse them. Follow semaphores and backpressure.

On Java 21, blocking inside synchronized or certain native execution can cause pinning: the virtual thread cannot release its carrier. This is version-specific guidance. The core virtual-thread lesson covers scheduling and newer JVM differences; monitors and explicit locks cover locking choices.

Pinning threatens scalability, not mutual exclusion. For frequent, long blocking operations inside a monitor, consider shortening the protected region or using ReentrantLock; short in-memory synchronized sections do not need blanket replacement.

ThreadLocal belongs to the thread, not the request

Thread-local storage gives each thread a separate slot behind the same key. Use it for context across a call stack; prefer parameters when they make ownership clearer. A slot does not clone its value: storing the same mutable object in several slots still shares it.

The worker starts with none, A fails, and the context before B is again none. The caller still sees caller-context. These sequential jobs reproduce the reuse that makes stale context dangerous in pools.

remove() affects only the caller's slot; cleanup in the submitter cannot clear a worker's slot. set(null) leaves an initialized null value, whereas removal permits initialization again. Clean request context in finally to avoid retaining old context and large objects.

This cleanup assumes serve owns the outer request boundary. If a nested operation temporarily replaces an existing context, save and restore the previous value in finally; unconditional removal would erase the outer operation's context.

Ordinary thread locals are not inherited. With inheritance enabled, InheritableThreadLocal transfers values at child creation, not task submission, and by default shares the value reference. It is not general pool context propagation. Virtual threads support their own slots, but expensive per-thread caches multiply with task count. Continue with confinement and thread-local state.

Install an uncaught exception handler before start

An uncaught exception handler observes failure on the dying thread. It cannot resume the failed task and should be small and reliable. A per-thread handler takes precedence; otherwise the thread group handles failure, normally delegating towards the default handler or printing a trace.

Termination follows handler completion, so the completed join makes this single handler's write visible. Many concurrently reporting workers need a suitable shared collection or synchronization policy. Submitted tasks normally capture failure in their futures before this boundary; see exceptions inside threads.

Worked example: the request timed out, but the worker kept running

A handler starts a worker, calls worker.join(100), and returns a timeout response. The worker later writes to shared request state. The timeout ended the wait, not the work. Check termination, then apply the operation's cancellation policy.

Request interruption if supported and allow a separately bounded cleanup wait. If termination remains unconfirmed, report that and retain ownership; do not pretend the worker stopped. Unbounded cleanup would defeat the response deadline. Define how late results are rejected before sharing request state; putting the toolkit together makes this a class contract.

Java 21 reference points

Check overload details in the Thread API, builder configuration in Thread.Builder, and slot initialization in ThreadLocal. Oracle's Java 21 virtual-thread guide documents the resource and pinning guidance.

The Java memory model defines the start and termination visibility edges. The executor close contract specifies its interruption policy, and FutureTask supplies the callable-to-runnable adapter.

Common mistakes

  • Equating a task with a thread. Direct run() or call() is synchronous; choose execution explicitly.
  • Assuming timeout means completion. Inspect termination and separately decide whether to request cancellation.
  • Testing interruption destructively. Use isInterrupted() to observe; consume the caller's status with Thread.interrupted() only deliberately.
  • Using daemon status, priority or sleep to guarantee an outcome. Await the event with a completion or synchronization mechanism.
  • Caching expensive resources per virtual thread. Borrow from a bounded resource pool and release reliably.
  • Clearing context on the submitter. Cleanup belongs on the thread holding the slot, even after failure.
  • Expecting join() to report failure. Record failures or inspect the future.

In the interview

Expect code-reading questions about which thread executes a line, followed by ownership questions: who waits, who cancels, and who sees failure? In LLD, separate your domain task from its execution policy.

Starting schedules execution once; joining observes termination. A timed wait and an interrupt request each leave me responsible for discovering whether the work actually stopped.
I choose virtual threads for many blocking tasks, retain a limit around scarce dependencies, and define result collection, cancellation and context cleanup.

Follow ups include interrupted joiners, failed request cleanup and Java 21 pinning. Shared-state fixes belong in volatile and atomics; changing thread type does not supply them.

Key takeaways

  • A task describes work; start() or an executor chooses concurrent execution. A Thread starts at most once.
  • A join timeout neither stops work nor reports failure; confirm termination before reading its completed result.
  • interrupt() requests; isInterrupted() observes; static interrupted() observes and clears the caller.
  • Virtual threads make waiting cheaper; CPU capacity, shared-state rules and resource limits still apply.
  • Thread-local context needs cleanup on its owning thread, and failures need an observation path.
  • Names aid diagnosis. Daemon status, priority and sleep cannot replace lifecycle ownership.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
A request owner calls worker.join(100), reads a plain result field, and returns. On timeout it adds worker.interrupt() and immediately reuses the request object. Identify the independent mistakes and correct the contract.
Model answer

The void join does not report completion: check isAlive() or the join(Duration) boolean. Reading the plain field while work continues has no completion visibility guarantee. interrupt() only requests cancellation, so immediate object reuse can overlap the old worker's writes.

Give each task private result ownership, read after confirmed termination or through a future, and define cancellation checkpoints. On timeout request cancellation if supported, allow a separately bounded cleanup budget, and report whether termination was confirmed. Do not reuse worker-owned state until safe; reject late results explicitly. If the joining caller is interrupted, propagate or restore its status at a boundary and separately decide what happens to the child.

Design
A service stores a request id and database connection in ThreadLocals on 20 reused workers. You propose virtual threads per request. What changes, and what remains the request owner's responsibility?
Model answer

Each virtual thread has its own slots, so a small request id can accompany its synchronous call stack. Clean it in finally and explicitly propagate context across execution boundaries. Do not allocate a connection per virtual thread: borrow from a bounded connection pool and return it on every path.

The owner still collects success or failure, defines cancellation and timeouts, awaits required completion, and bounds admitted work. Virtual threads do not make mutable shared objects safe. CPU-heavy stages need appropriate parallelism, and Java 21 code needs review for long blocking operations while pinned. Execution cost changes; ownership contracts remain.

Write code
Use ordinary int fields to pass 21 into one named worker and read its doubled result after it finishes. Write the handoff without volatile or a lock. Explain why moving the input assignment after start() breaks the argument.
Model answer

The caller's input write precedes start(), so the worker sees it. The worker's output write precedes observed termination, so a completed join() publishes the result back. No thread modifies either field concurrently with its reader.

Moving input = 21 after start() introduces an unordered read and write. The worker could read the initial zero instead; joining later cannot repair that earlier input race. A join that times out while the worker is alive also cannot justify reading output.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Walk me through Runnable, Callable and Thread. Why would you implement an interface instead of extending Thread?"
What a strong answer covers
  • Runnable and Callable describe tasks; Thread supplies an execution lifecycle
  • Runnable returns void without checked exceptions; Callable returns a value and may throw Exception
  • Direct run or call is synchronous; start schedules a thread once
  • Composition lets tasks be tested directly and scheduled by different owners
  • Completion and failure need joins plus reporting, or futures
How a senior would say it
I separate the work from the mechanism that runs it. A Runnable describes a task with no return value and no declared checked exceptions. A Callable can return a value and throw a checked exception. Neither interface starts anything: calling run or call directly executes on the caller. A Thread gives a Runnable an execution lifecycle, and start schedules that thread once. Extending Thread works, but it couples a domain task to one execution mechanism and uses its single class inheritance slot. I prefer a task object that I can test directly, give to a platform thread, or submit to an executor. Then the owner chooses how to collect completion and failure. With a raw thread I join and report failures separately; with a Callable I submit it and inspect the future. That keeps task behaviour separate from lifecycle policy.

Likely follow up: What happens if you call run, then start, then join, then start again on one platform thread?

Out loudabout 75 s
"Our request timed out after a join, but its worker kept changing state. What would you check and fix?"
What a strong answer covers
  • A timed join limits the caller's wait and does not stop the worker
  • Inspect isAlive after the void overload or the Duration overload's boolean
  • Interrupt requests cancellation and needs a cooperative task
  • Interruption of a joining caller does not cancel the worker
  • Bound cleanup separately and retain ownership if termination remains unconfirmed
  • Reuse or read result state only after safe completion or an explicit late-result policy
How a senior would say it
The timeout only ended the caller's wait. It did not stop the worker, so I would first check whether the code wrongly treats a timed join as completion. After the void overload I check isAlive; with the Duration overload I inspect its boolean. If the work is no longer wanted, I request interruption and check that the task actually cooperates, either through interruptible waits or explicit checks between bounded pieces of work. I also distinguish cancellation of the worker from interruption of the caller while it is joining. The latter ends the caller's wait and does not automatically cancel the worker. Next I give cleanup a separate bounded budget. If termination is still unconfirmed, I report that honestly and retain ownership rather than claiming the worker stopped. Finally, I stop reusing state that the old worker may still touch. I collect a private result after safe completion or define a policy that rejects late results. That fixes both the lifetime bug and the unsafe result access.

Likely follow up: What if the task never checks interruption and blocks in an API that does not respond to it?

Out loudabout 75 s
"Would you switch this blocking request service to virtual threads, and what would you review first?"
What a strong answer covers
  • Choose virtual threads for many waiting tasks, not added CPU capacity
  • Use a virtual thread per task and own completion, failure and cancellation
  • Bound scarce dependencies and admitted work independently of thread cost
  • Review Java 21 pinning during blocking synchronized or native execution
  • Review ThreadLocal cleanup and avoid expensive per-thread resource caches
How a senior would say it
I would consider virtual threads if the service has many requests waiting on blocking I/O. They reduce the cost of waiting; they do not add CPU capacity or make shared state safe. I would use a virtual thread per task and keep an explicit owner for results, failure and cancellation. An executor scoped with try with resources helps await termination, but its close can still wait indefinitely for uncooperative work. Next I would preserve a limit on database connections and remote calls, and bound admitted requests. Cheap threads must not become unlimited pressure on a dependency. Since this service runs Java 21, I would inspect long blocking operations inside synchronized regions or native execution for carrier pinning. Finally I would review thread locals. A small request id is reasonable with clear cleanup, but an expensive connection per virtual thread would multiply resource usage. I would borrow that connection from a bounded pool and return it reliably. Then I would measure the actual workload before claiming a throughput improvement.

Likely follow up: If each request is pure CPU work, what execution policy would you choose instead?
