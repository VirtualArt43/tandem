Client lifecycle wrapper

Build a primitivemedium40 minRubrikApple

An SDK can be thread-safe during requests and still fail when initialization or shutdown overlaps them. Make the whole lifecycle safe.

The task

Wrap the supplied Client. Its calls may throw unchecked exceptions in Java or exceptions in C++. The wrapper does not own the C++ client; it outlives the wrapper and all calls. Callbacks must not reenter the wrapper.

  • init() runs alone, with no client request or close overlapping it. A successful init is idempotent, including while requests are active. A failed init propagates its error and permits a retry; a waiting init caller may perform that retry.
  • A request arriving during init waits and rechecks the lifecycle state after each wakeup. It proceeds only when initialization is idle, a successful init has been published, and closing has not begun. A request before init, after failed init, or once closing begins throws IllegalStateException or std::logic_error.
  • Requests after success run concurrently. A throwing request propagates its error, still releases its active slot, and leaves the wrapper ready for later requests.
  • The first close() seals admission and wakes pending init and request callers so they reject without waiting for the initializer to finish. It then waits for the running init and admitted requests to drain. Then it calls the real close exactly once, even if init never succeeded. Concurrent and repeated closes wait for the real close to return or throw, then return without another client call. This is the sole idempotent exception to the terminal rejection rule.
  • A throwing real close still leaves the wrapper terminal; only its executing caller receives that exception. Java close coordination is uninterruptible and preserves an interrupt received before or during its waits, for both the executing caller and waiting closers. Java init and request waits are interruptible; an interrupted waiter reserves no active slot and does not call the client.

isClosing() is a synchronized read-only probe. It is false initially and stays true once closing begins, including after completion; it must not wait for client callbacks to finish.

For example, eight admitted requests may overlap. A ninth arriving after isClosing() becomes true is rejected while close waits for the first eight.

What the tests check

  • Concurrent init calls are exclusive. Failed initialization propagates its error, wakes all waiting requests to reject, and permits a later successful retry.
  • A request made during init waits. Successful init is idempotent even while requests are active.
  • Eight held requests reach the client together. Close seals admission before draining them and never overlaps client initialization or requests.
  • Close wakes existing init and request waiters while the initializer is still held. Both APIs reject during closing and after completion, even if the running initializer later succeeds.
  • Eight competing closers, arriving during request drain and during a held real close, wait for cleanup completion. All wake after success or failure; only the executing caller receives the close error. Cleanup runs once, including when init was never called.
  • A seeded eight-thread run makes exactly 1200 client requests. A throwing request releases its slot, preserves readiness for another request, and cannot strand shutdown.
  • Java init and request waiters respond to interruption without reserving work. Close owners and followers finish draining and preserve interrupts received before or during their waits.
  • Daemon workers and bounded joins in Java, plus bounded completion checks and a process watchdog in C++, turn stalled calls into failures.

Taught in: Readers and writers, three ways

Open them one at a time. Each one gives away a little more.

Separate admission from the slow client call. Which state must be recorded before releasing the wrapper lock?
Track initialization, successful readiness, closing, and the number of admitted requests under one lock.
Set closing before draining. Put active-count decrement in finally or an exception-safe C++ cleanup path.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

How does this model a shared uploader or image manager?
The Apple reports ask about concurrent uploads and downloads. Admit independent operations concurrently after setup, and drain them before disposing shared resources. A cache needs its own consistency policy; lifecycle protection alone does not deduplicate downloads.
Why not just use a read-write lock?
It can protect request lifetimes, but a waiting close must also seal admission. Do not rely on unspecified writer fairness to prevent new requests from extending the drain forever.
Can you reconnect after a failed request?
Make reconnection a new explicit state and generation. Stop admission, drain the old generation, and initialize the replacement exclusively. A request failure alone does not silently reset this contract.
How would a close timeout work?
Use one monotonic deadline and define whether timeout leaves the wrapper closing or rolls back admission. Keeping it closing is simpler; do not dispose resources still in use.
What if close itself throws?
Publish a terminal state and wake other closers in cleanup. Repeating an external close after partial failure may be unsafe, so this contract attempts it once.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea and invariant

The wrapper is an admission gate plus a drain counter. All state changes happen under one mutex. active counts calls that have been admitted but have not completed cleanup. Readiness is published only after successful init; closing never becomes false again. The invariant is that a real close starts only when initialization is idle and active is zero.

Why these primitives

The condition variable lets init waiters and closers sleep without holding the mutex. Each wait checks a predicate because notification is only a reason to inspect state again. Client code runs outside the mutex, which permits requests to overlap and avoids serializing slow external work. Each admitted request has exactly one decrement, even when its callback throws.

The admission increment is the request's lifecycle linearization point. The first assignment to closing is the shutdown boundary. A close racing with init preserves that boundary even if the initializer later publishes success. Waiting closers observe completion, rather than merely observing that somebody started close. Sealing admission wakes pending init and request callers immediately; publishing completion wakes every closer, including after a callback error.

The broken interleaving

The broken implementation decrements active only after a normal return. A request reserves a slot, the client throws, and the slot remains counted. The next close seals admission and waits forever for a request that has already ended. The request-exception test isolates this schedule; the bounded join reports the failure. Separate gated tests hold the real close so a follower cannot mistake closing for completed, and hold init so a missed shutdown notification cannot hide behind initialization finishing.

Cost and pitfalls

Bookkeeping is O(1) per call and O(1) extra state. Waiting time depends on the client, so no wrapper can promise bounded close when a callback never returns. Do not hold the mutex through the request, reset readiness while requests still run, or release a permit before client cleanup has completed.

How to say it in the interview

I will separate admitting a request from executing it. Under one lock I check readiness and reserve an active slot, then call the client outside the lock and release the slot on every exit. Close first seals admission, drains init and active requests, and publishes terminal completion even if the real close throws.
