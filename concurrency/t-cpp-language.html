C++ language questions interviewers ask

Forty spoken questions on C++20 object lifetime, polymorphism, ownership, moves, templates, exceptions, containers and language traps.

1Corecppinheritancevirtual-destructor
When does a base class need a virtual destructor?
Model answer

If callers destroy derived objects through an ordinary owning base pointer, I give the base a public virtual destructor. Otherwise, ordinary deletion through that base pointer has undefined behaviour, even if the derived destructor appears to do nothing. A virtual destructor makes destruction start with the derived object and then proceed through its bases.

If polymorphic deletion is forbidden, a protected nonvirtual destructor can enforce that design. A concrete value class does not need virtual dispatch merely because it owns resources. unique_ptr<Base> with its default deleter still needs the virtual destructor when it owns a derived object.

Likely follow up: "Does shared_ptr change this?" A shared_ptr<Base> converted from make_shared<Derived>() remembers how to destroy Derived. Constructing ownership from an already erased Base* does not recover that information.

2Seniorcppdiamondvirtual-inheritance
Explain the diamond problem and what virtual inheritance fixes.
Model answer

If Left and Right both inherit Root, and Leaf inherits both, ordinary inheritance gives Leaf two separate Root subobjects. Converting Leaf* to Root* is ambiguous, and each branch has its own root state. Making both branches inherit virtual Root gives the complete object one shared virtual base.

Leaf initializes that shared root; the intermediate root initializers are ignored when constructing a Leaf. Virtual inheritance changes object layout and may require pointer adjustments, so I use it only when shared base identity is part of the model. It does not automatically resolve unrelated same-name members or competing overrides.

Likely follow up: "What if both branches override one virtual method?" If the shared base has two competing final overriders, Leaf must supply an unambiguous override. Composition often avoids this complexity.

3Corecppbindingdefault-arguments
What is static versus dynamic binding, and how do default arguments interact with virtual functions?
Model answer

Static binding selects behaviour using compile-time information, including overload resolution and nonvirtual calls. A virtual call uses the object's dynamic type to select the final override, after name lookup and overload resolution have selected the interface. Default arguments still come from the statically selected declaration.

I avoid different default arguments on overrides because readers easily confuse those two decisions. An explicitly qualified call to object.Base::value() suppresses virtual dispatch. A compiler can also devirtualize a call when it proves the target, while preserving the required behaviour.

Likely follow up: "Are virtual calls always indirect?" No. Dynamic dispatch describes the language semantics; the optimizer may emit a direct call or inline the body when the target is known.

4Seniorcppvtableobject-layout
How do vtables work, and what is their cost?
Model answer

A common implementation gives a polymorphic object one or more hidden vtable pointers. These refer to tables associated with its class and base subobjects, containing virtual-call targets and often runtime type information or adjustment metadata. A call loads the appropriate target and may adjust this. The standard specifies the behaviour, not a mandatory vtable layout.

The costs can include object storage for hidden pointers, an indirect branch, instruction-cache effects, and fewer optimization opportunities when the target is unknown. Multiple or virtual inheritance makes layout more complicated. I would not claim every object has exactly one hidden pointer, nor that each object owns a separate table. Constructors and destructors also need dispatch behaviour appropriate to the construction or destruction stage.

Likely follow up: "How would you reduce this overhead?" First measure. Contiguous value storage, templates, or devirtualization can help a hot path, but runtime extensibility may justify the dispatch. Adding nonvirtual methods does not by itself add a pointer to each object.

5Corecppoverloadoverridename-hiding
Distinguish overloading, overriding and name hiding.
Model answer

Overloading gives a name several callable signatures and resolves the choice at compile time. Overriding replaces a base virtual function's implementation with a matching derived declaration, subject to rules including cv qualifiers, ref qualifiers and compatible return types. Name hiding happens when a derived declaration hides base declarations with the same name during lookup, even when their parameter lists differ.

I write override on every intended override so a missing const, for example, becomes a diagnostic instead of a new function. Here using keeps the zero-argument overload visible on a Derived object.

Likely follow up: "Can the return type differ?" Covariant returns allow certain related class pointer or reference types. They do not let an override replace unique_ptr<Base> with unique_ptr<Derived>.

6Seniorcppabstract-classconstruction
Can a pure virtual function have a body, and what happens to virtual calls during construction?
Model answer

A class is abstract when at least one virtual function's final overrider is pure. Implementing every remaining pure operation makes a derived class concrete; the base stays abstract. A pure virtual function can have an out-of-class definition, callable with explicit base qualification. A pure virtual destructor needs a definition when derived objects are destroyed, because base destruction still runs.

During a base constructor or destructor, virtual calls on the object being built or destroyed dispatch within that stage's class hierarchy. They do not reach overrides in a more-derived part that is not yet constructed or is already destroyed. A virtual call to a pure virtual function in that construction or destruction path is undefined behaviour, even if the function has a body. Explicitly qualified nonvirtual calls to a provided body are a different case.

Likely follow up: "How would you run derived initialization safely?" Prefer constructor parameters and composed helpers. If post-construction virtual work is necessary, a factory can construct the complete object before calling it, while handling failure and avoiding premature publication of this.

7Corecppobject-slicingpolymorphism
What is object slicing, and why does a virtual method not prevent it?
Model answer

Slicing happens when a derived object is copied into a base object by value. Only the base subobject initializes the new object; its dynamic type is now the base type. Virtual functions cannot restore the lost derived state. Passing a polymorphic object to a function taking Base by value, or storing derived objects in vector<Base>, is a common trigger.

I use base references for borrowing and suitable smart pointers for polymorphic ownership. If independent copies are required, I design a virtual clone operation returning an owning base pointer, or choose a value representation such as variant. A base assignment through a reference can also overwrite only the base portion of an existing derived object and break its invariant without changing its dynamic type.

Likely follow up: "How do you prevent accidental slicing?" Make an interface abstract and consider restricting its copy operations. Return unique_ptr<Base> from overrides of clone; smart-pointer return types are not covariant.

8Corecpprule-of-zerospecial-members
Explain the rule of three, five and zero, and which one you prefer.
Model answer

The rule of three says that a class managing a resource directly usually needs coordinated destruction, copy construction and copy assignment. Memberwise copying an owning raw pointer would duplicate the address without duplicating ownership correctly. The rule of five adds move construction and move assignment so ownership can transfer efficiently.

My default is the rule of zero: put ownership into members such as vector, string and unique_ptr, and let their operations compose. A class containing a unique_ptr naturally becomes noncopyable and may be movable without custom special members. These are design rules, not instructions to write five functions in every class. If copying has no sensible meaning, delete it; if a custom invariant spans members, defaulted moves may need review.

Likely follow up: "Why can adding only a destructor change performance?" A user-declared destructor, including one declared = default, suppresses implicit move generation. An apparent move can then copy instead, or fail for a move-only member.

9Seniorcppimplicit-membersdeleted-functions
Which special member functions does the compiler generate, and when are they deleted or suppressed?
Model answer

For an ordinary class, the compiler can declare a default constructor, destructor, copy constructor, copy assignment, move constructor and move assignment. Any user-declared constructor prevents an implicit default constructor. Copy operations are normally declared if absent, but declaring either move operation causes both implicitly declared copy operations to be deleted.

The implicit move rules require no user-declared copy operations, move operations or destructor. Generated operations can still be deleted because a required base or member operation is unavailable. Reference members and const scalar members prevent default assignment, while a mutex prevents copying and moving. Declared does not mean usable.

= default requests the language-defined implementation and = delete forbids an operation. An explicitly deleted move can win overload resolution and reject an rvalue; an absent move may allow copying. A defaulted move defined as deleted is ignored by overload resolution.

Likely follow up: "Does is_move_constructible_v<T> prove a move constructor exists?" No. It tests construction from an rvalue, which can succeed through a copy constructor accepting const T&.

10Corecppvalue-categoriesreferences
Explain lvalues, prvalues and xvalues without saying merely left and right of assignment.
Model answer

Value categories classify expressions. An lvalue identifies an object or function with identity; a prvalue computes a value or initializes an object; an xvalue identifies an object whose resources may be reused. Lvalues and xvalues are glvalues, and prvalues and xvalues are rvalues. These are separate from an expression's type and from whether its object is const.

A nonconst lvalue reference normally binds to an lvalue; an rvalue reference binds to an rvalue. A const lvalue reference can bind to either. A named variable expression is an lvalue, even when the variable's declared type is an rvalue reference.

Likely follow up: "Why does a move constructor use std::move on its parameter's members?" The named parameter is an lvalue, so its members would otherwise be offered as lvalues too.

11Corecppmove-semanticsconst
Does std::move actually move anything, and why can moving a const object copy?
Model answer

std::move is a cast that permits move-aware overload resolution. It does not transfer bytes, clear the source or invoke a move constructor itself. The selected constructor or assignment operator performs whatever transfer the type defines. A move of a scalar is effectively a copy, and a class without a viable move operation may copy.

Moving a const string produces a const rvalue reference. The usual move constructor takes a nonconst rvalue reference because it needs to modify the source. That overload cannot accept the const object, so the copy constructor accepting a const reference can be selected instead. Casting away const to force a move is not a sound ownership design.

Likely follow up: "When would you write it?" When I have finished using a named object and deliberately transfer its value or ownership, for example into a container. I avoid adding it to a returned local because that can prevent named return value optimization.

12Seniorcppmoved-frommove-assignment
What can you assume after a move, and what makes a correct move assignment?
Model answer

For standard-library types, unless documented otherwise, a moved-from object is valid but its value is unspecified. Its invariants hold, and operations whose preconditions are satisfied remain usable. I can destroy or assign it, but I cannot assume a moved-from vector is empty or call front without checking. Some types promise more: moving a unique_ptr transfers its pointer and leaves the source empty.

For my own types I define the moved-from contract. Move construction creates a new object; move assignment must also release the destination's previous resource. Both must preserve invariants and avoid double ownership. Defaulted moves operate member by member, so a moved buffer and an unchanged cached size can violate a class invariant. I also handle self-move assignment without corrupting the object and make moves nonthrowing when that is truthful.

Likely follow up: "Must a move be constant time?" No. Inline storage, allocator constraints or elementwise work can make it linear. Move semantics permit transfer; they do not promise a complexity.

13Seniorcpprvocopy-elision
What is guaranteed copy elision, how is NRVO different, and should you return std::move(local)?
Model answer

Since C++17, initializing an object from a same-type prvalue constructs directly in the destination in the relevant cases. There is no intermediate object to copy or move. Returning a same-type temporary therefore works even when both copy and move constructors are deleted, provided required destruction is accessible.

Returning a named local of the return type is NRVO, an optional optimization. If it is not applied, C++20's implicit-move rules normally let an eligible local move, or copy when appropriate. The required fallback must be well-formed even if a compiler performs NRVO. return std::move(local) prevents NRVO by changing the return expression.

Likely follow up: "Can I count on a particular constructor log?" Not for optional elision. I test semantics independently of whether NRVO occurs and distinguish it from the C++17 mandatory prvalue rules.

14Seniorcppforwarding-referencetemplates
What is a forwarding reference, and when do you use std::forward instead of std::move?
Model answer

A forwarding reference is an rvalue reference to a cv-unqualified template parameter deduced for that call, such as a function template parameter T&&. With an lvalue argument, deduction makes T a reference; collapsing produces an lvalue reference. With an rvalue, it produces an rvalue reference. Ordinary Widget&&, const T&&, and T&& where T was fixed by the enclosing class template are not forwarding references.

Inside the function the named parameter is an lvalue. std::forward<T> restores the caller's category; std::move would offer even an original lvalue for consumption. Reference collapsing yields an lvalue reference whenever either layer is an lvalue reference. Only two rvalue-reference layers collapse to an rvalue reference.

Likely follow up: "Is the returned reference always safe?" No. This identity helper does not extend lifetime. Saving its result from a temporary can leave a dangling reference, so forwarding is safest when passing directly to the next operation.

15Corecppunique-ptrshared-ptrownership
How do you choose between a value, a raw pointer, unique_ptr, shared_ptr and weak_ptr?
Model answer

I start with a value when ownership fits naturally inside an object or scope. A reference or raw pointer can express borrowing; the pointer also permits absence. Neither normally owns or extends lifetime. I use unique_ptr for exclusive dynamic ownership because it makes transfer explicit and has no shared reference count.

I use shared_ptr when several independent owners genuinely need to keep an object alive. Its control block tracks ownership and introduces storage and reference-count work. A weak_ptr observes that ownership without keeping the object alive; lock obtains a temporary strong owner or returns empty. I prefer make_unique and make_shared for construction. make_shared typically combines object and control-block allocation, although weak observers can keep that allocation reserved after object destruction.

Likely follow up: "What parameter type would a read-only helper take?" Usually const T&, or const T* when absence is meaningful. Taking shared_ptr<T> by value communicates that the helper participates in ownership.

16Seniorcppweak-ptrreference-cycles
Why do shared-pointer cycles leak, and how does enable_shared_from_this help safely?
Model answer

Reference counting cannot reclaim an unreachable cycle when each object still has a strong owner inside the cycle. I choose an ownership direction and make back-references weak. A parent can own children strongly while each child observes its parent through weak_ptr.

enable_shared_from_this needs public, unambiguous inheritance and established shared ownership to reuse the existing control block. Constructing an independent shared_ptr from this risks double destruction. shared_from_this in the constructor is too early and throws bad_weak_ptr. C++17 weak_from_this returns an empty weak pointer there; that saved copy does not later acquire ownership information.

Likely follow up: "Should I check expired before using the object?" No separate check guarantees continued lifetime. Call lock once and retain the returned owner. This example also assumes a tree discipline; it does not itself reject self-links or arbitrary graph cycles.

17Seniorcppshared-ptrthread-safety
Does a shared_ptr make its object thread-safe?
Model answer

No. I separate the control block, each smart-pointer variable, and the pointee. Different shared_ptr objects sharing one control block can be copied, reset and destroyed concurrently while managing ownership safely. That does not protect simultaneous mutation of the pointee, nor does it make unsynchronized reading and assignment of the same smart-pointer variable safe.

I protect the pointee's invariant with its own synchronization or make it immutable. To replace a shared pointer while readers acquire ownership, I use a mutex or, with supporting C++20 libraries, atomic<shared_ptr<T>>. That specialization is not guaranteed lock-free. The C++17 alternative is a mutex or the shared-pointer atomic free functions, which are deprecated in C++20. Reference counting answers lifetime, not data consistency.

Likely follow up: "Does use_count() == 1 let me modify without a lock?" Not as a concurrent protocol. It is an observation, not exclusive access; another thread may acquire ownership through a weak pointer, and raw borrowers may exist.

18Corecppraiiresource-lifetime
Explain RAII using something other than memory allocation.
Model answer

RAII makes a resource's lifetime follow an owning object's lifetime. Successful construction establishes ownership; destruction releases it. A named lock_guard acquires a mutex on construction and releases it when its scope ends, including when an exception unwinds that scope. The same pattern works for files, sockets and transactions with suitable cleanup semantics.

Ownership must be established before later work can fail. RAII members then clean up partial construction automatically. A temporary guard destroyed at the end of its statement protects no later work. RAII also depends on destruction actually happening; forced termination and std::_Exit do not unwind automatic objects.

Likely follow up: "Does RAII prevent deadlock?" It prevents forgotten releases on ordinary exits. It does not choose a safe lock order, eliminate cycles, or make blocking cleanup bounded.

19Corecppconstmutable
What does const correctness promise, and when is mutable justified?
Model answer

Const correctness expresses which operations may modify an object through a particular interface. const T* points to a const-qualified T; T* const is a fixed pointer whose pointee can remain mutable. A const member function cannot normally modify non-mutable members through this, and it can overload a nonconst member function.

Const is not automatically deep immutability or thread safety. A pointer member can still refer to mutable external state, and a const smart pointer need not have a const pointee. mutable is useful for implementation details such as a mutex used by a logically const reader or a synchronized cache. It does not provide synchronization itself. Casting away const and modifying an object originally defined as const is undefined behaviour.

Likely follow up: "Why might const unique_ptr<T> surprise me?" It prevents changing that owner through the const handle, but still permits modifying T. Use ownership of const T when the pointee should be read-only through that handle.

20Corecppcastsrtti
When would you use each of the four named C++ casts?
Model answer

static_cast performs specified compile-time conversions, including numeric conversions and suitable inheritance conversions. A base-to-derived cast does not check the dynamic type, so its preconditions must hold. dynamic_cast performs runtime-checked downcasts and cross-casts in polymorphic hierarchies; a failed pointer cast returns null and a failed reference cast throws bad_cast.

const_cast changes cv qualification. It is appropriate only when subsequent use is valid; modifying an originally const object remains undefined. reinterpret_cast handles low-level representation-related pointer or integer conversions, but does not grant permission to access an object through an unrelated type. Alignment, lifetime and aliasing rules still apply. For representation conversion between suitable equal-size trivially copyable types, C++20 provides bit_cast; C++17 code can use carefully constrained memcpy.

Likely follow up: "Why avoid C-style casts?" They can silently choose powerful combinations of these conversions, hiding intent and making review harder. I prefer the narrowest named cast and first ask whether the conversion should exist at all.

21Seniorcppinlineodr
What does inline mean today, and how does it relate to the one definition rule?
Model answer

inline primarily affects definition rules. In the usual header-based model, an external-linkage inline function can be defined in several translation units while denoting one entity, provided the one definition rule's requirements hold. Those include matching token sequences and consistent name lookup, subject to the standard's exceptions. C++17 inline variables similarly support header definitions of shared variables.

It does not require call-site substitution. Compilers can inline an unmarked function or emit a call to an inline function. Functions defined inside a class are normally implicitly inline; C++20 named modules introduce qualifications to that rule. constexpr functions are implicitly inline too. Inconsistent definitions caused by macros can violate the one definition rule even if the linker accepts them.

Likely follow up: "Does a local static inside an external-linkage inline function appear once per source file?" No, it is shared across the function's definitions. A namespace-scope static header variable instead creates a separate object in each translation unit.

22Corecppstaticexternlinkage
Explain the different meanings of static and what extern does.
Model answer

At namespace scope, static gives a variable or function internal linkage, so the name denotes a translation-unit-local entity. A function-local static has static storage duration and, when dynamic initialization is needed, initializes on first passage through its declaration. Since C++11, concurrent callers coordinate that initialization, but subsequent access still needs synchronization. Failed initialization is retried on a later call; recursive re-entry during initialization is undefined behaviour.

A static data member belongs to the class rather than each instance. A static member function has no this pointer. extern commonly declares an external-linkage variable whose definition appears elsewhere; a declaration with an initializer is a definition even with extern. Storage duration, scope and linkage are different questions. Ordinary namespace-scope const variables also have internal linkage by default, with exceptions such as explicit external linkage and inline variables.

Likely follow up: "How do you avoid static initialization order problems across source files?" Prefer constant initialization or a function-local static accessor. I still consider destruction order and dependencies; deferred initialization does not solve every shutdown problem.

23Seniorcpptemplatespolymorphism
When would you choose templates over virtual functions, and can a function template be virtual?
Model answer

Templates provide compile-time polymorphism: the concrete types determine instantiated code, often allowing inlining and specialization without a shared base class. They suit algorithms over known types, but can increase compile time and generated code size, and their definitions usually need to be available where instantiated.

Virtual interfaces provide runtime polymorphism through a common contract. They suit heterogeneous objects and runtime-selected implementations, with indirection and ownership choices to manage. A member function template cannot be virtual, but a class template can contain ordinary virtual member functions. C++20 concepts constrain template requirements and improve diagnostics; in C++17 I can document requirements and use traits, static assertions or SFINAE where needed.

Likely follow up: "Is there a middle ground?" Type erasure such as std::function offers a runtime interface without requiring callers to inherit from my base. It can still involve indirect calls and allocation, so I choose it for the interface and measure the cost.

24Seniorcppconstructorexception-safety
What happens if a constructor throws, and in what order are bases and members initialized?
Model answer

For an ordinary nondelegating constructor that throws, the complete object's destructor does not run because construction never completed. Fully constructed bases and members are destroyed in reverse construction order. Resources already stored in RAII members are therefore cleaned up. A resource held only in an unmanaged handle can leak unless its ownership was established before the failure.

The initialization order is virtual bases first for the most-derived object, following depth-first, left-to-right base traversal, then direct bases in declaration order, then members in declaration order, then the constructor body. Reordering the member initializer list does not change it. I declare dependencies before members that use them and avoid publishing this during construction.

Likely follow up: "Can a constructor function-try-block recover?" It can translate or log an exception, but cannot repair failed initialization or access already destroyed bases or members. A delegating constructor is a special case: if its target completed before the delegating body throws, the object's destructor is invoked.

25Seniorcppdestructorexceptionsterminate
Why should destructors not throw, and is every destructor implicitly noexcept?
Model answer

A destructor should release resources reliably without propagating failure. Destructors without an explicit exception specification are normally nonthrowing, but a potentially throwing base or member destructor can make that specification potentially throwing. An exception escaping a noexcept destructor calls std::terminate.

Even an explicitly potentially throwing destructor cannot safely propagate an exception while it is being run as cleanup for another exception: that situation terminates the program. I put reportable failure into an explicit operation such as close or commit, where the caller can handle it, and keep destructor cleanup nonthrowing. Cleanup may catch a local failure, provided the fallback is itself safe. Nonthrowing cleanup is part of the type's contract.

Likely follow up: "Is throwing anywhere inside a destructor forbidden?" No. A locally thrown exception that is caught inside the destructor can be fine. The issue is whether it escapes, the destructor's exception specification, and whether another exception is already unwinding.

26Seniorcppnoexceptvectormoves
Why can adding noexcept to a move constructor change vector performance?
Model answer

When a vector reallocates, it must construct existing elements in new storage. A throwing move could modify some old elements and then fail, making rollback impossible. If copying is available and moving may throw, implementations commonly copy to preserve the required exception guarantee. A truthful nonthrowing move enables safe relocation by moving.

std::move_if_noexcept captures that choice: it offers a const reference when copying is available and move construction might throw, otherwise an rvalue reference. For single-element insertion at the end, the C++20 vector guarantee has an exception when a noncopyable element's throwing move fails; the effects can be unspecified. Not every reallocation promises rollback for every type.

Likely follow up: "Should I simply mark every move noexcept?" No. If an exception escapes, the program terminates. I promise it only when all required work supports it. Moves defaulted on their first declaration infer their exception specification unless explicitly specified; defaulting a previously declared move out of class does not automatically make it nonthrowing.

27Seniorcppexception-guaranteescopy-and-swap
What are the exception safety guarantees, and how does copy-and-swap provide the strong guarantee?
Model answer

The basic guarantee preserves invariants and avoids leaks if an operation fails, although values may change. The strong guarantee leaves the observable state unchanged on failure. A nonthrowing guarantee means the operation does not propagate exceptions. I name which guarantee an API provides and what state it covers.

Copy-and-swap prepares a replacement first. If copying throws, the destination is untouched; if preparation succeeds, a nonthrowing swap commits the replacement and the temporary cleans up the old value. Fallible preparation followed by nonthrowing commit is the general pattern. RAII handles cleanup, but RAII alone does not roll back every logical update. Swap must actually be valid and nonthrowing for the types and allocator situation involved.

Likely follow up: "Why not use copy-and-swap everywhere?" It can allocate unnecessarily and prevent reuse of destination capacity. I use it when the simplicity and guarantee justify the cost; external effects such as network writes may need a separate transactional design.

28Corecppundefined-behavioursanitizers
Give several examples of undefined behaviour, and distinguish it from unspecified and implementation-defined behaviour.
Model answer

Undefined behaviour means the standard imposes no requirements on that execution. Examples include signed integer overflow, dereferencing a dangling pointer, accessing beyond an array, ordinary deletion through an unsuitable nonvirtual base pointer, and a data race. Reading an indeterminate ordinary int is another C++20 trap. The compiler may optimize on the assumption that these cases never happen; I cannot promise merely a garbage result.

Unspecified behaviour permits several allowed outcomes without requiring one documented choice, such as which function argument is evaluated first. Implementation-defined behaviour requires the implementation to document its choice, such as whether plain char is signed. Unsigned arithmetic wraps modulo its range; signed arithmetic does not gain that guarantee.

Likely follow up: "How would you find these bugs?" Warnings, static analysis, bounds-aware design and targeted tests, plus AddressSanitizer, UndefinedBehaviorSanitizer and ThreadSanitizer for different classes of bugs. A clean sanitizer run is evidence for exercised paths, not proof of defined behaviour everywhere.

29Corecppallocationobject-lifetime
What is the difference between new and malloc, including constructor failure?
Model answer

A new-expression obtains suitable storage and initializes an object, returning a typed pointer. Throwing allocation reports failure with bad_alloc; the nothrow allocation form returns null, but constructors can still throw. If construction throws after allocation, the corresponding deallocation function is normally called. The allocation function operator new itself does not construct the object.

malloc allocates a requested number of bytes, returns void* or null, and does not run constructors. Its alignment guarantee does not cover over-aligned types. C++20's implicit-lifetime rules permit some objects to be created there, but do not make malloc construct a string. free does not run destructors. Allocation and deallocation families must match; array and scalar new-expressions also have distinct matching deletion forms.

Likely follow up: "What is placement new?" It constructs an object in supplied storage without allocating that storage; alignment, lifetime and cleanup are the caller's responsibility. In ordinary application code I prefer containers and smart-pointer factories, reserving manual storage work for carefully designed low-level components.

30Corecppstructclassaggregates
What is the difference between struct and class in C++?
Model answer

The language differences are default access: a struct has public members and public base inheritance by default, while a class defaults to private for both. Both can have constructors, destructors, access control, templates, virtual functions and static members. Neither keyword determines stack versus dynamic allocation, copying cost or thread safety.

I usually use a struct for a simple value whose members can vary independently, and a class when methods protect an invariant. That is a convention, not a language restriction. A struct is not automatically an aggregate; aggregate eligibility depends on features such as constructors, access control, bases and virtual functions. In C++20 a user-declared constructor, including an explicitly defaulted one, prevents aggregate status.

Likely follow up: "Does changing struct to class change layout?" The keyword alone does not demand a different representation. Changed effective access can affect properties such as aggregate or standard-layout eligibility, so I check the complete declaration rather than assuming equivalence.

31Corecppvectoremplace-backpush-back
Is emplace_back always better than push_back?
Model answer

push_back inserts from an existing element value, copying an lvalue or moving a suitable rvalue. emplace_back forwards constructor arguments to construct the new element in container storage. It can avoid a temporary when I have constructor arguments rather than an element, but it does not eliminate reallocation or relocation of existing elements.

Emplacement can call explicit constructors, which is useful but can make a surprising overload choice easier. Passing an already constructed temporary to emplacement often offers no advantage over moving it with push_back. I choose the form that expresses what I already have.

Likely follow up: "What about emplacing an owning raw pointer?" Do not leave ownership unprotected while allocation can fail. Construct a smart pointer with its factory first, then insert or move that owner.

32Seniorcppiteratorsinvalidationcontainers
Which iterator invalidation rules must you know for vector, list, map and unordered_map?
Model answer

For vector, reallocation invalidates every element pointer, reference and iterator. Without reallocation, insertion invalidates positions at or after insertion, including the old end iterator; erasure invalidates positions at or after the erased position. Appending without reallocation preserves references to existing elements. reserve can itself invalidate them if it changes capacity.

List and ordered associative-container insertion preserve existing iterators and references, and erasure invalidates those to erased elements. Unordered-container rehash invalidates iterators, but preserves pointers and references to existing elements. An insertion may trigger that rehash; erasure invalidates only handles to erased elements. Iterator validity and reference validity are not interchangeable.

Likely follow up: "Is this vector loop efficient?" It is correct but can be quadratic because each erase shifts elements. C++20 std::erase_if is simpler and linear here; in C++17 use the erase-remove idiom. Neither approach supplies synchronization for concurrent access.

33Corecppinitializationmost-vexing-parse
What is the most vexing parse, and do braces always mean the same thing as parentheses?
Model answer

When a construct can be parsed as a declaration, C++ can choose that interpretation even when I intended an object. Widget object(); declares a function, and Widget object(Factory()); can declare a function whose parameter is a function pointer. Braces often make the object-construction intent unambiguous.

counts has three elements equal to seven; entries has two elements, three and seven. List initialization favours initializer-list constructors in its overload rules and rejects narrowing conversions. Replacing every parenthesis with braces mechanically can therefore change meaning. Empty braces also follow their own initialization rules rather than universally forcing an initializer-list overload.

Likely follow up: "How do you prevent accidental implicit conversion through a constructor?" Mark constructors explicit when conversion is not intended. Direct initialization can still call them; ordinary copy initialization cannot use them implicitly.

34Seniorcppautodecltypededuction
How do auto, decltype and decltype(auto) differ?
Model answer

By-value auto drops references and top-level const, often copying. auto& preserves reference binding and the referred object's const; auto&& can be a forwarding reference. decltype does not evaluate its operand. An unparenthesized ordinary variable name or member access gives the declared type. Otherwise, for an expression of type T, an lvalue gives T&, an xvalue T&&, and a prvalue T.

decltype(auto) applies those exact decltype rules to its initializer or return expression. It can preserve references usefully, but an extra pair of parentheses can create a dangling return reference if the expression names a local variable.

Likely follow up: "Why did my range loop stop updating the container?" A loop variable declared with plain auto copies ordinary elements. Use auto& to modify them or const auto& to borrow them read-only, accounting for proxy containers such as vector<bool>.

35Seniorcpplifetimestring-viewspan
When does a reference extend a temporary's lifetime, and do string_view or span extend it?
Model answer

Binding a temporary directly to a local const lvalue reference or rvalue reference can extend its lifetime: const std::string& text = std::string{"ok"}; keeps that string alive for text's scope. However, lifetime extension is not transitive. A temporary bound to a function's reference parameter survives only the full expression containing the call; returning that reference does not extend it further. Returning a reference to a freshly created temporary also leaves it dangling.

string_view and C++20 span are non-owning views. They do not extend the lifetime of the underlying characters or elements. Returning a view into a local string leaves it dangling, and modifying the original container can invalidate a view through reallocation. The owner must outlive every use of the view. A string view also need not end at a null terminator, so its data pointer is not automatically a C string.

Likely follow up: "What do you return from a function that creates text?" An owning string, usually by value. I return a view only when the backing lifetime is explicit. In C++17, use an established span library or a carefully documented pointer-and-length interface.

36Seniorcpplambdacaptureslifetime
What does a lambda capture, and what changes when the lambda runs later on another thread?
Model answer

A lambda expression creates a closure object. Value captures generally store captured values inside that object; reference captures borrow the original objects and do not extend their lifetimes. Capturing this stores the pointer, so the enclosing object must survive the call. C++17 [*this] captures a copy instead, with that class's copy semantics.

Asynchronous execution makes every borrowed lifetime a contract. Value capture of a pointer still borrows its pointee. A mutable lambda permits modifying its captured values through its call operator; it does not make concurrent calls safe.

Likely follow up: "Can this job go into C++20 std::function<int()>?" No, the unique ownership makes the closure noncopyable, while that wrapper requires a copyable target. A suitable move-only task wrapper or packaged_task can preserve the ownership.

37Seniorcppconstexprconstevalconstinit
How do const, constexpr, consteval and constinit differ?
Model answer

const restricts modification through an interface but does not require compile-time initialization. A constexpr variable is const and requires a constant-expression initializer. A constexpr function is eligible for constant evaluation when the context and inputs permit it; it can also run at runtime.

C++20 consteval declares an immediate function whose immediate invocations must produce constant expressions. C++20 constinit requires static initialization, meaning zero or constant initialization, of a variable with static or thread storage duration. It rejects dynamic initialization. constinit does not make the variable const.

Likely follow up: "What is the C++17 fallback?" Use constexpr values and constant-expression contexts such as static_assert to require compile-time evaluation where possible. There is no direct equivalent enforcing constinit for a mutable variable. None of these keywords makes concurrent increments of requests safe.

38Seniorcppsizeofalignmentobject-representation
Why can sizeof exceed the sum of member sizes, and when is byte copying an object valid?
Model answer

Members have alignment requirements, so an implementation may insert padding between members and at the end. Tail padding lets consecutive array elements satisfy alignment. alignof reports the type's alignment and sizeof includes its object representation, not dynamically owned allocations. Even an empty complete class object has nonzero size, though empty bases and C++20 [[no_unique_address]] members can use special storage rules.

For two distinct complete objects of the same trivially copyable type, copying all sizeof(T) bytes with memcpy preserves the source value in the writable destination. This guarantee excludes potentially overlapping subobjects such as bases. That is not a general serialization format. Padding, byte order, pointer values and ABI differences matter. Byte-copying a string or an owning smart pointer can corrupt ownership.

Likely follow up: "Can I compare structs with memcmp?" Not generally. Equal logical values can have different padding bytes or representations. Define value comparison over the meaningful members and use an explicit portable format for persistence or transport.

39Corecppoperator-overloadingconversions
What can operator overloading change, and what should an overloaded operator preserve?
Model answer

Operator overloading defines behaviour for expressions involving class or enumeration types. It cannot create new operator symbols, change precedence or associativity, or change an operator's required number of operands. I use it when the operation retains a familiar meaning, such as value equality, arithmetic on a numeric type or dereferencing an owning handle.

For symmetric binary operations, a nonmember function can permit conversions on either operand; a hidden friend is often useful. Assignment normally returns a reference to the destination so chaining behaves conventionally. Overloaded logical operators do not short-circuit, so overloading && or || easily surprises callers. In C++20, defaulted comparisons and the three-way comparison operator can reduce repetitive memberwise code, but ordering semantics still need thought.

Likely follow up: "Why make a conversion to bool explicit?" It allows intentional truth tests, including conditions, while avoiding many accidental arithmetic or unrelated implicit conversions. I design conversions around meaningful usage rather than convenience alone.

40Seniorcppevaluation-ordersequencing
Does C++ evaluate function arguments left to right, and how do you distinguish unspecified order from undefined behaviour?
Model answer

No. Since C++17, separate parameter initializations are indeterminately sequenced: one completes before another, but the language does not specify which comes first. That prevents their evaluations from interleaving, while leaving the order open. The function-call rules do not impose left-to-right argument order.

This produces either pair order. In contrast, unsequenced conflicting scalar modifications can still be undefined; two postfix increments of the same integer as operands of built-in addition are a classic case. Braced initializer clauses are evaluated in order, and built-in logical operators provide sequencing and short-circuiting.

Likely follow up: "How would you make an API call's order obvious?" Evaluate dependent operations in separate statements, then pass the results. Associativity describes grouping, not general execution order.
