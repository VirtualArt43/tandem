Races and atomicity

Lost updates, check-then-act, data races versus race conditions, and how to find shared state.

1Coreracesatomicity
What is the difference between a race condition and a data race?
Model answer

A data race is a precise, low level thing: two threads access the same memory location, at least one access writes, and happens-before does not order them. In C++ at least one must be non-atomic; atomic accesses, including relaxed ones, do not themselves create data races. A race condition is a higher level bug: correctness depends on the relative timing of operations, rather than on an enforced protocol. They overlap but are not the same. You can have a race condition with no data race, for example two threads doing check-then-act through individually synchronized methods, where each call is safe but the sequence is not. And you can have a data race that happens not to change the output this time. In C++ a data race is undefined behavior; in Java it is allowed but gives weak guarantees.

Two concrete examples: two threads both writing true to a plain bool flag may appear harmless in a test, yet in C++ the data race makes even the output unconstrained. And if (!map.containsKey(k)) map.put(k, v) on a ConcurrentHashMap has no data race at all, yet two threads can both insert: a race condition.

Likely follow up: "Which tool finds which?" ThreadSanitizer finds data races, because it watches for unordered conflicting memory accesses; it cannot see a race condition built from properly synchronized calls. Those you find by reasoning about invariants and with stress tests.

2CoreracesGoogle
Why is count++ not thread-safe, and what are your options to fix it?
Model answer

It is a read-modify-write: read the value, add one, write it back. Two threads can read the same value and one write erases the other, so updates are lost. Options, from my first choice down: avoid sharing (per-thread counts merged at the end); an atomic increment (AtomicInteger.incrementAndGet, std::atomic::fetch_add), or LongAdder for a hot counter; or a lock around the whole read-modify-write when it must stay consistent with other state. Java volatile gives visibility but not atomicity of the increment. C++ volatile provides neither inter-thread synchronization nor an atomic increment; a raced plain C++ counter has undefined behavior.

Likely follow up: "Sixty four threads hammer the counter and it is slow. Why?" Every increment fights for one cache line. LongAdder (or, in C++, an array of padded per-thread counters summed on read) spreads the writes, at the cost of a read that is not an atomic snapshot. C++ cells read during updates must themselves be atomic, or readers must wait for all writers to finish.

3Coreracescheck-then-act
What is check-then-act, and how can two thread-safe calls form an unsafe sequence?
Model answer

check then act means deciding based on an observation and then acting as if the observation were still true: if (!visited.contains(url)) visited.add(url), if (seat.isFree()) seat.book(), if (instance == null) instance = new X(). Each call may be perfectly atomic, but between them another thread can change the state, so the decision is stale. Two crawler threads both see a URL as unvisited and both fetch it; two users both book the same seat.

The fix is to make the check and the act one atomic operation: use an API that does both (add returning a boolean, putIfAbsent, computeIfAbsent, compareAndSet, a conditional SQL UPDATE), or hold one lock across both steps that every writer also uses.

Likely follow up: "So is a ConcurrentHashMap enough?" Only for the map operation. The frontier must also be thread-safe. If enqueue can fail after marking visited, you need retry or rollback so the URL is not silently lost; these two structures are not one transaction.

4Corecritical-sectionshared-stateApple
Given a class, how do you decide which parts are critical sections?
Model answer
  1. List the shared mutable state: fields of objects reachable from more than one thread, statics, captured variables, and objects stored inside shared collections. Unescaped locals and objects confined to one thread are not shared; C++ locals can become shared through escaped references.
  2. Write down the invariants that tie variables together: "the map and the list hold the same keys", "the elevator's current floor is between min and max", "requests in the window never exceed the limit".
  3. Choose one synchronization protocol for the invariant. With a lock-based design, every participating read and write, including decision-making reads, belongs to a critical section guarded by that lock.
  4. Shrink it: compute outside, mutate inside; no I/O and no calls to unknown code while holding the lock.

Apple has asked this about an elevator and a hit counter. A good answer sounds like:

addRequest and step both touch the request queue and the current floor, so they share one lock. The hit counter's increment and its eviction of old timestamps share another. The display method only reads, but it reads two fields, so it takes the lock too.

Likely follow up: "Is a getter a critical section?" Yes, if another thread writes what it returns: without the lock it can be stale in Java and is a data race in C++. If it returns two related fields, both must be read under the same lock to be consistent.

5Coreinvariantsatomicity
Why does replacing each field with an atomic not make a class thread-safe?
Model answer

Atomics protect one variable; invariants often span several. Take a range with lower and upper and the invariant lower <= upper, both held in AtomicIntegers. Starting at (0, 10), setLower(5) and setUpper(4) run at once: each checks the other field's current value, both checks pass, and the range ends up as 5 to 4. Every single operation was atomic; the pair was not. Likewise a cache with atomic hits and atomic requests can be read with more hits than requests.

Two fixes: one lock that guards both fields, or put both fields into one immutable object and swap it with a single compareAndSet. Every setter must follow that protocol, and a reader takes one snapshot reference for both bounds.

I identify the invariant first; the scope of the lock (or of the atomic swap) is the scope of the invariant.

Likely follow up: "Which is faster, the lock or the swap?" It depends on contention; the lock is simpler, and under heavy contention the retry loop wastes work, so I would start with the lock.

6Coreatomicityvisibilityordering
What are atomicity, visibility and ordering, and why do you need all three?
Model answer

They are three separate guarantees shared data can need:

  • Atomicity: an operation appears to happen all at once. No thread sees half of it or slips in between its steps (count += 1, check-then-act, updating two fields together).
  • Visibility: once a thread writes, other threads are guaranteed to see the new value at a defined point, instead of a stale value kept in a register or never reloaded.
  • Ordering: other threads observe your writes in the order you meant, for example the data written before the ready flag is visible whenever the flag is.

Tools cover different subsets:

  • Java volatile: atomic individual accesses and ordering through the volatile variable. C++ atomic loads and stores: atomic individual accesses, but ordering depends on the selected memory order; relaxed operations do not publish unrelated state.
  • Atomic read-modify-writes (incrementAndGet, fetch_add, compare-and-swap): add atomicity, for one variable.
  • A lock: all three, for everything inside the critical section, provided every access uses the same lock.

The classic bugs map onto them: a lost update is missing atomicity, a thread spinning forever on a flag is missing visibility, and seeing ready == true with stale data is missing ordering.

Likely follow up: "Which one does volatile not give you?" Atomicity of compound operations in Java. C++ volatile is not a thread-synchronization primitive at all.

7SeniorracesmapsGoogle
Many threads increment a per-user counter in a map. How do you make it correct, and what exactly does your version guarantee?
Model answer

The broken version is map.put(user, map.get(user) + 1): the get and put pair loses updates, and on a plain HashMap concurrent puts can also corrupt the table itself.

Then state the guarantees explicitly, because a Google L5 report shows that naming tools is not enough:

  • With no removal, replacement or reset, successful increments accumulate in one counter per user. Handle overflow according to the application contract.
  • LongAdder.sum() is not a linearizable snapshot during concurrent updates. After writers finish with proper synchronization, it gives the exact accumulated sum. For an exact atomic per-user update and read, use merge with Long values or a stable AtomicLong entry.
  • C++ reads must use the same mutex. Then each update and read is linearizable; ensure a plain signed counter cannot overflow.
  • There is no coordinated snapshot across users: traversal and per-user reads do not observe all entries at one common instant. LongAdder.sum() also lacks a snapshot guarantee.

A consistent cross-user snapshot needs a shared protocol, such as one lock used by all updates and the snapshot read; a separate atomic total alone does not make map-plus-total reads consistent.

Likely follow up: "The single C++ mutex is a bottleneck. Now what?" Shard by hash(user) % N, with one mutex and one map per shard.

8SeniorraceslocksLinkedIn
The interviewer says: "For every lock you add, give me the race it prevents." How do you answer?
Model answer

For each lock, state three things: the variables it guards, the invariant over them, and a concrete interleaving that breaks the invariant without it. Consider a cache holding the best N entries:

  • The cache lock guards the map and the size check together. Without it: the cache holds N minus 1 entries; thread A checks the size, sees room, and inserts; thread B checks before A's insert lands, also sees room, and inserts. The cache now holds N plus 1, and nothing evicts the extra.
  • The same lock guards the map and the ranking structure. Without it, an eviction can remove a key from the ranking while a concurrent put re-adds it to the map, leaving an entry that can never be evicted.
  • get can skip that lock only if it reads one key from a ConcurrentHashMap, does not alter rankings, and returns a safely published value whose own mutation is controlled. A C++ unordered_map read concurrent with modification still needs synchronization.

If you cannot name the invariant or publication edge, investigate before removing the lock. Over-locking is a negative signal; an Uber interviewer has complained about candidates who "put synchronization everywhere".

This lock guards the map and the ranking as one invariant. Without it, two puts can both see room and leave the cache over capacity.

Likely follow up: "What does your lock not protect?" Name it: two concurrent misses may both load the same value from the backend, which is acceptable here or fixed with single-flight.

9Coreatomicityjavacpp
Are reads and writes of a long or of a reference atomic?
Model answer

Java: reads and writes of references and of every primitive except long and double are always atomic. For non-volatile long and double, the language specification allows a write to be split into two 32 bit halves, so a reader can see a torn read: the top half of one write and the bottom half of another. 64 bit JVMs do atomic 64 bit accesses in practice, but do not rely on that as a language guarantee. Volatile accesses are atomic; ordinary accesses protected by one lock also cannot expose tearing to cooperating readers.

C++: there is no "atomic by size" rule. Any unsynchronized concurrent access where at least one is a write to a non-atomic object is a data race and undefined behavior, even for int or bool. std::atomic<T> makes accesses atomic, and is_lock_free() reports whether that atomic implementation is lock-free, not whether it is one hardware instruction.

And atomic is not the same as visible: in Java, a plain int field written by one thread may never be seen by another without volatile or a lock, even though each access is atomic.

Likely follow up: "Is incrementing an AtomicLong always atomic?" incrementAndGet() is; x.set(x.get() + 1) is not.

10Corethread-safetycomposition
If a class only uses thread-safe collections, is the class thread-safe?
Model answer

Not necessarily: thread safety does not automatically compose. Collections guarantee thread-safe operations, with atomicity only where their contracts specify it, but sequences of calls, and invariants that span two collections, are not. Examples:

  • "Add if absent" written as contains then add on a synchronized list.
  • Iterating a Collections.synchronizedList without holding its lock: the Javadoc requires you to synchronize on the list for the whole iteration, otherwise iteration is unsafe; fail-fast detection is best effort, not a correctness mechanism.
  • A concurrent map and a concurrent queue that must stay in step: an observer can see an item in one and not yet in the other.
Thread-safe components give me their documented operation guarantees. My class's invariants still need their own atomicity: one lock that owns all the related state, or one structure that captures the invariant.

Likely follow up: "Why not synchronized (this) there?" It excludes only clients following that outer-lock protocol. Synchronizing on the wrapper also coordinates with clients calling its individual synchronized methods.

11SeniorracesbookingAmazonMeta
Two users try to book the same seat at the same moment. Where is the race, and how do you close it in memory and in a database?
Model answer

It is check-then-act on a scarce resource: both requests read "seat free", both write "booked by me", the last write wins, and both users get a confirmation.

In one process, make check and reserve one atomic step: putIfAbsent on a concurrent map, a compare-and-swap from FREE to the user's id, or a lock per show around the check and the write. For several seats in one booking, lock them in sorted order (or lock the whole show) to prevent deadlock. Validate every seat before changing any, or roll back on failure; lock ordering alone does not make a multi-seat booking all-or-nothing.

With many app servers, a lock inside one process cannot coordinate other servers, so let the database arbitrate:

Assume (show, seat) is uniquely identified by seat_id and PostgreSQL-style conditional-update semantics. One row updated and a successful commit grants the hold; zero means unavailable. Retry transaction conflicts and confirm payment only against a matching, unexpired hold token. Alternatives are a unique constraint on (show, seat) in a bookings table, a version column for optimistic updates, or SELECT ... FOR UPDATE in a short transaction. A hold with an expiry covers the user's think time without holding a database lock for minutes.

Likely follow up: "Why not read the row, check it in application code, then update?" That moves the same race into the database: at read committed, both transactions read "free" before either writes. The condition must be part of the write.

12Seniorshared-state
Where does shared mutable state hide in code that looks single-threaded?
Model answer
  • Statics and singletons: a static cache, a static counter, a default singleton Spring bean or a servlet instance serving concurrent requests.
  • Library objects with hidden state: a shared SimpleDateFormat or DecimalFormat (not thread-safe; prefer DateTimeFormatter for dates and confinement for number formatters); in C++, strtok and localtime may use shared static storage, and rand has shared generator state with platform-dependent synchronization (POSIX offers strtok_r and localtime_r), and a shared std::mt19937 is not thread-safe.
  • Captured variables: a lambda submitted to an executor that captures a mutable list or builder; a C++ lambda capturing by reference.
  • Objects handed to a task and still used by the submitter afterwards.
  • "Immutable" objects with mutable insides: a final List field holding an ArrayList returned by a getter.
  • Lazy fields and memo caches filled on first use.
  • std::shared_ptr: separate smart-pointer instances can safely share control-block ownership, but the pointee is not protected, and two threads assigning to the same shared_ptr object is a data race.
  • Views into shared buffers: a std::string_view, std::span or iterator into a container another thread modifies.
For every object I ask two questions: can two threads reach it, and can either of them write it? If both answers are yes, it needs a safety story.

Likely follow up: "How do you fix the shared SimpleDateFormat?" Replace it with DateTimeFormatter, or give each thread its own copy with ThreadLocal.

13Stretchtoctoufiles
What is a TOCTOU bug, and why can a lock inside your process not prevent it on the file system?
Model answer

TOCTOU (time of check to time of use) is check-then-act where the shared state is outside your process. You check a property of a file, then use the file assuming the property still holds, while another process changes it in between. Classic cases: a privileged program calls access(path, W_OK) and then open(path), and an attacker swaps the path for a symbolic link to a sensitive file between the two calls; or two processes both see that a lock file does not exist and both create it.

Your mutex cannot help, because the other party is another process or user, and the file system is the shared state. The fix is to make the kernel do the check and the act in one call:

Related tools: operate on the opened file descriptor afterwards (fstat, not stat on the path); O_NOFOLLOW and openat against an already opened directory; rename a temporary file atomically on a supported local filesystem; Java ATOMIC_MOVE may be unsupported and replacement behavior is provider-dependent; advisory locks (flock, FileChannel.lock) when every party cooperates.

Likely follow up: "How do you update a config file so readers never see half of it?" For visibility, replace by atomic rename. For crash durability on POSIX, also fsync the temporary file before rename and the containing directory afterward, checking failures.

14Seniorcppundefined-behavior
Why is a data race undefined behavior in C++, and what can the compiler actually do to racy code?
Model answer

Avoiding data races is necessary for defined behavior, but does not alone imply sequential consistency: weaker atomic memory orders can permit non-SC results even without races. In return, compilers may optimize as if no other thread modifies a non-atomic object between synchronization points. On racy code that means:

  • Hoisting: while (!done) {} on a plain bool may compile to if (!done) for (;;) {}, an infinite loop.
  • Keeping values in registers and never reloading them.
  • Merging, removing or splitting stores, so another thread sees torn or missing writes.
  • Reordering independent loads and stores freely.

So there is no such thing as a "benign" data race in C++: a racy statistics counter or a racy flag is still undefined behavior, and ThreadSanitizer is right to report it. A suitable atomic load often compiles to an ordinary load on x86, but cost and ordering are platform-dependent. Relaxed operations suffice for a count that does not publish other data; publication needs a release/acquire protocol or stronger ordering.

Likely follow up: "Is volatile a fix in C++?" No. C++ volatile supports special observable accesses such as platform-defined device registers: it is not atomic, and it does not order other memory accesses.

15Stretchjavamemory-model
What does Java guarantee for a program that has data races?
Model answer

Unlike C++, a data race in Java is not undefined behavior; the JVM must stay memory safe even for racy code. What you still get:

  • Reads obey the JMM's allowed-write and causality rules, rather than arbitrary native undefined behavior. Non-volatile long and double accesses can tear, combining halves of different writes.
  • References are never torn, and type safety holds.
  • final fields of properly constructed objects are seen correctly even through a racy publication.

What you do not get:

  • Freshness: a thread may see a stale value indefinitely.
  • Order: after x = 1; ready = true; another thread may see ready == true and x == 0.
  • Complete objects: a racy reader may get a non-null reference to an object whose non-final fields still hold default values.
  • Atomic long and double writes, unless volatile.
Java gives racy code defined but nearly useless semantics, so I treat every data race as a bug anyway.

Likely follow up: "So can a String be shared through a racy field?" A thread that obtains a properly constructed String sees its initialized contents, but a racy reference field may stay null or stale. Immutability does not guarantee delivery of the reference; publish it safely anyway.

16Stretchracesnumbers
Two threads each run count += 1 one thousand times on a shared plain int that starts at 0. What final values are possible?
Model answer

State the memory model before giving a range. Assume both workers finish and the observer joins them before reading. In C++, conflicting accesses to the plain int are a data race, so behavior is undefined: there is no valid numeric bound, including on real hardware. In Java, plain accesses obey the JMM, not merely source-level read/write interleavings, so that interleaving model is not a complete analysis of optimized racy code.
