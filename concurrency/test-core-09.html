A stable pool completes 400 tasks per second and each occupies one worker for 50 ms on average, excluding queue wait. On average, how many workers are busy?
Why. Little's law: busy workers equals arrival rate times time per task, 400 times 0.05 s, which is 20. Fewer than 20 workers cannot sustain this throughput at that occupancy time. Twenty is an average demand, not a safe size with variable arrivals. Neither 8 nor 400 is the product, and 2,000 also uses the wrong unit conversion.

A request handler creates a fresh fixed pool of 8 workers, submits two subtasks, waits for both results and returns. It never shuts the pool down. With no automatic idle-worker timeout, what is wrong?
Why. The owner must stop and join the pool; a handler returning does not do that. Java's default fixed pool starts two non-daemon workers for these submissions and keeps them waiting. A C++ pool object leaked per request similarly leaves workers alive; a local RAII pool would instead shut down on scope exit. Either request-local construction wastes reuse. Share an application-owned pool or define another explicit lifecycle; request threads can submit to it, and two workers can run the subtasks concurrently.

A fixed pool with no caller execution accepts 1,000 tasks per second and completes 800 per second. Starting empty, what happens after an hour of sustained rates, assuming memory has not run out?
Why. The admitted excess is 200 tasks per second, so 200 times 3,600 gives about 720,000 additional unfinished tasks. Almost all are queued, apart from the fixed number in service. A machine has 4 cores. Each task computes for 10 ms and then waits 90 ms for a remote call. What does the formula cores × (1 + W / C) suggest?
Why. W / C = 90 / 10 = 9, so 4 × (1 + 9) = 40. Each worker uses CPU for 10 percent of its occupied time. Four ignores waiting, nine is only the ratio W / C, and 360 multiplies milliseconds by cores without cancelling the time unit.

Why. Futures do store exceptions for submitted tasks, but raw tasks from execute can throw out of run. In Java an uncaught throwable ends the worker thread; in C++ it ends the whole process. From: Scheduled executors and timers
A divide and conquer task splits into left and right. Which version gets parallelism while keeping the current thread useful?
Why. Forking left makes it available to other workers while the current thread does the right half, then the join collects the left. Joining before computing right serializes those halves. From: Fork/join, work stealing and parallel algorithms
In work stealing, why does a thief take a task from the opposite end of the victim's deque from the one the owner uses?
Why. The owner uses its newest tasks, which tend to be smaller and cache-friendly for recursive splits. Older forks often offer more work to steal. Task size is not measured by the deque, global FIFO order is not promised, and the last item still requires synchronization. Neither deque end is reserved by a lock held throughout user computation.

Why. Amdahl's law: 1 / (0.1 + 0.9 / 8) = 1 / 0.2125, about 4.7. Even with infinitely many cores the limit is 1 / 0.1 = 10. The answer 10 is the infinite-core limit, not the eight-core result. Why. With the available CPU capacity already saturated, multiplying tasks cannot multiply execution capacity. Exact relative performance is workload dependent, so neither a fixed speedup nor a fixed slowdown follows.

Which of these can suspend from inside an ordinary (non-async) function that it calls, deep in its call stack?
Why. Virtual threads and goroutines are stackful: supported blocking operations can suspend them deep in ordinary calls. A C++20 coroutine is stackless: its suspension points preserve its own frame, not an ordinary helper's arbitrary call stack. Many coroutines share one event loop thread. One of them calls a blocking function that sleeps for 2 seconds instead of awaiting an asynchronous sleep. What happens?
Why. A coroutine only gives up execution at a suspending coroutine operation; a normal blocking sleep is not one. A blocking call holds the scheduler thread, and nothing else scheduled on it can run. Why. Virtual threads are real threads to the memory model and run in parallel on several carriers. A candidate writes thenApply like this: if isDone() (which locks and unlocks) is true, run the callback now; otherwise lock, add the callback to the list, unlock. What can go wrong?
Why. Each step is safe, but the decision spans two critical sections, a check-then-act race. Completion can slip into the gap and drain the list before the callback is added. Why. Whichever thread takes the lock first sets the value and done; the other sees done and returns false without writing. Which one wins depends on timing, but there is exactly one winner, and the value never changes afterwards.
