Single writer, actors and message passing

One owner thread per piece of state, fed by messages: Go's slogan, actors, the LMAX single writer idea, and partitions across machines.

Asked atDatabricksUber
Before this:The safety ladderProducer and consumer with a bounded bufferBlocking queuesFutures and promises

When many threads must change one piece of state, there is a design that needs no lock on that state at all: give it one owner thread, and have everyone else send the owner messages. It is a reported approach to Databricks' log writer question, and the same idea runs whole distributed systems.

In plain words

At a bank branch, customers do not open the cash drawer themselves. Each one fills in a slip and drops it in a tray, and one cashier takes the slips one by one, updates the ledger, and hands back a receipt. Twenty customers can arrive at once without overwriting each other, because only one person updates the ledger, in tray order. The cashier must still check that each transaction is valid.

The only shared thing is the tray of slips. Instead of protecting the ledger from many writers, you arrange for it to have exactly one. That is the single writer principle, and a thread that works this way, with private state and a tray of messages, is an actor.

The idea in four parts

  • An owner: one thread that is the only code allowed to touch the state.
  • A mailbox: a queue of messages. It synchronizes senders with the owner, using proven queue code or a small class you wrote once. Reply futures and lifecycle control also synchronize.
  • Messages: each request is a message the owner applies in full before taking the next one. "Deposit 10 into account 7" is a message; so is "tell me the balance". Working this way is called message passing.
  • Replies: a caller who needs an answer gets a future that the owner completes. A caller who does not, just sends and moves on.

Why it is correct: the owner applies messages one at a time, so handlers do not interleave, and a FIFO mailbox applies messages in enqueue order. There is no interleaving inside the state to reason about, because only one thread ever runs code that touches it. This means isolation between handlers, not automatic rollback if one throws. Go's documentation puts the idea in a slogan: "Do not communicate by sharing memory; instead, share memory by communicating."

An actor in code

Here is a controlled-lifecycle example: a private map with no lock, a bounded mailbox, a private ask helper, and typed operations that return copied numbers. Start exactly once before clients submit; finish all client submissions before one controller calls stop(); do not submit afterwards or interrupt the owner. Amounts are nonnegative and checked for overflow. Concurrent close, cancellation and fatal owner failure need the protocol described below.

Four details carry the design. The bounded mailbox limits queued messages, but blocked senders and their payloads still consume resources, so admission upstream must also be bounded. Starting after construction avoids publishing a half-built actor. Ordinary operation failures complete their replies exceptionally; this example is not a recovery system for fatal failures. Java stops with a FIFO poison pill after all senders finish; C++ closes admission and drains accepted messages before joining. The output block shows Java; C++ reports out_of_range for the missing account.

C++

The reply promise is held by a std::shared_ptr because std::function requires a copyable callable and std::promise can only be moved. C++23's std::move_only_function removes that wrinkle; in C++20 the shared pointer works with std::function. The client threads use C++20 std::jthread for joining on exceptional exits; the C++17 alternative is std::thread plus a joining scope guard.

Ownership, visibility and order

A queue publishes a message; it does not freeze it. Writes made before a Java blocking-queue insertion happen before the consumer accesses that message. The C++ mutex hand-off provides the corresponding ordering, and future completion publishes the reply. Send immutable values, deep copies, or exclusively transferred objects; do not keep mutating an array or buffer after enqueueing it. A copied C++ pointer still aliases the same object, and std::move alone neither transfers every alias nor synchronizes threads.

The private helper deliberately keeps the map away from caller-supplied code. A public generic ask could return the live map, retain a reference, or execute arbitrary blocking code. Public commands should expose domain operations and return values or immutable snapshots.

FIFO means successful enqueue order. Concurrent senders have no predetermined total order based on when their calls began, and actor frameworks can have different mailbox policies. The example's final balance query follows every deposit because main first joins all submitting clients; waiting for that query's reply makes the observed 4000 deterministic.

Tell, ask, and the deadlock you can still build

A tell has no reply protocol; an ask requests a reply, usually through a future, and need not block. The demo discards deposit futures as a tell-like use, but still pays their allocation cost and loses their error reports. Blocking waits are where actor designs deadlock, because an owner that blocks inside a message handler cannot process anything else, including the message that would unblock it:

The rule: never block an owner on another owner's reply. Let the reply arrive as a new message (a continuation), or prove an acyclic wait graph with independent execution resources. One-way dependencies alone are insufficient on a starved shared pool. The same trap exists with one owner: a message handler that asks its own actor and waits will wait forever, because the answer is queued behind itself.

A bounded mailbox adds another wait: two owners can block trying to enqueue to each other's full queues even without waiting for replies. Use non-blocking admission with explicit rejection or an asynchronous capacity protocol between owners. Java adds a subtler hazard: non-async CompletableFuture continuations may run inline when the owner completes a reply, so arbitrary callback code can stall or reenter the owner. Dispatch such work to a suitable executor and send any state changes back as messages.

When slow work runs elsewhere, its completion is a new handler. Other commands may have changed the state in between, so carry a request id or version and revalidate before applying the result; an asynchronous sequence is not one atomic handler.

Reads: through the mailbox, or from a snapshot

Asking the owner gives a consistent answer at the point the read handler executes, at the cost of a queue hop and a wait. Reading the owner's map directly from another thread "because it is only a read" breaks the design: it can race with the owner's writes, which is undefined behavior in C++. For read-heavy state, have the owner publish an immutable snapshot after each change, or each batch of changes, through a Java volatile reference or a correctly synchronized C++ owning pointer. A C++ raw atomic pointer alone does not solve snapshot lifetime; for this C++20 libc++ target, the free atomic load/store functions for shared_ptr are available even though the atomic<shared_ptr> specialization is not. Readers then read snapshots with no messages at all, and accept that a snapshot may be a moment old. That is the immutable rung of the safety ladder serving the owner rung.

The single writer principle, and LMAX

The idea also has a hardware argument. When cores alternate writes to the same cache line, coherence repeatedly transfers write ownership, and that traffic, not the lock itself, is often what makes contended code slow. Martin Thompson's single writer principle says: arrange for every item of data to be written by only one thread, and let any number of threads read it. Readers still require atomics or an explicit publication protocol; a single writer does not legalize concurrent plain reads. Threads can migrate between cores, false sharing can place other writers on that line, and readers still generate coherence traffic.

The LMAX exchange became the well-known example. Martin Fowler's write-up of the LMAX architecture describes the core business logic running on a single thread, entirely in memory, with reported throughput in the millions of transactions per second for that particular workload, with input and output passed through ring buffers between threads. The lesson for an interview is not the ring buffer; it is that one thread doing simple sequential work on data it owns can beat many threads fighting over shared data.

Many owners: partition by key

One owner is one core's worth of throughput. When that is not enough, keep the idea and multiply it: split the state by key across N owners, and send each message to the owner of its key, usually a nonnegative hash(key) mod N. Messages for the same key still run one at a time, in order, on one thread; messages for different keys can run in parallel when they map to different owners. Hash collisions serialize unrelated keys too; keep a key's hash stable while it is in use. This is a keyed executor, and it is how you make a leaderboard, an account service or a per-user rate limiter thread-safe without a lock per operation.

What you give up: there is order per key, not across keys, and an operation that touches two keys owned by different lanes (a transfer from account 7 to account 12) is no longer one message. You either route both keys to one owner, or use a coordinating transaction protocol when all-or-nothing behavior is required. Two independent messages are not an atomic transfer; compensation is a different, weaker contract. Repartitioning also requires draining or transferring the old owner's work before activating the new one. The same idea scales past one machine: a log partitioned by key, with one consumer per partition in a group, gives per-partition order with no locks; a database with one primary per shard does the same for writes. That is ordering by ownership, the distributed version of this lesson.

Actors and their frameworks

An actor generalizes the owner thread: private state, a mailbox, and behavior that handles one message at a time. Actors send each other messages and can create new actors. They do not need a thread each: an actor system runs thousands of actors on a small pool, scheduling an actor's mailbox onto some pool thread when it has messages, and never on two threads at once. Erlang's processes and the Akka toolkit for the JVM are the best known; in Erlang, failure handling is built in as well, with supervisors that restart crashed actors. In a coding round, be ready to implement the ownership and mailbox mechanism without relying on a framework. Serial execution, rather than a fixed physical thread, is the invariant; the runtime must safely publish state when an actor moves between worker threads. Thread-local data therefore cannot serve as actor-local data.

Worked example: Databricks' event writer, as a single writer

A reported Databricks round asked for an EventWriter: many threads call appendEvent(bytes) for one file, throughput must be high, and appendEvent may return only once the event is durable on disk. The discussion went from one lock with a write and an fsync per event (far too slow, because every event pays a full disk flush), to a producer and consumer design with one writer thread, to batching, to a per-event future completed after the flush.

Seen through this lesson, the writer thread is the single owner of the file handle, the write buffer and the file offset. Producers never touch any of them; they only enqueue. That is what makes batching easy and ordering automatic:

One flush now covers a whole batch, a technique called group commit. If flush latency dominates, amortizing it improves throughput, but bandwidth, copy costs and latency targets limit the gain; it is not generally linear in batch size. Order is simply queue order, because one thread writes. Close first stops admission, then drains accepted work, flushes, completes the promises and joins the writer. Durability is a separate contract from queue ordering: flushToStorage must use the required OS and device guarantees, and failures must reach every affected caller. A future-returning appendAsync is a valid alternative API, but returning that future alone does not meet the synchronous appendEvent contract. The full problem, with its tests, is in the practice bank.

Shutdown and failure are protocols

A poison pill is safe only after admission stops. If a sender enqueues after the pill, its message has no consumer. For concurrent close, make the admission check and acceptance atomic with respect to closing, reject later submissions, wake blocked senders, drain accepted work, and let one controller join. A full queue must not prevent close from making progress. The C++ example's closed predicate illustrates the drain; concurrent controllers still require their own lifecycle coordination.

Catching an exception does not undo changes already made. Validate first, then commit a change that preserves invariants, or use a rollback strategy. Java's example catches RuntimeException, not fatal Error; an exception escaping a C++ thread calls std::terminate. A recoverable actor failure needs a policy for every pending reply, admission rejection, and state recovery before any restart.

A reply timeout or future cancellation does not prove the command did not execute. In this example a cancelled Java reply does not remove its queued deposit. Retrying without a request id and deduplication may apply it twice; exactly-once effects require an explicit protocol, especially across process crashes.

Common mistakes

  • Reading the owner's state from another thread. "It is only a read" is still a data race. Ask the owner, or read a published snapshot.
  • An unbounded mailbox. When senders outpace the owner, memory grows until the process dies. Bound it, and decide whether a full mailbox blocks the sender or rejects the message.
  • Blocking inside the owner. A synchronous ask to another owner can deadlock, and a slow network call stalls every message behind it. Keep handlers short and non-blocking.
  • Letting one exception kill the owner. Handle recoverable errors per message while preserving invariants, and define what fatal failure does to pending work.
  • Doing the heavy work in the owner. Parse and perform state-independent computation outside the owner; keep validation that depends on current balances or other owned state inside its handler.
  • Expecting order across owners. Keyed lanes order messages per key, not globally.

In the interview

It appears in several reported Databricks discussions. In the event writer round above, the reported path went through "producer and consumer with a single writer thread" before batching and per-event futures, and a 2026 senior log writer report describes starting with a lock-protected queue drained by one background writer. At Uber, a candidate who proposed a keyed executor to make a leaderboard thread-safe reported a strong result on that low level design round. More generally, "how would you avoid locking here?" invites it whenever the state has complex invariants and a modest write rate.

Rather than lock the state, I will give it one owner thread. Callers put commands on a bounded queue and get a future back; the owner applies commands one at a time, so handlers do not interleave and they apply in enqueue order. The mailbox, reply futures and lifecycle still synchronize, and failed handlers need an explicit state policy. The costs are a queue hop per operation and a throughput ceiling of one core, so if it becomes the bottleneck I will partition by key across several owners, which keeps per-key order. I will never block the owner on another owner's reply, because that can deadlock.

Follow ups to expect: "How do readers get data?" (ask, or a published snapshot). "What happens when the queue is full?" "How do you shut it down without losing messages?" (a poison pill after the last message, or a closed flag plus a drain). "What if one message is slow?" "How would this work across machines?" (partitions with one owner each).

Senior depth

Batching makes single writers fast. An owner that drains a bounded batch from its mailbox, applies it all, then does the expensive step once (a flush, a network send, publishing a snapshot) turns a per-message cost into a per-batch cost. Under load, batches grow by themselves, but batch size and maximum wait need limits so latency and fairness remain acceptable.

The mailbox can be cheaper than a general queue. Many producers and exactly one consumer is a special case: only one thread ever removes, so the consumer side needs no coordination with other consumers. High performance designs use queues specialized for "many producers, single consumer" for exactly that reason.

Hot keys are hot owners. Partitioning moves contention from locks to queues: if one key gets most of the traffic, its owner's mailbox grows while others idle. The fixes are the same as for a hot lock: split that key's work (by sub-key or by a deliberate fan-out and merge), or give it a dedicated owner to isolate other keys. A dedicated owner does not increase that hot key's own serial processing capacity.

Key takeaways

  • One owner thread per piece of state, a bounded mailbox, messages applied one at a time: no lock on the state, with isolation between handlers and FIFO enqueue order.
  • Replies publish results; recoverable failures complete them exceptionally. Stop admission before draining or placing a poison pill, and define fatal-failure behavior.
  • Never block an owner on another owner's reply; read through the mailbox or from published snapshots, never directly.
  • Partition by key across several owners for more throughput, keeping per-key order but not global order.
  • The same idea runs systems: one writer per partition, one primary per shard.

Quick check

Answer each question, then read why. Your score is saved for your module test.

In the actor implementation shown, which mutable state needs no synchronization while a handler accesses it?
Why. Only the owner thread touches the private state, so there is nothing to race with. The mailbox is shared by all senders and must be thread-safe, and direct reads from other threads race with the owner's writes.
Owner A, while handling a message, asks owner B for a value and blocks on the future. B, while handling a message, asks A and blocks on its future. What happens?
Why. An owner that blocks cannot process its mailbox, including the request that would unblock the other side. Reply with continuation messages instead of blocking, or establish an acyclic wait graph with independent execution capacity. There is no automatic timeout or mailbox reordering that releases these blocked owners.
Senders produce 10,000 messages per second and the owner can process 6,000. These rates persist, nothing drops messages, and the mailbox is unbounded. What happens over time?
Why. With sustained fixed rates, the backlog grows at 10,000 minus 6,000 = 4,000 messages per second. An unbounded queue neither drops nor blocks because of capacity, and it cannot increase the owner's service rate. A bounded mailbox makes senders wait (back-pressure) or get rejected, which surfaces the overload where it can be handled.
A keyed executor has stable routing and FIFO lanes. Two concurrent callers enqueue commands for key K: one sets its value to 1, the other sets it to 2. After both enqueue calls return, a third command for K prints the value. What can it print?
Why. K always maps to one lane. Its print command runs after both writes, so it cannot see the initial value. The two concurrent writes have no predetermined call-start order, so either can be last. This is per-lane enqueue order, not a global order across lanes; different keys can also collide into one lane.
A deposit handler changes the balance and then throws before completing its reply. A wrapper catches the exception and fails that future. Which guarantee follows?
Why. A failed reply reports an error, not a transaction rollback. A catch can let the loop continue, but changed state remains unless code restores it. Neither retry nor owner death follows automatically. If an exception escapes the wrapper, Java ends that thread while C++ calls std::terminate, which normally ends the process.
A developer adds a getBalanceFast() method that reads the actor's private HashMap (or C++ unordered_map) directly from the calling thread, "because reads do not change anything". What is wrong?
Why. A read concurrent with a write is a data race. The owner's writes are only safe because nobody else touches the map. Ask the owner, or have it publish an immutable snapshot for fast reads.
Each message makes the owner do a 50 ms blocking network call. About how many messages per second can this owner handle, whatever the number of senders?
Why. One thread doing 50 ms of blocking work per message completes at most 1000 / 50 = 20 per second. Move slow I/O out of the owner (or batch it, as the event writer does with one flush per batch), and keep the owner for the state changes.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a KeyedExecutor with execute(key, task): tasks with the same stable key run one at a time, in successful enqueue order; tasks with different keys may run in parallel. Then say what you would change for production.
Model answer

Each key always hashes to the same lane, and a lane has exactly one thread taking tasks in queue order, so tasks for one key never overlap and keep their order. Different keys can collide; only keys on different lanes run in parallel. Java may replace a worker after an uncaught task exception, so serial lane ownership does not guarantee a stable thread identity. The C++ lane catches task exceptions and reports them to standard error. The fragments use unbounded queues and require non-blocking tasks with no cross-lane waits. Stop external callers before shutdown or destruction; Java shutdown() rejects new work but does not wait, so also await termination before consuming final results. For production: bound each lane's queue and decide what a full lane does (block the caller or reject), and never fall back to running the task on the caller's thread, which would break single ownership; size the lane count to the cores and to the expected number of hot keys; and add metrics per lane, because one hot key makes one lane the bottleneck while the others idle.

Design
A game has a global leaderboard: millions of score updates per minute from many threads, and frequent reads of the top 100. Compare one lock, one owner thread, and partitioned owners, and pick one.
Model answer

One lock around a score map and a sorted top 100 is simple and correct, but every update and every read serializes on it, so it becomes the contention point first, and reads wait behind writes.

One owner thread holding the map and the top 100, fed by a bounded queue, removes lock contention and keeps updates ordered. If it publishes an immutable copy of the top 100 after each batch of updates, readers acquire an owning snapshot and inspect it without a mailbox hop. This is not a promise of a lock-free C++ shared-pointer operation. Its limit is one core's worth of updates; with cheap updates that can be a lot, but it is a ceiling.

Partitioned owners hash players across N owners. Each owner keeps the scores of its players and a local top 100, publishes it as an immutable snapshot, and a reader merges N small sorted lists, which is cheap. Updates can scale across lanes if the load is balanced, and each player's updates stay ordered. I would first confirm that stale reads are acceptable, benchmark one owner, then partition if necessary. Use a deterministic tie-breaker, keep enough local ranking state to handle score decreases, and merge local top-100 lists. Independently published snapshots need not represent any one global instant; strict global ranks need coordination. Choose N from measured load and available cores, and state an explicit freshness target rather than assuming a few milliseconds is always acceptable.

Explain
When would you choose an owner thread with a mailbox over a lock, and when would you choose the lock?
Model answer

I choose an owner when the state has complicated invariants that would need long or nested critical sections, when operations must apply in a strict order, when the owner can batch an expensive step such as a disk flush or a network send, or when callers do not need to wait for the result. It makes correctness easy to see, because only one thread ever touches the state.

I choose a lock when operations are short and callers need the result immediately, because an uncontended lock usually costs less than queueing and waking another thread; when reads dominate and can share a lock or a snapshot; and when the design does not justify a dedicated thread. Either way I watch the same thing: a single owner and a single lock are both serial points, and the fix for both is to partition the state by key.

"Why would you put this map behind an actor instead of locking it, and what ordering would callers actually get?"
What a strong answer covers
  • Only serialized handlers access the mutable map; mailbox and replies still synchronize
  • FIFO gives enqueue order, with no predetermined ordering between concurrent submissions
  • Commands carry immutable, copied or exclusively transferred data and return independent results
  • Readers ask the owner or acquire safely published immutable snapshots
  • Choose actors for batching or asynchronous operations, accounting for queue hops and one owner's capacity
  • Partition stable keys for throughput while explaining collisions and cross-key transaction limits
How a senior would say it
I would choose an actor when serial ownership makes the map's invariants easier to maintain, especially if I can batch expensive work. Every update and consistent read becomes a command. Only one handler accesses the mutable map at a time, while the mailbox and reply futures provide the synchronization between threads. With a FIFO mailbox, handlers run in successful enqueue order. Two concurrent submissions do not have a predetermined order based on which call started first. If a caller needs to know an update took effect, it waits for the reply after the update, not merely for enqueueing to finish. Commands must carry immutable data, copies, or exclusive ownership. Sending a reference does not stop its sender from mutating the object. Replies should return values or immutable snapshots, never the live map. Frequent readers can acquire safely published snapshots if their freshness requirement allows it. The costs are a queue hop, possible waiting, and one owner's serial capacity. For tiny synchronous operations, a lock may be simpler and faster. If measured load exceeds one owner's capacity, I can partition by stable key. Different lanes run in parallel, but hash collisions still serialize some keys, and a transaction across two owners needs additional coordination.

Likely follow up: What happens if a handler starts asynchronous work and the state changes before its completion arrives?

Out loudabout 90 s
"Your actor has a bounded mailbox. How would you close it without losing accepted work or leaving callers waiting forever?"
What a strong answer covers
  • Stop admission atomically with respect to accepting commands and reject later submissions
  • Wake blocked producers, drain accepted commands, then let a controller join the owner
  • A poison pill requires admission to have stopped so no command can land behind it
  • Distinguish recoverable operation failure from fatal owner failure and settle affected replies
  • Do not block owners on replies or full mailboxes; a timeout does not imply non-execution
  • For a durable writer, complete replies only after the required flush succeeds and report flush failures
How a senior would say it
I would make close a lifecycle transition, not just another message. First I would stop admission atomically with respect to accepting commands. Later submissions fail explicitly, and producers blocked on capacity must wake and either finish an already accepted operation or learn that admission is closed. The owner drains accepted work, completes its replies, and exits. A controller then joins it. A poison pill can implement the exit signal, but only after no sender can put another command behind it. Otherwise that command and its reply are stranded. For an ordinary rejected operation, I preserve the state invariant and complete that reply exceptionally. Catching an exception does not roll back partial changes. If the owner fails fatally, I need to reject new work and settle every affected pending reply before deciding whether recovery is possible. I would also check wait cycles. Owners must not block waiting for each other's replies or space in full mailboxes. A timeout only means the caller stopped waiting; the command may still execute, so retries need deduplication when duplicate effects matter. For a durable log writer, draining means writing and successfully performing the required storage flush before acknowledging the batch. A flush failure must fail the affected replies, not report success.

Likely follow up: How would you distinguish a command that never executed from one whose effect happened but whose reply was lost?
