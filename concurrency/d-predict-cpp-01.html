Predict the output, C++ set 1

Thirteen C++ snippets: thread lifetime, std::async, lock scope, condition variables, atomics and undefined behaviour.

Microsoft interviewers have handed candidates multithreaded C++ and asked them to predict the output before finding the bugs. In C++ the honest answer is sometimes "the program aborts" or "the behaviour is undefined", and the follow up is always "what would you see in practice". Every snippet here was built with clang in C++20 mode and run, with ThreadSanitizer or AddressSanitizer where a bug is claimed. Where several outcomes are possible, the question says "can" and every possible outcome among the options is marked correct.

13 questions, 20 minutes. Answers and explanations stay hidden until you submit or the clock runs out. Multi answer questions say so; pick every option that is true.

Why. A spurious wakeup can return from wait with no job available. Even after a real notification, another consumer can take the job before the awakened consumer reacquires the mutex. Because if does not recheck, either case can lead to front() on an empty queue, violating its precondition. cv.wait(lk, [] { return !jobs.empty(); }); loops until the predicate holds while the mutex is owned. What does this do?
Why. A condition variable has no memory. A notify with no waiter does nothing, and it is legal, with or without the mutex. The join() makes sure the notify happened before main waits, so main waits for a signal that already came and went (the run hung until it was killed). This is the lost wakeup. The cure is a predicate guarded by the mutex: set ready = true under the lock before notifying, and wait with cv.wait(lk, [] { return ready; }), which returns at once if the flag is already set. A semaphore, by contrast, does remember a release.

Compiled as C++20, which statements about this program's possible behaviour are valid? Select all that apply. Compiler optimizations may change the observed outcome. Select all that apply
Why. The plain stop flag is read and written by different threads without synchronization, so the program has a data race and undefined behaviour. The standard imposes no output guarantee: the expected sequence, an early worker message and a hang are all compatible with that lack of guarantees, and these are not an exhaustive list. A single-instruction store does not remove a data race. ThreadSanitizer reported the conflicting accesses to stop. A tested clang -O2 build printed the worker message before main's setting message, showing why source-level loop reasoning is unreliable here. Other builds may retain a stale value or behave differently. Use std::atomic<bool> or a mutex; C++ volatile does not supply thread synchronization.

Why. std::call_once runs the function exactly once, picked from whichever thread gets there first, and every other caller blocks until that call has finished, so no use line can come before the init line. After that the threads race for out, so the use lines can come in any order (one run printed init 1, use 1, use 3, use 2). If the function exits with an exception, the call does not count: the exception goes to that caller and a later call_once runs a function again (we confirmed a second attempt ran). A function local static gives the same once only guarantee for initialization.
What happens when restock_all(5) is called on an inventory that has at least one item?
Why. restock_all holds m_ and calls add, which locks m_ again on the same thread. std::mutex is not recursive, and locking it while owning it breaks a precondition of lock(), so the behaviour is undefined. An implementation may detect it and throw resource_deadlock_would_occur, but nothing requires that; our macOS build simply hung. The usual fix is a private helper that assumes the lock is held (add_locked), called by both public methods. Reaching for std::recursive_mutex usually hides a design problem. In Java, synchronized and ReentrantLock are reentrant, so the same code works there.
