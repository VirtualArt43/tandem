System coding rounds: what they are and how they are graded

Prepare for concurrent component coding: clarify the contract, build from primitives, handle failures and shutdown, and test the result.

Asked atRubrikDatabricks
Before this:Producer and consumer with a bounded bufferBuild it yourself: a thread pool with futures and shutdown

Rubrik's System Coding and Databricks' System Programming rounds ask you to build a small component and explain its concurrency contract. Prepare runnable code and the failure paths a library normally handles, while confirming the round's execution requirements.

In plain words

Picture a cooking practical where the examiner locks the masala cupboard. Anyone can make a curry with a ready-made masala packet. Here you grind your own from whole spices, the dish is actually cooked and tasted, and the examiner also watches how you turn off the gas and clean the counter at the end.

A system coding round works the same way. The ready-made packet is the library thread pool or blocking queue, and it is often banned. You build the component from a lock and condition variables, you should be ready to compile and run it, and you are graded on the finishing work as much as the main dish: shutting down cleanly, surviving a failing task, handling an interrupt or a timeout. The rest of this module is the recipe book for the dishes they ask most often.

Two rounds, one family

The names differ and the emphasis differs, but both rounds test the same skill: writing a correct, complete concurrent component under time pressure. Here is what the interview reports from 2022 to 2026 and Databricks' own prep guide say.

The library ban changes the problem

A short wrapper around a library executor can hide most of the work in "implement a thread pool". With that API banned, the same prompt means a queue, workers, a lifecycle, shutdown and interruption, all built by hand. Confirm the allowed primitives; these are the usual starting points:

  • Java: Thread, ReentrantLock with Condition, or synchronized with wait and notifyAll. Atomics are usually fine; ask.
  • C++: std::thread (or std::jthread), std::mutex, std::condition_variable, std::atomic. The C++20 standard library has no thread pool or blocking queue; confirm whether any third-party library is allowed.

Many system coding answers reuse the same building block: a bounded queue that producers put into, workers take from, and that can be closed, so the workers know when to stop. Learn it until you can write it in five minutes, because the pool, the log writer, the crawler and the job runner all stand on it. It is a monitor: one mutex guarding the items, and a condition variable for each thing threads wait for.

The capacity must be positive, Java elements must be non-null, and C++ elements must have nonthrowing moves so extracting an item cannot lose it halfway through. The demo assumes container allocation succeeds; it is not an allocation-failure recovery design. The split of 1,000 items between consumers is scheduling dependent.

Three decisions in that code are the ones interviewers poke at:

  • Close means "drain, then stop". take keeps returning items after close, and reports "closed" only when the queue is empty. Nothing that was accepted is lost. If the interviewer wants "stop now" semantics, that is a separate operation that hands back the items, like shutdownNow.
  • Every wait is a loop that re-checks both the data condition and the closed flag, so spurious wakeups and stolen wakeups are harmless.
  • Close wakes everyone. Two consumers may be asleep on an empty queue, and both must learn that the queue is closed. Waking only one can strand the other waiter indefinitely; spurious wakeups are not a progress guarantee.

The linearization points are the locked queue mutations and the assignment to closed. A put that wins the lock first may succeed before close; one that observes closure fails. Unlocking and subsequently locking the same mutex publishes the item to its consumer. FIFO describes removal order, not processing completion order, and this queue promises neither fair admission nor a byte-level memory bound.

Publication covers writes made before enqueueing. It does not make later mutations to a shared payload safe: transfer ownership, use immutable data, or synchronize further access. Closing also does not destroy the queue safely by itself; stop or join every caller before destroying a C++ queue and its mutex and conditions.

Tests that expose the contract

Test a forced schedule, then stress the invariant. A total of 1,000 removals can hide one duplicate and one missing item. Give every item an identity and check that each accepted item leaves exactly once.

ArrangeCheck
Several consumers waiting on an empty queue, then closeEvery consumer returns empty; bounded joins detect a missed wakeup
A full queue with blocked producers, then closeBlocked puts reject; previously accepted items still drain in FIFO removal order
A put racing with closeIt either succeeds before closure and is drained once, or rejects; no accepted item disappears
A timed poll with no item, then a poll after insertionThe first can time out without consuming anything; the next gets the item

Use gates or test hooks to arrange the contested state; a sleep does not prove another thread reached its wait. Bound the whole test process as well as individual waits. A timeout can mean a bug or a busy machine, so inspect the blocked stacks; ThreadSanitizer helps detect C++ data races but does not prove FIFO, shutdown or progress.

How the round is graded

Interviewers in these rounds keep score on the same handful of things. The 2026 Rubrik pool report is explicit: shutdown semantics, thread interrupts, and which exceptions the workers catch (that candidate's catch of InterruptedException plus Exception was judged not enough), with requirements changed three times during the hour. Which exceptions should a worker catch?

The report does not identify the missing exception policy. Always repair completion bookkeeping, including exceptional paths. A teaching pool may catch Throwable around a Java task and report it, or let the worker fail and replace it; catching a VM failure does not guarantee safe recovery. In C++, catch ... at the task boundary because an exception escaping the thread function calls std::terminate. Keep the error handler reliable too, and decide separately what interruption means in worker waits.

A plan for the 60 minutes

  1. Minutes 0 to 5: pin the contract. Exact method signatures. Does submit block or reject when full? What does wait return on failure? What happens to queued work at shutdown? Ordering guarantees? Which libraries are allowed? Which language?
  2. Minutes 5 to 10: state, invariant, primitives. Say out loud what the shared state is, what must always be true about it, which lock guards it, and what each thread waits for. For a pool: "a queue and a pending count under one lock; workers wait for work or shutdown; waitUntilComplete waits for pending to reach zero."
  3. Minutes 10 to 35: write it. Single-threaded logic first if the prompt is a data structure, then the lock and the waits, then the lifecycle. Keep it compiling as you go.
  4. Minutes 35 to 45: run it. A small main with several threads, a failing task, and a shutdown. Check exact counts, rejection and clean exit; a demonstration alone is not a correctness proof.
  5. Minutes 45 to 60: follow ups. Timeouts, shutdownNow, back-pressure, fairness, "now make it faster". This is where senior candidates separate themselves, so leave time for it.

Worked example: reading the prompt like the interviewer

The prompt (Rubrik, reported from 2020 to 2025 in several forms): "Implement schedule(task), which must never block, and waitUntilComplete(), which blocks until all scheduled work is done. No BlockingQueue, no ExecutorService."

Questions worth asking, with one possible clarified contract:

  • How many workers? "N, given in the constructor." So a fixed pool.
  • Does waitUntilComplete mean global idleness or a snapshot of accepted tasks? Choose global idleness for this first version: concurrent submissions extend the wait. For a fixed snapshot, capture a sequence boundary and track unfinished earlier tasks.
  • Does "never block" mean no waiting for task completion or capacity? The lock and allocation can still delay submission. A strictly non-blocking progress guarantee is a different requirement.
  • Can it be called many times? "Yes, batch after batch." So the pool must be reusable, not one-shot.
  • What if a task throws? "Your call." Say: catch it, keep the worker, count the task as finished, and report the error.
  • Who calls these methods? "One client thread, maybe several." Design for several.

The plan you say out loud: "One lock guards a task queue and a pending counter, which counts queued plus running tasks. schedule appends, increments pending, signals one idle worker, and returns. Workers wait in a loop for work or shutdown, run the task outside the lock, then decrement pending in a finally block and signal allDone when it reaches zero. waitUntilComplete waits in a loop while pending is above zero." That plan is the whole answer; the next lesson writes it in both languages.

Common mistakes

  • Reaching for the library without asking. At Rubrik ExecutorService and BlockingQueue are often banned, and they are exactly the parts the interviewer wants to watch you build. Ask first; if they are allowed, still be ready to build them.
  • Writing pseudocode when the round expects running code. A Rubrik new grad fixed the deadlock in a debugging round and still lost it on a compile error, and an Uber machine coding candidate was rejected partly for having no running code. Plan for compiling code.
  • Polling with sleep. while (queue.isEmpty()) Thread.sleep(10); is periodic polling with extra latency and wakeup overhead. Use a condition variable.
  • Running the task while holding the lock. It serializes the whole pool and can deadlock callbacks. C++ mutexes are nonrecursive; Java reentrancy permits some callbacks but does not make dependent waits safe. Take the task under the lock, run it outside.
  • Forgetting the end. No shutdown, or a close that wakes one waiter, and the program hangs on exit. The Java workers here inherit non-daemon status from main, so they keep the JVM alive until they finish.
  • Going lock-free to impress. A Databricks report (low confidence) describes a candidate who could not justify a lock-free attempt and recovered only by switching to a plain synchronized block. Correct and explained beats clever.

In the interview

At Rubrik the round often opens the process, as a screen named System Coding, Concurrency or Multithreading, and a weak result there can end it. At Databricks it is an onsite round, sometimes labelled System Programming, LLD, or even "system design" by a recruiter. In both, the first two minutes set the tone: ask about the contract, then state your design before typing.

Before I code, let me pin down the contract: does submit block or reject when the queue is full, what should happen to queued tasks at shutdown, and should a failing task be reported through a future? Then my plan: one lock guards the queue and a pending count, workers wait on a condition for work or shutdown, tasks run outside the lock, and the bookkeeping happens in a finally block so a failing task can never hang a waiter.

Expect the requirements to move: "now without the library", "now a task throws", "now add a timeout", "now shutdownNow", "now two of these share one buffer". Each later lesson in this module ends with exactly those follow ups.

Senior depth

Senior loops at Rubrik keep two concurrency-heavy coding rounds and add design rounds that also probe threads, such as an SCP-like copy of a very large file with chunking and parallel streams. Databricks grades design quality explicitly, so a senior answer shows the single-threaded component first, with clean seams (a writer, a buffer, a storage interface), and then adds concurrency without tangling it into every class. At both companies the deeper follow ups move from "is it correct" to "is it fast and does it fail well": batching and fsync cost, back-pressure policy, what a caller sees when the disk fails, and how you would test for races (stress runs with invariant checks, ThreadSanitizer in C++).

Key takeaways

  • These reported rounds commonly last 60 minutes and ask for a concurrent component; execution requirements vary, so prepare runnable code and confirm expectations.
  • Rubrik often bans the high-level library, so you build queues, pools and latches from a lock and condition variables.
  • Grading focuses on what a library hides: shutdown versus shutdownNow, interrupts, exceptions, timeouts, starvation, and clean exit.
  • Databricks leans on I/O systems: ordering, batching, fsync, flush and close, back-pressure, chunked fetch.
  • Pin the contract, state the invariant and primitives, write it, run it, then spend the last part on follow ups.

Quick check

Answer each question, then read why. Your score is saved for your module test.

Two consumers are blocked in take() on an empty ClosableQueue. A buggy close() sets closed = true and then calls notEmpty.signal() (one waiter) instead of signalAll(). What failure is possible when main then joins both consumers?
Why. signal (or notify_one) selects one waiter. With no further notifications or spurious wakeup, the other remains asleep indefinitely. Spurious wakeups are permitted, but relying on them for termination is incorrect. Both consumers were already waiting, so the notification is not too early. Closing must wake every waiter, here with signalAll or notify_all. Holding the lock while signalling is allowed and is required by Java's ReentrantLock conditions.
The interviewer allows threads, ordinary containers, locks and conditions, but bans ready-made executors and concurrent queues. Which approach fits that contract without periodic polling?
Why. The ban removes the high-level library, not the primitives. Locks and condition variables let a thread sleep until the state it needs appears. Polling with sleep adds latency and wakeup overhead; a concurrent queue violates this stated ban. CompletableFuture.allOf combines results but does not supply a permitted executor, and flag spinning consumes CPU while idle.
Java onlyA hand-built pool's worker runs while (true) { Runnable r = takeTask(); r.run(); finishTask(); }, where finishTask() decrements pending and signals waitUntilComplete. One task throws an IllegalStateException. What is the result?
Why. An uncaught exception ends only the thread that threw it: the default handler prints a stack trace and the thread dies. The pool silently has one worker fewer, and because pending was never decremented, the waiter can never see zero. Wrap the task in try with a catch (Throwable t) and do the bookkeeping in finally.
C++ onlyA hand-built pool's worker runs while (true) { auto task = takeTask(); task(); finishTask(); } on a std::thread. One task throws std::runtime_error. What is the result?
Why. In C++, an exception that leaves the function a std::thread runs calls std::terminate, which kills the entire process, not just that thread. join does not transport exceptions; a std::future backed by a promise or packaged task can. Wrap each task in try { ... } catch (...) { ... }.
Which statement about shutdown() and shutdownNow() is right?
Why. shutdown does not wait for task completion; that is the job of awaitTermination. shutdownNow cannot kill a thread: Java's Thread.stop throws UnsupportedOperationException in Java 21, and C++ has no safe way at all. It interrupts (Java) or requests a stop (C++), and a task that ignores the request keeps running.
Databricks' official guide says the System Programming round is done in pseudocode. What should you plan for?
Why. Reports conflict: one L4 had to write a full C++ implementation, and another candidate was told the code did not need to run but should be close to working. The guide itself grades design quality and covers both single and multi-threaded versions. Lock-free code you cannot justify is a risk, not a bonus.
You hand in a hand-built pool. Which behaviours is the interviewer likely to test? Select all that apply.Select all that apply
Why. Exception safety, shutdown semantics and interrupt handling are exactly the parts a library would hide, so they are what the round grades. Fewest lines is not the goal. Periodic polling adds overhead; a condition signal makes a waiter eligible to resume, subject to scheduling and reacquiring the lock.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
The interviewer says: "Build me a thread pool. No ExecutorService, no BlockingQueue." Say what you would ask and what you would say in the first three minutes.
Model answer

I would ask: how many threads, fixed or growing? Does submit return a result, a future, or nothing? When the queue is full, should submit block, reject, or is the queue unbounded? What should shutdown do with queued tasks, and do you also want shutdownNow? What should happen when a task throws? Is a timeout per task needed? Which language, and may I use atomics?

Then I would state the design: "One lock guards the task queue, the pool state (running, shutting down, stopped) and a pending count. Workers loop: wait on a condition until there is work or the pool is stopping, take a task under the lock, run it outside the lock inside a catch-all, then decrement pending in a finally and signal waiters. shutdown flips the state and wakes all workers, which drain the queue and exit. shutdownNow also removes and returns queued tasks, and requests cancellation of claimed work. A separate termination wait observes retirement and joins threads where required." Then I would start with the queue and the worker loop, and keep a main that runs a failing task and a shutdown.

Write code
Add poll(timeoutMs) to the ClosableQueue: it uses that waiting budget once it acquires the lock and returns empty on timeout, or when the queue is closed and drained.
Model answer

The Java loop keeps the remaining time from awaitNanos, so a spurious or stolen wakeup does not restart the full timeout. The C++ predicate overload of wait_for loops for you and returns the predicate's value, so false means the time ran out with nothing to take. Neither version bounds lock acquisition or scheduling delay, and either may return an available item with a zero budget. The Java unit conversion saturates instead of overflowing. A strict end-to-end deadline also needs timed lock acquisition and a remaining-time calculation.

Design
Name the core building blocks you would use for each prompt: (a) Databricks' durable log writer, (b) Rubrik's DAG job runner, (c) a crawler that must "now be multithreaded".
Model answer
  • Durable log writer: a bounded queue for back-pressure, one writer thread that drains the whole queue into a batch, a write-all loop handling short writes, then one successful fsync per batch (group commit), and a future or promise per event that is completed only after the fsync. Close means drain, fsync, complete, join.
  • DAG job runner: a count of unfinished dependencies per job, a ready queue, N workers, one lock over all of it, a first-failure field that stops new starts, and the quiescence rule "ready is empty and nothing is running". Validate the DAG first, or distinguish successful completion from unfinished jobs blocked by a cycle.
  • Crawler: a frontier queue, a visited set where check and insert happen as one atomic step, N workers, and an in-flight count so the crawl ends when the frontier is empty and no fetch is running. Use a separate admission policy if the frontier is bounded: all workers blocking while adding children can deadlock. Network fetches often benefit from overlap, subject to host limits and downstream capacity.

The shared pattern: one lock per invariant, condition variables for waiting, work done outside the lock, and an explicit end condition.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"You have an hour to build a thread pool using only threading primitives. Talk me through your first few minutes."
What a strong answer covers
  • Clarify worker limits, queue capacity, rejection and result delivery
  • Distinguish global idleness from a snapshot completion contract
  • State the locked invariant: pending equals queued plus claimed/running
  • Describe predicate waits, task execution outside the lock and exception-safe bookkeeping
  • Separate orderly shutdown, cancellation requests and termination waiting
  • Reserve time for adversarial tests and follow ups
How a senior would say it
I would agree the contract before writing the worker loop. I would ask how many workers we need, whether the queue is bounded, what happens when it fills, and whether submission returns a future. I would also clarify whether waiting means the pool becomes idle or only the tasks accepted before this call finish. Those are different contracts when submissions continue. My starting design is one mutex protecting the queue, lifecycle state and pending count. Pending equals queued tasks plus tasks already claimed by workers. Workers wait on a condition until work or shutdown is available, claim under the lock, and execute outside it. Completion bookkeeping runs even when a task throws, and the failure reaches its caller. Orderly shutdown rejects new work and drains the queue. Immediate shutdown returns queued work and requests cancellation of claimed tasks; a separate operation waits for termination. I would reserve time to test a full queue, a throwing task and shutdown racing with submission. That gives us a correct base before discussing performance or extra features.

Likely follow up: What changes if waiting must cover only tasks accepted before the call?

Out loudabout 75 s
"The queue passes its throughput test, but the program sometimes hangs during close. What do you check?"
What a strong answer covers
  • Check the closed predicate and wake every producer and consumer
  • Show two empty-queue consumers stranded by a single notification
  • Keep predicate checks and mutations under the same mutex and wait in a loop
  • Drain accepted items and reject puts that observe closure
  • Use controlled schedules and bounded joins; throughput alone proves little
How a senior would say it
I would first check whether close wakes every thread whose waiting condition changed. Suppose two consumers are asleep on an empty queue. Close sets the flag but signals only one. That consumer returns, while the other may stay asleep indefinitely and prevent its join from returning. A spurious wakeup might hide the bug, but it is not a termination guarantee. Close must change the flag under the same mutex used by put and take, then notify all waiting producers and consumers. Each wait loops on both its data predicate and closure. Consumers drain items already accepted and return empty only when the queue is closed and empty. Producers that observe closure reject the item, including producers previously blocked by a full queue. I would reproduce those cases with controlled coordination and bounded joins, including several waiters on each condition. I would also verify that main releases the queue lock before joining. A throughput run can miss all these schedules; exact item counts and clean termination test different parts of the contract.
