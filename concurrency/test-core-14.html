Two dumps taken 10 seconds apart both show thread "worker-3" BLOCKED with waiting to lock <0xa0>, and thread "worker-9" RUNNABLE inside a socket read with locked <0xa0>. No deadlock is reported. What is the most likely problem?
Why. The shown chain ends in network I/O; it provides no evidence of a two-thread lock cycle. RUNNABLE can describe native I/O and does not prove CPU use. worker-3 is acquiring a monitor, not waiting in a task queue. Move the slow call outside the shared lock while preserving the cache invariant, and check dependency timeouts.

A thread's stack shows - waiting on <0x10> (a WorkQueue) and, two frames lower, - locked <0x10> (a WorkQueue). Does this thread stop other threads from entering synchronized (queue)?
Why. Object.wait() releases the monitor while the thread sleeps and takes it back before returning. Dumps can still print the locked line for the frame that entered the synchronized block. Notification does not transfer ownership; the waiter must later reacquire it, and fairness does not change the release rule. Any other monitors it holds remain locked.

All threads are platform threads, and each described lock cycle is established with indefinite waits. Which hang will NOT produce a "Found one Java-level deadlock" section in a Java thread dump?
Why. The JVM can only follow "held by" edges for things with an owner: monitors and ownable synchronizers such as ReentrantLock. A latch has no owner, so the cycle through it is invisible. You find it by reading the WAITING threads and asking who is supposed to wake each one.

Three dumps taken 5 seconds apart show thread "indexer" RUNNABLE in the same three frames every time, and its cpu= value grew by about 5,000 ms between each pair of dumps. What is the best reading?
Why. 5,000 ms of CPU in about 5,000 ms of wall time is approximately one fully occupied core, even if the thread migrates. It could be a healthy indexing loop, so neither RUNNABLE nor repeated frames proves progress. Blocking or deadlock does not explain that CPU growth.

During an outage, 190 of a service's 200 pool threads show WAITING (parking) inside LinkedBlockingQueue.take, called from ThreadPoolExecutor.getTask. Requests are timing out. What does that tell you?
Why. getTask parking in take() is the normal idle state of a pool worker. Idle workers during an outage point away from the pool: look at the threads that are not idle, and at whatever feeds the pool.

C++ onlyA hung C++ program's all-thread backtrace shows thread 2 in transfer(from=0x8000, to=0x8040) and thread 3 in transfer(from=0x8040, to=0x8000), both with top frame __psynch_mutexwait under the second lock_guard. What is happening?
Why. The second lock_guard is the one that is blocked, so each thread already holds the first mutex (its from). Thread 2 holds 0x8000 and wants 0x8040; thread 3 holds 0x8040 and wants 0x8000. That is a two-node cycle. __psynch_mutexwait is a kernel wait, not a spin.

An atomic counter starts at 9. Each of two threads checks whether it is below 10, then increments if so. Java uses separate get() and incrementAndGet() calls; C++ uses separate load() and fetch_add(1) calls. After joining both threads, which final-value and diagnostic pairs are possible in C++ under TSan? Select all that apply.Select all that apply
Why. If one thread increments before the other checks, the result is 10. If both check at 9, both increment and the result is 11. At least one sees 9 and increments, so 9 is impossible. All accesses to the counter are atomic, so neither outcome creates a data race on it. The bound violation is a logic race; use one locked check and increment, or a compare-and-set loop that retries the check.
From: ThreadSanitizer and other race detectors
A report says "Write of size 4 at X by thread T1" and then "Previous read of size 4 at X by main thread". What does "Previous" tell you?
Why. TSan detects the race when the second access happens and reports the first one from its shadow memory. Neither side is singled out as guilty: two unordered conflicting accesses are the race. Whether a mutex was held shows up separately, as "(mutexes: ...)".
From: ThreadSanitizer and other race detectors
Your test passes cleanly under TSan 100 times in a row. Which statement is true?
Why. TSan is a dynamic tool. It cannot check code that did not execute, and an unrelated lock taken in a lucky order can create a happens-before edge that hides a race in that run. Instrumentation gaps, suppressions and finite history can also hide an executed race. "Clean" is evidence, not proof; it does not establish either general race freedom or deadlock freedom.
From: ThreadSanitizer and other race detectors
Two threads perform instrumented writes to a shared plain int, 50 ms apart, without a happens-before edge. Assume TSan retains the earlier access and no suppression applies. What does it report?
Why. "At the same time" is not the definition of a data race. Without a happens-before edge the compiler and CPU may reorder or cache the accesses, and timing gaps are not guaranteed on another machine. TSan compares vector clocks, so it catches the pair as long as it still remembers the first access.
From: ThreadSanitizer and other race detectors
In a TSan report, the writer's stack is marked "(mutexes: write M0)" and the reader's stack has no mutex listed. What is the most likely bug?
Why. Using the same mutex around every access is the usual protection rule. An unlock and a later lock can also order accesses outside the critical sections, but the report says no observed ordering covers this pair. "Locking the writes and forgetting the reads" is one of the most common races in real code, and the mutex annotation on only one side is the giveaway.

Java onlyYou want to check whether two actors running x = 1; r1 = y; and y = 1; r2 = x; on plain fields initially zero can ever end with r1 == 0 and r2 == 0. Which Java tool is built for this?
Why. jcstress is OpenJDK's harness for exactly these small concurrency tests: it runs the actors concurrently in many configurations and reports how often each result appeared. javac has no sanitizer, and dumps or JFR do not observe memory-model outcomes. With fields initially zero, 0, 0 is allowed; it need not appear on every run. Store buffering is one mechanism: each thread can read before the other thread's write becomes visible. Neither a stack dump nor a JFR lock event enumerates these outcome pairs.

Assume independent runs, each with a fixed race probability of 1 in 10,000. You run the test 100 times. Roughly how likely are you to see it at least once?
Why. 1 - (1 - 1/10,000)^100 is about 0.01. You would need about 30,000 runs to see it 95 percent of the time, which is why good tests raise the chance per run (start gates, noise, more threads) instead of only adding runs. 63 percent is the answer for 10,000 runs.
From: Testing concurrent code
Why do stress tests park every thread on a latch and release them together?
Why. A start gate prevents the tested operations from beginning before release and encourages overlap. It neither chooses a deterministic schedule nor changes TSan's rules. The latch publishes actions before its release to awaiters; it does not order the workers' later operations with each other.
From: Testing concurrent code
A test runs 1,000 random transfers between 10 bank accounts on 16 threads. Which check after all threads join can expose a lost update that changes the total money?
Why. Conservation catches lost debits or credits that change the total. It does not catch every bug: compensating errors can preserve the sum, so also check individual balances and histories. Return values and exceptions look perfectly normal when an update is lost, and timing says nothing about correctness.

In the broken booth example, sold starts at 4 and the limit is 5. Exactly two workers each call the broken booking method once. After both join, which final counts can be printed? Select all that apply.Select all that apply
Why. If one worker increments before the other checks, only one booking succeeds and the count is 5. If both read 4 before either increments, both succeed and the count is 6. Java onlyA plain JUnit test, with no extension collecting uncaught exceptions, starts a worker thread that runs assertEquals(5, counter.get()), then joins it. The counter holds 4. What happens?
Why. Starting and joining a raw thread does not propagate its exception to the JUnit test method. An error in another thread goes to that thread's uncaught exception handler, which prints it. Bring results or failures back (a future, an AtomicReference<Throwable>) and assert in the test thread.
From: Testing concurrent code
A concurrent test fails about once in 300 CI runs. What is the best first step?
Why. An intermittent failure can reveal a product bug, an invalid test assumption or environmental pressure. Preserve diagnostics and reproduce it; retries alone do not distinguish those causes. First make it fail reliably, then read the seed, the history and the stacks. Raising timeouts helps only when the failure really is a too-tight timing assertion, which you learn by reproducing it.

A fixed job spends 5 percent of its one-worker time in serial work. Assuming ideal parallelism on 16 cores with no overhead, roughly what speedup do 16 workers give, and what is the most any number of threads can give?
Why. 1 / (0.05 + 0.95 / 16) is about 9.1, and 1 / 0.05 is 20. Even a small serial fraction costs a lot at 16 threads, which is why shrinking critical sections matters more than adding cores.
From: Performance: contention, Amdahl and profiling
Every request takes a global lock once and holds it for 40 microseconds. What upper bound on requests per second does that lock impose, regardless of the number of cores?
Why. One lock serves one holder at a time, so it allows at most 1 / 0.00004 = 25,000 acquisitions per second in total. Cores do not change that; only a shorter hold time, or splitting the lock, does. Actual throughput can be lower because of CPU limits, handoff gaps or other bottlenecks; waiting depends on arrival patterns and hold-time variance.
From: Performance: contention, Amdahl and profiling
A service's throughput is flat and its p99 is bad. A CPU flame graph shows nothing unusual and the CPUs are 30 percent busy. What should you look at next?
Why. A CPU profiler samples threads that are on a core. Threads blocked on a lock or parked on a pool are off the CPU, so parked waiting time is missing there. Spinning and CAS retries do consume CPU and can appear in the profile. Low CPU plus flat throughput is the classic signature of waiting: profile the waits (async-profiler -e lock or -e wall, JFR lock events, off-CPU profiling in C++).

A team replaces a mutex-protected counter with a correct increment CAS loop on one shared lock-free atomic, expecting a big win under 64 threads. Which statement is justified without benchmarking this change?
Why. The implementation and workload determine the winner. CAS is atomic, so a correct increment loop does not lose updates, but retries still cost time. A simple lock-free counter loop has no lock cycle; that does not prove arbitrary CAS-based code cannot deadlock or starve. Striping may help when relaxed live reads are acceptable.

A profile shows threads queued on one global lock that updates 20 independent metric counters. The report permits a non-atomic live snapshot. Which change most directly removes serialization on that global lock?
Why. The stated reporting contract permits distributing writes and summing later. This removes the global lock, though hot cells and aggregation still cost work. More threads, fair admission and spinning all retain one shared serialization point; fairness does not automatically cause a convoy.
