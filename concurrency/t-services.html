Concurrency in services

Server threading models, I/O models, pool sizing, queueing, back-pressure, timeouts, retries, circuit breakers, bulkheads and limiters.

1Coreserver-modelsthreads
Compare thread-per-request, a fixed thread pool and an event loop for a network server.
Model answer

Thread per request: each request or connection gets its own thread and plain blocking code. It is easy to write and debug. Each thread costs stack memory (Java's default on 64-bit Linux is 1 MB of reserved stack), creation time and scheduler work, so thousands are fine and hundreds of thousands are not.

Fixed pool plus a queue: threads are reused and concurrency is capped. With blocking I/O, every in-flight request still parks a pool thread, so the pool size caps in-flight requests (Little's law), and under overload the queue grows and latency with it.

Event loop: one thread per core runs non-blocking I/O through epoll or kqueue and dispatches callbacks. Few threads serve huge numbers of connections. The cost is a strict rule, never block the loop: one slow handler stalls every connection on that loop, so CPU-heavy or blocking work is handed off to a worker pool. Code is harder to follow.

Real servers mix them. Netty and nginx run event loops for I/O plus worker pools for blocking work. Java 21 virtual threads give you thread-per-request code with event-loop-like scalability for I/O-bound work, because a blocked virtual thread releases its carrier thread (unless it is pinned, see the last question).

Likely follow up: "Which would you pick for a chat server with 500,000 mostly idle connections?" An event loop, or virtual threads in Java; never one platform thread per connection.

2Coreio-modelsepoll
Blocking, non-blocking and multiplexed I/O: what is the difference, and what do select, poll and epoll do?
Model answer
  • Blocking: read sleeps until data arrives, so you need one thread per connection.
  • Non-blocking (O_NONBLOCK): read returns at once with EAGAIN when there is no data. On its own that only lets you spin, so you pair it with readiness notification.
  • Multiplexed: ask the kernel which of many descriptors are ready, then serve only those.

select passes fixed-size bitmaps (usually capped at 1024 descriptors) and scans all of them on every call. poll uses an array with no fixed cap but is still O(n) per call. epoll (Linux) registers interest once with epoll_ctl, and epoll_wait returns only the ready descriptors, so cost follows activity rather than connection count. kqueue is the BSD and macOS equivalent.

Level-triggered notification repeats while a descriptor stays readable. Edge-triggered notification fires only when its state changes, so you must read until EAGAIN, or you will never be told again and the connection stalls.

Completion-based I/O is the other model: submit the operation and get told when it is done (io_uring on Linux, IOCP on Windows). Java exposes readiness through NIO Selector (epoll on Linux) and completion through AsynchronousChannel. Standard C++ has no networking library yet; Asio is the common choice.

Likely follow up: "Does non-blocking I/O make the disk faster?" No. select and poll always report a regular file as ready, and epoll_ctl refuses regular files outright (EPERM), so a disk read still blocks. Real asynchronous file I/O needs io_uring or a thread pool.

3Corelittles-lawpool-sizingDatabricks
How many threads do you need for a service that makes blocking calls?
Model answer

Start with little's law: in-flight work equals arrival rate times time in the system. At 1,000 requests per second, each holding a thread for 200 ms, about 200 threads are busy on average. Add headroom for bursts.

From the CPU side, Brian Goetz's formula: threads ≈ cores × target CPU utilization × (1 + wait time / compute time). With 8 cores, 80 percent target, 190 ms of waiting and 10 ms of computing per request, that is 8 × 0.8 × 20 = 128 threads. For pure CPU work the ratio is near zero, so threads ≈ cores.

Then cap it by what is downstream: 200 threads in front of a 20-connection database pool means 180 threads queue on the pool. Memory per thread, file descriptors and per-host politeness limits cap it too. Treat the formula as a starting point and tune with measurements of latency percentiles and CPU.

Likely follow up: "The dependency slows from 200 ms to 2 s. What happens?" At the same arrival rate, in-flight work grows tenfold to about 2,000. The pool saturates, the queue grows and latency explodes. Timeouts, a bulkhead around that dependency, and load shedding keep the rest of the service alive.

4Seniorqueueingutilization
Why does latency explode as utilization approaches 100 percent?
Model answer

For the simplest queue, M/M/1 (random arrivals, random service times, one server) with mean service time S and utilization ρ, the mean time in the system is S / (1 minus ρ) and the mean wait in the queue is ρ × S / (1 minus ρ). At 50 percent utilization a request spends 2S in the system, at 80 percent 5S, at 90 percent 10S, at 99 percent 100S.

The intuition: arrivals come in random bursts. At low utilization the server has idle time to absorb a burst; near 100 percent it has none, so every burst leaves a queue that never fully drains. The last 10 percent of utilization costs more latency than the first 90.

Variability makes it worse. Kingman's approximation for a general single-server queue multiplies the wait by the average of the squared coefficients of variation of arrivals and service times, so bursty traffic or a heavy-tailed service time lengthens queues at the same utilization.

In practice: keep latency-sensitive services at roughly 60 to 80 percent utilization (a rule of thumb, not a law), bound the queues, and use load shedding before the knee.

Likely follow up: "With N servers?" Pooling helps a lot: an M/M/c system at the same per-server utilization queues far less, which is one reason a shared pool beats N separate single-thread queues.

5Seniorbackpressureload-sheddingDatabricks
What is back-pressure, and what policies do you have when a queue fills up?
Model answer

back-pressure means a slow consumer's limit propagates upstream, so producers slow down instead of memory growing until the process dies. An unbounded queue has no back-pressure: it hides overload until it runs out of memory.

When a bounded queue is full, the options are:

  • Block the producer, with a timeout. This is natural back-pressure, and it propagates to whoever calls the producer.
  • Reject with an error: RejectedExecutionException, HTTP 429 or 503. The caller learns immediately and can back off.
  • Drop: the newest item, the oldest (keeps data fresh, as for metrics), a sample, or by priority (shed DEBUG logs and keep ERROR).
  • Caller runs: the producer does the work itself, which slows it down naturally (ThreadPoolExecutor.CallerRunsPolicy).
  • Spill to disk: bounded memory, but more latency and more code.
  • Credit or pull based: the consumer grants credit (Reactive Streams request(n), HTTP/2 and gRPC flow-control windows, TCP's receive window).

Choose by the contract. For a durable log writer, an event that was acknowledged must never be dropped, so block with a bound or reject before acknowledging. For telemetry, dropping is fine. Whatever you choose, export queue depth and rejection counts as metrics.

Likely follow up: "The producers are request threads. Is blocking them fine?" Only briefly: blocked request threads pile up upstream. Bound the wait and return 503 quickly.

6Corethread-pool-executorrejectionjava
How does ThreadPoolExecutor decide between queueing, adding a thread and rejecting? What are the rejection policies?
Model answer

For each execute(task):

  1. If fewer than corePoolSize threads are running, start a new thread with this task.
  2. Otherwise offer the task to the queue. If accepted, it waits there.
  3. If the queue refuses and fewer than maximumPoolSize threads run, start a new thread.
  4. Otherwise reject through the RejectedExecutionHandler.

The trap: with an unbounded LinkedBlockingQueue, step 2 never fails, so the pool never grows past the core size and the queue grows without limit. Executors.newFixedThreadPool is built exactly that way. newCachedThreadPool is the opposite extreme: a SynchronousQueue that holds nothing and a maximum of Integer.MAX_VALUE, so load turns directly into threads.

Built-in policies: AbortPolicy (the default, throws RejectedExecutionException), CallerRunsPolicy (the submitting thread runs the task, which is back-pressure), DiscardPolicy (silently drops: dangerous) and DiscardOldestPolicy (drops the head of the queue and retries). Tasks submitted after shutdown are rejected too.

A sane production setup: a bounded ArrayBlockingQueue, a maximum above the core size, AbortPolicy or CallerRunsPolicy, named threads, and metrics on queue depth. keepAliveTime retires threads above the core size; allowCoreThreadTimeOut(true) retires core threads too.

Likely follow up: "Why does a task seem to run on the caller's thread sometimes?" CallerRunsPolicy is active and the pool was saturated.

7Seniortimeoutsdeadlines
Why must every remote call have a timeout, and how do you choose and propagate it?
Model answer

Without a timeout, one hung dependency holds your thread or connection forever. Under load, every thread ends up stuck on it and your service is down too: a cascading failure caused by the slowest thing you call.

Choose the value from the dependency's latency distribution, a little above its p99 or p99.9 under normal load, and make sure it fits inside your own caller's budget. Use separate connect and request timeouts.

Propagate a deadline, not a timeout. Pass the absolute deadline (or the remaining budget) down the call chain, as gRPC does; each hop uses the smaller of its own limit and what remains, and refuses to start work that cannot finish in time. With fixed 1-second timeouts at three layers, the outer layer gives up while the inner ones keep working for nobody.

A timeout does not stop the work. The callee may still complete, so before retrying, the operation must be idempotent or checkable, and you should cancel downstream work: Future.cancel(true), cancellation of the request context.

API notes: Java has CompletableFuture.orTimeout and completeOnTimeout (Java 9 and later) and HttpRequest.Builder.timeout; C++ has future::wait_for and condition_variable::wait_until. Always measure with a monotonic clock (System.nanoTime, std::chrono::steady_clock), never the wall clock, which can jump.

Likely follow up: "What should the client do after a timeout?" Treat the outcome as unknown: retry only with an idempotency key, or query the status before trying again.

8Seniorretriesbackoffidempotency
When is it safe to retry, and how can retries make an outage worse?
Model answer

Retry only when the operation is idempotent (a read, a full-state PUT, or a request carrying an idempotency key), or when you know it never ran, such as a refused connection. A plain POST that timed out may already have succeeded. Retry only transient failures: timeouts, 503, throttling with a Retry-After. Never retry validation errors.

Space retries with exponential backoff and jitter, for example full jitter: sleep a random time between zero and the smaller of a cap and base × 2 to the power of the attempt number. Without jitter, every client that failed together retries together, in synchronized waves.

Retries multiply across layers. If each of three layers makes up to 4 attempts (1 plus 3 retries), a failing bottom service can receive 4 × 4 × 4 = 64 times the original load, precisely when it is struggling. The mitigations:

  • Retry at one layer only, usually the outermost client.
  • Use a retry budget, for example retries capped at about 10 percent of requests (a rule of thumb).
  • Put a circuit breaker in front of the failing dependency.
  • Honor Retry-After and server overload signals.

Likely follow up: "What are hedged requests?" Send a duplicate to another replica if the first has not answered by about the p95 latency, and take whichever answers first. It cuts tail latency, but needs idempotent operations and a cap on how many requests may be hedged.

9Seniorcircuit-breakerUberDatabricks
Implement a thread-safe circuit breaker. What are its states, and where are the races?
Model answer

A circuit breaker has three states. Closed: calls pass and failures are counted. Open: calls fail fast for a cooldown. Half-open: a limited number of trial calls go through; success closes the breaker, failure reopens it. The breaker's own work is tiny next to a remote call, so one lock around a small state machine is the clearest correct answer.

The races worth naming: in half-open, every thread could believe it is the trial and stampede the recovering dependency, which probeInFlight prevents. A late result from a call admitted before the breaker opened can be mistaken for the probe's result; the fix is a generation number returned by tryAcquire and checked on completion. And a probe that hangs keeps the breaker half-open forever, so the probe needs a timeout that reports failure.

Likely follow up: "Make it lock free." Keep an immutable state record in an AtomicReference and move between states with compareAndSet, so exactly one thread wins each transition.

10Seniorbulkheadisolation
What is a bulkhead, and how would you implement one?
Model answer

Bulkheads are the watertight compartments in a ship's hull. In a service, they isolate resources per dependency or per tenant, so one failing part cannot drain the shared pool. Without them, a service that calls payments and recommendations through one 200-thread pool goes fully down when recommendations hangs: all 200 threads end up waiting on it, and payments fail too. With recommendations capped at 40 concurrent calls, only that feature degrades.

Two implementations:

  • A separate thread pool per dependency, each with a bounded queue. Strong isolation, with timeouts enforced from the outside, but you pay a thread handoff per call.
  • A semaphore per dependency, which limits concurrent calls on the caller's own thread. Cheaper, and fail fast when no permit arrives in time.

In C++20 the same shape uses std::counting_semaphore with try_acquire_for and an RAII guard that releases. Size each bulkhead by Little's law for that dependency (normal rate × normal latency) plus headroom. Per-tenant bulkheads stop one noisy customer from starving the rest.

Likely follow up: "Bulkhead or circuit breaker?" Both. The bulkhead limits the damage while a dependency is slow, and the breaker stops calling it once it is clearly failing.

11Seniorrate-limitconcurrency-limit
Rate limit versus concurrency limit: what does each protect, and when do you need which?
Model answer

A rate limit caps requests per unit of time, usually with a token bucket. It enforces quotas and fairness among clients and stops abuse. It does not bound the work in flight if requests become slow.

A concurrency limit caps requests in flight, usually with a semaphore. It bounds what actually runs out: threads, connections, memory, downstream capacity.

Little's law links them: in-flight = rate × latency. When a dependency slows down, a fixed rate limit keeps admitting the same rate, so in-flight work grows without bound and the service falls over. A concurrency limit automatically lowers throughput instead, because admissions wait for completions. So protect your own resources with concurrency limits, and enforce client contracts with rate limits.

The best concurrency limits adapt. Borrowing from TCP congestion control, raise the limit while latency stays healthy and cut it when latency rises or errors appear; Netflix's open-source concurrency-limits library works this way.

Likely follow up: "Which kind is a database connection pool?" A concurrency limit: its size is the maximum in flight, and requests beyond it wait or fail.

12Seniorrate-limitertoken-bucketRubrikAtlassian
Implement a thread-safe token bucket. Would you refill with a background thread or lazily?
Model answer

Lazily. On each request, the token bucket computes how many tokens accumulated since the last call, caps them at the capacity, then spends one, all under one lock. A background refill thread per bucket does not scale to millions of users, refills in coarse jumps and needs its own lifecycle. Use a monotonic clock.

For per-user limits, keep a concurrent map from user to bucket (computeIfAbsent in Java), and evict idle buckets, because a full idle bucket is the same as a missing one. The refill and the spend must be one atomic step; splitting them lets two threads spend the same token.

Likely follow up: "Lock free?" Pack the token count and timestamp into one immutable object in an AtomicReference and CAS a new one, or keep a single "time at which the next token is free" in an AtomicLong and advance it with compareAndSet (the generic cell rate algorithm, GCRA).

13Seniorrate-limitersliding-windowcheck-then-actLinkedIn
In a sliding window rate limiter, two threads both read 99 of 100 and both get in. Walk through the race and fix it.
Model answer

The check and the increment must be one atomic step per key. The options:

  • A lock per user window (synchronized on that user's window object), covering eviction of old timestamps, the check and the add.
  • A CAS loop on a counter: read c; if c is at the limit, reject; otherwise compareAndSet(c, c + 1) and retry on failure.
  • ConcurrentHashMap.compute(user, ...), which runs the whole update atomically for that key.

A sliding log (a deque of timestamps) needs the lock, because it touches several fields. The sliding window counter approximation (the current window's count plus the previous window's count weighted by overlap) needs only two counters per key.

The same race reappears across servers: two gateways read the same count from a shared store. Then the atomic step must happen inside the store, for example a Redis Lua script that checks and increments in one call.

Likely follow up: "Why does the race not show in your unit test?" A single-threaded test cannot interleave. Write a stress test that starts 200 threads behind a latch against a limit of 100 and asserts exactly 100 successes.

14Seniorhead-of-linescheduling
What is head-of-line blocking in a worker pool, and how do you avoid it?
Model answer

In a single FIFO queue, a handful of slow tasks, such as big reports or one heavy tenant, can occupy every worker, and cheap requests that need milliseconds wait behind them for seconds. Average throughput looks fine while the latency of the fast class explodes. That is head-of-line blocking.

Ways out:

  • Separate lanes: different queues or pools for fast and slow work, or per tenant, so slow work can only occupy its own workers.
  • Priority with aging: cheap or interactive work first, while waiting time raises the priority of the rest.
  • Route by size: estimate cost up front and send big jobs to a batch pool.
  • Bound occupancy: per-task timeouts, and split big jobs into chunks that go back into the queue, so a worker is never held for long.
  • Weighted fair queuing across tenants: each tenant gets a share of the workers.

The same idea appears in networking. HTTP/1.1 pipelining suffers head-of-line blocking per connection; HTTP/2 multiplexes streams but still shares one TCP byte stream, so a lost packet stalls every stream; QUIC (under HTTP/3) removes that by giving each stream independent delivery.

Likely follow up: "How do you detect it?" Per-class latency percentiles and queue wait time, not just averages: the fast class's p99 queue wait jumps while its service time stays flat.

15Seniorshutdowndraining
How do you shut down a service instance without dropping requests?
Model answer

A graceful shutdown on SIGTERM runs in this order:

  1. Stop receiving traffic: fail the readiness check or deregister from the load balancer, and wait long enough for it to notice.
  2. Stop accepting new connections and requests.
  3. Drain in-flight work against a deadline: finish requests, flush internal queues, close idle keep-alive connections.
  4. Stop background consumers cleanly: commit offsets, finish or hand back leased jobs.
  5. Flush logs and metrics, then shut pools down with shutdown followed by awaitTermination.
  6. At the deadline, force it: shutdownNow, cancel what remains, and exit.

Orchestrators give you a fixed window: in Kubernetes, terminationGracePeriodSeconds (30 seconds by default), after which the process is killed. A pre-stop hook can cover the load balancer delay in step 1.

Language hooks: Java runs Runtime.addShutdownHook threads on SIGTERM. In C++, the signal handler only sets a flag (a volatile std::sig_atomic_t or a lock-free std::atomic<bool>) or writes to a self-pipe; the main loop notices and runs the steps above. In a multithreaded server the cleaner option is to block SIGTERM in every thread and receive it in one dedicated thread with sigwait (or signalfd on Linux), where ordinary code is safe.

Likely follow up: "Why so little in the signal handler?" Only async-signal-safe functions may run there: no mutexes, no malloc, no logging libraries. Taking a lock that the interrupted thread already holds would deadlock the process.

16Stretchvirtual-threadscoroutinesjavacpp
Do virtual threads or coroutines make thread pools and async code obsolete?
Model answer

They change the cost of blocking for I/O-bound work. A Java 21 virtual thread that blocks on I/O unmounts and frees its carrier thread, so plain thread-per-request code can hold hundreds of thousands of concurrent requests.

What they do not change:

  • CPU-bound work is still limited by cores.
  • Limits still matter: a million virtual threads can still overwhelm a database with 50 connections, so you need semaphores or bulkheads.
  • Races are exactly the same; shared state still needs synchronization.
  • In JDK 21 to 23, blocking inside synchronized pins the carrier thread (fixed in JDK 24), and thread-locals multiply by the number of threads.

Thread pools remain the right tool for CPU-bound work and for bounding resources. Do not pool virtual threads: create one per task and limit concurrency with a semaphore.

C++20 coroutines are a language mechanism, not a scheduler. They are stackless and need a library (Asio, or a hand-written executor) to resume them. They make asynchronous code read sequentially, but a blocking call inside a coroutine still blocks the thread running it.

Likely follow up: "When would you still choose an event loop over virtual threads?" When you need the lowest per-connection overhead and latency control, or the ecosystem is already reactive; and in C++, where there are no virtual threads.
