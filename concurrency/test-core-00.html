In "A deadlock on purpose", thread a locks left then right, and thread b locks right then left. Which single change guarantees the program can never deadlock?
Why. A deadlock needs a cycle: each thread holds one lock and waits for a lock another thread holds. If every thread takes its locks in one global order, no cycle can form. Changing the nap does not remove the cycle: a longer nap in b still leaves each thread holding one lock, and removing the nap only makes the unlucky timing rarer, so the bug survives and comes back under load. Reentrancy lets a thread take again a lock it already holds; here each thread wants the lock the other holds, so it changes nothing (Java's synchronized is already reentrant, and the demo still hangs). In C++, a std::scoped_lock that takes both mutexes in one call is the other standard fix.

A LinkedIn style follow up: "Walk me through the race in this rate limiter." count is an atomic integer (AtomicInteger in Java, std::atomic<int> in C++) and limit is 100. What is the race?
Why. Atomics make each single call indivisible, but nothing stops a second thread from running its get between your get and your increment. That gap is the 99 of 100 race. Fix it by making check and increment one step: a compare-and-set loop that only writes c + 1 if the value is still c and c is below the limit, or a lock around both. Atomics do guarantee visibility, and an atomic integer is lock-free on every mainstream platform, so there is no lock to deadlock on: the other two options are wrong. Interviewers ask this exact walk-through because naming the interleaving is the reasoning they grade.
