Classes, constructors, destructors and RAII

Constructors, initializer lists, destructors, the rules of zero, three and five, and RAII: why every lock in modern C++ is released by a destructor.

Asked atAmazonBloomberg
Before this:Object lifetime, the stack and the heap

Every lock you take in modern C++ is released by a destructor. RAII is not a style preference: it is the reason C++ locking code can stay short and still be correct when an early return or an exception cuts a function off halfway.

In plain words

Picture a library whose exit gate checks every book back in automatically. However you leave, through the front door, through the fire exit, or carried out on a stretcher, the gate returns the book for you. You cannot forget to return it, because forgetting is not one of the options.

That is RAII, resource acquisition is initialization. You acquire a resource (memory, a file, a lock, a thread) in an object's constructor, and the object's destructor releases it. C++ runs destructors for fully constructed local objects on normal scope exit and during stack unwinding, so early returns and unwinding release the resource.

Why this matters for concurrency

  • std::lock_guard, std::unique_lock, std::scoped_lock and std::jthread are RAII types. A hand-written m.lock() and m.unlock() leaks the lock on the first early return or exception, and every other thread then blocks forever.
  • std::thread's destructor calls std::terminate if you never joined or detached it: the one thread type that punishes you instead of cleaning up. std::jthread fixes that.
  • A class that holds a std::mutex cannot be copied or moved by default, because the mutex cannot. The rules of three and five tell you what to write when you do need copies.
  • RAII releases the lock when an exception flies, but it does not undo half-finished changes to the data. Exception safety is a separate design decision.
  • An Amazon online assessment question reported in 2025 showed a C-style container guarded by one mutex and asked for every problem in it, with deadlock, resource leak and memory corruption among the options. The worked example below has the same shape.

Constructors and member initializer lists

A constructor's job is to establish the object's invariant before anybody can use it. Members are initialized in the member initializer list, the part after the colon; by the time the constructor body runs, every member already exists.

  • Initialize in the list, not by assignment in the body. Assignment in the body means "default construct, then overwrite", which costs twice and is impossible for const members, references, and types with no default constructor.
  • Members are always initialized in declaration order, whatever order you write in the list. -Wall warns when the two orders differ. That is why the previous lesson could say "declare the thread last" and have it mean something.
  • Mark single-argument constructors explicit, so a std::string passed where an Account is expected (void audit(const Account&) called as audit(name)) does not silently become a brand new account.

Destructors: cleanup on scope exit

A destructor runs automatically: at the closing brace for a local, during stack unwinding when an exception passes through, when the owning smart pointer or container destroys a heap object, and after main for statics. The order is fixed: the destructor body first, then the members in reverse declaration order, then base classes.

  • Since C++11, a destructor without an explicit exception specification is normally noexcept, unless a base or member has a potentially throwing destructor. Escaping a noexcept destructor calls std::terminate; escaping a destructor invoked during exception unwinding also terminates. Design resource cleanup so it never throws.
  • A class meant to be deleted through a pointer to its base class needs a virtual destructor in the base. Without it the delete is undefined behavior; typically only the base part is destroyed.
  • A destructor may block. std::jthread's destructor joins, so destroying one while holding a lock the worker needs is a deadlock.

RAII: acquire in the constructor, release in the destructor

RAII is not a guarantee of cleanup during abrupt termination. std::abort and std::_Exit do not unwind local scopes, and std::exit skips automatic local destructors. When an exception has no matching handler, unwinding before std::terminate is implementation-defined.

A guard needs a name: std::lock_guard<std::mutex> guard(m_);. To end a guard early, give it its own block with braces instead of unlocking by hand.

std::thread versus std::jthread

std::thread is a handle that does not clean up after itself. If its destructor finds the thread still joinable, it calls std::terminate, and the process dies. The committee chose that on purpose: joining implicitly could hang the program, and detaching implicitly could leave a thread using destroyed locals. The trap is that an exception between starting the thread and joining it skips the join, and the unwinding destructor terminates the program.

A std::jthread is the RAII version. Its destructor calls request_stop() and then join. If the thread function accepts a std::stop_token, it can notice the request and finish early:

The rules of zero, three and five

Five special member functions decide what happens when an object is copied, moved and destroyed: the destructor, the copy constructor, copy assignment, the move constructor and move assignment.

  • Rule of three (classic C++): if a class needs a custom destructor, copy constructor or copy assignment, it almost certainly needs all three, because it manages a resource by hand.
  • Rule of five (C++11): the same, plus the two move operations.
  • rule of zero: better than both. Build classes from members that already manage themselves (std::string, std::vector, std::unique_ptr, guards) and write none of the five. The compiler-generated versions are then correct.

What the compiler generates depends on what you declared, and the table hides a trap in its second row:

You declareImplicit copy operationsImplicit move operations
None of the fiveGeneratedGenerated
Only a destructorStill generated (deprecated)Not declared: a "move" silently copies
A copy constructor or copy assignmentThe other one generated (deprecated)Not declared: moves copy
A move constructor or move assignmentDeletedThe other one not declared

So adding an empty ~Widget() {} "for logging" quietly turns every move of a Widget into a copy. If you must declare one special member, declare all five, using = default and = delete to say what you mean.

A class that holds a mutex

std::mutex can be neither copied nor moved: other threads may be blocked on it, at its address. So any class with a mutex member has deleted copy and move operations. For an object shared between threads that is usually exactly right. When you do want copies, say a snapshot of a thread-safe container, write the copy operations yourself: lock the source, copy the data, and let the new object have its own fresh mutex. Assignment must lock both objects, without deadlock, and must not lock one mutex twice.

The first number depends on timing, but it is always a consistent count, never a torn vector. Because this class declares copy operations, it gets no implicit moves, so std::move(tally) copies. That is fine here; if moves mattered you would declare them too, locking the source.

Exception safety: RAII releases, it does not roll back

exception safety comes in three levels. The basic guarantee: after an exception nothing leaks and every invariant still holds, though the state may have changed. The strong guarantee: the operation either completes or has no effect at all. The nothrow guarantee: it cannot fail. RAII hands you "nothing leaks" for free. It does not hand you invariants.

That matters more with threads, because releasing a lock publishes whatever state you left behind. If an exception escapes halfway through updating two fields under a lock, the guard unlocks during unwinding and the next thread walks into the half-updated object.

The recipe: do everything that can throw first, then commit with operations that cannot. A second form of the same idea also shortens critical sections: build the new state outside the lock, then swap it in under the lock with a swap that cannot throw.

Common mistakes

  • Calling lock() and unlock() by hand. Every early return and exception becomes a leaked lock. Use a guard.
  • A guard without a name. It unlocks at the end of the statement, or declares a new variable and locks nothing.
  • A std::thread that is not joined on every path, including the path where an exception is thrown. Use std::jthread.
  • Throwing from a destructor. It terminates the program if it happens during unwinding, and by default it terminates anyway because destructors are noexcept.
  • A custom destructor with default copies for a class that owns a raw handle: two copies, two releases. Follow the rule of zero, or write all five.
  • A hand-written copy constructor that does not lock the source. It copies while another thread writes: a data race.
  • Doing slow work while the guard is alive. Logging, I/O and callbacks inside the lock stretch the critical section. End the guard early with an inner block.
  • Assuming RAII rolls back state. It releases resources; your code must keep the invariants.

In the interview

RAII itself is asked by name: a 2020 Bloomberg C++ candidate was questioned on RAII alongside semaphores versus mutexes. Expect "why lock_guard instead of calling lock and unlock?", "what happens if an exception is thrown while you hold the lock?", "difference between lock_guard, unique_lock and scoped_lock?", and "what does std::thread's destructor do?". In review and debugging formats, such as the Amazon assessment item above and Rubrik's debugging round, you are handed manual locking and asked to find every way it fails.

I use RAII guards so the unlock is tied to scope exit: early returns and exceptions all release the lock. lock_guard for a single mutex held for the whole scope, unique_lock when I need to unlock early or wait on a condition variable, scoped_lock for two or more mutexes because it avoids lock order deadlocks.
If an exception is thrown under a guard, the destructor releases the lock during unwinding. That makes the half-done state visible to the next thread, so I structure updates to do everything that can throw first and commit with operations that cannot throw.

Follow ups: "Can you return early from inside a lock_guard scope?" (yes, that is the point); "Why is std::mutex not copyable?" (threads may be waiting on it at its address, and copying a lock's state makes no sense); "Why not make grow lock recursively?" (recursive mutexes hide the fact that an invariant may be broken when the inner call runs; prefer a locked helper).

Senior depth

Starting threads in constructors. A thread started in a base class constructor that calls a virtual function may get the base version (the derived part does not exist yet) or the derived one, depending on timing, because the object's dynamic type changes while the thread runs; that switch is itself a data race on the object, and a pure virtual base turns it into a crash. Anything the thread touches that is declared later is not constructed either. Start threads in the most derived class, declare the thread member last, or use a separate start() step.

Destructors that block can deadlock. A std::jthread destructor joins. Destroying it while holding a mutex the worker needs to finish means the join never returns. And a thread that destroys its own jthread would be joining itself, which the library reports as an error inside a noexcept destructor, so the program terminates.

Copy and swap gives assignment the strong guarantee: take the parameter by value (the copy happens first and may throw), then swap members with operations that cannot throw. For thread-safe classes it also keeps the locked part of assignment tiny.

Under the hood

Mainstream compilers implement exceptions with tables rather than extra code on the normal path. When an exception is thrown, the runtime walks the stack frame by frame and, for each one, runs a small cleanup block that the compiler generated to destroy the live locals of that frame, guards included, before continuing to the matching catch. This stack unwinding is why a guard's destructor runs even though no line of your code calls it.

Key takeaways

  • Initialize members in the initializer list; they are built in declaration order, whatever the list says.
  • RAII ties a resource to a scope: the destructor releases it on normal exit and during stack unwinding, including early returns and handled exceptions. Every C++ lock should be held by a named guard.
  • std::thread terminates the program if destroyed while joinable; std::jthread requests a stop and joins.
  • Prefer the rule of zero. Declaring only a destructor silently turns moves into copies. A mutex member deletes copying and moving unless you write them, locking the source.
  • RAII releases locks during exceptions but does not restore invariants: do the throwing work first, then commit with operations that cannot throw.

Inside a std::lock_guard scope, a function updates a_, then throws before updating b_, where a_ and b_ must always agree. What do other threads see?
Why. RAII guarantees the unlock, not a rollback. Releasing the lock publishes the half-done state. Do the work that can throw before changing shared state, or undo partial changes in a catch block before rethrowing.
class Buffer { std::vector<char> data_; public: ~Buffer() { std::puts("freed"); } };. What does Buffer b2 = std::move(b1); do?
Why. A user-declared destructor suppresses the implicit move constructor and move assignment, while the copy operations are still generated (a deprecated rule kept for old code). The rvalue then binds to the copy constructor, so the "move" copies the whole vector. Declare Buffer(Buffer&&) = default; and friends, or drop the destructor.
class Counter { std::mutex m_; long n_ = 0; /* methods */ };. What does Counter c2 = c1; do?
Why. std::mutex has deleted copy and move operations, so every class containing one gets deleted copy and move operations too. If you want copies, write the copy constructor: lock the source's mutex, copy n_, and let the new object's mutex be default constructed.
class Range { int size_; int start_; public: Range(int s) : start_(s), size_(start_ + 10) {} };. What is size_ after Range r(5);?
Why. Members are initialized in declaration order, not in the order of the initializer list. size_ comes first and reads an uninitialized start_, which is undefined behavior. -Wall warns that the list order does not match the declaration order.
A std::jthread object goes out of scope while its thread is still running. What does its destructor do?
Why. That is the point of std::jthread: request_stop() then join(). The thread is not killed; if it ignores its stop token, the join simply waits for it to finish. C++ has no safe way to kill a thread from outside.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a thread-safe Inventory with add(item, qty), remove(item, qty) that throws std::invalid_argument when there is not enough stock, and count(item). Use RAII, and say what an exception does to the lock and to the data.
Model answer

Every method holds a named std::lock_guard, so the mutex is released on every exit, including the throw in remove. The data stays consistent because remove checks first and throws before changing anything, and the only change, it->second -= qty, cannot throw: that is the strong guarantee. count takes the same lock as the writers, because reading without it would race with add. It uses find rather than operator[], which would insert a zero entry and could not be called from a const method.

Debug
A teammate's Cache has std::string get(int key) that calls m_.lock(), returns "" early when the key is missing, and otherwise unlocks and returns the value; and void put(int key, std::string v) that locks, calls evict() (which also locks m_) when full, inserts, and unlocks. List every problem and the fix.
Model answer

First, get returns early without unlocking, so after one miss the mutex stays locked and every later call blocks forever. Second, put calls evict while holding m_, and evict locks m_ again; std::mutex is not recursive, so that is undefined behavior and in practice a self-deadlock. Third, both functions can throw between lock and unlock (allocating the string copy, inserting into the map), which leaks the lock. Fourth, "" doubles as a real value and as "missing".

Fix: a named std::lock_guard in every public method, so every exit unlocks; split eviction into a private evict_locked() that documents "caller holds m_" and is called from put, with a public evict() that takes the guard and calls the helper; and return std::optional<std::string> from get. Then rerun the tests under stress and under ThreadSanitizer. Do not count on a sanitizer to find the self-deadlock for you: the second lock() on the same thread usually just hangs, and a stack dump showing put calling evict, which is blocked in m_.lock(), is how you recognise it.

Explain
Explain the rules of zero, three and five, and what a std::mutex member does to a class's copy and move operations.
Model answer

The five special members are the destructor, copy constructor, copy assignment, move constructor and move assignment. The rule of three says that if you need a custom destructor or copy operation, you are managing a resource by hand and need all three; C++11 made it five by adding the moves. The rule of zero says the best class needs none: hold resources in members that manage themselves, like std::vector, std::string, std::unique_ptr and lock guards, and the generated operations are correct. A trap: declaring only a destructor suppresses the implicit moves, so moves silently become copies.

A std::mutex cannot be copied or moved, so a class containing one gets deleted copy and move operations. For an object shared between threads that is usually what I want. If I need copies, I write the copy constructor to lock the source and copy the data, giving the new object its own mutex, and the assignment operator to check for self-assignment and lock both mutexes with std::scoped_lock so two concurrent assignments in opposite directions cannot deadlock.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"A function holds a lock_guard, updates one field, and throws before updating a second field that must agree with it. Has RAII made this safe?"
What a strong answer covers
  • RAII releases the mutex during unwinding but does not restore the two-field invariant
  • The next thread taking the mutex can observe the partial update
  • The basic exception guarantee preserves invariants; the strong guarantee leaves the logical state unchanged on failure
  • Perform throwing work before a nonthrowing commit, or roll back while still holding the lock
  • Preparation outside the lock requires revalidation if it depends on mutable shared state
How a senior would say it
RAII has made lock cleanup safe, but it has not made the update safe. When the exception unwinds this scope, the guard releases the mutex. The next thread can acquire it and observe the first field changed while the second still has its old value. If those fields must agree, the object has lost its invariant. The basic exception guarantee requires invariants to survive failure. The strong guarantee goes further and leaves the logical state unchanged. I would arrange the operation so everything that can throw happens before a commit that cannot throw. For example, prepare a new profile name and tags, then swap both into place under the same lock. If I must change shared state before a later step can fail, I need a reliable rollback before releasing the lock. Preparing outside the lock can reduce contention, but if that preparation depends on current shared state, I must revalidate it under the lock. My review therefore checks both resource cleanup and the state another thread can observe after failure.

Likely follow up: How would you test that the invariant survives an allocation failure in the second update?

Out loudabout 60 s
"You are implementing a queue and a transfer between two accounts. How do you choose among lock_guard, unique_lock and scoped_lock?"
What a strong answer covers
  • Use a named lock_guard for one mutex held for the whole scope
  • Use unique_lock for condition variable waiting or controlled unlock and relock
  • Use C++17 scoped_lock to acquire multiple distinct mutexes with deadlock avoidance
  • Handle a transfer to the same account before attempting to lock both mutexes
  • An unnamed temporary guard expires at the semicolon and protects no following statement
How a senior would say it
I choose the guard according to the operation. For a single mutex held until scope exit, I use a named lock_guard. It is the simplest ownership model and releases the mutex on return or during unwinding. In a blocking queue, I use unique_lock because the condition variable must release the mutex while waiting and reacquire it before checking the predicate again. It also supports an explicit unlock and relock when the algorithm needs that. For a transfer between two different accounts, I use C++17 scoped_lock with both mutexes, so acquisition uses deadlock avoidance. I handle a transfer to the same account first, because passing the same nonrecursive mutex twice is invalid. In each case the guard needs a name. A temporary guard dies at its semicolon, leaving the next statement unprotected. The guard's scope should cover the entire invariant update and no unrelated slow work.

Likely follow up: What can still deadlock if code under those guards calls a helper that locks one of the same mutexes?

Out loudabout 75 s
"A class with a mutex no longer copies. We need a snapshot while another thread updates it. How would you design copying and assignment?"
What a strong answer covers
  • A mutex is neither copyable nor movable, so default memberwise copying is deleted
  • If copying is required, give the destination a fresh mutex and copy data while holding the source mutex
  • Assignment checks for self-assignment and locks both objects with scoped_lock
  • Locking both objects together avoids deadlock between assignments in opposite directions
  • Preserve invariants if copying throws, and state that explicit copy operations suppress implicit moves
How a senior would say it
I would give each object its own mutex and copy only the protected data. A mutex cannot be copied or moved, so the compiler correctly rejects default memberwise copying. If the API only needs snapshots, returning a separate value object is often simpler. If the class itself must be copyable, its copy constructor can default construct a fresh mutex, lock the source, and copy the data while that lock is held. The destination is not yet published, so the source lock is the one that matters. Assignment is different because both objects already exist. I would first handle self-assignment, then lock both mutexes with scoped_lock. That avoids locking one mutex twice and avoids a deadlock when two threads assign in opposite directions. I would prepare any throwing copy before committing, or otherwise preserve the destination's invariants on failure. Finally, declaring copy operations suppresses implicit moves. I would state that policy explicitly rather than assume the compiler supplies a cheap move. The snapshot represents one protected moment; it is independent of later updates.

Likely follow up: If you add a destructor only for logging, how can that change move behavior for a class containing a vector?
