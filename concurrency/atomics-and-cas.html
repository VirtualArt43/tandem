Atomic variables and compare-and-swap

What the atomic classes and std::atomic give you, what compare-and-swap does inside the CPU, and what each atomic operation really costs.

Asked atRubrikDatabricks
Before this:The lost update: read, modify, writevolatile in Java, std::atomic in C++

Nearly every lock, concurrent queue and lock-free structure you will meet is built on one hardware idea: change a value only if it still holds what you saw. Interviewers ask how that works, and senior ones keep asking until you reach the cache line.

In plain words

Picture a shared whiteboard in an office with one number on it, the count of laptops left in the store room. The office has a strict rule: you may change the number only by saying out loud what you believe it says. "If it says 7, make it 6." If you are right, the clerk rubs it out and writes 6. If someone took a laptop a moment ago and it now says 6, the clerk refuses and tells you "it says 6 now", and you decide again with the new number.

That rule is compare-and-swap. Nobody ever writes a number based on an old reading, so no update is ever lost, and nobody had to lock the whiteboard. The price is that you sometimes have to try again.

What an atomic variable gives you

An atomic variable is a variable whose operations cannot be split by another thread. You met the problem it solves in the lost update: count += 1 is a read-modify-write of three steps, and another thread can slip in between them. An atomic variable gives you three guarantees:

  1. Indivisibility. Each operation, including a read-modify-write like increment, happens as one step. No thread ever sees it half done.
  2. Visibility and ordering. A write to an atomic becomes visible to other threads, and (with the default ordering) a thread that reads the new value also sees every write the writer made before it. That read creates a happens-before edge, which plain fields do not.
  3. No data race. In C++, two threads touching the same std::atomic is never a data race, so it is never undefined behavior, even when your logic is wrong.

Every atomic API offers the same four families of operations. Learn them as a set:

FamilyWhat it doesJavaC++
Load and storeRead or write the whole value at onceget, setload, store
ExchangeWrite a new value, return the old onegetAndSetexchange
Fetch and modifyAdd or subtract in one step, return the old or new value (C++ also has and, or, xor; Java's atomic classes do not, though VarHandle does)getAndAdd, incrementAndGet, addAndGetfetch_add, fetch_sub, fetch_or, +=, ++
Compare-and-swapWrite the new value only if the current value equals the expected onecompareAndSet, compareAndExchangecompare_exchange_strong, compare_exchange_weak

The first three cover most counters and flags. The fourth, compare-and-swap (CAS), is the universal one: anything you can compute from the current value, you can apply atomically with CAS and a retry loop. That loop is the next lesson; here you learn the instruction itself.

The atomic types in both languages

Java

The Java family. AtomicInteger, AtomicLong, AtomicBoolean and AtomicReference<V> cover single values; AtomicIntegerArray, AtomicLongArray and AtomicReferenceArray give atomic operations on each element of an array. Their get and set have the same visibility rules as a volatile field. When you need atomic updates on a volatile field of many small objects without a wrapper object per field, the field updaters (AtomicIntegerFieldUpdater, AtomicLongFieldUpdater, AtomicReferenceFieldUpdater) find the field by reflection once and then update it in place; the JDK itself mostly uses VarHandle for this since Java 9. Keep atomic fields final: you change the value inside, never the object.

One trap deserves its own sentence: AtomicReference.compareAndSet compares references with ==, not with equals. That matters for boxed numbers, as the quick check shows.

C++

The C++ family. std::atomic<T> works for integers, bool, pointers, and (since C++20) floating point with fetch_add. It also accepts any trivially copyable T, but a large T is implemented with a hidden lock: ask std::atomic<T>::is_always_lock_free. On this course's Mac, an 8 or 16 byte struct is lock-free and a 64 byte struct is not. std::atomic_flag is the one type guaranteed lock-free everywhere. C++20 also added std::atomic_ref (atomic operations on a plain object you already have) and wait, notify_one and notify_all on atomics.

Two traps. First, x = x + 1 on a std::atomic<int> is a load followed by a separate store: each half is atomic, the whole is not. x += 1 and x++ are single atomic operations. Second, std::atomic is not copyable, so it cannot sit in a std::vector that may reallocate; size the vector once, or use a std::unique_ptr<std::atomic<long>[]>.

The two languages report the outcome differently, and the difference shapes how you write loops later:

  • Java's compareAndSet(expected, desired) returns a boolean. If you need the value it found, compareAndExchange(expected, desired) (Java 9) returns the witness: the value that was there.
  • C++'s compare_exchange_strong(expected, desired) takes expected by reference. On failure it overwrites expected with the current value, so you already hold the fresh value for your next attempt.

Exactly one winner

The property you will lean on again and again: when several threads compare-and-swap from the same expected value, and the variable holds that value to begin with, exactly one succeeds. The first CAS to reach the variable changes it, so every later one sees a value that no longer matches. Three conditions make this exact: the CAS is the strong kind, each new value differs from the expected one, and nobody sets the variable back to the expected value afterwards. One-winner designs are built so all three hold. Below, eight threads race to claim a job by moving owner from 0 to their own id.

Run it many times: the owner changes, the number of winners never does. This one-winner property is how you build "start once", "close once" and "only the first completer wins", which you will do in CAS loops and atomic state machines.

How the CPU makes it indivisible

Each core has its own caches, and memory moves between them in fixed blocks called cache lines (64 bytes on most x86 chips, 128 bytes on Apple silicon). A coherence protocol, usually a variant of MESI (Modified, Exclusive, Shared, Invalid), keeps the copies consistent. Its central rule: to write a line, a core must hold the only valid copy. Every other core's copy is invalidated first.

An atomic read-modify-write uses that rule. The core fetches the line in exclusive state, does the read, the compare and the write, and does not give the line up to any other core until it has finished. Other cores asking for the line simply wait a few nanoseconds. Nothing is "locked" in the software sense; the cache line is held for the length of one instruction. That is the x86 picture; ARM reaches the same guarantee in its own way, as you will see in a moment.

On x86: the lock prefix

x86 has single instructions for this. compare_exchange and compareAndSet become lock cmpxchg, fetch_add and getAndAdd become lock xadd, and exchange becomes xchg (which is locked even without the prefix). Not every operation has its own instruction: x86 has no instruction that ORs (or ANDs, or XORs) and also returns the old value, so a fetch_or whose result you use compiles to a lock cmpxchg retry loop. On old processors the lock prefix asserted a signal that locked the whole memory bus. Modern processors hold just the cache line, except when the operand straddles two cache lines (a "split lock"), which still falls back to a bus lock and is very slow. A locked instruction is also a full memory barrier on x86, which is part of its cost.

On ARM: load-linked and store-conditional

Classic ARM (and POWER and RISC-V) has no single compare-and-swap instruction. It has a pair: load-linked and store-conditional. ldaxr loads a value and asks the core to watch that address. stlxr stores only if nobody else wrote the watched line in between, and reports whether it did. A compare-and-swap is built from the pair: load, compare, conditionally store, and if the store failed, go round again. ARMv8.1 added single-instruction atomics (the LSE extension: cas, ldadd, swp), which scale better under contention. Apple silicon has them.

What it costs

Atomics are cheap compared with blocking, and expensive compared with plain arithmetic. The numbers below are orders of magnitude and vary a lot between chips; what matters is the ratios.

OperationRough costWhy
Plain add on a value already in a register or the L1 cachewell under 1 nsOne simple instruction, often overlapped with others
Uncontended atomic increment or CAS, line already in this core's cacheabout 2 to 20 nsThe read-modify-write cannot overlap freely with surrounding work, and on x86 it is a full barrier
Atomic operation on a line another core just wrotetens of ns, around 100 ns or more across socketsThe line has to travel from the other core's cache first
Blocking on a contended lock: park, context switch, wakemicrosecondsThe operating system gets involved

The trap is the third row. When many threads update one atomic, each update has to drag the cache line to its own core, so the threads queue for the line one at a time. On the 16-core laptop this course was built on, 16 million increments of one AtomicLong took about 30 ms on one thread and between 350 and 450 ms when split across 8 threads (the exact figure moves with whatever else the machine is doing). More threads made the same work over ten times slower, with no lock anywhere. The fix for hot counters is striping, two lessons from now.

Atomic pieces do not make an atomic whole

An atomic variable makes each operation on that variable indivisible. It says nothing about two operations, or about two variables. Here is a classic: a range whose invariant is lower <= upper, with each bound in its own atomic.

Two fixes. Put both fields under one lock, or put both values in one immutable object behind one atomic reference and replace the whole object with a compare-and-swap. The second is a lock-free pattern you will write in the next lesson. The rule to remember: one atomic protects one invariant only if the invariant lives entirely inside that one variable.

Worked example: picking the operation

Hand out unique order numbers to 32 threads. Fetch-and-add: nextId.getAndIncrement() or next_id.fetch_add(1). Every caller gets a different old value, with no retries.

Make sure shutdown() runs its cleanup only once, even if three threads call it. Compare-and-swap on a flag: if (closed.compareAndSet(false, true)) cleanup();. Exactly one caller wins. A get() then set(true) would let two callers both see false.

Swap in a new routing table that request threads read constantly. A plain atomic store of a reference to a new immutable table: table.set(newTable) or a std::atomic pointer store. Readers get either the old table or the new one, whole. (In C++ you must also decide when the old table can be freed; the lock-free stack lesson is about exactly that problem.)

Track the largest latency seen so far. No single fetch-and-modify computes a max, so this needs a compare-and-swap loop: read, compare, CAS, retry. That is the first program of the next lesson.

Common mistakes

  • Get, then set. if (!started.get()) { started.set(true); run(); } is a check-then-act on an atomic: two threads can both see false. Use compareAndSet(false, true) and act only if it returned true.
  • x = x + 1 on a C++ atomic. It is a load and a separate store, so updates can be lost (though there is no undefined behavior). Write x += 1 or x.fetch_add(1).
  • Two atomics guarding one invariant. Each is safe, the pair is not, as the range example shows. Use one lock, or one atomic reference to an immutable object.
  • Compare-and-set on boxed values in Java. AtomicReference<Integer> compares identity, so compareAndSet(1000, 1001) can fail even when the value is 1000. Use AtomicInteger, or keep the exact reference you read.
  • Assuming every atomic is lock-free. A std::atomic of a large struct takes a hidden lock. Check is_always_lock_free when it matters.
  • Using C++ volatile for threads. It does not make anything atomic or visible across threads; std::atomic does.

In the interview

The question arrives in three shapes. As theory: "What is CAS, and how does it work?" As a follow up to a coding answer: "Can you do this without a lock?" Rubrik has asked exactly that path in an onsite: a thread-safe stack, then a lock-free version with CAS, with the candidate asked to explain the primitives. And as a design probe: "Why is your atomic counter slow under load?" A commenter tagged as working at Databricks has also said CAS questions are now common there; treat that one as unverified, but expect it.

Compare-and-swap is one atomic instruction: write the new value only if the variable still holds the value I expected, and tell me whether it worked. On x86 it is lock cmpxchg; the core holds the cache line exclusively for the read, compare and write, so no other core can get in between. On ARM it is either a single LSE instruction or a load-exclusive, store-exclusive pair that retries if another core touched the line. It never blocks, so it is cheap when uncontended, but every successful update moves the cache line, so a single hot atomic stops scaling with cores.

Follow ups to expect: "What happens if two threads CAS at the same time?" (exactly one wins), "Is incrementAndGet a CAS loop?" (in the JDK source it looks like one; on x86, and on ARM cores with LSE, the JIT turns it into a single lock xadd or ldadd), "What is ABA?" (see the ABA lesson), and "Why not just use atomics everywhere?" (they protect one variable; invariants across variables need a lock or one immutable snapshot).

Senior depth

Ordering comes with the operation. Java's get, set and read-modify-write methods behave like volatile accesses, and a successful compareAndSet is both a volatile read and a volatile write. (Java 9 added weaker variants such as getAcquire, setRelease, getPlain and weakCompareAndSetPlain, the Java cousins of C++ memory orders; you rarely need them.) C++ atomics default to memory_order_seq_cst, and every operation accepts a weaker order when you can justify it, as memory orders explains. On x86 the locked instruction is a full barrier whatever you ask for; on ARM the order decides between casal, casa, casl and plain cas.

Double-width CAS. Some algorithms need to compare-and-swap a pointer and a counter together. x86-64 has cmpxchg16b and ARMv8.1 has casp for 16 bytes, which is why a 16 byte struct can be lock-free in std::atomic. On x86-64 that depends on the build: clang reports it lock-free only when it may use cmpxchg16b (-mcx16 or a newer -march), so check is_always_lock_free rather than assume. It is the classic defence against the ABA problem.

Why CAS is called universal. Maurice Herlihy's 1991 paper on wait-free synchronization ranks primitives by their consensus number: how many threads they can bring to agree on one value without waiting. Plain loads and stores reach 1; test-and-set, exchange and fetch-and-add reach 2; compare-and-swap and LL/SC reach any number. That is the formal sense in which CAS is universal: with it you can build a wait-free version of any shared object for any number of threads, which fetch-and-add alone cannot do once there are three or more threads.

CAS inside the JDK. ConcurrentHashMap inserts the first node of an empty bin with a compare-and-swap on the table slot and only locks a bin when it already holds nodes. If an interviewer asks how the map avoids a global lock, that sentence is the start of the answer.

Under the hood: why one hot atomic is slow

When thread A on core 1 increments a counter, core 1 must own the counter's cache line exclusively. If thread B on core 2 incremented it a moment ago, core 1 sends a request, core 2 invalidates its copy and forwards the data, and only then does core 1's increment run. With eight cores taking turns, every increment pays that transfer, and the transfers cannot overlap because only one core may own the line at a time. Total throughput is then capped by how fast one line can bounce between cores: tens of millions of updates a second for the whole machine, however many cores you add (an order of magnitude, not a constant).

Key takeaways

  • An atomic variable makes each operation on it indivisible and visible to other threads; in C++ it also removes undefined behavior.
  • Compare-and-swap writes only if the value still equals what you expected; of several racing CASes, exactly one succeeds.
  • The hardware holds the cache line exclusively for one instruction: lock cmpxchg on x86, LSE cas or an LL/SC pair on ARM.
  • Uncontended atomics cost nanoseconds; a contended one moves its cache line on every update and stops scaling.
  • One atomic protects one variable. Invariants across variables need a lock or a single atomic reference to an immutable object.

Quick check

Answer each question, then read why. Your score is saved for your module test.

x is an atomic integer holding 0. Thread A runs print(x.compareAndSet(0, 1)) (in C++, compare_exchange_strong with expected = 0) and thread B runs the same line at the same time. What can the two threads print?
Why. The first CAS to reach x finds 0 and writes 1; the second finds 1, which no longer matches, and fails. Two successes would mean both read 0 and both wrote, which is exactly what CAS forbids. Two failures are impossible with the strong version because nothing else changes x.

Why. Each load and each store is atomic, so there is no data race. But read, add and write are still three steps with a gap, so two threads can read the same value and one increment overwrites the other. Atomic pieces do not make an atomic whole: use incrementAndGet or fetch_add.

Why. Old processors locked the bus; modern ones lock only the cache line, which is far cheaper. The bus lock still happens for a "split lock", an operand that straddles two cache lines. The operating system is never involved, which is why atomics are cheaper than blocking locks.
A class keeps lower and upper in two separate atomic integers with the invariant lower <= upper. Each setter checks the other bound, then sets its own. Is it thread-safe?
Why. Starting from (0, 10), setLower(5) and setUpper(4) can both pass their checks before either writes, leaving (5, 4). The invariant spans two variables. Use one lock for both, or one atomic reference to an immutable pair that you replace with compare-and-swap.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "What is compare-and-swap, and how does the CPU make it atomic?" Answer out loud, covering x86 and ARM, and say what it costs.
Model answer

Compare-and-swap takes a memory location, an expected value and a new value. As one indivisible step, it checks whether the location still holds the expected value, writes the new value if it does, and reports success or failure; a failed CAS also tells me the current value so I can retry.

The CPU makes it indivisible through cache coherence. To write a cache line a core must own it exclusively, so for an atomic read-modify-write the core takes the line in exclusive state and does not give it up until the read, the compare and the write are all done. On x86 that is the lock cmpxchg instruction; on modern parts the lock is just the cache line, not the bus, unless the operand straddles two lines. It is also a full memory barrier. On ARM there is either a single LSE instruction (cas) or a load-exclusive, store-exclusive pair: the store succeeds only if no other core wrote the line since the load, otherwise the code loops.

Uncontended, it costs a few nanoseconds and never blocks. Contended, every successful update has to move the cache line between cores, which costs tens of nanoseconds or more, so a single hot atomic caps throughput no matter how many cores I add. That is why hot counters are striped.

Debug
This code is meant to run startServer() exactly once, even if many threads call ensureStarted(): if (!started.get()) { started.set(true); startServer(); } (in C++, if (!started.load()) { started.store(true); start_server(); }). Find the bug and fix it in your language.
Model answer

The check and the set are two separate atomic operations, so two threads can both read false before either sets it, and the server starts twice. The fix is one compare-and-swap, which only one thread can win:

One more thing a strong answer adds: the losers return immediately, possibly before the winner has finished starting. If callers must wait until the server is actually up, add a second state (STARTING, then STARTED) and make losers wait for STARTED, for example with a latch or a condition variable.

Numbers
A metrics counter is a single AtomicLong (or std::atomic<long>) incremented by 32 threads. Moving its cache line between cores costs roughly 50 ns under contention. Roughly what is the most increments per second the whole machine can do on it, and what would you change?
Model answer

Each contended increment has to move the cache line, and only one core can own it at a time, so the increments are serialized on the line. At about 50 ns per transfer that is 1 / 50 ns, which is about 20 million increments per second for the whole machine, as an order of magnitude, whether there are 4 cores or 64. Adding threads does not add throughput; it adds queueing and coherence traffic.

The fix is to stop sharing one line: in Java use LongAdder, which spreads increments over padded cells and sums them on read; in C++ use a sharded counter with one cache-line-aligned atomic per thread or shard, summed on read, or per-thread counts merged at the end. The trade-off is that reading the total becomes a sum over cells and is not an instant snapshot, which is fine for metrics.

Out loudabout 90 s

What a strong answer covers

How a senior would say it
Exactly one of them wins. Compare-and-swap is a read, a compare and a conditional write done as one indivisible step, so whichever core gets there first finds 0, writes 1 and returns true. The other finds 1, which no longer matches, and returns false. In C++ the loser also gets the current value written back into its expected variable. The hardware makes this indivisible through cache coherence: to write a cache line, a core must hold the only valid copy. On x86 the instruction is lock cmpxchg. The core takes the line in exclusive state and keeps it for the read, the compare and the write, so the second core's request just waits a few nanoseconds and then sees 1. On ARM it is either one LSE instruction, casal, or on older cores a load-exclusive, store-exclusive pair, where the store fails if anyone touched the line and the code goes round again. Nothing blocks and the operating system is never involved, so the loser knows at once that it lost and can retry or do something else. The real cost is moving the cache line between cores, tens of nanoseconds, which is why one heavily shared atomic stops scaling.

"This class keeps lower and upper in two separate atomic integers, and each setter checks the other bound before it writes. A colleague says it is thread-safe because every field is atomic. Do you agree?"
What a strong answer covers
  • No: each operation is atomic, but check then set is two steps with a gap
  • The interleaving: from 0 to 10, setLower(5) and setUpper(4) both pass their checks, then both write, leaving 5 to 4
  • The invariant spans two variables, and an atomic only protects what lives inside one variable
  • Fix one: one lock around both fields, taken by readers too
  • Fix two: both bounds in one immutable object behind one atomic reference, replaced with a compare-and-swap loop
How a senior would say it
No. Every single read and write is atomic, but each setter does a check and then a set, and those are two separate steps. Here is the interleaving. The range starts at 0 to 10. One thread calls setLower(5) and checks 5 against upper 10, fine. Another calls setUpper(4) and checks 4 against lower 0, also fine. Then both write, and the range is 5 to 4. Every atomic did its job and the invariant is still broken, because the rule, lower at most upper, lives across two variables, and an atomic only protects what lives inside one. I would fix it one of two ways. The simple way is one lock around both fields, taken by readers as well. The lock-free way is to put both bounds in one immutable object behind a single atomic reference. Each setter reads it, checks, builds a new pair and compare-and-swaps it in, retrying if it changed. A reader then gets a consistent pair in one read.

Out loudabout 75 s
"We replaced a locked request counter with a single atomic counter to make it faster. On a 32-core box, throughput got worse as we added threads. What is going on, and what would you do?"
What a strong answer covers
  • Every increment needs exclusive ownership of the counter's cache line, so increments are served one at a time
  • Each hand over costs tens of nanoseconds, so the whole machine tops out around tens of millions of increments a second (an order of magnitude), however many cores
  • More threads only add queueing and coherence traffic, so total time grows
  • Fix: stripe it, LongAdder in Java, per thread or sharded counters on separate cache lines in C++, summed on read
  • Trade off: a read is a sum, not an instant snapshot, which is fine for metrics but not for an exact limit
How a senior would say it
The atomic removed the lock but not the sharing. Every increment has to own the counter's cache line exclusively, so with 32 threads the line bounces from core to core and the increments are served one at a time. Each hand over costs tens of nanoseconds, so the whole machine tops out somewhere in the tens of millions of increments a second, as an order of magnitude, no matter how many cores I add. More threads only add queueing and coherence traffic, which is why it got slower. On a laptop, eight threads doing the same increments as one can take over ten times longer. The fix is to stop sharing one line. In Java I would use LongAdder, which spreads increments over padded cells and sums them on read. In C++ I would keep per thread or sharded counters, each on its own cache line, and add them up when someone reads. The trade off is that a read is a sum, not an instant snapshot, which is fine for metrics but not for enforcing an exact limit.
