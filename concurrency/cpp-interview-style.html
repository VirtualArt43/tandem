Writing C++ in an interview

A skeleton for thread-safe components, scoped_lock and predicate waits, the compile errors that cost minutes, and how to talk while you code.

Asked atRubrikDatabricksGoogle
Before this:Templates, auto and type deductionExceptions, noexcept and exception safetystd::chrono: durations, clocks and deadlinesBuilding, debugging and sanitizers

In a concurrency round the interviewer grades two things at once: whether your design is correct, and whether you can turn it into compiling, readable C++ under time pressure. The second is a skill you can drill until it is automatic, which frees all of your attention for the first.

In plain words

Watch a good batter between deliveries: the same tap of the bat, the same guard, the same look around the field, every ball. None of that routine needs thought, so all of the thought goes to the ball that is coming.

Your routine is a fixed skeleton for every thread-safe class: the same includes, the same member layout, the same lock and wait idioms, the same names. When the syntax is automatic, the interview is about concurrency, which is where you want it.

Why this matters for concurrency

  • Expect to run your code. Rubrik reports describe system coding in CoderPad or similar environments; one new grad reported fixing a deadlock but then failing to compile the fix. A Databricks L4 candidate reported being expected to write the full C++ implementation of a concurrent event writer. Formats vary by round and team.
  • C++ concurrency is syntax heavy. Lock types, predicate lambdas, captures and thread construction are template-heavy, and a slip produces a wall of errors. A Google interviewer pointed out syntax errors in a C++ phone screen, and a Google L4 candidate needed help with C++ thread syntax in the middle of a concurrency question.
  • Reasoning out loud is graded. A Google L5 candidate who listed the right tools for a per-user counter map still got No Hire and concluded the interviewer wanted the race conditions and guarantees reasoned through. LinkedIn interviewers have asked for the specific race that each lock prevents, and an Uber interviewer complained of candidates who "put synchronization everywhere".

The skeleton: learn it until you can type it blind

A useful first design for many thread-safe components is a monitor: private state, one mutex that guards it, condition variables for the things threads wait for, and public methods that lock, wait, change state and notify. Here is a bounded queue that can be closed. Its capacity must be positive, and its element type must support non-throwing moves and destruction; the code checks those requirements.

The queue contract comes before the template. All access to the deque and closed_ uses mu_, so 0 <= items_.size() <= capacity_ always holds. Successful pushes take effect when the item is inserted; pops when it is removed; close when closed_ is set. A push racing with close either inserts before close or rejects after it. Accepted items remain available to consumers, while a closed, empty queue returns std::nullopt. Closing twice is harmless.

push takes its argument by value: passing an rvalue may move from your argument even if the queue later rejects it. If insertion allocation throws, the deque remains unchanged, and the catch wakes another producer so an available slot is not stranded. Non-throwing moves make extracting and returning an item safe after removal. For a type with throwing moves, choose a different contract or queue owning pointers such as std::unique_ptr<Job>; RAII alone does not restore a moved-from element.

Element moves and destruction still execute under the queue's mutex. Require them to be short and not reenter the queue; noexcept alone does not prevent a callback from deadlocking.

Close is not destruction. The owner must stop new callers, close, and join all existing users before destroying the queue, including callers between unlocking and notifying. The C++20 driver uses std::jthread and closes on partial startup failure before automatic joining; worker exceptions also close the queue and make the demo fail. The queue itself needs only C++17; in a C++17 driver use std::thread with a joining scope guard and the same close-before-join cleanup. A destructor cannot safely fix callers still using a destroyed object.

Every convention in it is deliberate, and each one saves you a bug or a question:

  • Members end in an underscore (mu_, items_), so state is never confused with locals or parameters.
  • A "guarded by" comment on every shared field. It tells the interviewer your locking rule, and it tells you which fields every method must lock for.
  • One mutex per invariant, declared mutable if any const method locks it.
  • Every wait has a predicate, and every predicate includes the shutdown flag; close also notifies both waiter groups.
  • Notify after changing the state. Unlocking before notifying is an optional refinement; notifying while holding the lock is also correct.
  • Copying deleted, single-argument constructor explicit, sizes as std::size_t. Small things that show fluency.

Two habits to drop before an interview. #include <bits/stdc++.h> is an internal header of GCC's library: it works on many judges, but on a Mac with clang it fails with "'bits/stdc++.h' file not found". And using namespace std; at the top of a file collides with names you are likely to use in concurrent code. With <algorithm> included, a global int count = 0; becomes "reference to 'count' is ambiguous", because std::count is now visible too; data, size and next collide the same way. Write std:: and the problem never arises.

Locks: the right guard in one second

SituationWrite
One mutex, no waitingstd::lock_guard<std::mutex> lock(mu_); (or std::lock_guard lock(mu_); in C++17)

Handle transfer(a, a) before locking: passing the same non-recursive mutex twice violates the locking requirements. Consistent use of std::scoped_lock for the pair avoids the opposing-transfer cycle, but it cannot prevent deadlocks involving unrelated locks, callbacks or joins while holding a lock.

Threads and lambdas without compile errors

The rules that prevent most errors:

  • In a member function, capture [this] explicitly when using members. Implicit capture of this through [=] is deprecated in C++20. Both capture a pointer, so keep the object alive; [*this] would copy the object and often cannot compile for a class containing a mutex.
  • Capture by reference ([&]) only when the variables outlive all accesses. Joining before scope exit solves lifetime; it does not synchronize concurrent modifications before the join.
  • Capture loop variables by value. for (int i = 0; ...) threads.emplace_back([&] { work(i); }); hands every thread a reference to the same, changing i. Write [i] or [&, i].
  • Move-only things go in with an init capture: [job = std::move(job)].
  • A member function as the thread body: std::thread t(&Worker::run, this);, or the clearer std::thread t([this] { run(); });.
  • For std::vector<std::thread>, add with emplace_back and join with for (auto& t : threads) t.join();, taking each by reference. Provide cleanup for partial construction: the next thread creation can throw while earlier workers are joinable.
  • Prefer std::jthread (C++20) where its ownership fits: destruction requests stop and joins. Workers must still have a path to finish, and an uncaught exception in their callable still invokes std::terminate. In owning classes, declare worker members after the state they use so workers are destroyed first, and signal shutdown before joining.

How to talk while you code

Silence makes the interviewer guess; narrating syntax ("now a semicolon") wastes their time. Narrate decisions. A shape that works for a 45 to 60 minute round, as a guide rather than a rule:

  1. Restate and clarify (about 5 minutes). The API, who calls what from which threads, blocking or not, bounded or not, shutdown, exceptions and allowed libraries. Rubrik reports include bans on ready-made executors and queues, but "no library" is ambiguous: confirm whether C++ threads, mutexes, conditions and atomics are allowed, and which language version is available.
  2. State the design in two sentences (about 5 minutes). What the shared state is, which lock guards it, what threads wait for and who wakes them.
  3. Write the skeleton first, then the methods (about 20 minutes). Members with "guarded by" comments, then each method as lock, wait with a predicate, change, notify. At each lock, say which race it prevents.
  4. Test by walking interleavings (about 10 minutes). Two producers on a full queue; close while a consumer waits; the last element taken by two consumers. Then say what you would run: a stress test with exact counts, under ThreadSanitizer.
  5. Extensions. Timeouts, fairness, a lock-free fast path, metrics. Offer them rather than building them unasked.

Saying which race each lock prevents is the strongest habit of the five. It answers the over-locking worry before it is raised, and it is exactly the follow up some interviewers ask for.

Worked example: "now several threads call it"

You have just solved a per-user hit counter, hit(userId) and count(userId), single-threaded. The interviewer says: "Now many request threads call hit at the same time, and a dashboard thread calls count." This is the follow up a Google L5 candidate faced with a per-user counter map.

Name the races first. "Concurrent inserts can race on the table's structure; an insertion that rehashes can race with another thread's lookup. Two increments of the same existing plain counter also race, and a read racing with that increment is unsafe even if no insertion occurs. In C++ these are data races and undefined behaviour, not merely the possibility of a lost increment."

Then the simplest correct design. "One mutex guards the whole map. hit does the insert-or-increment in one critical section. count uses find, not operator[], so a read never inserts, and returns a copy."

Then the guarantees and the scaling story. "Successful operations are linearizable: they take effect inside the lock. snapshot copies under that lock, so it is consistent across users. If contention matters, I would shard by key hash. An exact full snapshot must hold all shard locks together in a consistent order; separately copied shards give a mixed-time view. Atomic per-user counters still need protected map lookup, insertion and lifetime. They are simplest with a fixed set of users; dynamic membership needs a deliberate ownership scheme, such as retained handles, rather than unlocked map access."

The increment checks for signed overflow; a mutex would not make overflowing long arithmetic defined. A snapshot takes O(U) time and storage for U users and can hold the lock for a long time. The tiny driver assumes successful allocation; a reusable service must report allocation or task failures at the worker boundary rather than let exceptions escape a thread.

That last paragraph is what separates a list of tools from reasoning: each choice comes with the race it removes and the guarantee it keeps or gives up.

Common mistakes

  • Forgetting to join. A joinable std::thread destroyed at the end of main calls std::terminate. Join every thread, or use std::jthread.
  • [&] in a loop that starts threads. Every thread sees the same loop variable. Capture it by value.
  • An unnamed guard. std::lock_guard<std::mutex>{mu_}; protects nothing.
  • notify_one with two kinds of waiters on one condition variable. It can wake a thread that cannot proceed, and the signal is lost. Use two condition variables, or notify_all.
  • Locking around slow work. I/O, callbacks and sleeps under the lock serialize everything. Copy what you need, unlock, then do the slow part.
  • using namespace std; with globals called count, data or next. Ambiguity errors in the middle of the interview.
  • Atomics everywhere. An atomic per field does not make a multi-field update atomic. Default to one mutex per invariant; use an atomic for a lone counter or flag.

In the interview

Interviewers rarely ask about style directly. They notice it: whether the code compiles, whether every lock has a reason, whether you can explain each wait, and whether you recover calmly from a compile error. The sentences below are the ones to have ready.

I'll use the monitor pattern: one mutex guards the deque and the closed flag, with two condition variables, not full and not empty. Every wait takes a predicate, so spurious and stolen wakeups are handled, and close() sets the flag under the lock and notifies everyone, so nobody sleeps through shutdown.
This lock is here because two producers could otherwise both see space for one more item and both push: the check and the push have to be one critical section.
I'd test it with a few producers and consumers on a small capacity, checking every item arrives exactly once and the size never exceeds capacity, and I'd run that test under ThreadSanitizer.

Senior depth

Design for the test. For time-based components, inject the clock; for blocking components, agree on shutdown semantics. Treat size() as a snapshot, never permission for a later action: another thread may change it immediately. Test capacity 1, empty and full shutdown, racing close and push, and exact item identities, not just a total sum. Use gates or latches to arrange schedules, bounded completion checks to catch hangs, and ThreadSanitizer for executed data races. A clean run does not prove fairness or all possible interleavings.

Make locking visible. A carefully designed Guarded<T> wrapper can centralize locking, provided callbacks cannot leak references and follow reentrancy rules. It is a custom pattern, not a standard C++ type. Clang's thread safety annotations can check declared locking rules when enabled, but neither approach proves arbitrary callbacks safe.

State progress and cost separately. The queue preserves item FIFO, not FIFO service for waiting threads. Its storage is O(capacity), deque end operations are constant time aside from allocation and element operations, and lock or condition waits have no bounded completion guarantee. A reader-writer lock is not automatically faster, and an atomic is not automatically lock-free.

Know when to stop. When the first correct version works, say what you would change for performance (striping, a reader-writer lock where reads are truly read-only, batching, a two-lock queue) and what each costs, and let the interviewer choose. Building an unrequested lock-free version usually costs more than it earns.

Key takeaways

  • Drill one skeleton: private state with "guarded by" comments, one mutex per invariant, predicate waits that include shutdown, notify after changing state.
  • lock_guard for simple sections, unique_lock for waits, scoped_lock for several mutexes; always give the guard a name.
  • Capture [this] explicitly, capture loop variables by value, join every thread or use std::jthread.
  • Know the common error messages by sight, and fix them by reading the first error and your own line.
  • Talk in decisions: the race each lock prevents, the guarantee each method gives, and how you would test it.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A method waits on a std::condition_variable for the queue to become non-empty. Which guard must it use?
Why. condition_variable::wait takes a std::unique_lock<std::mutex>& so it can release and reacquire the mutex. Neither lock_guard nor scoped_lock exposes the required unlock/relock interface, so "any of them" is also wrong. std::condition_variable_any accepts other lockable types, but that is a different class.
What can this print?
Why. [&] refers to the loop's changing i. The conflicting accesses have no synchronization, so C++ gives undefined behaviour rather than a bounded set of numbers. Also, i is destroyed at loop exit, before the joins; a delayed worker has a dangling reference. Neither "always" answer follows, and the syntax is legal. Capture [i] to give each thread its own value. ThreadSanitizer can detect executed races; it is not a guarantee about every run.
for (auto t : threads) { t.join(); } where threads is a std::vector<std::thread>. What happens?
Why. std::thread is move-only. clang with libc++ reports "calling a private constructor of class 'std::thread'", GCC "use of deleted function". Write for (auto& t : threads).
For distinct accounts, no locks held on entry, and all transfers using the same chosen strategy, which line avoids a lock order deadlock against transfer(b, a)?
Why. std::scoped_lock uses a deadlock-avoidance algorithm for the supplied mutexes. Each other option locks in argument order or reversed argument order, so opposing transfers can hold one mutex each and wait for the other. The claim assumes distinct mutexes and no surrounding lock cycle. Sorting by a stable account id is another valid strategy, but is not one of these options.
What does this method do?
Why. The parentheses are parsed as a declaration: std::unique_lock<std::mutex> mu_;, default constructed and locking nothing, which also hides the member mu_. clang warns "parentheses were disambiguated as redundant parentheses around declaration of variable named 'mu_'". Give the guard a name: std::unique_lock<std::mutex> lock(mu_);.
With using namespace std; and #include <algorithm> at the top of a file, you declare a global int count = 0; and then write count += 1; in main. What happens?
Why. using namespace std; brings std::count into the global lookup, where it meets your ::count, and unqualified use is ambiguous. Interview code often uses names like count, data and next, so skip the using-directive and write std::.
The interviewer confirms: "Use standard threads, mutexes, guards and condition variables, but implement the queue and worker scheduling yourself." Which choices fit that rule? Select all that apply.Select all that apply
Why. The first three are explicitly permitted building blocks. std::async delegates task execution to the library, and a concurrent queue delegates the queue you were asked to build. Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
From memory, in under ten minutes: write a thread-safe BoundedQueue<T> with bool push(T), std::optional<T> pop() and close(). Reject zero capacity and require non-throwing moves and destruction. After close(), push returns false and pop drains what is left, then returns an empty optional. Preserve progress if insertion allocation fails, and state the owner's lifetime obligation.
Model answer

Every wait includes closed_; close changes it under the mutex and notifies both groups. The insertion catch passes an unused slot's wakeup to another producer before rethrowing. Non-throwing moves protect extraction and return; by-value input can consume an rvalue even on rejection. Two conditions keep waiter kinds separate. The owner must close and join all users before destruction; the queue does not own their threads.

Debug
Find every bug in this snippet: compile errors and concurrency bugs.
Model answer
  1. record: std::lock_guard<std::mutex>{mu_}; is an unnamed temporary, so push_back runs unlocked: a data race on the vector. Write std::lock_guard<std::mutex> lock(mu_);.
  2. count is const, so mu_ is const there and the lock_guard does not compile. Declare mutable std::mutex mu_;. Return std::size_t, or range-check before converting to int; a cast alone does not make a large size fit.
  3. waitFor passes a lock_guard to wait, which needs a std::unique_lock<std::mutex>: compile error.
  4. The predicate uses samples_ and n without capturing them. Write [this, n] and use a std::size_t target, or reject a negative n before converting it. Casting a negative target to an unsigned size silently changes its meaning.
  5. run captures i by reference: the read races with increments and may happen after i dies at loop exit. Capture [&stats, i].
  6. run never joins: destroying a joinable std::thread calls std::terminate. Join every worker, including after partial startup failure, or use std::vector<std::jthread> with a completion path.
  7. Define failure and shutdown: record can throw on allocation, and an exception escaping the thread terminates the process. A waiter whose target is never reached otherwise waits forever. Add a closed/failure predicate and wake waiters if the API requires cancellation.
Explain
You are asked to build a thread-safe LRU cache. Give the opening that you would say out loud before writing any code: the design and the locking rule, in four or five sentences.
Model answer

I'll keep a std::list in recency order and a std::unordered_map from key to list iterator, giving expected O(1) lookup and update aside from allocation, value copying and lock waiting; hash collisions can make lookup linear. One mutex guards both, because every map entry must point at a live node for the same key. get needs exclusive access because changing recency is a write. Values leave as copies or owning handles with a defined mutation policy, never as unprotected references into evictable nodes. If I shard by key hash for throughput, I will explicitly accept recency and capacity management per shard.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"You have a bounded queue in C++. Talk me through your locking rule, shutdown contract, and the failure cases you would test."
What a strong answer covers
  • One mutex protects deque and closed flag; capacity is positive and never exceeded
  • Producer and consumer predicates include closed, with separate condition variables
  • Close rejects new insertions, allows draining, and notifies every waiter
  • Insertion, removal and setting closed identify the operations' linearization points
  • Element moves cannot throw; failed insertion wakes another producer and rethrows
  • Owner closes and joins before destruction; tests cover capacity 1, racing close and exact item delivery
How a senior would say it
I would use one mutex for the deque and the closed flag, with a positive fixed capacity. That makes the space check and insertion one critical section, so two producers cannot claim the same last slot. Producers wait for space or closure. Consumers wait for an item or closure. I use separate condition variables because a normal insertion should wake a consumer and a removal should wake a producer. Close sets the flag under that mutex and notifies everyone in both groups. Push then rejects new insertions; pop drains accepted items and returns an empty optional only when closed and empty. The operation takes effect at insertion, removal, or setting the closed flag. That also defines a push racing with close: whichever wins the mutex determines acceptance. For generic values, I require non-throwing moves and destruction. If insertion allocation fails, I wake another producer before propagating the exception, because the free slot is still available. The owner must stop new callers, close, and join every user before destroying the queue. I would test capacity one, shutdown with an empty or full queue, a push racing with close, and exact item identities under multiple producers and consumers. ThreadSanitizer adds race detection, while bounded completion checks catch hangs.

Likely follow up: How would you support a type whose move constructor can throw after modifying its source?

Out loudabout 60 s
"All my workers sometimes print the same loop index. I captured by reference and joined them after the loop. Why is that still broken?"
What a strong answer covers
  • Workers refer to one loop variable while the creating thread modifies it
  • Unsynchronized conflicting accesses are a C++ data race and undefined behaviour
  • The loop variable dies before the joins, creating a possible dangling reference
  • Capture the index by value; separately preserve lifetimes of genuinely shared state
  • Join synchronizes completion with later reads, not earlier concurrent writes
How a senior would say it
Joining after the loop does not make the earlier accesses safe. Every worker refers to the same loop variable while the creating thread keeps changing it. Those accesses are not synchronized, so this is a C++ data race and undefined behaviour. I cannot even promise that the output is limited to the loop's range. There is a second bug: a variable declared in the for statement dies when the loop ends. A delayed worker can read through a dangling reference before we reach its join. I would capture the index by value, giving each worker its own copy, and capture shared state by reference only when its lifetime and synchronization are established separately. Join lets the caller safely consume completed worker results after joining. It does not retroactively order the parent's loop increments against worker reads. I would fix the capture first, then run the corrected code under ThreadSanitizer.

Likely follow up: Does capturing this by value keep the object alive?
