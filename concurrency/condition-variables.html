Condition variables and monitors

How a thread sleeps until shared state changes: wait releases the lock and sleeps in one step, notify wakes waiters, monitors package it all.

Asked atRubrikLinkedInDatabricksMicrosoft
Before this:Mutexes and RAII guardsBusy waiting, and when spinning is right

Locks answer "one at a time". Condition variables answer "not until": a consumer that must wait for an item, a worker that must wait for a task, a request that must wait for a free connection. They are the engine inside every blocking queue, latch and thread pool, and the tool interviewers ask you to use when they ban the library versions.

In plain words

A doctor's clinic has a receptionist's desk and a token display. Patients do not crowd the desk asking "is it my turn?" every few seconds (that would be spinning), and they do not stand at the desk while they wait (then nobody else could use it). They sit in the waiting room. When the doctor is free, the receptionist updates the display and rings a bell. Everyone looks up, and each patient checks whether the number on the display is theirs.

The desk is the lock. The number on the display is the shared state. The bell is the condition variable. And the one rule that makes it work: you check the display, and sit down to wait, without ever leaving a moment where the bell could ring unheard.

The problem: waiting for a condition on locked state

A consumer needs the queue to be non-empty before it can take an item. The queue is guarded by a lock, so the consumer must hold the lock to look at it. If the queue is empty, what now?

  • Keep the lock and wait: no producer can get in to add an item. The consumer waits forever.
  • Release the lock and spin or sleep-poll: wasteful or late, as the previous lesson showed.
  • Release the lock, then go to sleep until someone signals: closer, but between "release" and "sleep" a producer can add an item and signal, the signal finds nobody asleep, and the consumer then sleeps through it. That is a lost wakeup.

What is needed is an operation that releases the lock and goes to sleep as one indivisible step, and that takes the lock back before the thread continues. That operation is wait on a condition variable.

The idea: wait, notify, notifyAll

A condition variable is a place where threads wait for some condition on shared state, always paired with the lock that guards that state. It has three operations:

  • wait: the caller must hold the lock. Atomically release the lock and block. When woken, reacquire the lock before returning. So the code after wait always runs with the lock held again.
  • notify (signal, notify_one): wake one waiting thread, if any.
  • notifyAll (signalAll, broadcast, notify_all): wake all waiting threads.

A notification is not a message and is not stored: if nobody is waiting, it does nothing. So threads never wait for a notification. They wait for a condition on the state, and the notification only means "the state changed, check again". That gives the two shapes you will write over and over:

The while loop is not optional; the next lesson, always wait in a loop, is entirely about why. For now, notice that the waiter checks the condition while holding the lock, and the signaller changes the state while holding the same lock. That is what makes the check and the wait safe together.

Monitors

A monitor packages the pieces into one object: private state, one lock that guards it, and one or more condition variables tied to that lock. Every public method takes the lock, waits in a loop until its condition holds, changes the state, and signals whoever might now be able to proceed. The idea comes from Hoare and Brinch Hansen in the 1970s, and it is still the cleanest way to build a thread-safe object that blocks.

Java builds monitors into the language: every object has an intrinsic lock (taken by synchronized) and one wait set (used by wait, notify and notifyAll). C++ has no built-in monitor; you write the class yourself with a std::mutex and one or more std::condition_variable members. The result is the same pattern:

Notice the runners finish in no particular order. A notification does not promise who runs first: all three wake, and they take the lock back one at a time in whatever order the system picks.

Java: wait, notify and notifyAll

  • You must hold the monitor of the object you call them on, that is, be inside synchronized on that same object. Otherwise they throw IllegalMonitorStateException at run time; the compiler cannot catch it.
  • wait() releases only that object's monitor. Any other locks the thread holds stay held while it sleeps (more on that below). It does release that one monitor completely, even if the thread entered it several times through nested synchronized blocks, and restores the same hold count before returning; Condition.await on a ReentrantLock does the same.
  • wait(long millis) returns after the time even without a notification, and does not tell you which happened; you re-check the state and compute the time left yourself with System.nanoTime().
  • wait throws InterruptedException if the thread is interrupted, after taking the monitor back. Handle it like any other blocking call: propagate it, or restore the flag.
  • In a thread dump, a thread inside wait() is WAITING (or TIMED_WAITING). Once notified it becomes BLOCKED until it can re-enter the monitor.
  • Wait on a private lock object, not on this: outside code can enter synchronized (yourObject) and call notifyAll (or wait) on it, mixing its waiters with yours. And never use a Thread object as a monitor, because Thread.join itself waits and notifies on it.

Java: Condition objects

An intrinsic monitor has exactly one wait set. When different threads wait for different things on the same object (producers for "not full", consumers for "not empty"), they all share that one set, and a notification cannot be aimed at the right kind of thread. java.util.concurrent.locks.Condition fixes that: a ReentrantLock can create as many conditions as you need, each with its own wait set.

The methods mirror the monitor ones: await(), signal(), signalAll(), plus awaitNanos(nanos) (returns the time still left, which makes deadline loops easy), await(time, unit) (returns false if the time ran out), awaitUntil(date) and awaitUninterruptibly(). With a ReentrantLock, calling any of them without holding the lock throws IllegalMonitorStateException. You will build the full queue with these in producer and consumer.

C++: std::condition_variable

  • wait takes a std::unique_lock<std::mutex>, not a lock_guard, because it must unlock and relock the mutex. The lock must be held when you call wait, and every thread waiting on the same condition variable at the same time must use the same mutex; breaking either rule is undefined behavior.
  • Always use the predicate overload: cv.wait(lock, pred) is exactly while (!pred()) cv.wait(lock);. It is the loop, written for you.
  • Timed waits come in two flavours. wait_for(lock, 100ms, pred) and wait_until(lock, deadline, pred) return a bool: the predicate's value when they return, so false means the time ran out with the condition still false. The versions without a predicate return std::cv_status::timeout or no_timeout, which cannot distinguish a spurious wakeup and are easy to misuse.
  • notify_one() and notify_all() do not require holding the mutex, unlike Java. Notifying while holding it is always correct; notifying just after unlocking can save a context switch. The trade-offs, and the one case where it matters for correctness, are in lost wakeups. The state change itself must always happen while holding the mutex.
  • std::condition_variable_any works with any lockable type (a std::shared_lock, a custom mutex), at some extra cost, and in C++20 adds wait overloads that take a std::stop_token and return early when a stop is requested. Do not pair it with a std::recursive_mutex that this thread has locked more than once: wait unlocks one level only, so the mutex stays held while the thread sleeps and the signaller can never get in.

Timed waits, done right

A timed wait must handle three outcomes: the condition became true, the time ran out, or the thread woke early for no reason and must keep waiting only for the time left. Both languages have a clean form:

The C++ predicate version computes one deadline up front and waits until then, re-checking after every wakeup. The Java loop does the same by carrying the remaining time forward. The classic bug is a loop that calls wait(timeout) again with the full timeout after every early wakeup, so the total wait can stretch without limit.

Worked example: designing a monitor from a requirement

"Build a latch: countDown() decrements a count, and await() blocks until the count reaches zero." Whenever you build a blocking object, go through four steps out loud:

  1. State and lock: one count, guarded by one lock.
  2. What each blocking method waits for, as a predicate on the state: await waits for count == 0.
  3. Which changes can make a predicate true: only the countDown that brings count to zero. That is where the notification goes, and since every waiter waits for the same thing and all may proceed, it is notifyAll.
  4. Edge cases: extra countDown calls after zero must be harmless; a late await must return at once (it does, because it checks the state before waiting).

The same four steps produce a semaphore (state: permits; acquire waits for permits greater than zero; release notifies), a bounded queue (two predicates, two conditions) and a thread pool's work queue. The latch and semaphore problems add timeouts and a stress test.

Common mistakes

  • Waiting with if instead of while. The single most common bug with condition variables. The next lesson shows the two ways it breaks.
  • Changing the state without the lock. Even if the variable is atomic or volatile, the waiter's check and wait are only safe against changes made under the same lock. Otherwise the change and its notification can land between the check and the wait.
  • Waiting for a notification instead of a state. wait() with no condition to check misses any notification sent before it started waiting. Always wait for a predicate on shared state.
  • Calling wait or notify on the wrong object in Java: on this while holding a different lock, or on a different object than the waiters use. Runtime IllegalMonitorStateException at best, a silent hang at worst.
  • Using std::lock_guard with cv.wait: it does not compile, because wait needs a std::unique_lock.
  • Holding another lock while waiting. wait releases only the lock tied to that condition. A second lock stays held, and if the signaller needs it, both threads stop: nested monitor lockout.
  • Restarting the full timeout after every wakeup. Carry the remaining time (Java awaitNanos) or use a deadline (C++ wait_until, or wait_for with a predicate).

In the interview

Condition variables are the tool behind the most asked concurrency coding questions. Rubrik interviewers often ban library queues and executors, so you build the blocking queue, the "wait until all tasks are done" call and the thread pool from a lock and conditions; a LinkedIn round demanded plain wait and notify for a bounded blocking queue; a Databricks event writer round listed condition variables among its core topics; and a Microsoft C++ candidate answered producer-consumer with std::mutex, std::unique_lock and std::condition_variable. The interviewer watches whether you hold the lock when checking, wait in a loop, change state before signalling, and pick the right notify.

I use the monitor pattern: one lock guards the state, and each blocking method waits on a condition variable in a loop until its predicate holds. wait atomically releases the lock and sleeps, and re-acquires the lock before returning, so the check and the wait cannot be split by a signaller, as long as the signaller changes the state under the same lock. After any change that could make a predicate true, I signal: one waiter if each condition has one kind of waiter and one change frees one of them, otherwise all of them.

Follow ups to expect: "Why must you hold the lock to call wait?" (so the check and the sleep are atomic with respect to state changes), "What happens to the lock while a thread waits?", "How can releasing and sleeping be one step?" (join the wait queue before releasing; see Under the hood), "Why use a Condition instead of wait and notify?" (separate wait sets), "Why while and not if?" (the next lesson), and "Add a timeout" (carry the remaining time).

Senior depth

  • Wait sets and thread dumps. A hang involving condition variables shows threads WAITING on a monitor or parked in await, not BLOCKED in a cycle, so the JVM's deadlock detector reports nothing. Read which condition each thread waits on, and ask which state change was supposed to signal it.
  • Nested monitor lockout. Calling wait inside synchronized (a) { synchronized (b) { b.wait(); } } releases b only. If the signaller must take a first, it never can. Design so a thread holds exactly one lock when it waits.
  • Interrupts and cancellation. Java's wait and await are interruption points; a woken-by-interrupt thread re-acquires the lock, then throws. C++ has no interruption: use std::condition_variable_any with a std::stop_token (C++20), or put a stopped flag in the predicate and notify_all when setting it.
  • Condition variables have no memory; semaphores do. A release with nobody waiting is remembered as a permit; a notify with nobody waiting is gone. That is why condition variables are always paired with state, and why a semaphore can sometimes replace both.

Under the hood: how "release and sleep" becomes one step

No implementation does two things at the same instant. The trick is the order: the waiter joins the condition's wait queue first, while it still holds the lock, then releases the lock, then sleeps. A notify that arrives in the gap after the release still finds the waiter in the queue, and the sleep primitive is built so that a wakeup sent before the sleep starts is not lost.

  • Java monitors: HotSpot adds the thread to the object's wait set while it owns the monitor, exits the monitor, then parks. A notify moves it from the wait set to the threads queued to re-enter the monitor; once it wakes and has to compete for the monitor, a thread dump shows it as BLOCKED.
  • Condition on a ReentrantLock: the thread links a node into that condition's queue, fully releases the lock, and parks until a signal moves the node onto the lock's own queue. LockSupport.unpark leaves a permit, so an unpark that comes before the park makes the park return at once.
  • C++ on Linux: std::condition_variable is a thin wrapper over glibc's pthread_cond_t. The waiter registers, releases the mutex, then does a futex wait that sleeps only if a signal counter still holds the value it read, so a signal sent in between makes the wait return at once. That is the same idea how locks are built used for mutexes.

If an interviewer asks you to build a condition variable from a mutex and semaphores, this ordering is the whole answer: record yourself as a waiter under the lock, release the lock, then block on something that remembers a signal that came early.

Key takeaways

  • A condition variable lets a thread wait for a condition on locked state: wait releases the lock and sleeps as one step, and re-acquires the lock before returning.
  • Wait for a predicate on the state, in a loop, holding the lock; change the state under the same lock, then notify.
  • A monitor is state plus one lock plus its condition variables, with every method taking the lock. Java has one built into every object; C++ builds it from std::mutex and std::condition_variable.
  • Java: hold the monitor for wait and notify or get IllegalMonitorStateException; use Condition for several wait sets. C++: std::unique_lock, the predicate overload, and wait_for or wait_until with a predicate.
  • Notifications are not stored. A notify with no waiter is lost, which is harmless only if waiters check the state first.

Quick check

Answer each question, then read why. Your score is saved for your module test.

What does a thread's call to wait on a condition variable do with the lock it holds?
Why. Releasing is what lets another thread change the state; doing it atomically with going to sleep is what prevents a signal from slipping in between; re-acquiring is what lets the code after wait safely re-check and use the state.
Thread W runs: lock; while (!ready) wait; print "A"; unlock. Thread S runs: lock; ready = true; notifyAll; print "B"; unlock. W is already waiting when S starts. What is printed?
Why. A woken waiter must re-acquire the lock before wait returns, and S still holds it while printing "B". This is signal and continue: the signaller keeps running. W was already waiting, so the notification is not lost.
Producers wait for "not full" and consumers for "not empty", on the same lock. What do two separate condition variables (Java Condition objects, or two std::condition_variables) give you over a single wait set?
Why. With one wait set, a notification may wake a thread that cannot use it, forcing notifyAll or risking a stall. Separate conditions let a consumer signal "not full" for producers only. The lock is still shared, and loops are still required.
Thread W holds lock L1, then takes lock L2, and waits on a condition variable tied to L2. The thread that would make W's condition true must take L1 first. What happens?
Why. wait releases the lock tied to its condition and nothing else. Holding another lock while waiting creates a nested monitor lockout. Design so a waiting thread holds only the one lock its condition belongs to.
A timed wait is written as: loop while the condition is false, calling wait(lock, 100 ms) each time. Under a stream of spurious or unrelated wakeups, what can go wrong?
Why. A deadline must be fixed once and every re-wait must use only the time left. In Java carry the value returned by awaitNanos; in C++ use wait_until with a deadline, or wait_for with a predicate, which computes the deadline once internally.
Java onlyA Java thread calls queue.notifyAll() without being inside synchronized (queue). What happens?
Why. wait, notify and notifyAll all require the caller to own the object's monitor, and the check happens at run time. The JDK 21 message is "current thread is not owner". Condition methods on a ReentrantLock have the same rule.
C++ onlyWhich lock must you pass to std::condition_variable::wait?
Why. wait must unlock and relock the mutex, which std::lock_guard cannot do, and std::condition_variable is specified for std::unique_lock<std::mutex> only. For other lock types, use std::condition_variable_any. Calling wait without owning the mutex is undefined behavior.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "Why do you need to hold the lock when you call wait, and what exactly does wait do?" Answer as you would out loud.
Model answer

The thread waits because a condition on shared state is false, for example the queue is empty, and that state is guarded by a lock. It must hold the lock to check the condition reliably. If it released the lock and then went to sleep in two steps, a producer could add an item and signal in between; the signal would find nobody asleep and be lost, and the consumer would sleep with an item sitting in the queue.

So wait does three things: it atomically releases the lock and puts the thread to sleep on the condition, so no state change can slip between the check and the sleep; it lets the thread be woken by a notify (or a timeout, an interrupt in Java, or spuriously); and before returning it re-acquires the lock, so the code after wait can safely re-check the condition, which it must, in a loop. The other half of the contract is on the signaller: it must change the state while holding the same lock, then notify.

Write code
Implement a one-slot Mailbox with put(item), which blocks while the slot is full, and take(), which blocks while it is empty. Use one lock and two condition variables.
Model answer

Each condition has only one kind of waiter, and each state change lets exactly one waiter proceed, so signalling one thread is safe. With a single condition shared by producers and consumers, you would need notifyAll, a point the lost wakeups lesson makes precise. (The Java version uses null as "empty", so it cannot carry null items.)

Design
Design a monitor for a parking garage with N spaces: enter() blocks while the garage is full, leave() frees a space, and enter(timeout) gives up after a timeout. Walk through the four steps.
Model answer

State and lock: freeSpaces, starting at N, guarded by one lock. Predicates: enter waits for freeSpaces > 0. Which changes make it true: only leave, which increments freeSpaces, so leave notifies; since one freed space lets exactly one waiting car in and all waiters wait for the same thing, a single notify (or signal) is enough. enter decrements freeSpaces after its wait loop.

The timed version keeps a deadline: in Java, carry the remaining nanoseconds through awaitNanos and return false when they run out with freeSpaces still 0; in C++, if (!cv.wait_for(lock, timeout, [&] { return freeSpaces > 0; })) return false; then decrement freeSpaces and return true. One subtlety with a single signal plus timeouts: check the state before the clock. A waiter that is signalled just as its time runs out must still take a free space if there is one. If it returned false without looking, it would swallow the only signal and leave another car waiting next to an empty space. The while (freeSpaces == 0) { if (nanos <= 0) return false; ... } loop and the C++ predicate overload both get this right, because they test the state first. Edge cases: a leave without a matching enter must not push freeSpaces above N (reject it), and an interrupted enter in Java must not take a space. This is a counting semaphore built as a monitor, and in production you would just use Semaphore or std::counting_semaphore, but the four steps are exactly what an interviewer wants to hear when the library is banned.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 65 s
"How would you explain to a junior engineer why a condition variable is useless without a lock and a piece of state next to it?"
What a strong answer covers
  • A notification is not stored: a notify with nobody waiting does nothing
  • So a thread waits for a condition on shared state, and a notification only means "check again"
  • The waiter checks the state while holding the lock
  • wait releases the lock and sleeps as one step, and re-acquires the lock before returning
  • The signaller changes the state under the same lock, then notifies
  • Without the state an early notify is lost; without the lock a change slips between the check and the sleep
How a senior would say it
Because a condition variable has no memory. If a thread notifies and nobody is waiting yet, the notification simply disappears. So a thread never waits for a notification. It waits for something to be true about shared state, like the queue being non-empty, and a notification only means go and look again. That state needs a lock, and the lock is what makes the check and the sleep safe together. The waiter checks the state while holding the lock, and wait releases that lock and goes to sleep as one step, then takes the lock back before it returns. The signaller changes the state under the same lock, then notifies. So no change can land between my check and my sleep. Take away the state, and an early notify is lost for good. Take away the lock, and the change can slip into that gap.

Likely follow up: Then what does a semaphore give you that a condition variable does not?

Out loudabout 80 s
"You are building a bounded buffer. One condition variable shared by producers and consumers, or two? Talk me through the trade off."
What a strong answer covers
  • Two predicates: producers wait for "not full", consumers wait for "not empty"
  • With one shared condition, a single notify can wake the wrong kind of thread, so you are pushed to notify all
  • Notify all is correct with a loop, but wakes every waiter to let one through
  • Two conditions on the same lock let each change signal only the kind that can proceed, so a single signal is enough
  • Java: a monitor has one wait set, so two conditions means ReentrantLock with two Condition objects; C++: two std::condition_variable members on one mutex
  • One condition is fine when every waiter waits for the same thing, such as a gate or a latch
How a senior would say it
Two, for a bounded buffer. There are two different things to wait for: producers wait until the buffer is not full, and consumers wait until it is not empty. If both kinds sleep on one condition variable, a notification can land on the wrong kind. Say a consumer takes an item and notifies one thread. It can wake another consumer instead of the producer that could now add, and the producer stays asleep. So with one condition I am forced to notify all, which is correct as long as every wait is a loop, but it wakes everybody to let one through. With two conditions on the same lock, a put signals not empty and a take signals not full, so each signal reaches a thread that can actually proceed, and a single signal is enough. In Java that means a ReentrantLock with two Condition objects, because a plain monitor has only one wait set. In C++ it is two std::condition_variable members sharing one mutex. When every waiter waits for the same thing, like threads at a gate, one condition with notify all is simpler and fine.

Likely follow up: With two conditions and single signals, what changes if a waiting consumer can time out or be interrupted?

"Here is a symptom: a worker pool stops making progress. The thread dump shows every worker asleep in a condition wait, and the deadlock detector reports nothing. What do you check?"
What a strong answer covers
  • Asleep in a condition wait is not blocked on a lock, so there is no lock cycle for the detector to find: a signal was never sent or never reached them
  • Name the predicate each worker waits for, and find every code path that can make it true
  • Check that each path changes the state under the same lock, then signals the right condition object
  • Check whether a single signal can land on a thread that cannot use it
  • Check that every wait is a loop that also watches the shutdown flag
  • Look for a second lock held while waiting, with a signaller blocked on it: nested monitor lockout
How a senior would say it
First, what the dump says. Workers asleep in a condition wait are not stuck trying to take a lock, so there is no cycle for the deadlock detector to find. Somebody was supposed to make their condition true and wake them, and did not. So I name the predicate each worker waits for, say the task queue being non-empty, and I find every code path that can make it true. For each one I check that it changes the state under the same lock the workers use, and that it then signals the right condition object, not a different one. If it uses a single signal, I ask whether that signal can land on a thread that cannot use it. Then I check the waiters: is every wait a loop, and does the loop also watch the shutdown flag? Last, I look for a second lock. If a worker holds another lock while it waits, and the producer is blocked on that lock, that is nested monitor lockout. Before fixing anything, I would reproduce it in a stress test.

Likely follow up: How would you write a test that reproduces this hang reliably, without waiting forever when it happens?
