const correctness and mutable

const variables, pointers and member functions, mutable for a mutex in a const getter, and the standard library's promise about concurrent const calls.

Before this:Classes, constructors, destructors and RAII

Since C++11, const carries a promise that matters for threads: the standard library guarantees that const member functions can be called from many threads at once, and your own classes are expected to keep the same promise. mutable is how you keep it when a const function still has to lock, cache or count.

In plain words

A museum painting has a sign: look, do not touch. A hundred visitors can look at it at the same time and nothing goes wrong, because looking changes nothing. That is const: any number of readers, no coordination needed.

But the museum also counts visitors with a clicker at the door. The counting happens while people only look, yet the clicker changes. If two guards share one clicker without taking turns, some visitors go uncounted. In C++ the clicker is a mutable member: it may change inside a const function, so it needs its own protection.

Why this matters for concurrency

  • The standard library promises that concurrent calls to const member functions of one object do not race, as long as no thread calls a non-const function at the same time. That is why many threads can find in one std::map with no lock while nobody writes it.
  • Your own classes are expected to honour the same contract: a const function is either truly read-only or internally synchronized.
  • A const getter that locks needs mutable std::mutex m_;. Interviewers see that line constantly, and "why is the mutex mutable?" is a standard follow up.
  • A const function that fills a mutable cache without a lock breaks the contract: two "readers" race on the cache.
  • const is shallow. A const object holding a pointer can still change what it points to, so immutability for threads must go all the way down.

const on variables, references and pointers

const correctness starts with the simple forms, which you have met already:

  • const int max_workers = 8; cannot change after initialization.
  • const T& is a read-only path to an object somebody else may still change (the values lesson).
  • const T* cannot write through the pointer; T* const cannot be repointed.
  • constexpr means "known at compile time" (and implies const for variables). C++20 constinit means "initialized at compile time", but the variable may change later, which is handy for a global std::mutex or an atomic counter.

The part people forget is that const is shallow. It protects the object's own bytes, not the things its members point to:

So "I only hand out const references" does not make data safe to share if those objects lead, through pointers, to things other threads write.

const member functions

A member function marked const promises not to change the object. Inside it, this is a pointer to const: you can read members and call other const members, and the compiler rejects writes to members and calls to non-const members.

Const correctness means marking every member function that does not change the object's observable state const, and taking parameters as const T& when you only read them. For a single thread it is compiler-checked documentation. For several threads it is more: the set of const functions is the set of calls that should be safe to run concurrently.

Physical versus logical constness

There are two ways to read "this function does not change the object".

  • Physical (bitwise) constness: not one bit of the object changes during the call. The compiler enforces a narrower rule: ordinary writes through const access are rejected, but mutable members and pointed-to objects are exceptions.
  • logical constness: the object's observable value does not change, even though some internal bits do: a cached result, a statistics counter, a lazily computed hash, a mutex being locked and unlocked.

A mutable member may be modified even inside a const member function. It exists for logical constness: state that is not part of the object's value. Locks, caches and counters qualify. Anything a caller could observe does not; if you find yourself making real data mutable, the function was never const.

mutable for a mutex inside a const getter

Here is the pattern you will write in nearly every thread-safe class. std::lock_guard calls lock(), which modifies the mutex. Inside a const member function every member is const, so without mutable the guard does not compile (clang reports that there is no matching constructor for std::lock_guard<std::mutex>, because it was handed a const mutex).

The final balance is always 1000; what the auditor saw depends on timing. The mutable keyword is honest here: the mutex is not part of the account's value, and locking it changes no balance.

The standard library's promise

The rule, in plain words: a standard library function does not modify any object other threads can reach, except through its non-const arguments, including this. Concurrent read operations on a safely published, live container are supported. User-supplied comparators and element operations must also avoid races. Non-const operations need closer inspection: containers explicitly permit some of them concurrently.

Containers add two refinements. For data race purposes, these count as const even in their non-const overloads: begin, end, front, back, data, find, lower_bound, upper_bound, equal_range, at, and operator[] except on maps and the other associative containers. And different elements of one container may be modified concurrently, except in std::vector<bool>, whose elements share bytes.

For a single counter, a mutable std::atomic<long> is enough, because fetch_add is atomic on its own. Two separate atomics do not automatically make a combined update or snapshot atomic; consistency across them needs an additional protocol.

Immutable objects need no locks

An immutable object gets all its state in the constructor and never changes afterwards. Any number of threads can use it with no locking at all, because there is no writer to race with. In C++, share it through a pointer to const, so no thread can even call a non-const member:

Two conditions keep this honest. The constness must be deep: no mutable members without synchronization and no pointers to data that others write. And the hand-off of the pointer itself must be synchronized; here thread creation does that. Swapping in a new version while readers run is the copy-on-write pattern, built in the smart pointer lesson and in copy-on-write and snapshots.

Worked example: an LRU cache whose get is a write

A read-heavy LRU cache seems like the perfect place for a read-write lock: shared lock in get, exclusive lock in put. Here is that version:

get is const and its result does not change the cache's contents, so it is logically a read. Physically it is a write: marking an entry as most recently used moves a node to the front of the list. Two threads holding the shared lock splice the same list at once, corrupting its links. A Blind thread about a Microsoft LRU question (2024) turns on exactly this point: every get moves an entry, so a read lock does not help.

The fix is to admit that get writes and take an exclusive lock. Whether you keep get const (with mutable internals, because the contents do not change) or make it non-const (because it reorders), the threading rule is the same: decide locks by what the code physically writes, not by what the name suggests.

If one lock becomes the bottleneck, the senior answers are sharding (several independent LRU caches, each with its own lock, chosen by key hash, giving an approximate global order) or not moving an entry that was moved very recently. Those come back in thread-safe caches.

Common mistakes

  • A const getter that writes a mutable cache without a lock. Two readers race. Lock it, or compute it in the constructor.
  • Reading a shared std::map with operator[]. It inserts missing keys and counts as a write. Use find or at.
  • "const means immutable." It is shallow, and other non-const aliases to the same object may exist.
  • const_cast to modify something. Writing to an object that was defined const is undefined behavior, and casting away const on shared data invents a race.
  • Making real data mutable so a function compiles. If callers can observe the change, the function is not const.
  • A shared (reader) lock around code that writes internally, such as an LRU get or a lazy cache fill.
  • Returning const std::string by value. The const blocks moving the result. Return plain std::string.

In the interview

You write long get() const with a std::lock_guard inside and the interviewer asks, "why is the mutex mutable?" Or, "is std::vector thread-safe?", "can two threads call find on one std::unordered_map?", and for caches, "can get take a read lock?". Precise answers here separate people who memorized "STL is not thread-safe" from people who know the actual contract.

The mutex is mutable because locking it modifies it, and inside a const member function every member is const. It is legitimate: the mutex is not part of the object's observable value, so get stays logically const.
The standard containers guarantee that concurrent const operations on one container do not race, and that different elements can be written concurrently, except in vector<bool>. Any operation that can change the container's structure, like push_back, insert or map::operator[], needs external synchronization against every other access, reads included.

Follow ups: "What does mutable mean on a lambda?" (a different use of the same keyword: it lets the call operator modify by-value captures, covered in lambdas); "How would you make a read-mostly class scale?" (a mutable std::shared_mutex, shared locks in truly read-only const functions, unique locks in writers, or immutable snapshots); "Is a const object safe to share without locks?" (only if its constness is deep and it has no unsynchronized mutable state).

Senior depth

const gained a threading meaning in C++11. Herb Sutter's 2012 talk "You Don't Know const and mutable" made the point widely known: because the standard library assumes const operations are safe to run concurrently, a const member function in your class should be either bitwise const or internally synchronized. mutable members should be things like mutexes and atomics, which are safe to change from const functions by design.

Compiler-checked locking. Clang's thread safety analysis (-Wthread-safety) can check comments like "guarded by m_" at compile time, using attributes such as GUARDED_BY and REQUIRES on annotated mutex types. Large C++ codebases use it to catch an unlocked read of a guarded member before any test runs.

Read-write locks pay off only when const really means read-only and the critical sections are long enough to outweigh the extra bookkeeping. A mutable std::shared_mutex with std::shared_lock in const getters is correct only if no const getter writes anything, cache or statistics included.

Key takeaways

  • Mark everything that does not change observable state const; for threads, the const functions are the ones that should be safe to call concurrently.
  • mutable is for state outside the object's value: mutexes, caches, counters. A const getter that locks needs mutable std::mutex.
  • Concurrent container reads are supported, including specified non-const overloads such as find and at. Distinct existing elements may be modified concurrently, except in vector<bool>; conflicting accesses still need synchronization. map::operator[] is excluded from the const-operation guarantee.
  • A mutable cache written without a lock turns two "readers" into a data race.
  • const is shallow. Immutable objects shared through std::shared_ptr<const T> need no locks, provided their constness is deep and the hand-off is synchronized.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Explain logical versus physical constness, and why the mutex in a thread-safe class is mutable, as you would to an interviewer.
Model answer

Physical constness means no bit of the object changes. The compiler does not enforce that fully: const access still permits modification of mutable members and pointed-to objects. Logical constness means the object's abstract value does not change, even if internal bookkeeping does: a cache, a counter, a lock. mutable is the escape hatch for bookkeeping outside that abstract value.

A thread-safe getter must lock, and locking modifies the mutex, so in a const function the mutex has to be mutable. That is the textbook legitimate use: the mutex is not part of the value, it exists precisely to make const calls safe to run concurrently. And that is the contract C++ code is expected to keep, because the standard library assumes it: concurrent const calls on one object must not race. So any mutable state my const functions touch must itself be synchronized, by that mutex or by being atomic.

Write code
Make this class const correct and safe for many threads: class Sensor { std::vector<double> readings_; double cached_average_; bool dirty_; public: void add(double r); double average(); };
Model answer

average becomes const because it does not change the sensor's observable value. The cache and the mutex are mutable because they are bookkeeping, and the cache is only touched under the mutex, so two concurrent average calls cannot race. std::optional replaces the separate dirty_ flag, so the flag and the value can never disagree. add takes the same lock, appends, and invalidates the cache.

Debug
A read-mostly lookup table uses a mutable std::shared_mutex: lookup() const takes a std::shared_lock, insert() takes a std::unique_lock. A teammate adds hit counting to lookup: hits_[key] += 1; where hits_ is a mutable std::unordered_map<std::string, long>. What breaks, and how would you fix it?
Model answer

Many threads hold the shared lock at the same time, so many threads now run hits_[key] += 1 concurrently. That is a data race twice over: concurrent increments of the same counter lose updates, and operator[] may insert a new key, rehashing the map while other threads walk it, which can crash. The const and the shared lock both say "read-only", and the code no longer is.

Fixes, depending on needs: keep the counts out of the shared structure, for example per-thread counts in a thread_local map merged periodically; or give the stats their own mutex, taken briefly inside lookup, accepting some contention; or preallocate one std::atomic<long> per key when the key set is fixed, so lookup only does fetch_add with no structural change. Taking the exclusive lock in lookup also works, but it throws away the read concurrency the table was built for.

Out loudabout 60 s
"Your balance getter is const, but its mutex is mutable. Explain why that is legitimate and whether const makes the getter thread-safe."
What a strong answer covers
  • The getter preserves the account's logical value even though locking changes internal mutex state
  • A const member function cannot lock an ordinary non-mutable mutex member
  • Mutable permits modification through const access but supplies no synchronization
  • Readers and writers protect the balance with the same mutex
  • Const access is shallow and does not stop writes through other aliases
How a senior would say it
The getter is logically const because reading the balance does not change the account's value. Locking still changes the mutex's internal state. Through a const member function, an ordinary mutex member would be const, and its lock operation requires a non-const mutex. Declaring that member mutable allows this bookkeeping without making the balance mutable. The keyword supplies permission to modify the member, not synchronization. The actual safety comes from the getter and every writer taking the same mutex around the balance. A const qualifier alone does not make a user-defined function safe to call concurrently. It can still write a mutable cache, or follow a pointer to shared data. A const reference also does not stop another alias from modifying the account. I would therefore explain constness as the interface promise and the mutex protocol as the mechanism that keeps concurrent access safe.

Likely follow up: Why would returning a const reference to a protected string be risky after the getter releases its lock?

Out loudabout 75 s
"Two callers use a const getter under shared locks. You add a lazy cache and now ThreadSanitizer reports a race. What happened, and which fix would you choose?"
What a strong answer covers
  • Shared locks admit both callers; filling the cache is a physical write despite logical constness
  • Unsynchronized conflicting accesses are a data race even when both compute the same result
  • An exclusive lock must protect checking, computing or publishing, and reading the cache
  • For immutable input, eager computation or call_once can avoid repeated cache locking
  • Changing input requires synchronized invalidation; call_once is not a resettable cache mechanism
  • Choose lock mode by actual writes, including LRU recency updates
How a senior would say it
The getter stopped being physically read-only when it began filling the cache. Shared locks let both callers enter, so both can see an empty cache and write its value and readiness state. That is a data race and undefined behavior, even when they compute the same answer. My simplest fix is an exclusive lock protecting the cache check, initialization and read. If the input never changes, I would also consider computing eagerly in the constructor. That removes lazy writes entirely, provided the finished object is safely published. If computation is expensive and often unused, call_once is a good alternative for one successful initialization. If the input can change, I need writers to invalidate the cache under the same protocol; a once flag is not resettable and does not solve that case. I would choose using the cost of computation and the update pattern, then measure contention. The same reasoning applies to an LRU getter: it may return a value without changing that value, but moving its list node is still a write. Lock mode follows the implementation's accesses.

Likely follow up: Would making only the cache's ready flag atomic be enough, and what publication and initialization rules would still be needed?

Out loudabout 75 s
"A teammate says STL containers always need a mutex. Another says const access is always safe. Give me the precise rules you would use in a review."
What a strong answer covers
  • Concurrent standard container read operations are supported with safe publication and lifetime
  • Certain non-const overloads count as const for data races, such as find and at; associative operator[] does not
  • Existing distinct vector elements may be updated concurrently without structural changes
  • Vector is excluded from the distinct-element guarantee
  • Structural changes and same-element conflicting access need appropriate synchronization
  • Safe individual calls do not make a multi-call check and update atomic
How a senior would say it
I would inspect which operations run together and which memory they touch. Standard containers support concurrent read operations on a safely published, live container. The rules also treat some non-const overloads as const for data races, including find and at. Map subscript is excluded because it can insert a missing key, so I would use find or at for lookup. A pre-sized vector of integers allows two threads to modify different existing elements while its structure stays fixed. The packed vector of bool is excluded from that guarantee, because separate bits can share storage. If threads access the same element and one writes, I need synchronization for that element. If an operation changes the container's structure, such as push_back, I need to coordinate accesses that can conflict with metadata changes or invalidation. A mutex around those operations is the straightforward design. Finally, safe individual calls do not make a check followed by an insertion atomic. I would protect that whole decision with one protocol. Const is useful information, but I still check aliases, element behavior and the complete operation.

Likely follow up: Would reserving enough vector capacity make concurrent push_back and size safe?
