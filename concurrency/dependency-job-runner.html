A parallel job runner that respects dependencies

Run dependent jobs in parallel on N workers, reject cycles, and join every worker after success or cooperative cancellation.

Asked atRubrikUberAppleMicrosoft
Before this:An executor without libraries: submit, wait for all, shutdown and shutdownNowCondition variables and monitors

Rubrik reports repeatedly describe this pattern, with variants and follow ups: a pipeline manager, a job runner, a scheduler for overnight tasks. Run jobs in parallel as soon as their dependencies have succeeded, and stop everything on the first failure.

In plain words

Think of building a house with a team of three workers. The foundation must be done before the walls; plumbing and wiring both need the walls but not each other, so two workers can do them at the same time; painting needs both. A good site manager keeps one list on the wall: for each job, how many jobs it is still waiting for. When a job finishes, the manager crosses it off and reduces the count of every job that was waiting for it. Any job whose count reaches zero goes on the "ready" board, and a free worker takes it.

If the wiring catches fire, the manager does two things at once: nobody starts anything new, and everyone still working is told to put their tools down. The manager reports "wiring failed" only after the last worker has actually stopped, so nothing is left running when the report goes out. And if the plan says painting needs plumbing, plumbing needs painting, the manager refuses the plan before anyone picks up a brick.

The question in its reported forms

  • Pipeline manager (senior, 2024): jobs form a directed acyclic graph; each job's doWork() may throw; execute() ends on full success or on the first failure, with no job left running.
  • Job runner (G6, 2025): given getDependentTasks(completed) and tasks with doWork(); the first exception must stop everything immediately; library queues and executors are banned, so you build them with locks. Clarify which primitives are allowed.
  • Scheduler (L4, 2025): get_next_jobs(finished_jobs) returns the runnable jobs; run every available job concurrently while respecting dependencies.
  • Overnight tasks (screen, 2024): tasks doing I/O and network calls, an API that returns what can run now, maximum concurrency, no ExecutorService.
  • Graph problem (G5, 2025): solvable with a topological sort, graded on code quality, then "how do you make it thread-safe?"

Outside Rubrik, an Uber machine coding round asked for a multithreaded job scheduler with prerequisites and maximum parallelism, an Apple screen asked to optimize a topological sort for multi-core execution, and a Microsoft LLD round asked for a cron or Airflow style scheduler with dependencies and thread safety. Two API shapes cover all of them: the whole graph given up front, or an oracle that tells you what can run next. Build the first, then adapt it.

The design: count what each job is waiting for

Kahn's algorithm, the classic topological sort, already contains the parallel runner. Keep, for every job, the number of dependencies that have not yet succeeded. Jobs at zero are ready. When a job succeeds, decrement the count of each job that depends on it, and any count that reaches zero puts that job on the ready queue.

The shared state, all under one lock:

  • waitingOn[job]: unfinished dependencies, and dependents[job]: who waits for this job;
  • ready: jobs whose count is zero and that have not started;
  • running: how many jobs are executing right now;
  • firstFailure: empty until a job fails, then the error and the job's name.

Each of N workers loops: take a ready job under the lock, run it outside the lock, then come back under the lock to record the outcome. One lock is the right granularity here. Jobs run outside it, and the critical sections only touch a few counters, so this is a useful baseline. Tiny jobs or very large fan-outs can still make this lock a bottleneck; measure before replacing it.

The termination rule

The subtle part is knowing when a worker may leave. "Ready is empty" is not enough: a running job may finish in a moment and release three more. The rule that works is:

Wait while nothing is ready but something is running. If nothing is ready and nothing is running, no job can ever become ready again, so exit.

It holds because only a finishing job can make another job ready. With nothing running, nothing will finish, so the ready queue stays empty forever. For a validated static DAG, that means success. A recorded failure lets idle workers exit immediately, while the caller joins the remaining workers. Without validation, quiescence could instead mean a cycle: compare completed jobs with the total before claiming success.

Stopping on the first failure

"Stop everything" has three parts, and interviewers check each one:

  1. No new job is claimed after failure is recorded. Record the failure and clear the ready queue in the same critical section. Workers check the failure field under the lock before taking a job. Claiming a job is its scheduling start: a worker that claimed before the failure can enter the job body later, so jobs must check cancellation before side effects.
  2. Running jobs are asked to stop. Java: interrupt exactly the workers that are running a job (keep them in a set under the lock). C++: request a stop on a std::stop_source whose tokens every job received. Jobs must cooperate: an interrupt or a stop request is a request.
  3. The call returns only when nothing is running. Idle workers exit when the failure is set; busy workers exit after their own job ends; run() joins them and then reports the first failure. Later failures (often caused by the stop request itself) are ignored.

Here, "first" means the first failure recorded under the lock, not necessarily the first exception thrown in wall-clock time. Cancellation cannot force an arbitrary job to finish: a job that ignores it, blocks forever, or leaves detached work behind violates the job contract. Jobs must finish their own child work before returning. There is no finite return-time guarantee without a cancellation or completion bound.

One more rule hides in step 2: a job that stopped early may return normally. It must not count as a success, or its dependents would start. The runner only releases dependents when no failure has been recorded.

Cycles

Run Kahn's algorithm once, single-threaded, on a copy of the counts before starting any worker. Every job that never reaches zero is on a cycle or depends on one. Rejecting the plan up front beats discovering it at the end, after half the graph has already run and produced side effects.

The full runner

The demo builds a six-job pipeline, then a fresh runner with one failing job, then a cyclic graph. Configuration and run() belong to one caller, without concurrent or reentrant calls: the graph is frozen when run() begins and the runner is single use. Reject duplicate names, unknown dependencies, empty names, null jobs and nonpositive worker counts; repeated dependency edges count once. An empty graph succeeds.

The code uses Java 21 locks and conditions and C++20 stop tokens. With only Java monitors allowed, use one monitor with wait loops and notifyAll, retaining the same bookkeeping. For C++17, use std::thread with explicit joins and a shared cancellation flag; blocking jobs also need a wakeup mechanism or a bounded wait. The demo delays simulate work; they do not prove a particular schedule. Infrastructure allocation failures during bookkeeping and fatal runtime failure are outside this teaching implementation.

The output above is one Java schedule; C++ prints a stop-token message and formats the cycle list differently. Scheduling may change the order of independent jobs.

Points worth saying while you write it:

  • The wait condition is the termination rule. Java's while (ready.isEmpty() && running > 0 && firstFailure == null) and the C++ predicate are the same sentence: sleep only if there is nothing to take, someone may still produce work, and nothing has failed.
  • signalAll after every outcome. One finishing job can release several jobs, make the run finished, or record a failure, and different idle workers need to see different things. notify_one here can leave a worker asleep at the end.
  • Interrupt only the busy (Java). The runner tracks which workers are running a job and interrupts exactly those, under the lock. Each worker clears its own flag under the same lock after its job ends, so an interrupt aimed at an old job never leaks into a wait or a later job.
  • One stop source for the run (C++). Every job gets a token from the same std::stop_source, and the first failure calls request_stop(). Stop-state operations are thread-safe. Call request_stop() outside the scheduler lock: it synchronously invokes registered callbacks, which must finish promptly and must not throw. The failure flag already prevents new claims during this gap.
  • Only the first failure wins. The check firstFailure == null happens under the lock, so two jobs failing at the same moment cannot both claim it. The jobs that end with an error because they were stopped are ignored.

A third worker cannot shorten this ideal schedule, and that observation is a good thing to say when asked "how many threads?".

Now make parse-b fail at 50 ms. In that critical section the runner records the failure, clears the ready queue (already empty) and interrupts W1, which is in parse-a's sleep. W2 sees the failure and exits. W1's job throws InterruptedException at about 50 ms; its error is ignored because a failure is already recorded; running drops to 0 and W1 exits. run() joins both and reports "job parse-b failed", with nothing left running.

The oracle variant

Some Rubrik versions hide the graph behind an API: you call getNextJobs(finished) with the set of finished jobs and get back the jobs that may run now. These changes adapt the runner:

  1. Dedupe. If the oracle returns every job that is runnable, including ones you already started, keep a started set and only enqueue jobs you have not seen. The name means reserved here: insert on enqueue, not when a worker later starts. First call the oracle with an empty finished set to discover roots.
  2. Call it with a consistent snapshot. Call the oracle while holding the lock (simplest, and it serializes calls if the oracle is not thread-safe), or have a single coordinator thread own the finished set and the oracle while workers only run jobs and report back. If the oracle is slow, say I/O bound, prefer the coordinator so the lock is never held across a slow call.
  3. Define quiescence. Assume a finite static job universe and a synchronous oracle. A coordinator calling the oracle outside the lock must count that discovery as in flight, or workers could mistake a temporarily empty queue for completion. Treat oracle exceptions as run failures. Without an expected job set or a completion signal, an empty oracle result cannot distinguish success from blocked hidden jobs.
  4. Cycles cannot be checked up front. You do not see the graph. The termination rule still ends the run; afterwards, a run that ended with no failure but without every expected job finished means something could never start.

Prove the invariants and test the boundaries

For V jobs and E edges, each edge is processed once in validation and at most once in execution. Indexed adjacency lists give O(V + E) bookkeeping and storage. Java hash maps give expected linear bookkeeping with bounded-cost keys; the C++ std::map and std::set version adds logarithmic lookup and construction costs, roughly O((V + E) log(V + 1)) for bounded-size names. Broadcasting after completions can also add worker wakeup overhead.

Publication matters as much as ordering: a predecessor writes its result before taking and releasing the scheduler lock at completion. A successor acquires that same lock to claim its job before reading the result. That establishes the needed happens-before path. Independent jobs still need their own synchronization if they share mutable output. A lower bound on ideal duration is the larger of total work divided by N and the critical-path duration; real execution adds overhead.

Test an empty graph, one worker, disconnected roots, a diamond whose child must run exactly once, duplicate edges, unknown jobs, duplicate names, invalid worker counts, and a cycle with a downstream tail. Use gates to force sibling overlap and a failure while another job is active; verify cancellation, no descendant execution and zero active jobs after return. Interrupt the Java caller while it joins, and simulate startup failure when a test seam permits it. Progress assumes workers get scheduled and every job eventually returns or honours cancellation.

Common mistakes

  • Exiting when the ready queue is empty. Workers leave early and the pool loses its parallelism, or, with the opposite mistake, they wait forever at the end. Use the two-part rule.
  • Releasing the dependents of a failed job. Decrement counts only on success, and only while no failure is recorded, or the next stage starts on bad input.
  • Returning from run() while jobs still run. The prompt says nothing is left running. Wait for running to reach zero (join the workers) before reporting the failure.
  • Running the job under the lock. Every job would run one at a time, which is a sequential topological sort with extra steps.
  • Checking the failure flag without the lock. A worker reads "no failure", another thread records one and clears the queue, and the first worker then starts a job anyway. Check and take in the same critical section.
  • Interrupting idle workers, or every worker. An interrupt delivered to a worker between jobs leaks into its next wait or job. Track the busy workers and clear the flag after each job.
  • A thread per job. Easy to write, and the prompt usually says N threads. A 10,000 job graph would start up to 10,000 threads.

In the interview

Practise starting with a single-threaded topological sort, then answering "make it run on N threads", then "what if a job throws", then "stop everything immediately", then "what if there is a cycle" or "what if you only get getNextJobs". Interviewers have graded this one on code quality and LLD too, so keep the graph bookkeeping, the worker loop and the job interface separate.

I keep, for each job, the number of dependencies that have not succeeded, and a ready queue of jobs at zero, all under one lock. N workers take ready jobs and run them outside the lock. On success a worker decrements its dependents and enqueues any that reach zero; on failure it records the first error, clears the ready queue and asks the running jobs to stop. A worker waits only while nothing is ready and something is still running; when both are empty, no job can ever become ready, so it exits. run() joins the workers, so it returns only when nothing is running, and a cycle is rejected up front by running Kahn's algorithm on a copy of the counts.

Follow ups to prepare: "how many threads?" (the critical path bounds the speedup; for I/O bound jobs more threads help until the slowest shared resource saturates), "retry a failed job twice before failing the run", "keep running branches that do not depend on the failure", and "how do you test it?" (a graph with known parallelism, a job that blocks until its sibling starts to prove they overlap, a failing job plus a slow job to prove nothing keeps running).

Senior depth

  • Retries. Keep descendants blocked while a retry is pending. Release each outgoing edge once, only after final success. Use bounded attempts, cancellable backoff and idempotent effects; quiescence must include delayed retries, not just running jobs. Do not sleep under the scheduler lock.
  • Keep going instead of failing fast. make -k style: on failure, mark the failed job's descendants as skipped (a graph walk from the failed job) and keep running every job that does not depend on it. Report all failures at the end.
  • Which ready job first? When workers are scarce, start jobs on the longest remaining path first (critical path first). It is the classic list scheduling heuristic and often shortens the run noticeably on lopsided graphs.
  • Resource limits per job type. A semaphore can enforce "at most 2 database jobs", but waiting for permits inside workers can occupy the entire pool. To preserve useful parallelism, reserve capacity during dispatch and release it at completion, with cancellation waking the scheduler.
  • Without a central lock. Give each job an atomic count; whoever decrements a count to zero submits that job to the pool. In Java the library version is CompletableFuture.allOf(dependencies).thenRunAsync(job, pool). This needs atomic read-modify-write decrements and a thread-safe submission queue, including publication of predecessor results. allOf takes a future array, thenRunAsync takes a Runnable, and exceptional completion suppresses that dependent action; this expression alone neither cancels siblings nor implements the full fail-fast contract. The one-lock design is easier to explain and audit.
  • Across machines. Airflow style schedulers keep job state in a database, hand out jobs with leases, and need jobs to be idempotent, because a worker can die after doing the work but before reporting it. See idempotency and exactly-once effects.

Key takeaways

  • Count unfinished dependencies per job; a job whose count reaches zero goes on the ready queue. That is Kahn's algorithm, made parallel.
  • One lock over the counts, the ready queue, the running count and the first failure; jobs run outside it.
  • Wait while nothing is ready and something runs; exit when nothing is ready and nothing runs.
  • After failure is recorded: no new job is claimed, running jobs are asked to stop, and run() returns only after they have ended.
  • Reject cycles before running by checking which jobs a single-threaded Kahn pass can never release.

Quick check

Answer each question, then read why. Your score is saved for your module test.

In the DAG runner, when may an idle worker safely exit?
Why. Only a finishing job can make another job ready. If nothing is running, nothing will finish, so an empty ready queue stays empty forever and the worker can leave. Exiting on "ready is empty" alone gives up workers while a running job may still release more work, and "running is zero" alone is true at the very start, when the roots are waiting in the ready queue.
Job A has no dependencies; B, C and D each depend only on A; E depends on B, C and D. The runner has 4 threads and every job takes the same time. What is the largest number of jobs running at once?
Why. A runs alone. When it finishes, B, C and D all reach zero and run together on three threads. E waits for all three. At most three workers can be busy at once. One or two understates the available sibling parallelism; four exceeds what the dependencies permit.
A buggy runner releases dependents of a failed job under the lock, unlocks, and only later records the failure. What can another worker do in that gap?
Why. Decrementing on failure tells the dependents that their input succeeded. Another worker may claim the newly ready dependent before failure is recorded. If failure were already recorded and every claim checked it under the same lock, an incorrect enqueue alone would not let that dependent run. One erroneous decrement per edge need not make a count negative, and preflight cycle validation has already happened. Release dependents only on success, and only while no failure is recorded.
Kahn's algorithm finishes with some jobs whose waiting count is still above zero. What are those jobs?
Why. A job on a cycle can never reach zero because its cycle partner never finishes, and a job downstream of the cycle waits for something that never finishes either. In the demo, d is not on the cycle a, b, c, yet it can never start. To name the cycle itself, follow the remaining edges or run a depth-first search with colours.
The prompt says: "on the first failure, stop, with nothing left running". Which behaviour meets it?
Why. Returning at once leaves work running behind the caller's back, which the prompt forbids. Killing threads is not possible safely in either language, so stopping is a request (an interrupt or a stop token) and the runner waits for running to reach zero. Letting independent branches finish is a different policy ("keep going") that you may offer as a follow up.
Which properties does the one-lock, count-per-job design guarantee? Select all that apply.Select all that apply
Why. Counts reach zero only through successful dependencies; each edge causes at most one execution decrement, and only N workers take jobs. Linear edge visits do not make the map-based C++ implementation linear-time. The start order among ready jobs depends on timing, so it varies between runs. Total work divided by N and the critical-path duration are both lower bounds in the ideal model. Dependencies can prevent achieving the work-divided-by-N bound.
Java onlyWhy does the Java runner use awaitUninterruptibly() for idle workers and still stay correct under its own cancellation interrupts?
Why. Interrupts are sent under the lock, only to threads in the busy set. A worker leaves that set under the same lock and clears its flag there, so runner-generated interrupts cannot reach a waiting worker. This assumes outsiders do not interrupt private worker threads; awaitUninterruptibly() itself preserves the interrupt status and does not provide cancellation. Interrupts can be delivered to threads waiting on a Condition (plain await() would throw), which is exactly why the runner is careful about whom it interrupts.
C++ onlyAfter the first failure, parse-a sees its stop token, stops early and returns normally, with no exception. Why does the C++ runner not start parse-a's dependents?
Why. A job that stopped early did not complete its work, yet it returned normally. The runner protects against that by releasing dependents only under the condition "no error and no recorded failure". Stop tokens carry no result; they are only a request the job may observe.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Design
The interviewer changes the API: you no longer get the graph. You get getNextJobs(finished), which returns the jobs that can run given the set of finished jobs. What changes in your runner, and what new risks appear?
Model answer

The counts and dependents lists go away. On every success, under the lock, I add the job to a finished set and call getNextJobs with a snapshot of it. If the oracle repeats already discovered jobs, I keep a started set and enqueue only jobs I have not started. At the start I call it with the empty set to get the roots.

New risks: the oracle may not be thread-safe, so I either call it under the lock or give it to a single coordinator thread that owns the finished set, with workers only running jobs and reporting outcomes through a queue. If the oracle is slow (it does I/O), the coordinator design avoids holding the lock across a slow call. I can no longer reject a cycle before starting, because I never see the graph; the termination rule must also account for in-flight oracle calls, and if the run ends with no failure but with jobs the caller expected still unfinished, I report that they could never start. Fail fast is unchanged: record the first failure, stop asking the oracle, ask running jobs to stop, and return after they end.

Write code
Write the cycle check on its own: given each job's dependencies, return the jobs that can never start.
Model answer

With bounded-size names the Java hash-map version is expected O(V + E); C++ ordered maps add a log(V + 1) lookup factor. Both use O(V + E) storage. Every dependency must itself be a job; validate that first or a missing job is indistinguishable from a cycle. Here duplicate edges are counted and removed consistently, although deduplication is usually a clearer API contract.

Explain
The interviewer asks: "Convince me that your runner never starts a job too early, never hangs, and returns only when nothing is running."
Model answer

Never too early: a job enters the ready queue only when its waiting count reaches zero, and a count is decremented only when one of its dependencies succeeds, under the lock, while no failure is recorded. So by the time a job is ready, every dependency has succeeded. Workers take jobs only from the ready queue, under the same lock.

Progress, assuming jobs terminate and workers are scheduled: a worker sleeps only while the ready queue is empty, some job is running, and no failure is recorded. Every finishing job takes the lock, updates the state and signals all workers, so each change that could end a sleep is announced after it happened, under the lock the sleepers check. When the last running job finishes with nothing ready, the sleepers wake, see nothing ready and nothing running, and exit. Cycles are rejected before starting, so every job in an accepted graph eventually becomes ready unless a failure stops the run.

Nothing left running: after the first failure, the ready queue is cleared and no worker takes a new job, because the failure check and the take happen in one critical section. The running jobs are asked to stop, and workers exit only when they see the failure and finish their own job. run() joins every worker before reporting, so when it returns, no job is executing.

  • Wait only while ready is empty, running is positive and no failure is recorded
  • Broadcast completion changes and join workers before returning
  • Reject cycles before execution and state the job-termination assumption
How a senior would say it
I would use a ready queue and a count of unfinished dependencies for each job. I validate the whole graph with a topological pass before starting workers, so a cycle cannot cause partial execution. Initially, only roots enter the ready queue. One lock protects the queue, dependency counts, running count and failure state. A worker claims a job and increments the running count under that lock, then releases it before invoking user code. When the job succeeds, the worker takes the lock again, decrements its children's counts and enqueues each child that reaches zero. For example, if two parents feed one child, the first completion leaves the count at one and only the second releases it. The worker then broadcasts the state change. An empty queue alone does not mean completion: a running parent could release more jobs. A worker waits while the queue is empty, something is running and no failure is recorded. Without ready or running jobs, it can leave. On failure, idle workers can leave immediately, and the caller joins everyone before reporting. This progress argument assumes the jobs eventually finish and workers get scheduled. It does not make an arbitrary blocking job terminate.

Likely follow up: How does a child's read of its parents' results become safe even though jobs run outside your lock?

Out loudabout 75 s
"A job fails. Can you promise to stop immediately and return with nothing still running?"
What a strong answer covers
  • Separate immediate rejection of new claims from cooperative cancellation and eventual return
  • Record the first observed failure and clear ready work under the claim lock
  • Treat already claimed jobs as running, even before their bodies execute
  • Interrupt busy Java workers or request the shared C++ stop token outside callback-sensitive locks
  • Join every worker and state that uncooperative jobs prevent bounded completion
How a senior would say it
I can stop admitting new jobs immediately after recording failure, but I cannot promise that arbitrary running code stops immediately. Under the same lock used to claim work, I record the first failure and clear the ready queue. Another worker then either claimed its job before that point or sees the failure and exits. An already claimed job might enter its body afterwards, so it should check cancellation before side effects. I interrupt busy workers in Java, or request the shared stop source in C++. In C++, I make that request outside the scheduler lock because registered stop callbacks can execute synchronously. A job that returns early after cancellation must not release its dependents. Finally, I join every worker and report the recorded failure. That guarantees nothing remains running when the call returns, assuming jobs also join any child work they created. If a job ignores cancellation or blocks forever, the call may never return. A timeout can report that situation, but cannot safely kill an arbitrary thread or undo its effects.

Likely follow up: What must happen if the caller itself is interrupted while joining the Java workers?

Out loudabout 60 s
"Now the graph is hidden. An API returns jobs that are ready given the finished set. What changes?"
What a strong answer covers
  • Discover roots using an empty successful-completion set
  • Deduplicate on enqueue and add only successful jobs to the finished set
  • Serialize oracle access with a consistent snapshot, preferably through a coordinator for slow calls
  • Count in-flight discovery when deciding termination and treat oracle errors as failures
  • Require an expected job universe or explicit completion signal to distinguish hidden blockage from success
How a senior would say it
I replace the dependency counts with discovery through the API. I first call it with an empty finished set to find roots. Whenever a job succeeds, I add it to that set and ask again. I deduplicate when enqueuing, because the oracle may repeatedly return a job that is already queued or running. Calls need a consistent snapshot and serialized access if the oracle is not thread-safe. For a slow oracle, I would use one coordinator so workers never hold the scheduler lock across I/O. Discovery itself counts as outstanding work; otherwise an empty queue could look finished while an oracle call is still running. Oracle errors follow the same failure policy as job errors. I cannot validate hidden cycles up front. Without an expected job set or an explicit completion signal, no ready jobs could mean either completion or permanently blocked work.
