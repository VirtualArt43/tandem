Blocking, lock-free and wait-free

The four progress guarantees, from blocking to wait-free, with examples of each, when they matter, and why lock-free is not automatically faster.

Before this:A lock-free stack and the ABA problemSpinlocks, backoff and when spinning beats blocking

"Is your solution lock-free?" is a precise question with a precise answer. Lock-free, wait-free and obstruction-free are promises about what happens when threads are delayed, not about speed, and mixing them up is one of the quickest ways to lose credibility in a senior round.

In plain words

Picture a meeting where only the person holding the talking stick may speak. If the holder dozes off, nobody can talk until they wake up. That is blocking: one stalled participant can stop everyone.

Now a meeting without a stick. People just start talking; if two start at once, both stop and try again. If at least one sentence always gets finished, the meeting is lock-free, even if one shy person keeps getting talked over. If there is a rule that guarantees everyone finishes their sentence within a few tries, it is wait-free. And if you can only promise that a person finishes when everyone else goes quiet for a moment, it is merely obstruction-free.

The question that defines them

Every progress guarantee answers one question: if some threads are stopped at the worst possible moment, what can the others still do? The model lets a participant pause indefinitely while other participants keep taking steps. Preemption and page faults can resemble that pause. A stop-the-world collection stops every application thread, so none can make progress during it.

GuaranteeThe promiseWhat a stalled thread can do to others
BlockingAn operation may depend on another participant. Deadlock-freedom and starvation-freedom need additional assumptionsStop everyone who needs what it holds, for as long as it is stalled
obstruction-freeA thread that runs alone, with all others paused, finishes its operation in a bounded number of stepsNothing while paused; but running threads can keep undoing each other's attempts (livelock)
lock-freeContinued execution of pending operations guarantees system-wide completions, but not completion of a particular callerCannot stop system-wide completions by the remaining active threads; an individual can still starve
wait-freeEvery thread finishes every operation within a bounded number of its own steps, whatever the others doCannot prevent an active caller from finishing within its step bound

They nest: every wait-free algorithm is lock-free, and every lock-free algorithm is obstruction-free. These guarantees apply to a specified operation, not automatically to every method of a class. The last three are together called non-blocking. Blocking is outside all of them, because a thread holding a lock is exactly the "something others must wait for" that the non-blocking guarantees rule out.

See the difference

Latches deliberately pause one worker while the main thread probes the same object. First it tries a lock held by the paused worker. Then it updates an atomic counter after another worker has read the old value but before that worker attempts CAS. The coordination fixes the interleaving without relying on sleep durations.

The holder prevents lock acquisition until it resumes; the updater's saved local value prevents nobody else from updating the counter. Its stale CAS then fails and it retries with 1. The latches are blocking test instrumentation, and this single schedule illustrates the distinction rather than proving lock-freedom. std::latch is C++20; a C++17 demo can coordinate with a mutex, condition variable and predicate.

Steps are not milliseconds. A wait-free step bound counts work done by the caller under stated primitive assumptions. It does not schedule a paused thread, bound a page fault or promise a deadline. A bound may depend on a fixed participant count or input size; it must not depend on other participants eventually cooperating.

Examples of each

CodeGuaranteeWhy
synchronized, ReentrantLock, std::mutexBlockingA descheduled holder stops every waiter
A spinlock built from compare-and-swapBlockingSpinning is still waiting for the holder; using CAS does not change that
A fair lock (FIFO, ticket lock)Blocking; can be starvation-freeRequires continued scheduling, finite critical sections and an admission policy without bypass

A native atomic add treated as a bounded primitiveWait-free in that machine modelOne primitive step; this is an assumption about the target, not a Java or C++ API guarantee
An atomic add implemented by load-linked, store-conditional retriesMay be lock-free, without a per-caller boundInterference can force retries; inspect the implementation and its progress assumptions

Two rows deserve a second look. The spinlock row is the most common confusion in interviews: "no lock() call in my code" does not mean lock-free. If any thread can be forced to wait until a specific other thread does something, the algorithm is blocking. The atomic-add rows show why the same source operation can have different implementations. Neither Java 21 nor C++20 promises wait-freedom merely because the API performs one atomic operation. Even a single machine instruction does not establish a wall-clock deadline.

Starvation: the gap between lock-free and wait-free

In a correctly structured CAS update loop, a strong CAS mismatch shows that the shared value changed. If every such change advances an operation and the remaining work is finite and non-blocking, continued retries imply system-wide progress. A weak CAS may fail spuriously, so each individual failure need not mean another success. But nothing stops one unlucky thread from losing every race, forever in theory and for a long time in practice under heavy contention, for example a thread doing more work between its read and its CAS.

Wait-free algorithms close that gap, usually with helping: a thread that sees another's operation in progress finishes it on its behalf, so every operation completes within a bound. Helping needs operation descriptors that remain alive while helpers use them, a way to claim completion exactly once, and a policy that bounds how long a pending request can be bypassed. Helping alone is not a wait-free proof; the bound is. Its extra work can affect throughput, so compare implementations under the actual workload.

When the guarantee matters

  • Latency isolation. With locks, a descheduled holder can delay waiters until it resumes. Lock-free protocols let other active threads continue, which can reduce the tail-latency impact of that stall; an individual caller can still starve.
  • Restricted execution contexts. A signal handler must not take a mutex held by the code it interrupted. C++ permits the defined plain lock-free atomic operations in signal handlers, not arbitrary allocation, logging or an entire container built around them. Real-time audio and control paths additionally need bounded work, preallocated storage and a scheduling and timing analysis; lock-freedom alone is insufficient.
  • No dependency on a lock owner inside the protocol. Lock-freedom removes the classic lock-holder convoy and lock-based priority inversion for that operation. It does not make the whole application deadlock-free or give a high priority caller bounded latency: retries, scheduling and surrounding locks still matter.
  • Paused participants, not crash recovery. Tolerating a halted participant in the algorithmic model does not establish interprocess or persistent-memory correctness. Shared mappings, address representation, allocation and recovery need separate protocols. A stalled reader can also prevent epoch reclamation until memory runs out.

Why lock-free is not automatically faster

Lock-free code is often sold as fast code. It is a different trade-off:

  • The hot spot is still there. A Treiber stack's head is one cache line, just as a lock is. Under heavy contention every operation still moves that line, and failed attempts add traffic without progress. A good mutex lets one thread work while the rest sleep, which can give more throughput.
  • Uncontended locks are cheap. Many mutexes have a user-space fast path when uncontended. The exact instruction count and cost depend on the implementation; measure instead of assigning a universal nanosecond cost.
  • Extra work per operation. Allocation per push, helping with queue metadata, version stamps, and in C++ hazard publication, validation and reclamation scans all add work. CAS counts and fence costs depend on the algorithm and implementation.
  • The guarantee is only as strong as everything inside. An operation that calls a general-purpose allocator may take the allocator's internal locks, and a Java operation can be paused by a stop-the-world garbage collection like every other thread.
  • Complexity is a cost. ABA, reclamation and memory ordering bugs are subtle and rarely caught by tests.

An immutable snapshot can make reads cheap, while oversubscription can make lock-holder delays expensive. Neither pattern proves a particular implementation will win; allocation, reference counting and contention can change the result. For throughput: measure first.

Worked example: classify these

A counter incremented with synchronized (or a std::mutex). Blocking. A holder descheduled mid-increment stops every other incrementer.

The same counter guarded by the test-and-test-and-set spinlock from lesson 07-04. Still blocking. Spinning is waiting, and the waiters depend on one specific thread releasing the flag.

AtomicLong.incrementAndGet() on an x86 server. The API alone does not establish wait-freedom. If the selected JIT implementation uses a native atomic add and the analysis treats it as a bounded primitive, the update is wait-free in that model; x86 and the method name alone do not prove that premise.

ref.updateAndGet(list -> append(list, x)) building a new immutable list. The update protocol uses CAS retries, but the callback and allocator are part of the full method. Classify the protocol as lock-free only under non-blocking callback, allocation and atomic assumptions. The callback must be side-effect-free because it may be reapplied, and repeated list copies can make contention expensive.

A mutex-based bounded queue whose put waits while the queue is full. Blocking, twice over: it uses a lock, and waiting for space is part of what put promises. Progress guarantees are usually discussed for operations that can always complete; "wait until there is room" is a different kind of waiting.

A single-producer single-consumer ring buffer whose offer and poll return false or empty instead of waiting. Wait-free on both sides if each path uses bounded atomics and value transfers without allocation or retry. An operation returning full or empty is still a completed operation; wrapping it in an endless wait for success changes the guarantee.

Common mistakes

  • "Lock-free means fast." It means a stalled thread cannot stop the others. Throughput is a separate, measured property.
  • "There is no lock() in my code, so it is lock-free." A CAS loop that waits for a flag set by another thread is a lock in disguise.
  • "Lock-free means no thread ever waits." Individual threads can starve; only wait-free rules that out.
  • Treating "lock-free" in std::atomic<T>::is_lock_free() as the same thing. It describes that object's atomic operations, not your surrounding algorithm and not wait-freedom. is_always_lock_free == false means no unconditional type-wide guarantee; query is_lock_free() at runtime. If the required primitive is not lock-free, the algorithm cannot simply inherit lock-freedom.
  • Forgetting what is inside the operation. Allocation, logging or a callback can introduce blocking dependencies. A page fault pauses a thread in real time even when the abstract algorithm is non-blocking.

In the interview

This topic is often a follow up, and definitions can also be asked directly. After a CAS-based answer, expect "is it lock-free or wait-free?", "what happens if a thread is preempted in the middle?" and "why not make everything lock-free?". After a lock-based answer, expect "could you do it lock-free, and would you?". A Databricks report (lower confidence) describes a candidate who could not justify a lock-free attempt and recovered by switching to a plain synchronized block, which is the right instinct when you cannot defend the clever version.

Lock-free is a progress guarantee, not a speed claim: if any thread is paused at any point, the others still complete operations, under the atomic and finite-work assumptions in my progress proof. My stack is lock-free but not wait-free, since one thread can keep losing the race. The mutex version is blocking: a descheduled holder stops everyone. Under heavy contention the mutex version can even have more throughput, because both serialize on one cache line and failed CASes waste work. I would choose lock-free for latency isolation or for code that must never block, and measure before claiming it is faster.

Senior depth

Why CAS is special: consensus numbers. Maurice Herlihy's 1991 paper on wait-free synchronization ranks primitives by how many threads they can help agree on one value without waiting. Plain atomic reads and writes have consensus number 1: they cannot solve deterministic wait-free consensus for two participants in the standard asynchronous shared-memory model. That does not rule out useful wait-free structures built from registers, such as an SPSC ring. Test-and-set, swap and fetch-and-add reach 2. Compare-and-swap has unbounded consensus number and supports universal constructions. That is an expressiveness result, not a claim that every CPU supports it or every non-blocking structure requires it.

Obstruction-freedom is a design tool. Herlihy, Luchangco and Moir introduced it in 2003 because it is much easier to achieve than lock-freedom: design for the case where a thread runs alone, and handle interference separately with backoff or a contention manager. In practice, randomized backoff turns many obstruction-free designs into ones that progress with high probability.

Wait-free with a fast path. Kogan and Petrank published a wait-free queue in 2011, and later showed a "fast path, slow path" technique: run the lock-free fast path normally and fall back to the helping slow path only after repeated failures, so the common path can stay short while the slow path provides the completion bound. Explain the bound and helping protocol before making a performance claim.

Key takeaways

  • Progress guarantees answer one question: if threads are stopped at the worst moment, can the others still finish operations?
  • Blocking: no. Obstruction-free: a thread running alone finishes. Lock-free: some thread always finishes. Wait-free: every thread finishes in bounded steps.
  • Spinlocks are blocking; well-formed CAS update loops can be lock-free. Wait-free rings need bounded primitives and work; an API name or instruction count is not enough.
  • The guarantees remove specific dependencies between participants. They do not promise wall-clock deadlines, crash recovery or a deadlock-free application.
  • Lock-free is not automatically faster: hot spots, extra work and complexity remain, so measure.

What does wait-free promise that lock-free does not?
Why. Lock-free guarantees system-wide progress: some thread always finishes. Wait-free guarantees per-thread progress. They need not be faster or avoid CAS: either is compatible with wait-freedom. The defining property is bounded per-caller work, assuming that caller continues taking steps.
A benchmark with 32 threads hammering one stack shows a mutex-protected stack beating a Treiber stack. What is the most plausible explanation?
Why. Lock-free removes waiting on a specific thread; it does not remove contention. Under heavy contention failed attempts and cache line traffic can cost more than orderly handoffs through a mutex. A counter starts at 0. T reads 0 and pauses. U atomically increments to 1 and returns. T resumes, tries a strong CAS from 0 to 1, then retries using the refreshed value. No other update runs. What is the final value, and what does this show?
Why. U already changed the counter to 1, so T's expected 0 cannot match. T retries from 1 and writes 2 without U taking another step. This demonstrates progress despite a paused updater, not a bound on retries under arbitrary interference. CAS never blindly overwrites a mismatching value.
C++ onlyBig meets the requirements for std::atomic<Big>. You only know that std::atomic<Big>::is_always_lock_free is false. What follows?
Why. False means not always lock-free, which includes implementations that are sometimes lock-free as well as those that never are. It does not itself prove an internal lock on this run. Why. Progress guarantees compare threads with each other. A stop-the-world pause stops all of them at once, so there is no "other thread" to keep going. The queue does not change progress class when execution resumes. GC need not wait for an entire CAS loop to finish; safepoints are a runtime mechanism distinct from operation completion.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
Define blocking, obstruction-free, lock-free and wait-free precisely, and give one real example of each.
Model answer

All four answer the question: if some threads are stopped at the worst moment, what can the others still do?

  • Blocking: a stalled thread can stop others, typically because it holds a lock they need. Example: a counter under synchronized, std::mutex, or a spinlock.
  • Obstruction-free: any thread that runs alone, with the others paused, finishes its operation in a bounded number of steps; threads running together may keep aborting each other, so interference needs a separate progress argument. Example: some software transactional memory designs, and the deque Herlihy, Luchangco and Moir used to introduce the idea.
  • Lock-free: continued execution of pending operations produces system-wide completions; individual threads can starve. Example: the Treiber protocol with lock-free atomics, finite non-blocking local work and safe node lifetimes.
  • Wait-free: every thread completes every operation within a bounded number of its own steps. Example: a single-producer single-consumer ring whose operations return instead of waiting, assuming bounded atomic primitives and bounded value transfers with no allocation.

Among non-blocking guarantees, wait-free implies lock-free implies obstruction-free. Blocking sits outside that chain; fairness with scheduling assumptions does not turn a mutex into a non-blocking operation.

Design
Your team wants to replace the mutex-protected queue between request threads and worker threads with a lock-free queue "for performance". What do you ask and what do you measure before agreeing?
Model answer

First I would ask what problem we are solving. If it is tail latency caused by lock holders being descheduled, a lock-free protocol may help. If a thread must meet a deadline, I also need bounded work, allocation and scheduling analysis. If it is throughput, I would want evidence that the lock is the bottleneck: a profile showing time in lock acquisition or parking, and contention metrics, not just a hunch.

Then I would measure both under realistic load: same thread counts, same oversubscription, same message sizes, looking at throughput and at p99 and p99.9 latency, plus CPU usage, because failed CAS retries burn CPU. I would also check the lock-free design's hidden costs: allocation per element (and garbage collection pressure in Java), memory reclamation in C++, and whether the queue still needs a way for idle consumers to sleep, because a lock-free queue does not give you blocking waits. Often the better fix is reducing contention, for example batching handoffs or a queue per worker, rather than changing the synchronization primitive.

Explain
Classify each of these and say why in one line: (a) a counter guarded by a TTAS spinlock; (b) AtomicLong.getAndAdd with only the Java API guarantee known; (c) AtomicReference.updateAndGet building a new immutable map; (d) a mutex-based bounded queue's put that waits when full; (e) a single-producer single-consumer ring buffer whose offer returns false when full.
Model answer
  • (a) Blocking: waiters depend on one specific thread clearing the flag, and if it is descheduled they all spin uselessly.
  • (b) The API alone is insufficient to establish wait-freedom. Inspect the runtime and target; a native add treated as a bounded primitive supports a wait-free model, while a retry implementation may only give system-wide progress.
  • (c) A CAS update protocol, but full-method lock-freedom also needs non-blocking allocation, a finite side-effect-free callback and suitable primitives. The API call alone proves none of those. Retries may rebuild the map and one caller may starve.
  • (d) Blocking, by implementation (a lock) and by specification (waiting for space is part of what put promises).
  • (e) Wait-free if atomics and value transfers are bounded and the operation does not allocate or retry. Each side writes its own index and can return full or empty instead of waiting for the other.

"Explain blocking, obstruction-free, lock-free and wait-free. Where does a spinlock belong?"
What a strong answer covers
  • A spinlock is blocking because a paused holder prevents acquisition even by a lone running waiter
  • Obstruction-free means an operation completes when it runs alone long enough
  • Lock-free guarantees system-wide completions under continued execution, allowing individual starvation
  • Wait-free bounds each active caller's own steps under the stated primitive assumptions
  • Wait-free implies lock-free, which implies obstruction-free
  • Step bounds do not guarantee scheduling or wall-clock deadlines
How a senior would say it
A spinlock is blocking. If its owner pauses, another thread can spin alone forever without acquiring it. The use of CAS does not change that dependency. Obstruction-free means a caller finishes if it runs alone long enough; concurrent callers can still keep interfering without completing. Lock-free strengthens that to system-wide progress while operations keep executing. A Treiber stack can have many successful pops while one unlucky popper keeps losing its CAS. Wait-free goes further: every caller that continues taking steps finishes within its own step bound, regardless of interference. A fixed ring with one producer and one consumer can provide that for operations that return full or empty, provided the atomic primitives and value transfers are bounded. So wait-free implies lock-free, and lock-free implies obstruction-free. These promises count steps, not milliseconds. A paused caller does not get CPU time merely because its algorithm is wait-free, and a stop-the-world pause stops every application thread. I would state which operation I am classifying and the primitive and allocation assumptions behind that claim.

Likely follow up: Does a fair mutex become wait-free if every waiting thread eventually acquires it?

That result is plausible: lock-freedom does not promise higher throughput. Both queues may contend on shared cache lines, while failed CAS attempts add traffic and wasted work. A mutex can let one thread proceed while other callers park. I would first confirm that the benchmark compares the same capacity, ordering and empty-queue behaviour under realistic producer and consumer counts. Idle-consumer behaviour matters too: a spinning consumer and a sleeping consumer are different workloads. Batching or sharding may reduce contention more than changing synchronization, but sharding may change ordering. I would choose based on the required semantics and measured bottleneck, then state any progress assumptions separately.

  • Neither query establishes wait-freedom or a latency deadline
How a senior would say it
No. False means this type is not guaranteed always lock-free. It covers implementations that are sometimes lock-free as well as implementations that never are. I would query the actual object's is_lock_free() for this execution. A false runtime result prevents me from relying on that primitive for a lock-free proof. A true result still does not classify my whole method: a spinlock built from that atomic is blocking, and allocation or callbacks may introduce other dependencies. Neither query establishes wait-freedom or a deadline. For those stronger claims, I need a bound on the complete operation's work and explicit assumptions about its primitives and execution environment.

Likely follow up: Why can an atomic implemented with a retry loop be lock-free without being wait-free?
