Parking lot for cars and trucks

Thread-safe designsmedium35 minRubrik system coding rounds, 2026Rubrik

Rubrik asked this in two 2026 loops, once framed as memory allocation in a 1-D array. It looks like a toy, but it is the purest form of the question every booking design hides: find a free resource and claim it as one step, while other threads are doing the same.

The task

A parking lot is one row of spots places, numbered 0 to spots - 1. A car needs 1 spot. A truck needs 2 adjacent spots. Entry gates and exit gates run on different threads and call your class at the same time.

  • park(plate, size) parks a vehicle of size 1 (CAR) or 2 (TRUCK) in the lowest numbered place that fits: a car takes the lowest free spot, a truck the lowest i where spots i and i + 1 are both free. It returns the spot ids it took, in increasing order. It returns an empty list when nothing fits, or when a vehicle with this plate is already parked.
  • leave(plate) frees exactly the spots that vehicle holds and returns true. It returns false if no vehicle with this plate is parked.
  • freeSpots() returns how many spots are free right now.

Rules. Use any locking you like; a simple correct design beats a fast broken one. The "lowest numbered" rule lets the tests check exact answers from one thread. Under concurrency, arrivals may be served in any order, as long as each answer was the lowest fit at the moment that call took effect. Plates are non-empty strings.

What the tests check

  • The example above and more from one thread: first fit, refusals, a plate parked twice, leave of a plate that is not there.
  • A fragmented lot: two free spots that are not adjacent must refuse a truck.
  • 8 trucks arrive at the same instant at a lot of 6 spots, over and over (150 rounds in Java, 80 in C++): exactly 3 park, on disjoint adjacent pairs, and the lot ends full.
  • 8 gates park the same plate at the same instant, over the same number of rounds: exactly one succeeds each time.
  • A stress run: 8 threads park and leave random cars and trucks on 16 spots. The harness keeps its own record of who holds each spot, so a spot handed to two vehicles is caught the moment it happens. Trucks must always get adjacent spots, every leave of a parked vehicle must succeed, and afterwards all 16 spots must be free and reusable from spot 0 upward.
  • In C++, ThreadSanitizer must stay quiet.

Write down the state and its invariant before any code: who owns each spot, which spots each plate holds, and how many spots are free. Which of these must change together, so that no thread ever sees them disagree?
Finding a free place and claiming it must be one indivisible step. If you search without the lock and take the lock only to write, two gates can find the same free spots and both write. Where does your critical section begin?
The simplest correct design is one lock (a synchronized method, or one std::mutex with a std::lock_guard) around the whole of park and leave: check the plate, scan for the first fit, write the owner of each spot, record the plate's spots, update the free count. leave looks up the plate's recorded spots and clears exactly those.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

One lock serializes every gate. How would you let parks in different parts of a big lot run in parallel?
Split the row into segments, each with its own lock (lock striping). A car needs one segment. A truck whose pair crosses a segment boundary needs both segment locks, taken in segment order so two trucks can never deadlock. A per segment free count lets a gate skip full segments without locking them. The price: "lowest numbered overall" becomes "lowest in the segment you tried", and you should say that out loud.
Can you do it without locks?
Yes, with compare-and-swap on each spot (AtomicReferenceArray in Java, a std::atomic per spot in C++). A car CASes one spot from free to its plate. A truck CASes spot i, then i + 1, and if the second CAS fails it must put spot i back. While a truck holds half a pair, a car may see the spot taken and move on, and the plate to spots record needs its own concurrent map with putIfAbsent. It works, but it is much harder to prove correct in 45 minutes, which is the reason to start with the lock.
Make park wait for room instead of returning an empty list.
Add a condition variable on the same lock. park waits in a loop until its size fits; leave must wake everyone (notify versus notifyAll), because one freed spot may wake a truck that still cannot fit while a car that could fit stays asleep. Add a timeout, and think about fairness: a stream of cars can keep a truck waiting forever unless the oldest waiter may reserve spots as they free up.
Now the lot runs on ten app servers over one database. What changes?
The in-process lock protects nothing across servers, so let the database decide. UPDATE spots SET plate = ? WHERE id = ? AND plate IS NULL and check that exactly one row changed; for a truck, update both ids in one transaction and require two rows, else roll back. A unique index on the plate column stops a double park. Salesforce asked this exact progression: threads first, then a central database.
Trucks keep getting refused even though half the lot is free. Why, and what would you do?
Fragmentation: cars spread one per pair leave no two adjacent free spots. Fill cars from one end and trucks from the other, or give a car a lone free spot squeezed between taken ones before breaking up a free pair (best fit). It is the trade-off every memory allocator faces, which is why Rubrik framed the question as allocation.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

Three pieces of state form one invariant: owner[i] (the plate in spot i, or nothing), the record of which spots each plate holds, and the free count. They must always agree: every spot is in exactly one plate's record or in none, and the free count is the number of spots in none. Each method takes one lock, reads and changes all three, and lets go, so no thread can ever see them half updated.

The bug this design prevents

The tempting design searches for free spots first and takes the lock only to write, on the theory that the write is the dangerous part. But the search result is a check and the write is an act, and another gate can act in between. That is check then act, and it is exactly the broken version the tests are built to catch:

The fix is not "lock more carefully". It is to make the decision and the claim one critical section: search and write while holding the same lock, so the spots you found are still free when you take them.

Why each line is there

  • The plate check is inside the lock. Two gates parking the same plate at the same instant must not both pass it; the tests fire 8 at once.
  • The loop bound start + size <= n makes start + 1 a valid index for a truck, so there is no special case at the end of the row.
  • leave clears exactly the recorded spots. It never searches the row for the plate, so it cannot free a neighbour's spot, and it is O(size) instead of O(N).
  • freeSpots() takes the lock too. Reading free without it is a data race in C++ and may return a stale value in Java.
  • Java returns an immutable copy (List.copyOf), so a caller cannot change the lot's record from outside the lock. In C++ the vector is returned by value for the same reason.

Cost and trade-offs

park scans the row in O(N) under the lock; for a few hundred spots that is microseconds. For a big lot, keep the free spots in a sorted set (the lowest free spot is its first element) and the starting points of free pairs in a second sorted set, updated on every park and leave, which makes both operations O(log N). Either way the lock is held only for in-memory work, never for anything slow, so one lock goes a long way before striping is worth its complexity.

How to say it in the interview

The state is an owner per spot, a map from plate to its spots, and a free count, and the invariant is that they always agree. The race to avoid is check-then-act: two gates finding the same free pair. So one lock covers the search and the claim together, and the plate check, so the same plate cannot park twice. Leave frees exactly the recorded spots. Everything under the lock is O(N) in memory, which is fine at this size; if the lot were huge I would stripe it by segment and take two segment locks in order for a truck on a boundary, or move to per-spot CAS with rollback.
