What does holding a lock (synchronized, ReentrantLock, or a std::mutex through a guard) guarantee? Select all that apply.Select all that apply
Why. Mutual exclusion and visibility at the lock boundaries are the whole contract. Ordinary locks are not fair: a newly arriving thread may barge ahead of waiting ones. And the visibility edge exists only between an unlock and a later lock of the same lock, so a reader that skips the lock gets no guarantee (and in C++ it is a data race).

increment() updates count inside synchronized (lockA), and reset() sets count = 0 inside synchronized (lockB) (in C++, under two different mutexes). What is the problem?
Why. A lock only excludes code that takes the same lock. Two locks guarding one field protect nothing between the two methods. One field, one invariant, one lock.

x and y start at 0. Thread A runs: lock; x = 1; y = 2; unlock. Thread B runs: lock; print x and y; unlock. Both use the same lock. What can B print?
Why. If B's critical section runs first, it sees 0 0; if A's runs first, B is guaranteed to see both writes, because A's unlock happens-before B's lock. B can never see the middle (1 0), because A's two writes happen inside one critical section that B cannot interleave with.

A stack class locks inside each of its methods. A caller writes if (!s.empty()) { v = s.top(); s.pop(); }. Two threads run this when the stack holds exactly one element. What can happen?
Why. Each call is atomic, but the lock is released between them, so the sequence is a check-then-act. That is why thread-safe stacks and queues offer a single tryPop or poll that checks and removes in one critical section and reports "empty" through its return value.

Why should a read-only method such as size() take the same lock as the methods that modify the data?
Why. Visibility comes from the lock: only a thread that acquires it is guaranteed to see what the last holder wrote. Unlocked reads can be stale or see a broken invariant halfway through an update. If a value must be readable without a lock, make it atomic or immutable.

Why. balance and history form one invariant, so they need one lock held across both updates; separate locks or separate thread-safe objects let readers see the new balance with the old history. lastLoginTime is not part of that invariant, so putting it under the money lock would only add contention.

Every request takes one global lock and holds it for 50 microseconds. Ignoring everything else, what is the highest request rate this lock allows, however many cores you add?
Why. Only one thread can hold the lock at a time, so at most 1 / 50 microseconds = 20,000 critical sections run per second, no matter how many cores wait. In practice latency explodes well before that ceiling, because waiting time grows like a queue as utilization approaches 100 percent.

When is it acceptable for a thread to hold two locks at the same time?
Why. Deadlock needs a cycle in the order locks are taken. A single global order (or an all-at-once acquisition with deadlock avoidance) makes the cycle impossible. Reentrancy and short sections do nothing about cycles: two threads can deadlock on two microsecond-long sections.

From: tryLock, timeouts, interruptible locking and fairness
Why is an unfair (barging) lock usually much faster than a fair one when many threads compete for a short critical section?
Why. Waking a parked thread costs microseconds, and with FIFO hand off the lock sits owned but unused during that time, on every hand off. Both kinds of lock give the same mutual exclusion and the same memory visibility; the difference is who gets the lock next.
From: tryLock, timeouts, interruptible locking and fairness
Two threads move money in opposite directions. Each locks its first account, tries the second with tryLock, and on failure releases the first, sleeps exactly 2 ms and retries. What is the main risk?
Why. Releasing on failure does prevent deadlock, since nobody waits while holding a lock. But identical delays can keep the threads synchronized, so they collide again and again. Random jitter, ideally with exponential growth and a deadline, desynchronizes them. Balances are only changed while holding both locks, so updates are not lost.

Which statements about fair locks are true? Select all that apply.Select all that apply
Why. A fair lock serves waiters in arrival order, which prevents starvation at the lock, and it pays for that with a wake-up on every hand off. (The qualifier matters in Java: an untimed tryLock() barges even on a fair ReentrantLock.) It says nothing about CPU scheduling, and a long critical section is just as harmful with a fair lock; fairness only decides who waits for it.

Under a traffic spike, request threads pile up waiting on one hot lock and latency explodes. You replace lock() with a 20 ms timed attempt and return "busy" when it fails. What have you gained?
Why. A timed attempt does not make the lock faster or the critical section shorter; it caps the waiting and turns an unbounded queue into a quick rejection that callers can retry or route elsewhere. Fixing the contention itself means shrinking or splitting the critical section.

What does a reentrant lock track that a plain, non-reentrant lock does not need?
Why. Reentrancy needs the owner (to recognize "the same thread again") and the hold count (to know when the last release happens). Waiting time is what a fair lock tracks; that is a separate property. A count of waiters is something any blocking lock may keep, and it says nothing about who holds the lock.
From: Reentrant and recursive locks
On a reentrant lock, one thread runs lock(); lock(); unlock();, then starts a second thread that calls the no-argument tryLock() once and prints the result. What does the second thread print?
Why. Two acquisitions and one release leave a hold count of 1. The lock is released only at zero, so the other thread's attempt fails. A plain tryLock() never blocks, so the third option cannot happen.
From: Reentrant and recursive locks
An event bus holds its reentrant lock while calling listeners. One listener reacts by calling bus.subscribe(...). What goes wrong?
Why. A reentrant lock admits the same thread, so the call does not hang; it lands in the middle of publish, whose loop assumed the list would not change (in Java the loop then throws ConcurrentModificationException). With a non-reentrant lock the same code would self-deadlock. The fix for both is an open call: copy the listeners under the lock and call them after releasing it.

Why do many engineers treat "I need a reentrant lock here" as a design smell?
Why. The extra cost of reentrancy is one comparison. The problem is semantic: entering a locked method normally means "the object is consistent", and re-entry breaks that guarantee silently. Java's reentrant locks work fine with conditions, and C++ std::condition_variable_any accepts a std::recursive_mutex (safe only when it is held once). Reentrant locks still exclude other threads.
From: Reentrant and recursive locks
An async request handler locks a reentrant lock in its first stage, which runs on thread A. Its continuation runs later on thread B and calls unlock(). What happens?
Why. Ownership is per thread. In Java the unlock throws IllegalMonitorStateException; in C++ unlocking a mutex you do not own is undefined behavior. The tempting first option is the async mental model, but a lock knows nothing about requests, only about threads. Thread-owned locks must not be held across async boundaries.

For which workload does a read-write lock most clearly beat a plain mutex?
Why. The win comes from long reads overlapping. With 50 ns reads, each read lock acquisition and release (atomic writes to one shared cache line) costs about as much as the read, so the lock itself becomes the bottleneck. A counter is all writes. "More reads than writes" alone is not enough.
From: Read-write locks and StampedLock
A thread holds the read lock of a read-write lock that does not support upgrades, and asks for the write lock without releasing the read lock. No other thread is involved. What happens?
Why. Both ReentrantReadWriteLock and std::shared_mutex behave this way. Neither reports an error: Java simply queues the write request behind the readers, and in C++ it is formally undefined behavior, which libc++ and glibc both turn into a hang. The safe pattern is to release the read lock, acquire the write lock and re-check the state.
From: Read-write locks and StampedLock
A thread-safe LRU cache uses a read lock in get() and the write lock in put(). What is wrong?
Why. In an LRU cache every hit is a write to the recency list. Two readers moving nodes at the same time corrupt the list. Options: one exclusive lock with short critical sections, sharding by key with an LRU per shard, or approximate recency that is updated without moving nodes on every hit.
From: Read-write locks and StampedLock
You implement "upgrade" as: release the read lock, then acquire the write lock. What must you do next?
Why. Between the release and the acquire, other threads can run, including writers that make the same decision. Without a re-check, two threads both load the missing entry or both apply the same change. It is check-then-act again.
From: Read-write locks and StampedLock
An optimistic read copies x and y into locals, then the version check (validate, or the seqlock counter) says a writer got in. What should the reader do?
Why. A failed validation means the copies may come from different writes, so together they may break the invariant. The data is fine; only this reader's copies are suspect. Retry optimistically a few times, or take the read lock.

From: Read-write locks and StampedLock
Ten percent of each request's time is spent inside one global lock. What is the most this service can speed up by adding threads, however many?
Why. Amdahl's law: with a serial fraction s, the speedup is at most 1 / s, here 1 / 0.1 = 10. The formula gives about 6.4 for 16 threads; a server can get closer to 10 than that, because one request's work outside the lock overlaps another's time inside it, but it can never pass 10. In practice lock hand offs keep it lower still. 90 times confuses the parallel fraction with the ceiling.

Every operation holds one global lock for 2 microseconds. Roughly what is the maximum throughput of the whole process, on any number of cores?
Why. Only one operation can be inside the lock at a time, so at most one completes every 2 µs: 1 / 0.000002 = 500,000 per second. More cores cannot raise that ceiling; only shrinking or splitting the critical section can.

Why. Striping spreads different keys over different locks; it cannot split one key. The fix is to split the value (several sub-counters summed on read, like LongAdder) or to batch updates to the hot key.

Why. If one call takes both locks before the other starts, it finishes. If each thread gets its first lock before the other's second, they wait for each other forever. Neither language detects this at the lock call; a Java thread dump can report it afterwards.

Why. With a tie, two threads may lock the pair in opposite orders, which is the original deadlock. A secondary unique key restores a total order; a tie lock lets only one tied operation take its pair at a time, so no cycle can form among tied pairs.

All threads acquire locks A and then B. Some release A first, others release B first. Can the release order cause a deadlock?
Why. A cycle needs threads waiting for locks, and only acquisition waits. Releasing in reverse order is a good habit (and RAII does it automatically), but any release order is safe as long as acquisition follows the global order.

Why. The first thread holds C and cannot get A, which the second thread holds while it waits for C. In C++ std::scoped_lock simply blocks on A; a Java tryLock loop retries forever instead. Why. Each test-and-set is a write that needs the line exclusively, so a crowd of spinners steals the line from each other and from the holder. Reads can be served from each core's shared copy. Ordering, fairness and sleeping are separate concerns.
