Sliding window rate limiter

Concurrent systemsmedium30 minCommon rate limiter round (fixed versus sliding window)

"At most K requests per user in any rolling window of W milliseconds" sounds like a counter, and the counter is the classic wrong answer. Atlassian's code design round, for one, has asked candidates to compare fixed and sliding windows. This problem makes you get the window exactly right, then keep it exact with many threads.

The task

Build a per key limiter with a sliding window:

  • A request for key at time t is admitted if fewer than limit requests of that key were admitted in the window (t - windowMillis, t]: strictly after t - windowMillis, up to and including t.
  • Rejected requests do not count towards later decisions.
  • tryAcquire(key) returns true (admitted) or false. It never blocks.
  • Read time only from the given Ticker, a monotonic nanosecond clock that the tests move by hand. The boundary is exact to the nanosecond: convert the window to nanoseconds, not the clock to milliseconds.
  • Each decision uses the time its own call read from the ticker, and counts every earlier admission of that key inside that window.
  • Memory for a key stays bounded: forget a request once it has left the window, so a key never holds more than limit times.
  • Many threads call tryAcquire at once, for one key and for many keys. The limit must hold exactly.

Worked example: fixed versus sliding

Limit 3 per 1000 ms. A user sends 3 requests at 999 ms and 3 more at 1000 ms. A fixed window counter that resets every 1000 ms admits all 6, because the second three land in a fresh window: twice the limit inside 2 ms. A sliding window looks back exactly 1000 ms from each request, sees the 3 from 999 ms, and rejects. Those three leave the window only at 1999 ms.

What the tests check

  • Exact answers on scripted timelines: filling the limit, the exact moment a request leaves the window, a window that slides rather than resets, the boundary burst from the worked example (and the same burst against a fixed window that starts at a key's first request), and rejected requests not counting.
  • The boundary to the nanosecond: with 1 per 10 ms, a request at 0.6 ms still blocks at 10.599999 ms and is gone at 10.6 ms. A clock cut to whole milliseconds lets a request in at 10.4 ms.
  • Keys are independent.
  • 8 threads make 2400 attempts on one key with a limit of 500 and time frozen: exactly 500 pass.
  • 8 threads hit each of 300 brand new keys at the same instant: each key admits exactly 3.
  • 8 threads each sweep 400 keys three times, in their own shuffled order, so different keys reach the map at once: each key admits exactly 5.
  • A stale clock read. With 2 per 10 ms and two admitted at 0 ms, thread A reads the clock at 5 ms and stalls inside that read while thread B arrives at 10 ms. A, judged at the 5 ms it read, must be rejected, and B admitted. A limiter that reads the clock before taking the key's lock judges A at 5 ms against a log B has already pruned, and admits 3 within 10 ms.
  • While the threads move the clock forward 800 ms, a limit of 10 per 50 ms admits at most 170.
  • A long run: 150,000 requests on one key over 50,000 ms of fake time (limit 2 per 1 ms, 3 requests every ms) must admit exactly 100,000, leave the heap flat, and finish in 2 s in Java or 4 s in C++. Keeping every admitted time fails it.
  • In C++, ThreadSanitizer must stay quiet.

Taught in: Thread-safe rate limiters

Open them one at a time. Each one gives away a little more.

Keep, per key, the times of the admitted requests that are still inside the window, oldest first (a deque). On a request, first drop from the front every time &lt;= now - window, then admit if fewer than limit remain, and append now only when you admit.
The prune, the size check and the append are one read, modify, write: guard each key's deque with its own lock. Read the clock while holding that lock, so the times in the deque only ever increase.
Create a key's deque atomically: computeIfAbsent in Java, or create it under the map mutex in C++ and keep a stable pointer to it (a std::unique_ptr in the map), then lock the deque.

What the interviewer asks after your first version works. Try to answer each one out loud before you open it.

The log keeps up to limit timestamps per key. What if the limit is 10,000 per minute and there are a million keys?
That is up to 10 billion timestamps, too much. Use the sliding window counter approximation: keep counts for the current and previous fixed windows, and estimate the rolling count as current + previous times the fraction of the previous window still inside the rolling window. Two integers per key, slightly inexact, which is what most production limiters accept.
Walk through the race where two threads both see 99 of 100. (LinkedIn asked for exactly this walk through in a 2026 Staff onsite, after a thread-safe allowRequest.)
Limit 100, and 99 admitted in the window. Thread A prunes and counts 99; before A appends, thread B prunes and counts 99 too. Both see room, both append, and 101 requests sit inside one window. A ConcurrentHashMap&lt;String, Deque&lt;Long&gt;&gt; does not fix it: the map is safe, but prune, count and append are three steps on the deque, and even a ConcurrentLinkedDeque only makes each step safe on its own. The fix is one critical section per key around all three (a synchronized log, a mutex in C++, or compute on the map), or a compare and set loop over an immutable snapshot that retries when it loses. The tests replay this race with 2400 attempts against a limit of 500.
Rubrik's 2022 screening asked for a limiter with a capacity, where each accepted request holds a slot until it expires expireTime later. How does that relate to this problem?
It is the same structure read the other way round. A request accepted at a holds its slot during [a, a + expireTime), so "fewer than C slots held at time t" is exactly "fewer than C acceptances in (t - expireTime, t]". The deque of acceptance times works unchanged, and pruning the front is the expiry. It changes only if a request can give its slot back early, because it finished before expiring: then each slot needs an id, kept in an ordered set or a min heap by expiry plus a map from id to entry, and release and admission take the same per key lock, so a slot is never freed twice or counted after it was freed. That round went on to the concurrent version and then to sharing the state across machines.
Atlassian (2025) followed "X requests per Y seconds per user" with credits for unused requests. How would you add them?
Credits need window boundaries, so switch to fixed windows per user. When a request arrives in a new window, add the unused quota of the windows that passed to a credit balance, capped (say at one window's limit) so a quiet user cannot save up an unbounded burst. Admit if this window's count is under the limit, else spend one credit if there is one. Do the carry over lazily on the first request of the new window, the way a token bucket refills lazily, so no background thread is needed. The window start, the count and the balance change together, so they live in one per user object under one lock. Say out loud that this is close to a token bucket whose capacity is the limit plus the cap.
Why must rejected requests not be logged?
If they were, a client that keeps retrying while limited would keep its own window full forever, and could never get through even after slowing down. The limit is on admitted work, so only admitted requests count.
How does this compare with a token bucket?
The sliding log enforces the exact rule "at most K in any window of W", with no burst beyond K. A token bucket allows a burst of up to burst and then a steady rate, in O(1) memory per key. Pick the log when the contract is literally "K per window"; pick the bucket when you want smooth average rates with tolerance for bursts.
One lock per key, or one lock for everything?
One global lock is correct and simpler, and at modest load it is fine. Under heavy traffic every request in the process serializes on it, so a lock per key (or lock striping over keys) keeps unrelated users from contending. The map itself still needs safe lookup and creation.
How would you enforce this across a fleet of servers?
Keep the window in a shared store and update it atomically: for example a Redis sorted set per key with a script that removes old entries, counts, and adds the new one in one step. Or route each key to one server so its state is local.

Try for at least twenty minutes first. Reading a solution feels like learning; writing one is learning.

The idea

A sliding window log stores exactly what the rule talks about: the admission times inside the window. Pruning the front, counting and appending is a single critical section per key. Because the clock is read under the key's lock, the deque stays sorted, so pruning only ever looks at the front.

Invariants

  • A key's deque holds at most limit times, in increasing order.
  • After pruning at time now, every time in the deque is greater than now - window.
  • For any window (t - W, t], at most limit admitted requests of a key fall inside it.

Why each primitive

  • A lock per key (a synchronized method on the key's log, or a mutex inside it), because the prune, check and append must happen together.
  • computeIfAbsent or creation under the map mutex, because two threads that both create a log for a new key would each admit limit requests.
  • The clock read inside the lock, so one key's timestamps never go backwards.

Pitfalls

  • A fixed window counter: thread-safe and wrong, since it lets through twice the limit across a boundary. This is the broken version the tests catch.
  • Logging rejected requests.
  • Using &lt; instead of &lt;= when pruning, which keeps a request exactly one window old for one extra tick. Decide the boundary and test it.
  • A concurrent map with an unguarded deque inside, or a plain HashMap shared by per key locks: two different keys can then grow it at once.
  • Creating a key's log with a check then act (get, then put if missing): two threads each create a log for a new key and each admit limit.
  • Reading the clock before taking the lock. The stale time is then judged against a log that a newer request has already pruned, so one window can hold limit + 1 admissions, and an older time can land after a newer one.
  • Converting the clock to whole milliseconds, which moves the boundary by up to a millisecond and lets a request in early.
  • Never forgetting: keeping every admitted time and counting the window by scan or binary search. The answers are right, but memory (and with a scan, time) grows with every request ever admitted.

Cost

Amortized O(1) per request: each timestamp is appended once and removed once. Memory is up to limit timestamps per key.

How to say it in the interview

The rule is about any rolling window, so a fixed counter is wrong at the boundaries. I keep, per key, a deque of admission times. Under that key's lock I read the monotonic clock, drop times that are a full window old, admit if fewer than the limit remain, and append only when I admit. Each key has its own lock and the map creates logs atomically, so different users never contend and a new key cannot get two logs. If memory per key matters, I switch to the two window counter approximation.
