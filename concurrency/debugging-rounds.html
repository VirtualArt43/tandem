Debugging rounds: the bug in someone else's threaded code

Map unfamiliar threaded code, distinguish races from hangs, fix broken invariants, and test the result in a timed debugging round.

Asked atRubrikMicrosoft
Before this:The rules of lockingSpurious and stolen wakeups: always wait in a loopDeadlock: the four conditions and how to break eachFrom symptom to cause: the bug map

Rubrik reports describe a dedicated debugging round with unfamiliar multithreaded code, a deadlock or a broken producer-consumer hides inside, and you must hand back code that compiles and runs. It is a different skill from writing code, and you can drill it like one.

In plain words

A good mechanic handed a car they have never seen does not start by taking the engine apart. They look at what is connected to what, they start the car and listen, they check the usual suspects in a fixed order (battery, belts, fuel), and when they find the fault they replace one part, not the engine. Then they start the car again to prove it runs.

A debugging round rewards exactly that discipline: map, reproduce, check the usual suspects, fix the smallest thing, run it again. Candidates who start rewriting the program run out of time with a half-built new program and the old bugs still in it.

What the round looks like

From the Rubrik reports, 2024 to 2026:

  • The code: a barber shop simulation (a linked question-bank description specifies about 180 lines, shared chairs, brushes, scissors, combs, deadlocks and incorrect shutdown); a cinema ticket booking service; a multithreaded banking application (explain it, find the bugs, propose fixes and optimizations); a C++ producer-consumer program with a critical section bug; a program whose main bug was a deadlock.
  • The format: 50 to 60 minutes, the code handed over in your language or theirs (one candidate got C++), and the expectation that what you return compiles and runs. A new grad fixed the deadlock and still lost the round because the fix did not compile.
  • Who gets it: reported in new grad and Rubrik CPD team loops, but a candidate with 8.5 years of experience got the cinema version.

Microsoft has run the same idea in smaller form: predict the output of a multithreaded C++ program, then find its issues; or "identify the issues in this snippet, assuming multithreading is involved". The method below works for all of them.

The 45-minute method

  1. Map it (minutes 0 to 7). Ask what the program should do and what goes wrong. Then read for shape, not detail: which threads exist, what each runs, what state they share, which lock guards what, who waits for what and who signals it, and how the program ends. Write that map as a comment at the top of the file.
  2. Reproduce (minutes 7 to 12). Run it. Name the symptom: a hang, a wrong number, an exception, a crash, a program that never exits. A symptom narrows the suspects before you read another line.
  3. Walk the checklist (minutes 12 to 30). Go through the classic bugs below against your map, one shared variable and one lock at a time. Write each finding down as "bug, symptom, fix" before you change anything.
  4. Fix minimally, one at a time (minutes 30 to 40). The smallest change that restores the invariant. Compile and run after each fix.
  5. Stress and summarise (minutes 40 to 45). More threads, more iterations, a smaller buffer, then say your findings in order of severity.

Expect more than one bug. Reports include programs with several bugs, and a candidate who stops after the first fix leaves points on the table.

Tools, in order of usefulness. In Java, a thread dump (jstack PID, or Ctrl+\ in the terminal running the JVM) can name monitor and ownable-synchronizer lock cycles with "Found one Java-level deadlock". In an online editor without jstack, paste a watchdog that asks the JVM itself after a few seconds. In C++, run under ThreadSanitizer if you can (-fsanitize=thread) for data races; for a hang, attach a debugger locally (lldb -p PID then bt all, or gdb -p PID then thread apply all bt) and look for threads parked in mutex waits. In an online editor, a watchdog that turns a hang into a printed message is the C++ fallback.

The latches force both first locks to be held before either second acquisition, so the cycle does not depend on lucky sleep timing. The watchdog delay only allows time for observation; on an overloaded host a timeout alone proves no cause. Its process exit deliberately bypasses normal cleanup in this disposable debugging demo. C++ uses C++20 std::latch and std::jthread; C++17 can use a counter plus a predicate condition wait, and explicitly owned std::thread objects. The output shown is Java; C++ reports the deadline without identifying lock owners.

Prefer a gate or latch that forces a suspected interleaving in a regression test. Temporary yields or sleeps can widen a race window but never guarantee it. Shrinking a buffer to capacity 1 and varying thread counts are useful stress probes.

One caution for C++: some Linux ThreadSanitizer runtimes, with deadlock detection enabled, can report lock-order-inversion (potential deadlock) when execution reveals a lock-order cycle, even if that run does not hang. Availability and coverage depend on the runtime; absence of a report is not proof. The macOS toolchain Tandem uses did not report it in our tests, so here a lock order bug shows up only as a hang, and data races are what ThreadSanitizer catches.

Step 4: fix minimally, and keep it compiling

  • Restore the invariant, nothing more. Reordering two lock statements fixes a lock order deadlock. Replacing the class with ConcurrentHashMap and an executor is a rewrite: slower to finish, riskier, and it may break rules the interviewer set.
  • Fix causes, not symptoms. A sleep only changes timing, and ordinary lock deadlock throws no exception. A timed second acquisition with release of the first lock and retry is a valid avoidance protocol, but it needs a progress argument and can livelock. A fixed lock order is usually simpler.
  • One fix, one run. Compile and run after each change. If the language is not your own, keep changes in the same style as the surrounding code, so the fix compiles on the first try.
  • Do not over-lock. Wrapping every method in one big lock can fix the races and introduce a deadlock with the callbacks, or serialize the program so badly that the "optimization" part of the round goes nowhere.

Turn the diagnosis into a regression test

Test a contract, not just completion. For the print shop, assert the exact total after joins, accepted jobs exactly once, no dequeue from an empty queue, and termination when closing an empty queue with several sleepers. Verify that post-close submission is rejected under the same lock as enqueue; otherwise a producer can add work after the last consumer exits. The C++ zero sentinel is safe only because positive page counts are enforced.

Force the schedule you are diagnosing: gate two threads after the first lock acquisition to expose opposite order; park both consumers before closing; or arrange for a competitor to consume the last item before a notified waiter reacquires the mutex. Use bounded test deadlines and inspect failures, rather than treating a timeout as proof of deadlock. After the patch, verify both the invariant and progress with one, two and many workers.

Check lifetime and work dependencies too. A C++ task capturing a local by reference must finish before that local dies; joining a thread after destroying its mutex or queue is too late. A pool can deadlock when every worker waits on child jobs queued to that same pool, without a monitor ownership cycle. Replace those blocking dependencies with completion composition or schedule only runnable tasks; merely increasing the pool size can hide the issue. See pool failures.

A race detector observes executed conflicting accesses; it does not prove the absence of races, lost notifications or logically broken check-then-act sequences built from atomics. Thread dumps are snapshots: collect more than one and record progress counters. In Java 21, ThreadMXBean and Thread.getAllStackTraces() cover platform threads, not virtual threads. For virtual threads, use the newer thread-dump tooling discussed in reading thread dumps. Lock waiters may retain unrelated locks, and a null deadlock result cannot rule out all progress failures.

Worked example: the print shop

This is a teaching example, not recovered interview code. The main thread submits 9,000 positive-page jobs (18,000 pages), two printer threads print them, and a refiller thread tops up paper and toner. Expected output: "pages printed: 18000". Read it once and try to find three bug families before reading on. Paper and toner start at 18,000 and refills reset them to 18,000, so this workload never needs to wait for supplies. All submission finishes before main closes the shop.

The three bugs, as "bug, symptom, fix":

  1. Lock order inversion. print takes toner then paper; refill takes paper then toner. Symptom: the hang above, each thread holding the lock the other wants. Fix: one order everywhere, paper then toner (in C++, std::scoped_lock on both mutexes is the alternative). This is the lock ordering rule.
  2. Unguarded counter. printed += pages runs in both printers with no lock. Symptom, once the hang is fixed: a total below 18,000 in Java on some runs, and a C++ data race with undefined behaviour, which ThreadSanitizer can diagnose when the conflicting accesses execute. Fix: an atomic counter.
  3. Broken waiting. take waits with if, and close wakes only one printer. Symptoms: a printer woken for a job that another printer already took calls removeFirst on an empty queue and dies with NoSuchElementException (undefined behavior from front() in C++); and at shutdown one printer sleeps forever, so join hangs. Fix: while (the predicate overload in C++) and notifyAll in close.

Note what is not a bug: submit uses notify() (or notify_one), and that is fine, because every waiter on that monitor wants the same thing, a job or the close, so any one of them can use the signal. Saying why a line is correct is as much a signal of understanding as finding a bug.

The fixes preserve the design, and each has a one-sentence reason. That is what a strong debugging round looks like on paper.

Common mistakes

  • Rewriting instead of fixing. Forty minutes into a new design, the old bugs are still in the file and nothing compiles.
  • Stopping after the first bug. The deadlock hides the counter race: until the program finishes, you never see the wrong total. After each fix, run again and keep walking the checklist.
  • Fixing with sleeps or timeouts. They change the timing, so the bug hides for a while. Interviewers read them as "did not find the cause".
  • Breaking the build. A fix in an unfamiliar language that does not compile scores below no fix. Change little, and in the style already there.
  • Locking everything. One global lock around every method can fix the race and the deadlock and still fail the round: it serializes the printers and can deadlock with callbacks.
  • Not explaining. Say "bug, symptom, fix" for each finding. The interviewer grades the reasoning, and a correct fix with no reason looks like a guess.

In the interview

The opening is usually "this program is supposed to do X; it sometimes hangs and sometimes prints the wrong answer; make it work". Ask what correct output looks like, ask whether you may run it, and say your plan.

Let me first map it: which threads exist, what they share, which lock guards what, and who waits for whom. Then I will run it to see the symptom. The hang with threads blocked suggests a lock order problem, so I will compare the order in which each path takes its locks. After that I will check every shared write for a lock, every wait for a loop, and the shutdown path for a broadcast. I will fix one thing at a time and rerun after each.

Follow ups: "which of these would ThreadSanitizer have caught?" (the counter data race when exercised; a supported Linux detector may also diagnose an observed lock-order cycle), "how would you have caught this in production?" (thread dumps on a hang, deadlock detection through ThreadMXBean, lock contention profiling), and "can you make it faster now?" (shorter critical sections, one lock per resource only where needed, batching).

Senior depth

In production you rarely see the hang live. Senior engineers leave hooks: periodic deadlock checks through ManagementFactory.getThreadMXBean().findDeadlockedThreads() in Java services, thread names that say what each thread is for, deadlines on external operations and diagnostics on stalled progress, with an explicit cancellation policy; a timeout reports a symptom and does not automatically cancel work, and in C++ the ability to take a core dump of a hung process and read every thread's stack with gdb or lldb afterwards. For races that never reproduce on demand, the tools are ThreadSanitizer in CI on stress tests, and for Java the OpenJDK jcstress harness, which explores outcomes of small concurrent tests across many executions and configurations. Saying how you would have prevented the bug (a lock order documented on the class, a single owner for each piece of state) is the senior close to a debugging round.

Key takeaways

  • Map first: threads, shared state, locks and their order, waits and their signals, the end of the program.
  • Use symptoms to choose suspects, then prove the cause from ownership, predicates and an interleaving. A thread state alone is not a diagnosis.
  • Walk the checklist after each fix: a hang can hide a race, and a clean run can miss both.
  • Fix the cause with the smallest change, one at a time, compiling and running after each.
  • Explain every finding as bug, symptom, fix, and say why the lines you did not change are correct.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A thread dump of a hung program shows two threads in state BLOCKED. Each is "waiting to lock" a monitor that the other one holds. What is the bug, and what is the fix that removes the cause?
Why. BLOCKED threads are trying to enter a monitor, and a cycle of "holds one, wants the other" is a deadlock from inconsistent lock order. The evidence is the ownership cycle, not BLOCKED alone: ordinary contention also gives that state. A condition wait releases its associated lock, not every lock a thread holds. One global order breaks this cycle; consistent use of std::scoped_lock for both C++ mutexes is another avoidance strategy. Notifications, backoff outside the locking protocol and predicate loops do not fix opposite lock acquisition orders.
A program finishes all its work but never exits. The thread dump shows both workers WAITING in take(), the queue is empty, and main is in join(). findDeadlockedThreads() returns null. What is the most likely bug?
Why. Waiting threads with nothing to wait for, and no lock cycle, point at a missed signal. The classic version is a close that wakes one of two sleeping workers, or a wait condition that only checks "queue empty" and never "closed". Daemon status does not unblock join(): a non-daemon main thread explicitly joining a daemon can still wait forever. Making the workers daemon would therefore not fix this scenario. Queue capacity and opposite acquisition order do not explain both workers parked in the empty-queue condition.
Accounts have distinct immutable ids and transfers use two different accounts. Which strategy prevents a circular lock wait without a retry loop?
Why. A fixed global order makes a cycle of waits impossible, so the deadlock cannot happen. Releasing the first lock after a failed timed acquisition is also a valid avoidance strategy, but uses a retry loop and can livelock, so it does not meet this question's constraint; a sleep only changes how often the bad interleaving occurs, and a deadlock throws nothing: the threads just stop.
Two printers update a plain int printed without synchronization. All waiting bugs are fixed and main joins both printers. What can you conclude about the final total in Java and C++?
Why. In Java two printers can read the same count and overwrite one addition; joining publishes the final writes but does not repair lost updates. An execution without harmful overlap may get 18,000. In C++, conflicting unsynchronized non-atomic accesses are undefined behaviour: the Java-style numeric bound is not a language guarantee. Neither language promises an exception. Use an atomic increment or one common lock around the complete update.
You found and fixed the deadlock in a debugging round, and the program now finishes. Fifteen minutes remain. What should you do?
Why. Rubrik's debugging programs are reported with several bugs, and a hang hides any wrong result that comes after it. A stress run (more threads, more iterations, smaller buffers) and the rest of the checklist find the counter race and the shutdown bug. A rewrite or blanket timeouts add risk without finding causes.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
This bank class is used by many threads. Assume positive amounts and balances and totals within the int range. Find two concurrency bugs, say each as "bug, symptom, fix", and write the fixed methods.
Model answer
  1. Check then act in withdraw. Bug: the balance check and the update are two separate critical sections. Symptom: two threads withdrawing 80 from a balance of 100 both pass the check, and the account ends at minus 60. Fix: do the check and the update under one lock.
  2. Unlocked iteration in total. Bug: it walks the map while other threads insert. Symptom: in Java a ConcurrentModificationException or a wrong sum; in C++ undefined behaviour from conflicting accesses, even without rehash; a rehash can also invalidate iterators. Fix: hold the lock for the whole loop.

Say also what is already right: deposit and balanceOf take the lock, so a single deposit or a single read is safe on its own.

Explain
You are in an online editor with no debugger and no jstack. The program hangs about one run in five. How do you find out why, in your language?
Model answer

First I make the hang visible and repeatable: run it in a loop, raise the thread count, shrink buffers to capacity 1, and if I suspect a window, add a temporary yield or short sleep inside it, which I remove after the fix. Then I add a watchdog thread that wakes after a few seconds.

In Java the watchdog asks the JVM: ManagementFactory.getThreadMXBean().findDeadlockedThreads() names a lock cycle if there is one, and Thread.getAllStackTraces() prints where every thread is. A confirmed ownership cycle identifies lock deadlock. WAITING can mean a condition, an explicit lock, a join or a future, so inspect the stack and predicate together. RUNNABLE in a loop suggests spinning; CPU measurements and repeated stacks distinguish a busy loop from slow work. The Java APIs mentioned cover platform threads; a null deadlock result does not exclude a pool dependency cycle or a cycle involving virtual threads. In C++ there is no portable way to list lock owners, so the watchdog reports the hang and exits, and I add short fprintf(stderr, ...) traces with an assigned numeric worker id before and after each lock and wait to see the last thing each thread did. If ThreadSanitizer is available I run with it too, because data races often sit next to the hang. Then I read the code paths those traces point at, against my map of locks and waits.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"This service sometimes hangs. CPU is low and the JVM reports no deadlock. What do you check next?"
What a strong answer covers
  • A null detector result excludes only the detector's supported ownership cycles
  • Map threads, lock ownership, wait predicates, work dependencies and shutdown
  • Inspect repeated stacks and progress rather than inferring cause from WAITING alone
  • Check signals, retained locks, pool starvation and external I/O
  • Force the suspected schedule and verify a focused repair with a bounded regression test
How a senior would say it
A null deadlock result does not prove the service can make progress. The detector finds certain lock ownership cycles, not every dependency between tasks. I would map the threads, shared state, locks, wait predicates and shutdown path, then compare repeated thread stacks with progress counters. WAITING could mean a condition, an explicit lock, a join or a future. If workers are in a queue wait, I check the predicate under its lock, who changes it, and whether that path notifies the correct waiters. If the queue is closed and empty, every sleeping worker needs a route out. I also check whether a waiter retains an unrelated lock needed by the producer. If all pool workers are waiting for child futures, those children may be queued in the same exhausted pool. External I/O could simply be stalled. Once I have an interleaving that explains the evidence, I force it with gates in a small test, make one focused repair, and check both the invariant and termination with a deadline. Then I continue looking for bugs the hang hid.

Out loudabout 60 s
"The queue uses a loop around wait. Why might it still hang when we close it?"
What a strong answer covers
  • A predicate loop handles wakeups but does not create a shutdown protocol
  • Wait while empty and not closed, using one lock for the check and state changes
  • Close sets the flag and wakes every waiter
  • Drain accepted work and reject new submissions atomically with close
  • Join consumers before destroying the queue and test several sleeping consumers
How a senior would say it
A loop makes wakeups safe, but it does not tell a worker that no more jobs will arrive. The consumer should wait while the queue is empty and it is not closed. Close sets the closed flag under that same lock and wakes every waiter. With two sleeping consumers, waking only one can leave the other asleep forever, even though its exit condition is now true. After waking, consumers drain accepted jobs and exit only when the queue is both closed and empty. Submission must check closed under the enqueue lock, so a late producer cannot add a job after the last consumer leaves. The owner then joins the consumers before destroying the queue or its mutex. I would test closing an empty queue with several blocked consumers, plus close racing with submission, and verify that every accepted job is processed exactly once.

Out loudabout 60 s
"The counter is wrong, but only occasionally. It passed under the race detector today. Is the fix done?"
What a strong answer covers
  • A clean execution or detector run is evidence, not a proof of correctness
  • Explain one lost-update interleaving and distinguish Java from C++ undefined behaviour
  • Use an atomic read-modify-write or one lock over the complete invariant
  • Explain why join and volatile do not repair concurrent increments
  • Test exact totals and explain the happens-before argument
How a senior would say it
No. I need a reason the counter update is correct for every allowed interleaving, not just a clean run. Two workers can both read five, both add one and both write six, losing an update. Java permits that wrong result; in C++, unsynchronized conflicting accesses to a plain counter are a data race and undefined behaviour. I would use an atomic read-modify-write for an independent counter, or protect the whole invariant with one lock if other fields must agree with it. Joining workers makes completed writes available to the caller, but does not make those earlier increments atomic. Java volatile alone also leaves the read and write separate, and C++ volatile is not thread synchronization. I would assert exact totals after joins, exercise several worker counts, and run the detector again. The final justification is the atomic operation or lock protocol, with tests as supporting evidence.
