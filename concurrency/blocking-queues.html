Blocking queues

Queue contracts, bounded backpressure, timed waits, shutdown, Java's queue family, and building one-lock and two-lock queues in C++.

Asked atRubrikLinkedInBloombergMicrosoftDatabricks
Before this:Producer and consumer with a bounded bufferCondition variables and monitors

A blocking queue connects producers to consumers inside many thread pools, log writers, crawlers and pipelines. Interviewers either hand you one and ask which kind and why, or take it away and ask you to build it.

In plain words

Picture the order rail in a busy restaurant kitchen. Waiters clip tickets onto one end; cooks pull the oldest ticket off the other end. If the rail is full, a waiter has to stand and wait until a cook frees a clip. If the rail is empty, cooks wait until a ticket arrives. Nobody shouts, nobody checks the rail every two seconds: they simply wait until there is room or there is work.

That rail is a blocking queue. The waiters are producers, the cooks are consumers, and the fixed number of clips is what stops the waiters from burying the kitchen in tickets. The size limit is not a nuisance; it is how the kitchen tells the dining room to slow down.

What a blocking queue promises

A blocking queue is a thread-safe queue with two extra powers: a thread that wants an item can sleep until one arrives, and (when the queue has a capacity) a thread that wants to add an item can sleep until there is space. Three promises come with it:

  • Safety: each successful insertion creates one queue entry that can be removed at most once. Concurrent operations preserve the structure; eventual removal requires consumers to keep running. This says nothing about successful processing or durability after removal.
  • Waiting without a busy loop: a blocking queue can park waiting threads instead of continuously polling. Our implementation uses a condition variable; library implementations may briefly spin before parking, and wakes can be spurious.
  • A memory hand-off: everything a producer wrote before putting an item is visible to the consumer that takes it. In Java this is written into the BlockingQueue contract as a happens-before edge; in a C++ queue you build, the mutex gives you the same edge.

A bound makes back-pressure possible: producers can wait for space or receive an explicit rejection when consumers fall behind. The queue bounds queued entries, not the memory held by blocked producers or tasks already running. That is why the first question is "what is its capacity, and what happens when it is full?"

Four ways to put and take

Java's BlockingQueue offers four flavours for insertion and removal, and choosing the right one is a design decision. Inspection has only two flavours. The custom queues below implement blocking insertion and removal, timed insertion, and close; the checkpoint adds timed removal.

  • put and take are for worker threads whose whole job is to wait for work or for room.
  • Timed offer can limit a dedicated request thread's admission wait to its remaining budget. Rejecting when that wait expires is load shedding; do not block a network event loop waiting for capacity.

Null elements are rejected with NullPointerException, because poll uses null to mean "nothing there". On full or empty queues, add throws IllegalStateException, while remove() and element() throw NoSuchElementException. peek() returns null on empty. Immediate offer and poll do not wait for space or data, but may still contend for an internal lock.

drainTo(collection, max) removes up to max available items. ArrayBlockingQueue batches this under one lock acquisition; that locking strategy is not an interface guarantee. It is not a transaction with the destination collection: an exception from that collection can leave a partial transfer. Use a private batch owned by the consumer.

Building one: what you write when the library is banned

The C++20 standard library has no blocking queue, so you build one or use a suitable library. Rubrik and LinkedIn reports include rounds that disallow built-in queues. The design is the monitor from the producer and consumer lesson, extended with timed insertion and an explicit shutdown contract.

Every wait rechecks its predicate under the lock. Java's awaitNanos carries forward the remaining condition-wait budget; C++ uses a fixed steady-clock deadline. Neither restarts a full timeout after a wakeup. These are not hard return-time guarantees: initial mutex acquisition, reacquisition and scheduling can delay return. The Java example does not charge initial lock acquisition to its budget; an end-to-end admission budget needs timed lock acquisition too.

Close wakes every waiter and permits draining. The invariant is 0 <= size <= capacity, with contents and closed guarded by the same mutex. Insertion, removal and setting closed each take effect under that mutex. If insertion wins the race with close, the item is accepted and remains drainable; if close wins, insertion fails. Repeated close is harmless. A closed, empty queue returns an end marker rather than waiting.

The C++ sample requires nonthrowing moves and destruction so taking an item cannot fail midway through removal. Allocation during insertion can still throw; the catch wakes another producer to use the available slot. Arguments are passed by value, so a caller that moved an item into a failed put or offer must not assume it still owns the original payload. These features also work in C++17. Timed examples assume representable clock arithmetic; a general API must validate or clamp oversized durations. Java propagates interruption before modifying the queue; recovery from allocation failure is outside this teaching sample's contract.

Shutdown is a lifecycle protocol. Stop admission, close, let consumers drain, then join every thread before destroying the C++ queue. Waiting for producers before closing is safe in this demo because consumers continue draining; it could hang if all consumers had failed. With one shared condition for both predicates, use broadcast notifications to avoid waking only the wrong kind of waiter. Two separate conditions make single-waiter signals useful, but do not promise fairness or a scheduling deadline.

Blocking also needs a progress argument: if every thread in a fixed pool blocks trying to produce into a full queue, consumers queued behind them cannot run. Likewise, never keep a lock needed by consumers while waiting for space. Use separate execution capacity or an admission policy that can fail instead of creating a resource cycle.

Three special shapes

Hand-off. A SynchronousQueue is a rendezvous: put returns only once a consumer has taken the item. It is the right queue when buffering would hide a problem, for example when you would rather start a new worker (or reject) than let tasks pile up.

Delay. A delay queue is a priority queue ordered by due time, where take sleeps until the earliest item is due. The trap is the item that arrives while a taker is already asleep:

Java's DelayQueue also uses a leader: only one taker does the timed wait for the head, and the others wait without a timeout, so a hundred idle takers do not all wake at every deadline. You build this in the delay queue problem and use it in scheduled executors.

Its elements implement Delayed: getDelay(TimeUnit) reports remaining delay, and compareTo(Delayed) must order consistently with it. Base elapsed time on a monotonic clock, and do not mutate a queued element's priority in place. peek() may return an unexpired head and size() counts it, while poll() returns null until an item expires. FIFO element order and waiter fairness are separate properties; even a fair ArrayBlockingQueue does not guarantee that consumers finish processing in dequeue order.

Transfer. A normally returning LinkedTransferQueue.transfer(e) guarantees receipt by a consumer, not completion of processing. Ordinary put does not wait for receipt. tryTransfer(e) returns false without retaining the item if no waiting consumer can receive it; the timed overload can wait for a match. A SynchronousQueue similarly has zero storage capacity: size() is always zero, even with producers waiting to hand off items.

Two locks: how LinkedBlockingQueue lets both ends run at once

With one lock, a producer and a consumer can never work at the same time, even though they touch opposite ends of the queue. LinkedBlockingQueue uses a two-lock queue, a variant of the two-lock algorithm Michael and Scott published in 1996:

  • A linked list that always starts with a dummy node. The first real item is head.next.
  • For ordinary enqueue and dequeue, a put lock guards the tail and a take lock guards the head. Some operations, such as clearing the whole queue, need both locks.
  • An atomic count tells each side about the other. A producer links its node, then increments the count; a consumer reads the count before reading head.next. That atomic increment and read are the happens-before edge that makes the new node's contents visible.
  • Signals cross locks sparingly. A producer signals "not empty" only when the count goes from 0 to 1 (and must hold the take lock to do it), and a consumer that leaves items behind wakes the next consumer itself. This is called cascading notification.

Why it is safe: linking happens before incrementing the atomic count. A consumer follows a link only after observing a positive count, so it cannot read an unpublished link. With one item, producer and consumer may touch different fields of the same node: the producer appends through its next, while the consumer takes its item and makes it the dummy. The cross-lock signal happens after releasing the producer lock, avoiding nested acquisition in this example.

This teaching version omits capacity, close and cancellation in C++, and assumes fewer than Integer.MAX_VALUE queued entries. Its C++ node also requires a default-constructible, move-assignable payload. LinkedBlockingQueue adds a capacity and a mirror-image notFull condition on the put lock. Two locks can improve throughput when both ends are busy, but allocation, the shared atomic count and cross-lock signals still cost work: measure rather than promise a speedup.

Worked example: picking the queue for a log writer

Databricks reports repeatedly describe a concurrent, ordered, durable log writer: many threads call append(event), events must reach the file in order, and storage sync can be slow. Walk the queue decisions out loud:

  1. Shape: many producers, one writer thread, so a multi-producer queue drained by a single consumer. One consumer keeps the file order equal to the queue order for free.
  2. Bound: bounded, for example 10,000 events, subject to a measured memory and latency budget. Also bound bytes if event sizes vary. A stalled disk otherwise lets pending data consume memory without limit.
  3. Full policy: for durable logs, block the producer with put (or a timed offer that reports failure to the caller). Silently dropping an event that the caller believes was logged is the one unacceptable choice.
  4. Batching: the writer does take() for the first event, then drainTo(batch, 511) for whatever else is waiting, writes the batch, and calls fsync once. Under load, one sync now covers hundreds of events. That is group commit, and you will build it in the durable log writer problem.
  5. Shutdown: close() stops new appends, the writer drains everything that was accepted, syncs, and exits.

FIFO means queue insertion order, not wall-clock invocation order for overlapping appends. Assign sequence numbers at admission if the API needs an explicit order. Enqueue success is not a durability acknowledgement: complete each caller's future only after the batch's sync succeeds, and propagate write or sync failures. The shutdown contract must say how such failures reach waiting callers.

In C++ the drain is one more method on the queue you built: wait until the queue is not empty or closed, then move up to max items into the caller's vector under the same single lock acquisition.

Common mistakes

  • Unbounded by accident. new LinkedBlockingQueue<>() and newFixedThreadPool are unbounded. Always pass a capacity and decide what happens when it is full: block, time out, or reject.
  • Re-arming the timeout. Writing while (empty) cv.wait_for(lock, timeout) gives a fresh full timeout after every wakeup, so the total wait has no limit. Fix the deadline once (wait_until, or loop on the value awaitNanos returns).
  • Check, then act. if (!q.isEmpty()) x = q.take(); or if (q.size() < cap) q.put(x); races with other threads between the two calls. Use the single call that does both: poll, offer.
  • Wrong poison-pill protocol. If every consumer exits after consuming one pill, N consumers need N pills. Stop ordinary producers before inserting them into a FIFO queue; otherwise work can arrive behind the pills. In a priority queue a pill may not sort last, and a bounded queue can block the shutdown thread while it inserts pills.
  • Spinning on a non-blocking queue. while ((x = clq.poll()) == null) {} burns a core. If consumers must wait, use a blocking queue.
  • Swallowing interrupts in a worker loop. Catching InterruptedException and carrying on means shutdownNow can never stop the worker. Restore the flag and exit.
  • Changing an item after putting it. The hand-off makes writes before the put visible, not writes after it. Treat a queued object as handed over.

In the interview

It comes in three forms. First, "implement a bounded blocking queue" (LeetCode 1188), which Rubrik, LinkedIn and Bloomberg candidates report, sometimes with the library banned and, in one LinkedIn loop, with only wait and notify allowed. Second, inside a bigger problem: the queue in a thread pool, a crawler or a log writer. Third, as a choice: "which queue would you put here, and what happens when it is full?"

I will make it bounded, because the bound is the backpressure: when consumers fall behind, producers slow down instead of memory growing. It is a monitor: one lock, a not full and a not empty condition, every wait in a loop. For timeouts I fix the deadline once and wait for the time that is left, and close wakes everyone so consumers can drain and exit.
If producers and consumers both contend, I would use the two-lock design that LinkedBlockingQueue uses: a put lock for the tail, a take lock for the head, and an atomic count that carries the happens-before between them.

Follow ups to expect: add poll(timeout) and close(); why while and not if; one condition or two; "build it on a fixed array" (a ring buffer with head, tail and count, as in the ring buffer problem); Rubrik's "now two queues share one buffer"; "how would you shut down the consumers"; and "what does SynchronousQueue do, and which executor uses it?"

Senior depth

Queue depth is a health signal. Monitor depth, oldest-item age, rejection rate and processing latency together. A full queue can mean a stalled consumer or dependency, not just too few workers. With steady FIFO service, an item behind Q others waits roughly Q divided by the aggregate drain rate; this is an estimate, not a tail-latency guarantee. Little's law relates long-run averages in queueing math.

When the lock itself is the bottleneck. An SPSC ring can avoid a mutex: the producer release-publishes the tail after filling a slot, and the consumer acquire-loads it before reading. The consumer release-publishes the head after finishing with the slot, and the producer acquire-loads it before reuse. Reserve one slot or use sequence counters to distinguish full from empty across wraparound. Multiple producers or consumers need a different protocol, and adding a blocking wait requires its own missed-wakeup proof. Measure before replacing the monitor.

Key takeaways

  • A blocking queue is a thread-safe queue where takers sleep while it is empty and, if bounded, putters sleep while it is full. The hand-off carries happens-before.
  • Choose the flavour on purpose: put and take for workers, timed offer to shed load at the edge, timed poll for periodic work, drainTo for batches.
  • Choose a bound and an explicit full policy. Sustained overload with unbounded buffering risks memory exhaustion and increasing latency.
  • C++ has no blocking queue: build a monitor with one mutex, two condition variables, predicate waits, a deadline for timeouts and a close that notifies everyone.
  • LinkedBlockingQueue allows enqueue and dequeue to overlap with two locks and an atomic count, with occasional cross-lock signalling. SynchronousQueue has no storage capacity; DelayQueue must wake a taker when an earlier head arrives.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A fixed-size worker pool accepts every task into an unbounded FIFO queue. Its sustained arrival rate exceeds its processing rate. What follows if this continues?
Why. More work arrives than the fixed workers remove, so pending work accumulates. This queue supplies no finite capacity threshold that would block or reject submissions, and the stated pool cannot add workers. The time to exhaust memory depends on spare memory, task sizes and the excess arrival rate; one hour is not a universal threshold.
A timed take is written as: lock; while (queue is empty) { wait on the condition for up to 100 ms; }; then take. Several producers often call notify-all for unrelated reasons. What is the bug?
Why. A timed operation must fix its deadline once and wait only for the time that remains (wait_until(deadline), or the value awaitNanos returns), and must return "nothing" when the deadline passes. As written, the loop never exits on timeout, and each wakeup grants another full 100 ms. Timed waits do release the lock while waiting.
Why can the two-lock linked queue let one producer and one consumer modify the queue at the same instant, while a single-mutex bounded queue cannot?
Why. ArrayBlockingQueue has one lock for both ends, so a put and a take serialize. LinkedBlockingQueue keeps a dummy head node so producers only touch the tail and consumers only touch the head; the atomic count tells each side whether the other has made the queue non-empty or non-full, and its increment and read carry the happens-before. It is still a locking, FIFO queue.
A producer writes payload.value = 42, successfully enqueues the payload, and never mutates it again. A consumer takes it and prints value. With Java's BlockingQueue or our C++ monitor queue, what is guaranteed?
Why. The successful hand-off carries a happens-before edge, so the consumer sees 42 without making the field atomic or volatile. This is not unique to ArrayBlockingQueue. A later unsynchronized producer mutation would need separate coordination; enqueueing does not publish future writes.
A delay queue holds one item due at 10:00:05, and the only taker is sleeping until then. A producer adds an item due at 10:00:01. Which notification policy is sufficient and avoids wakes for insertions that leave the head unchanged?
Why. The taker computed its sleep from the old head. Unless put signals when it installs a new earliest item, that item is served four seconds late. Waking everyone on every put would be correct but wasteful; the precise rule is "signal when the head changes".
Java onlyFor a valid non-null item and a bounded BlockingQueue that remains full, which call returns false without waiting for capacity?
Why. offer(e) is the special-value flavour; acquiring an internal lock may still delay it. add throws IllegalStateException when full, put waits for room, and timed offer waits for room within its wait budget before returning false.
C++ onlyIn the C++ offer, what does notFull_.wait_until(lock, deadline, pred) return?
Why. The predicate overload behaves like while (!pred()) if (wait_until(lock, deadline) == std::cv_status::timeout) return pred(); return true;. So the result is about the condition, not about whether a notify happened: a notify that finds the queue still full keeps waiting, and a timeout that races with a freed slot still returns true. std::cv_status is what the overload without a predicate returns.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Add poll(timeout) to the bounded queue: it waits up to the timeout for an item, and returns nothing (null in Java, an empty optional in C++) if none arrives or the queue is closed and empty. Write it in your language.
Model answer

The key points: C++ computes a steady-clock deadline once, Java carries forward the remaining condition-wait budget, and every wake rechecks the predicate. Timeout or closed-and-empty returns an end marker, and removal signals a producer. As with offer, lock acquisition and scheduling mean neither method promises a hard return-time bound.

Design
You are building the work queue for a service's request handlers. Requests arrive from the network; a pool of 32 workers processes them. Which queue would you choose, with what capacity and full policy, and why?
Model answer

I would start with a bounded FIFO queue: ArrayBlockingQueue in Java or a monitor queue in C++. At a steady aggregate drain rate of 400 requests a second, 250 ms corresponds to about 100 queued items. That is a first sizing estimate, consistent with Little's law for averages, not a guarantee about the slowest request; I would measure service-time variation, bursts and memory use. An event-loop thread should use immediate admission and reject overload, for example with HTTP 503, instead of waiting for space. A dedicated request thread may use timed admission within its remaining deadline. Even immediate offer can contend for the queue lock. I would monitor depth, oldest-item age and rejections, and stop admission before draining and joining workers.

Explain
An interviewer asks: "Explain how LinkedBlockingQueue can let a producer and a consumer run at the same time without breaking the queue." Answer as you would out loud.
Model answer

It separates normal enqueue and dequeue work: the put lock protects the tail and the take lock protects the dummy head. A producer links its node before incrementing the atomic count. A consumer observes the count before following the next link, which safely publishes the node across the two locks. When empty, a consumer waits instead of following an unpublished link. At one item, the threads may access different fields of that same node, which is safe. Cross-lock signals still exist: after a zero-to-one transition, the producer releases its lock and takes the consumer lock to signal; a consumer leaving more items signals the next consumer. The bounded library queue mirrors this for waiting producers. Some whole-queue operations take both locks. This permits useful overlap but does not guarantee higher throughput: allocation and count contention can dominate.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"Design a bounded blocking queue with a timeout and graceful shutdown. Talk me through the races you have to get right."
What a strong answer covers
  • One mutex protects contents, capacity checks and the closed flag
  • Separate not-empty and not-full conditions recheck predicates after every wake
  • Timed waits consume one budget rather than restarting it; return timing is not hard real time
  • Close rejects new insertions, wakes both sets of waiters and lets accepted entries drain
  • The shared mutex orders insertion against close and publishes payload writes
  • Stop admission and join users before destruction; dequeue is not processing or durability acknowledgement
How a senior would say it
I would use one mutex, two conditions and an explicit closed flag. The invariant is that the number of entries stays between zero and capacity. Producers wait while full, consumers wait while empty, and both predicates also check whether the queue has closed. Every wake rechecks under the mutex because another thread may already have used the slot or item. For a timeout, I preserve one deadline or a decreasing wait budget. I do not restart a full timeout after each notification. Lock acquisition and scheduling can still delay the return, so this is not a hard real-time promise. Close takes the same mutex, marks the queue closed and wakes every producer and consumer. New puts fail, while takes drain accepted items and then return an end marker. If a put races with close, whichever changes the state first under the mutex determines whether that item was accepted. The mutex also publishes the producer's earlier payload writes to the consumer. Finally, I stop admission and join every user before destroying the queue. Removing an item only transfers responsibility. It does not prove that processing succeeded or that a log record is durable; those require a separate acknowledgement protocol.

Out loudabout 75 s
"Our service gets slower during a burst, but adding queue capacity seems to help briefly. What would you check, and which queue policy would you choose?"
What a strong answer covers
  • Compare sustained arrival and drain rates; extra capacity cannot fix a throughput deficit
  • Inspect depth, oldest-item age, service latency and rejection rate
  • Choose a finite bound from memory and latency budgets, with workload measurements
  • Use immediate rejection on event loops or timed admission on suitable request threads
  • Separate queue receipt from completion, including synchronous hand-off
How a senior would say it
I would first check whether arrivals exceed the workers' drain rate. A larger queue can absorb a short burst, but it cannot fix a sustained throughput deficit. It stores more waiting work, which can hide overload until latency or memory becomes unacceptable. I would compare queue depth and oldest-item age with worker service times and rejection rate. A slow dependency or a failed consumer can look like too few workers, so adding threads is not automatically the fix. I would choose a finite capacity from the memory and queueing budgets, then validate it with realistic bursts and service-time variation. For example, at a steady four hundred completions a second, a hundred queued requests represent roughly a quarter-second of work, not a tail-latency guarantee. On a network event loop I would reject when immediate admission fails. A dedicated request thread could wait within its remaining deadline. A zero-capacity hand-off is another choice when buffering is undesirable, but even that only confirms that a consumer received the job. The caller needs a separate completion signal if it must know the work succeeded.
