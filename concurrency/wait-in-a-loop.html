Spurious and stolen wakeups: always wait in a loop

Why a woken thread must re-check its condition: spurious wakeups, stolen wakeups and notifyAll, with the interleavings that break an if.

Asked atRubrikLinkedInApple
Before this:Condition variables and monitors

The most common condition variable bug is one word: if where while belongs. It passes most tests, then crashes a consumer on an empty queue in production. Interviewers ask "why while and not if?" constantly, and the full answer has three parts, while most candidates stop after the first.

In plain words

In a busy restaurant kitchen, a bell rings when a plate is ready. Two waiters hear it and both walk to the counter, but there is only one plate. The waiter who arrives second must look at the counter and go back to waiting, not grab at empty air. And once in a while a gust of wind rings the bell with no plate at all.

So the rule for every waiter is: the bell means "go and look", never "your plate is there". Look every time, and wait again if there is nothing for you.

The rule

A woken thread must re-check its condition before acting, and go back to waiting if the condition is false. In code, the wait always sits inside a loop on the condition:

Why is the loop necessary, when the thread was only woken because something changed? Because being woken does not mean the condition is true, for three separate reasons.

Reason 1: spurious wakeups

A spurious wakeup is a return from wait that no thread asked for: no notify, no timeout, no interrupt. Every mainstream API allows it. The Java Language Specification permits implementations to remove threads from wait sets without being told to; the Javadoc of Object.wait, Condition.await and LockSupport.park all warn about it; the C++ standard says wait may unblock spuriously; and POSIX says the same of pthread_cond_wait, which is what both runtimes use underneath on Linux and macOS.

Why allow something so odd? Because it makes condition variables cheaper and simpler to implement: on a multiprocessor it can be hard to guarantee that a signal wakes exactly one thread and never more, and a sleep can be interrupted by an operating system signal. The POSIX rationale adds the real point: since callers must loop anyway, they also become robust to extra notifications sent from anywhere else in the program. Spurious wakeups are rare in practice. That does not matter: a correct program cannot depend on them not happening.

Reason 2: stolen wakeups

The more important reason, and the one that happens all the time. Java, C++ and POSIX all use mesa semantics: a notification only makes the waiting thread runnable. It does not hand it the lock. The woken thread must compete for the lock again, and by the time it wins, another thread may already have taken the lock and used up the state it was woken for. That is a stolen wakeup.

No unusual timing is needed: one thread that is already running takes the lock while another is still waking up. That is barging, which the fairness lesson showed is exactly what locks are designed to allow. So stolen wakeups happen constantly in any system with more than one consumer. Count them:

Every one of those hundreds of wakeups is a moment where an if version would act on an empty queue. In this demo it would return "closed" while the producer is still running, so a consumer would quit early; in a queue whose take() calls removeFirst() or pop_front(), it would throw or corrupt memory. Most come from the third reason below, notifyAll waking four consumers for one item, and the rest from consumers that were already running and got to an item first. Few, if any, are spurious in the strict sense. That is the point to make in an interview: even on a platform that never wakes spuriously, if is wrong.

Reason 3: notifyAll and shared wait sets

notifyAll wakes every waiter, but often only one of them can proceed: one item, four consumers. And when threads waiting for different conditions share one wait set (a Java monitor, or one C++ condition variable used by both producers and consumers), a notification meant for one kind of thread also wakes the other kind. In both cases most of the woken threads find their condition false and must wait again. With a loop, notifyAll is always correct, merely wasteful; with if, it is a bug. How to choose between notify and notifyAll, and the hang that the wrong single notify causes, is the subject of the next lesson.

The C++ predicate overload is the loop

In C++, cv.wait(lock, pred) is specified to be exactly while (!pred()) cv.wait(lock);. Use it every time; the house style of this course does. The predicate always runs with the mutex held, once before the first wait and again after every wakeup, so it may read the guarded state directly; keep it cheap and free of side effects, and never lock the same mutex inside it. The timed versions are loops too, with one important extra: they fix the deadline once.

  • cv.wait_until(lock, deadline, pred) loops until pred() is true or the deadline passes, and returns pred(): false means the time ran out with the condition still false.
  • cv.wait_for(lock, duration, pred) is wait_until(lock, steady_clock::now() + duration, pred): the deadline is computed once, so spurious or stolen wakeups do not extend the total wait.

Java has no predicate overload, so you write the loop yourself. For timed waits, carry the remaining time: awaitNanos returns it, and Object.wait(ms) does not, so with intrinsic monitors you compute it from System.nanoTime().

What the loop must check

The loop condition is the whole reason the thread may stop waiting, not only the happy case. A consumer that must also stop on shutdown waits while (queue is empty and not closed), and after the loop decides which one ended the wait: an item means take it, empty means the queue was closed. The demo's take() does exactly that. Forget the closed part and a consumer sleeps through shutdown; check closed outside the loop and a thread can be woken for shutdown, see an empty queue, and go back to sleep forever.

Worked example: proving the if version wrong in a debugging round

You are handed a bounded queue whose take() says if (items.isEmpty()) wait(); and whose put() calls notifyAll(). It passes the provided single-consumer test. The interviewer asks whether it is correct. Do not argue from "spurious wakeups are possible"; build a concrete interleaving with no spurious wakeup at all:

  1. Consumers C1 and C2 both call take(), find the queue empty, and wait.
  2. A producer puts one item and calls notifyAll(): both consumers become runnable.
  3. C1 re-acquires the lock first, takes the item, returns.
  4. C2 re-acquires the lock. With if, it does not re-check: it calls removeFirst() on an empty queue and throws NoSuchElementException (in C++, pop_front on an empty deque is undefined behavior).

Then fix it with while, and say the general rule: a wakeup is a hint to re-check, because of spurious wakeups, stolen wakeups and broadcasts. This is exactly the bug in the fix the lost wakeup problem, which also has a second bug you will meet next lesson.

Common mistakes

  • if around wait. Breaks on spurious wakeups, stolen wakeups and notifyAll. Always while, or the C++ predicate overload.
  • "notifyAll fixes it." It makes things worse with if: more threads wake for the same single change.
  • Calling C++ wait without a predicate. Then you must write the loop yourself; the predicate overload removes the chance to forget.
  • A loop condition that leaves out shutdown or timeout. The loop must cover every reason to stop waiting, and the code after it must tell them apart.
  • Re-waiting with the full timeout. Each early wakeup restarts the clock, so the total wait has no bound. Keep a deadline.
  • Treating a wakeup as a count. Code that does "one wakeup means one item arrived" miscounts under spurious and stolen wakeups. Count the state, not the wakeups.

In the interview

Expect "why while and not if?" after any blocking queue or producer-consumer you write by hand, which is exactly what Rubrik rounds (library queues banned) and LinkedIn rounds (plain wait and notify only) ask for, and "wait() in a loop and spurious wakeups" is on the theory checklist that keeps coming back in phone screens. An Apple report asked a close cousin: why wait() instead of a busy loop, with spurious wakeups in the answer. The weak answer stops at "spurious wakeups". The strong answer names all three causes and shows an interleaving that needs no spurious wakeup at all.

A wakeup only means "the state may have changed, check again", for three reasons. First, every API allows spurious wakeups, returns from wait that nobody signalled. Second, and much more common, wakeups get stolen: notify only makes the waiter runnable, and before it gets the lock back another consumer, possibly one that never waited, can take the item. Third, notifyAll, or one wait set shared by different kinds of waiters, wakes threads whose condition is still false. So I always wait in a loop on the condition, and in C++ I use the predicate overload, which is that loop.

Follow ups to expect: "How often do spurious wakeups happen?" (rarely; it does not matter), "Does notifyAll fix the if?" (no), "Show me an interleaving that breaks it without a spurious wakeup" (the worked example), "How do you add a timeout without breaking the loop?" (a deadline), and "With the loop, can a waiter still starve?" (yes, under barging; see Senior depth).

Senior depth

  • Mesa semantics are why the loop exists. Under hoare semantics the signaller hands the lock directly to the woken thread, the condition is guaranteed true, and, on a platform that also never woke threads spuriously, if would be enough. Every mainstream library chose Mesa semantics (signal and continue) for simplicity and throughput, and the loop is the price. The next lesson compares them.
  • The loop also makes notification sloppiness safe. With a loop, an extra notifyAll anywhere in the program costs CPU but never correctness. That robustness is a design feature, not an accident: the POSIX rationale for pthread_cond_wait names it as an added benefit of allowing spurious wakeups.
  • The loop buys safety, not fairness. Because of barging, an unlucky waiter can lose the race for the lock again and again while newcomers are served, so in principle it can starve (see livelock and starvation). A fair ReentrantLock(true) reduces this, because it favours the longest waiting threads when they re-acquire the lock, but it does not promise strict order. For strict first come, first served, put a ticket number in the state, make each waiter's predicate "my ticket is being served", and wake with notifyAll, since only one particular waiter can proceed. The loop stays in every version.
  • Library waits that loop for you. CountDownLatch.await, Semaphore.acquire, BlockingQueue.take, Thread.join, std::latch::wait and std::counting_semaphore::acquire re-check internally and never return early without reason (apart from interruption in Java). Raw wait, await, LockSupport.park and std::condition_variable::wait without a predicate are the ones that can.

Key takeaways

  • A wakeup means "check again", never "go ahead". Always wait in a while loop on the condition; in C++, use the predicate overload.
  • Spurious wakeups are allowed by Java, C++ and POSIX. Rare, but a correct program cannot rely on their absence.
  • Stolen wakeups are common: notify makes a waiter runnable, and another thread can take the state first. notifyAll with several waiters guarantees it.
  • The loop condition must cover every reason to stop (data, shutdown), and timed waits must keep one deadline.
  • Even on a platform with no spurious wakeups, if is wrong.

Two consumers wait on an empty queue. A producer adds one item and calls notifyAll. Both consumers use if around their wait. What happens?
Why. notifyAll wakes both. They re-acquire the lock one after the other; the first empties the queue, and the second, having used if, never looks again. With while, the second would see the empty queue and wait again. They cannot take the same item, because each removal happens under the lock.
"Our platform never produces spurious wakeups, so if is safe." Is that right?
Why. Even with a single notify, a newly arriving thread can take the lock and consume the state before the woken thread re-acquires it. The loop is required by Mesa semantics, independent of spurious wakeups.
Which description fits a stolen wakeup?
Why. The first option is a spurious wakeup and the third is a lost wakeup. A stolen wakeup is a real notification whose benefit someone else consumed, which is normal under Mesa semantics, where the signaller does not hand the lock to the woken thread.
A consumer must stop waiting when an item arrives or when the queue is closed. Which wait is right?
Why. The loop condition must include every reason to stop waiting. Checking closed outside the loop means a thread woken by close() sees an empty queue and waits again forever. Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer points at your while (queue.isEmpty()) notEmpty.await(); and asks: "Why while? Isn't if enough, since you only get woken when something was added?" Answer fully.
Model answer

if is not enough, for three reasons. First, spurious wakeups: Java, C++ and POSIX all allow wait to return with no notification, so being awake proves nothing. Second, and far more common, stolen wakeups: Java and C++ use Mesa semantics, where signal only makes the waiting thread runnable; it does not give it the lock. Before it re-acquires the lock, another consumer, even one that was never waiting, can take the lock and the item. Third, broadcasts: signalAll or notifyAll wakes every waiter for what may be a single item, and with a shared wait set it also wakes threads waiting for a different condition.

So a wakeup only means "the state may have changed". The loop re-checks the condition while holding the lock, and only proceeds when it is true right now. It also makes the code robust to extra notifications from anywhere, and the same loop is where shutdown and timeouts get checked. In C++ I would write it with the predicate overload, cv.wait(lock, [&] { return !queue.empty(); }), which is that loop.

Pseudo code
A queue uses if (empty) wait() in take(), and put() calls a single notify(). Write an interleaving, with no spurious wakeup, in which a consumer removes from an empty queue.
Model answer
  1. Consumer C1 calls take(), sees the queue empty, and waits (releasing the lock).
  2. Producer P calls put(x): takes the lock, adds x, calls notify(), which makes C1 runnable, and releases the lock.
  3. Before C1 gets the lock back, consumer C2 calls take(), gets the lock first, sees x, removes it, and returns.
  4. C1 finally re-acquires the lock. Because of the if, it does not re-check: it removes from the empty queue and fails.

The key move is step 3: C2 never waited, so a single notify() and perfectly ordinary scheduling are enough. Using while makes C1 see the empty queue in step 4 and wait again.

Write code
Write poll(timeout) for a queue guarded by a lock and a condition variable: return an item if one arrives within the timeout, otherwise return nothing. Early wakeups must not extend the total wait.
Model answer

The "take with a timeout, deadline kept across wakeups" code-pair in this lesson is a complete answer. In Java: convert the timeout to nanoseconds once, loop while (items.isEmpty()), return null if the remaining nanos are not positive, and otherwise nanos = notEmpty.awaitNanos(nanos), which returns the time still left, so a spurious or stolen wakeup only waits for the remainder. In C++: if (!cv.wait_for(lock, timeout, [&] { return !items.empty(); })) return std::nullopt;, which computes one deadline on the steady clock and loops internally; after it returns true, the item is guaranteed to be there because we hold the mutex. Both versions re-check under the lock after every wakeup and remove the item only while still holding it.

It is not paranoia, and spurious wakeups are the smaller half of the reason. Yes, Java, C++ and POSIX all allow a wait to return with no signal, and they are rare, but correct code cannot depend on rare. The bigger reason is stolen wakeups. Out loudabout 65 s
"Here is a symptom: under load, consumers occasionally fail on an empty queue, a NoSuchElementException from take() in Java or a crash in pop_front in C++. The unit test with one consumer always passes. What is your first hypothesis, and how do you confirm it?"
What a strong answer covers
  • Failing on an empty removal means a consumer went past its wait while the condition was false
  • First suspect: if around the wait instead of while
  • A single consumer test cannot show it, because nobody else can take the item
  • Under load a barging consumer steals the item, or notifyAll wakes several consumers for one item

How a senior would say it
My first guess is an if around the wait where a while belongs. The failure says a consumer removed from an empty queue, so it went past the wait while the condition was false. The unit test has one consumer, so nobody can steal the item and the bug never shows. Under load there are many consumers. A producer adds one item and notifies, but before the woken consumer gets the lock back, another consumer barges in and takes it. Or notifyAll wakes four consumers for one item. The first takes it, and the other three walk straight into an empty queue. To confirm, I would read the wait code, then write a stress test with several consumers and short bursts, which reproduces it in seconds. The fix is while instead of if, or the predicate overload in C++, and the stress test stays as a regression test.

Likely follow up: Would switching notifyAll to a single notify make the if safe?

Out loudabout 65 s
"Walk me through what goes wrong if a consumer's wait loop checks only that the queue is empty, and the closed flag is checked after the loop."
What a strong answer covers
  • The outcome: a consumer can sleep forever, and shutdown hangs in join
  • The interleaving: the consumer waits on an empty queue; close sets the flag under the lock and notifies all; the consumer wakes, sees the queue still empty, and waits again
  • Nobody will ever notify it again, because the producers have finished
  • The fix: the loop condition covers every reason to stop, so wait while the queue is empty and not closed
  • After the loop, tell the cases apart: take an item if there is one, otherwise report that the queue is closed
How a senior would say it
The consumer can sleep forever, and shutdown hangs. Say the loop is: while the queue is empty, wait, and closed is only checked after it. A consumer finds the queue empty and waits. Now shutdown runs: it sets closed under the lock and calls notify all. The consumer wakes and re-acquires the lock, but its loop condition only asks whether the queue is empty. It is, so it waits again. Nobody will ever notify it, because the producers are gone, and the thread that called shutdown hangs in join. The loop condition has to be every reason to stop waiting: wait while the queue is empty and not closed. After the loop I decide which one ended the wait. If there is an item, I take it, even during shutdown, so nothing is dropped. If the queue is empty, it must be closed, so I return a sentinel, like null or an empty optional.

Likely follow up: How would you also let a consumer give up after a timeout, without early wakeups stretching the wait?
