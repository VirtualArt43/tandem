Copy, move and move-only types

lvalues and rvalues, std::move, move constructors, moved-from objects, and the move-only types of threaded C++: threads, locks, owning pointers and promises.

Asked atAdobe
Before this:Classes, constructors, destructors and RAII

Threads, locks, futures and owning pointers in C++ can change hands but can never be duplicated. Move semantics is how ownership of a thread, a lock or a result travels between functions and between threads, and it is why handing data to another thread can be both cheap and free of sharing.

In plain words

You can photocopy a letter as often as you like. You cannot photocopy the one key the landlord gave you for your flat: you can only hand it over, and after that it is no longer in your pocket. A copy duplicates; a move hands over and leaves you empty handed.

Moving is also how you relocate a big library cheaply. Instead of copying every book into a new building, you hand over the keys to the old building. The books never move; only the right to use them does. That is why moving a vector of a million elements costs about as much as moving three pointers.

Why this matters for concurrency

  • std::thread, std::jthread, std::unique_lock, std::unique_ptr, std::promise, std::future and std::packaged_task are move-only. You store threads in a vector, return them from functions and pass promises into workers by moving them.
  • Moving data into a thread transfers ownership: the thread has it, you do not, so there is nothing to share and nothing to lock. It is the cleanest fix for the dangling reference bugs of the lifetime lesson.
  • A moved-from object is still alive. Knowing exactly what state it is in (a moved-from thread is not joinable, a moved-from lock owns nothing) prevents a class of crashes.
  • Moving instead of copying keeps critical sections short: pushing a large object into a shared queue under a lock should move a pointer, not copy megabytes.
  • At Databricks, one 2025 candidate wrote the durable event writer in C++ with std::promise and std::future, one promise per event. A promise can only be moved, so every one of those hand-offs is a move.

Copying is the default, and it has a price

From the values lesson: std::vector<int> b = a; copies every element. That independence is what makes copies safe, and the cost is real: copying a million int values copies about 4 MB and touches every cache line. When the source is about to be thrown away anyway, a temporary or a local you are returning, copying is pure waste. C++11 added a way to say "I am done with this; take its insides".

lvalues and rvalues

Every expression has a value category. Two questions decide it: does it have an identity (a name, an address you can come back to), and may its resources be stolen?

CategoryHas identityCan be moved fromExamples
lvalueYesOnly if you ask with std::movex, v[0], *p, a call to a function returning T&
xvalue ("expiring")YesYesstd::move(x), a call to a function returning T&&
prvalue ("pure" temporary)NoYes42, a + b, std::string("hi"), a call to a function returning T by value

xvalues and prvalues together are called rvalues: things you are allowed to move from. The short version: an lvalue is something with a name you might use again; an rvalue is a temporary nobody else can see, or an object you have declared you are finished with.

Rvalue references and overload resolution

An rvalue reference, written T&&, binds only to rvalues. Overloading on const T& versus T&& lets a function, or a constructor, pick a cheap path when the argument is expendable. That is exactly how the library chooses between a copy constructor and a move constructor.

Look at the last two lines of output. Inside pass_along, the parameter s has type std::string&&, yet take(s) picks the lvalue overload. A named rvalue reference is itself an lvalue, because it has a name and you could use it again on the next line. To pass it on as an rvalue you must say std::move again.

std::move is a cast, not a move

std::move(x) does nothing at run time. It is a cast to T&& that says "you may steal from x". The actual move happens later, if and when a move constructor or move assignment receives that rvalue. Two consequences:

  • If the type has no move constructor, the rvalue binds to the copy constructor and you get a copy. No error, no warning.
  • std::move preserves constness. The cast produces const T&&, which cannot bind to an ordinary move constructor's T&&. A copyable type such as std::string falls back to its const T& copy constructor; a move-only type such as std::unique_ptr cannot be transferred this way and fails to compile.

Writing a move constructor

Under the rule of zero you rarely write one: std::vector, std::string and std::unique_ptr members move themselves. You write one when your class owns a raw resource, such as an operating system handle. Here is the canonical shape, a move-only type that owns a file descriptor:

  • std::exchange(other.fd_, -1) takes the old value and leaves the source owning nothing, so its destructor does no harm.
  • Copies are deleted, so the type is move-only, exactly like std::thread.
  • Both moves are noexcept. That is not decoration. During reallocation, std::vector can use a nonthrowing move, or fall back to copying a copyable type whose move might throw. If copying is unavailable, it must use the move even if it can throw; a failure can then waive the strong exception guarantee. Mark a move noexcept only when it really cannot throw.

The moved-from state

A moved-from object is still a live object: its destructor will run, and you may assign it a new value. For standard library types the general promise is valid but unspecified: you may call functions with no preconditions (size(), empty(), clear()) and assign to it, but you must not rely on its value. A moved-from std::string is usually empty in practice, and nothing guarantees it.

The types you use with threads make specific promises, and these are worth memorizing:

Moved-from typeGuaranteed state
std::thread, std::jthreadNo thread: joinable() is false. Calling join() on it throws.
std::unique_lockNo mutex and no ownership: owns_lock() is false, and its destructor unlocks nothing.
std::unique_ptrNull
std::shared_ptrEmpty: null, use_count() is 0
std::futurevalid() is false; calling get() is undefined behavior
std::promiseNo shared state: set_value on it throws
std::string, std::vectorValid but unspecified: queries such as empty() are safe; satisfy each operation's preconditions, or assign a new value

Move-only types in threaded code

Each of these is move-only for the same reason: it represents something that must have exactly one owner. Two copies of a std::thread would mean two objects that could both join one thread. Two copies of a std::unique_lock would both unlock the mutex.

TypeOwnsWhy there can be only one
std::thread, std::jthreadOne running threadExactly one object may join or detach it
std::unique_lockThe right to unlock a mutexA mutex is unlocked once per lock
std::unique_ptrOne heap objectExactly one delete
std::promise, std::packaged_taskThe producer end of one resultA result is set once
std::futureThe consumer end of one resultget() can be called once; std::shared_future is the copyable version

Do not confuse move-only with immovable. std::mutex, std::condition_variable and std::atomic can be neither copied nor moved: other threads refer to them by address, so their address must never change while anyone might use them.

Passing move-only values into threads

The thread constructor moves its arguments into the new thread's storage when you pass rvalues, so move-only arguments work as long as you std::move them. Here a worker takes ownership of the data and hands its result back through a promise; nothing is shared, so nothing needs a lock.

Writing std::thread worker(fn, data, result) without the moves does not compile, because the thread would have to copy a unique_ptr and a promise. Three more patterns you will use constantly:

  • Threads in a container: workers.emplace_back(run, i); constructs in place, and workers.push_back(std::move(t)); moves an existing one in.
  • Returning a thread from a function: return std::jthread(run); just works.
  • Moving into a lambda: [job = std::move(job)] { job->run(); }, an init capture, covered in the lambdas lesson.

Returning values: elision, implicit moves, and the return std::move trap

Since C++17, returning a prvalue (return Widget(args);) constructs the result directly in the caller's object: copy elision is guaranteed, and no copy or move constructor runs, even for a type that has none. Returning a named local (return local;) may be elided too; if it is not, the local is treated as an rvalue and moved automatically. So return std::move(local); is never needed and is often harmful: it turns off elision. Clang's -Wall warns: "moving a local object in a return statement prevents copy elision". By-value parameters are moved implicitly too, and since C++20 so are T&& parameters, so they need no std::move either. The exception is returning something that is not a local or a parameter, such as a data member or an element of a container you want to move out; there std::move is right.

Moving keeps critical sections short

For shared queues and maps, the rule is: build the object before you take the lock, move it in under the lock, move it out under the lock, and do the work after you release it. Moving a std::unique_ptr transfers ownership without copying the payload, and ordinary vector move construction transfers its buffer. Do not assume every move or insertion is constant time: short strings can copy inline storage, allocator differences can require element moves, and queue insertion can allocate. Taking parameters by value ("sink" parameters) puts the caller's copy or move before the function takes the lock.

Notice the shape of pop: move the front element out, then pop_front the empty shell, then return by value. In C++98 a pop that returned the element could lose it if the copy threw after removal, which is why std::stack::pop returns void. With a noexcept move, returning by value is safe.

Worked example: a pool that aborts when it resizes

A hand-built pool keeps its workers in std::vector<std::thread> workers_. A new resize() replaces worker i with a fresh one, and the program sometimes dies with "terminate called without an active exception" or an abort:

Move assignment into a std::thread that is still joinable calls std::terminate, for the same reason its destructor does: the old thread would be silently abandoned. Whether the old worker is still running does not matter: a thread that has finished its function but was never joined is still joinable. The assignment only "works" when some other path already joined or detached that slot, so in practice the abort is almost certain.

The fix is to finish the old thread first: signal it to stop, join() it, then assign. Or hold std::jthreads, whose move assignment requests a stop and joins the old thread before taking the new one. Either way, say the rule: a joinable thread must be joined or detached before its handle is destroyed or overwritten.

Common mistakes

  • Ignoring the moved-from contract. Valid queries such as empty() on a string or joinable() on a thread are allowed. Joining a moved-from thread throws, and calling get() on a moved-from future is undefined behavior.
  • Expecting std::move to remove const, which instead makes ordinary copyable types copy and prevents transferring move-only types.
  • return std::move(local);, which blocks copy elision.
  • Forgetting noexcept on move operations, so containers copy instead of move when they grow.
  • Move-assigning into a joinable std::thread, which terminates the program.
  • Moving out of shared data without the lock. A move modifies the source, so it is a write and races like any other write.
  • Believing std::move makes anything thread-safe or atomic. It is a cast; ownership transfer is safe only when the hand-off itself is synchronized, by thread creation, a mutex, or a promise.

In the interview

A 2021 Adobe C++ candidate was grilled on move semantics together with smart pointers, lambdas and mutexes, and the questions come in these shapes: "why is std::thread not copyable?", "how do you return a value from a thread?", "how do you put threads in a vector?", "what state is a moved-from object in?", and as live coding: a queue of move-only tasks, or a promise per request in a writer like Databricks' event writer.

std::thread represents ownership of one running thread, and exactly one object may join it, so it is move-only. I store threads with emplace_back, return them by value, and transfer them with std::move. A moved-from thread is simply not joinable, and assigning over a joinable one terminates the program, so I always join or use std::jthread.
To get a result out of a thread without sharing a variable, I move a std::promise into the thread and keep its std::future; the worker calls set_value, and get() hands me the value with the right happens-before edge. Large inputs I move in too, so the thread owns them and nothing needs a lock.

Follow ups: "What does std::move actually do?" (a cast to an rvalue reference, nothing at run time); "Why noexcept on the move constructor?" (so std::vector moves instead of copies during reallocation); "Can std::function hold a lambda that owns a unique_ptr?" (no, std::function requires a copyable target; that is in the lambdas lesson).

Senior depth

Forwarding references. In a template, T&& with T deduced is not an rvalue reference but a forwarding reference: it binds to anything, and std::forward<T>(x) passes the argument on with its original category. std::thread's constructor is declared this way, then decay-copies (or moves) every argument into the new thread's storage. That is why rvalues are moved in and lvalues are copied, and why std::ref is needed to share.

Small buffer effects. Moving is not always cheaper than copying. A short std::string stored inside the object (the small string optimization) is copied byte by byte even when moved, and a std::array moves element by element. Moving a std::vector or a long string is a pointer swap.

A move is a write. Moving out of cache_[key] while another thread reads cache_[key] is a data race on that element, and the reader may see the hollowed-out source. Every move of shared data belongs under the same lock as every other access.

Key takeaways

  • lvalues have identity; rvalues are temporaries or objects you have given up. A named rvalue reference is an lvalue.
  • std::move is only a cast. The move happens in a consuming constructor or assignment; constness is preserved, so an ordinary copyable type copies and a move-only type cannot be transferred.
  • Moved-from standard types are valid but unspecified; threads become unjoinable, unique locks own nothing, unique pointers are null, futures invalid.
  • Threads, unique locks, unique pointers, promises and futures are move-only; mutexes, condition variables and atomics cannot move at all.
  • Move data into threads instead of sharing it, mark moves noexcept, never return std::move(local), and never move-assign over a joinable thread.

What does std::move(x) do when it executes?
Why. std::move is static_cast<T&&>. Only when that rvalue is handed to a move constructor or move assignment does anything move. If nothing consumes it, x is untouched.
const std::string s = std::string(1000, 'x'); std::string t = std::move(s); What happens?
Why. The move constructor takes std::string&&, which cannot bind to a const rvalue. The copy constructor takes const std::string&, which can. The code compiles, runs, and copies 1,000 characters.
std::thread t1(work); std::thread t2(work); t1 = std::move(t2); What happens on the last line?
Why. Move assignment to a joinable std::thread terminates the program, just like destroying a joinable one. Join or detach t1 first. std::jthread's move assignment instead requests a stop and joins the old thread.
What does this print?
Why. s has type std::string&&, but as an expression it has a name, so it is an lvalue and picks the const std::string& overload. std::move(s) turns it back into an rvalue.
Which of these types can be moved but not copied? Select all that apply.Select all that apply
Why. Threads, unique locks and promises each represent a single owner, so they are move-only (as are std::future and std::unique_ptr). std::shared_future exists precisely to be copied. std::mutex can be neither copied nor moved, because other threads find it by its address.
void run(std::unique_ptr<Job> job); and then auto job = std::make_unique<Job>(); std::thread t(run, job);. What happens?
Why. std::thread copies lvalue arguments into the new thread's storage, and std::unique_ptr cannot be copied. With std::move(job) the pointer is moved in, the thread owns the job, and job is null afterwards.
A copyable class has a move constructor that is not marked noexcept. A std::vector of it runs out of capacity during push_back. How are the existing elements transferred to the new buffer?
Why. push_back promises the strong exception guarantee. If moves might throw and a copy is available, the vector copies, so it can abandon the new buffer on failure. Mark moves noexcept and reallocation moves instead.

Write code
The caller has a large std::vector<int> it no longer needs. Start a worker thread that sums it and get the sum back, without sharing any variable between the threads and without copying the vector.
Model answer

No variable is shared: the vector moves from the caller into the parameter and then into the lambda, the promise moves into the thread, and the caller keeps only the future. Nothing is copied, because every hand-off is a move of a few pointers. get() blocks until the worker calls set_value, and that call happens-before get returns, so the sum is safely visible. (std::async or a std::packaged_task would also work; the promise version shows the moves explicitly.)

Explain
An interviewer asks: "What state is an object in after you move from it?" Answer in general, then for std::thread, std::unique_lock, std::unique_ptr, std::future and std::string.
Model answer

In general a moved-from object is still alive and its destructor will run. Standard library types promise "valid but unspecified": I can destroy it, assign it a new value, or call functions with no preconditions, but I must not rely on its value. Some types make precise promises, and the threading ones matter most. A moved-from std::thread or std::jthread represents no thread, so joinable() is false and joining it throws. A moved-from std::unique_lock has no mutex and owns nothing, so its destructor unlocks nothing. A moved-from std::unique_ptr is null. A moved-from std::future is invalid, and calling get() on it is undefined. A moved-from std::string is valid but unspecified: in practice usually empty, but I would assign or clear it before reusing it. For my own types I make moved-from objects cheap to destroy and safe to assign, like a file handle that holds -1.

Debug
A teammate writes std::string body = std::move(cache_[key]); inside Cache::take(key), while another thread calls Cache::peek(key), which returns a copy of cache_[key]. Both functions lock the same mutex, but take releases the lock before that line to "keep the critical section short". What can go wrong?
Model answer

Moving out of cache_[key] modifies the stored string: it steals the buffer and leaves the source hollow. Done outside the lock, it is a write racing with peek's read of the same element: a data race and undefined behavior. In practice peek may copy a half-moved string or read a freed buffer. There is a second problem: cache_[key] itself (an operator[] lookup that can insert) now runs without the lock, racing with any thread that changes the map's structure.

The fix keeps the move under the lock, which is still cheap because moving a string is a pointer swap: lock, find the entry, move it into a local, erase the entry or mark it taken, unlock, then do the slow work with the local. The general rule: a move is a write, and every access to guarded data, including moves out of it, happens under the guard.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"I wrote std::move, but a large string was still copied. What does std::move actually do, and what would you check?"
What a strong answer covers
  • std::move is a cast to an rvalue reference; the consuming operation determines whether resources move
  • Moving from const string selects copying because its ordinary move constructor needs a non-const source
  • A user-declared destructor can suppress implicit moves and leave a copy fallback
  • A named rvalue-reference parameter is an lvalue expression when passed onward
  • A moved-from standard object remains valid; its documented state and operation preconditions govern reuse
How a senior would say it
I would check overload resolution, because std::move does not move anything by itself. It casts the expression to an rvalue reference; the constructor or assignment that consumes it decides what happens. If the string is const, the cast preserves constness. The ordinary string move constructor cannot bind that source, so the copy constructor is selected. For a wrapper class, I would also check whether a user-declared destructor suppressed its implicit moves and left copying as the fallback. Another trap is forwarding from a parameter declared as an rvalue reference. Its name is still an lvalue expression, so passing it onward without another cast can copy. After a real move, I would follow the type's contract. A string remains valid but its value is unspecified; checking empty is allowed, assuming it is empty is not. The cast enables a choice, not a guarantee of cheap transfer.

Likely follow up: Why might a vector copy existing elements during reallocation even when their type has a move constructor?

Out loudabout 75 s
"Design a queue that hands large tasks from producers to workers without copying the payload. Where does ownership move, and where do you still need locking?"
What a strong answer covers
  • Represent each task with unique_ptr so ownership is explicit and cannot be copied
  • Build the payload before locking and move the owning pointer into the queue under its mutex
  • Wait with a predicate, then move the front pointer out and remove its slot under the same mutex
  • Process the owned task after unlocking; a noexcept pointer move avoids losing it through a throwing return move
  • Moving shared state is a write and does not create a synchronization edge by itself
  • Ownership transfer does not eliminate escaped aliases or guarantee allocation-free queue operations
How a senior would say it
I would queue unique pointers to tasks, so each task has one explicit owner and the payload stays in place. The producer builds the large task before taking the queue mutex, then moves its pointer into the queue while holding that mutex. A successful move leaves the producer's pointer null. The worker waits with a predicate for an available item. Still under the same mutex, it moves the front pointer into a local and removes the empty slot. It then releases the lock and processes the task through its local owner. Moving the pointer is nonthrowing, which also makes returning the removed task safe from a throwing move. The queue itself still needs synchronization: moving out of its front element modifies shared state, and std::move supplies no ordering. I would also check that the producer has not retained a raw pointer and continued using the task. Unique ownership does not erase aliases. Finally, queue insertion may allocate even though the payload move is cheap. For strict allocation limits, I would choose storage that is prepared in advance.

Likely follow up: What failure guarantees would change if the queue stored a task type whose move constructor could throw?

Out loudabout 75 s
"Replacing a worker with workers[i] = std::thread(run) terminates the process, even when the old worker has finished. Explain the failure and your replacement protocol."
What a strong answer covers
  • Move assignment to a joinable std::thread calls terminate
  • Finishing the thread function does not make its handle non-joinable
  • Signal and wake the old worker as needed, join it, then create and assign the replacement
  • Do not join while holding a mutex needed by the worker, and serialize handle management
  • Jthread move assignment requests stop and joins the old worker, but stopping remains cooperative
  • The replacement starts before assignment, so inline replacement can overlap old and new workers
How a senior would say it
The destination handle is still joinable, so thread move assignment calls terminate. Finishing the thread function is not enough: the owner must still join or detach that handle. For an owned worker, I would signal it to stop, wake any blocking wait as required, and join it. Only after the join would I create and assign the replacement. I would release any mutex the old worker needs before joining, and serialize management operations so two callers cannot replace the same slot concurrently. A jthread changes the assignment behavior: it requests a stop and joins the old thread before accepting the new handle. That helps with cleanup, but cancellation is cooperative, so an unresponsive worker can still hang the assignment. There is another timing detail in the original expression. The new thread starts when the right-hand temporary is constructed, before assignment begins. Replacing it inline with a jthread can therefore overlap the old and new workers. If the design requires exactly one active worker for that slot, I would keep stopping, joining and starting as separate ordered steps.

Likely follow up: What state is the source thread handle in after a successful move, and what happens if you call join on it?
