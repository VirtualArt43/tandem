Safe publication, immutability and final fields

How to hand a newly built object to other threads so they see it complete: the safe ways, immutable objects, final fields, and this-escape.

Before this:Happens-before and synchronizes-withvolatile in Java, std::atomic in C++

Building an object is not the dangerous part of sharing it. Handing it over is. Publish it the wrong way, and another thread can see the reference before it sees what the reference points to: a non-null object with empty fields.

In plain words

You are moving into a new flat and a friend will move in with you. If you text them the door code while the movers are still carrying furniture up the stairs, they may walk into an empty room. If you text the code only after the last box is inside, they find the flat ready. The furniture is the object's fields; the door code is the reference.

Safe publication means handing over the reference through a channel that guarantees the furniture arrived first. And an immutable object is a flat that, once furnished, nobody ever rearranges: any number of friends can live in it without coordinating at all.

What goes wrong: a reference without its contents

To publish an object is to make it reachable by another thread: store it in a shared field, put it in a shared collection, return it from a shared method. The natural code is a plain assignment:

new Config(...) is several steps: allocate memory, write the fields, store the reference. Nothing stops the compiler or the CPU from making the reference visible to another thread before the field writes, and nothing stops the reader from reading the fields early (the reordering lesson's message passing shape). So a request thread can see current != null and still read timeoutSeconds == 0 and region == null. In C++ the unsynchronized pointer is a data race, so the behavior is undefined.

The safe ways to publish

Safe publication means the reference travels over a happens-before edge, so everything written into the object before publication is visible to anyone who receives the reference. Each language has a short list; learn it.

The number of versions the reader happens to see changes from run to run; the "every one complete" part never does. Two design points in the C++ version deserve attention. First, the old versions are not freed while the reader runs, because the reader might still be using one; deciding when an old version can be freed is the reclamation problem, and it is why production C++ uses std::shared_ptr (below) or schemes like hazard pointers and RCU. Second, the reader loads the pointer once and uses only that object, which is what makes each check consistent.

Immutable objects

An immutable object is one whose state cannot change after its constructor finishes. It is the easiest thread-safe object there is: readers need no locks at all, forever, because there is nothing to race on. Only the hand-off of the reference needs one of the safe channels above.

  • Java: all fields final, no setters, the class final (or a record), and defensive copies of any mutable input or output (List.copyOf, Map.copyOf). A record is only shallowly immutable: record Order(List<Item> items) still lets anyone call items().add(...) on a list that was passed in, unless the compact constructor copies it.
  • C++: private members, const accessors only, and share the object as std::shared_ptr<const T> (or a const T* that outlives every reader). const is a promise the compiler checks, not a publication mechanism: the hand-off still needs release and acquire, a mutex, or one of the other channels.

There is a useful middle ground. An object whose class allows changes, but which nobody changes after it is published, is effectively immutable: a HashMap filled before Thread.start, or a std::vector filled before it is handed to a std::thread. Safely published, it can be read by any number of threads without locks. The difference from a truly immutable object is that the guarantee lives in your code's discipline, not in the type, so say so in a comment.

Java final fields: a guarantee even without an edge

Java gives final fields a special promise (final field semantics, JLS 17.5). When a constructor finishes, its final fields are "frozen". Any thread that later obtains a reference to the object, even through a data race, is guaranteed to see the final fields with their constructed values, and also everything reachable through them as of the end of the constructor (the contents of a final array or list it built). Non-final fields get no such promise.

The final field promise is why String, Integer and the other immutable JDK classes are safe to share even when published carelessly, and why immutability plus final fields is the most robust design in Java. Two limits matter. First, final fields guarantee the contents, not that the reader ever sees the reference: with a plain field, the reader may see null for a long time. Second, the guarantee holds only if this did not escape during construction. C++ has nothing similar: const members are not a memory model guarantee, so every hand-off of an object built at run time needs a real edge.

this-escape: publishing an object before it exists

This-escape is letting this reach another thread before the constructor finishes. The usual ways: starting a thread inside the constructor, registering this (or a lambda or inner class that captures it) as a listener with some other object, or storing this in a shared field. The other thread can then run code on a half-built object, and in Java even final fields lose their guarantee.

The Java version prints name = null although name is final; the sleep only makes the window wide enough to see every time. The C++ version has a second trap built in: members are initialized in declaration order, not in the order of the initializer list, so a std::thread member declared before the data it uses starts running before that data exists. ThreadSanitizer reports the race on interval_ms_.

The fix is the same in both languages: finish constructing, then publish. Use a private constructor and a static factory method that constructs the object and only then starts the thread or registers the listener. In C++, also declare thread members last, or start them from a separate start() call. Do not count on a compiler to catch this. javac 21 added -Xlint:this-escape, but it looks for a narrower bug, a public class that a subclass could extend leaking this before the subclass is initialized: in our tests it flagged list.add(this) in a public class, missed a thread started with this::poll, and stayed silent for final and non-public classes.

(The C++ factory uses new inside std::unique_ptr because std::make_unique cannot call a private constructor; ownership is still RAII from the first instant.)

Publication in C++, the practical options

For an object that is created once, let the language do it: a function-local static (thread-safe initialization since C++11) or std::call_once; the double-checked locking lesson covers both. For an object that is replaced over time, such as a configuration, the problem is not only publishing the new version but also freeing the old one once no reader uses it. std::shared_ptr solves the freeing; the question is how to share the pointer itself.

The C++ version holds the lock only to copy a pointer, so contention is low. C++20 adds std::atomic<std::shared_ptr<T>>, which does the same without a visible mutex. Check your standard library: GCC's libstdc++ (from version 12) and Microsoft's library provide it, while libc++, the library Apple's clang uses (and this site's runner), does not yet, which is why the snippet below is not runnable here. "Atomic" does not mean lock-free: libstdc++ implements it with a small internal lock, and is_lock_free() returns false there.

Worked example: hot reload of a rate limit table

A gateway checks every request against a table of per-customer limits. An admin thread reloads the table from a database every minute. Requests must never see a half-loaded table, and must never block on the reload.

  1. Make the table immutable. Build a complete Map (Java: Map.copyOf; C++: a std::unordered_map inside an object shared as std::shared_ptr<const Limits>). Nobody ever modifies a published table.
  2. Publish through one reference. Java: volatile Limits current or an AtomicReference. C++: the mutex-guarded std::shared_ptr holder above, or std::atomic<std::shared_ptr<const Limits>>.
  3. Read the reference once per request. Limits l = current; then use only l. Reading current.get(a) and later current.get(b) could straddle a reload and mix two tables.
  4. Old tables free themselves. In Java the garbage collector frees a table once no request holds it; in C++ the last shared_ptr copy does.
  5. Two admins reloading at once? Publication handles readers, not competing writers. If two reload paths can race, serialize them with a lock, or publish with a version check in a compare-and-set loop (the checkpoint below shows one) so a slow reload cannot overwrite a newer one.

The result is the shape behind copy-on-write designs (see copy-on-write and snapshots): readers never wait for a reload (in Java they take no lock at all; with the C++ mutex holder they wait at most for a pointer copy), writers do all the work, and the only shared mutable thing in the whole design is one reference.

Common mistakes

  • Publishing through a plain field. Readers can see the reference before the contents. Use a volatile or atomic reference, a lock, or a concurrent collection.
  • Mutating after publishing. Safe publication covers the writes made before the hand-off. Any later write to the shared object needs its own synchronization; better, never write it again.
  • "Final reference means immutable." final List<String> hosts stops reassignment of the field, not hosts.add(...). Copy mutable inputs and expose unmodifiable views or copies.
  • Unmodifiable wrappers over a live list. Collections.unmodifiableList(list) still reflects later changes to list. Use List.copyOf.
  • Starting threads or registering listeners in a constructor. Construct first, then publish, from a factory method.
  • Declaring a std::thread member before the data it uses. Members are initialized in declaration order.
  • Reading a swapped reference twice in one operation. Read it once into a local and use the local.
  • Freeing the old version too early in C++. A reader may still be using it. Use std::shared_ptr, or keep versions alive until no reader can hold them.

In the interview

It comes up as "how would you share a configuration that is reloaded at runtime?", as "is this class thread-safe?" for a class with a lazily assigned field, as "make this immutable", and in code review as a constructor that starts a thread. It also underlies every caching and snapshot design question: copy-on-write maps, routing tables, feature flag sets.

My default for shared data is an immutable object published through one volatile or atomic reference. Readers take the reference once and read a consistent snapshot with no locks; a writer builds a complete new version and swaps the reference, so the only concurrency question left in the design is who swaps it. Immutability means final fields, defensive copies and no escaping this from the constructor. In C++ I share it as a shared_ptr to const, behind a small mutex or an atomic shared_ptr, which also frees old versions when the last reader is done.

Follow ups to expect:

  • "What are the ways to publish safely?" The table above, in your language.
  • "What do final fields guarantee?" Visible contents for anyone who sees the reference, if this did not escape; not visibility of the reference itself.
  • "What is this-escape, and how do you prevent it?" Constructor starts a thread or registers a listener; use a static factory.
  • "How do you free old versions in C++?" shared_ptr, or hazard pointers and RCU in very hot paths.
  • "What if two threads update the config?" Serialize writers, or use compare-and-set so updates are not lost.

Senior depth

Benign races in the JDK. String.hashCode() caches its result in a non-final, non-volatile field with no synchronization. That is a data race, and it is still correct: the computed value is always the same, an int cannot tear, and a thread that sees 0 just recomputes it. It also reads the field exactly once into a local (int h = hash;) and returns the local, because two racy reads of the same field may return the new value and then the old one, so if (hash == 0) { ... } return hash; could return 0. This "racy single-check" idiom works only for idempotent results stored in a field that cannot tear, read once. In C++ the same code is a data race and undefined behavior, so it is never benign there; use a relaxed atomic.

The cost of immutability. Every change allocates a new object, so it fits read-mostly data. For a large map that changes often, copying the whole map per change is too slow; persistent data structures (sharing unchanged parts between versions) or a concurrent map are the alternatives.

Reclamation in C++. A reader that loaded a raw pointer to version 7 may still be using it when the writer wants to free version 7. shared_ptr solves it with reference counting, at the cost of an atomic increment and decrement per read. Read-heavy systems use epoch-based reclamation, hazard pointers or RCU instead; C++26 adds hazard pointers and RCU to the standard library. Saying "publication is half the problem; reclamation is the other half" is a strong senior signal.

Key takeaways

  • Publishing through a plain field lets readers see a reference before its contents. Publish over a happens-before edge.
  • Safe channels: volatile or atomic references, static or one-time initialization, locks, concurrent collections, thread start, executors and futures.
  • Immutable objects need no locks to read; only the hand-off of the reference needs care. Copy mutable inputs.
  • Java final fields guarantee visible contents even after a racy publication, unless this escaped. C++ const gives no such guarantee.
  • Never let this escape a constructor: construct, then publish. In C++, members are initialized in declaration order.
  • Read a swapped reference once per operation; in C++, use shared_ptr so old versions are freed safely.

Model answer

Each request calls snapshot() once and uses that object for the whole request, so it never mixes two versions. Readers never block on writers for longer than a pointer copy.

Explain
Explain to an interviewer what Java's final fields guarantee when an object is published through a data race, what they do not guarantee, and what a C++ programmer uses instead.
Model answer

In Java, when a constructor finishes, its final fields are frozen. Any thread that later obtains a reference to that object, even through a plain field with no synchronization, is guaranteed to see the final fields with the values the constructor wrote, and also whatever those fields referenced as of the end of the constructor, such as the elements of a final array it filled. That is what makes String and the other immutable JDK classes safe to share however they are passed around.

It does not guarantee three things. It does not make the reference itself visible: with a plain field the reader may keep seeing null or an old object. It does not cover non-final fields, which may still appear as default values. And it does not hold if this escaped during construction, for example by starting a thread or registering a listener in the constructor. C++ has no equivalent: const members are not a memory model guarantee, so the publication itself must carry a happens-before edge, such as a release store of the pointer and an acquire load, a mutex, call_once or a function-local static, or a shared_ptr behind a mutex or in std::atomic<std::shared_ptr>.

Because current is a plain field, there is no happens-before edge between the reload thread and the reader, so the compiler and the CPU may make the reference visible before the field writes, and the reader may even read the fields before it reads the reference. One interleaving: the reference lands, the request reads current, sees non-null, reads the timeout and gets the default zero, and only then do the field writes arrive. In C++ the same code is a data race, which is undefined behaviour. The fix is to publish over an edge. In Java I make current volatile or an AtomicReference; in C++ I store the pointer into an atomic with release and load it with acquire, or guard it with a mutex that readers take too. Making the fields final in Java also guarantees the contents through a race, but not that readers ever see the new reference, so I would still use volatile.

Out loudabout 75 s
"People call immutable objects the easiest kind of thread safety. Why is that, and what traps do you watch for when you make a class immutable?"
What a strong answer covers
  • Nothing changes after construction, so readers cannot race with writers and need no locks
  • The hand-off of the reference still needs a safe channel; Java final fields add a guarantee for the contents even through a race
  • Trap: a final or const field that points to a mutable list freezes which list, not its contents; copy inputs, never hand out the live list
  • Trap: letting this escape the constructor, which breaks even final fields
  • Cost: every change builds a new object, so it suits read-mostly data
How a senior would say it
Because once the constructor finishes, nothing changes, so there is nothing for two threads to race on, and readers need no locks, ever. The one moment that still needs care is the hand-off of the reference, which must go over a safe channel such as a volatile or atomic reference or a lock. Java adds an extra promise: final fields are visible to any thread that sees the object, even through a race. The traps are things that look immutable but are not. A final field that points to a mutable list only freezes which list, not what is in it, so I copy inputs with List.copyOf and never hand out the live list. In C++, a const pointer to a non-const vector has the same hole. The other trap is letting this escape from the constructor, by starting a thread or registering a listener, which breaks even the final field promise. And the price is that every change builds a new object, so immutability fits read-mostly data.
