Database isolation levels and anomalies

What each isolation level lets concurrent transactions see, the anomalies it allows, and what the Postgres and MySQL defaults really prevent.

Asked atAmazonDatabricksMetaRipplingMicrosoftLinkedIn
Before this:The lost update: read, modify, writeCheck then act: two safe calls, one unsafe sequenceInvariants, critical sections and finding shared state

Every race in this course has a twin inside the database. When two requests run transactions at the same time, the isolation level decides which interleavings the database lets through, and the defaults let through more than most engineers think.

In plain words

Picture a hospital rota pinned on a wall, and two doctors, Alice and Bob, both on call tonight. Both feel unwell. Each takes a photo of the rota on their phone, sees that two doctors are on call, and decides it is safe to go home. Each crosses out only their own name. Each change was fine on its own, and neither touched the other's line. Tonight nobody is on call.

A database transaction is a doctor working from a photo. The isolation level decides what the photo shows: the live wall at every glance, one photo taken at the start, or a promise that the outcome is the same as if the doctors had taken turns at the wall. The weaker the promise, the more of your own races the database lets through.

Transactions are critical sections with an undo button

A transaction groups reads and writes so that they commit or roll back as one unit, and, ideally, run as if nothing else were running. That second property, isolation, is concurrency control: it is the database's version of the locks you met in module 4, protecting rows instead of fields.

The gold standard is serializability: the result of running transactions concurrently is the same as running them one at a time in some order. Weaker levels relax guarantees, which can reduce coordination but permit specific anomalies. An isolation level tells you which interleavings the database promises to prevent. It does not guarantee a particular throughput improvement.

Databases combine locks, versions and conflict detection. Two-phase locking means acquiring locks in a growing phase, then releasing them in a shrinking phase without acquiring more; strict two-phase locking keeps write locks until commit or rollback. With MVCC, multi-version concurrency control, a reader can use an older committed row version instead of waiting for a writer. Postgres and MySQL InnoDB use versions for plain snapshot reads and row locks for writes; explicit locking reads and schema locks can still block.

The anomalies, one interleaving each

Each anomaly has an analogy in in-process code. The changes below come from other transactions, not your own writes; SQL transactions normally see their own earlier writes.

A phantom read means repeating a predicate query and seeing a changed set of matching rows. The weaker standard levels are commonly described by dirty reads, non-repeatable reads and phantoms; that list alone does not fully describe lost updates or write skew. Under snapshot isolation, a transaction reads one committed snapshot plus its own writes, and overlapping transactions that write the same row cannot both commit. It prevents dirty reads, non-repeatable reads, read skew, phantoms on snapshot reads and lost updates within the transaction, but it allows write skew: the two doctors write different rows. Constraints can introduce additional conflicts.

That history is why the same level name means different things in different databases. Never answer "what does repeatable read prevent?" without asking "in which database?".

What Postgres and MySQL actually do

The shipped defaults in PostgreSQL 18 and MySQL 8.4 InnoDB are READ COMMITTED and REPEATABLE READ, respectively; deployments can change them. The examples assume ordinary transactional tables, all reads and writes of an operation inside the same explicit transaction, and no concurrent schema changes.

PostgreSQL

  • READ UNCOMMITTED behaves like READ COMMITTED: ordinary table reads do not expose another transaction's uncommitted writes. Your own writes remain visible.
  • READ COMMITTED: a plain SELECT uses a fresh statement snapshot. An UPDATE that finds its target row locked waits; if the other transaction commits, it re-checks its WHERE clause against the updated row and uses that row's new values. This does not refresh every other row or subquery in the statement.
  • REPEATABLE READ is snapshot isolation. The snapshot is taken at the first non-transaction-control statement, not at BEGIN. Updating or locking a row another transaction changed and committed after that snapshot fails with could not serialize access due to concurrent update, SQLSTATE 40001; retry the whole transaction.
  • SERIALIZABLE uses Serializable Snapshot Isolation (SSI). It tracks read-write dependencies and may abort with SQLSTATE 40001 when it detects a pattern that could cause a serialization anomaly. SSI's predicate tracking adds no blocking beyond REPEATABLE READ; ordinary row and table lock waits still exist.

MySQL InnoDB

  • REPEATABLE READ (the default): plain consistent reads normally establish their snapshot at the first such read; START TRANSACTION WITH CONSISTENT SNAPSHOT can establish it immediately. UPDATE, DELETE and locking reads use current versions, including your own writes, and wait for conflicting writers. Range scans use gap or next-key locks; an exact lookup of an existing unique key needs only a record lock. There is no snapshot write-conflict check, so assigning a stale application-computed value can lose an update.
  • READ COMMITTED: a fresh snapshot per consistent read. Gap locking is normally disabled, except for foreign-key and duplicate-key checks, so new matching rows can appear.
  • SERIALIZABLE: like REPEATABLE READ, but with autocommit off every plain SELECT becomes SELECT ... FOR SHARE, so everything you read is share-locked until commit. Conflicts show up as lock waits and deadlocks (error 1213, SQLSTATE 40001), and you retry.

Fixing each anomaly without raising the level

  • Lost update: let the database do the arithmetic (UPDATE accounts SET balance = balance - 30 WHERE id = 42 AND balance >= 30), lock the row before reading it (SELECT ... FOR UPDATE), or check a version on write. The next lesson, optimistic versus pessimistic concurrency control, covers all three.
  • Read skew: read everything you need in one statement (a join, one query), or run the read-only report at Postgres REPEATABLE READ so it sees one snapshot.
  • Write skew on rows that exist: lock the rows the decision depends on, then decide from the returned values. Every path that could break the rule must participate.
  • Write skew over absent rows: PostgreSQL row locks cannot lock an absence. Use a constraint, lock an existing parent before a fresh check at READ COMMITTED, pre-create the rows you will fight over, or use SERIALIZABLE for all participating transactions.

Walk it at Postgres READ COMMITTED: Bob's SELECT ... FOR UPDATE blocks on the rows Alice locked. When Alice commits, Postgres re-checks each locked row against the WHERE clause; Alice's row no longer matches, so Bob gets one row back, and his check fails. At REPEATABLE READ, Bob gets a serialization error instead and retries, and the retry sees one doctor.

A constraint enforces the rule for every writer, including a code path added next year. For one ticket per seat, use a unique constraint on non-null (show_id, seat_id). Define nullability, valid time ranges and cancellation semantics too: an exclusion constraint alone does not reject an empty booking interval.

Retrying is part of the contract

Serializable isolation does not mean no conflicts. Transactions may wait or abort and require a retry. Postgres reports SQLSTATE 40001 for serialization failures and 40P01 for deadlocks; MySQL reports deadlocks as error 1213 with SQLSTATE 40001. Retry the whole transaction from BEGIN, including its reads and decisions.

C++ has no standard database API, so the C++ version wraps whatever client you use. Two rules hold in both languages. The body must not do anything outside the database (send an email, call a payment API), because a retry would do it again; that problem is the subject of idempotency and exactly-once effects. And the retries need a cap and jitter, or a burst of conflicts turns into a retry storm, as in bulkheads, timeouts and retries.

The Java helper owns a fresh, idle connection per attempt; the body must not commit, close or share it. A pool must reset connection settings on return. The C++ callback owns the transaction through its client library and must roll back on every failed attempt before the helper sleeps. Neither helper retries arbitrary connection errors, where the commit outcome may be unknown.

Worked example: which tool for which job

A transfer between two accounts on Postgres. At READ COMMITTED, lock both rows using SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE, with immutable account ids and the same order on every path. Check both exist and the debit is affordable, subtract from the source and add to the destination, then commit together. Alternatively use a guarded debit and an atomic credit in one transaction, checking both row counts and rolling back on failure; this still needs deadlock handling.

A nightly report that sums every balance. One plain aggregate query already has a statement snapshot at READ COMMITTED. For several related queries, use a read-only REPEATABLE READ transaction. It avoids row-lock conflicts with ordinary writers, but retains old versions and can conflict with schema changes.

The on-call rota. Lock the shift's on-call rows before counting, or use SERIALIZABLE with whole-transaction retries. Serializable protects the reads and decisions the transaction actually makes; it cannot invent a missing business-rule check.

Meeting room bookings. An exclusion constraint on (room_id, during). No locks to forget, no level to set, and a clear error to turn into "that slot was just taken".

Common mistakes

  • "Repeatable read prevents lost updates." In Postgres it does (with an error you must retry). In MySQL it does not: the UPDATE silently overwrites. Name the database before you answer.
  • "Serializable means I never see conflicts." It can reject an attempt. Retry safely or return an explicit failure; never treat an aborted transaction as successful.
  • Retrying only the failed statement. The reads that fed it are stale. Retry from BEGIN.
  • Locking the absence of rows. A PostgreSQL SELECT ... FOR UPDATE with no matches takes no row locks that exclude competing inserts. Table locks still exist. Use a constraint, a parent-lock protocol or serializable to protect the predicate.
  • Trusting a single UPDATE with a subquery to stop write skew. UPDATE ... WHERE (SELECT count(*) ...) >= 2 reads a snapshot without locking the rows it counted. Two such statements can both pass.
  • Side effects inside a retried transaction. An email sent inside the body is sent once per attempt.
  • Long transactions at snapshot levels. They pin old row versions (Postgres cannot vacuum them) and, if they took locks, hold them for the whole time.

In the interview

Reported designs include Amazon's last inventory unit, Databricks payments with concurrent transactions and failure recovery, Meta ticket booking, and Rippling hotel bookings over several nights. The precise anomaly depends on the schema and operations; a hotel booking is not automatically write skew. Microsoft reservation and LinkedIn screening reports also mention isolation directly. Name the invariant and the interleaving, state what your database prevents, then choose a fix.

At Postgres's default, read committed, two requests that read the balance and then write a computed value can lose an update, so I would not read-then-write. I would make the change one conditional statement, UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0, and check that one row changed.
The rule here spans rows: at least one doctor on call. Snapshot isolation allows write skew for exactly this shape, so I would either lock the rows the rule reads with SELECT ... FOR UPDATE, or run at serializable and retry on 40001. If the rule can be a constraint, like no overlapping bookings, I would let the database enforce it.

Follow ups to expect: "What is the default in Postgres and MySQL, and does it prevent this?", "What is the difference between repeatable read and snapshot isolation?", "Why not just use serializable everywhere?" (abort rates and retries under contention, plus every caller needs the retry loop), and "How do you prevent double booking when the conflicting row does not exist yet?".

Senior depth

A lock does not refresh your snapshot. At Postgres REPEATABLE READ, a parent-row locking statement can establish a snapshot before it waits. If the previous holder only locked the room row and inserted a booking, your later booking query can miss that committed insert. At READ COMMITTED, a separate query started after acquiring the parent lock gets a fresh snapshot. Every booking writer must follow the protocol; locking the parent and checking availability inside one statement is not the same guarantee.

Serializable is not automatic business correctness. Every transaction must preserve the invariant when run alone, and all participating operations must use the required isolation or locking protocol. Splitting the read and write into separate autocommit transactions defeats that protection. Serializability also does not itself promise real-time order; strict serializability adds that requirement.

Replica freshness is separate. An asynchronous replica can be behind your own last write even if each local transaction is isolated. Route a read to the writer or wait for the relevant replication position when read-your-writes is required. A successful commit whose acknowledgement is lost is another boundary: use an idempotency key before retrying an operation with an unknown outcome.

Under the hood

Postgres leaves old row versions available while snapshots still need them; long transactions can delay reclamation. SSI records read dependencies using nonblocking predicate locks, often called SIREAD locks. It detects dangerous dependency structures rather than waiting for a complete cycle, so some safe executions can also be aborted. All participating serializable transactions must successfully commit before you rely on their results.

InnoDB keeps the newest version in the table and rebuilds older versions from undo logs, using a read view (the snapshot) to decide which version a consistent read sees. Its locks live on index records: a record lock, a gap lock on the space before a record, and a next-key lock that covers both, which is how a locking range scan stops inserts into the range.

Key takeaways

  • Isolation levels are lists of races the database prevents; every anomaly has an in-process twin.
  • Defaults: Postgres READ COMMITTED, MySQL InnoDB REPEATABLE READ. Neither stops read-then-write lost updates or write skew.
  • Snapshot isolation stops torn reads but allows write skew, because the conflicting transactions write different rows.
  • Fixes: conditional statements, locking the rows a rule reads, constraints for booking predicates, or SERIALIZABLE plus retries.
  • Retry the whole transaction, with backoff and jitter, and keep side effects out of it.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Explain
An interviewer asks: "What is write skew? Give an example and two ways to prevent it in Postgres." Answer as you would out loud.
Model answer

Write skew is when two transactions read the same facts, each makes a decision from them, and each writes a different row, so together they break a rule that each one checked. The classic example is on-call doctors: the rule is at least one doctor on call; Alice and Bob each count two on call, each sets only themselves off call, both commit, and nobody is on call. Snapshot isolation, which is what Postgres REPEATABLE READ gives you, allows it, because there is no write-write conflict: they wrote different rows.

Two fixes. At READ COMMITTED, lock the matching rows in a common order, count the returned rows and update only if two remain. The second transaction then sees one doctor and refuses. At REPEATABLE READ a concurrent change can instead cause a serialization failure. Alternatively, use SERIALIZABLE for both transactions and retry the whole aborted attempt on SQLSTATE 40001. A unique or exclusion constraint is preferable when it can express the actual rule; neither directly expresses the rota's at-least-one requirement.

Design
Your meeting room booking service runs on Postgres at the default level. Two people booked room 7 for overlapping times. Explain the bug, the fix you would ship, and one alternative.
Model answer

The bug. Both transactions check before either inserts, so both see no overlap. An empty SELECT ... FOR UPDATE takes no row locks that exclude the competing inserts. This is write skew over a predicate, and it can occur even with stable snapshot reads.

The fix I would ship. Store non-null room ids and valid, nonempty, half-open tstzrange intervals. Enable btree_gist and add EXCLUDE USING gist (room_id WITH =, during WITH &&). If the competing booking commits, a conflicting insert fails with SQLSTATE 23P01, which the API maps to "that slot was just taken". The constraint covers every writer.

Alternatives. Lock a parent row that always exists, SELECT ... FROM rooms WHERE id = 7 FOR UPDATE, before the check, so bookings for one room queue up; this works at READ COMMITTED because each later statement takes a fresh snapshot, but not at REPEATABLE READ, where the snapshot predates the lock. Or run the booking at SERIALIZABLE and retry on 40001. Or pre-create one row per room per slot and claim it with a conditional update, which turns the phantom into an ordinary row conflict.

Write code
Write a helper in your language that runs a transaction body at SERIALIZABLE and retries it on SQLSTATE 40001 or 40P01, with capped exponential backoff and jitter. Then say what the body must not do.
Model answer

The body must start from scratch on every attempt, reads included, and must not cause effects outside the database (emails, payment calls, messages), because each retry would repeat them. If it needs such an effect, record the intent in the same transaction (an outbox row) and perform it afterwards, idempotently.

How a senior would say it
This is write skew: a consistent snapshot does not make a decision across rows safe. The rule is that at least one doctor stays on call. Alice and Bob each see a snapshot with two doctors. Alice changes only Alice's row, and Bob changes only Bob's row. Both changes can commit under Postgres repeatable read because they do not write the same row. The result is zero doctors, which no valid serial execution of those decisions would produce. One fix is to use read committed, lock all the shift's on-call rows in a consistent order, and count the rows actually returned before deciding. The second request then sees only one doctor and refuses to leave. The check and write must remain in the same transaction, and every relevant writer must follow that protocol. Alternatively, I would run both transactions at serializable and retry an aborted attempt from the beginning, including its reads. I would keep external side effects out of that retry loop. The choice depends on contention and how easily we can identify the complete set of dependencies.

Out loudabout 75 s
"We added FOR UPDATE to our availability check, but rooms still get double booked. What would you inspect and change?"
What a strong answer covers
  • Check the isolation level, transaction boundaries and whether the query returned any rows
  • Explain that an empty PostgreSQL locking read cannot exclude competing booking inserts
  • Distinguish write skew over a predicate from observing a phantom on a repeated query
  • Use an exclusion constraint with non-null room ids and valid half-open ranges
  • Offer a parent-row lock followed by a separate fresh check at READ COMMITTED, or SERIALIZABLE with retries
How a senior would say it
I would first check what was actually locked. At Postgres read committed, if both availability queries find no overlapping booking, neither locks a booking row that can exclude the other insert. Both requests can then commit. That is write skew over an absence predicate; neither request needs to repeat its query and observe a phantom. I would inspect the transaction boundaries too, because a lock released by autocommit cannot protect a later insert. For arbitrary time intervals, I would enforce the rule with an exclusion constraint on room equality and interval overlap. Room ids and ranges must be non-null, and valid half-open intervals let one booking end exactly when another begins. A conflicting insert becomes a clear booking conflict. An alternative is to lock an existing room row, then run a separate availability query at read committed before inserting. Every booking writer must cooperate. I would not assume that waiting for that parent lock refreshes a repeatable-read snapshot. Serializable with whole-transaction retries is another option when the invariant cannot conveniently be expressed as a constraint.
