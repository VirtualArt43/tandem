Under the hood: how std::thread maps to the OS

How C++ threads map to pthreads, where Linux and macOS differ, and how to implement safe waits and shutdown in C.

Asked atNvidia
Before this:Classes, constructors, destructors and RAIIBuilding, debugging and sanitizers

std::thread is a thin C++ coat over the operating system's threads. Knowing the layer underneath explains the frames in every stack trace and the costs of every primitive, and it lets you write a correct producer and consumer in plain C when an interviewer takes the C++ library away.

In plain words

Think of a car with an automatic gearbox and the same car with a manual one. The engine is identical. The automatic picks gears for you and never lets you forget the clutch; the manual makes you do every step yourself, in the right order, every time.

C++'s thread library offers automatic help: named guards release their locks, predicate waits re-check their condition, and std::jthread joins on destruction. You still have to choose those tools correctly; std::thread does not automatically join. POSIX threads is the manual: you initialize, lock, check in a loop, unlock, destroy and handle errors yourself. Same engine, more ways to stall.

Why this matters for concurrency

  • Some rounds are C only. Reports from Nvidia system software interviews in India describe rounds that allowed only C, and an Nvidia SDE-2 report asked for a C program in which one thread prints even numbers and another prints odd numbers, in order, with mutexes and condition variables. You must be able to write that with pthread_create, pthread_mutex_t and pthread_cond_t from memory.
  • Stack traces speak pthreads. ThreadSanitizer says a thread was "created by main thread at pthread_create"; a hung process shows __psynch_mutexwait or a futex wait. Reading those frames needs this map.
  • Costs come from the OS. Each pthread corresponds to a kernel thread and has its own stack. Ordinary mutexes usually acquire in user space when free; contention may require spinning or kernel-assisted blocking.
  • Platforms differ. macOS has no unnamed POSIX semaphores, no pthread_barrier_t and no pthread_mutex_timedlock. Code that compiles on your Mac can fail at run time, and code from a Linux interview may not compile on your Mac at all.

The map: C++ types to OS objects

The usual libstdc++ and libc++ builds on Linux, and Apple's libc++ on macOS, use POSIX threads. This is an implementation map, not a C++ standard requirement. Details below describe those backends, including the libc++ shipped with this Mac's Apple clang 17:

What a thread is, on Linux and macOS

On Linux, glibc's pthread_create obtains a stack, sets up thread-local storage and creates a kernel task through clone or clone3, depending on the runtime and kernel. Flags such as CLONE_VM, CLONE_FILES, CLONE_SIGHAND and CLONE_THREAD arrange the sharing. Each task is independently scheduled: this is the 1:1 kernel thread model. macOS uses different kernel interfaces with the same 1:1 result.

Stack sizes are defaults, not language guarantees. On macOS inspect the actual size with pthread_get_stacksize_np(pthread_self()) instead of assuming a fixed value. On Linux with glibc, the finite stack resource limit at program startup sets the usual default, commonly 8 MiB; an unlimited limit instead selects an architecture-specific default. Stack address space is reserved, with physical backing generally acquired as pages are touched. pthread_attr_setstacksize changes the requested size for a thread you create with those attributes.

Locks: user space first, the kernel only when needed

An ordinary mutex usually has a user-space fast path using atomic operations; it is not guaranteed to be exactly one compare-and-swap. Contention may first cause spinning and then kernel-assisted parking: a futex on Linux, or macOS mechanisms such as psynch and ulock. Unlock may need a kernel wakeup when waiters exist. Special mutex protocols can take different paths.

As rough orders of magnitude, an uncontended lock/unlock pair can cost tens of nanoseconds, while blocking and rescheduling can cost microseconds or more. These are not measured results or bounds for your machine. Scheduling, cache traffic and the critical section determine the actual cost; how locks are built explains the context switch and contention trade-offs.

Reaching the pthread from C++

On these pthread backends, std::thread::native_handle() exposes a pthread_t. Its type and operations are implementation-defined. Linux offers pthread_setname_np(handle, "worker"), with at most 15 name bytes plus the terminator, and affinity APIs; macOS's pthread_setname_np("worker") names only the calling thread and does not need a handle. Linux-style core pinning is not a portable pthread facility.

Keep lifecycle ownership in C++. Do not call pthread_join or pthread_detach on a std::thread handle: the C++ object would still believe it is joinable. Do not retain a handle beyond its valid thread lifetime. For native scheduling changes, check return codes and permissions; for identity, treat pthread_t as opaque and compare with pthread_equal, not a numeric OS thread id.

Threads in C: create, pass data, join

pthread_create takes a function that receives and returns void*. You pass data in through that pointer, usually a pointer to a struct that you keep alive until the thread is joined, and you get results out through the same struct.

The C examples below use a small check helper: an unexpected pthread error prints the returned error number and terminates the process. This is an explicit demonstration policy, not recoverable library error handling. A reusable component must unwind partial startup: stop and wake already-created workers, join only successful creations, then destroy initialized resources. No example uses pthread_cancel.

The samples in this lesson are written in C, in a style that is also valid C++, because Tandem's Run button compiles C++; saved as a .c file they build with cc -std=c11 -Wall -pthread. Three C habits matter here:

  • Return codes, not errno. The pthread operations used here, such as create, join, lock and wait, return 0 or an error number such as EAGAIN. Diagnose that return value with strerror(rc), not errno. Some other pthread APIs return values instead, such as pthread_self and pthread_equal.
  • Give each thread its own argument. Passing &i, the loop variable, hands every thread a pointer to the same changing integer: they read whatever value it holds when they get around to it, and the read races with the loop's writes. Use an array with one element per thread, as above.
  • Join or detach every thread. A thread that finishes but is never joined keeps its resources until someone does, much like a zombie process. There is no destructor to remind you.

Mutexes and condition variables in C

A pthread_mutex_t can be initialized statically with PTHREAD_MUTEX_INITIALIZER, or with pthread_mutex_init(&m, NULL) and later pthread_mutex_destroy(&m). With no RAII, every path out of a critical section must call pthread_mutex_unlock, including every early return and error path; C code usually funnels them through one exit at the end of the function. For debugging, a mutex of type PTHREAD_MUTEX_ERRORCHECK (set with pthread_mutexattr_settype) returns EDEADLK if a thread locks it twice and EPERM if a thread unlocks a mutex it does not own, where a default mutex would hang or misbehave.

A pthread_cond_t is the condition variable itself. Its contract is the same as in C++:

  • pthread_cond_wait(&cond, &mutex) requires ownership of the mutex. It atomically releases it and begins waiting relative to another thread acquiring that mutex and signalling. A successful return holds the mutex again. Use the same mutex for concurrent waits on a given condition variable.
  • It may return without a signal (a spurious wakeup), and another thread may have changed the state before you got the mutex back. So the wait is always written while (!condition) pthread_cond_wait(&cond, &mutex);. With no predicate overload in C, the while is entirely your job.
  • When waiters exist, pthread_cond_signal unblocks at least one, and pthread_cond_broadcast unblocks all. Neither immediately hands over the mutex. A signal with no thread waiting does nothing and is not remembered, which is why the waiter must check the state, not wait for the signal.
  • Change the state and signal while holding the mutex. Signaling just after unlocking is also legal, but holding it is the version that is easy to prove correct.

Producer and consumer in raw pthreads

Here is the bounded buffer from producer and consumer, written the way a C-only round expects: a ring buffer of capacity 4, two producers, two consumers, one mutex, and two condition variables. The consumers stop when the buffer is empty and every producer has finished.

Walk through it the way you would in the interview:

  • The invariant. 0 <= count <= CAPACITY, and head, tail and count describe exactly the occupied slots. One mutex guards all of them, because they change together.
  • Two conditions. Producers wait on notFull, consumers on notEmpty, so each pthread_cond_signal reaches a thread of the kind that can use it. With one shared condition you would need broadcast to avoid waking the wrong kind of thread and losing the signal.
  • The end condition is part of the wait. Consumers wait while "empty and producers remain". The last producer broadcasts, because every consumer must wake and see that it is over; a single signal would leave the others asleep forever.
  • Per-thread results need no lock. Each consumer writes only its own results[i], and main reads it only after pthread_join, which guarantees the writes are visible.

Compare it with the C++ version: std::unique_lock replaces every pthread_mutex_unlock, the predicate overload of wait replaces each while, and std::thread checks its argument types at compile time instead of passing void*. The design is identical. The C version only removes the guard rails.

Timed waits in C

pthread_cond_timedwait(&cond, &mutex, &deadline) takes an absolute struct timespec deadline, not a duration. The default clock is CLOCK_REALTIME; wall-clock changes can distort a timeout. On Linux, initialize condition attributes, set CLOCK_MONOTONIC with pthread_condattr_setclock, initialize the condition variable using those attributes, then destroy the attributes. Compute the deadline from that same clock and keep tv_nsec in the range 0 to 999999999.

Keep one total time budget. Reuse the absolute deadline after wakeups. On ETIMEDOUT the mutex has been reacquired: check the predicate once more under the lock, since state change can race the timeout. Other unexpected errors need handling, not a retry loop. macOS lacks pthread_condattr_setclock and offers pthread_cond_timedwait_relative_np instead; compute one monotonic deadline and pass only the remaining duration on each retry. Passing the original relative duration repeatedly can extend the wait forever. See clocks and deadlines.

Semaphores, and the macOS gap

POSIX has two kinds of semaphore. Unnamed ones live in your memory: sem_init, sem_wait, sem_post, sem_destroy. Named ones are system-wide objects: sem_open, sem_close, sem_unlink. Linux supports both. macOS does not implement unnamed semaphores: sem_init is marked deprecated, and on this Mac it returns -1 with errno set to ENOSYS ("Function not implemented").

The code compiles with a deprecation warning, but failed initialization leaves no valid semaphore. Do not call sem_wait or sem_post on it: using an uninitialized semaphore has undefined behaviour, not a guaranteed harmless failure. Nvidia's reported "print 1 to N with N threads using semaphores" is one reason to know the platform distinction. Your options on a Mac:

  • Build a counting semaphore from a mutex and a condition variable (the checkpoint below). It is portable, and writing it is itself a common question.
  • Use a named semaphore with sem_open and sem_unlink. It works, but it is a system-wide object that can outlive a crashed process.
  • Use Grand Central Dispatch's dispatch_semaphore_t (Apple only), or C++20's std::counting_semaphore when C++ is allowed.

POSIX semaphore operations use a different error convention from pthread operations: for example, sem_wait returns -1 and sets errno on failure. Retry EINTR only if your cancellation policy says to continue; handle other errors. A successful sem_open result is closed with sem_close, not sem_destroy. Arrange sem_unlink for the name's lifetime as well.

Two more POSIX pieces are missing on macOS: pthread_barrier_t and pthread_mutex_timedlock. If an interviewer's Linux code uses them, know that they exist and what they do, even if you practice without them.

Worked example: the even and odd printer in C

The task, as reported from an Nvidia interview: one thread prints the odd numbers and another the even numbers, and together they print 1 to N in order. In C, with pthreads only.

The design in one sentence: a shared next number guarded by a mutex, and each thread waits on a condition variable while it is not its turn, where "my turn" means next % 2 == myParity.

Points the interviewer will probe. The wait condition includes next <= LIMIT, so the thread that is not printing the last number also wakes and exits; without it, one thread would sleep forever and pthread_join would hang. signal is enough because exactly one other thread can be waiting. With N threads taking turns (the round-robin version), several threads wait on one condition, each for a different turn, so you must broadcast or give each thread its own condition variable; a single signal could wake a thread whose turn it is not, and the right thread would never be woken. The printf runs under the lock, which is what keeps the output in order.

Common mistakes

  • if instead of while around pthread_cond_wait. Spurious and stolen wakeups make the thread proceed when its condition is false.
  • Reading errno after a pthread call. pthread functions return the error number. Check the return value.
  • Passing &i from a loop to pthread_create. Every thread sees the same, changing variable. Give each thread its own argument.
  • A missing unlock on an early return. There are no guards in C: one forgotten path leaves the mutex locked forever.
  • Signaling without changing the state under the mutex. The waiter can check the old state, then sleep through your signal: a lost wakeup.
  • A relative time in pthread_cond_timedwait. It wants an absolute deadline; passing "100 ms" means a time in 1970, which has already passed, so it returns at once.
  • sem_init on macOS without checking the result. It returns -1 with ENOSYS. Stop there: subsequent operations on the uninitialized object are invalid.
  • Destroying a mutex or condition variable while a thread still uses it. Join first, then destroy.

In the interview

In a C-only round, say the design before typing, then write it in the order the invariant needs: state and its mutex, the conditions, then each function as lock, wait in a loop, change state, signal, unlock. State your error policy, check return codes, and join every successfully created joinable worker.

I'll keep the shared state in one struct guarded by one pthread_mutex_t, with two condition variables, not full and not empty. Each function locks, waits in a while loop on its condition because wakeups can be spurious, changes the state, signals the other side while still holding the mutex, and unlocks. The last producer broadcasts so every consumer can see that the stream has ended.

Follow ups to expect:

  • "Why does pthread_cond_wait take the mutex?" Because releasing the mutex and going to sleep must be one atomic step; otherwise a signal sent between your check and your sleep is lost.
  • "signal or broadcast?" Signal when every waiter is interchangeable and one change helps one waiter; broadcast when waiters wait for different things, or when a change (like "finished") concerns all of them.
  • "What is the difference between a mutex and a binary semaphore?" A mutex has an owner: the thread that locked it must unlock it. A binary semaphore has no owner: a different thread may post it, allowing a signal between threads. You can also use a semaphore for exclusion, but callers must enforce the one-permit protocol themselves.
  • "How is std::thread implemented on Linux?" Usually through pthread_create; glibc obtains a stack and uses clone or clone3 with sharing flags. The kernel schedules each thread independently.
  • "What happens if main returns while other threads are still running?" In a C program it terminates the process, including the workers. pthread_exit(NULL) ends only the calling thread, but its stack locals must no longer be used by others. Joining is the clearer lifetime contract. In C++, destruction of an unjoined, joinable std::thread first calls std::terminate; std::jthread instead requests stop and joins.

Senior depth

Creation and join are synchronization boundaries. Initialize arguments before creating the worker: it may run before pthread_create returns. Read its result only after a successful join, and never return a pointer to the worker's own stack. Detaching releases thread resources when it ends; it neither extends argument lifetimes nor waits for completion.

Cancellation needs cleanup. A POSIX condition wait is a cancellation point. Deferred cancellation reacquires its mutex before running cleanup handlers, so a raw C implementation using pthread_cancel needs pthread_cleanup_push and pthread_cleanup_pop to release it. Prefer a guarded stop flag plus broadcast for these examples. A C++ stop token is cooperative and does not invoke POSIX cancellation.

Mutual exclusion does not promise fairness. Neither the default mutex nor signalling this condition variable guarantees FIFO waiter selection. The bounded buffer preserves item order, but cannot promise a particular waiting producer runs next.

Key takeaways

  • The usual Linux and macOS C++ libraries wrap pthread threads, mutexes and condition variables; that backend is not mandated by C++.
  • Ordinary mutexes usually acquire in user space; contention can add spinning, kernel calls and scheduling delay.
  • In C, every guarantee is manual: unlock on every path, wait in a while, check return codes, join every thread.
  • pthread_cond_wait releases the mutex and sleeps atomically; signals are not remembered, so waiters check state.
  • macOS lacks unnamed POSIX semaphores (sem_init returns -1 with errno == ENOSYS), pthread_barrier_t, pthread_mutex_timedlock and pthread_condattr_setclock.

Quick check

Answer each question, then read why. Your score is saved for your module test.

int rc = pthread_create(&t, NULL, work, NULL); fails. Where is the reason?
Why. pthread_create reports an error number directly, such as EAGAIN when resources are insufficient. Print it with strerror(rc); errno does not report this failure. No worker was created, and the output thread identifier is not valid for a join, so there is no worker return value to inspect.
What is wrong with this consumer?
Why. Waking up means "check again", never "go ahead". POSIX allows spurious wakeups, and another consumer can take the item before this one regains the mutex. signal does not prevent either case. The wait requires ownership of the mutex, and the subsequent shared-buffer access must stay protected by it.
What can this print?
Why. All workers receive the same address while the loop writes through it without synchronization. That is a data race and undefined behaviour in C11 and C++20, so even a range of 0 to 4 is not guaranteed. The loop-local i is also dead before the joins, allowing a dangling access. Keep separate arguments alive through successful joins. The pointer conversion is legal; it provides no synchronization.
On macOS, sem_t s; sem_init(&s, 0, 1); compiles with a deprecation warning. What happens at run time?
Why. macOS's sem_init reports "Function not implemented"; it neither crashes as its specified failure path nor creates a named object. Using s after that failure has undefined behaviour. Use a mutex and condition variable semaphore, sem_open, dispatch_semaphore_t, or std::counting_semaphore instead.
A thread signals an initialized condition variable c when it has no waiters. Later another thread calls pthread_cond_wait(&c, &m) while owning the valid mutex m. What does the earlier signal guarantee?
Why. A signal stores no permit. The later wait can block indefinitely without another notification, but spurious wakeups are also allowed. With valid arguments, an earlier signal is not an EINVAL error or a cause for the signalling thread to deadlock. Check shared state under the mutex before waiting; if the predicate already holds, skip the wait.
Which std::condition_variable call corresponds to pthread_cond_broadcast?
Why. On the pthread backend, notify_all maps to pthread_cond_broadcast and notify_one to pthread_cond_signal. wait blocks rather than notifying, while wait_for is a timed wait. All woken threads still reacquire their mutex and recheck the predicate.
What is the essential difference between a mutex and a binary semaphore?
Why. A mutex must be unlocked by its owner. A semaphore can transfer a permit between threads, or implement exclusion if callers obey a protocol; ownership is not enforced. There is no universal speed ranking. POSIX supports process-shared forms of both where the implementation supplies them; this is not a promise that every such form exists on macOS. A POSIX semaphore initialized to 1 also does not prevent erroneous extra posts from increasing its count above 1.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
sem_init is unavailable on macOS. Write a process-local counting semaphore in C with semInit, semWait, semPost and semDestroy. Reject a negative initial count and report overflow from semPost. Assume cooperative shutdown, with no POSIX cancellation.
Model answer

The count remembers permits, including posts before a wait. Each successful post adds one permit, so signalling one interchangeable waiter is enough; every waiter still loops. Initialization rolls back its mutex if condition initialization fails. Destroy only after every user has finished, and never copy the initialized struct. Unlike POSIX sem_post, this mutex-based semPost is not async-signal-safe, and it provides neither process sharing nor FIFO admission.

Explain
Explain what happens inside pthread_cond_wait(&c, &m), and why it needs the mutex as an argument.
Model answer

The caller must hold m. The call atomically releases m and puts the thread to sleep on c; when the thread is woken, by a signal, a broadcast or spuriously, it locks m again before returning, so it always returns holding the mutex. The atomic release is the whole point. The waiter checked the shared state under m and found it not ready. If it released m and only then started sleeping, a producer could change the state and signal in that gap, the signal would find no waiter and vanish, and the waiter would then sleep forever: a lost wakeup. Because unlocking and sleeping are one step relative to anyone who signals under m, that gap does not exist. Since the thread may wake without its condition being true, and another thread may get the mutex first, the call always sits in a while loop that re-checks the condition.

Explain
An interviewer asks: "What does std::thread actually do on Linux, and what does a thread cost?" Answer in under a minute.
Model answer

In the usual Linux builds, std::thread uses pthread_create. Glibc obtains a stack, prepares thread-local storage and creates a kernel task through clone or clone3. Threads share the process address space but are scheduled independently. Creation costs allocation, kernel bookkeeping and scheduling work; the actual time depends on the system. The default stack often follows the finite resource limit at program startup, commonly 8 MiB of virtual space, with physical backing acquired as pages are touched. Each thread also adds scheduling and cache costs. Pools amortize creation across many tasks. The C++ standard specifies synchronization and lifecycle behaviour, not this OS implementation or its timing.

"Walk me through what happens underneath std::thread on Linux. Which parts would you rely on in portable C++?"
What a strong answer covers
  • Usual Linux C++ libraries use pthread_create; this is an implementation choice
  • The runtime obtains a stack, prepares thread-local storage and creates a kernel task
  • Linux uses clone or clone3 with sharing flags; each thread is independently scheduled
  • Creation, stacks and scheduling have costs; defaults and timings are platform-dependent
  • Portable reasoning uses lifecycle and synchronization guarantees, including successful join
  • Native handles are platform-specific and must not bypass the C++ object's lifecycle ownership
How a senior would say it
On a typical Linux system, a C++ thread is backed by a pthread and an independently scheduled kernel task. That is an implementation choice, not a requirement that portable C++ exposes. The library stores the callable and its arguments, then uses pthread creation. Glibc obtains a stack, prepares thread-local storage and creates the task through clone or clone3, with flags that share the process's address space and other resources. Each thread still has its own execution state and stack. Those resources, creation work and scheduling costs explain why a pool can be useful for many small tasks. Stack defaults and timings depend on the system, so I would measure rather than promise a fixed cost. In portable code, I rely on the documented lifetime and synchronization contracts: keep captured objects alive and join before consuming a worker's result. A native handle is only for platform-specific operations. I would not join it through pthreads, because the C++ object would still think it owns a joinable thread. On Windows the implementation changes, while those C++ guarantees remain.

Likely follow up: How would you change a worker's stack size, and can std::thread do that portably?

Out loudabout 75 s
"My pthread consumer occasionally hangs during shutdown. Walk me through the predicate and wakeups you would check."
What a strong answer covers
  • Check queue contents and producer-completion state under the same mutex
  • Wait while empty and producers remain, using a while loop
  • Condition wait atomically releases the mutex and starts waiting, then reacquires it
  • The last producer broadcasts so all consumers can observe completion
  • Drain existing items, exit only when empty and finished, then join before destruction
  • Signals are not stored permits and wakeups do not imply the predicate is true
How a senior would say it
I would first check whether shutdown is part of the state that the consumer waits on. For this buffer, queue contents and the number of remaining producers belong under the same mutex. A consumer waits only while the buffer is empty and at least one producer remains. The wait goes in a while loop because a wakeup does not reserve an item, and it can be spurious. The condition wait atomically releases the mutex and starts waiting, then reacquires the mutex before the successful return. That closes the gap in which a producer could otherwise change the state and send a missed signal. When the final producer finishes, it decrements the producer count under the mutex and broadcasts to all consumers. Signalling only one can leave the others asleep forever. Each consumer drains any remaining item and exits only when the buffer is both empty and finished. Then the owner joins every thread before destroying the synchronization objects. I would test both an empty shutdown and a shutdown with queued items. The shared state remembers completion; notifications alone do not.

Likely follow up: What would change if you also wanted to cancel producers blocked on a full buffer?
