Templates, auto and type deduction

Function and class templates, auto and decltype, how deduction works and how to read template errors, aimed at one generic blocking queue.

Before this:Classes, constructors, destructors and RAIICopy, move and move-only typesLambdas, captures and callables

Every thread-safe component you build in an interview holds something: a queue of tasks, a cache of values, a future of a result. Templates let you write it once for every element type, and auto keeps the code short enough to finish in the time you have.

In plain words

A kulfi seller fills the same set of molds with mango mix in the morning and pista mix in the afternoon. The mold fixes the shape; the mix decides the flavor. Every kulfi that comes out is complete and separate, and all of them came from one design.

A template is that mold for code: "a queue of something". When you write BlockingQueue<std::string>, the compiler pours std::string into the blank and builds a complete, ordinary class from the design. auto works the other way round: when the type is obvious from the right-hand side, you let the compiler write it in for you.

Why this matters for concurrency

  • Your components are generic. Interviewers often start with "a blocking queue of ints" and then say "make it work for any type". With templates that is a two minute change, if you know which ints to replace and which to keep.
  • The concurrency library is made of templates. std::lock_guard, std::unique_lock, std::atomic, std::future and std::scoped_lock are class templates. The predicate overload of std::condition_variable::wait is a function template. So the error messages you get when you misuse them are template errors.
  • std::thread deduces and stores its arguments by value. That one rule explains the most common compile error in threaded C++, and why std::ref exists.
  • auto can hand you a reference into shared state. auto& can bind a reference to an element of a guarded container; that reference can outlive the lock. Knowing exactly what auto deduces is how you keep shared data inside the critical section.

Function templates: one definition, many functions

A function template is a function with a type left blank. You name the blank with a template parameter, usually T, and use it like any other type.

At a call, the compiler checks which specialization is needed. The compiler deduces T from the arguments: 3 and 7 are both int, so T is int. It instantiates the needed specialization, such as maxOf<int>. Repeated calls with the same type reuse that specialization; there is no runtime code generation. When deduction cannot work, or you want a different type, you name T yourself, as in maxOf<double>(2, 2.5).

Syntax and names that do not depend on a template parameter are checked at definition time. Requirements that depend on T are checked when the relevant specialization is instantiated. maxOf copies its arguments and needs operator<, and a std::mutex has neither a copy constructor nor operator<, so trying maxOf(mutexA, mutexB) fails. Deduction also refuses to guess: in maxOf(1, 2.5) the first argument says int and the second says double, and clang reports "candidate template ignored: deduced conflicting types for parameter 'T' ('int' vs. 'double')".

Class templates: a container of anything

typename and class are interchangeable when declaring a type parameter. Templates can also take compile-time values: std::array<int, 16> fixes its length through a non-type parameter, unlike a vector's runtime size. A different length produces a different array type.

A class template puts template <typename T> in front of a class, and inside the class T is the element type. Notice what did not become T: the mutex, the condition variable, and anything that counts. Only the element type is generic.

auto: let the compiler write the type

auto asks the compiler to deduce a variable's type from its initializer. It follows the same rules as a template parameter taken by value, which leaves one rule to remember: plain auto makes a new object, dropping references and top-level const. To refer to an existing object you must say auto& or const auto&.

A new object is not necessarily an independent value. auto p = pointer copies an address, auto view = stringView copies a view, and auto bit = flags[0] on std::vector<bool> copies a proxy that still refers to a bit. For a real boolean snapshot use bool bit = flags[0]; while holding the required lock. With const int* const p, auto q = p keeps the pointed-to const int and drops only the pointer's top-level const.

For brace initialization, auto x{1} is int, auto x = {1} is std::initializer_list<int>, and auto x{1, 2} is ill-formed. Include <initializer_list> when using that type. By-value deduction also turns arrays and functions into pointers; auto& preserves an array's extent.

For an ordinary string, plain auto gives a value while auto& gives an alias. The copy must still happen under the lock. Look at this getter:

A caller writes const auto& e = dir.emailOf(7); and reads e a moment later, with no lock held. If another thread runs update(7, ...) at the same time, the read and the write touch the same string with nothing ordering them. Changing the caller to auto e = dir.emailOf(7); does not fix it either: that copy would happen after the getter releases its lock. That is a data race, and in C++ a data race is undefined behavior. The fix is to return std::string by value, so the copy is made while the lock is still held.

decltype and deduced return types

decltype(expr) gives you the type of an expression without evaluating it. You will rarely write it by hand in an interview, but you will meet it in generic code that has to name a type it cannot spell, and in its relative decltype(auto).

Functions can deduce their return type too. Here is a wrapper worth knowing for senior rounds: Guarded<T> keeps a value and its mutex together, and exposes a callback that runs under the lock. This requires trusted callbacks that do not retain aliases to the data.

with is a member function template inside a class template. Here T must support the value_{} initialization. Its auto return type is deduced from return f(value_);: void for the first lambda, int for the second. The lambdas take auto& m, which makes them generic lambdas; each is a small template whose parameter type is deduced when with calls it.

Plain auto as a return type decays, so even if f returns a reference, with returns a copy. If you declared decltype(auto) with(F f) instead, the return type would keep the reference, and a caller could carry a reference to the guarded map out past the lock. Plain auto avoids this particular reference leak, but does not enforce ownership: a callback can return a pointer, iterator, proxy or std::string_view, or store an alias elsewhere. Require an owning result and no escaped aliases. Callbacks must also avoid reentering the same non-recursive mutex or doing unbounded work while holding it.

The parentheses trap in decltype

For an unparenthesized ordinary variable name or member access, decltype gives the named entity's declared type. For other expressions, an lvalue gives T&, an xvalue gives T&&, and a prvalue gives T. Thus for int x = 7, decltype(x) is int but decltype((x)) is int&. decltype(auto) applies exactly these rules to its initializer or return expression.

This prints 7 9 0 1. A function with decltype(auto) that returns (local) would return a dangling reference when local dies. Prefer explicit owning return types at synchronization boundaries. C++17 structured bindings follow the same ownership question: auto [key, value] = *it copies the pair, while auto& [key, value] = *it aliases its elements.

How deduction works: the rules you need

Template argument deduction matches the parameter's declared form against the argument. Three forms cover nearly everything you will write:

auto uses the by-value row, which is why it drops top-level const and references. A deduced T&& is a forwarding reference only when T is an unqualified function template parameter deduced by that call. const T&& and a class template's already-fixed T&& are ordinary rvalue references. Reference collapsing gives T& if either reference is &; only && combined with && stays &&.

A named parameter is always an lvalue expression, even if its type is T&&. Use std::forward<T>(x) to preserve the caller's value category; std::move(x) unconditionally casts to an rvalue and could move from a caller's lvalue. Include <utility> for both.

Since C++17, class templates can deduce too. This is class template argument deduction: std::lock_guard lock(m_); deduces std::lock_guard<std::mutex> from its argument, and std::scoped_lock lock(a, b); deduces two mutex types at once. In C++14 you spell the argument, std::lock_guard<std::mutex> lock(m_);, and many interviewers still write it that way, so be fluent in both.

The rule behind the most common std::thread compile error

std::thread's constructor is a variadic template: template <class F, class... Args> explicit thread(F&& f, Args&&... args). It deduces each argument, creates an owned value of each decayed type in the calling thread, copying lvalues and moving rvalues when supported. The new thread invokes the stored callable with the stored arguments as rvalues. std::ref(data) wraps the reference in a std::reference_wrapper. The wrapper is what gets copied, and it converts back to std::vector<int>& at the call. A lambda that captures by reference does the same job and reads better. Both put the same duty on you: the vector must stay alive until the thread has been joined.

Decay has a second, quieter trap. With void log(const std::string& msg) and a local char buf[64], std::thread t(log, buf); compiles, but what gets copied is the decayed char*, not a string. The conversion to std::string happens later, inside the new thread, and if the thread outlives that buffer, for example after its thread object was moved to a longer-lived owner, buf is gone. The buffer must also be null-terminated and not concurrently modified. Convert in the caller instead: std::thread t(log, std::string(buf));.

Reading a template error message

When a template goes wrong, the compiler reports the place where it finally failed, which is usually deep inside a standard header. The real cause is a line in your file. Read it in this order:

  1. Find your own file. Look for the note that names it: clang says "in instantiation of ... requested here", GCC says "required from here". main.cpp:13 is the call that went wrong.
  2. Read what was deduced. std::thread::thread<void (&)(std::vector<int> &, int), std::vector<int> &, int, 0> shows F and each argument type. The note above it is even more telling: the tuple the thread stores holds std::vector<int>, a copy, not std::vector<int> &.
  3. Then read the first error. "attempt to use a deleted function" means some call or copy was impossible. Here the stored copy cannot be passed to a non-const reference parameter.
  4. Skip the plumbing. Names that start with two underscores, such as __thread_proxy and __invoke, are the library's internals, not your problem.

GCC commonly reports "static assertion failed: std::thread arguments must be invocable after conversion to rvalues". Learn to read both, because you do not choose the interviewer's compiler.

C++20 constraints let a template state its requirements at its declaration. A named concept is a reusable boolean constraint; a requires expression can test whether operations are valid. C++17 code can use the earlier static_assert for diagnostics, or std::enable_if_t when invalid types must be removed from overload resolution. Templates live in headers

The compiler can only instantiate BlockingQueue<int>::push if it can see the body of push in the file that uses it. Declare the class in queue.hpp, define the members in queue.cpp, and use BlockingQueue<int> in main.cpp: both files compile, because main.cpp sees the declarations and queue.cpp never asks for int. On Linux the message says "undefined reference" to the same two functions. The fix is to define template members in the header, inside the class or below it. Identical template definitions can appear in several translation units under the one-definition rule; implementations commonly merge duplicate generated code. Alternatively, put definitions in queue.cpp and explicitly instantiate the supported types there with template class BlockingQueue<int>;. That supports only the types you list, not arbitrary caller-chosen types. It is also why every C++ problem on Tandem puts your class in solution.hpp, which the test harness includes.

One more check before you say "done": the assertion makes moves and destruction nonthrowing. Without it, a failed move from the front could leave that entry modified, or a failed move of the local return value after pop_front() could lose an item. Named return value optimization is optional. Separating access from removal, as std::queue does with front() and pop(), lets callers choose how to handle extraction. Insertion can still fail on allocation; the catch above wakes another producer because the free slot remains available. The full story is in exceptions and exception safety.

Common mistakes

  • Template members defined in a .cpp file. Every file compiles, then the link fails with undefined symbols. Define them in the header.
  • Turning every int into T. Capacity, size and indexes are counts. Only elements become T.
  • auto& into a guarded container, used after the lock is released. The reference outlives the critical section. Copy the value out while you hold the lock.
  • Returning const T& from a locked getter. Same bug, built into the API. Return by value.
  • Passing a reference parameter straight to std::thread. The thread stores decayed argument values, copying lvalues or moving rvalues. Use std::ref or a lambda capture, and join before the object dies.
  • auto snapshot = hits; on a std::atomic<int>. That asks for a copy of the atomic, which is deleted. hits.load() gives you the int.
  • std::deque<T>::iterator it = items_.begin(); inside a template. In this local declaration, a dependent type needs typename to disambiguate it. C++20 permits omission in some contexts that can only name a type. auto it = items_.begin(); avoids the question entirely.

In the interview

Templates are rarely the question; they are the vehicle. You will hear "make it generic", "why doesn't this compile?" about a std::thread and a reference, "what does auto deduce here?", or "why does std::stack::pop return void?". The interviewer is checking that the language never slows down the concurrency discussion.

I'll make the queue a class template over the element type only. push takes T by value and moves it in, so copies, temporaries and move-only types like unique_ptr all work. pop moves the front element out before removing it. Capacity and size stay plain integers.
std::thread stores decayed argument values and passes them as rvalues, so a non-const reference parameter can't bind. I'd pass std::ref(v) or capture it by reference in a lambda, and I'd join before v goes out of scope.

Follow ups to expect: "Can pop return by value safely?" (yes, when moving T cannot throw), "How would you add emplace?" (a variadic template with perfect forwarding, below), and "Where does the code for BlockingQueue<int> live?" (definitions normally in the header, with needed specializations instantiated by the compiler; explicit instantiation is another option).

Senior depth

emplace and the length of the critical section. template <typename... Args> void emplace(Args&&... args) takes forwarding references and passes them on with items_.emplace_back(std::forward<Args>(args)...), so the element is built directly inside the deque. That also means its constructor runs while you hold the lock. For a cheap T that is fine; for an expensive one, build it outside and push(std::move(x)), so the critical section pays only for insertion and the move, which is cheap for pointer-owning types but not necessarily for every T.

Templates at the edge, type erasure inside. A thread pool's queue cannot be BlockingQueue<F> for each lambda type F, because each distinct lambda expression has its own closure type. So pools take a template at the API (template <typename F> auto submit(F f)) and store a type-erased std::function<void()> or a move-only task wrapper inside. C++20 std::function requires a copyable target, so a lambda owning a unique_ptr cannot go straight into it; use a custom move-only wrapper or deliberately introduce shared ownership. std::move_only_function is C++23, not C++20. Templates can enable inlining; type erasure gives one queue for every kind of task.

What a template costs. Each distinct T can generate different code, so many instantiations can increase binary size and build time. Inlining, dead-code elimination and identical-code folding can reduce the final size. It rarely matters in an interview, but it is the honest answer when someone asks.

Key takeaways

  • A template is a recipe. The compiler instantiates a real function or class for each set of types you use, and checks type-dependent operations when their specializations are instantiated.
  • Make only the element type generic. Take elements by value and move them in; move them out before removing them.
  • Plain auto creates a value, which may itself be a pointer or proxy; auto& refers. Copy guarded data out under the lock, and never let a reference escape it.
  • std::thread stores decayed copies of its arguments: use std::ref or a lambda for references, and join before the referent dies.
  • Read template errors from your own line first, then the deduced types, then the first error.
  • Template definitions normally live in headers; explicit instantiation can support selected types from a .cpp file.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Write a generic, unbounded BlockingQueue<T> with push(T) and a blocking T pop(), requiring nonthrowing move construction and destruction, so that BlockingQueue<std::unique_ptr<Task>> compiles and works. Explain in one sentence why push takes T by value.
Model answer

Taking T by value and moving it in gives one overload that accepts copies of lvalues, temporaries and objects explicitly offered with std::move, so move-only types such as std::unique_ptr<Task> work without a second push(T&&). pop moves the front element out before pop_front(), and the asserted nonthrowing move contract prevents extraction or return from losing an item through a throwing move.

Debug
This compiles cleanly, but under load a reader now and then prints garbage. Find the bug and fix it.
Model answer

get returns a reference into the map. The lock is released when get returns, so the caller reads the string with no lock held, while set may be assigning to the same string (a rehash alone does not invalidate this reference). That read and write are a data race: undefined behavior, which shows up as garbage or a crash. Fix: return std::string by value, so the copy is made inside the critical section.

The fix also stops using operator[] in a getter: values_[key] inserts an empty entry for a missing key, which turns a read into a write.

Explain
An interviewer shows std::thread t(fill, data); where fill takes std::vector<int>&, and asks why it fails to compile and how to fix it. Answer as you would out loud.
Model answer

std::thread's constructor is a template that stores decayed argument values, copying lvalues or moving rvalues, in storage owned by the new thread, and then calls the function with those copies as rvalues. That is deliberate: the new thread must not depend on objects that may die on the caller's stack. A non-const lvalue reference cannot bind to an rvalue, so the call inside the library is ill-formed. If I really want the thread to work on the caller's vector, I say so explicitly with std::ref(data), or I write a lambda that captures data by reference. Either way I take responsibility for the lifetime: I join the thread before data goes out of scope, and if other threads touch data at the same time I protect it with a mutex.

"You made the integer blocking queue generic. Walk me through what changes, and what could still go wrong with a move-only element."
What a strong answer covers

  • Take by value and move into storage; lvalues copy and move-only arguments need ownership transfer

How a senior would say it
I would template the element type and keep capacity and size as counts. Enqueue takes the element by value and moves it into the deque. A copyable lvalue is copied into that parameter; a move-only object must be passed as a temporary or explicitly offered with a move. Dequeue waits for an item under the mutex, constructs an owning result from the front, and only then removes the front. The moved-from object still exists until removal, so moving is not the same as destroying. The difficult part is exception safety. A throwing move can modify the front before extraction succeeds, and a throwing return move after removal can lose the item. I would require nonthrowing move construction and destruction for this API, as our implementation does. Allocation can still fail during insertion; in a bounded queue I pass the wakeup to another producer because the slot remains free. The locking and predicate waits stay unchanged. Finally, I would define close separately, wake all waiters on close, and join users before destroying the queue.

Likely follow up: How would you support a type whose move constructor can throw without losing queued work?

Out loudabout 75 s
"This locked wrapper returns auto. Does that prove callers cannot escape the lock with shared data?"
What a strong answer covers
  • No: plain auto removes references but does not guarantee an owning result
  • A string returned by value is copied while the wrapper still holds its lock
  • Pointers, views and proxies copied by value still alias shared storage
  • decltype(auto) preserves a returned reference; parenthesized names can produce references
  • Require owning snapshots and trusted callbacks, with no retained aliases or reentry
How a senior would say it
No. Plain auto prevents one particular reference leak, but it does not prove ownership. Suppose the callback returns a reference to a string. The wrapper's auto return type becomes string, so the caller receives a copy constructed before the lock guard is destroyed. That is useful. But if the callback returns a pointer, a string view, or a proxy object, copying that result still leaves an alias to protected storage. The callback could also save an address somewhere else. Changing the wrapper to decltype auto makes matters sharper: it preserves the reference returned by the callback. Parentheses matter too. For an integer variable, decltype of its name gives int, while decltype of the parenthesized expression gives int reference. I would make the API promise an owning snapshot, or expose specific operations that complete under the lock. If we retain callbacks, they must be trusted not to save aliases, reenter the same mutex or block indefinitely. The synchronization boundary is the entire access to shared state, not just the lookup that found it.

Likely follow up: Would writing plain auto at the caller fix a getter that returns a reference after unlocking?

Out loudabout 75 s
"Why won't std::thread t(fill, data) compile when fill takes a vector reference, and which fix would you choose?"
What a strong answer covers
  • Thread construction stores decayed argument values in the calling thread
  • An lvalue vector is copied; the worker invokes fill with the stored argument as an rvalue
  • A non-const lvalue reference cannot bind to that rvalue
  • Use std::ref or reference capture for sharing, or move ownership into the worker
  • Sharing requires sufficient lifetime and synchronization; join orders later caller reads
How a senior would say it
The thread constructor does not automatically preserve the vector reference. It stores argument values with decayed types, copying this lvalue vector in the calling thread. The new thread then invokes the function using the stored argument as an rvalue. Fill expects a non-const lvalue reference, which cannot bind to that rvalue, so the program fails to compile. If the worker is supposed to fill the caller's vector, I would use std ref or a lambda that captures the vector by reference. The wrapper or lambda is stored by value, but it deliberately refers back to the original vector. That makes lifetime my responsibility: the vector must remain alive until the worker finishes. I also need a mutex if another thread accesses the same vector concurrently. In this example I can simply avoid touching it until join returns, which also makes the worker's writes visible. If sharing is unnecessary, I would move ownership into the worker instead and accept a vector by value. Adding move to the original reference-taking call alone would not fix its signature.
