Lambdas, functional interfaces and method references

Lambdas and the functional interfaces behind them, method references, what a lambda may capture and why, and lambdas as tasks for threads and executors.

Asked atRubrikGoogle
Before this:Genericsfinal, immutability and records

Almost every task you hand to a thread, an executor or a future in modern Java is a lambda. Knowing exactly which interface a lambda becomes, what it captures, and when and how often its body runs is the difference between a task that is correct and one that quietly shares state.

In plain words

A lambda is a sticky note with instructions: "water the plants in room 3". You hand the note to a helper (a thread), who carries it out later, maybe while you are busy with something else. The note includes the details it needs, copied down at the moment you wrote it. Java insists those copied details never change afterwards (effectively final), because the helper reads the note later and you must not be able to scribble on it in the meantime.

But if the note says "water the plants in the shared garden", every helper holding such a note works in the same garden. Copying the note never copies the garden. A lambda copies the values of local variables, never the objects they point to.

Why this matters for concurrency

  • Lambdas are how you give work to threads: new Thread(() -> ...), executor.submit(() -> ...), CompletableFuture.supplyAsync(() -> ...).
  • Lambdas are how you make updates atomic: map.computeIfAbsent(k, key -> ...), map.merge(k, 1, Integer::sum), ref.updateAndGet(v -> ...). These functions may run under a lock, or more than once, so they must be short and free of side effects.
  • The capture rules prevent races on local variables but not on fields or on captured objects. Knowing exactly what is shared is the whole game.
  • Runnable and Callable differ in results and checked exceptions, which decides how you handle InterruptedException and whether a failure is visible or silently swallowed.
  • Rubrik has asked for a non-blocking API that runs a Runnable after a delay, and for a JavaScript-style promise in Java; Google has asked for a custom variation of CompletableFuture. All three are built out of functional interfaces.

From anonymous class to lambda

Before Java 8, a task was an anonymous class. A lambda expression says the same thing with only the parts that matter:

FormExample
No parameters() -> doWork()
One parameterx -> x * 2 (parentheses optional)
Several parameters(a, b) -> a + b
Explicit types(String s, int n) -> s.repeat(n)
Block bodyx -> { log(x); return x + 1; }

A lambda is not an anonymous class in disguise. It creates no new scope for this (inside a lambda, this is the enclosing object, as you saw in classes and interfaces), and it is compiled differently, as the senior section explains.

Functional interfaces: the type of a lambda

A lambda has no type of its own. It takes the type the context expects, which must be a functional interface: an interface with exactly one abstract method. Default and static methods do not count. The annotation @FunctionalInterface asks the compiler to check that, but any interface of the right shape works. These are the ones concurrency code uses all the time:

InterfaceAbstract methodShapeWhere you meet it
Runnablevoid run()nothing in, nothing outnew Thread(r), executor.execute(r)

Supplier<T>T get()nothing in, a result outCompletableFuture.supplyAsync, ThreadLocal.withInitial
Consumer<T>void accept(T t)a value in, nothing outthenAccept, forEach

BiFunction<T, U, R>R apply(T t, U u)two values in, a result outcompute, merge, thenCombine

There are primitive versions that avoid boxing: IntUnaryOperator for AtomicInteger.updateAndGet, LongBinaryOperator for LongAccumulator, IntSupplier, IntPredicate and more. On hot paths in concurrent code, prefer them.

Runnable or Callable?

The two task interfaces differ in two ways, and both matter:

  • A Callable returns a value. Submitted to an executor, it gives you a Future<V> that carries the result back to whoever calls get(), along with a happens-before edge, so you can see everything the task wrote.
  • A Callable may throw checked exceptions; a Runnable may not. Inside a Runnable, a call that throws InterruptedException must be caught on the spot.

The compiler picks the interface from the lambda's shape. A lambda whose body produces a value can be a Callable, so executor.submit(() -> counter.incrementAndGet()) returns a Future<Integer>. A void block can only be a Runnable, which leads to a classic puzzle:

Either let it propagate (a Callable can), or restore the interrupt flag before returning, so whoever is trying to cancel the task, often a pool shutting down, still sees the request. Method references

When a lambda only calls one existing method, a method reference says it shorter:

KindExampleEquivalent lambda
Static methodInteger::sum(a, b) -> Integer.sum(a, b)
Method of a particular object (bound)queue::offer, this::handlex -> queue.offer(x)
Method of whichever object is passed (unbound)String::length, Stats::withHits -> s.length()
ConstructorArrayList::new() -> new ArrayList<>() or n -> new ArrayList<>(n), depending on the target

Two traps hide in that last column. A constructor reference picks whichever constructor fits the target's parameters, so with Map<Integer, List<String>> byUser, byUser.computeIfAbsent(userId, ArrayList::new) calls new ArrayList<>(userId): an initial capacity equal to the user id, a huge allocation for a large id, and IllegalArgumentException for a negative one. And computeIfAbsent(key, LongAdder::new) does not compile at all, because LongAdder has no constructor that takes the key. Write k -> new ArrayList<>() and k -> new LongAdder().

Also, a bound reference evaluates its receiver once, when the reference is created: logger::log captures whichever logger object existed at that moment, and throws NullPointerException immediately if it was null. A lambda x -> logger.log(x) reads the field every time it runs.

What a lambda can capture, and why

A lambda can use three kinds of outside variables, and they behave very differently. That difference is variable capture:

What the lambda usesHow it gets itRuleShared between threads?
A local variable or parameterIts value is copied into the lambda object when the lambda is createdMust be effectively finalThe copy is not; an object it refers to may be
An instance fieldThrough the captured this, read each time the lambda runsNone: it may changeYes
A static fieldDirectly, each time the lambda runsNoneYes

The effectively final rule matters because the lambda may run on another thread after the method that created it has returned and its stack frame is gone. Java chooses to copy the value, and makes sure the copy can never disagree with the original by forbidding the original to change. Fields carry no such rule, so they are where lambdas meet shared mutable state:

The output is guaranteed, not lucky: Thread.start() creates a happens-before edge, so the worker sees every write main made before starting it. A write to greeting after start() would come with no such guarantee.

Loops are where the rule bites most often. A classic for loop's counter changes, so it cannot be captured; copy it into a fresh variable inside the body. The variable of an enhanced for loop is a new variable on every iteration, so it can be captured directly:

One more trick to recognize: int[] count = {0}; captured by a lambda that does count[0] += 1. It compiles, because the array reference never changes, but the array element is shared heap state. With several threads it is a data race, exactly like any other shared counter.

Lambdas as tasks for threads and executors

Every way of running work on another thread takes a functional interface:

  • new Thread(task, "name").start(), or with the Java 21 builders, Thread.ofPlatform().name("worker").start(task) and Thread.ofVirtual().start(task).
  • executor.execute(runnable) runs a task and returns nothing.
  • executor.submit(callable) returns a Future; executor.invokeAll(tasks) runs a batch and returns their futures in order.
  • CompletableFuture.supplyAsync(supplier, executor).thenApply(function).thenAccept(consumer) chains steps; each step is a lambda.

The cleanest concurrent code makes each task return its result instead of writing into shared state. Since Java 19 an ExecutorService is also AutoCloseable: closing it waits for submitted tasks to finish, so try-with-resources gives you a pool that cannot leak.

No lock, no atomic, no shared variable: each Callable computes privately, and Future.get() carries the result back with the visibility guarantee built in. You will build these pieces yourself in inside an executor and futures and promises.

Functions that may run twice, or under a lock

Many atomic APIs take a function and promise to apply it atomically. They keep that promise in one of two ways, and each puts a rule on your lambda.

Retry: the function may run more than once. AtomicReference.updateAndGet(fn) reads the current value, applies fn, and tries to swap the result in with a compare-and-swap. If another thread changed the value in the meantime, it reads again and calls fn again. The JDK documentation says the function should be side-effect-free for exactly this reason.

The result is still exactly right, because include is a pure function of its input. Put a log line, a metric, an add to a list or a remote call inside, and it happens a variable number of times.

Locking: the function runs while a lock is held. ConcurrentHashMap.computeIfAbsent, compute and merge run your function at most once per call (computeIfAbsent skips it when the key is present, merge when it is absent), but while holding the lock of the key's bin. Other threads writing to that bin wait, so the documentation asks for the function to be short and simple, and it must not update other keys of the same map (Java 9 and later may throw IllegalStateException with "Recursive update"). Never do slow I/O inside it: to load a value once per key without holding the lock during the load, store a CompletableFuture in the map and complete it outside, as in thread-safe caches.

Exceptions inside lambdas

Where an exception thrown by a task ends up depends on how the task was started:

Started withAn uncaught exception in the task
new Thread(task).start()Ends that thread; the uncaught exception handler prints the stack trace
executor.execute(task)Ends that pool thread, which the pool replaces; the stack trace is printed
executor.submit(task)Is captured in the Future and rethrown, wrapped in ExecutionException, by get(). If nobody calls get(), nobody ever sees it.
CompletableFuture.supplyAsync(...)Completes the future exceptionally; later stages see it in exceptionally or handle, or when someone calls join()

The third row is a classic production mystery: work silently stops happening, with no error in any log, because every task was submitted and no future was ever checked. Exceptions and failures inside threads covers the fixes.

Worked example: one parallel sum, three ways

Four tasks each sum a quarter of a range. Here are the three shapes you will see in interviews, from wrong to best:

  • Racy: the capture rule was satisfied (the array reference never changes), but total[0] += i is a read-modify-write on shared heap state from four threads: a lost update on almost every run, plus a plain long that is not even guaranteed to be written atomically.
  • Correct: each task accumulates in a local, which lives on its own stack, and touches shared state once. LongAdder makes that one update safe and cheap even if many tasks finish at once.
  • Best: no shared state at all. Results travel back through futures, which also provide the happens-before edge for free. This is the shape interviewers hope to see.

The habit to build: when a lambda wants to write to something outside itself, ask whether it could return the value instead.

Common mistakes

  • Mutating a captured object from many tasks: results.add(x) on a shared ArrayList, or the int[] counter trick. The capture rules do not protect objects.
  • Swallowing InterruptedException with an empty catch inside a Runnable. Restore the flag with Thread.currentThread().interrupt(), or use a Callable and let it propagate.
  • Side effects in updateAndGet, accumulateAndGet or similar CAS-based functions. They may run several times per update.
  • Slow work or I/O inside computeIfAbsent, compute or merge on a ConcurrentHashMap. The function holds a bin lock; keep it tiny, and never touch other keys of the same map inside it.
  • Calling thread.run() instead of thread.start(). run() executes the task on the current thread, with no new thread at all.
  • submit and forget. Exceptions vanish into futures nobody reads.
  • Constructor references with the wrong arity: computeIfAbsent(id, ArrayList::new) with an Integer key allocates a list with that capacity.

In the interview

Lambdas are everywhere in a Java concurrency round, so interviewers probe them indirectly: "why does this not compile?", "what does this print?", "is this task thread-safe?". They also appear in design-your-own-API questions: Rubrik's "run this Runnable after a delay, without blocking the caller", Rubrik's "a JavaScript-style promise in Java", and Google's "your own version of CompletableFuture" all come down to storing functional interfaces and calling them later, on the right thread.

A lambda captures local variables by value, so they must be effectively final; that makes stack variables impossible to race on. It does not copy objects: a captured list, or anything reached through this, is shared with every thread running the lambda. So I prefer tasks that return results through Callable and futures over tasks that write into shared state.
Functions passed to updateAndGet may be retried under contention, so they must be pure. Functions passed to ConcurrentHashMap.compute run under a bin lock, so they must be short and must not modify the map.

Follow ups to expect: "What is the difference between execute and submit?" (return value, and where exceptions go), "Why does Runnable not allow throws InterruptedException?" (its signature declares no checked exceptions; use Callable), "What does this mean inside a lambda?" (the enclosing object), and "How would you handle a very large number of delayed tasks?" (one scheduler thread with a priority queue, not a thread per task).

Senior depth

  • How lambdas are compiled. javac turns the body into a private method of the enclosing class and the lambda expression into an invokedynamic call that, on first use, spins up a small class implementing the interface. A lambda that captures nothing is, in current HotSpot, a single shared instance; a capturing lambda allocates a small object per evaluation holding the captured values. Neither is guaranteed by the language.
  • A lambda that accesses an instance field through this captures the enclosing object. A long-lived task, a listener or a scheduled job written that way keeps its enclosing object alive, which is a common leak in services. Accessing a static field does not require capturing this.
  • Where CompletableFuture callbacks run. A non-async stage such as thenApply runs on whichever thread completes the previous stage, or on the caller's thread if it is already complete. That can put slow work on an I/O thread. The Async variants take an executor; pass one explicitly instead of relying on the common pool. See composing async work.
  • Functional interfaces compose. Function.andThen, compose and Predicate.and are default methods: building blocks for pipelines, each still a plain function that must follow the same purity rules when used in atomic APIs.

Key takeaways

  • A lambda implements a functional interface: Runnable, Callable, Supplier, Consumer, Function, BiFunction, Predicate and friends.
  • Callable returns a value and may throw checked exceptions; Runnable does neither, so it must handle InterruptedException itself.
  • Locals are captured by value and must be effectively final; fields and captured objects stay shared.
  • Prefer tasks that return results over tasks that write shared state.
  • Functions given to CAS-based updates may run several times; functions given to ConcurrentHashMap.compute run under a lock. Keep both pure and short.
  • submit captures exceptions in the future; check it, or failures disappear.

What happens when you compile this?
Why. Lambdas copy captured locals, so Java requires them never to change. i += 1 changes it. Declare int id = i; inside the loop and capture id, a fresh variable on every iteration. The "prints 3 three times" behavior is what JavaScript closures over a shared variable used to do; Java rejects the code instead.
What does this print?
Why. The local local is copied when the lambda is created. The field greeting is read through this when the lambda runs, and the write to it happens before t.start(), which guarantees the new thread sees it. Fields are never subject to the effectively final rule.
Why does pool.submit(() -> { Thread.sleep(100); }) fail to compile, while pool.submit(() -> { Thread.sleep(100); return null; }) compiles?
Why. The compiler chooses the functional interface from the lambda's shape. A void block fits only Runnable, and an unhandled checked exception is a compile error there. Returning a value makes it fit Callable<V>, whose call() is declared throws Exception. The alternative fix is to catch the exception inside the Runnable and restore the interrupt flag.
The function passed to AtomicReference.updateAndGet logs a line each time it runs. With 8 threads updating at once, the log has many more lines than there were updates. Why?
Why. updateAndGet is a CAS loop: read, apply the function, try to swap; on failure, read the new value and apply again. That is why the documentation asks for side-effect-free functions. Move the logging after the call, using the returned value.
The following runs on the main thread. What does it print?
Why. run() is an ordinary method call: the Runnable executes on the calling thread, here main, and no new thread is ever created. Only start() creates the thread named "worker" and runs the task on it.
A task is submitted with executor.submit(task), it throws a RuntimeException, and the code never calls get() on the returned future. What happens?
Why. submit wraps the task in a future that catches whatever the task throws and keeps it for get(). With execute, the exception would instead reach the worker thread, which dies and has its stack trace printed by the uncaught exception handler. Always check futures, or handle errors inside the task.
What does byUser.computeIfAbsent(50_000_000, ArrayList::new).add("x") do, where Map<Integer, List<String>> byUser = new HashMap<>();?
Why. computeIfAbsent wants a Function<Integer, List<String>>, so the constructor reference must take one argument; unboxing makes ArrayList(int initialCapacity) fit. The result is a huge backing array allocated for one element. Write k -> new ArrayList<>() to say what you mean.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Write code
Rubrik style: write runAfter(Runnable task, long delayMs) that returns immediately and runs the task once on a background thread after the delay, without using ScheduledExecutorService. Return something the caller can use to cancel it. Then say how you would handle a very large number of pending tasks.
Model answer

The lambda captures task and delayMs, both effectively final, and the caller returns as soon as the thread is started. If interruption causes the sleep to throw, the task is skipped. Cancellation can race with the end of the delay: once the sleep has returned, this implementation may still invoke the task, which must cooperate with interruption itself. An exception thrown by the task ends only that thread.

One platform thread per pending task does not scale: each reserves a stack of a megabyte or more, so thousands of pending tasks waste memory and scheduler time. For many tasks I would use one scheduler thread that owns a PriorityQueue ordered by due time, guarded by a lock: it waits with Condition.awaitNanos until the earliest task is due, and runAfter adds a task and signals the condition so that an earlier deadline wakes the scheduler. Due tasks run on a small worker pool so a slow task cannot delay the others. In Java 21, a virtual thread per delayed task is also reasonable, because a sleeping virtual thread costs very little.

Explain
Explain why Java requires captured local variables to be effectively final, and why that rule does not make lambdas thread-safe.
Model answer

A lambda may run later, on another thread, after the method that created it has returned and its stack frame is gone. So Java copies the values of captured locals into the lambda object. If the local could still change, the copy and the original would disagree, and sharing the original instead would mean two threads racing on a stack variable. Requiring effectively final locals removes both problems: the copy is always correct, and stack variables can never be shared.

It does not make lambdas thread-safe, because it only constrains the variable, not the object the variable points to. Capturing a reference to an ArrayList, a map or an array shares that object with every thread running the lambda. Fields are read through the captured this, with no rule at all, and static fields are shared by definition. So a lambda that writes to anything outside itself needs the same care as any other code: a thread-safe structure, an atomic, a lock, or, better, returning its result through a Callable and a future instead of writing shared state.

Debug
A price cache does return cache.computeIfAbsent(sku, s -> pricingService.fetch(s)); on a ConcurrentHashMap, where fetch makes a network call of about 200 ms. Under load, requests for unrelated, already cached products sometimes stall, and when the pricing service times out, nothing gets cached and the next request waits again. Explain both effects and fix them.
Model answer

computeIfAbsent runs the mapping function while holding the lock of the key's bin. For 200 ms, every other write to that bin waits, including computeIfAbsent calls for products that are already cached (they take the bin lock too, unless the key happens to be the bin's first entry), so unrelated products that hash to the same bin stall. Plain get calls never block. Holding a lock across I/O also makes latency depend on a remote service. When fetch throws, computeIfAbsent rethrows and records no mapping, which is correct, but every caller then retries the slow call itself.

The fix is to store a future instead of the value. Create an incomplete CompletableFuture<Price> and install it with putIfAbsent; callers that find an existing future share it. Only the caller that installs its candidate schedules the fetch, after the map operation returns, and completes that future with the result. This keeps the load outside map coordination even if the executor runs submitted work on the caller's thread. Merely calling supplyAsync inside computeIfAbsent would not guarantee that separation. If loading or task submission fails, complete the candidate exceptionally and remove it with cache.remove(sku, candidate), so waiters observe the failure and a later request can retry without deleting a newer future. Callers can then await the shared future, preferably with a timeout. Add an expiry policy if cached prices must be refreshed.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 75 s
"This lambda captures a final ArrayList and several workers call add on it. My teammate says final makes it safe. Walk me through your review."
What a strong answer covers
  • final fixes the captured reference, not the mutable list it points to
  • Captured locals must be final or effectively final; Java copies their values, not their objects
  • Concurrent adds to the same ArrayList can lose elements or corrupt its state
  • Thread.start() or executor submission publishes earlier writes but does not protect later mutations
  • Prefer private task results combined through futures; otherwise guard all list access, including iteration, with one lock
How a senior would say it
It is unsafe if that list is an ordinary ArrayList. Final prevents reassignment of the reference; it does not freeze the list or synchronize its methods. A lambda captures the value of a local variable, and that local must be final or effectively final. When the value is a reference, every copy still points to the same object. For example, two workers can both append using the same current size and overwrite an element. Concurrent resizing can also leave the list inconsistent. Starting a thread or submitting a task safely publishes the state established beforehand, but that does not make later concurrent adds safe. My first choice would be for each task to build a private list and return it through a Callable. The coordinator retrieves the futures and combines the results on one thread. That removes shared mutation and also gives failures somewhere to go. If callers really need one live shared list, I would protect every access with the same lock, including iteration. I would choose that based on the required sharing, not the final modifier.

Likely follow up: What changes if the lambda reads an instance field instead of a captured local?

Out loudabout 60 s
"You are submitting a task that waits for work and returns a result. Would you use Runnable, Callable or Supplier, and what happens if it is interrupted?"
What a strong answer covers
  • Choose Callable for an executor task that returns a result and may throw checked exceptions
  • Runnable returns no result; Supplier returns a result but declares no checked exceptions
  • Let InterruptedException propagate from the Callable; a Runnable should restore the flag and stop
  • Future.get() exposes a task failure through ExecutionException and its cause
  • An interrupt of the thread waiting in get() is separate from cancellation of the worker task
How a senior would say it
I would choose a Callable, because it returns a value and its method allows checked exceptions. That lets a blocking operation propagate interruption to the task boundary. A Runnable returns nothing and cannot declare checked exceptions. A Supplier returns a value, but it also cannot declare checked exceptions, so it does not solve that part. If I had to use a runnable, I would catch interruption, restore the current thread's flag, and return promptly. After submission I keep the future and call get to observe the result. If the task throws, get throws ExecutionException, whose cause identifies the failure. That differs from the waiting thread itself being interrupted: its get call throws interruption directly, and the worker may still be running. If the result is no longer needed, I separately request task cancellation. I never treat merely submitting the work as observing its outcome.

Likely follow up: Why does adding return null make a block containing Thread.sleep fit the Callable overload?

Out loudabout 75 s
"An atomic update lambda sends an audit event. Under load we get more events than updates. Why, and would moving it into ConcurrentHashMap.compute solve the problem?"
What a strong answer covers
  • Atomic update functions may be reapplied after a failed compare-and-set
  • Give an interleaving where another update wins and the first caller retries
  • Keep the update function free of externally visible side effects
  • Moving the event after a successful update avoids retry duplicates but does not make delivery atomic
  • ConcurrentHashMap.compute calls its function once per invocation but can block competing updates
  • Keep map callbacks short and do not use them to make remote event delivery transactional
How a senior would say it
The extra events come from retrying the function, even though each atomic update commits only once. Imagine two callers read the same value. Both compute replacements and send events. One wins the compare and set. The other loses, reads the newer value, and may run its function again, sending another event. I would keep that function pure: calculate a replacement without sending messages or mutating another object. For simple logging, I can emit after the update returns, using the returned value. That avoids retry duplicates, but a crash between the update and the event still leaves a gap, and events from different threads can arrive out of order. ConcurrentHashMap.compute has a different contract: it invokes its function once per call while coordinating the update, and competing updates can block. A slow event service inside that callback would therefore delay map operations. It still would not make a remote event and an in-memory update one transaction. I would keep that callback short too, and design a separate durable delivery protocol if the event must survive failures.

Likely follow up: How would you share one slow cache load among callers without performing the load inside a map callback?
