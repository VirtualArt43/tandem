Check then act: two safe calls, one unsafe sequence

Deciding on shared state and then acting on it is a race even when every call is thread-safe; the four ways to make check and act one step.

Asked atLinkedInGoogleMetaAmazon
Before this:Race conditions versus data racesThe lost update: read, modify, write

The second most common race in real code: look at shared state, decide, then act on the decision, while another thread changes the state in between. It survives every thread-safe class you throw at it, because the bug is in the sequence, not in any single call.

In plain words

Two flatmates each open the fridge, see there is no milk, and each go out and buy a litre. Both checked correctly. Both acted sensibly on what they saw. You now have two litres of milk, because the fridge changed between one person's look and their return, and nothing stopped the other person from looking in that gap. Computer science textbooks call this the "too much milk" problem.

A railway berth works the same way: two booking clerks see berth 23 free on their screens, and both press "book". Each screen was right when it was drawn.

The shape

A check then act is any code of the form "if the shared state looks like X, do Y, where Y is only correct if X is still true". Between the check and the act another thread can make X false. Once you know the shape, you see it everywhere:

  • Lazy initialization: if (instance == null) instance = new Service();
  • Put if absent: if (!map.containsKey(k)) map.put(k, load(k));
  • Get if present: if (map.containsKey(k)) return map.get(k);
  • Limits: if (count < limit) { count += 1; admit(); }
  • Money and seats: if (balance >= x) balance -= x; and if (seat.isFree()) seat.book(user);
  • Queues: if (!queue.isEmpty()) item = queue.remove();
  • Files: if (!file.exists()) create(file);, the classic TOCTOU (time of check to time of use) bug.

The fix is always the same idea, make the check and the act one indivisible step, and it comes in four flavours, below.

Thread safety does not compose

Here a ConcurrentHashMap in Java, and in C++ a map whose every method takes the same lock, guard a cache. Each call is perfectly thread-safe. Two threads ask for the same missing key at the same moment, and the expensive load runs twice. Then the same cache with check and act made atomic.

ThreadSanitizer is silent on the C++ version: there is no data race, only a race condition (the distinction from the previous lesson). The slow load is realistic, not a trick: in real code the "act" is often the expensive part (a database call, opening a connection), which is exactly what holds the window open. And a duplicate load is the mild outcome. If the value were a counter or a connection, the second put would overwrite the first, and anything already done through the first one would be lost.

This is why thread safety does not compose: a class made of thread-safe calls is not automatically safe to use in sequences. When you see a read of shared state whose result feeds a later write, the whole span from read to write needs to be atomic.

Fix 1: use an atomic compound operation

The best fix is an operation that already does the check and the act as one step inside the data structure. The Java map operations below require a concurrent implementation with the stated atomic guarantees, such as ConcurrentHashMap; ordinary Map default methods do not promise them. The queue operation likewise requires a thread-safe queue.

A note on ConcurrentHashMap's computeIfAbsent: competing calls share the installed value when the loader succeeds with a non-null result and the entry remains present. A null result, an exception or later removal permits another computation. Some other updates can wait during computation, so keep the function short and never modify the same map from inside it. If the load is slow, install a future with a short atomic operation and perform the load outside that operation; that is the single-flight pattern in thread-safe caches.

Fix 2: one lock around check and act

When no ready-made operation exists, hold one lock across the check and the act, and make sure every other access to that state takes the same lock. A lock around only the check, or only the act, or two different locks, leaves the gap open. In the cache above, get_atomic does this in C++.

The cost: the lock is held for the whole span. If the act is slow (the 20 ms load), every other thread, even one asking for a different key, waits. Holding a lock during I/O is one of the rules of locking you will learn to avoid, which is why the cache fix in practice is per key (Java's computeIfAbsent locks only one bin) or a single-flight future.

Fix 3: check again at the moment of acting (compare-and-swap)

Instead of holding a lock across the gap, let the act itself verify that the check still holds, and retry if it does not. That is a compare-and-swap: "set it to the new value only if it still has the value I based my decision on". Here is a ticket counter that can never oversell, with no lock at all:

Compare it with the tempting version, if (remaining.get() > 0) remaining.decrementAndGet();: each call is atomic, and it still oversells, because two threads can both see 1. The compare-and-swap version can only subtract from the exact value it checked. The retry loop is called a CAS loop, and you will build many of them in CAS loops and atomic state machines.

Fix 4: let the outer system decide

When the shared state lives outside your process, in a database or a file system, a lock in your program cannot cover other processes or other servers. Then you push the check and the act down into one operation of the system that owns the state:

  • A conditional update: UPDATE seats SET holder = ? WHERE seat_id = ? AND holder IS NULL. If it reports one row changed, you got the seat; zero rows means someone else did. No read, no gap.
  • A unique constraint: insert the booking and let the database reject the duplicate. The losing request gets a constraint violation, which you turn into "already taken".
  • Atomic file creation: Files.createFile or open with O_CREAT | O_EXCL, as in the table.

These ideas grow into optimistic and pessimistic concurrency control, covered in optimistic versus pessimistic concurrency. For an interview, the key sentence is: the final arbiter must be the place where the data lives.

The check that lies even when you do not act

A check followed by a read is the same bug. containsKey said yes, then another thread removed the key, and get returns null. The fix: read once, then decide on the value you actually got.

The same goes for size(): on a concurrent collection it is a snapshot that may be wrong by the time you use it. Never write if (queue.size() > 0) queue.remove() against a structure other threads also change.

Lazy initialization, the most famous check-then-act

if (instance == null) instance = new Service(); run by two threads at startup can build two instances, and callers can end up holding different ones. Without volatile or atomics, a thread can even see the reference before the object's fields are written, a problem covered in double-checked locking. Both languages give you a lazy, thread-safe initializer for free:

These are the holder class idiom and the function-local static. When the initializer needs arguments known only at run time, use std::call_once in C++, or double-checked locking with a volatile field in Java.

Worked example: the rate limiter that admits 101 requests

A limiter allows 100 requests per window. The counter is an AtomicInteger (or std::atomic<int>), and the code reads if (count.get() < 100) { count.incrementAndGet(); admit(); }. LinkedIn interviewers have asked candidates to walk through exactly this race, two threads that both see 99 of 100. Here it is:

Three correct fixes, and when to pick each:

  1. Increment first, then check the result: if (count.incrementAndGet() <= 100) admit(); else reject();. This works for a fixed window provided the counter cannot overflow and resets are coordinated. Rejections also increase the counter; with unbounded attempts, integer wraparound can admit requests again. Use the bounded CAS version if you cannot enforce that assumption.
  2. A CAS loop, exactly like tryReserve above: read, give up at the limit, and only increment from the exact value you checked. The counter never exceeds 100.
  3. One lock around the check, the increment and any window reset, when the limiter has several fields (count and window start) that must change together.

Saying all three, and choosing between them by whether the state is one variable or several, is what a strong answer sounds like. Distributed rate limiting is the same problem one level up: an atomic increment in Redis instead of a local read-then-write.

Common mistakes

  • "I used a ConcurrentHashMap, so it is thread-safe." Only each call is. containsKey then put, or get then put, is still a race. Use the atomic methods.
  • Locking the check but not the act (or the other way round), or using two different locks for them. One lock must cover the whole span, and every writer must use it.
  • Atomic pieces, non-atomic whole: if (count.get() < limit) count.incrementAndGet();. Use a CAS loop or increment-then-check.
  • Doing slow work inside computeIfAbsent or under the one lock on a hot structure. Correct, but everyone waits; cache a future instead.
  • Calling back into the same ConcurrentHashMap from inside computeIfAbsent. The map does not support recursive updates; it may throw or hang.
  • Using exists(), size() or isEmpty() to decide what to do next on state other threads or processes can change. Do the operation and handle "it did not work".
  • Fixing it with a retry and a sleep. The window gets rarer, not closed.

In the interview

It comes as "is this thread-safe?" with a ConcurrentHashMap and containsKey in it, as the follow up "now many threads call this" (a Google L5 report had a per-user counter map), as the walk-through of a rate limiter at 99 of 100 (LinkedIn), and in system design as "two users book the same seat" (Meta's ticket booking questions, Amazon's last item in stock).

Each call is thread-safe, but the sequence is not: another thread can change the map between the check and the put. Thread safety does not compose. I'd make check and act one step: computeIfAbsent here, or a compare-and-set for a single counter, or one lock around both if several fields change together. If the state lives in a database, I'd let the database decide with a conditional update or a unique constraint.

Follow ups to expect: "Fix it without a global lock" (computeIfAbsent, merge, CAS). "What if creating the value is expensive?" (computeIfAbsent shares a successful installed value but can block other updates; for slow loads, install a future and load outside the map operation). "What if there are many servers?" (the database or a shared store must arbitrate: conditional update, unique key, or an atomic increment in Redis). "Why not volatile?" (it gives visibility, not atomicity of a sequence).

Senior depth

Database isolation does not save you by default. SELECT the seat, see it free, then UPDATE it: under the common read committed isolation level, two transactions can both see "free" and both write. You need SELECT ... FOR UPDATE (a row lock, pessimistic), a conditional UPDATE ... WHERE holder IS NULL (atomic at the row), a version column (optimistic), or serializable isolation. This is the same bug, one level up; see isolation levels and anomalies.

TOCTOU is a security class. A privileged program that checks a path's permissions and then opens the path can be tricked by swapping a symbolic link in between. The fix is the same principle: operate on what you checked (open first, then check the opened file descriptor), or use an atomic system call.

Idempotency turns some check-then-acts into non-issues. If acting twice is harmless, for example "set the status to SHIPPED" rather than "add one to shipped count", a lost race costs nothing. Designing operations to be idempotent is often cheaper than making the check atomic; see idempotency.

Key takeaways

  • Check-then-act: a decision on shared state, then an act that assumes the decision still holds. Another thread can invalidate it in between.
  • Thread safety does not compose: two thread-safe calls in a row are not a thread-safe sequence.
  • Four fixes: an atomic compound operation (computeIfAbsent, merge, CAS), one lock over check and act, a CAS loop that re-checks at the moment of acting, or letting the database or file system arbitrate.
  • Read once and decide on what you read; containsKey then get, and size() checks, lie under concurrency.
  • Lazy initialization is a check-then-act: use the holder idiom, a function-local static or std::call_once.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Debug
Many threads call hit(user) on this per-user counter (Java shown; the C++ version does the same with a map whose methods each lock). Find the race, describe an interleaving that loses a hit, and write a correct version in your language.
Model answer

Creating the counter is a check-then-act. Two threads see no counter for a new user and both create one. Thread A puts counter 1 and increments it to 1. Thread B, which also passed the check, puts counter 2, replacing counter 1, and increments it to 1. The user has two hits but the map shows 1: A's hit went to a counter nobody can reach any more.

In Java, computeIfAbsent guarantees one counter per user, and LongAdder keeps a hot user's counter cheap under contention. In C++ there is no concurrent map in the standard library, so one mutex covers the lookup, the insertion and the increment. If that lock became a bottleneck, the next step would be lock striping: several maps, each with its own mutex, chosen by a hash of the user.

Design
Two users on two different app servers click "book seat 14C" for the same show at the same moment. Walk through how you guarantee that only one booking succeeds.
Model answer

A lock inside either server cannot help: the two requests are in different processes. The check and the act must happen as one step in the system that owns the seat data, the database. I would make booking a single conditional statement: UPDATE seats SET holder = :user, held_until = :expiry WHERE show_id = :show AND seat = '14C' AND (holder IS NULL OR held_until < now()). The database row-locks the seat while it evaluates and applies the statement, so exactly one of the two updates changes a row. The application looks at the affected row count: 1 means this user won, 0 means it tells the user the seat is gone.

As a second line of defence I would keep a unique constraint on (show, seat) in the confirmed bookings table, so even a bug elsewhere cannot confirm two bookings. Holds expire, which is why the condition includes held_until. Alternatives I would mention: SELECT ... FOR UPDATE in a transaction (pessimistic, holds the row lock longer) or a version column with optimistic retries. What I would not do is read the seat, check it in application code, then write it: under read committed isolation both requests would see it free.

Explain
An interviewer says: "I made every public method of this class synchronized. Is the class thread-safe now?" What do you answer?
Model answer

It depends on the contract and how callers use it. Methods that hold the same monitor throughout their accesses exclude one another, but I would still check for different locks, escaped mutable state and waits that release the monitor. Callers that combine methods, like "if not contains(x) then add(x)", or "read size(), then get the last element", can have a check-then-act race between calls because the lock is released after each one. Thread safety does not compose.

The fix is to give the class the compound operations its callers need, such as addIfAbsent(x) or pollLast(), each doing the whole sequence under one lock. Alternatively the class can document a client-side locking policy, as Collections.synchronizedList does for iteration (callers synchronize on the list itself), but that is fragile because every caller must remember it. I would also check that no method leaks a reference to internal mutable state, since callers could then change it without any lock.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 90 s
"We use a concurrent map, but two requests load the same missing key and overwrite each other. How would you fix that, especially if loading is slow?"
What a strong answer covers
  • Two contains-then-put sequences can both observe absence before either inserts
  • Use ConcurrentHashMap.computeIfAbsent in Java or one mutex around lookup and insertion in C++
  • Successful non-null installation is shared; null, exceptions or removal can permit recomputation
  • putIfAbsent protects installation but does not prevent eager construction by both callers
  • For slow loads, atomically install one future; its owner loads outside the map operation and completes it for waiters
How a senior would say it
I would make the decision to create an entry atomic with claiming that entry. Right now, request A checks and sees no value. Request B checks before A inserts and also sees no value. Both load, and the later put can replace the earlier result. The map has protected each call, but not their sequence. For a short computation in Java, I would use computeIfAbsent on a ConcurrentHashMap. For a C++ map, I would initially protect lookup, creation and insertion with the same mutex used by other accesses. I would state the Java guarantee carefully: callers share a successful non-null installation while it remains present. A null result, exception or removal can allow another computation. putIfAbsent alone prevents replacement, but if both callers build the argument first, both still do the expensive work. For a slow database call, I would instead atomically install a future representing the in-progress load. Only the caller that installed it performs the load, outside the map operation. Other callers wait on that same future. The owner completes it with a value or failure, and the cache has an explicit retry policy for failures. This keeps slow work out of the map's critical section while coordinating callers for the same key.

Likely follow up: If a failed future should be removed for retry, how do you avoid removing a newer entry for the same key?

Out loudabout 75 s
"My limit is 100. The atomic counter is 99, and each request checks it before incrementing. Show me the failure and fix it without a lock."
What a strong answer covers
  • Both requests can read 99 before either increments, admitting two and reaching 101
  • Atomic accesses or stronger memory ordering do not combine the check and update
  • Read the count, reject at the limit, then CAS the observed count to one more
  • On CAS failure, recheck using a fresh value; only successful CAS admits the request
  • The reasoning assumes one fixed window; coordinating a reset adds state to protect
How a senior would say it
Both requests can pass the check before either increments. A reads ninety-nine, B reads ninety-nine, and both decide to admit. Their atomic increments then take the counter to one hundred and one hundred and one. There is no data race on the counter, but the admission rule has failed. I would use a compare-and-set loop. Read the current count and reject if it is already at the limit. Otherwise, attempt to replace that exact observed value with one more. Only a successful replacement grants admission. If another request changed the count first, retry from the updated value and check the limit again. In Java I reload after a failed compare-and-set. In C++, compare-exchange updates its expected argument on failure, and the weak form belongs in a retry loop. Stronger memory ordering alone would not close the original gap. This answer assumes one fixed window with no independent reset. If the window timestamp and counter must change together, I would coordinate them as one state, often under a lock, rather than reset the counter separately.

Likely follow up: What can go wrong if you increment first, reject above the limit, and allow unlimited rejected attempts?

Out loudabout 75 s
"Two app servers both check that a seat is free and then book it. Where would you put the synchronization?"
What a strong answer covers
  • A process-local lock cannot coordinate the independent app servers
  • Put the check and update in one operation at the shared database
  • Use a conditional update and treat the affected row count as the decision
  • Report success only after commit; a unique booking constraint protects the shared rule
  • Separate contention from retries after an uncertain response, using an idempotency key
How a senior would say it
I would put the decision in the database that owns the seat state. A mutex in either server protects only that process, so both servers could still decide that the seat is free. Instead of reading and then writing, I would issue one conditional update that assigns the holder only if that show's seat is still unassigned. In a database with atomic conditional row updates, the affected row count is the decision: one means this transaction claimed it; zero means it did not. I would report success only after the transaction commits. A unique constraint on show and seat in the bookings table can also enforce that there is only one confirmed booking. The losing request receives an ordinary unavailable result rather than overwriting the winner. I would separately handle retries after a lost response: the client may not know that its first transaction committed, so a request identifier should let it recover the same outcome. That retry policy complements the atomic claim. It does not replace the database operation that prevents two different users winning.

Likely follow up: If you add expiring holds, what must confirmation check atomically before it succeeds?
