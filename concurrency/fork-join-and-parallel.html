Fork/join, work stealing and parallel algorithms

Split one big computation across every core with divide and conquer, keep cores busy with work stealing, and avoid the parallel stream traps.

Asked atAppleGoogle
Before this:Why thread pools existFutures and promises

Some work is not many small requests but one big computation: sum a billion numbers, sort a huge array, walk a tree. Fork/join splits it into pieces that can use several cores, and work stealing helps keep workers busy even when the pieces turn out uneven. It is also the engine under Java's parallel streams and CompletableFuture's default executor, which is why its traps reach code that never mentions it.

In plain words

A teacher has 1,000 exam papers and 8 assistants. She splits the pile in half, keeps one half and puts the other on her desk for anyone free to take. Each assistant does the same with the pile they took: split, keep half, leave half out. Piles smaller than 25 papers are just graded, because splitting them would take longer than grading them.

An assistant who runs out of work walks over to a busy colleague's desk and takes the oldest available pile lying there, not the one the colleague is working on. That is work stealing: idle workers find work by themselves, and in this balanced splitting example, older piles tend to be larger, so each steal provides substantial work.

Divide and conquer, in parallel

Fork/join is recursion where the recursive calls may run in parallel:

  1. If the problem is small, below a sequential cutoff, solve it with a plain loop.
  2. Otherwise split it in two, fork one half (make it available to run on another thread), compute the other half yourself, then join the forked half (wait for its result) and combine.

The cutoff is a major tuning choice. Forked tasks add allocation, queue and synchronization overhead, so each should do enough work to amortize that cost. There is no portable task-cost constant; measure on the target runtime and workload. The ForkJoinTask documentation's rough rule is that a task should perform between about 100 and 10,000 basic computational steps. Too small and the overhead dominates; too large and there are too few pieces to balance across cores.

The order of fork, compute and join is the second thing interviewers check. Fork one half, compute the other, then join. Joining right after forking (left.fork(); left.join(); right.compute();) serializes those two halves, and forking both halves and then joining both leaves the current worker with nothing to do but wait for, or help with, its own children.

The output block illustrates Java; its steal count is an estimate and varies. C++ prints its depth and thread limit instead. C++20 has no standard work-stealing pool, so the example uses std::async and a depth cap of floor(log2(budget)), with a demo budget of at most four threads including the caller. Without the cap, recursion on a large array would try to start a thread per piece. Notice it still follows the same rule: start the left half, compute the right half on the current thread, then wait.

Work stealing

A ForkJoinPool does not have one shared queue; it uses work stealing. Each worker owns a double-ended queue (deque) of tasks, in the default mode:

  • A worker pushes the tasks it forks onto its own end of its deque, and pops from that same end: last in, first out. For balanced recursive splits, newer tasks tend to be smaller and may have better cache locality.
  • An idle worker becomes a thief: it picks a victim and takes a task from the other end of the victim's deque: an older task, often a larger remaining piece in recursive splitting. One steal gives it a lot of work.
  • Because owner and thief work at opposite ends, they rarely contend for the same slot; the owner's operations are cheap, but owner operations also need memory ordering and arbitration for the last item. A deque is not safe just because its two ends have different users.
  • join() cooperates with the pool: a worker may execute an unstarted child, help related work, or eventually wait while the pool attempts compensation. This supports nested, acyclic fork/join dependencies and avoids the simple queued-child starvation in the failures lesson. It does not resolve dependency cycles, locks held across a join, or arbitrary blocking I/O.

Work stealing shines when pieces are uneven (a tree with one deep branch, a search that prunes unpredictably): busy workers keep splitting, idle ones keep stealing, and the load balances itself. It is built for CPU-bound work. A default dedicated Java fork/join pool targets the available processor count; you can set another parallelism. A task waiting on I/O occupies a worker without using a core, reducing execution capacity. If fork/join tasks must block, Java offers ForkJoinPool.managedBlock, with a ManagedBlocker whose isReleasable() checks without blocking and whose block() performs the wait. This lets the pool attempt compensation within its limits, but the right answer is usually to keep blocking work in a separate pool.

The common pool and parallel streams

Java has one shared ForkJoinPool.commonPool() per JVM, the common pool. With default settings in OpenJDK 21, its target parallelism is normally max(1, availableProcessors() - 1), leaving room for a participating caller. It is a configurable target, not a hard cap on total threads; java.util.concurrent.ForkJoinPool.common.parallelism can override it. Three things run on it unless you say otherwise:

  • Parallel streams: list.parallelStream() or stream.parallel() splits the source with a spliterator into fork/join tasks.
  • CompletableFuture's async methods called without an executor, provided common-pool parallelism is at least two; otherwise CompletableFuture creates a thread per async task (the composition lesson).
  • Arrays.parallelSort and your own RecursiveTasks when they are forked outside any pool.

So the caveats come as a set. Blocking can starve unrelated work: a parallel stream that makes HTTP calls occupies the common pool, and unrelated async stages and parallel streams elsewhere in the JVM slow down. Small or cheap streams get slower: for sufficiently cheap work, splitting and merging dominate. Some sources split badly: arrays and ArrayList split cheaply; linked, generated and I/O-backed sources may require traversal, batching or serialization. Order costs: forEach runs in any order; forEachOrdered, findFirst and limit on an ordered stream force coordination. And unsynchronized shared mutation can race:

The scalable fix is structural: let each piece compute its own partial result and combine at the end (sum, reduce, collect), which is what divide and conquer does anyway. Java

To run a parallel stream somewhere other than the common pool, a widely used trick is to start it from inside a task of your own pool: myPool.submit(() -> list.parallelStream().map(f).toList()).get(). It works because fork() is documented to use the pool the current task runs in, and streams happen to be built on fork(); the Stream API itself does not promise it. For blocking work, a plain executor with CompletableFuture is clearer.

C++: async, pools and the parallel algorithms

C++ gives you three routes:

  • std::async with a depth cap, as above: std::launch::async starts a thread per call in this libc++, so cap depth at floor(log2(thread budget)). Without an explicit policy, std::async may defer work until a waiting call executes it. Keep the future: destroying the last future for an unfinished async task can block and accidentally serialize a loop.
  • A thread pool with futures. Careful: a pool worker that waits on its children's futures can deadlock a fixed pool exactly as in the failures lesson; task runtimes such as oneTBB support nested task waits, but dependency cycles and blocking on unrelated locks can still deadlock.
  • C++17 parallel algorithms: pass an execution policy such as std::execution::par to std::sort, std::reduce, std::transform and friends. Availability and backend depend on the toolchain. On this Mac, Apple clang 17 with its default libc++ rejects std::execution::par; do not assume an experimental flag supplies a working backend. The next C++ fragment targets a library that implements these policies. In an interview it is fine to mention them, with that caveat.

Why it never scales perfectly: Amdahl's law

If a fraction p of the work parallelizes and the rest is sequential, n cores give at most a speedup of 1 / ((1 - p) + p / n). With 90 percent parallel work, 8 cores give 1 / (0.1 + 0.1125), about 4.7, and infinitely many cores give at most 10. Sequential setup, combining results and synchronization all contribute. In the simple merge sort with a sequential merge, the root merge touches every element on one thread; implementations can parallelize the merge too. This ideal bound ignores task overhead and memory bandwidth limits. More on this in Performance: contention, Amdahl and profiling (amdahl's law).

Worked example: a parallel merge sort with at most P threads

This is the parallel merge sort problem. The plan: recurse, and at each level sort the left half in a new task while sorting the right half on the current thread, until the spawning depth reaches floor(log2(P)) (so at most P threads including the caller) or the range falls below a cutoff such as 4,096 elements, where a sequential sort takes over. Then merge the two sorted halves into a buffer and copy back.

Where the time goes for 8 million elements on 8 threads: the 8 leaves sort a million elements each, fully in parallel. Then 4 merges of 2 million run in parallel, then 2 merges of 4 million, then one merge of 8 million on a single thread. Lower-level merges overlap, but the root merge lies on every critical path, limiting scaling. In the uncapped recursion with a constant leaf cutoff, sequential merging gives O(n log n) total work and an O(n) critical path, so only O(log n) parallelism is available even before overhead. A fixed thread budget adds the sequential work done inside each leaf. The senior follow up is a parallel merge: pick the median of the larger half, binary search its rank in the other half, place that pivot at its final output rank, and merge the two pairs into disjoint output ranges in parallel. A cutoff avoids tiny merges; consistent lower-bound versus upper-bound tie rules preserve stability when keys are equal.

Common mistakes

  • No sequential cutoff (a task per element). Overhead swamps the work and it runs slower than a loop.
  • Joining immediately after forking, which serializes the two halves with extra scheduling overhead.
  • Blocking I/O in fork/join tasks or parallel streams. The pool is sized to cores and shared; blocking starves everything else on it.
  • Shared mutable state in a parallel computation: forEach(x -> list.add(x)) on an ArrayList, or a shared counter. Use reductions and collectors.
  • Parallelizing small or cheap work, or sources that split badly. Measure before and after.
  • C++: unbounded std::async recursion. A full depth-20 splitting tree can request roughly a million threads before resource limits stop it. Cap the depth or use a pool.
  • Relying on std::execution::par on Apple clang. It does not compile by default; use std::async, a pool or TBB.

In the interview

It comes as "now parallelize it". Apple has asked candidates to sum the values of an iterator and then parallelize the sum with two threads, and in another loop to optimize a topological sort for multi-core execution. A Google L5 candidate was told mid-round that the processing could be parallelized, and believed needing that hint cost a Strong Hire. Prepare the associated theory questions too: "why is my parallel stream slow?" and "what is work stealing?"

I would split the data into ranges, solve ranges below a cutoff sequentially, and combine partial results, so partial results are private and the shared input remains read-only. In Java that is a RecursiveTask on a ForkJoinPool, forking one half and computing the other before joining; in C++ std::async with a depth cap, or TBB. Work stealing balances uneven pieces: idle workers take an older, often larger task from the far end of a busy worker's deque. I would keep blocking I/O out of the fork/join pool, and I would expect Amdahl's law to cap the speedup at the sequential combine step.

Follow ups: "How do you pick the cutoff?" (big enough to amortize task overhead, small enough for several tasks per core; then measure), "Why do thieves take from the other end?" (often a larger piece, less contention with the owner), and "Can join still deadlock?" (helping supports acyclic subtasks; cyclic dependencies or locks held across joins can still deadlock).

Senior depth

A reduction needs an algebra. Java reduce(identity, op) requires an associative operation and a neutral identity. Subtraction is not associative, and an identity of 10 for addition contributes 10 per partition. Prefer collect with a fresh container per partition for mutable accumulation; sharing one mutable identity with reduce defeats isolation. Floating-point addition changes with grouping, so a parallel sum may differ from a sequential sum even without races.

C++ std::reduce may regroup and reorder even without an execution policy; it is not an ordered left fold like std::accumulate. For predictable mathematical results, use operations valid under both regrouping and reordering, such as addition on integers when overflow is excluded. Java long overflow wraps; signed C++ overflow is undefined behaviour. Choose accumulator widths and input bounds explicitly.

Completion publishes results. Publish Java task inputs before submission or fork(); a successful join makes completed task effects available to the caller. In C++, async launch and future completion supply the corresponding synchronization. Do not mutate inputs concurrently. In a merge sort, sibling tasks may write disjoint elements of an ordinary array, but the parent must join before reading them, and no thread may resize the shared buffer.

Failure is not automatic tree cancellation. Java RecursiveTask returns a value; RecursiveAction returns none. An unchecked child failure is rethrown by join(), whereas get() reports it through ExecutionException and supports interruption. Cancelling a ForkJoinTask does not interrupt its running worker, even with true; siblings need cooperative cancellation and explicit accounting. C++ future get() rethrows the child exception; std::async has no standard cancel operation. Keep captured inputs alive until all launched work has finished, including failure paths.

Execution policies are permissions, not speedup promises. A C++ library may execute par sequentially; callbacks must not wait for another iteration to run concurrently. par_unseq also permits unsequenced calls on one thread, so mutex-taking and other vectorization-unsafe operations are unsuitable. Exceptions escaping element operations under standard execution policies call std::terminate; they do not propagate like an exception from an async future.

Measure the limiting resource. A large sum often becomes memory-bandwidth-bound before every core is useful. Compare a sequential baseline with several cutoffs and thread counts on the real input, account for JVM warm-up, and exclude logging from the measured body. The common pool's workers are daemon threads, so arrange explicit completion before process exit; its shutdown() does not shut down the shared pool. For non-joined event tasks, ForkJoinPool also offers asyncMode=true, using FIFO local scheduling instead of the default LIFO policy.

Key takeaways

  • Fork/join is parallel divide and conquer: below a cutoff, loop; above it, fork one half, compute the other, join.
  • Work stealing: each worker owns a deque; owners use one end, thieves take older tasks from the other; join can help, but cyclic waits remain unsafe.
  • It is for CPU-bound work. Java's common pool is shared by parallel streams and async methods, so blocking in it hurts everyone.
  • Combine partial results instead of sharing mutable state; parallelize only work big enough to pay for the overhead.
  • C++: std::async with a depth cap, a pool, or TBB; C++17 parallel algorithms exist but the installed Apple clang/libc++ does not support the execution-policy fragment by default. Amdahl's law caps every speedup.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A divide and conquer task splits into left and right. Which version gets parallelism while keeping the current thread useful?
Why. Forking left makes it available to other workers while the current thread does the right half, then the join collects the left. Joining before computing right serializes those halves. Computing both before forking exposes no parallel work during those calls. Starting two new threads and joining them parks the current thread; recursively repeated without a budget, it also creates excessive threads. Forking both and joining both works but leaves the current worker idle or helping instead of doing its own half directly.
In work stealing, why does a thief take a task from the opposite end of the victim's deque from the one the owner uses?
Why. The owner uses its newest tasks, which tend to be smaller and cache-friendly for recursive splits. Older forks often offer more work to steal. Task size is not measured by the deque, global FIFO order is not promised, and the last item still requires synchronization. Neither deque end is reserved by a lock held throughout user computation.
Someone sets the sequential cutoff to 1, so every element becomes its own task in a bounded fork/join pool. Assuming resources suffice, what is the likely performance effect for 10 million additions?
Why. A task costs an allocation and queue operations, far more than adding two numbers. With millions of tiny tasks, overhead dominates. A larger measured cutoff amortizes that overhead. A small cutoff does not by itself change the arithmetic or introduce a dependency cycle, so it does not imply a wrong answer or a deadlock.
A job is 90 percent parallelizable and 10 percent sequential. What is the best possible speedup on 8 cores?
Why. Amdahl's law: 1 / (0.1 + 0.9 / 8) = 1 / 0.2125, about 4.7. Even with infinitely many cores the limit is 1 / 0.1 = 10. The answer 10 is the infinite-core limit, not the eight-core result. Eight assumes all work parallelizes, and 7.2 incorrectly multiplies the core count by the parallel fraction.
A service uses a fork/join pool targeting 8 workers, all blocked in ordinary socket reads without managedBlock. The remote service takes 200 ms. What risk does this create?
Why. The pool does not guarantee compensation for unmanaged I/O. Other system threads can still use the cores, but stealing cannot make a blocked worker execute more tasks. Use a bounded I/O executor or Java virtual threads with a separate concurrency limit. Managed blocking allows compensation attempts, not unlimited threads or guaranteed throughput.
Java onlyWhat can IntStream.rangeClosed(1, 5).parallel().forEach(i -> System.out.print(i + " ")) print?
Why. forEach on a parallel stream makes no ordering promise; elements are processed by whichever worker holds them. Every element is still printed exactly once. forEachOrdered would print 1 2 3 4 5, at the cost of coordination between the workers.
C++ onlyA recursive parallel sum calls std::async(std::launch::async, ...) for one half at every level, with no depth limit, on a range split down to a cutoff 20 levels deep. What is the problem?
Why. With libc++ and libstdc++, each std::launch::async call starts a new thread, and every level doubles the count: 2 to the 20th is about a million. Cap the depth near log2(cores), below which you recurse sequentially, or use a pool.

Write code
Write a parallel maximum of an array of integers using divide and conquer with a sequential cutoff, in your language.
Model answer

Points to say: each task reads only its own range and returns a value, so the input is shared read-only and partial results are private; safe publication and completion synchronization are still required; the cutoff keeps tasks large enough to pay for themselves; the current thread computes one half while the other is forked; and the C++ depth cap bounds the number of threads. An empty array must be handled by the caller, because "the maximum of nothing" has no answer.

Explain
Explain work stealing to an interviewer, including how cooperative join() avoids ordinary queued-child starvation and which waits can still deadlock.
Model answer

Each worker has its own deque. Tasks it forks go on its own end, and it takes work from that same end, newest first, which keeps small, cache-warm tasks local. When a worker runs dry it steals from the other end of another worker's deque, taking an older task, often a larger remaining piece in divide and conquer, so steals are rare and owners and thieves seldom collide. Locally forked work avoids one central queue, although external submissions also use pool queues, and load balances itself even when pieces are uneven.

In a fixed pool, a task that calls get() on a child future simply blocks its thread; once every thread is a blocked parent, children in the queue never run. In fork/join, a joining worker may execute the child or help related work; if it must wait, the pool can attempt compensation. This supports the intended acyclic task tree. It does not guarantee progress through a dependency cycle, unmanaged blocking, or a parent holding a lock the child needs. Helping is a scheduling mechanism, not a deadlock proof.

Numbers
A batch job spends 5 percent of its time in sequential setup and 95 percent in perfectly parallel work. What is the best speedup on 16 cores, and on unlimited cores? What would you work on first?
Model answer

Normalize the original one-core time to 1. On 16 cores, time is 0.05 + 0.95 / 16 = 0.109375, so speedup is about 9.14. On unlimited cores the limit is 20. At 16 cores, the parallel term 0.059375 is still slightly larger than setup 0.05. Halving setup while keeping the same parallel work gives time 0.025 + 0.95 / 16 = 0.084375, or 11.85 times the original baseline. Doubling to 32 cores gives 1 / (0.05 + 0.95 / 32) = 12.55. Here more cores give the larger ideal gain, but cost, actual scaling and the effort to reduce setup determine which I choose. I would profile before spending either engineering time or cores.

"Walk me through fork/join and work stealing. Why does joining a child usually work here when waiting in a fixed pool can deadlock?"

  • Describe default owner LIFO access and stealing older tasks from the opposite deque end

  • Explain cooperative joining and contrast it with every fixed-pool worker blocking on queued children
  • Limit the progress claim to suitable acyclic dependencies without blocking locks or unmanaged I/O
  • Distinguish a bounded C++ async recursion from a reusable work-stealing pool
How a senior would say it
Fork/join divides one computation into independent pieces and combines their results. I stop splitting below a cutoff. Above it, I fork one half, compute the other on the current thread, and then join. That exposes parallel work while keeping the current worker useful. In the default work-stealing policy, each worker pushes and pops at its own end of a deque, newest first. An idle worker takes older work from the opposite end. For recursive splitting, older work often represents a larger branch, so a steal gives the worker plenty to do. Opposite ends reduce contention, although the last item still needs synchronization. A joining worker can help execute the child or related work, and the pool can attempt compensation when a worker must wait. Compare that with a fixed pool where every worker blocks on a child future and all the children remain queued. There is nobody left to execute them. This is not a general deadlock guarantee. A cycle between tasks, or a parent holding a lock its child needs, can still deadlock. Blocking network calls also consume workers. In C++, our capped async example uses separate threads and ordinary future waits; it demonstrates divide and conquer, but it does not implement work stealing.

Likely follow up: What would change if the tasks were mostly waiting for HTTP responses rather than computing?

"A teammate replaced a loop with a parallel reduction. It is slower and sometimes returns a different result. What do you check?"
What a strong answer covers

  • Check associativity, neutral identity, floating-point regrouping and integer overflow
  • Use private partial results and completion synchronization before combining

How a senior would say it
I would investigate correctness first, then performance. A parallel reduction needs independent partial results and a valid combining operation. If workers update one shared counter or append to one ordinary list, I would remove that shared mutation. I would also check the algebra: subtraction is not associative, and a nonzero identity for addition can be contributed once per partition. Different floating-point results do not necessarily mean a race. Regrouping changes rounding. Integer sums need range checks too: Java wraps on overflow, while signed C++ overflow is undefined behaviour. I would keep the input stable, compute private partial results, and join before combining them. For performance, I would compare against the original loop with representative input and a warmed-up JVM. Small tasks, expensive splitting, ordered operations and memory bandwidth can erase the benefit. I would vary the cutoff and worker count instead of assuming more tasks help. In Java, I would also inspect common-pool contention and blocking calls. Unrelated parallel streams and async stages can compete there; isolation may justify an explicit executor.
