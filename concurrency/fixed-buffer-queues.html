Queues inside a fixed buffer

Build bounded rings, prove single-producer single-consumer ordering, and share fixed storage between two FIFO queues with a free list.

Asked atRubrikGoogleMicrosoft
Before this:Producer and consumer with a bounded bufferCondition variables and monitors

Rubrik's senior screens have asked for a FIFO queue inside a fixed-size buffer with no dynamic allocation, then for multiple threads, then for two queues sharing one buffer of hundreds of megabytes with minimal waste. Google and Microsoft ask the circular buffer and its locking too. This lesson builds each step.

In plain words

Think of a conveyor belt sushi bar with eight plate spots going round. The chef puts a plate on the next free spot; diners take the oldest plate; both just keep walking round the same eight spots. Nothing new is built while the restaurant runs, and when all eight spots hold a plate, the chef waits. That is a ring buffer.

Now two restaurants share one parking area of numbered bays. Each restaurant keeps its own waiting line of cars, and every car holds a slip saying "the next car in my line is in bay 17". A board at the gate lists the empty bays. A car takes any empty bay from the board and joins its line; a car that leaves puts its bay back on the board. Neither restaurant owns half the lot: space flows to whichever line needs it. That is two queues in one buffer with a free list.

The ring buffer

A ring buffer is an array of capacity slots plus two indices: head (the next slot to read) and tail (the next slot to write). Writing puts the value at tail and moves tail forward; reading takes it from head and moves head forward; both wrap to 0 at the end of the array. The index updates take O(1) work and payload storage never grows after construction. Blocking operations can still wait indefinitely. Java lock contention and condition waits can allocate internal waiter nodes, so a fixed array alone is not a promise of zero runtime allocation.

The one subtle question is how to tell full from empty, because in both cases head == tail. Three standard answers:

ConventionEmpty whenFull whenTrade-off
Keep a countcount == 0count == capacitySimplest; one more field to update
Leave one slot unusedhead == tail(tail + 1) % capacity == headNo count, but one slot is always wasted
Logical counters; index is counter & (capacity - 1) for a power-of-two capacitytail == headtail - head == capacityNo wasted slot and no count; the SPSC version below uses modular counter arithmetic

At a billion increments per second, a signed 64-bit counter reaches its sign boundary in about 292 years, but correctness should still cover wraparound. The SPSC example uses defined modular arithmetic: Java long arithmetic wraps, and C++ uses unsigned uint64_t. A positive power-of-two capacity, far below half the counter range, keeps the bounded distance and low-bit index meaningful across wraparound; signed C++ overflow would be undefined behaviour.

Making it thread-safe

The multi-threaded version is the bounded buffer you already know, with the deque replaced by the array: one lock guards slots, head, tail and count as a single invariant, producers wait for "not full", consumers wait for "not empty", and every wait is a loop. The demo below pushes 30,000 items through 8 slots, so the indices wrap thousands of times.

Microsoft has asked candidates to find the mistake in a circular buffer's locking. When reviewing such code, look for: size() or isEmpty() reads count without the lock and a caller acts on the stale answer; separate head and tail locks with a shared count that neither protects; a single condition with notify (one) where producers and consumers both wait, so a producer's signal wakes another producer; and an if instead of a loop around the wait. Even a locked isEmpty() is only a snapshot; another consumer can remove the item before take(). Use one atomic poll when you need a nonblocking check and removal.

One producer, one consumer: no lock at all

If exactly one thread produces and exactly one consumes, the ring needs no lock. Look at who writes what: only the producer ever moves tail, only the consumer ever moves head. Each index has a single writer, so there is no read-modify-write race to prevent. What remains is visibility and ordering: the consumer must not see the new tail before it can see the value written into the slot. That is exactly what a release store and an acquire load provide: the producer writes the slot, then stores tail with release; the consumer loads tail with acquire, then reads the slot. This is a single-producer single-consumer queue, useful when a logging or audio pipeline has exactly one producer and one consumer. Safely publish the constructed ring before either thread starts, and keep it alive until both have stopped.

Three details carry the correctness argument. The slot is written before the release store of tail, so anyone who sees the new tail through an acquire load also sees the slot (the acquire and release pairing). The consumer releases head after reading the slot, so the producer, which loads head with acquire, never overwrites a slot that is still being read. And the producer reads its own tail with a plain or relaxed load, because no other thread writes it. The C++ alignas(64) separates the indices on machines with 64-byte cache lines, reducing false sharing. It is a tuning assumption, not a portable cache-line size: larger lines may require more padding. Java has no portable object alignment guarantee; dummy fields alone are not a portable proof of separation.

Each offer or poll attempts bounded work and returns false on observed full or empty; the retry loops in the demo may spin indefinitely if the peer stops. Thread.onSpinWait() is a processor hint, not a yield or a synchronization operation. C++ atomics are not universally lock-free: check is_lock_free() on the target before claiming that progress property.

The moment there are two producers, this breaks: both can read the same tail, write the same slot, and publish the same index. Multiple producers need a lock, or a compare-and-swap on tail plus a per-slot flag saying when the slot's data is ready, which is a much harder design. In an interview, say exactly where single-writer stops holding.

Two queues in one buffer

Rubrik's follow up: two FIFO queues share one buffer (one report says 100 MB to over 1 GB), each must stay FIFO, space should shift with usage, and waste should be minimal. The tempting answers fail:

  • Split the buffer in half. Simple, but if one queue holds 90 percent of the traffic, half the buffer sits idle while the busy queue blocks.
  • Grow one queue from each end. That works for two stacks, not two queues: a FIFO queue moves through memory as it is used, so the two would collide in the middle.

The answer that works is a free list of slots. Every slot has a value and a next index. Unused slots are chained into the free list. Each queue is a linked list of slots with its own head and tail. Enqueue pops any free slot, fills it and links it after the queue's tail. Dequeue unlinks the head slot, reads it and pushes the slot back on the free list. Each operation makes O(1) index updates without allocating an element node, and a slot freed by one queue can be used by the other a moment later. The examples use two arrays for clarity; if the contract literally supplies one byte buffer, carve value and link regions out of that buffer and count both against the capacity. In C++, respect alignment and object lifetimes; Java can use absolute ByteBuffer access with a specified byte order.

For threads, one lock guards everything (the free list is shared by both queues, so one lock is the honest granularity), with one "not empty" condition per queue and one "not full" condition for the whole buffer. After acquiring the lock, a producer waits for space only when every slot is used; a consumer waits for data while its own queue is empty. Lock contention can block either operation too. Each slot belongs to exactly one of three disjoint lists: queue 0, queue 1, or free. Their lengths sum to the capacity, empty queues have both ends equal to -1, and every nonempty tail has next equal to -1.

Worked example: the arrays after five operations

Six slots, queues A and B, every slot free at the start (free list 0, 1, 2, 3, 4, 5).

OperationSlot usedQueue AQueue BFree list
enqueue(A, 10)00 (10)empty1, 2, 3, 4, 5
enqueue(B, 20)10 (10)1 (20)2, 3, 4, 5

enqueue(B, 21)0 again; next[1] = 02 (11)1 (20), 0 (21)3, 4, 5

Slot 0 served queue A and then queue B. Within each queue the next links keep FIFO order even though the slots are scattered through the array: queue B reads 20 from slot 1 and then follows next[1] to slot 0 for 21.

Minimal waste for a very large buffer

For 1 GiB of payload containing 4-byte ints, a 4-byte next index per slot doubles the storage: 268,435,456 values and another 1 GiB of links. If the total budget is 1 GiB including links, only half that budget remains for values, before other metadata. That is the "minimal waste" follow up, and the fix is to link chunks instead of slots, which is also what the Rubrik SSE candidate did with lists of fixed-size chunks:

  • Carve the buffer into chunks of, say, 1,024 values (4 KiB). Each chunk has one next index. The free list and each queue are lists of chunks.
  • Each queue keeps a head chunk with a read offset and a tail chunk with a write offset. Enqueue writes into the tail chunk and takes a new chunk from the free list only when it is full; dequeue frees the head chunk once it is drained. When the last value leaves a queue, return even a partly filled last chunk and reset both ends; otherwise small queues can retain empty chunks forever.
  • Overhead: one 4-byte link per 4 KiB chunk is about 0.1 percent, 1 MiB for 1 GiB of payload. Waste: at most a partly filled head chunk and tail chunk per queue, a few KiB each.

The locking is unchanged: one lock over the free list and both queues' ends. If the two queues are very hot, each queue can get its own lock for its own chunks, with the free list behind a third lock that is touched when a chunk changes ownership, roughly once per 1,024 operations during steady streaming. Always acquire the queue lock before the free-list lock, and never take a queue lock while holding the free-list lock.

Shutdown, deadlines and tests

The blocking demos use fixed item counts and assume every worker runs to completion. For a reusable service add a closed flag under the same lock: puts reject after close, takes drain queued items and then report end of stream, and close wakes every producer and consumer. A failure that abandons the pipeline must wake peers too; merely interrupting one Java producer can leave consumers waiting for items that will never arrive.

For timed operations, use one monotonic deadline and recompute the remaining wait after every wakeup. Test capacity one, many wraps, empty-to-nonempty and full-to-nonfull transitions, invalid capacities and queue ids, close with waiters, and each producer's FIFO sequence. A correct sum alone does not prove no duplicates or losses: track unique item ids. For SPSC, also start counters near wraparound and verify both publication and slot reuse under ThreadSanitizer.

Common mistakes

  • Full and empty confused. With only head and tail modulo the capacity, head == tail means both. Keep a count, leave a slot empty, or use counters that only grow.
  • Allocating per element. A LinkedList, a std::list or new Node per enqueue breaks "no dynamic allocation". Links must be indices into arrays allocated once.
  • Reading the count without the lock. if (!ring.isEmpty()) ring.take() from two consumers is a check-then-act, and the unlocked read is a data race in C++.
  • Calling the SPSC ring from two producers. The SPSC design is correct only with one thread on each side; a second producer invalidates it and creates undefined behaviour in C++.
  • A fixed split between two queues. It meets the letter of the question and fails "space shifts with usage".
  • Forgetting the other queue's waiters. When a slot is freed, a producer for either queue may be waiting for it. Signal the shared "not full" condition, not a per-queue one.

In the interview

The Rubrik sequence, as reported: a FIFO of ints in a fixed buffer with no dynamic allocation (a commenter adds O(1) put and get), then "support multiple threads", then "two queues share one buffer of 100 MB to 1 GB, each FIFO, space shifting with usage, minimal waste". The cited Google and Microsoft reports cover a circular buffer and its locking; they do not establish a ceiling on possible follow ups.

The buffer is an array of slots, each with a value and a next index. Free slots form a free list, and each queue is a linked list of slots with its own head and tail, so enqueue pops any free slot and links it after the tail, and dequeue unlinks the head and returns the slot to the free list. Both make O(1) index updates with no per-element allocation, and space moves to whichever queue needs it. One lock guards the free list and both queues, with a not-full condition for the buffer and a not-empty condition per queue. For a gigabyte buffer I would link fixed-size chunks rather than single slots, so the links cost about 0.1 percent instead of doubling the memory.

Follow ups: "one queue's producer is flooding; the other queue starves for space" (reserve a minimum number of slots per queue, or cap each queue's share), "make the single-queue version lock-free" (SPSC with acquire and release if there is one producer and one consumer; otherwise say how much harder MPMC is), and "why a power-of-two capacity?" (the index becomes a mask, and the low-bit index still works when the counters wrap).

Senior depth

  • Multi-producer, multi-consumer without locks. A bounded design can give each slot a sequence number that identifies its reuse generation. A producer checks availability, claims a position with compare-and-swap, writes, and release-publishes the slot; a consumer acquire-observes readiness before reading and releasing the slot for reuse. Reserving a position is not publishing a value. A stalled owner can block progress behind its reservation, so using CAS does not by itself prove lock-freedom; explain the particular algorithm's progress guarantee.
  • Payload lifetime and exceptions. These examples store ints. A Java queue of references should clear removed slots to avoid retaining objects. For generic C++ payloads, define construction, destruction and move-failure handling before unlinking a slot; an exception must not lose that slot from both the queue and the free list.
  • Batching through rings. The LMAX Disruptor and similar designs let consumers read many slots per acquire load and producers claim many slots at once, which cuts the synchronization per item.
  • Fairness between two queues. A shared buffer trades isolation for utilization. If one tenant must not be able to starve the other, give each queue a guaranteed reserve: a producer may take a free slot only if doing so leaves enough free slots to cover the other queue's unused reserve.
  • Memory layout. Chunked lists keep values contiguous, which matters for cache behaviour on a multi-gigabyte buffer, and allocating the whole buffer at startup (and touching its pages) reduces initial page faults on the hot path. It cannot prevent later paging or guarantee real-time latency.

Key takeaways

  • A ring buffer is an array with a read index and a write index that wrap; decide up front how you tell full from empty.
  • For many threads, one lock guards the array and the indices, with not-full and not-empty conditions.
  • With one producer and one consumer, each index has a single writer, and release and acquire on the indices replace the lock.
  • Two queues share one buffer through a free list of slots, each queue a linked list of slot indices: O(1) index updates, fixed element storage, space follows demand.
  • For huge buffers, link chunks rather than slots so the links cost a fraction of a percent.

Quick check

Answer each question, then read why. Your score is saved for your module test.

A ring of capacity 8 keeps head, tail and count. Right now head = 6, tail = 2 and count = 4. Which slots hold the queued items, oldest first?
Why. Items run from head forward for count slots, wrapping at the end of the array: 6, 7, then 0 and 1. tail = 2 is the next slot to write, consistent with 6 + 4 wrapping to 2. A tail below the head is normal after the write index wraps.
A ring allows all capacity slots to be occupied but stores only head and tail modulo capacity, with no count or full flag. What goes wrong?
Why. After capacity writes with no reads, tail wraps right back onto head. Without more information, full and empty look identical. The fixes are a count, leaving one slot always empty, or counters that only grow and are reduced modulo the capacity when indexing.
In the single-producer single-consumer ring, why can the producer read tail with a plain or relaxed load but must read head with acquire?
Why. A thread always sees its own writes, so the producer needs no ordering to read tail. The consumer releases head after reading a slot; the producer's acquire load of head pairs with it, so a slot is never overwritten while it is still being read. The same pairing in the other direction publishes the slot's value to the consumer.
Two producer threads start calling offer on the SPSC ring at the same time. What can happen?
Why. The design is correct only because tail has a single writer. Two producers can load the same tail before either publishes, then both write the ordinary slot. Java can lose a value; the C++ data race permits undefined behaviour, not merely a predictable lost write. Multiple producers need a lock or a compare-and-swap protocol with per-slot readiness flags.
Two FIFO queues share one buffer of N slots through a free list. Ignoring lock contention and waiting time, what is the update cost, and when does enqueue wait for space?
Why. Popping and pushing the free list, and linking at a queue's tail or unlinking at its head, are constant-time pointer updates on index arrays. No slot is reserved for either queue, so a producer blocks only when the free list is empty, which is what lets space shift with usage.
Which designs satisfy "a FIFO queue whose payload and link storage never allocate after construction"? Select all that apply.Select all that apply
Why. Both correct options allocate everything up front and then only move indices. Ordinary linked lists allocate nodes. The growable deques in the option allocate additional storage when expanding; a size check alone does not preallocate nodes or blocks. This question concerns data storage, not internal lock waiter allocations.
Java onlyThe Java SPSC ring uses setRelease and getAcquire on AtomicLong. What would happen if both indices used ordinary get() and set() instead?
Why. get and set are volatile reads and writes, which include acquire and release ordering and more (a total order). Release and acquire are the minimum the algorithm needs, which is why tuned queues use them (or lazySet), but the volatile versions are a safe default in an interview.
C++ onlyOn a target with 64-byte cache lines, why are the C++ SPSC indices declared alignas(64)?
Why. Correctness does not need this extra alignment; performance may benefit. Two threads writing different variables on one 64-byte line force the cache line to ping-pong between cores. Separating them is the standard fix; C++17 also offers std::hardware_destructive_interference_size as an implementation-provided estimate where the library supports it; it is not available in every libc++ build. A machine with larger cache lines needs a different layout.

Checkpoint

Write your own answer first. Then compare with the model answer, or ask Bar Raiser to mark it like an interviewer would.

Numbers
Two queues have 1 GiB of payload storage for 4-byte ints; link metadata is additional. (a) How much extra memory does a slot-level free list with a 4-byte next index per slot need? (b) With chunks of 1,024 values and one 4-byte link per chunk? (c) In the chunked design, roughly how much space can be wasted at any moment?
Model answer

(a) 1 GiB holds 2 to the power 30 bytes, so 2 to the power 28 ints, about 268 million slots. One 4-byte index each is another 1 GiB, so the links double the memory.

(b) Chunks of 1,024 ints are 4 KiB, so there are 2 to the power 18 chunks, 262,144 of them. One 4-byte link each is 1 MiB, about 0.1 percent of the buffer.

(c) Each queue can have a partly read head chunk and a partly written tail chunk, so at most about 2 chunks per queue, 4 chunks in total, about 16 KiB, small at this scale. The trade is that a queue holding a single value still occupies a whole 4 KiB chunk.

Write code
Single-threaded first, as the interviewer asks: write a fixed-capacity int queue with O(1) offer (returns false when full) and poll (reports empty when empty) and no allocation after construction.
Model answer

Java reuses a caller-owned one-element array and returns a boolean; OptionalInt.of would create a wrapper unless the JIT eliminates it, so it cannot promise no allocation. C++ std::optional<int> contains the int inline and needs no separate allocation. The Java output array must be non-null and have at least one element. For many threads, wrap both methods in one lock and turn the full and empty returns into waits on two conditions.

Design
In the two-queue buffer, queue A's producer is very fast and its consumer is slow. A's queue grows until it holds every slot, and queue B's producer blocks even though B's queue is empty. The interviewer asks you to prevent B from starving. Propose a fix and its cost.
Model answer

Give each queue a guaranteed reserve, say R slots. Track how many slots each queue holds. A producer for queue q may take a free slot only if, after taking it, the free slots still cover the other queue's unused reserve: free minus 1 must be at least max(0, R minus used by the other queue). Otherwise it waits on the not-full condition. So A can grow into everything except B's unused reserve, with 2 * R <= capacity and R > 0, so A cannot consume B's unused reserve. This protects capacity, not scheduling fairness or progress when B's own consumer stops.

The cost is utilization: up to R slots may sit idle while A is blocked, and the choice of R is a policy decision (equal reserves, or proportional to expected traffic). Signalling also changes: use signalAll or notify_all on the shared not-full condition when capacity is released. A single signal can choose a producer whose reserve predicate is still false and leave an eligible producer asleep. Every woken producer re-checks its own predicate; alternatively, maintain separate conditions and explicitly wake eligible queues.

Say it out loud

Interviews are spoken. Answer each question out loud as if the interviewer just asked it. Tandem transcribes you on this Mac, word for word, measures your pace, fillers and pauses, and Bar Raiser scores what you said and how you said it.

Out loudabout 60 s
"Design a bounded queue in a fixed array. How do you make it safe for several producers and consumers?"
What a strong answer covers
  • Define head, tail and count with a positive fixed capacity
  • One lock protects slots and all queue metadata
  • Producers wait while full and consumers while empty, using separate conditions
  • Update the invariant before signalling and recheck after every wakeup
  • Close wakes all waiters and allows consumers to drain
  • Distinguish fixed payload storage from runtime waiter allocations and test unique ids
How a senior would say it
I use a fixed array with a head index, a tail index, and a count, all protected by one lock. Head identifies the next value to remove, tail the next slot to fill, and count distinguishes empty from full when the indices are equal. Producers wait while count equals capacity; consumers wait while count is zero. I use separate not-full and not-empty conditions, always in loops, because a wakeup does not reserve a slot or an item. Each operation updates the slot and metadata before signalling the opposite side. For shutdown I set a closed flag under the lock, reject new puts, let takes drain, and wake everyone. The data array never grows, but Java's lock machinery may allocate waiter nodes. I would test capacity one, repeated wrapping, unique item identities, per-producer order, and closing while both kinds of caller are waiting.

Likely follow up: Would a locked isEmpty() followed by take() make a nonblocking removal safe?

Out loudabout 60 s
"There is exactly one producer and one consumer. Explain both memory-ordering directions in your ring."
What a strong answer covers
  • Producer alone writes tail; consumer alone writes head
  • Slot write precedes release publication of tail
  • Consumer acquires tail before reading the slot
  • Consumer releases head after reading; producer acquires head before reuse
  • Own-index accesses need no cross-thread ordering
  • Power-of-two modular counters survive wrap; extra producers invalidate ownership
How a senior would say it
The lock can go because each index has one writer, but ordering must work in both directions. The producer writes the value into a slot, then release-stores the new tail. The consumer acquire-loads tail before reading that slot, so observing publication also makes the value visible. After reading, the consumer release-stores head. The producer acquire-loads head before reusing the slot, ensuring it cannot overwrite data while the consumer still reads it. Each thread can read its own index with a plain Java or relaxed C++ atomic access. I validate a positive power-of-two capacity and use defined modular counter arithmetic so wraparound preserves both the distance and masked index. Two producers break the ownership proof: both can claim one slot, and C++ then has undefined behaviour. Failed offers and polls return immediately; a surrounding retry loop can still wait forever if its peer stops.

Likely follow up: Why is atomically incrementing tail before writing the slot insufficient for multiple producers?

Out loudabout 60 s
"Two FIFO queues must share one large buffer with little wasted space. What would you build?"
What a strong answer covers
  • Use queue head and tail indices plus one shared free list
  • Enqueue takes a free slot; dequeue returns it while preserving FIFO links
  • One lock protects the disjoint-list ownership invariant
  • Shared space condition and per-queue data conditions govern waits
  • Link chunks to reduce metadata, accepting bounded partial-chunk waste
  • Reserve capacity for isolation and wake all producers when admission predicates differ
How a senior would say it
I would let both queues draw storage from one free list instead of reserving half the buffer for each. Each queue has its own head and tail. Enqueue removes a free slot and links it after that queue's tail; dequeue removes the head and returns its slot to the free list. One lock protects the invariant that every slot belongs to exactly one queue or the free list. Consumers wait on their own queue's data condition, while producers share a space condition. For a large buffer, I link chunks of values rather than individual values. One four-byte link per four-kibibyte payload chunk costs about a tenth of a percent, at the cost of partially used end chunks. If one queue needs guaranteed capacity, I add a reserve. Producers then have different admission predicates, so a shared single signal is insufficient; I wake all and recheck.
